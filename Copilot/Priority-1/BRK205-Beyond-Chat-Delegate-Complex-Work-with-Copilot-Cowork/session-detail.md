# BRK205 Beyond Chat: Delegate Complex Work with Copilot Cowork

## 1. はじめに

このセッションは、Copilot の新しいアプリケーション **Copilot Cowork** を紹介する 45 分のブレークアウトです。Chat が「質問して答えをもらう」アシスタントだとすると、Cowork は「ゴールや成果物を伝えると、複数のステップをまとめて進めて完成物を返してくれる」という位置づけで説明されています。

中心になるのはライブのウォークスルーです。プロダクトマネージャー（PM）が月曜の朝に Cowork を開き、顧客の不満の発見から、仕様書の作り直し、ロードマップへの登録、プロトタイプの作成、その後のフォローアップの自動化までを一気通貫で進める流れが示されます。あわせて、モデルを自動で使い分ける **Auto**、利用量に応じた課金（usage-based billing）に対する IT 管理者向けのガバナンスや FinOps の考え方も紹介されます。

> 補足：発表では、ウォークスルーで見せた機能は「利用可能になっているか、Ignite の期間中にロールアウト中」で、今後数週間で試せるようになると説明されています。ただし、declarative agents については、別の箇所で「準備中（in the pipeline）」とも述べられています（5.6、7 章を参照）。

## 4. 発表者が伝えたいメッセージ

発表者が繰り返し伝えているのは、「ユーザーが各ステップをつなぐ『糊（glue）』でなくなる」という点です。Chat では、やり取りのたびにユーザーが文脈を持ち、次の手を決めます。Cowork では、ユーザーが成果を渡すと、Cowork が検索、下書き、アプリをまたぐ操作を自分で計画して実行し、完成した作業を返します。

ただし、人間が蚊帳の外になるわけではありません。メッセージやメールの送信、同僚やグループへの資産の共有、Teams のグループチャットでの投稿など、重要なアクションの前では Cowork が承認を求めて止まります。発表の言い方では、ユーザーは「すべてのステップを自分で回す」立場から、「結果とビジネス上の成果物だけをレビューする」立場に移ります。

もうひとつのメッセージは、モデル選択の自動化です。目標は「最も安いモデルを選ぶこと」ではなく、「その仕事に合った知能を選ぶこと」だと説明されています。

## 5. 発表内容の詳細

### 5.1 Chat と Cowork の違い

Chris 氏は、左に Chat、右に Cowork を置いた比較で違いを説明しています。Chat は、ユーザーが尋ね、Copilot が答え、ユーザーが追加で尋ねる、というやり取りの繰り返しです。何かを考えている最中には向いていますが、ターンの間で文脈を運ぶのも次の判断をするのもユーザーです。

Cowork はユーザーからアウトカムを受け取り、検索、下書き、アプリをまたぐ操作を自分で計画します。Cowork はすでにユーザーのファイルやアプリにつながっており、ブラウザーも使え、日常の業務で使うさまざまなツールにアクセスできます。Chris 氏は、違いは「Cowork がデータを整理し、推論し、アクションまで取ること」だと述べています。

### 5.2 Cowork の機能（ウォークスルーで紹介されたもの）

ウォークスルーで登場した Cowork の機能を、先に整理します。

| 機能 | 発表での説明 |
| --- | --- |
| Suggested tasks（提案されたタスク） | Cowork は毎日、ユーザーが来る前にメール、会議、Teams、チャットを読み、ユーザーがしばらく気づいていないパターンを見つけて、タスクの開始を提案する |
| Skills | チームの進め方を組み込んだ再利用可能な手順。誰でも、いつでも数秒で使える。組織内で同じ言葉・同じ形式をそろえ、やり直しを減らす効果があると説明されている |
| Plugins | Microsoft のデータパイプ（Work IQ）にあるナレッジグラフ、Teams、メールなどには自動でアクセスできる。それ以外のデータソースは plugins で接続でき、ユーザー自身が持つアクセス権の範囲で、同じアクセス制御を保ったまま使える |
| Projects | 文脈、ファイル、指示、過去のタスクを 1 か所に蓄積する場所。Cowork が文脈を構築し、記憶し、ユーザーも簡単にアクセスできる |
| 承認の確認 | 機密データにアクセスするときにも、確認と承認を求める |
| Declarative agent の呼び出し | 他チームが作った declarative agent を Cowork から呼び出せる（新機能として紹介） |
| Browser tool | ローカルでログイン済みの Edge ブラウザーを使い、任意の Web サイトを操作できる |
| Scheduled prompts / automations | 定期的、あるいはイベント駆動でタスクを走らせる |

### 5.3 ライブウォークスルー：PM の月曜の朝

Pratyusha 氏は、「Cowork を紹介するには自分たちが実際にどう使っているかを見せるのが一番」として、自分たちのチームが日々 Cowork で Cowork を作っていると述べたうえで、Caldova という会社の PM「Andrei」を演じます。Caldova は IT 管理者がデバイスやデバイスの健全性、インベントリを管理する Caldova Console を作っており、アラートが大量に出る製品です。ストーリーは、顧客の問題の発見から、エンジニアリングチームへのプロトタイプ引き渡しまでを Cowork が支える、というものです。

詳しい手順は「6. デモ・手順」に書きます。ここでは、ウォークスルーのポイントだけを整理します。

- 受信箱を開く前から Cowork が待っていて、複数の顧客がアラートがうるさいと指摘している、と教えてくれる
- Skeptic という skill でアイデアを検証する
- Salesforce から顧客データを取り、仕様書が本当に課題を解いているかを確認する
- 仕様書の作り直し、デザインルールの検証、ロードマップへの登録、プロトタイプ作成を 1 つのワークフローとして委任する
- 最後に、顧客フィードバックを継続的に取り込む自動化を設定する

### 5.4 Auto：モデルとエフォートの自動選択

Pratyusha 氏のワークフローが裏で動いている間に、Chris 氏が Auto を説明しています。ウォークスルーでは、モデルを一度も変えず Auto のままで、内容も難易度もさまざまなタスクを実行していたと説明されています。

Cowork には、モデル、推論の強さ（reasoning effort）、fast mode を使うかどうかなど、体験と出力を左右する設定があります。fast mode は最近リリースされ、fast に使えるモデルで一般に利用可能になったものと紹介されています。Auto は、これらを意識しなくてもよくするための機能です。品質、速度、コストの観点で、結果を犠牲にせずに体験を最適化することを目指しています。

Auto は、モデルと effort を選ぶだけのものではなく、「ゴールや成果を渡せば、あとは任せられる」ことがビジョンだと説明されています。タスクの各部分を、適切なモード、モデル、effort に動的に割り当てます。

Chris 氏が示した例は、顧客の更新（renewal）に向けたスライドデッキづくりです。

1. まず Auto が仕事のモードを選ぶ（この例では Cowork）
2. 次に、作業を実行してサブタスクに分解する「リードモデル」を選ぶ（この例では Opus 5.5、high の reasoning effort）
3. サブタスクごとに、それぞれのモデルと effort が割り当てられる

サブタスクの割り当て例は次のとおりです。

| サブタスク | 割り当て |
| --- | --- |
| ファイルとメモの収集 | GPT-5.5（medium effort） |
| より深い推論が必要なリサーチ | Opus（high effort） |
| ビジュアル（挿絵）の生成 | GPT Image 2.5 |
| スライドの作成 | Opus |

> 注意：モデル名の綴りと版数（Opus 5.5、GPT-5.5、GPT Image 2.5）は、音声認識の都合で表記が確定できません。聞こえたとおりに記載しています。

この割り当ては、社内の評価（internal evals）に基づいて、特定のタスクに向くモデルを選んでいるものだと説明されています。比較対象として挙げられた「高コストなやり方」は、すべてのステップを最も強力なモデルで最高の effort で実行することです。

発表で挙げられた社内テストの数字は次のとおりです。

- 最も強いモデルは、適切なサイズのモデルより **コストが 2.5〜5 倍**かかる。毎回のリクエストが同じ固定のコンテキストを運び、価格差はそのコンテキスト部分にあるため
- 複雑なリクエストでは、軽いモデルは出力品質の面で **10〜20 ポイント多く失敗する**

### 5.7 ガバナンスと FinOps for AI

最後に Chris 氏が、ガバナンスと AI の FinOps を説明しています。

**IT 管理者ができること**

Microsoft 365 管理センター（Admin Center）で、IT 管理者は次の操作ができると説明されています。

- usage-based services を有効にする
- テナント、グループ、ユーザーのレベルで支出ポリシーを設定する（ハードリミット、アラート、モデルファミリー単位でのモデル選択）
- クレジットのリクエストを承認する

**ビジネス側の役割**

消費型課金の管理では、ビジネス側も重要なパートナーです。予算を持つところで価値を測定します。ビジネス部門やチームリードは、IT に問い合わせなくても、自分のチームのクレジット使用量、傾向、集中度のほか、Cowork のタスクカテゴリ、assisted hours、クレジットあたりの提供価値を確認できます。

**ユーザーへの透明性**

ユーザーには、タスクのコストと残りの上限を示す live meter が表示されます。履歴や、アプリ内での追加リクエストもでき、ガードレールの内側で作業を止めずに進められます。

発表では、統制、測定、最適化を「3 つの別々のプロジェクトではなく、1 つにつながったレイヤーでの共同作業」と表現しています。

**管理者が使えるレバー**

- 使えるモデル
- plugin やコネクタによる拡張性
- アプリ構築やブラウザー利用といった高度な機能
- メッセージ送信、システム・オブ・レコードを変更する操作などに対する承認

**セキュリティとコンプライアンス**

Cowork は Microsoft 365 のセキュリティとコンプライアンスの基盤を、Purview を通じて継承します。セキュリティチームがすでに運用している DLP エンジン、ポリシー、ラベル、監査証跡が同じように適用され、インサイダーリスク、eDiscovery、データ損失防止、データライフサイクルなども含まれると説明されています。時間の都合で詳細は省かれ、関連セッションの参照が案内されました（セッション名はトランスクリプトからは確認できません）。

## 6. デモ・手順

このセッションには、**Pratyusha 氏によるライブのデモ（ウォークスルー）があります**。発話では "Let's go to Cowork. All right. This is Cowork." などと画面を切り替えて進められています。録音は音声だけのため、画面上の細部（ボタン名やレイアウト）は確認できません。以下は、語られた順番に沿った内容です。プロンプトの全文は読み上げられておらず、ここに書くのは説明された要旨です。

### 6.1 設定（シナリオ）

Pratyusha 氏は、Caldova の PM「Andrei」として進めます。Caldova Console は、IT 管理者がデバイス、デバイスの健全性、インベントリを管理する製品で、何が問題か問題でないかを知らせるアラートが多数出る製品です。

### 6.2 手順

1. Cowork を開く。Cowork は Chat と並んで Home から使える。月曜の朝で、まだ受信箱を開いていないのに、Cowork が「複数の顧客がアラートがうるさいと指摘している」と教えてくれている。
2. その提案（suggested task）をクリックして実行する。Cowork が、メール、Teams、複数のプラットフォームのメッセージを調べ、重要なパターンを示す。Fabrikam が「アラートがうるさすぎる」と言っているという内容が見つかる。
3. 解決案の冗談として「チャイムを穏やかにする」「エレベーターミュージックを入れる」を出し、続けて **Skeptic** に確認する。Skeptic は、チームが長年かけて磨いてきた「プレッシャーテスト（アイデアを疑い、適切な問いを投げる）」のプロセスを skill に組み込んだもの。実際のチームなら複数回の会議が必要な問いを、数秒で投げてくれる。
4. Skeptic は「何を解決しようとしているのか」「顧客は実際に何と言っているのか」と問い返す。そこで顧客の声を調べるために、プロンプトをコピーして使う（「入力するところを見せずに済むように」と説明）。内容は、Salesforce から適切なデータを取ってくるよう依頼するもの。
5. 顧客データは Salesforce にあるが、Cowork がどうアクセス・収集するかは意識しなくてよい、と説明される。「このオブジェクトを探せ」「このクエリを実行しろ」とは指示せず、営業チームにデータ提供を頼むときと同じ言い方で依頼している。
6. Customer Voice という skill が、チームが使う形式で必要な詳細を引き出す。機密データにアクセスするときには、承認の確認も求められる。
7. 返ってきたデータを見ると、単純な問題ではなく、顧客が関心を持つ複数のディールに影響していることが分かる。Pratyusha 氏は「PM として、正しいことに集中しているかを確かめたかったデータだ」と述べる。
8. この取り組みは今後も続くものなので、タスクを「alert redesign」という既存の **project** に移す。Project には文脈、ファイル、指示、過去のタスクが蓄積される。
9. project に移した状態で、現在のアラート仕様書（spec）の内容を確認する。単なる要約ではなく、「顧客の声が分かったので、要件ごとに、現在の仕様書が本当に問題を解いているか教えて」と依頼する。Cowork はチームごとに、これまでの指標を見ながら PM のように優先順位を付け、「この優先度で spec を更新すべき」と返す。
10. ここから先は、プロンプトを重ねて反復する代わりに、一連のタスクを Cowork に **委任**する。依頼内容は、spec を書く、デザインの intake を通す、ロードマップに追加する、プロトタイプを作る、というワークフロー。実行には時間がかかる。
11. 実行中は、Chris 氏が Auto を説明する（5.4 を参照）。

### 6.3 ワークフローの結果

数分後、Cowork が行った作業を Pratyusha 氏が順に確認しています。依頼内容は「文脈がそろったので spec を作り直し、デザインルールに照らして検証し、ロードマップに公開し、チームに共有できるプロトタイプを作る」というものでした。

1. **spec の作成**：問題、ゴール、ノンゴールを含め、構築した文脈全体を踏まえて spec を作り直した。チームが使うのと同じテンプレートと形式を使っており、共有できる状態に近い。
2. **declarative agent の呼び出し**：Caldova のデザインチームは、spec を事前定義されたデザインルールに照らして検証する declarative agent を作っている。通常は、spec をデザインチームに送り、レビューと会議を経てフィードバックを反映するところを、Cowork が declarative agent を呼び出して spec をルールに照らし、フィードバックを反映して反復する。数分で完了した。この機能は「新機能」として紹介されている。
3. **ロードマップの更新**：社内には、古いロードマップツールのように、MCP や plugin を作れないツールが多い。そこでは従来、自動化が止まり、自分でその Web サイトに入力する必要があった。Cowork の browser tool は、ローカルでログイン済みの Edge ブラウザーを使い、ユーザーと同じセキュリティ設定のまま任意の Web サイトに入れる。ここでは、ロードマップを開いて、チームが見る場所に Clear Alerts という項目を追加した。「自分としての、同じ権限での」操作だと説明されている。
4. **アプリの構築**：本来なら、チームに spec を説明し、デザインして何度か反復する必要がある。Cowork は、Caldova Console の見た目に沿ったアプリを実際に作り、エンジニアリングチームにそのまま渡せる形にした。

### 6.4 ループを閉じる（automations）

顧客のフィードバックは数週間にわたって続くため、Pratyusha 氏は「closing the loop」として scheduled prompts（automations）を使います。依頼内容は、アラート関連のフィードバックを監視して spec に取り込むこと、そのあたりの動向を毎日のダイジェストで受け取ることです。Cowork がその設定をしている間に、Pratyusha 氏が全体を振り返っています。

> 補足：振り返りでは、（1）Cowork がパターンを自分で見つけた、（2）Skeptic で優先順位づけの考え方を得た、（3）Salesforce から優先順位づけに必要なデータを取った、（4）spec を作りプロトタイプまで進めた、（5）フォローアップの自動化を設定している、という流れでまとめられました。この流れは PM に限らず、エンジニアやほかの職種でも使えると説明されています。

## 7. 注意点・発表者の気付き

- **承認ステップがある。** メッセージ・メールの送信、同僚やグループへの共有、Teams グループチャットでのやり取りや投稿など、重要なアクションの前で Cowork は止まって承認を求めます。機密データへのアクセスでも確認が入ります。
- **アクセス権はユーザーのまま。** plugins は、ユーザーがアクセスできる範囲で、同じアクセス制御を保って使われます。Browser tool もローカルでログイン済みの Edge を使い、ユーザーと同じ権限・同じセキュリティの下で動きます。
- **コストは管理対象になる。** 最も強いモデルをすべてに使うと、適切なサイズのモデルより 2.5〜5 倍のコストがかかり、軽すぎるモデルでは複雑な依頼で品質が 10〜20 ポイント多く落ちるという社内テストの結果が示されました。Admin Center の支出ポリシーや live meter で、コストを可視化・制限できます。
- **一部の機能は準備中。** declarative agent の呼び出しは「in the pipeline」、Auto の fast mode と Auto による reasoning effort の選択は「coming out soon」です。デモでは declarative agent の呼び出しが見られましたが、発表の投資領域の説明では今後の機能として扱われています。
- ガバナンスの詳細は時間の都合で省略されており、関連セッションへの参照が案内されました。

## 8. 利用者にとっての利点

発表で語られた効果と利点は次のとおりです。

- **ワークフロー全体の短縮**：Pratyusha 氏は、デモのタスクを「複数の会議を挟んで数日かかる仕事」が数分で終わったと説明している。
- **反復の削減**：チームのテンプレートや skills（Customer Voice など）を使うことで、同じ形式・同じ言葉で成果物が出てくるため、やり直しが減る。
- **データソースを問わない自動化**：MCP や plugin が作れない古い社内ツールでも、browser tool を使えば自動化が止まらない。
- **コストと品質のバランス**：Auto が、タスクごとにモデルと effort を選ぶ。
- **事例の成果**：グローバル銀行は 30 件のタスクで 56 時間を削減し、金融サービス企業はアンケートからスライドを作るワークフローを 120 分から 10 分にした。グローバル製薬企業は、ドキュメント作成の時間とコストを 50% 削減することを目標にしている。
- **管理のしやすさ**：IT 管理者は支出ポリシー、モデル選択、承認、Purview を通じたセキュリティとコンプライアンスを管理でき、ビジネス側は IT チケットなしで利用量と価値を確認できる。

## 9. まとめ

Cowork は、ユーザーがゴールを渡すと、複数のステップを計画し、アプリやファイル、ブラウザーを使って完成物まで進める Copilot のアプリケーションです。承認が必要な場面では止まり、レビューするのは結果だけ、という分担が基本になります。

ウォークスルーでは、PM が顧客の不満の発見、Skeptic による検証、Salesforce のデータ取得、spec の作り直し、declarative agent によるデザインルール検証、browser tool によるロードマップ登録、プロトタイプ作成、フォローアップの自動化までを進めました。Auto は、タスクの各部分に合うモデルと effort を自動で選びます。運用面では、Admin Center の支出ポリシー、live meter、Purview による統制が用意されています。ウォークスルーで見せた機能は、Ignite の期間中に順次ロールアウトされ、数週間以内に試せるようになるとのことです（declarative agents は準備中とされています）。
