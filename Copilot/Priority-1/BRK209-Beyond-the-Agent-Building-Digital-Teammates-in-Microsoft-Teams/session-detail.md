# BRK209 Beyond the Agent: Building Digital Teammates in Microsoft Teams

## 1. はじめに

このセッションは、Microsoft Teams 上で動く AI エージェントを「デジタルな同僚（digital teammate）」として作るための考え方と機能を紹介する 45 分のブレークアウトです。内容は、Teams 向けにエージェントを開発する方法が中心ですが、IT 管理者によるエージェントの管理・統制（ID、ポリシー、監査）にも多くの時間が割かれています。

発表は **Design（設計）・Identity / Security / Access（ID・セキュリティ・アクセス）・Context（コンテキスト）** の 3 つの柱（発表では「Act」＝幕と呼んでいます）で進みます。さらに、セッションの冒頭で登壇者が GitHub Copilot に「Zava Helper」というエージェントを作らせ、終盤でそれを実際に動かして見せる構成でした。新発表として、HTML widgets、plan mode、socket mode（preview）などが紹介されています。

## 4. 発表者が伝えたいメッセージ

発表の結論は「**人が一緒に働きたいと思うエージェントは、優れた同僚のようにふるまうエージェントである**」という一点に集約されています。そのために必要な要素として、3 つの柱が示されました。

- **Design**：スレッドで返信する、絵文字でリアクションする、必要な人を @mention するなど、人間が自然に行う作法（ソーシャルシグナル）を最初から備える。

## 5. 発表内容の詳細

### 5.1 導入：Teams にエージェントを迎える

登壇者は、エージェントが「チャット・チャネル・会議の内容を把握し、Microsoft 365 のコンテキストと外部ツールのコンテキストを持ち、組織がすでに信頼している ID・権限・コンプライアンスの枠内で動く」とき、チームメイトになると説明しています。

Teams ストアにはすでに多くのエージェントがあり、パートナー製品の例として、開発者向けに Cursor と Factory、IT・運用向けに PagerDuty と Datadog が挙げられました。Teams 上でこれらを @mention でき、管理者が承認すれば組織内ですぐ使えるようになります。

エージェントの作り方は 2 通りです。

| 方法 | 内容 |
| --- | --- |
| ローコード | Copilot Studio |
| コードファースト | Teams SDK と Teams CLI |

このセッションは主にコードファースト（pro-code）の話です。

### 5.2 ライブ構築の依頼（Ricky）

### 5.3 3 つの柱

Umang が、チームメイトとして輝くエージェントには 3 つの柱があると紹介しました。Design、Identity / Security / Access、Context です。Context については「Microsoft ではコンテキストが差別化要因になりつつある」と説明しています。

### 5.4 Act 1：Design

**ソーシャルシグナル。** 人間が効率よく働くときの振る舞いとして、スレッドで返信して会話を整理する、絵文字で了解を示す、エスカレーションや専門家の招集で @mention する、詰まったら質問して追う、が挙げられました。これらを備えたエージェントはチームメイトに感じられ、備えていないとただの bot に感じられる、という整理です。Teams SDK にはこうした機能がすでに組み込まれており、次の 3 点が例示されました。

- 他の同僚と同じようにエージェントを @mention できる
- スレッド内で直接返信し、会話を整理する
- 絵文字リアクションで、メッセージを読んだこと・作業中であることを示す

**信頼のためのシグナル。** 新機能として **plan mode** が発表されました。エージェントが考えていること、取り組んでいること、完了した作業を、対話的に更新として送る機能です。また、citation（出典）と sensitivity label（機密度ラベル）も用意されており、情報の出どころと機密性、次に渡す際の扱いが分かるため、回答を信頼しやすくなる、と説明されています。

**行動につなげる 3 つの形。**

1. **フィードバック**：エンドユーザーが、エージェントの回答が正しかったか誤っていたかを、アプリを作った開発者や ISV に伝える（発表では "custom feedback models" と聞こえますが、音声認識の都合で正確な名称は確定できません）。
2. **Suggested actions**：会話を特定の方向へ導くため、実行すべきタスクや承認などを提案する。
3. **Targeted messages**：今年の Build で発表され、**GA になりました**。エージェントから特定の人にだけ非公開のメッセージを送れます。グループチャットやチャネルに出す前に人間がレビューする human-in-the-loop の承認などに使え、ユーザーが主導権を握っているという安心感につながる、と説明されています。

**メッセージ形式。** Teams はプレーンテキストに加えて、次の形式を提供します。

| 形式 | 説明 |
| --- | --- |
| Markdown | 表、見出し、箇条書き、チェックボックスなどで、長い回答を整理して読みやすくする |
| Adaptive cards | 承認・却下のボタンやテキスト入力欄などで、ワークフローを会話に持ち込む。外部へのリンクも可能。メッセージが積み上がるのを減らせる。エージェント自身が作ることもできる |
| HTML widgets | **今回の Ignite で発表**。エージェントがカスタムの UI を生成し、その上で共同作業できる |
| Canvases | メッセージ内に収まらない大きな画面で開く |

HTML widgets について登壇者は、LLM がないと素早くは作れない、チャートや地図、テーブルビューのようなものを、データを自分で問い合わせることなく生成できる点がエージェントの強みだと述べています。Canvas は、例えば Figma のデザインのようなものを皆で操作するとき、小さなメッセージスレッドではなく大きな画面で扱えるものとして紹介されました。

### 5.5 GitHub Copilot エージェントの紹介

Act 1 の締めとして、数か月前にリリースされた GitHub Copilot エージェントが「優れたチームメイト」の例として紹介されました。従来は、顧客バグが会議やチャットで話題になり、誰かが修正に取りかかり、PR を作り、別の人が状況を尋ねる、という流れで、Teams を離れて作業し、完了報告も自分で覚えておく必要がありました。GitHub Copilot ではそれが不要になる、という説明です。紹介された映像の内容は次のとおりです。

- Priya が越えられないバグのスクリーンショットをチャネルに投稿する。Diego は Android を除外し、Sam はサーバーエラーの急増を見つけ、Jordan は 1 つの失敗するエンドポイントまで追跡するが、何が変わったかは誰も分からない。
- Maya が GitHub を @mention して根本原因を尋ねる。コンテキストを繰り返す必要はなく、GitHub Copilot がスレッドを読む。
- このチャネルに接続されたリポジトリで調べ、前日のマイグレーションでカラムの型が変わったことを突き止める。
- Jordan がそのリポジトリへのアクセス権を持っているので、修正を依頼する。GitHub Copilot が変更し、テストを実行し、画面を確認する。
- 動作する画面のスクリーンショット付きで pull request を作る。メッセージには絵文字でマークも付けた。

チームは最初から最後まで Teams の中にとどまり、調査も修正もフォローアップも 1 つのスレッドで完結しました。

Act 1 のまとめとして、登壇者は次の点を挙げています。コンテキストを踏まえてスレッド内で応答する、作業を認識したことを示す、いつ口を挟みいつ追いかけるかを心得て会話を騒がしくしない、説明するだけでなく見せる（整理された内容とワークフロー、HTML widgets による対話型 UI の生成）。

### 5.6 Act 2：Identity / Security / Access

登壇者は、組織に入った人には UPN、メールアドレス、Teams のハンドルがあり、セキュリティグループに属し、管理者がポリシーで見られるもの・アクセスできるものを決める、と整理します。エージェントが同僚になるには、同じ構造と考え方を適用する必要がある、という主張です。管理者がエージェントを信頼できる条件として、次が挙げられました。

- エージェントが何者なのかを確認できる
- アクセス先を決められる
- 人間に適用しているのと同じポリシーを適用できる
- 何を、どこで行ったか、影響範囲（blast radius）を監査できる
- 暴走したときに止めるキルスイッチがある

エージェントが行動する主な方法は 2 つです。

| 方式 | 説明 |
| --- | --- |
| On behalf of | ユーザーのトークンを使い、そのユーザーに代わって行動する。例として Copilot Cowork が挙げられた |
| Agentic user | エージェント自身に ID を与える方式。独自のエイリアス、Teams ハンドル、SharePoint を持ち、PowerPoint などのファイルも自分で作れる |

Agentic user は Entra の ID を持つため、Teams では人間と同じように現れます。組織図に表示され、誰かの部下として報告関係があり、プロフィールカードと Outlook の受信箱を持ち、メールを送受信できます。同じディレクトリ・同じピッカーで他の同僚と同様に見つかり、SharePoint、PowerPoint、Excel、OneDrive などでも自然に見つけられます。さらに、エージェントとしての能力（リッチな応答、ストリーミング、adaptive cards、フィードバック、chain of thought など、Act 1 で見せたもの）も使えます。つまり「人間が持つものと、従来のエージェントが持つものの良いところ」を合わせた存在です。発表の最後には、agentic user には Teams SDK 側で接続できるようになった（we're now connected to）とも述べられ、エージェントが同僚として現れ、他の従業員と同じようにポリシーで統制される、と説明されています。また、人間に適用するポリシーに加えて、エージェント向けのポリシーもさらに用意されているとのことです。これにより、スケールに加えて、管理者がポリシー・ガバナンス・可観測性・証跡を適用できる信頼と制御が得られる、と説明されています。

セキュリティ担当者が最初に尋ねる 3 つの問いは「エージェントは何体いるか」「誰が所有しているか」「何をしているか」です。Teams は **Agent 365** とよく統合されていて、agentic user が何インスタンス作られたか、そのうち何がアクティブか、どのチャネルで活動しているか、どう統制するか、他のユーザーと同様にカスタムポリシーをどう設定するか、といったことを深く確認できると述べられました。

### 5.7 Act 3：Context と Work IQ

登壇者は、会議に臨む人がプロジェクトの履歴、チャネルの会話、最新のドキュメント、先週決まったこと、関連する Jira チケットなどを把握しておくのと同じように、デジタルなチームメイトにも文脈が必要だと説明します（もちろん、見られるのはアクセス権のあるものだけです）。

文脈の層は、第 1 にチャット・チャネル・会議といった会話、第 2 にメール、会議、ファイル、組織の知識を含む Microsoft 365 全般、第 3 に API・コネクター・MCP サーバー経由の外部ツールです。ただし多くの AI は、あるチャット、ファイル、メール、チャネルの一部、会議録画といった「ある時点のスナップショット」しか見られず、仕事は常に変化し続け連結しているため、コンテキストのギャップが生じる、という課題が示されました。

その例として、デモの Finance Auditor エージェントへの質問「Q3 の 3 件のフラグは今どうなっているか」の背景が次のように説明されました。

1. 1 日目：チャットで財務チームがさまざまな支払いを投稿する。
2. 2 日目：チャネルで accounts payable がどのチームが支払われたかを確認する。
3. 3 日目：会議で、ポリシー違反（breach）が議論される。
4. 4 日目：DRI が CFO の承認を得る。
5. 5 日目：エージェントがチャットに参加し、Brandon が状況を尋ねる。

同僚であれば数秒で答えられても、答えがチャット・会議・チャネル・ファイルに散らばっているため、最初の 1 回で正しく集められるかが回答品質を左右する、という指摘です。ここで登場するのが **Work IQ** で、「あなたと組織に合わせてパーソナライズされるインテリジェンス層」と説明されました。Work IQ は次の層で構成されます。

| 層 | 内容 |
| --- | --- |
| データ | Microsoft 365 の内部データや外部データなどのコンテンツ |
| コンテキスト | 仕事の進め方のパターン（スタイル、好み、習慣、定常的なワークフロー） |
| スキルとツール | 特定のタスクのためにエージェントをカスタマイズする専門的な指示 |

Work IQ を使わずに同じ結果を得るには、チャット履歴の取得、チャネルメッセージの読み取り、会議のトランスクリプト取得、ファイルへのアクセスなど複数のツール呼び出しを手で組み合わせ、優先付け・絞り込み・トリアージを行い、独自のオーケストレーション、インデックス、キャッシュまで用意し、それらを開発者や ISV が最新・的確に保ち続ける必要があります。Work IQ を使えば Microsoft がそこを担い、「Q3 の 3 件のフラグは今どうなっているか」と **1 回の ask 呼び出し**で尋ねるだけで、チャット、ファイル、会議、チャネルから必要な内容が返ってくる、という比較でした。

**ガバナンス。** Work IQ は既存の権限とアクセス権を尊重し、一貫した制御を持ちます。テナントのポリシーが上限（ceiling）となり、特定のエージェントについてはポリシーを追加してアクセスをさらに絞れます。また、グラウンディングコンテンツを Work IQ の trust controls で保護します。

- **Sanitization**（public preview）：隠れた指示を除去する。
- **Signed provenance**（coming soon）：コンテンツの出どころと改ざんの有無を検証可能にする。

登壇者は「より多くのコンテキストを与えることではなく、適切な境界内で適切なコンテキストを取り込むことが大切」と述べています。

### 5.8 まとめと socket mode の発表

3 つの Act を振り返った後、Ricky がステージに戻り、**socket mode の preview 提供開始**を発表しました。socket mode は、エージェントを Teams のサービスに接続するときに、パブリックな HTTPS エンドポイントを公開する必要がなくなる機能です。開発ライフサイクル中の依存関係が減り、Teams CLI と Teams SDK を併用すれば、ソケットを自分で管理する必要はない（すべて Teams 側が処理する）と説明されました。

### 6.3 Finance Auditor を agentic user として作る映像（再生できず）

Cecil（IT 管理者）が作成する流れを端から端まで見せる予定でしたが、**映像が正常に再生されませんでした**。部分的に聞き取れたナレーションは次のとおりです。

### 6.5 ライブ構築した Zava Helper の確認

セッション冒頭に依頼した内容の結果を、終盤に Ricky が説明しました。

1. 最初のプロンプトを見せる。それを送ると GitHub Copilot がすぐ作業を始めた。
2. GitHub Copilot はインターネット上で利用できるスキルやリソースを使い、Teams SDK と Teams CLI でエージェントを bootstrap し、ソースコードを書いた。書いたのは約 500 行。
3. 依頼どおり、自分で何もせずインストールできるリンクが提示された。ただしリンクをコピーできなかったため、テキストで出すよう追加のプロンプトを 1 回だけ入力した。
4. 裏側では、Teams CLI が bot とアプリの登録、およびローカルで動く資源と Teams アプリの接続を担う。Teams SDK がメッセージとアクティビティのルーティングを担う。
5. リンクをコピーし、Teams の Web アプリ（仕事用クライアントを使いたくないため）で開く。「Zava Helper」を開き、実データのある test team（Ignite demo team）に追加する。
6. スレッドが複数あるチャネルで Zava Helper を @mention し、スレッドの要約を依頼する。少し長い間があったが、要約が返ってきた。ただし文章の塊で、あまり役に立たない状態だったとして、改善を試す。
7. もう一度 Zava を @mention し、アクションアイテムを追跡する adaptive card の作成を依頼する。カードが表示され、本人またはチームの誰でも完了にマークできる。
8. カードの項目を完了にすると、操作した本人だけに見える確認メッセージが届く。チーム全体に通知があふれるのを避けつつ、状況は全員が把握できる。

プロンプトで依頼した内容はこれで一通り確認できた、という流れでした。

## 7. 注意点・発表者の気付き

## 8. 利用者にとっての利点

発表で語られた利点を整理します。なお、このセッションで具体的な顧客名による導入事例は紹介されていません。

- **Teams の外に出ずに作業できる**：HTML widgets のデモでは、地図・テーブル・計画の確認を Teams 内で完結できました。GitHub Copilot の例では、調査から PR 作成、フォローアップまでが 1 つのスレッドで進みました。
- **管理者が統制しやすい**：agentic user は人間と同じディレクトリに存在し、同じポリシー、セキュリティグループ、監査、キルスイッチの考え方を適用できます。Agent 365 では、agentic user が何インスタンス作られ、いくつがアクティブで、どのチャネルで活動しているかを確認できます。
- **開発者の手間が減る**：Work IQ により、複数のツール呼び出し、オーケストレーション、インデックス、キャッシュを自前で組む必要がなくなり、数行のコードで有効にできます。
- **開発のハードルが下がる**：socket mode により、パブリックな HTTPS エンドポイントを公開せずに接続でき、依存関係が減ります。ライブ構築では、約 500 行のコードを GitHub Copilot が書き、最初のプロンプトと追加のプロンプト 1 回だけで、インストール可能な状態まで到達しました。
- **通知過多を避けつつ主導権を保てる**：targeted messages により、非公開のレビューや、本人にだけ届く確認ができます。

## 9. まとめ

登壇者は、エージェントを優れたチームメイトにするための要素として、次の 3 点を挙げました。

1. **Design**：ソーシャルシグナル（@mention、スレッド返信、絵文字リアクション）に加え、plan mode、targeted messages、Markdown、adaptive cards、HTML widgets、Canvases を使い、仕事を前に進める。
2. **Identity**：on behalf of か agentic user かを選び、人間と同じポリシー・監査・可観測性で組織の信頼を得る。agentic user は同僚として Teams に現れる。
3. **Context**：Work IQ を数行のコードで有効にし、必要な文脈を適切な境界の中で取り込む。

セッションのライブ構築では、最初のプロンプト（と追加の 1 回）から Zava Helper が作られ、スレッド要約、アクションアイテムの adaptive card、本人だけに見える確認メッセージまで動作しました。詳しく学びたい人向けに、直後のラボと aka.ms の beyond the agent series が案内されています。
