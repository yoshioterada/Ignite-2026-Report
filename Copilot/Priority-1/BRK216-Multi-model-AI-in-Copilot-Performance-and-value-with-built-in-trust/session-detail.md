# BRK216 Multi-model AI in Copilot: Performance and value with built-in trust

## 1. はじめに

このセッションは、Microsoft Copilot に複数の AI モデルが載るようになった今、「どのモデルを使うべきか」「コストをどう管理するか」「新しいモデルを安全に受け入れるにはどうするか」という 3 つの疑問に答える内容です。登壇者は 3 人で、それぞれ 1 つずつテーマを担当しました。

1 つ目はモデル選択です。Copilot のモデルピッカーには、Microsoft が最適なモデルを選ぶ **Auto** と、利用者が自分でモデルを指定する選択肢の 2 つがあります。2 つ目は FinOps で、ユーザーのサブスクリプションライセンスに含まれる範囲と、usage-based billing（使用量課金）で使える高度なモデルの切り分け、そして管理センターでの支出管理を扱いました。3 つ目は信頼とガバナンスで、モデルが入れ替わっても「ひとつの統制された入口」を通る限り、データ保護や管理者のコントロールは変わらないという説明です。

デモは、Auto と個別モデル選択（Nagu 氏）、利用者のクレジット消費と管理センターでの操作（Peter 氏）の 2 回あります。

## 5. 発表内容の詳細

### 5.1 モデル選択の考え方と Copilot の設計方針（Nagu 氏）

冒頭の問い「どのモデルがタスクに最適か」への答えは **「場合による」** でした。モデルごとに得意なことが違うためです。Copilot の選択肢は 2 つで、車のオートマ（Auto を選ぶ）かマニュアル（モデルを自分で指定する）にたとえて説明されました。どちらを選んでも最良の体験が得られるように作っている、という位置づけです。

Copilot を作る際の設計上の考え方は、次の 4 点でした。

| 考え方 | 説明 |
| ---- | ---- |
| フロンティアの進歩 | 知能の向上ペースが非常に速く、情報が洪水のように流れてくる |
| 全員のための AI | すべての人・組織が AI でより多くのことをできるようにする（一部の人だけのためではない） |
| タスクごとの違い | 天気の確認のような質問は即答でよく、データ分析や資料作成には時間をかけたい。「十分な品質の答えを得るのに必要なだけ」の時間にとどめる |
| IT への選択肢と統制 | 業務価値を最大限に引き出せるという信頼と確信を IT が持てること |

**フロンティアモデルの現状**については、次のように語られました。

- 直近 3 か月だけで、40 以上のフロンティアモデルが発表された。
- 顧客からは「情報が多すぎる。シンプルにしてほしい」という声を繰り返し聞く。
- どのモデルもすべてのカテゴリで最強ではない。ある週はモデル A が優れ、翌週にモデル B が追い抜く。バージョンが落ち着いても、Web 検索が得意なモデル、成果物（アーティファクト）の生成が得意なモデル、画像生成が得意なモデルなど、得意分野は分かれる。
- モデルプロバイダーごとにサブスクリプションを持つと、各社は利用者の仕事環境・関係者・プロジェクトを共有して理解していないので、エンタープライズ・グラウンディングが引き継がれず、モデル間で一貫しなくなる。

そこで Copilot は、タスクの複雑さにかかわらず仕事を済ませられる「1 つの場所」にする、という方針です。モデルはリリース当日、または非常に近いタイミングで提供してきたと説明しています。

### 5.2 モデルピッカーと Auto

Copilot のモデルピッカー（モデルセレクター）は 2 つのセクションに分かれます。

- **Auto**（左上）: 適切なモデル、適切な reasoning effort（推論の度合い）、適切な harness（モデルを動かす実行環境）を Microsoft 側が選ぶ。
- **個別のモデル**: Anthropic や OpenAI（GPT）のモデルが並び、他のモデルプロバイダーも追加中。各ラボが公開した時点でピッカーに現れる。

Auto を選んでも特定モデルを選んでも体験は一貫します。利用者が誰で、どんな業務文脈にいるかが引き継がれ、これはデモで示されました。また、最新モデルの取り込みと、Auto が最新で最適なモデルへルーティングするための改善は継続して行われています。

### 5.3 出荷前の評価プロセス

Copilot に載せるモデルは、すべて厳格な評価を通っています。

1. モデルごとに、多数のテスト（evals）を実行する。
2. 通過後も、まず小さな利用者グループにだけ公開し、品質やレイテンシーなどを確認する。
3. コストなどの懸念が見つかれば、すぐに改善して評価を繰り返す（聞き取りでは "cost for concerns" と聞こえ、正確な語は確定できません）。
4. そのうえで、初めて出荷対象と認める。

この結果、Web 検索、ファイルアップロード、コンテナー実行、アーティファクト生成、画像作成といった標準ツールが、Work IQ によるグラウンディング（企業の文脈）と合わせて期待どおり動く、と説明されました。クエリごとに適切なモデルへルーティングされ、必要以上に待たされないことを狙っています。

### 5.4 Auto の今後

Nagu 氏は「今日の体験ではない」と断った上で、Auto の方向性を示しました。顧客との更新（renewals）に向けた準備を例に、次のような構想です。

- チャットで進めるか co-work で進めるか、適切なモードを自動で選ぶ。
- 「リードモデル」がサブエージェントを生成し、各サブエージェントにモデルと harness を割り当てて、作業を分担させる。
- 例として、ファイルの理解は GPT-5.5、調査は Opus、画像は画像生成モデル、スライドへの統合は Opus、最後の要約は GPT 6.2 Astra が担当する。

> 注意：モデル名はいずれも聞こえた綴りのままです。音声認識の都合で表記が確定できません。

### 5.5 FinOps の考え方（Peter 氏）

ここから Peter 氏が担当しました。冒頭で会場に「管理センターで co-work や Work IQ などの spending policy（支出ポリシー）を作ったことがある人は」と尋ね、多くの手が挙がりました。

テーマは、モデルの幅を提供しながら、どうやって経済的に持続可能にするか、です。AI 支出を膨らませず、予算内に収めつつ、利用者を行き止まりにさせないことが目標でした。そのために次の構成をとっています。

- 日常的な AI の用途には、ユーザーのサブスクリプションライセンスで十分な価値を提供する。
- 複数ステップのエージェント型ワークフローなど、より高度で堅牢なモデルが必要な用途では、ライセンスに含まれる範囲を超えて usage-based billing と FinOps の機能を使い、高度なモデルにアクセスできるようにする。
- 高度なモデルでクレジットを使い切った場合は、Copilot Chat のライセンス範囲の機能にフォールバックできる。これにより利用者は行き止まりにならない。

### 5.6 GigaOM の調査

独立した第三者の調査会社 GigaOM と共同で、約 1 か月分のタスクにかかる月額コストを試算しています。日常的な AI 利用に当たるタスクと、より高度な AI タスクの両方を対象に、次の 2 つを比較しました。

- Copilot と Cowork を **Auto** で使った場合
- 同じタスクを Claude（Opus 5.5）と ChatGPT（GPT-6 Sol）で実行した場合

結果として、これらのシナリオ全体で出力の品質に大きな差はなく、**品質を大きく落とさずにコストを大幅に削減できる** と説明されています。具体的な金額や削減率は、発表では示されていません。理由は 3 つです。

| 理由 | 内容 |
| ---- | ---- |
| ライセンスに含まれる範囲 | 日常的な AI タスクは、予測しやすい 1 つのユーザーライセンス費用の中で、追加設定なしに実行できる |
| Work IQ | Copilot と Cowork の下にある知能レイヤー。M365 内のコンテンツを横断して推論する際にモデルの往復回数を減らし、見つけるまでに使うトークンが少なくなる |
| Auto | タスクの要求に応じてモデルを適切なサイズで選ぶ（right sizing） |

### 5.7 管理センターのコスト管理（Peter 氏）

M365 管理センターの Agent 365 の中にある cost management が、AI 支出の設定・レポート・最適化の中心です。

- 現在は Copilot セクションの下にあるが、Agent 365 へ移行中。
- **Agent 365 のライセンスは不要**（何度も質問されたと述べていました）。
- Cowork、Work IQ に加え、Copilot Studio agents の spending policy を設定できる機能を公開したばかりで、対象は今後さらに増える。
- 組織全体で今月消費したクレジットを確認できる。クレジット消費だけでなく、実際の金額（テナントの通貨）も表示するようになった。
- Agent 365 の business analytics と value metrics（価値指標）に関する発表があり、Cowork の value metrics を今週から Frontier で提供開始する。価値の算出方法は別の話題になるため、興味があれば終了後に声をかけてほしい、とのことでした。

次の機能が紹介されました。

| 機能 | 状況 | 内容 |
| ---- | ---- | ---- |
| モデル別の利用量と支出 | 今日から利用可能 | ライセンス範囲の利用と usage-based billing の利用の両方、および Auto が裏で複数モデルに振り分けた分も含めて見える |
| ユースケース別の分析 | 今週から Frontier で Cowork 向けに開始 | エージェントやサービスがどんな仕事に使われているかを可視化。6,000 を超えるユースケースのライブラリで分類し、コストだけでなく価値も算出する。ロールアウト時は既定でオフで、明示的に有効化する |
| モデルテンプレート | 直近の機能 | spending policy ごとに、選べるモデルを制限する |

### 5.8 信頼とガバナンス（Natan 氏）

Natan 氏は、新しいモデルが出るたびに「利用者が使いたがる」が、その前に必要なのは多数のレビューだという課題から始めました。セキュリティ、コンプライアンス、プライバシー、法務、責任ある AI、IT の各チームが、それぞれ次のような問いを持っています。

- 誰がそのモデルを動かすのか
- データは保持されるのか
- 新しいプロバイダーをオンボードする必要があるか
- どの規約が適用されるのか

これらは形式的な手続きではなく「正しい問い」であり、Microsoft も同じ問いを立てているとのことです。たとえ話は住宅購入でした。検査を省くことはできないが、新しい物件が数週間ごとに出るなら、毎回検査をやり直すことになる。いまのモデルもそれと同じで、選択肢は「審査されていない条件を受け入れて速く動く」か「待って機会を逃す（または利用者が独自の回避策を探す）」の二択になってしまう、という説明です。

これに対する答えが、**「1 つの統制された入口（governed front door）」** です。一方に複数プロバイダーのフロンティアモデル、もう一方にチャット・Cowork・エージェントなど利用者が AI を使いたい場所があり、Copilot が両者をつなぎます。新しいモデルは利用者が既にいる場所に現れるので、新しいアプリ、新しい統合、新しいベンダーのオンボードは不要です。すべて Microsoft の規約と保護策の枠内で、Microsoft が審査し、エンタープライズ向けの統制がかかり、既存の Microsoft 契約でカバーされます。この枠の外にあるものは、有効化しない限りオフのままです。

#### モデルが Copilot に入る 3 つの経路

| 経路 | 内容 | 適用される規約 |
| ---- | ---- | ---- |
| Microsoft が運用するモデル | Microsoft 自身のモデルや Azure OpenAI など。Azure インフラ上で動き、データは Microsoft の外に出ない。オプトイン不要 | Microsoft の data protection addendum と製品規約 |
| AI sub-processors | Anthropic のような他社のモデルを、Microsoft に代わってプロバイダーが動かす経路 | 同上 |
| 独立したプロセッサー | 各社の規約で動作する。管理者が有効にしない限りオフ。さらに広いモデル選択を得るための経路 | 各社の規約 |

どの経路でも、Copilot のエンタープライズグレードの統制は適用されます。

#### プロバイダーとモデルの審査

AI sub-processor になるには、多くの要件があり、その作業は Microsoft がモデルが利用者に届く前に行います。

1. 新しいプロバイダーは、セキュリティとコンプライアンス、データの取り扱い、責任ある AI、Microsoft の規約の基準をクリアする。ギャップは解消するか、事前に開示する。Natan 氏は自身が何度かのオンボーディングに関わった経験から、数週間ではなく数か月かかることがあると述べています。複数のチームが関与し、先ほどの問いと同じことを確認します。この工程が終わるまで何も公開されません。
2. この工程は **プロバイダーごとに 1 回** で、モデルごとではありません。
3. 次に、新しいモデルごとに個別のチェックがある。Nagu 氏が説明した品質テストに加え、すべてのモデルが red teaming を受け、リリース前に責任ある AI の基準でレビューされ、リリース後も監視される。新しいバージョンだからといって優遇はされない。

#### 1 つのプロンプトで見るデータの流れ

「キャンペーンの概要をローンチプランに変えてほしい」という依頼を例に、次の順で説明されました。

1. Work IQ が、利用者が既にアクセスできる文脈とコンテンツで依頼をグラウンディングし、入口で責任ある AI のチェックが走る。
2. プロンプトが選ばれたモデルに送られ推論される。**変わるのはこのステップだけ** で、sub-processor の場合はプロバイダーが Microsoft に代わってこの処理を行い、回答の生成に必要なコンテキストだけを受け取る。
3. 回答は同じチェックを通って戻り、Purview のポリシーが適用される。グラウンディングとアクセス制御は Microsoft 365 内にとどまる。

#### sub-processor モデルでの保護

既存の Microsoft の約束がそのまま引き継がれる、という説明でした。

- 同じ契約が適用され、プロバイダーごとの新しい契約は不要。
- プロバイダーは回答の生成に必要なデータだけを受け取り、そのデータで自社の AI モデルを学習させない。
- データは Microsoft 365 に保存され、転送中・保存中は暗号化され、他の顧客とは分離される。
- Purview の統制が適用される。
- 特定のモデルに限らず Copilot 全般に適用される約束（例: customer copyright commitment）も適用される。
- プロバイダー間で違いがある点は、Microsoft のドキュメントにプロバイダーごとに記載されている。

データ処理の場所に関しては、Copilot の「cloud models」（音声認識の都合で表記が確定できません）が **今年末までに EU data boundary に入る** と最近発表した、とのことです。EU および EFTA 諸国でデータを保存・処理するという Microsoft の約束を、選べるモデルにも広げるものです。実務的には、これらの約束を 1 度確認し、あとはプロバイダーごとに「違う点」だけを見ればよいことになり、自社で評価する際の出発点にもなる、と説明しました。

#### 管理者のコントロール

Peter 氏が見せたのは支出の制御で、こちらは信頼のための制御です。Anthropic を例に、3 段階で説明されました。

1. **決める**: M365 管理センターで、モデルにアクセスできる利用者やグループを指定する（例: マーケティンググループでパイロット開始）。
2. **守る**: Purview の data loss prevention で、どのモデルが答える場合でも、Copilot がアクセスできるデータを設定・制限する。
3. **検証する**: Purview の監査ログに Copilot の活動が記録され、どのプロバイダーが、誰により、何に対して使われたかを確認できる。

## 6. デモ・手順

### 6.2 利用者のクレジット消費と管理センターのデモ（Peter 氏）

**利用者側（Copilot Chat）**

1. 設定は、Caldova（製薬製造会社）のサプライチェーンマネージャー **Elvia** の視点（音声認識の都合で綴りが確定できません）。

3. cold shade management（後の発言では cold chain management と聞こえます。音声認識の都合で表記が確定できません）に関する、製薬関連の高度なプロンプトを入力した。背景で Work IQ と他のコネクターを使って答える、と説明している。

5. 「view usage」リンクで詳しい利用状況を確認できる。消費を機能別（この例では advanced models and chat）で切り替えられ、利用履歴も見られる。Copilot と Cowork の両方で機能する。
6. 月の後半で、ほとんどのクレジットを使い切った状況を想定し、もう 1 つプロンプトを入力して月の上限を超える状態にした。**タスクは途中で止められず最後まで完了し、管理センターで設定した月次上限を超えて課金されることはない**。
7. 画面のボタンから、IT 管理者に追加クレジットを依頼した。依頼後、メニューを開くと Astra は選べなくなっていた。

**管理者側（M365 管理センター）**

1. Agent 365 の cost management を開く。組織全体のクレジット消費、金額が見られる。
2. Elvia のクレジット依頼を開き、「resolve」を選ぶ。クレジットの履歴が見える。解決方法は 2 つで、spending policy の設定タブで月次上限を上げるか、より高い月次上限を持つ spending policy に関連付けられたセキュリティグループに追加する。

## 7. 注意点・発表者の気付き

- **Auto の将来像は現在の体験ではありません。** サブエージェントごとにモデルを割り当てる構想は「今日の体験ではない」と明言されています。
- Cowork のユースケース分析は、ロールアウト時は **既定でオフ** で、管理者が明示的に有効化する必要があります。また、今週から Frontier での提供開始です。
- Auto の使い方：チャットの Auto は usage-based billing を使いませんが、Cowork は使うため、Cowork ではクレジットを消費します（Q&A での回答）。
- Purview のポリシー（DLP など）は、現時点ではモデル別ではなく Copilot 全般に適用されるという認識が示されました（回答者自身が「と思う」という言い方で答えています）。
- sub-processor の新規オンボーディングは数か月かかることがあり、その間は何も公開されません。
- 独立したプロセッサー経由のモデルは各社の規約で動き、管理者が有効にしない限りオフです。
- プロバイダー間の違いは、Microsoft のドキュメントにプロバイダーごとに記載されています。
- cost management は、今は Copilot セクションにありますが、Agent 365 に移行中です。Agent 365 ライセンスは不要です。

## 8. 利用者にとっての利点

- **選択の負担が減る**: Auto を使えば、モデル・推論の度合い・harness を Microsoft が選ぶ。マニュアル操作派には個別選択も残る。
- **最新モデルをすぐ使える**: リリース当日、またはごく近いタイミングで提供される。
- **一貫した文脈**: Auto でも個別モデルでも、利用者の memory や業務文脈、画像生成、ファイルアップロード、Web 検索などの機能が引き継がれる。
- **コストの低減**: GigaOM の試算では、Auto の Copilot/Cowork は、Claude（Opus 5.5）や ChatGPT（GPT-6 Sol）で同じタスクを実行する場合より、品質に大きな差がなく、コストが大幅に低い。
- **予算と体験の両立**: 月次上限を超えて課金されず、タスクは途中で止まらず、クレジットが尽きてもライセンス範囲にフォールバックできる。
- **管理者の可視化と制御**: モデル別の支出、ユースケース別の分析、model template による制限、クレジット依頼の承認。
- **審査の重複を減らせる**: プロバイダーの審査（セキュリティ、コンプライアンス、データ取り扱い、責任ある AI）と各モデルの red teaming は Microsoft が行う。既存の Microsoft 契約が引き継がれ、プロバイダーごとの新規契約は不要。
- **データの保護**: プロバイダーは必要なデータだけを受け取り、学習には使わない。EU data boundary への対応が今年末までに予定されている。

## 9. まとめ

- Copilot は、Auto と個別モデル選択の 2 つの入口を持ち、どちらでも利用者の文脈が引き継がれる一貫した体験を提供する。
- すべてのモデルは、出荷前に多数の評価と、小さな利用者グループへの段階的な公開（品質やレイテンシーの確認）を経る。
- FinOps では、ライセンスに含まれる日常利用と、usage-based billing による高度なモデル利用を組み合わせ、上限を超えず、行き止まりにならない設計になっている。管理センターでは、モデル別支出、ユースケース、model template などで最適化できる。
- 信頼面では、3 つの経路（Microsoft 運用、AI sub-processors、独立プロセッサー）があり、プロバイダーは 1 回、モデルは個別に審査される。モデルが変わっても、グラウンディング、Purview、既存の契約は変わらない。
- 管理者は、誰が使えるかを決め、Purview で守り、監査ログで検証できる。
