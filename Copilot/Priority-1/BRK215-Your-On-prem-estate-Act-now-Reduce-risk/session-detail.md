# BRK215 Your On-prem estate: Act now. Reduce risk.

## 1. はじめに

このセッションは、インターネットに公開されたオンプレミスの SharePoint Server、Exchange Server、Skype for Business Server を運用している方に向けて、Microsoft が見ている脅威の現状と、Microsoft がこれから提供する対策、そして今日からできる基本的な対策を率直に伝える内容です。

発表の結論は明快です。**サポート終了バージョンを使わない、パッチを速く当てる、そしてインターネットに直接公開せず、認証付きのリバースプロキシの背後に置く**。この 3 点が、最も効果的な対策として繰り返し強調されました。あわせて、Microsoft 側が「Configure（構成）、Protect（保護）、Patch（パッチ）」の 3 本柱で、オンプレミス製品のセキュリティを引き上げる計画（新機能は来年の初めに提供予定）が示されています。画面を使ったデモはありません。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK215](https://ignite.microsoft.com/en-US/sessions/BRK215)

## 4. 発表者が伝えたいメッセージ

発表の中心は、「脅威の状況はこの 12 か月ほどで劇的に変わった」という認識です。国家支援レベルの攻撃者は 10 年以上前から活動し、公開されたオンプレミス製品を逆コンパイルして脆弱性を探してきました。そして 2026 年の変化として、同じ能力が、Claude、Codex、ChatGPT、GitHub Copilot などのサブスクリプションを持つ誰にでも使えるようになった、と述べています。

そこで Microsoft は、パッチを速く出すだけでなく、「構成、保護、パッチ」の 3 つの脚を揃える方針です。登壇者はこれを「三本脚の椅子（three-legged stool）」にたとえ、次のように説明しています。

- パッチの頻度を上げるだけでは、利用者に「もっと速く走れ」とトレッドミルを強いることになる。
- 緊急の緩和策（Emergency Mitigation Service）だけを出して、パッチを遅らせたり、「緩和策があるからパッチを先延ばしにできる」と誤解させたりするのは避けたい。
- 使われない高リスク機能は、既定でオフにするなど、露出を減らす構成にする。

また、オンプレミス製品を見捨てていないという点も、何度も強調されました。インシデントレビューでは、サポート対象のバージョンを、クラウド版もオンプレミス版もすべて評価するため、オンプレミスが「後回し」になることはないと述べています。組織面でも、直属の上司（OneDrive と SharePoint の president と述べています）が、オンプレミス製品の脆弱性の発見・評価・修正に追従するためにリソースを移している、という話もありました。

## 5. 発表内容の詳細

### 5.1 脅威アクターと AI がもたらした変化

登壇者は、Microsoft の脅威インテリジェンスチーム（音声認識では「Mystic, Ghost, Dart」と聞こえます。名称は確定できません）と日常的に協力していると述べました。詳細な事例の紹介は許可が得られず、詳しくは Microsoft Security のブログに各脅威アクターの詳細ページがあると案内しています。要点は、各アクターがインターネット公開資産を積極的に狙っており、国家支援レベルの脅威に対しては「インターネットに公開されているか」「最低限のことはやったか」を超えて考える必要がある、ということです。

次に、AI の影響が語られました。

- 攻撃者には、ソフトウェアエンジニアとリバースエンジニアリングの専門家の「軍隊」がいて、顧客が入手できるオンプレミスのソフトウェアを逆コンパイルして脆弱性を分析し、その結果が情報機関に渡って、足がかりの確保や知的財産の窃取などに使われてきた。
- 2026 年の変化として、同じことが、AI サブスクリプションを持つ人なら誰でもできるようになった。登壇者の一人は、2026 年の初めに、自宅の IoT 機器のファームウェアを Claude でリバースエンジニアリングし、脆弱性を見つけて報告し、バグバウンティの報奨金を得て、ベンダーから無料のハードウェアが送られてきた、という個人的な体験を述べています。
- 一方で、国家レベルの攻撃者と違い、土曜の朝に思いついた人が AI のクレジットを使って脆弱性を探し、見つけたものを慎重に扱うとは限らない。
- MSRC（トランスクリプトでは "Microsoft Security Research Center" と話されています）への報告でも、2026 年に入って**重複した報告が増えた**。セキュリティ研究者や、小遣い稼ぎをしたい大学生などが、同じ手法で調査しているためだと説明しています。

AI は脆弱性調査だけでなく、攻撃のキルチェーン全体で使われているとのことです。エクスプロイトのペイロードの開発、悪用可能な形への加工、インターネット公開サーバーへの試行、さらに、リモートコード実行が成功した後の侵害後の行動（次に実行するスクリプトの判断、バイナリや情報の収集、リバースエンジニアリング、第 2・第 3 段階のペイロードの配信）でも、エージェントが使われている実例があると述べています。10 年前の感覚では、初期の偵察から目的の達成まで数週間から数か月かかったものが、今は**数分**で進むこともある、という話です。

### 5.2 パッチの時間軸：Microsoft が戦っている時計

登壇者は、お客様は「パッチが出た時点から時計が始まる」と考えがちだが、Microsoft にとっての時計は、もっとずっと手前から始まると説明しました。流れは次のとおりです。

1. **脆弱性を知る**：社内のパートナーチームや AI による自社スキャンからの報告、MSRC への外部の研究者による責任ある開示、インシデント調査を行う脅威インテリジェンスチームや外部の脅威インテリジェンス企業からの通知。
2. **トリアージ**：緊急度と優先順位を判断する。
3. **バリアントの評価**：報告された 1 件だけでなく、同種の問題すべてを直し、パッチが包括的になるようにする。
4. **サポート対象のすべてのバージョン向けにパッチをビルド**する。

ビルドの時間については、SharePoint Server Subscription Edition は数時間でビルドを回せるが、2016 と 2019（SharePoint では最近までサポート対象だった版）は、クラウド以前の旧世代の事情から、**パッチのビルドに 1 週間かかることもある**と説明しています。Exchange についても「ひどい（brutal）」という反応がありました。また、7 日かかるビルドの 4 日目にバリアントが見つかると、最初からやり直しになります。サポート対象のすべてのバージョンのパッチが揃うまでは公開しないため、Subscription Edition の利用者の保護も遅れます。

その間にも、研究者による重複報告が増えているため、攻撃者が同じ脆弱性を独自に見つけるリスクがあります。攻撃者はパッチを待たず、「Microsoft はもう知っているはずだ」と考えてすぐに悪用に移る、と述べています。

パッチを公開して CVE を発行し、バイナリの更新を出すと、その問題は広く知られます。攻撃者は更新を入手して逆解析し、武器化します。独立した研究者が、名声のために、Patch Tuesday の更新から数時間以内に概念実証（PoC）をオープンソースとして GitHub に公開することもあるそうです。そこで「Patch Tuesday から、顧客が実際にパッチを適用する日までの期間」が非常に重要になる、という指摘です。

会場には挙手での質問もありました。Exchange のパッチを、Patch Tuesday から 1 週間以内、1 か月以内、あるいは修正の hotfix が出たら（9 月に出した hotfix のように）すぐに適用するのは誰か、という質問です。登壇者は、専門家が集まる会場でも、全員が望む速さで適用できているわけではないと述べています。

### 5.3 Microsoft の取り組み：Configure / Protect / Patch

登壇者は、Microsoft の社内の発見状況にも触れました。「MSRC への投稿と社内の発見のどちらが多いか」という問いに、「おそらく社内だ」と答えています。登壇者は、1,000 件の Windows のセキュリティ更新のうち、CISA が取り上げたのは 1 件で 6.3 だった、それより深刻なものを複数、社内で見つけて修正していたという話をしています（音声認識の都合で細部は確定できません）。CVE は攻撃者の材料になる一方で、「Microsoft が見つけ、文書化し、安定して直している」という安心材料でもあるという考えです。

3 本柱は次のとおりです。

| 柱 | 内容 |
| ---- | ---- |
| Configure（構成） | ソフトウェアを最初から安全にデプロイできるようにする。Secure by default |
| Protect（保護） | Emergency Mitigation Service（EMS）などの緩和策。オプトインから既定でオンへ |
| Patch（パッチ） | 耐久性のある修正を、より速く出し、適用のギャップを埋める |

**Configure の例（Exchange）**
- Exchange サーバーの **86%** は、「1 本脚の DAG」、つまり Exchange サーバーが 1 台だけで動いている構成だと述べています。
- そこで、ドキュメントの既定構成を 2 台の Exchange サーバーに変える作業を進めています。パッチを適用するときに、1 台目を適用して稼働を確認してから、2 台目に進めるようにするためです。
- 小規模の導入でも考え方を変える方針です。目標は、大学を出たばかりの新入社員でも、長年の経験なしに Exchange をオンプレミスで導入・運用できるくらい簡単にすること。分かりにくい点、高コストな点、難しい点があれば、Microsoft に押し返してほしいと述べています。

**Protect の例（EMS）**
- EMS に登録している利用者は多いが、これをオプトインから「既定でオン」の姿勢に変える、と述べています。
- 緩和策は有効だが、すべてをカバーするわけではなく、一時的なものです。

**Patch**
- 「パッチを当て、プロキシを使い、インターネットに公開しない」という基本に新しいことはないが、Exchange も SharePoint もパッチ適用が大きく遅れている、と述べています。
- パッチが出た後、テストのための猶予期間を設けたうえで、それでも適用されない場合（管理者が休暇中など）はサーバーにパッチを**自動適用**する方向です。Microsoft がワークロードに責任を持つ、という位置づけです。
- Exchange サーバーには、専任の管理者がいない（兼務やバックアップ的な運用）場合もあることを前提にしている、と説明しています。
- その結果、Patch Tuesday 以外のタイミングで出すパッチが増えます。重要（critical）と important のパッチは、必要と判断したときに出します。これは大きな変化で、利用者の作業は増えるが、それを楽にする工夫も進めている、とのことです。

### 5.4 今日できる基本対策：3 つの大罪

Microsoft の「到来する新機能（来年初頭の予定）」を待たずに、運用者が今日できることとして、**攻撃者に狙われやすくなる 3 つの大罪**が示されました。

1. **サポート終了バージョンを使っている。** 2026 年には脆弱性とパッチが増えており、パッチはサポート対象バージョンにしか出していません。古いコード（2010 年や 2012 年のコード）が 2016、2019、Subscription Edition に引き継がれていることがあり、旧バージョンのサーバーも、その脆弱性から免れません。攻撃を世界中のサーバーに無差別にばらまく攻撃者は、バージョン番号を気にせず、試してみて成功することがあります。
2. **サポート対象バージョンでも、パッチを適用していない。** 数か月も適用しない場合です。脆弱性があると分かっている状態なので、最も重大なリスクだとされています。攻撃者はパッチの逆解析と武器化に長けているため、テストから本番展開までのサイクルが長いほど、リスクにさらされる期間が長くなります。
3. **未知の脆弱性（ゼロデイ）のリスクが残っている。** 最新でサポート対象でも、まれに起きるゼロデイは大きな被害をもたらします。

ゼロデイへの最善の助言として、Microsoft が自社環境の強化（Secure Future Initiative）で行っていることと同じ方針が示されました。

- **サーバーをインターネットから外す**。受信は、VPN や社内ネットワークなど、信頼できるネットワークからのみ許可する。
- 組織外からのアクセス（BYOD やモバイル端末など）が必要な場合は、**プロキシの段階で認証を要求するリバースプロキシ**を使う。そうすれば、攻撃者が未知のゼロデイのペイロードをインターネットにばらまいても、組織の資格情報を持たない限りサーバーに到達できず、緩和策やパッチを適用する時間が得られる。

> 注意：登壇者は、1 つだけお願いするとしたら「インターネットに公開されているサーバーの前に、認証を要求するリバースプロキシを置くこと」だと述べています。認証なしのリモートコード実行やゼロデイから守り、ニュースに載らずに済む、という説明です。

### 5.5 現場の実態：公開 CVE から 1 時間未満で悪用可能

Exchange を担当する登壇者は、社内で行った思考実験を紹介しました。ある CVE について、リスクの評価がセキュリティチームと食い違ったため、公開された CVE の情報だけから、動作するエクスプロイトに至るまでの時間を実証しました。結果は、**20 ドルのサブスクリプションで 1 時間未満**でした。CVE の公開は必須でありオプションではないため、公開と同時に悪用される機会が生まれます。すべてが悪用されるわけではないが、悪用され得る、という説明です。

あわせて、実環境の Exchange の状況も共有されました。

- サポート終了バージョンは、Exchange のフットプリントの**約 30%**。
- インターネット上でメールを送っている最も古い Exchange は **2007**で、政府機関のものだった。登壇者は電話で CIO に連絡し、対話を始めた。
- Charles Lamanna 氏に更新を報告したところ、状況を非常に懸念している。Microsoft は、状況の悪い顧客に電話をかけ、「あなたの環境ではこう見えている」と伝え、積極的に働きかけている。すべての顧客には対応できないが、Subscription Edition を導入したのに hotfix を一度も適用していないような大きな対象から順に、アカウントチームを通じて連絡している。
- 実環境の大半は最新に保たれていない。「最新」とは、hotfix 1 つ前、おおよそ 30 日という旧来の基準で、Patch Tuesday に追従していても今は不十分だ、と述べています。
- 400 台以上の Exchange サーバーを運用し、hotfix を 1 つも適用していない企業の例もあった。上位 10 の対象には、本人が直接連絡した。

オンプレミスの Exchange を引き続きサポートしたい、必要性やミッションも理解している、だから「パッチを早く届けるので、適用に協力してほしい」というのが、登壇者のメッセージです。

### 5.6 クラウドへの移行を検討してほしい理由

登壇者は、「可能ならオンプレミスのワークロードをクラウドに移すことを検討してほしい」というスライドを、あえて入れたと述べています。1 週間前の Exchange の障害を踏まえると意外に聞こえるかもしれないが、セキュリティ実務者の立場からは、クラウドで提供できる安全性と網羅性は、オンプレミスを大きく超える、という考えです。理由は次のとおりです。

- 「発見、ビルド、パッチ、展開待ち」というオンプレミスの時間軸が、クラウドには存在しない。
- クラウドでは 1 日に数百件の変更を出荷している。
- 数分で（正確には数秒でも）トラフィックのブロックや機能の停止ができる。
- エージェントが入ってくるテレメトリを監視し、研究者、脅威アクター、被害者を識別する。研究者や脅威アクターは、顧客に影響のない、隔離された場所に積極的に移す。
- SharePoint のオンプレミスの修正を出荷するときは、まず SharePoint Online の全体に展開する。検証のためと、セキュリティ対策のため。

オンプレミスの運用者に求めている運用の厳格さは、Microsoft がクラウドで長年、より速いペースで実施してきたことだと述べ、信頼性や可用性でときどきミスがあるとしても、セキュリティの観点では「当然の選択（no-brainer）」だと説明しています。同時に、移行が選択肢にならない顧客がいることも理解しており、クラウドでもオンプレミスでも、今日と今後の脅威環境を生き延びるための支援を続ける、と述べています。

### 5.7 ハードニング（強化）の基本

後半は「新しくない話」として、すでにやるべきことの整理でした。

- **Health Checker** を使う。
- **SE（Subscription Edition）と最新のバージョン**に更新する。
- 正しいバージョンか、安全に構成しているかを確認する。

> 補足：登壇者は、Exchange のサポート対象外の版（サブスクリプション版以外）のビルドシステムが 12 月 1 日で廃止されること、10 月 31 日で非サブスクリプション版の Exchange サーバーがサポート終了になったことに言及しています。これらのバージョンには、パッチをビルドする時間が長すぎ、差異が大きすぎるため、もはやパッチを出せないという説明です。

**Defender との連携（新しい点として強調）**
- 登壇者の一人のチームのエンジニアが、「Exchange や SharePoint への受信リクエストを Defender で検査できないか」という発想を出した。以前は、パッチの開発、展開、有効化を待つ必要があった。Defender のシグネチャで、HTTP リクエストの POST 本文や URL が悪意のあるものに見えるかを判定してブロックする。
- 性能テストを経て、SharePoint と Exchange の両方で、**既定で有効**になっている（登壇者は「I believe」と述べています）。
- Exchange / SharePoint サーバーに Defender を入れ、**AMSI 連携**を有効にしておくと、ゼロデイの脅威をプロファイルして攻撃の特徴を特定し、まず**テレメトリのみ**のシグネチャを配信する。ブロックしようとしているものが、顧客のサーバーに大量に来ていないかを確認してから、テレメトリからブロックモードに切り替えられる。これにより、パッチが必要な脆弱性を告知する前から保護できる。
- オプトインしたサーバーのテレメトリから、「実環境での悪用は観測していない」と言えるようになる。

この仕組みの実例が、9 月の更新でした。登壇者は、9 月に important の更新を出したときにリスクは実在した（社内で激しく議論した）が、テレメトリで「まだ誰も悪用していない」と確認できた、と述べています。情報を公開してから 24 時間以内に、「フルの QA サイクルを回して構わない。実際に悪用されているわけではないので、緊急扱いにしなくてよい」というフィードバックが得られたそうです。つまり、悪用されていないため critical ではなく important のまま扱えた、という話です。「約 4 万台の Exchange サーバーからのフィードバックループがなければ、仕事ができない」とも述べています。

### 5.8 インベントリ（棚卸し）

会場には「環境に何が展開されているかを 100% 正確に把握しているか」という質問があり、数人が手を挙げました。登壇者は、棚卸しは地味な話題だが基礎であり、存在を知らなければパッチも当てられないと述べています。出発点は、exposure management でオンプレミスのネットワークや資産をスキャンし、把握している資産がすべて管理下にあることを確認することです。そのうえで、それぞれを次のいずれかに結びつけます。

- クラウドへの移行
- サポート対象バージョンへの移行
- hotfix と毎月のセキュリティ更新で、パッチが当たるような運用の習慣

### 5.9 製品ごとのハードニングと EMS

ハードニングは、Exchange、SharePoint、Skype for Business ごとの機能に分かれます。AMSI 連携はいずれでも重要で、証明書の衛生管理も重要だと述べています。

**Emergency Mitigation Service（EMS）**
- サーバーに対して、緊急時に、ごく限られた構成変更を行える仕組みです。
- EMS の配信は、**実際に悪用されている、または悪用される可能性が高い**場合に限ります。アイデアだけではやらず、テストしてから配信します。
- 今年は今のところ 2 回で、これは過去 3 年間の回数より 2 回多い、と述べています。広く使う機能ではありません。
- 現行バージョンの範囲は限られています。**EMS 2.0** では、機能と緩和策が増え、より頻繁に対応できる可能性があります。
- 既定の手段としてサーバーを黙って更新することはせず、登録している利用者には明確なプロセスが示されます。
- Defender AV のフィードバックは、EMS を行うか、悪用されているか、QA をもう 1 日回せるかなどの判断に使われます。

### 5.10 パッチの品質について

Windows Server の 10 月の更新が、Exchange に問題を起こしたことが話題になりました。登壇者は、フラストレーションを感じていると述べたうえで、1,000 件のセキュリティ修正のうち問題があったのは 1 件で、24 時間以内に取り下げた、障害は許容できないが取り下げは得意だと説明しています。構成ガイダンスの変更や、より耐障害性の高いアーキテクチャへの誘導も、このためです。オンプレミスのサーバーは「遊びで」動かしているのではなく、ミッションクリティカルなアプリケーションとして動かしているので、そのように扱う、と述べています。

### 5.11 これからの計画：on-prem baseline security mode など

最後の数枚のスライドで、数か月以内に提供される内容が説明されました。3 本柱に沿った計画は次のとおりです。

| 柱 | 計画 |
| ---- | ---- |
| Configure | **既定の構成モード**を製品に組み込む。今は構成ベースラインを読み、構成アセスメントを行って、有効になっているものを確認できる。Microsoft 365 とクラウドの baseline security mode と同じように、攻撃対象領域を減らす推奨構成を示し、有効化と影響の把握を支援する。同様のことをオンプレミス製品でも行う |
| Protect | **EMS 2.0**（EMS のバージョン 2.0）。Exchange、SharePoint、Skype for Business で既定でオンにする。悪用が確認された重大な脆弱性に対して、より多くの手段が使える |
| Patch | **一定期間後に、対象を絞った自動セキュリティ更新**を有効にする。Ignite に来ていない、運用が整っていない、数か月から数年パッチを当てていない長い裾野の顧客にも、自動で適用する。すべてのリスクをなくすわけではないが、P95・P99 のパッチ状況を **30〜45 日程度**に戻すのが目標 |

**M365 Local との関係**
- M365 Local は、Subscription Edition に関わるもので、Azure の機能を活用する（「3 つをまとめる」と語られた部分は音声認識が不明瞭です）。
- 狙いは、「デプロイする」というボタンを押すだけの成果を提供するパッケージ。自分たちの QA サーバーは、すでに M365 Local の実装に移行している。
- Exchange のビルドは、既知の構成、既知の設定、ネットワーク制御でテストできる。これまで 150 ページあったインストールと設定の手順を、クラウドの template のような形で提供できるようにするために取り組んでいる。
- Azure Local の再構築（repaving）機能も使える。そのため Exchange を「良い仮想マシン」にするテストを進めている（今は優れた振る舞いではなく、改善中）と述べています。

**提供時期**
- 12 月の更新（スライド上は「December 2026」と書かれていたが誤記で、正しくは Q1）。年末年始の間は何も出さない。
- Exchange と Skype for Business、そして SharePoint（登壇者は「I believe」と述べています）では、自動パッチングと中核機能を、**2 月の Patch Tuesday** に出すのが目標。非常に意欲的な目標だと認めています。
- すでに自動で更新できるサーバーはあり、適用済みでテスト中だが、**回帰がなく、障害を起こさないほど安定している**ことが必要。変更があれば、ブログと、Secure Now の一部である baseline security mode のブログで更新する。
- 既定の構成の自動化、M365 Local、自動セキュリティ更新、EMS 2.0 のうち、EMS 2.0（Exchange）は進捗が早く、少し早く出る可能性がある。前倒しできるものは発表を待たずに前倒しする、という方針です。
- 2 月や 1 月と明言しないのは、製品チームが品質を最優先にリリースできるようにするため。安定性に満足できなければ 2 月から 3 月に延ばすこともある。回帰を含む機能を出すと、自動更新の有効化や今後の hotfix、今後の Microsoft の投資への信頼が損なわれるためです。

## 7. 注意点・発表者の気付き

- **サポート終了バージョンは、パッチの対象外**です。古いコードが新しい版にも残っているため、旧バージョンのサーバーも、新しく見つかった脆弱性の影響を受ける可能性があります。
- **EMS は一時的な緩和策**で、すべてをカバーしません。緩和策があるからといって、パッチ適用を先送りしてはいけない、と明確に述べられています。
- パッチ適用の遅れ（長い裾野）が最大の問題で、「Exchange も SharePoint も、パッチ適用が遅れすぎている」と認めています。
- 今後、Patch Tuesday 以外のパッチが増え、利用者の作業が増える点を、発表者自身が認めています。
- 高度な攻撃者に対しては、「インターネットに公開されているか」だけでなく、最低限の対策を超えて考える必要があります。
- 提供時期（来年の Q1、2 月の Patch Tuesday）は目標で、品質次第で遅れる可能性があります。
- 10 月の Windows Server 更新による Exchange の問題については、1,000 件の修正のうち 1 件が問題で、24 時間以内に取り下げたと説明されています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

| 項目 | 内容 |
| ---- | ---- |
| ゼロデイへの備え | 認証付きのリバースプロキシで、未知の脆弱性でも、資格情報がない攻撃者がサーバーに到達できなくなる。緩和策やパッチを適用する時間が稼げる |
| 構成の簡素化 | 既定構成の見直し（Exchange 2 台構成）、構成ベースライン、既定の構成モード、M365 Local によるボタン一つの展開を目指す |

| パッチ適用の負担軽減 | 自動セキュリティ更新で、長い裾野の顧客の適用状況を 30〜45 日程度に |
| クラウドの保護 | クラウドでは、1 日数百件のデプロイ、数分から数秒でのブロック、テレメトリ監視、隔離などが使える（クラウド移行を検討する理由として説明） |

## 9. まとめ

AI により、脆弱性の発見から悪用までが数分から 1 時間未満のレベルまで短縮され、オンプレミスのサーバーを取り巻くリスクは大きく変わりました。Microsoft は、Configure、Protect、Patch の 3 本柱で、既定構成の見直し、EMS の既定オンと EMS 2.0、自動セキュリティ更新、M365 Local を、来年の Q1（自動パッチ適用は 2 月の Patch Tuesday が目標）にかけて提供していく予定です。

運用者が今日できる対策は、サポート対象バージョンを使うこと、パッチを速く当てること、そして**インターネットから外すか、認証付きのリバースプロキシの背後に置くこと**です。その前提として、環境の棚卸しが必要になります。可能であればクラウドへの移行も検討してほしい、というのが登壇者の最後の呼びかけです。
