### 5.1 導入：まず「知っているエージェント」から

Brendan は、エージェントに identity、owner、利用可能なセキュリティコンテキストがあれば、保護の土台になると説明しました。ただし、保護が実際に効くのは、その agent にコントロールを適用できるときだけです。そこで、インベントリの外に目を向ける前に、Sri が「この出発点を、サポートされているセキュリティ上の判断につなげる流れ」を説明する、という構成です。

### 5.2 Agent 365 の registry と Shadow AI

Sri は、基調講演で見せられた画面として、Agent 365 の registry の overview ページを紹介しました。その中に **Shadow AI** という専用セクションがあります。

Sri の説明では、Shadow AI は組織が昔から知っている「シャドー・ソフトウェア」と同じ概念で、しかもより危険です。Agent 365 は Shadow AI を検出し、検出できたものの数と、まだ検出できていないものの数の両方を示すとのことです。広めに網を張り、「これだけ存在しうる」と先回りして知らせる位置づけです。

対処の流れは、従来のシャドー・ソフトウェアと同じです。リスクを評価し、軽減または解決の手順を取ります。

### 5.4 Agent 365 で取れる対策（Sri の説明）

画面の説明の中で、次のようなコントロールが紹介されました。

| コントロール | 説明 |
| ---- | ---- |
| Block the agent | 「とっさの反応」として、まず動かさない。Intune を通じて、その agent やバイナリの実行を防ぐポリシーを配信して止める。デバイスは最終的に Intune で管理されているため、とのことです。 |
| デバイスの状態を変える | デバイスを non-compliant（非準拠）にする。監査にフラグが立ち、機密情報への接続ができなくなる。 |
| ネットワーク通信の制限 | 制限したい特定のサイトを細かく指定できる。 |
| Isolate the agent | Windows デバイス上で、agent をコンテナー内で実行させる。ファイルシステムや OS を仮想化し、ローカルのデバイスやリソースに触れさせない。この機能は「Microsoft Execution Container」との統合によるものと説明されています（音声認識の都合で表記が確定できません）。 |
| Activity view | 過去 30 日間の活動の概要。インスタンスの数、利用ユーザー数、Global Secure Access を使っている場合は agent が訪れたサイトも見える。 |

Sri は、これらをインスタンスが未検出の状態でも先回りして適用できると述べています。たとえば将来、開発者がインストールしようとしても、すでにポリシーで保護されている状態にできます。

### 5.5 Zenity：agent の意図（intent）を読み取る

### 5.6 Shadow AI の発見を「手で」やってみる

Brendan は会場に 2 つの挙手を求めました。まず、会社に承認済みの AI ツールの一覧があるか。次に、手を挙げたまま、過去 2 週間にその一覧にないツールを使ったか。Brendan はこれを「Shadow AI discovery を手で行った」と表現しました。続けて Sri に引き継ぎ、Agent 365 での Shadow AI discovery を紹介する流れになりました。

Sri は、Zenity の例で見せた内容と重なるため、すでに見せたいことは見せたと述べたうえで、補足をしています。

- shadow tools も話の一部で、例として Open claw を挙げた（トランスクリプトの表記。音声認識の都合で確定できません）。
- Zenity のデモで示された「本番環境のバックアップをローカルのデスクトップに取ってはいけない」という点を、Sri が引き取って説明した。ローカルにパスワードのバックアップがあると、これらのツールがローカルファイルシステムから取り出して外部に出せてしまう。
- 正当なユーザーが本番バックアップを取るという正当な操作でも、リスクになりうる。それを、Zenity の意図ベースの制御が止められたという説明。
- Agent 365 は、ローカル agent がリモートの MCP server を使ってローカルのデータを外に出すケースを検出するのに役立つ。
- 会場に「ローカルのツールが shadow agents に使われているのを見たことがあるか」と聞くと、手を挙げたのは 2 人。「Agent 365 に戻って、Shadow AI を見てほしい。先ほどの承認済み一覧にない tools がどれだけあるか確認し、止めるか、少なくとも制限してほしい」と呼びかけた。

### 5.7 Check Point：Agent Behavior Defense

Check Point の Rob Parrish は、買収を経て入社し、AI セキュリティ向けの独自 foundation model を開発してきたと自己紹介しました。目的特化のセキュリティで、agent が何をしようとしているかを理解し、誰も頼んでいない行動を止める、という説明です。

Rob は、agent を配備するたびに生じる問いを 2 つ挙げました。

1. **どこまで届くか（blast radius）**：誰の代理として、どのモデル、tools、データを使えるか。
2. **その権限の範囲内でも、意図した安全な行動を取っているか。**

生産性を求めればアクセスを広げ、リスクを下げれば狭める、というジレンマがあります。狭めすぎると agent は配備する価値がなくなるため、権限だけでは解決できず、両方のコントロールが統一されたシステムとポリシーの下で動く必要がある、という主張です。この観点から、Microsoft のようなパートナーとの深い統合が重要だとされています。

Check Point Agent Behavior Defense の特徴として、次の 3 点が挙げられました。

1. **影響が出る前に止める。** 行動はコマンドの段階でブロックされ、システムに届かない。
2. **文脈で判断する。** 各アクションを、agent に与えられたタスクやユーザーのリクエスト（提供されている場合）と照らして評価する。正当な作業は止まらない。
3. **圧力のかかる状況でも維持される**（"it holds under pressure"）。agent の kill switch、特定セッションのブロック、個別アクションのブロック、方向のずれた agent を軌道に戻す steering など、複数の対応が取れる。

デモの内容は 6.3 に書きます。

### 5.8 Agent 365 で使える保護手段のまとめ

Sri は、Zenity と Check Point の両方を使っている人が会場にいることを確認したうえで、既存のセキュリティ投資を置き換える必要はないと強調しました。ランタイム保護や意図ベースの保護など、見たものはすべて Agent 365 に表れ、「single pane of glass」として使えます。これが、single open AI observability plane であり、Agent 365 がその答えだというのが Sri の説明です。

あわせて、利用できる保護手段が整理されました。

- **Block the agent**：node.js や VS Code の実行を止めることになる。
- **ネットワーク通信の制限**：デモで見せたとおり。
- **Defender のランタイム保護**：agent の実行中に、リアルタイムの意図、プロンプトインジェクション攻撃、機密性のあるファイル添付の流出などを検出する。
- **App control for business によるブロック**：Intune を使っているならご存じの、悪意のあるファイルの実行を防ぐ手段の 1 つ。
- **デバイスの状態を non-compliant に変更**：ネットワークから切り離される。デバイス自体は動き続けるが、SharePoint サイトなど社内サイトへのアクセスを失う。

これらは、Shadow AI の実行を隔離、制限、封じ込め、ブロックする、またはガバナンスのガードレールを置くための手段として挙げられました。

### 5.9 顧客視点：Lumen Technologies

Lumen Technologies の Andrew Gaskins は、Lumen を「人、データ、アプリケーションを、拡大する AI エコノミーにつなぐインフラを運用している会社」と紹介し、shadow discovery の観点で Agent 365 に取り組んでいると述べました。

Lumen の進め方は次のとおりです。

1. **まず可視化から始める。** 可視化は、判断をすでに下したことを意味しない。
2. 背景（context）を見る。誰が所有しているか、何をするためのものか、何が起こりうるか、問題が起きたら誰が影響を受けるか。
3. 比例的に判断し、次の手を選ぶ。レビューする、制限する、条件付きで承認する、ブロックして退役させる。

Andrew は、これにより、何を使うべきか、誰が使うべきか、誰が所有するかについて明確な説明責任（accountability）が得られ、一貫した判断ができると述べています。この判断を governance に戻して継続的に見直す「フィードバックループ（learning loop）」が、Lumen にとって重要だとのことです。

### 6.2 Zenity のデモ（Israel）

Israel は「デモを流している間に話す」と述べ、動画の再生に手間取る場面もありました。デモで語られた内容は次のとおりです。

1. Shadow AI から始める。組織内の agent と AI ツールをすべて検出する。この例では **Devin** が見つかった。
2. Devin は組織で承認されていないため、**unsanctioned** に設定した。開発者が自分のデバイスで起動できないよう、Defender ADR に prevention rule も追加した（"Defender ADR" は聞こえたままの表記で、音声認識の都合で確定できません）。
3. 一方、組織で承認したい AI サービスは Zenity に接続する。integration page で、ここでは **GitHub Copilot** を追加する。integration の本番用の詳細を入力し、接続が確立されると healthy ステータスが表示される。
4. GitHub Copilot のセッションに移る。本番の payment API が動かず、何かが壊れている、という設定で、「本番運用」のセッションを行う。状況を尋ねてヘルスステータスを出させると、一部のインスタンスがダウンしているという結果が返る。
5. Zenity に戻ると、Zenity がセッションの意図を「production operation（本番運用）」と分類している。セッション自体、ユーザーのメッセージ、AI の応答、tool calls、そして正当性の根拠（justification）が見える。
6. 組織のルールとして、「本番運用のシステムを扱う agent は、secrets に触れてはならない」という enforcement rule を追加済みである。
7. GitHub Copilot に戻り、「ローテーションする前に、credential のローカルコピーを取る」操作を試す。一見正当だが、Zenity がブロックした。hooks により「本番運用を扱うセッションなので、このセッションでは secret に触れられない」と伝えられた。
8. Zenity では、このイベントのエビデンス、すべての findings、根本原因、Zenity が agent に送ったメッセージが見える。
9. これらの findings は、Defender の findings と相関付けられて同じイベントとして A365（Agent 365）に送られる。

### 6.3 Check Point のデモ（Rob Parrish）

1. Check Point のコンソールから、**Agent Behavior Defense** を有効にした。これは agent 向けの monitor sidecar で、左側に動作中の agent、右側にその sidecar が表示される。
2. sidecar は agent の行動をすべて監督し、各アクションにチェックポイントを置いて、有害なアクションをリアルタイムにブロックする。この例では、agent が機密情報を、さらなる分析のために非機密の送信先へ送ろうとするたびにブロックし、それを繰り返し止めている。Rob は、この種の挙動は実運用の agent で見られるもので、「a la the OpenAI case earlier」（先ほどの OpenAI の事例のような）と述べている。この事例の中身は発表では説明されていません。
3. kill だけではなく **steering** 機能が追加された。agent に、意図している内容と、守るべきスコープを返して伝えることで、セキュリティのガードレール内に収めたまま、本来のタスクを達成させる。agent はタスクから外れ、アクションがブロックされ、その後に軌道へ戻される。
4. 別の例として、「たとえば Copilot Studio 上に構築された」communications agent を示した。過去 14 日間に複数のオープンなランタイムアラートがある。
   - agent の活動に悪意のある URL が現れ、agent がその URL に tool call を行った。Agent Behavior Defense がこれをブロックした（タスクからの逸脱として扱われる）。
   - 3 つ目として、credential が追加のサードパーティ connector に送られようとした。
   - この agent はデータシステムへの書き込み権限を持ち、役員が所有している。そのため blast radius が重要になる、と説明されている。
5. これらのシグナルは、ブロックされることに加えて、Agent 365 の admin center に届く。Check Point のアラートは、同じ agent の同じケースで Microsoft のアラートと並んで表示される。

## 7. 注意点・発表者の気付き

- known agent でも、データの露出、過剰な権限、tools を通じたリスクのある操作が起きうる。登録は出発点であり、コントロールを適用できて初めて保護になる。
- 権限だけでは、安全性と生産性のトレードオフを解決できない。Check Point は、blast radius の制御と、意図に沿った行動の制御の両方が必要だと述べている。
- 一見正当な操作（本番バックアップや、ローテーション前の credential のローカルコピー）でも、ローカルにデータが残ると、ローカルのツールがそれを外に出すリスクになる。意図に基づく制御が、そうした操作を止められた事例として紹介された。
- 可視化は判断ではない。Lumen は、見えていることと、承認・拒否の判断を分けている。
- 公式概要の表現にあるとおり、利用できるコントロールは「サポートされているもの」に限られ、governance の機能は進化の途上にあります。発表でも、Shadow AI のコントロールを使い、「機能の進化に合わせてガバナンスを計画する」ことが playbook の 3 番目に入っています。具体的なロードマップの日付は語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- Agent 365 で、既知の agent と Shadow AI の両方を 1 か所で見られる。Shadow AI には、検出数と未検出数の両方が表示される。
- インスタンスごとの LLM、OS、tools、リスク、exposure、blast radius、推奨事項が見え、そこから ServiceNow や Azure DevOps に case を作れる。
- ブロック、デバイスの non-compliant 化、ネットワーク制限、コンテナーでの isolation など、段階の異なる対処を選べる。未検出のインスタンスにも、先回りでポリシーを適用できる。
- Zenity や Check Point などの既存のセキュリティ投資を置き換えずに、そのシグナルを Agent 365 に集約できる。Zenity の findings は Defender の findings と相関付けられ、Check Point のアラートは Microsoft のアラートと同じケースに表示される。
- Lumen Technologies は、可視化から文脈、比例的な判断へ進めることで、何を誰が使うべきかについて明確な説明責任と、一貫した判断が得られ、学習ループとしてガバナンスを継続的に見直せると述べている。

## 9. まとめ

月曜朝のトリアージは、次の 3 ステップです。

1. 登録と、エビデンスに基づくレビューで、知っている agent を守る。
2. インベントリの外の活動を見つけ、使える文脈をたどる。
3. Shadow AI に対しては、サポートされているコントロールを使い、機能の進化に合わせてガバナンスを計画する。

Agent 365 は Shadow AI の observability のギャップを埋め、Zenity の意図ベースの制御と、Check Point のランタイムの監査・制御のシグナルを 1 つの画面に集める、というのが発表の位置づけです。最後に Brendan が投げかけた問いが、発表の要点を表しています。自分たちのセキュリティプロセスは、知っている agent だけを対象にしていないでしょうか。まだ見つけていない活動まで届いているでしょうか。
