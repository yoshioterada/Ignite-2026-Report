# BRK521 Frontier Partners: Delivering agents to accelerate Industrial AI

## 1. はじめに

このセッションは、製造業を中心とした「産業分野」で Microsoft と組んで AI ソリューションを届けたいパートナー企業に向けた、パネル形式の発表です。冒頭で Microsoft の担当者が FY27 の go-to-market（市場への出し方）の考え方を説明し、その後、Microsoft のエンジニアリング、パートナー組織、そしてパートナー企業である Sight Machine の CEO が、実際の協業の進め方を語り合います。

技術的な機能解説やアーキテクチャの発表ではありません。語られているのは、**「ビジネス成果から入る」「数カ月で 1 つの成功を作る」「その成功を再現・拡大する」** という進め方です。あわせて、Microsoft Marketplace やパートナー向けプログラムの使いどころ、顧客事例（Chevron、Husqvarna、Toyota）も紹介されています。

## 5. 発表内容の詳細

### 5.1 冒頭のビデオと Microsoft の AI 導入の見方

セッションはビデオで始まります。蒸気、組立ライン、ロボティクス、そして機械が「見る」ことを助ける時代へと産業の歩みをたどり、いま知能があらゆる層を流れているというメッセージで、キャッチコピーは「Microsoft, industrial intelligence unlocked」でした。

Lindsay は、この「Microsoft は単独で担うのではなく、パートナーとお客様が使うプラットフォームとして提供する」という点を強調します。お客様はすでに「部分的な導入」の段階を越え、バリューチェーン全体へ規模を広げることを考え始めている、という認識です。

Microsoft が考える frontier transformation の進め方は、(1) 将来のビジョンを描く、(2) 変革の機会が最も大きい中核領域を特定する、(3) 成功を届ける、の 3 段階です。戦略的な投資領域（strategic bets）として挙げられたのは、次の 5 つです。

- Copilot
- Agentic AI
- Physical AI
- データプラットフォーム
- OT セキュリティ

### 5.2 use case 起点の go-to-market

AI の領域は広すぎるため、お客様と一緒に「これまでに成果が出た場所」を洗い出した use case の一覧を作り、それを起点に市場へ出ているという説明です。use case の特定は今後も進化し続ける作業であり、フィードバックを歓迎するとも述べています。

現時点の最重要の目標は「ビジネス成果で先導すること」です。これを次の 3 点の組み合わせと位置づけています。

1. ビジネス成果を会話の中心に置く
2. time to value を意識する（5 年かかるものではなく、成果を示せるところから始める）
3. パートナーが過去に出した実績と強く結びつける

こうして「use case があり、それを実現するソリューションがあり、似た課題を持つ他のお客様で機能した証拠がある」という value story を作ります。個別の成功例や実験から、お客様が予測し頼れる「繰り返し可能な効果」へ進むことが目標です。

### 5.3 エコシステムの重要性と FY27 の go-to-market モデル

Lindsay は、パートナーとの協業に関する数値を 2 つ紹介しています。

| 項目 | 数値 |
| ---- | ---- |
| 反復的・通年のパートナー主導の共創に取り組んでいる上位企業の割合 | 48% |
| 製造業のプロジェクトのうち、戦略パートナーが少なくとも 1 社関わるものの割合 | 60% |

パートナーは大手から、ニッチなソリューションを持つ小さな企業まで幅広く含まれます。AI ではドメイン専門知識が差を生み、パートナーがそれを持っているほど、業務プロセスの中で AI がすぐ価値を出せる箇所を見つけやすい、という説明です。さらに、パートナーは AI ソリューションを時間をかけて拡大するための「チャネル」でもあると位置づけています。

FY27 の go-to-market モデルは、「お客様から始めて、ワークフローを特定し、価値への道筋を設計する」流れです。お客様とのアイデア出し、適切なパートナーとエンジニアリングソリューションの投入、価値の拡大、という動きが全体の設計になっています。

このセッションのねらいは、パートナーとエンジニアリングを含めバリューチェーンの各所の人から、実際にどう機能しているかを聞くことだと説明されています。工場が何を必要とするかを理解している Microsoft のエンジニアリングチームと、ドメインに深いパートナーが組んでいる点が、ここでの前提です。

### 5.4 共同開発（co-build）に値するパートナーとは（Mike の答え）

Lindsay の質問は、「パートナーが再現可能なソリューションを持っていることが共同構築の前提になるが、どの時点で co-build に良い状態だと分かるか」です。Mike は次の観点を挙げています。

- ソリューションが PowerPoint のスライドにとどまらず、お客様に届けたときに簡単に、最初から動くこと（テスト済み・検証済みで、背後にリファレンスがあること）
- 一緒に事前の準備（homework）をしていること
- パートナーが、自分たちが解く問題と Microsoft の提供物との関係を理解していること。境界や重なりがあることを理解し、それを一緒にうまく扱えること

### 5.5 成功するパートナーシップの条件

**John の見方。** まず、お客様に何が必要か（具体的な ROI を伴う早い勝ち）と、Microsoft・自社が何を達成する必要があるかを考えます。その重なり（Venn diagram）は、ほとんどの場合うまく見つかります。関係者は少なくとも 3 者、おそらくそれ以上で、製造企業の中では IT の関係者、オペレーションのリーダー、工場の人たちを考慮する必要があります。さらに、案件の前・最中・後を通した人間同士のコミュニケーションが重要だと話します。産業のプロジェクトに簡単なものはなく、直線的には進まないからです。

**Jason の見方（win activation formula）。** 他のセッションの内容も含めて、成功の公式を整理していると断ったうえで、4 つの「foundational anchors」を挙げています。

| 順番 | アンカー | 説明（発話に基づく） |
| ---- | ---- | ---- |
| 1 | customer zero | 自社が技術やサービスを使い、学び・開発・痛み・落とし穴を共有することで、お客様への信頼性と差別化を作る |
| 2 | Microsoft のリソース | Frontier Transformation や Industry Hub などを活用し、ソリューションを use case や業界の vertical に合わせる。ペルソナ、ROI、halo の会話も揃う |
| 3 | 見つけてもらう | Microsoft Marketplace に公開し、営業担当とお客様が内容を識別・理解できるようにする |
| 4 | プログラム・ツール・投資 | MAICPP、Partner Center、Frontier Accelerate など。資金などの支援がある |

> 注意：「MAICPP」は、音声認識の都合で表記が確定できません（後半では「MAICPV」とも書き起こされています）。発話では、これがパートナーにとって Marketplace や Partner Center、各種プログラムへの入口になるものとして説明されています。

これらが揃えば「ほぼ到達」で、go-to-market の各種レバーと共同販売（co-sell）の力が働き出す、と Jason は述べています。パートナーシップがこの成熟した状態に達するまでに、数年かかったとも話しています。

### 5.6 Marketplace とプログラムの活用（John の経験）

John が特に有用だったと挙げたのは次の点です。

- **Marketplace:** 購入の摩擦を減らし、スケールを助ける。
- **インセンティブプログラム:** 毎年、プロジェクトの資金を得る機会がある。これを使い、お客様との動きを速くする。

具体的な成果として、過去 1 年で、製造業の分野で 20 社を超える企業に共同でサービスを提供したと述べています。妥当な金額で案件を始め、2〜3 カ月で「勝ち」に到達する進め方です。John は、製造業の時間感覚ではこれが「光速」だと話します。製造企業は最初のプロジェクトで数百万ドルの価値を生み、Microsoft はクラウドと AI の提供で大きな成果を得て、Sight Machine もサービスプロバイダーとして問題なくやっていける、という三者の見立てです。

さらに、最近は 1 社のパートナーと Microsoft だけでなく、複数社のチームで取り組む段階にあるとも言います。SAP をプロジェクトに入れ、D365、Teams、Copilot など Microsoft の他の提供物も使います。Microsoft のプログラムが必要な部品を揃えてくれるため、ソリューションを素早く組み立てられるという説明です。ただし、Microsoft 内には多くのチームがあり、それぞれ目標とインセンティブがあります。これを理解して組み合わせることが、関係の速度を引き出す鍵だったと John は述べています。

もう 1 点、Microsoft が何年も前に業界を率いると決め、世界の 1 万社の製造企業と関係を築き、ドメインを研究してきたことが、共同で動くうえで大きな強みになっているとも語っています。お客様は技術だけでなく、「自分たちの仕事を理解している相手」を求めるからです。

### 5.7 協業から得た学び（Mike と John）

**Mike の学び**（パートナーと協業して得たもの）

1. 人間的なつながり、継続的な接触。共同ピッチで、お互いが信頼し合っている関係かどうかは、お客様にすぐ伝わる。
2. 言ったことを届けてくれる相手と最もよく働ける。Microsoft 側も完璧ではなく、エンジニアリングの遅れを抱えることがある。その場合は、頼りにしているパートナーに遅れを伝えることになるが、遅れそのものが関係と共同の勢いを損なう。これは双方向の話であり、「ビジョン」を売る前に、まず「トラックに積んであるもの（実際にあるもの）」を売るほうが成果が出る。

**John の答え（Microsoft エンジニアリングがまだ「作っている最中」の製品に関わること）。** Lindsay の質問は、Microsoft のエンジニアリングが製品をまだ作っている段階でパートナーが関わることについてです。John は、それは「関われる機会」だと答えています。2 つの観察を共有しています。

- パートナーが Microsoft の製品・エンジニアリングの人たちと実際の関係を築くことは、例外なく良いことです。相手が方向性を考えている最中に関わると、互いに学び、影響を与え合えます。お客様もこれを理解しています。
- 今は全く新しい時代で、6 カ月、9 カ月、12 カ月かけるソフトウェアの設計・リリースサイクルではありません。AI のアーキテクチャは、「文脈（context）を持つデータ」と「harness」などの重要な部品の組み合わせでエージェントを動かすもので、これは各社・各チームが非常に速く作れます。自社の数人と Microsoft の数人が集まり、早く何かを作れば、勢いが出ます。

他のパートナーへの励ましとして、「まず始めること」、つまり成果と価値が定義された何かを作り始めることを挙げています。エージェント時代はツールがそろっており、Microsoft が end-to-end のプラットフォームを用意しているので、見かけほど難しくないという説明です。「まだ全部は分かっていない。一緒にどうやるか」と言ってよい、とも述べています。

### 5.8 営業組織との連携と、お客様との会話の変化

#### 5.8.1 営業組織とどう連携するか（Jason）

最初の勝ちを得たら、次の動きは「repeat and scale」です。既知のパートナーでも新規でも、顧客の成功事例（customer success story）や win wire を作ることで、パートナー自身の delivery チームや account チームだけでなく、Microsoft の営業担当の認知を高められます。営業担当がそれを理解し、自分のお客様に持ち込めるようになります。

また、成功事例があれば、次の業界イベントのステージで共有されるソリューションになるかもしれません。Microsoft は多くの共同販売の取り組みで、パートナーを営業と結びつけています。これが Microsoft の顧客エンゲージメント手法である **MSEM** につながります。MSEM は、初期の探索的な会話から、導入、最適化、そしてより大きなワークロードへの拡大までを通した、共同販売と go-to-market の進め方だと説明されています。

#### 5.8.2 IoT から AI へ：お客様との会話はどう変わったか（Mike）

Mike は、IoT 出身の立場から、お客様との会話が変わったと話しています。

- お客様はまず C レベルから AI やエージェント型 AI の話を聞き、「うちはどう使っているのか」というトップダウンの指示が降りてきます。同時に、現場からも「自分の仕事を効率化できないか」というボトムアップの動きが出ています。この 2 つの会話をつなぐのが役割です。
- 工場フロアのマネージャーやプロセス自動化のエンジニアは、成功を早く示すことを気にします。彼らは OEE のチャートに関する根本原因分析（root cause analysis）のリストを片づけるのに追われており、新しい技術の導入に時間を割くのは難しい状況です。そのため、技術がそのリストを手放させてくれること、日々の繰り返し作業を解決できることを理解してもらうことが重要です。
- パートナーを入れるときは、お客様が今いる場所に合わせます。多くの場合、お客様はすでに SI、オートメーションのパートナー、ISV などを選んでおり、モデルが必要だと考えて調査を始めていることもあります。そこで、パートナーとの共同の価値提案を探します。
- 重なる領域でも、Microsoft はパートナーに「売るな」とは言いません。お互いの P&L を左右するものを率直に共有し、お客様の必要を最優先にしながら補完的な形で価値を出す、という姿勢です。

Lindsay は、産業の DNA を共有する他のパートナーと組むことが、信頼面でも違いを生むと補足しています。

#### 5.8.3 工場の現場に響く進め方（John）

John は、同じ状況をパートナーの側から語っています。この 15 年で今が最良の時期であり、経営層・取締役会からは AI 戦略とイノベーションを求められている一方、肝心なのは実際に働く人たちだ、と述べています。工場では、いつも問題が起きており、うまくいかなかったプロジェクトもあり、そこへ本社から新しい提案が来ます。そのため、「hearts and minds（心と頭）」を勝ち取る必要があります。

具体的には、Microsoft のプラットフォームとツールを使えば、お客様のために行う内容のデモを、Fabric、Adaptive Cloud、RTI、Copilot などを組み合わせて数日で作れると話します。お客様のデータを使う場合もあれば、お客様の運用データそっくりの合成データ（synthetic data）を使う場合もあり、お客様はそれで問題ないそうです。これを一緒に見せると、Microsoft のアカウントチームも「自分がコミッションを得る対象がこのパッケージに入っている」と盛り上がります。お客様にとっての成果の価値も、アカウントチームにとっての販売の価値も計算でき、数週間で提供まで持っていけるといいます。

John は、**90 日を超えると顧客を失う**とも言います。1 つの季節が過ぎても盛り上がりがなければ終わり、という感覚だそうです。目指すのは、工場や倉庫の人たちが「これを取り上げないでくれ。必要だ」と言う状態です。ここまで来れば、スケールの話は簡単になるとのことです。

Lindsay は、決め手になるコンテンツは、お客様の環境に合わせて作り込んだデモだと同意します。出来合いのデモではなく、「製品のデモ」であるべきで、「AI の見せかけ（vaporware）」ではいけません。「これがあなたのデータで、Microsoft のスタックの上にあり、触ってみてください」と言えることが重要だ、という趣旨です。

#### 5.8.4 「pointy（的を絞る）」ことと ROI の具体性

Jason も、お客様の成果、use case、time to value に絞って（pointy に）進めることを勧めています。Microsoft は go-to-market の枠組みをこの方向に再編したとも述べています。

続けて登壇者の一人（発話からは名前を特定できません）が、工場の世界は算術（arithmetic）で、ユニット数と 1 台あたりの価格で計算できるため、重要なユースケースのほぼ全てに ROI を置けると話します。Microsoft とパートナーは、ダウンタイムや品質の根本原因といった項目ごとの計算ツール（calculator）を作っており、例として「企業全体で 1% 改善すれば 6,720 万ドルの価値」という数値の出し方が挙げられました。「1 カ月で回収できる IT プロジェクトは他に無い」という発言もありました。

さらに、全員がまだ手探りの状況なので、本物のパートナーを見つけ、少し弱みを見せることも大切だと、同じ登壇者は話しています。できないことは認め、「それは我々の範囲外」と言えると、産業のお客様は信頼してくれるそうです。

### 5.9 信頼、パッケージ化、再現性

**デモと「再現性」（Mike）。** Mike は、デモはお客様の現場で動くことを示せるため有効だと述べます。さらに、公開された事例（public references）と再現性が、お客様の安心感を作ると言います。お客様が心配するのは、次のような点です。

- 自分だけのために作り込まれた、他では動かないソリューションではないか
- 作り終えたパートナーがいなくなり、サポートの受け方が分からなくならないか
- 長期のパートナーでなかった場合や、調達部門が方針を変えた場合はどうなるか

これに対し、「何度も実施済みで、あなただけではない」と示せることが重要で、動くデモと過去の実績の両方があるときに強い提案になる、という話です。

**Microsoft の長期コミットメント（John）。** John は、産業のお客様は「うちは 100 年続いている。あなたたちも 100 年続くか」と考えている、と話します。Microsoft は続くだろうという信頼があり、Microsoft が信じてスケールの方法を知っているかどうかも見られます。Mike が共同のお客様との朝 6 時の電話会議に出て「我々はこれを信じており、一緒にやる」と伝えた例を挙げ、Microsoft のリーダーシップによるコミットメントが信頼を作ると言います。パートナーの技術がどれほど優れていても、Microsoft が支えると示されなければ意味が薄い、とも述べています。そのため、自社の説明をしたい気持ちを捨て、ソリューションに集中し、Microsoft と実際に一緒に進めることを学んだそうです。

**パッケージ化。** Lindsay は、お客様は特別扱いを望み、実験台にはなりたくないという点を挙げ、複数パートナーのパッケージをどう考えるかを尋ねます。これに答えた登壇者（名前は明示されていませんが、John の発言に言及しているため John 本人ではありません）は、次のように話しています。

1. 最初に、自分たちの限界、相手の限界、一緒には解けないものを明らかにする。それにより、別のパートナーが必要か、お客様側の開発が必要かが分かる。
2. 一緒に解ける問題の範囲を、境界のある、繰り返し可能なものとしてパッケージ化する。「万能」ではない。境界が分かれば、パッケージ化、複製、拡大ができる。
3. 一晩ではできない。アーキテクチャ、データの受け渡し、コネクタモデル、情報モデルといった地味な細部を、お客様の前に出る前に一緒に詰める。そうすれば、お客様の前でも簡単に動き、導入と成果が早く、「1 つの季節以内」に届けられる。

**再現性とスキル習得（Jason）。** Jason は、産業分野でも再現とスケールの動きが現れており、formula に従えば確認できると述べます。use case は複雑ですが ROI があります。パートナーの準備として、Microsoft は認定、specialization、**Frontier Transformation の engineering badge**（約 100 時間の時間投資が必要）を用意しており、hyper-velocity engineering の観点もあると説明しています。これが、再現性、実装、スキル習得を通じたお客様での成功につながるという位置づけです。

### 5.10 Microsoft と組む価値（John）

Lindsay の「Microsoft の go-to-market で最も価値があった点は何か。プラットフォーム企業であることか、ドメイン知識か」という問いに、John は次のように答えています。

- **end-to-end のビジョン。** Sight Machine は「工場を直す」ことに集中していますが、製造企業にはサプライチェーンや需要側もあります。工場だけ直しても他が不均衡になれば、売れないものを作ったり、必要な材料が足りなくなったりします。Microsoft は企業全体にわたる end-to-end のプラットフォームによる AI とデジタル変革に、長年「大胆で揺るがない」ビジョンを持ってきた、と評価しています。経営層が AI に目を向けている今、そのビジョンが響くという話です。
- **パートナーとの協業の姿勢。** 多くの企業は「チーム」や「パートナー」と口にするが実際には信じられていない、と前置きしたうえで、Microsoft には「パートナーが成功すれば Microsoft も成功する」と本気で考える人が多くいると述べています。皮肉の意図はないとのことです。ただし、全員がそうだとは言えず、いつも一直線だったわけでもないとも付け加えています。
- **失敗から学ぶ姿勢。** 「完全にうまくいかなかったこと」もあり、そのたびに双方で「何を学んだか、次どうするか」を話し合ったことを、本当のパートナーシップだと評価しています。この文化が、さらに投資を深めたい気持ちにつながったそうです。

Lindsay は、これは会社の根本的な信念で、Windows の時代からエコシステムであり、単独の戦略ではなかったと補足しています。
