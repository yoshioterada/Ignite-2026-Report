# BRK203 Copilot Code: Build custom solutions for your unique needs

## 1. はじめに

このセッションは、Microsoft Copilot の新しいコーディング体験である **Copilot Code** を紹介するものです。業務の中にある「この作業を楽にしたい」というアイデアを、エンジニアリングの待ち行列に並ばずに、自然言語で動くアプリやダッシュボードに変えられる、というのが発表の骨子です。

発表では、HR の担当者が Copilot Code で作ったトラッカーの事例、模擬の小売企業を使った 2 つのライブデモ（店舗向けアプリの試作、プロダクト責任者の個人用ダッシュボード）、そして管理者向けのガバナンス・セキュリティ・コスト管理の説明が順に続きます。アプリを作る側（情報ワーカー）と、それを管理する側（IT 管理者）の両方に向けた内容です。

## 3. 何に関する発表か

Copilot Code は、情報ワーカーが自分の仕事に必要なツールを自分で作るための機能です。AI が仕事のやり方を変えていくなかで、Copilot では 4 つのテーマが現れていると説明されました。

| モード | 主に向くタスク |
| ---- | ---- |
| chat | 下書き、要約 |
| co-work | 調査、成果物（アーティファクト）の作成 |
| code | アプリやトラッカーの構築 |
| autopilot | 長期的なゴールの委任 |

発表の流れは次のとおりです。

1. Copilot Code の背景と、顧客事例（HR のトラッカー）
2. 模擬企業 Lakeshore Retail でのデモ（店舗向けアプリ、個人用ウィジェット、共有）
3. 管理者の視点：ガバナンス、セキュリティ、コスト（ROI）
4. 3 つの持ち帰りポイント

## 4. 発表者が伝えたいメッセージ

Copilot Code の出発点は、「仕事をしている人こそが、自分に必要なツールを一番よく知っている」という観察です。ところが現状は、毎日 15 分かかる反復作業を自動化したいと思っても、IT 部門やエンジニアリングチームの依頼リストに入れて、優先順位づけ、開発、デプロイ、保守を待つことになります。その問題に悩んでいるのが自分だけなら、依頼が上位に上がる可能性は低く、永遠にその 15 分を抱えるかもしれません。

そこで Copilot Code は、スキルセットに関係なく、誰でもアプリを作れるようにすることを目指しています。一度もアプリを作ったことがない人にも、少しコードを書いたことがある人にも合わせ、社内のデータを使ってアプリを役立つものにします。同時に、**アプリ作りの中心にガバナンスを置く**ことで、管理者もエンドユーザーも安心して使えるようにする、という考えです。進め方は「安全に作り、改良し、共有し、スケールさせる」と表現されました。

## 5. 発表内容の詳細

### 5.1 顧客事例：HR の人材育成トラッカー

発表者は、Frontier で提供を始めて数週間の間に、実際の顧客が作ったアプリを見て、想像していなかったユースケースが多いと述べています。例として、ウィスコンシンの電動モーターの会社（トランスクリプトでは「Regal Rexnerd」と聞こえます。音声認識の都合で表記が確定できません）の HR リーダーの事例が紹介されました。

この会社では、全マネージャーが集まる、人材育成についての四半期ミーティングがあります。以前は、ミーティングでアクションアイテムが決まっても、時間とともに優先度が下がり、次の会議のときには振り出しに戻って勢いを失っていました。そこで HR リーダーは Copilot Code に、自然言語で「トラッカー」を頼みました。

Copilot は **Work IQ**、会議のトランスクリプト、SharePoint のアセットを使い、適切な担当者に割り当てられたアクションアイテム入りのトラッカーを作成しました。組織内に共有でき、各マネージャーは、アプリを開くと自分の作業項目が表示され、ステータスと進捗を設定できます。次の会議では、3 か月前と現在の差を見て行動でき、説明責任と勢いが保たれるとのことです。

発表者が最もよく聞くフィードバックの一つは、「プロンプトを送ったときに、期待以上のものが出てきた」だそうです。良いトラッカーにはコーディングや日付、フィルターが必要だと、情報ワーカーが知らなくても、Copilot が数百万のアプリから学んだ知識でそれを補う、と説明しています。

### 5.2 デモの舞台：Lakeshore Retail

デモに出てくる会社は実在せず、**Lakeshore Retail**（家具とアウトドア用品の小売）という模擬企業です。Dynamics 365、Power BI、Microsoft 365 の構成で、データは、実際のテナントに、実際のコネクターを使って入れたサンプルデータだと説明されました。

### 5.3 Copilot Code の仕組み：モード、サンドボックス、プラグイン

デモの合間に、Copilot Code の構成が説明されました。

**ローカルとクラウド**

| 項目 | local | cloud |
| ---- | ---- | ---- |
| 実行場所 | ローカルのオーケストレーターが、コードをローカルに保存し、アプリもローカルで動かす | クラウドのコンテナーでアプリを構築し、コードもアプリもクラウドに置く |
| サンドボックス | Windows のサンドボックス内で動く。アクセスできるデータとネットワークエンドポイントが制限される | コンテナー自体にもサンドボックスがあり、制約される |
| 共有 | （この説明では触れられていません） | チームメンバーと共有しやすい |

ローカルのサンドボックスは既定でオンで、オフにできません。管理者が信頼するユーザーに対してのみ、オフにすることを許可できます。ローカルの選択肢は、管理者が有効にしているために使えた、との説明もありました。

**関わり方のモード**

Copilot の他のモードには無いドロップダウンで、コーディングでの関わり方を選びます。

- **interactive**（既定）：質問をしながら、やりとりを重ねる
- **plan**：一緒に何をするか決めるまで、コードを書かない
- **automatic**：質問で邪魔せず、ゴールに向かって進む

**プラグイン**

プラグインは Copilot のすべてのモードで共通で、Cowork や chat で使うプラグインは code でも使えます。Power BI、Dynamics、Fabric などの first party や、Adobe、Canva などの third party があり、**350 のプラグイン**がすべて code で動くと説明されました。Copilot は、スキーマを問い合わせ、データの様子を見てから、どのビューを作るか決めます。プラグインは管理者が管理できます。

Andrew 氏は、権限モデルについても述べています。ワークスペース外のファイルや、ネットワークホストにアクセスしようとするたびに、ユーザーに許可のプロンプトが出ます。プラグインも、管理者とユーザーの両方が有効にしたものだけが使えます。

### 5.4 管理者向け機能

Andrew 氏は、顧客が最初は期待するものの、多くの疑問や懸念を持つと述べ、それを 3 つに分類しました。

| 懸念 | 内容 |
| ---- | ---- |
| ガバナンス | 開発者ではない人が公開するアプリの規模をどう管理し、リスクを抑えるか |
| セキュリティ | ソフトウェアエンジニアではない人が作るソフトウェアのもとで、会社とデータをどう守るか |
| コスト（ROI） | AI ツールが価値を出しているなかで、支出に見合う ROI をどう得るか（2026 年は、ほぼ全員の頭にある話題だと述べています） |

**アプリの可視性（ガバナンス）**

管理者の画面でアプリを一覧し、Lakeshore のアプリに絞り込むこともできます。作成者、利用状況、データ接続が確認でき、アプリのリスクを判断できます。作成されたアプリのユーザーが 1〜2 人なら低リスクだと考えられるが、社内で広まって 20,000 人が使うようになれば、業務上重要なアプリになり、作成者の手に余る可能性がある、と述べています。そのときは IT かエンジニアリングチームが引き継ぐ判断ができます。

**セキュリティ設定**

Copilot Code の設定ページで、ローカル開発の設定を、既定で安全な構成から組織に合わせて調整できます。紹介された設定は次の 3 つです。

- ローカルのサンドボックスを、誰もオフにできないようにする
- cloud だけにするか、cloud と local の両方にするか（環境そのものの有効化）
- GitHub アカウントの接続。GitHub の顧客でなければ、既定では許可されない（仕事のデータが個人リポジトリに行くのを避けるため）。GitHub Enterprise Cloud の顧客なら、接続を許す特定の URL を選べる

**支出ポリシー（ROI）**

Copilot Code は、利用量ベースの課金（usage-based billing）で動く多くの機能の一つです。Cowork を有効にしている組織には、なじみのある仕組みだと述べています。次の制御ができます。

- セキュリティグループ単位で、どのツールを使わせるかを設定する
- 月あたりの上限を、ユーザー単位と、グループ全体の両方で設定する。例として「各従業員に $500、ただし合計は $50,000 まで」が挙げられた

booth での顧客との会話も紹介されました。ベストプラクティスに決まった答えはなく、判断のための制御を提供するという立場です。その顧客は、全社に同額の支出枠を与え、さらに「高い支出者（high spenders）」のカテゴリーを設ける方針に落ち着きました。上限に達した人が追加を求めてきたとき、あるいは管理者から声をかけて、何をしているのか、実際の業務価値があるかを聞き、納得できれば、より高い上限に引き上げる、という運用で ROI を管理します。

**Microsoft の基盤**

発表の図では、左側が Microsoft の製品づくりの基盤（特に Microsoft 365 と Copilot）で、規制へのコンプライアンスなどが含まれます。右側は、製品ごとの調整で、リスクと脅威の検出など、組織に合わせて調整できる制御です。いずれも、既定で安全な方向で提供されると説明されています。Marc 氏は、新しいクラウドアプリの管理方法を発明していない点が好評だと述べました。すべては **Copilot managed runtime** で、Copilot Studio、Cowork、Code に適用するのと同じ構成を使い、Code 固有の新しい設定を大量に作っていません。

## 6. デモ・手順

このセッションには、ライブデモがあります。画面の細部は音声からは確認できないため、語られた範囲のみを書きます。デモは、Marc 氏の店舗向けアプリ（途中で何度か戻る形で進行）と、Andrew 氏のローカルアプリの 2 本です。

### 6.1 Marc 氏：店舗の販売員向けアプリの試作

**設定された場面**：Lakeshore Retail で小売のイネーブルメントを担当する立場。店舗の販売員は、携帯端末で商品情報や SKU、店舗ごとの在庫を調べるアプリを使っています。テレメトリや販売員の声から、「客が特定の商品を求めたが、店舗に在庫が無い」という行き止まりがあると分かりました。客に別の店舗を探すよう伝えるしかなく、販売につながるかも分かりません。通常なら IT 部門に試作を頼みますが、今回は自分で作って検証します。

1. 販売員が使っている現行アプリの **スクリーンショット**を撮り、Copilot に渡す
2. 新しいプロジェクトを作成する。既存のプロジェクト（ローカルフォルダーや、GitHub アカウントを接続していれば、リポジトリのクローン）も使えるが、この場面では「コーダーではなく、GitHub アカウントも持たない」ため、新規作成にした。Scratchpad は、最初のブレインストーミングや簡単な質問に使えるが、今回は使わない
3. 大きなプロンプトを貼り付けて送信する。発表者は、「象のように目立つ大きなプロンプトで、本来の使い方ではない」と認めている。実際は、1〜2 文で始めて、やりとりしながら固めていくのが想定で、詳細を与えすぎるとモデルの動きを制約してしまう。今回は、デモとして最初のプロンプトから望みどおりの見た目にするための近道だった
4. Copilot は、プロンプトに「販売員と共有したい」と書いてあることから、クラウドで始めることを提案した。「continue in cloud」を選び、クラウドのセッションに引き継がれた
5. 構築中の間に Andrew 氏のデモ（6.2）に移る
6. 約 5 分後に戻る。プロンプトで「ライブのデータソースにつなぐ」ように頼んでいたため、パイロット店舗に送れるよう、在庫をリアルタイムで参照する。Dynamics や ERP システムにつながっていると説明された。店舗を選べる
7. 商品検索（item lookup）が配線済みかを確認する。Copilot はまだ作業中で、アプリが数回更新される。構築、テスト、準備確認のエンドツーエンドの流れを自分で行っており、ユーザーが QA をして不具合をフィードバックする必要がない、と述べた
8. 依頼しておいた「代替品を探す（find alternatives）」ボタンを、在庫切れの商品（店舗名は「Sale North Gate」と聞こえます。音声認識の都合で表記が確定できません）で押す。以前は行き止まりだったが、似た在庫品が 1 件表示され、販売員が薦められる
9. 利用コストを確認する。フォローアップで cost を尋ねると、セッションのこれまでの費用を示す。結果は **555 credits、約 $5** だった。完成済みの別セッションに切り替えて実演した
10. フォローアップのプロンプトで、「complete the set」（関連商品をセットで薦める機能）の追加を依頼する。画面上部には、クレジットの割り当てに対する使用状況を示すゲージが常にある
11. 普段は、Copilot に作業を任せて席を離れても、スマホの Copilot アプリに完了や追加質問の通知が届くため、PC の前で待ち続ける必要はない、と説明された（この場面では実演せず、完成版に進んでいます）
12. 完成版を確認する。代替品の選択に加えて、complete the set の機能が入っている
13. 共有する。Word 文書のリンクをコピーして Teams で送るのと同じくらい簡単で、Andrew 氏が店長の役でリンクを受け取った

プロジェクト全体の結果について、「1 時間未満、約 $10 で、ライブデータにつながった動くプロトタイプを最初から最後まで作った。IT 部門を煩わせず、3 週間分のプロセスを短縮した」と述べています。パイロットが失敗しても無駄にしたのは 1 時間で、成功すれば他店舗への展開につながる、という説明です。

**Andrew 氏による受け取り側の確認**：Teams でリンクを受け取り、開くとデータを読み込んで表示される。アプリを開けるのは、元のデータソースにアクセスできる人だけで、店長の Andrew 氏は Dynamics の在庫データにもアクセスできるため読める、と説明された。共有は Copilot managed runtime を通じて行われ、管理者の観点でデータの確認や、アプリについての判断ができる。

### 6.2 Andrew 氏：プロダクト責任者の個人用ローカルアプリ

すでに作成済みのローカルアプリを使ったデモです。

**設定された場面**：Lakeshore Retail の product lead で、Web サイトとモバイルアプリで、商品検索、カート追加、支払い、フルフィルメント開始までが良い体験になるよう責任を持つ立場。Power BI のダッシュボードや、課題管理に使う Azure DevOps のクエリなど多くの場所を見る必要があり、壊れたものについての連絡に受け身で対応しがちなので、自分の作業のためのウィジェットを、ローカルで Copilot Code に作ってもらった。

1. 依頼の過程で、interactive モードだったため、Copilot が質問をしてきた。**Fabric IQ** と Azure DevOps のデータソースを見つけ、「これで正しいか」と確認し、確認後に構築を始めた。いくつかの質問に答えると、依頼した内容が完成した
2. 画面の右側がプレビューで、アプリを別ウィンドウに切り出せる。切り出しても、メインアプリと同じサンドボックス、権限モデル、データの制御が効く
3. 朝の利用を想定して開く。Web サイトのトラフィックは上昇、検索からカート追加までのコンバージョンファネルも前週比で上昇
4. チェックアウトに進むと、**チェックアウト完了率が 4.4% 低下**している。指標は Fabric IQ から、下側のバグは Azure DevOps から来ており、「住所を変更すると支払いボタンが反応しない」という課題が複数あると分かる
5. そこから、誰が取り組んでいるかを確認し、適切なチームが適切な課題を優先しているかを確かめ、カスタマーサービスに知らせる、という動きが取れる。4 つのシステムを個別に見に行く必要がなかった

## 7. 注意点・発表者の気付き

- Marc 氏は、デモで使った巨大なプロンプトは「本来の使い方ではない」と述べています。1〜2 文のあいまいな指示から始め、詳細を与えすぎないほうが、モデルの動きを制約しないという助言です。
- アプリを共有しても、アプリを開けるのは、元のデータソースにアクセスできる人だけです。
- ローカルのサンドボックスは既定でオンで、管理者が許可しない限りユーザーはオフにできません。ワークスペース外のファイルや新しいネットワークホストへのアクセスには許可のプロンプトが出ます。
- アプリが社内で広まり、利用者が大きく増えた場合は、IT またはエンジニアリングチームが引き継ぐことを検討します。
- GitHub を使わない顧客では、仕事のデータが個人リポジトリに流れないよう、GitHub の接続は既定で許可されません。
- コストは使った分だけかかります。デモでは、セッションの費用を、セッション内で尋ねて確認していました。
- ここで示されたデモ用のデータは、サンプルデータです。実際の企業のものではありません。
- 料金体系の詳細（クレジット単価など）は、発表では触れられていません。「555 credits が約 $5」という例のみです。

## 8. 利用者にとっての利点

- **待ち行列に並ばずに試せる**：デモでは、1 時間未満・約 $10 で、ライブデータにつながるプロトタイプを作り、「3 週間分のプロセスを短縮した」と説明されています。パイロットが失敗しても、無駄にしたのは 1 時間
- **データにつながる**：プラグイン（350）により、Power BI、Dynamics、Fabric などのデータを踏まえて、Copilot がアプリを作る
- **作業を任せられる**：テストまで Copilot が行い、完了はスマホに通知される
- **管理者が統制できる**：アプリの一覧（作成者、利用状況、データ接続）、サンドボックス、cloud / local、GitHub 接続、ユーザー別・グループ別の支出上限
- **既存の管理方法を使える**：Copilot Studio、Cowork と同じ Copilot managed runtime の構成で、Code 専用の新しい設定が大量に増えない
- **事例**：HR の人材育成トラッカーでは、アクションアイテムが担当者に割り当てられ、各マネージャーが進捗を更新でき、次の会議で差分を見て、説明責任と勢いが保たれる

## 9. まとめ

発表者は「3 つの持ち帰り」と切り出しましたが、トランスクリプトで明確に述べられたのは最初の 2 つで、3 つ目は続く呼びかけです。

1. 問題の一番近くにいる人が、必要なツールを一番よく知っている。そこにコードを持っていけば、より多くのことを達成できる
