# BRK210 Work IQ: Powering Copilot for the Frontier Firm

## 1. はじめに

このセッションは、Microsoft 365 Copilot の「見えない部分」にあたる Work IQ を解説する 45 分のブレークアウトです。Work IQ は、メール、会議、チャット、ファイルといった仕事のデータに意味づけ（コンテキスト）を与え、Copilot やカスタムエージェントに渡す仕組みです。

発表の中心にある考え方は、「どのチームも同じ最新モデルを使える時代には、差を生むのはコンテキストだ」というものです。この記事では、Work IQ の 3 つの構成要素（memory / context / skills）、Dynamics 365 や Power Platform、コネクターとの連携、Work IQ を使ったアプリ作成のデモ、そして Agent 365 による管理までを、発表の順に整理します。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK210](https://ignite.microsoft.com/en-US/sessions/BRK210)

## 4. 発表者が伝えたいメッセージ

登壇者は、次の 3 点を軸に話しています。

- **同じモデルを使っていても、コンテキストを持つかどうかで結果が変わる。** 組織の M365 環境にあるコンテキストはモデルの入力枠に入り切らないため、「いつ、どのコンテキストを、どのモデルに渡すか」を決める層が必要で、それが Work IQ だという主張です。
- **Work IQ は Copilot の中だけのものではない。** M365 の基盤を、エージェント向けの API として開放しているという位置づけです。MCP や REST を通じて、他のエージェントや開発者の環境からも同じコンテキストを使えます。
- **エージェントが増えるほど、見えることと管理できることが重要になる。** Agent 365 が、エージェントの ID、権限、データアクセス、コストを一元的に扱います。

## 5. 発表内容の詳細

### 5.1 Work IQ の規模と、コンテキストが差を生む理由

登壇者は、仕事は区切りなく連続して進むものだと説明し、Microsoft 365 の規模を次の数字で示しました（週あたり）。

| 項目 | 数値 |
| --- | --- |
| Teams のチャット・チャネルメッセージ | 約 150 億件 |
| 送信されるメール | 900 億通超 |
| SharePoint と OneDrive の新規ファイル | 100 億件超（権限変更などの更新は含まない） |

Work IQ の背後にあるシステムは、19.5 エクサバイトのデータを扱い、1 分あたり 30 万件のアーティファクトに対して推論できるとのことです。ただし登壇者は「ポイントは大きさではない」と述べ、重要なのは、メールが届く、ファイルが更新される、権限が変わるといった変化に応じて、全体を処理し直さずにコンテキストを更新できる点だと説明しています。Copilot はこれをグラウンディング情報として使い、Teams 会議で意思決定を議論している最中にも、現状を踏まえて判断できます。回答は、ユーザーが M365 で持っている権限の範囲内に収まります。

次に、モデルとの関係です。登壇者によると、300K トークンのコンテキストウィンドウに入るのは 1〜2 MB 程度で、フロッピーディスク 1 枚ぶんの情報量です。一方、平均的な組織の M365 環境には約 600 テラバイトのコンテキストがあり、Teams メッセージや共有ドキュメントによって 1 分あたり数ギガバイト単位で変化します。コピー＆ペーストでは入りませんし、人手もかかります。そこで、適切なモデルに適切なタイミングで適切なコンテキストを渡す役割を Work IQ が担う、という整理です。

役割分担は次のとおりです。Work IQ が「モデルが理解すべきコンテキストは何か」を決め、モデルがそのコンテキストの上で推論します。

### 5.2 価格資料（pricing deck）の例

登壇者は、価格資料を作る場面を例に、ステップを追って説明しました。

- Work IQ は、メール、会議、チャット、CRM、人に関する情報からコンテキストを取得します。ただし**取得できるのはエンドユーザー本人が見られる範囲だけ**です。
- 作業中の PowerPoint だけが文脈のすべてではありません。チームのリアルタイムな変更、レビュー担当者への共有、付けられたコメント、価格の考え方を話している会議なども関係します。
- Copilot は、ユーザーの仕事の習慣に基づく memory も使って、より良い回答を作ります。

続けて Copilot での例が示されました。「Beacon」というデモ用プロジェクトの最新状況を尋ねる簡単なプロンプトで、ファイルの添付も背景説明もありません。Copilot は会議、チャット、ドキュメントからシグナルを集め、タスクとコンテキスト、複雑さに合わせてモデルを選ぶ auto model router に渡します。結果として、現在の状況と次に注力すべきことが、引用とパーソナライズ付きで返ってきて、新しい PowerPoint にも反映される、という説明でした。Work IQ が無い場合は、見た目は整っていても中身の薄い、一般的な回答になる、と登壇者は述べています。

会場向けに、次のようなプロンプトの試用も呼びかけられました。

- 上司からの返信が必要な最近のメールを探し、返信案を作る
- 過去 2 週間の、スキップレベル上司からのメッセージにフラグを付ける

上司やスキップレベル上司が誰かをプロンプトに書く必要はなく、M365 にすでにある情報が回答に反映される、という点が強調されました。

### 5.3 Work IQ の構造

John 氏が、左から右へ図を追う形で構造を説明しました。

- **左（入力）**：Microsoft 365 のデータ（メール、会議、チャット、ファイル）、Dynamics 365 や Power Platform などのビジネスアプリ、Microsoft 外のシステムをつなぐコネクター。
- **中央（Work IQ）**：これらに推論をかけ、memory、context、skills の 3 つに分けて扱う。
- **右（出力）**：Copilot、Copilot Studio、ユーザーが作るカスタムエージェントやアプリ。

3 つの意味は、memory が「重要なことを覚えていて、毎回やり直さなくて済むようにする」、context が「生産性データ、人、組織の情報を結びつける」、skills が「その理解を成果に変える」です。

### 5.4 Memory

Memory は、Copilot が時間をかけて「あなた」を理解する仕組みです。発表では次の順で紹介されました。

1. **カスタム指示と保存したメモリ**：仕事の進め方を伝えたり、覚えてほしいことを保存したりできる。以前からある機能。
2. **チャット履歴**：過去のチャットから学ぶ。伝えなくても理解が深まる。Copilot のチャットで有意義な仕事が行われている現状を踏まえ、これもコンテキスト層の一部になるという説明です。例として、「次の会議のアジェンダを用意して」と言うだけで、過去のチャットから特定の顧客会議だと分かる場面が示されました。
3. **メモリの引用（memory citations）**：先月発表され、GA になっている。回答の下で「sources」から「personalization」タブを開くと、その回答に使われた指示、メモリ、過去のチャットが分かる。例では 8 月 5 日のチャットが引用されており、そのチャットを開いて確認したり、保存されたメモリを削除したりできる。
4. **メールの文体（email writing style）**：Ignite の当日から GA として展開。口調、メッセージの構成、箇条書きを好むかどうか、相手が経営層かチームかによる話し方を学び、下書きが最初からユーザーらしくなる。カスタムスキルを書く必要もない。
5. **アプリをまたぐメモリ**：こちらも Ignite 時点で GA（書き起こしでは「not to general availability」と聞こえる箇所があり、発言は不明瞭です）。Word の下書き、PowerPoint のスライドなど、M365 のアプリ全体でユーザーのスタイルや好みが反映される。

> 注意：メモリの引用は、**メモリが回答を実質的に形作ったときだけ表示され**、常にユーザーのカスタマイズ設定に従う、と説明されています。

### 5.5 Context（productivity / people / organization）

登壇者は、「memory は Copilot を『あなた』に根付かせ、context は Copilot を『仕事そのもの』に根付かせる」と整理しています。Context は 3 つの領域から成ります。

| 領域 | 内容 |
| --- | --- |
| Productivity | Teams のチャット、Outlook のメール、会議のトランスクリプト、Office 全体のドキュメント。現在 Copilot が主に使っている領域。メールの添付も背景説明の繰り返しも不要。 |
| People | 自分の役割、上司、上司の上司、同僚のスキルなど。 |
| Organization | 会社の構造、用語、定義、ポリシー。ジョブファミリーや事業部門のような、その会社固有の属性も含む。 |

Ignite では、People と Organization のコンテキストの拡張が発表されました。例として、セキュリティポリシーについて Copilot に尋ねると、その組織にどのポリシーが当てはまるかを理解したうえで、そのテーマに詳しい人を紹介してくれる場面が示されています。

リーダー向けの例も語られました。新しい AI イニシアチブを立ち上げるプロダクトリーダーが、チーム内のデータサイエンスや機械学習のスキルの分布（ヒートマップ）と不足領域を確認し、アップスキリングの施策につなげる、というシナリオです。また、Copilot にはすぐ使えるスキルがあり、組織構造の分析ダッシュボードのようなカスタムダッシュボードも作れると紹介されました。

スライドでは、memory と context の機能の時系列（これまでに提供したもの、Ignite での新発表、今後の予定）も示されました。個々の項目は、音声からは詳しく分かりません。

### 5.6 Skills

Skills は、memory と context を「答え」ではなく「完成した仕事」に変える部分です。週次のステータス更新や顧客向けブリーフのような定型作業を一度まとめておくと、チームが速く動けます。スキルはプラグインとしてパッケージ化され、1 つのレジストリから、さまざまな Copilot の体験で使えます。スキルは Work IQ のコンテキストに基づくので、結果が一貫し、自社のビジネスに根差したものになる、という説明でした。

### 5.7 Dynamics 365 / Power Platform とコネクター

**Dynamics 365 と Power Platform が Work IQ で GA** になりました。Dynamics や Power Platform のデータが、生産性データと一緒に付いてくるため、ゼロから説明し直す必要がありません。

Microsoft 外にある知識は、コネクターで同じコンテキスト層に取り込まれ、同じセキュリティ制御に従います。コネクターは 2 種類あります。

| 種類 | 動き方 |
| --- | --- |
| Federated connectors | データは元の場所に置いたまま、Copilot が必要とした瞬間に取りに行く。 |
| Sync connectors | 組織のデータを Work IQ に取り込み、事前にインデックス化して、素早く検索・推論できるようにする。 |

スライドには 350 以上あるコネクターの一部が並び、これらは前日に公開された **plugin marketplace** に収められています。ServiceNow のコネクターなら、「このサービスはなぜ失敗しているのか」と聞いてインシデントやサービスの正常性を取り込み、Copilot 上でチケットに対して操作できます。Jira については、サービスのブロッカーやリリースリスクを例に挙げています。いずれも顧客の権限を尊重し、同じ Work IQ コンテキストの一部になります。

### 5.8 Volkswagen Group の事例

登壇者は、Volkswagen Group が Copilot を「副次的な実験」ではなく全面的に導入したと紹介しました。

- Copilot を、330,000 人以上の従業員に提供。
- テレメトリでは、30 万人以上が毎月 Copilot チャットを利用。登壇者は、Copilot を持つ人のほぼ全員が日常業務で使っている状態だと説明しています。
- Work IQ により、エンジニアリング、生産、調達、営業のより高度なシナリオに適用。
- 注目すべき数値として、**26,000 のアクティブなエージェント**。自分たちのプロセスのために自分たちで助けを作っている兆しだと述べています。

Volkswagen の担当者のコメントとして、「価値は、AI を日常業務の規模で使えるようにすることから生まれる」という趣旨の発言が紹介されました（担当者名は書き起こしで「Sophie, Vasarati」と聞こえ、音声認識の都合で表記が確定できません）。登壇者は、スライドに並んだ各業界の企業が Copilot を限定的なパイロットから本格的な規模へ広げており、共有コンテキストがあると、使う人が増えるほど価値が積み上がり、早期導入者の小さなグループにとどまらない、と述べています。各社の事例は、customers.microsoft.com で動画やストーリーを見られると案内されています。

### 5.10 エージェントにコンテキストを与える考え方

Amanda 氏は、新入社員を生産的にするには何が必要かというたとえで説明しました。優れた頭脳だけでなく、チームの標準的な手順、最初の 1 か月に会うべき約 30 人など、文脈を渡す必要があります。コンテキストは次の 3 つのバケツに分けられます。

1. **チーム、役割、ワークフロー**：どの組織か、上司は誰か、誰と働くか、つながるべき相手は誰か。
2. **状態（state）**：物事がどう進んでいるか、何が進行中か。
3. **キュレートされた知識**：ポリシー、手順、事例など、組織が整えてきた知識。

エージェントでも同じで、Copilot 自身でも自作のエージェントでも、オンボーディングにはコンテキストが必要だという主張です。M365 はこれまで人間が協働するためのプラットフォームでしたが、今後は人間とエージェントが並んで働き、共有コンテキストを作り上げていく世界になる、と話しています。

Work IQ が無い場合のエージェントは、迷路を進むようなものだとのことです。簡単な質問に答えるにも、ファイル、会議、メール、チャットを順に調べ、行き止まりに当たって何度も引き返します。遅く、費用もかかり、部分的な答えで終わることもあります。Work IQ があれば、エージェントは、自分がどう働いているか、誰と働くか、何が重要かを把握したうえで、正しい答えにまっすぐ向かえます。登壇者は、これは比喩だとしつつ、実測として次の数字を挙げています。

> Work IQ を使うエージェントは、従来の API と比べて、実行時間あたりの出力が 2 倍で、トークンは 80% 少ない。

80% というトークン削減について、登壇者は、エージェントを日常的に使うか、たまにしか使わないか、あるいは一部の優秀な社員だけに限るか、全員に開放するかの差になりうる、と述べています。

| 窓口 | 用途 |

### 5.12 Agent 365 によるガバナンスと AI の FinOps

エージェントが増えるにつれて、「AI が何を見られるか」「いくらかかるか」「エージェントに何をさせるかを誰が決めるか」が問題になります。Agent 365 は、エージェントの ID、権限、データアクセス、ライフサイクルのリスクを 1 か所にまとめ、ツールの乱立（tool sprawl）にも対応するもの、と説明されました。

- **管理**：エージェントとアプリ、使うツールを 1 か所に集めて、文脈のなかで見られる。
- **ガバナンス**：エージェントとアプリの所有者を明確にし、何が見られるかの権限と説明責任を持つ。
- **セキュリティ**：リスクを把握し、制御を適用し、ID、データ、エンドポイントを保護する。
- **ROI**：展開したエージェントのビジネス価値を、使った時間と費用の面から見る。

Agent 365 はビジネス価値の領域にも拡張され、**AI の FinOps** として次の 3 つが紹介されました。

1. **計画**：支出枠を展開する前に、AI の予算を計画・予測する。コスト見積もり機能もある。
2. **制御**：テナントや組織内のグループに予算を設定し、個々のユーザーに上限を設け、支出が上限に近づいたらアラートを出す。
3. **最適化**：AI の支出が、ユーザー別、グループ別、ワークロード別、タスク別にどこへ使われているかを見て、適切な Azure サブスクリプションなどに課金を振り替え、さらに投資する先を判断する。

## 6. デモ・手順

このセッションにはデモが 3 つあります。録音は音声のみなので、画面の細部は分かりません。以下は、語られた範囲の内容です。

### 6.1 Beacon プロジェクトの状況確認（Amanda 氏、5.2 で既出）

ファイルを添付せず、背景説明も書かない簡単なプロンプトで、Beacon というデモ用プロジェクトの最新状況を尋ねます。Copilot が会議、チャット、ドキュメントからシグナルを集め、auto model router に渡す様子が説明されました。結果は、現在地と次の注力点、引用、パーソナライズ付きで返り、PowerPoint にも反映されると語られました。

> 補足：この部分が実際のライブ操作か、事前に用意した画面かは、発話からは判別できません。

### 6.2 Fourth Coffee のプロダクトマネージャーのシナリオ（John 氏）

設定：John 氏は、オーストラリアに拠点を置くコーヒー会社 Fourth Coffee のプロダクトマネージャー役です。ニュージーランドへの拡大を検討しています。

1. 最初にダッシュボードを見せる（書き起こしでは「PowerPoint dashboard」と話し、続けて Power BI で絞り込めると述べています）。プロダクトマネージャーにとっての「信頼できる情報」であり、同じデータに、仕事の入り口として使うことが増えている Copilot からもアクセスできる、という流れ。
2. Copilot に「昨年オーストラリアで一番売れた製品は何か」と尋ねる。回答は「House #4 beans」（書き起こしの綴りのまま）。
3. sources を開くと、先ほどの Power BI ダッシュボードが参照元として出る。personalization を開くと、「売上実績について聞かれたら、この Power BI レポートを正式な情報源として使う」という、John 氏が以前保存させたメモリが表示される。
4. 上司の Amanda 氏が「正しい製品を投入できるか」を知りたがっているという設定で、「オーストラリアの第 1 四半期のトップセラーは」と尋ねる。同じデータソースから回答が返る。
5. 判断に必要な追加情報の置き場所として、次を見せる。アナリストが作った Excel（価格の詳細、ベンチマーク、ダッシュボード、需要の根拠）、ニュージーランド進出の是非を巡る Teams のやり取り、メール、アナリストが作った提案の PowerPoint（スライドのコメントに進め方の議論がある）。
6. Work IQ に「ニュージーランド展開の意思決定に向けて、何が未解決か」と尋ねる。ファイルのリンクも添付もなく、「昨日 9 時のメール」といった指定もしていない。未決事項と、House #4 が有力候補に見えることを含む、決定の方向性が返る。
7. 「未決事項と担当者をまとめて」と尋ねる。Amanda 氏が意思決定者、John 氏が推奨案の担当というように、役割を Copilot が理解している。価格とマージンの承認は財務と営業（commercial）から、という他の人の役割も把握している。一方、チャネルと顧客構成の確認は、分からないので推測せず「unassigned」と表示された。
8. その結果、推奨案の準備、財務と営業による価格の検証、サプライチェーンによる在庫の確認、最終的な Go / No-Go は Amanda 氏、という整理になる。
9. 「Amanda と Anthony 宛てに簡単なブリーフのメールを、売上結果を含めて下書きして」と依頼する。Copilot 内に Outlook メールが作られる。John 氏が好む「1 文＋短い箇条書き」のスタイルになっている。Copilot 内で編集するか、Outlook で開いて編集するか、そのまま送信できる。ここでは送信した。
10. 次に、Rachel とニュージーランド向けの Web サイトの画像案について交わした会話（「日常の瞬間」「クラフトの裏側」「文脈の中の製品」といったテーマ）を見せる。
11. PowerPoint に戻り、Copilot に「Rachel に送った、ニュージーランドの Web サイト画像案のスライドを追加して」と依頼する。「Rachel に、いつ、メールで」とは指定していないが、Work IQ が該当の内容を探し出した。
12. 作成の途中で、Copilot が「どのスタイルで作るか。4th coffee の標準デザインにするか」と尋ね、John 氏は yes と答えた。Copilot の create モジュールで more → brand templates と進むと、会社のブランドテンプレート（4th coffee roaster）があり、画像やフォントなどが含まれている。
13. Copilot は 4 枚のスライド（24〜27 枚目）を追加した。24 枚目は Rachel へのメールでの方向性に沿い、ブランドキットを使っている。AI 画像も作るよう指示した。方向性が良ければ、カメラマンと契約して正式な画像にできる。

### 6.3 Code タブによる Web サイトと営業アプリ（Amanda 氏）

1. Work IQ のコンテキスト（ブランドテンプレートの画像など、John 氏が示したもの）と、簡単なモックアップを使い、**Code タブ**でニュージーランド展開向けの新しい Web サイトを作る。初稿を作ったあとに何度も反復を重ねた、長い会話の結果だと説明されている。
2. 自然言語でプログラムを作るやり方で、Code タブがアプリを生成する。生成された Web サイトが Copilot 内で表示され、ブランドコンテンツが使われている。スクロールして見せながら、自分が作るより出来が良いと述べている。シンプルなランディングページやダッシュボードには非常に有用で、チームは常用しているという。
3. 次に、同じコンテキストを自分のアプリに組み込む例として、ニュージーランドとオーストラリアのフィールドセールス向けの**モバイルファーストのアプリ**を見せる。これも Copilot と共同で作ったもの。Dynamics 365 で定義された商談を見て、詳細を確認できる。画面は Copilot の右側に表示されている。

5. Dynamics に加えて Power BI のコンテキストも取り込み、チーム全体が売上目標とその達成度を見られる。
6. 最後に、Agent 365 の管理センターにある Apps ビューで、アプリの在庫に「4th coffee field dashboard」があり、詳細（所有者、更新日、最終デプロイ）、使用状況、ヘルスの監視、使われているコネクターを見られると見せた。

## 7. 注意点・発表者の気付き

- **権限の範囲**：Work IQ が使えるのは、ユーザー自身が見られる範囲のデータだけです。ファイルやメールにアクセス権があれば Work IQ のコンテキストにも入ります。コネクターも同じセキュリティ制御に従います。
- **メモリの引用の条件**：メモリが回答を実質的に形作ったときだけ表示され、ユーザーのカスタマイズに従います。不要なメモリは削除できます。
- **分からないことは推測しない**：デモでは、チャネルと顧客構成の担当が分からない項目を、Copilot が推測せず「unassigned」と表示しました。登壇者はこれを好ましい挙動として示しています。
- **Dynamics 365 / Power Platform の GA**：コンテキストが M365 だけでは完結しないことへの対応として語られています。
- **Code タブの Web サイト**：登壇者は、初稿から多くの反復を経たものだと説明しています。
- **料金面の試算**：Copilot Credit Estimator で、アプリやエージェントの想定コストをモデル化できます。具体的な金額は発表では示されていません。

## 9. まとめ

Work IQ は、Microsoft 365 のデータに memory、context、skills という 3 つの層で意味を与え、Copilot や自作のエージェントに渡す仕組みです。

- 同じモデルを使う者同士の差は、モデルに渡すコンテキストで決まる、というのが発表の出発点でした。
- Ignite では、メールの文体とアプリをまたぐメモリ、Dynamics 365 / Power Platform の Work IQ への GA、People と Organization のコンテキスト拡張、plugin catalog の公開が紹介されました。
- 開発者は、MCP、REST、A2A（書き起こしの表記は「8A」）を通じて同じコンテキストを使え、Copilot Studio、Foundry、GitHub Copilot からも利用できます。
- エージェントの規模が拡大する前提で、Agent 365 が管理、ガバナンス、セキュリティ、ROI、そして AI の FinOps を担います。

次の一歩として、まず Copilot で「上司からの返信が必要なメールを探して」といったプロンプトを試し、Copilot Credit Estimator で自社の想定コストを見積もり、plugin catalog で使えるプラグインを探すことが案内されています。
