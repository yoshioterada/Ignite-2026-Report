# BRK239 Employee Self-Service to Enterprise Scale: Managing Intelligent Agents

## 1. はじめに

このセッションは、Microsoft の **Employee Self-Service（ESS）エージェント**を題材に、「エージェントを作ること」と「エンタープライズ規模で安定して運用し続けること」の違いを説明するものです。ESS エージェントは、IT や HR といった社内サービスの問い合わせを 1 つの窓口で受け付ける Copilot のエージェントです。

発表は 3 部構成です。最初に ESS エージェントの位置づけと顧客事例、次に Copilot エコシステムにおける plugin の考え方と ESS の関係、最後にエージェントの**ライフサイクル管理**（計画、構成、テスト、展開、分析）の取り組みが語られます。画面を使った説明は、あらかじめ用意された 2 本のデモ動画で行われ、最後に会場からの質問に答える Q&A があります。

発表の中心にある主張は、**エンタープライズ向けのエージェントは「一度デプロイして終わり」ではなく、継続して見守り、調整し、改善し続ける運用の営み**だという点です。ESS エージェントがすぐに使える完成品（turnkey）ではないことも、繰り返し強調されています。

## 3. 何に関する発表か

### 3.1 背景

Kyle は、組織内のエージェント投資や Microsoft 側の投資の大半は「生産性」に向いていると説明しました。生産性の領域では、できるだけ広い網を張って情報を集め、学び、新しいインサイトを得ることを最適化します。

一方、従業員向けサービス（employee services）の領域では、この方向と**ときに対立する要件**があります。

| 要件 | 内容 |
| --- | --- |
| 狭く絞った検索 | 個人の文脈と、質問に答えるのに使うコンテンツの文脈を理解する必要がある |
| 権威あるコンテンツ | HR の領域では、実際のポリシーに基づく回答と、回答らしく見えるだけで実際のポリシーに由来しない回答を区別する必要がある |
| 記録システムの利用 | systems of record からデータを取り、さらにそのシステムに対して行動（action）を起こす必要が高まる |

利点としては、従業員サービスの提供では、人手で処理するチケットの削減といった形で、ROI が直接的に分かりやすい点が挙げられています。そのため Microsoft は、この数年にわたり Copilot プラットフォームに新しい機能を作り、その上に ESS エージェントの投資を積み上げてきました。

## 4. 発表者が伝えたいメッセージ

- **ESS は「1 つの入口（single front door）」であり、管理された権威ある層である。** 従業員と、記録システムやポリシーの間に立ち、権威ある回答、データ取得、アクションを、信頼できる形で提供します。メッセージングやコンテンツの範囲も管理できます。
- **ターンキーではない。** Microsoft は共通の課題に投資し、基盤を提供しますが、企業ごとに環境が違うため、最後の「ラストマイル」の構成とカスタマイズは必要です。
- **ESS 単体の入口だけでなく、Copilot のあらゆる体験の中でも使えるようにする。** ESS を、管理者が指定できる、権威ある管理された plugin としても提供する方向です。
- **エンタープライズのエージェントは、見守り続ける「実践（practice）であり規律（discipline）」である。** コンテンツ、ポリシー、サードパーティのシステム、モデルなど、足元が常に変わるため、評価とテストが欠かせません。
- **展開の速さと品質の両方を狙う。** 12 週間かかるデプロイ手順を短縮するため、ライフサイクルのツールを作っており、Fortune 500 の顧客が 4 週間で全従業員に展開した例があります。目標は 2 週間未満です。

## 5. 発表内容の詳細

### 5.1 ESS エージェントとは（Kyle）

ESS は **Copilot chat のエージェントのファミリー**です。1 年前に提供を始めた時点では Copilot エコシステムの中のカスタムエージェントでしたが、いまは Copilot chat のシステムに移行しました。Copilot Studio で構成できる一方、Copilot chat スタックへの投資の恩恵も受けられます。これらのエージェントは、組織内の従業員サービス提供を始めるための「Kickstarter」のようなものだと説明されました。

ESS は、従業員が雇用主と関わるための**集約された 1 つの体験**を提供します。HR と IT が対象で、Microsoft 社内ではさらに施設（facilities）などのシナリオにも広げています。これを「single front door」の体験と呼び、会話だけでなく、組織のお知らせや、チケットを開いている場合のステータスなど、会社と従業員のコミュニケーションの場としても使えるようにしています。

構造としては、ESS は Copilot エコシステム内の入口として、従業員と、バックエンドの記録システム、ポリシーとコンテンツの間に置かれます。センシティブなトピックのメッセージングやコンテンツの範囲を制御しながら、権威ある回答、データの取得、記録システムに対するアクションを信頼できる形で提供する「管理された層」です。

> 注意：Kyle は、ESS は「ターンキーのそのまま使えるソリューション」ではないと明言しています。Microsoft は誰もが直面する共通課題に投資し、記録システムへの接続機能も提供しますが、環境は企業ごとにかなり個別性があるため、その上で社内プロセスやシナリオに合わせた最後の構成とカスタマイズが必要になります。

### 5.2 顧客事例：Fortune 100 の米国金融サービス企業（Kyle）

ESS は昨年末から顧客に提供されています。顧客名はまだ公表できないとして、次の事例が紹介されました。

| 項目 | 内容 |
| --- | --- |
| 顧客 | Fortune 100 の米国の金融サービス企業（名前は未公表） |
| 規模 | 180,000 人を超える従業員に ESS を展開 |
| 回答の正確性 | 90% 超を目標に最適化している |
| データに基づく回答（grounded） | 回答の 95% 超 |
| golden set | 100% の正確性を満たす必要がある「golden set」という概念を設けている |
| 権限 | 記録システムに組み込まれた権限の上に構築され、従業員が見るべきでない情報やデータにアクセスできないようにしている |

この顧客のプロジェクトリードの発言として、「ESS は、この会社での AI 活用の理想的なお手本として見られている」という引用が紹介されました。Kyle は、ESS を従業員サービスの提供手段としてだけでなく、**エンタープライズのエージェントを、信頼性が高いミッションクリティカルな形で作る例**としても誇りに思っていると述べています。

### 5.3 ESS を Copilot のあらゆる体験で使う（Kyle）

ESS を入口として投資し続けるのは、従業員を 1 か所に送り込み、サービスとメッセージングの一貫性を保つことに価値があるためです。一方で、ユーザーのいる場所で応えることも重視しています。従業員が Copilot Chat、Cowork、その他の Copilot 体験を使っているときにも、ESS への投資が、管理された権威ある情報源として現れるようにします。そのために、ESS をスタンドアロンの体験だけでなく、**管理者が指名できる権威ある管理された plugin** としても使えるようにします。

### 5.4 Copilot エコシステムの用語と plugin（Renima 氏）

Renima 氏は、キーノートでも触れられた新しいエコシステムとして、4 つの概念を整理しました。

| 概念 | 説明 | ESS での例 |
| --- | --- | --- |
| Skills | ノウハウ。指示、リソース、ワークフローの集合で、毎回同じやり方でタスクを実行する | HR 担当者が、休暇や福利厚生の質問に、毎回同じポリシー文書を使って同じように答える |
| Tools | Copilot がアクションに使うもの。コネクターや MCP サーバーにつながる | 記録システムを更新するために、HR や IT のシステムに直接接続する |
| Agents | 目標に向かって動く。skills と tools を使ってタスクをこなす | 従業員が「子どもが生まれる。次に何をすればいい？」と聞くと、agent が関連するポリシー文書を skills で引き、tool 呼び出しでライフイベントをシステムに登録する |
| Plugins | skills や tools などをまとめて **インストールし、パッケージ化する**仕組み（発言の 3 つ目の要素は聞き取り不明瞭）。新しい概念。現在の A365 のポリシーと同じ形で管理される | — |

**共有 plugin レジストリと管理**

Renima 氏は、組織で plugin を同じように統治するための仕組みとして、次の構成を図で説明しました。

1. 最上位に **1 つの共有 plugin レジストリ**があり、ESS エージェントの plugin もここに置かれる。
2. 左側のレジストリには、Microsoft やパートナーの plugin が公開され、すべて組織が定めた権限の範囲内で扱われる。Microsoft は、その設定を尊重する。
3. その上の層が管理者で、アクセスのオン・オフ、ブロック、特定のユーザーグループへのアクセス割り当てを行う。
4. 右側の「discover and use」が従業員の体験で、従業員がプラグインやエージェントにアクセスする方法は現在と同じく **ストア**経由であり、新しく覚えることはない。ユーザーが作業する場所（Copilot や Office）で、近く発見できるようになる。

> 補足：この展開は 9 月から顧客に向けて始めており、組織にも近く届くはず、と述べています（具体的な提供状況の詳細は発表では語られていません）。

エコシステムは拡大中で、Copilot エコシステムで動く plugin は **350 以上**あり、キーノートでも触れられたこの数字はまもなく 400 に達する見込みだと述べています。組織が承認した範囲でユーザーが Copilot から使えます。共有 plugin レジストリを詳しく知りたい人向けに、翌日 2:45 に Mandy Whaley 氏と Rachit Malik 氏のセッションがあると案内されました。

**デモ動画 1：管理者主導のルーティング**

Renima 氏は、ESS が「admin-led routing」で呼び出される様子を、動画で紹介しました。管理者が、ユーザーがクリックしたときに Copilot にエージェントがどう現れるかを設定でき、さらに近く Copilot の体験の中で暗黙的に呼び出せるようになる、という概念です。内容は 6 章に記載します。

### 5.5 エージェントのライフサイクル：なぜ必要になったか（Swati 氏）

Swati 氏はまず、需要が受け入れ能力を上回ったため、待機リストに入ってもらった参加者に謝罪しました。その理由は、初期のデプロイを通じて、簡単なエージェントを作ることはできるが、**大規模に管理・展開するには別の筋力が必要**だと分かったことです。初期の導入は想定より長くかかり、Microsoft のフィールドチームとコアチームの手作業が多く必要で、スケールしませんでした。そこで一歩引いて、導入をはるかに簡単にするための投資を検討し、それを「**エージェントのライフサイクル**」と呼んでいます。計画、構成、信頼できる形での大規模な展開までの旅を楽にするためのものです。

**顧客から学んだ課題**

顧客の話は一貫していたといいます。

1. **関係者を集めるだけで数週間を失う。** 成功するエージェントには、コンテンツ担当者、ポリシー担当者、HR、システムを知り権限を持つ IT 担当者が必要で、勢いが止まる。
2. **接続したつもりで、実際には動かない。** 既存のシステムと統合したつもりでも、従業員が質問すると動かない。接続は正常だと考えていたため、誰も予期していなかった。
3. **コンテンツの問題。** ある顧客（名前は非公表）では、展開してすぐ、HR が出すはずの答えと違う回答が従業員に返りました。原因は、同じトピックについて**矛盾するポリシーが 2 つ ESS エージェントに接続されていた**ことです。一方は古く、もう一方は新しいものでしたが、エージェントは古いほうを選びました。そこで顧客と一緒にコンテンツを直しました。スケールさせるには、コアのエージェントの外側にも目を向ける必要がある、という例です。
4. **変更が全体に影響する。** たとえばモデルが変わると、エージェントに影響する。昨日動いていたものが明日も動くことを、どう保証するか。エージェント全体の健全性を見守る必要がある。

> 補足：Swati 氏は「顧客の 5 つの課題すべてに投資し、エージェントのループに対応づけた」と述べていますが、トランスクリプトで具体的に語られた課題は上の 4 つです。

**エンタープライズのエージェントが違う理由**

エンタープライズのエージェントを大規模に展開するには、異なるレベルの信頼性と信用が必要です。HR と IT の中心にある ESS のようなエージェントは、通常のソフトウェアのように「一度デプロイして終わり」ではなく、**継続的に見守り、世話をし、調整し、改善する「practice であり discipline」**です。関わる人も、HR と IT のリーダーに加えて、各種の管理者、Workday や ServiceNow などの専門家と広がります。

さらに「足元が常に動いている」と説明されました。

- コンテンツやポリシーは日々変わり、新しいポリシーがエージェントの真実の源になる。
- サードパーティのシステムとの接続は、そのシステムの信頼性までしか信頼できず、システム側に問題が起きればエージェントの信頼性を取り戻す方法がない。
- これらをまとめるために、堅実な評価とテストが必要になる。

**デプロイ・プレイブック**

ツールが整う前の対応として、**デプロイメント・プレイブック**（デプロイ・ガイド）が作られました（スライドにリンクがあります）。100 ページほどの Learn のコンテンツを辿る代わりに、ステップ 1 からステップ N まで、各ステップの主たる責任者（DRI）と必要なことが分かる内容です。ただし、これに従うと現状は **12 週間**かかります。顧客ごとに固有のガバナンスやプロセスが必要なためで、12 週間からの短縮を進めている、とのことです。

**エージェントのループ**

Swati 氏は、エージェントを、組織固有のシグナルで育っていく「ループ」として説明しました。

1. エージェントから始め、シナリオ（エージェントで何を達成したいか）を決める。
2. それをもとに、記録システムと必要な構成を選ぶ。
3. コンテンツ、システム、シナリオに基づき、品質の基準に達するまでテストする。コア以外に原因があることも多い（例：ESS 側のマッピングと、自社システム側のマッピングの違い）。
4. 従業員に、まず小さなグループから展開し、実際にどんな質問が来るか、システムが動いているかを見る。
5. その結果をもとに、テストを更新する。

従業員が誤った回答に不意を突かれないよう、シナリオが増えるのに合わせてテストも増やす必要があります。これを手作業でやらなくても、多くをエージェントに任せられるようにしており、統合が健全か、健全でなければギャップは何か、推奨される修正は何かを見て、担当者が**承認してから本番に反映する**形を目指しています。

### 5.6 デモ動画 2 の後の補足と助言（Swati 氏）

動画のあと、ライフサイクル全体の機能は、計画（どのシナリオを作るか）、構成が健全かの確認、テスト作成（ゼロから書かなくてよい）、分析で改善を続けるまでをカバーすると整理されました。

別の顧客（Fortune 500、名前は非公表）が、これらのライフサイクル機能を使い、**4 週間で全従業員に展開**したと紹介されました。基本の状態から始め、パイロットのテストを経て本番に至る全工程を含みます。4 週間でも大きな前進だとして、目標は 2 週間未満、来年初めにそのための投資を見せられる見込みと述べています。

提供が一般公開されるまでの間、始める人へは次の助言がありました。

1. **最小のシナリオ**から始める。Kyle も言うようにスコープを絞り、非常に絞った範囲に集中する。
2. 従業員に共有する前に、たとえ小さなグループでも、正しい答えをよく知っている人たちでテストする。それがテストベッドになる。
3. その後、より広い対象に公開する。Microsoft 社内でも、地域（geo）ごとに展開しながらテストと改善を重ね、グローバル展開でも健全性を確かめた。

### 5.8 Q&A

**Q1：Blue Cross Blue Shield Association の参加者**

1 年半取り組んでおり、「期間を短く言いすぎではないか」と指摘した上で、統合を正確に動かすのは極めて難しく、いまも手作業でやっている、動画で見たテストベッドの機能は提供されているのか、と質問しました。

回答：テストベッドの機能はすでに提供されています。登壇者は、agent development kit やライフサイクルのツールのオンボーディングを受けているかどうかを確認したうえで、受けていなければ自分たちとアカウントチームに伝えるよう案内しました。質問者は agent development kit に「すぐには思い当たらない」と答えています。質問者は FastTrack チームと作業しているが、これらの話は聞いていないと答え、登壇者は後で個別に連絡先を共有し、適切な担当につなぐと述べました。「FastTrack なら正しく案内できるはずだが、行き違いがあるのかもしれない」と話しています。

**Q2：ライフサイクルのツールを使うには、オンボーディング・プログラムへのアクセスが必要か**

回答：必要です。アカウントチームに連絡してください。より多くの顧客に開く方向で進めています。これまでは課題（その多くは環境起因）があるため、ESS にオンボードしたすべての顧客に、Microsoft の担当者を（フルタイムで担当する形で）つけて、一緒に解決してきました。ライフサイクルのツールに多くを取り込めるようになるにつれて、より多くの顧客に開けるようになります。いまは、アカウントチームを通じて、シナリオの早期評価を行い、プログラムに入ってもらう形が正しい方法です。

**Q3：オンボーディングなしにライフサイクルのツールを使えるのはいつか**

回答：ライフサイクルに入る予定のツールの 1 つに、オンボーディング型のツールがあります。ESS のセットアップを始める前に、シナリオの評価（どのシステムか、関係者は揃っているか）を行います。たとえば会社内の 2 つのグループが互いに話していない、といった単純なことも事前準備で解消します。Workday を使うなら Workday の SME を参加させ、プロジェクトを理解させておきます。これをツールに組み込む作業を進めており、開放が進むのは **来年の第 1 四半期から第 2 四半期（Q1、Q2）** ごろです。それまでは、オンボーディング・プログラム経由の、より手作業のプロセスになります。

**Q4：ServiceNow 以外のプラットフォーム（Dynamics Customer Service、Halo ITSN（聞こえた表記）など）は、ロードマップにあるか（Cerberus の参加者）**

回答：標準で（out-of-the-box）サポートしているものはあるが、サポートされていないシステムには、plugin 向けの MCP と A2A の統合ポイントを公開することで拡張できるようにします。Dynamics については、Microsoft 社内では統合を行っており可能だが、製品としてはまだ完全にはサポートしていません。質問者の「顧客側でオーケストレーションする必要があるということか」という確認に、登壇者は「そのとおり」とし、Copilot Studio ではすぐ使えるエージェントがあり、さらに統合を追加できる、完全にカスタマイズ可能な構成だが、システム側を立ち上げる重い作業は顧客側で必要になる、と答えました。

別の登壇者は次の点を補足しました。

- ここ数か月で、サードパーティのシステムのほぼすべてが MCP サーバーのサポートを公開または発表している。過去およそ 18 か月は個別性の高い従来型の API ベースの道筋だったが、MCP のサポートによってはるかに簡単になりつつある。他のシステムを統合するときは、まず MCP を見るのが最も簡単な道になる。
- 社内の自作システムでも、従来の API でつなぐか（ESS の中でも可能）、MCP の入口を作るか。後者なら ESS や他のエージェント用途での利用が簡単になる。
- サードパーティのシステムが、いつ MCP を公開するかを確認しておくと、両側で統合を進められる。
- 動画 1 の中で、MCP アプリの拡張ポイントの例として、福利厚生の登録を見せた。背後は MCP サーバーで、チャット上の UI ウィジェットが **MCP apps** にあたる。これも拡張ポイントの 1 つ。

**Q5：Barclays の参加者（独自の Copilot Studio カスタムエージェントを構築。コンテンツとナレッジ管理に苦労している）**

動画で、重複コンテンツや作成者を特定していた。そのためにコンテンツとナレッジ管理でどんなセットアップが必要だったか、という質問でした。

回答の要点：

- それは **agent lifecycle management ツール**の機能です。ライフサイクル管理は、ESS エージェント自体の作成を支えるエージェントのことで、まだ始まったばかりです。
- 顧客がコンテンツの品質で苦労している共通点を集め始めた。例として、主な成功指標が「人との対話の削減」だった顧客で、エージェントは正しい答えを返しつつ、ほぼ毎回「この番号に電話してください」と付け加えていた。調べると、CMS のほぼすべての記事の最後に「この HR サポート番号に電話してください」と書かれていた（「答えが得られなかった場合は」とも書かれていなかった）。LLM はそれを「すべてがこの番号に電話するよう言っている」と受け取り、常に電話を勧めるようになった。
- ライフサイクルのツールでは、エージェント自身が使うのと同じコネクターでコンテンツを取り込み、推論して、こうした問題を**事前に**探す。例：「自分の組織では、常に番号へ電話するよう積極的に勧めたくない。コンテンツがそれを支えているか」、ポリシー間の矛盾、ServiceNow の記事にリンクされていない添付ファイル（またはその逆）。
- 事前の分析で見つけられなかった問題には、メーカー（作成者）、評価、エンドユーザーが誤りを見つけた時点で、なぜ誤ったのかを追えるようにする。推論の過程、通ったスタック、取得された記事などを見て、コンテンツに根本原因がないかを調べる。つまり**事前と事後の両方**で行う。

別の登壇者は、応答品質の問題のトラブルシューティングについて補足しました。

- ESS のように、バックエンドのシステムに加え、複数の検索インデックスが関わる場合は、診断が非常に複雑になる。
- 応答を合成する部分に、顧客が見られるツールや可観測性（observability）が足りないと認識している。例として、ある顧客で、動いていたものが急に動かなくなった。調べると、動いていたときの応答は、実は技術的に誤った応答で、顧客が思っていた情報源から来ていなかった。
- 現在、顧客が調べるツールはなく、インシデントを起こす必要がある（Microsoft は内部ツールを使う）。ESS ではプラットフォームのパートナーと協力し、顧客が観察・診断できるようにするギャップを埋めようとしている。ESS 専用のツールを足すだけでなく、**プラットフォーム自体を強化して**、すべてのエージェントで使えるようにする方向。

質問者の「ルールをツールで設定して、重複や重なり、誤りを特定するのか」に対して、登壇者は、特定の問題に対するスキルとツールを作り、**コアのエージェントの外で**調整している、エージェントと並行して動くシステムだ、と答えました。また、ライフサイクル管理ツールは現在**ESS 専用**で ESS プログラムの一部だが、Copilot のオーサリング・ツールに取り込む方向でプラットフォームのパートナーと協力しており、来年初め（Q1）にその一部が広いツールに統合され始める、と述べました。ESS は、エンタープライズ級のエージェントに共通する顧客ニーズで、先頭を切っている立場だと説明しています。

## 6. デモ・手順

このセッションでは、登壇者が画面を操作するライブデモは行われていません。事前に用意された 2 本のデモ動画が上映され、動画のナレーションがトランスクリプトに含まれています。以下は、そのナレーションで語られた内容です。画面の細部は音声からは確認できません。動画は架空の企業 Caldova Pharmaceuticals（社内の ESS エージェントは「Caldova Connect」）の従業員 Kat Larson を主人公にしています。

### 6.1 動画 1：ESS を Copilot の中でも使う（admin-led routing）

動画 1 は、Renima 氏のパートで上映されました。

1. Kat Larson は、Caldova Connect のランディングページで、米国の従業員向けの福利厚生の登録に関するお知らせを見る。
2. 選択肢を確認して確定し、会社が作ったカスタムの **MCP アプリ**で登録を始める。
3. 登録を送信したあと、残りの休暇日数を確認する。ESS エージェントが残高を表示する。
4. 休暇を取ろうと考えるが、会議のリマインダーが出て、計画は後回しにする。
5. 数日後、Copilot で作業中に、休暇の計画を立てようとする。Copilot に休暇の計画の手伝いを頼むと、**管理者が設定した体験**によって、Caldova Connect（会社の ESS）に直接ルーティングされる。
6. ESS が現在の残高と承認済みの会社のガイダンスを示す。Kat は日付を確認し、同じ権限と安全策のもとでリクエストを確定する。
7. 引き続き Copilot の中で、チームへの不在のお知らせを確認し、宛先と日付を確かめて、カレンダー招待を送る。

ナレーションのまとめは、「会社のサービスは 1 つ、仕事が行われる場所がどこでも同じ」「ESS は信頼できる入口であり、Copilot の中でも同じ権威あるサービス」という内容です。

### 6.2 動画 2：エージェントのライフサイクル

動画 2 は Swati 氏のパートで、機材のトラブルで冒頭が何度かやり直されたあと上映されました。Kat が福利厚生の登録方法、休暇の残高、ポリシー情報の回答を得られたのは偶然ではなく、背後にチームがいる、という導入で始まります。登場するのは、HR リーダーシップの Mona、IT の Lawrence、Workday の Aaron、HR のコンテンツライターの Adi です。

1. **計画：** IT チームの Lawrence が ESS を有効にする。Microsoft のエージェント・ライフサイクルのツールが、サポートチケットからシナリオに優先順位をつけ、マイルストーンを設定し、成功を定義し、必要な関係者を集める明確な計画を示す。
2. **準備状況の確認：** ツールが、システムの準備ができているかを確認する（Workday が接続されている、サインインが機能している）。
3. **コンテンツの矛盾：** ツールが、**休暇に関する 2 つの矛盾するポリシー**を検出し、HR のコンテンツライターで SME の Adi に通知する。Adi が古いポリシーを削除する。
4. **テスト：** 先に定義した成功基準を使い、ツールがテスト一式を作成して実行する。**92% が合格**。
5. **失敗の特定：** 1 件の失敗が目立つ。従業員が休暇残高を尋ねたのに、エージェントは一般的なポリシーを答える。ツールは、原因がコンテンツでも Workday の接続でもなく、**エージェントの指示の矛盾**にあると突き止める。質問が Workday に届いていなかった。
6. **修正：** ツールが修正を提案し、テスト一式を再実行する。Lawrence が確認して承認する。修正は「動くと仮定する」のではなく、テストされる。
7. **本番へ：** テストが健全になり、Lawrence が同じエージェントを test から production に移す。**作り直しは不要**。Microsoft が改善を出荷しても、カスタマイズはそのまま残り、更新が従業員に届く前にテストが走る。
8. **運用：** 本番稼働後、HR リーダーの Mona が、採用状況と回避されたチケットを追跡する。Lawrence は否定的なフィードバックを調べる。エージェントが、勤続記念日の質問に、従業員の直近の昇進日で答えている。ライフサイクルのツールが、すでに修正案を用意し、この問題のテストを追加し、一式を再実行している。Lawrence が修正を試して承認する。サイクルは続く。

ナレーションの締めは、「エージェントの構成は一瞬だが、管理はライフサイクルだ」という内容です。

## 7. 注意点・発表者の気付き

- **ESS はターンキーではない。** ラストマイルの構成とカスタマイズが必要です。
- **初期のデプロイは時間がかかり、Microsoft の手作業が必要だった。** そのため待機リストが発生し、現在も導入にはオンボーディング・プログラムが必要で、各顧客に Microsoft の担当者が付いています。
- **コアのエージェント以外の要因が多い。** 矛盾する古いポリシー、システム側のマッピング、接続の問題など。「接続は正常なはず」という思い込みが落とし穴になった例が挙げられました。
- **コンテンツの書き方が回答に影響する。** すべての記事の末尾に「この番号に電話」とあると、LLM は常に電話を勧めるようになった例があります。
- **変更への備え。** モデルの変更などの影響を受けるため、昨日動いたものが明日も動く保証が必要です。
- **可観測性の不足。** 合成された応答の背後を、顧客が自分で調べるツールが足りていません。ある顧客では、うまく動いていた状態が、実は技術的に誤った情報源からの回答だったと分かりました。
- **関係者のサイロ化。** たとえば Workday を使うなら、Workday の SME を最初から参加させる必要があります。
- **現時点のライフサイクルのツールは ESS 専用。** 広く使えるようになるのは来年の Q1〜Q2 以降の見込みです。
- **始めるときはスコープを小さく。**

## 9. まとめ

ESS エージェントは、HR や IT の問い合わせを 1 つの入口で受け、権威ある回答、データ取得、記録システムへのアクションを管理された形で提供する Copilot のエージェントです。plugin として Copilot のあらゆる体験の中でも使えるようにする方向で、共有 plugin レジストリと管理者による制御の仕組みも説明されました。

もう一つの柱は、作るだけでなく運用し続けるためのライフサイクル管理です。矛盾するポリシー、動かない接続、モデルの変更といった実際の課題から、計画・構成・テスト・展開・分析のループと、それを支えるツールが作られています。顧客によっては 4 週間で展開できましたが、現時点でツールの利用はオンボーディング・プログラムに限られます。目標は 2 週間未満、広い提供は来年の Q1〜Q2 以降です。
