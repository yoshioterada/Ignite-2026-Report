# BRK214 Manage and Secure your AI Agents at Enterprise Scale with Agent 365

## 1. はじめに

このセッションは、Microsoft Agent 365 の 1 年間の歩みと最新の機能強化を紹介するブレークアウト（45 分）です。Agent 365 は、組織内のエージェントを一元的に把握・管理するための「コントロールプレーン」です。発表では、これを **「ノーと言うための仕組み」ではなく「イエスと言うためのオブザーバビリティ（可観測性）プラットフォーム」** として位置づけ直します。

構成はユニークです。急成長中の小売企業「Caldova」（社名の綴りは機械翻訳のため確定できません）の 3 人の同僚（データ/AI 担当、IT・セキュリティ管理者、ビジネス・財務担当）という役割を登壇者が演じ、それぞれの立場から次の 3 つの問いに答えていきます。

1. 他のプラットフォームで動くエージェントも Agent 365 に取り込めるか（Databricks の接続）

## 4. 発表者が伝えたいメッセージ

中心にあるのは、冒頭から終わりまで繰り返される「どうすればイエスにたどり着けるか」という問いです。Nirav Shah 氏は、多くのコントロールプレーンが「ノー」と言うための道具になっていると指摘します。ブロックし、上限を設け、組織内のイノベーションを抑え込んでしまうという見方です。

これに対して Agent 365 は、見えないものには「イエス」と言えない、という考えに立ちます。オブザーバビリティがあって初めて、組織全体が判断し、行動し、「イエス」に到達できるという主張です。オブザーバビリティは「見る」だけでなく、見たものに基づいて理解し、判断し、動くことまで含むとも説明しています。

もう一つのメッセージは、エージェント管理は **チームスポーツ** だという点です。エージェントが単に答えるのではなく、計画し、ツールを呼び出し、他のエージェントに引き継ぎ、ユーザーの代わりに行動する世界では、誰かがその行動に責任を持たなければなりません。その責任は IT、セキュリティ、ビジネスリーダー、開発者にまたがります。そのため全員が同じ視点で動く必要がある、というのが Agent 365 を AI スタック全体に広げる理由です。

## 5. 発表内容の詳細

### 5.1 1 年間の振り返りと市場の状況

- Agent 365 は 1 年前の Ignite で、Microsoft Frontier プログラムの一環として発表されました。当時の考えは、エージェントと人が一緒に働くなら、管理できる場所が必要で、エージェントが何をしているかを把握する必要がある、というものでした。
- 何千もの参加者が Frontier プログラムに加わり、そのフィードバックに素早く対応した結果、発表の数か月後の 5 月に一般提供（GA）になりました。「すでに作業管理に使っているツールの内部でエージェントを管理できるコントロールプレーン」と説明しています。
- Gartner は、AI エージェント管理プラットフォームの初のマジック・クアドラントで Microsoft をリーダーに選びました。
- 現在、数万のお客様が Agent 365 を利用しており、管理対象のエージェントは **5,000 万を超える** とのことです（機械翻訳では「5,000 万人」。エージェントの数を指していると読み取れます）。Nirav Shah 氏は、これは単なるパイロットではなく、エンタープライズ規模の実践の証拠だと述べています。

### 5.2 AI 運用モデルの変化と、組織の問い

IDC の見通しとして、2029 年までに 10 億を超えるエージェントが存在するようになると紹介されました。続けて、毎日 2,000 億件以上のアクションが行われるという数字が挙げられています（機械翻訳では主語が不明瞭ですが、エージェントのアクションを指す文脈です）。単なるプロンプトと回答ではなく、重要なビジネスプロセスを動かすアクションであり、人手で確認するのは最も熱心な管理者でも不可能だという話でした。

これまでの AI は「1 人が 1 つのプロンプトを送り、1 つの答えを受け取る」使い方が中心でした。これが「AI を管理する世界」へ移りつつあるという認識です。そこで各ロールから出る問いとして、次が挙げられました。

- 自分の組織にはどんなエージェントがいるのか。何が使われ、誰が使っているのか
- エージェントは何をしているのか。何にアクセスでき、どんなリスクがあるのか
- リスクを管理・軽減し、安全とコンプライアンスを保つには何をすべきか
- これにどれだけのコストがかかり、ビジネスに何を返しているのか

### 5.3 4 本目の柱：ビジネス価値

Nirav Shah 氏は、この 1 年の最大の学びの 1 つを、お客様がエージェントだけでなく AI 資産全体を管理できる Agent 365 を求めていることだと説明しています。理由は、エージェントの行う作業の複雑さと幅が増え続けているためです。

1 年前の発表では、エージェントも企業リソースとして同じ厳格さで扱うべきだとし、**アイデンティティ、アクセスコントロール、エンド・トゥ・エンドで管理できるライフサイクル** が必要だと確認しました。エージェントは単独で動くわけではないため、今回はそれに加えて、プラグイン、モデル、使うデータやツールまで管理対象に含めるとしています。

昨年は 3 つの柱を主に IT のニーズに向けて発表しましたが、組織全体を支えるには足りません。そこで Agent 365 は AI のオブザーバビリティプラットフォームへと移行し、4 本目の柱として **ビジネス価値** を加え、ビジネスリーダーをチームの新メンバーとして迎えます。1 年のうちに「コントロールプレーン」は、業界全体で AI 管理を指す一般的な概念として定着した、とも話しています。

### 5.4 管理：すべてのエージェントを 1 か所で見る

従来のコントロールプレーンは、登録されたものしか見えません。Agent 365 のオブザーバビリティは、すべてのデバイス、ユーザー、プラットフォーム、ツールを対象にし、誰も登録していないエージェント（例として、週末に誰かが新機能を試すうちに PC 上に現れたようなもの）も表示するとしています。

見えるようにするべきこととして、次の 3 点が挙げられました。

1. Microsoft 製か否か、クラウドかローカルかを問わず、すべてのエージェントの在庫（インベントリ）を持つ
2. 各エージェントがどう動き、誰と関わり、どんなデータ・ツール・モデルに触れているかを見る
3. 責任を割り当て、注力すべき課題を見極める

これを実現する新機能として、次が紹介されました。

| 機能 | 説明 |
| ---- | ---- |
| Connected platforms | 他社プラットフォーム上のエージェントを、Microsoft で作ったものと同じレジストリに取り込む。Agent 365 にとって全く新しい機能 |
| ローカルエージェント検出 | 個人のノート PC や PC 上で動くエージェントもレジストリに表示する |
| ツール・モデルのレジストリ | すべての MCP サーバーとモデルを、それを使うエージェントにひも付ける |
| シャドウ AI の検出 | ポリシーやルールで管理されていないエージェントを見つける |

**Connected platforms** では、見つかったエージェントはレジストリに記録され、それぞれに独自のエージェント ID が付きます。そのため、Agent 365 が管理する他のエージェントと同じように管理・監査できます。単にレジストリに 1 行追加されるだけではなく、Agent 365 の機能と、基盤プラットフォームがサポートする機能が組み込まれる、という説明です。この日の時点で **11 のパートナープラットフォーム** が接続済みで、Amazon Bedrock、ServiceNow、Databricks、OpenAI などが挙がりました（他にも複数あります）。

### 5.5 Databricks のパートナー視点（David Meyer 氏）

Databricks の David Meyer 氏が、Agent 365 と連携する理由を話しました。

- Azure Databricks は 2018 年から、ファーストパーティの Microsoft サービスとして提供されています。世界最大級の Azure のお客様がデータ管理に Databricks を使い、AI も多く利用しています。AT&T や Walgreens のようなお客様は、AI をすべて Azure Databricks 上に構築しているそうです。
- Databricks の Genie などは Copilot にそのまま表示され、構築した AI は Foundry からも利用できます。ただし、それらを管理する必要があり、そこで作られるエージェントにも、コントロールプレーンに対する同じ要求があります。
- レジストリの同期は **アカウントレベル** で行われます。Databricks のアカウントには数百のワークスペースがある場合があり、Unity Catalog で整理された AI、MCP、ツール、エージェント、Genie が Agent 365 に同期されます。リストだけでなく、Databricks で管理されるすべての OTEL（オブザーバビリティ）データも、オン/オフのスイッチ付きで同期されます。より広い脅威と関連付けられるのも利点だとしています。
- 開発者は Claude Code、Codex、GitHub Copilot などの好きなツールを使い、Unity Gateway（表記は機械翻訳のため不確かです）を経由して Databricks 内でエージェントを作ります。開発者は「作り続けたい」と考えており、Agent 365 側では、Unity Catalog で設定された制約に従えば、許可を求めて回る必要がありません。管理者は、懸念すべき兆候、テレメトリ、システム全体のコストとの相関を確認でき、問題があれば所有者である開発者に連絡できます。

具体的なシナリオも示されました。Databricks 上でプロコードのエージェントを作り、お気に入りの新しいモデルにアップグレードして展開したとします。新しいモデルは応答が短くなるなどして、システム全体の NPS スコアに影響を与えることがあります。Agent 365 は別の仕組みでそれに気づくことがあり、その場合は知らせたうえで一時停止します。開発者は原因を調べ、前のモデルに戻して素早く対応できる、という流れです。David Meyer 氏は「みんなが自分のレーンを守りつつ、素早く動ける」と表現しています。

### 5.6 ガバナンス：3 つの要素と Action Center（Caroline Stanford）

Caroline Stanford 氏は、Agent 365 でいう「ガバナンス」を 3 つに分けて定義しました。すべてのエージェントに当てはまる必要がある、という位置づけです。

1. **知っていること**：すべてのエージェントにアイデンティティと責任ある所有者がいる
2. **コントロールがあること**：エージェントの挙動を制御するポリシー、権限、統制が整っている
3. **観察できること**：実行時のアクティビティシグナル・リスクシグナルを継続的に観察できる。エージェントは変化していくため、「設定して忘れる」ものではない

Agent 365 でガバナンスが形になる要素として、次の 4 つが挙げられました。

| 要素 | 内容 |
| ---- | ---- |
| 承認ゲート | エージェントがユーザーに届く前に、誰かが「はい」と承認する |
| スコープ付きアクセス | エージェントが仕事をするのに必要なものだけにアクセスを絞る |
| ツール管理 | MCP サーバー、プラグイン、コネクタなど、エージェントが使うものを管理する |
| ポリシーテンプレート | エージェントごとに Entra の保護、Purview、SharePoint などのポリシーを 1 つずつ決める作業を避け、大規模に適用する |

背景として、お客様のエージェント数は数千、場合によっては数万に及び、ベンダーを問わない異種混在の環境で運用されている点が語られました。エージェントを 1 つずつ管理する方法は、ある時点で成り立たなくなるという考えです。そこで、すべてを 1 か所で見ることを **「P0」（最初の最重要の土台）** と位置づけました。そのうえで、どのエージェントに時間と注意を向けるべきかを判断する必要があるとして、次の例が挙がっています。

- しばらく放置されて誰も使っていないエージェント
- 使われているが、もう所有者がいないエージェント
- 以前は問題なかったが、今はリスクが高くなったエージェント

こうしたシグナルは Defender、Entra、Purview、そしてエージェントを動かすサードパーティツールなど、複数の場所から届きます。これをまとめるための目標として、次の 3 つが示されました。

1. **キューを 1 つにする**：エージェントを管理する場所ごとに 7 つのキューを見に行くのではなく、注意が必要なエージェントが 1 つのキューに集まる
2. **リスクレベルを 1 つにする**：ID、セキュリティ、コンプライアンスのシグナルを集約したビューを持つ
3. **ベンダーの自動化を求める**：ルールセットとポリシーを組み込んだツールが代わりに動くことで、人は本当に必要なところに判断を使える

これらを担うのが **Action Center** です。Microsoft の IT 部門（Customer Zero for Agent 365）と共同で作られ、ユーザーから「シグナルは良いが、どこに注力すべきかを考えるのに自分でツール作業をしなければならない」というフィードバックを受けて作られたと説明されています。

その中核にあるのが **動的エージェントリスク（dynamic agent risk）** です。ID、アクセス、エンドポイント、ネットワークにまたがるランタイムシグナルを組み合わせ、影響範囲（ブラスト半径）で合成して、エージェントのリスクを総合的に示します。静的な評価ではなく、エージェントの挙動に応じて動的に更新される点が特徴です。何をしているのか、何を頼まれているのか、モデルが更新されたのか、新しい指示が入ったのか、標的にされたのか、といった変化が反映されます。このリスクは Agent 365 全体で優先順位付けの指標として使われています。

#### その他の機能（発表で紹介されたもの）

- **Copilot Cowork**：「Copilot Cowork も表示されるか」とよく聞かれるそうです。答えは「はい」で、エージェントとして扱われ、期待される管理・ガバナンス制御が適用されます。
- **マルチテナント管理**：複数テナントの環境や、顧客を支援するパートナー向けの機能です。テナントごとに作業するのではなく、すべてのテナントをまたいで見たり、ツールを展開したりできます。
- **エージェントアクティビティのエクスポート**：Agent 365 の情報を CSV や Excel にまとめられます。すでに使っているツールには Microsoft Graph API で組み込めます。エージェントのトレースは、Azure Monitor と Application Insights を通じて継続的に同期できます。

### 5.7 ビジネスバリュー：コスト、価値、ROI（Ray Smith）

Ray Smith 氏は、エージェントの利用が広がると、CIO や CISO が慎重な姿勢を緩め、現場が本格的に動き出し、やがて月々の請求書の話になると説明します。そこで CFO が尋ねるのは、金額そのものよりも「何が得られるのか。投資収益率（ROI）はどうか」という点だという話です。

典型的な状況として、毎月の請求書が届き、使っている量は見えても、それに対して得ているものが分からない、というお客様の声が紹介されました。使用状況は数えられているが成果が見えないため、予算の議論は推測になってしまいます。目標は「請求額を小さくする」ことではなく、「いつ加速し、いつ特定分野への投資を縮小するかを説明してくれる請求書」を持つことで、それを損益や事業成果に結びつけると述べています。そのために必要な要素は 3 つあるとされ、語られた内容は次のとおりです。

- **月末に突然の請求が来ない**ようにする。お客様は複数のプラットフォームを使い、複数の請求書が届くため、エージェント、チーム、モデルをまたいで、請求額がリアルタイムで形になっていく様子を見られるようにする
- **価値を理解する**。継続的な投資を、実際に効果のある場所に移す
- 管理や予算ポリシーを通じて、投資を適切なチーム、モデル、エージェント、ハーネス（発話の前半で「コーディングハーネス」が挙がっています）に合わせ、リターンを最大にする（機械翻訳では、これが 3 つ目の要素かどうかの区切りが不明瞭です）

お客様から最も明確に聞いたのは、予算は独自のクレジットなどではなく通貨で組むという点です。そのため、コストと価値の両方を **単一のドル換算** で示し、5〜6 のプラットフォームにまたがるエージェント資産全体で ROI の倍率を出すことが重要だと述べています。

#### コスト上位 7 エージェントの例

Ray Smith 氏の部署の「コスト上位 7 エージェント」の画面が示されました。合計は 13 万 5 千とのことですが、単位は機械翻訳から確認できません（文脈上は支出の合計です）。オブザーバビリティのトレースから、各エージェントのセッションとイベントについて、タスクの遵守や推論を見てタスクを分類し、価値を関連付けています。コスト順に並べても、ROI は 7 つのエージェントでそれぞれ違います。

- 最も高価なエージェントは、実は **4 倍** というかなり健全な ROI を出している
- 一方、下位のエージェントは **1 ドルあたり 1 セント** しか返していない

コスト目標へのプレッシャーがあると、ROI の高いエージェントの利用を誤って減らしてしまうおそれがあります。Ray Smith 氏は「コントロールプレーンは使った金額のコントロールに役立ち、オブザーバビリティは価値を知るためのカギになる」とまとめています。

#### トップダウンのコントロールと、現場の判断

組織での典型的な流れとして、CFO が CIO や IT に「予算をどう確保するか」「ガードレールをどう敷くか」「特定のチームに最新のフロンティアモデルを使わせないにはどうするか」と相談するところから始まる、と説明されました。コントロールの要素として挙げられたのは次のものです。

- 予算、チャージバック、グループ単位の設定、エージェントやリソースへの設定
- **モデルプロファイルとモデルポリシー**（コストの最大のレバー）
- **リソーススコープのポリシー**：エージェントやサービスに予算を設定しても、部署全体の支出には影響しないようにできる。人ではなくリソースに結びつくポリシー

監視では、使用状況、残りの予算の余裕（ランウェイ）、請求額が形になる様子を見られるので、超過の前に検知できます。最適化は、ROI が最も大きくなる領域に計画を切り替えることで、高コスト・低 ROI のエージェントに力を注ぎ、難しい判断を下せるようになる、という説明でした。

ただし、IT 管理センターは IT のためのものです。成果に責任を持つのは日々のビジネスで、ビジネス側の人は管理センターにアクセスできません。そこで、**A365 Business Analytics アプリ** を発表しました。同じオブザーバビリティの基盤とスコアカードをドル建てで、ビジネス側に割り当てて提供するものです。チームの階層の中でエージェントを見て、支出を把握できます。さらに、チームやビジネスの KPI を重ね合わせ、エージェントの支出や ROI を事業を動かす KPI と結びつけられます。トップダウンのガードレールと、分散した現場の判断が両立する、というのが狙いです。

### 6.3 コストと価値の確認（Ray Smith）

役割は、R&D オペレーションチームを率いる Caldova のビジネス・財務担当です。CEO から目標を与えられ、AI とエージェントを活用して達成する立場、という設定です。

## 7. 注意点・発表者の気付き

- **「ノーのコントロールプレーン」への反省**：Nirav Shah 氏は、1 年前に提供したのはコントロールプレーンだったと「小さな告白」を切り出しています。1 年の運用で、多くのコントロールプレーンが、ブロックや上限設定によって組織のイノベーションを抑え、得られる価値を制約しがちだと学んだという話です。
- **動的リスクは静的ではない**：一度リスクだと決めて終わりではなく、エージェントの挙動に応じて更新され続けます。
- **自動化は実行前にプレビューを確認する**：Action Center では、自動化を有効にする前に対象エージェントを確認し、ガードレールの影響を見てから「はい」を押せます。
- **コストと価値の算出は目安**：タスク分類器などを使う価値の算出は完璧ではなく、お客様が設定し調整するための尺度だと明言されています。
- **コストだけで判断しない**：コストが大きいエージェントが、実は高い ROI（例では 4 倍）を出している場合があります。コストだけを見て利用を絞ると、価値の高いエージェントを抑えてしまうおそれがある、という警告です。
- **ベンダーに自動化を期待する**：エージェントを 1 つずつ見る運用は成り立たないため、ルールセットとポリシーを備えたツールで自動化できるものを選ぶよう呼びかけています。
