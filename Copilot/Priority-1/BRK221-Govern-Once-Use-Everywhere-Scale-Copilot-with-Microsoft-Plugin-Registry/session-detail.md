# BRK221 Govern Once, Use Everywhere: Scale Copilot with Microsoft Plugin Registry

## 1. はじめに

このセッションは、Microsoft Copilot の拡張機能（extensibility）が増えるなかで、「どう見つけ、どう作り、どう統制するか」を Microsoft plugin registry を軸に紹介する 45 分のブレークアウトです。ほぼ全編がデモで構成されており、架空の会社 Caldova が「カスタマーサービスポータルを来週ローンチできるか」を判断するシナリオに沿って進みます。

内容は、プラグインの発見と利用、カスタムプラグインの作成（Work IQ Developer Tools）、Agent 365（A365）での承認・展開・利用状況の確認、Copilot 上でのスキル作成、そして Adobe プラグインを使ったローンチ準備、という 5 つのステップです。

発表者が伝えている骨子は、**tools（何ができるか）と skills（どう使うか）と agents を plugin としてまとめ、一度作って Copilot の各所で使い、A365 で一元的に統制する** という考え方です。

## 3. 何に関する発表か

Copilot が「intelligence built for work」として広がるなか、Microsoft は次の構成を示しています。

- Copilot は、仕事をする場所。
- Agents は、ビジネスを動かすのを助ける。
- Work IQ は、必要なすべてのコンテキストを提供する。
- すべては A365 で保護・管理・統制される。
- これらの基盤の上に、**plugins** を載せる。

Copilot の能力が広がるのに合わせて、サポートする拡張の種類も広がっています。これまで重要だった agents に加えて、**skills と tools** をサポートし、それらをまとめて **plugin** として扱います。

発表は Caldova の「来週ローンチできるか。大きくいくか、範囲を絞るか、見送るか」という問いを軸に、次の 5 ステップで進みます。

1. プラグインを発見して使う
2. 自分たちのプラグインを作る
3. プラグインを統制する
4. 自分たちのスキルを作ってチームで共有する
5. ローンチの準備を整える

## 4. 発表者が伝えたいメッセージ

発表者がまとめた、Microsoft plugin registry が助けになる 3 点は次のとおりです。

1. **ユーザーにとって**：Copilot と Office で使うプラグインを、1 か所で管理・発見・利用できる。
2. **管理者にとって**：プラグインの統制、管理、承認を大規模に行う 1 か所がある。
3. **継続的な保護と最適化**：使用状況の情報で、継続的に保護・最適化できる。

タイトルの「Govern Once, Use Everywhere」は、プラグインを **一度作ってパッケージ化し、Copilot が動くあらゆる場所で使い、A365 で統制する** という意味合いで説明されています。

## 5. 発表内容の詳細

### 5.1 プラグインとは

プラグインは、tools、agents、skills をまとめてパッケージにする方法です。説明された狙いは 3 つです。

- ユーザーが、自分の役割・仕事・扱うデータに合う機能を見つけやすい。
- 管理者が統制しやすい。
- 組織向けのカスタムプラグインを作って公開しやすい。

構成要素の関係は次のとおりです。

| 要素 | 内容 |
| ---- | ---- |
| Tools | MCP servers や connectors を含む。「何ができるか（the what）」にあたる。システム・オブ・レコードや社外のパートナーなどに接続できる |
| Skills | 「どう使うか（the how）」。エージェントが tools を効果的に使い、特定のシナリオを最善の方法で完了できるよう指示する |
| Agents | ビジネスを運営するうえで引き続き重要。プラグインにも含められる |

これらが Microsoft plugin registry に入ります。registry は **プラグイン（skills、tools、agents を含む）の単一のストア** で、自分でプラグインを作って公開でき、すでに **350 の公開プラグイン** がさまざまなパートナーから提供されています。

使える場所は、Copilot の Home、Code、Autopilot、そして Word、Excel、PowerPoint などの Office 製品です。管理と統制は Agent 365 で行います。エージェントですでに慣れている統制（有効化・無効化、ブロック、特定ユーザーグループへのアクセス付与）が、プラグインにも拡張されます。管理者が A365 で築いてきた知識と使い慣れた操作を、プラグインやツールにも広げる考え方です。

プラグインのエコシステムには多くのパートナーが参加しており、350 超がそのまま使えます。役割やタスク、接続したいデータの多くについて、すでに自分たちが使っているものに対応するプラグインがある可能性が高い、と説明されています。

### 5.2 ステップ 1：プラグインの発見と利用

Rachit がデモを担当しました（デモの手順は 6.1 を参照）。ここでは、そこで示された要点を整理します。

- 作業データ（Teams など）には答えがなく、事実は **MCP server の背後にある外部システム** にある、という状況から始まる。
- Copilot は Work IQ（仕事のコンテキストに基づく）を使って作業データを検索するが、このケースでは事実が見つからない。そこでプラグインの出番になる。
- plugins タブには **350 を超えるプラグイン** があり、社外システムに接続したいときはすでにあるかもしれないので、まずカタログを探すことが勧められた。組織で作ったカスタムプラグインも同じ場所で見つかる。
- Caldova の launch readiness プラグインは、**MCP server と 2 つの skills** で構成されている。MCP server は、ローンチゲート・データ・承認などの情報を持つ Caldova の内部システムに接続する。
- スキルは、Excel レポートを特定のフォーマットで作る要件（例：経営層向けの executive summary）を **自然言語** で記述したもので、プラグインに含まれて Copilot の各サービスで使える。
- プラグインを使うには、**トグルをオンにするだけ**。
- Copilot の回答には、作業データと並んで、呼び出されたプラグイン名が表示され、**MCP app による rich UX（ウィジェット）** でローンチまでの状況が表示される。
- Copilot からの refresh で、データを読むだけでなく、システム・オブ・レコードへのデータの書き込み・取り込みもできる。

まとめとして、**tools がビジネスデータを取得し、skills がそのデータの使い方（エージェントへのガイダンス）を与え、プラグインがそれらをまとめる** と整理されています。

### 5.3 ステップ 2：カスタムプラグインの作成（Work IQ Developer Tools）

カスタムプラグインを作るためのツールとして、新しい **Work IQ Developer Tools** が紹介されました。

- **CLI ツールとスキルの組み合わせ** で、GitHub Copilot や他のコーディングエージェントから、エージェント的な方法でプラグインを作れる。
- 意図（プロンプト）から始まり、どんなプラグインを作りたいか、どんなコンテキストを持ち込むかを記述する。
- ライフサイクルの全体を支援する：**build（作成）、package（パッケージ化）、preview（プレビュー）、feedback（フィードバック）、evals（評価）の実行、そして publish（公開）**。公開先は、自分のテナント、またはパートナーなら公開カタログ。
- ここで紹介するのは、すでに API と MCP endpoint を持つ既存サービス（launch readiness）をプラグインにパッケージ化して Copilot で使う例。

Mandy は、これらを「intent から publish までライフサイクル全体をカバーする」ものとまとめ、略称は CLI の省略名として「Wicked」と聞こえますが、音声認識の都合で表記が確定できません。**評価（evaluations）の機能は Ignite に合わせて最近リリースされたばかり** で、今後さらに投資を増やす領域であり、フィードバックを求めています。

デモの手順は 6.2 に書きます。

### 5.4 ステップ 3：A365 でのプラグインの統制

統制は A365 で行い、エージェント向けにすでにある基盤を土台にしています。

- すべてのプラグインを絞り込んで表示でき、skills、MCP servers、バージョンや対象ユーザー（audience）などの情報が見られる。
- ロールアウトを制御できる。特定のグループにアクセスを許可する、あるいは特定のグループにはプラグインを **最初からインストールして** おく、といった設定ができる。
- 使用状況のインサイトが得られる（例：ある MCP server がどれだけ使われているか）。

デモでは、Rachit が管理者の立場で、先ほど申請したプラグインを承認し、registry でプラグインを管理する様子を見せました（6.3 を参照）。

### 5.5 ステップ 4：Copilot 上でのスキル作成と共有

プラグインに加えて、**Copilot Cowork で作業するすべてのユーザーが、自分でスキルを作り、チームメイトと共有できる** と紹介されました。作業の流れのなかで、チャットの中だけで再利用できるスキルを作る例です（6.4 を参照）。

スキルには、概要、使うべきとき・使うべきでないとき、ステータスの更新方法（システム・オブ・レコードを呼び出すため）、繰り返し使えるワークフローが含まれます。また、共有する前に、きちんと役割を果たすかを確認する **quality report** があります（デモでは 92%）。プラグインの評価ほど詳細ではなく、適切なタイミングで起動するか、何をするかを理解しているか、といった点を確認するものと説明されています。

作成したスキルは、プラグインカタログに表示され、Office アプリ、Code、Autopilot など、すべてのサーフェスにインストールして使えます。

### 5.6 ステップ 5：Adobe プラグインでローンチを準備する

ローンチ前にやることとして、次の 3 つが示されました。

1. ソーシャル向けに、すべての画像をリサイズする。
2. 動画を、プラットフォームごとに長さの違うショート動画に編集する。
3. 既存のドキュメントをもとにホワイトペーパーを公開する。ただし公開前に機密情報を編集（redact）する。

これらを、plugin registry で利用できる **Adobe プラグイン** で行います（6.5 を参照）。

## 6. デモ・手順

このセッションは、ほぼ全編がデモです。ただし録音は音声だけなので、画面上の細部は分かりません。以下は、語られた範囲の流れです。

### 6.1 プラグインの発見と利用（Rachit）

1. Teams で、「Caldova のカスタマーサービスポータルを来週ローンチできるか。何がまだ足りないか。最小で最も安全なローンチは何か」という問いから始める。Teams での議論から、データは作業データの外にあり、ローンチ状況の最新情報を持つ MCP server の背後にあることが分かる。
2. Home に移動し、同じ質問をする。Copilot は右側に Work IQ から情報を引いていることが表示され、Teams チャネルは見つかるが、事実は作業データにはない、と分かる。
3. plugins タブを開く。350 を超えるプラグインのカタログがあり、組織のカスタムプラグインもここで見つかる。その中から Caldova Launch Readiness プラグインを見つける。
4. このプラグインには、MCP server（外部データへの接続）と 2 つのスキルが含まれている。スキルの 1 つは、Excel レポートの作り方（経営層向けの executive summary を含む）を自然言語で記述したもの。
5. プラグインをトグルでオンにし、Home に戻って同じ質問をする。
6. 回答には、作業データと並んで、呼び出されたプラグイン（Caldova Launch Readiness）と、MCP app による rich UX が表示される。ローンチまでの状況は **6 ゲート中 4 つが完了**。共有データの readiness ワークストリーム（Priya の完了待ち）と、もう 1 つが残っている。
7. Copilot は status が narrow（まだ準備ができていない）であること、サマリー、クリアすべきゲートの一覧、不足している点、次のステップを示す。これは、プラグイン内のスキルが「次のステップが明確になるよう形式を整える」ように指示した結果。
8. Priya が更新したことを受けて、Copilot から refresh する。readiness が更新され、1 ステップ進む。status はまだ narrow だが、次のステップは 2 つになる。
9. 更新後のデータで、同じ Copilot のコンテキストから Excel レポートを作る。レポートには、ローンチ概要、executive summary、ゲートの合計、前回からの変更、次のステップが含まれる。
10. Excel でも、**choose plugins** から同じプラグインを使える。作業の流れを離れずに、同じプラグインでレポートの作業を続けられる。

### 6.2 カスタムプラグインの作成（Rachit、GitHub Copilot アプリ）

1. 開発者として GitHub Copilot アプリを開き、意図から始める。「ローンチオーナーが、ローンチの状況とローンチゲートについて質問できるプラグインを作りたい。データは業務のシステム・オブ・レコードから取得する」と記述し、MCP server の URL も開始プロンプトに入れる。
2. Caldova は、プラグインに特定のブランド資産（アイコン、ブランドガイドライン）を含めることを求めている。それらは OneDrive の launch asset catalog にあり、Work IQ を使って GitHub Copilot のコンテキストに取り込む（ダウンロードやコピー＆ペーストをしない）。
3. build の段階で、GitHub Copilot 内のスキルを使ってプラグインをパッケージ化する。Work IQ からアイコンが取り込まれ、プラグインのパッケージが作られ、ファイルが追加される。
4. preview として registry に公開され、テストに使える。リンクを開くと、Copilot の plugins ページで確認できる。
5. 内部の構造を見ると、パッケージには skills と `manifest.json` があり、manifest.json に MCP server へのリンクが含まれている（データのソース・オブ・トゥルース）。
6. 構造を再検証する（サーバー側で行われるのと同じチェックを、作成中に実行する）。manifest のフィールドや構造が問題ないことを確認し、**package validation が通る**。
7. Mandy を含む同僚にプラグインを共有し、フィードバックを得る。
8. より深く確認するため、重要な 10 ケースの **evaluation set** を実行する。評価システムが呼び出され、10 ケースが定義される（例：利用可能なローンチの発見、フルスコープとコアのみの readiness の対比）。結果のレポートを要約できる。
9. 最初の実行は **0 / 10**。エージェント的な仕組みの中で、プラグインの構造や評価セットを更新して再実行する継続的な改善を行い、スコアをベンチマークにする。数回の実行後に 70%、正確には **77.8%** になった。
10. レポートには、プラグインに送ったプロンプト、返ってきた応答、期待される応答、複数の指標による採点が含まれる。多くの指標で良好だが、あまり良くないものもあった。
11. 77% で十分と判断（「完璧主義ではないので、80% あれば使い始めてよいと思う」と語られた）し、承認を求めて公開（submit）する。Coldova Launch Readiness が組織のカタログに申請される。管理者が承認するまで利用できない。
12. 公開カタログに出したい場合は、**store checks** を実行し、**Partner Center** に進む（実演はされず、説明のみ）。
13. request タブで、申請したプラグインが届いていることを確認し、A365 側で詳細を見られる状態にした（このあとガバナンスの話に戻る）。

### 6.3 管理者としての承認と管理（Rachit、A365 / Microsoft 365 admin center）

1. 管理者の立場になり、申請されたプラグインの内容を確認する。launch reviews の一覧表示、launch updates の下書き、launch demos（聞こえたまま）の承認などのツールが含まれている。
2. Approve をクリックする。テナントの全員が registry で使えるようになる（デモでは本人が管理者を兼ねている）。
3. Microsoft 365 admin center の tools registry を開く。プラグインカタログのプラグインと、組織のユーザーや開発者が公開したカスタムプラグインの両方が表示される。
4. 例として sales plugin を開く。何をするプラグインか、構成要素（Dynamics 365 の MCP server と、営業チームに役立つ豊富なスキルの一覧）を確認する。
5. 右上の **install** ボタンから、すべてのユーザー、または特定のユーザー・グループにインストールできる。デモでは営業部門のグループを検索して Next、Install をクリックし、数秒でグループ全員が使えるようになった。ユーザーが探す必要はなく、Copilot の中に表示される。
6. 使用状況：launch readiness プラグインについて、過去 30 日の利用状況を確認する。大きなスパイクがあり、「別のセッションで使われたのだろうか」と発言があった（原因は発表では説明されていません）。利用できるすべてのツールも見られる。
7. プラグインが不要になった場合は **block** もできる。

### 6.4 Copilot 上でのスキル作成と共有（Rachit）

1. Home に戻る。readiness ウィジェットで、最新の refresh 後に **6 ゲート中 6 つがクリア** と表示される。残りは最終承認のみ。
2. 経営層に最新状況を伝えるため、Mandy と Simon にローンチを承認してもらうメッセージを下書きする。システム・オブ・レコードに基づいてすべてのゲートがクリアしたことが確かなので、Copilot からメールを送信する（実際に送信した）。
3. この更新のやり取りを繰り返し行うので、**launch readiness** という名前のスキルとして保存する。Copilot の中でスキルが作成される。概要、使うべきとき・使うべきでないとき、ステータスの更新方法、ワークフローが含まれる。
4. **quality report** は 92%。
5. プラグインでステータスを更新したため、スキルはその目的を達成するために実際に使われた tools を取り込んでいる。
6. チームに共有する。共有後、A365 に移ると、launch readiness（実体はスキル 1 つを含むプラグイン）の概要、最終更新日、作成日が見られ、users に共有した相手（Mandy）が表示される。
7. 作成したスキルは、プラグインカタログから、Office アプリ、Code、Autopilot などすべてのサーフェスにインストールして使える。

### 6.5 ローンチの承認（Rachit、デモは途中で失敗）

1. Mandy が先ほど送ったメールに返信して承認する（Mandy が大げさに承認を入力した、と語られている）。
2. Rachit は Copilot に「Mandy の最新のメッセージを探し、その内容に基づいてローンチを承認して」と依頼する。想定されていた動きは、Work IQ で Teams から Mandy の承認を取得し、プラグイン経由でシステム・オブ・レコードに送って承認ステータスを更新する、というもの。
3. Copilot は、メールとチャットを探し、Mandy の承認が届いたことを示した。
4. しかし **コネクターが利用できず、画面の読み込みが止まった**。成功していれば、先ほどと同じウィジェットで「承認済み」と表示される、と口頭で補足された。

### 6.6 Adobe プラグインによるローンチ準備（Rachit）

1. Home で、Mandy から渡された 3 つの作業を行う。
2. **画像のリサイズ**：ソーシャル向けの 4 枚の画像に対して、「Caldova のカスタマーサービスポータルのローンチ用に、Adobe を使って Facebook、Instagram、LinkedIn 向けにリサイズして」と依頼する。右側に、Adobe プラグインが作業データ、SharePoint データ、Graph データと並んで呼び出されたことが表示される。各プラットフォームの要件は、プラグインのスキルがプラットフォーム名から要件へのマッピングを持っているため、名前を指定するだけでよい。ウィジェットで、サイズの異なる編集済みの画像が確認できる。
3. **動画の編集**：OneDrive にある約 4 分のローンチ動画を、15 秒、20 秒、45 秒のカットにする。Adobe が再び呼び出され、まず 15 秒版が作られる（再生して確認した）。続いて 20 秒版、45 秒版も作成でき、ダウンロードして視聴できる。要件を満たしているかのサマリーも示される。
4. **ホワイトペーパー**：社内向けのマーケティング文書の下書きには、Caldova の機密情報が含まれている。Word の右側のパネルから、launch readiness プラグイン、そのスキル、Adobe プラグインが使えることも示された（同じプラグインを Office の中でも使える例）。
5. メインのタブに戻り、ホワイトペーパーと簡潔なブローシャー PDF を作る。Adobe のツールを呼び出して 2 つのドキュメントが作られ、**redaction（機密情報の編集）を承認した後にのみ** 顧客向けのものが生成される。
6. Acrobat のウィジェット（Copilot に埋め込まれた rich なインターフェース）で、元の下書きより見栄えの良いコピーを確認する。機密情報が残っていないことを確認し、ダウンロードしてマーケティング担当に送れる。

## 7. 注意点・発表者の気付き

- **ライブデモは失敗することがあります。** 最後の承認のデモでは、コネクターが利用できず、画面の読み込みが止まりました。発表者は、成功していれば同じウィジェットが「承認済み」と表示されると口頭で補足しています。
- **評価は 0 点から始まることがあります。** カスタムプラグインの最初の評価は 0 / 10 でしたが、プラグインの構造や評価セットを更新して再実行し、77.8% まで改善しました。スコアは、継続的に改善するためのベンチマーク（定量的な基準）として使うと説明されています。
- **プラグインを公開しても、管理者の承認までは使えません。** 組織のカタログに申請しても、管理者が承認するまで利用できません。
- **データが作業データの外にある場合があります。** その場合は、まず plugins タブでカタログを探し、なければカスタムプラグインを作る、という流れが紹介されました。
- **Work IQ Developer Tools の評価機能は、Ignite に合わせて最近リリースされたばかり** で、今後も投資する領域です。フィードバックが求められています。
- 発表では、プラグインの価格やライセンス、各製品の提供状況の詳細までは触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **ユーザー**：Copilot（Home、Code、Autopilot）や Office アプリで、同じプラグインを使える。作業の流れを離れずに、外部システムのデータ取得、Excel レポートの作成、Adobe による画像・動画・PDF の処理ができる。プラットフォームごとの要件を知らなくても、スキルが補ってくれる。
- **開発者・ローンチオーナー**：意図から公開までのライフサイクル（build、validate、preview、feedback、evals、publish）を、GitHub Copilot などのコーディングエージェントから進められる。Work IQ を使って OneDrive 上の資産をダウンロードせずに取り込める。
- **管理者**：A365 の既存の統制（有効化・無効化、ブロック、グループへの付与）を、プラグインにも使える。ロールアウトの制御（特定グループへの事前インストール）、使用状況の確認（過去 30 日の利用など）ができる。
- **組織全体**：スキルの共有により、再利用できるワークフローを同僚に展開できる。

## 9. まとめ

Microsoft plugin registry は、tools、skills、agents を plugin としてまとめ、Copilot（Home、Code、Autopilot）と Office で使えるようにする、単一のストアです。350 の公開プラグインがあり、組織向けのカスタムプラグインも作れます。

- カスタムプラグインは、Work IQ Developer Tools（CLI とスキル）で、意図から build、validate、preview、評価、publish まで進められます。
- 管理者は A365 でプラグインの承認、グループへのインストール、ブロック、利用状況の確認ができ、エージェントで慣れた統制がプラグインにも広がります。
- ユーザーは Copilot Cowork などで、自分のワークフローをスキルとして作って共有できます。
- Adobe プラグインの例では、画像のリサイズ、動画のカット、機密情報を編集した PDF の作成を、Copilot の中から行いました。

最後に、学習用のリソースとして、Work IQ Developer Tools のスタートガイドと、Copilot 向けのすべてのプラグインを集めた新しいカタログが案内されました（URL は音声では読み上げられていません）。関連する多くのセッションの録画も紹介されました。
