# BRK212 Secure the Follow-Through: Trusting Autopilot at Scale

## 1. はじめに

このセッションは、ユーザーが席を離れている間も作業を続ける「自律型エージェント」を、組織としてどう信頼できる状態にするかを説明するものです。題材は Microsoft の first-party の Autopilot です。ただし登壇者は、ここで話す考え方は Autopilot に限らず、他の自律型エージェントを評価するときにも使えると述べています。

発表は大きく 2 つの部分でできています。前半では、自律型エージェントを信頼するための **4 つの原則**（識別できる、アクセスが制限・統制されている、継続的に保護されている、透明で監査できる）を示し、Autopilot がどういう構造でそれを満たしているかを説明します。後半では、4 つの原則それぞれについて、Microsoft Entra、Microsoft Purview、Microsoft Defender、Agent 365 の管理画面を使った実演（スクリーンショットによる説明）を行います。

最も重要な主張は、人間の従業員やベンダーを守るために身につけた知見があれば、自律型エージェントを守るために必要なことの **80〜90%** までは到達できる、という点です。エージェント向けに追加で必要になる作業は、主に 2 つの要素に絞られると説明しています。

## 5. 発表内容の詳細

### 5.1 自律型エージェントとは何が違うのか

従来のアシスタント型のエージェントは、質問に答える、あるいは会議の準備のために 1 つのドキュメントを分析する、といった使い方が中心でした。自律型エージェントは、ゴールを与えると、自分でたくさんのサブタスクを作って動きます。情報を集め、その情報で次のステップを決め、同僚に連絡して情報を集めることまでできます。Eric 氏は、プレゼン資料の作成のように、これまでより多くを任せることになるので、信頼の度合いも上げる必要があると説明しています。

### 5.2 信頼のための 4 つの原則

Eric 氏は、人間に対するゼロトラストの原則と多くの共通点があるものの、エージェントでは少し違ってくると述べながら、次の 4 つを挙げています。

| 原則 | 説明 |
| --- | --- |
| 1. 一意に識別できる | 従業員が各自のアカウントや ID を持つのと同じく、エージェントも識別できること。管理者がログ上で区別できるだけでなく、**エージェントとやり取りする他の人間にも区別できる**こと。例えば、ドキュメントを編集したのが同僚なのか特定のエージェントなのかが分かる必要がある。 |
| 2. アクセスの制限と統制 | 経営層向けプレゼンの準備のような価値の高いゴールを与えられたからといって、無制限の権限を持たせてはいけない。人間の従業員は研修や採用時の判断、解雇のリスクから一定の良識を期待できるが、エージェントにはその良識がない。そのため最小権限などのゼロトラスト原則を、より厳しく適用する。 |
| 3. 継続的な信頼 | 従来のアシスタントは開始時の保護が中心だった。エージェントは数時間、数日、数週間と動き続けるので、内部・外部のリスクから常に守る必要がある。エージェント自体に変更が無くても、新しい情報を取り込むことで挙動が変わり、間違うことがある。 |
| 4. 透明性と監査可能性 | 人間が間違えたら「3 日前に何を考えていたのか」と聞けるが、エージェントには聞けない。そのため、行動の根拠（いわゆる「思考過程」）を透明にする工夫が必要。通常の監査ログでもある程度は得られる。 |

### 5.3 原則を実現するための制御

Eric 氏は、4 つの原則を具体的な制御に落とした全体図を示しています（スライド）。

* **識別**：エージェントを区別し、責任を明確にできる identity プラットフォーム。
* **アクセスの制限**：2 つの要素がある。1 つは、エージェントを実行する安全な実行環境（従業員にとっての、企業管理下のデバイスに相当）。もう 1 つは、エージェントがアクセスできる情報と、使ってよい操作の統制。
* **継続的な保護**：エージェントは長時間動くので、従業員向けのデータセキュリティや脅威保護と同じものが、エージェントにも働き続ける必要がある。これに加えて、エージェント固有のセキュリティ機能。
* **透明性**：監査記録。ベンダーや従業員と同様のコスト管理。関与する AI モデルとサービスの把握。

この図の右端の列（エージェント固有の部分）を除けば、従業員や人間のベンダー向けのベストプラクティスと同じです。つまり、人間向けの強いベースラインがあれば、それをエージェントにも使えます。エージェント向けに追加で必要な作業は、主に右側の 2 つの要素です。

### 5.4 Microsoft Autopilot の基盤

Eric 氏によると、Autopilot はこの 1 年ほど進化させてきたもので、Microsoft 社内でも自律型エージェントを信頼できるかを検証するために、ストレステストとして使ってきたと説明しています。かつては Scout や Lobster など別の名前もあった、という話があり、Omar 氏の組織にも触れています（聞き取りが不明瞭で関係の詳細は確認できません）。Omar 氏による先行セッションで Autopilot のデモがあったとのことで、見ていない人には見直すことを勧めています。

Copilot Chat や Cowork とは、信頼の考え方が次の 2 点で異なると説明されています。

1. 人間のアクセスを拡張するものである。
2. Exchange、Teams、OneDrive に、**エージェント自身の identity** を持つ（自分のメールアドレス、Teams の @mention ハンドル、OneDrive のファイル）。そのため、メールのやり取りやチームでの共同作業など、人間のユーザーと協働できる。

Autopilot の基盤は 4 つの要素で説明されています。

1. Microsoft が作った agent であり、Microsoft のサービスである（自分で構築しなくてよい）。コンシューマー向けに Facebook が Muse で行っているのと似た形だと例えています（Muse の表記は音声認識の都合で確定できません）。
2. 独自の identity とリソースを持ち、SaaS アプリや M365 での共同作業では別の従業員のように見える。
3. **Work IQ** と密接につながっている。Work IQ は Autopilot の知性とコンテキストの源であり、同時に、人間のユーザーにもエージェントにも適用されるポリシーや制御をかけられる場所でもある。
4. エージェント向けのアクション（操作）と安全策を、エージェントの周囲に追加で構築している。

アーキテクチャ図（Omar 氏のセッションでも使われたもの）の説明は次のとおりです。

* **サーフェス（左上）**：Teams、Outlook、Copilot アプリ、Word など、同僚と共同作業する場所。Word ではコメントのスレッドにエージェントが返信したり提案したりする。M365 で人間と共同作業できる場所なら、どこでも Autopilot と共同作業できる。
* **untrusted sandbox（右下）**：コアのエージェントが動く場所。この例では OpenClaw を使っている（音声認識の都合で表記が確定できません）。この実行環境は **設計上、信頼しない（untrusted）** 扱いで、Autopilot ごとに分離されたコンテナを持つ。コンテナの中に認証情報（credentials）は置かない。
* **trusted multi-tenant service（中間）**：Microsoft が運用する追加のロジック層。エージェントの機能を管理し、アクションを承認し、データへのすべてのリクエストを仲介して認証情報を付加する。sandbox が侵害されても、盗める認証情報はそこにない。
* **状態の保存**：エージェントがアクセスする情報の状態はすべて M365 内にある。エージェントは Work IQ を使い、記憶（メモリ）を OneDrive に保存する。そのため、OneDrive に適用している地理的な保管場所のポリシーや DLP ポリシーが、人間の従業員の場合と同じようにこのエージェントのコンテンツにも適用される。

Eric 氏は、この構造は複雑だが実現可能で、強い信頼レベルを達成できると述べています。Autopilot の価値よりも、管理・セキュリティ制御と運用モデルをどう重ねるかに関心のある聴衆を想定して、次にその層の話に進んでいます。Microsoft 社内でこの 1 年、より苦労したのがこの層だったとも述べています。

### 5.5 運用モデル：ベンダーの比喩

Autopilot の基盤とセキュリティツールがそろっても、運用モデルが必要です。ベンダーについて Microsoft がすでに答えを出している問いが、そのままエージェントに当てはまります。

* 誰が仕事を割り当て、誰が成果をレビューするか（ベンダーには担当のスポンサーがいる）。
* 誰がアクセスを承認し、アクセス制御をレビューするか。
* 調査が必要になったとき何が起こるか（通常はベンダーのスポンサーとなる従業員を巻き込む）。

エージェントでも同様に、責任を持つ従業員のスポンサーを置きます。IT は、従業員よりも厳しいポリシーをベンダーやエージェントに適用する場合があります。セキュリティ部門は、従業員やベンダーと同じようにエージェントを調査できる必要があります。

### 5.6 使える Microsoft のセキュリティ製品

| 製品 | 発表での役割の説明 |
| --- | --- |
| Microsoft Entra | identity とアクセスのガバナンス（書き起こしでは「Intra」と表記される箇所が多く、本書では Entra と表記します） |
| Microsoft Purview | データセキュリティ、コンプライアンス、監査 |
| Microsoft Defender | 関連する脅威保護とセキュリティの証跡 |
| Microsoft Perception | 新しい製品の 1 つで、セキュリティ調査の能力を拡張・支援する（音声認識の都合で製品名の表記が確定できません） |
| Microsoft Agent 365 | AI の可観測性（observability）のプラットフォーム |

これらは人間向けに別々に進化してきたが、統合が進んでおり、その統合によって Autopilot のような自律型エージェントを end-to-end で管理できる、と説明されています。Entra、Defender、Purview はエージェントより前からある製品で、DLP のような機能の多くは、人間にも Autopilot にも同様に適用されます。エージェント固有の機能は一部で、デモの中で紹介するとしています。

### 5.7 原則 1：識別できる（SecOps の観点）

Eric 氏は、SecOps チームがすでにインシデント調査の手順を持っている前提で、それを Autopilot にも再利用できるかを問います。Microsoft 自身と、パイロット中の他の顧客の経験では、**現在のプロセスのかなり大きな割合を再利用できる** そうです。「Autopilot」という言葉を担当者に研修しなくてもかなり進められる、とも述べています。理由は、エージェントが人間のアカウントやベンダーのアカウントと同じように見えるからです。Entra は、M365 のすべてのアカウントを、人間のアカウントを区別するのと同じように一意に識別できるようにしています。

たとえば、調査中に問題のアカウントがベンダーだと分かったら、まずそのベンダーを後援する正社員を探し、調査に加えます。Autopilot についても、Entra が employee sponsor を特定する標準的な方法を持っています。調査チームはそのスポンサーから、「これは人間のベンダーではなく Autopilot だ」と聞けます。そこから、通常のインシデントとして扱うか、エージェントを前提とした特別な対応をするかを判断できます。Eric 氏は、自身の経験では「10 回のうち 9 回は、ベンダーと同様に扱えば、セキュリティのフローを通過して問題ない」と述べています。

なお、最初の原則のデモは管理者の視点で行い、エンドユーザー視点（ドキュメントの編集が、どのエージェントや同僚によるものか分かる）の説明は Omar 氏のセッションで行われたと述べています。

### 5.8 原則 2：アクセスの制限と統制（Entra Governance）

ベンダーに対して、セキュリティ部門が多要素認証や管理対象デバイスを求める（環境を制限する）のと同様に、Autopilot も十分に管理された環境（Autopilot の基盤）で動かすことが、管理対象デバイスに相当します。さらに、アクセスできるファイルを制限すれば、ガバナンスの統制が始まります。

Eric 氏は、業界の多くの組織で最小権限（least privilege）が理想ほどには徹底されておらず、従業員にも、ベンダーにも、必要以上のアクセスを与えていることが多い、と認めています。この部分を強化するためのツールとして、**Microsoft Entra Governance**（書き起こしでは「Intra Governance」と表記）を挙げています。ゼロトラストの最小権限のために設計され、ベンダー、従業員、Autopilot のような自律型エージェントのすべてに同じように機能します。

重要な機能として **access packages** を説明しています。チームの多くのメンバーが使う共有権限をひとまとめにしたものです。

経営層向けプレゼンの例では、次の流れが語られています。

1. すでに他の人間メンバー向けに、リソース配分などの重要ファイルにアクセスできる access package がある。
2. Autopilot の人間のスポンサーが、その access package を Autopilot に付与するよう申請する。操作の流れは、人間の同僚に付与する場合と同じで、同僚のメールアドレスや名前の代わりに Autopilot のものを入力する。
3. 承認されて権限が付与されたら、Autopilot はチームのファイルを分析し、ドキュメントにコメントを書き込んだり、共有の PowerPoint にチームメンバーが情報を追加するように働きかけたりして、共同作業を進められる。ユーザーが移動中や睡眠中でも進む。
4. レビューが終わったら、スポンサーが access package のアクセスを取り消すべきだが、実際には多くの人はそれが得意ではない。

そこで、Entra Governance には **期限付きアクセスの機能** があります。エージェントの場合、追加の人間によるレビューを通して延長されない限り、アクセスは自動的に取り消されます。これらの access package、レビュー、ライフサイクル管理は、もともとエージェントのために作られたものではなく、ベンダーと人間のために作られたものですが、エージェントのアクセスを絞る点でさらに価値があると述べています。

また、Autopilot から使い始めて、すごいと感じてベンダーに広げ、さらに従業員に広げる組織もあれば、従業員から始めてベンダー、Autopilot へと広げる組織もある、とのことです。どこから始めても、AI 時代への準備になるという説明です。

### 5.9 原則 3：継続的な保護（Purview と Defender）

Autopilot が、経営層向けレビューの準備のために Teams のファイルへのアクセスを与えられ、メンバーがオンラインの間も動き続けて、追加のファイルにアクセスしたり、メールを送受信したりする場面を想定します。Microsoft Defender と Microsoft Purview を使っていれば、これらの製品は人間の従業員やベンダーと同様に、その活動を保護し続けます。Eric 氏は、「Purview や Defender の構成を変えなくても、ほとんどの組織ではデフォルトで Autopilot に対して動作し始める」と述べています。

* **Purview**：たとえば、アクセスを与えたフォルダの中にあっても、特に機密性の高いファイルへの Autopilot のアクセスを防ぐ。Autopilot が誤って組織外にドキュメントをメールで送ろうとした場合に検出する。
* **Defender**：受信・送信メールのスパムやフィッシングなどの攻撃を監視する。調査が必要な、リスクのある活動のログの監視という従来の役割を続ける。

さらに、どのアカウントタイプにも適用される多くの制御に加えて、エージェント固有の制御もサポートされます。発表で挙げられたのは、**エージェントに対するプロンプトインジェクション攻撃への保護**です。Defender はメールを見ることで、Purview はエージェントがアクセスできるドキュメントを見ることで対応できる、と説明されています（発話の一部は聞き取りが不明瞭です）。

### 5.10 原則 4：透明性と監査

Autopilot は独自の Entra の identity と M365 リソースを持つため、M365 へのすべてのアクセスがその一意の identity で記録されます。Eric 氏は、次のように整理しています。

* Entra のサインインログに、その identity が残る。ブロックされたアクセスも含まれる。
* Purview のデータアクセスログに、identity とともに記録される。ブロックされたデータアクセスも含まれる。
* Entra Governance に、access package が付与された記録と、後で取り消された記録がある。
* Defender に、ブロックしたメールの悪意ある内容や、リスクのある活動・攻撃の記録がある。

これらをまとめて使うことで、セキュリティ調査だけでなく、監査人が必要とする場合の監査証跡にもなるとのことです。

### 5.11 発展シナリオと他のツールを使う場合

セッションは主に M365 のデータにアクセスする Autopilot に焦点を当てましたが、Eric 氏は、それに限られないと述べています。ベンダーに M365 だけでなく、Azure、GitHub、Salesforce、自社の業務アプリのリソースを用意することもあるのと同様に、ベンダーのアクセスをプロビジョニング・管理するのと同じ Microsoft のセキュリティツールを、Autopilot が他のツールにアクセスする際にも使えます。例として次の 2 つが語られています。

* 従業員が Autopilot に、Salesforce の sales pipeline の継続的な分析を頼む。1 時間ごとに最新情報を取り込み、Excel の予測を更新する。
* 管理者が Autopilot に、特定のメールボックスに届く Azure の追加ストレージ予算に関する従業員のリクエストを、常時処理させる。

また、Autopilot は Microsoft のセキュリティツールでしか使えないわけではありません。組織がライセンスしたツールや自社開発のツールを使うこともできます。その場合は、先に示した 3 つの層のうち、運用モデルだけでなく、管理とセキュリティ制御も組織の責任になります。エージェント向けにそれらを適用する学習も必要です。

さらに極端な場合、組織は Autopilot 自体を使わず、自律型エージェントを別途ライセンスまたは自作するかもしれません。Microsoft は、Microsoft 365 の上に構築され、Entra ID を持つエージェントについての選択肢も検討していると述べています。どの場合でも、4 つの原則は、Microsoft と関係があるかどうかにかかわらず、自律型エージェントを組織で信頼できるものにするために必要だと述べて締めくくっています。

## 6. デモ・手順

デモを担当した Erica 氏は、冒頭で「スライド形式のデモ（slide demo）をするのは初めて」と述べています。Autopilot は限定プレビューが続くため、環境に出てくるまで数週間かかるかもしれませんが、事前に準備できるように、セッションページからダウンロードできる PowerPoint に、これらのスクリーンショットをすべて載せているとのことです。スクリーンショットは直近数日間に、実際の環境（ライブ環境）で、画像加工なしで撮影したものだと説明されています。つまり、ライブの操作ではなく、スクリーンショットを使ったウォークスルーです。

> 注意：録音には音声しかないため、画面の細部は確認できません。以下は、語られた範囲の手順です。

### 6.1 デモ 1：Entra で Autopilot の identity を確認する（原則 1）

1. Entra ポータルを開く（identity、Autopilot の identity を管理する場所と説明）。
2. 「agents」をクリックして agents の概要（overview）エリアに進み、「agent identities」を開く。
3. 他のエージェントや組織内のものと並んで、Autopilot が表示されている。
4. Autopilot の identity をクリックして、次の点が目立つと説明している。
   * **sponsor（スポンサー）と owner（オーナー）** がいる。
   * 大規模にエージェントを管理するための **agent blueprints**（ブループリント）がある。
5. owner と sponsor の違いの説明：
   * owner は、アクセスを承認したり、日常のビジネス運用を扱ったりする。sponsor は、セキュリティポリシーを管理し、より IT 管理者に近いレベルで監督する。
   * その後の言い直しとして、owner が技術的な管理を担い、sponsor が業務上の説明責任を担う、とも述べている（2 つの説明の表現が少し異なる）。
   * このデモ環境では、owner と sponsor は同じ人物だが、実際には別々の人であることが多い。
6. 概要ページに戻り、Autopilot に関連付けられた blueprint をクリックする。blueprint は、アクセスポリシーなどの共通のセキュリティ設定を 1 つのパッケージにまとめ、同じタイプのエージェント全体に適用するための仕組みで、大規模管理に重要だと説明している。自律的に動けるため人間やほかのエージェントと違うルールを Autopilot に設けたい場合に、blueprint で一括適用できる。
7. Autopilot は、identity に加えて、人間のユーザーアカウントに非常に近い **agent user account** を持つ。そのアカウントを開くと、専用のメールアドレスがある。これにより、ユーザーと同様に、権限、ポリシー、動作のガードレールを割り当てて管理できる。access package などのセキュリティ設定もユーザーのように確認できる。
8. サインインログ（sign-in logs）を開くと、人間のユーザーとよく似ており、通常のユーザーのようにサインインしている。サインインの調査に必要なメタデータもある。

デモの結論は、「Autopilot は自律型エージェントだが、自律的に野放しに動いているのではなく、追跡でき、識別でき、だからスケールできる」というものです。

### 6.2 デモ 2：access package を Autopilot に割り当てる（原則 2）

1. Entra の管理センターで、entitlement management から access packages を開く。
2. いくつかの access package があり、その中の Finance チーム向けのものを開く。これは Autopilot が財務のタスク（月次決算の処理、重複の排除、計上漏れの確認）を支援できるように設定したもの。
3. resource roles を見ると、**Microsoft 365 グループと SharePoint サイト** が含まれている。作業に必要なものを 1 つのバンドルとして割り当てる（2 つの画面で個別に権限を割り当てる必要がない）。
4. そのポリシーを開くと、**30 日で期限切れになる** 設定が強調表示されている。30 日後に誰かがレビューし、アクセスを続けるなら延長する。承認を必須にしたり、承認ワークフローを構成したりもでき、柔軟性が高いと説明している。
5. assignments（割り当て）で、ポリシーを選び、identity として Autopilot（専用アカウントを持つもの）を選択して、パッケージに割り当てる。
6. 割り当ての終了日を指定する。月次決算が終わる月末までで足りるので、30 日より短い期間にした。最小権限で、タスクが実際に必要とする期間に限定するためだと説明している。
7. 送信して「add」をクリックすると、Autopilot が access package の一部になる。
8. Entra でグループのメンバーシップを見ると、人間のユーザーと並んで Autopilot がメンバーとして表示されている。

### 6.3 デモ 3：Defender でのインシデント調査と Agent 365 での管理（原則 3）

SOC 管理者の視点から、問題が起きたときや一連の出来事のつながりを確認したいときの画面が紹介されています。

1. Microsoft Defender ポータルで incidents を開き、一覧からインシデントを 1 つクリックする。
2. Autopilot が取った一連のイベントが表示される。この例は悪質なものではなく、ファイルへのアクセスとダウンロードだった。場所、identity、IP アドレスなどがつながって表示される。
3. アラートをクリックすると、ファイルのダウンロードに関するアラートがあり、多くの情報が含まれる。timeline（イベントの時系列）を展開すると、各イベントについてテレメトリと詳細情報があり、それを使って脅威かどうかを調査し、必要に応じて緩和に進める。
4. 調査後に IT 管理者として取れる対応を見るため、Microsoft 管理センター内の **Agent 365 ポータル** に切り替える。
5. 「all agents」ビューで autopilot を検索し、autopilot のエージェントタイプをクリックする。
6. その環境にある、このエージェントのインスタンスが見られる。この例では 2 つあり、そのうち 1 つが、発表を通して見てきた Autopilot。
7. それをクリックすると、IT 管理者向けのビューで詳細が見られ、右上でそのエージェントを **ブロック（block）** できる。
8. この操作は、**すべての Autopilot ではなく、この 1 つの Autopilot だけ** をブロックできる点が重要と説明している。ブロックすると、その Autopilot は作業を続けられなくなる（Brad という例のユーザーは続けられる、と述べているが、この部分は聞き取りが不明瞭）。

### 6.4 デモ 4：Defender・Purview での透明性（原則 4）

ペルソナごとに、すでに行っている仕事の中で透明性を確保する方法の紹介です。

1. Defender で **advanced hunting** を開く。
2. エージェントの identity（Entra で見た GUID）で絞り込み、クエリを実行する。Microsoft 365 全体と、導入しているネットワークやツールにまたがるイベント一覧が得られる。先ほどのファイルダウンロードのイベントも、記録として見られる。
3. Purview 管理者の視点で、**data security posture management** の **activity explorer** にある **AI activities** ビューを開く。Erica 氏が「お気に入りの、使いやすい画面の 1 つ」と紹介している。Copilot などを含め、環境内の任意のエージェントや AI が、ユーザーとどのようなやり取りをしたかが見られる。
4. エージェントを選択し、対象の特定のエージェントを指定すると、Copilot Super App（書き起こしの表記のまま）、Teams、Web にまたがるやり取りが一覧になる。1 つをクリックすると、アクティビティの詳細が見られる。
5. **近日中に**、入力された内容とその応答といった実際のやり取りのテキストも見られるようになる。このレベルの詳細には特別なアクセス権が必要なので、Purview 管理者に依頼するよう案内している。
6. **Purview の audit log** で、エージェントを検索して結果を取得する。M365 全体で行われていることとアクションについて、非常に網羅的なログが得られる。エクスポート API を使い、SIEM ツール（書き起こしでは「SEM tool」と表記）に取り込み、さらに相関分析ができる。

## 7. 注意点・発表者の気付き

* **信頼の保証ではなく、条件づくり。** 4 つの原則でエージェントが間違えなくなるわけではない。合理的に信頼できる条件を整える枠組みである。
* **最小権限は、多くの組織で十分でない。** 従業員にもベンダーにも、望ましい以上のアクセスを与えている組織が多いと認めている。エージェントで強化する機会になる。
* **アクセスの取り消しは忘れられがち。** スポンサーが access package の取り消しを実際にはあまりしないので、期限付きアクセスで自動的に失効させる。
* **エージェントは新しい情報だけで間違うことがある。** エージェント自体が変わらなくても、取り込んだ情報で挙動が変わりうるため、継続的な保護が必要。
* **管理・セキュリティ制御と運用モデルが最も苦労した部分。** Microsoft 社内でこの 1 年、この層で課題が多かったと述べている。
* **Autopilot は限定プレビュー。** 環境に出てくるまで数週間かかるかもしれない。
* **Purview の詳細なやり取りの閲覧には特別なアクセスが必要。** 実際のやり取りのテキスト表示は「近日中」であり、現時点では提供されていない。
* **Microsoft 以外のツールを使う場合は、管理とセキュリティ制御も自分たちで担う。** 学習のプロセスが必要になる。

## 8. 利用者にとっての利点

このセッションでは、具体的な顧客事例や数値実績（時間短縮の割合など）は紹介されていません。発表で語られた利点は次のとおりです。

* 人間の従業員やベンダー向けにすでにあるセキュリティのベースラインと運用プロセスを、エージェントに再利用できる（Eric 氏の見立てでは、必要な対応の 80〜90%）。
* SecOps チームのインシデント調査のプロセスを、大部分は再利用できる。ベンダーと同様に扱えば、10 回のうち 9 回は問題なく通る。
* Purview や Defender は、構成を変えなくてもほとんどの組織でデフォルトで Autopilot に対して働き始める。
* 状態やメモリが OneDrive など M365 にあるので、既存の保管場所ポリシーや DLP ポリシーがそのまま適用される。
* Autopilot をすべてではなく 1 つだけ指定してブロックできる。
* Entra、Purview、Defender に残る一貫した記録が、セキュリティ調査にも監査人向けの証跡にも使える。

## 9. まとめ

自律型エージェントを組織で信頼するには、次の 4 つを満たすことが必要というのがこのセッションの結論です。

1. 一意に識別できる（Entra の agent identity、sponsor、owner、blueprint）。
2. アクセスが制限・統制されている（Autopilot の分離された実行環境、Entra Governance の access package と期限付きアクセス）。
3. 継続的に保護されている（Purview と Defender、Agent 365 での個別ブロック）。
4. 透明で監査できる（Entra、Purview、Defender の記録、advanced hunting、AI activities、audit log）。

実現の鍵は、エージェントを「従業員が後援するベンダー」として扱い、既存のベンダー管理の運用モデルとセキュリティツールを延長することです。Eric 氏は、Autopilot を使うかどうか、Microsoft のツールを使うかどうかにかかわらず、この 4 つの原則を、自律型エージェントを信頼できるものにするための枠組みとして使うよう勧めて締めくくっています。
