# BRKSP595 Get an AI advantage when the Microsoft ecosystem works together

## 1. はじめに

このセッションは、Insight 社の 2 人が、自社で Microsoft の製品群（Copilot、GitHub Copilot、Foundry、E7、Agent 365 など）を使い込んだ経験をもとに、「AI エージェントを速く作る」ことと「エージェントを統制する」ことを両立させる方法を、ライブデモ付きで紹介する内容です。

前半は、Insight が「Customer Zero」として全社でエージェントを展開した結果（約 16,000 のオーナー不在エージェントの可視化、94% の社員が日常的に利用、など）を紹介します。後半は 3 つの場面に分かれます。

1. **HVE（hypervelocity engineering）** と、その中核である **RPI（research, plan, implement）** を VS Code で動かし、Terraform を生成するデモ
2. 同じ操作が **Entra Global Secure Access（GSA）**、Agent 365、Defender などでどう見えるかというセキュリティ側のデモ
3. **Surface Ultra（RAM 128GB）上のローカルモデル**で GitHub Copilot CLI を動かし、トークン課金なしで開発支援を受けるデモ

発表者は、開発側の生産性とセキュリティ側の可視性・統制が、同じ操作の表と裏として同時に成立することを、実機の画面を行き来しながら見せています。なお冒頭で、発売前のハードウェアや未リリースの機能を使うため、デモがうまくいかない可能性があると断っています（7 章）。

### 5.3 デモ：HVE / RPI で Terraform を生成する

#### HVE とは

Parker 氏は HVE（hypervelocity engineering）を、Microsoft の Frontier に関わる取り組みから生まれた考え方だと説明しています（発言の該当箇所は音声認識が不明瞭で、正確な組織名は確定できません）。スクリプト、スキル、エージェント、インストラクション一式が OSS として、無料で VS Code の拡張機能マーケットプレイスに公開されています。インストールして自社の知識で拡張でき、必要な中核機能だけを取り出して自社の標準を差し込むことも可能です。ここでは **HVE Core** を使っていると述べています。

#### RPI（research, plan, implement）

RPI は、質問とコードベースに対して深い調査（research）を行い、計画（plan）を作り、実装（implement）まで進める 3 段階の流れです。最後に、計画と実装を突き合わせてレビューする工程があります。小さな部分を 1 ステップずつ進めることもできるが、主眼は実装フェーズをエージェントに任せることだと説明しています。

#### 実演された内容

デモ対象は、1〜2 つの処理だけを行う小さな API アプリ（モックデータ入り）です。Parker 氏は「デプロイ方法が分からない」という状況を設定しました。語られた順は次のとおりです。

1. VS Code の右側のチャットで RPI を使い、Terraform を作成するよう依頼する
2. Bing で Terraform の業界のベストプラクティスを調べ、MCP 呼び出しなども使って反映するよう指示する（モデルは auto モードで、「もっと速いモデルでもよかった」と述べています）
3. エージェントが既存の Terraform ディレクトリなどのコンテキストを確認する
4. 左側に、demo root の下に「.copilot tracking」というフォルダ（音声からの表記で、ハイフンの有無などは確定できません）が作られる。生成される Markdown ファイルを保存する場所で、BA や SRE ops エージェントなどが後から参照できる。「なぜその日にその機能を提供したか」という履歴が、メンバーの入れ替わり（leaver, mover, joiner）の際にもコードベースに残る
5. research が完了し、Markdown ファイルと、判断指標を記録した JSON ファイルが開く。コミットすればチームがそのまま引き継げる
6. Terraform 一式が自動で生成され、plan も完了し、変更はすべてログに残った（Will 氏がトラフィックログを確認する場面のあとに、Parker 氏が出力に戻って確認しています）
7. その後、plan のファイルを開いて見せた。フェーズごとのチェックリストと目標（インフラの追加と検証、デモ用インフラのプロビジョニングなど）が並び、実装が進むにつれて項目がチェックされ、会社の仕様と標準に従って進む

画面の細部（ファイル名や UI の配置など）は音声からは確認できません。

Parker 氏は、Will 氏がセキュリティ側の画面を見せていた間に、自分のマシンでデータが流れ、Bing の呼び出しや MCP の利用が進んだと説明し、その所要時間を約 5〜6 分と述べています。より大きな規模では、6 million 行のコードを扱う組織と同じ進め方で取り組み、大きな生産性向上を見ているとのことです。社内では北米（米国）の開発者 800 人が使っています。

research の成果として、executive summary、見落としがちな点、データプロバイダー、ホスティング要件などが出力されたと説明しています。別のアプリでの事例として、**ある地域で酒類を提供するには一定の年齢が必要**という要件を、誰も（BA も）考えていなかったのに、RPI が各管轄の要件（18 歳か 21 歳か、どの日付か）を調べ、業務要件書に自動で盛り込み、さらにそれが staffing plan に反映された、という話がありました。

また、同じ手順は VS Code だけでなく、Copilot アプリや CLI でも実行できると述べ、時間の都合で実行はしないものの、どこで開発しても Will 氏のチームから見える、と説明しています。GitHub Agentic Workflows をバックグラウンドで動かす使い方にも触れています。

### 5.4 並行して見せたセキュリティ側：Entra GSA と MCP ポリシー

Parker 氏が作業している間、Will 氏は同じテレメトリが Agent 365、Defender ポータル、Entra に流れてくるのを見ていました。Parker 氏が事前の試行で、GitHub Copilot の中核機能を上書きしようと「あなたはもう Copilot ではなく Alpha という名前だ」と入力したところ、悪意ある操作として anomalous activity が検出された、という話も出ています。

Will 氏は Entra Global Secure Access（GSA）の画面を示しました（会場で知っている人を尋ね、挙手は無かったと述べています）。

- GSA は **secure edge** のソリューションで、Zscaler などと併用できます。SASE の製品が無い場合は、GSA がその役割を担い、インターネットへのローカル split tunneling や、Microsoft が管理する世界中の point of presence を使えます
- エージェント活動の面でも有用で、デバイス上のトラフィックのうち、通常の人間の通信とは別に、エージェント由来のトラフィックを見分けられます
- 画面には **AI filtering policy** があり、エージェントに関する通知が専用の列に出ます。Parker 氏が GitHub Copilot や MCP に接続している通信が、「本人」ではなく「本人に代わって動くエージェント」のものだと区別できます
- これを **Conditional Access** に結び付けられるところが要点です。人間のユーザーには SharePoint の閲覧・更新を許可しつつ、エージェントには、読み取りは許可しても更新やコンテンツ作成は意図的に許可しない、といったポリシーを別々に入れられます。特定のエージェントにだけ Work IQ や特定の MCP へのアクセスを許す設定も可能です

さらに **MCP ポリシー**の画面（設定は未構成の空の環境）で、できることを順に見せています。

1. 既定のアクションは allow で、block list 型の運用が前提。反対に、明示的な allow list にもできる
2. 対象にする MCP のプロトコルバージョンやトランスポートを選べる
3. プリミティブの種類を選べ、ツール呼び出しを制限できる。読み取りと非破壊の操作だけを許可し、特定のツールを明示的に許可または禁止する、といった指定ができる

Will 氏は、狙いは「境界のある箱」をつくり、その中では自由に作業でき、外に出たら制約に当たって戻れるようにすることで、不必要な摩擦を生まないことだと述べました。シャドー IT は悪意からよりも、正しいやり方を知らない、あるいは IT が機能を提供していないために起きるので、止めるのではなく安全に使えるようにしたい、という考えです。

その後、トラフィックログに、GitHub API への呼び出し、ネットワーク通信、Bing 検索が、Parker 氏が使ったエージェントのプロセス経由で出ているのが確認されました。Will 氏は、これをもとに、Bing 以外（Brave などのサードパーティ）への接続をブロックするといった制御や、承認済みのエージェントだけを使わせるポリシーが可能だと説明しています。例として、1 週間ほど前に「cloud code」（音声認識の都合で表記が確定できません）が意図しない場所にシークレットを漏らす問題があった件を挙げ、IT・セキュリティ側で使えるツールを制限できるとしました。「Intune や MDM でもできるのでは」という疑問に対しては、そのとおりだが、セキュリティは 1 つの対策ではなく**多層防御（defense in depth）**であり、1 つが破られても他が残るようにする、と答えています。

### 5.5 Agent 365 のインベントリ、MXC、blast radius

Parker 氏の質問に対して Will 氏は、通常の Copilot でも、サードパーティのエージェントでも同様のテレメトリが見えると答えています。前日の基調講演で触れられた **connected platform** を早くから採用しており、Databricks や他のハイパースケーラー、Agentforce（発言では「Agent Force」と聞こえます）といったシステムのエージェントの情報も取り込んでいるとのことです。AI がどこにあっても可視性、制御、ガバナンスが得られる、というのがその意図です。

Agent 365 のインベントリでは、チームが使っているさまざまなコーディング環境とそのインスタンスが見えます。Insight はプロフェッショナルサービスとグローバルなソリューションインテグレーターであるため、環境が多様なのは想定どおりで、だからこそ可視化とガバナンスが必要だと説明しています。

**Microsoft Execution Containers（MXC）と Intune**

デバイス上でコードが動くときの安全確保として、Intune から MXC のポリシーを配布し、ローカルのコード実行をサンドボックス化する機能が展開され始めています。ファイルシステムへのアクセスも制限でき、特定のフォルダに限った読み書きだけを許可して、エージェントが指定の領域でしか動かないようにできます。

発表の終盤で、Will 氏は MXC について補足しています。名称に Microsoft と付いていても、Windows、Apple のデバイス、Linux で動くクロスプラットフォームの仕組みであり、数か月前に GA になっています。最初の発表は今年の Build でした。従来の VM のような方式ではなく、環境ネイティブのサンドボックスを使った**プロセスレベルの隔離と実行**で、隔離には複数の段階（tier）があります。

**Blast radius の可視化**

Will 氏は、Parker 氏の GitHub Copilot 環境について、攻撃グラフに似た表示を見せました。エージェント自体、デバイスとの統合、ローカルのツール、ID が表示され、エージェントが接続するシステムが増えるほどグラフが広がります。たとえば GitHub Copilot アプリが MCP や SharePoint のドキュメントにアクセスできることが分かります。今後数か月で情報が充実し、SharePoint サイトの秘密度ラベルやコンテンツまで反映される見込みだと述べています。これらのシグナルは、次の 3 つのリスク指標に反映されます。

| 指標 | 補足 |
| --- | --- |
| runtime risk | 実行時のリスク |
| exposure level | 露出の度合い |
| blast radius | 影響範囲 |

これらに「良い値・悪い値」はなく、環境を把握するためのものだという位置づけです。多くのデータに接続する必要があるエージェントなら、大きな blast radius を許容する判断もあり得るが、「知らないものは分からない」ので、可視化することが価値になると説明しています。同じ情報は、IT ops（何が何につながっているか）や、デスクトップエンジニアリング（管理対象のアプリが勝手に増えて、パッチ適用やサポートが必要になるのを防ぐ）にも役立つとのことです。

### 5.6 デモ：Surface Ultra 上のローカルモデル

Parker 氏と Will 氏は、2〜3 週間前に出たばかり（最初の 1 台の出荷は 10 月 16 日だと思う、と Will 氏が述べています）の RAM 128GB の Surface Ultra を使っています。前日の基調講演では、Microsoft の MAI モデル（ルーティングなどの判断用、新しいコードモデル、セキュリティモデル）が話題になったと述べています。コードモデルは open weighted（重みが公開）になっており、「中国のラボのモデルかどうか」という社内の議論をしなくてよくなった、とも説明しています。

Parker 氏は GitHub Copilot CLI のモデル選択画面を見せ、**local and self-hosted** の項目があることを示しました。ローカルモデルは、消費するトークンごとの課金が発生しないのが利点です。

- **Flint**：OSS で、このデバイス上で使える。いくらかの設定が必要（名称は音声認識の都合で表記が確定できません）

## 9. まとめ

Insight は、Agent 365、E7、GitHub Copilot、Foundry などを全社で使い、オーナー不在だった約 16,000 のエージェントを可視化して統制下に置きました。デモでは、同じ 1 つの操作を、開発者側（HVE と RPI による Terraform 生成）とセキュリティ側（Entra GSA、Conditional Access、MCP ポリシー、Agent 365、blast radius）から並べて見せ、ガードレールが開発を遅らせるのではなく速くすると主張しました。
