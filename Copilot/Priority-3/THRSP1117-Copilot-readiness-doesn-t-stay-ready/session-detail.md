# THRSP1117 Copilot readiness doesn't stay ready

## 1. はじめに

このセッションは、Copilot 導入のための準備（Copilot readiness）を一度完了させても、その状態は時間とともに崩れていく、という問題を扱う約 15 分の登壇です。登壇者は、Microsoft 365 テナントの構成と ID が日々どれだけ変わるかを、自社プラットフォーム上の平均的なテナントの数値で示し、サインオフしたときのテナントは「もう存在しない」と述べます。そのうえで、状態を保つための 3 つの原則（known good state を持つ、すべての変更を観測する、すべてのオブジェクトを元に戻せる）を紹介します。

登壇者は Coreview で製品チームとエンジニアリングチームを率いていると自己紹介しており、セッションの後半は同社の configuration resilience と identity resilience、および新たに発表された無料の **Tenant Observer** の紹介にあてられています。つまり、ベンダーによる製品紹介を含む内容です。結論は、「**Readiness は走り続ける状態であり、終わりのあるプロジェクトではない**」という一文にまとめられています。

## 4. 発表者が伝えたいメッセージ

登壇者の主張は、readiness は「ある時点の状況のスナップショット」にすぎず、日々の普通の業務で簡単に崩れる、というものです。変化は攻撃や悪意によるものとは限らず、通常の運用で起きます。そのため、一度整えたことを前提に Copilot を展開し続けるのではなく、サインオフした状態を基準として持ち、変化を見つけ、元に戻せる仕組みが必要だと述べています。

さらに、エージェントの時代には、管理者が承認する変更が増え、そのうちの多くは自分で行った変更ではなくなる、という課題が加わります。そのため、「元に戻せるか」が、変更を自信を持って承認できるか、それとも止めてしまい Copilot の活用が進まなくなるかを分ける、というのが登壇者の考えです。

## 5. 発表内容の詳細

### 5.1 導入：Copilot readiness とサインオフ

登壇者はまず、基調講演で、Copilot があらゆる業務に組み込まれていくことが示されたと述べ、ほとんどの人が Copilot readiness プログラムを経験した、または経験することになると説明します。これは負荷の高い、ストレスの多い作業です。

仮の例として、約 6 か月前の March に readiness を済ませ、状態が green になったとします。そこで行ったこととして、次が挙げられました。

- 過剰共有（oversharing）の是正
- 壊れていた権限継承の修復
- コンテンツ向けの DLP ポリシーと秘密度ラベルの整備
- 本来あってはならないゲストアクセスの削除
- 管理者ロールの修正

これでサインオフし、Copilot の導入に自信を持った、という想定です。

### 5.2 なぜ readiness が重要か

登壇者は、上司に求められるからだけではなく、Microsoft がドキュメントではっきり述べているからだと説明します。「Copilot とエージェントは、Microsoft Graph からデータを取得し、既存の権限、共有設定、ポリシーを尊重する」という内容です。実際には、Copilot は主に次の 2 点を見ます。

- **構成**：共有設定、権限、ポリシー
- **ID**：ユーザーの ID が許す範囲で動く。誰が、どのアクセスを、どのグループ経由で持っているか

### 5.3 「サインオフしたテナントはもう存在しない」：変化の規模

登壇者は、readiness はある時点のスナップショットだと強調し、「サインオフしたテナントは、まだ今のテナントか。答えは no」と述べます。根拠として、Coreview が観測している実データを示しました。Coreview は 200 万ユーザーを大きく超えるテナントも含め、世界最大級のテナントを見ているとのことで、ここでは平均的な 30,000 ユーザーのテナントを例にしています。

| 項目 | 平均的な 30,000 ユーザーのテナント |
| --- | --- |
| 構成のポイント数 | 約 90,000 |
| ID の数 | 約 50,000（人間の ID、非人間の ID、グループ、管理者プロファイルなどを含む） |
| 構成の変更 | 1 日あたり 100 件超 |
| ID の変更 | 1 日あたり 300 件超 |

登壇者は、サインオフ後の 6 か月間（April から October。控えめに数えて March と November は含めない）で、約 70,000 件の変更が起き、その内訳は構成の変更が約 80,000 件、ID の変更が約 54,000 件だと述べました。

> 補足：トランスクリプト上、「約 70,000 件」と「構成 約 80,000 件、ID 約 54,000 件」の数値は整合して聞こえません。ここでは、話されたとおりに記載し、どれが誤りかは確定していません。登壇者の結論は、サインオフしたテナントはもう存在しない、という点です。

### 5.4 変化の理由：通常の運用で起きる

登壇者は、変化は必ずしも攻撃や悪意と結びつかず、会社の普通の運用で起きると述べます。構成面では次のような例です。

- パートナーとのプロジェクトのために外部共有を追加した
- ファイルを移動して、継承ルールが壊れた
- 作業を早く進めるために、DLP ポリシーに例外を作った
- 世界中を出張する役員のために、Conditional Access ポリシーを変更した

ID 面は、さらに深刻だと説明されました。例として「Maria」という社員が、January に財務チームに加わり、その後チームを移るが、財務の仕事が残っているため完全にはオフボードされない。次にインシデントが起き、復旧のために管理者権限が付与される。さらに新しいプロジェクトに参加し、アクセスが積み上がり、本来持つべきでない権限を大量に持つことになる、という流れです。これは人間の ID だけの話ではなく、AI の動きによって非人間の ID も速く積み上がると述べています。

冒頭のチェックリストに戻ると、結果は次のとおりです。

| 当初の対応 | 現在の状態 |
| --- | --- |
| 過剰共有を是正 | 再び過剰共有が発生 |
| 継承ルールを修復 | 継承ルールが再び壊れた |
| DLP ポリシーを導入 | audit only モードになり、観測するだけでブロックしていない |
| ゲストアクセスを見直し | ゲストが追加された |
| 管理者ロールを見直し | 管理者が追加された |

登壇者は、これらは平均的な顧客のプラットフォーム上で観測した実データだと強調しています。

### 5.5 ツールの分断と 3 つの黄金律

登壇者は、どの会社にも、これらの問題それぞれに対応するツールがあると述べます。具体的には、誰が何を持つかを教えるツール、ポスチャを確認するツール、変更を通知するツール、データをバックアップするツール、ディレクトリを復旧するツールです。しかし、**テナントの状態全体を誰が管理し、そこへ戻す方法があるのか**が問題で、制御を 1 か所に集める（single pane of control）ことが重要だと述べます。

構成のドリフトと ID のドリフトは、別の問題に見えて、実は同じ問題だというのが登壇者の見方です。ドリフトによる混乱を避ける最善の規律として、次の 3 つの黄金律を挙げています。

1. **known good state を持つ**：サインオフしたベースライン（アクセス、設定、構成）を明確に把握している。
2. **すべての変更を観測できる**：何かが起きたと通知されるだけでなく、誰が、何を、いつ変えたかを特定できる。
3. **すべてのオブジェクトを元に戻せる**：known good state 全体に戻すのは簡単だが、ドリフトが起きたときに 1 つ 1 つの設定の粒度で戻せることが重要で、これは一般的ではない。

登壇者は、Coreview の configuration resilience と identity resilience で、known good state を保持し、ドリフトを検出して対処し、ロールバックできるとしています。また、ポスチャ管理ツールとバックアップツールが別々だと、ドリフト後に「ある状態」へ復元できても、それが readiness としてサインオフした状態かは分からない、と指摘しました。さらに、多くのバックアップ・復元ツールはデータの復元はできても、そのデータを動かしている**構成**までは対象にしていない、とも述べています（そのうえで、「あなたのツールは構成をバックアップ・復元できているか」と問いかけています）。

### 5.6 実例 1：構成ドリフト（MFA ポリシーと break glass グループ）

登壇者は、実際のケースとして次の流れを紹介します（"This is a real case"）。

1. Monday 9 時に、MFA ポリシーをサインオフして設定した。
2. 午前 2 時に、誰かが PowerShell スクリプトで break glass グループを削除した。これは目的があって行った変更かもしれないが、午前 2 時では判断が良くないかもしれない、と述べています。
3. ツールが変更をほぼリアルタイムで検出し、誰が、いつ、どのように変更したかをフラグ付けした。
4. 数分後に、ツールが自動的に known good state にロールバックした。
5. 10 分で、混乱なく状態が復元された。

### 5.7 実例 2：ID ドリフト（リーダーシップサイトへのプロジェクトチーム追加）

通常の稼働日に、誰かがプロジェクトチームをリーダーシップサイトに追加したとします。その時点から Copilot はそのスコープにアクセスでき、リーダーシップサイトのデータを読んで回答できるようになります。登壇者は、これは既知のリスクだと述べます。ツールは変更をほぼリアルタイムで検出し、リスクと判定された場合は、混乱なくすぐに元に戻せるとしています。

登壇者は、Office に Copilot が組み込まれた今は大きなリスクだと強調し、構成面の帰属の誤りが原因で、Copilot が本来あってはならないデータを検出し、提供したインシデントを観測したと述べています。

### 5.8 Coreview のアプローチ：Harden、Detect、Restore

Coreview には configuration resilience と identity resilience の 2 つのモジュールがあり、どちらも 3 つの黄金律に対応する **Harden、Detect、Restore** の流れで動きます。

| 項目 | Configuration resilience | Identity resilience |
| --- | --- | --- |
| Harden | 状態を強化し、構成をベストプラクティスに沿わせる。CIS baseline との整合を提供し、必要に応じて調整できる | 誰が、どのグループ経由で、いつからアクセスを持っているかを把握する |
| Detect | 数分以内にドリフトを検出する | あらゆる変更を検出する |
| Restore | 1 つずつの構成単位で、known good state に戻す | 過剰共有や混乱を起こさずに、すぐ復元する |

> 補足：Identity resilience の Harden に相当する説明は、トランスクリプトでは「who holds which access through which group and since when の状態を設定し、把握できる」という趣旨でした。

### 5.9 エージェントの時代の課題

登壇者は、エージェントの動きによってこの問題はさらに緊急になっていると述べます。Microsoft が言うように、エージェントがテナントを独断で変更することはなく、必ず人が承認します。これ自体は良いことですが、管理者や運用担当者は、**自分で行っていない変更を、今までよりはるかに多く承認する**ことになります。それはエージェントによる変更なのか、という疑問が生じます。

最終的に重要なのは「元に戻せるか」で、これが、変更を承認するか、すべてを止めてしまって Copilot の活用が進まなくなるかの分かれ目になる、と登壇者は述べています。元に戻せることで、自信を持って承認し、Copilot の価値を最大限に引き出せる、という主張です。

### 5.10 Tenant Observer の発表

「月曜日からできること」として、Coreview は **Tenant Observer** をローンチしたと発表しました。内容は次のとおりです。

- ライブの構成に対して、100 を超えるセキュリティチェックを提供する
- 重大度別のスコアを出し、どこから始めるかが分かる
- 自分たち自身の出発点に対するドリフトを検出する
- 構成の履歴を提供する
- 読み取り専用（read-only）でセルフサービス、**無料**

状態の把握と変更の監視は無料でできます。修正やロールバックまで行いたい場合は、ブース 5247 で製品のフルデモを案内する、とのことです。

## 7. 注意点・発表者の気付き

- **サインオフ後の変化は、悪意のある攻撃ばかりではなく、通常の運用で起きます。** パートナーとの外部共有、ファイル移動による継承の破損、DLP の例外、役員の出張のための Conditional Access の変更などが例に挙げられました。
- DLP が audit only モードになると、観測するだけでブロックしなくなります。readiness 時に導入した DLP が、いつの間にかその状態になっている例が示されました。
- ポスチャ管理ツールとバックアップツールを別々に使うと、復元した状態が、readiness としてサインオフした状態と一致するか分からないという点。
- 多くのバックアップ・復元ツールは、データは対象にしても、データを動かす構成までは対象にしていないという指摘。
- 構成面の誤った設定が原因で、Copilot が本来あってはならないデータを検出・提供したインシデントを観測している。
- エージェントが変更を行う場合も、人が承認する形です。ただし承認する変更が増え、その多くは自分で行ったものではなくなります。
- 数値（5.3）は、Coreview が自社プラットフォーム上の平均的な顧客から観測したものです。

## 8. 利用者にとっての利点

登壇者が語った利点は、Coreview の製品に関するものです。

- 構成ドリフトの検出が数分、ロールバックまで含めて 10 分で、混乱なく復元できた実例（MFA ポリシーと break glass グループ）。
- ID の変更をほぼリアルタイムで検出し、リスクと判定されたものは即座に戻せる。
- 変更を戻せるという確信により、エージェントが関わる変更を自信を持って承認でき、Copilot の活用が止まらない。
- Tenant Observer では、100 を超えるセキュリティチェック、重大度別スコア、ドリフト検出、構成履歴を無料・読み取り専用で利用できる。

具体的な顧客名の事例は、このセッションでは紹介されていません。

## 9. まとめ

Copilot readiness は、サインオフした時点のスナップショットにすぎません。平均的な 30,000 ユーザーのテナントでは、構成が 1 日 100 件超、ID が 1 日 300 件超変わり、過剰共有、継承の破損、DLP の audit only 化、ゲストや管理者の増加といった形で、readiness は崩れていきます。

対策として、known good state を持ち、すべての変更を観測し、すべてのオブジェクトを元に戻せるようにする、という 3 つの黄金律が示されました。Coreview の configuration resilience と identity resilience はこれを Harden、Detect、Restore として実装するもので、無料の Tenant Observer から始められます。登壇者が最後に残した言葉は、「Readiness is a running condition, not a project with an end date.」です。
