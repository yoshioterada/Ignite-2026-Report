# THR981 Essential Insights for Governing Copilot Agents

## 1. はじめに

このセッションは、Copilot のエージェントを組織でどうガバナンスするかを、約 25 分で整理した発表です。登壇者は、チャットの回答から、Agent Builder、Copilot Studio、プロコードの自律エージェントまで、エージェントには段階（昇格のはしご）があるわけではなく、**エージェントごとに必要なガバナンスの強さが違う**という点を出発点にしています。

発表の中心は、Microsoft 由来として紹介されたゾーン分け（Zone 1、2.1、2.2、3）です。リスクが低い個人用の回答エージェントから、ビジネスプロセスや戦略的な影響を持つ自律エージェントまで、どのゾーンに入るかで、必要な統制が変わります。そのうえで、受付（intake）プロセス、リスク分類、ライフサイクル管理、オーナーとインベントリ、環境と DLP、セキュリティとコンプライアンス、本番稼働の準備という実務の論点が、順に説明されます。

登壇者が繰り返し述べるのは、「新しいことは何もない。新しい理由ができただけだ」という点です。このセッションでは、画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。

## 4. 発表者が伝えたいメッセージ

最も強いメッセージは、「**すべてのエージェントにガバナンスは必要だが、すべてのエージェントに同じガバナンスは要らない**」という点です。登壇者は、エージェントを「チャット → Agent Builder → Copilot Studio → プロコード」という卒業の順序のように捉えないよう、何度も注意しています。エージェントは何をするか、誰が管理するか、どんな情報を返すかによって、いずれかのゾーンに位置づけられ、時間をかけてゾーン間を移ることはあっても、全員が最終的に上へ上がるわけではない、という説明です。

もう 1 つは、ガバナンスは新しい概念ではないという点です。ソフトウェア開発ライフサイクル、環境戦略、データ衛生、SharePoint や Power Platform で過去にやってきたことと同じことを、エージェントに対して「新しい理由」でやり直す機会だと位置づけています。発表の最後でも、「エージェントが多すぎるのが問題なのではない。すべてを同じようにガバナンスする必要はない」と述べています。

## 5. 発表内容の詳細

### 5.1 エージェントは「昇格」ではない

冒頭で登壇者は、チャット、Agent Builder、Copilot Studio、プロコードを「卒業の順序」として扱わないよう強調します。各エージェントはそれぞれガバナンスに値し、その内容は、エージェントが何をするか、誰が管理するか、どんな情報を返すかによって変わる、というのが前提です。

### 5.2 回答、意思決定、成果で変わるガバナンス

**回答（質問に答えるだけ）**

Copilot Chat で毎回同じ情報源を参照するなら、そのためのエージェントを作れます。自分専用で、質問に答えるだけのものは、必ずしも高リスクではありません。ただし、情報源に機密データが含まれる場合は、リスクが上がるのに合わせてガバナンスを付ける必要があります。この種のものは以前は「チャットボット」と呼ばれていたもので、「質問があり、このデータソースに基づく正しい答えがある」という低リスクの用途だと説明されています。

**意思決定（推奨を返す）**

次の段階は、エージェントに判断材料を集めさせ、推奨を返してもらう使い方です。ユーザーが明示しないコンテキストも集めさせます。登壇者は、これを Microsoft IQ（データとコンテキストを理解する仕組み）と結びつけています。例として、ビルトインやマーケットプレース由来の researcher や analyst のエージェントが挙げられました。これらはレポートの作成や SWOT 分析、長所と短所の整理、推奨や追加の質問の提示を行います。

多くのコンテキストが必要になるぶん、ガバナンスも必要になります。ここで問われるのはデータ資産の整理（クリーンさ）です。機密ラベルが適用されていること、エージェントが使う情報が「唯一の正しい情報源」であることが挙げられています。

> 注意：登壇者は「ガバナンスはずっと前からある問題で、新しくない」と述べたうえで、Agent Builder がデータ階層で 2 階層より深くは辿れない、と説明しています。かつて SharePoint Online に移るときに構造をフラットにする話があったのに、今度は「バラバラの場所にある情報を、まとまりのある 1 か所に集める」ことを考えなければならなくなります。これは、情報をその場に残してきたレコード管理やコンプライアンスの考え方とは逆方向で、コンテキストを同じ領域内に置く必要がある、という指摘です。登壇者は、この IQ の仕組みは非構造化データの扱いが、一般に思われているよりずっと優れているとも述べつつ、「情報源が唯一の正しいものであること」を確かめたい、としています。

**成果（書き込みを伴う自律動作）**

最後が、エージェントが自律的に動き、システムに書き戻す段階です。意思決定は情報を読んで推奨を受け取る段階で、成果は書き戻しを含みます。ERP や CRM と連携して、データを読むだけなら、ガバナンスの焦点はデータと ID（アイデンティティ）にあります（登壇者は「低い」とは言いたくないと断っています）。一方、書き込みまで行う場合は、読むだけではなく「書く」ことの統制が必要になります。エージェントにさせたいことが複雑になるほど、統制の必要性は上がります。

### 5.3 ゾーンの全体像（Microsoft 由来のスライド）

登壇者は、このスライドを「写真に撮るべきもの」と位置づけ、Microsoft から直接得たものだと述べています。ここでも、段階を上がっていくものではなく、「どのエージェントも、いずれかのゾーンに着地する」ものだと繰り返しています。ゾーン間でライフサイクルを移ることはあり得ます。

| ゾーン | 位置づけ | 説明 |
| --- | --- | --- |
| Zone 1 | Quick assist（quick access）エージェント。個人用 | 情報を返す、情報を読む。ユーザー自身がコンテキストとソースを与える。ノーコード。技術的には Agent Builder、または、スケジュールされたプロンプト。自分用で、数人に共有する程度 |
| Zone 2.1 | チーム向け。ローコード | 複数の人が推奨を頼りにするので、データ衛生が重要になる。シチズンデベロッパーが対象。Agent Builder も使えるが、Copilot Studio のライセンスを一部の人（チャンピオン）に与える段階 |
| Zone 2.2 | ビジネスプロセスに触れる | IT の関与が必要。レガシーデータにつなぐ場合がある。リスクが上がるのでガバナンスを強める |
| Zone 3（strategic impact） | 自律エージェント | プロ開発者による開発が必要。2 日や 2 週間ではなく数か月かかり、多くの変更管理を伴う |

> 補足：登壇者は Zone 1 について、基調講演で話があったとおり「ワークスペース」が出てきたと述べ、製品の進化にともない、個人用のエージェントを作る代わりに、チーム全体で作業するワークスペースを作る人が増えている（Zone 2.1 に近い）と説明しています。「いつエージェントを作るべきか」は次の論点（5.4）です。

ゾーンは低リスクから高リスクへと並んでおり、ガバナンスをプロセスに組み込む必要があるのは、リスクが上がる地点だと説明されています。ここから先の話は主に Zone 2.2 から Zone 3 のエンタープライズ規模が対象で、Agent Builder だけの話は発表後に個別に受ける、と述べられています。

### 5.4 受付プロセス（intake）と、エージェントが本当に必要かの見極め

ガバナンスの基本は、**すべてのエージェントにオーナーがいること**です。オーナーを置くなら、受付（intake）プロセスが必要になるだろう、というのが登壇者の考えです。受付プロセスで決めるのは、シチズンデベロッパーで対応できる（Zone 2.1）のか、ローコードまたはプロコードの解決策が必要なのかです。ユーザーが開発に助けを必要とするまでは、受付プロセスは要りません。例えば新しいコネクタが必要になったときに初めて必要になります。受付では、エージェントの名前、オーナー、やりたいことの説明を尋ね、それをインベントリに載せます。登壇者は、このインベントリは Agent 365 で持てる、と述べています。

受付プロセスを担うのは、望ましくは **Center of Excellence（CoE）** です。IT ではない理由は「IT はプロコードのエージェント開発で忙しいから」です。CoE は受付を分析し、シチズンデベロッパーに割り当てるのか、トレーニングにつなげるのか（「こんなことができると知っていましたか」）を判断できます。また、組織内で共通する要望も見えてきます。例えば承認ワークフローを Cowork で繰り返し作っているなら、それは必要以上のことだ、という例が挙げられました（発言の意図は音声からはやや不明瞭です）。

受付で見極める観点は次のとおりです。

- そもそもそのエージェントは存在すべきか。ワークスペースで足りないか、Cowork で足りないか。「以前はエージェントだったものの多くが Cowork になる」可能性があります。
- エージェントは何者で、何を許されるか。さらに重要なのは「何ができないか」。
- リスク分類を付ける。機密データか、他システムへのシングルサインオンが必要か。
- 本番稼働の準備ができたと言える条件は何か（5.9 で説明）。

登壇者は、組織に行くと「エージェントにやらせたいこと」の長いリストがあるが、その多くは Power Platform、Agent Builder、SharePoint ワークフローで既にできたことだ、と指摘します。「いまは名前（エージェント）ができただけ」であり、かつて SharePoint を「ハンマー」と呼び、ハンマーを持つとすべてが釘に見える、と言われたのと同じことが、エージェントでも起きているという例えです。

登壇者は、エージェントを作る前に次の問いを通すよう勧めています。

1. それは存在すべきか。
2. 誰がオーナーか。オーナーが退職したとき、ライフサイクルのどこでオーナー権を移すか。
3. エンタープライズのエージェントのライフサイクルをどう監視するか。

### 5.5 ライフサイクル管理と分析

ソフトウェア開発ライフサイクルは新しいものではありません。登壇者は、エージェントを「アプリや製品」のように扱うよう提案します。そのため、本番稼働の準備ができる条件（done とは何か）だけでなく、**いつエージェントを再評価して、標準やガイドラインとの整合を確認するか**も決めておく必要があります。

分析については、「利用状況の分析でエージェントを評価するのをやめてほしい」と述べています。必要なのは、**ビジネス成果を測る現実的な方法**です。個人の生産性（1 日 15 分の節約など）は、もう通用する答えではないとのことです。受付の時点で、何を分析するか、どの指標を与えるかを決めておきます。また、もっと大きく考えるべきだとして、オンボーディングプロセスのエージェントが離職率（attrition）を測れるか、エージェントを提供することで離職率を下げられるか、という例を挙げています。単位時間あたりの処理量や節約時間だけでなく、ビジネス目標を見たうえで「そのためのエージェントが必要だ」となる、という考え方です。

### 5.6 オーナーとインベントリ

登壇者は、「オーナーがいなければエージェントはない。以上」と強く述べています（本人も、この話を繰り返していると自覚しています）。オーナーは、データソースに責任を持ち、機密情報にアクセスされているかどうかに責任を持ち、エージェントの読み書きの能力にも責任を持ちます。

インベントリを持つことは **Agent 365** で簡単にできる、と登壇者は述べています。ただし問題は、エージェントのガバナンスを担う人たちが、おそらく Agent 365 にアクセスできないことです。IT に管理を任せるとボトルネックになるので、シチズンデベロッパーや Center of Excellence が Agent 365 にアクセスできるようにする必要がある、と主張します。

### 5.7 環境戦略と DLP

登壇者は、環境管理と DLP（data loss prevention、データ損失防止）のポリシーは「いくらでも語れるが、とても退屈（dry）な話題だ」と前置きしたうえで、**すべての人がデフォルト環境でエージェントを作っているなら、やめてほしい**と求めています。個人の生産性エージェント用の新しい環境を作り、環境が 1 つしかないなら、その環境を個人生産性エージェント用にする、という助言です。Power Platform のときにも環境戦略が必要だったのに実行しなかった、同じことが繰り返されている、とも述べています。

環境を決める際の観点は次のとおりです。

- ID とアクセス管理の「壁」を理解し、その範囲内に環境を置く。権限が同じなら新しい環境は要らないが、その環境が安全な場所であることを確認する。
- 開発、テスト、本番の環境を分ける。開発環境でうまくいかなければリセットでき、テスト環境は本番に似せてユーザー受け入れテストを行い、その後に本番に進む。
- DLP は、環境で使えるコネクタを制御する。例えば個人生産性の環境には M365 のデータリソースだけを許し、プロコード開発者の環境には可能なあらゆるコネクタを許す。DLP のコネクタは環境レベルで設定される。

### 5.8 セキュリティとコンプライアンス、チーム体制

セキュリティとコンプライアンスでは、**Purview の担当者を巻き込む**ことが挙げられます。ガバナンスには、すでに複数の管理者の協力が必要です。登壇者は、誰をチームに入れるべきか確認し、エージェント専用のロールを作ることを勧めています。CoE の中の 2〜3 人が、Power Platform、Entra（音声では "intra" と聞こえます）、Power Platform 内の環境、SharePoint の管理者を兼ねる、という構成です。

### 5.9 本番稼働の準備

最後のスライドは、エージェントが成長していく際の準備確認です。多くの場合、パイロットとして限られた人が使い、そのあとスケールさせると決めます。スケールの準備ができているかを示す項目として、次が挙げられました。

| 項目 | 登壇者の説明 |
| --- | --- |
| 指示（instructions）の変更 | 変更は軽く見られがちだが、エンタープライズのエージェントなら、指示の更新でも開発環境、テスト環境に戻る。指示は「定款（articles of incorporation）」のようなもので、頻繁には変えないが、正当な理由で変えるときは再評価する |
| ナレッジソースの変更 | 新しい知識ソースを追加したら、すべてのナレッジソースでセキュリティを確認する。テストなしで追加してはいけない。テスターは信頼できる人にする（テスト環境で、見るべきでないデータに当たる可能性があるため） |
| 連携（integrations） | すでに必要と分かっているはずの項目 |
| オーケストレーターエージェント | 複数のエージェントを呼び出してエンタープライズのエージェントを構成する。ここから「魔法」が見えてくる、と述べている |
| リリース承認 | 指名されたオーナーが準備完了を承認する。本番に出す前に、オーナーが「これが意図したものだ」と了承する |

## 7. 注意点・発表者の気付き

- ゾーンは「昇格のはしご」ではありません。エージェントをチャットからプロコードへと段階的に上げていく前提で考えない、と複数回注意しています。
- Agent Builder が辿れるデータ階層は 2 階層までで、情報を 1 か所にまとめる必要が出てくるため、SharePoint でフラット化してきた従来の流れや、レコード管理・コンプライアンスの考え方と逆行する、と述べています。
- ガバナンスのための Agent 365 に、ガバナンス担当者（CoE やシチズンデベロッパー）が実際にアクセスできていない可能性がある、と指摘しています。
- デフォルト環境でエージェントを作り続けないこと。個人生産性エージェント用の環境を別に作ることを求めています。
- 「何でもエージェント」にしない。Power Platform、Agent Builder、SharePoint ワークフローで既にできたことも多く、まず「存在すべきか」を問う、という立場です。
- 指示の変更も、エンタープライズのエージェントでは開発・テスト環境で再確認します。ナレッジソースの追加時は、テスターは信頼できる人にします。
- 利用状況の分析ではなく、ビジネス成果で測る。登壇者は「個人の生産性（15 分の節約）はもう通用しない」と述べています。
- チャンピオンネットワークを作ること。登壇者は「難しいことは承知している」と述べ、発表後に話そうと呼びかけています。

## 8. 利用者にとっての利点

このセッションは製品の売り込みではなく、ガバナンスの考え方の提案であり、成果の数字や顧客事例は語られていません。語られた利点・効果は、次のように整理できます。

- ゾーンで考えることで、個人用の低リスクなエージェントには軽く、自律エージェントには強いガバナンスと、統制を使い分けられる。
- 受付プロセスと CoE により、IT がボトルネックにならずに、エージェントの要望をシチズンデベロッパー、トレーニング、プロコードへ振り分けられる。
- Agent 365 を使えば、エージェントのインベントリを簡単に持てると述べられている。
- 環境ごとに DLP でコネクタを制御し、用途に応じて接続範囲を変えられる（例：個人生産性の環境は M365 のデータリソースのみ）。
- 指示やナレッジソースを変更したときの再評価と、オーナーによるリリース承認を、本番化の条件にするという進め方が示された。

## 9. まとめ

エージェントのガバナンスは、段階を上がっていくものではなく、エージェントの用途とリスクで決まるゾーン（Zone 1、2.1、2.2、3）に応じて変わります。リスクが上がる Zone 2.2 と Zone 3 では、CoE による受付、リスク分類、オーナーの指名、Agent 365 でのインベントリ、環境と DLP、Purview を含むチームの連携、本番前の再評価とオーナーの承認が必要です。評価は利用状況ではなく、ビジネス成果で行います。登壇者の結論は、「新しいことは何もなく、新しい理由があるだけ。すべてのエージェントに同じガバナンスは要らない」というものです。
