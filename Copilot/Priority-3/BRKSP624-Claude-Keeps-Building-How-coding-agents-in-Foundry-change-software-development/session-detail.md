# BRKSP624 Claude Keeps Building: How coding agents in Foundry change software development

## 1. はじめに

このセッションは、Anthropic で Claude Code に取り組むエンジニアが、**Microsoft Foundry 上で Claude Code を使い、チーム全体でコーディングエージェントを運用するときの設計の考え方**を話したものです。コードを書く速度が上がった今、ボトルネックは「何を作るかを決める」「戻ってきた成果物をレビューする」「壊さずにリリースする」側に移っています。登壇者は、この状況で「誰が決めたのか。Claude か、チームが定めたルールか、人か」という同じ問いを繰り返しながら話を進めます。

構成は、1 人のエンジニアが 1 つのチケットを処理する **インナーループ**、プルリクエスト以降のチームの流れである **アウターループ**、そして全社で決めるべき **組織レベルの設定** の 3 段です。サンプルのチケット「注文履歴を CSV でエクスポートする」を、Azure DevOps のチケットから Azure 上の本番まで運びます。

最大の結論は、**「Claude が決めること」と「仕組みで強制すること」を分け、取り返しのつかないことは、プロンプトではなく決定的なルール（hook、deny ルール、sandbox、managed settings）で止める**という点です。

このセッションでは、画面を使った実演（デモ）が複数ありますが、音声から分かるのは語られた内容までです。画面の細部は確認できません（6 章）。

## 3. 何に関する発表か

テーマは、コーディングエージェントを「個人の道具」から「チームと組織の開発プロセスの一部」に広げるときに、何を Claude に任せ、何をルールで固めるかです。デモは Microsoft Foundry に接続した Claude Code と Claude desktop で行い、チケットは Azure DevOps、デプロイ先は Azure App Service のステージングスロットという構成です。登壇者は、中身の大半はリポジトリ内のファイルなので、Claude のプランや API キーで使う場合も同じように使えると述べています（違いがあるときは都度指摘すると説明しています）。

発表の流れは次のとおりです。

1. 背景：PR 数の増加と、インナーループ／アウターループの区別
2. 「Claude が決める領域」と「ハーネスが強制する領域」の違い
3. インナーループ：3 つの失敗パターンと対策（コンテキスト、完了の定義、触らせないもの）
4. インナーループのデモ（チケット → PR）
5. 長時間・大規模タスク：`/goal`、並列セッション（Git worktree）、サブエージェント
6. アウターループ：ハンドオフの見直し、ループの上限、レビュー量の調整
7. チームループのデモ（GitHub Actions 上の Claude Code → CI → 承認 → デプロイ）
8. Claude Code Review（マネージド版）と auto fix
9. 組織レベルの 4 つの問い：認証、データの行き先、managed settings、可観測性
10. 「やめてよいこと」と、明日からの始め方

## 4. 発表者が伝えたいメッセージ

### 4.1 速度が上がったのでボトルネックが移った

登壇者によると、Anthropic ではマージされるプルリクエストが、5 月の 1 日あたり約 2,500 件から、9 月には約 30,000 件に増えました。コードを書くのは格段に速くなった一方、何を作るかの判断、結果のレビュー、壊さないリリースには依然として人が責任を持ちます。今は時間の大半がそこにかかっている、という認識です。

### 4.2 「誰が決めたか」を設計する

登壇者は、各ステップで「Claude が決めたのか、チームがコード化したルールが決めたのか、人が決めたのか」を問います。基本姿勢は、**どうやって実装するかは Claude に任せる**（ファイルの探索、計画、実装は自分のプロンプトより Claude の方が上手だと述べています）。それ以外については「Claude が失敗したとき、元に戻せるか」で判断します。間違ったコードは revert できますが、漏えいしたキーや本番で削除されたテーブルは戻せません。戻せないことには、プロンプトよりも強い仕組みが必要だという考えです。

### 4.3 ガイダンスと強制の違い

Claude が読むもの（CLAUDE.md、skills、プロンプト）は**ガイダンス**で、Claude は通常従いますが、大規模言語モデルは本質的に非決定的です。一方、Claude Code のハーネスが強制するもの（command hook、deny ルール、sandbox）は**モデルの外側で動き、決定的**です。この後者があるからこそ、より長い時間軸の野心的なタスクをエージェントに任せられる、というのが主張です。

簡単な確認方法として、CLAUDE.md に「never」という語を書いていないか見るよう勧めています。書いてあるなら、それは強制側（ルール）に移すべきものです。

### 4.4 ループで考える

終盤では、「ループで考える」ことが今最も価値のあるスキルだと述べます。ループ内で人が何をしているか、そこに人がいる必要があるか、人の持つ「センスと判断」をコード化して取り除けないかを検討し、本当にセンスと判断が必要な部分に人を集中させる。この考え方が、1 日 2,500 件から 30,000 件への移行を可能にした、という説明です。

## 5. 発表内容の詳細

### 5.1 背景：2 つのループとボトルネックの見つけ方

登壇者は、これまでの開発の進め方は「コードを書くのが遅い」ことを前提に設計されていたと説明します。仕様を先に書き、変更を大きな PR にまとめ、各段階にゲートを置いてきました。今も仕様は書きますが、形が変わり、Claude がプログラムで確認できる**受け入れ基準**が中心になっています。PR も、レビュアーの時間が貴重なので小さく出すようになりました。ゲートの多くは人がチェックリストを見ているだけなので、スクリプトに変換できます。

変更は 2 つのループを通ります。

| ループ | 内容 |
| --- | --- |
| インナーループ | エンジニア 1 人と Claude Code。チケットを読み、コードを変更し、実行して結果を確認し、必要なら繰り返す |
| アウターループ | コードが自分のマシンを離れた後のすべて。コードレビュー、CI、承認、会社のルール。例として、そのコードのコードオーナーが 1 週間会議続きで、2 日間開きっぱなしの PR が挙げられています |

どちらが詰まっているかは、直近 20 件のクローズ済み PR で、「開くまでにかかった時間」と「開いていた時間」を比べると分かります。後者の方が大きいなら、コードを速く書いても何も解決しません。

### 5.2 サンプルのチケットと、デモの前提

チケットは「注文履歴を CSV でエクスポートする」です。要件は 3 つあり、ボタンが必要なこと、タイムアウトせずに大きな履歴をストリーミングできること、フィーチャーフラグの裏でリリースすることです。いずれも検証しやすい要件だと強調しています。デモはモックの会社とモックのデータで、例示用です。

実行環境は Claude Code と Claude desktop を Microsoft Foundry に接続したもので、チケットは Azure DevOps にあります。登壇者は、これから見せることは desktop、ターミナル、VS Code 拡張のどこで Claude Code を動かしても当てはまると説明しています。リポジトリには Azure DevOps の MCP server が設定されていて、Claude は自分でチケットを読めます。

### 5.3 auto mode と分類器

セッションは **auto mode** で実行します。編集やコマンドごとの確認を省く代わりに、シェルコマンドや編集がリスクのあるものかを分類器が判定します。リスクがあると判断されたものは既定でユーザーにエスカレーションされ、通過したものは介入なしで実行されます。登壇者によると auto mode は今年から Claude Code の既定です。

不安に思う必要はないとして、8 月に公開した調査を紹介しています。約 1,000 人の有料テスターに、テスト環境でコマンドを承認してもらい、その中に危険なコマンドを 1 つ差し込んだところ、気づいたのは約 14% でした。一方、分類器は 89% をブロックしました。つまり人手の承認より良いが、失敗の余地は残る。だからこそ、後述の決定的なガードレールが重要になる、という流れです。

### 5.4 失敗パターン 1：リポジトリに無いものは見えない

最初の失敗は、Claude が「完了し、テストも通った」と言うのに、ステージングスロットの話が出てこないケースです。このチームは App Service のステージングスロットへ先にデプロイしてから swap しますが、その情報はリポジトリのどこにもないため、Claude には読むものがなく、飛ばしてしまいました。

登壇者は、Claude が何かを見落としたときは、まず「そもそも見えたのか」を考えます。見えなかったのなら、より賢いモデルを使っても解決しないからです。事前に見つける方法として、セッションの最後に「リポジトリやコネクタに無かったので推測したことは何か」を Claude に尋ねる方法を紹介しています。その一覧が、足りないコンテキストを教えてくれます。エンジニアが使っている情報とツールと同じものを Claude にも渡すことが、チームの一員として働かせる条件だという考えです。

そのための手段は 2 つです。

| 手段 | 使い方 |
| --- | --- |
| CLAUDE.md | セッションの開始時に毎回読まれる。短く保つ（200 行未満が適量）。スタックやフォルダ構成など、コードを読めば分かるものは書かない。ビジネス上の判断や、リポジトリの外で起きていることなど、コードに現れない背景を書く |
| skill | ステージングスロットへのデプロイは skill にする。常にコンテキストへ読み込まれるのは name と description（skill の front matter）だけで、残りの手順は必要なときに読み込まれる |

登壇者は skill を「本棚の本」にたとえます。Claude は背表紙（name と description）を見て、必要なときに本を取り出して開く、というイメージです。description は skill を起動するかどうかの判断材料なので、skill がなかなか起動されないときは、description が基準を満たしていない可能性が高いとのことです。

ただし、スライドで示された skill の手順 3 は本番への swap です。skill もガイダンスにすぎないので、この手順を skill 任せにはしません。そのコマンドに ask ルールを付けて auto mode でも止まるようにするか、skill を人だけが起動できるように設定するか、といったガードレールを置けると説明しています。

### 5.5 失敗パターン 2：終わっていないのに「終わった」と言う

2 つ目は、Claude が「レビューの準備ができた」と言うのに、手動で型チェックをかけるとエラーが 2 件ある、というケースです。登壇者は、Opus 5.5（発表での表記）は自分の成果物のチェックが非常に得意だが、「完了」の定義を誰も伝えなければ、自分の定義を使うと述べます。テストが通っても安心できないのは、そのテストも今は Claude が書いているからです。

例として、CSV エクスポートで、Claude が「エクスポートは一度に 1 年分でよい」と仮定して機能もテストも書いてしまうと、テストは緑でも、本当は 1 年以上必要だったという誤解が実装とテストの 2 か所に現れます。そのため、要件と検証方法を先にはっきりさせます。大きなチケットでは、Anthropic では最後に成立しているべきことのテストを Claude にすべて書かせ、レビュー時間をまずその検証方法に使います。それが妥当なら、長い時間軸で Claude に任せられます。

仕組みとしては **stop hook** を使います。hook は Claude Code ハーネスのライフサイクルの各イベントで動くスクリプトで、stop hook は Claude がターンを終えるたびに実行されます。スライドの例では、先ほどの型チェックスクリプトを実行します。.NET のビルドやテストスイートでも構わないと説明しています。

> 注意：スクリプトは **exit 2** で終了させる必要があります。失敗したビルドは通常 exit 1 を返しますが、Claude Code は exit 1 を「スクリプト自体が壊れている」と扱い、そのまま停止してしまいます。exit 2 だけが、停止をブロックし、かつエラーを返して Claude に読ませ、再試行させます。Claude はエラーを見て、設定できる再試行上限まで作業を続けます。

hook と検査を置いたら、わざと何かを壊して、意図どおりにブロックされるかを確かめるよう勧めています。

### 5.6 失敗パターン 3：触らせてはいけないものがある

3 つ目は、「聖域」のファイルやプロセスです。例では、大きなアカウントでエクスポートのクエリが遅く、Claude がインデックスを追加するデータベースマイグレーションを書こうとします。理由は妥当です。しかしこのチームでは、マイグレーションは別途レビューを通すルールで、それは Claude の推論の質に依存させません。そこで編集は拒否され、Claude は別の方法としてページネーションを使い、今後のためにデータベースチーム宛てのメモも残します。

登壇者は、人がプロンプトで承認する方式では助けにならなかっただろうとも指摘します。説明つきで確認が出たら、多くの人は「インデックスを足そう、マイグレーションくらい問題ない」と許可してしまうからです。ルールとしてフローに埋め込む意味はそこにあります。

大事なファイルを守る層は 3 つあり、それぞれ見えるものが違います。

| 層 | 見えるもの・特徴 |
| --- | --- |
| deny ルール | ツール呼び出しを見て、実行前にブロックする。ただしコマンドのテキストだけを見るため、`npm run migrate` はブロックできても、同じことを別の呼び出し方でされると止められない |
| pre-tool use hook | ツールが使われる前に必ず動くスクリプト。バリエーションも捉えて、Claude に代わりにすべきことを伝えられる。deny ルールより網が広い |
| sandbox | スクリプトが実行中に何をするかは、上の 2 つでは見えない。例えばテスト実行中に依存パッケージがキーを返した場合、一致するルールがない。そこで OS がシェルコマンドの届く範囲を制限する。有効化が必要で、隠すキーを指定する必要がある。Windows では WSL2 が必要 |

### 5.7 インナーループのデモ：チケットから PR まで

ここまでを組み合わせたデモです。登壇者は、チケットを取って PR を書くよう Claude に指示します。入力したのはこの最初のプロンプトだけだと説明しています。語られた流れは次のとおりです（画面の細部は音声からは確認できません）。

1. Claude が MCP 経由でワークアイテムを読み、理解した内容を伝える。
2. 注文履歴が現在どう動いているかを読み、リポジトリに既にあるカーソルと CSV ヘルパーを見つけて、その上に実装する（登壇者はどちらも指定していない）。
3. 「レビューの準備ができた」と言うが、stop hook が型エラー 2 件を検出して停止をブロックする。
4. Claude が戻って 2 件を直し、型チェックを再実行して、クリーンになる。
5. 止まる前に、大きなアカウントでも試す。遅いのでマイグレーションを追加しようとするが、ブロックされ、hook が理由を伝える（exit 2 のため）。
6. Claude は既存のインデックスを使うことで解決する。
7. デプロイ用の skill を使って push し、PR を開き、ワークアイテムをリンクする。
8. stop が通る。以前飛ばしたステージングスロットの swap も一覧に載せる。

登壇者は、これを「誰が決めたか」で整理します。**どう作るかは Claude が決め、まだ終わっていないことは stop hook が決め、マイグレーションに触れないことはルールが決め、この PR のレビューは依然として人がする**、という分担です。

これらのルールを最初から全部書く必要はありません。同じことで Claude を 2 回直したら、次の 3 つのどれかを考えます。

- 見えていなかったなら、書き残す
- 早く止まりすぎたなら、検証チェックを足す
- 絶対に起きてはいけないなら、ルールとしてコード化する

チームで共有するには、skills、hooks、MCP servers を **plugin** にまとめ、チームメンバーがワンクリックのクイックインストールで受け取れるようにします。deny ルールは通常 settings.json にあり、これは個人のものです。会社が MDM などで配布する **managed settings** を使えば、全員に同じルールを適用できます。

### 5.8 長時間セッションと並列化

チケットが大きくなり、数時間かかる作業になると、2 つのことが変わります。

1. **チャットで伝えたことが失われる。** 例えば「確認するまで push しないで」と言っても、そのメッセージは後で要約されて消えることがある。これは ask ルールとしてコード化する。
2. **続ける理由が必要になる。** そのためのコマンドが **`/goal`** で、終了状態を渡す。先のテスト先行の例なら「エクスポートのテストがすべて通る」といった終了状態で、Claude はそこに向けて作業を続ける。

作業が大きく、API、UI、ドキュメントのように触るファイルが分かれるなら、分割できます。ただし先に API の契約を合意しておく必要があります。分割したときは、複数のセッションを並列に走らせ、それぞれを専用の **Git worktree**（同じリポジトリの、ブランチ付きの別コピー）で動かします。エージェント同士が足を踏み合わずに並列作業できます。

各セッションの中では、Claude がサブエージェントに作業を渡せます。登壇者が常に足すというのは、**読み取りツールだけを持つレビュアー**です。コードを書いていないので、diff を白紙の状態で読めます。デモの例では、ページサイズに上限がないことと、abort signal が無いことを指摘しました。

並列デモの語られた流れは次のとおりです。

1. 3 つのセッションが並走する（発表で名前が挙がるのはエンドポイントのセッションとドキュメントのセッション）。
2. エンドポイントのセッションがルートを書き、5 ファイルの更新が必要なテストをサブエージェントに渡す。サブエージェントが報告し、テストが通る。
3. あるセッションが、エクスポートボタンをどこに置くかを尋ねる。これはプロダクトの判断なので、聞いてくれるのが良いと登壇者は言う。「注文テーブルに置く」と答える（デモで入力したのはこれだけ）。
4. その間にドキュメントが完了する。
5. 3 つのブランチを統合し、読み取り（read、grep、glob）しかできないレビュアーを起動する。
6. レビュアーが、商品名にカンマがあると 2 列に分かれてしまう問題を見つける。個々のセッションは自分の担当部分しか見ていなかったため見逃していた。
7. エンドポイントのセッションがそれを直してテストを追加し、3 ブランチを含む PR を更新する。

登壇者が答えた質問は 1 つで、あとはレビューするだけです。ここまでがすべてインナーループです。

### 5.9 アウターループ：ハンドオフを見直す

チーム全員がこう働くと、PR は大幅に増えるのに、レビュアーは同じ人数のままです。レビューできる量を超えてセッションを走らせても、キューが長くなるだけです。だから、ソフトウェアの出荷そのものもループにする必要がある、という流れです。

以前の変更の流れには 6 回のハンドオフがありました。ハンドオフのたびに待ちが発生します。1 か月かかったプロジェクトを振り返ると、時間の大半はハンドオフ間の待ちだった、と登壇者は言います。自チームのフローを図に描き、各ハンドオフで次の問いを立てるよう勧めています。

> この人は何かを**判断**しているのか、それとも何かを**チェック**しているのか。

テストが通ったか、変更履歴が更新されたかを確認しているだけなら、コード化したチェックにできます。そうすると、Claude がチケットに取り組み、実行結果を確認し、失敗なら Claude に戻る、という形になり、ハンドオフは 2 つ（ループに入るところと、出てきたものを承認する人）だけが残ります。その人は、既にチェックを通ったものだけを見ます。

擬似コードにすると「Claude がチケットを実装し、チェックが通るまで失敗を直し、その後に人を待つ」です。登壇者は、この while ループに**上限がない**というバグを指摘します。自分たちのチームでも問題になったそうで、回数と時間に上限を設け、上限に達したら人に渡すようにします。強調表示した行が、自分を置く場所です。人を挿入する手段は既にあり、手元では ask ルール、バージョン管理では PR、リリースではデプロイ環境の承認です。何かを自動化する前に、人がどこにいるべきかを先に決めることが最重要だと述べています。

先ほどの 2 列の図（Claude が決めること／強制されること）をチーム向けにすると、左は Claude が決めることで、間違えたら足りなかった行を加えます。右は CI や managed settings で、一致したものをブロックします。

> 注意：ここにも落とし穴があります。目標が「チェックを緑にすること」なら、チェック自体を変えて緑にする方法もあります。したがって、**「緑」の意味を決めるファイルを守ります**。対象は、テスト、ワークフローファイル、package ファイルのスクリプト、`.cloud` フォルダです（音声認識の都合で表記が確定できません。トランスクリプトでは Claude が "Cloud" と書き起こされています）。Azure Repos ではこれらをコードオーナーや必須レビュアーの配下に置き、特定の人の承認が必要になるようにします。

### 5.10 レビューの量をリスクに合わせる

すべての変更に同じレビューが要るわけではありません。文言変更は軽い確認でよく、決済関連は 2 人が必要かもしれません。Anthropic では、変更ごとに何人のレビューが必要かを**分類器で決めて**います。

| 変更の種類 | 扱い |
| --- | --- |
| ドキュメント、色、フォントなど低リスクの軽微な変更 | 人を付けない。Claude Code Review が承認（stamp）して流す |
| 大半の変更 | Claude Code Review が最初のパスを行い、人が時間を使うべき箇所を示す。通常は 1 人のエンジニア |
| 重要な変更 | 人が 2 人 |

### 5.11 チームループのデモ：GitHub Actions 上の Claude Code

先ほどのエクスポート機能の PR を、チームのループに通します。語られた流れは次のとおりです。

1. PR を自分のノート PC から開く（最初のデモのとおり）。
2. Claude Code が **GitHub Actions** 上で Foundry を使って動き、diff を読み、問題を見つけて修正を push する。ここは Claude が決める部分。
3. CI が、手元と同じチェックを実行する。登壇者は、stop hook と**まったく同じコマンド**にして、両者がずれないようにすることを勧めている。ここは強制される部分。
4. チームメイトが diff を読んで承認する。早くするため、Claude に「何を実行したか、何をテストしなかったか、どこに自信がないか」を書き出させ、レビュアーが時間を使う場所を分かるようにする。レビュアーの範囲を減らせることは何でもやる、という考え。
5. ステージングスロットに進み、swap して、Azure 上で公開される。

デモ中に画面上で起きたことは、次のように語られています。

1. PR が開き、ワークフローが自動的に始まる。
2. ワークフローが Azure にサインインする。API キーは保存されておらず、GitHub がこのワークフローに発行するトークンを Entra が信頼している。
3. Claude Code が Foundry 上で起動し、diff とチームのレビュー skill を読む。
4. エンドポイントがアカウントの所有者を確認していないこと（他人の注文をエクスポートできてしまう）を見つける。
5. その確認とテストを追加し、push してコメントを残す。
6. 新しいコミットで CI が走り、すべて緑になる。ただしそれ以上は何も起きない。「Dana」の承認を待っているため。
7. Dana が開いてコメントを読み、diff を見て承認し、マージする（Dana という人物の素性は、発表では説明されていません）。
8. マージでデプロイが始まる。まずステージングスロットに入り、ヘルスチェックをして、swap する。
9. Azure 上のアカウントページにエクスポートボタンが表示される。これがストーリー 4,812 の、ノート PC から本番までの流れ。

整理は「Claude が何を直すかを決め、CI が終わりを決め、Dana がいつ出荷するかを決めた」です。

### 5.12 ワークフローファイルの要点

登壇者は、短くしたワークフローファイルの形を示しています（完全な例はドキュメントにあり、最後にリンクを案内するとのこと）。語られた要点は次のとおりです。

- ハイライトされた行が Foundry の部分。Entra でサインインするので保存されたキーはなく、1 つの設定で Foundry が有効になる。Foundry を使わない場合に変わるのはこの行。
- prompt を書くと自動で動く。省略すると、誰かが Claude にメンションするまで待つ。信頼を築く最初の段階では良い方法。
- 常に足すべきものは**上限**。必要なツールを列挙し、permission mode を自分で設定し、最大ターン数とタイムアウトを指定する。これが先ほどのループ上限に当たる。
- 意外に知られていない点として、GitHub は既定のトークンで作られたコミットに対して CI を起動しない。Claude の GitHub App として push させないと、その修正はチェックされない。
- この action は GitHub 専用。コードが Azure Repos にある場合は、同じ効果を得る部品として **`claude -p`**（音声では "Claude-P"。Claude Code をヘッドレスで自分の CI パイプライン内で実行する）を使う。

### 5.13 無人で動かす前の 4 つの確認

| 観点 | 内容 |
| --- | --- |
| 何に届くか | Claude を動かすジョブは、モデルを呼ぶだけでよい。実際にデプロイするジョブには、別のスコープを持たせる。action は Claude の設定を**ベースブランチ**から取り、PR から取らない。一方、package のスクリプトは PR から来る。だからコードオーナーが重要になる |
| どこで動くか | 使い捨てのランナー。ローカルと同様、sandbox を有効にしてシェルコマンドに制限を足せる。Claude が読むもの（チケット、コメント、ログ）はすべて誰かが書いたものなので、信頼できない入力として扱う |
| 何が完了を決めるか | Claude の要約は人が読むためのもので、PR を動かすのは最終的に CI のステータス |
| 誰が承認するか | 重要な変更ではブランチで人の承認（複数）を必須にする。Claude も push できるので、新しいコミットのたびに承認をリセットする設定を有効にする。そうしないと、変更されたコードに古い承認が残る |

### 5.14 Claude Code Review（マネージド版）と auto fix

ここまでは自分たちで書いたループです。Anthropic は、同じ工程のマネージド版を **Claude Code Review** という製品として提供しています。

- Anthropic のインフラ上で動き、Foundry 経由では動かない（登壇者は「免責事項」として述べている）。
- Claude の Team プランと Enterprise プランで利用でき、リポジトリが GitHub にある場合に限る。
- 複数のエージェントが、作者のコンテキストを持たない状態で PR の**敵対的レビュー**を行う。さらに、見つけたものを投稿前に確認する、「敵対的レビューの敵対的レビュー」がある。
- 例として、履歴全体をメモリに読み込んでいたバージョンに対し、なぜタイムアウトするかと、どのヘルパーを使うべきかを書いたコメントが付く。
- Claude Code Review は何も**承認もブロックもしない**ので、そのチェックは赤にならない。重要な指摘でマージを止めたい場合は、指摘の件数を自分の CI に読み込んで、そこで判断する。

さらに、コードを書いたセッションにつなぎ戻せます。Anthropic ではクラウド上で開発することが増え、すべてのセッションを Claude Code Remote で動かしています。**auto fix** を有効にすると、バックグラウンドのルーチンが PR を監視し、Claude Code Review が指摘を報告するとそのセッションを再開して、出てきた指摘を修正させます。登壇者はこれを、PR が上がった後に「自己修復」する形だと説明しています。機械が決められることがすべて緑になっても、マージボタンは Dana を待っています。

### 5.15 組織レベル：4 つの問い

次は組織の話です。何百台、何千台のノート PC でコーディングエージェントがコマンドを実行することに、誰かが承認を出す必要があります。セキュリティ部門、プラットフォームチーム、あるいは会場のあなたかもしれません。その会話は通常、次の 4 つの問いになります。

1. 信頼できないどんなものを読むか（これは既に説明した）
2. 誰として動くか
3. 間違った場合にどこまで届くか
4. 何をしたか見えるか

このパートにはデモはなく、一度設定すればよいことの説明だと断っています。

**誰として動くか（認証）。** Foundry では Azure CLI でサインインし、Foundry を有効にして、リソース名を指定します。保存する API キーはなく、アクセスはそのリソース上のロールです。アカウントを無効にすれば、トークンの有効期限が切れた時点でアクセスが終わります。API キーは別物なので、配る際はより慎重にします。Claude の Teams／Enterprise プランでは SSO などを使います。いずれの場合も Claude は**あなたとして**動くので、ログイン後に実行されるコマンドはあなたの Azure ロールを使えます。このため、本番環境の Just-in-time アクセスは良い安全網になります。

**コードの行き先（データ）。** セキュリティ部門が聞くのは、コードがどこへ行くかで、これはデプロイごとの選択です。Azure でホストする場合、プロンプトと補完は Azure 内に留まり、Anthropic に流れるのは、利用状況のメタデータと、安全性の分類器がフラグを立てたコンテンツだけです。誤用や不正利用の理由でフラグが立ったものは一部通過する、という説明です。もう一方は Anthropic で完全にホストする選択です。

> 注意：初日から、特に Foundry では、モデルを自分のデプロイに**固定（pin）**します。Foundry の既定は古いモデルであることが多く、そうしたモデルは auto mode をサポートしません。auto mode が見当たらないときは、まずこれを確認してください。

**ルールの配布（managed settings）。** 組織レベルで sandbox 設定や deny ルールを適用する最適な方法は、managed settings の JSON ファイル（音声では "manage settings.json"）です。IT が Intune などで管理対象デバイスに配置します。Anthropic の Teams／Enterprise プランでは admin console でも設定できますが、**それは Foundry セッションには届きません**。

例では、ユーザーが手元で deny リストを空にし、sandbox を切っていますが、右側の会社の設定が勝ちます。managed settings は個人の settings.json の設定より優先されます。組織全体でガードレールを強制したいなら、managed settings に書きます。厳しすぎないかを見直すためのコンソールを用意することも勧めています。ただし、決して譲れないガードレールはここにコード化します。

> 注意：Windows では、sandbox に WSL2 が必要で、**WSL は既定で Windows のポリシーを読みません**。全員を sandbox のために WSL に移すと、配布したルールがその中では適用されません。直すための設定は 1 つとのことですが、設定名は発表では語られていません。展開前に 1 台で `/status` を実行し、ポリシーが表示されることを確認します。

**組織が持つ 3 つの制御。**

| 制御 | 役割 |
| --- | --- |
| Entra ID | 誰が使えるか |
| managed settings | それらのデバイスで何ができるか |
| OpenTelemetry | 何をしたか（可観測性） |

Claude の Team／Enterprise プランには利用状況ダッシュボードがありますが、Foundry は対象外です。Foundry で動かす場合は、始める前に OpenTelemetry を設定するよう強く勧めています。留意点は次の 3 つです。

- Foundry のセッションには Claude アカウントが無いので、ユーザー ID を属性として追加するまで、イベントに「誰か」が載らない。
- プロンプトとコマンドは既定ではログされない。保存・保持するかは、セキュリティチームと決める。
- トークン数と推定コストは「何を使ったか」を教えるが、「うまくいっているか」は教えない。そこで見るべきものが 2 つある。

1 つは**拒否されたツール呼び出し**で、どのルールが効いていて、どれがただ邪魔になっているかが分かります。その拒否が意図したものか、本来は許可した道を塞いでいないかを確認します。もう 1 つは、最初に挙げた数字、つまり **PR がどれだけ開いていたか**で、リポジトリから取れます。

### 5.16 「やめてよいこと」

これらが整えば、やめられることがたくさんあると登壇者は言い、自分がやらなくなったことを挙げています。

- 長い手順書のようなプロンプトを書かない。ゴール、制約、検証方法を渡す。
- plan mode は、計画を先に見たいとき（通常は全く新しいプロジェクトをゼロから始めるとき）以外はほとんど使わない。
- ファイルを手で選ばない。エントリポイントを指すだけにする。
- すべてのルールを CLAUDE.md に書かない。古いモデル向けの指示は、むしろ逆効果になりうる。
- 各コマンドを手で承認しない。ただし `/permissions` を一度は実行する。「don't ask again」を押すたびに allow ルールが保存され、それに一致するコマンドは通常、分類器を飛ばすため。**allow ルールは分類器より優先される**。
- 各 diff を見張らない。チェックを走らせ、PR を一度レビューする。通常は Claude Code Review が「皿に載せて」くれた箇所だけを、同僚とのレビューと同じように見る。

古い指示が逆効果になる点について、登壇者は、最近 Claude Code のシステムプロンプトの 80% を削除した（世代 5 のモデルのとき、という記憶）と話します。3〜6 か月前に穴を埋めていた足場（scaffolding）が、新しいモデルが出ると妨げになる、というのが要点です。そのため、あるモデルと新しいモデルの性能を比べて、知能の向上を実際に得られているか確認できるよう、**eval を用意しておく**ことが重要です。得られていないなら、通常は足場の問題です。

この点で役立つコマンドとして `/doctor prompt-audit`（発表での呼び方）を紹介しています。古くなった指示や自己矛盾している指示を見つけてくれるもので、あるユースケースでモデルをアップグレードするたびに実行するよう勧めています。

### 5.17 明日から始める方法と、締めくくり

登壇者が示した 3 つの要点は、次のとおりです。

1. Claude が決めることを決め、残りは強制する。取り返しがつかないことは、チェックかルールにする。
2. 人が承認する場所を決め、その手前のチェックを守る。
3. チームが毎週やっていることを 1 つ選び、ループとして書く。

最初のループは、頻繁に起きる、合否がはっきりしている、元に戻しやすい、の 3 条件を満たすものが良く、例は依存関係の更新や不安定なテスト（flaky test）です。最初の 1 週間はコメントだけにして、コメントを信頼できるようになったら push を許可します。最初から大きく始めなくてよい（"boil the ocean" しなくてよい）、とも話しています。変更が出ていくたびに「誰が決めたか（Claude、ルール、人）」を言えるようにします。

明日から始めるなら、**すでに出荷したチケットを 1 つ選び、Claude にチケットを渡す前のコミットをチェックアウトして、結果をマージ済みの内容と比べる**ことを勧めています。違いは「問題ない」か「3 つの対策のどれか」のどちらかです。そうしたチケットを数件取っておけば、モデルを変えるたびに再実行でき、それ自体が eval になります。

資料の最後に、Foundry のセットアップガイドと、今日の設定を全部載せたページへのリンクがある、と案内されています（スライドの左端）。code review、クラウドセッション、admin console が必要な場合は、Anthropic のプランが必要です。大きな展開では Microsoft か Anthropic のアカウントチームに相談するよう勧め、相談時には「1 つのチーム、1 つのリポジトリ、自動化したい 1 つのループ」を持参すると立ち上がりが速いと述べています。登壇者自身も多くをまだ模索中で、一部のパターンは数か月前のものだそうです。セッション後は Anthropic のブース（Moscone South の 4009）にいるとのことです。

## 7. 注意点・発表者の気付き

- **exit 2 でなければ、停止がブロックされない。** 失敗したビルドは通常 exit 1 だが、Claude Code はそれをスクリプトの故障と見なして止まる。hook を作ったら、わざと壊して確認する。
- **deny ルールは「テキスト」しか見ない。** `npm run migrate` は止められても、別の呼び方は通る。pre-tool use hook と sandbox で補う。
- **sandbox は有効化が必要。** 隠すキーも指定する。Windows では WSL2 が必要で、WSL は Windows のポリシーを既定では読まない。展開前に `/status` で確認する。
- **ループには上限を。** 回数と時間の上限、最大ターン数、タイムアウトを置く。登壇者のチームでも上限のないループが問題になった。
- **「緑」を決めるファイルを守る。** テスト、ワークフロー、package のスクリプト、`.cloud` フォルダ（表記は 5.9 の注記参照）はコードオーナーの下に置く。
- **GitHub の既定トークンで作ったコミットには CI が走らない。** Claude の GitHub App として push させる。
- **信頼できない入力。** チケット、コメント、ログは誰かが書いたものなので、信頼しない前提で扱う。
- **承認のリセット。** Claude も push するので、新しいコミットごとに承認をリセットする設定を有効にする。
- **allow ルールは分類器より優先される。** 「don't ask again」の積み重ねを `/permissions` で見直す。
- **Foundry の制約。** 既定モデルは古く auto mode が使えない場合がある（モデルを固定する）。admin console の managed settings と Claude の利用状況ダッシュボードは Foundry に届かない。Foundry には Claude アカウントがないので、ユーザー ID を属性に追加しないとイベントに「誰か」が載らない。プロンプトとコマンドは既定でログされない。
- **Claude Code Review は Foundry 経由ではない。** Anthropic のインフラで動き、Team／Enterprise プランと GitHub のリポジトリが条件。承認もブロックもしない。
- **Azure Repos の場合。** GitHub Actions の action は使えず、`claude -p` で自分の CI に組み込む。
- 登壇者自身も、これらのパターンの一部は数か月前のもので、まだ模索している、と述べています。

## 8. 利用者にとっての利点

発表で語られた効果や利点は次のとおりです。顧客事例の紹介はありません。

- 取り返しのつかない操作を、決定的なルールで止められるため、エージェントにより長い時間軸の野心的なタスクを任せられる。
- Foundry では、API キーを保存せずに Entra と Azure ロールでアクセスを管理できる。アカウントを無効にすれば、トークンの期限切れでアクセスが終わる。Azure でホストする場合、プロンプトと補完は Azure 内に留まる。
- 決まったチェックを自動化することで、人は判断が必要な箇所に集中できる。Anthropic 自身では、マージされる PR が 1 日約 2,500 件（5 月）から約 30,000 件（9 月）に増えた。
- チームでは、plugin や managed settings で、skills・hooks・MCP servers・ルールを全員に配布できる。
- Claude Code Review の指摘と auto fix で、PR が上がった後も自己修復的に直る。

## 9. まとめ

このセッションは、Claude Code をチーム・組織で使うときの考え方を、同じ問い「誰が決めたか」で貫いたものです。実装は Claude に任せ、取り返しのつかないことは hook、deny ルール、sandbox、managed settings で強制します。インナーループでは、見えない情報を CLAUDE.md や skill で渡し、完了の定義を stop hook（exit 2）で持たせ、触らせないものをルールで守ります。アウターループでは、ハンドオフごとに「判断か、チェックか」を問い、チェックをコード化して上限を付け、人の承認を最後に残します。組織としては、Entra ID（誰が）、managed settings（何を）、OpenTelemetry（何をしたか）の 3 つを、Foundry では特に事前に整えます。最初の一歩は、出荷済みのチケットを 1 つ選んで結果を比べること、そして週に 1 回の定型作業を、まずコメントだけのループにすることです。
