# BRK237 Plugins for Copilot: build once, govern once, use everywhere

## 1. はじめに

このセッションは、Microsoft Copilot のプラグインとは何か、そしてプラグインを企画からエンタープライズ配布、さらに Partner Center での公開までどう作るかを扱った発表です。前半では、ツール・スキル・エージェントを 1 つのパッケージにまとめるプラグインの構造と配布の仕組みを説明しています。後半では、新たに発表された開発ツール Work IQ Developer Tools（略称 WIQD）を使い、コーディングエージェントとの会話だけでプラグインを作り、評価し、改善し、組織へ配布するまでをデモで見せています。

一番の結論は、**プラグインのライフサイクル全体（作成・検証・評価・改善・配布）をエージェント主導で回せるようになった**という点です。Copilot の拡張機能を作る開発者、社内システムを Copilot につなぎたい IT 担当者、ISV（独立系ソフトウェアベンダー）の方が主な対象です。

## 4. 発表者が伝えたいメッセージ

タイトルの「一度作り、一度管理し、どこでも使う」が全体の主張です。プラグインを 1 回パッケージ化すれば、Copilot のさまざまな画面で利用でき、管理者は 1 か所で配布とポリシーを制御できる、という考え方です。

Sébastien 氏はもう 1 つ、ソフトウェア開発は公開日に終わるのではなく、公開日に始まるという点を強調しています。公開した途端にユーザーから良い評価も悪い評価も届きます。Copilot の高評価・低評価ボタンのデータをプラグインの改善に使えるようにしたい、というのが WIQD を一般公開した動機です。社内で多数のチームがプラグインを作る中で必要になったツールを、そのまま企業とソフトウェア会社に開放したと説明しています。

## 5. 発表内容の詳細

### 5.1 Adobe プラグインのデモと、プラグインを作る理由

Garry 氏は自分のチームが各地のイベントで登壇し、帰国後に出張報告を書く立場だと話しています。報告には写真が欠かせません。サンフランシスコで撮った写真は、スマートフォンから OneDrive にアップロード済みです。自分は写真が得意ではないため、パートナーの Adobe がストアに公開したプラグインで補正し、仕上がりをそろえます。

Adobe のプラグインには複数のスキルと MCP サーバーが含まれています。Microsoft 365 の OneDrive にある画像を Adobe に渡して補正し、クラウドへ画像を送り、共有用の Firefly ボードまで作れます。共有すればマーケティング担当者も使えます。

Adobe がプラグインを選んだ理由として、次の 4 点が挙げられています。

- **見つけやすい**：左側のレールにプラグインがあり、検索してインストールし、有効にするだけで使える
- **取っつきやすい**：「写真を直して」という一言でも、写真家向けの専門用語を使った細かい指示でも動く。習熟度を問わない
- **使い慣れている**：Creative Cloud など既に使っているツールにつながる
- **管理できる**：管理者が配布先とポリシーを決め、誰がどのプラグインを使えるかを制御できる

Adobe 以外のパートナーも多数プラグインを作っており、直近では 350〜400 ほどだと Garry 氏は述べています（本人は「確か」という口ぶりで話しています）。また、この場でプラグインカタログ（aka.ms/plugins）を発表しています。Copilot 全体で利用できるパートナー各社のプラグインを一覧できます。

### 5.2 プラグインの構造と配布

プラグインは、ツール、スキル、エージェントを 1 つにまとめるものです。Adobe のデモでは、スキルと MCP が連携して写真補正と Firefly ボード作成を行っていました。

技術的には、Microsoft Copilot のプラグインは Microsoft 365 アプリです。Microsoft 365 で開発した経験があれば馴染みのある概念で、`manifest.json` に次の 3 つの主要なプロパティがあります。

| プロパティ | 役割 |
| --- | --- |
| agent connectors | ツール（MCP サーバーなど） |
| agent skills | パッケージに同梱するスキル |
| Copilot agents（追加で指定可能） | 同じパッケージで配布するエージェント |

エンドユーザーはパッケージを 1 つインストールするだけで必要なものがすべてそろいます。「このスキルはここから、この MCP はあちらから」と個別に集める必要はありません。

ガバナンスの中心は Microsoft Plugin Registry（プラグインレジストリ）です。プラグインはレジストリに登録され、Copilot のさまざまな画面に配布されます。デモでは Cowork を使いましたが、Chat でも使えます。Office でもプラグインが使えるようになり、対応する画面は今後さらに増える予定だと説明されています。セキュリティとガバナンスは Agent 365 と、管理者が既に使っている管理センターで担保されます。

### 5.3 既存資産からの移行

現状に応じた移行の道筋が、次のように説明されています。

- **Cowork で既にプラグインを作っている場合**：変更は不要です。プラグインをレジストリに入れ、エンドユーザーへ配布します。
- **エージェントを開発している場合**：既存のアプリパッケージを開き、スキルと MCP を追加してレジストリに登録し、配布します。
- **別のツールや形式（エージェントプラグイン標準）を使っている場合**：現時点では Microsoft 365 の形式への変換が必要です。将来的には、この変換なしでレジストリに取り込めるようになる予定です。

### 5.4 WIQD の紹介と開発の経緯

ここから Sébastien 氏が登壇します。新しく発表されたのが Work IQ Developer Tools（WIQD）で、プラグインをエージェントで丸ごと開発するための、プロ開発者向けのツールです。

WIQD 自体も一種のプラグインで、GitHub Copilot などのコーディングエージェントの中に入り、会話で作業を進められます。さらに CLI も用意されています。プロ開発者にとって CLI は、決定的（毎回同じ結果になる）なワークフローを実現する手段です。プラグインを自社のソースコード管理に置き、レジストリへ公開するといった、通常のソフトウェアと同じ運用ができます。使い始めるには Work IQ プラグインをインストールします。入り口は aka.ms/wiqd です。

開発の経緯は次のとおりです。Microsoft 社内の多くのチームが、Cowork で使えるプラグインを作っています。そのため、チームのアイデアから、評価・テスト・フィードバックに基づく改善まで、開発を自動化する手段が必要でした。また、小さな製品チームでの試用、さらに Microsoft 内で早期利用者にあたる社内先行利用者（ドッグフード）への展開、そしてストアへの公開も必要でした。社内で作ったものを、プラグインを作りたいあらゆる企業とソフトウェア会社に開放した、という流れです。

### 5.5 プラグインのライフサイクル

Sébastien 氏は、ライフサイクルを次の段階で説明しています。

1. **作成（意図から始める）**：今のソフト開発は会話、会議、仕様書といった意図から始まります。プラグインの目的を言葉で説明するか、既にあるものを取り込みます。既存のものにスキルやコネクタを足す場合もあります。
2. **接続**：スキル単体は簡単な作業には向いていますが、サードパーティのシステムにつなぐと真価を発揮します。オフィスのどこかで動いている古い基幹業務システムや SaaS につないだり、既に作った Power Platform のコネクタを再利用したりできます。
3. **組み立て**：プラグインはビュッフェのようなものだとたとえています。必要な要素を選んで皿に載せ、ユースケースと「片づけたい仕事」を構成します。
4. **検証**：パッケージが正しいか、Microsoft が定めるベストプラクティスに沿っているかを確認します。
5. **評価**：評価（エバル）は、ソフトウェア開発における単体テストに相当すると説明されています。この週は何度も耳にする言葉になるとのことです。評価と修正を繰り返しますが、その作業は AI が大きく助けてくれます。
6. **ユーザーからの学習**：公開後のフィードバックを製品に戻します。
7. **プレビューと共有**：小さなグループに共有します。
8. **組織への公開**：管理者を統制役として残したまま公開します。管理者は承認依頼を受け取り、1 つ、10 個、あるいは複数のグループ、または組織全体へ配布できます。

自社製品を顧客向けに作るソフトウェア会社は、WIQD で作ったプラグインをそのまま Partner Center に出せます。Partner Center は、オファーを登録する公開の窓口です。顧客はプラグインレジストリからダウンロードして、自分のワークフローを改善できます。

### 5.6 デモの背景：Caldova の出荷準備プラグイン

デモの詳細は 6 章に書きます。想定しているのは、Caldova という組織です。製品のローンチ準備（出荷準備）の状況を管理するシステムを持っていて、来週カスタマーサービスポータルを公開する予定です。

### 5.7 今回の発表内容と今後の予定

Sébastien 氏が、Ignite での発表内容として挙げた項目です。

- Work IQ プラグインに WIQD を組み込み、多くの開発者が使う環境にそのまま入るようにした
- コードを書かずに、プラグインが何をすべきかを伝えるだけで作れる、ガイド付きの作成体験
- キーボードに触れなくても組織へ公開できるよう、CI/CD 向けの CLI 体験を提供
- エージェントプラグインのネイティブ対応。任意の GitHub リポジトリや、エージェントプラグイン対応の他のコーディングエージェントのものを直接取り込める
- agent builder のエージェントや agent toolkit のプロジェクトを WIQD に取り込める
- Power Platform コネクタを、その場で作ってプラグインに自動で組み込める。MCP サーバー作成が非常に簡単になる点を、大きな変化として挙げています
- プラグインの評価スイート（ツール呼び出しとスキル実行の評価）を、エージェント体験または CLI から利用できる
- 検証の前倒し（シフトレフト）。ストアに載せるための規則を知りたいという声に応え、開発環境の中で「ストアに出せるか検証して」と頼めるようにした
- ソフトウェア会社向けに、Partner Center への公開に対応

**今後の予定**（まだ提供されていないもの）は次のとおりです。

- エージェントプラグイン標準のネイティブ対応（「かなり近い」と説明）
- Copilot Chat だけでなく Copilot Cowork での評価（同じく「かなり近い」）
- プラグインへの反応（高評価・低評価の数、フィードバック件数、誰が気に入ったか）を開発者に返す仕組み
- より充実した公開プラグイン体験。マーケットプレース向けの検証の強化と、Partner Center でのオファー管理を含みます

## 6. デモ・手順

デモは 2 つあります。

### 6.1 デモ 1：Adobe プラグイン（Garry 氏）

冒頭の導入として、Adobe プラグインが写真補正を行う様子が紹介されています。操作を一歩ずつ語る形ではなく、「OneDrive の画像を Adobe に渡して補正し、クラウドに送って Firefly ボードを作る」という流れが語られています。画面の細部は音声からは確認できません。

### 6.2 デモ 2：WIQD でプラグインを作って配布する（Sébastien 氏）

料理番組のように、完成形を見せてからゼロで作り直す構成です。以下は語られた順です。

1. **完成形の確認**：Cowork で、Caldova の出荷準備について「カスタマーサービスポータルを公開できるか」と質問します。画面がなかなか立ち上がらず、見せたい画面とは別のものが出るなどの手間取りがありましたが、最終的に回答が表示されました。Caldova Readiness のウィジェットとコネクタを見つけ、「現状では不可。目標は今週木曜日で、来週ではない。誰も公開を承認していない」という内容を返しました。このデータは Copilot が作った架空のものではなく、外部に置いたサーバーから、プラグイン経由で自動取得したものだと説明されています。
2. **開発ツールの選択**：GitHub Copilot アプリを使います。Visual Studio、Copilot アプリ、Copilot CLI など、どのコーディングツールでもよく、他のコーディングエージェントでも構わないと説明しています。
3. **要件の収集**：過去にあった Caldova のカスタマーサービスポータル出荷準備レビューを探し、そこから今回の要件を作るよう依頼します。エージェントは、Microsoft 365 組織の中の Teams を探せばよいと判断します。数日前に実際の会議とチャットがありました。
4. **Work IQ の利用**：エージェントが Work IQ を呼び出し、Caldova に関する会議の文字起こし、要約、チャットを含むクエリを自動で作ります。MCP の URL、合意事項、利用可能な情報源、未解決の項目が見つかりました。最後に「短い実装用の概要」にまとめさせています。会議で決めたことを忘れて作成につなげられない、という悩みを例に挙げ、Work IQ が組織の文脈をコーディングエージェントに戻せる点を強調しています。
5. **プラグインの生成**：「WIQD を使って Copilot プラグインを作って見せて」と依頼します。WIQD が参照ファイルを読み込み、アイコンの作成と画像の生成を行い、外部の MCP サーバーも調べます。完了後、約 20 個のファイルが作られました。その 1 つが `manifest.json` で、Copilot エージェント、エージェントスキル、エージェントコネクタが含まれています。スキルは出荷準備全体を表し、MCP サーバーとの対話方法、呼び出すツール、表示方法を、具体的な指示がなくても自分で判断していました。コネクタは、Power Platform コネクタや OpenAPI で記述した API からも作れると補足しています。コードを読む必要は必ずしもなく、確認とレビューができれば十分、という考え方です。
6. **プロビジョニング**：検証、プロビジョニング、リンクの表示を依頼します。Cowork か Chat でテストできるリンクが示されました。プラグイン一覧に「Caldova readiness development」が現れ、接続、MCP サーバー、先ほど作成したスキルが入っています。
7. **評価セットの生成**：AI が作ったものなので品質が気になる、という理由で「評価セットを作って」と依頼します。評価セットは「良い状態とは何か」の定義で、AI コーディングの本質はそれを記述することだという説明でした。評価用 CLI で使う大きなファイルが作られ、プロンプト送信時にツールが呼ばれること、スキルが実行されること、期待する応答（たとえば、依頼が「評価」であって「公開承認」ではないこと）を確認します。
8. **評価と修復の繰り返し**：GitHub Copilot 内で長時間評価を回し、途中で「少しやりすぎた」場面もあったと話しています。最初のレポートでは評価結果が良くなく、そのまま公開すれば低評価が付く水準でした。そこから挙動を再現し、スキルや MCP サーバーを変えた影響を調べ、改善を重ねました。最終結果は 10 件が合格、2 件が不合格で、合格率は 83.3%。100% ではないものの、同僚に共有できる確信は得られたという説明です。スキルは構造、内容、データの見せ方が大きく変わり、「内容を表示する際に守るべき規律」も加わりました。評価を 2 回実施しています。スキルは自然言語の指示の集まりで、指示そのものはテストできないため、評価を通すしかない、という説明です。
9. **共有**：評価と修復を経たプラグインを Garry 氏ともう 1 人（発話では Ratchet という名前に聞こえます。音声認識の都合で表記が確定できません）に共有し、チャットや製品の画面からフィードバックを求めます。
10. **フィードバックの確認**：過去に固定したチャットを開き、特定の ID を指定して「Caldova readiness へのフィードバックは？」と質問します。環境に似たシナリオが多数あるため、ID を指定したという説明です。結果は 4 件のフィードバックで、使いやすさは好評、結果の見つけやすさは要対応、レポートの書式は改善要望、文章コメントのない低評価が 1 件でした。これは Insights Agent という仕組みで見せていますが、同じことをプラグインとエージェントのフィードバックに基づいて、このコーディングエージェントの中から聞くこともできます。ここから、新しい評価の候補（最新のゲート表示、最新レビューの比較、準備状況の更新作成）が提案されました。
11. **CI/CD の追加**：ZIP をメールで管理者に送ってアップロードしてもらうのではなく、組織で統制された方法で出荷したい、と述べています。ここでは GitHub を使いますが、他のパイプラインでも構いません。「CI/CD を追加して」と依頼します。GitHub に変更が入るたびに、開発者がレビューして承認し、マージすると、新しいバージョンが自動で公開される仕組みです。
12. **プルリクエストの確認**：届いていたプルリクエストを 1 件開きます。内容は「プラグイン使用時、すべての応答の冒頭に Hello Microsoft Ignite を付ける」という変更で、ビジネス向きではないが仕組みの説明にはなる、と話しています。変更差分をソフトウェア開発者が確認でき、評価も追加できます。マージ済みで、本番のプラグインが組織カタログへ自動公開され、検証の全手順が履歴で確認できます。
13. **管理者の承認**：Microsoft 365 管理センターに、プラグインを組織全体へ承認・配布する新しい依頼が届いています。Caldova Readiness の MCP サーバーとその URL、ツール一覧を確認でき、「承認」を押すと、組織のユーザーが自分の Cowork や Chat に追加できます。

## 7. 注意点・発表者の気付き

- AI が生成したプラグインでも、品質の確認が欠かせません。スキルは自然言語の長い指示で、人手では十分にテストできないため、評価で品質を確かめます。デモの最終合格率は 83.3% で、100% ではありません。
- 生成されたコードは、読む必要が必ずしもない一方で、確認とレビューはできるようにしておく、という姿勢です。
- 組織への配布は、ZIP をメールで送る方法ではなく、統制された方法（今回は GitHub）で行うという考えです。
- 他形式のプラグイン標準は、現時点では Microsoft 365 形式への変換が必要です。ネイティブ対応は今後の予定です。
- 評価は現時点では Copilot Chat が対象で、Copilot Cowork での評価は今後の予定です。
- 発表中のプラグイン数（350〜400）は、登壇者がうろ覚えのような言い方で述べた数字です。

## 8. 利用者にとっての利点

- **利用者**：プラグインを 1 つ入れるだけで、ツール、スキル、エージェントがそろう。習熟度を問わず自然言語で使える
- **管理者**：配布対象とポリシーを一元管理でき、承認の依頼が管理センターに届く
- **開発者**：会議やチャットの文脈からコーディングエージェントで要件を作り、コードを書かずに生成、評価、改善、配布まで進められる
- **ソフトウェア会社**：ストアの規則に沿った検証を開発環境で済ませ、Partner Center から顧客へ公開できる

## 9. まとめ

プラグインは、ツール、スキル、エージェントを 1 つにまとめた Microsoft 365 アプリで、プラグインレジストリと Agent 365 を通じて Copilot の複数の画面に、管理された形で配布されます。新しい WIQD は、要件の収集から生成、検証、評価、フィードバックの取り込み、CI/CD、管理者承認、Partner Center への公開までを、コーディングエージェントと CLI で通して実行できるようにします。デモでは Caldova の出荷準備プラグインを作り、評価で 83.3% の合格率まで改善して組織へ公開しました。エージェントプラグイン標準のネイティブ対応と Cowork での評価は、今後の予定です。入門は aka.ms/wiqd、フィードバックは aka.ms/wiqd/feedback です。
