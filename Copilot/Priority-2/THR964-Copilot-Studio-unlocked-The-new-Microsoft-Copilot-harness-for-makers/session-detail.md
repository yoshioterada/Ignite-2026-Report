# THR964 Copilot Studio unlocked: The new Microsoft Copilot harness for makers

## 1. はじめに

このセッションは、Copilot Studio の新しい実行基盤「Microsoft Copilot harness（以下、Copilot ハーネス）」を、ライブでエージェントを作りながら紹介する短いシアター形式の発表です。従来の標準ハーネスでは、トピックで会話の流れを事前に台本として書く必要がありました。新しいハーネスでは、目的を平易な言葉で書くと、計画、実行、評価、再計画を繰り返す仕組みがエージェントの動きを決めます。

発表者は IT ヘルプデスクのエージェントを最初から作り、同じ依頼を標準ハーネスのエージェントと比較し、評価、監視、公開までを見せました。**画面を使ったデモが中心**のセッションです。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR964](https://ignite.microsoft.com/en-US/sessions/THR964)

## 3. 何に関する発表か

テーマは、Copilot Studio のハーネス（エージェントとモデルの間で動く実行基盤）の違いと、新しい Copilot ハーネスでエージェントを組み立てる方法です。流れは次のとおりです。

1. 標準ハーネスと Copilot ハーネスの違い、3 種類のハーネス
2. Copilot ハーネスが役立つ理由
3. 構成要素（指示、スキル、ツール、ナレッジ、ワークフロー、サンドボックス）
4. ライブデモ：IT サポートエージェントの作成
5. 標準ハーネスとの比較
6. 評価（Evaluate）、監視（Monitor）、公開
7. プレビュー中の自然言語によるエージェント作成と学習リソース

## 4. 発表者が伝えたいメッセージ

メッセージは、**会話のすべての経路を事前に台本にする時代から、目的を書いて任せる時代へ変わる**ということです。ハーネスが計画し、実行し、結果を評価し、うまくいかなければ計画し直すため、作り手は失敗しそうな箇所をすべて予想して作り込む必要がありません。さらに、必要なときだけ呼ばれるスキルのおかげで、より信頼できる出力を、より少ないトークンで得られると説明されています。

締めくくりで、発表者は次の要点を挙げています。ハーネスはエージェントとモデルの間の実行基盤であり、推論を多く要する複数ステップの作業には Copilot ハーネスを選ぶ、という整理です。

## 5. 発表内容の詳細

### 5.1 標準ハーネスと Copilot ハーネス

標準ハーネスでは、トピックを使ってユーザーの意図を判断し、会話の流れを台本化します。「トラブル対応の質問が来たら、この追加質問をして、このツールを呼ぶ」という経路を、すべて事前に決めます。

Copilot ハーネスでは、目的を平易な言葉で記述するだけで、計画ループ（計画、実行、適応）が動き、必要なツールを実行時に選びます。作り手は、良い指示を書き、必要なナレッジ、ツール、スキルを持たせます。

ハーネスの役割は次のように説明されました。エージェントは、作り手が設計する指示、ナレッジ、ツールです。モデルはエージェントの頭脳で、Copilot Studio は GPT と Anthropic の複数のモデルをサポートしています。ハーネスはその間の実行基盤として、いつモデルを呼ぶか、どの文脈をモデルに送るか、返ってきた内容をどう解釈するか、どのツールを呼ぶかを決めます。

計画ループの例として、「新しいデバイスが欲しい」という依頼が挙げられました。まず新しいデバイスが妥当かを確認します（たとえば 4 年ごとに更新するルールの期間内かどうか）。次に計画を立て、必要なツールとナレッジを使って実行します。その後で結果を評価し、必要を満たしていなければ、あるいはツールがエラーになれば、計画を作り直して適応します。標準ハーネスでは、こうした失敗点をすべて想定して作り込む必要がありました。

また、現在の Copilot Studio には 3 つのハーネスがあります。標準ハーネス、Copilot ハーネス、そしてカスタマー対応のための会話ハーネスです。会話ハーネスは音声とチャットに最適化されており、カスタマーサービスのシナリオを想定しています。Copilot ハーネスは、論理が多く推論が必要な高度な複数ステップの処理に向く、と位置づけられました。

### 5.2 Copilot ハーネスが重要な理由

1. **難しいワークフローに強い**：作業をステップとタスクに分解し、反復できます。特に失敗からの復旧（適応）が組み込まれており、エージェント作りで最も難しい部分を担います。
2. **ツール呼び出しの精度が高い**：従来は、どのときにどのツールを呼ぶかを説明に丁寧に書き込む必要がありました。これが動的に処理されます。
3. **性能が良い**：ツール呼び出しが正確で、スキルが必要なときだけ呼ばれるため、指示に多くを書かずに済みます。トークンの使用量が正味で減ります。

### 5.3 構成要素

発表者は「構成要素は 5 つ」と話しましたが、説明の中で挙げたのは次のものです。

| 要素 | 役割 |
| --- | --- |
| 指示 | そのエージェントを使うすべての人に常に当てはまる内容。目的、口調、境界を平易な言葉で書く。スキルがあるため短くできる |
| スキル | 繰り返し使う手順やノウハウ。必要なときだけ呼ばれる |
| ツール | 単なる質疑応答から、実際に動くエージェントへ進める要素。Power Platform のコネクタを裏で利用し、コネクタがあれば更新、作成、削除ができる。MCP サーバーも呼べる |
| ナレッジ | エージェントをデータに根拠づける |
| ワークフロー | 順番どおりに確実に進める処理。エージェントからワークフローを、ワークフローからエージェントを呼べる |
| サンドボックス | このハーネスに特有。Python コードを安全に実行し、ファイル、グラフ、計算を作る場所。追加設定は不要 |

> 補足：発話では最初に 5 つと言い、終盤のまとめでは「指示、ナレッジ、スキル、ツール、ワークフロー、サンドボックス」と述べています。上の表は発話に出た要素をすべて載せたものです。

ヘルプデスクのエージェントの例では、基本的なトラブルシューティングの手順、デバイスの要求の扱い、パスワードのリセットなどを、指示に書き込まずスキルに任せます。デバイス更新の質問ならトラブルシューティングのスキルは呼ばれません。

エージェントは曖昧で自由度の高い場面が得意ですが、決まった順に進めたい処理を気まぐれに任せたくはありません。その部分をワークフローが担います。

## 6. デモ・手順

画面を使ったライブデモが行われました。発話で語られた順に、次のとおりです。

### 6.1 IT サポートエージェントの作成

1. copilotstudio.microsoft.com を開き、ホームページの「エージェント」ボタンから、Copilot ハーネスでエージェントを作る。
2. 名前を「IT support」にする。
3. 指示を入力する。IT ヘルプデスクのアシスタントとして従業員の一般的な問題解決を手伝う内容で、スキルを使うため一部はプレースホルダーにしてある。トラブルシューティングの質問は「troubleshooting procedure」というスキルに回す、デバイスの要求では必要事項を尋ねて選択肢を示す、セキュリティとコンプライアンス、範囲外には答えない、という指示も入れた。やるべきこと以上に、やってはいけないことを伝えることが重要だと話している。
4. ツールの欄に Work IQ が既定で入っていることを確認する。このハーネスで作ると常に既定のツールになる。Work IQ では、SharePoint（サイト、リスト、ライブラリ）、OneDrive、Outlook メール、Teams、予定表、人、そして Dataverse や Dynamics のデータ（ビジネスアプリ）の読み取りと書き込みができる。
5. Work IQ の権限は設定できる。たとえば「人」は読み取りのみに変更する、Outlook を使わないならチェックを外して機能ごとオフにする、といったことができる。
6. ナレッジを追加する。既定ではすべての Web サイトを検索する設定になっているが、社内向けのエージェントでは通常望ましくないため、オフにする。support.microsoft.com を、社内ナレッジ以外の公式な情報源として指定した。
7. プラスボタンからスキルを追加する。空から作ることも、アップロードすることもできる。ここでは作成済みのトラブルシューティングのスキルをアップロードした。
8. 1 つのエージェントには最大 50 個のスキルを持たせられる。

### 6.2 スキルの中身

スキルは**テキストの Markdown ファイル**で、エージェントへのテキスト指示です。いつ動的に呼ぶかは説明文で決まるため、アップロード時には、何をするスキルか、いつ呼んでほしいかを十分に書く必要があります。今回の説明は「トラブルシューティングが必要な IT の問題があるときに呼ぶ。手順を段階的に示す」という趣旨でした。

スキル本体の内容は、まず問題を明確にする、安全な診断を行う、手順を順に案内する、代替案を示す、2〜3 回失敗したらエスカレーションする、というものです。チケット起票を提案する前に、十分なやり取りをする狙いです。

スキルにはリソースと Python の実行も持たせられます。例として、PowerPoint のスライドを作るスキルに、テンプレートと、計算やグラフを含めて組み立てる Python を同梱する構成が挙げられました。

### 6.3 テスト：デバッグモード

「ブルースクリーンになった。新しいノート PC が必要」と入力しました。テスト中はデバッグモードで、エージェントの思考が見えます。この表示は公開後のエンドユーザーには見えません。

エージェントは、トラブルシューティングの依頼と判断してスキルを呼び、Web 検索をして結果を取得しました。入力にはトラブルシューティング（ブルースクリーン）とデバイス更新（ノート PC）の 2 つの依頼が混ざっていますが、最終回答は次のとおりでした。

- PC がクラッシュしていることを認める。
- 新しいノート PC の選択肢を示す前に、まずトラブルシューティングの手順を提示する（新しいハードウェアの取り外し、セーフモードでの起動、それでも直らなければ別の手順）。
- それでも解決しなければ、選べるデバイスを案内する。

標準ハーネスなら台本化が必要だった多くの論理を、エージェントが処理していると説明しています。

### 6.4 標準ハーネスとの比較

同じシナリオの標準ハーネス版のエージェントを見せました。

- スキルがないため、トラブルシューティングの手順をすべて指示に書いてある。メッセージごとに指示全体を取り込み、コンテキストウィンドウが大きくなり、やり取りのたびにトークンが増える。
- トピックを作る必要がある。「利用可能なデバイス」を尋ねる場合のトリガーのトピック、SharePoint リストからデバイスの項目を取得して保存する流れ、実際にデバイスを要求する別のトピックなどを、手で組み立てる。
- 同じ「ブルースクリーンで新しいノート PC が必要」を入力すると、ナレッジソースを検索するものの、段階的なトラブルシューティングには従わず、デバイスの確認の応答もない。計画ループがないためで、期待どおりにするにはトピックを追加して手作業で作り込む必要がある、と説明しています。

### 6.5 評価（Evaluate）

プレビュー画面で素早く確認できますが、本格的に試すのは Evaluate タブです。エージェントの単体テストに相当し、想定される質問と期待する回答を多数読み込み、自動実行して合否を出します。デモでは「トラブルシューティング品質」の評価を設定済みで、結果は **82%** でした。何かを見直す必要があることがわかる、という説明です。テストセットはエクスポートでき、追加の評価に使えます。

### 6.6 監視（Monitor）

公開後は Monitor タブで、1 日のユーザー数、成功率、チャットの平均時間などを確認でき、個々のセッションで質問と結果も見られます。

### 6.7 公開と動作確認

1. デプロイ先のチャネルを選ぶ。Microsoft 365 と Teams にネイティブに公開できる。Microsoft 365 や Teams の外で使う場合は、アプリのオプションで埋め込みコードを取得し、公開 Web サイトやアプリに埋め込める。
2. 今回は Microsoft 365 と Teams を選んで公開した。
3. Teams に切り替えると「IT concierge」というエージェントが表示される。
4. 「パソコンが遅いのを直すには」と曖昧な質問をして、エンドユーザーの体験を示した。

最初から作って 10〜15 分ほどだったと述べています。

### 6.8 補足：プレビュー中の自然言語による作成

copilotstudio.preview.microsoft.com では、自然言語でエージェントを作れます。「IT ヘルプデスクのエージェントが欲しい」と入力すると、指示、必要なスキル、必要そうなツールまで作り、あとから調整できます。現在プレビューで、まもなく提供されると説明されました。これはデモではなく口頭での紹介です。

## 7. 注意点・発表者の気付き

- スキルを呼ぶかどうかは**説明文**で決まるため、何をするスキルか、いつ呼ぶかを詳しく書く。
- 既定では**すべての Web サイトを検索する**設定になっている。社内向けのエージェントでは、通常はオフにして範囲を絞る。
- 指示では、やることだけでなく、やらないこと（範囲外の質問に答えない等）を明示する。
- デバッグモードの思考表示は、公開後のエンドユーザーには見えない。
- Work IQ は既定のツールだが、権限は機能ごとに読み取り専用にしたり、オフにしたりできる。
- Evaluate で 82% だった例のように、結果が低ければ原因を調べて直す。
- 自然言語での作成はプレビューで、一般提供の時期は発表では示されていません。

## 8. 利用者にとっての利点

- 会話の経路を台本化せず、目的を書くだけでエージェントを作れる。
- 失敗やエラーからの復旧がハーネスに組み込まれている。
- ツール呼び出しが動的に決まり、説明を書き込む手間が減る。
- スキルで指示を短くでき、トークンの使用量を抑えられる。
- Work IQ により、Microsoft 365 のデータを追加設定なしで利用できる。
- 評価（Evaluate）と監視（Monitor）で、公開前後の品質を管理できる。
- 発表者のデモでは、最初から 10〜15 分ほどでエージェントを作り、Teams で動かした。

## 9. まとめ

ハーネスはエージェントとモデルの間の実行基盤で、Copilot ハーネスは、推論を要する複数ステップの作業に向いています。指示、ナレッジ、スキル、ツール、ワークフロー、サンドボックスで構成し、計画、実行、評価、再計画の流れでエージェントを動かします。デモでは、スキルとツールで作った IT サポートエージェントが、ブルースクリーンとノート PC 要求の混在した依頼を、標準ハーネスより適切に処理しました。学習リソースとして、発表者のチームが作る無料の実践教材「Agent Academy」が紹介されています。入門の「Recruit」、中級の「Operative」の 2 つのコースと、DocuSign MCP との統合やカスタム MCP 連携などを個別に学べる「Special Ops」ラボがあります（短縮 URL は音声からは確認できません）。

発表の中で質疑応答の時間は設けられず、質問は発表後に会場の廊下で受けると案内されました。
