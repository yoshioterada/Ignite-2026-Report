# THR1018 Creating agent-ready data with Azure SQL Hyperscale & Microsoft Fabric

## 1. はじめに

このセッションは、「エージェントが使えるデータ（agent-ready data）を用意するには、レイクハウスのような大がかりな基盤が必要だ」と考えている人に向けた、25 分の短い登壇です。想定している聴衆は、Azure SQL や SQL Server を持ち、Fabric も持っているものの、Fabric は Power BI のレポートにしか使っていない、という組織の人たちです。

登壇者は、すでに手元にあるものを使って、トランザクションの変更をリアルタイムなイベントとして Fabric に流し、異常を検知して行動につなげる方法を示します。鍵になるのは **Change Event Streaming（CES）** で、Azure SQL と SQL Server 2025 から、コミットされた変更をイベントとして Fabric の Event Stream に送り出す機能です。発表の時点でプレビューです。

セッションの中盤で、画面を使ったライブデモが行われます。チケット販売のデータに、Bot によるものと見立てた異常な販売が混ざった状況を、T-SQL のループで作り、Fabric の Event House で KQL を使って検知します。デモは約 7 分で、登壇者は、編集した動画ではなくすべてライブだと強調しています。

## 5. 発表内容の詳細

### 5.1 背景：置き去りにされるトランザクション系

登壇者は、多くの顧客が「agent-ready なデータが必要だ」と言うので、「それはどういう意味か」と尋ねると、「分からないが、準備しておく必要はある」と返ってくる、と話します。経営層からは、「エージェントは自分のために何ができるのか」「なぜエージェントが間違ったことを言うのか」「昨日ではなく今起きていることに、どうエージェントを反応させるのか」といった問いが来ます。

そこで登壇者は、トランザクション系から Fabric への流れに焦点を当てます。トランザクションシステムは、分析系やレポートにデータを供給する心臓部です。それでも、データをエージェントで使えるようにする議論では置き去りにされがちだ、と指摘しています。

### 5.2 agent-ready data の 4 つの原則

登壇者が顧客との会話から整理した 4 つの原則です。

| 原則 | 説明 |
| --- | --- |
| Fresh（新鮮） | 起きたとおりにデータが届くこと。エージェントは過去のデータにも反応できるが、少なくとも一部のデータは、起きている最中に反応したい。すべてのイベントが重要なわけではなく、重要なものを見極める |
| Grounded（根拠づけ） | Fabric データエージェントに、指示、ルール、ガードレールを与え、既知の事実に基づいて回答させる。信頼できるデータを渡すことで、ガードレールが機能する |
| Isolated（分離） | このデモでは、Fabric の Event House に置く。ただし、Lake house でも同じことができ、自社の考え方はこのスタックに限らない |
| Actionable（行動可能） | Activator、Foundry のエージェント、あるいは人間が、「人間さん、この問題を見てください」のように、問題を示す条件を検知して動ける |

> 補足：登壇者は、このセッションでは Fabric データエージェントのデモは行わない、と明言しています（デモはあくまで Event House と Activator 周辺です）。

登壇者は、Event House が Kusto エンジンの上に構築されていることにも触れています。Kusto は、長年 Azure Data Explorer の基盤となってきたエンジンで、15、16 年ほど前（本人の記憶による言い方です）に Xbox Live のログと Skype のテレメトリを軸に作られた、と説明し、Microsoft が書いた中で最も格好いいデータベースエンジンだと評価しています。Fabric では新しく見えますが、SQL Server ほど成熟してはいないものの、それに近い成熟度だという評価です。

### 5.3 Change Event Streaming（CES）とは

CES は、Azure SQL と SQL Server 2025 にある機能で、トランザクションがコミットされた瞬間を**イベントとして外へ押し出す**（push する）ものです。登壇者は「ブロードキャスト」と言いたくなるが、リーダー層は公開インターネットにデータが流れると思ってしまうため、実際には Fabric の Event Stream に接続する「emit（発行）」だと言い換えている、と話します。

**プレビューである点には注意が必要**です。登壇者は、Microsoft では状況がいつ変わるか分からないと断りつつ、本番で使っている人もおり、うまく動いていると述べています。

対応範囲は次のとおりです。登壇者は Hyperscale を「Azure SQL で最高のアーキテクチャ」と考えており、ここでは Hyperscale を前面に出していますが、Azure SQL Database のすべての tier で動作します。

- Azure SQL Database（全 tier）
- Managed Instance
- SQL Server 2025（制限付き）
- Fabric（発話は「SQL database and Fabric as well」で、Fabric のどの機能を指すかは音声からは確定できません）

CES を動かす手順は 3 つです。

1. **Stream group を作る**：どのテーブルを追跡するかを指定します。ビジネス、エージェント、人間が行動する必要のあるトランザクションが発生するテーブルです。
2. **Event Stream に接続する**：Fabric の Event Stream につなぎます。Fabric をまだ使っていなくても、Azure を使っていれば Azure Event Hub に接続できます。
3. **消費側が反応する**：受け取った側が、イベントに何らかの反応をします。保存する、分析する、コマンドセンターのリアルタイムダッシュボードで人が傾向を見る、あるいはエージェントや Fabric の Activator が「条件を満たしたので行動が必要」と判断して動く、といった形です。

従来の変更追跡技術との違いは、CES が push 型である点です。変更を知るために問い合わせる必要がなく、トランザクションが起きると、それを Cloud Event としてパッケージ化して送り出します。

変更された**行ごと**に、トランザクションのタグを付けた Cloud Event が Event Stream に送られます。100 行をコミットすれば 100 個のイベントです（よく聞かれる質問だと登壇者は言います）。タグがあるため、100 万行を更新するクエリでも、後で共通の糸をたどってグループ化できます。デモでは使わないものの、監査目的での追跡にも使える、という説明です。

### 5.4 CES と CDC の違い

登壇者は、「Change Data Capture と何が違い、なぜ良いのか」とよく聞かれると言い、次の違いを挙げます。

| 観点 | Change Event Streaming（CES） | Change Data Capture（CDC） |
| --- | --- | --- |
| 取得の方向 | データベースがイベントを**押し出す（push）** | 利用者が**取りに行く（pull）**。時刻 X から Y の間に何が変わったかを問い合わせる |
| 時間軸 | ほぼリアルタイムで動ける | 過去を見る。ほぼリアルタイムでは動けない |
| 単位 | 変更行ごとに 1 イベント。トランザクション ID でタグ付けされ、グループ化できる | 似ているが、トランザクション ID でそこまで結びつかず、タイムスタンプで突き合わせる必要があり、厄介になりうる |
| 保存先 | Azure Event Hub または Fabric Event Stream | データベース内 |
| 負荷 | 軽量で、オーバーヘッドは小さい | リソース不足のデータベースでは、ストレージと、おそらく CPU にも大きな負荷が掛かる |
| 目的 | イベント駆動のデータ基盤、agent-ready なデータ、リアルタイムな行動 | 変更履歴。スケジュールで照会し、レポートを出したり誰かに通知したりするが、見るのは過去 |

登壇者は、CDC より古い change tracking にも触れ、同様に「X から Y の間に何が変わったか」を聞きに行く必要があると説明しています。また、低レイテンシのデータでなくても、トランザクションデータを同じようにストリームできる、とも述べています。

### 5.5 アーキテクチャ

流れは次のとおりです。

1. **Azure SQL Database**：CES を有効にします。セットアップは 1 時間のセッションで扱う内容で、今回は省略するので「信じてもらうしかない」と述べています。
2. **Fabric Event Stream**：Fabric の Real-Time Intelligence にデータが入る入り口です。ここでは軽い**インフライト変換**ができます。演算子（operators）を追加すれば、データが流れる途中で変換できます。「ETL の別の方法に見えるが、変換はどこで行うのか」という疑問への答えです。シルバー層のような層に一度置き、変換して取り出し、別の場所へ送る必要はありません（置いても構いません）。すべては、リアルタイムまたはほぼリアルタイムを追求するためです。
3. **Event House**：Kusto 上に作られており、**KQL** で照会します。T-SQL でも照会でき、性能はほぼ同等です。登壇者は、KQL は怖くなく、T-SQL に慣れている人が KQL を学ぶコツも紹介すると予告しましたが、本編ではそのコツの説明は確認できませんでした。
4. **Activator**：Fabric で条件の発生を監視する仕組みです。「値が X を超えたらこうする」だけでなく、「ある範囲に一定期間とどまった」といった条件も書ける、豊富なルールを持ちます。登壇者は、作成方法は示せるが、実際に発火させる時間はない、と述べています。

登壇者はここで、友人の Chris Schmidt 氏（音声認識による表記）が作った言葉として **action systems（アクションシステム）** を紹介します。レポートではなくイベントに反応するシステムのことです。多くのデータ基盤は、レポートと過去分析のために作られており、リアルタイムな行動やエージェント活用は想定していません。

イベントが流れてきたときの処理は 3 段階です。

1. **検知**：探している条件が発生したかどうか。データ品質の異常、何かの温度、想定より多い行数など。自分の ETL で探したい条件を考えてみてほしい、と登壇者は言います。
2. **評価**：設定したルールとしきい値に照らす（良い、悪い、緑・黄・赤など）。
3. **行動**：Activator で、Teams のメッセージやメールを送る（「人間さん、これを見てこうしてください」）、API を呼ぶ、他の Fabric の成果物を呼び出す、など。データの品質問題が頻繁に起きるのでノートブックを書いて修復している場合、そのイベントを検知してノートブックを実行し、人が介在せずに修復することもできます。さらに Foundry のエージェントまで広げれば、「ほとんど何でもできる」と述べています。これが「洞察から行動へ」のループを閉じる、という説明です。

### 5.6 Fabric を使えない場合の代替

Fabric がない場合でも、近いことはできると登壇者は述べます。

- **Azure Event Hubs**：Fabric の Event Stream は、これを SaaS として提供したものに近い、という趣旨の説明です（発話が不明瞭で、この意味かどうかは確定できません）。
- **Azure Stream Analytics**：デモで示した内容の多くができます。
- **Azure Data Explorer**：Event House が SaaS として提供する Kusto であるのに対し、Azure Data Explorer は PaaS として提供する Kusto で、制御は増えますが簡単ではありません。
- **Azure Functions と Logic Apps**：デモに近い処理を実現できます。

### 5.7 持ち帰りの要点（セッション末尾）

登壇者はまず、バッチを必要のない場面で続けるのをやめようと呼びかけます。

- ETL は死んでいないが、リアルタイムで行動したいデータはストリームにする。
- この方式は**デフォルトでインクリメンタル**です。登壇者の顧客には、ベンダーに安く作らせたウェアハウスがインクリメンタルになっておらず、後で苦労するケースがあるという話です。
- ソースに負荷を掛けず、SQL にあまり多くを求めません。インフライト変換もあります。

そのうえで、持ち帰る 5 点は次のとおりです。

1. agent-ready なデータは fresh、grounded、isolated である（このまとめでは 3 つが読み上げられました。actionable は 5.2 で 4 つ目の原則として挙げられています）。
2. すべてのコミットは、イベントにできるだけでなく、すでにイベントである。業務に重要かどうかを決めればよい。
3. **CES は CDC ではない**。片方しか知らなかった人は、これで両方を知ったことになる。
4. **システム・オブ・レコードにエージェントを置かない**。登壇者自身は、SQL データベース内にエージェントを置かず、Fabric 上のデータに対して、自分が指示した統制された行動を取らせています。これが正しいかどうかは議論の余地がある、とも述べています。
5. Fabric はイベントを行動に変えられる。そのために Azure SQL を活用できる。

## 6. デモ・手順

デモはライブで行われ、登壇者は、編集した動画でも、ごまかしでもないと述べています。画面上の細部は音声からは確認できないため、語られた範囲で整理します。

**シナリオ**：夏に米国で開催された大型のサッカー大会を題材に、**チケット販売の異常（Bot 活動）**を検知する、という設定です。商標への配慮から、登壇者はブログや LinkedIn では「global glass」と呼んでいるそうです（実際の大会名ではありません）。データ品質などの異常検知にも置き換えられる、と補足しています。

1. **構成の前提**：Azure SQL Database で CES が有効になっています。Fabric の Event Stream を経由して Event House に流れます。セットアップは見せません。
2. **ベースライン（約 90 秒）**：T-SQL のループを実行します。通常のチケット販売を、1 秒あたり約 1〜1.5 件でテーブルに入れます。登壇者は、このコードは「ごく単純なループ」だと言います。
3. **Bot の模擬（約 30 秒）**：2 回目のラウンドとして、1 秒に 1 件の販売ではなく、100、200、250 件へ増やして Bot の活動を模擬します。これもテーブルに入れるだけの T-SQL ループです。
4. **通常に戻す（約 30 秒）**：大きな画面でスパイクが見やすいよう、あえてトラフィックを通常に戻します。人工的な設定だが、異常が際立つようにするためだと説明しています。
5. **Event House で KQL を実行**：KQL のクエリを説明します。グラフを見やすくする工夫（色の変更など）が入っています。注目すべきは、下から 4 行目あたりにある関数 **series_decompose_anomalies**（登壇者の発音は「series decompose anomalies」）で、KQL に組み込まれた異常データの識別機能です。クエリを実行すると、まず視覚的な分析として結果が表示され、**赤いスパイク**が現れます。直近 15 分を振り返る設定で、15 分の終わりのほうにスパイクが見えます。
6. **数値を返すバージョン**：画像ではダッシュボードやアラートの元にできないため、少し違うバージョンのコードを実行します。ここでは異常スコアが **2 を超えたものを表示**する出力になっており、今回の大きなスパイクでは **異常スコア 274** となりました。登壇者は、これは必ずフラグを立てるべき異常だと述べています。
7. **アラートの追加（Activator）**：グラフの結果には「Add alert」が灰色になっており追加できません。Activator は画像を理解できないためです。数値の結果からは Add alert ができ、アラートを作る画面には、元になるクエリと、実行できる動作（メッセージの送信、さまざまな Fabric の成果物の呼び出しなど）が表示されます。登壇者は、嘘ではないと分かるようにその一覧を見せています。アラートを実際に発火させる操作は、時間の都合で行っていません。
8. **ねらいの説明**：人を完全にループに残すことも、完全に外すこともできる、と登壇者は述べます。これを Azure SQL Database（または SQL Server）だけで実現している、というのがデモの趣旨です。実時間で約 7 分程度のこの流れが、顧客の言う「agent-ready なデータ」の具体例だ、と締めています。

デモのコードは T-SQL を含めて約 200 行で、登壇者は友人の Claude にコードの一部を書いてもらい、点を赤くしてもらった、と冗談交じりに話しています。

## 7. 注意点・発表者の気付き

- **CES はプレビュー**：Microsoft ではいつ状況が変わるか分からないと断ったうえで、本番利用者もいてうまく動いていると述べています。
- **すべてのイベントが重要なわけではない**：どのイベントが業務に重要かを見極める必要があります。
- **「ブロードキャスト」は誤解を招く**：公開インターネットに出ると誤解されるため、「emit」と言い換えています。
- **変更行ごとにイベントが出る**：100 行のコミットは 100 イベントです。
- **CDC は負荷が大きくなりうる**：リソースが不足したデータベースで CDC を多用すると、ストレージとおそらく CPU の負荷が増えます。
- **グラフには Activator のアラートを設定できない**：アラートの元には数値を返すクエリが必要です。
- **システム・オブ・レコードにエージェントを置かない**：登壇者の流儀であり、議論の余地があることも認めています。
- **アーキテクチャの前提**：ここでの isolated の例は Event House ですが、Lake house でも同様にできます。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- Fabric を Power BI にしか使っていない組織でも、持っている Azure SQL / SQL Server と Fabric で、agent-ready なデータを用意できる。
- コミットの時点で変更をイベントとして押し出すため、翌朝のバッチではなく、起きているときに反応できる。
- CDC と比べて軽量で、ソースへの負荷が小さい。
- データが流れる途中で変換でき、ETL の別層を作る必要がない（インフライト変換）。デフォルトでインクリメンタルである。
- 異常の検知から、通知、API 呼び出し、ノートブックによる自動修復までを、人が関与するかしないかを選びつつ構成できる。
- Fabric を使えない場合も、Azure Event Hubs、Stream Analytics、Azure Data Explorer、Azure Functions、Logic Apps で近いことができる。

## 9. まとめ

トランザクションのコミットは業務上のイベントであり、Azure SQL と SQL Server 2025 の Change Event Streaming（プレビュー）を使えば、それを Fabric の Event Stream に押し出せます。agent-ready なデータの条件は、fresh、grounded、isolated、actionable の 4 つです。

デモでは、模擬のチケット販売データを SQL に入れ、Event House の KQL（series_decompose_anomalies）でスパイクを検知しました。異常スコアは 274 で、数値を返す形にすれば Activator のアラートの元にできました。

CES は CDC と違い、押し出す方式で、軽量で、変更行ごとにイベントを出します。登壇者は、ETL は死んでいないが、必要のないバッチはやめ、エージェントはシステム・オブ・レコードではなく Fabric 上のデータの側に置く、というスタンスで話を締めています。
