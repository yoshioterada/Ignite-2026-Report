# THR925 From prompt to production: Build a Fabric app live

## 1. はじめに

このセッションは、Microsoft Fabric 上で動くアプリを、コーディングエージェントに作らせながらライブで見せる発表です。登壇者はまず、Fabric Apps とそのフレームワーク／SDK である **Rayfin**（表記については 2 章の補足を参照）の位置づけを数枚のスライドで説明します。その後、2 つのエージェント環境でそれぞれ別のアプリを同時に作らせ、どちらが先に仕上げるかを競わせる形でデモに進みます。

発表の主張は、**エージェントによる開発の速さと、IT 管理者や CISO が求めるガバナンスは両立できる**という点です。アプリが接続できるサービスはアプリケーション定義に静的に書かれていて、エージェントが勝手に接続先を作れません。また、作ったアプリは何度でも同じ形でデプロイできます（deterministic）。デモでは、簡単なプロンプトから約 10 分でレポートアプリを動かすところまで進みました。

このセッションには**画面を使ったライブデモがあります**。ただし録音は音声のみなので、画面の細部は音声からは確認できません。本書では、登壇者が語った範囲に絞って書いています。

## 4. 発表者が伝えたいメッセージ

登壇者がまず示した課題は、開発者やビルダーはできるだけ速く作りたい一方で、データが無秩序に扱われてはいけない、という両面の要請です。例として、データがランダムなサイトの HTML レポートに直接書き出されるような状況は避けたい、と語っています。そこで「速く、しかも安全に作れて、管理しやすい」仕組みとして位置づけられたのが、Rayfin と Fabric Apps です。

もう 1 つの主張は、**エージェントがフロントエンドの作成を劇的に簡単にした**ことです。会社のスタイルガイドラインに合わせることも、ビジュアルを少し調整することも、いまでは容易です。難しいのは、その新しいフロントエンドを、独自のアプリ登録を作り、スコープを決め、CISO に承認してもらうといった手間なしに、データへ安全につなぐことだとして、それを「ターンキーで簡単にする」のが Rayfin SDK の役割だと説明しています。

最後に、登壇者は「エージェントによる生産性と、きちんと統制された状態の両方が得られる」とまとめています。エージェントが作ったものを別のワークスペースに向けて `up` すれば同じアプリが同じ形で立ち上がる、という点がその根拠として語られています。

## 5. 発表内容の詳細

### 5.1 Fabric と Fabric Apps の位置づけ

登壇者は冒頭で、会場に「今日 Fabric を使っている人」「Fabric アプリをデプロイしたことがある人」を挙手で尋ね、2 つ目の質問のあとに「だから皆さんは学びに来たのですね」と述べて、本題に入っています。

Fabric は統合データプラットフォームです。Power BI のような製品を使ったことがあれば、それが Fabric の土台になっている、と説明しています。データベース、Data Factory、データウェアハウス、巨大な **OneLake** をサポートし、ビジネスのあらゆるデータを置く統一的な場所になります。

### 5.2 Rayfin（フレームワーク／SDK）と Fabric Apps（ホスト）

登壇者は、ASP.NET と App Service にたとえています。**Rayfin** はアプリを作るためのフレームワークと SDK で、ASP.NET に当たります。**Fabric Apps** はそのアプリをホストする側で、App Service に当たります。

Fabric Apps は Fabric のワークスペース内で動き、Fabric のキャパシティを使えます。加えて、Power BI Pro ライセンスのワークスペースと、Copilot Credit のワークスペースでも使えることが発表済みだと説明しています。支払い方法は複数あるが、ほとんどの人は通常の Fabric キャパシティを使うことになるとのことです。

アプリ自体と、アプリが作る子アイテムはすべて、その Fabric キャパシティの中に置かれます。Azure 側に別途置かれるものではない、という説明です。アプリが接続する先は、他のワークスペースにあっても構いません。ただし、アプリが作るものはすべてそのアプリの子アイテムになります。

### 5.3 アプリモデルと GA 時点のサービス

Rayfin SDK は単なる SDK ではなく、アプリケーションモデルでもあります。このモデルには、アプリが利用するサービスが定義されます。登壇者は、レビュー担当のエンジニアにとって重要な点として、**アプリが接続するサービスや持つ機能がすべて静的に定義されている**ことを挙げています。そのため、エージェントが接続先を勝手に作り出すことはできません。エージェントにとっても、何ができて何をすべきかを見つけやすくなります。

また、実際のアプリでは Pull Request を出し、SDLC プロセスを通すべきだとしたうえで、最も機微な部分であるサービスコントラクトが簡単に検査できるとも述べています。コントラクトは、各サービスをモデル化したものです。

GA（発表では「今日の GA」と述べています）時点のサービスは次のとおりです。

| サービス | 説明（登壇者の説明） |
| --- | --- |
| data | データベースと、その上に載る GraphQL レイヤー。GraphQL には「Data API Builder」として知られる技術を使う |
| Fabric single sign-on | 独自の Entra アプリを作る代わりに、Fabric アプリに関連付けられた RBAC でアプリへのアクセスを制御する |
| storage、functions、hosting | バックエンドでの処理や、任意のファイル・画像などの保存に使う（それぞれの詳細な説明は語られていません） |
| connectors | ライフサイクルの外で管理されるデータへの接続。ほとんどの人が最初に使うのはセマンティックモデル |

> 補足：「独自の Entra アプリ」は、音声では "enter app" と聞こえます。文脈から Entra のアプリ登録を指すと解釈しています。

登壇者は、最初に使うコネクタはセマンティックモデルだろうと述べました。Power BI レポートを見栄えよくしたい人が、セマンティックモデルをエージェントにプロンプトとして渡す、という流れです。

### 5.4 Fabricator：Rayfin 向けのオープンソースのハーネス

登壇者は、デモで使う新しいプロジェクトとして **Fabricator** を紹介しています。Rayfin 用のオープンソースのハーネスで、**GitHub Copilot CLI SDK** を使っています。「結局は GitHub Copilot であり、他の GitHub Copilot の利用と変わらない」が、Fabric のリソースと Rayfin を理解するように最適化されている、という位置づけです。たとえば、アップグレードがあることを知らせるといったコンテキスト情報も出せます。

Fabricator は他のコーディングエージェントでも使えるようにしたい、というのが登壇者の考えです。Claude や、"whatever Grok is doing" といった他のエージェントでも使えると述べ、エージェントごとの性能の差は、主にビジュアルの扱い方だけで、あとはエージェント自体の能力次第だと説明しています。

### 5.5 デモの設計：2 つのアプリの競争

デモでは、**Fabricator** と **GitHub Copilot アプリ**で、2 つのプロンプトを走らせ、2 つのアプリを同時に作ります。プロンプトの全文は読み上げられていません。

- **GitHub Copilot アプリ側**：自分のチーム向けの「launch control dashboard」を作る。ローンチの準備のチェックリスト項目（マーケティングへの連絡、セキュリティレビューなど）を全員で確認・マークできる簡単なダッシュボードで、従来の読み取り専用の Fabric 分析アプリではなく、CRUD が中心。
- **Fabricator 側**：セマンティックモデルを使うレポートアプリ。セマンティックモデルは AdventureWorks のサンプルデータセットをアップロードしたもの。リーダーシップと共有し、レポートにコメントを残せるようにする。リーダーが会議を待たずに、事前に質問やフォローアップをレポートに書き込めるようにして、情報とコンテキストを同じアプリに集約する、という狙い。

登壇者は、2 つの環境は「同じフォルダをコピーして同じ状態から開始した」と述べています。また、2 つの実行の本当の違いは、一方で **Copilot Fusion**（聞こえた表記のまま）を選び、他方では標準的な Claude Opus モデルを使ったことだと説明しています。そのため、挙動に大きな差があっても、Fabricator と GitHub Copilot の差というより、モデルごとの問題へのアプローチの違いによるものだ、という留保を付けています。

### 5.6 デモ中に起きたこと

#### Fabricator 側

- 新しいアプリを用意して実行すると、多くのスキルを読み込みます。Rayfin で Fabric アプリを作ると分かっているため、開いた直後からアプリのレンダリングを始め、待ちません。
- 別の古いサンプルに切り替えると、コールドセッションでも即座にアプリを読み込みました。作業中は、切り替えても状態がローカルに保持されますが、アプリを閉じると、プロセスに「続けるよう」指示する必要がある、と説明しています。
- 登壇者は、これはセッションコンテキスト管理の新機能ではなく、ハーネス自体の挙動だと強調しています。
- 渡されたワークスペースとセマンティックモデルの名前から、Fabric 内のモデルを探し出し、スキルを実行してスキーマを取り出し、DAX クエリを作りました。プロンプトでは「トレンドの内訳」「ランキングのサマリー」程度しか指示していないため、どんなデータ型があるかをコンテキストから判断し、どんなグラフを出せるかを決める必要があり、そのためのスキルだと述べています。
- 次に、表示するビジュアルの計画を立てました。Fabric 向けに出荷しているビジュアルがあり、Vega ライブラリへのプロンプトを工夫しなくても、データが最初から見栄えよく表示されるとしています。
- GA に合わせたリリース（バージョン表記は音声では聞き取り不明瞭です）で、エージェントからシグナルを受け取れるビジュアルが加わりました。ローカルで動かしている間、テンプレートに実際に何が起きているかを示す表示で、別のシステムブラウザで開くこともできます。
- 自分で「warm paper と navy ink」という視覚的アイデンティティのテーマを決めた点も紹介されています。

#### GitHub Copilot アプリ側

- 多くのスキルを読み込みました。こちらは「汎用のセッション」で、何を作るのか、アプリをどう起動するのか、接続先はどこかを自分で見つける必要がありました。サンプルデータも渡していないので、データモデリングやビジネス領域・オブジェクト領域の整理を自分で行いました。
- Rayfin で使える機能を読み取り、データモデルを検討し、アプリ設計や UI を考えました。登壇者は、人間が本来自分で考えて配線したりプロンプトしたりする部分が、テンプレートとして最初から用意されていると述べています。
- Fabric のサインインの背後に置き、launch list とチェックリスト項目の両方に Rayfin を使うと決めました。コードを書き、ワークスペースを確認し、実装を進めました。

#### 生成されたコードの確認

- Fabricator は、ヘルパー、ステート、データレイヤーの型を書き、裏で TypeScript のチェックを実行しました。
- Rayfin のすべての型は **TypeScript でモデル化**されています。理由は、単純なコンパイルでサービス間のコントラクトの一貫性を検証でき、TypeScript は高速にコンパイルでき、壊れても明確なエラーが出るためです。人間のレビューでも、GitHub で読むにも、VS Code の IntelliSense で関係を見るにも、既存のツールが充実していると説明しています。
- packages の data の下には、今回のデモ用に、フォローアップ用のデータの型が作られていました（音声では「text model」と聞こえます）。`rayfin up` を実行すると、コードファーストでデータベースのスキーマ移行が行われ、title、owner、due date、notes などを持つ「follow up」テーブルが作られます。のちにプロパティを追加してデプロイすれば、**既存のデータを保ったまま、スキーマ移行も処理される**と述べています。
- 続いて型チェックと軽い lint を実行しました。スキルが含まれているのは、管理しきれないコードを書かせないためで、1 ファイルの簡易サンプルをまとめて書くのではなく、長期的にリファクタリングを重ねなくても拡張できる設計になっている、という説明です。

#### 結果

- 登壇者は GitHub Copilot 側に、ローカルで起動するよう指示を足しました（どのエージェントでも誘導できる、という例示です）。GitHub Copilot 側がローカルのキャンバスを起動しようとして、プレビューのリスナーを確認し、computer use を使うかどうかを考えている間に、Fabricator はダッシュボードの実装を終え、ライブ UI を描画しました。登壇者は、セッションの開始から 6〜8 分ほど経ってから始めたと述べ（発話のまま）、**約 10 分で簡単なプロンプトからレポートアプリ一式まで作れた**としています。
- Fabricator のグラフでは、Y 軸が異様に長くなり、ページが非常に長くなる問題が出ました。登壇者は原因を調べましたが、その後 Y 軸は修正され、正しく表示されました。
- 修正後のアプリでは、データ項目をクリックしてフォローアップを作成できます。さらに登壇者は、画面をポイント＆クリックで指す形で、特定のデータ項目に紐付かない汎用のフォローアップを作る機能を追加したいという例を挙げています。キャンバス上での指示がどこまで実行されたかは、音声からは確認できません。
- もう一方のエージェントは、登壇者の意図と違う場所で開こうとしたり、追加の指示を実行しなかったりしました（どの場面がどちらのエージェントかは、音声だけでは判別しにくい箇所があります）。登壇者は、自分の指示に誤りがあったようだと述べ、手動で進めています。
- 最終的に登壇者は、Fabricator が「明確な勝者」だったと述べています。

> 補足：このセッションの録音からは、GitHub Copilot 側のアプリが最終的に完成したかどうかは確認できません。

### 5.7 キャンバスのスクリーンショットと Playwright

登壇者によると、Fabricator と GitHub Copilot アプリには、組み込みのキャンバス体験があり、エージェントがスクリーンショットを撮れます。どのターミナルやエージェントでも Playwright を起動して同じスクリーンショットを撮れますが、Playwright のインスタンスを立ち上げる時間の分だけ遅くなります。そのため、レポート系アプリで多くを占める色の調整、書式の調整、テキストやタイトルの変更といった仕上げでは、このビジュアル指向の環境のほうが、ポイント＆クリックと描画で素早く反復できると述べています。

### 5.8 `rayfin up` と `rayfin dev`

CLI の大きなコマンドは 2 つです。

| コマンド | 内容（登壇者の説明） |
| --- | --- |
| `rayfin up` | アプリの実行に必要なものすべてを、Fabric へ完全にデプロイする |
| `rayfin dev` | コード関連はローカルマシンに残し（ブレークポイントを置いたり素早く繰り返したりできる）、データなどステートを持つものは Fabric 側に置く、ハイブリッドのローカル／リモート開発モード |

`rayfin dev` を実行すると、必要なスキーマ変更などだけをデプロイし、ローカルで動くプロキシを立てます。ローカルで動く Vite プロセスと、Rayfin の functions 用のローカルプロセスに振り分け、それ以外はリモートで動き、**1 つのコマンド**で全体が連携して立ち上がると説明しています。

> 補足：コマンド名は、音声では「Raifin up」「Raven dev」などと聞こえます。コード表記は、本書でのフレームワーク名の表記に合わせたものです。

### 5.9 Rayfin DevTools

登壇者は、**今週木曜**（Thursday）に出る予定のプレビュー機能として **Rayfin DevTools** を紹介しました。Fabricator には、アプリが使うサービスの「ブループリント」があり、データモデルを見たり、実際のデータを確認したりできる **data explorer** があります。登壇者は follow-ups を開き、アイテムを 1 件挿入したうえで、ブループリントのデータエクスプローラーに表示されるはずだと説明しました（デモの音声からは、表示の結果までは確認できません）。データ、ビルダー、エージェントが 1 つの体験に収まる点を利点に挙げています。

さらに、Fabricator に限定せずにどのエージェントでも使えるよう、同じ概念をアプリ自体に埋め込めるようにしました。Rayfin DevTools のリンクをクリックすると、同じアプリの中で開きます。それを示すため、localhost の URL を Edge ブラウザで開き、通常の Edge でも同じローカルの開発ツールが使えることを見せています。そこでは、まだデプロイされていないデータソース（登壇者は「まだデプロイしていないようだ」と述べています）を、デプロイ後に探索できること、ローカルの functions を確認できること、全体のアーキテクチャ（有効になっているサービスとデプロイ済みのスキーマ）が見られることを説明しています。

### 5.10 始め方と連携先

登壇者は、「どう始めればよいか」とよく聞かれると述べたうえで、**好きなアイデアを選んで好きなエージェントハーネスに投げるか、Fabricator を試す**ことを勧めています。エージェントは、これらの組み合わせに関する調査や判断の多くを自分で行うよう設計されています。ただし、不透明で壊れやすい作り方ではなく、作られたものを**別のワークスペースに向けて `up` すれば、まったく同じ形でアプリが立ち上がる**ことを示しました。「緩く接続されているだけでなく、毎回 deterministic にデプロイできるよう設計されている」と述べています。エージェントの生産性と、開発マネージャーや CISO などが求める統制の両方が得られる、という主張です。

次に試してほしいこととして、次の点が挙げられました。

- どのコーディングエージェントでも使える。
- **Replit** との連携がある。Replit を使っている場合は、Replit から直接統合して操作できる。
- 「Scout」から使える（発話のまま。音声認識の都合で製品名の確認はできません）。
- **Copilot** の中でも使えるようになった。GA が発表された **Copilot managed runtime** とあわせて使える。
- ソースは GitHub で公開されており、問題や機能要望は `github.com/microsoft/rafin`（聞こえた表記のまま）に issue として出せる。登壇者は Microsoft Fabric の subreddit でも質問に答えている。
- Rayfin に関するセッションが他にも多数ある。（録音はこの案内の途中で終わっています。）

## 6. デモ・手順

ライブデモが行われています。録音は音声のみのため、語られた順に、語られた範囲で整理します。

1. 2 つのプロンプトを用意した。1 つは GitHub Copilot アプリで launch control dashboard を作る（CRUD 中心）。もう 1 つは Fabricator で、AdventureWorks のセマンティックモデルを読むレポートアプリ（リーダーシップがコメントを残せる）を作る。
2. 2 つの環境は、同じフォルダをコピーして同じ状態から開始し、それぞれにプロンプトを実行した（一方は Copilot Fusion、他方は標準的な Claude Opus を選択）。
3. Fabricator はスキルを読み込み、Rayfin アプリであることを前提にアプリをすぐ描画し始めた。別の古いサンプルへ切り替えても即座に読み込まれた。
4. Fabricator は、ワークスペースとセマンティックモデル名からモデルを見つけ、スキーマと DAX クエリを作り、表示できるグラフを判断して、ビジュアルの計画を立てた。
5. GitHub Copilot 側は、データモデリングから UI の設計までを自分で行い、Fabric サインインの背後に置き、Rayfin で launch list とチェックリストを実装した。
6. Rayfin の型が TypeScript でモデル化されていることを、生成されたコードで説明した。`rayfin up` で、follow up テーブル（title、owner、due date、notes など）のコードファーストのスキーマ移行が行われる。
7. 型チェックと lint が実行された。GitHub Copilot 側はプレビューの起動を試みていた。
8. Fabricator が先にダッシュボードを描画した。Y 軸の問題が出たが修正された。データ項目からフォローアップを作れることを示し、汎用フォローアップの追加にも触れた。
9. `rayfin dev` で URI が得られ、ビルドの続行を指示した。Rayfin DevTools のブループリント、data explorer、Edge ブラウザでの表示を確認した。
10. Fabricator が競争に勝ったと述べて終了した。

> 補足：画面上のボタンやレイアウトの細部、プロンプトの全文は、音声からは確認できません。

## 7. 注意点・発表者の気付き

- **エージェントが出す結果にはばらつきがある。** デモ中にも、Fabricator の Y 軸が異様に長くなる問題や、GitHub Copilot 側が指示と異なる動きをする場面があったことが語られています。登壇者は、挙動に差が出た場合はモデルごとの問題の進め方の違いによる可能性が高いと、デモの冒頭で説明しています。
- **実際のアプリでは SDLC を通す。** アプリ定義でサービスやコントラクトが見えるとはいえ、Pull Request を出し、SDLC プロセスを通すべきだと述べています。
- **Fabricator でアプリを閉じたとき。** 作業中は状態がローカルに保持されますが、アプリを閉じるとプロセスに続行を指示する必要があります。
- **Playwright では時間がかかる。** ビジュアルの反復はキャンバス体験のほうが速い、という経験が語られています。
- **コード生成の品質。** 付属のスキルは、管理しきれない 1 ファイルのコードを書かせず、長期的に拡張できる構造にするためのもの、と説明されています。
- **DevTools はプレビュー。** Rayfin DevTools は今週木曜に出る予定のプレビュー機能です。
- 料金や制限事項の詳細（Fabric キャパシティの消費量など）は、発表では触れられていません。

## 8. 利用者にとっての利点

- フロントエンドのビルドが容易になり、会社のスタイルに合わせたビジュアルの調整も簡単になる。
- 独自のアプリ登録を作って CISO に承認してもらう手間なしに、データに安全につなげる（Fabric single sign-on と Fabric アプリの RBAC を利用）。
- アプリが使うサービスが静的に定義されているため、エージェントが勝手に接続先を作れず、レビュー担当者はサービスコントラクトを検査しやすい。
- Rayfin の型が TypeScript なので、コンパイルで一貫性を検証でき、人間によるレビューもしやすい。
- コードファーストでスキーマ移行が行われ、プロパティを追加しても既存データを保てる。
- 作ったアプリを別のワークスペースに向けて `up` すれば、同じ構成で再現できる。
- デモでは、簡単なプロンプトから約 10 分でレポートアプリが立ち上がった。
- アプリとその子アイテムは Fabric のキャパシティ内に置かれる（Azure 側ではない）。

## 9. まとめ

Rayfin は Fabric Apps で動くアプリを作るためのフレームワークと SDK で、アプリが使えるサービスを定義ファイルで静的に決めることで、エージェントによる高速な開発と、レビューしやすいガバナンスの両立を狙っています。ライブデモでは、オープンソースのハーネス Fabricator が、GitHub Copilot アプリより先に、AdventureWorks のセマンティックモデルを使ったレポートアプリを描画しました。

登壇者の勧めは、好きなアイデアを好きなエージェントに渡してみることです。Fabricator のほか、Replit、Copilot、Copilot managed runtime などから使えます。Rayfin DevTools は、今週木曜にプレビューとして出る予定です。
