# BRK350 Building high-performance analytics with Fabric Data Warehouse

## 1. はじめに

このセッションは、Microsoft Fabric のデータウェアハウス（Fabric Data Warehouse、以下 Fabric DW）を、AI エージェントがデータに大量にアクセスする時代に向けて、どう高速化し、どう運用しやすくしているかを紹介する内容です。前半では、GPU で分析クエリを実行する **GPU Accelerated Fabric DW** を取り上げます。ワークスペースの設定を 1 つ切り替えるだけで、クエリの書き換えもデータ移動もなしに高速化できるという説明で、画面を使ったデモと、同時実行ユーザー数を変えたときの比較結果も示されました。後半は、Ignite の週に発表された Fabric DW の機能追加を、SQL analytics endpoint の再設計、ワークロード管理、MCP サーバーとエージェント向けスキル、CI/CD、セキュリティ、移行、SQL 構文の拡張といった順で一気に紹介します。

発表の根底にあるのは、「エージェントは人間の分析者よりはるかに多く、はるかに短い間隔でクエリを投げてくるので、データ基盤の負荷の形が変わる」という認識です。

## 4. 発表者が伝えたいメッセージ

Maraki 氏は、2028 年までにエージェントが 10 億を超えるという見通しを示し、1 人あたり 2〜3 のエージェントが同時に動くイメージを挙げています。そのうえで、「データ基盤はこの AI に備えられているか」と問いかけました。エージェントが増えると、ユーザー数が増えるだけでなく、ワークロードの種類が多様になり、エージェント自身の活動を監査するための新しいデータが生まれ、よりリアルタイムな判断が求められ、AI を前提とした分析ワークロードも増える、という 4 点を挙げています。

これに対する Microsoft の答えが、Fabric という 1 つの統合データプラットフォームと、その中核である Fabric DW です。Fabric DW は 2020 年代、つまり AI の時代に作られたため、先行する製品に対して「後発の利点」があると説明しています。さらにエージェント特有の高い同時実行性に対しては、GPU を使った分析エンジンで応える、という主張です。

Rakesh 氏は「速いウェアハウスは良いウェアハウスだが、性能だけではない」と述べ、運用管理、AI 連携、エンタープライズ機能、SQL 機能まで幅広く強化していると伝えています。

## 5. 発表内容の詳細

### 5.1 AI 時代のデータ基盤と Fabric の位置づけ

冒頭で Maraki 氏は、会場に Fabric を知っているか、Fabric DW を使っているか、AI をデータ基盤の上で使っているかを挙手で尋ねました。AI を既に使っている人は会場の大半で、1 年以内に使う予定の人はほぼ全員でした。

氏によると、AI で先行している組織は、既存の業務に AI を後付けするのではなく、AI とエージェントの機能で日々の仕事そのものを変えることを深く考えている組織です。

Fabric は、データベース、データ準備、分析、リアルタイム、BI、IQ（エージェント体験のための層）といった、データ基盤に必要な要素を 1 つの統合プラットフォームにまとめたものです。Maraki 氏は、Fabric が AI 時代に適している理由を 3 点挙げています。

1. **AI を組み込んだプラットフォームである。** データエンジニアリング、データサイエンス、分析のどこでも、作業を助けるエージェント体験がある。
2. **オープンで AI Ready なデータレイクである。** OneLake は「データのための OneDrive」というたとえで説明されました。Oracle、Google BigQuery、Snowflake、Databricks、SQL Server、S3 などのデータを、mirroring と shortcuts で簡単に OneLake に取り込めます。
3. **ビジネスユーザーにも AI を使える。** data agents で、マーケティング、財務、HR など部門ごとのエージェントを作れます。

### 5.2 Fabric DW の特徴

Maraki 氏によると、データウェアハウス自体は新しい概念ではなく、分析ワークロードや ETL ワークロードのためのものです。Fabric DW は後から登場した分、AI の時代に合わせて作られており、「作り始めたタイミングに運が良かった面もある」と話しています。特徴は次の 4 つです。

| 特徴 | 説明 |
| --- | --- |
| サーバーレス | 予測できない需要を吸収できる。スケーリングが足りているかを利用者が気にしなくてよい |
| レイクハウスアーキテクチャ上に構築 | 性能管理、vacuum、データの最適化、ジョブに必要なノード数の管理は、サービス側が行う |
| AI Ready | ブロンズ層でもゴールド／プラチナ層でも、インテリジェンスがデータの近くにある。具体的な AI 機能は Rakesh 氏が後で説明 |
| 画期的な性能 | 詳細は GPU の章で説明 |

コンピュートは自動でスケールします。小さなクエリか大きなクエリか、同時ロードがあるかによって、ウェアハウスにかかる需要は変わり、10 個の並列タスクが必要になることもあります。Fabric DW は、ワークロードの特性から必要な分散クエリプランを自動で決めます。Maraki 氏は例として、ユーザーが 100 人なら 2 ノード、1000 人なら 10 ノードが必要になるかもしれないが、それを利用者が考える必要はない、と述べています（数字は説明のための例えとして語られたもので、仕様の保証ではありません）。

また、Fabric DW は「レイク中心（lake-centric）」のウェアハウスです。独自形式でもオープン形式でも、mirroring や shortcuts といったコピー不要（zero copy）、ETL 不要の方法でデータを持ち込めます。一番難しいのはデータをプラットフォームに載せる最下層の部分で、そこはこれらのオプションで解決済みという説明です。すべては OneLake の上で動き、Fabric DW のエンジンも OneLake 上にありますが、必要なら他のエンジンも使えます。その上で動かせるワークロードとして、Fabric IQ、Power BI（ダッシュボード）、M365（データへの直接アクセス、Fabric DW 上の data agent、Fabric DW にクエリを押し下げる Fabric app）、ETL が挙げられました。Fabric app は「Raven」という基盤で作られると語られています（音声認識の都合で表記が確定できません）。

**顧客事例：Eastman。** 製造業の Eastman は、Oracle を含む複数のシステムにデータが散らばっていました。mirroring でそれらを初めて 1 か所の Fabric DW に集めた結果、顧客向けの会話の準備に 4 時間かかっていたものが 40 分になったと紹介されました。

### 5.3 人間の分析者とエージェントの違い

性能の話の前提として、Maraki 氏は人間とエージェントのクエリの出し方の違いを説明しました。

- 人間の分析者は、基本的に 1 本のスレッドで 1 つの質問に答えようとします。結果を受け取り、考えてから次の質問をします。結果を見て考えるのに 60 秒から数分かかります。
- エージェントは、人間の **29 倍**のクエリを書くとされています。また複数の枝で並行して動きます。例えば、マーケティングのインサイトを導きながら、財務チームの依頼もこなし、広告収益に関する Google Analytics の情報も扱う、といった具合です。次の質問までに考える時間は 4 秒程度で、リトライも多くなります。

発表では、左に人間だけの場合のグラフ（山と谷が交互に現れる）、右に人間とエージェントが同時にアクセスする場合のグラフを並べて説明しています。右側では山が何度も現れ、山の間隔がずっと短くなります。この負荷はウェアハウスに大きな負担をかけるもので、これまでに無かった種類の需要だと位置づけました。

### 5.4 GPU Accelerated Fabric DW

この課題への Maraki 氏の答えが GPU Accelerated Fabric DW です。GPU はこれまで主に推論や LLM の構築に使われてきましたが、Nvidia と協力して、分析用途にも GPU を活用したとのことです。発表では、**GPU で動く分析エンジンを持つ SaaS のデータウェアハウスとしては市場で最初**だと述べています。

性能の目安は次のとおりです。

| 比較対象 | 説明された改善 |
| --- | --- |
| Synapse DW | 最大 19 倍高速 |
| 他社製品（競合分析の結果） | 最大 7 倍高速、一部のワークロードで最大 60% 安価 |

使い方は単純で、有効にしてからクエリを実行するだけです。データ移動もクエリの書き換えも不要で、同じワークロード、同じ data agent、同じ Power BI レポート、同じ M365 ワークフローをそのまま実行できます。有効化はワークスペースレベルで行い、そのワークスペース内のすべての SQL analytics endpoint とすべてのデータウェアハウスに適用されます。この仕組みは受賞歴のある研究に基づいており、論文は aka.ms/codspeed で読めると案内されました。論文には、今後の方向性を示す手がかりも書かれているそうです。

**効果が出る 4 種類のワークロード**

1. **Power BI の DirectQuery セマンティックモデル。** 1 人のユーザーが 1 つのレポートや Excel の分析を出すだけで、数十から数千のクエリが生成されることがあり、高い同時実行が生まれる。これを GPU に押し下げると速い。
2. **mirroring や shortcuts でデータを取り込むシナリオ。** mirrored database や SQL analytics endpoint が付いてくるため、そこで実行するクエリの一部が GPU アクセラレーションの対象になる。
3. **大規模アプリケーション。** Raven で作って Fabric apps に公開したアプリは、GPU で高速化した Fabric DW 上で動かせる（デモあり）。
4. **AI 駆動のワークロード。** data agents や、Claude、OpenAI などのモデルを使うエージェントが対象。

いずれも対象になるのは SELECT クエリで、結合、集計、大量スキャン、重い算術計算が該当します。

> 注意：高速化の対象として語られたのは SELECT クエリです。

### 5.5 ベンチマーク：DirectQuery の同時実行

Maraki 氏は、300 GB のデータに対する DirectQuery セマンティックモデルで、product A、product B（製品名は伏せられています）、GPU Accelerated Fabric DW を比較した結果を示しました。横軸は同時実行数で、例えば同時実行数 2 は、2 人のユーザーが同時に同じことをしている状況です。

- 同時実行数が増えても、GPU Accelerated Fabric DW は product A、product B より高速な性能を維持しました。
- 同時実行数 128 では、product B は処理しきれず、使うならインスタンスをスケールアップする必要があったと説明されています。GPU Accelerated Fabric DW は処理を完了し、product A の 2 倍高速でした。
- コスト面では、Power BI のセマンティックモデルから生成されたクエリが押し下げられるソースシステム側の費用を比較しています。どの同時実行数でも product A、product B より安く、同時実行数 128 では product A より 32% 安価でした。

**どんなときに向くか。** 縦軸をレイテンシ、横軸を同時実行数とした図で説明されました。1 日に 5〜10 回ほど動かす ETL ジョブは、ユーザーが少なく、常時動かず、増分で動く「低同時実行・高レイテンシ」の領域に入り、GPU アクセラレーションはあまり向きません。人間だけでなく AI エージェントも負荷をかける「低レイテンシ・高同時実行」が求められる場面で、GPU アクセラレーションが力を発揮するという整理です。

### 5.6 顧客事例：UNC Health

UNC Health は Microsoft の近しいパートナーで、臨床医や意思決定者に向けてインサイトを出す際の課題を抱えていました。GPU Accelerated Fabric DW を試したところ、約 5 倍の性能向上があったとのことです。利用者の言葉として、性能の管理に使う時間を減らし、インサイトを届けることにより多くの時間を使えるようになった、と紹介されました。Maraki 氏は、性能向上への投資は標準の Fabric DW と GPU 版の両方で続けると述べています。

### 5.7 SQL analytics endpoint の刷新

ここから Rakesh 氏が担当します。まず前提として、SQL analytics endpoint はすべての lakehouse とすべての mirrored database に標準で付いており、先ほどのサーバーレスや高性能といった特徴は、この endpoint を動かしているのと同じデータウェアハウスエンジンによるものです。OneLake 上のどこにあるデータも、使い慣れた SQL で問い合わせできます。

今週の新しい点として、この endpoint をゼロから再構築し、データの鮮度（latency）を最高水準にしたことが紹介されました。

- lakehouse にデータが着地した時点から、数秒でクエリできる（これまでの数分や数時間ではない）。この点はここ数か月の主なフィードバックの 1 つで、**一般提供（GA）** になったと説明された。
- 新しく作る lakehouse には自動でこの新しい endpoint が付き、手作業は不要で、クエリの挙動も予測しやすくなる。
- 既存の SQL analytics endpoint を使っている場合は、新しいメタデータ同期への移行を計画するための、評価（assessment）とアップグレード用の API を提供する。UX は今後数週間で展開される。
- あわせて、Delta の新しい機能である V2 checkpoints に対応した。
- 大きな文字列、テキスト、JSON などのラージオブジェクト型を、切り詰めなしで SQL から扱えるようになった。

### 5.8 ワークロード管理

Fabric DW はサーバーレスで、既定のままで十分に動きますが、ワークロードが増えて変化していくと、チューニングのための調整項目が欲しくなります。そこで 3 つの機能が紹介されました。

1. **custom SQL pools**：ワークロード単位の分離を行う。データ取り込みや特定のレポートに計算資源を割り当て、リソースを奪われないようにできる。それらが使うコンピュートの上限も設定できる。既定では読み取りに最適化された default pool があるため、設定は必須ではない。
2. **on-demand billing（パブリックプレビュー）**：Fabric の容量モデルは、ワークロードやワークスペースをまたいで同じ容量を使えるが、データウェアハウスと SQL 分析のワークロードを特定の容量に分けたい場合がある。その場合に、完全な従量課金（pay-as-you-go）で利用できる。容量モデルと組み合わせて、課金の仕方を選べる。
3. **cache cooldown**：キャッシュにヒットするクエリを warm query、そうでないものを cold query と説明したうえで、アクティビティが無いときにバックエンドのノードをどれだけ維持するかを設定する。既定値は 5 分で、コストと性能のバランスに応じて増減できる。

これらにより、規模が大きくなっても管理と可視性を保てる、という位置づけです。

### 5.9 AI ネイティブ／AI 対応の機能

- **MCP サーバーとスキル。** Fabric DW が MCP サーバー経由で利用できるようになりました。VS Code、GitHub CLI、Claude Code（音声認識では「Cloud Code」。表記が確定できません）、Codex など、どのクライアントからでも直接接続し、データの取り込み、管理、モニタリングといったデータ基盤の作業を一通り行えます。MCP サーバーはパブリックプレビューで、エージェント向けのスキル（エージェントが Fabric DW を操作するための指示）も公開されました。スキルには、consumption（利用）、management（管理）、data ingestion（取り込み）などがあり、ライフサイクル全体を扱えます。
- **Fabric Ontologies との統合。** ビジネスのメタデータを、Fabric IQ や Microsoft IQ といった下流の体験に持ち込めます。
- **エージェントによるモニタリング（限定プレビュー）。** Fabric の UX 内で、Copilot を軸にした対話により、長時間かかっているクエリの診断、SQL pool への負荷の確認、データの健全性の把握を、自然言語で行えます。問題から、インサイト、アクションへと続けて進めるという説明です。

### 5.10 エンタープライズ対応

1. **CI/CD。** データウェアハウスでは手動デプロイが本番障害やダウンタイムの原因になりやすいことから、CI/CD を作り直し、DacFx ベースのデプロイを導入しました（音声では「DAC FX」）。デプロイライフサイクルを端末から端末まで自動化できます。パブリックプレビューとして、デプロイ前後に実行する自動化スクリプトも発表されました。デプロイ前の準備作業や、デプロイ後の一時テーブルの削除、セキュリティの適用などをスクリプトで設定し、人手を介さず実行できます。VS Code でのスキーマ比較も一般提供になります。スキーマのずれ（drift）を比較し、デプロイ前に計画を検証できます。
2. **新しい接続方式。** プロフェッショナルな開発者向けで、ETL や ELT でネットワーク上の中継（ホップ）が問題になりやすい点に対応します。クライアントがデータウェアハウスを支える SQL バックエンドに直接接続することで、レイテンシを下げ、長時間の処理の信頼性を高め、大量のデータ転送のスループットも向上します。プライベートリンクが有効なワークスペースでも、まもなく利用できるようになります（発表では「available for all workspaces, which are private link enabled soon」と述べており、正確な対象範囲の細部は音声からは確認できません）。
3. **データウェアハウスのクローン。** 本番環境を直接触りたくないが、別チームが非同期に作業できるデータのコピーが欲しい、という要望に応えます。ゼロコピーのクローンを作成でき、ある時点のコピーに留まらず、ワンクリックの更新で定期的に同期できます。現在はプライベートプレビューで、参加希望者は QR コードから申し込めます。パブリックプレビューは来年になる予定です。
4. **ワークスペースモニタリング。** エージェント向けモニタリングとは別の、モニタリング面の改善です。Fabric のすべてのワークロードにまたがるワークスペース全体の視点から、問題のあるウェアハウス、さらに問題のあるクエリへと掘り下げられます。全体から個別のクエリまで、シグナルから調査、解決へ続けて進めると説明されました。
5. **OneLake security。** すべてが OneLake 上にあるので、データとガバナンスの中心になります。SQL analytics endpoint 向けに、グループの登録、セキュリティの伝播、ユーザーのマッピングが改善されました。SQL の監査ログも、より安全な監査ができるよう強化されました。データ取り込みでは Fabric identities に対応し、より安全に取り込めます。
6. **移行。** 移行アシスタント（migration assistant）は、SQL Server と Synapse SQL pool から Fabric へ、製品内の操作で移行する機能で、既に一般提供されています。今回は、レガシーなソースとして Teradata にも対応しました。**増分移行**にも対応し、一度に移すのではなく、データ資産の一部を選んで移し、後で戻って続けるという段階的な進め方ができます。エージェントで Fabric を操作する場合に向けて、移行用のスキルも GitHub に公開されています。

### 5.11 内部的な性能改善と SQL 機能

GPU を使わなくても、内部の改善が続いています。例として、文字列処理の高速化、クエリの見積もり精度の向上、distributed bitmap filters が挙げられました。多くは既に展開済みで、日々の利用でクエリが速くなったと感じられるとのことです。

SQL 開発者向けには、次の拡張が紹介されました。

| 項目 | 内容 |
| --- | --- |
| クエリの書きやすさ | `FROM` first、`GROUP BY ALL`、`QUALIFY` により、より豊かな SQL を直接書ける |
| 分析関数 | 大規模データ向けの analytics functions に対応 |
| 正規表現 | ネイティブの正規表現。大きな文字列の操作が SQL 内で可能。まもなくパブリックプレビュー |
| LOB 型 | `varchar(max)`、`varbinary(max)` の完全対応。新しい SQL analytics endpoint で、現在パブリックプレビュー |
| Fabric functions | Python の関数を作って SQL から再利用できる |
| identity columns | 安全なデータ取り込みのシナリオを強化 |
| ユーザー定義関数（UDF） | 現在パブリックプレビューで、まもなく GA。ビジネスロジックを 1 か所に定義して再利用でき、行ごとの実行ではなくクエリプランに組み込まれるため、性能が良い |

SQL Web エディターも刷新されました。オブジェクトエクスプローラーとリソースグリッドを作り直し、一瞬で読み込まれて応答が速くなりました。さらに、ノーコードのテーブルデザイナー、よく使う機能に素早く届くテーブルの概要画面、エディター内でクエリ結果を見やすく表示するクエリビジュアライゼーションが加わりました。

## 6. デモ・手順

デモは GPU Accelerated Fabric DW の有効化と効果の確認で、Maraki 氏が行いました。画面の細部は音声からは確認できないため、語られた範囲で語られた順に書きます。

**6.1 有効化とクエリの実行**

1. Fabric のワークスペースビューを開いた状態から始める。
2. ワークスペース設定（workspace settings）に移動する。
3. Data warehouse の項目に新設された **query acceleration** のオプションを、トグルでオンにする。
4. オンにすると、そのワークスペースのすべての SQL analytics endpoint とすべてのデータウェアハウスに適用される。デモのワークスペースでは、finance warehouse、operational warehouse、supplier logistics の mirror database がすべて対象になると説明された。
5. ウェアハウスを開き、画面の下部に有効になっていることが表示されているのを確認する。
6. Run を押すと結果テーブルが表示される。クエリのために特別な操作は不要。
7. クエリプラン（query plan）を表示する。内部結合を含むボックス全体が GPU に押し下げられており、すべてが高速化されていた。
8. モニタリングに移動し、テーブル内に新設された **query acceleration** の項目を見る。どのクエリに GPU アクセラレーションが適用され、どれに適用されなかったかが分かり、どの種類のクエリで効果があるかを判断できる。

**6.2 同時実行数を変えた比較**

同じデータウェアハウスの上に Raven で作ったアプリを使い、紫が標準の Fabric DW、緑が GPU Accelerated 版として比較しました。

| ユーザー数 | GPU 版（緑） | 標準版（紫） |
| --- | --- | --- |
| 1 人 → 10 人 | 1.3 秒で完了。紫の約 36 倍高速 | － |
| 10 人 → 100 人 | 約 80〜90 クエリ／秒のスループットで、5 秒で完了 | 268 秒 |
| 250 人 | 同程度のスループットを維持し、11.4 秒で完了（リアルタイムで実行） | 682 秒 |

250 人のケースでは、待ち時間を省くため標準版側の再生を早送りしたと説明されています。GPU 版は標準の Fabric DW の約 **60 倍**高速（682 秒 対 11.4 秒）でした。

## 7. 注意点・発表者の気付き

- GPU アクセラレーションの対象は SELECT クエリです（結合、集計、大量スキャン、重い算術計算）。
- 1 日に 5〜10 回動かす増分 ETL のような低同時実行・高レイテンシの処理には、GPU アクセラレーションはあまり向きません。
- ベンチマークの比較対象は product A、product B という匿名の製品で、製品名は明かされていません。同時実行数 128 では product B は処理を完了できなかったと説明されています。
- 比較の数値（最大 19 倍、最大 7 倍、最大 60% 安価）は「up to」であり、ワークロードによって異なります。
- 既存の SQL analytics endpoint を新しい版に移すには、評価とアップグレードの API を使って計画します。
- 発表された機能の提供状況は、GA、パブリックプレビュー、限定プレビュー、プライベートプレビューと混在しています（5 章に記載）。
- 新しい接続方式の提供範囲の細部は、音声から確認できません。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **Eastman（製造業）**：Oracle を含む散在したデータを mirroring で Fabric DW に集約し、顧客向けの会話の準備が 4 時間から 40 分になった。
- **UNC Health**：GPU Accelerated Fabric DW で約 5 倍の性能向上。性能管理の時間を減らし、インサイトを届ける時間を増やせた。
- **性能**：Synapse DW 比で最大 19 倍、競合比で最大 7 倍の高速化と、一部ワークロードで最大 60% の低価格。DirectQuery の 128 同時実行で product A より 2 倍高速、32% 安価。
- **運用の手間**：サーバーレスで、vacuum や最適化、ノード数の管理が不要。GPU 版はクエリの書き換えもデータ移動も要らない。
- **鮮度**：新しい SQL analytics endpoint で、lakehouse に着地したデータを数秒でクエリできる。

## 9. まとめ

エージェントは人間の約 29 倍のクエリを、数秒間隔で投げてきます。このセッションは、その負荷に対する Fabric DW の備えとして、まず **GPU Accelerated Fabric DW**（ワークスペースで query acceleration をオンにするだけ）を示し、250 ユーザーの比較で標準版の約 60 倍という結果を見せました。続いて、再構築された SQL analytics endpoint（秒単位の鮮度、GA）、custom SQL pools・on-demand billing・cache cooldown、MCP サーバーとエージェント向けスキル、DacFx ベースの CI/CD、クローン、移行アシスタントの拡張、SQL 構文と Web エディターの強化が紹介されました。詳細は Fabric Community Blog で随時案内される予定です。
