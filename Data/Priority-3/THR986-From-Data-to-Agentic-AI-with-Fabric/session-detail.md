# THR986 From Data to Agentic AI with Fabric

## 1. はじめに

このセッションは、生のデータからビジネスユーザーが満足する回答を返すエージェントを作るまでの流れを、Microsoft Fabric 上のデモで見せる約 25 分のセッションです。登壇者は「エージェントを作ったことがある人は、最初から正しい答えが返ってきたか」と会場に問いかけ、うまくいかない原因を、数字・通貨・合計行・意味・アクセス権の問題として整理しています。

結論は次のとおりです。**エージェントを生データのテーブルに直接つなぐと、たいていプロジェクトは失敗します。** 先に「信頼できるデータ」「ビジネス上の意味」「アクセス制御」の 3 層を整えてから、4 層目でエージェントを作るべきだ、という主張です。

デモでは、複数ソースの財務データに品質ゲートをかけて整え、Semantic Model に意味を書き込み、Ontology でテーブル間の関係を定義し、最後に Fabric data agent で回答させるところまでを順に見せています。このセッションにはライブデモがあります（6 章）。

## 4. 発表者が伝えたいメッセージ

登壇者の主張は、**エージェントの問題は信頼できるデータから始まる**、つまりデータに品質と意味が無いことが間違いの原因になる、というものです。エージェントを Fabric のデータレイクに直接つなぐと、エージェントは列名や数字から意味を推測します。たとえば `revenue` という列があっても、net revenue なのか total revenue なのか、拠点別なのか国別なのかは分かりません。推測はたいてい外れる、というのが登壇者の説明です。

そのため、意味や品質の情報をエージェントの外側（データ基盤側）で整え、エージェントに渡す必要があるとしています。さらに、基盤側に Semantic Model と Ontology を作っておけば、Fabric の data agent でも Foundry で作るエージェントでも、同じ文脈を使い回せます。意味の定義を直したときも、Semantic Model を修正すれば、そこにつながるすべてのエージェントに反映されるという点が、この構成の利点として語られました。

## 5. 発表内容の詳細

### 5.1 エージェントが直面する問題

登壇者は冒頭で「主な問題は 3 つ」と切り出しますが、実際には、ビジネスユーザーが期待する動きをするエージェントを作るときに出会う問題を、次の 4 つの表と、その後のアクセス権の問題に分けて話しています。

| 問題 | 内容 |
| --- | --- |
| 間違った数字 | 汚れたデータから始めると、エージェントも間違った答えを返す。デモの最初で、生データをクリーンなデータにする方法を見せる。 |
| 通貨の不一致 | ドルやユーロなど複数の通貨が混在する。1 か所・1 つの通貨に統合して照合する必要がある。 |
| 合計行の二重計上 | データソースに、個別の値の行と合計の行が混在していると、エージェントはすべてを 2 回数えてしまい、誤った答えになる。 |
| 間違った意味 | Fabric data agent をデータレイクに直接つなぐと、エージェントは意味を推測する。これが最も大きな問題だと登壇者は述べている。 |

ここで登壇者は、推測の例として `revenue` という列名を挙げています。net revenue、total revenue、拠点別の revenue、国別の revenue のどれなのか分からず、データレイクに revenue を探しに行くエージェントは、答えは返しても、多くの場合は間違った答えを返す、という説明です。

もう 1 つの問題は、データを見る権利のない人にエージェントが答えてしまうことです。例として、給与テーブルがある状態でエージェントを公開すると、テーブルへの権限は無くてもエージェントへの権限がある人は、そのデータを見られてしまいます。登壇者はこれを **exfiltration（情報の持ち出し）の問題**と呼んでいます。

### 5.2 エージェントを作る前の 4 つの層

登壇者は、良いエージェントを作るには次の 4 つの層が必要だと説明しています。

1. **信頼できるデータ（Trusted data）**：複数のソースからデータを取り込む。デモでは signup（音声認識の都合で表記が確定できません）、Tableau、Excel、CSV など多数のソースが登場する。bronze → silver → gold というメダリオン構成に従う。ただし gold に進む前（または gold の前段）に **quality gates（品質ゲート）** を置き、エージェントに渡すデータを検証する。
2. **ビジネス上の意味（Business meaning）**：エージェント作成で最も難しい部分の 1 つ。必要に応じて Semantic Model という層を作り、そこにビジネス上の意味が入っているかを確認する。
3. **データの保護（Secure the data）**：エージェントを使う人の役割によって、見てよい情報だけが見えるようにする。たとえば財務結果を扱うエージェントなら、ロールに応じて閲覧できる範囲を変える。
4. **エージェントの構築**：1〜3 層が揃ってから作る。

第 1 層の品質ゲートについて、登壇者は具体的な確認項目を挙げています。間違った数字、間違った通貨、合計値、数字の一致の有無です。たとえば売上の情報が ERP（SAP）、Tableau、signup のそれぞれにあり、月次売上の数字が一致しない場合があります。どれを真の値とするかをエージェントに取り込む前に決める必要がある、という説明です。

第 2 層について、登壇者は、ビジネス担当者と会い、「初めて仕事をする人に教えるように」数字の意味を説明してもらうことを勧めています。会議を録音してメモを取り、その内容をエージェントが理解できる形に落とし込みます。

登壇者は、第 4 層から始めて、生のテーブルに直接エージェントを向けると、ビジネス上の意味もクリーンなデータも無いため、間違った答えを返し、たいていそのプロジェクトは失敗すると断言しています。

### 5.3 デモのシナリオ

扱うのは、複数の国に拠点を持つ金融系の会社です。国ごとに通貨も意味も異なり、情報を 1 か所に統合する必要があります。データソースは Tableau、signup、SQL Server、Oracle などです。統合したうえで、ビジネス上の意味を踏まえて答えるエージェントが必要、というのが設定です。

### 5.4 データ品質：品質ゲートと実際のノートブック

登壇者は Fabric の画面で、メダリオン構成（bronze、silver、gold）を示しました。作成する項目は、クリーンなデータを持つ gold 層、その上の Semantic Model、Semantic Model の次の Ontology、そしてエージェントの順です。よくある失敗は、SAP や Tableau のデータをロードしただけで、bronze 層に直接 data agent を向けてしまうことだと説明しています。この場合、エージェントはデータの意味を持たず、汚れたデータに対して答えることになります。

データのロード後に、パイプラインを作ります。パイプラインにはデータのロードの段階があり、その後に **品質ゲート** があります。品質ゲートには業務ルールがあり、次のことを決めます。

- どの情報をエージェントに渡してよいか
- どの情報にクロスバリデーション（相互検証）が必要か
- 同じ売上でも 2 つの値がある場合、どちらが正しいソースか
- データソース間に食い違いがあるとき、何をエージェントから外すか

あわせて、データを記録する場所（ログ）も作ります。ノートブックとモデルはすべて GitHub から入手でき、聴講者が自分でデモを再現できると登壇者は案内しています（URL は発表では読み上げられていません）。

品質ゲートのノートブックでは、まず **entity map** を作っています。実在する会社を想定しており、システムごとに言語も技術も異なります。ブラジルの拠点ならポルトガル語、コスタリカならスペイン語、米国なら英語、日本も含め、内部システムごとに国名や数字の表記が違います。そのため、国をまたいで照合できる 1 つの層に統合する必要があります。

次に、"Brazil consolidated" という項目を取り上げています。金融系の会社では、複数の国や地域を 1 つにまとめた連結データがよくあります。連結されたデータと連結されていないデータが同居していると、すべてを二重に数えてしまいます。そのため、このような連結データはエージェントには使えず、除去する必要があります。

その後に **cross tab export** を実行します。これは、データソース間の関係を作り、どのソースが本物かを判定するものです。ここでは Tableau、CSV、signup を比較しています。品質ゲートでは、たとえば拠点数が 12 であれば、どのソースでも 12 拠点あることを確認します。国についても、各拠点に対応する国がそろっているかを確認するという趣旨の説明です（発話がやや不明瞭です）。そのほか、金額が二重になっていないか（発話は聞き取りが不明瞭で、"dual amounts" と聞こえます）、重複行がないか、一致しないデータがないかを確認します。

そして、品質ゲートに「**一致率の差が 1% を超える場合は、そのデータをエージェントに渡さない**」というルールを置いています。データに一貫性が無いためです。この結果は 1 つのツールにログとして残り、ビジネスユーザーがレビューします。これらを経ると、きれいなファクトテーブル（クリーンなデータ）が得られます。

> 注意：登壇者は、データがクリーンになっただけでは、エージェントを作るには不十分だと強調しています。ビジネス上の意味がまだ無いためです。

### 5.5 Semantic Model にビジネス上の意味を書く

Fabric には、意味を設定できる場所が複数あり、最初の場所が **Semantic Model** です。クリーンなデータに基づいて作りますが、この状態でエージェントを作ると、エージェントは列名から意味を推測してしまいます。

そこで、テーブルの各列やメジャーに説明（description）を付けます。デモでは次のような記述が紹介されました。

- net revenue（米ドル）は signup のものを使う。signup が system of record（正本）であり、これが正しいデータであること。
- total revenue から pass-through cost（立替コスト）を引いたものであること。
- 売上（revenue）は、拠点と期間をまたいで加算できる（additive）。そのため、売上を聞かれたら、複数の拠点の売上を合計して答えること。

もう 1 つの例が、フルタイム従業員数（full-time employees）のメジャーです。単に人数を数えるだけの単純なメジャーですが、落とし穴があります。従業員数は月ごとに登録されているため、エージェントに「フルタイム従業員の総数は」と英語で聞くと、毎月分を合算して間違った答えを返します。そこで Semantic Model の文脈に、フルタイム従業員数は「**最新（直近）の値を使う**」という計算方法を書き込みます。比較を行う場合はどう比較するか、といった注釈も同じ場所に書けると説明しています。

### 5.6 Ontology でデータ同士の関係を伝える

次のステップは **Ontology** の作成です。Ontology は、データがどのように関連しているかをエージェントに伝えます。デモでは、Semantic Model で説明を付けたのと同じテーブルに対して、関連を定義しています。

- fiscal period（会計期間）は month（月）で構成される。
- 月次レポートは、すべて office（拠点）に関連付けられる。
- したがって、office は fiscal period を持ち、office は monthly report を持つ。

office を開いて properties を選ぶと、関係の説明とコンテキストを追加できます。これにより、エージェントはテーブル間の関係を理解できます。

ここまでの 3 つの工程（データのロードとクリーニング・品質ゲート、Semantic Model での注釈、Ontology による関係付け）を、登壇者はあらためて整理しています。これらを行わないと、エージェントはリレーションを推測し、たいていそれは正しくありません。

### 5.7 エージェントの作成と接続先

Semantic Model と Ontology をプラットフォーム側に作っておけば、エージェントを作るツールは問いません。登壇者は次の例を挙げています。

- **Foundry** でエージェントを作り、Semantic Model に接続する。Ontology にも接続すれば、同じ文脈が使える。
- **Fabric data agent** を Fabric 内で作る。

デモでは、Fabric で作成した Fabric data agent を見せています。データソースとして Ontology と Semantic Model が指定されています。エンドユーザーから質問を受けたときの動きは、次のとおり説明されました。

1. エージェントがユーザーの質問を理解し、まず Ontology で、質問の意味とデータレイク内のデータとの関係を把握する。
2. 次に Semantic Model に進み、付けられた説明を使って、答えに必要なデータを見つける。
3. その後、lakehouse に対するクエリを実行する。

登壇者は最後にこの流れをもう一度見せています。Semantic Model に対しては、クエリは「DXX」と聞こえる言語で実行され（音声認識の都合で表記が確定できません。（補足）Semantic Model 向けのクエリ言語を指していると考えられます）、データベースに対しては Transact-SQL が実行されると説明しています。

意味の変更が必要になったときは、Semantic Model を直します。その Semantic Model に接続したすべてのエージェントが、更新された説明とコンテキストを受け取ります。数式やデータの解釈方法を修正したいときも、ここで直す、という使い方です。

### 5.8 Copilot Studio との連携と公開

Fabric data agent を作ったあとは、Copilot Studio からそのデータエージェントに接続できると説明されています。データエージェントはレイクハウスの情報に基づく文脈をすべて持っています。登壇者は "regional agent" という名前のエージェントを見せ、そこから Teams や Microsoft Office、Web アプリへの埋め込み、または Copilot などどこからでも呼び出せる形で公開できると述べています（画面の細部は音声からは確認できません）。

エンドユーザーに渡したあと、典型的な質問が用意されており、質問するとエージェントはすべての層をたどって文脈を集めると説明されました。具体的な質問文や回答の内容は、音声では読み上げられていません。

### 5.9 持ち帰りのポイント

最後に、登壇者は次の 3 点を挙げています。

1. 層と層の間に品質ゲートを作る。
2. 明示的なメジャーとスキーマを作る。
3. すべてを文書化する。時間はかかるが、必ず文書化する。

その上で、適切なエージェントを作る、という順序です。

## 6. デモ・手順

このセッションにはデモがあります（"Let's go to the first demo"、"This is my fabric"、"I will show you here" などの発話から確認できます）。ただし、録音は音声だけのため、画面上の操作はナレーションで語られた範囲までしか分かりません。語られた順序は次のとおりです。

1. Fabric の画面で、メダリオン構成（bronze、silver、gold）と、gold の後に作る項目（Semantic Model、Ontology、エージェント）を示す。
2. ロードしたデータに対するパイプラインを見せる。データのロードの段階の後に、業務ルールを持つ品質ゲートがある。
3. ノートブック（品質ゲート）を開き、entity map（国名・表記の統合）と "Brazil consolidated" の扱い（連結データの除外）を説明する。
4. cross tab export で、Tableau・CSV・signup を比較する。拠点数の一致、金額の重複、重複行、不一致を確認し、差が 1% を超えるデータはエージェントに渡さない。結果はログに残り、ビジネスユーザーが確認する。
5. クリーンなファクトテーブルができあがる。
6. Semantic Model を開き、テーブル・列・メジャーの説明（net revenue、revenue の加算性、フルタイム従業員数の「最新値を使う」など）を示す。
7. Ontology を開き、fiscal period、month、monthly report、office の関係と、office の properties に説明を加える画面を示す。
8. Fabric で作成した Fabric data agent を開き、Ontology と Semantic Model がソースになっていることを示す。
9. Copilot Studio から接続し、公開先（Teams、Microsoft Office、Web アプリ、Copilot）に触れる。regional agent を見せ、典型的な質問が用意されていると説明する（質問文と回答の中身は語られていません）。
10. 最後に、質問を受けたエージェントが Ontology → Semantic Model → クエリの順に動くことを説明する。

> 補足：デモの中で、第 3 層（アクセス制御）の設定を見せる発話はありません。また、Foundry でエージェントを作る操作も、デモではなく口頭の説明です。

## 7. 注意点・発表者の気付き

- エージェントを bronze 層など生のテーブルに直接つなぐのが、典型的な失敗です。ビジネス上の意味もクリーンなデータも無いまま、間違った答えを返します。
- 売上のデータソースが複数あり、数字が一致しないときは、どれを正とするかをエージェントに渡す前に決める必要があります。
- 連結データ（例: Brazil consolidated）と連結前のデータが両方あると、二重計上になります。
- 月次で登録される値（フルタイム従業員数など）は、そのまま合計すると誤った答えになります。計算方法（直近値を使う）を Semantic Model に明記します。
- 意味付けは、ビジネス担当者に説明してもらい、メモや録音を取って、エージェントが理解できる形にする必要があります。時間がかかる作業ですが、すべて文書化することが求められています。
- 権限のないユーザーに答えを返さないよう、エージェントを公開する前にデータの保護（ロールに応じた閲覧範囲）を設計する必要があります。

## 8. 利用者にとっての利点

発表では、導入企業の数値的な成果や顧客事例は語られていません。利点として語られたのは、次の点です。

- Semantic Model と Ontology を基盤側に作っておくと、Fabric data agent、Foundry のエージェント、Copilot Studio のエージェントなど、使うツールが違っても同じ文脈を共有できる。
- 意味の定義を修正したいときは、Semantic Model を 1 か所直せば、接続しているすべてのエージェントに反映される。
- 品質ゲートでデータの食い違いをログに残し、ビジネスユーザーがレビューできる。
- 作成したエージェントは、Teams、Microsoft Office、Web アプリ、Copilot など、さまざまな場所から呼び出せる。
- デモで使ったノートブックとモデルは GitHub で公開され、各自で再現できる。

## 9. まとめ

Fabric でエージェントを成功させる鍵は、エージェントを作る前の準備にあります。bronze から gold への各段階に品質ゲートを置き、Semantic Model に列・メジャーの意味と計算方法を書き込み、Ontology でテーブル同士の関係を定義します。その上で、Fabric data agent、Foundry、Copilot Studio のいずれからでも、同じ文脈を持つエージェントを作って公開できます。登壇者が最後に挙げたのは、層の間の品質ゲート、明示的なメジャーとスキーマ、そして全体の文書化の 3 点です。
