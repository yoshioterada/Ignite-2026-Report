# BRK359 Build intelligent PostgreSQL apps with Microsoft Fabric HorizonDB

## 1. はじめに

このセッションは、Ignite で発表された **Microsoft Fabric HorizonDB**（パブリックプレビュー）の紹介です。Fabric HorizonDB は、Fabric の中で動く、フルサーバーレス・フルマネージドの PostgreSQL です。容量計画やプロビジョニングといったインフラ作業が不要で、数秒で作成でき、人間のユーザーからでも AI エージェントからでも接続できます。

話の中心は、「**1 つの Postgres エンドポイントから、運用データと分析データの両方に届く**」という点です。登壇者は、約 1 億件の注文データを使い、次の 4 つのデモを行いました。

1. VS Code から Fabric HorizonDB に接続し、通常の運用クエリを実行する
2. 同じ集計クエリを、ミラーリングされた OneLake 上のデータに向けて実行し、**約 40 秒が約 3 秒**になることを確認する
3. 分析データを Postgres に戻す「リバース ETL」を構成し、Fabric アプリから複数のクエリを実行する
4. Foundry のモデルを SQL 関数から呼び出し、運用データと分析データを根拠にした顧客向けの「アカウントブリーフ」を生成する

Postgres のアプリを作る開発者や、Fabric 上でデータ駆動型アプリを作る人が、どんな構成と使い分けができるかを把握できる内容です。

## 5. 発表内容の詳細

### 5.1 Fabric HorizonDB の概要

冒頭で、Satya 氏が朝に話したことに触れ、「運用データにも分析データにも届く単一のエンドポイントを、フルサーバーレス・フルマネージドの Postgres から使える」ことを想像してほしい、と切り出しています。登壇者が挙げた特長は次のとおりです。

| 項目 | 発表内容 |
| --- | --- |
| プロビジョニング | 数秒で完了。容量計画やプロビジョニングなどのインフラ作業は不要 |
| 接続主体 | 人間としても、エージェントとしても、運用データベースに接続できる |
| 規模 | プレビューでは **4 TB** まで。GA ではさらに大きくスケールする |
| Fabric アプリとの関係 | Fabric アプリを新規作成するときにプロビジョニングできる、運用データベースのバックエンド |
| 自動停止と再開 | **アイドル 5 分で自動停止**し、新しいクエリが来ると数秒で自動再開 |
| 設定 | Postgres には数百の設定があるが、最大でどれだけのキャパシティやリソースを割り当てるかを含め、サービス側がすべて管理する（SaaS のデータベース） |
| 認証 | Microsoft Entra と統合。Entra ユーザーが自分の資格情報で接続できる |
| 権限 | Fabric のロール（管理者、作成者、ユーザーなど）に基づく |
| 開発ツール | Visual Studio の Postgres 拡張機能と連携。Postgres を使う既存のアプリケーション、ライブラリ、ORM ツールはそのまま使える |

**組み込み済みの拡張機能**として、登壇者は次の 4 つを挙げています（綴りは発言から聞き取ったものです）。

- **Azure AI**：SQL 関数から Microsoft Foundry のモデルとやり取りする
- **vector と PGDiskNN**（音声認識の都合で表記が確定できません）：スキーマでベクトル型を使い、大規模なインデックスを高い性能で作る
- **PG text search**：テキストの検索と全文検索
- **PG fabric FDW**：「秘伝のタレ」（secret sauce）と呼ばれる拡張機能で、運用の世界と分析の世界をつなぎます。Postgres のエンドポイントから、レイク全体、Fabric のデータウェアハウス、Fabric Lakehouse に対してクエリを実行し、分析側のデータを運用データと結合できます

**提供状況**は次のとおりです。

- Microsoft Fabric HorizonDB は、この日にパブリックプレビューとして発表され、数日のうちに Fabric テナントで利用可能になる
- Azure HorizonDB は、同日の朝に GA が発表された。PaaS で、コンピュートのコア数やメモリを自分で決める必要がある

登壇者によれば、Fabric アプリはデータ駆動型アプリを作る手段として注目を集めており、Fabric HorizonDB はそのバックエンドとして最適です。また、運用データと分析データを、RAG のようなパターンで AI モデルとつなぐ AI 機能も組み込まれています。

### 5.2 アーキテクチャ：OneLake との 3 つの連携パス

Fabric HorizonDB は、Azure HorizonDB と同じ **コンピュートとストレージの分離**を採用しています。大きな違いは、コンピュート層が完全にサーバーレスである点です。Microsoft Foundry のモデルと話すための拡張機能も、あらかじめ入っています。

OneLake を含む Fabric プラットフォームとの連携には、大きく 3 つのパスがあります。

| パス | 内容 |
| --- | --- |
| 1. ミラーリング | 運用データベースに挿入・更新されたデータが、**ほぼリアルタイム**で OneLake に自動ミラーリングされる。ミラーされたデータは、分析ワークロード向けに最適化された列指向のネイティブ Delta テーブルになる（大規模なスキャンや集計向け） |
| 2. Fabric データのクエリ | Fabric FDW 拡張機能を使い、同じ Postgres エンドポイントから、OneLake 上のミラーデータをクエリする。ミラーデータだけでなく、Fabric の任意のウェアハウスやレイクハウスも、SQL 分析エンドポイントを通じて Postgres からクエリでき、Postgres のローカルデータと結合もできる |
| 3. リバース方向の提供 | メダリオンアーキテクチャのゴールド層にある整形済みデータ（経営ダッシュボードやレポート用など）を、Postgres 経由で提供する。アプリケーションがすでに Postgres の方言で動いている場合に向く。多数の顧客が同じデータにアクセスするときに必要な、高スループット・低レイテンシのクエリには Postgres が最適だと説明しています |

### 5.3 サーバーレスの動作と課金

登壇者はアニメーションを使って、次のように説明しています。プロビジョニングすると、数秒でコンピュートノードとストレージが用意され、クエリを受け付けられます。データベースが稼働している間は、消費したコンピュートとストレージの量に応じて課金されます。

Fabric アプリのような新しいデータ駆動型アプリでは、ユーザーがしばらくデータを使わないことが多く、アイドル状態が 5 分続くとコンピュート層を停止します。その間はデータベースが占有するストレージ分だけが課金されます。次のクエリが来ると、コンピュート部分を再び立ち上げ（rehydrate）、再度コンピュートとストレージに課金されます。つまり、**コンピュートは必要なときだけ動き、使っていないときは支払いが発生しません**。

### 5.4 Fabric FDW で分析エンジンを Postgres に登録する

運用データと分析データの「融合」の仕組みとして、次のような構成が説明されました。

1. Fabric HorizonDB には、`orders`、`customers` といったローカルテーブルがあり、アプリケーションが利用している
2. 一方で Fabric には、ウェアハウスやレイクハウスがあり、列指向（column store）や GPU アクセラレーションなど、Fabric のデータウェアハウスチームの技術革新の恩恵を受けている
3. Fabric FDW 拡張機能を使って、いくつかの DDL コマンドで、Fabric の分析エンジンにあるアセットを Postgres に登録する。**Postgres に取り込まれるのはメタデータだけで、データそのものはコピーされない**
4. どの Fabric データウェアハウスのテーブルを Postgres エンドポイントから見せるかを選べる（スライドの左下に、メタデータをインポートする数個のコマンドが示されました。コマンドそのものは読み上げられていません）
5. 登録が済めば、Postgres に対するクエリが Fabric の分析エンジンに届き、大規模スキャンや集計の最適化が使われる。実際には、Fabric 側のリモートテーブルと Postgres のローカルテーブルを結合する、「トランスアナリティカル（transanalytical）」クエリを使うことが多い

登壇者はこの点を次のように整理しています。接続は 1 つで、使い慣れた Postgres の接続です。どの Postgres ライブラリ、どのクライアントでも使えます。大規模なスキャンや集計の重い処理は Fabric が担い、同時にローカルのテーブルとも結合できます。例えば、顧客テーブルを主キーで絞り込む（典型的な OLTP クエリ）と同時に、Fabric のデータウェアハウスにある巨大な注文テーブルと結合する場合、重い部分は Fabric が処理するため高速に解決できます。ETL によるコピーは不要で、分析データは Fabric 側に、運用データは Postgres 側に残ります。

### 5.5 デモ 1：データベースの作成と VS Code での操作

登壇者が語った順に、実演の内容を示します。画面の細部は音声からは確認できません。

1. Fabric のワークスペースで「新規アイテム（new item）」を選ぶと、新しいアイテムタイプがある（発言では「Azure Horizon DB」と聞こえますが、文脈上は今回の Fabric HorizonDB のアイテムです。音声認識か言い間違いかは確認できません）

3. 作成直後で空のデータベースを、Fabric の SQL エディターで見られる。Fabric のエディターで開発することも、VS Code に接続することもできる
4. 新しい **Postgres 拡張機能（VS Code）**を使う。この拡張機能は、Fabric HorizonDB だけでなく、ローカルのコンテナーやインスタンス、Azure のインスタンスなど、任意の Postgres に接続できる。今回は、Fabric のワークスペースを参照できるようになっており、ワークスペースとデータベースを選んで接続する
5. 拡張機能のパフォーマンスダッシュボードで、データベースの利用状況（上位のクエリ、開いているセッション）を確認できる。接続直後なので、まだ空である
6. バージョンを確認するクエリを実行し、HorizonDB であることを確認する
7. あらかじめ `customers`、`orders`、`products` の 3 つのテーブルを作ってある。Postgres のカタログに問い合わせて確認した。3 テーブルだけだが、注文は **約 1 億件**ある
8. 主キーで絞ったクエリは、運用データベースなので高速。実行計画を見ると B3 インデックスなどが使われている（発言は「B3 indexes」と聞こえます。音声認識の都合で表記が確定できません）
9. customers、orders、products を結合するより複雑なクエリも実行した。顧客 ID で絞り込んでいるので高速。VS Code の Postgres 拡張機能では、実行計画をグラフィカルに表示することもできる

登壇者は、ここまでは「従来型の高速な運用データベース」であり、数秒でプロビジョニングでき、完全にサーバーレスで、Fabric 内で完全にマネージドである、とまとめています。

### 5.6 デモ 2：ミラーリングデータで分析クエリを高速化する

ここから、運用の世界と分析の世界の統合を見せています。

1. **典型的な分析クエリ**を実行する。「過去の売上に基づく上位 100 顧客」を求めるもので、約 1 億件の注文を、指定した期間で集計して顧客ごとの売上を計算し、ローカルの顧客テーブルと結合する
2. Postgres には列指向ストアも分析向けの最適化もないため、このようなクエリは難しい。実際に画面右下で、約 **40 秒**かかっていることが示された
3. 次に、Fabric HorizonDB から OneLake へ自動的・透過的にミラーリングされているデータを使う。新しいスキーマを作り、ミラーデータベースにある customer、products、orders の外部テーブルをインポート（登録）する
4. これらのテーブルは Postgres のスキーマ内に現れ、ローカルテーブルと同じようにクエリできる（スキーマ名が違うだけ）。1 億件の注文、1,000 万件の顧客などが見える
5. **まったく同じクエリで、orders テーブルだけを OLAP スキーマ側のものに変えて**（ローカルの customers テーブルとの結合はそのまま）再実行すると、40 秒かかっていたものが **3 秒**で終わった
6. 実行計画では、集計などの重い処理が、外部スキャンとして Fabric DW エンジンにプッシュダウンされている

登壇者は、これは、アプリケーションもクエリも変えずに、OneLake にある分析向けに最適化されたミラーを利用するだけで、Postgres 上の分析クエリを最適化できる例だと説明しています。

### 5.7 デモ 3：リバース ETL と Fabric アプリ

3 つ目のパスです。Fabric の整形済みデータセットを、多くのユーザーが同時にアクセスするダッシュボードのようなアプリのために Postgres のエンドポイントから提供したい場合に、**リバース ETL パターン**を実装します。従来の ETL は運用側から分析側へ流しますが、ここでは、分析エンジンの整形済みデータを運用側の Postgres に戻します。

登壇者は、より完成度の高いアプリを用意しています。構成は、2 つの Fabric アプリ（1 つは新しい注文を生成し、もう 1 つは注文の分析を助ける）が Fabric HorizonDB と連携するものです。

1. 注文生成アプリが、新しい注文をシステムに流し込む
2. 注文が入ると OneLake にミラーリングされる。ただしこのデモでは、ミラーするだけでなく、メダリオンアーキテクチャで一般的なデータ拡充も行う（発言では「mid-ion architecture」と聞こえますが、直前に Medallion アーキテクチャに触れており、同じ文脈で語られています）
3. Lakehouse を作り、ミラーされた（運用のままの）スキーマのデータを、完全な**スター スキーマ（ディメンショナルモデル）**に変換し、さらにそこから、ダッシュボードやレポートに使える整形済みの「ゴールド」データセットを作る
4. Lakehouse には **silver** と **gold** の 2 つのスキーマがある。silver 層はディメンショナルモデルで、ファクトテーブルとディメンションテーブルがあり、データウェアハウスのワークロードで使う
5. gold のデータセットを Postgres に戻すために **コピージョブ**を使う。コピージョブは Fabric 統合のパイプラインで、ソースと宛先を指定し、**CDC データに基づく継続的なコピー**を行える
6. Postgres 側では、Lakehouse のエンドポイントを登録し、そのテーブルを外部テーブルとしてインポートする
7. これで、ミラーされたデータベースのテーブルと、Lakehouse のディメンションテーブルを、通常の SQL（スキーマ名が違うだけ）でクエリできる。1 億件の注文に加え、ゴールド層の月次と日次の経営ダッシュボード用の 2 つの新しいテーブルが見える

その後、売上分析用の **Fabric アプリ**で、次の 4 つのシナリオを実演しています。

| シナリオ | 内容と結果 |
| --- | --- |
| 1. 上位 100 顧客 | 先に見たクエリ。運用データベースだけに問い合わせると、トランザクションが入ってくるため**さらに時間がかかる**。ウェアハウスを使うと速い。画面には、運用のみの実行計画（左）と、Fabric DW にプッシュダウンした述語を含むハイブリッドの実行計画が並ぶ |
| 2. 顧客の売上履歴 | ディメンショナルモデル全体に問い合わせる。1 億件の注文のスキャンを含めて**数秒**で終わる。重い処理は Fabric 側で行うが、接続は Postgres のエンドポイントのまま |
| 3. 結合クエリ | ローカルデータ、ミラーデータ、ディメンショナルモデル、整形済みデータセットを、**1 つのクエリで結合**する。大きな分析クエリで **6 秒**。実行計画に、Fabric とローカルの結果セットがマージされる様子が見える |
| 4. ゴールド層への運用クエリ | リバース ETL したゴールドデータにローカルでクエリを実行する。Fabric ではなく Postgres のエンドポイントに問い合わせるため、**ミリ秒**で終わる。経営ダッシュボードの提供向け |

登壇者は、ここまでの内容を次のように整理しました。Fabric HorizonDB では、ワークロードやクエリの種類ごとに、どこで実行するのが適切か、データがどこにあるべきかを選べます。

- **ミラーされたデータ**：Postgres でトランザクションが実行されると、ほぼリアルタイムで OneLake にレプリケートされる。分析的なクエリはミラーデータで、より選択的な運用クエリは Postgres で実行し、必要なら両者を結合する
- **データ全体へのクエリ**：Postgres エンドポイントから、Fabric の任意のデータウェアハウス、レイクハウスに、SQL 分析エンドポイントを経由してクエリできる。それらを Postgres のカタログに登録し、Fabric FDW 拡張機能でアクセスする
- **整形済みデータの読み戻し**：OneLake の整形済みデータを HorizonDB に読み込み、低レイテンシ・高スループットで提供する

### 5.8 AI 連携：Azure AI 拡張機能と Microsoft Foundry

AI のパートでは、AI アプリはデータに根拠づけられたときに最良の結果が出る、という前提から始まります。Fabric HorizonDB では、運用データだけでなく Fabric 全体のデータにアクセスできるため、データベース内の SQL クエリや関数で、プロンプトを補強するためのコンテキストを取り出して Microsoft Foundry のモデルに渡せる、という説明です。

**Azure AI 拡張機能**は、Azure Database for PostgreSQL Flexible Server と Azure HorizonDB では以前から使えるもので、データベースの領域にとどまったまま、SQL で任意の AI モデルとやり取りできます。例えば、セマンティック検索のための新しい埋め込み（embeddings）の生成や、LLM への問い合わせにデータを補うことができます。呼び出しの流れは、Azure AI が Microsoft Foundry とそのモデルへの呼び出しを管理し、モデルが Fabric HorizonDB に応答を返し、HorizonDB がアプリケーションに返します。データベース環境を離れずに、SQL だけで AI アプリを実装できる、という点を強調しています。

### 5.9 デモ 4：アカウントブリーフを生成する

営業チームが顧客との契約交渉などで使う、シンプルな「アカウントブリーフ」ページを Fabric アプリに作る例です。語られた順は次のとおりです。

1. Fabric HorizonDB データベースで利用可能な拡張機能をカタログに問い合わせると、**Azure AI のバージョン 2.4** が使えることがわかる
2. このインスタンスには、Foundry のモデル **GPT 5.4 mini**（発言どおりの表記）が登録されており、自分で作ったエイリアス「Ignite account brief」で呼べる
3. Postgres 関数を 2 つ作成した
   - **account grounding**：顧客 ID を入力として受け取り、その顧客について運用データと分析データを横断して調べ、モデルにコンテキストとして渡すすべてのデータを含む **JSON 断片**を返す。この JSON には、LLM が解釈に使うルールも含まれる
   - **account brief**：account grounding を呼び出し、その結果を、プロンプトとともに Azure AI の generator 関数に渡して LLM に問い合わせる。返される結果のうち、ブリーフのテキストの部分は、完全に AI が生成したものである
4. Fabric アプリで、顧客 ID で検索する。最初のボタンを押すと、右側に、運用データと分析データから取り出されたデータの塊が表示される
5. そのデータを AI 関数に渡すと、**主要な所見と、その顧客への次の推奨アクション**を含む、AI 生成のブリーフが返る。営業チームが新しい契約を交渉するときに頼れる内容だと説明しています

登壇者は、運用と分析の融合が 1 つのエンドポイント・1 つの Postgres 方言で実現し、Foundry の AI 関数とモデルにも、同じデータベース環境の中から簡単にアクセスできる、とまとめています。

## 7. 注意点・発表者の気付き

- **現時点はプレビュー。** ストレージは 4 TB までで、利用にはテナント管理者によるプレビュー機能の有効化が必要です。利用可能になるのは数日以内とのことです。
- **運用データベースだけで分析クエリを実行すると、さらに遅くなる。** デモ 3 のシナリオ 1 で、トランザクションが入ってくる分、先のデモ 2 の約 40 秒よりも時間がかかると述べています。
- **分析クエリは Postgres 単体では難しい。** 列指向ストアも分析向けの最適化も無いため、1 億件を集計するクエリは約 40 秒かかりました。
- **Fabric FDW では、メタデータだけを登録する。** データはコピーされないため、分析データは Fabric 側に残ります。
- **サーバーレスの課金。** アイドル 5 分でコンピュートが止まり、その間はストレージ分だけが課金されます。新しいクエリが来ると数秒で自動再開するという説明で、それ以上の詳細（再開直後の性能など）は触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **インフラ作業が不要**：容量計画、プロビジョニング、数百ある Postgres の設定の管理から解放され、データベースは数秒で作成できる
- **コスト**：使っていないときはコンピュートの料金が発生しない（アイドル 5 分で自動停止）
- **既存資産の流用**：Postgres を使う既存のアプリケーション、ライブラリ、ORM、クライアントがそのまま使え、VS Code の拡張機能で開発できる
- **性能**：デモでは、同じ分析クエリが約 40 秒から約 3 秒になった。結合クエリは 6 秒、ゴールド層のクエリはミリ秒
- **データのコピーが不要**：メタデータだけを登録し、運用データと分析データを 1 つのエンドポイントで結合できる
- **セキュリティと管理**：Entra の資格情報で接続でき、Fabric のロールで権限管理できる
- **AI アプリ**：SQL だけで、データベースの外に出ずに、運用データと分析データを根拠にした AI 生成の結果を得られる

発表では、顧客事例や具体的な導入企業は紹介されていません。

## 9. まとめ

Fabric HorizonDB は、Fabric 内のサーバーレス・フルマネージドの PostgreSQL で、この日パブリックプレビューが発表されました。ミラーリング、Fabric FDW による分析データのクエリ、リバース ETL の 3 つのパスで OneLake とつながり、1 つの Postgres 接続で運用データと分析データをまたいで扱えます。

デモでは、約 1 億件の注文に対する分析クエリがミラーデータの利用で約 40 秒から約 3 秒になり、ゴールド層のデータを Postgres に戻せばミリ秒で提供できること、さらに Azure AI 拡張機能で Foundry のモデルを SQL から呼び出してアカウントブリーフを作れることが示されました。始めるには、テナント管理者にプレビューを有効化してもらい、データベースを作り、VS Code から接続して、Fabric アプリと組み合わせます。
