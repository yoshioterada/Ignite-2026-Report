# THR881 Microsoft Fabric HorizonDB: One PostgreSQL endpoint for AI apps

## 1. はじめに

このセッションは、Microsoft Fabric の新しいワークロード **Fabric HorizonDB** の紹介です。Fabric HorizonDB は、Fabric の中に統合された、フルマネージドでサーバーレスの Postgres エンジンです。数秒で起動でき、Postgres のデータ（運用データ）だけでなく、Fabric のデータウェアハウスやレイクハウスのデータにも、同じ Postgres の接続と SQL 方言のままアクセスできます。

発表の柱は 3 つです。

## 5. 発表内容の詳細

### 5.1 Fabric HorizonDB の概要

Fabric HorizonDB は、Fabric に統合された、フルマネージドでサーバーレスな Postgres エンジンで、数秒で起動します。次の 3 つのアクセスを提供します。

| アクセス | 内容 |
| --- | --- |
| 運用データ | Postgres のストレージにあるデータ |
| 分析データ | Fabric のデータウェアハウスやレイクハウスの成果物（artifact）を、使い慣れた Postgres の方言でクエリでき、Postgres 側の運用データとジョインできる |
| AI | Fabric AI と Microsoft Foundry の AI 機能と統合。データベース内に SQL 関数を書き、LLM モデルを呼び出して RAG などのパターンを実装し、Fabric のデータ資産に基づいて AI モデルを根拠付けできる |

### 5.2 アーキテクチャとプレビュー時の制限

アーキテクチャは、今週一般提供（GA）として発表された **Azure HorizonDB** と同じ土台の上にあります。計算とストレージを分離し、それぞれ独立してスケールできます。

Fabric HorizonDB では、計算層にサーバーレスの機能が加わっています。容量計画やサイジングを考える必要はなく、設定は製品側が面倒を見ます。クエリが来ていないときは計算を自動で一時停止するため、計算分の料金は発生せず、Postgres に最適化されたストレージ層に保存しているデータ分だけを支払う形になります。

現在のパブリックプレビューでは、**データベースのサイズは 4 テラバイトまで**に制限されています。発表者はこれでも相当な量のデータだと述べています。

Fabric HorizonDB は **Fabric apps** のバックエンドにも向いています。Fabric app を作るときに、MS SQL 方言の代わりに Postgres 方言を選び、Fabric HorizonDB をバックエンドに指定できる、という説明です。

### 5.3 事前導入された Postgres 拡張機能

Fabric HorizonDB には、事前に作成・統合された Postgres 拡張機能が多数付いてきます。最初に挙がるのは **Azure AI** 拡張機能で、SQL コマンドや関数から Microsoft Foundry のモデルと対話できます。ほかにも多くの拡張機能があり、発表者の記憶では **72 個**が事前に作成・インストールされています（"if I remember correctly" と前置きされた数字です）。外部パッケージをインストールせずに使い始められると説明されています。

### 5.4 Fabric との 3 つの連携経路

Fabric HorizonDB と Fabric の機能の連携は、次の 3 つの経路で行われます。

1. **OneLake への自動ミラーリング**：Fabric HorizonDB に作成したすべての Postgres データが、自動的かつ透過的に、同期的な方法で OneLake ストレージにコピー（ミラー）されます。OneLake にミラーされたデータは、Delta Parquet の圧縮と列指向ストア（column store）の機能を引き継ぎ、分析ワークロードを実行しやすくなります。
2. **PG Fabric FDW 拡張機能**：専用の Postgres 拡張機能 **PG Fabric FDW** を使い、ミラーされたデータだけでなく、SQL 分析エンドポイントを公開している OneLake 上のほかのデータストア（SQL データウェアハウスやレイクハウスなど）にもクエリできます。Postgres エンジンがデータウェアハウスやレイクハウスとフェデレーション（連携）を作り、同じ接続・同じ Postgres 方言で両方のストアにクエリできます。
3. **reverse ETL**：OneLake で、典型的な **メダリオンアーキテクチャ**（bronze の生データを silver の、例えばディメンショナルモデルや、gold のキュレーション済みデータセットへ変換する構成）を使って整えたデータを、Postgres エンジンへ戻します。発表者は、ダッシュボードやレポートなどを、できるだけ低いレイテンシ・高いスループットで素早く提供したい場合に、Postgres エンジンが最適だと説明しています。トランスクリプトでは "reverse CTL" と聞こえますが、文脈から reverse ETL を指していると考えられます（音声認識の都合で表記が確定できません）。

### 5.5 サーバーレスの仕組みとコスト

プロビジョニングにかかる時間は、現時点でおよそ **5 秒**です。「新しい Fabric HorizonDB データベース」をクリックすると、計算層とストレージ層が起動します。

課金は計算層が動いている時間に対して発生します。スライド上の図では、緑の点がエンジンに入ってくるクエリを表しています。

- クエリが来ている間は、ストレージと計算の両方に料金が発生する。
- **5 分間**クエリが来なければ、計算層をシャットダウンする。この間はストレージのデータ分だけを支払う。
- 一時停止中に新しいクエリが来たら、数秒で計算エンジンを再開する。アプリケーションからは、最初に少し遅延があるだけで、**接続は失敗しない**。
- 再開後は、次の 5 分間のアイドル間隔が来るまで使い続けられる。

発表者は、システムの中で最もコストの高いリソースである計算を、使っている時間だけ支払うのが利点だと述べています。これが **Azure HorizonDB との最大の違い**で、Azure HorizonDB は常時稼働のシステムのため、プロビジョニングすると使っていてもいなくても課金が続きます。

### 5.6 連携の詳細：リモートテーブルとジョイン

連携経路の図では、左にアプリケーションがあり、Fabric HorizonDB のインスタンスに接続します。インスタンスには、customers や orders のような典型的なトランザクション向けのローカルテーブルがあり、アプリがこれらだけを使うのも問題のないシナリオです。

Fabric との統合を使うと、数個のシンプルな DDL 文で、Fabric 側にあるウェアハウス、レイクハウス、ミラーデータベースのリモートテーブルを、ローカルテーブルのように登録できます。説明では、`fabric` という別のスキーマを選んで登録しています。以後は、同じ Postgres 方言・同じ接続のまま、Fabric Data Warehouse のデータを Postgres アプリから読めます。

さらに、ローカルテーブルとリモートテーブルを、標準の SQL でジョインすることもできます。特別なコマンドは不要で、アプリのロジックを変える必要もありません。

この構成が役に立つ理由として、次の点が挙げられています。

- 非常に大きなテーブルを集計・分析したい場合がある。
- Postgres エンジンはトランザクション処理に最適化されており、重い分析クエリは得意ではない。実際、Postgres エンジンには現時点でネイティブの列指向ストアがない。
- Fabric 側の投資、例えば GPU アクセラレーションされたクエリや、クエリプランの最適化の恩恵を、Fabric の成果物を Fabric HorizonDB に登録するだけで受けられる。

トランザクション処理の部分と分析処理を一緒に行うこの種のシナリオは、**trans-analytical apps**（発表者の呼び方）と呼ばれ、Fabric HorizonDB が可能にするのはまさにこれだ、と説明されています。

### 5.7 AI アプリ向けの構成

発表者は、Satya 氏をはじめ多くのリーダーが週を通して語っていたように、AI アプリは実データに根拠付けされていると良い結果を出す、と述べています。Fabric HorizonDB は、運用データと分析データに同じ接続でアクセスできるため、データを準備して AI モデルに送るのに最適な場所です。用途としては、セマンティック検索型の分析や、データ分析的な分析などが挙げられました。

この構成が可能なのは、**Azure AI 拡張機能が Fabric HorizonDB にネイティブに組み込まれている**からです。流れは次のとおりです。

1. アプリケーションが Fabric HorizonDB に、Azure AI 関数を呼び出す SQL リクエストを発行する。
2. その SQL は、Postgres エンジンおよび Fabric DW エンジンの両方からクエリしたデータと組み合わせて使える。
3. 大量のデータが準備できたら、Azure AI 拡張機能に渡す。拡張機能は、Microsoft Foundry にインストール・デプロイした任意のモデルを呼び出す。
4. モデルがレスポンスを返し、Fabric HorizonDB がアプリケーションに返す。

単一の接続、単一の Postgres 方言で、複雑さをシステム側に押し込む、というのがこの構成の特徴です。

## 6. デモ・手順

### 6.1 作成と接続

1. Fabric のプロビジョニング画面で、新しいアイテムを作成する。必要なのはデータベース名だけで、ほかの設定は不要。数秒で、ワークスペースに Fabric HorizonDB が立ち上がる。
2. 操作には Fabric の SQL エディターも使えるが、開発者向けには **Visual Studio Code** のボタンをクリックし、VS Code で開ける。使うのは、Microsoft が以前に作った Postgres 拡張機能で、ローカルマシン、ローカルのデータセンター、Azure 上の Postgres サービスなど、どの Postgres にも使える。
3. この拡張機能で、Azure サブスクリプションに加えて **Fabric のワークスペース**も閲覧でき、作成したデータベースを見つけて接続できる。
4. 拡張機能には監視用のダッシュボードがあり、データベースに負荷をかけている上位のクエリ、現在開いているセッション、待機統計などが分かる。

### 6.2 運用クエリの確認

1. バージョンを確認し、**Postgres 17 の HorizonDB 版**であることを見る。
2. customers、orders、products などの、典型的なリレーショナルデータベースを作成する。orders テーブルには約 **1 億行**があり、かなり大きなデータベースである。
3. インデックスが効いているため、主キーによる検索クエリは非常に高速。より複雑な運用クエリも問題なく動く。
4. VS Code の Postgres 拡張機能のグラフィカルな表示で、実行計画も確認できる。

### 6.3 分析クエリの高速化

1. 「過去の売上上位 100 顧客」を求める分析クエリを実行する。約 1 億件の orders を customers とジョインする、大規模なスキャンと集計のクエリであるため、Postgres エンジンでは**約 40 秒**かかり、期待より少し長い。
2. すべてのデータベースは自動で OneLake にミラーされている。ミラーされた 1 億行のテーブルなどを、OneLake から、自分のローカルの Postgres スキーマにインポートする。インポート後は、ローカルのテーブルのようにクエリできる。
3. 同じクエリを、orders テーブルだけ、以前の `OLTP` スキーマから `OLAP` スキーマに変えて再実行する。実行時間は 40 秒から **3.8 秒**になる。
4. 発表者は、運用データを Fabric の分析エンドポイントと統合し、重い処理の部分を、ローカルの Postgres ストレージではなく Fabric DW エンジンにプッシュダウンした効果だと説明しています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **運用・分析・AI を 1 つの接続で**：同じ Postgres 方言で、Postgres のデータ、Fabric のウェアハウスやレイクハウスのデータ、Foundry のモデル呼び出しを扱える。アプリのロジックを変える必要がない。
- **性能**：デモでは、1 億行規模の orders を使った分析クエリが、40 秒から 3.8 秒になった。
- **コスト**：計算は使った時間だけ、ストレージのデータ分は常に支払う。5 分のアイドルで自動停止する。
- **運用の手間**：容量計画やサイジングが不要で、数秒（現在は約 5 秒）で起動する。
- **導入のしやすさ**：72 個の拡張機能が事前に導入済みで、外部パッケージをインストールせず使い始められる。
- **開発環境**：VS Code の Postgres 拡張機能から、Fabric のワークスペース内のデータベースへ接続・監視できる。

## 9. まとめ

Fabric HorizonDB は、Fabric 内の、サーバーレスでフルマネージドな Postgres エンジンです。ミラーリング、PG Fabric FDW、reverse ETL の 3 つの経路で OneLake・Fabric のウェアハウスやレイクハウスとつながり、Azure AI 拡張機能で Foundry のモデルを SQL から呼び出せます。デモでは、重い集計クエリを Fabric 側にプッシュダウンして 40 秒から 3.8 秒に短縮しました。現在はパブリックプレビュー（4 TB まで）で、Fabric テナント管理者が管理ポータルでプレビューのワークロードを有効にすれば試せます。
