# THR884 Two PostgreSQL services, one confident architecture decision

## 1. はじめに

このセッションは、Azure で使える 2 つの PostgreSQL ベースのマネージドデータベース、**Azure Database for PostgreSQL Flexible Server**（以下 Flexible Server）と、今週一般提供（GA）が発表された **Azure HorizonDB**（以下 HorizonDB。発表では "Azure Horizon DB" と発音されています）を比較し、「どのワークロードにどちらを選ぶか」を整理する内容です。

結論は明快です。登壇者の推奨は、**オープンソースの PostgreSQL との完全な互換性や、小規模・低コストを重視するなら Flexible Server、Tier 1（ミッションクリティカル）の性能、高速なフェイルオーバー、読み取りのスケールアウト、大規模・AI 連携を重視するなら HorizonDB** というものです。両者は同じ PostgreSQL のコードベースの上に作られているため、どちらを選んでも土台は同じだと説明されています。

このセッションは約 25 分の短い登壇で、画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。

## 3. 何に関する発表か

テーマは、2 つの Azure の PostgreSQL サービスの**位置づけと選び方**です。登壇者は、Flexible Server がすでに数年前から一般提供されていること、HorizonDB が今週 GA になったことを背景に、顧客やパートナーが自分のニーズに合うサービスを判断できるよう、2 つを比較すると説明しています。

発表の流れは次のとおりです。

1. 2 つのサービスの共通点と基本的な違い
2. ストレージとパフォーマンスの考え方の違い
3. 高可用性、プロビジョニング、フェイルオーバー、読み取りスケールアウトの違い
4. AI 機能の違い
5. 価格の比較
6. どちらを選ぶべきかの判断基準と、Flexible Server から HorizonDB への移行
7. 締めと、Microsoft による PostgreSQL への貢献

## 4. 発表者が伝えたいメッセージ

最大のメッセージは、**選択はワークロードで決まる**という点です。登壇者は、2 つのサービスは同じ PostgreSQL をベースにしており、PostgreSQL の方言も、ドライバーも、ライブラリも同じで、どちらも Microsoft Entra ID 認証やカスタマー管理キーによる暗号化といったエンタープライズ級のセキュリティを備えたマネージドサービスだと説明しています。だからこそ、顧客は自信を持ってどちらでも選べる、という立場です。

そのうえで違いが出るのはアーキテクチャです。Flexible Server は「最も互換性の高い PostgreSQL」、HorizonDB は「プレミアム（Tier 1）のミッションクリティカル向けサービス」と位置づけられています。また登壇者は、最近の AI 関連の投資の多くは HorizonDB に向かっていると述べています。

もう 1 つのメッセージは、「小さく始めて大きくなれる」道があることです。Flexible Server から HorizonDB へ、ほぼダウンタイムなしで移行できるツールが用意されていると説明しています。

## 5. 発表内容の詳細

### 5.1 2 つのサービスの位置づけ

| 項目 | Flexible Server | HorizonDB |
| --- | --- | --- |
| 位置づけ | マネージドのオープンソース PostgreSQL サービス | クラウドネイティブな PostgreSQL 実装。プレミアムの Tier 1 ミッションクリティカル向け |
| エンジン | 自分の仮想マシンやサーバーにインストールできるのと同じ PostgreSQL エンジンを選べる。コミュニティの新しい機能を最も早く取り込める | コンピュートとストレージを分離（disaggregate）した新しいアーキテクチャ |
| ストレージ | 顧客がサイズや IOPS を決める | 完全に新しい分散ストレージ。非常に信頼性が高く、数百 TB まで拡張できる |
| 運用上の責任 | 高可用性を使うか、リードレプリカを何台にするかなどを顧客が決める | ストレージの構成を考える必要がない |

共通点として、Flexible Server も HorizonDB も、Microsoft のプラットフォームで完全にマネージドされ、Entra ID 認証やカスタマー管理キーによる暗号化といった安全性を備えています。

HorizonDB は、ストレージとコンピュートの両方で水平スケールアウトを標準で備えます。読み取りの多いワークロードに対しては、必要なだけリードレプリカを作って対応します。

### 5.2 ストレージ：IOPS を決める世界と決めなくてよい世界

Flexible Server では、サーバーをプロビジョニングするときに、コンピュートの構成とストレージの構成を決めます。スパイクのあるワークロードの場合、ストレージが提供する IOPS の上限（スライド上の点線）をどこに置くかを自分で決めることになります。

- 高く置きすぎると、必要以上にコストがかかる
- 低く置きすぎると、データベースの性能に影響する
- 最大ストレージサイズも自分で選ぶ

そのため、ワークロードをよく理解したうえで、この線をどこに置くかを決める必要がある、と登壇者は話しています。

HorizonDB では、同じスパイクのあるワークロードでも IOPS の上限を決める必要がありません。ストレージは Microsoft が裏で管理し、必要に応じて水平に拡張します。現時点のサポート上限は **128 TB** ですが、必要なら実際にはそれ以上も追加できると述べています（トランスクリプトでは "under 28 terabytes" とも聞こえますが、文脈から 128 TB と読み取れます。音声認識の都合で表記が揺れています）。

HorizonDB の新しいストレージは、ログ（発話では "wall management" と聞こえ、WAL を指すと思われますが確定できません）の管理とデータの管理を分離しています。これにより、トランザクションのコミットのレイテンシは現在 **1 ミリ秒未満** になり、同等の Flexible Server より大幅に速くなる、と説明しています。

### 5.3 高可用性とストレージのコスト

高可用性の構成は、2 つのアーキテクチャで大きく異なります。

**Flexible Server** は、オンプレミスの PostgreSQL と同様に、プライマリとホットスタンバイ、さらに読み取りの負荷に応じた数のレプリカを作ります。トランザクションが来ると、プライマリ、ホットスタンバイ、必要なら全リードレプリカにコミットする必要があります。ストレージのコピーが 3 つできるため、**データベースが使っているストレージ量の 3 倍を支払う**ことになります。

**HorizonDB** は、ストレージ層がデータの**コピーを 1 つだけ**提供します。裏側では冗長なストレージ（発表では "so redundant storage" と聞こえ、正確な名称は音声認識の都合で確定できません）を使い、高い冗長性を持ちますが、**支払うのは 1 コピー分だけ**です。その上に、必要な数だけリードレプリカを作れます。プライマリがトランザクションをコミットすると、それは直ちにすべてのリードレプリカから利用可能になります。登壇者によると、これによって書き込みスループットが最大で **8 倍**向上します。この数字は、Microsoft 自身のベンチマークで測定した値だと述べています。

### 5.4 プロビジョニングとサイジング

| 項目 | Flexible Server | HorizonDB |
| --- | --- | --- |
| コンピュート | VM ファミリー（Burstable、D シリーズ、E シリーズなど）を選ぶ。キャパシティプランニングは顧客の責任 | VM の詳細は選ばず、必要なノード数と、ノードあたりのコア数だけ選ぶ |
| コアとメモリの比率 | ニーズに応じて複数の比率から選べる | コア 1 に対し RAM 8 GB で固定（Microsoft があらかじめ決めている） |
| ストレージ | 32 GB から 64 TB まで。ストレージは自分で管理する | 現時点で 128 TB まで。IOPS は選ばず、管理は Microsoft が行う |
| PostgreSQL のバージョン | 現在サポートされているオープンソースのバージョンから選べる | Microsoft が提供するバージョンを決める。現在は PG17 をサポートし、PG18 も利用できる。選択肢は限られる |

登壇者は、Flexible Server で任意のバージョンを選べる点が好きだと述べています。

### 5.5 フェイルオーバー

フェイルオーバーは「重要な差別化ポイント」だと説明されています。

- **Flexible Server**：プライマリが落ちたとき、すべてのトランザクションがコミットされていることを確認し、さらに新しいレプリカを作り直して、健全な高可用性の状態に戻す必要がある。登壇者によると、プライマリの混み具合によっては、フェイルオーバーに **60 秒程度**かかることもある。
- **HorizonDB**：データを移動する必要がなく、ストレージは同じままで、新しいリードレプリカを指し示して新しいプライマリにするだけで、データベースは動き続ける。通常は **5 秒未満** でフェイルオーバーでき、これが HorizonDB の **99.995% の可用性 SLA** に重要だと説明している。

### 5.6 読み取りのスケールアウト

1 つのアプリケーションがデータを書き、多数のアプリケーションが読み取るような場面では、アーキテクチャの違いが出ます。

Flexible Server では、**リードレプリカ**（プライマリのデータの同期コピー。発表で "synchronous copy" と述べています）を最大 5 つまで作れます。登壇者は、OpenAI が ChatGPT サービスで、この構成を使って Flexible Server の読み取りワークロードをスケールさせている例を挙げています。

> 補足：このあたりで登壇者が「5 つのうちの 1 つが追加のレプリカを持てる」という趣旨の発言をしていますが、文が途切れていて意味を確定できません。ここでは触れていません。

HorizonDB はストレージが 1 コピーなので、その上に好きなだけリードレプリカを作れます。

### 5.7 AI 機能

データベースの中に AI の機能を取り込む取り組みは、数年前に **Azure AI** という PostgreSQL 拡張から始まりました。Flexible Server と HorizonDB の両方がこの拡張を提供しており、SQL 言語から LLM モデルとやり取りして、セマンティック検索やデータのエンリッチメントなどの AI 関連ワークロードを実装できます。

ただし、最近の投資の大半は HorizonDB に向かっています。登壇者は、HorizonDB では AI インフラの部分がデータベース層の内部に統合されているため、利用者がそれを意識する必要がないと説明しており、次のような新機能が挙げられています。

| 機能 | 内容 |
| --- | --- |
| モデルの管理を代行 | Flexible Server では、Microsoft Foundry でモデルをプロビジョニングし、Postgres に登録してから使う。HorizonDB では**チェックボックスを選ぶだけ**で、AI モデルが Microsoft によってプロビジョニングされ、すぐ使える。管理の手間が減り、アプリケーションとの統合が進む |
| マルチモーダルエンジン | リレーショナル、全文検索、グラフ検索、ドキュメントモデルを 1 つのデータベースサービスで扱える |
| ベクターインデックスの最適化 | ベクターインデックス（発話では "KNN" と聞こえますが、音声認識の都合で名称が確定できません）を、HorizonDB が標準で持つキャッシュ機構を活用するようチューニングしている。ベクターワークロードでは、Flexible Server より大幅に高い性能が得られる |
| AI pipelines | RAG パターンのためにリレーショナルデータを準備する、耐久性のあるワークフロー。チャンク分割、埋め込み（embedding）の作成と保存といった準備を、アプリケーションではなくデータベースの中で行える。アプリケーションコードが単純になる |

### 5.8 価格の比較

登壇者は、小さく始める場合は Flexible Server のほうが安いと説明しています。Flexible Server には、HorizonDB より安い VM ファミリーの構成があるためです。Flexible Server は、最小のワークロードも含めて「最も柔軟な選択肢」として設計されているという位置づけです。

- B シリーズや D シリーズの単一ノードは、HorizonDB より**大幅に安い**
- E シリーズでも相対的に安く、差は **25% 以内**程度。ただし、差がもっと大きくなることもある
- 一方、HorizonDB の単一ノードは、Flexible Server の **4 倍のローカル SSD キャッシュ**を持つ。ワークロードがデータの一部に高頻度でアクセスし、このキャッシュが効く場合は、HorizonDB のほうが大幅に高い性能を出せる
- **AI と高可用性を使う構成にすると、HorizonDB のほうが安くなりうる**。Flexible Server の高可用性は、データベースの 2 つ目のコピーを作る必要があり、そのコピーが高価なため。その場合は両者の価格差はそれほど大きくない、と説明している

要するに、シングルノードの安さは Flexible Server が勝りますが、高可用性と性能を伴う本番構成になると、HorizonDB のほうが競争力を持つ可能性があるという話です。

### 5.9 どちらを選ぶか

**Flexible Server を勧めるとき**

- オープンソースの PostgreSQL との**完全な互換性**が最優先のとき
- 新しい PostgreSQL バージョンを、リリースと同時に使いたいとき。Flexible Server では新バージョンを **day zero** で採用でき、オープンソースのチームが新しい PG バージョンをリリースした時点で使える。HorizonDB ではそうではない
- 単一サーバー構成で、最も安い選択肢を求めるとき
- 汎用の OLTP アプリケーション。セキュリティ、保存時の暗号化、プライベートネットワークといったエンタープライズ級の機能はあるが、最も安価な選択肢になりうる
- 小規模でバースト性のあるエントリーレベルのワークロード
- 完全な Postgres 互換性が必要な典型的な OLTP ワークロードで、適切な VM ファミリーでコンピュートを拡張できる場合

**HorizonDB を勧めるとき**

- **Oracle から Postgres への大規模な移行**：登壇者によると、Oracle や Exadata のアプリケーションを Postgres に移したいという問い合わせが毎日来ている。HorizonDB は単一クラスターで最大約 **3,000 コア**までスケールでき、1 ノード 192 コア、最大 15 台のリードレプリカで、読み取りも書き込みも重い（Oracle 移行にありがちな）アプリケーションに対応できる
- JSON だけでなく、グラフ、ベクター、全文検索も必要な、マルチモーダルなモダンアプリ
- 高速なフェイルオーバー（5 秒未満。Flexible Server は主サーバーの混み具合によるが 60 秒程度かかることがある）が必要なとき
- 生産者より消費者（読み取り側）のほうが多い、読み取りスケールアウトのワークロード
- IOPS に課金されない点：Flexible Server では IOPS を事前にプロビジョニングする必要があり、使っても使わなくてもコストがかかる。そのため、予測できないバースト性のあるワークロードでは HorizonDB が最適になりうる
- 将来、データベースのボリュームやサイズが大きく増えそうなとき。数百 TB のデータを置く余地がある
- Tier 1 の性能が必要なとき

### 5.10 Flexible Server から HorizonDB への移行

登壇者は、Flexible Server から HorizonDB への「最良の移行パス」を提供していると述べています。Azure の Postgres 移行ツールで、既存の Flexible Server に接続し、スキーマとデータを移行し、最後の切り替え（カットオーバー）を、実質的なダウンタイムなしで行えます。小さく始めて、最大規模のワークロードまで拡張したい場合の選択肢になると説明しています。

### 5.11 締め

登壇者は、今週時点で両方のサービスが GA であり、次の Postgres ワークロードを Azure で動かすなら、2 つのサービスを見て、ワークロードに合うほうを選んでほしいと話しています。また、Microsoft には PostgreSQL の最大のコミッターグループが所属しており、オープンソースの PostgreSQL コードにバグが見つかった場合も含め、エンドツーエンドでサポートできると述べています。これは業界で一般的ではない、という説明です。

## 7. 注意点・発表者の気付き

- HorizonDB は、**サポートする PostgreSQL バージョンが Microsoft により決められ、選択肢が限られます**。現在は PG17 をサポートし、PG18 も利用できます。新しい PG バージョンの day zero 対応は Flexible Server のみです。
- 小さな単一ノード構成では、Flexible Server のほうが明確に安くなります。HorizonDB が価格面で競争力を持つのは、高可用性や AI を含む構成になったときだと説明されています。
- Flexible Server では、コンピュート構成、ストレージの容量、IOPS、高可用性の有無、リードレプリカ数などをすべて顧客が決める必要があります。特に IOPS の上限は、高く置きすぎるとコストが増え、低く置きすぎると性能に影響すると説明されています。
- 現時点のストレージ上限は、Flexible Server が 64 TB、HorizonDB が 128 TB です（HorizonDB は必要ならこれ以上も追加可能と説明されています）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 共通の PostgreSQL 基盤、同じドライバーとライブラリ、同じエンタープライズ級のセキュリティ（Entra ID 認証、カスタマー管理キー）により、どちらを選んでも安心して使える
- HorizonDB では、IOPS やストレージの上限を考えなくてよく、使っていない IOPS の分を払わなくてよい
- HorizonDB では、データのコピーは 1 つ分の料金で済む（Flexible Server は 3 倍）
- 書き込みスループットが最大 8 倍（Microsoft のベンチマーク）、コミットのレイテンシが 1 ミリ秒未満、フェイルオーバーは 5 秒未満、可用性 SLA は 99.995%
- HorizonDB では、AI モデルをチェックボックスで用意でき、AI pipelines により RAG の準備をデータベースの中で行える
- Flexible Server から HorizonDB へ、ほぼダウンタイムなしで移行できる
- Microsoft に PostgreSQL の最大のコミッターグループがおり、バグが見つかった場合も含めてサポートされる

## 9. まとめ

- Flexible Server と HorizonDB は同じ PostgreSQL を土台にした Azure のサービスで、どちらも GA です。選択はワークロードで決まります。
- **Flexible Server**：完全なオープンソース互換、新しい PG バージョンの day zero 対応、単一ノードの低コスト、小規模から汎用 OLTP まで。
- **HorizonDB**：コンピュートとストレージの分離、IOPS 不要の分散ストレージ（現在 128 TB まで）、5 秒未満のフェイルオーバー、最大 15 台のリードレプリカと約 3,000 コア、AI 機能の統合。Oracle からの大規模移行や、読み取りスケールアウト、バースト性のあるワークロードに向く。
- 小さく始めて、あとから HorizonDB に移行する道もあります。
