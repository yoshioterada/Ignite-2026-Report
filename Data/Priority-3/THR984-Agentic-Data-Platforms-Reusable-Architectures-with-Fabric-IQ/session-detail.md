# THR984 Agentic Data Platforms: Reusable Architectures with Fabric IQ

## 1. はじめに

このセッションは、ビジネスの問いに AI エージェントが信頼できる答えを返せるようにするために、データ基盤をどう作るかを 5 つのパターンで整理した約 25 分の発表です。題材は、ハイキング用品のオンラインショップ「Contoso Outdoors」で突然起きた購入失敗のインシデントです。デジタルコマースの責任者 Maya が「どの購入が失敗したのか」「いくらの損失か」「なぜ起きたのか」「次に何をするか」を知りたい、という流れで話が進みます。

登壇者が最後に持ち帰ってほしいとしたメッセージは 3 つです。**エージェントを作る前に基盤を作ること、ビジネスを一度だけモデル化すること（Fabric IQ と ontology）、エージェントは提案し、最終的に決めるのは人であること**です。

このセッションを読むと、次のことが分かります。

- 5 つのパターン（信頼できるデータ、共有メトリクス、ビジネスコンテキスト、専門エージェント、制御されたアクション）の役割
- 共有の semantic model と Fabric IQ の ontology を、データエージェントからどう使うか
- Microsoft Foundry のコーディネーターエージェントが、複数のデータエージェントとインデックスをどうまとめるか

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR984](https://ignite.microsoft.com/en-US/sessions/THR984)

## 3. 何に関する発表か

## 4. 発表者が伝えたいメッセージ

発表者は、エージェントを作る前に基盤を作ることが、信頼でき持続可能な結果を得るために最も重要なステップだと述べています。そのため、まず信頼できるデータを作り、次に指標の定義を共有し、さらにビジネスの意味をモデルとして持たせる、という順序を示しました。

また、エージェントに全部を任せる設計にはしません。1 つの巨大なエージェントに全データと巨大なシステムプロンプトを持たせるのは持続可能ではない、というのが発表者の意見です。担当範囲の明確な専門エージェントを使えば、誰が何を処理したかが明確になり、洞察を再利用・追跡できると説明しています。最後のパターンでも、エージェントの提案に対して人の承認を挟み、実行後の結果を検証する形を取ります。

## 5. 発表内容の詳細

### 5.1 シナリオ：Contoso Outdoors の購入失敗

発表者は、オンラインショップで買い物をしているときに、スピナーが回り続けて先に進まない、あの不安な状況から話を始めています。「ちゃんと通ったのか」「もう一度押すと二重に課金されないか」と不安になる画面の裏側では、店舗側に購入失敗の赤い線が積み上がっています。

Contoso Outdoors は、テント、バックパック、ブーツなどのハイキング用品を扱うオンラインショップです。通常の忙しい日の購入成功率は約 96% です。ところが当日は 2 時 5 分（発表では "2.05" と読まれており、午前・午後は語られていません）に成功率が 70% まで下がり、「約 3 人に 1 人が、カートがいっぱいのまま何も買わずに帰る」状態になりました。デジタルコマースを担当する Maya は、早く答えを知りたく、それを AI エージェントに助けてほしいと考えています。

### 5.2 パターン 1：Trusted data

最初の質問は「どの購入が本当に失敗したのか」です。複数のソースシステムにあるデータを集めて検証し、重複を取り除き、バージョン履歴も残します。最終的な目標は、再利用できるデータプロダクトを作ることです。

そのために使うのが data contract です。発表では次の取り決めを挙げています。

- オーナーを決める
- 1 行が何を意味するかを定義する
- キーを決める
- 品質チェックを設ける

このパターンは投票で選ばれなかったため、詳細ではなく結果のみが紹介されました。画面には、品質チェックと共通の data contract を設定したノートブックが示されています。Maya のケースでは、失敗した支払い試行が約 3,500 件、失敗した購入は 1,144 件でした。試行回数だけを数えると、問題が実際より大きく見えてしまう、というのがこのパターンの示す点です。

### 5.3 パターン 2：Shared metrics

2 つ目の質問は「このインシデントはいくらの損失か」です。発表者によると、多くの企業では、同じ OneLake のデータを読むレポートやエージェントが、それぞれ独自の計算式を持っていて、少しずつ違う答えを出します。Maya は、どの数字を信じてよいか分かりません。

そこで、ドメイン別の共有 semantic model を作り、承認済みの指標（business KPI）をそこに定義します。エージェントには事前に決めた固定の指標だけを使わせ、勝手に推測させないという狙いです。データは OneLake にそのままあり、その上に共通のレイヤーが入ります。レポートも、エージェントも、Copilot も、事前に確立されたこの指標を信頼して使えます。

デモでは、Power BI レポートと、共有指標を使うデータエージェントの両方に同じ質問をしています。語られた内容は次のとおりです。

- レポートの baseline（平常時）の購入成功率は 96%。失敗は一般的なミスによるもの
- インシデント期間は購入成功率が 70% で、最も多いエラーは payment timeout
- semantic model には、承認済みの指標として purchase success rate が 1 つの定義と 1 つの数値フォーマットで入っている。説明（description）も追加されている
- データエージェントに同じ質問をすると、独自の計算式は書かず、semantic model から承認済みの指標を読み、レポートや他のエージェントと同じ答えを返す
- 失敗した購入の件数や成功した件数について、完全な分析が返ってくる。裏側のクエリを見ると、データソースとして接続した semantic model を参照し、承認済みの指標を読んでいることが分かる。画面の左側には、データエージェントに接続された semantic model が表示されている

> 補足：このデモで損失額（金額）が示されたかどうかは、音声からは確認できません。語られたのは、成功率、エラーの種類、失敗件数の分析結果までです。

### 5.4 パターン 3：Business context（Fabric IQ と ontology）

3 つ目の質問は、成功率の落ち込みが何とつながっているのか、です。ここで Fabric IQ の ontology が登場します。

スライドの右側には ontology のモデルが描かれ、青色で entity と、その間のつながりが示されました。発表者の説明では、ontology は次の要素で構成されます。

- **Entity type**：スライドに出てきたのは update、purchase、order など
- **Key**：entity ごとに 1 つの識別子
- **Data binding**：OneLake や lakehouse にすでにあるデータで、モデルを裏付ける
- **Relationship**：entity 同士の関係を、自然言語で表現できる。発表者は「以前はできなかった」と述べています

目的は、人とエージェントが同じ言葉で話し、同じ意味を理解することです。スライドの例では、支払い関連の update が payment service を変更し、payment service が purchase を支え、purchase は order によって作られる、というつながりが示されました。この後のデモでは、この構造をたどって、落ち込みの起点となった update までさかのぼります。

デモでは、Fabric 上の Contoso Outdoors ontology を開いています。

1. 画面に entity と、その関係が自然言語で表示される。payment attempt と purchase、purchase と order、そして customer のつながりが見える
2. service と update を拡大し、つながりを確認する
3. service をクリックすると、メタデータとして description と synonym（同義語）を追加できる。これらはエージェントが扱うビジネス用語になる
4. relationship を見たあと、data binding がプロパティにどう接続されているかを見せる。データは lakehouse の OneLake データにつながっている。ここでも description と synonym を設定できる
5. データエージェントに「購入が失敗している理由」「どの update が payment service を変えたか」「それが何件の失敗購入に影響したか」を尋ねる
6. 回答では、payment timeout が失敗の原因とされ、不確実性とデータの根拠についての情報も付く。ontology にアクセスできるため、エージェントは SQL クエリを生成してデータに対して実行する。発表者自身は SQL を書いていない
7. 画面左側に表示されるソースが ontology であり、データエージェントに数クリックで接続でき、lakehouse のデータが裏付けとなっている

### 5.5 パターン 4：Specialist agents

4 つ目は、Maya が「なぜ起きたのか」の全体像を知るための専門エージェントです。発表者は、1 つの大きなエージェントに全種類のデータと巨大なシステムプロンプトを持たせる作り方が多いが、ビジネスコンテキストとルールを 1 つのエージェントに集約して保守し続けるのは持続可能とは言えない、と述べています。

提示された構成は次のとおりです。

- Maya が使うアプリケーションは Microsoft Teams の 1 つだけ
- Teams は、オーケストレーター（コーディネーター）である Foundry agent につながる
- コーディネーターが質問を振り分け、適切なツールを選ぶ
- ツールは、business impact のデータエージェント、operations のデータエージェント、そして runbook と policy constraint を入れたインデックス（knowledge）

誰が何を担当するかが明確になり、ビジネス上の問いに対する洞察を再利用でき、追跡できるようになる、というのが効果として語られました。

デモでは、Microsoft Foundry 上のコーディネーターに「なぜこのインシデントが起きたのか」を尋ねています。会場で Foundry を使ったことがある人は多く、発表者は、見覚えのある画面もあるはずだが、ここで見てほしいのは Foundry を Fabric IQ、データエージェント、共有ビジネス言語とつなぐ方法だと前置きしました。

1. instruction（指示）で、エージェントの振る舞いと回答の形式を設定する。ここでは impact、cause などを含む回答フォーマットを設定している
2. tools を見ると、Foundry と Fabric IQ にアクセスできるデータエージェントと、インデックスが接続されている
3. 理由を尋ね、impact の根拠と次のステップも出すよう依頼する。回答は設定した形式に沿っており、提案される next step と、使われたデータソースも表示される
4. データソースとして、runbook とインシデント調整計画のインデックスが使われていることが分かる
5. trace では複数のツール呼び出しを確認できる。コーディネーターは business impact エージェントと operations エージェントの両方と、インデックスを使っている
6. publish を選ぶと、コーディネーターエージェントを Microsoft Teams または Copilot に公開できる

### 5.6 パターン 5：Controlled actions

最後の質問は、「エージェントが何をすべきか分かったとして、それを実行してよいか」です。エージェントが提案を出し、それを人が承認（authorize）し、その後に実行と検証へ進みます。この一連の流れを発表者は verified recovery（検証済みの回復）と呼んでいます。エージェントが提案する行動には、人が関与するべきだと強調されました。

このパターンは投票で選ばれなかったため、デモではなくスクリーンショットでの紹介です。発表者は、これはシミュレーションで、画面に manual trigger と表示されているのはそのためだと説明しています。画面は Power Automate で、承認待ちの状態です。Maya は Teams 上でその承認依頼を見て、詳しい情報を確認するか、すぐに承認できます。

### 5.7 5 つのパターンのまとめと 3 つの持ち帰り

5 つのパターンの役割は、次のように整理されました。

- 信頼できるデータで、ビジネスについて信頼できる事実を持つ
- 共有メトリクスで、アプリケーションとエージェントの間で一貫した数字を保つ
- ビジネスコンテキストで、ビジネスとエージェントが共通の言語を持つ
- 制御されたアクションで、結果を検証し、特定の種類のアクションには承認を求める

これらによって Maya は 1 つの答えを得られ、その答えの各行は元のソースまでたどれる、と発表者は述べています。

最後の 3 つの持ち帰りは、冒頭で述べたとおりです。エージェントを作る前に基盤を作ること（信頼性が高く持続可能な結果を得るために最も重要なステップ）、ビジネスを一度だけモデル化すること（Fabric IQ と ontology）、エージェントは提案するが最後に決めるのは人であること、の 3 点です。

## 6. デモ・手順

このセッションにはデモがあります。参加者の投票で選ばれた 3 つ（ビジネスコンテキスト、共有メトリクス、専門エージェント）がデモで、Trusted data は結果の紹介のみ、Controlled actions はスクリーンショットでの紹介です。画面の細部は音声からは確認できないため、語られた範囲で整理します。

| パターン | 形式 | 語られた内容 |
| --- | --- | --- |
| 1. Trusted data | ノートブックの結果を紹介（詳細は説明せず） | 品質チェックと data contract を設定。失敗した支払い試行は約 3,500 件、失敗した購入は 1,144 件 |
| 2. Shared metrics | デモ | Power BI レポートとデータエージェントに同じ質問をし、semantic model の承認済み指標を参照して同じ答えが返ることを確認 |
| 3. Business context | デモ | Fabric 上の ontology（entity、関係、description、synonym、data binding）を確認し、データエージェントが ontology から SQL を生成して答える |
| 4. Specialist agents | デモ | Foundry のコーディネーターに理由を尋ね、2 つのデータエージェントとインデックスを使った回答と trace を確認。Teams / Copilot への publish を見せる |
| 5. Controlled actions | スクリーンショット | Power Automate の承認待ちと、Teams での承認画面（シミュレーション） |

手順の詳細は 5.3、5.4、5.5 に、語られた順で記載しています。

## 7. 注意点・発表者の気付き

- 失敗件数は、試行回数だけで数えると問題が実際より大きく見えます。このケースでは、失敗した支払い試行が約 3,500 件であるのに対し、失敗した購入は 1,144 件でした。
- 同じ OneLake のデータを読んでいても、レポートやエージェントごとに計算式が違えば答えが変わります。共有の semantic model に承認済みの指標を置くことで、この食い違いを防ぎます。
- 1 つの大きなエージェントにすべてのコンテキストとルールを持たせる設計は、保守の面で持続可能とは言えない、と発表者は述べています。
- 制御されたアクションの画面は、発表者が「シミュレーション」と明言しており、画面に manual trigger と表示されています。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- レポート、エージェント、Copilot が同じ承認済み指標を読むため、数字が一貫する
- ontology と data binding により、データエージェントが SQL を自動生成して答えられる。ユーザーが SQL を書く必要はない
- 専門エージェントとコーディネーターによって、誰が何を担当するかが明確になり、洞察を再利用・追跡できる
- Maya のようなビジネス担当者は、Teams（または Copilot）という 1 つの入口からエージェントを使える
- 最終的な回答の各行は、元のソースまでたどることができる
- 承認を挟んだ実行と検証により、エージェントの行動を人が管理できる

発表では、具体的な顧客事例や定量的な導入効果は示されていません。

## 9. まとめ

このセッションは、Contoso Outdoors の購入成功率が 96% から 70% に落ちたという 1 つのインシデントを使って、データ基盤の 5 つのパターンを順に見ていく構成でした。信頼できるデータ、共有メトリクス、ビジネスコンテキスト、専門エージェント、制御されたアクションが積み重なることで、Maya は信頼できる 1 つの答えにたどり着きます。

登壇者の結論は、エージェントを作る前に基盤を整えること、Fabric IQ の ontology でビジネスを一度だけモデル化すること、そして提案はエージェントに任せても最終判断は人が行うことです。
