# THRSP1082 Want smarter AI workflows? Power them with Oracle data in Azure

## 1. はじめに

このセッションは、Oracle の登壇者が、Azure で Oracle Database を動かす意味と、Oracle のデータを AI エージェントにどう結びつけるかを紹介する発表です。登壇者は冒頭で持ち時間を 25 分と述べており、トランスクリプトは約 18 分半で終わっています。冒頭で登壇者は、Azure と Oracle が提携して 3 年になるいまでも「なぜ Azure は Oracle と提携したのか」「Oracle は何を提供しているのか」と聞かれると述べ、この 2 つの質問に答えたうえで、今後の方向性を説明すると予告しました。

登壇者が繰り返し強調したのは、**データのガバナンスとセキュリティをデータベースの中で維持する**という考え方です。データを複製したり移動させたりせず、AI エージェントがデータベースにアクセスする際も、データベース側のルールで権限を絞ります。Microsoft 側の話題としては、本カンファレンスで発表された新しいコンソール **Azure Workload Center**（プレビュー）が紹介されました。

このセッションでは画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。Azure Workload Center のデモは、Oracle のブースで行われているとの案内がありました。

## 3. 何に関する発表か

テーマは、Azure のリージョンに置かれた Oracle のデータベースサービス（Oracle AI Database at Azure）と、そこに載せた業務データを AI の取り組みに活用することです。発表は次の流れで進みました。

1. Oracle Database の歴史と、顧客が Oracle を使い続ける理由
2. データベースへの AI エージェント統合（AI ネイティブなデータベース、MCP サーバー、ベクトル検索）
3. Azure で提供される 2 つの主要サービス（Autonomous AI Database、Exadata）
4. Microsoft との提携の経緯（2019 年の Interconnect、2023 年の Oracle AI Database at Azure）と、Azure リージョンへの Exadata ハードウェアの展開
5. 顧客事例（Conduit、Cephe）
6. 今後の方向性（データガバナンスとエージェント、Azure Workload Center）とリソースの案内

## 4. 発表者が伝えたいメッセージ

登壇者の主張は、Oracle のデータベースは、ミッションクリティカルなアプリケーションを支えてきた実績と、新しいデータ型を共通エンジンに取り込み続ける設計によって、AI 時代にもそのまま使える、というものです。顧客が最も求めているのは、Oracle にある「ライブの業務データ」を AI 戦略につなげることだと述べています。

そして、AI エージェントを使うときこそ、データを複製せずデータベース内でガバナンスを効かせるべきだと主張しています。理由は、エージェントは目標志向であり、アプリケーション層にルールを置いても、それを回り込んでしまう可能性が高いからです。

## 5. 発表内容の詳細

### 5.1 Oracle の歴史と顧客基盤

登壇者は、Oracle の顧客が 40 万社以上いること、決算説明会では最初に必ず「データベースのライセンス事業は伸びているか」と聞かれ、答えは「はい」であることを述べています。また、かつてミッションクリティカルなアプリケーションを作るなら Oracle Database を選んだこと（時期の言い回しは音声が不明瞭で確定できません）、いまも世界で 1 位のデータベースであること、医療、政府、軍、株式市場のような環境でも Oracle が選ばれることを挙げました。これらは登壇者自身の主張です。

Azure が Oracle と提携した理由は、この大きな顧客基盤にあると説明しています。顧客が Oracle を使い続けるのは、数年ではなく数十年にわたるイノベーションのためです。登壇者は、2000 年代に生まれたオープンソースのデータベースとは異なり、Oracle は最初の商用 SQL データベースで、PL/SQL を開拓したと述べています。1980〜90 年代は移植性（portability）に注力し、その後に出した **RAC**（音声では「Rack」）は、ワークロードを複数のサーバーに分散してダウンしないようにする機能で、いまも「RAC のために Oracle を買う」と言う顧客がいるとのことです。

### 5.2 共通のデータエンジンと「AI ネイティブ」なデータベース

Oracle は共通のデータベースプラットフォームであり、数十年前から同じ共通エンジンを使っています。新しいデータ型が普及するたびに、その対応を共通エンジンに統合し、ライセンスの一部として提供します。例として挙げられたのは次のとおりです。

- **JSON**：JSON が普及した際に対応し、さらに **JSON duality** を提供した。データをリレーショナルテーブルに 1 回保存し、JSON ドキュメントとしても提示できる
- **ベクトル**：最近の例。リレーショナルデータをベクトル化できる

その結果、1 つのデータベースで、ほぼあらゆるデータ型とワークロードを扱えると説明しました。

最新のリリースは **26 AI** で、登壇者はこれを「AI ネイティブなデータベース」と呼んでいます。AI エージェントをデータベースの中に置き、AI エージェントがアクセスしやすくするというものです。Microsoft との協業では、エージェント間通信（agent to agent、A2A）を行いますが、それをデータベースの中で行いたいのは、ガバナンスとセキュリティがそこにあるからだと説明しています。今後 2 年ほどの Oracle の発表は、データを複製したり移動させたりせず、データガバナンスをデータベース内で維持することが軸になるそうです。

登壇者は、次の段階として、データベースの業務データを AI エージェントにつなぐ接続をできるだけ簡単にしようとしており、**MCP サーバーをデータベースに含める**こと、**ベクトル検索をそのデータと統合する**ことを挙げています。顧客に聞かれるのは、Oracle にあるライブの運用データを AI 戦略につなげる方法で、Oracle Apps であれカスタムアプリであれ、Oracle Database 上に作られたアプリケーションのデータが、AI エージェントの価値を引き出すために必要なデータだと述べています。

### 5.3 Azure で提供される 2 つの主要サービス

**Autonomous AI Database**：2021 年ごろに登場した、Oracle のデータベース自体を継続的、能動的にパッチ適用、更新、スケールする仕組みです。DBA の日常的な作業をなくすことが狙いで、頻繁に出るセキュリティパッチも自動で更新されると説明しています。これを Azure のネイティブサービスとして提供しています。

**Exadata（Exadata Database Service on dedicated infrastructure）**：登壇者が「Microsoft との提携の核心」と呼ぶサービスです。Oracle の重要なワークロードを動かす顧客の多くが Exadata で動かしており、ハードウェアは第 16 世代、最初のリリースは 2008 年だと述べています。Oracle Database を動かすためだけに設計された専用のハードウェアで、「アプリの速度はデータベースの速度で決まる」ので、データベースの性能向上を重ねてきたそうです。このクラウドサービスを購入すると、ハードウェアと、ハードウェア部品間のデータの流れを管理するソフトウェアの両方が得られます。

Exadata のアーキテクチャは次のとおりです。

| 要素 | 説明 |
| --- | --- |
| データベースサーバーとストレージサーバーの分離 | SQL のロジックをストレージサーバー側にオフロードする。データベースのコンピュートサーバーに過負荷をかけないため、あらゆるアプリ、ワークロードを非常に高い水準で処理できる |
| ストレージサーバーのスケール | 64 ノードまでスケールアウトできる |
| 階層化ストレージ | 「XRM」（Oracle 独自の高速アクセス用ストレージ、音声認識の都合で表記が確定できません）、ディスク、フラッシュキャッシュの 3 階層。クエリに応じて自動で使い分ける |

登壇者は、Oracle のデータベースが株式市場や PayPal、e-コマースの取引、ATM、クレジットカード、航空券の予約を支えているとし、「世界のデータは Exadata の上で動いている」と述べています。Oracle は分析と OLTP を土台に事業を築いてきましたが、そのアーキテクチャはたまたま AI にも最適で、非常に複雑なベクトルクエリも Oracle のデータベースで実行できると説明しました。

顧客は AI 戦略の採用に合わせてモダナイズしたいと考えており、現行バージョンの 26 AI を Exadata 上で使うことを目指し、その際に Azure を選ぶことが多いそうです。理由は、Oracle の顧客基盤と Azure の顧客基盤の重なりが大きく、アプリケーションを Azure に移した後、オンプレミスで使ってきた同じ Exadata アーキテクチャをクラウドサービスとして Azure に持ち込みたいからです。

Exadata の顧客の約 **89%** は、いまもオンプレミスで動かしているとのことです。Exadata は、オンプレミス、ハイブリッドの **Exadata Cloud at Customer**、パブリッククラウドの OCI と Azure で提供しています。データセンターを閉じるためにクラウドへ移る顧客は、すでにアプリケーション層を Azure に移していることが多く、Oracle はそこへ自社のデータベースを持ち込む（登壇者の言葉では repatriate する）ことを狙っているそうです。

### 5.4 Microsoft との提携の経緯

Microsoft との提携は約 30 年の歴史がありますが、転機は 2019 年でした。Oracle の顧客から、Microsoft と組んで OCI と Azure を直接物理的に接続してほしいという要望があり、**Azure Interconnect（Microsoft Interconnect）**を導入しました。Oracle Cloud と Microsoft Cloud を直接物理的につなぐもので、2 つのクラウド間のレイテンシーは 2 ミリ秒です。登壇者は「IT で最も価値のある製品」と呼んでいます。使い方の例として、ライブデータは OCI に置き、夜中にバッチジョブを Azure に送って、分析や Fabric で処理する、というものが挙がりました。これが提携の第 1 段階です。

第 2 段階は 2023 年の **Oracle AI Database at Azure** です。狙いは、Oracle のデータベースクラウドのポートフォリオ全体を、Azure のネイティブサービスとして提供することです。

顧客は、クラウドへの移行を完了させようとしています。アプリケーションはすでに Azure に移したが、オンプレミスに閉じ込められていた Oracle のデータベースもクラウドへ移し、Azure のプラットフォームを活用してセキュリティと耐障害性（resilience）を高めたい、データセンター自体を閉じたい、という動機です。

登壇者は、3 年経ってもよく聞かれる質問として、次の仕組みを説明しています。

- Exadata のハードウェアを、**物理的に Azure のリージョンへ出荷**している。現在 **33 のリージョン**に展開している
- Microsoft がスペースを提供し、Oracle がそこにハードウェアを置いて、サービスを動かす
- サービスは「Mac credits」（聞こえたまま。音声認識の都合で表記が確定できません）で利用できる。すでに Azure のクレジットに投資している場合、そのクレジットで Oracle の製品を利用できる
- Oracle のすべての製品を Azure とネイティブに統合しており、プラットフォーム上でファーストクラスの存在になっている

アプリケーションのワークロード層と同じリージョン、同じ AZ に Oracle のミッションクリティカルなデータベースを置けば、低いレイテンシーで動かせます。その次の段階として AI の価値の解放が始まる、という流れです。登壇者は、話をしてきた企業の多くは AI の初期段階にあり、顧客向けの軽量なエージェントを動かしている段階だと述べ、Oracle が管理するライブの業務データにアクセスできれば、エージェントを使って事業運営のリアルタイムの情報を得られるようになると説明しています。

### 5.5 顧客事例

登壇者は、クラウドへ移行する Oracle 顧客の波が来ており、すでに**数千社**がオンプレミスから Azure に移ったと述べています。共通して「データセンターを閉じた。さまざまなワークロードをすでに Azure に移した。次は Oracle のワークロードを移す」と話しているそうです。Oracle のデータベースは事業全体を動かす部分のため、慎重にオンプレミスで保持されてきましたが、提携 3 年を経て、顧客は安心してミッションクリティカルなデータベースをクラウドへ移せるようになったと説明しています。

- **Conduit**：この移行の最初の顧客の一つで、料金所の通行料徴収（toll taking）のアプリケーション。車が料金所を通るたびに多くのデータポイントが発生し、複数の領域に流れ込む。多数のクエリとストレージへのアクセスがある。Oracle のデータベースとそれを使うアプリを Azure に移すことで、アプリのパフォーマンスが向上した
- **Cephe**（音声認識の都合で表記が確定できません）：EMEA の顧客。同様に、データセンターを閉じ、すべてのワークロードを Azure に移している

### 5.6 今後：データガバナンスと AI エージェント

登壇者は、Oracle と Microsoft が最も力を入れている領域として、データのセキュリティとガバナンスを挙げています。データベースで運用しているガバナンスを、安全で保護された形で AI エージェントから利用できるようにすることです。Microsoft とも協力して、エージェントが簡単にデータにアクセスできつつ、安全に行えるようにしているそうです。

顧客が Copilot を開発し、AI の取り組みを始めると、Oracle のデータベースとの A2A（エージェント間通信）や、データベースに組み込まれた MCP サーバーを使いたくなります。**Oracle Database のライセンスがあれば、MCP サーバーも利用できる**と説明しています。エージェントがデータにアクセスすると、データガバナンスを通ります。Oracle がデータを保護し、エージェントには権限のある範囲のアクセスだけを与えます。エージェントは目標志向のため、ルールをアプリケーション層に置くと回り込む可能性が高いと述べ、**すべてのデータガバナンスルールをデータベースの中で強制**していると説明しています。

### 5.7 Azure Workload Center

Oracle のデータベースやツール、アプリケーションを Azure に移した後は、アプリケーション、Oracle のデータベース、基盤の Azure インフラを統合して管理する手段が必要になります。そこで、このカンファレンスで発表されたのが **Azure Workload Center** です。単一のコンソール（インターフェイス）で、次の 3 層を管理できます。

1. Azure のインフラ上で動くアプリケーション
2. Oracle AI Database at Azure で動くデータベース
3. Azure 側のその他の関連インフラ

新しいコンソールで、現在プレビューです。デモは Moscone North の Oracle のブースで行っているとのことです。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 既存の Azure のクレジットで Oracle の製品を利用できる
- オンプレミスで使ってきた Exadata のアーキテクチャを、クラウドサービスとして Azure で使える。アプリケーションと同じ AZ に置くことで低レイテンシーになる
- 2 ミリ秒のレイテンシーで OCI と Azure をつなぐ Interconnect で、夜間のバッチ分析などを Azure（Fabric を含む）で行える
- 事例として、Conduit は Oracle のデータベースとアプリを Azure に移してアプリの性能が向上した
- Autonomous AI Database は、パッチ適用や更新、スケールを自動化し、DBA の日常的な作業をなくす
- Oracle Database のライセンスで MCP サーバーも利用でき、データガバナンスはデータベース内で維持される
- Azure Workload Center で、アプリ、データベース、インフラを単一のコンソールで管理できる（プレビュー）

## 9. まとめ

登壇者は、Oracle が 40 万社以上の顧客基盤を持ち、共通エンジンで新しいデータ型（JSON、ベクトル）を取り込み続けてきたことが、Azure が Oracle と提携した理由だと説明しました。Azure では Autonomous AI Database と Exadata がネイティブサービスとして提供され、Exadata のハードウェアは 33 のリージョンに物理的に展開されています。2019 年の Interconnect、2023 年の Oracle AI Database at Azure を経て、数千社がオンプレミスから Azure へ移行しているとのことです。

今後の軸は、MCP サーバーと A2A を通じて AI エージェントを Oracle のデータにつなぎつつ、ガバナンスをデータベース内で強制することと、新コンソール Azure Workload Center による一体管理です。
