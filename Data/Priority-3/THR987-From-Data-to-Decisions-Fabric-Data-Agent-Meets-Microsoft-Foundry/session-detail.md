# THR987 From Data to Decisions: Fabric Data Agent Meets Microsoft Foundry

## 1. はじめに

このセッションは、Microsoft Fabric の **Fabric data agent** と **Microsoft Foundry** のエージェントを組み合わせて、「売上が落ちた理由を調べ、次の打ち手を提案し、最終判断は人が行う」という流れを、3 つのデモで見せる約 23 分の発表です。

シナリオは小売企業です。CTO の Alex が、2025 年 9 月から 2026 年 9 月にかけて売上が下がっていることに気づきます。その売上減は約 40% で、「在庫切れが原因だ」と誰もが思い込んでいるものの、誰も確かめていません。発表では、Fabric 側で信頼できるデータから事実と証拠を取り出し、Foundry 側でその証拠をもとに次の打ち手を提案する、という役割分担が示されます。

結論として、このシナリオでは「在庫切れが原因」という最初の仮説は覆されました（在庫切れだけが原因ではなく、プロモーションの問題が手がかりになりました）。ただし、発表者は、Foundry は何も変更せず、行動を決めるのは人だと繰り返し述べています。

## 3. 何に関する発表か

テーマは、データ（Fabric）からインサイトを得て、AI（Foundry）が行動案を出し、人が意思決定するまでの流れです。冒頭で示されたアジェンダは次のとおりです。

2. アーキテクチャ

登場する人物は 3 人です。SQL が書けるデータエンジニアの Daniel、SQL を知らないビジネスアナリスト Priya、技術に詳しくないビジネスユーザー Sarah です。人物ごとに、使う道具（SQL、data agent、チャットアプリ）が変わる構成です。

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**Fabric は「何が起きたか」を信頼できるデータから示し、Foundry は「次に何をするか」を提案し、決めるのは人である**という役割分担です。

発表者によると、データエージェントは自然言語の質問を SQL、KQL、DAX（発表では "dex query" と聞こえます。音声認識の都合で表記が確定できません）といったクエリに変換してデータを読み、答えを返します。これにより、SQL を知らない Priya のような人も、データエンジニアの Daniel が SQL で確認した事実に、自分で到達できます。ただし Fabric が示すのは、信頼できるデータに基づく事実までです。「次に何をするか」は大規模言語モデルを使う Foundry の役割です。

もう 1 つのメッセージは、デモと本番は違うという点です。デモはあくまで POC で、エンタープライズで使うには、アイデンティティ、ネットワークセキュリティ、ガバナンス、監査と監視、オブザーバビリティ、そして人の判断が必要だと整理されています。

## 5. 発表内容の詳細

### 5.1 業務上の課題

CTO の Alex は、売上が落ちていること、特に 2025 年 9 月から 2026 年 9 月にかけての 9 月の売上減に気づきました。そこで、なぜ売上が下がったのかを調べます。最初に思い浮かぶ仮説は「在庫切れで売上が下がった」というものです。発表者は、これは皆が当然のように思っているものの、実際に確かめた人はいない、と指摘しています。この仮説が本当に正しいのかを検証するのが、今日のテーマです。

### 5.2 アーキテクチャ

構成要素は次のとおりです。

| 要素 | 役割 |
| --- | --- |
| UI | Web アプリまたはチャットアプリ。デモでは Streamlit（発表では "stream light"）を使い、ローカルマシンで実行する。Azure portal からも、ワンクリックで Web アプリを確認できる |
| Foundry agent | 質問を受け取り、オーケストレーションする。理由と不確実性を整理する |
| Fabric data agent | Fabric IQ のツール経由で Foundry から呼び出される。ユーザーの質問に応じてクエリを実行し、結果を返す |
| Lakehouse | 信頼できる（trusted）データが置かれている |

流れは次のとおりです。ビジネスユーザーの Sarah が UI で質問すると、質問は Foundry に渡り、Foundry は Fabric IQ のツールを通じて Fabric data agent を呼びます。data agent が小売の lakehouse に対してクエリを実行し、結果が逆の順で画面に戻ります。

発表者が注意点として強調したのは、**Foundry はビジネスデータを更新も変更もしない**ことです。ビジネスデータ（信頼できるエンタープライズデータ）に対してクエリを実行するのは Fabric data agent です。また、発表者によると、以前は「Fabric data agent」としてつなぐ方式でしたが、現在は Fabric IQ をツールとして使えるようになっています。

役割分担としては、Fabric が調査を行い、Foundry がオーケストレーターとして、Fabric data agent から得た信頼できる情報をもとに理由と不確実性を整理します。その提案を見て、人が意思決定します。

### 5.3 デモ 1：Fabric で事実と証拠を確認する

最初のデモは、どんなデータがあり、本当に売上が下がっているのか、なぜ下がっているのかを確認する内容です。Daniel は SQL で調べられますが、SQL も KQL も知らない Priya は、Fabric data agent に英語で質問できます。たとえば、売上がどれだけ落ちたかを尋ねられます。

データエージェントには、チャートを表示するための **code interpreter** も組み込まれています。発表者によると、code interpreter は data lake には接続せず、data agent の出力を受け取って可視化するだけです。

デモの内容は 6 章に順番に記載しています。ここでの要点は次のとおりです。

- Lakehouse のデータはキュレーション済みの gold layer で、ビジネスユーザーや KPI に使える「正しいデータ」
- Daniel の SQL の結果で、2025 年 9 月と 2026 年 9 月の比較から、約 40% の減少が確認できた。つまり、Alex の指摘は事実に基づいていた
- ただし、この時点では「なぜ減ったか」は分からない
- Priya がデータエージェントに質問すると、SQL で見たものと同じ数字が得られ、根拠（どのテーブルを使ったか）と、code interpreter によるグラフも表示される
- 追加で原因を探る質問をすると、**店舗 5 と店舗 6 でプロモーションキャンペーンの問題**があることが分かった。低在庫は売上減の理由ではない、と説明された。ただし、低在庫が当てはまる場所が 1 か所あり、それだけで 100% 言い切れるわけではない

### 5.4 デモ 2：Foundry で次の打ち手を提案する

Fabric が示すのは、信頼できるデータに基づく事実までです。そこから「次に何をするか」を示すには、大規模言語モデルを使う Foundry が登場します。

Foundry のデモは、Azure のリソースグループから始まります。リソースグループ内に Foundry プロジェクトがあり、それを開くと Foundry agent に移れます。この agent には、Fabric IQ 経由で Fabric data agent と、code interpreter ツールが接続されています。

デモの途中で、発表者は用意したプロンプトを見失ったと述べ、以前に実行したプロンプトを使うこともできると説明しています。Foundry 側では、次の点が紹介されました。

- どのプロトコルを使ったかなどの詳細を確認できる
- trace を見ると、Fabric agent を実際に呼んだかどうかが確認できる
- tool call や agent run などの情報も見える。このほか evaluation や optimization に当たる項目にも触れているが、音声認識では "evolution and optimization" と聞こえ、正確な名称は確定できません

### 5.5 デモ 3：ビジネスユーザーの Sarah が使う

3 つ目のデモは、ビジネスユーザーの Sarah の体験です。Azure portal からワンクリックで開ける Web アプリでも同じ質問ができ、すぐに答えが生成されます。発表者はローカルで動かした Streamlit アプリで質問しました（質問内容は「なぜ売上が落ちたのか」という趣旨です）。

回答には、取れる選択肢が示されます。発表者によると、Foundry は変更を加えられず、次に何をするかは人が決めます。Foundry は不確実性があれば指摘し、「売上減に対して、次にできる 3 つのステップ」を推奨しました。Sarah のようなビジネスユーザーはそれを見て行動を決めます。3 つの提案の具体的な内容は、音声からは確認できません。

### 5.6 本番化のために必要なこと

発表者は、デモはいつも本番向けとは限らず、POC にすぎないと断ったうえで、エンタープライズ向けに適用すべきことを次のように挙げています。

- アイデンティティとアクセス、ネットワークセキュリティ、プライベートエンドポイントなどによる安全性の確保
- ガバナンスの適用
- 監査（auditing）と監視（monitoring）
- トレーサビリティ（追跡可能性）とオブザーバビリティ。Foundry は、各プロンプト、各呼び出し、トークン、価格、入力と出力を見せられる
- 判断を行う human in the loop

### 5.7 まとめの整理

発表の最後で、全体の流れが整理されました。

- Lakehouse には、小売関連のキュレーション済みの gold layer データがある
- Fabric data agent は、クエリ（SQL を含む）をもとに根拠（ground evidence）を提供する
- Microsoft Foundry は、その証拠に基づいて提案を出す
- シナリオでは提案までだが、他の使い方として、メールの送信、サードパーティツールの呼び出し、Fabric 外のデータベースの更新などもできる、と説明された
- 「Fabric が何が起きたかを示し、Foundry が次に何をするかを手伝う」ため、両方にエージェントが必要
- 業務側のレビュアーが、在庫を確認して補充するのか、プロモーションの問題を直すのか、などを判断する

最初の「在庫切れが原因」という仮説は、在庫切れだけが原因ではないと分かり、覆されました。ただし、このシナリオでは実際のアクションは行っておらず、問題の特定と案の提示までです。最終判断は人が行い、その後に Foundry がそれを自動化することもできる、と発表者は述べています。

### 5.8 Q&A

デモの途中で、会場から「1 つの data agent で、異なる workspace のデータを扱えるか」という質問がありました。発表者はまず、workspace ごとにそれぞれの data agent を持つ形だと思う、と答えています。そのうえで、1 つの data agent に、複数の lakehouse や複数のテーブル、SQL database、DAX クエリなどを組み合わせて接続できると説明しました。ワークスペースをまたぐ接続が可能かどうかについては、質問者との聞き取りが不明瞭で、はっきりした回答は音声から確認できません。

## 6. デモ・手順

### 6.1 デモ 1：Fabric workspace と data agent

1. Microsoft Fabric の workspace を開く。中には retail data agent と、すでに開いている lakehouse がある
2. Lakehouse のデータは、キュレーション済みの gold layer データで、ビジネスユーザーや KPI 用。デモは簡略化のため、小売の product、store、inventory、promotional のテーブルを中心に使う（ほかに fact table も言及されている）。再現用の資料は GitHub リポジトリにあり、後で共有できると述べられた

4. Fabric で data agent を作成できると説明し、retail lakehouse に接続した data agent を見せる。関係する 5 つのテーブルだけを選んでいる

7. 時間の都合で、質問はすでに実行済みであると述べ、根拠として元のソースファイルが示されると説明する
8. 別のプロンプトで、「キャンペーンの問題か在庫切れか」を調べる。結果として、店舗 5 と店舗 6 にプロモーションキャンペーンの問題があり、低在庫は売上減の理由ではない、との手がかりが得られる
9. データエンジニアが手動で確認する場合は、notebook で同じことができると説明される

## 7. 注意点・発表者の気付き

- 「在庫切れが原因」という思い込みは、検証しなければ分かりません。このシナリオでは、データを確認した結果、低在庫は売上減の理由ではないとされ、店舗 5 と 6 のプロモーション問題が手がかりになりました。ただし、低在庫が当てはまる場所が 1 か所あり、100% の断定はできないとも言われています。
- Foundry は、Fabric のビジネスデータを更新・変更しません。エージェントは提案までで、決定するのは人です。
- デモはいつも本番向けではなく、本番化には、アイデンティティ、ネットワーク、プライベートエンドポイント、ガバナンス、監査、オブザーバビリティ、human in the loop が必要です。
- 発表者によると、Foundry から Fabric data agent に接続する方式は、以前の「Fabric data agent」から Fabric IQ ツールに置き換わっています（発表者は旧方式を deprecated と述べています）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- SQL や KQL を知らないビジネスアナリストや業務ユーザーが、自然言語でエンタープライズデータに質問できる
- データエンジニアが SQL で確認した結果と、同じ事実をデータエージェントで確認できる
- 根拠として、使ったテーブルや元のソースが示される
- 「Fabric が何が起きたかを示し、Foundry が次に何をするかを手伝う」形で、仮説の検証から次の打ち手の提案までが 1 つの流れになる
- Foundry の trace で、各プロンプト、呼び出し、トークン、価格、入出力が見える

発表では、具体的な顧客事例や定量的な導入効果（売上減 40% は、デモのシナリオ上の数値）は示されていません。

## 9. まとめ

このセッションは、売上が約 40% 落ちた小売企業のシナリオで、Fabric data agent が信頼できる lakehouse のデータから事実と証拠を示し、Microsoft Foundry がそれをもとに次の打ち手を提案する流れを、3 つのデモで見せました。結果として、最初の仮説だった在庫切れだけが原因ではなく、店舗 5 と 6 のプロモーション問題が手がかりとして示されました。

持ち帰りとして重要なのは、Fabric がデータから事実を、Foundry が次の行動案を担当し、行動を決めるのは人であるという分担です。本番にするには、セキュリティ、ガバナンス、監査、オブザーバビリティ、人の判断を組み込む必要があります。
