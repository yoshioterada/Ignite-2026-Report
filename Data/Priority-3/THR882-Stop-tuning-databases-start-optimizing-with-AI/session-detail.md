# THR882 Stop tuning databases, start optimizing with AI

## 1. はじめに

このセッションは、Azure Postgres のプロダクトマネージャーである Brian Holt 氏が、限定パブリックプレビュー中の **database agent** を紹介するものです。深夜 2 時にデータベース障害で呼び出されたとき、ログ・メトリクス・実行中クエリを集めて状況を組み立てる「証拠集め」の作業を、エージェントに先に済ませてもらうという発想で話が進みます。

発表の中心は「**証拠集めはエージェントに任せ、判断は人間が行う**」という役割分担です。database agent は原因の調査と修正案の提示までを担当し、データベースに直接接続しません。修正を実行するかどうかは常に利用者が決めます。

発表は 25 分ほどの短いセッションで、Visual Studio Code の Postgres 拡張機能を使った画面デモが中心です。デモは、インデックス不足による CPU 高騰、長時間セッションによる接続枯渇、そして MCP サーバー経由で Copilot に調査内容を問い合わせる流れの 3 つです。

## 4. 発表者が伝えたいメッセージ

Brian 氏は、自分は DBA ではなく開発者であり、データベース障害の呼び出しを受けると状況が余計に混乱しやすいと話しています。障害対応で最初にやるのは、ログ、メトリクス、実行中のクエリ、直近のデプロイを見て文脈を組み立てることです。それをチャットウィンドウに貼り付けたり、スクリーンショットを撮ったり、MCP サーバーがあればそれを参照させたりして Copilot に「何が起きているのか」を聞く、という作業になっていると言います。

ここに着目して、ログも、メトリクスも、実行中のクエリも毎回同じ種類の情報だという「範囲が決まった問題」であり、エージェントが常にデータベースを見張って集めておけると考えました。メッセージは、証拠集めをやめて、すぐに判断に移ってほしいということです。「A をやるか B をやるか」という判断だけを人間が行います。

もう 1 つのメッセージは **信頼とコントロール** です。インタビューした DBA は「エージェントに直してほしいか」と聞くと「いや、自分でやりたい」と答える人が多く、そのため database agent は初日からゼロトラストで使える設計にしたと説明しています。

## 5. 発表内容の詳細

### 5.1 課題設定：午前 2 時 7 分の呼び出し

Brian 氏は、アプリケーションのリクエストがタイムアウトし、自分がオンコールになっている午前 2 時 7 分という場面を設定しました。このとき最初にやることは、ログ、メトリクス、アクティブなクエリ、デプロイの履歴を見て証拠を集めることです。database agent を使うと、この最初の単調で繰り返しの多い作業を飛ばして、「このグラフと状況から何が起きたのか。A と B のどちらにするか」という意思決定の段階から始められます。

database agent は証拠を集めるだけで、判断は人間に残されます。「判断はまったく database agent に渡していない。それは人間の仕事のままだ」と述べています。

### 5.2 database agent の概要

database agent は、発表時点で限定パブリックプレビューです。Brian 氏は、スライドにあるリンクと発表の最後の QR コードから申し込めると説明しています。プレビュー期間中は無料で、将来的には課金する予定ですが、「今日ではない」としています。

「database agent は利用者より先に起動する」と表現されています。利用者に呼び出しが届いた時点で、database agent にも同時に（おそらくそれより前に）通知が入り、調査を始めます。利用者が起きてコーヒーを淹れ、ノートパソコンを開くころには、調査が終わっているか、ほぼ終わっている状態を目指しています。

動き方は 3 パターンあります。

| パターン | 内容 |
| --- | --- |
| プロアクティブなヘルスチェック | 定期的に実行し、メトリクスが以前と比べてどうかを見て、異常があれば調査を開始する |
| リアクティブな調査 | メモリ不足、接続の切断、CPU の張り付き、ハングしたトランザクションなどをきっかけに調査を開始する |
| 調査後の提案 | 推奨アクションを提示し、なぜそう考えたかの根拠となるメトリクスなどの証拠をすべて示す |

対応先は、Azure Database for Postgres と、近日登場予定の Fabric Postgres です。SQL Server 向けにも同様の機能があり、Horizon DB 向けは「近日提供」と説明されています（Horizon DB の表記は聞こえたとおりで、音声認識の都合で確定できません）。

調べる対象は、人間が調べるものとほぼ同じで、次のとおりです。

- Azure Monitor のメトリクス
- データベースのログ
- クエリ統計
- 構成設定
- 最近のデプロイ
- 既知の障害パターン

加えて、利用者がアクセスできない **Microsoft 内部の Azure ログ** も database agent に取り込んでいる点を、付加価値として挙げています。

処理のパターンは「検出する、調査する、説明する、推奨する」です。例えば「午前 2 時 7 分に CPU が張り付いた」と事象を示し、その原因だと考える証拠（実行されていたクエリ、トラフィックの異常な急増など）を集め、次の手を提案します。次の手には、推奨される修正、次に何をすべきか分からない場合の調査結果とさらに調べる手段、あるいは GitHub への Issue 登録があります。

### 5.3 デモ 1：インデックス不足を VS Code で見つける

Brian 氏は、見てほしい点として「証拠と結論をどう分けているか」「修正をいつ実行するかを利用者が決めること」の 2 点を挙げて、デモに入りました。内容は 6 章にまとめます。結論として、高 CPU の原因はテーブルスキャンと同時実行クエリで、database agent は「インデックスを作成して直す」という推奨を出しました。担当者が呼び出される前に検出され、誰も問い合わせていない、という位置づけです。

### 5.4 デモ 2：接続枯渇から GitHub Issue と PR へ

2 つ目のデモは、午前 2 時に呼び出された場面を再び設定し、長時間のセッションが接続を使い切って接続が切れる障害を扱います。手動でクエリを止めることはできますが、それでは再び呼び出されることを防げません。そこで「即時の対処」を超えて、長期的な修正につなげる流れを見せました（6 章）。

Brian 氏が強調した点は次のとおりです。

- 推奨アクションには、手動での対応が必要なものがある。このデモの場合、database agent が実行できる playbook はない
- **database agent はデータベースに接続しないので、これらの修正を実行することはない。** すべて利用者が実行する
- 「GitHub Issue を登録」ボタンを押すと、GitHub Copilot が横で開き、調査のログ全体を渡して質の高い Issue を作る
- いまは GitHub Issue のみの対応で、Azure DevOps は「まもなく」対応する。ほかの課題管理ツールも要望があれば検討する

Brian 氏は、database agent の主な価値は、ARM、Bicep、Terraform などを更新するような、**質が高く耐久性のある修正** を作れることだと述べています。さらに、Issue を GitHub Copilot に割り当てれば、Issue から修正済みの PR までを人手なしで進められる可能性がある、とも説明しました。ご自身の個人リポジトリでは、database agent が作った Issue を GitHub Copilot が自動で引き受けるように設定しており、朝席に着くころには PR ができている状態になっていると言います。

### 5.5 1 つの問題に複数の修正

Brian 氏は、1 つの障害に対して修正が 1 つとは限らないと話しています。メモリ飽和や CPU の張り付きでは、まず悪いクエリを止めてサービスを復旧します。次に原因となっているコードを直し、その後、再発しても耐えられるようにデータベースの SKU を上げることもあります。「1 つの問題に 3 つの修正」という状況です。

そのため database agent では、1 つの事象に対して複数の修正を扱えるようにしており、深夜の修正、朝 8 時の修正、来週の修正のように段階を分けられます（発話では最初の時刻が「00 AM」としか聞き取れません）。

### 5.6 デモ 3：MCP サーバーと Copilot で調査を掘り下げる

database agent には、Copilot が調査の全情報を直接取得できる **MCP サーバー** が付属しています。Brian 氏は、database agent が作った Issue と、それを解く PR の画面から、「なぜこの修正を提案したのか。自分は同意できないかもしれない。database agent が十分な文脈を持っていないかもしれない」という疑問を Copilot で掘り下げる流れを見せました（詳細は 6 章）。

この機能について、Brian 氏は次のように説明しています。

- VS Code の拡張機能には「magic sparkles（魔法のきらめき）」と呼ぶ AI ボタンが随所にある。クエリを可視化する画面にもある
- これらのプロンプトは Microsoft のチームが自分たちのデータベース調査に使っているもので、かなり調整されている
- 「もう database agent を信頼しなくてもよい。理由を尋ねれば完全な答えが返り、進路を変えることもできる」と感じている

MCP サーバーは、発表当日に Visual Studio Code 向けに公開されたと述べています。今後は VS Code 以外のコーディング環境にも対応し、MCP を話すものならどれでも database agent の Issue を引き込めるようになる、という説明です。Brian 氏は、自分が頻繁に使う Copilot アプリで、Word ドキュメントに障害後の振り返り（postmortem）を書くときにも使えるとし、実際に試したことがあると話しています。

### 5.7 全体の価値の流れ

Brian 氏は、ここまでの流れを時系列で整理しています。

1. 午前 2 時に、利用者が呼び出される前に問題を検出する。タイムアウトを見つけて調査を開始する
2. メトリクス、ログ、クエリストアに加え、Microsoft の外部には公開しない追加情報も見て、根本原因と、今すぐの修正、朝 8 時の修正を示す
3. 疲れている利用者が推奨アクションに従う。一部は「はい、実行」というボタンで済む（例：クエリを kill する）。Postgres を開く必要もない
4. 再発防止のために Issue を登録する。完全な文脈が GitHub に届く
5. 面倒な人は Issue を GitHub Copilot に自動で割り当て、朝 8 時には PR ができている

なお、「ボタンで実行できる」のは Brian 氏の説明では一部の修正に限られます。

### 5.8 自動修復と安全性の設計

Brian 氏は、DBA は不信感の強い人たちなので、この話題をあえて発表の最後に置いたと断っています。**影響の小さい一部の問題**については、database agent に自動修復（auto remediate）をさせる設定ができます。

例として auto vacuum が挙げられています。auto vacuum はほとんどの場面で実行して問題が少なく、database agent は悪いタイミングでないかも確認します。「はい、修正を適用」というクリックを何度も繰り返すようになったら、自動修復をオプトインすれば、問題を見つけたときにすぐ、または影響が出にくい時間帯に直してくれます。

安全面の仕組みは次のとおり説明されました。

| 項目 | 内容 |
| --- | --- |
| オプトイン | 自動修復は利用者が明示的に選んだときだけ有効になる |
| 対象 | Microsoft が管理する、低リスクの修正だけ |
| 実行方式 | エージェントが修正案を作るのではなく、Microsoft のエンジニアが書いた playbook が決定論的に実行される |
| データベースへのアクセス | database agent 自身はデータベースに対して何もしない |
| その他 | 自動での再起動はない。修正は検証され、常にログに記録されるので監査できる |

playbook の数は、現時点で作業中のものが **31 件**（31 の実際の障害シナリオでテスト済み）で、約 **150 件** を作りたいと考えており、順次公開していくとのことです。playbook がない問題については、証拠、メトリクス、GitHub に登録できる質の高い Issue は得られますが、database agent は一致する「シグネチャ」を持たない修正を提案せず、直接データベースにアクセスしないので修正の実行もしません。

### 5.9 参加の呼びかけと今後の予定

Brian 氏は、限定パブリックプレビュー期間は無料なので、ぜひ申し込んで試してほしいと呼びかけています。今後数か月かけて開発を進めるとし、Brian 氏が製品のプロダクトマネージャーなので、質問は自分宛てになると話しました。

今後の予定として、「GitHub への Issue 登録」と「自動修復」を挙げています。ただし、どちらも「まだ準備できていない」と述べています。

> 補足：デモの中では GitHub Issue の作成を実際に見せ、「いまは GitHub Issue のみ対応」とも話しているため、「Issue 登録は今後」という最後の発言と矛盾して聞こえます。トランスクリプトからは、どの範囲が提供済みで、どの範囲が未提供かは断定できません。

## 6. デモ・手順

このセッションにはデモがあります。画面は音声から確認できないため、語られた範囲だけを順に書きます。

### 6.1 デモ 1：VS Code でインデックス不足を調べる

1. Extension Marketplace で「Postgres」を検索して、Postgres 拡張機能をインストールする。この拡張機能には database agent が含まれる。Brian 氏は「Postgres を使っているなら昨日までにインストールしておくべき」と話しており、どのクラウドでも、ローカルでも、Postgres を使う人なら便利だと説明している
2. 拡張機能をインストールしたあと、サイドバーにある小さなゾウのアイコンをクリックする
3. 接続済みのデータベースが複数あることを確認する。Brian 氏が接続したのは「Caldova」と聞こえる名前のもの（音声認識の都合で表記が確定できません）。Azure 上のデータベースの一覧から選ぶ方法、接続文字列を貼り付ける方法、IAM に対応した接続方法もあると説明している。ローカルの Postgres コンテナを作る機能も、立ち上げては試して削除する用途で頻繁に使っているという
4. **パフォーマンスダッシュボード** を開く。どの Postgres でも使え、Azure 上ならメトリクスが増える。ここで CPU の疑わしいスパイクと、CPU の張り付きを調べる。クエリやセッションなども 1 か所で見られる
5. database agent を開く。実際の database agent の Issue が表示され、推奨アクション、期待される結果、検出内容、いつ起きたと推定されるかのタイムラインと、判断に使ったイベント群が見える。このデモを準備した際にはメトリクスが表示されなかったが、通常はグラフが出ると説明している
6. 午前 2 時に起きたことを確認し、推奨アクションを見る。「インデックスが足りない」と指摘され、実行すべきクエリが提示される。本番を止めないよう **concurrently（並行）で作成できる** ことも示されている
7. 「なぜこれが安全なのか」「なぜこれを推奨したのか」を Copilot に質問できる。納得できない場合は、その場で確認できる
8. 「Open in editor」をクリックすると、実行すべきクエリがエディタで開く。そこで再生ボタンを押して、修正をデータベースに直接実行できる

Brian 氏は、午前 2 時にクエリを止めて寝たいだけなら、これがちょうど求めているものだと述べました。一方で、VS Code から直接実行したくない人も多く、Issue を起こす、設定を直す、Terraform、Bicep、ARM を更新したいという要望があることにも触れ、次のデモにつなげています。

### 6.2 デモ 2：接続枯渇から GitHub Issue と PR へ

1. 事象は、長時間のセッションが接続を使い切り、接続が切れること。CPU にも同様のスパイクが見える
2. database agent の画面に移り、別の database agent の Issue を開く。タイムラインと、接続が落ちているという状況が確認できる
3. 「推奨アクション」を表示する。手動対応が必要で、database agent が実行できる playbook はない
4. 「file GitHub issues」ボタンをクリックする。GitHub Copilot がサイドで開き、ログ全体を渡して調査し、ポイントを押さえた質の高い GitHub Issue を作り始める
5. 登録先のリポジトリを選ぶ。事前に指定して手順を短縮することもできる
6. Copilot が database agent の MCP サーバーを直接呼び出す様子が確認できる。作られた Issue は非常に長く詳細な内容である
7. 実際に登録された Issue を表示する。続けて「GitHub Copilot に割り当てる」操作で、Issue から PR の作成へ進む。Copilot がすでに作業を始めている

> 補足：この時点でのナレーションは「Copilot がすでに作業を始めている」までです。続くデモ 3 では「すぐ出荷できる PR」が示されますが、それがこのデモの Issue から作られた PR かどうかは、音声からは確認できません。

### 6.3 デモ 3：MCP サーバーと Copilot で理由を調べる

1. database agent が登録した質の高い Issue と、すぐ出荷できる PR の画面を開く
2. PR で変更されたファイルを確認する。「よさそうだが、なぜこの修正を提案したのか知りたい」
3. Copilot を開き、技術的な詳細を確認する。「Ask Copilot about this section」ボタン（magic sparkles）をクリックする
4. 長いプロンプトが GitHub Copilot に渡される。そこで「なぜそうしたのか」「どのメトリクスを使ったのか」「ほかにどんな解決策があるか」と問い詰められる
5. Copilot は MCP サーバーから、その Issue に含まれるあらゆる情報を自動で取得する。文脈が自動で持ち込まれる

## 7. 注意点・発表者の気付き

- **database agent はデータベースに接続しない**。修正の実行は利用者が行う。自動修復の場合も、実行するのは Microsoft のエンジニアが書いた決定論的な playbook で、エージェントが考えた修正ではない
- playbook に一致しない問題では、修正は提案されない。証拠、メトリクス、Issue が提供されるのみである
- 自動修復は、低リスクの問題に限り、オプトインで有効にする。自動での再起動は行わない
- 状況によって「今すぐ・朝・来週」と複数の修正が必要になることを前提に設計している
- 限定パブリックプレビューであり、GitHub への Issue 登録と自動修復は、今後の予定として挙げられた（5.9 の補足も参照）
- Brian 氏は、DBA が「自分でやりたい」と考える層だと述べており、そのため利用者が判断と実行を握る設計にしたと説明している

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 午前 2 時の呼び出しで、ログやメトリクスを手作業で集める作業を省ける
- Microsoft 内部の Azure ログも調査に使われるため、利用者が見られない情報も根本原因の分析に反映される
- 推奨アクションの一部は、ボタンを押すだけで実行できる（例：クエリの kill）。深夜は応急処置、あとで恒久的な修正、という段階的な対応ができる
- ボタン 1 つで質の高い GitHub Issue が作られ、GitHub Copilot に割り当てれば朝 8 時には PR が用意される
- MCP サーバー経由で、Copilot から調査の根拠を問い詰められるため、エージェントを信頼するのでなく、確認して使える
- 無料のプレビュー期間中に試せる

発表では、顧客事例や、時間短縮などの定量的な効果の数値は示されていません。

## 9. まとめ

database agent は、Postgres（Azure Database for Postgres、近日の Fabric Postgres）のインシデント対応で、人間の判断の前に必要な証拠集めを先に済ませるエージェントです。メトリクス、ログ、クエリ統計、構成、デプロイ、既知の障害パターン、さらに Microsoft 内部のログを調べ、原因と推奨アクションを根拠とともに示します。

VS Code の Postgres 拡張機能から使え、インデックス作成のような修正は利用者が自分で実行できます。再発防止は GitHub Issue と GitHub Copilot、MCP サーバーを通じて PR まで進められます。

信頼を得るための設計も重要です。エージェントはデータベースに直接触れません。自動修復はオプトインで、Microsoft が書いた playbook に限られます（31 件が現在作業中、約 150 件を計画）。限定パブリックプレビューは無料で、Brian 氏は参加を呼びかけています。
