# THR989 No More ETL? A Real-World Playbook for Fabric Mirroring

## 1. はじめに

このセッションは、Microsoft Fabric のミラーリングを使えば ETL は不要になるのか、という問いに実体験から答える発表です。発表者は、Power BI のレポートが Direct Lake 接続でセマンティックモデルにつながり、そのセマンティックモデルがミラーリングで複製されたデータを読む、という構成でデモを作りました。その過程で、ミラーリング後にレポートの行数が 42 行から 9 行に減るという出来事に遭遇しています。

結論は、**抽出（E）と読み込み（L）はミラーリングが担うが、変換（T）は残る**ということです。ビジネスロジックの理解とセマンティックモデルでの整理は、引き続きデータエンジニアの仕事だと述べています。

内容は、ミラーリングの料金上の特徴、3 つの種類、提供状況（GA とプレビュー）、移行計画のテンプレート、オープンミラーリングを使ったライブデモ、失敗から学んだ 3 点、パイプラインを置き換える手順、質疑応答です。

## 5. 発表内容の詳細

### 5.1 問題提起：42 行が 9 行になった

発表者はデモを作っているときに、Power BI のレポートに 42 行があるのを確認しました。ところが、ミラーリングが戻ってきたあとにレポートを更新すると、9 行しか表示されませんでした。これが「ETL はもう不要か」という問いのきっかけです。

### 5.2 ミラーリングと E・L・T

ミラーリングは、データの抽出と読み込みのパイプラインを置き換え、Fabric の OneLake でほぼリアルタイムのインテリジェンスを実現します。ただし、セマンティックモデルの側では、ビジネスロジックを整える実際のエンジニアリング作業が残ります。つまりミラーリングでも、ビジネスのロジックとプロセスを理解し、Power BI のレポートに渡せるセマンティックモデルを作る**変換の層は必要**です。

### 5.3 料金と容量

| 項目 | 内容 |
|---|---|
| コンピュート | ミラーリングは容量ユニットを 0 消費する。消費の課金はかからない |
| ストレージ | 1 TB 分のミラーリングデータが無料。たとえば Fabric の 64 容量なら最大 64 TB まで無料で取り込める |
| コネクター | 自分でコネクターを作る必要はない。複数のネイティブコネクターがあり、データソースを指定して直接ミラーリングできる |
| 注意 | データのクエリには引き続き課金される。Power BI はレポートのために残り、セマンティックモデルに対するコンピュートが発生する |

### 5.4 ミラーリングの 3 つの種類

1. **データベースミラーリング**：Azure SQL、Cosmos DB、Snowflake などから、データを OneLake に複製する。データを移動する。
2. **メタデータミラーリング**：データは移動せず、システムに接続して取得する。Azure Databricks の Unity Catalog が該当する。Snowflake でも可能で、Snowflake のデータウェアハウスのデータを Iceberg として保存し、OneLake に直接つなぐ。データを移動せず、ショートカットとして扱う。
3. **オープンミラーリング**：任意のアプリに接続し、書き込みの処理とランディングゾーンを自分で作り、ソースシステムから OneLake へデータを取り込む。ライブデモで使うのはこの種類。

取り込んだあとは、Spark ノートブックによる変換、レイクハウスまたは SQL エンドポイントを持つデータウェアハウスでのビュー作成、その上のセマンティックモデル、そして Power BI のレポートへと進みます。

### 5.5 Fabric と Power BI

Power BI は Fabric ファミリーの一部です。Fabric を契約すると Azure 上のサービスとして Fabric 容量が 1 つ現れ、その容量にすべてのデータを集めて単一の統合データ基盤を作れます。

### 5.6 提供状況の確認

クライアントと話すとき、機能一覧を確認して、一般提供（GA）と、プレビューを区別することを勧めています。**パブリックプレビューのものは本番環境に入れるべきではない**という考えです。変化が速く、準備中は SharePoint リストのミラーリングなどがパブリックプレビューだったものの、今週のニュースまとめでは GA になっていたと話しています。

発表時点での整理は次のとおりです。

| 状態 | 対象 |
|---|---|
| GA | Azure SQL Database、Cosmos DB、BigQuery、Snowflake、Databricks Unity Catalog、Snowflake のメタデータミラーリング |
| パブリックプレビュー | MySQL、Dremio（音声認識の表記は「Dreamio」で、確定できません） |

GA になったことを確認してから POC を作り、そのうえで本番に移す進め方です。

### 5.7 移行テンプレート

移行ごとに使えるテンプレートを示しています。例は、CRM（背後が Azure SQL Database）、SaaS アプリ、メインフレームのファイルの手動抽出の 3 行です。各行で次を確認します。

1. 種類を決める（データのミラーリング、メタデータミラーリング、オープンミラーリングのどれか）
2. 今日の提供状況（GA かパブリックプレビューか）
3. 自分のユースケースでどう動くかの確認
4. 担当者（移行のオーナー）
5. ロールバックの方法

最後の行（メインフレームの手動抽出）には、ミラーリングの道筋は置いていません。システムからデータを取り込み、パイプラインのまま運用するためです。**すべてのユースケースにミラーリングを強いない**というのが発表者の方針です。

パイプラインをミラーリングに置き換える進め方も示されました。まずミラーリングを構成し、ミラーリングとパイプラインを並行して稼働させます。行数を比べて、正しく動いていることを確認します。次に、ゴールド層を、ミラーリングされたテーブルから作る新しいセマンティックモデルに向け、そのうえでパイプラインを無効化します。パイプラインは削除しません。失敗したときにパイプラインへ戻れるよう、ロールバックの期間を確保します。

### 5.8 Q&A

質疑応答の時間は約 2 分で、2 つの質問がありました。

1. **Power BI の「ビジュアルの更新」は常に手動か**：デモのような手作業は不要で、レポート層の設定で自動的に更新できます。
2. **ミラーリングのときのソースシステムへの性能影響（遅延）**：ソースシステムによって異なる、というコンサルタント的な答えでした。たとえば Azure SQL は数ミリ秒の遅延です。発表者は、新しい Fabric アプリを使えば、自分のテナントで遅延の監視フレームワークを立ち上げられると紹介しました。Snowflake、Cosmos DB、Azure SQL など、ソースごとの遅延を確認できます。ソースシステム側の負荷そのものについては、答えられていません。

発表者は、会場の脇で追加の質問を受け付けると述べています。

## 6. デモ・手順

デモは、オープンミラーリングで旧システムの CSV ファイルを取り込み、Power BI のレポートの行数が変わる様子を見せるものです。画面の細部は音声からは確認できず、以下は語られた範囲です。

1. Power BI のレポートを開く。42 行が表示されている。レポートは Direct Lake 接続でセマンティックモデルにつながり、そのセマンティックモデルがミラーリングのデータを読む。青い線がレポートとセマンティックモデルの直接接続を示す。このため背後での更新は不要。
2. レイクハウスには注文データがある。レポート、セマンティックモデル、レイクハウスの順に、関係する成果物を確認する。
3. ミラーリングの構成画面を開く。ここではオープンミラーリングを使い、旧システムから抽出した CSV ファイルをアップロードしている。このデモでは手作業だが、実運用では、ソースシステムにつながる自律的な処理になる。
4. 監視（レプリケーションのモニタリング）を確認する。最初の取り込みの 42 行が見える。
5. レプリケーションを停止し、確認する。
6. ファイルをアップロードする。**追記ではなく、全件の初回ロード**である。差分の 9 行だけをアップロードすると、レプリケーションにもレポートにも 9 行しか表示されない。そこで、ダウンロードフォルダーにある全ファイルを、同じテーブル名でアップロードする。
7. レプリケーションを再開する。51 行がミラーリングの領域に入る。
8. 51 行が入ると、セマンティックモデルが自動的にデータを更新し、レポートにも反映される。実際に確認すると、行数は 51 行になっている。
9. 発表者は、セマンティックモデル、レイクハウス、レポートでは何もしていない。レポートでは手動で「ビジュアルの更新」を行っただけで、セマンティックモデルは更新していない。

つまり、ソースからミラーリングへのレプリケーションごとに、レイクハウス、セマンティックモデル、Power BI のレポートが自動的に更新されます。

## 7. 注意点・発表者の気付き

デモの作成中に学んだ 3 点が語られています。

1. **沈黙の失敗**：新しい CSV を取り込んだとき、誰も警告してくれませんでした。51 行を期待したのに 9 行になりました。発表者は、請求データ（発話では Billing）が差分で更新され、42 行に 9 行が加わって 51 行になると考えていました。ところが実際には、**ゼロからの最初のロードのように、すべての行を含む CSV 全体が必要**でした。POC では、手動でレプリケーションを停止し、再開して、この仕組みを理解したと述べています。
2. **レポートが古いまま**：Power BI のレポートに戻ると 42 行しかなく、51 行になっていなかった。原因は、レポートのビジュアルを更新していなかったためです。
3. **1 日のレプリケーション保持**：既定では保持が 1 日で、設定はいつでも変更できます。

そのほかの注意は次のとおりです。

- パブリックプレビューの機能を本番に入れない。GA を確認する。
- ミラーリングを使ってもデータのクエリと Power BI のコンピュートには課金される。
- 移行では必ずロールバックの方法を用意する。

## 8. 利用者にとっての利点

- ミラーリングのコンピュートは容量ユニットを消費せず、課金されない。
- ストレージは、容量に応じた量まで無料（Fabric 64 容量なら最大 64 TB）。
- ネイティブコネクターが多数あり、自分でコネクターを作らなくてよい。
- Azure SQL のミラーリングの遅延は数ミリ秒との説明だった。
- ミラーリングのデータが更新されると、セマンティックモデルとレポートも自動で更新される（Direct Lake 接続）。

顧客事例や具体的な成果は、発表では示されていません。

## 9. まとめ

1. ミラーリングは E と L を担う。T は残り、ビジネスロジックを理解するデータエンジニアの仕事になる。
2. ミラーリングのコンピュートは課金されず、ストレージは 1 TB 単位の無料枠がある。ただしクエリと Power BI の計算は課金される。
3. 種類は、データベース、メタデータ、オープンの 3 つ。GA かどうかを確認し、プレビューは本番に入れない。
4. ミラーリングはすべてのケースに使うものではない。メインフレームの手動抽出は、パイプラインのまま運用する例として挙げられた。
5. オープンミラーリングでは、全件の初回ロードが必要で、差分だけでは足りない。保持は既定で 1 日。ビジュアルの更新も忘れない。
6. パイプラインの置き換えは、並行稼働、行数の確認、ゴールド層を新しいセマンティックモデルに向ける、パイプラインの無効化（削除はしない）、ロールバックの期間の確保、の順に進める。
