# THR988 From Fabric Machine Learning to AI Agents with Microsoft IQ

## 1. はじめに

このセッションは、Microsoft Fabric で動かす従来型の機械学習モデルを、Microsoft Foundry で作る AI エージェントにつなぐ方法を扱います。あわせて、エージェントに適切な文脈を与える Microsoft IQ の層を、どの場面で使うのかを説明しています。

題材は、販売店の離反リスクです。機械学習モデルで「誰が危ないか」を予測し、Fabric の AI 関数で「なぜか」を調べ、オントロジー（用語と関係の定義、ontology）とデータエージェントで「それは何を意味するか」を解釈します。その後、Foundry のエージェントが次の行動を決め、Azure Logic Apps で担当者へ通知する流れです。

本セッションは一日の最後の時間帯で、発表者は聴衆に拍手を送りながら始めています。**画面を使った実演は行われておらず**、スライドと口頭の説明が中心です。実際に試したい人向けに、ハンズオンラボが用意されています。

発表者は、機械学習モデルと生成 AI を対立させず、**組み合わせて使う**ことを勧めています。機械学習モデルが既存データから予測を作り、エージェントがその結果を使って次の行動を決めるという分担です。このセッションの例は離反リスクへの対応でしたが、割引の提示や追加プロモーションの検討など、他のユースケースにも同じパターンを使えると述べています。

もう 1 つの主張は、エージェントの指示を長く書くのではなく、ビジネスロジックを小さな単位（スキル）に分けることです。指示が長いと、ユーザーが対話するたびに全文が大規模言語モデルに送られ、遅延も増えるためです。

## 5. 発表内容の詳細

### 5.1 なぜ従来型の機械学習を取り上げるのか

どのセッションも生成 AI やエージェントが中心ですが、従来型の機械学習にはまだ役割があると説明しています。理由は次のとおりです。

| 観点 | 説明 |
|---|---|
| 説明可能性 | ある判断がなぜ下されたのか、その根拠を示せる |
| 低遅延 | 数ミリ秒で応答が必要なシステムや、エッジデバイスで動かす場合に向く |
| 少量データ | データが少ない状況では従来型のほうが適する |
| 効率・再現性・安定性・コスト | 計算効率がよく、再現性と安定性があり、最先端の生成 AI モデルに比べて実行コストがかなり低い |

### 5.2 Microsoft IQ の 4 つの層

Microsoft IQ の中に 4 つの層があると紹介されています。

| 層 | 内容 |
|---|---|
| Work IQ | Microsoft 365 のデータ（メール、Teams のメッセージと録画、SharePoint のファイルなど）から文脈を得る |
| Fabric IQ | Fabric のワークロードから洞察を得る。Fabric のデータエージェントと オントロジーを含む |
| Foundry IQ | Microsoft Foundry の一部。企業データの上でのエージェント型の検索を提供する。データは Azure SQL や Blob ストレージ、その他の基幹システムなどから来る |
| Web IQ | 生成 AI モデルには知識の期限があるため、Web 上の最新情報を使いたいときに使う |

### 5.3 エージェントを作る選択肢

Microsoft のスタックには多くの選択肢があります。Copilot Studio と Fabric のデータエージェントは SaaS（ソフトウェアサービス）に分類されます。今回使う Microsoft Foundry は PaaS（プラットフォームサービス）に分類されます。オープンソースのフレームワークを使いたい場合も、Microsoft Agent Framework、LangGraph、LangChain に対応しています。

### 5.4 Fabric と Foundry

Fabric は、AI 変革のための Microsoft の統合データ基盤で、多くのワークロードを持ちます。今回は、ノートブックの実行、機械学習の実験、そして生成された機械学習モデルを オントロジーと Fabric のデータエージェントなどと併用する流れに絞っています。

Fabric でデータエージェントを作る一般的な流れは次のとおりです。

1. Fabric のデザイナーを開き、データソースを追加する。データソースはレイクハウス、ウェアハウス、セマンティックモデルなど。
2. 指示とツールを構成する。
3. データエージェントを MCP エンドポイントとして公開する。
4. Fabric のポータル、Copilot Studio、Teams、Microsoft Copilot、Microsoft Foundry から利用する。REST API としても使える。

Foundry は複数のサービスの総称で、次のものが挙げられました。

- モデルカタログ（11,000 を超えるモデル）
- エージェントサービス（マネージドなランタイムとスレッド。プロンプトエージェントとホステッドエージェントの 2 種類を作れる）
- IQ の層
- 各種ツール
- 従来型の機械学習モデルの実行

今回のラボで Fabric を使うのは、データの多くが Fabric にあり、機械学習を学ぶのに適しているからだと説明しています。

### 5.5 ユースケース：離反リスクのある販売店

架空の取引先 Alpine Ascent Cycle（Denver の販売店と説明されていますが、聞き取りは不明瞭です）が、離反しそうな兆候を示しています。この取引先は年間でおよそ 200 万の収益をもたらしており、先回りして対処しないと失うおそれがあります。

問いと、それぞれに答える部品が次のように整理されています。

| 問い | 担当する部品 |
|---|---|
| 誰が危ないか | Fabric の機械学習でデプロイしたカスタムモデル |
| なぜ危ないと考えるのか | Fabric の AI 関数 |
| それは何を意味するか | Fabric IQ の オントロジーとデータエージェント |
| 次にどうするか（適切な関係者への通知） | Microsoft Foundry で作ったエージェントのビジネスロジック |
| 判断ループと関係者への通知 | Azure Logic Apps による連携 |

発表者は、同じシナリオを別の構成で実現する選択肢も挙げています。Fabric の機械学習の代わりに Foundry の機械学習機能、Foundry のエージェントの代わりに Copilot Studio のエージェント、Azure Logic Apps の代わりに Copilot Studio のワークフロー機能です。特定の技術に縛られないための例です。

### 5.6 機械学習モデルの学習と登録

モデルの学習では、Fabric のノートブック（Python）で実験を行い、1 つの MLflow 実験の中で 2 回の実行を比較します。結果を評価し、成績のよい実行のモデルを登録します。その登録したモデルを、ビジネスロジックで使います。モデルは、データがある場所で実行するのがよいと述べています。

### 5.7 AI 関数

機械学習モデルの出力の例として、「Fabrikam Cycles が一覧価格の 35 を提示してきた」という趣旨のコメントが示されました（数値の単位は聞き取りでは確認できません）。AI 関数を使うと、このようなコメントから次のものを取り出せます。

- 感情（センチメント）
- テーマ
- 競合の名前
- 話題にしている製品

実装の手順としては、まず 1 つの販売店についてセンチメントとテーマを設定します。次に、52 件のコメントすべてに競合と製品を付加します（「52」は聞き取りの数値です）。最後に、販売店ごとに 90 日分を要約します。

### 5.8 オントロジーとデータエージェント

オントロジーは、**データとエージェントの間の取り決め**（コントラクト）です。販売店について、エンティティとして、販売店の活動、アカウントマネージャー、離反リスク、販売店の声、販売店のフィードバックなどを定義できると説明しています。値の意味づけの例として、「リスクあり」の場合は離反リスクの値が高になること、「リスクのある収益」は米ドルで表すことが挙げられました（音声認識の都合で正確な項目名は確定できません）。

Fabric で行う作業は次のとおりです。

1. Alpine Ascent のグラフを調べる。
2. データエージェントに自社の用語を教える。
3. ビジネスの質問を投げ、グラフクエリを確認する。
4. 他のエージェントが使えるよう、Fabric のデータエージェントを公開する。

### 5.9 指示をスキルに分割する

Copilot Studio でも Microsoft Foundry でも、エージェントには指示を書きます。エージェントは、前の手順の結果やユーザーの要望に応じて、その指示をもとに判断します。多くの開発者は、あらゆる場面を想定して長い指示を書きがちです。

代わりに、ビジネスロジックを複数の**スキル**に分けることを提案しています。パターンに応じてエージェントがスキルを呼び出し、スキルが詳細な手順、呼び出せる知識ソースやツールを持ちます。メインの指示は最小限で済みます。ユーザーが対話するたびに、指示のすべてが基盤の大規模言語モデルに送られるため、ビジネスロジックを小さく分けると処理が効率的になり、エージェントの遅延も減るという説明です。

このラボでは、まず調査スキルの手順を読み、それをハーネス（エージェントの実行枠組み）に追加して実行します。

### 5.10 人による確認と全体のフロー

Fabric のデータエージェントが「この取引先は危険」と推奨を返したあと、リスクをどう軽減するかと、どう人を関与させるかが課題になります。そこで Azure Logic Apps のコネクターを使い、適切な担当者にメールを送ります。受け取った担当者（または販売店の担当者）は、ケースを確認し、データを見たうえで予防的な措置を取るか、エスカレーションを承認します。

エスカレーションの内容には、どの販売店か、リスクは何か、なぜリスクがあると考えるのか、取りうる対処、軽減策の承認者は誰かを盛り込めます。最後の手順としてすべてを文書化できます。

全体のフローは次のとおりです。

1. Foundry の中に販売店の売上データがある。
2. 販売店の維持（リテンション）エージェントが動く。
3. エージェントはスキルを使い、Fabric IQ ツールで Fabric IQ を呼び、Fabric のデータエージェントと対話する。
4. その出力に基づき、Azure Logic Apps を呼ぶ。Outlook のメール送信、または Teams チャネルでの担当者への通知を行う。

## 7. 注意点・発表者の気付き

- 機械学習モデルは、データのある場所で実行するとよい。
- エージェントの指示を長く書くと、対話のたびに全文が大規模言語モデルへ送られる。ビジネスロジックを分割して、メインの指示を最小限にする。
- 同じシナリオでも、Fabric の機械学習、Foundry のエージェント、Azure Logic Apps は、それぞれ別の製品に置き換えられる。
- Fabric のデータエージェントは、Fabric のポータルだけでなく、Copilot Studio、Teams、Microsoft Copilot、Foundry、REST API からも使える。

制約や失敗談については、発表では特に触れられていません。

## 8. 利用者にとっての利点

- 従来型の機械学習は、説明可能で、低遅延で、少量のデータでも使え、生成 AI より実行コストが低い。
- 機械学習の予測と、エージェントによる次の行動の判断を組み合わせることで、離反リスクのある取引先への対応を先回りして進められる。例では、年間およそ 200 万の収益がある取引先が対象。
- スキル分割により、遅延を抑え、指示を小さく保てる。
- 離反対応のほか、割引の提示や追加プロモーションの検討にも同じパターンを使える。

具体的な数値の成果や顧客事例は、発表では示されていません。

## 9. まとめ

1. 従来型の機械学習は、説明可能性、低遅延、少量データ、低コストの面で今も役割がある。
2. Microsoft IQ は Work IQ、Fabric IQ、Foundry IQ、Web IQ の 4 層で、エージェントに文脈を与える。
3. 離反リスクの例では、機械学習が「誰が」、AI 関数が「なぜ」、オントロジーとデータエージェントが「何を意味するか」を担い、Foundry のエージェントが次の行動を決め、Azure Logic Apps が担当者に知らせる。
4. エージェントの指示は長く書かず、スキルに分ける。
5. ハンズオンラボは QR コードで入手でき、Ignite の GitHub リポジトリにも追加される予定。
