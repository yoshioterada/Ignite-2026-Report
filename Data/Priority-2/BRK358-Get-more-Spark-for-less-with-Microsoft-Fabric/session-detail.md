## 5. 発表内容の詳細

### 5.1 セットアップ：ボトルネックに合わせてサイズを決める

Spark を始めるとき、すべてを最大にしてしまう人や、ほかのプラットフォームの設定をそのまま持ち込む人がいます。そこで、ボトルネックを理解したうえでサイズを決めることを勧めています。

Fabric ではまず容量（キャパシティ）のモデルを理解します。容量は消費できる量を制御するもので、次の点を確認します。

- ワークロードがフルで動くときに受け付けられるか
- 並列実行の分を見込んでいるか
- ジョブが来たときに、すべてのコアを予約するかどうかという受け付け方針をどうするか
- ノードサイズが適切か

見落としがちな例として、大規模な分散クラスターを用意しても、読み込み元が細いストローのようにしかデータを返せない小さな API であれば意味がない、という指摘がありました。

Spark は急に大量に消費しうるワークロードのため、課金モデルの選択が重要です。課金モデルは 2 つあります。

| モデル | 内容 |
| --- | --- |
| 容量モデル | Fabric の容量を購入して使う方式 |
| 自動スケールのサーバーレス課金 | F0 の容量から始め、Spark の使った分だけ支払う方式。Synapse の課金モデルに近い |

サーバーレス課金を選べば、Spark の消費が容量を食いつぶして他のワークロードが止まる事態を避けられる、というのが発表者の説明です。コスト抑制に有効だとも述べています。

規模の小さいワークロードについては、Spark ではなく Python ノートブックで足りる場合があると指摘しています。また、個別のノートブックではなく、アプリケーション全体（やるべき仕事の全体）として、並列実行モードをどう組み合わせるかを考えるよう促しています。

### 5.2 高い並列実行モード

高い並列実行モード（high concurrency mode）は Synapse には無かった機能です。1 つの Spark ドライバーの中で、複数のアプリケーションを同時に実行し、クラスターと容量を共有させます。小さなジョブが多い場合や、起動コストを避けたい場合に特に有効だと説明されました。

制約として、同じユーザー、同じ環境などの条件が必要です。既定値は 5 セッションで、慎重な設定としているものの、最大 50 セッションまで共有できます。ノートブック、レイクハウス、Livy の 3 つが高い並列実行に対応しています。

### 5.3 セキュリティ

本番に持っていくときは、データがどこかから入りどこかへ出ていくため、安全な環境で動かす必要があります。発表では次のキーワードが挙げられました。

- **ネットワーク分離**：Spark ジョブに対して提供されます。外部への通信を境界の外に出さない「アウトバウンドアクセス保護」と、外から中に通すときのプライベートリンクを組み合わせます。
- **きめ細かなアクセス制御**：Synapse ではオブジェクト単位が中心でしたが、Fabric ではレイクハウスのテーブルに対して行レベルと列レベルのセキュリティを設定できます。OneLake セキュリティとして知られる概念です。
- **カスタマー管理キー（CMK）**：コンプライアンスが必要な場合にデータを守る手段として挙げられました。
- **管理されたエンドポイントと VNet**：接続したいエンドポイントや VNet の設計を、ワークスペースの設定時に考えておきます。

メダリオンアーキテクチャや、取り込みと提供を別ワークスペースに分ける構成では、ワークスペース間の接続と、各ワークスペースの権限・ロールを最初に整理しておくと、あとでロールやレイクハウス、スキーマを分離する作業をやり直さずに済む、と説明しています。

### 5.4 ライブラリ管理

Spark ジョブやノートブックには、自社で作ったライブラリなど、本体以外のコードが必要になります。セッションを起動するとき、そのコードをクラスターに読み込むのがライブラリ管理です。

既定では、Microsoft が検証した PIP のチャネルや Conda のチャネルから取得できます。これを禁止して、自社が管理するデータソースやチャネルだけに制限したい場合は、自前のプライベートな PyPI ミラーを用意する方法があります。管理されたプライベートエンドポイントでストレージアカウントを接続し、そこからミラーを提供する構成で、安全でコンプライアンスにも沿うと説明されました。

### 5.5 信頼性

ジョブを予測どおりに動かすことが目的で、SQL の世界でいうワークロードガバナンスに当たります。ワークスペースと容量には CU の上限やスロットリング率があり、それを理解しておく必要があります。

- **優先度付きのジョブ投入**：ユーザーからの要望を受けて、近日中に提供予定です。プール単位またはノートブック単位で優先度を付けられるようになります（提供済みではなく、予告された計画です）。
- **コア予約**：ジョブが来たときに必要なコアをすべて予約する方式と、しない方式があります。予約すれば信頼性は上がりますが、同時に動くジョブの数は減ります。既定では予約しません。予測可能性が必須なら有効にします。
- **容量レベルの制御**：ジョブのバーストの制御や、スタータープールの無効化ができます。

スタータープールは、ノートブックを開くとすぐセッションが得られる「5×5」の体験を支える仕組みで、あらかじめ一定の構成のクラスターを多数用意しています。構成が気に入らなければ無効にして、自分で構成したクラスターを必ず使わせることができます。

ただし、スタータープールは VNet に対応していません。利用者自身の VNet 内の安全な環境では、スタータープールを動かせないためです。即時接続の体験を再現したい場合はカスタムプールを用意します。多少の費用がかかりますが、コストを減らす工夫を進めてきたとのことです。カスタムプールには、利用者の環境設定が事前に適用されるという利点もあり、既定のスタータープールより少し費用を節約できると説明されました。

### 5.6 ジョブの起動方法（オーケストレーション）

既存環境から移行する場合に、Fabric へジョブをどう投入するかの選択肢が紹介されました。

- スケジュール実行のパイプライン
- Airflow（コネクタあり）
- Livy API（Livy 向けの Spark Python クライアントを開発中で、後日公開予定）
- ODBC・JDBC のコネクタ
- プラットフォーム組み込みの Spark スケジューラー
- イベントベースのトリガー（何かが起きたときにジョブを起動する、Reflex と呼ばれるもの）

ODBC・JDBC のドライバーは Livy に接続できます。オンプレミスで Cloudera や Hortonworks の HS2 サーバー、Spark の接続エンドポイントを経由していた場合、Simba や Insight Software などから入手したドライバーを使っているはずです。その場合、ドライバーを差し替えて接続先を指すだけで、アプリケーションのコードを変えずに済みます。もちろんデータとメタデータの移行は必要です。

発表者は、ODBC・JDBC に高い並列実行、ネイティブ実行、カスタムプールを組み合わせた構成が、既存の環境を再現する理想の一例だと説明しました。

### 5.7 チューニング：ランタイムとネイティブ実行エンジン

Fabric Spark は GA から 3 年たち、古いバージョンのまま使っている利用者が多いため、まず **Runtime 2.0 へのアップグレード**を強く勧めています。Runtime 2.0 は Spark 4.1 に対応しています。発表では、Spark 4.3 が最新で数週間前にリリースされたが、Fabric で使える最新は Spark 4.1 と述べられています。機能と性能の両面で利点があります。

次に、既定では有効になっていない**ネイティブ実行エンジン**です。Spark は従来 Scala の JVM ベースのアプリケーションで、JVM には性能面のコストがあります。そこで、Meta や IBM などと協力し、Spark のスタックをネイティブコードで動かす取り組みを進めており、Gluten と Velox の 2 つのプロジェクトを使っています（Velox は聞こえた綴りが「Vlox」で、音声認識の都合で表記が確定できません）。12 月の VeloxCon で関連する発表があるとも触れています。

有効にした顧客からは 2〜4 倍の性能向上というフィードバックがあり、場合によってはそれ以上の向上もあります。**追加料金は無い**ため、使わないのは機会損失だと発表者は述べています。節約した分を Copilot の費用に回せる、という言い方もしています。

Spark 4.1 での性能面の更新として、次の点が挙げられました。

- Z オーダーとリキッドクラスタリングの読み書きに対応
- CSV と JSON のネイティブパーサーに対応
- 複雑なデータ型にネイティブ実行エンジンで対応
- Python や Scala の UDF が出てきてもネイティブ実行を維持（他社製品の中には、UDF を見た時点でネイティブをやめ、残りの計画を JVM で実行するものがある、との比較）
- オプティマイザーのコストモデルを改善して最適な計画を出し、JVM コードへのフォールバックを減らす取り組み

2 週間前に試した人も、早期アクセスのチャネルで試し直すと、ネイティブ実行エンジンで動くコードの割合が大きく増えていることに驚くはずだ、と述べています。今後の予定として、ネイティブエンジンでの構造化ストリーミングへの対応と、完全な ANSI 対応が予告されました。有効化は Spark のプロパティを 1 つ設定するだけです（プロパティ名は発話では確認できません）。

ほかに、Runtime 1.3 と 2.0 を比較した、ライブラリ管理（クラスター作成時のカスタマイズ）の高速化のグラフがありました。Runtime 2.0 のほうが速く、時間の節約になります。複雑なデータ型を使った場合でも、ネイティブ実行エンジンで 2 倍高速になることを示すスライドもありましたが、発表者はデモ部分を省略しました。

### 5.8 チューニングの前に：目標と実験の設計

チューニングの前に、まずアーキテクチャのレビューを行うよう勧めています。そのうえで、スライドに無いが最も大事な点として、**目標が無ければチューニングを始めない**と述べました。終わりの基準も、かける労力の見当もつかないからです。目標としては SLA を決めます。そのうえで、次の問いに答えます。

- データモデルはどうか。クエリの種類に対して、正規化が必要か、スタースキーマが必要か
- データ量はどのくらいか
- 取り込みのパターンはどうか。追記か、マージか、上書きか

なぜそのやり方なのかを疑うことも重要です。ほかの SQL 系のシステムの知識を持ち込む顧客が多いものの、Spark の動きは同じではありません。例えば Spark には ID 列（identity）や制約の強制がないため、マージのやり方が変わる、という例が挙げられました。

その後で、Spark の設定、クラスターサイズ、ジョブのスケジュール（受け付けや並列実行の問題を避けるため）を調整します。

実験は再現できるように設計します。並列負荷が高く再現できないワークロードや、5 つの設定を一度に変えてどれが効いたか分からない例が多いので、理科の授業のように、変更の効果を確信できる実験にする必要があります。

### 5.9 よくある問題：データの偏りとシャッフル

**データの偏り（スキュー）**：Spark は 1 台のノードでは大きすぎるジョブを複数ノードに分割する仕組みです。8 ノードのうち 7 ノードが遊び、1 ノードだけが働いていれば、リソースを活かせていません。発表者が顧客の性能改善に呼ばれるとき、最初に見るのがこの偏りだそうです。実行ノードではなく、ジョブの合間にドライバーがログ出力や集計をしていて、クラスターを使っていない例もあります。長い尾（遅れて終わるタスク）を特定して直し、すべてのノードを稼働させます。

偏ったノードは、それ自体が遅いだけでなく、メモリ不足からディスクへの退避（スピル）を起こし、二重に遅くなることがあります。偏りとスピルは、ジョブが速くならない最大の原因だと述べています。

**シャッフル**：各タスクが処理した後、次の段階でデータを再配置して分散処理するのがシャッフルで、全員が待つ関門になります。偏りがあると遅れが積み重なります。対策は次のとおりです。

- シャッフルを無くす。小さい側をブロードキャストする結合に変えれば、結合の両側をシャッフルしなくて済む
- マージクエリでは、行の特定ロジックのせいで絞り込み条件をシャッフルより前に押し下げられず、シャッフルが巨大になることがある。データ移動を減らすほどジョブは速くなる
- 適応型クエリ実行（AQE）は既定で有効だが、古いランタイムで性能が出なかったために無効にしていた顧客がいる。再度有効にする
- リモートシャッフルの開発中。8 ノードのうち 7 ノードが不要になったとき、データを転送してノードを返却し、自動でスケールダウンできるようにする構想（提供済みではなく開発中の計画）

実例として、フィールドエンジニアが共有した顧客の事例が紹介されました。ジョブが極端に遅く、Spark の計画が繰り返しのシャッフルに支配されていて、数百テラバイトのデータをシャッフルしていました。結合の 1 つをブロードキャスト結合に変えたところ、データ量が大きく減り、全体が高速になりました。

そこで、**クエリ計画を読めるようになる**ことを強く勧めています。SQL の経験者なら特に有効な技能で、不要な作業を見つけられます。典型的には、絞り込み条件が十分に押し下げられていない、シャッフルするデータが多すぎる、集計や結合が誤っている、といった点です。考え方としては、入力で詰まらせない、不要なシャッフルを避ける、書き込みを最適に行う、の 3 点です。

### 5.10 書き込みの設定とメダリオンアーキテクチャ

Spark はメダリオンの 3 層すべてで使えますが、通常はブロンズとシルバーで使い、ゴールドは別の仕組みが提供する形が多いようです。ゴールド向けとシルバー向けでは設定を変えるとよく、特に Power BI の DirectQuery モードでレイクから直接読ませる場合は、Power BI が読みやすい形でファイルを書くことが大切です。そのために、データをより圧縮する最適化書き込みや V オーダー（発話では「reorder」と聞こえます）を有効にします。増分更新が続く場合は、自動コンパクションでデータの断片化を防ぎます。特別な用途以外には、有効にしないことを勧めるフラグもスライドに載っていましたが、個別の名前は発話では確認できません。

### 5.11 監視：Spark 履歴サーバー

Spark エコシステムで最も役立つツールの 1 つが Spark 履歴サーバーです。オープンソースでも長く使われてきたもので、Fabric の監視ページから移動できます。読み方に慣れておくことを強く勧めています。

発表では、前述のデータの偏りの例をスライドの画像で見せています。実行ノードを 1 本の帯として表示した画面で、上の 2 つの実行ノードだけが忙しく、残りが遊んでいます。目立つ部分ではタスクが走り続けていました。レイテンシーだけでなく利用効率の面でも避けたい状態であり、この見た目を判別できるよう、実際にジョブを開いて確認することを勧めています。別の例として、約 30 GB のデータがディスクにスピルし、ジョブを遅くしているものも示されました。

### 5.12 サポートに問い合わせるとき

Fabric Spark により、ビッグデータの技術に慣れていない初めての利用者も増えました。Python や分散技術に不慣れで、どう質問すればよいか分からず不満を持つ人がいるため、問い合わせ時のお願いが示されています。

1. アプリケーション ID を明らかにする
2. どのようなジョブをしていたかを説明する
3. ログを添付する
4. 承認された経路で安全に共有する（メールでは送らない）

これを守れば解決までの時間が短くなると述べています。

### 5.13 テストとデプロイ

夜中に起こされないために、繰り返し同じ性能が出て、ジョブが確実に動く状態が必要で、そのためにテストとデプロイの戦略が要ります。GitHub Actions で自動化し、すべてのプルリクエストをテストし、チェックイン時の関門を置き、夜間テストを行い、テスト用・ステージング用・本番用の環境を用意するよう勧めています。

**リリースチャネル**には、既定と早期アクセスの 2 つがあります。本番で使うのは既定です。早期アクセスは夜間ビルドのようなもので、既定にする前の変更が先に出ます。テスト環境やステージング環境の 1 つで早期アクセスを有効にしておけば、問題が既定に届く前に見つけられ、本番での想定外を防げます。問題があればケースを起票して相談できます。

**リソースプロファイル**は、メダリオンの各層ごとにチューニングやサイズ設定が異なる事情に対して、関連する設定をまとめて適用する仕組みです。例として、読み取り重視（スライドの名前は「read heavy」）や書き込み重視のプロファイルがあります。Power BI 向けにデータを圧縮し V オーダーで書く場合、10 個ほどのプロパティを一度に設定する必要がありますが、プロファイルを 1 つ選べば適用されます。変数ライブラリと組み合わせると、設定の組を一貫して保てます。提供されるプロファイルのほかに、カスタムプロファイルも作れます。変数ライブラリやテスト環境と組み合わせて、接続先や設定の組を選び、テストとデプロイの戦略に組み込みます。

**自動更新プロファイル**：従来の静的プロファイルを選ぶと、本番で挙動が変わらないという利点がある一方、Microsoft が性能改善を出し続けても利用者がその恩恵を受けられず、発見も難しいという課題がありました。そこで Spark 4.1 と Runtime 2 で、自動更新プロファイルが導入されました。本番環境では静的プロファイル（リリースチャネルの既定に相当）を使い、テスト環境やステージング環境では自動更新プロファイルを選びます。既定でオンになる新しいフラグなどのチューニング変更がここに入るため、性能に差が出るかを確認できます。明確なテストとデプロイの戦略があれば、本番を壊さずに、性能を継続的に改善できるという説明です。

## 7. 注意点・発表者の気付き

- 目標（SLA）が無いままチューニングを始めない。終わりの基準が分からなくなる
- 設定を一度に複数変えない。再現できる実験でなければ、何が効いたか分からない
- ほかの SQL 系システムの知識をそのまま持ち込まない。例えば Spark には ID 列や制約の強制が無く、マージの方法が変わる
- スタータープールは VNet 環境では使えない。即時接続が必要なら、カスタムプールを用意する（多少の費用がかかる）
- コア予約は既定でオフ。予測可能性が必要なら有効にするが、並列実行の数は減る
- 高い並列実行モードには、同じユーザー、同じ環境などの条件がある
- AQE を過去に無効にした顧客は、有効に戻す
- 静的プロファイルでは性能改善に気付けない。本番以外では自動更新プロファイルを使う
- 優先度付きのジョブ投入、リモートシャッフル、ネイティブエンジンの構造化ストリーミング対応と完全な ANSI 対応、Livy 向け Spark Python クライアントは、いずれも予告・開発中で、提供済みの機能ではない

## 8. 利用者にとっての利点

- ネイティブ実行エンジンで 2〜4 倍の性能向上（顧客のフィードバック。場合によってはそれ以上）。追加料金は無い
- サーバーレス課金により、Spark の消費で他のワークロードの容量が不足する事態を避け、コストを抑えられる
- 高い並列実行モードで、小さなジョブの起動コストを避けられる（既定 5、最大 50 セッション）
- ODBC・JDBC のドライバーを差し替えるだけで、オンプレミスのアプリケーションコードを変えずに移行できる
- ある顧客の例では、結合をブロードキャスト結合に変えることで、数百テラバイト規模のシャッフルを減らし、全体が高速になった
- リリースチャネルと自動更新プロファイルにより、本番を壊さずに性能改善を取り込める

## 9. まとめ

Fabric 上の Spark を本番で成功させる鍵は、デモの手軽さの先にある設計判断です。セットアップでは、課金モデル、容量、並列実行、ネットワークとアクセス制御、ライブラリの取得元、ジョブの起動方法を最初に決めます。チューニングでは、Runtime 2.0 へのアップグレードとネイティブ実行エンジンの有効化を行い、目標と再現できる実験を用意してから、偏りとシャッフルを減らします。監視では Spark 履歴サーバーとクエリ計画の読み方を身につけます。最後に、リリースチャネルとリソースプロファイル、自動更新プロファイルを使ったテストとデプロイの戦略を持つことで、本番の安定と継続的な改善を両立します。
