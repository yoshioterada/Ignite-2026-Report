# THR970 What if your data agents spoke your business language

## 1. はじめに

このセッションは、組織で作る AI エージェントに、自社の業務の言葉を理解させるにはどうするか、を扱う約 25 分の発表です。題材は **Fabric IQ** の **オントロジー（ontology）** で、データを 1 か所に統合しただけではエージェントはデータの意味を理解できない、という問題から始まります。

発表者は、架空のコーヒーチェーン 4th Coffee を例に、「エスプレッソが酸っぱい」という問いに答えられないエージェントを、オントロジーによって答えられるエージェントへ変えていく流れを見せました。会場で画面を操作するデモがあり、オントロジーの画面、Copilot Studio のエージェント、GitHub Copilot からの接続が示されています。**統合されたデータは、理解されたデータではない**というのが中心のメッセージです。

## 3. 何に関する発表か

テーマは、データエージェントや AI エージェントが業務の言葉を話せるようにするための、Fabric IQ のオントロジーです。Fabric IQ は、発表のなかで **Microsoft IQ** の 4 つの種類のうちの 1 つとして位置づけられています。

発表の流れは次のとおりです。

1. 導入の例：コーヒーショップで「エスプレッソが酸っぱい」と言われた店長の問い
2. 4th Coffee のシナリオと、データが分散している状況
3. 「統合」と「理解」は別、というエージェントが直面する課題
4. Microsoft IQ の 4 つの種類
5. Fabric IQ の 3 つの層と、オントロジーの構成要素
6. デモ：オントロジーの画面、Copilot Studio、GitHub Copilot
7. 始め方と提供状況、注意点

## 4. 発表者が伝えたいメッセージ

発表者は、データを OneLake に統合しても、エージェントから見ればテーブル、列、行があるだけで、意味がないと説明します。そのため、有効なクエリを実行して正しいデータを取り出せても、業務上の質問への答えを間違える可能性があります。エージェントが 10 個あれば、同じ質問に 10 通りの答えが返りかねません。それぞれが、クエリ結果を自分なりに解釈するからです。

これに対する発表者の答えは、業務の言葉を地図にしたオントロジーを作り、あらゆるエージェントがそれを参照する形にすることです。始め方としては、組織全体を一度にモデル化しようとせず、**2 つのシステムにまたがる業務上の問いを 1 つ選んで**始めることを勧めています。

## 5. 発表内容の詳細

### 5.1 導入の例とシナリオ

シアトルのコーヒーチェーンで、朝に客が注文したコーヒーについて「エスプレッソが酸っぱい」と伝えます。店長は、問題が機械にあるのか、豆にあるのか、と考えます。長く働いている従業員なら原因を切り分けられますが、AI エージェントに同じことを尋ねると、運用に関するデータをすべて渡していても、答えられないかもしれません。このセッションでは、これに答えられないエージェントを、明確に答えられるエージェントに変える過程を示します。

シナリオ上の会社は 4th Coffee です。発表では、店舗は 33,000 以上、85 を超える国と地域、従業員は 274 以上と述べられています（従業員数は店舗数に比べて極端に少なく、音声認識の都合で正確な数値が確定できません）。調達から客への提供までの工程ごとに標準を持ち、コーヒーは、育てる農家、それを製粉する加工業者、焙煎業者を経て、店舗の客の手に渡ります。朝の問題は、この連鎖のどこでも起こりえます。店舗の機械かもしれず、農家かもしれません。そのため、AI エージェントは、連鎖全体にまたがるデータを根拠に答える必要があります。

データは複数のシステムにまたがっています。

| システム | 保存しているデータ |
| --- | --- |
| Azure SQL Database | 運用の記録（店舗、オペレーション、注文） |
| Cosmos DB | 各店舗に設置された機械（接続されたエスプレッソマシン、グラインダー）のデータ |
| Lakehouse | 多数のパートナーに関する記録 |
| Azure Horizon DB（表記は音声認識の都合で確定できません） | サプライチェーンと監査 |

これらはすべて OneLake に集約されています。発表者は、多くの組織が同じようにデータを 1 か所に集め、その上に分析システムや AI エージェントを構築しようとしていると述べました。

### 5.2 統合と理解は別である

データを統合しても、エージェントが持つのはデータであって、意味ではありません。発表では、エージェントが直面する課題として次の 3 つが挙げられました。

1. **同じ対象の呼び名が違う。** 店舗は Azure SQL Database では店舗 ID で参照されますが、サプライチェーンの Horizon DB では「配送先」と呼ばれ、列名は配送先 ID です。この組織に長くいる人は調整できますが、AI エージェントは Cosmos DB、Azure SQL Database、Horizon DB の店舗を結びつけられません。関係が定義されていないからです。
2. **言葉の意味が違う。** 「出荷済み」と「配達済み」は同じではありません。エージェントはすべてのデータにアクセスできますが、この違いを教える方法がありません。
3. **業務ルールがある。** 4th Coffee には、ある事業者（発話では firm）が、コーヒーを買う日に良好な状態（standing）でなければならない、という調達の規則があります。この規則は従業員の頭の中にありますが、AI エージェントに明示的に伝える手段がありません。

> 補足：この規則の対象が農家なのか別の事業者なのかは、発話では確認できません。音声認識では「firm」と書かれており、そのまま事業者と記しています。

### 5.3 Microsoft IQ の 4 つの種類

Microsoft IQ は「企業向け AI のための統合的な知能」で、AI エージェントに 4 種類の文脈を与えるものだと説明されました。

| 種類 | 役割 |
| --- | --- |
| Web IQ | 現実世界の情報に接続する。例：特定の地域でのコーヒー生産の動向 |
| Work IQ | 従業員やチームの協働に接続する。会議、カレンダー、Teams など、従業員が一緒に働く場にあるデータ |
| Foundry IQ | 組織の知識。ポリシー、契約、権威ある文書、ナレッジベース |
| Fabric IQ | ビジネスの状態。組織内のビジネスエンティティ、記録のシステム、取れる行動に答える |

### 5.4 Fabric IQ の 3 つの層

| 層 | 内容 |
| --- | --- |
| OneLake | 構造化、非構造化、リアルタイム、バッチ、グラフのデータを 1 か所に統合する。 |
| ビジネスインテリジェンス | Power BI のセマンティックモデル。組織が過去 10 年かけて作ってきた指標や KPI が置かれる。 |
| オントロジー | 最上位の層で、運用のインテリジェンスを加える。指標、KPI、統合したデータの上に、企業のビジネス言語を構築する。 |

### 5.5 オントロジーとは何か

発表者は、オントロジーを「**ビジネスの言葉を定義し、AI エージェントが解釈できる地図**」「ビジネス全体の共有モデル」と説明しています。前に挙げた、ルールを伝える手段がない、同義語を表現できない、システム間のエンティティを結べない、という障壁を解消できるとしています。構成要素は次の 4 つです。

1. **エンティティ型**：4th Coffee なら店舗、顧客、機械など。データベースのテーブルとしてではなく、実際のビジネス上の対象として捉え、そこにデータを持ち込みます。
2. **リレーションシップ（関係）**：エンティティ型の間の関係です。Azure SQL Database の店舗と Horizon DB の配送先を 1 つのエンティティとして扱い、それが機械とどう関係するかを定義できます。たとえば「シアトルの店舗に設置されている機械は何台か」という質問をして、掘り下げられます。
3. **データバインディング**：エンティティと関係を定義したあとで、複数のデータソースをエンティティに結び付けます。
4. **ビジネスルール**：専門家の頭の中にある業務ロジックを、直接オントロジーにエンコードします。

発表時間の都合で簡略化された例として、店舗、出荷、梱包作業、焙煎バッチなどのエンティティと、その関係が示されました。焙煎バッチは特定の農場の生豆ロットを使い、梱包作業は特定の焙煎バッチを梱包する、といった具合に、工程全体を 1 つのオントロジーで表現します。そのため、ビジネス用語で直接質問でき、オントロジーが意味を補います。その下にはデータソースがあり、SQL のバッチデータ、Horizon DB の PostgreSQL、機械から送られるテレメトリのようなリアルタイムのデータ（イベントハウスに保存）も含められます。

### 5.6 オントロジーを使うエージェント

構築したオントロジーは、複数のエージェントから使えます。

- **オントロジーエージェント**：オントロジーに問い合わせられるエージェントです。
- **Copilot Studio**：構築済みのオントロジーに接続するエージェントを作り、M365 Copilot に公開すれば、組織全体がアクセスできます。
- **MCP クライアント**：MCP に対応するクライアントなら、Fabric IQ のオントロジーに直接接続できます。
- **データエージェント**：オントロジーをデータエージェントのデータソースにすることもできます。

### 5.7 始め方

1. **提供状況**：オントロジーは現在も**パブリックプレビュー**です。デモで見せた内容は、すべて自分で試せるとされています。オントロジーを構築し、MCP サーバーとして公開し、Copilot Studio で使い、エージェントを作って M365 Copilot に公開できます。データエージェントのデータソースとして追加し、Foundry IQ などで使うこともできます。
2. **作り方**：キャンバスにエンティティをドラッグし、関係を追加し、データをバインドする方法のほか、**オントロジーエージェント**を使って、自然言語でオントロジーを記述する方法もあります。
3. **進め方**：組織全体を一度にモデル化するのは、多くの組織が犯す最大の間違いの 1 つです。複数のシステムをまたぐ業務上の問いを 1 つ選び、そこからモデル化します。ビジネスルールとビジネス言語（同義語を含む）を表現したうえで、オントロジーエージェント、データエージェント、または M365 Copilot に公開して使います。

## 6. デモ・手順

発表者は会場の端末に切り替えて、次の内容を実演しました。音声のナレーションで語られた範囲に限り、順に記します（画面の細部は音声からは確認できません）。

1. **オントロジーの画面を開く。** 4th Coffee のオントロジーの全体を表示しました。左側にエンティティ型（店舗、設備、作業指示など）が並び、それぞれの間に関係があります。
2. **ルールを開く。** ルールの一覧を展開し、調達のルールを開きました。ルールには名前と定義があり、定義は自然言語で書けます。さらに、特定のオントロジーの要素にひも付けられ、このルールが適用されるエンティティ、関係、プロパティを指定でき、追加のメタデータも付けられます。プロパティは、たとえば店舗なら場所や営業時間のように、エンティティを定義する属性です。
3. **Copilot Studio のエージェントを使う。** 発表者は、オントロジーを Fabric 内のオントロジーエージェントでも M365 でも試せると述べたうえで、Copilot Studio にすでに作成してあったエージェントを、オントロジー MCP に接続した状態で使いました。「特定の日付に、シアトルのドライブスルーへ送られた梱包作業を見せて」と尋ねると、シアトルへ出荷された出荷分がすべて表示されました。
4. **掘り下げる。** さらに、シアトルへ出荷されたロットのうち、調達のルールに適合していないものがないかを確認し、問題の原因が豆だったのか、壊れた機械だったのかを判断できる、と説明しました。設備のエンティティ型はリアルタイムデータにバインドされており、機械から OneLake に流れ込むリアルタイムのデータにも問い合わせられます。
5. **GitHub Copilot から接続する。** GitHub Copilot をオントロジーの MCP に接続済みの状態を見せました。URL を指定するだけで、Office 365 アカウントでのサインインを求められ、それで設定が完了するとのことです。MCP に対応するものなら何でも接続できる、と説明されています。

発表者は、デモの画面が戻らなくなる場面があった（「デモが戻ってこない」）と述べています。オントロジーエージェントを使って自然言語でオントロジーを作る方法は、画面では示されず、口頭で紹介されました。

## 7. 注意点・発表者の気付き

- オントロジーは**パブリックプレビュー**です。
- 多くの組織が犯す最大の間違いは、組織全体のオントロジーを一度にモデル化しようとすることです。システム 2 つにまたがる業務上の問い 1 つから始めます。
- エンティティは、データベースのテーブルと同じように考えないでください。実際のビジネス上の対象として捉え、データをそこに持ち込みます。
- 有効なクエリで正しいデータが返っても、意味を持たないエージェントは業務の質問に誤って答えることがあり、エージェントごとに答えが食い違うおそれがあります。
- 4th Coffee は説明用のシナリオです。デモは最後に表示が戻らなくなる場面がありました。
- 料金、必要なライセンス、一般提供の時期は、発表では触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 業務の用語、同義語、システム間のエンティティの対応、ビジネスルールを 1 か所に定義でき、エージェントが業務の言葉で質問に答えられる。
- 同じオントロジーを、Copilot Studio のエージェント、M365 Copilot、MCP に対応する任意のクライアント（GitHub Copilot を含む）、データエージェントから使える。
- 複数のエージェントが同じ意味の定義を参照するため、解釈の食い違いを抑えられる。
- キャンバスでの構築のほか、自然言語でオントロジーを記述できる。
- リアルタイムのデータ（機械のテレメトリなど）もオントロジーにバインドして問い合わせられる。

発表では、導入企業の事例や、効果を示す数値は紹介されていません。

## 9. まとめ

データを OneLake に統合しても、エージェントにはテーブル、列、行しか見えず、意味が伝わりません。同じ対象の呼び名の違い、言葉の意味の違い、頭の中にある業務ルールが、エージェントの答えを誤らせます。発表者は、Fabric IQ の最上位の層であるオントロジーに、エンティティ型、関係、データバインディング、ビジネスルールを定義することで、業務の言葉を AI エージェントに伝える方法を示しました。

オントロジーは、Copilot Studio と M365 Copilot、MCP クライアント、データエージェントから使えます。現在はパブリックプレビューです。始めるなら、2 つのシステムにまたがる業務上の問いを 1 つ選び、自然言語やキャンバスでモデル化するのが発表者の勧めです。
