## 5. 発表内容の詳細

### 5.1 Azure DocumentDB とは

発表者の説明によると、これまで MongoDB 互換のマネージドサービスは何度か世代交代があり、数年前に現在のサービスを開始しました。以前は「vCore ベースの Azure Cosmos DB for MongoDB」という名称で、昨年のちょうどこの時期に、独立したサービス「Azure DocumentDB」になりました。

特徴として次の点が挙げられました。

- 互換性：これまでの NoSQL サービスの中で最も MongoDB 互換性が高く、MongoDB の代わりに差し替えて使える。見えない部分があるとすれば、Microsoft が代わりに管理している部分だけ。
- Azure のネイティブなサービス：サードパーティ製品ではなく、別途ライセンスを買う必要がない。セキュリティ、耐障害性、暗号化など Azure のエコシステムと統合され、災害対策、地理レプリケーション、ローカルレプリケーションもマネージドで提供される。
- ベクトル検索の統合：別のデータベースを用意せずにベクトル検索を使える。既に稼働中のクラスターでも、移行なしで利用できる。
- コスト：同じ SKU で比べて 40% 安い。TCO（総保有コスト）で見ると、平均で少なくとも半分、67〜70% の削減に達する例もある。
- 性能：少なくとも同等。1 ドルあたりのトランザクション数は 2 倍以上で、通常の OLTP だけでなく、統合ベクトル検索にも当てはまる。
- オープンソース：マネージドサービスを動かすエンジンは MIT ライセンスのオープンソース。フォークでき、オンプレミスなど任意の場所で動かせ、制限はない。

提供リージョンについては、データベースを置きたい Azure リージョンのすべてで利用できると説明されました。

### 5.2 製品の歩み

| 時期 | 出来事 |
|---|---|
| 4 年強前 | MongoDB に興味はあるが、サービスの違いを学ぶ負担が大きいという顧客の声から、機械とディスクだけを意識すればよい vCore ベースのサービスを構想 |
| 2023 年後半（Ignite 2023） | 一般提供（GA）開始。当初は小さな範囲の用途 |
| 翌年末まで | Azure のネイティブ統合を一通り完成 |
| 2025 年 | ベクトルデータベース機能を統合。Microsoft Research 発で Microsoft 独自の DiskNN を含む（音声認識の都合で表記が確定できません） |
| 2025 年末 | MongoDB Atlas、IaaS 上の MongoDB、他社クラウド上の MongoDB などからの移行手法を確立 |
| 現在 | MongoDB 以外にも対象を拡大 |

現在は、新規（グリーンフィールド）開発で広く使われる API を求める場合や、Cassandra、Couchbase、リレーショナルデータベースからの移行にも向く、と説明しています。これらの移行手法も過去 1 年で固めたそうです。

### 5.3 事例 1：AB and Bev

**会社の概要。** 世界最大の醸造会社で、本社はベルギー、従業員は約 14 万人、少なくとも 40 か国で事業を展開しています（社名の綴りは音声認識どおりで、確定できません）。飲料の小売でもあり、国や時期によってトラフィックの急増があります。発表では、直近のワールドカップ、これから来る感謝祭やクリスマスが例に挙がりました。

**移行の動機。** 次の 3 点です。

- Azure に統一したい
- 現状より安くしたい
- 地理レプリケーション構成で、急激なスパイクにも耐えたい

**規模。** 数百クラスター（後半では 500 以上と言及）で、重要な事業領域が含まれるため、コスト削減だけでなく耐障害性と性能の確かな置き換えが必要でした。クラスターのサイズは大きく異なり、20 テラバイト、50 テラバイト、100 テラバイトに迫るものまであります。20 テラバイトは、本番環境ではおそらく最も小さい部類だったと発表者は話しています。一方、小さな開発・テスト用クラスターも多数ありました。

**この事例から製品側が磨いた点。**

1. **並列移行と負荷の制御。** 数百クラスターは 1 つずつ移せません。ただし、ジョブを単純に増やすと、本番稼働中の移行元に負荷をかけてしまいます。移行先でも、元の 10 倍の性能をプロビジョニングして急いで移せば、コストが 10 倍になります。そのため、速さと負荷・コストのバランスをとる設計にしました。
2. **カスタムスキーマ移行。** DocumentDB は独自のデータベースエンジンの上に MongoDB のインターフェースを載せています。そのため、得意な部分を活かせるよう、スキーマを調整する移行ツールを用意しました。ユーザーが細かく知らなくても、ツールが最適な経路を示します。
3. **コレクションの配置。** MongoDB では通常シャーディングしますが、DocumentDB では不要です。ただし巨大なクラスターでは、クエリパターンを分析して「このコレクションはノード 1、あのコレクションはノード 2」のように最適な配置を管理します。
4. **構成のガイダンス。** 内部実装が違うため、移行元と同じ規模を用意する必要がない場合があります。ストレージ中心か計算中心かというワークロードの傾向に基づいて推奨を示します。移行元が過剰にプロビジョニングされていても、移行先を同じにしない方針です。
5. **VS Code 拡張機能。** 従来の移行ツールは、リポジトリをクローンし、頻繁な更新に追従する形でした。AB and Bev のように複数の事業部門のチームが関わると、チームごとにバージョンも体験も異なり、拡張できません。そこで開発者が普段使う VS Code にツールを持ち込みました。
6. **スパイク時の考え方。** 業務が 20 倍に急増したとき、移行も 20 倍の速度にすべきかという問いに、否と結論しました。その間は移行が遅くなっても、5 分、15 分で追いつくという考えです。
7. **サイズの幅への対応。** 20 テラバイトで破綻せず、小さなクラスターで速すぎもしない共通の解決策が必要でした。
8. **長期間の移行。** 本番クラスターでは、移行を 4 か月間動かし続けました。本番を DocumentDB に移したあとも、元の MongoDB クラスターを消すまでは二重書き込みで同期を続け、問題が出たときの戻り先を確保するためです。発表者は、必要なら 1 年でも続けられたと述べています。
9. **可視化とテレメトリ。** 100 テラバイトの本番移行を 4 か月続けるなら、失敗の有無、自動リトライの状況、調整やスケールアップの要否を把握できなければなりません。この点も AB and Bev から学んだとのことです。

### 5.4 事例 2：Abercrombie and Fitch（Hunter 氏）

Hunter 氏は Abercrombie and Fitch のソフトウェア開発者で、所属は Digital Product Hub チームです。同社はファッション小売で、商品属性や販売チャネルなど多くの取引先（ベンダー）に、商品情報と在庫リストのフィードを提供しています。ベンダーごとに要望が異なり、項目に接頭辞を付けたい先、在庫のある商品だけを求める先などがあります。更新頻度も毎時から日次までさまざまです。

チームの役割は、在庫・商品・価格といった社内の各システムからデータを集め、保存できる形に正規化し、ベンダー向けのフィードを作ることです。毎時や 20 分ごとのジョブが 900 件あり、増え続けています（取引先の数ではありません）。データベースへの負荷は高く、フィードを 1 週間ほどで切り替える必要もあります。

**移行前の課題。** 移行前は Azure 上の、RU（リクエストユニット）ベースの課金モデルのサービスを使っていました（発話では「RU ベースのサブスクリプションモデルの vCore Cosmos DB」という言い方で、正確な製品名は確認できません）。Hunter 氏は良い製品としたうえで、自分たちのニーズには合わなかったと述べています。データベース評価の 3 つの柱で整理しました。

- データサイズと複雑さ：多くのシステムからのデータで増加中だが、データレイクなどと比べれば小さく、複雑でもない。
- コスト：フィードを増やすたびに RU が積み上がる。フィードを毎時の頃に集中して動かし、鮮度が切れる前に配信を終える必要があるため、ピークを分散できない。その結果、高い RU/秒の階層を払い、残りの時間は使わない RU の分まで払っていた。
- 性能：高い階層でも RU/秒の上限でスロットリングされ、上限を超えるとエラーになってリトライが発生。失敗したフィードと無駄な作業が増え、フィードの追加とともに滞留も増えた。

インデックスにも課題がありました。RU ベースの環境の複合インデックスは、フィルターよりも並べ替えの高速化を重視した作りでした。同社は並べ替えの順序を気にせず、リストを返せればよいので、フィルターに効くインデックスが必要でした。

**選定。** MongoDB の自前ホスティングも含めてほぼすべてを調べ、Azure 環境にとどまる DocumentDB を選びました。理由は次のとおりです。

1. 予測できるコスト：CPU・メモリ・ストレージに課金される従来型で、同じ階層なら毎月同額。週末に 3 倍使われて月曜に原因を調べる、といったことがなくなり、予算見通しが安定した。
2. ピークと谷への適合：RU/秒のような上限がない。上限は CPU に分散され、CPU が高まるとレスポンスが遅くなる程度で、すぐにエラーやスロットリングにはならない。
3. インデックス：複合インデックスがフィルターに向いている。間に GraphQL 層があり、必要なフィルターを作れた。
4. 階層の切り替え：コンピュート階層を簡単に上げ下げできる。翌週の Black Friday のように、小売では重要な週に備えて拡張できる。

**移行の流れ。** すでに Azure 環境にいたため、RU ベースのサービスの画面に「DocumentDB に移行」というボタンがありました。いくつかの質問に答えて数クリックで開始します。移行は、全データのコピーのあと、移行元から移行先へのチェンジストリームを設定する形でした。

1. 金曜に開始し、監視をしながら週末を過ごす
2. 月曜に、全データの転送完了と、その間の変更の反映を確認
3. 月曜朝にカットオーバー。まず読み取り専用のテストとして、アプリケーション 1 つで接続を確認
4. 読み取り専用のアプリケーション全体を切り替え。変更は接続先の差し替えと、バックエンドの縮小・再起動だけ
5. 次に、データの重要度が比較的低い書き込みアプリケーションを切り替え
6. 最後に、コンシューマー側を向け替え。ここが後戻りできない点

結果として、アプリケーションコードの変更はなく、ダウンタイムもアプリケーションの再起動程度でした。緊急で急ぐ必要もなく、自分たちのタイミングで切り替えられたそうです。

**得られた成果。**

| 観点 | 結果 |
|---|---|
| データ | 以前と同程度（フィードやカタログは増えたが、急増はなし） |
| コスト | QA と本番を合わせた年間コストを約 75% 削減 |
| 性能 | 目標は「旧環境の 90% の性能なら成功」としていたが、フィードの開始から完了までの時間は 20% 短縮 |
| エラー | RU/秒のスロットリングによる数千件のエラーがほぼゼロに。エラーが出ても原因を特定して調べられる |

同じワークロードで、性能は上がり、価格は大きく下がったとまとめています。

### 5.5 2 社の事例から得た学び

発表者は、2 社の動機と学びの違いを次のように整理しました。

- AB and Bev（500 以上のクラスター）からの学びは、ほぼ全面的に移行ツールの作り方に関するもの。
- Abercrombie and Fitch からの学びは、同じ MongoDB 互換のマネージドサービスから最新のサービスへ、どう移すか。ポータルに「Azure DocumentDB に移行」ボタンを追加し、ワイルドカードインデックスの扱いも改善した。
- スケールの単純さ：RU モデルは優れているが、何 RU まで上げ下げするかを見積もる必要がある。DocumentDB なら 8 コアのマシンから 16 コアへ変えるだけで済み、不要になれば戻せる。

### 5.6 当日発表の 5 つの新機能

エンタープライズ向けの話（14 万人の従業員の顧客）から始まり、開発者向けの VS Code 拡張機能を経て、次はデータベースをエージェントに適したものにする、という流れで紹介されました。エージェントは待つことを嫌い、素早く試行錯誤します。また、16、32、64、96 コアのような大きなマシンではなく、機能検証のための小さなマシンを作るというのが、発表者の見方です。

1. **ほぼ即時のクラスター作成。** 2 コア未満のマシンが対象で、約 1 分で稼働します。従来は 10〜15 分かかっていました。一部はその場でプロビジョニングが必要です。
2. **統合された検索。** OLTP、全文検索、ベクトル検索が 1 つのクラスターに入ります。別のベクトルデータベースや Lucene ベースの検索エンジン、Elastic を重ねる必要はなく、追加の計算リソースもかかりません。
3. **VS Code の移行拡張機能。** 移行体験を VS Code に統合したものです。リソースをローカルマシンで動かす必要はなく、裏側でプロビジョニングされ、操作画面だけが VS Code にあります。
4. **きめ細かい RBAC（ロールベースのアクセス制御）。** これまでは管理者と読み取り専用ユーザーというクラスター単位でした。今回、データベース単位とコレクション単位の権限が使えるようになりました。次の段階として、エージェント向けの RBAC との統合を予定しています（今後の計画で、現時点では提供済みではありません）。
5. **分散コーディネーター。** 従来は単一のコーディネーターノードが入口となり、クエリを各ノードに振り分けていました。今回、マルチノードクラスターのどのノードでも要求を受け付ける構成になりました（発話では「分散コーディネーターの概念を持つようになった」という言い方です）。受けたノードが全体の構成を把握し、要求やサブ要求の送り先（複数ノードの場合も）を決め、結果を集約して 1 つの応答として返します。発表者はこれを「エンタープライズ向けの話」と位置づけています。AB and Bev のようにノード数の多いクラスターから着想した機能です。

## 6. デモ・手順

デモは VS Code の移行拡張機能を紹介する形で行われました。「画面で見せる」旨の発話があり、画面の様子を解説しながら進めています。なお、トランスクリプトは音声のみのため、画面の細部は確認できません。デモでは数分かかった処理を結果まで示しており、発話にある「デモ目的で、最大のコレクションではない」という言及から、小さな例を使ったことが分かります。語られた順の手順は次のとおりです。

1. VS Code に移行拡張機能をインストールする（インストールできる、という説明）。画面左側に、既存の MongoDB 接続（他社クラウド上、オンプレミスなど）が並ぶ。
2. この例は、MongoDB の VM から Azure DocumentDB への移行。移行ソリューションとして DocumentDB への移行を選ぶ。
3. 移行ジョブを作成する。ジョブは手元のマシンではなく、Azure のリソース上にプロビジョニングされる。
4. オンライン移行を選び、移行元クラスターはパブリック接続できる設定にして、同期を選ぶ。ウィザード形式で IDE 内から操作できる。
5. クラスターを選び、移行ジョブに名前を付ける。名前は DMS（Data Migration Service。データ移行サービス）に付けるもの。ワンクリックで移行サービスを作成する。
6. 作成後、現在のトポロジー（構成）が表示される。すべてを移す必要はなく、不要な古い資産を除いて選択的に移せる。
7. カスタムスキーマ移行の機能で、シャーディングを同じにするか、しないかを選ぶ。この例では「シャーディングしない」を選択。DocumentDB ではその方が良い体験になるという説明。
8. 移行を開始する。
9. 進捗を確認する。移動しているか、進んでいるか、止まっているか、再起動したか、再起動が必要かといった状態を見られる。AB and Bev の 4 か月の移行で必要性が分かった可視化に当たる。
10. この例では数分で完了し、移行元から移行先へのカットオーバーが可能な状態になった。

全体を通して、操作は手元の VS Code から開始し、処理は Azure 上で動きます。クラスターのサイズ、データサイズ、ノード構成に関わらず、移行が簡単になるという説明です。

## 7. 注意点・発表者の気付き

- **ワイルドカードインデックスの扱い。** Abercrombie and Fitch では、RU ベース環境で、あまり管理していない小さなテーブルにワイルドカードインデックスを使っていました。移行後はそれが効かず、インデックスを使わないアクセスで CPU が上昇しました。結局、対象を絞ったインデックスを追加して解消しています。Hunter 氏は、現在はワイルドカードインデックスが再び使えると思う、と述べています。
- **本番移行は長く並行運用する。** AB and Bev は、本番クラスターで 4 か月間、二重書き込みで移行を維持しました。すぐにカットオーバーして元を消す進め方は現実的ではなく、戻り先を確保しておく必要があると説明されています。
- **並列化には限度がある。** 移行元・移行先の双方で負荷とコストを考慮しなければならず、ジョブを増やせばよいわけではありません。
- **カットオーバーの順序。** Abercrombie and Fitch は、読み取り専用のテスト、読み取りアプリケーション、重要度の低い書き込みアプリケーション、最後にコンシューマーの順に切り替えました。最後の段階が後戻りできない点でした。
- **今後の計画と提供済みの区別。** エージェント向け RBAC は次の統合予定であり、発表時点で提供済みとは語られていません。

## 8. 利用者にとっての利点

- コスト：同じ SKU で 40% 安く、TCO では平均で少なくとも半分、最大で 67〜70% の削減。Abercrombie and Fitch では QA と本番の年間コストで約 75% 削減。
- 性能：1 ドルあたりのトランザクション数が 2 倍以上。Abercrombie and Fitch ではフィード処理の所要時間が 20% 短縮し、スロットリングによる数千件のエラーがほぼゼロになった。
- 予測しやすさ：CPU・メモリ・ストレージの課金で毎月同額。階層の上げ下げで拡張できる。
- 移行の容易さ：Abercrombie and Fitch はアプリケーションコードの変更なし、ダウンタイムはアプリケーションの再起動程度。47 テラバイトの事例は 48 時間未満で完了。
- 統合：ベクトル検索、全文検索、OLTP を 1 つのクラスターで利用でき、別製品を追加する必要がない。
- オープン性：エンジンが MIT ライセンスのオープンソースで、任意の場所で動かせる。

## 9. まとめ

Azure DocumentDB は、MongoDB 互換の Azure ネイティブなマネージドサービスで、同じ SKU で 40% 安く、性能は同等以上です。AB and Bev の数百クラスター・最大 100 テラバイト規模の移行は、並列移行、スキーマ移行、コレクション配置、構成ガイダンス、VS Code 拡張、長期の二重書き込み、可視化といった移行ツールの進化につながりました。Abercrombie and Fitch は、ほぼ 1 人で、コードを変えずに移行し、年間コスト約 75% 削減、処理時間 20% 短縮を得ています。当日は、ほぼ即時のクラスター作成、統合検索、VS Code 移行拡張機能、データベース・コレクション単位の RBAC、分散コーディネーターの 5 つの機能が発表されました。
