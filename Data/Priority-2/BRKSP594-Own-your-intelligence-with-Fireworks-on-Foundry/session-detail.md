# BRKSP594 Own your intelligence with Fireworks on Foundry

## 1. はじめに

このセッションは、Fireworks の Rob Ferguson 氏と PayPal の Srini Manoharan 氏が、「モデルを 1 つに決めて次の新モデルを待つ」状態から抜け出し、自社の仕事に合わせてモデルを使い分け、必要なら自社専用のモデルを持つ方法を話す発表です。Fireworks on Foundry（Microsoft Foundry 上で Fireworks の推論や学習を使う構成）を前提にしています。

## 5. 発表内容の詳細

### 5.1 モデル依存とベンチマークの限界

Rob 氏は、AI の現状を表す「誰もが見慣れたグラフ」を出して、各チームが次のモデルがすべてを解決してくれるのを期待していると話しました。そして一般的なベンチマークのグラフは、高価なモデルほどタスクを成功させる確率が高いことを示しています。しかしベンチマークは**他人の試験**にすぎず、たとえば古いフランス語に強いことが、コーディング事業にとって意味があるかは別の問題だという例えが使われました。

もう 1 つの論点は、モデルがあるところで自社の品質要件を満たしたなら、それ以上の部分は知能のコストを払いすぎている、という点です。そのため、1 タスクあたりのコストを把握し、自社の仕事に近い測り方で必要な知能の水準を理解することが重要だとされています。

### 5.2 Specialized Intelligence Index とモデルのポートフォリオ

Rob 氏は「Fable や Astra が素晴らしいモデルだと聞いたかもしれないが、常にポートフォリオから選ぶ方が良い」と述べています（両モデル名は音声認識の都合で表記が確定できません）。そのうえで、Fireworks は多くの顧客に対して同様の試験を行い、Specialized Intelligence Index（SII）と呼ぶものを作りました。さまざまな分野の企業と協力し、法務、医療の分類や書き起こし、共同作業型の補助といった実際の業務負荷でモデルの性能を測るものです。

発表で示された数値は次のとおりです。

- 5 つの SII ベンチマークにまたがる 479 のタスクについて、「仕事を終えられる最も安いモデルはどれか」を問うた。35 のモデルがそれぞれどこかのタスクで勝ったが、タスクの半分をこなせるモデルは 1 つもなかった。全体を合わせると、SII ベンチマークの 78% を達成できた（音声が途切れており、数字の対象は文脈からの読み取りです）
- Pharos AI などのデータサイエンス企業や、Fireworks を初めて評価する企業と取り組んだ結果でも、コスト面でも最難関のタスクの面でも、単一モデルよりポートフォリオを選ぶ方が常に良かった

モデルごとに得意分野が異なり、選ぶツールや結果の確かめ方といった振る舞いも違うため、タスクの性質に応じてルーティングすると完了率が上がる、という説明です。「モデルはテストを実行できることを知っているが、実際に実行するかは別問題」という例が挙がりました。

**コーディング課題での比較**：公開テスト「DeepSuite」（音声認識の都合で表記が確定できません）の 113 件のエージェント型コーディング課題を、18 のモデルで評価しました。

| 条件 | 課題の完了率 | 備考 |
| --- | --- | --- |
| 最良の単一モデル | 74% | コストは約 6.5 ドル |
| 上位 3 モデルを組み合わせ | 91% | — |
| 18 モデルをオラクルルーティング | 97.6% | すべての組み合わせを網羅的に試した理論上の最大値。コストはすべての中で最安 |

Rob 氏は、これは理論ではなく、過去の実行を遡って再計算し、ポートフォリオを広げた場合の実際のコストと効果を確認できる、と説明しています。モデルの個性として、「Kimmy（音声認識の都合で表記が確定できません）は JavaScript が得意だが Python はそれほどでもない」という経験談も語られました。ただしモデルの印象だけに頼らず、組織の仕事の中で知能がどう使われているかを測定し、テストと構築で繰り返し改善すべきだというのが主張です。

新しいモデルは翌日にも出ます。「次のモデルを待てばよいのでは」という質問に対し、待つことはできるが、そうすると自分の知能も他者と同じ速度でしか良くならず、ほぼ確実に払いすぎになる、というのが Rob 氏の答えです。

### 5.3 Fireworks Nexus

Nexus は、既存のワークロードに知能を組み込むためのものと説明されました。

- Claude 系や GPT 系を使っているワークロードでも、Fireworks の API は API 互換で、クローズドモデルとオープンモデルのどちらも選べる
- 使い慣れた IDE やハーネス（エージェントの実行環境）にそのまま組み込める。例として Claude Code（発話では Cloud Code と聞こえる）に、ボタン 1 つで組み込めると述べている
- タスクの難易度を理解するカスタム学習済みモデルが、クローズドの最良モデルとオープンの最良モデルのどちらが適切かを判断して選ぶ

既存アプリでそのまま動くため、有効にするだけで使えます。**平均的な顧客は、クローズドモデルへのルーティングを続けるだけでも、ポートフォリオの自動拡張で即座に 40% を節約した**と述べています。さらにオープンなモデルの利用や学習へ進んだ組織は、それを桁違いに上回る成果を得ているそうです。

ルーターは Fireworks 内で学習したもので、「タスク対応」型です。Fireworks の従業員が協力した多数のトレース（コーディングが中心）を元に、タスク全体のコストを考慮しています。ホスト型の推論なので、キャッシュされた結果を使う可能性を高められる点も挙げられました。エージェント型のタスクの多くは、AI がタスクの状況を把握し直す作業であり、同じ文書を 100 回要約する必要はなく、同じ情報を再利用できるという説明です。

Nexus については、**1 つのモデルより多くのタスクを 1 ドル未満で解ける**ことが示せた、と述べられています。バランス型から、クローズドの最良モデル寄りまで知能の配分を調整でき、トレードオフを意識せずに済むようにしています。オープンなモデルを使ったことがない人は 1 つのモデルファミリーしか使っていないことが多いため、最初のトレードオフを理解しやすくすることを狙っています。

### 5.4 PayPal の事例（Srini Manoharan）

Srini 氏は PayPal の AI プラットフォームのディレクターと名乗りました。PayPal は予測型と生成型の AI のユースケースを、オンプレミスとクラウドで動く自社の推論基盤でセルフホストしています。クローズドモデルやフロンティアモデルは、ファーストパーティのモデル提供元やサードパーティのクラウド経由で使っています。

**セルフホストの課題**：オープンモデルがコーディングタスクで良くなってきたため、まず自社の LLM 推論基盤でホストしました。そこで次の課題に直面しています。

1. 各オープンモデルに対するコーディング需要を予測できない
2. GPU が不足している状況で、需要が分からないまま GPU を確保するのは難しい
3. モデルの公開が頻繁で、推論チームがチューニングや最適化に付きっきりになる一方、モデルの寿命が短く、すぐ次の版が出る

**Fireworks on Foundry を選んだ理由**：従量課金で利用の事前確約が不要であること、GPU 調達の問題がないこと、新モデルが Fireworks で早く使えること、そして Foundry へ直接統合され、エンタープライズのガードレールと連携できることです。

**公開ベンチマークだけでは足りない理由**：1 つのユースケースには多数のタスクがあり、コーディングも実装、設計、テスト、レビューなどに分かれます。公開ベンチマークからはモデルの能力と性能は分かりますが、社内の開発者のタスクの分布や、同じ精度で安く実行できるモデルは分かりません。公開ベンチマークは公開タスクで構成され、どの会社でも同じ、標準的な設定で、答えがベンチマークの正解と合うかを見て、順位表の位置に至る、という説明でした。一方、自社のユースケースには実際の顧客リクエスト、自社のツール、コンテキスト、テスト基準があり、モデルが状況を理解し、正しい行動を取り、仕事を完遂したかが分かります。その結果として、タスクごとにコスト最適化されたモデルが得られます。

**自社ベンチマークの作り方（タスク分類）**：

1. LLM ゲートウェイからすべてのセッションをログとして記録し、実際のセッションをタスクにする
2. Clio（Claude insights and observations）という手法を使い、Claude にトピック、言語、対話の特徴でタスクをクラスタリングさせ、名前と説明も付けさせる
3. それらを階層的な分類にする。PayPal のコーディングタスクの例として、コードのリファクタリング、可観測性、ドキュメント作成が挙がった

**ベンチマークのパイプライン（左から右）**：

1. コーディングのセッションを取得する
2. セッションを絞り込み、Jira のチケットとマージされた PR に結び付ける。依頼された作業と受け入れられた成果が対応付く
3. タスクに必要な情報を残し、無関係な情報を除く。そのタスクで追加されたテストも加える
4. 実行環境を作る。環境を作成し、依存関係をインストールし、サービスとデータベース呼び出しをモックにして、オフラインで動くコンテナイメージにする
5. テスト環境を作る。テストケースを集め、PR が結び付くチケットと整合しているか確認し、挙動の評価基準（ルーブリック）を追加し、テストが再現して検証できるか確認する

この仕組みがあれば、新しいモデルが出たときや、タスクの分類が変わったときにいつでも再実行できます。コスト、体験、精度の 3 つの軸の最適化問題を解き、コスト効率の良いモデルが得られます。

### 5.5 「測れるものは改善できる」

Rob 氏は、PayPal の例が、巨大な組織でもワークロードの多様さに圧倒されず、まず観察することから始められることを示している、と述べました。AI が知らないのは、自社のデータ、ユーザー、ワークロード、基準です。

例として動画圧縮の分野が出ました。長年多くの博士が取り組み、改善の余地はないと考えられていましたが、強化学習で参照画像に照らして測定することで、さらに 6% の圧縮が見つかったそうです。かつては最高水準の AI ラボだけができたことを、今は一般の組織が規模をもって行えます。

### 5.6 自社専用モデルの学習

GPT-3 の学習コストだけで 2,500 万ドルと推定されているとして、多くの人は自社の知能を作るコストは手が届かないと考えています。しかしそれは、必要以上の情報を含んだ見積もりだ、というのが Rob 氏の見方です。

**Fireworks のサーバーレス学習**：GPU を時間単位で借りるのではなく、トークン単位で学習できます。Rob 氏は、このあと見せる例のモデルを **29 ドル**で学習しました。

**振る舞いを学習する**：事前学習で、モデルは家の建て方や議会の情報など、多くの知識を得ています。しかし、利用者が期待する仕事の仕方は身についていません。ツールの存在は知っていても、完了までツールを動かして結果を検証する方法は知らない、という例えです。有名な Hugging Face の件は、同じモデルを「粘り強く、決してあきらめない」ように学習させた例だと触れられています（詳細は発話では語られていません）。モデルが何を知っているかだけでなく、どう振る舞うかに目を向けるべきだという考えです。

**学習を検討する目安**：コア製品機能の品質、コスト、速度に課題があるワークロードがあるなら、学習を検討する良い理由になります。そうでなければ、まずモデルのルーティングから始めるのが最良の入口です。

**ワークショップの例（スキルのモデル重み化）**：Rob 氏は、人気のあるスキルを使って、Fireworks でダウンロードできるワークショップを作りました。これは任意のスキルをモデルの重みに変えるもので、ベースモデルに GLM（音声では「GLM 53 Flash」と聞こえる。表記は音声認識の都合で確定できません）を使い、その上に小さなアダプターを学習して振る舞いを変えます。

スライドでは、ベースモデルと、taste（センス）スキルで学習したアダプターが同じプロンプトと設定で作ったウェブページを比べました。画面は音声からは確認できず、説明された範囲は次のとおりです。

- ガラスの家のページ：ベースは全部が狭い領域に詰め込まれている。アダプターは余白や使いやすさ（アフォーダンス）が増え、ページ全幅を使って画像全体を見せる
- 営業時間と料金のページ：ベースは小さな名前と薄い営業時間の帯、非常に密な時刻表で始まる。アダプターは緑の地に大きな見出しを置き、その下に営業時間と料金を置く
- 表を含むページ：アダプターは表をページの全幅で表示する
- 印刷所のお知らせ：写真はなく、書体、余白、色の使い方で見せる。ベースは小さなラベルの短い中央寄せの告知。アダプターは大きな文言（ステートメント）
- モバイルファースト（スマートフォン優先）の設計で、より反応性の高いウェブ環境を想定している

Rob 氏は、この例ではコードの書き方を教えたわけではないと述べています。お気に入りのスキルをモデルの重みとしてアダプターに変えるのが、学習を始めるうえでもっとも簡単な方法だということです。cowboy や ponytail といった人気スキル（音声認識の都合で表記が確定できません）でも同様に試したと話しました。taste アダプターには、最も反応性の高いウェブサイトと見なせる例となる 250 以上のウェブページが参照画像として使われています。

**Fireworks の学習の仕組み**：自分たちのコードがデータと学習ループを持ち、Fireworks はリモートで計算を実行します。バッチと報酬を作り、パラメータ更新、チェックポイント、チェックポイントからの評価サンプルを依頼し、候補をリリースゲートに通すまで進めます。管理するのは自分のデータだけで、共有プール上で多数のテストを手元のマシンから実行して山登り（改善の反復）ができ、GPU 時間ではなくトークンで最初の専門知能を作れる、という説明です。

**アダプターとフルパラメータ**：低ランクアダプターだけでなく、フルパラメータのファインチューニングも提供しています。Fireworks で人気の Ember モデル（表記は音声認識の都合で確定できません）は、最初はアダプター（ごく小さな重みの集合）で、あとからフルパラメータのモデルにしたものだそうです。違いは、フルパラメータなら細部まで自由にカスタマイズでき性能も上がり、アダプターなら複数の重みを動的に切り替える柔軟性がある、という点です。

**スキルをプロンプトに書けば済むのでは**：Rob 氏自身が出した疑問です。回答は、スキルは確かにプロンプトにも入れられるが、継続して改善したい場合、組織全体で共有されているか、少しずつ調整できるかが問題になります。モデルのリリースごとにプロンプトを調整し直すのが負担なので、重みにしておけば、改善を多様なモデルに対して続けられ、新しいモデルが出ても手持ちの例のデータから再び始められます。

### 5.7 学習の判断基準：知識か、やり方か

Rob 氏は、モデルの学習を始めるときの隙間を「何を知っているか」と「やり方を知っているか」の違いとして整理しました。

- **情報の取得は、依然として最先端の方法**です。語が「意味のある働き」をする場合を除き、事実は取得して使う方が、最新状態を保て、相手側で何が起きているかも把握できます
- 語が働く例は医療で、毎年新しく出る薬剤名を使って表を並べ替えたり SQL で問い合わせたりする場合です。語が辞書的な働きをするなら、その語で学習するとモデルが 1 回でうまくこなす確率が上がります
- 不足しているのが情報なら取得、語が働くなら学習、ツールを一緒に動かすならエージェントがツールにアクセスできているか、同じ間違いを繰り返していないか、といった問いを立てます

**システム全体で見る**：Fireworks の調査では、モデルが動くハーネスを替えると性能に大きく影響しました。Cursor のチームが示したように、ハーネスと一緒にモデルを学習して結果を高めることもできます。Rob 氏は「Claude がやった」「Opus がやった」というものは存在せず、**AI システムがやった**のだと述べました。LLM が使えるツールを変えれば結果が変わり、システム全体の性能を測り始めると、キャッシュやサブエージェントの有無といった影響も出てきます。そのため、モデルだけでなくシステムを理解する必要があります。

**最初に専門化する価値があるもの**：

- **繰り返される仕事**。ゲートウェイで人々の作業を観察すれば分かる。たとえば仕事がすべてコードなら、コード向けに蒸留したモデルにできないか。ツールを動かすのにバロック期のフランス語を知っている必要はなく、使われない重みにコストを払っていることになる。多くの顧客が自分のタスクで蒸留しており、それだけで速く安くなり、できることも増える
- **明確な成果がある仕事**。ツールの使い方や測るべきものが分かっていれば、曖昧な状態から、いつでも測って改善できる状態に移れる
- **繰り返し起きる失敗**。何をしたいかだけでなく、何がうまくいっていないかを知ることで、より良い問いを立てて AI システムを作れる

**進め方**：強いベースラインから始めます。直接のプロンプトを試し、適切なコンテキストを与え、ツールが動くようにします。それでも失敗する部分を調べ、残った差が学習がポートフォリオに入る理由になります。**プロンプトで十分なら変えずにルーティングする**、とも述べました。AI でうまくいくチームは、複数のモデルを選べる柔軟性を持った時点で、システムを改善し続けられるほど理解できている、という観察です。

**シグナルの扱い**：トレースはモデルが何をしたかを示し、プロダクトのシグナル（編集、再試行、受け入れられた作業、顧客の成果）はその後に何が起きたかを示します。シグナルを該当するトレースの部分に対応づけ、意味を検証します。再試行は答えが間違いだったとは限らず、「高評価」もすべての事実を保証しません。だから強い候補となるシグナルが必要で、最終的にはそのシグナルが手法を決めます。SFT、DPO、RL のどれを選ぶかという質問に対しては、手持ちのデータに応じてそれらの組み合わせになることが多い、という回答でした。

### 5.8 Foundry への持ち込みと提供状況

- Foundry では Multi-LoRA を**プレビュー**で提供しており、利用したい顧客は Fireworks のチームへ連絡する
- Fireworks の性能（Fireworks performance）は Microsoft のファーストパーティとして直接組み込まれており、**Microsoft の請求書に表示される**。既存の Azure ワークフローで使え、エンタープライズ級のガバナンスとセキュリティ、どのシステムが AI にアクセスするかの把握も得られる
- すでに Foundry 上でカスタム重みを使っている企業がある
- 概算（Rob 氏自身が「封筒の裏の計算」と述べている）では、**月 15,000 ドルの推論を使っている顧客は、すべて少なくとも 1 つのカスタムモデルを持つ方が得**だった。その金額で学習して実行できるためで、ほぼ全員が利益を得られる。実際にはそれよりはるかに多く支出している組織が多く、AI の予算を年初の第 1 四半期で使い切った組織もある、とも話しました

**カスタムモデルの持ち込みは 5 ステップ**です。

1. ファイルを準備する
2. Foundry にモデルを登録する
3. アップロードする
4. デプロイする
5. プレイグラウンドでテストする

この持ち込みのサービスはすでに一般提供（GA）されています。アダプターをさらに追加したい場合は、チームに連絡するよう案内されました。

## 7. 注意点・発表者の気付き

- **単一モデルに依存しない**：新モデルを待つだけでは、他者と同じ速度でしか良くならず、価格も他社に決められる
- **ベンチマークは他人の試験**：公開ベンチマークは自社のタスク分布も、コスト効率の良いモデルも教えてくれない
- **再試行や高評価は正誤の証明にならない**：シグナルは、トレースと対応付けて意味を確認する必要がある
- **システム全体を見る**：ハーネスやツールを替えると性能が変わる。モデル単体でなく AI システムとして測る
- **まずルーティング**：学習は最初からではなく、強いベースライン（プロンプト、コンテキスト、動作するツール）を試して、それでも残る差を埋めるために行う
- **事実は取得、振る舞いは学習**：新鮮さが要る事実は取得で扱い、語が働く領域や、やり方（振る舞い）を学習の対象にする
- **学習コストの思い込み**：自社の知能を作る費用は手が届かないという通念に対し、トークン単位の学習で 29 ドルの例を示している（この金額は特定の 1 例であり、一般的な費用の保証ではありません）
- **サービスの提供状況**：カスタムモデルの Foundry への持ち込みは GA。Multi-LoRA は Foundry でプレビュー

## 8. 利用者にとっての利点

- **コスト削減**：平均的な顧客は、クローズドモデルへのルーティングを続けるだけでも、ポートフォリオの自動拡張で 40% を節約できたと述べられています
- **完了率の向上とコストの低下**：DeepSuite の 113 課題で、最良の単一モデルは 74%（約 6.5 ドル）、上位 3 モデルで 91%、18 モデルのオラクルルーティングで 97.6% かつ最安
- **導入の手軽さ**：API 互換で、IDE やハーネスにそのまま組み込め、有効にするだけで使える
- **PayPal にとっての効果**：従量課金で事前確約が不要、GPU 調達の問題がなく、新モデルがすぐ使え、Foundry のガードレールと連携できる。タスクごとにコスト最適化されたモデルが得られる
- **Foundry 上の運用**：Microsoft の請求書にまとまり、既存の Azure ワークフロー、ガバナンス、セキュリティを使える
- **自社データの蓄積**：重みにして学習すれば、新しいモデルが出ても手持ちの例から再現して改善できる

なお PayPal の導入後の具体的な削減額や成果の数値は、発表では語られていません。

## 9. まとめ

Rob 氏と Srini 氏は、単一モデルを頼りに次のリリースを待つことをやめ、自社の仕事を測定してモデルのポートフォリオを組み、必要に応じて自社の重みを持つことを勧めました。SII の結果とコーディング課題の結果は、複数モデルを使い分ける方が完了率もコストも優れることを示しています。PayPal の事例は、ゲートウェイのログをタスクに分け、Jira と PR に結び付けて、再実行できるベンチマークを構築する手順を示しました。

学習は、ルーティングで解決できない差が残ったときに検討します。サーバーレス学習なら 29 ドルでアダプターを作れる例があり、Foundry へは 5 ステップで持ち込めます。チームへの問いは次の 3 つです。どのモデルが自社の仕事で価値を出しているか、タスク 1 件を成功させるコストはいくらか、評価で効果を確認できる繰り返しの失敗はどれか。
