# THR985 Enterprise Data & AI with Azure, Azure Databricks and Snowflake

## 1. はじめに

このセッションは、Snowflake と Azure Databricks にデータが分かれている企業が、データをコピーせずにエージェントから横断的に使うための構成を扱います。発表者は「1 つの問い、Azure 上の 1 つのアーキテクチャ、2 つのライブデモ」という構成で進めています。

中心にある考えは、**「一度だけ保存し、一度だけ統制し、どこでも計算し、エージェントはデータの近くで動かす」**ことです。データは Azure Data Lake Storage 上にオープンな形式（Apache Iceberg）で 1 コピーだけ置き、各プラットフォームは自前の計算資源で読みます。その上で、エージェントを Microsoft Foundry と API Management で統制します。

発表では、この構成で判断が必要になる 5 つの決定と、実際に踏んだ落とし穴、読み取りの二重課金やセキュリティ上の注意が具体的に語られます。

## 5. 発表内容の詳細

### 5.1 アーキテクチャの全体像

Azure 側は 3 層で構成されます。

| 層 | 構成要素 |
|---|---|
| データ基盤（最下層） | Azure Data Lake Storage。Apache Iceberg 形式で 1 コピー |
| ID とセキュリティ（側面） | Microsoft Entra |
| AI コントロールプレーン（最上層） | Microsoft Foundry と API Management。社内外のエージェントを統制 |

その間に、Snowflake、Azure Databricks、Fabric がそれぞれ自前の計算資源を持ち込みます。Snowflake と Databricks は自前のエージェントも持っています。プレビュー段階なのは、Genie の MCP サーバーと、MCP ツール向けの AI ゲートウェイの 2 点です。Snowflake の MCP サーバーは一般提供（GA）と説明されています。

### 5.2 決定 1：データ基盤

1 つの形式で 1 コピーとし、データプロダクトごとに書き込み側を 1 つに決めます。Snowflake は自分のプロダクトを Horizon カタログ付きの Iceberg テーブルとして Data Lake Storage に書き、Azure Databricks は自分のプロダクトを Unity Catalog のテーブルとして書きます。読み取り側は書き込みません。各エンジンが自分のコンテナーにだけ書けるよう、ストレージのロールで強制します。

ストレージにはフェイルセーフ（誤削除からの自動復旧）がありません。**論理的な削除（ソフトデリート）を有効にし、バックアップも取ってください**。

落とし穴は 2 つ挙げられています。

1. ストレージアカウントでは Blob エンドポイントではなく **DFS エンドポイント**を使います。両者を混ぜると、もう一方のエンジンがテーブルを使えません。Databricks が使えない場合はクエリフェデレーションにフォールバックし、計算が二重になります。
2. テーブルは互換性のあるシリアル化ポリシーで作成します。後から変更できません。

### 5.3 決定 2：自前の計算資源の持ち込み

読み取りの経路は 3 つあります。

| 経路 | 内容 |
|---|---|
| 経路 1 | Snowflake が自分のテーブルを自分のウェアハウスで読む |
| 経路 2 | Azure Databricks がカタログフェデレーション経由で同じファイルを読む。最初に Snowflake からメタデータを取得し、その後ファイルを直接読む |
| 経路 3（落とし穴） | Databricks が Iceberg のメタデータを使えないと、Snowflake ウェアハウス経由の JDBC にフォールバックする。両方のエンジンが課金される |

発表者は、デモの準備を最初に行ったときに GRANT 文の問題があり、結果として二重計算になったと話しています。デモでもその点が示されます。

セキュリティ面の落とし穴も重要です。Snowflake は、自分の計算資源で読むときに行アクセスポリシーとマスキングを適用します。しかし Databricks が同じファイルを直接読むとき、それらのポリシーが適用されるとはドキュメントに記載されていません。ポリシーは Snowflake 側にあり、ストレージに届いたクエリにはポリシーが存在しないためです。発表者のテストでは適用されず、売上テーブルにリージョン別の行アクセスポリシーを設定していたのに、Databricks はストレージ上の 150 万件すべてを読めました。

結論は、**カタログフェデレーションが移すのはメタデータであり、ポリシーではない**ことです。対策は次の 2 つです。

- ユーザーにテーブルそのものではなく、統制されたビューを渡す。
- ポリシーはコードとして 1 回だけ定義し、関係するすべてのプラットフォームで適用する。この例では Snowflake と Databricks の 2 か所です。

### 5.5 決定 3：ID とセキュリティ

Microsoft Entra はあらゆるエンジンが共通して対応する要素です。

- **人**：両プラットフォームに Entra でサインオンします。Azure 上の Entra グループを、Snowflake のロールと Unity Catalog のグループに対応づけます。
- **ワークロード**：Snowflake は自前の Entra アプリとストレージアカウントのロールを使い、Databricks はマネージド ID を使います。
- **ネットワーク**：ストレージアカウントのファイアウォールを有効にする前に、各エンジンのプライベート接続を計画します。そうしないとデータにアクセスできなくなります。

Databricks では、グループをワークスペースに追加しただけでは権限が付与されません。発表者のユーザーは 403 エラーになり、グループにコンシューマーアクセスを与えて解消しました。

### 5.6 決定 4：データプロダクトごとのエージェントと MCP サーバー

データプロダクトごとに 1 つのエージェントを置き、それぞれ専用の MCP サーバーの背後に置くパターンです。

| プラットフォーム | データプロダクト | エージェントの種類 | MCP サーバーの状態 |
|---|---|---|---|
| Snowflake | commercial（商業）、loyalty（ロイヤルティ） | Cortex agent | GA |
| Azure Databricks | demand forecast（需要予測）、supply chain（サプライチェーン） | Genie agent | パブリックプレビュー |

プロダクトごとに分ける理由は 3 つです。各エージェントは自分のデータだけを見ます。オーケストレーターには分かりやすい少数のツールだけが渡ります。プロダクトごとに独立したクォータと緊急停止スイッチ（キルスイッチ）を持てます。店舗や商品などの共通データにはエージェントを置かず、各エージェントが SQL で結合します。**結合はデータベースに任せ、AI モデルには任せません**。

MCP サーバーの背後に Cortex agent を置くか、SQL を置くかについて、2 つの設計が比較されています。

| 設計 | 構成 | 結果 |
|---|---|---|
| 設計 A | SQL ツール付きのセマンティックビュー | B より約 2 倍速く、Foundry のトークンも少ない |
| 設計 B | Cortex agent | Snowflake のクレジットで約 6 分の 1 のコスト。西地域が目標を達成できなかった理由を尋ねると、20 回中 20 回とも供給の問題を挙げた |

設計 A は同じ質問で供給の問題を一度も挙げず、理由をでっち上げたと述べています。発表者の既定は設計 B です。設計 A は、正確な数値が必要な場合や、独立した読み取り専用サーバーとして使う場合に残します。

### 5.7 決定 5：Foundry によるエージェントの統制

Eva が質問を投げる先のオーケストレーターは、Foundry エージェントで、独自の Entra エージェント ID を持ちます。すべての MCP 呼び出しは、API Management の AI ゲートウェイを通り、クォータ、IP フィルタリング、ログが適用されます。

落とし穴は、Foundry がツールではなくプロジェクト接続の URL を使う点です。接続の向き先をゲートウェイにしないと、呼び出しがゲートウェイを迂回します。

4 つのエージェントはすべてコントロールプレーンに登録され、トレースと停止ボタンを備え、OAuth による ID のパススルーに対応します。Databricks は、サービスアカウントではなく Eva 本人に対してポリシーを確認します。また Foundry は呼び出しを把握できますが、エージェントが OpenTelemetry を送らない限り、エージェントの推論内容は見えません。

## 6. デモ・手順

### 6.1 デモ 1：同じ Iceberg テーブルを両エンジンで照会

事前の説明では、売上テーブルを Data Lake Storage に 1 つだけ置き、Snowflake が自分のウェアハウスで、Azure Databricks が自分の計算資源で同じクエリを実行すると予告されています。

1. Azure ポータルでリソースグループを開く。Foundry リソース、API Management、ストレージアカウント、Databricks、アクセスコネクターがある。
2. ストレージアカウントのコンテナー一覧を開く。コンテナーごとにアクセスの定義があり、たとえば Snowflake の commercial データでは Snowflake が書き込み、Databricks は読み取りのみ。
3. `gold` レイヤーのテーブルを開く。Iceberg テーブルで、`metadata` フォルダーと `data` フォルダーがある。
4. `metadata` フォルダーで、列や属性（`sales date` など）を確認する。`data` フォルダーは Parquet 形式。
5. Snowflake で、commercial の売上テーブルを照会する。リージョン別（Central、East、South、West）の数値が出る。Central は 9928。
6. 同じクエリを Databricks ワークスペースで実行する（クラスターの準備を待つ）。同じ結果になり、Central は 9928。
7. Databricks はまず Snowflake にメタデータを問い合わせ、その後ストレージにクエリを送る。
8. Snowflake のクエリ履歴を開く。Databricks が最初に送った、メタデータ取得のクエリが残っており、ウェアハウスのサイズもスキャンしたバイト数も表示がない。Databricks 用のユーザーで実行されている。
9. Databricks 側のクエリ履歴でも、同じ結果とクエリを確認する。

> 補足：画面の細部は音声からは確認できません。数値の「9928」は発話の聞き取りに基づきます。

### 6.2 デモ 2：設計 A と設計 B の比較

デモ 2 は 2 部構成と予告されました。パート A は Cora が同じ質問を設計 A と設計 B に投げて結果を比較する部分、パート B は西地域マネージャーの Eva と東地域マネージャーの Ben が、目標未達とその理由を尋ねる部分です。時間があればキルスイッチも見せる予定でした。

実際に行われた手順は次のとおりです。

1. 最初のユーザーは、本社の commercial 部門の Cora。質問を貼り付ける。
2. オーケストレーター A に質問すると、Central、South、West などのリージョン別の回答が返る。所要時間は 22 秒で、設計 A のトークン数も画面に表示される。
3. 同じ質問をオーケストレーター B にも投げ、時間とトークン数を確認する。
4. トレースを開くと、B では最初の呼び出しが MCP のツール一覧に向かい、commercial agent analyst が呼ばれている。設計 A のトレースでは、SQL セマンティックビューと SQL 実行が見える。
5. 時間が足りないため、パート B は省略した。デモ動画を GitHub リポジトリに公開するとのこと。

> 注意：デモで画面に出た設計 B の時間・トークンの値は、発話では読み上げられていません。

## 7. 注意点・発表者の気付き

- **ポリシーは移らない**：カタログフェデレーションはメタデータだけを移す。Databricks が直接読むと、Snowflake の行アクセスポリシーは効かない。発表者の検証では、150 万件すべてが読めた。
- **二重課金**：Databricks が Iceberg メタデータを使えないと Snowflake ウェアハウス経由の JDBC にフォールバックし、双方で課金される。発表者自身も GRANT 文の不備で遭遇した。
- **DFS エンドポイント**：Blob エンドポイントと混在させない。
- **テーブル作成時のシリアル化ポリシー**：作成後は変更できない。
- **フェイルセーフなし**：ソフトデリートとバックアップを有効にする。
- **403 エラー**：Databricks では、グループをワークスペースに追加するだけでは権限がつかない。
- **ファイアウォール**：有効にする前に、各エンジンのプライベート接続を計画する。
- **ゲートウェイの迂回**：Foundry はプロジェクト接続の URL を使うため、接続をゲートウェイに向けないと迂回される。
- **推論の可視性**：エージェントが OpenTelemetry を送らない限り、Foundry は推論内容を見られない。
- **プレビュー段階**：Genie の MCP サーバーと、MCP ツール向け AI ゲートウェイはプレビューである。

## 8. 利用者にとっての利点

- コピーを減らすことで、パイプライン、費用、アクセスポリシーの同期という負担が減る。
- Snowflake と Azure Databricks の既存の資産を、それぞれの計算資源のまま使い続けられる。
- 設計 B（Cortex agent）は、Snowflake のクレジットで約 6 分の 1 のコストとなり、原因の分析でも 20 回中 20 回で供給の問題を特定した。
- 設計 A（SQL ツール付きセマンティックビュー）は約 2 倍高速で、Foundry のトークンも少ない。正確な数値を返す用途に向く。
- Entra の ID が Databricks まで渡るため、ポリシーはサービスアカウントではなく質問した本人に対して確認される。
- すべてのエージェントはトレースと停止ボタンつきで登録され、API Management のクォータ・IP フィルタリング・ログが適用される。

## 9. まとめ

1. データは Azure Data Lake Storage 上に Iceberg 形式で 1 コピーだけ置き、書き込みはデータプロダクトごとに 1 つのエンジンに限定する。
2. 各エンジンは自前の計算資源で読む。フォールバックによる二重課金と、ポリシーが移らない問題に注意し、統制されたビューとコード化したポリシーで対処する。
3. 人は Entra のサインオン、ワークロードはアプリまたはマネージド ID で認証する。ネットワークはファイアウォールの前に計画する。
4. エージェントはデータプロダクトごとに MCP サーバーの背後に置く。既定は Cortex agent（設計 B）で、正確な数値が必要な場合は設計 A を使う。
5. Foundry と API Management でエージェントを統制する。接続の URL をゲートウェイに向ける。
6. 発表者は、コードとセットアップスクリプトを GitHub リポジトリで公開すると述べている。
