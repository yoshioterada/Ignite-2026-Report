# BRK364 Powering AI with Azure Databricks, Foundry, Fabric and Copilot

## 5. 発表内容の詳細

### 5.1 Azure Databricks が Microsoft 製品である意味

他のクラウド上の Databricks とは異なり、Azure Databricks では請求が Microsoft から届き、サポートも Microsoft が担当します。Azure のサポートポータルでチケットを開くと、裏側では Databricks と連携して一貫した体験になります。今週は、Azure Databricks の画面内からサポートチケットを作成できるようになったことも発表されました。

### 5.2 エコシステム全体像

発表者は、全体像のスライドを示し、上の層から順に説明しています。

**利用者のいる場所への展開（最上位の層）**

- **Excel**：Azure Databricks の Excel アドインで、Databricks 内のデータに対するクエリを実行できます。最近、このコネクタに Genie の機能（Genie One）が加わり、Genie と対話した結果を、列または行として Excel に書き出せます。
- **Microsoft 365 の統合監査コネクタ**：Exchange、SharePoint、Entra ID など Microsoft 365 の各ワークロードのデータを Azure Databricks に取り込めます。発話では「Microsoft 365 Excel Unified Audit Connector」と聞こえます（音声認識の都合で表記が確定できません）。
- **Teams**：Genie は Teams のファーストパーティのネイティブアプリです。テナント管理者が有効にすれば、会話やチャネルで Genie を指名して分析を依頼でき、Azure Databricks に接続して、チャット内に結果を返します。Databricks の専門家でなくても使える点が強調されました。
- **Power Platform のコネクタ、GitHub との統合**：詳細は後半の David 氏に委ねられました。
- **VS Code のアドイン**：VS Code の画面を離れずに使えます。

**モデル**：Azure OpenAI のモデルと、Azure Databricks でネイティブに使える Anthropic のモデルを利用できます。Foundry など Azure Databricks の外にあるモデルでも、外部モデルサービングで接続して使えます。

**基盤の層**：Azure のコンピュート、ストレージ、ネットワークが土台です。1 日に Azure のコンピュートへデプロイされる VM の最大の割合は、Azure Databricks と、その顧客によるものです。直近で確認した数字は 4,000 万 VM ですが、確認のたびに増えているため、正確ではない可能性があると断っています。また、Entra ID との統合により、ユーザーを Entra に追加すれば自動で ID が管理されるため、かつてのような手動での同期は不要です。Entra ID を持つ相手とは、Azure Databricks で作ったダッシュボードも共有できます。

**Fabric 側**：Power BI と Azure Databricks の組み合わせは多くの顧客に使われています。Data Factory は Azure Databricks と直接統合されており、さまざまなソースからデータを Azure Databricks に取り込めます。OneLake 連携ではデータのコピーが不要（ゼロコピー）です。AI 側の連携（Agent 365、Foundry、Copilot、Copilot Studio）は第 3 部で説明されました。

### 5.3 Azure Databricks の 4 つの層

**1. オープンなインフラの層**：データと、そのメタデータの層です。好きな形式を選べ、書き直す必要はありません。固定スキーマの構造化データ（在庫の表計算、CRM のテーブル、銀行取引）も、PDF、動画、音声、SNS のファイルといった非構造化データも扱えます。ロックインは無く、Azure のストレージアカウントと Azure Data Lake のストレージアカウントは利用者が所有します。

**2. エージェントに適応した製品の層**：エージェントは、人間のアナリストやデータエンジニアと違い、仮説を立てて複数の接続を続けざまに、同時に大規模に実行します。データ製品はそれに合わせる必要があります。

- **Lakeflow**：100 以上のネイティブコネクタ（Salesforce や Workday など）。Lakeflow Designer は Genie で動いており、データの流し方を設計すると、裏で Genie がコードを実行します（発話では「Lake Floor Designer」と聞こえます）。
- **Lakehouse**：Raiden エンジンで動くとの説明で、オープンな分析処理を担います（エンジン名は聞き取りが不明瞭で、音声認識の都合で表記が確定できません）。エージェントの時代に必要な、1 秒未満の応答と高い並列性を SQL 実行で実現するとしています。
- **データベース**：即時のブランチ作成とコピーオンライトなどを挙げ、本番に影響しない個別のサンドボックスを、大きなデータベースの複製を持たずに素早く作れる、と説明しました。エージェントがサンドボックスで作業し、人が承認すると本番にデプロイされる、という流れです。

**3. ガバナンスとコスト管理の層**：Unity Catalog（Azure Databricks のカタログ）が、テーブル、ファイル、MCP ツール、自作のスキル、エージェントといった企業のデータを、ビジネスのセマンティクスとともに集約します。データリネージ、自動の品質管理、モニタリング、そしてデータと AI の共有のためのオープンソースのプロトコルによる共有も可能です（プロトコルの名前は発話では確認できません）。品質管理と監査を、データを見える化したその場で強制できます。

さらに Unity AI Gateway を組み合わせると、ダッシュボードだけでなく、チーム単位や個人単位のアラートを設定でき、しきい値を超える前に対応できます。例えば、トークンを使い切っているチームがいれば、そのチームにレート制限をかけられます。モデルへの通信すべても見られます。

**4. エージェント型アプリを作る層：Genie**

Genie は、安全で管理され、最新のデータと AI に常にアクセスできる「賢いデータ・AI の同僚」と説明されています。ファミリーとして次の機能が紹介されました。

| 機能 | 説明 |
| --- | --- |
| Genie（Genie One） | 自然言語で質問すると SQL をリアルタイムに実行し、棒グラフなどで可視化する。途中経過の結果を出してから最終結果を出す。クリックで実行された SQL を確認でき、検証できる |
| Genie エージェント | 毎週金曜 17 時に売上目標の達成を確認する、といった定期作業に、会話を変換して自動実行させる |
| Genie code | パイプラインの作成と ML のワークフローを自動化する。現在の Azure Databricks のパイプラインの半数以上が使っている |
| Genie ZeroOps | 本番のオンコール対応を肩代わりする自律エージェント。壊れたパイプラインを監視し、原因を特定し、PR を作って承認のため送る |
| Genie アプリビルダー | 業務アプリやインタラクティブなダッシュボードを安全に作る |

Genie ZeroOps については、午前 2 時に起きて 3 時間かけて修正を作る代わりに、モバイルアプリからでも内容を確認して承認し、また眠りにつける、という使い方が語られました。AI の価値は、チームメンバーの生活の質を高める点にある、というのが発表者の考えです。

Genie の例として、不動産管理会社が複数ある実在の顧客シナリオにもとづいて準備したデモの内容が語られました。「どの種類の物件に投資するのが最も収益性が高いか」を Genie に尋ねると、SQL をその場で実行して棒グラフなどで可視化し、途中結果、続いて最終結果を返します。クリックすると実行された SQL を確認できます。この内容は画面キャプチャを使った説明で、ライブ操作は発話では確認できません。

### 5.4 Genie を Microsoft 製品の中へ

Genie は Teams だけでなく、Copilot の中でも使えるようにする方針です。発表者は個人の体験として、Databricks の製品全体会議の前夜（夜 10 時）にスライドが無いことに気付き、ベッドの中でスマートフォンの PowerPoint Copilot に、自分のチーム、提携、最大の悩み、OneDrive のフォルダにあるファイルの売上数字を含む 5 枚のスライドを作らせ、翌日そのまま発表したと話しました。1 時間足らずかかる作業が、ベッドの中で済んだとのことです。Genie と組み合わせればさらに強力だ、という趣旨です。

また、Microsoft Foundry でもデータチーム以外のエージェントを作る人がいるため、Azure Databricks のエージェントを Foundry のツールカタログから使えるようにしたい、と述べています。

### 5.5 最近の発表：Private Network Gateway

Azure Databricks には、サーバーレスとクラシックの 2 つの実行方式があります。サーバーレスは、コンピュートや仮想ネットワーク、ストレージアカウントを利用者が用意せず、Azure Databricks が管理する方式です。

**Private Network Gateway** は、サーバーレス向けの新機能で、現在パブリックプレビューです。他のクラウドより先に Azure で提供しており、提携の成果だと述べています。Databricks のネットワークチームが構想を持ち込み、実現に必要な Azure の機能を一緒に洗い出したという経緯が語られました。

- 価値：サーバーレスから外へ出る通信を、拡張しやすい固定的な IP を送信元として安全に流せます。IP が頻繁に変わらないため、ファイアウォールで許可しやすくなります。インフラの運用負荷はゼロです。
- 従来は、オンプレミスや自作のプライベートアプリケーションと安全に通信するため、プライベートリンクを個別に管理する必要がありました。Private Network Gateway ならその管理が不要です。
- PrivateLink を補完する位置づけです。PrivateLink は Azure の PaaS リソースや、自作のサードパーティアプリへ、Microsoft のバックボーンから出ずにプライベート接続する仕組みです。
- 参照アーキテクチャでは、Azure Databricks のサーバーレス環境（赤い枠）が、ネットワークインターフェースカードとハブ VNet（緑の枠）を経由して通信を出します。オンプレミスのサーバー、プライベートなデータベース、別の仮想ネットワークへ到達できます。

この機能が必要になった背景として、顧客の規模が拡大し、チームと製品が増えるなかで、数百、数千のプライベートリンクを管理するのは現実的でないことを挙げています。

### 5.6 最近の発表：OneLake との連携

**用語の整理**：ミラーリングとは「読むこと」であり、鏡に映る自分のように、コピーではなく、動くたびにリアルタイムに更新される 1 つの実体です。OneLake 側はこれをミラーリングと呼び、Databricks 側はカタログフェデレーションと呼びますが、どちらも読み取りです。カタログフェデレーションは、Azure Databricks の外にあるカタログ内の外部テーブルを読むための、Azure Databricks 側の用語です。読み込まれたテーブルは、外部テーブルやフェデレーテッドテーブルと呼ばれます。OneLake と Azure Databricks を両方使うハイブリッドなチームのため、双方向のミラーリングが用意されています。

OneLake は、データを効果的に管理でき、Delta や Iceberg といったオープンな形式も使える統合データ分析基盤として説明されました。

**(1) Unity Catalog から OneLake へのミラーリング（利用者が Fabric 側にいる場合）**

Fabric のデータエージェントを作りたいが、データの一部が OneLake に、一部が Azure Data Lake Storage 上の Azure Databricks にある、という場合の解決策です。

- 2025 年 7 月に一般提供（GA）となり、本番水準の SLA があり、すでに顧客が利用しています。
- ミラーリングされるのはメタデータのみで、データはコピーされません。二重のコンピュートもなく、常に単一のデータソースを参照し、リアルタイムに更新されます。実行時のコンピュートはすべて Fabric 側です。
- 「将来の更新を自動で同期する」オプションにより、テーブルやスキーマの追加・削除が OneLake に自動で反映されます。追加や削除を反映させず、ある時点の状態だけが必要な場合は、このオプションを無効にできます。
- カタログの構造は Fabric へミラーリングされ、基になるデータはショートカットでアクセスされます。
- 対象は 1 つの Unity Catalog の項目単位です。複数必要な場合は、Fabric 内に複数のミラーリング対象を作ります。
- 2 週間前から、ストリーミングテーブルとマテリアライズドビューにも対応しました。まだ未対応のものもあり、顧客からの要望を求めています。
- マネージドとアンマネージドの両方の Delta テーブルに対応しています。
- プライベートエンドポイントに対応し、Microsoft のバックボーンから出ない、完全にプライベートな接続ができます。CI/CD 向けなどに API による自動化も可能です。
- OneLake セキュリティとの統合は、スタートアップ企業と協力して容易にする取り組みがあり、ロードマップにもあります。現時点ではポリシーを複製する必要があり、改善を進めている段階です（提供済みではなく、今後の計画です）。

**(2) OneLake から Azure Databricks へのカタログフェデレーション（利用者が Azure Databricks 側にいる場合）**

OneLake にあるデータを Azure Databricks から読み、Genie に質問するための機能です。今年 6 月の Databricks の Data and AI Summit で発表されており、現在使えます。

- データのコピーは無く、データは OneLake にあるまま Azure Databricks から直接クエリできます。コンピュートは Azure Databricks 側で動き、Fabric 側では動きません。
- 要件として、ネットワーク接続の観点で、Databricks Runtime 18.0 以上、SQL ウェアハウスはバージョン 2025.4.0 が必要です。多くの顧客がすでに使っているバージョンだと説明されています。
- コピーが 1 つなので常に最新で、同期や古いデータの心配がありません。Unity Catalog により、両者にまたがる権限を一元管理できます。

**(3) OneLake を Azure Databricks の保存先にする（読み書き）**

最近発表され、現在パブリックプレビューです。Azure Databricks の世界でのパブリックプレビューは、本番利用でき SLA が付くと説明されました。Azure Databricks の外部ロケーションとして OneLake を使い、OneLake へ直接読み書きできます。上記の双方向の読み取りに加わる機能です。セキュリティ面では、この保存先へのアクセスは、Azure Databricks の管理対象 ID に限定されます。

まとめのスライドでは、Fabric と Azure Databricks のどちらの顧客でも、データを Microsoft のエコシステム内に置き、ゼロコピーで双方向に読める点が示されました。Azure Databricks で Unity Catalog を使いデータを Azure Data Lake Storage に置くことも、OneLake に置くこともできます。OneLake も Azure Data Lake Storage の上で動いている、と補足されています。

### 5.7 AI 連携（David Meyer 氏）

**Unity Gateway**

AI ゲートウェイを拡張し、Unity Gateway と呼ぶようになりました。Unity Catalog と同様、すべての AI をここ経由にすることを狙っています。Databricks はこの利用に課金しません。

- GitHub Copilot（内側の開発ループ）、Codex、Claude Code などの通信をすべて Unity Gateway 経由にできます。開発者は使い慣れたツールを変えなくてよく、予算や制御は Unity Gateway で管理します。
- エージェントのターンごとに OTel のトレースが Databricks に保存され、スマートルーティングに使われます。Azure Databricks にあるオープンウェイトとクローズドウェイトの全モデルへ振り分けられます。
- 属性ベースのアクセス制御で PII を保護している場合、開発者のワークステーション上のエージェントのターンが PII に触れたことを Unity が把握し、そのセッションからは Anthropic などの外部へ出さない、といったポリシーを設定できます。AI の通信をデータの通信の隣に置くことが重要だと述べています。
- Foundry を中心に使う組織では、Foundry からの特定のモデルだけを使うように設定でき、それも Unity Gateway を通せます。AI をどこで動かしていても対象にでき、FinOps のために入れ子の予算や、誰がどのモデルを使えるかを設定できます。Databricks の中だけでなく、組織内のあらゆる AI が対象です。
- 同社が公開したレポート「AI index」では、1 万社の顧客全体で、オープンウェイトモデルを通るトークンの割合が、6 月の約 5% から 10 月の約 30% に増えました。「使っていなければ、まもなく使うことになる」「コストを管理するのは受託者責任だ」という言い方です。
- トレースにはコードベースやデータ組織の情報が含まれるため、それにもとづく処方的なスマートルーティングができ、GitHub Copilot での作業にも支出制限をかけられます。観測、最適化を繰り返して、より効率的で速く安く、良い体験になる、という説明です。
- **Unity Gateway は本日 GA** と述べられました。

**Agent 365 との連携**

Databricks に作った AI（Unity Catalog の MCP、エージェント、前半で紹介された Genie エージェントなど）は、Agent 365 に自動で同期されます。アカウント単位のレジストリ同期で、数百から数千のワークスペースを持つ顧客も、レジストリ同期を有効にするだけで、Databricks の AI がすべて Agent 365 に表示されます。各 AI サービスには、Azure Databricks に保存された OTel による可観測性の入口があり、さらに停止の機能もあります。Unity Catalog の各 AI サービスに「中断」の呼び出しがあり、呼び出す側にそのサービスの管理権限が必要です。問題を見つけたら中断し、解決して再開する、という操作を Agent 365 のガバナンス用の管理画面から行えます。この連携は Agent 365 のチームと進めたもので、発表者は前日に同チームの担当者とステージに立ったと述べています。この部分は短い動画で紹介され、接続済みプラットフォームから Databricks を選んで接続すると、エージェントが Agent 365 に取り込まれる様子が示されています。

**Copilot と Genie オントロジー**

Genie は Databricks で行うあらゆる作業の「デジタルな同僚」で、他のシステムへのアクションも取れます。例えば Databricks では、誰も Salesforce や Jira にログインせず、Genie に更新を依頼するそうです。Microsoft の顧客にとってその体験の中心は Copilot なので、どちらかと聞かれれば Copilot だと答えています。

- Copilot Cowork は Genie オントロジーに接続します。Azure Databricks に生まれた知識を、Microsoft のツールから使えます。Genie オントロジーのコネクタが持つメタデータの説明にもとづき、質問を Genie に回すか判断されます。
- Genie オントロジーは「会社に関する蒸留された知識」で、毎回トークンを使って導き出す必要がありません。生データに Copilot を向けると高コストで品質が低くなりますが、Genie オントロジーなら速く、安く、正確になります。メトリクスの層とセマンティクスがあるためで、DAX のセマンティクスと同期させることもできます。発表者は、精度が約 40% から 90% になる、と述べています。
- **プラグインが今週、テナントレベルで利用可能になりました。**管理画面の場所は発話で「Copilot or admin, Microsoft.com」と聞こえ、音声認識の都合で確定できません。 有効にすれば、Entra ユーザーは設定不要で、あらゆる質問ができ、答えが Azure Databricks にあれば返ってきます。
- Copilot、Copilot Chat、Copilot Cowork、Teams、Docs、Excel などで同じ体験が得られます。ビジネスユーザーはそれぞれ使う場所が違い、財務チームのように Excel で過ごす人もいるため、場所を指定できないという考えです。
- Genie のすべてのターンが OTel のトレースを生成し、説明可能性と後の分析に使われます。
- **Work IQ が、来月または今月末に、Azure Databricks 内の Genie のネイティブな一部になる**と予告されました（発話の言い回しは「next month or at the end of this month」です。これは提供済みではなく予告です）。
- Power Platform や Copilot Studio からの利用も多く、以前は DB SQL のインターフェースにアクセスして全データを取り出していました。現在は同じインターフェースで Genie オントロジーに接続し、より速く答えを得られ、Azure Databricks 環境の内容を理解します。

**Foundry との連携**

Unity Gateway に「プロバイダー」というタブがあり、Foundry を選んでキーを入れると、Foundry 内の AI がすべて Databricks で使えます。Databricks 内の他のモデルを止めて、Foundry のモデルだけを使うこともできます。例えば Claude は Foundry から、Kimi K3 は Databricks で使う、といった組み合わせも、組織の望む形で管理できます（Kimi K3 の綴りは音声認識の都合で表記が確定できません）。逆に、Databricks のものはすべて Foundry でも使え、Genie の入口と Agent 365 のレジストリ連携も同様に機能します。

**GitHub Copilot**

簡単な設定で、GitHub Copilot の体験を変えずに、すべての通信を Unity Gateway 経由にできます。Unity Gateway で予算を設定する例として、「1 日 100 ドル」を挙げています。GitHub Copilot を、起動の前に「UG」を付けて起動すると、コストの上限が減っていく様子と、それがモデルのルーティングに与える影響が見えます。開発者は慣れたツールにとどまり、Unity Gateway で設定した管理がそのツールに表示されます。

## 9. まとめ

Azure Databricks は Microsoft のファーストパーティ製品であり、Excel、Teams、VS Code、Power Platform、Copilot、Foundry、Agent 365、Fabric と連携します。データ面では、Unity Catalog から OneLake へのミラーリング（GA）、OneLake から Azure Databricks へのカタログフェデレーション（利用可能）、OneLake を保存先にする読み書き（パブリックプレビュー）により、どちらの製品にもデータを置けて、コピーなしで読めます。ネットワーク面では Private Network Gateway（パブリックプレビュー）が加わりました。AI 面では、Unity Gateway（本日 GA）が AI の通信、予算、ポリシーを一元管理し、Agent 365 への同期と Copilot からの Genie オントロジー利用が、Microsoft のツールの中で Databricks の知識を使えるようにします。発表者はこれらを、一方通行の扉のない統合として位置づけています。
