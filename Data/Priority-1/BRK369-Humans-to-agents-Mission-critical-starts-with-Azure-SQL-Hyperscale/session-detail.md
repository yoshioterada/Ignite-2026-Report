## 4. 発表者が伝えたいメッセージ

発表者が繰り返したのは、Hyperscale が「巨大なデータベース専用」ではないという点です。10 GB、0.5 vCore から始められ、自動停止（auto pause）でコンピューティング課金をゼロにでき、必要になれば 128 TB、192 vCore まで広げられます。そのため、最初の規模を見積もれなくても始められ、成長しても同じデータベースで続けられる、というのが「start here, stay here」の意味です。

## 5. 発表内容の詳細

### 5.1 Microsoft SQL の中での位置づけ

Azure SQL Database、Azure SQL Managed Instance、Fabric の SQL DB は、**同じエンジンのコードベース**を使っています。それを PaaS として継続的に提供し、数年ごとにパッケージ化して次の SQL Server を出す、という構造です。そのため、どの形態でも一貫した挙動が得られると説明されました。

Hyperscale は新しい製品ではありません。2016 年に開発に着手し、2019 年に提供を開始した（発話は「launched in 19」）とのことで、近年あらためて注目されているため「再紹介」という位置づけです。

### 5.2 Azure が Hyperscale を支える仕組み

Bob 氏は、Hyperscale はクラウドネイティブなデータベースであり、Azure なしには成立しないと説明し、次の 4 つの「プレーン」を挙げました。

| プレーン | 説明で挙げられた内容 |
| --- | --- |
| コントロールプレーン | Resource Manager、Entra ID、監視、ポリシー。Azure のどのリソースにも共通で使える |
| AI プレーン | Microsoft Foundry。モデルのカタログ、エージェントのホスティング、組み込みのコンテンツ安全性。登壇者は「世界で最高の AI クラウドサービス」と評価している（発表者の評価） |
| プラットフォーム | ストレージ、ネットワーク、availability zones。Hyperscale はこれなしには存在できず、仮想マシンなど他のワークロードも同じ基盤を使える |
| アプリプレーン | ローカルの Web サービスを Azure に載せる、関数（Function）を実行する、change event streaming を Event Hub に流す、など |

### 5.3 start here：小さく始める

登壇者は、2016 年に「SQL Server を分解して、クラウドネイティブなサービスとして作り直したらどうなるか」という発想で Hyperscale を作り始めたと述べています。仕様として語られた数値は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| 最小構成 | 10 GB から開始。ストレージのサイズを指定する必要はなく、自動で拡張される。コンピューティングは最小 0.5 vCore |
| 自動停止 | auto pause により、コンピューティングを 0 まで下げられる |
| コストを抑える構成 | HA レプリカ、geo レプリカ、named replica を持たなくても、それなりの SLA が得られる |
| 最大構成 | 128 TB、192 vCore。HA レプリカを多数、geo レプリカ、named replica は 30 個まで |
| 可用性 | 4.5 nines（発話は「4 1/2 nines」）。自社環境の SLA と比較してみてほしい、と呼びかけている |
| named replica | プライマリとは異なるサイズで作成でき、数分で起動する |
| スループット | 現在 150 MB/s（さらに増やす取り組み中） |
| ライセンス料 | **なし**。価格をオープンソース並みに設定しており、Aurora Postgres と競争力のある価格 |

### 5.4 コスト効率：elastic pool と serverless

**elastic pool**は、複数のデータベースでコンピューティングを共有する仕組みです。ピークに備えて各データベースを過剰にプロビジョニングする代わりに、1 つの箱を共有します。登壇者は、プールのような仕組みを提供しているクラウドは自分たちだけかもしれないと話しています。1 つのデータベースがプールを占有しないよう上限も設定でき、これはデモで示されました。

**serverless**は、断続的・予測しづらいワークロード向けです。日中は使われ、夜は誰もログインしないアプリを例に、次の動きが説明されました。

- 最小と最大のコンピューティングを設定する
- 必要な CPU やメモリに応じて**秒単位**でスケールする
- 使われなくなると、キャッシュの回収の仕組みで元に戻す
- auto pause を有効にした場合、設定した遅延までは最小コンピューティング分のみ課金する
- 停止後はコンピューティングとストレージが完全に分離され、**ストレージ分のみ**の課金になる

serverless の auto pause は General Purpose にはありましたが、Hyperscale にはありませんでした。「auto pause があるので Hyperscale に移れる」という声があり、プレビューの数か月で大きな採用があったとのことです。

### 5.5 発表：Hyperscale elastic pool での cross-database querying

昨日の Ignite で発表された新機能が、**Hyperscale の elastic pool での cross-database querying** です。SQL Server から Azure SQL Database に移行する顧客にとって、インスタンス内のデータベース間でクエリを実行していた作業が障壁になっていた、という背景が説明されました。登壇者は、これを長年データベースに対する要望の第 1 位だったと述べています。なお、提供状況（プレビューか一般提供か）は、発表では触れられていません。

### 5.6 ベンチマーク

第三者企業に、Azure SQL Database Hyperscale と Amazon Aurora Postgres（発話は "Amazon Aurora Post"）をできるだけ同条件で比較してもらった結果が紹介されました。指標は 1 分あたりのトランザクション数で、Hyperscale が **51 または 52% 高速**でした。さらに価格は「50% 優れる」と話しています。ライセンス料がないことと、この結果から、「Hyperscale は高い」という見方は当たらないというのが主張です。

### 5.7 アーキテクチャ（level 200）

Bob 氏は、スライドの図に沿って次のように説明しました（登壇者は「レベル 200 の説明」と位置づけています）。

- **compute と storage の分離**：プライマリのコンピューティングにはトランザクションログがなく、ストレージ側の IO もありません。それらは下層の **log servers** と **page servers** が担当し、プライマリは独自のキャッシュ層を持つ
- **高可用性**：データをコピーせずに HA レプリカを起動できる。システムの動きを見てホットなページを温めておくため、HA からの読み取りは高速。プライマリに障害が起きると、必要ならゾーンをまたいで自動フェイルオーバーする。元のプライマリは HA になれる
- **プール**：コアは共有するが、各データベースは別々の page servers とストレージ層を持つ。共通のログサービスはあるが、ストレージは分かれているため、デモのようにデータベースごとに独立して成長する
- **named replica**：HA レプリカではなく、read scale 用のポイント。プライマリと別のコアで動き、コピー作業は不要。レポート、読み取りアプリ、ベクトル検索のスケールアウトなど、プライマリに影響を与えない用途に使え、プライマリと同じストレージ層を使うので整合性が保たれる
- **効果**：チェックポイントやレイジーライトがプライマリのコンピューティングに影響しない

まとめとして、compute と storage の分離、HA の組み込み、プール、serverless、read scale on the fly、ソフトウェアを購入する必要がないこと、が「start here, stay here」の根拠だと述べています。より深い（レベル 400 の）資料は、MSSQL decks のサイトと GitHub リポジトリにあり、HTML でクリックして構成を確認できる、とのことです。

### 5.8 AI 向けの機能の概観

「データベースを、開発者とエージェントのために作る」という方向で、次の機能が駆け足で紹介されました。

| 機能 | 内容 |
| --- | --- |
| JSON データ型 | ネイティブの JSON データ型。インデックスと、性能の高い関数が付く。1 行あたり 4 GB |
| Regex | T-SQL で正規表現をサポート。これを使った動的データマスクなども可能になった |
| 検索 | BM25 を使う全文検索に加え、typo に対応する fuzzy matching の新しいアルゴリズムを 2 つ追加。AI を使わなくてよい検索のシナリオもある |
| ベクトル | ベクトルインデックスとベクトルデータ型 |
| change event streaming | CDC は書き込みと読み取りの両方に IO が必要。これに対し、SQL のエンジンから Event Hub などへストリームを直接流す。イベント処理をエンジンから外へ出せ、追加の IO が不要になる |
| コンテナー | Azure SQL Database container を public preview で提供。無料のオフライン版 |
| 開発者向け | developer hub、Microsoft Agent skills、VS Code や SSMS を使わない場合のプラグイン対応、MCP server |
| REST endpoints | REST API を呼ぶストアドプロシージャ。当時は AI のシナリオが開けるとは思っていなかったが、RAG を可能にした（発話は「ragging the engine」） |

### 5.9 顧客事例：CDW

CDW は Fortune 500 の企業で、最大級の IT ソリューションプロバイダーの 1 つです。米国、英国などで、企業、政府、医療、教育機関など約 25 万の顧客にサービスを提供している、と紹介されました。

**課題と動機**（Anurag 氏）：エンタープライズアーキテクチャの情報（アプリケーション、ビジネス能力、ビジネスプロセス、どのアプリがどの能力を支えるか、廃止時期、前後のアプリ、利用者など）を Excel で管理していました。AI ガバナンスや API ガバナンスの情報も別途管理しており、非効率でスケールしないという認識です。自作した理由は次のとおりです。

- 要件に合わせ、将来の機能追加を自分たちで制御できるようにする
- AI ネイティブな機能を持たせる
- 部署ごとに見方（レンズ）が違うので、カスタマイズする（EA は EA の視点、セキュリティは SSO の有無、インフラは tier 1 かどうか、など）

**開発の経緯**：コーヒーショップで、2 人で「自分たちで作ろう」と決めたそうです。1 月に開発を始め、約 6 週間で作り、4 月 1 日に公開しました。4 月 1 日から発表時点まで、**一度も障害なしで稼働**しているとのことです。

**作り方**：すべて Azure 上でホストし、GitHub Copilot を使いました。ビジネスルールとして「自分でコードを書かない」と決め、すべてのコードを GitHub Copilot に書かせています。ストレージにはスケーラブルな構成のため Azure SQL Hyperscale を選びました。

**アーキテクチャ**（Michael 氏が説明）：

- ユーザーが APIM 経由でアクセスし、Entra で OAuth により保護する
- フロントエンドは React、バックエンドは C#。Microsoft Agent 1.0 framework が組み込まれている（音声認識の都合で表記が確定できません）
- データストレージは Azure SQL Hyperscale。ログは Datadog などを使う
- 開発者はコーディングエージェント（GitHub Copilot）と対話し、Azure DevOps Pipelines を通して AKS クラスターにデプロイする。コードとデータベースの操作、デプロイまで、すべてエージェントが行い、人は 1 行もコードを書いていない
- 人が使う UI のほかに、ツール自体を「AI ファースト」にするため、CDW EA tool のエージェントが組み込まれている

**データ層**：リレーショナルデータベースに、カスタムフィールド用の**大量の JSON**を保存します（EA ツールは多くの属性を扱うため）。そのうえで、ベクトル埋め込みと、データの性質がグラフ中心であることからグラフも構築しています。エージェントと外部クライアントは、ホストされた MCP server を通してデータを探し、埋め込みとグラフのどちらが適切かを判断して使い分けます。

**スケーラビリティと今後**：現在、CDW の全従業員がこのアプリにアクセスできます。約 10,000 人が一度にアクセスしても耐えられる構成になっているとのことです。次の目標は、セキュリティ、社内チーム、EA、インフラなど、部門ごとに別テナントを持てる**マルチテナント構成**で、単一のアプリでそれが実現できると述べています（実装の詳細は触れられていません）。

**得られた学び（5 点）**：

1. 開発中は**同じモデルファミリー**を使い続ける。プロンプトの書き方はモデルファミリーごとに通用しないことがある
2. 開発はモデルに任せる。コードは 1 行も書いていないが、構造化されていて読みやすく、人が見てバグを直せる
3. モデルは**組み込みの知識**を持っている。「エンタープライズアーキテクチャのツールを作って」と頼むと、必要な情報や細かな観点を理解していた（本人が最も大きな学びと述べた点）
4. **コンテキストが重要**。コンテキストが豊かなほど、求めるものが作れる。当初 4〜5 段落だったプロンプトが、徐々に 1〜2 段落に減った
5. **スケーラビリティは必須**。作った直後から、コンサルティング部門、セキュリティ、インフラからも要望が来た。最初から設計に入れておけば、利用者が増えてもアーキテクチャを変えずに済む

**成果**：

| 項目 | 内容 |
| --- | --- |
| ポートフォリオの可視化 | メニューをクリックして探す代わりに、アプリの上のエージェントに質問できる（例：「次の四半期に廃止されるアプリの数は」「財務で使っている主要な 3 つのアプリは」） |
| 自分たちで制御 | 新しい機能を、Excel に列を足すのではなく、自分たちで追加できる |
| 価値実現の速さ | 構築は 6 週間未満、既存データの移行は 3 か月未満。レコードは約 5,000 件（音声認識の都合で数値が確定できません）、データ量は 20〜30 GB 程度（登壇者自身が正確なサイズは覚えていないと話している） |
| スケーラビリティ | 他の視点や利用者が増えても対応できる |
| AI ネイティブ | アプリに AI 機能が組み込まれている |

## 6. デモ・手順

### 6.1 serverless と elastic pool と cross-database query（Caldova の患者予約システム）

患者予約システムを持つ Caldova 社を例にした、Bob 氏のデモです。予約アプリそのものではなく、運用状況を見せる画面が使われています。

1. 画面の左側に、予約件数、患者のチェックイン、スタッフのシステムへのサインインが表示される。右側には、使用中のコア数のメトリクスが表示される
2. スタッフのサインインが増えると、serverless のコア数が増え、昼ごろのピークまで負荷を処理する。スタッフがサインアウトすると、コアは自然に減る。**使うコア数の分だけ課金される**
3. 昼休みや業務終了でスタッフがサインアウトし、1 時間後にデータベースが**一時停止**する。この間は課金されない
4. スタッフが再びログインすると、データベースが再開される。再開は**1 分未満**程度かかるが、通常の業務は問題なく続けられる。その後、コアが再び自動でスケールする
5. Azure Monitor の課金チャートで確認する。均等な棒は最小コアで、課金される下限。大きな棒はスパイク。途中の空白は、コンピューティング無課金（ライセンス料がないのでストレージ分のみ）の時間
6. 次の話題として、Caldova が他のクリニックを買収した設定になる。地域でのブランドがあるため名前は分けたまま、ネットワークとしてつなげたい。Caldova Health は serverless、他は provisioned コアの Hyperscale で、コア数もまちまち
7. 3 つのデータベースで 8 コアを共有する elastic pool を作る。ただし最大が 8 だと 1 つのデータベースがプールを占有しうる。そこで、プールを **24 コアにスケール**する（コントロールプレーンの呼び出し）。1 つのデータベースあたりの上限は 12
8. クリニックごとの使用状況は偏りがある。やがて Caldova Health が上限の 12 に達するが、24 コアのプールには他のクリニックが使える余裕がある
9. ストレージも「手間いらず」。サイズを指定していないが、Caldova Health が 20 GB に達し、30 GB まで割り当てられて自動で拡張された
10. cross-database query に移る。クリニックをまたいで空きを探して予約したい。Caldova をベースのデータベースにする。アプリが複数のデータベースに問い合わせる方法もあるが、Caldova のデータベース内で実行する、という考え。Caldova の中で、ネットワーク全体の患者予約を取得するビューを作ってある。そのビューの中身を見せる（データベースをまたぐ JOIN）
11. さらに**リモートトランザクション**として、Caldova にいたまま、別のデータベースへ UPDATE と INSERT を実行する

登壇者は、これで予約が速くなると述べています（予約のスケジュールが、単一クリニックなら 2 週間かかるところ、ネットワークがあれば 1 日で済む、という説明）。もう一方の登壇者は、この流れを「start here, stay here」の例として整理しました。1 つのクリニックから serverless で始め、クリニックが増えて scale up し、elastic pool でコストを抑え、全体を横断するクエリが必要になっても、同じ Hyperscale 上で対応できる、という内容です。

### 6.2 ベクトル検索のスケール（Anna 氏）

生物医学のエビデンス検索の pilot（biomedical evidence explorer）です。

1. 約 4,000 行の記事データを持ち、記事ごとにチャンクに分けて埋め込みを作成し、全体にベクトルインデックスがある
2. 睡眠障害、インスリン抵抗性、血糖調整に関する詳細な質問を入力し、査読済み記事のみに絞るフィルターも使う。検索されるのは「意味」。結果には前後の文章も表示される
3. 検索は**ハイブリッド**。ベクトル検索（フィルター付き）で意味を探し、全文検索で薬の正確な名前や遺伝子コードを探し、**reciprocal rank fusion** で結果を統合する
4. 画面の時間は、エンジン内で測ったベクトルインデックスの時間
5. この pilot は Hyperscale の serverless で、auto pause の遅延は 1 時間。使っていない間は課金されない
6. 規模が増えた想定で、**192 vCore、約 8 TB、10 億行**にスケールアップし、同じ検索を実行する。結果はミリ秒で返る
7. named replica を作る。サイズと名前を指定するだけで、すばやく作れる（最大 30）。プライマリと同じ page servers を使い、コンピューティングだけを追加する。同じ検索を実行しても同じ速さ
8. 検索時間の比較：4,000 行で約 6 ミリ秒、10 億行で 12〜13 ミリ秒。named replica で実行したため、プライマリには影響しない。同期された変更が反映される

Bob 氏は、10 億件のベクトルをミリ秒で検索する例は見たことがないと述べ、Anna 氏は「私たちの知る限り、これは最速のベクトル検索」と発言しています（比較対象の語は聞き取り不明瞭）。

### 6.3 エージェントへの発展（Bob 氏）

6.2 のアプリに、Bob 氏がエージェントのインターフェースを追加した例です。

1. アプリでエージェントをクリックすると、調査用エージェント（研究アシスタントのようなもの）の画面になる
2. プロンプトを入力すると、エージェントは named replica 上で**複数のベクトル検索を並列に実行**し、情報を集めて要約し、次にすべきことの推奨を返す
3. 単なるベクトル検索の結果ではなく、要約が返る。**追加の質問（フォローアップ）**も提示される
4. フォローアップを選ぶと、エージェントは直前の文脈を把握している。再び並列検索を行い、詳しい情報を返す
5. 構成は、**SQL MCP server** と **Foundry agent**。アプリのコードを Foundry agent に移し、MCP server と Hyperscale に接続してベクトル検索をさせている。「エージェントのための、安全で再利用できるソフトウェア」と説明している

コードはすべて公開されており、試せるとのことです。

### 6.4 automatic index compaction（Bob 氏の hidden gem）

Anna 氏のアプリ（trial のデータを持つ）で、通常のインデックスが原因で性能が落ちた状況を題材にしています。

1. 更新でテキストが伸び縮みするなどの変更が多いと、インデックスが sparse（スカスカ）になり、同じデータでも遅くなる
2. ダッシュボードを更新すると、**約 1 分**かかる（以前は 300 ミリ秒だった、と語られた）
3. データベースの設定として **automatic index compaction** を有効にする。変更のたびに fill factor を保ち、密度の観点でインデックスを維持する。バックグラウンドの処理で、アプリをブロックしない
4. ベースラインは 383 ミリ秒。ダッシュボードを再度更新し、インデックスが良くなり読み取りが減ったことで、ベースラインに近い結果になった、と説明した（具体的な数値は語られていません）

## 7. 注意点・発表者の気付き

- **named replica は HA レプリカとは別物です。** read scale のためのポイントだと説明されました。
- **serverless の一時停止からの再開には時間がかかります。** デモでは 1 分未満とされ、業務上は許容できるという前提でした。
- **elastic pool では、1 つのデータベースがプール全体を占有しないよう、データベースごとの上限を設定します。** 最大値だけを設定した場合の問題が、デモで示されました。
- **serverless の auto pause は、Hyperscale では最近追加されたばかりです（プレビュー中の採用）。** （補足）発表では、この機能の一般提供の時期には触れられていません。
- **Hyperscale の資料は 2 段階です。** この日の説明は「レベル 200」で、より深いレベル 400 の資料とコードは別に公開されています。
- **CDW の学び**：5.9 の 5 点（同じモデルファミリーを使う、コンテキストを豊かにする、最初からスケーラビリティを設計に入れる、など）が、自分たちで作る場合の注意点として語られました。人はコードを書いていませんが、構造化された読みやすいコードなので、人が保守できることも述べられています。
- Hyperscale への移行方法は、この日は扱われていません。

## 9. まとめ

1. Hyperscale は、10 GB・0.5 vCore の小さな構成から、128 TB・192 vCore まで同じデータベースで拡張できます。ライセンス料がなく、第三者のベンチマークでは Aurora Postgres に対し 51〜52% 高速だったという結果が紹介されました。
2. serverless、auto pause、elastic pool、named replica で、コストと読み取りのスケールを調整できます。compute と storage を分離したアーキテクチャが、その土台です。
3. 昨日発表された Hyperscale elastic pool の cross-database querying が、Caldova のデモで示されました。データベースをまたぐ JOIN とリモートトランザクションが実行されました。
4. ベクトル検索は、10 億行・192 vCore の規模でも約 12〜13 ミリ秒、named replica を使えばプライマリへの影響なしに動きます。MCP server と Foundry agent を組み合わせたエージェントのデモも行われました。
5. CDW は、GitHub Copilot などのエージェントだけでエンタープライズアーキテクチャ管理ツールを約 6 週間で作り、Hyperscale 上で JSON、ベクトル、グラフを使って稼働させています。
6. automatic index compaction は、データベースの設定を有効にするだけで、更新でインデックスがスカスカ（sparse）になり遅くなる問題を抑える機能として紹介されました。
