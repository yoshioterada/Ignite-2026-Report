# THR926 Power BI Development in the Agentic Era

## 1. はじめに

このセッションは、Power BI のレポートやセマンティックモデルを、GitHub Copilot app などのコーディングエージェントで作る方法を、初心者向けに紹介する 25 分のシアターセッションです。架空の顧客「Nat」の依頼を題材に、バラバラの Excel ファイルから、セマンティックモデルとレポートを作り、さらに Fabric app というカスタム Web アプリまで発展させる流れで説明されます。

登壇者が一貫して伝えているのは、**エージェントは作業を速くするが、要件の確認と結果の検証は人間の仕事である** という点です。仕様（spec）を先に書く進め方、モデルの選び方、API キーの扱いなど、実際に使うときの注意点も具体的に語られています。

## 3. 何に関する発表か

背景として、AI が BI の世界を大きく変えていることが説明されます。そのうえで、アナリストやアナリティクスエンジニアが、AI の生産性向上を実感できるよう、エージェント活用の手順を分解して示すのが狙いです。

流れは次のとおりです。

1. AI による BI 開発の変化（Quick Measures の例）
2. エージェント開発の考え方（greenfield と brownfield）
3. ツールキット（コーディングエージェントと 3 つのプラグイン、Power BI Desktop）
4. 重要な概念（spec-driven development、mobile-first のワークフロー、human in the loop）
5. デモ：要件から spec を作る → セマンティックモデルとレポート → 検証 → Fabric app → 書き戻し（data annotations）→ Foundry による AI 組み込み
6. モデルの選び方、セキュリティ上の注意

## 4. 発表者が伝えたいメッセージ

- **すべての作業にエージェントを使う必要はない。** 日々の仕事の中から 1 つのワークフローを選び、エージェントを使う形に分解することから始めるよう勧めています。
- **データ分野では、場当たり的なプロンプトより、予測可能で、レビューしやすく、再現できる spec-driven development が向く。**
- **検証は人間の責任。** 上司や顧客が責任を問うのは AI エージェントではなくあなたである、という主張です。
- **価値は成果物ではなくインサイトにある。** 誰にも使われない「AI slop」のダッシュボードを作るのではなく、実際に使われ、意思決定につながるものを作るべきだと述べています。

## 5. 発表内容の詳細

### 5.1 AI による BI 開発の変化

登壇者は、2022 年に、最初の LLM を使った機能である **Quick Measures** をリリースしたと述べています。自然言語を入力して DAX を得る機能で、当時は 50% が完全に間違っていたそうです。Marco Russo 氏が「この機能は使うな」という動画を出したとも話しています。それから 4 年が経ち、Marco 氏は、AI がよい DAX を書けるようになったと自ら支持する動画を出した、という流れです。

画面右側には、コーディングエージェントで本格的なデータアプリケーションを作った例が示されました。セマンティックモデル、すべての DAX、すべてのビジュアル、書式設定まで含まれるものです。

ただし、技術の進歩が自動的に生活の改善にはつながらない、という問題提起もありました。8 年前は Excel、SQL、Power BI、Tableau を知っていれば足りていたのに、今は上司や顧客の期待が大きく上がり、AI で約束された生産性向上を実感できていない人がいる、という指摘です。このセッションは、まさにそういう人に向けた内容だと述べています。

### 5.2 greenfield と brownfield

エージェント活用に万能の方法は無く、まず自分にとって重要なワークフローを理解するべきだとして、2 つに分けています。

| 種類 | 内容 |
| ---- | ---- |
| greenfield | ゼロから新規に作る。例えば、アナリティクスエンジニアが、データの取り込み、パイプライン、セマンティックモデルの作成、ビジネス要件への整形、レポートまたはアプリの構築までを担当する、エンドツーエンドの流れ。セマンティックモデルだけを作る場合もある |
| brownfield | 既存のセマンティックモデルを改善・反復し、要件の変化にエージェントが適応する |

全ワークフローにエージェントを入れようとすると圧倒されるので、**1 つのワークフローから小さく始める** ことを勧めています。

### 5.3 題材：Contoso bike company の Nat

デモの題材は架空の話です。サンフランシスコの Contoso bike company で働く Nat は、小規模事業者によくある「Excel chaos」を抱えています。営業、HR、財務のバラバラのスプレッドシートと、誰も触るべきでない古い CRM のエクスポートがあります。彼女は「売上とコラボレーションを増やせる機会が分かるレポートが欲しい。しかも昨日欲しかった」と依頼してきます。だから手作業ではなく、エージェントを使うという設定です。

### 5.4 ツールキット

土台は **コーディングエージェント** です。デモでは **GitHub Copilot app**（内部にコーディングエージェントがある）を使いますが、どのコーディングエージェントでもよいとのことです。そこに、3 つのプラグインを入れます。プラグインとは、AI エージェントがあるシステムをうまく扱えるように、ツールとスキルをまとめたものです。

| プラグイン | 役割 |
| ---- | ---- |
| Power BI authoring plugin | エージェントがセマンティックモデルと対話し、セマンティックモデルを作成し、Power BI レポートを作る方法を理解する。現時点では既定では有効になっておらず、手動で追加する必要がある。今後、既定で有効にする予定と述べています |
| Rafin（Raven とも聞こえます）plugin | 登壇者が Fabric Apps と関連づけて紹介したプラグイン。エージェントが、Fabric のバックエンドをゼロから作る方法を知るためのもの。書き戻しができるデータアプリや、Fabric 内の複数のソースにつなぐデータアプリを作りたいときに有用（綴りは音声認識の都合で確定できません） |
| Work IQ MCP | 会議、会議のトランスクリプト、メール、業務で使うファイルに関するコンテキストをエージェントに与える |

さらに、**Power BI Desktop** もインストールしておきます。エージェントがレポートのスクリーンショットを自動で撮り、検証できるようにするためです。エージェントでレポートを作っても良い結果が得られない理由は、作ったものを検証できないからだと説明しています。エージェントは PBIR（レポートの定義）までは作れても、検証ができないため、authoring plugin と Power BI Desktop が重要になります。

設定は、GitHub Copilot app の customize から行います。Work IQ は最初から一覧にあり、インストールします。Rafin plugin は検索して有効にします。Power BI authoring plugin は、プラグイン名を手動で追加します。スライドは後で共有すると述べています。

### 5.5 重要な概念

**spec-driven development**

vibe coding はよく知られていますが、spec-driven development を知っている人は会場で少数でした。データソリューションには、予測可能で、レビューしやすく、できれば再現できることが望まれるため、場当たり的なプロンプトより spec ベースの方が適しているというのが登壇者の考えです。ただし、素早い調整なら vibe で行ってもかまいません。このデモでは、多くの部分で spec ベースを使います。

**mobile-first のワークフロー**

デモには含めませんが、エージェントが作業している間ずっと待つのではなく、必要なときだけ対話するために、モバイルでの作業を勧めています。コーディングエージェントに「backslash remote」を on にするよう伝え、GitHub mobile app などからエージェントとやり取りします（コマンド名は音声のまま記載しており、正確な表記は確定できません）。

**human in the loop**

宣伝的な AI デモでは、人間の仕事の重要性が省かれがちです。ツールが短時間でレポートやアプリ、セマンティックモデルを作れても、それだけでは価値は生まれません。データの価値は、ビジネス価値につながるインサイトを提供できるかにあり、人が実際に使うダッシュボードなのか、誰にも見られない AI slop のダッシュボードなのかが問われる、という話です。

### 5.6 モデルの選び方

登壇者は、シナリオに応じてモデルを選び分けることを強調しています。

- **曖昧さが多く、多くを任せる複雑なワークフロー**（デモのように、あいまいな指示を出す場合）：フラッグシップのモデルを使う。例として「Opus 5.5」と「Astra」が挙がりました（音声のまま。モデル名は音声認識の都合で確定できません）。
- **非常に精密で、詳細な spec を渡している場合**：高価なフラッグシップは不要で、より安いモデルを使える。速く、コストも低い。

また、auto モードについて、登壇者の経験では、自動で適切なモデルを選ぶ水準にはまだ達しておらず、いずれ良くなるだろうが、現時点ではどのモデルを使うかを自分で決めて選ぶことを勧めています。

### 5.7 検証の重要性

デモの結果が出たあと、登壇者は、多くの派手なデモが見落とす検証に時間を割く必要があると述べています。検証には 2 つの観点があります。

1. **正しいものを作ったか**：要件を満たしているか、余分なものを足していないか、spec にあるものがすべてあるか。
2. **正しく作ったか**：ソースデータを見て数値が一致するか。特に重要なレポートでは、数値の誤りは致命的になる。フィルターやエッジケースも考える。

どこから検証を始めればよいか分からなければ、エージェントに「手動で検証できるように、実行した手順を分解して説明して」と頼むこともできます。このセッションでは、時間の都合で検証の過程は見せていません。

### 5.8 Fabric app とカスタム Web アプリ

Nat の要望は、ダークモード、アニメーション、filter pills、hover card など、増えていきます。ここまで来ると、Power BI レポートではなくアプリケーションが欲しいのではないか、という状況です。同じセマンティックモデルが、Power BI レポートだけでなくカスタム Web アプリにも使えるのが、Power BI の利点で、そのために提供しているのが **Fabric app**（カスタム Web アプリのソリューション）だと説明しています。Fabric app では、より自由な UI、書き戻し、カスタムワークフローが使えます。

### 5.9 Q&A

Q&A の時間はありませんでした。登壇者は、このセッションが短時間であるため、質問があれば Fabric のブース（「7.30 まで」と述べています。音声のままです）で答えると案内しています。終了間際にも、Fabric のブースに来るよう重ねて案内しています。

## 6. デモ・手順

画面を使ったデモを含みます。登壇者は「fast forward」「skip through」と述べ、時間の都合でエージェントの実行中の部分を早送りしたり、結果だけを示したりしています。そのため、ライブ実演か録画かは、発話からは区別できません。画面の細部は、音声からは確認できません。

### 6.1 要件から spec を作る

1. 前提として、登壇者は、Teams の通話で Nat に要件を質問しています。この部分は見せず、バックグラウンドで済ませてあるという設定。
2. コーディングエージェントに、autopilot モードで、Astra というモデルを使って依頼する。入力は、文字入力でも音声でもよい。音声入力は、マシン上のローカル AI モデルで書き起こされる。
3. プロンプトは、「opportunity tracker sync の会議のトランスクリプトを使い、Nat がレポートに求める要件をまとめた markdown ファイルを作成して」という趣旨。Work IQ があるので、トランスクリプトのリンクを探す必要がなく、会議名と人物名（Nat）を指定すれば Work IQ が探し出す。
4. 実行を早送りして、結果の markdown ファイルを見せた。Nat が作ろうとしているものの目的、重要な KPI とディメンション、曖昧さを持ち込まないための重要な定義がまとまっている。

### 6.2 spec の検証と、セマンティックモデル・レポートの生成

1. spec の検証が重要である。曖昧さがあると、エージェントは作り話をしてしまう。例として「company status」というフィールドがあり、承認・却下・レビュー中・開始済みのいずれかを表す。Nat が company status と offer status を同じ意味で使っていると、エージェントはそれが同義語だと分からない可能性がある。
2. 次の 3 つを入力として渡す。(a) markdown の spec、(b) Nat から受け取ったデザインガイダンスの PNG ファイル（タイポグラフィとブランドカラーが含まれる）、(c) Excel ファイルが大量に入ったフォルダー（どのファイルが必要かは手動で選ばず、エージェントに任せる）。
3. エージェントに **PBIP 形式**（セマンティックモデルとレポートを「コードとして」表現する、コードファーストの形式）で作るよう依頼する。エージェントが作りやすくなり、あとで Power BI Desktop でも操作できると説明している。
4. すべてをローカルの 1 つのフォルダーに集約して、そのフォルダーでコーディングエージェントの新規プロジェクトを開始する。エージェントが見られる範囲をそのフォルダーに限定する。適切な粒度のフォルダーを選ぶことが大切だと述べている。
5. プロンプトは「フォルダー内の spec とデザイン標準を使って、必須のデータだけを使い、セマンティックモデルとレポートを作成して」。登壇者は、あえて曖昧に指示している。
6. 結果：デザイン標準に沿い、使用したロゴを含むフルレポートができた。モデルビューには、エージェントが作ったセマンティックモデルがあった。
7. その後、検証が必要だが、時間の都合で見せないとして進めた。

### 6.3 Fabric app の作成

1. Nat から追加の要望が出たため、新しいソリューションなので新しい spec を作る。要件の確認と、エージェントによる spec の作成（と検証）は、省略して結果だけ示した。
2. コーディングエージェントに、新しい spec と、先ほどと同じデザイン標準（PNG）を追加する。
3. 「添付の spec とデザインガイダンス（PNG）に基づいて Fabric app を作成して」と指示する。**公開済みのセマンティックモデル**（先に service に公開済み）を使い、セマンティックモデル名とそのワークスペース名を伝える。完了したら同じワークスペースに公開するようにも指示できる。
4. ローカルのセマンティックモデルでは動かず、公開済みである必要がある。
5. 実行には約 20 分かかる。時間の都合で、実行は見せず、結果を示した。
6. 結果：よりカスタマイズされた画面。ステータスごとのアイコン、ユーザーの連絡先カードのツールチップ、値のコピー、ダークモードがある。

### 6.4 data annotations（書き戻し）

1. 次の要望は、書き戻しと data annotations。これは spec ほどではないとして、**vibe coding** で指示した。
2. コーディングエージェントに、data annotations が欲しいと伝え、必要な理由を説明する。プロンプトの全文は省略。
3. 結果：売上の推移を示す finance のチャートに、アノテーションを追加できる。財務アナリストが、特定のデータポイントにコメントを付けられる。例えば、数値が高い理由として「buy one, get one の夏のプロモーションがあった」と記入できる。
4. 裏では、アノテーションは Fabric の SQL DB に保存される。

### 6.5 Foundry による AI の組み込み

1. Nat は、アプリの中に AI が欲しいと要望する。ここで **Microsoft Foundry** を使う。Foundry は、自分専用の LLM エンドポイントを持つためのもので、データを渡して LLM に判断や提案をさせたいときに適している、という説明。
2. 使いたいモデルを決め、API キーをエージェントに渡す。ただし、**チャットや markdown ファイルに API キーを入力してはいけない**（セキュリティ上のタブー）。
3. エージェントには、OpenAI エンドポイントなどの LLM エンドポイントがあり、アプリ内で AI の推奨が欲しいと伝える。Rafin plugin を使うと、安全なウィンドウがポップアップし、そこに API キーを安全に入力できる。
4. API キーを扱うときは、**セキュリティスキャナー**でコードをスキャンして脆弱性がないか確認する。GitHub Copilot app には組み込みのセキュリティ機能があり、インストールして、エージェントにコードのスキャンを頼めばよい。今回のスキャンでは問題は無かった。ただし、組織が要求する場合のペネトレーションテストのようなことは行わない。
5. 結果：LLM を使い、データのインサイトからアイデアを生成するペインがある。Robert Johnson との共同作業の例で、最新のコメントに「屋外ランウェイショーをやりたい」とあり、顧客として獲得するためのアイデアを生成した。続いて自転車を可視化する場面があった（詳細は時間切れで、音声からは細部が分かりません）。

## 7. 注意点・発表者の気付き

- 全部のワークフローにエージェントを入れず、1 つのワークフローから小さく始める。
- 仕様の曖昧さをそのままにすると、エージェントは作り話をする。spec は必ず検証する。
- Power BI Desktop を入れておかないと、エージェントがレポートを検証できない。
- フォルダーを指定して、エージェントが見られる範囲を制限する。粒度に注意する。
- Fabric app は、公開済みのセマンティックモデルが必要。ローカルのモデルでは動かない。
- Power BI authoring plugin は、現時点では既定で有効でない。
- **API キーを、チャットや markdown に書かない。** セキュリティスキャナーを使うが、ペネトレーションテストは含まれない。
- モデルの auto モードは、現時点では適切なモデルを選べているとは言えない、という登壇者の見解。
- 上司や顧客が責任を問うのは人間なので、数値の検証、フィルターとエッジケースの確認を怠らない。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **作業の効率化**：セマンティックモデル、DAX、ビジュアル、書式設定を含むデータアプリケーションを、コーディングエージェントで作れる。
- **要件定義の効率化**：Work IQ により、会議のトランスクリプトから要件の spec を作れる。
- **再現性とレビューのしやすさ**：spec-driven development により、予測可能で、レビューでき、繰り返せる。
- **同じモデルを再利用**：Power BI レポート用のセマンティックモデルを、そのままカスタム Web アプリ（書き戻し、カスタムワークフロー）にも使える。
- **コストと速度の最適化**：詳細な spec があれば、安価で速いモデルを使える。
- **作業中の待ち時間の削減**：モバイルからエージェントとやり取りできる。

発表では、数値による効果測定（例：何割の工数削減）は示されていません。

## 9. まとめ

このセッションは、Power BI の開発に、コーディングエージェントを実践的に取り入れるための手引きでした。spec を先に作り、適切なモデルとツール（Power BI authoring plugin、Rafin plugin、Work IQ MCP、Power BI Desktop）を使い、Excel から、セマンティックモデル、レポート、Fabric app、書き戻し、AI 組み込みまで進める流れが示されました。

登壇者の結論は、機械的な作業が減る分、**正しいものを作っているか、正しく作れているかを人間が確かめること** がいっそう重要になる、というものです。使われて価値を生む成果物を作ることが目的で、AI slop のダッシュボードを作ることではないと述べています。
