### 5.1 HorizonDB の概要（Rajesh 氏）

Rajesh 氏は、GA を迎えた HorizonDB を、エンタープライズ、開発者、そして増えつつある AI エージェントのために作った製品だと紹介しました。スライドの数値として語られたのは次のとおりです。

| 項目 | 内容 |
| ---- | ---- |
| コンピュート | 最大でおよそ 3,072 vCores |
| ストレージ | 128 TB |
| 性能 | self-hosted の Postgres より 8 倍高速 |
| コミットレイテンシー | アベイラビリティゾーンをまたいで 1 ミリ秒未満 |

> 注意：ストレージ容量は、スライドの紹介では 128 TB、アーキテクチャ説明の途中では「120 テラバイトから始める」と話されています。いずれも、その先にも進めるという趣旨で話されています。

### 5.2 Postgres アーキテクチャの進化

Rajesh 氏は、3 つの世代を比較しました。

| 世代 | 構成 | 課題 |
| ---- | ---- | ---- |
| オンプレミス | 1 台のサーバーにコンピュートとストレージ（結合している） | スケーラビリティが限られ、HA の構築など管理の負担が顧客側に大きい |
| Azure Database for PostgreSQL flexible server（約 5 年前） | 同じ Postgres エンジンのまま、ストレージ層を切り離し、マネージドディスクを接続 | コンピュートとストレージを別々にスケールできるが、クラウドネイティブではない。コンピュートを 1 つ増やすにもデータをコピーして接続する必要があり、構成が固い |
| Azure HorizonDB | ストレージとコンピュートを **完全に分離**。複数のコンピュートが同じ WAL（write-ahead log）と同じストレージを共有する | コンピュートを足すときにデータのコピーは不要。必要なときにコンピュートだけ、ストレージだけをスケールできる |

### 5.3 クラスターの構成を下から順に

HorizonDB のクラスターは、コンピュートとストレージで構成されます。

1. **最下層のストレージ**: ゾーン冗長の Azure ストレージ（Blob storage）を使う。データセンター全体で事実上無限にスケールできる。現時点では 120 TB から始めるが、それを超えられない制約はない。
2. **ゾーン冗長の WAL ストレージ**: 完全に書き直したサービスで、一から **Rust** で作り、WAL の書き込みに強く最適化している。ゾーンをまたぐ 1 ミリ秒未満のコミットレイテンシーを実現する。詳細は Sandeep 氏が後で説明すると予告された。
3. **共有データストレージ（page servers）**: Postgres のリレーションファイルは Azure ストレージにあるが、Azure ストレージは耐久性に優れる一方で性能は出ない。そこで page servers と呼ぶサーバー群にデータをシャーディングして配置し、ローカルの NVMe ディスクにキャッシュして、低レイテンシー・高スループットでアクセスできるようにしている。これもゾーン冗長で、ストレージスタック全体（Azure ストレージ、WAL ストレージ、共有データストレージ）が **既定でゾーン耐障害**。選択の余地なく最初からそうなっている。
4. **コンピュート層**: 変わっていない点を先に強調した。Postgres そのもので、VM や flexible server のような PaaS で動かす場合と同じ wire protocol と拡張性を持つ。現在は 70 前後の拡張機能に対応しており、今後さらに増やす。

コンピュートは **コンピュートプール** という単位にまとめられます。

- 各ノードは **ステートレス**。コンピュートとストレージを分離したため、ローカルにあるのはクエリ処理とデータベースエンジンの実行に必要なものだけ。
- 1 クラスターに **ライターノードは 1 つ**、**リーダーノードは最大 15**。
- ライターを含むプールは「read-write pool」と呼ぶ。このプールで高可用性（HA）を有効にでき、ライターとリーダーをゾーンにまたがって配置できる。ライターに問題が起きたら、リーダーがライターを引き継ぐ。
- クラスターは **read-write endpoint** を持つ。プール内のどのノードがライターでも常にライターを指すので、接続文字列を変える必要がない。
- 各プールには **read-only endpoint** もあり、接続ごとにラウンドロビンでリーダーノードへ振り分ける（接続のロードバランス）。
- read pool は必要な数だけ追加でき、プールごとにサイズを変えられるため、クラスター全体で大きな読み取りスケールが得られる。

クラスターのスペックとして語られた数字は次のとおりです。

| 項目 | 内容 |
| ---- | ---- |
| ノードあたりのコンピュート | 最大 192 vCores |
| メモリ | 1 コアあたり 8 GB |
| ローカル NVMe キャッシュ | 32 GB |
| ストレージ | 120 TB（上限ではなく現時点の区切り。話者の言葉では "click stop"、表記は音声認識の都合で確定できません） |
| リーダーノード | 15 |
| フェイルオーバー | ステートレスなため高速。「5 秒以内」のような時間に聞こえる（音声認識の都合で正確な値は確定できません） |
| SLA | 「4 nines」と、もう 1 つの値が語られている（"4 nines and a 5 SLN" と聞こえ、音声認識の都合で確定できません） |

### 5.4 トランザクションの流れ（Rajesh 氏）

HorizonDB のクラスターは **「ログがデータベース」** のアーキテクチャです。

1. トランザクションがライターに来たら、WAL ストレージに書く。
2. ログレコードが WAL ストレージに書き込まれた時点で、**トランザクションはコミットされる**。ページのフラッシュなど、他のストレージ操作を待たない。それらはストレージスタックが引き受ける。
3. 同期的に、ログレコードを共有データストレージに適用して、ページを追従させる。
4. 読み取りワークロードのためにリーダーノードのキャッシュにページがあれば、WAL レコードをリーダーノードにも送って追従させる（任意）。メモリ上のページも最新になる。
5. これらはサービスの設定なしに、自動で行われる。
6. ライターやリーダーがストレージからデータを取る必要があるときは、共有データストレージに取りに行く。ローカル NVMe にキャッシュされているため、おおむね 1 ミリ秒未満から 1 ミリ秒前後で返る。

### 5.5 リソース階層

| 階層 | 設定・内容 |
| ---- | ---- |
| クラスター | 作成時にストレージが付き、8 MB という小さな単位から始まって必要に応じて増える（聞き取りどおり。音声認識の都合で確定できません）。read-write endpoint がある。認証、ネットワーク、バックアップポリシー、Postgres バージョン（17、18、まもなく 19）をクラスターレベルで設定する。追加プールのサポートはまもなく |

| ノード | サービスが完全に管理する。ライターかリーダーかのメタデータと、動いているアベイラビリティゾーンが見える |

つまり、**クラスターを管理し、プールのサイズを決め、ノードはサービスに任せる** という分担です。

### 5.6 LSEG における HorizonDB（Dave 氏）

Dave 氏は、London Stock Exchange Group というと取引所を思い浮かべる人が多いが、実際には **収益のかなりの部分をデータ製品の販売から得ている** と説明しました。

**Microsoft とのパートナーシップ**

- Microsoft と 10 年間の戦略的契約を結んでいる。Microsoft は LSEG に相当な投資を行い、取締役会の席を持つ。見返りに LSEG はクラウドへのコミットメントを行った。
- 主な利点は **共同エンジニアリング** の機会。Microsoft Fabric で幅広く行い、最近は HorizonDB でも行っている。HorizonDB は今年の大きな焦点だった。
- Microsoft の世界水準のエンジニアと、データプラットフォームのアーキテクチャと戦略で協力できることが大きな利点、と述べています。

**データプラットフォームの規模**

- 数多くのペタバイト規模のデータ（"many petabytes"）。
- 1 時間あたり数十億行が更新される。
- 1 つのデータ製品に数百のリレーショナルテーブルがある場合もある。
- 非常に大きなデータ量、非常に高い更新率、非常に複雑なデータモデルを同時に扱うため、HorizonDB や Fabric への要求は高い。

**アーキテクチャ**: 数十万の外部データソースを取り込み、整理（curate）し、システム・オブ・レコードでマスターデータとして管理し、データ品質を管理して、データ製品を組み立てます。それを、UI、フィードファイル、Databricks や Snowflake といったクラウドのネイティブな形式への配信など、さまざまな配信チャネル向けの商用パッケージに切り分けて販売しています。

**HorizonDB の位置づけ**: これまでのアーキテクチャは、Delta Parquet のオープンテーブル形式によるレイクハウスが中心で、フィードや UI で配信してきました。一方、**戦略的な低レイテンシー API 配信** はまだ成熟していません。顧客が AI、多くの場合 MCP 経由でデータを消費するようになるなか、MCP サーバーのための API を、レイクハウスの上で直接提供したくない、というのが出発点です。データ更新とクエリレイテンシーの両面でより高い性能が必要だと述べています。

**HorizonDB に傾いた 4 つの理由**

1. 標準の PostgreSQL であること
2. 伸縮するコンピュート
3. スケールするストレージ
4. 簡単な管理（シャーディングは内部で行われ、利用者が管理する抽象に含まれない）

ワークロードは負荷の波が大きく、使う容量が大きいのでコストが無視できない。そのため、顧客の性能への期待に応える面でも、社内のコストとコンピュート効率を管理する面でも、弾力的なスケーリングが重要だとのことです。

**検証結果**: 現在使っている Postgres のソリューションと比べて「大幅に良い性能」が出ており、しばらくテストを続けてきた。具体的な数値は発表では語られていません。来年にかけて戦略的な本番エコシステムの重要な一部とし、より多くのワークロードを載せ、顧客への説明にも使うと述べています。これは「もはや理論上の話ではない」、徹底的に試験して、既存のソリューションを置き換えられる品質だと判断した、という発言でした。

### 5.8 AI エージェントが DB に求めること（Sandeep 氏）

Sandeep 氏は、「エージェントがデータベースに求める中核要件は何か」という問いから始めました。

| エージェントの性質 | データベースへの要求 |
| ---- | ---- |
| とてもせっかちで、結果をすぐに求める | 高い性能 |
| 創造的になる。ときに暴走する | 常に強い分離を提供するセキュアなデータベース |
| データ量・負荷・バーストに対応する必要がある | 常にスケールする |
| インフラは常に動くと仮定する（ゾーン障害や障害があっても） | 高可用性 |

これらは、性能、スケーラビリティ、セキュリティ、高可用性という、エンタープライズのワークロードに常にあった要件と同じで、HorizonDB の土台でもあると説明しています。

### 5.9 パフォーマンス（Sandeep 氏）

#### 比較デモ

self-hosted の Postgres と HorizonDB で、同じコンピュート SKU（聞き取りでは "64 Intel Gen 6 VMs"）を使い、HA 構成にして標準の TPC-C ベンチマークを実行しました。

- 約 9 TB のデータをロード（約 95,000 ウェアハウス、約 470 億行）。
- 結果は、self-hosted Postgres が約 **120K**（トランザクション／分）で頭打ちに対し、HorizonDB は **900K**。同じコンピュート SKU で **8 倍** の性能とのことです。

#### なぜ速いのか: ストレージ責務の分離

Postgres には 2 種類の責務があります。1 つはワークロードやクエリに関する処理（全文検索、ベクトル検索、グラフインデックス検索など）、もう 1 つはストレージに関する多くの責務（チェックポイント、ダーティページのフラッシュなど）です。通常は同じコンピュートノードが両方を担います。HorizonDB は、**ストレージ関連の機能の多くをストレージ層に移し、各役割に特化したサービスを作りました**。コンピュートはクエリとワークロードの実行に専念でき、これだけで 1 桁分の性能向上につながる、と説明しています。

#### コミットレイテンシー

- **ゾーン冗長の self-hosted Postgres**: 通常コミットは 4 ステップ。各レプリカが WAL の自分のコピーを持つため、プライマリが自分の WAL に書き、スタンバイに送り、スタンバイが書いて ack を返す。クラウドではマネージドディスクなので、ネットワークホップが 4 回ほどになりうる。
- **HorizonDB**: WAL の保存に特化した、ゾーン耐障害の WAL ストレージサービスを構築した。書き込みは複数のゾーンの WAL ストレージノードに同時に送られ、**1 回のラウンドトリップ** でコミットできる。HorizonDB が提供されているすべてのリージョンで、複数ゾーンをまたぎ 1 ミリ秒未満で行える。

#### WAL ストレージの内部

WAL のアクセスパターンは特殊で、書き込みは末尾（tail）に行われ、レプリカや page servers といった読み手も末尾から読みます。この点に絞って最適化しています。

- **append-only** の書き込み。WAL ストレージノードでは、複数の層を飛ばして直接 NVMe ディスクに書き込む。
- **io_uring** 上に独自の async runtime を実装し、コンテキストスイッチを最小化、メモリ割り当てをゼロにした。マイクロ秒単位のレイテンシーになるものをすべて取り除き、予測不能性を排除した。
- 読み取り側は、末尾がよく読まれるため、末尾のインメモリキャッシュを維持する。WAL が古くなると、ジオ冗長ストレージに押し出し、災害時にもデータを守る。

#### フルページライトの削減

Postgres では、チェックポイント後にページへ最初に触れるたび、8K の完全なページイメージを WAL に書く（full page writes）。HA 構成ではスタンバイにも同じイメージが複製されます。長時間動かすと、これが繰り返されて書き込み増幅が生じます。HorizonDB はこの処理の多くをストレージ層に移し、**差分（delta）の WAL 更新** だけを送ります。それがレプリカにも、WAL ストレージサービスを通じて page servers にも届きます。この結果、書き込み増幅が劇的に減り、ログが小さくなり、トラフィックが減り、チェックポイント後の急増（burstiness）が減り、CPU がクエリに戻ります。

#### 多層キャッシュ

最下層は冗長性のための Azure ストレージ、最上位は Postgres 本来の shared buffers です。そこに 2 層のキャッシュを足しています。

1. コンピュート側: Postgres のメモリ内キャッシュを、ディスク上の拡張キャッシュで拡張。
2. ストレージ側: page servers のローカルメモリと NVMe ディスクにすべてのページをキャッシュ。

データセットがコンピュートのメモリやローカルキャッシュに収まらなくても、page servers のキャッシュにあふれさせて、低レイテンシーで提供できます。

#### 書き込みの経路

1. 書き込みがライターノードに来て、ストレージ（WAL ストレージ）に送られる。
2. WAL ストレージから、リードレプリカに送られる。
3. 同時に、**filtering service** という特別なサービスにも送る。WAL レコードに対応するページがどこにあるかを判断し、対応する page servers に WAL レコードを振り分ける。
4. page servers で WAL を適用してページイメージを更新し、永続ストレージに押し出して、コンピュートがアクセスできる状態に保つ。

### 5.10 セキュリティ（Sandeep 氏）

利用者向けの機能として、Rajesh 氏が customer-managed keys、private endpoints、Entra などを紹介しました。Sandeep 氏は、内部でもデータ保護に注力していると説明しています。

- すべてのストレージサービスと、そのクライアントは **Rust** で実装している。バッファオーバーフローやデータ競合といった種類の脆弱性は、コードが 1 行も動く前に、コンパイル時に排除される。
- page servers で Postgres の WAL を再生（replay）する部分には、わずかに安全でないコードが含まれる。ここは **Hyperlight**（Microsoft のオープンソース技術）によるセキュアなコンテナーの中で実行する。テナント間の影響が出ない。

### 5.11 読み取りの経路

1. ページの取得要求は、通常キャッシュから返される。
2. キャッシュミスのときは、page server から取得する。ライターは自分がどの LSN まで書いたかを知っているので、その地点を指定して page server に取りに行く。
3. page servers は常に WAL を再生しているため、通常は既にそのページを持っている。まだ持っていないまれな場合は、WAL を再生して新しいページイメージを作り、コンピュートに返す。
4. リードレプリカには WAL が継続的に流れており、キャッシュにあるページについては再生している。キャッシュミスのときは、同じ経路で page server に行き、必要なら WAL の適用を待ってからページを返す。

### 5.12 高可用性（Sandeep 氏）

- **WAL ストレージ**: 複数のゾーンにある。1 つのゾーンが落ちても、**過半数（majority quorum）の書き込み** なので書き込みは通る。
- **コンピュートのフェイルオーバー**: まず self-hosted の Postgres との比較です。
  - self-hosted では、プライマリとスタンバイを別ゾーンに置き、Patroni のようなオーケストレーターが障害を検知してスタンバイを昇格します。HorizonDB にも独自のオーケストレーターがあり、素早くフェイルオーバーできます。この部分は両者でよく似ています。
  - 違いが出るのは、古いプライマリが戻ってきたときです。self-hosted では新しいプライマリとタイムラインを同期する必要があり、WAL が分岐している可能性があるため **pg_rewind**（発表では "pgRewind"）が必要になります。これには時間がかかり、その間に障害にさらされる恐れがあります。
  - HorizonDB には共有の WAL ストレージ層があるので、古いプライマリは戻って WAL を読み始めるだけで済みます。フェイルオーバーとフェイルバックを何度繰り返しても、途中に長い停止はありません。
- **ストレージのフェイルオーバー**: page server 層も複数のゾーンにある。1 つのゾーンが落ちたら、トラフィックは自動的に別のゾーンの page servers に回り、ワークロードやコンピュートからは透過的に行われる。データは Azure ストレージに耐久的に残っているため、元のゾーンが戻れば、キャッシュを裏でストレージから再構築（hydrate）するだけでよい。

### 5.13 スケーラビリティ（Sandeep 氏）

- データページをまとめて **シャード** の集合にし、それを page server 群全体に分散させる。1 つのノードに集中する（ホットスポット）ことがない。
- データが増えると、システムが自動的にシャードの追加を判断し、動的に追加して分散する。コンピュートやワークロードには影響が出ない。現時点の上限は 128 TB だが、先に進めない理由はない。
- **ホットシャードの移動**: 特定の page server のトラフィックが他より多くなると、システムが自動検知して、そのホットなシャードを余裕のある別の page server に移し、ホットスポットを解消する。
- **シャードの分割**: 1 つのシャードがあまりに熱く、移動だけでは偏りが解消しない場合は、自動的に検知してシャードを小さな断片に分割し、ストレージ群に散らす。これは、多数の page server が常にトラフィックパターンを見て、負荷を均等にする方法を判断しているためできる。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **性能**: 同じコンピュート SKU で self-hosted Postgres の 8 倍（TPC-C で 120K → 900K）、ゾーンをまたぐ 1 ミリ秒未満のコミット。
- **スケール**: 最大 192 vCores のノード、最大 15 のリーダー、120〜128 TB のストレージ。コンピュートの追加でデータのコピーが不要。
- **耐障害性**: ストレージスタックが既定でゾーン耐障害。素早いフェイルオーバーと、pg_rewind が不要なフェイルバック。
- **運用の簡単さ**: シャーディングは利用者が管理する抽象に含まれない。接続文字列は変えなくてよく、read-write endpoint が常にライターを指す。
- **標準の PostgreSQL**: wire protocol、拡張機能の仕組みが同じ。
- **セキュリティ**: Entra 認証、private endpoint、customer managed key。Rust と Hyperlight による内部の保護。
- **AI 開発**: AI model management により、PostgreSQL のクエリの中から AI 関数でモデルを使える。
- **LSEG の事例**: 低レイテンシーな API 配信（MCP を含む）の基盤として検討し、テストでは現在の Postgres より大幅に良い性能を確認。来年に向けて本番ワークロードを広げる計画。

## 9. まとめ

Azure HorizonDB は、PostgreSQL のコンピュートはそのままに、ストレージを完全に分離し、WAL 専用のゾーン冗長ストレージ、page servers によるキャッシュ層、filtering service、Rust による実装、Hyperlight による隔離を組み合わせたクラウドネイティブなサービスです。この設計により、同じコンピュート SKU で self-hosted Postgres の 8 倍の TPC-C 性能と、ゾーンをまたぐ 1 ミリ秒未満のコミットを実現しています。高可用性は共有 WAL と過半数の書き込みで、スケーラビリティはシャードの自動追加・移動・分割で支えています。LSEG は低レイテンシー API 配信の基盤として HorizonDB を評価し、来年にかけて本番へ広げる計画です。

最後に Sandeep 氏は、性能・可用性・セキュリティ・スケーラビリティという、AI エージェントとエンタープライズのワークロードに共通する要件が、HorizonDB の土台だと締めくくりました。
