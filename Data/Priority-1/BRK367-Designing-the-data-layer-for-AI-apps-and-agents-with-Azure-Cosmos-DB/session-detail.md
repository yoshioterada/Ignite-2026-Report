# BRK367 Designing the data layer for AI apps and agents with Azure Cosmos DB

## 1. はじめに

このセッションは、AI アプリやエージェントのデータ層を Azure Cosmos DB でどう設計するかを、3 つの観点で整理した 45 分のブレークアウトです。観点は **operate（エージェントがアプリのデータに対して何をするか）**、**remember（エージェントが何を覚えておくか）**、**retrieve（今のデータで回答の根拠をどう取るか）** です。

進行は、Azure Cosmos DB に携わる 2 名の登壇者（Madeline Egan 氏は product manager と自己紹介）が、会場参加型のクイズを挟みながら対話形式で行います。途中で、バグ調査を題材にした画面デモがあります。後半には、Willis Towers Watson（WTW）のエンジニアが、自社の AI 機能 Violet で Cosmos DB を使っている構成と、実装で学んだ教訓を話します。最後に GA・プレビューの発表と、AI Search との使い分けに関する質疑応答があります。

## 3. 何に関する発表か

テーマは、AI アプリやマルチエージェントのシステムで、運用データ・メモリ・状態・検索を 1 つのデータ層でどう組み合わせるかです。登壇者は、モデルの話題が中心になりがちだが、**モデルが触れられるのはデータとその下の層である** ことから、データ層を取り上げる、と説明しています。

発表の流れは次のとおりです。

1. operate：エージェントが運用データに対して動くとき、データベースに必要なこと（Agent Kit、managed MCP server、4 つの統制、デモ、バックアップ、スケール）
2. remember：コンテキストとメモリ、マルチエージェントでの共有
3. retrieve：検索方式の選び方、search と rank の 2 段構え、新しい埋め込みモデル
4. 顧客事例：Willis Towers Watson の Violet
5. 発表（GA・プレビュー）と Q&A

> 補足：公式概要には sparse や multi-vector の検索も挙がっていますが、トランスクリプトではこれらには触れられていません。

セッション中には 4 回のクイズ（スマートフォンで QR コードを読み込んで回答）があり、正解数の多い参加者に Cosmos DB のぬいぐるみ（"Cosmonaut plushies"）が贈られました。

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**エージェントのガードレールはプロンプトだけでなく、プラットフォームに置く** という考えです。エージェントは Entra ID で認証し、ロールと権限で触れる範囲を決め、診断ログで事後に確認します。プロンプトは、アプリケーションの権限・検証・監査の境界の代わりにはなりません（2 回目のクイズの答えでもあります）。

次に、**エージェントのデータ層は、運用データ・会話履歴・メモリ・状態を同じ Cosmos DB に置ける** という点です。複数のエージェントが同じ現在の情報から動けるうえ、検索のために別システムへデータをコピーしなくて済むと説明されています。

最後に、**検索は質問に合わせて選ぶ** ことです。すべてに 1 つの検索方式を使うのではなく、完全一致のキー、キーワード、意味の近さ、その両方、のどれが必要かで方式を選ぶ、という整理です。

## 5. 発表内容の詳細

### 5.1 3 つの領域とクイズ 1

登壇者は、エージェント向けデータベースが担うべきことを operate、remember、retrieve の 3 つに分けています。

| 領域 | 問い | 内容 |
|---|---|---|
| operate | エージェントは実際に何ができるか | アプリのデータに対して、データベース上で直接作業する |
| remember | エージェントは何を保持するか | コンテキストとメモリ。毎回ゼロから始めないようにする |
| retrieve | 今、データは何を語っているか | 現在のデータで回答の根拠を取る（grounding） |

クイズ 1 は「エージェントのメモリはどれか」でした。答えは **ユーザーの好み（user preferences）** です。やり取りをまたいで持ち越せるのがメモリだからです。このターンのツール出力は現在のタスクの作業状態にすぎず、製品ドキュメントは知識であり、エージェント自身のデータの外にある公開コンテンツだと説明されました。この区別は、その後も何度か出てきます。

### 5.2 operate：エージェントに必要なデータベース

エージェントがツールを持つと、ライブのアプリケーションデータに対して作業を始めます。そのとき必要なのは、スケールするエンタープライズ向けデータベースと、データに対して何ができるかを制御する権限です。ここで 2 つの要素が紹介されます。

* **Agent Kit：** スキルとして読み込まれ、130 以上の Cosmos DB のコツやベストプラクティスを含みます。Cosmos DB を正しく設定するためのもので、パーティションの問題などが対象に含まれると説明されています（"AgentKit" と表記される箇所もあります）。
* **managed MCP server：** 新しく導入されたもので、デプロイするものはありません。読み取り専用の接続と Entra ID による接続を、データベースとエージェントに直接提供する、と説明されています（この箇所の音声はやや不明瞭です）。

エージェントをどう制御するかについては、**他のアプリと同じ 4 つの統制** を適用すれば、新しいものは要らないという説明です。

1. **ID：** エージェントは、アプリと同じように Entra ID でサインインする
2. **呼び出し：** すべての呼び出しはエージェントとして実行されるので、誰が要求しているかが分かる
3. **権限：** ロールと権限で触れる範囲を決める。エージェントが間違えても、データは安全に保たれる
4. **記録：** すべてが診断ログに記録され、後から何があったか確認できる

### 5.3 スケールとバックアップ

エージェントアプリは、一般的なアプリよりもユーザーあたりのリクエストがはるかに多く、ユーザーは世界中に分散している、という前提で次の点が挙げられました。

* 選んだ任意の Azure リージョンにデータをレプリケートできる
* マルチリージョン書き込みで、ユーザーとエージェントのレイテンシを低く保つ
* オートスケールで Request Units が需要に応じて増減する。サーバーレスも選べる
* 自動フェイルオーバーと、マルチリージョンアカウントでの **99.999% の可用性 SLA**

エージェントのメモリを持つ同じデータベースが、ユーザー数に合わせて全リージョンでスケールします。

あわせて、**Azure Backup for Azure Cosmos DB** が紹介されました。バックアップの保持期間をはるかに長く管理でき、**最長 10 年の日次バックアップ**、RPO、リージョンをまたぐ・サブスクリプションをまたぐ構成など、コンプライアンスに必要なものを備えるとのことです。**これは一般提供（GA）になった** と説明されています。

### 5.4 クイズ 2

「エージェントがアプリのデータに書き込む前に最も重要なことは何か」というクイズでした。答えは **権限、検証、監査可能性（permissions, validation, and auditability）** です。プロンプトは、アプリケーションの権限・検証・監査の境界の代わりにはならない、と説明されています。

### 5.5 remember：コンテキストとメモリ

コンテキストとメモリの違いは、**エージェントが今やっていること** と、**将来に持ち越して覚えておく必要があること** です。それぞれが Cosmos DB 内で別のライフサイクルを持つべきだと説明されています。AI アプリやエージェントに必要なデータは 3 種類です。

| 種類 | 内容 |
|---|---|
| 会話履歴（conversational history） | 今のチャットで起きていること。メッセージ、ターン、セッション、コンテキスト |
| メモリ | 現在のチャットから取り出して、将来のために覚えておくこと。例は「Gal は寿司が好きではない」で、次から寿司店を勧めないようにする |
| 運用データ | すでにあるアプリのデータ |

3 つとも Cosmos DB に置けます。メモリは、コンテキストから特定のことを抜き出してデータベースに覚えさせるものです。

このメモリのライフサイクルを、各チームが手作業で作る必要はありません。登壇者は、そのためのツールキットがあると説明しています。コンテキストからメモリを取り出す、保存する、覚える、呼び出す、そして不要になったものを整理・削除する、という手順を支援します。

### 5.6 複数エージェントでの共有

複数のエージェントが同じ問題に取り組む場合の答えは、**すべてが 1 つのデータ層を共有する** ことです。

1. **メモリの共有：** あるエージェントが覚えたこと（寿司が好きではない、など）を、他のすべてのエージェントが呼び出せる。誰もゼロから始めない
2. **状態を通じた協調：** 状態も同じデータベースに保存されるので、各エージェントは何が終わり、何が進行中かが分かる
3. **保護：** 単一のエージェントと同じように保護される。各エージェントは自分の ID を持ち、ロールと権限で触れる範囲が決まる

メモリ、状態、運用データがすべて Azure Cosmos DB にあるため、エージェントは同じ最新の情報から動けると説明されています。

### 5.7 クイズ 3

「どれが通常、永続的なメモリになるべきか」というクイズでした。答えは **「簡潔な回答を好む」という、ユーザーが述べた好み** です。述べられた好みは、今後のすべてのやり取りでエージェントの助けになります。リトライ回数、一時的なエラー、スピナーは作業状態に属し、作業が終われば消えるべきものだと説明されました。

### 5.8 retrieve：検索方式の選び方

単純なルックアップは、ユーザーが検索に使うキーやフィルターを正確に知っているときに有効です。しかし多くの質問はもっと曖昧で、キーワード、似た意味、またはその両方が必要になります。そこで登壇者は「質問そのものに対して検索方式を選ぶ。すべての仕事に同じ検索モードを使わない」と述べています。選び方は、次の問いを順にたどります。

| 状況 | 使うもの |
|---|---|
| 正確なキーやフィルターがある | 既知のキーと構造化フィルターに対する通常のクエリ |
| キーワードが重要 | キーワードの精度を出す **フルテキスト検索** |
| ユーザーが違う言葉で似た意味を指している | 意味の類似性を見つける **ベクトル検索** |
| 正確なキーワードと意味の両方が必要 | 精度と意味を両立する **ハイブリッド検索** |

大きな利点として、すべてを別システムにコピーせずに、エージェントを現在のアプリケーションデータに根拠づけられる点が挙げられています。

### 5.9 search と rank の 2 段構え

エージェント向けの検索は、**search、そして rank** の 2 段階で考えるとよい、という説明です。

1. **search：** 候補を見つける段階。ベクトル検索のように、正確な語ではなく意味で一致させる
2. **rank：** semantic reranking が search で見つかった結果を並べ替え、最も関連性の高いものを先頭にする

search が網を広げ、ranking が最良の答えを上に置きます。どちらも現在のアプリケーションデータに対して動くので、別システムへのコピーなしでエージェントを根拠づけられます。**semantic reranker は一般提供（GA）になった** と説明されています。

### 5.12 顧客事例：Willis Towers Watson の Violet

Nick Blake 氏が、自社を **WTW** と呼び、企業のリスク、資本、人に関する領域で多くの事業を行うグローバルな大企業だと紹介しました。自身は benefits outsourcing 部門に所属し、大企業のクライアントが従業員の福利厚生を運営するのを支援し、その体験を支えるテクノロジープラットフォームを構築・運用しています。年次の福利厚生の登録（医療プランの選択、HSA の拠出設定など）を行った人は、同社のツールを使っている可能性が高いとのことです。

#### Violet とは

WTW の AI 機能群の名前で、クライアント、その従業員、自社のデリバリーチームを支援します。従業員向けの Web アプリケーションの中で、AI を使ったアシスタント兼コンシェルジュとして動き、質問に答えるだけでなく、登録フローや福利厚生に関する判断を、1 年を通じて能動的にナビゲートします。

Violet のはじまりは約 10 年前の「ささやかなチャットボット」でした。**Microsoft Bot Framework** 上に、Language Understanding や QnA Maker などの初期の Cognitive Services を使って作られ、この夏まではほぼ意図検出と FAQ ベースのボットでした。この夏に **生成 AI とエージェントベースのオーケストレーション** へ移行し、これが必要なデータを根本から変えたと説明されています。

#### なぜデータ層が重要だったか

福利厚生は複雑で、人は重要な金銭的判断をします。そのため一般論ではなく、焦点が絞られた個別の回答が必要です。数百万人の参加者と多数の雇用主を支援しており、雇用主ごとに福利厚生プログラム、プラン設計、用語、適格性ルール、プラン設計文書などが異なります。汎用の最先端モデルだけでは対応できず、モデルは与えるデータ次第です。与えるデータは 2 つに分かれます。

* **従業員固有の属性データとトランザクションデータ：** プラットフォームとリレーショナルデータベースにあり、**決定論的な MCP ツール** で LLM に渡す
* **知識データ：** 会話の文脈における意味で検索でき、かつ雇用主、従業員、適格性、アクセス権でフィルターできる必要がある

このため、モデルのコンテキストを根拠づけるバッキングストアには、知識コンテンツ本体、その **ベクトル表現**、パーティション・フィルタリング・帰属などを管理する **メタデータ** の 3 つを置く必要がありました。リサーチと概念実証を経て、選ばれたのが Cosmos DB でした。

#### Cosmos DB を選んだ 5 つの理由

1. **単一の運用ストア：** 1 つの検索可能なレコードにデータ、メタデータ、埋め込みが入り、複数のシステム間で同期する必要がない
2. **ハイブリッド検索：** ベクトル検索は用語がずれていても質問の意味に合わせられる。フルテキスト検索は、クライアント固有のプラン名、ベンダー名、略語などの特定の用語に強い。Cosmos では両方を組み合わせ、結果を **reciprocal rank fusion（RRF）** で統合できる
3. **リアクティブな取り込み：** 元データは予告なく頻繁に変わる。Cosmos の **change feed** で非同期処理を起動し、コンテンツを埋め込み・再埋め込みする。ベクトル表現がデータにほぼリアルタイムで追従する
4. **既存のインフラに合う：** すでに Bot Framework のボットが Cosmos をボットの状態管理と会話履歴に使っており、セマンティック検索用のコンテナを 1 つ追加するだけで、既存の Azure リソースや DevOps の実践になじむ
5. **コスト：** Cosmos の消費ベースの Request Unit モデルで、使った分だけ支払う。専用の固定の検索ティアも、別のベクトルクラスターも要らない

#### エンドツーエンドのアーキテクチャ

LLM のコンテキストを知識データで根拠づける部分で、**populate、embed、retrieve** の 3 段階です。

1. **populate：** クライアントが管理する複数のソース（独自のナレッジベース、FAQ、福利厚生の教育コンテンツ、プラン文書、プラン設計文書、PDF など）から取り込む。デプロイパイプラインで Cosmos に同期する。Cosmos では、小さな記事は個別の記事として、PDF は **Document Intelligence** で解析したチャンクとして保存する。その後、出所（provenance）、帰属、テナントによるパーティション、アクセスによるフィルタリングに必要なメタデータを付与する
2. **embed：** Cosmos 内で何かが変わると、change feed を処理する **Azure Functions** が、非同期の埋め込み・再埋め込み処理を起動し、ベクトルを同じレコードに書き戻す
3. **retrieve：** 従業員が質問した会話時（実行時）に、発話をベクトル化し、ベクトル、フルテキスト、テナントやアクセスのためのメタデータ条件を含むクエリを作る。Cosmos がハイブリッド検索を実行する。結果をさらにメタデータでフィルターし、**semantic re-ranker** で、直前の会話の文脈における意味に基づいて並べ替える。上位 N 件がモデルのプロンプトのコンテキストウィンドウに入る

サンプルの Cosmos レコードが LLM のコンテキストになる流れもスライドで示されました。要点は、**テキスト、ベクトル、各種メタデータが、同じ検索可能なレコードに共存している** ことです。

### 5.13 Nick Blake 氏の教訓

実装中に、ときには痛い思いをして学んだ点として、次の 4 つが挙げられました。

1. **ベクトルとフルテキストのポリシーは早い段階で固める：** 変更するにはコンテナーを削除して作り直す必要がある。本番データが入って停止できないコンテナーでは、これが大変な作業になる
2. **ハイブリッドクエリ全体（または複数のクエリ）を評価する：** ベクトルだけの検索は高速で安価だが、ハイブリッドと RRF を加えると、RU の消費の面でかなり高くなる
3. **現実的な負荷、特に同時実行で試す：** 1 人のハッピーパスでは何でも動くが、数百万の会話に、非同期の埋め込みバッチが競合し始めると、すぐに悪化する
4. **圧力とパフォーマンスのシグナルをテレメトリで監視する：** レイテンシ、リトライ、特に **スロットリング（429 応答）** を見る

### 5.15 Q&A

**質問：** Azure AI Search を Cosmos DB の上で使っている。今回の機能が出た今、AI Search を使う必要はまだあるのか、それとも Cosmos DB だけで済ませられるのか。

## 6. デモ・手順

このセッションにはデモがあります。架空の小売業 **Zava Retail** のサポートが、「顧客が自分の注文をすべて見られない」という問題をエスカレーションした、という設定です。画面の細部は音声からは確認できないため、語られた範囲で順に書きます。

### 6.1 1 人目の開発者（Gal）：バグの調査と修正

1. **Resolutions Hub** というアプリが、デモ担当者のノート PC 上で、Cosmos DB とともに動いている
2. アプリは **managed MCP** で Cosmos DB に接続している。エージェントはホストされた managed MCP と通信し、それがエージェントに代わってデータベースに接続する
3. Azure Cosmos DB の、新しく導入された埋め込み生成も使われている（この箇所の音声は不明瞭です）
4. Copilot を通じて、接続に関するバグが何かを調査する。Copilot が MCP サーバー経由でデータを確認し、コードを直す小さな変更を提案する
5. バグが見つかって修正された。同様の問題に出会ったとき、毎回すべての手順をやり直さなくて済むよう、この問題を覚えておく
6. 実際の問題を埋め込みにして、意味を持たせて Cosmos DB に取り込み、将来に検索できるようにする
7. 保存されるのは、**バグとその修正の知見だけで、会話ログ全体は保存しない**

### 6.2 2 人目の開発者：新しい会話での検索

後半は、登壇者の 1 人が「2 人目の開発者」として操作します（話者ラベルが無いため、どの登壇者かは特定しません）。

1. プロフィールを選ぶ。会話は空であることに注目するよう促される
2. 問題を自分の言葉で説明する
3. 取得された知見は、1 人目の開発者の調査であり、完全な finding ID は、先ほど公開したものと一致する
4. ホストされた MCP の検索レシートには、**スコープ付きの取得（公開された知見のみ、ランキングの前）** で見つかったことが示される
5. アシスタントが現在のレポートコードとライブデータを確認し、**関連はあるが修正が異なる原因** を見つける
6. テストを実行し、すべて通る
7. すでに 1 人目が既知の問題と修正を記録しているので、2 つ目の知見は公開しない

共有メモリは手がかりを示し、検証で修正が効いたことが分かりました。**1 回公開し、新しい会話で何度でも取得できる** というまとめです。

## 7. 注意点・発表者の気付き

* **プロンプトは境界の代わりにならない：** 権限、検証、監査の境界は、プラットフォーム側に置く。
* **メモリと作業状態を分ける：** ツール出力、リトライ回数、一時的なエラー、スピナーは作業状態で、作業が終われば消える。永続メモリにするのは、ユーザーが述べた好みのようなもの。会話ログ全体も保存しない（デモ）。
* **ベクトル・フルテキストのポリシーは早めに決める（WTW）：** 変更にはコンテナーの削除と再作成が必要。
* **ハイブリッド検索は高くなる（WTW）：** RRF を加えると RU 消費が大きく増える。ベクトルだけなら速くて安価。
* **負荷試験を現実的に行う（WTW）：** ユーザー 1 人では動いても、数百万の会話と非同期の埋め込みバッチが競合すると悪化する。
* **テレメトリを監視する（WTW）：** レイテンシ、リトライ、429 を見る。
* AI Search との使い分けは、データの場所で決める（5.15 の Q&A）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* **別システムへのコピーが不要：** 現在のアプリケーションデータに対し、フルテキスト、ベクトル、ハイブリッド検索と semantic reranking を直接使える。
* **データ層の一本化：** メモリ、状態、運用データを同じ Cosmos DB に置くことで、複数のエージェントが同じ最新情報から動ける。
* **プラットフォームでの統制：** Entra ID、ロールと権限、診断ログという、他のアプリと同じ 4 つの統制を使える。
* **スケールと可用性：** 任意のリージョンへのレプリケーション、マルチリージョン書き込み、オートスケールまたはサーバーレス、99.999% の可用性 SLA（マルチリージョンアカウント）。
* **長期バックアップ：** 最長 10 年の日次バックアップ（GA）。
* **WTW の事例：** 単一の運用ストア、ハイブリッド検索、change feed による近リアルタイムの埋め込み追従、既存の Azure インフラとの適合、使った分だけ支払うコスト、の 5 点が採用理由。数値の成果（件数や削減率など）は、発表では語られていません。

## 9. まとめ

Azure Cosmos DB を AI アプリとエージェントのデータ層に使う設計を、operate、remember、retrieve の 3 領域で整理した発表でした。エージェントには、他のアプリと同じ Entra ID、ロールと権限、診断ログの統制をかけ、メモリ、状態、運用データを同じデータベースで共有させます。検索は質問に合わせて、通常のクエリ、フルテキスト、ベクトル、ハイブリッドを選び、semantic reranker で並べ替えます。

発表された新しい点は、Azure Backup for Azure Cosmos DB、semantic reranker、フルテキスト検索の score projection の GA、embedding generation と Microsoft Embedding One のプレビューです。WTW の Violet の事例からは、ポリシーを早く決める、ハイブリッドクエリのコストを評価する、現実的な負荷で試す、テレメトリを監視する、という実装上の教訓が得られます。
