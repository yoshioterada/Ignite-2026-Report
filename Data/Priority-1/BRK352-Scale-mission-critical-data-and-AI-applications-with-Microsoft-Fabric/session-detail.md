## 5. 発表内容の詳細

### 5.1 課題と導入実績

Fabric の位置づけとして、Gartner が評価するデータ統合ツール、クラウドの管理システム（発表の文言のまま）、分析と BI、AI の各分野でリーダーとされていること、Forrester もリーダーとしていることが挙げられました。ただし発表者は「アナリストよりも顧客の声を聞いてほしい」と述べ、実績として次を紹介しています。

- **40,000 を超えるテナント** が利用している
- Fortune 500 企業の **90% 以上** が、ミッションクリティカルな用途で Fabric を使っている
- **London Stock Exchange**（音声では "LSEC" と聞こえます）：33 PB を超えるデータで 1,200 のデータベースを扱い、London Stock Exchange の data group 全体を支えている。データの扱い方が変わったと説明されました
- **Apollo Hospitals**（アジア最大の医療提供者と紹介）：病院管理のデータをすべて Fabric で管理しており、70 を超える病院、30 TB のデータ規模

### 5.4 Developing（3）：OneLake catalog

OneLake catalog は **Microsoft のデータガバナンスソリューション** で、Teams や Excel を含む **100 以上のアプリ統合** と、**3.5 億を超えるデータアイテム** の管理があると紹介されました。業界が「単体のカタログ」から「プラットフォームに組み込まれた統合ガバナンス」へ移っているという認識のもと、OneLake catalog は次の 3 つを 1 つにまとめ、画面では Explore、Govern、Secure の各タブで提供されます。

- 統合されたデータの探索とキュレーション
- 統合されたデータガバナンスと管理
- 統合されたデータのセキュリティと保護

Explore のデモ（6.2）の後に、次の補足がありました。

- **カタログ API（パブリックプレビュー）**：search API などで、OneLake とセマンティックモデルのテーブルを、ほかのランク付けされた Fabric アイテムとともに探索できる。AI 開発者やビジネスユーザーが、Teams、Excel、Foundry などの 100 以上のアプリでデータにアクセスできるようにする
- **サードパーティのガバナンスツールとの統合**：Collibra、Atlan などのエンタープライズカタログとの統合に対応。サービスプリンシパルによる認証や増分スキャンなどの機能も備える
- **KPMG** の例が挙がり、「顧客の信頼は、明確なデータ境界と強いガードレールから始まる」という趣旨の説明がありました（具体的な事例内容は語られていません）

### 5.5 Managing（1）：キャパシティ管理

ここから Pankaj 氏が担当します。キャパシティ管理者は、スロットリングのリスクや発生したスロットリングへの対応、何が使用率を押し上げているか（ビジネスにとって良い使用か、超過か）の把握、キャパシティの適切なサイズ決めという課題を抱えていると説明されました。過去 1 年半、「actions（アクション）」と「insights（インサイト）」に投資してきたとのことです。デモは医療企業 Caldova（音声の綴りのまま）の管理者の 1 日、というシナリオで進みます（詳細は 6.3）。

機能ごとの整理は次のとおりです。

| 機能 | 状態 | 説明 |
| --- | --- | --- |
| Capacity overage billing（超過課金） | GA（FabCon Barcelona で GA） | 従量課金でベース容量を超えて使える保険（車のシートベルトにたとえられた）。24 時間の期間で上限を設定でき、既存のキャパシティにも使える |
| Fabric on-demand billing：F0 | 説明中に新しい F0 として紹介 | 純粋なオンデマンド課金。ワークロードに対応する課金カテゴリごとに、24 時間のローリング上限を設定できる |
| on-demand のハイブリッドモード | 説明あり | たとえば F32 のキャパシティの中で、特定のワークロードだけをオンデマンドで動かせる |
| Workspace-level surge protection | GA | キャパシティに対するワークスペースごとの使用割合の上限を設定し、超えると選んだ期間（無期限も可）ブロックする。「noisy neighbor」問題や暴走するジョブ・ユーザー対策になる。ワークスペースを「mission critical」にして対象外にでき、手動でのブロック／解除もできる |
| キャパシティ設定の置き場所 | — | ガバナンスと全キャパシティ設定の拠点として、新しい OneLake catalog に集約 |
| Monitor Hub の insights と actions | — | キャパシティの状態を一目で把握し、その場で操作できる |
| Capacity metrics app | 改善 | 全ページを見直し、フィードバックを反映。インサイトを目立たせ、分かりやすくし、UX を刷新 |
| Capacity events（Real-time hub） | overview events は GA、operation events は最近プレビュー | アラートだけでなく、自動での是正やアクションの実行、履歴データの保持にも使える |

発表者は、使用状況データを Eventhouse に集め、自分で capacity metrics app のようなものを作った顧客もいると紹介しています。まとめのチェックリストと、ベストプラクティスを示す **Fabric Capacity Guide** へのリンクが案内されました。

### 5.6 Managing（2）：Monitor Hub による監視

顧客から「Fabric の監視が不十分で、統一された可視性がなく、何が起きているか、どんな対処をすべきかが分かりにくい」という声があると説明されました。そこで、検出と調査のライフサイクル全体にわたり、インサイトのある場所でアクションを取れるようにし、根本原因の分析を簡単にする取り組みを進めていると語られています。新しい Monitor Hub のデモ（6.4）の内容は次のとおりです。

- もとはジョブ中心だった Monitor Hub が、**対応するアイテムタイプが大幅に増えた**
- ジョブの平均所要時間、成功率、最終実行、ステータス、実行履歴のヒートマップ（成功と失敗）が見られる
- 直近の実行のデバッグ詳細に加え、詳しいエラーも確認できる
- **Investigate ボタン**から operations agent が起動し、ログと過去の実行をもとに根本原因を示し、対処のアクションを提案する
- Investigate を使うには、ワークスペースのモニタリング設定で workspace monitoring を有効にする。人気のある要望として、詳細なデバッグログを **1 つの Eventhouse にまとめて出力** できるようになった
- ジョブ以外に、**アプリケーション**（実行統計、クエリのエラー率、アプリのロード）や **エージェント**（呼び出し率、失敗、エラーの推移）の履歴や傾向も見られる
- Activator のアラートも組み込まれており、標準のアラートがある。履歴や宛先の設定ができ、「Run Fabric activities」でアラートだけでなく是正のアクション実行もできる

今後もエージェントを活用したデバッグ支援が追加される予定で、エージェントや自分でのデバッグのため、workspace monitoring を有効にしておくことが勧められました。

### 5.7 Governing：OneLake catalog の Govern と Secure

ここから Adi 氏のパートです。データ資産が増え続けるなか、ガバナンスは複雑さを増しており、Fabric の管理者は「何が起きているかを理解する」「適時に直す」「次の問題を防ぐガードレールを敷く」ための場所を必要としているという前提です。

| 領域 | 発表された内容 |
| --- | --- |
| Govern タブ（インサイト） | データの状態に関するインサイトと推奨アクションが標準で生成される。例として、機密ラベルの適用範囲のギャップが表示される。ワークスペース別・ドメイン別のレポートに掘り下げられ、レポートには Copilot も組み込まれている |
| 一元管理 | 管理ポータルにあった機能が、インサイトとアクションを備えた形でここに集まる。キャパシティ、ドメイン、ワークスペース、テナント設定を管理できる。新しい apps ページでは、アプリとそのワークスペースを確認し、ブロック／解除できる |
| Policies | ガードレールを設定する。例：顧客管理キー（customer managed keys）やアウトバウンドアクセス保護などの機微なワークスペース設定を、信頼する指定管理者だけが変更できるようにする。キャパシティのレベルで「誰がどのアイテムタイプを作成できるか」を制御するポリシーは、数百の組織で採用されており、誰でもコンピュートを立ち上げられないようにできる。ABN Amro（音声では "AB and Amro"）が広く使っていると紹介された。今後はドメインなど、ほかのレベルにもポリシーを追加する予定 |
| ガバナンススキル | これらの機能を AI 経由で提供し、エージェント、Copilot、自動化と連携できる（デモは 6.5） |
| Secure | OneLake のセキュリティを、データプレーンからロール、コントロールプレーンまでカタログ内で管理 |

#### セキュリティの階層

発表では、各レベルのセキュリティが整理されました。

- **組織全体**：Microsoft Purview Security と統合し、組織単位の定義やポリシーがサービス間で引き継がれる。具体例は、Purview Information Protection の機密ラベル、データ損失防止の DLP、インサイダーリスク管理、Copilot の監査アクティビティを追跡する DSPM for AI
- **テナント**：Entra、Private Link、secure by default の原則
- **ワークスペース**：Private Link のサポート、ワークスペース単位の IP ファイアウォールルール、インバウンド／アウトバウンドのアクセス制御、顧客管理キー。これらは GA と説明されました
- **ID とアクセス制御（近日公開）**：assigned identities と Fabric managed identities。アイテムの所有者への依存をなくしたいという顧客の要望に応えるもので、数週間以内に公開予定。最初は Fabric apps と UDF で提供し、ほかのアイテムにも広げる

Fabric と Microsoft はガバナンスを OneLake catalog に集約する方針で、公開されたロードマップがあると案内されました。

### 5.8 Fabric は自分自身をどう運用しているか

最後に Yitzhak 氏が、信頼性について話しました。「どのクラウドも障害がゼロとは約束できない」と前置きしたうえで、Microsoft 自身も Fabric 上で動いていること（例として Microsoft Finance の収益分析や営業分析）を挙げ、ミッションクリティカルだと説明しています。

背景として、Yitzhak 氏は Power BI のプラットフォームを率いていたときに、数十万人のユーザーから数千万人の月間アクティブユーザーへ急成長した経験に触れ、AI の時代にはユーザーがエージェントにもなるため別次元のスケールが必要だと述べています。目標は **現在の 50 倍のスケール** です。設計原則は次の 3 つです。

1. **単一障害点をなくす**：依存先が落ちても代替の使い方で動けるようにし、サービスのチョークポイントを減らす。継続的に取り組んでいる
2. **影響範囲（blast radius）を小さくする**：クラスターやリージョンで問題が起きても、影響するテナントが少なくなるよう、サービスの境界を小さくする。互いに分離された小さな stamp を使い、顧客に対するスロットリングも制御する
3. **重要なワークを動かし続ける**：依存サービスが止まっても、サービス全体は止めず、機能を縮退させて継続する。健全なキャパシティを守ることも含む

加えて、検出と復旧、安全なデプロイにも触れられました。

- **検出**：North Star は、顧客への影響が始まってから、実行可能なアラートが発火してエンジニアが呼ばれるまで **5 分**。SLA に影響し得る各シナリオを検出・診断できるようにし、Fabric の基盤サービスが備える仕組み自体を検出に使う
- **復旧**：ロールバックやフェイルオーバーなどの仕組み
- **安全なデプロイ**：Azure の safe deployment procedure のように段階的にロールアウトする（小さなリージョンで、社内、Microsoft 全体、カナリアリージョン、全世界の本番の順）。Fabric ではさらに、小さなリージョンに加えて **小さな stamp から始めて徐々に広げ**、シグナルを観察・分析しながら次の段階へ進み、多数の顧客に影響する前にリグレッションを検出する
- **AI の社内利用**：スケールを支えるために、エンジニアリングチームを増やすのではなく、AI エージェントでシグナルの監視、分析、相関付けを行う。発表では「毎秒、数百万のシグナルが届く」と述べられ、復旧や緩和の手順もエージェント機能で進める

### 5.9 全体のまとめ部分で語られたこと

Tessa 氏は、Fabric は **毎週デプロイされており**、新機能が継続的に出ていると述べています。スライドでは、データセキュリティ、ネットワークセキュリティ、パフォーマンス、管理などの分野で、2026 年 9 月から 11 月までの最新機能がまとめられていました。**Fabric release plans** で公開ロードマップが確認でき、コミュニティで機能に投票してロードマップに影響を与えることもできると案内されています。特に ID（アイデンティティ）は要望が多く、権限とロールアクセスについても今後の追加があるとのことです。

行動の候補として、テナント管理者、キャパシティ管理者、開発者の別に、ガバナンス、セキュリティ、キャパシティの機能を学ぶことが勧められました。参考資料としては、新機能の発表記事、capacity planning guide、Fabric security white paper、CI/CD のベストプラクティスが挙げられています。

### 6.3 キャパシティ管理者の 1 日（Pankaj 氏）

### 6.5 ガバナンスとガバナンススキル（Adi 氏）

1. OneLake catalog の Govern タブで、機密ラベルの適用範囲のギャップを示すフラグを見る。理由と修正方法が表示され、そこからアクションを取れる
2. ワークスペース別やドメイン別の詳細レポートに進む。レポートには Copilot が組み込まれている

8. 別の例として、データをビジネスドメインに対応付けるようエージェントに依頼する。データをスキャンして推奨を返し、承認すると自動で割り当てる

## 7. 注意点・発表者の気付き

- **手作業の構成は不整合のもと**：開発ワークフローを自動化することが、ガバナンスの前提になるという考えです。
- **エージェントの作業は人間が確認する**：Fabric Copilot のデモでは、実行内容とチャット履歴を確認して「正しい操作をしているか」を把握することが強調されました。ガバナンススキルでも、説明の追加は人間が確認して承認してから適用されます。
- **説明の欠落はコンテキストの欠落**：説明がないと、ユーザーもエージェントもデータを正しく扱えないと語られました。
- **キャパシティの超過に備える**：capacity overage は、「保険」「シートベルト」にたとえられています。上限は 24 時間の期間で設定します。
- **ワークスペース間の干渉**：重要なワークスペースは mission critical にして surge protection の対象外にできます。
- **アクションとインサイトを同じ場所に置く**：Monitor Hub の設計原則として繰り返し語られました。
- **一部の機能は準備段階**：Fabric Copilot の体験は QR コードによる登録案内の段階、ID 関連（assigned identities / Fabric managed identities）は近日公開、policies はドメインなどのレベルへの拡張が今後の予定です。
- **試していない機能は「宿題」**：発表者は、挙手で確認した Monitor Hub や policies について、試していない参加者向けに「宿題」と繰り返しました。新機能を追うために、ロードマップやコミュニティの活用も勧められています。

## 9. まとめ

このセッションは、Fabric を AI 時代のミッションクリティカルなデータ基盤として使うために、**開発、管理、ガバナンス** の 3 つの面から必要な機能を整理したものでした。Fabric skills と Fabric Copilot、deployment plans、Git 統合、API レート制限の拡張が開発の自動化とスケールを支えます。キャパシティの超過課金、F0 とハイブリッドのオンデマンド、workspace-level surge protection、Monitor Hub と Real-time hub が運用を支えます。OneLake catalog の Govern と policies、Purview との統合、ガバナンススキルが統制を支えます。

最後に、Fabric 自身が 50 倍のスケールを見据えて、単一障害点の排除、影響範囲の縮小、重要ワークの継続、5 分の検出目標、小さな stamp から始める段階的デプロイ、AI による運用の補強に取り組んでいることが説明されました。Fabric は毎週デプロイされており、Fabric release plans とコミュニティを通じて今後の機能を確認し、意見を出せます。
