# BRK368 Postgres in production on Azure: Lessons in fleet modernization

## 4. 発表者が伝えたいメッセージ

Guy 氏によれば、フリートとは「管理している Postgres サーバーの集合」で、1 台でも数千台でも同じです。モダナイゼーションとは、周囲の環境が変わり続ける中で、投資に対する最大のリターンと最大の生産性を得ることです。マネージドサービスへ移行すれば費用を抑えられますが、そこで終わりではなく、継続的な最適化でさらにコストを下げ、生産性を上げられるというのがメッセージの核心です。

Sven 氏の事例は、この考え方の実例です。シャーディング向きのアプリケーション設計があり、Elastic Cluster と pg_partman を組み合わせて、12 か月の移行で単一ノードの競合を解消できたと語っています。一方で、事前の見落としが運用で問題になった経験も、具体的に共有されました。

## 5. 発表内容の詳細

### 5.1 フリートのモダナイゼーションとマネージドサービスの価値

Guy 氏は、マネージド Postgres の PaaS で共通して語られる「高い投資対効果」を、カテゴリごとに整理しています。いずれも自前で管理すると高くつく領域です。

- **信頼性と災害復旧：** 問題の検出時に自動でフェイルオーバーする仕組みがあり、アーキテクチャ変更時にスケールアウトしやすい（例として Elastic Cluster）。
- **セキュリティ：** 間違えたときの代償が大きい領域。特に Flexible Server と Entra ID の統合を挙げ、BYOD で境界が曖昧になったネットワークの代わりに、認証に基づくセキュリティ境界を定義できると説明しています。コンプライアンスを担う技術者チームや、全タイムゾーンに待機するエンジニアがいる点も利点としています。
- **統合：** Fabric との自動統合を例に、分析と OLTP を分離できる。
- **アップグレードと自動化：** セキュリティ修正を含むメンテナンス更新を、自動で適用できる。

そのうえで、「環境の何が変わるか」を次のように整理し、後半の新機能と対応づけています。

| 領域 | 変化の例（発表で語られたもの） |
| --- | --- |
| ハードウェア | ストレージの進化（IOPS）。SSD v2 は SSD v1 と追加コストなしで利用でき、スループットが向上すると述べています。世代ごとに CPU が向上。新しい Azure リージョンで接続遅延を削減 |
| ソフトウェア | メジャーバージョンの選択。この日は PostgreSQL 19 のコミュニティ版が GA。Postgres 13 以下は有償の延長サポートとなり、セキュリティ修正が提供されなくなる |
| セキュリティ | AI による攻撃の規模拡大で、最新の CVE と、自分のサーバーへの適用時期の把握がより重要になる |
| アプリケーション | ユーザー数とデータ量の増加。スケールアップ（例：AMD v6、192 vCore）か、スケールアウト（Elastic Cluster でデータを分割）かの判断が必要 |

### 5.2 Wolters Kluwer の事例（Sven Hubert 氏）

**会社とビジネスの背景。** Wolters Kluwer は 190 年の歴史を持ち、税理士、医療関係者、会計士、弁護士向けの出版社から、専門家向けソフトウェアのベンダーへ移行した会社です。Tax and Accounting は売上の 4 分の 1 を占めると述べたうえで、「昨年 16 億」と続けています（通貨は発話されておらず、聞き取りでは会社全体と部門のどちらの数字かも曖昧です）。ドイツでは約 20,000 の税理士事務所と中小企業を顧客に持ち、ドイツの財務諸表の 15% を扱い、毎月およそ 250 万件の給与明細を処理しています。給与、会計、税務、事務所管理といったアプリケーションがあるため、データスキーマも多様です。

- グラフ状でリレーションの多いスキーマ
- 給与向けのワイドなテーブル（ドイツの給与システムでは、従業員 1 人にほぼ 1,000 のプロパティがあるとのこと）
- 会計向けの、小さなレコードが長く続くテーブル（仕訳は約 17 年間保存が必要）

**移行の経緯。**

1. 12 年前に、クラウド非依存を目指して、VM 上の自己管理 Postgres から始めた。
2. データベースが 2 TB まで増えた。容量自体は問題ではなかったが、単一テーブルが 100 GB を超え、テーブルのメンテナンスに負荷がかかった。
3. セキュリティやアップグレードのため、外部サービスプロバイダーと契約しており、予算は年間で「5 桁の高い額」だった。
4. 複数のマネージドサービスを評価し、当時リニューアルされた Azure Postgres（Flexible Server）を選んで移行した。サービスパートナーは不要になり、メンテナンスジョブは Azure 内でうまく動き、コネクションプーリングも無償で得られた。
5. ただし、大きなテーブルの問題は残った。垂直スケールだけでは解消せず、テーブルが IOPS のボトルネックを引き起こしていた。
6. 昨年から選択肢を評価し、拡張として Citus を選ぶことに決め、Citus を使う最も代表的なマネージドサービスである Azure Postgres Elastic Cluster に、過去 12 か月で移行した。

**Elastic Cluster を選んだ理由。**

- **シャーディングモデルとの相性：** 20,000 の顧客のテナント ID と、顧客の顧客にあたる組織 ID（数百万件）が、すでにプライマリキーに含まれていた。テナント単位のシャーディングの前提が整っていた。
- **Flexible Server に慣れていた：** バックアップ、Terraform によるプロビジョニングなどが確立していた。
- **pg_partman との互換性：** 17 年保存する会計テーブルを、会計年度や四半期でパーティション分割したかった。
- **コスト効率：** 既存の Azure SQL エラスティックプール上のスタックと比べて、ライセンスと運用の両面で大きな差があった（倍率は語られていません）。
- **移行の障壁が低い：** pgcopyDB（聞こえた表記のまま）などのツールに慣れていた。発表時点では、Flexible Server から Elastic Cluster へディスクスワップで移行する方法もある。

**移行プロジェクトの進め方。** 開発者、DB 管理者、運用チーム、Microsoft の製品チームが密に連携しました。初期採用者の立場だったことが成功の鍵だったと話しています。並行して進めた作業は次のとおりです。

- 12 のアプリケーションチームが、データアクセス層に時系列パーティションを導入した。これは 6 か月がかりの作業だった。
- 運用チームの 1 人が、移行のリハーサルを繰り返した。本番データのテストサーバー（最終的にはテストクラスター）への復元を自動化し、開発者のスキーマ変更を毎回適用してアプリを起動し、問題を修正して次のサイクルに進んだ。
- 検証として、アプリが起動するかに加え、テーブル数とサイズを確認し、全データが新クラスターに移ったかを確かめた。

### 5.3 移行と運用で得た学び

Sven 氏が挙げた学びを、発表の順に整理します。

> 注意：以下は Sven 氏自身の失敗や気付きです。Elastic Cluster で pg_partman を使う場合や、移行・運用のチェックリストとして参考になります。

**移行について**

1. **本番の切り替え前にリハーサルをする。** チェック項目を決めておく。復元後に `ANALYZE` を実行し忘れたことがあった。統計情報が更新されないと、クエリプランナーが誤った計画を立て、クエリがいつまでも終わらなくなる。
2. **速度のために大きめの SKU を選び、移行後にスケールダウンする。** スケールダウンにはサポートチケットが必要なので、Microsoft サポートを巻き込む。
3. **コストに注意する。** テスト用クラスターは、停止してもその月の請求に積み上がる。
4. **ステージ間の構成を揃える。** 本番では高可用性を有効にしていたが、前段のステージでは有効にし忘れ、移行中に問題が起きた。
5. **細則を読む。** pg_partman と Elastic Cluster は互換だが、細かい条件がある。

**シャーディングとパーティショニング**

シャーディングは、テナント ID などのプライマリキー列で大きなテーブルを複数のバケットに分け、バケットをワーカーノードに載せる方法です。そこに、月単位などのパーティションが別の次元として加わります。同社は最初にバケット数を 128 にしましたが、すぐにその数は適切ではないと分かったと述べています（適正な数は発表では示されていません）。シャードごとにパーティションができるため、テーブル数は大きく増えます。

**学び（運用）**

1. **テーブル名の長さ制限：** 上限は通常 63 文字ですが、シャーディングとパーティショニングの併用では、ハッシュ化された ID のサフィックスが付き、約 20 文字を失う。自分の命名規則を 40 文字程度で検証しておくこと。リリース後期になって気付いた問題だった。
2. **メモリ枯渇（OOM）：** 本番運用の数週間後に発生した。メモリ使用量には日次のピークがあったが、アラートのしきい値内だったので正常と判断していた。週末を越えた月曜日に、クラスター全体がメモリ不足になった。
   - pg_partman では、パーティションを事前に作成するスケジュールが必要。新しい月（例：11 月）のパーティションがないと、データがデフォルトパーティションに入り、巨大なテーブルになる。
   - パーティションを作成すると、すべてのシャードに作られるため、Citus のメタデータキャッシュが膨らむ。一度に 3 つ作ったことで、キャッシュが 40 MB から 80 MB に増えた。このキャッシュは接続ごとに作られるため、2 倍になったことでクラスターが破綻した。
   - Sven 氏は、大手の最先端モデルのラボ（名称は発話されていません）でも、初期のグローバル障害が、パーティション作成に絡む同様の原因だったと述べています。
3. **ノード間の接続：** アプリケーションの接続数だけでなく、クラスター自身がワーカーノードに接続するため、その分も見込む。クエリが 1 ノードで済むか、複数ノードに及ぶかは、最初には分からないためです。この領域は改善の余地があり、Microsoft の製品チームと、TPS の向上とコネクションプーリングの効率化に取り組んでいます。
4. **プライマリキーの欠落とリバランス：** パーティションテーブルの 1 つでもプライマリキーが欠けていると、ブロッキングなリバランスが必要になる。リバランスは、テナントごとの成長差に応じてバケット間でデータを移す作業で、正しく設定されていれば、アプリの稼働中にダウンタイムなしで行える。しかし同社は 1 つ見落とし、先週末に 8 ノードへスケールアウトした際、アプリケーションを停止して、数時間かかるリバランスを実行した。リバランスの並列化には「ブラックボックス」の部分があり、透明性やドキュメントの改善を Microsoft に期待しています。製品チームは週末を通して待機してくれ、リバランスは成功した。

**開発者向けの学び**

データアクセス層の fluent interface（コードのサンプルは画面で示されました）で、アプリケーションのコードにシャーディング設定を書き、スキーマを初期化しています。発話で挙げられた設定の種類は、system management table、reference table、time series table です（表記は音声認識の都合で確定できません）。型安全で、たとえば時系列テーブルを 3 か月（四半期）単位でパーティション分割できます。約 90 人の開発者がこの層を使っており、どのときに reference table を使い、どのときにパーティショニングを使うかを、学びと一緒に共有して指導する必要があると述べています。

### 5.4 移行の成果と今後（Sven 氏）

- 切り替え前の数か月は単一ノードの競合が続いていたが、サポートチケットは最初の 1 週間で、再現しないとしてほぼ閉じられた。
- 平均ステートメント時間は 20 ミリ秒未満になった。さらに重要なのは、95 パーセンタイルが何分の一かに下がり、問題でなくなったこと。
- 手作業のクエリ最適化に費やす労力が減り、新機能の開発に回せるようになった。
- 新しい burstable SKU により、dev/test ステージでは、単一の Flexible Server より Elastic Cluster のほうが安く運用できた。

今後については、データ量は 2 年ごとに倍増する見込みで、エージェント型ワークロードが製品に加わるにつれ、需要がさらに高まると述べています。Elastic Cluster のスケールアウトの解決策を、一緒に考えたい、という呼びかけで締めています。Guy 氏は、協力関係に感謝すると応じました。

### 5.5 新しいコンピュート SKU（Guy）

顧客との取り組みから、フリートのモダナイゼーションに焦点を当てた機能が優先されているとして、次の SKU が紹介されました。

| SKU・機能 | 発表された内容 |
| --- | --- |
| Burstable V2 | AMD EPYC プロセッサーベース。同じ費用でより高速な CPU を使え、バーストクレジットの消費が減るので、バースト時の挙動が改善する。今週から利用でき、順次リージョンを拡大する。いずれ V1 はすべて V2 に移行される予定で、早めの移行を推奨している |
| Cobalt 200 | 今週発表された Azure の ARM ベースの SKU。初期のパフォーマンステストでは「見事な」性能。特にディスクにスピルしない、ほぼメモリ上で動くワークロードで、価格性能比が高い。試す価値があると勧めている |
| Confidential compute | すでに GA。保存時と転送時の暗号化に加えて、使用中のデータを暗号化でき、VM のメモリがダンプされてもデータは見えない。AMD と Intel の V6 をサポートする |
| Diskless SKU | 一時ディスクなしの SKU。価格ページで確認でき、「20〜30% 安い」と記憶していると話している。V5 と Intel / AMD V6 を提供。数週間以内に Intel / AMD V7 も対応予定で、372 vCPU または 2.8 TB までスケールできる。いずれもネットワークが高速で、全般に性能も向上する |

**diskless SKU の補足。** ワークロードがメモリに収まるなら、性能への影響はありません。結合などで一時ファイルがディスクにスピルする場合は、一時ディスクの代わりにアタッチされたマネージドディスクの IO を使うため、性能が低下します。OLTP や、メモリに収まる分析ワークロードなら、同じ性能をより低コストで得られるというのが説明です。

**ベンチマーク。** HammerDB の TPROC-H で、一時ファイルにあまりスピルしない分析ワークロードを、初期テストとして試した結果が示されました。

- 結果は CPU 世代（V4、V5、V6）別のグラフで、V4 には diskless SKU がない。
- 世代が進むほど性能が上がる。V3 や V4 の SKU を使っている場合は、新しい世代に上げることで性能が向上する余地があると説明している。
- V5 と V6 では、ディスクありとディスクなしの差は誤差の範囲。
- スケールファクター 10（約 10 GB のデータ、16 vCPU）、スケールファクター 30、さらに 64 CPU の大きな SKU でも、同じ傾向だった（スケールファクター 30 では V4 が少し健闘した、とも述べています）。

まとめとして、ワークロードがほぼメモリに収まる構成かを確認し、収まるなら diskless SKU で大きくコストを下げられると述べています。

### 5.6 ストレージとバックアップ（Danyal 氏）

**ストレージ。** 従来の SSD v1 は 32 TB まで、20K IOPS でした。今年前半に発表された SSD v2 は 80K IOPS です。今回新たに **Ultra Disk** が発表され、最大 400K IOPS、10 GB/秒のスループットに対応します。最も複雑なワークロード向けで、多くのユーザーには SSD v2 が適切かもしれない、とも述べています。

また、**ストレージの自動拡張（storage auto grow）** も発表されました。しきい値（例：ストレージの 90% 使用）を設定しておくと、自動でプロビジョニングして弾力的に拡張し、アプリ側にダウンタイムを生じさせないという仕組みです。

**イミュータブルバックアップ（パブリックプレビュー）。** ランサムウェア攻撃を想定した機能です。バックアップをサーバーのライフサイクルから切り離し、別のサブスクリプションに置きます。保持期間は延長のみで、短縮はできません。サーバーが削除されても、任意の時点に復元できます。コンプライアンスに重要で、DORA への準拠が必要な欧州の多くの国で求められると説明しています。

**長期保持 V2（LTR V2、パブリックプレビュー）。** V1 は 1 TB の上限があり、頻度は週次まででした。V2 は物理スナップショットベースで、最初のバックアップがフルバックアップ、以降が増分なのでコストを節約できます。スナップショットは完全に分離されたバックアップボールトに転送され、イミュータブルの設定もでき、復元は 1 クリックでできます。

### 5.7 PostgreSQL 19 とアップストリームへの貢献

Azure Database for PostgreSQL Flexible Server で PostgreSQL 19 が使えるようになり、今日の時点で PostgreSQL 19 へのアップグレードも可能になりました。昨年も、リリース当日に提供したと述べています（そのバージョン番号は聞き取れませんでした）。

オープンソースをホストする立場として、アップストリームへの貢献も重視しており、Microsoft には PostgreSQL 19 に貢献しているコミッターが約 20 人います。今回は PostgreSQL 19 のコミットの約 16% が Microsoft の社員によるものでした。顧客の課題を聞いて、修正を今後の機能に反映していく、という説明です。

### 5.8 Fabric の Database Hub（GA）とデモ

**Database Hub in Fabric** が一般提供（GA）になりました。Postgres、Azure SQL、Cosmos DB のフリート全体を 1 か所で監視できます。個々の Postgres サーバーに掘り下げたり、サーバーのパフォーマンスビューを見たりでき、監視から「行動につながる洞察」へ進むことを狙っています。FabCon でパブリックプレビューを発表して以来、多くのフィードバックを受けており、アラート機能も追加されたと説明しています。デモは 6 章に記載します。

さらに、次の 2 つが発表されました。

- **Database Hub agent skill：** 「Database Hub CLI」という名前の、Skills for Fabric に含まれるスキル。自然言語で、たとえば「Postgres 13（サポート終了間近）のサーバーは何台あるか」のように質問できる。ダウンロードして使うスキルなので、GitHub Copilot CLI や Cursor など、どこでも使える。
- **Database Agent（プレビュー）：** 現在は Visual Studio で利用でき、Fabric Database Hub には近く追加される予定。サーバー情報とメトリクスを持ち、問題を検知すると GitHub の issue を作成し、自動で GitHub Copilot に割り当てて、PR を作らせる。その PR をレビューすればよいので、何時間もの調査に頼らずに済む、という説明です。

### 5.9 その他の発表とリソース

- **Chaos Studio のゾーンダウンシナリオ：** Postgres インスタンスで、ゾーン障害をシミュレートして HA フェイルオーバーを起こし、アプリケーションにダウンタイムがなく、接続がシームレスに切り替わることを確認できる。
- **DMS の Oracle ソース対応：** Azure Database for PostgreSQL Flexible Server と HorizonDB を含む、任意の Postgres サービスへ移行できる。
- **VNet からプライベートエンドポイントへの移行：** これまでは複雑だった移行を、機能として提供する。
- **Elastic Cluster CDC（プレビュー）：** Elastic Cluster の水平シャード全体を、他の任意のデータベースへ論理レプリケーションできる。
- **エンジニアリングロードマップ：** 新機能の設計時に、提供予定時期とともに公開する。QR コードから参照でき、ロードマップの形成にフィードバックしてほしいとのこと。Guy 氏は、できるだけオープンに開発することが重要だと述べています。
- ブースでは、AMD が Postgres を題材に作ったゲームが紹介され、参加を呼びかけています（抽選の条件は聞き取り不明瞭です）。

## 6. デモ・手順

デモは、Danyal 氏による **Fabric Database Hub** のデモが 1 つだけです。「Let me do a little demo on this」と述べて始まっており、画面の細部は音声からは確認できないため、語られた範囲のみ書きます。

1. Fabric Database Hub の「estate」ページを開く。ここにサーバーが一覧表示される。今回は PostgreSQL に限定している。
2. 選択したスコープに基づいて、サブスクリプション内のサーバーがすべて表示される。セキュリティやパフォーマンスに関して検出された問題も一緒に一覧化され、問題で並べ替えられる。
3. 表の下のほうにスクロールすると、推奨事項が確認でき、上部から詳細を開ける。
4. テストが必要な場合は、そのまま Visual Studio で開ける。
5. 新しいインスタンスが必要なら、この画面から、情報を入力してプロビジョニングできる。CMK の設定など高度な設定が必要な場合は、Azure で確認するための直接リンクが用意されている。
6. パフォーマンスのセクションでは、Azure SQL、Postgres、Cosmos に絞り込める。フリート全体のディスク IOPS、パフォーマンス、メモリ、ストレージの状況が見え、リスクのあるサーバーが強調される。そのサーバーに直接ドリルダウンして、原因を調べられる。
7. 概要（overview）ページでは、フリート全体を確認でき、セキュリティ、パフォーマンス、最適化に関する推奨事項が表示される。

## 7. 注意点・発表者の気付き

- 本書 5.3 のとおり、Sven 氏が失敗として共有した点（ANALYZE の実行忘れ、ステージ間の HA 設定の不一致、63 文字のテーブル名制限、pg_partman のパーティション事前作成とメタデータキャッシュ、ノード間接続の見積もり、プライマリキーの欠落によるブロッキングなリバランス）が、このセッションで最も具体的な注意点です。
- Postgres 13 以下は有償の延長サポートになり、セキュリティ修正が提供されなくなります。
- diskless SKU は、メモリに収まらないワークロードで一時ファイルがスピルすると、性能が低下します。
- Burstable V1 は、いずれ V2 に移行される予定です。
- 発表では、Elastic Cluster のリバランスの並列化の透明性やドキュメント、コネクションプーリングの効率には、まだ改善の余地があると語られています。

## 8. 利用者にとっての利点

Wolters Kluwer の事例で語られた成果は次のとおりです。

- 単一ノードの競合が解消し、関連するサポートチケットが最初の 1 週間でほぼ閉じられた。
- 平均ステートメント時間が 20 ミリ秒未満になり、95 パーセンタイルが大きく改善した。
- 手作業のクエリ最適化が減り、新機能の開発に集中できる。
- 外部サービスパートナーを不要にできた（Flexible Server への移行時）。
- Azure SQL のエラスティックプール構成と比べて、Elastic Cluster はライセンス・運用の両面でコスト優位だった。
- dev/test では、burstable SKU により、Elastic Cluster を単一の Flexible Server より安く運用できた。

新機能に関して語られた利点は、diskless SKU のコスト削減（20〜30% と記憶していると発言）、Burstable V2 のバースト挙動の改善、Cobalt 200 の価格性能比、イミュータブルバックアップによるランサムウェア対策や DORA 対応などです。

## 9. まとめ

マネージドサービスへの移行はゴールではなく、ハードウェア、ソフトウェア、セキュリティ、アプリケーションの変化に合わせて見直し続けることで、コストと生産性をさらに改善できる、というのが全体の主張です。

Wolters Kluwer は、テナント ID を含むプライマリキー、pg_partman との互換性、Azure の運用への習熟といった前提を活かし、12 か月で Elastic Cluster に移行しました。成果は大きかった一方、ANALYZE の実行忘れやメタデータキャッシュの肥大、リバランスの見落としなど、事前に知っておくべき落とし穴も共有されました。

Microsoft 側の発表は、Burstable V2、Cobalt 200、diskless SKU、Ultra Disk、ストレージの自動拡張、イミュータブルバックアップ、LTR V2、PostgreSQL 19、Fabric の Database Hub（GA）と、Database Hub agent skill、Database Agent、Chaos Studio のゾーンダウンシナリオ、Oracle の DMS ソース対応、Elastic Cluster CDC、エンジニアリングロードマップの公開と多岐にわたります。
