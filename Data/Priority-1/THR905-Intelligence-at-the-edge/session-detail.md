# THR905 Intelligence at the edge

## 1. はじめに

このセッションは、**Fabrikam** という企業を題材に、IoT と AI を組み合わせて「現場に近いところで判断する」運用を、Azure IoT 関連サービスと Microsoft Fabric のデモで見せる 25 分のシアターセッションです。

デモは 3 つのパートで構成されます。トラックのファームウェアをクラウドから無線更新する場面、工場に新しい設備をつなぎ、AI で安全ドアの状態を判定してパレット搬送機の速度を自動制御する場面、そして集めた運用データを Fabric で統合し、エージェントに活用する場面です。発表者が最後に強調するのは、個々のデモではなく、その背後にある **「一貫した管理」「文脈を持つ運用データ」「産業向けインテリジェンス」という基盤**です。

## 5. 発表内容の詳細

### 5.1 トラックのファームウェアを無線更新する（Isabella 氏）

トランスクリプトは、Fabrikam のトラックが使うファームウェアについて、詳細を確認している場面から始まります。同じファームウェアを使っている他のトラックもあると分かります。幸い Fabrikam には修正版のバージョン 1.5 がすでにあります。Fabrikam は**統合された Azure IoT SDK**を使っているため、Azure Device Registry の**ソフトウェア更新**を使って、無線（over the air）で更新を送れます。

あわせて、左側のメニューに **groups** と **jobs** という新機能があると説明しています。ソフトウェア更新を含め、これらはすべて **premium** にあるとのことです。この画面では、あらかじめ「Seattle のトラック」のグループと、そのグループを対象にしたソフトウェア更新ジョブが作られています。

結果として、Fabrikam は**現地に人を送ることなく、単一の管理プレーンから**更新を配信しました。更新後のトラックのリソースは、安全なファームウェアバージョン 1.5 で動作しており、**ファームウェア分析（firmware analysis）**では重大な脆弱性がゼロです。

### 5.2 工場を Azure につなぐ（Sean 氏）

Sean 氏は、Fabrikam が新しい工場を Azure クラウドにつなぐ手順を見せます。使うのは **Digital Operations Experience Portal** です。OT（Operational Technology、運用技術）のユーザー向けに作られた専用の体験で、裏側では Fabrikam 全体を管理するのと同じ **Azure Resource Manager のグラフ**を使います。

インスタンスを開くと、クラスターの概要とヘルスメトリクスが見られます。さらに進むと、**カスタムコードなしに、クリックだけで**産業用機器を Azure IoT Operations のインスタンスにつなげられます。すぐに使えるエンドポイントとして、OPC UA、ONVIF、メディア、SQL Server などが挙げられています（トランスクリプトでは「ONVIV」と聞こえます）。

現場のネットワーク上にある機器は自動的に検出され、Azure Resource Manager に**管理対象のアセット**として登録されます。この産業用アセットは、通常のクラウドリソースと並んで Azure 上に表示され、全体をまとめて見られます。

アセットの登録後は、機器自体から**情報モデル（information model）**を自動検出できる場合もあります。これらのモデルは **schema registry** に保存され、エッジとクラウドの間で同期されます。

### 5.3 Sight Machine による統合情報モデル

情報モデルを自動検出できた機器と、モデルのない「生の」機器が混在している状況で、実在のパートナーである **Sight Machine** が Microsoft のプラットフォーム上でインターフェースやシステムを作り、Fabrikam が必要とする文脈をすべて含む、**拡張された情報モデル**を作る流れが紹介されます。

* Sight Machine は、Azure IoT Operations から Fabric に流れ込むすべてのデータにアクセスできます。
* **Azure Device Registry** は、Azure IoT Operations と連携して、エッジとクラウドで情報を同期するクラウドサービスです。パートナーはこれを通じて、検出されたアセットの情報モデルを読み取ったり、モデルを拡張・追加したりできます。
* Azure Device Registry には**オープンな API** があり、パートナーはそれを使ってアプリケーションの価値を大きく広げられます。
* Sight Machine の画面には、Azure に流れているデータが表示されています。アセットから届いた直近のメッセージペイロードも含まれ、ペイロードは Azure IoT Operations がマシンのすぐ隣で検出したフィールドやタグに従った形式です。
* Sight Machine は、現場のアセットを、収集・仕分けから、袋詰め、パレットの取り扱いまで、**工場全体の工程**として整理できます。これは単なるグループ化ではなく、物理的な工場を映した**統合情報モデル**です。
* 各アセットは異なるメーカー製で、異なるプロトコルで動き、互換性のない別々のシステムで制御されている場合があります。統合情報モデルが、それらをまとめ、アセット間のリンク、状態、関係、ライブデータの流れを示します。

### 5.4 安全ドアの追加と、エッジ AI での検知

文脈とデータがつながったところで、Fabrikam のデータサイエンスチームが、価値の高い機会を見つけます。**特定の機械式ドアが閉まっている限り、工場のパレット搬送機（pallet movers）の速度を上げられる**というものです。

データサイエンティストは、Sight Machine のソフトウェアが提案する最適化を利用して、情報モデルに次の変更を加えます。

* 新しい「safety door」の値（ドアのポリシー）を追加する。
* データの関係を変更し、いくつかの値の名前を変更する。
* 現場のエンジニアに通知し、現場のデータをこの新しい情報モデルの仕様に合わせて整形するよう依頼する。

新しい情報モデルは、Azure Device Registry の API を通じて公開（publish）され、現場の Azure IoT Operations に取り込まれます。情報モデルは、**W3C の Web of Things のオープン標準**に基づいており、システム同士が標準的な方法で連携しやすくなる、と説明しています。

問題は、**安全ドアにセンサーがなく、開閉が分からない**ことです。そこで Fabrikam のエンジニアは、低コストの PTZ カメラを設置し、新しい **Azure Local の小型フォームファクターのボックス**に接続します。このサーバーは **Foundry Local** の AI を実行し、センサーがなくて欠けているドアの開閉データを補うモデルを動かします。視覚検査（visual inspection）で複数のドアの開閉を判定し、Sight Machine がクラウドで作った拡張情報モデルに沿って、その結果をシステムに報告します。

> 補足：Sean 氏は、視覚検査が「人気のトップ 10 のユースケースの 1 つ」だと以前に話したと言及しています。その部分はトランスクリプトに含まれていません。視覚検査は、レガシーなシステムに高度な機能を加えるのに役立つ、とも述べています。

重要なドアが閉まっていると確認できれば、パレット搬送機は、データサイエンティストが見つけた**より速い 100 RPM**で安全に運転できます。

### 5.5 データを流す仕組み

エンジニアは、カメラを Azure IoT Operations の新しい **predictive AI inference connector** に接続します。開閉の分類用にトレーニングした **bring your own のカスタムモデル**が、Foundry Local 上で継続的に動きます。この種のモデルは比較的単純で、実装も簡単だと説明しています。

機械学習モデルの結果は**ローカルの MQTT ブローカー**に公開されるため、他のあらゆるデータと同じように扱って、処理や反応ができます。

さらに、視覚検査のデータを、ローカルで動く**小規模言語モデル**にも、Azure IoT Operations の新しい**内蔵 MCP サーバー**を通じてつなぎます。これにより、ローカルのエージェントが OT エンジニアと自然言語でデータについてやり取りし、ドアが開いていることが問題かどうかを判断できます。

新しい Azure IoT Operations のリリースでは、エンジニアは AI を使って、ローカルのデータを新しい情報モデルに合わせて整形する **data flow の変換（transformation）** の構築も支援してもらえます。必要な変換を自然言語で説明すると、複雑なデータパイプラインを数分で組み立てられる、という説明です。

### 5.6 アラートと自動化

データが Azure に流れ始めて、Fabric と Sight Machine に入ると、**Dynamics 365** との統合が働き、Dynamics 365 にチケットが開き、**Teams** に問題の全文脈つきのアラートが届きます。OT エンジニアには、ドアを閉める、搬送機の速度を手動で下げる・上げる、といった複数のチケットが届きます。手動の対応では、速度の引き下げが遅れると危険になりうるため、エンジニアは **Azure IoT Operations の management actions** を使い、搬送機を自動で減速させる自動化を追加します。

エンジニアが設定した data flow のルールは次の 2 つです。

1. 特定の安全ドアが開いていると、パレット搬送機を **50 RPM** に落とす。
2. 重要な安全ドアがすべて閉まると、**100 RPM** に戻す。

結果として、重要な安全ドアが開いたままになると、速度が 100 から 50 RPM に変わることが、現場で確認できます。工場は、データサイエンティストが見つけた 100 RPM で通常運転できます。エンジニアに届く Teams のアラートは、ドアが開けっぱなしのときだけになり、速度を手動で変える必要はなくなりました。

### 5.7 Fabric real-time intelligence で運用データを統合する（Isabella 氏）

Isabella 氏のパートに戻り、ここまでの「機器の管理、問題の検出、アクション」に続いて、運用データを 1 か所に集める部分を説明します。

* **Fabric real-time intelligence** で、Azure IoT Operations と IoT Hub の両方のデータストリームを、同じ **event house** にルーティングし、Microsoft Fabric 内に共通のデータ基盤を作る。
* その上にカスタムのレポートとダッシュボードを作れる。運用マネージャーは、トラックの速度や位置を、工場で起きていることと並べて見られる。特定のトラックをクリックすれば、収集量の推移、メンテナンススケジュール、他のトラックの状況、注意が必要なものを確認できる。
* 工場のマネージャーは、設備のダウンタイム、稼働率、最も多い故障の種類などの専用ビューを持てる。

これにより、Fabrikam は運用の**統合ビュー**を得ます。

### 5.8 セマンティックモデル、オントロジー、エージェント

同じデータに、さらに文脈を持たせる話が続きます。

1. Sight Machine のデータを使って、データと関係を整理する**セマンティックモデル**を作る。
2. さらに**オントロジー**を作り、データを、機械やトラックなどの現実世界の対象に対応づける。ライブデータをそれらのエンティティに結びつけられるため、文脈が実際に起きていることをリアルタイムに反映する。
3. これにより、エージェントが企業全体の文脈を得て、より良い判断ができる。

運用データ、関係、リアルタイムの文脈がそろうと、それが**産業向けインテリジェンスの基盤**になり、人とエージェントが運用全体を推論し、パターンを見つけ、事業の改善を続けられる、という説明です。

例として、Fabrikam のサイトマネージャー（トランスクリプトの表記は "Sites Manager"）が、新しい **Fabric IQ MCP** を使って **Cowork** を利用する場面が紹介されました（画面の詳細は音声からは分かりません）。Cowork は文脈全体を見渡してパターンを見つけ、推奨案を作ります。**マネージャーが常にコントロールを持ち**、内容を確認して承認してから先に進みます。承認後は、次のことを数秒で行ったと述べています。

* Microsoft Word で計画を作成する。
* 従業員に送るメールの下書きを作る。
* 情報モデルを JSON で更新する。
* プレゼンテーション資料を作る（提示先はトランスクリプトでは「Lt.」と聞こえ、音声認識の都合で表記が確定できません）。

## 6. デモ・手順

このセッションは、画面を見せながら進むデモ形式です。「I'll click and run the job」「we'll refresh again」「Notice on the right」といった発話があります。音声のみのため、画面上の操作は語られた範囲に限ります。

### 6.1 デモ 1：トラックのソフトウェア更新（Isabella 氏）

1. トラックのファームウェアの詳細を確認し、同じファームウェアを使う他のトラックがあることも確認します。
2. 修正版のバージョン 1.5 があり、統合された Azure IoT SDK を使っているため、Azure Device Registry のソフトウェア更新で配信できると説明します。
3. 左側に **groups** と **jobs** があります。あらかじめ作成済みの Seattle のトラックのグループと、そのグループを対象にしたソフトウェア更新ジョブがあります。
4. ジョブを実行します（「click and run the job」）。
5. job runs を開いてステータスを確認します。ジョブが有効になると、トラックが更新を確認し、互換性があるので更新を取得してダウンロードを始めます。
6. 左側のジョブの画面で進捗を追跡します。数秒後に再読み込みすると、**成功（succeeded）** になります。
7. トラックのリソースに戻ると、安全なファームウェアバージョン 1.5 が動作しており、ファームウェア分析では重大な脆弱性が 0 です。次の配送に出られる状態になりました。

### 6.2 デモ 2：工場の接続と、安全ドアによる速度制御（Sean 氏）

1. Digital Operations Experience Portal でインスタンスを開き、クラスターの概要とヘルスメトリクスを確認します。
2. 産業用機器をクリックだけで Azure IoT Operations インスタンスにつなぎます。機器は自動で検出され、アセットとして登録されます。
3. Sight Machine の画面で、アセットの直近のメッセージペイロードを確認し、アセットを工程ごとに整理して、統合情報モデルを作ります。
4. データサイエンティストが safety door の値を追加し、データの関係と名前を変更します。新しいモデルは Azure Device Registry の API で公開され、追加された safety door がモデルの下の方に表示されます。
5. カメラを predictive AI inference connector に接続し、Foundry Local 上のカスタムモデルを動かします。画面の右側には、パレット搬送機の現在の最大速度として 100 RPM が表示されています。
6. カメラが工場を走査してドアの開閉を判定します。ローカルのエージェントが、開いているドアが問題かどうかを判断します。
   * 最初に確認したドアは問題がないとエージェントが判断します。
   * 閉まっているドアも問題ありません。
   * 開いているドアが見つかると、速度を **50 RPM** に落とす必要があると判断します。
   * システムが動作することを確認し、エンジニアは、求められたデータを Azure とデータサイエンティストに送る設定ができる状態になります。
7. エンジニアは、新しい Azure IoT Operations のリリースで AI を使い、data flow の変換を作ります。自然言語で変換を説明できます。
8. データが Azure に流れると、Dynamics 365 のチケットと Teams のアラートが発生します。
9. management actions を使った data flow のルールを設定し、安全ドアが開いたら 50 RPM に、すべて閉まったら 100 RPM に戻します。現場で 100 から 50 RPM に切り替わることを確認します。

### 6.3 デモ 3：Fabric と Cowork（Isabella 氏）

発話で確認できる範囲は 5.7 と 5.8 のとおりです。event house へのルーティング、ダッシュボードの閲覧、Fabric IQ MCP を使った Cowork による推奨案の作成と承認、Word・メール・JSON・プレゼン資料の作成が示されました。具体的な操作手順は、語られていません。

* 安全ドアにセンサーがない場合は、カメラと視覚検査 AI で補うという解決策が示されています。
* ソフトウェア更新、groups、jobs は **premium** にあると説明されています。
* Sight Machine は「real life partner（実在のパートナー）」と紹介されています。
* 具体的なリリース時期、価格、制限事項などは、発表では触れていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* 現地に人を送らずに、単一の管理プレーンからデバイスにソフトウェアを更新できる。更新後は、ファームウェア分析で脆弱性の状況を確認できる。
* 産業用機器を、カスタムコードなしにクリックで接続できる。産業用アセットを、通常のクラウドリソースと並べて見られる。
* 異なるメーカー・プロトコルの機器を、統合情報モデルでまとめて扱える。
* センサーのない設備に対しても、低コストのカメラとエッジ AI で、欠けたデータを補える。
* 判定結果が MQTT ブローカーに流れ、他のデータと同じようにアクションに使える。
* ルールの自動化により、搬送機を 100 RPM で通常運転しつつ、ドアが開いたときだけ 50 RPM に減速できる。エンジニアは、アラートへの手動対応が不要になった。
* 運用データを Fabric に統合して、トラックと工場を 1 つのビューで見られる。文脈（セマンティックモデル、オントロジー）を持たせることで、エージェントがより良い判断をできる。

なお、顧客名や数値による導入効果は、発表では紹介されていません。

## 9. まとめ

このセッションは、Fabrikam という企業の運用を例に、**管理、運用データ、インテリジェンス**の 3 つを 1 つの基盤にまとめる考え方を示しました。トラックのソフトウェアを無線で更新し、工場の設備を Azure IoT Operations につなぎ、Sight Machine で統合情報モデルを作り、エッジ AI で安全ドアを判定して搬送機の速度を自動制御し、Fabric でデータを統合してエージェントに活用させる、という流れです。

発表者は、持ち帰ってほしいのは個々のデモではなく基盤であるとし、IoT Hub と Azure IoT Operations の今後の投資を通じて、クラウドとエッジにまたがる、ガバナンスの効いたクローズドループのエージェント運用を目指すと述べています。
