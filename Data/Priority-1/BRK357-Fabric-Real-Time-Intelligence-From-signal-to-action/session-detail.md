# BRK357 Fabric Real-Time Intelligence: From signal to action

## 1. はじめに

このセッションは、Microsoft Fabric の Real-Time Intelligence（以下 RTI）を使って、リアルタイムに発生するデータ（シグナル）を取り込み、分析し、人や AI エージェントのアクションにつなげるまでを、一通り紹介するものです。タイトルの "From signal to action" のとおり、発表は「ストリームでデータを取り込む」「分析する」「アクションを起こす」の 3 つの段階で構成されています。

前半では、エネルギー事業を営む Transgrid Energy の CTO が、Fabric と RTI を導入して得られた効果を語ります。後半では、バルセロナのスタジアムの入場ゲート運用という想定シナリオを題材に、Event Stream、Eventhouse、リアルタイムダッシュボード、Activator、Operations agent を順に見せています。あわせて、今週の Ignite で発表された新機能が、スライドで駆け足で紹介されます。

リアルタイムデータやイベント駆動のアーキテクチャを、Fabric 上で組みたい方が、RTI の全体像と最新機能を把握するのに向いた内容です。

## 3. 何に関する発表か

### 3.1 背景：なぜリアルタイムは難しかったのか

Kim 氏は、運用（operations）の意味は組織や業界ごとに違う、と話を始めます。工場や配送で物を動かす物理的な運用もあれば、顧客対応（いつ連絡し、いつエスカレーションするか）や、ソフトウェア（適切なレコメンドや、キャパシティのスケールアップ）もあります。こうした日々の判断の多くで、人がダッシュボードを見つめて判断を待っているところに大きな機会がある、という見方です。

これまでイベント駆動やリアルタイムのアプローチが難しかった理由として、次の 3 点を挙げています。

1. 技術的に難しく、管理するインフラも、組み合わせるソフトウェアも多い。
2. データがクラウド、オンプレミス、デバイスなど、あちこちに散らばっている。
3. その結果、コストが高く、見合わなかった。

さらに、インフラとソフトウェアを作り込んだ後も、結局は人がダッシュボードを見て判断するため、反応できる速さに限界があり、リアルタイムの利点が失われました。そのため、リアルタイム関連のプロジェクトは、立ち上がる前に失敗することが多かった、と説明しています。

## 5. 発表内容の詳細

### 5.1 Fabric と RTI の位置づけ

Kim 氏は Fabric を、Office のようなデータツールのスイートにたとえています。Office では Word、PowerPoint、Excel がそれぞれの作業に最適化されつつ、ユーザー体験（スペルチェックやコピー＆ペーストなど）と、基盤（OneDrive や SharePoint でのファイル共有、管理とガバナンス、支払い）を共有しています。Fabric も同様に、データ統合、データウェアハウス、リアルタイム、BI といったツールがそれぞれのタスクに最適化されていて、次の要素を共有しています。

- データをシステムに取り込む方法
- 開発から、テスト、本番への移行
- ワークスペースによるプロジェクト管理
- OneLake にすべてのデータを 1 つの開放形式で保存する基盤
- ガバナンスとセキュリティ、そして支払いも一元化されていること

RTI は、大企業（Fortune 500）で広く使われている Azure のサービスを、Fabric に統合して実装しやすくしたものです。OneLake とリアルタイムコネクタの上に作られており、どのクラウド、場所、デバイスのデータにも、データ移動なしでつなげます。構築が簡単になり、コストが最適化され、セキュリティとガバナンスが組み込まれていて、サービスを個別に組み合わせる必要がありません。Fabric のキャパシティ上で最適化できる点も利点として挙げています。

基盤となる Azure サービスは、毎日テラバイト、ペタバイト規模のデータを取り込む規模と信頼性を持つ、と説明しています。比較としては、Confluent と Snowflake を AWS 上で動かして構築したソリューションよりも、**12 倍高速で、コスト効率も良い**と述べています。コスト効率の数値は "37 times a percent" と聞こえ、倍率なのか割合なのか、音声認識の都合で確定できません。

利用も増えており、RTI の利用量は昨年の 3 倍で、特定の業界に限らず全業界に広がっているとのことです。

### 5.2 顧客事例：Transgrid Energy

Tony 氏は、Transgrid Energy を、データセンター向けのサービスとクリーンエネルギー関連のサービスを提供する企業と紹介しています。顧客が電力を確保し、運用の経済性を改善するのを支援しており、データセンターからテレメトリを集めて AI アルゴリズムを動かし、インフラを最適化するための推奨を毎日提供していると話しています。「トークン / ワット」や、消費電力の最適化、電力網への負荷の低減などが例に挙がりました。

会社の規模は従業員約 200 人で、従業員数は前年比で 300% 成長しています。市場としては、エネルギー分野の主要な市場（発話では "Kaizo, ERCOT, PGM" などと聞こえます。音声認識の都合で表記が確定できません）で事業を行っていて、特にデータセンター分野の成長が大きく、需要に追いつくのが難しいほどだそうです。

**課題**：小さな成長中のチームで、自分たちで基盤のコードを書かずに済むプラットフォームが必要でした。素早く作りながら、セキュリティと信頼性（特にエネルギーとデータセンター分野では極めて重要）を満たす必要があります。データセンターから出る大量のテレメトリを、整理して適切な場所にルーティングすることも重要でした。

**導入の経緯**：Tony 氏が chief architect として入った当時は、異なるクラウド上に、サイロ化した複数のサービスと、手作りのナレッジグラフなどが散らばっていました。動いてはいたものの、保守、進化、セキュリティの確保が、時間とともに難しくなると感じたそうです。そこで Fabric を早期に導入し、Microsoft のチームと密に連携して、オントロジーを使ったメダリオンアーキテクチャに RTI を取り入れました。データセンター向けのオントロジー **Watt Schema** を自社で作り、オープンソース化しています（watschema.org と話しています。音声認識の都合で綴りが確定できません）。これを Microsoft の ontology サービスと重ね、データセンターからのデータの一貫した「玄関口」を作りました。データは RTI のメダリオンアーキテクチャ上に保存され、1 つの一貫したプラットフォームと、その下の OneLake になりました。

**効果**：

- カスタムサービスと、外部のグラフデータベースを廃止できました。データセンターのあらゆる要素のグラフを手作業で保守するのは大変で、ミスも起きやすかったそうです。ナレッジグラフが安定したことが大きいと話しています。
- メダリオンアーキテクチャの各層のデータにアクセスでき、さまざまな分析ができるため、より良い判断ができるようになりました。
- 例えばアラームのように、すぐに見たいものは RTI でストリームを監視します。一方で、バッチデータは AI で分析して、アラームで見るべき新しいルールを作りました。そのルールに基づき、RTI に流れるリアルタイムのデータを監視してアラームを出す、という流れです。Kim 氏はこれを「フライホイール」と呼んでいます。
- **40 個の別々のサービスを 1 つのプラットフォームに統合**できました。以前は、サービスごとに CI/CD や配布が異なり、管理のために、脆い積み上げ（"house of cards"）のような複雑さがあったそうです。統合により、分析だけでなく、安全で自信を持ったデプロイや問題の検出、すべてのデータを 1 か所に置けることなどの利点が生まれ、OneLake があることで将来の分析や AI の選択肢も広がる、と述べています。

**VPP（仮想発電所）の例**：姉妹会社の QCells（Hanwha グループ）が、太陽電池を製造し、住宅や商工業のお客様に販売しています。そうした太陽電池とバッテリーの集合である仮想発電所（VPP）から電力を電力網に売り戻せます。この VPP のポータルのデータを、リアルタイムの問題分析のために保存しています。住宅では、インターネットが切れたり停電したりしても商用のバックアップ系がないため、何が起きたかを秒単位で把握し、データの再取得などのアクションを起動できます。ライブのフリートビューも得られ、これらは Azure 上で動いています。

数値として、**16,000 の太陽光・蓄電池のお客様**がおり、**time to market を 50% 短縮**し、運用上のオーバーヘッドも下げたと説明しています。

**アドバイス**：Tony 氏は、Fabric と RTI を導入する人に対して、次のように述べています。

- メダリオンアーキテクチャとリアルタイムインサイトを慎重に設計する。それがほぼすべての基盤になる。
- データの使い方を考える。オントロジー経由で入ってきたからといって、1 か所に保存する必要はない。OneLake、Event Stream、リアルタイムインサイトなど、Fabric の部品を用途ごとに使い分けられる。それが AI 基盤の成果を高める。

Tony 氏は最後に、エネルギーフローと VPP の製品が Fabric で恩恵を受けており、今後も Fabric とともに進化させる、と締めています。

### 5.3 デモの題材：バルセロナのスタジアム

ここから後半です。Kim 氏は、実装の方法を取り込み、分析、アクションの順に見せ、継続的な改善につなげると説明しています。題材はバルセロナのスタジアムで、Amanda 氏の紹介に続いて、動画で場面が説明されます。

試合当日、数万人のファンが到着し、運用チームの目標は「全員を安全に、キックオフに間に合うようにゲートを通す」ことです。状況は急速に変わります。試合当日運用の責任者（動画では Lucia という名前で、姓は音声認識の都合で確定できません）は、スタジアム内のあらゆる状況をまとめたリアルタイムダッシュボードを持っていますが、1 日中グラフを見ていたいわけではなく、何かが起きたときに知りたい、という設定です。

そこで、Operations agent が通知を出します。複数の列車がほぼ同時に到着し、約 15,000 人のファンが Gate 14 にほぼ同時に着く見込みで、ゲートはまだ過負荷ではないものの、容量を超える可能性がある、という内容です。エージェントは、比較的空いている別のゲートから人員を移し、新しいレーンを開けることを提案します。その後も状況を監視して、対処が効いたかを確認できます。ファンは違いに気づかず、スムーズに入場でき、運用チームは速く判断できた、というのがこの例の要点です。

### 5.4 取り込み：Event Stream

Amanda 氏と Kim 氏は、イベントベースのシナリオはあらゆる業界にある、と説明しています（スタジアムへの入場、不正検知、システムの変化、小売店への来店、フライトの運用など）。AI の時代にはエージェントがイベントに基づいて動き続けられるため、重要性はさらに増します。

ストリーミングデータの取り込みは、以前は複雑で、新しいソースへの対応も常に増やしている、という説明です。Event Stream では、実質どこからでもデータを取り込めます。デモでは次のことが語られました。

- 新しいコネクタとして、Mir database CDC（音声認識の都合で表記が確定できません）や SAP Datasphere などが挙がった。
- このデモでは、データを Azure Event Hubs に置いており、**ショートカット**でそのまま取り込める。データ移動も、コードも、追加コストも不要で、設定すればセキュリティも引き継がれる。大きな移行プロジェクトなしに RTI で価値を出せる。
- データを接続すると、生のイベントがすべて見える。そこで Event Stream を編集すれば、変換、クリーニング、整形ができる。以前はコードを書く必要があったが、ドラッグ＆ドロップとクリックでできる。独自の処理が必要なら **SQL コードオペレーター**も使える。
- 宛先には、Activator のアラート、ビジネスイベント、レイクハウスなどを指定できる。
- デモではレイクハウスに、ゲートの混雑度（gate pressure）を追跡するための SQL のカスタム計算を追加した。
- 1 つのストリームから複数の経路を作れる。交通チームには、必要なデータだけをフィルターして専用のストリームに流し、分析チームには、生のイベントをすべて Eventhouse に流した。結果として、**1 つのストリームから 3 つの宛先**（レイクハウス、交通チーム向けストリーム、Eventhouse）に流れる。
- データはリアルタイムでプレビューできる。

### 5.5 取り込みの新機能（Kim 氏による解説）

Kim 氏は、多くの発表があるため駆け足で説明し、詳細は最後に示すブログで確認してほしい、と話しています。Event Stream 関連は次のとおりです。

- **コネクタの更新**：Oracle を追加し、複数の新しいコネクタが GA になった。
- **プライベート接続**：ストリーミングデータの通信を閉域化し、パブリックインターネットを遮断したい、という要望への対応。認証の改善も進行中。
- **Event Stream のショートカット**：既存の Azure 資産の上に、データ移動も追加コストもなく新しいソリューションを立ち上げられる。セキュリティとガバナンスは組み込み。
- **IoT Hub のネイティブなルーティングエンドポイント**：IoT Hub を使っているお客様は、大きな移行なしに RTI を始められる。
- **コピージョブとの双方向ストリーミング**：ストリームを取り込んでコピージョブを起動したり、Fabric のコピージョブがストリーミングイベントを起動したりできる。バッチとストリーミングの両方の良いところを使える。
- **イベントスキーマセットによるスキーマレジストリ**：スキーマの「契約」を設定してデータ品質を保ち、正しいデータが正しい場所に届き、スキーマのずれ（drift）でデータが壊れるのを防ぐ。スキーマに基づく振り分けも、ドラッグ＆ドロップで設定できる。
- **リファレンスデータ**：OneLake のデータを、ストリームと結合して判断に使える。例として、ストリームが来たときに、その顧客の売上や注文履歴を見てから、不正かどうかを判断する。

### 5.6 分析：Eventhouse、リアルタイムダッシュボード、Fabric Maps

運用データは複雑で、ストリーミングでは細部が重要です。集計すると、失敗したイベントや異常値など、行動すべき対象が見えなくなることがあります。そのため、大規模でも必要な性能で、詳細を見られること、「今」何が起きているかを、意味のある場所（地図）で見られること、スキーマが絶えず変わる構造化・非構造化データを調査できることが必要だ、と説明しています。そこで使うのが Eventhouse、リアルタイムダッシュボード、Fabric Maps です。

デモで語られた内容は次のとおりです。

- ダッシュボードには情報が多いため、**AI insights** を使う。これは AI が生成したクエリで、データの異常を探し、どこに注目すべきかを教えてくれる。
- **Fabric Maps** で、ゲートの色分けにより、健全な状態（緑）と問題のある状態（赤）を見分けられる。
- Eventhouse の画面では、データがどのソースから来て、どこにルーティングされているかを、ライブで確認できる。デモでは、直近 1 時間に取り込まれた分に絞られ、ストリームからテーブルに流れる様子が見える。
- Eventhouse には、Lakehouse からのショートカットでバッチデータ（改札口の数、最大収容人数、地図上の位置など、あまり変わらないデータ）も取り込まれている。履歴データとリアルタイムデータを並べ、ある改札口の通常の混雑度と現在の混雑度を比較して判断できる。
- **クエリ アクセラレーション**により、キャッシュとインデックスが作られ、ライブデータと同じ速度で併用できる。
- 赤くなっている Gate 14 を拡大し、リアルタイムダッシュボードの **Copilot 連携**で質問する。例として「スタジアムのライブデータが、近くの駅のデータとどう関連するか」と尋ねている。チャートがすぐ生成され、さらに仮説、置いた前提、データで起きていることの要約が示される。
- Eventhouse のデータは、**ontology** にもつながっており、ゲートが人や交通、主要な指標とどう関係するかを、より広いビジネスの文脈で理解できる。

### 5.7 分析の新機能（Kim 氏による解説）

- **Fabric apps から RTI データへのコネクタ**：Fabric apps が GA になったことに触れ、ガバナンスされた Fabric のデータの上に、「バイブコーディング」で独自アプリを作れるようになった。RTI はその標準の一部になっている。
- **アクセラレートされたショートカット**：OneLake のデータを使った Eventhouse の性能向上。データを 1 度 Fabric に置いて、適切なエンジンで再利用する「ゼロコピー」の考え方。Spark やデータ統合で取り込んだデータに対し、Eventhouse でも大規模分析ができる。
- **Eventhouse の粒度の細かいテーブル共有**：Eventhouse 全体を公開せずに、必要なものだけをコピーなしで共有できる。
- **Eventhouse のキャパシティプランナー**：支出やキャパシティの見積もりに関する要望への対応。シナリオプランニングで、性能とコストのトレードオフを見て、見積もりを得られる。
- **リアルタイムダッシュボードの強化**：より密度の高いビジュアル、より多くのビジュアルの選択肢、より豊かなビュー。さらに、Copilot によるダッシュボードの作成。
- **AI ネイティブなカスタムタイル**：入ってくるデータに基づいて可視化し、AI が適応することで、ワークフローや利用者ごとに合わせられる。

### 5.8 アクション：Activator と Operations agent

Kim 氏は「森で木が倒れても、誰も聞いていなければ音はするのか」というたとえを引いて、データを取り込み、ダッシュボードを作っても、アクションを取らなければ意味がない、と述べています。アクションの柱は 2 つです。

- **Activator**：状況が変わった瞬間にアクションを設定する。イベントが起きた時と場所で行動できる。
- **Operations agent**：イベントが起きている間に、エージェントが判断し、問題が起きる前に知らせる。これにより、より先回りして判断できる。

デモで語られた内容は次のとおりです。

1. 先ほどの Eventhouse で、その上に ops agent（Operations agent）を作ると指定する。Eventhouse への接続が作られ、エージェントのナレッジベースとして使われる。
2. **エージェントの指示**を与える。どのデータを見るか、何を観察するかなど、どう考えて動くべきかを伝える。
3. エージェントが実行できる**アクション**を紐づける。このデモでは、人員の再配置と、新しいレーンの作成。
4. 指示、ナレッジ、アクションの 3 つから、エージェントは自分の **playbook** を作る。人間が取る判断のロジックを渡し、Operations agent と一緒に設定する形になる。
5. エージェントが提案を出すと、深掘りするための情報が示される。デモでは「承認する前にさらに調査して」と依頼し、エージェントがデータを調べて、判断に必要な文脈を返した。
6. Operations agent の画面では、エージェントが選んだ動作をすべて確認できる。誰にメッセージを送るか、どのアクションを取るか、誰が承認するか、さらにトークン数とレイテンシも見える。これを見ながら改善を続けられる。
7. 信頼が積み上がったら、次回から自動で実行する設定にすることもできる、と補足されている。
8. エージェントの性能を監視する方法として、**ビジネスイベント**を使う。デモでは、先ほどのリアルタイムダッシュボードの上で Activator を使い、状態が変化するたびに（悪化したときと、Operations agent の推奨後に改善したとき）ビジネスイベントを発行している。発行されたものは **real-time hub** で確認でき、他の部門も活用できる。

Kim 氏は、ビジネスイベントの意味を次のように説明しています。例えば、改札口が回転しているというデバイスのイベントがありますが、本当に知りたいのは「改札口の混雑が高いか」「どの頻度で回転しているか」です。そこで、イベントをビジネスが理解できるものに引き上げ、他の人が購読してアクションを取れるようにします。

> 補足：デモの画面の細部（ボタン名や入力値など）は、音声からは確認できません。上記は、発話で語られた範囲だけをまとめています。

### 5.9 アクションの新機能（Kim 氏による解説）

- **Real-time hub での Activator ルールの一覧**：すべての Activator ルールを 1 か所で見て、ガバナンスし、オン / オフを管理できる。
- **ビジネスイベント**：real-time hub で、関心のあるビジネスイベントを見て、新しいものを購読し、その場で共同作業できる。
- **Operations agent**：自律的に動ける「仮想的なチームメンバー」と位置づけている。
- **Operations agent の investigation**：エージェントが何を見ているかを理解でき、完全な調査内容を確認して、信頼を築ける。

Kim 氏は、ここまでを「データのストリーミング、分析、行動」をつなぎ、エージェントが時間とともに良くなる、継続的な改善のループだと総括しています。

## 9. まとめ

RTI は、ストリームの取り込み（Event Stream）、分析（Eventhouse、リアルタイムダッシュボード、Fabric Maps）、アクション（Activator、Operations agent）を、Fabric の 1 つのプラットフォーム上でつなぐ仕組みです。OneLake とショートカットにより、データ移動なしで既存の資産を活用できる点が、繰り返し強調されました。

Transgrid Energy の事例では、40 のサービスの統合、time to market の 50% 短縮などの成果が語られました。デモでは、スタジアムの入場ゲートを題材に、取り込みから分析、エージェントによる先回りの提案までが示されました。

始めるには、無料の「Real-Time Intelligence in a day」ワークショップと RTI Featured Partners が案内されています。今週の発表の詳細は、ブログで確認できます。
