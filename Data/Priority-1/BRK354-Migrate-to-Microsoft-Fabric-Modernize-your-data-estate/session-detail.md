# BRK354 Migrate to Microsoft Fabric: Modernize your data estate

## 1. はじめに

このセッションは、Azure Data Factory（ADF）や Azure Synapse を使っている方に向けて、「なぜ Microsoft Fabric へ移行（アップグレード）するのか」と「どうやって移行するのか」を説明するものです。前半は Fabric Data Factory への移行、後半は Fabric Data Warehouse と Fabric の Spark への移行が中心です。

発表では、移行を支える 3 つの柱（製品内ツール、Microsoft の支援プログラム、パートナー）、ADF の「View in Fabric」、Synapse dedicated SQL pool 向けの移行アシスタント、そして顧客事例と性能・コストの数値が紹介されました。なお、移行を「単なる引っ越し」ではなく、アーキテクチャ刷新の機会として捉える顧客事例が繰り返し語られている点が、全体を通した特徴です。

## 5. 発表内容の詳細

### 5.1 背景：AI-ready なデータ資産と Microsoft IQ

前半の登壇者は、前日のキーノートに触れつつ、AI が至る所に組み込まれる転換点にあると述べています。そして「エージェントをどう信頼でき生産的にするか」という問いに対し、Microsoft IQ と、その一部である Fabric IQ が、エージェントに知識とコンテキストを与えるプラットフォームだと説明しました。

Microsoft IQ の構成要素として、発表では Work IQ、Fabric IQ、Foundry IQ、Web IQ が挙げられ、パートナーがサードパーティ製の IQ を組み込めることもキーノートで示されたと述べています。Fabric IQ については、このカンファレンスで多くのセッションがあるとのことです。

また、Fabric が「CIO が chief integration officer（統合担当役員）にならなくて済むようにする」ための統合プラットフォームである、という CxO との会話の話も語られました。

### 5.2 移行を支える 3 つの柱

移行を確信を持って進められるよう、次の 3 つの柱が示されました。

1. **製品に組み込まれたツール**：Data Factory、Data Warehouse、Spark の各チームが、数クリックで既存の資産を Fabric に移せるツールを用意している
2. **Microsoft のエキスパートによる支援**：ベストプラクティスの共有や、最初のアセスメントまで一緒に行う（Cloud Accelerate Factory）
3. **パートナーエコシステム**：無料のアセスメントを行うパートナーがおり、条件を満たす場合は、アップグレードの一部が資金面で支援されるケースもある

**Cloud Accelerate Factory** は、Microsoft 内のチームで、「ゼロコストのデプロイ」で Fabric への移行を立ち上げる支援をします。Microsoft のエキスパートがエンジニアリングチームと密に連携しており、joint delivery（共同提供）の形で Fabric サービスのデプロイを支援するという説明です。Fabric パートナーを自分で選んでもよく、社内の開発チームと進めることもできます。典型的な進め方として、目標と達成したいビジネス成果の確認、プロジェクトの前提条件の確認、合意できるスコープの確定、共同での実行、移行成功の検証、という流れがスライドで示されました。

**Fabric パートナーエコシステム**については、Fabric の認定を受けたパートナーが、独自の IP と専用に作り込まれたツールを持ち、最後の難所（last mile）まで支援すると説明されています。フォームから申し込めば Microsoft から連絡し、必要ならパートナーを紹介する、とのことです。パートナー側の参加も歓迎されています。

### 5.3 Fabric コミュニティの広がり

発表では、Fabric が一般提供（GA）されてからの 3 年間の成長についても触れられています。Fabric の認定資格は約 10 万件に達し、Microsoft の歴史の中でも最も速く伸びた認定資格の一つだと述べられました。コミュニティ、ユーザーグループ、ISV パートナーとの連携に感謝する場面でもありました。

### 5.4 Fabric Data Factory の概要

Fabric Data Factory は、「ingest（取り込み）、transform（変換）、orchestrate（オーケストレーション）」を行い、データプロダクトを目的の出力先へ届けるデータ統合サービスで、OneLake の上で動作します。さらに AI の面では、メタデータ駆動のパターンへ進化させており、パイプラインの開発生産性と提供速度を高めると説明されています。主な構成は 3 つです。

**データ移動（copy job）**
- ペタバイト規模のデータ移動を、Microsoft のクラウドを含む複数のクラウド間で行えます。
- FabCon Barcelona で、リアルタイムのデータ統合が発表されました。イベントストリームと連携し、「リアルタイム→バッチ」「バッチ→リアルタイム」のどちらも扱えます。

**データ変換**：おそらく業界で唯一、3 種類の変換方法を提供すると説明されています。

| 方法 | 説明 |
| ---- | ---- |
| セルフサービスのデータ準備 | Power Query のような Excel 風の準備を、エンタープライズ規模で提供 |
| SQL ベースの変換 | ETL ではなく ELT（extract, load, transform）の考え方で、負荷をコンピュートに寄せる。DBT jobs に対応し、今週の Ignite で DBT Fusion Engine との統合の GA を発表 |
| Spark ベースの変換 | Azure Data Factory の良さを持ち込んだ mapping data flows。ビジュアルのドラッグ＆ドロップが Spark コードにコンパイルされ、ペタバイト規模のデータでも実行できる |

DBT については、今日このトピックのシアターセッションがあるとのことです。

**オーケストレーション**
- ローコードからプロコードまで、使い慣れたパイプラインで実現します。
- パイプラインがオーケストレーションする対象を、データのアクティビティだけでなく、ビジネスのアクティビティにも広げました。連携先は 40 ほどから、今週の Ignite 時点で約 100 の業務システムになったと述べています。これにより、Fabric の中で起きることと外で起きることの両方を統合できます。
- Apache Airflow も取り込まれました。

「ADF は成熟していて成功した製品だが、Fabric Data Factory はまだ早期で期待に届かない」という声に対しては、**Azure Data Factory と Fabric Data Factory は同じ ADF の基盤（同じマシン群）で動いている**、Fabric 専用に別の環境を切り出したわけではない、と説明しています。

### 5.5 ADF から Fabric への 2 段階の移行体験

ADF から Fabric へのアップグレードは、2 段階の体験として設計されています。

**第 1 段階：View in Fabric（public preview）**
- Azure Data Factory の画面の右上に「View in Fabric」ボタンが表示されます。クリックすると、ADF が Fabric の中に現れます。
- Fabric のワークスペースが用意され、試用のキャパシティが割り当てられます。
- 実行、管理、監視を Fabric 側から行えますが、**実行そのものは引き続き Azure で動き**ます。現行の ADF への投資は、そのまま維持されます。
- View in Fabric を行った後は、アップグレード準備状況のアセスメントができます。パイプラインを確認し、接続のマッピングを確認して実行すると、そのパイプラインが Fabric ネイティブのパイプラインになります。

**第 2 段階：より高度な移行（今後）**
- ADF のデプロイが複雑で成熟している場合、ボタン一つの変換では対応しきれないことがあります。ARM デプロイや API デプロイを使っている場合、プライベートエンドポイントや VNet を使っている場合が例として挙げられました。
- この第 2 段階は、来年 3 月に追加で共有する予定だと述べられています。早期の private preview に興味があれば、問い合わせるよう案内がありました。それ以上の詳細は「まだ伏せておく」と語られ、発表では触れられていません。（会場名の表記は音声認識で揺れており、確定できません。）

> 補足：発表では、View in Fabric は FabCon Barcelona で発表され、現在 public preview だと説明されています。

### 5.6 顧客事例

前半の登壇者は 2 つの事例を紹介しています。社名は、1 件目は「大手のグローバルなテクノロジーサービス企業」、2 件目は「アジアの大手小売チェーン」とだけ語られました。

**事例 1：大手グローバルテクノロジーサービス企業**
- 狙いは、AI-ready なデータ資産と、Fabric 上でのスケーラブルで統合された分析基盤の構築です。
- Synapse と ADF のパイプラインに加え、Power BI のワークロードも Fabric に移しました。
- 1 対 1 の移行にとどまらず、モダナイズを目的としました。数百あったパイプラインを、メタデータ駆動のフレームワークにまとめて設計を大幅に単純化し、**数百のパイプラインが数十のパイプラインになった**と説明しています。
- あわせて、Activator によるリッチな通知なども活用しました。
- 成果として、**8 つの data agent が本番稼働している**と述べています。
- アーキテクチャとして、安全な接続、Fabric Data Factory のパイプライン、Spark ノートブック、Dataflow Gen2 による変換、そして data agent やアプリケーションからの利用、という構成がスライドで示されました。

**事例 2：アジアの大手小売チェーン（バッチレポートからリアルタイム在庫へ）**
- データソースとして、Synapse、オンプレミスの SQL、Azure SQL、Dynamics 365 などがあり、バッチの在庫フィードでは実際の在庫を反映できていませんでした。
- 事業を統合する中で、小売部門が Google Cloud と Google BigQuery 上にあり、中央の IT 部門は分析を Fabric に統合したいと考えていました。
- Fabric-first の設計について、顧客アドバイザリーチームと協力し、**パートナー主導で全体の資産を移行**しました。
- ここでもパイプラインはメタデータ駆動のパターンで簡素化されました。Synapse のコードとデータの移行には、Data Warehouse 側のツールを多く活用したと説明されています（詳細は後半で扱うとの言及）。
- 古いデータの問題にも向き合い、Real-Time Intelligence でリアルタイムの在庫を実現しました。
- BigQuery の資産は、Fabric の mirroring for BigQuery で Fabric に取り込みました。低レイテンシの要件には CopyJob を使っています。
- 成果は、semantic model 上の data agent と、**品切れ（stock out）の発生が 30〜40% 減った**という事業上の効果です。
- 期間については「約 3 か月」と述べられています（「パートナーを得るまで」とも聞こえ、どこからどこまでの期間かは音声認識上はっきりしません）。

### 5.8 Fabric Data Warehouse の特長（後半：Rakesh 氏）

後半は Rakesh 氏が担当し、まず Fabric Data Warehouse の特長を説明しました。AI エージェントと AI ワークロードによって、クエリの数だけでなく、データへのアクセスパターンやアプリケーションの種類も大きく変わった、という認識が出発点です。Fabric Data Warehouse は AI 時代の幕開けとともに作られたため、競合の製品に対して「後発の利点（latecomer advantage）」があり、基盤アーキテクチャを根本から見直せたと説明しています。

特長は次の 4 つです。

1. **サーバーレスアーキテクチャ**：コンピュートとストレージが分離されており、管理するノードはありません。需要に応じて自動でスケールアップ・ダウンし、すべて同じデータのコピーを使います。管理負荷は小さく、それでも運用をカスタマイズするための設定は用意されています。
2. **OneLake とオープンな形式**：Delta と Parquet 形式を使うため、ベンダーロックインがありません。mirroring と shortcuts の組み合わせで、データ資産のあらゆる場所からデータを OneLake に集約できます。
3. **AI-ready**：開発の面でも、利用・提供の面でも AI に対応しています。
4. **突出したパフォーマンス**：「より速いウェアハウスは、常により良いウェアハウス」という考えです。

人間のアナリストはクエリを書いて結果を見て修正する、というセッション単位で作業します。一方、AI エージェントは並列に多数のクエリを書き、休まず反復して解が出るまで動き続けます。人間と AI エージェントが同じウェアハウスで働く世界では、同時実行性、信頼性、性能への要求が従来と違ってくる、という説明です。

性能とコストについて、発表で挙げられた数値は次のとおりです。

| 項目 | 発表された数値 |
| ---- | ---- |
| 全般 | 最大 75% 高い性能を、70% 低いコストで |
| Synapse との比較（1 TB の TPC-H ベンチマーク） | 1.9 倍高速で、1.7 倍安価 |
| GPU による query acceleration（今年前半に対応） | Synapse と比べて最大 19 倍高速 |
| 競合との比較（同等のワークロード） | 最大 7 倍の性能 |

自動のテーブルメンテナンスとテーブルの健全性管理が、分散クエリエンジン上で動くため、手動の管理作業なしにクエリが速く動くとも説明されています。GPU の件は、この後のセッションで詳しく扱うと案内されました。

### 5.9 Synapse dedicated SQL pool からの移行アシスタント

**migration assistant は製品に直接組み込まれており**、アセスメント、コード変換、データ移動を AI の支援付きで行えます。現在は generally available です。発表者は「3 つに集約される」と述べましたが、確認できる要素は次の 2 つです（2 つ目に当たる部分は、音声認識の都合で聞き取れませんでした）。

1. **コード変換**：入力は 3 通りと説明されました。Synapse や SQL Server のワークロードを DACPAC ファイルまたは SQL project として抽出する方法と、ソースのウェアハウスに直接接続する方法です（3 つ目は聞き取れません）。AI 支援の画面が変換手順を案内し、推奨内容を受け入れるか却下するかを選べます。意味と機能を保つための操作です。この作業は少しずつ進めることもできると述べています。
2. **データ移動（copy job）**：full load でも incremental load でも移せます。

今回新たに発表された内容は次のとおりです。

- **Teradata** を移行元としてサポートし、同じ製品内の体験で Fabric Data Warehouse に移せるようになった。
- **段階的な移行（incremental migration）** に対応した。テーブルやビューなど一部だけを選んで移し、後で続きを行えて、コンテキストと連続性は失われない。
- AI エージェントやクライアントを使う人向けに、**自然言語で移行の全工程を案内する migration skill** を GitHub に公開した（リポジトリの場所の部分は聞き取れません）。

### 5.10 Spark の移行

最後の移行領域は、Azure の Spark から Fabric への移行です。Fabric Data Engineering は、**SaaS ベースの Spark** として説明されています。

- 「no-cliff」の体験で、Spark オブジェクトの管理を簡素化する。
- ネイティブ実行エンジン（native execution engine）を有効にすると、同等のワークロードで**最大 3.5 倍低いコスト**になる。
- OneLake が基盤なので、複数のデータソースを一か所に集約できる。
- 迅速に開始できる starter pool、複数言語に対応したノートブック、パイプライン内で複雑な変換ができる AI functions がある。
- materialized lake views により、よく使うクエリを事前計算して性能を上げる。

| 比較項目 | 発表された数値 |
| ---- | ---- |
| 週あるいは時間あたりのコスト（同等の Synapse との比較） | Fabric Spark は最大 43% 安い |
| ネイティブ実行エンジン有効時 | 最大 2.4 倍高速で、3.5 倍低いコスト |

移行の体験も製品に組み込まれており、検証ルール、監視、アイテム単位のマッピングが用意されています。Spark pools、libraries、Spark job definition といった一般的なオブジェクトには、Fabric 側に対応するものがあるため、安心して移行できると説明されました。

## 6. デモ・手順

このセッションでは、ナレーション付きの映像が 2 本再生されました。2 本目は、登壇者が「I'll play a video」と述べて再生しています。1 本目は「demo」と紹介され、「Now watch how you can easily upgrade…」と視聴者に語りかけるナレーションが付いていました。いずれも、登壇者がその場で画面を操作する形式ではありません。画面の細部は音声からは確認できず、以下はナレーションで語られた範囲に限った内容です。

### 6.1 View in Fabric のデモ（ADF から Fabric へ）

ナレーションの流れは次のとおりです。

1. 出発点は、データ統合が動いている Azure Data Factory の画面。
2. 「View in Fabric」ボタンを選ぶ。
3. Fabric のライセンスがあるかが確認される。
4. 利用可能な Fabric キャパシティを選ぶ。ライセンスやキャパシティが無い場合は、オンボーディングが案内される。
5. Data Factory を Fabric で表示しても、キャパシティは消費されない、と説明された。
6. Data Factory と同じ名前の新しい Fabric ワークスペースが作られる。
7. 既存の ADF のユーザーとグループを、Fabric ワークスペースの viewer として追加できる。今すぐ権限を付与しても、後回しにしてもよい。
8. 新しいワークスペースで ADF が開く。ここで ADF を探索・評価できる。この時点で、アップグレードも Fabric 上での作成も行われていない。
9. pipelines、datasets、linked services、triggers、監視がそこに表示される。実行、課金、ランタイムの挙動は Azure に残る。
10. より深く Fabric ネイティブに移行する評価には、「Assess and Upgrade」を選ぶ。
11. 準備状況のアセスメントが表示され、アップグレードの準備ができているもの、対処が要るもの、その理由が分かる。実行しても何も変更されない。
12. アップグレードするパイプラインを選び、接続のマッピングを確認して、アップグレードを開始する。そのパイプラインは Fabric ネイティブになり、残りのファクトリーは動き続ける。

### 6.2 Synapse dedicated SQL pool の移行アシスタントのビデオ

ナレーションの流れは次のとおりです。

1. ワークスペースで migrate ボタンをクリックし、「Azure Synapse Analytics dedicated SQL pool」のタイルを選ぶ。移行ウィザードが開く。
2. 入力方法を選ぶ。アップロード（DACPAC、または SQL ファイルの zip）と、ソースシステムへの直接接続がある。直接接続では、サーバー名、データベース名、認証の種類を入力する。
3. 移行するオブジェクトを、スキーマ単位または個別のオブジェクト単位で選ぶ。
4. 移行先として、ウェアハウスの名前を入力し、照合順序（collation）を選ぶ。ここでは case-insensitive を選んだ。
5. 入力を確認して Migrate をクリックする。テーブル、ビュー、ストアドプロシージャ、関数を含むすべてのスキーマの移行が始まる。選んだ照合順序でウェアハウスが作られ、変換から移行先への適用までの進捗が表示される。
6. 完了すると、移行サマリー付きでウェアハウスが開く。サマリーには、移行に成功したオブジェクトと、修正が必要なオブジェクトが表示される。Object Explorer にも移行済みのオブジェクトが表示される。
7. 次に、自動では移行できなかったオブジェクトを確認する。「Fix problems」には、修正が必要な主要オブジェクトと、依存オブジェクトの 2 つのタブがある。優先度は修正の順序を決めるためのもの。
8. 最初のオブジェクトを選ぶと、クエリを修正するメニューが出る。Copilot が修正案を生成し、受け入れるか破棄するかを選べる。ここでは受け入れ、クエリを再実行した。同様の作業を他の主要オブジェクトにも行う。
9. 主要オブジェクトの修正後、依存オブジェクトを再実行して移行する。
10. create user 文のようなセキュリティオブジェクトについては、「add user」アクションでウェアハウスに特定の権限を付与し、そのオブジェクトを移行する（Fabric での扱いに関するナレーションは音声認識が不明瞭です）。
11. すべての問題を修正したら、データコピーのステップに進む。copy job を呼び出し、Azure Synapse Analytics dedicated SQL pool から Fabric Data Warehouse へデータをコピーする。
12. copy job の画面で、ソースとして Azure Data Lake Storage を選び、接続情報を入力する。次にコピーするテーブルを選び、テーブルのマッピングを確認し、copy job のモードを選ぶ。確認して「save and run」を押すと、バックグラウンドでコピーが始まる。
13. データの取り込みが済んだら、最後のステップ「接続の付け替え（reroute connections）」に進む。dedicated SQL pool に接続していた ETL ツールとレポートツールの接続を、すべて Fabric Data Warehouse に向け直す。

Rakesh 氏は、オブジェクトが 100% 対応しないシナリオでも、手順を追って移行を支援する、統合された体験だと総括しています。

## 7. 注意点・発表者の気付き

- ADF の View in Fabric で表示するだけでは、アップグレードは行われず、Fabric 上で何かが作られることもありません。実行・課金・ランタイムの挙動は Azure のままです。
- ボタン一つの変換は、ARM デプロイや API デプロイ、プライベートエンドポイント、VNet を使う複雑な ADF では不十分な場合があると、発表者自身が述べています。この領域は第 2 段階で扱う予定です。
- Synapse の移行では、自動で移行できないオブジェクトが出ることがあります。そのため、修正が必要な主要オブジェクトと依存オブジェクトを、優先度に従って順に直す手順が用意されています。create user のようなセキュリティオブジェクトは、権限の付与を明示的に行って移行します。
- 先行事例では、1 対 1 の移行にとどまらず、パイプラインをメタデータ駆動にまとめる、古いデータの問題に対処する、といった**設計の見直し**も同時に行っていました。
- 移行は顧客のタイムラインと、リスク・価値の判断で進めるものだと、繰り返し述べられています。

## 9. まとめ

このセッションは、ADF・Synapse から Fabric への移行について、理由と手段をまとめて示したものです。Data Factory は、View in Fabric で既存資産をそのまま Fabric に表示し、準備ができたパイプラインから Fabric ネイティブに移す 2 段階の道筋が示されました。Data Warehouse は、migration assistant が GA となり、Teradata への対応と incremental migration が新たに加わっています。Spark も、製品内の移行体験が用意されています。

顧客事例では、移行をきっかけにパイプラインの再設計や data agent の活用まで進めた例が紹介されました。移行を検討する場合は、製品内ツール、Cloud Accelerate Factory、`upgrade.fabric.microsoft.com` のパートナーマッチングを入口にできます。
