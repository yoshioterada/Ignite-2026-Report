# BRK373 Build AI-ready apps on Azure SQL with GitHub Copilot in VS Code

## 1. はじめに

このセッションは、データベースが無い React アプリケーションに Azure SQL Database を組み込み、最終的に「データベース内のナレッジ記事を根拠に、カスタマーサポートの返信案を作る AI 機能（RAG）」まで作り上げるデモ中心のセッションです。作業はすべて VS Code の中で、MSSQL 拡張機能と GitHub Copilot を使って進めます。

流れは、ローカルの Azure SQL Database コンテナーの起動、PRD からのスキーマ設計、Data API Builder による API 生成、ネイティブのベクター型を使った RAG の構築、そしてクラウドへのデプロイです。ツールを何度も切り替えずに、1 つのエディターで 1 つのワークフローとして完結させる、というのが発表のねらいです。**ローカルコンテナーがクラウドの Azure SQL Database と同じエンジンで動くため、ローカルで作ったものをそのままクラウドへ持っていける**という点が、全体を貫く考え方です。

## 5. 発表内容の詳細

### 5.1 完成形のアプリと、実現したいこと

登壇者は VS Code で多くの時間を過ごす開発者として、次のことを 1 つのエディターで済ませたいと述べています。

* 開発・テスト用のローカルデータベースを持つ。
* アプリのモデルと仕様から、データベースのテーブル、カラム、外部キーを作る。
* データベースとやり取りする API を用意する。
* あまり手間をかけずに RAG を追加する。

そのために使うのは、VS Code と MSSQL 拡張機能、GitHub Copilot、そして**今週パブリックプレビューになった最新の Azure SQL Database ローカルコンテナー**です。さらに、データベースのスキーマから REST エンドポイントを生成する Data API Builder、検索用のネイティブなベクターデータ型を使います。別の検索サービスを運用・同期する必要がなく、データベース自身が AI generate embeddings で埋め込みモデルを呼び出せる、と説明されています。最後にクラウドへデプロイします。

### 5.2 セキュリティとプライバシー（Copilot が見られるもの）

登壇者は、GitHub Copilot の話をするときは必ずこの内容を示すとして、次の 3 点を挙げました。

| 論点 | 発表での説明 |
| --- | --- |
| スキーマの認識 | Copilot 単体はデータベースのスキーマを知らない。MSSQL 拡張機能を入れると、データベースへ接続し、クエリ実行やテーブル一覧、中身の把握ができるエージェントツールが付属し、正しい構文のクエリを生成できる。 |
| データへのアクセス | Copilot が持つのはテーブル、カラム、外部キーなどのスキーマ情報で、顧客データは持たない。ただし、`select top 1000` のようなクエリを Copilot が実行すれば、その結果として顧客データの情報を得ることになる。 |
| 権限 | Copilot はユーザーと同じデータベース権限を持つ。テーブルが読み取り専用なら Copilot も読み取り専用になる。 |

管理者向けには、エージェントツール、自動承認、エージェントモードなどを組織として一元的に制御できる VS Code のエンタープライズポリシーが複数あると紹介されました。

モデルのトレーニングとデータ保持については、今年 4 月に発表された新しい扱いとして、次のように説明されています。Business または Enterprise ライセンスなら、デフォルトでトレーニングには使われません（発話が不明瞭で、対象はプロンプトのコンテキストと聞こえます）。一方、Free、Pro、Pro Plus のライセンスでは、プライバシー設定からオプトアウトする必要があります。データを共有したくない場合は、設定を確認して無効にするよう呼びかけています。

### 5.3 Copilot に渡す 3 種類のコンテキスト

スキーマが分かっても、何を作りたいのか、チームがどう作業するのかは Copilot には分かりません。そこで、このデモでは 3 種類のコンテキストを渡します。コンテキストが良いほど、エージェントの出来も良くなるという考えです。

* **PRD**：仕様駆動開発の文書です。作るものの内容、データモデル、技術要件を書いておくことで、エージェントと何度もやり取りしなくても、望むものが早く出てきます。
* **Copilot instructions**：チームのルールにあたります。例えば snake case の命名や、推奨するデータ型などです。登壇者は、「status V2 のように Dave しか意味を知らないカラム（でも Dave は休暇中）」を例に、そうした暗黙知を Copilot が守れる形にするものだと説明しました。
* **skills**：エージェントに「より大きな頭脳」を与える Markdown のプレイブックです。専門知識やベストプラクティス、特定タスクの進め方をまとめたもので、プロンプトに応じてエージェントが適切な skill を読み込み、その指針に従います。トークン使用量の削減にも役立つ場合があり、例として「20 回の呼び出しが 10 回に減る」ことが挙げられています。

#### SQL agent skills

Microsoft SQL agent skills は今年 9 月に公開されました。スキーマ設計、ベクター、クラウドへのデプロイ、パフォーマンスチューニング、クエリ分析などを扱い、製品チームが生成・レビュー・キュレーションしています。毎月増えているとのことです。SQL の専門家でなくても、専門家でも自動化のために、好みのエージェントにインストールできます。

### 5.4 MSSQL 拡張機能

SSMS と MSSQL 拡張機能の利用経験を会場に尋ねたうえで、拡張機能の紹介がありました。

* VS Code の拡張機能ビュー（マーケットプレース）からインストールします。バージョンは 1.48 で、毎月リリースされるため、自動更新をオンにしておくよう勧めています。
* 新しい Getting started ページに、学習用リソースや agent skills などがまとまっています。agent skills は、GitHub Copilot にインストールするためのプラグインとして提供されます。このプラグインには 44 個の skills が含まれていると説明されました（例として Data API Builder の endpoint、lock analysis、Azure へのデプロイが挙がっています）。
* Getting started ページには、Case Desk の PRD と Copilot instructions の文書もあります。

> 注意：SSMS を使っている人向けの補足として、SSMS には constitution.md というファイルがあるが、VS Code にはそれがないと説明されました。VS Code にはすでに多くの instruction ファイルや設定方法があり、階層も異なるため、SSMS で定義した constitution が VS Code にも引き継がれると期待しないよう注意しています。

### 5.5 Azure SQL Database ローカルコンテナー

SQL Server をコンテナーで動かすことは以前からできました。しかし本番が Azure SQL Database の場合、ローカルは SQL Server になり、差異が後で問題にならないことを期待するしかありませんでした。今回のコンテナーは、**クラウドの Azure SQL Database と同じ Azure SQL エンジンで動き、ローカル開発では無料**です。そのためクラウド側のルールがローカルにも適用され、native vector type、vector distance、external models といった新しい AI 機能も、クラウドと同じようにローカルで試せます。ここで作ったものは、Azure にスムーズにデプロイできると説明されています。

### 5.6 スキーマ設計と Data API Builder

- スキーマデザイナー：テーブルとカラムの関係を図で見られる機能です。GitHub Copilot のボタンから、スキーマ設計ツールを呼び出せます。Copilot が作った内容はライブのデータベースにはまだ反映されず、「Apply changes」を押して初めて公開されます。GUI でテーブルを追加する使い方もできます。
- Edit data：テーブルの値を T-SQL を書かずに直接編集できます。裏で実行される UPDATE 文も見られます。
- Data API Builder：通常なら開発者が午後を費やして書くバックエンドコードの大半を省略できる、と紹介されました。拡張機能に組み込まれており、データベースのスキーマから REST、GraphQL、または**エージェント向けの MCP エンドポイント**を選んで生成できます。テーブルが 100 個ある場合のチェックボックス操作を避けるため、GitHub Copilot に自然言語で依頼することもできます。

### 5.7 セマンティック検索と埋め込み

RAG の検索部分（R）の前提として、次の違いが説明されました。

| 方式 | 説明 |
| --- | --- |
| キーワード検索（LIKE 構文） | 入力した単語に一致するものを探す。「フィールド更新が止まっている、なぜ同期しないのか」のような質問では、ナレッジ記事が同じ表現を使っていないため、何も返らない可能性が高い。 |
| 全文検索 | LIKE より賢く、何か返るかもしれないが、やはり単語の一致を探しており、顧客の質問の概念的な意味を捉えるものではない。 |
| セマンティック検索 | 意味によって順位づけする。埋め込みに対して vector distance 関数を使うと、「データ同期が遅れている」といった記事を、表現が一致しなくても返せる。 |

埋め込み（embedding）は、テキストの意味を表す数値の配列です。それを生成するのが埋め込みモデルです。数値の羅列は人間が読むものではありませんが、エージェントは扱えます。ベクターとして Azure SQL のテーブルに保存すると、vector distance 関数でコサイン距離を測り、2 つの埋め込みがどれだけ近いかを求められます。たとえ話として、「dog」と「puppy」は近く、「cat」と「dog」もペットとして比較的近く、「dog」と「exhibition hall water leak」は非常に遠い、という例が使われました。

実際の埋め込みは次元数がずっと多く、このデモでは 768 次元です（使うモデルによって変わります）。一般に次元が高いとベクター検索のコストは上がりますが、結果は正確になりやすいと説明されています。質問もナレッジ記事と同じ方法で埋め込み、ケースと記事のコサイン類似度を比べて、その記事がサポートケースに役立つかを判断します。

通常は埋め込みモデルを呼ぶアプリケーションコードを書きますが、Azure SQL では次の 2 つの T-SQL で完結します。

| 文・関数 | 役割 |
| --- | --- |
| `CREATE EXTERNAL MODEL` | モデルの登録（1 回だけ）。モデルがどこにデプロイされ、どの認証情報を使うかを指定する。キーはスクリプトではなく、暗号化されたデータベース資格情報に保管される。 |
| `AI_GENERATE_EMBEDDINGS` | テキストを受け取りベクターを返す関数。任意のクエリから何度でも呼べ、結果は Azure SQL に保存できる。 |

これにより、ストアドプロシージャ、Data API Builder、エージェントのいずれからも、アプリケーションコードを挟まずに意味で検索できる、という説明でした。

> 補足：デモは Azure OpenAI に接続しています。Azure OpenAI の設定で追加コストが出るのを避けたい人向けに、リポジトリには Ollama 版もあり、完全に無料でオフラインの設定で試せます。

### 5.8 Azure AI Search との違い

「Azure AI Search とは何が違うのか」という質問をこの週何度も受けたとして、登壇者は次のように整理しました。

* Azure AI Search は優れており、今回のケースにも対応できる可能性が高い。文書や PDF など多様なソースがある場合に力を発揮し、テキスト抽出、チャンク分割、埋め込みを代行し、ハイブリッド検索やセマンティックランキングも備える。
* Azure SQL が優れるのは、**データがすでにリレーショナルで、それを絞り込みたい**場合。例えば、防水のハイキングブーツを探す買い物客に対し、製品カタログがすでにデータベースにあれば、価格や在庫などのカラムでの絞り込みを、ベクター検索と同じクエリで行える。
* 既存の権限や行レベルセキュリティがそのまま適用され、追加のセキュリティ設定が要らない。
* OLTP データベースなので、新規注文や注文のキャンセルなどの変更がすぐに反映される。別の AI サービスだと、同期の遅延が生じ得る。

### 5.9 RAG のパイプライン

RAG の 3 要素を、このアプリに当てはめた説明です。

1. **R（Retrieval）**：エンジニアが Suggested reply をクリックすると、記事に使ったのと同じ埋め込みモデルがケースをベクターに変換し、Azure SQL が最も近い記事を返す。external model や AI_GENERATE_EMBEDDINGS はこの部分にあたる。
2. **A（Augment）**：取得した記事と元のケースを、チャットモデルに渡す。上位 3 件の関連記事のランキングが渡されるため、AI は何が起きていて、どの記事が最も関連が高いかを把握できる。
3. **G（Generation）**：チャットモデル（発話では GPT 5.4）が返信案を作る。「あなたは case support assistant です」といった役割と、返信の出力形式のルールを与えている。

重要なのは最後の指示です。**関連する記事がなければハルシネーションせず、正直に「関連する記事はありません」とエンジニアに伝えるよう指示**しています。登壇者は、設定した距離の最大値に収まらない場合は何も出さない設計だと説明しました。その場合、エンジニアが自分でナレッジ記事を調べるか、他の人に助けを求めます。

このデモでは 2 つのモデルを使います。1 つは埋め込みモデル、もう 1 つは GPT 5.4 のチャットモデルです（モデル名は音声認識の都合で表記が確定できません）。

### 5.10 クラウドへのデプロイとまとめの資料

Ignite リリースの MSSQL 拡張機能に、ローカルの Azure SQL Database コンテナーをクラウドへ簡単にデプロイする新機能が入った、と紹介されました。Object Explorer の「Deploy to Azure」から、「スキーマとデータ」か「スキーマのみ」を選べます。裏側では「backpack」と聞こえる仕組みと SQL プロジェクトが使われている、と説明されました（音声認識の都合で、仕組みの名称は確定できません）。Azure SQL Database をターゲットプラットフォームとした互換性チェックで、デプロイ前に非互換や警告を検出します。デプロイ先は**無料枠（free tier）の Azure SQL Database**で、Azure アカウントがあれば毎月の無償枠でプロビジョニングできます。

将来は、Azure アカウント内の既存のデータベースや、Hyperscale のような新しいデータベースへのデプロイにも対応したいとのことで、これらはロードマップにあります。今回のプレビューでは無料枠に限定されています。同じエンジンエディションなので、アプリ側は接続文字列の入れ替えだけで localhost からクラウドのサーバーへ切り替えられます。ローカルでは SQL ログインを使いましたが、クラウドのデータベースでは Microsoft Entra を使っています。

終盤のスライドで、次の点が語られました。

* エージェントにリポジトリ、コードベース、PRD、カスタム instructions などの十分なコンテキストを与えること。SQL agent skills をインストールすること（全部で約 100 個の skills があり、マイグレーションなども含むと発話で説明されています）。
* SSMS の GitHub Copilot に組み込まれていた skills と組み込み MCP サーバーが、最近、新しいプラグインに切り出された（発話では「admin plug-in」と聞こえ、名称は確定できません）。そのため SSMS の GitHub Copilot に限らず、Cursor など好みのエージェントにそのプラグインをインストールして、同様のデータ作業ができる可能性が高い。
* GitHub リポジトリ（セッション全体の手順があり、Azure OpenAI 版と無料のオフライン Ollama 版を選べる）と、MSSQL 拡張機能の関連リンクが示された。拡張機能は毎月リリースされるため、更新するよう案内された。

RAG をさらに深く学ぶ場として、同日 10:45 から実施されるラボが案内されました。ラボでは全文検索、字句検索とセマンティック検索を組み合わせるハイブリッド検索、チャンク分割などを扱います。ラボに参加できない人も、QR コードからリポジトリを見て、コードの構文やドキュメントを参考にできます（Azure リソースは用意されません）。

## 6. デモ・手順

このセッションは**デモが中心**です。登壇者は画面上で操作しながら説明しており、録音では「画面をどう操作したか」が語られた範囲だけ確認できます。画面の細部は音声からは分かりません。以下は語られた順です。

### 6.1 事前の完成形アプリの紹介

最初に、完成形の Case Desk を見せました。未対応ケースのキューがあり、「field update stuck in pending sync」というケースで Suggested reply をクリックすると、KB3 のようなナレッジ記事を引用した返信案が出ます。

### 6.2 ローカルコンテナーの起動と接続

1. Getting started ページから、ローカルの Azure SQL DB コンテナーを起動する（CLI でも可能と説明）。GUI では、コンテナーのランタイムを検出し、足りないものをインストールしてくれる。
2. 認証方式（SQL ログインまたは Microsoft Entra 認証）を選ぶ。プロファイル名、コンテナーを動かすポート番号などを入力する。
3. コンテナーイメージが取得される（初回は時間がかかる）。コンテナーが作られ、MSSQL 拡張機能に自動で接続される。左の Object Explorer に、Case Desk という接続が表示される。
4. Create Database ダイアログで「Casedesk」という名前のデータベースを作る（発話では "Casedusk" と聞こえます）。
5. データベースを右クリックして「Open in GitHub Copilot agent mode」を選ぶ。初期プロンプトが SQL agent ツールを通して作成したデータベースに接続する。
6. 「どのデータベースエンジンで動いているか」を尋ねる。クエリは先に承認が必要。結果の最初のカラムの engine edition が 5 で、クラウドの Azure SQL Database と同じ値だと説明された。

### 6.3 スキーマ設計

1. 空のデータベースで、拡張機能のスキーマデザイナーを開く（テーブルが無いので空）。
2. GitHub Copilot ボタンから、「PRD ファイルを読み、PRD のデータモデルに基づいてテーブルを作る」と指示する。
3. Copilot が PRD と、プラグインで入れた Azure SQL スキーマ設計の agent skill を読み込む。skill にはノンクラスタードインデックスキーのバイト数などの指針がある。
4. 完了後、スキーマデザイナーにテーブル、カラム、外部キーが表示される。見た目が乱れていれば自動再配置ができる。
5. Copilot が生成したものなので、慎重にレビューして変更を受け入れる。この時点ではライブのデータベースに公開されておらず、「Apply changes」ボタンで公開する。
6. 用意したスクリプトでサンプルデータを投入し、Edit data でテーブルを開く。要求したカラムとサンプルデータが見える。値を直接編集して保存できる（裏で実行される UPDATE 文も表示される）。

### 6.4 Data API Builder

1. Data API Builder で、REST、GraphQL、MCP のいずれかを選べる画面を使う。
2. GitHub Copilot に、REST エンドポイントのみ、anonymous の権限ロール、読み取り専用で構成するよう自然言語で依頼する。画面のチェックボックスがすべて外れ、意図どおりの構成になる。
3. エンドポイントをデプロイする。DAB CLI か、ローカルの Docker コンテナーかを選べる（ここでは DAB CLI）。
4. エンドポイントが生成され、Swagger で確認できる。Swagger のリンクを開き、ある API を実行してレスポンスを確認する（発話では「account API」と聞こえ、正確な名称は確定できません）。
5. アプリの環境変数を変更し、ハードコードされたサンプルデータから Data API に切り替える。未対応ケースが 2 件から 17 件になり、データベースの実データを読めていることを確認する。

### 6.5 ベクター検索と RAG

1. Copilot チャットに、PRD のデータモデルから埋め込みテーブルを作るよう依頼する。Copilot が vector search の Azure SQL の skill を読み込み、vector データ型のテーブルを、PRD の要件どおり 768 次元で作成する。Object Explorer でテーブルを確認する。
2. Foundry の「deploy base model」から、モデルをデプロイする。このデモでは GPT 5.4 と埋め込みモデルの 2 つをデプロイ済み。エンドポイントとキーを用意する。
3. SQL ノートブックを開く。MSSQL 拡張機能の MSSQL カーネルにより、接続プロファイルとシンタックスハイライト、IntelliSense が使える。
4. 用意済みのノートブックで、Foundry のモデルを登録する `CREATE EXTERNAL MODEL` を示す。続いて `AI_GENERATE_EMBEDDINGS` で、ナレッジ記事を埋め込みに変換して埋め込みテーブルに保存する。
5. 「モバイルアプリからのフィールド更新が今朝から保留のまま」という顧客の入力を、記事と同じモデルで埋め込む。vector distance 関数でコサイン距離を測り、最も関連の高い記事を求める。
6. 登壇者は残り時間が少ないとして、画面を見せながら急ぎ足で RAG の流れを説明した。ケースの埋め込み、記事との距離の測定、上位記事をモデルに渡す部分、役割と形式の指示（5.9 を参照）が示された。
7. 完成したアプリで、KB3 が最も関連する記事と判定され、エンジニアが確認して送信できる返信が出る。別のケースで Suggested reply を押すと何も出ない（距離が設定の範囲内に無いため、関連記事なしと返す設計どおり）。

### 6.6 クラウドへのデプロイ

1. Object Explorer の Case Desk のローカルデータベースで、「Deploy to Azure」をクリックする。
2. 「スキーマとデータ」か「スキーマのみ」を選ぶ。Azure SQL Database を対象とした互換性チェックが、デプロイ前に警告や非互換を検出する、と説明された。
3. 無料枠の Azure SQL Database にデプロイする。
4. アプリの接続文字列を localhost からクラウドのサーバーに入れ替える。ローカルでは SQL ログインだったが、クラウドでは Microsoft Entra で接続している。

## 7. 注意点・発表者の気付き

* **Copilot が見られるのはスキーマで、データではない。ただし、`select top 1000` のようなクエリを実行すれば結果として顧客データを見る。** 権限はユーザーと同じです。
* **Copilot が生成したスキーマは、レビューしてから Apply changes で反映する。** 生成直後はまだライブのデータベースには公開されていません。
* **プロンプトのトレーニング利用は、ライセンスで異なる。** Free、Pro、Pro Plus はプライバシー設定でのオプトアウトが必要です。
* SSMS の constitution.md は VS Code に引き継がれない。
* 埋め込みの次元数が高いほど検索のコストは上がる（精度は上がりやすい）。
* RAG は、関連する記事が無いときに作り話をせず「無い」と答えるように指示する。
* ローカルから Azure への新しいデプロイ機能は、このプレビューでは無料枠のみ対応です。
* コンテナーは今週パブリックプレビューになったばかりです。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* ローカルとクラウドで同じエンジンになるため、クラウド固有の問題をラップトップで早い段階で見つけられる（登壇者は、金曜朝 9 時半の障害対応にならないで済む、という例えで説明した）。
* ローカルでの開発・テストは無料。ネイティブなベクター型、vector distance、external models もローカルで使える。
* 別の検索サービスを運用・同期しなくてよい。データがすでにリレーショナルなら、絞り込み条件・権限・行レベルセキュリティを同じクエリと同じ設定で扱える。OLTP の変更が即座に反映される。
* Data API Builder で、バックエンドコードの大半を書かずに REST、GraphQL、MCP のエンドポイントを得られる。
* skills と instructions により、チームのルールやベストプラクティスを Copilot に守らせられ、場合によっては呼び出し回数やトークンも減らせる。
* ローカルからクラウドへは、接続文字列の入れ替えが中心。

## 9. まとめ

このセッションは、VS Code、MSSQL 拡張機能、GitHub Copilot、Azure SQL Database ローカルコンテナーを組み合わせ、データベースの無い React アプリを、RAG による返信案作成機能つきのアプリに仕上げて、無料枠のクラウドに載せるまでを見せたものです。鍵になるのは、PRD、instructions、SQL agent skills というコンテキストを Copilot に与えること、そしてローカルとクラウドで同じエンジンを使うことです。

発表で案内された次のステップは、セッション全体の手順が入った GitHub リポジトリ（Azure OpenAI 版と Ollama 版）の利用、同日 10:45 の RAG ラボ、MSSQL 拡張機能の毎月の更新の確認でした。
