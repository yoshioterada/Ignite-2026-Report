# THRSP1098 Strengthen Microsoft 365 backup, recovery, and archiving with Azure

## 1. はじめに

このセッションは、Microsoft 365 のバックアップ・リカバリ・アーカイブを、Azure 上で動くバックアップ SaaS の **CrashPlan** で行う方法を紹介する 25 分のシアターセッションです。話の中心は、Microsoft 365 のストレージ容量を超えたときに発生する超過料金（overage charge）を、アーカイブによって抑えるという点です。

発表では、アーキテクチャの考え方、Azure のストレージ冗長化と階層化の仕組み、Indiana University と Hyatt の事例を順に説明しています。後半には、Teams から CrashPlan の MCP server に問い合わせるデモがあります。Microsoft 365 の運用を担当している方や、バックアップ製品の選定でコストを気にしている方に向いた内容です。

## 5. 発表内容の詳細

### 5.1 CrashPlan の背景と設計方針

CrashPlan は約 10 年の歴史があり、数千の企業顧客がいると説明されています。経験豊富な人材が集まっており、Commvault、Druva、Veritas、StoreMagic の出身者（ベンダー名は音声認識の都合で表記が確定できません）を挙げたうえで、「私たち 4 人だけで合計約 800 件の特許を持つ」と述べています。また CTO の Anand 氏は、McAfee で約 5 年間、大きな組織を率いた経験があり、CrashPlan のサイバーレジリエンス機能はその経験が反映されたものだと紹介されました。

顧客のフィードバックで最も多かったのは「コスト効率が良いこと」と「シンプルで使いやすいこと」の 2 つで、この 2 点を軸に新しい製品を作ったとのことです。設計は Microsoft と歩調を合わせて進め、Azure に最適化しています。

コスト面では、次の点が挙げられました。

- 他社の一部製品は重いデータベースを抱えている。例として SQL Server Enterprise Edition（定価でおよそ 30,000 ドルと発言）を挙げ、そのコストは顧客に転嫁されると指摘しています。
- 他社製品の多くは、オンプレミス製品をそのままクラウドの VM に載せている。そのため VM が大きくなり、実行コストが上がる。
- CrashPlan は Azure のコンピュートだけで動かしており、複数クラウドへの対応による肥大化が無い。

一方で、ストレージの接続先は Azure に限定せず、「業界で最も多くのストレージターゲットに対応している」と述べています。Azure 以外のターゲットも使えますが、後述する Azure 固有の機能は使えない場合があるという説明です。また、Azure 認定ソリューション（Azure certified solution）を取得していることにも触れています。

### 5.2 Microsoft 365 のストレージ超過料金とアーカイブ

登壇者は、Microsoft 365 の利用者の約 75% がストレージ上限を超えていると述べています。SharePoint や OneDrive にデータをためてきた結果、現在は超過料金が発生しており、その額は **1 TB あたり年間 2,400 ドル** と発言されています。M365 チームが知らなくても、調達部門には請求書が届いているはずだという話もありました。

CrashPlan のアーカイブ機能は、この超過分のデータを Azure Blob に移すことで超過料金を避けます。ユーザー側では、アーカイブ後も SharePoint、OneDrive、Exchange 上でこれまでと同じようにデータにアクセスでき、新しい操作を覚える必要が無いと説明しています。アーカイブの条件は、ファイルの古さ、所有者、サイズ、種類で指定できます。「上限の 90% に達したらアーカイブを始める」といった設定も可能です。

さらに、データ量は年平均で 25% 増えており、AI 関連の利用で Microsoft 365 に蓄積されるデータはさらに増えるため、現在の超過料金は「将来の端数に見えるかもしれない」と警告しています。バックアップ・リカバリのコストの約 70% はストレージに使われているとも述べています。

### 5.3 共同責任モデルと管理者の責任

Microsoft の責任はインフラとサービスの可用性、認証、ネットワークセキュリティで、世界最大の攻撃対象でありながらセキュリティをしっかり行っていると評価しています。これに対して、管理者側の責任は **バックアップ、アーカイブ、リカバリ、データのサイバーレジリエンス、ユーザーのアクセス確保、コンプライアンス、データの可用性** だと整理しています。

リカバリについては、多くの製品が Microsoft 365 へのリストアしか提供しないため、Microsoft 365 が使えないときに困ると指摘しています。CrashPlan は M365 への復元に加えて、ローカルデバイスへの復元、メールの PST ファイルへの書き出し、OneDrive ファイルへのアクセスにも対応するという説明です。保持期間は顧客が設定します。

そのほか、次の特徴が語られました。

- 任意の Microsoft 365 ライセンスに対応する（E3 / E5 に限らない）。登壇者は、E1 を使うフロントライン（病院の医師や看護師、法執行機関など）のデータも CEO のデータと同じくらい重要だと述べています。
- 異常検知（anomaly detection）とランサムウェア警告は組み込み済みで、追加料金は無い。
- コンテンツによる検索。SharePoint のアイテム名を覚えているユーザーは少ないが、中身は覚えているため、内容で検索できるようインデックスを作成する。これも追加料金は無い。
- アーカイブ済みのファイル、Exchange の添付ファイル、SharePoint のアイテムを、**HTML 描画のプレビュー**で画面表示できる。復元や呼び戻しをせず、Microsoft 365 の容量も消費しない。
- マルウェアスキャンも含まれる。
- サーバー、エンドポイント（Windows 365 を含む）、Microsoft 365、Google Workspace に対応する。Google 側も超過料金が高いため、Google Workspace のバックアップも Azure を使って行うと説明しています。

処理の流れとしては、エンドポイント、M365、Google Workspace、サーバー（オンプレミス・クラウド）のデータをバックアップし、コンテンツ検索と対話型 AI のためのインデックスを作り、マルウェアスキャンと異常検知を行ってから、ストレージにデータを置く、と紹介されています。

### 5.4 Azure の一貫性と Azure Local

Randy 氏は、CrashPlan は会社として Azure に賭けたと述べています。Azure を選んだ理由の 1 つが、世界中での一貫性です。Microsoft 側の登壇者は、同じ VM ファミリー、同じサービス、同じ機能を **80 のリージョン** で揃える努力をしており、CrashPlan が使う主要な SKU はどこでも利用できるため、データの一貫性、コンプライアンス、データ所在地の要件に応じてどこにでもデプロイできると説明しています。

> 補足：Randy 氏は「データセンターは 500 を超えていると思うが、数えていないので違うかもしれない」と話しています。数値の裏付けとして扱わないでください。

Azure Local については、Randy 氏が「オンプレミスを望む顧客向けに CrashPlan は Azure Local に対応している」と述べ、Microsoft 側の登壇者が次のように補足しました。

- Azure Local は、Azure で動くサービスや機能を、大きなコード変更なしに、同じコントロールプレーンのままオンプレミスに持ち込む仕組みである。
- 規制やコンプライアンスの都合で特定の場所で動かす必要があるデータに使う。金融サービスやヘルスケアでは、95% は Azure のリージョンで動かせても、残り 5% はそうできないことがある。そのために別のバックアップ製品を用意しなくて済む。
- クラウドにデータを置きたくないが、オンプレミスなら置く、という外国政府もある。

### 5.5 Azure ストレージの耐久性と階層化

**3 コピー相当の耐久性**

バックアップの世界では、3 つのコピーを 2 つの場所に置く 3-2-1 の形式が好まれます。Microsoft 側の登壇者は、Azure Storage で最も冗長性の低い（最も安価な）選択肢でも、3 コピー相当以上の耐久性があると説明しました。データは、少なくとも 3 つのラックの 3 つの異なるノードに書き込まれるまで、書き込み完了を返しません。ディスク、ノード、ラックのいずれの障害でもデータは失われません。その後、コスト効率のために、さらに多くのラックにまたがって、データが分散して保存されます（音声では erasure code と聞こえますが、音声認識の都合で表記が確定できません）。

あわせて、バックグラウンドで CRC チェックサムによる耐久性チェックを常時行っており、ビット腐敗があれば自動で修復します。ハードウェアの世代交代も Azure 側が行います。これは GA（一般提供）から 16 年続けていることだと述べています。

**ストレージ階層**

Azure には Hot、Cool、Cold、Archive という階層があります。ある顧客が「自分の Azure テナントで CrashPlan を 1 年使っているが、Archive の方が Cool より安いと聞いた。移せないか」と相談してきたそうです。CrashPlan 側で対応するなら何か月もの設計作業が必要でしたが、Azure には 1 つの名前空間のもとで階層を切り替える仕組みがあり、次のように動くと説明されています。

- CrashPlan のコードが「このデータをより安い階層に置きたい」という信号を送るだけでよい。
- 課金は直ちに安い階層で始まり、実際のデータ移動は都合のよいタイミングでバックグラウンドで行われる。
- **smart tiering** という機能は、アクセスパターンを見て、読まれていないデータを自動で下の階層に移す。アカウント全体を smart tier に設定すれば、個別の判断は要らない。

これらの機能は、顧客自身の Azure テナントを使う場合も、CrashPlan が Azure を提供する場合（ターンキー）も同じように使えます。後者はエアギャップ（隔離）の面で追加の保護にもなるという話です。

**冗長化の選択肢**

地理的な冗長性を求める顧客向けに、次の 3 段階が説明されました。

| 方式 | 内容 |
| ---- | ---- |
| LRS（ローカル冗長） | 単一のデータセンター内に 3 コピー。ディスク・ノード・ラック障害から守る。データセンター自体に障害が起きると（竜巻など）使えなくなる可能性がある |
| ZRS（ゾーン冗長） | 3 つのデータセンターにまたがる。ネットワーク遅延が約 1 ミリ秒、距離にして約 50〜60 マイルの範囲。同期書き込みで、3 つのゾーンに永続化してから書き込み完了を返す |
| GRS / RA-GRS（geo 冗長 / 読み取りアクセス geo 冗長） | プライマリリージョンのコピーを非同期でセカンダリリージョンにコピーする。同期の遅れ（sync gap）は CrashPlan のコードに通知される。リージョン全体の障害でも、最後の 10〜15 分ほどのデータを失う可能性はあるが、大部分は復旧できる |

さらに、2 つの国や大陸にデータを持ちたい場合には、**object replication** があります。CrashPlan 側がストレージ層で有効にすると、顧客が選んだ国またはリージョンペアにデータが複製されます。CrashPlan の開発チームがこれらを自前で作る必要が無い点が、Azure を使う利点として語られています。

### 5.6 事例：Indiana University

Indiana University は大規模な組織で、Microsoft 365 の超過料金として 100 万ドルの請求を受けました。Microsoft から CrashPlan に「アーカイブを入れられないか」と声がかかったという経緯です（超過請求に Microsoft のフィールドチームが困った様子だったとも語られています）。

| 項目 | 発表で語られた内容 |
| ---- | ---- |
| 契約 | 最初の 5 年間のソリューションに 30 万ドル |
| 削減額 | 初期の時点で 70 万ドルの削減 |
| ROI | 1 年目で 110% |
| 管理データ量 | 3.4 PB を管理、うち 2 PB 超をアーカイブ |
| 移行先 | Azure Blob |

スロットリングの上限にできるだけ近づけて大量のデータを移すため、スループットを最大化する工夫をしているとも説明しています。

Indiana University から得た教訓として、登壇者は 2 点挙げました。1 つ目は、**単にストレージを買い足さない** こと。調達部門は 1 か月目の請求書は支払い、2 回目の請求書が来たときに議論が始まるはずだという話です。2 つ目は、超過のコストを、データのライフサイクル管理ソリューションに振り向けることです。さらに、登壇者が過去 18 か月で約 500 の顧客と話した中で、ユーザーに行動を変えさせることができたのは Missouri State University の 1 社だけだったそうです。ユーザーにファイルを消すよう言っても難しいため、日々の仕事の流れを変えさせるべきではないという考えです。

アーカイブで空いた分は、E5 や E7 ライセンスの追加や、AI に使う余裕に回せるという話もありました。

### 5.7 事例：Hyatt

Hyatt は世界的に展開する企業ですが、実態は 3,800 の独立所有・独立運営の施設のネットワークで、各施設には技術の専門家がほとんどいません。Hyatt が把握しているだけで 5 種類のバックアップ製品が使われていました。5 大陸にまたがるため、欧州の GDPR など国ごとのデータ主権要件にも対応が必要です。

進め方は次のとおりです。

1. CrashPlan の紹介後、3 か月かけてセキュリティテストを実施し、SOC などの要件をすべて満たした。Azure の機能によって、要件の一部は確認項目として満たされた。
2. 最初の 7 拠点は中国で開始した。
3. 中国では、現地規制に準拠した形の Azure が運用されており、ソフトウェアから見れば Azure と同じに見える。そのため CrashPlan のようなソリューションが要件を満たしやすい（Microsoft 側の登壇者の説明）。
4. 中国での導入がうまくいった後、北米、欧州、南米、アフリカ、オーストラリアに展開した。

結果として、世界で一貫した見た目・操作性のもと、バックアップが初めて一貫して行えるようになったと説明しています。ローカルでの管理を持ちつつ、本社側から概観を見て支援することもできます。

### 5.8 G2 での評価

あわせて、コンテンツ検索、異常検知、アーカイブの復元・呼び戻し・閲覧は、管理者・セルフサービスのどちらでも使えること、追加費用は無いことが改めて整理されています。

## 6. デモ・手順

デモは、セッション後半にあります。Randy 氏が「AI query デモ」と呼ぶもので、Teams から CrashPlan の MCP server に自然言語で問い合わせる内容です。登壇者の説明では、MCP server は **既存の CrashPlan 顧客向けに翌月提供予定の新機能** とされています。録音は音声だけなので、画面上の操作や表示の詳細は確認できません。以下は語られた順です。

前提として、Teams 上に「CrashPlan Portal」というチームサイトを接続しており、CrashPlan を導入すれば付属するものだと説明されています。また認証はデモの開始前に済んでいます。

1. Teams で「search for Randy in baseball」と入力した。情報がどこから引かれたかという文脈つきで回答が返ってきた。Randy 氏は、時間があるときは Google 検索の結果と比べており、Google 検索では正しい情報と誤った情報が混在するが、組織が所有するデータから得た情報は正確だ、と説明した。
2. 次に、Microsoft 365 のアーカイブの話題として、MCP server に「2 MB より大きいファイルをすべてアーカイブしたら、どれだけの容量を回収できるか」と尋ねた。ドライラン（dry run）が実行され、ポリシーが表示された。
3. 管理者なら理解できるが自分には難しいとして、「このための計画かスクリプトをください」と尋ねた。ドライラン用のスクリプトが添付され、スクリプトの冒頭部分が示された。Randy 氏は、このスクリプトをダウンロードしてインストールすることもできると説明した。
4. これにより、すでに CrashPlan でバックアップしている顧客は、アーカイブ機能を簡単に作成でき、Microsoft 365 を離れず Teams 内で操作できる、と述べた。

デモの流れの中で、CrashPlan と OneDrive の連携についての質問も取り上げられました。Randy 氏は「OneDrive もバックアップしている」「M365 のコンテンツをアーカイブする」と答え、小規模の顧客向けには OneDrive をバックアップ先として使う方法もあると説明しました。この部分で画面に何が表示されたかは、音声からは確認できません。

アーキテクチャについては、「ベクトルデータベースのコストを避けられる」と語られていますが、具体的な構成は説明されていません。

## 7. 注意点・発表者の気付き

- Randy 氏は、AI を使って製品を使いやすくしている製品が多いことに触れ、「使いやすくするために AI が必要なら、元々それほど簡単な製品ではなかった」と述べています。それは AI の最良の使い方ではなく、バックアップデータが役に立つようになることの方が重要だという考えです。
- 対話型 AI で使うデータは、組織が持つ SharePoint や Exchange のデータの方が、ソーシャルメディアやニュースフィードよりも正確で関連性が高いという主張です。
- Azure 以外のストレージターゲットも使えますが、Azure 固有の機能は使えない場合があると述べています。
- 超過料金の請求は、最初の月は支払われてしまい、2 回目から議論が始まるという指摘がありました。
- 登壇者は、ユーザーに削除や保存の抑制を求める方法はうまくいかないと述べています。
- MCP server の Teams からの操作は、認証とロールベースのアクセス制御の範囲内に限られます。
- 発表では、料金体系（CrashPlan 自体のライセンス料）、提供開始日（「来月」のみ）、サポートされるリージョンの詳細などについては触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **コスト**：Microsoft 365 の超過料金（1 TB あたり年間 2,400 ドル）の回避。Indiana University では、100 万ドルの超過請求に対して 30 万ドルの 5 年契約で、初期の時点で 70 万ドルの削減、1 年目の ROI 110% と説明されている。
- **使い勝手**：ユーザーはアーカイブ後も SharePoint、OneDrive、Exchange で従来どおりデータにアクセスでき、HTML プレビューで復元せずに閲覧できる。
- **復旧の選択肢**：Microsoft 365 が使えなくても、ローカルデバイスへの復元、PST への書き出し、OneDrive ファイルへのアクセスができる。
- **セキュリティ**：異常検知、ランサムウェア警告、マルウェアスキャンが追加料金なしで含まれる。
- **グローバル展開**：Azure のリージョン間の一貫性により、Hyatt は 5 大陸で同じ操作性のバックアップを実現した。
- **Azure の耐久性・冗長化**：LRS / ZRS / GRS / object replication から選べ、smart tiering で階層の判断を自動化できる。
- **対応範囲**：すべての Microsoft 365 ライセンス、Google Workspace、サーバー、エンドポイントに対応する。

## 9. まとめ

CrashPlan は Azure 専用に作った軽量な SaaS として、Microsoft 365 のバックアップだけでなく、容量超過料金を避けるためのアーカイブを提供すると説明されたセッションでした。Azure 側の 3 コピー相当の耐久性、階層化と smart tiering、ZRS / GRS / object replication といった冗長化の選択肢が、その土台になっています。

Indiana University では 100 万ドルの超過請求に対して大幅なコスト削減を、Hyatt では中国を含む 5 大陸での一貫したバックアップを実現したと紹介されました。最後のデモでは、Teams から MCP server に問い合わせ、アーカイブで回収できる容量の見積もりとドライランのスクリプトを得る流れが示されました。権限は認証とロールベースのアクセス制御で守られると説明されています。
