# BRK371 Why Azure is the best cloud for SQL

## 1. はじめに

このセッションは、SQL Server や SQL 系のワークロードを抱える開発者・IT 担当者に向けて、「なぜ SQL の置き場所として Azure が最適なのか」を説明するものです。話の流れは、アプリケーションとデータベースのモダナイズ、AI アプリケーションの構築、Fabric との連携、そして多数のデータベースの運用管理、という順番です。

モダナイズの進め方は、Azure Catalyst で環境全体を調べて計画し、データベースを Azure SQL Database Hyperscale に移し、Microsoft Foundry で AI を足し、Database Hub と database agents で運用する、という道筋として提示されました。顧客事例として H&R Block の Sameer Agarwal 氏が、SQL Server への移行から Azure SQL Hyperscale への標準化まで、8 年間の経験を語っています。デモは 3 本あり、いずれも Pam 氏が担当しました（6 章を参照）。

## 4. 発表者が伝えたいメッセージ

Priya 氏の主張は、「SQL をどこでも動かせるが、Azure には Microsoft が 1 つの SQL エンジンを一貫して提供する強みがあり、モダナイズから AI、分析、運用までを 1 つの道筋で進められる」というものです。冒頭で、自分が SQL チームの VP of product である点にも触れたうえで、Azure が最適な理由を説明すると話しています。

主な論点は次のとおりです。

- アプリケーションこそが事業を動かすもので、可用性は技術要件ではなくビジネス要件である
- 同じ SQL エンジンが、Azure（Azure SQL MI、SQL DB、SQL Hyperscale）、他のクラウド（AWS、GCP）、SaaS の形態で使え、アプリは書き換え・移行し直しが不要で、同じ T-SQL の範囲で動かせる
- モダナイズを今すぐ考える理由は、AI 対応、セキュリティ、コストの 3 つ
- 運用データを取り出さず、データのある場所に AI を持っていく

## 5. 発表内容の詳細

### 5.1 顧客が求めていることと、1 つの SQL エンジン

Priya 氏はまず、どの業界でも、アプリケーションが事業を動かしていると指摘します。例として、売上処理、価格設定、顧客向けの決済、ロイヤルティ、サプライチェーン、不正検知、SaaS 製品などを挙げました。そして顧客が考えている問いとして、明日も動くか、新しい顧客・データ・トランザクションを増やす余地があるか、AI の用途を足せるか、スケールできるか（過剰にプロビジョニングしたくない）、常に利用できるか、を挙げています。

Microsoft の SQL は、35 年以上の歴史を持つ 1 つの一貫した SQL エンジンです。昨年 GA した SQL Server 2025 で AI 機能も備え、同じエンジンが Azure 上の Azure SQL MI、SQL DB、SQL Hyperscale として使え、AWS や GCP にも、SaaS の形態でも展開できると説明しています。データを OLTP データベースから出さずに AI を持ち込み、責任ある AI（セキュリティ、ガバナンス、信頼）の枠組みも組み込む、という考え方です。アプリは T-SQL の 1 つの面（surface）で、別のデプロイ形態に持っていけます。

### 5.2 なぜ今モダナイズするのか

オンプレミスで SQL を動かしている人が、「なぜモダナイズするのか」と問うことを想定し、3 つの理由が示されました。

| 理由 | 説明 |
| ---- | ---- |
| AI readiness | データセンターで動いていても、エージェントはレガシーシステムにアクセスできない。Oracle、Sybase、DB2 など他のエンジンでも同じ。AI が届かないデータでは AI のユースケースを動かせない。調査に基づく数字として、企業のデータの 70% 超がサイロ化したデータベースに閉じ込められている、と紹介された |
| Security | オンプレミスではセキュリティの責任を自分で負い、パッチ適用が難しくなる。agentic な脅威が脆弱性を突く可能性がある（データ侵害の解決時間に関する統計も出ましたが、数値は音声で読み上げられていません） |
| Cost | 古いシステムの維持は、サーバーやメモリのコストが時間とともに高くなる。PaaS に移ると総所有コストを下げられる |

PaaS に移すと、パッチは継続的に当たる、とも述べています。また、アプリのコード変換は AI で容易にできる一方、運用の準備、運用プラクティス、セキュリティ、性能、可用性、認証・コンプライアンスなどへの投資も、Azure 上で大きな中断なくモダナイズできると説明しました。新規アプリを作る場合も、既存のスキルと投資を活かせる、という流れです。特にモダナイズと新規開発の両方に向く選択肢として、Azure SQL Database Hyperscale を挙げています。

移行の道筋は 2 つです。1 つは lift and shift で、データセンターを出たい場合に VM（SQL VM）へ移し、アプリは AKS で動かします（フルコントロール）。もう 1 つは PaaS へのモダナイズで、コスト削減と生産性向上が見込めます。データセンター撤退や VMware 撤退に取り組み、AI インフラを自前で買いたくない顧客が、まず VM に出てから Azure SQL PaaS にモダナイズする流れが多い、とのことです。

### 5.3 顧客事例: H&R Block（Sameer Agarwal 氏）

Priya 氏が質問し、Sameer 氏が答える形式でした。

**移行の始まり。** 2018 年から数えて 8 年（現在 2026 年）になります。当時は、クラウドに持っていけないデータセンターのラック（メインフレーム、Netezza のボックスなど）をどうするかが課題でした。そこで SQL Server への移行を、ある程度「計算されたリスク」として選びます。5 ラック分のシステムを、2 台のピザボックスのようなサーバーに移した、と冗談を交えて話しています。リスクを取れたのは、事業の半分がすでに SQL Server で動いていたからです。この経験が、クラウド（Azure は選択肢に入っていた）への移行への自信になりました。最も難しい問題を解いたので、残りも Azure のデータサービスに合わせられる、という考えです。その後、複数あった ETL ツールの戦略を整理しました。

**1 つのエンジンに標準化した理由。** 50 年の歴史のある会社なので、あらゆる種類のデータベースが混在していたそうです。この 3、4 年はそれを簡素化しています。理由は、技術が増えると、それぞれに優れたエンジニアを何十人も確保できなくなり、4 月 15 日のような繁忙日に担当者が休んでいると事業に影響しかねないから、というものです。エンジンが動いていなかったわけではなく、クラウドへ移るなら構成を簡素化すべきだと判断しました。結果として、あるチームや案件でうまくいかないとき、専門知識を他へ展開できるようになり、パッチ適用と保守が楽になり、契約の数も減りました。

**Hyperscale を選んだ技術要件（季節性）。** 米国の確定申告では、1 月に W2 が届いてシーズンが始まり、4 月 15 日が申告期限で、10 月 15 日までに申告を終えないと、大きなペナルティがかかります。つまり、大きなピークが 2 回、小さなピークが 1 回あります。オンプレミス時代は、年間を通じてピークに備える構成にしていたため無駄が大きかった、とのことです。Hyperscale では、ピークに対応しつつ、普段は容量とコストを下げられる、という期待です。スタックを簡素化して節約したうえで、Azure 上でさらに最適化している、と述べています。

**AI のロードマップ。** 検討中のユースケースとして、特定のアプリケーションではなく「顧客体験」を挙げました。企業が 5 つのサービスを提供していて、顧客との接点も 5 つあるとします。それらのやり取りをすべて集め、アプリ単位ではなくクライアント単位のリポジトリを作る構想です。H&R Block のデータ量でも Hyperscale が耐えられるという高い確信がある、とのことです。5 か所それぞれで MCP を有効にする必要が無く、1 つのエコシステムにまとめられる点が利点です。次の段階として、RDBMS 内でベクトル（vector）の概念を使い、クライアントや税務の専門家、カスタマーサービスに別の体験を提供できないかを考えています。従来の AI/ML ワークロードを置き換えるわけではなく、運用ワークロードとベクトルを組み合わせると速くできるものがある、という整理です。

### 5.4 Azure Catalyst

Priya 氏は、今週発表された Azure Catalyst を紹介しました。データベースだけでなく、アプリ、インフラ、ネットワーク、ストレージを含めたワークロード全体をモダナイズするためのもので、次の特徴が語られています。

- 環境全体を調べ（discover）、モダナイズの道筋を計画する
- 推奨の wave plan（移行の波の計画）を出す
- その中で、SQL ワークロード向けに適切なデータベースも推奨する
- データベース部分の実行と最適化には、Azure Database Migration のツール体験を使う
- 発表者はこれを agentic modernization と呼んでいる

### 5.5 SQL と Microsoft Foundry で AI アプリを作る

すでに Hyperscale で AI のユースケースを始めている顧客として、DocuSign、Point Click Player（音声認識の都合で表記が確定できません）が例に挙がりました。ユースケースは、ドキュメント処理、コード生成、パーソナライズされた推奨、チャット with my data、不正検知、コンテンツ生成、カスタマーエクスペリエンスです。

構成は **SQL + Microsoft Foundry** です。

- システムオブレコードのデータは SQL（Hyperscale）にある。これを、用意されている SQL MCP server で簡単に公開できる（AI ready な API、MCP エンドポイント）
- モデルは Foundry 経由で使い、モデルのライフサイクル管理も Foundry で行う
- 管理された SQL アクションを、エンタープライズのガードレール付きで安全に実行できる
- セットアップは容易で、インストールも接続も不要。開発者向けに事前に配線されている

### 5.6 SQL と Fabric

自社開発のアプリをモダナイズしたあとに、SAP、銀行系アプリ、CRM のようなサードパーティのアプリのデータも含め、全体を AI 向けに準備する段階として、Fabric が位置づけられています。ここで 1 日目の基調講演で触れられた Microsoft IQ に言及し、各層でのインテリジェンス（下から、Azure へのモダナイズ、SQL と Foundry による AI の追加、Fabric での推論）として説明しました。

- **OneLake。** 「データにとっての OneDrive」と説明。オンプレミス、他のシステム、他のクラウドなど、どこのデータでも zero ETL で統合でき、ショートカットを作れる。データは分析向けの Delta Lake 形式でミラーリングされる。取り込みやショートカット、複製に課金はしない（"All of this is free"）
- **SQL のミラーリング。** 運用データを OneLake にミラーリングでき、セットアップは不要。ニアリアルタイムのレプリケーションで zero ETL
- **Fabric IQ。** OneLake にデータが集まったら、semantic model と ontology で、データの構造ではなく事業の動き方を定義する。製品、注文、顧客の意味、関係、主要指標などを定義する。エージェントには文脈が必要で、顧客・製品・純売上の定義を知っていれば、企業の文脈で行動できる、という理由です。Fabric では AI-guided authoring が使える

### 5.7 Database Hub と database agents

「それでも自分でデータベースの資産を管理しなければならない」という問いに対し、今週 Database Hub の一般提供（GA）が発表されました。これは、SQL Server、Azure SQL、SQL DB Hyperscale、Cosmos DB、Postgres、Horizon DB（音声認識の都合で表記が確定できません）などをまとめて管理する、フリート管理機能です。可観測性、性能とセキュリティの単一画面、最適化を提供します。さらに、何百、何千というデータベースの管理は人の手ではもはや不可能だとして、database agents も提供されています。

デモは 3 本ありました。どれも Pam 氏が担当し、ビデオを再生する場面が確認できます（1 本目はビデオの再生に手間取っていました。クロスデータベースクエリの部分がビデオかライブ操作かは、発話からは判別できません）。画面の細部は音声からは確認できないため、語られた範囲に限って書きます。

### 6.1 デモ 1: Azure Catalyst とクロスデータベースクエリ

シナリオは、Caldova Pharmaceutical という会社の移行をシミュレーションするものです。この会社は、環境全体をモダナイズし、コストを最適化しつつ、レジリエンスも保ちたいと考えています。

1. プロンプトから始まる。Catalyst がそのプロンプトを分析し、計画を作る
2. 既存の ServiceNow のインベントリ情報を使って、AI が環境全体（DR クラスターやネットワークを含む）をマッピングする
3. アプリケーションを、ビジネスの複雑さと重要度で整理する
4. 上記の情報から、landing zone（モダナイズに必要なインフラ）を提案する。提案は well-architected framework のベストプラクティスに基づく
5. アプリケーション設計に進む。例として Caldova Asset Managers が表示され、アプリ全体のアーキテクチャが提案される。SQL Server クラスターの移行先には、Azure SQL Database Hyperscale Elastic Pool が提案される
6. 実行計画では、wave に分ける。Caldova Asset Manager は、データベースが古くセキュリティ上のリスクがあるため優先度が上がり、第 1 wave に入る
7. wave を実行する。インフラに続き、データベースの Hyperscale への移行、ファイル共有の Azure Files への移行などが、1 つの計画に載っている
8. データベースチームは、計画に従ってデータベースを移行するためのツールを、Catalyst の中で使える。全体の中での自分の作業の位置づけも見える（ツール切り替え不要）
9. データベースが移ったら、開発者が GitHub Copilot でアプリを開き、テストして、Azure にデプロイする

続いて、クロスデータベースクエリの確認です。今回発表された、Hyperscale でのクロスデータベースクエリ機能（Hyperscale Elastic Pool）に関するデモです。

1. Asset Manager は、inventory、reporting、sales の 3 つのデータベースを持ち、3 部構成の名前（three-part naming）でクロスデータベースクエリを使っている。レポーティングビューや、アドホッククエリが例として示される
2. まず SQL Server 上で、そのコードを実行して成功することを確認する
3. 次に、3 つのデータベースを Hyperscale Elastic Pool に置き、クロスデータベース機能を有効にする。コードを変えなくて済むよう、データベース名は同じにしてある
4. Management Studio に戻り、Hyperscale のデータベースに接続していることを確認し、同じビューと同じアドホッククエリを実行する
5. データベース名を変えておらず、同じ elastic pool にあるため、コードの変更なしで動く

### 6.2 デモ 2: ローカル開発から Hyperscale へ

背景として、開発者がノート PC でローカル開発したい、しかも Azure SQL で動くものと同じコードで、という要望が長く寄せられていた、と説明されています。そこで **Azure SQL local container** が使えます。開発者のマシンで動くコンテナーで、Azure SQL Database と同じエンジンです（シミュレーションではない、と強調）。

1. 題材は、花を買う Web ショップ「Golnara」（音声認識の都合で表記が確定できません）。色、カテゴリ、イベントで検索するのが従来の方法だが、意味や気持ちで検索できるようにしたい
2. Visual Studio で、数回のクリックで Azure SQL database のローカルコンテナーをデプロイする
3. アプリはローカルで動き、データベースは他のデータベースと同じように参照できる
4. 追加したい機能は、「友人の就職祝いに、喜びを感じる、暖かい色、元気の出る花」のような感覚的な検索
5. そのために embeddings が必要で、Foundry で embedding model を用意する（Foundry プロジェクトを作り、埋め込みモデルを選ぶ）
6. コード側で SQL を embeddings に向け、embeddings とベクトルデータ型を作り、**vector similarity search**（値ではなく意味で検索）ができるようにする
7. 準備ができたら、Visual Studio Code から Azure に直接デプロイする（アプリも含む）
8. この例では Azure SQL Database Hyperscale を選ぶ。スケーラビリティのためで、コードは同じ。クラウドのデータベースに接続しても、同じコードで動く
9. Hyperscale Serverless を選ぶ。小さく始めて、アプリの成長に合わせて Hyperscale が成長し、可用性の高いデータベースになる
10. アプリがクラウド上で動いていることを URL で確認する。「喜びの花」が表示される

発表者は、開発者向けに **Azure SQL Developer Hub** で開始できると案内しています。

### 6.3 デモ 3: Database Hub と database agents

DBA の朝の始まりを想定したデモです。

1. Fabric Database Hub で、データ資産全体を見る。何千のデータベースでも、SQL、Postgres、Cosmos DB をまとめて管理できる
2. カテゴリ別の主な課題（セキュリティ、性能、最適化の機会）が表示される
3. 性能を開く。Microsoft SQL、PostgreSQL、Cosmos DB のデータベースが 1 つのツールに並び、過去の傾向分析と現在の状況の両方を見られる
4. ダッシュボードの監視に時間を使いたくないので、database agent を設定する。全データベースを対象にするか、重要なものだけを選べる。サポートされるシナリオ全部を見るか、必要なものだけを選ぶこともできる
5. エージェントが環境を監視し、問題が一覧に出る（並べ替えやフィルターが可能）
6. 長時間実行されているクエリを開く。エージェントが、要約、推奨アクション、分析、結論に至るまでの調査内容を示す
7. 詳しくない DBA（accidental DBA）は、Copilot を使って「これは何を意味するか、根本原因は何か、何をすべきか」を尋ねられる。判断の根拠となったデータも示される
8. 熟練 DBA は、そのままクエリの分析に進める。推奨の実施は、慣れたツールに移って行える

発表者は、ユーザーが問題を見つけるのを待たず、エージェントが先に見つけるため、問題が起きる前に対処できる、と締めています。

## 7. 注意点・発表者の気付き

- モダナイズは、データベースだけでなく、アプリ、インフラ、ネットワークを含むワークロード全体で考える必要がある（Catalyst の前提）。
- クロスデータベースクエリを使うアプリでは、デモのとおり、データベース名を同じにし、同じ elastic pool に置くことで、コード変更なしに動いた。
- H&R Block では、移行当初の SQL Server への集約を「計算されたリスク」と表現している。また、エンジンを標準化する理由として、複数技術のエキスパートを確保しにくいことを挙げている。
- 古いデータベースは、セキュリティリスクとして移行の優先度を押し上げる（デモ 1 の例）。
- 発表者は冒頭で、「SQL はどこにでもインストールできる」「選択肢があることは分かっている」と前置きしており、他のクラウドでも SQL は動くことを認めている。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

- **H&R Block:** エンジンの標準化により、パッチ適用と保守が楽になり、契約数が減った。専門知識を他のチームや案件に展開できる。オンプレミス時代は通年でピーク対応の構成にしていて無駄が大きかったため、Hyperscale でピークに合わせつつ普段は容量とコストを下げることを目指している（実際の削減効果の数値は語られていません）
- **PaaS へのモダナイズ:** 継続的なパッチ適用、総所有コストの低減、生産性の向上
- **コード変更が不要な移行:** Hyperscale Elastic Pool でクロスデータベースクエリが動く（デモ 1）
- **ローカルと Azure の一貫性:** ローカルコンテナーと Azure SQL が同じエンジンで、同じコードを使える（デモ 2）
- **運用の自動化:** Database Hub と database agents で、多数のデータベースの問題を先に検知できる（デモ 3）
- **コスト面の支援:** Cloud Accelerate Factory による移行コスト 0 の選択肢（営業担当に連絡）

## 9. まとめ

Priya 氏の整理では、Azure は、モダナイズのツール、開発者が AI アプリを作れる環境（最新の AI インフラと Foundry models）、Microsoft IQ による推論、の 3 つを 1 か所で提供します。推奨する道筋は、Azure Catalyst で発見・計画し、データベースを SQL Hyperscale に移し、Foundry で AI を足し、Database Hub と database agents で運用する、というものです。

セッションで紹介された主な項目は、Azure Catalyst、Hyperscale Elastic Pool のクロスデータベースクエリ、Azure SQL local container、Database Hub の GA、database agents、DP800 認定資格です。顧客事例の H&R Block は、2018 年に始めた SQL Server への移行を経て、季節変動の大きい税務事業のために Hyperscale への標準化を進めています。
