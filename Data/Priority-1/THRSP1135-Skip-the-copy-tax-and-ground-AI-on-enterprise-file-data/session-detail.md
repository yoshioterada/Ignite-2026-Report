# THRSP1135 Skip the copy tax and ground AI on enterprise file data

## 1. はじめに

このセッションは、企業のファイルデータ（SMB / NFS 上の非構造化データ）を、コピーせずに AI のグラウンディングに使う方法を紹介する約 25 分のシアターセッションです。使うのは Azure NetApp Files と、Azure Storage の「BLOB access point」という新しい機能です。

AI を使うために、データを別のストレージにコピーし、同期し、ガバナンスをかけ直すコストを、登壇者は **「copy tax（コピー税）」** と呼んでいます。発表では、ウィンドファーム（風力発電所）を運営する架空の企業 Contoso を題材に、3 本のデモ動画で「コピーなし」の構成を見せます。

- Microsoft Foundry の agent を Azure NetApp Files 上のデータにグラウンディングし、回答の根拠をたどる。
- 同じ agent を Microsoft 365 Copilot から使う。
- VS Code の GitHub Copilot から MCP server を使い、Azure NetApp Files のボリュームを自然言語で拡張する。

## 4. 発表者が伝えたいメッセージ

登壇者の主張は、**AI のためのデータコピーは避けられる**、というものです。AI を使うたびにデータのコピーが 1 つ増え、そのたびにガバナンス、データ保護、コストの問題が生じます。Azure NetApp Files の同じデータを、ファイル（NFS / SMB）と、オブジェクト（REST API / BLOB access point）の 2 つの窓口で見せれば、1 つの管理されたデータセットのまま AI に使えます。

「ガバナンスされた 1 つの source of truth、1 つのデータセット」を保ったまま、AI を使う場面も、AI でプラットフォームを管理する場面も扱えます。デモでは、データが更新されると agent の回答も変わり、その回答が元のレコードにたどれることが強調されています。

## 5. 発表内容の詳細

### 5.1 課題：AI がエンタープライズデータに届かない

登壇者は、多くの顧客が AI を最大限に活用したいが、AI は企業データに届かない、と述べています。AI のために管理された経路がないためです。その背景として、次の数字を挙げました（聞こえた数字のままで、出典の説明はありません）。

| 項目 | 発表での数字 |
| ---- | ---- |
| 10 年の終わりまでに、非構造化データが占める割合 | 約 80% |
| ハイブリッドクラウド環境で動く顧客 | 約 75%（「roughly, 73%」とも発言） |
| 本番に至る前に放棄された AI プロジェクト（これまでの実績） | 60% 超 |
| 「AI をスケールする準備ができている」と答える組織 | 70%（"only 70%" と発言。音声認識の都合で確定できません） |

ファイルデータは SMB・NFS ベースでオンプレミス、クラウド、エッジに分散しています。一方で AI プロジェクトは、ファイルとは別のインターフェース、典型的にはオブジェクトアクセスを求めます。さらに、ガバナンス、セキュリティ、ポリシーは、コピーを作るとデータと一緒には移動しません。

### 5.2 Copy tax：1 つのデータセットに 4 つの請求書

登壇者は、AI を動かすための回避策がどれも、少なくとも 1 回はデータのコピーを作る、と指摘します。コピーごとにガバナンス、データ保護、コストの問題が生じるため、これを copy tax と呼びます。1 つのデータセット（プライマリのデータソース）に対して、**4 つの請求書** を払うことになる、という説明です。

1. データを保存するコスト
2. 同期されたコピーを維持するための、データパイプラインを構築・運用するコスト
3. コピーごとに必要になるガバナンス
4. 古い（stale）コピーができることによるリスクへの備え

### 5.3 Azure NetApp Files

登壇者は、Azure NetApp Files は名前に NetApp が付いていても、**Microsoft のファーストパーティのプラットフォームサービス** だと説明しています。エンタープライズのファイルサービスやアプリケーションを動かす基盤で、ポータルから使え、大容量・高性能を確保して、ファイルデータを必要とする要求の厳しいアプリケーションを動かせます。

- **NFS または SMB を使う** ことで、既存のアプリケーションやワークフローを、移行や作り直しなしに、オンプレミスと同じようにクラウドで動かせる。
- 同じファイルデータに **オブジェクトのセマンティクス** を適用し、Object REST API としても公開する。ファイルデータを扱いにくいが、オブジェクトインターフェースには向いているアプリケーションが使える。つまり 1 つのデータセットに 2 つのインターフェースがあり、インターフェースをアプリケーション側が決められる。
- NetApp のオンプレミスや他のクラウドの技術とも統合され、オンプレミスからの replication や caching が製品に含まれる。これにより、オンプレミスのデータを同じ Azure NetApp Files の体験に取り込み、追加のコピーなしに AI を有効にできる。

### 5.4 題材：Contoso Wind Farm

Contoso Wind Farm は、風力タービンを作り、保守する技術系の組織という設定です。CAD ファイルや simulation ファイルなどの設計データといった、大量のエンジニアリングデータを持ちます。生産が始まった後は保守が必要になり、それが次の課題になります。

アーキテクチャは単純です。アプリケーションが Azure 上の Azure NetApp Files にファイルを書き込み、生産や保守のためのデータ処理パイプラインを多数運用しています。ところが、利用可能な AI のモデルやサービスには、この会社の領域知識がありません。コピーしない限り、データをモデルに渡せず、それが governance の問題と copy tax を生んでいました。顧客が望んだのは、データを AI に持っていくのではなく、**AI をデータに持ってくる** ことです。

### 5.5 BLOB access point

これを実現するために使うのが、Microsoft Storage が導入した新機能の **BLOB access point** です。登壇者の説明では、Azure Storage 内の仮想化レイヤーで、Azure NetApp Files を、あたかも Azure Storage アカウントであるかのように見せます。BLOB API で Azure Storage と話すアプリケーションは、同じインターフェースで Azure NetApp Files と話せます。

重要なのは、これはコピーではない点です。データをいったんストレージアカウントに移してから配信するのではなく、直接ストリームとして出入りします。この機能により、OneLake、AI Search、Foundry のいずれからでも、既存の Azure NetApp Files のデータに対して、コピーなしで AI サービスを有効にする構成を作れます。

アーキテクチャ図の説明では、左にアプリケーションパイプライン、中央に Azure NetApp Files の非構造化ファイルデータがあり、Object REST API と BLOB access point を通じて、AI サービスにデータが透過的に届きます。

### 5.6 「4 つの請求書」がなくなる

デモ 2 の後で、登壇者は copy tax の話に戻ります（「領収書を持ってきましょう」という言い方でした）。コピーが 1 つで請求書が 4 つあった状況が、次のように変わると説明しています。

- 重複したデータセットを作らない。
- コピーの同期パイプラインを維持しない。
- ガバナンスをかける別のコピーがない。
- データは 1 つのデータセットでガバナンスされるため、信頼性も同じ。

結論は「zero copy, zero duplicates, therefore zero extra cost」です。データがオンプレミスにあっても他のクラウドにあっても、Azure NetApp Files で利用可能にできる、とも述べています。

## 6. デモ・手順

このセッションにはデモがあります。登壇者は「ビデオを流します」と述べ、3 本のデモ動画を再生しています（動画のナレーションで語られた範囲のみを書きます）。録音は音声のみのため、画面の細部は確認できません。

### 6.1 デモ 1：Foundry agent を Azure NetApp Files にグラウンディングする

シナリオ：Contoso Energy は風力発電所を運営し、ドローンでタービンを検査しています。タービン T14 の新しい画像の解析で、疑わしい hairline crack（微細なひび割れ）が見つかります。AI は過去の検査画像を調べ、ひび割れの進行や気象条件の影響を探ります。Contoso の予防的ルールにより、調査の間、T14 は運転停止になります。

構成の説明：

- 画像、検査レポート、ステータスレジスタは、チームが使っている **Azure NetApp Files のボリューム** に置いたまま。
- Azure NetApp Files の Object REST API が、同じファイルへのオブジェクトベースのアクセスを提供する。
- private connection と BLOB access point を通じて、OneLake と Azure AI Search が標準の BLOB API でデータにアクセスする。
- Foundry agent が、index のレコードを使って T14 の状態を説明し、出典を示す。

ポータルでの確認（語られた順）：

1. Azure NetApp Files のボリュームから始める。検査画像と運用記録がすでにある場所です。
2. bucket が、同じファイルへのオブジェクトベースのアクセスを提供している。
3. 接続は private で、BLOB access point 用に作られた private endpoint があり、接続は承認済みである。
4. BLOB access point の構成を見る。データソースは Azure NetApp Files で、access point は active。ネットワークの項目で、private link service への private connection を使っていることを確認する。
5. Fabric では、あるフォルダーが Azure NetApp Files 上のデータへの OneLake shortcut（トランスクリプトの表記は "OneLink shortcut"）になっている。ソースデータのコピーを作らずに、既存のレコードにアクセスできる。
6. Azure AI Search では、index が BLOB access point 経由の取得を支えている。元のレコードは Azure NetApp Files に残ったまま。ここで T14 の検査記録が search index に表示される。
7. その search index を Microsoft Foundry の knowledge base に接続しており、agent がそこからレコードの情報を取得する。
8. ナレーションは「gateway VM も、ソースデータの同期ジョブもなく、既存のデータが AI から使える状態になった」とまとめる。

Foundry playground での質問と回答：

1. agent を Foundry playground で開き、「T14 は運転に復帰してよいか」と質問する。
2. 回答は **「いいえ」**。検査レポート IR2291 が、ブレードの疑わしいひび割れを記録し、ステータスレジスタがタービンの運転停止を示している、と答える。
3. citation（引用）を開くと、回答の根拠になった実際の検査レポートが、先ほどの Azure NetApp Files のボリュームに保存されている。ナレーションは「グラウンディングされているとは、たどれるということ」と述べる。

データが変わったとき：

1. 別のコピーなら、回答は最後の同期の時点までしか新しくない、という問題提起から始まる。
2. 現場のエンジニアがブレードを検査・修理し、修理を承認し、チームがタービンのステータスレジスタを更新する。
3. 2 つのレコードは、これまでと同じ Azure NetApp Files の共有に保存される。
4. Azure AI Search の indexer が変更を拾い、更新された情報が Foundry agent で利用可能になる。
5. Foundry playground で同じ質問をすると、今回の回答は **「はい」**。修理が承認済みで、ステータスレジスタに反映されており、回答は修理記録 RS0147 を引用する。
6. 「同じ agent、同じ質問、違う答え」。移行も gateway も、ソースデータの 2 つ目のコピーも不要で、画像とレコードは Azure NetApp Files に残っており、レコードが変わると回答も変わり、どちらの回答も元のレコードにたどれた、とまとめている。

デモの後、登壇者は、Contoso の非構造化ファイルデータが、コピーなしで AI から使えるようになった、と整理しています。顧客は、アプリケーションを Azure に移行・モダナイズし、ハイブリッドのモビリティの選択肢でクラウド間を移動でき、データがどこにあっても、コピーなしで AI を有効にできる、という説明です。

### 6.2 デモ 2：同じ agent を Microsoft 365 Copilot で使う

1. 設定：Sam は Contoso の site operations manager で、日常の業務で Microsoft 365 Copilot を使っている。そこに inspections agent が使えるようになった。別のアプリケーションに切り替える必要も、2 つ目の agent を作る必要もない。
2. Sam が「どのタービンが運転できず、その理由は何か」と質問する。
3. 結果として、T12 は bearing（軸受）の交換待ちで、復帰予定は 11 月 13 日。T13 は稼働中だが、出力が低下している。T14 は運転停止の一覧に入っていない。デモ 1 で運転に復帰したタービンである。
4. agent は、Foundry playground で見せたのと同じグラウンディングされた情報を使っている。
5. フォローアップとして「T14 の修理を承認したのは誰か」と質問する。回答は、Dana Whitfield が修理にサインし、Lena Novak が運転復帰を承認した、というもの。どちらも、デモ 1 で使った同じ修理記録に基づく。
6. ナレーションは、左に Foundry、右に Copilot という構図で、「同じ agent、同じグラウンディングされたデータ、違う体験」と整理し、AI プロジェクトと、人が普通に使うものとの違いだと述べる。

### 6.3 デモ 3：VS Code と MCP server で Azure NetApp Files を管理する

シナリオ：T14 の疑わしいブレードのひび割れから、「同様の問題が風力発電所の他の場所にもあるのでは」という疑問が生まれます。Contoso は、タービン全体の総点検を決め、過去の検査画像を、新しいドローン検査と合わせて、発電所全体で再解析する計画です。過去の画像はすでに Azure NetApp Files にあり、新しい検査で画像とレポートが増えるため、必要な容量が増えます。

現状の説明：既存のボリュームはすでに 88% が使用されていて、保存されているデータは 900 tebibytes、空きは 124 tebibytes です。画像が増え、過去データを再解析する前に、容量とスループットの両方を準備する必要があります。

環境：プラットフォームエンジニアが **VS Code** で作業し、GitHub Copilot が、Azure NetApp Files の管理ツールを持つ **MCP server** に接続されている。これらのツールは Azure の control plane で動作し、ボリュームを管理するもので、検査ファイルそのものは読まない、と明言されています。

手順（語られた順）：

1. MCP server を使ってボリュームを照会する。プロビジョンされた容量、使用量、空き容量、現在のスループットを尋ねる。Copilot が MCP server 経由で現在のボリューム情報を取得した。CLI のコマンドも、スクリプトも、ポータルの操作も必要ない、と述べている。
2. 次に、「inspections ボリュームのプロビジョン済み容量を 1.2 mebibytes に、スループットのエンタイトルメントを 4,000 mebibytes per second に増やしてください」と依頼する。容量の単位は音声認識のまま（聞こえた "mebibytes" のままで、確定できません）。
3. Copilot が必要な MCP の操作を特定し、変更の前に **承認を求める**。
4. 変更の完了後、更新された構成を確認する。ボリュームは、プロビジョン済み容量 1.2（聞こえた単位は mebibytes）、スループットのエンタイトルメント 4,000 mebibytes per second になっている。
5. 「自然言語の 1 回の依頼で、今後のワークロードのためのインフラを準備できた」とまとめる。

その後の様子（ナレーション）：Contoso は、過去の検査画像の再解析と、新しいドローン検査の処理を始められる。追加のスループットが大規模解析を支え、拡張したボリュームが新しい検査データの余地を提供する。画像が解析され、潜在的な異常が追加の検査のためにフラグ付けされる。ナレーションは、「Foundry と Microsoft 365 Copilot でデータに問い合わせ、自然言語で大規模検査分析のためのインフラを準備し、その結果を見た。同じデータ、同じ Azure NetApp Files プラットフォームで、データは移動していない」とまとめています。

## 7. 注意点・発表者の気付き

- MCP の管理ツールは Azure の control plane で動作し、ボリュームを管理する。検査ファイルの中身を読むものではない、とデモで明示されています。
- Copilot は、ボリュームの容量やスループットを変更する前に、承認を求めます。
- BLOB access point のコストについては、質疑応答で「コストが発生する可能性はあるが、金額は分からない」とされています（5.7 参照）。
- 数字の単位：デモ 3 では、容量が "1.2 mebibytes" と聞こえますが、既存ボリュームの使用量と空きは tebibytes 単位で語られており、単位が一致していません。音声認識の都合か言い間違いかは、トランスクリプトからは確定できません。
- 登壇者は課題として、ガバナンス、セキュリティ、ポリシーが、コピーを作るとデータとともに移動しない点を挙げています。

## 8. 利用者にとっての利点

発表で語られた利点です。

- データのコピーを作らずに AI をグラウンディングできる。ストレージ、同期パイプライン、コピーごとのガバナンス、古いコピーのリスクという「4 つの請求書」を避けられる。
- 既存のアプリケーションは、NFS / SMB のまま、移行や作り直しなしにクラウドで動かせる。同じデータを、AI サービス向けにはオブジェクトのインターフェースとして使える。
- gateway VM や、ソースデータの同期ジョブが不要になる。
- 回答に出典があり、元のレコードにたどれる。レコードが更新されると、indexer の実行後に agent の回答も更新される。
- 同じ agent を Foundry playground と Microsoft 365 Copilot の両方で使える。別の agent を作る必要はない。
- ポータル、CLI、スクリプトを使わずに、自然言語で Azure NetApp Files の容量やスループットを管理できる。
- オンプレミスや他のクラウドのデータも、同じ Azure NetApp Files の体験に取り込める。

## 9. まとめ

発表の要点は、AI のためにデータをコピーしなくても、Azure NetApp Files の BLOB access point と Object REST API により、ファイルデータを Foundry、AI Search、OneLake から使える、という点です。3 本のデモでは、Foundry agent が元のレコードを引用して回答し、データ更新後は答えも変わり、同じ agent が Microsoft 365 Copilot でも使え、VS Code から MCP server を通じて自然言語でボリュームを拡張できることを示しました。

登壇者は締めくくりに、AI の使い方が 2 通りあると整理しています。1 つはデータに対する実際の利用、もう 1 つは AI を使ったプラットフォーム管理です。後者では、可用性や容量などの管理作業を、ポータル、CLI、スクリプトを使わずに行えます。

始め方として、登壇者は「手持ちのファイル共有を 1 つ選び、agent を 1 つそのデータにグラウンディングして、MCP server 統合で MCP の操作を動かしてみてほしい」と呼びかけています。最後に、ブースでの raffle（抽選）への案内もありました。
