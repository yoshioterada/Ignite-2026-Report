## 5. 発表内容の詳細

### 5.1 Azure HorizonDB が GA

最初に紹介されたのは、PostgreSQL のクラウドネイティブ版である **Azure HorizonDB** です。Satya 氏が当日に GA を発表した、という趣旨の発言があります（聞き取りが不明瞭で、「GAS」と聞こえます）。Microsoft は数年にわたって PostgreSQL コミュニティに貢献しており、コミッターのスポンサー数が最も多く、バージョン 16 から 19 の累計のコミット数は他のどのハイパースケーラーよりも多い、と説明されました。

HorizonDB は、開発者向けの用途とミッションクリティカルな用途の両方を狙ったエンタープライズ向けデータベースで、中身は PostgreSQL そのものです。発表で挙げられた仕様は次のとおりです。

| 項目 | 発表内容 |
| ---- | ---- |
| ストレージ | 128 TB まで対応（さらに拡張する計画） |
| コンピュート | 各レプリカ 192 v-core |
| レプリカ | 読み取りレプリカ 15 台などの構成（レプリカ数の発話は音声認識の都合で正確には確定できません） |
| 可用性 | HA の保証値が発話されていますが、音声認識の都合で数値が確定できません（"49.5" と聞こえます） |
| コミットレイテンシ | ミリ秒レベル |
| 性能 | セルフホストの PostgreSQL と同条件で比較して 8 倍高速 |

アーキテクチャは、数年前に導入した Azure SQL Hyperscale と同じで、コンピュートとストレージを分離した「disaggregated」構成です。流れは次のように説明されています。

1. プライマリレプリカが書き込みを受け付け、ゾーンを考慮した共有ログストアに 1 ミリ秒でコミットする。
2. 書き込みは、ゾーン対応の共有データストレージに反映される（発話は "paid servers" と聞こえ、音声認識の都合で表記が確定できません）。
3. そこから、フェイルオーバー用レプリカを含む多数の読み取りレプリカを増やせる。これらのレプリカはホットなテールログも受け取る。

コンピュートとストレージを個別にスケールできることが、速さとスケーラビリティの理由だと説明されています。詳細は Microsoft のブログに書かれているとのことです。

### 5.2 ベンチマークのデモ（HorizonDB 対 セルフホスト PostgreSQL）

「大きな主張には大きな証拠が必要」という流れで、Shireesh 氏が比較ベンチマークを実演しました（詳細は 6.1）。結論として、セルフホストが約 52,000 トランザクション/分だったのに対し、HorizonDB は約 428,000 トランザクション/分で、8 倍高速という結果でした。

### 5.3 HorizonDB の機能紹介（Charles 氏）

続けて Charles 氏が HorizonDB の機能を駆け足で紹介しました。ポータルでの作成、AI 向けのパイプライン、ハイブリッド検索、グラフ分析、スケールアウトと可視化が含まれます。詳細は 6.2 にまとめています。要点は、**ベクトル検索・全文検索・グラフを、トランザクションデータの上で一貫性を保ったまま使える**ことです。データを別の場所に移さないので、アーキテクチャが複雑にならないと説明されています。

### 5.4 Fabric 上の PostgreSQL と、OLTP/OLAP の統合

次の話題は Fabric です。Fabric は統合された分析プラットフォームとして生まれ、データエンジニアリングやデータ統合、レポーティングなどをカバーする事前統合された SaaS 環境でした。そこにデータベースを加え、シンプルで自律的、最適化された AI 体験を作れる統合データプラットフォームにする、という位置づけです。SQL と Cosmos DB はすでに Fabric で GA で、今回 PostgreSQL、つまり **Fabric 上の HorizonDB** が加わりました。Azure で見せた HorizonDB が Fabric でも同じように動くため、PostgreSQL の方言のまま、運用データ、分析インサイト、AI 機能を ETL パイプラインなしで使えると説明されています。Satya 氏が前日に発表した内容だとも述べています。

背景として、次の課題が語られました。

* OLTP は、低レイテンシ・高スループット・頻繁な更新に向き、分離性が重要になる。
* OLAP は、大規模クエリ、ダッシュボード、レポートに向く。
* 両者の間では、データが分析側に届くまで時間がかかり、リアルタイム性が失われる。データの重複や不整合も起こりうる。さらに、アプリケーションが 2 つのエンドポイントを扱う負担がある。

これに対する構成は次のとおりです。

1. 左側に HorizonDB（行ストアの ACID な運用系）、右側にデータウェアハウスのクエリエンジン（列指向ストレージ）を置く。ウェアハウスのクエリエンジンについては、最近 GPU による高速化を発表したと触れています。
2. データベースが Fabric ネイティブなので、ミラーリングが自動で働き、行ストアから列指向にデータが移され、分析エンジンが最新のデータを参照できる。
3. さらにクエリエンジンを融合する。運用系のクエリは PostgreSQL 側で従来どおり処理しつつ、大規模スキャンのような分析向けの部分は分析エンジンで実行するよう、クエリエンジンが判断する。

その結果、アプリケーションは PostgreSQL の方言のまま **1 つの接続エンドポイントで OLTP と OLAP を扱え**、エンドポイントも SDK も権限モデルも 2 つ用意する必要がありません。

もう 1 つの機能として、**低レイテンシのマテリアライズドビュー**が紹介されました。ミラーリングが「運用系で生まれたデータを分析側に持っていく」ものであるのに対し、マテリアライズドビューは「レイク側で生まれたデータ（例として Parquet や Iceberg）を Postgres 側にマウントし直し、スピードレイヤーとして提供する」ものです。この 2 つで、運用と分析の統合インターフェースを目指すと述べています。

### 5.5 Raven と Fabric apps

Shireesh 氏は、ここ 18 か月でアプリケーション開発に必要な時間と労力が大きく減ったと述べました。以前は数か月から数年かかったものが、いまは数日、ときには数分でできる。これはコーディングエージェントのおかげだとしています。一方で、開発者の速度と、エンタープライズの保証を両立させるところにまだギャップがあるとして、**Raven** を導入しました。

> 注意：製品名は、発話では "Raven" と聞こえますが、一度だけ "Rayfin SDK" とも聞こえます。音声認識の都合で表記が確定できないため、本文では聞こえた "Raven" を使います。

説明された内容は次のとおりです。

* オープンソースの SDK と CLI。Fabric のインフラ上にあり、コーディングエージェントが Fabric のエンタープライズ保証、スケーラビリティ、ガバナンスを利用できる。
* コードファーストのインターフェースで、開発者とエージェントの両方が使える。トークン数を最小に、価値を最大にするよう、クリーンな API スキーマと MCP 統合で設計されている。
* 管理プレーンもあり、IT 担当者や開発者がコンプライアンスとガバナンスを扱える。
* 成果物として **Fabric apps** が作られる。Fabric apps は GA。Power BI 向けに作ったセマンティックモデルを活用でき、運用アプリの上に、データモデルや権限を作り直さずに「流動的な（fluid）レポート」を作れる。
* OneLake のガバナンスハブに app ビューがあり、管理者と IT 担当者が制御と可視性を得られる。
* Microsoft Copilot から Fabric apps を直接構築できる機能が、Frontier プログラムでプレビュー中。複雑なセットアップもインフラ管理も不要とのことです。

デモは 6.3 に記載します。

### 5.6 Azure SQL Hyperscale

次は 2 つ目のクラウドネイティブデータベース、Azure SQL Hyperscale です。使い慣れた SQL エンジンをクラウド向けに調整したもので、HorizonDB と同じアーキテクチャを共有しています。発表された仕様は、128 TB、192 v-core、高可用性は "4 and 1/2" と聞こえる保証（音声のまま）です。コンピュートとストレージが分離されているため、小さく始めても、ストレージやコンピュートの要求が増えたときにデータの再パーティションやアプリの再設計が要らないと説明されています。

新機能は次の 3 点です。

1. **Azure SQL Database Container（パブリックプレビュー）**: ローカルで開発でき、secure enclaves、ledger、ベクトル検索なども含め、SQL のキー機能をローカルで利用できる。クラウドにデプロイしても動くことが保証されると説明されています。
2. **ローカルからクラウドへの SQL デプロイウィザード**: VS Code の Microsoft SQL 拡張機能で使える。ローカルで始めてスキーマの互換性を確認し、準備ができたらクラウドに切り替える。寛大な「永続的な無料枠」も使える。
3. **高密度エラスティックプールでのクロスデータベースクエリ**: Hyperscale で最大 50 データベースまで対応し、今後も増やしていく。あるデータベースのスキーマのテーブルと、別のデータベースのテーブルを結合するアプリケーションを作れる。

### 5.7 Cosmos DB と Azure Managed Redis（Kirill 氏）

Kirill 氏は、Cosmos DB が世界最大級の AI アプリを支えており、そうしたアプリにはリトリーバルやベクトル検索が必要だと述べ、次の発表を行いました。

* **新しい埋め込みモデル "Microsoft Embedding One"**（名称は音声認識の都合で確定できません）。チャートや表を含むドキュメントなど、マルチモーダルなコンテンツ向けに最適化されている。ビジュアルドキュメント検索の有名なベンチマーク（"Vidora 3" と聞こえます。表記は未確定）で最上位。Cosmos DB の embedding generation API から利用でき、Cosmos の外でもこの埋め込みを使える。
* **semantic re-ranker の GA**。検索精度をさらに高める。
* **agent memory toolkit**。エージェントにはメモリが必要で、メモリがないと「毎日新しくなる新入社員」のように、有能でも毎日ゼロから始めることになり、トークンも毎日余計にかかる、という説明でした。Cosmos の AI 機能で作ったエンドツーエンドのメモリ管理システムで、要約、メモリの分類、メモリの調整（reconciliation）のワークフローを内蔵する。サーバーレスで、Mem0 のような一般的な代替手段と比べて 30% 以上のトークンを節約できると説明されています（"up to more than 30%"）。

**OpenAI の事例**として、OpenAI がアプリ全体で 100 を超えるワークフローを Cosmos DB で動かし、チャット履歴、メモリ、あらゆるユーザーインタラクションを提供していると紹介されました。OpenAI の説明として、1 秒あたり 7,000 万を超えるトランザクションを処理し、500 ペタバイト超のデータセットを、毎週 10 億人超のユーザーに提供しているとのことです。続けて OpenAI が学んだことを紹介する動画が流れました。動画の内容は次のとおりです。

* 1.2 billion のユーザーに、高速で信頼できる体験を提供している。OpenAI の規模は特別だが、アプリの要件はほかの利用者と似ている。
* OpenAI のアプリは、"Habitat" と聞こえる共有の Cosmos DB データベースを使う（名称は音声認識の都合で確定できません）。
* Cosmos DB のマルチテナンシーにより、数か月ではなく 1 日で 10 億ユーザー規模にできる。サーバーレスがスケールを処理する。
* 500 ペタバイトのデータ資産を 1 人のエンジニアが管理している。
* ジオパーティショニングにより、グローバルに 1 桁ミリ秒のレイテンシと 5 ナイン（five nines）の耐障害性を提供する。
* コーディングエージェントで変更頻度が 10 倍になるが、スキーマレスの柔軟性により、データモデルを毎日進化させても影響がない。
* エージェントのメモリにも Cosmos DB を使える（Agent Memory Kit）。

最後は「OpenAI にできるなら、あなたにもできる」というメッセージでした。

**Azure Managed Redis** については、Redis 8 を Azure Managed Redis に導入すると発表されました。CPU あたりのスループットが 2 倍以上になり、ベクトル検索、時系列、確率的データ構造といった高度な機能をコアエンジンに備えるため、部品を減らしてリアルタイムアプリを作れると説明されています。

### 5.8 Azure Catalyst によるモダナイゼーション

第 2 章はモダナイゼーションです。理由は前述の 3 点（セキュリティ、コスト、AI）で、ここで **Azure Catalyst**（本日からパブリックプレビュー）が紹介されました。アプリ、データ、インフラの 3 つの面で、エージェントによるモダナイゼーションを統合的に扱う体験で、開発者と IT の両方のニーズに応えます。「発見（discover）、評価（assess）、計画（plan）、実行（execute）」を 3 つの面にまたがって行います。

特徴として挙げられたのは次の点です。

* ワークロードごとにカスタマイズできる。アーキテクチャのニーズ、設定、ポリシー、エンタープライズの知識に合わせたプランとエージェントを理解する。モデルを選べる場合もある。
* 利用者のセキュリティとガバナンスの境界内で動く。

流れは、まず手元の環境（estate）を出発点として、Catalyst が発見と評価を行い、ビジネスプランを作ります。ワークロードごとに、リホスト、リプラットフォーム、リファクタリング、リアーキテクト、置き換え（replace）、維持（retain）のどれが適切かを示します。移行先の例は次のとおりです。

| 対象 | 移行先の例 |
| ---- | ---- |
| VM | Azure managed VMs、VMware solution |
| データベース | 先に紹介したクラウドネイティブなデータベース |
| アプリ | GitHub Copilot を使って Azure Kubernetes Service または Azure App Service へ |

データベース側の取り組みも説明されました。

* SQL Hyperscale: ネイティブに統合された。
* PostgreSQL: 同種・異種の移行（Oracle から PostgreSQL を含む）に、AI ネイティブな機能がある。
* Cosmos DB: AI 支援によるデータ移行。リレーショナルモデリングが合わない場合に、スキーマの移行やパーティショニングを支援する。
* Azure DocumentDB（Mongo API 互換）: Arc 経由で DocumentDB を使え、ハイブリッドやジオレプリケーション、マルチクラウドの構成が取れる。さらに Azure Local にも対応し、ソブリンや規制要件にも応える。

### 5.9 顧客事例: LSEG（Claire Armstrong 氏）

Shireesh 氏との対話形式で、LSEG の事例が語られました。

**LSEG の領域とデータ資産**
Claire 氏の担当は、リファレンスデータとプライシングデータです。このデータは LSEG の製品の 90% で使われ、年間 21 億（"2.1 billion"、通貨は発話されていません）の金融収益を支えています。データベースは同社の中核で、権威あるデータソースである database of record（DBOR）が、リアルタイムの価格データ、リファレンスデータ、役員などの組織データ、企業イベント、ニュースのトランスクリプト、提出書類、サステナビリティ（炭素排出量など）といった幅広いコンテンツを保持しています。

**モダナイゼーションの方針**
モダナイゼーションは大きな投資で、DBOR 資産を変革するために今後 4〜5 年続くとのことです。1 つのデータベース技術に統一するという方針の中心に Azure Cosmos DB を置いており、柔軟性とスケールが理由です。データは年ごとに桁違いに増えています。Cosmos DB のほかに、社内の知識をグラフとして格納する用途で Azure PostgreSQL も使っています。単一のデータベースですべてのニーズを満たせないので、幅広いポートフォリオが必要だと述べています。Azure Catalyst については、取り組みの「ゲームチェンジャー」になるだろうと語りました。

**AI とエンジニアリング**
Claire 氏が挙げた課題は「コンテキスト」です。高品質なコンテキスト（ドキュメント、エンジニアリング標準、信頼できる知識へのアクセス）が高品質な成果を生み、それが効率につながり、SDLC に組み込むほど効率が増すという考えです。AI を最もうまく使うエンジニアは、ビジネス、課題、データを低いレベルまで深く理解し、顧客がそれをどう使うかも理解している人で、エンジニアリングはビジネス分析やプロダクトマネジメントに近いスキルを身につけつつある、とのことです。

エンジニアに投げかけてほしい問いとして、技術選定と同じ質問を AI にも当てはめる、という 3 つが示されました。

1. そのモデルは、やろうとしているタスクに適切か。
2. どんな推論とコンテキストを与える必要があるか。
3. コストはどれくらいか。POC で動かすのと、企業全体で自由に動かすのは大きく違う。

Shireesh 氏は、Azure Catalyst の顧客として LSEG のほか UBS、BlackRock、Nike、NBA などを挙げ、レガシー（リレーショナル、非リレーショナル、ベクトルなど）をクラウドネイティブなデータベースに移そうとしていると述べました。AI のモダナイゼーションもデータから始める必要がある、という趣旨です。

### 5.10 エージェントによる運用: Database Hub と database agents

最後の章では、顧客が 1 台ではなく、数百から数十万にもなるデータベースの群れ（fleet）を扱っているという課題から始まります。

* ヘルスシグナルが、異なるエンジンや環境に散らばっている。問題が運用チームに見える前から、顧客はその影響を受けている。
* セキュリティとコンプライアンス: ポリシーのドリフト、パッチ適用の不整合があり、パッチ未適用のデータベース 1 台が大きな問題になりうる。
* 顧客が求めているのは「データベースを選ぶこと」ではなく「管理すること」。

これに対し次の 2 つが発表されました。

1. **Database Hub in Fabric**（Fabric で GA）: PostgreSQL、SQL、Cosmos など、すべてのデータベース資産にまたがる統合ビジビリティ、オブザーバビリティ、ガバナンスを 1 か所で提供する。
2. **database agents**: データベース資産のヘルスを継続的に監視し、問題の原因を診断して推奨を出す。推奨が効いているかも検証する。さらに、時間をかけて効果を分析し、推奨したアクションを取る手助けをする。「信頼できる自動化」と「明示的な制御」の両立を狙うと説明されています。

SQL ではすでに intelligent query processing に取り組んできており、同じ技術に、テレメトリとモデルのインテリジェンスを組み合わせて、問題を先回りして軽減する、という考えです。デモは 6.4 にまとめています。

## 6. デモ・手順

このセッションにはデモが 4 つあります。録音は音声のみのため、ライブ実演か録画かの区別や、画面上の細かい操作（ボタン名、入力値）は分かりません。以下は、語られた内容の順に整理したものです。

### 6.1 ベンチマークのデモ（Shireesh 氏）

1. セットアップを実行する。左側は、セルフホストの PostgreSQL（ゾーンを考慮した構成）、右側は HorizonDB（共有ログストレージ、ゾーン耐性のあるストレージ）。
2. 両方にデータをロードする。95,000 ウェアハウスのベンチマークで、データ量は 9.1 TB、47 billion 行（ベンチマーク名は "T-proxy" と聞こえ、音声認識の都合で確定できません）。
3. 両側で VS Code の SQL 拡張（PostgreSQL 向け）を起動し、スキーマ、テーブル、データが同じであること（apples to apples）を確認する。
4. ベンチマークを実行する。読み取りと書き込みの両方を含む代表的な負荷で、45 分間続ける旨の発言がある。画面の表示は縮めたものだと断っている。
5. 結果として、セルフホストは約 52,000 トランザクション/分、HorizonDB は約 428,000 トランザクション/分で、8 倍の差が出た。

> 補足：途中でセルフホスト側が「100,000 トランザクション/分」「書き込み側 900,000 トランザクション/分」と話している箇所がありますが、何の数値かは音声からは確定できません。最終的な比較値は上記の約 52,000 と約 428,000 です。

### 6.2 HorizonDB の機能紹介（Charles 氏）

1. ポータルで作成する。クラスターに名前を付ける（"a quick cluster" と聞こえます）。構成では **コンピュートだけを選ぶ**（16 v-core とメモリ）。HorizonDB ではストレージは完全に自動。
2. 「Entra enabled for Postgres」が有効で、エンタープライズ ID を使える。途中で AI 機能もオンにする。
3. Private endpoints は GA、Terraform も標準でサポートされている。
4. AI の例として、2 列だけの suppliers テーブルを使う。ベクトル用の列を追加した新しいテーブルを作り、**DiskANN インデックス**を作成する（pgvector もサポート）。全文検索用に **BM25 インデックス**も作成する。
5. suppliers のデータを enrich テーブルに挿入する。埋め込みモデルが呼ばれ、動作はしたが約 4 秒かかった。
6. **AI pipeline** を設定する。非同期で埋め込みモデルを呼ぶ方式で、作成はメタデータ操作のためほぼ一瞬。VS Code でパイプラインを source から sink までの図で表示でき、中間に埋め込みのステップがある。
7. 同じ INSERT を再実行すると大幅に速くなった。ただし enrich テーブルを確認するとデータはまだない。非同期なので、INSERT はミリ秒で終わり、埋め込みの生成はバックグラウンドで行われるため。トランザクションを切り離し、データベースの性能を守る狙い。
8. ハイブリッド検索の関数を作る。ベクトル検索と全文検索を組み合わせ、**reciprocal rank fusion** で結果をまとめる。
9. 「無菌充填（sterile fill finish）の能力を持ち、ローンチ製品を製造できるサプライヤーはどれか」という質問を実行すると、上位 3 つの候補（Apex、Meridian、Cobalt）が返った。
10. パイプラインに戻り、**グラフの更新も非同期で扱える**ことを示す。グラフはテーブルとは別のデータ構造なので、テーブルへの挿入後にグラフも更新する必要があり、それが性能上の障害になりうるため。
11. グラフを作成する文を示し、クエリを実行すると、上位 2 社が同じ製造工場に依存していることが分かる。その工場には洪水というリスク（濃い青で表示）がある。ハイブリッド検索やベクトル検索だけでは見えない依存関係を、グラフが可視化できると説明されています。
12. クエリを拡張してリスクのあるレコードを除外し、再実行する。VS Code のネイティブなグラフ可視化で、すべての条件を満たす別のサプライヤーが見つかる。
13. 読み取り負荷が増えたら、共有ストレージ基盤の上でノードを数台追加してスケールアウトできる。グラフやベクトル検索は計算負荷が非常に高い、と説明されています。VS Code にはクラスタートポロジーの可視化もあり、ノードをたどって監視・管理できる。

### 6.3 アプリ開発デモ（Charles 氏と Sachin 氏）

前半は Sachin 氏が GitHub Copilot を使ってアプリを作り、後半は Charles 氏が遅くなった分析クエリを高速化します。

1. GitHub Copilot で Raven プラグインをインストールし、「顧客スコアを見て、クレジットを設定でき、上位 100 顧客を確認して分析クエリを実行できる」アプリの構築を始める。
2. Raven が要件を受け取り、バックエンドをコードとして構成する。完成後、裏側を確認する。
3. データサービスとして Postgres が有効になり、認証も自動で配線されている。バックエンドのデータベースは、Fabric 上の Postgres HorizonDB のテーブルになる。
4. customer エンティティが定義され、認証ポリシーもコードで設定されている。「所有者だけが読み取りと更新ができる」というポリシー。product クラスは、ログインしているユーザーなら誰でも読み取れる。
5. アプリはしばらく稼働し、当初は高速だったが、データが増えて分析クエリが遅くなった。レポートが以前は数秒だったのが、36 秒かかる。
6. Charles 氏がクエリを示す。共通テーブル式（CTE）を含む比較的複雑なクエリで、スキーマ名は **OLTP**（データが物理的に Postgres にあることを表す）。orders テーブルと大きな customers テーブルを結合している。実行は時間の都合で早送りし、Postgres 上のネイティブ実行では約 36 秒かかることを確認する。
7. Fabric に切り替えると、データベースのすべてのテーブルが OneLake に自動でミラーリングされており、行数も確認できる。
8. ミラーされたテーブルを、別のスキーマ **OLAP** として Fabric 側から登録する。
9. 列指向のテーブルに対して count(*) を実行すると、ほぼ即時に終わる。以前は 36 秒のクエリだった。
10. クエリの **OLTP を OLAP に変えるだけ**にする。依然として Postgres のクエリのままで、Fabric のデータウェアハウスのエンドポイント（列指向フォーマット上の分散実行）で動くよう、クエリがトランスパイルされる。実行すると約 3 秒で返る。
11. VS Code で Postgres のクエリプランを表示すると、左下で foreign table scan にプッシュダウンされていることが分かる。これにより OneLake 上のすべてのデータに対する transanalytical（取引系と分析系を兼ねる）アプリを実現する、と説明されています。
12. Sachin 氏が Copilot に、新しいミラーテーブルを参照するよう指示する。Copilot が新しいコードを書き、クエリを再実行すると 3 秒で返る。

### 6.4 database agents のデモ（Priya 氏）

想定は、予約チーム（reservations team）が 2 つのアプリで業務を回しているシナリオです。

**問題の確認**

1. 1 つ目は宿泊者の予約レポート（guest booking report）で、Azure SQL Database 上で動く。更新を実行すると、40 秒、50 秒と時間がかかり、最終的に 78 秒になる。SLA として許容できない。
2. 2 つ目は予約検索アプリで、予約を検索すると約 10 秒かかる。

**Azure SQL Database の調査（Fabric の Database Hub）**

1. Fabric の Database Hub を開く。セキュリティ、性能、最適化をデータベース全体にわたって見渡せる単一のペインであることを示す。構成済みの agents の一覧が見られる。
2. 対象の Azure SQL DB（予約レポートのデータベース）を開くと、エージェントに構成されたポリシー（守るべき性能監視ポリシー）が確認できる。
3. エージェントがこの予約追跡データベースで何を見つけたかを確認すると、長時間実行されているクエリがすでに検出されている。
4. その問題をクリックして詳細を確認し、Copilot を開く。Copilot はクエリレベルまでの完全なコンテキストを持っており、追加情報を渡す必要がない。アプリケーション開発者が書いた問題のクエリが特定される。
5. クエリを分析すると、性能のベストプラクティスに沿って書き換えたクエリが提示される。Priya 氏は、約 1 分で原因を突き止められたこと、query store や DMV などのテレメトリを自分で触らなかったことを強調している。

**PostgreSQL のアプリの調査（VS Code）**

1. VS Code の新しいダッシュボードを見ると、CPU が過去 6 時間スパイクしていることが分かる。
2. database agent が問題をすでに指摘している。頻繁なデータの参照が原因で、インデックスで改善できる。ロールバック方法も示される。
3. 自分でアクションを実行することもできるが、今回は 2 つの問題とも、通常の開発・テスト・デプロイの手順（SDLC）に沿って本番に反映してもらうため、アプリケーション開発者に差し戻す。

**結果の確認**

1. 開発者が変更を適用したという想定で、レポートを更新する。以前 78 秒だったものが約 1 秒になった。
2. 予約検索も、以前の約 10 秒から約 1 秒になった。

Priya 氏は、通常なら数時間、場合によっては数日かかる作業を、database agent が「相棒（sidekick）」として行ってくれた、とまとめています。

## 7. 注意点・発表者の気付き

* **音声認識の誤りが多い**: Raven と Rayfin、Microsoft Embedding One、Vidora 3、Habitat などは、表記が確定できていません。数値の一部（HorizonDB のレプリカ数や HA の値、ベンチマークの途中経過）も同様です。
* **HorizonDB の 8 倍の比較条件**: 発表では、セルフホストの PostgreSQL と同じ構成・同じデータで比較した結果として示されました（95,000 ウェアハウス、9.1 TB）。ほかの条件での数値には触れられていません。
* **データベース資産はパッチと一貫性が課題**: パッチが当たっていないデータベースが 1 台あるだけで大きな問題になりうる、と話しています。
* **database agents の使い方**: Priya 氏のデモでは、エージェントが見つけた改善策は DBA が本番に直接反映するのではなく、アプリ開発者に差し戻し、通常の SDLC（開発・テスト・デプロイ）に沿って反映していました。発表では「信頼できる自動化と、明示的な制御」の両立が強調されています。
* **AI を本番に広げるときのコスト**: Claire 氏は、POC で動かすのと、企業全体で自由に動かすのは大きく違うと注意しています。モデルの適切さ、推論とコンテキスト、コストの 3 点を問うことを勧めています。
* **Fabric 上の HorizonDB や Raven の細かい制約**（対応リージョン、料金、GA の範囲など）は、発表では触れられていません。

## 9. まとめ

このセッションは、エージェントを新しい利用者として迎えるためのデータ基盤を、3 つの章で紹介しました。

1. **クラウドネイティブ**: Azure HorizonDB が GA になり、Fabric 上でも使えるようになりました。Fabric 上では 1 つの PostgreSQL 接続で運用と分析を扱えます。SQL Hyperscale、Cosmos DB、Azure Managed Redis も、エージェント時代に向けた機能が追加されています。
2. **モダナイゼーション**: Azure Catalyst（パブリックプレビュー）で、アプリ、データ、インフラを 1 つの計画で移行できます。LSEG の事例は、Cosmos DB を軸にした長期の取り組みです。
3. **エージェントによる運用**: Database Hub（GA）と database agents が、データベース群の健全性を継続的に見て診断し、推奨を出します。デモでは、遅いクエリが約 1 分で特定され、レポートの表示時間が 78 秒から約 1 秒に縮まりました。

ロードマップサイト（パブリックプレビュー）と、SQL、Cosmos DB 向けの新しい認定資格も案内されています。
