# BRK360 The semantic layer for the AI era with Power BI and Microsoft Fabric

## 1. はじめに

このセッションは、AI エージェントが組織のデータから正しい答えを返すために、なぜ「セマンティックレイヤー」が必要なのかを、Microsoft Fabric と Power BI の立場から説明するものです。前半では、OneLake に統合したデータの上にセマンティックモデルを作り、それを GitHub Copilot app や Microsoft 365 Copilot から使うところまでをデモで見せています。後半では、Fabric に **semantic views の public preview** が発表され、Apache Aussie（旧 OSI）への対応が紹介されました。

先に結論を書くと、発表の主張は「人間が操作しても、エージェントが答えても、同じ指標なら同じ数字が返る状態をつくる。そのために、ビジネス上の意味（セマンティクス）を一度定義して、あらゆる場所で再利用する」というものです。

## 4. 発表者が伝えたいメッセージ

前半の登壇者（Christian 氏）は、「組織の AI は、与えたデータの質で決まる」と話を始めています。Web 上の ChatGPT のような AI とは違い、組織向けの AI は自社のデータ次第だという考えです。ところが組織のデータは断片化し、サイロ化し、ポイントツーポイントの連携だらけです。人間でも AI エージェントでも、これでは意味を読み取れません。

そこで、まず OneLake でデータを統合し、その上にセマンティックなコンテキストを載せます。ビジネスユーザーが昔から持っていた「上位 10 社の前年比成長率は？」といった質問は、AI の時代になっても変わりません。変わったのは、レポートを自分で作る代わりにエージェントに聞くという聞き方だけです。中央で管理された再利用可能なセマンティクスと、専用の BI エンジンによる高速なクエリは、今も必要だと説明しています。

後半の登壇者は、セマンティクスの実体はメタデータであり、メタデータは利用者のものだという立場から、ベンダーをまたいで一度だけ定義して共有する方向を示しています。最も強調されているのは、**人が聞いても、エージェントが聞いても、同じ数字が返る一貫性**です。

## 5. 発表内容の詳細

### 5.1 データの断片化と OneLake

Christian 氏は、Fabric は約 3 年前に、データを統合して「データ統合の税」を取り除くために作ったと説明しています。OneLake は、断片化したデータソースの上の仮想化レイヤーとして使います。

| 状況 | 発表で説明された方法 |
| --- | --- |
| データソースが Delta Lake や Apache Iceberg などのオープン標準に対応している | コピーなしの純粋な仮想参照で、OneLake のファーストクラスのテーブルとして取り込む |
| 対応していない | mirroring を使う。レプリケーションのコンピュートは Microsoft が負担し、change data capture のフィードも Microsoft が動かす |

mirroring のコストを Microsoft が負担するのは、戦略的な判断だったと述べています。組織の重要なエンティティが OneLake に集まると、ガバナンスとセキュリティを一か所で管理できるためです。セキュリティは OneLake security と Microsoft Information Protection ラベルなどで定義し、Fabric の各ワークロードはデータをコピーせずに、そのルールに従います。

> 補足：Gartner の評価について、"relevant" な Magic Quadrant でリーダーに位置付けられていること、特に Analytics and Business Intelligence Platforms では 18 年連続のリーダーであることが語られています。Forrester の Wave でも高く評価されているとのことです。

### 5.2 なぜセマンティックモデルなのか

データを統合して保護しても、それだけではビジネス価値は取り出せないと Christian 氏は言います。人間にも AI エージェントにも、意味づけ（セマンティックなコンテキスト）が必要だからです。Fabric IQ では、その主な手段が **セマンティックモデル** です。

裏付けとして、次の数字が挙げられています。

- 月間アクティブユーザーは 3,500 万人を大きく超える（"well over 35 million"）
- 市場浸透率は約 90%
- セマンティックモデリングには約 25 年の蓄積がある

競合各社も今は同じようにセマンティックレイヤーに投資しており、成熟度と機能の面で Microsoft は大きく先行している、というのが発表者の見方です。また、すでに顧客組織には多数のエンタープライズセマンティックモデルがあり、AI の利用を加速する下地になっているとも説明しています。

### 5.3 AI にセマンティックモデルを作らせる

デモは GitHub Copilot app で行われました。VS Code や M365 code でもほぼ同じ体験になるとのことです。仕組みは plugin モデルです。Fabric Skills は aka.ms/fabricskills から入手でき、デモでは Fabric Skills と Power BI authoring の plugin をインストール済みです。plugin は、AI の skills と MCP サーバーを標準的な形でまとめ、組織全体に配布するものと説明されています。

Christian 氏はここで、架空の組織 Coldova の開発者を演じます。話している要点は次の 3 つです。

**ビジネス要件だけを書けばよい。** 双方向リレーションシップや、メジャーの増殖を抑える calculation group といった技術的な話は不要です。時間インテリジェンス（前年比、前期間）や、在庫の集計ルールのようなビジネス要件を書きます。在庫の例では、リージョン内の倉庫は合算するが、月別の在庫は日を合算せず月の最終日を取る、という要件が挙げられました。エージェントによる作成の時代には、ビジネス要件のドキュメントがむしろ重要になるという考えです。

**AI は指示に従うことが得意。** AI は非決定的ではあるものの、大きな組織に展開するときには、人間よりも指示に忠実だという主張です。アーキテクチャガイドを配っても無視する開発者がいる、という例えが使われました。ベストプラクティスの標準化と、総所有コストの低減に役立つと述べています。ビジネスアナリストにとって、技術を気にせず要件に集中できるのは「解放感がある」こと、コンサルタントとしてセマンティックモデルを作ってきた BI の専門家にとっても、発表者自身は、AI のほうが自分よりベストプラクティスに忠実に従えるだろうと話しています。

**中央 IT の独自ルールも plugin で配る。** 中央 IT が Coldova 固有のベストプラクティスを持つ場面として、通貨換算を挙げています。財務部門がすでに財務セマンティックモデルを持っているので、通貨換算の定義・計算・テーブルはそこから流用し、作り直さないというルールです。命名規則や、社内用語を使った明確なビジネス定義も、同じ plugin で配布できます。すべてのメジャー、テーブル、列にビジネス定義を持たせれば、ビジネスユーザーが社内の言葉で質問しても正しいメジャーに行き着く、という説明です。

### 5.4 実装計画の確認と、Web モデリング UI

Copilot は、レビュー用の実装計画（implementation plan）を作ります。そこには技術仕様が書かれています。Christian 氏は、エージェントは高速で動くのでブラックボックスにしてはならず、透明性と検証が必要だと強調しています。実装計画はそのための仕組みです。

承認後の作成には、実際には 5〜10 分かかったとのことで、デモでは早送りしています。スキルのコンテキストがない場合より大幅に速く、使うトークンも少ないと述べています。コンテキストなしで Claude のようなものをつなぐと、大量のトークンを消費するという説明です。

完成したモデルについて、画面を見ながら次の点が語られています。

- 財務セマンティックモデルの通貨換算の定義を再利用している
- ユーザーに見えるすべてのオブジェクトの description にビジネス定義が入っている
- 外部キーなど技術的な列は非表示にしてある
- テーブル名にはスペースを使い、ビジネス寄りの名前になっている
- ビジネス要件に基づく高度な計算を DAX で書いている

その後、Web モデリングビューの TMDL ビュー（Tabular Model Definition Language）に移ります。これはプロ開発者向けの画面で、VS Code から持ってきたのと同じ IDE だという説明があり（トランスクリプトでは "ID" と聞こえます）、CI/CD の統合もネイティブでスクリプトにも強いとのことです。AI が作れるのになぜ UI が必要なのかという点には、「AI が何をしたかを検証するために必要。3 日後に確認したくなったときにも UI が使える」と答えています。

### 5.5 レポートをエージェントで作る：Power BI レポートと Fabric Data App

モデルは Direct Lake セマンティックモデルとして作られ、データをレイクから直接、高速に読めます。更新の操作もなしでレポートを作れます。Christian 氏は UI から作ることもできるとしたうえで、ここでもエージェントにレポートを頼みます。

プロンプトの内容として語られたのは、次のとおりです。

- 見た目は、提示したスクリーンショットの Coldova 標準に合わせる（デモ用の指定。本来は Coldova のベストプラクティスの plugin に、フォント、ロゴ、配色を入れて配る）
- 上部に KPI カードを置く
- 中心のビジネス要件は、先ほど作ったモデルに対する通貨換算
- **「おまけに」2 種類のレポートを作る**。Power BI レポートと、Fabric Data App（音声認識では "Rafin App" と聞こえる）

Fabric Data App は、Power BI レポートを作る「新しい、エージェントネイティブな方法」だと位置付けられています。実装計画を作成してから進む流れは同じで、コンテキストなしだと 1 時間以上かかるところ、5〜10 分で済んだとのことです。Fabric IQ のコンテキストが、Copilot の足場を固めるのに必要だと述べています。

出来上がった 2 つを順に確認し、どちらも依頼したルック・アンド・フィールで、クロスフィルタリングなどのインタラクティブな機能も同じだと説明しました。Fabric Data App を使う理由は 2 つ挙げられています。1 つはエージェントネイティブであること。もう 1 つは、想像力以外に制限がないことです。例えば、ドリルインして閾値に達したらボタンを有効にし、Fabric SQL database などのストアドプロシージャを呼ぶといった、「洞察からアクション」までをアプリ内で閉じることができます。

### 5.6 Ontology：ビジネスインテリジェンスから業務インテリジェンスへ

Fabric IQ の「ロシア人形のような」構造の最後の層が ontology です。これを使うと BI から operational intelligence（業務インテリジェンス）へ進めます。アプリではなくエージェントに質問し、データが返ってきたら、そのままアクションまで取れる、という考え方です。ontology は、ビジネスルールを内蔵した、複雑な関係を持つエンティティです。

例えば「パイロットを飛行機に割り当てる」アクションなら、その機体に対する資格があるか、前回のフライトから十分に眠っているか、といったルールを検証できます。詳しくは、木曜日の別の Fabric IQ セッション（登壇者として "Bogdan" と "Shafia" と聞こえる。音声認識の都合で表記は確定できません）で扱うと案内しています。

### 5.7 ビジネスユーザーの体験：Microsoft 365 Copilot と Work IQ

ここまでで、OneLake の統合データ、一元的なセキュリティ、セマンティックモデル、ontology がそろいました。次は、ビジネスユーザーの視点でセマンティックモデルを使う場面です。plugin モデルなので、Microsoft の Copilot にも Microsoft 以外の Copilot にも使えると Christian 氏は話し、明日の conversational analytics のセッションでは ChatGPT や Claude との統合も発表される、と案内しています。

デモでは、Microsoft 365 Copilot にビジネスの質問を投げます。質問文は読み上げられていませんが、"releasable inventory"、在庫の制約、運賃などのデータが必要な質問だと説明されています（"releasable inventory" は発話のままの表記です）。質問にセマンティックモデルという言葉は出てきません。ビジネスユーザーはセマンティックモデルを知らないことが多い、という前提です。

裏で起きていることは、次のように説明されています。

1. Copilot が、質問にデータが必要だと判断し、Fabric IQ を呼ぶ
2. Fabric IQ が、質問に合う正しいセマンティックモデルを選ぶ。これは重要なステップで、洗練されたアルゴリズムがユーザーに合うモデルとの照合を行う
3. 選定では、認定（certification）の状態や、利用量の多さを使う。経営陣のダッシュボードを支えているモデルを優先し、半年誰も使っていないモデルは避ける
4. Microsoft Graph と社内ディレクトリに基づく組織上の近さも考慮する。Fabric グループのユーザーに、Xbox グループのモデルを当てることはしない

正しいモデルに到達すると、詳細な分析、関連する Power BI レポートの引用、Power BI の資産を生かしたビジュアルが返ってきました。どのレポートも同じ権威あるセマンティックモデルから来るので、同じデータになります。

続いて、「この承認オーダーを修正したい。何をすればよいか」という趣旨のフォローアップを入力します。すると Fabric IQ から Work IQ にシームレスに切り替わり、まだ読んでいないメールの情報が使われました。参照範囲は自分の受信トレイのみです。Work IQ のデータとして、メール、Teams メッセージ、Teams の会議録画、Office ドキュメントが挙げられています。

最後に、オーダーの承認を進めるため、会議と PowerPoint 資料を作る場面です。Cowork に切り替えると、コンテキストが引き継がれます。

- 会議の参加者（ステークホルダー）は、指定しなくてもメールから補われる
- 招待状に Fabric IQ のデータが入る
- 会議で提示する PowerPoint 資料が作られ、セマンティックモデルが引用される。Power BI と数字が一致する
- PowerPoint のデータは実行時に取得される。1 週間後に開けば、その時点の最新データになる。データを資料にコピーしているわけではない

データは OneLake から来ます。ショートカットやミラーで別のシステムにつながっているなら、資料を開いたときに元のシステムから直接取得されます。スタック全体でゼロコピーだと説明しています。

Christian 氏はここで、混沌としたデータから、OneLake での統合、一元的なセキュリティとガバナンス、ビジネスユーザー向けのセマンティックモデル、業務インテリジェンス向けの ontology まで、全体の流れを振り返ってバトンを渡しています。

### 5.8 Apache Aussie と、semantics の相互運用

ここからは後半の登壇者です。AI とエージェントの時代には、チームの役割やワークフロー、組織の知識、ビジネスの状態とアクションといったセマンティックレイヤーが、ユーザーだけでなくすべてのエージェントにとって重要になる、という前置きがあります。M365 の conversational analytics、composable apps、autonomous actions なども、セマンティクスに依存すると述べています。Power BI では、セマンティックレイヤーがセマンティックモデルとして具体化され、約 10 年間改善してきた、という説明です。

業界の動きとして紹介されたのが **Apache Aussie**（旧称 OSI）です。トランスクリプトでは Aussie、Ozzy、Oz など複数の綴りで聞こえるため、音声認識の都合で表記が確定できません。コミュニティの目標は、セマンティックコンテキストを一度定義して、ベンダーやエージェントの体験をまたいで使うことです。セマンティクスはメタデータであり、メタデータは利用者のものだという立場から、Microsoft はこのコミュニティの Apache incubating の取り組みにコミットしており、Snowflake とは特別な協業もあると述べています。

動画を再生する予定でしたが、音声が出なかったため省略されました（Carl という人物が話す内容だと触れられています）。代わりに、次のような説明がありました。

- ベースラインの Aussie ドキュメントがあり、相互に変換できる
- 例えば Snowflake のウェアハウスで定義した semantic view を Aussie ドキュメントに変換し、さらに Power BI セマンティックモデルに変換して、Power BI と Fabric でネイティブに使える
- **コンバーターが Apache Aussie の GitHub リポジトリで利用できるようになった**（ここで発表）
- **DAX が公式の Aussie dialect として登録された**
- 他ベンダーのコンバーターも同じリポジトリに掲載されている（スライドの QR コードからリポジトリに行ける）

### 5.9 Semantic views in Fabric（public preview）

次に、役割の境界があいまいになっているという背景が語られました。これまでセマンティックモデルを使ってきたビジネスアナリストは、同じ成果物の上で開発を続けられます。一方で、データエンジニアや IT 管理者にも、ビジネスロジックやセマンティクスの定義への関与が求められるようになっています。そこで、セマンティックモデリングの知識を、Fabric の他の部分にも持ち込むことにしました。

**Semantic views in Fabric の public preview** が発表されました。後半の登壇者によると、1〜2 か月前のヨーロッパの Fabric カンファレンスでは "coming soon" としか言えなかったものを、ホリデーシーズンの前に public preview として出せたとのことです。ポイントは次のとおりです。

- Aussie で定義した軽量なセマンティクスを、データのある OneLake に直接定義できる
- コンテキスト（AI コンテキスト）も、データのそばに置ける
- OneLake の **ショートカット** を使い、ガバナンスの効いた形でメトリックを共有できる（「一度定義して、どこでも使う」を実現する）
- オープン標準に基づくので、ベンダーに依存せず、クロスプラットフォームで使える
- メトリックは DAX で定義できるため、時間インテリジェンスやコンテキストフィルタといった DAX の機能は失われない
- Lakehouse に新しい入口があり、ファイルをドラッグ＆ドロップして始めることもできる

発表では、これらのデモと機能が「本日リリースされるもの」だと言っています。オンラインのドキュメントも公開済みで、以前のスライドの QR コードからたどれます。

| Fabric IQ との連携 | ビジネスユーザーが Fabric IQ で質問したときにも、メトリックが直接使われるようにする |

## 6. デモ・手順

このセッションには画面を使ったデモが 5 つあります（最後の 1 つは、今後の方向を示すスニークピークです）。画面の細部は音声からは確認できないため、ナレーションで語られた範囲だけを順番に書きます。

### 6.1 デモ 1：AI でセマンティックモデルとレポートを作る（Christian 氏）

1. GitHub Copilot app を開く。Fabric Skills と Power BI authoring の plugin はインストール済み
2. Coldova の開発者としてビジネス要件を指定する（時間インテリジェンス、在庫の集計ルールなど）
3. 中央 IT のベストプラクティス（財務セマンティックモデルの通貨換算の再利用、命名規則、社内用語）を plugin 経由で適用する、という説明をする
4. Copilot が作成した実装計画を確認し、承認する（実際は 5〜10 分かかるため、早送りしている）
5. 完成したセマンティックモデルを確認する（description、非表示の技術列、DAX の計算など）。Web モデリングビューの TMDL ビューを開く
6. 同じ GitHub Copilot app で、別のプロンプトを送る。見た目（スクリーンショットで指定）、KPI カード、通貨換算の要件、そして Power BI レポートと Fabric Data App の 2 種類を依頼する
7. 実装計画が作られ、2 つのレポートが生成される。ワークスペースで両方を開き、機能が同じであることを説明する

### 6.2 デモ 2：Microsoft 365 Copilot から会議と資料まで（Christian 氏）

1. Microsoft 365 Copilot でビジネスの質問をする（セマンティックモデルには触れない）
2. Fabric IQ が正しいセマンティックモデルを選び、分析と Power BI レポートの引用を返す
3. 「承認オーダーを修正するには」という趣旨のフォローアップで、Work IQ のメール情報に切り替わる
4. Cowork に切り替え、会議と PowerPoint 資料の作成を依頼する。出席者はメールから補われ、資料のデータは実行時に取得される

### 6.3 デモ 3：semantic view の作成とメトリックの一貫性（後半の登壇者）

1. Lakehouse に、context ファイルと system context ファイルが並んでいる（"context and system context files" と聞こえる）
2. 「create a new semantic view」を実行すると、スキーマとメトリック用のプレースホルダーファイルが作られる
3. スキーマとメトリックを（DAX で）書く
4. 財務チームが定義したメトリックへのショートカットを作ると、その定義を継承する。財務側が更新すると、自動的に反映される
5. 裏でセマンティックモデルが作られる。DAX クエリビューで、コンピュータが **48.6 million**、前年比 **81%** と確認する
6. Power BI レポートでフィルタしても同じ数字になる
7. sales agent に「Wide World Importers で、年間売上が最も高い商品カテゴリと前年比成長率は？」と尋ねると、同じ 48.6 million と 81% が返る

### 6.4 デモ 4：エージェントによる作成（後半の登壇者）

1. GitHub Copilot で「リージョナル営業チームが使える OneLake 上のビジネスメトリックは何か」と尋ねる
2. DAX で定義された既存のメトリックファイルが示され、財務チームに gross revenue、net revenue、いくつかの YoY 計算があることが返る
3. 財務のメトリックを、リージョナル営業の Lakehouse で再利用するよう依頼する
4. 財務にない分の semantic view を作り、セマンティックモデルを作成する
5. semantic view が公開され、Power BI レポートでも同じメトリックを確認する
6. Microsoft 365 Copilot の sales agent に「Pacific Northwest の net revenue はどう変化したか」と尋ねる。Power BI と同じ答えが返る

### 6.5 スニークピーク：今後の semantic view（後半の登壇者）

これは、今後実現したい方向を示すデモです。

1. OneLake catalog で、sales performance の semantic view を開く。データの出どころだけでなく、誰が使っているかというリネージも見える
2. Lakehouse 側で、Aussie ファイルの SQL と DAX のメトリック、AI コンテキスト（instructions、descriptions など）を確認する
3. 使われているセマンティックモデルを確認する
4. データエージェントを作り、semantic view を選ぶと、エージェントがそのメトリックと AI コンテキストを使う
5. Power BI レポートでも、同じメトリックになることを示す

## 7. 注意点・発表者の気付き

- 実装計画の確認と UI での検証は、エージェント作成の時代でも必要だと繰り返されています。AI は高速で動くので、ブラックボックスにせず、透明性と検証を持たせるという考えです
- セマンティックモデルを選ぶ段階は「重要なステップ」と呼ばれています。ユーザーを正しいモデルと正しい指標に導けないと、組織内で一貫して正しい答えが出せないためです
- デモは時間の都合で早送りされています（モデル作成は実際には 5〜10 分）
- 後半のデモのうち、TMDL、SQL メトリック、インポート／エクスポートなどは「次の予定」であり、現時点で使えるものではありません。「本日リリースされるもの」と明言されているのは、後半の 2 つのデモ（semantic view の作成と、エージェントによる作成）の内容です
- 後半の動画は音声が出ず、再生されていません

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

- **ビジネスアナリストにとって**：技術的な知識（双方向リレーションシップ、calculation group など）がなくても、ビジネス要件を書くことでモデルを作れる
- **中央 IT にとって**：plugin の仕組みで、独自のベストプラクティスや社内用語、レポートの見た目を、組織全体に自動で配布できる。人間より指示に従う AI で標準化と総所有コストの低減ができる
- **ビジネスユーザーにとって**：セマンティックモデルを意識せず、普段の仕事の流れの中で質問し、そのままアクションまで進める。資料のデータは常に最新で、コピーされない
- **データエンジニアにとって**：セマンティックモデリングの経験が浅くても、データのある Lakehouse 上でメトリックを定義できる。ショートカットで、財務のような中央のメトリック定義を継承し、更新も自動で反映される
- **組織全体にとって**：人間が操作しても、エージェントが答えても、同じ数字が返る一貫性。オープン標準によって、ベンダーに縛られない相互運用

事例の数値は、デモ上の 48.6 million（コンピュータ）と前年比 81% のみで、顧客名を挙げた導入事例は、このセッションでは語られていません。

## 9. まとめ

- 組織の AI は、組織のデータで決まります。まず OneLake でデータを統合し、一か所でセキュリティとガバナンスを管理します
- その上のセマンティックモデルが、人間にも AI エージェントにも必要なビジネスの意味を与えます。Fabric Skills の plugin を使えば、ビジネス要件を書くだけで、モデルとレポート（Power BI レポートと Fabric Data App）を AI に作らせられます
- ビジネスユーザーは Microsoft 365 Copilot から質問し、Fabric IQ と Work IQ を経由して、会議や資料の作成まで進められます。Fabric IQ は、認定状況、利用状況、組織上の近さから、正しいセマンティックモデルを選びます
- Apache Aussie のコンバーターが公開され、DAX が公式 dialect になりました。semantic views in Fabric の public preview により、OneLake 上でメトリックを一度定義し、ショートカットで共有し、人もエージェントも同じ数字を得られます
- 今後は、TMDL、SQL メトリック、インポート／エクスポート、agentic skills、Databricks や Snowflake との相互運用などが予定されています
