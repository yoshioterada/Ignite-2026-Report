# BRK363 Less hunting, more building: Database agents in a unified estate

## 1. はじめに

このセッションは、SQL Server チームのプロダクトマネージャー 2 名が、複数のデータベースを抱える管理者・開発者に向けて **Database Hub（Fabric 内のデータベース管理画面）** と **Database Agent** を紹介する発表です。Database Hub は、Azure SQL や PostgreSQL、Cosmos DB など散らばったデータベースの状態を 1 か所で見られる仕組みです。Database Agent は、その上で問題を検出し、原因の説明や修正案の提示まで行うエージェントです。

発表の大半はライブデモで、ハブの有効化から、Estate view、エージェントによる検出、Copilot による原因説明、VS Code と SSMS への展開までを順に見せています。結論として、Database Hub は無料で使え、エージェントは現時点では「検出と提案」までで、最終的な判断と実行は人が行う設計だと説明されています。後半では GA 時期などのロードマップも語られています。

## 5. 発表内容の詳細

### 5.1 Database Hub の概要と有効化

Database Hub は無料で、期限もありません（「いつまで無料か」と問われて「永久に」と答えています）。Fabric が必要ですが、Fabric を使ったことがなくても、fabric.microsoft.com にアクセスしてサインインすれば無料版の Fabric が使えます。Power BI の無料ライセンスでも利用できます。

登壇者が自分の本番テナントで試したところ、存在を知らなかったデータベースや、気づいていなかったセキュリティ上の問題が表示されたそうです。ほぼ容量上限に達しているデータベースも見つかりました。設定作業はしていません。

有効化の手順は、次のように説明されています（デモは 5.2 参照）。

1. Fabric の設定から管理者ポータルを開き、「database hub」で検索して有効にする。
2. 公開範囲は組織全体でも構いませんが、DBA などのセキュリティグループを作って追加し、小さな範囲で試してから広げることを勧めている。
3. 省略記号（…）から「Databases」を選んで Hub を開き、左のレールにピン留めする。

Azure のリソースも Hub から見られると、もう 1 人の登壇者（Charles 氏）が補足しています。Power BI の画面からも使えます。Power BI と Hub に直接の関係はなく、ペルソナ切り替えのどちらからでも同じ URL で使えるという説明です。Power BI でデータベースを分析用に使う開発者にも、セキュリティやパフォーマンスの改善点を見せたかったことが、Hub を Power BI 側にも置いた理由とされています。

### 5.2 Database Hub のデモ：データベース一覧と Estate view

対応するデータベースは Azure SQL、Microsoft SQL、PostgreSQL、Cosmos DB です。Fabric SQL は、テレメトリを取得している段階で、まだ対応していません。

**オンプレミス・他クラウドの扱い。** オンプレミスやハイブリッド、他社クラウド上の SQL Server は、Azure Arc を有効にすれば同じ体験が得られます。会場から「全データベースで Arc が必要か」と聞かれ、オンプレミス、ハイブリッド、マルチクラウドの場合は必要だと答えています。Arc の有効化自体は別セッションの内容だとして、触れていません。

**データの置き場所。** 有効にすると、テレメトリは Kusto データベース（登壇者は「ADX proxy」とも呼んでいます）に集められます。保持期間は 28 日分です（当初「14 日か 28 日」と言い直して 28 日に確定）。利用者はここに自分でクエリを書けます。デモでは KQL で書いたクエリを見せましたが、SQL でも書けるとされています。登壇者は KQL を勉強中なので KQL にしたそうです。クエリは後で公開すると話しています。また、この KQL を書くよりもさらに良いエージェントの使い方を、翌日（11 時ごろ）のシアターセッションで見せると予告していました。28 日より長く保持したい場合は、データを取り出して自分のリポジトリに保存する処理を作ればよいと説明しています。

**Estate view でビューを保存する。** 最初は見えるリソースが多すぎて圧倒されたそうです。そこで次の手順を見せています。

1. Estate view で、タグによって環境を絞り込む。
2. ビューを保存する（名前は「production critical」）。
3. 適用して Overview に戻ると、その環境のサーバーだけに絞られている。

SQL Server だけを見ているとダッシュボードも SQL 向けに変わります。PostgreSQL の DBA であれば PostgreSQL に絞れます。さらに、ビューのリンクをコピーして共有できます。例として、休暇中に同僚へ自分のデータベースの監視を任せるため、リンクを渡す場面が挙げられました。その場合、同僚にはサーバー上で最小限の権限を与える必要があると説明されています。

**権限。** 特別な仕組みは無く、Azure の RBAC をそのまま使います。アクセス権のあるデータベースだけが表示され、Azure で何の権限も無い人には何も表示されません。これは Azure Resource Graph のクエリと同じ要領で、利用者の権限でデータを取りに行くという説明です。セキュリティに関する質問への回答として、データは保存せず、Azure 上の現在の状態をライブで照会すると説明されています。なお、テレメトリを集約する Kusto データベースとの関係は、発表では詳しく語られていません。ドキュメントはこの日に公開されたとのことです。

**Security と Performance。** Security で絞り込むと、セキュリティ上の問題が表示されます。登壇者の環境では、パブリックインターネットに公開されているデータベースが多数あり、VNet やプライベートネットワークの設定を勧められました。ネットワーク範囲に全インターネットを許す設定をしていたことも明かしています（数値は音声が不明瞭です）。Performance では、ストレージや compute に関する最適化の余地が表示されました。

Performance ダッシュボードでは、過去のデータとリアルタイムのデータを見られます。リアルタイムダッシュボードを自分で作ることもできます。PostgreSQL や Cosmos DB の情報も同様に表示されます。時間範囲は変更でき、デモでは直近 24 時間でした（別の登壇者が「直近 24 時間と最新のホットデータ」だと補足しています）。

### 5.3 アラートと、diagnostic query から SSMS を開く操作

画面にはアラートの追加ボタンがあります。これは Fabric の **Activator** を使っており、利用者が自分でしきい値やアラートを設定できます。別の登壇者によると、ここには 2 つの部分があります。1 つはアラートとカスタムワークフローの設定、もう 1 つは Estate view に出る提案や問題です。後者は実行可能な内容で、セキュリティ、パフォーマンス、コストやリソースの最適化のための変更をその場で設定できるとされています。アラートについては、登壇者が「もっと良いものがある。お楽しみに」とも話しています（内容は発表では示されていません）。

issue をクリックすると Estate view に移り、問題をさらに診断するための diagnostic query が表示されます。その横の「アクションボタン」を押すと、次の流れになります（デモで操作）。

1. SSMS が起動する。対象のサーバーとデータベースのコンテキストが設定された状態で開く。
2. 認証を求められる（登壇者は何度も認証が出ると冗談を言っています）。
3. diagnostic query がクエリウィンドウに持ち込まれ、すぐに実行できる。

サーバー名、データベース名、クエリの 3 つをコピーする手間が省けます。登壇者はこれを「クリックの税金（click tax）を省く」と表現しており、Charles 氏の発案だと紹介しています。

### 5.4 Database Agent の設定とデモ

ここから話題は、観測から「エージェント」へ移ります。まず、Microsoft が検証した「デフォルトのスキル」から始めると説明されています。数を絞る理由は、ノイズを出したくないからです。Microsoft には多くの知見があり、数百個出すこともできますが、実際に問題を示す信号だけを出すために検証済みのものに限っています。

設定の手順は次のとおりです（デモで操作）。

1. 管理者ポータルで「database agent」を検索し、有効にする。現在はプレビューで、テナント設定になっている。
2. 有効にすると、環境に「Agent」タブが表示される。
3. Performance monitoring を有効にする。フィルタをかけて一括で、または個別に選べる。
4. 画面右上の「manage database agents」から、エージェントを動かす対象のデータベースを選ぶ。フィルタで絞り込める。
5. 検出するシナリオを選ぶ。

Performance monitoring を有効にすると、データベースにはエクステンデッドプロパティ（登壇者は `sp_add_extended_property` のようなものと説明、正確な名前は発話では確定していません）が追加されるだけです。テーブルは作られず、侵入的なことはしません。これはテレメトリの収集を許可する印だと説明されています。設定後、データベースが表示されるまで数分かかります。

シナリオ（スキルと同義）は現在約 8 種類とされ、発話で挙がった 7 項目は次のとおりです（8 つ目は聞き取れていません）。

| シナリオ | 内容 |
| ---- | ---- |
| blocking | ブロッキング |
| long-running queries | 長時間実行クエリ |
| plan regression | プランの劣化 |
| missing indexes | インデックス不足 |
| high CPU / high memory / high IO | リソース使用率の高騰 |

これらを検出すると、エージェントは自動で issue を作成します。今後さらに増やす予定です。

issue の詳細画面では、エージェントが実行したクエリ（緑色で表示）、diagnostic query、ブロッキングの詳細、発生時刻（夜間に起きた場合も確認可能）が見られます。クエリを kill できるようにしたかったものの、セキュリティ側から止められて、現在は実装されていません。issue log には調査の内容、つまりエージェントが裏で行ったことが表示されます。登壇者はこれを「デジタルな作業員が行った作業の記録」と表現し、観察できることが重要だと述べています。

**質疑から分かる現状の制約。**

- 現時点のエージェントが対応するのは **Azure SQL と Hyperscale のみ**です。VM 上の SQL Server（IaaS）を含め、Database Hub が対応する全データベースに拡大する計画だと答えています。
- ITSM との連携（Azure DevOps、Jira、ServiceNow など）は、取り組み中と答えています。人間の作業者がチケットを拾うのと同じように、エージェントがチケットを起票し、既存のワークフローにつなぐ構想です。

### 5.5 Ignite での新機能：issue への Copilot

Ignite で初公開として紹介されたのが、issue に Copilot の文脈を付ける機能です。issue の画面に Copilot の吹き出しが並び、次のような質問をボタンで投げられます（スライドとデモで説明）。

- 根本原因を理解する手助けをして
- 何が引き金になったか
- この推奨事項を説明して

デモでは、Copilot が「query 559 がこの問題を起こしており、booking date に関するフィルタ条件の不一致が原因」と説明しました（音声認識の都合で、不一致の中身の表記が確定できません）。続いて、問題のクエリ（query 560、561 なども挙げられた）の推奨事項を説明し、書き換え案のクエリも出しました。

ここで登壇者は、**この書き換えをそのまま適用しない**と強調しています。理由は次のとおりです。

- 速くなっても、意味が同じであることを人が確認する必要がある。
- 元のクエリと同じ行数が返るか、検証が必要である。
- そのため、書き換え案はデータベース開発者など、クエリの作者に渡して確認させる。

この機能は自動化されておらず、人の関与が前提です。これは決定論的なスキルやシナリオの上に、推論（登壇者は compound intelligence と表現）を足したものだと説明されています。

### 5.6 DBA は不要になるのか

会場から「エージェントが DBA を置き換える」という意見が出ました。登壇者は否定し、Copilot は問題を教えてくれても、変更の実装と検証には専門家が必要だと答えています。例として、世界のトップ 500 に入る小売企業のブラックフライデーに、検証せずエージェントに任せるかと問いかけ、「おそらくそうしない」としています。DBA が 1,000 人必要でなくなる可能性はあっても、検証する DBA は必要だという立場です。責任ある AI が鍵だとも述べています。

### 5.7 クエリ書き換えの正しさに関する研究

登壇者は Microsoft Research の取り組みにも触れています。書き換え後のクエリが、(1) 意味的に同じ結果を返し、(2) 速い、ことを保証するための研究です。内容として語られたのは次のとおりです。

- 社内に知的財産（IP）があり、これを統合して、顧客からは「クエリが信頼でき、裏で何度も実行して最良のものを選んでいる」と見える体験にしたい。
- 背景には数学と統計がある。例えば left join から right join、full outer から inner への変更は結果を大きく変える。
- AI がコードを書くのは得意でも、データベース全体の文脈、例えば小さな例では問題ない表が実際には 100 億行の表であることなどを踏まえる必要がある。

これらは研究・開発中の内容で、提供時期は発表では示されていません。

### 5.8 エージェントの将来像とロードマップ

**メモリと意味理解。** エージェントがデータベースのワークロードやベースラインを意味的に理解し、記憶を持つ構想は、ロードマップ上にあるとされています。デモの時点では実現していません。

**ガードレール。** エージェントがどこまでアクセスできるか（スキーマだけか、データも含むか）という質問には、利用者が決めること、ガードレールを置くこと、人が関与することと答えています。

**知識の帰属。** 学習した内容が自社だけのものか、全体に共有されるかという質問に対しては、ビジネスの文脈と知識は顧客自身の IP であるべきだとして、顧客が制御できる形で提供する方針を述べています。詳細は、ロードマップ上の話として具体化していません。

**履歴からの先読み。** 登壇者は、ADX proxy に対して自分で作ったものを「スニークピーク」として見せると予告しましたが、発話からは実演が行われた形跡がなく、将来像のスライドの説明に進んでいます。ここではシアトルの雨をたとえに、エージェントは嵐が来る前に気づくのだと語っています。履歴を持ち続ければ、データベースを作った時点からエージェントがワークロードを学習し、異常や変化が出た時点で「問題がある、または起きようとしている」と知らせられる、という構想です。例えばデプロイで悪いコードが入ったと分かれば、開発者に連絡し、修正する。エージェントはその対応を覚えているので、同じことが起きたときに活かせます。

**自律性は信頼を得てから。** エージェント設定のスキルの場所には「autonomous」というボックスがあり、今回は無効にさせられたそうです。登壇者は、いつか自律的にできるようにするが、それは信頼を得てからだと述べています。現在は検出までで、解決策は提示しません。何をするにも利用者の制御下に置き、データベースを勝手に削除するような動作はさせない方針です。最初にこの内容を発表したのは FabCon だったそうで、その場には「自分のデータベースでは有効にさせない」と言う参加者もいました。登壇者は「時間をください。そのうち信頼してもらえます」と答えたと話しています。

**ロードマップ（登壇者の説明）。**

| 時期 | 内容 |
| ---- | ---- |
| Ignite（今回） | issue に Copilot の文脈を追加 |
| FabCon US（来年 3 月） | GA を予定。アラート通知（Teams、Slack、ポケベルなど）を導入したい |
| 来年春 | Agent 365 との統合。スキルのカスタマイズも「できるかもしれない」とされた（デッドロックの比率など環境ごとの違いに対応する狙い） |
| 来年秋（ヨーロッパ） | 現状は、issue が開いている間は新しい issue を作りません。これを一歩進め、小さな問題（登壇者の言う「1,000 cuts」）が過去にも起きていたと認識して、同じ情報を繰り返し送らないようにする |

「来年 3 月に GA」は、「Charles はたった今知ったかもしれない」と冗談めかして明かされた内容です。出荷頻度は「できるだけ頻繁に、毎月大きな機能を出す」と説明されています。

### 5.9 VS Code と SSMS への展開

Database Hub の中だけの機能ではなく、「フレームワーク」としてツールの選択肢に合わせて統合していくと説明されています。SSMS の GitHub Copilot にあった「クエリの書き換え」スキルを、issue の Copilot に持ち込みました。どの画面でも同じスキルが使われ、同様の答えが得られるようにする方針です。DBA が調査したいときのために、アクションボタンから SSMS を開く導線を用意しています。

**VS Code（デモ）。** 画面が暗かったと謝りつつ、PostgreSQL データベース（小売の販売データ）を使いました。

1. データベースを右クリックし、「database agent」を選ぶ。
2. 「dashboard」を選ぶと、期間を選んで CPU、メモリなどのチャートとレポートが表示される。SQL Server でも同じ情報が拡張機能に出るようになる（発話は将来形）。
3. Database agent を開くと、CPU スパイクがあり、PostgreSQL にインデックスを追加すべきだという issue が表示される。
4. 「review the action」から、アクションを承認または却下できる。

登壇者は、開発環境やサンドボックスでは実行しても、本番では実行したくない場合があるので、承認するかどうかは利用者が決めると説明しています。必要なのは PostgreSQL 拡張のインストールだけで、Microsoft SQL 拡張でも同様にできます。1 つのサーバーしか管轄しない開発者が、フリート全体を見る Hub ではなく、手元のツールで同じ機能を使える形です。

**SSMS（画面を見せながらの説明）。** SSMS には GitHub Copilot が組み込まれています。登壇者は「先ほど Copilot と会話した」として、その内容を見せています。Copilot へ「データベースの調子は」と聞くと、同じスキルで答えが返り、そのときは問題なしでした。ブロッキングを再現すると、先頭のブロッカーと kill すべき対象を教えられました。その後「全体の健康状態をもう一度」と聞くと、CPU のシグナルが入り混じっていると返され、さらに負荷を再現しても同様に検出されました。

もう 1 人の登壇者に「スクロールして」と促されて画面を下へ進めると、「このスパイクは登壇者自身が生成した（シミュレーションのようだ）」と Copilot が指摘していました。クエリは 1 本も書かず、クエリウィンドウで接続中のデータベースを文脈として会話しただけです。画面の細部は音声からは確認できません。

## 6. デモ・手順

このセッションは**ライブデモが中心**です。画面の細部は音声からは確認できないため、語られた範囲で整理します。

**デモ 1：Database Hub（本番テナント）**

4. Estate view でタグ絞り込み、「production critical」としてビューを保存・適用する。

6. アラート追加ボタン（Activator）を見せる。
7. issue から diagnostic query を表示し、アクションボタンで SSMS を開き、対象サーバー・データベースとクエリが引き継がれることを確認する。

**デモ 2：Database Agent**
1. 管理者ポータルでデータベースエージェントを有効にする。

## 7. 注意点・発表者の気付き

- **エージェントは現在プレビューで、対応するのは Azure SQL と Hyperscale のみ。** 他は今後拡大する予定です。
- Performance monitoring を有効にしないと、Performance タブとエージェントが動きません。
- **オンプレミス・他社クラウドのデータベースには Azure Arc が必要です。**
- Fabric SQL は Database Hub に未対応です。
- Hub のテレメトリは 28 日分です。それ以上は自分で保存する必要があります。
- 現時点では issue の kill 操作や自律動作は無効です。Copilot が出した書き換え案は、意味が同じか、行数が同じかを人が検証してから使います。
- 登壇者は、自身の環境のセキュリティ設定が甘かった点を例に、気づいていない問題が可視化されると述べています。
- スライドのタイトルには「Fabric 内」とありますが、登壇者は、Fabric 内に限らず estate 全体が対象だと訂正しています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **無料で使える。** Database Hub は無料。無料版の Fabric や Power BI 無料ライセンスでも利用できる。
- **estate 全体を 1 か所で見られる。** 存在を知らなかったデータベースや、セキュリティ上の問題、容量不足も見つけられた（登壇者自身の環境での経験）。
- 保存したビューや共有リンクで、自分の担当に絞って見たり、不在時に同僚へ引き継いだりできる。
- アクションボタンで、サーバー名やクエリのコピーという手間（click tax）が省ける。
- エージェントが問題を先に検出する構想で、「夜中 2 時の電話をなくす」ことを目指している。
- SSMS、VS Code、ポータルで同じスキルを使い、どこでも似た答えが得られる方針で、手元のツールで調査できる。
- RBAC に従い、データは保存しない。人が承認する前提で、エージェントの動作範囲を決められる。

顧客事例や数値による成果は、このセッションでは紹介されていません。

## 9. まとめ

Database Hub は、Azure SQL、PostgreSQL、Cosmos DB やオンプレミス（Arc 経由）を含む estate を、無料で 1 か所に集約する Fabric の機能です。Database Agent はその上で、ブロッキングや高 CPU など約 8 種類のシナリオを検出し、issue を作成します。Ignite では Copilot が加わり、原因や推奨事項の説明、クエリの書き換え案まで出せるようになりました。

ただし、書き換えの正しさの検証と実行の判断は人が行う設計です。エージェントの自律性は、信頼を得てから広げる方針です。同じ機能は VS Code（PostgreSQL / MSSQL 拡張）と SSMS にも展開されます。ロードマップでは、来年 3 月の FabCon US で GA とアラート通知、春に Agent 365 統合（スキルのカスタマイズも検討）、秋にさらなる改善が予定されています。登壇者は、試してフィードバックを送ってほしいと呼びかけています。
