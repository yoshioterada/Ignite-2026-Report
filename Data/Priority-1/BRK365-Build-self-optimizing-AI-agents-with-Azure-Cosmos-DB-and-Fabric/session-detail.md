# BRK365 Build self-optimizing AI agents with Azure Cosmos DB and Fabric

## 1. はじめに

AI エージェントは作って公開するところまでは速くできるようになりましたが、本当に難しいのは公開後です。回答の質は十分か、トークンコストが増えていないか、エージェントが遅くなっていないか、といった疑問が出てきます。さらに、見つけた改善点（モデルの切り替えや古いメモリの削除など）を、コードを再デプロイせずに素早く反映する方法も必要になります。

このセッションでは、マルチエージェントアプリを Azure Cosmos DB 上に構築し、運用データを Microsoft Fabric に流し込んで分析し、その結果を稼働中のアプリへ設定変更としてフィードバックする流れを、デモ付きで紹介しています。後半では、AML（アンチ・マネー・ロンダリング）コンプライアンス・プラットフォームを運営する Kinectify の CTO が、約 20 のエージェントから成る本番システムの運用と、自己最適化に向けた取り組みを説明しています。

エージェントの運用データをどこに溜め、どう分析し、どう設定に戻すのかを具体的に知りたい開発者に向けた内容です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK365](https://ignite.microsoft.com/en-US/sessions/BRK365)

### 5.1 課題：公開後に直面する問い

エージェントの構築と公開は速くなりましたが、利用者が増える公開後に、次のような問いが出てきます。

- エージェントは本当に良い回答を返しているか
- トークンコストはどこで膨らんでいるか
- エージェントはなぜ遅くなっているか
- 改善点が見つかったとき、モデルの切り替えや古いメモリの整理といった小さな調整を、フルのコード再デプロイなしでどう素早く反映するか

### 5.2 サンプルアプリ「Cosmos Voyager」のアーキテクチャ

Cosmos Voyager は、Python と LangGraph で作った旅行計画アプリです。利用者が自然な言葉で計画を依頼すると、supervisor agent が専門のエージェントを調整し、50 都市・約 3,000 か所を対象に日ごとの旅程を作ります。裏では、利用者の好み（ベジタリアンである、高級ホテルが好き、など）を抽出して保存し、以後の旅行にも自動的に反映します。

1 回のチャットで連携する構成要素は次のとおりです。

1. supervisor agent がユーザーのプロンプトを受け取り、ヘルパーエージェントを調整する
2. find places agent が、関連するホテル、レストラン、観光先などを探す
3. itinerary agent が、選ばれた候補から旅程を組み立てて保存する
4. Microsoft Foundry がクエリを埋め込み、ベクトル検索と全文検索に使う。これにより、キーワード一致だけでなく自然言語で照合でき、検索が速くなる

エージェントを 1 つの大きなものにせず、役割ごとに分けた理由として、各エージェントのコンテキストが小さくなって推論が良くなること、システム全体を書き換えずに個別のエージェントだけ更新できることを挙げています。

アプリを支える Cosmos DB の使い方は次の 4 点です。

| 用途 | 内容 |
| ---- | ---- |
| コアデータ | 場所、旅行、チャットのターンなどを保存。ベクトル埋め込みも同じ場所に持つので、別のベクトルデータベースは不要 |
| 実行状態 | Cosmos DB connector for LangGraph で、エージェント間の引き継ぎ時に実行状態をチェックポイントする |
| 長期ユーザーメモリ | Cosmos DB agent memory toolkit で管理する。好みを共有すれば、過去のチャットを全部走査せずに以後の会話で思い出せる |
| 最適化ポリシー | アーキテクチャ図の右端にある要素。エージェントの設定変更を稼働中に適用するために使う（5.5 で説明） |

### 5.3 Cosmos Voyager のデモ（アプリの操作）

Arroyo 氏が画面を使ってアプリを操作しました。アプリでは、都市、日付、旅行者数を選んで旅行計画を作ります。

**Profile memories タブ**

- 左側に、利用者がデフォルトで設定済みの好みが表示される
- 右側に、アプリが作った AI メモリが表示される。上部は要約された「ユーザーについての知識」で、Cosmos DB memory toolkit が約 20 ターンごとにスナップショットとして保存している
- 下にスクロールすると「stored memories」があり、チャットから抽出された情報に、fact や episodic memory といった分類と、salient score（重要度のスコア）が付与されている。エージェントが推薦時に何を取り出すかを判断するのに役立つ

**旅行計画の実行**

デモでは、Bahamas への旅行計画と「おすすめの夕食スポット」を依頼しました。裏では orchestrator agent がサブエージェントと連携して、場所探しと旅程作成を行い、ユーザーの保存済みメモリを Cosmos DB から取得しています。結果として 2 日間の旅程が作られました。

ここで確認されたのは、プロンプトにはベジタリアンと書いていないのに、**ベジタリアン向けのレストランが推薦された**点です。Cosmos DB 上のメモリから情報を引いているためだと説明されています。

### 5.4 Cosmos DB の特徴と、データの中身（VS Code）

Cosmos DB は Microsoft の分散 NoSQL データベースで、AI アプリ向けの利点として次の 3 点が挙げられました。

1. **柔軟な NoSQL（JSON）**：スキーマを時間とともに変えられる。SQL のような固定のテーブルはない
2. **ベクトルを同じデータベースに持てる**：Microsoft Research が開発したネイティブの DiskANN ベクトル検索により、高性能なベクトル検索とハイブリッド検索を運用データと並べて実行できる
3. **水平スケールアウト**：リレーショナルデータベースのように縦方向にスケールアップするのではなく、パーティションキーを選べば、パーティショニングは Cosmos DB が裏で自動処理する。スケールの増減が即座に行え、どの規模でも読み書きを高速に保てる

規模の例として、ChatGPT が Azure Cosmos DB 上で動いていると紹介されました。ChatGPT のセッションやチャットのデータは Cosmos DB に保存されており、発表では「10 億人超のユーザー、100 ペタバイトのデータ、チャット履歴とユーザーメモリで毎秒 7,000 万件超のリクエスト」と述べています。

続いて、VS Code の拡張機能で、アプリを支えるデータベース（travel assistant データベース）のコンテナーを確認しました。

| コンテナー | 内容 |
| ---- | ---- |
| messages | チャットの各ターンを保存する。履歴を 1 つの長い文書にまとめず、メッセージごとに 1 レコードにしており、クエリやデータの取得が高速になる |
| agent memory | 先ほどの要約を支える。ユーザーのコンテンツ、その種類、salient score、埋め込みを持ち、高速な取得を可能にする |
| node executions | LLM 自体はステートレスなので、supervisor とサブエージェントの間でやり取りがあるたびに状態を保存する。失敗時にチェックポイントから何が起きたかを辿れる。各エージェントの種類、使用モデル、消費トークンなどが記録される。引き継ぎは Cosmos DB の LangGraph 連携で処理している |

### 5.5 最適化ポリシー：再デプロイなしで挙動を変える

次に、Maldonado 氏が最適化ポリシーを説明しました。上記のコンテナーと並んで optimization policy コンテナーがあり、その中のポリシー文書を、LangGraph の supervisor が**毎ターン**確認します。

画面で示された内容は次のとおりです。

- プロンプトの複雑さに応じて、どのモデルを使うかを決める。1 つのモデルを全てに使い続けるとコストが膨らむため
- classifier フィールドがある
- 誰がいつポリシーを更新したかの監査記録（audit record）がある。変更は元に戻せ、時間の経過とともに追跡できる

ライブアプリがリクエストごとにポリシーを使う流れは、次の 4 ステップです。

1. ユーザーのメッセージを受け取る
2. モデルを呼ぶ前に、supervisor が Cosmos DB から有効なポリシーを読み込む
3. 軽量な classifier がプロンプトを複雑さで分類する
4. ポリシーで定義したモデル階層（tier）から、対応するモデルを選ぶ

これにより、アプリは**次のターンから**更新された挙動で応答します。

### 5.6 Microsoft Fabric による分析

運用データはそろいましたが、何を最適化すべきかを知るには分析が必要です。そこで Microsoft Fabric を使います。Fabric は OneLake 上に構築された統合分析基盤で、運用ワークロードと分析ワークロードをつなぎます。これにより、ユーザーとのやり取りに対する 1 桁ミリ秒の読み書きを保ったまま、重い分析スキャンがユーザートラフィックと競合しないようにできると説明しています。

**Fabric Mirroring の特徴**

- Cosmos DB のコンテナーを、ほぼリアルタイムで OneLake に複製する
- データは自動的にオープンな Delta Parquet 形式で OneLake に置かれ、構築・保守が必要な ETL パイプラインはゼロ
- OneLake へ複製するためのコンピュートは無料
- ストレージの一部は Fabric SKU に応じて無料。例として F2 キャパシティなら OneLake に 2 TB が無料
- 分析側のキャパシティはアプリと独立してスケールし、トランザクションの RU には影響しない

**このアプリでの分析の流れ**

1. データが OneLake に着地したら、Spark ノートブックでミラーされたテーブルを gold layer のインサイトに変換する
2. Spark Connector で、そのインサイトを Cosmos DB に書き戻す（reverse ETL）
3. 新しいポリシー変更を確認・適用する方法は 2 つある。Fabric 内で Power BI レポートから user data functions を起動する方法と、今回のように Cosmos DB に書き戻したデータの上に独自の分析ポータルを作る方法

### 5.7 Fabric でのデモ（ミラーリング、ノートブック、ダッシュボード）

Maldonado 氏が画面を操作しながら説明しました。語られた順に整理します（画面の細部は音声からは確認できません）。

1. Fabric のワークスペースで「新しいアイテム」から **Mirrored Azure Cosmos DB** を選ぶ。そこでアカウントのエンドポイントを入力し、複製したいコンテナーを選ぶだけで、ミラーリングの開始は簡単だと説明
2. すでに設定済みのミラー済みアーティファクトを開く。複製が済んだ状態で、選んだコンテナー、着地した行数、最終完了時刻が確認できる。データベースに新しいドキュメントが入ると、下流の分析用に OneLake へ自動で複製され続ける
3. 登壇者 2 人がアプリで実行したやり取りは約 200 ターンほどなのに、複製された行数はそれよりずっと多い。エージェント同士がタスクを完了するために大量のやり取りをしているため
4. 左側のコンテナーのうち、特に **optimization turns** コンテナーを示す。ノード実行の状態が保存されており、エージェントがタスク完了時に記録した挙動の豊富な生データが入っている。見つけた最適化は optimization insights に、適用するポリシーは optimization policies に入る
5. Spark ノートブックを開く。ノートブックは生データを下流で使いやすい形に変換する。注目点は 2 つある
   1. **LLM analyst**：変換後のデータをノートブック内の LLM に渡し、問題を検出して解決策を提案させる。画面のプロンプトは「You're an optimization analyst for a multi-agent app. Given a detected issue, propose exactly one change as strict JSON.」と読み上げられた
   2. **Spark Connector による書き戻し**：LLM のインサイトを optimization insights コンテナーに書き込む（reverse ETL）。ノートブックの中で、Fabric に着地した分析データを変換し、LLM でインサイトを得て、データベースに書き戻すところまで完結する
6. optimization insights に LLM の提案が入る。レポートはこの上に作れるが、今回は書き戻したデータを直接読む別の分析ポータルを作った。これがダッシュボードになっている

### 5.8 ダッシュボードで見つかった最適化と適用結果

Maldonado 氏がダッシュボードで次の点を示しました。

- すべてのターンが 1 つのモデルしか使っていない。ここに改善余地がある
- Optimizations タブに、ノートブックの LLM が見つけた提案が並ぶ。1 つ目は **capability tiered model selection**で、簡単なプロンプトは小さな LLM に回してトークンコストを抑える
- 2 つ目は **memory retention optimization** で、古いメモリを削除する。ストレージの節約に加えて、エージェントが関連情報を見つけやすくなる

tiered model selection を適用すると、先ほどの optimization policy コンテナーに新しいポリシーが作られました。その後、数ターン進めると、リクエストが別のモデルにも振り分けられるようになったことが確認できました。説明では、それまで 1 つのモデル（「5.1」と聞こえます）だけだったのに対し、mini と nano にも回るようになりました。ターン数については「約 1,200 ターン、つまり追加の 1,000 ターン」といった発言があります（音声認識の都合で、モデル名と数値は確定できません）。推定の削減額は約 3 ドルです。

登壇者は、3 ドルは小さい額に見えても、アプリが成長して利用者が増え、10 万ターン、100 万ターン、10 億ターンと規模が大きくなれば大きく積み上がる、と述べています。

### 5.9 Kinectify の本番事例

Kinectify は、ゲーミング業界向けの AML コンプライアンス・プラットフォームです。最大手のカジノ、スポーツブック、デイリーファンタジーの事業者からプレイヤーと取引のデータを取り込み、不審な行為や犯罪の可能性がある行為を分析し、顧客が連邦政府に適切に報告できるよう支援します。Azure、Microsoft Fabric、Application Insights の上に構築されていると紹介されました（音声認識の都合で、一部の固有名詞は聞き取り不明瞭です）。Calvin 氏は、本番環境でのマルチエージェントアプリの運用と、自己最適化に向かう過程を話しました。

**対象システムとデモ**

対象は、新しい customer intelligence module の enhanced due diligence（EDD）システムです。プレイヤーに対する AML 特有の身元調査（背景調査）を行い、1 件あたり約 5〜7 分かかります。Calvin 氏はデモを開始して実行を走らせ、スライドに戻りました。

- 顧客が、自社のプレイヤーについて知っている情報（属性など）を入力する
- システムが入力データを分析し、サードパーティのプロバイダー情報で補強し、そのプレイヤーが顧客のビジネスにもたらすリスクを要約する

**エージェント構成**

- customer intelligence module は約 20 のエージェントで構成される
- 多くはデータのドメインごとに特化したエージェント。ほかに、実行中のプロセスを監視する observer agents と、入口となる orchestrator agent がある
- 各エージェントが特定のタスクを担い、全体で EDD レポートを完成させる。流れは調査（research）、評価（evaluate）、レビューして完了
- Semantic Kernel と Microsoft Agent Framework で作られ、C# のものと Python のものが混在する。適材適所のツールを使う異種混在のアーキテクチャ

**本番で直面した問題**

エージェントの構築自体は簡単でした。しかしプライベートプレビュー（ベータ）として本番に出すと、次の問題が出ました。

1. KYC レビューが開始されても終わらず、止まったままになる。原因は様々。その 1 つは structured output の問題で、エージェント間は明確に定義されたインターフェースで通信するが、守られないことがあった
2. 誤検知（false positive）が多い。多数のデータプロバイダーから大量のデータを集めるため、その人に似ているが別人のデータが見つかりうる
3. 従来の APM（アプリケーション・パフォーマンス・モニタリング）の手法が、非決定的なシステムにはうまく合わない。監視と観測のやり方を調整する必要があった

**LLM call recorder と 3 か所へのデータ保存**

LLM とのやり取りの情報をすべて保存する LLM call recorder を作り、観測とテレメトリ用に 3 か所へデータを置いています。

| 保存先 | 保存するもの |
| ---- | ---- |
| Cosmos DB | LLM エージェントとの間を行き来する、生のリクエスト・レスポンスの内容 |
| Blob Storage | サードパーティとのやり取りの、生の HTTP リクエストとレスポンス |
| Application Insights | トークン数、使用モデル、往復にかかった時間などのテレメトリ（従来から APM として使用） |

これらを管理者ポータルに集約し、システムで何が起きているかを把握できるようにしました。この可視化により、次の改善ができたと説明しています。

- research agents の強化、プロンプト定義の反復改善、structured input/output 問題の解決
- observer agents の追加。サードパーティから来るデータと、それを要約するエージェントを確認し、EDD の対象者に関係するデータかどうかを見る
- エージェントから、EDD を行っているアナリスト（エンドユーザー）に質問を返せるようにした。例えば、その人物がカリフォルニアで活動しているように見えるが確信がないとき、アナリストに尋ねられる
- すべてのエージェントが完了し、結果をアナリストに返す前に、KYC レビュー全体に対する relevancy check を行う

**本番が教えてくれた 3 つのこと**

1. **完全なテレメトリとログを取る（サンプリングしない）**。従来の決定的なアプリは毎回同じ動きをするため、サンプリングでコストを下げられた。非決定的なシステムでは、ある実行ではエージェント間で 10〜15 回やり取りし、別の実行では 2〜3 回で終わることがある。何が起きたかを再構築するには、テレメトリが完全である必要がある
2. **カーディナリティ（作業単位）を理解し、相関 ID を付ける場所を考える**。従来は個々のマイクロサービスをブラックボックスとして単独で見ていたが、このシステムでは個々のコンポーネントよりも作業単位で見るほうが有用だった。1 つのエージェントのログだけを孤立して見ても再構築できない
3. **レジリエンス**。大手ゲーミング事業者が使う本番プラットフォームなので、テレメトリや観測の仕組みが本番の性能や信頼性に影響してはならない。例えば Application Insights のログ上限に達するなどして書き込めなくても、システムが止まらないようにする

**デモの結果と管理者ポータル**

Calvin 氏はアプリに戻り、先ほど実行した EDD が完了したことを示しました。デモの対象者（Clarence と呼んでいます）が高リスクであり、その理由が分かること、悪い評判の報道（adverse media）や法務情報が出ていることが説明されました。システムの中身には深入りせず、本題は「どう自己最適化へ育ったか」だとしています。

次に管理者ポータルを示しました。KYC システムで起きていることを分析するためのツールで、使用モデル、リクエスト・レスポンス、ログ情報などが確認できます。例として、ある実行では web scraper が失敗していることが分かり、その場合に EDD レポートから何が欠けるかを自分たちは把握している、と説明しました。各エージェントにかかった時間などのテレメトリも見られます。

**Fabric を使った自己最適化**

次の段階がシステムの最適化で、そこに Microsoft Fabric を使っています。

- Cosmos DB mirroring で Cosmos DB のデータを Fabric に取り込む（観測データは 3 か所にあるため、これだけでは全体にならない）
- Log Analytics ワークスペースを Fabric のワークスペースに shortcut する
- Blob Storage の情報も shortcut する
- これらを分析してシステムへの推奨を出す。さらに、Fabric 上に **data agents** を作り、このデータをリアルタイムに分析して、データサイエンス・データエンジニアリングのチームに提案させている

デモでは data agent のワークスペースを開き、テレメトリ情報と設定情報があることを示しました（公開できない情報が含まれるため詳細は割愛）。ミラーされたテレメトリを参照する agent が推奨を出します。何を質問したかは音声から確認できませんが、ミラーされたデータソースを分析し、特定のエージェントにどのモデルを使うべきかの提案を返す、と説明されました。

さらに、Fabric で作った data agent を copilot アプリに移し、データサイエンス・データエンジニアリングのチームが **scheduled tasks** を作っています。1 時間ごとに、直近に完了した KYC を確認し、システムの改善提案を出す scheduled task があります。将来的には、プロンプトの変更やコスト削減・性能向上のためのモデル推奨といった低リスクの最適化は、システム自身が行えるようにしたい、とのことです。**現時点では人間が判断する形を維持しており**、データサイエンティストが copilot の scheduled tasks 経由で提案を受け取り、採用するかどうかを決めています。

## 7. 注意点・発表者の気付き

- Maldonado 氏は、3 ドルの削減額は小さく見えるが、規模が大きくなると効いてくる、と述べています。
- Kinectify は、非決定的なエージェントシステムでは**サンプリングを使えない**と明言しています。実行ごとにエージェント間のやり取りの回数が変わるため、すべてを記録しないと何が起きたかを再構築できないという理由です。
- 観測は個々のエージェントではなく、作業単位で見る必要があり、相関 ID を付ける場所の設計が重要だと述べています。
- 観測・テレメトリの仕組みは、書き込み失敗（ログ上限に達する場合など）があっても本番を止めないようにしておく必要があります。
- Kinectify では、自動最適化はまだ行っておらず、人間が採否を判断しています。低リスクの最適化（プロンプト変更やモデル推奨）を自動化することは「将来できればよい」という位置づけです。
- Fabric Mirroring の無料ストレージは Fabric SKU に依存します（F2 で 2 TB の例）。
- mirroring TTL や Cosmos DB for Mongo API と Fabric の連携は private preview の段階です。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **データの一元化**：アプリデータ、ベクトル埋め込み、エージェントの状態、ユーザーメモリを Cosmos DB 1 つで持てる。別のベクトルデータベースは不要
- **再デプロイ不要の改善**：最適化ポリシーを Cosmos DB に置き、supervisor が毎ターン読むため、モデルの切り替えなどを次のターンから反映できる。変更は監査記録で追跡でき、元に戻せる
- **運用への影響を抑えた分析**：Fabric Mirroring により、分析がユーザー向けの読み書き（1 桁ミリ秒）と競合せず、トランザクションの RU にも影響しない。ETL パイプラインの構築・保守は不要で、複製用のコンピュートは無料
- **コスト削減**：デモでは、tiered model selection の適用で mini や nano にも振り分けられ、推定で約 3 ドルの削減が示された
- **Kinectify の成果**：観測の強化により、research agents の改善、structured input/output 問題の解決、observer agents による関連性の確認、アナリストへの確認機能、結果返却前の relevancy check を実現した。さらに、1 時間ごとの scheduled task で、データサイエンスチームが改善提案を受け取れるようになった

> 注意：Kinectify の事例では、削減率や処理時間の改善といった数値の成果は語られていません。

## 9. まとめ

このセッションは、エージェントを公開した後の「観測して、分析して、設定として戻す」サイクルを、Cosmos DB と Fabric で作る方法を示しました。Cosmos Voyager では、supervisor が毎ターン読む最適化ポリシーを使い、Fabric の Spark ノートブックで LLM が見つけた提案（モデルの階層化、メモリの整理）を Cosmos DB に書き戻して適用する流れが実演されました。

Kinectify の事例では、約 20 のエージェントを持つ規制業界の本番システムで、完全なテレメトリ、作業単位での観測、観測系の耐障害性という 3 つの教訓が共有されました。同社は Fabric の data agent と scheduled tasks で改善提案を自動的に受け取る仕組みを持ち、採否は人間が判断しています。

試すには、紹介された QR コードからオープンソースのサンプルとドキュメントを入手してください。
