## 5. 発表内容の詳細

### 5.1 Azure Managed Redis の紹介

Azure Managed Redis は、最新の Redis の革新の上に作られた、ファーストパーティのフルマネージドなインメモリデータストアです。ハイパースケール向けに設計されており、発表では次の特徴が挙げられています。

- 5 nines の可用性が得られ、TCO の面でもコスト効率が高いこと
- データベースを使うアプリにも使わないアプリにも向き、AI アプリにも適していること
- 低レイテンシ・高スループットで、数百万リクエスト規模までスケールできること
- Active-active geo-replication により、5 つの Azure リージョンにデータを分散できること（ユーザーが分散していれば、データも分散できるという説明）
- Flash optimized により、ホットなデータはメモリに、アクセス頻度の低いデータは安価な NVMe ストレージに置けること。大きなキャッシュをコスト効率良く持てるという説明です
- 自動アップデートとオンラインスケーリングを備えていること

Redis のモジュールも紹介されています。

| モジュール | 説明（発表より） |
|---|---|
| Redis Search | キャッシュを検索エンジンに変える。セマンティックキャッシュやベクトル類似検索を支える |
| Redis Time Series | 高スループットな時系列データ向け。IoT、テレメトリ、金融の株価などの用途 |
| Redis JSON | JSON データの保存・クエリ・検索を効率的に行う |
| Redis Bloom | 確率的データ構造のためのモジュール |

また、**Redis 8.2 が Azure Managed Redis で利用可能になった**と発表されています。実際のパフォーマンス向上があり、モジュールが組み込み済みなので、作成時に事前設定しなくてもいつでも使い始められます。さらにベクトル検索や API の拡張、vector sets も加わっています。これらは新しく作成した Azure Managed Redis クラスターで利用できます。

### 5.2 Redis を使うアプリの 4 分類

Redis を使うアプリは、おおむね次の 4 つに分かれると説明されています。このセッションで中心に扱うのは、1 と 2 です。

1. データベースアプリ：Redis がデータベースと並んで置かれ、アプリを高速化する
2. アプリ状態：セッション状態やアプリケーションのメタデータなど、一時的なデータを保存する
3. リアルタイム・メッセージング：PubSub と Streams を使う。IoT や金融などの分野に向く
4. AI アプリ：RAG や生成 AI 系のアプリ

### 5.3 Sitecore の事例：Content Hub とそのアーキテクチャ

Sitecore は、デジタルエクスペリエンスとコンテンツ管理のプラットフォームを提供する会社です。事例の主役は、アセット管理とコンテンツ管理を担う Content Hub です。ここは、複数のチームが集まってアセットを作成・整理し、メタデータやアセット間の関係を管理し、レビューと承認を行い、複数のチャネルに配信するための共有ワークスペースと説明されています。扱うのは画像、動画、PDF、ドキュメントなどで、アクセス権、バージョン管理、権利、承認といった要素や、バックグラウンド処理も伴います。

例えば小売業者が商品のアセットを管理する場面が挙げられました。1 つの商品には、さまざまな角度から撮った画像、動画、ドキュメント、使用説明書などがあります。ここでのアセットは単なるファイルではなく、メタデータや注釈などの文脈情報を持つものとして扱われます。

アセットが増えると探すのも大変になります。Content Hub には、メタデータ属性による検索・フィルターと、画像や説明文から関連アセットを探す AI を使った検索があります。検索可能にするまでの裏側では、正しいバージョンの特定、権利・権限の確認、承認、適切な形式での生成といったバックグラウンド処理が走ります。これを複数チームの数千のアセットで行うと複雑になります。発表では、Content Hub のアプリケーションが直面する課題を次の 3 つにまとめています。

- つながったデータの管理
- バックグラウンド処理の調整
- コンテンツを見つけやすくすること

アーキテクチャ（高レベルの図）では、役割が次のように分かれています。

| コンポーネント | 保持するもの |
|---|---|
| Azure Blob Storage | 元のファイルとそのレンディション |
| Azure Managed Redis | エンティティデータ（アセットを記述するレコードと、アセット間の関係） |
| Elasticsearch | 検索・取得を支える非正規化されたプロジェクション（検索インデックス） |

この 3 つはそれぞれ異なるアクセスパターンに対応しています。加えて、Azure Kubernetes Service（AKS）上で動く非同期ワーカーもあります。検索インデックスは再構築されることがあり、全体を作り直す場面もあります。ここでも Redis が関わります。

発表者は、この構成での Redis は「データベースの前に置かれた使い捨てのキャッシュ」ではなく、アプリケーションの核であるエンティティデータを保持していると説明しています。

- **コスト削減**：顧客に合わせてプロビジョニングやサイズ調整を柔軟に行えるため、大きなケースにも小さなケースにも、コスト効率良く、安全に対応できる。浮いたコストは製品への再投資に回せる

### 5.5 Sitecore における Redis の 3 つの役割

Shruti 氏は、同じ Content Hub のなかで Redis が果たす役割を 3 つに整理しています。

**役割 1：ネイティブのデータ構造によるエンティティ・関係モデル**

Sitecore は、顧客ごとに柔軟なスキーマ、分類体系（タクソノミー）、モデルをサポートしています。これらを JSON ドキュメントとして保存することもできたはずですが、Sitecore は Redis のネイティブなデータ構造（hash と set）を使い、アセット間の関係を表現しています。関係は set で表され、両方向からアクセスできます。商品同士の関係が変わったときは、hash や set に対する操作を行います。

発表者はここで、「すべてのアプリがデータベースを Redis に置き換えるべきだと言っているのではない」と明確に述べています。これはアプリケーションレベルの関係モデルを Redis のデータ構造で作った例であり、学ぶべき点は、アプリがどんなデータオブジェクトを必要とし、どんな操作をするかを考えることだ、という説明です。Sitecore ではその操作に hash と set が合っていました。

**役割 2：低レイテンシ・高スループットのデータ層**

レイテンシというと Web ページの読み込みを思い浮かべがちですが、Sitecore の場合は「検索インデックスをどれだけ速く再構築できるか」に直結します。小売業者が商品を一括で更新すると、アセット、エンティティ、関係、set など商品に関わるすべてが変わり、Redis には膨大な数のデータ操作（発話では thousands of thousands と語られています）が発生します。エンティティが変わると、非正規化プロジェクションと検索インデックスも再構築が必要です。再構築では、Redis からエンティティと関係のデータを大量に取り出し、インデックスを作り直して Elasticsearch にエクスポートします。

同じ操作を大きなワークフローで繰り返すと、わずかなレイテンシやスループットの差も全体の処理時間に表れます。そこで低レイテンシ・高スループットのデータストアが必要になり、Azure Managed Redis がそれを満たしたという説明です。ユーザーが直接触れないバックグラウンド処理でも、レイテンシは重要になります。

**役割 3：メッセージブローカー**

ホリデーシーズンに、小売業者が季節商品を数千〜数万点追加する場面が例に挙がりました。1 つの商品を追加すると、エンティティ、関係、アセットが連鎖的に作られ、メタデータの付与、レンディション生成、外部呼び出しなどのバックグラウンド処理が発生します。これは大きな処理の波になります。Sitecore は、この対応のために Redis をベースにした**カスタムのメッセージブローカー**を作っています。

- **優先度付きのメッセージキュー**で、裏側は sorted set。作業項目ごとに優先度を持ち、ワーカーが取り出すと最も優先度の高い項目から処理される
- ワーカーは Kubernetes 上のワーカー Pod
- Redis をベースにしたキューには、未処理メッセージ数（バックログ量）がある。Sitecore はこの数をカスタムエンドポイント経由でアプリケーションメトリクスとして公開し、**KEDA（Kubernetes Event-driven Autoscaler）** がそれを拾って水平スケールする。ここでの水平スケールとは、ワーカー Pod の数を増減させることを指す
- バックログが長ければ Pod が増え、未処理がなくなってカウントが 0 になれば Pod は停止する。これでキューを起点としたエラスティックなオートスケールが実現している

役割 1 では set、役割 3 では sorted set を使っており、**同じ Redis インスタンスでもデータ構造が違えば全く別の課題を解決できる**、とまとめられています。同じ Azure Managed Redis インスタンスを 3 つの用途で使える、という点が versatility（多用途性）の例として語られました。

### 5.6 事例から持ち帰ること

- Redis を足したから速くなった、というのが要点ではない。Redis はアプリケーションの不可欠な一部であり、システムが仕事とデータをどう解釈し、どう調整するかを表している
- ほかのアプリでは要件が異なり、主データはデータベースに置くのが適切な場合もある
- 自分のアプリについて、データオブジェクトの種類、そのデータへの操作、オートスケール用に出したいシグナルを問いかける

### 5.7 データベースの前段にキャッシュを置く：まず検討すべきこと

Justine 氏は、小売の EC サイトの例で話を進めます。フロントエンドと複数の API（カート API、注文 API など）があり、焦点は商品を返す products API です。ユーザーから「商品ページの表示が遅い」という声があり、ピーク時にはデータベースの CPU が高い、という設定です。データベースは Azure SQL ですが、キャッシュのパターンは Postgres や Cosmos DB など広く当てはまると説明されました。

> 注意：キャッシュを足すとパフォーマンスは上がりますが、複雑さも増えます。そのため、まずデータベースへのアクセス自体の最適化を行うよう勧めています。

データベース側で確認することとして、次が挙げられました。

- クエリが効率的に書かれているか、定義したインデックスを効率的に使えているか、必要な箇所で複合インデックスを使っているか
- データベースごとの適切な設定。例えば Azure SQL には、ストレージ読み取りを減らす buffer pool と、クエリのコンパイルを減らす plan cache（特にパラメータ化クエリで有効）がある。Postgres には、頻繁にアクセスされるページをキャッシュしてディスク I/O を避ける shared buffer cache があり、割り当てを調整できる。ただしデータベース内の他の処理とメモリを共有するため、大きくしすぎないほうがよい
- 結果の事前計算。複雑な集計結果を直接テーブルに格納する summary tables や、スキーマを少し変えて見せる materialized view

ここまで行っても遅い場合に、データベースの前にキャッシュを置く検討をします。キャッシュなら、結果を再利用して、データベースの CPU・メモリ・IOPS を使わずに読み取りを返せます。一方で、サービスが増えるため、2 つの間の**一貫性**、キーの期限切れ、リフレッシュを考える必要があります（これがトレードオフとして語られています）。

キャッシュを足すか判断する観点は次のとおりです。

1. **結果が再利用されるか**：もう 1 つのコピーを持つ以上、何度も使われる必要がある。人気の商品ページはその好例で、Black Friday のようなトラフィック急増の前に備えたいという例が語られています
2. **鮮度**：商品が更新されたときに古い値が残らないこと。ただし更新の種類によって求める鮮度は異なる。価格はいつも非常に新しくあるべきだが、在庫数のように、正確な数より増減の傾向が重要なものは非同期の更新でも許容できる
3. **書き込み側への効果**：キャッシュは書き込みにも使える。すべてをすぐデータベースに書く必要があるか、一部を遅らせてバッチで書けないかを考える

パターンは用途ごとに目的が違い、「1 つのパターンで全部」ではなく、1 つのアプリで全部使うこともある、と説明されています。

### 5.8 5 つのキャッシュパターン

#### (1) Cache-aside（読み取り）

最も一般的なパターンで、商品の閲覧のように頻繁に起こる読み取りに使います。source of truth は Azure SQL、キャッシュは Azure Managed Redis です。

1. products API は、まず Azure Managed Redis から商品を読みにいく
2. cache hit なら、そのまま API が返し、データベースには触れない
3. cache miss なら、Azure SQL から取得する
4. 取得した商品を、**TTL を付けて**キャッシュに保存する。保存しないと次回も miss になる

TTL（time to live）は鮮度を管理するための設定です。説明やタイトルの変更、新色の追加などが反映されなくなるため、永遠に残さず、業務要件に合う鮮度の TTL を決めます。

**鮮度と eviction**：TTL が短すぎるとデータは新鮮ですが miss が増え、SQL へのフォールバックが増えます。つまり鮮度と再読み込みのバランスが大事です。また、TTL を設定しても、その期間ずっとアイテムが残る保証はありません。キャッシュには容量があり、満杯になったときのために eviction policy があります。Azure Managed Redis の既定は **volatile LRU** です。

- volatile：TTL を持つアイテムが対象になる
- LRU（least recently used）：最も長く使われていないものから追い出される。このため、頻繁にアクセスされるホットな商品はキャッシュに残る

#### (2) Reference data prefetching（参照データの先読み）

安定した参照データを、cache miss や最初のリクエストを待たずに先に読み込むパターンです。例は商品カテゴリです。ページを開くたびにカテゴリを全部読み込みますが、変更は多くありません。そこでアプリの起動時に、products API が SQL からデータを取得し、Azure Managed Redis に入れておきます。TTL は付けません。読み取り時は SQL ではなく常に AMR に問い合わせ、データがあることを前提にできます。カテゴリが変わった場合は、あとで説明するイベント駆動の無効化で対処します。

#### (3) Write-behind（書き込みの遅延・バッチ化）

ページビューカウンターが例です。どの商品がどれだけ見られているかを数えるため、products API は AMR 上の hash をインクリメントします。ビューごとに SQL に書くとデータベースを過負荷にする恐れがあります。そこで、タイマーで動くバックグラウンドタスクが（例では 15 秒ごと、設定は自由）AMR に溜まった保留分を読み出し、Azure SQL に**1 回でまとめて**書きます。

> 注意：これは非同期のモデルです。業務要件に合う場合にだけ使います。ページビューは、毎回完全に正確であることよりデータベースのリソースを守るほうが重要なため適しています。

#### (4) Write-through（書き込みの同時反映）

価格更新のように、すべてのコピーが即座に正しい必要があるデータに使います。古い価格が表示され、会計時に驚かれてはいけない、という例です。products API が価格を $30 にする場合の流れは次のとおりです。

1. source of truth である Azure SQL の価格を更新する
2. cache miss と TTL を待たずに、すぐ AMR も更新する。このとき新しい TTL を付ける

SQL と AMR は別のサービスで、2 回の別々の呼び出しになります。**分散トランザクションや、両方が成功する保証はありません。** そのため、エラー処理、リトライ、一貫性の確保が必要です。SQL を先に更新するのも重要な点で、SQL への書き込みが失敗すれば、誤った結果をキャッシュに入れることがありません。

#### (5) Event-driven invalidation（イベント駆動の無効化）

アプリケーション外から書き込みが入る場合のパターンです。例では、倉庫が入荷時にキャッシュを使わず直接 SQL の在庫を更新します。一方で、Web サイトは在庫数を AMR 経由で表示しています。ここで、Azure SQL の **change tracking** を Azure Functions のトリガーにつなぎます。SQL で変更が起きるとビジネスロジックを持つ関数が実行され、AMR のアイテムを更新し、あるいは無効化（invalidate）します（発表では「アイテムを無効化する」と説明されています）。次にページが読まれると、SQL に保存された最新の結果が取得されます。TTL を設定していないカテゴリの更新にも同じパターンが使えます。

データ変更に反応する方法は、ほかにも紹介されています。

| 方法 | 説明（発表より） |
|---|---|
| Change data capture | データベースの変更通知の仕組み。SQL では change tracking、Cosmos DB では change feed |
| Redis Streams | 永続的なグループにイベントを発行し、コンシューマーが追いついたり再生（replay）したりできる。イベント駆動や CDC パイプラインに向く |
| Key space notifications | Redis の PubSub を使い、Redis 内のキーが変更されるたびに自動で通知する。ポーリング不要 |

そして、**Azure Managed Redis の key space notifications が一般提供（GA）になった**と発表されています。

### 5.9 本番に向けて考えること

デモアプリを実際の EC サイトにするなら、というかたちで次が挙げられました。

- **TTL jitter**：すべてのキャッシュ項目が同時に期限切れになると、リクエストがすべてデータベースに流れ、負荷を減らすつもりがデータベースを落としてしまうことがある。TTL にランダム性を持たせて、同時に切れるのを避ける
- **接続管理**：Redis の接続は、アプリの寿命の間続く長寿命の TCP 接続。クライアントを再利用し、コネクションプールを使う
- **レジリエンス**：リトライやサーキットブレーカーパターンなど、一般的なベストプラクティスは Redis を使うアプリでも有効
- **キー設計**：マルチテナントでは、キーにテナント分離が入っているか、あるユーザーが他のユーザーのデータを見てしまわないか。キーのスコープを決め、cache hit を認可する
- **バージョニング**：アプリの新バージョンをデプロイするとき、複数バージョンが共存できるか。破壊的変更を避けるため、キー形式にバージョンを入れる

## 6. デモ・手順

このセッションには、画面を使ったデモが 2 つあります（Sitecore の録画パートでも、Content Hub 画面を見せながらの簡単な紹介がありました）。いずれも画面の細部は音声からは確認できず、以下は発話で語られた範囲です。

### 6.1 EC サイト（Contoso）での 5 つのキャッシュパターンのデモ

登壇者（Justine 氏）が Contoso という架空の EC サイトに切り替えて、パターンを実演しています。

1. **参照データ先読み**：サイトに表示されているカテゴリのチップは、すでに Azure Managed Redis から読み込まれた状態。SQL を呼ぶ必要はなく、最初から表示されていた
2. **cache-aside**：最初のリクエストでは Redis に何も入っていないため、商品ページは Azure SQL から読み込まれ、約 **136 ミリ秒**かかった。カタログに戻って同じ商品を開くと、Redis キャッシュから提供され、**1 ミリ秒**だった。以降も Redis から返り、Azure SQL に追加の負荷はかからない
3. **write-through**：価格を更新するデモ。最初の価格は $110.05 で、「$100 を値引きする」ために 0 を 1 つ消して $11.05 にして保存した。価格は Azure SQL と Redis キャッシュの両方で更新され、ページの表示も Redis から 1 ミリ秒で返された
4. **event-driven invalidation**：在庫が 85 の状態から、アプリの外（倉庫）で 10 個の入荷があったという想定で restock を実行した。すると、ページは Azure SQL から返された（キャッシュが無効化されていたため）。在庫は 95 になっている。ページを再読み込みすると、再び Redis から返され、Azure Functions が SQL の変更を監視していたため在庫数は正しく 95 のまま、価格は $11 のままだった
5. **write-behind**：stats ページを開くと、Redis に保留中の項目はない（バックグラウンドタスクは 15 秒ごとに動作し、直近 15 秒はページを読み込んでいない）。商品をクリックして stats に戻ると、その項目が Redis に保留として表示された。ページを更新すると Azure SQL にフラッシュされており、バッチとして 1 回で書き込まれていた。デモでは 1 件のバッチだが、数千人のユーザーがいれば DB の負荷を大きく減らせる

### 6.2 Azure Managed Redis Agent Kit のデモ

Agent Kit は、AI 支援の開発をワークロードに取り入れるためのもので、今回の発表ではパブリックプレビューと説明されています。今使っているコーディング環境の中で、Redis を使ったアプリをより良く作るためのガイダンスを提供し、クライアント構成のリスクの検出やインフラの推奨も得られます。デモは次の順で語られています。

1. Visual Studio Code でコード一式のプロジェクトを開く
2. エージェントに、SQL Web アプリの**接続管理**がベストプラクティスに沿っているか確認を依頼する。あわせて、ファイル名と行番号付きで改善の推奨事項のトップ 3 を求める
3. 処理に時間がかかるため、以前に同じ質問をした結果の画面に切り替えて見せる
4. 推奨として示された内容は次のとおり
    - 既存の接続の認証を更新（リフレッシュ）すること。コードでは Microsoft Entra ID が使われていて（パスワードはどこにもない）良いが、接続が長寿命なので、トークンの再認証が必要
    - タイムアウトと、上限のあるリトライ（bounded retries）に取り組むこと
    - 最大接続数を設定し、アプリの回復性を高めること
5. すでにうまくできている点についてのアドバイスも表示されていた

Justine 氏は、Agent Kit によって、使っている環境の中で、アプリケーションに直接こうしたガイダンスが得られると説明しています。

## 7. 注意点・発表者の気付き

- **キャッシュの前にデータベースの最適化**：クエリ、インデックス、DB 設定、事前計算（summary tables、materialized view）を先に見直す。キャッシュは複雑さを増やす
- **一貫性**：データベースとキャッシュの 2 つのコピーになる。TTL、キーの期限切れ、リフレッシュの設計が必要
- **write-through は分散トランザクションではない**：2 つの別サービスへの呼び出しで、両方が成功する保証はない。エラー処理、リトライ、一貫性の確保が必要で、SQL を先に更新する
- **write-behind は非同期**：業務要件を満たす場合にだけ使う（正確さより DB 保護を優先できるページビューなどに限る）
- **TTL があっても eviction は起こりうる**：メモリが満杯になれば、volatile LRU に従って追い出される
- **TTL を同時に切らさない**：TTL jitter を使い、キャッシュ miss の一斉発生でデータベースを落とさないようにする
- **アプリ外からの書き込み**：キャッシュを使わない更新元がある場合は、event-driven invalidation が必要
- **マルチテナントとキー設計**：テナントをキーに組み込み、cache hit を認可し、バージョンをキー形式に入れる
- **Sitecore の構成をそのまま真似ない**：Sitecore の選択はその要件から来ており、ほかのアプリでは主データがデータベースに属する場合もある、と発表者は述べている

> 補足：Justine 氏が write-behind の説明で、書き込み先として「MySQL」と発言している箇所が 1 か所あります。本文では、ここまでの流れに合わせて Azure SQL として書いています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **Sitecore の事例（顧客からの動画での説明）**：専用リソースによる予測可能なパフォーマンス、日常的な管理とアップグレードの自動化による 2 名分の運用リソースの解放、Entra ID とマネージド ID・プライベートエンドポイントによるセキュリティ向上、顧客ごとのサイズ調整によるコスト削減
- **キャッシュ導入のデモ結果**：商品ページが Azure SQL からは約 136 ミリ秒、Redis キャッシュからは 1 ミリ秒で返った
- **write-behind**：ページビューのような更新をまとめて SQL に書き込み、データベースの負荷を減らせる
- **Redis のデータ構造と機能**：hash、set、sorted set などを使えば、同じインスタンスでデータストア、優先度付きキュー、オートスケールのシグナルといった別々の役割を担える
- **Agent Kit**：コーディング環境の中で、接続管理などの設定リスクや推奨事項を確認できる

## 9. まとめ

Azure Managed Redis は、Sitecore の Content Hub では、エンティティデータの保存先（hash と set）、検索インデックス再構築を支える低レイテンシ・高スループットのデータ層、そして sorted set によるメッセージブローカー（KEDA によるワーカー Pod の自動スケールと連動）という 3 つの役割を担っています。データベースを持つアプリでは、まず DB 側の最適化を行い、それでも必要なら、用途に合わせて cache-aside、reference data prefetching、write-behind、write-through、event-driven invalidation を組み合わせます。

本番に向けては、TTL jitter、接続の再利用とコネクションプール、リトライやサーキットブレーカー、テナントを考慮したキー設計、キーのバージョニングも設計に含めます。発表では、Redis 8.2 の利用開始、key space notifications の GA、Azure Managed Redis Agent Kit のパブリックプレビューも紹介されました。そのほかの Ignite での Azure Managed Redis に関する発表は、ブログ（aka.ms/ignite26/amr）にまとめられているとのことです。
