# BRK366 Database SOS: Choosing the right engine for your job

## 1. はじめに

このセッションは、「どのデータベースエンジンを、どの仕事に選ぶべきか」をテーマにしたパネルディスカッションです。Microsoft のモデレーター 1 名と、パートナー企業 3 社（TCS、IBM、Tech Mahindra）のパネリストが登壇し、お客様の要件の変化、選定時のトレードオフ、選び方の進め方を話し合います。後半では、各社が実際に手がけた案件を 1 件ずつ紹介します。

全体を通じて繰り返される結論は、**「万能のデータベースは無く、ビジネス上の成果（アウトカム）から逆算して、用途に合ったデータベースを選ぶ（場合によっては複数組み合わせる）」** という考え方です。スライドの製品紹介よりも、現場の判断基準と実案件の話が中心なので、データベース選定の議論に参加する開発者・アーキテクトが「他社はどう考えているのか」を知るのに向いた内容です。

> 補足：このセッションでは画面を使ったデモは行われていません。パネル形式の対話と、各社の事例紹介が中心です。

## 3. 何に関する発表か

アプリケーションや AI エージェントは、新鮮で高速、かつスケールするデータをデータベースから受け取ります。しかしリレーショナル、NoSQL、オープンソースなど選択肢が多く、「自分のプロジェクトにはどれが合うのか」が分かりにくくなっています。このセッションは、その判断を現場で行っている人たちの経験から学ぶ場です。

進行は次のとおりです。

1. モデレーターによる導入（データ要件の変化の整理）
2. パネル質問 1：お客様の技術要件はこの数年でどう変わったか
3. パネル質問 2：最も多く求められるデータベースの機能は何か
4. パネル質問 3：データベース技術を比較するときのトレードオフは何か
5. パネル質問 4：お客様が正しいデータベースを選ぶのをどう支援しているか（エージェントによる vibe coding の話題を含む）
6. 各社の実案件の紹介（TCS、IBM、Tech Mahindra の順）
7. モデレーターによるまとめと、データベースのロードマップなどの案内

> 補足：時間の都合で、準備されていた質問のうち最後の 2 つは省略され、「終了後に個別に話しましょう」とモデレーターが述べています。省略された質問の内容は発表では明らかにされていません。また、会場からの質疑応答（Q&A）の時間はありませんでした。

## 5. 発表内容の詳細

### 5.1 モデレーターによる導入：データ要件の変化

モデレーターは、セッションの背景として「データへの要求が変わってきた」点を挙げています。

- **新鮮なデータへの即時アクセス**：数年前は顧客に「リアルタイム」の意味を聞くと実際には厳密なリアルタイムは不要でしたが、今は AI で正しい判断をするために本当にリアルタイムのデータが必要になっています（モデレーターの説明）。
- **トランザクションの大量データ**：モデルの学習や情報取得のために、大量のデータが必要になっています。
- **低レイテンシ**：データベースは AI の取り組みを支える基盤としてますます重要になっています。同日に別のセッションで「データ統合 → コンテキスト → 信頼」という流れを取り上げており、その最初の基盤層が重要だと触れています。
- **AI 向けの機能**：ベクトル埋め込みや複雑な検索機能が必要で、「ベクトル専用のデータベースを別に作る」のではなく、運用データベース自体が AI ワークロードを扱えることが求められています。
- **トランザクションと分析の両立**：リレーショナルか非リレーショナルか、SQL か NoSQL かにかかわらず、トランザクションデータと分析データを同時に扱う必要があります。モデレーターは「translitical」という言葉に触れています（音声認識上の表記）。仕事の情報（Work IQ に言及）やファイルストレージなど、他のデータにも簡単にアクセスできることが必要だと話しています。
- **プライバシーとコンプライアンス**：正しく行い、データを信頼できることが求められます。

### 5.2 質問 1：お客様の技術要件はこの数年でどう変わったか

**Vilas（TCS）の回答**

- 経営層（CXO）は、測定可能なビジネス成果、ROI、コスト削減を求めています。
- ユースケースは、一方の端が移行・モダナイゼーション、もう一方の端が AI の先進的な変革です（音声認識上は「AL8 frontier transformation」。表記は確定できません）。
- モダナイゼーションでは、総所有コスト（TCO）の削減、CapEx・OpEx の削減に加え、AI 支援による「より速い移行・変換」が求められます。
- 分断されたデータセットが AI のパイロットから先へ進めない原因になっているため、統一されたガバナンスのあるデータ基盤が求められています。
- 実行主体が人やアプリケーションだけでなく、Copilot、プラグイン、エージェントになってきたため、監査可能性（auditability）の要件が出てきています。
- パフォーマンス、レイテンシ、規制遵守の要件も、より厳しくなっています。

**Eric（IBM）の回答**

- 技術要件は「何をするのか」「どんな成果を出したいのか」に主導されるようになり、技術やバックエンドは二の次になっています。
- データの分け方も変わりました。以前は 1 種類のデータベースエンジンに入っていたものが、ワークロードや成果に応じて複数のエンジンに分かれています。
- セキュリティが大きな関心事です。ネイティブなデータプラットフォームやネイティブなセキュリティモデルが無いと、「なぜ無いのか」を問われるようになっています。セキュリティと一体のものとして ID（アイデンティティ）も重要です。
- コストの会話も増えました。データ資産を一度にすべてプロビジョニングする必要があるのか、アプリケーションと一緒に成長できるのか、といった観点です。
- Fabric とどうつなぐか、監視（observation）に何を使うか、といったデータ資産の相互接続も、5〜7 年前には話題にならなかった技術的論点です。

モデレーターは、Eric の「用途に合わせて複数のデータベースに分ける」という点に意外さを示しました。Eric は、データベースをコンテナや PaaS サービスに置くなど、データを扱う方法が増えており、セキュリティや運用を制御しやすくなると説明しています。これに対してモデレーターは、ツールが充実し、セキュリティなどを横断して一貫して扱えるので、1 つのシステムに無理に押し込まなくてよいという整理をしています。

**Moin（Tech Mahindra）の回答（CRM を例にした変遷）**

- 2022 年まで：CRM は、小売やコールセンター、チャットで顧客に対応するためのもので、アカウント情報、請求情報、プロファイル、返金などの複数の記録システム（system of record）を統合して担当者の前に並べ、「担当者が自分で見つける」形でした。
- ChatGPT 登場後（2022 年〜2025、2026 年）：AI 機能を求められ、検索ベースや RAG ベースのエンジンを CRM 内のポップアップとして追加しました。しかし、これは独立したウィンドウで、背景や顧客対応の流れ（ジャーニー）、意図を理解しないため、目的を満たしません。
- 現在：お客様は、**文脈を理解し、かつ先回りして動く「つながった層」（control plane）** を求めています。窓口の担当者は日々の業務の中で「顧客にとって価値があるのに自分が見落としていること」を知りたいと考えています。そのための機能として、Data Cloud や Fabric が重要になるという見方です。

### 5.3 質問 2：最も多く求められるデータベース機能は何か

回答は Moin、Eric、Vilas の順（モデレーターが「後ろから」と宣言）で行われました。

**Moin（Tech Mahindra）**

- マルチモーダルは多くの人が求めていますが、現在の意味は文書、契約書、ナレッジ資産が中心です。それ以上に、CRM では顧客からの**音声通話**や、担当者の操作を記録する**画面録画**といったデータタイプが対象に入ってきています。
- 画面録画の用途として、コーチングのためのツールがあります。Moin の側では guided selling（案内型の販売支援）のユースケースがあり、熟練した担当者の発話とアプリケーション上の操作を学習データとして使い、モデルをよりよく訓練しています。
- さらに、スマートなアノテーションとメタデータの拡充が挙げられています。1 つのアプリケーション・1 つのデータベースにデータが集まっていれば、バックグラウンドでデータを修正・相関させる作業が減るという考えです。

**Eric（IBM）**

- スケーラビリティ、信頼性、障害時の冗長性。以前はサーバークラスターを複数用意し、複数環境やデータセンターへフェイルオーバーするため、ハードウェアが大きく高価でした。Azure SQL と、他のサービスとのネイティブな接続によって、この部分の機能が実現しやすくなっていると説明しています。
- AI のコンテキストに同じデータを使えること。データ資産の準備ができていなければ、強力な AI アプリケーションは作れません。会社が「使うべき」と言われている AI 機能を、どのようにスケールさせて活用できるかが問われています。

モデレーターは、信頼性とパフォーマンスは昔から重要だったが、エージェントが水平にすばやくスケールする環境ではさらに重要になると述べています。

**Vilas（TCS）** は、ユースケース別に求められる機能が違うと説明しています。

| ユースケース | 求められる機能 |
| ---- | ---- |
| 移行 | 移行を支援する AI |
| AI 変革 | データベースにネイティブな AI 機能。運用データの近くでの統合ベクトル化（integrated vectorization）、マルチモーダル |
| データ全体 | データエンティティ間で、つながったビジネスコンテキストを広げること（オントロジー層への期待） |
| 分離 | 1 つのデータベースの中でトランザクションと分析のワークロードを分離すること（isolation） |

Vilas は、Microsoft が AI ready なデータベースをリリースしているため、これらにお客様が関心を持っていると話しています。

### 5.4 質問 3：データベース技術を比較するときのトレードオフ

**Eric（IBM）**：判断は「成果は何か」に戻ります。コストとパフォーマンスの例として、VM から Azure SQL へ移行する際、パフォーマンスを測ったところ、特定の処理で Intel のチップのほうが AMD の SKU より少し遅い場面があった、と述べています。そのため「どのバージョンの VM を使うのか、本当にその VM を使うべきなのか」を要件から考えることになります。お客様は、以前は考えなくてよかったこと、たとえば「データ資産の最終的な姿は何か」を考える必要があります。特に AI ではコストが大きな要素で、データ資産が大きくなるほど、正しくスケールできることが重要になると話しています。

**Moin（Tech Mahindra）**：選んだユースケースにおけるコスト最適化と、収益機会のバランスだと説明します。例として、**自己管理の Cassandra と Cosmos for Cassandra を併用しているお客様**を挙げています。

- 書き込みが多い処理は、自己管理の Cassandra で処理する。
- Cosmos for Cassandra は、保証された SLA のために使う。
- 理由：オファー、リワードカード、プロモーションを提示する場面は収益機会であり、お金をかける以上は、利益が戻ってくることを確実にしたいため、厳密な SLA が必要になる。

**Eric の補足**：以前は技術的なトレードオフ（ディスクの本数、IOPS、ネットワークスループット）を議論していたが、今は成果ベース・製品ベースの「ソフトな」トレードオフをデータ資産レベルで議論する、という変化が最大の違いだと述べています。

**Vilas（TCS）**：完璧なデータベースは無く、コスト、期間、予算と、ワークロード（パフォーマンスやスケール）の間でトレードオフがあると述べ、2 つの例を挙げています。

1. **ベクトル**：専用のベクトルデータベースか、データベースに統合されたベクトル化・ベクトル検索か。数十億のベクトルやペタバイト規模、複雑なシナリオなら専用ベクトルデータベース。そうでなければ、運用データと統合データの同期が不要になる統合ベクトル化を選ぶ。
2. **セキュリティ**：銀行や医療などでは、業界規制のために顧客データの暗号化が求められる。一方、開発者の速度を重視する場合もある。そのため、カスタマー管理キーなどを使った暗号化と、より簡単な既定のセキュリティのどちらを選ぶかのトレードオフが生じる。

モデレーターは、CMK のような機能が、アーキテクチャだけでなく「どのデータベースを選ぶか」の判断にも関わると整理しています。

### 5.5 質問 4：お客様が正しいデータベースを選ぶのをどう支援しているか

**Vilas（TCS）：重み付けスコアリングモデルとタイムボックスの POC**

1. ワークロードを評価し、クエリパターン、読み取り・書き込みトランザクション、ピーク負荷を把握して、選択肢を出す。
2. 規制要件で必須となる機能がある場合は、それを満たさないデータベースは候補から外れる。必要な統合機能も条件になる。ここで候補を絞る。
3. お客様と一緒に、重み付けスコアリングモデルでスコアを付ける。ワークロード、性能とスケールの優先度を、お客様と席を並べて決める。
4. 2〜3 個のデータベースまで絞り、スコアを鵜呑みにしてもらうのではなく、**既存のデータを使ったタイムボックスの POC** を行い、成功基準に基づいて選択肢を出す。
5. その他の要素：今後 2、3、5 年の TCO、ライセンス、必要なスキルを確保できるか。

モデレーターは、これを「拒否権（コンプライアンス上合わなければ除外）＋お客様のルーブリックによる重み付けスコア」と整理し、TCO もスコアモデルに含まれるのか確認し、Vilas が「そのとおり」と答えています。

**Eric（IBM）：データ資産の理解と、移行と新規の 2 つのプロセス**

Eric は、データ資産を理解することが最も重要だとし、「Texture」というツール（社内ツールまたは公開ツール）を使うと述べています（音声認識上の表記）。移行と新規開発は別のプロセスであり、多くの人は今も一括りに「実装」と考えていると指摘しています。

- **移行・モダナイゼーションの評価**：パフォーマンス、スループットなどの基本要素に加え、どこで接続が発生し、どのアプリケーションがそれを動かし、同じ枠内の他のデータセットやデータベースとどう関係するかを、ツールで把握する。Azure Migrate のデータ、または出始めている Catalyst のデータと組み合わせる、と話しています。そのうえで「目標は何か」（支出削減、パフォーマンス向上、セキュリティ強化）を決める。経営層の視点で、これらのいずれかが動機になる必要があり、「最新バージョンにしたい」「より信頼できるサーバーにしたい」だけでは動機にならない、という考えです。
- **新規構築**：まず「構想」（envisioning）から始め、「魔法の杖を振れるなら、どう作りたいか」を聞く。「frontier elements」や「frontier engineering firm」の考え方も取り入れる、と話しています（詳細は語られていません）。エコシステムがどう動くべきかを理解したうえで、個別のサービスを組み合わせる。Fabric とどう連携するか、エコシステム全体でどう使うか、を考える。
- **オントロジー**：今年重要になる要素で、オントロジーを引き出しながら同じ場所でデータを扱えれば、データベース選びでも大きな意味を持つと述べ、Fabric を例に挙げています。

モデレーターは、移行と新規という 2 つの取り組みの分け方に賛同し、Catalyst について「今週まだ聞いていなければ調べてほしい」と案内しています。

**Moin（Tech Mahindra）：4 つの「仕事のポートフォリオ」**

1. **移行**：企業の目指す方向（North Star）に合わない旧アプリケーションや旧データベースを廃止する。リフト＆シフト。
2. **安定化**：例として Apache Cassandra は管理にリソースを多く要するため、Azure のマネージド Cassandra に移す選択肢がある。
3. **モダナイゼーション（デジタル変革）**：データベースだけを見るのでは足りず、体験につながる。顧客に正しく対応できているか、先回りできているか、どんな機能が必要かを考える。
4. **並行トラック**：変革・モダナイゼーションのプロジェクトには、終わりが見えないものがある。そのためお客様は、AI ベースの vibe coding のアプリケーションを並行して立ち上げ、グリーンフィールドで作る選択肢を取れる。

どのカテゴリかが決まったら、**2〜3 日のハッカソン**にビジネス側、SME、技術チームを最初から巻き込み、現在と将来の働き方で何が変わるかを見せます。そうすると採用・合意形成が進みやすく、その日の終わりには「基本的に 60% は合意できている」状態になり、その後の実装・実行に進めると説明しています。

#### 5.5.1 vibe coding とデータベース選定（やり取り）

モデレーターは「vibe coding をするとき、エージェントがデータベースを選ぶのか、候補を絞って渡すのか」と質問しました。

- 並行トラックを話した登壇者（文脈上 Moin）は、ビジネスは別アプリケーションや別データベースとのつなぎ方を気にするため、5〜6 年、数百万ドル規模で続くプロジェクトから「抜け出す」ために、グリーンフィールドの vibe coding 基盤を作るのは新しいカテゴリだと述べ、エージェントにデータベースを選ばせて自由に走らせる案にも触れています。
- Eric（IBM）は、エージェントに自由度を与えるのは良いが、**適切な ADR、ルール、スキル**（どの種類の作業にどの種類のデータベースを使うか）を与えることが重要だと述べています。コード開発のフレームワークの一部としてデータベースが含まれ、要件に合わせてコードとデータベースを並行して作るため、小さな用途特化型（fit for purpose）のデータベースが作れる、という説明です。

モデレーターは、2 人の話から、データ層でも開発者主導の設計・開発が増えていると受け止め、社内でも話題になっている点だと述べています。

### 5.6 事例 1：TCS ― 欧州の大手銀行のアーカイブ記録管理システム

Vilas が紹介した事例です。買収した銀行を統合した欧州の大手銀行の**アーカイブ記録管理システム**を、メインフレームの DB2 から **Azure SQL Hyperscale** へ移行したものです（音声認識上は「Hyperscaler」と聞こえます）。

**ワークロードの規模と特徴**

- 数ペタバイト級のデータ。顧客ノートや KYC の詳細を含む、数十億件の顧客レコードがあり、機密データを含みます。
- アーカイブ用途のアプリケーションですが、法務・監査チームが毎日利用し、銀行のリレーションシップマネージャーも利用するため、法務とコンプライアンスが重要です。

**課題**

- クラウドネイティブなデータベースへ移行すること。元は DB2 のメインフレームでした。
- 稼働中のデータベースで、毎日確保できる移行のための時間が非常に短いこと。
- 移行と照合（reconciliation）を組み合わせ、照合にはハッシュ手法を使ったこと。
- お客様は早くデータセンターから退出して TCO、CapEx、OpEx を下げ、浮いた費用を今後の取り組みに再投資することを目指していたこと（「DC ads」と聞こえる部分は、音声認識上の都合で正確な表記が確定できません）。
- データベースにアクセスするアプリケーションはオンプレミスのモノリシックなものでしたが、一部はマイクロサービスアーキテクチャで移行されたこと。
- 高可用性、バックアップ、エンタープライズレベルのセキュリティ、柔軟な価格モデルが必要で、お客様はリザーブドの価格モデル（reserved capacity）を選んだこと。

**Hyperscale を選んだ理由**

- 要件のスケール。当初は約 20 の Azure Hyperscale データベースを構成し、2 ペタバイトのスケールに対応できました。最終的には、ホットクラスターに 400 テラバイトのみを置き、残りは ADLS ストレージに置く形に絞り込む予定です。
- 欧州のお客様として必要な**データレジデンシ**と条件付きアクセス制御。
- Hyperscale は**1 データベースあたり 128 テラバイト**を持てること。

> 補足：このプログラムでは、AI の実装はまだ先行していないとのことです。

**成果**

- 2 ペタバイトの移行に**1 年以上**かかりました。毎日の枠が短く、1 日に少なくとも **4〜5 テラバイト**を移行できました。
- 継続的な（毎日の）照合にも相応の時間がかかりました。
- **TCO を約 60% 削減**。規制対応・コンプライアンスの向上、顧客とエンドユーザーの体験向上を達成しました。
- 単なるモダナイゼーションにとどまらず、将来のデータ基盤になったと説明しています。

モデレーターは、メインフレーム移行、ペタバイト規模、ハッシュによる比較（銀行なので完全に一致が必要）、データレジデンシという課題を挙げ、要件に基づいて決定したことを評価しています。

### 5.7 事例 2：IBM ― AWS 上の SaaS 製品を Azure へ

Eric が紹介した事例です。**AWS 上にあった SaaS 製品を Azure へ移した、AWS からの切り替え（compete）案件**です。アプリケーションはクラウドで生まれ、クラウドで作られたものでしたが、Azure のワークロードとして動かす必要がありました。将来を見据えて Azure プラットフォームでの AI にも目が向いていたため、Microsoft と協力してアプリケーションを Azure に持ち込みました。

| 移行元 | 移行先 | 補足 |
| ---- | ---- | ---- |
| AWS RDS | Azure SQL Managed Instance | アプリケーション全体で変換。使い慣れた柔軟性を保ちつつ、Azure プラットフォームの他のサービスとの接続を活かせる |
| AWS DynamoDB | Azure Database for PostgreSQL | 最初は Cosmos DB を検討したが、事業成果の観点から、アプリケーションとシステムの動き方では大きく**過剰にプロビジョニングされる**ことが分かった。そこで Postgres を選び、より制御しやすくなった |

その他の点です。

- Microsoft の **Cloud Acceleration Factory**（CAF）チームと協力しました。多くのパートナーがさまざまな形でこのチームと関わっていますが、IBM はこのチームの技術を積極的に取り込み、Microsoft と IBM が一体となって、お客様に両社の技術の幅を提供しています。データプラットフォームレベルでのデータ資産の移行にこのチームを活用し、データベースエンジンの変換は IBM が担当しました。
- AWS 上のクラウドネイティブなアプリケーションを「functions」に持ち込むには、多くの統合作業が必要で、アプリケーション自体の変換も多く発生したと話しています（functions の具体的なサービス名は発表では語られていません）。
- 結果として、お客様は Azure 上で顧客基盤を新しい形で拡大できるようになった、と説明しています。

モデレーターは、「すべてのデータベースがすべてのワークロードに最適とは限らない」例だとコメントし、顧客でもパートナーでも、Factory は Microsoft がお客様の成功に投資しているものなので活用してほしいと呼びかけています。

### 5.8 事例 3：Tech Mahindra ― Fortune 500 企業の Customer 360

Moin が紹介した事例です。複数の小さな会社を買収してきたグローバルな Fortune 500 企業の案件です。

**背景の課題**

- 似たアプリケーションの維持が、時間とともにコスト高になっていた。
- アプリケーションの応答が遅く、顧客検索のロジックにも非常に時間がかかった。
- コンテンツが定期的に更新されず、店舗で見る画面とコールセンターで見る画面が異なっていた。
- 規模は 1 日あたり **6,500 万回の API コール**（65 million）。

**アプローチ：ポリグロットアーキテクチャ**

用途ごとに目的特化型のデータベースを、その強みに合わせて採用しました。

| データベース | 選んだ理由・役割 |
| ---- | ---- |
| Azure Cosmos DB | 主に**スケール**を担う。この点で一貫して優れていた |
| Azure Cosmos DB for Cassandra | 保証された SLA。読み取りの価値が高く、上流のアプリケーション（デジタルセンター、小売など）の収益機会を支える |
| AMR | Cosmos や Cassandra に負荷をかけすぎないための層。7 日以内に再来した顧客のような「ホット」なデータを置く。7 日以内に電話や来店があれば、前回の行動を知る必要があるため価値がある（略称は音声認識上の表記で、正式名称は発表で確認できません） |
| Azure DB for PostgreSQL | 2 つの目的。(1) ルールエンジン（適格性の基準、データ品質の適格性）、(2) 適格性ルールのバージョン管理（ドラフト → テスト → 公開、と進めて、A/B テストに使う） |

**現在進めていること**

- お客様は、自己管理の Cassandra と Solr の組み合わせも検討していました。「デュアルライト問題」があり、現在は、あいまい検索（アカウント ID、電話番号、メールアドレスなどを使った顧客検索）に Solr のインデックスを使っています。
- これを Cosmos DB と AI Search に移して、デュアルライト問題を解消しようとしており、これは現在進行中の取り組みです。

**成果（value realization）**

- 上流の**アクティブなアプリケーションが 50 個**このデータを利用している。
- 実装前と比べて、API コール数が約 **29%** 減った。
- 応答時間が **8〜10 秒から、300 ミリ秒〜1 秒**（ページロード）になった。
- Web サイトでの顧客の滞在時間は短く、価値ある情報をその場で出せなければ離脱されるため、セルフサービスチャネルを強化し、人手の窓口への電話（1 件ごとに対応コストがかかる）を減らすという KPI が重要になっている。
- お客様が目指しているのはオムニ体験で、「言うは易し、行うは難し」と述べています。
- 認証済みの顧客ごとに、表示するカード情報などが異なるパーソナライズされたレコメンデーションを、Customer 360 のデータベースで可能にしています。

### 5.9 まとめ・案内（モデレーター）

モデレーターは最後に、次のようにまとめ、案内しています。

- **使い分け**：3 人は一貫して「ビジネス成果 → 課題 → 要件 → 用途への適合」の順で考えている。1 つのデータベースですべてをまかなう考えではなく、4〜5 個使うこともある。Azure には、AI に最適化され用途に合わせて選べるデータベースがそろっており、「1 つ使っても、複数使っても、1 つのアプリケーションですべて使ってもよい」。
- **共通点**：どのデータベースも AI スケールのデータを扱え、リアルタイムで動き、高速で効率的なベクトルサポートがある。モデレーターは EBC をいくつか担当していて、各データベースの利点の説明スライドがほぼ重複することがあると話しています。一方、スケールアウトとスケールアップで選択を誤るとコストが高くなるため、どれが何に向くかは理解が必要だとしています。
- **ロードマップ**：データベースのロードマップを**外部に公開し始めた**。Fabric のロードマップが以前から公開されているのと同様で、四半期ごとの計画が見られる。今週の火曜日に公開されたばかりだと述べています。
- **関連セッション**：当日残っている関連セッションとして、次のものを挙げています。
  - Azure DocumentDB（オープンソースの DocumentDB 上に構築。スケールアップ型のワークロード向け）
  - 「Why Azure is the best cloud for SQL」
  - 「Building multi-agent solutions on Cosmos DB」（スケールアウトを目指すなら Cosmos DB が最適、と述べています）

## 7. 注意点・発表者の気付き

- **コストと過剰プロビジョニング**：Eric の事例では、DynamoDB の移行先として最初は Cosmos DB を検討しましたが、アプリケーションの動き方では大きく過剰にプロビジョニングされると分かり、Postgres に切り替えました。
- **VM の選択**：VM から Azure SQL への移行で、パフォーマンスを測ると、Intel のチップが特定の処理で AMD の SKU より遅い場面がありました。どの VM を使うかは要件から決める必要があります。
- **ベクトルデータベースの選び分け**：数十億のベクトルやペタバイト規模、複雑なシナリオでは専用ベクトルデータベース、そうでなければ統合ベクトル化、という Vilas の目安があります。
- **セキュリティと開発速度**：業界規制で暗号化が必要な場合と、開発者の速度を優先する場合では、カスタマー管理キーの採用などの判断が分かれます。
- **移行の所要時間**：TCS の事例では、稼働中のデータベースで毎日使える移行時間が短く、1 日 4〜5 テラバイトのペースで 2 ペタバイトの移行に 1 年以上かかりました。照合も毎日必要でした。
- **移行と新規構築は別のプロセス**：Eric は、両者を同じ「実装」として扱う人が多いが、評価の進め方が異なると指摘しています。
- **移行の動機**：Eric は、経営層の視点で、支出削減・パフォーマンス向上・セキュリティ強化のいずれかが無いと進まず、「最新バージョンに上げたい」だけでは動機にならないと述べています。
- **エージェントにデータベースを選ばせる場合**：自由度は与えつつ、ADR やルール、スキルでデータベースの定義と使い分けを与えることが重要という点が、Eric の経験として語られています。
- **ビジネスを最初から巻き込む**：Moin は、2〜3 日のハッカソンにビジネスと SME を入れると、採用と合意形成が進むと述べています。
- **発表で触れられなかったこと**：具体的な製品の価格、各データベースの詳細な性能数値の比較、機能の比較表などは示されていません。

## 9. まとめ

データベース選びは、技術仕様の比較ではなく、ビジネス成果から始める話になっています。3 人のパネリストは、要件の変化として、成果、セキュリティ・ID、コスト、AI 対応、監査などをそれぞれ挙げ、完璧なデータベースは無いという立場でした。

選定の進め方としては、規制などで候補を絞り、重み付けスコアで 2〜3 個に減らし、既存データを使ったタイムボックスの POC で確認する（TCS）、移行と新規構築を別プロセスとして扱い、データ資産の把握と構想から始める（IBM）、ビジネスを巻き込んだ短いハッカソンで合意を作る（Tech Mahindra）、といったやり方が紹介されました。

事例は、メインフレーム DB2 から Azure SQL Hyperscale への移行（TCO 約 60% 削減）、AWS RDS・DynamoDB から Azure SQL Managed Instance・Azure Database for PostgreSQL への移行、Cosmos DB・Cosmos DB for Cassandra・Azure DB for PostgreSQL などを組み合わせたポリグロット構成（応答時間 8〜10 秒から 300 ミリ秒〜1 秒）の 3 件でした。いずれも「用途に合ったデータベースを使い分ける」という共通の結論につながっています。
