# THRSP1105 Redefine connectivity for frontier firms

## 1. はじめに

このセッションは、企業が AI を本番で使い始めるときに直面するネットワーク上の課題と、その対策としての「distributed AI hub」という考え方を、Equinix と Microsoft の 2 人の登壇者が説明する約 25 分のシアターセッションです。

前半では Equinix の登壇者が、AI 導入で多くの組織が抱える 4 つの問題と、それに対応するネットワーク層の新しいサービス（AI ゲートウェイ、ガードレール、エージェントの可観測性）を説明します。後半では Microsoft の登壇者が、Azure ExpressRoute と Equinix の提携内容を紹介します。最後に、Equinix 側が 3 つのユースケースを挙げています。

AI の利用が広がる中で、ネットワークとガバナンスをどう設計するかを考えている方に向いた内容です。

## 5. 発表内容の詳細

### 5.1 AI 導入で起きている 4 つの問題

Kal 氏によると、社内の各グループが AI を導入すると、次の 4 つの根本的な問題にぶつかります。

| 問題 | 説明 |
| ---- | ---- |
| Shadow AI | チームごとに、SaaS のモデル、オンプレミスのモデル、クラウド上のモデルなどに別々にアクセスし、ガードレールのポリシーを一貫して設定できていない。開発チームごとにやり方が違い、データが漏れる |
| アクセス制御 | 複数の CISO から聞いた話として、「人間は以前からデータにアクセスできたが、私たちは気づいていなかっただけ。エージェントは容赦なく動く」という。正しくアクセスを許可した 2 つのデータセットから、エージェントが 3 つ目のデータセットをつなぎ合わせて、機密性の高い洞察を導き出す可能性がある。エージェントの世界でのアクセス制御の設定に、多くの組織が苦労している |
| コストの増大 | 「フランスの首都は？」のような質問を、最も高価なモデルに送りたくない。単純なモデルで答えられる。10 人が同じ質問をするなら、すべてをモデルに送らずキャッシュを使うべき。オープンモデルとフロンティアモデルの両方が使えるようになり、価格と性能の差もある |
| ネットワークの不足 | AI を使う従業員が増え、アップロードするデータも増えるため、アップリンクの帯域が足りなくなる。多くの企業がネットワークを 400G に増強しつつある |

Kal 氏は、誰もが良い意図で AI を活用しようとしているが、これら 4 つの問題のためにガバナンスで苦労している、とまとめています。

### 5.2 Distributed AI hub

これらの問題への対応として、Kal 氏は「distributed AI hub」を説明します。OSI の「ネットワークスタック」の観点では、レイヤー 3 はルーティング、レイヤー 2 はデータリンクで、新たに**レイヤー 4 から 7 に新しいサービス**が登場している、という整理です。さらに、企業が成熟してオープンモデルを使いたくなると、クラウド、ネオクラウド、Azure Local へと広がります。自前のインフラを持ちつつ、ローカルと、クラウド上の資産の両方を Azure のコントロールプレーンで制御したい、という需要がある、と述べています。

distributed AI hub は、次のような新しいサービスで構成されます。

- **AI ゲートウェイ**：プロンプト単位で動く。ユーザーのプロンプトを、適切なモデルとプロバイダに、適切なコストとコンプライアンスで振り分ける。例として、Kal 氏のチームが香港でモデルを使おうとしたところ、そのモデルが香港では許可されていない（利用できない）ことがあり、デモのために急いで別のモデルに切り替えた経験を挙げ、コンプライアンスも重要になっていると述べています。
- **ガードレール**：モデルやプロバイダごとに個別にポリシーを設定することはできない、という考え方です。InfoSec チームが、会社のすべてのトラフィックが通る場所に、「交通整理役」としてガードレールを置く必要があります。
- **エージェントの可観測性**：エージェントが別のエージェントと話すたびに、何を言い、何をしているかを記録します。エージェントが意図せず、あるいは暴走して、してはいけないことをする可能性があるためです。

Equinix の従来の構成との関係として、Kal 氏は次のように説明しています。以前から、顧客はルーター、ファイアウォール、ロードバランサー、SD-WAN 機器などを Equinix に置いており、Equinix はこれを「performance hub」と呼んでいます。performance hub は 5,000 を超え、世界の上位の企業が展開しています。AI の世界では、そこに AI ゲートウェイ、AI ガードレール、可観測性を**追加**します。置き換えではなく、サービスを足す形です。形態は、物理アプライアンス、仮想ネットワーク機能（VNF）、クラウドサービスの 3 通りのいずれもあり得ます。

### 5.3 どこに配置するか：federated な配置

Kal 氏は、顧客から聞いている話として、distributed AI hub は**連携（federated）した形で**配置されるだろうと述べ、この点を重要だと強調しています。クラウド、オンプレミス、コロケーションのいずれか 1 つではなく、3 か所すべてに置かれるという意味です。

- エージェントやアプリがすべて Azure クラウドで動いているなら、Azure クラウドにゲートウェイ / ガードレールの hub を置く。
- データがエッジから来て、複数のプロバイダをまたぐなら、Equinix のようなクラウド中立（クラウド隣接）の場所に置くのが理にかなう。
- 一般には、1 つのコントロールプレーンが、分散した複数のインスタンス（Azure などのクラウド、Equinix、プライベートデータセンター）を管理し、すべてに一貫してポリシーを設定する。大手のセキュリティベンダーも、こうした機能を市場に出し始めている。

ガードレールも「どちらか」ではなく、多層のセキュリティモデルになります。Azure クラウド上で設定するガードレールのポリシーに加えて、InfoSec チームが、Palo Alto、Cisco、F5、Fortinet などの AI ガードレールサービスを、Equinix のようなクラウド中立の場所に展開します。すべてのトラフィックがこのガードレールを通り、ユーザーのクエリも、モデルからの結果も、スクラブ（検査・除去）されます。これは、クラウド側のモデルに設定するポリシーと併せて行います。

### 5.4 Microsoft と Equinix の提携（Sudha Mahajan 氏）

Sudha 氏は、Equinix との提携を、次の観点で説明しています。

1. **ロケーションの広さ**：Equinix は多くの拠点を持ち、Microsoft はほぼすべての拠点に存在する。
2. **ExpressRoute**：オンプレミスからクラウドへ、インターネットを通らずにプライベートに接続する仕組み。ExpressRoute の使い方の大半で Equinix を利用している。ExpressRoute Direct、Standard、Metro のいずれでも、Equinix を通じて、回復性のある接続方法を使える。
3. **データとモデルの近接性**：RAG のデータを持ち込み、Foundry のモデルにつなぐ場合、ExpressRoute を使って Equinix から接続できる。ユーザーのデータを、利用者がいる場所の近くに持ってくる。
4. **一貫したプラットフォーム**：Azure Local や Azure Arc を使う場合も、Equinix のホスティング環境から Azure クラウドに接続できる。
5. **分離のない選択肢**：ExpressRoute Metro を使って Equinix の複数のサイトに接続するなど、回復性を高められる。

エージェント型かどうかにかかわらず、接続性は重要で、Microsoft と Equinix は、利用者の需要がどこから来るか、新しいサイトをどこに作るかを一緒に見ている、と述べています。利用者がいる場所にエッジサイトや POP があるため、配置が強く、パフォーマンスの予測可能性も高まる、という説明です。

**ExpressRoute の規模**（Sudha 氏が挙げた数字）：

| 項目 | 内容 |
| ---- | ---- |
| ExpressRoute の顧客数 | 13,000 社以上 |
| Equinix の ExpressRoute ロケーション数 | 61 |
| Equinix 経由の対応地域 | 世界 40 の市場、24 か国 |
| Metro | すべてのロケーションで利用可能（"literally in every location"） |
| カバー範囲 | Equinix を通じて顧客ベースの 90% をカバー |

最大のモデルはプロバイダモデルで、Equinix は最大級のプロバイダの 1 つだそうです。新しいロケーションを追加するロードマップもあります。ExpressRoute はプライベート接続でインターネットを通らないため、レイテンシが予測でき、どのモデルの ExpressRoute でも SLA が予測可能だと説明しています。可観測性は、Equinix のサイト側でも Microsoft 側でも設定でき、問題が起きたときに情報が得られます。

### 5.5 3 つのユースケース（Kal 氏）

Kal 氏は、まとめとして 3 つのユースケースを挙げています。

1. **レイテンシと運用コスト**：Equinix のデータセンターは主要都市のほとんどにあり、エンドの（Tesla の車やスマートフォンなどの）端末から 10 ミリ秒以内にある。店舗、食料品店、空港、レストランなどに AI の GPU や推論処理を置きたくない顧客は、Equinix 上で Azure Local や Arc を使い、それを Azure クラウドとつなぐことができる。これにより、レイテンシの要件を満たしつつ、技術者を派遣せずに 1 か所から 10 店舗を支えられるため、OPEX を削減できる。
2. **主権（ソブリニティ）**：Equinix は現在 37 か国にある。それぞれの国で Azure Local などを使って推論スタックを展開し、データレジデンシーを守れる。さらに Equinix の fabric の geofencing 機能で、データがその国から出ないようにできる。
3. **トークノミクス**：多くの異なるモデルを試したい場合、Azure が承認したオープンモデルを、Equinix 上のローカルな Azure スタックで実行できる。データが生成される場所でオープンモデルをローカルに動かし、より高度なモデルは Azure クラウドで動かす、という選択ができる。

## 7. 注意点・発表者の気付き

- 配置は「クラウドか、オンプレミスか」ではなく、複数の場所に分散し、1 つのコントロールプレーンで一貫したポリシーを設定する、という考え方が強調されています。
- ガードレールも、クラウド側のポリシーと、クラウド中立の場所のガードレールサービスを重ねる多層のモデルです。
- Kal 氏自身の経験として、利用しようとしたモデルが、特定の地域（香港）では利用できなかった例が挙げられています。モデルの提供地域やコンプライアンスを、事前に確認する必要がある、という示唆です（補足）。
- Sudha 氏は、ExpressRoute は新しいロケーションを追加していく予定だと述べていますが、具体的な場所や時期は、発表では示されていません。

## 8. 利用者にとっての利点

発表で語られた利点は、次のとおりです。

| 利点 | 説明 |
| ---- | ---- |
| 一貫したガバナンス | 分散した AI hub を 1 つのコントロールプレーンで管理し、ポリシーを一貫して設定できる |
| コスト | コストの増大への対策として、簡単な質問には安価なモデルを使う、同じ質問にはキャッシュを使うという考え方が示された。店舗向けのユースケースでは、技術者の派遣を減らして OPEX を削減できると説明された |
| 予測可能なネットワーク | ExpressRoute のプライベート接続で、レイテンシが予測でき、SLA も予測可能 |
| データ主権 | 各国での推論の展開と、geofencing により、データをその国の外に出さない |
| モデルの選択肢 | ローカルでオープンモデル、Azure クラウドで高度なモデルを使い分けられる |

## 9. まとめ

AI の本番利用が広がると、Shadow AI、エージェント時代のアクセス制御、コストの増大、ネットワーク帯域の不足という 4 つの問題が出てきます。Equinix の Kal 氏は、その対策として、AI ゲートウェイ、ガードレール、エージェントの可観測性を、クラウド、コロケーション、プライベートデータセンターに分散して置く distributed AI hub を示しました。

Microsoft の Sudha 氏は、ExpressRoute と Equinix の組み合わせで、プライベートで予測可能な接続を、61 のロケーション、40 の市場で提供していると説明しました。
