# BRK355 Build like a startup. Deploy like an enterprise.

## 1. はじめに

このセッションは、Microsoft Fabric 上でアプリケーションを作る Rayfin と Fabric apps を紹介する 45 分の発表です。コーディングエージェントにアプリのバックエンドまで作らせつつ、企業のガバナンスのルールを守らせるにはどうするか、という課題に対する答えとして、Rayfin が示されます。

## 5. 発表内容の詳細

### 5.1 Rayfin の概要

Sachin 氏は、Rayfin の仕組みを次のように説明しています。

* バックエンドのすべてが、コードの**プリミティブ**として定義されます。そのため、アプリケーションのインフラをローカルで完全に立ち上げられ、素早く反復できます。
* コードを変えずに Fabric へデプロイすると、必要に応じてデータベースや Lake を立ち上げ、または semantic model に接続します。これらは、すべて組織のガバナンスのルールとポリシーに従って行われます。
* アプリケーションは「もう 1 つの Fabric artifact」であるため、lineage、共有、データに適用されたガバナンスルールを、自動的に引き継ぎます。

Ben 氏は後半で、Rayfin の SDK と CLI でアプリを定義し、デプロイすると Fabric の artifact として着地すると補足しています。

### 5.2 デモ 1：コストのシナリオプランナーと、AI による要約

Ben 氏が Billy を演じ、「コストが急増して利益が大きく落ちている」というシナリオで、上司から新しい商品の考案を任された、という設定です。Billy はデータに詳しい人物で、通常は分析担当者やエンジニアにダッシュボードを依頼し、数日から数か月待ちます。Ben 氏は、Microsoft でもデータ量とレポートの依頼が増えて、分析担当者が追いつけない状況が起きていると述べています。

Billy は **GitHub Copilot app** の中で Rayfin を使い、自然言語でほしい分析を伝えます。詳細は 6 章に書きます。

* 作成したのは、Caldova Pets の業務 semantic model に基づく「コスト削減プランナー」です。
* 完成した画面では、semantic model に接続され、コストの各項目を調整して、会社の利益への影響を確認できます。梱包や、特にタンパク質（protein）のコストを少し下げると、利益に大きな影響があることが分かる、という例でした。
* 次に、アプリに「知能」を加え、洞察を要約して上司に送れるようにします。Foundry のモデルに接続し、コスト削減のサマリーのメールを生成して、上司に送ります。

### 5.3 裏側の仕組み（Sachin 氏）

デモ 1 の後、Sachin 氏が仕組みを説明しています。

**semantic model へのコネクタ**

* Rayfin は、データに接続するためにコネクタを立ち上げ、適切な認証を配線します。
* 例のコネクタは semantic model タイプで、workspace ID と接続するアイテムを設定します。
* 認証の方式（この例では **delegated**）と、有効にする操作（この例では**クエリの実行**のみ）も宣言します。
* クライアント側では、semantic model に対して直接 **DAX クエリ**が作られていると説明しています。
* アプリケーション側で、認証用のアプリケーション（聞き取りでは "enter application"。Entra アプリケーションを指す可能性がありますが、音声認識の都合で確定できません）を用意して配線する必要はない、と説明しています。Fabric の item なので、ルールを継承し、semantic model に適用されたルールも自動的に尊重されます。

**functions と Foundry モデル**

* すべてを Rayfin の中に立ち上げる必要はなく、外部に接続できます。例では、Fabric 上にないモデルである Foundry のモデルを呼び出す function を作っています。
* モデルがデータにアクセスするための**ツール**にも、適切なコンテキストと認証情報が必要です。Rayfin では、モデルに接続する function と、Rayfin アプリのデータにアクセスするツールの両方を定義でき、Foundry のモデルはそのツールを使います。そのため、データに設定された認証・セキュリティポリシーが引き続き尊重されます。
* Rayfin の YAML で function service を有効にし、app auth principal の種類を設定します（delegated にもできますが、この例では application）。
* user data function が定義され、適切な認証コンテキストが自動で注入されます。そこに必要なコードを書けます。Fabric にデプロイすると **user data functions** として立ち上がり、**サーバーレスでスケール**します。

### 5.4 デモ 2：Kanban ボード、画像添付、カスタムロール

Billy は、上司から返信を受け取ります（洞察を気に入り、新商品のブレインストーミングを求める内容）。スケートボードで散歩中に、犬がコオロギ（cricket）を食べたことから、コオロギをタンパク源にしたドッグフードを思い付き、「高タンパク、手頃、犬に良い」という商品アイデアになります。

デモ 1 は既存の semantic model に接続する、従来型の分析ダッシュボードでした。今度は、チームからデータを取り込む**トランザクション型**のアプリです。

1. 「コオロギ・プロテインのドッグフードを立ち上げるための Kanban ボードを追加して」と依頼します（ライブでは動作せず、完成版に切り替えています）。
2. 完成版では、バックログ、次の予定、計画・実行といったフェーズ間で、項目を移動できます。
3. Billy がスケッチや画像を添付できるように、「画像を添付して」と依頼します。**OneLake でのストレージが Rayfin の新機能として加わった**ためです。完了すると、項目に新しい「attach image」ボタンが出て、画像を添付できました。
4. 上司は、「進行中」から「完了」への移動を Billy にさせたくないため、特定のロールを持つ人だけが項目を移動できる制限を求めます。新機能の **custom roles** で、上司と CFO だけが項目を承認できるように依頼します。custom claim が作られます。
5. Billy が「レビュー中」から「完了」に項目を動かそうとすると、そのロール（権限）がないというエラーが出ました。

### 5.5 裏側の仕組み：データベース、BLOB、custom claims（Sachin 氏）

アプリには、データベースとストレージの 2 つのインフラが必要でした。

* **データベース**：作業ボードは Rayfin ではクラスとして表れます。`entity` のような**デコレーター**を付けると、アプリケーションが公開されたときに、実際のデータベースとテーブルに変換されます。カスタムの RLS ロジックは、**ポリシーのデコレーター**として宣言し、ユーザーがテーブルやエンティティに何をできるかを指定します。
* **画像・BLOB**：BLOB 用のデコレーターを付けると、BLOB ストレージに置かれます。最大サイズや、競合時の動作などのオプションも指定できます。
* **custom claims**：Fabric には認証トークンに付くポリシーがありますが、アプリには独自のルールが必要なことがあります。例は、「この人は CEO、CFO、上司の 3 者のどれかか」という判定です。この function が、アプリが認証トークンを生成するときに評価され、クレームとして付与されます。アプリ内の各 function でこのクレームを検証できます。Fabric がサポートするよりも、さらに細かい制御ができると説明しています。

### 5.6 デモ 3：公開の投票アプリ（匿名アクセス）

Billy は新商品のブランド案を 3 つ考えました。**Bug Sur**、**Jump Start**、**Hot Dog** です。決められないため、会場に投票を募る公開の投票アプリを作ります。依頼すると、**anonymous data access**（匿名のデータアクセス。Rayfin の比較的新しい機能で、公開アプリのシナリオを可能にする）を使うアプリが作られます。これもライブでは時間がかかるため、完成版に切り替えています。画面には QR コードが表示され、スマートフォンで読み取るとこの Fabric アプリにアクセスできました。

### 5.7 IT 管理者から見たガバナンス（Ben 氏）

Ben 氏は、3 人目の架空の人物として、Caldova Pets の IT 責任者 **Anita Cool** を紹介しています。まず、Billy は非エンジニアなのに、分析アプリ、トランザクションアプリを、エージェントだけで作り、分析担当者やエンジニアに頼み込まずにセルフサービスできるようになった、とまとめています。

Anita にとっての価値は、Fabric の artifact としてのガバナンス機能です。

* すべてのアプリは、既定で **private auth**。ログインした認証トークンは、**行レベルセキュリティ（RLS）を尊重**し、アクセスすべきデータにのみアクセスできます。
* lineage ビュー、artifact レベルの共有、単一の課金モデルなど、Fabric artifact の機能が使えます。
* 管理者のコントロールを拡充中です。例として、匿名データアクセスのオン・オフ、組み込みの content security policy、アプリをブロックできる管理センターがあります。

デモでは、Anita にメールが届き、Billy が不在の間に、マーケティング用アプリで個人の連絡先を共有してしまったとの連絡が入ります（発言では電話番号とも、メールとも述べられています）。Anita は、**OneLake catalog の governance hub** でそのアプリを選んでブロックし、理由を入力します。ブロックされると、アプリの所有者だけがアクセスでき、他のユーザーにはブロック画面が表示されます。

### 5.8 Craneware Group の事例（Mark Sentell 氏）

Mark 氏は、Craneware Group は「4 つに 1 つの病院が知っており、信頼している」会社で、病院が医療ビジネスを運営するためのアプリケーションを提供していると紹介しています。

**従来の課題：「gates and waits」**

* 顧客の課題を、ドメインに詳しいビジネスアナリストが聞いて持ち帰る。
* エンジニアのスプリントに空きが出るのを待ち、作って、デプロイして、アナリストに戻し、2 週間後の顧客との会議で見せる。
* 顧客側や社内のチームを待つうちに、プロトタイプが顧客に届く頃には、顧客が次の課題に移っていることもあった。
* さらに、プロトタイプのあとに本番用に作り直す必要があり、アーキテクチャの承認、テスト、デプロイ、ドキュメント、マーケティングと、別の gates and waits がある。

それでも成果物は機能し、顧客の課題を解決してきた、と述べています。

**Rayfin の導入**

* Rayfin を見つけたのは、公開されて間もない頃で、取り組みを始めたのは数週間前、専門家とエンジニアを集めた場は「2 か月ほど前」と述べています。ドメインの専門家（subject matter expert）とエンジニアの専門性を、両方とも指示（instructions）として符号化（encode）し、Rayfin SDK に渡せる、というのが発見でした。
* 両グループを 1 つの部屋に集め、初めて Rayfin を見せた。エンジニアは、「アプリは React ではなく Angular で作る」「アプリの色やスタイルの方針を反映する」といった懸念を入力した。また、自社アプリのスクリーンショットを Rayfin に渡すと、UI を再現できた。
* 専門家は「service line（サービスライン）ダッシュボード」を作りたいと依頼した。Mark 氏とエンジニアは service line が何か知らなかったが、これは医療の用語で、病院内の特定の種類のケアを指す。専門家は、「サイドバーに新しいアプリを追加したい。名前は service lines で、病院内の特定の種類のケアを表し、収益性を分析し、改善の提案がほしい」といった内容を入力した。
* 出来上がった画面は、整えていないとのことですが、整形外科（orthopedics）を分析し、件数、傾向、財務結果、粗利益を示していた。Mark 氏は、非エンジニアに Rayfin を紹介してから **45 分ほど**でこれが出てきたことが驚きだったと述べています。
* ビジネスアナリストが上司に見せに行った後、エンジニアはコードを開き、**懸念事項が反映されているか**を確認しました。Angular で書かれているか、システムの他の部分に接続しているか、アプリ内の安全な iframe に埋め込めるかなどです。確認の結果、反映されていました。両者とも、上司への報告から戻り、満足しました。

**ヘルスケアのガバナンス**

* 医療情報の保護は、誤れば事業が成り立たない重要事項です。RLS に加えて、特有の要件があります。
* 例えば、保護対象の健康情報（public or private health information）を開示する場合は、権限と理由の証跡を**監査**できる必要があります。画面では、一部のデータが非表示になり（保護すべきと既に認識されている）、自分に権限がある場合に表示する上書き（override）が用意されていました。データは架空のものだとのことです。
* Mark 氏は「それでも自分たちで確認する」とし、Rayfin に面倒な作業を任せ、確認することで信頼を築いている、と述べています。

**Mark 氏自身の試用**

発表の約 30 分前に、Mark 氏は Rayfin に、アプリ内で起きていることをブックマークで強調しながら再生できる体験（CFO への見せ方のようなストーリー）を依頼しました。約 1 分半で、画面 1 に注釈付きで移動し、画面 2 に進む「Ignite story」ができたといいます。ライブ画面でストーリーを編集し、ブックマークを追加し、ハイライトを加えて保存、再生して見せました（画面の細部は音声からは確認できません）。

**学んだこと**

1. 専門家がビルダーになれるため、エンジニアリングチームの規模が**倍になったよう**だった。バックログは、医療を良くするためにまだ着手できていない機会であり、待たされるお客様を減らしたい。
2. ビジネス側が、プロトタイプを素早く、ほぼ同じミーティングの中で顧客に見せられる。成果物が本番に近いため、プロトタイプと本番で別々に gates and waits を通る必要がない。
3. 人が好きな仕事を続けられる。エンジニアは Rayfin に、ビジネス側が作っている間に、最適化の機会のリストを作るよう指示しており、例えば新しい計算は semantic model の measure として上流で扱うほうがよい場合を、Rayfin が教えてくれた。エンジニアは、デバッグやドキュメント作成のような退屈な問題ではなく、楽しい種類のエンジニアリングの問題を解けるようになった。

## 6. デモ・手順

このセッションでは、Ben 氏が **GitHub Copilot app** 内の Rayfin を使い、ライブでの依頼（プロンプト）と、事前に用意した完成版を切り替えながらデモを行いました。画面の詳細（ボタン名やレイアウト）は音声から確認できないため、語られた範囲のみを書きます。

### 6.1 コスト削減プランナーの作成

1. 「Caldova Pets のビジネス semantic model を使って、コスト削減のプランナーを作って」と依頼します。
2. エージェントは Rayfin SDK を導入済みのため、アプリの足場を作る方法を把握しています。`raven.yaml`（聞き取りの綴り。音声認識の都合で確定できません）というファイルをインストールします。ここにアプリの設定が定義されます。
3. アプリをどこにデプロイするかを尋ねてくるので、モデルと同じ workspace を選びます。
4. 続いて、アプリの動作に必要な Web ページ類を作ります。時間がかかるため、前日に実行した完成版に切り替えます。
5. 完成したシナリオプランナーは、semantic model に接続され、コスト項目を調整して、利益への影響を確認できます。梱包やタンパク質の値を変えて試し、タンパク質の影響が特に大きいことを示しました。

## 7. 注意点・発表者の気付き

* **デモの一部は完成版**：Ben 氏は、ライブでは時間がかかる、または動作しないため、Kanban アプリや投票アプリなどで完成版に切り替えています。
* **人のレビューは残る**：Mark 氏は、Rayfin の生成物を、それでも自分たちで確認すると明言しています。エンジニアは、コードを開いて、自分たちの懸念が反映されているかを確認しました。
* **ヘルスケアでは情報保護が最優先**：RLS だけでなく、保護対象の健康情報の開示に監査（権限と理由の証跡）が必要で、誤れば事業が成り立たないとのことです。
* **管理者のコントロールは拡充中**：Ben 氏は、管理者向けのコントロールを増やし続けていると述べています。
* **匿名アクセスは管理者が制御**：公開アプリを可能にする匿名データアクセスは、管理者がオン・オフを決められます。
* **ブロックの動作**：ブロックされたアプリは、所有者以外にはブロック画面が表示されます。

## 8. 利用者にとっての利点

* **セルフサービス**：Billy の例のように、非エンジニアが、分析アプリとトランザクションアプリを、エージェントだけで作れます。
* **規模**：Build 以降、Rayfin と Fabric apps で 10 万を超えるアプリが作られています。
* **ガバナンスの継承**：Fabric の artifact として、lineage、共有、データのガバナンスルール、RLS、単一の課金モデルが使えます。
* **ローカルでの開発から Fabric へ**：バックエンドがコードのプリミティブとして定義されるため、ローカルで反復でき、コードを変えずに Fabric にデプロイできます。
* **Craneware Group の成果**（Mark 氏の発言による）：
  * 専門家がビルダーになったことで、エンジニアリングチームが倍になったように感じられる。
  * 非エンジニアに Rayfin を紹介してから 45 分ほどで、service line ダッシュボードが得られた。
  * プロトタイプが本番に近いため、プロトタイプと本番で別々に待ちを繰り返す必要がなくなる。
  * エンジニアは、デバッグやドキュメントなどの退屈な作業から、楽しい種類のエンジニアリングに時間を使える。

  発表では、これらを裏付ける定量的な指標（時間短縮の割合など）は示されていません。

## 9. まとめ

Rayfin は、コーディングエージェントにアプリのバックエンドを作らせながら、企業のガバナンスを守らせるための building blocks です。バックエンドをコードのプリミティブとして定義するため、ローカルで反復でき、Fabric にデプロイすると、データベース、Lake、semantic model への接続が、組織のルールに従って用意されます。アプリは Fabric の artifact として、lineage、共有、RLS、管理者によるブロックなどを引き継ぎます。

デモでは、非エンジニアの Billy が、分析ダッシュボード、Kanban アプリ、公開の投票アプリを自然言語で作りました。Craneware Group の Mark 氏は、ドメインの専門家とエンジニアの両方の懸念を Rayfin に符号化し、gates and waits を減らせたと報告しています。Rayfin と Fabric apps は発表当日に一般提供となり、GitHub Copilot app、Power BI Desktop for apps、Replit、オープンソースの Fabricator から利用できます。
