# BRK370 Build integrated AI apps with Azure HorizonDB

## 1. はじめに

このセッションは、Azure HorizonDB（発表では「HorizonDB の Postgres」と呼ばれています）の上で AI アプリケーションを組み立てる方法を、4 つのライブデモで順に見せていく内容です。題材は、メーカー（manufacturer）の例で「どのサプライヤーを使うべきか」という問いです。新しいサプライヤー情報が入るたびに、AI パイプラインで非構造化テキストを取り込み、検索とナレッジグラフで絞り込み、最後に**同じ質問をしても答えが正しく変わる**ところまでを 1 つのデータベース内で示します。

後半では、Pediatric Associates Family of Companies の Dylan Addington 氏が、HorizonDB を「業務スキルのカタログ」として使った事例を、録画デモ付きで紹介します。

前半のデモの流れを追いたい開発者、HorizonDB の AI 関連機能（AI model management、AI pipelines、ハイブリッド検索、ナレッジグラフ）の位置づけを知りたい方に向けた内容です。

> 注意：このトランスクリプトは「4 つのステップで解決します」という場面から始まっています。冒頭の問題設定（サプライヤー選定の質問が最初にどう誤った答えを返すのか）の説明は、録音に含まれていません。以降の記述は、録音に残っている範囲だけに基づいています。

## 5. 発表内容の詳細

### 5.1 全体構成：4 ステップと設計方針

Jonathon 氏は、問題を 4 ステップで解くと説明しています。

| ステップ | 内容 |
| ---- | ---- |
| 1 | 新しいサプライヤープロファイルごとに、AI-ready なコンテキストを作る |
| 2 | HorizonDB の検索機能で、適切なサプライヤーを見つける |
| 3 | 抽出したエンティティ間の関係を、コネクションとグラフで表に出す |
| 4 | 新しい証拠が入ったときに同じ質問をして、正しい答えが得られるよう、エンドツーエンドの AI パイプラインにまとめる |

実装方法には 2 つの選択肢があると説明しています。1 つは、アプリが何か要求するたびにモデルを呼ぶ方法です。ただし、これはクリティカルパスにモデル呼び出しが入り、遅延が増えます。もう 1 つは、AI パイプラインでバックグラウンド（非同期）に前処理を行い、アプリはリアルタイムでは、準備済みのデータを使う方法です。こちらは遅延が減り、応答が速くなります。このセッションでは後者を採ります。

### 5.2 AI model management（public preview へ）

モデルをデータベースに取り込む機能が **AI model management** です。Jonathon 氏は、Ignite でこの機能を limited public preview から **public preview** に移行すると発表しています。

- スイッチ 1 つで、chat completion や embedding などのモデル（トランスクリプトでは「encoder models」にも触れています）を、アプリや SQL から使えるようにできます。
- エンドポイントの登録やキー管理は不要です。
- すでに Foundry にあるモデルを登録したい場合も可能で、並行して使えます。

### 5.3 AI pipelines

AI pipeline について、次の特徴が説明されています。

- パイプラインの定義は **1 つの SQL 文**で作ります。定義はデータベース内に置かれ、データベース内で動きます。
- 各ステップは durable node（耐久性のあるノード）です。例えばモデル呼び出しが失敗しても、リトライして成功できます。これは **PG Durable** という別の拡張機能の上に作られており、チェックポイントなどの耐久性の仕組みがこの機能を支えています。
- オンデマンドで実行できるほか、変更時のようなトリガー的な形でも実行できます。

### 5.4 検索：ベクトル検索、全文検索、ハイブリッド検索、再ランク

**ベクトル検索**は、意味で検索します。共通する単語が 1 つもなくても、同じ意味のものを見つけられるのが強みだと説明しています。

**全文検索**は、PG Text Search 拡張（Postgres と HorizonDB で多くの投資をしていると説明）が提供する **BM25** の全文検索です。証明書の名前のようなキーワードを、正確に一致させる用途に向きます。

**ハイブリッド検索**は、両方を併用して結果をマージしたい場面のための機能です。関数呼び出し 1 回で、全文検索（BM25）とベクトル検索という 2 つの検索結果を 1 つの結果セットに融合します。スコアの性質が異なる 2 つの検索結果が、1 つにまとまります。スライドの例では、Supplier F が両方のデータセットで見つかったため、3 位に上がっています。

さらに **cross-encoder** を加えて再ランク（re-ranking）できます。スライドの例では、再ランクにより A と B の順位が入れ替わり、精度がより高くなっています。

### 5.5 DiskANN の改善

ベクトル検索に関して、HorizonDB の DiskANN に多くの改善を入れたと説明しています。

- **spherical quantization** により、ベクトルを RAM 上で強く圧縮しつつ、スループットも高く保てます。
- **HNSW に比べてスループットは 1.7 倍**、**レイテンシは半分**になります。
- 詳細は、公開したばかりのブログに書かれているとのことです（リンクは最後のスライドで紹介）。

### 5.6 ナレッジグラフ（Apache AGE）

ナレッジグラフは、取り込んだデータをつなげ、それらの関係を表に出すために使います。前の検索のデモでは Supplier F と Supplier A が候補でしたが、さらに踏み込めば、次の関係から判断できます。

- サプライヤーはプラント（plant）を持つ
- プラントは認証（certification）を持つ
- 検査結果（finding）がプラントで観測される

Supplier F のプラントには finding があるため、候補から外すべきです。Supplier A にはそれがなく、おそらく認証されているので、候補に残すべきだという考え方です。

HorizonDB には、グラフを作るための新しいプリミティブ群があり、これを **knowledge graphs for AI pipelines** と呼んでいます。これまでグラフを構築するときに必要だった面倒な作業を減らし、より簡単に、速く、少ないコードで作れるようにするものです。

また、**Apache AGE 拡張のパフォーマンスも HorizonDB で大幅に改善**したと説明しています。グラフの構築と更新に使う重要な操作である **merge** で **190 倍**の性能向上、ピークメモリは **83% 削減**です。

### 5.7 Dylan Addington 氏の事例：Pediatric Associates

Dylan 氏は、Pediatric Associates Family of Companies の Enterprise Architect として、「The Last Interface We Should Have to Teach」を発表しました。

**問題提起。** あるクリニックで 10 年働いている、優秀な職員を想像してほしいと語りかけます。家族の登録、保険、スケジュール、紹介状の扱いに通じています。その電子カルテ（EMR）を別のものに替えると、10 年の経験も知識もそのままなのに、ボタンの配置が変わっただけで彼女は初心者になります。私たちは、人にソフトウェアの操作を教え、ソフトウェアを替え、また教え直します。新入社員、新しいベンダー、新バージョン、新しい画面、新しいワークフローで繰り返すこの状態が、問題として認識されないほど当たり前になっている、という指摘です。そこで Dylan 氏は「なぜ、数千人の従業員にソフトウェアの内部の仕組みを覚えさせるのか。優秀なエンジニアがソフトウェアに仕事のやり方を教えればよいのではないか」と考えるようになったと言います。

**既存の投資。** 同社は、相互運用性（interoperability）の基盤に年単位で投資してきました。

- 数百万件のイベントをリアルタイムで届ける event fabric
- 臨床・運用データを保持する FHIR データストア（Dylan 氏が Jonathon 氏と出会ったきっかけでもあると話しています）
- 一元化した API
- スケジューリングのアーキテクチャ（オーケストレーションにあたると説明）

それでも、どのアプリを開くのか、どの画面に移るのか、何回クリックしてフォームを埋めるのかという負担は、従業員側に残ります。「従業員が仕事を言葉で説明するだけでよければ」という発想です。

**目指す方向。** 新しいスケジューリングアプリやスタッフ向けの新しい画面を作るのではなく、従業員の意図が出発点で、その下にあるアプリは実装の詳細になる企業を目指す、という方向です。AI には少なくとも次の 5 つが必要だと整理しています。

1. どんな操作（オペレーション）が存在するか
2. どれが適切か
3. 必要な情報は何か
4. 何ステップかかるか
5. 承認されているか（ガバナンス）

そこで使うのが**スキル**です。プロンプトを投げて祈るのではなく、スキルとは「契約、検証、依存関係、認可、観測を備えた、実装済みのビジネス操作」だと定義しています。スキルは**アトミック**に作り、大きなワークフローを 1 つのスキルに詰め込みません。例として「患者を登録する」「患者の連絡先を管理する」「予約を取る」を挙げ、それぞれ単独でも、組み合わせても動くとしています。

**HorizonDB の役割。** 現在のスキルライブラリは約 70 個ですが、数百、数千に増えたときに、エージェントがどれが使えるかを知り、絞り込む必要があります。ここで HorizonDB を使います。データベースは従来「何が存在し、何が真か」を教えるものですが、それが「企業が実行できる機能のすべて」の理解も保持できないか、という発想です。使っている機能は次のとおりです。

| 機能 | 役割（Dylan 氏の説明） |
| ---- | ---- |
| DiskANN | ユーザーのプロンプトやクエリを分解し、意味でスキルを見つける |
| BM25 | 正確な用語で、それを補強する |
| Apache AGE | スキル同士の依存関係をマッピングする（Dylan 氏のお気に入り） |

### 5.8 責任の分担と Dylan 氏からの問いかけ

デモの後、Dylan 氏は役割分担を次のように整理しています。

| 担当 | 役割 |
| ---- | ---- |
| モデル（Foundry） | 言語を解釈する |
| HorizonDB | 発見可能なスキルのカタログを保持する |
| 実行ランタイム | 境界と認可を強制する |
| 人間 | 重大な判断の権限を持ち続ける |

シンプルなインターフェースにできたのは、その下がシンプルではない（作り込まれている）からだと述べています。将来像の例として、provider（医療提供者）が「最初の患者の準備をして」と言う場面を挙げています。必要な処理は、取得する、必要な作業を特定する、スキルの範囲で許可された操作を実行する、人の判断が必要なものだけを提示する、の 4 つです。

そのうえで、「画面を作り、バックエンドを書き、システムをつなぎ、テストし、デプロイし、教育する、というのが既定の流れだが、これに異を唱えたい」と述べ、人間がバックエンドのペイロードを組み立てるための画面をまた作るのをやめ、同じ工数を、スキル、API、データベースなどの**よく設計されたビジネス機能**に投資するよう呼びかけています。

冒頭の 10 年選手の職員に戻ると、彼女は今も「患者を登録して、保険を確認して、予約を探して」と言うだけです。インターフェースが変わっても変わらなかった「持続的なもの」はそのままで、ベンダー固有の実装はバックエンドのエンジニア側に移ります。EMR が変わっても、従業員を再教育する必要はありません。「どのアプリを開くか」ではなく「何を終わらせたいか」を聞く、というのが最後のメッセージで、Dylan 氏が一番作りたいのは、新しいアプリではなく、**アプリを理解しなくても仕事ができる企業**だと語っています。小児医療の現場では、電子カルテの操作が好きで出勤する人も、ソフトウェアの設計に惹かれて子どもを連れてくる人もいない、というのがその理由づけです。

## 6. デモ・手順

このセッションにはデモがあります。Jonathon 氏による 4 つのデモと、Dylan 氏の録画デモです。画面の細部は音声からは確認できないため、語られた範囲だけを順に書きます。

### 6.1 デモ 1：AI pipeline の作成と実行（VS Code）

1. VS Code で、事前に（画面外で）レコードを入れた 2 つのテーブルを見せる。製造業のサプライヤー例を模したもの。
2. 1 つ目のテーブルには、読み込み済みの manufacturer profile が入っている。続けて、未処理の生のコンテンツと、まだ何も入っていない AI context を見せ、これから埋めていくと説明している。
3. Azure AI 拡張にある関数を 1 回呼んで、AI pipeline を作成する。パイプラインには、非構造化テキストからエンティティを抽出する extraction ステップと、ベクトル埋め込みを生成する embed ステップがあり、最後のテーブルに保存する。
4. パイプラインを 1 行のコードで実行する。
5. 実行中に、VS Code の Postgres 拡張（Marketplace で入手可能）に組み込まれた、パイプラインの可視化機能に切り替える（この拡張は、Postgres 開発の最良の場にすべく投資している、と説明されています）。パイプラインが見つかり実行中であること、先ほど定義した内容が視覚的に表示されることを確認する。
6. 実行が完了したことを、結果を調べるクエリで確認する。結果は「Completed, 20 processed」。
7. 最終状態を見る。レガシーシステムから来た非構造化テキストが処理され、次のステップで使える findings とメタデータが JSONB 列に入っている。

### 6.2 デモ 2：ベクトル検索、全文検索、ハイブリッド検索、再ランク

1. 検索コマンドを実行して、ベクトル検索の結果を得る。
2. 同じ検索を全文検索で実行する。結果は少し違い、ベクトル検索で上位だった F が、全文検索では下位になる。
3. ハイブリッド検索を 1 回の呼び出しで実行する。F が 3 位に上がり、結果が融合されて 1 つのスコアを持つ結果セットになる。ここでは **reciprocal rank fusion（RRF）** が使われ、性質の違うスコアを統合する一般的なアルゴリズムだと説明している。
4. 呼び出しに re-rank を true にして実行する。cross-encoder モデルが呼ばれ、結果が少し改善される。

### 6.3 デモ 3：ナレッジグラフの構築

1. Apache AGE を使う際に必要なので、search path を設定する。
2. グラフの構成を説明する。supplier が plant を運営し、plant が certification を持ち、finding が plant で観測される。このグラフ定義は画面外で作成済みで、新しい「グラフを作るためのプリミティブ」を使っている。
3. 「AI.normalize entity」と呼ばれる関数を実行する（聞こえた綴りのまま記載しています）。Plant 2 が 3 通りの表記で入っていたものが、小文字化と空白のトリミングで同じ形に正規化される。重複排除や正規化は顧客がいつも悩む点だ、と説明している。
4. グラフの構造を使った 2 つ目の `create pipeline` を実行し、定義を作る。このパイプラインでグラフを読み込む。
5. パイプラインを実行する。ステータスを確認すると、すでに完了している。
6. VS Code 拡張機能に組み込まれたグラフ可視化で、グラフを見る。何もない状態から、非構造化データだったものが入ったグラフができている。
7. Supplier A と Supplier F について照会する。Supplier A は Plant 2 を持ち、Plant 2 は GMP 認証を取得している。Supplier F は、プラントにインシデントが関連付けられている。サプライヤーの適格性を判断するための、ビジネス上のインテリジェンスだと説明している。

### 6.4 デモ 4：エンドツーエンドのパイプライン

1. ハイブリッド検索を実行する。現時点では Supplier B と A が適格で、これが正しいデータである。
2. レガシーシステムから新しいプロファイルが届いた状況をシミュレートする。ソースデータには version 2 のプロファイルがある。
3. 出力先の AI context には、まだ読み込まれていないことを確認する（パイプラインを再実行していないため）。
4. 新しいパイプラインは作らず、前に作ったものをもう一度実行する。実運用では on-change イベントを捕捉して起動するのが望ましいが、ここでは例示のため手動で実行している。
5. supplier enrichment（1 つ目のパイプライン）が、非構造化データから JSONB を生成する。完了を確認する。
6. 新しい事実を確認する。JSONB には、インシデント番号付きの open finding がある。
7. 2 つ目のパイプライン（supplier graph）をもう一度実行し、完了を確認する。
8. グラフを見ると、Supplier A の Plant 2 にインシデント番号がある。
9. 最初の質問「どのサプライヤーを使うべきか」を再度投げる。Supplier A が外れ、Supplier B だけが残る。

Jonathon 氏は、実行前は Supplier A と B が適格だったのに、実行後は B だけになった理由を、抽出、処理、グラフ作成、グラフ更新を網羅するエンドツーエンドのパイプラインがあったから、とまとめています。

### 6.5 Dylan 氏の録画デモ（スキルカタログ）

ライブでのデモを予定していたものの、「マーフィーの法則」で実行できず、録画版を見せました。実在するのは、データベース、スキルカタログ、アプリケーション自体です。デモ用に合成したのは、裏で支えるモックの API で、実際の API でもテスト済みだと説明しています。

1. あらかじめ用意されたクエリのリストから、最初のクエリを選ぶ。内容は「患者を登録し、保険を登録し、保証人（guarantor）を追加し、特定の医師に予約を入れる」。
2. バックグラウンドで HorizonDB がこれらの要求をまとめて解決する。スキルカタログを検索し、各スキル内の指示を読み、計画を作る。
3. 一時停止して、計画が画面に出ることを説明する。医療では AI に好き放題させず、人間の判断（human in the loop）を入れるのが重要なので、作った計画を提示する。この計画でよいので、進める。
4. 各スキルをロードして API を呼び、1 つずつ順に実行する。最後に 4 ステップ全部が完了した。
5. 新しいスキルの追加を見せるため、「peelback」機能を開き、HorizonDB の裏側で何が起きているかを見る。目標は、再デプロイなしでスキルを追加できること。
6. 作り込み済みのスキルを呼ぶが、このスキルはまだライブラリに追加されていないため、「失敗」が正しい結果になる（スキルが見つからない）。
7. 「publish」ボタンでスキルを公開する。スキルカタログのプレビューには、このスキルを実行するために必要な依存関係のグラフが表示される。
8. 同じ依頼をもう一度エージェントに頼む。今度はスキルが見つかり、実行の準備に入る。
9. 問題が起きたときに取り下げられることも重要だとして、withdraw（撤回）ボタンを押す。同じプロンプトをもう一度試すと、エージェントは再び拒否する。

公開と撤回を素早くできることが、企業レベルで統制をかける方法だと説明しています。

## 7. 注意点・発表者の気付き

- アプリがリクエストのたびにモデルを呼ぶと、クリティカルパス上で遅延が増えます。エンリッチ処理はバックグラウンドのパイプラインに移す、というのがこのセッションの設計の前提です。
- Jonathon 氏のデモ 4 では、パイプラインの再実行は手動で行っています。実運用では on-change のイベントを捕捉して起動する想定だと説明しています。
- Jonathon 氏のグラフ定義は画面外で作成済みで、デモでは作成の過程は見せていません。
- Dylan 氏のデモは録画で、モックの API を使っています（実 API でもテスト済みと説明）。
- 医療の現場では、AI に自由に動かせるのではなく、計画を提示して人間が承認するステップを入れています。最終的な判断権限は人間に残る、という役割分担です。
- Dylan 氏の現在のスキルライブラリは約 70 個です。数百、数千に増えたときの絞り込みが課題で、ここを HorizonDB で解くという位置づけです。
- 発表では、AI model management の料金、リージョン、提供時期の詳細や、各機能の正式な提供状況（AI model management が public preview になる以外）には触れていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 1 つのデータベース（HorizonDB の Postgres）の中で、取り込み、検索、グラフ、パイプラインまでを完結できる。
- AI pipeline は 1 つの SQL 文で定義でき、データベース内で動く。durable なため、モデル呼び出しが失敗してもリトライできる。
- アプリは、準備済みのデータを使うため、モデルの遅延を待たずにリアルタイムで動作する。
- AI model management では、エンドポイントの登録やキー管理が不要で、Foundry のモデルも併用できる。
- ベクトル検索は HNSW 比で 1.7 倍のスループット、レイテンシは半分。
- Apache AGE の merge は 190 倍、ピークメモリは 83% 削減。
- Pediatric Associates の事例では、スキルを再デプロイなしで公開・撤回でき、EMR が変わっても従業員を再教育する必要がなくなるという狙いが語られています。

> 補足：Pediatric Associates の事例で語られているのは、目指す方向と録画デモの内容です。実運用での導入効果を示す数値は、発表では示されていません。

## 9. まとめ

Jonathon 氏のデモでは、サプライヤープロファイルの新バージョンが届くたびに、パイプラインを再実行するだけで、抽出、埋め込み、グラフ更新が進み、同じ質問への答えが「A と B」から「B のみ」に変わりました。AI pipelines、ハイブリッド検索（RRF と cross-encoder による再ランク）、Apache AGE によるナレッジグラフが、1 つのデータベースの中でつながっていることがポイントです。

Dylan 氏は、HorizonDB を使ったスキルカタログ（DiskANN と BM25 で探し、Apache AGE で依存関係を管理する）により、画面ではなく業務機能に投資する方向を示しました。人間の承認を挟み、スキルを公開・撤回で統制する、という設計です。
