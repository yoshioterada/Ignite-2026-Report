# THR1039 What 164 ISVs Reveal About Winning with Microsoft AI

## 1. はじめに

ソフトウェアを作っても、選ばれ、購入され、使い続けてもらえるとは限りません。導入、販売、運用など、製品の外側で顧客を支える人たちとの連携も必要です。

このセッションでは、ISV の調査結果を手がかりに、共同開発（Co-build）、共同マーケティング（Co-market）、共同営業（Co-sell）、共同サービス提供（Co-serve）の四つの協業を説明しています。**Marketplace への掲載は、売る理由や使い続ける仕組みの代わりにはならない**というのが中心的なメッセージです。

## 3. 何に関する発表か

ISV が顧客体験全体を提供するために、Microsoft、SI、MSP、リセラー、ディストリビューターとどう協業するかを扱います。

| 参加者 | 発表で説明された役割 |
|---|---|
| ISV | ソフトウェアや解決策を作る |
| SI | 顧客の業務やシステムへの統合を助ける |
| リセラー・ディストリビューター | 購入を支え、販売先を広げる |
| MSP | 運用を担い、利用継続を助ける |

複数社が関わるほど、「問題が起きた時、顧客体験に誰が責任を持つか」が曖昧になります。四つの協業の枠組みは、こうした役割と進め方を社内外で合わせるために紹介されています。

## 4. 発表者が伝えたいメッセージ

製品開発に集中し、選定、統合、定着、更新、保守を後回しにしないことが大切です。また、試行の回数を増やすこと自体が目的ではありません。繰り返せる商談と、測れる顧客成果へ変える必要があります。

その際、四つの協業を必ず順番に実施する必要はありません。共同開発の前に、共同マーケティングでメッセージを試し、設計に協力する顧客を見つける方法もあります。

最初から大きな体制を作るのではなく、一顧客、一つの切実な課題、一つの測定可能な成果から始めることを勧めています。

## 5. 発表内容の詳細

### 5.1 調査が示す課題を分けて考える

書き起こしで確認できる主な数字は次のとおりです。

| 回答 | 割合 |
|---|---|
| 自社開発や第三者のツールで AI 機能を構築している | 57% |
| AI の有効性を確かめるための資金支援をさらに求める | 36% |
| Marketplace への掲載が複雑だと感じる | 23% |
| さらにマーケティング支援を求める | 20% |
| Microsoft と共同営業したことがない | 51% |

登壇者は、掲載の難しさとマーケティング不足を別の問題として捉えました。前者は「買いやすくすること」、後者は「買う理由を作ること」です。掲載されただけで見込み顧客が集まるわけではありません。

### 5.2 共同開発（Co-build）：何のために一緒に作るか

AI 機能を追加するときは、顧客が対価を払うか、従来の価格設定が成り立つかを確認します。自社ですべてを作るか、ほかの企業と組むかも検討事項です。

共同開発は、顧客の課題に合意し、関係するチームを集め、一緒に解決策を作る活動です。単純な接続から始めることも、個別の顧客に合うものへ進めることもあります。

特に、社内だけで試験を終わらせず、実際の顧客で検証する必要があります。何を解き、どう展開し、どう試し、どの価値を示すかを、最初から測れるようにします。

共同開発の相手は Microsoft に限りません。SI、MSP、ほかの ISV も対象です。

### 5.3 共同マーケティング（Co-market）：同じ買い手へ一つの話を届ける

共同マーケティングは、二社、三社が共通の課題と価値提案を持ち、同じ顧客へ働きかける活動です。複数のロゴを資料へ並べるだけではありません。

誰が買い手で、どの用途を解決し、どのメッセージを届けるかをそろえます。枠組みでは、関連性（relevance）、到達範囲（reach）、互恵性（reciprocity）、経営資源（resources）など、協業で何を得たいかを確認する考え方を示しました。

活動も目的に合わせます。関係構築なら経営層のラウンドテーブル、相互の支援を使うなら MDF などのプログラムを挙げています。Microsoft のプログラムを使うことは、その資源、到達範囲、現場の関係を借りることでもあります。

ただし、スライドの全項目は読み上げられていません。この文書で、未確認のフレームワーク全体を再現してはいません。

### 5.4 共同営業（Co-sell）：営業に求めるものを三つへ絞る

共同営業では、対象顧客が共通か、双方の営業担当者が協業できる準備をしているか、案件の管理方法に合意したかを確認します。

相手の営業担当者に求められることは、主に三つだと整理しました。

| 項目 | 意味 |
|---|---|
| 紹介（Introductions） | 適切な相手への紹介 |
| 情報提供（Intelligence） | 顧客内で起きていることの情報 |
| 働きかけ（Influence） | 顧客が自社を理解するための働きかけ |

Microsoft の営業と組む場合は、自社製品が、その担当顧客の消費や利用拡大にどう関わるかを具体化します。ほかの ISV と組むなら、受注や平均販売価格の拡大にどう役立つかを説明します。

「何でも手伝ってほしい」ではなく、紹介、情報、影響力のどれが必要かを明確にすることで、多数の営業担当者がいても展開しやすくなるという考え方です。

### 5.5 共同サービス提供（Co-serve）：売った後の役割を決める

共同営業の次は、顧客の導入支援（onboarding）、利用開始（activation）、継続利用（retention）です。導入し、使い始め、使い続けてもらう活動を指します。

ISV は、どのパートナーを加え、その相手に何を教えるかを決めます。SI は業務の接続や導入を担い、運用・保守まで扱う場合もあります。そこを扱わない SI であれば、顧客に近い MSP と組む方法があります。

共同サービス提供の枠組みは、社内の関係者をそろえ、更新や追加販売へつながる提供体制を作るためのものです。

### 5.6 繰り返せる協業の仕組みにする

四つの活動をつなぐと、協業を個人のつながりだけに依存させず、会社として繰り返せるようになります。

登壇者は、整備に一年程度かかるという目安と、戦略的パートナーは十社未満に絞るという自身の助言を示しました。経営者の時間も必要になるためです。これはプログラムの参加上限ではありません。

Partnership Leaders 自身も 28 人の会社として、この枠組みを使っていると説明しています。大企業だけの方法ではないという例です。

### 5.7 Frontier Accelerate と Marketplace

調査結果を Microsoft のプログラムチームへ共有したところ、並行して Frontier Accelerate for Marketplace が進んでいたと話しました。調査を受けて初めて作られた制度、と説明しているわけではありません。

ISV に対しては、利用クレジット（credits）、市場展開の支援、強化されたサービスプランを挙げています。ほかの参加者に向けては、次のように整理しました。

| 参加者 | 発表で挙げた仕組み |
|---|---|
| ISV | Frontier Accelerate for Marketplace |
| MSP | Frontier Accelerate for Azure |
| リセラー・ディストリビューター | 複数社間のプライベートオファー（Multiparty Private Offers）、CSP 向けプライベートオファー（CSP private offers） |
| SI・MSP のサービス | サービス向けプライベートオファー（Private service offers） |

Marketplace を、すべての参加者が協業する取引の場として捉えています。各制度の申請条件、料率、地域ごとの利用可否までは説明していません。

### 5.8 一顧客、一課題、一つの測定可能な証拠

最後に示した出発点は、顧客を一社選び、緊急性の高い課題を見つけることです。事業成果の例として、売上を生む、費用を減らす、リスクを抑える、生産性の課題を解くことを挙げました。

そのうえで、最初から一つの測定可能な証拠を決め、プロジェクトを通じて追います。成果を届け、振り返り、次に同じ協業を改善する流れです。

会場との質疑応答は収録されていません。登壇者へメールすれば、スライドと詳しい枠組みを送るという案内で終了しています。メールアドレス自体は読み上げられていません。

## 6. デモ・手順

このセッションでは画面を使ったデモは行われていません。調査結果とスライド上の枠組みの説明です。

発表で示された始め方は、次のとおりです。

1. 一社の顧客と話し、切実な課題を一つ選びます。
2. 事業成果との関係を確かめます。
3. 測定できる指標を最初に決めます。
4. 必要な相手と、開発・市場展開・営業・提供の役割を合わせます。
5. 成果を届け、協業の方法を改善します。

共同マーケティングから始めて反応を確かめることも可能です。上記は、すべての案件に開発からの直列工程を求めるものではありません。

## 7. 注意点・発表者の気付き

> 注意：製品が Marketplace にあることと、顧客が買う理由があることは別です。購入のしやすさ、需要創出、導入後の継続利用を分けて整える必要があります。

複数社が関わる案件では、問題発生時に誰が顧客体験へ責任を持つかを曖昧にしないことも、大切な指摘です。

## 8. 利用者にとっての利点

顧客は、ソフトウェアだけでなく、選定、購入、統合、利用開始、運用までを支える体制を得られます。また、最初から測定対象を決めることで、導入した価値を確認しやすくする狙いがあります。

このセッションでは、特定顧客の削減額や受注率など、四つの枠組みによる成果の実測値は示されていません。

## 9. まとめ

協業は、共同で作ることだけでも、営業を紹介してもらうことだけでもありません。共同開発、共同マーケティング、共同営業、共同サービス提供を通じ、製品の前後にある顧客体験まで整えます。

まずは一社の課題と、測れる成果から始めてください。そこから繰り返せる方法を作るというのが、登壇者の提案です。
