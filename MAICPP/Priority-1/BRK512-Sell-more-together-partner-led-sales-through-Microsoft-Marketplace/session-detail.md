# BRK512 Sell more together: partner-led sales through Microsoft Marketplace

## 1. はじめに

このセッションは、Microsoft Marketplace を使った「チャネル主導の販売（channel-led sales）」を扱う 45 分のブレークアウトです。対象は、Marketplace で自社ソフトウェアを販売するソフトウェア企業、そのソフトウェアを顧客に販売するチャネルパートナー（リセラー、ディストリビューター、SI など）です。

内容の中心は、Marketplace の 2 つの販売形態である **multi-party private offer（MPO）** と **resell-enabled offer（REO）** です。登壇者は、この 2 つを単独で使う場合と、組み合わせて使う場合を寸劇で再現しました。そのうえで、Cisco の担当者が実践経験を語り、最後にソフトウェア企業・ディストリビューター・チャネルパートナーそれぞれが次に何をすべきかを整理しています。

このセッションにはライブデモ（画面操作）はありません。商談の流れは、登壇者が役を演じる寸劇で説明されました。

## 3. 何に関する発表か

Microsoft は、Marketplace を「パートナーシップのためのプラットフォーム」にするというビジョンを、ここ数年の Ignite で語ってきました。発表によると、この取り組みで想定している主な対象は 2 種類です。

## 5. 発表内容の詳細

### 5.1 Marketplace のチャネル主導販売の現状

Jason 氏は、Marketplace の案件はスピードが速く、チャネルパートナーが入った案件は平均よりはるかに大きいと説明しました。ソフトウェア企業は Marketplace を通じて数百万の顧客にリーチでき、チャネルパートナーは取り扱うベンダーとの関係を広げ、顧客や Microsoft のフィールド営業に対して差別化できる、という整理です。

地域展開についての数字は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| MPO の対応市場（1 年前の Ignite） | 米国、カナダ、英国のみ |
| MPO の対応市場（今回） | 約 40 市場 |

### 5.2 近日対応予定の「バンドル」

Jason 氏は、**ソフトウェアとソフトウェア、ソフトウェアとサービス、サービスとサービスを 1 つのオファーにまとめる機能（bundle）が近日対応予定**だと紹介しました。たとえば、ソフトウェア企業が自社のソフトウェアと大規模なマネージドサービスやサポート契約を 1 回の取引で売りたい場合や、チャネルパートナーが基幹業務アプリとそれを守るセキュリティ製品、設計・導入・長期サポートをまとめて売りたい場合を例に挙げています。

Alison 氏もこの点に触れ、MPO を拡張してソフトウェアとサービスをまとめて販売できるようにする計画と、価格設定や国際販売をより細かく制御できる通貨まわりの強化に取り組んでいると述べました。提供時期の詳細は発表では語られていません。

### 5.3 MPO（multi-party private offer）

Alison 氏は、MPO を次のように説明しています。ソフトウェア企業とチャネルパートナーが 1 つの取引で協力し、チャネルパートナーがオファーで収益を得たうえで顧客に提供できる仕組みです。販売側は、顧客のクラウドコミットメントを活用でき、築いてきた営業関係も維持できます。

直近 6 か月で提供された機能として、次の 4 点が紹介されました。

1. MPO の約 40 市場への拡大（マレーシア、サウジアラビアを含む）
2. 顧客が Marketplace 上でプライベートオファーを**リクエスト**でき、リクエストが直接パートナーに届く
3. ほとんどのプライベートオファーで、購入が **1 ステップ**になった。あわせて将来の開始日を指定でき、顧客は都合のよいタイミングで購入できる（契約はその将来日から始まる）
4. 契約期間を最長 **10 年**まで指定できる **custom contract duration**。flexible billing と組み合わせると強力だと説明

### 5.4 REO（resell-enabled offer）

REO は、ソフトウェア企業がチャネルパートナーに、自社製品を代理で販売する権限を与える仕組みです。ほぼすべての市場で利用できます。チャネルパートナーは、ソフトウェア企業が人員を増やさなくても新しい市場に入る手助けができ、顧客へのプライベートオファーの提案を主導します。精算はソフトウェア企業との間で直接行います。

### 5.5 REO と MPO の組み合わせ

3 つ目の使い方が、REO と MPO の組み合わせです。ソフトウェア企業が、好みのディストリビューターに自社製品を代理販売する権限を与え、ディストリビューターは MPO にもう 1 社のパートナー（リセラー）を加えて、自分のリセラーネットワーク経由で販売します。国ごとの権限付与には REO を、案件ごとの拡販には MPO を使う、という分担です。

### 5.6 Cisco の事例（対談）

Aaron Hipp 氏は、自身の役割を Cisco の Global Cloud Marketplace and AI ISV lead と説明し、顧客、チャネルパートナー、Marketplace の成功に責任を持っていると述べました。Jason 氏によれば、Cisco は 2026 Microsoft Marketplace Partner of the Year で、MPO には Microsoft の会計年度 24 から取り組み、REO の最初期の事例の 1 つを手がけ、今年は REO を使って Marketplace で 2 階層（two-tier）の販売も行っています。

**REO が Cisco に合った理由**として、Aaron 氏は次の 3 つを挙げました。

1. グローバルな機会：REO の開始時、取引できる国は少なかったが、多くの国に需要があり、そこで取引できるようになった
2. 複数アーキテクチャにまたがる大型案件：Cisco はこれを通常 enterprise agreement で販売していて、MPO ではスムーズに取引できなかった。REO でより多くの大型案件を取引できるようになった
3. チャネルパートナーごとに Marketplace の実務の組み方が違うため、パートナーやディストリビューターに合わせて購入方式を選べる柔軟性が必要だった

Cisco は、もともとハードウェア企業で、この 20 年ほどでソフトウェア企業へ移行してきたと説明しています。コラボレーション、ネットワーキング、セキュリティ、オブザーバビリティの各ポートフォリオがあり、最近 Splunk が加わりました。この結果、顧客とパートナーの機会が増える一方、案件構造の裏側が複雑になったとのことです。

**Cisco が取引モデル以外にやったこと**は、主に enablement（教育・啓発）です。

- REO の開始後、「この新しいモデルをどう市場に出すか」が課題になり、Microsoft と共同でグローバルなウェビナーシリーズを開催した
- 内容は、顧客にとっての価値、REO が可能にすること、MPO の仕組み、両者を組み合わせた実際の流れの順
- 米国、英国、カナダ、オーストラリア、ニュージーランドで数百のパートナーが参加し、さらに地域を拡大中
- 参加者にはチャネルパートナーだけでなく、他のソフトウェア企業も含まれた
- ウェビナーの冒頭には、Marketplace 担当やアライアンス担当ではなく、営業またはチャネル組織の担当者が登壇した

Aaron 氏は、社内の営業やチャネル部門を巻き込むことが重要だと説明しました。最初の Marketplace 案件を経験したチームは、顧客から Marketplace で買う価値を直接聞くので、自ら推進役（champion）になる傾向があるそうです。具体例として、ある enterprise seller が Cisco で 4 件目の Azure Marketplace 案件を成約した話が出ています。アライアンスチームだけではできず、営業を一緒に巻き込んでいくという考えです。

**ソフトウェア企業へのアドバイス**として、Aaron 氏が挙げたのは次の点です。

- 顧客の購買行動の変化に追随するには社内の変更とサイクルが大量に必要なので、同じ立場の ISV 仲間の cohort でブレインストーミングすると役に立つ
- **comp neutrality** を確保する。社内でどちらの経路でも「parity（同等）」になるようにし、顧客のいる場所に合わせるという趣旨（comp の意味は発表では定義されていません）
- 変更はすべてチャネルパートナーに影響する。Cisco の事業の 95% 以上はチャネル経由なので、変更を作る段階からパートナーと協力し、フィードバックをもらう

**チャネルパートナーへの要望**としては、各社でマーケットプレイスの収益認識、市場参入の方法、営業組織の成熟度、Marketplace への取り組みの段階が異なるので、それをできるだけ早く、明確に伝えてほしいと述べました。「全員に同じ方法でスケールする」やり方は試したがうまくいかなかったとのことです。

### 5.7 次に何をするか：ソフトウェア企業向け

Jason 氏は、ペルソナごとに次のアクションを示しました。ソフトウェア企業向けは次のとおりです。

1. **transactable であること**：リスティングに "Get it now" ボタンが表示される状態にする
2. **Azure benefit eligible であること**：MPO や REO で顧客の MAC（クラウドコミットメント）を減らせる構成が、チャネル主導販売の基礎になる
3. 取引モデル（どの市場でどの形態か）を決める。成果を出すには、おそらく複数の形態を使うことになる
4. 社内チームで取り組む。アライアンスだけでなく、営業、マーケティング、オペレーション、法務、税務が揃う必要がある
5. チャネルパートナーを活性化する。基本的な 200 レベルの内容は Microsoft が扱うが、自社製品の売り方を教えるのはソフトウェア企業自身の役割

### 5.8 次に何をするか：ディストリビューター向け

Jason 氏は、Marketplace のセッションでディストリビューターを取り上げたのはこれが初めてで、REO、MPO、2 階層の Marketplace 販売によって対象になったと述べました。ディストリビューターには、次の点が示されています。

- まずは、最も影響の大きいベンダーを選ぶ。おそらく Microsoft ライセンスを Microsoft から直接購入している顧客（MAC のある顧客）に売っているベンダーが最初の候補
- 販売する地域を考える。Microsoft が税を管理する国と、パブリッシャーが税を管理する国がある。また、MPO は承認が下りた時点で、プライベートプレビューを経ずに開始するので、新しい国での提供が始まる時期に素早く対応する必要がある
- 自社のリセラーを enablement する。ソフトウェア企業は、MPO、ディストリビューターなしの REO、複数のディストリビューターが関わる REO の 3 通りで販売するため、リセラーに Marketplace の機会を伝えるディストリビューターが最も多くの案件を得て、ソフトウェア企業からも注目される

### 5.9 次に何をするか：チャネルパートナー向け

MPO に参加するための条件は、非常に低く設定されているという説明でした。手順は次のとおりです。

1. Microsoft のパートナーであること（パートナー ID を持つこと。Ignite に参加できているなら、たいてい該当する）
2. Partner Center で Microsoft Marketplace に登録する。具体的にはパブリッシャー契約を読んで同意する。同意すると、パートナー ID とは別の **seller ID** が付与される
3. その seller ID に、税金と支払いのプロファイルを設定する。米国の場合は resale certificate も必要
4. ここまでで、MPO の対象パートナー一覧に載り、MPO が利用可能なすべての地域で MPO の案件を販売できる。コンピテンシー、スペシャライゼーション、売上のしきい値は不要

そのうえで、次の取り組みが示されました。

- どのソフトウェア企業の製品を販売するか決める。すでに関係のある企業から始め、案件を売るときに導入、設計、大型のマネージドサービス契約を引き寄せる（push / pull / drag along）ソフトウェア企業に優先順位を付ける。Marketplace を使って、自社のその他の事業も一緒に伸ばす狙い
- Microsoft のフィールド営業との関係が深まる、あるいは co-sell に参加できるベンダーも候補に入れる
- パイプラインを作り、案件を成約する。ソフトウェア企業と一緒に go-to-market（キャンペーン、イベントなど）を行う方法のほか、顧客に直接「この国でも MPO が使えるようになった。MPO が何か分からなくても、ソフトウェアの購入を効率的に進め、コストを抑える手伝いができる」と声をかける方法があるという話でした。

## 6. デモ・手順

**このセッションでは、製品の画面を使ったデモは行われていません。** 代わりに、登壇者が役を演じる寸劇（skit）で 3 つの商談の流れが再現されました。以下は、寸劇の中で語られた内容の要約です。寸劇なので、画面上の具体的な操作は語られていません。

### 6.1 寸劇 1：MPO（multi-party private offer）

役割は、顧客が Kristen 氏、チャネルパートナーが Jason 氏、ソフトウェア企業が Alison 氏です。ソフトウェア企業の名前は Northwind Data Solutions という架空の設定です。

1. 顧客は、データ移行（Azure 移行）の途中で、規制要件を満たすデータプラットフォームが必要。条件は次のとおり。
   - Azure のコミットメントが未消化なので、この購入をコミットメントの消化に充てたい
   - 契約期間は 6 年半（78 か月）。開始は新会計年度に合わせて 1 月 1 日
   - 請求は四半期ごと。請求通貨はユーロ（市場通貨は英国ポンド）
2. チャネルパートナーが Northwind Data Solutions を推薦。同社の製品は Marketplace で販売され、Azure benefit eligible なので MAC を減らせる。導入と、コンプライアンス設定は自社で行い、同じオファーに含める
3. チャネルパートナーがソフトウェア企業に連絡。MPO が向くか確認し、ソフトウェア企業側は、custom contract duration（78 か月）、将来の開始日（1 月 1 日）、flexible billing（四半期請求、ユーロの請求通貨）で対応できると回答。価格は前回の案件と同じとし、チャネルパートナーがマージンと導入サービスを上乗せして、顧客に単一のオファーとして出す
4. チャネルパートナーが、自社のプロフェッショナルサービスを加えたオファーを顧客に送る。顧客は Azure ポータルでオファーを確認する（データプラットフォーム、プロフェッショナルサービス、要件のすべてを含む）
5. 顧客は、従来のプライベートオファーでは「accept して purchase」だったが、今回は 1 ステップで購入できる
6. 顧客は、購入コストを purchase order に割り当てられる。部門ごとに技術コストを分担しているため、支出が ROI にどうつながるか追跡しやすくなり、FinOps チームが喜ぶという説明
7. 1 月 1 日にサブスクリプションが自動で開始され、顧客が Azure ポータルで何かする必要はない
8. 結論として、1 つのオファー、1 回の購入、1 枚の請求書で、purchase order と希望の請求通貨に対応できた

### 6.2 寸劇 2：REO（resell-enabled offer）

役割は同じです。ソフトウェア企業は欧州需要が強く、フランスを次の市場にしたいが、フランス語の営業、地域サポート、現地の顧客関係がありません。

1. ソフトウェア企業が、チャネルパートナーに REO での代理販売を依頼。契約書は事前に送付済みで、チャネルパートナーが確認して署名した。Marketplace の外でのソフトウェア企業への支払い方法も、契約の条件に含まれている
2. ソフトウェア企業が Partner Center で、チャネルパートナーにフランスでの販売を権限付与する。まずフランスから始め、広がりに応じて欧州に拡大する計画
3. チャネルパートナーは通知を受け取り、自社の Partner Center アカウントの REO セクションにソフトウェア企業の製品が表示されていることを確認する
4. パリの顧客がすでに関心を持っており、チャネルパートナーがその顧客向けにプライベートオファーを設定して送る
5. 顧客は、チャネルパートナーを通じて購入でき、ベンダーのオンボーディングを省ける。実装の窓口がチャネルパートナーなので、関係の管理もそこで行うほうが自然、と説明
6. 顧客は Azure ポータルでオファーを確認して購入する。販売、導入、サポートはすべて現地で、フランス語で対応される
7. Microsoft が顧客に請求し、チャネルパートナーに支払う。製品が Azure benefit eligible なので、この購入は顧客の MAC にカウントされる
8. チャネルパートナーが、Marketplace の外で、契約どおりにソフトウェア企業へ支払う手続きを進めている。ソフトウェア企業は、新しい人員も現地の営業拠点も追加せずに、フランスで最初の顧客を獲得した

### 6.3 寸劇 3：REO + MPO（ディストリビューター経由）

Darren 氏がディストリビューター役で加わります。

1. ソフトウェア企業はアジア進出を計画。ディストリビューターを国ごとに REO で権限付与し、ディストリビューターが案件ごとに MPO でネットワークを通じて販売する流れを説明する
2. ディストリビューターが契約書に署名（Marketplace 外の支払い条件を含む）
3. ソフトウェア企業が、ディストリビューターの Partner Center の seller ID に、マレーシア、香港、日本での再販権限を付与する。この 3 か国は、REO と MPO の両方が現時点で利用できる国
4. ディストリビューターは自社のチャネルを有効化済みで、マレーシアのリセラーに製品を必要とする顧客がいる。リセラーが顧客との関係を持つので、ディストリビューターが MPO を作成してリセラーに送る
5. ディストリビューターは、自社の Partner Center アカウントで Northwind の製品の MPO を作成し、顧客との関係を持つリセラーを案件に加えて送信する
6. リセラーは Partner Center でオファーを確認し、詳細とマージンを上乗せして顧客に送る
7. 顧客が購入する。Microsoft が請求と支払いを担当し、この案件は Azure benefit eligible なので MAC にカウントされる
8. Microsoft が顧客に請求し、リセラーにマージンを支払い、ディストリビューターに残りを支払う。ディストリビューターは、契約に従ってソフトウェア企業への支払いを進める
9. ソフトウェア企業は、販売チームを作らずにマレーシアで最初の顧客を獲得。次は香港と日本

## 7. 注意点・発表者の気付き

- 寸劇 3 では、REO と MPO の**両方が現時点で使える国**としてマレーシア、香港、日本が挙げられました。
- **REO では、Marketplace の外での支払いが発生します。** Microsoft が顧客に請求してチャネルパートナーに支払い、チャネルパートナーがソフトウェア企業へ支払う条件は、契約で事前に取り決めておく形です
- **新しい国で MPO が始まる時期は予告されません。** Microsoft は承認を得た時点で、プライベートプレビューなしで開始するため、ディストリビューターやパートナーは、その動きに合わせて対応を決める必要があります
- **Marketplace には税の管理方法が異なる国があります**（Microsoft が税を管理する国と、パブリッシャーが管理する国）。ディストリビューターは販売する地域を検討する際にこの点を考慮する、という話でした。具体的な違いは発表では説明されていません
- Aaron 氏の経験では、チャネルパートナー向けに全員同じやり方で拡大しようとしても機能しません。パートナーごとの事情を早く共有してもらうことが重要です
- Aaron 氏が挙げた comp neutrality の実現には、営業やチャネルだけでなく、法務や財務の関与が必要だと Jason 氏が補足しています
- 新機能（ソフトウェアとサービスのバンドル、通貨まわりの強化）は「近日対応予定」です。時期は語られていません

## 8. 利用者にとっての利点

このセッションで語られた、顧客側の利点は次のとおりです。

- Azure benefit eligible の製品を Marketplace で購入すると、購入額が Azure のコミットメント（MAC）の消化に充てられる
- MPO で、導入サービスやコンプライアンス対応を含む内容を、1 つのオファー、1 回の購入、1 枚の請求書にまとめられる
- 契約期間（最長 10 年）、将来の開始日、請求の頻度、請求通貨を、要件に合わせて指定できる
- ほとんどのプライベートオファーで購入が 1 ステップになり、購入額を purchase order に割り当てられる
- 信頼しているパートナーから購入でき、ベンダーのオンボーディングを省ける（REO の寸劇での説明）
- 購入後の請求と支払いは Microsoft が処理する

ソフトウェア企業とパートナー側の利点としては、人員や拠点を増やさずに新しい国へ販売を広げられること（寸劇での説明）、チャネルパートナーが入った案件が大きいこと、チャネル主導の販売が前年比で倍増していることが挙げられました。

## 9. まとめ

Marketplace のチャネル主導販売は前年比で倍増しており、MPO の対応市場は 1 年で 3 市場から約 40 市場に増えました。ソフトウェア企業とチャネルパートナーは、MPO、REO、その併用という 3 つの形態を、市場や顧客に応じて使い分けます。寸劇では、MPO は契約期間や請求条件の細かな要望に応える手段として、REO は現地の営業体制を持たない市場に入る手段として、併用はディストリビューター経由でリセラーに広げる手段として示されました。

Cisco の事例は、これを実際に実行した例です。複数の形態を使い分け、営業・チャネル部門を巻き込み、パートナーの enablement を自社で行っていました。次のアクションとして、ソフトウェア企業は transactable と Azure benefit eligible を満たしてモデルを選ぶこと、ディストリビューターはベンダーと地域を選んでリセラーを育てること、チャネルパートナーは Partner Center で seller ID と税・支払いプロファイルを整えることが示されました。支援が必要な場合は、Frontier Accelerate for Marketplace や ChannelReady@microsoft.com が窓口になります。
