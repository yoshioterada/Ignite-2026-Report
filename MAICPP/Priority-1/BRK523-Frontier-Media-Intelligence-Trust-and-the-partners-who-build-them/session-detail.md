# BRK523 Frontier Media: Intelligence, Trust, and the partners who build them

## 1. はじめに

このセッションは、メディア＆エンターテインメント（M&E）業界で Microsoft と組むパートナー企業に向けた発表です。技術の紹介ではなく、「AI を使ってメディア企業が変革を進めるとき、パートナーは何をどう売り、どう届けるか」が主題です。

発表は 3 部構成です。最初に Microsoft の Simon Crowshaw 氏が、メディア業界の変革の全体像と顧客事例を紹介します。次に Cara Catalane 氏が、パートナーが Microsoft と一緒に市場へ出るための進め方（Build / Sell / Deliver）を説明します。最後に、Avid の Kevin Isaacs 氏が Simon 氏との対談で、Microsoft と組んできた経験を語ります。

発表全体を貫く考えは、**「ツールやモデルは借りるものだが、インテリジェンスは自分のものとして持つ。それをつなぐのが信頼（trust）だ」** というものです。

## 5. 発表内容の詳細

### 5.1 メディア業界の状況

Simon 氏は、メディア業界の変化を示すスライドを紹介しています。成長、投資対効果、AI の採用、コンテンツ制作の変化が示され、AI による新しい業界収入が生まれつつあると述べます。そこで「$600 billion」という金額を挙げ、利益の分配構造やコンテンツのライセンスのあり方、体験が変わると説明しています。この金額が何を指すかの詳しい説明は、発表では語られていません。

もう 1 つの数字が、メディア経営層の 87% です。「AI が制作のやり方を大きく変えると予想している」と述べています。Simon 氏は Walt Disney Company 出身で、制作の現場は利益率に比べて非常に高コストだと話しています。

### 5.2 変革を見る 3 つの視点

Simon 氏は顧客との会話で、変革を次の 3 つの視点から捉えると説明します。

| 視点 | 説明された内容 |
| ---- | ---- |
| コンテンツ制作の加速 | 各社に固有のワークフローがあり、それ自体がある意味で IP。それを技術でどう実現するか |
| インサイトの変革 | パーソナライズされたエンゲージメント、リテンション、チャーン管理、サブスクライバーなど。コンテンツとユーザーを収益化するための柱 |
| オペレーション | メディアを大規模に運用・配信する基盤。バックオフィス、財務、テクノロジーを含み、AI で急速に変わりうる領域 |

オペレーションの話は、後半の Avid との対談につながるとも述べています。

### 5.3 AI native media company と IQ layer・trust plane

Simon 氏は「AI native media company」という言葉が好きだと述べ、その実現のために Microsoft の IQ layer を紹介します。目的は、より早く賢く動き、収益を伸ばし、大規模に運用・配信することです。

その前提として、制作、広告、配信など複数の柱にまたがるデータを 1 か所に集める必要があります。誰が何に取り組み、何が上手くいき、どの広告枠が効果的で、誰が一番買っているのか、といった問いに答えられるようにするためです。Simon 氏は「メディアは本当に雑然としている（messy）」と強調します。ワークフローごとに違い、情報はメール、Excel、Word などに散らばっています。それらを束ねると、正しい問いを立てられるようになるという説明です。

Simon 氏が挙げた観点は次のとおりです。

- **事業の状態と協業**：事業の状況、誰が何をしているかを把握する。
- **統制された知識**：どんなライセンスを持ち、どのツールが使え、コンテンツはどこへ出せるのかを把握する。メディア企業にはコンプライアンスや法務の確認が多い。Simon 氏の見方では、今日のほとんどのメディア企業は、コンテンツがどこで再生され、誰がアクセスできるのかを把握しきれていない。
- **外部シグナル**：web IQ layer を通じて、ファンや顧客が世界中でどう行動しているか（どれくらい視聴するか、視聴や滞在を伸ばす要因は何か）を知り、受け身ではなく先回りで動く。

これらを束ねるのが trust plane です。メディア企業はコンテンツをライセンスしたり購入したりしているため、流出は許されず、セキュリティと信頼が前提だと述べています。Simon 氏は、これらは「やるかもしれないこと」ではなく、AI native になるために必ずやることだとし、変革しない企業は変革する企業に対して苦戦すると述べています。

Simon 氏は Kantar の話で、「速すぎて正確さを失うことは望まない。適切なシグナルで組み立てる必要がある」とも補足しています。

### 5.5 パートナーが担う役割

Simon 氏は、メディア業界は小さく、ニッチで、ワークフローが固有だと述べます。そのため、Microsoft が作らないものを作るパートナーが生命線になるとしています。メディアは速く動くため、回復力（resiliency）のあるパートナーも必要です。

### 5.6 パートナー向けプレイブック：Build / Sell / Deliver（Cara 氏）

Cara 氏は、Microsoft とパートナーが「AI first の変革パートナー」になるための 3 本柱を示します。

| 柱 | 内容 |
| ---- | ---- |
| Build | すでに持っている IP やソリューションをパッケージ化する。業界・ドメイン固有のユースケースに着地させ、再現できる顧客事例（proof point）を作る。IP とサービスを再現可能な形で取り付け、co-sell readiness を達成する |
| Sell | 価値提案とユースケースをそろえ、共同で市場に出る。業界向けの資料作成、顧客成功事例の発信、パートナー向けのインセンティブ・プログラムへの整合を含む |
| Deliver | 信頼を作り、競合と差別化する層。専門性（specializations）、認定（certifications）、industry AI certified software の指定を取得する |

#### Build：ユースケースの選び方

スライドには、メディア顧客から繰り返し聞くユースケースが 7 つ並んでいました。Cara 氏が求めているのは、そのすべてで完璧になることではありません。**すでに自社の顧客と事例がある 1〜2 個を選び、深く掘り、再現可能にする**ことです。「10 社目は 1 社目より楽になるべきだ」と述べています。

#### Build：IP をどう取り付けるか

Microsoft の技術スタックに IP を結びつける方法として、次の 3 つが示されました。

1. **Operational IP**：customer 0 のアプローチ。自社内のツールや ROI を元に、スケールするためのプレイブックを作る。
2. **Services**：アクセラレーター、エージェントのブループリント、アセスメントツールなど。これらを軸にユースケースを作り、顧客に示す。
3. **Product IP**：従来型のパッケージ化されたエージェントや、本格的な SaaS。マーケットプレイスに掲載されるもの。

IP を最適化する方法も 3 つ紹介されています。customer zero のイノベーションモデル、最初のパイロットを一緒に進めて ROI と成功事例を作る anchor（lighthouse）顧客を選ぶこと、そして Microsoft や周辺のパートナーエコシステムと共同で作る（co-create / co-build）ことです。

#### Sell：業界を MSEM の各段階に組み込む

Cara 氏は、Microsoft の顧客エンゲージメントモデル MSEM の各段階に、業界の視点をどう組み込むかを説明しています。

- **Listen and consult**：技術から入る前に、まず業界の課題を聞く。顧客から繰り返し聞く課題を、特定のユースケースにつなげる。
- **Inspire and design**：顧客とワークショップを開き、志を同じくする企業が集まってその場でアイデアを出す。AI の可能性を一般論で語るのではなく、実際のソリューションにつなげる。
- **営業のロードマップ**：スライドには各段階での会話の例が載っていました。Cara 氏は「写真を撮るスライド」と紹介しています。例として、狙う企業の特定（業界の専門家や営業と定期的に、今四半期にあるソリューションで狙う上位 10〜20 社のメディア顧客を決める）、顧客内のペルソナの調査（Heads of Studio、CMO、CTO など、ユースケースを着地させる適切な人を同席させる）が挙げられました。
- **交渉・ソリューションの語り方**：顧客が気にする指標と ROI に結びつける。技術起点で入ることは陥りやすい罠だと述べています。指標の例として「60% の content time savings」、アップリフト、解約率の低下を挙げています。

#### Deliver：人の面

Cara 氏は、デリバリーを「人のソリューション」と捉えます。技術ごとに縦割りだった組織を、業界ごとの専門家を中心とした横断的なチームに移す考え方です。

- 1 つの製品領域に深い人ではなく、複数プラットフォームにまたがるソリューションセラーを置く。
- Microsoft 技術の一部に詳しい営業ではなく、ドメイン知識と技術の深さを組み合わせてワークフローを再設計できる業界スペシャリストを置く。
- Cara 氏が最も重要と考えるのが **AI upskilling**。ロールベースの学習パス、AI centers of excellence、認定・スキルをチーム内に埋め込み、「Microsoft の技術をパートナーが売り、パートナーの技術を Microsoft が同じように語れる」状態を目指す。

### 5.7 Avid の Kevin Isaacs 氏との対談

Kevin 氏は、Media Composer、SaaS サービス（新しい Avid Content Core、Media Central）、共有ストレージの Nexus など Avid の製品を作るエンジニアリングを統括していると自己紹介しています。Azure 上を中心に複数のデプロイメントがあり、Microsoft とのパートナーシップが成功していると述べています。

#### COVID 期の経験と Edit on Demand

- もともとニュースやスポーツのような速いターンアラウンドのメディアは、機材や作業を「4 つの壁の中（社内）」に置く傾向があった。COVID でそれができなくなり、遠隔・仮想化して、どこからでも大規模に運用する必要が生じた。
- Azure、特に VDI（仮想デスクトップ）を使い、編集室の環境を再現して自宅から作業できるようにした。
- 共有ストレージは、社内の閉じた部屋やデータセンターでしか動かなかった。Microsoft と密に協力して、ストレージを BLOB バックエンドに変換し、スケールでき弾力的な SaaS として動く **Edit on Demand** を作った。制作が必要になったとき、機材を借りる代わりに、その場で立ち上げられる。
- もともとはレンタル市場向けに作ったが、COVID で機材が入手できなくなり、すぐに立ち上げる手段として役立った。
- 副次効果として、それまで各部門が個別に持っていた環境の統合が進んだ。ロンドンの編集者が Hollywood の作品を仕上げることも可能になり、世界規模の大手メディア企業が各地向けのプロモを各地で制作できるようになった。Kevin 氏は、各社の固有でカスタムソフトウェア由来の硬直したワークフローから「解放された」と表現しています。

#### Teams を使った協業

- **Avid Huddle**：編集者の「肩越し」にディレクターが見る従来のやり方を、Teams クライアント上で別の場所からでも見られるようにした。
- スポーツでは、イベント会場へ機材を飛行機で運んでいたのが、フィードを持ち帰り、遠隔または大規模施設で集約して作業できるようになった。
- Simon 氏が、レンダリングやコンフォームを経た最終シーンは、多くの経営層が Teams 経由でレビューする、と話を向けました。Kevin 氏は、1 つのコンテンツが仕上げに至るまでに何度も行き来することに驚いたと答え、この往復も AI が変えつつある領域の 1 つだと述べています。
- 数百人規模の編集者が同じ施設で同じコンテンツを扱うとき、各自が見られるものだけを見て、ビンのロックで互いに上書きしないようにする仕組みが Avid のコア IP だと説明しています。Kevin 氏はこれを「メディア版の SharePoint」とたとえ、800 人の編集者の例を挙げています。Azure のエコシステムがこれを可能にしているとのことです。

#### マーケットプレイスと Foundry

Kevin 氏は、Edit on Demand、共有ストレージの Nexus、Media Central（上記の協業エンジンで、Azure で利用可能）の多くを、主にマーケットプレイス経由で提供していると述べます。最近の Content Core は、さらに多くの AI ワークフローを可能にし、定型作業をシステムから取り除くものです。さまざまな AI モデルと Foundry を使い、メディアのエコシステムでうまく動くようにしているそうです。「データをあちこちに動かすのではなく、メディアを人のところへ持っていく」とも述べています。

#### GitHub Copilot とエージェントの活用

- Kevin 氏のチームは「GitHub Copilot ショップ」で、開発の加速に使っています。コードを書くエージェントを多数作り、パイプラインに接続し、QA・QC も行っています。
- 導入は約 3 年半前と早く、当時は法務部門から、AI が書いたコードをどう把握するのかという懸念で反対されたそうです。社内の導入は最初は遅く、その後加速し、約 1 年前（昨年の 11 月ごろ）に大きく加速しました。理由は、エージェント型のモデルに移行したことです。開発者ごとに使い方が少しずつ違っても、エージェントがあるからスケールすると述べています。
- コーディングエージェントだけでなく、プロダクションのエージェントもあります。例として、ポストプロダクションで素材（dailies）が入り、アシスタントエディターが組み立ててエディターに渡すまでの段階は非常にコストが高く、エージェントで容易に置き換えられると説明しています。ソフトウェア開発で行っていることをモデルにしています。
- 顧客が自分のモデルを持ち込めるようにしています。モデルは「借りるもの」であり、変化が激しいので、特定の 1 社のモデルだけに固定していたら限られていただろう、と述べています。**大事なのは、借りているツールではなく、その上に築く基盤**だという考えです。
- Simon 氏は、「モデルが最も重要というわけではない」と Microsoft の別の講演（発言者名は音声認識の都合で表記が確定できません）でも語られたと紹介し、パートナーが実験して学び続け、顧客と足並みをそろえることが重要だと述べています。

#### パートナーへの助言

Kevin 氏の助言は、先に述べたとおり、**機会を見たら再現性を探し、パターンが見えたら早めに関わる**ことです。Avid は製品を提供しているがインテグレーションはしない立場であり（以前は自社でも行っていたが、それが問題を招いたと述べています。聞き取り不明瞭）、Microsoft は適切なパートナーを引き合わせ、顧客につなげるネットワークを持っているとしています。

#### メディアの視点で学んだこと

- メディア業界は IT から隔離されていた。運用チームが社内インフラにつながっておらず、エアギャップのため Teams も使えなかった。今は Copilot やエージェントがチーム、オフィス全体を横断して見られるようになり、Excel や Word を統合できる。
- 以前は Media Composer に、独立して組み込まれた「Script Sync」という機能があったが（音声認識の都合で表記が確定できません）、今は Word にある脚本をそのままつなげられる。社内の営業チームが「エアギャップで」と言ってくるたびに、本当に必要かを確認している、とも述べています。
- Simon 氏は、メディアが必要とする文脈の多くはエンタープライズ側にあり、それが今、新しい形で使えるようになったと応じています。
- 対談では両者が、エンタープライズはもともとメディアに近いべきだったと話しています。メディアは「church and state（教会と国家）」のように両者を分けてきたが、今はこれまでになく近づいたとしています。コスト削減の圧力が強く、メディアは非常にコストに敏感だという現実にも触れています。

#### これからの 1 年

Kevin 氏は、AI はすべてを変えると述べつつ、多くの企業が「自分たちで作れる」と考える点に落とし穴があると指摘します。作った担当者が辞めるとサポートできなくなる。これはエージェントで作った場合も同じだと述べています。そのため、ソリューションを顧客の業務全体に組み込むパートナーの差別化は残り、AI でむしろ素早く適応できるようになります。決定論的なフローを保ちつつ、ユーザーごとに調整することも、個別に作り込まずに実現できるそうです。価値の多くはモデルそのものではなく、どう使い、どこにつなぐかにあり、エコシステムに接続できるパートナーが必要だと述べています。

Simon 氏はこれを受け、メディアには回復力が必要で、自分も何でも自作できる時代だが、頼る相手は 24 時間 365 日動く堅牢なものでなければならないと述べて締めています。

## 7. 注意点・発表者の気付き

- **技術から入らない**：顧客に提案するとき、技術起点は陥りやすい罠。顧客が気にする課題と ROI から入る、と Cara 氏は述べています。
- **全部をやろうとしない**：7 つのユースケースの中から 1〜2 個に絞る。
- **変革は技術より難しい**：採用は難しく、ワークフローの見直しが必要。メディアには 20 年以上続く慣行がある。
- **速さと正確さ**：Kantar の話で、速さを優先しすぎて正しさを損なうことは望まない、と述べています。
- **自作の落とし穴**：作った人がいなくなるとサポートできなくなる（Kevin 氏）。エージェントで作った場合も同じ。
- **モデルへのロックイン**：特定のモデルだけに固定すると、変化の速さに対応できなくなる（Kevin 氏）。
- **信頼と回復力**：コンテンツの流出は許されず、頼る基盤は常時稼働する必要がある。
- **AI 導入の社内障壁**：Avid では、Copilot 導入の初期に法務部門が AI が書いたコードの把握方法を懸念し、導入は最初ゆっくりだった。

## 8. 利用者にとっての利点

発表で語られた成果と効果は次のとおりです。いずれも、スライドと口頭での説明に基づくもので、測定方法などの詳細は語られていません。

## 9. まとめ

- メディア企業にとって、ツールとモデルは借りるもの、インテリジェンスは自分のもの。それらをつなぎ、全体を成り立たせるのが信頼です。
- 変革では、制作、インサイト、オペレーションの 3 つの視点で考えます。散らばった情報を束ねる IQ layer と、統制を担う trust plane が前提になります。
- 技術は準備できていて、難しいのは変革そのものです。メディア固有のワークフローを知るパートナーの役割が大きくなります。
- パートナーは Build（IP のパッケージ化）、Sell（共同の営業）、Deliver（専門性と認定による信頼）の順で進めます。ユースケースは 1〜2 個に絞ります。
- Avid の経験からは、再現性を見つけて早めに Microsoft と関わること、モデルではなく基盤に価値を置くことが助言として示されました。
