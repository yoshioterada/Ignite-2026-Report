# THRSP1151 Why are we still treating AI agents as software?

## 1. はじめに

このセッションは、Gravity の Tim Tyler 氏が、AI エージェントを「ソフトウェア」ではなく「デジタルな従業員」として統治しようという考え方と、そのためのフレームワーク **Agent Accountability Framework** を紹介する約 21 分の登壇です。人間の従業員を 100 年にわたって管理してきた仕組み（ID、上司、職務記述書、権限、評価、懲戒）をエージェントに当てはめ、**Assign（割り当て）／Align（整合）／Account（説明責任）** の 3 つのドメインで整理しています。

登壇者の結論は「まず ID から始めてほしい（Give your agents identity today）」です。ソフトウェアの標準やプロトコルは必要だが、それだけでは足りない、という立場で話が進みます。

このセッションでは、画面を使ったデモは行われていません。スライドの図（Agent 409 という架空のエージェントを使った例）を使った口頭の説明が中心です。

## 5. 発表内容の詳細

### 5.1 導入：奇妙な求人票とエージェントを取り巻く状況

Tim 氏は、社内の人に頼まれたとして、本題の前に次のような求人票を示しました（Gravity が実際に採用中でもあると述べています）。職種は「マーケティングオペレーション、フルタイム、常時」で、場所は不問、ID は不要、マネージャーはなし、職務記述書はあいまい、主要システムにアクセスでき、パスワードは共有、24 時間 365 日、誰もチェックせず、問題が起きても解雇されない、という内容です。これを読んで採用するかと会場に尋ね、「あなたはすでに採用している。そうでなくても、他社は採用している。話しているのは AI エージェントのことだ」と話を接続しました。

現状の数字は、Gravity が実施した「state of AI agent security」（AI エージェントのセキュリティの現状調査）によるものとして、次を挙げています。

- **75%** の企業が、今後 12 か月でさらに多くのエージェントを展開する計画である。

本番品質のエージェントを妨げているものとして、次の 3 つが挙がりました。

- **コスト（expense）**：投資に見合うリターンが得られているのか。
- **無秩序（anarchy）**：誰も承認していないエージェント、つまりシャドー AI。
- **リスク**：1 つの共有パスワード、重要システムや全システムへのアクセス。

そこで、「すでに統治のやり方を知っているのに、なぜ AI をソフトウェアのように統治し続けているのか」という問いが出されます。

### 5.2 Agent Accountability Framework の全体像

過去 100 年、企業は人間の従業員をどう統治するかを工夫してきました。Gravity はこれをデジタルな労働力にも適用するため、Agent Accountability Framework を作ったと説明しています。3 つのドメインは次のとおりです。

| ドメイン | 役割 | 一言で |
| --- | --- | --- |
| Assign | エージェントの組織・業務プロセスにおける存在を確立する | Name every agent |
| Align | エージェントのスコープと成功の定義を確立する | Bound every action |
| Account | スコープを強制し、信頼を確立する | Trace every outcome |

### 5.3 Assign：あなたは誰か（ID）

入社するとまず ID が与えられます。小さな組織ではメールアドレス、大きな組織では入館用の ID バッジです。Tim 氏は、ID バッジの写真はたいてい「人生で最悪の写真」だと笑いを交えて話しています（Verizon 勤務時代のバッジの例）。エージェントにも同様に、**1 エージェント、1 つの名前、1 つの信頼できる情報源（one agent, one name, one source of truth）** を与える必要があります。

説明用の例として、Tim 氏は **Agent 409** という架空のエージェントを使います。409 は、組織全体から参照できる既知のレジストリに、一意の ID を持ちます。ID は、このフレームワークのあらゆる要素が結びつく原則です。

エージェントは単独で働くのではなくチームの一員です。人間が使う個人のエージェントなら「2 人のチーム」、特定の目標や役割をもつ小グループ、あるいは組織全体がコンテキストになることもあります。エージェントは、チームの目標、意思決定、履歴といったコンテキストを受け取るだけでなく、自分が何をしたか、何をしているかをチームへ返す必要があります。

ここで Tim 氏が強調したのが、**エージェントを「単一ユーザーのデジタルクローン」ではなく「チームメイト」として扱う**ことです。これは「なりすまし（impersonation）対委任（delegation）」の違いだと述べています。エージェントが単一のユーザーを代表し、OAuth の資格情報で動くだけなら、そのユーザーを代行しているにすぎず、チームメイトではありません。例えば、Mary という社員が Tim のバッジを下げて「私は Tim です」と歩き回るのではなく、Tim として行動する権限を委任される形が望ましい、という例えです。

### 5.4 Assign：上司は誰か（スポンサー）

次は、誰が指示を出すのかです。Tim 氏は、「エージェントについて責任者を名指しできる企業は **10% 未満**」という数字を挙げ、これを「怖いことだ」としています。そこで、エージェントごとに答えを出す責任者（スポンサー）を置きます。例では **Sven** が Agent 409 のスポンサーです。Sven は、エージェントを定義し、409 の支出に責任をもち、問題が起きたときに呼び出される人です。

Sven がすべてをやるわけではありません。開発者や財務部門も関与しますが、設定が行われたことと、問題があれば答えることに責任を持つのは Sven です。重要なのは、**役割でもチームでもなく、1 人の名前**を置くことです。Tim 氏はこれを **line of accountability（説明責任の線）** と呼んでいます。

この線は、人間の組織の統治にすでに組み込まれています。例では、Anika が支出に責任をもち、Stevenson 氏が Anika に責任をもち、取締役会が全員に責任をもちます。そして取締役会は、最終的に一般の人々、消費者、ステークホルダーに責任を負うため、線の行き着く先は私たち自身だと述べています。この線は逆方向、つまりエージェントが別のエージェントを呼び出す場合にも伸びます（5.6 で後述）。

### 5.5 Align：あなたの役割は何か（ロールとミッション）

Align ドメインは、エージェントのスコープと成功の定義を確立します。人間は入社初日に職務記述書をもらいますが、それがないと戸惑います。エージェントも同様で、役割を与えないと「勝手に作り上げて」しまうと Tim 氏は述べています。

Sven が 409 に与える内容は次のとおりです。

- **目的（purpose）**：例として「ベンダーの買掛金（AP）の帳簿を、より速く締める」。
- **具体的なタスク責任**：請求書を支出承認と照合する、支払いを請求書と照合する、など。
- **予算**：例として 400 ドル。エンタープライズのエージェントには少なく見えるかもしれず、4,000 ドルでも 40 万ドルでもよい。適切な ROI が得られる額を Sven が決め、ロール定義に設定する。

これらの箇条書きは、実際にはシステムプロンプトにあたり、成功をどう測るかの出発点になります。

ここで **オンボーディング時とランタイムの違い**が説明されました。

| タイミング | 内容 | 成功の単位 |
| --- | --- | --- |
| オンボーディング | purpose（例：請求書を発注書と照合し、仕訳を計上する） | ゴールレベルの成功 |
| ランタイム | mission（今この請求書の仕訳を計上する、など、エージェントがその瞬間にやろうと決めたこと） | タスクレベルの成功 |

ミッションは、タスクごとに、MCP サーバーのようなツールを呼び出す際の具体的な目的になります。

### 5.6 Align：権限（オーソリティ）と最小権限

役割の次は、仕事をするためのデータやツールへのアクセスと認可です。人間でいえば、アプリケーションへのログイン、特定のデータセット、特定のファイルへのアクセスにあたります。エージェントに、何が見えて何ができるかの権限を与えます。Sven はどの扉を開けるかを決め、409 に鍵を渡します。これにより境界と、権限ルール内でのエスカレーションが決まります。**必要以上の権限は与えない**のが原則です。

Tim 氏は、複数エージェントがつながる場合を次の例で示しました（用語が混ざらないよう、アクセスを A、B、C、D と呼んでいます）。

1. Sven は A、B、C、D のアクセスを持つ。
2. Agent 203 は、Sven から頼まれた情報を処理する。203 のアクセスは C と D だけ。
3. 203 は、請求書情報をもつ Agent 409 を呼び出すことにした。409 のアクセスは D、E、F。
4. 重なるのは D だけなので、409 が行った作業から返せるのは、結局 D のアクセスで得られる範囲だけになる。

つまり、**最も低い権限のスコープに合わせて制限する**必要があります。409 の権限が広くても、E と F の情報を Sven に返してはいけません。Sven は E と F の情報へのアクセスを持たないためです。

さらに、**整合（alignment）を前提にしない**ことも強調しました。Sven が制御できないものとして、次を挙げています。

- モデルのデフォルト：Anthropic と OpenAI 自身が「人間の期待に整合しているとは言えない」と述べている、と Tim 氏は話しています。
- チームのコンテキスト：他のデータソースやシステムから流れ込む情報、チーム用に設定されたコンテキストメモリは、常に動的に変わる。
- 外部のエージェント：Sven の範囲外の内部エージェント（203 など）や、今後のエージェントのネットワークが広がるにつれ、組織の外のエージェントが 409 を呼び出す可能性もある。

これらは Sven が制御できないものとして扱います。Sven が制御できるのは、ロールと権限に設定する決定論的（deterministic）なルールと、確率的（probabilistic）な意図の部分です（意図は音声上「intense」と聞こえる箇所で、文脈から intent と解釈しています）。この契約をどう履行させるかが、次の Account ドメインです。

### 5.7 Account：信頼するが検証する（オーバーサイト）

人間の従業員にも、強制する仕組みがないわけではありません。企業には「trust but verify（信頼するが検証する）」があり、ルールに従うことを期待されつつ、それを確かめる仕組みもあります。Tim 氏は、自分の端末に MDM ソフトウェアが入っていて、社内クラウドから特定のものをダウンロードできないこと、SharePoint などで何にアクセスできるかが制御されていることを例に挙げました。エージェントにも同様に、期待どおりにやっているかを見る監視が必要です。

その前提として、**「behaving（行儀よくする）」と「succeeding（成功する）」の違い**を説明しています。

- **Behaving**：権限の範囲。エージェント説明責任というと多くの人が、特定のデータに触れさせない、データに特定の操作をさせない、という話に飛びつくが、それがこちらにあたる。
- **Succeeding**：人間は、触ってはいけないデータベースには触れないようにされると同時に、上司から職務記述書を見ながら「実際に期待どおり、期待される方法で仕事をしているか」を確認される。エージェントも同じ。

評価は単一の指標ではなく **スコアカード**です。

- 権限の観点（authority dimensions）：スコープ内にとどまっているか、許可されたデータだけを承認しているか。
- ロールの観点（role dimensions）：請求書の照合精度、突合にかかる速さ（サイクルタイム）など。成功にあたる。

それぞれの重みづけ（何が重要で、何がそれほどでもないか）は、Assign で行ったロールと権限の定義の一部であり、それを監視で適用して測定します。

**エージェントには「マイクロマネージャー」が必要**だと Tim 氏は述べています。人間にとっての嫌なマイクロマネジメントではなく、エージェントの各ステップを観察し、ロールと権限で定義したことに合致しているかを評価する存在です。具体的には、次のようなものが挙がりました。

- LLM マネージャー、あるいは一般に「モデルマネージャー」
- 外部コンテキストのための「コンテキストマネージャー」
- 結果の「作業成果物（work product）マネージャー」

人間は四半期や年次で評価されますが、それを待つと、4 万件、40 万件、400 万件の判断が手遅れになります。そのため**マシンスピード**で動かす必要があり、Tim 氏は、これらのマネージャーを人間として置いていない点に注意を促しています。

### 5.8 ルールは「チェック」、意図は「判断」

ルールと意図の区別も説明されました。

| 種類 | 性質 | 例 |
| --- | --- | --- |
| ルール（rules） | チェックする。決定論的で、真偽がすぐ言える | 支払いを承認しない、台帳には書き込みだけ行う |
| 意図（intents） | 判断する。確率的な評価になる | 発注書との照合は正しいか。この取引にふさわしいベンダーを選んだか。金額は予算に対して妥当に見えるか |

Tim 氏は、「金額が予算に対して妥当に見えるか」が一番良い例だと述べています。こうした判断の評価が、そのエージェントに対する信頼度（confidence）を決めます。確率的な判断に対しても、監視では合否（pass/fail）が必要なので、**決定論的な等級（grade）を設定**し、それを次のアクションにつなげます。

### 5.9 Account：レコース（是正措置）

最後のステップがレコース（recourse）です。想定の範囲外だと分かったときに取る措置です。人間の場合、上司が観察した結果、問題が小さければ「こうしたほうがよい」と**修正（correction）**を促します。それでも続けば**制限（restriction）**です。例として、システムに入ってはいけないのに入り、データを変更してはいけないのに変更している Tim に対して、読み取り専用のアクセスに制限する、という話をしました。さらに**エスカレーション**として、解雇を言い渡せる上位者に上げる場合もある、という例えです。

エージェントのレコースの大きさは、先の信頼度スコアに応じて決めます。選択肢として挙がったのは次のものです。

- コンテンツの伏せ字（redact）
- 認可の制限
- アクセスの停止（suspend）
- 人間へのエスカレーション
- 繰り返しの違反の場合、運用全体の停止（確認できるまでそのエージェントを止める）

**軽い措置から始め**、違反が繰り返されるなら重くしていきます。個々のトランザクションやタスクだけを見るのではなく、**集計して**見ます。人間が見られるのもそのやり方だからだ、と説明しています。

実装面では、ルールには「警察（cop）」が必要です。Tim 氏は、このフレームワークは方法論に依存しない（methodology agnostic）と断ったうえで、文脈として Guardian agents、AI gateways、guardrails を例に挙げました。人間では遅すぎるため、マシンスピードで動かすべきだというのが主張です。一方、**判断（judgment）にあたるもの**については、責任者である Sven が、ロールと権限を見直して調整し、軽微な問題を時間をかけて直していきます。

## 7. 注意点・発表者の気付き

- **責任者の不在**：エージェントについて、答えられる責任者を名指しできる企業は 10% 未満だと述べています。責任者は役割やチームではなく 1 人の名前を置きます。
- **なりすましではなく委任**：単一ユーザーの資格情報（OAuth）でそのユーザーとして動かすのは、チームメイトとしての扱いではなく、望ましくないという考えです。
- **権限は最小に**：エージェントが他のエージェントを呼ぶ場合、返せる範囲は関係するエージェントの権限の重なり（例では D だけ）に限られます。
- **整合を前提にしない**：モデルの既定の挙動、チームコンテキスト、外部エージェントは、スポンサーが制御できません。
- **behaving と succeeding の両方を見る**：データへのアクセス制御だけでなく、仕事の成果も評価の対象にします。
- **評価の速度**：四半期や年次の評価を待つと、何万、何十万、何百万という判断が手遅れになります。監視はマシンスピードで行い、人間をそのマネージャーにはしません。
- **措置は段階的に**：軽い対応から始め、繰り返しの違反には重くします。
- 発表では、特定の製品や実装手順（ID を保持するレジストリの具体的な製品など）への言及はありません。

## 8. 利用者にとっての利点

発表は製品紹介ではなく考え方の提案のため、導入効果の数値や顧客事例は語られていません。語られた利点は次のとおりです。

- 人間のガバナンスで確立された概念を流用でき、新しい枠組みをゼロから考えなくて済む。
- ID、スポンサー、ロール、権限、監視、レコースというステップで、エージェントごとに責任の所在と成功基準を明確にできる。
- フレームワークは方法論に依存せず（methodology agnostic）、Guardian agents、AI gateways、guardrails など既存の手段と組み合わせられる。
- オープンソースで、自己監査のための **45 の既存の統制項目（controls）** が用意されている。

## 9. まとめ

Tim 氏は、3 つのドメインを「**Assign：すべてのエージェントに名前を付ける／Align：すべての行動に境界を設ける／Account：すべての結果を追跡する**」とまとめ、これがエージェントの説明責任（agent accountability）だと述べています。人間を統治してきた歴史から作ったものを、エージェント向けに調整したもので、ソフトウェアの標準やプロトコルも引き続き適用する必要があります。

始めるなら、まず ID です。「今日、あなたのエージェントに ID を与えてください」というのが登壇者の助言です。

最後に、Tim 氏は QR コードのランディングページと agentaccountabilityframework.org を案内し、原則 6 つとドメイン 3 つだけでなく、組織内でのセルフ監査用に 45 の既存の統制項目があること、フレームワークはオープンソースで、貢献者や、批判的に検討する人を募集していることを述べました。司会者からは、Tim 氏が booth 409 にいると案内されています。
