# THRSP1119 Extend Copilot Studio agents to securely act on enterprise data

## 1. はじめに

このセッションは、**Copilot Studio** のエージェントを、Microsoft の環境（estate）の外にあるエンタープライズデータへ、ガバナンスを効かせたまま到達させる方法を紹介する、CData 社のパートナーセッションです。登壇者は、CData の **Connect AI**（MCP サーバー、AI ゲートウェイ、コンテキストエンジンなどで構成されるプラットフォーム）を使うと、データへのアクセス制御、支出の上限管理、トークン消費の削減、回答精度の向上が同時に狙える、と説明しています。

登壇者は 3 つのことを行います。CData 自身が実施した比較調査（CData Labs の調査）の数値を紹介し、Salesforce、Zendesk、Snowflake をまたぐ「アカウントヘルス」エージェントをライブデモで見せ、最後に顧客事例を紹介します。

このセッションを読むと、Copilot Studio からのデータ接続を MCP でどう広げるか、ゲートウェイやコンテキストエンジン、ツールキットでどこまで絞って制御できるか、発表で示された数値（精度で約 25 ポイント差、コストで 178 倍差、トークン効率で 93%）が何を比較したものなのかが分かります。

## 5. 発表内容の詳細

### 5.1 全体像：Copilot Studio から Microsoft の外のデータへ

登壇者によると、CData は SAP への接続をきっかけに Microsoft のお客様に見つけてもらうことが多い会社です。CRM、ERP、財務、人事、さらにデータウェアハウスやデータレイクなど、幅広い領域のコネクティビティを持っています。

Copilot Studio のエージェントは、Microsoft の環境内では簡単にやり取りできますが、環境の外にあるエンタープライズデータ、しかも種類の違うプラットフォームが混在している状態になると課題が出ます。CData は Copilot Studio の**認定コネクタ**（certified connector）です。Copilot Studio で "CData" を探すと **MCP サーバー**が表示されます。OAuth でその MCP サーバーに認証すると、MCP プラットフォーム経由で **350 以上のコネクタ**を使えると説明されています。

登壇者は、少し複雑だと断りつつ、構成図を次のように説明しています。

| 位置 | 要素 |
| --- | --- |
| 左 | Copilot とエージェント |
| 右 | エンタープライズのデータ環境 |
| 上 | モデル。Connect AI Gateway で任意のモデル（Anthropic、ChatGPT などや、オープンウェイトモデル）にルーティングできる |
| 管理面 | 集中型のガバナンスプレーンによる制御とセキュリティ |
| コンテキスト | コンテキストエンジン。他のプラットフォームのセマンティック定義を取り込んで、エージェントに意味を与える |
| データ層 | 仮想データレイヤー。幅広いコネクティビティがすべて、導入作業なしで最初から MCP 対応（plug and play） |

ガバナンスは「フロントドア」からデータ層・レコード層までかかり、コンテキストエンジンがエージェントのツール呼び出しの判断を効率化することで、トークン効率とコスト効率が得られる、という説明です。

### 5.2 調査 1：精度（約 25 ポイント差）

CData Labs の精度調査では、CData の統合 MCP プラットフォームを、他の MCP プロバイダーと比較しました。比較対象として挙がったのは iPaaS プロバイダー、CRM プロバイダーで、登壇者の記憶では（"I think"）データレイクまたはデータウェアハウスのプロバイダーも含まれていました。結果、CData は**約 25 ポイント**上回ったと説明されています。

理由として、登壇者は MCP のアーキテクチャを挙げます。標準ツールのセットと、スキーマを理解してセマンティックな意味をエージェント層に返すコネクティビティ層により、効率的なツール呼び出しが可能になるためです。他のプロバイダーが精度で劣るのは、複数のフィルタリングのロジック、相関のロジック、フィールドの列挙値（enumeration）の意味の読み取りなどで、すべてが伝わらないからだ、とも述べています。CData はそれらをコネクティビティ層に組み込み、さらに**ソースをまたいで実行するデータ処理エンジン**を持ち、クロスソースの実行を自社のプラットフォームで処理します。調査レポートは、スライドの QR コードか、ブース 5241 で入手できると案内されました。

### 5.3 調査 2：コスト差（178 倍）

2 つ目は「cost spread（コスト差）」の調査で、数字は **178 倍**です。CData の MCP アーキテクチャとデータ処理エンジンを使うと、発話で「Fabo」「Fable」と聞こえるモデル（表記が確定できません）から、**オープンウェイトの Mistral Small** まで下げても、同じ正確な結果が得られたと説明しています。

仕組みは、エージェントに決定論的な方法とツールを提供することです。テストしたのは、次の 3 つのシステムのデータを相関させる必要がある質問です。

- Salesforce のアカウントと商談データ
- Zendesk のチケット（ITSM として説明）
- Snowflake から入ってくるテレメトリ

アカウントのヘルスに関する質問として、登壇者の記憶では「優先度が高く、ヘルスが悪化し、利用傾向が下がっているアカウントを見せて」というプロンプトでテストしました。

そのために、プラットフォーム上で **derived views（派生ビュー）** と呼ぶ事前結合のビューを作り、データ処理エンジンが Salesforce、Zendesk、Snowflake をまたいで結合できるようにしました。加えて、3 つのシステムにまたがるカスタムツールを MCP プラットフォームに追加しました。これにより、Mistral Small でも同じプロンプトに正確に答えられ、Fable と聞こえるモデルを使う場合と比べて 178 倍のコスト差が出たという説明です。登壇者は、このようにアーキテクチャ上で引けるレバーが多数あると述べています。

### 5.4 調査 3：トークン最適化（93%）

3 つ目は、178 倍のコスト差に対する「確率的（probabilistic）」な対となる調査です。178 倍の調査は決定論的な手法を導入して、安価なモデルを選んでコスト差を出しました。今回は**モデルは同じまま**で、トークンの最適化がテーマです。コンテキストを与え、モデルがどの MCP の経路を取るかを自分で選ぶ状況で、CData の MCP プラットフォームとコンテキストエンジンを、他の MCP サーバーと比較しました。同じコンテキストを与えたところ、**93% のトークン効率**になったと説明しています。

決定論から確率論までの幅広い範囲で、トークンを節約するアーキテクチャ上のレバーを提供できるため、トークン単価を下げるだけでなく、トークンの使用量そのものも減らせる、というのが登壇者の整理です。

### 5.5 CData の強み：実績とガバナンス

CData のエンタープライズ向け MCP コネクティビティは、**10 年以上**にわたってコネクタの中で鍛えられてきたもので、Google や Palantir など主要な企業に信頼されている、と述べられています。Microsoft とのパートナーシップもその証拠だと話しています。

ガバナンスについては、「入り口からレコードレベルまで」を所有して提供する考えです。登壇者は、これを「プロンプトの一生」として次のように説明します。

1. ユーザーがエージェントに質問する。
2. CData のプラットフォームにユーザーの ID があり、エージェントから MCP プラットフォームへ OAuth でつながる。
3. その資格情報で、どの接続にアクセスできるかを CData が把握している。
4. これにより、プロンプトから、どんなレスポンスが返り、どのデータにアクセスできるかまでをガバナンスできる。

### 5.6 AI ゲートウェイ（LLM ゲートウェイ）

アーキテクチャの上位、入り口に近い部分がゲートウェイです。誰もが支出に上限を設け、どの事業部門やユーザー群がどれだけ使っているかを見たく、さらにリクエストあたりのコスト効率も上げたい、という前提です。

登壇者は、デモと同じアカウントヘルスの例で、次のように設定したと説明しています。

- LLM プロバイダーに紐づけた「アカウントヘルス」プロジェクトを作成する。
- 許可するモデルは **Sonnet と Opus** の 2 つ。
- プロンプト攻撃に対するガードレールを入れる。
- 月間の支出を追跡し、例えば**月 1,000 ドル**で上限をかける。対象は、アカウントヘルスに関わるユーザー（例えばカスタマーエクスペリエンス担当）。

機能面では次のように語られています。

- **トークン予算**：暴走シナリオ（runaway）へのガードレールとして、トークン数、または一定期間（分、時間、日など）のリクエスト数にレート制限をかけられる。
- **プロジェクト単位の支出上限**：プロジェクト（＝ユーザー層）ごとに異なる上限を割り当てられる。
- **予算を考慮したルーティング**（budget-aware routing）。
- **可視化**：ダッシュボードとアラートがあり、すべてのモデルのコストが取り込まれるため、どんなクエリでユーザーがどれだけ使うかを把握できる。

### 5.7 デモの前提：アカウントヘルスエージェント

デモの前提として、アカウントヘルスエージェントは **Copilot Studio のエージェント**で、Salesforce、Zendesk、Snowflake の複数のデータソースとやり取りし、エンドツーエンドでガバナンスされています。プラットフォームに作成した**アカウントヘルス用語集（glossary）** に、Copilot Studio エージェントが search context という MCP ツールでアクセスします。さらに、エージェントに公開するのは**スコープを絞ったツールキット**で、関与する範囲を限定しており、これもコスト効率とトークン効率に効く要素だと説明しています。

### 5.8 顧客事例：Annaqua

登壇者は短い事例として、Annaqua（音声認識の都合で表記が確定できません）が、「government AI agent」（発話のまま。governed の意味かは確定できません）を、登壇者の記憶では（"I believe"）Claude と Copilot Studio で展開した例を挙げています。多様なユーザーが 2 つの異なる AI エージェントにアクセスし、**5 つの異なるシステム**のエンタープライズデータへの安全なアクセスのために、セキュリティと集中型のガバナンス基盤が求められました。結果、このユースケースで **POC から本番まで約 6〜8 週間**で到達し、CIO はプラットフォームの大きなファンになっている、と述べられています。

## 6. デモ・手順

このセッションでは、画面を使った**ライブデモ**が行われています（"I'll do a live demo"、"let's get into the demo here" などの発話があります）。画面の細部は音声からは確認できず、以下は語られた内容の範囲です。

1. **従来のやり方の確認**：Power BI のビューを見せる。ダッシュボードと Zendesk のチケット、セマンティック定義とデータモデルがある。これは従来方式で Connect AI 上にも置ける。ここから、Copilot Studio のエージェントが Connect AI を通じてクロスソースのデータセットとやり取りする方法を、ゲートウェイ、コンテキストエンジン、MCP コネクティビティを使って見せる、と説明。
2. **コンテキストエンジン**：コンテキストグラフの画面で、外部コンテキストを追加できる。既存の接続を選べる。デモでは Snowflake のコンテキストを示す。dbt や Power BI の PBIX ファイルも取り込める。ここではウィザード形式で、Snowflake にあるデータモデル全体のコンテキストを自動生成し、Markdown ファイルとして作られる。必要に応じて編集できる。
3. **ツールキット**：エージェントに公開する範囲（サーフェスエリア）を制御する。このデモでは、標準ツールと、アカウントヘルスエージェント専用に定義したカスタムツールに絞る。カスタムツールの 1 つが書き込み用のツール（発話では "right tool" と聞こえます）で、アカウントヘルスが閾値を下回るときに Salesforce にタスクを作成する。
4. **仮想スキーマ**：ツールキットに取り込まれており、データモデルを制御できる。アクセスを少数のオブジェクト（Salesforce のアカウントと商談、Snowflake のテレメトリなど）に限定している。このスコープに対して **CRUD レベルの権限**を管理できる。
5. **ログ**：エージェント層から MCP プラットフォーム、ゲートウェイ層まで、AI のやり取りを追跡・監査するためのログを確認できる。SIEM 連携があり、SIEM プラットフォームへストリーミングできる。
6. **Copilot Studio のエージェント**：公開されているツールは、Connect AI のツールキットに含めたものと同じ。アカウントヘルススコアは **37** で、閾値の **40** を下回っている。そのため、顧客体験（カスタマーエクスペリエンス）の担当者が、アカウントオーナーおよび顧客側の相手先とフォローアップするための Salesforce タスクを作成しようとする。スコアが 37 だった理由の全体像も表示される。
7. エージェントがタスク作成の**許可を求め**、「yes」と答えると、Salesforce 内にタスクが正常に作成される。

登壇者はこれを、複数ソースをまたぐエンドツーエンドのシナリオとして整理しています。3 つのシステムをまたいだ読み取り、コンテキストによるエージェントへの意味づけ、下流のデータオブジェクトへのガバナンスされたアクセス、そして Salesforce へのスコープが絞られた**ガバナンスされた書き込み**です。すべての呼び出しがログに残り、SIEM に流せます。これにより、エージェント層から MCP ツール呼び出しまでの**フルスタックのトレーサビリティ**（どのユーザーがどのシステムをどのツール呼び出しで使ったか、複数システムのどのレコードにどんなアクセスを使ったか）が得られると述べています。

## 7. 注意点・発表者の気付き

- ガバナンスは、エージェント層だけでは不十分で、データ層まで延ばす必要がある、というのが前提として語られています。
- 他の MCP プロバイダーで精度が落ちる理由として、複数のフィルタリング、相関、列挙値の意味の読み取りが、プロバイダーによっては伝わらないことが挙げられています。
- 精度・コスト・トークンの数値は、CData Labs が実施した比較調査の結果です。詳細は QR コードまたはブースで入手するよう案内されており、発表の中では、調査の実施条件の詳細までは語られていません。
- ライブデモは、事前に用意されたツールキット、仮想スキーマ（アクセスするオブジェクトを少数に限定）、用語集、コンテキストを組み合わせたもので、書き込みも許可確認を経て行われます。
- エンタープライズのコンテキストを、特定のプラットフォームの中に個別に設定してサイロ化すると、全ユーザーが使えなくなる。そのため、コンテキストを集中的に置ける場所があることを、登壇者は強みとして挙げています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **精度**：他の MCP プロバイダーとの比較で、約 25 ポイント上回った。
- **コスト**：決定論的な手法（派生ビュー、カスタムツール）で、Mistral Small でも同じ正確な結果を得られ、178 倍のコスト差が出た。
- **トークン**：コンテキストエンジンを使い、モデルが経路を選ぶ状況で、93% のトークン効率を実現した。
- **ガバナンスと可視化**：入り口からレコードレベルまでの制御、SIEM へのストリーミング、フルスタックのトレーサビリティ、支出の上限・ダッシュボード・アラート。
- **導入のしやすさ**：350 以上のコネクタが MCP 対応で、導入作業なしで plug and play。
- **事例**：Annaqua では、5 つのシステムへの安全なアクセスを、POC から本番まで約 6〜8 週間で実現した。

## 9. まとめ

CData は、Copilot Studio のエージェントを、Microsoft の外にあるエンタープライズデータへ MCP で接続し、データ層までガバナンスを広げる方法を示しました。認定コネクタと 350 以上のコネクタ、ゲートウェイ、コンテキストエンジン、ツールキットと仮想スキーマという仕組みで、精度（約 25 ポイント）、コスト（178 倍）、トークン効率（93%）の改善が得られると説明されています。

登壇者が挙げた持ち帰りポイントは、AI を scrappy にできること、ゲートウェイでトークンの支出と使用量を減らせること、そしてコンテキストエンジンが強力なアーキテクチャ上のレバーであることです。
