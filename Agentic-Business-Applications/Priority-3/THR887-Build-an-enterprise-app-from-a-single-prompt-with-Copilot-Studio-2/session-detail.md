# THR887 Build an enterprise app from a single prompt with Copilot Studio

## 1. はじめに

このセッションは、**Copilot Managed Runtime（CMR）アプリ**を Copilot Studio で作る方法を、約 25 分のデモ中心で紹介するものです。1 つのプロンプトから業務アプリを作り、さらにそのアプリ内にエージェントを持たせ、Dataverse のテーブルを作り、Cowork で作ったスキルを再利用してドキュメントまで生成するところまでを見せます。

登壇者は、AI でアプリのプロトタイプを作ること自体はすでに珍しくなく、難しいのは「プロトタイプから、会社として本番で運用できるものにすること」だと述べています。CMR 上で作ったアプリは、最初から Microsoft がホストするインフラ、Entra サインイン、管理者が決めたコネクタとデータポリシーの下で動くため、本番化は「作り直し」ではなく「すでにあるアプリに厳密さを足す作業」になる、というのが中心の主張です。

発表の序盤で、CMR アプリが前日に一般提供（GA）になったことが告げられます。このセッションを読むと、次のことが分かります。

- CMR アプリの 3 つの作成入口（Cowork、Copilot Studio、CLI と SDK）の使い分けの考え方
- CMR アプリが中身として何で構成されているか
- 1 つのプロンプトから、アプリ・インライン エージェント・Dataverse テーブル・ドキュメントを生成するデモの流れ
- GA 後に取り組んでいる機能（共同編集、共同オーナーなど）

## 5. 発表内容の詳細

### 5.1 問題提起：プロトタイプから「業務で動くもの」へ

登壇者は、多くの人がすでに、プロンプトを書いてエージェントに送ると数分でアプリができる体験をしていると前置きします。修正を指示して何度も改善でき、コードは「探索するには安価」になったため、PRDを何時間もかけて書いてエンジニアに渡す必要はなくなったと説明しています。

そのうえで、難しいのはもはやコードを書くことではなく、**最初のプロトタイプから、ビジネスが実際にその上で動かせるものへ到達すること**だと述べます。

### 5.2 CMR アプリの GA と 3 つの入口

CMR で生成・ホストされるアプリは、次の特徴を持つと説明されました。

- Microsoft がホストするインフラ上で動く
- Entra サインインに対応する
- SharePoint や Dataverse など、ガバナンスされた実データとつながる
- 管理者が組織向けに設定したコネクタとデータポリシーが、最初の 1 分から適用される

登壇者によると、CMR アプリは前日（発言では「as of yesterday」）にプレビューを終え、**一般提供（GA）**になりました。登壇者のチームがこの 6 か月ほど力を入れてきたものだと述べています。Cowork、Copilot Studio、CLI と SDK のどこで作ったアプリも、最初から本番に使える状態だという位置づけです。

作成の入口は 3 つあります。ただし登壇者は、「3 つの別製品から選ぶのではない」と強調します。土台は同じ Copilot Managed Runtime で、同じ app skill を使い、入口が 3 つあるだけだという説明です。たとえとして、家には玄関、ガレージ、裏口があるが、どれから入っても同じ家に着く、と語っています。

「どこで作ればよいか」への答えは、「作る人がいる場所で出会う（meet the makers where they are）」というチームの目標でした。

| 入口 | 向いている場面（発表での説明） |
| --- | --- |
| Copilot Cowork | すでに Cowork のエージェントとプロジェクトの相談をしていて、メール、ファイル、会議、チームのメッセージなど Cowork が組織について知っているコンテキストをアプリに反映したいとき |
| Copilot Studio | すでに Dataverse、エージェント、ワークフローで作っているとき。業務プロセスが実データ、エージェント、ワークフローの上で動くアプリなら、必要なものがすでに揃っているので Copilot Studio を選ぶ（今回のデモの場所） |
| CLI と SDK | プロの開発者で、コードとリポジトリを完全に自分で制御したいとき。生成されたコードを見て自分で変更したい場合 |

どの入口を選んでも、下にあるのは同じアプリで、同じレベルのガバナンスと制御がかかり、すべて Git に裏付けられます。そのため、ある入口で作り始めて、別の入口で続きを引き継ぐこともできると説明されています。

Cowork の利用例として、登壇者自身の体験が語られました。担当していた製品の提供終了にあたり、Microsoft のアカウントマネージャー 350 人以上にメールを送る必要があり、誰が確認の返信をくれたかを手作業で確認するのが大変だったそうです。Cowork はメールの下書きを生成したうえで、追跡用のアプリも作りました。このアプリは、2 時間ごとに受信トレイを確認して更新し、チームやアカウントマネージャーと共有して、どの顧客が通知を確認したかを全員が把握できるようにしています。

### 5.3 CMR アプリの中身

「ボンネットを開けて中を見る」という形で、CMR アプリの実体が説明されました。

- モックアップでも独自形式のファイルでもなく、**Git リポジトリ内の React と TypeScript による本物の Web アプリ**で、開発者が開いて拡張できる
- **SDK** が Microsoft 365 とつなぐ。サインイン、コネクタ、Work IQ がすぐ使え、そのまま動く
- アプリが作られた時点からガバナンスがかかり、DLP、共有、コネクタのルールが IT 管理者の設定どおりに自動適用される

1 つのアプリに対して、関わる人は 3 種類います。作る人（maker。現在 3 つの方法で作れる）、ガバナンスする管理者、アプリを開く利用者です。

### 5.4 デモの前提：1 つのプロンプトから得られる 4 つのもの

デモに入る前に、登壇者は見どころを 4 つに整理しました。

1. **業務アプリ**：自然言語から作られる、動作するビジネスアプリ
2. **アプリ内のエージェント**：サイドに置くチャットボットではなく、アプリの内側に組み込まれた AI。新しい **agent node connector** 経由でつながる
3. **Dataverse plugin**（新機能）：新しい Dataverse テーブルを作れるため、手作業でテーブルを作らなくてよい。SharePoint を使えるなら、それでもよい
4. **再利用できるスキル**：Cowork にあるスキルを Copilot Studio から呼び出せる

注意点として、2 番目の agent node と 3 番目の plugin は**ロールアウト中で、GA には含まれていません**。デモで見せるのは、Microsoft IT（自社テナント）向けに内部で使える状態のもので、十分なテストを経たあと順次展開されると説明されています。

### 5.5 アプリのプロンプトと生成

デモの詳細は 6 章に手順としてまとめます。ここでは、プロンプトの内容を整理します。

登壇者のチームでは、CMR アプリがパブリックプレビューの 3〜4 週間、コミュニティから多くのフィードバックと反響があり、追跡が難しくなっていました。毎朝 LinkedIn、YouTube、動画のコメント、ブログ、Reddit、Twitter を見て回る作業に多くの時間がかかっていました。そこで「CMR アプリのフィードバックを集めるのに、自分で CMR アプリを作る以上の方法はない」と考え、約 3 週間前に実際に作ったそうです。入力したプロンプトの内容は次のとおりです。

- CMR アプリのカスタマーフィードバックを集めるアプリを作る
- すべてのコミュニティフォーラム、ソーシャルメディア、ブログを検索する**インライン エージェント**を付ける
- エージェントはフィードバックをテーマ別にグルーピングし、新しい投稿、報告されたバグ（登壇者が特に重要と述べた項目）、センチメントの傾向（positive、trending、neutral、negative）を示す
- Dataverse plugin を使い、**コミュニティフィードバック、フィードバックソース、プロダクトエリア**の 3 テーブルを作り、エージェントが見つけたデータを保存して傾向を追えるようにする
- Cowork にある app skill を使って、このアプリのドキュメントを生成する（「whack app」のように呼び出せると説明。音声認識の都合で表記が確定できません）

登壇者はこれを 4 点に再確認しています。フィードバックを集めて保存し、チームと共有できるアプリ、テーマ別に分類するインライン エージェント、新規の Dataverse テーブル 3 つ、Cowork で作ったアプリドキュメント用スキルの再利用です。

### 5.6 GA 後に取り組んでいること

デモのあと、残り時間で「GA の後に取り組んでいること」が紹介されました。パブリックプレビューのお客様から特に多く寄せられた要望です。

| 項目 | 説明 |
| --- | --- |
| 共同編集（co-authoring） | チームメイトが同じセッションで同時に、同じアプリを編集できるようにする |
| 共同オーナー（co-owners） | 現在アプリのオーナーは作成者 1 人だけで、作成者が不在になるとアプリが事実上失われてしまう。アプリの継続性のため、共同オーナーを割り当てられるようにする |
| バージョン履歴 | ロールバックの方法。現在は CLI ではすでに可能だが、Copilot Studio、Cowork、ほかのサービスの UX に出す作業が必要 |
| ALM | dev・test から prod へアプリを移す仕組みに取り組んでいる。非常によく聞かれる質問だと述べている |
| GitHub Enterprise | 管理者から、自社のリポジトリにホストしたいという要望があり、対応を進めている |
| 環境の選択 | 現在、CMR アプリは既定で個人の開発者環境（PDE）に作られる。PDE 以外の指定のカスタム環境でも作れるように変更を進めている |

## 6. デモ・手順

このセッションにはライブのデモがあります。ただし、画面上の操作は音声のナレーションで語られた範囲しか分かりません。また、プロンプトの送信後の生成はその場で完走せず、事前に生成したアプリに切り替えて説明しています。

### 6.1 Copilot Studio でアプリを作り始める

1. Copilot Studio のホーム画面を開く。通常はここでエージェントやワークフローを作る場所だが、今回は**3 つ目のタイル**でアプリを作る。
2. このタイルには「preview」の表記がある。GA に伴って表記を外す作業がロールアウト中で、このテナントではまだ反映されていないため、**登壇者は、プレビューの表示は無視してほしい、CMR アプリはすでに GA だと説明**している。
3. 作りたいアプリのシナリオ（5.5 のフィードバック収集アプリ）と、画面に入力済みのプロンプトを説明し、送信（submit）する。
4. 生成を待つ間にプロンプトの 4 つの狙いを説明するが、途中で「ログアウトされたようだ」と気づき、**事前に生成しておいたアプリに切り替える。** 会場の Wi-Fi が弱く、それ以前にホットスポットへ切り替えていたことも話している。

### 6.2 事前生成アプリ「Community Pulse」の画面（Copilot Studio のアプリ画面）

1. 左側に、エージェントとのチャット履歴がある。元のプロンプトも含まれ、30 日、60 日、90 日後に戻ってきても、なぜその判断をしたのか、このアプリが何のためのものかを読み返せる。更新を続けたいときも、このチャットで指示する。
2. 右側がアプリのインタラクティブなプレビューで、エンドユーザーの体験を確認できる。
3. **コードビュー**に切り替えると、アプリの下にあるコードが見られる。プロの開発者向けの画面だと説明している。
4. 上部にある**デバイスプレビューの切り替え**で、アプリのフォームファクターが確認できる。タブレットや小さいモバイル端末からの利用でも動作すると述べている。
5. アプリ名をクリックすると、データ、接続、アプリ設定が見られる。
   - **データ**：プロンプトで依頼した 3 つのテーブル（community feedback、feedback source、product area など）が並び、これらは agent が Dataverse plugin を使って作った。
   - **接続（connections）**：次のコネクタが並ぶ。
     - Office 365 Users：アプリを開いたユーザーを識別し、あいさつ表示に使う（登壇者本人と、チームメイトとで名前が変わる）
     - GitHub：登壇者のチームのリポジトリに接続（発言は「Teams repo」と聞こえます）
     - エージェント：最初のプロンプトで作るよう依頼したエージェント
     - Microsoft Dataverse：テーブルを作成したコネクタ
6. チャットを折りたたみ、アプリ本体を広く表示する。このアプリは生成後に数ターンのやり取りで機能を足している、と説明。

### 6.3 生成されたアプリの内容

1. 画面には、今日のポーリング結果として、**新規投稿 45 件、うち 15 件がトリアージ待ち、約 77% が positive** と表示されている。
2. エージェントが 5 つのテーマに分類している。挙がったのは、Copilot Studio のアプリ体験、プレーヤーのホスティング体験、ドキュメント、アプリ内の AI などで、これらが上位のテーマとのこと（5 つのうち、聞き取れたもののみ記載）。
3. 下にスクロールして各バケットをクリックすると、そのテーマに集約されたフィードバックの一覧が見られる。例として「Copilot Studio experience」を開き、ソース、影響するプロダクトエリア、重大度、投稿者、元のソースでの反応数（engagement）が確認できる。チームがいつでも見返せる情報だと述べている。
4. 「untriaged（未トリアージ）」のフィードバックの一覧を開く。投稿された時期と重大度が表示され、多くはまだ識別されていない。GA 後は 15 件よりはるかに多くなるため、エージェントにトリアージさせたいという流れ。

### 6.4 アプリ内エージェントの利用

1. 「Ask the agent」ボタンでチャットパネルを開く。
2. 「今日のコミュニティのポーリングを要約して」と依頼する。登壇者は、毎朝のスタンドアップで 15 件を全部読む時間がないためと説明している。エージェントは、まだトリアージされていない新しいデータだけを使って要約を返し、パブリックプレビューへの強い熱意があること、エージェントとのやりとりや応答性に改善の余地があることなどを示した。登壇者は、これをそのまま Teams のチャネルに貼って、顧客の声として共有できると述べている。
3. このアプリは GitHub リポジトリにつながっているため、**「報告されたバグについて GitHub に Issue を作って」**と依頼する。エージェントは、その日に報告されたバグについて Issue の下書きを提示した（多くはパフォーマンスと信頼性に関するもの）。
4. 登壇者は、下書きに go を出せばエージェントが GitHub に Issue を作り始める、と説明している。
5. 登壇者は、複数のフォーラムやブログを巡ってその日のセンチメントを調べる作業や、GitHub に Issue を手で作ってチームメンバーをタグ付けする作業が不要になり、このアプリで多くの時間を節約できた、と述べている。

### 6.5 公開・共有とドキュメント

1. 準備ができたら **Publish** で公開し、チームメンバーと共有できる、と説明している。「Emma と共有する」と話し、リンクを共有すると相手にメールが届き、自動的にアプリを使えるようになるという。
2. 最初のプロンプトで依頼した**アプリドキュメント**が、Cowork にあるアプリ用スキルを使って、**PDF として一式生成**されている。登壇者の操作は、プロンプトに「app documentation」と書いたことだけだったと話している。Cowork で作ったスキルが Copilot Studio で再利用でき、「下は同じプラットフォームだから」動くという説明。
3. アプリのリンクと PDF のリンクをチームのチャネルに共有し、「アプリとドキュメントを作った。これ以上質問しないで」と添えて渡せる、と冗談めかして話している。アプリが進化したら、エージェントにこのファイルを再生成・更新させることもできる。

### 6.6 管理者から見たガバナンス

1. Microsoft 365 admin center を開き、**Apps** の下の**すべてのアプリ**を表示する。これはこのテナントで作られたすべてのアプリの一覧。
2. 自分のアプリ「CMR community pulse」を検索する。
3. 管理者には、このテナントで作られたあらゆるアプリについて、使われているコネクタ、使われ方（頻度）、作成者、オーナーなどの透明性があると説明している。時間が足りなくなったため、この部分は急いで進めている。

デモのまとめとして登壇者は、Cowork や Copilot Studio でアプリを作れること、Copilot Studio がアプリの中に住むエージェントも作れること、Cowork の再利用可能なスキルでドキュメントを生成できること、Dataverse plugin で新しいテーブルを作れることを挙げています。

## 7. 注意点・発表者の気付き

- **ロールアウト状況**：agent node connector と Dataverse plugin は GA には含まれておらず、ロールアウト中。デモは Microsoft IT の自社テナントで使える状態のもの。
- **プレビュー表記**：Copilot Studio のタイルにある「preview」の表記は、GA に伴い削除作業が進行中で、デモのテナントではまだ残っている。
- **オーナーが 1 人だけ**：現時点で、アプリのオーナーは作成者のみ。登壇者は「明日バスにひかれたり、会社を辞めたりしたらアプリは事実上なくなる」と例えて、共同オーナーの必要性を語っている。
- **作成環境**：CMR アプリは既定で個人の開発者環境で作られ、他のカスタム環境には変更を準備中。
- **ロールバック**：バージョン履歴からのロールバックは、現状は CLI で可能。Copilot Studio、Cowork などの UX にはまだ出ていない。
- **生成物は一度で完成とは限らない**：デモのアプリは、生成後に数ターンのやり取りで機能を追加している。
- **ライブ生成は完走していない**：プロンプト送信後、登壇者が「ログアウトされたようだ」と話して、事前生成のアプリに切り替えています。会場の Wi-Fi が弱く、途中でホットスポットに切り替えたことも話していますが、ログアウトとの因果関係は語られていません。
- **ALM**（dev・test から prod への移行）は「取り組み中」の段階で、提供済みとは語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **本番化の手間が小さい**：vibe coding したプロトタイプを書き直さず、すでにあるアプリに厳密さ（ガバナンス）を足すだけで本番に近づけられる。
- **管理者がコントロールできる**：DLP、共有、コネクタのルールが IT 管理者の設定どおり最初から適用され、管理者は Microsoft 365 admin center で、すべてのアプリとコネクタ、利用頻度、作成者、オーナーを確認できる。
- **入口を選べる**：Cowork、Copilot Studio、CLI と SDK のどこで始めても同じアプリで、Git に裏付けられているため、途中で別の入口に乗り換えられる。
- **開発者が中身を触れる**：生成物は React と TypeScript の Git リポジトリ内の本物の Web アプリで、コードビューや CLI で読んで拡張できる。
- **業務の手作業が減る**：登壇者自身の事例として、コミュニティの巡回、センチメントの把握、GitHub Issue の起票、ドキュメント作成の手間が減った（Issue はエージェントが下書きを提示し、登壇者が承認する流れ）。
- **スキルを再利用できる**：Cowork のスキルを Copilot Studio で使える。

## 9. まとめ

CMR アプリは前日に GA となり、Cowork、Copilot Studio、CLI と SDK のどこから作っても、同じ app skill、同じ Git リポジトリ、同じガバナンスに行き着きます。デモでは、1 つのプロンプトから、コミュニティのフィードバックを集める「Community Pulse」アプリ、アプリ内のエージェント、3 つの Dataverse テーブル、Cowork のスキルによる PDF ドキュメントが得られ、管理者は Microsoft 365 admin center でそのアプリを確認できることが示されました。

agent node connector と Dataverse plugin はロールアウト中で、共同編集、共同オーナー、バージョン履歴の UX、ALM、GitHub Enterprise でのホスト、環境の選択は GA 後の取り組みとして挙げられています。詳細はドキュメントのリンクと、エキスパートブースで確認できます。
