## 5. 発表内容の詳細

### 5.1 Joule Work とは

Joule Work は、今年の SAP Sapphire で発表された、SAP の中心的な AI ワークスペースです。利用者は達成したいことを自然言語で説明し、Joule Assistants、Joule Agents、Joule Studio がビジネスコンテキストに基づいて、質問への回答、ワークフローの実行、ソリューションの構築を行い、SAP と SAP 以外のシステムをつなぎます。すべて SAP の権限とコントロールの範囲内で動きます。

SAP が示す差別化要素は 3 つです。

1. **プロセスと業界の知識**：業務の動き方を理解していない AI は一般的な答えしか返さない。SAP の知識は何十年分の業務アプリケーションにエンコードされており、利用者が説明する前からプロセスを知っている。
2. **意味的に豊かなビジネスデータ**：企業のデータは分断され、一貫性がなく、つなぎにくい。Joule Work は、SAP Knowledge Graph により、企業全体にまたがる統一された文脈つきのデータに基づく。
3. **エンタープライズ級のデータガバナンス**：AI が提案から実行に移るとき、統制は不可欠になる。Joule Work は、エージェント AI のライフサイクル全体を標準でセキュアに管理し、自律性が説明責任を犠牲にしないようにする。

構成要素としては、エージェントを調整し、コンテキストを管理し、すべてのアクションが根拠づけられ統制されるようにする**オーケストレーションエンジン**が中心にあります（トランスクリプトでは "industry legion, agentic thinking orchestration engine" と聞こえ、正確な名称は音声認識の都合で確定できません）。**SAP Agent Gateway** は、SAP のエージェント、SAP 以外のエージェント、カスタムエージェントをつなぎ、あらゆるやり取りに一貫したガバナンス、認可、可観測性を与えるセキュアなレイヤーです。

これらの根拠となるのが **SAP Knowledge Graph** で、**700 万のフィールド、50 万のテーブル、5 万の公開 API、400 のデータ製品**を対象にしているとのことです。SAP Business Data Cloud と SAP Knowledge Graph は「補完的に設計されている」とされ、前者がエージェントに信頼できるデータへのアクセスを、後者がそのデータの意味の理解を与えます。これにより、Joule Work は SAP と SAP 以外にまたがる環境で、正確な回答と高度なワークフローの確実なオーケストレーションを行えると説明されました。

### 5.2 AI interoperability の 3 つの方法

発表者は、Joule Work が AI の相互運用を実現する方法を順に説明しています（Lorato 氏が「1 つ目はオープン標準とクロスプラットフォームのエージェント」と述べ、のちに Chris 氏が「次の方法」「もう 1 つの方法」としてサードパーティ連携と action bar を続けています）。

1. **オープン標準とクロスプラットフォームのエージェント**：マルチベンダー環境で SAP と SAP 以外のアプリをつなぐ。Microsoft 365 Copilot との統合により、アプリを切り替えずに SAP と Microsoft のデータや機能を組み合わせられる。
2. **サードパーティのエージェント連携**：A2A と SAP Agent Gateway による（5.6、5.7）。
3. **Joule action bar**：サードパーティの Web アプリが API、MCP、A2A でのアクセスを許さない場合に、WalkMe の技術で画面上のコンテキストを取得し、利用者が適切なエージェントを呼び出して案内・自動化できるようにする（5.8）。

### 5.3 Web 版の機能

Joule Work は、**Web、モバイル、デスクトップ**の 3 つの形態で提供されています。このセッションは、そのうち Web とデスクトップの 2 つを取り上げます。Web 版には、Joule Studio への容易なアクセス、個別のアプリを超えたエージェント主導の作業、断片化したワークフローでのコンテキスト切り替えや手作業の削減があります。

主な機能は次の 3 つです。

| 機能 | 説明 |
| --- | --- |
| Conversations | 意思決定を磨く場。ビジネスデータに基づく正確な回答が得られる（インターネット上の一般的なモデルの答えではない） |
| Spaces | 実行の場。洞察、アプリ、エージェントを集めた動的な空間で、各ステップを手作業で管理することなく、あらゆる業務領域でエンドツーエンドのワークフローを実行する |
| Develop | 拡張の場。Joule Studio で、自社固有のニーズに合わせたカスタムエージェントやワークフローを作り、企業全体につなぐ |

Web 版では Joule Assistants と Joule Agents にもネイティブにアクセスでき、ここで Microsoft Copilot との双方向統合が活きる、と説明されました。

### 5.4 Microsoft 365 Copilot との双方向統合

SAP と Microsoft は、コンテキスト切り替えが業務の摩擦になっているという認識から、**2023 年**に共同顧客向けの解決策づくりで協業を始めました。**2025 年 12 月**に、完全な双方向の Joule と Copilot の統合を開始し、**現在は一般提供（GA）**です。

- **Microsoft 側から Joule へ**：セットアップ後、利用者は Teams または Copilot Chat から Joule にアクセスできる。例として、経理担当が最新の発注書のステータスや請求書の詳細を見たり、Joule の紛争解決（dispute resolution）エージェントを Teams から直接起動したりできる。購買マネージャーが Microsoft 365 Copilot Chat でサプライヤーの最新情報を得る例も挙げられた。
- **Joule Work から Microsoft へ**：Joule Work の利用者が M365 のデータを検索できる。検索対象はメールと Teams メッセージ、会議、同僚や人物情報、OneDrive と SharePoint のファイル。

**近日対応予定**として、Microsoft の Work IQ の **MCP 版**に移行し、Joule 内の Copilot 体験を検索だけにとどまらないものにすることが挙げられました。利用者は、メール送信、Teams メッセージ送信、会議への返信、会議の送信、SAP データに基づくファイル作成といったアクションまで実行できるようになるとの説明です。時期は「近い将来」とのみ述べられています。

### 5.5 Joule Work Desktop

一部の組織では、ローカルファイルを完全にクラウド型の AI ソリューションにアップロードすることが選択肢にならず、機密情報が露出するセキュリティとコンプライアンスのリスクがあります。**Joule Work Desktop** は、ローカルファイルへのアクセスと、利用者のデスクトップ上のアプリとのやり取りを、セキュアでコンプライアンスに沿った形で提供します。単なる汎用のオープンソリューションではなく、利用者のビジネスコンテキストに根ざした回答を、セキュアでガバナンスされた形で返すという説明です。

Web 版との違いは次のとおりです。

- Joule Studio は使えないが、**Joule Conversations と Spaces** は使える。
- 外部の **MCP サーバー**に接続して体験をカスタマイズでき、アプリを切り替えずにワークフローを完了できる。
- M365 のデータ（メール、予定表、メッセージ、OneDrive と SharePoint のファイル）への**一方向の接続**がある。
- SAP ビジネスアプリケーションへのネイティブ接続を持ち、Joule Assistants と Joule Agents を使える。ローカルデバイスにも接続し、必要に応じてライブの SAP データやローカルファイルでワークフローを完了できる。

デスクトップ版を作った理由として、前述のセキュリティ・コンプライアンスの懸念に加え、Web アプリの制約を超える 3 つが挙げられました。

1. ブラウザは「壁に囲まれた庭」にあり、個別のファイルアップロードごとに明示的な許可を与えない限り、フォルダや開いているファイルにアクセスできない（発話は "browser folders or open files" と聞こえ、正確な意図は音声認識の都合で確定できません）。
2. Web アプリはデスクトップソフトウェアを制御できないが、Joule Work Desktop はできる。
3. データとプライバシーの懸念。デスクトップ版では、すべてのデータが利用者の管理下に置かれる。

### 5.6 サードパーティのエージェント連携（A2A）

Microsoft と SAP 以外のソリューションもある複雑な環境（マルチベンダー環境）では、AI エージェントが接続・通信・協調する共通の方法が必要だと発表者は説明しています。SAP は、エージェント間通信の基盤として **A2A（Agent to Agent）プロトコル**を使っています。エージェントが互いを発見し、能力を記述し、タスクを交換できるもので、プラットフォーム全体のエージェント通信の土台として使用しているとのことです。

**SAP Agent Gateway** は、SAP とサードパーティのエージェントをつなぐ、ガバナンスされた単一の接続点です。AI を企業全体で自信を持って拡大するためのセキュリティ、ガバナンス、ポリシー制御を提供します。

### 5.7 Agent Gateway によるガバナンスと Human in the loop

Agent Gateway は、2 つの補完的な制御で自律的なワークフローを統制します。

**オンボーディング時（設計時）**

- 組織の SAP 管理者が、エージェントが到達できるシステムを決めるガバナンスポリシーを定義する。
- エージェントが「**フォーメーション（formation）**」に参加すると、そのフォーメーション内の他のシステムと通信する認可を得る。これは SAP 管理者が完全に制御できる。
- フォーメーションの外にあるものには到達できない。エージェントは実行時に自分でアクセスを広げられず、権限は設計時に決まる。

**実行時**

- ワークフロー内のすべての呼び出しが Agent Gateway を通る。「統制された正面玄関」として、エージェント間の呼び出し、SAP ビジネスアプリへの接続、サードパーティや外部の MCP サーバー、外部 API の呼び出しの認可が、そのたびに確認される。
- 呼び出し元またはエンドユーザーが、管理者が事前に定義したフォーメーション内のターゲットに対応づけられていなければ、要求はブロックされ、ワークフローは停止する。
- これは独立したスタックで動くエージェントを含め、すべてのエージェントに適用される。

**第二の防御線として Human in the loop** があります。ポリシーの強制はすべての要求で自動的に動きますが、Human in the loop は、人間の判断が必要な操作でエージェントが進む前に意図的に一時停止するものです。承認を必須にする操作は次の 4 種類です。

1. 高額の取引の承認（重要な財務・ビジネス上のアクションを、エージェントが利用者に代わって開始する場合）
2. 機密データへのアクセス要求のレビュー（制限された情報に到達する前）
3. 破壊的な操作の確認（削除、上書き、取り消せないアクション）
4. 規制対象のワークフローでのエージェントの判断の検証（コンプライアンスやポリシーが人間の承認を求める場合）

これらの操作に当たるとエージェントは停止し、人間が承認するまで待ちます。

### 5.8 Joule action bar

API 接続も MCP エンドポイントも A2A 接続もないアプリのために、Joule を「仕事をしている場所」に持ち込むのが **Joule action bar** です。SAP の Web サイトに限らず、管理者が許可した**サードパーティの Web サイト**にも表示できます。

技術的には **WalkMe** の技術を使っています。発表者によると、WalkMe は 2025 年に SAP が（買収した）会社（発話は "SAP bot in 2025" と聞こえます）で、DOM だけでなくページの深い文脈を理解する "deep UI" 技術を持ちます。この技術がページのコンテキストを Joule に渡し、利用者のクエリに取り込まれます。Joule は、SAP システムに関する内部の知識と、そのページのコンテキストの両方を使って回答します。

### 5.9 セキュリティ・倫理・コンプライアンス

Lorato 氏は、Joule Work は SAP のエンタープライズ基盤（ビジネス AI プラットフォーム）の上に設計されており、セキュリティ、倫理、コンプライアンスは後付けではなく最初から組み込まれていて、リスクと運用負荷が下がると述べています。

- **AI の倫理と安全性**：UNESCO の AI 原則などのフレームワークを含む、10 の AI 倫理原則への準拠を SAP は約束している。
- **セキュリティ**：Joule は SAP Cloud と BTP のセキュリティを利用する。顧客データが大規模言語モデルの学習に使われることは決してない。
- **コンプライアンス**：GDPR や EU AI Act などの規制に沿い、ISO 42001 や SOC 2 などの認証に裏づけられている。これらは SAP Trust Center で確認できる。

### 6.1 Teams から Joule を呼び出し、Joule Work で生産オーダーを扱うデモ（約 2 分）

Chris 氏がナレーションを担当した動画です（Hub のブースで自分で試せるが、この日は開いていなかったと説明）。途中で一時停止し、一部を最初からやり直しています。

1. 利用者が Teams を開き、サイドバーの Copilot タブに移動する。
2. Joule を @メンションし、Joule のエージェントを起動して質問する。質問は、ある注文に関するマージンとコストのリスクについて。
3. Joule が Joule Work から回答を取得し、Teams（ここでは Teams 内の Copilot）の中に回答を表示する。利用者はアプリを切り替えずに答えを得られ、S/4HANA（発話では "S4HANA"）へのディープリンクも提示される。
4. Joule Work で、左下の Joule action bar を使って質問する。この生産オーダーに関する **Space** を作るよう依頼する。
5. 利用者のために作られた動的なワークスペース（Space）で対話する。必要に応じて追加の文脈情報を画面に読み込ませたり、どの選択肢を選ぶべきか Joule に推奨を求めたり、エージェントを呼び出して Space に情報を追加したりできる。
6. 最終的に、検討している 3 つの選択肢を比較するチャートが追加され、意思決定のために Joule に推奨を求める。
7. 実行の準備ができたら、Joule Work で生産オーダーの**リリース**を依頼する。すべてがトリガーされ、生産オーダーがリリースされる。

ブースでは、約 5 分の "choose your own adventure" 形式のデモが 2 本あると案内されました。

### 6.2 Joule Work Desktop のデモ（短いデモ）

1. 利用者が、最も機微なメールを検索する。
2. Joule が Outlook の受信トレイを検索し、翌日の取締役会に向けたインサイトに関するメールを特定する。
3. 利用者が、返信の準備のために Space を作るよう依頼する。その際、情報は特定の Excel ファイルにあると指定する。
4. Joule がその情報を使って Space を作成し、メールへの回答を手伝う。これは Joule Work Desktop の中で完結する。

### 6.3 ServiceNow 上の Joule action bar のデモ

1. 利用者が画面の左下に移動し、Joule アイコンをクリックする（画面は ServiceNow）。
2. Joule のウィンドウが開く。チャットウィンドウの上部に、コンテキストがこの ServiceNow の Web サイトから来ていることを示す小さなアイコン（ピル）が表示される。
3. Joule が質問に答えるとき、SAP システムに関する内部知識と ServiceNow ページのコンテキストの両方を使う。
4. デモでは、ServiceNow の画面に請求書 4471 の情報が表示されていた。Joule action bar が ServiceNow からコンテキストを取り、請求書 4471 が関連すると特定し、それを使って Joule 側からその請求書に固有の情報を取得した。

## 7. 注意点・発表者の気付き

- 現在のデスクトップ版には Joule Studio がありません（Conversations と Spaces は使えます）。
- Microsoft 365 データへの接続は、Joule Work Web では双方向ですが、**デスクトップ版では一方向**です。
- M365 データの検索に加え、メール送信などのアクションを可能にする Work IQ MCP 版への移行は「近日対応」で、時期は示されていません。
- Agent Gateway のガバナンスでは、エージェントは実行時に自分のアクセスを広げられません。フォーメーションの外は到達不能で、認可が通らなければワークフローが停止します。
- 高額取引、機密データアクセス、破壊的操作、規制対象ワークフローでの判断の 4 種類では、人間の承認が必須です。
- GCC High / FedRAMP への対応状況は、発表では確認できませんでした（5.10）。
- 製品名の表記は音声認識の都合で揺れています（1 章の補足）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **コンテキスト切り替えの削減**：Teams や Copilot Chat から SAP の注文・請求書・生産オーダーに直接アクセスし、アプリを切り替えずに答えを得られる。冒頭の調査では、アプリの切り替えは 1 日ほぼ 1,200 回、チームの年間最大 23 日分の生産性損失とされている。
- **手作業の引き継ぎの削減と、信頼できるビジネスコンテキストによる意思決定の改善**（Lorato 氏の説明）。
- **データが自社の管理下に残る**：Joule Work Desktop は、ローカルファイルを使い、クラウド型 AI にアップロードできない組織の要件に対応する。
- **多ベンダー環境への対応**：A2A と Agent Gateway により、SAP とサードパーティのエージェントを、統一されたガバナンスの下でつなげる。
- **API のないアプリでも使える**：Joule action bar で、管理者が許可した Web サイト上で Joule を使える。
- **組み込みのセキュリティ・倫理・コンプライアンス**：顧客データを LLM の学習に使わないこと、GDPR、EU AI Act への整合、ISO 42001、SOC 2 などの認証。

## 9. まとめ

Joule Work は、SAP Knowledge Graph と SAP Business Data Cloud を土台に、SAP と SAP 以外のデータ・エージェントをつなぐ SAP の AI ワークスペースです。Microsoft 365 Copilot とは 2025 年 12 月に双方向統合が GA となり、Teams や Copilot Chat から Joule を、Joule Work から M365 のデータを使えます。サードパーティのエージェントは A2A と SAP Agent Gateway でフォーメーション単位の認可と実行時のチェックの下でつなぎ、重要な操作には Human in the loop の承認を求めます。API を持たないアプリには Joule action bar があります。

詳細は SAP のブース（番号 5679、翌日に開く予定と発表者は述べています）で相談でき、翌日には Stuart 氏と Pragna 氏による、SAP と Microsoft がコンテキストを理解する AI エージェントを構築・統制する方法のセッションが予定されていると案内されました。
