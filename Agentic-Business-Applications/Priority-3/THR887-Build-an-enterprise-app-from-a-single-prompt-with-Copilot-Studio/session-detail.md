# THR887 Build an enterprise app from a single prompt with Copilot Studio

## 1. はじめに

このセッションは、Copilot Studio で 1 つのプロンプトから業務アプリを作り、それを「デモ用のおもちゃ」で終わらせず、組織で本番運用できる状態にするまでを紹介する、約 25 分の登壇です。中心になるのは、前日に一般提供（GA）になった **Copilot Managed Runtime（CMR）アプリ**です。

登壇者は、AI エージェントが数分でアプリを作る場面はすでに多くの人が見ていると述べ、本当に難しいのはコードを書くことではなく、最初のプロトタイプを業務で動かせる状態にすることだと位置づけています。CMR では、Microsoft がホストする基盤、Entra サインイン、ガバナンスされたコネクタとデータポリシーが最初から付いてくるため、本番化は作り直しではなく「少し厳密さを足す」ことで済む、という主張です。

デモは、顧客フィードバックを集めて分析するアプリ「Community Pulse」を題材にしています。Copilot Studio での作成、アプリの中に組み込まれたエージェント、Dataverse のテーブル作成、Cowork で作ったスキルの再利用、Microsoft 365 admin center でのガバナンス、GA 後の予定機能が順に説明されます。

## 5. 発表内容の詳細

### 5.1 背景：デモから本番へ

登壇者は、プロンプトでやりたいことを説明してエージェントに送ると、数分でアプリが生成され、編集を指示して改善を繰り返す、という流れをすでに見た人が多いはずだと話します。コードは「探索するには安いもの」になり、何度も磨き直せます。ただし、難しいのはコードを書くことではなく、最初のプロトタイプから、事業部門が実際に運用できるものへ進めることです。

CMR で生成・ホストされたアプリには、次の特徴があります。

- Microsoft がホストするインフラ上で動く
- Entra サインインが付く
- SharePoint や Dataverse など、実際のガバナンスされたデータに接続できる
- 最初の 1 分から、ガバナンスされたコネクタとデータポリシーの下に置かれる
- これらのポリシーは、管理者が組織向けに設定したもの

本番化は、バイブコーディングしたデモを完全に書き直すことではなく、すでにあるアプリに少しだけ厳密さを足すこと、というのが登壇者の説明です。

### 5.2 GA と 3 つの入口

登壇者は、前日にプレビューが終わったと述べ、これを「今週の見出し」と呼んでいます。チームがこの 6 か月、非常に力を入れてきたもので、**Copilot Managed Runtime アプリは一般提供（GA）になりました**。Cowork、Copilot Studio、CLI と SDK のいずれで作ったアプリも、最初から本番に向く状態です。

3 つの入口は次のとおりです。

| 入口 | 向いているケース（登壇者の説明） |
| --- | --- |
| Copilot Cowork | すでに Cowork でプロジェクトについてエージェントと話していて、メール、ファイル、会議、チームのメッセージなど、組織について Cowork が知っている文脈をアプリに生かしたいとき |
| Copilot Studio | すでに Dataverse で構築している、エージェントやワークフローを作っているなど、実データとエージェント、ワークフローを伴うビジネスプロセスのアプリを作るとき。すべてがすでにそこにある |
| CLI と SDK | プロの開発者で、コードとリポジトリを完全に制御したいとき。生成されたコードを見て自分で変更したい場合 |

登壇者の考えは、「作る人がいる場所で出迎える」ことです。どの入口を選んでも、下にあるのは同じアプリで、同じレベルのガバナンスと制御があり、すべて **Git** に裏付けられています。そのため、1 つの入口から始めて、別の入口で続きを引き継ぐことができます。

Cowork の例として、登壇者は先週の経験を話しています。自分たちが担当していた製品を終了する際、Microsoft のアカウントマネージャー 350 人超にメールを送る必要がありました。Cowork がメールの下書きを作ってくれたものの、誰が返信して認識したかを手作業で確認するのは大変でした。そこで Cowork に、データを使って追跡するアプリを作ってもらい、**2 時間ごとに受信トレイを確認してアプリを更新**し、アプリをチームやアカウントマネージャーと共有して、どの顧客が告知を確認したかを全員が把握できるようにした、という内容です。

### 5.3 Copilot Managed Runtime アプリの中身

登壇者は、ボンネットを開けて中を見る、という位置づけで説明しています。

- モックアップでも独自形式のファイルでもなく、**React と TypeScript の実際の Web アプリ**が Git リポジトリに入る。開発者が開いて拡張できる
- **SDK** が Microsoft 365 とつなぐ。サインイン、コネクタ、Work IQ が「そのまま動く」
- 作成した瞬間から（「最初のターン」ではなく、アプリが最初に作られた時点から）ガバナンスの対象になる
- DLP、共有、コネクタのルールが、IT 管理者の設定どおりに自動で適用される

1 つのアプリに、3 種類の関係者がいます。作る人（maker）、ガバナンスする管理者、アプリを開く利用者です。作り方は現在 3 通りあります。

### 5.4 デモの狙い：1 つのプロンプトで得られる 4 つのもの

登壇者は、デモが盛りだくさんなので、先に見どころを説明しています。1 つのプロンプトから、次の 4 つが得られます。

1. **アプリ**：自然言語から作られた、動く業務アプリ
2. **アプリ内のエージェント**：サイドのチャットボットではなく、アプリの中に入ったチャットで、AI の知能がアプリに組み込まれる。**agent node connector**（新機能）を通じてつながる
3. **Dataverse プラグイン**：新機能で、Dataverse の新しいテーブルを作れる。手作業でテーブルを作らなくてよい。SharePoint を使えるならそれでもよい
4. **再利用できるスキル**：Cowork にあるスキルを Copilot Studio で呼び出せる

> 注意：登壇者は、2 番目のエージェントノードと 3 番目のプラグインは、**GA にはまだ含まれず、展開中**だと断っています。デモで見せるのは、Microsoft IT（自社のテナント）で利用できる内部のものです。厳格なテストなどを経て準備ができたら、順次展開されるとのことです。

### 5.5 Community Pulse アプリの要件（プロンプト）

デモの題材は、登壇者自身が 3 週間ほど前に作ったアプリです。チームの Copilot Managed Runtime アプリがパブリックプレビュー中で、メーカーコミュニティから多くのフィードバックと反響がありました。毎朝 LinkedIn、YouTube、動画のコメント、ブログ、Reddit、Twitter を見て回るのが時間のかかる、負担の大きい作業になっていました。そこで、フィードバックを 1 か所にまとめ、チームが対応できるようにして、GA に備えたかったそうです。CMR アプリのフィードバックを集めるのに、CMR アプリを自分で作るのが最適だと考えた、と話しています。

プロンプトの内容は、次のように説明されました（原文のプロンプトそのものではなく、口頭の説明に基づく要約です）。

- Copilot Managed Runtime アプリに関する顧客フィードバックを集めるアプリを作る
- コミュニティフォーラム、ソーシャルメディア、ブログを検索する**インラインエージェント**を付ける
- エージェントはフィードバックをテーマ別に分類し、新しい投稿、報告されたバグ（特に重要）、センチメントの傾向（ポジティブ、ニュートラル、ネガティブ）を示す
- Dataverse プラグインを使い、コミュニティフィードバック、フィードバックのソース、プロダクト領域の **3 つのテーブル**を作り、エージェントが見つけたデータをそこへ保存して傾向を追えるようにする
- Cowork にあるアプリ用スキルを使って、このアプリのドキュメントを生成する

登壇者はこれを「アプリ、テーマ別に分類するインラインエージェント、新規の 3 つの Dataverse テーブル、Cowork で作ったアプリドキュメントスキルによるドキュメント」の 4 つに整理し直しています。

### 5.6 生成されたアプリの確認

生成には時間がかかる上、登壇者はいつの間にかサインアウトされていたため、プロンプトの送信後は、あらかじめ生成してあるアプリに切り替えています（詳細は 6 章）。登壇者は、アプリを開く画面について次のように説明しています。

- **左側**：エージェントとのチャット履歴。最初のプロンプトも残っており、30 日、60 日、90 日後に戻ってきても、なぜそう決めたか、このアプリが何のためかを思い出せる。更新したいときはこのチャットで依頼する
- **右側**：インタラクティブなアプリのプレビュー。エンドユーザーの体験を確かめられる
- **コードビュー**：アプリの下にあるコードを確認できる。プロの開発者向け
- **デバイスのプレビュー切り替え**：さまざまなフォームファクター（タブレットや小さなスマートフォンなど）で動くことを確認できる
- アプリ名をクリックすると、データ、接続、アプリの設定が表示される

データには、プロンプトで頼んだ 3 つのテーブル（community feedback、feedback source、product area など）があり、エージェントが Dataverse プラグインで作ったものです。接続には、次のコネクタが並んでいました。

| コネクタ | 役割（登壇者の説明） |
| --- | --- |
| Office 365 users | アプリを開いたユーザーを識別して挨拶する。登壇者と同僚では表示される名前が変わる |
| GitHub | チームのリポジトリに接続 |
| エージェント | 最初のプロンプトで頼んで作られたエージェント |
| Microsoft Dataverse | テーブルを作ったコネクタ |

ここでチャットを折りたたみ、アプリ本体を表示します。このアプリは数ターンかけて作ったもので、触りながら機能を足したとのことです。今日の集計では、**新しい投稿が 45 件、そのうち 15 件がトリアージ待ち、約 77% がポジティブ**でした。エージェントが分類したテーマは 5 つで、聞き取れた範囲では Copilot Studio のアプリ体験、ホスティング体験、ドキュメント、アプリ内の AI などです（テーマ名の細部は音声認識の都合で確定できません）。

各テーマを選ぶと、そのテーマに属するフィードバックの一覧が見られます。ソース、影響するプロダクト領域、重大度、投稿者、元のソースでの反応数が表示されます。チームが後から見直せる記録になっています。

次にトリアージされていないフィードバックの一覧を見ます。投稿時刻、重大度などが表示され、多くは未特定です。通常はチームで個別に確認して、対応を決め、担当を割り当てる必要があります。GA を迎えると、未トリアージの 15 件よりずっと多くなると見込まれるため、エージェントにトリアージさせられないか、という流れでデモが進みます。

「Ask the agent」ボタンで、アプリ内のチャットパネルが開きます。

1. 「今日のコミュニティの投稿を要約して」と依頼します。毎朝のスタンドアップで、15 件を 1 件ずつ見る時間がないためです。
2. エージェントは、まだトリアージされていない当日の新しいデータを読み、要約を返します。パブリックプレビュープログラムへの強い熱意があり、エージェントとのやり取りと応答性に改善の余地がある、という内容です。そのまま Teams チャンネルに貼り付けて「今日、顧客からこう聞こえている」と共有できると説明しています。
3. バグについては、通常は GitHub に個別に Issue を作成して Teams で割り当てる必要があり、これも時間がかかります。このアプリは先ほど見た GitHub リポジトリに接続されているので、「報告されたバグについて GitHub に Issue を作成して」と依頼します。
4. エージェントは、その日に報告されたバグの下書きを作り、「こう考えています」と提案します。パフォーマンスと信頼性に関するものが多いとのことです。登壇者が承認すれば、GitHub に Issue を作成します。

登壇者は、フォーラムやブログを巡ってセンチメントを調べる作業と、GitHub に手作業で Issue を作って担当者をタグ付けする作業が不要になり、すでに多くの時間を節約できたと話しています。

アプリが整ったら、**Publish** を押し、チームメンバーと共有できます。デモでは Emma と共有するとしており、リンクを共有すると相手にメールが届き、すぐにアプリを使えるようになります。

### 5.7 アプリドキュメントの自動生成と Cowork スキルの再利用

最後に頼んでいたのが、アプリのドキュメントです。Cowork に持っているスキルを使い、**アプリのドキュメントを PDF で最初から最後まで生成**しました。登壇者は「指一本動かしていない」と話し、動かしたのはプロンプトに「app documentation」と入力したことだけだと言います。Cowork のスキルが Copilot Studio でも動くのは、下にあるプラットフォームが同じだからです。アプリのリンクと PDF のリンクをチームのチャンネルで共有し、「作ったアプリとドキュメントです」と伝えれば済みます。アプリが進化したら、エージェントにこのファイルを再生成・更新させることもできます。

### 5.8 ガバナンス：Microsoft 365 admin center

次に、管理者から見える範囲を、Microsoft 365 admin center で示します。登壇者は、管理者が最初から、すべてのアプリとコネクタを見られると繰り返し述べています。

- admin center の Apps で、このテナントで作られたすべてのアプリを確認できる
- 登壇者のアプリ（CMR Community Pulse）を検索して表示
- 管理者は、テナントで作られたすべてのアプリについて、使われているコネクタ、使用頻度、作成者、オーナーなどを確認できる

時間が少なくなったため、この部分は駆け足でした。登壇者は、デモの要点を次のようにまとめています。Cowork や Copilot Studio でアプリを作れる。Copilot Studio にアプリの中に住むエージェントを作らせられる。Cowork の再利用可能なスキルでドキュメントを生成できる。Dataverse プラグインで新しいテーブルを作れる。

### 5.9 GA 後に取り組んでいること

デモ後の残り時間で、GA 後の予定が語られました。登壇者は、これらを「寄せられている主な要望」への取り組みとして説明しています。

| 項目 | 説明 |
| --- | --- |
| 共同編集（co-authoring） | チームメイトと一緒にアプリを作りたいという声が多い。複数の作成者が同じセッションで同時に作業できるようにしたい |
| 共同オーナー（co-owners） | 現状はアプリのオーナーが 1 人だけ。その人が突然いなくなったり、退職したりすると、アプリは事実上失われる。アプリの継続のために、共同オーナーを割り当てられるようにしたい。プレビュー顧客からの大きな要望の 1 つ |
| バージョン履歴 | ロールバックの方法について。現在は CLI でできるが、Copilot Studio、Cowork などの UX にも出す作業が必要 |
| ALM | dev から test、本番へ移す ALM のストーリーに取り組んでいる。よく聞かれる質問だと話している |
| GitHub Enterprise | 管理者から、自分たちのリポジトリでホストしたいという要望があり、対応を進めている |
| 環境の選択 | 現在は、CMR アプリは個人用の開発者環境（PDE）で作られるのが既定。PDE 以外の、指定されたカスタム環境でも作れるように変更を進めている |

### 5.10 参考ドキュメント

登壇者は、宿題として、ドキュメントへのリンクを示しています。今日すぐ自分のアプリを作りたい人は、読んで試してほしいという案内です。最後のリンクには、それまでのリンクの内容がすべて含まれ、管理者向けの情報も入っていると説明しています。

質問がある人は、会場のエキスパートブースで CMR（Copilot Managed Runtime）アプリのチームメンバーに聞くか、同日 2 時のセッションに来てほしいと案内して終わっています。

> 補足：冒頭で、主催者から「セッションが人気なので再度やってほしい」と連絡があったと語られ、同じデモを同日 2 時に Theater E で再度行う予定だと案内しています。

## 6. デモ・手順

このセッションには、Copilot Studio での実演があります。ただし録音は音声だけで、画面の細部（ボタンの配置や入力した文字列）は分かりません。以下は、登壇者が語った範囲の流れです。

1. Copilot Studio のホームページを開く。通常はエージェントやワークフローを作る場所だが、ここでアプリを作るとして、**3 つ目のタイル**を選ぶ（登壇者は、GA の展開中でテナントにはまだ反映されておらず、プレビューの表示が残っているが無視してほしいと説明）。
2. 作りたいアプリの背景を説明したうえで、前述の内容のプロンプトを入力して**送信**する。
3. 生成に時間がかかるうえ、途中でサインアウトされてしまったため、**あらかじめ生成したアプリ（Community Pulse）に切り替える**。Wi-Fi が不安定でホットスポットに切り替えたという話もある。
4. 左のチャット履歴、右のインタラクティブなプレビュー、コードビュー、デバイスのプレビュー切り替えを見せる。
5. アプリ名をクリックし、データ（3 つのテーブル）と接続（Office 365 users、GitHub、エージェント、Microsoft Dataverse）を確認する。
6. チャットを折りたたみ、アプリの画面（今日の件数、センチメント、テーマ）を確認する。テーマを開き、フィードバックの詳細（ソース、プロダクト領域、重大度、投稿者、反応数）を見る。
7. 未トリアージのフィードバックの一覧を見る。
8. 「Ask the agent」から、今日の投稿の要約を依頼し、返答を確認する。
9. 「報告されたバグについて GitHub に Issue を作成して」と依頼し、エージェントが提案した下書きを確認する（承認すれば Issue が作られると説明）。
10. Publish して、チームメンバー（Emma）と共有できることを説明する。
11. Cowork のスキルで生成した PDF のドキュメントについて説明する（画面で PDF を開いたかどうかは語られていません）。
12. Microsoft 365 admin center の Apps で、すべてのアプリを一覧し、登壇者のアプリ（CMR Community Pulse）を検索して、使用コネクタ、使用頻度、作成者、オーナーなどの情報を見せる。

## 7. 注意点・発表者の気付き

- **エージェントノードと Dataverse プラグインは GA に含まれていません。** 展開中で、デモは Microsoft IT のテナントで使える内部のものです。
- Copilot Studio のホームのタイルに、**プレビューの表示が残っているテナント**があります。GA の展開途中のため、登壇者は無視してほしいと述べています。
- 1 つのプロンプトで完成させるのではなく、このアプリも**数ターンの修正**を経ています。
- 現状、アプリの**オーナーは 1 人だけ**で、その人がいなくなるとアプリが失われる。共同オーナーを今後追加する予定です。
- **バージョン履歴のロールバック**は、現在は CLI でのみ可能です。
- **既定の作成環境は個人用の開発者環境（PDE）**です。
- 本番に向けた ALM（dev、test、prod）、GitHub Enterprise のリポジトリでのホストは、現在開発中の項目です。
- デモでのバグ報告は、エージェントがまず下書きを提示し、登壇者が了承すると GitHub に Issue が作られる、という説明でした（実際に作成されたかどうかは語られていません）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **作り直しが不要**：Microsoft がホストするインフラ、Entra サインイン、ガバナンスされたコネクタとデータポリシーが最初から付いており、本番化は厳密さを足すだけで済む。
- **入口を選べる**：Cowork、Copilot Studio、CLI と SDK のどこから始めても、同じアプリ、同じガバナンスで、Git を介して引き継げる。
- **実際のコード**：React と TypeScript の Web アプリが Git リポジトリに入り、開発者が開いて拡張できる。
- **管理者の可視性**：Microsoft 365 admin center で、テナントのすべてのアプリ、使用コネクタ、使用頻度、作成者、オーナーが見える。DLP、共有、コネクタのルールが自動で適用される。
- **デモの事例での時間の節約**：コミュニティの巡回、センチメントの把握、GitHub への Issue 作成の手作業が不要になった。Cowork の事例では、350 人超のアカウントマネージャーの確認状況を、2 時間ごとの受信トレイ確認で自動的に追跡した。
- **スキルの再利用**：Cowork のドキュメント生成スキルを Copilot Studio でも再利用でき、PDF のドキュメントが自動で作られる。

## 9. まとめ

Copilot Managed Runtime アプリは前日に GA になり、Cowork、Copilot Studio、CLI と SDK のどこで作っても、同じ React と TypeScript のアプリ、同じガバナンスで本番に向かえます。Copilot Studio のデモでは、1 つのプロンプトから Community Pulse アプリを作り、アプリ内のエージェントによる要約とバグの Issue 作成、Dataverse の 3 つのテーブル、Cowork スキルによる PDF ドキュメント、Microsoft 365 admin center での管理者の可視性が示されました。エージェントノードと Dataverse プラグインは展開中で、GA には含まれていません。GA 後は、共同編集、共同オーナー、バージョン履歴の UX、ALM、GitHub Enterprise でのホスト、作成環境の選択の対応を進めるとのことです。
