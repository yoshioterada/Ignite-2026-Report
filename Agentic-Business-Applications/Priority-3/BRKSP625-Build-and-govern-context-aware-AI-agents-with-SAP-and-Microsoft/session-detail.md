# BRKSP625 Build and govern context-aware AI agents with SAP and Microsoft

## 1. はじめに

このセッションは、SAP の 2 人のプロダクトマーケティング担当者が、SAP の Business AI プラットフォームを、Microsoft のスタックと組み合わせて使う方法を紹介する内容です。軸になるのは「**エージェントを作ること自体はもう簡単で、難しいのは、作ったエージェントを信頼して業務に任せられるかどうかだ**」という認識です。

話は 3 部構成です。

1. エージェントを作る：SAP の新しい開発プラットフォーム **Joule Studio**
2. エージェントを統治する：SAP LeanIX の AI Agent Hub、SAP Signavio、SAP Cloud ALM
3. エージェントに業務の文脈を渡す：**SAP Business Data Cloud (BDC)** と、Microsoft Fabric へ SAP データを共有する **BDC Connect**

画面を使ったデモが 3 回あります。Joule Studio でのエージェント作成、AI Agent Hub を中心とするガバナンス画面、BDC Connect のセットアップです。BDC Connect の Fabric 連携は、発表時点でプライベートプレビューで、GA（一般提供）は 3 月を予定していると説明されています。

## 5. 発表内容の詳細

### 5.1 なぜ「文脈を持つエージェント」なのか

スライドには 2 つの数字がありました。**74%** の組織が、AI に関してまだパイロット段階にあること。そして **42%** が、データへのアクセスとデータ品質を参入障壁として挙げていることです。

Stuart 氏は、調達（procurement）の簡単な例で違いを説明しています。請求書が届き、支払いの承認が必要な場面です。

- **汎用エージェント**：限られた情報しか見られない。購買発注（PO）があることを確認して支払いを承認し、支払いが実行される。
- **文脈を持つエージェント**：生のデータの先まで、企業全体を見渡せる。複数の事業部門が同じサプライヤーとやり取りしている場合、SAP の調達プラットフォームである Ariba で、一定期間内に支払えば 3.2% の割引が得られることが分かり、支払い時にクレジットを請求できる。この例では 8,000 ドルのリベートを使い逃さずに済む。

8,000 ドルや 3.2% は例示のための数字で、大企業には大きな額に見えなくても、1,000 回繰り返せば相当な金額になると述べています。

### 5.2 SAP が持つ土台

文脈を持つエージェントのための基盤は、すでに SAP の中にあるというのが Stuart 氏の見方です。次の 3 点を挙げています。

| 項目 | 内容 |
| --- | --- |
| プロセスと業界の深い知識 | 大企業向けのミッションクリティカルなプロセスを 120 以上カバー |
| 意味を持つビジネスデータ | SAP 内に 730 万のフィールド（このセッション内で 730 万と 720 万の 2 通りの発言があります）。独自のナレッジグラフでカバー |
| エンタープライズ品質のガバナンス | 後付けではなく最初から組み込まれている |

### 5.3 概念的なアーキテクチャと Microsoft との連携

Stuart 氏は、概念的なエージェントアーキテクチャのスライドで、各層に Microsoft のスタックとの連携または補完的な製品があることを示しています。

- 一番下の層：SAP の AI Agent Hub が、API 呼び出しで Copilot のエージェントとやり取りする。
- 文脈化の層：SAP のデータプラットフォーム Business Data Cloud に、信頼されたデータプロダクトがあり、zero copy のプロトコルで Microsoft Fabric と双方向に共有できる。
- 構築の層：エージェントを作れる。MCP サーバーなどにより、Microsoft で作ったものとも相互にやり取りできる。
- エージェントの層：エージェント間（agent-to-agent）のプロトコルにも対応する。

以降は、Pragnya 氏が構築とガバナンス、Stuart 氏がデータ（文脈化と推論）を担当すると予告されました。

### 5.4 Joule Studio の位置づけ

Pragnya 氏によると、SAP がこの 1 年ほどで提供してきたのは、事業アプリケーションに付属してくる、パッケージ済みの **Joule エージェント**です。ペルソナ別に作られた「アシスタント」もあり、各アシスタントが複数のエージェントをまとめて動かし、利用者がより戦略的な仕事に集中できるようにします。

しかし業務はお客様ごとに固有のため、既存エージェントを自社のワークフローに合わせて拡張したい場合や、標準にはない新しいカスタムエージェントを作りたい場合があります。そのための新プラットフォームが **Joule Studio** です。「今四半期に GA、段階的に提供中（phased availability）」と説明されています。

Joule Studio は、SAP 初の統合 AI 開発プラットフォームで、エージェント、アプリケーション、ワークフローを 1 か所で作れます。特徴は次のとおりです。

- **文脈の組み込み**：SAP と非 SAP のアプリケーションにあるデータの文脈を、最初から取り込んで解決策を考える。
- **ノーコードとプロコード**：Joule に意図を伝えて作らせるノーコードだけでなく、Python と React のコードが見え、開発者は好みのツールに持ち出せる。
- **自分のやり方で**：業務に詳しい利用者が要件を Joule に伝えて作ることも、アイデアを開発者に引き継いでアプリケーションにすることもできる。
- **組み込みの運用機能**：開発者向けに、ネイティブなオブザーバビリティ、モニタリング、デプロイ、セキュリティ、ガバナンスのパイプラインが用意されている。

### 5.5 Joule Studio と Microsoft の連携

Pragnya 氏は、Microsoft への投資も Joule Studio に引き継げる点を 2 つ挙げています。

- **Fabric との zero copy 連携**：SAP Business Data Cloud で作ったデータプロダクトを Joule Studio で使い、アプリ、エージェント、ワークフローを作れる。逆に、Joule Studio でデータプロダクトをネイティブに作り、データクラウドへ、さらに Fabric へ送って広く利用することもできる。
- **N8N のワークフロー・オートメーションエンジンの組み込み**：SAP データに体系化されたバックエンドプロセスを自動化し、Outlook や Teams、SharePoint や Excel など Microsoft 側にある作業も N8N でオーケストレーションできる。その接続性とロードマップは、より広く展開していく中で、今後数か月で利用可能になると説明されています。

### 5.6 Joule Studio のデモ（関税への対応）

デモの内容は 6 章にまとめます。ここでは、デモを通して語られた機能を整理します。

- プロンプトを受けると、Joule Studio は連携済みの複数の **MCP サーバー**と、SAP ナレッジグラフ、SAP データドメインモデル、買収によって得た LeanIX の機能などの独自スキルを使い、環境内に何があるかを把握します。

### 5.7 エージェントの統治：なぜ必要か

Pragnya 氏は、2026 年 11 月の時点で、エージェントやアプリを作ること自体は難しい問題ではないと述べ、本当の課題は作ったあとだとしています。根拠として、SAP LeanIX が顧客約 300 社に行った調査を挙げています。この調査では、直近 1 年で既に **65 万個のエージェント**が存在し、LeanIX が追跡していました。1 年の間に、ベンダー提供のエージェントから、あらゆる場所で作られるエージェントへ移ったという説明です。

導入とガバナンスの差は縮まっていません。技術はムーアの法則の速度で進むのに、ガバナンスは従来と同じサイクルで見られており、AI の波に対する「アンカー」を業界はまだ提供できていない、という認識です。組織で起きているギャップとして、次の 3 つが挙げられています。

- **乱立（sprawl）**：どの AI を使うべきか、誰が決めるのか、戦略は何か。
- **リスク**：エージェントがポリシーの範囲内で動いているか、アクセスすべきでないデータに触れていないか、誰がそれに責任を持つか。
- **コスト**：エージェントが使っている費用を誰か把握しているか。夜にパソコンを閉じて翌朝に想定外のコストが出ている、という会話が実際に出ている。

多くの企業は水面の上、つまり「どんなエージェントがあるか、棚卸しできるか、どこにあるか」に集中していると指摘したうえで、水面の下、つまりエージェントの活動を、広いポートフォリオや狙うビジネス成果に結びつけた測定可能な成果へ進む必要があると述べています。必要なこととして次の 3 点が挙げられ、SAP の製品群がそれに応えるという構成です。

1. AI のディスカバリー、インベントリ、マイニングを、資産ポートフォリオとビジネス KPI に対応づける。
2. すべての意思決定、ツール呼び出し、エージェントの動きを、追跡、測定、監査できるようにして、責任の所在を明確にする。
3. 最初の構築から廃止まで、エージェントごとのアイデンティティ、アクセス、ポリシーの統制を提供する。

### 5.10 SAP Business Data Cloud の構造

ここから Stuart 氏の担当です。SAP の Business AI プラットフォームのデータ製品である **SAP Business Data Cloud** について、個々のサービスではなく、概念的な 3 つの層で説明しています。

1. **レイクハウス層（最下層）**：データが置かれる場所。複数のサービスから要件に合うものを選べる。従来 SAP は SAP データへのアクセスに強いと言われてきたが、投資を重ね、データは SAP 以外のほぼどこからでも持ち込める。オープンスタンダードと業界のベストプラクティスに従い、今年の早い時期に **Dremio** を買収したことがこれを後押ししている。
2. **ビジネスデータファブリック層（中間）**：データに目的と意味を与える層。データプロダクトを通じて、セマンティクスやメタデータなどが集まる。その上部に**ナレッジグラフ**があり、**約 50 万のテーブル**にまたがる **720 万のフィールド**（先に 730 万とも述べています）に加えて、リファレンスアーキテクチャやビジネスプロセスの知識が補強されている。さらに **ontology manager** があり、顧客やパートナーが文脈をカスタマイズできる。
3. **利用層（最上位）**：プラットフォームのエージェントや AI モデルによる利用に加え、ダッシュボードも引き続き使われる。

こうして、データに意味が通り、エージェントの判断が文脈ある現実に基づくものになる、というのが狙いです。

### 5.11 データプロダクト

データプロダクトは、SAP または SAP が管理する形で提供されます。SAP がエンジニアリング作業を顧客に代わって行い、パイプライン、ロジック、テーブル間の関係、メタデータとセマンティクスをすべて備えています。顧客がそれらを自分で作る必要はありません。Stuart 氏は、データエンジニアの時間の 75% がパイプライン構築に費やされ、データの活用は 25% という調査を読んだことがあると述べ、これを「逆転させる」と話しています。

データプロダクトは、ドメインや事業ライン（line of business）ごとに分けられています。そのおかげで、データ担当者が LOB のリーダーとデータの話をし、事業成果につなげやすくなるという説明です。Stuart 氏は、データプロダクトを「私たちが作った、文脈を持つ成果物（artifact）の集まり」と捉えています。

### 5.12 BDC Connect と Microsoft Fabric

データプロダクトは、Business Data Cloud の外にも共有できます。「SAP はもう壁に囲まれた庭ではない」と Stuart 氏は述べ、テーブルのデータをデータベースやシートにダンプしてポリシーに違反する、という方法をとる必要はないとしています。その仕組みが **BDC Connect** です。

- BDC Connect は汎用的なサービスで、すでにいくつかのパートナーが登録されている。Microsoft は、Stuart 氏が最も期待しており、毎日、少なくとも毎週質問を受けているパートナー。
- **zero copy** でデータを外へ出す。使っているのは **Delta Share** プロトコル。
- Fabric（または他のサードパーティのプラットフォーム）との間に、まず安全で信頼できる関係を作る。これは **BDC formation**（「信頼の輪」というたとえ）に登録することで行う。
- 登録後は、データプロダクトを**双方向**に共有できる。SAP データを Fabric へ出すだけでなく、Fabric にあるデータを SAP のレポートに活かすこともできる。どちらもデータを移動せずに共有する。

Stuart 氏は効果を次のように整理しています。データ環境が簡素化される。安全で双方向である。SAP の全事業ラインにわたり SAP データを zero copy で扱える。文脈が付いた SAP 管理のデータプロダクトで AI と分析の導入が加速する。SAP と非 SAP のデータを移動せずに調和でき、インサイトの提供が非常に速くなる。総保有コストも下がる。

また、データを SAP と Fabric の間で行き来させることで、どちらのスタックにあるエージェントも、そのデータを使ってより情報に基づく判断ができます。例えば CRM に Dynamics、ERP に S4 を使っている場合、今はエージェントを別々にデプロイして、互いにうまく連携することを期待するしかありません。ほかに、Dynamics のデータを SAP Analytics Cloud に取り込む、あるいはより現実的な例として SAP データを Power BI に取り込む、といった利用が挙げられましたが、後者についてはその場では詳しく話されていません。

### 6.1 Joule Studio：関税への対応（Pragnya 氏）

想定シナリオは、新しい関税が発表され、チームの各メンバーがその影響を調べる状況です。ビジネス上の問いは、「自分たちの製品、サプライヤー、コスト、在庫への影響を理解するには何をすべきか」です。この時点では、解決に必要なのがエージェントかアプリかワークフローかは考えなくてよい、と説明されています。

1. プロンプトを与えると、Joule Studio が作業を始める。
2. 連携済みの MCP サーバーと、SAP ナレッジグラフ、SAP データドメインモデル、LeanIX の機能などのスキルがネイティブに起動し、環境内の利用可能なものを把握する。
3. 情報が必要なときは質問してくる。
4. PRD（製品要件定義書）が生成される。チームで議論できる。
5. 環境内に存在するもの／しないものを示すソリューションアーキテクチャが示され、構築が始まる。
6. 業務担当者は構築の様子を見られ、開発者は Python コードにアクセスして修正し、組織が必要とする動作を教え込める。エージェントのモデル設定や、PRD に入っていなかったツールの追加もできる。
7. 組み込みの N8N エンジンの画面で、SAP エコシステムをまたぐワークフローと、エージェントを呼び出す agentic ワークフローを確認する。
8. 解決策の一部として生成された CAP アプリケーションが示される（Vercel の V0 を使った React の UI）。BTP へデプロイしてテストでき、単体テストもプラットフォーム内で行えると説明された。
9. エージェントごとの分析（モニタリング、オブザーバビリティ、オフライン／オンラインの評価）が得られると説明された。実際の画面を操作したかどうかは、語りからは分からない。
10. 作成後は LeanIX の AI Agent Hub に登録できる（詳細は次のデモ）。

### 6.2 ガバナンス：AI Agent Hub、Cloud ALM、Signavio（Pragnya 氏）

1. SAP AI Agent Hub のダッシュボードで、環境内の AI 資産のポートフォリオビューと、発見された資産などの主要な KPI を確認する。
2. 「discovery inbox」で、稼働しているエージェントの一覧を見る。エージェントのメタデータと詳細、集計分析を確認できる。
3. Cloud ALM のアナリティクスダッシュボードに進む。特定のエージェントのヘルスビューがあり、セッションビューにも入れる。ここで見せたのは「billing creation」のエージェント。
4. これがエージェントのインベントリになる。各項目に番号、追加メタデータ、AI ガバナンス関連のフィールドがあり、ハイレベルな表示だけでなく、インスタンス単位でエージェントを把握できる。
5. Signavio に進み、エージェントマイニングと、集約されたプロセスビューを確認する。エージェントの振る舞いと性能に満足できれば、検証（verify）でき、それがランタイムに影響しうる。
6. 最後に、組織図ビューで、誰がどのエージェントを作っているかだけでなく、それらのエージェントが組織内でどう位置づけられるかを見る。人が作っているもの、エージェントの性能、誰が何を使っているかを並べて確認できる。

### 6.3 BDC Connect：Microsoft Fabric 向けのセットアップ（Stuart 氏）

Stuart 氏は、これは短いデモで、プライベートプレビューの機能だと断っています。

1. SAP for Me（SAP 製品の管理画面）で、BDC Connect サービスを立ち上げ、Fabric への接続を作成する。各種パラメータが表示される。
2. プロビジョニングが終わったら BDC cockpit に入り、共有する対象を選ぶ。デモでは sales order（受注）のデモ用データプロダクトを選んだ。含まれるテーブルや成果物の数が画面に出た。
3. データプロダクトを共有する。
4. Fabric 側に移る。ここは別の人（Fabric の管理者）が行う場合もある。接続を受け取り、ハンドシェイクを承認する。
5. Fabric から BDC を見て、共有された sales order のデータプロダクトを確認する。矢印を展開すると、テーブル、セマンティクス、メタデータなどが持ち込まれており、データを参照できる。
6. このあとに、状態を維持するための追加手順があるが、「技術的で退屈」として説明は省略された。

## 7. 注意点・発表者の気付き

- **ガバナンスは追いついていない**：エージェントの導入は急速に進む一方、ガバナンスは従来のサイクルのままで、差は縮まっていないと述べています。LeanIX の約 300 社の調査では、1 年で 65 万のエージェントが確認されました。
- **棚卸しだけでは不十分**：多くの企業は「どんなエージェントがあるか」という水面の上の話に集中していますが、エージェントの活動を事業成果に結びつける測定可能な成果まで進む必要があります。
- **製品を入れれば統治できるわけではない**：Pragnya 氏は、これらのツールを入れれば環境全体が統治・保護されるという意味ではない、と明言しています。
- **提供状況の制約**：Joule Studio は今四半期に GA ですが、段階的な提供です。N8N 連携のロードマップは今後数か月で提供予定、BDC Connect for Microsoft Fabric はプライベートプレビュー（10 社）で GA は 3 月の予定です。
- **数値の例示**：調達例の 8,000 ドルのリベートと 3.2% の割引は、例示のための数字と断られています。
- **デモで省かれた手順**：共有した状態を維持するための追加手順があり、デモでは説明されませんでした。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 汎用 LLM に自社の業務文脈を教える時間を省き、1 つのプラットフォームで早く始められる（Joule Studio）。
- 業務担当者と開発者が同じプラットフォームで協力でき、ノーコードとプロコードの両方、さらに開発者向けのオブザーバビリティ、デプロイ、ガバナンスが使える。
- 作成したエージェントを AI Agent Hub に登録して、利用状況と台数を把握できる。
- ツール呼び出し、応答時間、ヘルススコアなどが Cloud ALM で追跡でき、意思決定の追跡と監査ができる。
- SAP 管理のデータプロダクトにより、顧客自身がパイプラインを構築する負担がなくなる。
- Fabric との zero copy・双方向の共有により、データ環境が簡素化され、SAP と非 SAP のデータを移動せずに調和でき、インサイトが速く得られ、総保有コストが下がる。
- SAP の技術は EU AI Act と GDPR に準拠している。

発表では、具体的な顧客事例や、導入による数値的な成果（削減額など）は紹介されていません。

## 9. まとめ

このセッションは、エージェントを作る難しさは下がり、課題は「信頼できる運用」に移ったという認識から始まりました。SAP の答えは、**Joule Studio**（業務文脈を組み込んで作る）、**AI Agent Hub・Signavio・Cloud ALM**（発見・追跡・統治する）、**Business Data Cloud と BDC Connect**（意味付けされたデータを、Fabric とも zero copy で双方向に共有する）の 3 本立てでした。

Microsoft との接点は、Fabric との zero copy 連携、AI Agent Hub と Copilot のエージェントの API 連携、MCP サーバーとエージェント間プロトコルによる相互接続、N8N 経由の Outlook、Teams、SharePoint、Excel のオーケストレーションです。BDC Connect の Fabric 向け機能は 3 月の GA を予定しています。
