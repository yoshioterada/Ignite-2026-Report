# THR1021 Scaling Copilot Studio Adoption Through Community-Led Agent Building

## 1. はじめに

このセッションは、Copilot Studio のようなプロダクトを社内に導入したあと、「最初の 1〜2 週間は盛り上がるのに、その後に利用が落ちていく」という問題を、**コミュニティの力で解決する方法**を扱う約 19 分の発表です。発表者は Microsoft でコミュニティ運営を担当する David 氏です。

発表の中心は、「イベントを開くことがコミュニティではない」という主張です。目標設定から始め、小さな中核チームを作り、チャンピオン（推進役）を育て、従業員がすでに使っているツールで活動を続けるという道筋が、State Farm、ZF Group、Lumen などの事例とともに紹介されます。最後に「最初の 90 日の計画」が示されます。画面を使ったデモは無く、スライドと口頭の説明で進みます。

## 3. 何に関する発表か

テーマは、コミュニティを使って、プロダクトの社内利用（adoption）を持続的に広げることです。

発表者は冒頭で、2 つの質問を会場に投げかけています。1 つ目は、組織で Copilot Studio をすでに使っている人です。2 つ目は、新しいプロダクトを社内全体に広げようとしたが、最初の 1〜2 週間は盛り上がっても、2 週目を過ぎると利用が落ちる経験をしたことがある人です。どちらも挙手を求めており、後者が、このセッションで解決したい問題です。

発表の流れは、予告された次の 4 点です。

1. Copilot Studio でエージェントを作るだけでは、なぜ導入が拡大しないのか
2. その中で、コミュニティはどこに位置づくのか
3. エンタープライズ組織でコミュニティを作るとき、基盤（foundation）から認知（recognition）までどう進めるか
4. 次の 90 日の計画（組織によって 1 月から始まる人もいれば、来週から始まる人もいる、と述べています）

## 4. 発表者が伝えたいメッセージ

発表者が最も強く伝えているのは、次の 3 点です。

1. **エージェントを作っても、それだけでは導入は広がらない。** 「すごいものを作ったから皆使うはず」では拡大しません。
2. **コミュニティは「人が集まっていること」ではなく、「成果が出ていること」で測る。** 組織内で 5,000 人が参加していても、それだけで何かを達成しているとは言えません。コミュニティの目標を、組織のビジネス目標に結びつけることが必要です。
3. **イベントはコミュニティの始まりではない。** イベントは火花（spark）にすぎず、その後に勢いを回し続ける仕組み（engine）が必要です。90 日計画でも、定期的なイベントは 3 番目の施策で、最初でも 2 番目でもありません。

発表者自身は、アフリカ最大級のコミュニティの 1 つ（1 万人超）を運営しており、約 10 年にわたってコミュニティを理解してきたと述べています。その経験から、イベントから始める失敗を何度も学んだ、というのがこの主張の背景です。

## 5. 発表内容の詳細

### 5.1 なぜ「作るだけ」では導入が広がらないのか

コミュニティは、普段の仕事の外側にあるものだと思われがちです。そこで発表者は、コミュニティによって成長を実現した組織の事例（Microsoft の顧客ストーリー）を順に紹介すると述べています。ただし、コミュニティを動かすことと、その結果を定量化することは別の話であり、「5,000 人がコミュニティにいる」だけでは成果にはならない、と強調しています。

### 5.2 火花（spark）とエンジン（engine）

多くの人は、コミュニティを火花として始めます。Copilot Studio、Foundry、Dynamics 365 などの話題を盛り上げるため、ミートアップやハッカソンを開き、初期の勢いを作ります。しかし発表者は、**火花はコミュニティではない**と言います。変革を進めるリーダーが「イベントを作って人を迎え入れよう」と言うのは出発点にすぎず、火を灯したあとに、フライホイールを回し続けるエンジンが無ければ問題になる、という説明です。

事例として、ボランティアのリーダーから「メーカー（maker）のコミュニティ」を作った組織が紹介されました（組織名は発話からは確認できません）。900 人のボランティアから始め、2,000 人に成長したそうです。

### 5.3 コミュニティの目標を組織の目標に結びつける

組織内でコミュニティを作っても、リーダーが「組織にどう役立つか」を見られなければ意味がありません。発表者は、「このコミュニティは、これらの組織目標を達成するために作る」と指し示せる必要があると述べています。

### 5.4 コミュニティの成功への道筋

道筋は、基盤、トレーニング、運用、パートナー、認知（recognition）の順に紹介されます。

**基盤（foundation）**

1. 最初にビジネス目標との接続を作る。
2. 次に、ミッションを定義する。最初に決めるのは「どのイベントを開くか」ではなく、**測定可能で、ビジネスの優先事項と揃った目標**である。
3. この土台があれば、小さく始めやすくなる。

発表者は、「2 人から始めて、組織の規模によっては 1 万人のコミュニティまで行くのは難しい」と感じることが、コミュニティを始める際の大きな障害だと指摘します。これに対し「**1 から始めなければ 500 には到達しない**」と述べ、小さく始めること、ただしビジネス目標は最初から入れておくことを勧めています。

事例として、"P, J, and E" と聞こえる組織が紹介されました（組織名は音声認識の都合で確定できません）。この組織は同じようにコミュニティを始め、数千〜数十万時間の削減と、**7,500 万ドル超**の削減につながったと述べています。コミュニティを製品の導入拡大のために育てたことが理由、という説明です。

**メーカーを育てる 3 つの段階**

発表者は、メーカーを次の 3 段階で育てると説明します。

1. オンボーディング
2. スキル構築
3. 高度な実践（advanced practice。発話では "the first thing is the advanced practice" と聞こえますが、順序から 3 番目の段階と読めます）

これらを担う、選ばれた人たちがコミュニティづくりを助けます。

**イベントから始めない**

発表者は、「私が最初に手がけたのはイベントではない」と述べ、最初に犯しがちな間違いはイベントを作ることだと言います。イベントから始めて、2,000 人を超える人に「コミュニティを始めたので WhatsApp グループ、Telegram、Teams のチャンネルに参加してください」と告げても、その日のうちに、LinkedIn や Twitter、自分自身の投稿でも「コミュニティに参加を」という告知を目にする、と指摘しています。つまり、イベントは目標の達成には役立つことがあっても、コミュニティそのものは育てない、という考えです。

イベントの後に続く流れは次のとおりです。

1. 認知（awareness）を作る。
2. スキルを育てる。ビジネス目標を作ってあるので、「この人たちにはどのスキルが必要か」が決めやすくなる。
3. ソリューションを作る。
4. 進捗を示し、人を称える（celebrate）。

事例として、**State Farm** が紹介されました。学習者をチャンピオンに変えた組織で、最大のワークショップには 150 人超が参加したそうです。発表者は、紹介した企業は 150 人から数千人まで規模がまちまちですが、いずれもその時点で得られた最良の成果であり、「5,000 人いなければ成果を示せない」わけではない、と述べています。2 人のとき、10 人のとき、1,000 人のとき、それぞれの時点で成果を示すことが大事です。

### 5.5 続けるために：チャンピオンとオフィスアワー

次の問いは「どう続けるか」です。発表者は、**チャンピオンが主催するオフィスアワー**を挙げています。

コミュニティを続けてくれる人は、多くの場合、最初は「コミュニティ活動をやりたくない」と言っていた人たちです。「なぜ私に来いと言うのか。時間が無い」と言う同僚が、チャンピオンに変わることがあります。そこで発表者は、アドバイスとして、**コミュニティ活動には乗り気でないが、発信力（voice）のある人を探す**ことを勧めています。そういう人を味方にできれば、準備は整うという考えです。

事例は **ZF Group** です。20 人から 37,000 ユーザーに広がり、スライドには、Power Platform と Copilot Studio で **25,000 個のアプリ**が作られたことも示されていました。発表者は、こうした結果を見せ、ビジネス目標につなげる必要があると述べています。

### 5.6 従業員のいる場所で会う

勢いを保つ次の要点は、従業員がどこにいるかを見極めることです。従業員が Teams を好んでいるのに、コミュニティには WhatsApp が最適だと考えて WhatsApp に移るよう頼んではいけません。Telegram に慣れている人に「Telegram では駄目なので、こちらに来て」と言うと、その人たちを失います。発表者はこれを「最も重要なこと」と呼び、**常に相手のいる場所で会う**よう繰り返し述べています。

### 5.7 パートナーを探す

次はパートナーです。発表者は、IT のパートナー、データ分析のパートナー、ビジネスパートナー、さまざまなチャンピオン、エグゼクティブスポンサー、ユーザーグループを挙げ、これらの人々が、探している導入拡大を助けてくれると述べています。

事例として **Lumen** が紹介されました。7,800 人を超えるメーカーがおり、多くの成果を出しているそうです。発表者は、Lumen は Microsoft のパートナーの 1 社だとも述べています。

### 5.8 認知（recognition）

最後の要素が、コミュニティの人々を認め、称えることです。組織の中での人の位置づけに応じて、さまざまな形で示すことが大切で、できるだけ彼らをリーダーにし、感謝を示すよう勧めています。

事例として、"East Coast" と聞こえる組織（名称は音声認識の都合で確定できません）が紹介されました。Copilot の導入率を **4% から 74%** に伸ばし、3,000 人超を教育したそうです。

発表者は、これらの事例を見せたのは、コミュニティづくりが単なる追加作業だから求めているのではなく、**ビジネス目標のために必要な理由**を理解してもらうためだと説明しています。

### 5.9 最初の 90 日の計画

計画は次の順で示されました。

1. **小さな中核チーム**を作る。
2. そのメンバーを、教えられる**チャンピオン**に変えていく（自分 1 人ではできないため）。
3. **定期的なイベント**を始める。発表者は、これが 3 番目で、1 番目でも 2 番目でもないと強調しています。
4. 従業員がすでに使っているツールを使って、エンゲージメントを続ける。

## 7. 注意点・発表者の気付き

発表者が「気をつけてほしい」「やってはいけない」と述べた点を整理します。

- **イベントから始めない。** イベントはコミュニティではなく、火花にすぎない。イベントから始めると、全員が同じ日に複数の「参加してください」という告知を見るだけになる。
- **参加人数を成果にしない。** 5,000 人の参加者がいても、成果が出ているとは限らない。測定可能なビジネス目標と結びつけて示す。
- **最初から大きく考えすぎない。** 2 人から 1 万人を想像すると、始めにくくなる。1 から始めないと 500 にはならない。
- **従業員の使うツールを変えさせない。** Teams を好む人に WhatsApp を、Telegram を使う人に別のツールを強要すると、人が離れる。
- **乗り気でない人の中に、チャンピオンがいる。** 発信力があるのに、活動に消極的な人を味方につける。

## 9. まとめ

Copilot Studio の導入を持続させるには、エージェントを作るだけでは足りず、コミュニティが必要です。ただし、イベントを開くことはその始まりにすぎません。まずビジネス目標と結びついた、測定可能なミッションを決め、小さく始めます。

そのうえで、オンボーディング、スキル構築、高度な実践の 3 段階でメーカーを育て、乗り気でなかった人を含めてチャンピオンを作り、オフィスアワーで勢いを保ちます。従業員のいる場所で活動し、IT、データ、ビジネスのパートナーやエグゼクティブスポンサーを巻き込み、貢献者を認めてリーダーにします。最初の 90 日は、小さな中核チーム、教えられるチャンピオン、定期イベント、既存ツールでのエンゲージメントの順で進めます。
