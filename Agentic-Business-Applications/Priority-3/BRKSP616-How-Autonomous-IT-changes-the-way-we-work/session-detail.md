# BRKSP616 How Autonomous IT changes the way we work

## 1. はじめに

このセッションは、IT ヘルプデスクの仕事を「自律型 IT（Autonomous IT）」でどう変えられるかを、Atera 社の **Robin** という製品を軸に紹介するものです。Robin は「AI テクニシャン」と位置づけられ、端末上で診断から修正、ユーザーへの確認、チケットのクローズ、ログの記録までを、人間のテクニシャンを介さずに行います。

発表の骨子は次のとおりです。

- 従来の AI チャットボットは、ユーザーに手順を案内するだけで、端末の状態を見ることも操作することもできない
- Robin は、ユーザーの申告、端末で実際に起きていること、テクニシャンの過去の対応という 3 つを同時に見る
- 顧客事例では、ある組織でチケットの 67% が人の手に渡る前に解決され、別の組織では 85% が Robin によって解決されている
- IT チームの新しい仕事は、Robin に自社のやり方を「教える」ことになる

このセッションでは、画面を使ったデモが行われています。競合他社の Web サイト上のデモ、および Robin の 3 つの動作例（端末が遅い、ヘッドセットが使えない、印刷できない）が、登壇者の解説とともに紹介されました。ただし、これらがライブ操作か録画かは、登壇者は明言していません。

## 5. 発表内容の詳細

### 5.1 IT の問題の実態

冒頭で登壇者は、会場の全員が IT の問題を経験していると指摘します。例として、午前 8 時 58 分に、CEO が午前 9 時の取締役会に入ろうとしたところ、ヘッドセットがつながらない、という場面が紹介されました。これはおそらくチケットにはならない問題ですが、失われた 1 分であり、そうした分が積み重なります。

登壇者自身の経験として、数週間かけて準備した顧客向けのプレゼンの直前に、会議が Zoom ではなく Cisco Webex だと気づいた話も出ました。端末に Webex が入っておらず、ダウンロードの権限もありませんでしたが、幸い IT チームの人が間に合うように助けてくれて、商談を取れたとのことです。

Atera が今年の初めに数千人へ行った調査では、次のような結果が出ています。

| 項目 | 結果 |
| --- | --- |
| 毎日、IT の問題で数分を失っていると答えた従業員 | 約 88% |
| そのうち、毎日 20 分以上を失っていると答えた人 | 約 35% |
| 同じグループのうち、報告しなかった問題があった人 | 37% |

多くの問題が、チケットが提出されないために検知されないままになっている、という点が強調されています。例として、米国中西部の顧客の女性の話があります。新しいプリンターが届いてから数週間、設定の仕方が分からず、印刷が必要になるたびに、キャンパスの別の建物にいる友人にメールで送って印刷してもらっていました。1 日に何度もキャンパスを歩いて取りに行っていたのは、IT に頼むのが恥ずかしかったからだそうです。

### 5.2 従来のチケットの流れ

登壇者は、今日の標準的な IT の流れを次のように説明します。

1. ユーザーが問題に遭遇する。チケットにする価値があると判断した場合だけ、複雑なフォームで提出する。
2. チケットがキューに入り、テクニシャンが取り上げる。
3. テクニシャンは、情報の質に不満を持つことが多い。たとえば「PC が遅い」としか書かれていない。
4. 連絡を取り、都合の合う時間を探す。相手は昼食に出ていたり、印刷に行っていたりして、やり取りが何度も往復する。数秒で直せる問題が、数時間かかる。
5. 接続してリモートで操作し、直ったかを確認し、また同じ流れが始まる。

登壇者が顧客に「チケットのうち、人の介入なしで解決している割合は」と尋ねると、答えはほぼ必ず 0 だそうです。

### 5.3 競合のデモと会話型ナレッジボットの限界

登壇者は、競合他社（社名は伏せられています）の Web サイトにあるデモを、手を加えずに見せています。ユーザーが「PC が固まる」と言うと、強制終了を試す、開いているアプリを閉じる、エージェントにつなぐ、といった手順が案内されます。登壇者は、これは問題をユーザーに返しているだけで、いわゆる「ディフレクション（deflection）」だと述べています。ユーザーに自分で解決させるという意味であり、問題解決のための操作は何も行われていません。

今日の IT 分野の「従来型 AI」は、会話型のナレッジボットのことです。ユーザーとやり取りし、質問し、修正方法を説明し、ときにはテクニシャン向けに情報を集めます。しかし、そのデバイスで実際に何が起きているかを見ることも、解決のための操作を行うこともできません。ヘルプデスクに頼む人は、自分では解決方法が分からないか、自分で解決したくない人だ、という指摘もあります。

### 5.4 Robin とは何か

Robin は「AI テクニシャン」と考えるのが最も分かりやすい、と説明されています。特徴は、**デバイスやネットワーク上のエンドポイントで実際に操作を行い、ティア 1 とティア 2 の問題を、人のテクニシャンを介さずに解決できる**ことです。

Robin の動きは次のとおりです。

1. 診断：根本原因を理解する（「遅い」という訴えには多くの原因があり、まず絞り込む）。
2. 修正：取りうる操作や組み合わせの中から、適切な方法を選んで直す。
3. ユーザーとともに結果を確認し、満足していることを確かめる。
4. チケットをクローズする。
5. 行った操作はすべてログに残り、チームが監査できる。オペレーターにとって不透明なものは何も無い、という説明です。

### 5.6 Robin が同時に見る 3 つの情報

Robin の強みの核心（登壇者の言う secret sauce）は、3 つのことを同時に見られる点だと説明されています。

1. **ユーザーが報告したこと**：会話型ボットも見られる情報です。ナレッジベースやランブック（runbook）を参照して解決策を示せます。
2. **エンドポイントで実際に起きていること**：デバイスに軽量なエージェント（lightweight agent）が入っています。診断を実行して、問題の根本原因を把握できます。
3. **テクニシャンのこれまでの対応**：過去にテクニシャンがどう対応してきたかも見ています。

この 3 つを組み合わせることで、市場にある他のソリューションより多くの問題を解決できる、と登壇者は述べています。

### 5.7 セキュリティと導入の進め方

AI にはセキュリティ上の懸念がある、という前提に立ち、登壇者は次のように説明します。

- **Secure by default**：エンドポイントのエージェントは、**そのユーザーと同じ権限を継承**して動きます。直接指示されていないことは行えません。ワンオフの操作に対して、特定の昇格した権限を与えることもできます。
- **信頼を築くことが大切**：導入は「crawl, walk, then run（這う、歩く、走る）」の順で進めるのが一般的です。最初から何でも任せるのではなく、プリンターの問題、PDF、Office の問題といった簡単なケースから始め、動くことと信頼できることを確かめます。そこから、解決できるチケットの割合を 30%、40%、60% から 80% へと広げていきます。

### 5.8 Robin の機能と連携

Robin は、すぐに使える状態で**約 600 のアクションを実行**できます。登壇者は、これを 2 つに分けています。

**デバイススキル**：デバイスの上で診断し、直す機能です。たとえば「印刷できない」と言われたとき、どのプリンターが入っていて、既定のプリンターがどれかを知ることが重要です。「Zoom や Teams の通話で音が聞こえない」という場合も、そのデバイスで何が起きているかを知る必要があります。そうしないと、誰にでも当てはまる一般的な答えになってしまいます。デバイスの履歴や、ユーザーがこれまで訴えてきたことも把握したい、と説明されています。

**クラウドアクション**：他のシステムと連携する機能です。「IT にとっての 1 つの窓口、1 つの Robin」が、与えられたガードレールの範囲で、人の介入を待たずに解決することを狙っています。代表例はパスワードのリセットです。これは組織ごとに調整できます。

- 単純な例：ユーザーが「パスワードを忘れた」と言うと、2 要素認証を使って、一時パスワードがテキストメッセージで送られる。
- 複雑な例：金融サービスの顧客の中には、IT 担当者との会話と、政府発行の ID の提示を、パスワードリセットの前に求める組織がある。Robin はこれにも対応できる。

さらに、Robin は「チームの延長」として、今の働き方の中で動くことが重要だと説明されています。

| 連携の対象 | 発表で挙げられた内容 |
| --- | --- |
| ID プロバイダー | Entra（ほかの ID プロバイダーにも対応） |
| チケットを受け付けるチャネル | Microsoft Teams、サービスポータル、メール、電話 |
| ITSM | ServiceNow、Jira、Freshdesk など、主要な ITSM |

**Robin Voice**：最近発表された機能です。多くの組織で、チケットの約 20〜40% がいまだに電話で入ってくるため、これに対応するものと説明されています。登壇者は、ブースに案内したいが水浸しになっている、とも冗談を言っています。

**ITSM との関係**：数十年使われてきた ITSM を入れ替えるのは非常に大変なので、使っているものの上で動くようにしています。Robin のあらゆる操作とやり取りは、ユーザー起点のものも含めてログに残り、ITSM 側のプレイブックにも従います。特定の問題を扱うチームがあればそこへルーティングし、特定の種類の問題に承認フローが必要なら、それにも従えます。なお、登壇者は、Atera 自身にもチケット管理システムと RMM があるが、すでに使っている環境の中でシームレスに動けることを重視している、と説明しています。

### 5.9 Robin の動作例（デモ）

登壇者は、3 つの例を選んで見せています。画面の細部は音声からは確認できないため、以下は語られた範囲に限ります。

**例 1：PC が遅い**

- ユーザーが「PC が今日は遅い」と入力します。登壇者は、これは IT テクニシャンが最も不満を感じるチケットで、コンテキストがゼロだと述べています。
- Robin はデバイスに行き、人間のテクニシャンと同じように動きます。CPU、メモリ、ディスク容量、バックグラウンドで動いているプロセス、起動時に読み込まれるものを確認します。ユーザーが 1 秒も待つことなく、リアルタイムに行われます。
- 原因をすぐに特定できない場合は、ユーザーに質問します。ユーザーは、PC 全体で、何をしていても遅い、と答えます。
- Robin は、ディスク容量や RAM 不足のようには見えず、起動時に立ち上がるバックグラウンドのアプリが原因らしいと判断します。電源プランを確認し、エラーログを調べ、掘り下げを続けます。
- 画面に表示されたものはすべて ITSM に記録されます。登壇者は、実際のテクニシャンが残すより、はるかに精度の高いデータが得られると述べています。
- 結果として、最大の問題は Chrome の特定のタブにあると特定します。Robin が「再起動してよいか」と尋ね、ユーザーは「はい」と答えます。画面の右側にはタスクマネージャーが見えています。その後、Robin は問題が解決したかを確認し、ユーザーにも確かめます。

登壇者は、現在の平均的な IT チケットは **8 時間** かかるとし、これほど単純な問題で 8 時間待つのは不要だと述べています。

**例 2：ヘッドセット（CEO）**

- 冒頭の CEO が、午前 9 時の会議の前に Robin に「ヘッドセットのどこが悪いか分からないが、相手に自分の声が聞こえない」と伝えます。
- Robin はまず**プレイブック**を参照します。登壇者はプレイブックを「Robin に教える指示」と説明しています（後半の 5.12 でも、テクニシャンがプレイブックを磨く話が出ます）。Robin は、出力デバイスの選択ミスか、ドライバーの問題かなどを調べます。
- Robin は、Jabra のヘッドセットは接続されているが、Windows が内蔵のマイクとスピーカーを使い続けていることを突き止めます。
- 入力と出力を切り替えて解決します。数秒で済み、誰かに助けを求める必要がありません。

**例 3：印刷できない**

- ユーザーは最低限の情報として「印刷できない」とだけ伝えます。
- Robin は、スプーラー、既定のプリンター、エラーログを確認します。印刷サービスは動いているが、Windows がうまく通信できていない状態だと判断します。
- プリンターサービスを更新し、以前のプリンターを見つけ直します。ユーザーに「これが使いたいプリンターか」と尋ね、ユーザーが特定の HP プリンターだと答えます。
- さらに「テストページを送ってよいか」と尋ねます。

この例では、すべてが ServiceNow に記録される様子も示されました。登壇者は、どの ITSM でも同じように、Robin のあらゆる操作とやり取りを記録できると述べています。

### 5.10 エンドツーエンドで解決するための 4 要素

登壇者は、問題をエンドツーエンドで解決するとは、ユーザーに何をすべきかを伝えることではない、として次の 4 つを挙げています。

1. **ユーザーに指示を出さない**：デモでは、ユーザーは操作を求められておらず、「PC が遅い」「印刷できない」「誰にも聞こえない」と伝えただけでした。
2. **テクニシャンを介さない**：多くの組織は効率化の圧力を受けており、組織が成長しても、ヘルプデスクを同じ比率で増やし続けたくありません。テクニシャンの作業を減らし、より大きな課題に取り組めるようにするのが大切だと説明されています。
3. **エンドポイントで操作する**：ナレッジボットではなく、印刷サービスの再起動、出力の問題の特定、遅さの原因の特定とその対処まで行う。
4. **ユーザーに確認し、フィードバックループを作る**：満足できる形で解決したかを確かめ、時間とともに賢くなっていく。

### 5.11 ROI（Forrester の調査）

顧客のデータに加えて、Forrester が過去数か月にわたって Atera と行った調査で、**Total Economic Impact（TEI）** が公表されたと紹介されています。幅広い顧客への聞き取りの結果、Robin に使った 1 ドルあたり **3.2 倍**のリターンがあるという数字です。

ROI には 2 つの側面があるという説明です。1 つは、テクニシャンの時間をどれだけ節約できるかという分かりやすい側面です。やり取りの往復、チケットの作業、ユーザーの追跡、デバイス上の実作業の時間が含まれます。もう 1 つは、エンドユーザーが誰かの助けを待たずに解決を得られるという側面です。

登壇者が印象に残った言葉として挙げたのは、AI の時代に IT 部門への期待は、問題を解決するだけの受け身のヘルプデスクから、はるかにプロアクティブな存在へ移っている、というものです。

### 5.12 IT チームの役割の変化：Robin に教える

「自律型 IT の世界で、IT チームはどうなるのか。これまで 40〜80% のチケットを解いてきた人たちはどうなるのか」という質問は、よく受けるそうです。登壇者の答えは、**新しい仕事は Robin に教えること**です。

Robin は、15〜20 年の経験を持ち、いつも礼儀正しく、時間に正確で、休暇も取らない最高の IT テクニシャンのようなものです。ただし、その組織のことは何も知りません。プロセス、ポリシー、エスカレーションのやり方、どれに承認や権限が必要か、どの連携を使えるようにするか、といったことです。

登壇者は、IT チームの働き方に大きな変化が起きていると述べています。チームは今、AI を使いこなして組織により大きな価値を提供する方法を学んでいます。端末が遅い理由が「3 年半再起動されていなかったから」と分かるような、従来の仕事を大きく超える内容だそうです。

**顧客のグラフの例**

実際の導入事例として、月ごと（横軸は月）のテクニシャン別の解決チケット数のグラフが紹介されました。Robin の解決割合は毎月増えています。これは、テクニシャンが「悪くなっている」ことを意味するのでしょうか。この顧客は、**Robin の成功をテクニシャンの実績として評価する**ようにしました。グラフには Dana、Riley、Ryan、Logan といったテクニシャンの名前が出ていて、彼らの仕事は Robin を「使えるようにする（enabling）」ことになっています。

たとえば Dana が、より多くの人が早く仕事に戻れ、困りごとが減り、いら立ちが減るプレイブックを作ったなら、それは彼女の仕事の大きな部分です。手作業に時間を使うのではなく、AI に指示を出す立場にいるためです。Dana のシェアは縮んで見えますが、組織への影響はむしろ大きくなっている、という説明です。

先進的な IT 組織は、プレイブックを磨くことに時間を使い、最も価値を出せる領域を探しています。スナップショットとして、解決されている問題の種類とカテゴリが示されました。

- コアアプリケーションのアクセス処理（core application access handling）：届いたチケットの **95%** を Robin が解決し、解決件数は 653 件
- 備品の依頼処理（work equipment request handling）：ハードウェアの世界は Robin にできることに限りがある。ただし、ここも掘り下げて改善できる領域

どんな情報を集めるか、どのシステムから情報を引くか、承認プロセスはどうあるべきか、手順はどうするか。これがテクニシャンにしてほしい仕事だと述べられています。目指すのは、「もう 1 件、あるいは 10 件閉じる」という直線的な仕事を超え、組織と自分たちに力を与え、**AI テクニシャンとしてレベルアップ**することです。

### 5.13 成熟度の 5 段階

登壇者は、組織が成熟度曲線の上にあるとして、5 段階を挙げています。

| 段階 | 内容 |
| --- | --- |
| 1. ticketing foundation | チケット管理の土台。あらゆる IT の基礎 |
| 2. self-service knowledge | エンドユーザー向けのナレッジベース。ナレッジ管理は構築も維持も非常に難しい領域 |
| 3. answer bot | 質問すると、さまざまなナレッジソースを見て、リアルタイムに正しい答えを返す |
| 4. self-service help desk | パスワードのリセット、承認済みリストからのソフトウェアのダウンロード、アプリへのアクセス申請などを、ボットが手伝う |
| 5. autonomous IT | エンドポイントで問題を解決する。チケットの 40〜80% を無くす |

最上位の自律型 IT では、エンドユーザーにとって SLA は 0、テクニシャンはもっと面白い仕事ができます。登壇者は、チケットの両側を解放することで、IT 組織はより深く関与し、より主体性と影響力を持つ、と述べています。エンドユーザーはヘルプデスクを待ちたくなく、できるだけ早く解決を求めている、という指摘も添えられています。

### 5.14 締めくくりの逸話

Robin を展開し始めたころ、顧客を訪問したところ、導入後にチケット数がむしろ増えていました。理由が分からず、エンドユーザーに聞き取りをしたところ、以前は IT チームに評価されたくなくて、チケットを出すのが恥ずかしかった、という答えでした。AI の導入にはさまざまな懸念があることを、Atera も認識している、と登壇者は述べています。

Robin は、人間のテクニシャンと話したいと言えばすぐにつなぎ、いら立ちを感知した場合もつなぐように作られています。ただ実際には、ユーザーは Robin を気に入って繰り返し使い、以前よりはるかに多くのチケットを開くようになり、期待以上の効率が得られている、と述べています。

## 7. 注意点・発表者の気付き

- **ユーザーはチケットを出さないことが多い**：調査では、報告しなかった問題があった人が 37%。恥ずかしいから、という理由で報告されない問題もあります。
- **権限は最小から始める**：Robin はユーザーと同じ権限から始まり、昇格した権限は特定の操作にだけ与えられます。
- **信頼は段階的に築く**：crawl, walk, run のアプローチが勧められています。
- **ハードウェアには限界がある**：備品依頼のような領域では、Robin にできることに限りがあると登壇者は認めています。
- **AI には知識がない**：Robin は優秀でも、自社のプロセスやポリシー、承認ルールは教えないと分からない。
- **成功の測り方を変える**：Robin の解決割合だけを見ると、テクニシャンの成果が縮んで見える。プレイブックを作った貢献を評価する、という顧客の工夫が紹介されました。
- **解決率は顧客によって差がある**：登壇者は、67%、85%、あるいは 40% と差が出る理由について、答えは Robin の作り（3 つの情報を同時に見られること）にあると述べています。また別の箇所で、どこまで任せるかは組織の姿勢にも左右されると述べています。

## 9. まとめ

Atera の Robin は、会話型ナレッジボットとは違い、端末上で診断し、修正し、ユーザーに確認し、ログを残すところまでを担う AI テクニシャンです。ユーザーの申告、エンドポイントの実態、テクニシャンの過去の対応を同時に見ることで、顧客によっては 67%、85% のチケットを人の手に渡る前に解決しています。Forrester の調査では、1 ドルあたり 3.2 倍のリターンが示されました。

登壇者は、IT 担当者の新しい仕事は Robin に自社のプロセスや承認ルールを教えること、つまりプレイブックを磨くことだと述べています。導入は簡単なケースから始めて信頼を築き、5 段階の成熟度の最上位である自律型 IT を目指す、という流れです。
