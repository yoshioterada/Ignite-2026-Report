# THR978 Hardening MCP: Advanced Security and Scale for Enterprise AI Hubs

## 1. はじめに

このセッションは、MCP（Model Context Protocol）を開発段階から本番運用、それも企業規模・グローバル規模に引き上げるときに、何を考え、どう守るかを話す約 25 分の講演です。「MCP を作って動かす」ことではなく、「大量のシステムとユーザーが接続する本番環境で悪意ある相手から守る」ことに焦点を当てています。

登壇者は、現場でのデリバリー経験が長く、失敗の「傷跡」を持つ立場から、最小限の製品（MVP）ではなく大規模運用を前提に話すと冒頭で述べています。内容は、MCP の認証強化の経緯、ゲートウェイを中心にした構成パターン、認証・ネットワーク・プロンプトインジェクション・ガバナンスの各対策、そして Azure のサービスを組み合わせた参照パターンです。画面を使ったデモはなく、チェックリストのスライドを撮影して持ち帰るよう案内して終わります。

## 5. 発表内容の詳細

### 5.1 本番・大規模運用で考えるべきこと

登壇者は冒頭で、会場に MCP を聞いたことがあるか、実際に使ったか、問題に遭遇したかを尋ねました。完璧な技術は存在しないという前置きのうえで、前週に起きた Microsoft のインシデントにも触れています。このとき、Satya 氏が MCP に約 90 秒を割いたことをうれしく思うと述べています。

開発と本番は別物で、本番では最小限の製品ではなく大規模を想定する必要があります。例として、有名人がテレビで製品に言及して突然 10 万人、1,000 万人、ワールドカップなら 1 億人がアクセスする状況を挙げました。AI を使うよう言われている状況で、悪意ある攻撃者が存在することを前提にします。このセッションでは、誤った設定による事故ではなく、悪意ある脅威に焦点を当てます。

スケールの問いは、1 つのシステムの接続なら動くが、複数の VNet、VLAN、Azure リージョン、他のクラウドにまたがる 1,000 のシステムが接続したらどうなるか、というものです。適切な相手とだけ通信させるにはどうするか、最小権限と分離をどう考えるか、接続してくる相手が本当にその相手かをどう信頼するか、を考える必要があります。登壇者は、昔は「管理者権限をください、全部できます」と言っていたが、今は最小権限で考えると述べています。

### 5.2 MCP の認証強化

昨年までの MCP は、接続時にハンドシェイクで認証の手続きを行えば、その後はすべて問題ないと見なされていました。登壇者はこれを、訪問販売を名乗る人に「信頼できそうだから家に入って」と言うようなもので、入った人はすべてにアクセスできる状態だったとたとえています。

今年に入り、これを強化する変更が入りました。往路も復路も完全に認証し、誰が、またはどのシステムが自分のシステムと通信しているかを確認する、という考えです。**各リクエストは自己記述的**になり、プロトコルのバージョン、クライアントの機能、通ってきた経路といった情報を持ちます。登壇者は、これらはセキュリティ上必須だと述べています。

### 5.3 ゲートウェイを中心にした構成

構成は次のとおりです。

1. エージェントが、ゲートウェイ（場合によってはロードバランサー）を呼ぶ。
2. 各リクエストが自己完結しているため、ラウンドロビンで振り分けられる。
3. ゲートウェイはルーティング、認可、レート制限を行う。
4. MCP サーバーに届き、データを取得して戻る。ここでは、すべての MCP サーバーが同一で、選択の問題はないと単純化している。

ロードバランサーが必要な理由として、登壇者は Microsoft が公開した前週のインシデントの根本原因分析に触れました。簡単にまとめると、サーバーが復旧するとすぐ過負荷になって再びオフラインになり、自己増殖的に広がったという内容です。点と点の直接接続ではなく、間に分散させるシステムを置くという考えです。

戻りのリクエストも自動的に信頼せず、すべて検証します。国家や企業を含む悪意ある主体は、接続して抜け穴やバグを探し、報酬を得ており、企業スパイもその一つだと述べています。

### 5.4 明示的であること、エージェント ID

登壇者は、Microsoft 365 Copilot など生成 AI を使う人に、インターンや 7 歳の子どもを相手にするつもりで、指示は曖昧にせず明確にするよう伝えていると話しました。同じく、セッション（暗黙の継続状態）ではなく、明示的に扱う方針です。

すべてを結びつけるための仕組みとして、Microsoft Entra のエージェント ID を挙げています。AI を扱うなら必ず確認すべきもので、Agent 365 も、探索方法の 1 つとしてこれを使います。

ステートレスにするとスケールしやすい一方、マルチテナントでは苦労します。同じクライアントの中でも、テナントをまたぐなら、往路・復路の認証とセキュリティをすべて確保します。決して仮定してはいけない、というのが主張です。ゲートウェイを使い、すべてがゲートウェイに認証されて入るようにし、テナントをまたぐか同じテナントに留めるかを制御します。

登壇者は、複数テナントは可能な限り避けたいと述べています。クライアントがベストプラクティスの単一テナントに従わないことがあり、データ境界やデータ所在地の考慮が影響するためです。

### 5.5 拒否して報告する

ブロックするだけでなく、**拒否して報告する**ことが大切だと述べています。認証、ヘッダー、プロトコルが正しくない接続を落とすだけでは、誰が攻撃しているのか、どのデータを狙っているのか分かりません。接続できなかったときも、どこから接続しようとしたかを調べ、脅威として他の経路に報告すべきかを判断します。ペイロードも記録して報告します。

> 補足：登壇者は、ガバナンスの視点に立つと、カンファレンスで人と話していても「自分の秘密やデータを狙っていないか」と警戒するようになる、と冗談交じりに話しています。

### 5.6 検証の具体策

- ディスカバリーサービスを置き、エラーを適切に返し、すべてをログに残す。通ってきたものの出どころを特定し、認証して追跡する。
- 店で警備員が客を見ているように、サイバー空間でも、接続がどこに向かうか確認する。入口を通れても、その先に悪意があるかもしれない。
- 発行元を検証する。証明書が有効か、期限切れや名前解決できないものを信頼しない。
- 検証したからといって自動的に通さない。自分を信頼して入ってきた相手を、自分の認証情報で別のシステムへ通す仲介役になってはいけない。各段階で、何枚ものドアをカードキーで開けるように確認する。
- 煩雑に感じても、企業規模（数十万ユーザー、1 日に数百万リクエスト）では、1 つの不正リクエストで情報漏えい、金銭的・評判上の損失が生じうる。最初に手間をかけたほうが楽である。
- 予算を説得する必要があれば、コンプライアンスとリスクの担当者を同席させ、「やらなければ本番に出せない」と言ってもらう。
- アクセスは無制限にせず、期限切れにする。今日入れたからといって、来週、来月も入れるとは限らない。

### 5.7 ネットワーク境界

アイデンティティが 1 つの境界で、もう 1 つがネットワークです。公開アクセスは避け、Azure Front Door や仮想ネットワークを使い、公開をできるだけ閉じます。こうすると、接続できる人が限られ、余計なものを相手にしなくて済みます。登壇者は Azure Front Door を優れた製品としつつ、技術には時々不調がつきものだとも述べています。公開が絶対に必要な場合は、自分ではなく上位の人の署名をもらい、問題が起きたときに責任を取る人を決めておきます。

### 5.8 プロンプトインジェクション

MCP は人間が考えて入力するのではなく、モデルが大量に実行します。お茶やコーヒーを淹れる間に 10 万通りのプロンプトを押し込める、という例えが使われました。さらに MCP では、プロンプトだけでなく指示全体を含められるため、プロンプトを少し変えるだけで穴を開けられる可能性があります。問題が起きる前提で、何も信頼しないところから始める考え方を勧めています。

被害を限定する対策は次のとおりです。

1. **検出：** Azure AI Content Safety の Prompt Shields を、API Management ゲートウェイの層で強制する。ただし完璧ではない。登壇者は 10 歳になる息子のために、15 世紀の騎士の画像を生成しようとして、剣という概念がセーフティフィルターに引っかかった経験を紹介した。キング・アーサーや円卓の騎士は国際的に知られた題材だとして、Microsoft に伝えたと述べている。
2. **最小権限のスコープ：** 必要なときだけ与え、不要なら与えない。専用の領域を持たせ、そこから出ないようにする。
3. **スロットリング：** ゲートを通ったあとでも、バックエンドを叩きすぎないよう制御し、その状況も報告して、暴走を見つける。最初は友好的でも、5 分後に不穏なコマンドを出し始めることがある。
4. **人への確認：** AI が AI を設計する段階にはまだ至っていない。監視から、コンプライアンスや IT の担当者に、大量のコマンドが来ていると知らせて確認してもらう。通知しないより、通知するほうがよい。

### 5.9 ガバナンス

- **棚卸し：** 持っているもの、入ってくるものすべてのインベントリを持つ。シャドー IT は許さない。登壇者自身、中央の IT が 2 年遅れていて必要なものをくれず、シャドー IT を作ってしまうことがあると認めている。Entra のエージェント ID で発見できない MCP サーバーは、どのデータに触れるか分からず、露出している可能性がある。
- **即時遮断：** 悪意あるものは、フラグを立て、確認し、直ちにブロックする。正常だった他のシステムが侵害される場合もある。例えば、数週間、数か月にわたり毎分 100 回の呼び出しだった相手が、突然毎分 10 万回になったら、すぐにブロックしてから調べる。
- **監査証跡：** 外部境界に当たった時点から内部、そして外に戻るまでを追えるようにし、すべての呼び出し、与えられた各プロンプト、返された各データを記録する。保存コストと保持期間は検討が必要だと述べている。何か暴走したとき、監査証跡が助けになる。

### 5.10 Azure での参照パターン

Microsoft のイベントなので Microsoft の技術に絞ると断ったうえで、サードパーティの選択肢もあると述べています。次の要素が順に示されました。

| 層 | 使うもの | 説明 |
|---|---|---|
| 公開入口 | Azure Front Door（WAF 付き） | 最初の制御点 |
| ID | Microsoft Entra ID | 有効期限とトレーサビリティを持つトークンの検証。ID がなければどこにも通さない |
| ゲートウェイ | API Management | MCP サーバーのホストまたはフロント。レート制限、ヘッダーに基づくルーティング、製品とバージョンの分け方（新機能を持つバージョンに接続できる先を限定する）を設定 |
| コンテンツの安全性 | Azure AI Content Safety の Prompt Shields | 内部ユーザー、外部ユーザー、システムのいずれのプロンプトにも適用。内部の悪意ある主体も現実に起こりうる |
| コンピュート | Container Apps と環境、または Azure Functions | ステートレスな MCP プール。プライベートアクセス |
| シークレット | Key Vault | シークレットの保管 |
| データストア | プライベートエンドポイント | 外部公開しない |
| ネットワーク | VNet、Private Link、プライベート DNS、Azure Firewall | 送信トラフィックは Azure Firewall 経由 |
| 可観測性 | Azure Application Insights、Azure Monitor、Azure Log Analytics | テレメトリ収集。サードパーティも可 |
| 棚卸し | Azure API Center | 承認済みサーバーの単一のインベントリ。シャドーサーバーがすぐ目立つ |

これは大規模向けの参照パターンであり、ガバナンスチームを巻き込むよう勧めています。

### 5.11 実際の導入から得た教訓と、チェックリスト、ロボット犬

残り時間が短いと断ったうえで、次の教訓が語られました。

- 問題が起きたら、速やかに特定する。遅くてはいけない。
- 技術が増えるほど、特にレガシー技術とマルチテナントでは、技術の乱立が起きる。これを制御する。
- 良さそうに見えて入ってきたツールに、悪意のあるものが潜んでいる場合がある。

高いレベルのチェックリストのスライドは、写真に撮って持ち帰るよう案内されました。各項目は、それぞれ独自のホワイトペーパー、文書、手順になる規模だと説明されています。

冒頭で、AI が別の AI を攻撃する様子を見せる方法を考えたが難しいと述べていました。最後に、会場にいる Fido という名の犬型ロボットを紹介します。登壇者の会社は、自律巡回によるセキュリティ用途などでこれを使い、MCP サーバー経由で接続しています。愛らしく芸もできますが、実体はコンピューターで、アクセスされれば悪用されうる、現実世界への影響もあると述べました。例として、原子力発電所を巡回している場合に制御系に接触し、MCP を管理していなければ誰かに乗っ取られうる、と挙げています。システムだけでなく、物理的に作用するものに対する制御が必要だという主張です。

## 7. 注意点・発表者の気付き

- 完璧な状態に今すぐ到達できなくてよいが、持ち帰って本番システムをすべて止めるようなことはしない。より良い状態を目指す旅である。
- 戻りのリクエストも信頼せず、検証する。
- 点と点の直接接続を避ける。サーバーが復旧した直後に過負荷でまた落ちた、前週のインシデントが例として挙げられた。
- 拒否するだけでなく、報告する。どこから、何を狙って来たかを把握する。
- 検証した相手を、自分の認証情報で別のシステムに通す仲介役にならない。
- アクセスは無期限にしない。
- 公開アクセスは、絶対に必要な場合を除いて避ける。必要なら上位者の署名を得る。
- Prompt Shields は完璧ではなく、無害な依頼を止めることがある。
- シャドー IT と、Entra のエージェント ID で発見できない MCP サーバーを作らない。
- 監査証跡に保存コストがかかることは、検討が必要である。
- 物理的に作用するシステムでは、MCP の管理不備が現実世界の被害につながる。

## 8. 利用者にとっての利点

発表は、特定の製品の導入効果や顧客事例を示すものではありません。語られた効果は次のとおりです。

- 認証の強化、ゲートウェイ、ネットワークの閉域化、Prompt Shields、スロットリング、監査証跡を組み合わせて、大規模運用での情報漏えい、金銭的・評判上の損失のリスクを下げる。

## 9. まとめ

MCP を本番の企業規模で運用するには、開発時とは別の視点が必要です。各リクエストを自己記述的にして往復とも認証し、ゲートウェイとロードバランサーで分散し、最小権限、期限付きアクセス、ネットワークの閉域化で守ります。プロンプトインジェクションには、Prompt Shields、スコープの限定、スロットリング、人への通知で被害を限ります。

ガバナンスでは、棚卸し、不審な接続の即時遮断、すべての呼び出しの記録を行います。Azure では、Front Door、Entra ID、API Management、Content Safety、Container Apps、Key Vault、プライベートネットワーク、Azure Monitor、API Center を組み合わせた参照パターンが示されました。

最後に、チェックリストは写真に撮って持ち帰ること、そして物理世界に作用するシステムでは、MCP の管理不備が現実の被害につながりうることが述べられました。
