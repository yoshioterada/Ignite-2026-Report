# BRK501 Partners: Unlock growth with AI across apps, agents, and workflows

## 1. はじめに

## 5. 発表内容の詳細

### 5.1 3 つの課題領域と、エージェント・ワークフロー・アプリの役割

Thomas は、業務プロセスはエージェントだけで完結しないと述べています。エージェントは推論を担い、不確実な状況から明確な結論を導くことが得意です。ただし、あらゆる問題に LLM を使う必要はなく、一貫して動くワークフローのほうがずっと安価な場合があります。アプリは構造を与え、人間がエージェントやワークフローと視覚的な画面で関わる手段になります。

実際には、顧客が「エージェントを作らなければ」と考えても、掘り下げると解くべき問題がワークフローだった、という例が多いそうです。適切なものを見極めることがコスト効率にもつながる、と説明しています。

### 5.2 Copilot Studio の進化

Thomas は、製品は約 6 か月前とほぼ別物になったと述べ、進化を 3 つに分けました。

1. **作成者体験の改善**：デザイン体験の刷新。今週発表されたワークフローには、上から下か左から右かを選べるボタンがあり、Microsoft 社内でもっとも意見が割れる論点の 1 つだったと冗談交じりに紹介されました。自然言語とプロコードの両方で、誰でも業務プロセスを作れるようにする方針です。
2. **エージェントの能力向上**：約 2 か月前に Microsoft Copilot harness を導入。エージェントはより持続的で賢くなり、複雑な作業を担えます。
3. **運用者の共通基盤**：最初のエージェントを公開した後も、評価、改良、最適化を業務に近い人が続けられるようにする。Power Platform 由来のローコードの考え方です。

作成体験の拡張として、次の 2 点が紹介されました。

* copilotstudio.microsoft.com だけでなく、**Cowork の中から業務プロセスを直接作れる**。
* MCP 互換の CLI から自然言語で同じ機能を使える。プロ開発者が好みの IDE で Copilot Studio の成果物を作って公開し、非開発者が編集・改善を続けられる。Thomas は、パートナーが顧客のために作って、業務プロセスの組織側の所有者に引き渡す関係として興味深いと述べました。

### 5.3 Microsoft Copilot harness の効果

約 2 か月前に GitHub Copilot harness in Copilot Studio という名前で始まった技術は、社内で単一の技術に統一され、Microsoft Copilot harness in Copilot Studio と呼ばれています。Copilot Studio を最新のモデル技術に合わせてゼロから再設計した、と説明されました。

Thomas が示した社内でもっとも難しい評価（エバリュエーション）の結果は次のとおりです。

* 標準の harness と新しい Copilot harness を比べると、全評価で向上している。
* モデルの小刻みな更新（6.1 から 6.2、5.4 から 5.5 など）では、評価セットで通常 1 ポイント程度の改善。
* 標準の harness から Microsoft Copilot harness への移行では、10 から 20 ポイントの改善。
* 概算で、harness の効果はモデルの小幅な更新の約 50 倍から 100 倍。Thomas は、モデルは改善の源泉としてある意味コモディティ化していると述べました。

効率面も改善しています。Copilot harness ではエージェントの呼び出し回数がほぼ 2 倍に増えますが、プロンプトのキャッシュがはるかに多く効くため、Copilot クレジットのコストの最大要因である正味の入力コストが **15 から 21% 減る**と説明されました。品質向上と効率向上が同時に得られるという主張です。

標準の harness を使っているエージェントについては、Cowork で「このエージェントを標準の harness から Microsoft Copilot harness に移行して」と頼めば、Copilot Studio が移行を試みます。Thomas は、まだ完全ではなく改良中だと断っています。

### 5.4 アカウントを持つエージェント

Thomas がもっとも期待している機能として、エージェントにアカウントを持たせる機能が紹介されました。現状のエージェントは会話ペインの中に閉じているか、利用者から見えない自律プロセスとして動いています。しかし組織で働く人は人と働いています。そこで、エージェントを同僚のように組織に置き、次のことができるようにします。

* 自分の ID を持つ。
* Word、Excel、PowerPoint、Outlook、Teams など、人が働く場所で働く。
* A365（Agent 365）などの技術で、人と同じようにガバナンスをかける。
* 専用のコンピューターを持ち、実際の画面で応答できる。

この機能はプレビュー中で、12 月にパブリックプレビューに進む予定と説明されました。

### 5.6 パートナーの市場機会（Ben）

Ben は、毎年多くの調査会社と調べる市場調査をもとに、4 つの領域を扱うと予告しました。市場機会、「カンバセーション」（今年パートナーとともに進めている新しい共同販売の仕組み。固定報酬から成果ベース報酬やマネージドサービスへの転換を目指す）、機会、パートナー投資です。

覚えておいてほしい数字が 2 つありました。

* **81%**：パートナーも顧客も、マネージドサービスのコストをどう減らすかを常に求められている。エージェントが増えれば拡張しやすい動きが生まれ、市場の圧縮が起きる、という認識です。
* **93%**：多くの顧客は、成果ベースの契約と、投資対効果（ROI）がどこにあるかを見られることを望んでいる。

市場の見通しはインデックス値で示され、割合ではないと断られました。2025 年から 2028 年にかけて AI エージェントは大きく成長しますが、その成長の一部は、人が提供するマネージドサービスをエージェントで補うことを顧客が求めるため、マネージドサービスの利益から奪われる形になります。今後 2 年の転換先として、パートナー向けの共同販売、投資、市場投入の進め方を更新した、という説明です。価値が移る先は、FinOps、ガバナンス、エージェントの展開だけでなくライフサイクル全体を管理する、次世代のマネージドサービスです。

パートナーが成功している 5 つの領域として、Ben は次を挙げました。発話では、5 つが番号付きでは読み上げられていません。話された内容は次のとおりです。

* パートナー自身を最初の顧客（カスタマーゼロ）にして、自社の業務プロセス変革のマネージドサービスを作り、それを顧客向けにパッケージ化する。Ignite 全体で、そのためのパートナー向け提供物や投資を増やしてきた。
* 製品と繰り返し使えるソリューションを作る。エージェントが担える繰り返しの動きが探索フェーズにあるか、人の創造性とパートナー独自の知的財産（IP）が活きる領域はどこかを見極める。
* 大規模に運用し、価値を示す。

提供物としては、実践を変革するための資料が多数用意されています。パートナーのプレイブックは、将来のマネージドサービスを作るためのベストプラクティスをまとめています。評価（アセスメント）とそれに基づくアクションプランもあり、パートナーと顧客のセグメントごとに ROI の高い機会を見つけられます。資料とリンクは会議後に共有されます。

機会の規模として、**ユーザー 1 人あたり月 16 ドル**という数字が示されました。100、1,000、1 万、10 万ユーザーと採用が進むにつれ、パートナーにとって大きな額になる、という説明です。目的は初期展開ではなく、常時稼働のサービスで選ばれるパートナーになることです。顧客の全事業にわたる業務プロセス変革、エージェント・アプリ・ワークフローのガバナンス、セキュリティまでを視野に入れます。Ben は、消費と ROI の層を管理するための FinOps のツールも Microsoft が整備してきたと述べました。

### 5.7 カンバセーション、Frontier Accelerate、ASPX

**カンバセーション**は、Power Platform で広く行ってきた進め方を Microsoft 全体に広げたものです。顧客やパートナーと業務プロセスごとに ROI がどこにあるかを見ます。Power Platform と Copilot Studio では「あらゆる場面でのイノベーション（ubiquitous innovation）」と「業務プロセスの特定」の 2 つで構成され、従来の「X 人の従業員に展開する」という固定価格の話から、AI センター・オブ・エクセレンスの実践の確立へと進めます。事業部門ごとのフェーズ 1、フェーズ 2、そして企業が進められる案件とエージェントの一覧という、常時稼働の機会を見ます。

* あらゆる場面でのイノベーション：エージェント中心の会話。効率、ガバナンス、セキュリティの向上を続け、パートナーが効果のあるマネージドサービスを作ってエージェントを保護するためのツールを整える。
* 業務プロセスの特定：ERP や CRM などの主要プロセスとエージェント型アプリが対象。Copilot Studio では MCP や Cowork プラグインの作成など、アプリ、エージェント、ワークフローを拡大して作る手段と、ガバナンスを整えた。

Ben は、これは従来の MSEN のモデルであり、営業の進め方だと説明しました。毎年、1 年の最後の 3〜4 か月に顧客の需要とパートナーが最も使う投資を調べ、顧客とパートナーのジャーニーを更新しています。

**Frontier Accelerate** は、現在の代表的なプログラムで、エージェント型の成長を狙うものです。販売前と販売後の両方を対象とします。販売前は、エージェントと業務プロセス変革を開発できるパートナーの機会を探ります。販売後は、エージェントの採用を拡大することが目的で、Microsoft はそこに先行投資するとしています。

**ASPX** は、昨年モダンワーク（Copilot）側で始まったパートナー向けダッシュボードです。Ben の説明では、次のことができます。

* 顧客ごとに、展開したライセンスの月間アクティブユーザー数を見る。例として、1,000 ライセンスのうち採用が 50% にとどまる顧客がわかる。
* 今後、消費レベルの指標や、見込み度（プロペンシティ）の指標を追加する。
* Copilot 側では、パートナーが更新率や次に売るソリューションをデータから見て共同販売を進めている。
* 営業チームが Microsoft の営業担当と繰り返し使える動きを作る対象を、Copilot と Cowork から Power Platform と Copilot Studio に広げる。

ASPX は Frontier Accelerate の採用フェーズを支える位置づけで、パートナー向けのダッシュボードに加え、PDM 向けのダッシュボード（略称の意味は発話では説明されていません）も用意されると説明されました。Ben はもう 1 つ、Microsoft のフィールド営業と共同販売してマネージドなライフサイクルの段階に入るためのプログラムにも触れる、と予告しましたが、発話では名称は確認できません。

プレビューには、次の 1 か月間チームで試せるようサインアップできると案内されました。

スケールのジャーニーは、ビジネスユーザーから IT 担当者までエージェントを広げる最新内容に更新済みです。FinOps については別のセッションが多数あり、顧客で想定外の支出が膨らまないよう、事業部門やユーザーごとの状況を把握するツールをパートナーに提供する、という説明でした。Ben は、81% と 93% の対比をもう一度示し、エージェントのライフサイクル全体でパートナーと顧客に選ばれるプラットフォームになることを目標とすると述べ、Copilot の専門性認定を持つパートナーなどに謝意を示しました。

### 5.8 パートナーインタビュー（KPMG と Verada）

Paula は、Partner of the Year Award のローコードアプリとエージェント部門の最終候補として、Accenture、Zlalan（音声認識の都合で綴りが確定できません）、Verada を紹介し、**受賞は KPMG** と発表しました。その後、KPMG の Marco Amuedo と Verada の Jordan O'Halloran を舞台に迎えました。

**マネージドサービスの圧縮にどう向き合うか（Marco）**
圧縮は現実で、従来型の実装やマネージドサービスの収益は減っている。一方、Ben のスライドにあった収益の連鎖の後半は、別の領域で広がっている。これらのツールは優れているが、採用、トレーニング、プロセスの進め方の変更に多くの支援が必要で、これまでの実装中心から、そうした多様なサービスを引き出している。全体としては圧縮があっても状況は良くなっている、という回答でした。

**価値ベースの価格設定は成り立つか（Jordan）**
うまくいく領域はある。繰り返し可能なソリューション、予測できる成果、理解しやすく繰り返せる KPI がある場合で、ISV の領域や Dynamics の自社製品領域が例です。一方、個別の企業向けエージェント開発や、Power Platform や Azure のカスタムソリューションでは、事前に KPI を定義し契約前に範囲を詰めるのに時間をかけすぎ、価値を届ける速さを損なう。そこで、最初にすべてを設計する従来型から、顧客の中でどれだけ速く価値を出せるかという「速度のパラドックス」に重心を移し、顧客の組織に入り込んで継続的にイノベーションを届ける周期へ移行している。これが FinOps やエージェント基盤のマネージドサービスの話につながる。Verada は **Frontier Operations** という市場投入の提供物を開始した。マネージドサービス、イノベーション、継続的な提供周期を、顧客に組み込む形で提供するもので、Jordan は FDE（顧客先に入り込む開発者）の契約にマネージドサービスを組み合わせたものと説明しました。Paula は、パートナーからよく聞かれる質問だと応じました。

**AI の拡大で組織はどう変わったか（Marco）**
過去 2〜3 年で大きく変えた。圧縮と機会の拡大を受け、大企業の複雑さを隠し、顧客には 1 つのプラットフォームとして見せる方向に作り直した。以前は Dynamics、セキュリティ、モダンワークなど別々の実践があったが、それが 1 つにまとまりつつある。顧客が求めるのは、Microsoft の描く構想や、業務プロセスを変革する技術を実行できるパートナーだからだ。同時に、採用や変更管理、設計の担当者と技術を一緒に動かすマトリクス型の組織を作っている。助言領域全体で技術の会話が増え、技術の実践同士も、プラットフォーム型プロジェクトのために融合している。

**IP の位置づけ（Jordan）**
IP は常に成長戦略の中核であり、今はこれまで以上に重要で、コミュニティ全員にとって重要だと答えました。エージェントやソリューションの開発は民主化され、Copilot Studio やバイブコーディング系のツールを使えば、誰でも数分で業務の中核アプリを作れると感じる時代になったが、そうではないことを私たちは知っている。差別化には、賢い人材や Microsoft 認定だけでは足りず、成果へのコミットと、届ける価値を示すことが必要で、いちばん簡単な方法が IP である。本格的な ISV ソリューション、アクセラレーター、デリバリーの手法がその形になる。Verada では、RFP に参加するかどうかの判断で、IP がなければ自分たちがそこにいるべきかを問い直すと述べています。IP は必ずしも ISV ソリューションとは限らず、実証済みの経験を示し、その顧客にとっての価値を具体的に説明できればよい、という補足もありました。

**Copilot を仕事の入口とするとき、クロスプラットフォームの視点はどれほど重要か（Jordan）**
Power Platform は、すべての実践領域に広がってきた。Copilot が仕事の OS になった今は、その傾向がさらに強い。すべてのパートナーがあらゆる分野の高度な専門性認定を持つ必要はない。Azure のソリューションが答えなのに Power Apps パートナーである場合や、Dynamics の力が必要なのに自社にその能力がない場合は、ISV を購入する、または他の Microsoft パートナーのサービスを使うなど、連携に開かれているべきだ。Verada も、自社が ISV ソリューションを提供する側にも、ISV ソリューションを買う側にも、特定の Dynamics パートナーのサービスを取り込む側にもなる。「上げ潮はすべての船を持ち上げる」という考えで、イノベーションの多い今は連携がよく機能する、という発言でした。

**Microsoft とのアライアンスの位置づけ（Marco）**
Paula は台本を変えて、特定メーカーを優先できないグローバル SI が多いことに触れ、KPMG のアプローチにおける Microsoft アライアンスの位置づけを聞きました。Marco は、自分は Microsoft 一筋だと断ったうえで、これまで KPMG を含む同業各社はあらゆる技術に中立の立場を取ってきたが、今はそうではないと答えました。本当に価値を出すプラットフォームには立場を取る。また、基調講演で Satya が示したように、いまはエコシステムの動きがある。Microsoft は素晴らしいプラットフォームだが、Salesforce、Oracle、ServiceNow など別のアライアンスも持っており、エコシステム全体で動くことで顧客への対応範囲が広がり、孤立した見方をやめられる、という趣旨です。主張を持つ場面も増えており、「これが推奨プラットフォーム」と言いつつ、顧客が別の選択をしても対応する。KPMG は自社でも Copilot、Cowork、Agent 365、Foundry、Power Apps、Copilot Studio を 30 万ユーザーで使っており、Marco は、受賞も顧客事例に関わる、という趣旨の発言をしています（聞き取りが不明瞭です）。自分たちで使って顧客に見せるので、中立の見方も変わった、と述べています。

### 5.9 参加者への行動の呼びかけ

Paula は、最後に 3 つの行動を示しました。

1. チームのスキルを育てる。多くの発表と革新があるので、パートナー向けの資料を使う。
2. 実践を築き進化させる。AI ファーストの変革パートナーになる。Copilot とエージェント向けに更新中のプラクティスガイドを使う。
3. 市場投入を加速する。Frontier Accelerate の投資（市場に出るための資金）や、Ben が紹介した各種プログラムを使う。

エージェント型アプリと Copilot に関係するセッションの一覧も示され、資料はイベント後にも参照できます。会場からの質問は、発話では確認できません。

## 6. デモ・手順

デモは Thomas が約 10〜11 分話した後に行われました。事前にキャッシュしたものを多く使っていて、うまく動くことを期待している、と断っています。画面の細部は音声からは確認できず、以下は語られた範囲です。

### 6.1 Cowork から業務プロセスを作る

1. Copilot Cowork を開く。Thomas は、あらゆる業務プロセスを自然言語から作れると述べ、デモのためにプロンプトをかなり作り込んだことを認めたうえで、実際は 5 段落も書く必要はないと話しました。
2. 顧客からのフィードバックを管理する業務プロセスを作るプロンプトを Cowork に送る。内容は、顧客のフィードバックを優先度付けし、割り当て先を決め、重大度を付け、経営層が状況を見られるよう可視化する、というものです。
3. Cowork が Copilot Studio という新しいプラグインを読み込む。スライドを作るときに PowerPoint につなぐのと同じように、Copilot Studio につないで成果物を作ります。
4. 処理には時間がかかるため、事前に実行済みの結果に切り替える。実行はおよそ 30 分で、プロンプト全体で Copilot クレジットが約 20 ドルかかった、と説明されました。
5. 結果として、ワークフロー、エージェント、アプリが 1 つずつ作られた（1 つずつ作るよう、プロンプトを調整してあります）。
6. アプリを開く。Copilot Studio の新しいアプリで自然言語から作られた成果物で、自然言語で改良もできます。データは SharePoint リストにあり、フィードバックと関連データを表示します。リロードで一度うまく表示されず、Thomas が戸惑う場面がありましたが、その後表示しました。
7. エージェントを開く。同じ自然言語の指示から、アプリに出るフィードバックを扱う指示が作られている。

### 6.2 エージェントにアカウントを付与する

1. 課題の整理：顧客からメールで問題の相談が多く届くため、エージェントを自分のそばで働く同僚にして、GAL（組織のアドレス帳）に載せ、自分に報告させたい。
2. エージェントにアカウントを追加する。プレビュー機能で、12 月にパブリックプレビューに進む予定です。
3. 権限を設定する。エージェント自身の認証情報を使うか、自分の認証情報を使うかを場面ごとに選べる。デモでは、ツールにはエージェントのアカウントの認証情報を使い、ワークフローには自分の認証情報を使う設定にしました。人に連絡するときに、エージェントのアカウントではなく自分から来たと見せたいためです。
4. エージェントの名前、メールアドレス、誰のために働くかを設定できる。デモでは Chase という人物になりきり、その部下としてエージェントを展開する形です。作成ボタンは、プロビジョニングに数分かかるため押さず、事前に作成済みの版を使いました。
5. 作成済みのエージェントには、完全なメールアカウントがあり、SharePoint、OneDrive、Exchange Online、Teams のアクセスが用意されている。組織内の完全な主体になります。
6. Outlook に移る。Chase 宛てに届いたフィードバックのメールに、「@feedback coordinator（作成したエージェント）、これを低優先度でトラッカーに追加して。他の顧客も同じ症状を報告している？」と返信し、同僚に頼むようにエージェントに依頼した。
7. エージェントは約 1 分考える。分類し、アプリ内の既存データと照らして優先度付けし、アプリに新しい項目を追加して、Chase に状況を返すはずだと Thomas は説明しました。
8. 失敗：全員に返信してしまい、組織外の自分の Microsoft アカウントに返信してしまった。やり直したところ、エージェントは自分の Microsoft アカウント宛てに返そうとする動作を組織の境界を守って拒否した、と Thomas は説明しました。Thomas はデモを失敗させたと話しています。
9. 待つ間に、過去に別の顧客からのフィードバックを送った例を見せた。エージェントが「ポータルに登録した」と返信し、フィードバックコード、要約、詳細を返している。
10. 最後のリフレッシュで、今回送った件への返信が届いた。内容は、項目は追加しなかった、似たものがすでにアプリにあるため、というもの。同じデータエクスポートの問題について、3 社の顧客が、少しずつ違う形で報告している、と説明されました。
11. feedback coordinator は Chase の部下として GAL に独自のエントリを持つ。Teams で話しかけたり、会議に追加したり、Teams チャットを始めたりできる。複数人が同時に使え、フィードバックを送るのが自分でも他の人でも、組織内の一員として同じようにやり取りできます。

Thomas のまとめは、自然言語による作成、Copilot harness による指示と能力の改善、Copilot Studio のエージェントアカウントの 3 点を見せた、というものでした。

## 7. 注意点・発表者の気付き

* デモの冒頭で、Thomas はプロンプトを意図的に作り込んだと認めています。5 段落も書く必要はありません。

## 9. まとめ

組織が所有する業務プロセスは、推論のエージェント、低コストのワークフロー、人との接点となるアプリを組み合わせて作ります。Copilot Studio は Cowork や MCP 互換の CLI からも使えるようになり、Microsoft Copilot harness により品質とコスト効率が同時に上がると説明されました。エージェントにアカウントを持たせる機能は、同僚としてメールや Teams で働く姿をデモで示しました（プレビュー中）。

パートナーにとっては、従来型マネージドサービスの圧縮が避けられない一方、FinOps、ガバナンス、エージェントのライフサイクル管理という次世代のマネージドサービスに価値が移ります。KPMG と Verada の事例からは、採用支援や変更管理などのサービス拡大、継続的な提供周期、IP による差別化、他のパートナーとの連携が挙げられました。参加者への行動は、スキルを育てること、実践を進化させること、Frontier Accelerate で市場投入を加速することの 3 点です。
