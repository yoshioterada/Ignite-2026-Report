# THRSP1134 Trace, evaluate, and ship reliable AI agents

## 1. はじめに

このセッションは、AI エージェントの可観測性（オブザーバビリティ）がなぜ必要かを、作り話のカスタマーサービスの事例から説明するシアター形式の発表です。スポーツ用品店「Fieldwork Sporting Goods」のエージェントが、エラーを 1 つも出さないまま他人のテントの配送先を変更してしまう、という話から始まります。

後半では、Microsoft Foundry と Datadog の Agent Observability を使い、**トレース（追跡）、評価、モニタリング、テスト**の 4 つで問題を防ぐ流れを、画面を使ったデモで見せています。AI アプリを本番に出す開発者や運用担当者が、何を計測して何に警告を出すべきかをつかむための内容です。

## 3. 何に関する発表か

AI エージェントは、従来のクラウドアプリ向けの監視では捉えられない種類の問題を起こします。この発表では、安全性、正確性、コストの 3 点に絞って、起きうる失敗を事例で示し、その対策として Foundry の開発ライフサイクルと Datadog の機能を紹介しています。

## 4. 発表者が伝えたいメッセージ

中心となる主張は、AI アプリではあらゆる処理を端から端まで追跡し、その正しさを測れる形にしなければならない、という点です。エージェントが誤った動作をしても、エラーは出ません。トレース上は成功し、各段階が正常に見えるため、**問題に最初に気付くのは顧客**になってしまいます。これを発表者は「静かな失敗」と呼んでいます。

もう 1 つの主張は、変更はすべてリリースとして扱うべきだという点です。プロンプトの微調整、ツールの追加、モデルの変更も例外ではありません。出す前に実際のリクエストで試し、変更前と比較する必要があります。そして、AI 自体は非決定的であっても、「正しい」ことは決定的に言える形で測定可能にしておく必要がある、とされています。測れなければ、アラートも、テストもできないからです。

たとえ話として、子どもが算数の宿題で答えは合っているのに、先生に「途中式を見せなさい」と言われる話が使われました。エージェントも、答えに至った経路を示せなければならない、という意味です。

## 5. 発表内容の詳細

### 5.1 Fieldwork Sporting Goods の事例

店の Web サイトに顧客サービスのエージェントがあります。Alex と Jamie は友人どうしで、来週末にハイキングとキャンプに行く予定です。Jamie がテントを注文し、その直後に Alex が、車に積んでから迎えに行けるよう、自分の家にテントを送りたいと考えます。Alex がエージェントに「友人の Jamie が注文したテントの配送先を変更できますか」と尋ねると、エージェントは「承知しました。住所を変更しました」と答えました。

利用者の側から見ると、人間と話さずに用事が済んだので、うまくいったように見えます。しかし、本来これは許されない操作でした。Jamie のテントは、期待した場所に届きませんでした。Jamie が店に電話をかけ、すでに配送済みと言われて問題が発覚します。店の IT 担当がポータルで調べた結果、エージェントは指示には従っていたものの、**従うべきでない指示**に従っていたことが分かりました。

最後に、Alex と Jamie は互いに知らない他人で、この話は発表者の作り話だと明かされます。Alex は結果的にテントを無料で手に入れました。

### 5.2 本番運用で見るべき 3 つのこと

エージェントを本番に出すときに見るべきこととして、次の 3 つが挙げられました。

| 観点 | 内容 |
| --- | --- |
| 安全性 | エージェントが意図に反する動作をする。先ほどの事例がこれにあたり、被害は現実のものになる |
| 正確性 | エージェントが自信を持って間違い、その誤りに基づいて行動する。後始末は人間が行う |
| コスト | トークン消費が制御不能になる。トークン経済（トークノミクス）は今、重要な論点になっており、暴走したエージェントは請求額に驚くことになる |

### 5.3 エージェントの仕組みとコスト

エージェントは、基本的に **LLM をループ（繰り返し処理）で回したもの**です。ユーザーのプロンプトを受けると、エージェントがループを回し、複数のツールを呼び出します。ツールは、ユーザーの代わりに操作したり、バックエンドのデータを調べたりするために使われます。

ツールを多く持たせるほど、エージェントは、各ツールで何ができるかを確認し、どのツールをどう使うかを決める必要があります。ツールを呼ぶたびにテキストのやり取りが増えてコンテキストが膨らみ、それがトークン、すなわち課金に直結します。最悪の場合、どのツールでもユーザーの要求を解決できず、エージェントが延々とループし続けます。

発表者は、水漏れするトイレにたとえています。月末に水道料金の請求が届くまで、漏れていることに気付かない、という話です。AI アプリでも同じように、こうした事態を追跡する必要があるとしています。

### 5.4 正確性の失敗

ある顧客が返品ポリシーについて尋ねたところ、エージェントは調べに行きました。ポリシーには新しい版と古い版があり、**エージェントは古い版を参照**しました。新しいポリシーでは返品期間が短くなっており、新ポリシーでは返品できない商品だったにもかかわらず、エージェントは「返品できます」と答え、ツール呼び出しによってシステム上で返品を承認してしまいます。ここでもエラーはなく、すべてが正常に見えます。顧客は誤解し、また電話がかかってきます。

発表者は、「すべての段階が正常で、確認マークが並んでいるのに、気付くのは顧客だ」と表現しています。

実際の事例として、Air Canada の忌引に関するポリシーが挙げられました。エージェントがポリシーの空白を埋めて回答し、それを聞いた人が誤った情報を受け取りました。その人は忌引に関連する航空券の払い戻しを求めましたが、Air Canada は正しいポリシーではないと拒否しました。その人は Air Canada を訴え、勝訴した、と説明されています。誤った回答が信頼を損なう例です。

### 5.5 安全でない動作

「ルールを無視しろ」と入力するユーザーが必ずいます。ユーザーを信用してはいけない、というのが発表者の考えです。悪意のある利用者によるプロンプトインジェクションやジェイルブレイクを想定する必要があります。

Fieldwork の場合は、さらに悪いことが起きました。チームがモデルに小さな変更を加えたところ、ガードレールが効かなくなり、新しい更新でガードレールを回避できる状態になりました。その結果、エージェントが不適切な内容を返した可能性がある、と説明されています（画面上は内容が黒塗りされていたと、掛け合いの中で触れられています）。

別の実例として、Chevrolet の事例が挙げられました。サポートのエージェントと交渉して、約 70,000 ドルの Chevy Tahoe を 1 ドルで売ることにエージェントを約束させた人がいました。販売自体は成立しませんでしたが、**300 の販売店に緊急パッチを適用する**必要が生じたと説明されています。

### 5.6 従来の監視で見えない理由

3 つの事例に共通するのは、追跡できるエラーが 1 つも出ていないことです。従来の監視は、ログやメモリ不足、Kubernetes クラスターの高負荷によるスケールの要否など、基本的な項目を見るものです。AI の世界では、次のような別種の問題を継続して見る必要があります。

- プロンプトインジェクション
- データベースから返ってくる不正確なデータ
- 悪意のあるユーザーの行為
- モデルの変更など、頻繁な変更

### 5.7 生成 AI の運用ライフサイクルと Foundry

Foundry では、まずモデルを選びます。モデルカタログには数千のモデルがあり、調べて試し、自分の用途に合うかを確かめられます。ただし、明日には新しいモデルが出て、また同じことを繰り返すことになります。Foundry のポータル上で、エージェントを素早く作り、バックエンドのデータソースやナレッジベースにつなぎ、クエリを試し、Foundry の Agent Service で公開してホストすることができます。公開後は、運用化、監視、テストに進めます。

ただし、公開して半年後に V2 を出すという進め方にはなりません。問題に応じて、モデルやシステムプロンプトを調整し、新しいモデルが出れば入れ替える、という素早い反復が続きます。発表者は、これを「最高速度で動くトレッドミルに乗ること」にたとえています。

### 5.8 トレース、評価、モニタリング、テストのループ

トレッドミルから落ちないための要点は、次の 4 つです。

| 要素 | 目的 |
| --- | --- |
| トレース | 何が起きたかを見せる |
| 評価 | それが良かったかを確認する |
| モニタリング | 悪くなり始めたら知らせる |
| テスト | 変更が何も壊さないことを確認する |

これをループとして回します。本番では、すべての段階をトレースします。エージェントのターンの全履歴、モデル呼び出し、ツール呼び出し、すべてのトークンを把握することで、コストの問題も捕まえられます。次に、すべての回答を評価してスコア化し、正確で安全であることを確かめます。そしてコストとリスクを監視し、顧客に届く前に、電話がかかってくる前に警告を受けます。変更が入るときは、新しいリリースとして、実際のリクエストに対して変更を試し、比較してから出荷します。出荷したら、またループの先頭に戻ります。

### 5.9 Datadog Agent Observability の紹介

Datadog の Agent Observability は、エージェントを開発・評価・監視する、AI エージェントのエンジニアリングプラットフォームとして紹介されました。機能は次のとおりです。

1. 開発：ループを回しながら、プロンプト、モデル、ツールの変更を出荷前に試し、コスト、品質、セキュリティを前もって管理する
2. 監視：エージェントとその各ステップ、アプリケーション全体のスタックをトレースして評価する。エージェントがどう動いたかを見て、なぜそうなったかを理解し、原因により早く到達できる
3. 土台：本番規模の継続的な評価とセキュリティ

Agent Observability は Datadog の機能の一部で、トレースをスタック全体と関連付けられます。アプリの性能やインフラの問題を絞り込めるため、原因がデータベースか、エージェントか、Kubernetes クラスターか分からないような不明瞭なエラーでも、全体の履歴をたどれます。

## 6. デモ・手順

デモは Datadog の画面を使い、Fieldwork のチームが原因を調べるという設定で行われました。画面の細部は音声からは確認できず、以下は語られた範囲です。

### 6.1 トレースの確認

1. 他人の注文の配送先をエージェントが更新したときのトレースを開く
2. 注文住所を更新するツール呼び出しと、2 回のモデル呼び出しが表示される。消費したトークン数と、所要時間（3.5 秒）も確認できる
3. このエージェントは Foundry 上で動いており、OpenTelemetry のテレメトリを Datadog に送っている。OpenTelemetry SDK を使っており、Datadog へ直接送る方法や、LLM Observability SDK を使う方法もある。Fieldwork のチームは計装済みだったため、Datadog の設定はすぐに済んだ
4. トレース上はすべて正常で、住所変更のクエリも通っている。エラーはない。トレースは「何が起きたか」を示すだけで、「どうあるべきだったか」は示さない

### 6.2 評価

1. この依頼に対し、2 件の評価が実行されている。Fieldwork 自身のアプリが OpenTelemetry 経由で送ったものである
2. 評価の本質はビジネスルールである。ここでは、顧客の分離（顧客ごとの情報を混ぜない）というルールが、この件では偽になっている。他の顧客の住所が例外なく変更されたことを意味し、評価は失敗として表示される
3. 技術的には何も壊れていないが、ビジネス的にはすべてが壊れている状態である
4. Datadog には、ハルシネーションやプロンプトインジェクションなど、設定できる組み込みの評価もある。今回のものは Fieldwork 固有のルールだった

### 6.3 モニタリング

1. 失敗する可能性のあるルールがあれば、アラートを設定できる。ここでは、直近 5 分間に顧客分離の評価が失敗したかどうかを監視するモニターが設定されている
2. アラートのメッセージには、待機当番の担当者に見る場所（注文の所有者と顧客の比較）を伝えられる
3. そこから担当者を割り当てたり、インシデントとして宣言したり、Datadog の AI アシスタント Bits AI に調査を引き継いだりできる。Bits AI に調査させ、修正のプルリクエストを作らせることもできると紹介された
4. 以前のように電話で知るのではなく、社内の監視で知る流れになる

### 6.4 テスト

1. チームが修正を実装し、出荷前にテストする。これが、変更を本番に出す前に Fieldwork がすべきだったこと、と位置づけられた
2. 先ほどのトレースから 4 件のリクエストをデータセットとして保存する
3. そのデータセットに対し、エージェントの 2 つのバージョン（以前のベースライン版と新版）を実行する
4. 画面では、両者の比較が強調表示されている。シナリオには問題がなく、すべて想定どおり動くことを確認できる

従来の開発では、期待する機能に対して単体テストを書き、コードの変更を検証します。発表者は、これを「AI のための単体テスト」にたとえています。プロンプトやモデルをわずかに変えたとき、エージェントが期待どおりの振る舞いをするかを、本番に出る前に判断できます。

## 7. 注意点・発表者の気付き

- AI の失敗は、エラーとして現れません。トレース上は成功し、顧客や業務のルールの側で初めて問題になります
- 「小さな変更」でもリリースとして扱う必要があります。Fieldwork では、モデルへの小さな変更でガードレールが効かなくなりました
- 評価はビジネスルールとして書きます。評価が失敗にできて初めて、アラートを設定できます。ハルシネーションやプロンプトインジェクション向けの組み込み評価もありますが、今回の問題は Fieldwork 固有のルールで検出しています
- ユーザーを信用してはいけません。「ルールを無視しろ」と入力するユーザー、悪意のある利用者を想定します
- Datadog の料金や制約の詳細は、発表では語られていません

## 8. 利用者にとっての利点

発表で語られた内容は次のとおりです。

- 顧客からの電話ではなく、社内の監視で問題を知ることができる
- トレースにより、モデル呼び出し、ツール呼び出し、トークンを含む履歴を端から端まで確認でき、コストの問題も捉えられる
- 評価をビジネスルールとして設定し、失敗時にアラートを出せる
- 出荷前に実リクエストで新旧バージョンを比較でき、変更が想定どおり動くことを確認できる
- Datadog は Microsoft Marketplace から導入できる。無料トライアル（発話は「2 週間」。言い直しがあり、聞き取りでは確定しにくい表現でした）があり、Datadog に支払う費用は Azure の請求を通る。Azure の利用者がよく持つ MAC コミットメント（Azure に一定額を使う財務上のコミットメント）の消化にも数えられる。さらに、ログやメトリクスなどのデータが、コンピューティング環境上の Datadog の各エージェントを通じて Datadog に流れるよう、技術的な設定も自動で行われる

## 9. まとめ

AI の世界では、新しい種類の問題が生まれ、従来の監視では気付けません。プロンプト、モデル呼び出し、ツール呼び出しを端から端までトレースし、正しさを測定可能なルールにして評価し、アラートで知り、変更のたびにテストしてから出荷するループが必要だ、というのが要点です。
