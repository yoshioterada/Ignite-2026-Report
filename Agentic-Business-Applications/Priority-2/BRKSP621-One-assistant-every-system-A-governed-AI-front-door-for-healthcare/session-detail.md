# BRKSP621 One assistant, every system: A governed AI front door for healthcare

## 1. はじめに

このセッションは、Microsoft 365 Copilot を「あらゆる業務システムとエージェントの共通の入口（フロントドア）」として使い、Agent 365 で統制する、という考え方を説明するブレイクアウトセッションです。Microsoft の Srinivasan Venkatarajan 氏と、Cognizant の Manpreet Singh 氏の対談形式で進みます。

前半は Microsoft 側から、エージェントが急増する一方でガバナンスが追いついていない現状と、共有の知能レイヤーである Microsoft IQ、統制の仕組みである Agent 365 が説明されます。後半は Cognizant が顧客に提供している実装の考え方（Copilot Launchpad）、モデルの選び方、利用状況の確認方法、会場からの質疑応答へと続きます。

セッションのタイトルにはヘルスケア（医療）とありますが、医療分野に特化した説明は少なく、コールセンターの例で Epic、Salesforce、ServiceNow を行き来する負担が語られる程度です。内容の大半は、業種を問わない企業向けの話です。

## 3. 何に関する発表か

エージェント型 AI が企業に急速に広がるなかで、「システムごとにエージェントがあり、利用者がそれらを行き来しなければならない」「どのエージェントが動いているのか IT が把握できない」という問題を、Copilot を単一の画面にして Agent 365 で統制することで解決する、という内容です。

発表の流れは次のとおりです。

1. Microsoft 側の前提：エージェントの普及予測、Frontier Transformation、Microsoft IQ
2. エージェントの増加とガバナンスの遅れ、Agent 365 と全体構成
3. Cognizant の取り組み：Copilot を AI の UI にする（休暇申請、チケット作成などの例）

7. まとめ

## 4. 発表者が伝えたいメッセージ

中心となる主張は「**Copilot を AI のための UI にする**」ことです。Microsoft の技術スタックで作ったエージェントも、他のハイパースケーラーやサードパーティのエージェントも、利用者は Copilot という 1 つの画面から使います。裏側ではエージェントが連携し、管理者は Agent 365 でそれらを観察、統制、保護します。

Manpreet 氏は、各 SaaS 製品がそれぞれ自前のエージェントを持つ状況を「それぞれのプラットフォームの文脈に閉じており、AI に詳しくない利用者が切り替えながら使うのは難しい」と指摘しています。昨年は顧客から「このユースケース用のエージェントが欲しい」と求められたが、今年は発想を変え、たくさんのエージェントは要らず Copilot があればよい、という方向に切り替えたと話しています。

Srinivasan 氏は、個人の生産性だけで終わらせず、チーム、組織全体の業務フローへ広げることが事業効果につながる、と締めくくっています。また、各部門が別々に同じことをすると企業の知能が共有されないため、Work IQ、Foundry IQ、Fabric IQ で作る知能レイヤーを自社のものとして活用すべきだと述べています。

## 5. 発表内容の詳細

### 5.1 エージェントの普及と Frontier Transformation（Srinivasan 氏）

IDC の推計として、2028 年までに企業内のエージェントは 13 億に達し、約 82% の企業が今後 1 ～ 3 年のうちに業務フローへエージェントを組み込む、と紹介されました。

Frontier Transformation は、AI をあらゆる場所に入れることではありません。人、プロセス、事業が持つ知能を生かし、**意図をもって業務フローを再構想し、事業への効果を引き出す**ことだと説明されています。そのために必要な要素として、次が挙げられました。

- エージェントがデータやシグナルにアクセスできる、豊かな文脈
- 業務部門の利用者でも作れる、ローコードの開発手段
- エージェントを観察でき、信頼でき、統制できること

成功には、人の志、それを実現する知能、そして信頼が必要だという整理です。

### 5.2 Microsoft IQ：共有の知能レイヤー

エージェントを優秀な社員と同じくらい信頼でき、生産的にするには、社員が持つのと同じ知識と文脈を与える必要がある、というのが出発点です。そこで Microsoft は、企業ごとに共有の知能レイヤー（Microsoft IQ）を持ち、その上に自社の IQ を築くことを勧めています。日々の仕事、チーム、業務フロー、各システムの業務データ、各プロセスから得られる整理された知識が、このレイヤーの材料です。

構成要素は次の 4 つです。

| 要素 | 説明（発話に基づく） |
| --- | --- |
| Work IQ | 人、コラボレーション、従業員の業務フローの文脈 |
| Fabric IQ | 事業の文脈。基幹システムなどの記録系システムのデータ |
| Foundry IQ | 企業内のナレッジベースにある方針などの文脈 |
| Web IQ | 画像、動画、天気など、公開情報源のリアルタイム情報 |

### 5.3 エージェントの増加とガバナンスの遅れ

Fortune 500 の多くの企業がすでにローコード、ノーコードのツールでエージェントを展開していますが、統制が追いついていないという状況が語られました。数値として、従業員の 29% 超が承認されていない AI エージェントを業務で使っていること、成熟したガバナンスモデルを持つ組織は 20%（発話の中では 21% とも述べられており、数値が揺れています。「約 2 割」と読んでください）であることが挙げられました。

結果として、チームごとにエージェントやワークフローが分断され、企業全体で共有できる知能が生まれません。大規模に採用するには、IT がエージェントを追跡、監視できる可観測性と制御が必要です。ガードレールを設け、プロンプトインジェクションの防止や機密データの漏えい防止など、エージェント自体を保護することも求められます。

### 5.4 Agent 365 と全体構成

Microsoft は約 6、7 か月前に Agent 365 を発表した、と説明されています。Agent 365 では、システム内で作られたエージェントや、企業内で動いているエージェントの数を把握（観察）し、統制し、保護できます。

Microsoft スタックの全体像は次のように語られました。

- 共有の知能レイヤー：Work IQ、Fabric IQ、Foundry IQ、Web IQ
- その土台：Microsoft Foundry と Fabric、さらに Microsoft Security
- インターフェース：Copilot（エージェントを使い、連携させる画面）
- 統制レイヤー：Agent 365

顧客は複数のハイパースケーラーや多くの製品企業と取引しており、それぞれが自前のエージェントを持ちます。サードパーティのエージェントも Microsoft スタックで作ったエージェントと併せて使いたい、という要望が出ています。すべてに別々の UI を作るのではなく、**Microsoft 365 Copilot を AI とエージェントの UI** とし、Microsoft スタックのエージェントでも他社製のエージェントでも Copilot から呼び出す、という考え方です。前日の基調講演のデモも、ほぼすべて Copilot を画面として行われたと触れられています。Agent 365 は、観察、統制、保護を担う信頼レイヤーです。

### 5.5 Cognizant の取り組み：Copilot を AI の UI にする（Manpreet 氏）

Manpreet 氏は、Salesforce、Workday、ServiceNow など、どの SaaS 製品にもエージェントがあることを前提に話します。各エージェントは自社プラットフォームの文脈に強く依存するため、AI に詳しくない利用者がシステムを切り替えながら使うのは困難です。例えば ServiceNow でタスクやインシデントを作り、Outlook で何かを探し、Copilot に戻って検索する、といった行き来が発生します。

そこで Copilot を入口にします。語られた例は次のとおりです。

- **ServiceNow のチケット作成**：Teams、Web、スマートフォンの Copilot に「ServiceNow でチケットを作って。新しいノート PC が必要で、今のものがクラッシュする」と伝えると、ServiceNow のチームにチケットが作られ、調達チームへ連絡が行き、上司に予算の承認が求められ、数日後に自宅へノート PC が届く。複数のエージェントやシステムの画面ではなく、1 つの UI、1 つのエージェントで完結する。
- **休暇申請**：「木曜日は Ignite なので休暇を申請して」と頼むと、Copilot が木曜日の日付を理解し、Workday で休暇残日数を確認し、残りがあれば申請する。上司に承認依頼が届き、承認されると同じ Copilot アプリに通知が届く。以前は Workday や PeopleSoft などのシステムを開く必要があった。
- **Salesforce への記録**：Ignite で出会った顧客（ある会社の CIO）について「この人の名前を記録して」と頼むと、Salesforce にコンタクトカードやケース、レコードが作られる。
- **旅行の予約や経費**：Concur や Expedia などでの航空券の予約を、API や MCP のチャネルとして接続する例が挙げられました。経費では、上限が 200 ドルなどの条件で自動承認する仕組みを顧客先で見たと話しています。

Manpreet 氏はこの構成を、親となるマスターの Copilot エージェントの下に子エージェントがぶら下がり、複数のモデル、システム、エージェントにまたがって拡張する形と説明しています。「重心は Copilot になった」という表現です。キーノートで触れられた、Salesforce の機能が Copilot の中に入ってくる予告（Copilot force と発言）にも触れています。

> 補足：これらの例について、発話では「プレビュー」「デモ」と呼ばれていますが、画面の操作手順や画面の内容までは語られていません。詳しくは 6 章を参照してください。

アーキテクチャは「Microsoft のおかげでとても単純」と説明され、次の層で構成されます。

| 層 | 内容 |
| --- | --- |
| 基盤となる文脈 | Work IQ |
| UI 層 | Microsoft Copilot。Teams、WhatsApp、Web、SharePoint などに展開 |
| エージェント層 | Copilot Studio、Foundry、Work IQ、CLI などで、複数のシステムにまたがるエージェントを構築 |
| 統合層 | Power Platform、2,000 以上のコネクタ、MCP、API クローラー |
| データ層 | ハイパースケーラーのデータベース、Dataverse、SQL、Oracle など |

Manpreet 氏は「Copilot のライセンスで 1 人あたり 30 ドルをすでに払っているのだから、会議の記録や SharePoint の Q&A だけで終わらせず、基幹システムと連携するアシスタントとして使ってほしい」と顧客に伝えていると述べています。

Cognizant 自身も約 35 万人の会社であり、目的別にエージェントを増やすと自分でも迷うため、GSD というエージェントを 1 つ用意していると語っています。チケット管理や Salesforce への記録などを、この 1 つを通して行うという話です。

### 5.6 統制：Entra ID と Agent 365

Entra ID はエージェントに ID を与えます。サードパーティやカスタムのエージェントでも、エージェント ID を Entra に接続すれば、数時間以内に Agent 365 上でそのエージェントの接続、API エンドポイント、統合が見えるようになる、という説明です。エンドユーザーが Copilot でやり取りすると、データの出どころや、どのエージェントを呼び出したかも分かります。

Agent 365 で確認できるものとして、次が挙げられました。

- 消費されたトークン量
- サードパーティのシステムと社内システムのどちらが使われたか
- 企業内にあるすべてのエージェントの一覧（Copilot、ChatGPT、Claude などの企業向け版を使っている場合も、Manpreet 氏のダッシュボードで消費状況とアクセス制御を確認できる、と話しています）
- 使われていないエージェント。6 か月や 9 か月など一定期間使われないものを削除できる

Srinivasan 氏と Manpreet 氏の対話では、退職した社員が作ったまま所有者のいないエージェントが数百残る問題が挙げられました。それらがどこにあり、何に接続しているかを把握し、承認された Microsoft のコネクタと Cognizant のコネクタだけを許可し、未承認の API で Copilot のデータを出し入れさせないことを Agent 365 で制御します。

Manpreet 氏の開発環境にはすでに約 1 万のエージェントがあり、35 万人規模の本番では個人、グループ、プロジェクトの各エージェントが非常に多くなると述べています。Agent 365 に最近加わったビジネス分析の機能で、事業への影響も確認できるようになったと紹介されました。

セキュリティ面では、コードを大量に書かなくても、DLP、Defender、Purview のポリシーがサードパーティのエージェントと Copilot のエージェントの両方に適用され、統制された状態をすぐに作れる、と語られています。プロンプトの扱い、PHI（保護対象の医療情報）なども統制層で制御できるという説明です。また、Copilot Code（発話では Copilot code と聞こえます）がこれから大量のエージェントや成果物を作るため、それらの挙動も Agent 365 で見る必要があるという見方が示されました。

### 5.7 Copilot Launchpad の 5 つの領域

Microsoft と Cognizant が共同で作ったのが Copilot Launchpad です。Manpreet 氏は「市場投入（GTM）というより、企業が拡大していくための構想」と位置づけ、ヘルスケア、ライフサイエンス、小売、製造などで使っていると説明しました。5 つの領域は次のとおりです。

1. **導入（アダプション）**：Copilot のライセンスを渡すだけでは、スーパーの店員が何をすればよいか分からない、という問題があります。そこで、スーパーの店員、医師、小売や製造の担当者など、職種ごとの一日に合わせて対象グループを分けて教育し、社内研修資料や変更管理を提供します。
2. **ガバナンス**：Agent 365、SAM、DLP、Purview、Defender を設定し、データが社外へ漏れないようにします。PHI 向けのコントロールとアクセラレーターもあり、SSN を入力しても受け付けない、といった制御を作ってあるという話です。
3. **変革（トランスフォーメーション）**：ヘルスケアや保険などの顧客が、エージェント型 AI で何を拡張でき、何を改善できるかを、業界に詳しい Cognizant のコンサルタントが一緒に考えます。請求処理や在庫管理などが例に挙がりました。
4. **拡張性（エクステンシビリティ）**：Microsoft のツールを組み合わせ、Copilot の UI を企業全体の AI の入口にします。クラウドだけでなくオンプレミスにも対応し、オンプレミスの ServiceNow に Copilot をつないでインシデントを確認、作成している顧客がいます。数千のカタログフォームを Copilot から使えるようにした会社の例もあります。
5. **自律型 AI（オートノマス）**：Copilot Studio などで、エージェントがタスクを自律的に実行する領域です。

コールセンターの例も語られました。ヘルスケアでは、Medicare や Medicaid の確認、保険の請求処理などで大量の電話を受けます。オペレーターに Epic、Salesforce、ServiceNow を行き来させるのではなく、1 つの UI と 1 つのエージェントを与え、エージェントが通話を聞いて関連情報を提示したり、Salesforce や SAP に新規ケースを作ったりします。

Srinivasan 氏は、Copilot Code（発話どおり）のクイックアプリを使えば、統合された UI も作れると補足し、前日に Judson 氏が、コードを 1 行も書かずに作ったアプリを見せたと触れました。画面すら要らず、Copilot へのプロンプトでエージェントのオーケストレーションを開始し、そこから一連のワークフローを動かす使い方もあると述べています。

Manpreet 氏は、専門家用、人事用、営業用など、エージェントを何百も作って用語集やライブラリで利用者に案内する進め方は勧めない、と明言しています。統制しやすい統合的な仕組みを持ち、Agent 365 を管理画面にして、Copilot の機能を最大限に使わせることを推奨しています。

### 5.8 モデルの選択と導入状況の確認（質疑の前の対談）

Manpreet 氏が Srinivasan 氏に 2 つの質問をしました。

**Copilot と各社のモデルはどう共存するか**：Microsoft は Copilot 内でどのモデルを使うか選べるようにしており、MAI や Opus、Claude などの名前も挙がりました。新しい Copilot のインターフェースにはホームがあり、モデルルーターで `auto` を選ぶと、依頼や作業の複雑さに応じて、高速なモデルから最先端の複雑なモデルまで自動で選ばれます。最先端のモデルがすべてのタスクに必要なわけではなく、その判断は Copilot のルーターが担います。Manpreet 氏も、メール送信、会議の要約、ServiceNow のチケット作成に GPT 6 のような大きなモデルは不要で、バックエンドの業務自動化は小さなモデルで十分な場合がある、と述べています。低いモデルで結果が出るならそれを使うのがコストの最適化につながる、という考えです。

また Srinivasan 氏は、最新の発表であるハイブリッドインテリジェンスにも触れました。高性能なノート PC の GPU でモデルをローカルに動かし、必要に応じてクラウドの最先端モデルも使える、という説明です。Manpreet 氏は、Windows で動くローカル LLM を使う Windows エージェントも近く登場する、と述べています。

**導入状況（アダプションスコア）はどこで見るか**：Copilot のダッシュボードで、トークンの消費量、個人別やチーム別の利用状況、エージェントのダッシュボードを確認できます。Microsoft スタックにある Foundry には FinOps（クラウド費用管理）の機能があり、Agent 365 の中でも消費と効果を把握し、効果を測定できる、と説明されました。

Manpreet 氏は、まず試してみることを勧めています。Copilot Studio を開くと、エージェントの公開やモデルの選択（任意のモデル、または自動モード）が簡単にできることに驚くはずだと述べ、Copilot のエージェントビルダーやアプリ作成機能も取り上げて、すでにいくつかアプリを試作したと話しています。

### 5.9 質疑応答

会場から 1 件の質問がありました。

**質問**：「フロンティア変革を後押しする」というスライドの上部に Copilot Studio と GitHub Copilot があるが、Copilot Code でバイブコーディングして Copilot のマネージドランタイム上で動かしたアプリも、Copilot で統制できるか。

**回答（Srinivasan 氏）**：エージェントであれば Agent 365 に登録でき、ID を与え、アクセスできるデータソースを把握して、監視、統制できます。Microsoft Foundry で作った AI アプリケーションの場合は、Foundry 自体に統制のためのツールとアクセラレーターが備わっています。

**補足（Manpreet 氏）**：現時点では、Copilot Code でデプロイしたアプリは Power Apps 管理センターのマネージドサービス環境に置かれ、「アプリ」のセクションで、開発環境や個人環境で作られたアプリを確認できます。前日に Microsoft の担当者から聞いた話として、Microsoft 365 管理センターの Agent 365 のアプリの下にも表示される予定で、システム全体のアプリが見えるようになる、と述べています。なお、「来週には何か変わるかもしれない」と前置きしています。アプリが数千になる状況について、Power Platform 管理センターでの CI/CD と環境管理は従来どおり行え、Microsoft 365 管理センターにも来る、との見方です。

> 注意：Microsoft 365 管理センターへの表示は、発話の範囲では今後の予定です。現在提供済みの機能とは区別してください。

## 6. デモ・手順

語られた内容として、休暇申請のシナリオは次の順序でした（実演された操作ではなく、説明された流れです）。

1. 利用者が Copilot に、木曜日の休暇を申請するよう依頼する。
2. Copilot が木曜日の日付を判断し、Workday で休暇の残日数を確認する。
3. 残日数があれば申請し、上司に承認依頼が届く。
4. 上司が承認し、同じ Copilot アプリに承認の通知が届く。

## 7. 注意点・発表者の気付き

- Copilot のライセンスを配るだけでは、利用者は何をすればよいか分かりません。職種ごとの教育と変更管理が必要だという指摘です。
- エージェントを部門ごとに大量に作り、一覧を配る進め方は避け、統合的な仕組みを Agent 365 で統制する方がよいとされています。
- 所有者のいないエージェントや長期間使われないエージェントが残るため、削除の運用が必要です。
- 個人の生産性にとどまらず、チーム、組織全体の業務フローに広げないと事業効果につながりません。
- 最先端のモデルをすべての処理に使う必要はなく、タスクの複雑さに応じてモデルを選ぶ（`auto`）ことでコストを抑えられます。
- Copilot Code のアプリを Microsoft 365 管理センターで見られるようにする件は、今後の予定として語られています。

## 8. 利用者にとっての利点

- 利用者は、複数の SaaS システムやエージェントを切り替えず、1 つの Copilot から休暇申請、チケット作成、顧客情報の記録、予約などを行えます。
- IT 管理者は Agent 365 で、Microsoft 製、他社製、カスタムのエージェントを横断して可視化し、トークン消費やアクセス先を管理できます。DLP、Defender、Purview のポリシーを適用できます。
- 目的に応じてモデルを選ぶことで、コストを最適化できます。
- Cognizant の説明では、すでに数百の顧客と協力し、多数のエージェントを展開済みです。社内だけでなく、航空券やリゾートの予約など、一般向けにも Copilot のエージェントを展開した顧客がいます。具体的な顧客名や数値の成果は、発表では語られていません。
- Microsoft Marketplace でこの Enterprise Launchpad を確認できる、と案内されました。

## 9. まとめ

エージェントの普及に対して統制が遅れている現状に、Copilot を単一の UI とし、Microsoft IQ で文脈を与え、Agent 365 で観察、統制、保護する構成が提案されました。Cognizant は、Copilot Launchpad（導入、ガバナンス、変革、拡張性、自律型 AI）として、顧客に実装を提供しています。複雑な UI を作らなくても Copilot からワークフローを始められること、最先端のモデルを常に使う必要はないこと、まず試すことが重要だというのが、2 人の共通した結びでした。Cognizant のブースは 659 番と案内されています。
