## 5. 発表内容の詳細

### 5.1 Kantar と広告制作プロセス

Ashok 氏は Kantar を、世界最大級のマーケターと取引するブランドインテリジェンスの会社だと紹介しました。消費者が何を考え、何を言い、何をしているかの情報を提供し、マーケティング投資にとっての意味を伝えています。クリエイティブ（広告表現）は特に強い分野です。質の高いクリエイティブには、マーケティング投資に対する大きなリターンがあるためです。

Link AI は、Kantar 独自の深層学習モデルで、広告の効果を大規模に評価します。MP4 ファイルを入力すると、数分後に広告効果のスコアが得られます。数千万件規模の実際の消費者の反応から作った独自のデータベースで学習し、実際の販売データで検証済みだと説明されました。以前のスライドでは「大規模に」と書いていたものが、今は「超大規模に」になっており、それは過去 1 年の Microsoft チームとの取り組みで可能になった、とも述べています。

キャンペーンのクリエイティブのプロセスは、テーマや戦略の決定、具体化、最初のクリエイティブ作成、批判的な評価、最適化、実際の展開（予算の投入、運用中の微調整）、次のキャンペーンへの学習の還元、と進みます。Kantar はこの全体で複数のツールを持ちますが、Link AI は従来、評価に重点を置いてきました。今回の取り組みは、これを上流（アイデア構築）と、特に下流（素材の最適化）の両方向に広げるものです。

最適化が重要な理由として、広告業界が変化していることが挙げられました。ブランドは何百、何千というバリエーション（プラットフォーム別、ローカライズ、パーソナライズ）を作り、クリエイターやインフルエンサーも大量の素材を作ります。しかも期間は圧縮されています。

### 5.2 広告効果を決める 6 つの要因

最適化とは、何を最適化するのかを正確に定義することです。Kantar は数十年の研究と、実際の販売やブランド向上の調査による検証を通じて、広告効果の主要な要因を 6 つ挙げています。発話で説明されたのは次の項目です。

| 要因 | 説明 |
| --- | --- |
| メモラビリティ（記憶に残るか） | 広告が気づかれ、記憶されるか |
| ブランディング | 記憶されても、ブランドと結びつかなければ十分ではない |
| メッセージング | 発話では詳しい説明はありません |
| 差別化 | 発話では詳しい説明はありません |
| 意味のあるものか（ミーニングフルネス） | そのカテゴリーでの自分のニーズに合うか |
| コンバージョン | 広告を見た後に、そのブランドを購入する可能性が高まるか |

> 補足：発話では、メモラビリティ、ブランディング、メッセージング、差別化、意味のあるものか、コンバージョンの順に読み上げられています。メッセージングと差別化には個別の説明がありません。

広告を最適化するとは、この 6 次元の 1 つ以上で評価を高めることを意味します。そのため、6 次元での採点は高速で、堅牢で、拡張可能である必要があります。

### 5.3 Link AI を採点役（グレーダー）として拡張する

Kanyo 氏は、エージェント型アプリケーションの中の採点役としての Link AI を説明しました。ループは 3 つのステップ、**採点、提案、生成**で、採点の段階で Link AI を呼び出します。

良い採点役の条件として、次の点が挙げられました。

- 信号が強く信頼でき、質の高いデータに基づいていること。Kantar には 35 年分の蓄積があり、4,000 万件の消費者のやり取りと、30 万本の広告のテスト結果があると述べられています
- ループの速度に合わせられること。改善のたびに採点役を通して検証するため、人がループに関わり続けられる速さが必要

ループが採点役に求めるものは 3 つです。

1. **速度**：1 回が遅すぎればループではなく、レポートになってしまう
2. **粒度**：当初は動画全体を単位にしていたが、キーフレーム（画像）やシーン単位でも評価できると有益だと分かった。例として、30 秒の動画のうち 6 秒のシーンは動画の 20% でも、そのシーンにとっては 100%。シーンを改善するには、そのシーンの品質を Link AI の各次元で示す信号が必要
3. **信頼性**：粒度を細かくした副作用で、Link AI へのリクエストが大幅に増える（以前は動画 1 本につき 1 リクエスト、今はキーフレームとシーンの数だけ）。グローバル企業では年に数千のキャンペーン、数十万の素材が対象になるため、遅延とスケールがバックエンドだけでなく製品としての要件になる

### 5.4 スケールのためのエンジニアリング

採点役を拡張した手順は、次のとおりです。

1. **ML サービスの標準化**：Link AI は、オープンソースモデル、Kantar 独自のモデル、大規模言語モデルを組み合わせた ML サービス群。モデルを FastAPI から VLLM（音声認識の都合で表記が確定できません）に移して性能を改善した。GPU が必要なモデルは近くのノードにまとめ、より多くのサービスを CPU に移せるようにした
2. **サービステンプレートの導入**：数十あるモデルサービスのそれぞれに、統一されたエンドポイント、テスト、テレメトリ、マニフェストを持たせた。チームはコーディングエージェントを使っており、テンプレートを渡すと、モデルサービスを数週間ではなく数時間で作成できた
3. **オーケストレーションの改善**：モデルサービス間の連携（入力、出力、「パンイン、パンアウト」と聞こえる処理。音声認識の表記）を担う層。複数のパッケージを検証し、Azure Kubernetes Service 上で動く Dapper Workflow（音声認識の都合で表記が確定できません）を土台に選んだ。同じテンプレートの方式で、ワークフローのステップもコーディングエージェントが数時間で作れた
4. **リクエストの分類と SLA**：リクエストをライブとバッチの 2 グループに分け、製品チームがそれぞれに SLA を定義した。SLA ごとに並列のキューを用意し、リクエストを適切なキューに入れて、約束した SLA に間に合うよう処理する
5. **統合と負荷テスト**：最初のテストでは、リクエストの 80% が失敗した。ワークフロー間の通信に関する高度なパターンの試行、優先度付きキューの設定改善、モデルサービスの微調整、各種メトリクスに基づく自動スケールの調整を経て、**99.9% の成功率**を達成した

**アーキテクチャ（口頭の説明）**：クライアントは、Kantar のダッシュボード、顧客が自社製品やプラットフォームに直接組み込む Link AI のスコアリング API、そしてエージェント型アプリケーションの好例である Link AI のコンテンツオプティマイザー です。流れは次のとおりです。

1. リクエストが スコアリング API に届き、検証して適切なキューに入れる。キューは Azure Service Bus で、SLA に合わせて複数ある
2. 反対側のリクエストプロセッサが取り出す。優先度付きキューは時間を稼ぐ手段で、急がない動画は待たせ、緊急のものはすぐに取り出せる
3. このロジックはリクエストプロセッサにあり、Dapper Workflow が動かしている。耐久性のある長時間実行のワークフローエンジンで、障害が起きても状態がデータベースに保存されているため、同じチェックポイントから再開でき、ロジックを再生（リプレイ）することもできる。顧客から「リクエストを失ってはいけない」という要件があり、再試行やリプレイは許容されると説明されている
4. ワークフローが、数十のモデルサービスの間のフローを調整する
5. 結果、メタデータ、参照データの保存には Cosmos DB と PostgreSQL を使い、可観測性には OpenTelemetry を使う。数十のサービスにまたがるため、リクエスト送信から完了までの各ステップの入出力と遅延が追跡でき、次に何を改善すべきかが見える
6. セキュリティと構成には Key Vault と App Configuration を使う。Foundry がエージェント層の背後の AI ワークフローを統制する。推論とマルチモーダル生成には Azure OpenAI Service のモデルを使う

**成果**は次のとおりです。

| 指標 | 改善 |
| --- | --- |
| バッチ処理 | 20 倍（数日から数時間へ） |
| 動画 1 本の処理 | 6 倍（50 分から 2 分未満へ） |
| 本番運用の運用コスト | 4 分の 1（4 倍削減と述べられています） |
| 推論 | 8 倍 |

これらは本番環境での実績で、すでに 22 万件を超える素材を採点し、以前のバージョンと比べて 20 倍を超える数の素材を採点しています。成功率は 99.9%（現在も改善中）です。エージェント型アプリケーションが生む大幅なトラフィック増に備え、現在のシステムは最大 50 倍のトラフィックに対応できる状態だと述べられました。

### 5.5 既存のワークフローへの組み込み

Kantar の顧客からは、Link AI を、今使っているクリエイティブのワークフローやプラットフォームの中に直接組み込みたい、という要望がありました。対象として、デジタルアセット管理、コンプライアンス、クリエイティブ品質のプラットフォーム、DSP での展開（アクティベーション）が挙がっています。ルールに基づく起動とオンデマンドの両方に対応し、公開前（プリフライト）と公開中（イン・フライト）の両方の用途で、結果をできるだけ早く各プラットフォームに返してループを閉じる、という設計です。

追加の説明として、次の点が述べられました。

- Link AI は、複数のチャネルとフォーマットでの追加の指標を提供する
- クリエイターコンテンツのテストに対応し、1 万件を超えるクリエイター素材をベンチマークとしてスコアを示す
- 新しい Kantar の API が Link AI を顧客のワークフローとプラットフォームに直接組み込む。デジタルアセット管理にアセットをアップロードした時点で Link AI を呼び出し、プラットフォームを離れずに品質を改善し続けられる
- 今はアップロードという確定的なイベントで起動するが、エージェントでこの継続的な改善を駆動することもできる

### 5.6 Kantar の IP の変遷と広告改善ループ

Don 氏は、Kantar の IP の変化を説明しました。

1. **AI 以前**：IP はファイルと人の頭の中にあった。専門知識は、消費者の調査と専門家から集められ、人が IP の作り手であり、伝達役だった。このため事業の拡大に速度の上限があった
2. **機械学習モデルの追加**：保有する広告評価のデータの大半をモデルが体現した。機械の速度で動き、客観的で、疲れず、いつでも呼び出せる。API から使えるようになり、多くのユースケースが開け、事業を日単位で運用できるようになった
3. **マルチモーダルモデルの追加**：画像と動画を理解し、複雑なタスクを推論できる。Link AI のスコア、広告の内容、独自ルール、ブランドガイドラインを組み合わせて、広告の改善方法を提案する。さらに生成 AI で新しい広告を作り、採点ループに戻して再採点し、基準を満たさなければ反復する

**広告改善ループ**は次のとおりです。生成 AI が変更を提案する（理解と提案）。人が提案を選ぶ。生成 AI が新しい素材を作る（生成）。再び採点する。人が、先に進むか、反復を続けるかを判断する関門の役を担います。このパターンは静止画にも動画にも当てはまります。静止画の改善から始め、情報が流れるバックプレーンを作った際、動画も扱うデータ量が大きく時間的変化を考慮する必要がある以外は、ほとんど差がないと気づきました。一方を調整すると、他方にも効果が及んだと述べられています。

### 5.7 エージェント型システムの設計パターン

Don 氏は、システムを構築した 4 つの要点として、耐久性のある土台、分割したエージェント型タスクと集約、チューニングと一貫性のための評価、機能指標を挙げています。

**(1) 耐久性のある土台（ハーネス）**

コンポーネントは時間とともに変わります。使っているモデルの提供終了の通知、強制的なアップグレード、技術の進歩に伴い取り入れたい新機能があります。広告改善ループの 3 つの段階には、差し替え可能なコンポーネント（LLM、メディアを理解するモデル、生成モデルなど、自前では作らず取り込むもの）があります。その下に、データと調整可能な要素（プロンプトやスキル）があります。

コンポーネントが変わるとシステム全体の挙動も変わりうるため、評価用データセットで変更を評価し、データや調整可能な要素を調整して、一貫した挙動を保ちます。新しいモデルは多くの場合より良いものの、**性能が悪化することもあり、アップグレードを強いられることもあります**。そのため、新しい機能が元のタスクをこなせるか、どこが改善されるか、新しい失敗が出ないかを試し、既知の挙動を何度も再テストします。製品としての文体や冗長さの一貫性を保つためです。

**(2) 分割したエージェント型タスクと集約**

同じ質問を LLM に翌日にしても、大きく異なる答えが返ることがあります。広告の評価では望ましくありません。そこで、各エージェントは確率的に答えを変え、見落としや誤りがありうるものと仮定しました。同じタスクを 3 つのモデルに任せると、誤りがすべて同じ場所に重なることは考えにくく、少しずつ違うものを見落とします。回答を集約すれば見落としがなくなる、という考え方です。

実際には、少しずつ焦点の違う複数のエージェントが、依頼された軸と次元で広告を改善します。**リコメンデーション・アグリゲーター**が回答を見て、重複や矛盾を整理し、4 つの説得力のある変更にまとめます。1 つのエージェントに複雑な指示を与える代わりに、多数に仕事を分散する形です。選択と重複排除は、別のステップで行います。

**(3) 評価によるチューニングと一貫性**

システムの品質は、3 つを分けて評価します。

- **提案の品質**：提案された行動が根拠で裏づけられているか。専門家が見て妥当だと同意するか。説明が筋が通っているか
- **生成の忠実度**：最良の提案があっても、生成の忠実度が低ければ意図した変更にならない。指示どおりに変更され、気に入っていた部分が変わっていないか
- **採点**：変更が効果的か。採点がその変更を捉えられるか。広告に良い影響があるか

1 つの結果が良くても、他の 2 つの代わりにはなりません。3 つすべてが必要です。それぞれのチューニングループは、基準（ベースライン）と評価セットの確立、失敗の調査（専門家のフィードバックやトレース）、スキルやツールの調整、証拠を比較した評価、組み込むかどうかの人の判断、の順です。提案については、エージェントごとの出力、提案数、各提案の語数、重複と重複排除の割合、提案同士の意味的な距離をテスト項目にしました。提案が互いに異なるか、正しく集約されているか、最終的に意味があるかを確認するためです。このループを回すほど品質が上がり、ばらつきが減ります。コンポーネントを入れ替えたときも、前世代で良かった性能との相対位置が見えます。

評価セットが大きいため、同じユーザーに元の版と変更後の版を長期間評価してもらうのは現実的ではありません。そこで **LLM を審査役** にして、多くを自動化しました。ただし根拠は専門家のフィードバックで、定期的に較正しています。専門家が課題の評価基準と品質を定義し、審査役が採点し、専門家の評価との不一致を比較します。不一致があれば再較正し、ずれ（ドリフト）を確認します。自動化された審査役は専門家の判断の範囲を広げますが、専門家の責任がなくなるわけではなく、常に確認が必要だと述べています。

**(4) 機能指標とテレメトリ**

テレメトリにより、すべての結果を説明可能にし、あらゆる経路を追跡できるようにします。テレメトリに対応した大きなフレームワークを使うべきで、自前で書くのは現実的でないと述べています。記録した情報は次のとおりです。

- 入力：元の広告、目標、広告のブリーフ、ターゲットオーディエンス、制約
- プロンプトとスキルのファイルを含むすべてのバージョン
- 採点の設定と評価基準
- すべての出力

品質の失敗は実行の失敗と同じではありません。システムが完璧に動いていても悪い結果を出すことがあり、良い結果を出しながら重要な点を時々見落とすこともあります。品質、遅延、コストは別々に比較します。

## 6. デモ・手順

デモは、Ashok 氏が事前に録画された画面を使って行いました（発話で「再生してください」と述べ、画面が早送りされていることにも触れています）。画面の細部は音声からは確認できないため、語られた範囲で書きます。題材は、このデモのために作った架空の企業「Quarter Roast Company」です。品質と職人技を打ち出す、高級コーヒーの会社という設定です。

### 6.1 静止画広告の最適化

1. 改善したい素材をアップロードする。チャネル、国、ブランド名などのメタデータを指定する
2. 採点を実行する。右下のパネルに、広告の効果の見込みを 1〜100 で示す指標が表示される。この例では、ブランディングと意味のあるものか（ミーニングフルネス）が他より低い
3. 最適化ボタンを押し、最適化する指標を選ぶ。ここでは、ブランディングと意味のあるものかを選んだ。本来は効果を切り分けるために順番に行うべきだが、時間の都合で同時に行った
4. 提案を生成する。内部ではまず、「データバックプレーン」を作る。広告に含まれる情報（クリエイティブタグ：著名人の有無、行動喚起の有無、商品デモの有無、プロモーションの有無など、数百の属性）、広告の要約、Kantar の IP（データ、フレームワーク、分析手法）で構成される。これが最適化エンジンへの入力になる
5. 最適化エンジンは、データバックプレーンにブランドガイドライン、広告の目的、Kantar の IP を組み合わせ、それぞれ異なる観点で見る複数のプランナーに渡す。多数の提案が出され、少数に集約される。今回は最終的に 4 件
6. 4 件の提案が説明付きで表示される。各提案は、左に画像、右に変更内容の説明が出る。ブランド名に関する提案も確認した
7. 最後に見た提案を編集し、最初の提案にあった背景に関する要素も追加するよう入力する。新しいビジュアルを生成する
8. 新旧を並べて確認する。ブランディングと意味のあるものかの両方が大きく向上し、他の指標は維持されるか、わずかに向上した。これは常に保証されるわけではないが、今回はそうなった。満足できなければ、さらに反復できる

### 6.2 動画広告の最適化

動画は、静止画が高速で動くものに音声が重なったものだと説明されました。枠組みは静止画とほぼ同じで、フレームのまとまり（シーン）を扱い、時間変化を扱う追加のツールが必要です。

1. Instagram 向けの広告を再生する。内容は、「大切なコーヒーは急がない。ゆっくり育て、100% オーガニック。低温でじっくり焙煎。3 回失敗し、4 回目で完璧。Quarter Roast Company、フォーミュレーション 4」という趣旨
2. 採点する（デモでは速度を上げている）。この例では、ブランディングとコンバージョンが相対的に低い
3. 最適化を押し、ブランディングとコンバージョンの両方を選ぶ。ブランディングは広告がそのブランドとして記憶されるか、コンバージョンは広告を見て購入しやすくなるかを指す
4. 内部では、Azure Content Understanding で広告をシーンに分解する。この動画は 4 つのシーンに分かれ、各シーンにラベルが付く。各シーンをデコードして、シーンの要約などを含むデータプレーンを作る（画面の JSON は抜粋）
5. 静止画と同様に、ブランドガイドライン、広告の目的、Kantar の IP を組み合わせ、複数のスキル（静止画のプランナーに相当）に通す。スキルごとに別の観点で、今回はシーンごとの提案を作成し、集約する。結果は 4 件で、シーンごとの提案が 1 つずつと、全体の提案が 1 つ
6. 全体の提案を先に確認し、続いてシーン別の提案を見る。最初のシーンを最適化し、新しいクリップを生成する。プロンプトは編集できるが、ここでは既定のまま進めた
7. 元のクリップと新しいクリップを比べる。ペースが遅くなっており（高級ブランドではよくある）、自然でオーガニックな背景になり、右上にロゴが追加された
8. 残りのシーンも処理する。最後の画面にソーシャルメディアのアイコンがなく、コンバージョンに有益なことが多いので、自分でその編集指示を入力して追加した。シーンごとに処理が進む（左下に表示）。反復するかを聞かれるが、満足したのでクリップを 1 本の動画に組み立てる
9. 新旧を並べて再生する。シーンごとのスコアが、例外を除き概ね上がっている。複数回のパスが必要なことも多く、それで構わないと述べた
