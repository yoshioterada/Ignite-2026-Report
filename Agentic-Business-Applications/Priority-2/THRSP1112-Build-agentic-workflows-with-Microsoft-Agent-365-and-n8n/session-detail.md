## 5. 発表内容の詳細

### 5.1 エージェントが本番に届かない 3 つの障害

Anna 氏は、会場に「エージェントを作ったが本番に出せなかった人は」と挙手を求めたうえで、ベンダーからの請求書を承認してよいか判断するエージェントを例にしました。簡単に作れそうに見えますが、実際には次の 3 つが障害になります。

| 障害 | 問いの内容 |
|---|---|
| ID | エージェントとは誰か。誰がそのエージェントに責任を持つか |
| アクセス | 何を読めるか、何を書けるか、どのツールを使えるか。ツールの中でどのレベルの権限を与えるか |
| オーケストレーション | どのシステムをまたいで動けるか。それらがどうつながるか |

### 5.2 構成：Agent 365、n8n、Foundry

| 要素 | 役割（発話での説明） |
|---|---|
| Microsoft Agent 365 | ID、アクセス、ガバナンスの層。Entra で、すでに使い慣れたツールから ID とアクセスを制御でき、IT 管理者はガバナンスを Agent 365 で行える |
| n8n | オーケストレーションの層。さまざまなシステムをつなぎ、読み取りや承認などを実行できるようにする |
| Foundry | モデルのデプロイ先 |

> 補足：Copilot Studio との関係について、Anna 氏は、Copilot Studio は優れていて役割をよく果たすと述べたうえで、n8n が効くのは Microsoft のエコシステムの外へ広げたい場合だと説明しています。

n8n の利点として、次の点が挙げられました。

- どのシステムでも使える。デモでは経理システムを使うが、Slack や Telegram なども使える。
- どのモデルでも使え、1 つのワークフローの中で複数のモデルを使える。
- 実行中の各ステップが見える。ワークフローの実行時には、通ったステップが緑色に光るので、エージェントが何をしているかが視覚的に分かり、デバッグも楽になる。

### 5.3 デモの前提：事前に準備したもの

Liam 氏は、エージェントが増えて複雑になり、手に負えなくなりつつあると述べたうえで、デモの内容と事前準備を説明しました。

- **Entra アプリ登録**：n8n のワークフローから Microsoft ノード（Microsoft 365 のサービス）を使うための資格情報、権限、アクセスを与える。
- **Agent 365 CLI**：エージェント自体の足場（スキャフォールド）を作るために使い、その上に構築する。
- **管理者承認**：エージェントに対して、テナントの管理者が承認する。これにより Microsoft 365 とワークフローを接続できる。
- **トリガーノード**：ワークフローを起動するための入り口。
- **モデル**：Foundry にデプロイした GPT-5.6 Sol（音声では「GPT-56 sold」とも聞こえます）。
- **メモリ**：エージェントごとに範囲を分けて持たせる。経理エージェントは金額を扱うため、他のエージェントと記憶が混ざらないようにする必要がある。

全体像は、2 つのワークフローです。左上が最初のトリガーのワークフローで、Foundry のインスタンスとユーティリティ関数を含みます。右側が、その子にあたるサブワークフローで、業務ロジック（判断の分岐）を担います。

## 6. デモ・手順

Liam 氏は、ライブデモだと述べています（Anna 氏も、ネットワークが不調でも寛容に、と会場に頼んでいます）。画面が小さく後ろの席から見づらいため、拡大しながら説明しています。

### 6.1 ワークフローの構成の説明

1. **最初のワークフロー**：上部にある Foundry ノードを開く。左側にシステムプロンプトがあり、その下に、メール、Excel、SharePoint、Word などのツールが含まれている。Liam 氏は、Foundry を使ったことがある人には馴染みのある構成で、新しいものを作り直したのではなく、1 つのワークフローの中にまとめて抽象化したものだと説明している。サービスの API を通じて、Microsoft 365 のスイートにアクセスできる。
2. **モデル**：OpenAI のモデルファミリーを使い、GPT-5.6 のうち「5.6 Sol」を選んだ。自分たちのケースで最良の結果が出たためである。他のモデルファミリーも選べる。費用の観点で選ぶこともでき、ここではトークンを使い切ることが目的ではなく、非決定的なエージェントで業務ロジックを包むことが目的だと述べている。
3. **メモリ**：コンテキストウィンドウの大きさを選べる。会話履歴の量に応じて大きくも小さくもでき、費用管理のためである。
4. **ユーティリティ関数（青色）**：請求書の管理では、価格、通貨、請求書ごとの会社などを扱うため、基本的な関数を置いている。多くの処理が入っているわけではない。
5. **サブワークフローのトリガー**：説明文と、サブワークフローの ID を指定する。1 年ほど前は 1 つのワークフローのキャンバスにノードを詰め込んでいたが、いまはサブワークフローに切り出せる。
6. **請求書の台帳（Excel）**：請求書番号、仕入先、金額、照合状況、ステータスなどの列があり、デモの時点ではすべて「保留中」。例は簡略化されたものだが、経理チームで見る実際の形式に近いと説明している。
7. **サブワークフロー**：業務ロジックを担う。左の入口で、前のワークフローから呼ばれ、台帳から請求書を読み込む。Excel のノードでは ID で行を取得する。この ID と認証は Entra に登録したアプリから来ており、Excel や Outlook などの全体にわたって資格情報の文脈を持てる。その後は、条件分岐（if-else）の決定木に入り、アクションごとに振り分ける。承認の処理と、CFO の承認の 2 系統がある。
   - 1 万ユーロ以内であれば承認される。ただし、請求書が見つからない、保留でない、ブロックされているといった場合は別の経路になる。
   - 1 万ユーロを超える場合は、CFO の承認に回る。
   - いずれも、Excel の台帳を更新し、Teams に返信する。

Liam 氏は、AI エージェントで業務ロジックの多くを処理するとトークンを多く使い、費用がかさむため、この部分は通常のノードで書いていると説明しています。

### 6.2 Teams からの操作

1. **エージェントの準備**：Teams にエージェントを置く。作成には Agent 365 CLI を使い、CLI が出す設計図（ブループリント）を使って、作成、インストール、Teams との連携を行った。
2. **請求書の一覧**：Teams で「請求書を見せて」と依頼する。エージェントがワークフローを起動し、Excel の台帳からデータを読み込み、請求書番号、相手先、金額、期日、照合状況の一覧を返す。人間ではなく、バックグラウンドで動くエージェントが処理している。
3. **1 万ユーロ以下の承認**：請求書 101 の承認を依頼する。n8n の実行履歴に、実行中のワークフローが緑色の「正常経路」で進み、限度額の範囲内と判断され、請求書が計上されたことが表示される。Teams にも返信が来る。Excel を再読み込みすると、その日付で承認済みになっている（あわせて Liam 氏は「0 の請求」と述べていますが、意味は音声から確認できません）。ほとんど人手を要しない流れである。
4. **1 万ユーロ超の承認**：金額 18,450 の請求書 124 の承認を依頼する。同じワークフローが、別の分岐に進む。実行履歴で CFO の承認の段階に入り、待機状態になる。まだ台帳は更新されない。
5. **CFO への承認依頼メール**：メールの受信箱を再読み込みすると、CFO 宛てのメールが届いている。Liam 氏は「自分を CFO に昇格させた」と冗談を言い、メールのフォームから承認を押す。
6. **結果の確認**：Teams に、請求書が限度額を超えており、金額は 18,450 で、CFO の承認に回したという結果が返る。

Liam 氏は、これが Agent 365 と n8n のワークフローを組み合わせる方法で、経理チームの手間のかかる作業を減らせると述べています。

## 7. 注意点・発表者の気付き

構築中に学んだ教訓として、次の点が挙げられました。

1. **セットアップの順序は重要。** Entra のアプリ登録がないと正しい資格情報が得られず、Agent 365 CLI のブループリントも得られず、承認の処理もエージェントも作れなかった。
2. **クライアント ID を一致させる。** Entra アプリのクライアント ID が一致していないと、Excel に書き込めなかった。大変な作業だったが、最終的に動いた。
3. **メモリの範囲を分ける。** 範囲を分けないと、複数のエージェントが同じメモリを共有し、記憶が混ざった。
4. **Frontier へのアクセスの反映に約 1 時間かかった。** 待ち時間が発生したが、いったん接続すると工程は大きく効率化される。

また、**一般提供と Frontier Preview の区別**に注意するよう、Anna 氏が強調しました。

| 項目 | 状態 |
|---|---|
| Microsoft Agent 365 | 一般提供済み |
| 固有の ID を持つエージェント | Frontier Preview |

自宅で試すときに見え方が違うことがあるのは、このためだと説明しています。

## 8. 利用者にとっての利点

発表で挙げられた利点は次のとおりです。

- ID とガバナンスを Entra と Agent 365 で扱えるため、IT 管理者が使い慣れたツールで制御できる。
- Microsoft の外のシステムや、複数のモデルを 1 つのワークフローで組み合わせられる。
- ステップごとの実行状況が見えるため、デバッグしやすい。
- 業務ロジックを通常のワークフローで処理することで、エージェントによるトークン消費と費用を抑えられる。
- 金額による承認の分岐を自動化し、経理の作業を減らせる。ただしデモでは請求書は例示用のデータです。実際の導入効果の数値は、発表では示されていません。

## 9. まとめ

本番に届くエージェントには、ID とガバナンス（Agent 365 と Entra）、オーケストレーション（n8n）、モデル（Foundry）の分担が必要です。デモでは、Teams からの依頼に対して、1 万ユーロ以下の請求書は自動で承認と記帳が行われ、1 万ユーロを超える 18,450 の請求書は CFO の承認を待つ流れが確認されました。
