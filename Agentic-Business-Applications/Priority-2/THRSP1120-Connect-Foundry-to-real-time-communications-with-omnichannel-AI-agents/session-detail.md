# THRSP1120 Connect Foundry to real-time communications with omnichannel AI agents

## 1. はじめに

このセッションは、Microsoft Foundry で作ったエージェントを、Twilio の通信基盤（電話、SMS、WhatsApp など）につなぐ方法を紹介するシアター形式の短い発表です。前半はスライドで、Twilio と Foundry の分担、どちらを選ぶべきかの判断基準、Twilio Agent Connect（以下 TAC）の仕組みを説明しています。後半は、架空の航空会社「Owl Airlines」を題材にしたライブデモです。

デモでは、顧客が先に SMS で手荷物の追加を依頼し、その後に電話をかけて座席を変更します。2 つのチャネルが 1 つの会話として扱われ、過去のやり取りの記憶も使われる様子が示されました。この連携は**オープンソースで、現時点で一般提供されている**と説明されています。

## 5. 発表内容の詳細

### 5.1 背景：AI 支出の増加と本番化の遅れ

AI への支出は急増しており、年の数か月で AI の予算を使い切ってしまう組織も多いと説明されています。前年比で 50% 増える一方、AI やエージェントから財務上の効果を見られていない組織が多数あります。Twilio が日々話している顧客の大半は、エージェントを本番用途にまだ載せていません。載せた場合も、予約の日程調整のような低リスクの用途が中心です。支払いなど、より高いリスクを伴う領域では、どう本番化すべきか確信が持てていないとのことです。

### 5.2 Foundry と Twilio の役割分担

Foundry 側は、エージェントを作る体験を担います。発表で挙げられた要素は次のとおりです。

- ホステッドエージェント：6 月に提供開始
- Voice Live
- 1,000 を超えるモデルから選択可能
- 評価機能とガードレール、Agent Framework

つまり、エージェントの構築と監視に必要な機能一式が Foundry にある、という位置づけです。

Twilio 側の強みはチャネルです。音声（カスケード方式のモデルを含む）、SMS、WhatsApp、RCS、チャットなど、考えうるあらゆるチャネルを提供できるとしています。

その上に Twilio が提供する仕組みが次の 3 つです。

| 仕組み | 説明 |
| --- | --- |
| Conversation Orchestrator | すべてのチャネルを 1 つの連続した会話にまとめる。電話が切れても、同じ番号にテキストを送れば最初からやり直さずに会話を続けられる |
| メモリ機能 | 会話の途中、会話をまたいで、チャネルをまたいで、顧客の文脈が付いてくる |
| 人間への引き継ぎ | 通話中に「人に引き継ぐべき」状況をリアルタイムに判断する。例えば、エージェントが意図どおり動かない場合や、顧客が何度も「担当者につないで」と繰り返す場合 |

人間への引き継ぎについては、Twilio のカスタマーサービス基盤は Flex だが、引き継ぎ先は任意の場所にできると補足されています。

Microsoft Foundry と Twilio の共同の成果が **Twilio Agent Connect** です。Foundry で作ったエージェントを Twilio のプラットフォームにつなぐ、Foundry 向けの専用パッケージが用意されています。

### 5.3 どちらで作るか：Foundry Voice Agents と TAC

Foundry には直接使える Foundry Voice Agents があり、もう 1 つの選択肢が TAC の SDK（Twilio Agent Connect SDK）です。選び方は用途次第だと説明されています。

**Foundry Voice Agents が向く場合**：音声のみの体験で、音声から音声へ直接やり取りする形にしたい場合です。トレーシングと評価を含む知能のすべてを Foundry に持たせたい場合も、これが適します。アプリや Web サイト内の音声アシスタント、音声のみの電話エージェントが具体例です。電話の回線と番号の提供は Twilio にできますが、ソリューション自体は Foundry Voice Agents が合う、という整理です。

**TAC が向く場合**：オムニチャネル（複数チャネル）で使いたい場合です。チャネルをまたいでメモリを引き継ぎ、1 本のスレッドにしたい場合や、仮想エージェントだけでなく人間への引き継ぎまで含めたい場合が挙げられました。具体例は、SMS や WhatsApp と音声の併用、先にテキストを送ってから電話してくる顧客、引き継ぎやワークフローのオーケストレーションが必要なケースです。TAC はチャネルをまたいだオーケストレーション、メモリ、引き継ぎを提供できるからです。

発表者は「モデルを気にするより、自分の用途と会話を気にしてください」と述べ、どちらにも適した場面があるとしています。

### 5.4 TAC と Microsoft Foundry の連携の仕組み

TAC の中に **Agent Framework Connector** という部品が作られています。Foundry 上のイベントと Twilio のイベントの間のオーケストレーションの多くを担います。

TAC は、Azure のホステッドエージェント内にデプロイされます。そのため、別途コンピューティング環境を用意する必要はありません。電話、メッセージ、メールを Foundry のホステッドエージェントに渡し、LLM を呼び出し、顧客に文脈を返す役割です。

流れは次のとおりです。

1. 顧客が電話をかけてくる
2. Twilio が顧客を識別する
3. ホステッドエージェントのエージェントに引き渡す
4. LLM とツールなどが処理を行う
5. 結果を Twilio に返し、Twilio が顧客に届ける

TAC に含まれる主な機能は次のとおりです。

- 会話メモリ：過去の会話の文脈と記憶を持ち込む。例えば、3 週間前に電話し、今日テキストを送っても文脈が引き継がれる
- 組み込みツール：メモリ、ナレッジ、Twilio Studio のフローへの引き継ぎ（Twilio Studio を使っている場合）

> 補足：発表者は、会話メモリの強化に取り組んでいると述べています。例として、顧客が直前に Web サイトで注文の問題を調べていた場合に、そのデータを取り込み、電話を受けたエージェントが最初から注文の話を始められるようにする、という構想です。これは取り組み中の内容であり、現在提供済みの機能としては説明されていません。

発表者は、Foundry のホステッドエージェントだけをゼロから使うより、TAC のほうがオムニチャネルのエージェントに近い状態から始められる、と述べています。

## 6. デモ・手順

デモは Ryan が担当しました。架空の航空会社「Owl Airlines」の顧客として、最初に SMS を送り、次に電話をかけます。

### 6.1 デモの構成

- Twilio Conversation Orchestrator が、テキストと電話を同じ会話にまとめる
- 会話メモリが、過去のやり取りから得た顧客に関する情報（過去の観察）をエージェントに渡す
- Twilio Conversation Relay が、エージェント向けの音声からテキスト、テキストから音声の変換を担う。これにより、1 つのエージェントでメッセージングも音声も扱える
- Twilio とエージェントの間に Azure API Management を置く。Twilio からのリクエストを検証し、安全にエージェントへ渡す
- エージェント本体は Microsoft Agent Framework で作り、TAC とのネイティブ統合を使う。すべて Foundry のホステッドエージェント上で動く

### 6.2 実演の手順

1. Ryan が、航空会社に SMS を送る。内容は、これから乗る便に手荷物を 1 つ追加したいというもの（デモの最初に電話が固まるハプニングがありました）
2. このテキストにより、Twilio 上で新しい会話が作られ、Foundry のホステッドエージェント内に新しいエージェントセッションが作られる。セッションは自分の会話専用で、他の会話から完全に分離されていると説明された
3. 画面では、作られたセッション（番号は 1052 と発話されています）を開き、エージェントのライブログを確認する。見やすくするため、事前に用意したログに絞り込んでいる
4. ログから、次の点が分かる。Twilio から新しい会話が作られたこと、会話メモリから過去のやり取りに基づく窓側席の好みが引き出されたこと、SMS が届いたこと、電話番号からフライトを検索してエージェントがフライトの文脈を持っていること
5. エージェントから料金（45 ドル）が提示され、Ryan が了承の返信をする
6. エージェントが手荷物追加のツールを呼び出し、手荷物を追加し、確認のテキストを送ってくる
7. 次に、空港に向かう途中で中央席だと気付いた、という設定で、AirPods を使って音声操作により Owl Airlines に電話をかける
8. 音声エージェントが応答し、Ryan がより良い座席が空いていないか尋ねる
9. エージェントは、窓側席が好みなので 23A を提案する。Ryan は窓側席を希望すると一度も言っていないが、会話メモリを使ってエージェントが自発的に提案した
10. Ryan が変更を依頼し、エージェントが座席を 23A に変更する。さらに、テキストで追加した手荷物が予約にそのまま残っていると伝える
11. Ryan は通話で手荷物に触れていないにもかかわらず、エージェントが把握していた点を指摘する。Twilio がテキストと電話を同じ会話に、したがって同じエージェントセッションにまとめているため、エージェントは完全なエージェントループと情報を含む会話全体の文脈を持っていると説明された

> 補足：画面の細部（ログの具体的な文言など）は音声からは確認できません。上記は発話で語られた範囲です。

### 6.3 実装の紹介

Ryan は、実装がどれほど簡単かをコードで紹介しました。

1. 公開リポジトリは、Twilio Agent Connect と Microsoft の連携を扱うオープンソースで、**一般提供済み**。Python パッケージがあり、`pip install` で自分のエージェントに追加できる。サンプルと、本番利用を想定した参照デプロイメントも複数ある
2. リポジトリには基本のスターターエージェントがあり、デモで使ったのもこれである。変更点は、システムプロンプトの差し替えと、手荷物追加や座席変更を模擬するツールの追加のみ
3. エージェントは、Microsoft Agent Framework を使って好きなように作る。Twilio のすべてのチャネル（メッセージングと音声）につなぐためのコードは大半が定型で、エージェントの登録は 1 行
4. ローカルでテストして問題なければ、本番へのデプロイは `make deploy` の 1 コマンド。設定の入力（例：Twilio の API キー。Azure に保存される）を、本人またはコーディングエージェントを案内しながら進める。続いて Azure のリソースとエージェントをデプロイし、Twilio 側の設定も新しいエージェントを指すように更新する

TAC は任意の LLM や任意のエージェントで動作します。Foundry との統合により、Foundry のエージェントを Twilio のプラットフォーム全体に、ひいては顧客につなぐ作業がシームレスかつネイティブになる、とまとめられました。`pip install` のコマンドは画面に表示され、QR コードからリポジトリを開いて確認できる旨も案内されました。

## 7. 注意点・発表者の気付き

- 本番化されているエージェントは、低リスクの用途に偏っています。支払いなどリスクの高い領域では、慎重な姿勢が残っているという認識が示されました
- エージェントはまだ完全には信頼されていないため、通話中のリアルタイムな判断で人間に引き継ぐ仕組みを持つことが重要だとされています
- 選択の基準はモデルではなく用途と会話です。音声のみなら Foundry Voice Agents、複数チャネル・メモリの引き継ぎ・人間への引き継ぎが必要なら TAC です
- Web サイト上の行動データを会話メモリに取り込む構想は、取り組み中の内容です
- 料金やライセンス、サポート範囲、他の制約については、発表では触れられていません

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 1 つのエージェントを作れば、SMS、WhatsApp、電話などの複数チャネルで動く
- 電話が切れても、テキストで同じ会話を続けられる。チャネルが変わっても最初からやり直さずに済む
- 会話メモリにより、顧客が言っていない好み（デモでは窓側席）も踏まえた提案ができる
- 会話ごとにエージェントセッションが分離されており、他の会話と干渉しない
- TAC は Azure のホステッドエージェントにデプロイされるため、別のコンピューティング環境が不要
- 通信プラットフォームへの接続コードは大半が定型で、エージェントの登録は 1 行、デプロイは 1 コマンド
- オープンソースで、すでに一般提供されている

## 9. まとめ

AI 支出が増えるなかでも、エージェントの本番化は低リスクの用途にとどまっています。この発表では、Foundry のエージェント構築・評価・ガードレールと、Twilio のチャネル・会話の継続・メモリ・人間への引き継ぎを組み合わせる Twilio Agent Connect が紹介されました。音声のみなら Foundry Voice Agents、複数チャネルや引き継ぎが必要なら TAC という使い分けです。デモでは、SMS で追加した手荷物の情報が後の電話でも引き継がれ、保存された好みから座席が提案されました。実装は、オープンソースの Python パッケージと 1 コマンドのデプロイで進められます。
