# THR915 Modernizing trading with agent-to-agent negotiation

## 1. はじめに

このセッションは、Microsoft と BNY が共同で作った、エージェント同士が債券取引の価格を交渉する仕組み「ANP（Agentic Negotiation Protocol）」の紹介です。10 月 15 日の正午ごろに、両社のエージェントが交渉した初の実取引（100 万米ドルの米国短期国債）が成立しており、その経緯、設計、シミュレーションによる検証、実取引の録画再生までが語られます。

チャットや音声で行われている機関投資家向けの取引を、エージェントがどう効率化するかが主題です。ただし、人間の判断を外すのではなく、**人間が決めた範囲の中でエージェントが交渉し、最後は人間が承認する**という設計が一貫しています。

## 5. 発表内容の詳細

### 5.1 解決する課題

登壇者は、外国為替（FX）取引の多くがチャットか音声で行われており（割合の数字は聞き取れません）、固定利付債の取引でも **40%** がチャットと音声で行われていると述べました。これらの市場は非常に非効率で、AI で効率化できる機会がある、という問題意識です。

Microsoft にとって取引は本業ではなく、事業に必要な現金残高と流動性を保つための手段です。それを担う Microsoft Treasury のチームには、市場の専門知識に加えて、監督のための連絡が多く、メールやチャットが業務の周辺に大量に発生します。

もう一方は、BNY のような市場の売り手側（マーケットメーカー）です。取引はチャットや音声に限られるため、毎日大量の Bloomberg のメッセージが届き、トレーダーは「週に 1 件ほどしか対応できないが、その取引には超過収益（アルファ）がある」と感じています。財務担当者はアルゴリズム取引のシステムを作りたくない、売り手は多数の市場に対応しなければならない、という両側の課題があります。

### 5.2 エージェントが役立つ領域と、そうでない領域

チームが特に気にしたのは、「エージェントを使っている」と言いながら、実際は**決まりきった自動化（決定論的な自動化）**にすぎない状態を避けることです。デモでは株式を扱わない理由として、例が示されました。

| 例 | 性格 | エージェントの要否 |
| --- | --- | --- |
| 「Apple の持ち分を整理中。価格が 325 を下回ったらすぐ 10 万株売る」 | 条件が明確。「こうなったらこうする」 | 不要 |
| 「Apple の債券を 1 億ドル分欲しい」。ディーラーとチャットで価格を交渉する | 誰に話すか、どう交渉するかを判断する必要がある | エージェントが役立つ領域 |

取引票（トレードチケット）は固定のスキーマで、エージェントを必要としません。会話や交渉では、スキーマが流動的になります。例えば「このレベルのリスクを求めているが、この債券を出せるか」というリスクの同等性の話で、「Apple を買いたい」とは違います。厳格なルールを作らず、**エージェントが柔軟に動ける範囲を定める**のが狙いです。

目標は、エージェント同士が、タスクやツールを一段階ずつ自動化するのではなく、交渉を通じて実際に取引を行うことです。必要なことは次の 3 つです。

1. 組織をまたいでエージェントが互いを見つける。
2. 価格の合意に向けて、台本通りでない交渉を行う。範囲は人間のトレーダーが決める。
3. エージェントが合意に達し、トレーダーがその内容に同意する。

こうしたインフラはネット通販や消費者向けの買い物の分野では見られるようになっているが、資産運用や金融市場のような、統制と規制がある領域には、これまで存在しなかった、と説明しています。そこで作られたのが ANP です。

### 5.3 ANP の仕組み

構成図では、左に Microsoft Treasury（青）、右に BNY の債券デスク（緑）があり、それぞれの上部に **Fleet Command** があります。Fleet Command は、各トレーダーがエージェント交渉を操作する画面（体験）です。将来は、このプロトコルに参加する市場参加者全員が使える SDK になり得る、と述べています。中央にあるのが ANP です。

流れは次のとおりです。

1. **相手の検索**：Microsoft のトレーダーが Fleet Command でボタンを押し、取引の意図に合う取引相手を探す。ANP の**レジストリ**（参加エージェントの一覧）が検索を助ける。現在の参加者は主に BNY と Microsoft だが、今後増える。チャットでは誰に連絡すべきか分からないが、レジストリでは意図（誰が買い、誰が売り、誰が何を求めているか）が分かるため、エージェントの自動化の前から市場が効率化する、と説明されました。
2. **交渉の依頼**：この時点で Microsoft 側が知るのは相手の身元だけで、BNY のトレーダーの戦略や上限は一切明かされない。Microsoft のトレーダーが交渉を依頼し、BNY のトレーダーが承認または拒否する。
3. **エージェントの交渉**：BNY が承認すると、エージェント間でメッセージが往復する。組織間を行き来するメッセージは、すべて **AI のガードレールと決定論的なルール**で制御され、すべて監査される。例として、テスト中に、交渉の途中で鳥の話などの無関係なメッセージを送ると相手のエージェントが債券取引の話だと思って幻覚（ハルシネーション）を起こすことが分かった。そのため、ANP は話題などを全メッセージで確認し、不適切なものは相手に送る前に遮断する。目的は、ネットワーク上のすべての取引相手のための中立的な安全性と公平性の確保。
4. **台帳での照合**：合意に達すると、各側が構造化した条件を ANP 内の**台帳（ledger）**に送る。ANP は双方の条件が完全に一致するかを確認する。一致しない項目があれば、相手側の条件を明かさないまま、その側に差し戻す。
5. **人間の最終承認**：両側のトレーダーに承認または拒否のメッセージが届き、両者が承認すると、その交渉を ANP が記録する（発話では「ACON」と聞こえます。音声認識の都合で表記が確定できません）。

発表では、BNY のトレーダーと Microsoft のトレーダーの間に直接の接続はなく、ガードレールと決定論的ルールが働き、全体を通じて人間が制御していた点が強調されました。

### 5.4 シミュレーションによる検証

「お金を失わずにどう試すか」への答えがシミュレーションです。BNY には、約 **150 のエージェント**が動く債券市場のシミュレーションがあります（この数字はすでに古い、との補足あり）。約 **400 時間**、約 **1 万件**の模擬取引を行い、実取引に踏み切る確信を築きました。エージェントにわざと損をさせる、敵対的な攻撃を仕掛ける、異なる交渉戦略を試す、といった実験も行ったそうです。

- **安全性**：最初はガードレールなしで自由に交渉させたところ、**20% の確率で自分の損益（P&L）を損なう行動**をとりました。その後、プロトコルと Fleet Command を整備し、エージェントが考える公正価値に基づく決定論的な上限を設けることで、損失の発生が **0** になった、と説明されています。
- **取引品質**：安全が確保できた後、プロンプトの調整やツール呼び出しの追加で取引の質を高めました。シミュレーションでは、エージェントが考える公正価値からの乖離が **0.1% 未満**で、非常に小さいとのことです。

### 5.5 初の実取引

**10 月 15 日の正午ごろ**に、BNY と Microsoft のエージェントが交渉した初の取引が実行されました。**100 万米ドルの米国短期国債（Treasury bill）**の取引で、エージェントの交渉から合意までに約 **63 秒**でした。この時間は、人間のトレーダーが相手とチャットする場合と同程度です。重要なのは時間そのものではなく、取引量が増えたときにトレーダーの時間が戻り、より収益につながる仕事に集中できることだと説明されています。また、参加者が増えれば、人間では不可能な数千の相手とエージェントが交渉でき、価格発見（より良い価格を見つけること）が改善する、という考えです。

### 5.6 得られた学び

1. **中央集権的で中立なプロトコルが突破口だった**。世界最大のカストディアンとして、市場が安全で公平であることを重視している。情報の非対称性をなくし、自らの市場で逆選択を生まないようにし、全参加者が安全に参加できると感じられるよう配慮した。
2. **交渉は最初の一歩にすぎない**。自動化を見せると、取引戦略のエージェント、他の用事があることを検知して取引を派生させるエージェントなど、取引の実行より上流の要望が出る。
3. **チームの協力体制が最も重要**。Microsoft の顧客先常駐型エンジニアリング（forward deployed engineering）チームは BNY のチームと一緒に作業し、ピッツバーグでともに過ごし、BNY のチームも Redmond のハッカソンに参加した。BNY 側は債券取引デスクの支援を、Microsoft 側は Microsoft Treasury のトレーダーとの協力を得た。証拠に基づく反復的な進め方だったと述べています。

## 6. デモ・手順

ライブの操作デモではなく、**実際の取引を記録した画面を再生**しました。再生前に、何事もなく終わるので派手な展開はない、と断られています。語られた内容は次のとおりです。

1. 左側（明るいテーマ）が Microsoft のトレーダーの画面。条件を設定し、交渉を開始する。
2. 右側（暗いテーマ）が BNY のトレーダーの画面。依頼が届き、交渉を承認する。
3. エージェントが交渉を始め、メッセージが往復し、合意に至る。
4. BNY のトレーダーが条件を確認し、承認するダイアログが出る。
5. Microsoft Treasury 側のトレーダーにも確認が出て、承認する。
6. 承認の確認が表示されて終わる。

画面の細部（入力した価格や数量など）は、音声からは確認できません。「期待どおりで、拍子抜けするほど地味」と説明されています。

## 7. 注意点・発表者の気付き

- エージェントの使いどころを見極める：決まりきった処理は、エージェントではなく決定論的な自動化でよいという立場です。
- ガードレールなしでは、シミュレーションで 20% の確率で損失につながる行動が出ました。決定論的な上限が欠かせないと説明されています。
- 無関係な話題のメッセージがエージェントに幻覚を起こさせたため、組織間の全メッセージを話題で確認しています。
- 63 秒という時間は、現時点では人間の手作業と同程度で、速さそのものが成果ではありません。
- 現在の参加者は Microsoft と BNY のみで、これは初期段階です。今後の拡張は計画であり、現在提供済みのものではありません。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- チャットや音声での取引の手間（メール、チャット、メッセージの対応）を減らし、トレーダーが収益につながる仕事に集中できる。
- レジストリにより、誰が何を求めているかが分かり、連絡先を探す非効率が減る。
- 参加者が増えれば、人間には不可能な数の相手と交渉でき、価格発見が改善する。
- 各側の戦略や上限を相手に明かさず、全メッセージを監査し、人間が承認する設計で、統制と公平性を保つ。

実取引は 100 万ドルの 1 件で、コストや収益の数値は語られていません。

## 9. まとめ

Microsoft と BNY は、エージェントが組織をまたいで取引相手を見つけ、決められた範囲で価格を交渉し、人間の承認で取引を確定する ANP を作りました。シミュレーションで約 1 万件の模擬取引を重ね、安全性（損失 0）と取引品質（公正価値から 0.1% 未満）を確認した後、10 月 15 日に 100 万ドルの米国短期国債で初の取引が約 63 秒で成立しました。今後は FX、レポ、デリバティブなどへの拡大と一般公開を目指します。
