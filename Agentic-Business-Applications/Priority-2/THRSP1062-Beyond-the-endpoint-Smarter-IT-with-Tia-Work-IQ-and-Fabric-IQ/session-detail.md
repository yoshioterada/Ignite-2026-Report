# THRSP1062 Beyond the endpoint: Smarter IT with Tia, Work IQ, and Fabric IQ

## 1. はじめに

このセッションは、TeamViewer の自律型エージェント「Tia」が、Microsoft の Work IQ、Fabric IQ と組み合わさることで、IT サポートをどう変えるかを紹介する短い発表です。前半は TeamViewer の Alfredo Patron 氏が戦略を語り、Microsoft の Liam Cavanagh 氏との対談を挟み、後半は Athan Papacostas 氏がデモ（技術プレビュー）で実例を見せる流れです。

デモの題材は、入社したばかりの経理部門の社員が VPN に接続できない、という実際に TeamViewer で起きた問い合わせです。Tia は 6 つのシステムをたどり、6 回の「ナレッジホップ（情報をたどって原因に近づく段階）」を経て、10 個のスクリプトを実行し、原因を突き止めて修復します。発表では、人手なら 1 時間以上かかる作業が、技術者の承認を挟みながら 5 分未満で終わったと説明されています。

## 5. 発表内容の詳細

### 5.1 TeamViewer の現状認識と「シフトレフト」

Alfredo 氏は、現在の IT サポートを「端末やエンドポイントで問題が起き、利用者が IT に連絡するか、自分で解決を試みるか、技術者が端末に来る」という、人が介在する対応の組み合わせだと説明します。TeamViewer は創業以来、この修復を自動化し、さまざまなプラットフォームにつながるデジタル体験を提供してきました。

数年前に始めた新しい戦略が、問題の発生を待たずに手前（左側）で解決するシフトレフトであり、その中心が自律型エージェントの Tia です。Tia の狙いは、端末で何が起きているかの文脈をつかみ、その端末に対する解決策を示すことです。これを、反応型から能動型へ進む「無限ループ」として図示しています。

目指す姿は、問題を理解し、解決策を提案し、多くの場合は先回りして修復することです。さらに、行った作業はすべて記録システム（Intune、ServiceNow など、使っているものを問わない）に反映する、という点を重視しています。

### 5.2 IT 問い合わせの典型的な原因

症状は端末に出ても、原因は別の場所にあることが多い、として次の 4 分野を挙げています。

| 分野 | 発話で挙げられた例 |
|---|---|
| ID | 端末にログインできない。メールが使えない。原因はバックエンド側にある |
| プロビジョニング | アプリや端末（複数台の場合も）を用意したいときに、ヘルプデスクへの連絡が発生する |
| 端末の状態 | バージョンの問題や動作の遅さで、生産性が落ちる |
| セキュリティ | 環境を安全に保ち、最新の状態に保つ。IT スタックが複雑化するなか、業界の基準を満たし、端末ではなくクラウド上にあるアプリケーションも含めて最新にする必要がある |

問題を解決するまで、利用者は生産性の上がらない状態に置かれます。Alfredo 氏はこの状況を改善することを狙っています。

### 5.3 Tia の仕組みと位置づけ

Tia は、TeamViewer がすでに端末から収集している情報の上に、状況を理解する知能の層を加えたものです。接続先は次のとおりです。

- **Work IQ**：その人が端末をどう使って仕事をしているかという業務の文脈
- **Fabric IQ**：デモの中では、業務がどのように行われるかを表す構造化データとして使われる（6 章で後述）
- **IT システム**：ServiceNow、Salesforce など、利用者が使っている主要なシステムとの連携

Alfredo 氏は、Tia の強みは「いま使っているものと一緒に動く」ことだと述べています。Microsoft との取り組みで推論力が上がり、端末内の文脈をすべて持っているので、診断、修復、推奨がしやすくなるという説明です。根本原因が分かれば Tia は端末上で操作を実行できる、と述べ、これは競合との大きな違いだと位置づけています。

利用者との対話は会話形式です。例として、端末が遅く、Chrome が古い場合に、Tia が古いことを伝え、更新が必要であり、それを会話の中で代行できると説明しています。これにより、第 1 層のサポート担当の時間が空き、投資をより上の層に振り向けられ、IT 部門全体と従業員の生産性が上がるとしています。

エンドポイントの外へ広げる部分では、Microsoft 製品では Intune（端末管理）と Entra、ITSM（IT サービス管理）の分野で人気の高い ServiceNow と連携します。ServiceNow とは深いパートナーシップがあるとのことです。Tia は問題の知識が集まる中心になり、反応型から能動型へ移行します。

さらに精度の高い解決のために、次の投資を行ったと説明しています。

- **ヘッドレス化**：MCP（Model Context Protocol）が普及しているため、Tia を画面を持たない形（ヘッドレス）にして、他のエージェントから接続できるようにした。顧客から多く要望があった
- **端末外の文脈の理解**：端末の状況だけでなく、実施済みの作業やつないだシステムの情報から、なぜ不調なのかの文脈を得る
- **クラウド上での操作**：端末上だけでなく、状況によってはクラウド側でも操作を実行する

その効果として、より賢く推論し、運用が 24 時間体制で動き続けられる点を挙げています。

### 5.4 対談：Microsoft の IQ 群と今後

Alfredo 氏が Liam 氏に 3 つの質問をしました。

**質問 1：Microsoft の IQ 群と Foundry を、TeamViewer のような会社はどう活用できるか。**
Liam 氏は Azure AI 領域で、特にナレッジ検索に力を入れていると自己紹介します。エージェント、コパイロット、エージェント型ワークフローのどれでも、必要な情報を取得し、その取得を効果的にできなければ、質問への回答や問題解決という役割を果たせないという考えです。そのうえで、TeamViewer が長年蓄積してきた情報と組み合わせて、このタスクを効果的に実現している点を評価しました。多くの組織が、自社の情報を活用して同様のものを作ろうとしているとも述べています。

**質問 2：IQ 群は Tia をどう豊かにするか（当日の発表を踏まえて）。**
Liam 氏は IQ 群を次のように整理しました。

| IQ | Liam 氏の説明 |
|---|---|
| Work IQ | Microsoft 365 環境にある情報を活用する。SharePoint のコンテンツ、Teams の会話などのデータで、問題解決や質問への回答に必要な文脈と知識を加える |
| Web IQ | 例えば最近出たばかりの問題を調べるなど、Web の情報を取り込む |
| Fabric IQ | 構造化データ。データベースの情報を問題解決に取り込む |
| Foundry IQ | 非構造化情報を活用する（質問 3 の回答の中で触れられた） |

Tia は、Intune や MCP などを使ってこれらの機能を活用し、エージェント型ソリューションを組み上げている、と評価しています。

**質問 3：将来。Copilot が知識労働者でも IT 担当者でも入口になる。Microsoft の戦略では Copilot が入口で、その下に基盤がある。仕事の体験や TeamViewer のような会社にはどういう意味があるか。**
Liam 氏は、同日に紹介されたナレッジグラフ（知識グラフ）を使えるようになったことに最も期待していると述べました。正しい情報を取り出すだけでなく、データを理解し、物事の関係性を把握して、関連するものを結びつけたり、相関や意図を見つけたりできるようになる、という点です。これが進めば、TeamViewer が目指す能動的な取り組みの機会がさらに広がると考えているとのことです。

## 6. デモ・手順

デモは、実際に TeamViewer で起きた事例です。入社 1 週目の経理部門の社員が VPN に接続できずエラーが出たため、チケットを起票します。Athan 氏は画面の映像（拡大表示された動画）を見せながら説明しており、ライブ操作か録画かは発話からは断定できません。画面の細部は音声のみでは確認できないため、以下は Athan 氏が語った内容に沿った流れです。

1. **Microsoft 365 Copilot から開始**：技術者（対応担当者）の作業は Microsoft 365 Copilot から始まります。Tia を MCP で Copilot につないでおり、仕事が行われる場所で Tia を呼び出せる構成です。
2. **インシデントの取得**：技術者が「このインシデントを手伝ってほしい」と依頼すると、Tia が ServiceNow に接続し、チケットから報告内容やメモなどの文脈を取得します。この段階では、他の操作は行いません。
3. **推論と次の一手**：Tia は情報が足りているか、追加の調査が必要かを判断し、証明書の問題だと理解して端末に確認しに行く、と判断します。
4. **端末でのリモートスクリプト実行**：ユーザー認証の問題なので、端末上で証明書の状態を確認するスクリプトを実行します。結果、VPN 用の証明書が端末に保存されていないことが分かります。
5. **Intune の調査（2 ステップ）**：証明書が端末にない理由を調べるため、まず Intune のログを分析し、証明書が一度も端末に配信されていないことを確認します。次に、ユーザーの端末が正しいグループに入っているかを確認し、正しい動的グループに入っていないことを見つけます。
6. **Entra の調査**：動的グループに入っていない理由を調べるため、Entra の MCP スキルを呼び出してユーザーのグループ情報を取得します。このスクリプトはその場で生成されたものです。Tia にはスクリプトのライブラリがありますが、必要が分かればその場でスクリプトを作って追加情報を取りにも行きます。結果、Entra 上のユーザープロファイルの部署フィールドが正しく設定されておらず、これが証明書が配信されなかった理由だと特定します。
7. **ユーザーの文脈の確認（2 ステップ、IQ 群の出番）**：原因は分かりましたが、ユーザーがどの部署に属するかを確認する必要があります。Athan 氏は、Work IQ はユーザーの文脈（どんな仕事が行われたか）、Fabric IQ は仕事がどのように行われるかを表すものだと説明しています。Tia はまず Work IQ からユーザーの入社案内メールを取得し、経理部門の所属と開始日を把握します。次にその情報を検証するため、Fabric IQ を通じた MCP 呼び出しで、人事のマスターデータ（信頼できる情報源）を参照し、開始日と正しい部署を確認します。
8. **修復（Entra）**：Entra に書き込み、ユーザープロファイルを修正します。書き込み操作は、技術者が承認できるよう、より目立つ形で表示されます。
9. **Intune の強制同期**：Intune がデバイスとデータを同期するには数時間かかるため、Tia は Intune でデバイス同期を強制し、証明書が端末に自動配信されるようにします。
10. **端末での最終確認**：端末に再接続し（画面の右側に表示）、リモートスクリプトで証明書ストアを確認し、問題が解決したことを検証します。

**デモのまとめとして語られた数値**

| 項目 | 内容 |
|---|---|
| 連携したシステム | 6 つ（端末、ServiceNow、Intune、Work IQ、Fabric IQ、Entra） |
| ナレッジホップ | 6 回 |
| 実行したスクリプト | 10 個（TeamViewer のカタログにあるものと、その場で作ったものの両方） |
| 所要時間 | 5 分未満（各ステップを技術者が承認） |
| 人手で行う場合の見積もり | 少なくとも 1 時間（端末に 2 回接続し、Entra と Intune にログインし、人事情報も確認するため） |

Athan 氏は、単に「証明書がない」と答えて証明書を直すだけなら簡単だが、このデモでは本当の根本原因まで到達した点が重要だと述べています。また、各ステップを人が監督しており、すべての実行が技術者に確認されている、とも述べています。

## 9. まとめ

TeamViewer の Tia は、端末の情報、ServiceNow、Intune、Entra と、Microsoft の Work IQ、Fabric IQ という業務の文脈を MCP でつなぎ、根本原因の調査から修復、検証までを会話の中で進めます。デモでは VPN 接続不能の問い合わせが、6 回のホップと 10 個のスクリプトで、技術者の承認のもと 5 分未満で解決しました。機能は技術プレビュー段階で、リリース日は未発表です。TeamViewer はブース 5503 でも同じデモを実施するとのことです。
