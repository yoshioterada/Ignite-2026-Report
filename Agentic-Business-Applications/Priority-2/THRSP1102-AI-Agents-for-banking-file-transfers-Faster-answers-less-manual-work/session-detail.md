# THRSP1102 AI Agents for banking file transfers: Faster answers, less manual work

## 1. はじめに

銀行の業務は、ファイル転送の上に成り立っています。このセッションは、ファイル転送サービス files.com を使っている米国の銀行が、その運用に AI エージェントを組み合わせて、「ファイルが届かない」という問い合わせの調査を短縮した事例を紹介します。files.com の Wade Callison 氏が司会を務め、銀行側の 2 名（Sean Debnath 氏、Max Polakowski 氏）が自社の取り組みを語ります。

内容は、銀行がなぜクラウド型のマネージドファイル転送（MFT）に移ったか、files.com と Azure をどう構成しているか、そして files.com 用の MCP サーバーを Azure API Management の背後に自前で立て、GitHub Copilot アプリから調査させる方法です。デモは録画で、ライブではありません。最後に、銀行が実際に使っている手順書（Markdown ファイル）を一般化したものが、QR コードで配布されます。

## 5. 発表内容の詳細

### 5.1 Town Bank の紹介

Sean 氏によると、銀行は 1999 年にガレージで創業し、現在の総資産は約 220 億ドル、支店は 80 以上で、バージニア州、ノースカロライナ州、サウスカロライナ州にあります。2024 年以降に 3 つの銀行を買収し、来年に向けて 4 つ目も発表済みです。Wade 氏は、商業銀行と個人向け銀行業務のほか、モーゲージ、保険、福利厚生、ウェルスマネジメントも手がけていると補足しています。

### 5.2 銀行にとってのファイル転送

ファイル転送の大半は files.com で動いています。そうでないものは、時間制約が厳しく、コアバンキングの提供元（ベンダー）と組んで対応が必要なごく一部の場面です。その場合は導入に数か月かかります。社内に取り込んで files.com 経由で動かすと、数時間、場合によっては数分で済みます。

### 5.3 files.com の利用規模

Sean 氏が示した規模は次のとおりです。

| 項目 | 内容 |
|---|---|
| ルートフォルダー | 200 以上 |
| 同期 | 多数。外部や社内のファイル保管先を監視する自作ジョブを書かずに済むため、気に入っている機能として紹介 |
| 自動化 | 約 70 件。ファイルの暗号化と復号を自動化 |
| リモートマウント | SFTP、Blob Storage、Amazon S3 など |
| SIEM 連携 | files.com 上の出来事をすべて SIEM に集約し、SOC が監視 |

### 5.4 移行の経緯

Sean 氏は、IT が単なるコモディティ（代替可能な存在）ではなく、事業部門の真のパートナーになりたかったと述べています。そのために管理負担を減らし、クラウドのハイパースケーラーや SaaS を活用しました。

従来は、自前で SFTP サービスを運用し、PowerShell スクリプトで多くのファイル処理をつないでいました。管理の手間が大きく、さらに当時使っていた SFTP 製品の提供元が大規模なサプライチェーン攻撃を受けました。自社が使っていた製品は影響を受けませんでしたが、オンプレミスで動かす以上、簡単に侵害されうるリスクは負いたくないと考え、クラウド型の MFT を探し始めたと説明しています。Azure もこの判断を後押ししました。

Wade 氏は、アーキテクトや開発者は古いシステムを廃止しても昇進せず、新しいシステムを入れると昇進しがちだという記事を読んだとして、古いシステムの廃止を称えるべきだと述べています。古いシステムは環境をもろくし、不要なリスクを生むためです。

### 5.5 アーキテクチャ

新しい MFT を探すときは、クラウドファーストで、files.com と、Azure および AWS で使える選択肢の 2 つを見ました。重視した点は、大手の多くが、SaaS とオンプレミスの間をつなぐインフラをオンプレミスに必要とすることでした。files.com は SaaS ファーストで、オンプレミスにエージェントやゲートウェイを置く必要がありませんでした。

Azure のストレージアカウントを files.com に直接マウントできます。会員（顧客）がファイルを送ると、files.com に一時的にも保存されず、SFTP の窓口を公開しているだけの状態で、そのまま銀行の Azure ストレージに入ります。そこから銀行のオーケストレーションツールが引き継いで、必要な場所へ転送します。Wade 氏は、規制対象のデータではコピーが 1 つも外に残らないストリーミング型が重要だと補足しています。

買収した銀行はそれぞれ別のインフラを持っていますが、files.com なら他のクラウドのストレージも簡単に接続してマウントできる、と Sean 氏は述べています。

### 5.6 MCP サーバーとエージェントの構成

ここからは Max 氏の担当です。構成は次のとおりです。

- files.com 用の MCP サーバーを自前で立て、**Azure API Management** にホストしている。
- 開発者は GitHub Copilot アプリを使っているが、Copilot、Codex、Claude など、どのツールでも構わない。
- files.com 自体にも、API、ホスト型の MCP サーバー、CLI、SDK があり、エージェントに CLI を使わせることもできる。
- それでも自前のゲートウェイを前に置いたのは、**銀行に必要なセキュリティと追跡性**のためであり、公開するツールを選びたいからでもある。
- 今回のデモは**読み取り専用の調査**に限定している。将来は、オンボーディングの作成にも広げたい考えがある。
- 認証は、**委任された短寿命の OAuth トークン**を使う。誰もシークレットを保存せず、呼び出しを行ったユーザーを追跡できる。
- すべて API Management を通るため、二重の追跡ができる。MCP サーバーへのツール呼び出しと、MCP サーバーから API Management を経て files.com のバックエンドに届く呼び出しの両方が見える。

GitHub Copilot アプリでの設定は、次のように説明されています。

1. カスタマイズのタブを開き、追加をクリックして、MCP サーバーを設定する。
2. API Management 上の URL を入力する。
3. 委任トークンを使うため、クライアント ID を入力する。アプリ登録がスコープを公開しており、呼び出し時にユーザーの資格情報がそのスコープを引き継ぐ。
4. サインインをクリックするとブラウザーが開き、アカウントでサインインして完了する。認可が有効な間は接続が維持される。

> 補足：Max 氏は、委任トークンが不要なら、従来どおり API Management のサブスクリプションキーを設定する方法もあり、手間は少ないが、自分たちのケースには合わなかったと述べています。画面操作の細部は音声からは確認できません。

### 5.7 動機となった出来事

「ファイルが届かない」というメールは日常的に届きます。Max 氏は実際の経験として、受け取り時間の枠が厳しく、ファイルが大きく、しかもすべてを同時に宛先システムへ取り込ませる必要があった同期処理を挙げています。しかも発生は午前 4 時でした。files.com 関連のリードを務める Donna 氏が Max 氏を調査に引き込み、約 10 分で問題を理解でき、その日のうちに files.com の専門家になった気分になったと言います。files.com の側も即座に調査し、比較的早く更新を出しました。以来、午前 4 時に起こされていないとのことです。

エージェントの狙いは、この調査時間の短縮です。午前 4 時には自分のパスワードさえ思い出せないため、複雑な手順を覚えていなくても調査できる状態にしたい、と述べています。これらのファイル転送は、会員が朝起きてすぐ使うデジタルバンキング基盤や、ポジティブペイ（小切手詐欺対策）などの重要な処理を支えており、時間どおりに届くことが不可欠です。

### 5.8 銀行におけるエージェントのセキュリティ（Sean 氏）

Sean 氏が語った内容です。

- **ID が最優先。** 人間からエージェントまで、すべてに ID を持たせる。ID プロバイダーは Entra で、エージェント、サービスプリンシパル、自動化プロセス、人間のすべてに ID を与えている。files.com もこの連携に対応している。
- **権限。** files.com の MCP サーバーは機能が完全だが、リスク許容度のため、自前の API ゲートウェイに引き込み、より細かい権限設定とログ記録をしている。
- **ログ。** files.com、Entra ID、API Management のログを SIEM に流し、統合スタックの全体で相関分析とテレメトリ（監視データ）の活用を行っている。

### 5.9 オンボーディングの速さ

買収が続くなか、業務側から「これを立ち上げられるか」と頼まれることがあり、3 か月という見積もりは受け入れられません。files.com では、月曜に依頼を受け、複数環境でのテストを経て金曜に稼働させられます。典型的な流れは、会員が files.com にファイルを置き、同期の自動化が暗号化や復号をして Azure Blob Storage に置き、銀行側のオーケストレーション層（Logic Apps の Blob トリガーなど）が処理して、再び files.com が拾う形です。Azure スタックとの統合がスムーズで、必要な柔軟性があると述べています。

### 5.10 カスタマイズと設定

Max 氏は、「何でもカスタマイズできる」というプラットフォームの売り文句には注意が必要だと述べています。カスタマイズしすぎた巨大なシステムは、他の環境とまったく違う姿になり、ベンダーとの対話が難しくなり、保守に専任の開発者が必要になります。構築は簡単でも、誰が保守し、費用がいくらかかるかが問題です。

files.com でも API で独自の処理は書けますが、MCP や Logic Apps による社内のオーケストレーションで補う形です。最近出た自動化の V2 は優れており、戦略を見直す必要があると感じているとも述べています。また、files.com は現代的で洗練された見た目であり、90 年代のような UI のアプリとは違うと評価しています。Sean 氏は、UI の設計は見た目だけでなく操作性に影響すると補足しました。

## 6. デモ・手順

Max 氏は、デモは**ライブではなく録画**だと述べています（ライブでタイピングを見せたくないため）。画面の細部は音声からは確認できず、以下は語られた内容に沿っています。使用したツールは GitHub Copilot アプリです。

**デモ 1：今日、何か問題はあったか**

1. 「files.com で今日、何か問題はあったか」と質問する。
2. Copilot が自前の MCP サーバーを呼び出し、自動化、その実行履歴、ログ、フォルダーを順に調べていく。
3. 約 30 秒で、有力な原因を示す。自動化の設定が間違っており、テンプレートの宛先パスが誤っていること、files.com が 1 時間後に自動再試行を予定していることが示される。
4. 開発者は「完了した」と報告していたが、実際には完了していなかった。Max 氏は開発者に連絡して直してもらう。

**デモ 2：特定の自動化の確認とファイルサイズの確認**

1. 同じチャットで、別の自動化について尋ねる。名前はうろ覚えだが、自動車ディーラーからファイルを受け取るはずだ、という手がかりだけを与える。
2. エージェントは、自動化が実行され、ローンの支払いファイルを移動したこと、移動元と移動先、実施内容（ファイル名にタイムスタンプを付けただけ）、失敗がないことを返す。
3. 続けて「そのファイルの大きさは」と尋ねる。サイズが想定どおりかを見るためである。files.com には、期待値を設定して通知やアラートに使う機能もあると触れている。
4. このデモではテストファイルで、サイズは 277 バイトと報告された。正規のファイルではないが、期待に合っているかを確認できる。

**デモ 3：修正後の再確認**

1. 開発者から「先ほどの PNC の自動化を直したので確認してほしい」と連絡が来た、という設定。
2. エージェントに取引ファイルを再確認させる。
3. 自動化は修正され、失敗なく実行されたと返る。ただし**ファイルが 1 つ詰まっている**ことも示された。UI を見ているだけでは気づかなかった情報で、追加の確認になった。

**デモ 4：定期レポートの自動化**

1. 退社前、または業務開始前の朝に、ファイル転送が正しく動いたかを確認するレポートを出す自動化を設定する。Max 氏は、どのツールの自動化機能でも可能と説明している。
2. 実行後のレポートでは、問題が起きたことがすべて示され、MCP サーバー側のツールで起きていた失敗も見つかった。
3. このレポートは、事業責任者、開発者、各アプリを調べる時間のないマネージャーに渡せる。そのうえで、追加の質問を続けられる。

Max 氏は、MCP サーバーを使えば Teams などに出てくるエージェントにも直接つなげられると述べています。

## 7. 注意点・発表者の気付き

- **画面の「正常」と実態は違うことがある。** 自動化が直っていても、ファイルが詰まっている場合がある。エージェントが追加の層の情報を出した例です。
- **開発者の「完了」報告を信じ切らない。** デモ 1 のとおり、完了と聞いたものが未完了だった例が語られています。
- **深い知識より広い知識。** Max 氏は、files.com に詳しくなくても、何が起きるはずかという幅広い知識があれば調べられると述べています。
- **当番の属人性。** 7〜8 人のチームで 1 週間ずつ交代し、Max 氏の当番は 2 か月に 1 回です。2 か月前に見たことは忘れるので、エージェントに聞けるのは大きいと述べています。
- **エージェントは野放しにできない。** 銀行ではリスク許容度があるため、files.com にも MCP サーバーがあるが、自前のゲートウェイでより細かい権限と記録を行っています。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- 新規のファイル転送の導入が、ベンダーとの連携で数か月かかるものから、files.com では数時間、場合によっては数分になった。
- 依頼が月曜に来て、複数環境でテストしたうえで金曜に稼働できる。
- 問い合わせの調査が約 30 秒で有力な原因の提示まで進む（デモでの例）。
- ツールに詳しくない当番担当者でも調査できる。
- レポートの自動化により、事後対応から先回りの対応に移れる。
- 追跡性：MCP サーバーと API Management の二重のログで、誰が何を呼び出したかが分かる。

## 9. まとめ

Town Bank は、オンプレミスの SFTP から files.com と Azure の組み合わせに移り、files.com 用の MCP サーバーを自前で立てて、GitHub Copilot アプリのエージェントに読み取り専用で調査させています。Wade 氏が示した持ち帰りの要点は次の 5 つです。

1. **自分の AI を持ち込む。** API ファーストで、ドキュメントとログが整っていれば、銀行と同じ制御ができる。
2. **自前のゲートウェイを前に置く。** セキュリティ部門がすべてを見て、制御し、仲介できる。
3. **エージェントには自由に調べさせ、最後の判断と操作は人が行う。**
4. 当番の誰でも調査できるようにする。
5. 保守しやすく拡張しやすい形にする。

銀行が実際に使っている Markdown の手順書（一般化したもの、専有情報なし）は、最後のスライドの QR コードで入手できます。質疑応答の時間は発話では確認できず、質問は終了後に会場の脇か、files.com のブース（発話では 5326R と聞こえます）で受け付けるとのことです。
