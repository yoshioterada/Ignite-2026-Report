## 5. 発表内容の詳細

### 5.1 BC の現状と、従来の ERP 体験

Dave 氏は、Microsoft に入って 1 年ほどで、AI が自分の生涯で最大の技術の波だと考えて入社したと話します。Microsoft が成功できる理由として、AI を根幹から実現する技術力、長期的なビジョン、自律的なワークロードを任せてもらえる顧客からの信頼の 3 点を挙げました。

現在は「Copilot が仕事の OS になった新しい段階」にあり、AI への関心も高まっている、と Dave 氏は話します。

BC については、**55,000 を超える顧客**と、**マーケットプレイスに 10,000 を超える拡張機能（extensions）**があり、消費財、製造、小売、プロフェッショナルサービス、政府など、あらゆる業界で使われていると紹介しています。

従来の ERP 体験の例として、Juanita という架空のサプライチェーンマネージャーの話がありました。午前 3 時に、サプライヤーが約束どおり納品できないというメールが届きます。Juanita は次のことを自分でこなす必要があります。

1. メールを確認することを思い出す
2. メールの意味を理解する
3. 影響を受ける顧客、代替の在庫、他のサプライヤーを、社内を駆け回って調べる
4. 計画を作り、承認を得て、顧客にとって許容できる利益率に収まるかを確認する
5. 物流部門と顧客に変更を連絡する

Dave 氏はこれを、遅く、受け身で、人が間違えやすいプロセスだと述べます。記録システム（systems of record）と、メールや Teams などの生産性アプリケーションがあり、その 2 つをつなぐ「ミドルウェア」が人になっている、という整理です。

### 5.2 目指す姿：Frontier reality

Dave 氏は、あるべき姿を「frontier reality」と呼びます。Juanita は「エージェントのボス（agent boss）」になります。

- Copilot と IQ があり、IQ には M365 と Dynamics 365 の両方が情報を供給する
- 作業はエージェントが行う
- Agent 365 が、すべてを根拠に基づいた統制下に置く

同じシナリオでは、エージェントがメールを受け取り、関係者の間を回って情報を集め、計画をまとめて Juanita に持ってきます。Juanita は判断と指導に集中できます。これを実現するのが、BC と Copilot が組み合わさることだ、と説明しています。

### 5.3 BC に組み込まれた Copilot（現在利用可能）

ここから Dmitry 氏が引き継ぎます。「PowerPoint ではなく、ライブ環境の製品をデモする」と宣言しています。デモの詳細は 6 章に書きますが、機能としては次のとおりです。

- Copilot が BC の画面（canvas）の中に直接組み込まれている。以前の BC には軽量版のチャットがあったが、実際の Copilot が BC にある方が良いとのこと
- モデルを選べる。「cloud models」と「GPT models」が選べると語られている（音声では cloud と聞こえます）。設定で応答の冗長さなどの好みを調整でき、笑顔の絵文字を使わない設定も例として挙げられた
- BC 環境のデータ全体にアクセスできるが、**実行しているユーザーの権限の範囲内**に限られる。ユーザー自身が見られない情報は、Copilot 経由でも見られない
- Work IQ を通じて Outlook などの組織データと結び付けられる

Dmitry 氏は、この機能は今日すでに使えると述べています。最新バージョン（音声では「2029」と聞こえます。終盤では 29.1 にも言及されており、バージョン表記は音声認識の都合で確定できません）で Copilot を開き、BC について質問してみてください、と促しています。

### 5.4 次のステップ：Copilot が BC の中で操作する

Dmitry 氏は、現在作業中の機能として、Copilot が質問に答えるだけでなく BC の中で行動する版を紹介します。この版の Copilot は、**ユーザーと同じように BC を操作します**。ユーザーが使える機能とユーザー体験は、Copilot にも使えます。権限もデータに対するユーザーの権限のままで、ユーザーが手作業でやることと同じことを代行する形です。

「データを変更した主体が分かる」点が強調されました。ERP システムである以上、すべてのステップを記録に残す必要があるためです。変更された項目は画面上で確認でき、人間が制御できる状態を保つ、という考え方です（具体的な画面は 6 章参照）。

### 5.5 Business skills（まだ製品にありません）

Dmitry 氏は、Business skills を「現在作業中で、まだ製品では利用できない新機能」と断ったうえで、先に知らせておきたいと紹介しました。

- スキルは製品内で定義する。ある領域（例えば仕入先の登録）の担当者が作成できる
- 中身は、業務フローを記述した、**ごく単純な自然言語の指示**。同僚に頼むときに伝えることをそのまま書く、というイメージ
- お客様自身が所有する「レシピ」であり、Copilot が必要なときに（just in time）取得し、ユーザーの指示と組み合わせて実行する
- 全業務を Copilot の判断に任せたくない、という狙いに応える。組織ごとに、仕入先登録の手順などを正確に指定できる

例として、仕入先登録のスキルには「Web から登録する場合はステータスをブロックにする（人間が承認し、銀行情報などを確認するまで取引に使わせない）」「税エリアコードを指定する」「各種検証を行う」「他の命名と一貫させる」といった内容が書かれていました。品目登録のスキルでは、属性、カテゴリー、利益率の定義に加え、品目を登録するときは最低 10 個を販売できる状態にするため、その仕入先に対する購買発注（purchase order）を作成する、という指示が含まれていました。

Dmitry 氏は、Copilot はすでに読み取りができ、書き込みも「もうすぐ」できるようになる、と説明しています。

### 5.6 Expense agent

BC の最新バージョンで追加された、経費精算のためのエージェントです。BC に経費を直接扱う機能がないことは長年の欠落でしたが、今回のバージョンで、経費の管理・登録機能と、領収書を各所から取り込んで処理するエージェントの両方が導入された、と説明されています。

- **有効化**：BC にログインして Expense agent を有効化するだけ（他の設定もあるが必須ではない）
- **モバイルアプリ**：外出先での経費申請用に、新しい専用モバイルアプリが作られた
- **ポータル**：領収書をまとめてアップロードできる、軽量なオンラインポータルがある。**BC のライセンスは不要で、Entra のユーザー ID があれば組織の誰でも使える**
- エージェントが領収書から内容を抽出し、**ポリシー違反（non-compliant）にフラグを付ける**
- 経費ポリシーは BC 内で自然言語で定義する。カテゴリーごとに、説明と確認事項を書く
- 経費はプロジェクトやプロジェクトタスクに関連付けられ、プロジェクト単位でまとまる
- 承認後は BC に登録され、総勘定元帳エントリ、プロジェクト元帳エントリなどが作成される。経費に関するレポートと分析の一式がある

流れの全体像は、エンドユーザーが領収書を取り込み、ポリシーが適用され、違反があれば修正し、マネージャーに提出して承認され、BC の標準的な方法で登録される、というものです。

### 5.7 Payables agent

Payables agent は、仕入先請求書の処理を自動化するエージェントで、BC では以前から動いているエージェントの 1 つです（Dmitry 氏は「すでにしばらく稼働している 2 つのエージェント」のうちの 1 つとして紹介）。顧客から、任意の時点で 200〜300 件の仕入先請求書が処理待ちになっていると聞いている、という背景が語られました。

今回の強化点は次のとおりです。

- 試しやすさ：購買請求書の一覧から、PDF をアップロードするだけでエージェントのタスクが自動的に始まる。追加の登録や有効化は不要。Dmitry 氏は、会社に戻ったらまず試してほしい最初の課題として勧めており、請求書を手で入力したくなる気持ちを抑えて PDF をアップロードするよう呼びかけた
- 注文との突合（マッチング）：仕入先が複数の注文に対して 1 通の請求書を送ってきても、エージェントが注文を探して突き合わせる。金額に価格差がある場合や、金額が完全に一致する場合には、警告が表示される。どう扱うかは人が決められる
- **クレジットノート（返金）のサポート**：仕入先からのクレジットノートの明細を読み取り、BC 内の文書と突き合わせる

### 5.8 Sales Order agent

営業担当者からのフィードバックが背景です。営業担当は自分の引き合いを他人に扱わせたくない傾向がある、という話でした。そこで、2 つの大きな強化が行われました。

1. **同じ種類のエージェントを複数作成できる**：営業担当者ごとに Sales Order agent を作り、各自のメールボックスを監視させて、PDF の見積依頼から BC の販売見積を作る。ユーザーは他人の見積や文書を見ずに作業できる
2. **試しやすさ**：「新規」アクションで、顧客、メッセージ、顧客から受け取った PDF を指定して送るだけで、エージェントを試せる。エージェントは PDF から情報を抽出し、品目、コード、ロケーションを含む販売見積を作り、在庫の有無も確認する

### 5.9 Cowork（Microsoft の、より複雑な業務向けソリューション）

Dmitry 氏は、Cowork は BC ではなく Microsoft のアイデアで、**より複雑で手間のかかるプロセス向けのソリューション**だと説明します。例として、売掛金業務（accounts receivable）を挙げました。請求書を送っても入金されず、代わりに「支払えない」「この件を返金してほしい」「期日を変えてほしい」というメールやメッセージが届きます。その調査に多くの時間が使われている、という状況です。

Cowork で、これを調整するプロセスを作ります。Cowork はメール、倉庫チームの Teams メッセージを探し、BC のデータと突き合わせて、結果を伝えます。BC と Work IQ（Outlook のメール、Teams）の両方を使って動く、と説明されました。

- BC 向けの **Cowork プラグイン**が、**1 月を目標**に導入される。BC のデータを取得し、BC のエージェントを呼び出してタスクを処理できる
- Cowork 側でも、BC と同様に処理手順（スキル）を設計できる。何を読むか、どう読むか、何に注意するかを書く

### 5.11 アプリケーション全体の強化

「アプリケーションの残りの部分はどうか」という疑問に答える形で、この半年間の強化点が語られました。

- **マスターデータ管理**：環境間でデータを同期できる。会社（company）間の同期はすでに可能だったが、BC の**環境間**に拡張
- **レイアウト**：販売見積や販売請求書のレイアウトを、繰り返し利用できるレイアウト、ヘッダー、フッターで作成できる。テーマを付けられ、Word と BC のプラグインを使うと簡単
- **分析**：Excel レポート、財務レポート、分析ビュー。ペルソナごとの Power BI の標準レポートを数十個追加
- **Microsoft Fabric へのミラーリング**：BC のデータを直接 Fabric にミラーリングする機能が導入済み。BC で書き出すテーブルを指定でき、複数の会社・環境のデータを、他アプリのデータと組み合わせて知的なデータ基盤を作れる。**バージョン 29.1 ですぐに使える**
- Power BI アプリは Fabric 上でネイティブに動くようになった。BC 関連の大きな製品についても Fabric でのネイティブ実行が今後さらに増える、という発言がありましたが、聞き取りが不明瞭です
- 財務、製造、コマースなどの領域にも機能追加があり、**過去 1 年で 160 以上の新機能**を製品に追加した

最後に、Dmitry 氏は「BC YouTube」チャンネルを案内し、今回の強化点を確認して新しい BC を使い始めてほしい、と呼びかけました。

## 6. デモ・手順

このセッションでは、Dmitry 氏が**ライブの BC 環境**で実演しています（「ほとんどが製品のデモ」と発言）。録音は音声のみのため、画面の細部（ボタン名や入力値）は、ナレーションで語られた範囲しか分かりません。

### 6.1 Copilot で現金ポジションのリスクを分析する

1. Copilot に、システム内の仕入先取引を見て、現金ポジションへのリスクを評価するよう依頼する。仕入先への未払い、期日などを分析し、どの仕入先がどう影響するかを求める
2. モデルの選択、設定（応答のスタイル）を画面で見せる
3. Copilot が、仕入先の支払状況と、保留中の最もリスクの高い支払いをまとめた小さなレポートを作る。どの仕入先から先に支払うべきかも示された
4. テキストではなく視覚で見たいと依頼し、Copilot が可視化を作る。内部のエンジンでコードを書いて実行している様子が見える
5. 「経営層向けで、行動を促す現金計画のブリーフィングメール」の作成を依頼する。Work IQ 経由で Outlook にアクセスし、複数のスタイルの下書きを作成する。プレビューは Copilot の画面内に表示され、Outlook には下書きが作成される。ユーザーが内容を確認してから CFO などの関係者に送る流れ

### 6.2 Copilot に BC の画面操作を代行させる（開発中）

1. 「Alpine の最新の販売注文を探して、納期を来週月曜に変更して」と依頼する（顧客から電話で期日変更を頼まれた想定）
2. Copilot が作業している間、ユーザーは他の作業ができる。Dmitry 氏は Copilot の作業内容を開いて、Copilot が販売注文の一覧に移動し、並べ替えとフィルターで文書を探し、要求納期を更新する様子を説明する
3. 文書が更新された。ヘッダーと、そのヘッダーの 3 行が更新されている
4. 販売注文の画面に移動して確認する。元の文書は 1 人のユーザーが作成し、その後 Copilot が更新した、と履歴で分かる。注文のページを開くと、Copilot が更新した項目を示すペインが出る。要求納期の項目に移動でき、何が依頼されたかを示すツールチップもある

### 6.3 Web サイトから仕入先を登録する（Business skills を使用）

1. 「Adventure Works のサイトを見つけたので仕入先として登録したい」と、サイトのリンクを付けて依頼する
2. Copilot の作業ログの最初の行は、「BC から vendor onboarding skill を読み取る」という内容
3. Business skills の画面で、仕入先登録のスキル（自然言語の指示）と、品目登録のスキルを見せる（内容は 5.5 のとおり）
4. 登録済みの仕入先を開く。Copilot が登録したことが分かり、9 つの変更が加えられている。Web ページの情報が BC のレコードに取り込まれ、指示どおりステータスはブロックになっている

> 注意：Business skills は発表時点で製品に入っておらず、開発中です。

### 6.4 Expense agent

1. BC にログインして Expense agent を有効化する
2. スマートフォンのモバイルアプリで領収書をスキャンする。コペンハーゲンのタクシーの手書きの領収書。エージェントが処理を始め、金額 68 ドル、誰のためのものか、目的を読み取り、種類を「ground transportation（地上交通）」に分類した。経費精算書に追加する
3. オンラインポータルを開く（モバイルから送った領収書がすでに表示されている）。レストランの請求書、ホテルの請求書、旅程（フライトとホテルの滞在）を追加でアップロードする
4. エージェントが内容を抽出し、経費精算書にエントリが追加される。レストランの請求書は「参加者が必須」というポリシーで non-compliant と表示されたため、参加者を追加した
5. ホテルの請求書は 3 泊分で、エージェントが自動的に宿泊料、食事、ルームサービスに分けている
6. BC で経費ポリシーを確認する。自然言語で書かれており、例として「ホテルのミニバーの購入は精算対象外」というポリシーが示された
7. ポータルでホテルの項目に、このポリシーによるフラグが付いていることを確認する。上司に承認を依頼するか、明細から外すかを選べる
8. 確認が済んだらマネージャーに提出する。マネージャーにはメール通知が届き、同じ情報（ポリシー適合性を含む）を見て承認でき、承認後は BC に登録される
9. 経費はプロジェクトのタスクに関連付けられる、と説明された（画面での実演は語られていません）
10. 同僚の Yannick 氏が提出した経費精算書を開き、転記（posting）のプロセスを見せる。転記すると、総勘定元帳エントリ、プロジェクト元帳エントリなどが作成される

### 6.5 Payables agent

1. 購買請求書の一覧で、仕入先の請求書（PDF）をアップロードする。タスクが自動で始まる（この場でのアップロードのデモ）

3. PDF の内容と下書きの内容を見比べられる。注文のマッチングの結果、注文番号、価格差などの警告が表示される

### 6.6 Sales Order agent

1. 営業担当者ごとのエージェントの例として、「John's sales order agent」が John のメールボックスの見積依頼を監視している様子を見せる
2. 「新規」アクションで、顧客（Jan からのメールという設定）、メッセージ、PDF を指定して送信する
3. タスクが始まり、エージェントが PDF から情報を抽出して販売見積を作り、在庫を確認する（結果の詳細な画面は語られていません）

### 6.7 Cowork（売掛金のレビュー）

1. 発表直前に実行した結果を見せる。「顧客の請求書を確認して」と指示しただけで、やり方は指定していない。車で出勤中にモバイルから行う、というイメージで説明された
2. Cowork は BC と Work IQ（Outlook のメール、Teams）を使い、関連しそうな情報を調べ、苦情を見つけ、BC での調整を依頼してくる
3. 要約を音声で聞けるようにも依頼してある。再生された音声の内容は、トランスクリプトでは一部しか聞き取れません（完全な返金の希望、期限超過の請求書、高優先度が 3 件、などの断片）
4. 提案が良ければ「go」と言うだけで、Cowork が BC にクレジットメモの作成、期日や納期の変更を実装する、と説明された。「go」を実行した様子は語られていません
5. Cowork 側の画面で「receivables を確認するスキル」の定義を見せる。処理方法（何を読み、何に注意するか）を設計できる。結果は、BC のクレジットメモと期日・納期の変更として確認できる

## 7. 注意点・発表者の気付き
