# BRK499 Agentify Your Business Processes for ERP Partner Opportunities

## 1. はじめに

このセッションは、Dynamics 365 ERP を扱うパートナー企業に向けた 45 分のブレークアウトです。ERP の業務プロセスをエージェントで作り変える時代に、パートナーは自社の事業と提供価値をどう変えていくのか。その答えを、Microsoft 側の 4 人の発表と、パートナー 2 社のパネルで示します。

発表の中心は次の 4 点です。

- ERP のエージェント基盤に、業務プロセスを記述する **business skills** と、メタデータを補う **AI descriptions** が加わったこと

登壇者が多く、冒頭で「かなり速く進める」と断っています。画面を操作するライブデモはありません。最後に Q&A の時間もありませんでした。

## 5. 発表内容の詳細

### 5.1 市場機会と、業務プロセスを再設計するビジョン

Dave は、Fortune の調査をもとに、現在 2,000 億ドル規模の機会があり、CAGR（年平均成長率）は 11% だと説明しました。2034 年には 5,000 億ドルに近づくとしています。ただしこれは、今と同じ事業の延長ではありません。業務プロセスを再設計した、変わった後の事業の話だという位置づけです。

たとえとして、Microsoft が全員の机に PC を置いた時代が挙げられました。PC を大量に買えば生産性が自然に上がったわけではなく、企業側が PC を理解し、プロセスを作り直して初めて生産性が出た。AI でも同じことが起きているという説明です。

今日の ERP の業務例として、サプライヤーから「納品できない」というメールが届く場面が示されました。担当者（例として Juanita）は次の作業をすべて自分で行います。

- メールを確認して納期遅延に気づく
- 社内で代替の在庫や別のサプライヤーを探す
- 影響を受ける顧客を特定する
- 代替案を考え、価格を決めて計算し、承認を取る
- 顧客へ連絡し、在庫を移動する

Dave は、これを遅く、後手に回り、人為的な誤りも起きるプロセスだと述べました。原因は、業界が人を「ミドルウェア」にしてきたことです。ERP などの記録システムと、Outlook・Excel・Teams といった実際に仕事をする場所が分かれており、その間を人が走り回って情報をつないでいます。

ビジョンの姿では、Juanita は「エージェントのボス（agent boss）」になります。Copilot が支援し、Microsoft 365 と Dynamics 365 の IQ レイヤーがエージェントに情報を与え、全体を Agent 365 が制御します。メールの確認、情報収集、提案の作成はエージェントが行い、Juanita は提案を受け取って人間としての判断を下します。その分、顧客や利益について考える時間が増えるという流れです。

その第一歩は、優れた中核システムを持つことだとされ、Dynamics 365 ERP が直近の Gartner Magic Quadrant 3 つでリーダーに選ばれたことが紹介されました。対象は次の 3 分野です。

- Cloud ERP for finance
- Cloud ERP for service-centric organizations
- Cloud ERP for product-centric enterprises

### 5.2 エージェントに文脈を渡す仕組み（Jared）

Jared のセクションのテーマは「文脈（context）」です。基調講演で多く語られた Work IQ（および Microsoft IQ）に、ERP の文脈を取り込む取り組みを、business skills と組み合わせて進めているという説明でした。

エージェント・フレームワークの中心には、**Dynamics 365 ERP MCP server** があります。昨年の Ignite で紹介されたもので、エージェントのハーネスや LLM、オーケストレーション層と、アプリケーションのデータ・ビジネスロジックをつなぐ役割です。現在の MCP server は、アプリケーションのビューモデル、メタデータ、列名、フィールド、ツールチップといった情報から、エージェントがどう動くべきかの文脈を得ています。これはよく機能しますが、顧客ごとの仕事の進め方に合わせた調整は得意ではありません。

次の世代では、データとビジネスロジックの上に、**business skills** と **AI descriptions** からなる「インテリジェンス層」が入ります。両者の違いは次のとおりです。

| 項目 | 役割 |
|---|---|
| business skills | プロセスに関するもの。エンドツーエンドの業務の手順、ポリシー、プロシージャを記述する |
| AI descriptions | メタデータに関するもの。アプリケーションのメタデータに説明を足して、オブジェクトの扱い方をエージェントに伝える |

AI descriptions の例として、Jared は社内評価で遭遇した事象を挙げました。販売オーダーに "settled" というフィールドがあり、エージェントはこれを「この販売オーダーは決済済み」という意味に取って混乱します。しかし実際は別の意味のフィールドです。説明を足してメタデータを補強すれば、エージェントはアプリケーションに対して正しく動けるようになります。

AI descriptions は発表の約 2 週間前に発表され、**パブリックプレビュー**になっています。Jared はスライドを用意していないとしたうえで、F&O（Finance and Operations）向けに拡張機能を作っているパートナーは、コード、フォーム、エンティティについて AI descriptions で情報を足してほしいと呼びかけました。

### 5.3 business skills

business skills は、**前日にパブリックプレビューになった**機能です。正式発表は翌日の予定と話しており、"10.050" がある環境ならすぐ試せると述べています（バージョン表記は音声からの聞き取りです）。ERP のシナリオごとに、名前、説明、業務プロセス、リソースを定義します。形式は Anthropic の標準の skill 仕様に従っています。

skill 自体は、Cowork、Copilot Studio、他のエージェント・ハーネスにもあります。それでも ERP に加えた理由として、Jared は次の点を挙げました。

- 組織で共有する skill になり、どのユーザーにも提供できる
- F&O のセキュリティモデルで保護される。つまり、セキュリティロールに基づいて共有先を決められる
- どのエージェントやハーネスを使っても、同じ業務プロセスに沿った一貫した体験になる

skill の出どころは 2 種類です。

1. **built-in skills**：AOT（application object tree）で作成します。フォーム、エンティティ、テーブル、X++ のコードユニットと同じく、AOT に追加された新しいノードタイプ "skill" として定義し、アプリケーションと一緒に配布します。アプリを出荷するときに、エージェントがそのアプリを扱うための知識も同梱できます。
2. **custom skills**：ERP アプリケーション上で作成します。お客様自身がフォームを開き、自社のプロセスを書き下ろせます。

skill の目的は大きく 2 つに整理されました（実際にはもっと多いが、単純化したと説明）。

- **MCP の性能向上**：Microsoft はすでにこのフレームワークとあわせて、経費、経費仕訳、procure-to-pay に関する skill を出荷しています（環境内で確認できる）。エージェントがタスクをこなせても非効率な場合や、ときどき完了しない場合に、skill で指針を与えて、ツール呼び出しの回数や所要時間を減らし、確実にゴールへ導きます。
- **エンドツーエンドの業務プロセスの定義**：例として、Jared が前日のシアターセッションで扱った cash flow analysis があります。期待する結果、見たいデータ、ダッシュボードの姿を skill に書けば、その skill にアクセスできる全員が一貫した体験を得られます。inventory analysis、procure-to-pay、経費のシナリオでも同じです。ポリシーも skill に含められます。

パートナーへの期待は次のとおりです。

- ISV ソリューションや拡張機能に business skills を組み込み、アプリと一緒に展開するインテリジェンス層の一部にする
- お客様と一緒に、お客様の体験を定義する。この「プロセスの整理を支援する」ことが大きな機会になる
- 分析などの end-to-end プロセスのテンプレートを、ソリューションの一部として配布する。ただし、展開後は各お客様の環境に合わせてカスタマイズする必要がある

Jared は、skill の作り方のデモやベストプラクティスは時間がなく別の機会に回すと話しました。また、プライベートプレビューに参加したパートナーへの謝辞を述べ、フィードバックを今後のリリースに反映すると言っています。

### 5.4 パートナー支援プログラムと FastTrack（Gokul）

Gokul は、ERP 向け FastTrack program を率いています。主力の施策として Success by Design とポートフォリオ・パートナーが継続中です。昨年はポートフォリオ・パートナーが約 180 社あり、合計で約 2,000 件の go-live を実現しました。ポートフォリオ・パートナーではない場合は、参加の機会だとしています。

持ち帰る要点として 3 つが挙げられました。

1. FTRSA（FastTrack Recognized Solution Architect）の来年度分の指名が開始された
2. ポートフォリオのスコアリングを、AI・エージェント関連の貢献も含める形に拡張する（来年に向けて考慮される）
3. 営業前段階（プリセールス）のコストが上がっているという声を受け、エージェント機能を強化する

3 点目の具体例は次のとおりです。

- 顧客の文脈（顧客の業務プロセスとデータ）を持つデモ環境を作成できる新しい体験が、今後登場する
- FastTrack をプリセールスにも拡大する。**必ず勝ちたい案件で 100 万ドルを超える場合**は Microsoft の営業担当に連絡して FastTrack の支援を受ける。**100 万ドル未満**なら COE の portfolio architect に連絡する

### 5.5 アプリとエージェントの融合と、3 層のエコシステム

Gokul は、この 2 年でアプリとエージェントが一体になり、境界が曖昧になっていると述べました。前述のとおり「すべてのユーザーに Copilot」から「すべての業務プロセスにエージェント」へ広げる。そして、Microsoft がすべてを作ることは現実的に不可能なので、エコシステムを 3 層で考えると説明しています。

| 層 | 内容 |
|---|---|
| Microsoft 層 | ファーストパーティのエージェントと FastTrack templates |
| サードパーティ層 | パートナーがエージェントを作って顧客に届ける |
| カスタム層 | お客様ごとのラストワンマイルのエージェントを、パートナーが作って展開する |

FastTrack templates はこれまでに約 7 つが出荷されています。ストア監視、財務の照合や期末処理（period close）、sales order processing agent などです。利用状況では、sales order processing agent を使うお客様が最も多く、今後さらに拡張するとのことです。

### 5.6 Azure SRE Agent for Dynamics 365（動画）

マネージドサービスを提供しているパートナーに向けて、Gokul は「夜中にバッチの失敗で起こされることがなくなったら」と問いかけ、動画を流しました。Azure SRE Agent と D365 を統合した、1 つのエージェントで Azure 全体の展開と D365 の両方を監視できるという内容です。動画の内容は次のとおりです。

- アラート「本番の sales order フォームの読み込みが遅い」を受けて、エージェントがインシデントを作成し、自律的に調査を始める
- FastTrack skills を使い、Dynamics のテレメトリと Application Insights を分析して、前夜のリリース直後にロード時間が跳ね上がったことを突き止める
- ライブレポートで、どのフォームがどれだけ遅いか、何人のユーザーに影響しているかを確認する
- そのリリースのカスタマイズを調べ、原因を特定する。原因は、フォームを開くたびに注文明細行ごとに照会を実行する新しい credit check パネル
- 修正と構成変更の案を、根拠、リスク、ロールバック計画つきで提示する。**人が確認して承認するまで何も変更しない**
- 承認後、エージェントがプルリクエストを作り、ビルドとチェックを実行し、既存のパイプラインで sandbox にデプロイする
- 同じテレメトリで検証し、ロード時間が 2 秒未満に戻ったことを確認する
- 本番への反映は次の承認済みリリースで行い、エージェントがインシデントレポートを生成する

動画は、「Dynamics 365 向けの FastTrack skills で始め、自分たちの専門知識で拡張してほしい」と呼びかけ、sre.azure.com を案内して終わります。Gokul は、このエージェントは状況を監視し、そのうえで次の最善の行動を取るもので、その行動は人が事前に説明しておいたものでもよいと補足しました。常に human in the loop が保たれる点も強調されています。

### 5.7 Agent deployment program と Dynamics 365 Activate

Work IQ や business skills などの投資に加えて、お客様とパートナーを支える **Agent deployment program** があります。昨年は枠が完売したため、今年は枠を増やしたとのことです。昨年この機会を活用したお客様として、Coca-Cola、John Deere などが挙げられました。Microsoft がパートナーと協力して約 4 つのエージェントを作り、本番稼働まで支援する。残りの 40〜50 のエージェントはパートナーがお客様のために作る、という説明です（この数の部分は音声が聞き取りにくく、正確な意味は確認できません）。目的は、可能性を示すことと、Microsoft 自身も投資することの両立です。

その上で Gokul は、**Dynamics 365 Activate** を発表しました。人とエージェントが協力して、D365 の導入を最初から最後まで進める新しい方法で、複雑さを減らして価値実現までの時間を短縮します。現時点では次の機能があると説明されました。

- configuration（構成）
- migration（移行）
- requirement analysis（要件分析）
- assessment（評価）

翌日には、移行に関する 2 つの機能が発表される予定です。1 つは Salesforce からの移行、ERP 側は SAP からの移行です。SAP については翌日に 2 つのセッションがあり、1 つはラボで製品を体験できるもの、もう 1 つは一日の終わりに仕組みを見せるものだと案内されました。

### 5.8 ビジネス変革：AI transformation model、プログラム、インセンティブ（Maitane）

Maitane は、「パートナーのサービスモデルが書き換えられている」と問題提起しました。AI がお客様の期待を変え、パートナーは Business Applications だけでなく、Copilot、Azure、データ、セキュリティにも投資している。その結果、以前は考えなかった新しい能力、人材、プラクティスへの投資が必要になっているという認識です。

支援は次の 2 本柱です。

**(1) パートナー自身の変革を支援する**

- **AI transformation model**：今年に McKinsey と共同で作成したプレイブックです。製品づくり、go-to-market（パッケージの仕方）、デリバリーモデルなど、市場の動向を扱います。価格モデルでは、時間単価（bill hours）からお客様の成果に基づく形への動きが見られるとのことで、これは後のパネルで扱うと予告されました（固定価格に触れた部分は音声が不明瞭で、内容を確定できません）。経営層やプラクティスリード向けの内容です。
- **アセスメント**：プレイブックが白書で終わらないよう用意されたものです。質問に答えると、同じ業界や同じ国の組織とのベンチマークが得られ、強みとギャップが分かります。結果は経営層やプラクティスリードと共有し、投資する領域を決めます。
- **customer zero**：自社の組織を AI で変革し、その経験を語れるようになることです。お客様から依頼や需要が多い領域（財務、HR、オペレーションなど）から始め、プロセスを洗い出すことを勧めています。顧客に対する信頼性と語れるストーリーになります。Microsoft は成功事例を増やしており、共有を呼びかけました。
- スキリングとセルフサービスの教材は Partner Hub にあります。

**(2) 製品イノベーションを顧客に届けるためのプログラムとインセンティブ**

- プリセールスとポストセールスをより良くするための資金提供プログラムがあり、対象には business application も含まれます（資金の対象コンポーネントの部分は音声が不明瞭です）。
- 10 月に発表したインセンティブ変更（音声では "CSP seaport" と聞こえます。表記は確定できません）：自社が CSP 経由でサービスを取引していなくても、プリセールスを行った場合はインセンティブを請求できる。以前は Enterprise セグメント向けだったものを、全顧客セグメントに拡大したとのことです。
- すべてのプログラムを **Frontier Accelerate** に統一しています。顧客の席数や TPIT などの適格基準を揃え、プログラムごとに読み込まなくても済むようにする狙いです。ソリューション領域をまたいで一貫性を持たせます。

### 5.9 パートナーパネル（HSO と Hummingbird）

Niels の司会で、従来型の ERP パートナーの立場として Alan（HSO）、AI ネイティブでアウトカムベースの納品を行う立場として Greg（Hummingbird）が登壇しました。

**Alan（HSO）：大きな変化と、2 つの取り組み**

- Alan は ERP に約 34 年携わっています。ERP は高額で長いプロジェクトと見られがちで、終盤にはお客様が「ERP 疲れ」の状態になり、これ以上お金を使いたくなくなる。そうなるとマネージドサービスに進めず、本来は基盤が動いた後に出る価値の大きい部分に届かない、という課題を語りました。
- 想定外だったのは、お客様の期待が変わる速さです。ツールが完全に整う前から、「はるかに低いコストでやってほしい」と求められます。
- 対応として、HSO は自社でエージェントを構築し、導入を加速しています。これが多くのプロジェクトで売上を押し下げているものの、お客様にとってはコスト低下になる、と話しました。この取り組みの社内名称が **Project Velocity** です。
- もう 1 つが、ビジネスアプリのプロジェクトを行っていないお客様に AI を提供する取り組み、**Horizon** です。Alan は、これで売上減を補って余りあることを期待していると話しました。

**Greg（Hummingbird）：AI を前提にした会社づくり**

- 創業 3 年の会社で、すべて AI を前提に作られています。
- 例 1：プロジェクトの進め方の方法論全体が AI ベースです。デリバリーチームは 360 人、プロジェクトマネージャーは 10 人で、agentic delivery によって少人数で多くをこなしています。
- 例 2：プロジェクト期間を短縮しています。ERP でも 6 か月を超えるプロジェクトはやらず、期間に区切りをつけています。
- 例 3：ERP 向けのエージェント・ライブラリ **Flight Path** を作りました。アクティブなプロジェクトのお客様には、クリックしてドラッグするだけで使える形で提供しています。例として、荷物の写真を撮って ERP に記録する shipping copilot agent が、無償で提供され、導入も無償です。サービスプロジェクトが、お客様の良い成果の妨げにならないようにしたいという考えです。

**事例 1：AB Mori（HSO、Alan）**（社名の綴りは聞こえたままの表記です）

従業員 6,000 人のベーカリー向け原料の製造・流通会社で、グローバル企業です。課題は注文入力でした。注文情報は、メール、添付 PDF、WhatsApp など非構造化された形で届き、担当者がマスターデータと照合して ERP に入力する必要があり、遅くて誤りも起きやすい。そこで、HSO が持つ order management agent で非構造化データの取り込みを自動化し、検証を行いつつ ERP に入力できるようにしました。このエージェントは 2 年ほど前に本番稼働したもので、HSO は以前から agentic delivery を続けているとのことです。初期テストの結果は次のとおりです。

- 5,000 件の注文
- 精度 99.9%
- 入力にかかる時間を 93% 削減

学びとして Alan が挙げたのは、お客様にエージェント開発を受け入れてもらうには、**十分に小さく、しかし十分に困っている課題**から始めることです。お客様が投資し、フィードバックもくれる「特定された問題」から始め、そこから広げます。この事例では注文入力から始めて、order-to-cash 全体に向けて次々にエージェントを作れたそうです。

**事例 2：Pittsburgh のデータセンター企業（Hummingbird、Greg）**

Hummingbird は time and materials のプロジェクトをほとんどやらず、上限を設けて、go-live や顧客が望む事業成果に自社の報酬を結びつけることが多いと話しました。リスクを抑えるために、エージェントを使います。理由として、人を大量に投入しても利益が出ず、進行も速くならないと説明しています。

事例は、Pittsburgh に拠点を置くデータセンター企業です。project ops、field service、supply chain を扱う複雑なプロジェクトで、モジュールごとの go-live に報酬の解放を結びつけました。財務上の結びつきがある成果は 150 件になり、それぞれに対応するエージェントのツールキットを作って、素早く進めたとのことです。

顧客から「GL の体験を良くしたい」といった要望が出たとき、すでに作ったことがあれば「ここにエージェントがある。まずこれを使おう」と始め、ゼロから作るのではなく gap fit（差分の確認）で進めると説明しています。Greg は、このツールキットと ScaleFast（Alan のパートでは ScaleFest とも聞こえます。表記は確定できません）が助けになっていると話し、後者には「Another plug for you」と Niels に向けた一言を添えています。

**最後の質問：既存の ERP パートナーが最も変えるべきこと**

- Alan：変わらないのは、業界、データ、ビジネスプロセスに関する知見が中心にあることです。優れたエージェントも、その知識がなければ優れたものにならない。最大の変化は技術そのものではなく、**人が運用モデルと取り組み方を変えること**で、長く続けてきたパートナーほど影響が大きい、と話しました。
- Greg：Alan と同じ意見で、新興のパートナーでも人の変化は必要だと述べました。運用モデルを変える必要はなかったが、人の働き方（human operating model）は変えなければならない。加えて、Activate に強く依存しており、データ移行、ディスカバリー、フィールドとフォームの設計の自動化は大きな強みになる。毎回同じ作業の費用をお客様に払わせるのは筋が通らない、と述べて Activate を評価しました。

## 9. まとめ

このセッションは、ERP の業務プロセスを作り直す機会は大きく、そこでパートナーが果たす役割も大きいという話でした。要点は次の 4 つです。

1. エージェントの性能は文脈の質で決まる。business skills（プロセス）と AI descriptions（メタデータ）が、ERP のインテリジェンス層として加わった。どちらもパブリックプレビューで、パートナーは ISV 製品への組み込みと、お客様のプロセス整理に使える。
2. 導入の進め方も変わる。Dynamics 365 Activate が発表され、FastTrack、Agent deployment program、Azure SRE Agent for Dynamics 365 とあわせて、導入から運用までをエージェントで支援する。
3. パートナーの事業モデルも変わる。AI transformation model とアセスメントで自社の立ち位置を測り、Frontier Accelerate に統一された資金・インセンティブを活用する。
4. パネルの 2 社は、導入の加速（Project Velocity）やアウトカムベースの契約を実践していて、最大の課題は技術よりも人の変化だと話した。
