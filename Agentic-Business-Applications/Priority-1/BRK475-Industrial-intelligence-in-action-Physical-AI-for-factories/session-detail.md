# BRK475 Industrial intelligence in action: Physical AI for factories

## 1. はじめに

このセッションは、工場の運用に「フィジカル AI（Physical AI）」を持ち込むときの考え方、Microsoft が用意する技術スタック、そして Unilever の実例を紹介する内容です。前半は Microsoft の 2 人が、インテリジェンス（知見）をどう束ね、エッジからクラウドまでをどう構成するかを説明します。後半は Unilever の Bhaskar Das 氏が、工場でのデジタル化と AI 導入で得た教訓を語ります。

Bhaskar 氏の話の核心は、「**自律化を追い求めるのではなく、獲得していく**」という姿勢と、「**デジタルツインを作りたい、から始めてはいけない**」という点です。最初に解決すべき現場の課題を決め、技術的な成功、運用上の成功、経済的な成功の 3 つを満たすことが重要だとしています。

このセッションでは、ライブのデモは行われていません。ただし、Unilever の Pondicherry 工場に関する紹介ビデオが上映されました（6 章）。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK475](https://ignite.microsoft.com/en-US/sessions/BRK475)

## 4. 発表者が伝えたいメッセージ

Alfonso 氏は、組織にとって最も重要な資源は「インテリジェンス」だと述べています。それは、30 年勤めた現場担当者の知識、日々使うシステムやツール、データに宿っていますが、いまはまだサイロに分かれています。AI をスケールさせるには、これを統合する**インテリジェンスレイヤー**が必要です。そして産業の領域では、セキュリティだけでなく、従業員に提示するインテリジェンスが正しいという意味での**信頼**、データを組織、国、拠点、工場の中に留めたい場合の**ソブリン性**、複数のエージェントをどう統治するかも、同じく重要だと述べました。

Michael 氏は、製造業の基本（安全、品質、効率、生産）は変わらないが、それを実現する方法が AI とデータによって根本的に変わりつつあると話します。IoT は「何が起きたか」を教え、産業 AI は「何をすべきか」を教え、フィジカル AI は「新しいことを起こす」助けになる、という整理です。

Bhaskar 氏のメッセージは、AI を現場の人々の信頼とともに進めることです。モデルの精度の数字を示すのではなく、現場が認識している課題を一緒に解く、ブラックボックスにしない、という姿勢を説いています。

## 5. 発表内容の詳細

### 5.1 インテリジェンスレイヤー（Alfonso 氏）

Alfonso 氏は、組織の集合的な知識と業務のやり方を表す概念として、インテリジェンスレイヤーを 3 つに分けて説明しました。

| 層 | 内容 | 対応する Microsoft の機能 |
| --- | --- | --- |
| Work intelligence | 従業員が日々使っているツール | Work IQ |
| Data intelligence | 設備監視用の時系列データや、新製品のシミュレーション用の機微なデータなどのリポジトリ | Fabric IQ |
| Organizational intelligence | 組織がどう動き、どう統治されているか。エージェントにコンテキストを与える | Foundry IQ |

前日の基調講演で触れられたとおり、これらをまとめて産業のインテリジェンスレイヤーを作る取り組みが **Microsoft IQ** です。その上にエージェントが載り、使うモデルやツールを問わず、このインテリジェンスレイヤーに基づいていれば必要な性能が出せる、という説明でした。

産業領域で見られるユースケースとして、Alfonso 氏は、リスクを予測して自己対応できる「エージェント型サプライチェーン」を例に挙げています。ほかに、製造・モビリティに加えエネルギー、防衛、消費財などで数百から数千の事例があるとのことです。本セッションはそのうち、工場運用でのフィジカル AI を扱います。

### 5.2 製造業の基本と IoT → 産業 AI → フィジカル AI（Michael 氏）

Michael 氏は、製造業がまず心配するのは安全で、次に、持っている機械を最も効率的・効果的に使って高品質な製品を作ることだと述べています。基本は変わらず、変わっているのはその実現方法です。

簡単な例としては、ビジョンシステムが保護具（ヘルメットや視認性ベストなど）の着用を確認して警告すること、天井ホイスト（吊り具）の下を歩くような危険区域を特定して警報を出すことなどがあります。大きな成果が出るのは、品質検査、AI による音響監視、資産の信頼性と保全（部品を事前に発注するツール利用型モデルなど）、生産フローの最適化、プロセスの例外検出、さらに例外が起きる前の修正といった分野だと説明しています。

Michael 氏のチームは Azure IoT を扱っており、IoT／産業 IoT は 10〜15 年ほど「可視化」を担ってきました。センサー、機械に接続されたデバイス、SCADA、DCS からデータを集める安全で更新可能な基盤です。その整理が次のとおりです。

| 段階 | 役割（発言どおり） |
| --- | --- |
| IoT | 何が起きたかを教える |
| 産業 AI | そのデータを使って、何が起きるべきかを教える |
| フィジカル AI | 新しいことを起こす（リアルタイムで成果を出す） |

また、産業データは付随するコンテキストの質で決まるので、データのセマンティクスを管理し、その上にインテリジェンスレイヤーを作る必要があるとも述べています。

### 5.3 顧客の段階

顧客は旅路のあらゆる段階にいると、Michael 氏は説明しています。

- **可視化から始める顧客**：1950〜60 年代に設置された設備にはデジタル信号を取り出しにくいものが多く、カメラをセンサーとして使う（古い計器やダイヤルを文字認識でデジタル化する）使い方が、よく要望され効果も高いユースケースになっています。
- **中間の顧客**：可視化から、データ上の機械学習へ進んでいる。人とエージェントの混成チームで成果を出す例も多い。
- **最先端の顧客**：ソフトウェア定義の自動化と、クローズドループのフィジカル AI を実現している。例として Husqvarna が、カメラと AI で組み立てラインから出てくる部品を検査し、仕様を満たさなければ自動的に排除している。

### 5.4 アーキテクチャの考え方：アダプティブクラウドと perceive / reason / act

意思決定は、自動化に近い、必要な場所（エッジ）に置くべきだと、Michael 氏は述べています。これはクラウドとエッジの対称性であり、Microsoft は「**アダプティブクラウド**」と呼んでいます。狙いは、Arc 対応の統合された管理プレーン、データとセマンティクスのプレーン、インテリジェンスのプレーンを持ち、データや意思決定の場所を気にしなくて済むようにすることです。時間と安全が重要なプロセスの近くで判断されるようにするという考え方です。

フィジカル AI は **perceive（知覚）／reason（推論）／act（行動）** で整理されます。

- **Perceive**：IoT の技術が基盤。資産の接続や管理、OPC UA のようなオープン標準による資産の自動検出も含みます。センサーのデータを集めます。
- **Reason**：データをもとに機械学習や AI の推論を行います。
- **Act**：制御信号を同じチャネルで戻し、管理アクションや実行中のプロセスのパラメーター更新を行います。実機にリアルタイムで作用し、問題を未然に防ぎます。

### 5.5 Microsoft の製品・機能

データを取り込む 2 つの方式が示されました。

| 方式 | 説明 |
| --- | --- |
| **Azure IoT Operations**（2 年前の Ignite で発表） | 拠点から多くのものをつなぎ、システムとして機能させる。データを上に送る前に、設備が動いている状況のコンテキストを把握できる |
| **IoT Hub** | 埋設タンク、輸送、物流、サプライチェーンなど、デバイスや資産をクラウドに直接つなぐ場合に使う |

Michael 氏は、目的は接続を売ることではなく、**OEE、歩留まり、品質、安全の改善**といった事業成果だと述べています。そのために、AI の推論には **Microsoft Foundry**、より深い分析には **Microsoft Fabric** へつなぎます。さらに、すべてを Azure のリソースとして登録・管理する **Azure Device Registry** が使われます。これにより、あらゆる資産を他の Azure リソースと同様に管理でき、OT の資産にも IT のポリシーを適用したり、証明書のセキュアな入れ替えを行ったりできます。これらが ARM ベースのリソースになるためです。

エッジには **Azure Local** があり、Azure Local の **小型フォームファクター**も新たにプレビューとして紹介されました。ゲートウェイや「robotic surfaces」（聞こえたまま。意味は確定できません）のような、より小さなデバイスに載せられるとのことです。**Foundry Local** は今回のイベントで GA となり、モデル、エージェント、推論をエッジで実行できます。

2 年ほどの投資で、次の新情報が語られました。

| レイヤー | 内容 |
| --- | --- |
| IoT Hub の近代化 | IoT Hub と Azure Device Registry の統合。X509 証明書管理、MQTT 5 サポート、Azure Device Update のデルタ更新など |
| Azure IoT Operations の新しいフォームファクター | **AIO Essentials**。ロボットのヘッドや産業用ゲートウェイのような、より小さなデバイスに載せられる |
| Perceive | **Fabric へのネイティブ統合**。IoT から Fabric へ直接データをストリーミングし、より高度な分析を行う（Michael 氏が最も楽しみにしていると述べた点） |
| Reasoning | ソリューションカタログに加え、MCP クライアントと MCP サーバーを「あらゆる所に」追加し、エージェントとこの領域のシステムが相互作用できるようにする |

### 5.6 パートナーエコシステム

Michael 氏は、顧客はすでに自動化ベンダー、ISV、SI と協力しているため、Microsoft は事前にパートナーと検証し、顧客に展開する際に「動く」状態、検証済みで参照があるカタログを用意するよう努めていると述べました。モデル提供者、ISV、自動化ベンダーとも協力しており、NVIDIA とは Open USD でデジタルツインを提供しているとのことです。

### 5.8 Unilever の紹介ビデオ（Pondicherry）

ビデオはナレーションで進みました。内容は次のとおりです（固有名詞の綴りは音声認識の都合で確定できないものを含みます）。

- **目標**：Pondicherry の 2026 年の目標は、1.7 倍の成長で 50 万トン、60% のキャパシティの解放、トンあたりコストの 3% 削減。これは、軽微な停止（minor stoppages）と非効率な段取り替え（changeover）が OEE に影響しているために制約されている。
- **取り組み**：Accenture、NVIDIA、Microsoft と組んで、次世代のフィジカル AI デジタルツインを構築している。機械の可観測性、マルチモーダルなインテリジェンス、クローズドループの実行、物理的に正確なシミュレーションを組み合わせ、リアルタイムの機械データを最適な運用判断につなげる。エッジ AI、Microsoft のハイブリッドクラウド、NVIDIA の AI と Omniverse が基盤で、**23 台のカメラと 130 を超える IoT センサー**で、性能に影響する細かな事象を捉えている。
- **段取り替えの支援**：ライブ映像がフィジカル AI ツインに入り、2 本のセンターライン（キャップ用の白線、ボトル用の緑線）が表示される。オペレーターは緑線を白線に合わせるよう視覚的に誘導され、揃ったら設定を固定してボルトを締める。これにより、初回から正しく、正確で一貫した段取り替えができる。
- **軽微な停止による OEE 損失**：デジタルツインの「エージェント型の頭脳」が、映像とセンサーデータを分析してアラームを出す。対象は Posimat マシン（音声認識の都合で表記が確定できません）。1 件は圧力低下による複数の「inverse bottle」の偏差（聞こえたまま。意味は音声からは確定できません）、他の 2 件はピストンの位置ずれの可能性を示す。システムが問題を強調表示し、オペレーターが素早く解決できるよう手順を案内する。
- **エージェント**：Optimus AI（聞こえた綴り）が、オペレーターの入力を待つ従来のシステムと違い、映像、センサー、OEE、保全のデータを継続的に分析して異常を検出し、根本原因を分析して対応を提案する。

### 5.9 Unilever との対談（Bhaskar Das 氏）

Michael 氏は、Unilever の美容・パーソナルケア・ホームケア・食品の製品が 190 か国の 37 億人に届き、その背後の大きな製造ネットワークが、約 6 年にわたって Microsoft Azure 上でデジタル基盤を構築してきたと紹介しています。いまは AI、産業 AI、フィジカル AI の領域に移っています。

**(1) 6 年前と今の工場**

Bhaskar 氏によれば、6 年前の工場には多くのデータがあったものの、サイロ化され、OT と IT の間に大きな断絶がありました。製造や設備のマネージャーが自分で点と点をつなぐ必要があり、改善活動ではなく情報の収集とレポートに時間を使っていたそうです。そこで最初に次の 3 つに取り組みました。

1. 工場とクラウドの間のサイバーセキュアな接続レイヤー。当初は工場からクラウドへ情報を引き出す一方向の「ハイウェイ」だったが、現在は双方向。すべての工場で標準化する必要があった。
2. 「デジタルファクトリーのマスターアプリ」群。製造エクセレンスのチームと合意した特定の課題を解く機能で、例として工場のパフォーマンス管理、SPC、既存のワールドクラス・マニュファクチャリング手法のデジタル化を挙げている。
3. Azure 上の基盤となる機能。スケールさせるために必要で、最初は Azure のクラウドで始め、今は Azure のエッジにも基盤を構築している。

Michael 氏が画面のボードにある数字として挙げたのは、**26 のツイン、1,000 を超える生産ラインの接続、190 の工場**、1 日あたり大量のメッセージ、でした。

**(2) AI の投資先をどう決め、どうスケールさせたか**

次のような判断の流れが語られました。

1. 工場から上がってくる課題の種類（資産の最適化か、品質改善かなど）を見て、**金額的に大きな価値**があるものを選ぶ。
2. **本当に AI が必要かを自問する**。エンジニアリングによる解決策を現場に入れれば足りる課題もある。
3. 通過すれば、良質なデータがあるかを確認する。探索的データ分析で、相関や因果があるかを理解する。
4. データがあれば、そのソリューションが工場の仕事のやり方に収まるかを確認する。

**(3) 人を巻き込み、AI の判断への信頼を築くには**

Bhaskar 氏は、現場（製造マネージャー、エンジニア、オペレーター）が、そのプロジェクトを行う理由を理解することが重要だと述べました。「モデルは 95% 正確」のような統計を売り込んでもオペレーターには効かず、**現場が自分の課題として認識する問題を見つけ、解決の旅に連れて行く**ことが有効だというのが経験です。

- AI モデルをブラックボックスにしない。データサイエンスの詳細でなく、何を解こうとしているか、どんな制約を扱うか、何を最適化するか、出力は何かを理解してもらう。
- 探索的データ分析に現場を巻き込み、コントロールした試行（control trials）を行い、期待どおりの価値と正しい結果が出ることを示す。
- ロジックと価値を理解すると信頼が生まれ、使われ方が増える。クローズドループに進みたいなら、人がモデルの裏側を理解し、信頼を築き、使って推奨を気に入ってからクローズドループに進む。

**(4) 「自律化を追い求めるのではなく、獲得する」**

Michael 氏が、Bhaskar 氏の哲学として「自律を追いかけるのではなく、獲得している」と紹介し、次のステップに進む前に何を証明する必要があるかを尋ねました。Bhaskar 氏の答えは次のとおりです。

- 製造プロセスは複雑で、AI モデルを入れればプロセス全体が最適化されると考えるのは危険。設備の損傷、廃棄の発生、品質低下、最悪の場合は安全事故のリスクがある。
- 出力が、プロセスを熟知した**工場の人々**によって検証されていること。
- データの品質が、モデル構築中だけでなく、**通常運用（business as usual）の段階でも**一定以上に保たれていること。
- go-live 後に、モデルのドリフトや特徴量のドリフトを測るなどのプラクティスを裏側に組み込んでおくこと。
- この土台ができたら、獲得の旅を続ける。クローズドループで動くシステムを作り、デプロイすることは、時間をかけて獲得する「運用上の特権」だと述べています。

**(5) 製造業の人が最初にすべきこと、すべきでないこと**

- **最初にすべきこと**：自分たちの製造の人々に、本当に解決したい課題を尋ねる。これで現場の支持が得られ、成功の測り方も決まります。
- **成功の 3 つの側面**：技術的な成功（モデルがうまく動く）、**運用上の成功**（人が継続的に使い、仕事のやり方に組み込む）、**経済的な成功**（価値の実現と、良い費用対効果）。あとの 2 つが成り立つには、工場が価値あると認識する課題から始め、現場に旅に加わってもらう必要があります。
- **決して最初にすべきでないこと**：「デジタルツインを作りたい」から始めること。間違った前提だと述べています。

## 7. 注意点・発表者の気付き

- **信頼は技術だけでは得られません。** 精度の数値を示すより、現場が認識する課題に取り組み、モデルをブラックボックスにせず、試行を一緒に行うことが有効だと、Bhaskar 氏は経験から述べています。
- **AI が必須かを最初に問い直します。** エンジニアリングの解決策で足りる課題があります。
- **クローズドループは段階を踏みます。** 人がモデルを理解し、信頼してからクローズドループに進みます。設備の損傷、廃棄、品質低下、安全事故のリスクがあるためです。
- **データ品質は構築後も維持します。** ドリフトの測定を含め、運用段階の仕組みが必要です。
- **「デジタルツインを作りたい」から始めてはいけません。**
- 古い設備ではデジタル信号が取り出しにくいという現実があり、カメラをセンサーとして使うことが入口になる例が挙げられました（Michael 氏）。
- インテリジェンスのサイロ化が、AI をスケールさせる最大の問題として挙げられました（Alfonso 氏）。

## 8. 利用者にとっての利点

## 9. まとめ

このセッションは、産業の現場でインサイトと行動の間を縮めるための、フィジカル AI の考え方と実装を説明しました。Alfonso 氏は、サイロ化した知見を Work IQ、Fabric IQ、Foundry IQ（Microsoft IQ）で束ね、信頼とソブリン性とともに進めることを示しました。Michael 氏は、IoT から産業 AI、フィジカル AI への流れを perceive / reason / act で整理し、Azure IoT Operations、Azure Device Registry、Azure Local、Foundry Local などの新情報（AIO Essentials、Fabric へのネイティブ統合、MCP の追加、Foundry Local の GA）を紹介しました。

Unilever の Bhaskar 氏は、6 年のデジタル基盤づくりを経て、課題の選び方（価値、AI の要否、データ品質、現場への適合）、人を巻き込む方法、自律化を「獲得する」姿勢、そして「デジタルツインから始めない」という助言を語りました。
