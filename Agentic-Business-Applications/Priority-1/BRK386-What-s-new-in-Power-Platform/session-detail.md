# BRK386 What's new in Power Platform

## 1. はじめに

このセッションは、Power Apps、Power Automate、Power Pages を使うメーカー（maker）や開発者に向けて、この 1 年の Power Platform の改善点と、AI（コーディングエージェント、Copilot）との組み合わせ方を紹介する 45 分の発表です。前半は Jed Brown 氏が、既存製品の性能改善と「hybrid authoring（ハイブリッドオーサリング）」を、後半は Adrian 氏が、アプリの中の Copilot と、Copilot や Cowork からアプリのデータを使う仕組みを、それぞれデモ中心で説明します。

発表全体のメッセージは、最後に Jed 氏が挙げた次の 3 点に集約されます。

1. すでに作ったアプリやフローへの投資は、守られ、さらに良くなる。
2. 人とエージェントが、作る側としても、仕事をこなす側としても協力できるようにする。
3. 今日使うためのツールを、フィードバックを受けて改善し続ける。

なお、このセッションの発表者は、AI の利用は「あなたの条件で（on your terms）」と繰り返し述べています。本日紹介する内容のために、トークンの消費が必須になることはない、という説明でした（デモの中には、自分の Copilot クレジットを使うものもあります）。

## 4. 発表者が伝えたいメッセージ

Jed 氏は、チームの判断基準として次の 4 つの原則を挙げています。

1. **エンドツーエンドのソリューション**：優れたビジネス変革は、アプリ単体や自動化単体ではなく、ROI の高い「end-to-end」のソリューションである。そのためにガバナンスを効かせられるプラットフォームが土台になる。
2. **品質**：基盤が速く、信頼でき、期待を満たしていなければ、他のことは意味がない。Jed 氏自身、目新しい機能よりも性能と品質に興奮すると述べている。
3. **AI on your terms**：トークンと予算を尊重し、AI を節度を持って取り入れる。本日紹介する内容に、トークンの消費は必須ではない。
4. **投資を守り、活かす**：Canvas も Model-driven apps も Power Automate も「なくならない」。投資を増やしている。

「AI で勝つには作り直しが必要」と言われることがあるが、それは正しくない、というのも強い主張です。アプリとフローのひとつひとつが、データ、ルール、承認、プロセスという、自社の仕事の進め方を記録した知識であり、それは置き換えるのではなく、積み上げるものだと説明しています。

### 5.1 この 12 か月の実績と、プラットフォームの考え方

Jed 氏が挙げた数値は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| リリースした改善 | 130 件超（過去 12 か月） |
| うち品質向上・性能の分類 | 65% |
| 削除した領域 | 24 以上（性能や使いやすさの基準を満たさない、あるいは邪魔になっているもの） |
| 評価 | ローコード分野で第 1 位のプラットフォームと、Gartner と Forrester に再確認された |

発表者は、ここに挙げた数値は今後も増えていくと述べています。また、Copilot Studio と Power Platform が並んで存在すること、コネクター、Dataverse、ガバナンス、環境（environments）といった共有サービス、Azure AI Foundry のようなファーストパーティとサードパーティのソリューションとの連携についても触れました。重視しているのは、問題の発見から、構築、自動化、そして観察・変更・変化への対応まで、**エンドツーエンドで考えること**です。

現状の課題として、ツールが孤立している、知識がサイロ化している、従業員がアプリの切り替えを繰り返している、という点を挙げ、「思考パートナー」「共有コンテキスト」「意図に基づくアクション（intent-driven actions）」を目指す、と説明しています。構成としては、Copilot が AI と人が出会う UX、Copilot Studio がエージェントとエージェントフローを作る層、Power Platform がエージェント、コネクター、ビジネスロジック、人間（human in the loop）をつなぐ層で、Power Platform Admin Center、M365 Admin Center、Managed Environments で管理する、という整理でした。

### 5.2 Canvas apps とモバイル

Jed 氏は、既存製品の改善（過去 12 か月の投資の 65%）から紹介しています。

**Canvas apps**：パフォーマンスの大幅な改善、機能の削除と、ペインポイント（paper cuts）の解消、そして標準コントロールへの継続投資が柱です。標準コントロールは、より簡単で、速く、トークンの面でも安価に使えることを重視しているとのことです。約 50 秒の動画で、最近リリースしたコントロールのハイライトが紹介されました（今週リリースされたものもあるとのこと）。

**モバイル**：起動時間などの性能と品質を重視し、最新の取り組みで**起動が最大 55% 高速**になりました。バックグラウンド同期やオフライン対応も強化しています。さらに、ネイティブ機能の強化として 3 つの領域を紹介しています。

1. **組み込みのネイティブコントロール**：今すぐ Canvas アプリにドラッグ＆ドロップで使える。発話では「6 つ」と聞こえました。名前が挙がったのは、QR コードにも対応する Barcode Scanner、PDF Viewer、Pen Input、DataWedge、Geolocation で、Biometrics（生体認証）は「これから来るもの」と説明されています。ログイン・ログアウトが楽になる、という話です。
2. **独自のネイティブコンポーネントの構築**：コーディングエージェント向けの新しいスキルや、好みの IDE を使って、提供済みのもの以外のコンポーネントを作れる。ファーストパーティ化してほしいコンポーネントの要望も歓迎している。
3. **ネイティブモバイルアプリのエージェント型オーサリング**：コードを最初から最後まで自分で持ちたい場合や、iOS / Android 固有の機能・ジェスチャーが必要な場合向けに、React Native アプリを Power Platform 上で直接サポートする。コードアプリ（code apps）に近い考え方で、モバイルのみ、モバイルファーストのアプリに向く。

顧客事例として、倉庫で Bluetooth センサーの温度をリアルタイムに読み取る「温度プローブ」を作った話があります。既存の Canvas アプリに直接つながり、温度の手入力をせずに、デバイスに近づくだけで値が入ります（顧客名は挙げられていません）。

1. 性能の向上（デモあり。後述）
2. データ列とグリッド上に、見やすい表現（ビジュアライザー）を作りやすくする
3. （3 点目は、音声認識の結果からは聞き取れませんでした）
4. 現在のビュー（views）をもとにした、より豊かな体験。以前から要望の多かった**カレンダー**がその例

性能については、フォームページの描画が、改善前と比べて「50% 近く（わずかに下）」速いとし、グリッドページも同様に速くなったと説明しています。既存のグリッドと、新しいビューの両方に当てはまります。理由の大きな部分は、ローカルだけでなく**サーバー側でのレンダリングを増やしている**ことだと述べています。

**新しいポータル**：メーカー向けの改善として、「まもなく」新しいポータルが利用可能になると発表されました。既存のポータルはすぐにはなくしません。Pages、Automate、Apps を 1 つのビューにまとめ、横断して最近使った項目に戻り、各資産の新機能を見つけやすくします。パフォーマンスを最優先にしている点も強調されました。Power Automate、RPA、Process Mining、Pages の改善は、今回は詳しく触れず、今後のセッションと最新のブログ記事で扱うとのことです。

### 5.4 Hybrid authoring

Jed 氏は、長年、テクノロジーの言葉は「ショートカット、メニュー、フライアウト」だったが、AI により、自分の言葉と得たい結果から始められるようになった、と述べます。**人の意図が新しいインターフェースになる**、という考えです。それが **hybrid authoring** で、既存のプロセスから始め、AI を使うタイミングと使わないタイミングを混ぜながら、ビジュアルな微調整にも戻れるようにします。トークン予算の有無にかかわらず使えることも重要としています。

対象は 3 種類のユーザーに分けられます。

| 対象 | 想定する環境 |
| --- | --- |
| Pro-dev | Visual Studio、GitHub Copilot など好きな IDE。自分のエージェントを持ち込める（Mistral、Claude など、新しいモデルも例に挙がった） |
| メーカー | Power Platform のスタジオ。ドラッグ＆ドロップに、AI とコーディングエージェントを加える |
| エンドユーザー | Cowork や Copilot の中で、同じ体験を使える |

3 者は、スキルや体験を支える共有インフラを使い、Power Automate、Canvas、Model-driven、Pages の既存または新規の体験の上に構築できます。Code apps では、すでにこの形で作れている、と説明されています。

> 補足：Canvas の GitHub Copilot 連携については、スタジオの画面で「今回発表した」「リリースしたばかり」と述べており、将来は自分の Copilot クレジットを使えるようになるとも話しています。

### 5.5 「作る」から「保守する」へ

Jed 氏は、vibe coding やコーディングアプリでは新規作成のデモが目立つが、**大きなコストは作成後の保守・セキュリティ・監視・変更への対応にある**と述べています。そこで、Automate、Model、Canvas、Code Apps の全体で、保守のライフサイクルのコストを下げるためのスキル群を作り込んでいるとのことです。具体的な領域として、次が挙がりました。

- 要件変更に伴うアプリの改善
- トラブルシューティング（Power Automate の例を後で紹介）
- ガバナンス、アクセシビリティ、ブランドの統一、コードの理解しやすさやドキュメント、承認済みコネクターや API の確認
- セキュリティ監査。「今日発表した、セキュリティに特化したモデル」を使うことも例示された

**顧客の例**（社名は不明）：規制の厳しい業界の顧客で、Canvas、Model、コードアプリの開発に力を入れている。ただし、ある部門は「AI が作ったコードを本番に出してはならない」という方針・規制がある。それでも、アクセシビリティの確認と改善提案、コーディングスタイルやドキュメントの水準の確認など、それ以外の難しい作業ではコーディングエージェントを積極的に使っている。目的は、次の担当者に知識を引き継げるようにすることです。

**Power Automate の診断と修正**：決定論的なフローは、予測可能で信頼でき、安く速いが、下流で何かが変わって壊れると「本当に壊れる」と述べています。MCP またはこのプラグインのスキルで、**何が起きたか、修正案は何か**を理解することで、対応と保守が大きく変わるとのことです。短い動画で示され、資料は終了後に共有すると案内されました。

### 5.6 Copilot in apps（Adrian 氏）

Adrian 氏は、アプリの中の Copilot を、生産性と基幹業務にまたがる「思考パートナー」と位置づけています。単なる汎用チャットではなく、**アプリに基づいて（grounded）**、ユーザーの前にある業務プロセスを理解します。ユーザーはプロセスの流れから離れずに、分析、判断、実行ができ、アプリのデータと権限の範囲にとどまり、ガバナンスのルールも維持されます。

提供状況は次のとおりです。

| 対象 | 状況 |
| --- | --- |
| Model-driven apps の Copilot | 4 月に GA |
| Canvas apps の Copilot | 「11 月の後半に」GA を発表 |

メーカーが形づくれる項目は、画面ごとに定義するコンテキスト付きプロンプト（ディスカバリー用）、画面のコンテキストをデータとして使った回答、データへのフォーカスを持つ既定のエージェント（declarative agent）の設定、そして双方向のアクション（bidirectional actions）です。

### 5.7 Power Apps in Work IQ（Copilot / Cowork / Copilot Studio からアプリを使う）

Adrian 氏は、アプリを頻繁に使うユーザーには Copilot in apps が向く一方、アプリの外にいるユーザーや、たまにしか使わないユーザーには、**アプリとそのデータを、人が作業している場所（Copilot、会議、エージェント）に持っていく**必要があると説明します。そのための仕組みが、Work IQ の **business apps** で、Power Apps を Copilot、Cowork、Copilot Studio から使えるようにします。

要点は次のとおりです。

- 基盤を共通にする：データとユーザーの ID を使う。作業がアプリの外に出ても、ガバナンスされたコンテキストが付いてくる。
- ユーザーの ID、セキュリティ、ロールを使うので、AI を通じても、アプリでできる以上のことはできない。
- コンテキストとして取り込む対象は、Model-driven と Canvas のアプリ、クラウドフローとデスクトップフロー。AI がそれらを読んで応答する。
- 表示先は、Copilot in apps、Copilot、Cowork など。

### 6.2 Canvas アプリ + GitHub Copilot（ライブデモ）

### 6.3 アプリの中の Copilot（Adrian 氏のライブデモ）

### 6.4 Work IQ の business apps（Cowork からアプリを使う）

シナリオは、イベントの管理です。

1. Cowork で、「Event Command Center」アプリについて、近く予定されている特定のセッションのステータスを尋ねるプロンプトを送る。軽い操作。
2. Copilot が「このプラグインを、データに対して実行することを許可しますか」と確認する。
3. 環境の場所は伝えていない。このプロンプトではアプリ名を挙げたが、挙げないプロンプトもある。Work IQ の business apps が、ユーザーが使えるアプリを調べ、適切なアプリとそのテーブルを使って回答する。
4. 該当する 1 件のセッションが見つかった。ほかのセッションも確認したが、対応が必要なものはなかった。
5. 結果をコピーして、「そのレコードについてもっと見せて」と依頼する。レコードだけでなく、データ内の関係も調べ、確認すべき問題を示すこともある。
6. 回答には、スピーカーの名前、開始時刻、部屋が示された。
7. 「スピーカーが確認済みになった」ことを反映するよう、更新を依頼する。
8. アプリで強制されるビジネスルールに従って更新される。保存は**2 段階**で、まず変更内容（pending から confirmed へ）を示し、変更するか保存するかを選ぶ。
9. 保存を選ぶと、データがコミットされ、レコードを確認できる。

- **機能の削除も行っている**：24 以上を削除した。使いやすさの妨げや、基準を満たさなかったため。

Power Platform チームは、4 つの原則（end-to-end、品質、AI on your terms、投資の活用）に基づき、この 12 か月で 130 件超の改善を行い、その 65% を品質と性能に充てました。Canvas のネイティブコントロール、モバイルの起動 55% 高速化、Model-driven のフォーム・グリッドの高速化、新しいポータルなど、既存製品の改善が前半の中心です。
