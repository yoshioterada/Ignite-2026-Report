# BRK382 Deploy solutions at scale with Power Platform or Copilot Managed Runtime

## 1. はじめに

このセッションは、アプリ、エージェント、フローを「作る」段階の次にある「安全に展開し、運用する」段階を扱う 45 分のブレークアウトです。主な聞き手は Power Platform の管理者です。登壇者は、IT 部門が統制しつつ、メーカー（アプリやエージェントを作る人）が止まらずに作れる「グリーンゾーン」の作り方を、Novartis の事例とデモで示します。

後半では、今週 GA になった **Copilot Managed Runtime**（Microsoft の外のツールで作ったアプリも動かせるホスティング基盤）を取り上げ、Power Platform との管理・ガバナンスの違いを説明します。さらに、運用（ホスト、ALM、モニタリング）、コスト管理、そして Copilot Cowork から Power Platform を管理する拡張性のデモが続きます。

## 3. 何に関する発表か

冒頭で Zohar 氏は、次のたとえを使いました。500 年前なら肖像画は、プロの職人（レオナルド・ダ・ヴィンチ）に仕様を伝え、3 年後にモナ・リザのような作品を受け取るものでした。Zohar 氏は、このセッションの準備に GPT で画像を作らせたところ、アートのように見えるものもあったものの、多くは下書きだったと話しています。同じように、誰もが AI でアプリ、エージェント、フローを作れる組織では、管理すべき成果物が大量にできます。それらすべてをモナ・リザのように厳重に守り、結果を恐れるのでは、イノベーション、コスト管理、リスク管理のバランスが取れません。IT は「どんな絵筆と絵の具を机に並べるか」を決め、初心者にも上級メーカーにも作れる環境を用意し、本番へ移せるようにする、という整理です。

Power Platform には新しい 2 つの仲間が加わりました。

- **Copilot Managed Runtime**：今週 GA。自然言語でアプリを作れる。Copilot Cowork、Copilot Studio、Code タブ、前日のデモにあった Lovable などで作ったものが、このプラットフォームに載り、新しいアプリとして管理できる。
- **Microsoft Copilot harness**：最新の AI モデルで強力なエージェントを作れる、エージェント領域の新しい仲間。

「マネージドプラットフォーム」は約 3 年前に Managed Environments から始まり、現在は 4 つの柱に育ったと説明されています。聞き取れたのは **ガバナンス**（少ない労力で可視性と制御を高める）、**マネージドセキュリティ**（Power Platform 管理センターでアプリ、エージェント、フローを守る）、**マネージドオペレーション**（パイプラインで本番へ移す）の 3 つで、4 つ目はトランスクリプトからは確認できません。このセッションでは、グリーンゾーンの確立と、本番への移行に焦点を当てます。

発表の流れは、(1) 背景とビデオ、(2) Novartis の事例、(3) グリーンゾーンのデモ、(4) Copilot Managed Runtime と、そのデモ、(5) 運用（ホスト、ALM、モニター）、(6) コスト管理、(7) 拡張性（Cowork と Power Platform admin plugin）、です。

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**「統制された方法が、いちばん楽な方法であれば、人はそちらを歩く」**という考え方です。冒頭のビデオでも「ガバナンスは結局、人の仕事だ」「ブロッカーではなくガードレールを」という趣旨の発言が繰り返されました。

もう 1 つは、**作る場所が Power Platform の外にまで広がっても、IT が管理できるようにする**という点です。Power Platform のグリーンゾーンは Power Platform の中でしか効かず、しかも管理者が有効化する必要があります（オプトイン）。Copilot Managed Runtime は、これを「既定でオン」にし、外部ツールで作ったアプリも 1 つの管理画面に集約します。

## 5. 発表内容の詳細

### 5.1 ビデオ：ガバナンスは初期から考える

冒頭のあと、複数の人の声をつないだビデオが流れました（話している人の名前・所属・立場はトランスクリプトからは分かりません）。語られた内容は次のとおりです。

- Power Platform は、メーカー側から広がった。メーカーが何も知らずに使い始め、既定の環境から増えていくことが問題になる。
- 数年間は「ワイルド・ウェスト」だった。個人の生産性向上の環境にあった大量のアプリやフローが、ある時点で業務上不可欠になった。
- まずは「作ったものを見られるか、測れるか、誰が作ったか分かるか、ガードレールを設けられるか」。ガードレールはブロッカーではなく、メーカーが壁に当たらず、安全に問題を解決できるようにするもの。
- 悪意で作る人は多くなく、問題に巻き込まれないようにするのが目的。
- 管理者のワークショップで環境ルーティングを知り、ワークショップが終わるまでにはオンにしていた、という話。
- 数人で数万、数十万の環境・アプリ・フローを管理するには、環境ルーティングや高度なコネクターポリシーなどのツールが要る。
- 管理環境グループ（managed environment groups）は、バランスを取りながら規模を広げるのに役立った。
- コミュニティに相談すれば、他の人がすでにぶつかった壁を避けられる。「1 社のセキュリティは、すべての企業のセキュリティだ」という発言もあった。
- 最初からガバナンスを考えること。チームは驚くようなものを作り、本当に業務の要になる。メーカーのそばにいて、障害物を置かない。

### 5.2 Novartis の事例（Nick 氏）

Zohar 氏の質問に答える形で語られた内容です。

**会社と役割**：Novartis のミッションは、患者の生活を改善し延ばすための医療の再構想で、従業員は 77,000 人、医薬品は 3 億人超の患者に届いています。Nick 氏は Novartis に 16 年在籍し、IT サービスデリバリーと運用が出身です。元 M365 の製品オーナーで、Power Platform が導入され、ガバナンスを組み立てた時期を担当していました。この 1.5 年は米国商業部門でテクノロジーパートナーシップを担当し、シチズンデベロッパーのコミュニティと、セルフサービスの AI・技術の機能づくりにも関わっています。

**Power Platform の導入の経緯**：

- 当初から、摩擦を取り除くことを重視した。メーカーが試して作れるようにし、適切なガードレールで一定のガバナンス原則の範囲に収める。
- メーカー向けには、主に**既定の環境**を使った。DLP ポリシーで作れる範囲を制限し、主に M365 のエコシステム内にとどめた。
- **Center of Excellence（CoE）**を置いた。ソリューションが成熟し、プレミアムコネクターや基幹業務アプリに触れる必要が出たら、統制された経路で支援を受け、本格的なエンタープライズアプリとして管理できる。

**シチズンデベロッパー向けの取り組み**：

- 米国商業部門で、**6,000 人**の社員が「AI とデータの基礎」トレーニングを受け、最終課題は Copilot でエージェントを作ること。全員が実践的なユースケースを経験した。
- 使われないエージェントの「墓場」ができうるが、問題ないという立場。オーナーが定期的に資産を**認証（attest）**し、古くなったものや持ち主不在のものはライフサイクル管理で廃棄するため、真のビジネスオーナーがいるものだけが残る。
- **シチズンデベロッパープログラム**：8〜10 週間のコースで、応募制、波（wave）ごとに実施。カリキュラム、専門家とのライブ演習、オープン Q&A、Viva Engage のコミュニティがある。過去 1 年で約 **500 人**が修了し、その約半数が成果物を作り、**本番稼働中のエージェントが約 250** ある。

**製品チームへの願い**：Power Platform が使用量ベースの課金に向かうなかで、メーカー自身にも、IT だけでなく、何を作り、そのコストはいくらで、使われ方はどうかという**消費とコストの可視性**が必要だと述べています。アプリやエージェントから得られる価値を測るためです。

### 5.3 グリーンゾーンの作り方（Zohar 氏）

Zohar 氏は、メーカーが作り始められる場所を「実験ゾーン（グリーンゾーン）」と呼び、次の要素で構成すると説明しました。

1. **環境ルーティング**：全員が着地する既定の環境にとどまらず、制約のある個人用の開発環境（書き起こしでは「OneDrive-like environment」と表現）で、自由にアプリ、エージェント、フローを作れるようにする。IT は、どれを本番に移すか介入するタイミングを決める。これまではオプトインで、有効にする製品を選ぶと、個人環境が自動で作られ（未作成の場合）、環境グループに入る。
2. **環境グループのルール**：個人環境が従うルールを、環境グループに設定する。
3. **高度なコネクターポリシー（advanced connector policies）**：今回の新発表で、DLP の置き換え。管理しやすく、メーカーごとに何が有効かを読み取りやすい。
4. **メーカー側の分かりやすさ**：IT が何を許可しているかをメーカーが分かるようにしている。
5. **案内（ハンドホールド）**：Microsoft IT が自社社員向けに作った **Ask Mica** というエージェントが例として示された（スライド上の名称を音声から書き起こしたもので、綴りは音声認識の都合で確定できません）。メーカーが例外申請をしたいとき、パネルに現れ、例外の取得方法や、新しいものを作れる環境の探し方を案内する。
6. **インベントリと使用状況**：アプリ、エージェント、フローのメタデータを見られるリッチなインベントリと、よく使われているものを示す新しい使用状況（usage）の画面。Nick 氏の話のとおり、使われていないものは、この API でクリーンアップできる。

### 5.4 Copilot Managed Runtime（Ryan 氏）

Copilot Managed Runtime（CMR）は新しい製品で、今週 GA になりました。Ignite の複数セッションで紹介され、前日（Clay 氏と Emma 氏が登壇）に、デモ付きの専用セッションがあったと案内されています。

**課題**：Zohar 氏のグリーンゾーンには 2 つの制約があります。1 つは Power Platform の中でしか効かないこと（外部ツールで作る、または外部ツールを統合すると、ポリシーが適用されない可能性がある）、もう 1 つはオプトインで、管理者が構成しないと使えないことです。

AI ツールの普及で、組織のデータと話し、業務プロセスと統合できるアプリを、誰でも簡単に作れるようになりました。しかし、組織で実際に使う段階になると、次のような部分は自動では付いてきません。

- 本番へのデプロイ、テスト用のデプロイパイプライン、本番データに安全に接続できるという保証
- 組織の法務・コンプライアンス要件を満たす、初期状態のセキュリティ
- 稼働の監視（意図どおりに動いているか、誰が何に使っているか、落ちないか）

**CMR の位置づけ**：Microsoft 内外のどのツールで作ったアプリでも、ホストして動かせるプラットフォームです。メーカーにとっては、出発点にかかわらず Microsoft のエコシステムとやり取りする統一された場所です。Power Platform と同様にコネクターやデータソースにつなげるほか、work IQ、インテリジェンス、エージェントをアプリに組み込めます。

**メーカーの入口**：

| 種類 | 例 |
| --- | --- |
| Microsoft 製品内 | Copilot Cowork、Copilot Code、（プロ開発者向けに）GitHub Copilot と VS Code |
| 外部のアプリビルダー | Lovable |
| その他のエージェント系ツール | Claude や OpenAI のツールなどで作った成果物も CMR にデプロイできる |

**管理者にとっての利点**：どのツールで作られたかにかかわらず、インベントリ、動作の追跡、接続先、監視を、1 つの統一されたコントロールプレーンで見られます。

**既定でオンのグリーンゾーン**：Power Platform ではオプトインだったグリーンゾーンを、CMR では逆にしています。Microsoft があらかじめ用意した一連のポリシーが最初から有効で、アプリは限られたコネクターとデータに制限され、それ以外とは通信できません。メーカーは「舗装された道」を使え、何も設定しなくても初日からガバナンスが効きます。

**車輪の再発明はしていない**：Zohar 氏が見せたマネージドプラットフォームの機能を CMR 向けに発展させたもので、管理の場所が Power Platform 管理センターではなく **Microsoft Admin Center** になります。インベントリ、コネクターやデータのポリシー、各種ガバナンス設定など、よく似た機能があります。

### 5.5 運用：マネージドホスト、ALM、モニター（Austin 氏）

Austin 氏は、メーカーが作ったソフトウェアが、管理者のコントロールの範囲内で信頼性高く動くことが重要だとして、3 つのプラットフォーム機能を挙げました。

**1. マネージドホスト**：アプリ、ワークフロー、エージェントが実際に動く場所です。Power Platform と同じだけ古い仕組みですが、Austin 氏によると、話題にし始めたのは約 2 年前からです。AI の時代より前は、Power Platform で「作って、ここで動かす」だけでした。いまはメーカーが好きな場所で作り、そのうえで「うちで動かす」ことを選べます。Microsoft の目標は、その選ぶ理由を提供することだとしています。ホストはワークロードごと（アプリ、エージェント、ワークフロー）に固有のものがあり、次のことを保証します。

- すべてのエンドユーザーが認証を経てアプリに入る。
- メーカーがアプリを共有したとき（Austin が Ryan と共有するなど）、認可の確認が行われる。
- ユーザーの操作が Purview ログに残る。これもホストがログを出すから。
- 管理センターで見える、初期状態のヘルスメトリクス。メーカーが意識しなくても、ホストから取得できる（任意のアドオンもある）。

**2. ALM（アプリケーションライフサイクル管理）**：メーカーの作業と本番のランタイムを切り離し、本番を動かし続けたまま改善を続けられるようにします。Power Platform では、ソリューション、パイプライン、Git によるバージョン管理を使います。メーカーは寛容な環境で作り、最小権限の環境にデプロイできます。Austin 氏はこれを、本番環境に「シュリンクラップ」を掛けるようなガバナンスと呼びました。CMR でも似た形で、寛容な場所で作り、より制限された場所にデプロイできます。ただしスライドの左側には、少し違う点が示されています。開発環境と本番環境が別に用意されていない組織のために、**ターゲット（target）**という概念を導入するというものです。Austin 氏によると、ALM は誰も意識していなくても必ず存在し、デプロイ先は常にあります。同じガバナンス境界内の場合もあれば、管理者と調整した、より厳しい境界のターゲットの場合もあります。

**3. モニター**：本番で、アプリ、エージェント、ワークフローが落ちたとき、気付けるかどうかです。Monitor は数年前から GA ですが、**今秋利用可能**になるものとして、**より高感度なアラート**が紹介されました。落ちたことを 1 時間以内に把握し、通知を Teams チャンネルや ServiceNow のチケットなど好きな宛先に流せます。データは UI に閉じず、**API ファースト**で、外へ取り出せます。

### 5.6 コスト管理（FinOps）

Zohar 氏によると、管理者が考えることが 2 つあります。

1. **USL（subscription licenses）**：長年扱ってきたもの。
2. **クレジット**：新しいもの。CMR アプリを作る人と、動かす人にクレジットを割り当てる必要がある。クレジットは Copilot や、Microsoft Copilot Studio で新しい Microsoft Copilot harness を使って作るときにも使われる。

誰にどれだけ割り当てるかを検討する必要があり、消費されたコストは見えるようになっています。Copilot Studio の左上にクレジットが表示され、Cowork では `/cost` と入力するとコストが表示されます。コスト管理は、USL と一部のクレジットだった Power Platform 管理センターから、**Microsoft Admin Center** に移り、そこにクレジットの管理も集約されます。さらに詳しい内容は、BRK262 で扱われたと案内されています。このセッションでは Graham 氏、Thomas 氏、Andrew 氏（Lumen の話をした、と聞き取れます）がクレジット管理のデモを行ったとのことです。

### 5.7 拡張性：Copilot Cowork と Power Platform admin plugin

Zohar 氏は、今回の Ignite で Power Platform 管理者にとって「おそらく最もエキサイティングな発表」だと前置きして、拡張性の話をしました。過去数年、Power Platform 管理センターの機能を API として公開し、SDK でも使えるようにしてきて、いまは **Cowork の中でも使えます**。新しい **Power Platform admin plugin** があり、アプリ、エージェント、フロー、インベントリ、ライセンスについて質問できます。デモは 6.4 を参照してください。

画面の最後には、Power Platform を使う組織の成熟度の段階が示されました。左は数人のメーカーが少数のものを作る初期段階、右は、Nick 氏のような、イネーブルメントチームがあり、個人環境で作り、コネクターを定義し、案内するエージェントと例外の仕組みを持ち、効率的な段階を祝う状態です。

## 6. デモ・手順

このセッションには 4 つのデモがあります。録音は音声のみなので、画面の細部は分かりません。以下は語られた範囲です。

### 6.1 グリーンゾーンの設定とメーカー画面（Zohar 氏）

1. Power Platform 管理センターで、環境の一覧を開く。環境ルーティングの設定は、**環境グループ**から行う。
2. 環境ルーティングの設定パネルで、有効にする製品を選ぶ（オプトインの体験。後で Ryan 氏が、既定でオンの新しい体験を見せると述べている）。個人の開発環境が自動作成される方向に移っており、オプトアウトもできるが、これを大規模な管理・統制の標準にしていく、という説明。
3. 環境グループは階層にできる。全員が入る既定の「すべて受け入れる」グループに加え、上に「pro」グループを作って、より多くの機能を与える。例として作った「pro maker group」に、Zohar 氏の個人環境が入っている。
4. グループにルールを設定する。ここでは**高度なコネクターポリシー**。このグループで高度なコネクターポリシーだけに従うか、従来の DLP にも従うかを選べる。チェックボックスを入れると、システムは DLP を無視して新しいポリシーだけに集中するので、移行に役立つ。
5. 高度なコネクターポリシーでは、グループのメーカーが使うことを許可するコネクターを一覧で指定する。SQL を例にとると、管理者が**アクションごとに許可を選べる**（例えば delete は許可し、update は許可しない）。さらに新機能として、**認証の種類**を制御できる（例えば OAuth 認証のときだけ SQL を許可し、他の認証方式はブロックする）。認証の種類が複数あるコネクターごとに設定できる。今後は、SQL Server 001 は許可し 005 は許可しない、といった粒度も可能にしていく、という話。
6. **ウェルカム（オンボーディング）メッセージ**を設定して、メーカーに案内を出す。
7. メーカー側の Copilot Studio に入ると、設定したオンボーディングメッセージが表示され、「読んで理解した」と確認する必要がある。メッセージを更新するたびに、再度の確認を求められる（そうしたい場合）。
8. 特定のエージェントを開き、ツール → コネクターを見ると、許可されたコネクターが表示され、許可されていないものは無効化されている。IT が許可しないものでメーカーが作ろうとすると、ブロックされる。
9. SQL Server は、制限付きで許可されていることが表示される。中に入ると、IT が有効にしたアクションだけが見える。
10. ステータスを開くと、対処が必要な項目が 3 つあるというトースト（通知）メッセージが出る。これは IT 組織のメッセージで、メーカーが自分で行き詰まりを解消できるよう、独自の文面を入れられる（例えば、カスタムコネクター用の特別な環境の取得方法へのリンク）。

### 6.2 Copilot Cowork でアプリを作り、Microsoft Admin Center で管理する（Ryan 氏）

**メーカー側（Copilot Cowork）**

1. Copilot Cowork で、長いプロンプトからアプリの作成を開始する。内容は、Ignite のセッションを追跡する「Ignite tracker」アプリの作成で、組織内でも似たアプリを実際に使っている。自分とチームに関係するセッションを見つけて、リンクなどの情報と一緒に個人向けの表示を出すもの。
2. Ignite のセッション一覧（Web サイト由来）などのデータも渡す。Cowork は仕事の文脈（自分が誰で、チームは誰か）を知っている。
3. 完了まで数分かかるので待たずに、事前に同じプロンプトで作っておいたセッションに切り替える。
4. 「Ignite session planner」アプリが表示される。1 つのプロンプトで作ったもので、必要なら反復できる。全セッションが表示され、同僚の特定、関連セッションの抽出、カレンダー表示ができる。**今行われているこのセッションも拾っており**、Ryan 氏自身もその機能は知らなかった、と述べている。
5. 組み込みコネクターの 1 つでプロフィール情報を取得し、同僚や関係者のアバター画像を表示している。

**管理者側（Microsoft Admin Center）**

1. 左のナビゲーションの **Apps** タブを開く。
2. **インベントリ**に、どのツールで作られたかを問わず、組織内のすべてのアプリが表示される。各アプリの詳細にドリルダウンできる。
3. コネクターを開くと、アプリがどのデータソースと話しているかが分かる。使用状況（誰が使い、誰に共有されているか）も見られ、アプリの 360 度の情報が得られる。
4. 読み取り専用ではない。挙動がおかしいアプリや不審なアプリは、**ブロック**、一時的な**無効化**、**削除**ができる。
5. **環境グループ**のビューに移り、**既定の環境グループ**を開くと、これが既定のグリーンゾーンである。許可されたコネクターは少数で、M365、Office、SharePoint のように、ユーザーが普段使うデータのもの。**1,500 のコネクターの全体ではなく**、最初から絞り込まれ、管理されている。
6. **共有の設定**：Office の「リンクのコピー」のような簡単なリンク共有を許可するか、広がりすぎる共有を防ぐため無効にするかを選べる。**ゲスト**がアプリにアクセスできるかも制御できる。
7. **コンテンツセキュリティポリシー**：コネクターの制御に加え、アプリのサンドボックスを制御する。アプリはサンドボックス内で動き、外部のデータソースと通信できない。既定ではロックダウンされており、他のエンドポイントとは通信できない。社内のエンドポイントや内部 API に接続させたい場合は、メーカーに限定的にその権限を与えられる。

### 6.3 マネージドホストがポリシーを実行時に強制する（Austin 氏）

1. Power Apps の外で作ったアプリを見せる。Power Apps の code apps、CLI、GitHub Copilot と SDK を使って作ったという。画面は左、中、右の 3 つの部分。
2. 左：大きなカードのボタンを連打すると、アプリがコネクター経由でリクエストを送る。これは**許可されたコネクター**なので、問題は起きない（PC がスリープしていたため、通常より少し遅い）。
3. 中：外部で作ったアプリなので、任意の API を呼べる。管理者には怖いことだが、Ryan 氏が示したコンテンツセキュリティポリシーの既定のポリシーで、狭いサンドボックスに収まっている。ボタンを連打すると、**右側にエラーが次々に表示される**。
4. エラーの理由は、アプリが**コンテンツセキュリティポリシーの範囲外のエンドポイント（Bing）**を呼ぼうとしているため。マネージドホストがポリシーを**実行時**に守らせている、という簡単な例として説明された。

### 6.4 Cowork と Power Platform admin plugin（Zohar 氏）

1. 管理者としてログインした Cowork で、新しい **Power Platform admin plugin** について、「このプラグインで何ができるか」を尋ねる。アプリ、エージェント、フロー、インベントリ、ライセンスについて何でも聞ける、という一覧が返る。
2. 「**週次ダイジェスト**」として「このテナントについて分かっていることをすべて教えて」と尋ねる。プロンプトに応じてグラフィカルな説明が返り、PowerPoint も作れる。コスト管理やリスク管理に関心のある経営層に共有できる。
3. **CoE Toolkit**の話。Zohar 氏は以前、導入が難しかったと言う。カスタマーアドバイザリーチームの Reza 氏が、このプラグインを使って Cowork と夜 9 時から 12 時までの 3 時間やり取りし（奥様に寝るよう言われるまで）、CoE Toolkit の上位互換にあたるものを作った。
4. Reza 氏に zip ファイルを共有してもらい、Zohar 氏のテナントの Cowork に入れたところ、**Copilot Managed Runtime のアプリ**ができた。Ryan 氏が示したのと同様に、プラグインと CLI を使っている。
5. `/cost` と入力して費用を確認する。zip ファイルを受け取ってから、反復して合計 **10 ドル**、30 分後に CoE Toolkit が完成した。
6. アプリの中身は豊富だが、時間がないため深くは見せていない。スライドの QR コードから、同じ zip ファイルを使って自分でも導入でき、費用は約 10 ドル、Cowork とプラグインに約 30 分与えれば作ってくれる、と説明された。

## 7. 注意点・発表者の気付き

- **グリーンゾーンの制約**：Power Platform のグリーンゾーンは Power Platform の中でしか効かず、管理者が構成しないと使えません（オプトイン）。外部ツールで作られたアプリにはポリシーが適用されない可能性があります。CMR は既定でオンです。
- **DLP からの移行**：環境グループで、DLP を無視して高度なコネクターポリシーだけに従わせるチェックボックスがあります。
- **使われないエージェントの放置**：Nick 氏は、墓場ができうるが、オーナーによる定期的な認証とライフサイクル管理で整理していると話しています。
- **管理者は数人で大規模環境を見る**：数万、数十万の環境・アプリ・フローを少人数で管理する現実があるため、環境ルーティングなどのツールが必要だと、冒頭のビデオで語られました。
- **外部で作ったアプリが任意の API を呼べる怖さ**：実行時にコンテンツセキュリティポリシーで抑えられる、というのが Austin 氏のデモの要点です。
- **クレジットの割り当て**：作る人と動かす人の両方に、誰にどれだけ与えるかを検討する必要があります。
- 高度なコネクターポリシーの粒度（SQL Server のインスタンス単位など）は「将来そうできるようにする」段階で、現時点の機能ではないと述べられています。
- 時間の制約で、スライドが順番どおりに出なかったり、一部のスライドや内容（ガバナンスとセキュリティのエージェント関連のスライドなど）が説明されず、QR コードで案内されたりしました。

## 9. まとめ

Power Platform と Copilot Managed Runtime の目標は、メーカーが自由に作り、IT が安心して眠れる状態を両立させることです。

1. **グリーンゾーンを作る**：環境ルーティング、環境グループ、高度なコネクターポリシー（アクションと認証方式まで制御）、オンボーディングメッセージ、Ask Mica のような案内役のエージェント。
2. **作る場所が外に広がっても管理する**：Copilot Managed Runtime（今週 GA）は、Microsoft 内外のツールで作ったアプリを 1 つのコントロールプレーンに集め、既定でオンのグリーンゾーンを提供する。管理は Microsoft Admin Center で行う。
3. **運用する**：マネージドホストによる認証・認可・ログ・コンテンツセキュリティポリシーの実行時の強制、ALM（ソリューション、パイプライン、Git、CMR のターゲット）、モニター（高感度アラートは今秋）。
4. **コストと自動化**：USL に加えてクレジットを管理し、Microsoft Admin Center に集約する。Cowork と Power Platform admin plugin で、管理作業を自動化する。

Novartis の事例は、既定の環境と DLP から始め、CoE と研修、ライフサイクル管理でスケールした、実際の道筋として示されました。
