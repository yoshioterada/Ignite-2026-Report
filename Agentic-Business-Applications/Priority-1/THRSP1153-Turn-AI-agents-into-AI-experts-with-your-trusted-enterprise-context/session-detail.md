# THRSP1153 Turn AI agents into AI experts with your trusted enterprise context

## 1. はじめに

このセッションは、AI エージェントに「信頼できるデータ」と、そのデータに意味を与える「エンタープライズのコンテキスト」を渡すにはどうすればよいかを扱う 25 分のシアターセッションです。Informatica（Salesforce 傘下）の技術アライアンスを担当する登壇者が、Informatica の各機能を MCP（Model Context Protocol）サービスとして公開し、Copilot や Foundry のエージェントから使う構成を説明しています。

発表では、画面を使ったデモが 2 回あります。1 回目はマーケティング分析担当者を演じ、「高額顧客」の一覧づくりから、データ資産の探索、データ品質、リネージ（データの出どころ）の確認、Power BI ダッシュボード作成の依頼までを Copilot で進める流れです。2 回目は、Copilot Studio で作ったエージェントに Informatica の MCP サーバーをつなぎ、ライブで動かすものです。

## 4. 発表者が伝えたいメッセージ

中心にあるのは、「データがあること」ではなく「エージェントがそのデータを理解できること」が課題だという考えです。Ajay 氏は、どの企業にもデータはあるが、エージェントが関連性の高い回答や行動を返すには、次の点が必要だと述べています。

- 使ってよいデータと、最も品質の高いデータが何かを、エージェントが理解できる
- 回答が悪いデータから来ていないことと、回答を信頼できることが確認できる
- データの出どころ、誰が使っているか、使ってはいけない人が使っていないか、アクセス管理のポリシーを governance 層で把握できる
- 正しい人に、正しい質問に対して、正しいデータを届けられる

そして、これを可能にするのが「コンテキスト層」だと主張しています。Informatica を使うと、作られるものは「もはやカタログではなく、エージェントのためのコンテキスト」だ、という言い方です。

## 5. 発表内容の詳細

### 5.1 Informatica と Microsoft の関係

Ajay 氏は、Informatica は Salesforce の一部で、Microsoft との戦略的で長期にわたるパートナーシップがあると説明しています。Salesforce 傘下で提供するのは **Informatica Data Management Cloud** で、SaaS として、データを Azure のデータサービスや Azure Databricks に移す・持ち込むだけでなく、governance 層も含みます。

governance 層は、オンプレミス、クラウド、SaaS にあるエンタープライズのデータ資産にカタログを作るためのものです。発表では、Purview を使っている人に向けて「Purview は retire される」という趣旨の発言があり、カタログへ移行する際の governance 層として Informatica を提示しています（この点は、発表では詳しく説明されていません）。また、Informatica は Azure 上でネイティブサービスとして見え、多くのお客様が Azure 上で使っていると述べられています。

### 5.2 なぜコンテキストが必要か

Ajay 氏は、例を 2 つ挙げています。

1. **「Chicago City の、golden tier または platinum tier の小売顧客」と聞いたとき。** Copilot や Foundry のエージェントなど、どのツールでも、「tier」「Chicago City」「Q2 の業績」が何を指すのかを理解する必要があります。
2. **「Q2」の意味。** 先週お客様と話した「面白い話」として、Q2 を 4〜6 月と考える人は多いが、組織によって違うと説明しています。Microsoft の Q2 は 10〜12 月にあたる、と述べています。EMEA や North America といった地域も、組織ごとの区切り方で変わります。

また、データは Azure 上の Snowflake、Azure Databricks、Fabric、ADLS、OneLake など多くのリポジトリに広がっているため、それらを横断して明確なコンテキストを出す必要があります。

### 5.3 Informatica の headless スタックと MCP

Informatica は、「headless stack」の層を提供するために投資してきたと説明されています。最下層は、エンタープライズ全体のデータソースやリポジトリを管理する部分です。その上で、Informatica のすべてのサービスを **MCP として公開**しています。MCP はコンテキスト層を提供し、OpenAI の ChatGPT、Copilot、Foundry エージェントなど、どの AI ツールともつながり、コンテキストを取得できると述べています。トランスクリプトにはこの列挙に「cloud」という語も出てきますが、音声認識の都合で何を指すのか確定できません。

アーキテクチャの図（スライド）は次のように説明されています。

- 中心は headless の Informatica ツール層で、すべてのツールが MCP サービス
- 左側に **system of engagement**（Teams、Copilot、Web アプリケーションと統合した Copilot など、データとやり取りする入口）
- MCP は現時点でほぼ 20 個。データガバナンス、データ品質、データ移動の質問などで、それぞれ性質が違う
- data marketplace のように、人が関与するプロセスも含む。例として、営業担当者がマーケティングのデータにアクセスしたい場合は、データオーナーの特別な承認が必要になる。データスチュワードシップも MCP にまとまっている
- データを MCP gateway を通じて、安全な仕組みで取得する

### 5.4 認証情報の保護：secure agent と単一の MCP レイヤー

Ajay 氏は、前日にお客様から聞いた課題を紹介しています。「データを取ること自体は、複数の MCP でできる。問題は、取得用の MCP が複数あること」「すべての認証情報を Copilot に渡したくない。脆弱な状況になる」というものです。多くのデータリポジトリが MCP を出しており、Copilot や Foundry エージェントに接続して 1 つのエージェントに 20 個の MCP を載せることもできる、という前置きがありました。

Informatica の答えとして、データ管理層にある **secure agent** と約 **380 のコネクタ** が示されています。組織で使うであろうデータソースをこれらのコネクタがカバーし、コネクタ全体が、Copilot 向けの **単一の MCP レイヤー** で包まれます。その結果、渡すのは単一の認証情報だけで、データの認証情報そのものは公開されず、公開されるのはラッパーだけです。Ajay 氏は、これを「単一の認証情報、単一の kill switch」と表現しています。

### 5.5 Microsoft との連携実績

- 事前構築のスキャナーがある
- Informatica は **Microsoft Fabric の design partner**。Fabric が作られているときから、データの Fabric への移動、Fabric 環境でのガバナンス、マスターデータ管理（「single click switch」と説明）を支援してきた。オントロジー、データ分析層、Power BI のチャートなど、すべてが Informatica のスキャナーで管理される
- Foundry チームとも連携している。mcp.microsoft.com や Foundry を見ると、よく使われる MCP サーバーの一覧の上位に Informatica が出る

### 5.6 Q&A

Ajay 氏が質問を受け付けると呼びかけ、司会者も会場に質問を促しましたが、トランスクリプトに質問と回答のやり取りは残っていません。終わりに、司会者が「Informatica が MCP サーバーを通じて提供するツールと API を使い、自分のワークフローを作って成果を出せる。非常に魅力的」という趣旨の感想を述べています。Ajay 氏は、ブース 1655 で完全なデモや追加質問に対応すると案内しています。

## 6. デモ・手順

デモは 2 回あります。いずれも録音は音声のみのため、画面の細部（ボタンやレイアウト）は確認できません。以下は語られた内容に沿った記述です。

> 補足：公式概要には Microsoft Foundry で作ったエージェントを使うとありますが、発表で実際に画面で示されたのは、Copilot と Copilot Studio で作ったエージェントです。

### 6.1 デモ 1：マーケティング分析担当者のシナリオ（Copilot）

Ajay 氏は「Copilot のデモを用意した」と述べて始めています。この部分がライブだったか、事前に用意した画面だったかは、発話からは判別できません（後半で改めて「ライブデモをお見せします」と述べています）。

設定は、Ajay 氏がマーケティング分析担当者で、上司から「高額顧客向けのキャンペーンを作ってほしい」と頼まれた、というものです。組織にはマスターデータ管理（MDM）層があります。

1. 「高額顧客の一覧を見せて」と質問する。顧客の一覧が返る。
2. 「Chicago City で実施したい」という条件が加わり、「Chicago City の高額顧客の一覧」を質問する。Informatica を使った MDM から、組織内の 1 人（顧客、サプライヤー、ベンダー）につき 1 つの「ゴールデンレコード」に基づく一覧が返る。
3. この情報で足りるかが分からないので、キャンペーンに使えるデータ資産を知るため、コンテキスト層に「エンタープライズ内のすべてのデータ資産を見せて」と質問する。データガバナンスのカタログが、ビジネス資産や複数のデータソースにデータがあると返す。クラウドデータウェアハウスは Snowflake だと分かる。
4. 上司はキャンペーンを Fabric の Power BI で作りたいが、データは Snowflake にある。そこで「Snowflake のすべてのデータセットを見せて」と依頼する。約 **138 のテーブル**が返り、そのサンプルも示される。
5. 顧客に関するテーブルを知るため、「顧客関連のテーブルはどれか」と尋ねる。Copilot は自動的に Informatica の **Cloud Data Governance MCP** を呼び、顧客に関連するテーブルの一覧を返す。「customer」や「table」が何を意味するかを理解した結果だと説明されている。
6. 大きなテーブルを全件見るとトークンを大量に消費する（Ajay 氏は、自分もトークンを使いすぎて、周囲に良く思われなかったと述べている）ため、上位 20 レコードなどのプレビューを依頼する。
7. 信頼できるデータかを確認するため、「customer sales のデータセットの詳細を見せて」と依頼する。品質スコアカード（quality scorecard）が必要で、Informatica の **data quality MCP** を使って、このテーブルの品質情報を取得する。
8. データの出どころを知るため、リネージを確認する。システム・オブ・レコード由来か、誰かが作ったダミーのテーブルかを見分けたい、という意図。リネージは、データが customer data set から渡され、品質面の処理や変換が加えられてきた経緯を示す。
9. 高品質で、信頼でき、安全なデータだと確認したうえで、「Snowflake のデータを Fabric に移し、Power BI のダッシュボードを生成して」と依頼する。

ここまでの質問の流れの中で、Copilot は **action plan（計画された進め方）** を示します。どうデータを取得し、どうコンテキストを取得するかの計画です。MCP から MCP へ引き継ぐときも、コンテキストは内部で渡されるため、質問が変わってもエンタープライズのコンテキストが蓄積されていく、と説明されています。

> 注意：9 の Power BI ダッシュボードが実際に生成された結果は、発表では語られていません。

### 6.2 デモ 2：Copilot Studio のエージェント（ライブ）

発話では「ライブデモをお見せします」「ライブデモでは遅延などが課題になる」と話しており、ライブで進めています。

1. Microsoft Copilot の画面を開き、先ほどと同じ例を見せると述べて、「Titanium の顧客の一覧を見せて」と依頼する（言い直しが入っています。「Titanium」は聞こえた綴りのままで、音声認識の都合で確定できません。結果についての説明はありません）。
2. Copilot Studio で作ったエージェントを見せる。説明の趣旨は、先ほど話した各 MCP サーバーをどうエージェントにつなぐか、というもの。
3. 追加できる MCP の一覧を示す。複数のツールの MCP を追加済みで、Informatica の cloud data catalog などのコンポーネントが一覧に表示されている。
4. 各 MCP サーバーのツールの一覧を見る。MCP サーバーはツールで構成されている。例として **job management MCP**（データ移動を依頼したとき、どのツールが使われたかが分かる）と、**マスターデータ管理のツール**（データセットをエージェントに取り込むよう依頼できるレコード）が挙げられた。カタログには、先に話したコンテキストを扱うツールがある。
5. コンテキスト用のツールでは、コンテキストがどこから来るかや、ドメインのデータを確認できる。製造、小売、コンプライアンスが必要な規制業種などでは、「この目的のために、このデータをマスクして見せて」といった依頼も、アクセス制御の範囲で可能だと説明されている。
6. エージェントに「すべてのデータ資産を一覧して」とオープンエンドで頼む。エンタープライズのカタログが返る。すべてのシステムにはアクセスせず、セマンティック層（メタデータ）のコンテキストを作り、データが何で、どこから来て、どんなソースがあるかをテンプレート化して示す。
7. 裏でさまざまな情報が要求されている間、待ち時間（遅延）が発生する。結果として、データが Informatica のシステムから複数の場所から来ていることが分かる。Snowflake にデータがあり、複数のクラウドデータウェアハウスにデータがある。ハイブリッドクラウドをまたぐ場合もある。

## 7. 注意点・発表者の気付き

- **コンテキストは組織ごとに違う。** Q2 の定義や地域の区分のように、同じ言葉が組織で別の意味になるため、エージェントにはその会社の定義を知らせる必要がある、という点を例を使って伝えています。
- **大きなテーブルをそのまま取らない。** 全件を見るとトークンを大量に使うため、プレビュー（上位 20 レコードなど）を依頼するやり方がデモに出ています。
- **MCP を増やすと認証情報の管理が課題になる。** お客様から出た課題で、1 つのエージェントに多数の MCP をつなぐと、認証情報をまとめて渡すことになり脆弱になる、という懸念です。
- **ライブデモは遅延が出る。** 発表者自身が、ライブデモは遅延が課題だと述べています。
- 発表の中で、Purview について「retire される」という発言がありました。この点について、移行時期などの詳細は語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **エージェントが何を使えるかを判断できる**：データのカタログ、品質スコア、リネージ、アクセス管理をコンテキストとして渡せるため、回答の信頼性を確認できる。
- **トークンの節約**：プレビューにより、必要以上にデータを読み込まない使い方ができる。
- **認証情報の保護**：約 380 のコネクタを単一の MCP レイヤーで包み、単一の認証情報と単一の kill switch で管理できる。
- **人の承認を組み込める**：data marketplace では、別部門のデータに対し、データオーナーの承認を求められる。
- **Microsoft 製品との統合**：Azure 上のネイティブサービスとして使え、Fabric の design partner としてのスキャナーがあり、Foundry や mcp.microsoft.com でも MCP サーバーが見つかる。

## 9. まとめ

発表の主張は、エージェントを「AI エキスパート」にするには、データに加えて、意味・品質・出どころ・アクセス権を含むコンテキストが必要だという点です。Informatica は、そのコンテキストを約 20 の MCP として公開し、Copilot、Foundry エージェント、Copilot Studio のエージェントなどから使えるようにしています。

デモでは、顧客一覧の質問から、データ資産の探索、データ品質の確認、リネージの確認を経て、Fabric と Power BI への移行を依頼するまでの流れが示されました。2 回目のライブデモでは、Copilot Studio のエージェントに MCP サーバーとそのツールをつないだ構成が紹介されています。詳しいデモはブース 1655 で見られると案内されています。
