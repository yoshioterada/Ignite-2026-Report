# BRK234 Agentify your business processes-the next era of business applications

## 1. はじめに

このセッションは、Microsoft の Apps and Agents 部門と AI Business Process のチームが、「業務アプリケーションをエージェント前提で作り変える」という方針と、その具体的な製品・デモを紹介した 45 分のブレークアウトです。Dynamics 365 や Copilot、Copilot Studio を使っている（または検討している）開発者・IT 技術者が、Microsoft の現在の構成と、実際に何ができるのかを把握するのに向いています。

構成は大きく 3 部に分かれています。

1. **Copilot をユーザー体験の入口にする**（Dynamics 365 を Copilot の中から使うデモ、Visa との対談）
2. **カスタムエージェント／ワークフロー／アプリを作る**（Copilot Studio と Copilot Managed Runtime のデモ）
3. **顧客との関係を変える**（Microsoft Contact Center Intelligence のデモ）

登壇者は冒頭で「このセッションで話す内容のほぼ全ては、今日時点で利用できるものだ」と述べています。3 つのデモが画面を使って実演されています。

## 3. 何に関する発表か

Jeff Teper は、業務アプリケーションのスタックを **UX 層・データ層・ガバナンス層** の 3 つで捉え、AI 時代の Microsoft の答えを次のように整理しています。

| 層 | Microsoft の呼び方 | 発表での説明 |
|---|---|---|
| ユーザー体験 | Copilot（加えてカスタムのアプリとエージェント） | 業務アプリを横断する入口 |
| データ | Microsoft IQ（IQ layer） | AI 向けに作られた、知識と業務プロセスのためのプラットフォーム。セキュリティと整合性が強制される |
| ガバナンス | Agent 365 | AI をどのプラットフォームで作った場合でも、その周りを囲む管理層 |

Jeff は、数か月前に Dynamics 365 が Microsoft 365 と並んで Microsoft IQ の「first-class」な構成要素になったと説明しています。スライドには出ていないものの、Fabric も同じ位置づけです。これにより、Exchange、SharePoint、Teams などの共同作業、CRM と ERP の業務プロセス、Fabric の分析を、1 つのスタックでまとめて提供できるのは Microsoft だけだ、というのが Jeff の主張です。独自の MCP、スキル、プラグインと組み合わせることもできます。Dynamics のエージェント向け API とデータ拡充（data enrichment）は、AI で質の高い成果を最低のコストで出すための基盤という位置づけです。

会社としては「Copilot、IQ、Agent 365」の 3 層を、製品戦略の持続的な枠組みとして維持すると述べています。

## 4. 発表者が伝えたいメッセージ

発表全体の主張は、「業務アプリの使い方が、アプリの画面を開くことから、エージェント経由で仕事を進めることへ移る」という点です。

Jeff は、営業担当者は CRM の画面の前に座る時間より顧客と過ごす時間を増やしたいはずだ、という見方を示しました。そのため、会議のまとめや顧客との会話、Web で調べた背景情報を、エージェントが記録システム（system of record）に反映する形が望ましいと説明しています。これを **「headless」な使い方** と呼び、Microsoft だけでなく SAP、Salesforce、Oracle、Workday、ServiceNow など業界全体の方向だと述べています。そのうえで「今は、誰が AI にとって最良のプラットフォームを持つかの競争だ」という位置づけです。

Microsoft が Dynamics で重視する点として、Jeff は次を挙げています。

- **コストあたりの成果**：売上成長、パイプライン転換、インシデント抑止（incident deflection）、在庫回転などを、AI と従来型の決定論的コードの適切な組み合わせで、信頼性と性能を保ちながら実現する
- **非構造化データと構造化された業務プロセスの接続**：営業サイクルでは Outlook、SharePoint、OneDrive にある情報を合成して顧客の 360 度ビューを作る
- **headless 化**：標準の UI を使うことも、Cowork、Autopilot、Copilot の新しい Today タブから使うこともできる。Teams や Copilot の UI は Dynamics チームと共同で設計（co-engineering）している
- **Fabric との高速なデータ同期**：トランザクション系と分析系をつなぐ。ダッシュボードを自分用に作りたい場合は生成でき、後述の Copilot Managed Runtime 上で動く

## 5. 発表内容の詳細

### 5.1 2026 年のここまでと、導入の壁（Activate）

Jeff は今年の流れを次のように振り返っています。昨年末に新世代のモデルが登場し、年明けから前半はコーディングが中心だった。自社の開発チームでは生産性が「20% 向上」から「2 倍」、さらに「5 倍」（品質を伴うコード出力）へと進んだ。年の半ば頃から、そのコーディング用のモデルとハーネス（モデルを包む実行の仕組み）を業務アプリに適用し始め、Dynamics 365 を含む営業・サービス・財務・オペレーションの領域で、売上成長、顧客満足、コスト削減の面で投資対効果が出る本番事例が出てきている、という説明です。Jeff は、モデルとハーネスの進化によって、業務アプリが AI の効果を実感できる「hockey stick」の時期に入ったと表現し、2027 年は大きな年になると述べています。

一方で、多くの企業はレガシーシステムから移れずにいます。そこで Jeff は **Dynamics 365 Activate** を紹介しました。AI を使って、業務プロセスと関係者を棚卸しし、既存システムを調べるものです。

- 今年の 9 月（Jeff の記憶では）に Salesforce 向けの Activate を発表済み
- 今回、**SAP（ERP）向けの private preview** を発表し、Dynamics 365 への移行を計画できるようにする
- 複雑な SAP や Salesforce の移行に関するドメイン知識を体系化し、「わずかなコスト」「わずかな時間」で移行できるとしている
- パートナーとして congruentX と HSO が多くのエンタープライズ顧客向けに取り組んでいる

なお Bryan Goode は最後に、Activate は Salesforce からの移行が現在 GA で、SAP ECC の移行向けに新機能が加わったと述べ、Activate のセッションへの参加を勧めています。

### 5.2 Copilot で業務を回す（Karan Nigam のデモと Jeff の補足）

Jeff の説明では、Dynamics 365 は顧客、注文、商談、インシデント、アカウント、収益、サプライチェーン、在庫などを持つ AI 向けの業務レイヤーで、この数年、API とデータを「agentify」（エージェントが効率よく扱える形に）する作業を進めてきました。従来の Dynamics Customer Service のような画面もなくなりません。むしろ AI で速く、AI 統合された形に改善していくとしています。

Jeff 自身も、前日に飛行機の中から Teams と携帯電話で、CRM プラグインを入れた Autopilot に「今週会う顧客は誰か。メール、チャット、ドキュメント、CRM のデータを基に更新情報をまとめて」と依頼した、と紹介しています。

Karan Nigam は、「Copilot は仕事の OS」というキーノートのメッセージを受けて、仕事には生産性だけでなくビジネスのコンテキスト、ロジック、プロセスが含まれるため、業務プロセスが Copilot の一部になる必要がある、と話しました。このデモの詳細は「6. デモ・手順」に書きます。

### 5.3 Visa との対談（Jeff Teper と Manish Mittal）

Visa は、銀行、フィンテック、加盟店、パートナーという多様なエコシステムの中で、決済、不正対策、リスク、コアバンキングなど数百の製品・機能を持っています。Manish Mittal は、課題はデータ不足ではなく、データが多くのシステムに分散していることだと説明しました。営業担当者は顧客との会話の前に、過去のやりとり、関係の履歴、使っている Visa 製品、関連しそうな提案を、CRM を含む複数のシステムをまたいで確認する必要があり、それでも「点をつなげられずに」機会を逃すことがある、という状況です。

そこで、Visa の集合知を **Visa IQ**（Microsoft の構成に合わせた呼び方）としてすべての顧客との会話に持ち込み、営業担当者が顧客と過ごす時間を増やして、より適切な会話をできるようにすることを目指しました。

取り組みは次の順で説明されています。

1. まず Copilot と Dynamics のネイティブ機能（アカウントの情報、購買情報、会議の準備、顧客とのやりとり）から始めた。
2. 次に、購買データ、製品ポートフォリオ、顧客理解などを注入した **独自の customer 360** を構築した。
3. その Visa IQ（Visa のコンテキスト）を、Microsoft のチームと協力して **Sales Agent** に取り込んだ。

具体的なシナリオとして、顧客から「承認率（authorization rate）が下がっている」「不正が増えている」「拒否（decline）が増えた」と言われた場合が挙がりました。従来は担当者が複数のチームに確認して後日フォローしていましたが、Sales Agent を使うと、顧客のコンテキストを少し与えるだけで、営業の流れの中でそのまま、状況に合わせた回答が得られます。会議準備や、製品・顧客ポートフォリオの理解にも使われています。

今後の方向として、Manish は次を挙げています。

- 営業担当者は単一の Copilot という「front door」を気に入っている。一方で、これまで Dynamics に移動して行っていた更新を、Sales Agent の側から行えるようにしたい（Microsoft のチームと取り組み中）
- Satya がキーノートで話した **Copilot-enabled workspaces** を使い、共同で提案を作ったり、競合状況を調べたりする協働営業に役立てている
- AI の進化を「理解する AI」から「提案する AI」、さらに「行動する AI」へと捉えている。顧客が製品を明示的に求めていなくても、ビジネス上の課題を話したときに、サポートデータなどから適した提案をエージェントが裏で見つけて営業担当者に示す、といった形
- 優れた営業担当者の過去の成功事例から集合知を取り出し、他の担当者の力を底上げする。個人の生産性ではなく、営業全体の生産性を考える

学びとして、Manish は「孤立した別の AI 体験を作らず、営業担当者がいる場所で出会うこと」を挙げています。また、Microsoft 側の人が Visa のチームと並んで摩擦を解消しながら共同設計していることが重要だと述べました。

### 5.4 Copilot Studio と Copilot Managed Runtime

Jeff は、コーディングエージェントとハーネスの変化の波を、この夏に新しい Copilot Studio へ取り込んだと説明しています。

- 複数のモデルを使い、その上で動く **Copilot harness** という agentic harness を採用
- **カスタムエージェント、ワークフロー、アプリ** を 1 か所で作れる新しい UX。ダッシュボード用の UI が必要な場合、低コストで決定論的なワークフローがほしい場合、AI とワークフローを混ぜたエージェントがほしい場合のいずれにも対応する
- 構築（build）、デプロイ、評価（evaluate）、最適化（optimize）を一貫して行える
- 提供開始から 3〜4 か月。以前のリリースに対し、最新のハーネスとモデルによって、品質とコストの面で「10、20、30、40 ポイント」規模の改善があったと説明されています。モデル層と UI 層の両面で最新の AI 技術に作り直した、という位置づけです
- GPU 上で動く LLM のコードと、CPU 上で動くワークフローのコードを組み合わせられる。8 月のリリース以降も改善が続いており、前バージョンの Copilot Studio と比べてトークン使用量は約半分
- **エージェントのアイデンティティ**（agent ID）のサポートを preview に入れた。Teams や Outlook でやりとりできるカスタムエージェントに ID を持たせることで、使いやすさと管理しやすさが上がる。エージェントが文書やアプリにアクセスする際はすべてこの ID を介するため、アクセス制御、ラベル、監査、DLP など、人に対して使っている統制を適用できる。コントロールプレーンは Agent 365 になる

さらに、この日の午前中に **Copilot Managed Runtime** の最初の段階が GA になりました。Power Platform や SharePoint でのアプリ開発では、誰がアクセスするか、どのデータを持つかを統制するガバナンス層があるから安心して使われている、という学びを Copilot に取り込んだものです。

- AI モデルを使って、フォーム、ダッシュボードなどのアプリを生成できる
- この「app skill」は Cowork、code、GitHub、Copilot Studio に入っており、Lovable のような場所にも載る。ほかの AI ツールにも公開される予定
- 生成したアプリは、未知のオープンソース依存関係を持つ任意の仮想マシンではなく、**制御・監視できるマネージドなスタック** 上で動く
- 誰がアクセスし、誰が共有でき、どのシステムと通信するかを決められる。例として、Dataverse と SharePoint との通信は許可し、それ以外は監督下に置きたい、という使い方が挙げられました

### 5.5 Microsoft Contact Center Intelligence

Jeff は冒頭で、この 3 つ目のテーマを、顧客から最もよく聞かれる話題として紹介していました。内容は、顧客との関係をどう良くするか、顧客をどう維持し満足度を上げるか、コスト効率のよい 360 度の関係でどう売上を伸ばすか、です。

Bryan Goode は、会場の 10 人に 9 人が、顧客エンゲージメントに AI を適用することに関心を持っていると述べました。Dynamics 365 Contact Center はすでに数千の顧客に使われています。ただ、多くの顧客から「rip and replace（既存システムの入れ替え）はできない、方法も時間もない」という声があるため、既存のコンタクトセンターを置き換えずに上へエージェントを重ねる新ソリューション **Microsoft Contact Center Intelligence（CCI）** を紹介しました。

Heidi Elmore は、顧客は速くパーソナライズされた対応を求めているが、AI の進化は速く、コンタクトセンターの近代化には時間がかかる、という課題を挙げています。CCI は、その差を埋めるためのものです。

- **universal connector**：多くの既存ソリューションにそのまま接続できる。既存のコンタクトセンターのキーを数個貼り付けるだけで、ルーティングや電話基盤の変更は不要。既存の DID も維持できる
- パートナーシップ：Avaya、Cisco、Five9 との提携を発表
- 自然言語で作りたいエージェントを記述すると、必要に応じて複数のエージェント（サブエージェントを含む）が生成される。各専門サブエージェントは 1 つの領域を深く理解しており、顧客はより速く高性能な回答を得られる
- 各エージェントは、それぞれ独自のモデル、ナレッジ、ツールを持つ
- Microsoft IQ を参照すれば、メール、Teams、SharePoint などのバックオフィスにある決定事項やポリシーを使える
- スキルには、「どのようなご用件ですか」といったオープンエンドの質問に対応する **生成系のスキル** と、送金のように精度とコンプライアンスが重要な場面で使う **決定論的な手順のスキル** の両方がある
- 既存のエンタープライズエージェントを再利用できる（「一度作って何度も使う」）
- 通話後の要約を人間のエージェントへ引き継ぐ、品質保証（QA）エージェントが通話を評価する、といった機能がある（詳細は次章）

Heidi は最後に、CCI は「本日 generally available」であり、詳細は翌日 1:00 の Breakout Session #3 で確認できると案内しています。

## 6. デモ・手順

このセッションでは、3 つのデモが画面上で実演されています（デモ 2 では、アプリとエージェントの生成は途中で、事前に生成したものに切り替えています）。録音は音声のみのため、画面上のボタン名や細部は、発話で語られた範囲に限って書きます。

### 6.1 デモ 1：Copilot の中で営業プロセスを進める（Karan Nigam）

営業担当者が、Copilot を離れずに更新が近い案件を処理する流れです。

1. Copilot の画面を開く。チャットなどが見える、おなじみの画面。
2. 新しい **Today ページ** を表示する。パイプラインの状況（pipeline health）が見え、重要な更新（renewal）の案件が出ている。
3. その案件の **「Start Task」** を押す。Copilot は Work IQ（メール、会議、チャット、ドキュメント）と業務プロセスのコンテキストを基に回答を返す。
4. 回答は、更新を通すために必要な 3 つのアクションを示す。
   - 未解決のサポートケースが 2 件あり、その詳細と推奨アクションが示される。
   - アカウントとは接点があるが、CFO にはまだ連絡していない。最終的に支払いを決める人物である、という指摘。
   - 購買（procurement）側の作業を始める時期である。
5. 画面右端には、この結果を支えているプラグイン（Dynamics 365 sales、service、Work IQ など）が表示されている。
6. Customer Success Manager を割り当てるという提案を受け入れ、残りのアクションも進める。Copilot が次のステップを用意する。
7. 用意されたのは、レビュー・編集して送れる **Teams メッセージ** と、CFO との会話を始めるために顧客へ送る **メール**。確認して、Copilot から両方を送信する。
8. 画面の左下にある、**CRM システムへの更新の書き戻し** を示す。作業中のコンテキストや更新を CRM に自動で反映できる。営業担当者が「何でも CRM に入力しに行くのは嫌だ」と感じる点への対応、と説明されています。
9. **Autopilot** を開き、「毎週月曜 8 時に、重要アカウントの最新情報と競合情報を送る」ルーティンを作成する。現在は営業担当者が毎週 4〜5 時間かけている作業だと説明されている。作成後も更新でき、すべてのルーティンは確認できる（observability、transparency）。
10. 別の Copilot 画面に切り替え、右下にある **Dynamics 365 ERP プラグイン** を示す。ここまでは CRM のシナリオであり、CRM とバックオフィスの ERP を Copilot の中でまとめて扱える、という説明。

### 6.2 デモ 2：Copilot Studio でアプリ、エージェント、ワークフローを作る（Jessica Lo）

シナリオは、Jessica が自社として語る **Caldova** がサプライチェーン不足に対応するため、主力製品の別バージョンを作る、という設定です。チームは SharePoint List で地域、ワークストリーム、ローンチを阻む要因を管理しており、毎日のスタンドアップで手作業で更新して確認しています。これを自動化します。

**アプリの作成**

1. 自然言語のプロンプトを入力する。Copilot Cowork、Copilot Code、Copilot Studio のどこからでも始められる、と説明されている。生成されたアプリは Copilot Managed Runtime でホストされ、組織のポリシーに自動で準拠する。
2. プロンプトの内容は、「ローンチプログラムを管理するコントロールセンターのアプリを作る。先ほどの SharePoint List を使い、重要な阻害要因やチームが知るべきことを目立たせる」というもの。
3. 時間の都合で、**同じプロンプトで事前に生成したアプリ** に切り替える。
4. 画面は、左がチャット（元のプロンプトとエージェントとのやりとり）、右がクリックして操作できるアプリのプレビュー。ローンチゲートの判断一覧が表示され、SharePoint に接続されている。編集を続けることも、公開してエンドユーザーに共有することもできる。
5. 「Play」で実行する。KPI、地域ごとの準備状況（readiness by region）、介入が必要な地域が表示され、現在は **ブラジルがリスク状態** になっている。

**エージェントとワークフローの作成**

1. Copilot Studio のホーム画面のテキストボックスに、プロンプトを入力する。SharePoint を使ってローンチの準備状況を評価するエージェントを作ること、準備状況のポリシー文書を追加して、ポリシー、阻害要因、次のステップの質問に答えられるようにすること、阻害要因があるときにエスカレーションを作成するワークフローを作ること、Teams に通知を送ることを依頼している。
2. 送信すると、「regulated launch gate escalation workflow」と「program coordinator agent」が提案される。「Start Building」を押す。
3. 作成に数分かかるため、**事前に生成されたエージェント** に切り替える。
4. エージェントには SharePoint のデータから取り込まれた指示（instructions）があり、右側に付与されたツールが並ぶ。最初のツールが、エスカレーション用のワークフロー（regulated launch gate escalation workflow）。プロンプトで指定した SharePoint のリストもツールとして含まれる。
5. エージェントは Work IQ のビジネスコンテキストも持つ。コストと効率のバランスを見て、用途に適したモデルを選べる（管理者が気にする点として紹介）。
6. 「Publish」して、テストする。質問は「どの地域がローンチ日に間に合わない可能性が最も高いか、その根拠は何か。承認が必要なら、承認の動作を確認したいので承認をトリガーして」。
7. エージェントは複数のデータソースを並行して参照する。このエージェントは A365 のポリシーに基づく既定の統制の下にある。
8. 回答では、アプリで見たとおりブラジルが「very red」で、ほかにサプライチェーンが止まっているなどの重大な阻害要因があると示される。
9. ワークフローを確認する。エスカレーションが必要なときだけエージェントが呼び出すワークフローで、承認の依頼は同僚に送られる。承認されると、SharePoint のリストとアプリのステータスが自動で更新され、Teams 通知も届く。
10. Teams に切り替えると、承認リクエストの詳細が入った **承認カード** が届いている。「Approve」を押すと、ワークフローが再開し、SharePoint のリストとアプリのステータスが更新される。

Jessica は結びとして、エージェントが推論とエスカレーションの要否の判断を、ワークフローがルーティングとエスカレーションを、アプリが情報の集約と更新の追跡を担当した、と整理しています。

> 注意：ワークフローの分岐（エスカレーションが不要な場合の動き）は、発話が不明瞭で、上記のとおり承認の依頼が同僚に送られる、という範囲しか確認できませんでした。

### 6.3 デモ 3：既存コンタクトセンターに AI エージェントを載せる（Heidi Elmore）

1. 既存のコンタクトセンターに **universal connector** で接続する。キーを貼り付けるだけで、ルーティングも電話基盤も変更しない。DID も維持する。
2. 作りたいエージェントを自然言語で記述する。事業部やユースケースをまたぐセルフサービスのエージェントで、クレジットカードに関する具体的な指示を追加している。
3. CCI が、サブエージェントを含む複数のエージェントを生成する。クレジットカードサービスのエージェントを選ぶ。
4. このエージェントに製品ガイドを与える例として、パンフレットを選択する。目的別に作ったエージェントに、固有のナレッジを持たせる方法の例。
5. バックオフィス（メール、Teams、SharePoint）の判断やポリシーが必要な場合は、Microsoft IQ を参照させることもできると説明。
6. **スキルを編集** する。例として「新しいクレジットカードを申し込む」スキルを開く。
7. このスキルは、決められた順序で特定の質問をし、申込みに必要な情報を集める **決定論的なフロー** になっている。
8. さらに統制を強めたい場合の例として、**生体認証（biometric authentication）** を有効にする。通話者は、声紋（voice print）で登録して認証できる。
9. 既存のエンタープライズエージェントも再利用できる。例として、チームが **Microsoft Foundry** で作った transaction analysis agent を紹介。
10. 公開先として既存のコンタクトセンターを選んで公開する。エージェントは、すでに運用中の番号の上で稼働を始める。
11. 銀行のエージェントに実際に電話をかける。
    - Contoso Bank の仮想アシスタントが応答する。ミュンヘンへの出張を理由に、旅行向けの特典が良いカードを尋ねる。
    - 年会費が許容できるか聞かれ、マイルが欲しいと答えると、「Contoso Premium Advance Card」が提案される（航空マイルが貯まる、旅行割引がある、年会費が低い）。
    - ドイツ語に切り替えると、エージェントもドイツ語で応答した。英語に戻し、申込みを依頼すると、申込みを開始してフォームをメールで送ると返答する。
    - 利用限度額について人と話したいと伝えると、アカウントのスペシャリストに引き継ぐ旨を案内する。
12. 人間のエージェントの画面（サードパーティの agent desktop。一部は Avaya と説明）に、AI との会話の **要約** が表示されている。変更管理の観点でも大きい、と説明している。
13. 通話中に、**QA エージェント** が品質計画（quality plan）に照らして通話を採点した。同じ計画で人間のエージェントの対応も評価できる。挨拶、適切なブランド用語を使ったかなどの観点で結果を見られ、設定は変更できる。
14. IT 管理者の視点では、この customer assist agent は **Agent 365** で、社内の他のエージェントと同様に見える。

## 7. 注意点・発表者の気付き

- **既存環境への組み込みでの課題（Visa）**：Manish は最大の課題として、クラウド上の Copilot と、オンプレミスにある自社情報を接続することと、その認証を挙げ、チームがかなりの時間を費やしたと話しています。他の企業でも同様の課題に遭遇するだろう、という見立てです。
- **孤立した AI 体験を作らない**：営業担当者がいる場所で AI を使えるようにし、多数のツールに誘導しないことが有益だったという学びです。
- **Visa の現状**：展開を始めたところで、学習を進めている段階です。営業担当者は単一の Copilot の入口を気に入っている一方で、Sales Agent から更新できるようにすることは、今後の作業項目です。
- **提供状況の違い**：Jeff は大半が今日使えると述べていますが、Activate の SAP 対応は **private preview**、エージェントの ID サポートは **preview**、Copilot Managed Runtime は「最初の段階が GA」です。CCI は GA と案内されました。
- **デモの前提**：Copilot Studio のデモでは、アプリとエージェントの生成に時間がかかるため、事前に生成した成果物に切り替えて説明しています。

## 9. まとめ

このセッションの要点は次の 4 つです。

1. Microsoft は、Copilot、Microsoft IQ、Agent 365 の 3 層を、業務アプリケーション戦略の軸としている。Dynamics 365 は Microsoft IQ の一部になった。
2. 営業などの業務は、アプリの画面ではなく Copilot やエージェント経由（headless）で進む方向にある。Karan のデモでは、案件の確認、メールと Teams の送信、CRM への書き戻し、Autopilot のルーティン作成までを Copilot 内で行った。
3. Copilot Studio ではエージェント、ワークフロー、アプリを一か所で作れる。アプリは GA となった Copilot Managed Runtime で動かし、アクセスや接続先を統制できる。
4. Microsoft Contact Center Intelligence は、既存のコンタクトセンターを置き換えずに AI エージェントを重ねる仕組みで、本日 GA。Agent 365 で他のエージェントと同じく管理できる。
