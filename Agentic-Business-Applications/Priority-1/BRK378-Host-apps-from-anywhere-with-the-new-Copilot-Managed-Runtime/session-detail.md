# BRK378 Host apps from anywhere with the new Copilot Managed Runtime

## 1. はじめに

このセッションは、**Copilot Managed Runtime** の紹介です。Cowork、Copilot Studio、CLI、Lovable といった入口の違うツールで作ったアプリを、同じ場所でホストし、同じガードレールで管理する仕組みを扱います。

登壇者は、アプリの作り方そのものよりも、「作ったアプリがどこで動き、どう守られ、管理者にどう見えるか」に重点を置いています。デモは多めで、Cowork での作成、Copilot Studio での作成、Lovable からの公開、CLI と VS Code での修正、Microsoft Admin Center での管理が順に紹介されます。発表によると、紹介された機能の多くは前日に一般提供（GA）になっており、今すぐ試せる状態です。

このセッションを読むと、次のことが分かります。

- Copilot Managed Runtime が何を担う基盤なのか
- どの入口から作ったアプリも、同じ場所に載って同じガバナンスを受けること
- 管理者が Microsoft Admin Center で何を設定・確認できるのか

## 4. 発表者が伝えたいメッセージ

最大のメッセージは、**どこで作っても、行き着く先と管理は同じ**という点です。

Clay 氏は、自分が 2 週末前に Copilot Managed Runtime 上で作った約 100 個のアプリの画面を見せています。これらは Cowork、Copilot Studio、CLI など作り方がバラバラで、OpenAI 系や Opus など複数のモデルも混在しています。それでも共通点があり、どれもローカルホストの URL を持たず、Entra による認証がかかり、Git で管理されるリポジトリを持ち、管理者が Admin Center から見える状態になっている、という説明でした。

もう 1 つの主張は、アプリが「静的なデータ接続アプリ」で終わらないという点です。アプリがエージェントに支えられ、エージェント、ワークフロー、アプリが 1 つのソリューションとして組み合わさる方向に進んでいる、と説明しています。

さらに、作る人の出発点が違っても詰まらないことも強調されています。業務の流れの中で作る人（Cowork や Copilot Studio）と、最初からコードで作る人（コード・GitHub・Lovable・CLI）が、同じスキルとガバナンスを使えます。ビジネス側の人が作ったものを、後からプロの開発者が CLI で引き取って育てられる、という「崖のなさ」が一貫して語られました。

## 5. 発表内容の詳細

### 5.1 Copilot Managed Runtime の位置づけ

Copilot Managed Runtime は、アプリが「実行・ホスト・管理」される土台です。このセッションの時点で、ランタイム自体が前日に GA になったと説明されています。

どの入口を使っても、デプロイ先は同じ Copilot Managed Runtime です。公開すると、認証、コネクタ、そして Microsoft Admin Center での集中的なガバナンスが得られます。管理者はすべてのアプリを一覧で見て、何に接続しているかを把握し、組織に合ったガードレールを設定できます。

### 5.2 アプリスキルがポリシーを理解する

画面の体験は、ここ数年の vibe coding / アプリ作成ツールと同じで、左側でエージェントとチャットし、右側でアプリをプレビューします。違いは、Cowork や Copilot Studio で使われる **アプリスキル**（app skill）が、管理者が Microsoft Admin Center で設定したポリシーを理解したうえで作る点です。例として挙げられたのは次の項目です。

- アプリが接続できるデータ
- 環境のルーティング
- コンテンツ
- 共有の制限

エージェントがこれらのガードレールを把握しながら作るため、最終的に組織内で配備も共有もできないアプリのためにクレジットを使い込む、という事態を避けられると説明されています。

入口として挙げられたのは、新しい Copilot Home（チャットと Cowork）、Copilot Code（発表では "Copilot code" と聞こえます）、Copilot Studio、CLI などです。

### 5.3 Work IQ のコンテキストを使う

Clay 氏によると、1 つの大きなプロンプトで完璧なアプリを作ろうとしても、あまり良いアプリにならないことが多いそうです。Cowork や Copilot Studio では、アプリを作るときに、直前の会議、Loop コンポーネント、「自分のチーム」「Emma との会話」といった参照が使えます。エージェントは **Work IQ** の豊富なコンテキストを引いて、ビジネス、ブランド、チームの運用や業務プロセスを理解したうえでアプリを作ります。

また、テレメトリから見えた傾向として、Cowork では最初のプロンプトでアプリスキルが呼ばれるとは限らず、10〜20 回ほどやり取りした後に呼ばれることも多いそうです。Excel や PowerPoint を作ったり会議を要約したりしているうちに、「繰り返し使える、構造化された、組織で共有できるもの」にしたくなり、アプリ作成に進むという流れです。

### 5.4 コネクタとガバナンスの初期設定

公開後のアプリは、Microsoft 製ツールやサードパーティのサービスに、**1,500 を超えるコネクタ**で接続できると説明されています。データの保存先としては、Dataverse、SharePoint、Rayfin Fabric（音声認識の都合で表記が確定できません。後半では "Fabric, or Rafin" とも聞こえます）といったデータベースの作成が挙げられています。

ここで重要なのが、画面の下に出ていた「governed by default（既定でガバナンスされる）」という考え方です。1,500 のコネクタをすべて有効にはせず、**グリーンゾーン**と呼ばれる比較的安全なコネクタの集合だけが既定で有効になります。そのうえで、管理者が、組織全体でどのコネクタを使えるか、誰が使えるか、アプリでどれを使えるかを選びます。

### 5.5 エージェントに支えられたアプリ

アプリの裏側は、コードベースのアプリです。プレビュー期間中に追加された機能として、アプリをエージェントが支える仕組みが紹介されました。具体的には次の 2 種類です。

- インラインのプロンプトと関数
- GitHub のハーネス上で動く、完全な Copilot Studio エージェント

これにより、データに対するレコメンドや分析といった知的な機能をアプリに組み込めるほか、アプリ自身にアクションを実行させることもできます。

### 5.6 Cowork でのアプリ作成（デモ）

Emma 氏は Cowork から始めています。日々、多くのドキュメントを作り、データが複数の場所に散らばっていること、日付を追う Excel や経営層向けの PowerPoint が静的なため古くなっていくことが課題として語られました。これを解決するには、アプリにするほうが良いという流れです。

Cowork では、たとえば「チームトラッカーアプリを作って」と機能を書いたプロンプトを送ると、Cowork のアプリスキルが Work IQ を使って、これまで作業してきたファイルや参照、自分のチームの情報を踏まえて作り始める、と説明されました。時間がかかるため、実演は完成済みのアプリに切り替えています（詳細は 6 章）。

プラグインとスキルの話も出ています。Emma 氏は、アプリのユーザーガイドを作る「アプリドキュメントスキル」をチームで使っており、多くの人と共有できると述べています。スキルやプラグインとアプリの組み合わせにより、**エコシステム効果**が生まれるという説明でした。

### 5.7 Copilot Studio でのアプリ作成（デモ）

Copilot Studio は、ビジネスプロセスを変革する場所で、エージェントとワークフローに加えて、いまはアプリも作れると紹介されました。アプリは単独で島のように存在するものではなく、エージェントやインテリジェンスと連携して仕事を進めるものだ、という趣旨です。

デモでは、現場点検（field inspections）アプリ「Gauge」が示されます。詳細は 6 章に書きます。

### 5.9 すべての入口が同じ Git リポジトリとランタイムに着地する

ここまでは、主にシチズン開発者・ビジネスユーザー、業務の流れの中でアプリを作る人が対象でした。ここから先は、もっと明確に「アプリを作る」意図を持つ人（Lovable、CLI など）の入口に移ります。

重要な点として、すべての入口が同じ場所にデプロイされるだけでなく、**裏側に Git リポジトリがあり、各アプリのソースコードを保存している**と説明されました。アプリの作成、背後のコード、バージョン履歴は、作成時にできるこのリポジトリに保持されます。Copilot Studio と Cowork からはコードに切り替えて確認でき、開発者は Cowork や Copilot Studio で始まったものを CLI でリポジトリにつないで続きを作れます。つまり、入口が縦割りにならず、「どこから始めたかで崖にぶつかる」ことがない、という考えです。コードは 1 か所にあり、見え、同じ場所でホスト・実行・ガバナンスされます。

### 5.10 Lovable からの公開

Lovable のパートは、Malavika 氏（Lovable の Product Manager）が話しました。Lovable は AI アプリ構築プラットフォームで、「誰でもアイデアをソフトウェアにする最速の方法」として知られている、と紹介されています。数字として語られたのは次のとおりです。

- 40,000 を超えるビジネスが利用
- 70 million を超えるプロジェクトが作成済み
- ユーザーは個人事業主や小規模な店から、Deutsche Telekom や Nvidia といった大企業まで

Copilot Managed Runtime との統合では、ビルダーは Lovable で作り、IT 管理者は Microsoft 365 テナント内でそのアプリを管理できます。流れは次のとおりです。

1. IT 管理者がワークスペースで設定する（所要は約 20 分と説明されています）。
2. Lovable が Copilot Managed Runtime に接続されると、ワークスペース内のビルダーは誰でも作り始められる。
3. Microsoft コネクタを使って作ると、Lovable がアプリを作り、アプリを 365 テナント内のリソースにバインドする。
4. ユーザーが公開すると、アプリは Copilot Managed Runtime に公開される。

**Lovable は裏側のデータにはアクセスできません。** Lovable が Copilot Managed Runtime に公開するのは React のフロントエンドだけで、ホストと実行は Microsoft が行い、IT が管理します。Lovable は、すでに今日利用可能と案内されています。

### 5.11 ガバナンスの 4 つの観点

Clay 氏は、ガバナンスを次の観点で整理しています。

| 観点 | 説明 |
| --- | --- |
| 作成時のガードレール | 適切な環境、適切なデータ、適切な開始点を使う。使えないものにクレジットやトークンを無駄にしない |
| 接続（コネクタ） | 1,500 のコネクタ全体と、カスタムコネクタを作る機能。管理者はグリーンゾーンから始め、組織全体で許可するものと、対象グループ、使い方を決める。エージェントは作成中にこれを尊重し、ランタイムも強制するので、アプリは接続すべきでないデータに接続しない |
| 共有 | アプリの配布方法の制御。名指しで個別に共有させるか、ドキュメントや Excel のような組織リンクを使えるようにするか。Admin Center でルールを作り、作られるすべてのアプリに適用する |
| 監視（oversight） | どこで作られたかにかかわらず、作成されたすべてのアプリを見られる。何のデータに接続し、誰が使っているかが分かり、隔離（quarantine）もできる |

### 5.12 CLI と VS Code でのコード修正（デモ）

ドメインの専門家が作ったアプリが、重要性や複雑さを増したときに、プロの開発者に引き継ぐ場面が想定されています。各アプリは Git のリモートリポジトリに支えられているため、`git clone` して開発環境（このデモでは VS Code）で作業できる、という説明です。デモの流れは 6 章に書きます。

### 5.13 Microsoft Admin Center でのガバナンス（デモ）

Admin Center の新しい **Apps** カテゴリで、Copilot Managed Runtime のアプリを管理します。アプリ一覧、環境グループ、コネクタとアクション、共有、コンテンツセキュリティポリシー（CSP）、コスト管理が順に示されました。詳細は 6 章のとおりです。

## 6. デモ・手順

このセッションにはデモがあります。ただし録音は音声のみで、画面の細部は確認できません。以下は、語られた内容の範囲だけをまとめています。また、Emma 氏は Cowork や Copilot Studio の作成を、完成済みのものに切り替えて見せています。

### 6.1 Cowork でのアプリ作成（Emma 氏）

1. Cowork で、「チームトラッカーアプリを作って」と機能を書いたプロンプトを送れば、アプリスキルが Work IQ を使って作り始める、と説明した（登壇中に操作が思うように動かないトラブルがあった）。
2. 作成には時間がかかるため、完成済みのアプリに切り替えた。これは Atlas プロジェクトの Q4 2026 ロードマップで、PowerPoint やドキュメントにあったデータが表示されている。
3. アプリはインタラクティブで、スプレッドシートの行だったデリバラブルをフィルタし、掘り下げ、編集し、時間を更新し、チームに共有できると説明した。
4. 共有は、Office ドキュメントと同様にリンクをコピーする方法（組織内の人向け）か、個人を指定する方法で行える。Clay 氏と共有する例を示し、開くと、そのまま動く Web アプリとして使える状態になっていた。データは「system of record」にあるという説明。

### 6.2 Cowork の Figma プラグイン連携（Emma 氏）

1. 先に、デザインチームが作った Figma のデザインを見せた。青色の使い方やグラフの配置、ワークキューのページなどが整っている、と説明した。
2. このデザインを実際に使えるアプリにするため、Figma のファイルのリンクをコピーした。
3. 新しい会話を開始し、「この Figma に基づいてアプリを作って」と入力してリンクを渡した。
4. Cowork は Figma 用のプラグインを探し、Figma Design の特定のスキルを呼び出してコンテキストを取り込む、と説明した。数分かかるため、完成済みのものに切り替えた。
5. 完成したアプリはデザインにかなり近く、違いは**実データにつながっている**点。接続先として SharePoint のリストが、画面上で確認できた。デザインチームが作ったデザインが、数分で組織内で共有・管理できる実アプリになった、と述べた。

### 6.3 Copilot Studio でのアプリ作成（Emma 氏）

1. 現場点検アプリを作る、という説明から始めた（用意していたプロンプトの貼り付けがうまくいかず、キーボードにも入力できないため、ここでも完成済みのものに切り替えた）。要望として、分析機能と、是正が必要な点を扱うエージェント、合格率などの分析を挙げていた。
2. 完成したアプリは「Gauge」という現場点検の分析アプリで、合格率、チェックリスト項目、失敗のヒートマップなどの可視化が表示される。合格率の推移、繰り返し出る指摘事項、結果の詳細一覧も確認できる。
3. データの出どころは Dataverse。自分の環境にあるデータテーブルであることを画面で確認した。
4. Dataverse プラグインを使い、エージェントとやり取りしながらテーブルの作成とスキーマの更新を行った、と説明した。
5. アプリには「Gauge Risk Advisor」というエージェントも作らせてあった。これは、リスクと次の是正アクションを示すための指示と知識を与えられた Copilot Studio エージェント。
6. アプリ内のカスタム UX から、エージェントに「North Yard で期限を過ぎている是正アクションは何か」と質問した。エージェントは公開済みで、関連情報を取得して返し、期限超過のアクションが 2 件あると示された。
7. エージェントとは別に、AI によるリスク概要も表示されていた。これは、データセットと時間に基づいて生成される**単純な LLM プロンプト**で、完全に動くエージェントではない、と説明された。

### 6.4 Lovable から Copilot Managed Runtime への公開（Malavika 氏）

1. 新入社員向けのオンボーディングアプリを作る。Entra ID に基づいて個人ごとのオンボーディングの流れを表示し、バックエンドには Excel を使う。
2. Lovable で作成をプロンプトし、Copilot Managed Runtime にデプロイする、と説明した。
3. バックエンドの Excel には、メールアドレスに紐づく新入社員の一覧、タスク、関係者などが入っていた。
4. 公開のフローを見せた。アプリができたらボタンを押すだけで公開され、Microsoft のテナントで実際に動く。
5. 公開されたアプリを、Microsoft Entra ID でサインインした状態で開いた。個人用のオンボーディングの流れが表示され、データは Excel によるものだった。
6. アプリを操作し、タスクを完了にした。操作に応じて、小さなトースト通知が出た。

### 6.5 CLI と VS Code で Gauge アプリを修正（Emma 氏）

Emma 氏は、Copilot Studio で作った Gauge アプリを、プロの開発者の立場で引き取る流れを見せています。

1. CLI で、自分に編集権限のあるアプリを一覧した。Gauge アプリが、自分に共有されたものとして表示された。
2. そのアプリをクローンした。事前のテストで作ったクローンが残っていたため、それを削除し、別のフォルダーで再実行した。
3. クローンは Git Credential Manager を介して行われ、キーやトークンを置く必要がない、と説明した。
4. ローカルに取得したファイルの一覧を見せた。ホームの TypeScript ファイルのほか、この React アプリに関連するフック、コンポーネント、ライブラリが含まれていた。
5. VS Code で、通常の環境（Node、Git など）のまま作業できる。ここで Copilot を使い、アプリを編集する。
6. 現場点検を地図上に表示する地理位置の機能を追加するよう Copilot に依頼した。依頼には、ホーム画面に追加すること、既存の内容を保つこと、既存の計算を再利用すること、地図は既存データに応答することを含めた。
7. Copilot が作業を始め、ローカルのファイルを直接編集する様子を見せた。
8. 続いて、開発サーバーを起動してリンクを出すよう依頼した（この部分は実行済みの画面に切り替えた）。
9. リンクを開くと、ローカル開発モードのアプリが表示された。追加した地図コンポーネントが読み込まれ、これはローカルの開発サーバーで動いており、顧客向けにはまだ公開されていないという表示も確認できた。
10. 最後に、ドメインの専門家が作ったアプリを VS Code に取得し、変更して、元に戻す流れができた、とまとめた。

> 補足：10 の「元に戻す（push back）」は口頭で説明されましたが、デモ中にデプロイ操作を実行する様子は語られていません。

### 6.6 Microsoft Admin Center でのガバナンス（Emma 氏）

1. Microsoft Admin Center に新しいカテゴリ **Apps** がある。ここで Copilot Managed Runtime のアプリを主に管理する。
2. **All apps** タブには、組織内で作られたすべてのアプリが表示される。アプリごとに、最終更新、作成者、アプリの内容とビジネスへのリスクに関する詳細、使用状況データ、使うコネクタとアクションを確認できる。
3. 操作として、**ブロック**（隔離して実行を止め、リスクに対処してから再デプロイする）と**削除**ができる。
4. ガバナンスは何も設定しなくても既定で適用される。設定は**環境グループ**に入っている。環境グループでは、どのアプリがこのグループの管理下か（どのポリシーを、誰の、どの環境に適用するか）と、構築時に使えるデータを設定する。
5. コネクタの全一覧が表示され、許可したものとブロックしたものが分かる。新しく許可するものを追加できる。
6. コネクタ単位だけでなく、個別の**アクション**単位でも許可を設定でき、リスクがあると思うものは有効・無効を切り替えられる。
7. 共有ポリシーもここで管理する。リンクによる共有の可否、セキュリティグループへの共有、ゲストユーザーへの共有などを設定できる。
8. **コンテンツセキュリティポリシー（CSP）** は、既定でかなり厳格になっている。信頼できるコンテンツだけを使うための設定で、許可されていないサービスや API にアクセスできる状態でも、ここで設定した CSP によってブロックされる。
9. **コスト管理**は、Admin Center の Copilot の下の cost management から行う。設定（configuration）で、実行する Copilot Managed Runtime アプリの支出ポリシー（spending policy）を作れる。「field inspections」という支出ポリシーを例に、対象とするエージェントとサービスを選べること、Copilot Managed Runtime をサービスの 1 つに設定したことを示した。
10. この支出ポリシーには上限があり、デモでは 5,000 になっていた（単位は発表では聞き取れません）。アプリの展開先ユーザーが増えるのに合わせて拡張できる。

## 7. 注意点・発表者の気付き

- **1 つの大きなプロンプトでは良いアプリにならないことが多い。** Work IQ のコンテキストを使い、会話を重ねながら作るほうが良い、という見方が示されました。
- **アプリスキルは最初のターンで呼ばれるとは限らない。** テレメトリでは、10〜20 ターン後に呼ばれることも多いそうです。
- **ガードレールを知らずに作ると無駄になる。** 配備や共有ができないアプリにクレジットを使わないよう、エージェントが作成中にポリシーを把握する設計になっています。
- **既定で有効なコネクタは、1,500 のうちグリーンゾーンだけ。** 管理者の選択で広げます。
- **CSP は既定で厳格。** 許可されていない外部への通信は、CSP でブロックされる設計です。
- **デモは一部、完成済みの画面に切り替えて行われた。** Emma 氏は、入力が動かない問題と時間の都合で、作成途中の待ち時間を省いています。作成にどのくらいかかるかは、発表からは分かりません（「数分」「少し時間がかかる」といった言及のみ）。
- **Lovable は裏側のデータにアクセスしない。** Lovable が公開するのは React のフロントエンドだけです。
- **Copilot Code のデモは本セッションにない。** 別のセッションの録画を見るよう案内されました。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **選んだ入口を変えなくてよい。** Cowork、Copilot Studio、Copilot Code、Lovable、CLI のいずれから作っても、アプリは Copilot Managed Runtime に着地し、管理者が見る場所は 1 つです。
- **作成途中で止まらない。** 作成時にエージェントが管理者のポリシーを把握しているため、後から配備できないと分かって作り直す無駄を減らせます。
- **ビジネス側と開発者側の連携。** ドメインの専門家が作ったアプリを、Git リポジトリ経由でプロの開発者が引き継げます。Gauge の例では、VS Code で地図の機能を追加できました。
- **既存の業務コンテキストの活用。** Work IQ により、会議、ファイル、チームの情報を踏まえた作成ができます。
- **デザインから実アプリへ。** Figma のデザインから、実データ（SharePoint のリスト）につながるアプリを数分で作れる、と説明されました。
- **既定のガバナンス。** 既定のグリーンゾーン、厳格な CSP、環境グループのポリシー、共有ルール、隔離（ブロック）、支出ポリシーによって、アプリが増えても管理を拡大できます。
- **Lovable 利用者向け。** IT 管理者の設定は約 20 分で、その後はワークスペース内のビルダーが作り始められます。

発表では、個別の顧客企業のアプリ導入事例や、導入による定量的な効果（削減時間や費用など）は示されていません。Lovable の利用規模（40,000 超のビジネス、70 million 超のプロジェクト）が語られたのみです。

## 9. まとめ

Copilot Managed Runtime は、Cowork、Copilot Studio、Copilot Code、Lovable、CLI など、入口の違うツールで作られたアプリを、同じ場所でホスト・実行・管理するための基盤です。前日に GA となり、Cowork と Copilot Studio でのアプリ作成、インテリジェントアプリ機能も GA、CLI でのエージェントとワークフローの構築はプレビューという整理でした。

デモでは、Cowork と Copilot Studio での作成、Lovable からの公開、VS Code での修正、そして Microsoft Admin Center での一覧・ブロック・コネクタ・共有・CSP・支出ポリシーの管理が示されました。共通するのは、**作る場所は自由に選べるが、管理は 1 か所で一貫している**という考え方です。詳しい発表内容と、GA / プレビューの区別は、**aka.ms/cmrblog** のブログで確認できます。
