# BRK472 Agentic AI in financial services: From assistants to business systems

## 1. はじめに

このセッションは、金融サービス業界向けに「AI アシスタントから、業務そのものを動かすエージェントへ」という流れを説明するものです。前半は Microsoft の 2 人の登壇者が、業界の動向と Microsoft の戦略を語ります。後半では、債券運用会社 PIMCO の Ewan Lowe 氏が、社内で実際に起きた変化を 3 つのデモとともに紹介します。

聞き終えて分かるのは、次の点です。

- 金融機関で AI の導入が加速していることを示す、発表で引用された数字
- Microsoft が整理した 3 つの課題領域（従業員の生産性、ビジネスプロセス、プロダクト開発）と、それを支える土台
- PIMCO で、ビジネス部門の担当者（citizen developer）が Cowork を使って分析ツールや業務ツールを作った事例と、そのために IT 部門が整えたデータ基盤
- コスト管理、スキル習得、ガバナンスについての PIMCO の実体験にもとづく助言

結論を先に書くと、PIMCO の Ewan 氏は AI 活用のカギを「データ、データ、アップスキリング、アップスキリング、アップスキリング、そしてガバナンス」と表現しています。

## 5. 発表内容の詳細

### 5.1 業界の状況（Hemanth）

Hemanth は、Microsoft の顧客がすでに AI の効果を得ていると述べ、次の例を挙げました。

| 企業 | 語られた内容 |
| --- | --- |
| Barclays | Copilot を約 100,000 人の従業員に提供し、100 万時間を節約した |
| Investec | 200 時間以上を節約し、顧客と過ごす時間に回している |
| UBS | 速度を活かして意思決定を速めた |
| BlackRock | 新商品を提供することで、市場投入までの速度を高めた |

規模感として、研究によれば、リテール銀行の AI による年間利益ポテンシャルは約 3,700 億ドル、アセットマネージャーは顧客カバレッジを 3〜5 倍に増やせる可能性があると紹介されました。また、スライドのグラフでは、四半期ごとにエージェントの展開が 11 ポイント増えています。

IDC の調査では、組織を AI の成熟度で 3 つ（laggards、neutral、frontier firms）に分けています。AI への投資に対するリターンは、laggards が 0.84 倍（1.0 を下回る）、フロンティア企業（全社戦略を持ち、AI を広く使う）は 2.84 倍でした。金融サービス業は他業界より進んでおり、**フロンティア企業に分類される割合は 31%** です。

Microsoft 自身の調査として、次も紹介されました。

- Copilot の会話テレメトリでは、**やり取りの 49% が「分析、推論、判断」** であり、文章作成、書式設定、基本的な質問への回答ではない。AI を「事実を調べる道具」より「思考のパートナー」として使う傾向が強い。
- フロンティア・プロフェッショナル（AI ユーザーの上位 16%）は、高度なエージェントを使い、ワークフローを再設計し、自社の AI 拡大にも関わっている。80% が「昨年より多くの仕事を生み出せている」と答え、53% が「AI に任せることと自分でやることを意図的に判断するために立ち止まる」、43% が「自分のスキルを保つために自分でも作業する」。つまり「思考を外注しない」人たちです。
- Microsoft 365 のシステム内では、エージェントが前年比で約 15 倍に増えている。

Hemanth は、フロンティア企業は「学習するシステム」であり、これからは「タスク」ではなく「成果」が仕事の単位になると述べています。金融サービスの業界が求めるものとして、パーソナライゼーションが限界費用なしで標準提供される AI 駆動のオペレーション、仕事の流れの中でのリアルタイムのインサイト、信頼できるインテリジェンスプラットフォームを挙げています。

### 5.2 Microsoft の戦略（Jared）

Jared は、多くの金融機関と話してきた経験から、課題を 3 つの領域に整理しました。

**① 従業員の生産性**

多くの企業が「全従業員を昨年の 10 倍生産的にしたい」と考えています。10% や 40% ではなく、10 倍です。机の上に置くアシスタント（Copilot、Cowork）が中心で、ChatGPT や Claude なども同じ領域にあります。データ、スキル、プラグインを与えて拡張できますが、使うのは人間で、プロンプトを書くのも人間です。ある時点から、人間の注意力が限界になって価値が頭打ちになります。例として、ローンのリスクを Copilot で分析するローン担当者が、「人の注意力に縛られない形で、ローン処理の全体をどう変えるか」を考え始める、という流れが語られました。

**② ビジネスプロセスの革新**

ここが Copilot Studio の領域です。長時間動き続ける、エージェント型のビジネスプロセスを作ることに注力していると説明されました。人の外側に置かれるものを作る領域で、個人用の「OneDrive」に対して、会社全体の資産である「SharePoint」のようなものだというたとえが使われました（Jared の上司がかつて SharePoint に携わっていて、冗談でそう言っているとのことです）。個人の領域では従業員を 10 倍生産的にしますが、ここでは **特定のプロセスについて事業を 10 倍効果的にする** ことが目標です。

**③ より良い製品・サービスの開発**

開発者を雇って行う領域です。GitHub Copilot、Foundry、Visual Studio などが対応し、多くは外部向けですが、社内向けに開発者に作ってもらうものもあります。この 3 つは別物で、別の領域に流用しないことが大切です。Word と Visual Studio はどちらもテキストエディターだが、Python スクリプトを書くのに向いているのは片方だけ、というたとえで、「適切な場面で適切なツール」を選ぶよう述べています。

**この 3 つを支える土台**

3 つはいずれもユーザーが触れるフロントエンドで、その裏には次の投資が必要だと説明されました。

| 土台 | 説明 |
| --- | --- |
| コンテキスト | モデルは与えられるコンテキストの分しか強くならない。CRM や財務データなどにアクセスできなければ、答えは同業他社と同じになる。Microsoft はこの領域を **Microsoft IQ** と呼ぶ製品群で投資している（会場に大きなブースがある）。その一つ **Work IQ** は、メール、PowerPoint、SharePoint など M365 エコシステム内のあらゆる情報をコンテキストに取り込む |
| フロンティアモデルとモデルの多様性 | 最新モデルをすぐ使え、効率的なモデルも適切な時に使えるようにする。自動モデルルーターやフュージョン機能に投資しており、プロンプトを分解し、重要な部分は高品質なモデル、2 万回繰り返すような部分は効率的なモデル、と使い分けられる。前日の Mustafa の MAI の話にも触れ、Opus 品質で 100 倍低コストといったものを入れていきたい、と述べた |
| ガバナンス | Microsoft 社内だけで 50 万を超えるエージェントがあり、IT 部門は同じ悩みを抱えている。**Agent 365** 周りの製品群で、すべてのエージェントに ID を与え、その ID でアクセス範囲を制御する。エージェントの存在、アクセスできるデータが分かり、従業員と同じ規則を設定できる |
| スケーラブルなインフラ | データは **Fabric**、GPU は **Foundry**。Azure は 36 時間ごとに新たに 100 万コアを追加している。Jared が Azure にいた 2012 年頃、コア数が 100 万に達した日はケーキを囲んで祝ったという思い出が添えられた |

> 補足：Jared 自身、ガバナンスについては「8 時間話せる内容を 30〜45 秒で話している」と述べ、詳しくは他のセッションに行くよう案内しています。

Jared は、これを「Jared 版の Microsoft 全体を 30 秒で」と呼んでいます。

**働き方の変化：ローカルなアシスタントとエージェントの群れ**

多くの人は、ローカルなアシスタントにスキル、プラグイン、コンテキスト、データを足していくところから始めます。最良のチームは、そこから「自分が不在の間にも動く、エージェントの群れ（fleet）」へ広げていると述べています。例として、Copilot Studio を Copilot Studio のエージェントで作っていること、そのエージェント群がものを作り、フィードバック対応などを進め、利用者側はローカルのアシスタントでそれを最適化していることを挙げました。両者はスキル、ツール、データフィードを共有し、密に結合しています。将来は、デスクトップで動く個人用のスタックと、企業・事業部門が運用するエージェントの群れという、**2 つの中核スタック** になるという見方です。

### 5.3 PIMCO の紹介（Ewan）

PIMCO は、債券（active fixed income）の運用に特化したグローバルな投資運用会社で、公開市場と非公開市場の両方に専門性を持ち、運用資産はおよそ 2.3 兆ドルです。Ewan 氏は、顧客対応部門、オルタナティブ事業、投資データ、そして AI プラットフォームを支えるテクノロジーチームを率いています。

PIMCO の AI は 2000 年代から長い歴史があり、古典的な機械学習の「1.0 時代」と生成 AI の「2.0 時代」に分けて語っています。技術そのものではなく、既存の優先事項というレンズで見ており、特に次の 3 つの目標に役立つ技術に関心があります。

1. 顧客により効果的にサービスを提供する
2. ポートフォリオマネージャーの投資プロセスを支え、データセットから追加のインサイトを引き出す
3. 業務効率を上げる

進め方は 2 つで、主要な業務ワークフローに沿った **社内独自の AI ツール** を作ることと、**Copilot と Cowork を全世界の全従業員に展開** することです。今回扱うのは後者です。

### 5.4 この 1 年の変化（Ewan）

Ewan 氏は「3 月」にタイムマシンで戻る形で振り返りました。

- 3 月：Cowork がプレビューで登場し、初期の技術イノベーターに展開した。
- 数週間後：米州のアカウント・アソシエイトの一人が、Cowork で作ったツールをメールで送ってきた。地理的な可視化を使った分析ツールで、「かっこいい」だけでなく「価値がある」ものだった。長く議論されていたが、優先順位キューの中ほどにあったもので、彼女は自分で作ってしまった。本業はアカウント・アソシエイトで技術部門ではない。こうした人を **citizen developer**（技術部門の外でソリューションを作る人）と呼んでいる。
- その後：Cowork を全世界に展開すると、他の citizen developer たちがツールや自動化を作って共有する「カンブリア爆発」が起きた。

一方で、順調だったわけではなく、特に第 2 四半期に次の摩擦がありました。

- ツールを作る能力が、デプロイとガバナンスの能力を先に追い越し、急いで対応する必要が生じた。
- データの問題。citizen developer が作りたいものには PIMCO のあらゆるデータが必要で、M365 のデータだけでなく、社内データやサードパーティのデータも要る。第 2 四半期はこれらを Cowork に入れるのが簡単ではなく、戦術的な作業と工夫でデータを入れた。

その後プラットフォームが急速に成熟したとして、citizen developer が作ったものから、価値を示す代表的な 3 つをデモで紹介しました（デモの内容は 6 章にまとめています）。

### 5.5 トークンの使いどころ（AI でコードを作るか、実行時に AI を呼ぶか）

デモ 2 の流れで、Jared がトークンの使い方について Ewan 氏に尋ねました。

ワークフローの中で AI を使う方法には、2 つあります。

1. ワークフローの各段階で LLM を呼び出す。
2. AI を使って、ワークフローを動かすコードを作る。

2 つ目は、作ったものをテストして推論できるので、より決定的（deterministic）です。一般にトークンのコストが低く、レイテンシーも速くなりやすく、AI の実行時のリスクやガバナンスの問題も少なくなります。一方で、柔軟な入力には対応しにくく、その場での推論はできません。そのため、基本は「AI で決定的なコードを作る」側に寄せ、柔軟性や解釈が必要なところだけ実行時に AI を使う、という考え方です。

### 5.6 個人のツールが組織に広がるとき

Jared が「ビジネスユーザーが作ったものが組織で広がったらどうなるか」と尋ね、Ewan 氏が答えました。AI 以前も、citizen developer が Excel や Python を作って大きくなりすぎると技術部門に引き継ぐことがありましたが、いまははるかに速く起きています。アイデアが試され、検証され、Cowork である規模まで広がり、ある時点で技術・エンジニアリングチームが入って規模を拡大します。Ewan 氏はこれを **「Cowork からエンタープライズ・テクノロジーへのベルトコンベア」** と呼び、そのスピードは毎週速くなっていると述べました。

### 5.7 コスト管理

Jared は、ほぼ毎回の顧客との会話で「コストをどう扱うか。トークンは今年の予算に入っていなかった」と聞かれると述べて、Ewan 氏に率直な意見を求めました。Ewan 氏が挙げたレシピは次の 3 点です。

1. **コストを価値の創出と対応させる。** PIMCO ではビジネス経費として扱い、事業部門に割り当てている。中央部門が支払う形は、請求と利用を結びつけるのが難しいので勧めない（PIMCO では行っていない）。
2. **レポーティング。** 個人や組織単位ごとに、どれだけのプロンプトを実行し、いくら使ったかという基本が必要。ただし、それで得られた価値は分からない。前日のキーノートで、コスト管理と FinOps が、作られた成果物との関連づけまで広がると聞いた。
3. **「価値 > コスト？」というマインドセット。** PIMCO にはこの題のスライドがある。トークンにお金を使う現場の事業判断として、作られたもの（時間の節約や、事業を前進させる新しい能力）の価値が、トークンのコストより大きいかを問う。両者をそろえると、たいてい答えは「はい」になる。価値が何倍にもなると見込めるため、あえて規模を拡大してコストを増やすこともある。ただし、この価値とコストの照合はローカル（事業部門）で行う必要がある。

### 5.8 初めて取り組む人への助言（Ewan）

Ewan 氏が PIMCO で使っているスライドが紹介されました。AI の変革は単一の要素ではなく、複数の要素が連動する、という前提です。「AI velocity（組織が AI から価値を得て前進する速さ）」を、複数の項と、べき乗や除数を使った式の形で表しています。

| 項 | 説明 |
| --- | --- |
| 基盤モデル | 品質は重要だが、今日の議論ではこの場の外にある要素とする。ただし昨年の進歩で多くが可能になった |
| プラットフォーム | Cowork と、PIMCO のチームが周辺で行ったエンジニアリング |
| データ（二乗） | ファーストパーティとサードパーティの両方。データが無ければプラットフォームは役に立たない。Ewan 氏は「データの項を二乗にした」と述べている |
| アップスキリング（三乗） | AI を使いこなす力とスキルが無ければ価値は得られない。取り組みに要した労力は驚くほど大きく、AI プラットフォームチームは時間の約 50% をアップスキリングに使っている |
| 実行 | プロセスの再設計を伴う変更管理 |
| ガバナンスのギャップ（除数） | デプロイ、セキュリティ、法務・コンプライアンスとの整合、コスト管理にギャップがあれば、すべて足を引っ張る要因になる |

PIMCO のアップスキリングは **4 ステップ** です。

1. 新機能ごとに、全社向けの teach-in を行う。
2. 事業部門ごとに、その機能がどこで使えるかを理解し、同僚が使い方を見せる。
3. 実際に手を動かすハンズオン。ビルドアソン、ジーニアスバーなど、あらゆる手段で使う。
4. 多くのフォローアップ。

最後に持ち帰ってほしいこととして、「**データ、データ、アップスキリング、アップスキリング、アップスキリング、そしてガバナンス**」と述べました。

### 5.9 今後の見通し（Jared）

Jared は「個人的な見解（hot take）」として、仕事は「毎日の仕事をする人」から「その仕事をするエージェントを作る人」に大きく変わると述べました。自身のチームでは、すでに日々コードを書くのではなく、コードを書くエージェントを作り、調整し、改善していると述べています。そして、これは地球上のすべての情報労働者に来ると見ています。

### 5.10 Q&A

質問者は、エジプトの銀行セクターの参加者で、Copilot と Cowork の導入の初期段階にあり、従業員への展開方法と、支店の従業員と本社（HQ）の従業員の区別の仕方について助言を求めました。

**Jared の回答（戦略面）**

- 本社は主に情報労働者であり、いま最も力を入れるべき場所で、最も価値が出る場所でもある。
- 支店の従業員は情報労働者の割合が低く、顧客対応やデータ入力に時間を使っているだろうと Jared は推測している。フロントエンドやアプリの話はあるが、それらは通常、静的で、コストに非常に敏感である。支店の数だけ掛け算になるため、支店のレベルではよりコストに敏感になる必要がある。本社には同じ掛け算の効果は無い。
- 実装面では、ユーザーのグループごとに提供内容を分けるツールが多数ある（Jared は「intergroups」と述べており、正確な製品名は聞き取れません）。

**質問者の補足**

Copilot の保護とポリシーについて、1 時間かけて扱うセッションがあると案内しました。A365、Defender、Purview、Conditional Access、Intra（聞こえた表記。音声認識の都合で確定できません）などの製品群があると述べ、午後に Charles Lamont 氏と Hyatt 氏による A365 の 1 時間半のセッションがあるとも紹介しています（人名の綴りは音声認識の都合で確定できません）。

## 6. デモ・手順

Ewan 氏が 3 つのデモを行いました。元のものは PIMCO の環境で顧客データと独自の分析を使って作られたため、今回は Microsoft のサンドボックスに移し、元に非常に近い形で用意したものだと断っています。画面の細部は音声からは確認できず、以下は語られた内容に限っています。

### 6.1 デモ 1：個人の生産性（月次ファンド・レポート）

米州の製品戦略アソシエイトが作った例です。毎月初めに、ファンドの AUM（運用資産）、フロー、市場の状況を説明するレポートを作ります。AI 導入前は手作業か、技術チームの仕事でした。

1. アソシエイトは、スラッシュコマンド（トランスクリプトでは「slash P big close」と聞こえます。表記は音声認識の都合で確定できません）を実行する。以前の作業をスキルとして一つにまとめてある。
2. スキルは、以前の手作業の全ステップを実行する。データをダウンロードし、データ品質の検証を行い、レポート用の分析キューブを作って、複数の出力を作る。
3. 出力の一つとして、ツールが開く。リターン、超過リターン、フロー、ファンドサイズが表示され、Morningstar のデータも入っている。PIMCO のシステムのデータとサードパーティのデータの組み合わせの例である。
4. 他のタブとして、パフォーマンス、資産とフロー、ポートフォリオ、市場の背景が紹介された。
5. AI が、データの上にコメント（分析やインサイト）も生成している。Ewan 氏は「完全には信頼していない」と述べ、1 年で改善はしているが、人が見るためのインサイトの出発点として興味深いという位置づけです。
6. フィルターなどのコントロールもある。

Ewan 氏はこれを、PIMCO で非常によく見られるパターンだと説明しました。重いレポートで、3 時間かかっていた作業が 15 分に圧縮された例があり、**出力は人間が検証する（human in the loop）** 形を保っています。

Jared の質問「レポートのユースケースはこの 1 年でどう進化したか」への答えは次のとおりです。

| 時期 | 状態 |
| --- | --- |
| 第 2 四半期 | フィルタやドリルダウンのない静的ダッシュボード。定期更新で、手動で共有 |
| 現在 | ドリルダウン付きの動的ダッシュボード。MCP（トランスクリプトは「NCPs」と聞こえます）からデータを動的に更新し、ガバナンスと権限（entitlement）がより強い形でプラットフォーム上で共有される |

### 6.2 デモ 2：チームのワークフロー（ファンド立ち上げ前プロセス）

2. プロンプトの全文は見せず、Ewan 氏が要約して説明した（デモの形式として向かないため）。プロンプトには、機能や技術的な実装の詳細は書かれておらず、実行しているプロセスの性質と、理想の状態が説明されているだけだった。
3. 出力として、ファンドのステータス・ダッシュボードが表示された。充実したトラッカーが付いており、可視化の下には、各グループがファンドをワークフローの次の段階へ進めるためのフォームがある。

### 6.3 デモ 3：データ基盤とスライドの自動更新

最初の 2 つは citizen developer が作ったものでした。ここで Jared が「技術チームの出番はどこか」と尋ね、Ewan 氏は「技術チームも変わらず忙しいが、仕事の性質が変わっている」と答えました。

**アーキテクチャ（スライドでの説明）**

citizen developer のツールに共通するのは、データへの大量のアクセスが必要なことです。口座の参照データ、パフォーマンス、フロー、取引といった PIMCO のファーストパーティ・データや、サードパーティのコネクターです。これらは自社のシステムにあるデータで、Microsoft の Work IQ には含まれません。Cowork は M365 への接続が標準で付いていますが、自社データを足す必要があります。

スライドでは、左に Work IQ のスタック、中央に PIMCO のアーキテクチャ、右に Power BI が示されました。

- 数年前、AI 以前に、特に顧客対応領域で「データ・アズ・ア・プロダクト」の再編に大きく投資した。データプロダクト、データガバナンス、データオペレーションがあり、この領域ではデータオペレーションとテクノロジーのチームを統合した。その上にデータ API がある。
- AI の時代に入り、そこにセマンティックレイヤーと MCP を足した。さらに、それを Cowork の環境に統合した。ファーストパーティのデータを Cowork に統合する取り組みでは Microsoft と最初に協働した顧客の 1 社で、インフラとセキュリティの面で新しい部分があった。今後は、自社の MCP を持ち込める機能として製品化されるよう Microsoft と話している。
- Power BI：PIMCO は大量に使っており、統制された有用な指標を含むダッシュボードが多い。Cowork を Power BI につなぐと、多くの質問に答えられる。
- ただし、基盤モデルの学習データに含まれる概念は得意だが、PIMCO 固有の概念になると、Power BI ダッシュボードへの質問とインサイトの抽出の性能が大きく落ちる。そのため、セマンティックなラベル付けを上に追加した。改善はしたが完璧ではなく、易しいものから中程度、ほぼ難しいものまでは機能する。最も複雑なユースケースでは、いまも結果を精査している。
- 3 つ目の柱はサードパーティのデータと MCP（スライドには Morningstar が載っている。デモ 1 に出たもの）。

**デモ（スライドの更新）**

サービシング資料（10〜20 枚の、情報が密なスライド）の 1 枚を使った例です。毎月更新したいが、PowerPoint の全セルの元データにアクセスできなければ更新できません。いま取り組んでいる段階だと説明されました。

1. 入力のスライドは 8 月までのデータになっている。
2. 「このパフォーマンスのスライドを、直近の月末データで更新して」と依頼する。
3. 内部では、スライドを調べ、ビジュアルとデータの出所を理解する。
4. MCP を特定するメタデータで補強してあり、それをもとに MCP を呼び出し、データを取得し、可視化に戻して、出力を描画する。
5. 下部の結果では、10 月まで更新されている。

Ewan 氏は、Work IQ のデータ、PIMCO のデータ、サードパーティのデータの **3 つの柱** をそろえた例だとし、Cowork を「個人の事務作業（メールや SharePoint）のプラットフォーム」から「ビジネスの生産性と成果のプラットフォーム」に変えると述べています。

## 7. 注意点・発表者の気付き

- **ツールを作る能力が、デプロイとガバナンスの能力に先行することがある。** PIMCO は第 2 四半期にこれに直面し、急いで対応しました。
- **データの取り込みは容易ではなかった。** 第 2 四半期は、戦術的な作業と工夫でデータを Cowork に入れました。
- **AI が生成するコメントや分析は、完全には信頼していない。** 出力は人間が検証します。
- **PIMCO 固有の概念では、Power BI への質問の性能が落ちる。** セマンティックなラベル付けを足しても完璧ではなく、複雑なユースケースは今も結果を精査しています。
- **ファーストパーティのデータを Cowork に統合するには、インフラとセキュリティの面で新しい作業があった。** Microsoft とは、自社の MCP を持ち込める機能の製品化について話しているとのことです。
- **アップスキリングの労力は予想以上。** AI プラットフォームチームの時間の約 50% を使っています。
- **コストは中央で払うより、事業部門に配賦する。**
- **ワークフローは、AI を使って決定的なコードを作る方向に寄せる。** 実行時に AI を使うのは、柔軟性が必要な場面に限ります。
- **デモは、元の環境のものを Microsoft のサンドボックスに移したもの。** 元のデータは顧客データと独自の分析を含みます。

## 9. まとめ

このセッションは、AI の活用が「個人のアシスタント」から「ビジネスプロセスを動かすエージェント」へ進む流れを、Microsoft の戦略と PIMCO の実体験で示しました。Microsoft は課題を、従業員の生産性、ビジネスプロセスの革新、製品・サービス開発の 3 領域に分け、コンテキスト（Microsoft IQ）、モデルの多様性、ガバナンス（Agent 365）、スケーラブルなインフラ（Fabric と Foundry）で支える考えです。

PIMCO では、ビジネス部門の担当者が Cowork で月次レポート、ファンド立ち上げ前のプロセス、スライド更新のような仕組みを作り、IT 部門はセマンティックレイヤーと MCP でデータを整えて支えました。コストは事業部門で「価値 > コスト」を問い、成功の式は「データ、アップスキリング、ガバナンス」という整理でした。
