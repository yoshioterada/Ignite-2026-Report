# THR871 Build once, ground many with Fabric IQ

## 1. はじめに

このセッションは、Fabric IQ の ontology を使って「ビジネスの文脈（business context）」を一度だけ作り、それを複数のエージェントから使い回す方法を紹介する 25 分のシアター形式の発表です。冒頭に数枚のスライドで考え方を説明し、残りの大半は Fabric IQ 上でのライブデモに充てられています。

デモでは、既存の Power BI semantic model から ontology を作る方法、RDF 形式の既存 ontology（石油・ガス業界のもの）をインポートする方法、完成した ontology を Fabric のデータエージェントや Foundry のカスタムエージェント、Microsoft 365 から使う方法が示されました。発表者は冒頭で、多くの顧客がすでに Power BI のレポートや semantic model を持っていることを出発点にしています。

テーマは「エージェントに渡すビジネスの文脈を、どう作り、どう共有するか」です。発表では、データだけでなく、意味づけ、用語、概念同士の関係、業務ルールまでを含めたものを business context と呼んでいます。Fabric IQ はこの文脈を作るための仕組みで、その中心に ontology が置かれています。

発表の流れは次のとおりです。

## 4. 発表者が伝えたいメッセージ

発表者は「データとメジャー（semantic layer）だけではエージェントには足りない」という立場で話しています。エージェントが正しく判断するには、データの意味、用語の統一、ビジネス概念とその関係、そしてデータの外にあるルールとアクションが必要だという主張です。

もう一つの柱が、**文脈は一度作れば、Fabric 内のエージェントにも、自作のカスタムエージェントにも、Microsoft 365 にも使い回せる**という点です。タイトルの「Build once, ground many」はこのことを指しています。さらに、スタート地点はどの層からでもよく、最初から ontology まで作る必要はないとも述べています。

## 5. 発表内容の詳細

### 5.1 business context とは何か

発表者はまず、context という言葉自体が多義的であると断ったうえで、business context に最低限含めたい要素を順に挙げています。

| 要素 | 発表での説明 |
| --- | --- |
| データ | データベースやリアルタイムイベントから集めた「事実」。business context の中核です。 |
| メジャーとメトリクス | データの上に作る再利用可能な計算。ビジネス上の意思決定に使うもので、データと合わせて一般に semantic layer と呼ばれます。 |
| メタデータ（意味づけ） | 例えば在庫数量が何を意味するのかを記述し、エージェントが理解できるようにするもの。 |
| 共通の語彙 | 1 つのものを別の言葉で呼ぶのは問題ないが、**異なる 2 つのものを 1 つの言葉で呼ぶと問題になる**ため、曖昧さを避けるための用語集です。 |
| タクソノミー | 用語同士が互いにつながっている様子と、ビジネスがその用語をどう使っているかの体系。 |
| 中核となる概念 | スキーマやテーブルではなく、フローやプロセスなど、ビジネスの視点で物事がどう連携するかを表す概念です。 |
| 概念間のリレーションシップ | 主キー・外部キーの関係とは別の、ビジネス概念同士の関係です（データ側にはそうした関係もある、と補足しています）。 |
| ルールとアクション | データの外（人の頭の中、ストアドプロシージャ、ノートブックなど）にあるビジネスルールと、そのルールに紐づく「いつ何をするか」というアクション。 |
| skill へのパッケージ化 | 上記を skill としてまとめ、Fabric や Microsoft のエージェントだけでなく、自作のカスタムエージェントからも使えるようにすること。 |
| フィードバック | 展開したエージェントが skill をうまく使えているか、改善が要るかを文脈に戻し、文脈を継続的に良くしていく仕組み。 |

発表者は、これが「必要な文脈のすべて」ではなく、**始めるための最低限の構成**だと位置づけています。

### 5.2 Fabric IQ の 3 つの層

Fabric IQ は、上記の文脈を作るための仕組みとして、3 つの層で説明されました。

1. **OneLake**：データを保存し、管理し、ガバナンスをかける最下層。
2. **BI / semantic model（Power BI）**：OneLake のデータの上に、メジャーなどを持つ semantic model を作る層。発表者は、多くの人が今すでに使っており、現在のビジネス判断を支えている層だと説明しています。
3. **ontology（operational intelligence）**：ビジネス概念（entity type）、ルール、アクションを載せる層。発表では、ここが public preview の部分だと述べています。

どの層から始めてもよい点が強調されました。テーブルを持つデータベースだけをエージェントに公開してもよく、semantic model を作ってメジャーごと公開してもよく、その上に ontology を作って 3 層すべてをエージェントに公開してもかまいません。いずれも途中で文脈を豊かにしながらエージェントに渡せます。

また、この文脈はエージェントだけでなく、部署や領域をまたいで協力する人間にとっても、ビジネスロジックや判断について一貫した会話をするために役立つと述べています。

### 5.3 出発点となるデータ

デモは「多くの顧客が最初に持っているもの」、つまり Power BI のレポートと semantic model から始まりました。画面には、finance 用の semantic model（顧客や製品などの基本情報を含む）のほか、forecast や product returns などの semantic model が並んでいます。発表者は、こうした semantic model は特定のシナリオ向けに手作りされているのが普通だと説明し、これらを出発点に文脈を作っていくと述べました。

### 5.4 ontology agent で ontology を作る（データ先行のアプローチ）

新しい ontology を作ると、最初は空の画面が表示されます。作り始める方法は複数あり、発表では 2 つが示されました。1 つ目が **ontology agent** の利用です。既存のデータから文脈を作り、管理するのを手伝うエージェントです。

発表者は、semantic model を起点に、あとから lakehouse やリアルタイムデータを加えて文脈を拡張していく流れを取りました。エージェントには、次のような内容のプロンプトを貼り付けています。

- 複数の semantic model を見て、promotion effectiveness（販促の効果）と profitability（収益性）の分析のための文脈を生成する

発表者によると、ontology を生成するときには 2 点を与えます。1 つはドメインとデータセット、もう 1 つは **competency questions**（解きたいビジネス課題や、答えたい問い）です。問いは、具体的すぎても曖昧すぎてもいけず、エージェントが自分で推論できる余地を残すのがよいと説明しています。

処理には数分かかるため、この間に別のデモを進めています。なお、この「既に持っているデータ（semantic model や OneLake）から文脈を作る」方法を、発表者は **data first approach** と呼んでいます。

### 5.5 RDF 形式の既存 ontology をインポートする（model first アプローチ）

2 つ目の方法が **model first approach** です。すでに定義済みのモデルがあり、それを持ち込む場合に使います。ontology は標準のデータモデル言語である RDF（発表では RDF と並べてもう 1 つ言語名が挙がっていますが、音声認識では「OVL」と表記されており、確定できません）で記述されるのが一般的で、業界ごとに 20 年以上かけて、その分野の共通 ontology が作られてきたと説明しています。RDF 形式の ontology があれば、インポートしてそこから始められます。

デモでは、インポートのオプションを選び、ファイルを参照して石油・ガス業界の ontology を取り込んでいます（名称は音声認識で「OSTU」と聞こえますが、確定できません。発表者は、業界全体と協力して石油・ガス向けの ontology を作ったものだと説明しています）。発表者が示した内容は次のとおりです。

- インポート後、画面を縮小すると石油・ガス業界の概念全体が見える。**2,500 を超える型**があり（別の箇所では「2,000 を超える概念」とも発言）、この業界で出会うほぼ全領域をカバーしている。
- 何が失敗したか、何が足りないかを示すログが多数出力される。
- 例として、地震探査のトレースデータ（seismic trace data）の型を拡大し、詳細を開くと、そのプロパティや、地震データの最低要件が確認できる。

ただし、インポートした時点では **「地震データとはこういうものだ」という定義があるだけで、実データはまだ結び付いていません**。実データを ontology に bind して初めてエージェントがクエリできるようになるため、ここで先ほどの data first の手順が必要になると説明しています。

### 5.6 データソースを加えた完成版 ontology

発表者は、semantic model だけでなく、lakehouse と eventhouse も加えて作った完成版の ontology を見せています。構成するデータソースは次のとおりです。

- **semantic model**：売上などのデータとメジャー
- **lakehouse**：silver 層・bronze 層のデータ。注文データや、製品などの詳細を持つ order lines が入っている
- **eventhouse**：出荷（shipment）のテレメトリのリアルタイムデータ。5 秒ごとに、出荷品の温度や湿度の測定値が届く

これらすべてを 1 つの ontology にまとめ、全体にわたる文脈を提供するのが狙いです。完成版では、顧客が複数の注文を持ち、注文は複数のリージョンや出荷（shipment）とつながり、出荷は shipment telemetry につながる、という一連のつながりを画面で順にたどって見せています。

shipment telemetry には、位置情報（geolocation）、温度、湿度などのプロパティがあり、eventhouse のリアルタイムデータソースに直接 bind されています。そのため**クエリすると、バインド先のデータソースからリアルタイムで値が返ります**。一方、shipment のデータは lakehouse に由来し、ontology はこの別々のデータソースを 1 つのビジネス概念としてつなぐ、という説明でした。

> 補足：デモ内で発表者が「pine data」と発言している箇所があり、音声認識の都合で正確な内容が確定できないため、ここでは触れません。

### 5.7 メタデータ、property constraints、metrics

entity type には、次のような情報を重ねられます。

- **メタデータ**：説明文、同義語（synonyms）、追加の key-value ペア。エージェントが entity type を理解し推論するのに使います。
- **property constraints**：プロパティに対する意味づけや制約。例として温度のプロパティを開き、検証に使う最小・最大の範囲（below / above の範囲）と、そのときエージェントが何をすべきかを設定できると示しています。entity type の各プロパティにこの制約を持たせられ、エージェントが推論するときにこれを見て検証します。
- **metrics**：Power BI semantic model の資産を同じ文脈に取り込むための仕組み。semantic model のテーブルや列に加えて、Power BI 向けに作った**メジャーが ontology に metrics として入ります**。デモでは active customers という metric を開き、実際の DAX 式が確認できる様子が示されました。つまり ontology には DAX メジャー、semantic model、リアルタイムデータや lakehouse が一緒に入ります。

### 5.8 生成された ontology の確認と承認

先に始めた ontology 生成が完了すると、エージェントが ontology を作成し、内容を提案してきます。発表者がプレビューを実行すると、左側に生成された ontology が表示されました。発表者が示した点は次のとおりです。

- 概念の重複が無いようにしている。
- semantic model など、プロンプトで指定した既存データソースの文脈をすべて取り込んでいる。
- ダブルクリックすると、概念だけでなくデータソースへの bind も作成されていることが分かる。**ontology は更新した時点でクエリ可能になる**（概念を作るだけでなく、データと生きた状態で接続する）。
- エージェントとやり取りしながら変更を加えることもできる（このセッションではそこまでは行っていません）。

次に、プレビューを承認して更新を開始しました。ここには**人による承認**のステップがあります。発表者は、データからの推論だけでは、相互運用可能な ontology では不十分だと述べています。相反する 2 つのものを統合したい場面があり、エージェントに任せることもできますが、全エージェント向けの文脈層を作る前には、ほとんどの場合で人間の承認が欲しい、という考えです。

### 5.9 ontology の使い方

#### ontology agent での問い合わせ

ontology の構築を手伝う組み込みエージェントは、ontology への問い合わせにも使えます。発表者は、1 つのソースだけでは答えられない質問を貼り付けています（質問の文面は音声からは分かりません）。複数のソースの情報を結び付けて答える必要がある質問で、発表者はこれを「事実を尋ねる質問（factual question）」と呼んでいます。エージェントは、リアルタイムシステム、semantic model のメジャー、lakehouse の値を合わせて最新の値を回答しました。

事実だけでなく、エージェントが利用可能な情報を踏まえて推論する必要のある質問もあります。その推論で重要なのが **rules** です。

#### rules（ルール）とアクション

発表者は、inventory（在庫）のルール（「在庫がリスクになるのはいつか」という内容）を開いています。こうしたルールは通常の言葉で書くだけでは取り込みにくいため、**ルールを自然言語の指示（first class の instruction）として ontology 上で扱えるようにした**と説明しました。ルールを入力し、複数の entity type に直接接続できます。エージェントは該当の型について回答・推論するとき、これらのルールを参照し、守るようにします。

もう 1 つの例として、監視（monitoring）を伴うルールも示しています。ルールに基づいて何らかのアクションを起こす trigger が必要な場合も、同じ場所に設定でき、エージェントがそれを使ってアクションを起動します。

#### data agent

Fabric の組み込みの data agent は、ontology を first class のコンテキストソースとしてサポートしています。デモでは次の流れでした。

1. 「add ontology」をクリックする。
2. favorites の中から作成した ontology を選んで追加する。
3. 追加された ontology は、定義、ルール、メタデータ、ソース横断のリレーションシップといった文脈全体に加え、ontology が接続している実際のデータソースも同時に受け取る。
4. 先ほどと同じ質問を data agent に尋ねると、同様のクエリができるはず、と説明している（実行は裏で進めており、結果の説明は発話に出てきません）。

#### operations agent

operations agent は、ontology にあるルールをもとにアクションやトリガーを作るためのエージェントです。ontology を knowledge source として追加し、その上でトリガーとアクションを作成できます。こちらはデモではなく口頭での説明でした。

#### カスタムエージェント（MCP endpoint）

Fabric の外にあるカスタムエージェントは、**すべての ontology が MCP endpoint を持つ**ため、そこから使えます。文脈層全体に対して、ツールは `ask ontology` の 1 つです。デモでは Foundry のカスタムエージェントを使っています。

1. Fabric IQ をクリックする。
2. 自分の ontology を選択する（絞り込みもできる）。
3. 裏側では同じ MCP endpoint に接続している。
4. 先ほどと同じ質問を投げると、`ask ontology` を呼び出してクエリする。
5. trace を見ると、どのツールが呼ばれたか、何トークン使われたかなど、オブザーバビリティの様子が分かる。

#### skill

ontology 向けの skill も用意されています。skills に対応していれば、他のエージェントにインストールできます。発表者は、skills for fabric リポジトリに、ontology を利用する（consumption）ための skill があると説明しています（インストール手順は発表では示されていません）。

#### Microsoft 365

現在の ontology は構造化データが中心で、semantic model、lakehouse、warehouse、mirrored database、eventhouse が連携する様子を理解できます。一方、非構造化データにも多くの文脈があり、それを構造化データと組み合わせる場面で Microsoft 365 が登場します。発表者は、**early preview の段階で、ほとんどの顧客に対して「来週から」利用可能になる**と述べています。

M365 Copilot にはすでに非構造化データのインデックスがあり、そこで ontology が first class の項目として自動的にインデックスされ、同じ体験の中でクエリできるようになります。Office、SharePoint、OneDrive と、ontology でモデル化した構造化データを一緒に問い合わせられます。デモでは、operations の ontology を使ってキャンセルされた注文をすべて取得したあと、同じ文脈で「これらの注文に関連して受け取ったメールをすべて出して、要約してほしい」と依頼しました。結果の画面の詳細は音声からは確認できません。

検索の画面でも、ontology は検索対象の first class の種別として絞り込みができます。ontology を作成するたびに自動でインデックスされ、すべての M365 の利用体験から使えるようになる、とのことです。

### 5.10 生成した ontology の完成確認

最後に、冒頭で始めた ontology の生成が完了したことを確認しました。region という型が作られ、クリックすると binding とメタデータが確認できます。「show me all the regions」と尋ねて、クエリできることを確かめようとしています（クエリ結果は発話では語られていません）。発表者は、**文脈層がデータにライブでバインドされており、直接クエリできる**ことがゴールだとまとめています。

## 6. デモ・手順

このセッションの大半はライブデモです（「ライブデモに時間を使う」と冒頭で宣言しています）。画面の細部は音声からは確認できないため、語られた範囲で、行われた順に整理します。

1. Power BI の semantic model の一覧（finance、forecast、product returns など）を見せる。
2. 新しい ontology を作成する。最初は空白の画面。
3. ontology agent に、複数の semantic model を見て promotion effectiveness と profitability analysis の文脈を作るよう指示するプロンプトを貼り付けて実行する（処理に数分かかる）。
4. 別の方法として、RDF 形式の ontology をインポートする。石油・ガス業界の ontology を参照して取り込み、2,500 を超える型を表示。seismic trace data の型を拡大してプロパティを見せる。
5. 生成処理が進んでいること（semantic model のスキーマを取得中で、入力待ちなどで止まっていないこと）を確認する。
6. lakehouse（注文データと order lines）と eventhouse（出荷テレメトリ、5 秒ごと）を含む完成済みの ontology を見せる。顧客、注文、リージョン、出荷、shipment telemetry とたどり、telemetry が eventhouse に bind されていることを示す。
7. entity type のメタデータ（説明、同義語、key-value）、温度の property constraints、metrics（active customers と DAX 式）を見せる。
8. 生成処理の完了を確認し、プレビューで重複の無さと data source への bind を確認する。
9. 人による承認として更新を開始する。
10. 組み込みの ontology agent に、複数ソースにまたがる質問を投げて回答を得る。
11. inventory の rule を開き、複数の entity type に接続したルールを見せる。監視を伴うルールも見せる。
12. data agent で「add ontology」から ontology を追加する。
13. Foundry のカスタムエージェントから Fabric IQ と ontology を選び、同じ質問を投げて `ask ontology` が呼ばれるのを見せる。trace で呼び出されたツールやトークン数も確認できる。
14. Microsoft 365（early preview）で、キャンセル注文を取得し、関連するメールを要約するよう依頼する。検索画面で ontology の絞り込みも見せる。
15. 作成が完了した ontology で region の型の binding とメタデータを見せ、「show me all the regions」と尋ねる。

## 7. 注意点・発表者の気付き

- ルールは、データの外（人の頭の中、ストアドプロシージャ、ノートブックなど）にあることが多く、意思決定を左右するので、文脈に取り込む必要があるという指摘です。
- 用語は「異なる 2 つのものを 1 つの言葉で呼ぶ」ことが問題で、これを避ける共通語彙が要るという考えです。
- competency questions は、**具体的すぎず曖昧すぎない**ほうが、エージェントが自分で推論できると説明しています。
- ontology の生成では、データからの推論だけでは足りない場面があり、ほとんどの場合で人間の承認が望ましい、と述べています。
- RDF などの既存 ontology をインポートしただけでは、定義があるだけでデータと結び付いていません。実データを bind して初めてエージェントからクエリ可能になります。
- ontology は現在 public preview で、Microsoft 365 での利用は early preview です。
- 今回の文脈の構成は「始めるための最低限」であり、これが唯一の文脈ではないと断っています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **どの層からでも始められる**：テーブル、semantic model、ontology のどこからでも文脈を豊かにして、エージェントに渡せます。
- **既存の Power BI 資産を生かせる**：semantic model のメジャーが DAX 式のまま ontology の metrics として取り込めます。
- **複数のデータソースを 1 つのビジネス概念に結び付けられる**：semantic model、lakehouse、eventhouse（リアルタイムデータ）をまたいで、実データとバインドしたままクエリできます。
- **業界標準の ontology を活用できる**：RDF 形式の既存 ontology をインポートして始められます。
- **文脈を一度作れば、複数のエージェントで共有できる**：data agent、operations agent、MCP endpoint 経由のカスタムエージェント（例：Foundry）、skill、Microsoft 365 から利用できます。
- **人も恩恵を受ける**：部門をまたぐ協力で、ビジネスロジックや意思決定について一貫した会話ができます。

数値としての効果指標や、顧客の導入事例は、このセッションでは紹介されていません。

## 9. まとめ

business context は、データとメジャーだけでなく、意味づけ、用語、概念とその関係、ルールとアクションまでを含むものだ、というのがこの発表の出発点です。Fabric IQ では、OneLake、semantic model、ontology の 3 層でこれを作り、どの層からでも始められます。

デモでは、semantic model から ontology agent で ontology を作る data first の方法と、RDF の既存 ontology を取り込む model first の方法を示しました。完成した ontology は、データソースにライブでバインドされたまま、data agent、operations agent、MCP endpoint 経由の Foundry エージェント、skill、Microsoft 365 から使えます。ontology は public preview、Microsoft 365 との連携は early preview という位置づけです。
