## 4. 発表者が伝えたいメッセージ

Brian 氏は、要点を 3 つにまとめています。

1. **エージェントの有用性は、アクセスできる情報で決まる**：モデルを賢くするだけでは足りない。今朝公開されたセキュリティアドバイザリや、昨日発表された規制変更は、モデルの中にない。取得する必要があり、Web IQ は出典情報付きの新しい根拠（evidence）を返す
2. **質問ごとに必要な情報の種類は違う**：ニュース、Web ページ、特定の URL、画像、動画、場所の情報。個別のエンドポイントも、auto も使える
3. **グラウンディングはエンタープライズの規模で機能する必要がある**：品質、速度、効率、コンテンツに対する責任ある扱い。モデルが必要とする情報だけを取り出し、余計な文脈を渡さない

さらに、**Web IQ が根拠（evidence）を取得し、モデルが回答を生成する**という役割分担が重要で、アプリケーションが次に何をするかを決める、と述べています。モデル、アプリケーション、業務ロジックの制御を手放さずに最新情報の利点を得られる、という設計の考え方です。

もう 1 つのメッセージは、AI 変革でも、すべての業務プロセスを作り直す必要はないという点です。すでにうまく動いているプロセスに、これまで得られなかった情報を渡すのが最も強力な場合があり、古いモデルを使えば非常に安くできる、と Brian 氏は述べました。

## 5. 発表内容の詳細

### 5.1 グラウンディングとは

Brian 氏は、天気を例にしています。モデルは昨日までの学習データから、明日の天気を知ることはできません。そこで、モデルがクエリを Web IQ のようなグラウンディング API に送り、API がウェブから最も関連する情報を取得してモデルに返します。モデルはこの情報を使って、出典付きの正しい最新の回答を作ります。Brian 氏は、事実に引用を付けたいので「evidence（根拠）」と呼んでいます。

**Web IQ は、AI エージェントが必要なときに外の世界の情報を得るための、Microsoft の Web グラウンディングレイヤー**と説明されています。「ただの Web 検索ではないか」という疑問には、従来の Web 検索は主に人がウェブサイトを探すために設計されたもので、グラウンディングはエージェントがタスクを完了するための情報を渡すものだと答えています。

### 5.2 エンドポイントと auto

ウェブは 1 種類ではなく、質問ごとに必要な情報が違います。Brian 氏は旅行アシスタントを例に、週末の Tokyo の出来事なら最近のウェブ情報、ホテルの見た目なら画像、近くのレストランなら場所の情報が必要になると説明しました。

Web IQ には、用途別のエンドポイントがあります。

| エンドポイント | 用途 |
| --- | --- |
| web | ウェブの情報 |
| news | ニュース |
| images | 画像 |
| videos | 動画 |
| browse | 特定の URL の内容を取得（質問に対する passage も返せる） |
| places | 物理的な場所の情報 |

Q&A では、このほかに weather と、ショッピング向けの commerce もあると説明されています。今回のカンファレンスでは、commerce まわりの機能が追加発表されたとのことですが、詳細はこのセッションでは語られていません。各エンドポイントは構造化された結果を返し、出典情報も含まれるため、アプリケーション側で帰属表示ができます。

**auto** は、すべてを包む単一の入口です。質問を送ると、Web IQ が適切な取得機能を選び、ときには複数を組み合わせます。単純な質問には速度と効率を優先する **fast モード**、複雑な質問には複数回の反復で必要な情報を探す **advanced モード**があります。精密に制御したいときは個別のエンドポイント、オーケストレーションを任せたいときは auto を選ぶ、という使い分けです。

### 5.3 品質・速度・効率

Brian 氏は、グラウンディングの価値は次の 3 点だと述べています。

| 観点 | 発表された内容 |
| --- | --- |
| 鮮度（quality fresh data） | 社内の fresh search evaluation で、Web IQ の auto は **87.5** のスコアで、評価した他のプロバイダーを上回った。意図的に難しい尺度にしてあり、100 には届かない（Brian 氏自身も改善の余地があると述べている）。情報が古いと、誤りに気づきにくい「silent failure」になる、という指摘 |
| 速度 | 世界 8 リージョンのベンチマークで、検索処理は **P95 で平均 154 ミリ秒**。比較したエンジンのうち次に速いものの**約 2 倍速い**（品質は同等でないとのこと）。エージェントは複数回呼び出すことがあるため、待ち時間がそのままタスクの遅れになる |
| 効率 | 評価した他のプロバイダーに対し、品質とトークン効率のバランス（quality to token efficiency frontier）で先頭にある |

> 注意：これらは Microsoft の社内評価・ベンチマークの数値で、条件の詳細は発表では語られていません。

### 5.4 passages

**passages** は、コードで content format を指定して有効にする機能です。Brian 氏は、Golden Gate Bridge の料金支払い方法という質問を例にしました。Web IQ が見つけたページには、ナビゲーションや背景情報など、質問に関係のない内容が数千語含まれます。そのまま LLM のコンテキストに渡すとコストが増えます。content format に passages を指定すると、Web IQ はページの中から質問に関連する部分だけを返します。

この例（illustrative、つまり説明用の例）では、ページ全体で約 12,000 トークン、passage では約 750 トークンで、**約 94% 少ない**トークンで必要な情報を保てます。Brian 氏は、今週ある別のパートナーから、Web IQ に移行したら、トークンと GPU・推論コストの削減で元が取れたと聞いたとも述べています。数百万回のグラウンディング呼び出しでは、不要なトークンが総所有コストを押し上げる、という考えです。

### 5.5 scopes（Ignite で新規発表）

**scopes** は、Web IQ が取得してよい情報源を開発者が制御する機能です。Brian 氏は、自動車ブランドの AI アドバイザーを例に挙げています。匿名の掲示板と公式の製品ドキュメントを同列に扱うべきではなく、信頼できない情報源に基づいて自社の車両について主張すべきでもない、という問題意識です（前日に Toyota と同じステージに立ったとも述べています）。

- 自社の公式ドメイン、信頼できるパートナー、承認済みのサイトを **include** に、最大 10,000 ドメインまで指定できる
- 要件に合わないソースを **exclude** に、最大 10,000 ドメインまで指定できる
- 以前の custom search 機能は、約 450 ドメインが上限だった
- include と exclude の両方に入れた場合は **exclude が優先**される
- 制御の粒度は、ドメイン、サイト、URL、パスのレベル
- プログラムから動的に設定できる（Q&A での説明）

取得してから絞り込むのではなく、取得前に信頼する情報の境界を決められる、という利点が語られました。自動車なら公式ドキュメントで製品情報を根拠づけ、独立したレビューは他の承認済みソースから取る、金融なら規制当局への提出書類や承認済みの金融出版物に限定する、といった使い方が例として挙げられています。

### 5.6 ZQL（zero query logging）

エージェントのクエリには、業務プロセスや運用上の問題など、組織が取り組んでいる内容が含まれる可能性があります。目的が公開情報の取得であっても、そのクエリがどう扱われるかを企業は把握する必要があります。そこで追加されたのが **ZQL** です。標準では、サービスの通常運用の一部としてクエリがログに記録されることがありますが、ZQL を有効にすると、Web IQ はサービスログにクエリを残しません。取得に使う情報源は変わりません。

> 注意：Brian 氏は、ZQL は良いアプリケーション設計の代わりにはならず、機密情報を不必要に送らないようにする必要があると述べています。

### 5.7 National Grid の事例

Brian 氏は、National Grid を、信頼性、運用の規律、最新情報へのアクセスが重要な（さもないと停電になる）環境と紹介しました。すべてを AI で作り直すのではなく、既存のワークフローを賢くする形で Web グラウンディングを取り入れている、という説明です。その後、同社の取り組みを紹介するビデオが流れましたが、ビデオの内容はトランスクリプトに含まれていません。

Lou 氏はまず、これまでのウェブ情報の取得方法を振り返りました。

- 2020 年に RAG が登場し、すべてはそこから始まったと Lou 氏は感じている
- Python の requests ライブラリと Beautiful Soup、PowerShell の Invoke-WebRequest や Invoke-RestMethod、動的ページには Selenium を使ってきた
- ページが変わると処理が壊れ、ページ構造（div と段落、section や article など）の違いを手作業で解析する必要があり、保守が大変。取得後にデータのクリーニングも必要になる
- robots.txt、no snippet、no archive、no cache などの制御は、どれも**自主的なもの**で、スクレイパーを止める手段にはならない。ファイアウォールのルールで防ぐと、通したいスクレイパーまで止める可能性がある
- 検索 API が登場したが、RAG 向けに作られておらず、通常の検索向けのものがほとんどだった。そこに Web IQ の強みがある、という見方

現在の Microsoft 製品については、Foundry のエージェントには Grounding with Bing、Copilot Studio には web search、ノーコードのエージェントビルダーにも web search 機能があると説明しています。Lou 氏は、これらは Bing の従来の検索機能を使っており、最終的にはすべて Web IQ に切り替わる計画だと**自分は理解している**と述べました（当面の焦点は Foundry だと思う、という個人の見立てです）。

Lou 氏が検討している Web IQ のユースケースは次のとおりです。

- 現在は Downdetector を使い、システムの障害を Teams チャンネルに流し、重大インシデント管理チームへの通知などの自動化につなげている。ITSM のプラットフォームから CI やシステムを取り出して Web IQ に送り、**ライブの障害検知**を行うことを考えている
- 数千ある knowledge article を、Web IQ で自動的に充実させる
- セキュリティアドバイザリの影響、OS やアプリの更新の準備状況

自動化を proactive（誰かが気づく前に直す）、reactive（フォーム起点が多い）、background（重大インシデント対応のようなバックグラウンド処理）の 3 種類に分けて考えているとも述べています。

アーキテクチャについては、呼び出し側はエージェントでもコードでもよく、Web IQ には **MCP サーバーと REST API** があると説明しました。取得したコンテンツは、passages、テキスト、Markdown、HTML で抽出できます。

### 5.8 まとめの部分と GA

Brian 氏は、数百社が Web IQ を選んでおり、その中には ChatGPT や Mistral など主要な AI エージェントも含まれると述べました。Web IQ は Ignite で **generally available** として発表され、利用できます。

### 5.9 Q&A

| 質問 | 回答の要点 |
| --- | --- |
| scopes でカテゴリ（ギャンブルサイトなど）で除外できるか | カテゴリ単位ではできない。良い機能案なのでチームに持ち帰る。カテゴリの定義は業界や人によって恣意的になりうるため、最大限の自由度を優先した。自社でギャンブルサイトのリストを作って渡せるし、各国政府が公開している一覧もある。scopes はプログラムから動的に設定できる |
| 取得はテキストだけか、マルチモーダルにも対応するか | 対応する。web、images、videos のほか、places、weather、shopping 向けの commerce もある。auto は複数の種類を組み合わせ、どれが最も関連するか判断する。Brian 氏の例は、ロンドンの Heathrow 空港から Windsor Castle に 7 時間で行けるかという質問で、結果には、要人の公式訪問（state visit）に関するニュースと、住所を確かめるための places の情報も含まれていた（ニュースの語は聞き取り不明瞭）。画像や動画のデータ自体ではなく URL を返す（画像は thumbnail server の URL、動画は元サイトの URL）。LLM やエージェントはその URL を使って表示できる |
| Web IQ、Work IQ など複数の IQ を組み合わせる必要があるか | **Microsoft IQ** という包括的な capability があり、Work IQ、Fabric IQ、Foundry IQ、Web IQ を含む。それぞれ役割が違い、組織ごとに組み合わせは変わる。自社データや業務の文脈に、ウェブの情報を加えるとよい。Web の情報を LLM に渡すと、社内文書の略語など「inside baseball」が補われ、社内向けの回答が正確になる |
| Lou 氏の立場から、コストと投資の見合いはどうか | Lou 氏は費用対効果が高いと答えた。関数に API 全体を実装するのに約 30 分しかかからず、30 分の手間で任意のモデルに RAG ができる。これらの関数を GitHub に置く案も話題に上っている（確定した話ではない）。LLM に渡さない使い方（結果をループして特定のキーワードを探す、Teams チャンネルに流してメールを送る）もある。価格は、「1,000 コールあたり 1 ドル」「browse」「1,000 あたり 7 ドル」という発言があったが、どの機能の価格か聞き取り不明瞭 |
| ローコード・ノーコードのエージェントで、personality（指示）をどう書けばよいか | Lou 氏は、今回のエージェントの personality は Copilot に作らせたと説明。Web IQ の説明のリンクとデモの目的を伝えただけで生成され、中身は単純な Markdown。まず Copilot で基本を作り、そこから調整するとよい |

## 6. デモ・手順

Lou 氏が 2 つのデモを行いました。画面の細部は音声からは確認できず、以下は語られた内容に基づきます。

> 補足：モデル名と関数名は、音声認識の都合で表記が確定できません。トランスクリプトでは、軽量モデルが "4.1.nano"、大きいモデルが "6" / "6 chat"、関数名が "ask AOI" / "ask AOI web"、ツールの名前が "Studio" と書き起こされています。

### 6.1 デモ 1：ノーコードのエージェントに Web IQ MCP を追加する

Lou 氏が飛行機の中で約 5 分で作ったというエージェントです。

1. 画面は "Studio" と呼ばれたエージェントの作成画面。instruction（指示）を Lou 氏は「personality」と呼ぶ。実体は system prompt
2. 組み込みの web search を**オフ**にし、代わりに **Web IQ MCP** を追加する
3. 「Ignite 2026 から出てきた Web IQ の最新ニュースは何か」と質問する
4. 左側に、エージェントが MCP サーバーを呼び出す必要があると判断する内部の動きが表示され、Web IQ からの応答が返ったあと、右側にレンダリングされる。最後に、直接の回答と key findings が表示された
5. system prompt で出典（sources）を付けるように指示してあった。このエージェントを公開し、当日の朝には「株式市場の最新ニュース」を質問して、ライブのエージェントにデータが返ることを確認した
6. Lou 氏の経験では、組み込みの検索より質の高い回答が得られる。エージェントに Web 検索を統合するなら、MCP サーバーとして Web IQ を試す価値がある

### 6.2 デモ 2：PowerShell のスクリプトに AI と Web IQ を組み込む（AI infusion）

Lou 氏は、すでにあるプロセスやスクリプトに AI を組み込む考えを "AI infusion" と呼び、Frontier に向けてバックグラウンドエージェントが増える流れの中でも、現時点で最も価値があると感じていると述べています。コードは、古い PowerShell ISE で見せました。VS Code が不調だったためです。

1. 冒頭にこのセッションに関する質問がある。LLM を任意に呼び出して質問を渡す関数（ask AOI）と、measure command のラッパーである show latency 関数（レイテンシをマゼンタで表示）を使う
2. 軽量モデル（4.1 nano）は、このセッションで何があったかを知らない。パラメーターでモデルを切り替えて大きいモデル（"6"）に変えると遅延が大きくなり、Lou 氏の説明では約 3 倍遅い。大きいモデルもセッションの内容は知らない
3. Foundry の既存のモデルで使える **JSON mode** を見せる。「フランスの首都は何か。JSON で、answer、confidence、score を返して」と質問すると、すぐに応答が返る
4. 返ってきた JSON は文字列なので、オブジェクト形式に変換する。すると、プロパティをドットでたどれるようになり、answer（Paris）を取り出せる。これは Web IQ とは別の話で、あらゆるコードに AI を組み込み、構造化された JSON を受けて、コード内の判断に使えるという意図
5. Web 版の関数（ask AOI web）を実行する。同じ質問（このセッションについて）を渡すと、結果が 5 件返る（件数はパラメーターで指定）。結果は auto でランク付けされ、上位の結果を開いて内容を確認できる。出力形式はテキストで、content format を passage にして再実行すれば、ページ全体ではなく passage が得られる
6. Web の結果をモデルに渡すため、**return AI response** という Boolean のパラメーターを追加した。また、Web IQ が標準で提供する機能を拡張して、**複数の vertical を同時に呼ぶ**機能も付け、ここでは web と news を指定した（それまでは web のみ）。実行すると、Web IQ の結果が 4.1 nano に渡され、元の質問に対する簡潔な回答が返る
7. コストの最適化として、まず 4.1 nano に「Web で補強する必要があるか」を判定させる。
   - 「New York の州都は」と質問すると、Web IQ は不要と判定され、Albany と答える
   - 「Ignite 2026 の Web IQ の最新情報は」と質問すると、4.1 nano は答えを知らないため、コードが自動で Web IQ を呼び出し、RAG による補強が行われる

Lou 氏がデモに 4.1 nano を使った理由は、学習が 2024 年に終わっていて 2 年以上前の知識しかない一方、入力トークンのウィンドウが大きく、高速だからです。Web IQ で補えば、「I think GPT-6」と発言した大きいモデルに近い、あるいはそれ以上の性能が得られるというのが Lou 氏の見方です。

## 7. 注意点・発表者の気付き

- **ZQL は万能ではありません。** 機密情報を不必要に送らないという、アプリケーション側の設計は引き続き必要です
- 掲載された数値（鮮度のスコア 87.5、P95 の 154 ミリ秒、passages の約 94% 削減）は、Microsoft の社内評価と説明用の例です。passages の 12,000 トークンと 750 トークンは「illustrative」と断られています
- scopes にはカテゴリでの除外がありません。カテゴリの定義が人や業界で異なるためで、除外したいサイトのリストは利用者側で用意します
- 画像と動画は、データではなく URL が返ります。表示は、エージェントやアプリ側で行います
- 現在の Foundry、Copilot Studio、ノーコードのエージェントビルダーの web search が将来 Web IQ に切り替わるという話は、Lou 氏個人の理解として語られたもので、Microsoft 側の計画として発表されたものではありません
- ライブデモには細かなトラブルがありました。Lou 氏は VS Code の調子が悪いと述べて PowerShell ISE を使い、Teams を終了してしまったと話しています。Brian 氏もデモのあとで、少しトラブルがあったと触れています（トランスクリプトの表記は "demo hail"）。Q&A の最中にも、Lou 氏がボタンが反応しないと話す場面がありました

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 最新の情報を、出典付きで取得でき、利用者に「その情報をどこから得たか」を示せる
- passages により、トークン、GPU、推論のコストを削減できる（例：約 12,000 トークンから約 750 トークン）
- scopes と ZQL で、取得元とクエリの扱いを制御できる
- 既存のプロセスやスクリプトに少ない手間で組み込める。Lou 氏は、実装にかかった時間は約 30 分だったと述べている
- 古い、安価なモデルでも、Web IQ で補えば最新の情報に答えられる
- LLM に渡さない用途（キーワード検索、Teams への通知、メール送信）にも使える（Lou 氏）
- Web の情報が、社内文書の略語などを補い、回答の正確さを高める（Brian 氏の説明）

## 9. まとめ

Web IQ は、AI エージェントに最新のウェブ情報を出典付きで渡す Microsoft の Web グラウンディングレイヤーで、Ignite で一般提供が発表されました。個別のエンドポイントと auto を使い分けられ、passages によるトークン削減、scopes による情報源の制御、ZQL によるクエリログの抑制が、エンタープライズ向けの特長として説明されました。

National Grid の Lou 氏は、ノーコードのエージェントへの MCP 追加と、PowerShell の既存コードへの組み込みを、ライブデモで示しました。役割分担は、Web IQ が根拠を取得し、モデルが回答を生成し、アプリケーションが次の処理を決める、というものです。なお Q&A では、Web IQ を単独ではなく、Work IQ、Fabric IQ、Foundry IQ とともに含む Microsoft IQ の一部として使う考え方も紹介されました。
