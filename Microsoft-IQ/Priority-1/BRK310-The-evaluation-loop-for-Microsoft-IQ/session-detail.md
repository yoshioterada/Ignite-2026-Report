# BRK310 The evaluation loop for Microsoft IQ

## 1. はじめに

このセッションは、Microsoft IQ でコンテキストをつないだエージェントの品質を、どうやって測り、継続的に改善していくかを扱います。登壇者は冒頭で、答える問いを 1 つに絞っています。「コンテキストを使うエージェントを、どうすれば継続的に改善できるか」です。

内容は大きく 2 部構成です。前半は Divya 氏が、トレース、golden data set、evaluator（評価器）を使って、リリース前の品質基準とベースラインを作る流れをデモします。後半は Ahmad 氏が、本番運用後に、continuous evaluation、新しい評価用モデル（Decision Model 1.1）、insights、optimization で、劣化を検出して直す流れをデモします。発表全体の主張は、評価を回して品質の変化を測り、改善を重ねていくことです。なお、公式概要には「評価によって、コンテキストエンジニアリングを当て推量から、データに基づく反復的な実践に変える」と書かれています。

## 3. 何に関する発表か

背景として、登壇者は次のように話しています。どの組織もフロンティアモデルにアクセスできるため、差を生むのは、人々の働き方、事業の運営、組織内の知識といった**コンテキスト**です。Microsoft IQ は、エンタープライズ向けのコンテキスト管理プラットフォームで、次の 4 つの部分から成ると説明されています。

| 構成要素 | 役割（発表での説明） |
| --- | --- |
| Web IQ | Web へのタイムリーなアクセス |
| Work IQ | 人々がどう働いているかの情報 |
| Fabric IQ | 事業がどう運営されているかのデータ |
| Foundry IQ | 組織の知識のリポジトリ |

エージェントを作るたびに事業の仕組みを説明する必要はなく、エージェントを接続するだけでよい、というのが狙いです。ただし、接続しただけでは足りません。発表の流れは次のとおりです。

1. 何がうまくいかなくなるか（retrieval とエージェントの問題）と、observability の考え方
2. 前半（Divya 氏）：traces、golden data set、evaluator、offline evaluation、monitoring のデモ
3. 後半（Ahmad 氏）：continuous evaluation、Decision Model 1.1、insights、optimization のデモ
4. ドキュメントへのリンクと関連セッションの案内

## 4. 発表者が伝えたいメッセージ

メッセージは「**エージェントが期待どおりに動いているかを、評価で継続的に確かめるループを作る**」ことです。登壇者は、従来の observability が「動いているか、速いか、エラーはないか」に答えてきたのに対し、エージェントでは **"is it doing the right thing?"（正しいことをしているか）** という問いが加わると説明しています。同じ依頼を 2 回すると違う答えが返ることがあり、ダッシュボードは良好でも、エージェントは自信を持って誤った答えを返しているかもしれません。こうした**振る舞いの誤り**を捉えるのが evaluations で、observability の一部に加わった、という位置づけです。

## 5. 発表内容の詳細

### 5.1 問題の整理：何がうまくいかなくなるか

コンテキストをつないでも、問題は複数のレベルで起こります。

- **Retrieval**：役割は、適切な情報を見つけ、最も関連する情報を上位に持ってくることです。しかし、適切な情報を見つけられない、LLM が最も注意を払いにくい「中間」に情報が埋もれる、ノイズが多すぎて答えが埋もれる、といったことが起こります。
- **エージェント**：情報は受け取っても、見落とす、誤って表現する、コンテキストではなくモデル自身の知識から事実を付け足す、といったことが起こります。

対策としては、文書の前処理で情報を正しく取り込む、retrieval モデルの reasoning strength を見直す、より良いモデルを使う、などがあります。ただし、どの決定にも**レイテンシ、コスト、品質のトレードオフ**があり、「品質が本当に良くなっているかをどう知るか」が残ります。これに答えるのが今日のテーマです。

業界の状況として、次の 2 つの数字が挙げられています。

- ある業界調査では、回答者の **32%** が、品質がエージェントを本番に出す際の大きな障壁だと答えた。
- Gartner によると、本番稼働したエージェントの **40%** が、**2027 年末までに無効化される**。理由は、コストの暴走、価値を証明する能力、リスクを管理する能力の 3 つ。

これを解決するのが observability で、評価を含めて 4 つの問いのループとして捉えます。

| 問い | 内容 |
| --- | --- |
| 1 つ目（Build） | 見えて、測れるか |
| 2 つ目 | 動いているか、問題はないか（従来の observability） |
| 3 つ目（Detect） | 本番のトラフィックで正しく振る舞っているか |
| 4 つ目 | どうすればより良くし続けられるか |

評価は、このループの強調された各部分に関わります。エージェントのライフサイクルを通じて、このループを継続的に回します。

### 5.2 Build：トレース

トレースは、エージェントが行う各ステップ・各アクションを記録するものです。

- Foundry 上のエージェント（prompt agent または hosted agent）は、トレースが自動で有効になる。トレースの保存先である App Insights を接続すればよい。
- Foundry の外でホストされるエージェントも、トレースを Foundry の observability に送り、評価などを使える。この機能は「今日から」一般提供（GA）。
- 外部エージェントでは、Microsoft の OpenTelemetry 系ライブラリ（トランスクリプトでは "Microsoft Hotel Distro Library" と聞こえますが、音声認識の都合で表記が確定できません）を数行のコードで追加すると、トレースが自動でインストルメントされる。
- Azure Monitor の App Insights を使っている場合は、アプリケーションの insights とエージェントの insights を 1 か所で見られる。

### 5.3 Build：golden data set

トレースを土台に、次は品質のベースラインを作ります。そのために **golden data set**（エージェントが取りうる行動を代表する、多様な分布のクエリの一覧）を使います。エージェントをそれらのクエリで動かし、結果を評価してスコアにします。

- 作成方法：synthetic data の生成、トレースからの送り込み（任意の属性で検索できる高度なフィルターがある）、既存データのアップロード。
- **専門家の知識**を入れる場所でもある。トレースをデータセットに送る際に、ground truth（そのクエリの期待）と、エージェントが何を誤り、何を正しく行ったかのフィードバックを付けられ、評価の入力になる。
- 高度な評価向けに **task-level evaluator** を追加できる。特定のタスクを行うトレースの部分集合に対して、そのタスクが行われたかを追加でチェックするもので、全体に適用する汎用の評価の代わりに使う。これは「今日から」の新機能。

### 5.4 評価の 3 つの方法と、新しい発表

エージェントの良し悪しを判定する方法は 3 つあります。

| 方法 | 特徴 |
| --- | --- |
| Code-based evaluation | 答えが決定論的な場合に使う（例：tool call の schema の確認）。安く、速い。 |
| Model-based evaluation | LLM でトレースを判定する。コスト効率が良く、複数の観点で見られる柔軟性もあり、最も使われている。 |
| Human evaluation | 最良だが非常に高価。専門家がすべてのトレースを見る。使うのはごく一部の場合。 |

今日は model-based evals に時間を割くとして、次の発表が紹介されました。

- 組み込みの evaluator は約 **60 個**。
- **voice evaluator** の導入（音声エージェントの品質確認に使える）。
- **rubric evaluator**。ゼロから evaluator を作るのは難しく、品質の観点はエージェントごとに異なるため、エージェントのコンテキストを見て、そのエージェント専用の evaluator を作る仕組み。品質向けは数か月前に導入済みで、今回、**安全（safety）向けの rubric evaluator** が使えるようになった。
- スコアの付け方として、Likert 形式（音声では "Lickhart" と聞こえます）に加え、**Boolean** にも対応した。

### 5.5 Monitoring（エージェントのポートフォリオ監視）

品質以外の問題を見るため、プロジェクト全体にわたる **monitoring** が発表されました。トレースとメトリクスを有効にすると、ヘルス、品質、コストを 1 か所で見られます。詳細は 6.5 のデモで説明します。

### 5.6 内側のループと本番のループ

Ahmad 氏は、前半の内容（良い evaluator、golden data set、オフラインの評価）を **inner loop（closed loop）** と呼び、ローカルで反復して、品質指標が満足できる水準になれば本番に出す段階だと整理しました。ただし、本番はローカルのテストとは別の話です。ユーザーがどのようにエージェントを使うかは分からず、テキストでも音声でも動画でも、ユーザーにこう使ってはいけないと言うガードレールもありません。例として、他人の代わりに航空券を予約する、顧客に提供されるはずのない「隠れた航空券」を探す、といった使い方を挙げています。そこで、本番に出したエージェントを**継続的に評価する（continuous evaluation）**必要があります。

### 5.7 Decision Model 1.1

Microsoft が評価用に提供する新しいモデルとして、**Decision Model 1.1** が紹介されました。

- チャットモデルではなく、自然言語で質問に答えない。
- 送るのは **state**（顧客のクエリ、エージェントの応答、会話全体など）と、**typed questions**（型付きの質問）。モデルは state に基づいて、決定と確率（信頼度）を返す。
- 質問の型は、true/false（例：緊急か）、choice（複数の選択肢から選ぶ、例：担当チーム）、score（指示と選択基準を与えて優先度を決める）。送信はチャットモデルへの送り方とは違い、API で扱う JSON オブジェクトとして行う。
- **非常に速く、非常に安く、大規模に実行できる**。一方、欠点は、判断の理由をモデルが説明しないこと。
- トークン消費：デモでは、Decision Model の completion tokens は **12** で無視できる程度。同じ評価をチャットモデルで行うと約 1,100〜1,200 トークンで、約 **100 倍**。登壇者は、Decision Model は平均して評価のトークンを **100 倍から 200 倍**節約できると述べています。

### 5.8 Insights と optimization

評価指標が緑でも、カスタマーサポートから「想定していなかった問題がある」と連絡が来ることがあります。評価者が事前に想定していなかった問題を、**systematic に**見つけ、劣化（regression）を防ぐのが insights です。

- エージェントの insights タブで、live traffic に対して問題を見つけるモデルを設定する。
- 優先して探す問題の種類は、多くのエージェントに共通する 8 種類が提案される（コストとトークン、hallucination、tool failures、risk と compliance など）。追加やカスタムカテゴリも可能。
- 加えて自由な指示を与えられる（例：旅行予約システムを悪用する人を優先、重要度の低い insight は無視、など）。
- 保存するとバックグラウンドで動き、問題を high / medium / low で順位付けして出す。

また、プロンプトを直してゴールデンデータで試して本番に出す、という「もぐらたたき」ではなく、**この流れを systematic にする**のが optimization の狙いだと説明されています。

## 6. デモ・手順

このセッションには**画面を使ったデモ**があります。音声で語られた範囲のみを書き、画面の細部は音声からは確認できません。デモのエージェントは、**フライトとホテルの予約を行う出張（travel）エージェント**です。

### 6.1 デモの対象エージェント（Divya 氏）

1. 目的は、フライトとホテルの予約。すべてがポリシーの範囲内であることを確認する必要がある。
2. **Web search**（WebIQ による）を追加している。
3. フライト予約用とホテル予約用の **2 つの MCP サーバー**がある。
4. **Foundry IQ** の knowledge を追加している。retrieval モデルとして GPT 4.1（low reasoning effort）と retrieval instructions を選び、Azure AI Search のインデックスと、出張ポリシーを網羅するいくつかのファイルを追加した。

### 6.2 トレースの確認とフィードバック

1. エージェントにリクエストを送ると、トレースが表示される。トレースのナビゲーションには、トレースビューと、ユーザーとの往復がある場合の会話全体のビューがある。
2. 最近の会話を開くと、**trajectory / user / graph** の 3 つのビューがある。
   - trajectory：エージェントの呼び出しから、実行呼び出し、LLM 呼び出しまで、各ステップを表示し、各ステップの所要時間を見られる。トークン表示に切り替えて、ステップごとの使用量も見られる。
   - user：ユーザーの入力と出力を確認する。
   - graph：呼び出されたツールと LLM 呼び出しをグラフで見る。
3. 会話の各部分をクリックすると、入出力、指示、メタデータが見られ、**フィードバックを追加**できる。良ければ good を付ける、カテゴリ（例：hallucination タグ）を付ける、自由コメントを書く、**期待される出力（ground truth）**を追加する、といったことができる。ground truth は、golden data set に送ったあとの評価で使われる（新たに提供開始した機能と説明）。

### 6.3 データセットの作成

データ画面で作成する方法は 3 つあります（アップロード、トレースから、synthetic）。

**Synthetic データセット**

1. 作成の指示を入力する。エージェントのタスクの種類、複数のユーザー層がある場合は persona、生成したいシナリオ（曖昧なリクエスト、ポリシーに従わないリクエスト、happy path とエッジケースなど）を自由に書ける。
2. エージェントを選ぶと、エージェントの情報が自動で入力される。
3. データ生成に使うモデルと、行数（クエリ数）を指定する。
4. 実行には時間がかかるため、その場では行わず、事前に作った例を見せた。ビジネスクラスの予約や、ホテルの上限（cap）を正しく守るかなどのテストケースの説明とクエリ一覧が並んでいた。

**トレースからのデータセット（実際に多いやり方と説明）**

1. フィードバックを付けたトレースをフィルターし、すべて選んで、データセットに送る。新規作成も、既存への追加もできる。時間とともにバージョンを重ね、新しい問題が見つかるたびに追加する。
2. 名前を付け、**golden data set** としてマークする（探しやすくなる）。
3. 新しいオプションとして、rubric ベースのテストケースを追加する。そのために使うモデルを選ぶ。
4. 作成後に開くと、golden data set として区別して表示される。synthetic よりはるかに網羅的で、クエリの詳細、ツール呼び出しを含む応答、ユーザーによる評価（rating）、期待される ground truth（旅費ポリシーの上限に収まる適合するフライトとホテルを示す、という内容）、追加の rubric metadata が入っている。

登壇者は、エージェントを変更して本番に出す前に、このデータセットに対して品質が改善しているか同等かを確認し、下がっていれば本番に出す前に戻って確認すると述べています。

### 6.4 Evaluator の作成と offline evaluation

**組み込み evaluator の利用**：Evaluations の evaluator catalog に多数ある。例えば、KPI がタスク完了と出力品質を高くしてかつ groundedness も確認したい場合は、その 3 つを選んで使える。

**独自の rubric evaluator の作成**

1. create evaluator で名前を入れ、quality か safety を選ぶ（ここでは quality）。
2. スコアの方式（1〜5 または Boolean）を選ぶ。ここでは曖昧さをなくすため Boolean（pass/fail）。
3. evaluator を作るモデルと、対象エージェントを選ぶ。対象エージェントを選ぶと、そのコンテキストが取り込まれる。
4. 追加のコンテキストとして、本番トレースや、重要なことを記した製品仕様などのコンテキストファイルを渡せる。
5. rubric を生成する。このデモではトレースを渡さず簡単な指示のみを与えたため、完全な rubric ではないかもしれないと断っている。生成された観点には、ツールのトレーサビリティ（フライトの予約前に、そのフライト情報がツール呼び出しで取得されていること）、並列ツール呼び出しの順序（ポリシーとして安い順に並べる）、ポリシー確認と違反の通知などがあった。
6. safety を選ぶと safety evaluator も作られる。safety evaluator は、許可する行動と許可しない行動の 2 つのカテゴリを持つ。ここでは許可しない行動が 3 つと、許可する行動がいくつか生成された。例：安全でない国へのフライト予約は許可しない（従業員の安全のため、別のプロセスにする）。ほかに、信頼できない交通手段、ポリシー非準拠の宿泊も許可しない。scope、禁止される行動、適用の定義、例が含まれている。

**評価の実行（offline evaluation）**

1. Traces の evaluation タブで create を選ぶ。評価対象のエージェントを選ぶ。
2. 個々のターンを評価するか、会話全体を評価するかを選ぶ。
3. データは既存のデータセットを選び、作成した golden data set を指定する。
4. 判定に使う judge model を選ぶ。エージェントに使うモデルとは**別のファミリー**のモデルを使うのが一般的で、同じだとエージェントの応答に有利になりがちだからだと説明している。
5. 頻度は 1 回の実行にした（まだ本番に出していないため）。確認して submit する。
6. 結果：複数回の実行が 1 か所に並ぶ。今回は 1 回だけ。**safety は問題なし、quality に問題がある**。選んだ 1 件のスコアは **0.35**（満点 1）で、予約に関する主張とツール呼び出しは正しかったが、並列ツール呼び出しの管理、ポリシー違反、確認と制約の扱いが不十分だった。

**次に何をするか**：すぐエージェントを直すのか、golden data set の分布が正しいか、LLM judge の観点が適切かを先に確認するのか。最初は全体を確認してから決めるとよいと述べています。デモでは、rubric を少ない情報で作っていたため、情報を足して作り直した。すると、「あるとよいが必須ではない」観点が失敗の原因だと分かり、rubric を調整した。それでもスコアは約 37% で、エージェントの評価と改善を続ける必要があると結んでいます。

### 6.5 Monitoring ダッシュボード

1. プロジェクト単位の monitor ダッシュボードがある。エージェント内にも monitor があり、ドロップダウンで 1 つのエージェントを選ぶこともできる。
2. 上部に、実行数、トークン使用量、コストなどの主要メトリクスが並ぶ。組織のポリシーに違反している場合は詳細が見られる。
3. 選んだ期間のアクティブなエージェントとモデルが表示される。
4. 運用メトリクスとして、エラー、使用量、モデルの所要時間、レイテンシ。プロジェクトで有効なモデルの一覧と、それぞれの使用量も見られる。
5. 品質トレンド：evaluator を設定していれば、全エージェントで同じ evaluator（デモでは coherence）の推移を見られる。会社によっては task completion や task adherence などを全エージェントに入れている。
6. デモでは、エラーが多いエージェントがあり、品質の問題は把握していなかったため確認したところ、クリックして該当トレースを見ると、**レート制限（rate limit）**の問題だった。より容量の大きいモデルを選ぶか、原因を調べると述べている。
7. コスト：先月の費用、予測コスト、プロジェクトの日次または月次の予算に対する推移、エージェント別のコストを見られる。エージェントごとに詳細を開くと、総コスト、コストに寄与するトレース、トークン使用量が見られる。例として、ある日突然 1 回の実行あたりのコストが上がり、**キャッシュヒット率が非常に低い**ことが原因だったという場面を挙げている。リクエストにタイムスタンプを付けるといった小さな変更で、キャッシュが使われなくなるといった問題を早期に見つけられる、という説明です。

### 6.6 Continuous evaluation（Ahmad 氏）

1. Foundry で評価に使うモデルを選ぶ。新しい評価用モデルとして **Decision Model 1.1** を紹介した（5.7）。
2. 例として、「アカウントの支払いが今日 2 回失敗した。今日中に助けてほしい」という問い合わせを state として送った。typed questions は次の 3 つ。
   - urgency：緊急か（true/false と信頼度）
   - team selection：複数のチームのどれが担当すべきか（選択肢ごとの確率）
   - priority：routine（時間的な圧力なし）、important（ある程度の圧力）、urgent（すぐの対応が必要）から選ぶ
3. 実行すると非常に高速で、結果は、urgency は true（緊急）、team selection は billing team（確信度はほぼ 100% で、トランスクリプトでは 99.8% / 99.9% と聞こえる）、technical support はほぼ 0、priority は urgent で信頼度約 67%、その選択肢のスコアは 77.8% だった。

**continuous evaluation の作成手順**

1. evaluations で create an evaluation を選び、対象エージェントを選ぶ。
2. ドロップダウンから、評価対象の**バージョン**を選ぶ（本番、開発中、アーカイブ済みなど複数ありうる）。
3. 個々のターンを評価するか、会話全体を評価するか選ぶ。トレースに会話 ID があれば、会話にまとめて end to end で評価できる。
4. データの種類を選ぶ。synthetic generation（offline の評価ループ）、既存のデータセット、benchmarks、本番の既存トレース（期間指定）、live traffic がある。ここでは **live traffic** を選んだ。
5. 実行頻度（例：1 時間に 1 回）と、サンプリング方法を選ぶ。**random** は無作為に選ぶ。**intelligent** は、冗長な会話やトレースを避け、本番で起きていることを適切に代表するよう選ぶアルゴリズム。
6. 評価の criteria として、decision model か chat model を選ぶ。evaluator は、offline のデータセットで使ったものと**同じ**ものを選ぶのが基本で、同じ条件で比較できる（apples to apples）ため。
7. 確認して submit する。evaluation タブに、recurring（定期）や one-time（1 回）などの種類が表示される。
8. 作成した recurring evaluation を開くと、すべての実行が表示され、評価されたトレースやスコア、詳細を掘り下げられる。

### 6.7 Insights と optimization の流れ

1. エージェントの **Insights** タブで、問題を見つけるモデル（デモでは "GPT-6 Luna" と述べた）を設定する。
2. 優先する問題の種類（提案された 8 種類）と、カスタムの指示を設定する（例：旅行予約システムを悪用して、一般には出ない隠れたフライトを探す人を優先する）。
3. 保存すると、バックグラウンドで動き、問題を high / medium / low で順位付けして出す。
4. 上位 2 つの insight は関連しており、次のような問題だった。
   - ロンドンからストックホルムへの旅行を探すと、エージェントは実際のフライトを探すが、結果の通貨が統一されておらず、米ドル、スウェーデンの通貨、英国の通貨などが混在する。
   - Foundry IQ に入れた旅行ポリシー（例として、Contoso 社のホテル予約は 1 泊最大 200 ドルの上限）に関して、エージェントが英ポンドを米ドルに換算していなかった。そのため、200 ポンドを 200 ドルの上限内として予約してしまい、実際の 200 ドルより高い金額になって上限を超える。
5. insight には、問題の原因となったトレースや会話へのリンクがある。別タブで最初のトレースを開いた。
6. トレース上で、これは**悪い振る舞い**だと注釈を付け、なぜかを自然言語で書く。1 つ目は「比較と並べ替えのため、すべての価格をローカル通貨に換算すべき」、2 つ目は「旅行ポリシーを一貫して適用し、旅行者に許される予算を超える予約を避けるため、すべての通貨をローカル通貨に換算すべき」という内容。
7. 画面上には、エージェントのプロンプトに加えるべき、または直すべきプロンプトの提案も表示される。
8. **optimization run** を作成する。修正対象のエージェントとバージョンを選び、optimization model を選ぶ。optimization model には、**frontier モデルを選ぶこと**が推奨されている。
9. 実行後、候補（candidate）の一覧が表示され、どれが最良かが示される。**最良の候補を本番に promote する**。

## 7. 注意点・発表者の気付き

- **ダッシュボードが緑でも安心できない。** エージェントは自信を持って誤答することがあり、従来の指標だけでは捉えられない。
- **評価の出発点**：スコアが低いとき、いきなりエージェントを直さず、golden data set の分布、LLM judge の観点が正しいかも確認する。デモでも、rubric の作成時に与える情報が少なすぎたため、情報を足して作り直した。それでもスコアは約 37% だった。
- **judge model はエージェントのモデルと別のファミリーに**する。同じだと、エージェントの応答に有利になりやすいため。
- **Human evaluation は最良だが高価**で、使うのは少数のケース。
- **本番では想定外の使われ方をする。** 他人の代理での予約、隠れたフライト探しなどの例が挙がった。そのため、本番での継続的な評価が必要。
- **offline の evaluator と同じものを本番でも使う**。比較できるようにするため。
- **Decision Model は理由を説明しない。** 速く安いが、モデル生成の説明は得られない。
- **評価指標が良くても、想定外の問題は残る。** 評価者が拾えない問題は insights で見つける。
- **optimization model は frontier モデルを推奨**。
- **品質以外の問題も多い。** レート制限やキャッシュヒット率の低下（リクエストにタイムスタンプを付ける変更など）は、モニタリングで見つかる。
- 一部の発表（GA、task-level evaluator、rubric evaluator の safety 対応など）は「今日から」と述べられていますが、提供範囲やリージョンなどの詳細は発表では語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **品質の可視化**：traces、golden data set、evaluator により、品質のベースラインを作り、変更のたびに改善か劣化かを比較できる。
- **エージェント専用の評価**：rubric evaluator で、エージェントのコンテキストから専用の評価基準を作れる（品質と、新しく safety）。
- **評価コストの削減**：Decision Model 1.1 は、チャットモデルと比べ、デモで completion tokens が 12 対 約 1,100〜1,200 と約 100 倍の差。平均で 100〜200 倍のトークン節約と説明された。速く、安く、大規模に動く。
- **本番の継続的な監視**：live traffic を一定の頻度でサンプリングして評価できる。intelligent サンプリングで冗長なトレースを避けられる。
- **ヘルス・品質・コストを一画面で**：プロジェクト全体のモニタリングで、レート制限やキャッシュの問題、予算の推移を早く見つけられる。
- **systematic な改善**：insights で想定外の問題を見つけ、optimization で修正候補を作り、最良の候補を promote できる。

## 9. まとめ

このセッションは、Microsoft IQ を使ったエージェントの品質を、評価のループで改善し続ける方法を、出張エージェントのデモで示したものです。前半は、トレースで見えるようにし、専門家のフィードバックを入れた golden data set と rubric evaluator で、品質のベースラインを測りました。その結果（スコア約 0.35、調整後でも約 37%）から、エージェント、データセット、judge のどこを直すかを見極める流れも示されています。

後半は、本番運用です。live traffic を対象にした continuous evaluation、安価で速い Decision Model 1.1、評価者が想定しなかった問題を見つける insights、そして修正候補を作って最良のものを promote する optimization を紹介しました。最後に、observability のドキュメントと continuous evaluation loop のリンク、関連するオンデマンドセッションが案内されました。
