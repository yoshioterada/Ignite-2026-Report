# INV641 Harnessing Your IQ with a continuously improving agent platform

## 1. はじめに

このセッションは、前日に発表された Microsoft IQ のプラットフォームが「企業の中でどう動くのか」「なぜ重要なのか」を、架空の企業 Caldova の事例とライブデモで見せる Innovation Session です（60 分）。Microsoft Azure チームを率いる Arun Ulag 氏と、Core AI チームを率いる Jay Parikh 氏が進行し、デモ担当の登壇者が順に加わります。

主張は 2 つです。1 つ目は、**自社のコンテキスト（業務知識）はその企業の資産であり、自社の手元に残るべきだ**ということ。2 つ目は、**エージェントを動かすほど、システム全体が継続的に賢くなる**ということです。

デモは 4 つあります。Copilot で調査して Skill とプラグインにする流れ、1 回のプロンプトでアプリを作る流れ、GitHub と Foundry でエージェントを作って改善させる流れ、そしてモデルをファインチューニングする流れです。サプライチェーンの遅延対応を一貫した題材にしているので、一連の流れとして追えます。

## 3. 何に関する発表か

テーマは、エージェントを「デモでは動くが、業務では任せられない」状態から、本番で数千規模で運用できる状態へ進めるための基盤です。登壇者は、ギャップはモデルではなくモデルの周辺にあると述べています。具体的には次の 3 点です。

- エージェントが自社の業務のやり方を知らない
- チームの最良の仕事が 1 チームの中に閉じてしまう
- プロトタイプが増え続けるが、安全に本番へ出す道がない

これに対し、構築（build）、コンテキストの付与、本番運用、継続的な改善、ガバナンス、チームとの接続を 1 つの場所で提供する、というのが Microsoft の位置づけです。

発表の流れは次のとおりです。

1. 全体像: 「自社のインテリジェンスが手元に残ること」と「継続的な改善」

4. デモ 2: Fabric apps による 1 プロンプトでのアプリ作成と OneLake の説明
5. デモ 3: GitHub Copilot app でのエージェント構築、Foundry での本番化、Foundry Optimization による改善

## 4. 発表者が伝えたいメッセージ

### 4.1 自社のインテリジェンスは自社に残る

モデルは誰でも買えるものになりつつあり、**他社が持っていないのは自社の知識だけ**だ、というのが Arun 氏の主張です。知識は知的財産であり、他社のモデルを良くするために流出するべきではない、と述べています。Microsoft の目標は、その恩恵が Microsoft にもモデル会社にも競合にも渡らず、自社に蓄積されること（IQ が常に自社のものであり、複利的に積み上がること）だと説明しています。

### 4.2 エージェントは新入社員と同じように文脈が要る

Arun 氏は、新入社員にログインだけ渡して「頑張って」とは言わない、と例えます。誰と働くか、知識はどこにあるか、事業の状況、自分が判断できる範囲を教えます。エージェントにも同じ知識とコンテキストを与えるべきで、人とエージェントは 1 つの統合されたチームになる、という考えです。ただしエージェントに会社の全てを渡すのではなく、仕事に必要なものだけを渡す、とも述べています。

### 4.3 継続的な改善

Jay 氏は、エージェントが実際に仕事をして、チームや顧客、パートナーとやり取りするほど、そのフィードバックがシステムに戻って学習ループになる、と説明します。モデルは入れ替えられますが、エージェントが蓄積した自社に関するコンテキストは手元に残ります。システムはオープンで拡張可能であり、Microsoft の harness を使うことも、自前の harness やツールを持ち込むこともできます。そして**観測可能で、安全で、デフォルトでガバナンスが効く**ことが最も重要だと強調しています。

### 4.4 本番運用の難しさ

Jay 氏は、どの CIO に聞いてもエージェントは「作るのは簡単だが、本番で動かすのは難しい」と言うと述べます。本番のエージェントには、アイデンティティ、認証、サンドボックス、モニタリング、レッドチーミングなどが必要で、この一覧はさらに続くと述べています。また Arun 氏は、コンテキストが数多くのシステムや人の頭の中に散らばっていることも理由に挙げ、パイロットは 1 日で済んでも本番化には 6 か月かかり得ると説明しています。

## 5. 発表内容の詳細

### 5.1 Microsoft IQ とは

Arun 氏は、Microsoft IQ を**エンタープライズのコンテキスト管理プラットフォーム**と説明します。コラボレーションデータ、業務データ、非構造化データ、Web のデータなど、組織全体のコンテキストを 1 か所に集め、全てのエージェントで一貫して使えるようにするものです。構成要素は次のとおりです。

| 要素 | 発表での説明 |
| --- | --- |
| Work IQ | Microsoft 365 のチャット、メール、ドキュメント、SharePoint のファイルなどのコラボレーションデータを提供します。Microsoft 365 で設定済みのアクセス許可をそのまま尊重するため、各エージェントは見てよいものだけを見ます。 |
| Fabric IQ | Power BI のセマンティックモデルに定義済みのメトリクスと KPI をエージェントに提供します。セキュリティとアクセス許可はそのままです。Power BI は Azure 以外の AWS、GCP、Databricks、Snowflake などにも接続できるため、人向けに作った指標を、セマンティクスを作り直さずにエージェントが使えます。 |
| Foundry IQ | 契約書や判例、技術マニュアル、事例などを統合したナレッジベースを作り、エージェントに提供します。 |
| Web IQ | 規制情報や特定トピックのニュースなど、Web 上のコンテキストを選択的に取り込みます。 |
| コネクタ | ERP や CRM（Salesforce、SAP など）を含むサードパーティ向けに 350 以上のコネクタを提供します。 |

このコンテキストは、人向けの Copilot、エージェント向けの Foundry、さらに ChatGPT や Claude のようなアシスタントなど、仕事が行われる場所で使えると説明しています。

### 5.2 Caldova のシナリオ

Caldova は消費者向け電子機器の会社で、Arun 氏は「Caldova は実在しないが、課題は実在する」と前置きしています。ホリデー向けの注文は全て確定し、スケジュールどおりという状況です。サプライチェーン担当の Jessica 氏は、部品が遅れたときに、どの注文に影響するか、いくらかかるか、何をすべきかを突き止めなければなりません。現状ではそれに 3 日以上、20 通のメール、5 つのシステム、4 つのチームが必要になる、という設定です。遅延への対処方法を知らないわけではなく、時間がないことが問題だと説明されています。

### 5.3 デモ 1: Copilot での調査から Caldova IQ まで

Jessica 氏のデモの詳細は「6. デモ・手順」にまとめます。ここでは位置づけだけ整理します。

1. まず Copilot が Work IQ を通じて Teams、メール、ファイルから 2 週間の遅延を確認する（だが、影響する注文、コスト、サプライヤーとの合意は答えられない）
2. 調査を Skill にして再利用する。Skill は平易な言葉で書かれコードは不要で、Copilot、Cowork、Office で使え、チームと共有できる
3. 開発側と組んで Skill をプラグイン化する。MCP（AI を業務システムにつなぐオープン標準、と登壇者が説明）で調達、在庫、生産、販売のシステムに接続している
4. IT は Agent 365 の 1 つのレジストリで全プラグインを把握・承認・停止できる
5. プロセス、コスト、過去の教訓、関係者を束ねたビジネスプラグイン「Caldova IQ」を作り、責任者が Certify（認証）する
6. 同じ質問をもう一度すると、Caldova IQ から必要な分だけを読み込み、約 $35,000 のペナルティなどを答える

Arun 氏はこれを、Jessica 氏がサプライチェーンの専門家として、自分の知識を会社全体で使えるビジネスプラグインにしたものだとまとめます。知識の出どころは、ドキュメント、SharePoint、Power BI のセマンティックモデル、承認者となる具体的な人、守るべきルールなど数十に及びます。これが Microsoft IQ で管理され、Copilot と Foundry の全てのエージェントが使えます。

### 5.4 デモ 2: Fabric apps による 1 プロンプトのアプリ作成

Arun 氏は、毎朝、リスクのある注文、担当者、対応状況、次の予定を追う必要があるが、そのためのアプリは IT のバックログに何か月も残りがちだ、と問題を示します。Copilot に組み込まれた **Fabric apps** では、必要なアプリを平易な言葉で説明すると、Microsoft IQ のデータとビジネスコンテキストを使って Copilot がアプリを作ります。Arun 氏が挙げた特徴は次のとおりです。

- Fabric が裏側のデータと AI のサービスを担当し、エンドツーエンドで動く
- 共有用のリンク付きで動くアプリが得られ、アクセス許可は最初から組み込まれている
- 管理するサーバーも、設定する Azure サブスクリプションも不要
- シャドー IT ではない。アプリはライブで統制されたデータ（OneLake にあるもの）で動き、古くなるコピーではない
- IT は全アプリを見つけられ、業務上重要になったら引き継いで認証・管理できる

Eren 氏のデモ内容は「6. デモ・手順」に記します。

### 5.5 OneLake の説明

Arun 氏は、OneLake を「データ版の OneDrive」と例えています。Fabric に組み込まれ、Fabric と Foundry の両方のストレージになります。「データが無ければ AI も無い」という考えです。

SAP、Snowflake、Oracle、Databricks、Azure SQL、Postgres、Cosmos DB、AWS や Google Cloud 上のデータなど、分散したデータを、**ショートカットとミラーリング（どちらも仮想化の技術）**でデータを移動せずに 1 か所へ集められます。これによって大規模なデータ移行プロジェクトなしで早く価値を出せる、と説明しています。**ショートカットとミラーリングの仮想化機能は完全に無料で、Microsoft がコストを負担する**ともはっきり述べています。IT は引き続き全体をガバナンスできます。

Eren 氏も、Fabric ではアプリとその基盤データが最初から統制され、1 つのリンクで IT に渡せると補足しています。渡した後はプロ開発者が引き継いで拡張でき、規模が広がっても自分たちが管理するエンタープライズコンテキストに基づいたままでいられる、という説明です。

### 5.6 継続的に改善するエージェント基盤（Jay 氏の説明）

Jay 氏は、全体を 1 つの連携したシステムとして示します。**GitHub で構築し、Fabric でデータを整理してエージェントにつなぎ、Foundry でスケール運用する**（統制、モニタリング、セキュリティを確保）という役割分担です。

GitHub については、Jay 氏が前月の GitHub Universe で語られた内容として次を挙げています。

- **Git のインフラ**: スケールのための新アーキテクチャで、現行システムの 180 倍の書き込みスループットを達成したと説明
- **Copilot harness**: マルチモデルで効率的かつ高速。Foundry のエージェントでも使え、他の Microsoft のプロジェクトも支えている。同じ harness を Copilot SDK として、自社のエンタープライズアプリ構築にも使える
- **サーフェス**: VS Code、CLI、GitHub app、github.com の間でセッションがつながり、作業を行き来できる

さらに、前月発表された **Copilot Fusion** を紹介しています。タスクを見て、単一のモデルを使うか複数のモデルを使うかを判断する仕組みです。Jay 氏は、前日の発表として、Fusion モデルが Terminal Bench 4.1 で最高点を出し、Opus 5.5 を 5% 強上回りつつコストは半分だったと述べています（ベンチマーク名とモデル名は音声認識の都合で表記が確定できません）。

また Jay 氏は **Microsoft Decision 1.1** モデルにも触れています（前日に発表されたモデルで、表記は音声認識の都合で確定できません）。エージェントは緊急かどうか、人に連絡するかといった小さな判断を何十回も行います。それらを毎回フロンティアモデルに送るのはコストが高いため、専用の decision モデルを使います。Jay 氏は、専門モデルが各種 LLM への振り分けやエスカレーションを担い、小さなモデルが単純なタスクを担い、複雑な推論は大規模なフロンティアモデルが担う、というモデルの組み合わせが、ソフトウェアの向かう先だと述べています。

### 5.7 Foundry の機能

Jeff 氏は Foundry の機能として次を挙げています。

- **モデル**: 11,000 以上。Anthropic、OpenAI、Meta、Microsoft 自身の MAI モデルなど。エージェントを再デプロイせずにモデルを切り替えられる
- **model router**: OpenAI と Anthropic の複数モデルの中から、ルーターが選ぶ。簡単な要求は高速なモデルに送り、フロンティアモデルは難しい要求のためにとっておく。単純な作業にフロンティア価格を払わずに済む
- **エージェントごとのアイデンティティ**（Jay 氏）: データや対話できる相手などのきめ細かい権限を設定でき、Agent 365 とも統合される。IT は他のエージェント、アプリ、人と並べて、1 か所で観測、管理、操作できる
- **トレース**: エージェントの全ての対話が自動で追跡・記録され、ツールの呼び出しや、人が軌道修正したときのフィードバックも含まれる
- **Foundry Optimization**: トレースを分析して学びを見つけ、Skill の更新を提案する

### 5.8 モデルのファインチューニング（Seth 氏の説明）

Seth 氏は、Foundry Optimizer は、エージェントが正しく動くための指示、アセット、Skill の作成に優れているとしつつ、Caldova には多様な復旧の課題があり、指示がどんどん大きくなって入力トークンのコストが膨らむことを懸念します。**指示を非常に大きくしないと済まないなら、それはモデルを学習・ファインチューニングする時期のサイン（code smell）**だ、というのが考えです。

用意するものは次の 3 つです。

1. **データ**: 過去の履歴データに加え、エージェントのトレースに付けるアノテーション（良い／悪い）が、後でモデルの学習データになる
2. **ベースライン**: MAI Code Flash 2（音声認識の都合で表記が確定できません）を学習に使う。ベースラインのモデルをデプロイして評価しておく
3. **評価**: Microsoft Foundry の **rubric evaluator**。学校の成績のように、倉庫の確認で 90%、リクエストで 70% の配点、というように重みを付けた採点基準でエージェントを評価する

学習の手法は、supervised fine-tuning、direct preference optimization、reinforcement learning から選べます。Seth 氏は reinforcement learning を好むと述べ、理由は、rubric に合わせて作ったコードによる採点ファイルを使い、モデルが自分の改善を自分たちにとって重要な基準で採点できるからです（「採点ファイル」は、聞こえたのは "greater scoring file" で、音声認識の都合で表記が確定できません）。トレースのアノテーションから直接データセットを取り込めるため、エージェントが使われるほど学習のループができる、と説明しています。

結果は 6.5 節で述べます。Seth 氏は「このモデルはあなたのもの」と述べ、Jay 氏が「手元に残る」と応じています。タスクごとに最適化して自社のモデルが必要だと分かれば、人が常に検証した上で、そうしたモデルを何百も自律的に働かせられる、という見通しです。

### 5.9 顧客事例: AEMO

Jay 氏は、実在企業の例として AEMO を紹介します。AEMO はオーストラリアの電力網を運用し、「明かりを灯し続ける」ことが仕事です。障害時には数分、場合によっては数秒で対応する必要があり、各地域から何千もの信号が届きます。同社はこのリアルタイム情報を読み解くエージェントを構築しました。動画での発言の要点は次のとおりです。

- Michael Gatt 氏: 複雑さをリアルタイムで扱うには、チームの優秀な人材でも、緊急時に情報を消化して判断する認知能力が試される。解決策をスピードで取り入れられるかが、エネルギー転換を進める成功の尺度の 1 つになる
- Han Xiang Choong 氏: 以前は多数のシステムに情報が散らばっていた。それらを統合して AI エージェントに公開し、エージェントが情報源の間の重なりや相乗効果を見つけられるか、が出発点だった
- Joseph Reddy 氏: Foundry の能力は十分だと確信していた。課題は最初の問題で、強力なガードレールを提供する Fabric IQ と、正確さのために Foundry のコンテキストが必要だった。指針は「humans first、humans in the loop always」で、人が AI ソリューションの中心にいなければならない
- Azadeh Nia 氏: Foundry IQ、Fabric IQ、Work IQ が連携することで、ツール間の連携を自分で作る手間が省け、ほぼリアルタイムで成果を出すツールを作れる

### 5.10 オープン性

最後に両氏は、**あらゆる方向にオープン**だと述べています。

- コンテキストの接続: Salesforce、SAP、ServiceNow、Workday などのコネクタがあり、Microsoft 外のものも Microsoft IQ に入る
- コンテキストの利用先: Copilot に閉じない。Claude、ChatGPT、Gemini など、チームが既に使っているアシスタントやエージェントでも同じコンテキストが使える
- 構築側: Microsoft の harness を使っても、自前の harness を持ち込んでもよい。モデルもフレームワークも選べ、全て Foundry で動く

## 6. デモ・手順

このセッションは、前半（Caldova のシナリオ）と後半（エージェント構築）で、複数のデモがあります。画面は音声だけでは分からないため、以下は登壇者の説明の範囲に限ります。なお Caldova は発表用の架空の会社で、シナリオは演出です。

### 6.1 Jessica 氏: Copilot で調査し、Skill、プラグイン、Caldova IQ へ

**調査と Skill 化**

1. Teams で、サプライヤーがロボット用のメインロジックボードの納品を 2 週間遅らせ、最大手の小売の注文がそれを必要としているというメッセージを見る
2. Copilot で「what puts this at risk?」と質問する
3. Copilot が Teams のサプライヤー通知、メール、ファイル、未完了の項目を集約する。2 週間の遅延は、Work IQ を含むプラグインを通じて確認される
4. 一方で、どの注文に影響するか、コストはいくらか、サプライヤーとの合意内容は答えられない
5. 今後も遅延は起きるため、この調査を Skill にするよう依頼する
6. バックグラウンドタスクが動き、ファイルに触れるときは必ず承認を求める（勝手に動かず、人が承認する立場に残る）
7. 完了すると、手順を平易な言葉で文書化して保存する。コードは無く、チームの誰でも内容を見て変更できる。Copilot、Cowork、Office で使え、「Share」ボタンでチームに共有できる

**プラグイン化と IT による管理**

1. エンジニアリングと協力して、Skill をプラグインにする。MCP で調達、在庫、生産、販売のシステムに接続する

### 6.3 Jeff 氏: GitHub Copilot app でのエージェント構築と Foundry での本番化

**構築**

1. GitHub Copilot app を開き、平易な言葉で作業する
2. 新しい Copilot Fusion をオンにして構築を支援させる
3. 「Microsoft IQ と既存のプラグインと連携するカスタムのビジネスエージェント」を、チームがいる Microsoft Teams 内で動かすよう依頼する
4. エージェントの構築が始まる。その間に、エスカレーションすべきかという判断を、重いコンピュートやトークンを使う前に Microsoft Decision 1.1 モデルへ送ると、数ミリ秒で判断が返る
5. エージェントが数分で完成する（この時点では Jeff 氏のノート PC で動いている）と Jay 氏が説明している

**Foundry での本番化**

1. Foundry でモデル一覧と model router を見せる（5.7 節）
2. Foundry のホームページで、GitHub Copilot app が作ったエージェントがクラウド上で安全に動いている
3. Teams の、サプライチェーンの問題を扱うチャネルに、先ほどの問題（2,000 ユニット不足）を投稿する
4. Foundry 上のエージェントが投稿を拾い、Microsoft IQ に安全に接続して、プラグインのデータを使いながら対応を決め、提案を作る
5. 設定したガードレールと権限のため、エージェントはこの提案を単独では実行できず、承認が受信トレイに届く
6. 提案は、部品が足りないので $480K で新たに購入する、というもの
7. Jeff 氏は、近くの製造工場に在庫があるため、購入ではなく移送に変更するよう舵を切る（steer）。信号がエージェントに送られ、エージェントは作業を再開する

Jay 氏は、エージェントが推奨し、Caldova のプロセスが働く地点で止まり、人が判断して流れを変えた、これがプラットフォームに組み込まれた信頼だと説明しています。

**学習と改善**

1. Foundry は全てのやり取りを自動で追跡し、トレースにする。ツールの呼び出しや、人が舵を切ったフィードバックも記録される
2. Foundry Optimization の実行結果が、過去のトレースを分析して一連の学びを特定している。例として、「可能なら、常に新規購入せず、既存の在庫を移送する」が自動で捕捉された
3. 学びは、エージェントの Skill の更新案として提示され、レビューして適用し、エージェントやプラグインにマージできる
4. 1 週間ほど経った想定で新しい警告が来る。supply chain チームのチャネルでは、エージェントが問題を能動的に検知して変更案を出している。学びを適用し、新規購入ではなく移送を提案している

Jay 氏は、この流れを 3 点でまとめています。エージェントの構築と Foundry への展開が簡単であること、Caldova のビジネスプロセスに当たると止まる（信頼）こと、継続的に改善すること、です。

### 6.4 Seth 氏: ファインチューニング

1. Foundry のトレースを見せ、トレースにアノテーション（良い／悪い）を付けられることを示す。これが後でモデルの学習データになる
2. MAI Code Flash 2（表記は音声認識の都合で確定できません）をベースラインとして使う。rubric evaluator で、ベースラインのモデルをデプロイして評価する。結果は「まずまず（okay）」だった。Seth 氏は、エージェントの役割は人の仕事を代わりにやることではなく、人が正しい判断をするための情報を提供することだと念を押している
3. 「training」ボタンから、手法を選ぶ。supervised fine-tuning、direct preference optimization、reinforcement learning がある
4. reinforcement fine-tuning を選び、MAI Code Flash 2 を指定する。履歴データのデータセットがあり、エージェントのトレースのアノテーションから直接データを取り込むこともできる
5. 新規にジョブを実行すると約 9 時間かかるため、既に実行済みのジョブを見せる。training reward と最終的な valid mean reward が確認でき、後者はかなり高い
6. モニターのグラフで、青い線が学習データでの学習精度、緑の線が取り分けた検証データでの検証精度を示す。両方が上がるのが望ましい。別のグラフでは、モデルが内部でより多く推論している様子が見える

**結果**: 復旧のパフォーマンスは、ベースモデルの MAI Code Flash 2 で 70% から 83.3% に上がり、1,000 リクエストあたりのコストは $1.20 でした。Jay 氏は、これは 1 回の実行だけの結果で、繰り返せばさらに良くなると述べています。登壇者は、使うほど差が顕著になり、2 百万件の遅延を処理する場合は $60 で済むとも述べています（この数値は、1,000 リクエストあたり $1.20 という数値と単純に計算が合わず、音声認識か言い間違いの可能性があります。確定できません）。

## 7. 注意点・発表者の気付き

- **Caldova は架空のシナリオ**: Caldova は発表のために作られた架空の企業で、遅延や注文などのシナリオは演出です（Jay 氏が "fictitious company" と述べています）。「3 日が午後のうちに収まる」といった成果も、実測値ではなくシナリオ上のものです。
- **エージェントは人の判断に委ねる場面を持つ**: 提案が承認を要する設計で、人がエージェントの案を修正できる点が、デモで強調されています。Seth 氏も、エージェントの仕事は人の代わりではなく判断の補助だと述べています。
- **Skill への指示肥大化は学習の合図**: 指示が大きくなり入力トークンのコストが膨らむなら、ファインチューニングを検討する、という Seth 氏の目安です。
- **ファインチューニングには時間がかかる**: デモで使ったジョブは約 9 時間とのことです。
- **結果は 1 回の実行**: 70% から 83.3% への向上は 1 回の実行によるものだと Jay 氏が述べています。また Seth 氏は、報酬の値は用意したデータセットと自作の採点基準での結果だと断っています。
- **発表では触れられていない点**: 各製品の提供状況、価格（OneLake の仮想化の無償化を除く）、Fabric apps や Foundry Optimization などの利用条件・制約の詳細は語られていません。

## 9. まとめ

このセッションの結論は、締めに語られた 2 点です。

1. **自社のインテリジェンスが競争優位であること。** 誰もが同じモデルを使える時代に、自社だけが持つのはコンテキストです。Microsoft IQ ではそれが自社のために働き、自社のものであり続けます。
2. **システムは動かすほど良くなること。** 実行と修正のたびにシステムが改善し、その価値は自社だけに蓄積されます。

その手段として、Work IQ、Fabric IQ、Foundry IQ、Web IQ と 350 以上のコネクタでコンテキストを 1 か所に集め、ビジネスプラグインとして認証します。GitHub で構築し、Fabric のデータにつなぎ、Foundry で統制しながら運用し、トレースと人のフィードバックから Skill とモデルを改善する、という一連の流れをデモで示しました。そしてコンテキストも構築側も、Microsoft の外へ向けてオープンです。
