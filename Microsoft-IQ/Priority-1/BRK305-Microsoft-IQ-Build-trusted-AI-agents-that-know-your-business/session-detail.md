中心にある主張は、「**コンテキストがエージェントを賢くし、Foundation がエージェントを信頼できるものにする**」という一文に集約されています。

Yitzhak 氏は、2028 年までに数十億規模のエージェントが業務に展開されるという見通しを示しました。エージェントは、プロンプトに答えるだけの存在から、ビジネスについて推論し、シグナルを収集・分析し、人間の監督と承認のもとで行動まで行う、継続稼働型のものへ変わりつつあるという認識です。そのためには、エージェントが信頼でき、ガバナンスが効き、会社の知識の上で動く必要があると述べています。

また、「自社の IP をモデルに取り込まれるのではなく、自社の IQ を作るために使う」という姿勢も語られました。

## 5. 発表内容の詳細

### 5.1 エージェントの本番化を阻む 3 つの課題

冒頭では、ビジネスが「一体となって考え、動く」姿を描いた短いビデオが上映されました。ビデオでは、エージェントがデータ、文書、コミュニケーション、関係性といった企業全体のコンテキストを横断して推論すること、日常的な判断や行動は明確なガードレールの中で自律的に行われること、重要な判断ではエージェントが最善の選択肢を提案して人が決めること、が語られています。

発表では、AI に投資している企業は多い一方で、実際に価値を出せている企業の割合は期待より低いと説明されました（具体的な数値は示されていません）。理由は次の 3 つです。

1. **エージェントは推論できるが、自社のビジネスを知らない。** AI モデルは世界の一般知識で学習されているため、顧客、チームの動き方、社内ポリシーを知りません。その結果、一般的な知識から一般的な回答と判断しか出てきません。しかもコンテキストが断片的だと、判断の一部しか推論できず、人間が結果を検証する手間が大きくなります。
2. **エージェントを大規模に作るコストが高い。** エージェント 1 つなら簡単に作れますが、本番化には「何カ月もの作業」が必要になると説明されました。意図、知識、ガバナンス、ライフサイクル、品質とコストの把握まで必要です。実際の顧客例として、本番に必要な要素を並べた複雑な図（発表者の言う eye chart）も示されました。チームごとにエージェントを作ると、コストが積み上がるうえ、ポリシーやコンテキストがバラバラになります。
3. **パイロットから本番への移行。** コストが予測できること、価値を継続的に評価できること、成果が検証できることが必要です。

さらに、課題とは別に **IP の問題** も挙げられました。会社の独自性を支えるのは長年積み上げた知的財産であり、それを使って自社の IQ を作るべきだ、という考えです。

### 5.2 「完全なコンテキスト」とは何か

発表では、エージェントに渡すべきコンテキストを次の 4 種類に整理しています。

| 種類 | 例（発表で挙げられたもの） |
| --- | --- |
| 生産性・コミュニケーション | メール、Teams のやり取り、意思決定や承認のフロー |
| ビジネス・業務データ | KPI、データとセマンティックモデル、OKR、業務上のアクション、ルール、ポリシー |
| 組織の知識（institutional knowledge） | 文書、社内ポリシー、会社の運営の仕方 |
| 公開知識 | Web 上のニュース、顧客レビュー、開示情報、地政学ニュースなど |

これらを「最新で、完全で、ガバナンスが効き、追跡可能な形で」エージェントに渡すことが求められると説明されています。さらに、複数ステップの業務（在庫管理、サプライチェーン、ロイヤルティプログラムが例）では、従業員に渡すプレイブックと同じものをエージェントにも渡す必要があるという考えです。誰が承認するのか、どの KPI を追うのかといった情報が含まれます。

### 5.3 Microsoft IQ の位置づけ

Yitzhak 氏は、前日のキーノートで語られた 3 つの柱（human ambition、intelligence、trust）が、Copilot、Microsoft IQ、Agent 365 に反映されていると紹介しました。

Microsoft IQ は **企業のコンテキスト管理** を担うプラットフォームです。生産性データ、業務データ、ビジネスデータ、非構造化データ、実世界のデータ、サードパーティシステムを 1 つのコンテキスト管理に統合します。コンテキストにはガバナンス、バージョニング、階層があり、その土台には、コンテキストとエージェントの結果を継続的に改善する仕組みがあると説明されました。

その上に載る新機能が **Business Plugins** です。Work IQ などの各 IQ を組み合わせて「自社の IQ」を作り、次の効果を狙っています。

- 自社データに基づく、より根拠のある判断
- エージェント構築のコストと時間の削減
- ガバナンスの効いた本番化への道筋
- IP を自社で管理できる、オープンな相互運用性

### 5.4 Business Plugins の 4 つの役割（Dipti 氏）

Dipti 氏は、コンテキスト管理システムに必須の機能として次の 4 つを挙げました。

1. **Curate（キュレーション）**: サプライチェーン、税務アドバイザリー、法務といった領域の専門家がコンテキストを整え、Business Plugins としてエージェントに提供します。
2. **継承と共有**: 繰り返し使えるように、継承（inheritance）と共有を可能にします。スキルだけでは企業規模にスケールしない、という問題意識です。
3. **インサイト**: どのプラグインが使われ、どのコンテキストが活用されているかを把握します。
4. **ガバナンス**: 認定（certification）と秘密度ラベル（sensitivity labels）など、Microsoft に期待されるガバナンスを備えます。

階層の例として、デモの題材の企業 Coldova の下に commercial、manufacturing、R&D があり、サプライチェーンは manufacturing の下にある、という構成が示されました。それぞれを Business Plugin として表現し、関係者（ステークホルダー、承認者）もあわせて持たせます。承認（endorsement）と認定を付けたうえで、昇格（promote）、認定（certify）、共同作業（collaborate）ができると説明されました。

### 5.5 Business Plugins を支える各 IQ

Business Plugin には、次の IQ からコンテキストを取り込みます。

| IQ | 発表での説明 |
| --- | --- |
| Work IQ | 生産性のコンテキスト。メール、Teams チャット、SharePoint 文書など、組織の働き方そのもの |
| Fabric IQ | OneLake、セマンティックモデル、オントロジー、業務インテリジェンス |
| Foundry IQ | ナレッジベース。PDF、コンプライアンス文書、契約書、チェックリストなどの非構造化データを AI 検索で扱えるようにする |
| Web IQ | 公開情報（Web、ニュース、画像、動画、ブラウジング） |

Fabric IQ については、次の点が説明されました。

- **OneLake**: 1 日あたり 1,000 億件超（100 billion plus）のインタラクションを扱うサービスだと紹介されました。データはショートカット（リンク）またはミラーリングで OneLake に集約され、データ資産の統一ビューになります。移行（migration）は不要で、データのコピーも作らない、という考え方です。Delta と Iceberg のオープンフォーマットに対応し、OneLake security でセキュリティを、OneLake catalog でガバナンスを担います。Excel の OneLake Explorer からデータを引くこともできると紹介されました。
- **セマンティックモデル**: Power BI のセマンティックモデルは 2,200 万個あるとされ、すでにあるリッチなコンテキストを Microsoft IQ で使えます（続けて「35 million active users」という発言もありましたが、何の数字かは音声から確定できません）。
- **オントロジー**: 事業はテーブルの行と列だけでなく、トラック、飛行機、ルートといった実体で動いています。それをグラフとして表現し、IQ や Copilot が理解できるエンティティにする層です。

### 5.6 サードパーティ連携と「1 つの API」

Microsoft 外のエコシステムも同様に重要だとして、発表では **350 個のコネクタ** を発表すると説明されました（公式概要には「400+ other sources」とあり、数字は異なります）。例として Salesforce（前日のキーノートで言及）、Google Drive、プロジェクト管理の Asana、HubSpot が挙がりました。

接続の入口は **Microsoft IQ API という 1 つの API（1 つのエンドポイント）** です。Copilot だけでなく、Claude、Gemini、ChatGPT など他のエージェントやモデルからも、同じビジネスコンテキストを使えるという説明で、「一度キュレーションすれば、どこでも使える」と表現されています。カスタムエージェントや自律エージェントも対象です。

### 5.7 今後の計画

Dipti 氏が語った今後の計画は次の 2 点です。

- **エージェントによるキュレーション**: Business Plugin を最新に保つ作業をエージェントが肩代わりします。例えば、プレイブックが 30 日更新されていなければ、プラグインへの更新提案が出て、人が承認する、というポリシーベースの運用です。
- **保護**: Agent 365 との統合が計画に入っています。

### 5.8 EY の事例

EY の Michael Porter 氏（partner、global assurance analytics leader）は、アシュアランス（監査、アドバイザリー、フォレンジック、気候関連サービスなど）を、「資本市場や顧客のプロセスに対する信頼を提供する仕事」と説明しました。

スケールの数字として、次のものを挙げています。

| 項目 | 現在 |
| --- | --- |
| 顧客数 | 160,000 社超（グローバル） |
| 年間に処理する構造化データのレコード | 1.5 兆件超 |
| 管理しているエビデンス | 常時およそ 1.5 億〜2 億件 |
| ユーザー数 | 640,000 人超 |

これらを 1 つのエージェント基盤（agentic framework）に収め、一貫性と信頼性の面で完全に動かす必要があり、同氏は「毎回 100% 正確でなければならない」と冗談を交えて話しています。

EY のサービス提供は、おおまかに 4 層で説明されました。

1. **データの取り込み**: 顧客のシステムからデータ（構造化・非構造化）を自社環境に持ち込む。
2. **データプラットフォーム**: データを管理、ガバナンス、ラベル付けし、オントロジーの状態にして、共通のタクソノミーに対応づける。これにより AI システムを顧客間で再利用（ポータブルに）できる。
3. **ナレッジ層**: 160,000 社分の情報を推論することが最も難しい部分。次の 3 つに分けて扱う。(a) 顧客から入ってきた情報の推論と理解、(b) EY 自身のポリシー、手順、方法論、(c) 人のコンテキスト。
4. **インテリジェンス層**: 1 つのマルチエージェントフレームワークの下で、大規模に動作するエージェント。

ナレッジ層では、Microsoft と協力して IQ スイート、特に **business connectors**（発話のまま。音声認識の都合で表記が確定できません）を導入しているとのことです。顧客ごとに分類された知識オブジェクトが、AI を大規模に動かすために必要だという説明でした。

今後については、Microsoft とは毎週のように協力して製品づくりに関わり、バックログも合同で持って共同開発していると述べています。さらに、EY は世界最大のビジネスインテリジェンス消費者であり、Azure の大口利用顧客の 1 つだとして、規模は現在の 3〜4 倍になる見込みを語りました。データ資産は 4 兆〜5 兆件のレコード、年間で 2 億〜2.5 億件を大きく超えるデータオブジェクトを管理する想定で、ナレッジ層とインテリジェンス層を体系的に作ることが不可欠になるとしています。

### 5.9 Foundation 層（Dorit 氏）

Dorit 氏は、Yitzhak 氏が冒頭に述べた「パイロットは午後 1 回で作れるが、本番化には非常に時間がかかる」という話を受けて、エージェントがどう作られ、どう動くのかを説明しました。まず、エージェントを次の 2 種類に分けています。

- **コーディングエージェント**: ソフトウェアやエージェント、システムを作るエージェント。ビジネスコンテキストがないと、汎用的なアプリしか作れません。
- **ビジネスエージェント**: カスタマーサポート、財務、HR などの実務を行うエージェント。

**コーディングエージェントと Rayfin**

コーディングエージェントが正しく作るには、データベースの中身、データの形、アプリが何をすべきか、ユーザーとのやり取り、チームの動き方、IT が定めたポリシーといった情報が、ビジネスコンテキストから来る必要があります。そこで、Rayfin にコーディングエージェントと対話させ、ビジネスコンテキストを持ち込んで **Fabric アプリ** を作らせる、という使い方を紹介しています。

Dorit 氏は、アプリが「どこかに置かれた静的な Web ページ」で終わりがちだと指摘し、Rayfin はその裏にデータベースを持たせて、ステートフルなアプリにできると説明しました。ストレージ、コネクタ、関数（functions）、認証（企業では特に重要）が揃っています。Rayfin が提供するものとして、フルカスタムの UX、アクション、ガバナンス付きの信頼できるデータ、スキルが挙げられました。

> 注意：Rayfin の綴りは、トランスクリプトで「Rayfin」「Raifen」と揺れています（音声認識の都合で表記が確定できません）。

**ビジネスエージェントとエージェントの成熟度**

Dorit 氏は、エージェントには連続的な段階があると話しています。

1. 1 人の質問に答えるアシスタント
2. チームのヘルパー
3. ワークフローエージェント（デモの Maya が使っているもの）
4. 完全自律のエージェント

自律まで進むには、**構築（build）、大規模なデプロイ、運用、改善のループ** が必要で、そのすべてが同じガバナンス層の下になければならないという説明です。

**モデルの選択肢**

「賢いモデルほど賢いエージェント」と考えがちだが、大事なのは **モデルの選択肢（optionality）** であり、適切なタスクに、適切なコストで、適切なモデルを使うことだと述べています。1 つのプラットフォームにあらゆるユースケース向けのモデルを用意し、データは非公開に保たれ、カスタマイズ、コストとレイテンシの把握ができ、安全性が組み込まれているという説明でした。

**エージェントを「資産」として扱う**

エージェントを、話しかける相手としてだけでなく、資産（asset）として捉えます。指示ファイル、スキル、ポリシー、テスト、評価（evals）はすべて、エージェントの動き方に関するビジネスコンテキストの一部です。資産として扱うと、次のことが可能になります。

- 異なるモデルやハーネスをまたいで移植できる（明日新しいモデルが出ても、動き続ける）
- バージョン管理により、エージェントが何をしたか、どのスキルを得たかを把握できる
- 他のエージェントの構築を、別のエージェントに手伝わせる

**CI/CD から本番へ**

バージョン管理、テストと評価による検証、ステージング、ポリシーがどう働くかの確認、大規模なリリースという一連の流れを CI/CD として用意するとのことです。ホスティング、デプロイ計画、自動スケーリング、安全なロールアウトにより、「午後にノート PC で作ったもの」がチーム全体へ展開できます。基盤は Azure で、グローバルな展開、スケール、セキュリティが組み込まれていると説明されました。

**運用と改善**

デプロイ後に何が起きているか分からなければ意味がなく、エージェントが暴走する可能性もあると Dorit 氏は述べています。そのため、次のような可視性と制御が必要です。

- トレースと監査ログ
- 監視とアラート
- ガードレール
- メータリングと予算

加えて、エージェントやアプリは初日はうまく動いても、1 週間後、1 カ月後、3 カ月後に状況が変わります。新製品や新ポリシーが出ることもあります。そこで AI 自身が振り返って、使われ方やビジネスの変化を理解する **改善ループ** が、企業で持続させる鍵だと語られました。

**ガバナンス**

最後の要素がガバナンスです。次の点が挙げられました。

- すべてに ID があり、すべてに所有者がいる（誰が責任者かを対応づける）
- 安全性と制御。人による監督と、AI のやり取りの一部としての人間の承認
- 監査とコンプライアンス
- フリート（群）としてのガバナンス

これらが Microsoft IQ Foundation にあたります。

### 5.10 Yitzhak 氏による締めくくり

孤立したエージェントやアプリは簡単に作れるが、重要なのは **断片化せずにつなぐ** ことだと述べられました。ポリシー、ツール、コンテキスト、スキルが相互に連携し、互いを使い合うことで、ある層への投資が使うほど複利的に効くという説明です。これにより、構築にかかる時間を減らし、信頼性を高め、コストを下げます。

発表の流れは次のとおりです。まずコンテキストを作り、エージェントとアプリがそれを再利用し、デプロイしてガバナンスをかけ、継続的に改善する、というサイクルです。M365 や Power BI のセマンティックモデルなど、長年の投資を活かせる点も強調されています。

## 6. デモ・手順

このセッションには 2 つのデモ（物語仕立ての実演）があります。どちらも画面操作の細部は音声からは分からないため、**語られた内容の範囲** でまとめます。なお、Business Plugins のデモの後で Dipti 氏が「2 倍速で話していた」と述べています。デモが録画か実演かは、発話からは確認できません（公式概要には「Watch us build an agent live」とあります）。

### 6.1 Business Plugins のデモ（Dipti 氏）

舞台は、Halo というデジタルウォッチ（スマートウォッチ）を製造するグローバル企業 Coldova（綴りは音声認識で揺れており、Caldova とも聞こえます）です。嵐の日にヒューストンのデータセンターで問題が起き、グローバルな流通（distribution）と顧客への納品を担当する Maya が、重要顧客 Aurora の注文が危うくなっていることに気づきます。

1. **Business Plugin なしの場合**: Maya が Copilot に対応策を尋ねます。返ってきたのは、「ルートの変更」など妥当だが一般的な内容でした。cross dock を使うべきだという提案も出ましたが、その拠点は洪水地域にあり、会社のポリシーにも沿いません。Copilot は文書にアクセスできても、完全なビジネスコンテキストを持っていないため、という説明です。
2. **Business Plugin の作成**: iq.microsoft.com の IQ Copilot で、Maya が、この質問に正しく、繰り返し一貫して答えるために何が必要かを IQ Copilot に尋ね、コンテキストを整えていきます。新しい Business Plugin を作り、必要な情報を追加します。Foundry IQ からナレッジベースも追加し、エージェントがいつ、どう使うべきかが分かるよう要約も加えます。
3. **階層**: 最上位には supply chain operations の Business Plugin があり、control tower の Business Plugin がそれを継承します。階層とネスト（入れ子）に従って情報が下に流れます。Word 文書、Excel スプレッドシート、Foundry IQ、Fabric IQ、Power BI レポートが 1 か所にまとまっています。
4. **昇格と有効化**: Business Plugin を promote（昇格）して activate（有効化）すると、Copilot で使えるようになります。
5. **Business Plugin 有効後**: Copilot に同じ質問をすると、「Aurora は tier one なので対応が必要」「洪水地域にあるデータセンターは使わない」「経路を変えて、ヒューストンの代わりにマイアミを使う」という回答になります。Maya は自分の権限の範囲で承認します。
6. **カスタムエージェント化**: 毎回繰り返さなくて済むよう、チームでカスタムエージェントを作り、同じ Business Plugin を有効にします。エージェントがアラートを出し、Maya は計画に問題がなければ承認するだけです。

> 補足：トランスクリプトには拠点名が「KD」「KDE」と出ますが、音声認識の都合で正確な名称が確定できません。

### 6.2 Rayfin のデモ（Dorit 氏）

Dorit 氏の「Here's the demo」という発言に続いて、再び Maya が登場します。

1. Maya は、ホリデーシーズンの需要急増に備えられているかを心配しています。サプライチェーンの状況を把握するだけでなく、自分が作ったエージェントを監督し、何をしているかを理解したいと考えて Copilot に依頼します。
2. Microsoft IQ のビジネスコンテキストをもとに、Copilot が自社のビジネスに合わせたアプリを作ります。
3. Maya は、Florida に問題があることをアプリ上で確認します。需要が上がった場合のビジネスへの影響も試せます。
4. エージェントの推奨事項を見て、適用するかどうかを決められます。
5. 続いて、エージェントを管理する画面に移ります。エージェントの実行内容や状態を確認できます。

Dorit 氏は、データアプリを作っただけでなく、ビジネスを動かすのに役立つものを作れたと述べています。さらに、これは **開発者ではない Maya が、実際のデータと実際の会社のコンテキストの上で、自分のために作ったカスタムアプリ** だと強調しました。

## 7. 注意点・発表者の気付き

- 課題として強調されたのは、エージェントのコンテキストが **断片的だと信頼できない判断になる** 点です。人間が結果を検証する負担も増えます。
- パイロットの構築は簡単でも、本番化は **何カ月もの作業** になりうるとされています。
- 組織ごとにエージェントを作ると、コンテキストやポリシーが **バラバラ（inconsistent）** になり、最適化されなくなります。
- デプロイした後に状況が見えないと、エージェントが暴走する可能性があります。
- デモの前半（Business Plugin なしの Copilot）は、一般的な回答が会社のポリシーに合わないことを示す例として使われました。
- Business Plugins の更新自動化（エージェントによるキュレーション）と Agent 365 との統合は、今後の計画の段階です。
- Microsoft IQ は **限定的なプライベートプレビュー** で、利用には申請が必要です。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

- **より根拠のある判断**: 自社のコンテキストに基づいた回答になります（デモでは、洪水地域を避け、ポリシーに沿った経路案が出ました）。
- **構築コストと時間の削減**: 毎回ゼロから作らず、コンテキスト、スキル、ポリシーを再利用できます。
- **一貫性**: 階層と継承、認定により、チーム間で同じコンテキストを共有できます。
- **ガバナンスの効いた本番化**: ID、所有者、人間の承認、監査、予算管理を備えます。
- **オープン性**: データのコピー・移行は不要で、Copilot 以外（Claude、Gemini、ChatGPT）からも 1 つの API で同じコンテキストを使えます。
- **EY の事例**: 160,000 社超の顧客、年間 1.5 兆件のレコード、640,000 人超のユーザーという規模で、1 つのエージェント基盤に収める取り組みが進められています。

## 9. まとめ

Microsoft IQ は、エージェントが自社のビジネスを理解するための **コンテキスト管理** と、エージェントを本番で信頼して動かすための **Foundation** を 1 つのプラットフォームとして提供するものです。コンテキスト側の中核は新機能の Business Plugins で、Work IQ、Fabric IQ、Foundry IQ、Web IQ、サードパーティのコネクタを束ね、階層、継承、認定、秘密度ラベルを備えます。Foundation 側は、モデルの選択、CI/CD、運用、改善ループ、ガバナンスを扱います。

試すには iq.microsoft.com でアクセスを申請します（プライベートプレビュー）。発表では、ドキュメントや動画、始め方の案内が用意されていると紹介され、フィードバックの送付も呼びかけられました。関連するセッションやラボが会期中に他にもあるとのことです。
