# BRK304 What's new in Work IQ

## 1. はじめに

このセッションは、Microsoft 365 の仕事のデータ（メール、チャット、会議、ドキュメントなど）を AI エージェントに渡すためのコンテキスト層である **Work IQ** の最新情報を紹介するものです。Work IQ が必要になる理由を説明し、Ignite で発表された新機能を整理したうえで、3 つのデモで具体的な使い方を見せています。1 つ目は営業準備で、Copilot と、同じコンテキストを使う独自アプリ（B2B）の両方が登場します。2 つ目は ServiceNow を接続したサポート対応、3 つ目は ChatGPT から Work IQ を使うケースです。

発表の中心にある主張は、**エージェントが仕事を終えられない原因は、モデルの性能ではなくコンテキストの不足にある**という点です。Work IQ は、既存の Microsoft 365 の権限やポリシーを保ったまま、そのコンテキストをエージェントに渡す仕組みとして位置づけられています。

## 4. 発表者が伝えたいメッセージ

Amanda 氏は、エージェントが仕事で役に立つには **context（コンテキスト）、action（アクション）、trust（信頼）** の 3 つが必要だと述べています。モデルは誰でも使えるようになっており、顧客商談に向かうエージェントも十分に優れたモデルを持っているはずだが、足りないのは「自分たちのビジネスがどう動いているか」という知識だという主張です。

Work IQ は、メールやチャット、会議、ドキュメントなどの、人々の働き方に関するコンテキストをエージェントに提供する層です。ユーザーの権限やポリシーをそのまま引き継ぐため、「委任しても信頼できる」状態にできると説明しています。さらに、プロンプトごと、エージェントごとにエンタープライズ環境を作り直さなくてもよいように、**再利用可能にする層**だと位置づけています。

## 5. 発表内容の詳細

### 5.1 エージェントが直面する「コンテキストの壁」

Amanda 氏はまず、自己紹介として Copilot にプロンプトを渡し、Work IQ を使って自分の仕事を可視化する画像を作らせたと話しています。経歴や履歴書、名前の一覧は与えず、Microsoft 365 上の履歴だけから、取り組んでいること、過去の仕事、戦略文書から読み取れる優先事項、参加している会議や会話、チームへの接し方から読み取れる価値観まで推論されたそうです。情報は 1 つの文書やメールにあるわけではなく、M365 の履歴全体から導かれたものだと説明しています。このコンテキストの仕組みが、Copilot 内のエージェントにも、自作のエージェントにも使えます。

Amanda 氏は多くの組織から「エージェントが組織に価値をもたらしているかどうか、どうすれば分かるのか」と聞かれると話し、エージェントが仕事で役に立つには、コンテキスト、アクション、信頼の 3 つが必要だと述べています。信頼については、他の従業員に設定済みの権限、ポリシー、制御がエージェントにも適用されていなければ、仕事を任せられないという考えです。

そのうえで、顧客との会議の準備を例に説明しています。必要な情報は、受信箱の最新メール、顧客との Teams チャネルでの議論（展開スケジュールへの反論）、アカウントチームの議論（エンジニアを追加できるか）、前月の会議メモと約束、CRM に出ている更新まで 60 日であること、サービスデスクにある誰も話題にしていないチケット、などに散らばっています。個々の情報は単体で意味がありますが、本当に重要なのは、それらがどうつながるかです。

エージェントはこれらを 1 つの全体像にまとめられず、「コンテキストの壁」にぶつかります。そのため人間が「接着剤」になり、6 つのアプリを開き、適切なバージョンを探し、プロンプトにコピーして、背景を AI に説明し直すことになります。それでもエージェントは一般的な答えしか出せず、仕事を完了できないことが多いそうです。**エージェントを増やしても、コンテキストがなければ解決しません。**また、より高度なモデルを使っても解決しないと述べています。必要なデータはすでに組織内にあるので、それをエージェントが利用できるようにし、人間は監督に回って制御を保てるようにする、というのが方針です。

### 5.2 IQ の構成要素

Amanda 氏は、チームの「ロックスター社員」を思い浮かべてほしいと言い、その人が持つ知識やスキルのように、エージェントに渡すコンテキストを次のように整理しています。

| 名称 | 説明 |
| --- | --- |
| Work IQ | チームの全員の働き方。メール、チャット、会議、ドキュメントなど、Microsoft 365 とビジネスアプリでやり取りされる情報。 |
| Fabric IQ | ビジネスの動き方。Power BI に作り込んだセマンティックモデルを、エージェントのコンテキストにでき、アナリストと同じように数字を理解させられる。 |
| Foundry IQ | 正規の知識を作るための仕組み。ベクターデータベース、サードパーティのデータベース、SharePoint サイト、Web、独自ドキュメントなどを、ナレッジベースとして整えてエージェントに提供する。 |
| Web IQ | 組織の外の世界（公開 Web）。使わせる範囲を制限できる。市場、競合環境、サプライヤー、規制のニュース、速報などを取得できる。 |
| サードパーティ IQ | Microsoft 以外の環境への対応。CRM やサービスデスクなどの SaaS を、コネクタープラットフォーム経由でコンテキスト層に取り込む。 |

### 5.3 Work IQ が理解すること

商談準備の例では、Work IQ は次の点をエージェントに理解させると説明されています。

- 関係する人物とその関係性、過去に議論したこと、約束したこと、チームが知っていること、優先事項
- メール、チャット、会議、ファイルから構築されるコンテキスト。最も信頼できる情報源となる人物の推論も含む
- 利用しているビジネスアプリやサードパーティ SaaS に関するコンテキスト

ポイントは、**追加の統合や権限設定が不要**なことです。既存の Microsoft 365 環境の権限とポリシーをそのまま使うため、エージェントも、そのエージェントに委任する人も、見てよい情報だけにアクセスします。これは「プロンプトと添付ファイルから始まるエージェント」から、「社員のようにコンテキストが蓄積していくエージェント」への転換だと説明しています。

Work IQ は、Copilot の各システムのほか、**MCP、REST、agent-to-agent** のプロトコルで独自アプリに組み込めます。Copilot Studio、Microsoft Foundry、GitHub Copilot から利用でき、Databricks、Google、Amazon など他のエージェントプラットフォームからも同じコンテキスト層にアクセスできると述べています。

### 5.4 共有コンテキストと、権限の考え方

デモのあと、Amanda 氏は仕組みを整理しています。Camille は Copilot で準備し、John は自社のアプリで作業しましたが、どちらも自分で何かをつなぎ合わせる必要はありませんでした。両者は同じコンテキストを使いつつ、それぞれの**個人の権限**の範囲で情報にアクセスします。この例では、パートナーとの共同作業でよくあるように、共有 SharePoint が使われていると説明しています。

### 5.5 効果を測った数値

Work IQ は「エージェントのために作られた」ものだとして、同じタスクを Work IQ と、Microsoft 365 の従来の API で実行して比較したと説明しています（デモは証明ではない、という前置きです）。

| 観点 | 結果 |
| --- | --- |
| 完了するタスクの数 | Work IQ のエージェント向け API を使うと **1.7〜3.9 倍**。コンテキスト不足で止まりにくいため |
| 所要時間 | 完了したタスクで **最大 70% 短縮**。検索や再試行が減り、プロンプトを書く人が穴埋めをする必要が減る |
| コスト | 完了したタスク当たりのコストが **40〜74% 低い**。エージェントのコストは「完了タスク当たり」で考えるのが適切だと述べている |

### 5.6 Ignite で発表された新機能

Amanda 氏は、発表内容を context、action、trust の 3 つに分けて紹介しています。

**Context（コンテキスト）**

- より豊かな検索（richer retrieval）
- リアルタイムの Teams トランスクリプト
- 60 を超える SharePoint ツール
- メモリ。Copilot がアクセスできるメモリに、独自のエージェントや他のエージェントクライアントからもアクセスできる

**Action（アクション）**

- Word、Excel、PowerPoint を扱う作業（当日朝の発表で紹介された内容として触れています）
- 重要なことが起きたとき、プロンプトを待たずに**プロアクティブに反応**する。そのためのイベントの仕組み（eventing）が Work IQ から提供される。例として、特定のメールが届いたとき、会議が設定されたとき、が挙げられています

**Governance and trust（ガバナンスと信頼）**

- コンテンツのサニタイズ、来歴（provenance）、きめ細かい制御など、人間のユーザーに与えるのと同種のコントロールを、エージェントにも適用する

### 5.7 Plugin Registry

Microsoft 以外のシステムを含む異種環境に、このコンテキスト層を広げる仕組みが「Plugin Registry」です。システムをパッケージ化して、エージェントが扱い方を理解できるようにします。構成要素は次の 3 つです。

1. **Skills**：仕事のやり方を書き下した、エージェント向けのプレーンテキストの指示。
2. **Tools**：さまざまなシステムを統合するもの。Plugin Registry の一部として **250 を超えるコネクター**を提供しており、オープンプロトコルの MCP により、自作または SaaS プロバイダーが提供するシステムを数多く追加できる。
3. **Agents**：Skills と Tools を Work IQ と組み合わせ、処理のガバナンス、指示、可観測性を高めるもの。例として、Fourth Coffee が ServiceNow を統合するケースや、Wide World Importers の出荷履歴などのコンテキストを持つ別のエージェントがあげられています。

**Agent 365** は、Copilot から展開されたエージェントと、自社で作って展開したエージェントのすべてを、組織全体で可視化するものとして触れられています。

### 5.8 パートナーが Work IQ を取り込む事例

逆方向の取り組みとして、パートナーが Work IQ を自社のエージェントやツールに取り込んでいます。重要なのは統合の方法ではなく、他の製品内のエージェントも Microsoft 365 のコンテキストを理解できる点だと説明しています。

| パートナー | 発表された内容 |
| --- | --- |
| Adobe | CX Coworker の体験に Work IQ を取り込み、顧客データ、コンテンツ、ビジネスコンテキストを業務の流れの中でつなぐ |
| Atlassian | Rovo Studio に Work IQ を統合し、ビルダーが Microsoft 365 のコンテキストを持つエージェントを作れるようにする |
| SLB | エネルギー業界向け AI アシスタント Tela に Work IQ を取り込み、エネルギー分野のエンジニアに、Microsoft 365 での人同士のやり取りから蓄積されるコンテキストを提供する |

さらに OpenAI との連携として、ChatGPT 向けの Work IQ プラグインが紹介されています（6.3 を参照）。

## 6. デモ・手順

このセッションでは 3 つのデモが行われました。録音から分かるのは語られた範囲に限られ、画面の細部は音声からは確認できません。なお、プロンプトの応答に時間がかかるため、デモの一部は「ready-made（事前に用意した）プロンプト」に切り替えて見せています。

### 6.1 デモ 1：営業担当 Camille の商談準備（Lior 氏）

**登場人物と設定**

- Camille：Fourth Coffee Roasters のグローバルセールスリード。ニュージーランドへの展開を進めている。
- John：Wide World Importers（物流会社）にいる Camille のパートナー。B2B のシナリオとして紹介された。
- 顧客：Contoso。Dynamics 365 に 120K（12 万ドル）の商談がある。

**手順（語られた順）**

1. Camille は Dynamics 365 から 1 日を始め、Contoso の商談を確認する。
2. Cowork に「Contoso のニュージーランド展開のフォローアップについて、Dynamics の商談、議論のメモ、調査、Power BI のパイプラインを含む短いブリーフィングを」とプロンプトを送る。Lior 氏は応答に時間がかかるため、「料理番組のように」事前に用意した画面へ切り替えると断っている。
3. Dynamics 365 の情報、OneDrive、Teams、メール、ファイルなどのエンタープライズコンテキストが集められる。最初に Power BI のレポートが表示され、先ほどの 120K が Contoso として確認できる。
4. チャットを離れずに、同じ商談を開くことができる。
5. Camille は John との Teams のやり取りを見直したいと Copilot に依頼する。Cowork が提示した文書の 1 つとして、Camille が John と共有した「New Zealand logistical proposal request」が開かれる。
6. John 側の画面に切り替える。John は「Octopus」という自社のチャットボット（独自アプリ）で作業し、「Camille との物流提案の準備」をプロンプトで依頼する。
7. 応答の途中で、アプリが **conversation API と chat API** を使っていることが見える。独自アプリのエージェントを Work IQ API に向けると、同じ情報、同じ機能、同じコンテキストを得られる、という説明です。
8. 結果には Outlook のメールや文書が含まれ、最後に使われた情報源の一覧が表示される。開いた文書は Camille 側で見たものと同じで、John と Camille が B2B で同じコンテキストを共有していることを示している。
9. Cowork に戻り、Camille が Contoso 以外にも Woodgrove、Lakeshore、Northwind の顧客を抱えていることを示す（AdventureWorks も試したが動かなかった、と話しています）。
10. 最後に Camille は、ニュージーランド展開のための物流計画と、地図などの可視化を依頼する。計画は、そのままの案が却下される形になり、Cowork は **Auckland と Christchurch に展開し、出荷コストを分担する**ことを提案した。Amanda 氏は「より強い商談機会になる」と補足している。

**Amanda 氏との確認のやり取り**：Camille が自分でやったのはプロンプトを入力することだけでした。Dynamics 365、Power BI、Fabric IQ、ファイル、Teams メッセージ、Outlook の接続は、組織があらかじめ設定した拡張性（pluggability）によるものだと説明されています。

### 6.2 デモ 2：サポートエンジニア Julie のインシデント対応（Lior 氏）

Fourth Coffee のニュージーランド展開が終わった後（「編集の魔法で」と話しています）、POS システムが止まり、Julie に問い合わせが来る、という設定です。

1. Cowork で「店舗でカード決済が遅いと報告されている。何が起きているか。誰が調査すべきか」とプロンプトを送る。
2. ServiceNow が呼び出される。Fourth Coffee では ServiceNow コネクターが設定されており、その背後のプラグインから ServiceNow のインスタンスにつながっている。
3. プラグインには **スキルをバンドル**でき、このデモでは「ServiceNow incidents」スキルが、インシデントの分析と Julie への伝え方をエージェントに理解させる。
4. 回答に ServiceNow のインシデントが表示される。インシデントを開こうとして内部エラーが出たが（予定外とのこと）、もう一度クリックして開けた。Ben という人物が遅い認可を報告しており、RV-01、RV-02 という名称で POS システムが関係している（音声認識の都合で表記が確定できません）。インシデントは 3 件あり、同じパターンが見える。「誰が助けるべきか」への回答には Sam が挙がる。
5. 2 つ目のプロンプトで、Julie は POS システムに慣れていないとして、アーキテクチャと最近の変更を教えてほしいと依頼する。チャット内で「store checkout architecture」の文書を開ける。Lior 氏は、このとき「プラグインは接続されていない」と述べています。
6. 3 つ目のプロンプトで、「Riverside のインシデントを、POS を担当するフィールド技術者の Sam に割り当て、わかった内容を追記して」と依頼する。編集により割り当て完了の状態を見せている。
7. Amanda 氏は、Julie が「Sam」と書くだけで、組織内の **Sam Patel** という特定の人物だと推論されたと補足している。

### 6.3 デモ 3：ChatGPT 上の Work IQ（Vibhor 氏）

Amanda 氏は、全社が Copilot に標準化しているわけではなく、ChatGPT を使う人もいるとして、Work IQ が他の環境にも現れる例を紹介しています（「この会議で見られる ChatGPT のデモはこのセッションだけ」と冗談交じりに話しています）。

前提として、Vibhor 氏は Work IQ が OpenAI の **Plugin Directory で今日から利用可能**だと述べています。技術スタックの再設計やカスタム統合は不要で、プラグインを入れるだけで使え、IT が設定した権限が適用されるため、エージェントはユーザーと同じ権限で動きます。

**比較の数値**：Microsoft が 81 の企業向けタスクで、Work IQ なしの現行プラグインと、Work IQ プラグインを比較したと説明しています。ChatGPT は Work IQ プラグインで 71% 多くのタスクを完了でき、旧プラグインは 42% だったとのことです（音声の表現のとおりで、71% が完了率か増加率かは発話からは判別できません）。コストは 40% 低く、行き止まりが減り、速度は同等でした。

**デモの設定**：Fourth Coffee Roasters がニュージーランドで新しいコーヒーを発売する。マーケティングコンサルタントの Alice が ChatGPT を使う。会社は Work IQ を使っており、Alice には適切なアクセス権が付与されている。プロンプトは時間節約のため、事前に実行したものを見せています。

1. 「ニュージーランドの顧客が好むコーヒーのフレーバーは何か」と尋ねる。ChatGPT が Work IQ プラグインで Fourth Coffee Roasters の過去の文書を取得し、ニュージーランドの顧客の好みのデータが出る。
2. ChatGPT は **Generative UI** でビジュアルを作る。顧客は cocoa-caramel（ココア・キャラメル）のフレーバーを好む。（なお、途中で Vibhor 氏が別の画面を開いてしまい、Amanda 氏が「Copilot をデモしている」と冗談を言う場面があり、スライドに戻しています。）
3. 次に、このフレーバーに近いコーヒーが社内にあるかを尋ねる。Work IQ により、2024 年の、約 3 年前（と発話どおり）の文書から **Project Ember** が似たフレーバーだと見つかる。ChatGPT は、レシピが現在も再現可能か、顧客の好みが調査当時から変わっていないかを確認すべきだとも助言した。
4. 最後に、過去の仕事から、コーヒーのパッケージのバージョンを探す。Project Ember の一環で作られた **2 種類のパッケージ**が見つかる。画像を展開すると、SharePoint 経由で Work IQ から取得した画像と詳細を確認できる。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 追加の統合や権限の設定をせず、既存の Microsoft 365 の権限とポリシーを保ったまま、エージェントにコンテキストを渡せる。
- エンタープライズ環境をプロンプトごと、エージェントごとに作り直す必要がない。
- 従来の API と比べ、完了タスク数が 1.7〜3.9 倍、所要時間が最大 70% 短縮、完了タスク当たりのコストが 40〜74% 低下（Microsoft の比較）。
- 独自アプリ、Copilot、ChatGPT など、利用者が使う場所で同じコンテキストを使える。
- 情報を探し回る人間の手間が減り、新しく加わったコンサルタントや新任のサポートエンジニアでも、社内の背景を知らずに必要な情報にたどり着ける（デモで示された例）。

## 9. まとめ

エージェントが仕事を完了できない主な原因は、モデルではなくコンテキストの不足であり、Work IQ はメールやチャット、会議、ドキュメントなどの Microsoft 365 のコンテキストを、既存の権限のまま、再利用可能な層として提供します。Work IQ は Fabric IQ、Foundry IQ、Web IQ、サードパーティ IQ と並ぶ構成要素の 1 つです。

Ignite では、コンテキスト（richer retrieval、リアルタイムの Teams トランスクリプト、60 超の SharePoint ツール、メモリ）、アクション（イベントの仕組み、Word/Excel/PowerPoint）、ガバナンスと信頼（サニタイズ、来歴、きめ細かい制御）の強化が発表されました。Plugin Registry と 250 超のコネクター、MCP で外部システムに広げられ、Adobe、Atlassian、SLB、そして ChatGPT へと Work IQ が取り込まれています。
