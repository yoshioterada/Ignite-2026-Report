# BRK297 The shift from RAG to context: Grounding agents with Foundry IQ

## 1. はじめに

このセッションは、AI エージェントに企業データを渡す「コンテキスト層」を、Microsoft IQ と Foundry IQ（Azure AI Search の進化形）でどう作るかを、実際の画面を見せながら説明する 45 分の発表です。エージェント開発者、検索基盤や RAG を構築している開発者、データ基盤の担当者に向いた内容です。

発表は 3 つの柱で進みます。

1. **使いやすさ**：Foundry プロジェクトが丸ごと管理する Foundry IQ のナレッジベースと、12 月に GA が予定されている Foundry IQ Serverless
2. **品質とトークン効率**：ナレッジグラフ（Entity Graphs と Topic Graphs）と、新モデル Microsoft Retriever 1 / Microsoft Ranker 3
3. **エンタープライズ対応**：SharePoint、ファイルアップロード、SQL DB インデックス作成の GA と、アクセス権限（permission）の伝播

最初に結論を一言でいうと、**単純な検索で足りる場面ではシンプルなままでよい。一方で、集計や俯瞰が必要な複雑な質問には、検索以外の部品（プリミティブ）が要る**というのが、発表者の立場です。

## 4. 発表者が伝えたいメッセージ

- 多数のエージェントが、信頼できる企業ナレッジを安全に使うために、**共有のコンテキスト層**が必要になっている。Microsoft IQ がその入口で、Foundry IQ は非構造化コンテンツのナレッジベースを作る場所である。
- ナレッジベースの**作成**は技術者向けの作業だが、**利用**は組織全体に摩擦なく広げられるべきである。
- 単純な検索インデックスで十分な場面では、複雑なことをしなくてよい（「シンプルなシステムのほうがよい」）。複雑な質問のために、グラフやトピックなどの新しいプリミティブと、速い Agentic retrieval を用意している。
- エンタープライズでは、ネットワーク分離やアクセス制御の伝播も、検索品質と同じくらい重要である。

## 5. 発表内容の詳細

### 5.1 Microsoft IQ と Foundry IQ の位置づけ

発表者は、Microsoft IQ を「企業のコンテキスト管理システム」と説明しています。会社が持つデータ資産全体への**単一の入り口**となり、構造化データ、M365 で作る生産性コンテンツ、あらゆる非構造化コンテンツ、Web、さらに多数のコネクターを束ねます。例として、Copilot Cowork は会社全体を探索することをエージェントに求めるため、すべてを見渡せる集中的な入り口が要る、という話がありました。すべてのエージェントが汎用である必要はなく、特定のエージェントを特定のデータの一部に向けることも引き続きできます。

汎用的なケースでは、Copilot のような画面から企業コンテキストのどこでも探索でき、そこで起きていることを 1 つのシステムで統制・監視できることが望ましく、後者を担うのが **Agent 365** だと位置づけています。

**Foundry IQ** は、非構造化コンテンツ向けのナレッジベースを作る場所です。作ったナレッジベースは、目的特化型のエージェントにも、Microsoft IQ のエコシステムにもつなげられます。

### 5.2 Foundry IQ のスタックと名前の由来

Foundry IQ は **Azure AI Search の進化形で、同じものです**。Azure ポータルからも Foundry からも使えます。発表者によると、スタックを発展させるうちに、検索ではない部品も多く扱うようになり、検索に限定されない、より一般的な名前が必要になったとのことです。

スタックは次の構成です。

| 層 | 内容 |
| --- | --- |
| 下層 | データソースへ接続し、データを取り込む層 |
| 検索の基盤 | 字句（lexical）検索とベクトル検索。ベクトル検索データベースとしてだけ使うこともできる。リランキング、ハイブリッド検索も組み込み済みで、組み合わせを選ぶだけ |
| 上層 | より複雑な問題をその場で扱う Agentic retrieval の層 |

### 5.3 使いやすさ：Foundry 管理のナレッジベースと Serverless

#### Foundry プロジェクトが管理するナレッジベース

Foundry を使っている開発者が、エージェント用にその場でナレッジベースを作りたいとき、追加の部品を探し回らなくて済むようにする取り組みです。今後は、Foundry IQ のナレッジベースを、含まれる Foundry プロジェクトが**丸ごと管理する**選択肢が使えるようになります。プロビジョニングも管理も権限設定も不要で、Serverless 版を基にしているため、固定の追加コストもありません。

#### Foundry IQ Serverless は 12 月に GA

発表者は、**Foundry IQ Serverless が 12 月に GA になる**と発表しました。本番利用できる状態になることを意味します。

| 項目 | 語られた内容 |
| --- | --- |
| 特性 | ゼロまでスケールダウンでき、コストはストレージ分のみ。必要なだけ作成でき、即座にプロビジョニングされ、すばやく立ち上がる |
| 品質と SLA | 品質面の部品がすべて揃った本格的な検索システムで、本番グレードの SLA が付く |
| 制限の拡大 | GA に向けて、インデックスサイズを 10 GB に、1 サービスあたりのインデックス数を最大 10,000 に引き上げる（1 つの検索サービスに 100 TB のデータを置ける計算と説明） |
| 互換性 | 既存の（専用の）サービスと完全な互換性があり、プロビジョニング時の違いだけ |

専用（dedicated）サービスは、非常に大規模なシナリオや専用のコンピュートが必要な場合に向いていて、数十億件のドキュメントを持つインデックスを運用している顧客もいる、と述べています。一方、作成と削除を素早く繰り返す動的なシナリオや、使われていないときは休眠させたい場合に Serverless が向いています。

### 5.4 品質：プレーンな RAG が届かない質問

発表者はまず、「多くのシナリオではプレーンな RAG、つまり検索インデックスの参照でうまくいき、そのときは複雑にしなくてよい」と断っています。そのうえで、単純なシステムでは足りない 2 つの例を挙げました。題材は、約 10 年分の Microsoft の決算説明会（earning calls）のトランスクリプトです。

- **集計の質問（zoom-in）**：「Dragon Copilot を使っていると言及されたヘルスケア組織は何件か」。答えがそのまま書かれたチャンクがなければ答えにくく、「全部を走査したか」の確認も難しい。力ずくでエージェントに全トランスクリプトを読ませるとトークンを大量に消費する。構造を取り出して問い合わせ可能にする方法が要る。なお、これは Microsoft の顧客数ではなく、**トランスクリプトで言及された数**を問うものです。
- **俯瞰の質問（zoom-out）**：「AI の需要がインフラを上回ったとき、Microsoft はどう対応したか」。複数の製品、複数の決算説明会、複数のリージョンをまたぐ時間的な経緯の話で、1 か所に答えがない。取得結果を並べ替えても、必要な断片がすべて入る順序は存在しない。データをもっと理解する必要がある。

必要な能力は 3 種類に整理されました。

1. 事実を探す：検索が得意で、今後も改善を続ける。
2. コンテンツの潜在的な構造（要素と、その間の関係）を理解して活用する。
3. コーパス全体の高位の構造を理解し、テーマごとにまとめ、関係を把握する。

2 と 3 は、検索システムだけではモデル化しにくいとして、プリミティブを増やす方針が説明されました。これまでにキーワード、ベクトル、ハイブリッド、リランキングを提供し、1 年以上かけて Agentic retrieval に取り組んできました。今回、**ナレッジグラフを Foundry IQ のネイティブなプリミティブとして**加えます。グラフはインデックスと別のシステムではなく、**同じ情報をテキスト、ベクトル、グラフとして表現できる 1 つのシステム**です。

### 5.5 ナレッジグラフ①：Entity Graphs

ナレッジグラフは、構造のためのコンポーネントである **Entity Graphs** と、全体の要約的な視点のための **Topic Graphs** の 2 つから成ります。

Entity Graphs では、データの重要な要素とその意味を、ユーザー自身が記述します。すべてを書く必要はなく、重要なものだけで構いません。例えば決算説明会のトランスクリプトなら、会社、製品、人物と、それらの関係を扱います。

1. ユーザーがスキーマ（オントロジー）を与える。
2. 次のどちらかでデータを渡す。トリプル（グラフのエッジ）を直接送る、または生のコンテンツを指定する。
3. 生のコンテンツを指定した場合、Foundry IQ がスキーマに沿ってエンティティと関係を抽出する（schema-guided entity extraction）。
4. 通常の検索用のチャンク化とベクトル化を行いつつ、同時にエンティティと関係を抽出し、チャンクインデックスとともにインデックスに格納する。

評価の結果、複雑なシナリオでは回答できる質問数が大きく増え、**同じ質問に使うトークンが約 64% 少ない**と述べています。単純な RAG でうまくいくケースでは、すでに飽和しているので改善しないとも断っています。評価は公開されており、グラフが得意な質問のパターン（「X は Y より多いのはどれか」、「この事実を裏付けるものは何か」、「何件か」といった集計系の質問）も示しています。

### 5.6 ナレッジグラフ②：Topic Graphs と結果の多様化

Entity Graphs が「ズームイン」なら、Topic Graphs は「ズームアウト」です。同じ決算説明会のデータで、**トピックの階層**が見つかる様子が示されました。

- クエリが「ローカル」と判断される場合は、階層のどこか 1 か所に降りて、そこにあるドキュメントだけを検索する。ほかの場合は、複数トピックをまたぐ横断的な見方をする。この local/global の選択は自動で行われる。
- このワークフローのステップを実行すると、トピックマップとその元になるクラスターが作られる。希望すれば、人間が読めるサイトマップも生成される。

構築したトピック情報は、2 つの用途に使えます。

1. **オントロジー（スキーマ）作成の出発点**：システム全体の形が分かるため。
2. **結果の多様化（result diversification）**：情報検索でよくある、ランキングに集中しすぎる問題への対応です。質問との一致度だけで厳密に並べると、同じ話題のドキュメントばかりになり、別の話題をカバーするドキュメントが入らなくなります。Topic Graph で多様化を有効にすると、各クラスター内で最も関連性の高いものを選びつつ、クラスターをまたいで取得し、結果の多様性を最大化します。

多様化には、英語のテキストは不要で、**ベクトルの重心（centroid）**だけで足ります。希望すれば、読めるテキストを逆生成して、エージェントがコーパスをナビゲートするサイトマップとして使えます。

発表では、「RAG のみ → エンティティを追加 → トピックによる多様化を追加」という順に、各段階で品質が改善していくグラフが示されました（クエリがこの能力を必要とする場合という前提）。さらに、**同じ答えを得るためのトークンは半分**になったと述べています。ナレッジベースが適切な事実を見つけるのがうまいため、走査の手間が減るからです。

発表者は、ローカルディスクにファイルを置いてエージェントに探させる方法も、小さなコードベースや小さなデータセットなら成立するが、規模が大きくなると現実的でないと話しています。顧客と話すと「このフォルダーに数百万の PDF がある」という例が非常によくあり、契約書（保険会社など）や、産業分野の仕様書などが例に挙がりました。

### 5.7 基盤となる API とプラグイン

エンドツーエンドの体験に加えて、下層の仕組みへも直接アクセスできる、というのがここでの主張です。

- **プラグイン**：ここまでのワークフローをスキルのセットとして、プラグインにまとめて提供している。ダウンロードして自分のコーディングエージェントなどで使え、Foundry IQ の作業（インデックスの作成、データ取り込みなど）やグラフを理解していて、発表のシナリオも再現できる。「Ignite のデモを一緒にやって」と頼むと、同じデモを自分のデータまたはこのデータセットで再現してくれる、と説明している。
- **`/retrieve`**：ナレッジベースに自然言語で質問する。**ナレッジベースはすべて MCP サーバー**として使え、通常の検索、Agentic retrieval、グラフ検索のどれを使うかは、質問の性質に応じて内部で選ぶ。
- **トリプルインデックス**：Foundry IQ の完全なインデックスで、subject-predicate-object のテーブルになっている。ソースから確率的に抽出するため、信頼度（confidence）の値があり、元のチャンクへのポインターもある。グラフとチャンクのインデックスはつながっており、検索とグラフクエリを組み合わせられる。
- **GQL**：クエリエンジンに直接 GQL でクエリを書ける。集計の質問に表現力がある。発表者は「GQL にはクセがあるが、書くのはエージェントなので、エージェントの問題」と冗談めかしている。
- **チャンクインデックス**：検索エンドポイントで直接検索でき、プレーンな RAG で足りる場合はそのまま使える。
- **トピック**：内部ではベクトルクラスターとして構築されるが、トピックマップを作れば、人間が読めるトピックになり、アプリの体験やエージェントのナビゲーションに使える。
- **多様化**：通常の検索で多様化を有効にするには、検索 API をトピックグラフに向ける。

> ご参考：グラフについては、翌日に BRK307 でセッション全体を使って扱う、と案内されました。

### 5.8 Agentic retrieval と Microsoft Retriever 1 / Ranker 3

Agentic retrieval は 1 回の検索では答えられない質問に答えられる反面、遅いのが課題でした。検索に長く携わってきた発表者は、検索パイプラインに 10 ミリ秒、100 ミリ秒の遅延を足す議論は大変なのに、Agentic retrieval は 10〜15 秒かかっても皆が受け入れているが、対話型の体験では受け入れがたいという趣旨を述べています。

そこで、**Microsoft Retriever 1 と Microsoft Ranker 3 の 2 つの新モデルを、その日から展開する**と発表しました。

- **Retriever 1**：Agentic retrieval のオーケストレーターとして作られた専用モデル。この 1 つのタスクに限って大きなモデルと同等の品質を目指し、高速。発表者は、特定のタスクに絞れば小型・高速・経済的なモデルで非常によい結果が出る例として、「Microsoft Decision One」を挙げている（音声認識の都合で表記が確定できません）。
- その結果、**サブ秒（sub-second）の Agentic retrieval** になった。グラフの左側はナレッジベースで、Retriever 1 を有効にした automatic effort モードが、1 秒未満のままで品質の境界（Pareto boundary）を押し上げている。反対側には、自分で選ぶ最高性能の LLM を使い、遅延と引き換えに品質を高める auto モードがあり、選択できる。右側のコア検索では、遅延は 1 秒程度かそれ以下で、品質が大きく向上している。
- カスタムモデルなので、**プロビジョニングも設定も不要**。Retriever モードで実行すると宣言するだけ。
- 同じ質問に必要なトークンは**約 32% 少ない**。推論の内側のループが、巨大モデルではなく、専用の高速なオーケストレーターで回るため、と説明している。

> 補足：Microsoft Ranker 3 は 2 つの新モデルの 1 つとして名前が挙がっただけで、発表では個別の説明はありませんでした。

> 補足：グラフの凡例にあるモード名（automatic effort、auto など）の対応は、音声だけでは確定できません。上の説明は聞こえた発言に沿った記述です。

評価は公開されており、方法論、評価データ、結果を資料で読める、と案内されました。Agentic retrieval 全般は、同じ週の別セッションで全体を使って扱うとのことです（セッションコードは発表では言及されていません）。

### 5.9 エンタープライズ対応

ネットワーク分離、アクセス制御情報の伝播、産業グレードの基盤など、実運用での問いに応えることも重要で、投資を続けているという位置づけです。この日の発表は次のとおりです。

| 項目 | ステータス |
| --- | --- |
| SharePoint のインデックス作成 | GA |
| ファイルアップロード | GA |
| SQL DB のインデックス作成 | GA |
| OneLake shortcuts | パブリックプレビュー |
| Fabric Data Agents | パブリックプレビュー |
| Fabric Ontology のサポート | パブリックプレビュー |

すでに Cosmos DB、SQL、Blob Storage、ネイティブの検索インデックスなどのデータソースをサポートしています。権限伝播に対応するデータソースでは、**権限を完全に伝播**します。Foundry と Fabric の統合を広げ、構造化データと非構造化データの混在に対応します。

**SharePoint** は、取り込み元として顧客から最も多く求められている項目と紹介されました。Foundry IQ へのコンテンツのインデックス作成に対応し、コンテンツを自分のシナリオ向けに変換したい場合や、グラフなどと組み合わせたい場合に便利だとされています。Entra ベースのアクセス制御ポリシーを完全に伝播し、ソース側の権限がそのままターゲットに引き継がれます。

発表者は、「ドキュメントをフォルダーに入れてベクトルデータベースにインデックスし、アクセス制御情報を置き去りにする」というよくあるパターンを問題視しており、企業では権限が仕事の進め方の要なので、権限が他の情報と同じように流れるシステムが望ましいと述べています。

これらの機能は Foundry で使えますが、MCP でも公開されているので、**別のスタックでエージェントを作る場合にも同じように適用できます**。Microsoft IQ からも、Foundry IQ のエコシステムの中でこのナレッジベースを見つけられます。

## 6. デモ・手順

画面を使ったデモが複数あります。録音は音声のみのため、画面上の細部（ボタンの位置、正確なラベルなど）は確認できず、**語られた範囲**で記載します。トランスクリプトに「No audio」と表示される箇所もあります。

### 6.1 Microsoft IQ のビジネスプラグインに Foundry IQ をつなぐ

1. 発表者自身の Microsoft IQ のインスタンスを開く。
2. 約 10 年分の Microsoft の決算説明会のトランスクリプトを使った、架空の「ビジネスプラグイン」（金融分析向け）が作ってある。
3. プラグインにはスキルがあり、すでに Foundry IQ のインスタンスがつないである。
4. 新規に追加する手順は簡単だと説明された。IQ にパーツを追加し、名前が分かれば直接、分からなければ組織で作成済みのナレッジベースを閲覧して探せる。
5. 見つけたナレッジベースについて、「何が入っているか」と「Copilot や他のエージェントはいつそれを使うべきか」を記述する。この 2 つで準備は完了。
6. 以降、Cowork や Copilot が決算説明会などの情報を必要とすると、探す場所が分かる。
7. 事前に実施済みの Copilot の画面で、決算説明会に関する質問をした結果を見せた。回答は Foundry IQ から来ている。ユーザーはそれを意識する必要はなく、Microsoft IQ が適切なビジネスプラグインを見つけ、その先のソースを指す。

### 6.2 Foundry で、管理されたナレッジベースを作る

1. Foundry を開く。すでにいくつかのナレッジベースがある。
2. 使用する Azure リソースの欄は「Foundry IQ resource」になっている。何もプロビジョニングしていないことを意味する。
3. ナレッジベースを作る際、既存の検索インスタンスを選ぶか、「Foundry に管理させる」を選べる。ここでは、Foundry プロジェクトを作っただけで、ほかは何もしていない。
4. 名前を付ける（「transcripts」）。実際のシナリオでは他のソースにも接続できるが、手早く始めるため、ファイルをまとめて渡した。
5. 取り込み、チャンク化、ベクトル化、インデックス作成を行い、ナレッジベースとして保存される。
6. 作成したナレッジベースは、Microsoft IQ で見つけられるほか、MCP サーバーなので任意のフレームワークのハーネスから指せる。Foundry で「build an agent」を選び、エージェントを作ってからナレッジベースを指すこともできる。配線は内部で行われる。
7. 「Knowledge」で「Add」を選ぶと、先ほど作ったナレッジベースが出る。エージェントを公開すると、そのエージェントがこのナレッジベースを使う。
8. ソースデータの変更に追随して、データは更新され続ける（複数のインデックスやデータソースにも対応できると補足）。

### 6.3 Azure で Foundry IQ Serverless を作る

1. Azure で、名前を付け、リージョンを選ぶ（Central〜と聞こえた部分は音声が途切れており、正確な名称は不明）。
2. 価格レベル（tier）では、既存のレベルに加えて **Serverless** を選べるようになっている。
3. Serverless を選ぶと、即時にプロビジョニングされ、実際に使うまでコストは発生しない。
4. 作成の速さは、クライアントのポーリング周期のほうが遅いほどで、1 回更新すると作成済みになっていると説明された。
5. 作成後は、専用サービスと同様に動作する。

### 6.4 ナレッジグラフのプレイグラウンド（Entity Graphs）

プレイグラウンドは、オントロジーやスキーマの作成、前述のワークフローを動かせる機能を備えていて、スキルのセットとしてプラグインにも同梱されています。

1. 質問「その製品について、何件のヘルスケア組織に言及したか」を、2 通りの方法で実行して比較する。
2. **Passages クエリ**：速いが、1 つの答えを探そうとして、どこかに書かれた答えを拾ってしまい、誤る。その答えは、製品を使っているすべての組織のことで、トランスクリプトで言及された組織ではない。
3. **グラフによる回答**：言及された具体的な組織を見つけ、それぞれの根拠となる箇所へのポインターも付く。
4. 履歴を見ると、内部で次の順に動いたことが分かる。クエリプランナーが非構造化の検索を数回実行し、グラフクエリを作って実行し、全体に対して Answer Synthesis を行った。
5. 自然言語で直接使え、グラフと通常のインデックスの選択、グラフクエリの生成は自動で行われる。
6. 内部を見ることもできる。グラフ全体を重ねると乱雑になるが、オントロジー（スキーマ）を見ると、データセットのいくつかの切り口が分かる。決算説明会は会計期間に対応し、話す人と、質問する人、答える人がいる、という具体例が挙げられた。
7. 生のクエリを書く例：GQL で、「組織が製品を開発し、その製品がある機能をサポートする」というパターンのトリプルを探す。答えは、「Microsoft が開発する、ワークフロー自動化を行う製品のうち、決算説明会で議論されたもの」。すべての製品ではなく、決算説明会で議論された製品である。

### 6.5 トピックの抽出と結果の多様化

1. 同じ決算データに対してトピック抽出を行い、トピックの階層を表示する。
2. 多様化の比較図：左はベクトル検索、色はトピッククラスターを示す。ベクトル検索はほとんど同じトピックで固まる。右は、さまざまなクラスターからの結果が含まれ、多様性が高い。
3. 抽出したトピックの例では、「capacity」や「modernization」といったカテゴリーの下にさらに分類があり、それぞれ少数のドキュメントに紐づく。教師なしで、データセットに向けて実行するだけで得られると説明された。

### 6.6 HTTP で各エントリポイントを呼ぶ

発表者は、エージェントがコードを書く時代であり、言語は HTTP という中立なものを選んだと説明しています。コード自体の読み上げはありません。

1. ナレッジベースの `/retrieve` に自然言語の質問を送る（これまで見てきた内容）。
2. トリプルインデックスを表示する。subject、predicate、object の表で、信頼度と、元チャンクへのポインターがある。
3. GQL クエリエンジンを直接使う。使ったトリプルインデックスのスキーマに沿ってクエリを書く（途中で画面を閉じてしまうという場面があった）。
4. チャンクインデックスを検索エンドポイントで検索する。
5. トピックマップを生成し、読める形のトピックを表示する。

### 6.7 Retriever 1 によるサブ秒の Agentic retrieval

1. Xbox ゲームと競合コンソールでの動作に関する質問を、インデックスに対して実行する。
2. まず semantic モード（ベクトル + キーワード + リランカー）で実行し、回答を見る。
3. 次に agentic に切り替える。Agentic retrieval の有効化に必要なのはこれだけ、と説明された。「query type equals agentic」を指定する。
4. 1 回目の検索の結果から、モデルは、質問になかった情報（Xbox の一部として「Play Anywhere」がある）を学んだ。
5. その情報で 2 回目のクエリを作り直し、よりよいドキュメントを取得した。
6. 十分な情報があると判断して止まった。LLM の推論を含めて、**700 ミリ秒未満**で完了した。

### 6.8 ドキュメントレベルのセキュリティ

1. Foundry でナレッジベースを作成する（Azure でも可能）。
2. アクセス制御情報に対応するソース（Blob Storage や SharePoint など）を指す。
3. データの変換方法などを入力する。
4. 最後に、「document-level security を尊重する」というチェックボックスがある。これをオンにすると、正確な情報を持つインデックスが作られ、アクセス制御情報が直接伝播される。

## 7. 注意点・発表者の気付き

- **プレーンな RAG で十分な場面もある**。うまく動いているなら複雑にしない。グラフは、問題がすでに飽和しているケースでは改善しない。
- **トランスクリプトで言及された件数と、事実としての件数は別物**。デモでは、Passages クエリが、全体の事実に関する答えを拾って誤った。
- **GQL にはクセがある**が、書くのはエージェントを想定している。
- **Retriever 1 は、最大級のフロンティアモデルと常に同等ではない**。ただし多くのタスクでは妥協のない選択肢になる。品質を最大にしたい場合は auto モードで好きな LLM を選べるが、遅延と引き換えになる。
- **アクセス制御情報を置き去りにしない**。ドキュメントをベクトル DB に入れて権限を捨てるパターンは「懸念すべき」と述べている。
- **デモの事情**：音声が途切れる箇所があった。また、いくつかのデモは事前に準備した結果を使っている（Copilot の画面）。
- 提供状況：Foundry IQ Serverless は 12 月 GA 予定。Retriever 1 / Ranker 3 はこの日から展開。OneLake shortcuts、Fabric Data Agents、Fabric Ontology はパブリックプレビュー。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

| 利点 | 根拠として語られたこと |
| --- | --- |
| 導入の手間の削減 | Foundry 管理のナレッジベースは、プロビジョニング、管理、権限設定が不要で、固定の追加コストなし |
| コストの柔軟性 | Serverless は、ゼロまでスケールし、ストレージ分のみの課金。即時に作成できる |

| 権限の維持 | SharePoint や Blob などでドキュメントレベルの権限が伝播する |
| 他スタックでも利用可 | すべて MCP で公開されている |

## 9. まとめ

Foundry IQ は、Azure AI Search を土台にした、非構造化・構造化コンテンツ向けのコンテキスト層で、Microsoft IQ とつながり、エージェントに共有の知識源を提供します。このセッションで示された内容を整理すると、次のようになります。

1. Foundry 管理のナレッジベースと、12 月 GA 予定の Foundry IQ Serverless で、作り始める手間を減らす。
2. ナレッジグラフ（Entity Graphs、Topic Graphs）で、集計や俯瞰といった、プレーンな RAG が苦手な質問に答え、トークンも削減する。
3. Microsoft Retriever 1 / Ranker 3 で、Agentic retrieval をサブ秒にし、設定も不要にする。
4. SharePoint、ファイルアップロード、SQL DB の GA と、権限の伝播で、エンタープライズの要件に応える。
