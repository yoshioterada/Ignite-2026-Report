# BRK309 Optimizing AI agents to meet your goals: Grounding with Web IQ

## 1. はじめに

このセッションは、AI エージェントが Web から根拠（evidence）を取ってくる「grounding（グラウンディング）」を、品質・速度・コストのバランスの中でどう設計するかを扱った 45 分のブレークアウトです。中心になるのは、前日に発表され Azure で一般提供（GA）となった **Web IQ Auto** で、エージェント側で書いていた「検索を繰り返すループ」を Web IQ 側に任せるという考え方です。

Web IQ を担当するエンジニアリング責任者が仕組みと比較デモを示し、続けて Cloudforce と Genspark の 2 社が、自社の本番環境での使い方と成果を紹介しました。最後に、品質・鮮度・速度・コスト効率の 4 つの観点で Web IQ の測定結果が示されます。

結論を先に言うと、発表者が会場に伝えているのは **「複数の意図を持つタスク、反復的な探索、多様な情報源が必要なタスクでは、Auto に grounding と検索の複雑さを任せてほしい」** ということです。

## 5. 発表内容の詳細

### 5.1 Web IQ とは：grounding に必要な 3 要素

Web IQ は Build で発表された、**エンタープライズ向けの grounding サービス** です。エージェントが推論して行動する一方で、Web IQ は証拠を探し、引用して信頼できる出典をすべての結果に付けます。

発表者は、Hawaii での製油所の火災を例に、エージェントが必要とする情報を挙げました。オアフ島で車両の配送サービス（fleet）を運営している場合を想定すると、ニュース、親会社の株価、代替の物資の調達先、天気などを理解する必要があります。この例は後のデモに再び登場します。

grounding に必要なものとして、次の 3 つが示されました。

| 要素 | 内容 |
| ---- | ---- |
| Coverage（網羅性） | Web IQ は **Bing のクロールとインデックスのエコシステム** の上に作られている。Microsoft は 20 年以上検索に携わり、Bing は 10 億人以上に使われている。インターネットの、信頼できて更新されたコピーを持つ組織は片手で数えられるほどしかない、と説明された |
| Intelligence（知能） | 検索と取得に frontier モデルが必要で、非常に効率の良い retrieval スタックも必要。クロールとインデックス、最新のベクトル検索エンジン、ランキングシステム、ページ全体ではなく **passages や構造化データ** を返す evidence システムがある。取得とランキングのモデルは自社で学習している |
| Trust（信頼） | パブリッシャーがコンテンツをインデックスに入れることを信頼できること。企業が信頼できるよう、**zero query logging** などの制御を提供すること。ユーザーやモデルが確認できる、信頼できる citations（引用）を付けること |

### 5.2 残る課題：検索のオーケストレーション

証拠そのものは見つけられるようになっても、「検索を指揮する」部分が残る、と説明されました。エージェントは次のことを判断しなければなりません。

- どの API を呼ぶか。何回呼ぶか。
- API からどれだけのデータを取るか。どの形式にするか。
- それで十分か。再試行や、クエリの言い換えが必要か。

典型的な流れは、AI が考えて Web IQ を検索し、Web ページ、画像、ニュース、動画を得て、十分かを考え、足りなければもう一度尋ね、最終的に回答を書く、というループです。Web IQ は検索を担当しますが、**このループは開発者が書いて、チューニングして、保守する必要があります**。発表者は、ループを自分で動かすのは面白い挑戦でもあるが、難しく、しばしば高価だと述べています。

### 5.3 Web IQ Auto

**Web IQ Auto** は前日に発表され、**Azure で一般提供（GA）** されています。インフラの課題を解いた Web IQ に対し、Auto は **オーケストレーションの課題** を解くもので、エージェントも開発者も検索の専門家である必要がなくなる、という位置づけです。

仕組みは次のように説明されました。

1. AI が「これは自分の知識の範囲外だ」と判断して、Web IQ Auto を呼ぶ。
2. Web IQ Auto の内部で、取得（retrieval）と **fan out（複数クエリへの展開）** を行い、クエリが複雑なら追加の反復も行う。
3. 結果を **1 回の応答** でエージェントに返す。

発表者はこれを「ループを自分で回す代わりに、zero shot の grounding に近づける」ものと説明しています。

### 5.4 Auto の挙動の特徴

発表者は、Auto が 3 種類のクエリに対して異なる振る舞いをするとまとめています。

| クエリの種類 | Auto の動き |
| ---- | ---- |
| 素早い事実の確認 | 通常の Web IQ と同じ速度で動き、トークンも余分に使わない |
| 複数のソースにまたがる探索（ニュース、株価、天気、場所など） | 複数のソースへ fan out する |
| 深いリサーチの質問 | 反復して探索する |

これらを「1 秒未満」の範囲で行う、と説明されています。

### 5.5 デモ 1：ベンチマークの質問での比較

デモ内容は「6. デモ・手順」で詳しく書きます。結果は次のとおりです。

| 指標 | 標準の harness（通常の Web IQ） | Web IQ Auto |
| ---- | ---- | ---- |
| モデルのターン数 | 8 | 5 |
| 検索回数 | 35 | 7 |
| 所要時間 | 約 29 秒 | （発表では所要時間は語られていません） |
| モデルに入るトークン数 | 370,000 | 25,000 |

トークンは約 **93% 削減** で、発表者は「持ち帰ってほしいのはここ」と強調しています。回答自体は同じで、強力なモデルを判定役にして確認しています。また、クエリの形式にも違いがあり、標準側はキーワード検索（Alta Vista を思わせる、引用符付きのクエリ）、Auto 側は自然言語で意味的な深みがあるクエリでした。Auto の最初のクエリは、エージェントに与えられた依頼文そのままに近かった、とのことです。

### 5.6 デモ 2：Honolulu の例

2 つ目の例は、「Honolulu で製油所が火災になったと聞いた。燃料配送のフリートを運営している。何が起きたのか、製油所はここだけか、影響の広がり、親会社の株価、天気を調べ、事実・報道・未解決の疑問を分けて」という質問です。

この質問には **罠** があり、実際には製油所ではなく排水処理施設（wastewater treatment plant）が火災になった、という点でした。両方の方式がこの罠を見抜いています。

| 指標 | 標準の harness | Web IQ Auto |
| ---- | ---- | ---- |
| モデルのターン数 | 6 | 5 |
| クエリ数 | 42 | 12 |
| トークン数 | 320,000 | 65,000 |

Auto の実行では、1 つの evidence object に、Web ページの passage 36 件、ニュース 6 件、ファイナンスの呼び出し 3 件、場所（places）6 件が含まれていた、と説明されました。場所は、世界中の約 2 億の places / businesses から見つけたものです。また、ページを取得する Web IQ の **Browse API** が 2 回使われています。

### 5.7 Auto の内部トレース

最初のベンチマーク質問について、内部の動きが説明されました（advanced モードで、応答の長さを最大 6,000 文字に制限した設定）。

1. 最初のクエリが実行される。
2. 数百ミリ秒後に「これでは不十分」と判断する（デバッグ出力には、そう判断した理由も出る）。
3. 追加のクエリを 2 件作成し、2 回目の反復として実行する。
4. 「完了」と判断する。結果は、反復 2 回、クエリ 3 件、取得ページ 18、保持したページ 6、所要時間 **818 ミリ秒**。

同じ種類のもう 1 つの例では、Auto はさらに速く、最初の結果で十分と判断し、複数回の反復をしませんでした。発表者は、「十分かどうかの判断と反復は、これまでエージェントのループで行っていたもので、今は Web IQ Auto がインデックスの近くで担当する」と整理しています。

### 5.8 顧客事例：Cloudforce（Nebula One）

Hussein Sharaf 氏（Cloudforce の創業者兼 CEO）が、大学向けの AI プラットフォーム **Nebula One** での利用を紹介しました。

| 項目 | 内容 |
| ---- | ---- |
| 製品 | Nebula One。世界で 100 を超える大学に導入され、学生に **プライベートで公平な AI アクセス** を提供する。高等教育で最も広く導入されている AI プラットフォームとのこと |
| 受賞 | 今週、2 年連続で education 分野のグローバルな partner of the year に選ばれた |
| 用途 | AI モデルへのアクセスに加え、学費の支払い、次の学期の住まい探し、履修プログラムの登録など、大学のリソースに関する質問に答える |

従来の「レガシーな Web grounding」は、Bing 検索で関連コンテンツを取り、何度も反復ループを回すものでした。時間がかかり、トークンも多く使います。

Web IQ Auto の導入による効果は次のとおりです。

- 同じクエリで、モデルに送られるトークンが **58% 削減**。
- ある学生の予算が月額 20 ドル（ユーザーあたり）の場合、**16 回分多く** の会話ができる。大学が学生に設定する月額予算は 5 ドルから 50 ドル、100 ドルなどだが、多くの学生は 20 ドル程度を消費している。
- ある大学では、22,000 人の学生が利用し、月に 420 億トークン、Foundry 経由で約 110,000 ドル相当のトークンを消費している。この大学だけで、**年間約 58,000 ドル分の効率化** になる。
- 従来のレガシー grounding からの切り替えで、検索の速度が **12.5 倍** になった。
- 精度の向上：従来は Web サイトのテキストのみを取っていたが、Auto ではさまざまなコンテンツタイプ（**入れ子になった PDF** など）にアクセスできる。大学の Web サイトには関連する情報が入った入れ子の PDF が多い。
- 画像や動画も取得できる。

Hussein 氏は、教育分野は新しい技術が最後になることが多いが、今回は **最初に** Web IQ Auto を受け取る、と述べています。100 の大学すべてに、この学期中に Web IQ Auto が提供される予定です。

> 補足：年間 58,000 ドルの効率化額と月額 110,000 ドルの関係は、音声の説明だけでは算出方法が確認できません。

### 5.9 良い grounding の 4 本柱

Knut 氏は、良い grounding サービスの柱として **quality（品質）、freshness（鮮度）、speed（速度）、cost efficiency（コスト効率）** の 4 つを挙げ、前日にも繰り返したのと同じことをまた繰り返すと述べました。

#### 品質（Quality）

- 品質の測定には、実際のワークロード（顧客が実行するクエリ）を使う。「ベンチマークは多くを教えてくれるが、顧客が何を実行するかは、顧客が何を信頼して任せているかを示す」という考え方。
- **grounding satisfaction** という指標で、約 2,850 件のクエリを使う。クエリは実際のエージェントからのもので、継続的にサンプリングしている。
- 4,500 トークンの予算で品質を測定する。0〜100 のスケールで、数値は 80 台とのこと（スライドの詳細な数値は音声では語られていません）。「まだやることがある」と述べた。
- Web IQ の web endpoint は非常に競争力があり、Auto は顧客のクエリで成果を伸ばしている。
- ただしこれは 1 つの動作点（4,500 トークン）の話で、「One size fits nobody」。重要なのは、縦軸に品質、横軸にトークン数をとった **曲線** で、左上が理想（最小のトークンで最高の品質）。これは **Pareto frontier** と呼べるもので、Web IQ はこのフロンティア上にいる。曲線の外側にわずかに出ている点が、Web IQ Auto である。

#### 速度（Speed）

- 「1 ミリ秒が重要」という考え方。本番環境で、**世界 8 リージョン** の任意のエンドポイントから各 grounding サービスまでの平均レイテンシーを測定している。米国西海岸や東海岸の体験ではなく、世界規模の体験。
- Web IQ は **最も近い競合の 2 倍以上** 速い。
- 新機能を出すたびに、何ミリ秒遅くなったかを確認し、遅くなっていれば再度改善する、とのこと。

### 5.10 顧客事例：Genspark（音声エージェント）

Ray 氏（Genspark のエンジニアリング責任者）が、音声エージェントでの Web IQ の利用を紹介しました。

**Genspark について**：1 つの super agent の上に作られた AI ワークスペースで、スライドやドキュメントの作成、電話をかけて会話することもできる、と紹介されました。

**なぜレイテンシーが重要か**：音声では、レイテンシーそのものが製品になります。

| 待ち時間 | 体感 |
| ---- | ---- |
| 300 ミリ秒未満 | 即時に感じる |
| 1 秒 | 気づき始める |
| 3 秒超 | 会話が壊れる |

テキストでは遅い回答は「スピナー」で済みますが、音声では **沈黙** になります。

**課題と Web IQ の効果**：音声通話の 5 回に 1 回は、価格、スコア、ニュース、営業時間、現在のルールなど、ライブの Web 検索が必要になる、と説明されました。

| 項目 | 以前の自社パイプライン | Web IQ |
| ---- | ---- | ---- |
| 応答時間 | 平均約 1.3 秒、最悪で 6 秒超 | 200 ミリ秒以内 |
| 結果の形 | ページ全体 | passage（ページ全体ではない）。トークンは **50% 未満** |
| 日付 | 日付が付いている結果は 10% 未満 | すべての結果に日付が付く |

**アーキテクチャ**：「1 relay、2 loops」と説明されています。

1. 電話は、Genspark が作った **voice relay** につながり、その下で speech-to-speech モデルが動く。
2. ターンごとに fast route があり、**0.5 秒未満** でライブ Web 検索が必要かを判断する。
3. 必要な場合は fast web search loop（Web IQ が組み込まれている）へ。Web IQ の検索は **0.4 秒未満** で結果を返す。
4. 難しいタスクは大きなループ（big loop）へ回し、バックグラウンドで非同期に実行して、完了したら主要な会話に戻す。
5. Web IQ の passage を **日付で再ランキング** して LLM に渡し、回答を作る。

**結果**：100 件を超えるクエリで、自社のパイプラインと Web IQ を組み込んだ新しいパイプラインを並べて比較した。最悪ケースで、6 秒超かかっていた（または結果が返らなかった）Web 検索が **0.6 秒** になり、**10 倍速く** なった。

**学んだこと**（3 つの教訓は、発話では明確に区切られていません）：

- 検索を、0.4 秒未満でループの中に入れる。「検索はストアではなくステップ」という考え方。
- すべてのホップを測定し、ハードキャップを設ける。いまは、Web 検索に 0.5 秒未満という小さな予算を与え、それを超えたら大きなループに回す。
- ループを分け、即時の応答は素早く返し、難しいタスクにはエージェントが時間をかけて非同期に実行できるようにする。

最後に、Web IQ はエージェントに「Web の素早く根拠のある見方」を与え、それを音声で完成した作業に変える、とまとめています。

### 5.11 鮮度（Freshness）と Copilot での例

Knut 氏は、速度が良くても、根拠が正しく最新でなければ役に立たない、として鮮度を取り上げました。

**Copilot での例**：Web IQ の鮮度が Copilot に統合された様子が、事前に撮影された画面で示されました。「最新のヘッドラインを引用付きでまとめて」「サンフランシスコの天気は」という例で、ヘッドラインには中国での会議、Ignite での Microsoft の主要なリリース、IPO に関する議論などが含まれ、天気は「傘を持っていくこと」が持ち帰りだった、と紹介されています。Web IQ のプリミティブは、全世界のテナントの Copilot に統合されていると説明されています（音声認識の都合で一部不明瞭）。さらに、**Auto を統合することで** Copilot のユースケースの鮮度を高める、と述べられました。

**FreshSearch ベンチマーク**：鮮度のベンチマークが存在しないため、Microsoft が自前でベンチマークを作りました（名称は「fresh search」と聞こえ、音声認識の都合で表記が確定できません）。以下、FreshSearch と書きます。**ハーネスとデータはオープンソース化する** 予定です。次の 2 点を測っています。

1. Web 上で起きている変化を拾える能力（最新のニュースを拾えるか、正しい答えを拾えるか）。
2. 拾ったデータのうち、最新のものか（天気、株価などで、秒単位で正しい数字を持っているか）。

これらは継続的に動くシステムにまとめられ、他の主要なプレイヤーと公平に比較しています。スライドでは 87.5 という値が示され、発表者は「ギャップがあり、まだやることがある」と述べたうえで、トップであることを喜んでいます（87.5 が何の指標かは音声からは確認できません）。

### 5.12 まとめ：Auto と Auto Advanced の使い分け

発表者は、grounding と取得の複雑さは Auto に任せるよう勧めています。特に次のような場合です。

- 複数の意図を含むタスク（multi-intent）
- 反復的な探索（iterative discovery）
- 多様な情報源が必要な場合
- 実行の効率を重視する場合

さらに、**Auto** と **Auto Advanced** があります。目安は、より深い反復探索が必要になると思うなら Auto Advanced に切り替える、というものです。レイテンシーの予算が長くなり、タスクが複雑なら平均してかかる時間も長くなります。これは「良い・悪い」ではなく、**どれだけ深く行きたいか** の選択、と説明されました。

## 7. 注意点・発表者の気付き

- **ループは開発者のもの、という前提が変わります。** Web IQ だけでは、検索回数、取得量、形式、再試行、クエリの言い換えを判断するループは開発者が書いて保守する必要がありました。Auto はそこを引き受けます。
- **Auto Advanced は「どれだけ深く行くか」の選択です。** 深い反復探索が必要なら切り替えますが、レイテンシーの予算が長くなり、複雑なタスクでは平均の時間も長くなります。
- **ベンチマークの数値は 1 つの動作点です。** 品質は 4,500 トークンの動作点で測っていますが、「One size fits nobody」であり、トークン数と品質の曲線全体で見るべきだと説明されています。
- **品質・鮮度の数値にはまだ伸びしろがあります。** 発表者は、品質（80 台）も鮮度（87.5）も「やることがある」と認めています。
- **音声エージェントでは、遅延が製品の質そのものです。** Genspark は、各ホップを測定してハードキャップを設け、超えたらバックグラウンドの大きなループへ回しています。
- **質問に「罠」がある場合もあります。** Honolulu の例では、製油所ではなく排水処理施設の火災でしたが、両方式とも見抜けました。
- デモは事前撮影のものが中心で、画面が映らないトラブルもありました。

## 8. 利用者にとっての利点

発表で語られた利点・成果は次のとおりです。

- **トークンとコストの削減**：ベンチマーク質問で 370,000 から 25,000 トークン（約 93% 削減）、Honolulu の例で 320,000 から 65,000 トークン。Cloudforce では同じクエリで 58% 削減。
- **検索回数の削減**：35 回から 7 回、42 クエリから 12 クエリ。Web IQ への呼び出しも少なくなり、発表者は「それだけコストも下がる」と述べている。
- **速度**：Auto の例で 818 ミリ秒。Cloudforce では検索速度が 12.5 倍、Genspark では最悪ケースが 6 秒超から 0.6 秒（10 倍）。世界 8 リージョンの測定で、最も近い競合の 2 倍以上速い。
- **精度・コンテンツの範囲**：Cloudforce では、入れ子の PDF や画像・動画も取得できるようになった。Genspark では、すべての結果に日付が付き、passage 単位で返る。
- **開発の負担軽減**：開発者が検索のオーケストレーションのループを書いて保守する必要がなくなる。
- **経済効果の例**：Cloudforce の大学では、月額 20 ドルの予算の学生が 16 回分多く会話でき、ある大学で年間約 58,000 ドルの効率化。

## 9. まとめ

Web IQ は、Bing のクロールとインデックスに基づく enterprise 向けの grounding サービスで、coverage、intelligence、trust を備えています。前日に発表され、Azure で一般提供となった **Web IQ Auto** は、エージェントの検索ループ（検索、十分か、再検索）を Web IQ 側に移し、1 回の呼び出しで結果を返します。

- 比較デモでは、トークンが約 93% 減り、検索回数も大きく減りましたが、回答は同じでした。
- Cloudforce（Nebula One）と Genspark（音声エージェント）は、それぞれ本番環境で、トークンの削減、速度の向上、コンテンツの範囲の拡大などの効果を報告しました。
- 良い grounding の 4 本柱は、品質、鮮度、速度、コスト効率です。品質は Pareto frontier 上にあり、速度は最も近い競合の 2 倍以上、鮮度は独自ベンチマーク FreshSearch（ハーネスとデータをオープンソース化予定）で測定されています。
- 使い分けは、通常は Auto に任せ、より深い反復探索が必要なら Auto Advanced に切り替える、というものです。

発表者のメッセージは、「**エージェントを airplane mode から出して、Auto を試してほしい**」でした。今後のセッションとして、翌日は Web IQ を使って構築するセッションがあり、金曜日には実際に動かす様子が紹介されること、また Web IQ の専門家と話せることが案内されました。
