Pablo 氏の主張は大きく 3 つです。

1. **道具は時間とともに変わるので、1 つのシステムに固執しない。** RAG が流行り始めた数年前は、ベクトルデータベースがすべての定番でした。今も多くの場合は適切ですが、教条的にならず、他の形の検索のほうがよい場面を見極めるべきだと話しています。

## 5. 発表内容の詳細

### 5.1 Foundry IQ とは何か

Pablo 氏は、考え方の転換（mindset shift）と技術的な問題が両方あると述べています。その上で、15 種類ものサービスやツールを学ばなくて済むよう、これらを統合することが課題だと説明しています。

Foundry IQ は、**単なるベクトルデータベースでも、検索エンジンでも、構造化データのシステムでもなく、全体としての検索システム** です。仕事は「エージェントが質問に答えるために必要なデータを、どんな手段を使ってでも見つけること」とされています。エージェントのシステムにおいて、取り組みを支える grounding data（根拠となるデータ）を持つことは最も重要な部分の 1 つだとも話しています。

### 5.2 エージェントの構成要素とデータ

現代のエージェントは、**モデル、ハーネス、そしてモデルとハーネスを現実世界につなぐデータとツール** の組み合わせだ、という整理です。モデルは（ファインチューニングしたものを使う場合を除き）誰もが同じものを使い、ハーネスもおおむね汎用のものです。柔軟性を持たせ、仕事を終わらせるためです。結局、エージェントを特別にするのはデータです。そこで、データをどうエージェントが簡単に使えるようにするか、そして、適切なタイミングで適切な部分に効果的にアクセスできるよう、どう整理するかが大切になります。

### 5.3 開発者からのフィードバックと、エージェント向けの提供形態

Pablo 氏が Ignite のような機会に楽しみにしていることとして、2 つが挙げられました。

* **方向性が合っているかのフィードバック：** 人々が困っている方向で作業できているか、各社の日々の課題の解決に役立っているか。この領域はこれほど広く開けているのは久しぶりで、「今、頭にある課題」を聞くことは非常に価値がある、と話しています。
* **提供形態の変化：** これまでは製品を作り、SDK を作り、ドキュメントを書き、人が API を呼び出して使うのが一貫していました。今は、ドキュメントを読んでコードを書くエージェント、より最適な解決策かを調べるエージェントがいます。そのため、人に分かってもらうだけでなく、技術を使うエージェントにも理解され、効果的に使われるようにする必要があり、これは大きな変化だという説明です。

その一例として、今回は SDK などに加えて **プラグイン** も提供していると述べています。エージェントを使うなら、専用のプラグインを渡すと、汎用的なものではなく Foundry IQ について必要なことを正確に知っているので、仕事がはるかに早く終わる、という説明です。

### 5.4 フィードバックから生まれた例：グラフ

過去のイベントからのフィードバックの例が 1 つ紹介されました。ベクトルや語彙（lexical）による検索、agentic retrieval には長く取り組んできました。その中で、**グラフ表現やグラフのシステムとどう統合するか** に強い関心が寄せられ、一般的なニーズに加え、システムがネイティブに対応すれば容易になる具体的なシナリオも得られた、という経緯です。その成果は Foundry IQ に取り入れられたと説明されています。詳細は、同日午後の Pablo 氏のセッションと、翌日のグラフに特化した別セッション（登壇者は "Luis" と聞こえます）で語られる予定です。

### 5.5 よくある落とし穴：複雑にしすぎない

Agentic retrieval を始めるときの落とし穴として、Pablo 氏は次のように話しています。

* 現在は技術が多く、毎週、検索の新しい手法に関する論文が出る。選択肢に圧倒され、**必要以上に複雑なシステムを作り、シンプルなシステムで十分だったのに、品質の見返りが得られない** ことが起こりやすい
* 最も大切なのは、**自分のタスクを理解すること**。ごく簡単な方法でもよいので評価から始め、そこに向けて、できるだけシンプルなシステムで作る
* プラットフォームには多くの機能があるが、それは多様なシナリオに対応するためで、1 つのソリューションがすべての部品を使う必要はない
* エージェントに「もっとやって」と頼むのが簡単な今は、特に複雑なものが実際に良いのかが明確でないものができやすい
* 過剰に設計されたソリューションは、本番での運用コストも高くなりやすい

### 5.6 ガバナンス・セキュリティと全体像

Pablo 氏は、週に 2〜3 回は顧客と会っており、ガバナンス、セキュリティ、そして一般的な可観測性（何が起きているかを知ること）に多くの時間を割かないミーティングはない、と話しています。機能とは直交するが、同じくらい重要だという見方です。

背景には、ここ数年の変化があります。当初は、リスクの低いシナリオで試していたのでガバナンスの必要性は低かったが、今はエージェントが仕事の真ん中にあります。そのため、信頼できるか、正しい仕事をしているか、想定どおりに費用を使っているか、どのモデルが使われているか、などを知る必要があります。

これを 1 つの絵として考えており、**Satya 氏が当日の朝に話した** 3 つの構成要素を紹介しています（Pablo 氏の発言による）。

| 構成要素 | 役割 |
|---|---|
| Copilot から始まるエクスペリエンス | Copilot で始まる体験 |
| IQ システム | 会社の自分たちのデータと振る舞いを表す |
| Agent 365 | ガバナンスを担う。M365 の視点でも、Foundry でも、外部のエージェントでも、起きていることを見渡せる |

Agent 365 は、モデルが何をしているか、誰が使っているか、うまくいっているか、いくら使っているか、といったことを示す、と説明されています。

### 5.7 Microsoft IQ とその位置づけ

聞き手は、昨年の Ignite で IQ が紹介され、Web IQ など新しいものも登場し、今は Microsoft IQ があると整理しました。Pablo 氏は、昨年の Ignite で Microsoft IQ を出したときの主要な構成要素を、組織内のデータが集中している主な領域に対応するものとして次のように説明しています。

| 構成要素 | 対象のデータ |
|---|---|
| Work IQ | 生産性に関するデータ（ドキュメント、スプレッドシートなど） |
| Fabric IQ | 分析データ（大規模なデータレイクなど） |
| Foundry IQ | 非構造化データ |

そこでのフィードバックは、「構成要素は気に入っているが、つなぎ合わせる作業が必要だ」というものでした。**Microsoft IQ は、組織全体の grounding context への単一の入口** です。Microsoft IQ では **business plugin** を作れ、あるタスクに対して、エージェントがどの資産（データソース、ツール、スキル）を必要とするかを理解できるようにします。その狙いは 2 つ説明されています。

1. 組織を横断するコンテキストを 1 か所に集める。新しいエージェントが「起きた瞬間に」どこへ行けばよいかが分かる
2. 特定のデータソースに固定されない、**co-work のような汎用的なエージェント** が増えている傾向への対応。Pablo 氏は Microsoft 社内を例に、SharePoint サイトが複数あって急速に増えていること、SharePoint 以外にもデータソースがあり、テレメトリデータも多いことを挙げています。質問するとき、どこに答えがあるのかを見つけること自体が課題になるわけです。Microsoft IQ は、人の頭の中や単発の文書に隠れがちな知識を捉え、正しい場所へのルーティングを助けます。そのうえで Work IQ や Foundry IQ などがそれぞれ適切な情報を取得し、エージェントに返します

> 補足：Pablo 氏の発言には、昨年と今年の Microsoft IQ の話が混在して聞こえる箇所があります。ここでは、トランスクリプトの発言のとおりに記載しています。

### 5.8 Foundry IQ のアクセス制御

聞き手は、それらのサーバーが、見ることを許されたデータだけが得られるという点でも優れていると指摘しています。Pablo 氏は次のように説明しました。

* M365 の境界では、すべての権限が適用される
* Foundry IQ には、**Entra と統合されたネイティブなアクセス制御システム** がある。同じ ID、同じグループで、**エンジン内部で強く強制される**
* 開発者が外側でフィルターを書くことに依存しない。「アクセス制御はすべてこちらで行う」
* **独自のセキュリティモデル** がある場合は、独自のアクセス制御を Foundry IQ にプッシュでき、Entra 経由で強制される
* Azure Data Lake Storage、SharePoint、OneLake のようにアクセス制御をサポートするソースからインデックスする場合は、**アクセス制御情報を伝播し、時間とともに維持する**。インデックスされたものはソースのセキュリティモデルに従い、**クエリ時に強制される**。「見えるべきものが見える」

Pablo 氏は、特にセキュリティが敏感な今、単発の（one-off）対応は避け、多くのレビューと内省を受け、実戦で試された 1 か所に集約すべきで、これこそプラットフォームの役目だと述べています。

### 5.9 始め方

Pablo 氏は、使い慣れた場所によって 2 つの選択肢を挙げています。

1. **Foundry から始める：** Foundry では、Foundry 内に直接ナレッジベースを作成できます。**この会期中に発表する新しい選択肢として、Foundry から新しい Foundry IQ インスタンスを作る必要さえなくなる。すべての Foundry プロジェクトがインスタンスを 1 つ持つ**、と説明されています（詳しくは会期中のセッションで紹介する、とのこと）。摩擦がなく、Foundry プロジェクト以外に追加費用はかからず、プロビジョニングも管理も要りません。ナレッジベースを作って、そのまま使うか、Foundry でエージェントにつなげられます。
2. **Azure ポータルから始める：** Azure に慣れているなら、ポータルで Foundry IQ を探してインスタンスをプロビジョニングします。1 分ほどで終わり、スタンドアロンの Foundry IQ のナレッジベース、または独自の検索システムを作りたい場合のための "row indexes"（音声認識の都合で表記が確定できません）が得られます。

出力は、**多くの制御ができる低レベルの retrieval API**、または **任意のハーネスやエージェントにつなげるスタックの最上位の MCP サーバー** のどちらかです。聞き手は「とても簡単」と述べ、Pablo 氏は、うまくいっている点も、もっと簡単にできる点もあり、フィードバックを受けている、と話しています。

また、ガイド付きで学ぶなら **ラボ** が最適な出発点だと説明されています。ラボにはプロダクトグループの人がいて、製品を隅々まで知っており、仕組みやその理由を話し合い、実際に手を動かせます。

### 5.11 Q&A

**質問 1：今後 12 か月で Foundry IQ をどう描いているか。特にエージェントの自律性が高まる中で。**

Pablo 氏は、12 か月は予測するには驚くほど長いと断った上で、次のように答えました。

* 以前は、エージェントとツール呼び出しのループ、使うツール、grounding 情報をまとめて作り、検索システムをエージェントから独立したものとして考えることは少なかった
* 今後は、横断的な一連のタスクをこなそうとする **汎用エージェント** が増えるため、Foundry IQ のような、**ドメインの知識を 1 か所にまとめたスタンドアロンのナレッジベース** を、必要とする任意のエージェントが発見して使う形が増える
* ナレッジベースの名前を知っているエージェントは今後もあるが、多くの場合 **ナレッジベースの動的な発見** が見られる
* Microsoft IQ の business plugin を作るとき、**Foundry IQ のナレッジベースを追加できる**。追加すれば、Cowork や Microsoft Copilot のようなものが、最初に指示していなくても、権限がある限り動的に見つけて使える
* エージェントとデータの、この動的な関係が、近く現れてくる

**質問 2：Foundry IQ は IT やデータ、高度な技術チームだけでなく、ビジネスユーザーにも広げるのか。**

Pablo 氏は、Foundry IQ は **主に技術的なビルダー（開発者、Azure や Foundry に慣れた人）向けのプラットフォーム** だと答えました。そのうえで、構築と利用を分けて考えるべきだと述べています。

* ビジネスユーザーが数個のドキュメントをどこかに置いて Copilot に使わせたいだけなら、**M365 が最適**。OneDrive のフォルダーや SharePoint サイトを作って使える
* データの扱い方、インデックスの方法、使う戦略を制御したいなら、Foundry IQ がそのすべてを提供する
* 完成したら、Teams などへの **スタンドアロンのエージェントとして公開** するか、Microsoft IQ が取り込めるように **ナレッジベースを公開** できる。利用者はエンドユーザーになりうる
* 簡単なケースは M365 でそのまま扱い、制御が必要なときは Foundry IQ の高度な検索スタックを使う、という分担が今後も続く考え方

聞き手は、Microsoft IQ がこの間をつなぎ、簡単にしている、とまとめました。

**質問 3：Fabric は構造化データと分析、Foundry IQ は非構造化データと言ったが、Fabric にも非構造化データがある。どのような非構造化データを指しているのか。**

Pablo 氏は次のように説明しています。

* Fabric に入るのは、やや非構造化に見える場合でも、主に Parquet ファイルや CSV ファイルなど、データウェアハウスのように **SQL や Spark でクエリするもの**。これらは Fabric に属する
* PDF のような **本当に非構造化のコンテンツ** は OneLake に置ける。その場合も、PDF を展開してテキストや画像を理解し、潜在的な構造を抽出する必要があり、それは Foundry で行う
* **Foundry IQ と Fabric IQ は非常によく連携する**。PDF が OneLake にあっても、追加の作業は不要。PDF が Blob storage や SharePoint、OneLake にあっても、Foundry IQ にネイティブ統合があり、接続して内容を抽出し、見つけられて検索できるようにして、維持する
* 後から変わったときは、変更とセキュリティ情報も伝播する
* この 2 つで、スペクトル全体をカバーする

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。具体的な顧客事例や数値は、このセッションでは紹介されていません。

* **多数のツールを学ばなくてよい：** 1 つの検索システムとして統合されている。
* **セキュリティの一元化：** Entra と統合されたアクセス制御がエンジン内で強制され、ソース（Azure Data Lake Storage、SharePoint、OneLake など）のアクセス制御を伝播・維持する。
* **始めやすさ：** Foundry なら追加費用なしで、プロビジョニングも管理も不要（Foundry プロジェクトごとにインスタンスがある新しい選択肢）。Azure ポータルからは 1 分ほどでプロビジョニングできる。
* **エージェントとの接続：** 低レベルの retrieval API、または任意のハーネスやエージェントにつなげられる MCP サーバーとして使える。
* **Microsoft IQ との連携：** Foundry IQ のナレッジベースを business plugin に追加すれば、Cowork や Microsoft Copilot が、権限の範囲で動的に見つけて使える。

## 9. まとめ

Foundry IQ は、ベクトルデータベースや検索エンジンの 1 つではなく、エージェントが必要とするデータを見つけるための総合的な検索システムです。エージェントを特別にするのはデータであり、そのデータをどう届け、どう整理し、どう守るかが課題になります。

発表者の勧めは、自分のタスクを理解し、評価から始め、できるだけシンプルに作ることです。アクセス制御は Entra と統合されたエンジン側で強制され、ソースの権限も維持されます。始めるなら、Foundry でナレッジベースを作るか、Azure ポータルでインスタンスを作ります。ラボや、同日午後・翌日以降のセッションで、新機能の詳細を確認できます。
