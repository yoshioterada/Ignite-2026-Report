# BRK301 Building context-aware agents with Microsoft IQ

## 1. はじめに

このセッションは、Microsoft IQ を構成する 4 つの IQ（Web IQ、Foundry IQ、Fabric IQ、Work IQ）を使って、コンテキストを理解するエージェントを実際にどう作るかを、デモ中心に見せるものです。題材は「ホテル」です。最初は 1 つのホテルのゲストサービスエージェントから始め、4 つの IQ を 1 つずつ接続していきます。最後には、独自の ID を持つ複数のエージェントが、**オーケストレーションなしに Teams やメールで互いに連絡を取り合って仕事を進める**デモまで進みます。

発表の中心にあるメッセージは、エージェントに必要なのは「コンテキスト」であり、IQ がそれを提供する、という点です。また後半では、エージェントに独自の ID（Entra ID と M365 のサブスクリプション一式）を持たせることで、最小権限の原則を適用でき、Work IQ を通じてエージェント同士の協調が可能になる、という考えが示されます。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK301](https://ignite.microsoft.com/en-US/sessions/BRK301)

## 3. 何に関する発表か

今週の Ignite で Microsoft IQ のプラットフォームと、個々の IQ の新機能が発表されたことを受けて、「それらを実際にどうエージェントの構築に使うか」をハンズオン形式で示す、というセッションです。

登場する IQ の位置づけは次のとおりです。

| IQ | 発表での説明 |
| ---- | ---- |
| Web IQ | 企業の外にある、実世界のコンテキスト。エージェントが人間のようにウェブを閲覧するためのグラウンディング API のセット |
| Foundry IQ | 非構造化データのための知識（ナレッジベース）。ホテルの方針やルールなどに利用 |
| Fabric IQ | 「ビジネスがどう動いているか」の情報。構造化データ（宿泊予約など）に利用 |
| Work IQ | 組織内の文脈。メール、チャット、人、組織内で起きているすべてのこと |

発表の流れは、シナリオの紹介、Web IQ、Foundry IQ、Fabric IQ、Work IQ、独自 ID を持つエージェント、マルチエージェントの協調、まとめと参考リソース、の順です。

## 4. 発表者が伝えたいメッセージ

発表者は、このシナリオを「だんだんと派手になっていく」ものだと述べ、1 つのエージェントから複数のエージェントへと進めます。主張は次の 3 点に整理できます。

1. **コンテキストがエージェントを機能させる。** 4 つの IQ が、それぞれ別の種類のコンテキスト（Web、方針・ルール、ビジネスデータ、職場の会話）を提供する。
2. **コンテキストは分担させる。** Fabric IQ のデータエージェントのように、データ関連のコンテキストを専用のエージェントに委譲すれば、下流のエージェントのコンテキストウィンドウを無駄に埋めずに済み、単体でテストもできる。Marco 氏は、これを「マイクロサービスのエージェント版」と表現しています。
3. **エージェントに独自の ID を持たせる。** ID を持つエージェントは、利用者の権限を借りるのではなく、最小権限の原則で別の権限セットを持てる。また、Work IQ を使えば、エージェント同士が Teams やメールという普段の連絡手段で協調できる（ad hoc collaboration）。Marco 氏は、これを「エージェントの次の世代で起こること」と述べています。

## 5. 発表内容の詳細

### 5.1 シナリオとアーキテクチャ

Ayca 氏は、会場の Marriott Marquis にちなんだホテルのシナリオを紹介しました。最初に用意するのは **Hotel Guest Services エージェント**です。ホテルの詳細、方針、ルール、予約などについて、ゲストの質問に答えます。

このエージェントは、Foundry 上で動く**ホステッドエージェント**で、4 つの IQ に接続されています。そして Agent 365 で管理されています。IQ の呼び出しには **Foundry のツールボックス（toolbox）** を使います。「hotel toolbox」には、あらかじめ定義した説明とともに 4 つの IQ が MCP サーバーとして入っており、同じツールボックスを別のエージェントに差し込めば、コンテキストとデータを再利用できると説明されました。

### 5.2 Web IQ

Web IQ は、グラウンディング API のセットで、エージェントが日常的にウェブを見るように外部の情報を取得できます。シナリオでは、ゲストが「今日の午後、天気はプールに十分か」と尋ねる想定です。

- Azure で Web IQ のリソースを作成し、そこから Web IQ のポータル（webiq.microsoft.ai）に進める。Get Started の画面に、REST、SDK、MCP サーバーによる呼び出し方がある。
- プレイグラウンドで試せる。バーティカル（検索対象の種類）を選べ、今回の Ignite で発表されたものとして **places** が新しい。ウェブ検索、動画の検索など。
- コードのセクションに、Python、JavaScript、C# のコードがある。
- Web IQ のブログでは、**価格**も発表された。

### 5.3 Foundry IQ

Foundry IQ は、非構造化データのためのナレッジベースを作る機能です。今回の発表として、非構造化データに対するオントロジーとナレッジグラフ、新しいモデルの **Microsoft Retriever 1** が紹介されました（詳細はブログ記事を参照するよう案内）。

ホテルのシナリオでは、各ホテルの方針やルール（バレーパーキング、プール、営業時間、チェックアウト時間など）をチャンク化して、ナレッジベースに入れています。ナレッジベースの設定は次のとおりです。

| 設定 | 内容 |
| ---- | ---- |
| 説明 | ナレッジベースが何についてのものかを定義 |
| 出力 | extractive data か、「answer synthesis」（トランスクリプトでは「enter synthesis」と聞こえ、音声認識の都合で表記が確定できません）を選べる。後者は非常に高品質な結果が得られると説明された |
| 完了モデル | answer synthesis では、完了モデルを選べる。今回は GPT 5.4 mini |
| 検索の推論の強度 | 今回は low |
| 検索の指示（retrieval instructions） | どのナレッジソースを参照するかのヒント（例：バレーパーキングならこのソース、HR ならこの HR ポリシー） |
| 回答の指示（answer instructions） | 回答の形式（例：正確に、短く、常に出典を付ける） |
| ナレッジソース | 今回は 4 つで、すべて Azure AI Search。ほかに、Fabric IQ、Work IQ、SharePoint、Blob Storage、自作の MCP サーバーも選べる |

### 5.4 Fabric IQ

Fabric IQ は、ビジネスがどう動いているかという情報を持ちます。シナリオでは、ゲストの予約情報はすべて Fabric にあり、エージェントが問い合わせて予約を確認します。

Marco 氏は、エージェントがデータを扱う難しさを次のように説明しました。人間は Power BI や Tableau のレポートを使うが、エージェントにレポートを渡しても、新しいクエリを組み立てる必要があるため十分ではない。レポートの背後には**セマンティックモデル**があり、テーブル同士のつながり、計算フィールド、基本的なメタデータを定義している。しかしそれでもエージェントが推論するには足りない。実際のデータベースは、「Q_RSTR」のような名前だらけで、人間にも読めない、という指摘です。

そこで、セマンティックモデルを出発点にして **オントロジー**を作ります（「generate ontology」というボタンがあり、今回は事前に生成したものを使用）。

| 観点 | セマンティックモデル | オントロジー |
| ---- | ---- | ---- |
| 箱が表すもの | データベースのテーブル | **ビジネス上のエンティティ**（予約、滞在、メンテナンス依頼、フォリオ＝退出時にもらう明細書など） |
| 線が表すもの | 外部キーの関係 | **動詞**（予約は滞在につながる、滞在はメンテナンス依頼を生むことがある、滞在は必ずフォリオを生む） |

これによりエージェントは、データがどうつながり、要素間で何ができるかが分かります。Fabric でオントロジーを作ると、**オントロジー用の MCP サーバー**が用意され、エージェントを直接つなぐこともできます。ただし今回のデモでは、これではなく、Fabric IQ の別の機能である **Fabric データエージェント**を使っています。

> 補足：ホテルのゲストサービスエージェントは、1 つのエージェントに見えるが、実際は複数のエージェントを 1 つの顔にまとめたものです。Foundry IQ も別のエージェントで、Fabric データエージェントも別のエージェントです。

Marco 氏のデモでは、Fabric データエージェントを 1 つではなく複数のデータソースに接続しています。このエージェントには、データを有効に使うために必要なコンテキストを入れる専用の場所が用意されています。データソースごとの要素は次のとおりです。

- データ辞書（すべてのテーブルと列、その説明）
- クエリの例（よくある問い合わせのクエリ方法）
- トピック（そのデータソースをいつ使うか）
- データソース用の指示
- エージェント全体の指示（agent instructions）

エージェント全体の指示が重要な例として、2 つが挙がりました。ホテル業界の「MICE」は、meetings、incentives、conferences、exhibitions を指すが、エージェントはこれを知らない。Microsoft 社内では Azure OpenAI Service を「AOAI」と略すが、その略語はデータにも辞書にもないので、「AOAI の前四半期の売上は？」と聞かれても何のことか分からない。こうした「他に書く場所がないこと」を書くのが、エージェントの指示だと説明されています。

これらのコンテキストは膨大なので、ホテルの複数のエージェントそれぞれに繰り返し持たせると、コンテキストウィンドウを無駄に消費します。そこで、**別の独立したデータエージェントに委譲**します。この方式には次の利点があります。

- 下流のエージェントのコンテキストウィンドウを散らかさない。
- データアクセスの部分を単体でテストできる。たとえば Fabric データエージェントと直接チャットして、「Maria Garcia の予約は？」と尋ねられる。ゲストサービスエージェントに問題が起きたとき、データアクセスの部分を切り分けられる。

Marco 氏は、これを、ソフトウェアエンジニアリングで長年やってきたことと同じ、「**マイクロサービスのエージェント版**」だと表現しました。

### 5.5 Work IQ

Work IQ は、組織内のコンテキストです。メール、チャット、人、組織内のあらゆる出来事を含み、組織内の会話や情報をエージェントに取り込むために使います。今週の発表で、一部の機能は GA になったと触れられています。

シナリオでは、ゲストの Maria Garcia からキャンセルと返金を求めるメールが届きます。エージェントが、管理者に Teams または Outlook で、キャンセルしてよいか確認します。管理者がキャンセルと返金を承認すると、エージェントが Maria に、予約をキャンセルして返金したと返信します。

**Copilot での Work IQ（デモ）**：Ayca 氏は、Copilot で Work IQ をオフにできることを示しました。Work IQ をオフにして、ホテルのエスカレーションに関する質問をすると、Copilot は、幻覚で答えるのではなく、「その情報源にアクセスできない」と答え、Work IQ をオンにする選択肢を提示しました。オンにすると、Maria Garcia に関する組織内の情報（例：Marco 氏が転送を拒否したこと）が Teams と Outlook から取得できるようになります。

**Work IQ MCP の対話型デモ環境**：Ayca 氏は、自分のアカウントまたはサンプルデータで Work IQ を試せる対話型の環境を紹介しました。Work IQ の MCP、A2A、REST について学べます。MCP のツールの欄には、**ask** ツールや、**do action**（メールの送信、Teams のグループチャットの作成などの操作）などがあり、ここで試せます。リクエストのヘッダーやボディ、レスポンスも見られます。ホテルのエージェントは、Work IQ との統合に Work IQ の MCP を使っています。

### 5.6 Work IQ の本質と、エージェントの ID

Marco 氏は、Work IQ を「**すべての Microsoft アプリケーションのヘッドレス版**」だと説明しました。つまり、エージェントが Outlook、Teams、Word、Excel、SharePoint などを使うための手段です。

Work IQ には 2 つのモードがあります。

1. **On-behalf-of（OBO）**：利用者に成り代わって使う。Ayca 氏が Copilot で使ったのはこの形で、彼女のメールや Teams を見ていた。
2. **エージェント自身の ID で使う**：ホテルのゲストサービスエージェントは、この形で、Teams メッセージやメールを顧客に送っている。

このエージェントは、単なるチャットボットではなく、**独自の ID を持つ別のユーザー**です。Marco 氏は、キーノートで紹介された Autopilot（Copilot の進化形と説明）も、同じインフラを使って独自の ID を持つと述べました。また、独自の ID を持つエージェントは、6 月から自作できたが、あまり注目されなかった、とも述べています。

エージェントの ID が意味するものは次のとおりです。

- Entra ID を持つ。Azure の RBAC ロールなどを付与できる。
- メールアドレスを持つ。さらに、**M365 のサブスクリプション一式**を持つ。Teams ボックス、メールボックス、OneDrive のファイル共有も持つ。M365 のユーザーそのもの。

仕組みとしては、Foundry のホステッドエージェントを Agent 365 に載せ、管理者として**エージェントテンプレート**を定義し、インスタンスの作成を組織の全ユーザーに有効化しています。Teams でボタンを押せば、誰でもこのエージェントのインスタンスを作れます（例：「Marriott Marquis San Francisco agent」）。インスタンスは自分のメールアドレスを持ち、作成者に報告する新しいユーザーになります。基になる Foundry のコードは同じですが、ユーザーコンテキストが違う、という説明です。

エージェントがユーザーであることを使って、データアクセスを分けることもできます。たとえば、Fabric のホテル用ワークスペースのアクセス権に、ホテルのエージェントのユーザーが入っています。

**最小権限の原則**の観点で、Marco 氏は次の比較をしました。

- 利用者の代わりにログインしているエージェント（Copilot、自作のエージェント、ChatGPT など）は、利用者のセキュリティコンテキストを引き継ぐ。メールやカレンダー招待を送れるが、OneDrive のファイルをすべて削除することもでき、エージェントが暴走すれば同じことが起こり得る。
- このホテルのエージェントは、独自のセキュリティコンテキストを持つ。権限は、チャットとメールの送信などに絞っている。ファイルについては、Marco 氏自身は Files.ReadWrite.All を持つが、**このテンプレートから作ったエージェントは読み取り専用**で、ファイルの削除も書き込みもできない。
- 人間のユーザーとは別の権限セットを与えられるので、エージェントが暴走した場合の**影響範囲（blast radius）** を限定できる。

### 5.7 マルチエージェント：Ad hoc collaboration

次のシナリオでは、ホテルの事業運営（財務、人事など）を支援するエージェントが登場します。2 つのエージェントが、同じチャットで利用者を支援します。1 つがユーザーに返信し、もう 1 つがもう 1 つのエージェントに返信する形で、最終承認は Ayca 氏または Marco 氏です。2 つのエージェントは、同じ IQ に接続されているので知能は似ていますが、**ID が異なるため、権限とアクセスできるものが異なります**。

Marco 氏は、幼児の遊びの約束（play date）を親が段取りして遊ばせるたとえを使い、2023 年から今までのマルチエージェントは、AutoGen、Microsoft Agent Framework、「LineGraph」と聞こえるもの（音声認識の都合で表記が確定できません）などで、エージェントを親が段取りするように**オーケストレーション**してきたと述べます。今回見せるのはオーケストレーションではなく、**ad hoc な協調**であり、独自の ID と Work IQ の組み合わせが可能にするものだ、という位置づけです。

デモの内容は 6 章に記載します。Marco 氏は、従来のマルチエージェントでは、同じコンテナで動かすか、A2A や MCP のようなプロトコルでエージェント同士をつなぐが、今回のエージェントは、**私たちが普段使う Teams とメールで会話する**と説明しました。また、これが次世代のエージェントが意味することで、「ad hoc collaboration」が次に世界で起きることだと述べています。

## 6. デモ・手順

このセッションには複数のデモがあります（Teams、Foundry のポータル、Web IQ のポータル、Fabric、Copilot、Work IQ の対話型環境、Outlook など）。**画面の細部は音声からは確認できません**。以下は、語られた順の記録です。

### 6.1 Web IQ のデモ

1. Teams で、Hotel Guest Services エージェントとのチャットを開き、「サンフランシスコの今の天気は？」と質問する。（外は大雨だと、会場に向けて語られた。）
2. エージェントが質問に取り組む間に、Foundry でのエージェントの作り方を見せる。Foundry のホステッドエージェントで、Foundry のツールボックスから IQ を呼び出している。hotel toolbox には、4 つの IQ が MCP サーバーとして入っている。
3. Azure で Web IQ のサービスを作成し、Web IQ のポータル（webiq.microsoft.ai）へ進む。Get Started 画面（REST、SDK、MCP サーバー）、プレイグラウンドを見せる。
4. プレイグラウンドで、「Microsoft IQ」を検索し、約 1 秒で結果が返ることを示す。動画に絞って検索すると、動画の結果だけが返る。
5. コードのセクション（Python、JavaScript、C#）を示す。
6. Teams に戻ると、エージェントが天気（寒くて風が強く、外出しない方がよい）を返している。

### 6.2 Foundry IQ のデモ

1. Teams で、ホテルのプールの営業時間とバレーパーキングの料金を質問する。
2. その間に、ツールボックスで、Foundry IQ が MCP サーバーとして使われていることを見せる。
3. Foundry のナレッジの画面で、「Hotel Foundry knowledge base」の設定（5.3 の表）を示す。ナレッジソースは 4 つ、すべて Azure AI Search。
4. 選べるナレッジソースの種類（AI Search、Fabric IQ、Work IQ、SharePoint、Blob Storage、自作の MCP サーバー）を見せる。
5. ゲストサービスエージェントが、裏で Foundry を呼び出し、プールの営業時間とバレーパーキングの料金を返す。

### 6.3 Fabric IQ のデモ

1. ここまでは Teams で使ってきたが、ゲストサービスエージェントには**メール**でも問い合わせられる。顧客の Maria Garcia が直接メールを送り、Marco 氏が CC に入っている。
2. エージェントが、今後の予約に関する質問に答えるために、Fabric IQ 経由で構造化データにアクセスしている。ツールボックスに Fabric IQ の接続がある。
3. セマンティックモデル（プロパティ、リクエスト、レストラン関連など、多数のテーブルが連結されたもの）を示す。
4. 「generate ontology」ボタンを示すが、事前に生成したものを使うため生成はしない。
5. オントロジー（滞在を中心に、予約、メンテナンス依頼、フォリオなどのエンティティと、動詞でのつながり）を示す。
6. Fabric データエージェントの画面で、データソースごとの要素（データ辞書、クエリの例、トピック、指示）と、全体のエージェント指示を示す。
7. データエージェントを単体で使い、「Maria Garcia にはどんな予約があるか」とチャットで尋ねられることを示す。

### 6.4 Work IQ のデモ

1. Copilot の UI で、Work IQ をオフにして、ホテルのエスカレーションの質問をする。Copilot は情報源にアクセスできないと答え、Work IQ をオンにする選択肢を示す。
2. Work IQ をオンにすると、Maria Garcia に関する組織内の情報（Teams、Outlook 由来。Marco 氏が転送を拒否した件など）が取得できる。
3. Work IQ の対話型デモ環境で、MCP のツール欄を開き、自分のアカウントでログインして ask ツールを呼ぶ。返答が返る（デモ環境なので役職は取得できないが、名前は取得できた）。do action でメール送信やグループチャット作成などができることも説明した。
4. ヘッダー、ボディ、レスポンスなど、MCP の裏側の動きも確認できることを示す。
5. Marco 氏が、Outlook の連絡先カードから、エージェントが独自のユーザーであることを見せる。Teams でエージェントのインスタンスを作るボタン、Fabric のワークスペースのアクセス権（ホテルのエージェントが入っている）も見せた。さらに、Files.ReadWrite.All の違い（Marco 氏は持つが、テンプレートのエージェントは読み取り専用）を説明した。

### 6.5 マルチエージェントのデモ（給与の支払い）

1. Teams の同じチャットに、Hotel Payroll エージェントがいる。そこで、「次の給与を支払うために資金を用意してほしい」と依頼する。
2. Payroll エージェントが起動するのに少し時間がかかる（事前に起動しておけばよかった、と述べている）。
3. 給与は支払えるが、銀行口座の間で資金を移動する権限はない。確認すると、口座の残高は **15,000 ドル不足**している。準備金の口座にはお金がある。
4. Payroll エージェントは、**Hotel Treasurer エージェント**には口座間で資金を動かす権限があると知っているので、Treasurer に連絡し、給与の支払いのために口座に資金を入れるよう依頼する。
5. Treasurer エージェントは、実行は可能だが、人間の承認なしに資金を動かしてはいけないという厳格な指示を受けているので、承認を求めて、Ayca 氏と Marco 氏が入っている同じグループにメッセージを送る。
6. 承認者は Ayca 氏または Marco 氏で、「I just approved it」という発言のあと、承認が行われた（「資金が動くのは一度だけで、二度ではないことを願う」と冗談も述べている）。
7. Treasurer が資金を動かし、Payroll エージェントがそれを見て給与を支払う。
8. Marco 氏が自分のメールを確認すると、エージェントがメールでも連絡していることが分かる。

Marco 氏は、これを**セミ自律（semi-autonomous）**と呼び、利用者がエージェントと働きながら、エージェント同士が協調して作業を進める形だと説明しました。Payroll エージェントには、銀行の操作が必要なときは Treasurer エージェントに連絡すればよい、という知識を与えただけだとのことです。

## 7. 注意点・発表者の気付き

- Fabric のデータはそのままではエージェントに適さない（人間用のレポートであること、列名が読めないことなど）。セマンティックモデルを出発点にオントロジーを作り、データエージェントにデータ辞書、クエリの例、トピック、指示を整備する必要があります。
- 略語や業界用語（MICE、AOAI など）は、データにも辞書にも無いため、エージェントの指示に書かなければエージェントは理解できません。
- コンテキストを多くのエージェントに複製すると、コンテキストウィンドウを無駄に消費します。専用のデータエージェントに委譲するのが対策です。
- 利用者のセキュリティコンテキストを引き継ぐエージェントは、利用者ができることをすべてできてしまいます。最小権限の原則を適用するために、独自の ID を持たせる、という使い分けが示されました。
- デモ中は、Payroll エージェントの起動に時間がかかる、画面の読み込みが遅い（Outlook から表示した）など、ライブならではの動作がありました。
- 発表では、Web IQ の価格の具体的な金額や、Microsoft Retriever 1 の詳細には触れていません（ブログ記事の参照を案内）。

## 9. まとめ

このセッションでは、ホテルのゲストサービスエージェントを題材に、Web IQ（外部のウェブ）、Foundry IQ（方針やルールのナレッジベース）、Fabric IQ（オントロジーとデータエージェントによる構造化データ）、Work IQ（組織内のメールやチャット）を順に接続して、エージェントにコンテキストを与える方法を示しました。さらに、エージェントに Entra ID と M365 一式の独自 ID を与えることで、最小権限の原則を適用し、Work IQ を通じて Teams とメールでエージェント同士が協調する様子をデモしました。

デモに使ったホテルのエージェントはリポジトリで公開されており、自分の環境で試すことができます。最後の言葉は、「Microsoft IQ で、あなたと、あなたのエージェントの IQ を上げましょう」という趣旨でした。
