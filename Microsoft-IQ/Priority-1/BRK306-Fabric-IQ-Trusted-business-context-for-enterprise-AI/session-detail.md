# BRK306 Fabric IQ: Trusted business context for enterprise AI

## 1. はじめに

このセッションは、エージェントに「自社のビジネスの文脈」を理解させるために、Microsoft Fabric 上でどのように信頼できるビジネスコンテキストを作るかを説明したものです。Microsoft IQ の中で、ビジネスデータを担当する Fabric IQ が主役です。

話は大きく 3 段階で進みます。まず、OneLake でデータを統合し、Power BI のセマンティックモデルを Copilot などのエージェントからそのまま使う方法です。次に、リアルタイムの信号やビジネスルールまで含めて「事業の動き方」をモデル化する **Fabric IQ ontology** です。最後に、ontology を data agent に載せて最適化まで行う例が示されました。ontology の顧客事例として、Toyota Motor Corporation の取り組みも紹介されています。デモは 5 本あり、6 章で順に整理しています。

## 5. 発表内容の詳細

### 5.1 Fabric と OneLake

Fabric は、AI 向けに作られた新世代の統合データプラットフォームで、Microsoft がこの 5 年間作ってきたものだと Bogdan 氏は説明します。一般提供（GA）は 2023 年で、ちょうど 3 年前です。含まれる要素は次のとおりです。

- 運用データベース（SQL Server、Postgres など）
- Data Factory（ETL パイプライン、データフロー、クラウド間のデータ移動）
- データウェアハウス（Azure 上の他のものより価格性能が優れる、という説明）
- Real-time intelligence（流れてくるイベントを扱う。何兆件ものイベントを処理できる）
- Power BI（レポートとビジネス指標の置き場所）
- IQ レイヤー（これらすべてを AI から利用しやすくする）

ストレージは単一の **OneLake** で、データはオープンな形式で、ガバナンスの下にあります。セキュリティをストレージのレベルで設定でき、Microsoft のエンジンだけでなく、Snowflake などパートナーのエンジンも同じセキュリティルールを適用できる、というのがオープン形式の価値だと説明されました。

OneLake に接続できるものとして、Dataverse へのショートカットや、SharePoint フォルダー、Excel ドキュメントへのショートカットが挙がりました。さらに Google や AWS など他のクラウドのデータ、SAP や Salesforce のデータにもつなげます。コピーではなく接続で、「ゼロコピー、ゼロ労力」と表現しています。ショートカットで他クラウドのデータを直接読み、ミラーリングで運用データベースを OneLake に反映します。ミラーリングではストレージにもミラーリングにも料金はかかりません（"for free"）。OneLake は分析資産のための OneDrive、とも例えられました。

データの整形（harmonize）には分析エンジンを使います。発表者は、Spark など他のエンジンの話は別のブレークアウトに譲る、としています。

### 5.2 Power BI セマンティックモデルという土台

テーブルには名前、説明、列がありますが、人やエージェントが推論するにはそれ以上の情報が必要です。その土台が **Power BI セマンティックモデル**です。論理的なデータベースで、複数のソースのデータをどうつなぐか、テーブル同士の関係、ビジネス指標、階層など、ビジネスの動かし方を知っています。世界に 2,200 万個以上（"more than 22 million"）のセマンティックモデルがある、と紹介されました。

エージェントにも同じ数字を返させたいなら、スタックを二重に作る必要は無く、ダッシュボードを動かしているエンジンに、Copilot などのエージェント技術を直接つなぐのが最も簡単だ、という主張です。

### 5.3 Fabric IQ の広がり

- **提供状況。** デモの技術はすべて今日 GA。チャット、core（音声認識の都合で表記が確定できません。派生オブジェクトの作成や毎日のスケジュールタスクに使う、という説明）、独自のエージェントから Fabric MCP server を直接使う形で利用できる
- **課金。** Microsoft Copilot chat での Power BI とのチャットに関わるトークンは、無料（ライセンスに含まれる）
- **Excel。** 今週、Fabric IQ が Excel に来ると発表。会計担当やビジネスユーザーが、使い慣れたツールから Power BI のデータに問い合わせられる
- **ChatGPT と Claude。** 今週、Fabric IQ が ChatGPT に直接入ると発表し、Claude にも近く入る、と述べた
- **Apache OC（音声認識の都合で表記が確定できません）との連携。** Snowflake との協力で、Power BI との統合のプレビューを今週発表した。ビジネス指標をシンプルなファイルとして分離し、データ資産全体で再利用できる。Snowflake の semantic views で宣言された指標を Power BI で使うことも、その逆もできる、という説明

さらに、Fabric IQ のスタックは Fabric 内のあらゆる知識をエージェントツールに公開する方法で、ビジネスインテリジェンスとセマンティックモデルに、**operational intelligence**（ontology）という層を重ねる、と述べて Chafia 氏に引き継ぎました。

### 5.4 Ontology: なぜ必要か

ここからは Chafia 氏（トランスクリプトの表記は Shafia）のパートです。ビジネスは、顧客、製品、サプライヤー、在庫、人が結び付いて常に変化するシステムです。エージェントに必要なのは、より多くのデータへのアクセスではなく、チームと同じようにオペレーションを理解し、次の判断と行動に生かせることだ、という問題提起です。

「demand spot」と聞こえる場面（音声認識の都合で、正確な語は確定できません）を例に、在庫（セマンティックモデル）や計画の文脈はすでにあります。しかし行動に移すには、入荷中の出荷、出荷待ちの配送、リアルタイムの生産状況、さらに契約などに基づく優先度のようなポリシーや制約も統合する必要があります。そこで ontology が、運用システムからの信号、テーブル、ストリームを 1 つのモデルに集め、意味を与えてエージェントとチームに公開します。

Fabric IQ ontology は、「事業の統合された運用の頭脳」だと説明されます。エンティティ、関係、指標、ルールをまとめ、データ自体だけでなく、事業がどう動くかを記述します。既存の Power BI セマンティックモデルや Fabric のデータの上に作られ、ガバナンスされた、再利用と拡張が可能な形でビジネスコンテキストを公開します。目標は「事業を一度モデル化し、必要なところすべてで使えるようにする」ことです。

### 5.5 Ontology の機能

Chafia 氏は、機能を次のように整理しています。

| 機能 | 内容 |
| ---- | ---- |
| コアコンセプト | エンティティ、関係、ルール、指標などで事業をモデル化する。セマンティックモデルにある既存の定義（measures、KPI）を、ontology から直接参照して再利用できる |
| Bindings | ontology は「定義」と「データ」の 2 つの部分から成り、定義をデータに結び付ける。対応ソースは、データウェアハウス、SQL データベース、ビュー、ショートカット、ミラーリングなどに拡大した。Fabric のエコシステム外のデータにも届く |
| データコピー無し | ontology の定義とメタデータはデータを参照するだけで、実行は各クエリに最適なエンジンが行う |
| AI による作成支援 | 「白紙の状態（blank page syndrome）」の問題（ontology 作成は難しく、時間とコストがかかる）に対し、AI で ontology を作成・検証・保守できる |
| ビジネスルール | ルールを自然言語で ontology に追加し、関係する概念にリンクする。エージェントのガードレールとなり、質問と回答の範囲も絞る。エージェントがどこで作られ、どこで動くかには依存しない |
| グラフ分析 | どのエンティティをグラフとして具体化するかを選べる。multi-hop 分析、最短経路などのネットワーク分析ができ、サイロ化した最適化ではなく、システム全体の最適化を見られる |
| 名前空間・継承 | 領域ごとに ontology を整理できる。複数チームが同じ定義を使いつつ、各自の属性を足せる |
| メタデータ | 任意の概念に、メタデータ、同義語、キーと値のペアを付けられる |
| バージョン管理 | ontology 組み込みのバージョン管理で、バージョンの追跡、比較、復元ができる。Fabric で使える Git と CI/CD パイプラインも使える |
| 相互運用性 | RDF のインポート/エクスポートに対応。Apache OC に参加しており、OC の ontology の定義にも貢献している（"which will come soon"） |
| IQ share | 今週リリース。テナントをまたいでデータを共有する IQ share で、ontology も共有できる（ISV や顧客がチームやテナント間で共有する用途） |

顧客・パートナーの事例として McKinsey が紹介されました。Brian Elliot 氏（音声認識の都合で表記は確定できません）の言葉として「ビジネスコンテキストをビジネス価値に変える」ことが語られ、McKinsey の Eclipse OS プラットフォーム（同じく表記は確定できません）が Fabric IQ と Foundry IQ を組み合わせて、ビジネスデータと企業の知識をつなぐ、と説明されました。物事が何で、どうつながるかを記述し、McKinsey の長年の業界知見を、ontology 内の「impact recipes」に落とし込む、という内容です。

### 5.6 顧客事例: Toyota Motor Corporation

Kimura 氏が、車という「最も文脈が豊かな環境」で Fabric IQ ontology を使う取り組みを話しました（以下、英語の発言に基づく整理で、聞き取りが難しい箇所があります）。

**課題。** 「夏は暑い」とドライバーが言ったとき、何を求めているかは人や場面によります。エージェントが 22 度に下げる提案をしても、そのドライバーにとって適切とは限りません。実際には 24 度のまま、ファンを強めることもあれば、別の日には汗ばんだ背中のためにシートを冷やしたい意味かもしれません。ファン、シート、窓、サンシェードなど、ドライバーごと、瞬間ごとに違い、エンジニアは事前にすべて列挙できません。車はドライバーが「何をしたか」は分かりますが、「なぜか」は分かりません。運転中のドライバーに、余計な操作を増やしたくありません。空調に限らず、運転支援の感じ方も人によって違う、安心感の話でもある、と述べています。

**ループの設計。** 1 回ごとにエージェントが少しずつ良くなるループを作っています（Microsoft はこれを hill climbing と呼ぶ、と述べています。2 日前の Foundry のセッションでは、エージェントの動作をどう確認するかが紹介されました）。今回の問いは、「この人にとって何が正しいかをどう学ぶか」です。ドライバーは理由を言いませんが、行動で示します。**修正を、失敗ではなく信号として扱います。**

1 つの体験として、次の 4 つをまとめて保持します。

1. 言われたこと
2. 状況
3. 提案
4. ドライバーが実際にしたこと

1 人のドライバーから始め、多くの走行で同じパターンを探します。例えば「強い日差しの下では、多くのドライバーが先にファンを強める」というパターンが見つかったとします。この段階では「候補」にすぎません。

**ontology に置く理由。** 候補をプロンプトに入れると、何が変わったか分かりにくく、元に戻すのも難しくなります。Fabric IQ の ontology に関係として一度書けば、人が承認し、バージョンが付き、すべてのエージェントが同じ意味を読みます。セマンティックモデルは数字を与え、ontology は意味を与える、という分担です。例として、「暑い」は「涼しくしたい」を意味し、現状は温度を下げる方法だけを知っている。そこに、「強い日差しの下では、まずファン」を足します。エンジニアが見るのはパターンであり個人ではなく、多くの走行に現れたパターンだけが共有の ontology に入ります。ontology は選択肢を与え、どれがそのドライバーに合うかは、そのドライバー自身の履歴が決めます。その履歴は、そのドライバーだけのものとして保持されます。

## 6. デモ・手順

### 6.1 デモ 1: Power BI セマンティックモデルを Copilot から使う

Bogdan 氏が "Let's play the demo" と述べて再生された動画です。話者の特定はできません（動画のナレーション）。食料品チェーンのオペレーションマネージャーの視点で、高利益の冷凍商品が棚から欠けるリスクを見つけるシナリオです。

1. 「オンシェルフ可用性が最も低い店舗」を尋ねる。Portland、Seattle、Denver が返る。回答には引用が付き、Power BI レポートにある on-shelf availability の指標（チームが信頼している定義と数字）が使われている
2. その 3 店舗で、安全在庫を下回っている商品を尋ねる。バニラビーンのアイスクリームが 3 店舗すべてで該当（1 商品のみ）。これはセマンティックモデルから得られた情報
3. 「サプライチェーンの上位 5 つのリスクは」と尋ねる。残り在庫日数で順位付けされ、3 店舗のバニラビーンが首位で、Portland は 1 日未満。尋ねていないリスクとして、Denver の wild blueberries と four cheese pizza も出る（安全在庫の上だが、あと 2〜3 日で切れる）

ナレーションの結論は、レポートとセマンティックモデルに蓄積された文脈が、同じ定義とセキュリティで、ワークの流れの中で使える、というものです。

### 6.2 デモ 2: Copilot chat で ontology を使う（private preview）

Chafia 氏が、Copilot chat に ontology を追加する体験を sneak peek として示しました（private preview）。

1. 冷凍食品オペレーションを ontology としてモデル化している。製品、在庫、サプライヤー、出荷とそのつながり。Power BI セマンティックモデルを土台に、冷凍ユニットから流れる温度のリアルタイム信号を加え、「cold chain exception rule」のようなルールも記述している
2. Copilot に、デモ 1 と同じ「サプライチェーンの上位 5 つのリスク」を尋ねる
3. ontology が在庫と、冷凍庫の温度、出荷をつなぐため、Seattle と Portland はどちらも 12 個不足で在庫だけなら同じだが、Seattle は冷凍庫が高温で、トラックが 5 時間遅れているため、Seattle が上位に来る
4. 「どの店舗で出荷が遅れているか」を尋ねる。San Francisco、Denver、Portland のトラックは 1〜3 時間遅れだが、遅延として扱われない。ontology のルールで「遅延は 4 時間超」と定義されており、Seattle の SH1001 だけが 5 時間で該当する
5. 「条件を満たす冷凍の温度異常があった店舗」を尋ねる。ontology なしでは、何が異常か、どのユニットがどの商品を保持するか、どのくらいが長すぎるかを推測するしかない。画面左では San Francisco、Seattle、Denver が該当。右の ontology 側では、冷凍商品を冷凍ユニットとそのストリーミングの値に結び付け、cold chain exception rule が一度だけ定義されている
6. 最後に、店舗の優先度、在庫、冷凍庫テレメトリ、ビジネスルール、出荷を横断する質問をする。ontology 側には、店舗、在庫、冷凍ユニット、テレメトリ、出荷と、それらをつなぐ 2 つのルールが表示される。両方のルールに該当するのは Seattle だけで、最初に対処すべき店舗になる

### 6.3 デモ 3: AI で ontology を生成する

Chafia 氏が、Fabric developer として Fabric workspace で操作する場面です。

1. workspace には、セマンティックモデル、lakehouse、eventhouse がある。ここで ontology item を作成する
2. 開始の方法は複数ある。RDF の既存 ontology をインポートするか、AI の支援を使う。ここでは AI を使う
3. 非構造化ドキュメント（非構造化データ）をコンテキストとして与え、workspace のデータを使って retail ontology を生成するよう依頼する
4. 下書きの ontology が提案されるので、確認して微調整し、作成を確定する。region、warehouse、promotion、store などが作られる
5. region を開くと、セマンティックモデルのデータと、リアルタイムの天気データに結び付いている。さらに別のデータソースでも拡充できる
6. ontology は Power BI セマンティックモデルのすべてのモード（import、direct query、direct lake）に結び付けられる。セマンティックモデルのメジャーが表示され、DAX 式も確認できる
7. 名前空間を使い、運用なら shipping、調達チームならサプライヤー、のように領域を整理できる。継承と再利用の概念もある
8. ルール（例: inventory at risk rule）に、リンクされた ontology 要素が表示される。概念にはメタデータ、同義語、キーと値のペアを持たせられる

### 6.4 デモ 4: Toyota のデモ（Kimura 氏）

Microsoft と共同で作ったデモコンソールで、背後のデータは Fabric にあります。

1. ドライバーが「暑い」と言う。エージェントは温度を下げる方法しか知らないため、温度を下げる提案をする
2. ドライバーは 24 度のままにして、ファンを強める。この変更が、失敗ではなく信号として Fabric に入る
3. Fabric が、1 人ではなく全ドライバーを見る。強い日差しの下で、多くの提案が「ファン重視」に変更されている。これらは ontology になかった。「暑さではなく日差し」という、誰も書いていなかった文脈
4. 候補が、Fabric の ontology agent（plan mode）に渡される。エンジニアが承認するまで何も変わらない。エージェントは、新しい関係「強い日差しの下では、ファンを優先」を 1 つ追加する計画を書く
5. エンジニアが承認し、バージョン 1.3 が使われる
6. 次の走行で同じ言葉を言うと、エージェントに選択肢があり、このドライバーには 24 度のままファンを強める提案をする。このデモの走行では、最初の提案で受け入れられた（2 回のやり取りが 1 回になった）
7. ドライバーが理由を尋ねると、ontology、日差し、そのドライバー自身の履歴を使って答える
8. Fabric 内の ontology を見せる。デモでは小さく 9 種類のエンティティタイプにしてあるが、本番の設計ははるかに大きい。すべての変更はバージョン履歴に残り、いつでも戻せる

「どうスケールさせるか」という質問（質問者は特定できません）には、次のように答えています。車両信号、音声、日差しなどの外部の文脈は Fabric に入る。本番ではストリーミングに event streams を選択肢としている。すべては OneLake の 1 つのデータコピーの上で動く。すでにできている点は、走行データが本番の信号定義を使っていることと、共有される意味は小さく保たれ、ドライバーが増えても増えないこと。これからの点は、Foundry Agent Service を ontology につなぐことと、このループを本番に持ち込むことです。

### 6.5 デモ 5: ontology を使う data agent と最適化（Bogdan 氏のパート）

Bogdan 氏は、まず自分の組織の例で、「もっとソフトウェアを出荷したい、ただしバグは増やしたくない」のように、ビジネスの目標は単純でも実現は複雑だと話しました。Fabric には、ontology の文脈を使って単純なビジネス課題を、明確な計画に変え、what-if 分析で判断の影響を評価できる技術があり、厳密な数理モデルで最適解を出す、という説明です。これは **プレビューで出荷中**で、Fabric の data agent（仮想データアナリスト）が ontology の上で動くのを、「おそらく今日が初めて」見ることになる、とも述べています。

1. retail ontology を見せる。製品、注文、在庫、出荷を、lakehouse、eventhouse、セマンティックモデルをまたいで結び付けている。例えば、予測される在庫不足を、影響を受ける製品や販売につなげられる
2. この ontology を data agent に追加し、最適化と what-if 分析のための分析ツール **OptiGuide** も追加する
3. 「配送を期限内に完了し、冷蔵品を冷たく保つには、キャリアをどう割り当てるか」と尋ねる
4. ontology がデータへの問い合わせを助け、OptiGuide が結果から最適なキャリア割り当てを生成する
5. agent が質問を最適化計画の案に変える。エンティティ（shipments、orders、regions、carriers）と、どの注文をどの出荷が満たし、どこへ行き、誰が担当するかの関係を整理する。モデルの入力はこれらの関係から決まる
6. 主な決定は、各出荷にどのキャリアを割り当てるかと、使うキャリアの数。各出荷には必ず 1 つのキャリアを割り当て、コールドチェーンの要件は必須。目標は、緊急の注文と期限内の配送を優先しつつ、キャリアを少なくすること
7. 計画を確認、調整してから実行する。計画を確定して最適化を実行する
8. 最適な計画は 3 つのキャリアを使う。「各キャリアの注文割り当てを見せて」と尋ねて内容を確認できる
9. what-if として、優先注文（expedited orders）の重みを上げる。同じ 3 キャリア、180 件の注文割り当ては変わらない。スコアが変わるのは優先度を変えたからで、配送性能が改善したわけではない。元の計画は、この新しい重み付けでも最適のまま
10. この data agent を Microsoft 365 に公開し、財務チームが日常業務の中で同じエージェントを使えるようにする

## 7. 注意点・発表者の気付き

- エージェントにアクセスできないデータの上で推論させることはできないため、まずデータの統合から始める。
- ontology 作成の難しさ（「白紙」の問題、時間とコスト）は、AI 支援で緩和する、という位置づけです。
- Toyota の助言: ①最初は全体ではなく 1 つのユースケースから始める、②先にすべてを書き出そうとしない（できないので）、ループを作って回す、③共有するのは意味であって個人ではない。多くの人が行うことは共有の意味になり、1 人が好むことは個人のものとして残す。
- Toyota の取り組みでは、まず空調から始めた理由として、外した場合も危険ではないからと説明している。次は、外すとコストが大きい場面（運転支援が各人にどう感じられるか）に広げたい、とのことです。
- ontology はプロンプトに埋め込むのではなく、バージョンと承認を持つ形で保持するほうが、変更点が見え、元に戻せる、と述べられました（Toyota の考え方）。
- what-if のデモで、スコアが変わっても割り当てが同じになる場合は、優先度を変えたことによるもので、配送性能が改善したことを示すものではない、と明確に説明されています。

## 8. 利用者にとっての利点

- **既存投資の活用:** 長年作ってきた Power BI のレポートとセマンティックモデルが、同じ定義とセキュリティのまま、Copilot、Excel、ChatGPT などから使える。Copilot chat での Power BI とのチャットのトークンは無料
- **オープン性:** OneLake はオープン形式で、他社エンジンも同じセキュリティルールを適用できる。ビジネス指標を Snowflake の semantic views とやり取りできる
- **一度モデル化して、どこでも使う:** ontology は、人、アプリ、Copilot、エージェントで共通の理解を共有する。ルールはエージェントがどこで動いても有効
- **精度の向上:** Copilot のデモでは、同じ質問でも ontology により、リアルタイム信号とルールを加味した、より的確な答えが得られた（Seattle の例）
- **顧客事例:** Toyota は、ドライバーの修正を信号として扱い、承認とバージョンを備えた ontology に反映するループを構築した。デモでは、2 回のやり取りが 1 回になる例を示した。McKinsey は、自社の業界知見を ontology 内の impact recipes に落とし込んでいる
