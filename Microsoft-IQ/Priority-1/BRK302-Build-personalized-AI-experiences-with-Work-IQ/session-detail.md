# BRK302 Build personalized AI experiences with Work IQ

## 1. はじめに

このセッションは、エージェントを開発する人に向けて、Work IQ を使って「自分のエージェントに、本物の仕事の文脈を理解させる」方法を紹介するものです。開発者が自前で連携の層を作らなくても、日々使っているツールの中で、組織の権限を守りながらエージェントが仕事の文脈を扱える、というのが発表の主張です。

構成は、(1) エージェントが仕事の文脈を見られない問題と Work IQ の位置づけ、(2) Copilot Studio、GitHub、VS Code、Claude Code を使った一連のデモ、(3) 今回発表された新機能（retrieve、SharePoint ツール、メモリ、Listen など）、(4) 組織への拡張（プラグイン、パートナー事例、Agent 365 によるガバナンス）です。

発表は、1 つのシナリオ（顧客ポータルをリリースできるか）を軸に、Work IQ がどの場面で何を変えるのかを見せる形で進みます。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK302](https://ignite.microsoft.com/en-US/sessions/BRK302)

## 3. 何に関する発表か

Work IQ は、メール、会議、作成・閲覧したドキュメントなどの仕事のデータと、接続されたビジネスアプリから、誰が関わり、どんな仕事が進み、今何が重要で優先度は何かという「理解」を作り、それをエージェントに渡すものと説明されています。登壇者の例では、Tolga 氏が自分のメール、参加した会議、作成・閲覧したドキュメントをもとに、Work IQ に「自分の仕事を描いて」と頼み、その結果が不気味なほど正確だったと紹介しています。

開発者がこの Work IQ にアクセスする方法は 3 つ示されています。

| 方法 | 用途 |
| --- | --- |
| MCP | MCP を話せるあらゆるエージェントやコーディングツール向け |
| REST | アプリやサービスから呼び出す |
| Agent to agent（A2A） | Work IQ から、Copilot やテナント内のエージェントにタスクを委任する |

Work IQ は「Studio」（音声では Studio とだけ聞こえます。続くデモは Copilot Studio です）、Microsoft Foundry、GitHub に組み込まれており、MCP を通じて、その他のエージェントやプラットフォームでも動く、と説明されています。

## 4. 発表者が伝えたいメッセージ

発表者は、「モデルは強力だが、仕事で役に立つには、さらに 3 つが必要」と述べています。

1. **Context（文脈）**: 決定事項、関わる人、プロジェクトの背景にあるシステムを理解する
2. **Action（行動）**: レコードの更新やメール作成だけでなく、実際に仕事を終わらせる
3. **Trust（信頼）**: 組織の権限、つまり自分の権限の範囲内に収まり、エージェントへのアクセスを統制できる

Work IQ はこの 3 つをまとめて、自分が作るエージェントに届ける、という位置づけです。そのため発表は「作る」「制御する」「どこから始めるか」の順に進みます。

## 5. 発表内容の詳細

### 5.1 エージェントが「仕事を見られない」問題

Tolga 氏は、モデルは有能で回答も流暢だが、「仕事が見えない」ことが問題だと説明しています。例は、顧客ポータルを開発するプロジェクトです。

- 会議で、法務が「バイリンガルで出荷しなければならない」と決める。しかしこの決定は、コードにも Jira にも入らなかった
- Jira には 2 件の未完了項目が残っているが、エージェントはそのシステムにつながっていない
- チームは GitHub や VS Code で作業しているのに、エージェントは別のチャットウィンドウにいる

どれも「つながっていない」状態で、エージェントは答えることはできても、自分の代わりに仕事をすることはできない、という整理です。

同じ質問「顧客ポータルは準備できているか」で比べています。

| 条件 | 回答 |
| --- | --- |
| Work IQ なし | リポジトリには届き、機能は完成して見えると答える。トラッカーを確認するよう言うが、引用もなく、会議のメモは見ていないのでつなげられない |
| Work IQ あり | まだ準備できていない。法務の要件でバイリンガルが必要だが、それがコードにも Jira にも入っておらず、Jira の項目が 2 件未完了 |

同じエージェント、同じモデルで、違いは「見えるもの」だけだと強調しています。

Work IQ は、すでにある会議、接続された Jira の 2 件の項目、ビジネスシステムやアプリなど、既存のプロビジョニングの範囲のデータから、関係者、仕事の内容、今重要なこと、優先度を理解します。その理解は、チャット、co-work、autopilot、コード、自分で作るエージェント、使っているハーネスなど、仕事の場所に付いていきます。エージェントは毎回白紙から始めない、というのが要点です。

### 5.2 Work IQ の API の設計

> 注意：「13 個のツール」と発話されていますが、続いて挙がったのは fetch、update entity、create entity、ask a question、do action の 5 つで、数字や名称は音声認識の都合で確定できません。

説明の骨子は次のとおりです。

- API の表面は意図的に小さい。ツールは数が少なく、安定させる方針で、変わらない
- 一方で、カバレッジは増やす。自分の M365 データは `/me` 名前空間（slash me namespace）、統合されたビジネスアプリは `/business apps` の下にあり、さらに追加していく
- ツールとパスを組み合わせるとアクションになる。例えば、fetch で Teams のメッセージを読み、do action で Teams のスレッドにメッセージを送信する。CRM のレコード更新も、business apps のパスに対する do action で行う
- モデルは、すでに知っているツールから選ぶので、何百ものエンドポイントを調べる必要がない。新しいソースが加わるとパスとして現れるので、今作ったものは今後も動き続ける

**retrieve ツール**: 最もよく使うツールとして紹介されています。「ポータルの言語について何を決めたか」と尋ねると、会議の録画と要件ドキュメントから 2 つの passage が返ります。retrieve は回答を作らず、エージェントに「証拠」を渡すので、回答の作り方は開発者側が制御できます。ユーザーとして実行されるため、そのユーザーの権限が回答にも引き継がれます。各 passage は出典にリンクし、Microsoft 365 と同期済みコネクタの、アクセス権のあるコンテンツ全体を検索します。

### 5.3 本番での効果の測定

デモが示すだけでは承認されないとして、測定結果が紹介されています。同じモデル、同じタスクで、エージェントを 2 群に分けた比較です。一方は Work IQ を使い、もう一方は従来の Microsoft 365 API を使います。後者は必要な情報を検索し、結果を全ページ読み、ダウンロードして読み込むため、コンテキスト（コンテキストウィンドウ）が増えます。Work IQ は直接の答えを返すので、ターン数とトークン数が少なく済みます。

| 指標 | Work IQ を使った場合 |
| --- | --- |
| 完了したタスク数 | 1.7〜3.9 倍 |
| 速度 | 最大 70%（音声では「up to 70% task」と聞こえます） |
| 完了したタスク 1 件あたりのコスト | 40〜74% 低い |

ターンとトークンが減れば、請求も小さくなる、という説明です。測定の詳細な条件（タスクの内容など）は、発表では説明されていません。

### 5.4 Work IQ にこれから加わる機能

ここまでは「質問に答える」エージェントで、次は「自分から動く」エージェントに進む、という流れで、3 つの投資が説明されています。今週から展開が始まり、来週にかけて続くという説明です。

**Context（文脈）**

- retrieve ツールの展開開始。引用付きの passage を、開発者自身のモデルに渡して推論できる
- 約 60 個の新しい SharePoint ツール。AI-ready なコンテンツを Work IQ 経由でエージェントに渡し、サイト、ライブラリ、ファイルの管理もできる
- メモリ。利用者から大きな要望として聞いたもので、Copilot だけでなく、自分のエージェントを含むあらゆる接点で優先事項を把握する。Work IQ の API にもメモリを導入する

**Action（行動）**

- **Listen**: 文脈に関わる情報が届いたときに、エージェントを起こすツール。次のスライドで説明
- エージェントが、Word、Excel、PowerPoint のドキュメントを、自然言語で作成・編集できる
- 長時間実行のタスク。エージェントを何度も起動する必要がなく、いつ起きて何をするかをエージェント自身が管理する

**Trust（信頼）**

- すべてが、エージェント自身の ID と、テナント、エージェント、ユーザーの各レベルで設定したポリシーのもとで動く

**Listen の詳細**: 現在、変化に反応させたい場合はポーリングを実装しますが、ポーリングのたびにトークンを消費し、そのたびに課金されます。Listen は、意味のあることが起きたときだけエージェントを起こします。Manuel 氏のデモでエージェントが起動したのはプルリクエストが開かれたときでしたが、仕事の大半は M365 の中で動いており、そこで起きた変化を待ち受けるために Listen を作っている、という位置づけです。例として、自分が出席しなかった会議でアクションアイテムを割り当てられた場合、通知だけでなく、レポートや PowerPoint 資料、メールの下書きの作成を、Listen のトリガーと長時間タスクでエージェントが始められる、と述べています。もう 1 つの例は、今後の会議で「先週何があったか」を上司に報告する準備をエージェントにさせる、というものです。**Listen は 12 月 4 日からパブリックプレビュー**と説明されています（年は発話では述べられていません）。

### 5.5 組織への拡張: プラグイン、スキル、エージェント

Work IQ は個人の文脈（仕事、人、会話）から始まり、組織の文脈へはプラグインを通じて広げます。Microsoft plugin registry があり、一度作ってプラグインとしてパッケージ化すれば、どこでも再利用できるため、チームごとに連携を作り直す必要がありません。役割は次のように整理されています。

| 要素 | 役割 |
| --- | --- |
| Skills | 仕事を片付けるための実績のあるやり方 |
| Tools | システム・オブ・レコードやデータストア（自社で作ったシステムを含む）をつなぐ |
| Agents | スキルとツールを orchestrate し、Work IQ を伴って仕事を進める |

一度つないでプラグインにして、あらゆる場所で再利用し、Agent 365 で統制する、という流れです。

### 5.6 Microsoft 以外のアシスタントとパートナー

Work IQ は、Copilot、Claude、ChatGPT、Gemini など、利用者がすでに使っているアシスタントにも提供されます。同じ仕事の文脈、同じ権限、同じアクセスで、どれを選んでも Work IQ が付いてくる、という説明です。現状は次のとおりです。

- ChatGPT の Plugin Directory では今日から利用可能
- Anthropic と Gemini Business にはまもなく対応
- Copilot ではすでに利用可能

パートナーの例として、次が挙げられています。

- 音声では「CNN ATAN」と聞こえる企業（綴りは音声認識の都合で確定できません）: 連携を実現し、ワークフローをつないでいる
- Adobe: Work IQ を CX co-worker に取り込み、顧客データ・顧客コンテンツと仕事の文脈を組み合わせる
- Atlassian: Work IQ を Rovo Studio に取り込み、Atlassian のワークフローと Work IQ のビジネス文脈を組み合わせる（音声では「Rover Studio」と聞こえます）
- SLB: エネルギー分野の地下データを Work IQ の文脈と結びつけ、研究を進める

これらはすべて同じ API と MCP サーバーの上に作られていると説明されています。

逆方向もあり、**300 以上のコネクタ**で、CRM、チケット管理、HR、財務など、すでに使っているシステムを Work IQ に取り込めます。デモの Jira がその例です。管理者が一度接続して設定すれば、作ったすべてのエージェントが、組織が設定した権限の範囲で利用できます。

### 5.7 Agent 365 による統制

エージェントやデータが増えたとき、管理者が必ず聞く質問として「どうやって制御するのか」が挙げられ、答えが Agent 365 です。

- **統制**: すべてのエージェントが、人と同じように自分の ID を持つ。エージェントが Work IQ を呼び出すたびにポリシーが実行され、このエージェントがこのデータにアクセスし、消費し、呼び出し元に返してよいか、が判断される
- **観測**: フローをエンドツーエンドで見られ、記録される。エージェントが触れたデータもすべて見える
- **消費の制御**: エージェントごとに月次の予算を設定し、使いすぎるとアラートを受け取れる
- **価値の評価**: Agent 365 でエージェントの価値を予測・測定し、調整に役立てられる。開発者がエージェントを作り、Agent 365 を通じて管理者が「はい」と言う、という関係です

**ポリシーの 2 階層**（スライドの例）:

1. テナントレベル: 管理者が上限の境界を設定する。この例では、エージェントはビジネスデータの読み書きとメールの読み取り、振り分け（triage）はできるが、ユーザーに代わってメールを送信することはできない
2. エージェントレベル: そのエージェント固有の、より狭いポリシー。この例では、ビジネスデータは読めるが、CRM レコードの削除や内容変更のような破壊的な操作はできない

さらに、エージェントは自分が書いていないコンテンツも読みます。その一部には、エージェントをだますための指示が隠されていることがありますが、**Work IQ は、エージェントが読む前にそれらを除去する**と説明されています。

**コスト**: Microsoft 365 管理センターには、何が、誰が、どれだけ、どのエージェント、サービス、モデルで使っているかが表示されます。IT が支出の上限を設定でき、到達すると追加は IT または財務が判断します。部署ごとの支出は、組織がすでに持つ請求構造に対応づけられ、使ったチームにコストが付きます。Fabric IQ にエクスポートして独自のレポートも作れます。組織全体で今月の支出を見て、高くなっていれば抑えられます。例として、claims agent のコストは上昇しているが、コストをはるかに上回る価値を生んでいるので、維持または調整できる、というスライドが示されています。エージェント単位で支出の上限を設定したり、エージェントを外したりと、効果のある所に手を打てる、という説明です。

### 6.1 シナリオの設定

- 主人公の Mateo は、コーヒー焙煎会社の開発者で（社名は音声では「Ford Coffee Roasters」「Forth Coffee Roasters」「4th Coffee Roasters」と揺れており、確定できません）、顧客ポータルを開発している

- ポータルは英語のみ

### 6.2 デモ 1: Copilot Studio で release readiness agent を作る

1. Copilot Studio でエージェントを作り始める。Work IQ は Copilot Studio で GA になり、既定でオンになっている、と説明される
2. Mateo は **release readiness agent** を作る。ポータルが出荷可能かを、全社で標準化された手順で評価するためのもの
3. Work IQ に加えて、Jira と GitHub に接続して文脈を取得する。また release readiness skill を使い、評価の一貫性を保つ
4. エージェントを公開し、Copilot で「顧客ポータルの最新状況は？リスクはあるか？」と尋ねる。実行には 1 分ほどかかるため、結果を先に見せる
5. 結果は、来週のローンチに対して**高リスク**。カナダでの提供のため英語とフランス語に対応する要件があるが、GitHub にも Jira にも記録がない。この要件は Teams のチャットから来ており、Work IQ がコネクターとして、それをエージェントに渡している。元のチャットは、数週間前に Mateo がチームに「英語とフランス語が必要」と伝えたもの
6. 次に、意思決定者である Maya の視点。同じ英語・フランス語の要件が、同じチャット由来で見える。さらにマネージャーとして、Victor が退職予定で、その役割の補充が必要という人員面の制約も見える。ここでは、**Maya には見えるが Mateo には見えない**情報があり、Work IQ が権限を尊重している、と説明される
7. 同じエージェントで、Maya が「マーケティング担当マネージャー向けの Teams チャネルに、この状況更新のサマリーを投稿して」と依頼する。数秒で実行され、事前に実行したものを見せたところ、マーケティングチームに文脈に沿った更新が届いていた。コンテキストを切り替えずに、タスクとワークフローを完了できる例として示される

### 6.3 デモ 2: GitHub agentic workflows と Work IQ による自動化

Mateo は、マーケティングの Tessa が「コードが変わったら、自分とチームにとって何を意味するのかを知りたい」と求めたことを受け、GitHub Actions と GitHub agentic workflows に Work IQ を組み合わせた自動化を作ります。

1. 「Code」というタブが示され、Mateo が、チームの理解を助けるアーキテクチャ図を準備する（コード側でも Work IQ が使えるため、Mateo の文脈がサイトに反映される、と説明される）
2. 仕組み: GitHub リポジトリに変更が push されると、agentic workflow が動く。GitHub Actions 内の Copilot エージェントが変更を分析し、何が変わったかを把握する（セキュリティ上の問題が出ていないかの確認にも触れています）。ただしそれだけでは、変更が自分たちにとってどう関係するかは分からない。そこで、サインインしたユーザーとして Work IQ にアクセスできる Teams エージェントを呼び出し、マーケティングや経営などの各チームに「何が変わり、何が自分に関係するか」を届ける
3. 先ほどの Maya の更新を受けて、Manuel 氏は、その変更を追跡する GitHub issue を作成した。Work IQ から、仕事の追跡に実際に使うシステムに情報を移した、という位置づけ
4. ワークフローが数分前に実行を終えている。コードの変更が、GitHub Actions 内のエージェントの起動につながり、Work IQ を持つ Teams エージェントに通知された
5. 結果として、Teams に更新が届き、「英語とフランス語に対応する必要がある」というコードの変更と、マーケティングが確認すべきこと（CTA、文言、プライバシーなど）が示された。コードの変更を、その日の次のアクションに翻訳した例です

**n8n への展開**: Work IQ は API なので、GitHub や GitHub Actions を使わない人向けに、n8n でツールを検索して Work IQ を MCP として agentic workflow に追加できる、と紹介されています。GitHub のトリガーがエージェントを呼び、エージェントが Work IQ と協調する、同じワークフローを別のプラットフォームでも実現できるという説明です。事前に試したものを見せています。

### 6.4 デモ 3: VS Code と Claude Code

1. VS Code の GitHub Copilot に「コードを説明して」と尋ねる。コードの理解には役立つが、決定事項と一致しているかは分からない
2. Work IQ MCP は、すでに VS Code にツールとして追加済み。chat customizations で Work IQ を検索すると MCP とプラグインが見つかり、プラグインは今後増える。スキルで、MCP の使い方を指示する
3. Work IQ を使って、コードが最新の仕事の決定と整合しているかを確認すると、CTA の文言など複数のギャップが見つかる。関連する Teams の議論も引かれる。主な不一致は、フランス語が有効になっていないこと
4. 「ポータルがカナダのローンチ向けに英語とフランス語に対応するようにして」と依頼する。読み込みに時間がかかるため、先に別の内容を見せる
5. **Claude Code** にも Work IQ MCP を追加できる。ツールとして retrieve、fetch、ask、list agent などが見える。「Copilot にある自分のエージェントを一覧して」と頼むと、M365 テナントで Copilot にインストールしたエージェントが一覧され、その中に Copilot Studio で作った release readiness agent がある。続けて「顧客ポータルの最新状況は？」と尋ね、Claude Code でも Work IQ 経由で状況を取得する
6. VS Code に戻り、変更を承認して再読み込みすると、英語とフランス語に対応し、言語を切り替えられるようになった。これで Mateo の仕事は完了し、来週出荷できる

## 7. 注意点・発表者の気付き

- **リリースの時期**: Listen は 12 月 4 日からパブリックプレビューです。retrieve は展開が始まったところで、今回発表された機能は今週から出荷が始まり、来週にかけて続くと説明されています
- **権限の扱い**: retrieve はユーザーとして実行され、そのユーザーの権限が回答に引き継がれます。デモでも、Maya には見える情報が Mateo には見えないことが示されました
- **ポーリングのコスト**: ポーリングはそのたびにトークンを消費して課金されるため、その代わりに Listen を使う、という説明です
- **エージェントは外部コンテンツも読む**: 隠された指示でエージェントをだますコンテンツがあるため、Work IQ が除去すると説明されています
- **デモの性質**: 一部は事前実行の結果を見せており、VS Code での修正は読み込みに時間がかかる場面がありました
- 一部の数値・名称（ツールの数、パートナー名や Rovo Studio の表記、「Cloud」と聞こえる Claude など）は音声認識の都合で確定できません

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **開発の観点**: 連携の層を自前で作らずに、エージェントが組織の仕事の文脈を理解でき、Copilot Studio、GitHub、VS Code、Claude Code、n8n など、使っているツールに組み込める
- **測定結果**: 従来の Microsoft 365 API を使うエージェントと比べて、完了タスクが 1.7〜3.9 倍、速度は最大 70%、完了タスクあたりのコストは 40〜74% 低い
- **安全性**: ユーザーの権限、テナントとエージェントのポリシー、除去される隠れた指示により、必要なものだけがエージェントに届く
- **管理者**: エージェントごとの ID、観測、月次予算とアラート、支出上限、部署ごとの課金への対応づけ、価値の予測と測定が可能
- **再利用**: 一度作ったプラグインを組織全体で再利用でき、Work IQ 自体も Copilot、Claude、ChatGPT、Gemini などで同じ文脈・権限で使える

具体的な顧客の成果としては、デモのシナリオ（デモのシナリオ上の Mateo の事例）以外は、発表では挙げられていません。

## 9. まとめ

発表の要点は、エージェントを役に立てるには、モデルの性能だけでなく、文脈、行動、信頼が必要で、Work IQ がその 3 つを MCP、REST、A2A で提供するという点です。顧客ポータルのシナリオでは、同じモデルでも、Work IQ があることで、コードにも Jira にも記録されていなかったバイリンガル要件に気づき、状況報告、チーム通知、コード修正までつなげられることが示されました。

今後は retrieve、SharePoint ツール、メモリ、Listen、Office ドキュメントの作成・編集、長時間タスクが加わり、エージェントは受け身で答えるだけでなく、自分から動くようになります。組織全体で使う段階では、プラグインで再利用し、Agent 365 でアクセス、消費、コスト、価値を管理する、と説明されました。
