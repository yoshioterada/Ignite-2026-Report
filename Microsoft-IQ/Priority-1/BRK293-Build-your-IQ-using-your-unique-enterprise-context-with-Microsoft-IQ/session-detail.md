## 5. 発表内容の詳細

### 5.1 いまのコンテキスト提供方法の限界

Dipti 氏は、現在はコンテキストを主に AI スキル（skills）で渡している、と説明します。文書の要約、メールの下書き、データへのクエリなど、あらゆるタスクがスキルになり、すでに数千のスキルがあります。有用ですが、複数のステップからなる複雑なプロセスでは、適切なコンテキストがないと実行のたびに結果が少しずつ変わります。

例として、CFO のラウンドテーブルで聞いた実例を挙げています。3 人のアナリストが同じ「四半期の差異レポートを準備して」という依頼を出しても、結果がたびたび違います。あるエージェントはあるスキルを拾い、別のエージェントは適切なコンテキストを持たず、さらに別のエージェントはまったく違うポリシーを拾う（あるいはポリシーを拾わない）、という状況です。

そのため、現状のやり方は、次の問題を抱えているとしています。

- **コスト**：1000 個のスキルや多数の MCP エンドポイントがあると、エージェントが正解にたどり着くために多くの作業とトークンを使う。
- **一貫性がない**。
- バックエンドで、独自のインデックス作成や検索が多く必要になる。
- 作業の重複と、弱いガバナンス。

こうした理由から、コンテキスト管理が主流になりつつある、とも述べています。基調講演でも触れられた内容で、必要なものを「コンテキストプラットフォーム、コンテキストレイヤー、コンテキストエンジン」などと呼んでいます。要件は 3 つです。

1. コンテキストを**整理（curate）**する。サプライチェーンや税務アドバイザリーなどの専門家が、自分のコンテキストを整理する。
2. コンテキストを**維持**する。最新に保ち、権威を持たせ、統制する。
3. 質問に応じて適切なコンテキストの断片を、エージェントに**配布**する。

### 5.2 Microsoft IQ と business plugins の位置づけ

Microsoft IQ は「エンタープライズのコンテキスト管理レイヤー」で、business plugins がそれをまとめる要素、と紹介されています。Copilot だけでなく、Claude、ChatGPT、任意のカスタムエージェントからも使え、モデルに依存しません。

Microsoft IQ の下には、すでにある次の IQ があります。

| IQ | 内容 |
| ---- | ---- |
| Work IQ | ビジネス生産性のワークフロー（メール、SharePoint、Teams、チャット、共同作業） |
| Fabric IQ | セマンティックモデル、オントロジー、OneLake、レポート |
| Foundry IQ | ナレッジ、コンプライアンス情報、ナレッジベース |
| Web IQ | 公開情報 |
| サードパーティ IQ | パートナーや、日々使っている他の製品のコンテキスト |

Copilot や Agent 365 との関係では、これらの IQ がその下に位置し、継続的な改善と関連性を保つ仕組みが必要だと述べています。基盤には Fabric、Foundry、GitHub があり、すべて Azure 上で動くとのことです。

### 5.3 顧客の声：EY（Jeremy Kolpak 氏）

Jeremy 氏は、EY を、テクノロジー、税務、監査の会社で、約 400,000 人の組織だと紹介しています。その規模では、組織中に知識が散らばっていて、質問は「友人に聞く」ような人間関係に依存しがちでした。長年、知識の統合に取り組んできて、Microsoft の IQ プラットフォームが、それを置く最適な場所だと考えています。

監査や税務の統制のように、推測では済まない領域で、コンサルタントが顧客と仕事をしながら権威ある答えを素早く得られる、次世代のフレームワークを築きたい、という説明です。

期待する効果として、2 つの観点を挙げています。

1. **社内向け**：毎日 10,000 人くらいが同じ質問をして、少しずつ違う答えを得ている（と見ている）ので、その知識を体系化できる。トークンの支出を減らし、コンサルタントやビジネスパートナーにより良い結果を提供できる。
2. **顧客向け**：6 か月前に、システムのモダナイゼーションで、レガシーシステムに関する組織知識を整理する方法を検討していた。個々のシステムの機能ではなく、ユーザーがビジネス上何をしているかを捉えたい。独自に作る方向で進めていたが、今回の新機能が出たので「作らなくてよい。これにつなげばよい」と考えた。システム開発のときに、画面だけでなく、信頼できる答えとして Copilot からも機能を公開できるようになる。

### 5.4 business plugins とは（Josh Caplan 氏）

Josh 氏は、最初に「business plugins はコンテキストを増やすものではない」と述べます。私たちはすでにドキュメント、チャット、会議、セマンティックモデル、オントロジーなど、コンテキストの海の中にいます。難しいのは、そのつど「どれが権威ある正しいものか」を知ることです。それを知っているのは、管理者ではなく、コンテキストを作ったり使ったりしている専門家ですが、それを整理する場所がありませんでした。

エージェントごとに教え込むこともできますが、従業員にするのと同じように、全体像を 1 か所にまとめる場所を作る、というのが business plugins です。チーム、プロジェクト、製品など、専門家が適切だと考える単位で、権威ある情報源を作れます。

#### 利用者・エージェントへの届け方（2 通り）

1. 従業員やエージェントが business plugin を**受け入れる（accept）**。一度受け入れるとパイプができ、プラグインが更新されるたびに、権威ある内容が自動で流れる。
2. 組織の管理者が、「公式に承認（certified）された business plugin」として設定する。誰も受け入れ操作をしなくても、自動でコンテキストが届く。

#### 動き方

これは通常のプラグインとは違い、探したり選んだりする必要がありません。エージェントが質問すると、プロンプトはどのプラグインを使うかを知る必要がなく、Microsoft IQ が、自分に有効なすべての business plugins を横断して、プロンプトに関連するものだけを検索します。結果は、答えになりそうな順にランク付けされ、「どんなときに何を使うか」を示す短い説明とともに返されます。エージェントに返るのはその一覧だけなので、トークン量を小さく保てて、エージェントはその優先順位付きの一覧から使うものを選べます。

Josh 氏は、新しい従業員に検索エンジンだけを渡して「自分で探して」とは言わず、ハンドブック、wiki、マニュアルなど「これが必要ならここへ」というガイドを渡すのと同じ、と説明しています。business plugins はエージェントにとっての**プレイブック（ルーター）**です。例えば、遅延を調べるときはこの Fabric IQ へ、予算ポリシーを知りたいときはこの Work IQ へ、といった指示になります。

作成は **IQ.microsoft.com** で行います。新しい UX が、手順を案内し、プラグインの構成を考えさせます。人に渡す wiki を作る感覚に近いそうです。Copilot（組み込みのもの、または利用者が選ぶ Copilot やチャットボット）にプレイブックを作らせることもできます。ただし、**常に人間がループに入って**検証し、プレイブックが権威ある指針を反映しているかを確認することが前提です。

### 5.5 ライブデモの内容（Josh 氏）

Josh 氏は「パンデミック以来初めてのライブデモ」と話しており、実際に画面を操作しています。デモの流れは、6 章にまとめています。ここでは、デモで示された仕組みの要点をまとめます。

- **business plugin の中身**：wiki のように、自然言語で使い方を説明するもの。そこに、スキル（例：返金額のチェック）、Word 文書、他のプラグイン（Stripe や Salesforce など、組織内または第三者のもの）、人、SharePoint サイト、Foundry のナレッジベース、Fabric IQ などが並んでいる。単なる一覧ではなく、「これは権威ある情報で、こう使う」という指示。
- **各要素の要約**：それぞれをクリックすると、何のためか、いつ使うか、いつ使わないか、が示される。これが、プロンプトが来たときの検索で、エージェントに「これを使え、あるいはこちらを使え、この 2 つを組み合わせて使え」と伝える情報になる。
- 結果として、エージェントは「新入社員」のように始めるのではなく、最初から、そのタスクに合った正しいコンテキストを持って動き出す。

### 5.6 階層構造、ガバナンス、セキュリティ

Josh 氏は、"compounding intelligence"（基調講演でも何度か使われた表現）という考え方を紹介します。組織はフラットではなく、階層があります。例えば、自分のチームの公式な顧客ダッシュボード、上司の持つより大きなチームのダッシュボード、Microsoft の全員が毎年受けるトレーニングなどです。

business plugins は、この階層に合わせて設計されています。

- 最上位に **root** があり、その下に **section** をいくつでも、必要なだけ入れ子にして作れる。
- 各 section に、それぞれの所有者、権限、専門家を置ける。
- 人やエージェントを、自分に合う最も低い section に追加する。そうすると、その階層のコンテキストに加え、**真上の経路にあるすべての上位階層の内容を自動で継承する**。
- 各チームが自分のレベルを管理し、専門家が自分の担当を管理するため、調整は不要。50 か所に追加される必要もない。

**エンドースメントと認証**：business plugin は、同じ品質とは限りません。「promoted（推奨）」にしたり、「certified（認証済み）」にしたりできます。certified には管理者（または管理者の委任先）の承認が必要で、どちらもバッジが付きます。certified になると、ユーザーやエージェントが受け入れや有効化の操作をしなくても、最初のプロンプトの実行時や、エージェントの最初の指示で自動的にコンテキストに注入されます。組織全体、または組織の一部の全員が知るべき内容には、certification が非常に強力だと述べています。

**アクセス制御とラベル**：アクセス制御で、誰が何を見られるかを決めます。さらに、ドキュメントに付けるのと同じ**データ保護用の秘密度ラベル**（Purview の sensitivity labels）を、プレイブックにも付けられます。名前は今朝変わったばかりで、Purview sensitivity labels と呼ぶことにする、と話しています。

**ロール**：各階層には 2 つのロールがあります。

| ロール | できること |
| ---- | ---- |
| curator | その階層の内容を変更できる。階層の下位の curator は、上位に権限がない限り、上位の内容は変更できない |
| member | その階層と、同じ経路の上位階層のコンテキストを受け取る。変更はできない |

### 5.7 Microsoft IQ の他の要素

- 4 つの IQ（Work IQ、Fabric IQ、Foundry IQ、Web IQ）のコンテキストに加え、**サードパーティのプラグイン**も取り込める。**今日発表された 350 以上**のプラグインで、さまざまな場所のコンテキストを取り込める。コンテキストを取り込むだけでなく、アクション（変更の実行）も行える。大きな名前の 1 つとして Salesforce が挙がっている。
- **OneLake** の力も組み込まれている。オンプレミスからクラウドへ、クラウドをまたいで、データを統合できる。Fabric IQ の共有により、他のパートナーのコンテキストやデータを、テナントをまたいで取り込める。
- 利用側は、Copilot と Microsoft 内のすべてのエージェントに加え、他社のエージェント（Dipti 氏が「others」と呼ぶもの）でも、同じコンテキストを使える。
- Dipti 氏は、IP とコンテキストは「オープンで、持ち運べる」ものであるべきだと述べています。選んだエージェントにどこでも持っていけ、パートナーとも、ガバナンスの管理下で共有できるという考えです。

### 5.8 パートナーの声：Celonis と Process IQ（Marc Kinast 氏）

Dipti 氏は、パートナーの専門知識もコンテキストの整理に重要で、「IQ Economy」の中でパートナーが大事な役割を担う、と説明して Marc 氏を紹介しています。

Marc 氏は、Celonis の使命を「人、企業、地球のために、プロセスを機能させること」と説明し、Microsoft の **Global ISV Partner of the Year** だと紹介しています。

**Celonis context model**：Celonis プラットフォームの中核で、「ビジネスが実際にどう動いているか」の表現です。プロセス、タスク、暗黙知を捉えます。その上で次のインテリジェンスを実行できます。

- ハインドサイト（何が起きたか）
- インサイト（なぜ起きたか、なぜ詰まるか）
- フォーサイト（次に何が起きるか、プロセスを変えたらどうなるか、というシミュレーション）

この基盤を使って、運用を改善するためにプロセスをどう変えるべきかを理解し、将来のプロセスを動かすエージェントにコンテキストとして公開できます。**Process IQ** は、Microsoft と数か月かけて取り組んできたもので、今日ここで提供を開始します。Celonis context model を、Fabric 上でネイティブに動かし、提供するものです。

**動画の内容**（動画のナレーションで語られた範囲）：order to cash（受注から入金まで）を、3 ステップで作り直す例です。

1. **context model を Fabric 内で構築する**：グローバルプロセスオーナーの Jordan が、より良い納期遵守とキャッシュフローを目標に、Fabric のワークスペースに Celonis Process IQ（Fabric のネイティブワークロード）を追加する。Process IQ は、Fabric IQ のオントロジーを直接読み、新たに立ち上げたり作り直したりする必要はない。その上に、仕事がどう流れ、どこで・なぜ詰まり、次に何が起きそうか、を表す context model を構築する。
2. **新しい運用モデルを設計し、公開する**：Jordan が Process IQ に、何がプロセスの足かせになっているか、エージェントがどこで役立つかを尋ねる。Process IQ は、優先順位付きの 6 つのエージェント活用の機会（最初が credit block triage）を見つけ、それを中心にプロセスを再設計する。確定する前に、新しいプロセスをシミュレーションできる。続いて、Process IQ を使って、order to cash の business plugin を Microsoft IQ に公開し、それを実行する Copilot Studio エージェントを作る。プラグインは、新しいプロセスを、エージェントが従う段階的な計画にする。各ステップは Process IQ のコンテキストに基づく。プラグインは Fabric のワークスペースにあり、OneLake で統制される。プロセスが変わったら、各エージェントではなく、1 つのプラグインを更新すればよい。
3. **新しい運用を監督し、学習ループを閉じる**：新しいエージェントが、信用ブロックのために出荷が遅れそうな注文にフラグを立てる。Jordan の business plugin に従い、エージェントは context model を確認し、与信限度額の超過を見つけて、人間にエスカレーションする。エージェントのトレース（実行記録）は context model に戻り、Process IQ がビジネスへの影響を継続的に測定して、プラグインの更新を提案する。

動画は、これを「1 つの Fabric ネイティブな context model、1 つの business plugin、実行のたびに良くなるエージェント」とまとめています。

動画のあと、Marc 氏は、Celonis の「ADO」（analyze、design、operate）というフレームワークを説明しています。まずプロセスを分析して理解し、新しいプロセスを設計し、それをプラグインとして公開し、Microsoft のプラットフォーム上で運用する、という流れです。これらは、Microsoft IQ のお客様にすでに利用可能になっていて、すでに複数の顧客が導入や展開を進めている、と話しています。Dipti 氏は、business plugins との深い統合が次に来る、と補足しています。

> 補足：Marc 氏の説明の途中に、ADO の分析の部分で "Apollo" という語が出てきますが、文意が確定できないため、ここでは触れていません（音声認識の都合で表記が確定できません）。

## 6. デモ・手順

このセッションには、Josh 氏によるライブデモがあります（"first live demo since the pandemic"、"let's try the fun part" など）。録音は音声のみのため、画面の細部は確認できません。以下は、語られた順です。

### 6.1 Microsoft IQ の画面（IQ.microsoft.com）

1. 新しい Microsoft IQ の画面（サービス公開後は IQ.microsoft.com で表示される）を開く。最初の business plugin は、作りたいことをプロンプトで入力して作れる。Work IQ、Fabric IQ など Microsoft IQ の全体から関連するコンテキストを探し、business plugin 全体を組み立てる。内容が正しいかを判断し、調整できる。
2. テンプレートを選び、質問票に答えて作ることもできる。ただし Josh 氏は、ほとんどの人は作るのではなく、すでに作られたものを使うだろうと見ている。

## 8. 利用者にとっての利点

| 利点 | 発表での説明 |
| ---- | ---- |

## 9. まとめ

組織のコンテキストは、自社の IP です。しかし、スキルや MCP エンドポイントを個別に渡すだけでは、結果が一貫せず、トークンも使い、ガバナンスも弱くなります。

Microsoft IQ の business plugins は、専門家が Work IQ、Fabric IQ、Foundry IQ、Web IQ、サードパーティのコンテキストをまとめ、権威ある「プレイブック」として公開します。受け入れ（accept）か管理者による certification で、エージェントに自動的に届き、階層に沿って継承されます。Copilot、GitHub Copilot、他社のエージェントでも、同じ答えが得られます。

Celonis の Process IQ は、Fabric 上のネイティブなワークロードとして提供され、プロセスを business plugin として公開し、エージェントの実行から学習するループをつなぎます。

Dipti 氏は最後に、Microsoft IQ を、キュレーション、certification、接続を行い、共有する「フェデレーテッドな運用モデル」だと総括しています。プラグインは一度作れば、どこでも使え、コスト面でも、再利用性、ガバナンス、データの鮮度の面でも良い状態になる、という説明です。そして iq.microsoft.com から始めることを勧めています。
