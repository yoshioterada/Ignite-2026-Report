# BRK356 Microsoft IQ roadmap: The operating system for enterprise AI agents

## 1. はじめに

AI エージェントを作ること自体は、もう難しくありません。難しいのは、それを企業の中で、チームのために、規模を持って動かし続けることです。このセッションは、Microsoft IQ チームのロードマップを紹介するもので、「Microsoft IQ をエンタープライズ AI エージェントのオペレーティングシステムにする」という方向性を、Maya というユーザーのシナリオに沿って説明しています。

発表は、ビジネス上の課題を 1 文伝えるところから出発し、次の 5 つのステップで構成されています。

1. コンテキストの収集
2. 構築とデプロイ
3. 実行と運用
4. 進化と最適化
5. ガバナンス

終盤には、Copilot 上でこの流れを見せるデモがあります。

## 5. 発表内容の詳細

### 5.1 ステップ 1：コンテキストを集める

AI モデルは一般的な知識で学習されていますが、自社のビジネス、プロセス、ステークホルダー、チームとのやり取りの仕方、箇条書きと表のどちらが好みか、といったことは知りません。これはビジネス用のエージェントだけでなく、何を作るべきかを知る必要があるコーディングエージェントにも当てはまります。

また、コンテキストを与えても、エージェントが見られるのは全体の一部だけです。顧客からは、エージェントが「正しいコンテキストは持っているが、正確なものではない」という声があるそうです。例えば、正しいナレッジ記事は見つけたものの、それと矛盾する内容のメールが届いていたことを見落とす、といった事例です。

**Microsoft IQ の context plugins**（キーノートでも紹介されたもの）は次のとおりです。

| 名称 | 発表での説明 |
| ---- | ---- |
| Work IQ | 従業員がどう働いているか（メール、チャットなど） |
| Fabric IQ | ビジネスがどう動いているか（セマンティックモデル、オントロジー） |
| Foundry IQ | 組織の知識（ナレッジベース） |
| Web IQ | 社外の情報 |
| business plugins | 上記を、ガバナンスの効いた形で、オーサリングしてまとめるもの。エージェントが何を知っているかを自分でコントロールできる |

business plugins は Copilot だけでなく、Claude、Gemini、ChatGPT にも接続できる、と説明しています。

**ビジネス目標（business goals）を知る**

追加しようとしていることとして、ビジネスのコンテキストだけでなく、企業のビジネス目標を理解することが挙げられました。コーディングエージェントが Microsoft IQ のソリューションを作り始めるときに、ビジネスコンテキストに加えてビジネス目標も含む設計図（blueprint）を作ります。これは、後の最適化で重要になるとしています。

**個人の知識を組織の知識につなぐ：エンティティ中心の考え方**

Work IQ、Fabric IQ、Foundry IQ、Web IQ がそろっても、個人から見れば全体像は見えません。例として、営業チームが挙げられました。

- アカウントエグゼクティブ（AE）は、更新が 60 日後に迫っていることと、予算が凍結されていることを知っている
- しかし、プロダクトマネージャーが顧客と話し、顧客が新機能を待っていることは知らない
- ソリューションアーキテクトが顧客と話し、レガシー ERP との統合に問題があることも知らない
- サポートエンジニアが、重大度 1 の障害で顧客とやり取りしていることも知らない

これらは、会議、メール、特定の個人だけが見られる情報にあるためです。そこで、データ全体から考えるのではなく、**ビジネスエンティティ（例：顧客名）から考える**というアプローチを提案しています。承認されたエンティティの周りに、顧客が送ったフィードバックのメール、回答したアンケート、サポートチームとの会議といった情報を前もって集め、組織の知識グラフ（knowledge graph）を作ります。エンティティは顧客のほか、ベンダー、製品など、組織が定義するものなら何でも構いません。

AE が「火曜日に Contoso と会う。何を知っておくべきか」と尋ねたとき、今の仕組みでは自分が持つ一部の情報しか使えず、製品チームが約束した修正を待っている顧客に、拡張の提案を持っていってしまうかもしれません。エンティティの視点から、Foundry や Fabric にある情報と、そのエンティティに関わった人々からの**事実（facts）**を融合すると、「意思決定に使えるビジネスコンテキスト」になります。同じ質問をしても、プロダクトマネージャーからの事実（新機能を待っている）、ソリューションエンジニアからの事実（レガシー ERP を使っている）、サポートマネージャーからの事実（重大度 1）が集まった答えになる、と説明しています。

### 5.2 ステップ 2：構築とデプロイ

登壇者は、顧客から「午後にエージェントは作れるが、本番に出す、チームに使わせる、IT に認定してもらうとなると、6 か月のプロジェクトになる」とよく聞くと述べています。顧客がよく見せる参照アーキテクチャは、箱（製品）が多くて「疲れる」ものです。箱になる製品は存在していても、それらをつなぐ「接着剤（glue）」が難しい、という問題意識です。

- ベストプラクティスや、自分のソリューションに適したアーキテクチャが分からない
- チームごとに問題が違い、すべてのチームがゼロから始め、エージェントごとに新しい問題になる
- 顧客は配管（plumbing）や、エージェントごとの組み立てに関わりたくなく、ビジネスの問題と成果に集中したい

**エージェントとアプリは対で考える**

市場の変化として、「エージェント」だけでなく「エージェントとアプリ」になっている、と指摘しています。すべてのエージェントには UX が必要で、すべてのアプリにはエージェントが必要です。アプリがソリューションの顔（front door）になり、エージェントがロジックを担うバックエンドになる。さらに、動いているエージェントを監督するためのインターフェースも必要で、それもアプリになります。アプリ担当とエージェント担当が別チームという時代は終わり、UX とエージェントを併せ持つハイブリッドなソリューションが必要だという主張です。

**エージェントは「ファイル」である**

登壇者の考え方は、エージェントは単なるチャットではなく**資産（asset）**であり、指示、スキル、ポリシー、評価（evals）の集まりだ、というものです。これをファイルにまとめると、次のことができます。

- IQ・IP を、ファイルとして持ち運べる。どのハーネス、どのモデルにも移植できる
- バージョン管理ができる
- リポジトリに保存できる
- エージェントが他のエージェントを作ることもできる
- 任意のモデル、任意のハーネスを使え、組織全体で、オープンで持ち運びできる状態を保つ

ソリューション全体は、アプリかエージェントかではなく**目的**から見ます。ビジネスコンテキストとビジネス目標に加えて、どのエージェントがあるか、コンテキスト、アプリ、承認、環境を、ファイルに集約します。ファイルになっていれば、CI/CD、ホスティング、デプロイ計画、必要に応じたスケールが考えやすくなります。例えば、最初はごく少ないコンピュートで始め、利用者が増え、自律性やツールが増えたら多くのコンピュートが必要になりますが、そのたびに作り直さない、という考えです。狙いは、**パイロットから本番へ、安全に自信を持って移行できる**ことです。

**Microsoft IQ が裏で用意するもの**

コーディングエージェントが Microsoft IQ にビジネスコンテキストとビジネス目標を渡すと、最終的にアプリとエージェント群ができます。その裏で Microsoft IQ は、次のものをデプロイしたりつないだりできる、と説明しています。

- データベース、ストレージ
- さまざまなシステムへの接続、AI 関数、認証
- モデル（複数可。画像生成用、単純な回答用の小さなモデル、判断用のモデルなど）
- 企業内で問題を起こさないようにするためのサンドボックス
- ツール、セキュリティを確保するネットワーク構成
- そして、最も重要なものとして**アイデンティティ**

登壇者は、これを「すべてのエンタープライズのソリューションにはオペレーティングシステムが必要で、Windows がアプリケーションに提供しているものと同様に、Microsoft IQ がアプリとエージェントのオペレーティングシステムになる」とまとめています。信頼性とコントロールを得て、責任を持ってスケールできる。裏に Azure があるので、世界中にデプロイでき、リージョンを問わず、マルチリージョン対応も確保できると述べています。

想定する例は、顧客と話すカスタマーサポートのエージェント、社内の IT サービス管理、福利厚生を扱う HR、届く請求書を素早く処理したい財務などです。

### 5.3 ステップ 3：実行と運用

> 補足：トランスクリプトでは、このステップに独立した区切りは置かれておらず、デプロイの説明（Maya の例）に続けて語られています。

Maya は、エグレスやネットワーク、Azure リソースの容量、Fabric データベースの設定などを指定したいわけではありません。そこで、Maya が与えたビジネス目的をもとに、Azure と企業向けアプリ構築の専門知識を使って最適化されたソリューションを作り、**組織全体のポリシー**を適用する、と説明しています。

- アイデンティティを持ち、会社のポリシー（これもコンテキストの一部）の範囲内でアクセスできる
- テスト済みのソリューションになる。評価（evals）は難しく、多くの場合データサイエンティストにならないと何を改善すべきか分からない。ビジネスのデータ、コンテキスト、目的にアクセスできるので、Maya のために評価を作り、必要な品質を満たしているかを確認できる
- ソースと実行環境を管理可能な状態に保つ

Maya はビルダーになりたくないが、会社の誰かがプロの開発者として彼女のソリューションを管理してもよい、と登壇者は述べています。すべてがファイル（資産）としてリポジトリにあれば、適切な権限があれば誰でもアクセスできるため、IT のエンジニアがコードを変更することも可能です。顧客からは、エージェントを作ってツールを足したり自律性を持たせたりしようとして IT に相談すると、「全部間違っている、要件を最初から教えてくれ」と言われて作り直しになる、という話をよく聞くそうです。これを解決し、ソリューションが「卒業（graduate）」できるようにしたいと述べています。

### 5.4 ステップ 4：進化と最適化（IQ loop）

登壇者が「一番好き」と言う、多くのアプリやエージェントが失敗しやすい部分です。初日や 1 週間目は素晴らしくても、その後に次のようなことが起きます。

- 上流のデータベースでスキーマが変わり、列名が変わったことを知らないアプリが動かなくなる
- 会社の KPI が変わり、ダッシュボードが意味をなさなくなり、誰も使わなくなる
- アプリがよくできていても、皆が気に入る機能が 1 つ足りない

80% には素早く到達できても、残りの 20% が難しい、というのが登壇者の見方です。そこで、コーディングエージェントでソリューションを作り終えた後も、**コーディングエージェントがアプリに残り続ける**ようにする取り組みを、**IQ loop** と呼んでいます。構築と本番は別々ではなくループの一部で、本番に出したら、ビジネスデータ（KPI の変化、傾向の逆転など）やユーザーの使い方からフィードバックを得て改善します。

**signals layer**

ソリューションごとに、環境を知覚する signals layer が必要だとしています。見るべきものとして、システムのログ（問題が起きていないか）、利用状況（増えたか減ったか、どう使われているか）、ビジネスで何が起きているか、そして登壇者が最も気に入っている点として、**「先週は触ろうとしなかった、あるいは触るべきでない情報に触ろうとしていないか」**が挙げられました。

**3 つのループ**

| ループ | 目的 |
| ---- | ---- |
| engineering loop | システムが健全であり続けるようにする |
| business loop | Maya が最初のプロンプトで伝えたビジネス目標が、継続的に改善され、忘れられないようにする |
| governance loop | セキュリティを統制下に置き、起きたことにシステムが適応できるようにする |

最適化の単位は、個別のエージェントやアプリではなく、**問題を解決するソリューション全体**です。システムは、適切なシグナルを取り、品質を評価し、場合によっては A/B テストも行い、改善を提案します。ただし、**リリース前には必ず承認を取る**としています。アイデンティティとオーナーも必要で、コーディングエージェントはソリューションと一緒に来ても、単独ではなく「マネージャー」とともに動く、という位置づけです。

**エージェントの連続体（continuum）**

最初から自律型のエージェントで始めることはなく、次の段階で進むと説明しています。

| 段階 | 内容 |
| ---- | ---- |
| assistant | 質問して推奨を得るなど、小さく始め、動いているかを確認し続けられるもの |
| team helper | チームのために特定の役割で動くが、チームの監督下にある |
| workflow agent | エンドツーエンドのプロセスを自動化する |
| autonomous agent | 成果を渡せば、解決策を自ら進める |

この連続体は、エージェントの進化だけでなく、**誰が次の段階へ移す権限を持つか**でもあります。ビジネスユーザーは assistant や team helper を作れても、workflow agent にはセキュリティの承認が要るかもしれません。autonomous agent なら、財務や IT の承認が必要になります。Microsoft IQ のソリューションは、組織内のソフトウェアの「ファクトリー」になることを目指しており、assistant から autonomous agent に移るときも、作り直さず、同じ IQ ソリューションが進化していく、と説明しています。

### 5.5 ステップ 5：ガバナンス

自律性には明確な境界が必要です。登壇者は次の点を挙げています。

- **アイデンティティと責任あるオーナー**：すべてのエージェントが自分のアイデンティティと、アカウンタブルなオーナー（マネージャー）を持つ。管理者のいない従業員がいないのと同じ
- **すべてのステップを追跡できること**：A365 と Azure Monitor に接続し、エージェントが何をし、どんな活動と意思決定をしたかを把握できるようにする
- **実行の分離**：先に示したサンドボックス。コーディング能力を持つエージェントは強力なので、コーディングは分離された環境で行い、エージェントが害をなすツールを自分で作ることを防ぐ
- **証明されたビジネス価値**：信頼のないインテリジェンスは、デモとしては素晴らしくても IT、CISO、財務の承認は得られない。ビジネス目標から始め、ソリューションのあらゆる時点でコスト対便益を問う。一貫性のない結果、安全でない判断や行動にはアラートを出す
- **継続的な評価**：評価セットはビルド時だけでなく継続的に動かし、ビジネスとともに改善される必要がある。半年前の無関係なものをテストしてしまうと品質に影響する
- **統合**：サードパーティのシステムとのやり取りの考え方
- **安全性の制御、データ保護、人による監督**
- **監査とコンプライアンス**、さらにエージェントの群れ（fleet）が増えた際の fleet governance

**AI から人への human in the loop**

登壇者が取り組んでいることとして、エージェントが承認を求めるときの仕組みが挙げられました。例えば、5 万ドルを超える請求書は財務の人の承認が必要です。エージェントは誰に聞けばよいか分からず、指示に書いても、その人が 1 か月前に退職しているかもしれません。そのたびに指示を更新するのではなく、Microsoft IQ で作ったエージェントが人に連絡するとき、**その人が誰か、休暇中か、代わりに頼める人は誰か**を理解できる仕組みを作ろうとしている、と説明しています。エージェントを、横で保守し続けるものではなく、私たちと協働する存在として見る考え方です。

要約として、エージェントには仕事の委任という形で自律性を与えつつ、人が統制を保ち、必要な部門は何が起きているかを見られ、ビジネスは結果が改善されていることを見られるようにする、と述べています。

### 5.6 Copilot でのデモ（Maya の例）

登壇者は、Maya が Copilot でソリューションを作る様子を見せました。（音声のみのため、画面の細部は確認できません。語られた内容を順に書きます。）

1. Maya が Copilot に、不意打ちを受けていること、2 週間前の通知が欲しいこと、不意打ちのエスカレーションの減少・更新の改善・NPS の向上が重要であることをテキストで入力する
2. Microsoft IQ がまず**ビジネスコンテキスト**を取得する。business plugins を使い、Maya のチームがどう動いているか、ステークホルダーは誰か、大口顧客をどう定義するか、ARR とは何か、などを見つける。質問が出ることがあり、Maya が答えるとコンテキストが更新される
3. 次に**ポリシー**を探し、このエンタープライズのコンテキストで Maya に許されること・許されないことを把握する。その結果、会社は Maya に、**読み取り専用で、ユーザーに委任された**エージェントしか作成を許していないと判明する（自律型エージェントは作れない）。ソリューション全体がこの権限に基づいて作られる
4. Maya は、何を作るかの**アウトカムプラン**を受け取る。求めるビジネス成果が含まれている。Maya が「読み取りアクセスで構わない、構築を開始して」と伝える
5. 「配管なし」で構築が進む。Foundry エージェントの作り方や Azure のリソースの作成を Microsoft IQ が理解している。エージェントは**ファイル**になっており、必要なポリシーを持つ
6. Maya は作成されたアプリと、エスカレーション・ウォッチリストを確認できる。気に入らない点があれば、チャットに戻って指示できる。デモでは、「product health のフォローアップは見たくない」と伝えると、該当のエスカレーションが一覧から消えた。エスカレーションのオーナー向けのメールのドラフトも得られる
7. メトリクスも確認できる。さらに重要な点として、**評価セット**が作られている。Maya がデータサイエンティストになる必要はなく、ビジネス情報にアクセスできるため、**18 か月分の履歴**に基づいて評価が返ってくる。システムは「ソリューションは良好。品質管理のヒルクライミングは済んだ」と伝え、最適化のためにコーディングエージェントがソリューションに追加されたことも伝えた
8. Maya はチームに共有できるリンクを得る。会社側は、ポリシーに合致し、ガバナンスもできる、フルに構築された状態のものを得る。「6 か月のプロジェクトにはならない」

**60 日後**

コーディングエージェントを Maya のアプリにつなげた状態で、60 日後の様子が示されました。シグナルが取得され、評価が行われ、推奨が作られています。エスカレーションに関するメトリクスは大きく良くなり、Maya は **12 日前に** 警告を受け取れるようになっています。メトリクスの改善は、最初の構築だけでなく、システム内の最適化ループによるものだ、と説明しています。紹介された改善は 3 つです。

1. **スキーマ変更への対応（engineering loop）**：システムがログからスキーマに何か起きたことを検知し、アプリ内のデータの変更を提案した。IT が承認し、アプリは動き続けた。誰もトラブルシュートする必要がなく、誰かが壊れていると気付くまで待つ必要もなかった
2. **新しいタブの提案**：チャットで皆が顧客のケースについて繰り返し尋ねていることを見つけ、新しい「customer cases」タブを提案した。人が自分から聞かなくても情報を届けられる
3. **フィルターの追加**：皆が高リスクのものを見ていて、中リスクと低リスクは誰も気にしていないことに気付き、ワンクリックで高リスクの項目を見られるフィルターを提案した。**Maya が承認する**と、アプリの中のコーディングエージェントが実装、テスト、デプロイを行い、新しいフィルターがアプリに追加された

### 5.7 まとめの 4 点と Q&A

登壇者は、Microsoft IQ で取り組んでいることを次のようにまとめています。

1. コンテキストを継続的に良くする。人の受信箱、会議、頭の中にある情報をビジネスコンテキストに取り込み、すべてのエージェントと従業員が情報を持てるようにする
2. 最小限の配線でエージェントを作れるようにする。クラウドエンジニアや IT エンジニアにならなくても、必要なソリューションを得られる
3. アプリとエージェントのデプロイ、ガバナンス、改善を進め、ループを継続的に進化させ、3 か月後に忘れられる静的なものにしない
4. 最も重要なのはビジネスの成果

最後に、時間が約 4 分残っているので質問を受け付けると呼びかけましたが、トランスクリプトには質問は記録されておらず、Q&A はありませんでした。

## 7. 注意点・発表者の気付き

- 顧客から「午後にエージェントを作れても、本番化、チーム利用、IT の認定は 6 か月のプロジェクトになる」と聞くと述べています。登壇者自身は、会場の挙手に意外感を示しています。
- エージェントが見ているコンテキストは「正しいが正確ではない」ことがあります。例：正しいナレッジ記事はあるが、矛盾するメールを見落とす。
- 80% までは速く到達できても、残りの 20% が難しく、運用開始後（スキーマ変更、KPI 変更、足りない機能）に多くのアプリとエージェントが失敗しやすいとしています。
- 最初から自律型エージェントで始めることはなく、assistant から段階的に進めます。段階を上げる権限（セキュリティ、財務、IT の承認）も段階的です。
- 最適化の提案は、リリース前に承認が必要です。
- 承認者が誰か（退職、休暇）をエージェントが知らない問題があります。指示にハードコードする方式は更新が必要になります。
- 紹介された内容の多くはロードマップ上の取り組みであり、現時点で利用可能かどうかは発表では明示されていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです（デモ内の数値はデモ上の例です）。

- ビジネス上の課題を伝えるだけで、コンテキスト収集、構築、デプロイ、評価セットの作成までを Microsoft IQ が行う。6 か月かかるプロジェクトにならない
- Maya のデモでは、会社のポリシーに基づいて、読み取り専用・委任型のエージェントとして構築された
- 評価セットは、18 か月分の履歴に基づいて自動で作られる
- 60 日後には、Maya は 12 日前にエスカレーションの警告を受け取れる
- 構築後も、スキーマ変更への対応、新しいタブ、フィルターの追加が、承認のもとで自動的に行われる
- IT は、すべてが資産（ファイル）としてリポジトリにあるので、権限があればコードを変更でき、最初からやり直さなくてよい
- 企業側は、アイデンティティ、オーナー、トレース、サンドボックス、評価、監査によって、統制を保てる

## 9. まとめ

このセッションは、エージェントの作成だけでなく、企業内での構築・運用・進化・統制までを担うプラットフォームとして、Microsoft IQ の方向性を示すものでした。ユーザーはビジネスの課題を伝えるだけで、Microsoft IQ がビジネスコンテキストと目標を集め、会社のポリシーに沿ってエージェントとアプリを構築し、評価を作ります。

構築後は、コーディングエージェントがアプリに残り、engineering、business、governance の 3 つのループで継続的に改善案を出し、リリースは人の承認を経て行われます。エージェントはファイルとして持ち運べ、assistant から autonomous agent まで同じソリューションとして進化します。

発表の根底にあるのは、**ビルダーになることではなく、ビジネスの成果を中心に置く**という考え方です。
