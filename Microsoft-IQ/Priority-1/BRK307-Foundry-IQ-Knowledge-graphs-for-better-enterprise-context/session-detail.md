# BRK307 Foundry IQ: Knowledge graphs for better enterprise context

## 1. はじめに

このセッションは、Foundry IQ に新しく加わる「ナレッジグラフ（knowledge graph）」機能を、2 人の Product Manager が紹介したものです。エージェントは取得できた情報の範囲でしか推論できません。従来の RAG は「この事実はどこに書いてあるか」という質問には強い一方で、コーパス全体にまたがるテーマや、関係性、件数の集計といった質問には苦手です。そこで Foundry IQ は、文書をエンティティと関係のグラフにする **Entity graph** と、内容をトピックにまとめる **Topic graph** を用意しました。

このセッションでは次のことが分かります。

- どんな質問で従来の検索が苦戦するのか
- Entity graph と Topic graph がそれぞれ何をするのか
- 仕組み（オントロジー、グラフ構築、トピック検出）
- 3 つのデモ（動画 1 本、Python ノートブック、プラグインの Playground）
- 導入時に気をつけたい点（プライベートプレビューで得た教訓）

## 5. 発表内容の詳細

### 5.1 背景：質問が難しくなっている

Louis は、この 1 年でエージェントが多くの本番システムに入り、ユーザーが入力する質問そのものが難しくなってきたと説明しています。難しくなっているのは人にとってだけでなく、エージェントや検索システムにとっても同じです。顧客や開発者と作業する中で、次の 3 つのパターンが見えてきたそうです。

| パターン | 内容 | 例として挙げられたもの |
| ---- | ---- | ---- |
| 構造・関係の中に答えがある | 答えが 1 つの文章（passage）には無い | 「先四半期のインシデントに関連するサプライヤーはどれか」 |
| テーマ | エージェントに「質問」ではなく「ゴール」を与え、大量のデータを分析させる。針を探すのではなく、パターンやテーマを探す | 具体的な質問例は挙げられず、「広さ（breadth）が必要」と説明された |
| 非構造化文書をデータベースのように問い合わせる | 裏にデータベースは無いのに、集計や順位付けを求める | 「この製造分野のトップサプライヤーを出して」「過去のインシデントが何件あったか数えて」 |

Louis は 3 つ目が自分のお気に入りだと話し、これは実際のビジネスの質問であり、類似度ベースの検索が苦戦するところだと述べています。

具体例として、次の質問が挙げられました。「Microsoft の決算で、経営陣は AI 投資についてどんな主張をし、それを裏づける証拠は何か」。これは RAG を失敗させるために作った質問ではなく、アナリストや戦略チームが普通に聞く質問です。色分けして解説したところでは、次の分解になります。

- 「case（主張）」：多数の決算説明会と、その下にある製品・サービスを横断して見る必要がある
- 「management（経営陣）」：登壇者、例えば決算説明会で発言した Satya のような人物を指す
- 「evidence（証拠）」：RAG で慣れた chunk（元のテキスト）に戻って裏づける

### 5.2 ナレッジグラフ機能の位置づけ

今週発表した機能が、Foundry IQ の knowledge base 体験に統合された 1 つの機能「knowledge graph」です。2 つの視点（lens）があります。

- **topics（トピック）**：テーマや、データ全体に対するグローバルな質問、見つけたいパターンのためのもの
- **entities（エンティティ）**：型付きでつながったレコード。データ全体に散らばっていても、非常に正確な答えを得るためのもの

データ基盤や検索システムを運用する人向けの大事な点として、**別のグラフデータベースを立てて、保護し、運用する必要はありません。** 既存の Foundry IQ と同じエンジンで動き、フィーチャーフラグで有効にして、既存のパイプラインを通すという説明です。

歴史的な流れとしては、次のように整理されました。最初はキーワード検索（正確な語を探す）、ここ数年はエンベディングが安価になりエンベディング検索、その中間にハイブリッド検索、さらに多様性や明示的な関係へ進みます。左から右へ進むほど精度が上がり、難しい質問に答えられる一方で、構築のコストも上がります。開発者は、ユースケースや扱う文書の種類に応じてこのトレードオフを選べます。

ベクトルとレキシカルのインデックスはなくなりません。そこへエンティティとトピックを足し、エンジン全体として答えられる質問の種類を増やす、という位置づけです。

「良い答え」の例としては、決算の質問に対して、次の要素を含むことが示されました。

- 主張を、GitHub Copilot など別の製品・サービスにも広げて答える
- 決算説明会でアナリストがどんな質問をし、どの役員が答えたかというエンティティを押さえる
- 従来どおりの snippet（chunk）で、答えや数字を元データに結びつける

### 5.3 Entity graph（Louis）

#### 5.3.1 Entity graph とは

Entity graph は、人、場所、契約、インシデントなどのエンティティと、その関係をつなげたネットワークです。重要な性質は 2 つ説明されました。

1. エンティティは、型付きで一意の ID を持つ。人物の「Ben」（音声認識の表記は「BIN」で、後半の発話から「Ben」と読んでいます）が数百の文書に出てきても、同じ ID（例として 1, 2, 3 と説明）で特定でき、エージェントは常に「その Ben」だと分かる。
2. Entity graph は図書館システムのようなもの。書棚の前に行ってたまたま正しいページが開くのを期待するのではなく、精密な検索（lookup）ができる。「いくつあるか」「これらをすべて見せて」といった質問は、データを結びつけて見渡せるグラフがあることで可能になる。

#### 5.3.2 オントロジー

何をエンティティとして取り出し、どんな関係が重要かを定義するのが **オントロジー（ontology）** です。非構造化データの上に置く意味の層で、「ビジネスの語彙を、機械やエージェントが読んで推論できるように書き出したもの」と説明されています。セッションでは決算説明会の例（組織、人、カンファレンスコールとその関係）を使っていました。

オントロジーを Foundry IQ に渡す方法は 3 つあります。

1. Fabric IQ の顧客なら、オントロジーをエクスポートして Foundry IQ に再アップロードする。
2. 自分のオントロジーファイルを使う。サードパーティのツールや、Copilot や Claude Code（トランスクリプトでは「cloud code」。文脈から判断）に書かせてもよい。
3. プラグインに組み込まれた既製のオントロジーを使う。例えば消費財の会社で、製品と顧客のような一般的なエンティティから素早く始められる。

#### 5.3.3 グラフ構築の難しさと、Foundry IQ が引き受けること

紙の上では手順は 6 つです。文書を用意し、理解し、エンティティを抽出し、関係を抽出し、正規化する、といった流れです（6 つすべての名称は発話では読み上げられていません）。概念的には簡単ですが、難しさは「堅牢に作ること」にあると、5 点が挙げられました。

| 課題 | 説明 |
| ---- | ---- |
| データのクレンジング | 企業のデータは雑然としており、集約して役に立つ形にするには掃除が必要 |
| 品質 | 6 つの各手順でモデルが誤りを持ち込む。誤りが積み重ならないようにする必要がある |
| コンプライアンス | 元データの権限が、作られるグラフにも引き継がれる必要がある |
| スケール | 数百ではなく数百万の文書を扱う |
| 増分更新 | 文書の変更や差し替えがあるとき、全体を作り直さずにグラフを更新できるか。Louis が最もよく聞かれる質問の 1 つ |

Louis は、プロトタイプや PoC が失敗したり古くなったりするのは、まさにこうした箇所だと話し、これらを Foundry IQ にネイティブに組み込んで負担を減らしたと述べています。

流れは次のとおりです。文書を Blob ストレージにアップロードします。コネクタは 26 種類の文書タイプに対応しています。それをフルマネージドでスケールするパイプラインに通すと、Entity graph が自動で作られます。

#### 5.3.4 グラフへの問い合わせ

問い合わせ方は 2 つです。

- **自然言語で聞く**：裏側で NL から GQL への変換が行われ、構造化クエリとして実行し、構造化データを得る。そのコンテキストを LLM に渡して最終回答を作る。
- **開発者向けにグラフクエリを直接書く**：プリミティブが提供されている。

#### 5.3.5 デモ動画 1：Agentic search とナレッジグラフの比較

Louis は、「画面の文字が見えるか分からないので」と断って、動画の質問文を読み上げながら左右比較を再生しました。同一コーパスは Microsoft の決算説明会です。左は agentic search（1 回きりの検索ではなくエージェント的な検索）、右は同じ agentic search にナレッジグラフを組み合わせたものです。

1. 質問：Microsoft の決算説明会で、各アナリストと、その質問に答えたすべての役員を挙げる（最終回答の形式の指定も含む）。
2. 左側は、関係のネットワークを調べる段階にステップを費やし、「かなり頑張って」探すものの、見つかったのは 1 組だけだった。類似するコンテキストを探す agentic search の限界として説明されています。
3. 右側は、質問をオントロジーに基づく構造化クエリに変換して実行し、アナリストと役員の組を得た。1 対多の関係も得られた。
4. 企業では説明可能性が重要になるが、決定的（deterministic）な結果が返るので、より自信を持って元データに結びつけられる。
5. 質問を変えて「いくつか」を数える例を実行した。同じ決算コーパスで、今度は「いくつあるか」を問います。コーパスの中に質問数や役員数を直接書いた箇所は無いため、従来の RAG では完全に失敗する、という説明です。右側では、自然言語の質問をグラフクエリに変換し、結果にカウントが含まれ、答えは **7** だった。

#### 5.3.6 評価と、グラフが効くユースケース

今年の初めに取り組みを始めたとき、チームはグラフの進捗を測るためのベンチマークを探しましたが、市場には見つかりませんでした。既存のクエリセットはナレッジグラフには簡単すぎ、agentic search で解けるものが多かったためです。そこで顧客に聞き取りをして、実際に動いてほしいケースを集め、内部データセットを作りました。

その結果、難しいクエリでは品質が大きく向上しました。マルチホップのクエリでは **最大 64.3% のトークン削減** が見られたそうです。グラフ構築時に企業コーパスの「迷路の地図」を作るので、エージェントがリンクをたどって効率よく答えに到達できます。構築のコストは先に払い、その後の各クエリでは実行時コストを節約できます。

agentic search の上でグラフが大きく効く（leapfrog）ユースケースとして、4 つが挙がりました。

1. **集合の交差（intersection）**：エネルギー系の顧客がプラントのインシデントと原因を調べる。「この条件とこの条件を満たすインシデントをすべて見せて」という網羅的なリストを求める。
2. **一覧・カウント**：製造分野の売上上位 5 社のサプライヤーを聞く、など。
3. **欠けている属性・リンク**：通常の検索は入れたものを取り出すが、今は「無いもの」を聞く。ヘルスケアの例として「初期段階で症状が出ない病気はどれか」。エージェントにすべての文書・可能性を確認させれば（トークンを無制限に使えば）答えは出せるが、企業の現場では効率的でない。
4. **明示的な根拠と説明**：答えをエンティティと構造化クエリまでたどれる。エージェントを決定的に根拠づけられる。

Louis は、業界全体がエージェントへのグラフ導入の初期段階にあり、想像していないユースケースも出てくるだろうと述べています。

### 5.4 Topic graph（Matt）

#### 5.4.1 なぜトピックか

Matt は、Entity graph が「精密な答え」のためのものなら、まったく別の視点が必要な質問もあると続けます。例は「Azure と、見出しになる Copilot の数字以外で、私たちが見落としているものは何か」。これには、コーパスの文書に対する広い理解が必要です。

RAG は、コーパスの 1 つの側面に固執しがちです。BM25 のキーワード検索やベクトル検索は、完全一致に近いものを探すのは得意です。しかし、このような質問では完全一致が欲しいのではなく、コーパスの全体像で検索を豊かにしたいのです。広さと多様性を狙うために導入されたのが **トピック** です。

Matt は、トピックを「コーパスの目次」にたとえています。エージェントに「探して答えを見つけて」とだけ言うと、特定の部分だけ見て諦めがちですが、どこにどの文書があるかを示す目次（地図）があれば、問題を違う角度から見られるという説明です。

#### 5.4.2 トピックの作り方

1. エンティティ抽出と同じ出発点で、文書を chunk に分割する。
2. トピック検出アルゴリズムを実行する。chunk をエンベディングしたベクトルには、単純なベクトル検索を超えた関係があり、関連する chunk をグループ化して、それらを結びつける隠れた意味を見つけ、トピックを形成する。
3. Louis が説明したエンティティ抽出のパイプラインを使ってグラフを構築する。
4. そこで終わらず、トピックに戻って要約する。本の索引のように「この章は何について書かれているか」が分かる形になり、コーパスの事前知識なしに、必要なときに合成できる。

#### 5.4.3 トピックの副次効果：オントロジー作りを助ける

Matt は、トピックのもう 1 つの利点を説明しています。例えば、大きな組織で「HR のデータでナレッジグラフを作って」と頼まれたが、HR のことを何も知らない場合です。まずトピッククラスタリングでトピックグラフを作ると、休暇のルールなど、HR のテーマが分かってきます。コーパスの全体像が見えると、ナレッジグラフ作りで最も難しい部分の 1 つであるオントロジー作りが、以前ほど難しくなくなります。簡単になるとは言っていないと断りつつ、「ずっと楽になる」と述べています。

さらに、学習ループも作れます。まずトピックグラフからオントロジーの案を作り、ユーザーがオントロジーを構築するエージェントにフィードバックします（例：「人事のことが分かってきたので、personnel や managers のエンティティが必要だ」）。エージェントが戻って修正し、満足できるオントロジーになるまでこのループを回します。このため、トピックは **広いテーマの質問に答える** ことと、**エンティティグラフの立ち上げを助ける** ことの二役を担います。

#### 5.4.4 Foundry IQ でのトピックの扱い

Matt は、結果から逆に説明しています。トピックのインデックスには、次を保持します。

- トピックのタイトルと説明、親トピックと子トピックの関係（目次を表すため、グラフクエリ言語（GQL）が必要）
- 重心（centroid）。クラスタリングの結果であるクラスタはベクトルの集まりで、中心がある

実際の埋め込みベクトルは数千次元で理解しづらいため、ここで示す図は 2 次元に単純化したものです。使用したデータセットは、決算説明会の 841 個の passage で、FY14 から FY26 までの 41 回の決算説明会を扱います。

クラスタリングには **Leiden** というアルゴリズムを使い、Microsoft Research の GraphRAG の論文に着想を得ています。実行すると、広いクラスタが小さなクラスタを包む入れ子の構造が得られ、これがトピック（コーパスの目次）の種になります。Foundry IQ で検索に最も関係するのは、広いトピックの下にある **サブトピック** で、passage の出どころになるのもこちらです。サブトピックから重心を計算します。ただし、エージェントにコーパスの「宝の地図」を渡すには、広いトピックも重要です。

#### 5.4.5 デモ 2：Python ノートブックでトピックグラフを歩く

Matt は Python ノートブックを画面に表示し、Foundry IQ の SDK を使ってコードを実行して見せています（準備のセルは省略して先に進んでいます）。語られた流れは次のとおりです。

1. トピックグラフから出発し、「Azure growth and infrastructure」というトピックを取り上げ、サブトピックへ進み、関連する passage を見る、というサイトマップの歩き方を示す。
2. まず、トップレベルのトピックを一覧する。GQL クエリを実行する（Louis のデモで見せたのと同様の、関係を記述する構文）。
3. 次に、親がこのトピックであるものを指定するクエリで、サブトピックへ下りる。
4. 特定のトピックに紐づく passage を取り出す。トピックの重心のベクトルを使う。各 passage は自分のベクトルを持つので、重心を使ってベクトル検索を行い、近いベクトルを取れば passage が見つかる。トピックがコーパスのどのくらいを占めるかの割合も保存されているので、逆向きにたどれる。コードでは「重心でベクトルクエリを実行する」だけ。
5. 続いて、検索結果の分布を可視化する。通常のベクトル検索（最近傍のみ）だと、結果が少数のトピックに集中している。焦点が絞られた質問ならそれでよいが、広いテーマの質問では望ましくない。
6. 2 種類のクエリを比べる。**diverse**（結果を他のトピックにも広げる）と **balanced**（ベクトル類似度と、新しいトピックの多様性の折衷）。
7. 仕組みは単純で、トピックをラウンドロビンしながら拾う。**diversity** というつまみで、いくつのトピックからサンプリングするかを決める。図の左は、コサイン類似度を最適化したが 1 つのトピックに集中する。右は多様性を最適化したので類似度は高くないがより多くのトピックが入る。
8. コードは、トピックグラフを渡し、diversity factor を設定するだけ。オプション名の細部は発話では明確には読み上げられていません。
9. 統計を見ると、最近傍のみでは全結果が 1 つのトピックに集まる。diverse にすると分散するが、ベクトル検索の持つ「似た結果が取れる」強みが薄れる。
10. diversity factor は「検索をトピック間でどこまで広げるか」を表す。既定値は **0.2** で、「ベクトル検索に近い結果を保ったまま、あまり広げない」設定。コーパスの全トピックを網羅したければ高くする。

> 注意：Matt は、**まず balanced から始めること** を勧めています。ベクトル検索は長年の業界標準であり、よくできているので、balanced ならトピックへの分散の利点を取りつつ、ベクトル類似度の高い結果も残せるという理由です。

#### 5.4.6 評価結果

決算説明会だけでなく、複数のデータセットで評価しています。Matt は、ナレッジグラフを「品質のはしご」と表現しました。RAG だけでも多くは正しく答えられ、エンティティを加えるとさらに増え、トピックが残りの差を埋めます。最も印象的なのはトークン効率で、品質が上がる一方でトークン使用量は下がる、と説明しています。エージェントのトークンは検索ではなく本来の問題の解決に使いたい、という考え方です。評価の方法は、スライドのリンク先のブログに詳しく書かれています。

トピックを使う場面は、次のとおりです。

- 全体像やメインテーマを知りたいとき（広い質問）
- 結果の多様性を高めて、広い・自由回答の質問や要約を良くしたいとき
- 見慣れないコーパスを探索するとき。最初に「何がどこにあるか」の地図が見えるとよい、と Matt は話しています。

### 5.6 プライベートプレビューで得た教訓（Louis）

ナレッジグラフを数か月間、さまざまな業界の顧客とプライベートプレビューで試しました。得られた教訓は 4 つです。

1. **何を解きたいかを見極める。** ナレッジグラフは今あるものを完全に置き換えるものではなく、拡張として考える。ユーザーがプロンプトに何を入れるか、どんな質問をするかを考えれば、グラフが効く場面か判断できる。「Ben とは誰か」を聞くだけなら不要な場合もある。
2. **小さなコーパスと、限定したオントロジーから始める。** 事業全体を表すオントロジーを作ろうとすると難しく、事業部間の合意を取るのも大変。
3. **取捨選択する。** グラフにあらゆる答えを入れたくなるが、現在の構築方法は、トリプルを作るために大量の出力トークンを消費する。コストが発生するので、元のコーパスがディスクにあるなら、すべてをグラフに入れる意味は無いことがある。エージェントがグラフを使って「発見」できればよい。
4. **モデルの選択。** 品質を上げるヒルクライムを多く実施した。より知能の高いモデルがあるのは承知しているが、品質とコストのバランスが非常に良いのは「GPT-406 Luna」だと述べ、ナレッジグラフの推奨モデルとしている。

## 7. 注意点・発表者の気付き

- **ナレッジグラフは万能ではない。** 「Ben とは誰か」のような単純な質問では不要なことがある。質問の種類を先に把握する。
- **グラフ構築にはコストがかかる。** 現在の方法では、トリプルを作るために出力トークンを多く消費する。すべてをグラフに入れず、必要なものに絞る。
- **オントロジーは小さく始める。** 事業全体のオントロジーを定義し、事業部間で合意するのは難しい。
- **balanced から始める。** 既定として balanced を選ぶのが Matt の推奨です。ベクトル検索の強みを残しながら、トピックへの分散の利点も得られるためです。
- **オントロジーには調整が必要。** トピックから作った案をフィードバックで磨くループがある、と説明しています。
- **まだ初期段階。** Louis は、業界全体がグラフをエージェントに取り込む初期段階にあると述べています。
- 本番の運用に関する価格、提供開始時期（一般提供のスケジュール）などは、発表では触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 従来の検索が苦手な質問に答えられる：関係をたどる質問、テーマ・パターンの質問、数える・列挙する・順位付けする質問、「無いもの」を探す質問。
- 結果の説明可能性：決定的なクエリ結果が返り、答えをエンティティと構造化クエリまでたどれる。
- トークン効率：マルチホップのクエリで最大 64.3% のトークン削減。構築コストを先に払い、実行時に節約する。
- 運用負担の軽減：別のグラフデータベースは不要。データクレンジング、品質、権限の引き継ぎ、スケール、増分更新を Foundry IQ が引き受ける。
- 導入の容易さ：Foundry IQ プラグインにより、コーディングエージェントにグラフの構築を任せられる。Playground で結果を比較・デバッグできる。
- 未知のコーパスの探索：トピックの地図で、データの全体像を素早く把握できる。

具体的な顧客名は挙がっていません。事例としては、エネルギー系の顧客がプラントのインシデントと原因を調べる、ヘルスケアの用途で症状のない病気を探す、製造分野でサプライヤーを順位づけする、という質問の例が語られた程度です。

## 9. まとめ

Foundry IQ のナレッジグラフは、エンティティを扱う Entity graph と、テーマを扱う Topic graph の 2 つの視点で、従来の RAG が苦手だった質問に答えます。

| 視点 | 向いている質問 |
| ---- | ---- |
| Entity graph | 精密な答え。一覧、カウント、集合の交差、欠けているものの発見、根拠づけと説明 |
| Topic graph | 広いテーマの質問、コーパス全体の把握、エージェントにコーパスの中身を教える、要約 |

別のグラフデータベースは不要で、ベクトル検索やキーワード検索も引き続き使います。導入では、解きたい質問を見極め、小さなコーパスとオントロジーから始め、グラフに入れるものを選び、モデルのコストと品質のバランスも考えるのがよい、というのが発表者の勧めです。
