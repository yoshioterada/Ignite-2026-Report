# BRK295 Web IQ: The new search engine for agents

## 1. はじめに

このセッションは、Microsoft IQ の一部である **Web IQ** を紹介するものです。Web IQ は、エージェントが外の世界（Web やその先にある商品・サービス・天気・場所など）の最新で確かな情報を使えるようにする「エージェントのための検索エンジン」です。発表者はこの仕組み全般を **grounding（グラウンディング）** と呼んでいます。

Web IQ は、AI エージェントを作る開発者や、エージェントを自社の業務に組み込む企業を対象としています。発表では、次のような内容が語られました。

- 良い grounding の 4 つの条件（品質、鮮度、速度、コスト効率）と、各指標での Web IQ の位置づけ
- Azure での一般提供開始と、新しい価格
- Places、Weather（一般提供）と Commerce（プライベートプレビュー）という構造化データ
- 健康分野向けにチューニングされた Web IQ
- 複雑な質問を 1 回の API 呼び出しで扱う **Web IQ Auto** と、その上位の Auto Advance
- Northern Trust、Genspark、Cloudforce の事例

## 3. 何に関する発表か

Roby 氏は、この 20 年ほど、Web は検索、購入、コミュニケーション、仕事など、私たちにとって当たり前のものになったと切り出します。AI が進むにつれて、こうした行動をエージェントが代行する場面が増えており、顧客サポート、経営層向けのブリーフィング、リサーチ、サプライチェーンの運用までを、1 分間に数千単位の意思決定として行っているといいます。そこで、エージェントは Web や外の世界とどう関わるべきか、という問いが生まれます。その答えが Web IQ だという位置づけです。

### Microsoft IQ の中での位置づけ

スライドでは、Microsoft IQ の左側に **Work、Fabric、Foundry** があります。これらはエージェントを「組織の内側」（人、データ、ナレッジ）につなぐものです。残りの半分が **Web IQ** で、エージェントを「組織の外側」で起きていることにつなぐものと説明されました。

### grounding が必要な理由（機内モードのたとえ）

Roby 氏は、grounding を説明するために、まず grounding が無い状態を機内モードにたとえました。飛行機のドアが閉まって Wi-Fi がまだつながっていない間は、スマートフォンやノート PC、手元の文書は使えても、外の世界とやり取りできません。grounding のない AI も同じ「機内モード」で動いており、難しい質問に推測で答えるしかなく、**推測が事実のように提示される**という結果になります。

したがって、エージェントを作る場面での grounding は、もはやオプションではなく、**エージェントシステムの基礎的な要素**であり、「もっともらしい答え」と「正しい答え」の違いを生むと説明されています。

grounding が答える問いの例としては、競合が新製品を出したか、価格を変えたか、株式市場の状況、新しい規制への対応、人事サポートの新しいベストプラクティスなどが挙げられました。

中心にあるのは、**エージェントを作る人は、検索を「人間が入力して読むもの」ではなく、「エージェントが使うもの」として作り直す必要がある**という主張です。発表者は、人間が検索ボックスに入力するという前提から、エージェントがどう検索すべきかへと、スタック全体にわたる何百もの前提を洗い出して書き直したと説明しています。

### 5.1 Microsoft を選ぶ 3 つの理由

Web IQ を紹介する動画のあと、Roby 氏は、なぜ Microsoft が grounding を手がけるのかを 3 つの理由で説明しました。

| 理由 | 説明 |
| --- | --- |
| スケール | Web は、エージェントにとっても非常に大規模な事業。Bing は 10 億人を超えるユーザーを抱え、Web IQ は同じインフラ投資、専門知識、教訓の上に作られている |
| エンタープライズ | Microsoft は、物事を企業の業務で使える形にすることが得意。詳細は後半で説明 |
| AI ネイティブ | 人間が検索ボックスに入力する発想から、エージェントがどう使うかという発想へ、プロダクトを最初から作り直した |

最初の顧客は **Frontier Labs**（大手 AI のフロントドア）でした。最先端の性能が求められるサービスから始めたかったためで、今週はその性能を、参加者が作るエンタープライズのエージェントに提供していくと説明しています。

### 5.2 Northern Trust の事例（Kelvin Xie 氏）

Northern Trust は、超富裕層向けのウェルスマネジメントを専門としています。顧客のライフイベントに基づくエンゲージメントが重要で、適切なタイミングでリード（見込み客）にリーチするために、リードリサーチが欠かせないという前提です。従来は熟練したチームが手作業で行っており、規模に限界がありました。

**課題**：リードが足りないのではなく、リードをリサーチする **キャパシティが足りない** ことでした。その原因の 1 つが検索の仕組みです。クエリを 1 つずつ入力し、結果を分析してから次の検索を決める流れは逐次的で、人間の処理能力と注意力が上限になります。あるリードを理解するには、研究者は届出書類、市場データ、CRM などの社内システム、さらにオープンなインターネットから情報を集め、1 つのリードプロファイルにまとめ、重複を除き、欠けている部分をインターネットで補います。この各ステップが逐次的で、研究者は「量を優先するか、深さを優先するか」のトレードオフに直面します。量を優先すると不整合や欠落が起き、深さを優先すると、終わった時点で情報が古くなっている可能性があります。

**新しい仕組み**：

1. Web IQ で外部の情報（届出書類、プレスリリース、ニュース記事）を取得する
2. 社内データ（CRM 情報、wealth intelligence、パートナーのデータセット）と組み合わせる
3. 間にある **リサーチエージェント** が、複数のシステムの情報を突き合わせて統合プロファイルを作る
4. リードにスコアを付けて優先順位を決め、営業担当が最良の機会に集中できるようにする

要点は、人間なら逐次で行う作業を、エージェントが **並列** で行うことです。Web IQ はその大きな支えとなっており、エージェントがタスクを「ファンアウト」して並列に実行できると説明されました。結果として、営業リサーチチームは書類をまとめる作業ではなく、自社との適合性に対する人間の判断に力を注げるようになります。

発表の Before / After では、以前は一度に 1 件ずつ、ごく一部のリードしかリサーチできなかったが、現在はリード全体を並列にリサーチできる、とされています。右側に示された 4 つの成果は、「量と質」「成長」の 2 つの軸に結びつくと説明されています。語られたのは次の点です（具体的な数値は示されていません）。

- **網羅**：すべてのリードをリサーチできる
- **優先順位付け**：リード全体を適切に順位付けでき、営業担当が最良の機会に集中できる
- **常に最新**：エージェントがデータを更新し続けるため、情報が古くならない
- **成長**：リサーチの質が上がり、リードとより意味のある会話ができ、コンバージョン率の向上につながる

Roby 氏はこの事例について、検索というとリードの拡充を思い浮かべにくいが、発想を広げるといろいろなことが可能になる、と受け止めています。

### 5.3 良い grounding を決める 4 つの指標

Roby 氏は、良い grounding は **品質、鮮度、速度、コスト効率** の 4 つに尽きるとし、「4 つすべてで先行している」と説明しました。

| 指標 | 発表での説明 |
| --- | --- |
| 品質 | より良い grounding は、エージェントが 1 回目から正しく有用な答えを返すことにつながる。**grounding satisfaction** という指標で測定し、高いほど良い。1〜2 ポイントの差でも、結果のエージェントの成功度合いに違いが見られるという。Web IQ は、比較対象のサービスの中で大きくリードしている |
| 鮮度 | 良い答えも、古ければ役に立たない。悪い答えは明らかだが、古い答えは「静かに失敗する」ため、テレメトリがあっても原因が分からない。測定も難しいため、**FreshSearch** というベンチマークを作った。「鮮度が必要なトピックに正しく答えられるか」と「返す根拠がどれだけ新しいか」の 2 つの観点で確認する。Web IQ は、この鮮度ベンチマークで最高スコア |
| 速度 | 音声モードなどでエージェントと常にやり取りする時代には、速度が必須。Web IQ は比較対象の中で最速の **154 ミリ秒（P95）**。これは話している間の息継ぎ程度の長さで、会話と「無音の空白」を分ける差だという |
| コスト効率（トークン効率） | エージェントは多くの情報を取り込めるが、全部を渡すとエージェントが遅く、扱いにくく、高価になり、誤答も増える。品質を縦軸、ペイロードを横軸に取り、左上にいることが望ましい。Web IQ はそこにいるとされた |

### 5.4 Genspark の事例（Olga Lykova 氏）

Olga 氏は、AI voice assistant を作る Genspark の事例を紹介しました。冒頭の個人的なエピソード（子どもと大型犬を抱え、散歩中などに Genspark を使う）で、音声で気軽に質問する使い方に触れています。

**会社の紹介**：Genspark は、人とエージェントが並んで仕事を進めるという考えに賭けた会社で、約 1 年でゼロから 2 億 5,000 万ドル（$250 million）に到達し、世界で数百万人のユーザーと、7,000 の企業が利用していると紹介されました。

**音声での使われ方**：音声でのやり取りが重要になったため、Web IQ を使い始めたといいます。「天気は？」「渋滞は？」「プレゼンに何を着ていけばいい？」「昨夜 Warriors は勝った？」「Pier 39 のおすすめのレストランは？」のような質問が例に挙がりました。ユーザーの質問を調べると、個人的な相談もある一方で、**通勤中に実際の仕事の質問をする**使い方が見られました。Olga 氏は、共同創業者の Ray 氏が自転車でオフィスに向かう間にたくさん質問して、到着前にエージェントに仕事を始めさせるエピソードを挙げ、「エージェントと実際に協働するのが新しい日常」だと述べています。また、通話の **5 回に 1 回はライブの Web が必要**、**3 回に 1 回はアドバイスを求める内容**だったという数値が示されました。

**待ち時間の重要性**：Olga 氏は、会話では普通の速さの応答を期待すると述べ、Jakob Nielsen 氏の UX 研究に触れて次のように説明しました。

| 待ち時間 | ユーザーの感じ方 |
| --- | --- |
| 0.1 秒 | 通常の感覚（電気のスイッチのようなもの） |
| 1 秒 | 気づき始める。AI が応答しないと、考えているためだと受け取ることもある |
| 3 秒 | 注意が散り始める |
| 10 秒 | 離脱する |

Genspark がエージェントを最初にテストしたときの標準は **6.22 秒**（離脱の直前）でしたが、Web IQ により **0.6 秒** を実現し、「ほぼ即時」になったと説明されました（音声認識の都合で表記が確定できませんが、本文では 0.6 秒と語られています）。さらに Genspark は 100 種類のモデルにまたがって動いており、ユーザーが自分の言葉で質問し、簡潔な 1 文で、数秒で、最新の情報が音声で返ってくることが大事で、バックグラウンドで仕事を完了まで進めることが大きな価値だと語られました。

### 5.5 企業で使うための観点と、Azure での一般提供

Roby 氏は、grounding は外の世界を企業に持ち込むことでもあるため、性能以外の評価軸を 3 つ挙げました。

1. **インターネットのコンテンツ**：インターネットのコンテンツは自由に使えるものではなく、人、企業、コンテンツ作成者が所有しており、誰がどんな状況で使えるかを決める権利を持つ。許可なく企業に入ってくれば問題になる。Web IQ は、パブリッシャーが **ページ単位で**、許可するコンテンツ、クロールしてよいもの、grounding 用に提供してよいものを決められる、おそらく最も高度な制御を備えていると説明された
2. **自社データ**：エンタープライズの機能として、規制要件のあるワークロード向けの **zero query logging**、主権（sovereignty）に関するオプションなどがある
3. **スケールとスタック**：大規模な本番ワークロード向けのスケール。Azure 上に構築されたセキュアな構成で、Entra ID、Azure 課金、MACC などの機能を備える

そして次を発表しました。

- **Web IQ は Azure で一般提供（broadly available）になった**。今すぐ Azure で試せる
- **新しい低価格**：1,000 トランザクションあたり 7 ドル、browse（ページの取得）は 1 ドル（"$1 for browse, which is the page fetch"。単位は音声からは明示されていません）

### 5.6 Web ページを超えた構造化データ：Places、Weather、Commerce

Roby 氏は、Web ページは良い出発点だがしばしば誤っており、今の Web は、事業者、商品、サービス、天気、データなど、ページ以外の形で提供される情報で構成されているとして、Web IQ を従来の Web ページの grounding から拡張すると述べました。今日から、エージェント向けの専門的な知識として **Places、Weather、Commerce** が加わります。

| データ | 提供状況 | 内容 |
| --- | --- | --- |
| Places | 一般提供 | エージェントに位置情報を持たせる。200 を超える市場の 2 億社以上の事業者について、住所、電話番号、営業時間、連絡先などの構造化された情報 |
| Weather | 一般提供 | 構造化された天気情報（例では 7 日間の見通し） |
| Commerce | プライベートプレビュー | 信頼できる加盟店のフィード（merchant feed）に基づく 400 億件を超える offers（オファー）。構造化された情報を使える |

各データでは、スライド上で「Web ページだけでの grounding」と「Web IQ のデータを重ねた grounding」を左右に並べた比較が示されました。画面の細部は音声からは確認できませんが、語られた内容は次のとおりです。

- **Places**：現場の技術者向けエージェントが、壊れた部品を買いに行く例。左（Web の内容のみ）は、店は見つかっても情報が古く、移転、住所変更、営業時間の違いがあり得る。右は構造化された情報で、事業者が存在し、有効で、営業中だと確認できる。「推測」と「行動できるデータ」の違いだと説明された
- **Weather**：Roby 氏は、前日にサンフランシスコの Moscone Center からパネルディスカッションのある場所へ移動する途中で雨が降り、音声モードのエージェントに「雨がすぐやむなら、途中で営業中のカフェを教えて」と頼んだところ、天気と場所の情報を組み合わせて案内され、カフェは営業中でコーヒーもおいしかった、という自身のエピソードを紹介した。あわせて、電力会社が気象イベントに備えて作業班を配置する例が語られ、左は大まかな気温だけで時間ごとの精度がない一方、右は 7 日間の見通しを含む構造化情報で、作業班を適切な場所に派遣できるとされた
- **Commerce**：ブラックフライデーを控え、商品が本物か、安全な販売者か、価格は最新か、在庫はあるかが重要になる。「プレミアムなコーヒー好きへのギフトのアイデア」という質問で、左は Web ページで見つけた目安の価格の付いたブランド、右は merchant feed の 400 億件超のオファーに基づく構造化情報、という違いが示された

こうして Web IQ は、**オープンな Web、ライセンスされた Web（bring-your-own license で利用）、目的別に作られたデータ（Places、Weather、Commerce から開始）** をつなぐものだと整理されました。

### 5.7 健康分野向けの Web IQ（Prerana 氏）

Roby 氏は、ソース（情報源）だけでなく、オーディエンス（利用者層）にも同様に取り組んでおり、信頼できる情報が最も重要な分野として **健康** から始めたと説明しました。Prerana 氏（Microsoft AI の Health チーム）の説明は次のとおりです。

- Microsoft の AI の各画面で、**毎週 1 億件の健康に関する質問**が寄せられる。健康エージェントを作る人にとって大きな機会
- 顧客や医療の専門家からは、**信頼できる情報源（credibility）** と **カスタムの制御（control）** が求められる。後者は、grounding に含める／除外するドメインを選びたいという要望
- **Web IQ は健康分野向けにチューニングされた**（health-aware）。National Academy of Medicine が独立して公開している信頼性の原則に基づく「権威性のシグナル」を作り、Web IQ のランカーがそれを認識する。測定の結果、健康クエリで grounding と情報源の信頼性が改善し、Web IQ の結果全体の権威性も高まったという
- **スコープ付きの結果**：エンタープライズが、消費者向けの一般的な健康情報エージェントに加え、研究者向け、専門医向けなどのエージェントを持つ場合に、エージェントごとに grounding するドメインを含める／除外して選べる。研究者向けなら、医学雑誌、論文、査読付き論文などに絞れる

デモの内容は 6.2 に書きました。Roby 氏は、自分の妻が医師で、回答を読む前に情報源を見る唯一の AI ユーザーだと述べ、オーディエンスが重要だと補足しています。

### 5.8 Web IQ Auto

Roby 氏は、複数の側面を持つ複雑な質問（シアトルで翌日に顧客と会う、会う場所、顧客の情報、天気を同時に知りたい、など）を取り上げ、現在のエージェントは、複数の質問を並列に投げ、答えが足りなければ次のターンでまた質問する、という繰り返しをするので、待っている間にコーヒーを飲めるほど長くなると指摘しました。

そこで「これを 1 回の API 呼び出しでできないか」という発想から、**Web IQ Auto** が作られました。その API 呼び出しは、質問を部分に分解し、各部分を取得し、まとめ、必要なものだけに絞り、答えが十分かを確認し、足りなければやり直し、最後にすべての根拠を一度に返す、という処理を担います。大きなモデルを API の中に入れるだけなら MVP は作りやすいが、それは「火炎放射器でろうそくに火をつける」ようなもので、効率的で速いやり方ではない、と発表者は述べています。Auto は多くの作業を要し、**Web IQ の新しい標準（デフォルト）の使い方**になります。どんなに複雑な質問でも、どんなデータが必要でも、grounding が一度に答えるものだと説明されました。デモは 6.1 です。

**価格**：Auto は「$1 more」で、ほとんどのエージェントの標準の入口になります。$9 の **Auto Advance** は同じ仕組みで、答えに対して複数回のパスを取れます。Auto Advance は今日発表した新しいもので、一部の顧客が早期に採用しています（$1 more と $9 の基準となる単位は、音声からは明示されていません）。

### 5.9 Cloudforce の事例（nebulaONE）

早期採用の例として、教育向けの会社 **Cloudforce** が紹介されました（同社から預かった内容を Roby 氏が代わりに発表）。

- 大学向けの AI プラットフォーム **nebulaONE** を提供しており、Azure テナントで運用される
- 100 を超える大学の 400 万人を超える学生が利用し、学生、教員などあらゆる用途で使われている
- 例として、学生が図書館のプロジェクトのために、「情報をガラスの中に保存する Microsoft のプロジェクト」について初めて調べる質問を行う。Auto は 1 回の呼び出しで、事実の根拠だけでなく、画像や動画などの適切なマルチメディアも含む「オーケストレーションされた答え」を返す。以前なら複雑なオーケストレーションが必要だった
- 性能：同じ回答に必要なトークン数は、以前使っていた「人間向けの検索」のようなレガシーの grounding より Web IQ のほうが少なく、Web IQ Auto ではさらに、平均 17,000 から 14,000 トークンに減った
- レガシーから Web IQ に切り替えた結果、回答速度は **12.5 倍**。精度と効率も向上した
- 複雑な質問をそのまま Auto に渡せるため、実装の負担も小さい
- CEO のコメントとして、「教育は常に最後に技術を手にするが、今回は最初に手にした」が紹介された

さらに Roby 氏は、多くの大学が学生 1 人あたり月 20 ドルのような上限を設けて AI を提供していて、AI を最も活用する学生ほど上限に達して使えなくなることがある、と述べ、トークン効率の高い Auto に切り替えると、最良のユーザーが月により多くのセッションを実行できるようになる、と説明しています。

## 6. デモ・手順

### 6.1 Web IQ Auto のデモ（Roby 氏）

Roby 氏は、会場の大きなスクリーンでも見づらいため一部を読み上げながら進めました。

1. 先ほどの質問に近い質問を用意する：シアトルの Pike Place 付近で顧客と会う。コーヒーショップを 2 つ探し、雨に降られないようにしたい
2. 画面の左は、エージェントが個別のツール（grounding の呼び出し）で動く構成、右は Web IQ Auto を使える構成
3. 回答はどちらも悪くない。コーヒーショップの 2 店は左右で異なるが、唯一の正解があるわけではない。天気もどちらも概ね妥当だが、右は、降水の可能性は低いが夜で昼間ではない、という説明が付いており、より良い答えになっていると評価された
4. 数値で比較すると、Auto は **トークンが 85% 少なく、1.4 倍速く、ターン数は 4 から 2 に減り**、大きな費用項目であるモデルのコスト（API の費用ではなく）が **68% 下がった**
5. 内部の動きを見る。個別ツールでは、まず「Pike Place 付近のコーヒーショップ」と「天気」を別々に質問し、「まだ十分でない」と考えて追加の質問を重ね、住所やコーヒーを確認し、Monorail Express の正式な住所を調べる。確認と検証を繰り返すので時間がかかる
6. Auto では、複雑な質問をまるごと 1 回で渡す。返ってくるのは、温度と降水を含む構造化された天気データ、レビューを含む 6 件の Web の回答（良いコーヒーショップを判断するための文脈）、そして場所の名前、住所、営業時間を含む Places の情報。二重の確認は不要になる
7. 内部の処理は Web IQ の中で行われるので、呼び出し先を決める複雑な「ハーネス」を自分で作る必要はなく、難しい質問を直接 Web IQ に送ればよい

### 6.2 健康向け Web IQ のデモ（Prerana 氏）

1. 「early signs of type 2 diabetes」（2 型糖尿病の初期症状）という、一般の利用者が Web 検索やエージェントで調べる典型的な健康情報のクエリを使う
2. 画面の左に健康エージェントの回答、右にその回答の根拠となった情報源が表示される
3. 最初は標準の Web 結果による grounding。結果は、トップの Web サイトなので、どれも優れている
4. 次に、Web IQ が権威性のシグナルを認識する状態でランキングが変わる様子を見せる。健康では、上位の Web 結果だけでなく、医療のプロトコルや実践に裏付けられた情報源を根拠にすべきだという考え方で、ランキングはそうした権威ある情報源を取り込むように変わる
5. 次に、研究者向けのエージェントの例を見せる。医学雑誌、論文、研究資料に grounding したエージェントの回答が示される
6. 同じクエリでも、オーディエンスが違えば grounding が異なり、回答も異なる。これが include / exclude のドメインを選ぶカスタムスコープである

## 7. 注意点・発表者の気付き

- **古い答えは静かに失敗する**：悪い答えは明らかだが、古い答えは原因が分からないまま誤った判断につながる、という指摘です。
- **情報が多すぎると逆効果**：エージェントに情報を渡しすぎると、遅くなり、高価になり、誤答も増えます。少ないペイロードで高品質にすることが求められます。
- **インターネットのコンテンツには権利がある**：許可なく企業に持ち込むと対応が必要になる、という注意が語られました。
- **待ち時間の影響**：3 秒で注意が散り、10 秒で離脱するという研究を引用して、速度が体験を左右すると述べられました。
- **1 回の失敗で使われなくなる**：Roby 氏は、エージェントが 1 回失敗すると、その用途では使わなくなるだろうと自身の経験から語っています（Weather の例の文脈）。
- **「大きなモデルを API に入れる」だけでは不十分**：それだけなら MVP は作りやすいが、効率的で速いやり方ではなく、Auto の実現には多くの作業が必要だったと述べられました。
- **Commerce はプライベートプレビュー**、Auto Advance は、この日に発表された新しいものです。

## 9. まとめ

Web IQ は、エージェントを外の世界につなぐ「エージェントのための検索エンジン」で、Microsoft IQ の中で組織の外側を担います。品質、鮮度、速度、コスト効率の 4 点で先行していると説明され、154 ミリ秒（P95）の速度や、FreshSearch での最高スコアが示されました。

今回の発表の要点は、Azure での一般提供と 1,000 トランザクションあたり 7 ドルの価格、Places と Weather（一般提供）、Commerce（プライベートプレビュー）、健康向けチューニングとカスタムスコープ、そして複雑な質問を 1 回の API 呼び出しで処理する Web IQ Auto（新しいデフォルト）と Auto Advance です。Northern Trust、Genspark、Cloudforce の事例では、並列化、レスポンス速度、トークン効率による効果が語られました。
