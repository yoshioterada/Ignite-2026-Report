# BRK313 Build with Web IQ: From API call to cited answer

## 1. はじめに

このセッションは、AI エージェントに「いまの Web」の情報を渡し、根拠（出典）付きで答えさせるための Web IQ を紹介する 45 分の発表です。Web IQ は、エージェントが新鮮な情報と、出典の付いた事実を Web から取得するために呼び出すレイヤーとして説明されています。

発表の前半では、1 回の API 呼び出しで複雑な質問に答える Auto、トークン消費を抑える passage、ソースを制御する scopes、そして Places、Weather、Commerce といった新しい情報源が紹介されます。後半では、Toyota の Takahiro Tsuchiya 氏が車載 AI エージェントの技術検証を披露します。最後に、品質・速度・効率の比較、信頼性（publisher の意向、ログ、エンタープライズ対応）、価格、Q&A が続きます。

## 5. 発表内容の詳細

### 5.1 課題：モデルは学習時点で止まっている

Deena 氏は、まず世の中の変化の速さを挙げています。新製品の発表、規制の変更、レストランの閉店、フライトの遅延、記録的な嵐などです。エージェントは推論、計画、コーディングなど、複雑なタスクをこなせるようになっていますが、世界はモデルの学習が終わった後も変化し続けます。

例として「Ignite の 1 日目に何があったか」という質問が挙げられました。人間なら調べますが、モデルは学習データしか持たないので、数日前のことも知りません。そこで grounding API が、モデルが調べ物をするための仕組みとして働きます。モデルが情報を求めると、呼び出しがライブの Web に出ていき、事実とデータを取得して、現在の情報と**引用元付き**で答えられるようになります。この役割を担うレイヤーが Web IQ です。

### 5.2 Web IQ の 6 つのエンドポイント

Web は単なるページの集まりではなく、エージェントが必要とするのはウェブサイトだけではありません。画像、動画、ニュース速報、物理的な場所の情報、あるいは読ませたい URL が決まっている場合もあります。Web IQ はこれらを 6 つの専用エンドポイントにまとめています。

| エンドポイント | 発表での説明 |
| ---- | ---- |
| web | Web ページ |
| news | ニュース |
| images | 画像 |
| places | 物理的な場所の情報 |
| browse | 読ませたい URL を指定して取得する用途 |
| commerce | 商品情報 |

> 補足：トランスクリプトでは 6 つの名称が列挙されましたが、個別の説明は後半の Places、Commerce 以外ほとんど語られていません。表の説明は、冒頭の「Web サイト、画像、動画、ニュース、場所、URL を指定した読み取り」という発言をもとに整理しています。Weather は、後半で別の機能（Web IQ weather）として紹介されています。

### 5.3 Auto：1 回の API 呼び出しで複雑な質問に答える

Deena 氏は、複数の要素を含む依頼の例を出しています。「明日 Seattle で顧客と会う。最新のニュースと市場の動き、天気、近くの良いコーヒーの店が知りたい」というものです。

従来のエージェントは、考え、Web やニュースや天気を調べ、足りないと気付いてもう一度調べる、という「search、think、search again」のループを繰り返します。その間、ユーザーは待たされます。

そこで、1 回の API 呼び出しで次のことを全部やる仕組みが提供されています。

* 質問を理解し、パーツに分解する
* 各パーツの情報を取りに行く
* まとめ、そのクエリにとって最も重要なものに絞り込む
* 答えが十分か確認し、足りなければもう一度行う

Deena 氏は、AI モデルを API の中に入れれば自分で作ることもできるが、それは「ろうそくに火をつけるのに火炎放射器を使うようなもの」で、動きはするが効率的でも安価でもないと話しています。このオーケストレーションを Microsoft 側が担うのが **Web IQ Auto** です。Auto は Web IQ の**新しい既定（default）**になりました。最後のまとめでは「Auto と Auto Advanced」が複雑な grounding を処理するとされていますが、Auto Advanced の詳細は発表では語られていません。

### 5.4 API の呼び出し例と passage によるトークン削減

Brian 氏は、RESTful な API 呼び出しの例を使って説明しています。MCP エンドポイントにエージェントを向けることもできますが、まず REST で設定方法を知ってほしい、という前置きです。例の質問は「今日、Golden Gate Bridge の通行料はどう払うか」でした。

スライドの設定項目は次のとおりです。

| パラメータ | 説明 |
| ---- | ---- |
| エンドポイントと API キー | 画面の最上部に表示 |
| query | 検索したい内容 |
| max results | 返す結果の数。例では既定の 10 |
| content format | 返るコンテンツの形。例では `passage` を指定 |
| max length | 各結果で返す文字数の上限。モデルに渡るトークン数に影響する |

Brian 氏は、エージェント構築の隠れたコストの 1 つが、モデルに入れる情報量だと説明しています。Web ページには、ナビゲーション、背景情報、メニュー、関連トピックなど、質問と関係のない内容も大量に含まれ、そのまま LLM のコンテキストに入れるとコストがかさみます。

`content format` に passage を指定すると、Web IQ がページ内の関連する部分を特定して、その部分だけを返します。説明用の例では、ページ全体なら約 12,000 トークン、passage なら 750 トークンで、**入力トークンが約 94% 減る**とのことです。必要な情報は保たれ、新しく、引用付きで正確なまま、総所有コストが下がります。

レスポンスは、検索結果だけでなく、AI が使える構造化された証拠として返ります。

* タイトルと URL（情報の出所が分かる）
* コンテンツ（passage を指定すると、質問に関連する部分のみ）。例では、Golden Gate Bridge の通行料の支払い方法や料金表が含まれていたと説明されています
* 取得可能な場合はタイムスタンプ。「発行元がページを更新した時刻」と「Web IQ が最後にクロールした時刻」という 2 つの異なる情報

Brian 氏によれば、**passage の利用でレイテンシのペナルティはありません**。また、Web IQ は 1 日に数十億回のクロールを行っており、データを新しく保つことは、最新情報を必要とするエージェントにとって重要だと述べています。

### 5.5 Scopes：取得元の制御

エージェントがどこから情報を取ってよいかも重要です。Brian 氏は、自動車ブランド向けの AI アドバイザーを例に、匿名の掲示板を公式の製品ドキュメントと同列に扱うべきではなく、信頼できない情報源で車両に関する断定をすべきではないと説明しています。そこで Ignite で導入されたのが **scopes** です。

* 使わなければ、Web 全体が対象になります。
* 使うと、自社の公式ドメイン、信頼できるパートナー、承認済みの Web サイトなどを**含める（include）**ことができ、上限は **10,000 ドメイン**です。以前の custom search 機能は約 450 が上限だったので、大幅な増加だと述べています。
* 要件に合わない情報源を**除外（exclude）**することもでき、こちらも上限は 10,000 ドメインです。
* 制御の粒度は、ドメイン、サイト、URL、パスのレベルです。

取得した後でフィルタするのは時間と計算資源がかかるため、信頼する情報の境界を最初に定義するほうがよいという考えです。例として、製品情報は公式のメーカー資料に基づかせ、独立したレビューには別の承認済みソースを使う、金融アプリなら規制当局への提出書類や承認済みの金融系の出版物に回答を限定する、といった使い方が挙げられました。

### 5.6 Places：物理世界の情報

「最寄りの店はどこか、開いているか、閉店前に着けるか」といった物理世界の質問に答えるのが **Web IQ Places** で、これも Ignite で提供が始まりました。2 億 700 万件超の事業所、ランドマーク、場所について、住所、電話番号、営業時間、位置情報を構造化して提供します。対象は 200 の市場です。

Brian 氏は、電気工事の現場で部品が足りなくなったフィールド技術者を例にしています。従来の Web 検索では、サプライヤーの候補は出ても営業時間が確認できず、電話をかけるか、行ってみたら閉まっていたということになりかねません。Places では、営業時間、住所、電話番号、距離を含む構造化された情報が返るため、エージェントが「行き先を提案する」だけでなく、「行動に移せる情報」を渡せるという違いが示されました。

### 5.7 Weather：天気の情報

天気は、移動、物流、建設、エネルギー、イベントの開催可否など、多くの判断に影響します。**Web IQ weather** は、Microsoft の天気情報を直接エージェントに届けます。内容は、現在の状況、時間ごとの予報、7 日間の見通し、政府の安全に関する警報です。

Microsoft の予報は、8 月に **2026 Forecast Watch の Most Accurate Forecast Award** を受賞し、世界で最も正確なグローバル天気予報として 3 年連続だと説明されています。

例は、太平洋岸北西部の電力会社です。嵐が近づく中で、運用エージェントに翌週の現場スケジュールの更新を依頼します。一般の Web 検索では漠然とした回答ですが、Weather を使うと、具体的な予報、時間ごとの状況、政府の警報が得られ、どの作業を再スケジュールすべきかをより詳しく把握できます。なお、運用上の判断では安全手順を考慮する必要があるとも述べています。

### 5.8 Commerce：商品情報（プライベートプレビュー）

買い物は、AI エージェントには意外に難しい問題です。商品を見つけることと、どの販売店がいくらで売っていて在庫があるかを知ることは別だからです。**Web IQ Commerce** は Ignite で**プライベートプレビュー**として始まり、**400 億件超**の構造化された商品オファー（商品識別子、価格、在庫、複数の販売店のオファー）を提供します。

例は「ホリデーの贈り物。コーヒー好きの友人に、200 ドル以内で」というものです。一般の Web 検索を使ったエージェントは、グラインダー、定期購入、トラベルマグなどの提案を返し、商品の確認、価格の確認、販売店の比較は利用者の仕事として残ります。Commerce を使うと、画像、価格、商品の詳細、複数の販売店のオファーを含む具体的な商品の選択肢が返り、「買い物のアイデアを出すエージェント」から「買い物の判断を完了する手伝いをするエージェント」に変わると説明しています。

### 5.9 Toyota の事例：車載 AI エージェント

Tsuchiya 氏は、Toyota は交通事故ゼロを目指しており、AI エージェントはそれを支える技術の 1 つとして検証しているものだと説明しています。**今日示すのは製品ではなく技術検証**です。Ignite の 3 つのセッションは、同じ AI エージェントが同じような旅をする内容で、3 つの問いを立てています（本セッションは最後のもの）。

1. エージェントは正しいことをしているか
2. このドライバーにとって正しいか（聞き取りでは "public IQ session" と述べられており、音声認識の都合で表記が確定できません）
3. 運転中に、エージェントは何を言うべきか（今回）

運転中、人は常に「知覚」「判断」「行動」の 3 つをしています。時速 65 マイルでは、車は 1 秒で約 95 フィート進むため、1 秒が重要です。ドライバーが道路に集中できるよう、答えは「正しく、速く、信頼しやすく」なければならないと述べています。

Napa Valley へのドライブという設定で、次の 3 つの場面が示されました（映像か実演かなどの提示方法は、音声からは確認できません）。

**場面 1：通行料**

* トリップのデータも Web IQ も持たない一般的な AI アシスタントは、答えは正しくても、北向きに走っていることを知らないため、通行料を払うかどうかをドライバーが自分で判断しなければなりません。
* 車載のエージェントに「Golden Gate Bridge に通行料はあるか」と尋ねると、「北向きは無料。帰りの南向きは、料金所用のタグ（toll tag）なしで $10.50」と答えます。
* 北へ向かっていることと、ファストトラック（聞き取りでは "fast track"。表記は音声認識の都合で確定できません）を持っていないことを、エージェントは把握しています。Web IQ が Web から最新の事実を素早く見つけ、通行料は南向きの車両だけにかかり、価格が 7 月 1 日に変わったことも分かりました。1 つの文で、この旅に合った答えになっています。

**場面 2：急速充電**

* Napa に着き、バッテリーが少ない状況で「近くに急速充電器はあるか」と尋ねます。
* エージェントは、1 つの充電器を 1 つの文で答えます。裏側では、Foundry IQ がオーナーズマニュアルを確認して、その車両の急速充電プラグを特定し、Web IQ が近くの急速充電器を探して、それぞれのプラグ情報を一覧にします。その上で、行き先に近いものを 1 つ選びます。
* ドライバーはプラグの名前を知らなくてよく、「車が代わりに知っている」と説明されています。

**場面 3：ランチ**

* ワイナリーの近くで「良いランチの場所はあるか」と尋ねると、エージェントは気軽なランチに向く店を 1 つ推薦します（店名は聞き取りでは "Velo Deli and Pizzeria"。音声認識の都合で表記が確定できません）。ドライバーは「Sounds good」と答えます。
* 裏側では、Web IQ が最新情報で近くのランチ場所を探し、"Public IQ" がこのドライバーの好みを把握し（"Public IQ" は音声認識の都合で表記が確定できません）、組み合わせて、その場に合う 1 か所を選んでいます。

**まとめとアーキテクチャ**

Web IQ がもたらす 3 つのこととして、次を挙げています。

| 観点 | 説明 |
| ---- | ---- |
| Freshness（新鮮さ） | 道路上では状況が分単位で変わるため、「いまのこの道」で正しい答えが必要 |
| Speed（速さ） | 速い応答でやり取りが短くなり、ドライバーが集中を保てる |
| Flexibility（柔軟性） | Web IQ は Foundry IQ や Public IQ などと一緒に動き、1 つの文でこの車両とこのドライバーに合わせられる |

Toyota AI エージェントは、**Foundry agent service** の上に構築しており、開発中です。車両データと IQ を組み合わせ、車両の情報には Foundry IQ、Web には Web IQ、ドライバーの好みには Public IQ を使います。さらに Foundry の observability（聞き取りでは "boundary observability"）で、回答の確認と改善を行います。

車は特別な環境で、車両ごとの環境、安全要件、プライバシーへの期待、国、言語、ドライバーが異なります。そのため、実際の車両でテストし、使い、学び、改善し、再度テストします。Toyota と Microsoft は、IQ を含む体験全体を一緒に改善しています。これを **EvalOps ループ**、または hill climbing（山登り）のアプローチと呼んでいます。

Toyota の発表の後、登壇者は、この例が、AI が質問に答えるだけの存在から、現実世界の体験の一部になるときに要件が変わることを示していると述べています。

### 5.10 品質・速度・効率の評価

登壇者は、競合との比較を継続的に行い、あらゆるカテゴリで 1 位であることを確認していると説明しています。数値は Microsoft の内部評価によるものです。

| 観点 | 結果 |
| ---- | ---- |
| 新鮮さ（freshness） | Web IQ Auto のスコアは **87.5**。比較した他のプロバイダーを上回る |
| 速度 | 8 リージョンのベンチマークで平均 **154 ミリ秒**。次に速いエンジンの約 2 倍の速さ |
| 効率 | 品質とトークン効率のフロンティアで、比較した他のプロバイダーをリードする |

新鮮さについては、間違った情報は失敗として検知しにくく、「静かな失敗」を引き起こすと述べています。速度については、競合は平均値を引用したがり、P95 を使わない理由があると説明しています。エージェントは 1 回ではなく複数回呼び出すため、待ち時間のミリ秒が、そのままエージェントが進めない時間になるからです。効率については、必要な情報だけを少ないトークンで渡すので、コスト効率が良く、スケールもしやすいという説明です。

### 5.11 信頼とエンタープライズ対応

続けて、信頼を次の観点から説明しています。

* **Publisher の意向**：Web 上のページや資産は、公開する会社や個人のものであり、使い方を決める権利があります。Web IQ は、publisher の意向を既定で尊重します。新しい**ページレベルのコントロール**により、publisher はページごとにコンテンツの使い方を決められます。利用者は、安心して最終ユーザーにコンテンツを届けられます。また、すべての結果が出典を持ち、主張を追跡して確認できます。
* **データ**：**zero query logging** により、クエリはお客様のものとして保たれます。規制要件のあるワークロードに関わります。データ主権の要件にも、オプションがあるとのことです。
* **エンタープライズ対応**：スケール、性能、信頼性のためのフルスタックで作られています。**Microsoft Entra ID** で動作し、Azure を通じて提供され、"Mac"（聞き取りでは "your Mac"。音声認識の都合で表記が確定できません）の消費にカウントされると説明されています。

### 5.13 Q&A

**Q1. Web IQ は Foundry の中だけで使えるのか。外でも使えるのか。**

どちらでも使えるという回答です。Foundry では、以前の grounding（聞き取りでは "grounding with Ring"。音声認識の都合で表記が確定できません）を、今週から Web IQ に置き換えています。ほぼすべての入口で置き換えており、一部は展開中です。Responses API と AI agents から Web IQ にアクセスできます。Foundry の外から直接使うことも、Copilot Studio の統合経由でも使えます。つまり、3 つの方法があります。Brian 氏は、他のクラウドからも呼び出せると補足しています。公開されたエンドポイントがあるためです。

**Q2. Toyota の例のようなパーソナライズ、リアルタイム性、知能を実現するには、何が必要か（Fabric、Web IQ、Foundry の関係）。**

回答者は、本編であまり触れなかった **Microsoft IQ** の話だと前置きして答えています。Microsoft IQ は、Fabric IQ、Work IQ、Web IQ、Foundry を含みます。Toyota の例は、文脈に応じて異なるストアから情報を取るためにこれらを使う例です。

* 企業は、Work IQ で仕事の情報を取り込める。
* Fabric IQ で、運用面のデータを取り込める。
* ユーザーの好みは、組織や個人のコンテキストの中で管理するのがよく、それを Web IQ と組み合わせて、好みに合った体験を作る。
* すべてを合わせて使いたい場合は、それらをまとめて簡単にする Microsoft IQ を見るとよい。

**Q3. 自社でライセンスを持つコンテンツ（例：Gartner のライセンスコンテンツ）を Web IQ に持ち込めるか。**

回答者は、**BYOL（Bring Your Own License）**という取り組みとチームがあると答えています。サブスクリプションの壁の後ろにあるプレミアムコンテンツは多く、その多くの提供元は、壁の後ろをクロールすることを許可しつつ、公開 Web で一般に使えるかどうかを自分で決められるようにしています。特定のプロバイダーのサブスクリプションを持つ場合、そのキーを持ち込めば、Web IQ にそのコンテンツのフィードがあれば、結果の一部として返せるようになります。コンテンツの扱いについては、"encumbrance management" と呼ぶ詳細な管理を行っているとのことです。コンテンツは順位付けされ、passage の形で、これまでに述べたトークン削減の利点とともに、Web IQ への 1 回の呼び出しで返されます。
