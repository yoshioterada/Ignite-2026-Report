# THRSP1139 Skip the pipelines and give AI live data with MongoDB

## 1. はじめに

このセッションは、MongoDB の Solutions Architect である登壇者が、会場の参加者に入力してもらったデータを使いながら、**「ライブのデータをそのまま AI に使わせる」** 構成を順に組み立てていくライブデモ中心の発表です。MongoDB Atlas にデータを入れるだけで、ベクトル検索、Foundry IQ によるマルチソース検索、Fabric IQ によるビジネス上の意味付け、Microsoft 365 Copilot（Work IQ）による業務コンテキストとの組み合わせまで、つなぎのための部品を自前で作り込まずにつながる、というのが主張です（Fabric への CDC 連携は、登壇者自身がパイプラインだと認めています）。

登壇者は、パイプラインやコネクタ、埋め込み（embedding）の変換処理のような「つなぎの部品」を **moving parts（動く部品）** と呼び、デモを進めるたびに「この部品が不要になった」と示していきます。

このセッションでは、画面を使ったデモが行われています（6 章）。

## 3. 何に関する発表か

背景として登壇者は、「みんなエージェントの話をしているが、エージェントの背後にあるコンテキストを忘れがちだ」と指摘します。運用データがライブであるなら、その上にエージェントを作るべきで、エージェントは取得できるコンテキストの質で決まる、という考えです。適切なコンテキストが適切なタイミングで得られなければ、エージェントは混乱し、ハルシネーションを起こします。そこで、このセッションは「データ基盤」に焦点を当てます。

まず MongoDB の位置づけです。登壇者の説明では、MongoDB は **リアルタイムの運用データベース** で、速いペースのトランザクションデータに焦点を当てています。銀行、EC サイト、小売、ゲーム、そしてエージェントが、こうしたリアルタイムデータを必要とする場面として挙げられています。**MongoDB Atlas** は、その MongoDB を核に、周辺の複数のサービスを加えて、フルマネージドで簡単に使えるようにしたものです。データベースの設定に何時間も費やすのではなく、「使うもの」にしたい、というのが全体の考えです。

デモの題材は、会場のオーディエンスに答えてもらう「次の大きな技術革新は何か」という質問です。発表の流れは次のとおりです。

1. 参加者がフォームから予測を投稿し、MongoDB Atlas にリアルタイムで入る
2. 意味で検索する（auto embedding とセマンティック検索）
3. Foundry IQ で、MongoDB のデータと戦略ドキュメント（SharePoint などの別ソースの例）を組み合わせる
4. Fabric IQ で分析し、オントロジーでビジネス上の意味を与える
5. Microsoft 365 Copilot（Work IQ）で、業務コンテキストと組み合わせる
6. 全体像のまとめと、始め方

## 4. 発表者が伝えたいメッセージ

メッセージは、**AI のインテリジェンスレイヤー（Foundry IQ、Fabric IQ、Work IQ）が良く働くためには、その下に 1 つのライブなデータ基盤が必要で、MongoDB がその役を担える**というものです。

登壇者は、moving part を「チームが作り、接続し、保守するコンポーネント」と説明し、デモを進めるたびに、それが 1 つずつ不要になることを示します。結びでは、役割や業界が何であれ、結局は誰もがデータを扱っており、そのデータは AI によってすでに変わりつつあるため、AI にそのデータへのアクセスを与えなければならず、配管（plumbing）に時間を使うべきではない、と話しています。データベースは「構築するもの」ではなく「消費するもの」であるべきで、データモデルやバックアップ、レジリエンスなどの設定に時間をかけず、エージェントに使わせて進めればよい、という考えです。

## 5. 発表内容の詳細

### 5.1 参加型の導入：データを入れてもらう

登壇者は、25 分でデモを一緒に作ると話し、人数が多くないのでデータが少なくなるため、参加者に協力を求めます。画面右の QR コードをスマートフォンで読み取るとフォームが開き、「次の大きな技術革新は何か」という質問に自由に答えられます。正解はなく、プレッシャーもありません。入力されたデータは、画面上にフローとして流れてきます。それは、MongoDB に挿入されたことを意味します。登壇者自身も、データをシミュレートして流していると述べています。

### 5.2 意味でアイデアを探す（auto embedding とセマンティック検索）

最初のエクササイズは **「意味でアイデアを探す」** です。登壇者によれば、これはエージェントを含むインテリジェンス層が行う基本的な処理です。

登壇者自身の予測は、「personal vehicles will take to the skies, letting people travel above city traffic」（個人用の乗り物が空に上がり、都市の渋滞の上を移動できるようになる）でした。つまり空飛ぶ車です。セマンティッククエリを実行すると、同じ言葉を使っていないのに「空飛ぶ車」というアイデアで考えている投稿が、類似のものとして返ってきます。

裏側の仕組みは次のように説明されました。

1. 参加者が QR コードからフォームに入力すると、MongoDB Atlas にデータを挿入する単純な操作が 1 回行われます。登壇者が見せたドキュメントには、メッセージ（予測、例では flying cars）、役割（architect など）、業界（technology など）のほか、画面には出していない複数の情報が含まれています。
2. データは MongoDB Atlas に入りますが、意味で検索するには、データをベクトル（embedding）に変換する必要があります。これを MongoDB の **auto embedding** が行います。登壇者の説明では、ドキュメントを埋め込みに変換して、データベース内で使える状態にしてくれるため、利用者は何も気にする必要がありません。
3. 検索ボタンを押すと、クエリ（A）が送られ、クエリ自体も埋め込み（ベクトル）に変換されます（B）。
4. 変換されたクエリを、データベースに入っている他の人の予測と比較し、ベクトルが似ているかどうか、何パーセントかというセマンティック類似度の計算を行います。登壇者は、スコアを見ていると話しています。
5. 意味的な結果が返され、アプリケーションに表示されます。

ここで登壇者は、**4 つの moving parts が不要になった**と整理します。

| 本来必要な部品 | このデモでの扱い |
| --- | --- |
| 運用データベース | MongoDB |
| 検索エンジン | MongoDB の中にある（実際に検索クエリを実行している） |
| ベクトルデータベース | MongoDB の中にある（埋め込みとベクトルを保存している） |
| 埋め込みサービスのパイプライン | auto embedding があるため別のパイプラインは不要 |

登壇者は、moving part が 1 つ不要になるとは、チームが作り、接続し、保守するコンポーネントが 1 つ減ることだと説明しています。狙いは、別々の配管（plumbing）を減らすことです。

### 5.3 Foundry IQ：MongoDB と他のソースを組み合わせる

関連するアイデアを見つけるだけなら基本的な処理です。そこで次の課題として、MongoDB にまだ入っていない、Azure 上のエンタープライズのソース（例えば SharePoint にあるドキュメント）と MongoDB のデータを組み合わせて、エージェントに両方を踏まえて推論させる場合を取り上げます。ここで使うのが **Foundry IQ** です。

デモのシナリオは、登壇者が「架空の会社」として、参加者の予測を使って次の大きな技術革新を予測する、というものです。登壇者は来年に向けて空飛ぶ車を信じるという戦略を持っており、参加者が投稿した関連する予測と比較したいと考えます。

仕組みは次のとおりです。

- ボタンを押すと、**Foundry エージェント** を呼び出します。
- この Foundry エージェントは、**Foundry IQ** に接続されています。
- Foundry IQ はこのエージェントの **ナレッジベース** です。登壇者は、ナレッジベースを「複数のソースから、読み取り専用で取得できるデータ」と説明します。Foundry IQ は、複数のソースから必要なデータを選んで取ってくるインテリジェンス層です。
- 1 つ目のソースは MongoDB の予測データで、**MongoDB MCP server** 経由でライブに参照します。
- 2 つ目のソースは、登壇者が作成した戦略ドキュメントで、Foundry IQ の中にインデックスされています。
- この 2 つのソースを持つナレッジベースは、再利用できます。作ったエージェントだけでなく、別のエージェントにも同じナレッジベースを接続できます。

ここでも、**カスタムのマルチソース知識検索** という moving part を作る必要がなくなります。Foundry IQ が、MongoDB のデータが必要か、ローカルのソースのデータが必要か、両方かを判断し、組み合わせてくれる、という説明です。

### 5.4 Fabric IQ：分析と、オントロジーによる意味付け

次に、全体像として分析の部分です。MongoDB は運用データベースですが、分析も必要になります。登壇者は、提出された予測のランキングなど、分析を行うスクリプトを用意し、その内容をエージェントに尋ねます。MongoDB は運用上の真実のソース（source of truth）であり続け、変更は長期的な分析のために **Fabric** に流れます。登壇者はこれを「パイプラインではあるが、自分たちは運用データベースなので、どこかの時点で分析プラットフォームにデータを渡す必要がある」と位置づけています。

裏側は次のとおりです。

- MongoDB は、保持しているリアルタイムのデータを **CDC コネクタ** 経由で Fabric に送ります。Fabric 側の受け口は real-time intelligence です。詳細には入らないと断ったうえで、長期的な分析などのユースケースに向けてデータを送る方法の 1 つだと述べています。
- その上に **Fabric data agent** があり、ボタンを押したときに動いたのはこのエージェントです。Fabric IQ のエコシステムの一部で、Fabric にあるデータについて推論できます。
- おまけとして、登壇者は回答データに対して **オントロジー**（Fabric IQ の新機能と説明）を作成しています。

オントロジーが必要な理由は、次のように説明されました。MongoDB Atlas に入っている回答には、例えば message というフィールドがありますが、それ自体は何の意味も持たず、どんなメッセージでもあり得ます。そこで意味を与えます。特に重要なのは、`created at` と `CDC event at` という 2 つの日付です。Fabric IQ を使わず、オントロジーを作らなければ、エージェントはハルシネーションを起こします。`created at` が予測を投稿した時刻で、`CDC event at` がデータが Fabric にコピー・転送された時刻だと、エージェントは知り得ないからです。この 2 つは別のものです。

これによって、**ビジネスコンテキストとセマンティックな配管** という moving part も避けられた、と登壇者は言います。数クリックで、オントロジーと Fabric data agent によって実現できたそうです。

### 5.5 Microsoft 365 Copilot と Work IQ：業務コンテキストと組み合わせる

ここまでで、左側の Foundry エージェントによる知識検索と、データへのビジネス上の意味付けができました。次の問いは、「会社としてこれらのデータがある今、次に何をすべきか」です。そのためには組織のコンテキストが必要になります。Microsoft 365 を使っているなら、Teams、カレンダー、Outlook のメールなど、日々使うデータが役に立ちます。エージェントがこれらを知っていてはじめて、「次に何をすべきか」を教えられるからです。

デモでは、登壇者が同僚（Paul）との間で、空飛ぶ車の戦略についての Teams のチャットを用意し、デモのための会議もスケジュールしています。この状況で、Copilot に参加者の予測と自分のコンテキストを組み合わせさせます。

仕組みは次のとおりです。

- Microsoft 365 Copilot は **Work IQ** の上にあり、Work IQ が組織のコンテキストを Graph API 経由で提供します。
- さらに **federated connector** によって、Work IQ が MongoDB のデータ（参加者全員の予測）にも同時にアクセスできます。
- 登壇者が行ったのは、Copilot が MongoDB に接続できるようにする federated connection の設定です。Copilot は MongoDB Atlas の MCP server に接続して、MongoDB のデータを取得します。

この仕組みも、業務コンテキストを自前で組み立てる必要がないという点で、moving part をもう 1 つ避けたことになる、と説明されています。Work IQ がすでに提供しているものを、MongoDB の運用コンテキストと組み合わせられるからです。

### 5.6 全体像

登壇者は、デモの流れを次のように振り返ります。参加者の予測は、最初にドキュメントになりました。それを検索して関連する意味を見つけ、Foundry が複数のソースを組み合わせ、Fabric がデータセットにビジネス上の意味を与え、Copilot が関連する証拠を仕事に結びつけました。つまり、Foundry IQ、Fabric IQ、Work IQ という AI のインテリジェンスレイヤーが、その一番下にある 1 つのライブなデータ基盤から、適切なコンテキストを受け取って動いている、という全体像です。

### 5.7 始め方と連携先

moving parts を減らす準備ができたら、**Azure Marketplace の MongoDB Atlas** から始められます。すでに Azure のサブスクリプションを使っていて、請求を MongoDB にひも付けたい場合も、その方法で行えます。MongoDB は Azure のエコシステムの中のネイティブなサービスのように、簡単にプロビジョニングできる、という位置づけです。

自分のアプリケーションに関する質問は、ブースで受け付けるそうです。ほかの連携としては、画面に出ているものとして Microsoft Agent Framework、Azure Databricks、OpenAI の接続、Visual Studio、Fabric、Foundry、Power BI などの多くの連携が挙げられています。

## 6. デモ・手順

画面の細部は音声からは確認できないため、語られた順に、語られた範囲で整理します。

### 6.1 データ投入（参加者の予測）

1. QR コードからフォームを開き、「次の大きな技術革新」の予測を投稿してもらう。
2. 投稿は画面上のフローに現れ、MongoDB Atlas に挿入される。

### 6.2 セマンティック検索

1. 登壇者の予測（空飛ぶ車に当たる文）をプロンプトとして表示し、セマンティッククエリを実行する。
2. 同じ言葉を使っていないが、空飛ぶ車というアイデアで考えている類似の投稿が結果に出る。

### 6.3 Foundry IQ のエージェント

1. 別の画面でプロンプトを実行する。内容は、登壇者の戦略（来年は空飛ぶ車）と、参加者の関連する予測とを比較するもの。
2. 回答には、戦略の要約（出典は登壇者の戦略ドキュメント）と、投稿者のアイデア（contributor ideas）が並ぶはずだったが、会場から空飛ぶ車に関する予測が返らなかったため、この部分は期待どおりに動かなかった。登壇者は、誰もそのような答えを投稿しなかっただけで正常な動作だと説明している。
3. エージェントは、戦略ドキュメントと MongoDB の証拠を統合し、それをもとに判断している。

### 6.4 Fabric IQ のエージェント

1. 提出された予測をランキングするなどの分析のプロンプトを、エージェントに投げる。
2. 関連する回答が十分にないため、要求されたランキングを確実には報告できない、という回答が返る。一方で、上位の業界、シェア、業界ごとの件数は表示された。
3. 登壇者の説明では、Fabric IQ が Fabric にコピーされた全データについて推論した結果。

### 6.5 Microsoft 365 Copilot

1. Copilot を開き、あらかじめコンテキスト（ハルシネーションを避けるため）を用意しておく。先ほど画面に出ていたプロンプトを追加する。
2. federated connection を使って、Copilot が MongoDB のデータに対して推論できるようにする。
3. Copilot は、MongoDB Atlas の MCP server に接続してデータを探し、Paul との Teams チャットやカレンダーの会議と組み合わせる。登壇者が求めたのは、参加者の予測と自分のコンテキストに基づいて、次に取るべきステップを示すこと。
4. 結果として事実が取得される。出典には MongoDB（ロゴが表示される）、Teams、ドキュメントなど複数のソースが並んだ。

## 7. 注意点・発表者の気付き

- 登壇者は冒頭で、参加者が少ないとデータが少なくなると述べていました。実際に、Foundry IQ のデモでは空飛ぶ車に関する予測が返らず、Fabric IQ のデモでは要求されたランキングを確実には出せない回答になりました。
- Fabric へのデータ連携は、CDC コネクタを使うパイプラインです。登壇者は、MongoDB は運用データベースなので、分析プラットフォームにはデータを渡す必要があり、MongoDB が運用上の source of truth であり続けると位置づけています。
- オントロジーなしでは、`created at` と `CDC event at` のようなフィールドの意味をエージェントが取り違えてハルシネーションを起こす、という注意が示されました。
- Copilot のデモでは、ハルシネーションを避けるために事前にコンテキストを用意しています。

発表では、auto embedding で使われる埋め込みモデル、料金、性能の数値などには触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は、moving parts が減ることです。

- 運用データベース、検索エンジン、ベクトルデータベース、埋め込みのパイプラインを、MongoDB 1 つで賄える（4 つの部品の削減）。
- カスタムのマルチソース知識検索を、Foundry IQ が肩代わりする。ナレッジベースはほかのエージェントにも再利用できる。
- ビジネスコンテキストとセマンティックな配管を、Fabric IQ のオントロジーと Fabric data agent で、数クリックで済ませられる。
- 業務コンテキストを自前で組み立てる代わりに、Work IQ が提供するものを MongoDB のデータと組み合わせられる。
- Azure Marketplace から MongoDB Atlas を始められ、Azure のサブスクリプションに請求をひも付けられる。

## 9. まとめ

このセッションは、参加者が投稿した予測を 1 つのライブデータ（MongoDB Atlas）として扱い、auto embedding によるセマンティック検索、Foundry IQ によるマルチソース検索、Fabric IQ のオントロジーによる意味付け、Work IQ を通した Microsoft 365 Copilot との組み合わせまでを、順にデモで見せる構成でした。それぞれの段階で、専用のパイプラインや部品を作らなくて済むことが、moving parts の削減として示されています。

Foundry IQ、Fabric IQ、Work IQ という AI のインテリジェンス層が、適切なコンテキストを得るための土台として、1 つのライブなデータ基盤を置く、というのが登壇者の結論です。始めるなら Azure Marketplace の MongoDB Atlas から、個別の質問はブースで、と案内されました。
