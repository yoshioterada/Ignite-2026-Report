# BRK308 How Microsoft IQ shapes the cost of enterprise AI

## 1. はじめに

このセッションは、Microsoft IQ（Foundry IQ、Fabric IQ、Web IQ、Work IQ の総称として語られています）を使ったエンタープライズ AI のコストと価値を、事例デモと試算の両面から説明する発表です。前半は、冷蔵が必要な薬品を扱う薬局を想定した画面デモを通じて、4 つの IQ が役割分担しながら 1 つの業務を支える様子が示されます。後半は、同じ事例を 5 年間の事業計画（ビジネスケース）として試算した結果と、価値を測るための進め方、会場との質疑応答です。

発表の核心は、**IQ ごとに課金の単位と最適化の手段が違うため、「Microsoft IQ 全体で 1 つの金額」というものはない**という点です。そのうえで、コストだけでなく業務への効果を合わせて見るよう勧めています。

## 5. 発表内容の詳細

### 5.1 ビジネス面と技術面の観点

事例のシナリオでは、ビジネス面で「異常が起きたことにどれだけ早く気付けるか」と「どれだけ早く対応して解決できるか」が指標になります。技術面では、開発の速度とコスト、市場に出すまでの時間、本番で使い始める前にソフトウェア開発者へかける費用、運用後の保守にかかる費用と時間、さらに次の段階へ革新する際の投資が挙げられました。

### 5.2 事例のシナリオ

舞台は、冷蔵が必要な薬品を扱う薬局です。薬品は決まった温度で安定させる必要があり、外れると薬品が傷んで損失が出るうえ、顧客へ供給できなくなります。現状は手作業の多い工程です。冷蔵庫の温度を監視する自動化があっても、温度は 1 つのシステム、人の居場所や冷蔵庫内の在庫は別のシステムにあり、集めるのは面倒です。信号を集められたとしても、問題発生時の方針や手順を記した業務の知識ベースを一緒に使わなければなりません。

この薬局向けに、Microsoft IQ の各製品を使った統合システムが作られました。各 IQ が、得意な知識領域とデータの種類について専門家として働きます。事例の薬局名は、音声認識の都合で表記が揺れており確定できません（Kildover、Caldova など複数の聞こえ方があります）。

### 5.3 IQ ごとの役割

| 製品 | 事例での役割 |
| --- | --- |
| Foundry IQ | 組織の知識（標準作業手順、コールドチェーンの方針）を扱う |
| Fabric IQ | 店舗・在庫・出荷・配送車・冷蔵庫のテレメトリなどのデータ分析。資産と在庫に結び付く |
| Web IQ | 気象警報、電力会社の停電情報、ニュース、冷蔵庫や圧縮機がリコールされた場合の製品リコールなど、組織の外にある情報 |
| Work IQ | 誰が待機・対応可能か、どこにいるかを見て、Outlook や Teams で連絡する。Teams 通知による承認やメールの承認も担当 |

発表では、この層に、業務のワークフローやエージェントをつなぐ構成が示されました。

### 5.4 なぜ IQ を使うのか

サプライチェーン、在庫、運用、価格、標準作業手順、ワークフローごとに個別のシステムやエージェントを作ると複雑になり、管理するものが増えます。各エージェントが、用途ごとにデータを取り込み、推論し、RAG を組むといった作業を毎回繰り返すことにもなります。IQ では、事業のエコシステム内の情報を IQ が取り込み、その上に載せるエージェントやワークフローに文脈を提供します。

IT 面の利点として、構築が想像より速いこと、Microsoft が IQ のプラットフォームを運用するためスケーラブルで信頼性が高いこと、トークンの使い方が効率的なこと、セキュリティも Microsoft が管理することが挙げられました。IQ は「サービスとしての AI」「サービスとしてのエージェント」のようなもので、LLM の安全性確保、更新・学習、複数の Azure リージョンにまたがる冗長化といった世話をする必要がない、という説明です。

### 5.5 IQ ごとの課金と最適化

Sonia は、IQ は別々の製品なので、請求を細かく見ると使い方ごとに費用が変わると説明しました。課金の単位として、グラウンディング呼び出し 1,000 回あたりの課金があること（どの製品に当たるかは、音声が不明瞭で確認できません）、Foundry IQ は検索の容量に基づくことが語られています。**Microsoft IQ 全体の単一の金額はなく**、各 IQ の使われ方が請求額を左右し、最適化もその単位で行う、という説明です。

最適化の手段は製品ごとに異なります。

| 製品 | 手段 |
| --- | --- |
| Foundry IQ | 圧縮、リランキング、グラウンディングの調整（聞こえた表記は「case grounding」で、音声認識の都合で確定できません）。PTU によるコミットメント割引 |
| Fabric IQ | セマンティックモデルの再利用 |
| Web IQ | タスクごとの重複クエリの削減、情報の鮮度が必要なときだけ検索する。エージェントごとの呼び出し回数の上限 |
| Work IQ | 文脈がタスクを改善する場面での利用。データアクセスの管理、利用のガバナンス、業務成果の管理 |

このほかの手段として、容量メトリクスと、エージェント・チームごとの予算クレジットの管理が挙げられました（どの IQ に対応するかは、発話では明示されていません）。

どの柱から取り組むかは、最も費用がかかっている IQ を見て決めるとよい、と述べています。

### 5.6 コストの試算（Nitin）

Nitin は、売上 50 億ドルの標準的な規模の薬局を想定し、標準的な想定のクエリ数・タスク数でコストを試算したと説明しました。IQ ごとの計測・支払い単位は次のとおりです。

| 製品 | 課金の単位 |
| --- | --- |
| Work IQ | Copilot クレジット。想定リクエスト数に平均消費クレジットを掛けた |
| Fabric IQ | Fabric IQ の容量ユニット |
| Foundry IQ | Azure の消費単位（ACR）での支払い。エージェント検索のトークン、ランキング、計画の観点で課金 |
| Web IQ | API の呼び出しごと |

定価を使い、割引は考慮していません。結果は、このユースケース全体で**年間 60 万〜70 万程度**です（通貨は発話では確認できません。発話は「60 万〜70 万」の意味に聞こえます）。内訳では、Work IQ の利用に由来する割合が大きくなりました。

### 5.7 4 つの観点での効果

IQ を使わない場合、多くを手作業で行うため反応時間がかなり長くなります。IQ を組み込むと、次の 4 つの観点で効果が出ると説明されました。

- **賢く**：信号の把握、事業上の意味の判断、取るべき行動への変換といった手作業を自動化できる。エージェントが何をすべきかを示し、場合によっては起動の合図まで出す
- **速く**：反応時間が短くなり、薬品が傷む損失を防げる。収益機会があれば素早く取りに行ける。最も大きな価値はこの観点にあった
- **無駄なく**：エージェントが文脈をすばやく理解し、トークンが減る。IQ により **25〜50%** 程度のトークン削減が見られる（IQ により幅がある）
- **安全に**：データがある場所で IQ が動くため、ユーザーやエージェントに設定したガードレールをデータに直接適用でき、セキュリティリスクを下げる。商品が傷んだまま市場に出るリスクも避けられる

リスクは定量化していません。質的な面があり、金額にしても意味が薄い場合があるためです。定量化した 3 つの観点を合わせると、年間で約 **250 万**の削減効果が見込まれると述べています。

### 5.8 5 年間のビジネスケース

経営層（CFO や経営会議）は、新しいエージェントの構築や消費量の確約を求める際、投資対効果を問います。そこで、効果と想定消費量を、立ち上がり期間を置いてモデル化しました。ボリュームの立ち上がりは、1 年目に約 50%、2 年目から 75%、その後 100% で、効果と消費の両方に同じ比率を適用しています。

5 年間でモデル化した結果は、ROI（投資対効果）が **200% 超**、回収期間は数か月、NPV（正味現在価値）は **700 万超**です。効果の内訳は、自動化による「賢く」と、価値の最も大きな塊である「速く」でした。これはあくまで一例で、ユースケースや業種で数値は変わるとしています。この試算は、コストのモデル化とユースケースの評価を行うために作られたフレームワークとツールに基づいています。価値を量る 4 つの柱はチームで決めたもので、KPI は業務プロセスやシナリオごとに異なります。

### 5.9 ユースケースの選び方と価値測定

一つのユースケースに限らず、部門や企業全体で見ることもできます。初期の IQ 立ち上げには投資と工数が必要ですが、同じ機能内で、似たデータを使いながら増分の価値を生む別のユースケースが見つかれば、効果は指数関数的に増えると説明されました。

ユースケース選びでは、次の 2 つの失敗が挙げられました。

1. 準備が整っていて作りやすいものだけを選ぶ。概念実証としては成立しても、事業上最も重要な課題ではないため、その後の広がりが出ない
2. 最も価値の高いものを選ぶが、準備状況を確認しない。必要なデータが IQ に入るか、システムの API が使えるか、すぐ立ち上げられるかを確認しないと、6〜8 か月を準備に費やして時間を失う

価値を示すために有効だった手順は次のとおりです。

1. 実装前に、対象の業務プロセスと、最重要の KPI（2〜3 個）を決めて合意する
2. 現状の基準値を測り、どう影響を与えるかを決める
3. 翌日から何を変えるかを準備し、増分の価値につながる文脈を作る
4. 測定の枠組みを作る：入力はどこから来るか、KPI を追うシステムは何か、変更と結び付くか、報告の仕組みは何か

### 5.10 Q&A

**Q1：石油・ガス業界向けに独自の領域を載せたい。既定のままではなく、文脈をどこまで合わせられるか。**
Nitin は、IQ は既定のままで使うものではなく、自組織の事業の運営や構造に固有のものであるべきだと答えました。Work IQ は M365 のデータ（メール、Teams の統計など）から個人・チーム・企業レベルで組織を理解します。Fabric IQ や Foundry IQ は事業そのものの上に載ります。Fabric IQ で作るオントロジーは、石油・ガス向けというだけでなく、KPI の定義や事業部の構成など、その会社に固有のものになります。前日に発表されたプレイブックとビジネスプラグインも同じ考え方で、階層は組織固有のものであり、汎用の階層に当てはめる作りではないと説明しました。導入の進め方は、Work IQ から始めて次に Fabric を使うユースケースを探すなど、顧客の出発点によって異なり、最終像（北極星）は持ちながら順に進めています。
Sonia は、オンボーディングの工数は見積もれないとしつつ、オーストラリアの発電会社の例を挙げました。同様のダッシュボードを、他の AI ツールで自前で作る場合より、はるかに短い期間で構築できたそうです。導入と事業の文脈合わせには時間がかかるものの、その後は Microsoft がプラットフォームを管理・更新・保護・改善するため、自社の管理負担や投資がなく、新しい機能を載せる際の市場投入速度とコストも改善する、と説明しています。

**Q2：オンボーディングは 1 回で済むのか。性能を評価・調整・最適化するツールはあるか。**
Nitin は、現状ではエージェント単位の性能評価ツールが中心で、IQ それぞれの評価ツールは別にはないと答えました。同じエージェントに対し、システムへ直接 API をつなぐ場合と IQ を付けた場合を比べ、応答の速さやトークン数を見られます。公開された形で数値が確認できるのは Web IQ で、速度、結果の精度、トークンの少なさを、市場にある他の 3〜4 の競合と比べたブログが公開されている、と述べています。Sonia は、会場に IQ チームの専門家がいるハブが夜遅くまで開いていると案内しました。

**Q3：事例のコストでは約 80% を占めていたようだが、コストを理由に Web IQ から Foundry IQ のような別の IQ へ処理を移せるか。**
Nitin は、割合が高かった理由は試算の想定（Work IQ・Foundry IQ・Fabric IQ のどれが何割のクエリを担うか）にあると答えました。なお質問者が挙げた Web IQ ではなく、最も高かったのは Work IQ で、約 80% だったと確認されています（発話の途中で訂正されています）。
移し替えはできません。扱うデータが別だからです。Work IQ が扱うのは M365 内のデータ（Teams のチャット、メール、SharePoint）で、Foundry や Fabric にあるデータではありません。直接 Graph API で解釈させることもできますが、エージェントの時間とトークンはかなり増えます。Work IQ のベンチマークでは、標準の Graph API を使う場合に比べ、トークン使用が**最大 80% 少ない**と述べました。Fabric IQ は、数値データを含む中核業務システム（CRM、ERP など）上で動きます。Foundry IQ は、非構造化の文書（ナレッジ記事、ポリシー、手順書）に対して使います。Web IQ は、組織の外にある情報（外部のサイトなど）を扱います。したがって、ユースケースに合う IQ を使うものであり、安いほうへ切り替えるものではありません。Sonia は、最も多く動いている IQ を特定し、その IQ の最適化手段を深掘りするのが筋だと補足しました。また、デモでは 1 時間ごとの定期確認を、説明のために手動で起動したと述べています。

## 6. デモ・手順

デモは行われました。Sonia が「Caldova retail command center」（聞こえた表記のまま。薬局名と同様、音声認識の都合で確定できません）の画面を使って実演しています。画面の細部は音声では確認できないため、語られた範囲を実施順に整理します。

1. Web IQ のニュース確認を手動で開始する。通常は外部のニュースを定期的に確認している
2. 電力供給の中断が、薬局のある 2 拠点に影響していると検出される
3. 冷蔵庫の中で何が危険にさらされているかを確認する。冷蔵庫、在庫のシステム、手順書を調べ、誰が助けられるかを探す。現場にいて、オンラインの人の情報も取得される
4. 冷蔵庫の 1 台が温度のしきい値を超えたと警告されたので、アラートを確認済みにする
5. 推奨アクションが表示される。現場にいる Thomas に、冷蔵庫のリセットボタンを押し続けて圧縮機が再起動するかを確かめるよう、メッセージで依頼する。停電後は再起動するはずが、この冷蔵庫は再起動しなかった。8 度に達する前に温度の上昇が見えており、現場へ連絡できた
6. Thomas が対応し、温度が下がり始める
7. 冷蔵庫の確認を続けると、もう 1 台の問題のある冷蔵庫と、その拠点の履歴が表示される
8. Web IQ のニュース確認を再度行うと、Met Office（気象機関）の風雨警報など、ウォッチ欄の更新がある。停電が天候によるものと分かり、さらに悪天候が予想される
9. その影響を確認すると、今夜も停電の可能性があり、起動に失敗した 2 台と同じファームウェアの冷蔵庫がこの地域にさらに数台あると示される。古いファームウェアが原因の可能性が見えてくる
10. ファームウェア更新の見積もりが用意されていたので、承認し、技術者が更新に行けるようにする（今夜に間に合うかは分からないが、進行中という安心がある）

デモ後の説明では、内部の動きが次のように語られました。Fabric IQ がアラートを見てデータの問題を認識し、Web IQ がニュースとの関連付けを行い、同じファームウェアを持つ 2 台の圧縮機の無関係に見える故障を結び付けました。技術者の位置情報には Azure Maps が使われています。Foundry IQ が方針と標準作業手順を参照し、Work IQ が Teams 通知による承認や Teams メッセージの送信、メールの承認を担当しました。

## 7. 注意点・発表者の気付き

- AI のコストは中身が見えにくく、LLM のトークンだけでなく周辺の仕組み（継続的な学習や推論を含む）も見積もりに含める必要がある
- Microsoft IQ 全体の単一の金額はなく、IQ ごとの使われ方で請求が決まる。最適化も IQ ごとに行う
- 試算は想定に基づく。Web IQ・Work IQ・Foundry IQ・Fabric IQ のどれがどれだけのクエリを担うかという想定が、コストの内訳に大きく影響した。定価で計算し、割引は含まれていない
- リスク低減は、定量化せず、質的な効果として扱った
- ユースケース選びは、事業上の重要度と準備状況の両方を確認する。片方だけだと、広がらないか、準備に時間を失う
- IQ の導入には初期の投資と工数が必要で、事業の文脈に合わせるオンボーディングの時間がある。工数の見積もりは発表者には示せなかった
- IQ 単体の評価ツールはなく、評価はエージェントの性能で行う。Web IQ のみ、競合との比較が公開されている

## 8. 利用者にとっての利点

- 事業面：判断が速くなる、対応の質が上がる、生産性が上がる、誤りやコンプライアンス上の抜けが減る。事例では薬品が傷むのを防ぎ、再発の原因となる冷蔵庫の問題も是正できる
- IT 面：構築が速い。Microsoft が運用するのでスケーラブルで信頼性が高く、セキュリティも管理される。トークンの使い方が効率的で、LLM の保守・更新・冗長化の世話が不要
- 試算（想定に基づく）：年間コスト 60 万〜70 万程度に対し、年間約 250 万の効果。5 年の ROI は 200% 超、回収は数か月、NPV は 700 万超。IQ により 25〜50% のトークン削減
- Work IQ は、標準の Graph API を使う場合より、最大 80% 少ないトークンで済むとされている
- 同じ IQ を複数のユースケースで再利用すると、効果が積み上がる。オーストラリアの発電会社では、自前構築より大幅に短い期間でダッシュボードを構築できた

## 9. まとめ

IQ は、データの文脈をエージェントとワークフローの共通の層として提供し、個別のエージェントを用途ごとに作る手間を減らします。薬局のデモでは、Web IQ、Fabric IQ、Foundry IQ、Work IQ が連携し、停電に伴う冷蔵庫の異常から、現場担当者への連絡、原因の推定、ファームウェア更新の承認までを 1 つの流れで支えました。

コストは IQ ごとに課金単位も最適化の手段も異なるため、単一の金額では語れません。試算例では、コストと効果を「賢く・速く・無駄なく・安全に」で整理し、5 年のビジネスケースとして示しました。実際に使い始めるときは、事業上重要で、かつ準備が整ったユースケースを選び、実装前に KPI と基準値を決めて測定の仕組みを用意することが勧められています。発表者は、関連セッションやツール、ドキュメントのリンクを後で共有すると案内しました。
