# THR870 AT&T's enterprise-scale transcript intelligence with Foundry IQ

## 1. はじめに

コールセンターの会話記録には、顧客が困ったこと、解約を考えた理由、競合他社への言及など、業務改善につながる情報が含まれています。しかし、非構造化の文章のままでは、部門を横断して分析するのに手間がかかります。

このセッションでは、AT&T が通話・チャットの記録を分析基盤へ取り込み、自然言語による問い合わせにつなげた取り組みを紹介します。会話を要約するだけでなく、分類結果を構造化し、SQL による集計や相関分析へ使うところまで扱っています。

もう一つの論点は、数字を調べる情報源と、業務上の「なぜ」を考える知識を組み合わせることです。**データを集めるだけでなく、その意味と関係をエージェントへ伝える必要がある** という、Foundry IQ の今後の方向にも話が広がります。

## 3. 何に関する発表か

AT&T には、数百の エージェント型 AI / RAG のユースケースを支える共通基盤があります。その重要な構成要素の一つが、知識の取得を担う層です。今回の会話記録インテリジェンス（transcript intelligence）は、その優先度の高い用途として紹介されました。

発表では、約 6 カ月で構築した基盤の説明から始め、本番データを使う問い合わせの実演へ進みます。その後、通話記録の分析と別の業務知識を組み合わせる例を示し、ナレッジグラフ（knowledge graph）やオントロジー（ontology）の役割を整理しています。

ここでの **Text-to-SQL** は、利用者の自然言語の質問を SQL へ変換するものです。会話記録の原文へ毎回直接質問するだけでなく、あらかじめ抽出した項目を SQL で調べる使い方が含まれます。

## 4. 発表者が伝えたいメッセージ

**非構造化データを、用途ごとに処理し直す必要はありません。** 共通の取り込み・要約・分類の基盤を作り、各部門はそこから分析を始める、という考え方です。

さらに、複数の情報源を検索できるだけでは十分でないと指摘しています。同じ言葉でも部門や業務によって意味が異なり、関係のない情報を結び付ける可能性があるためです。

業務で使う概念をオントロジーとして整理し、対象間のつながりをグラフで表すことが、次の段階として説明されています。ただし、AT&T でナレッジグラフの利用がすべて完了したという発表ではありません。採用を検討している部分と、本番利用中の基盤は区別されています。

## 5. 発表内容の詳細

### 5.1 共通基盤の上に、二つの利用方法を用意する

土台となるパイプライン（pipeline）は、会話記録から要約、分類、分析用の情報を生成します。その上に、二つの主要な機能があります。

一つは、**transcript IQ** と呼ぶ分析機能です。対象となる会話の集団（コホート）を選び、プロンプトを指定して掘り下げます。新たな分析のたびに パイプラインを一から作る代わりに、同じ仕組みで問いを変えます。

もう一つは **transcript Q&A** です。業務責任者がアナリストへ SQL の作成を依頼する代わりに、自然言語で質問し、集計結果と可視化を受け取ります。

Bo 氏は、その背後にある社内の Text-to-SQL 技術がベンチマークで 8 カ月間首位を維持しているとも説明しました。

> 注意：この箇所の内部技術名は「OS data」など、ベンチマーク名は「BERT benchmark」と認識されています。正式な綴りは確認できません。ここでは、それらを推測で別の名称へ置き換えていません。

### 5.2 取り込み・加工・分析・提供の四段階

| 段階 | 説明 |
| --- | --- |
| 取り込み（Ingest） | バッチとリアルタイムの両方を、共通のパイプラインへ取り込みます |
| 加工・付加情報の生成（Enrich） | 要約、分類、はい／いいえのフラグなどを、用途に応じたモデルで生成します |
| 分析（Analyze） | 蓄積した情報に対して、集計や追加分析を行います |
| 提供（Surface） | 他部門やアプリが使える形で、データと結果を提供します |

モデルを一つに統一するのではなく、処理内容に合うものを選びます。例えば、顧客との会話に競合他社が登場したか、というフラグを生成します。独自の分類モデルも使っており、発表の約 1 カ月前に公開したモデルにも触れています。

そのモデル名は「OTEL 2.0 decision model（意思決定モデル）」と認識されていますが、正確な表記は確認できません。モデルの名前よりも、分類のような個別作業に合うモデルを パイプラインへ組み込む設計が、ここでの要点です。

分析の追加にはプラグイン型の構成を使い、対象とする会話のグループ（コホート）とプロンプトを変えられるようにしています。

### 5.3 一つの処理基盤から、複数の形で提供する

会話とチャットの記録を Event Hub へ取り込み、AKS 上のワーカーで処理します。対象は今後、アンケートやメールなど、別の文章データにも広げる説明です。

処理結果には、複数の提供先があります。

- **ADLS Gen2** に保存し、Databricks や Snowflake から利用できる形にします。
- **PostgreSQL と GraphQL** を通して、リアルタイムのアクセスへ提供します。
- **Foundry IQ のナレッジベース（knowledge base）** にセマンティックレイヤー（semantic layer、業務データの意味を表す層）を持たせ、Text-to-SQL を支えます。

最後の点が重要です。Foundry IQ は、会話原文だけを保存して回答させるものとして登場するのではありません。SQL を生成する際に必要な、業務データの意味を取得する層としても使われています。

### 5.4 一つ目の実演：解約の推移を自然言語で調べる

本番利用中の仕組みとして、毎日数百人のアクティブユーザーが使っていると説明しています。実演では、直近 7 週間の解約状況を尋ねます。

通常アナリストが行うなら、どのデータベース、テーブル、列を使うかを調べ、SQL を書く必要があります。この例では、非構造化データからすでに **246 の列** を作っています。自然言語の問いを、これらへの問い合わせへ変換します。

実演画面では、参照する既存例、テーブル、列、SQL 実行の流れが説明されました。約 20 秒で、週別に集計した結果が返ったとしています。Liam 氏も、機微な部分がぼかされている本番データの実演だったことに触れています。

続いて、解約増加の背景として、競合他社への言及との関連を尋ねます。同じ環境から回帰・相関の分析へ進める例です。

> 注意：相関の数値は音声認識で「8-8」となっており、小数点や正確な値を確定できません。発表では強い関連があるという説明ですが、ここで正確な係数を補ってはいません。原因を切り分ける検証条件までは説明されていないため、解約の因果関係が証明されたとは記載していません。

### 5.5 通話の前後をつなぎ、担当者へ必要な知識を届ける

コールセンターでは、通話前、通話中、通話後で異なるモデルを使うと説明されました。

通話の開始時には、それまでの顧客との接点を要約します。通話中には、会社のガイダンスや技術的な解決方法を持つナレッジベースを参照して、回答を支援します。通話後は、やり取りと解決内容、今後改善できる点を要約します。

この部分は、担当者が十分な情報を持つことで、顧客へよりよい対応を提供するという位置づけです。これらの場面を一つずつ操作したライブ実演ではなく、利用方法の説明でした。

### 5.6 二つ目の実演：「何が起きたか」と「なぜか」で情報源を変える

次の例では、コールセンターの分析機能に加え、ほかの業務ロジックを含む独立したナレッジベースを使います。

「解約がどう推移したか」のような定量的な質問は、先ほどの **AskTranscript** のバックエンドへ送ります。一方、「何が解約と関連し得るか」という質問では、業務運営で得た知識を参照します。発表では、候補となる要因が五つか六つあると説明しています。

エージェントは情報源を振り分けるだけでなく、両者を組み合わせます。業務知識から調べる候補を得て、その候補について集計や回帰を行い、実際に関連があるかを調べる流れです。

画面上では青と緑の点が、どの情報源から取得したかを示すと説明されました。ただし、使用したエージェント実装の名称は音声認識が不明瞭です。特定のライブラリ名へ推測で置き換えてはいません。

### 5.7 8 組織へ広げ、重複した開発を避ける

AT&T 内では、コールセンター以外も含めて **8 組織** が基盤を利用していると説明しています。

従来は各部門がそれぞれパイプラインを作っていました。共通基盤なら、すでに生成された要約や分析結果を出発点にできます。これが重複コストの回避（cost avoidance）、つまり同じ費用を二重に払わずに済む効果です。

また、ケア（カスタマーケア）、マーケティング、ネットワークの各部門の責任者からの質問に、既存の分析情報で答えられる場面が増えています。以前はアナリストに依頼して数日かかっていた問い合わせを、より直接的に調べられるという説明でした。全質問が同じ秒数で解けると保証したものではありません。

### 5.8 次の段階：オントロジーとナレッジグラフ

終盤では、検索の発展を次のように整理しています。

1. **単一の情報源**：取り込んだ文書には答えられても、外側にある情報を逃します。
2. **複数情報源のナレッジベース**：横断して取得できますが、業務の意味がないと、誤った情報同士を結び付ける可能性があります。
3. **オントロジー**：業務上の概念やプロセスを明確にし、何を調べるべきかを導きます。
4. **ナレッジグラフ**：エンティティ（対象）や業務領域間の関係を表し、つながりを使って情報を取得します。

AT&T では、店舗や現場の技術担当者も含む複数チャネルから顧客を理解する **カスタマージャーニーマッピング** を進めています。ナレッジグラフの採用は、この統合を支える今後の検討として述べられました。

さらに、部門ごとに別のオントロジーを作る問題があります。Microsoft IQ の導入手引き（playbook）について、共有・再利用できるオントロジーの階層を作る方向が説明されました。これも、AT&T の全組織で稼働済みという紹介ではありません。

## 6. デモ・手順

セッション内では、二つの画面デモが行われています。

**一つ目：解約の定量分析**

1. 直近 7 週間の解約について、自然言語で質問します。
2. 参照例、テーブル、列を使って SQL を組み立て、実行する流れを確認します。
3. 週別の結果を確認します。
4. 解約増加と競合他社への言及の関連を追加で質問します。
5. 回帰・相関の分析結果を確認します。

**二つ目：定量データと業務知識の組み合わせ**

1. 定量的な質問を、AskTranscript のバックエンドで調べます。
2. 背景要因を尋ねる質問では、独立した業務知識を参照します。
3. 取得元の違いを画面の表示で確認します。
4. 得られた要因を、定量分析と組み合わせる考え方を示します。

SQL の全文、テーブルの実名、画面操作のすべては読み上げられていません。そのため、そのまま再現できるセットアップ手順やコードとしては記載していません。

## 7. 注意点・発表者の気付き

**共通基盤が使えることと、業務の意味が自動でそろうことは別です。** 同じ用語が異なる意味を持つ場合を考え、オントロジーと関係性を整える必要があります。

また、非構造化データを 246 項目へ構造化している点は、この実演の前提です。任意の会話記録を渡すだけで、同じ SQL 分析が直ちにできるという説明ではありません。

ほかの業界にも同じパターンを適用できるとしていますが、その前提には、十分なデータと業務プロセスがあることを挙げています。金融、医療、小売、部門横断の人事（HR）や財務が例示されました。

最後は会場での質問を促して終わっており、録音内には具体的な聴衆との質疑応答はありません。

## 8. 利用者にとっての利点

AT&T の説明で具体的なのは、各部門が同じ取り込み処理を作らずに済むことです。蓄積済みの要約と分析項目を再利用し、次の用途へ展開できます。

業務側は、SQL の作成を依頼する前に、自然言語で推移や関連を確認できます。定量的な結果だけでなく、背景となる業務知識を同じ対話へ持ち込める点も、二つ目の実演で示されました。

コールセンターの担当者には、過去の接点、会社の指針、技術的な解決策を適切な場面で届けます。発表では、従業員を情報面で支えることを、顧客対応の改善につなげています。

## 9. まとめ

AT&T の取り組みは、会話記録を検索対象にするだけで終わりません。共通パイプラインで要約と分類を作り、構造化した結果を自然言語から分析し、必要なら別の業務知識も組み合わせます。

現在の本番基盤で得られた再利用の効果と、今後のナレッジグラフの検討を分けて読むことが大切です。そのうえで、データの意味と関係を共有できる形に整えることが、複数部門へ広げる鍵として示されています。
