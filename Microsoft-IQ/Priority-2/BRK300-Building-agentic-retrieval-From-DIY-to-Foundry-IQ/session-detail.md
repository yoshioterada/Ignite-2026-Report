# BRK300 Building agentic retrieval: From DIY to Foundry IQ

## 1. はじめに

このセッションは、エージェント型検索（agentic retrieval。エージェントが検索の計画・結果の点検・再検索を繰り返して答えを探す方式）を、開発者が自前で組む場合と、Foundry IQ の組み込み機能で実現する場合とで比べる発表です。架空のチョコレート会社 Coco Rinth の社内文書を題材に、実際に動くデモを見せながら進みます。

前半では、Python の開発者としてゼロから組み立てる流れが紹介されます。単純なハイブリッド検索から始め、複合質問、多段（マルチホップ）質問、処理の複雑さを見分ける分類器（ルーター）へと、質問が難しくなるたびに部品を足していきます。後半では、Foundry IQ が Ignite で公開した検索特化モデル **Microsoft Retriever One**（パブリックプレビュー）と、段階的に処理を引き上げる **auto 検索推論レベル**が紹介されます。結論として、発表者は Coco Rinth のシナリオでは Foundry IQ の組み込み方式が優位だと述べています。そのうえで、自分のデータで評価して選ぶよう勧めています。

## 3. 何に関する発表か

Foundry IQ は、エージェントが仕事に必要な文脈を得るための仕組みです。ナレッジベース（knowledge base）を作ると、裏側でエージェント型検索エンジンが動きます。組織内に散らばった情報の置き場をナレッジソースと呼び、それらをまとめて検索します。発表では、取り込みパイプラインや最先端の検索技術を備えていることも挙げられました。

題材の Coco Rinth は、単一産地のチョコレートバーを作る会社という設定です。文書は PDF、PowerPoint、DocX など形式が多様で、英語とスペイン語が混在し、図表も含みます。質問者も多様で、例えば小売店は「ガーナ産のバーが灰色で粉っぽくなったのはなぜか、ロット全体が不良か」を、購入者は「このバーのカカオはどの農園産か」を知りたがります。目標は、単純な事実確認から複数文書をまたぐ質問まで答え、回答のたびに引用を示し、速く安く動かすことです。

発表の流れは次のとおりです。

1. ベースライン：ハイブリッド検索
2. 複合質問とクエリ計画
3. 多段質問と振り返り
4. 複雑さの分類（ルーティング）
5. Foundry IQ の Microsoft Retriever One
6. auto 検索推論レベルによる段階的な引き上げ
7. DIY と組み込みの比較、価格、まとめ

## 4. 発表者が伝えたいメッセージ

質問の種類によって必要な検索の手間は大きく違います。簡単な質問に毎回フルのエージェント処理を使うと、遅延とトークンのコストが無駄になります。DIY ではこの問題を解くためにクエリ計画、振り返り、ルーターを自分で作り、プロンプトと閾値を保守し続けることになります。

これに対して Foundry IQ は、最初に検索してしまい、結果が良ければそこで終わる方針をとります。結果が不十分なときだけ、専用に調整した小さなモデル（Microsoft Retriever One）が次のクエリを決め、それでも難しい質問だけ大きな LLM に渡します。発表では、これによりルーターなしで速度とコストを下げられると説明しています。一方で、LLM に回す頻度が減るぶん、集まる根拠が完全でない場合があるというトレードオフも明言されました。

## 5. 発表内容の詳細

### 5.1 ベースライン：ハイブリッド検索

最初の DIY 方式は、Foundry IQ の検索インデックス（1 つ）に対するハイブリッド検索を、エージェントの検索ツールとして呼ぶだけの構成です。デモの質問は「2026 年 9 月の単一産地バーのテイスティング審査で優勝した産地はどこか、風味の特徴は何か」でした。回答はマダガスカル、Zarabola、70%、風味は赤い実とラズベリー、柑橘の皮、明るくバランスの良い酸味、低い苦味です。

処理の中身は、エージェントが書き換えたクエリで検索を 1 回呼び、5 件の結果が返るというものです。結果は文書のチャンクで、中にはグラフを説明したチャンクもあります。各結果にはもとの検索スコアと、Foundry IQ のリランカーによる再順位付けスコアが付きます。コードでは公式 SDK で、クエリ、そのベクトル埋め込み、セマンティックランキングを指定し、上位 5 件を取得しています。

ハイブリッド検索の構成は次のとおりです。

| 要素 | 役割 |
| --- | --- |
| キーワード検索（BM25） | 完全一致に強い。月や年のような値（2026 と 2025 の区別）を拾う |
| ベクトル検索 | 意味が近いものを拾う。数字は同じように見えやすく不得意。埋め込みモデルは多言語対応なので、スペイン語の質問や文書にも対応 |
| 逆順位融合（reciprocal rank fusion） | 両方の結果を、それぞれの順位に基づいて並べ替えて統合する |
| セマンティックランキング | 専用モデルが元の質問と統合結果を見て並べ替え、各チャンクの関連度スコアを付ける |

スコアが低すぎる結果を捨てる判断もできる、と説明されました。この構成は数年前から使えますが、質問の大部分に対応できる強力な基準線だと位置づけられています。

### 5.2 複合質問とクエリ計画

複合質問とは、複数の質問を 1 つにまとめた質問のことです。例は「テイスティング審査はマダガスカルのバーをどう評価したか、その豆のロットはなぜ入荷時に保留されたか」です。この質問をハイブリッド検索 1 回で処理すると、クエリは 1 つだけで、回答には赤い実の記載しかなく、完全な審査の記録が含まれないと表示されました。ラズベリーも柑橘も欠けています。1 つのクエリで両方を満たそうとして、結果が片方に偏ったためと説明されています。

そこで加えるのがクエリ計画（query planning）です。LLM に質問を複数のクエリへ分解させ、並列に検索し、リランカーのスコアなどで統合します。デモでは、審査の全メモと保留の理由の両方が得られました。クエリ計画には GPT-55（推論は medium）を使い、2 つのクエリを作るのに 2.6 秒かかりました。検索自体はそれより速く、2 つの検索は並列に実行されました。精度が上がる代わりに処理が増えることが、画面の遅延表示で示されています。

### 5.3 多段質問と振り返り

多段（マルチホップ）質問は、最初の検索結果に含まれる手がかりを使って、次の検索を行わないと答えに届かない質問です。検索エンジン向けの宝探しのようなものだと説明されました。例は「マダガスカル限定版バーの発売を遅らせた、農園での出来事は何か」です。質問文には農園名もビーンロットの ID も出てきません。1 回目の検索で ID などの手がかりを含む文書が見つかり、2 回目でその ID を検索して答えが得られる、という構造です。

クエリ計画だけの構成では、「その農園で特定の出来事の記録はない」という回答になりました。計画は適切だったものの、返された 5 件に答えがなかったためです。

そこで振り返り（reflection）の段階を足します。LLM に、元の質問と検索結果を渡して、この結果で十分か、明らかな次の検索があるかを判断させます。同じ質問で、4 日間の大雨を受けたという答えが得られました。LLM が出力するのは、十分かどうか（はい・いいえ）、足りないものは何か、次に実行すべきクエリです。次のクエリには、元の質問に欠けていた ID が含まれ、並列に検索されました。その後もう一度振り返り、十分と判断して完了します。

その代償として、検索にかかる時間は合計約 12 秒になりました。最も長かったのは振り返りの段階で、約 5 秒です。質問と全結果を渡すため文脈が大きくなり、LLM の処理が長くなるためです。この段階では GPT-55 の推論レベルを low にしています。クエリ計画、振り返り、最終の振り返りと LLM を 3 回呼ぶため、すべての質問にこの経路を使うと、遅延もトークンコストも大きくなると説明されました。

### 5.4 複雑さの分類（ルーティング）

簡単な質問（例：チョコレートの適切な保管温度は）にまで同じ処理は不要です。そこで複雑さを判定する分類器を前段に置き、難しい質問だけフルのエージェント型検索に回し、簡単な質問は直接検索します。この種のルーティングは、エージェントの構成でよく追加される手法だと説明されました。

デモでは、判定に Microsoft の Decision One モデルを使っています（音声認識の都合で、モデル名の表記は確定できません）。発表者は、判定が速いことがルーターの目的に合うと述べ、OpenAI 側の別の API も Azure で使えるが今回は選ばなかったと補足しています（この部分の名称は音声認識の都合で確定できません）。簡単な質問では、正しい回答と引用が返り、ルーティングに 1.1 秒、その後に検索という内訳が遅延の図に表示されました。ルーターは、直接検索かエージェント型かの確率も返します。多段質問ではエージェント型の経路が選ばれ、正しい判断でした。

ルーターには注意点があります。発表者の Pamela は、自分でルーターを書いた経験から、正しい判断を安定して下すのはとても難しいため、普段ルーターをあまり使わないと述べています。GitHub Copilot では、どのモデルを選ぶべきかを多数の例題で学習させたルーターが使われている、との補足もありました。ルーターを入れるなら、想定する質問で正しく振り分けているかを確かめる評価が必要です。簡単な経路に誤って振ると情報を取りこぼし、難しい経路に不要に振るとコストがかさみます。完全にはならないため、取りこぼしを許容して安く済ませるか、コストをかけて精度を取るかの釣り合いを決めることになります。ルーターには、バランス、最大効率、最大精度といったつまみが付く場合が多い、とも説明されました。

### 5.5 Foundry IQ の組み込み方式：Microsoft Retriever One

Matt は、Foundry IQ のエージェント型検索を整理しています。ナレッジベースを定義し、LLM を指定すると、LLM が入力された会話や質問に対して最初にクエリ計画を立てます。複数のナレッジソースにハイブリッド検索をかけ、出力を評価し、十分と判断したら終了します。複雑な質問に対応できる点は DIY と同じですが、毎回最初に計画する必要があるのかが課題でした。

そこで Foundry IQ チームは、専用のモデルを自分たちで微調整しました。それが **Microsoft Retriever One** です（パブリックプレビュー）。戦略は、DIY の最初の方式と同じく、先に検索することです。最初の検索で良い結果が出れば、それで終わりです。このモデルは次の 2 点を得意とするよう学習されています。

1. 検索クエリと結果を見て、結果がクエリに合っているかを判断する
2. 合っていない場合に、より良い結果を得るための次のクエリを出す

導入は簡単で、Microsoft Retriever One は Foundry IQ に組み込まれているため、自分でデプロイする必要はありません。ナレッジベースで使うモデルを切り替えるだけです。Foundry IQ には検索推論レベル（retrieval reasoning effort）という設定があり、クエリにかける時間と労力を決めます。今回は最小（minimal）にして、できるだけ速く処理させています。

### 5.6 Microsoft Retriever One の実測と評価

同じ多段質問（農園での出来事）で、正しい答えが得られました。検索は 1 秒未満で終わり、最初に検索を発行し、すぐに判断しています。この例では、インデックスの検索のほうが、結果の振り返りと新しいクエリの計画より時間がかかったと説明されました。小さな専用モデルが、大きなモデルと同じ結論に短時間でたどり着いた形です。

時間の内訳を比べると、DIY ではクエリ計画が大半を占め、検索は約 0.5 秒、そのあと振り返りと、停止を決める最後の振り返りがあり、LLM を 3 回呼びます。Foundry IQ の組み込み方式では、検索、振り返り、計画の各段階がほぼ同じ短い時間で終わります。

評価は Coco Rinth のデータだけでなく、公開データと企業の非公開データの混合で行われました。得られた要点は次のとおりです。

- Microsoft Retriever One を有効にすると、検索の品質が上がった。品質は、質問に答えるのに必要な事実が得られているかで測り、約 8 ポイントの向上
- 検索を呼び出すエージェント側が主導する構成で、GPT 6.1 SOL に Microsoft Retriever One 付きの検索ツールを持たせると、使わない場合に比べてトークンが約 3 分の 1 減った（モデル名は聞こえた表記のままで、音声認識の都合で確定できません）

エージェントが「結果は十分か」と悩み、ツール呼び出しを重ねるためのトークンを使わずに済む、という説明でした。評価の詳細はブログで読めると案内されています。

### 5.7 auto 検索推論レベル：ルーターなしの段階的な引き上げ

DIY 側で挙がった複雑さのルーティングは、Foundry IQ では別の方法で扱います。8 月に導入された auto 検索推論レベルは、複雑さを前段のモデルで判定する代わりに、簡単な処理から順に試す段階（エスカレーション）方式です。当時は、クエリを実行して、リランカーから見て結果が良ければ完了、良くなければ LLM による従来の完全なエージェント型検索ループに移っていました。

Microsoft Retriever One の追加で、**検索 → Microsoft Retriever One → LLM** という組み合わせ（アンサンブル）に変わりました。LLM は、Microsoft Retriever One でも手に負えない質問のためだけに使います。設定は、モデルの一覧に Microsoft Retriever One と LLM を入れ、検索推論レベルを auto にするだけです。

デモは 3 つの質問で行われました。

1. 簡単な質問（チョコレートバーの推奨保管温度）：約 200 ミリ秒で回答。検索結果が十分な根拠を含むため、すぐに返す。ルーターを呼ばずに、ルーターがあるのと同じ効果を得られる
2. 多段質問（農園での出来事）：Microsoft Retriever One だけを使った場合と同じ流れ。検索し、結果が良くないと判断し、Microsoft Retriever One が再検索を指示し、再検索で良い結果を得て完了。2 段目までしか上がらない
3. 最も難しい複合質問（審査の評価と保留の理由）：初回検索の後、Microsoft Retriever One が難しすぎると判断して次の段階に上げる。GPT 5.5 が検索を担当し、ここで初めてクエリ計画のコストを払う。複数の検索を出し、リランカーが良好と判断したため、最後の振り返りは不要だった

古い auto では、中程度の難しさの質問でも常に LLM に上がり、その割合は約 80% でした。Microsoft Retriever One を加えた現在は、LLM に上がらずに処理できる質問が半分強に増えたと説明されています。結果として、検索時間の中央値は 1 秒未満になり、トークンは約 70% 減ります。ただし LLM に上げないぶん、集まる根拠が完全でないことがあり、これは auto を採用するトレードオフです。多くの場合は妥当な判断だと見込み、改善を続けている、とのことです。

### 5.8 DIY と組み込みの比較

Coco Rinth のデータで直接評価した結果が、質問の種類ごとに紹介されました。

| 質問の種類 | 組み込み方式の傾向 |
| --- | --- |
| 簡単な質問 | 複雑さの分類のためのモデル呼び出しが 1 回なくなる。LLM をあまり呼ばないのでコストが大幅に下がる |
| 複合質問（クエリ計画が必要） | 結果は分かれる。Microsoft Retriever One が一部を処理できるので時間は短くなるが、LLM に直行せず段階を踏むため、コストはやや増える。それでも大幅に速い |
| 多段質問 | DIY では毎回振り返りと LLM による計画が必要。組み込み方式では Microsoft Retriever One が効率よく処理でき、大幅に速く、大幅に安い |

自分で持つべきものも対比されました。DIY では、クエリ計画の方法、振り返りの方針、ルーティング、プロンプトの保守、各種閾値の調整をすべて自分で持ちます。Foundry IQ では、MCP に対応したナレッジベースをエージェントに接続するだけで、検索ツールが 1 つ使えるようになります。利用者が持つのは、知識の置き場所の定義と、質問と回答に対する評価です。DIY のエージェント型検索ループを、検索ツールの呼び出し 1 回に置き換える、という表現でした。

価格は、Microsoft Retriever One が入力 100 万トークンあたり 10 セント、出力トークンは無料と説明されました。コストが見通しやすく、簡単な質問ではトークンが減り、使うトークンの単価も LLM より安いという主張です。Coco Rinth の多段質問の例では、14 倍速くなったとされています。

ナレッジベースをまだ採用していなくても、Microsoft Retriever One は使えます。これまでの検索ではクエリの種類（query type）にセマンティックを指定していましたが、Foundry IQ に新しいエージェント型のクエリ種別（agentic）が加わりました。既存の検索クエリで、この種別を選べば Microsoft Retriever One が使えます。デモのアプリでは、1 行を差し替えるだけで時間とトークンを節約できる、と Pamela が述べています。

## 6. デモ・手順

デモは行われました。サイトに質問を入力し、回答、検索の過程、時間の内訳（遅延のウォーターフォール）が画面に表示される形式です。画面の細部は音声からは確認できないため、発話で語られた範囲を、実施順に整理します。

1. **ベースライン（ハイブリッド検索 1 回）**：優勝した産地と風味の質問。回答、書き換えられたクエリ、5 件のチャンク（グラフの説明を含む）、元スコアとリランカーのスコアを表示した。検索コードの概要も示した
2. **複合質問（ハイブリッド検索のみ）**：保留の理由と審査評価を含む質問。赤い実の情報しか得られず、完全な審査記録が出ないため失敗した
3. **クエリ計画を追加**：同じ質問で、審査メモと保留の理由の両方を取得。計画に 2.6 秒、2 つの検索は並列
4. **多段質問（クエリ計画のみ）**：農園での出来事は見つからず、記録がないとの回答になった
5. **振り返りを追加**：4 日間の大雨という答えが得られた。合計約 12 秒、振り返りが約 5 秒。振り返りが十分かどうか、不足、次のクエリを返し、2 段目の検索を行い、再度の振り返りで終了した
6. **複雑さの分類を追加**：簡単な質問は正しい回答と引用を返し、分類に 1.1 秒。多段質問ではエージェント型の経路が選ばれた
7. **Microsoft Retriever One（検索推論レベルは minimal）**：多段質問で正しい答えを 1 秒未満で取得。DIY との時間の内訳を比較した
8. **auto 検索推論レベル**：簡単な質問（約 200 ミリ秒）、多段質問（Microsoft Retriever One まで）、最も難しい複合質問（LLM まで）の 3 つを実行し、段階の流れを確認した

デモで使ったコードは、リポジトリで公開されていると案内されました。

## 7. 注意点・発表者の気付き

- ルーターは調整が難しく、評価用の質問集で判断の正しさを検証する必要がある。取りこぼしとコストの釣り合いを決める必要がある
- 複数クエリへの分解や振り返りは精度を上げるが、LLM の呼び出しが増え、遅延とトークンコストが大きくなる。文脈が大きいほど LLM は遅くなる
- 紹介された数値は、Coco Rinth のデータと、公開・非公開データでの発表者側の評価結果です。発表では、自分のデータと質問で評価するよう勧めています
- auto は LLM に上げる頻度を下げるため、根拠の完全さを少し犠牲にする場合がある
- 同じ検索推論レベルの設定で、時間と労力が変わる。モデルと推論レベルの選択でも時間は大きく変わる
- Microsoft Retriever One は Ignite で発表された直後（発表時点で 3 日目）で、パブリックプレビューである

## 8. 利用者にとっての利点

- 簡単な質問は検索 1 回で返し、難しい質問だけ段階的に LLM へ上げるので、時間とコストを質問ごとに最小化できる
- ルーターの構築・調整・保守が不要（ルーターなしで同様の効果）
- 検索品質の向上（約 8 ポイント）、エージェント側のトークン削減（約 3 分の 1）、auto でのトークン約 70% 減と検索時間の中央値 1 秒未満
- Coco Rinth の多段質問で 14 倍高速
- 価格は入力 100 万トークンあたり 10 セント、出力は無料で、見通しが立てやすい
- MCP 接続でナレッジベースを使え、既存の検索クエリも agentic クエリ種別への切り替えで Microsoft Retriever One を使える

## 9. まとめ

ハイブリッド検索を土台に、クエリ計画、振り返り、ルーターを足していく DIY の方式は、質問の難しさに応じて精度を上げられますが、遅延・コスト・保守の負担が増えます。Foundry IQ は、先に検索し、結果が不十分なら Microsoft Retriever One、それでも難しければ LLM という段階で処理し、同等の質問に速く安く答えます。

自分のシナリオでどの経路が合うかは、質問の種類、遅延、経路の選ばれ方を自分のデータで評価して決めるよう勧められました。発表後にはハンズオンのラボが 2 回（当日と翌日）予定され、新しいグラフ機能も試せると案内されています。ラボでは、試した参加者が「とても速いので、明日からこちらに切り替えたい」と驚いていた、という紹介もありました。Microsoft Retriever One の評価の詳細はブログに、デモのコードはリポジトリにあります。
