# THR993 Secure Workplace in the AI Era: An End-to-End Live Demo

## 1. はじめに

このセッションは、ユーザーが毎日行う作業（サインイン、社内ファイルサーバーや社内サイトへのアクセス、AI エージェントの利用、メール送信、外部の生成 AI サービスの利用）を 1 本の流れで見せながら、Microsoft の複数のセキュリティサービスがどう連携してユーザー体験を損なわずに保護するかを示すデモ中心の登壇です。登壇者は、ID 管理、デバイス管理、オンプレミスへのアクセス、DLP などを別々のサービス・ベンダーで持つと、それらを一体で動かしてシンプルな体験にするのは大変だ、という問題意識から話を始めています。

デモは前半が「パスワードを使わない認証と、ゼロトラストのアクセス」、後半が「AI 時代のデータ保護（Copilot、Cowork、メール、エンドポイント、外部 AI サービス）」という構成です。

このセッションのデモは**事前録画**です。登壇者は、録画にした理由を「デモに自信がないからではなく、安定した Wi-Fi を誰かと奪い合いたくないから」と冗談めかして説明しています。また、カットなしで実機の画面をそのまま見せると述べています。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR993](https://ignite.microsoft.com/en-US/sessions/THR993)

テーマは、Microsoft 365 のセキュリティ機能を組み合わせ、「安全で、しかも使いやすい」職場の体験を作ることです。登壇者は「セキュリティは、ユーザーに使ってもらうために複雑であってはならない。ユーザー体験はできる限りシンプルでなければならない」と述べています。

発表の流れは次のとおりです。

1. 導入：複数のサービス・ベンダーを組み合わせる難しさと、ユーザー体験にフォーカスしたデモの趣旨
2. ID と認証：Temporary Access Pass による Windows Hello for Business の登録
3. オンプレミスのレガシーリソースへのアクセス：ファイルサーバー、リモートデスクトップ、イントラネットサイト
4. 管理されていないデバイスからのアクセスを制御する Conditional Access
5. AI 時代のデータ保護：Cowork での機密データ作成、秘密度ラベル、Copilot・Outlook・エンドポイントでの DLP、未承認 AI サービスのブロック

## 4. 発表者が伝えたいメッセージ

登壇者が繰り返すのは、強い認証や制御は、ユーザーの手間を増やさずに実現できるという点です。パスワードなしでレガシーなオンプレミスのリソースにまでアクセスでき、それでいてゼロトラストのネットワークアクセスに沿っている、という構成を見せています。

もう 1 つは、AI エージェントが使われる時代に、ユーザーが見る警告やポリシーのヒントは、人間のユーザーに向けたものであって、エージェントには届かない場面がある、という気付きです。Cowork が自分の代わりに機密文書をメールで送ってしまった場面で、それが示されます（5.5 参照）。

最後の総括は、「認証、アクセス制御、DLP ポリシーまで、すべてのソリューションをどう組み合わせて、安全で使いやすい体験をユーザーに提供するか」です。

## 5. 発表内容の詳細

### 5.1 導入：サービスの乱立という課題

登壇者はまず会場に、ID・アクセス管理、デバイス管理、オンプレミスのリソースへのアクセス（VPN ではなく、オンプレミスリソースへのアクセスを与える仕組み）、DLP ポリシーなどについて、環境にいくつサービスやベンダーがあるかを考えるよう求めました。2 つ以上あるなら「その苦労は分かる」として、それらを一体で動かし、使いやすいインターフェースと体験を提供することの難しさを挙げています。デモはユーザー体験に焦点を当て、ユーザーが日常的に行う主要な作業を Microsoft 365 がどう支えるかを示します。

### 5.2 ID と認証：Temporary Access Pass と Windows Hello for Business

すべては ID 管理と認証から始まります。

登壇者は、ユーザーが安全な認証方法を登録する流れを見せています。これは既定の構成ではなく、**web sign-in** を追加した構成で、管理者がユーザー向けに **Temporary Access Pass** を作成し、それを使って Windows Hello for Business などの認証方法を登録させます。Temporary Access Pass はパスワードではなく、管理者が用意した、時間が限定されたものです。これを使って、ユーザーに使わせたい他の認証方法を登録（enroll）するという考えです。デモでは Windows Hello for Business の設定が行われ、これで「最も安全な、フィッシングに耐性のある認証方法」が揃った、と説明しています。

サインアウトしたあと、サインインオプションとして次のものが表示されました。

- web sign-in
- セキュリティキー（「UbiKeys」などと発話。音声認識の綴りのままです）
- PIN
- ハードウェアが対応していれば、顔認証や指紋認証

デモでは PIN だけを使っています。Windows Hello for Business を使うことが、後でなぜ重要になるかを説明するとしています。

### 5.3 オンプレミスのリソースへのアクセス

登壇者の設定では、デバイスはサンフランシスコにあり、ファイルサーバーはヨーロッパのデータセンターにあります。

**ファイルサーバー**：ユーザーはパスワードなしでアクセスできます。**Cloud Kerberos trust** が有効で、Active Directory のリソースがこの認証を受け入れるためです。登壇者は、ユーザー体験はシンプルで便利なのに、このアプローチは **ゼロトラストネットワークアクセス（ZTNA）に準拠**している、と述べました。技術的な仕組みは後で図で示すと予告しています。

**リモートデスクトップ**：サーバーへのアクセスに、フィッシング耐性のある認証だけを使わせたい、というケースです。Windows Hello for Business で認証されたユーザーがリモートデスクトップサービスにアクセスします。パスワード入力はなく、シングルサインオンで、PIN での認証だけです。

**イントラネットサイト**：HTTP ベースの文書管理システムやオンプレミスの SharePoint など。登壇者は、インフラの構成を示すスライドを見せ、写真を撮ってもよいと述べています。構成の説明は次のとおりです。

| アクセス対象 | 使う仕組み |
| --- | --- |
| HTTP ベースのイントラネット | Microsoft Entra application proxy |
| RDP、SMB など他のプロトコル | private access |

登壇者は、これがゼロトラストネットワークアクセスのアプローチだと説明しています。ここまでで、安全な ID、安全な認証、オンプレミスのレガシーリソースへの安全なアクセスを見たことになります。

> 補足：「private access」の正式な製品名は、音声からは「private access」としか確認できません。

### 5.4 管理されたデバイスの強制：Conditional Access

次に、管理されたデバイスだけが使われるように、リソースへのアクセスをどう制御するかです。登壇者は意図的にプライベートブラウザーのセッションを開きました。プライベートセッションでは、使っているデバイスの情報が Microsoft Entra に渡らないため、Entra にはそのデバイスが準拠しているか（compliant）、管理されているかが分かりません。管理されていないデバイスから接続した場合のユーザー体験を、デモ用に再現するための操作です。

同じイントラネットサイトに、同じ Temporary Access Pass で認証します。「サインインは成功した」というメッセージが出ますが、登壇者は、管理されていないデバイスからリソースにアクセスしてほしくない、それを実現するのが **Conditional Access（条件付きアクセス）** だと述べています。登壇者の考えでは、これは、ユーザーが管理されたデバイスからリソースにアクセスしていることを担保する、最も重要なサービスです。

> 補足：音声からは、リソースが最終的にどう拒否されたかの画面表示（メッセージの文言など）は確認できません。「サインインは成功したが、ポリシーによりリソースへはアクセスさせない」という趣旨の説明です。

### 5.5 AI 時代のデータ保護

デバイスは **Microsoft Defender for Endpoint** で保護されており、さまざまな制御があります。ここから登壇者は、ユーザーが日常的に使う AI の話に移ります。

**Cowork で機密データを作る**：Cowork（音声では「co-work」。ツールの正式名は音声からは確認できません）を開き、リトアニアの個人コード（personal code）のダミーデータを作って、デスクトップに保存するよう依頼します。リトアニアでは非常に機微な情報として慎重に扱うべきものだ、という説明です。Cowork がドキュメントを作成し、登壇者は保存アクションを承認します。ファイルがデスクトップに現れます。登壇者は、Cowork がユーザーの代理で動くエージェントである点も強調しました。

**秘密度ラベル**：登壇者は、ユーザーとして、Cowork が生成するデータに自分が責任を持つ立場であり、それを分類するのが自分だと述べています。組織が用意した秘密度ラベル（sensitivity labels）があり、情報の所有者としてラベルの選択を求められるので、この例では **Internal** を選んで保存します。

**Copilot の DLP**：Copilot とチャットし、作成した文書をレビューするよう依頼します。文書は非常に機微ですが、Copilot はこの情報が機微であることを理解し、組織が Copilot に渡すことを許可していない、という旨を表示します。登壇者は、これは **Microsoft Purview DLP for Copilot** のポリシーが働いている状態だと説明しました。

**Outlook の DLP**：友人に文書のレビューを頼むメールを送る場面です。メールの分類（ラベル）を求められ、登壇者は、社内向けの情報は社外に送るべきでないと分かったうえで、あえて **public** を選びます。すると、これはセキュリティチームが期待する行動ではないと通知され、続行するには理由の入力（justify）が必要になります。登壇者は理由を入力せず先へ進みます。これは Exchange 向けの DLP ポリシーと、ユーザーに警告するポリシーヒントです。

**Cowork が代理でメールを送る**：次に Cowork に、同じ文書を社外に送るよう依頼します。メールが準備され、登壇者がアクションを承認すると、メールは送信されます。登壇者の説明では、Outlook で見たコントロールと通知は、エージェントではなくユーザーが見るためのものなので、機微な情報を含むファイルは登壇者の代理で送信されてしまった、ということです。

> 補足：このあと登壇者は Outlook に戻り、「Cowork はファイルを送れたが、Exchange の DLP ポリシーがそれを止められた。ユーザーとして、エージェントが組織の期待しないことをしたと通知された」と述べています。直前の「送信された」という説明との関係（送信を止めたのか、送信後に通知したのか）は、音声だけでは明確に確認できません。

**エンドポイント DLP**：文書を別の場所に置こうとして、ファイルサーバーにファイルをアップロードします。この操作はブロックされ、組織が許可していない場所にファイルを置けませんでした。登壇者は、これが **Microsoft Purview DLP for endpoint** だと説明しています。

**未承認の外部 AI サービス**：デモ用に用意したダミーの AI サービス（第三者の生成 AI ソリューション）を開くと、「この AI ツールは組織によって承認されていません」というメッセージが表示されます。

### 5.6 未承認サービスをブロックする仕組み（Defender）

登壇者は、最後のデモに関わる仕組みを次のように説明しました。

1. 管理されたデバイスでは **Microsoft Defender for Endpoint** が動いており、ユーザーが使っているサービスの情報を **Microsoft Defender for Cloud Apps** に渡す。
2. Defender for Cloud Apps に、ユーザーが新しく使い始めたサービスを unsanction（未承認に指定）するポリシーを作れる。
3. unsanction されたサービスの URL が Defender for Endpoint に戻される。
4. Defender for Endpoint がそれらのサービスの利用をブロックする。

## 6. デモ・手順

このセッションでは、**事前録画のデモ**が全体を占めています（冒頭で「プレゼンは録画。カットなし、実機の画面」と説明）。録音は音声のみなので、画面の細部は音声から確認できません。語られた順番は次のとおりです。

1. 現在のセッションからサインアウトし、既定ではない構成（web sign-in を追加）のサインイン画面を見せる。
2. ユーザーが管理者の発行した Temporary Access Pass を入力し、Windows Hello for Business を設定する。
3. サインアウトして、サインインオプション（web sign-in、セキュリティキー、PIN など）を確認し、PIN で認証する。
4. ヨーロッパのデータセンターにあるファイルサーバーに、サンフランシスコのデバイスからパスワードなしでアクセスする（Cloud Kerberos trust）。
5. Windows Hello for Business の認証とシングルサインオンで、リモートデスクトップに接続する。
6. HTTP ベースのイントラネットサイトへのアクセス方法を、構成図を使って説明する（Microsoft Entra application proxy と private access）。
7. プライベートブラウザーのセッションを開き、同じイントラネットサイトに Temporary Access Pass でサインインする。「サインインは成功」と表示されるが、管理されていないデバイスなので Conditional Access の対象になる。
8. Cowork に、リトアニアの個人コードのダミーデータを作成してデスクトップに保存するよう依頼し、保存アクションを承認する。
9. 秘密度ラベルとして Internal を選び、保存する。
10. Copilot にその文書のレビューを依頼する → Purview DLP for Copilot のポリシーにより、渡せない旨が表示される。
11. 友人宛のメールで分類に public を選ぶ → 組織の期待に反するとの通知、理由の入力が必要。入力せずに先へ進む。
12. Cowork に同じ文書を社外に送るよう依頼し、送信アクションを承認する。
13. ファイルサーバーに文書をアップロードしようとして、ブロックされる（Purview DLP for endpoint）。
14. Outlook に戻り、Exchange の DLP ポリシーと通知について触れる。
15. 第三者の生成 AI サービスを開き、「この AI ツールは組織によって承認されていません」と表示される。

## 7. 注意点・発表者の気付き

- **エージェントには、ユーザー向けの警告が見えません。** Outlook のコントロールと通知は、エージェントではなく、人間のユーザーに見せるためのものだと登壇者は述べています。Cowork が代理で機密ファイルを送信できてしまった場面が、その例です。
- ユーザーは、エージェントが生成するデータに責任を持つ立場で、情報の所有者として秘密度ラベルを付ける、という考え方が示されました。
- Conditional Access では、サインイン自体は成功しても、管理されていないデバイスからは組織のリソースにアクセスさせない、という点が強調されています。登壇者は、これが管理されたデバイスの利用を担保する最も重要なサービスだという意見を述べています。
- プライベートブラウザーを使うと、デバイスの情報が Entra に渡らず、デバイスが管理されているかを判定できません。これはデモ用に未管理デバイスの状況を再現する手法として使われています。

## 8. 利用者にとっての利点

登壇者が示した効果は、定量的な数値ではなく、ユーザー体験と制御についてのものです。

- パスワードなしで、レガシーなオンプレミスのリソース（ファイルサーバー、リモートデスクトップ、イントラネット）にもアクセスでき、ゼロトラストネットワークアクセスに沿う。
- Temporary Access Pass で、フィッシング耐性のある Windows Hello for Business を登録できる。
- Conditional Access で、管理されたデバイスからのアクセスに限定できる。
- Purview DLP（Copilot、Exchange、エンドポイント）と秘密度ラベルで、機微なデータの扱いを多層的に制御できる。
- Defender for Endpoint と Defender for Cloud Apps の連携で、新たに使われ始めたサービスを未承認に指定し、ブロックできる。

顧客事例や、導入効果の数値は紹介されていません。

## 9. まとめ

このセッションは、認証から始まり、オンプレミスへのアクセス、デバイスの管理、AI エージェントの利用、DLP、未承認サービスのブロックまでを、ユーザーの 1 日に沿って 1 本のデモにまとめたものです。パスワードを使わない Windows Hello for Business と Cloud Kerberos trust によるシンプルな体験、Entra application proxy と private access によるゼロトラストのアクセス、Conditional Access による管理デバイスの強制、そして Purview DLP と Defender の組み合わせによる AI 時代のデータ保護が、順に示されました。

Cowork のようなエージェントが代理で動く場面では、ユーザー向けのポリシーヒントがエージェントには届かない、という点が実例とともに語られました。質疑応答は行われず、質問は会場で登壇者に直接、または QR コードから連絡するよう案内されました。登壇者は、検証用のラボ環境を用意しており、構成の説明や質問への回答ができるとも述べています。
