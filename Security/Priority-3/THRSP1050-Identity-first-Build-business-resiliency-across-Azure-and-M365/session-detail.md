# THRSP1050 Identity first: Build business resiliency across Azure and M365

## 1. はじめに

このセッションは、ランサムウェア攻撃で **ID（identity）が突破され、グローバル管理者権限まで奪われた場合に、事業をどう復旧するか** を扱う約 17 分の発表です。Rackspace の 2 人が登壇し、「バックアップはあるが、それを戻す手順と順序は決まっているか」という問いを軸に、Entra や Active Directory を含む ID の復旧、復旧の優先順位づけ（minimum viable business）、Rubrik と組み合わせたオーケストレーション復旧、Rackspace のサービスを紹介します。

発表の主張は、**攻撃の標的は ID であり、復旧設計も ID から始めるべきだ**というものです。最後に、自社に持ち帰って確認するための 3 つの問いが提示されます。このセッションでは画面を使ったデモは行われていません。

## 4. 発表者が伝えたいメッセージ

発表者は、「バックアップがあるか」はもはや論点ではなく、**復旧の手順、順序、責任者が決まっているか**が問われていると述べています。全員がバックアップを持っている前提で、攻撃者が ID を乗っ取り、グローバル管理者権限を持った場合に、バックアップへアクセスできない、担当者にも連絡できないという事態が起こり得る、という問題提起です。

さらに、従来の DR（災害対策）は、AZ 全体の障害のような「広い blast radius」を想定しているのに対し、実際の攻撃は顧客データや財務記録といった特定の部分を狙う、部分的で繊細なものだと説明しています。そして復旧については、どのアプリケーションを最初に復旧するかを、事業の観点で決めるべきだと述べています。

また、AI にできることや攻撃者が手にしている情報を考えれば、「侵害されることを前提にする（assume breach）」べきで、その次の議論は、侵害からどう復旧し、事業を立て直すかだと述べています。

## 5. 発表内容の詳細

### 5.1 ID 経由の攻撃というシナリオ

発表者は、ランサムウェアの攻撃者は数週間から数か月、あるいはそれ以上前から環境に入り込んで準備をしており、システムを無効化したうえで、午前 3 時 2 分に何も動かなくなる、というシナリオを描きます。バックアップを持っていない人は会場にいないはずなので、問うべきは、そのバックアップを戻すためにどんなプロセスを踏むかだと述べました。

攻撃が ID を通じて行われ、攻撃者がグローバル管理者権限を持った場合、バックアップがどれだけ安全でも誰もアクセスできません。システムがすべて落ちているため、午前 3 時 2 分に復旧担当者へ連絡を取ることもできません。こうしたことまで考えて、ランサムウェア攻撃に耐えうるアーキテクチャを作っているか、と問いかけています。

### 5.2 レジリエンスの考え方：RPO・RTO と blast radius

発表者は、平均復旧時間（meantime to resolution）の観点で、restore point objective（RPO）と restore time objective（RTO）が決まっているかを確認するよう求めます。

また、ランサムウェア被害は IT インフラ全体が止まるとは限らず、一部のシステムや重要なワークロードがいくつか失われるのが一般的だと説明します。そこで、自社で設定している blast radius（被害範囲）を把握すること、そして攻撃が内部から（ID を奪われて）来た場合にどう復旧するかが課題になります。

Zach 氏は、顧客が実際に被害を受けたときの様子を聞かれて、被害は「繊細で部分的」だと答えています。DR は AZ や別システムへの全体フェイルオーバーを想定しているが、攻撃者は顧客データや財務記録（業種によっては医療関連）など特定の部分を狙うため、従来の DR アーキテクチャは、こうした標的型の攻撃に向いていない、という説明です。

### 5.3 市場動向と事例

Zach 氏が示した市場動向は、**優先度の高い攻撃のうち 70% が ID を狙っている**というものです。Entra、Active Directory、あるいは両者を同期するハイブリッド構成が対象です。アプリケーションは切り離したりフェイルオーバーしたりできますが、ID を握られると攻撃者は「王国の鍵」を手にし、全体に手が届きます。このため、守り、監視し、レジリエンスを持たせる範囲も広がります。従業員が 5,000 人、11,000 人、20,000 人いれば、その一人ひとりが事業にとっての脅威の入口になる、とも述べています。

事例として、次の 2 つが挙げられました。

| 事例 | 発表で挙げられた推定被害額 |
| --- | --- |
| Jaguar Land Rover | 25 億ドル（その取引先、事業、英国経済への影響を含む） |
| Marks and Spencer | 1 億ドル |

金額だけでなく評判（ブランド）をどう回復するかも問題で、組織的な攻撃は、金銭だけでなく事業上の必須課題になっていると説明しています。

### 5.4 オーケストレーション復旧と minimum viable business

Rackspace は、他のパートナーとは違う立場を取っている、と発表者は述べます。DR として環境を評価・マッピングするだけでなく、全体にわたるオーケストレーション復旧を実際に組み立てます。スライドには "powered by Rubrik" とあり、Rubrik と Microsoft、Rackspace と Microsoft はそれぞれ長い協業の歴史があると説明されました。3 社の連携で、統合された仕組みを提供するという位置づけです。

復旧の原則として、多くの組織が逆に考えていると指摘します。「どのアプリがどれだけ信頼できるか」ではなく、**最も重要なアプリはどれで、何を最初に復旧するか**を考えるべきという主張です。ID の攻撃のときに、HR のチームを最初に復旧する必要があるか、といった例が挙げられました（「おそらくない」）。復旧の各部分を所有する事業部門の関係者は複数いて、それぞれ自分の小さなサイロだけに注目し、全体の事業の観点が抜けがちだと述べています。

そこで、最初の engagement で **minimum viable business（MVB）** を設定します。次の点を評価します。

- Tier 1、Tier 2 のアプリケーションは何か
- データパイプライン、依存関係、アーキテクチャがどうなっているか
- アプリケーションだけでなく、メールが落ちたときに Teams や SharePoint は動くか、顧客や社内の関係者とどう連絡するか
- 売上、ヘルスケアや患者のデータ、製造業務に必要なデータなど、事業を日々回すために必要なもの

なお、発表者は「この前の木曜日にみんなが経験したように」とメールが落ちた場合に触れていますが、その出来事の詳細は語られていません。

### 5.5 バックアップとクラウドだけでは足りない：クリーンな復旧ポイント

Josh 氏は、「バックアップがあるし、クラウドにいるので M365 上のメールや SharePoint は残っているはずだ」という考えへの見解を Zach 氏に尋ねました。

Zach 氏の回答は次のとおりです。DR の現場では、AZ 全体が落ちるような大きな blast radius は見られず、可用性ゾーンや冗長なデータサービスがあっても、すべてに影響が及ぶわけではない、と述べています。ランサムウェアの場合に問題になるのは、フェイルオーバーするときに「悪いデータも一緒に持っていってしまうのではないか」という点です。

Rubrik を使ったオーケストレーションでは、クリーンな時点（clean point in time）を確認できます。IOC（侵害の痕跡）を評価し、Sentinel や Defender for Cloud を使って攻撃者の居場所を確認します。そのため、悪意のあるデータがどこにあるかを特定して境界線を引き、クリーンな状態から再開できます。さらに、triage（影響の調査）の時間が確保でき、何が、どれだけ、どこから取られたかを調べて、そのデータを回復できる、という説明です。

### 5.6 ハイブリッド環境での ID 復旧（AD と Entra）

企業の多くは、もはや Entra だけ、AD だけではなく、両方を組み合わせて使っています。複数のクラウドやオンプレミス、製造施設にまたがる顧客への対応が質問されました。Zach 氏は次のように答えています。

- AD フォレストの再構築は、157 ページのマニュアル（発表では "book"）に沿った作業で、複雑さによっては 3 週間かかる
- Rubrik を使えば、リアルタイムで、あるいは粒度を絞って再構築できる
- Entra でも同様に復旧でき、RBAC、権限、条件付きアクセス（conditional access）は失われず、そのまま再構成（rehydrate）される
- ハイブリッド環境（オンプレミスと Azure）では、希望する順序で復旧できる。どのアプリケーションを優先するか、データがどこから来るかを見極めて、先に再構成すべき側を戻し、ミッションクリティカルではないオンプレミスのアプリケーションは後から立ち上げる、といった判断ができる

### 5.7 Rackspace のサービス：recovery as code と運用

Rackspace が他と違う点として、Zach 氏は **recovery as code** を挙げています。Terraform、ARM、Bicep など顧客が使っているコードベースに合わせて、すべてを顧客の事業向けにカスタマイズして構築します。基準になるのは MVB、つまり「他社や自社ではなく、あなたの事業を回すとはどういうことか」であり、顧客の収益、データ、パイプラインの成功に合わせて作ります。

サービスの流れは次のとおりです。

1. **Insignis operations**（音声認識の都合で表記が確定できません。録音では "Insignus" とも聞こえます）：日々の管理とアーキテクチャの制御。Azure や Microsoft 全体で何が新しく、何が変わっているかを追う負担を減らす。IOC や構成の変更を見ることで、早く検知する。特に AI の世界では変化が速いため、構成ドリフト（configuration drift）が大きな問題になると述べています
2. **Agentic SRE**（Azure 経由）による迅速な対応：AIOps プラットフォームで、月に 20 億件を超えるイベントを triage、診断、対応でき、runbook や自動アクションを実装できる。これにより、午前 3 時にボタンをクリックする人や、確認するチームを置かなくて済む
3. **Rubrik** のオーケストレーションで、クリーンな環境に再構築する。環境はすべてコードとして設計されているため、立ち上げ時にドリフトも捕捉され、測定可能なアクションに基づいてクリーンなデータが戻る

まとめると、「早く検知し、速く対応し、クリーンな空間で再構築する」という流れです。

### 5.8 workload ごとに考える

登壇者は、Rackspace を使わない人にも持ち帰ってほしい最大のポイントとして、**workload ごとに考える**ことを挙げています。顧客から「レジリエントな環境のコストはいくらか」とよく聞かれますが、答えは「家はいくらか」と同じで、状況によると述べました。そのため、最初の engagement では、顧客のチームと一緒にすべての workload を見て、RPO と RTO を理解します。

自社でも同じように、各 workload の RPO と RTO を決めたうえで、実際にテストすることを勧めています。たとえば、次の点を確認します。

- 環境に不正なグローバル管理者が現れたら、どう復旧するか
- 通常の連絡手段である Teams が使えないとき、どう復旧を進めるか
- そのための runbook が実際に作られているか

Rackspace は、最初のステップ（Insignis operations）で、顧客とエンドツーエンドで runbook を作り、どのワークロードやアプリケーションを最初にオンラインにするか、その他は後でよいものを決めます。

また、関係者が異なる点も指摘されました。M365 の管理者と、Azure のグローバル管理者は別人であることが多く、さらに DR やインシデント管理の担当者とも別であることが多いとのことです。エンジニアリング責任者、セキュリティ、CTO や CFO では、それぞれの最優先事項が異なります。この違いをまとめ、MVB を決めることが、復旧オーケストレーションでは重要だと述べています。侵害が小さな範囲か、ID 環境全体に及ぶ大規模なものかを問わず、クリーンな環境を用意できるようにするためです。

### 5.9 Rackspace の立ち位置と持ち帰りの問い

Rackspace は「単一の責任窓口となるパートナー」であり、稼働率（uptime）がすべてではない、というのが発表者の立場です。助言するだけでなく、復旧を再構築し、運用するところまで担い、Rubrik と組んでクリーンな環境のオーケストレーションを行います。また、侵害を前提にしたとき、取締役会レベルで「どこから始めるか、事業への影響は何か」という判断が必要になる、と述べています。

最後に、答えではなく、持ち帰ってほしい問いが提示されました。

1. **Identity first**：攻撃者が今夜グローバル管理者の鍵（認証情報）を握ったら、どの復旧ツール、どの環境が明日も使えるか
2. **One sequence, one owner**：どの順序で復旧するか。エンジニアリング（triage のため）、セキュリティ（SOC での調査のため）、インフラのどれを先に立ち上げるか。各ステップの所有者は誰か。ID と Azure が同時に失われたとき、誰が主導するか。どのアプリケーションを先に立ち上げるか
3. **Rehearsed and proven**：午前 3 時に誰が実行するか。どの関係者が所有するのか。ディレクターか、ハワイで休暇中の担当者か、1 人か、チームか。フロントエンドからバックエンドまで、誰が責任を持つか

発表者は、「問いに答えると、おそらくステップごとに複数の異なる答えが出てくる」と見ています。

## 7. 注意点・発表者の気付き

- バックアップの有無ではなく、復旧プロセスの有無が問われます。ID が乗っ取られると、バックアップにアクセスできず、担当者にも連絡できない状況になり得ます。
- 従来の DR は、AZ 全体のフェイルオーバーのような広範囲の障害向けで、顧客データや財務記録など特定部分を狙う攻撃には向いていません。
- フェイルオーバーするときに、悪意あるデータまで持ち込まない（クリーンな復旧ポイントを選ぶ）必要があります。
- 復旧の優先順位は、HR のような個別の部署の都合ではなく、事業全体の観点で最も重要なアプリケーションから決めます。エンジニアリング責任者、セキュリティ、CTO や CFO で最優先事項が異なるため、それらをまとめて MVB を決める必要があります。
- 通常の連絡手段（Teams）が使えない状況でも復旧を進められるよう、runbook が実際に作成されているかを確認する必要があります。
- 「レジリエントな環境のコスト」は一概には言えず、workload ごとの RPO と RTO によって決まります。

## 8. 利用者にとっての利点

発表で語られた利点は、Rackspace のサービスについての説明が中心で、導入事例や顧客の成果は示されていません。

- 顧客のコードベース（Terraform、ARM、Bicep など）に合わせた recovery as code で、顧客の事業に合った復旧環境を構築できる
- Rubrik により、クリーンな復旧ポイントを確認し、悪意あるデータを切り分けて再開できる
- AD フォレストの再構築に 3 週間かかるところを、リアルタイムまたは粒度を絞って再構築できる。Entra では RBAC、権限、条件付きアクセスが失われず再構成される
- AIOps プラットフォームが月に 20 億件を超えるイベントを triage し、runbook や自動アクションで、午前 3 時の手作業を減らす
- 単一の責任窓口として、助言だけでなく再構築と運用まで担う

## 9. まとめ

このセッションは、ランサムウェア攻撃の優先ターゲットの 70% が ID だという認識から、**ID が破られても事業を戻せるか**を問う内容でした。バックアップがあるのは当たり前で、問題は復旧の順序と責任者、そしてクリーンな復旧ポイントがあるかどうかだ、というのが発表者の主張です。

実践のポイントとして、事業を回すのに最低限必要なもの（MVB）を決め、workload ごとに RPO と RTO を確認し、グローバル管理者が不正に使われる状況を実際にテストすることが挙げられています。最後に、ID が奪われたときにどのツールが使えるか、復旧の順序と所有者は誰か、午前 3 時に実行するのは誰か、という 3 つの問いが提示されました。
