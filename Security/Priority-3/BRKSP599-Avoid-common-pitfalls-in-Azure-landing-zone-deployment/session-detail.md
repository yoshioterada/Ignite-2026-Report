# BRKSP599 Avoid common pitfalls in Azure landing zone deployment

## 1. はじめに

このセッションは、PwC の 3 人が、Azure のランディングゾーン（クラウド基盤）を構築・運用する中で実際に遭遇した失敗事例を「5 つの物語（tale）」として語る内容です。共通する主張は、**ランディングゾーンの設計そのものは正しくても、設計時の前提が現実とぶつかった時点で問題が起きる**という点です。

取り上げられる失敗は、(1) セキュリティのベースラインが変わり、既存アプリが動かなくなった、(2) ネットワークの IP アドレス（CIDR）設計が実際のワークロードの規模に合わなかった、(3) セキュリティポリシーの変更が稼働中のワークロードに影響する、(4) 障害対応のチケットが 9〜10 日間たらい回しになった、(5) AI エージェントがランディングゾーンを運用し始める、の 5 つです。最後に、登壇者が「持ち帰ってほしい問い」を整理し、会場からの質問に答えています。

このセッションでは、画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。

## 3. 何に関する発表か

テーマは、Azure のランディングゾーンが「設計した日は見事に見えるのに、使い始めると失敗する」理由と、その防ぎ方です。Greg 氏は、ランディングゾーンの構成図は多くの人が見慣れたものであり、アーキテクチャが理屈に合っていない状況にはほとんど出会わないと述べています。たいていはセキュリティやネットワークの観点で正しい意図をもって設計されています。問題が出るのはデプロイ後です。

発表は次の流れで進みます。

1. 導入：失敗の原因は、設計時の前提と判断が現実に当たること（セキュリティ、キャパシティ）
2. Tale 1：新しいランディングゾーンで、既存アプリが動かない（ベースラインの移動）
3. Tale 2：ネットワークの CIDR 設計とキャパシティ
4. Tale 3：セキュリティポリシーと統制フレームワークのライフサイクル
5. Tale 4：チーム間の「継ぎ目」を誰も所有していなかった事例（運用モデル）
6. Tale 5：AI エージェントがランディングゾーンを運用する時代
7. 持ち帰ってほしい問いと、3 つの運用シナリオ
8. Q&A

導入では、キャパシティには「ハイパースケーラー（クラウド事業者）側の容量」だけでなく「自分たちのチームの容量」も含まれると説明しています。何個のインスタンスを立てる必要があり、ランディングゾーンがそれを収容できるか、スペースやクラスタ内のインスタンス数が足りるか、という意味です。

## 4. 発表者が伝えたいメッセージ

登壇者が繰り返し伝えているのは、次の 3 点です。

**1 つ目は、ランディングゾーンを「一度作って終わり」にしないこと。** セキュリティポリシー、インフラのキャパシティ計画といった基盤の前提は、ある時点で決めたものです。そのため、アプリケーションと同じようにライフサイクルを持たせ、専任のランディングゾーンのプロダクトチームとプロダクトオーナーを置き、プロダクトとして資金を付けてバックログで育てるべきだ、という考えです。Gokul 氏は、環境を立てたらもうサポートは要らないと言われることがあるが、継続的な「care and feeding（世話）」は常に必要だと述べています。

**2 つ目は、技術だけでなく運用モデルと所有権が設計の一部であること。** Tale 4 では、各チームの視点は正しく、基盤も正しいのに、誰も「チーム間の継ぎ目」を所有していなかったために 10 分で直るはずの問題が 9〜10 日かかりました。構成図は通信の流れを示しますが、意思決定や RACI（誰が何に責任を持つかの割り当て）までは解決しません。

**3 つ目は、AI エージェントを新入社員と同じように扱うこと。** エージェントに運用を任せる前に、運用モデルが先に存在している必要があります。意図を文書化し、権限を絞り、承認フローとロールバックを用意し、段階的に自律性を与える、という考え方です。

締めくくりの冗談めいた一言が、この発表の姿勢を表しています。「**Temporary production exceptions are usually lies**（本番での一時的な例外は、たいてい嘘である）」。一時的なはずの例外は一時的に終わらず、規範になってしまうからです。

## 5. 発表内容の詳細

### 5.1 導入：設計の日は良く見える

Joe 氏のあいさつと進行のあと、Greg 氏は、ランディングゾーンの構成図のスライドを示して話を始めています。強調したのは、含まれるサービスの数ではなく、「構成そのものが理屈に合っていないことはほとんどない」という点です。意図は正しい（セキュリティやネットワークの要件を満たそうとしている）のに、デプロイ後に問題が出ます。今回の事例は過去 18 か月のあいだに実際に遭遇したもので、ランディングゾーンに問題があった、あるいは失敗した状況を、物語の形で紹介すると説明しています。

問題の根は、前提や設計判断が現実に当たったときに表面化します。セキュリティの統制フレームワークは紙の上では筋が通っていても、実際のワークロードを載せると、理想どおりには収まりません。キャパシティについても、前節の 2 つの意味（クラウド側と自チーム側）で現実とのずれが生じます。

### 5.2 Tale 1：新しいランディングゾーンで既存アプリが動かない

**背景。** 大規模な多国籍の産業製品企業が、新しいクラウド基盤を作る案件でした。以前の基盤は存在したものの、セキュリティ統制フレームワークと現在の状況に追従できなくなっていました。いわばブラウンフィールド（既存環境）からグリーンフィールド（新規環境）への移行で、ランディングゾーンをゼロから設計しました。CIO やセキュリティ部門と大量の作業を重ねて新しいベースラインを定義し、世界各地に複数の ingress（入口）と egress（出口）を持たせた高い耐障害性の設計にし、Equinix のバックボーンと Azure のバックボーンをどう接続するかも詰めました。Greg 氏は、顧客から見ても自分たちから見ても、設計の段階ではセキュリティ責任者の夢のような「ユートピア」だったと述べています。

**何が起きたか。** 移行を始めた途端に問題が出ました。Gokul 氏によれば、これは多くの顧客に共通するパターンです。クラウド初期は速く動いてランディングゾーンを立て、ワークロードを動かしました。時間が経って統制やベースライン、プロセスが成熟すると、組織の決定権者が「適切なガードレールで運用しよう。ブラウンフィールドはそのままにして、新しいグリーンフィールドを立てよう」と言い出します。意図もアイデアも良く、準備も適切に行われます。ところが、ブラウンフィールドで動いていたアプリが、新しいランディングゾーンでは動きません。何が変わったのかが分からず混乱し、責任の押し付け合い（finger pointing）が起きます。

本質は、標準のベースライン統制が作り直され、ベースラインが動いたことです。その統制に関する周知が不十分で、全員の合意が取れておらず、テストもされていないと、この状況になります。

**さらに難しかった点。** セキュリティチームは望みどおりの環境をようやく手に入れたものの、「アプリは移行できるのか」「移行したらアプリチームにどんな影響があるのか」を考えていませんでした。しかもこの案件には時間の制約がありました。データセンターを閉じなければならず（スペースが足りなくなっており、リース契約に起因するよくある問題だと説明しています）、速度が重要でした。セキュリティ統制を緩めてアプリが動き続けるようにするのか、それとも制約の中で全アプリチームに今すぐ修正を強いるのか、という選択です。結果として 2 つの部門が対立しました。セキュリティ側は「二度とあの状態では暮らさない」と言い、アプリチーム側は「ずっとこのやり方で運用してきたのに、なぜ変えるのか」と言ったそうです。

Greg 氏は、ランディングゾーンの設計が間違っていたとは限らず、組織のベースラインが変わり、アプリが影響を受けるのだ、という点を最初の日から念頭に置くべきだと述べています。

**よくある具体的なパターン（Gokul 氏）。**

- 旧環境では、あるサービスが「例外」として使えるようになっていた。会場に「一時的に承認されたリスク評価が、環境から消えないままになっているのを知っていますか」と問いかけ、会場から反応があった。
- 新環境では、アプリチームは同じ姿勢（ポスチャ）を期待するが、周知がなければ、サービスが既定で拒否されているためアプリが失敗する。
- 旧ランディングゾーンでは問題にならなかった新しい ingress のネットワーク経路が、標準になっている。

**どう判断したか。** 発表者は、期限があるためトレードオフの選択になったと説明しています。続けて話した登壇者は、セキュリティ、インフラ、アプリ、プロダクトなど役割は違えど全員に責任があり、自分はそのすべての立場を経験してきたので特定の側には立たない、と前置きしたうえで、アプリチームの立場に立つよう促しています。アプリには稼働させたい目標があるのに、ベースラインが動いたのです。解決はリスクに基づく議論になり、この案件では次の 3 つの道がありました。

| 道 | 内容 |
| --- | --- |
| 1. 即時に解決する | 絶対的な露出（exposure）があり重大な場合。例外プロセスは無く、ポリシーを適用する |
| 2. 例外ベースで進める | 代替の補完統制（compensating control）があり、後で戻って対処できる場合。Azure のポリシーの割り当て（assignment）を、スコープを厳密に絞り、有効期限を付け、オーナーを割り当て、バックログに入れて、プロダクトとして見直す。そうしないと決して直らない |
| 3. ガバナンス | 似たケースが旅程（journey）全体を通じて常に同じ経路で扱われるようにする |

この案件で最終的にどの道を選んだかは、発表では語られていません。

### 5.3 Tale 2：ネットワークの CIDR 設計とキャパシティ

**背景。** 別の顧客は、新しいランディングゾーンで Azure（クラウド）への「first mover」になり、データセンターを大きく抜け出すことを目指していました。変革を最小限にして、できるだけ速く移す、つまり実際には最善とは限らなくても、可能な限り lift and shift に近づける方針でした。

ネットワークチームは、オンプレミスからクラウドへ同報（broadcast）でき、一つの「どこにでもある」ハイブリッドネットワークとなる将来像を設計しました。魅力的な目標です。Azure 内のネットワークも、East-West（東西）トラフィックは集中した可観測性のポイントを通り、North-South（南北）は単一の egress/ingress ポイントを通るように、厳密に制御されていました。Greg 氏は、ネットワーク設計自体は見事だったと述べています。

**問題。** しかし、実際のアプリ所有者に、ワークロードの規模を聞いた人がいませんでした。インフラ側の情報は把握していても、ネットワーク側の質問はしていなかったのです。サーバーが 50 台程度なら大きな課題にはなりませんが、この環境は 50,000 コア、400〜500 のアプリケーションでした。IP アドレスと CIDR レンジが大問題になります。さらに、オンプレミスから来た CIDR レンジは、おおむねアプリごとに /24 で、とても大きなものでした。オンプレミスでは内部だけの話なのでネットワークを足せばよく、CIDR の制約はありませんでしたが、クラウドへ広げ始めた途端に制約になりました。

そこで、各アプリチームに戻って「今ある IP アドレス範囲」だけでなく「本当に必要な範囲」を確認し、使い切っていない領域をどこまで絞るのか、という作業が必要になります。

**Gokul 氏の補足。** 大規模な移行や、アプリを大幅に再設計するチームがいる場面でよく起きるボトルネックだと述べています。オンプレミスで持っているものは、クラウドで必要なものとは大きく異なりますが、多くの人は「いま何を持っているか」を基準にクラウドのサイズ決めをします。それが正しい方法とは限りません。ネットワークチームは効率を重視して境界やサイズを明確に決めます。しかし Azure（に限らずあらゆるクラウド）には予約済みの IP アドレスがあり、VPC やサブネットが必要とするもの、サービスごとの特殊な要件もあります。これは単なる lift and shift ではなく、適切なキャパシティ管理の問題だ、という説明です。

**教訓。** Greg 氏は、土台（ファウンデーション）とランディングゾーンを設計するときは、移行の途中の状態（transition state）を考慮しなければならないと述べています。どれだけ計画しても、元の計画に収まらず修正が必要になる部分が出ます。新しいランディングゾーンで最も大きいのはネットワークとアイデンティティであり、ランディングゾーン内も含めて初日から移行を見据えて設計する必要があります。逆に極端な例として、次の 2 つが挙げられました。

- 「Azure に巨大なフラットネットワークを 1 つ作る」と言う人がいる。すると CSO（最高セキュリティ責任者）が、East-West のブロックが無く露出していると慌てる。
- サブネットごとの IP アドレス範囲を 4、6、8、10 個などにしたがるネットワークチームもいる。すると成長が必要になったときに困る。

Gokul 氏は、right-sizing（適正なサイズ決め）を、移行計画と日々のプロセスの両方に組み込むべきだと述べています。何かをクラウドに移すたびに繰り返し起きるボトルネックだからです。また、現状と目標状態、その間の移行経路の図は丁寧に描くものの、一時的に共存が必要になる中間のフェーズが勘定に入っていないことがよくあり、そこでは例外が必要になる、という点を計画プロセスに含めるべきだと説明しています。

### 5.4 Tale 3：セキュリティポリシーと統制フレームワーク

Greg 氏は、Tale 1 の「ポリシーのベースラインが進化するとき、どうするか」を発展させます。初めて AI を導入し、Copilot のようなローコードだけでなく、プロコード（コードで作る）のソリューションを自分たちのネットワークの中にインストールするようになったとき、セキュリティポリシーをどう調整し、進化させ続けるかという問いです。

Gokul 氏は、ポリシーの観点では、どんな統制を実装するかについて明確な指示がある、と述べています。Azure には Azure Policy があり、管理に非常に有効な手段です。難しいのは、最初にデプロイするとき（環境に何も無いので簡単）ではなく、API やサービスで実行できる操作が頻繁に変わったあとです。ガバナンスチームやセキュリティチームが「ポリシーの変更を強制する必要がある」と気づいたとき、すでに動いているワークロードに影響を与えずにどう適用するかが問題になります。これは非常によくある問題で、変更しなければ露出が残り、十分なテストと分析なしに変更すれば業務アプリに影響が出ます。

**事前に使う確認手段。** Gokul 氏は、解決策に入る前に見るものが 3 つあると切り出しますが、語られたのは次の 2 つです（最初の診断・探索の手段として挙げています）。

- 何も停止せず、環境に対する操作も行わずに、影響を**監査（audit）**する。
- **スキャン**を（テストのように）実行し、「適用はしない（do not enforce）」状態で、変更の前に何が影響を受けるかを特定する。

これを受けて、Greg 氏が「環境の管理とは別に、ポリシーのライフサイクル管理をするということですね」と確認すると、「そのとおり」という返答があり、登壇者は次のように続けます。**セキュリティポリシーや統制フレームワークを、インフラ管理やアプリケーションと同じように扱う**という考え方です。ライフサイクルとガバナンスボードがあり、開発のライフサイクルから、廃止（decommission）まで進みます。統制の実装を、ライフサイクル管理される「プロダクト」として扱えば、アプリチームと意図的な会話ができます。例えば「このポリシー（127 番という例）を適用しようと思う。どんな影響が出ると予想するか。導入時期はいつがよいか。まず開発環境に入れて、共同作業にしましょうか」というように進められます。AI によって加速し、エージェント型の環境へ移行するほど、これらの統制は急速に進化する必要がある、と説明しています。

**policy as code について（Gokul 氏）。** policy as code は流行語になり、誰もが自動化を求めていますが、それは問題の一部にすぎないと述べています。ポリシー定義を作り、GitHub や ADO（Azure DevOps）、IaC を通して配布するのは簡単です。本当に必要なのは、次のことです。

- バージョン管理し、ポリシーのライフサイクルを管理する
- 特定の変更の影響を特定する
- ガバナンス面で、誰がオーナーで、誰に相談するかを決める
- どうテストするか、本番で悪いことが起きたときのロールバックはどうするかを決める

これらが無いと一度きりのものになり、「触るたびに確実に動く」と検証できる手段が無い限り、誰もそのコードを変更したがらなくなる、という説明です。

### 5.5 Tale 4：誰も「継ぎ目」を所有していなかった

この物語は技術の話というより、ランディングゾーンの設計の仕方に関する話です。多くの組織では、ネットワークチーム、セキュリティチーム、インフラチーム、アプリケーションチームが分かれています。アプリのデプロイを行う DevOps パイプラインはアプリチームが、IaC でインフラをデプロイするパイプラインはインフラチームが所有しており、各チームは自分の担当部分を必要な形で設計します。これは望ましいことです。

**事件。** この顧客では、実際の侵入イベントが起きました。どのチームが対処すべきかを探すと、チーム間をたらい回しになりました。

1. インフラチーム：「自分たちのインフラには関係ない。ポリシーには従っていて、すべてデプロイされ、正常だ」と答えてチケットを渡した。
2. セキュリティ統制チーム：「監査ログを見て、Splunk も Sentinel も確認したが、環境で何も起きていない。セキュリティの問題ではない」と答えた。
3. アプリチーム：「アプリに到達できない。SQL が落ちている。環境で何かが変わった。なぜ SQL インスタンスにアクセスできないのか。ネットワークに違いない」と答えた。
4. ネットワークチーム：「IP のトレースは至るところを通っており、問題ない」と答えた。

Greg 氏は、土台は正しく、ランディングゾーンも正しく、各チームの視点も正しかったが、**チーム間の引き継ぎ（継ぎ目）を誰も所有していなかった**、と指摘します。10 分で直るはずの修正が、9〜10 日間も組織内を回り、その間アプリは停止し、関係者は冷や汗をかいていました。基盤ではなく、運用と管理の組織設計の問題だということです。

**原因。** 最終的な原因は、サーバーへのパッチ適用の際に **forwarder をインストールし忘れた**という、人為的なミスでした。各チームは自分の視点では正しく、エンドツーエンドの話が抜け落ちていました。

**Gokul 氏の整理。** 多くの組織は、接続を担当するチーム、ファイアウォールルールを担当するチーム、権限（entitlement）を担当するチーム、アプリチームを支援するチーム、ポリシーが正しいか見るセキュリティチームというように構成されています。問題が起きると、まず各チームが自分の縦割りの範囲のログを見ます。しかし、リクエストの最初から最後までの全経路を縫い合わせ（stitch）て「期待どおりに動いているか」を確認する必要があります。そのテレメトリや診断が可観測性として無いと、本当の問題の場所を特定するのは極めて難しく、苛立たしく、時間がかかります。環境を立てるのは簡単ですが、本当に試されるのは、インシデントやチケットが発生する運用のときです。そのため、環境の構築時に、ドキュメント、明確な RACI、責任、引き継ぎを整えることが非常に重要だと述べています。

**所有権の考え方。** 要点は、ランディングゾーンの技術だけでなく、運用モデルがどう並び、どうオーナーシップを組み込むかだ、という点です。リクエストの始まりから終わりまでを通して、問題の場所を突き止める窓口役は誰か。アプリチームに戻るべきだと言う組織もあれば、アプリチームがネットワークから完全に分離されていて、ネットワークに何があるか知らない組織もあります。状況によって議論は変わりますが、この「所有権のマップ」は、技術そのものではないものの、ランディングゾーンに合わせる必要があります。

**成功している顧客の共通点（Gokul 氏）。**

- ライフサイクル全体にわたり所有権が明確で、インシデント時に、行動する決定権を持ち、全員を集め、その場で判断できる人がいる。
- アーキテクチャ図は美しく、フローを示すが、意思決定や RACI の問題は解決しない。それらは文書化して周知する必要がある。
- ランディングゾーンは常に進化し、1 回限りの実装ではなく、進化し続けるプロダクトとして扱い、プロダクトのように資金を付ける。適切なバックログがある。「環境を立てたので、これ以上のサポートは要らない」という声は決して正しくない。

### 5.6 Tale 5：AI がランディングゾーンを運用する

Greg 氏は、これは今まさにリアルタイムで進んでいる話だと言います。もはや「AI のワークロードをクラウドで動かす」だけの話ではなく、**AI がランディングゾーンを運用し始める**段階です。Microsoft の Azure SRE agent に関する記事を例に、最初の一歩になっていると述べています。

**エージェントの限界。** クラウド運用者が人間ではなくエージェントになると、エージェントはそのコンテキストに見えるものだけで動きます。

- 統制フレームワークにあるポリシーが Azure Policy になっていなければ、エージェントは知らない。
- アプリチームが大事にしている名前付きのサーバーが落ちたら、エージェントは単純にそれを消して新しく作る。
- 手持ちの容量を超えてデプロイしたり、ある VM の SKU が使えないときに、スタックの一番上の「1 分あたり 1 万ドル」のものを選んだりしかねない（Greg 氏の例え。実際に起きている種類の問題として挙げています）。

ある顧客は、まだ本番ではなく dev/test 環境だけで SRE agent を動かし、何ができて何ができないか、何が得意か、自動化スクリプトや runbook とどう違うかを探っています。そこで見えてきたのは、最初の 4 つの事例で語った「傷跡」が、まさにエージェントが苦戦している点だということです。

- エージェントは、Azure の内側しか見えないので、ネットワークのキャパシティ問題を知らない。
- セキュリティ統制のベースラインが変わったことも、Azure Policy だけを見て「ここはすべて有効」と判断するので知らない。
- 環境を意図どおりに復元させたいなら、IaC が必要。エージェントが知るのは Terraform に書かれたものだけで、意図は知らない。誰かがポータルでブロックを避けるために別の IP アドレスを素早く付けたことも知らず、「設計にこう書いてあるからこうする」と動く。

**Gokul 氏の見解：自動修復の経験則。** AI 以前から、自動修復（auto remediation）で自己修正・自己回復をさせたいと望まれてきましたが、実際に長期的に強制・有効化できたものはどれほどあるでしょうか。そこには信頼が必要です。エージェントはメトリクスやログを見て現状は把握できますが、「目標状態（意図した状態）」をどこから得るのかが問題です。数人のエンジニアが常に火消しをしている部族知識（tribal knowledge）のままでは機能しません。基本は変わらず、次の 3 点が必要です。

- エージェントの外側にガードレールがあること（実行できる操作を厳密に絞る）
- 承認され、証明された（attested）ドキュメントを、目標状態の基準にすること
- 適切な権限（entitlement）と、実行できる操作を与えること

進め方は、昔の自動修復と同じです。まず下位環境でテストし、慣れ、調整してから本番に入れます。エージェントでも次の段階を踏みます。

1. 診断だけから始める。診断が実際に機能し、意味があることを確認する。
2. 提案された修復を、隔離された環境（self-contained environment）で実行させてテストする。エージェントも学習し、利用者の安心感も得られる。
3. 十分に良い状態になったら、推奨だけでなく操作や変更も行う完全な自動修復に進む。

プラットフォームを運用する人（アプリ、セキュリティ、インフラのチーム）は、エージェントが別のアイデンティティで動いていても、その行動に責任を負います。

**Greg 氏の見解（PwC の視点）。** AI エージェントは、人間と同じように扱うべきです。新しく迎えたエンジニアに対する評価や感覚を、エージェントにも当てはめます。運用モデルは、新しいエンジニアを雇う前と同様に、エージェントが来る前に存在していなければならず、無ければ新人でも AI エージェントでも同じ混乱が起きます。さらに、次のように人間と同じプロセスに参加させます。

- ITIL、ServiceNow、DevOps のプロセスに参加させる。承認やステージゲートを通り、ファイアウォール設定を変更するなら、同じ可観測性、監査ログ、ServiceNow のチケットを通す。エージェントがチケットを起票し、人間の承認を待ってから実行する。
- 現状のルール、ガードレール、ポリシーがランディングゾーンに存在する。そのうえで、「このアプリは決して落としてはならない。VM を失ったらすぐ新しく立てる」「別のアプリは自動処理を一切しない。すべてチケットシステムを通す」といった**意図**もエージェントに示す。運用チームに「アプリが落ちたらどう反応するか」を伝えるのと同じことをエージェントにもする。

**準備ができたと言える条件（Gokul 氏）。** 「エージェントにランディングゾーンを運用させて安心できるか」と聞かれて、今は「たぶん無理」かもしれません。しかし次が揃っていれば安心できる、という説明です。

- エージェントが何をするはずなのか、明確に書かれている
- 承認ワークフローがある
- 推奨の根拠がある
- 結果を正当化するテストが行われている
- 問題が起きたときにロールバックする方法があり、文書化されている（本番デプロイと同様）

小さなステップでこれらを満たしていくのが、成功している顧客の進め方だと述べています。Greg 氏は、AI に「自分で自律性を獲得させる」という考えを付け加え、「新しく入ったばかりのエンジニアに、break glass アカウントを含む本番の鍵を渡さないのに、初日から AI に渡すのか」と問いかけます（「break class accounts」と聞こえますが、文脈から break glass と解しています）。意思決定の様子を見ながら、徐々に権限を広げるべきだという主張です。

### 5.7 持ち帰ってほしい問い

Greg 氏は、ランディングゾーンの観点で持ち帰ってほしい問いとして、次を整理しています。

- **移行途中の状態。** 今日の設計だけでなく、どう進化していくか。アプリはどう進化するか。運用チームとモデルはどう進化するか。基盤を真空の中で設計して、初日からうまく動くと期待してはいけない。
- **基盤の前提。** ランディングゾーン、セキュリティポリシー、インフラのキャパシティ計画は、ある時点で決めたもの。アプリケーションと同様に扱い、プロダクトオーナーと責任者を置いた専任のランディングゾーンのプロダクトチームを持つ。「セキュリティポリシーを見直してから 6 か月経った。長すぎる」と気づける体制にする。
- **ポリシーは変更に耐えられるか。** インシデントを受けて締めつけるのか。インシデントへの反応は通常業務（BAU）とは大きく異なる。ポリシーのライフサイクルはどう回すのか。
- **継ぎ目の所有者。** ランディングゾーンの構成要素間の接続を誰が持つのか。レビューは誰がするのか。セキュリティの問題か、ネットワークの問題か、アプリチームに差し戻すのか。クラウドオペレーターに頼るのか、アプリチームに頼るのか。誰かがエンドツーエンドを考えなければならず、そのために、全体に目を配る Cloud Foundation チームを置くことを勧めている。
- **AI エージェントと新入エンジニアのテスト。** AI エージェントを環境に放ったとき運用できるか。新しいエンジニアを雇って環境に配置したら運用できるか。ガードレールや統制が組み込まれているか、それとも部族知識や wiki のページに書かれているだけか。

**3 つの運用シナリオ（Gokul 氏）。** 環境が立ったあと、事業・プロダクトチームの速度や InfoSec が与えるガードレールに合わせて、一貫して管理・維持する方法が必要です。成功しているものとして、次の 3 つのユースケースを挙げ、自由にカスタマイズしてよいと述べています。

1. **BAU（通常業務）の運用：** プラットフォームに期待されることと各チームの役割が分かっている。その能力が文書化され、適切な自動化があり、見通しが利くか。
2. **トップダウンの突発的なイニシアチブ：** 資金も付かないまま、突然降ってきて、全員が慌てる状況で、運用モデルはどう機能するか。
3. **インシデント：** 適切なチェックとバランス、ステークホルダーを集める簡単な手段、適切なテレメトリがあり、すばやく業務を復旧できるか。

この 3 つに運用モデルが答えられれば、プロダクトとして成功裏に管理できる、という説明です。

### 5.9 Q&A

**質問 1：RACI と責任の確認について。** 質問者は、自分の状況は PwC と似ていると述べたうえで、作る設計ごとにコンサルタントと並行してレビュー（音声上は「racing review」と聞こえ、RACI を指すと解しています）を行う必要があると説明しました。この冒頭の部分は聞き取りが不明瞭です。そのうえで、問題が起きたときや運用中に、誰が何に責任を持つかをどう把握し、クライアントとどう会話するのかを尋ねました。登壇者の理解では、「変更のたびに RACI の所有マトリクスを参照し、他チームとどう連絡するかをどうするか」という質問です。

回答は次の 3 点と補足です。

1. RACI モデルを持ち、誰が何に責任を持つかを知るのが第一歩。
2. そこに指名された人が、実際にその権限を持っていると信じられること。依存先のチームの人が「自分では決められない」と言うのが最も苛立たしい。企業として、その人が意思決定の権限者だと合意しておく。
3. 頻繁にコミュニケーションを取る。15 分の毎日のスタンドアップで、その日の課題を発信するのを強く勧める。参加できない人には議事録を送る。

補足として、強い運用モデル、ガバナンスフレームワーク、毎週のリズム、チケットシステムも挙げています。ただしこれらは「基本中の基本（bread and butter）」で、当然備わっているものとして話を進めた、とのことです。

**質問 2：言及しているエージェントは何か。** 質問者は、Azure AI で作られたエージェントなのか、Azure 自体のためのエージェントなのかを尋ねました。

Greg 氏は、Tale 5 の例で指していたのは **Azure SRE agent** であり、同時に、顧客がクラウド運用の役割のために開発しているエージェント全般も指していると答えています。どの方向・技術を選ぶかによって長所と短所が大きく変わります。個人的には Microsoft の SRE agent が気に入っているが、現時点では「durable（永続的）」ではなく、コンテキストメモリの問題に直面し続けていると述べています。AI を環境で有効にするための初期の学びが、まだあります。エージェントに Azure Policy のコードだけを参照させるのか、すべてが書かれた wiki ページや、人間向けのガイドがある SharePoint サイトにも到達させるのかといった点は、状況次第です。自身の考えとして、その役割の人間ができる・アクセスできることは、エージェントもできるべきだとしています。ただし初期にそれを信頼するかは議論の余地があり、下位環境でテストして慣れてから環境に放つべきだと答えています。

**質問 3：AWS 中心でリソースが限られる環境の場合。** 質問者は、主に AWS を使っている組織で、ほぼ一人で回している状況だと説明しました。RACI の話や、エンジニアの人材の話を受けて、リソースが限られていること、ドキュメントが分散していて（保護されていて）扱いにくいことに触れ、プロダクトの進化を管理する判断のために、それらをまとめて扱える能力が必要だ、という趣旨のことを述べました（音声が不明瞭で、質問の細部は確認できません）。

登壇者は、「簡単な近道は本当に無い」と答えています。エージェントは穴を埋める助けにはなりますが、まず部族知識を引き出して、チームの水準を上げ、十分な容量を確保しながら、少しずつ引き渡していく必要があります。先週、ある顧客に出した提案として、「まだアクションを取るエージェントの準備ができていないなら、コンプライアンスとルールを監視するエージェントを立てる」ことを挙げました。セキュリティ統制フレームワークが何であるべきかが分かっているなら、エージェントに環境を継続的に監視させ、「誰かが公開エンドポイントのためにファイアウォールに穴を開けた。これはポリシー 123 に違反する」といった事態を通知させる、という案です。監査の役割から始めれば、エージェントは信頼に足ることを示していける、と説明しています。

## 7. 注意点・発表者の気付き

- **ベースラインの変更は周知する。** 標準の統制が作り直されても、周知・合意・テストが無ければ、既存アプリが動かなくなります。例外で動いていたサービスは、新環境では既定で拒否されます。
- **「一時的な例外」は残る。** 例外を使うなら、ポリシー割り当てのスコープを厳しく絞り、有効期限とオーナーを付け、バックログに入れて見直します。そうしなければ決して直らない、と述べています。
- **現状のサイズをそのまま持ち込まない。** オンプレミスのアプリごとの /24 をそのまま持ち込むと大きすぎてクラウドでは制約になり、かといって必要量だけに絞る際も、Azure の予約済み IP アドレスやサービスごとの特殊な要件を見込む必要があります。ただし、フラットな巨大ネットワークや極端に小さなサブネットも、それぞれ問題を生みます。
- **ポリシーの変更は、適用前に影響を確かめる。** audit と「適用しない」スキャンで確認し、policy as code では、バージョン管理、オーナー、テスト、ロールバックまで含めて管理します。
- **ログに基づく各チームの「問題なし」は、全体の正しさを保証しない。** 例では、単純な forwarder の入れ忘れが 9〜10 日間の停止につながりました。
- **AI エージェントは Azure の内側と IaC の記述しか知らない。** Azure Policy になっていない統制、ネットワークの容量問題、ポータルでの手動変更の意図は、エージェントには見えません。なお、登壇者は SRE agent について、現時点では永続的ではなくコンテキストメモリの問題があると述べています。
- エージェントが別のアイデンティティで動いても、**責任は運用する人間側にある**とされています。

なお、発表では具体的な数値による効果（コスト削減率など）は示されていません。

## 9. まとめ

- ランディングゾーンの失敗の多くは、設計が誤っているからではなく、設計時のセキュリティやキャパシティの前提が現実に当たることで起きます。
- 5 つの物語は、ベースラインの移動による既存アプリの停止、CIDR のサイズ決め、ポリシーのライフサイクル、チーム間の継ぎ目の所有権、AI エージェントによる運用、でした。
- ランディングゾーンは、専任のプロダクトチームとオーナー、バックログと資金を持つ「進化するプロダクト」として扱い、運用モデル（RACI、意思決定権、可観測性）を設計の一部にします。
- AI エージェントには、新しいエンジニアと同じように、意図の文書化、権限の限定、ITIL や ServiceNow などの既存プロセスへの参加、段階的な自律性の付与を求めます。
- 「本番での一時的な例外は、たいてい嘘」という言葉のとおり、例外を早い段階から管理することが勧められています。
