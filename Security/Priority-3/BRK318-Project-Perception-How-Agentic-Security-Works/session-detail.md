# BRK318 Project Perception: How Agentic Security Works

## 1. はじめに

このセッションは、Microsoft の agentic security（エージェント型セキュリティ）システム **Microsoft Perception（Project Perception）** の紹介です。Perception は、blue team（防御・調査）、red team（攻撃の検証）、green team（修復・リスク削減）の役割を持つ AI エージェントのチームが、セキュリティ担当者の代わりに、調査、検出ルールの作成、脆弱性の検証、修正案の作成を連携して進める仕組みです。発表の冒頭で、Perception がこの日（セッション当日）に **GA（一般提供）** になったと語られています。

発表は、架空の金融サービス企業 Caldova が受けた攻撃のストーリーを軸に進みます。「情報も検知もあったのに、行動が間に合わなかった」という状況を、Perception がどう変えるかを、3 つのデモで見せます。1 つ目は夜間に上がったインシデントの自動トリアージと調査、2 つ目は Web アプリのペネトレーションテストと修正 PR の作成、3 つ目は脅威インテリジェンスの記事から始める「自分たちは守られているか」の確認です。

このセッションでは、画面を使ったデモが 3 つ行われています。最後には、Nationwide の事例（脅威インテリジェンスの分析が 4 週間から 4 時間に）と、今日から始められる実践方法が紹介されます。

## 3. 何に関する発表か

テーマは、攻撃者が AI を使って攻撃のスピードと規模を上げている状況で、防御側も AI エージェントで対抗する、という考え方です。登壇者は、これを「攻撃側のエージェントに、防御側のエージェントで立ち向かう」と表現しています。

発表の流れは次のとおりです。

1. Caldova の攻撃のストーリー（問題提起）
2. Perception が解決する 3 つのこと（インシデントから回答へ、弱点を先に見つけて直す、協調して攻撃者より速く動く）
3. Perception の 3 層構造
4. デモ 1：SOC の定番ワークフロー（トリアージ、調査、対応）
5. デモ 2：Web アプリの Pen Test と修正 PR（プロアクティブな防御）
6. Perception の playbook とモデル選択の仕組み
7. デモ 3：脅威インテリジェンスの記事から始める「守られているか」の確認
8. GA・プレビューの発表と今後の方向性
9. 人間によるコントロール、効果、Nationwide の事例、今日から始める方法

## 4. 発表者が伝えたいメッセージ

最大のメッセージは、**セキュリティチームの課題は情報の不足ではなく、情報を行動に変える速度と規模の不足**だという点です。Caldova の例では、脅威レポートが 30 日前に公開され、3 日前には脆弱性スキャンの結果も出ていて、攻撃当日には Microsoft Defender が侵害の兆候を検知していました。それでも対応が間に合わなかったため、登壇者は「攻撃者は Caldova を出し抜いたのではなく、速さで上回った」と述べています。

そこで Perception は、既存の防御の上に載る AI システムとして、状況をつなげ（connect the dots）、調査し、対応し、強化（harden）します。ただし登壇者は、**自律性は監督を手放すことではない**と強調しています。重要な操作では人が承認し、すべての操作はログに残り、エージェントは人間とは別の専用の ID で動くと説明しています。

## 5. 発表内容の詳細

### 5.1 Caldova のストーリー

シナリオは次のとおりです。

- 火曜（または木曜）の午前 1 時 23 分、Microsoft Defender が、Caldova の財務サーバーに侵害の兆候を検知します。アラートが上がりインシデントが作られますが、SOC の担当者は夜中なので気づかず、インシデントはキューで待ち続けます。攻撃者側の AI ベースのシステムは待ちません。
- 実際の攻撃は午前 1 時 23 分より前から始まっていました。30 日前には、Onyx Sleet という新しい脅威に関するレポートが公開されていましたが、見る時間のある人はいませんでした。
- 3 日前には、セキュリティスキャンで潜在的な脆弱性が見つかっていましたが、チームは多忙で、どれが悪用可能か検証も修正の優先順位付けもできていませんでした。
- アナリストが勤務を始める午前 9 時 4 分まで、マルウェア検知は確認されませんでした。発表では、その 30 分後には攻撃者が Caldova の最も機密性の高い財務データを盗み出していたと語られています（何の 30 分後かは言い回しが曖昧です）。

登壇者はこの例を、「インテリジェンスもシグナルもあり、Defender は脅威を検知していた。足りなかったのは、それを十分な速さで行動に変えることだった」とまとめています。

### 5.2 Perception が解決する 3 つのこと

Microsoft Perception は、次の 3 つを助けると説明されています。

1. **インシデントから回答へ**：正しい答えと次のステップを、より速く得る。
2. **攻撃者より先に弱点を見つけて直す**：脅威に先回りする。
3. **協調して攻撃者を上回る**：専門化したエージェントが、共通のミッションに向かって一緒に動く。

### 5.3 Perception の 3 層構造

Perception は、新しいサイバースタックとして 3 つの層で構成されます。

| 層 | 内容 |
| --- | --- |
| 最下層：signals, sensors, actuators | すべてのワークロードにまたがるシグナル、センサー、アクチュエーター。Microsoft のセキュリティ製品が提供し、エージェントに「見える範囲」と「行動する力」を与える |
| 中間層：context layer | セキュリティデータとインテリジェンスをつなぎ、エージェントが状況を素早く効率的に理解できるようにする |
| 最上層：agents, models, harness | 推論、調査、協調した行動を支える |

これらの層によって、エージェント型の防御を大規模に実現しつつ、常に人をコントロール役に置く、という説明です。

### 5.4 継続的・プロアクティブな保護のワークフロー（全体像）

登壇者は、全体像として、アナリストが脅威インテリジェンスの記事を共有し「自分たちは守られているか」と尋ねる場面を挙げています。Perception は依頼を理解し、計画を立て、3 つのチームの専門エージェントを調整します。

- **blue team**：インテリジェンスを分析し、脅威を調べ、検出（detection）を作る
- **red team**：それらの防御をテストし、攻撃経路をマッピングし、脆弱性を見つける
- **green team**：リスクに優先順位を付け、的を絞った修正を準備して展開する

1 つの質問が、セキュリティスタック全体にまたがる協調した行動に変わる、という説明です。

### 5.5 デモ 1 の前提：SOC の日常課題

SOC チームの日常は、アラートが入り、インシデントがキューに現れ、「本物の脅威か」「何が起きたか」「どこまで広がったか」「何ができるか」に答えることです。証拠が複数のシステムにまたがると、答えを得るのに時間がかかります。Perception では、blue team のエージェントがトリアージと調査を自動化・加速し、アナリストがより速く対応に移れる、と説明されています。デモの詳細は 6.1 に書きます。

### 5.6 プロアクティブな防御：脆弱性の優先順位付け

次に、脅威に反応するだけでなく、先回りする話です。課題は、常に大量にある弱点の中で、本当にリスクの高いものを特定することです。Perception では red と green のエージェントが協調して、悪用可能な弱点を明らかにし、重要なものを優先して修復を加速する、と説明されています。デモの詳細は 6.2 に書きます。

デモの後、登壇者は Caldova の 3 日前の状況に戻ります。AI の加速や、MDASH のようにコードを深く調べるツールによって、発見される脆弱性は以前よりはるかに増えており、「修正すべきもの」も増えている、という認識です。しかし今回見たように、**数十個の潜在的な脆弱性から、本番環境で検証され、リスクで優先順位が付いた 3 つ**に絞り込めました。「存在するかもしれない脆弱性」ではなく、Pen Test エージェントが本番環境で悪用可能だと証明した弱点です。MDASH の検出結果、ペネトレーションテスト、ポスチャーの優先順位付けを組み合わせることで、影響の大きい修正を特定し、コードの修正ができるまでの間、保護的な緩和策を入れられる、と説明しています。成果は、脆弱性の継続的な選別、明確な優先順位、コードレベルまで露出を減らす高速で自動化された道筋です。

### 5.7 playbook の仕組み

Perception の **playbook** は、複雑な multi-agent の仕事を表します。セキュリティの専門家チームが集まって複雑なタスクを解決するイメージです。

1. セキュリティ上の目的から始まる。アナリストが手動で起動することも、イベントで自動的に起動することもできる。
2. Perception が、必要なエージェントを計画し、調整する。red、blue、green、またはその組み合わせになる。
3. エージェントはコンテキストを共有する。あるエージェントの出力や発見が、別のエージェントの入力になる。アナリストが介入しなければ、完全に手を離れて進む（hands-off）。
4. すべてはセキュリティデータに基づいており、重要な判断のときにアナリストが誘導、レビュー、承認できる。

### 5.8 エージェントを動かすモデルの選び方

すべてのセキュリティタスクに同じ種類の AI の推論が必要なわけではない、と登壇者は説明します。攻撃の調査、脆弱性のテスト、修復の優先順位付けは、専門性の異なるセキュリティチームのメンバーのように、まったく別の仕事です。そこで、1 つのモデルが何にでも最適だと決めつけず、**各エージェントが行う仕事に対して、候補モデルを継続的に評価**しています。結果の品質をコストやレイテンシーと比較して測り、それらのバランスが最も良いモデルをタスクごとに選ぶ、という説明です。「専門性はエージェントだけでなく、それを動かすインテリジェンスにも及ぶ」と述べています。

### 5.9 GA とプレビューの発表、今後の方向性

デモのあとのまとめとして、次の発表がありました。

- **6 つのエージェントが本日 GA**：blue、green、red の各チームにまたがるエージェントです（6 つの内訳は、トランスクリプトでは列挙されていません）。
- **定義済みの playbook**：セキュリティチームにとって非常に一般的で価値の高い仕事を達成できる、と説明されています。
- **Web App Pen Test を使った proactive security が public preview**：どの弱点が悪用可能かを検証し、risk reduction エージェントとともに優先順位付けと修正を進めます。
- **外部の TI（脅威インテリジェンス）記事への対応が public preview**：threat intelligence agent が、Defender システムにまだ無い情報も取り込めるようにします（デモ 3 で語られました）。
- **データソース**：デモ 1 で、Perception は Defender や Microsoft のデータだけでなく、Sentinel でつないだデータソースにも広げており、AWS、Okta、Salesforce から始めて、今後増やすと説明されています。
- **今後**：より多くのエージェント、シナリオ、ユースケースへ拡張します。さらに、内部で動作する AI エージェント自体を守る課題に取り組むと述べています（「insider AI risk」のセッションに触れていますが、音声認識の表記が不確かです）。方向性として、脅威への反応から、エクスポージャーを減らし、次世代の AI 環境を守る継続的でプロアクティブな保護へ進む、と説明しています。

### 5.10 エージェントのコントロールとガバナンス

大規模にエージェントを動かすときに、どうやって制御を保つのか。登壇者は「Perception では、自律性は監督を手放すことを意味しない」と述べ、次の点を挙げています。

- エージェントは独立して作業できます。今後さらに自律性を高めたいとしつつ、重要な操作の場面で、手動でレビュー・承認するか、エージェントに任せるかを利用者が決められます。
- 例えばエージェントはペネトレーションテストの準備まで行いますが、承認された人が許可するまで先へ進みません。
- すべての操作はログに記録され、監査できます。
- エージェントは**固有の agent ID** で動作します。人間の ID ではなく専用の ID を持つので、追跡でき、最小権限でコントロールできます。各エキスパートエージェントは、そのタスクに必要な権限だけを得ます。

### 5.11 効果と Nationwide の事例

セキュリティチームにとっての意味として、次の 4 点が語られました。

- **速く（faster）**：証拠を寄せ集める時間が減り、脅威が出たときの答えが速くなります。
- **広く（broader）**：これまでキューに手つかずで残っていたインシデントも含め、すべてのインシデントとアラートがトリアージ・調査されます。
- **早く（earlier）**：すべてが早期に分析・発見され、攻撃者に悪用される前に、悪用可能な弱点を見つけて優先順位を付け、修正できます。
- **コントロール**：前述のとおり、重要な判断は人が握り続けます。

登壇者は、現在の組織での対応と対比しています。脅威に対するエンドツーエンドの保護は、おそらく半年から 1 年に 1 回程度、専門家を呼んで評価するものです。ペネトレーションテストのチームが攻撃を試み、その学びを各チームに渡して、修正と追加の検出を行います。多くの人が関わる長くて重く、コストのかかるプロセスですが、AI エージェントの協調だけで行えることを誇りに思う、と述べています。

**Nationwide の事例**：数か月続いている拡張的なプレビュープログラムでは、実際の顧客が Perception を使っています。Nationwide はこれらのシナリオのテストで Microsoft と密に協力してきたと紹介されました。以前は脅威インテリジェンス分析に **4 週間** かかっていた作業が、**4 時間** でできるようになった、と同社が報告しているとのことです。エージェントが分析を担当し、専門家が発見をレビューして判断する形で、チームがコントロールを保っている点も強調されました。

### 5.12 今日から始める方法

登壇者が最後に挙げた「今日から Perception を使い始める 3 つの方法」は次のとおりです。

1. **Automatic Triage and Investigation をオンにする**：夜間やシフトの合間に入るインシデントを、誰かが拾うのを待たずに Perception がトリアージ、調査、証拠収集まで進めます。朝にアナリストが来たときは、手つかずのキューではなく、最も価値の高い発見だけを見れば済みます。
2. **コードスキャナーを実行して脆弱性を見つけ、Web App Pen Test エージェントで本番での悪用可能性を検証する**：脆弱性は山ほどあり、課題はどこから始めるかなので、Perception で検証して修正することが勧められました。
3. 3 つ目は、大きなマルチエージェントの継続的なワークフロー（プロアクティブな保護）に進むことです。録音はこの文の途中で終わっており、詳しい説明は確認できません。

## 6. デモ・手順

デモはすべて Naama 氏が担当し、Corina 氏が合間に補足しました。画面の細かいレイアウトや文言は音声からは確認できないため、語られた範囲で、語られた順に書きます。

### 6.1 デモ 1：SOC の定番ワークフロー（トリアージ、調査、対応）

シナリオは、Caldova の SOC アナリストである Dave に割り当てられた大量のインシデントです。Dave は、Perception を GA まで導いた CVP でもある、と冗談交じりに紹介されました。

1. Caldova の環境を開きます。Dave に割り当てられたインシデントの一覧があり、手作業では数時間かかる量です。
2. チェックボックスをオンにして、**automation rule** を設定します。新しいインシデントが入るたびに Perception のエージェントが動き出す設定です。この playbook は、検出カバレッジを確保する層も加えると説明されています。
3. トグルで「All new incidents」を選びます。
4. 新しいインシデントがすべて起動され、Perception のエージェントが作業を始めます。
5. 1 件を開きます。AWS と Okta のアカウントが侵害されたインシデントでした。ここで、Perception は Defender や Microsoft のデータだけでなく、Sentinel でつないだデータソースにも対応するという説明があります（AWS、Okta、Salesforce から開始）。
6. トリアージが済み、調査に進んでいます。**attack investigation agent** が作業中で、攻撃の範囲を把握するだけでなく、検出の不足（カバレッジの欠け）も特定します。
7. 調査の結果、AWS と Okta の活動に対するカバレッジの不足が見つかります。従来は、SOC アナリストとは別の検出エンジニアに引き継ぎ、その作業キューに入って、不足を埋めるのに数日かかることもありました。ここでは **1 クリック**で、エージェント同士が連携して不足を埋められます。
8. **detection authoring agent** の検出レポートを開きます。investigation agent から AWS と Okta の不足の情報を受け取り、環境固有の不足に合わせた**カスタム検出ルール**を作成しています。コンテキストが引き継がれるので、エージェント同士が協調して動きます。
9. 検出ルールは自動では環境に反映されません。カスタム検出の追加は影響のある操作で、SNR（信号対雑音比）が低いと、見たくないものでキューがあふれる可能性があるため、ユーザーがレビューして承認します。内容に満足したので「Submit」を押しました。
10. 追加された検出ルールの内容を確認します。通常は検出エンジニアのような専門家の仕事で時間がかかりますが、1 クリックで調査とカバレッジの確保を 1 つのワークフローで行えました。
11. 続いて Corina 氏が、エージェントが調査中に特定して追加した検出による、検出カバレッジの変化（前後）の表現を見せました。

Corina 氏は、午前 1 時 23 分の Caldova に話を戻してまとめています。アナリストが拾うのを数時間待つ代わりに、Perception が自動でトリアージと調査を起動し、証拠を集めて点をつなぎます。数時間かかる手作業が数分で進み、検出の不足を特定して新しい検出まで作ります。アナリストはゼロからやり直したり下働きをしたりせず、判断に集中できる、という説明です。

### 6.2 デモ 2：Web アプリの Pen Test と修正（Protect Web App playbook）

public preview となった **Web App Pen Test agent** が、Web アプリへの攻撃をシミュレートして負荷（ストレス）をかけ、その結果を green agent に引き渡して、脆弱性の修復につなげる流れです。

1. playbook として **Protect Web App** を選びます。この 2 つのエージェントの組み合わせです。
2. ペネトレーションテストの対象アプリケーションを選びます。Web App Pen Test は、重要な Web アプリすべてをテストするわけではありません。**自分が所有するアプリだけ**をテストすべきで、DNS による所有確認などの設定と検証が組み込まれていると説明されました（この検証は画面では見せなかった、と断っています）。
3. 自分が所有するアプリを選び、セッションを開始します。
4. green agent の他に、**MDash**（発表中の表記は MDASH とも聞こえます）が、このアプリのコードリポジトリを事前にスキャンし終えています。Web App Pen Test は MDash の検出結果を読み込み、検証すべき脆弱性を絞り込みます。コードは多くの場合きれいではなく、長い脆弱性リストが出るので、どれを優先して検証すべきか分からない、という課題への対応です。
5. Web App Pen Test が、そのリストの脆弱性が悪用可能かを検証します。まず計画を作り、**センシティブな操作なので、実行前に計画の承認を求めます**。計画を承認すると実行が始まります。
6. 実際の攻撃者と同じように、外側から内側へアプリを攻撃します。安全に行い、害は与えませんが、Pen Test が何を達成できたかの証拠（場合によってはアプリのスクリーンショットなど）を提供します。外部から何が悪用でき、何にアクセスできるのかを示す証拠になります。
7. MDash が挙げた **48 件**の脆弱性が、悪用を検証できた **3 件**（SQL injection と cross-site scripting を含む）に絞り込まれました。48 件が 100 件、数百件になることもあると説明しています。
8. 修正を開発者にどう渡すか。**承認して PR の下書きを作成させます**。risk reduction agent が GitHub と連携して修正の PR を作ります。「ここでは提出しない」と断ったうえで、coding agent に修正を作らせて展開する流れだと説明されました。
9. セッションの概要画面で、見つかった脆弱性、悪用可能と判断されたもの、修復計画（コード修正を含む）を確認します。
10. GitHub 側の見え方を少し見せました。risk reduction agent が作成した同じ PR が、そのアプリの所有者である開発者に、何が起きたのか、なぜこのコード修正が重要なのかといった豊富な情報とともに表示されます。開発者が承認して一緒に進められます。セキュリティチームだけでなく開発チームにも広がっている、という説明です。

Corina 氏は、開発者には直すものがたくさんある、と冗談を挟み、Naama 氏が「承認が必要です」と答えています。

### 6.3 デモ 3：脅威インテリジェンスの記事から始める「守られているか」の確認

時点は、攻撃の 30 日前（T minus 30 days）です。Microsoft Threat Intelligence に新しい TI の記事が公開され、CISO が「これは自分たちに関係があるか、守られているか」と尋ねに来る、という設定です。

1. Perception に「Am I protected from Onyx Sleet?」と尋ねます。通常は、記事から IOC や TTP、攻撃者が取りうる各手法を抜き出し、自社の環境・ネットワークでどこが露出しているか、カバレッジの不足はどこかを突き合わせるのに、数時間から数日かかると説明されています。
2. playbook を選びます。意図を説明して Perception に playbook を選ばせることもできます。ここでは「Protect against a threat」が選ばれ、仕事に合う TI 記事も推薦されます。
3. **外部の TI 記事に対応**する機能（threat intelligence agent）を public preview で発表する、という説明がありました。Defender に今は無い情報も取り込めます。
4. 推薦された記事（Onyx Sleet。音声認識では Onyx Fleet とも聞こえます）を選び、セッションを開始します。ワンクリックでエージェントのチームが動き出します。エージェントはセキュリティチームの役割（場合によってはそれ以上）を表し、playbook は特定の成果・達成すべき仕事を表します。
5. まず **TI agent** が記事を分析し、主要なアーティファクトを抽出して、playbook 内の他のエージェントに引き継ぎます。これらはデモ 1・2 に出たエージェントと同じですが、受け取るコンテキストと入力によって、行う仕事が変わります。
6. 例えば detection authoring agent は、TI 記事と TI agent が抽出した IOC・TTP に基づいて、検出のギャップがないかを分析できます。Corina 氏はこれを「reactive と proactive の違い」と言っています。
7. **recon agent** が、この攻撃者に対して脆弱になる攻撃経路を探ります。本番資産をスキャンするための許可を求めてくるので、承認します。
8. recon agent が、注目すべき Web アプリを見つけます。条件付きで Web App Pen Test に引き継ぎ、これも承認します。TI agent から recon、そして Web アプリの順に、コンテキストが引き継がれます。
9. MDASH がスキャン済みで、結果が組み合わされます。Web App Pen Test は一般的なテストではなく、**その脅威アクターが使う脆弱性や TTP に関係するもの**に絞って検証します（デモ 2 と重なるため駆け足で進めました）。
10. 次に detection authoring agent が、一般的な推奨ではなく、**自分の環境とこの脅威アクターの文脈に合わせたカスタム検出ルールと推奨**を出します。修復や修正の完了より前でも、攻撃者が入ってきたときに検出できる状態にできます。
11. ポスチャー（環境の堅牢化）の話に移ります。多くの場合、構成ミスや脆弱性などの推奨事項が数百〜数千件あり、優先順位付けが難しい状況です。エージェントは長いリストを推論して、実行可能で目的に関連する、優先順位付きの絞り込まれたリストにします。
12. 修復を進めると、修復計画が作られます。内容をレビューして、進めるかどうかを決めます。Web アプリに対する対応の 1 つは、GitHub でのコード修正の提供で、編集することも、開発者に送ることもできます。
13. 最後に、すべてのエージェントが何をし、何を達成したか、成果は得られたか、どんなアーティファクトがあるかの**最終レポート**が出ます。CISO に、守られているか、どんなギャップがあったか、検出カバレッジとポスチャーの強化のために何をしたかを詳しく報告できます。

Naama 氏のまとめでは、CISO からの 1 つの質問に対し、エージェントが協調して答えを出し、検出カバレッジとポスチャーを改善する行動も取りました。通常は数日から数週間かかることもあるところを、**数時間**で答えが出て、セキュリティが改善されるようになった、と述べています。

## 7. 注意点・発表者の気付き

- **センシティブな操作は人が承認する**：検出ルールの追加（SNR が低いと、不要なアラートでキューがあふれる可能性がある）、ペネトレーションテストの計画、本番資産のスキャン、修正 PR の下書きの作成は、エージェントが自動で進めず、ユーザーの承認を求めると説明されています。
- **Pen Test は自分が所有するアプリだけ**：Web App Pen Test の設定には、DNS による所有確認の検証が組み込まれている、と説明されています。
- **同じエージェントでも、受け取るコンテキストで動きが変わる**：デモ 3 では、Web App Pen Test も検出作成も、一般的な内容ではなく、特定の脅威アクターに絞ったものになる、と強調されました。
- **修正は開発者との共同作業**：Perception は PR を作成して開発者に渡しますが、承認は開発者側が行います。
- **機能の提供状況**：GA は 6 つのエージェントと定義済み playbook、public preview は Web App Pen Test を使った proactive security と、外部 TI 記事に対応する TI agent です。
- **発表で触れられていないこと**：6 つのエージェントの内訳、価格・ライセンス、前提となる製品や必要な権限の詳細、AWS・Okta・Salesforce に続く対応データソースの具体名は、トランスクリプトでは語られていません。

## 8. 利用者にとっての利点

発表で語られた利点と成果は次のとおりです。

- **夜間やシフト間のインシデントも放置されない**：Automatic Triage and Investigation により、朝にアナリストが来たときは、最も価値の高い発見だけを見れば済みます。
- **検出カバレッジの不足を 1 クリックで埋められる**：検出エンジニアへの引き継ぎで数日かかり得た作業を、調査と同じワークフローで進められます。
- **数十〜数百の脆弱性から、悪用が検証されたものに絞れる**：デモでは 48 件が 3 件になりました。
- **脅威インテリジェンスの確認が数時間に**：通常は数日から数週間かかるところを、数時間で答えと改善まで進められると説明されました。
- **開発チームとの連携**：GitHub の PR に、修正の理由を含む情報が付いた状態で届きます。
- **コントロールと監査**：重要な操作は承認制で、すべての操作がログされ、エージェントは専用の ID と最小権限で動きます。
- **顧客事例（Nationwide）**：脅威インテリジェンスの分析が 4 週間から 4 時間に短縮されたと報告されています。

## 9. まとめ

Microsoft Perception は、blue、red、green のエージェントがコンテキストを共有して協調し、インシデントの調査、検出の強化、脆弱性の検証と修復、脅威インテリジェンスへの対応を、playbook として自動で進める agentic security システムです。このセッションでは、午前 1 時 23 分の Caldova を例に、「情報はあったのに行動が間に合わなかった」という問題を、3 つのデモで解決する流れが示されました。

Perception はこの日に GA となり、6 つのエージェントと定義済みの playbook が提供されます。Web App Pen Test を使った proactive security と、外部の TI 記事への対応は public preview です。登壇者が強調したのは、自律性を高めながらも、重要な操作は人が承認し、操作はログされ、エージェントは専用の ID と最小権限で動くという点です。今日から始める方法としては、Automatic Triage and Investigation をオンにすることと、コードスキャナーの結果を Web App Pen Test で検証することが挙げられました。
