# THRSP1146 Get a clean signal, faster answers with Cribl and Microsoft Sentinel

## 1. はじめに

このセッションは、増え続けるテレメトリデータ（ログ、トレース、メトリクス）を Microsoft Sentinel に送る際に、データをどう整理・振り分けて「きれいなシグナル」にするかを扱う約 23 分の発表です。登壇者は Cribl の関係者で、同社の **AI platform for telemetry** のうち、**Cribl Stream**（データの経路上でデータを加工・振り分ける製品）と **Cribl Search**（保存先にあるデータをその場で検索する製品）を中心に、Sentinel との組み合わせ方を説明します。

発表の主張は次のとおりです。まず、AI の利用でデータ量が急増しているのに予算は増えないため、Sentinel に入れるデータを経路の途中で絞り込み、低価値なデータは安い保存先に回します。次に、安い場所に置いたデータは、必要なときにそのまま検索できる仕組み（フェデレーション検索）で取りに行けばよく、移し替える必要はありません。最後に、アナリストには自然言語の窓口を用意し、裏側の保存先やクエリ言語の違いを見せないようにします。

このセッションでは、画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。

## 5. 発表内容の詳細

### 5.1 問題提起：データ量の増加と、データの「形」の変化

セキュリティ部門は、予算内で「問題がないこと」を証明しなければなりません。そのため、Sentinel はテレメトリの送り先として有力な候補になります。しかし、発表者は「答えが出ないときは、より多くのデータが必要になる」とも述べています。

加えて、データの形が変わりました。かつて ArcSight、CEF、IBM の Leaf（聞こえた表記）、syslog などで扱っていたメッセージは、あまり大きくなりませんでした。いまは OpenAI の compliance API からチャットセッション全体を取得でき、その中には会話の本文だけでなく添付ファイルなども含まれます（発表者は、ある曲を別の言語に変換するよう頼み、WAV ファイルを添付する、という冗談交じりの例を挙げています）。メールの記録でも同様です。

コンプライアンス上「すべてのデータを SIEM に入れる」というパイプラインがあると、Base64 エンコードされた添付ファイルまで Sentinel に入ります。発表者は「その添付は送らなくてよいのではないか」と問いかけています。ChatGPT のログに添付が残ったままだと、調査が遅くなる、という指摘です。

### 5.2 ノイズが調査サイクルを遅くする

SIEM の中にノイズが多いと、調査のサイクルタイムが長くなります。発表者は「1 秒あたり 1 万件のシグナルが本当に有効なのかを確認する作業」が非常に厳しくなると述べています。

対策として、不要なデータはパイプラインから外します。ただしコンプライアンス要件があるため捨てるわけにはいかず、Blob などの安価な保存先に置きます。入口でシグナルをきれいにすると調査が速くなり、結果として対応に自信が持てるようになる、という流れです。

### 5.3 AI platform for telemetry の構成

Cribl のこの基盤は、数年前は「送信元が左にあり、真ん中にあるものを通して、右の送信先にきれいなデータを出す」という蝶ネクタイ（bow tie）型の図で説明していたそうです。その役割は現在も残っており、図の下段の **Stream** のレベルがそれにあたります。構成要素は次のとおりです。

| 要素 | 発表での説明 |
| --- | --- |
| Stream | 送信元と送信先の間に入り、データを加工・振り分けする層。Sentinel などの送信先へ書き込む |
| Edge | ノートパソコンなどのエンドポイントに常駐してログやメトリクスを集める。データの発生源にできるだけ近い場所で、削除・変更・振り分けをするため |
| Search | データの保存場所に出向いて検索する（フェデレーション）。5.5 で詳しく説明されている |
| Lakehouse | データを一か所に集めて、検索を高速にするためのローカルな仕組み |
| Apps | 上記の上に作るアプリケーション。検索などの用途を作る場所 |

発表者は、データをできるだけ発生源に近いところで扱うほど、「データをいち早く削る・変える・別の方向に回す」ことができると説明しています。

### 5.4 複数の送信先・保存期間・スキーマを扱う

Stream の役割として、発表者は次のような場面を挙げています。

- Blob ストレージなどのオブジェクトストレージや、データレイクへ振り分ける。
- CISO や CIO が、データストレージ事業者と結んだ契約で「すべてのデータを 7 年間保管してほしい」と要求してくる。万が一その契約がうまくいかない場合に備えて、別のコピーも持つ必要がある。
- 合併・買収（M&A）のあと、相手の組織が別のインフラとデータ保管の計画を持っている。移行までの 6 か月は、2 つのレイクに送り先を分けなければならない。

つまり、複数の送信先、複数の保管理由、複数の期間、複数の形式、複数のスキーマがあるときに、Cribl が役立つという説明です。

### 5.5 Cribl Search とフェデレーション検索

発表者は、データを散らかすだけでなく「後でまとめて使える」状態にすることも重要だと述べます。その層が検索です。ここでは **フェデレーション検索**（データのある場所に出向いて検索する方式）を重視しています。

理由は 2 つ語られました。1 つは、複数の企業が統合されて 10 年、20 年分の履歴があちこちに置かれているケースがあるからです。もう 1 つは、データを 1 か所に移し替える移行計画が、実際には「まあまあ（ish）」程度にしかうまくいかないことが多いからです。しかも、テレメトリの **90% は一度も見られない**そうです。必要になるまで価値がないので、必要なときに取りに行く方が現実的だという考え方です。

見る場面は、少なくとも四半期ごとに監査人へ「データを保管している」ことを示すとき、そして 1〜2 週間に一度ほど何か問題が起きたときです。発表者は「今月は 2 日に 1 回くらいかもしれない」と冗談交じりに述べています。

ただし、フェデレーション検索はネットワークをまたぐので遅くなることがあり、日常的な検索には向きません。発表者は「速くし続けているが物理的な制約がある」としています。そこで、**Lakehouse** を使ってローカルで検索する選択肢も用意されている、と説明しています。さらにその上に Apps を作れます。発表者は、最近は「vibe coding の世界」なので、CIO から 20 年間求められてきたリスクダッシュボードを「欲しいものを AI に伝えて作る」こともできる、と話しています。

### 5.6 Microsoft Sentinel との組み合わせ

発表者は、Cribl が **ベンダーニュートラルなパイプライン** であることを強調しています。Microsoft だけで固めている組織なら、E5 に含まれるものなど、ほかの選択肢もあるだろうと認めたうえで、次の点を挙げています。

- データを経路の途中で **フィルタ・エンリッチ** する。
- 価値の低いイベントは最も安い保存先に回し、必要になったら、より速い場所に戻す。
- Sentinel へのオンボードを速くする。Sentinel にデータを入れるための仕組みが組み込まれており、E5 のライセンスに含まれるものと非常によく連携する。
- **テンプレートキット** を用意している。発表者がドキュメントやブログ記事を見直したところ、典型的な上位 6 つのシステムのデータを Sentinel に取り込むための作業は合計で約 50 ページ分あった。それが今ではアプリになっており、ボタンを押し、フォームに入力し、キーを入れるだけで済む。
- 送信元と送信先の間に挟まる位置にコード実行環境（発表者の言う「bump in the wire」）があるため、**PII のスキャン** や、送信先に送る前の **マスキング** もできる。

発表者の考え方は、「できるだけ左（上流）で処理するほど、着地した後に解きほぐす手間が減る」というものです。Blob ストレージ（S3 や Azure など）は書き込みには向いているが、読み出して書き直すことにはあまり向いていない、とも述べています。

### 5.8 データ階層化の課題と自然言語インターフェース

データを複数の場所に置き、複数の場所から読めることで、**データ階層化（data tiering）** が可能になります。目的はコストです。予算は限られているのに、データの伸びが大きいからです。

階層化を導入した顧客に聞くと、「節約はできている」という答えが返ってきます。ところが SOC のアナリストに聞くと、「必要なデータが Blob にあるのか、SIEM にあるのか、Google にあるのか、Sentinel にあるのか、Databricks や Snowflake にあるのかが覚えづらい」という声が上がります。しかも、生（raw）のまま Blob に入れたデータは、コンプライアンスの面では安全で簡単でも、一般のユーザー、時には非常に優秀なユーザーにとっても扱いにくい、という指摘です。

ここ数年で変わったのは、インターフェースに自然言語で頼めるようになったことです。例として、「上位 10 のネットワークトーカー（通信の多いもの）と、6 か月前の同じ顔ぶれを知りたい」という問い合わせが挙がりました。後半（6 か月前）の部分は Cloudflare や Databricks（聞こえた表記）に取りに行き、もう一方は "NGSIM" と聞こえるシステムに聞く必要があり（音声認識の都合で表記が確定できません）、言語も API も異なります。それをアナリストに見せる必要はなく、アナリストは「IP アドレスを入れた 30 日分のクエリ」を実行したいだけです。

そこで、チャット型のダッシュボードを置き、自然言語で質問できるようにします。そのインターフェースは Cribl のものである必要はなく、Claude Desktop、Cursor、Sentinel の中でもよいとされています。Cribl は最近、AI インターフェースを数多く作っており、次のことができると発表者は述べています。

- クエリを横取りして、**その問題に対応できる最も安いモデル** に振り分けるルーターとして動く。
- 質問に応じて、正しい言語とスキーマを判断し、データを取りに行く。
- **ディープインベスティゲーションモード**（deep investigation mode）では、2、3、5 個の仮説を同時に立ててすべて試し、最もうまくいったものを選ぶ。最後に PDF を出力する。

この最後の機能は、「またフィッシングメールが来た」という状態から、「本当に成功した攻撃がありそうなので調べる」状態に進むときのためのものだと説明されています。調査で見たこと、試したこと、次に進むべきことを、KQL、結果、Markdown の説明を組み合わせた比較的静的な形式（フォレンジックの成果物）として書き出したい、という場面です。

### 5.9 Security Copilot との連携と、調査後の動き

発表者は、検索経路が 1 つで、Copilot への経路が 2 つあると述べています。**Security Copilot** は、この種の技術を使う優れたインターフェースだとされています。構成は次のとおりです。

- コールドデータ（使用頻度の低いデータ）は、コストが最も安い場所に置く。
- フェデレーション検索のインターフェースが、MCP を通じてデータを受け取り、MCP を通じて動作する。API やエンドポイントも使えるので、1 つの窓口として Copilot につなげられる（この部分は音声が不明瞭で、細部は確定できません）。
- 検索の結果を Security Copilot に渡す。分析の結果も渡せる。

調査の後に取れる行動として、発表者は「最初にやるのはデータをさらに取りに行くことだ」と述べ、次の例を挙げています。

1. **Cribl Stream の replay** を起動し、必要なデータを元の保管場所から取り出して、誰かが見られる場所に置く。（「90% は見られない」が、そのうち見る必要が出たデータを取りに行く場面）
2. 調査用のインターフェースで、同種のインスタンス（ほかにも発生していないか）を検索する。
3. Verizon DBIR を引き合いに、滞留時間（dwell time）が長くなってきた点を踏まえ、多くのデータを対象にした「長くゆっくりした」ハンティングを開始し、結果が戻るのを待つ。
4. インシデント後の分析のあと、ほぼ自動化されたランブックを起動する。結果は構造化された形で Sentinel に落とし、次の手順に使う。発表者は、制御用のインターフェースを触るために別のベンダーを追加で導入しなくて済む、とも述べています。

## 7. 注意点・発表者の気付き

- 着地した後のデータ（Blob や S3 など）は、書くのには向いても、読み出して書き直すのには向きません。そのため、加工やマスキングはできるだけ上流（経路の途中）で行う、というのが発表者の主張です。
- コンプライアンスの要件があるのでデータは捨てられません。「捨てずに、安い場所に置く」のが前提です。
- フェデレーション検索は、ネットワークをまたぐ分、遅くなることがあります。日常的な検索には向かないので、Lakehouse でのローカル検索を併用する、と説明されています。
- データ階層化でコストは下がっても、アナリストは「どこに何があるか」「別のシステムの言語や API」に苦労します。そのため自然言語の窓口が必要になる、というのが実際の顧客現場での気付きとして語られました。
- Microsoft だけで固めた組織の場合は、E5 の中にほかの選択肢もあるだろう、と発表者自身が述べています。
- 発表では、料金、対応する具体的なデータソースの一覧、性能の詳細などには触れていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 低価値なデータを最も安い保存先に回し、Sentinel に入るデータを減らすことで、コストを抑えつつ調査を速くできる。
- 約 50 ページ分の作業だった Sentinel へのデータ取り込みが、テンプレートのアプリでボタンとフォーム入力で済む。

- アナリストが自然言語で、保存先の違いを意識せずに問い合わせられ、ディープインベスティゲーションで PDF などの成果物も得られる。

- 事例として、「68 日」「Sentinel 移行は 1 日あたり 4 TB」という数字（顧客名や詳細は不明）と、Yale New Haven Health での 2 週間の移行が紹介された。

## 9. まとめ

AI によってテレメトリの成長が、30% だった年率から 50〜60% 程度へ上がるなか、予算は増えません。Cribl のアプローチは、Sentinel に入れる前にデータを経路上でフィルタ・エンリッチ・マスキングし、低価値なデータは Blob などの安い場所に置くことです。置いたデータは、フェデレーション検索や Lakehouse で、必要なときに取りに行きます。SOC のアナリストには自然言語のインターフェース（Claude Desktop、Cursor、Sentinel、Security Copilot など）を用意し、保存先やクエリ言語の違いを隠します。入手は Microsoft Marketplace で、既存の Azure のコミットメントで調達できます。
