# THRSP1142 Enact one firewall policy across the enterprise

## 1. はじめに

このセッションは、Azure 環境が成長しても、ファイアウォールの運用負荷とポリシーの一貫性をどう保つかを扱う約 20 分の短い発表です。登壇者は Check Point の Dan Morris 氏で、同社の **Check Point Firewall as a Service**（Check Point が運用するクラウド型ファイアウォール）を例に、「インフラの運用はサービスに任せ、セキュリティの制御は自社に残す」という考え方を説明します。

発表は問いかけから始まります。「Azure 環境が大きくなるとき、ファイアウォールのインフラも一緒に大きくなるべきか」という問いです。Morris 氏の答えは、**ファイアウォールのインフラとセキュリティチームは、環境と一緒に増やし続ける必要はない**というものです。インフラをサービスとして提供してもらい、ポリシーは 1 つの枠組みで集中管理しながら、事業部門にも変更権限を委任する、という構成が示されます。

## 3. 何に関する発表か

テーマは、クラウドの成長に合わせた **ファイアウォール運用の複雑化** と、その解き方です。Morris 氏によると、新しいアプリ、VNet、サブスクリプションが増えるにつれて、ファイアウォールの台数、キャパシティ、計画、そしてポリシーの数が増え、しかもそれらを環境内で一貫させ続ける必要が出てきます。クラウドは動的にスケールするので、セキュリティも同じ速度で追従しなければならない、という問題意識です。

発表の流れは次のとおりです。

1. 環境が成長すると何が難しくなるか（4 つの課題）
2. 運用とセキュリティ制御を分ける考え方
3. 1 つのポリシー枠組みと委任された制御
4. Azure のタグなど「クラウドのコンテキスト」を使った動的なポリシー
5. インライン保護と一元管理（Check Point のモデル）
6. ハブ＆スポーク構成での 3 つのトラフィックパターン（インターネット向け、東西、ハイブリッド）
7. Microsoft Marketplace での購入と利用
8. まとめと次のステップ

## 4. 発表者が伝えたいメッセージ

メッセージは、ファイアウォールそのものが問題なのではなく、**クラウドの規模でファイアウォールを運用することが問題**だという点にあります。Morris 氏は、セルフマネージドのファイアウォールではポリシーとインフラの両方を顧客が持つことになり、サイジング、監視、パッチ、アップグレードまで背負うことになると指摘します。そこで、インフラの作業はサービスに任せ、セキュリティ制御は手元に残すという役割分担を勧めています。

もう 1 つの主張は、ポリシーの運用を「中央のセキュリティチームだけ」でも「各事業部門に丸投げ」でもなく、その間で設計することです。中央は全社共通の土台（ガードレール）を決め、各事業部門は自分たちのクラウドアプリの層を自分のペースで変更できるようにします。

## 5. 発表内容の詳細

### 5.1 環境が成長すると起きる 4 つの課題

Morris 氏は、クラウド環境が成長するときに繰り返し見られる課題として、次の 4 つを挙げています。

| 課題 | 説明 |
| --- | --- |
| パッチ適用 | メンテナンスウィンドウの計画、テスト、検証、問題が起きた場合のロールバックが必要で、これがすべてのリージョン・すべてのファイアウォールに掛け算で増えて運用負担になる |
| 脅威防御（threat prevention） | ファイアウォールを置くのは始まりにすぎず、最新の脅威防御ポリシーやシグネチャに保ち続ける必要がある。脆弱性が次々に出るため、更新し続けること自体が難しい |
| 運用効率 | クラウド環境が大きくなってもセキュリティチームは同じペースでは増えない（まったく増えない場合も多い）ので、人を増やさずに一貫性を保つ方法が要る |
| ポリシードリフト | 環境が動的に変わるなかで、社内（corporate）や政府（government）のポリシーに沿った設定を、常に同じ形で適用し続けるのが難しい |

さらに、変更の適用を中央のセキュリティチームに頼るとボトルネックになります。逆に事業部門ごとに独自のポリシーを持たせると、一貫性とガバナンスが失われます。Morris 氏は「どちらの方法もクラウドではうまくスケールしない」と述べています。

発表では、サブスクリプション、テナント、複数リージョンといった広がりと、パッチ、アップグレード、脅威防御ポリシー、メンテナンスの効率が、アジェンダの最初の論点として示されています。

### 5.2 運用とセキュリティ制御を分ける

最初のベストプラクティスは、**運用とセキュリティ制御を切り離す**ことです。従来のセルフマネージド型では、顧客がセキュリティポリシーとインフラの両方を持ち、規模が大きくなればそれに見合うリソースも自分で確保しなければなりません。

Firewall as a Service では、スケーリング、監視、パッチ適用、キャパシティの管理、レジリエンス、ヘルスチェックといったインフラ側の作業をサービスが担います。一方で、管理されることは制御を手放すことではありません。顧客の手元に残るものとして、次が挙げられています。

- セキュリティポリシー
- ルーティングの判断
- ネットワークのセグメンテーション
- 脅威防御のプロファイル
- トラフィックそのもの

Morris 氏はこれを「インフラの作業は取り除くが、セキュリティ制御は取り除かない。その均衡が目標だ」とまとめています。

### 5.3 1 つのポリシー枠組みと委任された制御

運用の負担が軽くなると、次は「Azure 環境が増えても、ポリシーを一貫させつつ、中央のセキュリティチームをボトルネックにしない」という課題が残ります。解決策として示されたのが、**委任された制御を伴う 1 つのポリシー枠組み**です。

- 中央のチームは、脅威防御、コンプライアンス制御、ログ、可視性などの **全社共通のベースラインポリシー** を作り、すべての環境に適用します。
- 各事業部門には、自分たちのクラウドアプリを管理するための個別の層を与えます。
- 中央チームはガバナンスと可視性を握り、各チームはクラウドの速度で変更をプッシュできます。

Azure ではポリシーを静的にする必要はなく、静的 IP を使わずにダイナミックオブジェクトで Azure のリソースやタグをポリシーに反映できる、と説明されています（詳細は 5.4）。

ログとアラートは、Microsoft Sentinel や SOC のような一元的なサーバーに送って、ファイアウォールの活動やその他のテレメトリをまとめて扱えるようにします。Morris 氏は「すべてを中央集権にするのが目的ではなく、ガードレールを中央に置き、ローカルで必要な変更は委任するのが目的だ」と述べています。

### 5.4 Azure のコンテキストを使った動的なポリシー

従来のファイアウォールポリシーは静的な IP アドレスを前提に作られています。しかし Azure のワークロードは頻繁に変わり、スケールアウトで IP も変わります。変更のたびにポリシーやオブジェクトを更新するのは負担になるため、Morris 氏は **クラウドのコンテキストを軸にポリシーを組む** ことを勧めています。IP アドレスの代わりに、Azure のタグ、VNet、サブスクリプションの情報、ワークロードのメタデータなどが使えるという説明です。

簡単な例として、次の説明がありました。

- 「store servers」という Azure 上のタグが付いたサーバー群が、warehouse（倉庫）の VNet と通信する必要がある。
- サーバーごとに静的 IP のルールを作るのではなく、送信元は Azure 上の「store servers」というタグ（アイデンティティ）、宛先はワークロードの VNet として定義する。
- Azure が需要に応じてデータベースをスケールアップしたとき、新しいサーバーにはタグが自動で付き、ポリシーも自動で適用される。顧客はオブジェクトを新規作成したり IP を調べたりする必要がない。

> 補足：この例では、タグ名が「store servers」と「web servers」の両方で語られ、増えるサーバーも「データベース」と表現されています。名称は音声上で揺れているため、個々の名前は確定できません。伝えたい点は「タグに基づくポリシーがワークロードの増減に追従する」ことです。

この方法で手作業のメンテナンスが減り、セキュリティが環境の実際の動きに揃った状態で保たれる、と説明されています。

### 5.5 Azure に素直に収まるサービスであること

Firewall as a Service を選ぶときの条件として、Morris 氏は次の点を挙げています。

- マネージドサービスは、セキュリティチームからインフラの負担を取り除くためのもので、負担を増やすものであってはならない。
- サイジングやクラスターの構築、スケール時の対応を意識しなくて済むこと。
- 複雑なネットワーク構成を新たに持ち込まないこと。VNet ピアリング、UDR（ユーザー定義ルート）、ルーティングドメインといった既存の仕組みに収まり、アプリケーションの接続やトラフィックの向け方が「いつもの感覚」でできること。
- それでも、ポリシー、ログ、可視性を 1 か所で扱えること。

「ファイアウォールは環境を変えるのではなく、環境に合わせて動くべきだ」という考え方です。

### 5.6 インライン保護と一元管理（Check Point のモデル）

ファイアウォールを運用しやすくするだけでは半分で、もう半分は「トラフィックが当たったときに何が起きるか」だと Morris 氏は述べます。実際の強制は、Azure 環境に出入りするトラフィック、あるいは VM 間、ワークロード間、さらには AI アプリケーション間のトラフィックで行われます。許可された安全なトラフィックは通り、脅威が検出されれば宛先に届く前に止める、という考え方です。事後に気づくのではなく、流れている最中に守ることを重視しています。

同時に、Azure 環境ごとに別々のポリシーを管理するのではなく、サブスクリプションや環境、トラフィックが増えても **ポリシーを定義する場所は 1 か所** にします。この「インライン保護」と「一元管理」を組み合わせたものが Check Point のモデルだという位置づけです。

具体的には次のとおりです。

- Cloud firewall as a service では、トラフィックが複数層の脅威対策でインライン検査される。例として IPS、アンチウイルス、脅威エミュレーションが挙げられ、ほかにも多くのブレード（機能）があるとのこと。
- これらは **Threat Cloud AI** で駆動されており、継続的に更新され、状況の変化に応じて保護が自動で適用される。
- 管理は管理サーバー（management station）の **Smart One または Smart One Cloud** で行う（音声からの聞き取りどおりの表記で、正式な綴りは音声認識の都合で確定できません）。
- 同じ考え方を **AI ファイアウォール** にも広げている。AI ファイアウォールは、エージェントやツールなどの AI トラフィックについて可視性と制御を提供し、AI レベルでセキュリティと脅威防御を適用する。

従来のワークロードでも AI トラフィックでも、「インラインで強制し、管理は 1 か所に集める」という考え方は同じだ、と述べています。

### 5.7 3 つのトラフィックパターン（ハブ＆スポーク）

アジェンダでは、ハブ＆スポークのモデルでインターネット向け、東西、ハイブリッドの各トラフィックを守る構成が予告されていました。実際の説明は次の 3 つです。

**(1) インターネット向け（イグレス）**

最も一般的なユースケースとして説明されました。図の左側が顧客テナントで、複数の VNet にワークロードがあります。右側が Check Point が管理するファイアウォール（Check Point Firewall as a Service）です。

- インターネットに出るトラフィックは、VNet ピアリングとルーティングで Check Point Firewall as a Service に向けられる。
- ファイアウォールに到達した時点で、適用したセキュリティプロファイルや脅威防御プロファイルによる検査が行われる。拒否されたものは宛先に届く前にその場で遮断される。
- イグレス通信なので、送信元 NAT（source translation）を適用することもある。
- ロードバランシング、スケーリング、可用性、パッチ適用など、ファイアウォールの運用は Check Point 側が担う。顧客は、トラフィックの経路とセキュリティポリシーを管理するが、ファイアウォールのインフラは運用しない。

**(2) 東西トラフィック（Azure 内の VM 間）**

同じアーキテクチャで、トラフィックの流れだけが変わります。例として、QA が HR のサブネットと通信するケースが挙げられました。VNet ピアリングと UDR を使って同じ経路をたどって検査され、同じセキュリティポリシーが適用され、拒否や脅威検出があればその場でブロックされます。Morris 氏が強調するのは、**東西トラフィックは Azure の中にあるというだけで、自動的に信頼してよいわけではない**という点です。

**(3) ハイブリッド接続**

Azure を使う企業の多くは Azure だけで完結しておらず、データセンター、リモートユーザー、支店、企業内のその他の部分にアクセスする必要があります。この例では、トラフィックは ExpressRoute または VPN のゲートウェイを通って Azure に入り、そこから Firewall as a Service に誘導され、同じセキュリティモデルで検査され、ポリシーに従って破棄されます。

3 つのパターンを通じて、保護の方法（同じソリューション、同じポリシー枠組み、同じインライン防御）は変わらない、と整理されています。

### 5.8 Microsoft Marketplace での購入

技術面だけでなく、「購入と利用のしやすさ」も重要だというのが後半の話です。Check Point Firewall as a Service は、**Microsoft Marketplace 経由の SaaS 型サービス**として提供されます。多くの顧客はすでに Microsoft と購買関係があるので、新しい契約関係や別の請求経路を作らず、既存の調達プロセスに乗せられます。さらに **Microsoft Consumption Commit（MACC）** を、Firewall as a Service の支払いに充てることができると説明されています。Marketplace は採用時の摩擦を減らすもう 1 つの手段だという位置づけです。

## 7. 注意点・発表者の気付き

- 問題は「ファイアウォール」ではなく「クラウド規模での運用」にあり、中央集権と各部門任せのどちらの極端もスケールしない、というのが発表者の見立てです。
- マネージドサービスを選ぶときは、インフラの負担を減らすだけでなく、**制御（ポリシー、ルーティング、セグメンテーション、脅威防御プロファイル）を手放さない**ことが条件です。
- 新しい複雑なネットワークを持ち込まず、VNet ピアリング、UDR、ルーティングドメインなど既存の仕組みで接続できることが望ましい、と述べています。
- Azure 内の東西トラフィックも、自動的に信頼されたものとして扱わないよう注意しています。
- 発表では、料金、対応リージョン、性能数値、具体的な導入事例、AI ファイアウォールの詳しい機能などには触れていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- パッチ、スケーリング、監視、キャパシティ、ヘルスチェックなどのインフラ運用を Check Point 側に任せられ、セキュリティチームを増やさずに済む。
- 全社共通のベースラインを中央で定めつつ、事業部門が自分の層でクラウドの速度で変更できる。
- Azure のタグなどに基づく動的ポリシーで、ワークロードの増減に合わせたポリシーの手動更新が減る。
- インターネット向け、東西、ハイブリッドの 3 つのトラフィックを同じポリシー枠組みで検査できる。
- 既存の Microsoft との購買関係と MACC を使って調達できる。

## 9. まとめ

Morris 氏の結論は、ファイアウォールのインフラは**サービスとして提供・運用してもらう**一方で、セキュリティチームは制御を手元に置き、必要な部分を各チームに委任する、という分担です。ポリシーは中央の 1 つの枠組みから、ガードレールとして管理します。IP ではなく Azure のコンテキストに基づく動的なポリシーにすることで、環境の変化に追従させます。保護は、インターネット向け、東西、ハイブリッドのいずれでもインラインで行い、購入は Microsoft Marketplace で既存の調達や MACC に乗せられます。詳しい説明は、ブース 5227、QR コードからのデモ予約、Marketplace の提供ページで確認できるとのことです。
