# BRK317 What the Frontlines Reveal About Modern Security

## 1. はじめに

このセッションは、Microsoft Defender Experts チームの 2 人が、インシデント対応の最前線で実際に見てきた事例をもとに、現在のセキュリティで何が起きているのかを語る内容です。話は大きく 4 つに分かれます。最近の傾向、脅威インテリジェンスの使い方、インシデントが起きる前にレジリエンス（回復力）を築くこと、そして AI が攻撃と防御の両方に与える影響です。

発表全体を通した結論は 3 つに整理されています。**脅威インテリジェンスは「自分の組織に当てはめて行動できる」ものでなければならないこと、レジリエンスはインシデントの前に作るものであること、防御側も攻撃側と同じ「マシンスピード」に追いつく必要があること**です。

具体例として、ClickFix という手口の新しい変種を追った調査（28 本の長いスクリプトを解析した事例）と、2 つの攻撃グループが同時に入り込んでいたランサムウェア事案が紹介されます。なお、このセッションでは画面を使ったライブデモは行われておらず、スライドと口頭の説明が中心です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK317](https://ignite.microsoft.com/en-US/sessions/BRK317)

## 4. 発表者が伝えたいメッセージ

発表者の主張は、次の 3 点に集約されます。

1. **脅威インテリジェンスは、レポートを読んで終わりにしない。** 「そのレポートを使って何をしたか」が問われます。自分の環境でその挙動やインジケーターを探し、検知の前提を疑い、変種も試すことで、初めて「備えた」と言えるという考えです。
2. **レジリエンスはインシデントが起きる前に作る。** Troy 氏は、攻撃を受けた時点では手遅れになることが多いと述べています。保有していないデータは、インシデント中に後から作れません。何を守るべきかを把握し、法務・人事・広報・給与部門まで含めた現実的な演習で準備し、意思決定の権限を事前に決めておく必要があるとしています。
3. **防御側は AI を使ってマシンスピードに追いつく。ただし判断を手放さない。** AI の目的は盲信ではなく、専門家に時間を取り戻させることです。攻撃側も AI を使うため、機会は防御側だけのものではないとも述べています。

## 5. 発表内容の詳細

### 5.1 最前線で見える 3 つの傾向

Troy 氏は、最前線で見ている傾向を 3 つ挙げています。

**(1) ID が悪用され続けている。** Entra ID や O365 のアカウントだけではありません。SaaS アカウント、OAuth アプリケーション、SSH キー、パスキーなど、ID を持つものはすべて、脅威アクターに悪用されるリスクがあります。1 年前も 2 年前も今日も明日も同じだと述べています。

**(2) 1 件のインシデントが、より広いギャップを明らかにする。** すべてがつながっている現在、攻撃者に必要なのは侵入口 1 つだけで、そこから多くのことが見えてしまいます。さらに、特に AI で加速された攻撃者は、前提知識ゼロで ping やクエリを投げて組織の情報をすべて探れるため、組織の内部を防御側より広く、よく見られることがあるという指摘です。

**(3) AI が前提を変えている。** Troy 氏は、AI は過去になかったことをしているわけではなく、「より速く、より大規模に」行っているのが問題だと説明します。例として、脅威アクターが 1 日に 10 組織を狙っていたところを、1,000 組織、10,000 組織、100,000 組織へと広げられる点を挙げています。横展開も、探索も、ゼロデイの発見も速くなり、インシデント対応とハンティングに影響します。

これを受けた「現代のセキュリティで明らかになったこと」が、次の 3 点です。

- 脅威インテリジェンスの重要性が増している。ランサムウェアの脅威アクターは同じではなく、非常に速く動く Octo Tempest（別名 Scattered Spider）のようなグループもあれば、せいぜい恐喝（extortion）にとどまるグループもあります。行動につながるインテリジェンスがあれば、相手の違いとリスク、必要な統制・解決策を見分けられます。
- レジリエンスが重要。被害を受けた時点では遅すぎることが多く、継続的な取り組みです。インシデントがあったこと自体は失敗ではなく、改善点を知る学びの機会だと述べています。
- 防御は AI の速度に追いつく必要がある。ただし AI は全知全能ではありません。AI はデータの上に成り立つため、まずデータが必要です。そのうえで、持っているデータへの理解を深めるのに AI が役立ちます。

### 5.2 ClickFix の事例と、脅威インテリジェンスを「行動」につなげる（Vlad 氏）

Vlad 氏は、見慣れた脅威が AI 時代にどう変化しうるかを、ClickFix で説明しました。ClickFix とは、画面の「人間ですか？（Are you human?）」のような確認や、トラブルシューティングを装った口実で、ユーザーに操作させてコマンドを実行させるソーシャルエンジニアリング手法です。確認のつもりで操作すると、実際には実行フェーズの命令を実行している、という仕組みだと説明しています。

多くのセキュリティチームは、調査し、記録し、共有できる脅威インテリジェンスを作り、啓発を進めるというサイクルで ClickFix に対応してきました。Vlad 氏は、今年だけで多数の変種、誘い文句（lure）、実行経路、そして回避の層が確認されたと述べています。

#### 脅威インテリジェンスを使ううえでの問い

Vlad 氏は、「対策済みだから疑わなくなった脅威は何か」と問いかけ、新しいものを監視するのと同時に、すでに知っているものを見直すよう促しています。知っている・共有した・啓発したことと、備えができていることは別だという主張です。脅威インテリジェンスのレポートを手にしたら、次の点を確認すべきだとしています。

- その挙動をハンティングしたか
- IOC（侵害の痕跡）を探したか
- 自環境に対して、前提や検知の仮説を検証したか
- 変種（異なる実行経路や痕跡）を試したか

#### 最前線の調査事例

調査は逆向きに進める必要があったとのことです。ハンティングの端緒は、普段は接続しない IP アドレスに不審な接続をしているマシンでした。その IP は悪意あるものでも不審なものでもなく、ただ「prevalent（一般的に出現するもの）」ではなかった、つまり過去にそのコンピューターが接続したことのない先だったという説明です。そこから一連の流れを再構築し、3 つの発見に至っています。

1. **初期アクセスは ClickFix（偽の検証画面）。** 既知の手口が、実際に通ってしまっていました。
2. **実行経路が、それまで理解していたものと変わっていた。** ClickFix の調査を始めた頃は、ダイアログ（音声では "wrong dialog window" と聞こえ、正確な名称は確定できません）経由で実行されたコマンドをすべて記録するレジストリキーがあり、これが ClickFix の特徴でした。今回は、ユーザーが PowerShell を開いて貼り付けるよう誘導されており、コマンドはあらかじめクリップボードに入っていたため、Ctrl+V と Enter を押すだけでした。実行後には、事後フェーズを理解するために解析が必要な、非常に長いスクリプトが 28 本見つかりました。
3. **ビーコニング。** デバイスが、先ほどと同じ、不審ではないが一般的でもない IP アドレスに接続していました。

調査の結果、攻撃者のコマンド＆コントロール（C2）が存在することを確認できました。Vlad 氏は教訓として、**「見慣れた痕跡がないことは、足場（foothold）がないことと同じではない」**と述べています。足場はあったのに、従来の経路をたどらなかったため見えなかったのです。この調査で、検知に関する前提が変わったと説明しています。

#### 調査を行動につなげる 3 つのステップ

Vlad 氏は、あらゆる調査・検知から次の 3 段階を取れるとして、スライドで示しました。

| ステップ | 内容 |
| --- | --- |
| 1. 前提を特定する | 自分の検知はどの実行経路を想定しているか。依存している要素が変わったり存在しなかったりしたらどうなるか。見逃した場合に何が起きるか |
| 2. 代替経路を考える | 検知が外れたとき、活動を示す別の証拠はないか。すべての答えを持つことは不可能だが、不確実性は「次にどこを見るか」「追加の証拠やアラートが必要か」を決める手がかりになる |
| 3. オーナーを決める | 足りない部分を見て修正する担当者を決め、修正をテストする |

ここで Vlad 氏は Defender Experts の 2 つのサービスが補完しあうと説明しています。**Defender Experts Threat Intelligence** は「自分の業界、地域、環境にとって何が脅威か。何を心配すべきか」に答えます。**Defender Experts Hunting** は、その理解と文脈を受けて実際に探しに行きます。この 2 つがつながっているべきで、レポートの数ではなく、レポートで何をするかが重要だという主張です。原則は「自分にとって重要な場所で、何を探すべきかを理解する」とまとめています。

### 5.3 インシデント対応の事例：2 つの脅威アクターが同時にいたランサムウェア事案（Troy 氏）

続いて Troy 氏が、DART が関わったインシデント対応の事例を紹介しました。自身が直接担当した案件ではないため、詳細には踏み込めないと断っています。1 件の対応で、実は 2 つの別々の脅威アクターが関与しており、調査が大幅に複雑になった事例です。

最初はランサムウェアの調査として始まり、当初の調査では、帰属先が Storm 2603 という脅威アクターとされました。Storm 2603 は、2025 年からパッチ未適用のオンプレミス SharePoint サーバーを狙っているグループです。Troy 氏は、脅威アクターに関するインテリジェンスがあれば、目的、永続化の方法、横展開の方法、ランサムウェア目的かデータ窃取目的かが分かると説明します。今回のケースでは SharePoint を狙って横展開し、最終的な主目的の 1 つはランサムウェアでした。

#### Storm 2603 の攻撃の流れ

発表で語られた順に整理すると、次のとおりです。

1. SharePoint のパッチ未適用の CVE を悪用して侵入
2. Velociraptor を展開。正規のフォレンジック調査ツールを、攻撃者が自分のために使った
3. ネットワークの探索を行い、Velociraptor を使って CloudFlare Tunnel を展開。これも正規ツールで、組織の内外への通信のトンネルに使われた
4. Velociraptor と CloudFlare を使い、Zoho Assist（正規のリモート管理・監視ツール）を展開
5. Visual Studio Code を使って Secure Shell を展開（これも正規ツール）
6. 永続化のために、自分たちのドメイン管理者アカウントを組織内に作成（信頼された ID の悪用）
7. 脆弱なドライバーを持ち込み（bring your own vulnerable driver）、セキュリティツールを無効化
8. WinRM による横展開と PowerShell を実行し、ランサムウェアを展開

#### 別の脅威アクターの存在

調査の過程で、Storm 2603 の手口と合わない TTP（戦術・技術・手順）が見つかりました。具体的には、正規の Windows DLL を装った DLL による DLL サイドローディングで、Storm 2603 が通常行う範囲の外でした。これが帰属の判断を大きく複雑にし、最終的に 2 つの別のアクターだと分かりました。

2 つ目のアクターは、DLL をサイドロードして横展開し、Active Directory の NTDS.dit をダンプしていました。システム 1 台に横展開するだけよりも深刻な手口です。さらに別の正規 Windows DLL をサイドロードしていました。この時点で、2 つ目のアクターの帰属先は特定できておらず、VPS プロバイダー経由の VPN で侵入していました。

#### この事例から見える共通の TTP と学び

- **公開された脆弱性の悪用。** Troy 氏が対応したほとんどのインシデントで、パッチが不足しているシステムがあります。完全にパッチが適用された組織は見たことがないとも述べています。正当な理由はあるにせよ、AI で組織のフィンガープリントを取り、脆弱なシステムを見つけるのが容易になることを考えるべきだとしています。
- **正規ツールを使った検知回避。** ここ数か月の複数の対応で同じ戦術を見ています。別の RMM ツールを使った例、CloudFlare 関連のツールを使った例（音声では "CloudFlare D" と聞こえ、正確な名称は確定できません）、live response を使ってマルウェアをダウンロードした例も挙げられました。自組織を理解していれば、Zoho Assist を見たときに「うちでは使っていない、許可していない」とどれだけ早く判断できるかが問われます。
- **マスカレード（偽装）とカーネルレベルのアクセスによる防御回避。** システムレベルのアクセスを得ると、検知を避ける手段が非常に多くなります。

> 注意：攻撃者は、ネットワークの「暗い端（dark edges）」にある、見過ごされパッチが当たっていないシステムを見つけるのが得意で、侵入するだけでなく居座るために作られている（永続化・横展開を行う）と述べています。そのため、サーバー、ファイアウォール、SaaS、ストレージアカウント、SAN サーバー、ハイパーバイザー、データベース、使っている RMM ツールやリモートアクセスツールなど、**自組織に何があるかを把握しておくこと**が基礎になります。

### 5.4 レジリエンス：インシデントが起きる前の備え

Troy 氏は、準備が影響を最小化する、という観点から次を挙げています。攻撃者に侵入された後で準備するのは、経験上遅すぎるという立場です。

**守るべきものを知る。** 計画も実行も大事ですが、存在しないデータは後から作れません。SaaS ソリューション、RMM ツールなど、何を持っているべきかを知っている必要があります。「インシデントとは何か」の定義も組織ごとに決めておくべきだとして、Troy 氏は前日のインタビューで「どうやってインシデントだと分かるのか」と聞かれたことを紹介しています。ドメイン管理者やグローバル管理者が侵害されれば当然重要ですが、それ以外にも基幹業務アプリケーション、Salesforce のような SaaS、GCP などの他クラウド、ハイパーバイザー、SAN などがあります。給与アプリのデータベースがどこにあり、監視されているかを、インシデント中に調べ始めるのでは遅いという例が示されました。

**計画だけでなく、準備態勢（readiness）を負荷テストする。** テーブルトップやサイバーレンジは優れた手段ですが、現実的に行う必要があります。参加者が SOC だけでは不十分で、法務、人事、広報、給与（payroll）部門など、重要なアプリケーションの関係者も巻き込むべきだという説明です。

**意思決定の権限を事前に決めておく。** 人手によるランサムウェア攻撃の最中を想像するよう促しています。ネットワークが暗号化されていて、侵入経路も、出ていく経路も、横展開も、永続化の方法も分からない状況で、次の判断が必要になります。

- ネットワークから自分たちを切り離すか。誰が承認するか
- 誰に通知するか
- 弁護士に連絡するか。どの弁護士か
- IR プロバイダーへの連絡方法は。そもそも IR プロバイダーはいるか

これらを事前に決めておき、明らかなものだけでなく、組織に影響する全体を考えておく必要があるとしています。

### 5.5 DART が提供するソリューション（Cybersecurity Incident Response）

Troy 氏は、スライドで DART のメニューを説明しました。すべては「Respond（対応）」の下にあるインシデント対応を軸にしています。

| 区分 | 内容 |
| --- | --- |
| Cybersecurity Incident Response（IR） | イベントがあり、調査や封じ込めの支援が必要なときに DART に依頼する |
| Compromise Assessment（侵害評価） | IR と同じツール・目的を、プロアクティブに行う。環境に攻撃者がいないかを見つけて推奨事項を示す。変種として、Active Directory と Entra ID に焦点を当てた Identity Assessment や、AI 環境に問題がないかと AI 構成への推奨事項を見る AI Assessment がある |
| Plan & Harden | IR 計画の策定支援（新しい組織や成熟度が低い組織向け）、ハードニングの支援（対象は音声が不明瞭で、Active Directory と Entra ID を指すと確定できません）、アドバイザリーサービス（質問への対応） |
| IR readiness workshop | DART の IR の進め方と使うツールを紹介し、相手の組織が持つツールも確認する、従来のテーブルトップより「ワークショップ」に近い形式 |
| Executive tabletop | 取締役会や経営層が部屋に集まり、シナリオを最初から最後まで数時間かけてたどる、従来型のテーブルトップ |
| AI readiness workshop | IR readiness workshop と同様の内容を、AI に絞ったもの |
| Cyber range | 環境に攻撃者がいると分かっている前提で、自チームが Microsoft のツールを使って攻撃者を見つけ、状況を把握し、封じ込めの判断プロセスをたどる |

Compromise Assessment との違いは、「攻撃者がいるか分からない」のが侵害評価、「いると分かっている」のがサイバーレンジだという説明です。なお、オリンピックやワールドカップのような大規模イベントの際にも支援できると述べています。

### 5.6 AI と防御（Vlad 氏）

Vlad 氏は、学生時代の電卓の話から入りました。当時、先生たちは「電卓に頼ると頭を使わなくなる」「いつも電卓を持ち歩けるわけではない」と言っていましたが、今は常に持ち歩いている、と冗談めかして話しています。ただし、先生たちが正しかったのは、**ツールがあっても問題を理解する必要はなくならない**という点だと述べています。AI も同様で、「AI を使おう」と言われる中で、どう効果的に使うか、チームが効果的に使えているかをどう知るかが問題です。

セキュリティ運用で AI を使う目的は、AI を盲目的に信頼することではなく、時間を取り戻して専門家に返すことです。そして「マシンスピード」とは、判断を捨てずに作業を加速することであり、作業が瞬時に終わる、あるいは完全自律の防御になるという約束ではないと説明しています。

#### 攻撃側の AI 利用：3 つの観点

攻撃者側も AI を使っています。発表では、Microsoft のインテリジェンスが追跡している攻撃者が、開発（コード作成）、侵害環境の分析、より説得力のある誘い文句の作成などに AI を使っていると述べています（音声では "Microsoft Intelligence" と聞こえます）。そのため、明らかに怪しいメールのような「分かりやすい危険信号」は減り、より高度なフィッシング手法に備える必要があるとしています。これを 3 つの観点で整理しています。

1. **AI-assisted threats（AI に支援された脅威）：** コードの作成、ユーザーに対してより説得力のある見せ方、すでに侵害済みの状況の加速
2. **AI-enabled attack paths（AI が可能にする攻撃経路）：** 環境内の脆弱性、弱点、ギャップ、侵入経路を AI が見つける速さ。攻撃者にとっての機会は、コンテンツ作成だけでなく、AI が見つけてくれる機会そのもの
3. **AI as an attack surface（AI が攻撃対象になる）：** AI システム自体を守る必要がある

3 つ目については、最前線で見た話として次のケースが紹介されました。

> 財務部門のユーザーが侵害された。財務部門は、財務データと給与データのすべてにアクセスできる AI システムを試験運用していた。攻撃者がその AI に簡単な質問をするだけで、大量の機密データが得られる。HR の ID が侵害された場合も、AI を介してどのデータにアクセスされるかを考える必要がある。

Vlad 氏は、ここから「AI は何を読めるのか、何ができるのか、誰の権限で動くのか」という問いが残ると述べます。AI システムやツールは設計どおりに動いていても、使うべきでない人が使っているという状況があり得るという指摘です。

#### 防御側の AI 活用例

AI をまだ使っていない人は小さく始めよう、という前提で、2 つの例が示されました。

**例 1：スクリプトの解析。** 先ほどの調査の 28 本の長いスクリプトです。熟練の研究者なら読み解けますが、証拠の突き合わせや関係の理解に時間がかかり、専門知識があっても作業は瞬時にはなりません。これに対し、AI アシスタントが「これがコードで、目的はこれ、見えている証拠はこれ、実行後のプロセスや証拠はこれ」と分解してくれれば、たとえば 4 分程度で済む可能性があります。熟練の研究者が 4 分で終えるのは難しいだろうとも述べています。

**例 2：脅威インテリジェンスの補強（enrichment）。** Vlad 氏は、SOC 時代に 7〜8 個の Web サイトやツールを開き、IP アドレスをコピー＆貼り付けして調べていた経験に触れ、これは AI で容易に自動化できると述べます。ただし、「この IP は悪いか」と聞くだけでは不十分です。経験の浅い担当者がツールで IP を見て「suspicious」と出たとき、悪意があるのかどうかは分かりません。

ここで強調されたのが「**どう聞くか**」です。白か黒かを聞くのではなく、自分の評価を組み立てる助けになる質問をします。

- この IP アドレスについて、各ソースは何と言っているか
- ソース同士はどこで矛盾しているか
- いつ観測されたか
- それは今の調査にどう関係するか

別の文脈では悪意があるとされた痕跡を鵜呑みにすると、誤りにつながるためです。ガードレールを設けて、前提や判断を手放さずに自信を持って使うことが大切だとしています。

#### 取り戻した時間をどう使うか

答えは「最も重要なことに使う」です。より重大な調査に防御担当者を向け、重大度の低いものは別の担当に任せ、専門性を重要な作業に集中させます。セキュリティチームを拡張しつつ、コントロールを保ちます。そのために次を設定するとしています。

- AI がアクセスできるデータ
- AI が使えるツール
- AI が代行できる行動
- 結果が重大な場面での**人間のチェックポイント**

完全自律を望むかと問い、ツールが思ったほど良くなければ危険だと述べています。例として、ドメインコントローラーに関するアラートで、AI が調査を行い、脅威インテリジェンスのソースに問題があってドメインコントローラーを隔離してしまう場合を挙げ、それが致命的になりうると指摘しています。

#### レッドチーム・ブルーチーム・グリーンチームのエージェント

専門家の知見を、3 つの役割の継続的なサイクルに組み込む方向性として、Vlad 氏は次を説明しました。Microsoft の「Perception」（音声での聞こえ方で、正確な名称は確定できません。このセッションでは詳細は語られていません）が、この方向で顧客を支援するよう設計されているとしています。

| チーム | 役割 |
| --- | --- |
| Red team | 攻撃のシミュレーション、脆弱性や弱点の発見 |
| Blue team | トリアージ、調査、検知 |
| Green team | 何を修正すべきかの優先順位付け |

ポイントは、エージェントが 3 つあることではなく、**アクションが互いにつながり、サイクルの一部になっていること**だと述べています。互いに連携しなければ、それぞれの時間とスキルの使い方としては最適ではないという主張です。

Vlad 氏は、Defender Experts MDR が、セキュリティチームを置き換えるのではなく強化・拡張するためのサービスだと説明しています。内容は次のとおりです。

- Microsoft の脅威インテリジェンスを活用し、プロアクティブにハンティングする。顧客にとって重要なことを理解したうえで探す

- セキュリティデリバリーの専門家と協働でき、experts on demand サービスを利用できる。次に何を行うべきかの推奨も受けられる

## 7. 注意点・発表者の気付き

- **「見慣れた痕跡がない」ことは「足場がない」ことではない。** ClickFix の調査では、足場はあったのに、従来の経路をたどらなかったため見えていませんでした。
- **脅威インテリジェンスの「知っている」と「備えている」は別。** レポートを受け取ったら、ハンティング、IOC の確認、仮説の検証、変種の検証まで行います。
- **完全にパッチが当たった組織は見たことがない。** パッチ未適用の脆弱性悪用は、ほぼすべての IR に出てきます。AI でフィンガープリントが容易になる点に注意が必要です。
- **正規ツールの悪用。** Velociraptor、CloudFlare、Zoho Assist、Visual Studio Code などが攻撃に使われるため、自組織で許可しているツールを把握していなければ、異常だと気づけません。
- **インシデント中に存在しないデータは作れない。** 何を守るか、どこにあるか、監視されているかを事前に確認します。
- **テーブルトップは SOC だけで行わない。** 法務、人事、広報、給与部門も巻き込みます。
- **AI への質問の仕方で結果が変わる。** 「悪いか」ではなく、根拠の食い違いを問う質問にします。
- **AI に何を読ませ、何をさせるかの境界を設け、重大な結果が起こり得る箇所には人間のチェックポイントを置く。** AI が設計どおりに動いても、使う人が誤っていれば問題になります。

## 8. 利用者にとっての利点

このセッションは、サービスの導入効果の数値や顧客事例の成果を紹介するものではありません。発表で語られた利点は、Defender Experts の各サービスが組織に提供するものとして、次のように整理できます。

- **Threat Intelligence：** 自分の業界・地域・環境にとっての脅威と、心配すべきことが分かる
- **Hunting：** その情報をもとに、組織内で進行中の攻撃を探す「見張り役」になる
- **MDR：** アラートやインシデントのトリアージから解決までを任せられる。24 時間 365 日の体制で、セキュリティチームを置き換えずに拡張する
- **Cybersecurity Incident Response / DART：** インシデント時の調査・封じ込めの支援に加え、侵害評価、IR 計画、各種テーブルトップ、サイバーレンジなどで事前に備えられる

## 9. まとめ

- 最前線の傾向は 3 つです。ID の悪用が続き、1 件のインシデントがより広いギャップを明らかにし、AI が攻撃の速度と規模を押し上げています。
- ClickFix の事例が示すとおり、既知の手口も変種になります。調査から得た発見は、検知の前提、代替の証拠、担当者という形で「次の行動」につなげる必要があります。
- 2 つの脅威アクターが絡んだランサムウェア事案では、パッチ未適用のシステムを突くことと、正規ツールを悪用して検知を避けることが共通する手口でした。自組織の資産とツールを知っていることが、検知と対応の土台になります。
- レジリエンスはインシデントの前に作ります。守るべきものを定義し、全部門を巻き込んだ現実的な演習で試し、意思決定の権限を決めておきます。
- AI は攻撃にも防御にも使われています。防御側は小さく始め、聞き方とガードレールを整え、結果が重い場面に人間のチェックポイントを置いて活用します。
- 最終的な目標は、インシデント対応チームの出番が来る前に、ハンティングや MDR で食い止めることです。
