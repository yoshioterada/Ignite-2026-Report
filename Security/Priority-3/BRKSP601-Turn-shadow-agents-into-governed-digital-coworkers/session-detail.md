# BRKSP601 Turn shadow agents into governed digital coworkers

## 1. はじめに

このセッションは、組織の中で増え続ける「シャドーエージェント」を、**Agent 365** を使って管理下に置く方法を、デモを交えて紹介するものです。かつてシャドー IT やシャドーアプリが問題になったのと同じことが、今は AI エージェントで起きている、というのが出発点です。

発表では、Python で作られ、Azure Container Apps 上で動いている「誰も管理していないエージェント」を題材にしています。このエージェントを Agent 365 のスキルで登録して ID（identity）を与え、可観測性（observability）や Purview の DLP ポリシーを追加します。そのうえで、オーナーとスポンサー、Conditional Access、アクセスパッケージ、ライフサイクルワークフローが効く様子を見せ、「ガバナンスされたエージェント」に変えていく流れが示されます。

このセッションでは、画面を使ったデモが行われています。ただし、Agent 365 スキルでエージェントを登録する部分は、発表中に「recording（録画）に切り替える」と語られており、録画を使って紹介されています。

読むと、次のことが分かります。

- シャドーエージェントがなぜ生まれ、どんな問題を起こすのか

- 月曜の朝から何を始めればよいか

## 5. 発表内容の詳細

### 5.1 シャドーエージェントとは何か

冒頭で、会場に挙手が求められました。質問は、組織内に「把握していないエージェント」があるか、「過剰なアクセス権を持つエージェント」があるか、エージェントを開いても誰が作ったのか・誰が責任者なのかが分からないことがあるか、IT 管理者として制御が限られていると感じるか、というものです。登壇者は、これらの課題には解決策があると予告して先に進みます。

### 5.2 エージェントが急増する理由

エージェントは「あらゆる人」によって作られている、と説明されています。作り手は 4 つのグループに分けられています。

| グループ | 作り方・入り方 |
| --- | --- |
| 開発者 | エージェントを自分でコーディングして作る。他のエージェントを使って作る。Foundry やその他の SDK を使う |
| 業務部門 | Copilot Studio のようなローコードツールで、IT が知らないうちに数分で作ることも多い |
| ソフトウェアベンダー | 私たちが購入した製品の中に、頼んでいなくても AI エージェントや AI ツールを組み込んでくる |
| 一般の従業員 | 本格的なエージェントを作るわけではないが、Web でツールを見つけて、IT の審査を経ずに使う |

エージェントを作る障壁は下がり続け、作るスピードは上がっています。一方で、ガバナンスの能力は追いついていません。発見（discovery）、インベントリ、ID、アクセス、データ保護、監視、ライフサイクル管理といったものは、エージェントを作ったからといって自動的に付いてくるわけではありません。**作るペースがガバナンスのペースを上回ったとき、シャドーエージェントが生まれる**と説明しています。

### 5.3 顧客から寄せられる 4 つの課題

登壇者は、これは偶然ではなく、何十万もの顧客と日々仕事をする中で繰り返し見られるパターンだと話します。

1. **可視性が不完全**：誰かがエージェントを作っているのは分かっても、すべては見えない。
2. **オーナーが不明確**：実際に誰が責任者なのか、作った人が退職したらどうなるのかが分からない。
3. **アクセス権と権限**：エージェントは強力だが、権限が過剰なことがある。権限が過剰なときにエージェントに何ができてしまうかは、最近のニュースを見れば分かる、と述べています。
4. **監視が限定的**：エージェントが見えていても、可観測性やテレメトリが無ければ、誰が使い、どのデータを使い、どのツールを呼び出したのかが分からない。

データとして、**82% の組織が、IT が把握していない AI エージェントが何らかの形であると回答している**という数字も示されました。

### 5.4 Agent 365 が提供する 3 つの機能

解決策は Agent 365 です。登壇者によると、Microsoft が昨年発表したもので、それ以前は、AI エージェントを一元的にガバナンスしたいという声が寄せられていました。それまでも管理の方法はあったものの、プラットフォームごとにバラバラで簡単ではなかった、という背景です。Agent 365 は次の 3 つの機能を提供します。

| 機能 | 内容 |
| --- | --- |
| 可観測性（Observability） | 環境内にエージェントがいくつあるか、どんな操作ができるか、どのツールを使えるか、誰が・何回・どのチャネルで使っているかを見られる |
| ガバナンス | 各エージェントに固有の ID が付く。人を主体名（principal name）で管理するのと同じように、Conditional Access ポリシーやライフサイクルワークフローを対象にできる。Microsoft Entra Agent ID で、ID とブループリントを扱う |
| セキュリティ | Microsoft Purview で、エージェントが使えるデータを保護する |

新しいツールを覚える必要があるのか、という問いに対しては、**これまで何年も使ってきたのと同じツールで管理できる**のがこの製品の良い点だと答えています。使うツールと役割は次のとおりです。

- **Microsoft 365 admin center**：アプリ、ライセンス、ユーザーを管理してきた場所で、エージェントも管理する。IT 管理者は、エージェントの数、作成者、公開日、環境などを確認できる。
- **Microsoft Entra**：すべてのエージェント、ブループリント、ID の一覧を見られる。
- **Microsoft Purview**：エージェントの一覧、適用されている DLP ポリシー、アラートを確認できる。人間向けに作れるものは、エージェント向けにも同じように作れる。
- **Microsoft Defender**：エージェント向けのランタイム保護ルール、脅威検出ルール、継続的な監視を設定でき、エージェントが呼び出されるたびの完全なテレメトリが得られる。

進行役が、エージェントに ID を与えたから Purview や admin center の管理も自動的に付いてくるのか、と確認したのに対し、登壇者は「そのとおり」と答えています。**ID が無ければ、これらのポリシーを適用するのは非常に難しい**という説明です。

### 5.5 エージェントを Agent 365 に取り込む 3 つの方法

1. **自動同期**：Copilot Studio、Foundry、Agent Builder、SharePoint でエージェントを作ると、自動的に同期されます。公開していなくても、作った時点で同期されます。
2. **接続済みプラットフォーム（connected platforms）**：現実の組織は Microsoft の AI スタックだけでなく、AWS、Snowflake、Databricks なども使っています。そこで、これらのプラットフォームを Agent 365 に接続すると、そこで作られたエージェントの一覧とテレメトリが得られます。
3. **開発者による取り込み**：開発者は VS Code と GitHub Copilot を使い、OpenAI SDK のような任意のフレームワークでエージェントを作れます。この場合は、**Agent 365 SDK** を使って、エージェントを管理下に置きます。登壇者は、これが最も難しい経路であり、今日見せるものだと説明しています。

登壇者は、Microsoft のプラットフォーム内でエージェントを作るなら、この点を心配する必要が無く、そのほうが簡単だと補足しています。

### 5.6 admin center でのエージェント一覧（デモ）

登壇者は、Microsoft 365 admin center の「エージェント」セクションを開いて、可観測性の概要を見せています。画面にはプラットフォームとして Copilot Studio、Agent Builder、Foundry、SharePoint が並び、登壇者があらかじめ接続した Amazon Bedrock と Snowflake AI も表示されています。

**Copilot Studio のエージェント**

Copilot Studio を開くと、環境を問わず、Copilot Studio で作られたすべてのエージェントが一覧に出ます。そのうち 1 つを選ぶと、次の情報が見えると説明されています。

- エージェントの指示（instructions）、作成日、更新日、公開者、作成者
- **Entra agent ID**（登壇者は、Agent 365 が提供する最も重要な機能だと述べています）
- 完全な ID であるブループリント、環境（この例ではサンドボックス）、環境 ID
- プロパティ：編集権限を持つユーザーが 1 人いること、使っているモデル、エージェントカード、エージェントの場所と URL

「データとツール」の画面では、このエージェントが使っているナレッジソースの数、OneDrive・SharePoint・公開サイトへの読み取りアクセス、Copilot コネクタである Jira コネクタが 1 つあること、ツールとして Work IQ の MCP サーバーと、Snowflake 用に作ったカスタム MCP（Snowflake Sales MCP）が使われていることが示されました。「セキュリティ」はデフォルトの設定で、問題があればここにアラートが出ます。「アクティビティ」では、利用回数とユニークユーザーを確認できます。

この画面から、**新しいオーナーの割り当て、エージェントの削除、エージェントのブロック**もできます。進行役が「Copilot Studio に入らなくても、指示やツールが見られるのか」と尋ねたのに対し、登壇者は、IT 管理者やセキュリティ・コンプライアンスの担当者は開発者ではなく、エージェントを 1 つずつ開いて確かめるのは現実的でない（中身も複雑）ため、この一覧がツールと個々のユーザーをすばやく把握するためのビューになると答えています。

**Foundry のエージェント**

「all agents」から Microsoft Foundry で絞り込むと、Foundry のエージェントが表示されます。Copilot Studio と同じ情報が見えますが、プロパティでは、これが **prompt agent** であることが分かります。Foundry のエージェントには、設定で作る prompt agent と、hosted agent の 2 種類があり、その区別もここに出ると説明されています。

**接続済みプラットフォーム**

「Manage connected platform」から、外部プラットフォームを接続できます。登壇者の環境には AWS Bedrock と Snowflake の 2 つがすでに接続されています。「add connection」で必要な情報を入力して追加します。現在対応しているプラットフォームは画面に出ており、Microsoft は今後も追加していくとのことです（Databricks、Google などを挙げています）。追加すると自動同期が働き、この例では AWS 側に 4 つのエージェントがあります。誰かが明日新しいエージェントを作れば、同期されて 5 つになるという説明です。1 つずつ手で登録する必要はありません。

### 5.7 カスタムの Python エージェントを取り込む 4 ステップ

デモで題材にするのは、**Azure OpenAI のモデルを使う Python ベースのエージェント**です。架空の（synthetic な）給与データにつながり、Azure Container Apps 上で動いています。このエージェントには ID もオーナーもありません。ログから多少のテレメトリは得られますが、完全ではなく、どんなアクセス権を持っているかも分かりません。期待どおりに動作はするものの、管理されていない、という状態です。

これを Agent 365 に取り込む手順は、次の 4 ステップです。

1. **登録（Register）**：VS Code の GitHub Copilot で Agent 365 のスキルを使い、そのエージェント専用の ID とブループリントを作ります。依存関係をインストールしたあと、簡単なプロンプトを与えるだけです。
2. **可観測性の追加**：登録だけではあまり情報が得られないため、可観測性を追加します。任意で Work IQ ツールも追加できます。
3. **検証（Validate）**：エージェントが ID とブループリントを得られたことを確認します。これで Conditional Access ポリシーを対象にできます。
4. **継続的な監視**：エージェントが期待どおりに動作しているかを監視します。

### 5.8 エージェントの ID とブループリント

ID の概念は、冒頭のバッジのたとえに戻って説明されます。会社にエージェントが入ってくるときは、バッジに相当する ID を Agent 365 で与える。つまり「**1 エージェント、1 ID**」です。技術的には、ID は次の要素を持ちます。

| 要素 | 内容 |
| --- | --- |
| オーナー（owner） | エージェントを保守する技術担当者。指示の変更や、スキル・ツールの追加と削除を担う |
| スポンサー（sponsor） | 技術担当ではなく、エージェントのライフサイクルに責任を持つ業務側のリーダー。本番移行、社内ストアへの公開、廃止といった判断が、ライフサイクルワークフローで、この人のところに届く |
| 権限（permissions） | API 権限と Entra のセキュリティルールを ID に割り当てられ、それがエージェントに反映される |
| ステータス | 有効か無効か |

次に**ブループリント**です。バッジの例では、警備員が 100 枚ほどのバッジを手作業で作るのは大変なので、プリンターとテンプレートを渡したくなります。エージェントも同じで、多数のエージェントを作るなら、共通のブループリントから始めるべきだという考えです。エージェントは何個あっても、1 つのブループリントにひも付きます。理由は 3 つ挙げられています。

- Entra へのアクセス、資格情報（パスワードやフェデレーション資格情報など）、認証設定を、エージェント群で一元管理できる。
- **verified publisher**（発行元の検証）により、そのエージェントがどこから来たのかが常に分かる。
- 権限をブループリント単位で付与できる。付与すれば、ひも付くすべてのエージェントにすぐ追加され、取り上げればすぐに外れる。ガバナンスを効率的にスケールさせられる。

### 5.9 デモ：ガバナンス前の Python エージェント

Azure ポータルで、このエージェントは Azure Container Apps のコンテナーとして、ステータスが Running になっています。アプリケーションの URL を開くと、シンプルな Web チャット画面が出ます。そこで「who is my chance manager?」（音声認識の都合で表記が確定できません）と質問します。コンテナーが起動するまで少し待ったあと、マネージャー名が Marcus であるという回答が返り、続けて給与についても質問し、回答が返りました。エージェントは期待どおりに動いています。

次に Azure のログを見ると、基本的な情報は出ますが、これは開発者向けの情報で、IT 向けではありません。IT には、このエージェントだけでなく、すべてのエージェントを横断して見られる一元的なビューが必要だ、と登壇者は述べています。

### 5.10 デモ：Agent 365 スキルでの登録（録画）

ここからは、録画に切り替えて紹介されています。VS Code で GitHub Copilot を使い、Agent 365 のスキルを呼び出します。

1. 最初のスキルは、Agent 365 用にプロジェクトをセットアップするものです。実行すると、どんな種類のエージェントかを判別しようとします。
2. 判別が終わると、どの種類にするかを尋ねられます。ここでは汎用のエージェントではなく **AI teammate** を選びます。登壇者の説明では、AI teammate は「デジタル同僚」にあたり、独自の Teams プレゼンス、カレンダー、ユーザーアカウントを持ち、Teams に公開して Teams 内で使えます。
3. セットアップ全体の所要時間は、dry run を使う場合で 4〜5 分、dry run を使わない場合は 20 分と説明されています。進行役が「手作業ではどれくらいかかったか」と尋ねると、**数日かかった**と答えています。6 月に CLI を使って手作業で行ったとのことです。
4. ブループリントと ID が作成されます。次に、可観測性の作成を依頼します。
5. 可観測性の追加後、**Work IQ と mail MCP を組み込む**よう指示します。Work IQ のツールには、メールを送れる条件といった権限も与えています。手作業なら多くの時間と手間がかかるが、依存関係をインストールしておけば自動で行われる、と述べています。
6. さらに、**Purview の DLP をこのエージェントに追加する**よう指示します。例として、ユーザーが銀行口座情報をメールで送ろうとしたら、DLP ポリシーがブロックし、IT チームにアラートを送る、という内容です。
7. 対話の中でポリシーを絞り込むこともできます。ここでは「メールのリクエストにクレジットカード番号が含まれるときだけブロックする」と伝えています。ポリシーが作られ、Purview の DLP が組み込まれて有効になります。
8. Purview でポリシーを見ると、給与用に作ったポリシーが 1 つあります。その適用範囲（scope）は、**このエージェントの ID だけ**です。すべてのエージェントをブロックするのではなく、特定のエージェント ID を対象にしています。ID があるから、人間のユーザーと同じように扱えると説明されています。
9. 完成したら公開（publish）し、マニフェストファイルが作られます。これを M365 の Agent 365 にアップロードします。

登壇者は、コードを大きく書き換えるのではなく、機能を組み込むための数行のコードが加わるだけだと説明しています。また、進行役が、自動運転のように任せきりではなく、途中でいくつも判断を下しているのだと指摘したのに対し、登壇者は、いつでも対話で指示を出し直せると答えています。

### 5.13 デモ：Conditional Access

エージェントに ID があるので、Conditional Access も適用できます。Microsoft Entra Agent ID の Conditional Access に、ポリシーがいくつかあり、その 1 つが「payroll … block mail」という名前のもの（音声認識の都合で表記が確定できません）です。編集画面で、次のように設定されていると説明されています。

- **リソース**：このエージェントが Work IQ の mail MCP を使おうとしたらブロックする。

### 5.14 デモ：アクセスパッケージ

アクセスパッケージも使えます。登壇者は、権限とアクセスを管理するうえでのベストプラクティスの 1 つだと述べています。

1. エージェントのマネージャーがアクセスパッケージの画面で、必要なアクセスの「request」をクリックする。
2. 「others」を選び、アクセスを与えたいエージェントを選択する。ここでは給与のエージェントを選んで進む。
3. 業務上の理由（business justification）を入力し、申請（submit）する。
4. 「approvals」で、申請済みのものを確認できる。承認済みの申請を開き、誰（どのエージェント）が、どのアクセスを、どんな理由で要求したかなどの詳細を見られる。
5. アクセスを外したいときは、「remove access」をクリックする。

### 5.15 デモ：Purview の DLP がブロックする様子

次に、DLP ポリシーが実際に働く場面です。Teams のエージェントに、ある人物の銀行口座の詳細を、指定のユーザーにメールで送るよう依頼するメッセージを貼り付けて実行します（人名は音声認識の都合で確定できません）。

エージェントがメールを送ろうとする間に、「**block financial data in payroll**」というルールが検出されます。ルールは、エージェントがその情報をどのユーザーにも送ることをブロックします。Purview を開くと、**重大度 high のアラート**が出ています。登壇者は画面を更新し、アラート一覧でそのアラートを開いて、アラート ID、検出時刻、ステータス、ポリシーの一致、イベントを実行したユーザーなどを確認しています。エージェントが機密情報を含むメールを別のユーザーに送ろうとしたとき、自動的にブロックされた、という結果です。

> 補足：登録のデモでは「クレジットカード番号が含まれるときだけブロックする」と指示しており、この実演で送らせたのは銀行口座情報でした。発話では、ルール名が「block financial data in payroll」である点以上の説明はありません。

### 5.16 ライフサイクルワークフロー

エージェントを作った人が退職したらどうなるのか、という問題には、**ライフサイクルワークフロー**が対応します。「create workflow」を開くと「agents」というセクションがあり、ルールの 1 つに、**「agent sponsor job profile change」（スポンサーの職務プロファイルの変更）と「off board agent sponsor」（スポンサーのオフボード）** があります。

エージェントを作った人が明日退職しても、その上司が自動的に新しい担当者になります。登壇者は、これでオーナー不在のエージェントが無くなると述べています。進行役は、誰かが常に状況を把握していなくても、裏側で自動的に回る点を評価しています。

### 5.17 まとめ：1 つのエージェント、3 つのチーム

1 つのエージェントと 1 回の会話から、**3 つのチームがそれぞれの観点で影響を確認できる**と整理されています。

| チーム | 使うツール | 見えるもの |
| --- | --- | --- |
| セキュリティチーム | Microsoft Defender | エージェントの活動、ツールの呼び出し、推論呼び出し。問題があればアラートが届く |

## 7. 注意点・発表者の気付き

- **ID が前提**：ID が無ければ、Conditional Access や Purview のポリシーを適用するのは非常に難しい、と繰り返されています。
- **資格情報はブループリントで管理する**：ID 自体には資格情報が無く、1,000 個のエージェントのために 1,000 個の資格情報を作らないための設計だと説明されています。
- **ポリシーはエージェントを絞って適用する**：Purview の DLP は、すべてのエージェントではなく、特定のエージェント ID を対象にしていました。
- **最初にやるべきは可視化**：管理されていないエージェントをインベントリに入れる作業を先にしないと、後続の手順が進められません。
- **手作業は時間がかかる**：Agent 365 スキルを使う前は、同じことを CLI で手作業で行い、数日かかったという実体験が語られました。
- **ポリシーの粒度は対話で決める**：自動で進むものの、DLP のブロック条件を絞るなど、途中で判断を挟めると述べられています。
