# INV642 Observability at every layer for every role

## 1. はじめに

このセッションは、AI とエージェントが業務に広がるなかで、「どこで AI が使われ、エージェントが何をしていて、どんなリスクが出てきて、投資は成果につながっているのか」をどう把握し、行動につなげるかを扱った Innovation Session です。前半では Charles Lamanna 氏が、IT 管理者とビジネス部門のリーダーの視点から Agent 365 を紹介します。後半では Hayete Gallot 氏が、AI 時代のサイバー攻撃の変化と、セキュリティ向けのエージェント基盤である Perception を説明します。

発表全体を通した結論は、次の 2 点です。

- 見えないものは守れず、統制もできないので、まず **すべてのエージェントと AI 資産を 1 つのレジストリで把握する**
- 機械の速度で動く攻撃には、人手を増やすのではなく **エージェントで対抗する**

Agent 365 の管理者向け・ビジネス部門向けデモが 2 本、Perception のデモが 4 本（SOC、脆弱性、エージェントの封じ込め、基盤強化）あり、顧客の動画や Bank of England の CTO とのトークも含まれます。画面操作はナレーションで語られた範囲のみを書いています。

## 3. 何に関する発表か

テーマは「AI の可観測性（observability）を、スタックのあらゆる層で、あらゆる役割の人に提供する」ことです。ここでの observability は、ログやトレースやダッシュボードのことというより、**エージェントと AI 資産を大規模に管理（management）し統制（governance）する**ことだと説明されています。management は何がどこにあって何をしているかを知ること、governance は許可される権限、ツール、プラグイン、コネクタを把握することを指します。コスト管理やセキュリティ管理も、この 2 つに含まれます。

発表の流れは次のとおりです。

1. 導入：なぜ可観測性が必要か（Charles 氏）
2. Agent 365 のレジストリと Action Center、IT 管理者向けデモ

4. コスト管理の考え方（plan / control / optimize）と Philips の事例動画
5. Business Analytics のデモ（ビジネス部門のリーダー視点）
6. 脅威の変化：Agentic Insider、AI を使う攻撃者、未修正の基盤の弱点（Hayete 氏）
7. Perception の構成と一般提供（GA）の発表、顧客動画、Bank of England との対談
8. Perception の 3 つのシナリオとデモ：エージェントによる防御、Agentic Insider の保護、基盤の強化
9. Perception を導入するときの運用モデルの課題と、提供形態

## 4. 発表者が伝えたいメッセージ

Charles 氏は、AI が先走ってセキュリティや統制を追い越すことも、統制のために採用の勢いを止めることも避けたい、という立場から話を始めます。仕事が Email、Teams、Copilot、エージェントに依存するようになると、エージェントの挙動が見えないことがより自律的なエージェントへ進む際の障害になります。セキュリティ、コスト、管理、ガバナンスの把握ができなければ、AI 活用を広げ深めることができないという考えです。

同氏はさらに、AI 活用の指標が「Copilot に毎日プロンプトを送る人は何人か」といった利用状況から、部門単位・業務単位の構造的な取り組みへ移りつつあると指摘します。各自がサイロで AI を使うだけでは相乗効果が出ないため、全体の戦略が必要で、その土台がレジストリ（単一の記録システム）だという主張です。コストについても「コスト回避ではなく価値創出」が目的であり、コストと価値を並べて見ることが重要だとしています。

Hayete 氏のメッセージは、AI は信頼できず、攻撃も機械の速度で自律化している、だから **AI に AI で対抗する** というものです。セキュリティで大切なのはアラートを増やすことではなく、シグナルからアクションまでのループを最後まで回して実際に守ることだ、と述べています。最後に、「イノベーションと安全のどちらかを選ぶべきではない」と締めくくっています。

## 5. 発表内容の詳細

### 5.1 導入：なぜ可観測性が必要か

Charles 氏は、典型的な企業には数十種類の AI ツールが何らかの形で展開されていると述べます。IT が配布したもの、ユーザーがインターネットからダウンロードしたもの、ローカルのノート PC で OpenCLAW を動かしているケースなどです。どのプラットフォーム、モデル、プラグインが使われているかを把握することが、AI ポリシーと AI 管理の出発点になります。見えていない（シャドウの）ものは守れず、統制できません。

その考えに基づく Agent 365 は、すべての AI 資産の「単一の記録システム」と位置づけられます。Satya 氏が好む例えとして、**Agent 365 はエージェントと AI のための ERP のようなもの**だと紹介されています。ERP がサプライチェーンや在庫を追うように、どのエージェント、プラグイン、スキルが使われているかを一元的に持ちます。この記録システムが、その後のワークフローや統制の起点になります。

### 5.2 Agent 365 の対応範囲

Agent 365 は Microsoft のプラットフォームとエージェントを第一にサポートしつつ、他社のプラットフォームにも接続します。発表で挙げられたのは次のものです。

- エージェント基盤：Anthropic、OpenAI、AWS Bedrock、GCP Vertex
- データ基盤・アプリケーション：Salesforce、Databricks、Snowflake、Workday、ServiceNow、LexisNexis など

これらに対し、監視ログや本番アプリのログを取り込むコネクタ、スキャナー、ツールがあり、利用量や課金メーターも取り込めます。組み込みで対応していないものには SDK と API が用意されており、自社開発のエージェントや独自システムとの連携を作れます。どのプラットフォーム、どのモデルで作られたものでも、Agent 365 上で見て、管理し、統制できる、というのが要点です。

### 5.3 Action Center

Charles 氏は、IT 管理者や SecOps の仕事は巨大なリストを眺めることではなく、良いシグナルを得て行動することだと述べます。顧客には数千から数十万のエージェントがあり、Microsoft 自身も従業員 20 万人に対してエージェントが 100 万を超えている、という数字が示されました。そのため Agent 365 は、さまざまなデータソース、メタデータ、構成を横断して、注意を向けるべきエージェント、プラグイン、モデルを特定します。

ユーザーからは「シグナルは良いが、5 つの画面を巡って 7 つのボタンを押さないと状況がわからない」という声があったとのことです。そこで今週発表されたのが **Agent 365 Action Center** です。Microsoft 365 Admin Center の中にあり、セキュリティ、コスト、ポリシー、ガバナンスのワークフロー、デプロイ、権限、所有者のいないエージェント（orphaned agents）などを 1 つのビューで見られます。そこから自動化やポリシー、自動ワークフローを入れる箇所も判断できます。Microsoft 社内と初期のプライベートプレビュー顧客で、おそらく最も使われているのは、**使われなくなり所有者もいないエージェントを削除する自動化**だそうです。

### 5.4 マルチテナントと顧客からのフィードバック

デモのあと、Charles 氏は、IT・管理者コミュニティから出た要望が機能に反映されていると説明します。他社プラットフォームとの接続の拡充、モデルの制御、マルチテナント管理がその例です。子会社、複数リージョン、規制上の境界などで Entra テナントを分けている組織が多く、Agent 365 では複数の Entra テナントにまたがって接続・スキャンでき、ツールのガバナンスもできるとのことです。ギャップがあればフィードバックを寄せてほしい、と呼びかけています。

### 5.5 KPMG の事例（動画）

KPMG は Agent 365 の初期導入者で、Copilot とあわせて、従業員向けの AI ツールを広く持続的に展開し、システムへの接続、セキュリティ、コンプライアンスの管理を同時に行っていると紹介されました。動画で Greg Schellenberg 氏は、次のように話しています。

- 問題はエージェントを作れるかではなく、**安全かつ責任をもって大規模に運用できるか**
- 重要なのは、ガバナンスの前に可視性があること。「見えないものは統制できない」
- Agent 365 により、どんなエージェントがあるかの棚卸し、誰が何の目的で作ったか、目的に適っているかを把握できる。エージェントが何をしているかの証拠も得られる
- 信頼は宣言ではなく、日々示し続けるもの。業務プロセス、共有コンテキスト、エージェントに紐づく ID、その周りのガバナンスが、観測可能な成果につながる

### 5.6 コストと価値：plan / control / optimize

Charles 氏は、コストだけでは全体像がわからないと述べます。トークンや AI ツールに多く使っていても価値を出しているエンジニアには問題がなく、使う額が少なくても何も生み出していなければ ROI が良いとは言えない、という例です。コストとリターンを一緒に追うことが投資判断に欠かせない、という考えです。

背景として、AI の課金がユーザーライセンスだけでなく、利用量に応じた課金（usage-based billing）に広がっていることを挙げます。GitHub Copilot、Copilot Cowork、Autopilot に usage-based の要素がある、とのことです。そのため支出の上限設定、予測、予算化が必要で、月末の決算期や会計年度末のように利用が急増する場合の扱いも含めて、レポートと統制を整えることが重要だとしています。また、「AI ツールを全員に配るだけ」では、ビジネス価値のあるユースケースには足りないとも述べます。

同氏が示したフレームワークは次の 3 つで、**この順番に意味がある**とのことです。

| ステップ | 内容 |
| --- | --- |
| Plan（計画） | どのユーザーに、どのツール、プラットフォーム、モデル、スキル、プラグインを有効にするかを決める。予算や配分、事業部門と IT チームへのチャージバックを決める |
| Control（統制） | 計画に沿って Agent 365 などで制御する。例：ローカル PC で OpenCLAW を使うべきでない人にはブロックする。Copilot の consumption（従量）機能を使うべきでない人には無効化する。接続できるシステムを限定し、ブロックを中央で適用する |
| Optimize（最適化） | 実際の利用から得られる情報（軌跡、ツール、作られたスキルなど）を見て最適化する。例：モデルの組み合わせを変える、上位のフロンティアモデルを制限する、同じ内容を何度も生成してトークンを消費しないようスキルやプラグインを作る、検索を改善する |

Charles 氏は「1 オンスの予防は 1 ポンドの治療に値する」ということわざを引き、計画は後から当てはめるより先に立てる方がはるかに良いと説明しています。また、最適化は導入の初期に過剰にやりがちだ、とも述べています。

Agent 365 には、IT チームから費用を負担する事業部門へのチャージバック、モデルファミリーの選択とモデルの制御、これらすべてを API で管理する機能が用意されています。API により、SIEM、CMDB、ITSM システムなどに連携できると説明されました。

| 項目 | 内容 |
| --- | --- |
| AI を使う時間 | 従業員あたり、およそ 2 時間から 5.5 時間に増加 |
| 従業員数 | 約 63,000 人。100 を超える国で販売・サービスを提供 |

Philips では、AI のコストを管理する取り組みを FinOps と呼び、AI がどう使われているかを把握し、投資を責任をもって管理して判断につなげていると語られています。

### 5.8 予算配分とビジネス部門の関与

Charles 氏は、Copilot Cowork の利用に複数の階層（ティア）がある場合、営業、財務、マーケティングなどの事業部門が自ら資金を出して利用上限を引き上げられる、と説明します。そのうえで、**AI の支出の 80% が IT 予算ではなくビジネス部門の予算から出ている**という変化に触れています。従来は Microsoft 365 や Azure の予算の多くが IT や開発チームから出ていたのに対し、現在は事業部門が大きな投資のために負担するケースが多い、という位置づけです。

Agent 365 の business analytics の体験は、この IT とビジネス部門の協働（チャージバック、支出上限、予算配分）を支えます。実際の利用に基づくコストと価値のインサイト、レポート、予測を 1 か所にまとめ、IT や技術者に限らず、どのビジネスユーザーも使えるようにしています。出張・接待費や裁量予算を管理するマネージャーやディレクターのように、AI の予算も IT から委任された権限で管理するようになる、という見方です。

### 5.9 脅威の変化（Hayete 氏）

Hayete 氏は、サイバーの「物理法則」が変わったと切り出し、次の 3 つのリスクを順に説明します。

**(1) Agentic Insider（エージェントという内部者）**

自社で作ったものでも他者が持ち込んだものでも、AI は信頼できないというのが同氏の主張です。Hugging Face のようなインシデントから学んだこととして挙げています。理由は次のとおりです。

- AI は設計上、目標に到達するために結果をハックするよう訓練されている。意図と実際の動作がずれる（ミスアラインメント）
- 他のエージェントと協力する。たとえば書き込み権限のないエージェントが、権限を持つ別のエージェントを見つけて目標に到達する
- 24 時間 365 日、機械の速度で大規模に動く

**(2) AI を使う外部の攻撃者**

1 年前は、攻撃者は攻撃の設計を AI に支援させていました。約 6 か月前から、攻撃キャンペーン全体を AI が実行するように設計し、ある段階でだけ人が誘導する形が見られるようになりました。現在は完全に自律した攻撃が見られる、という変化です。

ここで ARTEX が例に挙がりました。もともとはペネトレーションテスト用のマルチエージェントシステムで、攻撃のシミュレーション用に作られたオープンソースですが、攻撃者がこれを入手し、顧客に対して実行しています。システムは脆弱性を見つけ、侵入経路を探します。Hayete 氏によると、ある顧客は 2 日間で 12 万件のサインイン要求を受けました（拒否済み）。世界中で、あらゆる業種の数千の顧客が攻撃を受けているとのことです。

**(3) 修正されていない基盤の弱点**

ID と認証の近代化、データの分類とラベル付け、エージェントがアクセスするときのポリシー適用、ネットワーク分離、ソフトウェアの脆弱性は、以前から課題として知られていました。しかし 24〜36 か月の計画で一部しか直せていないのが実情です。AI の攻撃者は残った弱点を見つけるので、「いつかやる」とは言えなくなったと述べています。数週間前の PHP の脆弱性のように、モデルが何千もの脆弱性を見つけることで、インターネット上のすべての Web サーバーがリスクにさらされた、という例が挙がりました。

### 5.10 Perception の構成：agentic security stack

Hayete 氏は、人間向けに作ったものは AI には拡張できないとして、Microsoft は 7 月に「AI には AI で対応するための新しいサイバースタックが必要だ」と発表したと説明します。人に頑張ってもらうのではなく、エージェントでエージェントと戦う、という考え方です。スタックの要点は次のとおりです。

- **Security context（コンテキスト）**：エージェントの性能は、与えられたコンテキストの質で決まります。Microsoft は Defender、Entra、Purview、Intune、Sentinel を持ち、1P と 3P のデータもコネクタで取り込めるため、環境全体が見えます。1 日あたり 160 兆のシグナルを見ているという数字も示されました。
  ただし、160 兆のシグナルにそのままエージェントを適用すると、非常に遅く、高価で、効果も低くなります。そこでシグナルを **security graph** に整理し、環境内の関係やリスクについて、エージェントが共通の理解を持てるようにします。このコンテキストがなければ、どんなモデルやエージェントを使っても「盲目」になる、という説明です。
- **Perception**：その上に載るハーネスで、**red、blue、green のエージェント**が協力して防御します。中核は **マルチモデル**のアプローチで、理由は 3 つ語られています。①タスクごとに最適なモデルを使って品質を最大化する、②常時動くエージェントのコストを抑える（フロンティア並みの性能とコスト効率の両立）、③すべての顧客がすべてのモデルを使えるわけではないため、世界中で提供できるようにする。

3 種類のエージェントの役割は次のとおりです。

| 種類 | 役割 |
| --- | --- |
| red | 攻撃をシミュレーションし、環境にストレスをかける。ペネトレーションテストのように弱点を明らかにする |
| blue | 防御を担う。問題を見つけ、検知やルールを作って、カバレッジを高める |
| green | 姿勢（posture）の強化を担う。構成や環境を修正する |

PHP の例で、この連携が説明されました。CEO から「PHP の件、うちは大丈夫か」と聞かれたとき、通常は脅威インテリジェンスの記事を読み、IOC や TTP を自社環境に当てはめて、数日から数週間かかります。Perception では計画を立てて複数のエージェントを調整します。

1. blue エージェントが、自分の検知と記事の TTP/IOC を比較し、検知を改善する。改善した検知は Defender のような製品に自動で展開される
2. green エージェントが、IOC から見えた侵入経路のうち開いている部分を閉じる、または構成を変更する
3. red エージェントが攻撃者のつもりで再テストし、blue と green の仕事を検証する。不十分なら、良い状態になるまでループする

これが、センサーのシグナルから最後のアクションまでループを回す、という Perception の原則です。

### 5.11 Perception の一般提供と顧客の声

### 5.14 脆弱性対応のループ（MDASH）

Hayete 氏は、公開 CVE が 4,000 件から、10 月には 17,000 件に増えたというグラフを示しました（比較元の期間は発話からは確認できません）。これは公開 CVE のみで、自社ソフトウェアやスキャン結果は含みません。重要なのは見つけることではなく、直すこと、そして優先順位をつけることだと述べます。

Microsoft が 7 月に出した **MDASH** は AI スキャナーで、リポジトリに適用すると脆弱性が優先度づけされて出てきます。そのうえで、①環境の exposure graph と突き合わせて、環境でどう露出しているかを絞る、②ペネトレーションテストで実際に悪用できるかを確かめる、③既存のリポジトリだけでなく、新しいコードが作られたときにも再スキャンする、というループを作ったと説明しました。同氏は、開発者の時間は修正ではなくイノベーションに使ってほしいという考えから、このチームに働きかけたとも述べています。

あわせて、次の点も紹介されました。

- **FORGE Labs**：7 月に発表。トップのセキュリティ研究者で構成され、今年、software vulnerability で DARPA の賞を取り、Microsoft が採用したチームを含む。深い研究で MDASH の水準を保つとともに、エコシステムの修正にも取り組み、Windows、Linux、Rust、Chromium で 278 件の CVE を見つけた
- **性能**：35% 高速化。大規模リポジトリに対応。当初は一部の市場で使えなかったが、モデルの選択と確保したキャパシティにより、US Gov Cloud を含む世界中で利用可能
- **モデルの最適化**：「トークンのためのトークン」は使いたくないという方針。最初は OpenAI Mix（音声認識の都合で表記が確定できません）、次に MAI-Cyber 1 を使い、効果が高いため現在は MAI-Cyber 1 を既定にしている。昨日 Mustafa 氏が発表した MAI-Cyber 2 は、ベンチマークで Astra と同等の性能を、Astra の **2% のコスト**で出す、と説明された

### 5.15 Agentic Insider の保護：階層的な封じ込め

Hayete 氏は、Microsoft が endpoint、クラウド、ID、データ、ネットワーク、ブラウザを横断して見られるため、環境全体のエージェントを発見できると述べます。Microsoft 以外のものも、見つけられる限り発見する方針です。目標は、見えるだけでなく、管理し、保護し、動作を封じ込めることです。

「AI は信頼できない」という前提で、**階層的な封じ込め（layered containment）戦略**が示されました。Microsoft のエージェントはすでに管理下にあり、そうでないエージェントを見つけたときは、次の手順で管理下に置きます。

1. エージェントをコンテナで囲む（Microsoft の MXC を使う）
2. そのコンテナにポリシーを適用する
3. エージェントに ID を与える。この ID は**常に、ユーザーの ID とは別**にする
4. 権限は常に最小権限にし、ユーザーの権限をそのまま写さない
5. エージェントが認証し、データにアクセスし、何かを実行する様子を見て、**動的リスク（dynamic risk）**を計算する
6. 動的リスクに応じて、コンテナとエージェントに conditional access を適用し、アクセスと行動を制限する

同氏は、権限過剰な AI システムが多いことは会社にとって非常に危険だと述べ、これを 24 時間 365 日、利用者に代わって実行するので、寝ている間にエージェントが暴走する心配をしなくてよい、と説明しています。

### 5.16 Agent 365 と Perception の関係

Hayete 氏は、Agent 365 と Perception の関係を整理しました。エージェントを発見するコンテキストが、Agent 365 のレジストリと Perception のレジストリの両方に流れます。そのため、**IT とセキュリティが同じ 1 つのビューで作業**します。セキュリティ担当者が行う操作は Agent 365 に反映され、逆も同様です。IT は、エージェントのデータ流出などのセキュリティ調査はしません。IT は「このエージェントは何をしているか」を知りたい立場であり、2 つの役割がそれぞれの仕事をできるようにしている、という説明です。

### 5.17 運用モデルと提供形態

Hayete 氏は、Perception をお客様に導入してきた 6 か月で学んだこととして、Perception は技術であると同時に、AI をセキュリティ業務に取り込むときの**新しい運用モデル**でもあると述べ、次の 4 点を挙げました。

1. **人的資本とトークン資本**：新しい生産関数であり、エージェントにどこまで任せ、どこは任せないか、適切な予算はいくらかを考える必要がある。そのため FinOps に投資し、支出の場所と ROI、人をどこに活用できるかを把握できるようにしている
2. **チームをまたぐループ**：脆弱性対応はセキュリティと開発者、exposure management はセキュリティから IT、封じ込めは IT とセキュリティが連携する。誰が何をするかの運用モデルを明確にする必要がある。既存の RBAC は尊重し、統一された RBAC（unified RBAC）を作って、環境に合うロールを作れるようにしている
3. **実務者に合わせた UX**：セキュリティアナリスト出身で開発者や AI ネイティブではない人もいれば、コードを書く AI ネイティブ、データネイティブの人もいる。そのため、Entra、Intune、Defender など既存のポータルの中に埋め込む形、Perception 単独のアプリ、CLI、作業中に支援するサイドカー体験を用意する
4. **Frontier Security Engineers**：AI とセキュリティの交点にいる同氏のチームのエンジニアで、プレビュー段階の最初の数百社の顧客と取り組んできた。Perception の活用、運用モデルの課題への対応、共同設計、自社の SOP に合わせたワークフロー作りを支援する

**提供状況**は次のとおりです。Defend with Agents シナリオが GA、Secure Agentic Insiders と Secure your Foundations（exposure management）はプレビューです。スライドに QR コードがあり、サインアップできます。Hayete 氏は「失うものはない。誇張ではなく、今起きていることだ」と呼びかけて締めくくりました。

### 6.1 Agent 365：IT 管理者の視点（Vandana Sharma 氏）

目的は、新しいプラットフォームを接続し、エージェントが使うツールにガードレールを設け、支出を計画内に収めることです。前日のキーノートでは、Agent 365 を AT&T の視点から見せ、Charles 氏が「AI を使う段階から運用する段階への移行」を語ったとのことです。Microsoft 以外のエージェントが Microsoft のエージェントと並んで見えていたことも、前日に示されています。このデモはそこから一歩進み、IT 管理者の席に座って見せる、という位置づけです。

1. 接続先として、Databricks、Salesforce、Google などの**プラットフォーム**、**ツールや MCP サーバーのカタログ**、**エージェントのトラフィックを保護するゲートウェイ**を選べる。ここでは Databricks 向けに「Platform」を選ぶ
2. 接続前に、エージェントレジストリ、アクティビティと使用状況、ガバナンスとセキュリティ、リスクインサイト、コストとビジネス価値といった、そのプラットフォームで得られる内容が表示される
3. ログイン方法を選び、同期するワークスペースを選ぶ。内容を確認して「Connect」を実行する
4. 裏側で Agent 365 が、選んだワークスペースのツールとエージェントを取り込む。数秒でレジストリに表示され、Microsoft のエージェントと同じ可視性とセキュリティで扱われる
5. ツール（プラグイン、スキル、MCP サーバー、コネクタ）の一覧を開く。Microsoft 製、自社製、Microsoft 以外のサービス由来のものがある
6. エージェントがよく使う MCP サーバーの 1 つにガードレールを設定する。ブロックせず、1 つずつ「何ができて何ができないか」を確認しながら設定する
7. Action Center を開く。使用状況、セキュリティ、権限、コストなど、注意が必要なものが 1 か所にある。前日は非アクティブなエージェントのクリーンアップ自動化を扱った。この日は**所有者のいないエージェント**を扱う
8. 所有者のいないエージェントと、以前の所有者、以前の所有者のマネージャーが表示される。**エージェントを以前の所有者のマネージャーに再割り当てし、通知を送る**自動化を設定し、オンにする
9. コストでは、前日に示した上限とアラートを持つ支出ポリシーに続き、「上限をいくらにすべきか」を扱う。推測せず、**Cowork cost estimator** を実行して支出の見込みを確認する
10. その実績に基づくアラートを追加し、課金方法を選んで R&D チームにチャージバックする。支出ポリシーは、ユーザーに Cowork を有効にする前の必須ステップになっている

### 6.2 Agent 365 Business Analytics：ビジネスリーダーの視点（Stephanie Cronin 氏）

R&D オペレーションのリーダーが翌月の AI 予算を受け取った、という設定です。

1. Overview ページで、Copilot Cowork、GitHub Copilot、Agents にわたる支出、利用、価値を確認する。月の半分を少し過ぎたところで、予算内に収まっている
2. 「Cost & forecast」で、各サービスからそれぞれのモデルまでの費用の流れを見る。Copilot Cowork は R&D の利用の 39%
3. 「Use cases」で、タスク推論（task inferencing）に基づくユースケースの要約マップを見る。R&D が Copilot Cowork を仮説検証などに使っていること、コストと価値が並んで見えることが分かる。**価値はリーダーが決める**もので、自分たちのタスク時間とコストを使う。控えめな見積りであり、現金の削減額ではない
4. 前のグラフに戻ると、Copilot Cowork の利用が複数のモデルに分散している。これは Auto Model が、コストを最適化しつつ価値を最大化するためにタスクごとに適切なモデルを選んでいるため
5. 「Users & groups」で、総コストの 49% が、上位 5% のヘビーユーザーから発生していることを確認する。エンジニアリングは、ユーザー数が 3 分の 1 未満だがコストは半分を超えている
6. 「Cost & forecast」に戻り、コスト要因とモデルを見る。Claude Opus 5.5 が最も多く使われ、前月から 2 倍以上に増えている
7. カスタム予測を実行する。「Model mix」と「Use lower cost Claude models」を選ぶと、ベースラインへの影響がすぐに分かる
8. 作業自体への影響も確認する必要があるため、この予測をエンジニアリングの部門長と共有する。部門長は、出力品質や業務継続性を確認するパイロットや評価を行える
9. 「Reports」で、自社のビジネス成果を組み込んだレポートを作る。例では、Cowork の利用レベル別に R&D の成果を比較し、利用が最も多いチームほど全体に良い成果が出ていることが分かる

### 6.3 Perception：SOC のアラート対応（David Weston 氏）

背景として、SOC はアラートとインシデントが多すぎて人がトリアージしきれず、データ上は、Defender に入るアラートのうち人が実際に見ているのは半分以下だと説明されました（Hayete 氏は「50% は処理し、50% は無視される」と表現）。

最初に、Perception 内のエージェントを紹介するツアーがありました。

- **blue（Triage Agents など）**：ハンティング、トリアージ、調査を担当する
- **red**：Recon Agent は攻撃対象領域を先回りして調べ、ギャップを指摘する。ペネトレーションテストや脅威エミュレーションをするものもある。膨大なリスクの中で最も重要なものを特定する「新しい脅威インテリジェンス」と位置づけられた
- **green**：攻撃対象領域を減らし、問題を修正し、対応の優先順位づけも手伝う
- **Playbook**：複数のエージェントをチームとして組み、複雑な作業をさせる構成要素。例えば脅威インテリジェンスの blue エージェントが red エージェントに特定の攻撃者のエミュレーションを指示する、複数の blue と green を組み合わせる、など

Playbook の例として、純粋な blue のチェーンが示されました。

| エージェント | 役割 |
| --- | --- |
| Triage Agent | SIEM やエンドポイント検知のアラートを受け取り、真陽性か偽陽性かを判断する |
| Attack Investigation Agent | Microsoft のトップエキスパートなどの分析データで訓練され、ティア 4 相当のアナリストの文脈で動く。深く調べ、レポートを書き、アラートがより広い問題に発展したかを判断する |
| Detection Authoring Agent | トリアージ結果と調査レポートをもとに、コーディング能力で独自の検知を書き、組織の耐性を高める |

このような検知のチューニングには、従来はコードを書けるセキュリティ専門家のフルタイムの採用が必要だったと説明されました。またコストと所要時間を透明にするため、使うほど賢くなる、結果ベースの予測コストを出すモデルを裏で用意しているとのことです。

実際の流れ（デモ）は次のとおりです。

1. 1 日の始まりとして Perception の受信トレイを開く。「3 件が自分の承認待ち」と表示される。これは、エージェントが機密性の高い操作などで人の承認（human-in-the-loop）を必要としたときに起きる
2. かんばんボードを開く。ここが、エージェントのチームを管理する拠点になる。多くのチェーンは、時間ベース（例：15 分ごと）やイベントベース（例：アラートが来たとき）のトリガーで起動される
3. Okta が関わる攻撃について、Playbook が調査した結果が表示される。エージェントは、一連のアラートをすでに検証・調査しており、「ルールを公開したい。人の承認が必要」と依頼している
4. セッションを開くと、判定は **true positive**、インシデントの判断は**アカウントの侵害**、信頼度は高い。影響を受けたのは Caldova Clinical Operations Portal（Web アプリ）で、AWS Federation 上で動く侵害されたユーザーが関与している（固有名詞は音声認識の都合で表記が確定できません）
5. 攻撃グラフ（Attack Graph）が視覚的に表示され、エージェントがどう到達したかが分かる
6. エージェントは、いくつかのカスタム検知の公開を求めている。理由は、見つけた状態よりも良くして残そうとするため。追加すれば、より成熟した、豊かな保護が得られる
7. ルールを送信する。Hayete 氏が示した actuators が動き、カスタム検知が API に公開される。全体の保護がどう改善したかの可視化も確認できる

### 6.4 Perception：脆弱性のスキャンから修正まで（David Weston 氏）

前のデモと同じアプリケーションを対象に、MDASH の結果と動的ペンテストを組み合わせる流れです。説明の前提として、MDASH でスキャンした後、人が 1 件ずつ悪用可能かを確かめる代わりに、**動的なペンテストエージェント**に引き継ぎ、さらに exposure graph で、どのアプリをテストする価値があるかを判断する、と語られました（exposure list にないアプリは優先度が低くなる可能性があります）。

1. セッションを開始する。エージェントが、以前の MDASH スキャンの結果（48 件）を取り出す。誤検知か、重要度が低いか、攻撃対象領域で実際に到達可能かは、この時点では分からない
2. ペンテストエージェントがレポートを読み、エージェント同士がやり取りする。本番の可能性があるアプリにランダムな入力を送るため、承認を求められる。アプリの所有者である人が関わるようにするためで、これを送信する
3. ペンテストエージェントがコンテキストを読み、SQLMap、Nmap などのツールを実行して、結果を出す
4. 脆弱性レポートを開く。48 件の脆弱性が、**証明された 3 件**に絞られている。critical の SQL injection、staff profile の stored XSS、ownership check の欠如。具体的なソース情報、除外された内容、再現に必要な情報が得られる
5. システムは GitHub に接続されている。green エージェント（risk reduction agent）が修正コードを書く。修正は PR としてレビューに提出される。PR では、攻撃対象領域にあったこと、過去のインシデントで標的になったことなどを開発者に伝えられる
6. 開発者側の画面では、Perception Risk Reduction Agent の完全なレポートがあり、48 件のコードスキャンの検出、証明された 3 件の脆弱性、3 件の修正案が説明されている。Vulnerability Report と Remediation Report、diff、修正後にテストできる再現用の POST リクエストが含まれる

Hayete 氏は、セキュリティ担当者が開発者に PR を送るときは信頼性が必要であり、これは両チームが本当に重要な修正で協力する方法だと補足しています。

### 6.5 Perception：エージェントの発見と封じ込め（Yina Arenas 氏）

Yina 氏は、セキュリティ担当者の役割で始めます。数十万のエージェントを、個人で 1 つずつ管理することはできないため、システムが管理する必要がある、という前提です。

1. Perception の「AI Systems and Agents」が出発点。最上部にスナップショットがある。これは IT が Agent 365 で見ているエージェントレジストリと同じで、同じインベントリとコンテキストで作業できる
2. クラウドのエージェント、ローカルのエージェント、ツール、アクセスしている MCP、リスクがある場所が見える。David 氏のデモにあった、green と blue のエージェントが実行していることも見える
3. 次の保護が表示される。エージェントが有害な操作に誘導されないようにするランタイム保護、機密データの漏えいを防ぐデータ保護、安全でない宛先や未承認の宛先への到達を防ぐネットワーク保護、高リスクのエージェントによる機密リソースへのアクセスを動的に遮断する conditional access の動的制御
4. 動的な権限はすでに数百万件の権限要求を監査し、最小権限を強制している。新しい防御層である封じ込め（Microsoft execution container）は、デバイス上でエージェントを閉じ込めるサンドボックスとして働く
5. 環境にある約 50 万のエージェントのうち、26 件で悪意ある活動が防止された。クラウド、ローカル、Claude Code、Amazon Bedrock、Microsoft Foundry など、Microsoft 以外も含めてドリルダウンできる
6. Claude Code を開く。エージェントがユーザーとは別の ID を持っている。Perception が動的なエージェントリスクを計算済みで、すでに封じ込められている。ランタイムレベルで何にアクセスでき、何が無防備だったか、exposure のレベル、blast radius などが見える
7. 50 万を超えるエージェントを 1 つずつ見ることはできないが、Perception が 24 時間 365 日、機械の速度で作業するので、注意が必要な少数のエージェントに集中できる

続いて、エンドユーザーの視点です。セキュリティを入れて製品が使いにくくなり、イノベーションを妨げる事態を避けるための確認だと説明されました。

1. ユーザーとして Cloud Desktop（音声認識の都合で表記が確定できません）を使い、Snowflake のデータでダッシュボードを作る。ユーザーの ID とエージェントの ID は別で、エージェントは最小権限から始まる
2. Claude に、Snowflake の承認済み顧客データへのアクセスを求める。エージェントが権限を求め続けるが、ユーザーは何を承認すべきか分からない、という問題がある。新しい **Microsoft Access Orchestrator** が解決する。一度承認すれば、そのタスクに必要な権限だけがエージェントに与えられるよう管理される。「always allow」を選んでも、ユーザーが持つすべてのアクセスをエージェントに常時与えることにはならない
3. Access Orchestrator が各要求を評価し、動的なエージェント権限を使って、タスクに必要な権限だけを割り当てる。権限を取得し、データが返る
4. 売上（revenue）ダッシュボードを作る。今度はもう少し情報が必要になり、Access Orchestrator が拡張した権限セットを付与する
5. わざと危険なプロンプトを送る。Web からコピーした内容に悪意のある指示が含まれる場合を想定している。1 つ目は、デバイス上の environment file の情報を読む指示を含むプロンプトで、**Defender が要求をブロック**し、モデルには届かなかった。ユーザーには何が起きたかの通知が出る
6. 2 つ目は、機密の予測データを使うよう依頼するプロンプト。**Microsoft Purview が機密情報を含む要求だと認識**し、モデルに届く前にブロックする。組織がすでに設定したポリシーが適用される
7. 複数のリスクシグナルが入り、動的エージェントリスクが高になる。Perception は、Snowflake への以降の要求をブロックする。ID が分離されているため、ユーザー本人は引き続き Snowflake の情報にアクセスできる

### 6.6 Perception：基盤の強化と exposure management（Ron Pessner 氏）

Ron 氏は、脆弱性管理を担当するセキュリティ担当者の役割で、green エージェントを使ってリスクを下げます。

1. 左のレールにある **AI Readiness Initiatives** を開く。Perception が環境と現在の露出を理解し、姿勢強化のための推奨を出す。取り組みは Identities、Devices、Data、Agents などのドメイン別に整理されている
2. Identity を開く。Perception が **Modernize Authentication** の取り組みを推奨している。長期の取り組みの 1 つで、中の「注意が必要な項目」を確認する
3. Perception が管理者向けの passkeys を推奨している。passkeys は、現在フィッシングに対して最も有効な保護だという説明がある。管理者のうち 121 人中 85 人が passkeys を登録済みで、**未登録は 36 人**
4. 選択肢は 2 つある。手動の手順で進めるか、green エージェントに任せるか。後者を選び、Playbook とエージェントが行うタスクを確認して、セッションを開始する
5. identity reduction agent が作業を進める。重要なステップでは人の承認を求める。ここでは、これらの管理者アカウントに対する **conditional access ポリシーの変更**の承認を求められ、「Submit」を選ぶ
6. 完了後、Modernize Authentication の取り組みの進捗レポートを作り、経営層に送れる
7. 次に新たな脅威を見る。Perception Home（1 日の始まりの受信トレイ）の最上部に、PHP の重大な脆弱性が推奨表示されている。Microsoft Threat Intelligence と Perception が、注意すべき点を示す
8. クリックして概要を見る。認証なしの攻撃者がリモートでコードを実行し、影響を受ける Web サーバーを完全に制御できる。「Review the risk overview」を選ぶと、Perception が自分の環境でなぜ重要かを説明する。Ron 氏は、これは自分のチームなら数日から数週間かかる作業で、Perception は数分で行うと述べた
9. PHP が動くサーバーは 684 台、うちインターネットに公開されているものは 126 台、攻撃パス上にあるものは 1 台。攻撃パスを開くと、インターネットに公開された customer web portal が、顧客の注文情報などの重要な資産に到達しうる経路になっている。公開されている 126 台も、それぞれ侵入口になるため重要だが、まずこの 1 台に対応する
10. **Risk Reduction Playbook** を起動し、計画を確認してセッションを開始する。Risk Reduction Agent が実行し、推奨される統制の確認を求める
11. 統制を確認すると、IT チームの作業が必要だと分かる。Perception は既存のロールベースのアクセス制御を尊重する。ServiceNow でチケットを開いて IT チームにタスクを割り当てる。**IT が承認するまで、エージェントは次の作業をしない**
12. IT が承認したことを Perception で確認し、エージェントが作業を完了する。重要な資産への経路は閉じられる

## 7. 注意点・発表者の気付き

発表の中で、導入や運用の注意として語られた点を整理します。

- **AI は信頼できない**：自社で作ったエージェントでも持ち込まれたものでも同様で、目標達成のために意図と違う動きをしたり、他のエージェントと協力して権限を得たりするという前提で設計する、と説明されました。
- **エージェントの権限**：エージェントにユーザーの権限をそのまま与えず、ユーザーとは別の ID、最小権限を基本とします。権限過剰な AI システムは非常に危険だという注意がありました。
- **人の承認を挟む**：Perception のデモでは、本番の可能性があるアプリへのペンテスト、検知ルールの公開、conditional access の変更、他部門の作業が必要な統制で、人や IT の承認を求めていました。Bank of England も、エージェントは判断の支援に使い、常に人が関与していると語っています。
- **先に計画する**：コストの統制は、後から適用するより先に計画する方がよい。最適化は初期に過剰に行いがちなので、順番を守る（plan → control → optimize）。
- **コスト上限は推測で決めない**：Cowork cost estimator の見込みに基づいて決める。Cowork の支出ポリシーは、ユーザーに有効にする前の必須ステップ。
- **モデルを下げるときの影響確認**：低コストの Claude モデルへの切り替えは、品質や業務継続性を、パイロットや評価で確認する必要がある（Business Analytics のデモで語られた点）。
- **セキュリティが使い勝手を損なわないようにする**：エンドユーザーの視点でも保護が働くことを確認する、という配慮が示されました。
- **未対処の基盤の弱点**：ID、データ分類、ネットワーク分離、脆弱性の修正を後回しにしていると、AI の攻撃者に見つけられる。
- **発見件数の増加**：脆弱性は見つけるだけでは騒音になる。優先順位づけと修正までをループにする。
- **運用モデルの再設計**：エージェントのループはチームをまたぐため、誰が何をするかを明確にしておく必要がある。
- **提供状況の差**：Perception の GA は Defend with Agents のシナリオのみで、Secure Agentic Insiders と Secure your Foundations（exposure management）はプレビュー。Business Analytics の一部機能は Frontier Public Preview、business impact reports は 12 月予定。

## 9. まとめ

このセッションの要点は次のとおりです。

1. Agent 365 は、Microsoft と他社のプラットフォームにまたがるエージェントと AI 資産の単一のレジストリで、Action Center により、注意すべきものの確認と自動化を 1 か所で行えます。マルチテナントのスキャンやツールのガバナンスにも対応を広げています。
2. コスト管理は plan、control、optimize の順に進め、コストと価値をあわせて見ます。AI 支出の 80% がビジネス部門の予算から出ているという変化に対し、Business Analytics が IT とビジネス部門の協働を支えます。
3. AI の攻撃者は自律化しており、Agentic Insider も含めて AI は信頼できないという前提が必要です。Microsoft は security context、Perception（red、blue、green）、マルチモデルで、エージェントによる防御を打ち出しました。
4. Perception は発表時点で GA（Defend with Agents）となり、Agentic Insider の保護と基盤強化はプレビューです。デモでは SOC のトリアージ、脆弱性の発見から修正、エージェントの封じ込め、exposure management が示されました。
5. 導入では、人とエージェントの分担、チーム間の運用モデル、RBAC、予算（FinOps）を決める必要があります。Hayete 氏は、イノベーションと安全の二者択一ではないと述べています。
