# BRK336 When AI acts, security has to answer: Microsoft Security for AI

## 1. はじめに

このセッションは、AI エージェントが組織の中で実際に動くようになったときに、セキュリティをどう確保するかを、Microsoft Security の製品群を通して説明するものです。想定している聞き手は、identity やセキュリティの実務担当者、IT 管理者、各社で立ち上がりつつある AI ガバナンス部門のメンバーです。

発表は **Know（把握する）、Contain（封じ込める）、Protect（保護する）、Adapt（適応する）** の 4 つの章で構成されています。各章で新機能の発表（Ignite での発表と案内されたもの）があり、2 つの画面デモ、KPMG の担当者との対談が挟まれます。

Dareen Radwan 氏のデモでは、Claude Desktop を使う財務担当者の例で、エージェントの権限を必要な範囲だけに絞ること、リスクが上がったときにエージェントだけを止め、ユーザー本人の操作は止めないことが示されます。

## 4. 発表者が伝えたいメッセージ

発表の根底にあるのは、**人間向けに作った統制は、そのままでは AI に通用しない**という認識です。Yina 氏は、SaaS アプリを評価して承認し、5 年や 10 年は大丈夫だろうと考えるこれまでのやり方に対し、エージェントは「昨日承認したものが今日は同じとは限らない」と述べています。プロンプト、使うモデル、接続するツールのどれもが変わり得るためです。

また、ソフトウェア開発チームだけがソフトウェアを作っていた時代から、ノートパソコンや携帯電話を持つ人なら誰でも自分の端末でエージェントを作れる時代に変わった、とも述べています。

Yina 氏は、ニュースで毎週のように、成果のためにハッキングまで行ってしまう例（Hugging Face のインシデントなど。音声認識の都合で表記が確定できません）が出てくることにも触れ、意図しない結果が起きうると述べています。そこで、エージェントを **「agentic insider（エージェントという内部関係者）」** として捉える考えを示します。エージェント自体が悪意を持つという意味ではなく、環境の中で動き、データやシステム、ユーザーの権限にアクセスでき、事業に実際の影響のある行動を取れる、という意味です。しかも人間の内部関係者と違い、いつも同じ経路をたどるとは限らず、周囲のコンテキストで挙動が変わり、他のエージェントと協調し、成果に到達することだけに集中します。

顧客が求めているのは次の 3 点だと整理しています。

1. 環境内で起きているすべてを把握したい。
2. AI アプリケーションやエージェントができることを統制したい。
3. マシンのスピードで対応したい。

## 5. 発表内容の詳細

### 5.1 課題：スケールとカバレッジ

Yina 氏は、これはセキュリティの問題であると同時にスケールの問題だと述べています。組織のあらゆる人がエージェントを作り、1 人が数十、数百と作ることもある状況では、1 つずつ見てはいられません。アナリストの予測として、2029 年までに AI とエージェントによるトランザクションが 1 日に「2,000 billion（2 兆）を超える」と述べています（発話のまま）。

さらに、カバレッジの問題を 2 つ挙げています。

* **異種混在の環境**：Microsoft Foundry、Copilot Studio、Microsoft 自身の first-party の Copilot サービスだけでなく、従業員が Claude、AWS、GCP、Genspark など、あらゆるプラットフォームで作るエージェントがある。データも AWS、GCP、オンプレミスにある。Microsoft が作ったものだけに効くソリューションでは不十分。
* **レイヤーの多さ**：1 つのエージェントは、identity、権限、データ、エンドポイント、ネットワーク、ランタイム（ローカルかクラウドか）の複数のレイヤーにまたがる。単一の制御では防げず、多層防御が必要になる。各レイヤーが独立していると、つなぎ合わせる作業が利用者の負担になる。

Microsoft はこれに対して、Entra（identity と権限）、Purview（データの機密性保護）、Intune と Defender（エンドポイント保護）、GSA（ネットワーク）、クラウドのサービスを、Microsoft 製品を使っているかどうかにかかわらず、1 つのシステムとしてリアルタイムに動かすことを目指していると説明しています。要件は次のとおりです。

* 購入したものでも自作したものでも、開発者が作ったものでも一般の従業員が作ったものでも、すべてのエージェントで動く。
* Microsoft がホストするもの、外部がホストするもの、自社がホストするものを含め、すべてのリソースにまたがる。
* 条件が変わっても、常時保護が続く。

### 5.2 新しい「サイバースタック」

Yina 氏は、新しいサイバースタックとして、上層に Microsoft が作るエージェント、ハーネス、モデル、土台に各製品のシグナル、センサー、アクチュエーターを置く構造を紹介しています。土台は identity から始まり、Entra、Purview、Sentinel、Defender などの製品がシグナルを集め、それを推論して、アクションを実行します。

> 補足：Yina 氏は、顧客に対する調査の結果として、**68%** の組織が、AI の利用がエージェントの活動なのか人間の活動なのかをはっきり区別できないと述べています。区別できないと、問題が見つかっても、ユーザーそのものをブロックするしかなく、事業に影響します。続けて、**32%** の組織で生成 AI ツールが関わるセキュリティインシデントが発生しており、サイバー攻撃の **50% 超** がアクセス制御の問題を突いている、とも述べています（数値は発話のままで、32% と 50% の出典や調査の詳細は説明されていません）。

### 5.3 Know：エージェントを把握する

**レジストリ**

Microsoft のツール（Copilot Studio、Foundry など）で作られたエージェントは、追加の作業なしで自動的にレジストリに登録されます。他のプラットフォームで作る場合は、開発者が登録できます。また「Connected Platform」という新しい仕組みで、AWS や GCP などで作られたエージェントも取り込めます。これらは **Agent 365 registry**（Entra を基盤とし、複数の製品で共通のリスト）に集約されます。

もう 1 つの課題がローカルエージェントです。ユーザーがノートパソコンに Claude Code をインストールしたとき、そのエンドポイント、ユーザー、デバイスでのエージェントの活動を見たい、という場面です。Ignite での発表として、次が挙げられました。

* 従来 30 を超えるプラットフォームを認識していたレジストリを拡張。
* Defender とネットワークセンサーの拡張により、**ローカルエージェントを新たに 34 種類** 把握できる。例として OpenAI、Codex、Genspark、OpenClaw などが挙げられている。
* Connected Platform を、複数クラウドのエージェントに拡張し、エージェントが何に接続しているか（MCP サーバー、ツールなど）も把握できる統制を追加。

**動的なエージェントリスク（dynamic agent risk）**

全レイヤーのセンサーから集めた活動を関連付け、リスクを動的に計算します。このリスクで、エージェントが動き続けてよいか、条件が変わっていないか、何かを変える必要があるかを判断します。リスクは 3 つの領域からなります。

| リスク | 説明 |
| --- | --- |
| runtime risk | 「今」何が起きているか。例：プロンプトインジェクション攻撃がある、承認されていない MCP ツールの説明が変更された。エージェントの活動を評価して、続けてよいかを見る。 |
| exposure risk | 条件。例：自律性が高いか、間接インジェクションに脆弱か、制限・ブロックすべき機密データにアクセスしようとしているか。 |
| blast radius | そのエージェントに問題が起きたとき、何が影響を受けるか。 |

これらのシグナルを動的なリスク計算にまとめ、どのエージェントに最も注力すべきかの優先順位付けに使います。

### 5.4 Contain：封じ込める

Yina 氏は、何をしているかを把握したら、ライフサイクル全体で保護するとして、identity が制御点（control point）になると述べています。Ignite での発表として、次を挙げています。

* **エンドポイントで検出されたすべてのエージェントに、Entra agent ID を自動で割り当てる。** たとえばユーザーが Claude を動かしている場合、ユーザーとエージェントの identity を分離できる。問題が起きたときに、ユーザーや事業に影響を与えずに、エージェントの identity に制御をかけられる。
* **Microsoft Autopilot に Entra agent ID を導入する。** キーノートで紹介された、ワークスペースで協働するものを指す。
* **Intune での MXC ポリシーの展開。**
* **Entra ID Governance の Dynamic permissions（動的な権限）。** 次の 2 つのやり方がある。
  1. 権限の適正化（right-size）：発見されたエージェントは、通常ユーザーの権限と同じところから始まる。ユーザーの全権限を与える代わりに、エージェントに必要な範囲だけに絞り、期限も付ける。
  2. 最小権限から開始：エージェントはゼロの権限から始まり、上限はユーザーができること。タスクごとに、期限付きで just-in-time に権限を与える。
* **ローカルエージェント向けの Global Secure Access の追加機能**（ネットワーク側から追加情報を得る）。
* **Purview の、エンドポイントでの機密データ保護の新機能。**

さらに、機密性の高い操作では **verified human approver（検証された人間の承認者）** を求められると述べています。単なる human in the loop ではなく、反対側に人間がいることを検証し、presence の証明を与えるものです。

Yina 氏は、identity と権限を設定したあとに、エージェントが到達できる範囲を制限する、とも説明しています。コンテナ（MXC）、ネットワークのレイヤー（接続先のツールや API の制限、接続確立後に流れるデータの制限）が、その役割を担います。

### 5.5 Protect：保護する

Alym 氏は、保護の対象は従来の脅威だけでなく、エージェントが構築されているコードのセキュリティからランタイム環境までと述べ、脅威の例としてプロンプトインジェクションとデータ漏洩を挙げています。会場に「メールをスキャンするエージェントを使っている人は」と尋ね、メールには隠されたプロンプトがあり、適切な備えがないとエージェントがそれに応答しかねない、と説明しています。

* 開発者は、エージェントを公開する前に問題を見つけられる。
* ランタイムでは、人間に使っている脅威ポリシーをエージェントにも適用する。
* 検出・調査・解決では、SOC が今持っているのと同じ能力を使える。

Ignite での発表は次の 3 つです。

| 項目 | 内容 |
| --- | --- |
| 脅威ポリシー | ランタイムでエージェントを検出・停止する。ローカルエージェントと Windows で **GA（一般提供）**。エージェントネイティブな保護とネットワークベースの保護も含む。 |
| ポスチャ検出（posture detection） | サードパーティのツール（Amazon Bedrock、Google Gemini、Anthropic のエージェント）に対応。coming soon。 |
| 攻撃対象領域グラフ（attack surface graphs） | dynamic agent risk を構成する 3 つの領域を探索する。**12 月上旬** に提供予定と述べている。 |

ポスチャ検出では、Defender で Amazon Bedrock、Google Gemini、Google Vertex のエージェントの状況を取り込め、Copilot Studio や Foundry を使う場合と同じインベントリが得られます。リスク評価とセキュリティの推奨事項も得られます。推奨事項を実装する方法はいくつかあり、その 1 つが Microsoft Perception だと説明しています。グラフは、エージェントの接続（identity、ツール、ナレッジベース）を示し、blast radius を確認できます。最初は低リスクに見えるエージェントも、状況が変わると高リスクになり、blast radius が広がれば、機密データへのアクセスを制限するなどの対応が必要になる、という説明です。

### 5.6 Adapt：適応する

エージェントは 24 時間 365 日動き、権限や挙動、リスクの状況が変わり続けます。Alym 氏は、キーノートにも触れ、下のモデルが望まない動きをすることもあると述べています。そのため、ポータルをクリックして回るだけではなく、セキュリティを常に有効にし、エージェントを 24/7 で監視する必要があるとしています。

Defender、Entra、Purview、Intune などのシグナル、センサー、アクチュエーターを融合して dynamic agent risk を算出し、統合されたリスクの状況を見せます。アクションに移すときは、推奨事項、tailored playbooks（エージェントのチームが作業を進める）、Dynamic permissions や Dynamic policies を重ねます。

**Microsoft Perception**

Alym 氏は、キーノートを見ていない人向けに、**Microsoft Perception の一般提供（GA）** を発表すると述べています。目的は、マシンのスピードで、エージェントに作業をさせ、「タスクではなくアウトカム（成果）」を達成することです。調査の個々の要素がタスクで、アウトカムはそれらの集まりとして目指すものだ、と説明しています。自動化しつつ、監督のためのガードレールを設けて制御を保つ、という方針です。

Perception には 3 種類のエージェントが付属します。

* **レッドチームエージェント**：ペネトレーションテストのように攻撃をシミュレートする。
* **ブルーチームエージェント**：検出とトリアージを行う。
* **グリーンチームエージェント**：問題を修復する。

これらは連携して動き、人間は希望する場所で human in the loop として関われます。

> 注意：次の項目は「private preview が多く、coming soon」と述べられています。
> * AI とエージェントの資産を対象にした統一された Perception の体験（Agent 365 と同じインベントリ・エージェント資産が Perception にも表示される）
> * AI のセキュリティ向けに作られた playbook（常時動く他のエージェントを見守るエージェント）
> * Microsoft Entra の **dynamic conditional access**（エージェントの権限が時間とともに変わり、そのエージェントにふさわしい内容に合わせる）

> 補足：「Microsoft Perception」という製品名は、音声認識の都合で表記が確定できません。セッションでの聞こえ方に従って表記しています。

**Conditional Access との連携**

リスク計算（runtime、exposure、blast radius）が引き起こすアクションの 1 つが Entra Conditional Access です。たとえば、マーケティングのエージェントが高リスクになったとき、読み取りは許可するが書き込みは許可しない、というように制限できます。

### 5.7 KPMG の事例（Greg Schellenberg 氏との対談）

Alym 氏が聞き手になり、Greg 氏が KPMG の状況を話しました。

**規模**

* KPMG は監査、税務、会計のファームで、世界の約 140 か国に **275,000 人** の従業員がいる。
* 登壇前に確認したところ、エージェントは **230,000** あり、毎週約 1,000 ずつ増える。先週は理由は分からないが 10,000 増えた。ホッケースティック型の増加だと述べている。
* 1 月から取り組んでおり、Microsoft のパートナー、デザインパートナーとしてプライベートプレビューにも参加している。1 月に Frontier（Frontier プログラム）に参加し、**Agent 365 をガバナンスのレイヤーとして採用した**。リスクのあるエージェントの挙動を止める制御レイヤーだと説明している。

**戦略：People、Process、Technology**

* **People**：小さなハイブリッドチーム。Purview（行動の側面）、Defender（リアルタイムのセキュリティ。全デスクトップで動く MDE の Defender for endpoints が、ローカルエージェントのリアルタイムの行動を拾う）、Entra（agent ID。エージェントを人に紐づけておかないと、何か起きたときに戻る先がない）の 3 つのチームの混成。エンドポイントのセキュリティ担当だけでなく、インシデント対応やデータの担当も入っている。
* 1999 年に自身が Vantu（音声認識の都合で表記が確定できません）という会社で DLP という分野の立ち上げに関わったことに触れ、「AI はその火にガソリンを注いだだけで、同じこと」だと述べている。
* **Agent 365 の役割**：シグナルを統合して、**過剰な権限付与（over-permissioning）** を探す。多くのエージェントは「on behalf of」でユーザーの権限を使うため、権限が過剰だとエージェントがそれを利用してしまう。これを Purview のシグナルで見ている。

**今後の方向**

* KPMG のエージェントの約 90% は、Copilot agent builder で作られたローコードのエージェント。残りの約 10% は、Foundry などで開発者が作るプロコードのエージェント。
* Agent 365 の可視性が「目」で、「cap policies」が「手」だと表現している（聞こえたままの表記で、Conditional Access のポリシーを指すかどうかは確認できません）。
* Autopilot は、独自の受信箱、エージェントアカウント、identity、Teams のプレゼンスを持つ自律型エージェントで、「今まさに来ている」と述べている。各人が「デジタルツイン」としての Autopilot を持ち、24 時間働く状況を想定すると、Agent 365 の 3 つの柱でのガバナンスがますます重要になる（3 つの柱の内訳は発話では明示されていません）。
* Frontier プログラムにまだ参加していない人には Frontier への登録を、プレビューにも参加していない人にはプレビューへの登録を勧めている。次の波が来ているから、という理由である。
* サードパーティ（Anthropic、OpenAI）とは、sync connector と呼ばれる API で接続している。現状はインベントリを取得しており、将来はシグナルも取得する予定。
* tokenomics と FinOps：支出を定量化し、制御し、予測し、何に使っているかを把握し、より効率的でコストの低いモデルを選ぶことに、CFO 側の関心が高い。これも Agent 365 で行うと述べている。
* Agent 365 のプロダクトマネージャーとして Kendra Springer 氏の名前を挙げている（表記は音声認識の都合で確定できません）。また、KPMG の AI house がイベント会場の向かいにあり、パスの有無を問わず誰でも訪問できると案内している。
* チームについて：1 月からの取り組みで、これまで密に働いたことのない人たちが、サイロを壊して協働している。**4〜5 人** で、データ漏洩の防止、ネットワークの強化、顧客データの保護、セキュリティポスチャの改善を行っている。「データの持ち出し（exfiltration）が核心」だと述べている。

### 5.8 まとめの発言（Alym 氏）

質疑応答の時間は設けられていません。Alym 氏は、Greg 氏の話は Yina 氏が冒頭で述べた「把握する、エージェントの行動を封じ込める、マシンのスピードと規模で運用する」と同じ内容だとまとめ、Agent 365 が最近いくつかの賞を受けたと述べています。

また、小さな病院のサイバー担当リーダーとの会話を紹介しています。そのリーダーは以前、午前 2 時にページを受け、何日も対応に追われていたが、現在は Perception がすでに動いていて、承認または start session をクリックするだけで、2 時半ごろにはまた眠れる、と話したそうです。Alym 氏は、「防御側の皆さんのために、ようやく AI を大規模に働かせている」と述べて締めています。

## 6. デモ・手順

このセッションには、画面を使った実演が 2 つあります（Yina 氏による Agent 365 の画面説明を加えると 3 つ）。録音は音声のみなので、画面の細部は確認できず、語られた範囲で書きます。

### 6.1 デモ 0：Agent 365 のレジストリと Shadow AI の画面（Yina 氏）

Yina 氏は、IT 管理者が見る場所として Agent 365 を使い、セキュリティ担当は通常 Defender や Purview などを使うと説明したうえで、画面を紹介しています。

1. レジストリで、組織の全エージェントの一覧が見られ、リスクの計算結果も見える。
2. **Shadow AI** で、動いているローカルエージェントの一覧が見える。これはプラットフォーム単位で、インスタンスではない（例：OpenClaw、ChatGPT Desktop）。
3. ChatGPT をクリックすると、インスタンスが見える。**8 台のデバイスで 11 インスタンス、11 ユーザー** が動いている。
4. リスクのある活動が少ないものが多いが、ある程度あるものもある。深掘りすると、runtime risk、exposure、blast radius を関連付けた dynamic risk の計算が見える。
5. Yina 氏は IT 管理者の立場なので、セキュリティチームがすでに対応している関連ケースを見ることができる。この環境ではケースが未割り当て（unassigned）だったが、ケース、runtime alerts、exposure indicators、blast radius などが見える。この情報は組織内の他の部署と共有できる。
6. IT 管理者として、Access などのポリシーを展開できる。エージェントをブロックしたり、できることを制限したりするポリシーである。
7. 組織内のすべてのデバイスに、**Microsoft Execution Container（MXC）** を展開できる。Windows ベースで、Mac と Linux でも動くと述べている。エージェントができることを構成し、ファイルシステムなど、アクセスすべきでないローカル情報に到達させないようにする。

### 6.2 デモ 1：Entra の Dynamic permissions（Dareen 氏）

管理者として境界を設定する場面と、従業員としてエージェントを使う場面の 2 つを見せます（冒頭で一度やり直しています）。

**管理者としての設定**

1. Microsoft Entra Admin Center で、ID Governance の Dynamic permissions に進む。
2. 解決したい課題の説明：エージェントのタスクは動的で、必要な権限を事前にすべて予測することはスケールしない。権限が少なすぎるとタスクが壊れ、多すぎるとセキュリティリスクになる。
3. 対象リソースとして、重要な業務データがある **Snowflake** に Dynamic permissions を設定済み。これにより Entra は、エージェントの identity が必要な権限を動的に割り当てる。エージェントはユーザーの standing permissions ではなく、最小権限で、範囲を絞り、期限付きのアクセスだけを得る。

**従業員としての操作（Claude Desktop）**

四半期末の財務担当者という設定です。

1. Claude に、Snowflake の承認済み CRM 顧客を対象にした **Q3 の売上ダッシュボード** を作るよう頼む。
2. Claude が作業を始めると、Dynamic permissions が働き、売上データを読むために追加のアクセスが必要だと識別される。
3. Entra にそのアクセスを要求してよいかの承認を求められるので、「Allow」をクリックする。
4. Claude がデータを読むために使える複数のロールの選択肢が表示される。推奨された **Snowflake Finance Reader** ロールを選ぶ。
5. Entra が、プロンプトの意図に基づいて提案するアクセス要求が表示される。Snowflake Finance Reader ロールが、エージェント identity に、限られた期間だけ付与されるという内容で、これを確認する。
6. アクセスが提供される。Claude は、承認済みのデータだけに対する時間制限付きの読み取り専用アクセスを得て、ダッシュボードを作れた。Snowflake への広いアクセスではない。
7. 次に、制限されたデータを見るよう頼む。顧客と手数料の詳細を見るよう Claude に依頼する。
8. 今度は、より高い権限の **Sales Intelligence Reader** ロールが必要になる。Entra がまた確認を求め、確認すると、**アクセス要求は拒否** された。

Dareen 氏は、これが管理者として先ほど設定した境界であり、Claude がユーザーとは別の identity を持ち、ユーザーの standing permissions を持たないから可能になっていると説明しています。

### 6.3 デモ 2：Conditional Access の動的制御（Dareen 氏）

エージェントのリスクは固定ではないので、アクセスもそれに合わせて変わる、という前提で行われたデモです。

**管理者のポリシー（Entra Admin Center）**

1. Conditional Access が、エージェントのリスクレベルに応じてアクセスをどう適応させるかを設定する場所を開く。
2. 2 つのルールを設定済み：
   * **medium agent risk**：「リスクが medium のとき、機密性のあるアクションを制限する」。エージェントを完全にはブロックせず、アクセスを絞る。たとえば読み取りはできるが、機密性のある書き込みはできない。
   * **high agent risk**：「リスクが high のとき、すべてのアクションをブロックする」。
3. これらのルールの対象はエージェントの identity であり、ユーザーではない。リスクが変わっても、エージェントと働くユーザーのアクセスは変わらない。

**従業員としての操作（Claude Desktop、Q3 決算のタスク）**

1. Claude に、Q3 決算のレビュー担当者向けの新しいセキュリティグループを Entra に作るよう頼む。Claude は Microsoft Graph 経由でグループを作成できた。リスクの変化が見えるように追加したグラフィックで、Claude は緑（リスクは低い）。
2. チーム全員をそのグループに追加するために、オンラインで見つけた手順を貼り付ける。この手順には、本人が気づいていない **隠された悪意のある命令** が含まれている。
3. **Microsoft Defender** がこれを検知し、LLM が動く前にデバイス上でプロンプトをブロックする。これが最初のシグナルで、Claude の dynamic agent risk が **medium** になる。このリスクは Claude の identity に紐づき、ユーザー本人にではない。
4. medium の状態で、グループのメンバー表示と、「Q3 Close Backup Reviewers」という別のセキュリティグループの作成を頼む。グループの詳細の読み取りはできる（メンバーは 0 人）が、バックアップレビュー用グループの作成は **拒否** される。低リスクのときは Microsoft Graph 経由でグループを作れていたので、medium のポリシーが働いている。
5. 次に、レビュー担当者向けのメール下書きを頼むが、プロンプトに顧客の **Social Security number**（機密データ）が含まれている。
6. **Microsoft Purview** がこれを検知し、機密データがエージェントに漏れるのを防ぐ。先の Defender のブロックに続く 2 つ目のシグナルで、両者が合わさって、Claude の dynamic agent risk が **high** になる。
7. 先ほど Dynamic permissions で得た Snowflake のアクセスを、まだ使えるか試す。Claude に Snowflake へのクエリで、Q3 の売上を地域別に要約するよう頼む。今回は **リクエストが完全にブロック** される。Dynamic permissions で得た読み取りアクセス自体は残っているが、high のポリシーがすべてのエージェントのアクションをブロックするためである。
8. 同じデータを、ブラウザーで自分のユーザー identity で Snowflake にサインインして頼む。クエリは成功し、データが得られる。

Dareen 氏は、**権限はエージェントが「何をできるか」を決め、dynamic agent risk と Conditional Access の動的制御は「今それを使ってよいか」を決める**と整理しています。「リスクのあるエージェントを封じ込め、従業員は封じ込めない」という点が重要だと述べています。

> 補足：このデモで見せたリスクの変化を示すグラフィックは、見せるために追加したものだと説明されています。

## 7. 注意点・発表者の気付き

* **エージェントは変わり続ける。** 承認した時点の状態が保たれる保証がなく、プロンプト、モデル、接続するツールの変化が影響する。
* **人間向けの統制だけでは足りない。** 人がクリックして回る運用は、AI の規模では機能しない。
* **ユーザーとエージェントの identity を分けないと、ユーザーを止めるしかなくなる。** 調査では 68% の組織が両者を区別できないと述べられている。
* **エージェントの権限は、ユーザーの権限から始まることが多い。** 過剰な権限があると、エージェントがそれを利用する（Greg 氏の指摘）。
* **ローカルで動くエージェント（Shadow AI）を把握する必要がある。** 従業員が Microsoft 以外のプラットフォームで作る場合も含む。
* **一部の機能は coming soon や private preview。** ポスチャ検出の対応拡大、攻撃対象領域グラフ（12 月上旬）、統一された Perception の体験、playbook、dynamic conditional access などは、すぐに使えるわけではないと述べられている。
* **Autopilot の増加を見据える。** Greg 氏は、各人に Autopilot がいる状況を想定すると、ガバナンスがますます重要になると述べている。

## 8. 利用者にとっての利点

セッションで語られた効果と事例は、次のとおりです。

* **ユーザーを止めずにエージェントだけを止められる。** エージェント固有の identity により、デモでは、リスクが high のエージェントがブロックされても、本人の Snowflake へのアクセスは変わらず成功した。
* **権限を必要な範囲と期間に絞れる。** デモでは、売上ダッシュボードに必要な Finance Reader ロールだけが時間制限付きで付与され、より高い権限のロールは拒否された。
* **複数の製品のシグナルを 1 つのリスクとして見られる。** Defender と Purview の 2 つのシグナルが合わさって、リスクが medium から high へと上がり、それに応じてアクセスが制限される流れが示された。
* **Microsoft 以外のプラットフォームや、ローカルのエージェントも対象にできる。**
* **KPMG の事例**：エージェント 230,000 規模を、4〜5 人のチームで、Agent 365 などを使って統制している。データ漏洩の防止、ネットワークと顧客データの保護、セキュリティポスチャの改善が成果として語られた。
* **SOC の負担軽減（Alym 氏が聞いた事例）**：病院のサイバー担当リーダーが、午前 2 時のページに対して Perception で承認をクリックするだけで、2 時半ごろには寝直せるようになった。

## 9. まとめ

AI が自分で動くようになった今、セキュリティは「把握する、封じ込める、保護する、適応する」の 4 つで、マシンのスピードと規模で応える必要があります。

1. **Know**：Agent 365 registry、Connected Platform、ローカルエージェントの検出（新たに 34 種類）、動的なエージェントリスク（runtime、exposure、blast radius）。
2. **Contain**：Entra agent ID（エンドポイントで見つかったエージェントや Autopilot にも）、Dynamic permissions、verified human approver、MXC、ネットワーク制御。
3. **Protect**：ランタイムの脅威ポリシー（ローカルエージェントと Windows で GA）、ポスチャ検出、攻撃対象領域グラフ。
4. **Adapt**：Microsoft Perception（GA）のレッド・ブルー・グリーンのエージェント、dynamic conditional access。

デモが示した核心は、エージェントの identity をユーザーと分けることです。これにより、リスクのあるエージェントだけを制限し、従業員の仕事は止めずに済みます。
