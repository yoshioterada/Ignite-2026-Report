# BRK334 Modern Phishing Doesn't End at the Click

## 1. はじめに

このセッションは、フィッシングを「メールのリンクをクリックさせて終わり」の攻撃ではなく、「欺瞞（だまし）が信頼されたアクセスに変わるまで」の一連の流れとして捉え直すものです。AI によってフィッシングが大規模・高速・高精度になっている現状を数字で示し、実際の攻撃の事例（フィッシングのツールキット 1 つと、脅威グループ 2 つ）を 3 つ取り上げたうえで、それらに対する Microsoft の防御を「検出と対応（Defender）」と「予防（Entra の passkey と Verified ID）」の 2 方向から解説しています。

結論は、発表の最後に出てきた次の一文に集約されます。**防御は、クリックの後に続く意思決定（アクセスを付与する、復旧する、拡大する場面）まで追いかけなければならない**、という考えです。

デモが複数あり、セキュリティ（SOC）担当者と ID 管理者の両方に向けた内容です。passkey と Verified ID を組み合わせた機能は public preview、Teams の合成音声検出は limited preview の例として紹介されています。

## 4. 発表者が伝えたいメッセージ

発表者は、AI はフィッシングを新しくしたのではなく、**より大規模で、安く、速く、はるかに説得力のあるものにした**と説明しています。見た目がプロフェッショナルな文面は、もはや信頼する理由として弱くなりました。そこで防御側は、人に届く「コミュニケーション」と、その後の「アクセスの判断」の両方に対処する必要がある、という主張です。

もう一つの軸は「セキュリティを左（上流）に寄せる」ことです。悪意のあるリンク・ファイル・メールを検出して対応するだけでなく、悪意のあるファイルやリンクやメッセージをブロックし、なりすましを遮り、アクセスを制限するポリシーを適用する。さらに上流では、攻撃者が欺瞞を「信頼されたアクセス」に変えること自体を防ぐ、という考え方です。

## 5. 発表内容の詳細

### 5.1 AI がもたらした変化

Sangeeta 氏は、次の数字を紹介しました。

| 項目 | 数字 |
| ---- | ---- |
| Microsoft がブロックしたフィッシングメール | 1 四半期で 83 億通（8.3 billion） |
| クリック率 | AI 生成のフィッシングは 54%、従来型は 12% |
| Evil Tokens の 1 年前と現在の比較 | 以前は 14 日かかっていたものが、1 時間強で可能に |
| Evil Tokens の到達ユーザー数 | 以前は 10 人に届いていたものが、数千人に |

Evil Tokens は、phishing-as-a-service のツールキットです。1 年の間隔を置いて同じ脅威活動を比較した数字だと説明されています。これらの傾向は今後も加速すると述べ、こうした攻撃への対処には組織にとって数十億（billions）規模のコストがかかり得る、とも触れています。また、AI はキャンペーン周辺の作業の自動化にも使え、準備から、アクセスを得て行動するまでの時間が縮まると説明されています。そのため防御側は、メッセージ、サインイン、アカウントの動きをすばやく結びつけて対応する必要がある、と述べています。

### 5.2 攻撃の 3 事例

Cristian 氏は、欺瞞がアクセスに変わる経路を 2 つに整理しました。1 つは、**人を説得して、自分自身でセッションを承認させる**経路です。もう 1 つは、**組織を説得して、攻撃者のペルソナを信頼させる**経路です。この 2 つを、3 つの独立した事例で追っています。

**(1) Evil Tokens：device code フィッシングの自動化**

本物の Microsoft のサインインページを使い、攻撃者が開始した要求を、被害者に承認させる手口です。流れは次のとおりです。

1. もっともらしいメッセージで、従業員にリンクを開く理由を与える
2. 攻撃者は、すでに device authorization の要求を開始している
3. 従業員は、本物の Microsoft のサインインページに認可コードを入力する
4. 認証と承認が完了し、攻撃者のクライアントが待っていた承認が通る
5. Microsoft は、付与された権限の範囲で、要求元のクライアント（攻撃者）にトークンを返す
6. ツールキットは、デバイス登録も試みる場合がある（テナントのコントロールに左右される）
7. メールボックスにアクセスできれば、会話や業務の文脈を読み取れ、次のフィッシングに使える

ポイントは、「重要だったのは、攻撃者が始めた要求を承認する動作だった」ことです。サインインページには「このコードは、アプリやデバイスがあなたのアカウントにアクセスすることを許可する」という趣旨の文言があり、次に確認すべきは「そのコードがどこから来たか、どの要求を承認しようとしているか」だと述べています。例では、従業員は業務文書を開くつもりでしたが、コードは攻撃者の要求を承認していました。「クリックは終点ではなく、さらなる悪用への入口だった」とまとめています。

**(2) Octo Tempest：アカウント復旧の悪用**

Octo Tempest は、金銭目的のサイバー犯罪グループで、Scattered Spider としても知られている（トランスクリプトの表記は「scatter spider」）と説明されました。従業員になりすまして、ヘルプデスクにアクセスの復旧を頼みます。

1. 攻撃者が、信じてもらえる従業員のペルソナを作る
2. 「アクセスできなくなって、戻るのを手伝ってほしい」とサポートに電話する
3. ヘルプデスクを説得して、パスワードのリセットや認証方法の変更をさせる
4. 既存の権限を持つアカウントへの経路を得て、侵入の拡大、データ窃取、恐喝につなげる

つまり、アカウント復旧は「アクセスの判断」になっており、組織には、正当な本人を助けているというより強い証拠が必要だ、という整理です。

**(3) Jasper Sleet：採用とオンボーディングの悪用**

Jasper Sleet は、北朝鮮と関連する脅威アクターで、同国のリモート IT ワーカー・プログラムに結びつけられると説明されました。

1. 盗んだ身元を使って、応募者のペルソナを作る
2. 応募資料や面接で、そのストーリーを維持する。この活動では、声を変えるソフトウェアも Microsoft により観測されている
3. 採用プロセスが応募者を受け入れ、書類を承認する
4. 組織が新入社員として本物のアカウントを作成し、会社のデータやシステムへのアクセスが開く

「通常のプロセスを通じて、偽の身元を示した相手に、資格情報が発行された」ことが問題で、身元確認は採用・オンボーディングの早い段階で必要だと述べています。同じ写真が別のペルソナで使われた、公開済みの例も示されました。Octo Tempest は「組織にアクセスの復旧を求める」、Jasper Sleet は「アクセスの発行を求める」。どちらも慎重な検証に値する、というのが Cristian 氏の締めです。

### 5.3 Defender による検出と保護

ここからは防御です。まず「コミュニケーション」に対して、Defender がやりとりを認識して遮断し、アナリストの調査を証拠で支える、と説明されました。公開されている Evil Tokens のメールを例に、次の機能が挙がっています。

- 送信者のなりすましチェックと、メッセージの分析
- リンクは別途精査され、クリック時にも悪意ある URL のチェックを行う
- 配信後に新しい証拠が出れば、保護が再評価し、悪意のあるメッセージを削除できる
- アナリストは関連する活動を調査し、侵害されたアカウントに対応できる

> 注意：発表では「結果は、構成と利用できる証拠に依存する」と明言されています。

**Teams の通話：合成音声（synthetic speech）の検出**

通話には、メディアのリスクシグナルという別の層が加わります。発表では、limited preview の例として、Teams が合成音声の疑いを示し、検出プロバイダーとして Microsoft を表示する画面を紹介しました。警告は会話が行われている場所に出るため、主催者は、機密情報の共有や要求の承認の前に、いったん立ち止まれます。

聞き覚えのある声は説得力がありますが、この機能は主催者にメディアに関する追加の証拠を与えるものです。相手の本人確認は別途必要で、主催者は機密の共有を止め、状況を評価し、必要なら参加者を退出させることができます。これらは主催者が行う判断です。カメラによる確認は文脈を足せますが、本人確認にはより強い証拠が必要だと述べています。

### 5.4 Passkey

Sangeeta 氏は、予防の戦略を 2 本柱で説明しました。1 本目の passkey は、認証経路を守り、トークン窃取やフィッシングを防ぎます。2 本目の Verified ID は、資格情報のライフサイクルの各段階（新入社員のオンボーディング、継続的なアクセスと資格情報の管理、アカウント復旧）で、本人が本人であることを確立します。これにより、正当な本人が passkey を受け取り、提示するようになり、**Verified ID に裏づけられた高保証の資格情報**になります。

passkey について、Microsoft 365 や OneDrive などの消費者向けアプリで数億人が使ってきた経験から、次の数字が語られました。

- 従来の MFA 要素より **14 倍速い**
- サインイン成功率は passkey が **95%**、パスワードは 30%
- Entra での passkey 利用は 100% 増。synced passkey だけで四半期ごとに 1,000% の勢いで増えており、Entra のユーザーの 75% が synced passkey を登録している

登録の体験は、10 億人超の消費者ユーザーでの実験を踏まえて設計されたものだと説明されています。組織での展開を楽にする機能として、次が挙げられました。

- **registration campaign**：次回サインイン時に、passkey の登録を促す（ナッジする）。ユーザーはアカウント管理ページに移動しなくてよく、督促を繰り返し送る必要もない
- 既定で passkey を使う体験：passkey を登録したら、認証で passkey が既定になる。登録しても、フィッシング可能な資格情報を使い続けていては意味がないため
- agentic workflow による移行支援（6 章で説明）

### 5.5 Verified ID

Entra は、Entra ID Protection や Defender などのシグナルから、追加の検証が必要な場面を判断します。そうした重要な場面（特権操作など）で、**Verified ID** を使います。Verified ID は、パスポートや運転免許証のような政府発行の文書と生体認証で、ユーザーの身元を検証します。NIST の ID プルーフィングのガイダンスに沿ったものと説明されています。

組織は、どの種類の Verified ID を受け入れるかを管理します。Microsoft Security Store を通じて管理者が構成する、信頼できる ID 検証プロバイダーを使うことも、従業員に発行する独自の（custom）Verified ID を使うこともできます。アプリ側も、重要な場面で本人確認を要求できます。例として、デモの機密 Teams 会議のほか、高額な取引の承認前が挙げられました。

passkey と Verified ID を合わせて使うと、Verified ID による確認の後に登録された passkey は **高保証の資格情報**として印が付けられ、いつ・どのように ID 検証が行われたかも追跡されます。時間をかけて、Verified ID に裏づけられていない passkey などの資格情報を整理し、各段階で高保証の検証済み資格情報だけを使わせる運用に移せる、と説明されています。発表の最後の方では、これらの機能は **public preview** で、試してフィードバックがほしいと述べています。

### 5.6 SOC と ID 管理者の協働と、持ち帰る 5 つのアクション

発表は、「通信を守る」「認証を強くする」「アクセスを付与・復旧・拡大する意思決定で本人を確認する」の 3 つをまとめました。これには SOC と ID 管理者の両方が必要で、Defender はセキュリティ上の証拠を調査に持ち込み、Entra は構成されたアクセスポリシーと検証要件を適用します。この協働を運用モデルの一部にしてほしい、と述べています。

持ち帰る 5 つのアクションは次のとおりです。

1. Defender でメールとコラボレーションのセキュリティを強化する
2. Teams の合成メディア検出に備える（認定パートナーの製品、または利用可能になった時点でネイティブの音声検出を使う）
3. passkey を展開し、テスト済みのポリシーで passkey のみの認証を強制する
4. フィッシング可能な資格情報を、復旧と緊急アクセスの手段を用意したうえで、管理された移行により廃止する
5. 資格情報のライフサイクル全体（オンボーディング、機密アクセス、新しい資格情報、復旧）で Verified ID を使う

プレビューの機能は、限定した範囲で試し、SOC と ID のチームでそのうち 1 つの journey を選んで、オーナーを決め、次のステップに合意してほしいとも述べています。

### 5.7 Q&A

最後に会場から 5 件の質問があり、要点は次のとおりです。

1. **Verified ID の課金**：複数の顧客が、従量課金（usage-based）であることから導入に慎重だという。定額にする動きはあるのか。回答は、適切なモデルを決めるために調査・検討を重ねているところで、フィードバックはありがたい、というものでした。
2. **ハイブリッド環境**：ハイブリッド環境でもここまでの話は有効か、何を考慮すべきかという質問でした。質問者は、自社ではオンプレミスで構築したものを外に出していると話しています。回答は音声が不明瞭ですが、クラウドアカウントの話だという趣旨に聞こえます。発表では、それ以上の説明はありません。
3. **MSP の passkey**：クライアントごとのテナントに、エンジニア（例として 10 人）が管理者としてアクセスしており、現在は CRM システムに保存した global admin の資格情報と、ソフトウェアトークンの MFA を使っている。passkey はどう使えるのかという質問でした。登壇者は、passkey はドメインに紐づく（domain-bound）ため、同じ事業体のテナントでない限り、ドメインごとに別の passkey が必要だと説明しました。それがフィッシング耐性の理由でもあります。なお「なぜ global admin をスマホに入れる必要があるのか」という趣旨の疑問も出され、詳しい議論は後でとなりました。
4. **UPN の露出と大量のサインイン試行**：ユーザーのプリンシパル名（UPN）が「イニシャル＋姓」の形式のため、公開情報から推測され、短時間に何千回もの試行を受けるアカウントが見える。UPN を隠す方法はあるか、という質問でした。質問者は、以前 MFA 環境でアカウントが数日間侵害されていた経験から、passkey もいつか破られないかを心配していました。登壇者の一人は「passkey を使っていれば、リモートからのフィッシングは不可能だ」と述べました。UPN を隠す方法については、技術的な内容のため、会の後に連絡を取って整理しよう、という対応で、発表では回答されていません。
5. **Bluetooth が無いデスクトップ**：Windows サインインにも passwordless を使っているが、Bluetooth の無いデスクトップが数百台ある。回避策はあるかという質問でした。回答は、「passkey は Bluetooth がないと使えず、回避策はない。それがセキュリティだ」というものです。Bluetooth ドングルを使った顧客もいる、と補足されましたが、質問者は、PC を置き換えて減らしていく方針だと述べています。

## 6. デモ・手順

このセッションには、複数のデモがあります（Defender の調査は、録画したものを見せる形だと述べられています）。画面の細部は音声からは確認できないため、語られた範囲のみを書きます。

### 6.1 Defender での合成メディアの調査（Cristian 氏）

発表者は「この調査を Microsoft Defender で録画してある」と述べて、証拠を追いました。

1. Defender のホームから、アラートキューを開く
2. 「synthetic AV」の検出を探す。見つけたアラートは、このデモ用に構成した **カスタム検出ルール**が出したもので、合成メディアのシグナルを表面化させている
3. 2 つのアカウントレコードが、調査の出発点の文脈になる
4. アラートに戻り、関連する通話アクティビティを開く。そこで、シグナルを通話に結びつけるレコードと、一致したイベントを確認する
5. そのイベントの元になったクエリを見る。「synthetic media detection events」テーブルには、Teams のディープフェイク検出イベントの詳細が入っている。クエリはその場で実行することも、Advanced Hunting で開いて実行することもできる
6. 同じ通話・検出 ID を共有する 3 件の参加者の行が見つかる。これは通話の文脈になる（調査を広げるには、追加のクエリが必要）
7. イベントに関連するアカウントは、調査の起点になる。ただし、誰が話していたのか、アカウントが侵害されていたのかは、まだ確定していない。次の段階は、範囲を絞った調査と、適切な対応

### 6.2 Passkey の登録と、既定での利用（Sangeeta 氏）

1. Entra で、ユーザーが passkey の登録を開始する。顔の提示を求められ、passkey を保存する。登録は以上
2. 別のデモ：ユーザーが新しいデバイスを手に入れる。このデバイスでは一度もサインインしていないが、同期された（synced）passkey がすでに届いている。ユーザーはユーザー名を入力し、passkey を使ってサインインする。認証方法の一覧から選ぶ必要はない

### 6.3 passkey 専用認証への移行を支援するエージェント（Sangeeta 氏）

フィッシング可能な資格情報を残したままでは意味がないため、passkey のみの認証へ移行する手順を助ける agentic workflow が紹介されました。プレイブックの名前は「Reduce credential phishing risk」と聞こえます（音声認識の都合で、前後の語は確定できません）。

1. エージェントとのセッションを開始すると、組織内の高い権限を持つユーザーのうち、フィッシング可能な資格情報を使い続けているユーザーを、組織全体でスキャンする
2. ユーザーごとに、passkey の採用状況を詳しく示す（passkey を登録済みか、適切なデバイスを持っているか）。新しいデバイスを配るべきかの計画に使える
3. 自分が締め出されないように、break glass アカウントを選ぶ
4. 準備ができているユーザーに対して、passkey のみの認証を強制する条件付きアクセスポリシーを、エージェントが作成する。最初は report-only モードで、適用する前に影響を把握できる
5. 各ステップで人間が制御する。エージェントが作成したポリシーは、確認して必要なら編集する

### 6.4 リスクのあるサインインでの Verified ID

1. 管理者が、高リスクのユーザーに対して、リスクを解消するために Verified ID による本人確認を求める条件付きアクセスポリシーを作成し、保存する
2. ユーザーがサインインする。未知のデバイス、見慣れない場所からで、少し怪しいため、追加の ID 検証を求められる
3. ユーザーは、モバイルデバイスの Microsoft Authenticator アプリにある Verified ID を提示する
4. 顔のチェックで、その Verified ID の正当な所有者であることを示す
5. Entra が裏で追加の検証を行い、問題なければアプリへ進める
6. 管理者には、リスクのあるサインインが発生し、解消されたというレポートが届く

### 6.5 機密 Teams 会議への参加時の Verified ID

1. 機密の Teams 会議で、主催者が、参加者に事前の ID 検証を求める
2. 参加しようとしたユーザーに、ID 検証が促される
3. ユーザーは、モバイルの Microsoft Authenticator にある Verified ID を提示する
4. 顔のチェックで、同じ人（正当な本人）が提示したことを確認する
5. 問題なければ、会議に参加できる

### 6.6 高保証のアカウント復旧（デバイス紛失時）

synced passkey があれば、新しいデバイスに passkey が現れるだけで済みます。デバイスに紐づいた（device-bound）passkey しか無い場合、従来はヘルプデスクへの電話になり、Octo Tempest のような手口につながり得ました。デモは、これを自力で復旧する流れです。

1. サインインできないユーザーが、アカウント復旧を開始する
2. 管理者が設定した、信頼できる ID 検証プロバイダーにリダイレクトされる。ここでは「IDMIA」と聞こえます（音声認識の都合で表記が確定できません）
3. 運転免許証を選び、表と裏をスキャンする
4. 顔のチェックで、免許証の正当な所有者であることを示す
5. Entra が追加の検証を行い、正当な本人が Verified ID を提示したことを確認する
6. 完了後、最初の passkey の登録を促される
7. ユーザーは復帰し、フィッシングに強い状態のまま。「電話で相手の言葉を信じる必要はなかった」と説明されています

### 6.7 オンボーディングでの Verified ID

管理者は、ID Governance の lifecycle workflows で 2 つのタスクを設定します。入社前（pre-hire）のタスクは、初日より前に ID の検証を求めます。新入社員（new hire）のタスクは、初日に、資格情報を渡す前に、その ID の提示を求めます。受け入れる Verified ID の種類は、管理者が選べます。

1. 入社前のユーザーが、初日の前に Verified ID を取得するよう求められる
2. 管理者が構成した信頼できる ID 検証プロバイダーに誘導される（ここでも「IDMEA」と聞こえます。前出と同じものと思われますが、確定できません）
3. 運転免許証の表裏をスキャンし、顔のチェックを行う
4. 検証済みの資格情報が、モバイルの Authenticator アプリに保存される
5. 初日に、ユーザーがその Verified ID を提示する。Entra が顔のチェックなど追加の検証をして、正当なユーザーが提示したことを確認する
6. ユーザーは、最初の passkey を登録できる

フィッシング可能な資格情報を許可しなければ、このアカウントは「フィッシングに強い方法で」立ち上げられます。条件付きアクセスポリシーで、どの資格情報の登録の前にも本人確認を求めることもできます（このパターンはデモではなく、画面の紹介のみ）。目的は、正当なユーザーだけが資格情報を登録できるようにし、攻撃者が自分の資格情報を登録してアカウントを乗っ取るのを防ぐことです。

## 7. 注意点・発表者の気付き

- Defender の保護や調査の結果は、構成と利用できる証拠に左右されます。
- Teams の合成音声の警告は、あくまで追加の証拠です。相手の本人確認が別途必要で、対応（共有を止める、参加者を退出させる）は主催者が判断します。カメラの確認も、本人確認としては弱い、という説明でした。
- passkey は、登録しても、フィッシング可能な資格情報が使える状態では効果がありません。そのため既定で passkey を使う設計にし、さらに passkey のみの認証を強制する流れを紹介しています。
- passkey のみの強制の前に、break glass アカウントを選び、report-only モードで影響を確認します。持ち帰り項目でも、「復旧と緊急アクセスを用意した、管理された移行」と述べています。
- passkey はドメインに紐づくため、複数テナントを扱う MSP などでは、テナントごとに別の passkey が必要になります（Q&A）。
- passkey は Bluetooth が無い PC では使えず、回避策は無い、という回答がありました（Q&A）。
- Verified ID は従量課金で、顧客の中には導入に慎重な声があります。料金モデルは検討中と回答されています（Q&A）。
- ここで紹介された passkey と Verified ID を組み合わせた機能は public preview です。Teams の合成音声検出は limited preview の例として紹介されています。

## 8. 利用者にとっての利点

- **攻撃の速度と規模に対抗できる**：Defender の事前・事後（クリック時、配信後の再評価）の保護と、調査の仕組み
- **ヘルプデスクを経由する乗っ取りの対策**：Verified ID を使った高保証のアカウント復旧では、ユーザーが自力で復旧でき、電話で相手の言葉を信じる必要がなくなる
- **不正な採用・オンボーディングの対策**：入社前と初日の ID 検証で、正当な本人にだけ最初の passkey を渡せる
- **サインインが速く、成功しやすい**：passkey は従来の MFA 要素より 14 倍速く、成功率は 95%（パスワードは 30%）
- **展開の手間を減らせる**：registration campaign、既定の passkey 体験、移行を支援するエージェント
- **資格情報の質を管理できる**：Verified ID の後に登録した passkey を高保証として追跡し、そうでない資格情報を整理できる

発表では、特定の顧客名や導入事例は紹介されていません。

## 9. まとめ

フィッシングの本質は「クリックの後」にある、というのがこのセッションの主張です。AI により攻撃は速く大規模になり、Evil Tokens の device code フィッシング、Octo Tempest のヘルプデスク悪用、Jasper Sleet の採用悪用は、いずれも「欺瞞を信頼されたアクセスに変える」手口でした。

防御側は、Defender でメッセージや通話を検出・調査し、Entra の passkey で認証経路を守り、Verified ID でアクセスを与える・復旧する・拡大する場面の本人確認を行います。この 2 つを SOC と ID 管理者が協力して運用するのが、発表者の提案です。まずは、5 つのアクションのうち 1 つの journey を選び、オーナーを決めて、プレビュー機能を限定した範囲で試すことが勧められています。
