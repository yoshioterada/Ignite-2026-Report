# THR969 Building security skills through hands-on learning

## 1. はじめに

このセッションは、シミュレーション形式の体験学習を通して、セキュリティの判断力を身につける方法を紹介する約 25 分のシアターセッションです。内容の大半は、架空の企業のカスタマーポータルと AI サポートエージェントを題材にした、**攻撃から調査、修正までを一続きで体験するシミュレーション**の実演です。

流れは次のとおりです。まず顧客として AI サポートエージェントを使い、異常に気づきます。次に、役割を切り替えて攻撃者側の立場から、自動化された red team agent による攻撃を見ます。最後に Microsoft Defender で、攻撃の原因となったコードの脆弱性を調べ、GitHub への pull request として修正を作成します。体験は、AI Skills Navigator で学べる形で提供されているという案内です。

## 3. 何に関する発表か

テーマは、「概念を練習するのではなく、セキュリティ上の判断が何を意味するのかを理解する」ためのハンズオンのシミュレーションです。Cami 氏は、アナリストや管理者に「どう学ぶのが好きか」と尋ねると、ほとんどが「ハンズオン」と答える、という話から入っています。

アジェンダは次のとおりです。

1. 架空の会社のカスタマーポータルと AI サポートエージェントが、一見正常に動いていることを確認する
2. その前提を疑い、制御された攻撃を追って、セキュリティ境界が破られると何が起こるかを見る
3. Microsoft Defender で、修復の手順を見る。開発者のワークフローで脆弱性にパッチを当てる方法を、製品の中で確認する
4. AI Skills Navigator で、この体験を学べる QR コードを案内する

## 4. 発表者が伝えたいメッセージ

発表の中心は、「AI エージェントを含むアプリケーションの脆弱性は、従来のパターンマッチング型の解析ツールでは見逃されがちで、その攻撃を防ぎ、見つけて、修正するには、エージェント型の仕組みが必要になる」という見方です。そのうえで、攻撃の影響の確認から、Defender での調査、GitHub での修正の提案までを、**短いシミュレーションの中で一続きに体験できる**ことを示しています。

もう一つの点は、学習の形です。実際の攻撃のシナリオを低リスクの環境で繰り返し練習し、「何をすべきか」だけでなく「なぜそれが重要か」を理解する、というのがこのセッションの狙いです（セッション概要の趣旨）。

## 5. 発表内容の詳細

### 5.1 シミュレーションの舞台：Caldoba

題材は、架空の薬局の配送サービス会社です。会社名は音声認識で「Caldoba」「Caldova」と揺れており、表記は確定できません。この会社には、とてもシンプルな加盟店（merchant）向けポータルと、AI サポートエージェントがあります。いずれも、一見すると正常に動いています。

- 加盟店のオーナーとしてポータルにログインすると、施設（facility）が「open」で、アプリケーションは稼働中であると表示される。
- 未処理の注文は 3 件ある。最初の注文を開くと、詳細は正しく見える。金額は 18.50 ドルで、施設は open と表示される。
- 顧客がサポートエージェントとチャットできる。エージェントは、注文について質問に答え、認可されている場合は注文の照会（order lookup）などのツールを呼び出し、返金（refund）も実行できる。

### 5.2 異常の発見：別の顧客の注文が返ってくる

顧客として、見えている顧客の名前は「North Loop」です。この文脈で、エージェントに注文について質問すると、注文のステータスが返ってきます。自然言語のサポートが、業務ツールに支えられている、というあるべき体験です。

ところが、エージェントは「Riverfront」という**別の顧客**の支払い済みの注文を返しました。画面上の顧客は North Loop のままです。ここから、通常とは違うパターンが見え始めます。

### 5.3 役割を切り替えて攻撃を体験する

シミュレーションでは、役割を切り替えて、セキュリティアナリストの立場から、この見かけ上の失敗がどこまで広がるかを確かめます。顧客としてアプリを使う代わりに、**自動化された red team agent** を呼び出して攻撃を実行します。

発表では、red team agent を、「攻撃者のように動く、AI を使ったセキュリティテスター」と説明しています。アプリケーションを探索し、安全策を迂回できないかを試して、攻撃者が何にアクセスし、何を変更できるかの証拠を集めます。

このシナリオで、red team agent は次の状態から始まります。

- ユーザー名なし
- パスワードなし
- merchant ID も customer ID もなし

URL だけを渡すと、agent は公開されている攻撃対象領域全体を探索し、アプリケーションの制御が持ちこたえるかを試します。シミュレーションで攻撃を実行すると、次のことが分かります。

1. アプリケーションが公開している識別子を見つける。
2. それらを連鎖させて、特権的な操作につなげようとする。
3. 結果として、サインインなしで施設のステータスを「opened」から「paused」に変えられることを突き止める。

ポータルを確認すると、施設は paused になっており、未処理の注文は 3 件のままです。施設のエンドポイントが、誰が要求しているかを確認していなかったため、red team agent はサインインなしで施設を停止できました。サーバー側の認証も認可もなく、状態の変更を受け付けていた、という説明です。

さらに、**identity trust の失敗**によって、ある顧客が別の顧客として振る舞うことができ、**不正な金融取引**も発行されました（補足：5.1 のとおり、エージェントは認可されている場合に返金を実行できるツールを持っています。ただし、発表では「不正な金融取引」とだけ語られ、具体的な内容までは説明されていません）。つまり、このシナリオでは、2 つの問題が同時に起きていました。

### 5.4 なぜ見逃されるのか

こうした脆弱性は、典型的なパターンマッチング型の解析ツールが見逃しやすいコードの問題であり、ここでは複数の問題が**連鎖**して攻撃が成立していました。組織には、セキュリティ制御と、保護のためのエージェント型のシステムが必要で、攻撃を防ぎ、特定し、修正まで行う必要がある、と説明されています。

シミュレーションでは、Microsoft Defender に含まれる、**エージェント型のコードスキャンのシステム**として、コードネーム **MDash**（「M-dash」「Code name M dash」とも聞こえます。名称は音声認識の都合で表記が確定できません）が紹介されました。

### 5.5 Microsoft Defender でのコードスキャン

画面操作の流れは 6 章にまとめ、ここでは説明された内容を整理します。

- Microsoft Defender の **Exposure Management** の **Initiatives** から、MDash（エージェント型のセキュリティ）にアクセスできる。
- Defender は、**GitHub と Azure DevOps** の両方から、ソースコードの組織をオンボードできる。既存のリポジトリを、ソースコードの置き場所も開発者の作業場所も変えずに、1 つのセキュリティプログラムのもとに取り込める。
- リポジトリを接続すると、スキャン結果は Exposure Management に集約される。これにより、セキュリティチームは、バラバラのスキャナの出力を寄せ集めたダッシュボードではなく、**プログラムレベルの視点**を得られる。
- Initiatives のページで、すべてのリポジトリと検出事項（findings）の概要、リポジトリのカバレッジを確認できる。リポジトリごとの推奨事項、深刻度での絞り込み、時間の経過に伴う**傾向（trends）**も見られる。傾向は、リスクが減っているのか、あるいは毎週、再発見されているだけなのかを示すため、重要だと説明されています。

### 5.6 検出事項の内容

今回のシナリオで、チャットボットのサービスのリポジトリを選ぶと、このスキャンで**5 件の検出事項**があることが分かります。深刻度は高、中、低で分かれます。最も重大な検出事項を開いて、証拠を調べます。

- この検出事項は、信頼できない顧客のデータが、サポートページの HTML に流れ込む経路を追跡している。
- スキャンの説明は具体的で、「顧客の principal が、攻撃者が制御するプロンプトによって、認可の前に再バインドされる」という内容。これは単なる構文エラーではなく、**信頼境界が破られているビジネスロジックの問題**だと説明されています。
- 検証の要素では、リクエストが customer「north」として始まったのに、プロンプトが customer「riverfront」を指定していて、ツールの呼び出しが別の顧客の支払い済みの注文に到達していることが示される。これは、先ほどのシミュレーションで見た、顧客をまたぐシナリオと一致する。
- 証拠として、攻撃者が制御する入力が、チャット経由で HTML を通って、サポートページに到達する状況が示される。ページがこれをテキストではなく**コード**として扱うと、ブラウザーで直接実行され得る、という説明です。

### 5.7 修正の提案と pull request

ツールは、修復の手順と修正案を示します。修正の内容は次のとおりです。

1. プロンプトやリクエストで渡された customer ID を使わず、**検証済みの資格情報を信頼する**。
2. 操作を行う前に、注文照会ツールと返金ツールの**両方で、注文の所有権を確認する**。
3. 施設を open から paused に変更する操作では、**加盟店のサインインを必須**にし、その施設が、その加盟店のものであることを確認する。

Defender から、この修正を **pull request** として作成できます。開発者には、脆弱なファイル、証拠、提案された変更が、**開発者が実際に作業しているワークフローの中**に届きます。シミュレーションでは、GitHub に pull request を作成しました。

## 6. デモ・手順

このセッションには、シミュレーションの実演があります。Felipe 氏が画面を見せながら説明しており、画面の細部（ボタン名など）は音声からは確認できません。以下は、語られた順の流れです。

**パート 1：架空の会社のポータルとエージェント（顧客・加盟店の視点）**

1. 加盟店のオーナーとして、ポータルにログインする。施設が open で、アプリケーションが稼働中、未処理の注文が 3 件と表示される。
2. 最初の注文を開き、詳細を確認する（18.50 ドル、施設は open）。
3. 顧客として、サポートエージェントに、注文について質問する。顧客名は North Loop。ステータスが返ってくる。
4. エージェントが、Riverfront という別の顧客の支払い済みの注文を返したことに気づく。

**パート 2：役割を切り替えて攻撃を実行（セキュリティアナリストの視点）**

5. 役割を切り替え、自動化された red team agent を呼び出す。
6. ユーザー名、パスワード、merchant ID、customer ID なしで、URL だけを渡して攻撃を実行する。
7. agent が識別子を見つけ、特権的な操作に連鎖させる。サインインなしで、施設の状態を opened から paused に変えられたことが分かる。
8. ポータルを見て、施設が paused になっていることを確認する（未処理の注文は 3 件のまま）。

**パート 3：Microsoft Defender での調査と修正**

9. Microsoft Defender で Exposure Management を選び、Initiatives から MDash（エージェント型のコードスキャン）にアクセスする。
10. 概要で、すべてのリポジトリ、検出事項、カバレッジを見る。スキャン結果を、先ほど見たエージェント型チャットボットの 1 つのリポジトリに絞り込む。
11. 深刻度での絞り込みや、時間の傾向を確認する。
12. チャットボットのサービスのリポジトリを選ぶと、5 件の検出事項が表示される。最も重大なものを選び、証拠と検証の内容を確認する。
13. 修復の手順（修正案）を確認する。
14. 修正を pull request として GitHub に作成する。深刻度の画面に戻り、生成された pull request を、そこから GitHub へたどれる。発表では、開発者が、この提案された修正をレビューし、テストしてから承認する、と説明されています。

発表では、この流れを「攻撃者が施設に与えた影響を見るところから、調査、Defender での証拠の確認、GitHub での修復手順の作成まで」の、短いシミュレーションだったと総括しています。

## 7. 注意点・発表者の気付き

- 見た目には正常に動いている AI サポートエージェントが、**別の顧客のデータを返していました**。この発表では、これが調査の出発点です。
- 問題の本質は、構文のミスではなく、**信頼境界の失敗（ビジネスロジックの問題）**です。プロンプトで渡された顧客 ID を、認可の前に信用したことが原因として示されました。
- 複数の問題が**連鎖**して攻撃が成立しており、パターンマッチング型のツールでは見逃されやすい、と説明されています。
- 検出事項の**傾向**を見て、リスクが実際に減っているのか、毎週再発見されているだけなのかを判断することが重要、と語られています。
- 修正は pull request として提案され、開発者がレビューとテストを行ってから承認する、という流れで説明されました。
