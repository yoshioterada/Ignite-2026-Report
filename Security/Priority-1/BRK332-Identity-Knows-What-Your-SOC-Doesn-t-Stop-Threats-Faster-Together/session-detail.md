# BRK332 Identity Knows What Your SOC Doesn’t: Stop Threats Faster Together

## 1. はじめに

このセッションは、ID を管理するチーム（IAM / ID 管理者）と、脅威の検知・対応を担うチーム（SOC / セキュリティ担当）が、攻撃に対してどう連携すべきかを扱った 45 分のブレークアウトです。Microsoft Entra と Microsoft Defender が、ID のコンテキストやリスクシグナルをお互いにやり取りしながら、1 つのシステムとして動く様子が紹介されました。

内容は、スライドによる考え方の説明と、4 本のデモで構成されています。デモでは、オンプレミスから始まるハイブリッド ID 攻撃（デモ A）、AI エージェントのリスク評価（デモ B）、デバイスコードフローを悪用してユーザーとエージェントの信頼関係を突く攻撃（デモ C）、攻撃経路を閉じる Perception のプレイブック（デモ D）が示されました。

発表の結論は 1 つにまとまっています。**ID セキュリティはチームスポーツであり、ID 側とセキュリティ側の間に手作業の引き継ぎを挟まず、コンテキストを自動でつなげることが勝負どころ**という考えです。

## 4. 発表者が伝えたいメッセージ

### 4.1 ID は攻撃の最初の足がかりである

Yair 氏は、攻撃はオンプレミスのユーザーから始まってアプリケーション、クラウドワークロード、機密データへと進むことがあり、攻撃者は組織図を気にしないと説明しています。Microsoft は 12 のコア脅威シナリオを追跡しており、そのすべての中心に ID があるそうです。盗まれたトークン、悪用されたアプリケーション、侵害されたサービスプリンシパル、操作された AI エージェントなど、見た目は別のチームや別のシステムの話でも、突き詰めると ID が関わっています。ID は侵入の入口であり、横展開の手段であり、最終目標に届くまでの道筋でもある、という整理です。

### 4.2 ID と SOC は 1 つのシステムとして動くべき

他社の組み合わせでも、ID プロバイダーと脅威検知・対応ベンダーはそれぞれ優れているかもしれませんが、両者は別のシステムなので連携ポイントが残り、シグナルの受け渡しに時間がかかる、というのが Yair 氏の見方です。その時間こそ攻撃者が突く部分だと述べ、Microsoft は ID の経路全体を 1 つのシステムとして提供しているのが違いだと位置づけています。

### 4.3 人が判断する余地を残したまま、引き継ぎの遅延を減らす

ID チームが見つけたポスチャ（態勢）のギャップが SOC に伝わらない、SOC が調べている実際の攻撃の内容が ID 側の強化に反映されない、といったことが手作業の引き継ぎでは起こります。これに対して Microsoft は、各ジョブの間に自動化と目的特化型のエージェントを入れたと説明しています。ただし、ユーザー（人）を外すものではなく、承認は必要だとも強調しています。

## 5. 発表内容の詳細

### 5.1 冒頭の問題提起

冒頭で Yair 氏は、会場で ID 側の人と SOC 側の人に挙手を求めました。両方いることが確認でき、これがまさに論点だと述べています。攻撃者は AI で攻撃を拡大し、アクセスを担うチームと脅威の検知・対応を担うチームの間にある隙間を突いてくる、そのうえ、シグナルを統合して全体像をつかむための時間も短くなっている、という認識です。

### 5.2 ID セキュリティの 3 つの柱

Microsoft は ID セキュリティを、同等に重要な 3 つの柱で定義していると説明されました。

| 柱 | 内容（発表での説明） |
| ---- | ---- |
| ID インフラストラクチャ | ID が作成され、認証され、ガバナンスされ、コンテキストの中で理解される場所 |
| ID コントロールプレーン | ID のコンテキストをリアルタイムのアクセス判断として反映する場所。サインイン時だけでなく、サインイン後に条件が変わったときにも判断する |
| 脅威の検知と対応 | 最初の 2 つの柱がどれだけ優れていても攻撃者は侵入してくるという前提で、できるだけ早く捕捉し、今の動きだけでなく次の一手を見越して対応する |

これらは 1 つのシステムとして連動する必要があり、人間・非人間・エージェントのすべての ID を、あらゆる接点（surface）にわたってカバーしなければならないとされています。

#### ID インフラストラクチャ

ID の種類と環境の組み合わせで ID は大量になるため、Entra のネイティブな範囲だけでなく、全体を見渡せる可視性が必要になります。そのために、統合された ID インベントリ（unified identity inventory）があり、人間のユーザーでは実現済みで、エージェントや非人間の ID にも広げる取り組みを進めていると説明されました。これがすべての基盤であり、可視性が出発点です。

#### ID コントロールプレーン

2 つ目の柱の中心は Conditional Access と Continuous Access Evaluation（継続的アクセス評価）です。複数の条件を考慮してアクセスを判断します。ここで新しい要素として、"last June" に GA したと説明された統合リスク（**Unified user risk**）が挙げられました。Defender と Entra にまたがって環境全体を見てリスクを計算する仕組みです。

> 補足：この箇所の発言は "unified agent risk" と聞こえますが、後半で Yair 氏が「6 月にリリースした unified user risk」と言及しているため、本書では Unified user risk と表記します。音声認識の都合で表記が確定できません。

Yair 氏は、リスクの変化や認証中の出来事にリアルタイムで対応できるのは ID プロバイダーだけだと述べています。他のシステムは API やログを取り込む形になるため、同じことはできないという主張です。

#### 脅威の検知と対応

Defender の脅威検知と対応は 2 つの部分に分けて紹介されました。

1. **統合された可視性**：互いに無関係に見える多数のアラートを、攻撃者が何をしようとしていて、次に何をしそうかが分かる「インシデント」という全体像にまとめます。この理解はポスチャやエクスポージャにも反映されます。なお、デモの中で Martin 氏は、このインシデントを現在「cases」という名称に変更中だと話しています。
2. **自律的な対応**：インシデントに対して、何を優先して見るべきかを示す agentic triage があります。攻撃である確度が非常に高いものには attack disruption（攻撃の遮断）が働き、SOC のアナリストが画面を開く頃には解決済みになっていることもあります。さらに predictive shielding は、今起きていることの解決だけでなく、次に起こりそうなステップの予防も行う機能だと説明されました。

### 5.3 3 つの Jobs to be done と自動化

顧客との会話では、ID を守るために行うことが 3 つに集約されると Yair 氏は述べています。

1. **ポスチャの改善・堅牢化**：通常は ID 管理者の仕事
2. **侵害の防止**：ID コントロールプレーンでリアルタイムに行う
3. **検知と対応**

重要なのは、この 3 つが互いに入力となり、精度を高め合う 1 つのシステムだという点です。従来であれば、ID チームが見つけたポスチャのギャップは SOC に伝わらず、SOC が調べている実際の攻撃は ID 側の強化につながりません。手作業の引き継ぎがあるため、2 つのチームが話し合うまで時間がかかるからです。Microsoft はこの間をすべて自動化し、ポスチャが防止や検知を支え、検知と対応の結果がポスチャの改善にフィードバックされる形にしたと述べています。各ジョブの接合部には、自動化と目的特化型のエージェントを追加しており、ユーザーの承認は引き続き必要です（その様子は最後のデモで示されました）。

### 5.4 デモ A の前提：ハイブリッド ID 攻撃のシナリオ

Martin 氏は、実際にデモする前に攻撃シナリオを説明しました。実際に観測された複数の攻撃を元にした内容で、セッションに収まるよう少し切り詰めてあるとのことです。攻撃は次のように進みます。

1. 攻撃者は、ドメイン内の権限を持たない通常のユーザーで、ある PC（発表では PC1 と仮称）にログインする
2. Kerberoasting を行う。サービスアカウントを狙う攻撃です
3. 特権ユーザーの資格情報またはアクセスを得て、ドメインコントローラーへ横展開する。ドメインコントローラーになりすまして、ドメインの資格情報や情報をすべてダンプする。これでドメイン全体を掌握し、組織内の任意のユーザーになりすませる
4. 管理者が所有するマシンに RDP でログインする。Martin 氏によると、実際に調査した事例では、数週間前から偵察（Recon）で組織内の管理者が誰かを調べていた
5. その管理者のマシンでブラウザーのクッキーをすべてダンプする。そのブラウザーには、グローバル管理者権限を持つ別ユーザーの資格情報も残っていた
6. 盗んだトークンをリプレイする。MFA を回避する最良の方法だと説明されています
7. さまざまな種類のデータ窃取を行い、さらにサービスプリンシパルにシークレットを追加して永続化する

ここでの教訓として、Martin 氏は、日常用のアカウントと管理用のアカウントを分けるというベストプラクティスに組織が従っていたのに、同じマシンに両方が現れたことで突破された、という点を挙げています。複数のアカウントを持つ ID 管理者はよく見かけるそうで、会場にも「アカウントを複数持っている人」を挙手で尋ねています。日常用の Martin アカウントと、管理用の Martin_admin のようなアカウントは、同じ人物のものです。

### 5.5 デモ A で示された Defender の機能

デモの手順は「6. デモ・手順」にまとめます。ここでは、デモの中で説明された機能の要点を整理します。

* **Case（旧称インシデント）**：個々のアラートを、共通の資産や時系列でつなげて 1 つのストーリーとして見せる。調査に役立つ
* **Attack disruption**：Defender が攻撃の深刻さを理解して即座に動く。SOC アナリストの調査開始、チケット起票、メール、ID 管理者への電話を待たない。デモでは、攻撃が続くよう、ユーザーを無効化する部分だけ意図的に止めてある
* **統合 ID インベントリ**：Active Directory、Entra、さらにサードパーティの SaaS アプリケーションなど、複数のシステムにまたがるアカウントを同じ ID に関連付ける。Martin 氏はこれを「Defender における ID セキュリティの頭脳と筋肉」と表現し、予防・調査・対応・ポスチャのすべてを支えると述べています
* **リスクスコア**：その人物に関するアラート、ポスチャの推奨事項などすべてを相関させ、さらに Entra のリスクレベルと、侵害された場合の被害範囲（blast radius）も加味して算出する
* **オペレーティングシステムとの近さ**：Defender が検知に使うシグナルの多くは、OS チームと協力して追加したテレメトリーやイベントによるもので、Kerberos、NTLM、RPC、LDAP などに変更を加えて、リアルタイムに近い情報を得ている。Martin 氏はこれを、IDP と XDR の両方であることによる「不公平なほどの強み」と表現しました

### 5.6 エージェントを守る：agentic insider と Dynamic agent risk

Yair 氏は、人間と非人間に加え、エージェントも保護対象に含める必要があるとして、"agentic insider" という言葉でエージェントの特性を紹介しました。

| 特性 | 説明 |
| ---- | ---- |
| Polymorphic（多形性） | 読み込んだ内容によって役割が変わりうる。例として、経費精算のエージェントが、読んだ指示によって送金のエージェントになってしまう |
| Result-driven | 結果を重視して動く |
| 機械の速度と規模 | 機械の速度とスケールで動作する |
| Collaborative | 協調して動く |
| 24 by 7 | 24 時間 7 日（常時）稼働する |

顧客からは、すべてを観測したい（observe）、エージェントができることを封じ込めたい（contain）、機械の速度で対応したい（respond）という声を一貫して聞くそうです。ユーザー向けに作ったものが基礎になりつつ、エージェントの特性に合わせた専用機能も必要とされます。すべてのエージェント、すべてのリソースに、常に、あらゆるレイヤーで適用されなければならないというのが前提です。

Microsoft Security は、AI エージェントを守り、ガバナンスするため、複数のレイヤーにまたがる一連の機能を構築しており、ID セキュリティの文脈では次の 2 つが紹介されました。

* **Dynamic agent risk**：ユーザー向けの Unified user risk（6 月にリリース）に相当する、エージェント向けの新しいリスクです。Microsoft Security の各製品から来る実行時（runtime）のシグナルと、blast radius、エクスポージャのシグナルを融合して、統一されたリスクを出します。公開プレビューは数週間後の予定で、「おそらく 12 月中旬」と述べられました。

* **Dynamic conditional access**：Dynamic agent risk のシグナルに基づいて動く仕組みで、現時点はプライベートプレビューです。パブリックプレビューは「おそらく 6 月、いや 1 月か 2 月」と言い直されています（発言のとおりの表現です）。Conditional Access が最初のアクチュエーター（作用する側）で、スタックの他の領域にも作用させると説明されています。できることとして、人間の確認（human in the loop）を求める、書き込みから読み取りへアクセスを減らす、アクセスをブロックする、が挙げられました。すべてのリクエストに対して動作し、ファーストパーティのゲートウェイ（Graph と、音声認識上 "walk IQ" と聞こえる製品。表記が確定できません）に統合されているほか、あらゆる宛先に対して Global Secure Access とも統合されています。

Yair 氏はこれを、シグナル、センサー、アクチュエーターという「新しいサイバースタック」の話として紹介し、コンテキストの層が Dynamic agent risk を計算すると説明しました。

### 5.7 Agent 365 でのエージェントのリスク（デモ B の背景）

エージェントのインベントリには、IT が作ったもの、ビジネス部門の管理者が作ったもの、ユーザーが自分のマシンで Claude や Copilot CLI を動かして作ったものなどがあり、すべてが IT に承認されているわけではない、と Martin 氏は指摘しました。デモでは、その中から未承認のエージェントを見ていきます。詳細は 6 章に示します。

デモで示されたリスクの構成要素は次の 3 つで、これらを合成して 1 つのスコアにします。

| 要素 | 説明（デモでの発言） |
| ---- | ---- |
| Blast radius | そのエージェントが侵害された場合の組織への影響。例：非常に高い権限の ID を使っている、価値の高い資産にアクセスできる |
| Exposure level | エージェントが使うツールや ID、利用を許されているユーザー数。ユーザー数が多いほど露出が増える。各指標には修正のための推奨事項もある |
| Runtime risk（Martin 氏の言う「緊急度」） | エージェントに対してアラートが発生したときに、リスクレベルを引き上げる |

### 5.8 デバイスコードフローによる信頼関係の悪用と、攻撃経路の閉鎖

Yair 氏は、攻撃者はグラフとして考える、つまり複数のエンティティ間のやり取りをたどる、と述べ、ここまでは「侵害されたユーザー」と「リスクが高くなったエージェント」を見たので、次は「ユーザーとそのエージェントの間の信頼が悪用されて両方が侵害される」場合を見ると紹介しました（デモ C。内容は 6 章を参照）。

続いて、Yair 氏は Defender の対応だけでは問題の半分だという話をしました。根本の原因が解消されなければ、同じ問題が繰り返されるからです。そこで紹介されたのが **Microsoft Perception** です（音声認識の都合で表記が確定できません。トランスクリプトの綴りのままです）。エージェントを基盤に、セキュリティ担当者が大規模に作業できるようにする仕組みで、攻撃をシミュレートする red team、検知してトリアージする blue team、修正・是正する green team の 3 種類があると説明されました。デモで使われるプレイブックは 1 つ以上のエージェントを束ねて動かす方法で、デモ D では攻撃経路を閉じるもの（Close attack paths）が使われました。

## 6. デモ・手順

このセッションには、画面を使ったデモが複数あります。トランスクリプトは音声のみのため、画面の細部（ボタン名やレイアウト）は音声から分かる範囲に限っています。

### 6.1 デモ A：Defender でハイブリッド攻撃を調査し、Entra に反映される様子（Martin 氏）

1. Defender ポータルを開き、Cases（ケース）から対象のケースの詳細に進む
2. ケースの詳細に **Attack disruption** のラベルが付いていることを確認する。Defender が攻撃の深刻さを理解して即座に動いたことを示している。デモでは、攻撃が続くよう、ユーザーを無効化する部分だけを意図的に止めてある
3. 画面を下にスクロールし、攻撃のストーリー全体を確認する。攻撃者が各ステップをたどり、マシンに RDP し、資格情報を盗むといった流れが表示される
4. Attack graph を確認する。2 つの円が、攻撃に関与した資産を介してつながっている。Kerberos に関するアラートは 1 件のアラートだが、前後の不審な活動と共通の資産や時系列で結びつけて 1 つのケースにしている
5. 標的となったユーザーのページに移る。標的は Aaron Baxton で、複数システムのアカウント（Active Directory、Entra、サードパーティの SaaS アプリケーションなど）が同じ ID に相関して一覧表示されている。この一覧は非常に長い
6. リスクスコアの詳細を開く。アラート、ポスチャの推奨事項、Entra のリスクレベル、blast radius から算出されている。異なる 2 つのアカウントでトリガーされたアラートも見える。Entra のリスクレベルを開くと、そのレベルに寄与した出来事のタイムラインが分かる
7. Entra ポータルに移動し、Defender の SOC アナリストが見ているのとまったく同じ情報が表示されることを確認する
8. エンドユーザーの立場に切り替える。Aaron のリスクは高いが、仕事は続ける必要がある。本人は別のアカウントが侵害されたことを知らない。そこで Aaron に対して ID 確認（identity verification）が求められる
9. Aaron として ID 確認を完了する。Aaron は仕事を続けられ、リスクを自分で是正（self-remediate）できた。ヘルプデスクに電話したり、ID 管理者がアカウントを再度有効にしたりする必要がなく、すべてが自己完結した
10. Entra ポータルに戻ると、Aaron のリスクが下がっていることが確認できる

### 6.2 デモ B：Agent 365 での動的なエージェントリスク（Martin 氏）

1. A365 ポータル（管理センター）を開き、All agents から組織内のエージェントの一覧（インベントリ）を見る
2. Shadow IT の画面で未承認のエージェントを確認し、その中から「cloud desktop agent」（原文の聞き取りのまま。Claude Desktop を指すかどうかは音声からは確定できません）を選ぶ。デモ用に用意されたものと説明されている。2 台のマシンでこのエージェントが動いていることが分かる
3. その特定のインスタンスの詳細を開く。動的リスクレベル（Dynamic risk level）は最初 Medium になっている
4. Security タブで、リスクを構成する 3 つの領域（blast radius、exposure level、runtime risk）を確認する
5. エージェント向けの Conditional Access ポリシーを確認する。リスクが高い場合にエージェントの動作をブロックする設定になっている（時間の都合で個々の設定項目は説明されていない）。リスクが低〜中程度の場合に、上司の承認を挟む human in the loop を使う例も語られた
6. Claude のエージェントで操作する。更新が必要なダッシュボードがあり、プロンプトを思い出せなかったので、検索エンジンで見つけたウェブページからプロンプトをコピーして、エージェントに貼り付けた。ウェブページには気づかなかった（白地に白などの）悪意のある 2 行目が含まれており、環境変数を露出させる内容だった
7. 実行すると、Defender が悪意があるとして、その動作をブロックする。これによりエージェントのリスクが上がる
8. プロンプトを変えて同じことをもう一度試す。今度は社会保障番号（social security number）を検証しようとするプロンプトで、DLP に捕捉される。これは Purview によるもので、1 回目は Defender for Endpoint によるブロックだった
9. 管理センターに戻ると、リスクが High になっている
10. さらに別の操作を試すと、エージェントのリスクが High のため、完全にブロックされる

Martin 氏は、組織に導入している Defender 製品が多いほど、Dynamic agent risk に入ってくるシグナルも増えると説明しています。

### 6.3 デモ C：デバイスコードフローの攻撃（Martin 氏、攻撃者の立場）

1. 攻撃者の立場（"hacker hat"）で、CLI（音声認識上 "compiler CLI" と聞こえるツール。文脈では Copilot CLI を指すと見られますが、確定できません）を起動し、ログインを開始する。デバイスコードフローを選ぶ
2. 画面に表示されたデバイスコードを使い、組織内のユーザーをだましてそのコードで認証させる。攻撃者はそれによりユーザーのセッションへのアクセスを得る
3. 用意したフィッシングメールの例を見せる。緊急性を煽り、早急に認証しないとアクセスを失うと伝える内容。Teams メッセージの場合もある
4. ユーザーは、アクセスを失うのを恐れてリンクをクリックし、攻撃者が渡したコードを入力した。これにより攻撃者は、そのユーザーの Copilot CLI のセッションにアクセスできるようになった
5. 攻撃者にできることとして語られたのは、そのユーザーがリモートセッションを実行していれば、そのマシンでコードをリモート実行できる、組織の内部リポジトリにアクセスできれば成果物をダウンロードできる、そのエージェントのメモリを汚染し、常に特定の変数や答えを返させて組織やユーザーに悪影響を与えられる、の 3 点です。
6. Defender ポータルで、左側のアタックストーリーとアタックグラフを確認する。悪意のあるメール、そのメールのリンク、ユーザーがクリックして URL にアクセスしたことが見える
7. そのユーザーのページを開く。Defender がこの活動を相関させ、アナリストの調査を待たずに、ユーザーアカウントまたは GitHub アカウントを自動的に無効化していることが分かる
8. リスクスコアのページで、スコアが High になっている。ここからアナリストが調査し、必要なら是正できる

### 6.4 デモ D：Perception のプレイブックで攻撃経路を閉じる（Martin 氏）

1. Defender の Perception を開き、プレイブックの一覧へ進む
2. 「Close identity attack paths」のプレイブックまで下にスクロールし、新しいセッション（Perception と対話する単位）を開始する
3. プレイブックは成果ベース（outcome based）で、特定のエージェントやタスクを指定する必要はなく、必要な成果を選ぶだけでよい
4. セッションの実行中、Perception は組織の情報を読み込み、Defender のシグナルとアラートをすべて読み、既存の Conditional Access ポリシーも確認して、ギャップを探す。デモでは「デバイスコードフローは無効にしたはずなのに、なぜこのユーザーが侵害されたのか」という疑問に答える形になっている
5. 結果として、スコープから漏れていた特定のユーザーのギャップを埋める Conditional Access ポリシーを作成するよう提案される
6. 自動で最後まで実行されるわけではなく、必ず人（human in the loop）による承認が必要。作成されるポリシーは、読み取り専用のモード（監査モード）で作られる
7. 管理者は監査モードでしばらく運用し、組織の変更管理や安全なロールアウト計画に沿って、有効化できる

> 補足：デモ D は、デモ C のデバイスコードフロー攻撃の穴を塞ぐ位置づけです。Yair 氏は「前のデモの攻撃経路が自動で閉じられる様子を見る」と予告しています。

## 7. 注意点・発表者の気付き

* **デバイスコードフローは無効化を検討すべき**：Martin 氏は「自分の組織でデバイスコードフローを有効にしている人」を会場に尋ね、手が少なかったことを歓迎しつつ、まさにこのデモが無効化すべき理由だと述べています。
* **アカウントを分けていても、同じマシンに両方の資格情報があると突破される**：日常用アカウントと管理用アカウントを分けるベストプラクティスに従っていた組織でも、両方が同じマシンのブラウザーに残っていたため、トークンのリプレイ（MFA の回避）を許したというのが、デモ A のシナリオです。
* **悪意のあるプロンプトは見えない形で紛れ込む**：エージェントに貼り付けるプロンプトに、白地に白のように人の目に見えない悪意ある指示が混ざる例が示されました。
* **承認と段階的なロールアウト**：Perception が提案するポリシーは、自動では有効にならず、人の承認と監査モードでの確認を経て展開します。
* **提供時期の確認**：Dynamic agent risk のパブリックプレビューは 12 月中旬の見込み、Dynamic conditional access は現在プライベートプレビューで、パブリックプレビューは 1〜2 月頃と述べられました（発言中に言い直しがあります）。
* **デモの前提**：デモ A では、攻撃を見せるために、ユーザーを自動で無効化する部分をあえて止めていると明言されています。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

* ID 側と SOC 側の手作業の引き継ぎを減らし、遅延を縮められる（ポスチャ、予防、検知・対応が互いにフィードバックする）
* 複数のシステムにまたがる同一人物のアカウントを 1 つの ID に相関させて見られる。Martin 氏はこれが予防・調査・対応・ポスチャのすべてを支えると説明している
* Defender の攻撃遮断により、アナリストが開く前に対応が済んでいることがある
* リスクの高いユーザーが、ヘルプデスクや ID 管理者を介さずに、ID 確認で自分でリスクを下げて業務を続けられる
* エージェントについても、リスクに応じたブロックや human in the loop の承認を、Conditional Access の仕組みで実現できる。導入している Defender 製品が多いほど、シグナルが増える
* Perception のプレイブックにより、攻撃の原因となった Conditional Access のギャップを見つけ、修正案の提案を受けられる。作成は監査モードで、管理者が段階的に有効化できる

> 注意：具体的な数値（検知時間の短縮率やコスト削減など）や顧客事例は、このセッションでは語られていません。

## 9. まとめ

Yair 氏は、ID インフラストラクチャ、ID コントロールプレーン、脅威の検知と対応という 3 つの柱が連動することを、デモで確認したと総括しました。最初のデモ（デモ A）では、ハイブリッド ID 攻撃が Entra のリスクに反映されることを、AI エージェントのデモでは、そのリスクが Dynamic agent risk としてアクセス制御に影響することを、さらに、ユーザーとエージェントの信頼関係が破られても SOC 側で自動遮断が働くこと、最後に Perception で攻撃経路を閉じて、SOC の知見が自律的にポスチャへ反映されることを示しました。

持ち帰ってほしいのは、**ID セキュリティはチームスポーツ**だということです。ID 管理者もセキュリティ管理者も、それぞれ固有のコンテキストを持っており、単独では守れません。両者のコンテキストを、手作業の引き継ぎなしにつなげることが鍵だと述べて、セッションは締められました。
