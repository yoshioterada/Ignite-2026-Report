# BRK345 Master Agent Governance with Agent 365

## 1. はじめに

このセッションは、組織内で急増する AI エージェントを「誰が作ったのか、誰が責任を持つのか、何にアクセスできるのか、想定どおり動いているのか」という観点で管理するための考え方と、Agent 365（発表では A365 とも呼ばれます）の機能を紹介するものです。前半は IT 管理者・AI 管理者向けの機能（Action Center とツールの管理）、後半はセキュリティ管理者向けの考え方（Microsoft Entra Agent ID を中心とした ID 管理、データ保護、デバイス上のエージェントの可視化）が中心です。さらに、LG U+ の事例として、2 万を超えるエージェントを持つ企業がどのように統制を始めたかも紹介されます。

結論を先に言うと、発表全体のメッセージは「エージェントごとに管理の仕組みを作るのではなく、**すべてのエージェントに共通のコントロールプレーンを持つ**」「従業員に対して行っている ID 管理（採用から退職まで）をエージェントにも同じように適用する」の 2 点です。

## 3. 何に関する発表か

AI エージェントは Copilot Studio、Foundry、他社クラウド、さらには未登録のエンドポイントなど、さまざまな場所で作られて動いています。発表者は、新しく人を採用したときには「相談できる上司がいる」「職務に合わせた権限がある」「承認済みのアプリとデータがある」「行動の監査証跡が残る」といった仕組みがあるのに対して、エージェントにはそれが付いてこない、と問題提起しています。

また、ガバナンスは導入初日に壊れるのではなく、**運用の中でじわじわ崩れる**（operational drift）と説明しています。例えば、エージェントの所有者が異動・退職したり、プロジェクトが終わったのにエージェントだけが動き続けたり、権限が古いまま残ったりします。

Agent 365 は、管理、ガバナンス、セキュリティ、ビジネス価値をひとつにまとめるもので、ユーザーやアプリの管理にすでに使っているツールの上に作られている、と説明されています。発表者は「見えないものは管理できない」ことを出発点にしています。

関心を持つペルソナも異なります。

| ペルソナ | 知りたいこと |
| --- | --- |
| IT 管理者 | どのエージェントが動いていて、誰が所有しているか |
| セキュリティ管理者 | エージェントが侵害されていないか、データを過剰共有していないか |
| ビジネスリーダー | 実行中のエージェントから実際にビジネス価値が得られているか |
| 開発者・メーカー | 速く作りたいが、ポリシーの範囲内にとどまる必要がある |

## 4. 発表者が伝えたいメッセージ

**エージェントの管理は「見える化 → 影響の把握 → 対処または自動化」という同じ流れで行う**というのが、Sneha 氏の整理です。所有者とライフサイクル、ツール、アクセス、リスク、コストのいずれも、この一つの運用モデルで扱えるとしています。

HC Jo 氏は、エージェントを作ること自体は比較的簡単だが、信頼して運用することが本当の課題になると述べ、「すべてのエージェントのために 1 つのプラットフォームは要らない。すべてのエージェントのために 1 つのコントロールプレーンがあればよい」と結論づけています。

Mark 氏は、エージェントが増える速度は人間が追跡できる速度を超えるため、手作業での判断は破綻すると述べています。そのうえで、従業員の ID 管理の考え方（最初に付与する権限、申請と承認、役割変更時の見直し、退職時の削除）をエージェントにも当てはめるよう勧めています。さらに、セキュリティ部門だけで決めるのではなく、エージェントのスポンサーやリソース所有者を巻き込むことが成功パターンだと述べています。

## 5. 発表内容の詳細

### 5.1 導入: 所有者のいないエージェントという問題

Sneha 氏は最初に、会場に「明確な所有者のいないエージェントを見つけたことがありますか」と尋ね、続けて「そのエージェントがどのデータ・ツール・ナレッジにアクセスできるか分からなかった人」にも挙手を求めました。この「分からない」というギャップが、このセッションのテーマです。

エージェントは Copilot Studio、Foundry、他のクラウド、他のベンダー、未登録のエンドポイントなど複数の場所で動いており、とくに他のクラウドやベンダー、未登録のエンドポイントで動いているものに運用リスクが隠れていると説明しています。

### 5.2 LG U+ の事例（HC Jo 氏）

HC Jo 氏は、韓国の通信事業者 LG U+ で Applied AI Lab を率いています。同社は韓国の 3 大モバイル事業者の 1 つで、3,200 万を超えるモバイル回線と、約 600 万世帯のブロードバンドを提供していると紹介しました。

**背景**

- AI を中心とする企業を目指し、AX（音声で「AX」と語られた言葉。発表では詳しい定義はありません）はまず自社のサービスから始める、という考えを述べています。
- 今年の 5 月に MS Copilot を全社の標準業務ツールにし、約 1 か月で従業員の 80% 超が利用した。
- Microsoft のテナントだけで、従業員が 2 万を超えるエージェントを作成した。このほかに、複数のクラウド、SaaS プラットフォーム、自社内のプラットフォームにもエージェントがある。

**生じた 4 つの疑問**

エージェントが増えるにつれ、次の 4 つの基本的な疑問が出てきたといいます。

1. エージェントは実際にいくつあるのか（プラットフォームごとに「エージェント」の定義が違う）
2. このエージェントの所有者は誰か（所有者情報とデプロイ情報が別々の管理センターにある）
3. このエージェントは何をしたのか（ログとトレースが各ランタイムに分散している）
4. 止められるのか、コストはいくらか

HC Jo 氏は、これらは AI モデルの問題ではなく**運用の問題**だと気づいたと述べています。

**「ゼロ・シャドウ」ルール**

そこで同社は「zero shadow」というシンプルなルールを定めました。「登録なし、ID なし、所有者なし、運用なし」です。新しいエージェントは、実行前に次の 3 つのチェックを通過する必要があります。

- 1 つのレジストリに登録されていること
- 固有の ID を持っていること
- 名前の付いたアクティブな所有者がいること

どれか 1 つでも欠けていれば、そのエージェントはブロックされるか、最終的には廃止されます。

**3 本の柱**

| 柱 | 内容 |
| --- | --- |
| Inventory | 1 つのレジストリをシステム・オブ・レコードにする |
| Observability | ログとトレースを各エージェントに紐づけ、数を数えるだけでなく品質を評価する |
| Governance | 事実に基づく受け入れ審査（intake）で追跡するかどうかを決め、すべての判断を証跡として残す |

**Microsoft との共同検証**

これを検証するため、Microsoft と 17 週間にわたって共同でエンジニアリングを行ったと説明しています。Microsoft が各シナリオを各テナントで構築し、LG U+ が自社の本番テナントで再現しました。対象は 10 のプラットフォーム、11 のゲート、23 のガバナンスシナリオです。結果として、Microsoft のエージェントは登録、ID、オブザーバビリティ、制御の領域で全機能が使えたとのことです。AWS と Google Cloud のエージェントは、今回の共同エンジニアリングで追加したものを通じて同様の機能が得られる一方、今後の作業でさらに必要な部分があると述べています（音声からは細かい内訳までは聞き取れません）。

**MVE（minimum viable environment）から得た 3 つの教訓**

1. 登録は制御ではない。エージェントは、固有の ID を持つまでは管理されていない状態のまま。
2. ファーストパーティとサードパーティのエージェントは、制御される場所が異なる。そのため共通のプラットフォームにコネクタを作っている。
3. 制御はモデルの外に置く。ユーザーの ID をデータまで一貫して伝え、キルスイッチが機能するようにする。

**アーキテクチャ**

HC Jo 氏の説明では、最上位に Agent 365 と Entra Agent ID が単一のコントロールプレーンとして置かれ、そこにレジストリと所有者、エージェント ID、アクセスポリシー、キルスイッチがあります。Microsoft のエージェントは標準で統合され、それ以外のエージェントはレジストリ同期、コネクタの作成、テレメトリの追加などで接続します。これにより、すべてのランタイムで「誰が依頼しているか」と「どのエージェントが動いているか」の両方をシステムが把握でき、アクセスの判断はモデルの外で行われ、各ランタイムにテレメトリの経路があるという構成です。

**今後の予定**

- 2026 年: 標準化。1 つのレジストリ、1 つの受け入れプロセス、1 つのログ標準。
- 2027 年から: 自動化されたガバナンス。3 つの要素として、evaluation gauge、automation isolation、evidence chain を挙げています（音声認識の都合で表記が確定できません）。

最後に、ガバナンスはデプロイ後の書類仕事ではなく、すべてのエージェントの動き方の一部であるべきだと述べ、APAC と Korea の Microsoft チームに謝意を示しました。

### 5.3 Action Center（IT 管理者向け）

Sneha 氏は、IT コミュニティからよく聞く 3 つの質問を挙げています。

1. 今日、どのエージェントに注意を払うべきか
2. このエージェントの所有者は誰で、まだ必要か
3. ツールが変更されたら、どのエージェントに影響するか

最初の 2 つに答えるのが、**Action Center** です。A365 に 12 月中旬にプレビューとして登場する予定と説明されています。エージェントのフラットな一覧を、「非アクティブ」「所有者なし」「レビュー待ち」などの優先順位付きのビューに変え、その場で実行できる組み込みアクションも付いています。3 つ目の質問は、後述のツールの機能で答えます。

**画面の構成（デモ）**

- 左側にガバナンススコアが表示されます。デモでは約 83% で、「かなり健全なエージェント環境」とのことです。過去 30 日間の対応でスコアは約 6 ポイント上がっています。その下に、カテゴリー別の未対応タスクが出ます。
- 右側には実施済みの作業があり、過去 30 日間で IT チームが Action Center を使って、約 8,500 のエージェントを承認し、約 12,000 のエージェントに所有者を割り当て、約 14,000 の非アクティブなエージェントをクリーンアップした、という数字が示されました。
- その下に推奨アクションがあります。デモでは 6 つあり、所有者のないエージェントへの所有者割り当て、シャドー AI の制限、非アクティブのクリーンアップの拡大、影響の小さいエージェントの最適化などが含まれています（残りは「など」としか語られていません）。各カードで「Review」を選ぶと、その自動化を構成するポリシーと条件が表示され、影響を受けるエージェントを確認してから有効化できます。
- さらに下では、アクションが IT 管理者の関心領域ごとに分類されています。「エージェントを所有され稼働中の状態に保つ」「公開して安全なものを承認する」「リスクを減らす」「コストを管理する」です。各行には対象のエージェント数とレビュー済みの数、優先度が表示されます。

**非アクティブなエージェントの例**

「最近のアクティビティがないエージェント」を開いた例が示されました。Microsoft Foundry、Copilot Studio、Agent Builder で作られ、90 日を超えて使われていないエージェントです。このデモテナントでは**約 98,000 件**あります。

| 項目 | 件数 |
| --- | --- |
| ブロック済み | 182 |
| 削除済み | 635 |
| 除外（Exclude） | 313 |
| 未対応（約） | 97,000 |

「除外」は、四半期に 1 回、年に 1 回しか使わない季節性のエージェントなど、自動化の対象にしたくないものを入れるカテゴリーです。横のグラフには、6 月から月ごとにクリーンアップが積み上がっている様子が出ています。ほとんどが未対応なので、自動化が役に立つ、という流れです。

ページを下にスクロールすると、すぐに使える自動化が並んでいます。オンにすると、例えば毎日午前 6 時に実行されるようにでき、オフのままにして下の表から手動で対応することもできます。

**Entra との連携**

自動化の 1 つを開いた画面で、Entra との接続が紹介されました。Entra ID を持つエージェントについては、これらのビューの元になるアクティビティデータは Entra から来ており、ここで行った操作は Entra に書き戻されます。これで、2 つの製品でエージェントのステータスが同期されます。Entra 向けのデフォルトポリシーも取り込まれ、オンにすると 90 日後に ID レベルでエージェントをブロックします。「A365 のエージェントと Entra のエージェントをどう同期させるか」は IT 管理者からよく聞かれる課題だったと説明されています。

独自の自動化も作成でき、条件を選び、ポリシーに合わせて実行時刻を指定できます。

**管理者が制御を失わないための仕組み**

- 季節性のエージェントなど、使えるままにしておきたいものは除外できる。
- エージェントがブロックされたと気づいた所有者は、ブロック解除を依頼できる。管理者側には「request to keep」として表示される。
- 手動・自動を問わず、すべてのアクションは「誰が（どの自動化が）実行したか」とともにアクション履歴に記録される。

### 5.4 ツール・レジストリ（デモ）

エージェントの安全性は、触れられるものに左右されるため、ツールの管理に進みます。**ツール・レジストリ**には、エージェントが呼び出せるあらゆるツールが 1 か所に集められています。対象はプラグイン、スキル、MCP サーバー、Power Platform コネクタです。Microsoft 製、Partner Center 経由のパートナー製、チームが手動でアップロードしたものがあります。プラグインは、スキルと MCP をパッケージにしたもので、現在 Cowork と Copilot で実際に使われているのはこのプラグインだと説明しています。

**finance プラグインを調べる**

1. 利用前に中身を確認できる。説明文があり、下にスクロールすると 4 つの MCP サーバーとスキルのセットが紐づいていることが分かる。
2. このプラグインを誰にも使わせたくなければ、その場でブロックできる。
3. 自動でインストールされているユーザーを確認すると、組織全体ではなく 2 人だけだった。
4. それ以外のユーザーは、Cowork 経由でこのプラグインの利用を申請でき、申請はツール・レジストリ画面のリクエストキューに表示される。

**MCP サーバーを調べる**

1. 概要に戻り、finance プラグインに紐づく MCP サーバーのうち finance のものを開く。
2. このサーバーに依存するプラグインは 2 つ（先ほどの finance プラグインと marketing プラグイン）。この MCP サーバーをブロックすると、依存する両方のプラグインに影響が出る。
3. 「Assessment」タブでは、ツール・ポイズニング、隠れた指示、他のサーバーを装うツールのチェックと、Entra ID 認証や TLS などの ID・サプライチェーンのチェックが行われる。デモでは全項目が合格（グリーン）だった。この Assessment は**ポスト Ignite でプライベートプレビュー**とのことです。
4. 「Activity」タブでは、このサーバーを誰が使っているかが分かる。過去 30 日で約 90 のエージェントが呼び出し、約 2,500 回のツール呼び出しがあり、呼び出しの多いエージェント（contract intelligence、procurement など）も表示される。このアクティビティビューは**パブリックプレビュー**。
5. 変更が必要になっても、影響範囲が分かる。サーバー全体を止めなくても、「Tools」タブで update ledger entity のような読み書き（read-write）のアクションだけをオフにし、他の読み取り専用ツールは動かし続けられる。

これで、先ほどの 3 つ目の質問「ツールが変わったらどのエージェントに影響するか」に答えられる、という流れです。

**GitHub 上のツールを一括で取り込む（Managed connections platform）**

多くの組織が自前のスキルと MCP サーバーを GitHub で管理し始めている、という前提で、次の流れが示されました。

1. 「managed connections platform」を開き、接続を追加する。
2. ツールカタログとして GitHub を選ぶ。
3. ツールやスキルが保存されているリポジトリの URL を入力し、インストールと認可（Install and Authorize）でアクセスを許可する。
4. 「Next」で、これらのツールを使えるユーザーを選ぶ（デモでは先ほどと同じ 2 人）。
5. 「Connect」を押す。処理はバックグラウンドで実行され、数秒から数分かかる。
6. 完了すると、新しいリポジトリ（GitHub Private 001）が接続済みプラットフォームに追加され、**198 のツールが一度に**ツール・レジストリに追加される。MCP サーバーの数は 235 に増えた。

これらのツールは、レジストリに入った時点で、追加の設定なしに Cowork で使えるようになると説明されています。この GitHub 接続は**プライベートプレビュー**で、ツールが GitHub にある場合はサインアップすれば順次案内するとのことです。

出所を問わず、レジストリに入ったツールは Assessment タブで評価されます（今取り込んだ 198 のツールも含む）。MCP サーバーとスキルの Assessment はポスト Ignite でプライベートプレビューに入ります。将来的には適用するチェックを選べるようになり、基準を満たさないツールは先ほどの Action Center に「レビューが必要なエージェント」として表示される、と説明されています。

最後に Sneha 氏は、所有者・ライフサイクル・ツールのガバナンスで見せた「何が注意を要するかを把握し、影響を理解して、実行するか自動化する」という動きは、アクセス、リスク、コストでも同じで、「1 つの運用モデルに 2 つのレンズ」だとまとめています。

### 5.5 セキュリティ管理者から見たエージェント（Mark Wahl 氏）

Mark 氏はここから、セキュリティ管理者やセキュリティアーキテクトの視点に切り替えました。

**Microsoft Digital Defense Report**

毎年出るこのレポートは「今年は 140 ページくらい」の大部で、エージェントに関する章もあります。そこには、攻撃ベクターの円グラフがあり、その割合が年ごとに変わっていると説明しています。link injection のような想定内のものに加えて、**jailbreak、tool abuse、identity abuse が増えている**とのことです。

問題として挙げたのは次の 3 点です。

- エージェントは追跡できる速度より速く増える。手作業で「今日エージェントを持つべきか」を判断するやり方は破綻する。
- アカウンタビリティ。エージェントの責任者は誰か。
- パーミッション。ツールで何をさせたいかだけでなく、エージェントが「行き先」でどの権限と ID を持つか（SharePoint、メール送信、SAP・Workday・Salesforce といった業務アプリなど）を見る必要がある。

**API キーや資格情報の使い回し**

これまでは、エージェントの ID が「誰かが API キーを渡した」ことで決まる例が多かったと述べています。OpenAI の API キーや、Box のクライアント ID とシークレットが組織内で回し使われ、変更しようにも全員が依存していて変更できません。「今日 50 個のエージェントをデプロイした」と言えるのは ID や資格情報を使い回しているからで、そうした ID は多くの人に使われ、アカウンタビリティも権限も不明確で、ビジネス目的に結びつけられない、「そうした ID はおそらく burned（使い物にならない状態）になっている」という説明です。

**エージェントにどの ID を持たせるか**

レポートでは 8 つの項目を扱っているが、今日はそのすべてには触れず、Mark 氏の専門である ID から話すと述べています。

- 共有の API キーは避け、**エージェント固有の ID** を持たせる。
- 人とも別にするかどうかは重要な論点。GitHub を手伝うエージェントは「Mark」として入るのか、「Mark の helper agent」として入るのか。エージェントを本人の延長と見なすか、別の存在と見なすかを組織として決める必要がある。
- 例えば、データベースで drop table ができる Mark の権限を、エージェントにも持たせてよいのか。メールをエージェントが本人名義で読み書きしてよいのか。多くの組織は「分離すべき」と考える。ただし、エージェントが孤立してよいという意味ではなく、アカウンタビリティは引き続き必要。
- もう 1 つの理由は**最小権限**。多くの組織では人が過剰な権限を持っているが、誰も気づかない（例として、Mark が誤って 500 の余分な AD セキュリティグループに入っていた、という話）。人間はそれを調べに行かないが、エージェントは自分が入っているグループや権限を「探索して使ってしまう」。実際にそうした事例が見られると述べています。エージェントには、担当する仕事に必要な範囲だけを使わせる必要があります。

Digital Defense Report は無料で公開されており、ライフサイクル管理などの話もあるので読んでほしいと述べています。

### 5.6 運用モデル: 従業員と同じ流れをエージェントにも

エージェントに関わる、AI 管理者以外のペルソナとして次の 2 つが挙げられました。

- **エージェントのスポンサー**: エージェントを持ち込む人。多くは事業部門。「新しいバージョンのアプリを入れたら 300 のエージェントが付いてきた」という例が語られました。
- **リソース所有者**: これまで API キー、クライアント ID、ローカルユーザーアカウントをエージェントに渡していたかもしれない人。正式な ID を与え、エージェントがそのリソースで持つ ID と権限が適切なものになるよう整える時期だと述べています。リソース所有者には「エージェントがそこで何をできるか、受け入れられるか」を確認することが求められます。

Mark 氏は、従業員に対して多くの組織が持つプロセスを、エージェントでも同様にやってみようと提案します。

従業員には、入社時にメールボックスやライセンスといった基本の権限（birthright access）が付きます。そのうえで、職務に応じた権限を付与し、役割の変更や退職に対応します。この後半部分をエージェントに当てはめると、次のようになります。

| 従業員の流れ | エージェントに当てはめたときの考え方 |
| --- | --- |
| 職務のための追加権限は、上司の申請と承認で付与され、監査証跡が残る | 新しいエージェントがどう権限、ツール、下流システムの権利を得るかを決める。後で必要になる権限の追加も含めた手順を用意する |
| 役割が変わったら権限を更新し、見直しで余分な権限を残さない | スポンサーが異動したらエージェントに新しいスポンサーを割り当てる。ベンダーが担当者の異動に付いていかないのと同じ |
| 退職時に ID を削除する | 価値がなくなったエージェントは削除する |

エージェントでは、初日に最終的な役割が分からず、必要な権限が時間とともに変わります。「チケットを起票してもらい、管理者が権限を付与して admin consent をクリックする」という手順は、新しいエージェントが数百万単位になるうえ、規制対象のデータや業務アプリへのアクセスなど簡単に承認できないものもあるため、適切な答えではないとしています。承認者を誰にするか、承認者がエージェントによる権限要求の増加に対応できるか、同じ職務のエージェントに対して権限を標準化して一度の承認で済ませられないか、を考えるよう促しています。

スポンサーの異動などがあっても、エージェントが孤立したり、価値がなくなったエージェントを何か月も何年も抱えたままにしたりしないよう、ライフサイクルを自動で回す必要があります。誰かが「このエージェントに責任を持つ」と確認し、役割を果たしていなければ権限を取り上げ、価値がなくなったら削除します。

これらの要素は**すべて今日利用可能**で、Entra Agent ID プラットフォームを使うエージェントなら、従業員と同様に実施できると説明しています。

### 5.7 Entra での権限管理とライフサイクル

Mark 氏は、Entra の機能として次を紹介しました。なお、このパートはスライドと口頭の説明が中心で、画面を操作する場面は音声からは確認できません。

**アクセスパッケージと API 権限**

OAuth ベースのアプリケーションが数十から数百ある場合、エージェントが受け取る権限セットは非常に大きくなり、1 つの長いリストでは管理しづらくなります。そこで、数か月前に entitlement management と ID governance に追加された機能として、**アクセスパッケージに API 権限を含められる**ようになりました。例えば「DevOps 本番を使うために必要な API 権限をすべて入れた 1 つのアクセスパッケージ」を作れます。

Agent 365 の管理センターのエクスペリエンスでは、新しいエージェントに対して「そのアクセスパッケージを含むポリシーテンプレート」を適用できます。DevOps の責任者はポリシーテンプレートを設定するときに一度承認すれば、以後に追加されるエージェントも同じテンプレートで権限を得られます。

**個別承認が必要な場合**

非常に機密性の高いものは、エージェントごとの個別承認にもできます。スポンサーが「自分がスポンサーしているこのエージェントに、そのアクセスパッケージを割り当ててほしい」と申請し、理由を入力し、いくつかの質問に答えます。すべて監査されます。従業員やビジネスゲストが申請するときと同様に、多段階の承認ワークフロー、期間限定（1 週間、1 か月など）、承認者による理由の記入が利用でき、人間の時限アクセスと同じプロセスをエージェント ID にも適用できます。

**使われないエージェントの扱い**

前半の顧客事例にもあったように、何千ものエージェントが作られ、その多くは「Hello, world」だった、と Mark 氏は述べます。自分も Foundry でエージェントを学習用に作って忘れ、数か月後に「エージェントが期限切れになります。まだ必要ですか」というメールが来た、という例も語られました。Entra にはすでに、エージェント ID を確認してブロックするコントロールがあります。

なぜ Entra Agent ID で行うのかについては、エージェントの ID は他の Microsoft・非 Microsoft アプリケーションへの認証に使われるため、悪用されないようにするためだと説明しています。攻撃者は、放置されたアプリケーションやサービスプリンシパルを狙うので、誰も見ていないエージェント ID を作らないようにしたい、という考えです。

設定できるルールの例は次のとおりです。

- 60 日ごと、1 年ごとなど、「まだ必要」という再確認
- アクティビティがあること
- スポンサーがいること

ポリシーはグループ分けでき、テナント全体に常に適用されるもの（非アクティブなエージェントの自動ブロックなど。「オンになっているので心配しなくてよい」とのこと）と、特定のコミュニティ向けのもの（例: スポンサー 2 人、90 日以内のアクティビティを必須にする）を使い分けられます。これにより、放置されたエージェントや残ったままの権限・アクセス権を防げます。

### 5.8 データ保護、ローカルエージェントの可視化、進め方

**データ漏えいと Purview**

セキュリティ面で大きな懸念になっているのがデータ漏えいです。エージェントは SharePoint サイトや OneDrive の文書を読み、内容を記憶に取り込みます。その文書に機密情報が含まれていても、**ラベルが付いていなければエージェントには分かりません**。Mark 氏は会場に「データのラベル付けをしている人」と尋ね、少数が手を挙げたことを受けて、まだ遅くないと述べています。Purview には自動スキャンと自動ラベル付けがあり、キーワードやタグを指定して SharePoint サイトのラベル付けを始められます。機密になり得るものがあるなら、エージェントが読み始める前に自動ラベル付けをオンにすることを勧めています。これがエージェントに見せる範囲の制御につながります。

また、情報管理を進化させる取り組みとして「information flow control」にも触れています。コンテンツがエージェントに入り、エージェントが新しいコンテンツを生成する過程でも保護が失われず、過剰共有が起きないようにするためのものです（発表では詳細な機能説明まではありません）。

**デバイス上のエージェントの可視化**

Foundry、Copilot Studio、SaaS アプリに埋め込まれたエージェント、Vertex や Bedrock から来るエージェントに加えて、BYOD や自由にソフトをインストールできる環境では、**従業員の PC 上にもエージェントがある**はずだと述べています。ある顧客で、この機能が出た時に「オンにしてみて」と勧めたところ、翌日に「社内で 26 人が OpenClaw を使っていると分かった。以前は知らなかった」と言われたそうです。

データは Defender で収集し、Agent 365 のエクスペリエンスに表示します。ローカルエージェントがどの PC にあり、どの技術（GitHub Copilot CLI、Claw など。発話のまま）を使っているかが分かります。セキュリティ管理者がそのエージェントの良し悪しを判断できなくても、問題があったときに、どのデバイスか、誰がサインインしているか、デバイスの所有者として誰が割り当てられているかをたどり、責任者に連絡できる、という説明です。

**コントロールが役に立っているかの確認と目的設定**

「すべてのエージェントをブロックする」という出発点は簡単ですが、効果的な制御にならなかったと述べています。ビジネス側が「仕事を進めるにはセキュリティを回避するしかない」と考えてしまうためです。

そこで、制御の目的から出発することを勧めています。外部要因（各種規制）や内部要因を整理し、Microsoft Cloud Security Benchmark のような既存の統制例を起点にして、Digital Defense Report の攻撃ベクターを統制に結びつけます。例えば、情報の過剰共有が見られるならコンテンツのスキャンとラベル付けを、プロンプトインジェクションやエージェントによるツールの悪用が見られるなら、それぞれに対応する制御を入れる、という流れです（発話はここで途切れています）。

**ステークホルダーの合意**

セキュリティ施策の成否を分けるのは、ステークホルダーの合意（buy-in）だと述べています。ビジネス側が意図せず、あるいは意図的にコントロールを回避しないようにする必要があるためです。

- エージェントには、導入される理由がある（個人のメール整理用のエージェントや、プロジェクト用のエージェントなど）。スポンサーとリソース所有者は、エージェントの目標、成功の基準、セキュリティ上のトレードオフを示す必要がある。
- 技術探索やインキュベーションのチームには、ある程度のリスクを許容して自由に動かすこともあり得る。その場合、それが本番システムや規制対象データに及ばないよう、組織の他の部分でより多くのガードレールが必要になる。
- リソース所有者は見落とされがちである。中央集権的なセキュリティ施策をとっても、事業部門の担当者が Box を運営する知人に「クライアント ID をくれないか」と頼んで渡されると、セキュリティ部門は知らないまま、アカウンタビリティもなくなる。
- SaaS ベンダーが組み込みのエージェント（例として Photoshop にも入るかもしれないと発言）を出荷し、社内の誰かが OpenClaw を PC に入れて API キーを求めてくる。リソース所有者が API キーを渡すのか、「ランダムな API キーではなく、エージェント ID を使うこと。固有の ID を持つこと」と言うのかを、あらかじめ決めておく必要がある。

エージェントに ID を与えれば、一元的な制御ができ、条件付きアクセスなど必要なポリシーを適用できます。回避しようとする動きがあっても捕捉できる、として、プレビュー中の機能が紹介されました。Snowflake をスキャンし、Entra Agent ID を使っていない過剰な権限のローカルエージェントを見つけてブロックする、というものです（発話の「Snowflake」は、音声認識の都合で表記が確定できません）。

成功パターンとしては、関係者全員を集めて合意を作ることを挙げています。プロセスが好きなら委員会を、そうでなければ Teams のチャットでもよく、組織としてエージェントをどう考えるかの方針を作り、リソース所有者、スポンサー、エージェント開発者を、セキュリティの課題解決の一員にします。そうすれば、制御の価値を理解し、適用方法を知り、安易に API キーを配ろうとする動きに対しても適切に振る舞えます。

## 7. 注意点・発表者の気付き

- **登録だけでは制御にならない**: HC Jo 氏の教訓として、エージェントは固有の ID を持つまで管理されていない状態のままです。
- **制御はモデルの外に置く**: アクセスの判断をモデルの外で行い、ユーザーの ID をデータまで伝えることが、キルスイッチを機能させる前提だと説明しています。
- **ID の使い回しは避ける**: API キーやクライアント ID の共有・再利用は、アカウンタビリティも権限の管理もできなくなります。
- **最小権限**: 人の権限の持ちすぎは気づかれにくいが、エージェントは自分の持つ権限を探索して使ってしまいます。
- **ラベルのないデータはエージェントには機密と分からない**: データのラベル付けと自動ラベル付けを、エージェントが読み始める前に行う必要があります。
- **「全エージェントをブロック」は効果的な制御にならなかった**: ビジネス側が回避に動くためです。
- **「チケットを起票して admin consent をクリック」は、エージェントの数が多いためスケールしない**と述べています。
- **機能のステータスに注意**: Action Center は 12 月中旬にプレビュー予定、ツールの Assessment（MCP サーバーとスキル）と GitHub 接続はプライベートプレビュー、ツールの Activity ビューはパブリックプレビュー、ローカルエージェントのブロック機能もプレビューと説明されています。
- **マルチテナント**: すべてのテナントに一貫した制御を入れないと、別のテナントが攻撃経路になり得ます。

## 8. 利用者にとっての利点

発表で語られた効果や成果は次のとおりです。

- **LG U+（顧客事例）**: 10 のプラットフォーム、11 のゲート、23 のガバナンスシナリオを 17 週間の共同エンジニアリングで検証し、Microsoft のエージェントについて登録、ID、オブザーバビリティ、制御の機能を確認した。「ゼロ・シャドウ」ルール（登録・ID・所有者）を、エージェントを動かす前の条件として定めた。
- **Action Center**: フラットなエージェント一覧を優先順位付きのビューに変え、組み込みアクションや自動化で、一件ずつ対応する手間を減らせる。デモでは過去 30 日間で約 8,500 件の承認、約 12,000 件の所有者割り当て、約 14,000 件の非アクティブなエージェントのクリーンアップが示された。
- **ツール・レジストリ**: プラグイン、スキル、MCP サーバー、コネクタを 1 か所で確認し、影響範囲を把握したうえで、特定のアクションだけを止められる。GitHub 接続では 198 のツールを一度に追加できる。
- **Entra との連携**: Action Center での操作が Entra に書き戻され、ID レベルでエージェントをブロックできる。
- **アクセスパッケージとポリシーテンプレート**: 同じ職務のエージェントについては、責任者が一度承認すれば済む。個別承認や期間限定の付与も選べる。
- **デバイス上のエージェントの可視化**: Defender で収集した情報を Agent 365 に表示し、問題があったときにデバイスの所有者をたどれる。

## 9. まとめ

このセッションでは、エージェントの管理を、LG U+ の実践、IT 管理者向けの Agent 365 の機能、セキュリティ管理者向けの Entra・Purview・Defender の考え方という 3 つの視点から説明していました。共通するのは、エージェントを「登録する」「固有の ID と所有者を持たせる」「権限とツールを必要な範囲に絞る」「使われなくなったら止める・削除する」という、従業員に対する管理と同じ流れで扱うことです。

Action Center とツール・レジストリのデモでは、全体の状況を見て、影響を把握し、手動または自動で対処するという運用が示されました。Mark 氏は、技術的な制御に加えて、スポンサーやリソース所有者を巻き込んだ合意が成功の鍵になると述べています。HC Jo 氏の言葉を借りれば、必要なのは「すべてのエージェントのための 1 つのプラットフォーム」ではなく、「すべてのエージェントのための 1 つのコントロールプレーン」です。
