# BRK331 A Single Policy for Humans and AI Agents? Here’s How to Make It Work

## 1. はじめに

このセッションは、Microsoft Entra Conditional Access（条件付きアクセス）を「人間と AI エージェントの両方に使える統合ポリシーエンジン」として使うための新機能を、デモ付きで紹介する 45 分のブレークアウトです。ポリシーが数十から数百に増えて管理しきれなくなっている管理者、そして AI エージェントのアクセスをどう制御するか悩んでいるセキュリティ担当者に向けた内容です。

発表は次の 3 つの成果（アウトカム）で構成されています。

1. ポリシーの乱立（policy sprawl）を避けながら、アクセス制御を拡大する
2. エージェントが機密リソースへアクセスする際の制御を行う
3. リスクの変化に合わせて、エージェントのアクセスを動的に調整する

それぞれに新機能が対応しており、**Conditional Access policy plans**（パブリックプレビュー）、**assistive agents 向けの条件付きアクセス**（パブリックプレビュー）、**Conditional Access dynamic controls**（プレビュー）が紹介されました。

AI エージェントが仕事の進め方を変えており、アクセス制御もそれに合わせて考える必要がある、というのが出発点です。アプリケーション、データ、ネットワーク、ID に加えて AI エージェントがつながるようになり、エージェントは新しい ID、新しいアクセスパターンをもたらします。しかも従来のアクセス制御が想定していない規模とスピードで動きます。

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**条件付きアクセスが人間と AI エージェントの双方に対する統合ポリシーエンジンである**という主張です。リアルタイムのシグナルをまとめて、ユーザー、AI エージェント、アプリケーション、エンドポイント、ネットワーク、リソースにまたがってアクセスを守り、生産性を損なわないという位置づけです。

背景として、発表ではエージェントの増加を示す 2 つの数字が示されました。

- 2029 年までに、セキュアなアクセス要求の 60% が非人間の ID（non-human identities）から来ると予想されている
- すでに 53% の組織で、AI エージェントが想定された権限を超えた経験がある

エージェントは仕事を進めるためにアクセスが必要ですが、組織はどこまで行けるか、何にアクセスできるかを制御し続ける必要があります。「AI エージェントを例外扱いせず、人と同じように ID として制御する」というのがメッセージの核です。

また、お客様の組織では条件付きアクセスの規模が大きくなり、ポリシーの抜けやポリシー同士の衝突を防ぎにくくなる閾値に達しつつある、とも語られました。

## 5. 発表内容の詳細

### 5.1 ポリシーの乱立（policy sprawl）という課題

現在の条件付きアクセスは、ポリシーのフラットな一覧として管理する構造です。最初は問題ありませんが、環境が大きくなると管理も安全な変更も拡張も難しくなります。

当初は MFA やデバイス準拠、スコープ指定と除外といった少数の制御だったものが、きめ細かなリスクポリシー、Global Secure Access のポリシー、エージェント ID 専用の条件などへ広がりました。個々のポリシーは作成時には妥当でも、MFA 用、準拠デバイス用、パートナー用、「一時的なはず」の例外用と積み重なります。結果として、どのポリシーがまだ必要か、どれが重複しているか、1 つ変更すると何が壊れるかが誰にも分からなくなります。

発表者はこれを **policy sprawl（乱立）と policy drift（ずれ）** と呼び、ポリシーが増えるたびに保護範囲は広がる一方で複雑さも増し、抜けと重複が生まれ、変更のたびに変更管理上のリスクが生じると説明しました。会場への挙手でも、多くの参加者が conditional access のスケールに苦労していることが確認されました。

### 5.2 Conditional Access policy plans

対応策として紹介されたのが **conditional access policy plans**（パブリックプレビュー）です。ポリシーを 1 つずつ管理するのをやめ、「アクセスの意図を一度だけ表現し、該当するすべての ID に適用する」という考え方で、**目的（objective）を軸にアクセス制御を整理するフレームワーク**です。

主な仕様として、次の点が語られました。

- プランには共有条件（shared conditions）を設定でき、プラン内のすべてのルールがそれを継承する。共有条件の利用は任意で、包含・除外の指定を拡大しやすくするための道具として提供されている
- 1 つのプランには少なくとも 1 つのルールが必要
- 1 テナントあたり 100 プラン、1 プランあたり最大 100 ルール
- プランには名前、説明、タグ、オーナーを設定できる。オーナーの設定は RBAC を変えるものではなく、変更には引き続き conditional access admin の権限が必要。あくまでポリシーガバナンスのための仕組み
- 複数ルールを一括で On にするバルク編集機能が追加された

### 5.3 既存ポリシーを plan に統合する

すでに条件付きアクセスを運用している組織向けに、既存ポリシーを plan にまとめる機能も紹介されました。Policies 画面で複数のポリシーを選んで plan にマージし、プレビューで名前を付けられます。

プレビューでは、ポリシー同士の共通点が示されます。同じグループを対象にしていたり、条件や除外が似ていたりする場合、その共通設定が **shared conditions** になります。各ポリシー固有の差分は個別の **rule** に残り、元の条件と制御が保持されます。そのため「忠実度が落ちない」と説明されています。

統合後の新しいルールは **Off の状態で作成**されます。作成しただけで強制適用が始まることはありません。お客様の変更管理プロセスを前提に、内容を確認し、Report-only に設定し、準備ができたらルールを有効にして、古いポリシーは自分たちのスケジュールで廃止する流れです。発表者は、ペルソナ（例：開発者ペルソナ）単位でプランを作る使い方を、お客様に見られる一例として挙げています。ただし、フレームワーク自体はどのような切り方でもできる柔軟なものだとのことです。

### 5.4 エージェントのアクセス：assistive と autonomous

エージェントが企業リソースにアクセスする方法は、2 つに区別されます。

| フロー | 内容 | 条件付きアクセスの適用 |
| --- | --- | --- |
| Assistive flow | ユーザーがエージェントにタスク（メールの要約、ドキュメントの更新など）を依頼し、エージェントがユーザーの委任された権限（delegated permissions）で動く | ユーザーの既存の条件付きアクセスが引き続き適用され、さらにエージェントのコンテキストとリスクに基づく保護を追加できる |
| Autonomous flow | エージェントが自分自身の ID と権限を持ち、サインインしたユーザーなしに、スケジュールやイベントに応じて独立して動く | エージェントの ID、または専用の agent user アカウントを通じて制御する |

1 つのエージェントが両方のフローを使うこともあります。アクセス要求のたびに「ユーザーの代理か、エージェント自身の ID か」が問われ、それによって適用されるポリシーが決まります。条件付きアクセスは両フローをサポートし、次のようなエージェントのリスク情報をリアルタイムに評価します。

- エージェントがどれだけ安全に構成されているか
- どのリソースに到達できるか
- 問題が起きた場合の影響の大きさ
- 行動がユーザーや組織の意図からずれていないか

保護はサードパーティのエージェントやローカルエージェントにも及び、最初の対象は **GitHub Copilot CLI と Claude Code** と説明されました（ここで「GitHub CLI」と聞こえる箇所もあります）。発表では、**assistive agents 向けの条件付きアクセスがパブリックプレビュー**になったことが発表されました。

### 5.5 Dynamic agent risk

エージェントのリスクは、**dynamic agent risk** という新しいリスク評価モデルで継続的に更新されます。次の 3 つの要素に基づきます。

| 要素 | 説明（発表で語られた範囲） |
| --- | --- |
| Runtime level | 実行時（ランタイム）のリスク |
| Exposure level | エクスポージャー（露出）のレベル |
| Blast radius | 問題が起きたときの影響範囲 |

3 要素それぞれの詳しい定義は、発表では語られていません。全体としては、ID、データ、ネットワーク、エンドポイント、エージェントのアクティビティといったサイバースタック全体のシグナルを使って、エージェントが何にアクセスしているか、アクションの潜在的な影響は何か、組織が設定した制御から行動が逸脱していないかを判断します。Entra、Defender、Purview のシグナルに基づくとも説明されました。

エージェントリスクは、**ユーザーリスクやサインインリスクとは別物**で、リスクの報告と分析を行う独立した機能です。「一度設定して終わりのスコア」ではなく、エージェントの作業中に変化していきます。

### 5.6 アクセス時点からアクション時点へ：dynamic controls

エージェントはアクセスが許可された後も長く動き続けます。そのため次の 3 つの課題があると説明されました。

1. **コンテキストが変わる**：エージェントのリスクが Low / Medium / High と変化し、作業中に周辺の条件も変わる
2. **アクションごとに影響度が違う**：ドキュメント情報の取得はできても、機密データの変更は止める、といった区別が必要
3. **保護範囲が断片化している**：ファーストパーティのリソース、サードパーティのリソース、MCP サーバー、管理外の API など、エージェントは幅広いエコシステムにアクセスする

そこで条件付きアクセスを**データプレーンに持ち込み、評価のタイミングを認証時（authentication time）からアクション時（action time）に移す**、というのが方針です。内容は次の 3 点です。

1. より包括的なリアルタイムシグナルの導入（リスク変化に応じたポリシー適用）
2. 細かな制御の導入（エージェントが定型作業を妨げられずに続けられるようにする）
3. Global Secure Access による、エントリー境界を超えた強制の拡張

これにより、エージェントがアクセスできるかどうかだけでなく、**何のアクションを許可するか**を制御できます。発表では **Entra Conditional Access dynamic controls** が発表されました（プレビュー。トランスクリプトでは「unlimited preview」と聞こえますが、音声認識の都合で表記が確定できません）。リスクとコンテキストの変化に応じて、**許可、制限、ブロック、人間の承認の要求**という段階的な制御を、複数の強制ポイントで適用します。対象は Microsoft リソース、サードパーティ、ローカルエージェント（Claude Code と GitHub Copilot CLI から）、そして Global Secure Access 経由のサードパーティの宛先です。

例えば、エージェントは情報を読み取れるが、次のアクションには人間の承認を必要とする、といった設計ができます。

### 5.7 アクションと宛先（Actions and destinations）

dynamic controls のルールでは、保護対象としてリソースだけでなく **アクション**を選べます。発表者は、ここが条件付きアクセスにとって大きな変化だと強調しました。

**Protect sensitive actions** を選ぶと、対応している Microsoft の宛先（Work IQ での操作と Microsoft Entra ディレクトリ）が対象になります。個別の API を気にしなくて済むよう、アクションはカテゴリにまとめられています。

- Identity and access changes（グループメンバーシップ、アプリアクセス、ロール変更を含む。発表者が最も重視するカテゴリ）
- Credential and secret actions
- Security and trust configuration
- Sensitive data access
- Data destruction
- Communication

また、Global Secure Access を経由する場合は、非 Microsoft の宛先を **application categories** で指定できます。例として CRM、finance、cloud computing platforms が挙げられました。

### 5.8 3 つのリスクレベルに対する比例的な応答

デモで構成されたのは、次の対応関係です。

| エージェントリスク | 制御 | 内容 |
| --- | --- | --- |
| Low | Require human approval | 機密アクションは、人が個別の操作を承認した場合のみ実行できる |
| Medium | Restrict actions | 選択した機密アクションのみブロック。それ以外は通常どおり動く |
| High | Block | エージェントのセッション全体をブロック |

Human approval は **Entitlement Management の access package** を使います。条件付きアクセスの承認ワークフロー向けに構成した access package を再利用できます。設定項目は 3 つで、access package、承認者、承認の有効期間です。有効期間の例として 15 分が画面に示されました。

これらの制御は **session control** です。認証自体は許可し、セッション内で何が起きるかを制御します。

### 5.9 エージェントごと・アプリごとにポリシーを作らない

発表者は繰り返し、ポリシーをエージェント別、アプリ別に作らなくてよい点を強調しました。assistive agents の条件では「すべての assistive agents」を選べるので、GitHub Copilot CLI でも Claude Code でも、今後使うものでも、エージェントごとのポリシーを定義する必要はありません。

## 6. デモ・手順

このセッションには、シナリオ仕立てのライブデモが 3 つ含まれています。画面の細部は音声からは確認できないため、語られた範囲で書きます。登場人物は架空のもので、会社名はトランスクリプトでは「Caldova」と聞こえますが、「Caltoba」「Coldova」とも書き起こされており、表記は確定できません。

### 6.1 デモ 1：policy plan を新規作成する（Eitan 氏）

シナリオは、開発チームが製品リリースの準備で機密リソースにアクセスする状況です。ID 管理者の Cecil が、新しい条件付きアクセスポリシーの作成、既存のネットワークアクセスポリシーの移行、そして乱立を増やさずに一貫した強制を維持することを目指します。

1. Entra ポータルの conditional access ブレードを開くと、新しく **policy plans** ビューがある
2. 開発者チーム向けのプランをゼロから作成し、名前を「secure developer access」にする
3. 説明とタグを追加する。タグには developers、phishing resistant MFA、compliant devices を入れた。オーナーには自分が自動的に設定される
4. 共有条件で users and groups を追加する。開発者チームのグループを include に選ぶ
5. 緊急アクセスアカウント（break glass accounts）を exclude に追加する。一度設定すれば、すべてのルールが継承する
6. 最初のルールを追加する。目的は「開発者チームに MFA を必須にする」こと。名前と説明を入力する。ID は共有条件を継承するため再設定は不要
7. 対象リソースに All resources を選ぶ
8. Grant control で authentication strength を要求し、**phishing resistant MFA** を選ぶ。レビュー画面を確認して作成する
9. 同じプランに 2 つ目のルール（trusted device ルール）を追加する。All resources を対象に、デバイスが compliant であることを要求する
10. ルールは **report-only モード**で始まる。影響を評価できるまで運用し、プランに戻って全ルールを一括で On にするか、個別に有効化する。デモではバルク編集で一括 On にする操作を示した

### 6.2 デモ 2：既存ポリシーを plan に統合する（Eitan 氏）

1. 従来の Policies ブレードを開く。開発者が Azure DevOps や GitHub Enterprise などの開発リソースにアクセスする際の既存ポリシーが複数ある
2. 同じ目的（開発者アクセスの保護）を持つ 3 つのポリシーを選び、plan にマージする
3. プレビューでカスタム名を付ける。共通する属性（同じグループ、似た条件や除外）が共有条件にまとめられる
4. 作成すると、新しいルールは Off の状態で作られる。確認と検証をしてから、自分のタイミングで有効化し、古いポリシーを廃止する

結果として、制御を作り直したり開発者のアクセスを妨げたりせずに、3 つのポリシーが 1 つの plan になりました。

### 6.3 デモ 3：高リスクエージェントをブロックする（Sharon 氏、Danielle 氏）

管理者 Lydia が、エージェントのリスクが変わったときに、開発者本人のアクセスを妨げずに適切な制御を適用するシナリオです。

**管理者側の設定**

1. AI agents テンプレートから、新しい policy plan を作成する。名前は「Block Caldova High Risk Agent Access」（表記は音声認識の都合で確定できません）。このプランを 2 つのパートで使う
2. テンプレートには 3 つのルールがある。block assistive agents、block high-risk autonomous agents、block high-risk agent users。デモでは最初の 2 つを使う
3. 共有条件は **Agent risk is high**。プランレベルで 1 回定義し、ルールが継承する
4. autonomous agent 用のルールは、対象が All agent identities。共有の高リスク条件がブロックの適用タイミングを決める
5. ルールを On にする。「変更管理プロセスは済ませてある」との冗談を添えた

**エンドユーザーの状況（autonomous agent）**

6. 開発者 Melissa が「Caldova bug triage agent」にリリースブロッカーの要約を依頼する。プロンプトは「summarize all current release blockers and bugs」で、期待どおり動く
7. Entra ID Protection の risk agents ブレードで、このエージェントが高リスクと判定されていることが確認される。内訳は runtime risk が medium、exposure level が high、blast radius が medium。セキュリティチームがレビューするまで従業員に使わせたくない状況
8. 「What are the current open bugs? Group them by component.」というプロンプトを送ると、エージェントはバグ情報を取得できず、要約を完了できない
9. 管理者に確認すると、エージェントが高リスクに分類されたため、conditional access が要求をブロックしていた。どのルールがブロックし、どの条件に一致したかも確認できる。「何も壊れていない。セキュリティは設定どおりに動作している」と説明された

**assistive agent の保護を追加**

10. Melissa が GitHub Copilot CLI を開発に使う、という設定。同じプランに、新しい policy plan を作らずにルールを追加する
11. 高エージェントリスクの条件はプランレベルで定義済みなので、新ルールが自動的に継承する
12. このルールは、エージェントではなく **users and groups** を対象にする（エージェントがユーザーの委任された権限で動くため）。条件で assistive agents 経由のアクセスに限定する
13. ルールを On にする。2 つのルールが同じ高エージェントリスク条件を共有し、それぞれ適切なアクセスタイプを対象にする

発表者は、この 1 つのルールで GitHub Copilot CLI などの assistive agents を、エージェントごとにポリシーを作らずに保護できると述べています。

### 6.4 デモ 4：dynamic controls でアクションを制御する（Eitan 氏）

シナリオは、開発チームが GitHub Copilot CLI のような assistive agents で製品リリースを進める状況です。「Block high-risk agent access」プランが Melissa の assistive agents 経由のアクセスを対象にするのに対し、こちらはより具体的に制限したい場合の、いわばサブセットです。

1. プランを作成し、名前を「secure agent actions」にする
2. 最初のルールを追加する。内容は「エージェントがディレクトリで機密アクション（グループメンバーシップやアプリアクセスの変更など）を試み、かつエージェントが **low risk** の場合、その操作を人が承認する。それ以外は通常どおり進める」
3. 対象は **All users**（assistive agents は、ユーザーの委任された権限で動く）
4. 保護対象に **protect sensitive actions** を選び、アクションカテゴリを**すべて**選択する
5. 条件を 2 つ設定する。1 つ目は **assistive agents**（All assistive agents）。Melissa 本人が同じ操作を自分で行った場合はこのルールは適用されず、エージェントが代理で行う場合に適用される
6. 2 つ目は agent risk で **Low** を選ぶ
7. 制御は session control の **Require human approval**。access package を選び、承認者と有効期間（例として 15 分）を設定する
8. レビューして作成する。All users、All resources、機密アクションカテゴリ、All assistive agents、low risk、human approval という構成のルールになる
9. 続けて、**medium risk 用のルール**を追加する。名前は「restrict sensitive actions at medium agent risk」。対象は All users、保護対象は sensitive actions（全カテゴリ）に加えて、**application categories**（非 Microsoft の宛先）も選ぶ。Global Secure Access が経路にあるため、サードパーティアプリにも制御が及ぶ。CRM、finance、cloud computing platforms などを選べる
10. 条件は All assistive agents、agent risk は Medium。制御は session control の **Restrict actions**。選択したアクションのみをブロックし、他は動き続ける。保存する
11. 結果として、low は人間の承認、medium はアクション制限、high はブロックという 3 つのリスクレベルと 3 つの比例的な応答が 1 つの plan にまとまる。エージェントごと、アプリごとのポリシーは不要

### 6.5 デモ 5：エンドユーザーが体験する強制動作（Danielle 氏、Sharon 氏）

Melissa は GitHub Copilot CLI を **YOLO mode** で使っています。エージェントが、自分の権限が許す範囲なら何でも呼び出せる状態です。発表者は「だからこそガードレールはツールではなく ID に置くべきだ」と述べています。

1. リリースのセッション、リリースノート、準備状況チェックリスト、ブロッカーの取得を依頼する。読み取りのみの作業で、エージェントはリスクなしと判断され、摩擦はない。3 つのブロッカー、担当者、期限が返ってくる
2. 明日のリリースレビュー担当者と 30 分の枠を探し、Caldova のリリースミーティングを代理で設定するよう依頼する。エージェントはレビュー担当者の空き状況を確認できず、本人に確認してくる。仮の招待状（provisional invite）を送ると、予定表に入る
3. Teams のリリースチャネルに、ブロッカーの状況を共有してほしいという投稿を依頼する。成功する
4. より複雑な依頼として、リリース準備状況の評価全文を Teams チャネルに投稿するよう依頼する。プロンプトの途中に埋もれる形で **local.env ファイルの内容を含める**という指示がある。発表者によれば、シークレットが漏れるのは悪意ではなく、誰もレビューしない長いプロンプトからというのが典型的なパターン。**Microsoft Defender がこれを検知**し、dynamic agent risk のシグナルが上がる
5. .env ファイルを求めないように投稿を修正して再送すると、エージェントは拒否はしないが、**先に承認が必要**だと返す
6. 承認依頼が指定された承認者に届く。承認者（Melissa の上司でもある Lydia）には、Microsoft Security からの action required メールが届く
7. メールでは、誰が要求しているか、どの access package が関係するか、なぜ条件付きアクセスの人間承認が要求を止めたかが分かる。承認と拒否の操作は **My Access** で開く。access package で使っているのと同じ体験
8. 承認者が要求を確認し、理由を入力して承認を送信する
9. Melissa に承認メールが届き、エージェントに Teams の投稿を再度更新させると成功する。.env の中身は投稿に含まれていない
10. さらにセッションを危険にする。認証情報をセッションに貼り付け、OneDrive に保存するよう依頼する。**Purview の data protection ポリシーによって、エージェントに届く前にブロック**される。機密データを AI エージェントと共有させない動作
11. リリースミーティングに関係者 Jordan を追加するため、エージェントに Entra の release reviewers に追加させる。ここまでのセッション内容によりエージェントのリスクは **medium** になっており、medium 用ルールが適用される。グループメンバーシップの変更は機密アクションなので、Entra がブロックし、エラーメッセージに「dynamic conditional access によるブロック」と理由が表示される。Melissa 自身が Jordan を追加することはできる。できなくなるのはエージェント経由の操作だけ
12. 外部コンサルタントに、トラブルシューティングメモ、設定メモ、テスト用認証情報を含む準備状況サマリーを送る依頼をする。ここでも data protection がブロックする。機密情報は、エージェントを通じて組織外に出られない。エージェントのリスクは、さらに高くなっているはずだと語られた
13. 方針を変え、PagerDuty の Caldova に関する未解決インシデントと、最近の GitLab の merge request やパイプライン失敗を比較するよう依頼する。エージェントリスクは **high** になっており、先に設定した high risk assistive agent のブロックルールが作動する。**エージェントのセッション全体が、読み取りアクションやサードパーティツールを含めてブロック**される。Melissa 本人はサインインしたままで、自分の作業は続けられる。止まるのは危険なエージェントセッションだけ

デモの締めくくりとして、low では人間の承認、medium ではアクションの制限、high ではブロックという制御が、**1 つの policy plan のまま、リスクの変化に合わせてリアルタイムに適用された**ことが示されました。

> 補足：リスクが上がった理由は、発表者の口頭の説明（Defender の検知、Purview のブロックなど）に基づいて書いています。各時点のリスクレベルや画面上の細かな表示は、音声からは確認できません。

## 7. 注意点・発表者の気付き

- **変更管理との関係**：policy plan への統合で作られた新ルールは Off の状態で始まります。発表者は、お客様の変更管理プロセスに合わせて、検証、Report-only、有効化、旧ポリシーの廃止の順で進められる点を強調しました。
- **オーナー設定は権限ではない**：plan のオーナーは RBAC を変えず、あくまでガバナンス上の指標です。変更には引き続き conditional access admin が必要です。
- **ユーザー自身の操作とは区別される**：assistive agents の条件があるため、Melissa が自分で同じ操作をする場合には、エージェント向けルールは適用されません。
- **漏えいは悪意とは限らない**：デモで取り上げられた .env ファイルの例のように、長いプロンプトに誰も気づかない指示が埋もれて秘密情報が漏れる、というリスクが語られました。
- **ガードレールは ID に置く**：YOLO mode のように、エージェントが権限の許す限り呼び出せる状況でも、ツール側ではなく ID 側で制御するという考え方です。
- **プレビュー段階であること**：policy plans と assistive agents 向け条件付きアクセスはパブリックプレビュー、dynamic controls もプレビューとして紹介されました。一般提供の時期については、発表では触れられていません。
- **対応範囲**：local agents の対応は GitHub Copilot CLI と Claude Code から始まると語られています。Sensitive actions の対象は、対応している Microsoft の宛先（Work IQ での操作と Entra ディレクトリ）です。

## 8. 利用者にとっての利点

発表で語られた利点は、次のとおりです。

- 共有条件とルールの構造により、ポリシーの乱立を避けながらアクセス制御を拡大できる
- 既存ポリシーを、制御の忠実度を保ったまま plan に統合でき、変更管理に合わせて展開できる
- 100 プラン × 最大 100 ルールの枠組みで、目的別、ペルソナ別に整理できる
- エージェントごと、アプリごとのポリシーを作らなくても、assistive agents 全体を 1 つのルールで保護できる
- リスクレベルに応じて、承認、制限、ブロックを使い分けることで、定型作業を止めずにセキュリティと生産性のバランスを取れる
- エージェントが機密データを組織外へ出す、またはセッションが危険化した場合でも、ユーザー自身の作業は継続できる

発表では具体的な顧客名や導入成果の数値は紹介されていません。

## 9. まとめ

発表の締めくくりでは、次の 3 点がまとめとして示されました。

1. **Policy plans** により、ポリシーの乱立なしにアクセス制御を拡大できる
2. 条件付きアクセスで、エージェントが機密リソースにアクセスする際の制御を、そのエージェントが代理するユーザーとは独立して行える
3. **Dynamic controls** により、生産性を損なわずに、リスクの変化に応じてエージェントのアクションを調整できる

Microsoft Entra Conditional Access が人間と AI エージェントのための統合ポリシーエンジンとなり、AI が仕事の一部になる中で、一貫したアクセス保護を実現するというのが結論です。次のステップとして、発表者は参加者に aka リンクの確認、新機能の試用、フィードバック、ブログのチェックを呼びかけ、今後数週間でさらに更新がある予定だと述べました。
