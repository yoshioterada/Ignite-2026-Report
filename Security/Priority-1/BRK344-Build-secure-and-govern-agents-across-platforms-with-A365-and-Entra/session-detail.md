# BRK344 Build, secure and govern agents across platforms with A365 and Entra

## 1. はじめに

このセッションは、AI エージェントが急増するなかで「エージェントを誰が管理し、どこまでのアクセスを許すのか」をどう統制するかを扱った発表です。前半は Microsoft Entra のエージェントガバナンスを担当するプロダクトマネージャーが、エージェントのアイデンティティ、ライフサイクル管理、アクセス管理、そして新機能の dynamic permissions（動的な権限付与）を、2 つのデモを交えて説明します。後半は NVIDIA のサイバーセキュリティエンジニアが、Agent 365 を使って自社でエージェントのセキュリティを高めている実例を、録画動画のデモとアーキテクチャ図で紹介します。

発表全体の結論は、**エージェントにも「責任者のいる独立したアイデンティティ」を持たせ、アクセスは最小権限・期限付き・意図ベースで与える**ということです。NVIDIA の事例では、エージェントの実行環境に使えるトークンを一切置かない設計が示されます。

## 5. 発表内容の詳細

### 5.1 なぜエージェントに独自のアイデンティティが必要か

エージェントは今、最も速く増えている ID の集団だと述べています。前述の各プラットフォームで作られたエージェントに対して、責任者や必要性、アクセス範囲、人の支援の範囲を超えた動作といった疑問が繰り返し寄せられている、というのが出発点です。

Copilot Studio や Foundry で作成されたエージェント、あるいはエージェントアイデンティティを持つエージェントは、既定で first class identity（第一級のアイデンティティ）を持ち、sponsor と owner も付きます。この 2 つが、エージェントを管理できる「説明責任を持つ代表者」です。

### 5.2 責任者の維持を自動化する Lifecycle Workflows

sponsor や owner は、私たちのような一般ユーザーです。異動や退職があれば、エージェントの責任者がいなくなってしまいます。管理者がエージェントを 1 つずつ確認して引き継ぎ先を探すのは現実的ではないため、Lifecycle Workflows が mover（異動）と leaver（退職）のイベントを検出し、その人が関わっているエージェントを調べます。

自動化の内容は次のとおりです。

- 責任者の上司と co-sponsor に通知する
- 通知だけでは足りないので、sponsorship を上司に自動で移す

sponsor や owner は管理者権限を持たない一般ユーザーであることが多いため、エンドユーザー向けの "managed agent experience" も用意されています。ここでは、エージェントがいつ作られたか、どこに属するか、どの blueprint に属するかといったメタデータを確認し、エージェントの有効期間の延長や sponsor の更新といった操作ができます。

### 5.3 孤立・休眠エージェントへの対処とライフサイクルポリシー

エージェントは最初から sponsor や owner がいない「孤立した」状態で生まれることもあり、非アクティブになったり忘れられたりします。そこで、非アクティブなエージェントアイデンティティを管理するための既定のポリシーが、標準機能として提供されています。ただし、この既定ポリシーでは設定できる項目は限られます。

より細かく制御したい組織向けには、カスタムのライフサイクルポリシーがあります。**E7 ライセンスが必要で、発表では「今週から利用可能」と説明されました。** 設定できる項目は、デモで次のように紹介されています（詳細は 6.1）。

- 特定のエージェントやエージェントプラットフォームをポリシーから除外する
- sponsor に「このエージェントはまだ必要か」を再確認させる頻度
- 非アクティブと判断する期間（既定のポリシーでは変更不可）
- エージェントが最低限持つべき sponsor の数
- 違反時のアクション（無効化、削除、無効化したうえで削除）
- 猶予期間と、孤立したエージェント向けのフォールバック受信者

### 5.4 アクセスパッケージと Agent 365 ポリシーテンプレート

アクセス管理については、「すべて許可すると危険、すべて遮断すると生産性が落ちる」という中間を目指すと述べています。その手段の 1 つが、**エージェントアイデンティティ向けのアクセスパッケージ**（一般提供）です。自律型・支援型のどちらのエージェントにも、意図的で監査可能な、期限付きのアクセスを付与できます。

ポリシーでは、承認者、申請者、アクセスの有効期間を定義します。たとえば、エージェントの sponsor がエージェントアイデンティティに代わって申請する構成も可能です。有効期限を設定すれば、忘れられたアクセスが残らず自動的に失効します。

作成したアクセスパッケージは、**Agent 365 のポリシーテンプレート**に含められます。ポリシーテンプレートは Microsoft Admin Center にあり、エージェントがオンボードされるときに適用するポリシーを定義する場所です。テンプレートにアクセスパッケージを選んでおけば、エージェントをデプロイするときにテンプレートを適用するだけで、アクセスパッケージが割り当てられます。

さらに、**digital teammates（autopilots）向けのアクセスパッケージ**が、今週から public preview になりました。誰が申請できるか、承認が必要か、アクセスをどれだけ維持するかといったポリシーを、同じ形で定義できます。

### 5.5 静的なアクセス定義の限界と dynamic permissions

アクセスを事前に定義する作業は大変だというのが、dynamic permissions を紹介する前提です。開発者もセキュリティチームもコンプライアンスチームもアプリ所有者も、あらかじめ「このエージェントにはこのリソース」と推測して決める必要があります。結果として、エージェントにはアクセスが付くものの、正しいアクセスかどうかは分かりません。

そこで、limited preview として公開されたのが **dynamic access（dynamic permissions）** です。エージェントのアクセスを **ゼロから始め**、特定の意図に対して、特定の期間だけ最小権限を与えます。発表では次の例で説明されています。

- 一般ユーザーの Brianna さんが、Claude や GitHub CLI などでエージェントに作業を依頼する。ここでは「Brianna Helper」と呼ばれるエージェントを例にしている。
- Brianna さんが与えるのは「意図」であり、アクセスが割り当てられる相手はエージェント。Snowflake で何かをしたい場合も、Snowflake のどの権限が必要かを事前に調べる必要がない。
- **管理者が定義するのはアクセスではなくポリシー。** ポリシーは、どのタスクを依頼されたか、必要なリソースと権限は何か、Brianna さん自身がすでにそのアクセスを持っているか、を見る。
- セキュリティリスク（toxic access combination、つまり separation of duties の問題など）の有無も評価する。

評価結果に応じて、次のように振り分けられます。

| 評価結果 | 動作 |
| --- | --- |
| リスクなし | 承認なしで、エージェントに自動的にアクセスが付与される |
| 判断が付かない場合 | 人の承認者にレビューを依頼する |
| 過剰な権限を求める場合（例: 管理者タスク） | 管理者の方針に基づいてブロックする |

**エージェントは、依頼した本人が得られる以上のアクセスを得られません。** つまり Brianna Helper は、Brianna さん以上のアクセスを取得できません。参加希望者向けの案内として、`aka.ms/dynamic permissions preview`（読み上げられた表記）と QR コードがスライドに示されました。

### 5.6 ID JAG：主体を入れ替えてエージェントのトークンを返す

ID JAG は、依頼者とアクションの実行者が異なる場合に、対象アプリケーションへ提示するアイデンティティを切り替える仕組みとして紹介されました（音声認識では "ID Jack" とも表記されています）。

1. Brianna さんが認証し、エージェントにタスクを依頼する（ここで使われるのは人のトークン）。
2. ID JAG が subject を切り替える。受け取るアイデンティティは Brianna さんだが、返されるトークンは Brianna Helper（エージェント）用。
3. エージェントがアクセスを取得し、ポリシーはエージェントに対して評価される。
4. 監査ログには、操作を実行したのが Brianna さんではなくエージェントだと記録される。

これにより、エージェントアイデンティティを持つ意味が実際のログ上に現れる、と説明しています。

### 5.7 過剰権限の検出と自動修復

dynamic permissions のもう 1 つの機能は、すでに付与されているアクセスの検出と修復です。エージェントが Copilot Studio、Foundry、Amazon Bedrock、Salesforce Agent Force、その他のカスタム基盤のどこで作られていても、Snowflake のようなリソースにアクセスしていれば、そのアクセスを検出します。管理者が事前に定義したポリシーと照らして、過剰権限かどうかを判定します。

現時点で対象の SaaS アプリは Snowflake で、今後 Salesforce、ServiceNow などに広げる予定です。意図ベースのアクセスではなく、対象アプリケーションで直接割り当てられたアクセスも対象で、検出、リスク特定、自動修復を大規模に行えると説明しています。

### 5.8 NVIDIA の事例（Chris Burgess 氏）

#### 現状の課題

Chris 氏は、自律型や長時間動くエージェントの認証情報には次の問題があると述べています。

- トークンがエージェントのランタイム環境のすぐ隣に置かれ、プロンプトインジェクションや依存関係の侵害が 1 つあれば、持ち出しや悪用につながりうる。オープンソースを狙うサプライチェーン攻撃もすでに多数見られる。
- エージェントが持つトークンは、そのユーザーに付与されたすべての権限を含む過剰な権限であることが多い。開発者が範囲を絞ったトークンを明示的に発行していなければ、そうなる。
- エージェントの操作と人の操作が区別できないため、独立して監査も失効もできない。

#### Agent 365 による解決

まず、IDP 内にエージェントのアイデンティティを持たせます。リソースの共有も、人と同じ方法でできます。

- ファイルは、そのエージェントに共有する
- カレンダーやメールは、Outlook でエージェントに委任する
- 配布リスト（DL）で管理される共有リソースは、そのグループにエージェントを追加する

エージェントの操作は、ユーザーのトークンだけでなく、エージェント自身のトークンで、自身のアイデンティティのもとで実行されるため、**既定で説明責任が成立します。**

#### アーキテクチャ（2 つのフロー）

Chris 氏はスライドの図で、Microsoft のフローとサードパーティ（ここでは GitHub）のフローを説明しています。

Microsoft のフロー:

1. ユーザーは Teams などを通じてエージェントにメッセージを送る（Outlook など Microsoft のエコシステムからでもよい）。
2. Agent 365 がそれらのアクティビティを正規化し、blueprint 層に設定されたメッセージングエンドポイントへ送る。
3. メッセージは、該当するエージェントのランタイム環境に渡される。
4. エージェントは OpenShell supervisor にトークンの有無を確認する。無ければ、spiffy SVID を提示して、credential broker に認可を求める。
5. credential broker は、エージェントユーザー用の Microsoft トークンが求められていると判断し、authority（ここでは Agent 365）にエージェントユーザートークンの発行を依頼する。
6. 発行されたトークンは credential broker で暗号化され、supervisor には「代役（stand-in）」として返される。
7. エージェントがトークンを使うたびに、outbound proxy を通る。proxy が credential injection を行い、プレースホルダーのトークンを実際のトークンに入れ替えて Microsoft を呼び出し、エージェントにはデータだけを返す。

GitHub のフローも基本は同じで、Microsoft の代わりに GitHub がトークンを発行します。呼び出しは同じ egress proxy を経由し、エージェントにはデータだけが返ります。

Microsoft 側のフローには、**常設の資格情報（standing credential）が 1 つもありません。** すべての認証情報は、定期的にローテーションされる短命な workload identity（spiffy SVID）で、呼び出しのたびに検証されます。仮に盗んで復号しても、5 分以内に使えなくなると説明しています。また、Microsoft が cross-app access を採用していくにつれて、サードパーティの発行者へのアクセスに ID JAG が使われ、このフローはかなり簡素化される見通しだとも述べています。

> 注意：spiffy SVID（トランスクリプトでは "SPIFI" とも表記）という表記は、音声認識の都合で確定できません。ここでは聞こえた綴りのまま記載しています。

#### 2 種類のエージェント

NVIDIA の環境では、このアイデンティティモデルが 2 種類のエージェントに対応していると説明されました。

| 種類 | 特徴 |
| --- | --- |
| digital twin | 共有スコープを持つ。本人の個人情報への委任アクセスを与えると、それを読めるトークンを使える。デモで使われた種類 |
| digital colleague | 複数人が話しかけられるが、共有スコープを持たない |

digital colleague は、仮に開発者がベストプラクティスに反して共有エージェントへ個人情報へのアクセスを与えても、必要なスコープ自体を持たないため漏えいを心配しなくてよい、とのことです。**ランタイムではなく IDP 層で統制できる点が利点**と述べています。

#### 設計の 3 要素

Chris 氏は、概要レベルの要点を次のようにまとめています。

1. ランタイムのアイデンティティを発行する。ここでは SPIFI（音声認識の表記）と呼ばれる仕組みで SVID を各ランタイム環境に与えている。ソフトウェアアテステーション（software attestation）も使え、エージェントがどこで何として動いているかが分かり、どのランタイムがどのアイデンティティを使ってよいかを IDP 側で対応付けられる。
2. 認証情報をランタイム環境から切り離す。**エージェントは使えるトークンを一切持たない。**
3. 外向きの通信をすべて proxy 経由にする。default deny のポリシーで、egress proxy へのルートだけを開く。これによって、ユーザーに影響を与えずにエージェントだけを独立して監査・失効できる。IDP 層でエージェントを失効させれば、broker と proxy への呼び出しがすべて拒否される。10 個、20 個と散らばるシステムのトークンを追いかける必要はなく、1 か所で失効すれば全体に波及する。

#### デモ環境（harness agnostic）

デモは特定のハーネスに依存しない設計で、Nemoclaw エージェントを Hermes ハーネスで動かし、推論には inferencehub.nvidia.com 経由で NVIDIA Nematron Super を使い、ランタイムは OpenShell のサンドボックスだったと説明しています（これらの固有名詞は音声認識の都合で表記が確定できません）。Claude、Codex、Cursor、自作のハーネスでも、OpenShell サンドボックスの内外を問わず同じ authority、broker、proxy を使い、「ハーネスが使えるトークンを持たない」という原則は崩れないとのことです。

#### 同じパターンを自社で再現するには

1. IDP でエージェントアイデンティティを発行できるようにする。Agent 365 では blueprint、agent identity、agent user を作成し、付与するスコープでエージェントの種類が決まる。
2. ランタイム環境ごとに workload identity を与え、エージェントと結び付ける方法を用意する。
3. すべての認証情報を broker 経由にする。「このランタイム環境に、この時点でこのトークンを発行してよいか」を判断するポリシー決定点を置き、返すのは代役のトークンだけにする。
4. 環境からの外向き通信をすべて proxy 経由にする（そうしないとエージェントは動作できない）。

自社に有益かを判断するために、次の 3 つの問いが示されました。

- エージェントは、ランタイムの中に使えるトークンを持っているか
- エージェントの操作は、独立したユーザーとしてログに残るか、借りているユーザーのものとして残るか
- ユーザーに影響を与えず、すべてのトークンを追いかけることなく、エージェントのアクセスを独立して失効できるか

### 5.9 Q&A

1. **ライセンスについて。** 質問自体は聞き取れませんが、Chirag 氏の回答から、ライセンスに関する質問だったと分かります。ライセンス情報は Web サイトに掲載されていると答えました。Entra はその一部で、E7 はセキュリティ製品を含むより広いスイートであるとのことです。詳細なリンクは、終了後に案内すると述べています。
2. **SaaS アプリケーションへのエージェントの認証をどう扱うか。** エージェントは Entra に認証する場合もしない場合もありますが、コネクタを使って、そのリソースにアクセスしているオブジェクトを検出します。管理者のポリシーに基づいて問題のあるエージェントとその原因を検出できるため、認証方式には依存しません。Entra のリソースだけでなく、エージェントがアクセスするあらゆるアプリケーションにエコシステムを広げているとのことです。さらに、cross-app access 用の ID JAG を統合し、エージェントが Entra で認証して、そのトークンをサードパーティのトークンに交換できるようにしたいと述べました（すでに Okta などで見られると言及）。Microsoft は cross-app access の採用を急速に進めており、エージェントの操作の効率化とセキュリティ向上につながるので期待している、という話です。今週 preview が始まったので、Web サイトで dynamic permissions を検索してほしいとのことです。
3. **Entra を使うカスタムアプリケーションにエージェントがアクセスする場合の検出。** 質問を「カスタムアプリケーションへのアクセスをどう検出し、問題のあるエージェントを見つけるか」と受け取ったうえで、質問者の話からオンプレミスの話と理解した様子で、「確認が必要だが、自分の知る限りそれを検出する機能は無い」と答えました。具体的なユースケースは別途相談し、チームの担当者につなぐと述べています（質問自体は聞き取りが不明瞭な部分があります）。

## 6. デモ・手順

### 6.1 デモ 1：Agent 365 のエージェント一覧とライフサイクル管理（Chirag 氏）

冒頭で "let me show you all this in action" と述べて開始されました。

1. Agent 365 のエージェントインベントリ（A365 registry）で、「agents」から「all agents」を開く。このテナントには約 15,000 のエージェントがある。
2. 説明として、Copilot Studio や Foundry で作ったエージェントは公開時にプラットフォームが Entra を呼び出し、登録してエージェントアイデンティティを発行する。Salesforce Agent Force や Amazon Bedrock など他のプラットフォーム、あるいは A365 SDK を統合したエージェントでも、SDK が Entra を呼び出して登録し、アイデンティティを作る。これにより、エージェントは認証・権限取得ができ、IT 管理者から見えるようになり、ガバナンスの対象にもなる。
3. AI 管理者の Melissa さんの立場で、Copilot Studio のエージェント「sales opportunity agent」を開き、メタデータを確認する。このエージェントはアイデンティティを持つため、Entra 管理センターへ移動してさらに調べられる。
4. Entra 側で、エージェントアイデンティティのメタデータを確認する。管理者はエージェントを無効化・削除でき、作成日時や所属する blueprint、付与されている権限、監査ログ、現在の sponsor と owner も見られる。
5. Melissa さんが Lifecycle Workflows を作成して、sponsor の維持を自動化している。このエージェントの sponsor である Emma さんが異動または退職した場合の動きが、次のように説明された。
   - Emma さんの上司と co-sponsor の Amber さんに、職務変更または退職の通知が届く。
   - 同時に、Emma さんの上司 Anton さんが新しい sponsor として自動的に割り当てられる。
6. 次に Lifecycle Workflows からライフサイクルポリシーを作成する。既定のポリシーがあり、非アクティブなエージェントアイデンティティを、スポンサーや owner への通知と合わせて自動的に無効化・削除できる。
7. カスタムポリシーの設定として、次の項目が順に示された。
   - ポリシー名と説明を入力する（複数作成できる）。
   - 対象をすべてのエージェントエンティティにする。エージェントが作られたプラットフォームで除外を指定できる。
   - ポリシールールとして、sponsor がエージェントの必要性を再確認する頻度を決める（忘れられたエージェントへの対処）。
   - 非アクティブとみなす期間を設定する（例として 90 日、120 日、30 日が挙げられた）。
   - エージェントアイデンティティが持つべき sponsor の最小人数を設定する（1 人でよい組織もあれば、複数を求める大規模組織もある）。
   - ルールに 1 つ以上違反すると、エージェントアイデンティティは non-compliant となり、設定したポリシーアクションが適用される。例として、まず無効化し、30 日後に削除する構成が挙げられた。
   - 猶予期間（例では 30 日の通知期間）を設ける。
   - 孤立したエージェントのために、フォールバック受信者（通常は AI 管理者）を入力する。
8. ポリシー作成後、数時間経って処理されたと仮定して、動作が説明された。ルールに違反するエージェントアイデンティティの sponsor または owner にメールが届き、管理用のエンドユーザー画面へ誘導される。対処がなければ、無効化された旨の通知、続いて削除の通知が届く。

> 補足：デモ 1 の Lifecycle Workflows の動作（Emma さんの異動など）は、"let's say" という仮定の形で説明されています。実際のメール画面などを操作して見せたかどうかは、音声からは確認できません。

### 6.2 デモ 2：アクセスパッケージ、dynamic permissions、自動修復（Chirag 氏）

**アクセスパッケージ（digital teammates 向け）**

1. すでに設定済みの、agent users が財務の請求書を照合する（reconcile finance invoices）ためのアクセスパッケージを開く。
2. 「policies」を見ると、agent users（digital teammates）向けに、割り当ての前に承認が必要であること、割り当ては 8 時間で失効することが分かる。
3. 次に、digital teammate の責任者（accountable representative）の立場でエンドユーザーとして、`myaccess.microsoft.com`（"my access.microsoft.com" と聞こえる表記）でアクセスパッケージ（名称は聞き取りが不明瞭）を探し、Melissa helper という digital teammate のために申請する。
4. ポリシー上 8 時間を超える申請はできないため、その期間で申請し、承認者向けにビジネス上の理由（business justification）も入力して送信する。
5. 承認者が承認したと仮定して、管理者の立場で状況を確認する。Melissa helper にアクセスが配信中（delivering）と表示され、更新すると 8 時間のアクセスが割り当て済みになる。

**dynamic permissions（Claude から Snowflake へのアクセス）**

前提として、管理者はテナントに dynamic permissions を設定し、エージェントにアクセスさせたい Snowflake 環境を構成済みです。特定のアプリケーション向けの設定は、アクセスパッケージと同様にカタログ方式で行えると説明されました。デモは Snowflake と Claude を使いますが、依頼者が人でも支援型エージェントでも自律型エージェントでも、同じガバナンスモデルが適用されると述べています。

1. Melissa さんが Claude に、承認済みの CRM データ（Snowflake 上）を使って revenue dashboard を作るよう依頼する。この依頼には、Melissa さんの Claude に設定された Snowflake MCP への認証が必要になる。
2. Melissa さんは人のアカウントでサインインしているが、アクセスは Melissa さんのエージェントに対して確認される。このエージェントには必要なアクセスが無いため、dynamic permissions が、目的の作業に必要な最小権限のアクセスを特定する。
3. Melissa さんがロールを確認すると、dynamic permissions がポリシーを評価し、承認なしで割り当てると判断する。割り当ての期間は短く、画面では 6:50 から 7:20 の 30 分間と示された。
4. アクセス配信後、エージェントが Snowflake で関連するデータクエリを実行し、目的の revenue dashboard が作成される。アクセスが意図に基づき、タスクの完了後に失効することが示された。
5. 次に Melissa さんが、より高い権限を要する別のクエリを試す。過剰な値引き（over discounting）や営業コミッション、契約金額に関する情報を求めるものである。
6. Melissa さんのエージェントにはそのリソースへのアクセスが無いため、dynamic permissions が最小権限のアクセスを特定し、Snowflake の必要なロールへの割り当てを提案する。
7. Melissa さんが確認して割り当てを試みるが、Melissa さん自身もこのリソースへのアクセス権を持たないため、dynamic permissions は割り当て要求を拒否する。重要リソースへのアクセスが統制されていることが示された。

**過剰権限の自動修復（Snowflake）**

1. Snowflake アプリケーションを設定したテナントを開くと、管理者のポリシーに基づいて過剰権限と判定されたエージェントアイデンティティが 111 件（"one-one-one" と聞こえた表記）あることが示される。
2. 詳細を開くと、問題のある割り当て（rogue assignments）の原因が、高権限のアクセスと、管理者の設定に基づく職務分掌（segregation of duties）の競合だと分かる。
3. 各検出には、リスクの文脈が示される。推奨される修復アクションは、自動修復が実行される前に、レビューするか対象アプリケーションで実行できる。
4. 時間が経ち、調査はしたものの手動で修復しなかった場合、自動修復が有効なら、その猶予の後に推奨アクションが自動的に実行される。デモでは、修復が自動的に完了した状態が示された。

## 7. 注意点・発表者の気付き

- **利用状況に関する前提が、ところどころに付いています。** カスタムのライフサイクルポリシーは E7 ライセンスが必要です。アクセスパッケージ（digital teammates 向け）は public preview、dynamic permissions は limited preview です（今週開始）。ライセンスの詳細は、発表では Web サイトの参照を案内するにとどまりました。
- 通知だけでは不十分なので、sponsor の移管まで自動化するという考え方が強調されました。
- アクセスは、少なすぎるとエージェントが動かず、多すぎるとセキュリティリスクになります。事前定義だけに頼らず、意図ベースの付与と過剰権限の自動修復を組み合わせるという方向性です。
- Chris 氏は、エージェントの外向き通信を default deny にして egress proxy だけを許可する必要があると述べています。トークンをエージェントに渡さない代わりに、proxy 経由でなければエージェントは外部へアクションを実行できなくなります。
- カスタムのオンプレミス系アプリケーションに対するエージェントのアクセスは、質疑の時点では検出機能が無いと回答されています（Chirag 氏は確認が必要とも述べています）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 責任者の異動・退職があっても、通知と sponsorship の自動移管でエージェントの説明責任が維持される。
- 休眠・孤立・忘れられたエージェントを、ポリシーに基づいて無効化・削除でき、大規模でも管理できる。
- アクセスパッケージにより、意図的で監査可能な期限付きアクセスを与えられ、忘れられたアクセスが自動的に失効する。
- dynamic permissions により、管理者はアクセスではなくポリシーを定義すればよく、エージェントは最小権限・短時間で必要なアクセスだけを得る。本人以上のアクセスは得られない。
- 対象 SaaS アプリで直接割り当てられた過剰権限も、検出から自動修復まで中央で大規模に行える。
- NVIDIA の設計では、IDP 層でエージェントを独立して監査・失効でき、盗まれた認証情報も 5 分以内に使えなくなる。

## 9. まとめ

エージェントの統制は、(1) 説明責任を持つアイデンティティ、(2) ライフサイクル管理、(3) 最小権限で期限付きのアクセス、(4) 意図に基づく動的な権限付与と過剰権限の自動修復、の順に進める、というのがこのセッションの筋道です。Chirag 氏は、Lifecycle Workflows と E7 のカスタムポリシー、digital teammates 向けのアクセスパッケージ、dynamic permissions をデモで示しました。NVIDIA の Chris 氏は、エージェントに使えるトークンを持たせず、broker と proxy を介して IDP 側で統制する構成を示し、「ランタイムに使えるトークンがあるか」「ログが独立して残るか」「独立して失効できるか」の 3 つの問いで自社の状況を点検するよう呼びかけました。
