# THR878 Secure exfiltration gaps with Microsoft Purview Data Loss Prevention

## 1. はじめに

このセッションは、Microsoft Purview Data Loss Prevention（DLP）を「エンドポイント」「ブラウザー」「ネットワーク」の 3 つの層で組み合わせ、データ持ち出し（exfiltration）の隙間をふさぐ考え方を紹介する 25 分のシアターセッションです。

発表のポイントは、3 つの DLP を **それぞれが得意な場所で守り、互いの死角を補い合うチームとして使う** ことです。USB へのコピー、個人クラウドへのアップロード、BYOD 端末からの SaaS 利用、生成 AI への貼り付けといった具体的なシナリオを使い、どの層がどの試みを止めるのかを順に説明しています。後半では、各シナリオの構成図と、導入を始めるための 4 つのステップも紹介されます。

なお、このセッションでは実機デモは行われていません。スライドと口頭の説明が中心です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR878](https://ignite.microsoft.com/en-US/sessions/THR878)

## 3. 何に関する発表か

テーマは、Microsoft Purview の data security における「layered protection（多層防御）」戦略です。ユーザーが今いる場所、触れているものに応じてユーザーを守り、さらにその層をまたいでデータそのものを守るにはどうするか、という話です。

ファイルや資産がユーザーの環境内を移動するとき、ユーザーはさまざまな層でデータに触れます。発表では、その中心となる柱として次の 3 つを挙げています。

| 層 | 発表での位置づけ |
|---|---|
| DLP for endpoint | OS レイヤーで動く機能。USB フラッシュドライブの利用や、ブラウザーにもネットワークにも触れないコピー＆ペーストなどを扱う |
| DLP for browser | ブラウザー内のクラウドアプリ（管理されたアプリも、管理されていない AI アプリも）に対する、ユーザーのライブセッションを保護する |
| DLP for network | ネットワーク境界での保護。すでにデバイスとブラウザーを越えたデータを捕まえる |

3 つの柱の間には「the void（空白）」があると説明されています。これは、製品の制約ではなく **ユーザーがデータを扱うやり方そのものによって生じる、持ち出しの隙間や可視性の不足** のことです。発表は、各層を使ってこの空白を埋め、データがデバイスやブラウザーから出入りするときの可視性と制御を高める流れで進みます。

発表の流れは次のとおりです。

1. 3 つの層の役割（全体像）
2. 各層が単独で働くシナリオ（エンドポイント、個人クラウドへのアップロード、BYOD）
3. 3 つの層が一緒に働くシナリオ（生成 AI）
4. 構成の詳細（エンドポイント DLP の仕組み、管理デバイス＋未管理 AI アプリ、未管理デバイス＋管理アプリ）
5. 導入の始め方と 4 つのステップ

## 4. 発表者が伝えたいメッセージ

最も強調されているのは、**3 つの DLP は互いに前提ではなく、チームとして働くものだ** という点です。「エンドポイントを入れないとブラウザーは使えない」「ブラウザーを先に入れないとネットワークは使えない」ということはなく、それぞれの得意分野を生かすという考え方です。発表者は "security is a team sport" という言葉で、これを Microsoft の考え方として説明しています。

もうひとつは、悪意のあるユーザーは **一度で諦めない** という前提です。USB のシナリオで発表者は、悪意のあるユーザーは強力なポリシーに一度阻まれたくらいでは諦めず、試し続けると述べています。以降のシナリオもそれぞれ 3 回の試みの形で組まれ、止められた経路を変えて試すユーザーを、層ごとに別の方法で止める流れが示されます。

導入については、すべてを一度に有効にするのではなく、**Purview の成熟度の道のり（maturity journey）に沿って、各領域で自社にとって重要なものから段階的に進める** ことを勧めています。

## 5. 発表内容の詳細

### 5.1 3 つの層と「空白」

DLP for endpoint は、OS レイヤーの基本機能です。例として挙げられたのは、ユーザーが USB フラッシュドライブを使おうとしたとき、そしてコピー＆ペーストのように **ブラウザーにも触れず、デバイスの境界も出ず、ネットワークにも到達しない操作** をしたときです。

DLP for browser は、クラウドアプリ内でのライブセッションを守ります。対象は管理されたアプリと、管理されていない AI アプリの両方です。

DLP for network は、発表者自身が "Hail Mary"（最後の頼みの綱）と呼んだ層です。ネットワーク境界に来た時点で、データはすでにデバイスを出ており、ブラウザーも通り過ぎています。前の 2 つの層をすり抜けたものを捕まえ、可視性と制御を高めます。

### 5.2 シナリオ 1：エンドポイントで完結する従来型のシナリオ

ユーザーが Word や PowerPoint などの資産を、USB フラッシュドライブでデバイスの外へ持ち出そうとするシナリオです。悪意のあるユーザーを想定し、3 回の試みを示しています。

1. **ラベル付きファイルを USB ドライブにコピーする。** DLP for endpoint がコピーをブロックします。この経路はブラウザーやネットワークを通らないため、DLP for browser と DLP for network は関与しません。製品にできないからではなく、資産がその境界をまたがない経路だからだと説明されています。
2. **DOCX を ZIP に名前変更する。** 発表者はこれを「巧妙な手口」と呼んでいます。MIME タイプで判断するため、ファイルが ZIP ではなく本当に Word 文書であることを見抜き、再びブロックします。これもエンドポイント層だけで完結します。
3. **先にネットワークを切断し、USB だけで持ち出そうとする。** エンドポイントにはオフラインでの検出機能があるため、この場合もブロックされます。

発表者は、最初の「USB へのコピー」が主要な対策であり、残りの手段は、ユーザーに本当に悪意がある場合や、環境内に脅威アクターがいる場合に関わってくる、と位置づけています。

### 5.3 シナリオ 2：個人クラウドへのアップロード

Google Drive、個人用 OneDrive、Dropbox などの個人クラウドは、実際にユーザーが持っているものとして扱われています。ここでも 3 回の試みです。

1. **Chrome で drive.google.com にアップロードする。** Purview の拡張機能と、ポリシーのブロックリストに入れたドメインによってブロックされます。許可されていないドメインだからです。
2. **Chrome がだめなら Edge に切り替える。** Edge でもブロックされます。ここでは、エンドポイントが主導しつつ、OS と Edge の連携を使って **セッション層で制御** できます。Edge は Microsoft 自身のブラウザーなので、エンドポイント DLP と Edge がより密に連携できる、という説明です。
3. **Google Drive の同期クライアントを使う。** このアプリのインストールをブロックし忘れていたため、DLP for endpoint はブロックしません。しかし通信がネットワークに出るため、**DLP for network のポリシー** が drive.google.com という FQDN（ドメイン）を見ており、機密情報であることを検知してブロックします。

ユーザーの目には、データをデバイスから出そうとする試みがただ「うまくいかない」と見えるだけです。ネットワークの観点では、第三者の SaaS アプリへ回線越しに行く操作を制御したことになります。発表者は、これはごく一般的な基本シナリオで、他にも多くの選択肢があると補足しています。

### 5.4 シナリオ 3：BYOD・委託先・ベンダーの保護（DLP for browser）

「自分で管理できないデバイス上のデータをどう守るか」という、よくある要望へのシナリオです。契約社員やベンダー、BYOD（私物デバイス）のように、管理されたデバイスを提供していない場合を想定しています。ユーザーは個人デバイスから Salesforce にアクセスしようとします。

発表者は、この方式の特徴を次のように述べています。

* エージェントは不要
* デバイスの登録（enrollment）は不要
* このシナリオでは、モバイルアプリケーション管理（MAM）も不要
* 必要なのは、**Edge for business の利用を要求するポリシー** だけ。ユーザーは職場プロファイルで Edge にサインインするだけでよい

試みは次の 3 回です。

1. **個人デバイスの Chrome で Salesforce にアクセスする。** 「組織は Edge の利用を要求しています」というメッセージが出て、Edge に誘導されます。
2. **Edge で Salesforce の顧客データをダウンロードする。** 制御下のセッション内なので、ダウンロードはブロックされ、理由を説明するポップアップが表示されます。
3. **データをブラウザーの外、自分のアプリ（発表者の言う「秘密のスパイ文書」）にコピー＆ペーストする。** 制御下のセッションで、信頼されていないデバイスであるため、コピーがブロックされます。

未管理デバイスでは、DLP for endpoint も DLP for network も効きません。どちらも **登録されたデバイス上のエージェントが必要** だからです。このシナリオでは、ブラウザーだけに頼っています。

この層ではほかにも、次のようなことができると触れられています。

* 管理デバイス上の AI アプリで、ユーザーが機密データを入力している最中に、ライブセッションで保護する
* 未管理デバイスについては、管理されたアプリのエクスペリエンスを制御する（詳細は発表では語られていません）
* ブラウザー内のスクリーンショットを制御する。**これは Edge for Business との統合を通じて、現時点では preview** と説明されています。ユーザーがブラウザー内の機密情報をスクリーンショットで持ち出すことを、以前ほど心配しなくてよくなる、という位置づけです。

### 5.5 シナリオ 4：生成 AI（3 つの層が一緒に働く）

ここで 3 つの層を組み合わせます。発表では ChatGPT が例ですが、「ChatGPT は自社が懸念する AI に置き換えて考えてよい」と述べられています。ただし、これらの統合には、特定の AI アプリケーションに関する要件があると断っています。主要なものであれば、このシナリオは当てはまるはずだという説明です。

1. **Web 経由（chatgpt.com）で、プロンプトに機密情報を貼り付ける。**
   DLP for endpoint が、OS レイヤーでコピー＆ペースト操作自体をブロックできます。ブラウザーに貼り付けるかどうかは関係ありません。さらに DLP for browser では、Edge の中で **より細かい粒度のアクション** を制御できます。必要なら Edge 側でもコピー＆ペーストをブロックし、プロンプトへのファイルアップロードもブロックします。ドキュメントごとアップロードして制御を回避しようとしても止められます。この試みでは、エンドポイントとブラウザーが役目を果たすため、ネットワークは関与しません。
2. **ChatGPT デスクトップアプリをインストールして使う。**
   エンドポイントは、許可されていない実アプリ（thick application）からの機密情報のコピー・ペーストを制御できます。しかし、ユーザーが機密情報を開いて **読みながら手で打ち直した場合**、DLP for endpoint はキーストロークを監視しておらず、何を入力したか分かりません。ブラウザーの外なので、DLP for browser にも見えません。そこで DLP for network が、ChatGPT の API 呼び出しに流れる通信の中で、打ち直したテキストを捕まえてブロックします。
3. **Office アドインを使う。**
   発表者は「多くの人があまり考えない試み」と呼んでいます。組織によってはアドインを禁止しますが、生産性向上のために許可する顧客も多くあります。ただし、作られるすべての AI アドインを把握することはできません。DLP for endpoint から見えるのは Word.exe が動いていることだけで、その中でサードパーティのサービスが動いて呼び出しをしていることは見分けられません。Word をブロックするわけにはいかないので、通信は許されます。ブラウザーの外のため、DLP for browser も無関係です。ここで DLP for network が、アドインによる API 呼び出しの通信を見てブロックし、リスクを大きく下げられます。

発表者は、ここまでの内容を、3 つの層を **別々に使った場合にできることのメニュー** であり、それ以上に **組み合わせた場合にできること** を示すものだと整理しています。

### 5.6 導入の進め方（成熟度の道のり）

3 つは独立して動かせます。1 つから始め、あとから追加できます。発表者は、Purview の maturity journey の一部として **各領域で一歩ずつ進める** ことを勧めています。重要なものに絞り、すべてを一度に有効にしないという考えです。

### 5.7 構成図 1：DLP for endpoint の仕組み

ここから「少しオタクな」内容として、構成の参照図が紹介されます。最初の図は、先のシナリオで見たエンドポイント DLP の内部です。図は、アクティビティ、コンテンツの評価、ポリシーに基づく判断、強制（enforcement）という流れで説明されています。

* **アクティビティ：** 先のシナリオに対応する操作。例はクリップボードへのコピーなど。
* **コンテンツの評価：** Purview のクラウド上のポリシーからデバイスに同期された **sensitive information types** を使う。
* **判断：** ポリシーに基づく判断。例では Office アプリが制限対象なので、他の場所への貼り付けを許可しない。
* **強制：** 右側。**Defender AV との統合** によって、デバイス上で実際に強制する層を持つ。

強制の方法には、block と block with override があります。これらはユーザーに実際に影響する厳しい強制です。成熟度の道のりでそこに進むときには注意が必要だと述べています。一方で、**audit や allow のままずっと留まるべきではない** とも言っています。まず audit などを使って、DLP ポリシーが各シナリオにどう影響するかを確認し、確信が持てたら block に移すという流れです。図には他にも細かな情報があり、スライドは後で入手できる見込みだと話しています。

### 5.8 構成図 2：管理デバイス＋未管理 AI アプリ

図の左端が Purview で、ポリシーを作成し、判断を決める **コントロールプレーン** です。そこからデバイスに流れます。このシナリオのデバイスは **Microsoft Intune** で管理され、対象は ChatGPT です。

Intune による管理で、ブラウザーごとに挙動を制御できます。先ほどの未管理デバイスでは Chrome を許可しませんでしたが、管理デバイスでも同じことができます。ユーザーは Chrome をそれ以外の用途（発表者の例は猫の写真）には自由に使えます。ビジネスの用事になったら Edge に移り、そこで **セッションを制御できる** ようになるため、chatgpt.com へのアクセスを許可し、制御を置けます。

ネットワーク側は、少し構成が増えますが、**Entra GSA のエージェント** を起点にします（音声認識では "enter GSA" と聞こえる箇所があります）。流れは次のとおりです。

1. エージェントをデプロイする
2. どの種類のトラフィックを気にするか、それがどこへ流れるかを判別するポリシーを作る
3. ブラウザーでもアプリでも、通信は Entra GSA クライアントを通り、Purview に「何を探すべきか、何が重要か」を問い合わせる
4. Purview が答えを返し、最後に判断が出る。ブロックなら Entra GSA にブロックを指示し、問題がなければそのまま通す（発表者の例は Amazon や Target での買い物）

一度設定すれば、あとは意識する必要がないと説明されています。

### 5.9 構成図 3：未管理デバイス＋管理アプリ

先のシナリオの逆で、デバイスを管理していない場合です。特定のブラウザーを使うよう強制できないため、**Entra の conditional access と、その Microsoft Purview および Defender for Cloud Apps との統合** によって、セッションを Edge の職場プロファイルに誘導します。

* Windows にはすでに Edge があり、Mac の場合は Edge をダウンロードして職場プロファイルにサインインするだけ
* その後はネットワークの場合と同様に、フローの中で判断が行われ、最後にアクションが出る
* 職場プロファイルを使っていなければ、ブロックされ、Edge for Business を使う必要があるとのメッセージが表示される
* 許可された場合はそのまま続行できる

### 5.10 始めるために

発表者は、始める前に確認すべき次の点に触れています。

* **ライセンス：** 高度な分類子（advanced classifiers）や DLP for endpoint の機能には、必要なライセンスがある（詳細は発表では語られていません）
* **新しい発表：** DLP for browser の一部の機能と、DLP for network について。**DLP for network が Entra GSA 連携で従量課金（PAYGO）ではなくなった** と説明されています
* **ロール：** 展開と構成に通常必要なロールがある（具体的な内容は発表では語られていません）

## 7. 注意点・発表者の気付き

* **強制レベルの選び方：** block と block with override はユーザーに直接影響します。成熟度の道のりでそこへ進むときは慎重に。ただし audit や allow に留まり続けるのは望ましくない、というスタンスです。
* **各層には死角がある：** エンドポイントは入力したキーストロークを監視しないため、打ち直しは見えません。Word.exe 内の Office アドインの通信は、エンドポイントからは見分けられません。ブラウザー DLP はブラウザーの外のアプリには効きません。だからネットワーク層が必要になります。
* **未管理デバイスの制約：** エンドポイント DLP と DLP for network は、登録済みデバイスのエージェントが必要なので使えません。未管理デバイスではブラウザー（Edge for Business）に頼ります。
* **設定漏れの例：** Google Drive の同期クライアントのインストールをブロックし忘れたため、エンドポイントでは止まらず、ネットワーク層が受け止めた、というシナリオでした。
* **AI アプリ側の要件：** これらの統合には、対象となる AI アプリケーションに関する要件がある（詳細は発表では語られていません）。
* スクリーンショット制御は **preview** です。

## 8. 利用者にとっての利点

発表で語られた効果は、次のとおりです。具体的な顧客事例や数値は、このセッションでは紹介されていません。

* **データの出入りに対する可視性と制御の向上：** 空白をふさぎ、リスクを軽減できる。
* **多層防御：** 1 つの層がすり抜けられても、別の層が止められる。
* **BYOD や委託先の保護：** エージェントも登録も MAM も不要で、Edge for Business の利用を要求するだけで制御できる。
* **AI の経路への対応：** Web、デスクトップアプリ、Office アドインの 3 つの経路を、それぞれ異なる層で止められる。
* **段階的な導入：** 3 つの DLP は互いに依存せず、1 つから始めて追加できる。
* **コスト面：** DLP for network が Entra GSA 連携で従量課金ではなくなった。

## 9. まとめ

DLP for endpoint、DLP for browser、DLP for network は、それぞれ OS、ブラウザーのセッション、ネットワーク境界という別の場所で働き、互いの死角を補い合います。USB、個人クラウド、BYOD、生成 AI のどのシナリオでも、1 つの層をすり抜けた試みが別の層で止められる様子が示されました。

導入は、1 つの層から始めて、成熟度に応じて広げていけます。持ち帰る 4 つのステップは、デバイスのベースライン作成、Edge for Business による AI ギャップの解消、BYOD の保護、そして DLP for network による取りこぼしの防止です。
