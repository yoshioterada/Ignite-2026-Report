# BRK319 Find and fix code vulnerabilities faster with Codename MDASH

## 1. はじめに

このセッションは、Microsoft Security のマルチモデル型エージェント型スキャンシステム「Codename MDASH」を紹介する 45 分のブレークアウトです。MDASH はプライベートプレビュー中で、Microsoft 社内の開発と一部の顧客がすでに使っています。MDASH は、100 を超える専門 AI エージェントが協調して、コードの脆弱性を見つけ、検証し、優先順位をつけるシステムとして説明されました。

構成は、コードセキュリティの状況の変化、MDASH の仕組み、Defender ポータルと開発者環境を使った一連のデモ、導入時の運用ガイダンス、Q&A の順です。早期顧客と数か月にわたって評価を進めた登壇者の経験から、既存の SAST との使い分けや、モデル選定、コスト管理、スケールの考え方まで語られています。

要点は 2 つあります。**MDASH はモデル単体ではなく、モデルを取り巻くシステムで差別化していること**、そして **SAST などの既存ツールを置き換えるものではなく補完するものであること**です。

## 5. 発表内容の詳細

### 5.1 コードセキュリティの変化

冒頭で John 氏は、AI モデルが断片的なコードだけでなく、アプリケーション全体を書けるようになっている点に触れ、同じように脆弱性を攻撃することも可能になっていると述べました。それを示す例として、ニュースや研究が日々出ていることと、前述の FreeBSD の事例を紹介しています。

### 5.2 Codename MDASH とは

Microsoft Security の**マルチモデル型エージェント型スキャンシステム**です。100 を超える専門 AI エージェントのチームとして働き、悪用可能な脆弱性をエンドツーエンドで発見し、議論し、検証します。開発したのは、DARPA の AI Cyber Challenge（2,950 万ドル規模）で優勝したメンバーを含む、Microsoft の自律型コードセキュリティチームです。発表では、研究プロジェクトにとどまらず、すでに Microsoft のエンジニアリング内部と一部の顧客で使われていると説明されています。

#### 4 つのフェーズ

| フェーズ | 内容（発表での説明） |
| ---- | ---- |
| Preparation（準備） | コードを取り込み、攻撃対象領域（attack surface）をマッピングする |
| Scan（スキャン） | 専門の auditor エージェントが、候補となる指摘（脆弱性の可能性）を提案する |
| Validation（検証） | 2 つ目のエージェント群である debater エージェントが、各指摘に対して賛成と反対の両方の立場で議論する |
| Dedupe（重複排除） | 同じ行や同じ領域など、重なっている指摘をまとめる。1 つの修正で複数の問題が解決する場合などを想定し、重要な指摘に絞り込む |

各ステージでは、異なる役割のエージェントが複数のモデルにまたがって動作します。これが「マルチモデル」という名前の由来です。

#### モデルの構成

MDASH は、次の種類のモデルを組み合わせています。

* フロンティアの推論モデル（最先端の重い推論を担う）
* 大量に回す処理向けの、コスト効率の良い蒸留（distilled）モデル
* 独立した対抗（counterpoint）モデル

検証フェーズでのモデル間の不一致それ自体が 1 つのシグナルです。auditor が指摘した問題を debater が反論できなかった場合、結果の信頼性が高まる、という考え方が説明されました。

各パイプラインには、固有の役割、プロンプトの方針（prompt regimen）、ツール、停止基準があります。エージェントは、過去の CVE とそのパッチを深く調べて構築されており、それぞれ独立して動いたのち、最後に 1 つのレポートにまとめられます。

### 5.3 顧客と Microsoft 自身での成果

#### プライベートプレビューの顧客から

John 氏は、プライベートプレビューに参加している顧客からのフィードバックとして、静的スキャナーや顧客が評価した他のスキャナーが見逃した脆弱性を MDASH が見つけることに長けていると紹介しました（会場で参加者に挙手を求めたところ、数人が使っていました）。

例として挙がったのが **BOLA（Broken Object Level Authorization）** です。認証済みのユーザーが、見てはいけないデータにアクセスできてしまう脆弱性で、Web アプリにログインした人が他の顧客の請求書データを見られる、といった状況を説明しています。こうした複雑なロジックの欠陥を、MDASH は横断的に推論して見つけるのが得意だと説明されました。

#### Microsoft 自身のコード

Microsoft 自身のコードにも MDASH を使っており、機密性の高い領域で、実際に悪用可能な脆弱性を見つけているとのことです。Use-after-free や double free などのメモリとロジックの問題が例に挙がりました。発表では、リモートコード実行の脆弱性を 2 件見つけた例が紹介されています。どちらも、特別に細工したパケットで、メモリ利用まわりの複雑なロジックの欠陥を突くものです。MDASH がメモリの割り当てと解放のロジックを追い、競合状態（race condition）とメモリ解放処理の問題を特定したことで発見できた、と説明されました。連鎖する複雑な問題が MDASH の狙いどころだとしています。

#### 月次更新での CVE 数

MDASH のスキャン結果は、毎月の更新で修正する CVE の総数にも貢献しています。グラフでは、初夏頃から MDASH を使い始めてから、発見される CVE が急激に増えています。

* 今年の 10 月に対処した CVE：**1415 件**
* 2025 年全体で修正した CVE：**1273 件**（会場への問いかけに対する答えとして述べられた数字です）

John 氏は、今年の 10 月 1 か月で、2025 年全体を合わせた数より多くの CVE を修正したことになる、と述べています。

> 補足：トランスクリプトでは、会場に「200 件？」と聞いたあとに「1273」と答える流れになっています。数字は音声のまま記載しており、音声認識の都合で確定できません。

### 5.4 デモの概要（Caldova）

Henrique 氏によるデモは、4 つのペルソナ（merchant owner、attacker、security team、application developer）を切り替えながら進みました。詳細は 6 章に記載しています。デモで示された主な機能は次のとおりです。

* Defender の設定画面で GitHub / Azure DevOps などのソースコード組織を接続する
* Exposure management の中にある MDASH から、リポジトリごとにスキャンを実行する
* スキャンには standard プロファイルと MAI cyber プロファイルの 2 種類がある
* 出力は 3 種類：SARIF ファイル（JSON）、HTML レポート、ポータル
* ポータルでは、重大度や信頼度（confidence）で絞り込み、CWE ID、エージェント間の検証の議論、再現に必要なコンテキスト（evidence）を確認できる
* Defender ポータルから PR を作成し、セキュリティ担当者と開発者の間をつなぐ
* 開発者側では、MDASH の結果の取得、スキャンの開始、コンテキストの取得ができ、出力に対して実行できるスキルも用意されている。デモでは GitHub Copilot 経由で修正を適用している

セキュリティ担当者は開発者のワークフローの中で作業する必要がなく、処理、レビュー、マージなどの工程は開発者の手元に残る、という点が強調されています。

### 5.5 運用ガイダンス（Henrique 氏）

#### SAST との使い分け

* SAST やシークレットチェックなどは、**ゲートとして開発者の近くに置き、PR ごとに**、ルールとパターンマッチングで評価するもの
* MDASH は**探索的な評価**で、アプリケーションに大きな変更があったとき（バージョンの変更、リスクのチェックポイント、あるいは MDASH で新しいモデルが使えるようになったとき）に実行する

「SAST と MDASH は同じ仕事を奪い合うものではない」というのが発表者の説明です。

#### スキャンの進め方

1. すべてのリポジトリを一度にスキャンしない。ビジネスに重要で、外部に公開されているアプリケーションを優先する
2. トリアージの担当者と、修正を行う余力（remediation capacity）を用意しておく。開発者は余裕がないため、指摘を優先順位づけして渡すことが有効
3. MDASH は探索的に動く。「100 人の専門家が部屋でコードを調べているようなもの」で、日によって異なる経路をたどるため、実行ごとに異なる指摘が見つかりうる
4. 指摘は長いリストになりうるので、脅威モデリング、デプロイのアーキテクチャ、有効な制御の確認、アプリケーションのドキュメントなどのコンテキストを追加し、Copilot の助けを借りて SARIF の出力に適用して再優先順位づけする。大量の脆弱性から「対処できる脆弱性」に絞るための方法として説明されました

#### カスタムハーネスに関する注意

Henrique 氏は、顧客がカスタムのハーネス（オープンソースも含め多数あるもの）を使っていることに触れ、取り組み自体は歓迎する一方で、リスクがあると述べました。パイプラインのどこかに変更を入れると、結果に重大な影響が出うるからです。例えば、重大度が High や Critical の脆弱性をすべて無視させるファイルを仕込まれた攻撃を想像してほしい、と話しています。**指摘が少ないことが、対処すべき指摘を見つけられていることを意味するとは限りません。**

また、モデルだけを見るのではなく、周辺のシステムも見るべきだとして、Foundry での推論時にどんなコンテキストが渡るかを把握し、高い忠実度（high fidelity）を保つことを求めています。各指摘には修復項目（remediation）が付くため、それも高い忠実度である必要があります。

#### モデルと Foundry

* MAI Cyber モデル：この日に紹介された MAI Cyber One（音声認識の都合で表記が確定できません。後半では John 氏が「MAI Cyber 2」「MAI Cyber 2.0」とも述べています）が MDASH の一部として使えると説明されました。短い実行でも優れた結果が出ており、大きなモデルと同等の性能を、はるかに低い価格帯で提供する小さなモデルだという説明です。
* 課金：発表時点で、MDASH 自体はサービスとして課金されていません。推論は Foundry で動かします。
* 接続方法：マネージド ID または API キーで Foundry に接続できます。セキュリティの面から、マネージド ID での接続が推奨されています。
* コスト管理：モデルごとの推論の請求内訳を確認できます。Azure Foundry 側で上限を設定する必要は必ずしもありませんが、設定は可能です。ただし、実行の途中で停止すると、完全な結果は得られません。

#### スケール

Azure Foundry の TPM を引き上げることで、並行処理数が増えます。小さなリポジトリから始め、慣れてきたら TPM を引き上げる進め方です。顧客の中には、2 本の同時スキャンから始めて 20 本の同時スキャンまで拡大した例があると紹介されました。拡大のペースは組織の判断に任されています。

### 5.6 始め方（John 氏）

#### 役割分担と、開発者に渡す情報の質

誰が MDASH を使い、誰が修正を適用するかを決めておきます。組織によって、1 人で兼ねる場合もあれば、別々のチームの場合もあります。SOC やセキュリティ担当と、アプリケーション開発やアプリケーションセキュリティのチームの間の可視性のギャップを埋めるのが狙いです。

開発者の目の前に届くものは、高い忠実度で、適切にレビューされており、使っているシステムに合ったコンテキストを含み、修正コードの提案が付いている必要があります。デモで見たように、スキャンの画面、GitHub、Copilot で使うスキルを通して、この情報が開発者に届きます。開発者は、脆弱性とその影響を理解しながら、提案された修正コードを検証します。さらに、修正がアプリを壊さないかをテストすることと、PR がコミットされる前に人が確認する（human in the middle）ことも勧められています。MDASH は、ワークフローの中で解決するのに必要なエクスポージャーと影響の情報を提供します。

#### Perception との連携

John 氏は、Project Perception のチームのスライドを借りたと断ったうえで（冗談めかして「cone of silence」と言っています）、MDASH の結果を、Perception の中の Web アプリペンテスト用エージェントと統合していると述べました。見つかった問題の可能性にエージェントを誘導し、Web ペンテストエージェント側で検証できるようにするためです。Perception の機能と MDASH を併用する場合に重要になる、と説明されています。

#### GitHub との連携（早期プレビュー）

GitHub Advanced Security との統合が、現時点では早期プレビューの段階で、まだ利用できないと明言されました。GitHub Advanced Security では、次のように複数の選択肢でスキャンできるようになる、という紹介でした。

| スキャン | 位置づけ（発表での説明） |
| ---- | ---- |
| Fast scans | 開発環境でコードを書いている最中にチェックする |
| Thorough scans | プルリクエストの工程で実行する。CodeQL や、軽量な AI スキャンレビューが含まれうる |
| Deep scan | **MDASH を搭載**。GitHub Advanced Security の体験の中で MDASH の結果が得られる |

#### 成功の鍵

1. **小さく始める**：今すでに静的解析などで何をスキャンしているかを確認し、それを MDASH のスキャン対象を広げる進め方の目安にする
2. **オーナーを把握する**：スキャン対象アプリケーションの所有者を把握し、アプリケーションセキュリティや開発のチームに、スキャンを始めること、結果をレビューして優先順位をつけることを事前に合意しておく。Critical や High の脆弱性は、取締役会への通知が必要になりうるため、誰に連絡するかを知っておくことが重要
3. **スキャンを計測する**：所要時間は、コードの複雑さとサイズに依存する。また、指摘の数（コードの衛生状態、hygiene）にも依存する。指摘が増えるほど、debater エージェントによる検証にかかる時間が増えるため。この計測から、スキャンの頻度（メジャーリリースごと、MAI Cyber 2 のような新しいモデルが出たときなど）を決める
4. **優先順位づけと修正の検証プロセスを固める**：開発チームが、必要な情報とリソースを持ち、本番前に修正をテストできるようにする

#### プレビューへの参加方法

MDASH はプライベートプレビューで、申し込みは審査されます。スライドのリンク（読み上げでは「aka.ms/ai-driven-scanning-harness」と聞こえます）のフォームに記入し、さらに自社のアカウントチームに、そのリンクから申し込んだこと、MDASH のプレビューに推薦してもらうための手続きを進めてほしいことを伝える必要があります。

### 5.7 Q&A

登壇者 2 人が、よくある質問を互いに質問する形式で進みました。

**Q1. MDASH に入れるモデルはどう選んでいるか。**
品質とコストのバランスを、エンジニアリングチームと継続的に評価して決めています（一部、聞き取り不明瞭な箇所があります）。モデルごとに強みが異なるため、脆弱性の発見と、その根拠への反論（challenge）の両方に向けて、補完的なモデルを選びます。目標は、最も安価、あるいは最も強力な単一モデルではなく、自信を持って示せるセキュリティ上の価値と結果です。ハーネスの進化に合わせて、常に見直しています。

**Q2. SAST / DAST / シークレットスキャンのツールを、MDASH にすべて置き換えてよいか。**
置き換えません。顧客からの最多の質問の 1 つだとして、MDASH は既存のコードセキュリティツールを**補完する**ものだと答えています。静的解析などは残し、MDASH は連鎖するような脆弱性を含む深い分析に使います。日常的に回すものではなく、歯磨き（SAST）と歯医者の診察（MDASH）の関係だと繰り返しています。

**Q3. 対応する言語は何か（質問者の例：Rust、PHP、Kotlin、Java、TypeScript）。**
詳細はオンラインのドキュメントに記載されています。大きく 2 つに分かれ、専門のサブエージェントがある言語として Java、C、C（原文のまま。音声認識の都合で表記が確定できません）、C# が挙がりました。より汎用的なエージェントが対応する言語として、Go、PHP、Ruby、Kotlin が挙がりました。Rust と TypeScript については、この回答では触れられていません。

**Q4. コードはどう保護されるか。**
* スキャンは、テナント内で暗号化によって保護された、ソースコードの一時的なコピーに対して行われる
* モデル推論は、Microsoft がホストするサービスを使い、一般向けの消費者向け AI サービスは使わない
* 推論の処理環境は一時的（ephemeral）で、ジョブの完了時に破棄される
* 顧客のコンテンツがモデルの学習に使われることはない
* 保存場所、処理場所、推論は、テナントの場所と Azure AI Foundry のモデル構成に依存するため、どこで行うかを制御できる

## 6. デモ・手順

デモは Henrique 氏が行いました。題材は、ロボットを使った薬局の配送サービス「Caldova」で、顧客がオンラインで注文して、近くから配送を受ける設定です。デモでは、merchant owner、attacker（Henry the Hacker）、security team、application developer の 4 つの視点を切り替えます。録音は音声のみのため、画面の細部は語られた範囲に限ります。

### 6.1 正常な状態の確認（merchant owner として）

1. merchant owner としてアプリケーションにサインインする。施設は稼働中で、すべて正常に動いている。薬局が停止すると、サービスの中断、収益の損失、健康への影響が出うると説明されている
2. 注文を 1 件選ぶ（Dana の注文）。購入品目、支払い金額、領収書などが正しく表示される
3. ダッシュボードにある AI サポートエージェント（チャット）を開き、ある注文の状況を尋ねる。エージェントはツールを呼び出し、データベースを参照して答える。期待どおりの結果が返ってくる

### 6.2 攻撃（Henry the Hacker として）

1. 攻撃者のペルソナに切り替える。ユーザー名、パスワード、merchant ID、顧客 ID など、アプリからの情報は一切持たない状態で、Caldova.com に対してエージェントによる攻撃を実行する
2. 攻撃は成功する。HTML のレポートに、2 つの精密な失敗点（脆弱性）が示される
   * 1 つ目：merchant としてサインインしていないのに、エージェントが施設 ID を発見し、toggle エンドポイントに認証なしでリクエストを送った。この脆弱性は完全に悪用された
   * 2 つ目：認証済みの状態で別のプロンプトを注入し、バックエンドが別の facility ID を持つそのプロンプトを信頼した。これが、John 氏が説明した BOLA の問題を引き起こした
3. 2 つの脆弱性を連鎖させ、正常に動いていた組織を変更できた。レポートでは、失敗した経路が緑（正しい認可パスで、悪用されなかったもの）、成功した 2 件が青で示されている
4. 影響を確認する。アプリケーションは停止され（画面では緑で表示）、ダウンタイムと収益の損失につながる。さらにエージェントの 2 番目のステップで、顧客の支払い済みの注文を返金済みに変更できた。金銭的な影響とデータの露出である

### 6.3 MDASH の設定とスキャン（security analyst として）

1. Defender の設定（Settings）で、GitHub や Azure DevOps などのソースコード組織を接続する。ここでは GitHub を使う
2. リポジトリの接続後、Exposure management に進む。MDASH はこのノードの中にある
3. MDASH の画面で Foundry を設定する（MDASH の推論に Foundry を使う）。接続済みのソースコードコネクタを確認し、スキャンを管理できる
4. Caldova のアプリケーションを構成するリポジトリ（バックエンド、フロントエンド、エージェントのリポジトリ）が表示される。ここから merchant portal を選んでスキャンを開始する
5. プロファイルは、standard と MAI cyber の 2 種類
6. ステータスページで、リポジトリ情報、そのリポジトリの関数の数、AI により検証された指摘の数、スキャン時間、これまでに消費したトークン数を確認する
7. 出力は 3 種類：SARIF ファイル（JSON）、HTML レポート、ポータル。ここではポータルを使う
8. Security recommendations で、重大度と信頼度で絞り込み、対象のリポジトリの脆弱性を表示する。「missing authentication for a critical function」（重要な機能に対する認証の欠落）が見つかる
9. 詳細を開き、信頼度と CWE ID を確認し、さらにエージェント間で行われた検証（debate）を見る。高い忠実度の指摘だという結論に至った議論である
10. Evidence（再現に必要なコンテキスト）を確認する。Henry the Hacker の攻撃で、これらの条件は満たされていた

### 6.4 Defender ポータルから PR を作成する

1. 優先順位をつけ、修正する指摘を決めたら、Defender ポータルから PR を作成する。セキュリティアナリストと開発者の間をつなぐために作った機能で、アナリストは開発者のワークフローの中にいる必要がない
2. 修正案を提案すると、PR に、脆弱性、リポジトリ、修正が必要なファイル、該当する行、提案された修正が含まれる。開発者はこれを確認して引き取れる
3. 開発者は GitHub で、コードの変更の理解、差分のレビュー、修正の適用ができる
4. このデモの修正は、認証を customer ID と facility ID に紐づける新しいチェックの追加で、これにより BOLA が悪用できなくなる

### 6.5 開発者のペルソナで修正を適用する

1. 開発者として、MDASH の結果を取得し、スキャンを開始し、コンテキストを取得できる。出力に対して実行するスキルも用意されている
2. 最初の脆弱性に対して修正を適用する。チェックを通しながら、GitHub Copilot を通して適用される。Python ファイルの該当行で特定された CWE がすべて修正された
3. 同じ手順を 2 つ目の脆弱性にも適用する。スキルが脆弱性と提案された修正を理解して、適用する
4. アプリケーションを再ビルドする。変更はローカルのものであり、組織にあるゲート用の仕組み（承認ステップ）はそのまま残る。コードの変更から本番稼働まで、すべての承認ステップを通る
5. ソースコードからライブのアプリケーションを再構築し、Caldova が正常に動作する。コンテナはすべて起動している
6. Henrique 氏は「Henry the Hacker が再度試しても失敗する」と述べ、前に実行したすべてのエクスプロイトが閉じられたと説明している。修復のために必要な行以外は変更していない

> 補足：6.5 の最後の部分は、トランスクリプトでは「もう一度試しても失敗する」という説明で、攻撃を再実行する場面があったかどうかは音声からは確認できません。

## 7. 注意点・発表者の気付き

* **SAST の置き換えはしない**：最も多い質問の 1 つで、答えは「置き換えない」。SAST は PR ごとのゲート、MDASH は大きな変更時の探索的な評価
* **カスタムハーネスの改変リスク**：パイプラインの途中に「High と Critical を無視する」ような変更を入れられると、結果に深刻な影響が出る。指摘が少ないことは、対処すべき指摘が見つかっていることを意味しない
* **全リポジトリを一度にスキャンしない**：重要で外部公開されているアプリケーションから始め、トリアージ担当と修正の余力を確保する
* **実行ごとに結果が変わりうる**：MDASH は探索的で、日によって異なる経路をたどる
* **Foundry で上限を設定している場合**：実行が途中で止まると、完全な結果は得られない
* **時間は指摘の数にも左右される**：指摘が多いほど、debater エージェントによる検証に時間がかかる
* **GitHub Advanced Security の Deep scan はまだ使えない**：早期プレビューで、後日提供の予定
* **プレビュー参加は審査制**：フォームの記入に加えて、アカウントチームへの連絡が必要

## 8. 利用者にとっての利点

発表で語られた内容に限って整理します。

* 静的スキャナーなどが見逃した脆弱性を見つけられるという顧客からのフィードバック。複雑なロジックの欠陥（BOLA など）を含む
* Microsoft 自身のコードで、リモートコード実行につながる脆弱性を実際に見つけている。MDASH の使用開始後に月次の CVE 修正件数が増え、今年の 10 月の対処件数は 1415 件に達した
* セキュリティ担当者が開発者のワークフローに入り込まずに、Defender ポータルから PR で修正を提案でき、開発者は GitHub と Copilot で修正を適用できる
* 組織のゲート用の仕組みは変わらず維持される
* 検証フェーズで debater が議論した内容と evidence を確認でき、指摘の根拠を理解できる
* MAI Cyber のモデルは、大きなモデルと同等の性能を、はるかに低い価格帯で提供すると説明された
* マネージド ID での接続、モデル別の請求内訳の確認、TPM による並行数の調整ができる。顧客は同時 2 本から 20 本のスキャンまで拡大した
* コードのコピーは暗号化され、推論環境は使い終わると破棄され、顧客のコンテンツは学習に使われない

## 9. まとめ

Codename MDASH は、100 を超える専門エージェントが準備、スキャン、検証、重複排除の 4 フェーズで動き、複数のモデルを組み合わせて脆弱性を見つけるシステムです。Microsoft 自身のコードでの成果（今年の 10 月に 1415 件の CVE に対処）と、プライベートプレビューの顧客からのフィードバックが紹介されました。

デモでは、認証なしのエンドポイントと BOLA を連鎖させた攻撃を示したうえで、MDASH で脆弱性を見つけ、Defender から PR を作成し、GitHub Copilot で修正を適用するまでの流れが示されました。

運用では、SAST は PR ごとのゲート、MDASH は大きな変更時の探索的な評価と使い分け、重要なアプリケーションから小さく始め、指摘にコンテキストを加えて優先順位づけし、修正の検証プロセスを固めることが勧められています。MDASH はプライベートプレビューで、参加はフォームの記入とアカウントチームへの連絡が必要です。
