# BRK495 Accelerate your security services at machine speed

## 1. はじめに

このセッションは、Microsoft Security を販売・導入・運用するパートナー企業に向けた 45 分の講演です。テーマは **Integrated Security Operations Center（ISOC）**。Microsoft Sentinel の機能を Microsoft Defender のポータルに取り込み、SOC の作業を 1 つの画面にまとめていく取り組みです。

構成は 3 部に分かれています。最初にパートナーにとっての事業機会、次に Defender ポータル上でのライブデモ（Sentinel からの移行手順を含む）、最後にパートナー企業 Ontinue の実際の移行体験です。この記事を読むと、ISOC がライセンス上どう位置づけられているのか、既存の Sentinel 環境をどう移行するのか、パートナーがどんなサービスを組み立てられるのかが分かります。

## 3. 何に関する発表か

テーマは、SOC（Security Operations Center）の分断された作業環境を ISOC で統合し、その上でパートナーがどんなサービスを提供できるかです。流れは次のとおりです。

1. 背景となる調査結果と ISOC の中身（ライセンス、価格、保持期間）
2. 従来の Sentinel 中心のサービスが ISOC でどう変わるか、サービスの機会
3. ライブデモ：ISOC への移行ウィザード、ルール移行、自然言語での Playbook 作成

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**ISOC は新しい SKU ではなく、E5・E7・Defender Suite のお客様がすでに使える「ライセンス上の特典」である**という点です。そのため、パートナーはお客様ごとに別の Azure サブスクリプションや Sentinel ワークスペースを立てなくても、SOC サービスを始められます。

もう 1 つは「Sentinel はなくならない」というメッセージです。Cat 氏は、ISOC の発表直後に最初に出る質問が「Sentinel は終わるのか」だったと述べ、これを明確に否定しています。Sentinel の人気の機能を、1 つの画面（single pane of glass）に持ち込む取り組みだという説明です。ただし、後述するように Azure ポータルでの Sentinel の利用は 3 月で終わります。

## 5. 発表内容の詳細

### 5.1 背景：SOC が抱える課題

Microsoft は昨年、Enterprise Strategy Group と Omdia に調査を委託し、300 人を超える SOC 担当者に聞き取りを行いました。結果は次のとおりです。

| 調査結果 | 数値 |
| --- | --- |
| 調査されないまま残るアラート | 42% |
| SIEM の外にあるセキュリティデータ（書き起こしでは「seam」と聞こえますが、文脈から SIEM と判断） | 46% |
| 1 人あたりが使うコンソールの数（平均） | 10.9 超 |

Cat 氏は、組織内のセキュリティデータの多くが調査や推論の対象になっていないこと（話の中では「半分以上」と表現していますが、上の数値は 46% です）、アラートのトリアージのたびに画面を切り替えるため時間が大きく伸びていることを課題として挙げました。ISOC は、数年がかりで「単一のガラス面」を目指す道のりの次の一歩だという位置づけで、今日明日で完成するものではないと断っています。

### 5.2 ISOC とは何か：ライセンスと価格

ISOC には SKU がありません。「Partner Center で探しても見つからない」と、Cat 氏は強調しています。E5、E7、Defender Suite のお客様は、現時点で次の機能を追加設定なしで使えます。

- ケース管理、ワークブック、Playbook ビルダー、オートメーションルール（Defender のデータに対してネイティブに利用可能）

サードパーティのデータ（ファイアウォールなど）を取り込みたい場合は、**ISOC workspace** を追加できます。ISOC workspace を加えると次のものが使えると説明されました。

- Yuba（音声認識の都合で表記が確定できません）
- 脅威インテリジェンス
- Content hub
- CI/CD リポジトリ
- カスタムテーブル

ほかに、次の変更が説明されています。

1. **保持期間**：Defender の標準保持期間が 30 日から 90 日になり、Defender ポータルに含まれるログが 90 日分になります。
2. **価格**：サードパーティデータの階層型価格がなくなり、**1 GB あたり 2.40 米ドルの 1 階層**になります。見積もりの計算が単純になるという説明です。
3. **コネクタ**：Sentinel で使っていた非 Microsoft データ向けのコネクタ（500 以上）を、そのまま Defender ポータルに取り込めます。

### 5.3 パートナーのサービスはどう変わるか

従来の流れとして Cat 氏が挙げたのは、Azure サブスクリプションを有効にして Sentinel ワークスペースを追加し、取り込むログを評価し、Sentinel を展開してつなぎ、アラート対応を代行する、という手順です。

ISOC では、E5・E7・Defender Suite のお客様に別のワークスペースも Azure サブスクリプションも不要です。次の流れになります。

1. 新しい特典を伝え、IT 運用の観点で現状を評価する。
2. 取り込みたいデータを確認する。サードパーティのデータや脅威インテリジェンスが必要なら ISOC workspace を追加する。
3. すでに Sentinel を使っているお客様は、「移行する」か「両者を共存させる」かを決める（共存モデルも支援されると説明されました）。
4. その上で、従来どおりマネージドセキュリティ運用を行う。

Cat 氏は新しい機会として、次の点を挙げています。

- これまで SIEM に関心がなかった、あるいは必要性が分からなかったお客様も、Defender ポータルの機能を使える。
- Defender のデータを二重に取り込む必要がない。調査とオートメーションを 1 つのポータルで行える。
- どのログを、どれだけの期間、なぜ、どこに保存するかを整理する支援が、マネージドサービスになる。

また、Cat 氏自身の推測として、パートナーが作れそうなサービスを段階別に示しました。

| 段階 | 内容 |
| --- | --- |
| 評価 | 初期環境の確認、SOC の経済性（すでに含まれるもの、追加が必要なもの） |
| 有効化 | 有効化、構成、接続、ID の確認、unified RBAC など |
| 移行 | 既存 Sentinel やサードパーティ製品から新しい体験への移行 |
| 検出エンジニアリング、SOAR 自動化 | ISOC の分析ティア（Fabric 上にある）を活かした活用。エージェントなどを使った取り組みも議論できるとの説明 |
| お客様に代わる運用 | アラートのトリアージ代行 |
| そのほか | トレーニングと定着支援、脅威ハンティング、規制業種向けのコンプライアンス支援 |

### 5.4 ISOC の 2 つの変更点（Sagi 氏の説明）

Sagi 氏は、ISOC は大きく 2 つのフェーズがあるとして話を始め、まず E5 と E7 のお客様向けに Sentinel ワークスペースなしで Sentinel の機能を開放した、と説明しました（2 つ目のフェーズについては、書き起こしでは詳しく語られていません）。パートナーと進める中で、規模をもって構築できるようにするため、次の変更を行ったとのことです。

1. **テナントレベルでのコンテンツ展開**：ワークブックなどのコンテンツはこれまで Sentinel ワークスペースに紐づいていましたが、ワークスペースなしでテナントレベルに展開できます（書き起こしでは「workspace, workbooks and things like that」と聞こえ、対象の一部は確定できません）。提供されるコンテンツは CI/CD にも対応しています。
2. **Content hub の更新**：Content hub はもともと Sentinel の概念で、ほとんどが Sentinel 専用でした。今は Defender 専用のソリューションも含まれ、Sentinel ワークスペースがなくても、ワークブックなどを展開できます。
3. **分析ルールからカスタム検出への移行ツール**：Sentinel から ISOC へ移る際の重要な点は、Defender のデータを Sentinel に取り込まなくなることです。Defender のデータを使うルールを持つお客様やパートナーのために、要件の把握とルールの作成までを行う移行ツールを用意した、という説明です。

### 5.5 新しい統合 UI

Sagi 氏は新しい UI を紹介しました。Cat 氏の話のとおり、セキュリティ体験を 1 つにまとめる数年がかりの取り組みの一部です。MDO、MDI、Sentinel など製品ごとではなく（書き起こしでは「MD, MDO, MDI」と聞こえます）、すべてを 1 つにまとめます。たとえばアドバンストハンティングでは、Sentinel と Defender の両方のデータが同じ画面に出ます。ISOC の一部として提供される **data lake** にも、同じ画面から直接アクセスできます。

### 5.6 既存の Sentinel から ISOC への変換

Sagi 氏によると、Defender 内の Sentinel のお客様には、ISOC への変換に必要な要件を示すポップアップが表示されます（表示される時期についての発言は聞き取りが不明瞭です）。よくある疑問は、「別の移行作業が必要か」「コネクタを再設定するのか」「すべてを一から展開し直すのか」ですが、答えは **いいえ** です。行うのは **インプレース変換** で、Sentinel のコネクタもコンテンツもそのまま残り、ISOC workspace に移るだけです。

要点は次のとおりです。

- **必須の前提条件**：すべてのワークスペースが統合体験（unified experience）にオンボードされていること。Sagi 氏は、3 月が近づいており、その後は Azure ポータルで Sentinel を使えなくなると警告しています。Ontinue の Alex 氏も、3 月末に Sentinel のポータルが Azure 環境から離れると述べています。
- **テーブルの保持期間の変更**：Sentinel への取り込みを止めたいので、テーブルの保持期間を延ばさないようにして、データが Sentinel 側に流れ込まないようにします。また 120 日と 150 日の保持はサポートされなくなり、**90 日か 180 日のどちらか**を選びます。変更しない場合は、最悪のケースとして 180 日に移して 180 日分として課金されると説明されました。
- **ロールの取り込み**：Azure ポータル側の Sentinel の Reader、Contributor、Responder などのロールを、Defender の unified RBAC に取り込めます。
- **最後の作業**：コンテンツを更新し、取り込みを止めます。

### 5.7 カスタム検出ルールの移行ギャップ

デモの最後に Sagi 氏は、分析ルールからカスタム検出への移行にはまだギャップがあり、閉じるために取り組んでいると述べました。今回の Ignite では次の発表があったとのことです。

- カスタム検出で複数の MITRE ATT&CK の戦術をサポート
- 相関の際の除外・包含（書き起こしでは「prompt correlation」と聞こえ、正確な名称は確定できません）
- カスタム検出を高頻度で実行
- 柔軟なルックバック

ただし、ギャップの大半は今後数か月で解消される見込みで、現時点ではまだ残っています。このプレビューでは、パートナーと組んで検証を進めたとし、その 1 社が Ontinue です。

### 5.8 Ontinue の事例（Alex 氏）

Alex 氏は Ontinue の Product Management を率いています。同社は XDR プロバイダーで、拠点はスイスのチューリッヒのほか、会場の近く（書き起こしでは「Redford City」と聞こえます）、英国などにあり、数百社のお客様を守っています。2019 年の初めに Microsoft セキュリティのエコシステムへ集中する決定をしました（Sentinel と Defender XDR スタック）。これまで Sentinel と Defender という 2 つのポータル、2 つのプラットフォーム、2 つの構成が課題だったが、今は 1 つの中央プラットフォームになった、と歓迎しています。

**お客様の 2 グループ**

1. **Sentinel をまだ使っていないお客様**：E5、E7、Defender Suite のお客様は ISOC の出発点になります。これまで Sentinel の営業は、ログ量やコストの予算の議論になりがちでした。その予算議論がなくなる、というのが Alex 氏の評価です。Defender ポータルに含まれるデータが増え、履歴も長くなるため、調査を深められ、お客様へのチケットのエスカレーション率を下げられるとも述べています。
2. **すでに Sentinel を使っているお客様**：SOC recommendations のウィザードを数週間テストし、このウィザードで多くのお客様が Sentinel から ISOC へ移行できるだろうと評価しています。一方、既存の運用で手一杯のお客様には、パートナーが移行ウィザードを使い、Log Analytics から ISOC へ段階的に移行を支援する余地があります。

**Ontinue が決めた提供形態**

- 評価パッケージ（Log Analytics から ISOC への変更点の整理と、展開まで）
- ISOC に特化した専用の MXDR サービス（将来的に Sentinel を前提としない）

Alex 氏は、多くのお客様ではすでに GA だと述べ、Sentinel を使っているお客様は来年初めから段階的に進める、としています。Ontinue は数百社のお客様すべてが Sentinel を使っているため、移行支援が重要だとしています。

**移行で検証した 4 つの領域**

| 領域 | 内容 |
| --- | --- |
| アクセス | Sentinel ポータルが Azure 環境から離れる（3 月末）ため、Defender 環境に GDAP と RBAC でアクセスする方法が必要。現在は Lighthouse を使っている。GDAP をまだ全顧客に導入していないため、お客様と話す必要がある。作業自体は難しくないが、事前に十分な時間を取り、社内の IT チームを巻き込むこと。 |
| 分析ルール | MSSP/MXDR として市場で差別化できる重要な領域。弱い識別子・強い識別子、エンティティマッピング、ASIM パーサーのカスタム関数（書き起こしでは「ASIN」と聞こえます）などの課題を製品グループと詰め、ほぼすべての分析ルールをカスタム検出に移行できた。 |
| オートメーション | Sentinel では標準のオートメーションルールで、自社独自の Ion SecOps プラットフォーム（インシデントを事前に判定して cyber defense center に共有する自社ツール）のインシデントを更新している。標準のオートメーションルールと、ISOC のケース向けの拡張されたオートメーションルールを試した結果、挙動はほぼ同じだった。 |
| 可視化 | Log Analytics で使っていたワークブックを、テナントレベルで ISOC でも使える。 |

**製品グループとの連携**：検出エンジニア、バックエンドエンジニア、オートメーションエンジニアと、Microsoft の担当者が、エンジニア同士で対等に議論できたと述べています。「Microsoft はよく聞いてくれる」とし、機能が数日で出荷された例もありました。具体例として、SOC optimization の移行ウィザードを使い始めた際、数百ある分析ルールで移行を始められないものがあり、追加のエンティティマッピング（後方互換）が必要と伝えたところ、数日で実装され、次のルール群を移行できたそうです。

**Alex 氏の要望（ウィッシュリスト）**

1. **API と as code の対応**：検出ルールを手作業で分析ルールとして実装しているなら、CI/CD パイプラインに移し、Detection as Code にする好機だと述べています。お客様ごとの移行プロジェクトが不要になるためです。Ontinue は、Sentinel 用の既存のパイプラインに加えて、Detection as Code 用の 2 本目のパイプラインを作りました。ただし、ポータルにあって API がまだない機能があり、その提供を望んでいます。
2. **パートナー規模でのオートメーション**：現在は Azure Lighthouse と標準のオートメーションルールの組み合わせで、Ontinue のテナントにある Logic Apps を起動している（インシデント作成・更新で使用）。OR（書き起こしの表記が不明瞭）と API キーは使えるが、パートナー規模で展開できる仕組みがほしい。
3. **全顧客向けの GA**：全顧客を ISOC に移せるようにしたい。

**今後の見通し**：この数日はエージェントの話が多かったが、高品質な結果には良い土台が必要だと述べました。ISOC は、データ・コンテキスト・シグナルを 1 つのプラットフォームに集める出発点で、その上に自社のモデルやエージェントを載せ、Microsoft のエージェントやお客様が作るエージェントも動かせる、という考えです。

### 5.9 今後 90 日の行動（Cat 氏のまとめ）

Cat 氏は、今後 90 日で取るべき行動を次の順で示しました。

1. **既存顧客を見直す**：Defender Suite、E5、E7 のお客様が対象。E3 のお客様にも、含まれうるセキュリティ特典を伝える機会がある。ISOC は SKU ではなくライセンス特典であることを忘れないこと。
2. **現状を評価する**：IT 運用の現状、誰が何をしていて、誰が何をしていないかを把握する。
3. **実際に有効化する**：ISOC workspace を有効にし、ワークブックを使う。お客様の環境で、これまでできなかったことを見せる。必要ならサードパーティのデータを取り込んで補強できる点も挙げられました。Cat 氏は、Microsoft の脅威インテリジェンスは「隠れた秘密」で、追加費用なしでプラットフォームに組み込まれていると述べ、デモの自然言語機能にも触れました。
4. **提供形態を決める**：アドバイザリー、導入代行（範囲を限定した固定価格のプロフェッショナルサービス）、マネージドサービスのどれにするか。

### 5.10 Q&A

| 質問 | 回答の要点 |
| --- | --- |
| Defender の特典は Business Premium に含まれるか | 登壇者は、Entra、Intune、Defender、Purview のポータルへのアクセスはライセンスではなくワークロードで決まり、購入したライセンスの下にそれぞれワークロードの権利があると説明。Defender 製品のライセンスがあればポータルにアクセスできる。 |
| 最大保持期間 | 「2 年」という発言があり（文意はやや曖昧）、lake ではそれより長いが正確な値は覚えていないと回答。Defender のファーストパーティデータはライセンスに 90 日分が含まれ、分析ティアで 180 日まで延ばすこともできる。価格は「1.2 くらい」とリージョンごとの GB 単価という話だが、通貨・単位は聞き取りが曖昧。 |
| Agent 365 のコスト管理（取り込み量や保持期間のコスト、予測など）について | 回答は持っていないが、あとで担当者につなぐと回答。 |

## 6. デモ・手順

Sagi 氏によるライブデモが行われました（「デモの神様が味方してくれますように」という発言あり）。録音は音声のみなので、画面上のボタン名やレイアウトは語られた範囲しか分かりません。デモ中に動作しない箇所もありました。語られた順に整理します。

### 6.1 画面の紹介

1. 新しい UI を表示。アドバンストハンティングで Sentinel と Defender の両方のデータが見えることと、data lake に同じ画面から行けることを紹介。
2. Sentinel のお客様に出る、ISOC への変換要件のポップアップを説明（5.6 のとおり）。

### 6.2 ロールのインポート（Unified RBAC）

1. 設定の「permissions」から「roles」の場所へ進むと、ISOC のロールインポートを開始するポップアップが出る（正確な文言は聞き取り不明瞭）。
2. 既存の Sentinel ワークスペースが開き、すでに設定されている権限が表示される。デモ環境には Reader、Responder、Contributor のユーザーとグループがあった。
3. 各項目をクリックすると、unified RBAC に作成される権限と割り当てられる人を確認できる。
4. パートナーにとって重要な点として、GDAP でワークスペースへのリモートテナントアクセスを設定している場合、ツールはそれも見て、リモートテナントのグループとして取り込む（デモ画面では 2 つのグループが該当）。データソースも確認できる。
5. 内容に問題がなければ「Next」「Submit」。裏でロールが作成される。ここでは問題が発生し、Sagi 氏は「もちろん動かない」とコメントした。インポート後は、あとから変更・編集もできる。

### 6.3 SOC optimization：分析ルールからカスタム検出への移行

1. Sentinel に送っているテーブル、検出ルール、Playbook、ワークブックを見直し、やるべきことを示す SOC optimization の画面に進む。
2. 例として device process event ログのテーブルを選択。このテーブルを見る分析ルールが 7 件あった。
3. 「View details」を開くと移行ツールが表示され、各ルールを評価して、移行できるかできないかを示す。
4. 移行できない場合は理由が表示される。仕組みの違いのこともあれば、まだ埋められていないギャップのこともある。変更できる内容ならその場で編集できる。ギャップが埋まるのを待つ選択肢もある。
5. 移行できるルールを移行すると、移行ツールが KQL を解釈し、Defender のテーブル向けに作り直してルールを作成する。完了後にルールを確認でき、Defender の中に新しいルールが現れる。
6. 移行時には **eval** というタグが付き、評価フェーズになる。この間は分析ルールと Defender 側のルールが重複して存在し、満足できたら移行を完了させる。トリガーされたアラートとアクションも画面に表示され、評価に使える。
7. ルールはいつでも編集できる。**タイトルだけは固有 ID のため変更できない。**
8. 問題がなければ「Complete migration」。分析ルールは無効化され、eval タグが外れ、ルールが検出ルール（detection rules）に入る。

### 6.4 SOAR NL（自然言語による Playbook 作成）

1. ISOC の一部として使える新機能として紹介。ポータルに Visual Studio Code が組み込まれており、Playbook 作成を支援する学習済みモデルとエージェントがある。
2. 指示の例として、「各アラートについて、ユーザーとその上司の情報で補強して」という趣旨の内容を入力（「incident か alert か」はあいまいな発言）。
3. エージェントが実行され、必要なコネクタがあるか確認し、なければコネクタの設定を促す。デモでは Graph API が不足しており、設定を求められた。
4. コネクタが揃うと、ドキュメント、Playbook（Python のコード）、テストが作られる。作ったコードが期待どおり動くか確かめるテストも作成するという説明。エージェントの発言はいつでも確認できる。
5. ドキュメントにはフロー図があり、入力を受け取り、ユーザーのエビデンスを抽出し、ユーザーが見つかれば識別子を取得、さらに上司を取得し、見つかれば強化結果をコメントに投稿する流れ。情報がなければスキップする。
6. Sagi 氏は、以前なら数日かかったコード・ドキュメント・テストの作成が、一緒にやって「3 分くらい」だったと述べた。

### 6.5 SOC optimization の続きと保持期間・RBAC の有効化

1. 必要な作業が終わるたびに、取り込みを止める操作が表示される。DCR（データ収集ルール）を使っている場合は、期待どおり動くか確認することが重要という注意。推奨事項は「完了」「進行中」「却下」にできる。
2. テーブルの保持期間は、data management の「data and connectors」にあるテーブルのブレードで確認・変更できる。ここで取り込みの状況と保持期間が見える。XDR の保持期間 90 日がライセンスに含まれる。現在 90 日分のデータが利用でき、過去分もすぐにクエリできる（「過去 60 日」という発言の意図は聞き取りが不明瞭）。90 日を超える分は Sentinel か ISOC workspace に送られる。
3. ロールを取り込んだ後、**Sentinel の unified RBAC を有効化**する。ISOC を使う資格には unified RBAC の有効化が必要。自動で案内されるほか、設定の Microsoft Defender XDR の「permissions and roles」から入り、Microsoft Sentinel の「manage workspace」でワークスペースを有効化できる。画面ではまだ有効化されておらず、有効化できる状態だった。
4. 有効化すると、unified RBAC が引き継ぐ。そのため、**有効化の前に unified RBAC を設定しておくこと**が重要という説明。
5. 続いて取り込みの停止を試みたが、できなかった。理由として、Sentinel data lake の version 1 がある場合は ISOC に変換できないと説明。version 1 から version 2 への移行プロセスが提供される予定で、それまで待つ選択肢がある。高度な分析の多くは Event House に移る。Sagi 氏は、カスタムグラフやノートブックを使っている人はいるかと会場に尋ね、手を挙げる人はいなかったとして「移行は簡単なはず」と述べた。

## 7. 注意点・発表者の気付き

- ISOC は SKU ではなく、ライセンス特典。Partner Center に項目はない。
- **Azure ポータルでの Sentinel は 3 月で終わる**（Sagi 氏と Alex 氏の発言）。すべてのワークスペースを統合体験にオンボードするのが必須条件。
- Sentinel data lake version 1 は、現時点では ISOC に変換できない。version 2 への移行プロセスは今後提供される予定。
- 120 日・150 日の保持期間は非サポート。変更しないと 180 日で課金される。
- Unified RBAC は、有効化の前にロールを設定しておく。
- DCR を使っている場合は、取り込み停止の前に動作確認が必要。
- カスタム検出への移行にはまだギャップがあり、閉じる作業が進行中。多くは今後数か月で解消される見込み。
- GDAP の導入は、お客様と話す必要があり、社内 IT 部門を含む「三者の握手」になるため、時間を十分に見込んでおく（Alex 氏）。
- デモ中、ロールのインポートでは問題が発生し、取り込みの停止は Sentinel data lake version 1 が理由でできなかった。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- E5・E7・Defender Suite のお客様は追加 SKU なしで、ケース管理、ワークブック、Playbook ビルダー、オートメーションルールをすぐ使える。
- Defender の標準保持期間が 30 日から 90 日になる。
- サードパーティデータの価格が 1 GB あたり 2.40 米ドルの 1 階層になり、見積もりが単純になる。
- 500 以上のコネクタを Defender ポータルで使え、1 つのポータルで調査とオートメーションができる（コンソール平均 10.9 超という課題への対応）。
- Sentinel からの変換はインプレースで、コネクタとコンテンツはそのまま残る。
- SOAR NL により、以前は数日かかった Playbook 作成が、デモでは約 3 分だった。
- Ontinue の事例：ほぼすべての分析ルールをカスタム検出に移行でき、標準オートメーションルールの挙動も同等だった。Microsoft の製品グループに伝えた要望が数日で実装された例もある。

## 9. まとめ

ISOC は、E5・E7・Defender Suite のお客様がすでに使えるライセンス特典で、Sentinel の主要機能を Defender ポータルに集約し、「単一のガラス面」を目指す数年がかりの取り組みの一歩です。Sentinel 自体はなくなりませんが、Azure ポータルでの利用は 3 月で終わるため、既存の Sentinel のお客様にはインプレース変換、ロール取り込み、テーブル保持期間の変更、ルール移行の作業があります。デモでは、その移行ツールと、自然言語で Playbook を作る SOAR NL が示されました。

パートナーにとっては、評価、有効化、移行、検出エンジニアリング、運用代行といった段階で、アドバイザリー、固定価格の導入支援、マネージドサービスのいずれの形でもサービスを組み立てられる機会です。Ontinue の事例は、その先行例として、移行の課題（アクセス、分析ルール、オートメーション、可視化）と今後の要望（API と as code、パートナー規模の自動化、GA）を具体的に示しました。Cat 氏が最後に挙げた次の一歩は、既存顧客のライセンス確認、環境の評価、ISOC の有効化、そして提供形態の決定です。
