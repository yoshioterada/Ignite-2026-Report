# BRK391 Manage and Govern AI Agents on Windows as Your Trusted Execution Layer

## 1. はじめに

このセッションは、社内で AI エージェントが急増する状況に対して、IT 部門が Windows と Intune を使ってエージェントをどう管理・統制するかを扱った発表です。中心になる考え方は、**エージェント自身に自制を任せず、IT が先に境界（ceiling）を決め、OS がそれを強制する**ことです。

発表では、エージェントを 2 つのクラスに分けて対処する方法が示されました。1 つは MXC（Microsoft execution containers）に対応した「MXC ready」なエージェントで、Intune の **agent containment policy** で上限を設定します。もう 1 つは社内に入れたくない「unwanted」なエージェントで、新しい **software compliance policy** でデバイスを非準拠にして締め出します。どちらにも Intune の画面を使ったデモがあります。さらに、Microsoft 社内の IT 部門（Microsoft Digital）による段階的な展開の経験と、HP Inc. の Jim Cooper 氏によるエンタープライズ側の課題も語られました。

## 3. 何に関する発表か

テーマは、**Windows 上で動くローカルのエージェントを、どう検出し、制限し、監査するか**です。扱うのは、Windows の MXC（コンテインメントの技術）、Intune（エンドポイント管理）、Entra、Defender、Purview などです。

発表の流れは次のとおりです。

1. エージェントが企業にとってなぜ重要か（Gartner の予測、HP の視点）
2. エージェントのリスクと、OS で境界を強制する必要性
3. 基本の備え（管理・準拠・条件付きアクセス・インベントリ）
4. エージェントを 2 クラスに分ける考え方
5. MXC ready エージェント向けの agent containment policy（デモ）
6. 社内に入れたくないエージェント向けの software compliance policy（デモ）
7. Microsoft Digital による展開の事例
8. Microsoft 全体のソリューションの俯瞰と、今後の予定

## 4. 発表者が伝えたいメッセージ

**エージェントは速く、常に動き続けるため、人が全部を見て止めることはできません。** そこで IT が事前に境界を決め、プラットフォームが強制する必要がある、というのが発表全体の主張です。

登壇者は、リスクの出どころを悪意のあるユーザーやエージェントではなく、「とても意欲的なエージェントが、タスクを達成するために境界を試す」ことだと説明しています。ニュースで毎日のように見かける、境界を試したり突破したりするエージェントの話が背景にあります。「エージェント自身による自制（self-policing）では足りない」ので、境界の設定と強制を OS で行います。

登壇者は、目的を **"give IT the keys, not the agent"** と表現しています。開発者は自分のエージェントをどう封じ込めるか選べ、IT は Intune でガードレールを設定します。

## 5. 発表内容の詳細

### 5.1 エージェントが増える背景

登壇者は、Gartner Research が、企業内のエージェント数が指数関数的に増えると予測していると紹介しました。現在は企業あたり平均 15 以下ですが、2030 年までに 150,000 を超えるという予測です。IT 運用の役割がどう変わるのか、今から何を準備できるのか、という問いが出発点でした。

### 5.2 HP Jim Cooper 氏の話：エンタープライズで見えていること

HP の Jim Cooper 氏は、HP の社内利用の視点から、次のような話をしました。

- HP でも、従業員が作るエージェントは 15 を超え、150,000 に向かっている。ただし、個人のタスクを自動化するエージェントと、業務のタスクを自動化するエージェントは別物で、業界として整理が必要。数を見て「本当にこれ全部必要か、削除すべきでは」と思うこともある。Copilot Studio などの学習で作られたものも含まれる。
- 従業員がエージェントを作ると、「全員への返信（reply all）」のような事故が起きる。エージェントが従業員とどう関わり、何をできるかを事前に想定し、ガバナンスと制御を考える必要がある。
- 「手に持てるデータセンター級のマシン」として NVIDIA RTX、Spark、AMD Halo（聞こえたままの表記）が挙げられ、ノート PC にも載りつつあり、高メモリ・高性能のプロセッサーが、この「reply all のような事故」を加速しうる。
- トークンのコスト（tokenomics）を踏まえ、エッジやオンデバイスで処理し、必要に応じてフロンティアモデルにバーストさせることを検討している。最初のユースケースは、GitHub を使うアプリ開発者の作業のうち、ローカルに移せる範囲を探ること。ただし、GitHub の作業を全て移せるわけではないという見通しです（本人は「推測」と断っています）。
- ローカルに移した場合の経済性（ROI）のモデルは、現時点では未提供。数か月以内に、経済モデルとホワイトペーパーを公開したいとのことです。
- オンデバイス AI は 2024 年 5 月から追いかけている。会場に、Copilot+ PC の recall や click to do 以外の機能を使っている人を尋ね、反応は少なく、自社でも同様の状況だと話しました。そのうえで、オンデバイスには機会があり、教育や対話の改善が必要だという考えです。そのなかで「1 / 50,000」という数字が出ましたが、何を指す比率かは音声からは確定できません。
- アプリケーションを小さな AI エージェントに分けて組み合わせる、「コンポーザブルな」構成を考えている。一方で、「PC 上なら安全」という考えは通用せず、ローカル AI にもガバナンスが要る。

ガバナンスの考え方について Jim 氏は、重要なものを見極めて良いポリシーを作らなければコンプライアンスには進めず、PC で何かを入力するたびにレビュー委員会を通すような進め方は、予算が無限でない限り成り立たないと述べています。HP のガードレールの考え方としては、Microsoft 365 のエコシステムの内側（bubble）なら一定の自由度を認め、外に出る場合は個別に相談するという方針が紹介されました。コンプライアンスの土台として、アイデンティティ、ガバナンス、最小権限が挙げられ、**MXC を Windows デバイス上のネイティブなポリシーの基準（baseline）にしたい**と述べています。エージェントを検出し、作ってほしいものは認め、そうでないものは止めることを狙っています。

進め方は段階的です。小さな（時には遊びのような）エージェントを作って連携させ、コンプライアンスを観測し、少しずつ進めるとのことです。Jim 氏は「最大の境界を決められなければ、監視もコンプライアンスの強制もできない」という問題意識を述べています。

### 5.3 リスクと、OS で強制する必要性

Daniel 氏は、エージェントは速く、タスクのために常に動くので、IT が先に境界を決め、プラットフォームに強制させるべきだと述べました。単一の担当者が、エージェントの動作を全て見て止めることはできません。

Microsoft は、パートナーとともに、次の要素から成る多層の戦略を打ち出していると説明しています（今週の基調講演でも触れたとのことです）。

- アイデンティティと権限
- コンテインメント（封じ込め）
- ネットワークとデータの管理

このセッションの焦点は、そのうち**エンドポイント管理**の部分です。より深い内容は、翌日のブレイクアウト BRK339（午後 4 時）で扱われると案内されました。

### 5.4 基本の備え：エージェント管理は既存のエンドポイント管理の延長

ここからは Jessica 氏（Intune）の説明です。どんなエージェントを使っていても、基本は同じです。**エージェント管理は、既にあるエンドポイント管理とデータ管理の戦略の延長**だという位置づけです。

- エージェントがいるエンドポイントは、管理下に置き、準拠させ、ポリシーと条件付きアクセスを設定する。
- どんなエージェントがいるかを可視化する。そのために Intune には次の機能がある。
  - properties catalog のポリシー（音声認識の都合で名称が確定できません）
  - アプリとローカル AI エージェントのインベントリ。ソフトウェアに加えて、"open claw-like"（音声認識の都合で表記が確定できません）なエージェントも探す。
  - 集めたデータを、Explorer や Perception（音声認識の都合で表記が確定できません）のようなソリューションで問い合わせ、詳細なレポートにできる。
- **Agent 365** は、Intune のソフトウェアインベントリに加えて、Defender のリアルタイムのヒューリスティックや Entra のシグナルを使い、ローカルエージェントの可視性をさらに高める。

ランタイムの面では、ローカルエージェントの多くが Node.js や Windows Subsystem for Linux に依存しています。これらが不要なデバイスでは、Intune の baseline で実行を止めることができます。Jessica 氏はこれを「やや粗い手段（a bit of a crude instrument）」と呼んでいます。該当する baseline は既に製品に入っており、グループに展開できます。

### 5.5 条件付きアクセス：エージェント向けの 2 つの新しい種類

人間のユーザー向けに既にある条件付きアクセス（CA）は、そのユーザーのワークフローの一部として動くエージェントも守ります。そのうえで、昨年（発話のまま）に 2 種類が加わったと説明されました。

| 種類 | 内容 |
| ---- | ---- |
| クラウドエージェントへのアクセス | 人間のユーザーが、クラウドエージェントにアクセスする際に、管理されたコンプライアンス準拠のデバイスを要求する |
| コンピューター使用エージェント（computer-using agents） | エージェントがリソースにアクセスする際に、管理された準拠のクラウド PC を要求する |

1 つ目が必要な理由として、例が示されました。デバイスが非準拠なら電子メールにアクセスさせない CA があっても、ユーザーがエージェントに「受信トレイから最新 5 件を取ってきて」と頼めば、既存のポリシーを回避できてしまいます。この抜け穴を埋めるものです。

2 つ目の「コンピューター使用エージェント」は、今週の Windows 365 for Agents のセッションで扱われたもので、エージェントに専用のクラウド PC、つまり専用の環境を与える仕組みです。

### 5.6 エージェントの 2 クラス

Daniel 氏は、ローカルエージェントを次の 2 つのクラスに分けるべきだと説明しました。片方を選んでもう片方を忘れてはいけず、両方を制御する必要があります。

| クラス | 対処 |
| ---- | ---- |
| MXC ready エージェント | MXC でコンテインされる、ガバナンスへの道筋が明確なエージェント。Intune で上限（ceiling）を設定する |
| unwanted エージェント | コンプライアンスで締め出す |

どちらの道でも、結果は同じです。エージェントは許可された範囲に届き、許可されていない場所には行けません。

### 5.7 MXC ready エージェントと agent containment policy

主要なエージェントのいくつかは MXC に対応済みです。管理者は、そのエージェントができることの**上限（ceiling）を決める最終的な権限**を持ちます。その範囲内で、エージェントが自分で境界を設けることもでき、ユーザーが「C ドライブには入らないで」といった境界をさらに重ねることもできます。MXC がそれを OS レイヤーで強制します。

MXC は、先に行われたセッションで触れたとおり、クロスプラットフォームで、幅広い種類のコンテナーで使えるものとして説明され、堅牢なソリューションが近く提供されるとのことです。

Intune には、**agent containment policy** がプライベートプレビューとして用意されています。MXC のコンテナーの上限を、既存のエンドポイントと同じ管理画面で設定できるデバイス構成ポリシーです。設定の流れは次のとおりです。

1. **対象のエージェントを決める。** デバイス上の MXC 対応エージェントすべてに適用して既定の姿勢を作り、その上に特定のエージェント向けのポリシーを重ねられる。
2. **構成を設定する。** 現時点で用意されている制御は次のとおり。
   - システム上の場所（ファイルシステムの場所）ごとのアクセスレベル：deny、read only、read-write
   - ネットワークの全体スイッチ（オン／オフ）
   - MXC 自身の機能の制御（例: permissive learning mode）
3. **割り当てる。** ほかの Intune ポリシーと同様に、グループへの割り当てやフィルターを使える。

対応範囲は今後広がり、MXC を採用する開発者やコンテインメントの種類が増えるほど、ポリシーも強力になるとのことです。現時点で提供されているのは process isolation（発話では「public preview は process isolation」）です。

> 注意：発表中、agent containment policy は「プライベートプレビュー」と説明される一方、別の箇所で process isolation について「public preview」とも述べられていました。両者の関係までは、発表では詳しく語られていません。

デモの内容は、6.1 にまとめています。

### 5.8 そのほかの設定：ADMX と settings catalog

MXC による OS レベルのコンテインメントに加えて、多くのエージェントが企業向けの構成オプションを公開しています。例えば、Claude を含む主要なエージェントのサポートサイトには、レジストリキーによる設定が詳しく書かれています。個人アカウントでのログインを防ぎ、企業の UUID だけにログインを制限する設定が例に挙がりました。こうした設定は、Intune から **ADMX テンプレート**で一元管理できます。

さらに、エージェントの開発元と、これらの設定を Intune の **settings catalog** に取り込むための話し合いを進めています。そうなれば ADMX を直接触らずに済みます。スクリーンショットでは、GitHub Copilot CLI については既に settings catalog にあると示されました。

### 5.9 unwanted エージェントを入れない：software compliance policy

社内に入れたくないエージェントに対しては、先ほどの基本（ランタイムのポリシー、条件付きアクセス）が使えます。加えて、Windows と Intune の新しいオプションが発表されました。**Windows デバイスを、制限対象のローカルエージェント（アプリとしてインストールされたもの）が見つかったら非準拠にする**機能です。

仕組みは次のとおりです。

- Intune のソフトウェアインベントリで、エージェントをホストしうるアプリを検出する。
- アプリは、MSI の product code か、package full name で特定する。
- ポリシーは、ホストアプリがインストールされているかを確認する。ユーザーがアプリを起動してエージェントとセッションを持つ前に、保護が効く。
- 今週、Intune のレイテンシー改善について触れたセッションがあり、このチェックは以前よりずっと速くなっている。
- 非準拠になったデバイスには、準拠状況に基づく条件付きアクセスを適用できる。ユーザーへのガイダンスの送信などもできる。
- アプリを削除すれば、ユーザーは準拠チェックをやり直し、すぐにリソースに戻れる。

デモの内容は、6.2 にまとめています。

### 5.10 Microsoft Digital による展開の経験

Microsoft Digital は、Microsoft 社内の IT 組織です。大規模なテナントで、デバイス、ビルド、アプリのバージョンがさまざまです。Customer 0 の取り組みとして、Windows 部門と GitHub のパートナーとともに、**サンドボックス版の GitHub Copilot CLI** の展開を支援したと紹介されました。

展開は、要件を定義し、Intune で、最初は絞った対象から段階的に行いました。新しいセキュリティ機能は、信頼できる少人数から始め、サンドボックスの形が正しいか早く確認すべきだという考えです。ポリシーが配信されたことの確認だけでなく、さまざまなペルソナの日常業務への影響を把握する必要もあります。

展開は 3 つのフェーズに分けられました。

| フェーズ | 内容 |
| ---- | ---- |
| 準備（prepare） | 社内の変更管理とプロダクトチームとの技術レビュー。範囲、リスク、責任、技術的な前提（最低バージョン、パッケージの入手先、アプリの再パッケージの要否など）を決めた |
| ターゲット設定と展開 | 社内のリングにポリシーを展開。まず Intune の remediation script で既存のインストールを最低バージョンなどの要件に更新し、サンドボックスの互換性の問題やユーザー体験の制御（許可された範囲でユーザーがサンドボックスを絞る機能など）に対処した |
| 検証（validation） | Intune のレポートに加え、製品開発をしている実際のエンドユーザーに、ワークフローへの影響を聞いた。結果が拡大を支持するなら、リングを大きくして、より多くのコホートに展開した |

**直面した課題は、順序（sequencing）でした。** 一度に全部を展開しようとするのは良くありません。まず更新などの前提条件を全て終えて確認し、そのあとでサンドボックスを有効にするポリシーを割り当てる、という順番を守る必要がありました。また、Entra のセキュリティグループを使い、OS ビルドのフィルターでポリシーを対応デバイスに限定しました。ユーザーには十分な連絡をし、IT が初期に設定したポリシーでは生産性が出ない人のための**オプトアウトの手順**も用意しました。連絡の経路は Teams などで、各コンポーネントについてチケットを起票できるようにして、フィードバックをリアルタイムで集めたとのことです。

この経験から、次のプレイブックの出発点が示されました。より詳しいプレイブックはオンラインで公開されています。

1. **準備状況の確認。** 前提を満たしていない、ビルドが違う、対象のアプリを使っていないなどで、展開しても何にも当たらない状況を避ける。
2. **ワークフローの検証。** 「ポリシーを配信した」で終わりにせず、開発者やユーザーのワークフローが動くことを確認する。
3. **リングでの展開。** グループへの反映、デバイスのチェックイン、ユーザーからの報告で、伝播の遅れが出ることを想定する。

進め方の助言は 3 点です。小さく始めること、体験を検証すること、リングで最終的にはエンタープライズ規模に広げることです。

### 5.11 Microsoft 全体のソリューションの俯瞰

Jessica 氏は、Daniel 氏が冒頭で見せた多層の図を、約 2 分で説明しました。詳細は BRK339 で、エンドツーエンドのデモを交えて扱われると案内されています。

| 段階 | 内容 |
| ---- | ---- |
| 全体 | **Agent 365** が、すべてのエージェントとそのアイデンティティ、リスクを、Entra、Defender、Purview をまたいで 1 か所で見せる |
| 検出と評価 | Intune のアプリインベントリ、デバイス上のローカルエージェントを見つける Defender、トラフィックを可視化する global secure access、各エージェントに人間とは別の ID を与える Entra agent ID |
| 統制と保護 | Entra の dynamic conditional access（リアルタイムのリスクに応じてエージェントの行動を調整）と dynamic permissions（人間のユーザーが持つ権限の全てをエージェントに許さない）。global secure access は、MXC のネットワークのオン／オフの上に、ネットワークのガードレールを追加し、特定の MCP サーバーのブロックもできる |
| 検出と調査 | Defender のリアルタイム保護（プロンプトインジェクション攻撃などのブロック）、Purview による機密データの流出ブロック、Defender XDR による SOC の追跡 |
| 問題発生時 | **従業員ではなくエージェントに対処する。** Entra ID protection で、アナリストがエージェントを侵害されたものとして確定できる。Intune では制限対象エージェントが見つかったデバイスを非準拠にできる |

Windows は、これらすべての土台です。アイデンティティの面を支え、MXC による分離されたランタイムと、OS が強制するコンテインメント制御を提供します。

### 5.12 すぐ使えるものと今後

Daniel 氏は、MXC は今すぐ利用でき（発話では "MXE" と聞こえますが、文脈上 MXC のことです）、さらに **learning mode** を展開中だと説明しました。learning mode は、エージェントがどの境界にぶつかるのかを把握し、最初のポリシー（ベースライン）を作るためのものです。出力が非常に詳細（verbose）で、大規模に展開するためのものではなく、初期のシグナルを得る用途と説明されています。

## 6. デモ・手順

このセッションには、Intune の画面を使った 2 つのデモがあります。録音は音声のみのため、語られた範囲で整理します。どちらも、発話の流れから Jessica 氏が進めたと読み取れます（映像が録画かライブかは、発話からは分かりません）。

### 6.1 agent containment policy のデモ

管理者側の設定:

1. Intune コンソールの endpoint security で、新しいポリシータイプ **agent containment** を選ぶ。
2. 「MXC 対応のすべてのエージェント」ではなく、特定のエージェント（例として GitHub Copilot CLI）を選ぶ。
3. エージェントの workspace フォルダー内に、広い read-write アクセスを設定する。
4. システムドライブ全体には read-only のアクセスを与える。
5. 企業の OneDrive は deny にする。機密性の高いビジネス情報があり、エージェントが書いたファイルが他のデバイスに同期されるのを避けたいため。
6. 通常のグループによる割り当て方法で、ポリシーを対象に割り当てる。

デバイス（開発者）側で確認した動作:

1. 画面左下に、エージェントが workspace ディレクトリで動いていることが表示される。read-write が許可されたフォルダーで、開発者はこれまでどおり自然言語で操作できる。
2. システムドライブ全体に read-only を与えているので、エージェントは hosts ファイルが望ましい設定かを確認できる。
3. そこでエージェントに、hosts にエントリーを追加するよう頼む。エージェントは変更の承認を求め、デモでは allow を繰り返し押した。それでも **OS 自身が操作をブロック**した。
4. 企業の OneDrive が deny の状態で、開発者が「顧客データが必要」とエージェントに頼む。エージェントは試みるが、Windows が拒否する。
5. GitHub Copilot CLI には、ユーザーが IT の設定をさらに絞れる機能がある。IT が「全てを read 許可」にしていても、ユーザーが個人の写真が見えるのは嫌だと考えて絞れる。
6. ユーザーが「pictures から screenshot を検索して」と頼むと、エージェントは pictures を調べるが、個人の写真フォルダーにだけはアクセスできない。

### 6.2 software compliance policy のデモ

管理者側の設定:

1. 新しいポリシーを、プラットフォームは Windows 10 以降で作成する。新しいタイプ **software compliance policy** がある。
2. 例として、デバイスでの ChatGPT の使用を制限する。
3. 検出ルール（discovery rules）で、製品を MSI product code または PFN で検出するように設定する。ソフトウェアが入っているデバイスは、Intune で非準拠の状態になる。
4. 既存の CA の非準拠ポリシーが効くようになる。
5. 非準拠時のアクションを選ぶ。ここでは、エンドユーザーに「ChatGPT を削除してください」というメールを送る。
6. 通常どおり Intune のグループに割り当てる。レポートでも、どのデバイスが非準拠になったかを確認できる。

ユーザー側の動作:

1. ポリシーが適用され、ChatGPT がインストールされたユーザーが、Outlook にサインインしようとすると CA でブロックされる。
2. Company Portal に「組織はこのデバイスでの ChatGPT デスクトップを許可していません。削除してから、ステータスを再確認してください」という趣旨のメッセージが出る。
3. 設定から ChatGPT をアンインストールする。
4. 準拠状況を再確認する。デバイスが Intune と同期し、アクセスが戻り、受信トレイに入れるようになる。

## 7. 注意点・発表者の気付き

- **agent containment policy はプライベートプレビュー**で、現時点の制御は限られています（ファイルシステムの場所ごとのアクセス、ネットワークの全体スイッチ、permissive learning mode など）。対応範囲は MXC の採用状況に応じて広がる予定です。
- ランタイム（Node.js、WSL）を baseline で止める方法は、発表者自身が「粗い手段」と呼んでいます。
- 既存の CA だけでは抜け穴があります。デバイスが非準拠でメールを開けない場合でも、ユーザーがエージェントに取得を頼めば、既存のポリシーを回避できる例が示されました。クラウドエージェント向けの新しい CA は、この穴を埋めるものです。
- 展開で課題になった点は、**順序**です。前提条件の更新と確認を全て終えてから、サンドボックスを有効にするポリシーを割り当てる必要があります。
- ポリシーを展開しても、グループの反映やデバイスのチェックインで伝播の遅れがあります。
- learning mode は出力が非常に詳細で、大規模展開向けではありません。
- HP の Jim 氏の発言として、ローカルに処理を移した場合の ROI モデルは、現時点では未提供です。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- IT が上限を決め、OS が強制するため、エージェントが自制することに頼らずに済む。ユーザーの生産性（自然言語での操作、許可された範囲の操作）は、これまでどおり保てる。
- 既存のエンドポイント管理の画面（Intune）、グループ、フィルター、レポートを使って、エージェントも管理できる。
- 社内に入れたくないエージェントは、アプリをインストールしただけの段階で検出され、ユーザーが使い始める前に保護が効く。アプリを削除すれば、すぐに元に戻る。
- Microsoft Digital の事例では、リングによる段階的な展開、2 方向のコミュニケーション、オプトアウトの手順によって、ユーザーが生産性を保てるようにサンドボックスの形を調整していったと語られています（定量的な成果は語られていません）。

## 9. まとめ

エージェントの数は今後急増すると予測されており、エージェントは速く動き続けるため、境界の設定と強制は IT が OS で行う必要があります。MXC に対応したエージェントは Intune の agent containment policy で上限を決め、受け入れたくないエージェントは software compliance policy と条件付きアクセスで締め出します。展開は、小さく始め、体験を検証し、リングで広げます。Entra、Defender、Purview、Agent 365 を含む全体像は、BRK339 でさらに詳しく扱われます。
