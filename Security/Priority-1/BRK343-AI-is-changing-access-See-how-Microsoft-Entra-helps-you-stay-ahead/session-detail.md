# BRK343 AI is changing access. See how Microsoft Entra helps you stay ahead.

## 1. はじめに

このセッションは、Microsoft Entra の最新情報を、デモと解説を交えて一気に紹介する「What's New on Entra」です。AI エージェントが人間に代わって動くようになった今、ID とネットワークのアクセス制御をどう進化させるかが主題で、発表は 3 つのチャプター（足場を固める、エージェントのアクセスを守る、AI で防御を拡大する）で構成されています。

発表者は冒頭で、「現在の基盤にある弱点は、エージェントや AI アプリケーションがそのまま引き継ぐ」と述べています。そのため、人に対する ID ガバナンスや権限の整理を後回しにせず、エージェントが増える前に片づける必要がある、というのが全体の出発点です。内容は盛りだくさんで、発表者自身が「時間が足りない」と言いながら進めたセッションです。

## 4. 発表者が伝えたいメッセージ

最初のメッセージは「今の基盤が、そのままエージェントに引き継がれる」ことです。Yina 氏は、前回このような転換点があったのは COVID の時期で、2 年分のロードマップを約 3 週間に圧縮する必要があった、と例えています。今回も同じように、人のユーザーで抱えている未解決の課題（弱い ID ガバナンス、不要な特権、永続的なアクセス）を、エージェントが増える前に片づけるべきだというのです。冒頭の動画でも、「人に対してやっていないことは、エージェントでは苦労する。人のために行う基本は、そのままエージェントにも引き継がれる」という趣旨の声が紹介されました。

2 つめは「エージェントの管理は ID から始まる」ことです。Yina 氏は、アナリストの推定として、ディレクトリ内の人間 1 人あたり 10〜20、場合によっては 100 のエージェントがあり得る、と述べています。その規模では、見つける、アクセスを管理する、リスクを評価する、使われなくなったら廃止する、という一連の流れを ID で扱う必要がある、という主張です。

3 つめは、John 氏がまとめた「**人とエージェントに対して、1 つの ID・アクセス制御のプレーン**」という考え方です。人に使う条件付きアクセスなどの既存の仕組みを、エージェントにも使い回すというメッセージが、発表を通じて繰り返されます。

## 5. 発表内容の詳細

### 5.1 チャプター 1: 足場を固める

**動画での同僚の声**

冒頭の動画では、次のような趣旨の発言が紹介されました。

- ディレクトリ中心の仕事から、ネットワークや、バックエンド（Copilot Studio、Foundry）とデスクトップ上で動くエージェントまで考える必要が出てきた。
- IT では常に緊急対応があり、基本方針や移行といった重要な基礎が後回しになるが、その土台の穴はなくならない。
- 過剰な権限や異常な行動のモニタリング、外れ値の検出が重要。
- アクセスは固定のままではなく、状況に応じて変わるべき。

**Yina 氏が述べたアナウンス**

1. **パスキー**: パスワードを置き換える長い道のりの中で、パスキーは Entra のすべての新規アカウントで**デフォルト**になった。管理者がまだパスワードを使っているなら、対応が必要だと述べています。
2. **パスキーと高保証の本人確認の組み合わせ**: 資格情報のライフサイクル全体で、信頼できる本人確認と組み合わせる。ユーザーが参加するとき、機密情報にアクセスするとき、アカウントを回復するときなど、重要なライフサイクルイベントで、ステップアップの本人確認（ID の提示）を求められる。
3. **BYOD の安全性向上とレガシー VPN からの脱却**: Global Secure Access で重い処理を肩代わりし、ユーザーは Edge の Work プロファイルでサインインするだけで、自分のデバイスからでも特権的なアプリケーションにアクセスできる。
4. **PIM（Privileged Identity Management）の強化**: 常時付与された権限が多すぎる問題に対して、必要最小限の権限を基本とし、必要なときだけ時間制限付きでステップアップする。この制御を、Azure の仮想マシンと接続されたクラウドに拡張する。
5. **条件付きアクセスのポリシープラン**: ID、アプリケーション、ネットワーク条件ごとに条件付きアクセスのポリシーを設定する手間をなくすため、ポリシーの意図を一度設計すれば、すべての ID に適用できる。隙間や矛盾のない包括的なポリシーを作りやすくする。

### 5.2 デモ: 高保証の資格情報（Teams 会議）

Nichole 氏は、機密リソースへのアクセス前、特権アクセスの前、さらには Teams 会議へ参加する前に、リアルタイムの本人確認を求められることを示しました。手順は 6 章に記載しています。John 氏は続けて、仕組みを次のように説明しました。

- パスキーは、リモートからだまされて認証させられることがなく（近接性が必要）、本物に似たサイトを使わされることもないので、ユーザーを守る。
- しかし、攻撃者は別の方法を探す。そこで **Verified ID** を使う。政府発行の ID などを使い、信頼できるパートナーを通じて Verified ID を作成する。これがデジタルウォレットに保存される。
- 機密リソースや、リスクが高いと検出されたときに、条件付きアクセスのポリシーで ID 検証を必須にする。ライブネス検出で撮影した顔を、ウォレットにある情報と比較し、一致すれば権限が付与される。

Nichole 氏は、これは Verified ID の顔チェックだけではなく、多くの世界的なパートナーも、オンボーディングやライフサイクルの途中で、高保証の資格情報と連携すると補足しています。

### 5.3 条件付きアクセスのポリシープラン

John 氏は、従来の条件付きアクセスの難しさから説明しました。ユーザー、グループ、ロール、エージェント、リソース、ネットワークと選択肢が多く、見た目が単純なポリシーでも、実際には多数のポリシーが必要になります。複数のポリシーで繰り返している共通部分（スライドの紫色の部分）を、**ポリシープランに 1 回だけ定義**し、粒度の細かい部分（許可、ブロック、セッション制御）は個別の「ルール」として作成します。共通点ごとにポリシープランを分けて作るという考え方です。これにより、複雑で階層のなかったポリシー群が、構造化された分かりやすいポリシープランになります。

Nichole 氏のデモの内容は 6 章にまとめました。John 氏は、既存の条件付きアクセスポリシーをプランに移行することもできると補足しています。

### 5.4 PIM とクロステナント構成管理

**PIM のデモ**

Nichole 氏は「My access」から、ユーザーが特権的な情報にアクセスする場面を見せました（手順は 6 章）。管理者側では、リソースグループの PIM アクティビティを確認でき、接続の**セッション録画**も見られるため、監督ができます。Nichole 氏は「証跡付きの最小権限アクセス」とまとめています。

**クロステナント構成管理と Entra Resource Policy**

Yina 氏は、「Entra のテナントが 1 つだけの人は？」と尋ね、多くは複数のテナントを持つと指摘しました。複雑なマルチテナント環境では、すべてのテナントを発見して管理下に置き、構成を自分の境界内に保つ必要があります。

- **Cross-tenant Configuration Management**: テンプレートを使って、各テナントに必要な状態を定義する。構成を展開すると、テナントガバナンスが自動で監視する。任意のリソース・テナントについて、定義した状態からのドリフトを 1 つの画面で確認できる。
- ドリフトの監視対象は、Entra、Purview、Defender、Intune、Exchange Online、Teams。さらに、Agent 365 と Copilot にもサポートを拡張する予定。
- **Entra Resource Policy**: 準拠しない変更が効力を持つ前にブロックするポリシーを割り当てられる。

**Entra Backup and Recovery Premium**

レジリエンスの強化として紹介されました。

- 保持期間を 7 日から **30 日**に延長する。
- Microsoft 365 Backup と統合し、ID と生産性の両方でエンドツーエンドの復元力を高める。
- エージェント ID のような重要なオブジェクトを完全削除から守る、**ハード削除保護**を含む。

### 5.5 チャプター 2: エージェントのアクセスを守る

**動画での同僚の声**

第 2 チャプターの前の動画では、次のような趣旨の発言がありました。

- AI エージェントによって生産性が上がる一方、AI ガバナンスとセキュリティへの対応に大きなプレッシャーがある。
- 「どのエージェントがあるか。各エージェントが何に到達できるか。今すぐ止めるにはどうするか」。
- 目的に合った最小権限にし、エージェントが、作成者である人に付与された権限のせいで過剰な権限を持たないようにする。
- ID の権限、データ、リスクを 1 つにまとめて見る必要がある。エージェントは情報を読むだけでなく、ユーザーや組織のために行動する可能性があり、アクセス制御だけでは足りない。

**エージェントの管理は ID から**

Yina 氏は、エージェントの数が多いこと（人 1 人あたり 10〜20、場合によっては 100）を踏まえ、次の 3 つが必要だと整理しています。

1. クラウド上かローカルか、Microsoft 製か否かを問わず、組織内のすべてのエージェントを見つける。
2. アクセスを継続的に管理し、リスクを評価し、エージェントができるすべてのことに条件付きアクセスを適用する。
3. 出入りが激しいため、クリーンな状態を保ち、誰も使っていないエージェントを廃止できるようにする。

Microsoft のリソースから来るものでも、外部から来るものでも ID を割り当てる必要があります。開発者が AWS や GCP でエージェントを作る場合も、従業員全員が Cloud Code（音声認識の都合で表記が確定できません）、OpenAI Codex、GenSpark、Perplexity などのツールを使う場合も同様です。

**より多くのエージェントの種類を検出**

デバイス上で動く **60 種類を超えるエージェント**を検出できるように拡張する、と発表されました。エージェント ID は 2 種類に整理されています。

| 種類 | 内容 |
| --- | --- |
| 登録されたエージェント ID | 開発者が登録したもの |
| 検出されたエージェント ID | エンドポイント上で動いているアプリケーションから検出されたもの |

検出には Microsoft Defender と Global Secure Access（GSA）を使います。Microsoft 製のエージェントは、すでに自動でエージェント ID が割り当てられます。

**John 氏の解説: 他のクラウドとローカルのエージェント**

- Microsoft のプラットフォーム上のエージェントは、Entra で ID を持つ。Microsoft のエコシステム外では、従来は Agent 365 SDK を使う方法があり、便利だったが、より良い選択肢を用意したい、という前提で説明している。
- **Agent 365 の connected platforms**（接続されたプラットフォーム）: OAuth、API、ID フェデレーションを使い、接続した他のクラウドの機能を使ってエージェントを検出し、ID を与える。**開発者のコードは不要で、アプリケーションの変更も不要。** Entra に ID ができ、ネットワーク制御などの将来のガバナンスの土台になる。
- **ローカルのエージェント**: Defender が 60 種類にわたって検出し、発見されたエージェントとして ID を割り当てる。ネットワークや制御の文脈は GSA で得る。これで、インベントリと ID ができ、ランタイムのポリシーを適用できる。
- ランタイムのポリシーは、エージェントによって何ができるかが変わる。Entra と統合されていれば条件付きアクセスを、統合されていなければ GSA を使い、ネットワークで特定のエージェントに基づいてブロックできる。

### 5.6 エージェントのガバナンス: ライフサイクル、アクセスパッケージ、動的な権限

Yina 氏は、ID があっても、エージェントが仕事をするにはリソースにアクセスできる必要がある、と述べます。人にはロールを作り、権限を割り当て、承認を管理し、あとでアクセスを削除します。エージェントは人間をはるかに上回る数になるため、これを簡単に、大規模に行えなければなりません。Entra では次を拡張しています。

- **ライフサイクルワークフロー**を、エージェントのアクセスのガバナンスに拡張する。すべてのエージェントについて、人間のスポンサーがいるか、まだ必要か、長く非アクティブではないかを追跡するポリシーを作れ、いずれかに該当しなければ、Entra が無効化または削除できる。これらは Entra で動き、Agent 365 に自動的に統合される。
- **デジタルチームメイト向けのアクセスパッケージ**: 人間のユーザーと同じように、自律的なクラウドベースのエージェントにもアクセスパッケージを割り当てられる。承認、期限、ポリシーも設定でき、前日の基調講演で紹介された Microsoft Autopilots にも拡張する。
- **動的な権限（Dynamic Permissions）**: エージェントごとにアクセスを事前設定する代わりに、動的に付与する。エージェント自身の権限と権限範囲を、現在のタスクに絞り、期限付きにする。最小権限から始め、タスクに応じて必要な権限を与えて期限を切る。

**John 氏の解説**

1. **人間のオーナー**: すべてのエージェントには、説明責任を負う人間のオーナーがいる。アクセスパッケージは、OneDrive やメールボックスなど、エージェントに必要な機能を割り当てるためのもので、割り当てるのは人間であり、ライフサイクル全体を制御できる。
2. **ID Jag**（音声認識の都合で表記が確定できません）: アシスタントに自分のトークンをそのまま使わせたくない。自分がトークンの subject になっているところを、「John のヘルパー」に切り替え、アクセス先（例: Snowflake）が「John ではなく John のヘルパー」を subject として見るようにする。監査されるのもこちらになる。
3. **権限のサブセット**: John 氏は自分の権限もこの 16 年間で少しずつ膨らんできたと述べ、エージェントにそれを引き継がせたくない、と説明します。エージェントには、やることに見合った権限のサブセットが動的に調整されて与えられる。エージェントが「それを返してほしい、正当な理由がある」と求めたときは、ユーザーが承認疲れしないよう、Entra が要求の内容に基づいて判断し、適切なら権限を付与する。
4. **クリーンアップ**: すべてのエージェントに人間のオーナーを置き、スポンサーがいるか、まだ必要と確認したかを見る。放置されたエージェントは、放置されたユーザーアカウントと同じく攻撃対象になるため、クリーンアップが重要だと述べています。

デモの内容（ライフサイクルワークフローとアクセスパッケージ）は 6 章にまとめました。

### 5.7 エージェントの運用: リスク、条件付きアクセス、ネットワーク

Yina 氏の説明によると、エージェントが動くとスタックの各層で操作のたびにシグナルが生まれます。これらのシグナルから、サインイン、アクセスしているツール、すべてのアクティビティに基づいて**動的なエージェントのリスク**を計算し、その上で条件付きアクセスのポリシーを適用します。実行手段（アクチュエーター）の 1 つがネットワークです。

- Global Secure Access を通るエージェントのトラフィックは、ユーザーのトラフィックと区別でき、エージェントのトラフィックにだけネットワーク制御を適用できる。Web コンテンツやリモート MCP サーバーに、制御された形でアクセスさせられる。
- ローカルのエージェントとクラウドのエージェントの両方を含む、AI エコシステム全体に広げる。Amazon Bedrock との統合はすでにあり、**プレビュー**中。Microsoft の製品やクラウドに限らない、と強調されました。

John 氏は、Entra、Purview、Defender のシグナルを組み合わせ、「人が何をしているか、エージェントが何をしているか」を見て、動的なリスクを作ると説明しています。考え方は「シグナルがエビデンスを与え、リスクを評価し、ポリシーを動かし、制御する」で、動的なリスクに応じて、許可、ブロック、人による承認の要求のどれにするかを、条件付きアクセスで決められます。

### 5.8 MCP のネットワーク制御（GSA）

John 氏は、MCP サーバーなどのリソースに対する制御を説明しました。人とエージェントで共通の機能を使うという流れです。

- 既存の Web フィルタリングの機能で、特定のエージェントを対象にできる。「すべてか無か」ではなく、OpenClaw、GitHub Copilot CLI、MS Copilot、Claude Code といったエージェントを指定して、許可またはブロックできる。
- より細かく制御するために、まず **TLS 検査**を有効にする。宛先名だけでなく、パケットの中身を見られるようになる。
- そのうえで **MCP ポリシー**を使い、対象の MCP サーバーと、許可する操作を指定する。例として、あるエージェントは MCP 1 には読み取り（read）だけを許可し、書き込み（write）は許可しない。GSA クライアントがマシン上でポリシーを強制し、読み取りは通し、書き込みを試みたらブロックする。
- ブロック時は **403** を返し、詳細な説明（Entra のインターネットアクセスがブロックした）が付くため、エージェントはそれを理解し、再試行し続けない。
- ポリシーで許可されていない、未承認のエージェントは、すべてブロックされる。完全なトラフィックログと監査が得られる。

デモは 6 章に記載しています。

## 6. デモ・手順

デモは主に Nichole 氏が行い、John 氏が事前に仕組みを解説しています。ライブか事前録画かは、発話から確認できたものだけ明記します（MCP サーバーのデモだけが、「ライブではなく動画」と明言されました）。画面の細部（ボタン名やレイアウト）は音声からは確認できません。以下は語られた順の整理です。

### 6.1 高保証の資格情報で Teams 会議への参加を制限する

1. 会議を設定し、オプションにある、ロビーをバイパスする人に高保証の本人確認を求める設定を使う（ユーザーが自分で見つけられる設定だと説明されています）。
2. 招待した協力者（contractor）が参加しようとすると、「Verification required」が表示される。
3. Verified ID を Authenticator で使う（パートナーも利用可能）。
4. 協力者がスマートフォンで QR コードをスキャンし、顔チェックで、人間であることと政府発行の ID と一致していることを示す。
5. 検証を通ると会議に入れる。検証手段がない場合は、ロビーで待ち、別の方法で本人確認することもできる。

### 6.2 条件付きアクセスのポリシープランの作成

1. Entra Admin Center の「Conditional Access」でポリシープランを作成する。
2. プラン名を付ける。説明が自動で簡単に書かれる。オーナーとタグを追加できる。
3. ID を構成する。ユーザーとグループから「HQ のすべてのユーザー」を対象にし、break glass アカウントを除外する。
4. 共有リソースと共有条件は、あとで構成する。
5. 最初のルールとして「Require phishing-resistant auth（フィッシング耐性のある認証を必須にする）」を設定する。対象リソースは「すべてのリソース」。付与コントロールで、フィッシング耐性のある MFA を必須にする。パブリックプレビューが終わると、ここで高保証の資格情報も必須にできるようになる。
6. 2 つ目のルールを追加する。プランで作った設定をすべて引き継ぎ、新しい条件や変数だけを足せる。
7. 「Create plan from template」で、テンプレートからも作れる。テンプレートの例として「require MFA for admins」「Block risky agents」が挙げられた。

### 6.3 PIM で Azure 仮想マシンに接続する

1. 「My access」で、ユーザー（例では「Peeter」）が特権的な情報へのアクセスを得る。
2. 接続したい仮想マシンを選び、Azure Bastion 経由で VM に接続するためのロール割り当てをアクティブ化する。
3. 理由を入力して「Activate」する。
4. アクティブ化が完了したら「Connect」を選び、同じ画面からブラウザで VM に接続する。
5. 管理者は Admin Center で、リソースグループの PIM アクティビティを確認し、接続のセッション録画を見られる。

### 6.4 エージェント ID のライフサイクルワークフロー

1. Entra Admin Center で、ユーザー ID と同様に、エージェント（アシスティブエージェントも含む）向けのライフサイクルワークフローを作成または有効化する。デモでは既定のポリシーを有効にする方法にも触れつつ、新しいポリシーを作成する。
2. 対象をすべてのエージェント ID にする。
3. スポンサーを 180 日ごとに確認する。過去 90 日以内にアクティブであることを求める。人間のスポンサーがいることを必須にする。
4. 一定日数使われない、または基準を満たさない場合に、エージェント ID を無効化する設定ができる。
5. 無効化や削除の前に、スポンサーなど指定した人へ通知する設定ができる。
6. 実行すると、既定では 3 時間ごとに繰り返される。
7. 例として、オーナーや管理者に届く、「エージェントは 30 日後に削除されます」という趣旨のメールが示された。無効化と削除が通知され、ID は組織内で動作できなくなる。

### 6.5 エージェント向けのアクセスパッケージ

1. アクセスパッケージを作成し、あとで分かるよう説明を書く。
2. グループやチームにリソースロールを割り当てる。例では finance グループ（財務部門の全員と、そのエージェント、アシスティブエージェント）を追加する。
3. 付与するものとして、finance グループの SharePoint へのアクセスを選ぶ。
4. このグループのエージェントとユーザーに、A365 ライセンスを追加する。
5. 正当性の説明（justification）は不要とし、SharePoint と A365 には、そのまま通す設定にする。
6. 誰が申請できるかなどの詳細を確認する。デモでは「マネージャーの理由は不要」と語られた。
7. 内容を確認してアクセスパッケージを作成する。これで、finance グループのエージェントは必要な finance のリソースにアクセスできる。

### 6.6 リスクのあるエージェントをブロックする条件付きアクセスポリシープラン

1. 管理センターでポリシープランを作成し、テンプレート「Block risky agents」を使う。
2. プラン名を付ける。説明文は「Evaluate agent risk signals, enforce policies that block sensitive actions for these agents」。
3. 最初のルールで、機密性の高いエージェントのアクションをブロックする。**レポート専用（report-only）モード**でオンにし、対象ユーザーはすべて。
4. 保護するリソースとして、テンプレートに設定された機密アクション（発話では data detection、communication などと語られています。音声認識の都合で正確な名称は確定できません）と、Web 上の任意のカテゴリー（CRM、財務、ID などの Microsoft 以外のアプリ）を指定する。
5. 条件として、ユーザーに代わって動くすべての機密エージェント（アシスティブエージェント）を対象にし、2 つ目の条件に「エージェントのリスクが medium」を設定する。
6. セッションコントロールで**人間の承認を必須**にする。この新しいコントロールはアクセスパッケージと統合されており、エージェントが保護されたアクションを試みると、条件付きアクセスがアクセスパッケージ経由で人間への承認ワークフローを起動する。

### 6.7 GSA の MCP ファイアウォール

1. GSA の MCP ポリシー（プレビュー）を開く。
2. MCP ポリシーを作成し、明示的に許可されない限り、どの宛先にもアクセスできない設定にする。
3. 新しいルールを追加し、保護するエージェント（Claude Code と Claude desktop）を指定する。
4. 一致させたい MCP サーバーを 2 つ、サーバー URL で追加する。
5. プリミティブの種類で「tools」を選び、許可するメソッド（MCP からツール一覧を取得する、ツールを呼び出す、など）を選んで許可する。
6. 許可する操作を確認して保存する。ローカルとクラウドのエージェント向けの MCP ファイアウォールポリシーが作成された。

## 7. 注意点・発表者の気付き

- **基盤の弱点は引き継がれる**: 弱い ID ガバナンス、不要な特権、永続的なアクセスといった課題は、エージェントがそのまま引き継ぐと述べています。
- **エージェントに人の権限を引き継がせない**: 長年の間に膨らんだ人の権限を、エージェントにそのまま持たせないため、権限のサブセットと動的な付与を使います。
- **トークンの subject を分ける**: アシスタントが人のトークンをそのまま使うと、アクセス先からは本人の操作に見えます。「John のヘルパー」として見せることで、監査でも区別できる、と説明されています。
- **放置されたエージェントは攻撃対象になる**: 放置されたユーザーアカウントと同じで、スポンサーの確認と、使われていないものの無効化・削除が必要です。
- **ブロックの返し方**: GSA が 403 と説明を返すので、エージェントが理解して再試行を繰り返さない、と説明されています。
- **機能のステータス**: MCP ポリシー（GSA）はプレビュー、Amazon Bedrock との統合はプレビュー、高保証の資格情報の条件付きアクセスはパブリックプレビュー後に対応予定、IT 管理者向け MCP サーバーは GA です。Perception の Entra ポータルへの組み込みは「将来」のビジョンです。
- **デモの一部は事前録画**: IT 管理者向け MCP サーバーのデモは動画でした。

## 8. 利用者にとっての利点

発表で語られた効果は、次のとおりです。

- **ポリシー管理の簡素化**: ポリシープランで共通部分を 1 回だけ定義し、テンプレートや既存ポリシーの移行も使えるため、隙間や矛盾のない包括的なポリシーを作りやすい。
- **本人確認の強化**: パスキーに加え、参加、機密情報へのアクセス、アカウント回復といったライフサイクルの重要な場面で ID 検証を要求できる。
- **最小権限と時間制限**: PIM と、エージェント向けの動的な権限・アクセスパッケージにより、必要なときだけ、必要な範囲の権限を付与できる。
- **マルチテナント運用**: ドリフトの一元的な監視と、非準拠の変更のブロックができる。
- **レジリエンス**: バックアップの保持が 7 日から 30 日に延び、エージェント ID などの重要なオブジェクトを完全削除から守れる。
- **エージェントの可視化と廃止**: 60 種類超のローカルエージェントの検出、他クラウドのエージェントの開発者コード不要での ID 付与、ライフサイクルポリシーによる自動の無効化・削除。
- **ネットワークでの制御**: エージェントのトラフィックの識別、MCP の操作単位（読み取りと書き込みなど）の許可、完全なトラフィックログと監査。
- **管理作業の効率化**: IT 管理者向け MCP サーバーによる、Box の SAML SSO 構成のような作業の簡素化（デモでは「手作業なら大変な時間がかかる」と説明）。

## 9. まとめ

このセッションは、エージェントのアクセス管理を、人に対して整えてきた ID・アクセス制御の延長で行うことを、デモを交えて示したものです。足場を固める段階では、パスキー、高保証の本人確認、PIM、条件付きアクセスのポリシープラン、クロステナントの構成管理、バックアップの強化が紹介されました。

エージェントについては、まず検出して ID を与え、スポンサーとライフサイクルで管理し、アクセスパッケージと動的な権限で必要最小限の権限を与え、リスクに基づく条件付きアクセスと GSA で実行時の制御をかける、という流れです。最後に、IT 管理者向け MCP サーバーの GA と、Perception の Entra ポータルへの組み込みという、AI を使って管理者の作業を減らす方向が示されました。John 氏の言葉では、共通するのは「人にもエージェントにも、1 つの ID・アクセス制御プレーン」という考え方です。
