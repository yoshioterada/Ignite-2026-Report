# THR877 AI agents: access granted. Trust not included

## 1. はじめに

このセッションは、AI エージェントに「白紙の小切手（blank check）」を渡さないために、エージェント専用の ID を持たせて管理・保護する方法を紹介する 25 分のシアターセッションです。扱う製品は Microsoft Entra（Entra Agent ID、Conditional Access、Global Secure Access）を中心に、Microsoft Defender、Microsoft Purview、Agent 365 です。

前半はスライドで「発見（discover）→管理（manage）→ガバナンスと保護（govern / protect）」の流れと、今回発表された新機能を説明します。後半は、ローカルで動く Claude Code を題材にしたデモで、リスクの上昇に応じてエージェントの権限が絞られ、最後にブロックされるまでを見せています。

## 3. 何に関する発表か

多くの組織では、AI エージェントが、支援している人間のユーザーと同じ ID・同じアクセス権で動いています。これでは、エージェント用の個別の制御ができず、人間とエージェントのどちらが何をしたのかも区別できません。登壇者はこの状態を「blank check を渡している」と表現しています。

発表の流れは次のとおりです。

1. 問題提起: エージェントに専用の ID が必要な理由
2. 4 つの柱（枠組み）の紹介: 発見、管理、ガバナンス、保護
3. 発見と管理: Agent 365 のレジストリと、ローカルエージェントへの ID 付与
4. ガバナンスと保護: 統合されたエージェントリスクと、Conditional Access の動的制御
5. 今回発表された内容のまとめ
6. デモ
7. 関連セッションの案内

## 4. 発表者が伝えたいメッセージ

エージェントがどこで作られ、どこで動くかにかかわらず、**エージェントには専用の ID を持たせるべきだ**というのが中心の主張です。専用 ID があれば、ユーザーの操作とエージェントの操作を完全に分けられます。さらに、エージェントの責任者（owner）を把握でき、最小権限（least privilege）とゼロトラストのポリシーを適用できます。登壇者は「ID が無ければ、エージェントに白紙の小切手を渡しているのと同じ」と述べています。

もう 1 つのメッセージは、リスクを見せるだけでは足りず、リスクに応じて制御まで行うことが必要だという点です。顧客からのこのフィードバックが、統合リスクと Conditional Access の動的制御という 2 つの新機能につながったと説明されています。

## 5. 発表内容の詳細

### 5.1 エージェントの環境と、ID を持たせる対象

顧客の環境には、さまざまな種類のエージェントが混在しています。発表で挙げられた例は次のとおりです。

| 分類 | 例 |
|---|---|
| Microsoft のエージェント | Foundry、Copilot Studio |
| 他クラウド・パートナーのエージェント | AWS Bedrock、Google、Zendesk、Manus（ほかにも聞き取りにくい名前のパートナーあり） |
| ローカルエージェント（今回の大きな話題） | GitHub Copilot、Claude Code、Claude Desktop |

（Claude Desktop は音声認識では「cloud desktop」と書き起こされています。）

登壇者は、これらがクラウドで動くか、ユーザーのデバイス上で動くか、Microsoft のプラットフォームか他社のものかを問わず、それぞれが自分の ID を持つ必要があると強調しています。

### 5.2 4 つの柱

セッションは、次の枠組みで進みます。

1. **Discoverability（発見）**: エージェントを見える状態にする。エージェント ID が助けになる
2. **Manage（管理）**: 誰がオーナーかを把握し、孤立（orphan）したエージェントを作らない。これも ID があって可能になる
3. **Governance（ガバナンス）**
4. **Protection（保護）**

前半の発見と管理は、Agent 365 のレジストリと ID の話です。後半の 2 つはリスクと制御の話です。

### 5.3 発見と管理: Agent 365 レジストリとローカルエージェント

登壇者は、基調講演で触れられた数字として、Agent 365 のレジストリで **5,000 万のエージェント**が見えていると紹介しています。この数字は、顧客企業とパートナーをまたいだ合計として説明されました。Agent 365 は、環境内のすべてのエージェントを見られる Microsoft の公式レジストリという位置づけです。

#### ローカルエージェントへの ID 付与

デバイス上で動くローカルエージェントは、IT 部門から見えないことが多いため、特に注目されています。**60 以上のローカルエージェントを自動的に発見**できると説明されています。Build 会議の時点では約 30 だったものが、60 以上に増えたとのことです。GitHub Copilot、Claude Code、Claude Desktop、OpenClaw などが含まれます。

発見は 2 つの仕組みの組み合わせで行われます。

| 仕組み | 役割 |
|---|---|
| Microsoft Defender | エンドポイントデバイス上で何が動いているかを可視化する |
| Microsoft Entra Global Secure Access（GSA） | ネットワーク層の可視性を提供する |

この 2 つが Entra に、「エージェントを識別した」というシグナルと、「どの種類（プラットフォーム）のエージェントか」というシグナルを送ります。すると Entra ディレクトリで、エージェントに **agent ID が自動的に割り当てられ**、エージェントの種類（Claude Code、Claude Desktop、GitHub Copilot など）の情報も登録されます。まとめると、Defender と GSA が発見し、Entra が ID を付与し、Agent 365 が一元的に見る場所になる、という流れです。

### 5.4 ガバナンスと保護: 統合エージェントリスク

顧客からのフィードバックで多かったのが、「エージェントについて必要なことを 1 つのリスクで知りたい」という要望です。従来は Entra、Defender、Purview がそれぞれリスクシグナルを持っていましたが、統合されていませんでした。

そこで今回、**unified agent risk（統合エージェントリスク）** が public preview で発表されました。

- Defender、Entra、Purview のシグナルを統合し、API ベースで提供する
- Agent 365、Defender、Entra、Purview の各ポータルで同じリスクが表示される
- リスクは 3 つの要素から成る: **runtime risk**（現在のエージェントの挙動）、**exposure risk**（エージェントが悪用される脆弱性）、**blast radius risk**（侵害された場合に害を及ぼせる範囲）
- シグナルは静的ではなく動的で、リスクレベルに応じて調整できる

### 5.5 ガバナンスと保護: Conditional Access の動的制御

リスクを見るだけでは不十分で、リスクを緩和する手段が必要だという声に応えるのが、**Conditional Access の動的制御（dynamic controls）** です。登壇者は、Entra の Conditional Access はユーザー向けとして多くの人が知っており、エージェント向けにも General Availability で提供されていると述べています。ただし、従来のエージェント向けの制御は **block か allow** の 2 択でした。

動的制御では、より細かい制御ができます。

- allow（許可）
- constrain（制約付きで許可）
- 高リスクな処理に対して人間の承認（human approval）を求める
- 機密データへのアクセスを制限する
- block（ブロック）

制御の対象リソースは、データソース、クラウドプロバイダー、機密ファイル、API、ネットワークなど多岐にわたると説明されています。

### 5.6 今回の発表内容と提供状況

| 機能 | 提供状況 |
|---|---|
| Entra Agent ID for local agents（ローカルエージェントへの ID の自動割り当て） | Preview |
| Dynamic agent risk（Defender、Entra、Purview の統合シグナル） | Public preview |
| Conditional Access の動的制御 | Limited preview（private preview） |

いずれも GSA と連携して動作し、GSA はローカルエージェントの発見に欠かせない要素と位置づけられています。登壇者は、Entra 関連の最新の発表をまとめたブログへの短縮リンクがスライドにあることも案内しました。

## 6. デモ・手順

画面を使ったデモが行われています（"Let's meet Cecile" から開始）。録音は音声のみのため、画面の細部は分かりません。以下は発話で語られた範囲です。登場人物の Cecile は、「Coldova の IT 管理者」という設定です（会社名は音声認識の都合で確定できません）。

### 6.1 デモ 1: エージェントの可視化とリスクの確認

1. IT 管理者の最初の関心は、自分のテナントにどんなエージェントがあるかを知ること。レジストリの画面で、エージェントの数を確認する
2. 「All agents」を開いてすべてのエージェントを見たうえで、ローカルエージェントに絞り込む。これは Microsoft のエージェントに限らず、サードパーティやローカルのエージェントも対象にした検出機能であると説明されている
3. その中から Claude Code を選ぶ。パブリッシャーとインスタンス（複数のマシンで動く Claude Code のそれぞれ）が見える
4. 1 つのインスタンスを開く。このインスタンスは **high risk** と表示されている。インスタンスごとに固有の ID があり、リスクもインスタンスごとに異なる
5. アクセス権の確認: そのインスタンスがアクセスできるデータとツールを確認できる。セキュリティの詳細では、総合リスクが high で、runtime risk、exposure risk、blast radius が示される。3 つは 1 つのリスクスコアに統合され、セキュリティ運用担当者の判断を助ける
6. インスタンスについて、アクセスしているユーザーのデバイスを見たり、エージェントから出ていくトラフィックを監視したりできる
7. 対応の選択肢として、**block だけではなく、アクセスを制限する**ことが示された。ブロックは混乱が大きいため、段階的な制限が用意されている。語られた制限の例は次のとおり
   - デバイスのステータスを変更し、侵害されたデバイスとして隔離（quarantine）する
   - ネットワークトラフィックを特定のサイトに制限する
   - エージェントを隔離（isolate）する。隔離には複数のレベルがある

### 6.2 デモ 2: Conditional Access ポリシー

1. Conditional Access のポリシー一覧を開く。エージェントを対象にしたポリシーが 2 つある
2. 1 つ目: エージェントのリスクが **high** のときにブロックする。この組織では、高リスクのエージェントには何もさせない
3. 2 つ目: リスクが **medium** のとき。運用を完全に止めたくないため、機密性の高い操作だけを制限する。例として、読み取りは書き込みや削除ほど機密性が高くないという考え方が示された

### 6.3 デモ 3: ユーザー側の体験（リスクの上昇とブロック）

ローカルマシンで Claude Code を使い、リスクが段階的に上がる様子が示されました。

1. 新しいセキュリティグループの作成を指示する。エージェントにアクセス権があり、リスクも無いため、グループが作成される。画面には、エージェントのアクセスレベルとリスクレベルが表示され、この時点で動的リスクは **low**
2. ネットで見つけた「興味深いリソース」のファイルを、エージェントへの指示で使おうとする。ファイルには悪意のあるコンテンツが含まれている。**Defender が攻撃をリアルタイムで妨害し、LLM に届く前にエージェントから LLM への転送をブロックする**
3. Defender が中央のインテリジェンス層にリスクを報告し、エージェントのリスクが **medium** に上がる
4. 「先ほど作ったグループのメンバー一覧を表示して」と、「新しいグループを作成して」を同時に頼む。メンバー一覧は表示されるが、グループの作成は拒否される（リスクが上がり、機密性の高い操作が許可されないため）
5. 次に、ユーザーの社会保障番号（social security number）を含めてレポートを生成するよう指示する。機密情報なので、**Purview の DLP が内容を検査して機密情報の種類を特定し、LLM への送信をブロックする**
6. Purview も検出を中央のインテリジェンス層に報告し、リスクが **high** に上がる
7. Snowflake へのクエリを実行する。アクセス権自体は残っているが、以前はできた操作ができない。エージェントが高リスクと判断され、完全にブロックされている

登壇者は最後に、この間 **人間のユーザーは妨害されない**点を強調しています。ユーザーとエージェントのインスタンスを別々に識別しているため、侵害された AI が動くマシンでも、ユーザー本人の操作は止まらず、2 つのリスクは別々に評価されます。

## 7. 注意点・発表者の気付き

- ユーザーと同じ ID・権限でエージェントを動かすと、エージェントを個別に制御できず、人間とエージェントの行動の区別もできません
- ブロックは混乱が大きいため、状況に応じてアクセスを制限する選択肢が必要です。medium リスクの例では、読み取りは許し、書き込み・削除・グループ作成のような機密性の高い操作だけを拒否しています
- 今回の新機能は、いずれも preview 段階です。Conditional Access の動的制御は limited preview（private preview）で、public preview や GA ではありません
- デモで検出された脅威（悪意のあるファイルと社会保障番号）はそれぞれ Defender と Purview が担当し、それぞれがリスクを「中央のインテリジェンス層」に報告し、エージェントのリスクが上がっていきました

発表では、価格、ライセンス、対応する OS やエージェントの詳細な条件には触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- エージェントの操作とユーザーの操作を完全に分離でき、エージェントの責任者も把握できる
- ローカルを含む 60 以上のエージェントが自動的に発見され、ID が割り当てられる
- Defender、Entra、Purview のリスクが 1 つに統合され、どのポータルでも同じ内容が見える。セキュリティ運用担当者の負担が減る
- リスクに応じて、許可、制約付き許可、人間の承認、機密データの制限、ブロックから選べる
- 侵害されたエージェントを止めても、ユーザー本人の作業は妨げられない

顧客の導入事例は、このセッションでは紹介されていません。

## 9. まとめ

AI エージェントに白紙の小切手を渡さないための方法は、エージェントごとに専用の ID を持たせることです。Defender と Global Secure Access がローカルエージェントを発見し、Entra が ID を付与し、Agent 365 がそれを一元的に見える場所になります。リスクは Defender、Entra、Purview の統合された動的シグナルとして扱われ、Conditional Access の動的制御がそのリスクに応じて、許可から制約、承認要求、ブロックまでを選べるようにします。

デモでは、Claude Code のリスクが low から medium、high へと上がるにつれて、グループ作成や Snowflake へのクエリが順に制限・ブロックされる一方で、ユーザー自身は影響を受けませんでした。

セッションの最後には、関連の学習機会が案内されました。当日の 6 時 15 分（"6.15"）にハンズオンラボがあり、木曜の午後 2 時には、Ehud 氏と話者が、ほかの PM や開発者とともに多くの Q&A を行うセッションがあり、製品をローンチする裏側の話も聞けると案内されました。質問がある人は、ステージ脇で話しかけてよいとのことでした。
