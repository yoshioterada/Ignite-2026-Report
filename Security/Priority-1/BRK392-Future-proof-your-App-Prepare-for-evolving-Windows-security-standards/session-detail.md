# BRK392 Future-proof your App: Prepare for evolving Windows security standards

## 1. はじめに

このセッションは、Windows に入りつつあるセキュリティ機能と、アプリ開発者がいまから備えておくべきことを扱います。中心は、今週発表された **Windows Baseline Protection** です。すべての Windows 11 デバイスが満たすべき 8 つの要件を定め、IT 管理者・エンドユーザー・アプリ開発者それぞれに、状態の確認と修復の手段を用意する取り組みです。

後半では、アプリに関係の深い 4 つのテーマが続きます。

- **NTLM から Kerberos への移行**（NTLM の利用状況の把握、ブロックポリシー、コードの修正）
- **Administrator Protection（Admin Protection）**
- **コード署名と Smart App Control**
- **サービスの権限を下げる（deprivileging）取り組み**

Adobe の Michael Draper 氏が、Baseline Protection に Adobe が取り組む理由を話す場面もあります。デモは 1 つで、Microsoft 365 管理センターでのデバイス状況の確認と、Windows 11 の設定アプリ・チェスゲームを使ったエンドユーザー／開発者体験です。

Brandon 氏は、約 1 年前に、あるアプリがユーザーの知らないうちに別のアプリをインストールしたり、アプリがユーザーの認識や同意なしにデバイスの設定を変更したりする事例に気づいた、と説明しています。ユーザー、IT 管理者、アプリ開発者に話を聞くと、同じ要望が繰り返し出てきました。

## 4. 発表者が伝えたいメッセージ

最大のメッセージは、**Windows のセキュリティの基準を、これから毎年引き上げていく。アプリもそれに備えてほしい**ということです。

Brandon 氏によると、今後は新しい要件をまず「任意」として導入し、同じ attestation、同じレポート、同じ修復手段を提供して移行の準備をしてもらい、約 1 年後に同じ要件を「必須」として強制に切り替える方針です。新しい要件の候補として、NTLM のブロックや、Admin Protection、Smart App Control といった機能との連携が挙げられています。

もう 1 つの主張は、「家全体を優れたセキュリティシステムで守っていても、横のドアが開いていれば意味がない。NTLM がまさにそれだ」というものです。Baseline Protection で土台を固めたうえで、NTLM のような古い抜け道をふさぐことが続きます。

アプリ開発者に向けた具体的な行動として、最後のスライドでは、Baseline Protection を試すこと、アプリの NTLM 依存を直すこと、コードに署名すること、そしてプライベートプレビューに参加することが挙げられました。

## 5. 発表内容の詳細

### 5.1 Windows Baseline Protection とは

Brandon 氏は、スライドが 1 枚抜けていたと断ったうえで、口頭で説明しています。Baseline Protection には 4 つの考え方があります。

1. **8 つの要件**: Windows 11 のすべてのデバイスが備えるべき、セキュリティ機能とポリシーを定める。全デバイスに明確な基準を設けて、セキュリティの最低ラインを引き上げる。
2. **シンプルなツールと構成**: 特に IT 管理者が、フリート内のデバイスを要件に合わせて設定できる。
3. **シンプルな体験**: 既存のセキュリティベースライン設定は、20 ステップに及ぶ手順書で、Windows の複数のアプリや設定パネルを渡り歩くことが多い。これを、できるだけ「1 クリック」に近づける。
4. **開発者エコシステムを巻き込む**: Windows が単独で要件を定めてもできることには限りがある。アプリ側と連携することで、より先へ進める。

要件の設計では、**Goldilocks zone**（ちょうどよい範囲）を狙ったと説明されています。すべてのデバイスがすでに満たしてしまうほど易しくなく、満たせるデバイスが無いほど難しくもない水準です。多くの要件は、Windows に何年も（場合により 10 年以上）前からある機能を使っています。ところが多くのデバイスで有効になっていません。ユーザーは気づかず、IT 管理者も必ずしも注意を払っていないためです。そこで、「推奨ベースラインに到達するには、これらを有効にすべき」という明確さを提供します。

要件は 2 群に分かれます。

| 群 | 内容 |
| --- | --- |
| ハードウェア要件（スライド上段） | **すべての Windows 11 デバイスが、このハードウェア要件を満たしている**と説明されている |
| ドライバー要件（スライド下段） | ドライバーはカーネルレベルで動作し、デバイス全体にアクセスできるため、整った形式であること、既知であること、署名されていることがセキュリティ上重要 |

発表では、8 要件のうち 3 つがプライベートプレビューで管理センターに表示されていると話されましたが、8 要件すべての一覧は読み上げられていません。デモで名前が出たのは virtualization-based security と memory integrity の 2 つです。

### 5.2 3 つのユーザーシナリオ

対象は Windows 11 のすべてのデバイスで、次の 3 者が想定されています。

1. **エンドユーザー**: Windows 11 デバイスの約半数は個人利用で、IT 部門の管理下にない。設定を見て、理解し、自信を持って直し、最良のセキュリティ状態にできる簡単な体験が必要。
2. **IT 管理者**: テナント内のデバイスを構成する立場。フリート内の全デバイスを見て、ポリシーで是正できる明確さが必要。サポートの手間をかけないよう、OS 側で多くを行う。
3. **開発者**: アプリごとに固有のセキュリティ要件がある。例は、マルチプレイヤーゲーム（不正行為防止のため、デバイスが要件を満たすか知りたい）。

### 5.3 アプリがデバイスのセキュリティを気にするケース

Brandon 氏が挙げた例は次のとおりです。

- **ゲーム**: マルチプレイヤーやトーナメント型は、チート対策（anti-cheat）を重視する。Baseline Protection は、anti-cheat の知見に強く影響されており、ゲーム向けにより簡単なユーザー体験を提供することも狙っている。
- **機密コンテンツ**: クラウドからデバイスに持ってくるコンテンツを、持ち出しや改ざんされないようにしたいアプリが、アクセスを許す前にデバイスのセキュリティを評価する。
- **試験・資格認定**: 同様の anti-cheat 体験に加え、受験前にデバイスが準備できているか確認したい。
- **企業**: 条件付きアクセスポリシーにより、テナントに接続する前にセキュリティ基準を満たす必要がある。後述する attestation は、テナントですでに行われている device health attestation の上に成り立つ。
- **金融系の統制**: 同様の用途がある。
- **対象市場の把握**: 開発者が API を使って、自分のアプリが動くデバイスの状態を把握し、改善を進められる。

どのケースでも、**アプリをどう動かすかの決定権はアプリ開発者にあります**。アプリの実行をブロックする、特定の機能だけをブロックする、テレメトリや監査トレースを収集して管理者などに通知する、といった選択が可能です。

### 5.4 Adobe の取り組み（Michael Draper 氏）

Michael 氏は Adobe の consumer trust チームを率い、詐欺防止、trust and safety、AI 製品の倫理的イノベーションなど、エンドツーエンドの信頼を担当しています。ここで話題になったのは、**Genuine service**（正規品と偽造品を検出するサービス）です。

- 目的は消費者の保護。偽造製品には悪意ある要素が埋め込まれ、攻撃などに使われる。
- Adobe は検出の分野に長くおり、良いソフトウェアと悪いソフトウェアを見分けられる。ただし**インストールの後でしか検出できず**、ユーザーが許可した場合にしか通知できなかった。悪意ある者は、Adobe のユーザーへの通信経路や啓発の経路を無効化しようともした。
- この協業により、より**能動的**になり、攻撃者がプラットフォームで攻撃を始める前に、エンドユーザーに直接関与して防ぐことが可能になる。
- 「この分野で関わった中で最も生産的なパートナーシップの 1 つ」で、Microsoft から「新しい製品を作っているので参加しませんか」と声がかかり、答えは「もちろん」だった。
- OS に何を許可するかの境目に立つことが、チームにとって重要。AI の時代に、高度な攻撃を仕掛ける能力が高まっており、OS にとって最も重要な局面の 1 つだと述べた。
- 「検出して通知する」から「ユーザーが被害に遭わないよう実際に守る」への転換。Adobe は、事前に脅威を止めることに 100% 取り組んでいる。

> 補足：Adobe の導入規模や効果などの数値は、発表では語られていません。

### 5.5 開発者向けの 2 段階の API

1. **Readiness audit API**（現在プレビューで提供）: 「このデバイスは Baseline Protection を満たしているか」という 1 つの答えを返す。詳細が必要なら、要件ごとの充足状況（ブート時点）も取得できる。次回のブートで満たされるかどうかも分かるため、ユーザーに「再起動すれば良い」と伝えられる。
2. **Attestation**: 侵害されたデバイスは嘘をつく可能性があるため、要件が満たされていることを証明する必要がある。デバイスの TPM を使って、マシンのブートを示す**暗号学的トークン**を作り、別個のクラウドの attestation サービスがそれを分析して、権威ある報告を返す。まずは **クラウド検証**のシナリオから始める。

クラウド検証の流れは次のとおりです。

1. アプリが Baseline Protection API を呼び、デバイスを直す必要があるか把握する。
2. 要件を満たしていれば、Microsoft Azure attestation を基にしたクラウドサービスから、暗号学的トークンを取得する。
3. アプリがそのトークンを自社のクラウドサービスに渡す。
4. 自社のクラウドサービスが、Windows の attestation サービスに対してトークンを検証し、デバイスが要件を満たしているか確認する。

コードの流れも説明されました（コード自体は読み上げられていません）。デバイス側は、単一の API で yes/no を得られ、パラメータを変えると要件ごとの状態も得られます。要件を満たしていればクラウド attestation を始め、満たしていなければ設定へ誘導して直してもらいます。クラウド attestation は、セッションを作ってトークンを取得し、そのトークンを自社クラウドに渡して必要に応じて応答し、最後にクリーンアップします。クラウド側は REST API で、トークンを Windows attestation サービスに渡すと、デバイスの状態が分かる報告（満たしたか、個別の要件も含む）が返ります。

従来は、開発者がトークンの構築、Azure Attestation Service の利用、独自のポリシー作成まで自前で行う必要がありました。これを既製品として提供する、というのが Brandon 氏の説明です。**attestation サービスは一般提供の一部になる予定で、現在プライベートプレビュー**です。参加希望は発表の最後に案内されました。

### 5.6 今後の要件

現時点では、導入した 8 要件に集中しています。ただし目的は、完全性、最小権限設計、そして Windows の最高のセキュリティ水準を、年々引き上げることです。新しい要件は「任意」から始め、同じ attestation、レポート、修復手段で準備してもらい、1 年後に「必須」へ切り替えます。新しい要件は、OS の完全性を保つこと、本当にセキュリティに関わることを軸に、開発者、IT 管理者、エンドユーザーと対話して決めるとしています。検討中として挙げられたのは、NTLM のブロック（開発者は Kerberos を使うべき）、新しい機能との連携（Admin Protection は今回の会議で GA、Smart App Control によるアプリの評判の確認）、高権限で動くアプリの数を減らす取り組みです。

### 5.7 NTLM から Kerberos へ（Mariam 氏）

Mariam 氏は、NTLM とは何かは説明せず、「なぜ悪いか」から入っています。

**なぜ NTLM を無くすのか**: 過去 10 年で、NTLM に関連するセキュリティ事例は**約 600% 増加**し、今後も加速すると見込まれています。強力な暗号化が欠けていること、リレー攻撃・リプレイ攻撃の余地があることなど、攻撃者が入り込める機会が多いと説明されています。

**NTLM が使われる 5 つの主なケース**（テレメトリによる）

| ケース | 内容 |
| --- | --- |
| ローカルアカウント | マシン上にしか存在せず、Active Directory にないアカウント |
| IP アドレス | クライアントがホスト名ではなく生の IP アドレスで接続する。IP アドレスからは SPN が作れず、Kerberos が失敗する |
| ドメインコントローラーへの見通しが無い（line of sight なし） | DC に届かない場合 |
| 不明な SPN | IP アドレスのケースに近い |
| ハードコードされた NTLM | アプリが negotiate を使わず、明示的に NTLM を呼ぶ |

多くは「事前条件」であり、「決定」ではないという整理です。Microsoft 側で対処を進めるものが多い一方、**不明な SPN とハードコードされた NTLM は、開発者と顧客側のアクション項目**です。

**顧客調査**: 174 社に調査を行い、NTLM 削減の最大の障害について、5 つのテーマが出ました。

1. 未知への恐れ（NTLM をブロックすると何が止まるか分からない）
2. どのシステムが NTLM を使っているか見えない
3. レガシーアプリケーションの負債（サードパーティ、ファーストパーティのハードコード NTLM）
4. セキュリティよりビジネスへの影響が大きい（ブロックすると壊れる）
5. どこから始めていいか分からない

**アクション項目 1: Enhanced NTLM auditing**: Server 2025 と Windows 11 24H2 で約 1 年半前にリリースされました。従来の監査イベント 4776 と 8004 を置き換えるもので、既定でオン、クライアント・サーバー・ドメインコントローラーで使えます。誰が・何が NTLM を使うのか、理由、使用元、NTLM v1 の使用の指摘などが分かります。多くの顧客の要望を受け、先月、**Server 2019 と 2022 にも GA** しています。

**アクション項目 2: NTLM ブロックポリシー**

- **従来のポリシー**（現在利用可能）: クライアント側で、リモートサーバーへの送信 NTLM を許可するか。サーバー側で受け入れる NTLM の制御。ドメインコントローラー側でドメイン全体の NTLM 検証ポリシー。例外リストは、クライアントのリモートサーバー例外と、DC のドメイン内サーバー例外の 2 つ。
- **新しい NTLM ブロックポリシー**: 特定のユースケース単位でブロックできる。Windows Insider の **Canary と Experimental チャネル**で利用可能で、管理用テンプレートの「System」配下の NTLM にあり、enhanced NTLM auditing と同じパスです。従来の 3 つに比べ、はるかに多くのポリシーがあり、各ポリシーが 1 つの範囲（scope）を制御します。「ブロックは 1 つの大きなスイッチではなく、範囲の決定の集合」という説明です。詳細は近日公開のブログで説明される予定で、まずは小規模なテストから、ウェーブとリング（wave と ring）で段階的に広げるよう勧められました。

**アクション項目 3: コード中の NTLM を見つけて直す（開発者向け）** NTLM は、アプリの中で 3 か所に潜んでいます。

1. **ハードコードされた NTLM**: コードが NTLM を直接指定すると、Kerberos を試す機会さえない。git grep で検索できる。修正は多くの場合、**NTLM から negotiate への 1 文字列の変更**。
2. **ターゲット名**: 未登録の SPN があるなら、SPN を登録する。
3. **依存関係**: ベンダーのライブラリやサードパーティアプリがハードコードの NTLM を使っていれば、棚卸しして更新し、ベンダーと協力して移行する。

コード検索ではすべては見つからないため、実行時の検証が必要で、そこで enhanced NTLM auditing が使えます。そのうえで、開発者のテストリングでブロックし、本番のリングへ広げます。Microsoft 社内でも、**AI のスキャンツールを作ってソースコードを調べ、NTLM の使用箇所を特定**したと紹介されています。誰でも AI でスキャナーを作り、NTLM の呼び出し経路や IP アドレス・不明な SPN の使用を探して対処できる、という趣旨です。ハードコード NTLM の可能性がある代表的な API として、**SSPI、RPC、COM**（クライアントとサーバー）が挙げられました。

> 注意：negotiate を使うクライアントは、NTLM しか扱わないサーバーに対して失敗することがあります。**まずサーバー側で register と negotiate を行い、そのあとクライアントに進めてください。**これが重要な持ち帰りポイントだと強調されています。

**Microsoft 側の取り組み: IAKerb と Local KDC**（トランスクリプトの綴りは「IA Kerb」「I occur」などで、表記は確定できません）

- IAKerb は、ドメインコントローラーへの見通しが無いときにも Kerberos 認証を可能にする機能。隔離された環境のクライアントやクラウド VM に当てはまる。
- Local KDC は、各マシンで動く、組み込みの Kerberos キー配布センターで、ローカルアカウントの Kerberos チケットを発行する。NTLM へのフォールバックを無くす。
- 当てはまるのは、ワークグループのマシンや、ローカルアカウントでの SMB 認証、ドメイン参加していないマシンへのネットワーク経由のローカル管理者アクセスなど。
- NTLM に無いセキュリティ上の利点は、クライアントとサーバーの**相互認証**と、**より強い暗号**。
- **12 月に Insider へ提供される**ので、ブロックポリシーと合わせて試せる。これで NTLM を完全に無くすための手段がほぼそろう。実際に NTLM を完全に無くした顧客もいる、と述べられています。

### 5.8 Administrator Protection（Mariam 氏）

現状の問題は、管理者ユーザーが、タスクが必要としているかどうかにかかわらず、常に管理者権限を持ち歩いていることです。Admin Protection は、管理者ユーザーが**既定では標準権限で動作**し、タスクが昇格を必要とするときに、Windows が**ジャストインタイムで**管理者権限を与える仕組みです。Windows Hello で本人確認ができたあとのみ、そのタスクの間のみ許可されます。

- Windows 11 の最新ビルドで利用可能（トランスクリプトでは「August 2016」と聞こえますが、音声認識の誤りと思われ、時期は確定できません）。
- **既定ではオフ**。有効にするかは管理者が決める。
- Intune またはグループポリシーで有効化できる。テストグループから始め、段階的に展開する。
- 開発者は、自分のアプリをテストしてフィードバックを送ってほしい。

> 補足：Brandon 氏は 5.6 で、Admin Protection がこの会議で GA になったと話しています。

### 5.9 コード署名と Smart App Control（Brandon 氏）

エージェントがアプリを作ること、マルウェアの存在から、新しいアプリが次々とマシンに現れています。そこで、Windows が全体として**アプリの評判（reputation）**を強く把握することが重要になる、というのが Brandon 氏の整理です。基盤になるのが、すでに Windows にある **Smart App Control** で、その中核がコード署名です。

3 つのシナリオが説明されました。

1. ユーザーがインターネットからアプリをダウンロードする。サービスとクライアントを通じて、署名とハッシュからそのアプリを認識し、評判があれば読み込みを許可する。
2. メールなど信頼できない場所から、未知のアプリが来る。Smart App Control が同じ評判分析を行い、流れを中断して「本当に実行しますか」と尋ねる。
3. 攻撃者が改ざんしたアプリをマシンに置く。Smart App Control は悪いものと認識するだけでなく、**実行を阻止し、実行の選択肢を与えない**。

今後は、**評判の高いアプリだけを実行させる**方向に進め、分析と注目が増えていくため、コード署名が重要になります。署名されていなければ、いまが署名を設定する時期だとされています。

**Azure artifact signing**: 月額約 10 ドル（"basically $10 a month"）で、かなりの数のアプリに署名できます。より大量の署名は、少し多く払えば可能です。エンドツーエンドの体験が提供され、Brandon 氏自身もサンプルアプリすべてに使っており、簡単だと述べています。鍵は Azure に保存・保護されるため、鍵を安全に管理する手間が無く、オープンソースのプロジェクトにも組み込みやすい、という説明です。署名していないアプリがあれば、アプリの評判を高めるために最も効果的な方策の 1 つとして勧められました。

### 5.10 プライベートプレビューの案内

**Windows 開発者ポータル**（近日プライベートプレビュー）

- 署名キーを Microsoft に登録して、評判を事前にロード（preload）できる。Smart App Control がアプリに対して最善の判断をしやすくなる。
- アプリのクラッシュ分析を得られる。Windows 経由で Microsoft に返送されたクラッシュレポートが、自分のアプリ分として見られる。
- アプリに関する連絡を受け取れる。Baseline Protection の取り組みでは最も重要で、NTLM の問題の修正など、アプリに問題があると分かったときに、ポータル経由で変更すべき内容を通知できる。

**サービスの権限低下（privilege ladder）**

管理者ロールや、特に SYSTEM アカウントのロールは、マシン上のあらゆる権限を持ちます。そうした強力なアプリが、本来持つべきでない場面で大きな権限を持っているという問題です。Microsoft は、人々を「管理者」から、必要最小限の権限へ移行させる道のりを進めており、これを **privilege ladder（特権のはしご）**と呼んでいます。最上段の危険な状態から、最下段の最も安全な状態へ導く考え方です。現在 SYSTEM で動いているすべてのサービスを、より安全なものへ移すという、かなり野心的なプロジェクトで、始まったばかりだと説明されています。開発者がコードをリファクタリングし、サービスを分析して安全な状態へ移るための支援について、初期のプライベートプレビューへの参加を募っています。

## 6. デモ・手順

このセッションにはデモがあります。Brandon 氏が行い、説明は主にナレーションです。録音は音声のみのため、画面の細部は確認できません。デモの前提を説明する場面で QR コードが示され、「見逃した場合は後半でまた出てくる」と案内されました。最後の行動のお願いでも、同じ QR コードがプライベートプレビューへの参加案内として使われています。

### 6.1 IT 管理者向け: Microsoft 365 管理センターでの確認

デモの前提は、IT 管理者がテナント全体を見て、どのデバイスが要件を満たしているかを確認し、是正できることです。Windows はすべての MDM プロバイダーをサポートする予定で、ここでは Intune と **Microsoft Baseline Security Mode** に焦点を当てています。

1. Microsoft 365 管理センターで、Baseline Security Mode のパネルを開く（時間がかかるため、パネルまで飛ばしてある）。
2. 複数のポリシーがある。Baseline Security Mode は前年の Ignite で導入され、今年は新しいポリシーが追加された。
3. 下へスクロールして、Windows のポリシーを見つける。現在は 8 つのうち 3 つが表示されている（プライベートプレビュー）。プレビュー期間が終わって来年出荷されるときには、8 つの要件すべてが一覧に載り、レポートと構成の両方ができる。
4. 要件の 1 つ、**virtualization-based security** をクリックして下へスクロールすると、どのデバイスがその要件を満たしているかを確認できる。
5. 該当するデバイスを一覧にした Excel ファイルを取得する。
6. 出荷時には、すべてのデバイスをそのポリシーを満たすよう構成する「簡単なボタン」も用意される（この操作は今回は実演されていない）。

### 6.2 エンドユーザーと開発者の体験（Windows 11 デバイスとチェスゲーム）

1. Windows 11 デバイスで、新しい**設定アプリ**を開く。Privacy と Security が 2 つのタブに分かれており、セキュリティの機能が 1 か所にまとまった。その先頭が Baseline Protection。
2. Baseline Protection を開くと、要件の 1 つである **memory integrity** が満たされておらず、修正のための簡単なボタンがあることが分かる。
3. ボタンを押す前に、ゲームの体験に切り替える。見せたのは**チェスゲーム**で、対戦で相手に勝ってランキングを上げる設定。トーナメントの公平性が重要になる。
4. 1 人でプレイする場合は、実際のプレイヤーと対戦しないので問題なく遊べる。
5. トーナメント（実際の別のプレイヤーとの対戦）を試すと、アプリが「デバイスが Baseline Protection の要件を満たしていません」と表示する。アプリ自身が、設定へ直接移動できる簡単な導線を提供している。従来、anti-cheat を使うアプリは、ドキュメントへ誘導し、多くのアプリを経由させる必要があった。それを簡単にする、という説明。
6. 「enable」のボタンを押す。要件の設定はマシンのブート時に測定されるため、**再起動が必要**。
7. このデモは**仮想マシン**で実行している（実機なら、ファームウェアの設定を見せるために全員がステージに上がる必要があった、と冗談を交えて説明している）。
8. 再起動後、設定アプリで Baseline Protection が完全に有効になり、取るべきアクションがなくなったことを確認する。
9. チェスのトーナメントに戻ると、対戦相手を見つけて、そのまま体験に入れるようになった。

## 7. 注意点・発表者の気付き

- **Baseline Protection は、ほとんどがプレビュー段階。** 管理センターのポリシーは 3/8 がプライベートプレビューで、全 8 要件の一覧と「簡単に構成するボタン」は来年の出荷時に予定されています。Readiness audit API はプレビュー、attestation サービスはプライベートプレビューです。
- **要件はブート時に測定される。** 設定を有効にしたあとは再起動が必要です。
- **将来の要件は、まず任意で、約 1 年後に必須へ。** アプリ開発者は準備期間を使えます。
- **NTLM: negotiate への切り替えは、サーバー側を先に。** negotiate のクライアントは、NTLM しか扱わないサーバーに失敗することがあります。
- **コード検索だけでは NTLM をすべて見つけられない。** 実行時の検証（enhanced NTLM auditing）が必要です。
- **ブロックは段階的に。** 小さなテスト展開から、ウェーブとリングで広げます。
- **新しい NTLM ブロックポリシーは現時点で Windows Insider の Canary / Experimental チャネルのみ。**
- **Admin Protection は既定でオフ。** テストグループから段階展開します。
- **サービスの権限低下は、かなり野心的で始まったばかり。** 発表者自身がそう述べています。
- 時間の都合で、**Q&A は行われていません。** 発表後にステージ周辺で質問に答える、と案内されました。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。個別の顧客の導入成果の数値は、Adobe の話を含めて出ていません。

- **IT 管理者**: テナント内のどのデバイスが要件を満たすかを、管理センターで確認し、Excel で一覧を取得できる。出荷時には一括で構成するボタンも用意される。20 ステップの手順書に替わる、ほぼ 1 クリックの体験を目指している。
- **エンドユーザー**: 設定アプリの 1 か所でセキュリティの状態を確認し、ボタンで修正できる。アプリから設定へ直接移動できる。
- **アプリ開発者**: Readiness audit API と、クラウド検証の attestation を、既製品として使える（従来は自前でトークン構築や Azure Attestation Service の利用、独自ポリシー作成が必要だった）。ブロック、機能制限、テレメトリ収集などをアプリ側で決められる。
- **Adobe の例**: 偽造ソフトの検出が「インストール後の通知」から「攻撃が始まる前の保護」へ進む。
- **NTLM 対策**: Enhanced NTLM auditing（Server 2019 / 2022 にも GA）で可視化し、ブロックポリシーを段階的に適用し、IAKerb と Local KDC（12 月に Insider）で、フォールバックの理由そのものを減らせる。
- **コード署名**: Azure artifact signing は月額約 10 ドルから。鍵は Azure に保管されるので鍵管理の手間がない。

## 9. まとめ

Windows Baseline Protection は、すべての Windows 11 デバイスが満たすべき 8 つの要件を定め、管理者・ユーザー・開発者がそれぞれ状態を確認して修復できるようにする取り組みです。開発者向けには、readiness audit API（プレビュー）と、TPM とクラウドの attestation による検証（プライベートプレビュー）が用意されます。今後は新しい要件をまず任意で導入し、約 1 年後に必須へ切り替える方針です。

これに合わせて、アプリ側には次の準備が求められました。NTLM の利用を調べ、ハードコードされた NTLM を negotiate に変え、SPN を登録し、段階的にブロックすること。Admin Protection をテストすること。そして、**コードに署名して、Smart App Control の評判を高めること**です。最後の行動のお願いは、プライベートプレビュー（Baseline Security Mode のポータル、Windows 開発者ポータル、サービスの変更）への参加、Windows Insider Preview での Baseline Protection の試用（青いボタンを見かけたら押す）、アプリの NTLM 修正、コード署名でした。
