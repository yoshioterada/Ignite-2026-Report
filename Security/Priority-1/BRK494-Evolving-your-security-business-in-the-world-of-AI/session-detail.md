### 5.1 オープニングとアジェンダ

Gabriela が冒頭で、Microsoft Perception が 11 月 19 日に GA になると述べます（「数日後」という言い方をしています）。アジェンダは、製品紹介、GA とビジネスモデル（「Microsoft はどう商用化するのか」という声が多く寄せられていたとの説明）、パートナーの機会と go-to-market 資産、IDC の Grace による業界トレンド、EY の Ken による学びです。

### 5.2 なぜ今か：攻撃者の AI 活用

Nadia は、会場の挙手で「Microsoft Perception を今日の基調講演の前から知っていた人」を尋ね、少数だったと触れてから説明に入ります。

攻撃者の AI 活用は段階的に進んだと説明されます。

- 最初は補助的な技術として使い、偵察（recon）、構築、展開に利用していた。
- 次に、人が AI に目的を指示してタスクを実行させるようになった。
- 現在は、AI 自身が目的を設定し、攻撃を最初から最後まで実行する「自律の時代」に入りつつある。

Microsoft は 7 月に Project Perception として顧客と一部パートナーにプレビューを提供し、今週 GA を迎えます。「AI から顧客を守るには、セキュリティを AI のために一から作らなければならない」という考えです。GA にあわせて、複数のプレイブックとエージェントも提供されます。

### 5.3 Microsoft Perception とは

Microsoft Perception は「AI を使った防御」で、次の 3 つの考え方で成り立っていると説明されます。

| 考え方 | 説明 |
| --- | --- |
| スピード | AI エージェントがチームとして動き、オーケストレーションされたワークフローを通じてインテリジェンスを共有する。脅威の検知と封じ込めが行われ、チーム間の引き継ぎと重複した分析が減る。 |
| プレイブックと常時稼働の保護 | エージェントが使える状態に整えられたコンテキスト（agent-ready context）の上に作られた包括的なプレイブックが、幅広いシグナルを取り込み、サイバースタック全体で常時稼働の保護を提供する。 |
| 信頼 | チームがガードレールを設定でき、影響の大きい操作には承認（サインオフ）を挟める。ガバナンスの効いた責任ある AI の形で判断できる。 |

エージェントの構成は、赤・青・緑の 3 チームを閉ループ（closed loop）で回す形です。

- **red team エージェント**: 攻撃者の視点で弱点を探す。
- **blue team エージェント**: アラートのトリアージ、攻撃の調査、脅威インテリジェンスとの連携を担う。
- **green team エージェント**: 発見事項に優先順位を付け、どこに集中して対処するかを示す。

3 つが連動し、探索・評価・修復を継続的に回します。セキュリティチームは目的を与えるか、ワークフローを選ぶだけで、Perception が適切なエージェントを選び、判断のための根拠（バックアップの証拠と事実）も提示します。

GA では **6 つのエージェント** が、red、blue、green の各チームに分かれて提供されます。各チームのエージェントは今後も追加される予定で、これについてはロードマップのスライドで紹介すると述べています（ロードマップの具体的な内容は音声では語られていません）。

### 5.4 プレイブック

GA では、エージェントを単体で動かすのではなく、**プレイブック**（あらかじめ定義された一連の指示）を実行する形になります。選んだプレイブックに応じて、複数のエージェントが順番に実行されます。

- GA で提供されるプレイブックの一覧はスライドで示されましたが、個々の名称は音声では読み上げられていません。
- 一部のプレイブックはパブリックプレビュー中です。
- 最初に挙げられたのが **protect against threat** で、red、blue、green のエージェントが入った旗艦（flagship）のマルチエージェントプレイブックです。これを選ぶと、すべてのエージェントが 1 つのチームとして連携して動きます。
- 今後パブリックプレビューに入るものとして、「think like an attacker」の下にある 3 番目の **Web App Pen Test** が紹介されました。顧客に人気があり、狙ったセキュリティシナリオで成果が出ているとのことです。

エージェントとプレイブックの詳細は、デモブースやエンジニアリングセッションで扱うとして、この場では省かれました。

### 5.5 Security Context と新しいサイバースタック

すべてのエージェントとプレイブックは **security context** の上で動きます。security context は、Perception の下にある「エージェントが使える形の知識レイヤー」で、デジタル資産全体のシグナルをつなぎ、エージェントが優先順位付け、推論、実行を行えるようにします。ノイズを減らして文脈を渡せることが重要だと説明されます。

基調講演で語られた「新しいサイバースタック」は、次の層構造です。

1. **最下層**: シグナル、センサー、アクチュエーター。Microsoft のセキュリティワークロード、自社（ファーストパーティ）と他社（サードパーティ）のインフラ、脅威インテリジェンスから来る生のシグナル。
2. **security context 層**: 生のシグナルをエージェントが使える知識に変える。エンティティの構築と正規化、グラフやテーブルでの関係づけ、脅威インテリジェンスによる意味付けを行い、攻撃ストーリー（attack stories）や影響範囲（blast radius）を作る。
3. **Microsoft Perception 層**: その上に載る。red、blue、green の各エージェントが、API と MCP サーバーを通じて、このコンテキストを、ハーネス（harness）とモデルを使って利用する。

### 5.6 既存ツールとの連携とサードパーティデータ

Perception は、顧客がいま使っている場所に統合できるように作られています。API と MCP（Model Context Protocol）のサポートにより、SOAR、ITSM、チケット管理ツールを使い続けたまま、プレイブックを実行できます。実行のセッションや成果物のデータも、既存のワークフローに戻せます。

Perception は Microsoft Defender の中にあり、統合 SOC（integrated SOC）とコネクターを通じて、サードパーティのデータを取り込みます。スライドでは、attack investigation、detection authoring、triage の各エージェントが利用できるサードパーティのソースが一覧で示され、今後は統合 SOC を通じてコネクターを増やす計画です（一覧の中身は音声では読み上げられていません）。

### 5.7 自律の中でも、人が制御を握る

エージェントは自律的に動けますが、セキュリティ担当者は主導権を保ちます。スライドのエージェントのアクティビティ画面では、プレイブックの実行中に、重要な局面で人の判断が必要（human in the loop）になると処理が止まり、人に操作を求める様子が示されました。これはスライドを使った説明で、実際の操作を見せるデモではありません。

GA 時点の提供リージョンはスライドで示されました。ただし **GCC と GCC High では GA 時点で利用できません**。取り組み中で、顧客の要望も理解していると述べています。

### 5.8 次の課題：エージェントインサイダー

各部門にエージェント（財務エージェント、HR エージェントなど）が入ってきます。ただし、エージェントに ID がなく、適切な権限もなく、設定も正しくなければ、そのエージェントは「侵害された従業員」と同じように振る舞います。そこで防御すべきは **エージェントインサイダー（AI insider）** だと説明されます。この課題に対応する追加のエージェントが、プレビュー段階で用意されています。

### 5.9 Security Copilot との関係

パートナーから最も多く出る質問が、「Security Copilot と Perception のどちらを使うのか」です。回答は「両方必要で、並行して使える」です。

| 観点 | Security Copilot | Microsoft Perception |
| --- | --- | --- |
| 動き方 | 対話型でタスクベース。質問すると答えが返り、次の手順は人が実行する。 | プレイブックでエンドツーエンドに動く。複数のエージェントが連続して、また一緒に動き、閉ループを作る。 |
| できること | 情報の要約、Microsoft セキュリティ製品からのクエリを速く得ること。パートナーが作った多くのエージェントも動く。 | 複数のエージェントが一緒に動く、新しいエージェント型ワークフローの投資先。 |
| 例 | triage エージェントは、エンドユーザーのフィッシングのトリアージのみを見る。 | triage エージェントは複数のソースを見て、他のエージェントにつなぐ。 |
| 課金 | 個別の価格体系（既存の Security Copilot の料金）。 | 別の価格体系（5.11 参照）。 |

Security Copilot は、Perception を学んで導入していく間も使い続けられます。一方で、**新しい投資と新しいエージェント型ワークフローは Perception に向かう** と説明されています。ユースケースに応じて選ぶよう勧めています。

### 5.10 パートナーの関与とモデルの選択

プレビューでは多くのパートナーが参加しました。顧客向けにサービスを作るだけでなく、自社の SOC で Perception を実際に運用し、顧客が得るのと同じ成果を現実のシナリオで確かめたパートナーもいるとのことです。

モデルについては、「閉ループ」とは、Perception がタスクに合った適切なエージェントを選ぶことだと説明されます。さらに、**1 つのモデルがすべてのセキュリティシナリオに適しているとは考えていない** ため、Perception はタスクごとに適切なモデルを選べます。サイバー専用のモデルやフロンティアの専門モデルを継続的にリリースしているため、この内容は今後更新されるだろうとの断りがありました。

### 5.11 ビジネスモデル

調達方法は 2 つです。

1. **従量課金**（consumption-based）のサービス。使った分だけ支払う。
2. **Flex の支出プラン**（トランスクリプトでは「Flex AI Flex spend plan」と聞こえます。音声認識の都合で表記が確定できません）。

どちらも「MCAE」チャネルパートナー経由で購入できます（「MCAE」の綴りは音声認識の都合で確定できません）。

考え方は、Security Copilot の経験も踏まえた **「コストを成果に結びつける」** ことです。AI は非決定的で、入力が分からないままプレイブックごとに固定価格を付けるのは難しい、と説明されます。顧客やパートナーからは「1 + 1 = 2 になる計算機が欲しい」と求められますが、AI の見積もりはそう単純ではないとのことです。そこで、製品の UI の中に、成果の確認と支出の制御のしくみを用意しています。プレイブックの実行状況と、各エージェントのコストを確認し、計画を立てられます。これまで摩擦の多かった点で、週内のエンジニアリングの深掘りセッションに質問を持ち込むよう案内されました。

### 5.12 パートナーの機会：Microsoft とパートナーの役割

プレビューに参加したパートナーからは、「Microsoft が自分たちのビジネスを食い始めている気がする」という声があったと、Gabriela は率直に紹介します。そのうえで、Microsoft の位置づけを次のように整理します。

| | 内容 |
| --- | --- |
| Microsoft が持つもの | エージェント型セキュリティのプラットフォーム（モデルを含む）、コアとなる red/blue/green のセキュリティエージェント、オーケストレーションとコンテキストのアクチュエーター、プラットフォームへの信頼。 |
| 顧客が得るもの | より速い調査、優先順位付け、統制された対応（governed response）。 |
| パートナーが加える価値（「better together」） | 顧客固有のコンテキスト（技術面とビジネス面。エージェント型プラットフォームを信頼して導入するために何を変えるか）、異種環境の統合（Microsoft が持たず、パートナーのエコシステムが得意とする領域）、ガバナンス、修復。導入前に顧客が行うべきことを一緒に進める。 |

結論として、**Perception はパートナーのサービスを置き換えるのではなく、補強する** と述べています。

### 5.13 6 つの value pools

パートナーがオファーを考える出発点として、6 つの value pools が示されました。スライドで示されましたが、音声で説明されたのは次の 3 つです。

| value pool | 例として語られた内容 |
| --- | --- |
| Advisory and readiness（アドバイザリーと準備） | 「AI で防御する（defend with AI）」の視点では、Perception の価値を活用した **SOC readiness のオファー**（統合 SOC も同時に提供開始）。内部者リスクの視点では、**agentic inventory**（複数のティアのサービス）。モデルは主にコンサルティング案件。複数の value pools を組み合わせると、より高い収益層のサービスに進める。 |
| Exposure reduction（エクスポージャーの低減） | 買い手は CISO やセキュリティエンジニアリング担当で、優先順位が付いていない露出が課題。**attack path assessment** や **remediation factory** を作れる。最初はプロジェクト型の収益で、継続サービスへの移行を考える。 |
| Governed response（統制された対応） | 買い手は CISO、リスク管理、監査担当。きっかけは、SOC への統制付きの導入拡大。モデルは主にアドバイザリーと保証（assurance）で、これも継続的な収益に寄せていく。 |

これらは「刺激（inspiration）」のための例で、マネージドパートナーの場合は Microsoft のパートナーチームと一緒に具体化してほしい、と説明されています。

### 5.14 パートナーの GTM とリソース

進め方は、次の段階で説明されました（段階名は発話に基づく要約です）。

1. **学ぶ**: Perception を学ぶ。ローンチ時点で、営業チーム向けのピッチデッキ、さらに技術的な L200 と L300 のデッキを用意している。Microsoft の会計年度の後半（H2）にあたる 1 月から、イネーブルメントの案内が増える（「starting January」と述べています）。
2. **設計**: value pools に沿った基本的なオファーを設計する。
3. **パイロット**: 目的は「海を沸かす（boil the ocean）」ことではなく、顧客と特定の項目だけを試し、うまくいく点を繰り返し確認すること。
4. **パッケージ化**: オファーをパッケージ化する。
5. **大規模な運用**: サービスを大規模に運用する。

各フェーズに「証拠」と「出口の基準（exit gate）」を置いて、成功しているかを確かめることが提案されています。最終的にはパッケージ化したオファー、継続サービス、マネージドサービスへ進みます。

支援リソースは次のとおりです。

- **ドキュメント**: イネーブルメントのリソースと、これから出る公開ドキュメント。
- **デモ**: demos.microsoft と Regale に、Perception のシナリオごとのデモのプレイリストがある。
- **共同設計**: マネージドパートナー向けのパートナーセキュリティアーキテクト（トランスクリプトでは「Microsoft FTs」と聞こえます）が、オファー作りに伴走する。
- **案件支援（フィールド主導）**: Microsoft の担当者に依頼して使うリソース。対象アカウント向けの顧客トライアルが用意される。Azure のアクセス（POC 用）、Azure クレジットのオファー、顧客投資のリソースといった通常の消費ベースのリソースも使える。
- **案件支援（パートナー主導）**: H2 のうち少し後に、消費型ワークロード向けのインセンティブが、Sentinel Accelerator 経由で提供される。さらに、MCI ワークショップ向けのモジュールとして「Frontier Accelerate for Security, Envisioning, and POC」が挙げられた（「MCI」と一部の名称は音声認識の都合で表記が確定できません）。

新しい製品のため、H2 により多くのリソースとインセンティブが提供されます。

### 5.15 IDC の見方（Grace、IDC）

IDC の AI セキュリティ担当のシニアリサーチディレクターで、グローバルリードだと自己紹介する Grace が、アナリストの視点を語ります。

**7 月の出来事と Perception の位置づけ。** 7 月は、Hugging Face が侵害され、Microsoft が歴史的な Patch Tuesday を迎えた時期で、数週間のうちに両方が起きたと述べます。Project Perception や他ベンダーの同様の取り組みは、この出来事への対応であり、これほど早く登場したことは心強い、とのことです。

**自動化の歴史との類比。** 医療、産業の自動化、航空（fly-by-wire）の例を挙げ、自動化には 4 つの段階があると説明します。

1. 実験（experimentation）
2. 破壊的な混乱（disruption）
3. 安定化（stabilization）
4. 変革（transformation）

メディアや市場の ROI の議論は、これが歴史上繰り返されてきた流れであることを考慮していない、という指摘です。航空では、**パイロットはいなくならず、自動化の監督者になりました**。パイロットは操縦だけでなく、ヒューマンファクターズ工学や注意力の維持も訓練されるようになりました。2000 年代の初めには、警告音の意味や、自動システムが異常になったときの解釈を理解していなかったパイロットによる事故があり、航空業界はこれを訓練で解決したと言います。AI の業界は、その現実に直面しなくても済み、いま準備できる、という主張です。

**企業の現状。**

- 企業は不意を突かれている。AI を守ることに加えて、**AI を前提にしたエージェント型のセキュリティ体制** を持たなければ追いつけないことを知らなかった。15〜20 年以上続けてきた従来のセキュリティスタックの運用は、もう通用しない。
- 現在は「破壊的な混乱」の時期にあり、安定化と変革にはまだ至っていない。
- CIO と CISO の多くはまだ **ディスカバリー段階** にあり、エージェント型のワークロードに非人間 ID を適用し始めた企業は、さらに少数の一部。
- **信頼の課題**: 経営幹部チームの **45%** が、AI が自律的に動くことを信頼している。セキュリティとコンプライアンスは、エージェントの自律を妨げる最大の障壁であり続けている。信頼と自動化を高めるための安心づけと教育を、業界として行う必要があり、移行は段階的に進む。
- 企業ごとに AI の運用方法も、自動化した範囲も、懸念事項も、脆弱性のトリアージの仕方も異なり、標準化された環境はない。IDC の調査では、回答者の **94%** が、エージェントの動作を提供されたまま使うのではなくカスタマイズすることを期待している。

**パートナーが貢献できる点。** 企業は AI を自社に合わせる支援を必要としていますが、そのための地図はまだありません。環境が複雑になるほど信頼の必要性も高まり、現時点では、反復的な伴走、小さな案件、PoC、各段階で「動く」ことを示すことが必要だと述べます。

2027 年にこの領域は大きく変わると予想しています。いま伝えているメッセージは「ワークフローを端から端まで理解すること」です。エージェントによる行動が自動化されている場所、自動化を止めるべき場所、人が常に介在すべき場所を把握し、そのためには組織のあらゆる面を知る必要があります。企業にはそれができておらず、運用、AI の準備、検出された脆弱性の修復について支援が必要になります。エージェント型の環境でも、すべての脆弱性を自動で修復できるわけではない、という指摘もありました。そして「AI セキュリティは AI の実現（AI enablement）である」「この市場は縮小せず、むしろ爆発的に拡大する」と締めくくっています。

Gabriela は補足として、Microsoft が IDC とともに、パートナーの機会に関する調査を進めていると述べました。より多くのデータポイント、具体的なシナリオを提供するもので、Microsoft の会計年度の後半（second half）に出る予定です。

### 5.16 EY の経験（Ken、EY）

Ken は EY のシニアセキュリティアーキテクトとして自己紹介し、次のように話します。

- EY は「Frontier firm」で、社内で Microsoft 製品を幅広く使う大きなユーザーであると同時に、顧客向けの仕事も行っている。Ken 自身は顧客向けの役割で、プライベートプレビューのテストを多く行い、監査サービスなども顧客に提供している。Perception のテスト段階にも非常に早くから関わった。

**脆弱性の波が最初の壁。** 顧客がいま苦労しているのは、指数関数的に増える脆弱性の波です。Perception や、shielding、「MDash」（聞き取り不明瞭な製品名。音声認識の都合で表記が確定できません）などの製品に進む前に、顧客はこの山を越えなければなりません。顧客の最初の質問は「脆弱性の量から抜け出せない」でした。これまでのように重大な課題を 1 件ずつ対処する方法はもう通用せず、規模で対処する必要があります。攻撃者は、規則、論理、予算、政治に縛られずに規模で攻撃してくるため、同じ規模で応じなければなりません。Perception に脆弱性へのロジックを適用し、vulnerability shielding なども組み合わせて負荷を下げ、先に進めるようにするのが大きなポイントだと言います（shielding については翌日のセッションで詳しく話す予定とのこと）。

**エージェントの拡散。** Agent 365 のようなツールで顧客環境を見ると、エージェントが拡散していることが分かります。ユーザーは、メールや会議の処理を任せたい、自分でエージェントを作りたいと考え、Foundry で作られたもの、サードパーティが提供するもの、本人の代理で動くものが環境に増えます。顧客が気付かないうちに存在していることもあります。そのため EY は顧客と、**エージェントの挙動を制御下に置き（corral）、「高すぎる、トークンが多すぎる、リスクが大きすぎて使えない」という結論に陥らずに活用する** 支援を行っています。その結論は過去 1 年ほどなら言えたかもしれないが、攻撃側がマルチエージェントのシステムで攻めてくる今は難しくなる、という見方です。

**Security Copilot のエージェントとの違い。** Ken は、Security Copilot のエージェントは特定の 1 つのタスクを行うもので、例として「conditional optimization agent」（聞こえた綴り。音声認識の都合で表記が確定できません）を挙げます。Perception はマルチエージェントで、データとサービスに対して推論します。EY のテストでは、脆弱性に圧倒されて見つけられなかった問題が見つかりました。自分が運用するラボでも、「すべて問題なし」と思っていたのに実際は違った、という経験を話しています。赤・緑・青だけでなく、さまざまなものが組み合わさり、XDR や脆弱性管理などと連携して「ツールのスイート」になる、という見通しです。

**SOC とマネージドサービスにとっての意味。** 最初に見たとき、マネージドサービスプロバイダーの SOC オペレーターにとって恩恵になると感じました。皮肉にも、**小さなチームや小さな顧客もスケールできる** ようになり、これまで対処できなかった課題に取り組めます。命名規則が悪い、所有者が不明確、CMDB の名前が更新されていない、といった複雑な環境にも深く入り込めます。脆弱性の負荷が高まる中で、マルチエージェント型の攻撃への防御の次の一歩として、そこが印象に残ったとのことです。

**コストと FinOps。** 顧客はよく「Microsoft にちまちま課金されている」と言いますが、Ken はその議論を反転させるべきだと言います。使った分だけ支払い、コストを制御できる、という考え方です。Perception について顧客や EY 内部のグループに話すと、「かなりの費用がかかるのでは」という反応があり、そこで FinOps をどう組み込むかが何度も話題になりました。この質問は、セキュリティ担当者ではなく、技術者でもない **財務部門** から来ており、コストをコントロールして発言権を持ちたいというものです。会場のフロアにいる FinOps 担当者のところで、追跡用の新しい FinOps モデルについて話を聞くよう勧めています。

**パートナーへの助言（1 つだけ挙げるなら）。**

- Perception は Defender の中にあり、使い始めるとその理由がよく分かる。
- **単体のエージェントでプレイブックを実行するところから簡単に始める。** 何が返ってくるかを見て、エージェントの動きに慣れる。
- 出力の **markdown ファイルを読み、何を伝えようとしているかを理解する**。人間が作れる量ではないデータなので、きちんと読む。
- SOC として運用する場合も、マネージドサービスも、顧客への助言でも、ゆっくり始める。
- 顧客を脆弱性の山の向こうに連れて行き、これらのツールに乗せられれば、再発を防げる。脆弱性は燃やし尽くしても再び増えるので、新しい方法で創造的に考える必要がある。

## 7. 注意点・発表者の気付き

- **リージョン**: GA 時点で GCC と GCC High では利用できません。
- **コストの見積もり**: AI は非決定的で、プレイブックごとに固定価格を付けにくい。UI で各プレイブックとエージェントのコストを見て計画する。
- **パートナーのオファー作り**: 6 つの value pools は「刺激」のための例で、マネージドパートナーは Microsoft のパートナーチームと一緒に作る。最初から大きく進めず、小さく試し、各フェーズに証拠と出口の基準を置く。
- **導入の順序**: EY の経験では、顧客は脆弱性の量が多すぎて Perception や shielding に進めない。まず脆弱性の負荷を下げる必要がある。
- **出力の読み込み**: Perception の出力（markdown ファイルなど）は量が多いが、必ず読んで内容を理解する。
- **すべてを自動化できない**: IDC は、エージェント型の環境でも、すべての修復を自動化できないと指摘している。
- **信頼**: 経営幹部の 45% しか AI の自律動作を信頼していないため、段階的に進める。
- **エージェントの ID と権限**: ID と権限が不適切なエージェントは、侵害された従業員と同じ挙動になる。

## 8. 利用者にとっての利点

- Perception の利点として、より速い調査、優先順位付け、統制された対応。

- EY の経験として、脆弱性に圧倒されて見つけられなかった問題が見つかったこと、小さなチームでも大きな環境に対処できるようになること。

## 9. まとめ

Microsoft Perception は、red、blue、green の AI エージェントを閉ループで連携させ、プレイブックとして動かす、エージェント型のセキュリティ製品で、11 月 19 日に GA となります。GA 時点では 6 つのエージェントと複数のプレイブックが提供され、GCC と GCC High は対象外です。Security Copilot とは補完関係にあり、新しい投資は Perception に向かいます。購入は従量課金と Flex の支出プランの 2 つで、コストは成果に結びつけて UI で確認できます。

パートナーにとっては、Perception はサービスを置き換えるものではなく、補強するものです。Advisory と readiness、Exposure reduction、Governed response などの value pools を足がかりに、小さなパイロットから継続サービスへ進める道筋が示されました。IDC は、企業が AI 時代のセキュリティ体制にまだ移行途中で、手厚い支援を必要としていると述べ、EY は、脆弱性の山を越えさせたうえで、単体のエージェントでプレイブックを実行するところから始めるよう助言しています。
