# BRK348 Microsoft Purview: From understanding sensitive data to protecting it

## 1. はじめに

Copilot やエージェントは、ユーザーがアクセスできるものを何でも、機械の速度で共有・要約します。そのため、機密情報を守るには、まず「どのデータが機密なのか」を正しく把握する必要があります。このセッションは、Microsoft Purview が機密データを保護するまでの流れ（コンテンツの抽出、分類、ポリシー適用）を、分類の仕組みを中心に、技術的に掘り下げて紹介するものです。

発表では、その各ステップで直面する課題（カバレッジと鮮度、品質と効率、保護のスケール）に対して、Purview が用意している対応が示されています。主な発表は次のとおりです。

- 分類の再評価を定期的に行う **Recurring Classification Refresh**。ベースラインスキャンと年 2 回の再評価が E5 ライセンスに含まれる
- 組み込みの機密情報の種類（SIT）の品質向上と、分類を一元管理する Unified Classifier Experience
- auto-labeling のスケール拡大と、SIT を直接条件に使える DLP for Copilot grounding

Purview の管理者、セキュリティ担当者、Copilot 導入を進めるチームに向けた内容です。登壇者は、聴講後に「L300 レベルの理解」が得られると述べています。

## 3. 何に関する発表か

テーマは、「機密データはどうやって保護されたデータになるのか」という問いです。発表では、ファイルがどこに保存されていても、保護は次の 3 ステップで行われると整理しています。

| ステップ | 内容 | 課題 |
| ---- | ---- | ---- |
| 1. コンテンツの抽出 | ファイルから内容（使えるテキスト）を取り出す | カバレッジ、鮮度 |
| 2. コンテンツの分類 | 機密情報の種類（SIT）、exact data match、trainable classifiers などの分類器で内容を評価する | 高品質な分類、効率 |
| 3. ポリシーの適用 | 分類結果をポリシーの条件と照合する。これにより auto-labeling、DLP ポリシー、IRM ポリシーが動く | 保護のスケール |

それぞれの課題に対する Purview の対応は、発表の冒頭と最後で次のようにまとめられています。

| 課題 | 対応 |
| ---- | ---- |
| カバレッジと鮮度 | on-demand classification から Recurring Classification Refresh へ |
| 品質と効率 | 強化された組み込み SIT と、unified classification management |
| 保護のスケール | auto-labeling のスケール改善と、SIT ベースの DLP for Copilot grounding |

## 4. 発表者が伝えたいメッセージ

AI によって、データの状況は 3 つの点で変わったと説明しています。

1. Copilot とエージェントが、ユーザーがアクセスできるものを機械の速度で共有・要約する
2. ユーザーとエージェントがこれまでにない速さでコンテンツを作り、その多くは保存後に二度と見られない
3. 機密情報が、受信トレイ、Teams のチャット、SharePoint だけでなく、AI のチャットやエージェントの会話にも現れる

その結果、組織はより速い保護を求めており、AI はそれをいっそう緊急にします。そして、**保護はすべて、データを理解すること（分類）から始まる**というのが、発表を通した主張です。分類の結果が信頼できなければ、その後の保護（ラベル、DLP など）もすべて揺らぐため、品質と鮮度とスケールをそろえる必要がある、という流れで話が進みます。

## 5. 発表内容の詳細

### 5.1 ステップ 1：コンテンツの抽出（カバレッジと鮮度）

**カバレッジ**

カバレッジには 2 つの問いがあります。顧客が業務で使うすべてのファイル形式を読めるか。まだ触られていない（untouched）ファイルにも届くか。

分類するにはファイルを読めなければなりません。Purview が扱える形式として、Office と PDF、OneNote、ソースコードのスクリプト、そして OCR（光学文字認識）による画像が挙げられました。これを Microsoft 365 のデータ全体に対して行います。

さらに重要なのが、最近のファイルだけでなく、環境内のすべてのファイルを分類することです。以前は、今月や今四半期のファイルなど、人が今作業しているものの保護を優先していました。Purview は、作成・更新のたびに分類しているので、その部分はカバーできています。しかし今は、AI がユーザーがアクセスできるあらゆるものにアクセスできるので、**これまで保存してきたすべてを理解し、保護する**必要があります。

Chui 氏は、どの組織の SharePoint にも「デジタルの物置」のような場所があると冗談を交えて語っています（「do-not-delete」フォルダー、「archive」フォルダー、そして「New Folder 7」）。誰も New Folder 7 の中身を知らないが、Copilot は知っている、という例です。

規模の数字として、最大規模の顧客 500 社について次の値が示されました。

| 項目 | 件数 |
| ---- | ---- |
| 直近 30 日に作成・更新されたドキュメント | 650 億 |
| 保有ドキュメントの合計 | 2,600 億 |
| これまで重要視されなかったが、今は理解・保護が必要なドキュメント | 1,950 億 |

スライドでは、1 つの点が 10 億ドキュメントを表し、アクティブなデータがほかに比べて小さいことを示していました。650 億だけでなく、すべての点を保護するのが仕事だ、という説明です。

触られていないファイルは、誰かが開いたり編集したりするのを待っても分類できません。そのため Purview は昨年、**on-demand classification** を導入し、触られていないコンテンツも分類の対象に入れました。

**鮮度：Recurring Classification Refresh**

on-demand classification でカバレッジは解決しますが、「スキャン済み」が「最新」とは限りません。分類は、その時点で存在する分類器に対して行われるので、分類器の改善、セキュリティチームによる新しい分類器の追加、組織の機密性の捉え方の変化などによって、結果が古くなります。そこで、手動で再スキャンしなくても鮮度を保つために、on-demand classification を **Recurring Classification Refresh** に進化させるとしています。

1. 自動の**ベースラインスキャン**が、数年触られていないものも含めて全ファイルを分類する
2. その後、Recurring Classification Refresh が自動で実行され、分類器や組織の捉え方の変化に合わせて、**年に最大 2 回**コンテンツを再評価する

これにより、DLP ポリシー、auto-labeling ポリシーなどが、より新しい結果に基づいて動きます。

**ライセンス**：on-demand classification は従量課金（使用量に応じた課金）でした。今回、**ベースラインスキャンと 2 回の Recurring Classification Refresh を、毎年、E5 ライセンスに含める**と発表され、会場で拍手が起きています。

**シナリオ（New Folder 7 の古い契約）**

画面での操作ではなく、シナリオとして次の流れが示されました。

1. 誰も覚えていない古い顧客契約が、New Folder 7 にある。Copilot はこれにアクセスできる
2. 自動のベースラインスキャンが、誰も指示しなくても実行される。契約は分類されるが、一致する SIT がないため「機密」とは見なされず、ポリシーも適用されない
3. その後、管理者が「顧客契約はすべて機密」と識別する分類器を追加し、Copilot のやり取りで契約が共有されないようにする DLP ポリシーも追加する
4. このファイルに誰も触れなくても、Classification Refresh が実行され、再評価される。新しい分類器に一致して、契約は「機密ではない」から「機密」に変わる
5. DLP ポリシーがあるので、Copilot は契約を応答に含めないようになる

Chui 氏は、これによりユーザーは Copilot を自由に使って生産性を上げられ、古いファイルの機密データも最新の分類結果で保護できると述べ、組織が Copilot をより広く展開する自信を持てると説明しています。

### 5.2 ステップ 2：分類の品質と効率（Aashish 氏）

ここから Aashish 氏が、分類の仕組み、技術スタックの位置づけ、測定の方法を話しました。分類の大きな課題は**品質と効率**です。

**品質**

分類の品質は、測るのが最も難しいものです。顧客、部門、ファイル、ユーザーごとに変わります。それでも期待されるのは、毎回完璧に、速く、コンピュータシステムらしく再現可能に動くことです。しかし分類は、本質的に**再現可能ではなく、確率的（stochastic）**だと説明しています。品質とは、分類の判定（verdict）を信頼できるかどうかで、下流のすべてがその判定の正しさに依存します。

**効率**

最高品質の技術をただ投入すればよいわけではなく、あらゆる技術にコスト（CPU・GPU の計算量、レイテンシー）が伴います。「素晴らしい技術でも非常に遅い」のでは、今すぐ送信すべきメールの役に立ちません。品質と効率のバランスを、テナント単位、さらに何千ものテナントの規模で取る必要があります。品質だけを解いた POC は動くが、規模を上げるとコストが膨らむかレイテンシーが障害になる、とも述べています。

**文脈の例：9 桁の数字**

9 桁の数字は、場合によって機密にも無害にもなります。HR 部門の W-2 フォームで「Social Security」という語が周りにあれば機密です。サプライチェーン部門の注文書で「Order」という語が周りにあるなら、同じ 9 桁でも違います。9 桁の検出だけだと結果は非常に悪くなるため、文脈が重要という説明です。

**判定の 4 つの結果**

| 結果 | 意味 | 影響 |
| ---- | ---- | ---- |
| true positive | 機密であるものを検出できた | 良い結果 |
| false negative | 機密であるものを見逃した（分類器の不具合、ダッシュの有無などパターンの違いなど原因は様々） | データが外に出るリスク。DLP ポリシーが動かず、データが流出する。大きな問題 |
| true negative | 機密でないものを機密でないと判定した | 良い結果 |
| false positive | 機密でないもの（例：注文書の 9 桁）を機密と判定した | SOC チームが重要でないアラートを処理する運用コスト。DLP がブロックする場合は、ユーザーが「なぜブロックされたのか」と不満を持つ |

**10,000 件のサンプルでの例**

機密 1,000 件、非機密 9,000 件の 10,000 件を例に取っています（ほとんどの文書は機密ではないのが現実で、本当に機密なものを探すのは「干し草の山の針」を探すことだ、と述べています）。例の内訳は次のとおりです。

| 項目 | 件数 |
| ---- | ---- |
| true positive | 400 |
| false negative | 600 |
| true negative | 8,500 |
| false positive | 500 |

4 つの数字を人に伝えるのは大変なので、測定・改善できる指標に落とします。

| 指標 | 意味 | 例での値 |
| ---- | ---- | ---- |
| Precision | 検出したもののうち、実際に正しかった割合。false positive の数に大きく左右される | 44% |
| Recall | 本当に重要なものを見つけられたか。1,000 件のうち 400 件だけ見つけた場合。false negative に大きく左右される | 40% |
| Accuracy | 正しく判定したものを全体で割った割合（400 + 8,500 を 10,000 で割る） | 89% |

> 注意：Aashish 氏は、**Accuracy は問題を隠す**と強調しています。89% は見栄えがよいが、precision と recall は悪いままです。「Accuracy が 95%」と言われたら、precision と recall は良いのかを確認してほしい、と述べています。Microsoft 社内では precision と recall を使っており、ユーザーが分類器の品質を評価するときも precision と recall を見るよう勧めています。

**classifier factory**

測定の仕組みとして、「classifier factory」が紹介されました。分類器を構築し、大規模にテストし、precision、recall、accuracy の誤りを測り、原因を理解して、ループで修正する、という流れが継続的に回ります。テストに使うデータは、合成データ、取得したデータ、自社（Microsoft）のテナントです。この豊富なデータで、分類器の誤りがどこから来ているかが分かります。

判定が true positive か false positive かなどを誰が決めるのか、という問いに対して、**AI が判定する**（人が間に入らない自動化を大規模に使う）と説明しています。大規模に判定できるので、大規模に測定でき、変更できます。「このループでは Microsoft が GPU を使い、お客様は使わない」と述べ、その結果を、お客様のライセンスの範囲で動く製品にします。

**お客様にとっての意味と出荷予定**

- 出力は、効率的な CPU ベースの分類器で、エンドポイント、Exchange、Teams、SharePoint などすべてのワークロードで動く。precision と recall が改善する
- 見逃し（recall）が減る。チューニングや手作業が減る。false positive が減り、業務への影響が減る
- 来年展開予定で、すでに進行中。100 件が準備済みで（と聞こえます）、その後ほぼ四半期ごとに追加される。多数の組み込み SIT のすべてがこのループを通り、改善されて展開される。追加料金はなく、ライセンスに含まれる（会場で拍手）
- 開始時期、影響、対応方法に関する通知に注意してほしい

組み込みの SIT で足りない場合に備え、カスタム分類器のスタックは今日も使えます。分類器は 2 つのカテゴリーがあります。

| カテゴリー | 例 | 見るもの |
| ---- | ---- | ---- |
| trainable classifier と document fingerprinting | 税務文書か、知的財産か、といった文書の分類 | 文書全体 |
| パターンマッチ・パターン認識の分類器 | 文書内の特定のものを探す | 文書の中の特定の要素 |

> 補足：トランスクリプトでは「document printing」と聞こえます（音声認識の都合で表記が確定できません）。

### 5.3 統合された分類器の管理（Unified Classifier Experience）

顧客は、どの分類器をいつ使い、どうつながっているかを分かっていないことがあります。そこで、すべての分類器が集まる中央の場所を用意しました。これは**パブリックプレビュー**で、今後さらに統合され、高速になり、分類の影響を理解できる場所として改善していく、とのことです。

Aashish 氏が、Unified Classifier Experience のページを画面で示しながら説明しました（画面の細部は音声からは確認できません）。

- すべての分類器が、公開状態、言語、種類とともに表示される
- 特に注目すべきは最後の 2 列、**「Classified items」と「Affected policies」**
- Affected policies は、その分類器がどのポリシーで使われているかを直接たどれる。多数のポリシーの中で使ったことを忘れていても、影響を理解でき、その分類器やポリシーが本当に必要か、役に立っているかを検討できる
- Classified items は、環境のどの程度にその分類器が当てはまるかを示す。分類器の改善や、自動の定期スキャンに合わせて、この数字が変わる

分類器の新しい**作成フロー（Create Flow）**もあります。Aashish 氏は「宿題」として、ここでは見せず、各自で試すよう勧めています。

### 5.4 ステップ 3：ポリシーの適用とスケール

分類を終えたので、次は保護です。課題は常にスケールで、どのポリシーがどのデータに適用され、正しく行えているかを理解することです。ポリシーを適用している範囲と、カバーできているデータ量が分かると、保護にギャップがある場所が分かります。**分類（Recurring Scan）と高品質な分類は Microsoft が解決しますが、保護はポリシーを設定するユーザー自身の仕事**だと説明しています。

分類結果から保護に進む道は 2 つあります。

1. **機密ラベル（sensitivity label）に変換する**：ユーザーが見て理解できる（Confidential、Secret、General、Public など。色もある）。ラベルは保護も駆動し、暗号化やコンテンツマーキングなどを設定できる
2. **DLP ポリシーの条件として直接使う**：機密データが見つかれば、ポリシーが直接強制される。これはなじみのある方法

Copilot では、現在は分類を機密ラベルにしてファイルに適用し、そのラベルを DLP の条件にして grounding から外す、という流れだと説明しています。目標は、これを一貫させ、ラベルでも SIT を使った DLP でも、すべてのワークロードで行えるようにすることです。Exchange では今日でも、機密データを直接見つけて DLP を使えます。

**auto-labeling のスケール**

データが 650 億ドキュメントから 2,600 億に広がる（約 4 倍）ため、auto-labeling も拡大しました。

| 項目 | 改善 |
| ---- | ---- |
| auto-labeling のスケール | 1 日 10 万件から 50 万件（5 倍） |
| シミュレーションモード | 400 万件から 2,000 万件（5 倍） |
| adaptive scopes | SharePoint の広い範囲を、100 件ずつ選ぶのではなく、数千サイトずつポリシーに渡せる |
| default library labels と auto-labeling ポリシーの組み合わせ | 現在ラベルがない古いファイルすべてに、既定のラベルを適用できる |

default library label は 1 年以上前からありましたが、従来は新しく追加されるファイルが対象でした。今回、枠組みを変え、新しいファイルだけでなく**すべてのファイル**を対象にします。目標は、データ環境を Copilot に備えさせることです。既定値で行うか、ポリシーと条件で行うかを選べ、以前よりはるかに大きな規模で実行できます。

**DLP for Copilot（SIT ベース）**

保護ポリシーの「主役」として、**SIT を直接条件にできる DLP for Copilot** が紹介されました。ラベルを経由する必要がなく、grounding の DLP で SIT を条件にできます。Microsoft が環境全体のスキャン、鮮度の維持（E5 に含まれる）、分類器の品質向上を担当し、ユーザーは、見つかった機密情報・分類器を保護ポリシーに使うだけでよい、と説明しています。

## 6. デモ・手順

このセッションには、画面を使った紹介が 2 つあります（音声だけのため、画面の細部は確認できません）。

**(1) Unified Classifier Experience ページ**：5.3 に記載した内容（分類器の一覧、Classified items、Affected policies）。

**(2) Copilot での DLP（ラベルベースと SIT ベース）**

語られた順は次のとおりです。

1. ファイルに confidential ラベルが付いている。ラベルベースのポリシーが設定された状態で、Copilot でそのファイルにアクセスしようとすると、「restricted」と表示される。これは現在あるラベルベースの grounding で、ラベルに基づいて Copilot が使えるデータを制御できる
2. ラベルがなく、ドキュメントの中に機密情報だけがある場合を試す。ポリシーがない状態では、Copilot は質問に答える（想定どおり）
3. ドキュメント内にあった機密情報（DEA 番号）を含むポリシーを追加する
4. 同じクエリを再度実行すると、今度は**直接ブロックされる**

ポリシーを作るだけで、それ以外は Microsoft が処理する、と説明しています。

なお 5.1 の「New Folder 7」の契約の流れは、スライドで示されたシナリオであり、操作のデモではありません。

## 7. 注意点・発表者の気付き

- 「スキャン済み」は「最新」とは限りません。分類器の改善、新しい分類器の追加、組織の捉え方の変化で、結果が古くなります。
- 分類は再現可能ではなく、確率的です。品質を測るときは **Accuracy だけを見ない**ことが勧められています。
- false negative は、データが外に出るリスクです。false positive は、SOC の運用コストとユーザーの不満につながります。
- 組み込み SIT で足りない場合は、カスタム分類器（trainable classifier、document fingerprinting、パターン認識）を使えます。
- 分類と分類の品質は Microsoft が担当しますが、**保護（ポリシーの設定）はユーザーの仕事**です。
- 組み込み SIT の改善の展開時期（来年）や、開始に関する通知に注意するよう案内されています。
- Unified Classifier Experience は現在パブリックプレビューです。それ以外の機能の提供時期や提供状況（Recurring Classification Refresh、SIT ベースの DLP for Copilot など）については、発表では細かく触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **最新の分類結果で古いファイルも守れる**：ベースラインスキャンと年 2 回の再評価で、誰も触れない古い契約が新しい分類器に合わせて機密になり、Copilot から除外される
- **追加費用なし**：ベースラインスキャンと 2 回の Recurring Classification Refresh は E5 に毎年含まれ、組み込み SIT の改善も追加料金なしで展開される
- **見逃しと誤検知の減少**：見逃し（recall）が減り、チューニングや手作業が減り、false positive が減って業務への影響が減る
- **CPU ベースの効率的な分類器**：エンドポイント、Exchange、Teams、SharePoint など全ワークロードで動く
- **影響の見える化**：Unified Classifier Experience で、分類器がどこにどれだけ当てはまり、どのポリシーに影響するかが分かる
- **5 倍のスケール**：auto-labeling は 1 日 10 万件から 50 万件、シミュレーションは 400 万件から 2,000 万件
- **Copilot 展開への自信**：ラベルがなくても、SIT を条件にした DLP で Copilot が機密情報を含む応答をしないようにできる

## 9. まとめ

AI の普及で、保護すべきデータは増え、機密情報が現れる場所も広がりました。Purview は、コンテンツの抽出、分類、ポリシー適用の 3 ステップで、次の改善を進めています。

1. カバレッジと鮮度：ベースラインスキャンと Recurring Classification Refresh（E5 に含まれる）
2. 品質と効率：classifier factory で磨いた組み込み SIT と、Unified Classifier Experience（パブリックプレビュー）
3. 保護のスケール：auto-labeling の 5 倍のスケール、default library labels の既存ファイルへの適用、SIT ベースの DLP for Copilot grounding

分類の質を測るときは、Accuracy ではなく precision と recall を見ること。そして、分類は Microsoft が担うが、保護はポリシーを設定するユーザーの仕事であること。いずれも Aashish 氏が繰り返し強調した点です。
