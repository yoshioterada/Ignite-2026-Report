# BRK323 Project Perception Roadmap: New Capabilities, Use Cases & What's Next

## 1. はじめに

このセッションは、Microsoft のセキュリティ向け AI エージェント製品 Perception（Project Perception）の GA（一般提供）後のロードマップと新機能を紹介するものです。7 月に発表された Perception が、Ignite の基調講演で GA と宣言されたことを受けて、「何が新しく入り、これから何が入るのか」を、デモと顧客の声を交えて説明しています。

発表の中心は、赤・青・緑の 3 種類のエージェントを使い分けて「攻撃者の視点で穴を探す」「脅威に機械の速さで対処する」「攻撃面を小さくする」という 3 つの成果を出す、という考え方です。新しい Web アプリのペネトレーションテスト（以下、ペンテスト）エージェントのデモと、ブログ記事から検知ルールを自動生成するデモが紹介されます。後半では、Insight と St. Luke's University Health Network の 2 社が、プレビュー期間中の使用経験を語ります。

SOC（セキュリティ運用センター）やセキュリティ担当の方が、Perception の位置づけと今後の方向性を把握するのに向いた内容です。

## 3. 何に関する発表か

### 3.1 背景

発表は「攻撃者は機械の速さで動いている」という認識から始まります。Hari 氏は、レンタル型（フィッシングキットのようなもの）の攻撃キットを例に挙げ、認証情報の持ち出しにかかる時間が短くなっていると説明しています。

| 攻撃キット等 | 所要時間の変化 |
| ---- | ---- |
| EvilTokens | 14 日から 1 時間 |
| ShinyHunters | 2 日から 2 時間 |
| Storm-1811 | 3 日から 1 時間 |

AI によって攻撃者は速く、広く動けるようになり、防御側が対応に使える時間は減っています。この課題に対する Microsoft の答えが Perception だと位置づけています。

### 3.2 発表の流れ

1. Perception のビジョン（「すべてのアナリストにエージェントのチームを」）とアーキテクチャの考え方
2. 赤・青・緑のエージェントと、プレイブックによる連携
3. ロードマップ 1「Think like an attacker」（Web アプリのペンテスト）とデモ
4. ロードマップ 2「Stop threats at machine speed」（脅威インテリジェンスと検知作成）とデモ
5. ロードマップ 3「Shrink your attack surface」（脆弱性への対処）
6. 基盤となるシグナルとコントロール（サードパーティコネクタ、API / MCP）
7. 顧客 2 社との対談

## 4. 発表者が伝えたいメッセージ

発表者の主張は、**「すべてのアナリストが専門エージェントのチームを持ち、人間は常にコントロールを保ったまま、より価値の高い仕事に集中できる」**という点にあります。

Hari 氏は、AI はまだ完全な自律動作を任せられる段階には達しておらず、人間が関与し続けることで AI が何をしているかを確認できる、という立場を取っています。そのため、すべてのプレイブックのセッションとエージェントの動作はログに残り、監査できるようになっています。

もう 1 つの軸は、Perception が「見つけるだけでなく、直せる」ことです。ペンテストで見つけた問題を、緑のエージェントが修復につなげるといった流れが、発表全体で繰り返し強調されます。

## 5. 発表内容の詳細

### 5.1 Perception のビジョンと全体像

Hari 氏は冒頭で、Perception を 7 月に発表して以来、100 社を超えるプレビュー顧客が使って多くのフィードバックを寄せたこと、そして Ignite で Satya が GA を宣言したことを述べています。

Hari 氏は、Perception の最終的な姿を「専門家のエージェントのチームが連携し、人間のコントロールを保ったまま、企業が攻撃を受けているデータ全体にわたって動き、推論し、状況を把握する」ものだと説明しています。タグラインは "We help defenders get ahead with agentic security" です。

その土台として、基調講演でも使われた「サイバースタック」のたとえを引いています。

- **最下層はシグナルとコントロール**です。Microsoft が持つ Defender、Entra、Purview、Azure のデータを集めて、そこから推論します。
- **その上でエージェント、ハーネス、モデルが動きます。** Perception のエージェントは「マルチモデル」で設計されており、複雑なタスクには大きなモデル、そうでないタスクにはより単純なモデルを使い分けます。目的は単なるコスト最適化ではなく、お客様に最良の効果をできるだけ速く届けることだと説明しています。

### 5.2 赤・青・緑のエージェント

Perception のエージェントは 3 つのグループに分けられています。

| 色 | 役割 | 位置づけ |
| ---- | ---- | ---- |
| 赤（Red） | 企業環境を能動的に調べ、設定の問題や脆弱性などの穴を見つける | 侵害前（pre-breach）。人間のレッドチームに相当 |
| 青（Blue） | トリアージ、調査、検知ルールの作成 | 侵害後（post-breach）。Defender などに上がるアラートへの対応 |
| 緑（Green） | 最も重要なエクスポージャー（露出）を特定し、修復を調整してリスクを下げる | 「修復担当（fixers）」 |

3 つのエージェントは 1 つのループとして連携します。赤のエージェントの出力を青に渡し、緑が修復する、という流れをプレイブックで組めます。狙いは、人間が大量のアラートに埋もれず、価値の高い成果に集中できるようにすることです。

7 月の発表時点のエージェントは、GA に向けて有用性、性能、速度が高められ、使用するトークン数も減っています。GA では Web app pen test（赤）と Risk reduction（緑）の、新しいエージェントが加わりました。これらは今後数か月に登場するエージェントのごく一部で、Microsoft のセキュリティチーム全体がエージェントを開発している、とも述べています。

### 5.3 プレイブック、監査、エージェント ID

- **プレイブック**でエージェントのチームを動かします。チャットから起動することも、クリックして直接起動することもできます。
- すべてのプレイブックのセッションと各エージェントの動作は記録され、完全に監査できます。
- Perception のすべてのエージェントには**エージェント ID** があります。Agent 365 から一覧し、権限を確認し、ブロックしたり停止したりできます。
- エージェントは RBAC（ロールベースのアクセス制御）で設計されており、必要な権限しか持ちません。権限を上書きして、いつでも実行を止めることもできます。

### 5.4 ロードマップ 1：Think like an attacker（赤のエージェント）

自分が安全かどうかを知る最善の方法は、環境の穴を把握することだ、という考え方に基づく領域です。

#### Web app pen test エージェント

GA で発表された新しいエージェントです。外側から攻撃する「アウトサイドイン」型で、Web サービスを調べて弱点や設定の問題を洗い出します。企業環境へのアクセスは必要なく、ネットワークの外側から Web サービスを攻撃できます。

これを使う 2 つの新しいプレイブックが用意されています。

1. **Web pen test**：基本のプレイブックで、Web app pen test エージェントを実行します。
2. **Protect web app**：Web pen test エージェントと緑のエージェントを組み合わせます。ペンテストが見つけたファイアウォール関連の問題を、緑のエージェントが修正します。

#### MDASH との連携

Hari 氏は MDASH を、ソースコードの脆弱性スキャンシステムと説明しています。ソースコードを読み、実際のゼロデイ脆弱性（読み取り後の書き込み、バッファオーバーランなど）を見つけるものです。

Web pen test 用のソースコードを MDASH に渡すと脆弱性の一覧が生成され、Web pen test はそれを使って Web サービスを狙い撃ちで攻撃します。これは「ブラックボックステスト」ではなく、自分たちのソースコードの知識を使った攻撃です。そのため、見つかる問題は、コンパイラが 500 件出すような警告ではなく、実際に悪用可能な脆弱性になる、という説明です。

#### 評価（eval）

Perception のすべてのエージェントは、厳密な eval（評価）の上に作られているとしています。Microsoft は M365 と Azure を運営しており、国家レベルの攻撃者や金銭目的の攻撃者から日々攻撃を受けています。その攻撃のテレメトリを使ってエージェントを訓練しているため、実際のデータで穴を見つけ、修復できる、という主張です。

Web pen test については、Incalmo という第三者の評価会社（シリコンバレー拠点、音声認識の都合で表記が確定できません）と独立検証を進めています。スライドで示された結果は次のとおりです。

- OpenAI Codex の最新モデルと比べて、2 倍を超える性能（発話は "more than double better"）
- Incalmo 側の同等のペンテスト（Terminus baseline harness）と比べて、40% 上回る
- ガードレールのないエージェントよりも安全で、より多くのタスクを解決する

### 5.5 ロードマップ 1 の今後

Abe 氏が、赤のエージェントの今後の予定を次のように紹介しています。

- 認証のサポート改善と、エンタープライズ向けの認証フローへの対応
- レッドチームのテスト専用のロールを追加し、誰が実行でき、誰が結果にアクセスできるかを制御できるようにする
- 証拠パッケージの改善（すべてが真陽性になるよう効率を高める）
- 修復フローの改善：どのコードの検出結果が悪用可能かを確認する処理を、より自動化する
- コードパッチの追加。デモで見た WAF ルールとアプリケーション設定の提案と合わせて、日々のワークフローに統合する

Hari 氏は補足として、エージェントが修正案そのものを提案するようになり、バグだけでなく **GitHub リポジトリに適用できる PR 付きの修正**を出せるようにする、と述べています。

### 5.6 ロードマップ 2：Stop threats at machine speed（青のエージェント）

Hari 氏は、多くの SOC は予算が足りず、数も足りていない、と述べています。CISO からは「アラートが多すぎて溺れている」という話を聞くそうです。ここでは次の 2 つが紹介されています。

- **Detect emerging threats**：TI（脅威インテリジェンス）エージェントが、外部のブログや投稿を分析して TTP、IOA、IOC を理解します。それを検知作成（detection authoring）エージェントに渡し、自社環境向けの検知アラートを生成します。Hari 氏が特に期待している機能として紹介されました。
- **トリアージエージェント**：一般的な Microsoft Defender のキューにあるアラートの約 80% を処理できるようになった、と説明しています。「多くのお客様の Defender キューのアラートのほぼ 80% を、トリアージエージェントが自動で処理できる」という意味です。これらのエージェントは自動でトリガーでき、アラートごとに右クリックして「トリアージして」と指示する必要はなく、バックグラウンドで動きます。

#### 今後の予定

- **TI、ハンティング、リバースエンジニアリングのエージェント**：新しい脅威を理解し、それが自社環境にあるかを調べるためのエージェントです。過去に遡ってハンティングし、何が起きたか、あるバイナリがどう攻撃してくるかを示す、と説明しています。デモで見たのは「今後を見据えた」検知で、こちらは「過去に遡る」方向です。
- **企業テナントのメモリ（SOP の取り込み）**：お客様から最も要望の多い機能の 1 つとされています。多くの企業が持つ標準作業手順書（SOP。例えばファイアウォールルールの表、管理者や閲覧者を示す表など）を Perception に読み込ませ、エージェントがそれを学習して検知をより良くするというものです。

### 5.7 ロードマップ 3：Shrink your attack surface（緑のエージェント）

セキュリティチームは、対応しきれないほど多くの脆弱性を見ており、課題は「どこでリスクが対応を求めているか」を知ることです。新しい **Reduce exposure risk** プレイブックは、次の流れで動きます。

1. 脆弱性を調査する。
2. パッチがあれば、Intune と連携してパッチを適用できる（API を使う場合は Intune を呼び出して有効化する）。
3. パッチがない、あるいはパッチが危険な場合は、パッチを当てられるようになるまでの時間を稼ぐために、対象を絞った保護で脆弱性を保護（シールド）する。

2 番目の経路が必要な理由として、サーバーが非常に重要でダウンタイムを許容できないなど、すべてのパッチをすぐに適用できるわけではないことを挙げています。

そのほか、次の 2 点が予告されました。

- **Exposure management が Perception に移ります。** 企業全体の資産のリスクビューを、Perception から離れずに確認できるようになります。
- **Secure your agents**：AI とエージェントを保護するインターフェースが近く登場します。どのエージェントが公開されているか、リスク面はどこか、ブロックできるか、各エージェントが悪い動作をしていないか詳しく調べられるか、といった点を扱います。Hari 氏は、Microsoft 社内では開発者 1 人あたり 10 個、PM 1 人あたり 25 個のエージェントを書いている、と話しています。

### 5.8 基盤：サードパーティコネクタと API / MCP

#### サードパーティコネクタ

9 月に、Defender のお客様が Sentinel を利用できるようになったことが発表されました。これにより、Defender 内で Sentinel のサードパーティコネクタを使えます。GA の時点で、Perception のエージェントが、Sentinel に取り込まれたサードパーティコネクタのデータを推論できるようになりました。

対応する最初の 3 つのコネクタは **AWS、Salesforce、Okta** です。Sentinel には 500 のコネクタがあるのに 3 つだけな理由について、Hari 氏は eval と関係があると答えています。サードパーティのデータを見るだけでなく、スキーマを理解してトリアージや検出、検知作成といった本当のセキュリティ成果を出す必要があり、Sentinel SIEM に入るデータには統一されたスキーマがないため、それぞれ推論と理解のためのエンジニアリングが要る、という説明です。お客様の声に応じて対応を広げ、すでに複数のコネクタの要望があることも述べています。

#### API ファースト

Defender ポータルを使わないお客様も多く、ServiceNow や Jira をチケット管理に使うお客様、コマンドラインを好むお客様もいます。そこで、UI で行えることはすべて API 経由で行え、API とあわせて MCP も公開される、**API ファーストのプラットフォーム**だと説明しています。

事例として BlueVoyant が挙げられました。BlueVoyant は API と MCP を使って「BlueVoyant Perception Studio」という独自のユーザー体験を作り、Defender に入らずに同じエージェント体験を提供しています。機能や忠実度の損失はない、というのが Hari 氏の主張です。

### 5.9 顧客対談（Insight、St. Luke's）

Hari 氏が司会となり、プレビューから使っている 2 社に質問しました。

**Will Pocknell 氏（Insight）**

- Perception によって、アナリストが短時間で、より深い調査ができるようになりました。複数インシデント・複数ケースにまたがる調査は 60 分、あるいはそれ以上かかっていたものが、**15 分**でできるようになったそうです。
- エージェントの判断が人間のアナリストと一致する割合は **99.7%** でした。リアルタイムのアラートのトリアージと、過去のインシデントに遡った確認の両方に基づく数字です。Hari 氏は、経験豊富な SOC の結果と同等の結果が 99.7% の割合で出た、と言い換えています。
- Insight は、現在限定プレビュー中の AI のセキュリティ保護にも早くから取り組んでいます。そこで学んだのは、環境全体の把握の必要性です。クラウド、デバイス、データセンターなどにエージェントが広がる中で、エクスポージャーリスク、ブラストラディウス（影響範囲）のリスク、ランタイムのリスクなど、複数の面から各エージェントのリスクを理解したいと述べています。シグナルはエージェントの速度で変わるため、緑のエージェントで環境を継続的に再評価し、問題が起きたら他のエージェントで対処したい、という考えです。
- 今後に期待する点として、アラインメント（整合）の問題や、エージェントがシステムに対して持つ権限、それが正しく使われているか、アタックグラフとブラストラディウスの把握、ユーザーの操作に基づいて正しいリソースへの正しいアクセスを要求しているかの確認を挙げています。
- レッドチームに関連して、脅威ハンティングも時間のかかる作業だと述べました。これまでは後ろ向きになりがちでしたが、Perception がニュース記事や脅威インテリジェンスのフィードを自動で確認して先回りして行うことで、SOC に時間を戻せるとしています。

**David Miller 氏（St. Luke's University Health Network）**

- Hari 氏は St. Luke's を、フロンティア AI の導入に「手順書はない」状況のお客様と紹介しています。David 氏も「手順書はなく、数か月にわたり試行錯誤してきた」と答えています。
- SOC のトリアージエージェントで、**月に約 250 時間**を節約できたそうです。人間とセキュリティエージェントの判断を突き合わせると、エージェントはほぼ的確だったといいます。
- 午前 2 時に起きたとき、すでにプレイブックが用意され、すべて相関付けされていて、自分は「ボタンを押してよいかを確認して押す」役割になるという例を挙げています。医療機関では、手術中にユーザーをロックアウトしたり、アカウントに対処したりはできないため、**毎回、最初から正しくなければならない**と述べています。
- 医療機関には「〜ology」（神経学、放射線学など）にまたがる多くの機器があり、自分たちの都合ではパッチを当てられないものもあります。その可視性が大きな価値で、エージェントの速度で動ける必要があるとしています。
- エージェントによるレッドチーム（ペンテスト）について：ペンテストは通常は静的なスナップショットで、修正に取りかかるころには手遅れになり、問題が次の優先事項に移ってしまいます。今後は「5 分以内に直す」か、「5 分以内に直せない理由のレポートを作らせる」という使い方ができると期待しています。パッチを当てられない機器について、ダウンタイムの見込みを経営層向けにまとめるレポートも、5 分で作ってもらえるといいます。ただし、内容を確認する人間は関与し続けるとしています。
- 脅威調査に関する機能（David 氏の発話では「lookup tool」。どの機能を指すかは発話からは特定できません）について、経営層から「自社は何に対して脆弱か報告してほしい」と言われることが多く、それを 5 分で出せるのがありがたい、と述べています。

両氏に共通した発言として、SOC の人員を減らすのではなく、より多くのことをこなし、より効果的に動けるようにしたい、という点がありました。

## 6. デモ・手順

このセッションには 2 つのデモ（画面を使った説明）があります。録音は音声のみのため、画面の細部は確認できません。また、ライブ操作か録画かも、発話からは確定できません。2 つ目のデモについては、Hari 氏が「PowerPoint をクリックして進めている」と話しているため、スライド上で画面を順に見せる形だったことが分かります。以下は、語られた内容に基づく順序です。

### 6.1 Web アプリのペンテスト（Abe Starosta 氏）

最初に、セキュリティチームが抱える 3 つの課題が設定されました。（1）攻撃者より先に Web アプリの脆弱性を見つける（攻撃者も AI を使い、こちらの何か（発話は "clone our decks"。音声認識の都合で確定できません）を複製して Web アプリに向けられる）、（2）どれが真陽性かを検証して誤検知に時間を使わない、（3）できるだけ速く修正する、の 3 つです。

1. Perception を開き、「Agents」から「Web Pen Test Agent」を開く。
2. 「Approved targets」で、赤のエージェントのスコープ（アクセスしてよいドメイン、URL、サブドメイン）を管理する。デモでは、ドメインを追加し、DNS TXT レコードで所有を確認している。
   - Hari 氏の補足：所有確認の目的は、他人のドメイン（例として google.com）を攻撃対象にできないようにすることです。
3. プレイブック「Run Web Pen Test」を開き、「Start New Session」をクリックする。表示されるセッション設定画面で、ターゲットを選ぶ。
4. 認証を設定すると、認証付きのペンテストになり、より多くの脆弱性を見つけられる。
5. MDASH を使ったソースコード対応のペンテストのチェックボックスを選び、対象 Web アプリに関連するリポジトリを選ぶ。デモでは、MDASH がそのリポジトリをすでにスキャンしており、重大度の高い脆弱性が 38 件見つかっていることが表示された。
6. セッションを開始すると、エージェントはまず探索フェーズに入り、ペンテスト計画を生成する。計画は、承認、却下、または別の指示のいずれかを選べる。デモでは承認している。
7. エージェントは数時間作業し、完了すると結果を返す。
8. 「pen test report」を開く。見つかったすべての脆弱性と、それが真陽性で悪用可能であることを示す証拠が載っている。例として、スクリーンショットの証拠、悪用可能と確認された脆弱性、脆弱性を再現するためのコマンドを含む検証内容が示された。さらに、緩和や修正のための WAF ルールとアプリケーション設定の更新案が提案される。
9. 「Exploit Validation Report」を開く。MDASH が見つけたすべての結果を列挙し、どれが外側から悪用可能だと確認されたかを示す。確認されたものから優先して対処できる。
10. エージェントとチャットして、追加の質問ができる。例として「修正すべき上位 5 件の脆弱性は何か」と聞いている。

Hari 氏は、エージェントに「結果を説明して」「上位 5 件、上位 10 件を教えて」「なぜそれを選んだのか」と聞ける点が重要で、他社製品で同様のことができるものは知らない、と述べています。

### 6.2 ブログ記事から検知ルールを作成（Hari Pulapaka 氏）

Hari 氏は、発表中に「PowerPoint をクリックして進めているが、実際のコードで、Perception を使い始めると見えるのはこの画面だ」と説明しています。

題材は、Bleeping Computer の記事（Crimson Collective が AWS 環境を狙い、公開されたキーで新しいユーザーを作成し、データを持ち出し、管理者に昇格し、サービスを停止してランサムウェアのようなことをする、という内容）です。通常は CISO がこの記事を読んで「自社は守られているか」とたずね、検知エンジニアに問い合わせる流れになる、という前置きがありました。

1. 標準の Perception チャットで、画面下部のプレイブック「Detect emerging threats」を選ぶ。
2. この記事の URL を入力し（他のブログでも構わない）、「Next」をクリックして、TI エージェントに分析を始めさせる。
3. 画面の右上には、脅威インテリジェンスエージェントと検知作成エージェントの 2 つのエージェントが表示され、右下に生成されたレポートが表示される。エージェントと直接対話して、何をしたか説明を求めることもできる。
4. TI エージェントのレポートには、MITRE ATT&CK フレームワーク、TTP、IOC、攻撃の指標、ハッシュ、C2 ネットワークなどが含まれる。
5. 検知作成エージェントがレポートを分析し、TI エージェントが見つけた Crimson Collective の 14 の技法のうち 11 をカバーする、**6 つの検知**を提案した。
6. これらは、お客様自身の企業の XDR データに対して検証されている。汎用的なものではない。
7. 例として AWS 認証情報の検知を開いた。盗まれた AWS 認証情報が機密性の高いサービスに対して使われることを探し、記事内の証拠までさかのぼる。1 時間ごとに実行されるスケジュールで、今後は変更できる。KQL クエリも表示でき、いつでも変更できる。
8. Perception はこのクエリを再実行し、**過去 15 日間の自社環境**に対して検証したことが画面上部に表示されている。誤検知でキューを埋めないよう、お客様のデータに対して検証とチューニングを行う、という説明です。
9. 「Next」をクリックして、これらの検知を有効にする。

Hari 氏は、これをもって「AI の検知エンジニアを Perception エージェントの価格で手に入れた」と述べ、ブログから自社環境向けの検知アラートまで約 5 分で到達できると説明しています。

## 7. 注意点・発表者の気付き

- **人間は常にループの中に残ります。** Hari 氏は、AI はまだ完全な自律動作を任される段階にない、と明言しています。David 氏も、医療機関では誤った操作が許されないため、人間が確認して最後に実行すると話しています。
- **所有していないドメインはペンテストできません。** DNS TXT レコードで所有確認を行う仕組みになっています。
- **サードパーティコネクタは 3 つに限っています。** 数を増やすことよりも、スキーマを理解して実際のセキュリティ成果を出せる品質（eval）を優先しているためです。
- **誤検知を増やさない設計です。** 生成した検知は過去 15 日間の自社データで検証し、キューを埋めてしまうことを避けます。
- **ロードマップの項目**（コードパッチ、SOP の取り込み、TI・ハンティング・リバースエンジニアリングのエージェント、Secure your agents、Exposure management の統合など）は「これから登場する」ものとして説明されており、具体的な時期は発表では示されていません。
- Hari 氏が冒頭で触れた OpenAI と Hugging Face の事例は、録音の内容が不明瞭で、詳細を確定できません。ここでは、赤のエージェントの役割を説明するための例として紹介されていた、とだけ記します。

## 9. まとめ

Perception は GA となり、赤（攻撃者の視点で穴を探す）、青（脅威に機械の速さで対処する）、緑（攻撃面を小さくする）の 3 種類のエージェントを、プレイブックで連携させて動かします。人間は常にループに残り、エージェントには ID と RBAC が設定され、動作は監査できます。

GA で追加された Web app pen test は、MDASH と連携して「実際に悪用可能な」脆弱性を見つけ、WAF ルールなどの修復案まで提示します。検知側では、ブログ記事の URL から TTP を抽出して自社データで検証済みの検知ルールを作成するデモが示されました。今後のロードマップには、コードパッチ、SOP の取り込み、ハンティングやリバースエンジニアリングのエージェント、Reduce exposure risk、Secure your agents などがあります。

Sentinel のサードパーティコネクタは AWS、Salesforce、Okta の 3 つに対応し、UI の機能はすべて API と MCP からも使えます。Insight と St. Luke's は、調査時間の短縮、99.7% の一致率、月約 250 時間の削減という成果を語りました。
