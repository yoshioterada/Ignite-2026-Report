# BRK337 Prioritize and remediate your riskiest agents with Project Perception

## 1. はじめに

このセッションは、組織内の AI エージェントを「見つけ、封じ込め、守り、リスクの変化に合わせて適応させる」ための Microsoft のセキュリティスタックを、実際に動くデモで紹介する 45 分のブレークアウトです。中心になるのは、AI エージェントのリスクを継続的に把握・調査・対処する **Perception**（セッションタイトルでは Project Perception）です。トランスクリプトでは、Perception が当日 GA になったと語られています。

発表者は冒頭で、「ライブコードで、モックは使わない」とデモへの姿勢を述べています。デモは大きく 2 つあります。1 つ目は Claude Code を使った、エージェントへの時間制限付きアクセスと多層防御の様子。2 つ目は Perception のポータルで、エージェントの棚卸し、リスク分析、封じ込めのプレイブック、動的な条件付きアクセスまでを順にたどる内容です。最後の約 7 分は Q&A で、価格、MXC、SASE、サードパーティエージェントの制御などの質問が出ました。

## 3. 何に関する発表か

### 3.1 背景

Ankur 氏は、以前の講演で扱ってきた shadow IT になぞらえ、**shadow agents** という言葉を使っています。人間向けに作られた仕組みはエージェントの世界では通用しない、というのが出発点です。しかも新しい脅威は、疲れず、あらゆる隙間を探し、適応的で多様に姿を変え、知的であるため、非常に厄介な相手だと説明されました。

お客様から繰り返し聞く要望は次の 3 つとされています。

1. **すべてを見る**：自社で作った・買ったエージェントだけでなく、あらゆるソリューションが新しいエージェントを有効にしてくるため、全体を見る必要がある
2. **各エージェントができることを封じ込める**：全員がエージェントを ID システムに登録してくれるクリーンルームは期待できないため、最初から敵対的なシステムとして扱う
3. **マシンの速度で行う**：人間が承認するやり方では間に合わない

Ankur 氏は、自動運転の比喩を使い、最初はハンドルに手を置いたまま、レーン（ルール）を定義してその中を走らせ、必要なときに割り込む形で始める、と述べています。

デモの範囲についても、冒頭で次のように述べられています。Fabric、SharePoint、Cosmos DB のような Microsoft のデータ境界内のリソースだけでなく、すべてのエージェントとリソースを封じ込めること、常時働くこと、ID とセキュリティのあらゆる層が連携して働くことです。どれか 1 つでも開いたままなら「ゲームオーバー」だと語られました。

### 3.2 3 層のサイバーセキュリティスタック

この数か月、Microsoft 全体で新しいスタックを作ってきたとして、3 つの層が示されました。

| 層 | 内容 |

## 5. 発表内容の詳細

### 5.1 エージェントの権限を「タスクと時間」で絞る

Ankur 氏は、エージェントから「これをやってよいか」と何度も確認され、疲れて「好きにやって」と認証情報を渡してしまう経験を挙げ、これを「恐ろしい」と述べました。理由は、本来の仕事（例：CRM ダッシュボードを作る）をしたいだけで、どのテーブルに何があるか分からないため、ついすべて任せてしまうからです。

そこで Microsoft が作ったのが、**identity orchestrator（access orchestrator）** です。これはプロンプトをインターセプトして意図を理解し、**必要なテーブルだけに権限を適切なサイズ（right size）に絞り**、時間制限付きの読み取り権限を与えます。説明では次の特徴が挙げられました。

- タスクベース、時間制限付きのアクセスである
- このマシン上で動いている特定のエージェントインスタンスに固有で、ユーザー本人とは別に扱われる
- 人間が承認に関わらない。データベース管理者に承認を求めても、エージェントは待ってくれないため

### 5.2 Perception とその拡張

Kristina 氏は、Perception を「マシンの速度で動くための新しい agentic security system」と紹介しました。エージェントがチームとして動き、情報を共有しながらエンドツーエンドのワークフローを実行します。プレイブックにより目指す成果に向かって動かすことができ、「自動化するが、あなたがコントロールを持つ」という信頼の考え方で作られています。

もともとは SOC 向けでしたが、AI とエージェントの資産にも広げています。

| チーム | 役割（AI・エージェント資産に拡張した場合） |
| --- | --- |
| red team | 攻撃者のように環境を探り、エージェントが悪用しうる点や、エージェントを狙う攻撃の入口を見つける |
| blue team | アラートをトリアージする。安全な AI 活用への投資により、runtime prompt injection など新しいアラートが出てくる。他のセキュリティアラートと同様に扱える |
| green team | 新しい保護、コントロール、センサー、アクチュエーターをデプロイして、態勢の強化とエージェントの封じ込めを行う。「発見を修正に変える」役割 |

Green agent は、エージェント資産全体を評価し、ギャップを探し、常時稼働し、新しいセキュリティガイダンスや新機能にも追従します。権限を与えられれば、コントロールをデプロイし、アクチュエーターを動かせます。そのコントロールは 1 つの製品ではなく、セキュリティスタック全体に及ぶ、と説明されました。

**プレイブック**は、入力（望ましい状態や既知のギャップ）、出力（推奨事項）、そしてそれを実行して得られる結果、という形で説明されています。

### 5.3 4 つの成果：Know / Contain / Protect / Adapt

Kristina 氏は、「Ankur 氏の話にも出た know、contain、protect、adapt（キーノートでも目にしたかもしれない）」という 4 つの重要なセキュリティ成果に沿って、デモを進めました。詳細は 6 章に書きます。

### 5.4 基盤となる多層防御（Joanne 氏）

Perception が分析してアクションを取るための基盤として、次の層が示されました。

1. **隔離と封じ込め**：特に従業員のデバイス上のローカルエージェント。エージェントに固有の zero trust 権限を与え、エージェントそのものを信頼しない。Ankur 氏のデモのように、タスクごとに評価・承認され、タスクベースで時間制限付きになる
2. **データ保護**：エージェントに入るデータ、モデルから来るデータ、ユーザーが機密データを入れる場合、エージェントが機密データを出力・利用する場合の、誤用と悪意のある試みの両方
3. **ランタイムの脅威対策**：OWASP Top 10、MITRE、NIST のフレームワークに沿って、主要な脅威が網羅されるようにする

エージェントのリスクが変わったら、ランタイムでアクションを取るというのが全体像です。

**既存の製品との対応**として、エージェントを「クラウドエージェント」と「ローカルエージェント」に大別し（「いろいろな分け方があるが、この目的ではこれが最もシンプル」）、次のように説明されました。

| 製品 | 役割 |
| --- | --- |
| Defender | クラウドエージェントとエンドポイント上のエージェントへの基本的なセキュリティ保護。脅威保護ポリシーも提供 |
| アクセス保護 | エージェント自体に対する zero trust・最小権限のアクセスを強制する（発表では「そのためのアクセス保護を追加する」と語られ、製品名は挙げられていません） |
| Purview DLP | ネットワークを流れる機密データを検査し、許可かブロックかを決める。sensitive information type（音声では "SIP base"）に基づく |
| Entra Global Secure Access（GSA） | ネットワークセキュリティ。AI プラットフォームに組み込まれた機能が「深さ」の保護を与え、ネットワークが「幅」の保護を与える。ネットワークは、何も通り抜けないようにする最後の網（choke point）と表現された |

### 5.5 リスクの 3 つのレンズと context engine

各層は保護するだけでなく、状況を知るためのシグナルも出します。それを次の 3 つの観点でまとめます。

| 観点 | 内容 |
| --- | --- |
| Runtime risk | 振る舞いの観点。prompt injection の試み、機密データの漏えい試行、不適切な MCP ツールアクセスなど |
| Exposure | 何にアクセスでき、それが保護されずに残っていないか。権限が過剰なエージェントは、その状態が残り続けるのを避けたい |
| Blast radius | 何に到達でき、影響は何か |

これらが **context engine** に集約され、ビッグデータの問題を処理して、**エージェントごとに agent risk** が割り当てられます。このリスクはエージェントのライフサイクルを通じて付いて回り、上下します。リスクが上がったときに、条件を設定しておけば、リアルタイムでアクチュエーターが動きます。選択肢は次のとおりです。

- アクションを許可する
- アクセスを封じ込める
- 人間を介在させてアクセスを検証する（human in the loop）
- アクセスを制限する
- 完全にブロックする

数十万のエージェントがあれば、数十万のエージェントリスクレベルがあり、設定したコントロールに基づいてブロックできる、とも述べられました。ミッションは、異種混在のデータとエージェント資産全体にわたる **AI の insider risk** に、統合された多層防御で、24 時間 365 日マシンの速度で対処することです。

### 5.6 Q&A

**Q1：Perception の価格は？（consumption ベースと聞いたが、Copilot credits か）**
Perception のライセンス詳細は手元になく、回答者の理解では今日の GA で詳細が公開されているはずなので、パッケージングの構造はオンラインで確認できる、という回答でした。

**Q2：MXC（Microsoft execution containers）について。WSL より下で動く、Firecracker のような VM という理解でよいか。エージェントを MXC に「押し込む」ことを自動化できるのか。**
質問者は、MXC が WSL より下で動く Firecracker のような VM かどうかも確認しましたが、これに対する明確な回答は聞き取れません。エージェントを MXC に押し込めるのかという点への回答は「逆で、エージェントの周りにコンテナを置く」というものでした。方法は 2 つあり、管理されていないエージェントには周りにコンテナを置きます。カスタム統合をした「enlightened な」エージェントは、中に押し込む（push する）こともできるようになる、という説明です（"you'll be able to push them into it"）。シャドー AI（ローカルエージェント）の検出から MXC への導入の具体的な手順は、「オフラインで具体的なドキュメントを案内する」とされ、発表では説明されていません。

**Q3：ネットワーク可視化に GSA を使うが、各社は Palo Alto、Checkpoint、Zscaler などを使っている。Agent 365 の POC でも、エッジの SASE 層を変えるのは大きな負担だった。既存層のまま実現できるか。**
アダプターはサポートされるが、Zscaler や Palo Alto を使っている場合も設計上、トラフィックを復号する中間者を入れることになり、遅延と管理の複雑さが増すため、「エージェントの速度では機能しない」という回答でした。追加の SIEM プロバイダーや追加のシグナルとして足すことはできるが、従来の SASE と同様に遅延は残るとのことです。Microsoft が独自の SASE を開発した理由はここにあり、8 年前に必要性を見越して始めたと説明されています。重要なのは、ネットワークレベルの制御を ID システムと一体にすることです。質問者が、3 万ユーザー規模の企業では簡単な移行ではないと指摘したのに対し、「簡単ではない」と認め、多くの企業は自社も含めて並行デプロイから始めたが、時間がかかり、費用は二重になる、と答えています。

**Q4：Windows 11、VDI、VM などの中でのエージェント（Claude Code など）の隔離について。WSL はエンタープライズ向けではない。MXC 以外のロードマップは？**
質問者は、WSL は家庭ユーザー向けで、MXC が選択肢になると述べています。回答は「把握している限り、Microsoft は MXC をその取り組みの進化形として注力しており、アクチュエーターと連携して動くようにする。それが将来への賭けだ」というものでした。

**Q5：Sentinel に Zscaler や Palo Alto のテレメトリを取り込めないのか。**
「できる。多くのサードパーティが実際にそうしており、Zanity と Wix が今その上で動いている」と回答しています（社名は音声認識の都合で表記が確定できません。別の箇所では「Zenity」とも聞こえます）。ただし、それはカスタム開発とメンテナンスを続けることになるとのことです。Microsoft は自社のスタックを作り込み、サードパーティが作業できる API を用意するという考えが述べられました。

**Q6：サードパーティエージェントも Perception でカバーされるか。是正の制御を行うには SDK が必要か。**（質問者は Synergy Advisors の Dylan 氏と名乗っています。1 つ目の質問への明確な回答は、トランスクリプトでは確認できません。）
可視化は、エージェントが存在することが分かれば、一定範囲で何をしているかまで見られます。しかし制御（actuation）を行うには SDK が必要で、サードパーティエージェントに ID を追加する場合も SDK が必要という回答でした。経験則として、**SDK を実装すると粒度が細かくなり、そうでなければ粗い on/off になる**とのことです。

## 6. デモ・手順

### 6.1 デモ 1：Claude Code でのタスクベースの権限と多層防御（Ankur 氏）

Ankur 氏は Claude Code を使い、「デモはすべてサードパーティ製品でやる。これは Microsoft Copilot でも動く」と述べています。あらかじめ用意したプロンプトで進めます。

1. 最初のプロンプトは「Snowflake からデータを取得し、CRM データベースのビューを作って」という、害のない内容。access orchestrator がプロンプトの意図を理解して、必要なテーブルにだけ時間制限付きの読み取り権限を付与する
2. 次のタスクとして「revenue data を持ってきて」と依頼する。orchestrator は意図を理解して権限の範囲を広げ、「目的はこれ。それを達成するため、数時間の追加の読み取りアクセスを与える。タスク終了時に期限が切れる」と説明する
3. 別のプロンプトに切り替える（最初は誤ったクエリを実行したと述べた）。内容は、revenue data を自宅で読めるよう個人の Dropbox にアップロードさせるもの。ここでは **Purview がブロック**した
4. 直前に「インターネットからコピーしたプロンプトやヒントをそのまま使ったことがあるか」と会場に問いかけたうえで、prompt injection については、Ankur 氏は「**Defender がブロックするはずだ**（would have blocked）」と説明している。貼り付けたクエリに外部へ向かう隠しリンクがあり、Defender がそれを検知してブロックする、というもの。この場面で実演されたかどうかは、発話からは確認できない

Ankur 氏は、これらが「ユーザーが何をしてよいか考えなくても、リアルタイムに層が連携して働く」様子だと説明しました。

### 6.2 デモ 2：Perception ポータルで Know / Contain / Protect / Adapt（Kristina 氏）

Kristina 氏は事前に用意した「demo #2」を開いて進めました。

**Know（優先順位付け）**

1. Perception の AI estate 画面で、クラウドエージェントとローカルエージェントを確認する。表示される数は、IT チームが M365 admin center で見ている数と同じで、「エージェントの数をめぐる議論はなくなる」と説明された
2. 「discover and inventory more agents」のプレイブックを開く。今日の午前に実行済みで、クラウドエージェントとローカルエージェントを再度検出し、次のような洞察を示している
   - Defender がデプロイされているため、ローカルエージェントは見えている。Global Secure Access もデプロイすれば、ネットワークトラフィックと MCP サーバーも発見して制御下に置ける
   - Foundry エージェントや Copilot Studio エージェントは見えているが、**A365 に接続すれば非 Microsoft のプラットフォーム**（キーノートで話題になった Salesforce AgentForce の接続など）も見える
3. ツールと MCP サーバーも確認できる。**高リスクのエージェントが 1 件**あると表示される
4. Perception のチャットで「このエージェントはなぜ高リスクか、なぜ重要か」と質問する（タイプミスがあったと本人が述べている）。しばらく考えた後、エージェントのコンテキストが取り込まれ、次が示される
   - エージェントは Entra ID を持っている（リスクやコントロールを紐付けられる）
   - 所有者は Anya
   - 管理者がこのエージェントを **compromised（侵害された）** とマークしている（Entra 管理センターでマークされたもの）
   - このエージェントは Graph の「create as manager」と聞こえる権限を持っており、エージェント型のインサイダーがさらにエージェント型のインサイダーを作れてしまう（権限名は音声認識の都合で表記が確定できません）
5. 要約を鵜呑みにせず、詳細を開く。リスク評価で dynamic agent risk が high で、その理由が見られる。Defender と同じ **attack surface graph（blast radius graph）** が表示され、SOC チームと同じコンテキストで考えられる。Access を見ると、Entra から取り込まれた Graph 権限が表示される

Kristina 氏は、デモテナントには高リスクのエージェントが 1 つだが、実際のテナントには数十、あるいはそれ以上あるはずで、1 つずつ対処する「もぐらたたき」ではなく、先回りのセキュリティを目指すべきだと述べました。

**Contain（封じ込め）**

6. ダッシュボードに、**MXC ポリシー**が 3 台のデバイスにデプロイ済みと表示されている
7. プレイブック一覧から、MXC の「limit agent access on devices」を開く。このプレイブックは、デバイスにサンドボックスを作り、準拠したエージェントがそれを使えるようにするためのもの。ポリシーを作成して Intune でデプロイする流れで、これによりローカルのコーディングエージェントが、リポジトリのワークスペースだけを使い、OneDrive に触れて変更するようなことがないようにできる
8. ライフサイクルのプレイブック「Identify agent governance gaps」を開く。評価を行い、適切な joiner / mover / leaver のポリシーが設定されているかを確認できる。例として、人が異動したときに、その人のマネージャーがスポンサーになるといったポリシーが挙げられた
9. プレイブックを探すだけでなく、Perception のチャットも使える。あらかじめ書いておいた質問「how do I drive least privilege access for agents dynamically?」を入力すると、先ほど Ankur 氏が見せた、Claude Code が Snowflake への適切な権限を JIT で得る仕組みに対応するポリシーをデプロイするプレイブックが示される

**Protect（保護）**

10. ダッシュボードで、Perception が環境全体の導入済み・未導入の保護を把握していることを示す。ここでは、2 つの重要な保護が不足していると指摘される。1 つは機密データがモデルに出ていくのを保護していないこと、もう 1 つはネットワークアクセスポリシーを使っていないこと。ランタイム保護はデプロイ済みだが、デモテナントのため何も検知されていない
11. プレイブックを起動するたびに **session** が作られ、後から見直したり同僚と共有したりできる。以前に実行した「エージェントのアクセスと機密データ」の評価 session を開くと、ローカルエージェントに適用されること、DLP のアクティビティがないことが示される。また、これがプレビュー機能であることも把握しており、「非本番テナントから始めて検証してから進める」という安全なデプロイを勧めてくる
12. 「restrict agent network access」の session を開く。GSA のポリシーを調べた結果、すべてのエージェントに適用される baseline security policy があり、そこに **web content filtering** と **threat intelligence** の 2 つのポリシーが不足していると示される。前者がないと悪意のあるサイト、ギャンブルサイト、違法ソフトウェアのサイトにエージェントが到達できる。後者は悪意のあるサイトを常に見て分類するもの
13. 「approve」を押して submit する。これでこのポリシーが Microsoft Entra で実際に強制される。この体験から離れる必要はなかった

**Adapt（適応）**

14. 画面に戻ると、クラウドエージェント、ローカルエージェント、高リスクエージェント、そして **agent sessions blocked for risk**（音声認識の都合で表記が確定できません）が見える。これは高リスクのエージェントを監視して止める dynamic conditional access policy で、高リスクのエージェント 1 件はクラウドリソースにアクセスしようとしていなかったが、それは問題ではないと述べている
15. 将来高リスクになるエージェントのために、適応型のポリシーが意味を持つ。エージェントの内訳は高リスク 1 件、中リスク多数、低リスク少数。先回りで条件付きアクセスのポリシーを入れておけば、中リスクのエージェントが明日高リスクに変わっても保護され、高リスクのエージェントが修復されれば、仕事に戻れる

### 6.3 デモ全体の補足

Joanne 氏は、Ankur 氏のデモを「end user scenario」と呼んでいます。デモ 2 の表示される数値は「デモテナント」のものであることが、発表者によって明示されました。

## 7. 注意点・発表者の気付き

- **見えている範囲を意識する**：Perception が示すのは「Microsoft が見えているエージェント」で、完全な文脈にするためにプレイブックで補う、と説明されました。Defender、GSA、A365 の導入状況によって見える範囲が変わります。
- **プレビュー機能は安全にデプロイする**：Perception は、対象機能がプレビューであることを把握したうえで、非本番テナントで検証してから進めるよう勧めます。
- **サードパーティエージェントは、制御に SDK が必要**：SDK なしだと可視化まで、制御は粗い on/off になる、という制約が Q&A で説明されました。
- **既存の SASE を使い続けるのは容易でない**：アダプターで対応できても、中間者による復号、遅延、運用の複雑さが残り、「エージェントの速度では機能しない」と説明されました。GSA への移行も簡単ではなく、並行デプロイでは費用が二重になるとのことです。
- **MXC について**：エージェントの周りにコンテナを置く方式（管理外のエージェント）と、カスタム統合をした enlightened なエージェントを中に押し込めるようになる方式があります。WSL に代わる将来の方向として MXC に注力している、と語られました。
- **価格・ライセンス**：発表者は詳細を把握しておらず、オンラインの情報を案内するにとどまりました。
- **人間の関与のしかた**：Ankur 氏は、完全な自動運転ではなく、手をハンドルに置いたまま始めるべきだと述べています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- IT チームが M365 admin center で見る数と同じエージェント数を、Perception でも見られる。数をめぐる議論がなくなる
- 検出、リスク説明、封じ込めのプレイブック、承認、強制までを 1 つの体験で行える。デモでは、GSA のポリシー追加も Perception を離れずに実行された
- SOC チームと同じ attack surface graph、同じコンテキストを共有できる
- エージェントごとにタスクベース・時間制限付きの権限を自動で与えられ、データベース管理者への承認依頼などの人手を省ける
- エージェントのリスクが変わっても、事前に入れた条件付きアクセスにより、数のとても多いエージェントを自動で制御できる
- 複数の製品を組み合わせるための統合作業を、自分たちでやらなくてよい

発表では、具体的な顧客名や、導入効果の数値は紹介されていません。

## 9. まとめ

AI エージェントの増加により、見えていないエージェント、権限が過剰なエージェント、リスクが変化し続けるエージェントが insider risk になりえます。発表では、それに対する答えとして、Defender、Entra、Purview、Global Secure Access などの多層防御と、そこから集まるシグナルを束ねる context engine、そして Perception という 1 つの画面が示されました。

デモでは、Claude Code に対するタスクベース・時間制限付きの権限付与と、Purview によるブロックが紹介され、続いて Perception のポータルで **Know → Contain → Protect → Adapt** の流れが示されました。Q&A では、サードパーティエージェントの制御に SDK が必要なこと、SASE の移行が簡単ではないこと、MXC の方向性が語られています。トランスクリプトで Perception は GA とされており、価格やパッケージングはオンラインで確認するよう案内されました。
