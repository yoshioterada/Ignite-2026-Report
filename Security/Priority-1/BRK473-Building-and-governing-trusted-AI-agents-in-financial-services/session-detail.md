# BRK473 Building and governing trusted AI agents in financial services

## 1. はじめに

このセッションは、金融機関をはじめとする規制の厳しい業界で、Power Platform と Copilot Studio による AI エージェントやアプリの開発を**どう統制しながら広げるか**を扱います。「ガバナンス」というと、すべてをブロックして監視する姿を思い浮かべがちですが、発表の主張はその反対です。摩擦を増やしすぎれば革新は起きません。一方で、CISO が安心して眠れる程度の可視性と統制は必要です。この両立が、全体を通した課題として語られています。

発表は次の順に進みます。最初に Microsoft の Zohar 氏がガバナンスの考え方を説明し、State Farm の事例が続きます。次に、メーカー（作る人）が管理者の視界の中で作り始められるようにする設定方法が、デモ付きで紹介されます。その後、Austin 氏が作成物を本番で動かす仕組み（managed host、昇格、監視）を説明します。最後に Zohar 氏が、課金とクレジット、そして管理センターをエージェントで操作する新しいアプローチをデモで見せます。

## 4. 発表者が伝えたいメッセージ

Zohar 氏の言い方では、IT が決めるのは、初心者が絵を描き始めるための「絵の具や筆やツール」と、プロが作品を本番まで持っていく手段です。すべてを「モナ・リザ」のように扱って、使う前にブロックして厳重に監視すれば、摩擦が大きすぎて革新が起きなくなります。

冒頭で紹介された顧客のコメント（発言者名は示されていません）にも同じ考えが現れています。**「統制された道が簡単な道であれば、人はそちらを歩く」**、そしてガバナンスは結局「人を相手にするビジネス」だという趣旨です。また「障壁（blocker）ではなくガードレールを」という言葉もあります。

State Farm の Dorton 氏の言葉では、「governance but not control（統制ではなくガバナンス）」が方針です。現場に近い業務部門の人こそ課題を解決するのに適しているという考えから、全員がビルダーになれる仕組みを意図的に作ったそうです。

## 5. 発表内容の詳細

### 5.1 ガバナンスの考え方と製品の位置づけ

Zohar 氏は、Power Platform が、アプリ、エージェント、フローを作る場所だと説明します。ファミリーに加わった「より agentic な」新メンバーとして、次の 2 つを挙げています。

- **Copilot managed runtime applications**：Cowork、Code タブ（音声認識の都合で表記が確定できません）、Copilot Studio、または前日に紹介した lovable などから、自然言語でアプリを作れる。
- **Microsoft Copilot harness**：エージェント向けに同様のことができる。

4 年前に発表した managed environments は、managed platform として成熟し、より少ない労力で可視性と統制が得られるようになった、と述べています。今回の Ignite で発表する機能も、さらに少ない労力で大規模に管理するためのものです。

### 5.2 顧客の声

発表の冒頭近くで、複数の顧客のコメントが紹介されます。発言者や会社は示されていません。要点は次のとおりです。

- 見えるか、測れるか、ガードレールを置けるか。環境ルーティング（environment routing）や advanced connector policy といったツールが鍵になる。
- 最初は default environment から始まり、数年は「Wild West（無法地帯）」だった。個人の生産性向けの環境に作られたアプリやフローが、いつの間にか業務上重要になった。
- 作る人は悪意があるわけではなく、トラブルに巻き込まれないようにするのが統制の目的。管理者ワークショップで environment routing を知り、ワークショップが終わるまでに有効化した、という例も語られた。
- managed environment groups により、定義したグループごとにプロセスを整えて、プラットフォームの運用をスケールさせられた。
- コミュニティの知見を活用すること。自分たちだけで同じ壁にぶつかる必要はない。
- 「導入の最初からガバナンスを考える」「メーカーの近くにいる」「障害物を置かない」という助言。

### 5.3 State Farm の事例

Dorton 氏は、State Farm を米国の P&C（損害保険）会社と紹介し、Power Platform 管理チームと一緒に取り組んだ「ビルダーが安全に作れるようにする」活動を紹介します。情報セキュリティ、プライバシー、コンプライアンス、法務と協力して進めたそうです。

#### 導入の道のり（ゆっくり段階を踏んだ）

1. **default environment を有効化**：Dorton 氏によると、default environment は今後 personal environment に置き換わる（deprecating）方向で、同社もそれに向けて進めています。当初は強く制限した環境で、厳格な共有制御ポリシーを置き、コネクターは主に M365 のものと、ロールと権限に関する 1 つのカスタムコネクターに限定。関係部門と進める出発点として低リスクだった。
2. **全従業員に Power Apps のプレミアムライセンスを提供**：課題に最も近いビジネスユーザーが最良の解決者だと考えて、意図的に行った。IT 部門は顧客向けの開発を中心にし、各業務部門が自分たちのために作る。
3. **すべての環境を managed にする**：情報セキュリティやリスク、コンプライアンスのパートナーと協力して、ガードレールを強化。
4. **Dataverse を有効化**：一歩ずつ、証明しながら進めた。
5. **Copilot Studio を展開**：利用可能になった時点で展開し、従業員の AI での作り方が変わった。

#### 成果

- 本番のエージェントは、スライドでは 52 だが、当日朝にもう 1 つ承認され、**54** になった。
- 全社員の約 **85%** が Power Apps を利用している。
- ビルダーコミュニティは、市民開発者とプロの開発者の両方で大きい。

エージェントの例として、2 つが紹介されました。

| エージェント | 内容 |
| ---- | ---- |
| HR&D ask（人事ポリシー） | 従業員が、ポリシーやマニュアルについて質問する。以前は人に電話・チャットしていた。社員を、パフォーマンスコーチングや人材管理といった、より高度な業務へ再配置できた。**月に約 38 日分の専門家の時間**を節約したと共有された。最も利用されている Copilot Studio エージェント |
| Spanish letter translation agent | 翻訳をサービスとして提供する。最初はマーケティング資料だったが、人気が出て、送付する保険金請求関連の手紙の翻訳にも広がった。他言語ではレイアウトも変わるため、送付書類の構成に合うよう HTML に再整形する。1 部門を超えた「サービスとしての翻訳」になった |

#### 「laddering effect」（段階的に広げる戦略）

Dorton 氏は、ビルダーのコミュニティを育てる戦略を「laddering effect」と呼びます。

1. まず、**自分のために**何かを作る面白さを知ってもらう。「一日を早く終えて、家族と夕食に間に合うようにしたくありませんか」というのが同氏の決まり文句（elevator speech）。研修・ワークショップの環境から、すぐ personal environment（従来は default environment）へ。
2. 自分の課題が解決できれば、**チームの生産性**に取り組む。
3. チームの課題が解決できれば、**部門や企業全体**の課題に取り組み、本番の構築へ進む。

#### 環境戦略

Dorton 氏は、明確で透明性があり、文書化された環境戦略が、安全で責任ある AI 活用に欠かせないと述べています。Ignite で会った参加者から、環境戦略が弱いという声を聞いたそうです。State Farm の構成は次のとおりです。

- **低位環境**：default environment または personal developer environment。ロックダウンされ、利用できるコネクターや Dataverse が限定される。リスク評価が済んでいる。
- **dev / QA / prod**：「virtual environment cluster」と呼ぶ。自動化でインスタンス化し、管理チームが個別に作ることはしない。Power Platform の pipelines でライフサイクルを管理する。

AI の導入では、まず本番レベルの Copilot Studio の事例を数件、情報セキュリティとリスクのチームに持ち込み、リスク評価の進め方を確認したそうです。同社には AI ガバナンスと AI の intake ポリシーがあります。ROI と成果を示す事例ができた後、AI ガバナンス、情報セキュリティ・リスクのパートナーと協力し、**低位環境で作る人は、dev / QA / prod に上がって IT 資産の定義に該当するまで、追加のリスク評価を免れる**というパターンを作りました。これが成果を出すうえで決定的だったと述べています。

#### クレジット消費（FinOps）

Power Platform は今年の 6 月から消費ベースのモデルに移行しており、まだ数か月で学習中だが、戦略には自信があると述べています。同社は、クレジットへのアクセスを 4 段階で設計しています。

1. **personal 環境**：最初に一定量を割り当て、さらに必要なら申請する。
2. **training / innovation 環境**：研修や実験用。当日、同社はハッカソンを開いており、参加者は個人用や本番のクレジットを使わず、innovation 環境で作る。
3. **dev / QA**：クレジットを最初に割り当てて、申請なしで始められるようにする。進行に応じて、環境ごとの予算を管理チームと見直す。
4. **本番**：履歴があるため予測しやすく、割り当てがしやすい。

#### 規制業界への教訓

1. 規制のある業界でも**実現可能**で、従業員の満足度も上がる。
2. 関係者（情報セキュリティ、プライバシー）を早く巻き込み、プラットフォームについて教育する。
3. 明確な環境戦略で、ビルダーと関係者の双方にガードレールを理解してもらう。
4. 監査証跡を取りやすくする（Purview や SIEM などを使い、各リスク・コンプライアンス担当が納得できるように）。
5. 信頼とともに拡大する：ワークショップ、責任ある AI のトレーニング。**Agent Academy** を勧めている。

帰ってからすぐできることとして、Copilot Studio の選択肢を確認すること、プラットフォームレベルで強いガバナンスを敷くこと、まず「リスクが低く、量が多い」業務から始めて火を付けること、を挙げています。

### 5.4 組織の設定：personal environment を起点に

ここから Zohar 氏が、メーカーが「落とし穴ではなく成功の穴（pit of success）」に落ちる、つまり IT の視界の中で作り始める設定を説明します。そうすれば、作られたものをすべて見て、監視し、統制でき、IT の目の届かないところで進む shadow IT に悩まされずに済みます。

会場に「default environment を知っている人、好きな人」と尋ね、知っているが好きな人はいない、という反応でした。Microsoft の現在の推奨は、全員を **personal environment** に移すことです。OneDrive が、ファイルを SharePoint で広く配る前に作る場所であるのと同じように、personal environment は、アプリ、エージェント、フローを隔離された「島」で作る場所です。IT は、共有の範囲、使えるツールとデータソースを制御できます。

| 機能 | 説明 |
| ---- | ---- |
| routing（環境ルーティング） | 設定の出発点。最初に利用したとき、personal environment を自動作成し、指定したグループへ入れる |
| advanced connector policy | メーカーがエージェント・アプリ・フローで使えるデータソースを IT が定義する |
| welcome onboarding message | メーカーが初めて入ったとき、またはメッセージを更新したときに、読んで理解したと確認させる。ヘルプの受け方も伝えられる |
| ステータス（Copilot Studio）への IT ガイダンス | エラーや警告を確認する画面に、IT の案内を表示できる。例として Microsoft IT が、例外の取り方、別の環境の入手方法、カスタムコネクターの依頼方法を説明する専用エージェントを、スタジオに埋め込んでいる |
| inventory | PA Platform admin center で、作られたエージェント、アプリ、フローを一覧できる。API でも取得でき、エージェント経由でも操作できる |
| usage | どのアプリ・エージェント・フローが人気かを、専用の usage ページなどで確認できる |
| Microsoft Admin Center の Copilot managed runtime applications | 昨年の金融業界のラウンドテーブルで、「設定のクリックが多い。最初から使える状態で出してほしい」という声があった。それに応え、専門家向けの PPAC だけでなく、ジェネラリストが Microsoft Admin Center から、設定済みの Copilot managed runtime applications を利用できる（「out-of-the-box 4」と聞こえるが、数の意味は音声認識の都合で確定できません） |

### 5.5 managed host、昇格、Monitor（Austin 氏）

Austin 氏は、「管理者は管理し、メーカーは作る。ただ作っているのはソフトウェアで、動くのか」という問いから始めます。ビジネスがそれに依存するなら、本番として扱うべきです。そのための 3 つのプラットフォーム機能を軽く紹介しています。

1. **managed host**：ソフトウェアが実際に動く場所
2. **promoting（昇格）**：dev で作ったものを本番にどう移すか
3. **monitor**：本番で動いているものが、自信を持って動いているとどう分かるか

#### managed host

Austin 氏によると、managed host は Power Platform と同じ古さで managed platform より古いのですが、話題にし始めたのは最近 2 年です。AI 以前は、Power Platform で作れば、その上で動かすしかありませんでした。AI の時代には作る道具が選べるので、「ホストに行く説得力のある理由」が必要で、managed host はその 1 つだと説明します。アプリにはアプリ用、ワークフローにはワークフロー用、エージェントにはエージェント用の managed host があり、ここではアプリを例にしています。

managed host が当たり前のように提供するものは次のとおりです。

- すべてのエンドユーザーが Entra で認証され、共有されたユーザーだけがアプリにアクセスできる。
- アクティビティログが Purview に流れ、異常検知も有効にできる。
- メーカーがテレメトリーや運用状態を考えなくても、アウトオブボックスの健全性メトリックがあり、アラートで障害に気付ける。

#### 昇格（ALM）

Power Platform では、メーカーが solutions を使い、IT と協力して pipelines を作り、本番環境へデプロイします。バージョン管理は Git で行います。Austin 氏は、メーカーが dev 環境で作り、pipeline で、制限が最小限（least restricted、least privileged とも）の本番環境（「shrink wrap governance」と呼んでいる）へ展開する流れを紹介します。

Copilot managed runtime では、それに加えて、メーカーは制約の緩い場所で作り、希望すれば、より制限された場所へデプロイできます。今日できるが、より「自動的で意識しなくてよい」ものに投資していくと述べています。管理者と環境戦略を詰めなくても済むよう、**メーカーの革新は、既定では本番ランタイムとガバナンスの境界から切り離される**ターゲットを導入します。管理者と協力するか、管理者がポリシーで構成すれば、より制限され堅牢な（shrink-wrap governance の）環境へ出せます。

#### Monitor

「森で木が倒れたら音がするか」のたとえで、アプリ、ワークフロー、エージェントが落ちたとき、気付けるのか、と問いかけます。Monitor は一般提供（GA）済みで、この秋に、要望の多かった次の機能がプレビューになりました。GA は「比較的近く」を見込んでいます。

- **より高い感度のアラート**：劣化を最短 1 時間で把握できる。
- **アラートイベントの購読**：運用チームが Teams チャネルや ServiceNow のチケットを使っているなら、そこに通知を流せる。
- **データは API でも取得できる**：システムのデータは閉じ込められていない。

### 5.6 課金とクレジット（Zohar 氏）

Zohar 氏はこの話題を「気が重い話」と前置きしています。

- サブスクリプションの世界から、**利用量（usage）ベースの課金**へ移った。基本的な AI を使い放題にするサブスクリプションを誰に渡し、最も高度なモデルを使えるクレジットを誰に渡すかを、管理者が決める。
- ライセンス管理は、PA Platform Admin Center から、クレジット管理を **Microsoft Admin Center に一本化する移行期**にある。
- Copilot Studio では、メーカー向けに、画面左上でクレジット消費量が見えるようになった。

管理者向けの整理は次のとおりです。

| 管理センター | 担当 |
| ---- | ---- |
| Power Platform Admin Center（PPAC） | ユーザー単位のサブスクリプション（USL）の管理。「licensing」タブで、レポート、利用状況、アプリ・エージェント・フローを使えるライセンスを誰に渡すか |
| Microsoft Admin Center | クレジットの消費管理。「Copilot」タブの「cost management」で、ポリシーを設定し、クレジットを付与し、消費を管理する |

FinOps の詳細は、前日のセッション BRK262（Graham 氏と Thomas 氏、音声認識の都合で表記が確定できません）の録画と、QR コードの資料が案内されました。

## 6. デモ・手順

デモは 3 つあります。画面の細部は音声からは確認できないため、語られた範囲のみを書きます。

### 6.1 Power Platform Admin Center での設定（Zohar 氏）

デモは「架空のデモ環境」で、管理者としてログインした状態です。

1. PPAC の manage から、作成済みの環境の一覧を見る。developer タイプの環境（OneDrive に相当する個人用）がある。
2. 「environment group」を開くと、環境をグループにまとめられる。
3. **environment routing**：初めてスタジオに入ったとき、personal environment がなければその場で作成し、管理者が指定したグループに入れる。そのグループが、そのメーカーの使える機能を決める。例では「pro maker」グループを作成済みで、デモ用の自分の personal environment がそこに入っている。
4. **rules**：ルールギャラリーから、約 50 種類のルールを追加でき、そのグループの環境の構成を決める。
5. 例として **advanced connector policy**：許可するコネクターの一覧が出て、約 1,500 のコネクターから追加できる。さらに、アクション単位でも定義できる。SQL では許可するアクションを選べる。
6. **今回の Ignite の新機能**として、SQL は使えるが「OAuth のみ」とする設定ができる（SQL Server など他の方法は不可）。
7. **welcome onboarding message** は、任意のテキストで設定できる。

続いてメーカー側の見え方です。

1. メーカーとして Copilot Studio に初めてログインすると、welcome message が表示される。内容を読んで理解したことを確認し、利用条件（terms and conditions）のページも開く。
2. agents から自分のエージェントを選び、ステータスを見る。tools でコネクターを選ぼうとすると、許可されたコネクターだけが選べる。SQL は機能が限定され、決まったアクションのみ。それ以外は無効。約 1,500 のコネクターのうち、許可されたものだけを使える状態になっている。
3. ステータスには、ポリシーでブロックされたときに解除する方法を表示でき、先に紹介した専用エージェントへのリンクも置ける。

**inventory**：

1. manage の inventory を開き、アプリ、エージェント、フローの全一覧を見る。
2. MSIT で以前に見せたとき、アプリ・エージェント・フローは合わせて **250 万件**あり、それでも一覧は即座に表示されたと説明している。アプリ名を変更すると、約 50 秒後に一覧に反映される、というデモも行ったと説明されている（今回の実演ではなく、以前の発表の説明）。
3. Copilot Studio などの製品を選ぶと、各資産のメタデータが表示される。例として、エージェントがどの harness を使っているか（Microsoft Copilot harness かどうか）や、どのモデルを使っているかが分かり、モデルで並べ替えて判断できる。

**Microsoft Admin Center**：

1. Agent 365 のほかに、「apps」（Copilot managed runtime apps）が加わったことを見せる。
2. settings では、PPAC の機能の一部が、既定で有効な簡易版として提供される。コネクターポリシーや、追加 API 向けのセキュリティポリシーが見られる。Copilot managed runtime のグループ向けに作れるものを、ここから制御する。

### 6.2 managed host のデモ（Austin 氏）

アプリを 1 つ、managed host のコンテキストで実行して見せます。すでにサインイン済みでした。画面には 3 つのものが見えています。

1. **左側**：Power Platform のコネクターのエコシステムを使うアプリ。advanced connector policy で許可されたコネクターで、ボタンを何度押しても、呼び出しは許可されて成功する。初回はユーザーがサインインして接続に同意する必要がある。
2. **中央**：Power Platform で作ったアプリではなく、**GitHub Copilot（CLI と SDK）で外部に作り、Power Apps の code app として Power Platform にデプロイした**アプリ。コードファーストなので任意の API を呼べるが、managed host は任意の API 呼び出しを許さず、content security policy（CSP）を強制する。既定は非常に制限が強く、IT は、アクセス可能なものを広げることも、さらに絞ることもできる。
3. **右側**：ブラウザの開発者ツール。承認されたコネクターを通らず、CSP で許可されていない API を呼ぼうとするたびに、ランタイムエラーが表示される。IT が許可していないため、managed host が拒否している。

### 6.3 Cowork と Power Platform Admin plugin（Zohar 氏）

1. 管理者としてログインした Copilot ツール（Cowork）で、「Power Platform Admin plugin」を使う（plugin を表示させる準備は済ませてある）。
2. 「何について聞けるか」と尋ねると、環境、アプリ、エージェント、フロー、環境グループ、ライセンスなどを把握していると答える。
3. **weekly digest**：事前に用意した長いプロンプトを貼り付け、テナントについて知っていることを週次ダイジェスト形式でまとめさせる。エージェントの利用状況と ROI などが表示される。Cowork なので、これを PowerPoint や Word にまとめて上長に共有することもできる。データは PPAC から直接来ている。なお、この操作は読み取り専用で、スケジューラーに載せることもできる、と説明している。
4. 次に、plugin と Copilot managed runtime application を組み合わせたデモ。customer advisory team の Reza 氏から共有された zip ファイルを取り込み、zip の中のプロンプトを与えて、約 10 分実行させた。
5. `/cost` で、Cowork がアプリを作るのにかかったコストを確認。「10 ドルで 30 分」という説明があり、従来の COE toolkit より豊かなアプリになるとのこと。コストの単位の発言（「1000 tokens は約 10 ドル」）は、音声認識の都合で正確に確認できません。
6. 生成されたアプリは、深くクリックして掘り下げられる。読み取り専用ではなく、Cowork から CLI を直接呼び、**資産の削除、隔離（quarantine）などの管理操作**ができる。PPAC や Microsoft Admin Center に満足できなければ、このサンプルをカスタマイズして使える。

このサンプルアプリは GitHub で公開されており（QR コードと URL を表示）、zip を Cowork に入れれば同じ結果を得られるとのことです。

## 7. 注意点・発表者の気付き

- **すべてを「モナ・リザ」扱いしない**：すべてをブロックして監視すると、革新が起きない。
- **default environment の問題**：数年間「Wild West」状態になり、個人用のアプリやフローが業務上重要になった例が語られた。現在は personal environment への移行が推奨されている。
- **環境戦略の文書化**：Dorton 氏は、Ignite で会った参加者の中に、環境戦略が十分でないという声があったと述べている。
- **AI のリスク評価は新しい経験になる**：State Farm では、まず本番レベルの事例を情報セキュリティ・リスクのチームに見せ、評価方法を学んだ。
- **消費ベースへの移行は学習中**：State Farm も、消費モデルになって数か月で、まだ学んでいる最中と述べている。
- **PPAC と Microsoft Admin Center の分担は移行期**：ライセンスは PPAC、クレジットは Microsoft Admin Center という整理（Zohar 氏）。
- **managed host は任意 API を許さない**：外部で作ったコードファーストのアプリでも、CSP により既定で非常に制限される。
- **Monitor の新機能はプレビュー**：高感度アラートとアラートイベントの購読は、この秋にプレビューとなり、GA は近いうちに見込むとされている。

## 9. まとめ

- 統制と革新は両立させる課題であり、「統制された道が簡単な道」であれば、人はそちらを歩きます。
- State Farm は、default environment を厳しく制限したところから始め、全員にライセンスを配り、環境を managed にし、Dataverse、Copilot Studio と段階的に広げて、54 の本番エージェントに到達しました。低位環境での作成は追加のリスク評価を免除し、dev / QA / prod に上がった時点で評価する仕組みが鍵でした。
- IT は、personal environment、environment routing、advanced connector policy、welcome message、inventory、usage で、メーカーが視界の中で作り始められる状態を作れます。
- 本番運用は、managed host（認証、ログ、健全性メトリック、CSP の強制）、昇格（pipelines、Git）、Monitor（アラート、購読、API）の 3 本柱で支えます。
- 課金は利用量ベースに移り、クレジットは Microsoft Admin Center、USL は PPAC で管理します。
- PPAC の全機能が API 化され、PAC CLI、plugin、Cowork と組み合わせることで、エージェントによるガバナンスが可能になります。
- 最後の呼びかけとして、Zohar 氏は、メーカーが作るときの摩擦をどこで減らせるかを考えるよう促しています。目指す姿は、State Farm のように、enablement チームが研修を行い、personal environment で作らせ、本番まで運べる組織です。
