## 3. 何に関する発表か

最近のアプリケーションは、クラウドリソース、ID、データ、コンテナー、ネットワークにまたがっています。攻撃者は、クラウド、ID、エンドポイント、アプリケーション、ネットワークといった組織の担当範囲の境界を気にせず、入り口から価値のある資産までの「道筋」を探します。そのため、個々の脆弱性やアラートを見つけるだけでは足りません。それらがどうつながり、攻撃者が実際にどこまで届くのか、どこで介入するのが最も効果的かを理解する必要がある、というのが発表の出発点です。

発表の流れは次のとおりです。

1. 攻撃経路の全体像と「チョークポイント」（攻撃を断ち切れる地点）の説明
2. SOC アナリストの視点での Defender のインシデント調査（デモ）
3. AI アプリケーションを含むアプリ全体を守るための、Defender の考え方（ポスチャー管理とワークロード保護）
4. セキュリティ管理者の視点でのポスチャー確認（デモ）
5. 同じ VM を SOC アナリストの視点から再調査（デモ）
6. ネットワークの視点: Azure Adaptive Virtual Patching（デモ）
7. Azure Firewall の AI Security アドオン（デモ 2 本）
8. Azure Bastion の RDP vision / SSH vision（デモ）

## 4. 発表者が伝えたいメッセージ

中心となる主張は、**攻撃は一本の途切れない道ではなく、途中に複数のチョークポイントがある**という点です。James は単純化した攻撃経路として、次の流れを示しています。

1. インターネットに公開された VM が入り口になる
2. 侵入に成功すると、そのワークロードが足がかりになる
3. 攻撃者は到達できる別のワークロード、認証情報、ネットワーク接続を探し、横展開（ラテラルムーブメント）で影響を広げる

これに対して、防御側には次の 4 つの打ち手があるとしています。

- 攻撃が入る前に、露出を減らす
- ワークロードを保護し、侵入された場合は悪意ある動きを検出する
- 動きが大きな攻撃に発展していることを見抜く
- 攻撃者が奥へ進むために使えるルートを制限する

前半のクラウド セキュリティ（ポスチャーとワークロード保護）が最初の 3 つを、後半のネットワークが入口でのフィルタリングと横展開の制限を担当する、という構成です。

もう一つの主張は、AI を使うアプリでも既存の攻撃手法がなくなるわけではない、という点です。AI アプリの保護は、その下にあるコンピュート、データ、コード、ID の保護と切り離せないとしています。さらに Ashish は、攻撃者が AI でエクスプロイトを作る時代にパッチ適用の期間（ウィンドウ）が長いままでは間に合わないとして、防御側も AI を使う（securing AI と securing with AI）方向を示しています。

## 5. 発表内容の詳細

### 5.1 背景: 攻撃者の視点と最近の事例

冒頭で James は、PHP で見つかった 2 つの重大な欠陥により、欧州の政府機関がウェブサイトをオフラインにせざるを得なかったという最近のニュースを引き合いに出しています。PHP は、既知のサーバーサイド言語を使うウェブサイトの約 70% で動いていると説明し、数日のうちに CISA が攻撃者による悪用を確認したと述べています。

### 5.2 SOC アナリストの視点: 相関されたインシデント グラフ（デモ）

最初のデモでは、160 件のアラートが 1 つの相関したグラフにまとめられたインシデントを開きます。詳細は 6 章に書きますが、要点は、アラートを個別に調べるのではなく、クラウド資産、ID、デバイス、ネットワークの各エンティティの関係をたどって調査できる点です。この連結された見え方は、チョークポイントの特定にも役立ちます。たとえば、インターネットに公開されたサーバーで早期に不審な動きを検出して対処できれば、攻撃が環境内で広がる前に止められる、と説明しています。

### 5.3 AI アプリケーションと Microsoft Defender の位置づけ

James は、AI は既存のアプリケーションを置き換えるものではなく、その上に載る追加のレイヤーだと説明しています。モデル、エージェント、API、AI サービスは、その下のコンピュートとデータに依存し、それらはさらにコード、デプロイ パイプライン、レジストリ、インフラ構成につながっています。したがって、脆弱性が AI レイヤーで始まらなくても、アプリは危険にさらされます。たとえば、露出したワークロード、権限過多の ID、コードの問題、保護されていないデータが入り口になります。

AI は、すでにセキュリティチームが扱っているリスクに新しいリスクを上乗せします。SQL インジェクション、データ流出（聞き取りでは "data exacerbation" で、音声認識の都合で表記が確定できません）、リモートコード実行といった従来のリスクが増幅されるうえ、AI アプリに固有の脅威として次が挙げられました。

- プロンプト インジェクション
- ジェイルブレイク攻撃
- データポイズニング
- モデルの窃取
- モデルのサービス拒否（model denial of service）

このため、AI 向けの保護だけを切り出すのではなく、アプリケーションスタック全体を保護する必要があるとしています。Microsoft Defender は、マルチクラウド環境にわたってアプリケーションスタックを保護し、資産、脆弱性、ID、権限、データ、それらの関係についてのコンテキストを構築するものだと位置づけています。

### 5.4 ポスチャー管理とワークロード保護

Defender は、次の 2 つの補完的な側面で説明されました。

| 側面 | 役割 |
| ---- | ---- |
| ポスチャー管理（posture management） | どこが露出しているかを把握し、意味のある攻撃経路になり得るリスクに優先順位を付け、攻撃者に使われる前にその機会を減らす |
| ワークロード保護（workload protection） | 実行中のワークロードを継続的に監視し、悪意ある動きが起きたときに検出・把握・対応する |

露出について学んだことは攻撃の機会を減らすのに役立ち、実際の脅威から学んだことはリスクのコンテキストを増やす、という相互関係も述べています。先ほどの攻撃経路で言えば、ポスチャーは侵害前の機会を減らし、ワークロード保護は攻撃がワークロードに到達したときに検出・阻止する役割です。

「何から直すか」の優先順位付けに使う要素として、次の 4 つが紹介されました。

- **アタックパス分析**: 露出と関係がどう組み合わさって環境内の実行可能なルートになるかを特定する
- **データのコンテキスト**: その経路で機密情報が危険にさらされるかを特定する
- **コードからクラウドへのコンテキスト**: デプロイ済みリソースの問題を、元になった開発ワークフローやインフラのコードまでたどり、発生源に近いところで直せるようにする
- **継続的な評価**: セキュリティとコンプライアンスのポスチャー全体を把握する

孤立したリソースの脆弱性は、機密データや重要リソースへの経路を持つインターネット公開ワークロードの問題ほど緊急ではない、というのが優先順位付けの考え方です。

### 5.5 セキュリティ管理者の視点: ポスチャー確認（デモ）

同じ環境を、今度はセキュリティ管理者の視点で見ます。重大・高リスクの推奨事項から、脆弱な OpenSSL に起因する「露出したコンピュートリソース」の推奨事項を開き、証拠、修復手順、関連リソースのマップ、統合されたサーバーページ、アタックパスをたどります。詳細は 6 章のとおりです。

### 5.6 ワークロード保護と SOC アナリストの視点（デモ）

攻撃者がワークロードに到達すると、問題の性質が変わります。「どこが露出しているか」ではなく、「ワークロード上で何が起きているか」「どんな証拠があるか」「攻撃が広がり始めていないか」が問いになります。アラートには、どのリソースが影響を受けたか、どのプロセスや動きが観測されたか、どんな証拠があるか、他の動きとどうつながるかというコンテキストが必要だと James は述べています。

デモでは、150 件を超えるアラートを含む重大度の高いインシデントから、同じサーバーへ戻ってきます。ここで James は、セキュリティ管理者はリソースの露出・推奨事項・アタックパスに注目し、SOC アナリストは進行中のインシデント・ネットワークアクティビティ・ワークロードの証拠をたどって同じリソースに着く、と整理します。**それぞれの役割が必要なコンテキストを、同じ環境の同じ見え方から得られる**ことが、Defender でこれらの体験がつながっている強みだとしています。

### 5.7 ネットワークをセキュリティのコントロールプレーンとして使う

ここから Ashish に交代します。James は、攻撃者がワークロードに到達する前に、トラフィックが環境に入る必要があること、また足がかりを得たあとはネットワークの接続性が次に到達できる範囲を左右することを説明しました。これにより、同じ攻撃を妨害する追加の機会（ワークロードに届く前の悪意あるトラフィックの検査・フィルタリング、横展開に使えるパスの制限）が生まれます。

Ashish は、パッチ展開のライフサイクルから話を始めます。新しいゼロデイが公表されると、セキュリティ管理者は脆弱性を調べ、影響を分析し、パッチをテスト・検証し、問題がなければ展開します。この展開には、これまでの傾向として最低でも 5 週間以上かかるといいます。しかし「私たちが vibe coding をしている間、攻撃者は vibe hacking をしている」ため、このパッチウィンドウはもはや通用せず、特化したモデルを使えばゼロデイのエクスプロイトを数時間、場合によっては数分で作れると述べています。

### 5.8 Azure Adaptive Virtual Patching

この課題に対して導入されるのが Azure Adaptive Virtual Patching です。Ashish は「嵐（AI を使う攻撃者）の中の傘」にたとえます。傘は、屋根（完全なパッチの展開）の下に安全に入るまでの時間を稼ぐもので、**パッチそのものを代わりに展開するわけではありません**。

仕組みは、3 つの「セマンティックレイヤー」で説明されました。

1. **脆弱性のレイヤー**: 新しいゼロデイが公表されると、サービスはその脆弱性が何をするものか、どう動くか、どのプロセス・モジュール・ポートを使うかを意味的に理解し、セマンティックマップを作ります。これを起点に、社内で構築されたパイプラインが動きます。このパイプラインは AI を使い、管理されたテスト環境でエクスプロイトを作り、その脆弱性で攻撃できる対象のテスト環境も作って実際に攻撃します。エクスプロイトが検証されると、次に適切な緩和策を特定し、それも検証します。Ashish はこれを「AI が AI から守る」と表現しています。緩和策が見つかると、人間が介在して（human in the loop）その緩和策が正しいか確認します。検証されると、その緩和策と脆弱性がサービスにオンボードされます。
2. **Azure 環境のレイヤー**: 実行しているワークロード、その構成、開いているポート、動いているプロセス、インストール済みのモジュールといった環境全体の棚卸しをします。
3. **露出面のレイヤー**: 1 と 2 を組み合わせ、露出面（攻撃面）を判断し、AI を使って対応する緩和策を特定します。この緩和策は、そのワークロードに特化した内容に変換されます。たとえば脆弱なワークロードが標準でないポートで動いている場合、その緩和策はデプロイ前に、ワークロードが使っているポートに合わせて自動的に更新されます。これは一例にすぎず、緩和策は非常にコンテキストに依存するとしています。

デモの内容は 6 章に書きます。

### 5.9 Azure Firewall: AI Security アドオン

Ashish は、今回発表する Azure Firewall の Premium SKU のアドオンとして **AI Security for Azure Firewall** を紹介しました。機能は「securing AI（AI を守る）」と「securing with AI（AI で守る）」の 2 系統です。

**securing AI**

- **プロンプト インジェクション保護**: プロンプトを受け付けるエンタープライズ向けの生成 AI アプリに対し、悪意あるプロンプトがありうるため、Azure Firewall をその経路に置いてネットワーク上でプロンプトインジェクション対策を適用する
- **ネットワーク DLP**: Microsoft Purview と同じデータセキュリティポリシーを、AI ワークロード（またはクラウドネイティブのワークロード）へのアクセス時にネットワーク上でも適用できるようにする
- **AI policy**: トラフィックとポリシーに AI を組み合わせ、ポリシーの最適化を提案させる。これにより Azure Firewall でのセキュリティ運用を円滑に回せるようにする

**securing with AI**

ネットワーク上でインラインに動く新しい AI モデルを 2 つ作ったと説明されました。1 つはマルウェア検出、もう 1 つはアプリケーション保護です。

#### マルウェア検出モデル

既知のものに対する防御は比較的容易ですが、未知のマルウェアは難しい、というのが前提です。多くの製品はサンドボックスと「デトネーション」を使います。新しいバイナリペイロードを見つけたらブロックし、サンドボックスで実行して、ファイル操作やネットワーク操作を観察し、悪意の有無を判断する方法です。Ashish はこれが次の理由で、現代のマルウェアには拡張しにくいと述べています。

1. インラインでは実行できない。時間がかかり、通常は事後（オフライン）に分析する
2. 新しいファイルペイロードごとにコンピュートやサンドボックスを立ち上げる必要があり、コストが高い
3. 最近のマルウェアは AI を使い、サンドボックスで動いていることを検知して本来の挙動を見せないため、無害と誤分類しかねない

そこで、**アセンブリのオペコードに基づいてバイナリペイロードを分類する AI モデル**を作りました。言語モデルが得意なのは言語であり、それは英語である必要はない、という考えから、オペコードを分類して悪意あるバイナリか無害かを判断するよう学習させたといいます。

#### アプリケーション脆弱性保護（Advanced application threat protection）

従来のアプリケーション保護は、正規表現、パターン、文字列一致に基づきます。しかし、特化したモデルを使うエージェントに「特定の正規表現を回避する悪意あるウェブリクエストを作れ」という目標を与えれば、固定の静的ルールセットを回避するリクエストを作らせることができます。このため従来型の保護は、現代の AI 時代には拡張しにくいと述べています。

新しい AI モデルは、ネットワーク上でインラインに動き、数ミリ秒でウェブリクエストを悪意あるものか無害かを、ルールではなく意味的に分類します。ルールのチューニングや正規表現の運用が不要になり、有効にするだけで、ウェブアプリに対する **35 を超える攻撃カテゴリ**から保護するとしています。

### 5.10 Azure Bastion: RDP vision と SSH vision

Azure Bastion は、VM を公開インターネットにさらさずに、RDP や SSH で Azure 上の VM に接続できるサービスです。昨年、RDP や SSH でユーザーが行ったことをすべてビデオとして Azure Storage の BLOB に保存するセッション録画機能が発表されました。ただし、数百のワークロード、数百のユーザーがあれば、毎日数千のセッション、数千本のビデオができ、「誰がそれを見て、何が起きたか、どれが危険な動きかを特定するのか」が課題になります。

そこで今回導入されるのが **RDP vision と SSH vision** です。セッションのビデオが作られたあと、AI で推論を適用し、リスクのある動きを見つけてフラグを立て、セッションで起きたことの要約も付けます。RDP と SSH の両方に対応します。

## 6. デモ・手順

このセッションは、デモが中心です。画面上の細部は音声からは確認できないため、語られた範囲の内容だけを順に整理します。

### 6.1 インシデント グラフの調査（SOC アナリストの視点・James）

1. 160 件のアラートが 1 つの相関グラフにまとめられたインシデントを開く。多数のエンティティが関連している
2. グラフ内の Woodgrove のノードをクリックし、周囲のインシデント ビューを維持したままコンテキストを開く
3. 資産の詳細を開く。Microsoft Defender が、この資産を Azure の仮想マシンとして識別し、クラウドリソースのコンテキストを提供している
4. クラウド環境の追加情報を展開し、別の資産へ接続をたどる。その資産は Google Cloud のインスタンスで、複数の環境にまたがっても同じ調査でコンテキストが保たれる
5. グラフに戻り、インシデントに関連する URL を表示し、そこから別のサーバーへたどる。このサーバーはインターネットに公開され、外部からのインバウンド通信を受けている
6. このサーバーに接続された ID を調べる。アカウントは機密（sensitive）としてマークされ、ドメイン管理者権限を持つため、調査上とくに重要
7. その ID はネットワーク ID の大きなグループにつながっており、展開すると、このインシデントに関連するネットワーク関係が見える。IP アドレスは 21 個
8. このように、孤立したアラートからインシデントを再構築しなくても、クラウド資産、ID、デバイス、ネットワークエンティティの関係をたどれることが示された

### 6.2 ポスチャーの確認（セキュリティ管理者の視点・James）

1. 重大および高リスクの推奨事項を開く。推奨事項ビューは環境全体の検出結果を整理している
2. 脆弱な OpenSSL に起因する「露出したコンピュートリソース」の推奨事項を開く。OpenSSL の検出内容と影響を受ける資産が示され、選択した資産がインターネットに公開されていることも分かる
3. 展開した詳細には、露出、脆弱性、対応付けられた攻撃手法のコンテキストが含まれる。「証拠」ビューは、推奨事項を、その資産で検出された具体的なソフトウェアと脆弱性の情報に結び付ける
4. 「修復アドバイス」ビューには、この検出結果に対処する手順が示され、影響を受けるソースと裏付けとなる証拠に関連付けられている
5. マップは、影響を受けるサーバーを周辺のクラウドコンテキストの中に置き、関連リソースを表示する。グループノードを展開すると、サーバーと並んで 3 つのストレージアカウントが見える
6. 推奨事項から影響を受けるサーバーへ進み、統合されたサーバーページを開く。このページには、資産の詳細、クラウドコンテキスト、アクティブなアラート、セキュリティ推奨事項、リソースの関係が集約されている。セキュリティ管理者にとって、リソースとそのセキュリティ問題を把握する 1 か所になる
7. クラウド環境のセクションには、サーバーの背後にある Azure のクラウドリソースのコンテキストがある。インシデントとアラートのセクションにはこのサーバーに関するアクティブな問題が出ており、ここで James は SOC チームを巻き込み、自分はサーバーの露出とポスチャーの確認・対処を続ける、という使い分けを説明している
8. インシデントを開くと、関連するアラートと動きが、サーバーを調査のコンテキストとして保ったまま表示される
9. セキュリティ推奨事項のセクションには、サーバーに関連するポスチャーの検出結果が出る
10. アタックパスを開くと、同じインターネット公開サーバーから始まる複数のパスがある。1 つを開くと、公開された VM から、そのマネージド ID を経由して Azure OpenAI リソースに至る流れが表示される。最終ノードを選ぶと、その Azure OpenAI リソースの詳細が開く
11. 同じ公開サーバーが、Microsoft Defender for Cloud（MDC）による複数のアタックパスに登場している
12. 脆弱性ビューには、サーバーに関する CVE の証拠（影響を受けるソフトウェアと関連する脆弱性）が示される。インベントリは、それらをサーバーにインストールされたソフトウェア（脆弱な OpenSSL パッケージを含む）に結び付ける
13. 概要ページに戻ると、サーバーと周辺リソースの関係マップに戻る。マップから、サーバー周辺のクラウドリソースへ移動できる
14. 最後にネットワーク インターフェースのペインが表示され、サーバーに関連するネットワーク コンポーネントが、リソースのコンテキストを一段広げる

### 6.3 インシデントの再調査（SOC アナリストの視点・James）

1. 150 件を超えるアラートを持つ重大度の高いインシデントを開く。Defender は関連する動きを 1 つのインシデントにまとめている
2. 「優先順位の要因（priority factors）」で、インシデントの何が重大度を押し上げているか、どこから見るべきかが分かる。Defender は、関与する重要資産も特定する。その 1 つが、調査の起点となるサーバー
3. インシデント グラフから、周囲のコンテキストを保ったままサーバーの詳細へ進む。サーバーは、インターネットに公開され、リスクが高く、露出が非常に高く、外部からのインバウンド通信がある、と表示される
4. インシデントのこの部分に関連するネットワークエンティティをたどる。2 つの IP アドレスがあり、Defender はこれらを関連するものとしてグループ化しつつ、個別にもコンテキストを調べられる。IP の詳細は、ネットワークとインシデントの追加のコンテキストを提供する。2 つ目のネットワークエンティティも開き、それに関連するセキュリティ上の動きを確認する
5. グラフに戻り、このエンティティに調査の焦点を絞る。インシデント全体ではなく、ネットワークの動きに関連するアラートと関係に表示を絞り込める
6. ネットワークシグナルから、関連するワークロードの動きへ移る。タイムラインが、ネットワークイベントとサーバー上のプロセスの動きを結び付けている
7. アラート インベントリで、スクリプトベースのネットワークの動きに関する別の検出を見る。Defender は、そのネットワーク検出に関連するプロセスの動きを表示し、アラートにワークロードのコンテキストを与える
8. そのワークロードの証拠は、より広いインシデントとつながり、影響を受けたデバイスも同じ調査にまとまる。関与する ID や基盤となるクラウドリソースもつながっている
9. 最後に、調査を始めたサーバーのページに戻る。これは先ほどポスチャーの視点で見たのと同じサーバーである

### 6.4 Adaptive Virtual Patching（Ashish）

1. PHP の脆弱性を例にする。影響を受けるバージョンの PHP は、特別に細工したウェブリクエストでメモリ不足の例外を起こせる。そこから実行中のメモリを外部に流出させ、リモートコード実行につなげられる
2. 脆弱なワークロードが動いている。バージョンを確認すると「812」と聞こえる（音声認識の都合で表記が確定できません）。脆弱なバージョンである
3. 攻撃を実行する。攻撃は成功し、サーバーの実行中メモリが流出する。これでリクエストを細工すればリモートコード実行も可能になる
4. Azure portal で Adaptive Shield リソースを使う。これは Azure portal のトップレベルのリソースで、まず「傘」にあたるこのリソースを作成し、その下に保護したいリソースを追加する
5. 脆弱だった PHP ワークロードがすでに追加されており、このワークロードに該当する脆弱性が検出されている。AI が、そのワークロードを当面守るためにどうするかという非常に細かい緩和策を提示する。展開するのはパッチではなく仮想パッチのみ
6. 推奨された緩和策を選び、「次へ」から緩和策を承認する。緩和策がワークロードに展開され、ステータスが「成功（succeeded）」になる
7. 同じ攻撃をもう一度実行すると、メモリはもう流出せず、攻撃は成功しない
8. ポイントとして、実際のパッチは一度も展開していない。ワークロードも停止していない。完全なパッチを展開したあとは、ポータルでロールバックを選べば、仮想パッチ（緩和策）はシームレスに外せる

### 6.5 Azure Firewall のマルウェア検出（ナレーション付きデモ）

最初に Ashish が設定を説明します。Alice の端末のトラフィックには Azure Firewall のアンチマルウェアを適用せず、Bob の端末のトラフィックだけがバイナリペイロードを新しい AI モデルに通す構成です。その後、ナレーションに沿ってデモが進みました。

1. アンチマルウェアのセキュリティ プロファイルを「アラートと拒否」モードで作成する。Azure Firewall を通過するファイルは分析され、マルウェアのリスクスコアが付く。スコアが 50 を超えるファイルはアラートを生成し、80 を超えるファイルは自動的にブロックされる
2. このアンチマルウェア プロファイルを、セキュリティ プロファイル グループに入れる。グループを使うと、複数のセキュリティ機能をまとめて適用できる
3. Bob の端末からのトラフィックに一致するアプリケーションルールと、Alice の端末からのトラフィックに一致するアプリケーションルールの 2 つを用意する。セキュリティ プロファイル グループは Bob のルールにだけ関連付ける。その結果、Bob の端末のトラフィックはすべてマルウェア検出モデルで検査される
4. 画面の左に Alice と Bob の端末、右に 2 つの監視ウィンドウがある。上のウィンドウはマルウェア検出モデルの出力、下のウィンドウは各ファイルのリスクスコアと結果のアクションを含む Azure Firewall のログ
5. Alice が悪意あるファイルを OneDrive にアップロードする。検出が有効でないため検査されず、アップロードは成功し、マルウェア関連のイベントも生成されない
6. Bob が同じ悪意あるファイルをアップロードする。今度は Azure Firewall が検査し、モデルが悪意あるコンテンツと判定して拒否する。設定された拒否のしきい値を超えるリスクスコアが付き、ファイルは即座にブロックされる。監視ウィンドウでは、モデルが悪意あると分類した結果と、Azure Firewall のアラートおよび実施されたアクションの記録の両方が見える
7. 最後に Bob が問題のないファイルをアップロードすると、同様にモデルが分析し、低いリスクスコアが付いて許可される。ログには、コンテンツが評価されて安全と判断されたことが残っている

Ashish は、既知・未知の両方のマルウェアを、Azure Firewall の新しいアドオンのインラインの AI モデルが分類した例だと整理しています。

### 6.6 Advanced application threat protection（ナレーション付きデモ）

1. Advanced application threat protection のセキュリティ プロファイルを作成する。このデモでは、アラートのしきい値が 50、拒否のしきい値が 80。エンジンはファイアウォールを通るコンテンツを分析して信頼度スコアを出し、50 を超えるとアラート、80 を超えるとブロックされる
2. プロファイルをセキュリティ プロファイル グループに追加する。この例では、このプロファイルだけが入っている
3. このグループを、クライアントのトラフィックに対するアプリケーションルールに関連付けて保存する。以降、クライアントのトラフィックは脅威防御エンジンで検査される
4. 構成は、悪意あるリクエストと無害なリクエストを混ぜて生成するクライアント端末が 1 台あり、そのトラフィックがすべて Azure Firewall を経由してアプリケーションルールに一致する、というもの。画面左上がクライアント端末、右上が AI モデルによる分析のログ、下が 2 つのバックエンド インスタンスの Azure Firewall ログ（検査中に生成された脅威の信頼度スコアを含む）
5. クライアントは、脆弱性を突くものと正常なものが混在する 2,000 件のリクエストを送る
6. トラフィックを流すと、エンジンがインラインでリアルタイムに分析する。拒否のしきい値を超える信頼度スコアで脆弱と判定されたトラフィックはブロックされ、残りは検査のうえ許可される
7. テストが終わると、左上にアプリケーション脅威防御エンジンの全体の精度が表示される。Ashish は、精度が 95% を超えたと説明し、従来型のアプリケーション保護では同じ数値が約 10% になると補足している（この比較の条件は発表では説明されていません）

### 6.7 RDP vision / SSH vision（ナレーション付きデモ）

**RDP**

1. Azure portal から、Bastion 経由で Windows VM に接続する。この Bastion Premium ホストは、セッション録画と RDP vision が有効で、Bastion ホストに設定された ID を使ってセッション全体が録画され、Blob ストレージに保存される
2. 悪意ある意図を持つユーザーを演じ、Windows Defender ファイアウォールを開いてファイアウォール保護をオフにする
3. デスクトップに保存されたプレーンテキストのファイルを開き、中に保存された API シークレットを確認する
4. セッション終了後、RDP vision が録画に対して推論を実行し、少し時間をおいて結果を公開する
5. Bastion のポータルに戻ると、セッションが「セッション録画」に AI のインサイトとともに表示される。RDP vision がセッションを要約し、2 件のリスクのある操作（ファイアウォールの無効化、プレーンテキストに保存された API シークレットの閲覧）にフラグを立てている。検出結果を選ぶと、録画のその場面に直接ジャンプする

**SSH**

1. Bastion 経由で Linux VM に接続する。コマンドのログと SSH vision が有効なので、セッション内のすべてのコマンドが記録される
2. ユーザーは、特権シェルを起動して、自分のアカウントにパスワードなしで昇格できるように設定するなどの、リスクのある操作を試みる
3. セッション終了後、SSH vision がコマンドログに対して推論を実行し、結果を公開する
4. セッションがポータルに分析結果とともに表示される。SSH vision がセッションを要約し、権限昇格の試行にフラグを立て、各検出結果を元のコマンドログの該当コマンドにリンクする

まとめとして、管理者がリスクのある動きに気づき、調査の焦点を絞り、AI のインサイトを元のセッションの証拠と照らして検証できる、と説明しています。

## 7. 注意点・発表者の気付き

- **パッチ展開には時間がかかる**: ゼロデイ公表後のパッチ展開は、これまでの傾向として最低でも 5 週間以上かかるとされ、AI を使う攻撃者に対してはこの期間が長すぎると述べられています。
- **仮想パッチは完全なパッチの代わりではない**: Adaptive Virtual Patching は、完全なパッチを展開するまでの時間を稼ぐための緩和策です。完全なパッチを展開したら、ポータルで仮想パッチをロールバックします。
- **緩和策には人間の確認が入る**: 緩和策がオンボードされる前には、人間が正しさを検証する工程があると説明されています。
- **従来型の防御が抱える限界**: サンドボックスとデトネーションは、インラインで実行できない、コストが高い、回避されうるという 3 点が挙げられました。また、正規表現やパターン一致に基づくアプリ保護は、AI が作る回避リクエストに対して通用しにくいと述べられています。
- **セッション録画の運用負荷**: 録画だけでは、数千本に及ぶビデオを誰が見るのかという課題が残ります。RDP vision / SSH vision はこの課題に対応するものです。
- **単体のアラートでは足りない**: 個々の脆弱性やアラートだけでは、攻撃者が実際に到達できるかは分かりません。コンテキストを組み合わせて判断する必要があります。
- 提供時期、価格、一般提供（GA）かプレビューかといった情報は、発表では触れられていません。Azure Firewall の AI Security アドオンについては、「今日発表する（announcing）」という発言と、Premium SKU のアドオンであるという説明のみです。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

| 領域 | 語られた利点 |
| ---- | ---- |
| Defender のコンテキスト連携 | アラートを 1 件ずつ調べず、1 つのインシデントにまとめて調査できる。セキュリティ管理者と SOC アナリストが、同じ環境の同じビューから、それぞれ必要なコンテキストを得られる |
| ポスチャー管理 | 全ての検出結果を同列に扱わず、攻撃経路やデータへの影響を元に、最も露出の大きいリスクに集中できる。コードからクラウドへのコンテキストで、問題を発生源に近いところで直せる |
| Adaptive Virtual Patching | ワークロードを止めずに、パッチ展開前に脆弱性を緩和できる。緩和策はワークロードの構成（ポートなど）に合わせて調整され、完全なパッチ展開後はロールバックできる |
| Azure Firewall のマルウェア検出 | 未知のマルウェアも含め、サンドボックスを使わずにネットワーク上でインラインに分類・ブロックできる |
| Azure Firewall のアプリケーション脅威防御 | ルールのチューニングや正規表現の運用なしに、35 を超える攻撃カテゴリから保護できる。デモでは精度 95% 超 |
| RDP vision / SSH vision | 大量のセッション録画の要約とリスク操作のフラグ付けを AI に任せ、元の録画やコマンドログに直接ジャンプして検証できる |

なお、顧客名を挙げた導入事例は、このセッションでは紹介されていません。

## 9. まとめ

このセッションは、攻撃を「入口の露出」「ワークロードでの侵害」「ネットワークでの到達と横展開」という一本の経路として捉え、各所にチョークポイントがあると示しました。クラウド側では、Microsoft Defender がポスチャー管理とワークロード保護を組み合わせ、同じ VM を管理者と SOC アナリストの 2 つの視点から調べられることをデモで示しました。ネットワーク側では、AI を使う攻撃者に対抗するため、Adaptive Virtual Patching による仮想パッチ、Azure Firewall の AI Security アドオン（プロンプトインジェクション保護、ネットワーク DLP、AI policy、マルウェア検出、アプリケーション脅威防御）、Azure Bastion の RDP vision / SSH vision を紹介しました。個々の機能の提供状況は発表では説明されていないため、利用を検討する場合は別途確認が必要です。
