# BRK341 Inside Look at Agent 365: Lessons from Microsoft's Office of the CISO

## 1. はじめに

このセッションは、Microsoft 社内でセキュリティを担う Office of the CISO（最高情報セキュリティ責任者の組織）の 2 人が、自社のエージェント群をどう守っているかを紹介するブレークアウトセッションです。Microsoft 自身が最初の利用者となる「Customer Zero」の立場で得た学びを、Agent 365 の画面を使った 2 つのデモとあわせて説明しています。

前半は Karen Dahmen 氏が、戦略とガバナンスの観点から「エージェントの資産をどう捉え、どう守るか」を語ります。後半は Vivek Vinod Sharma 氏が、Agent 365 と Microsoft Defender で実際にどう調べ、どう止めるかを実演します。結論は、**エージェントはすでにどの組織にもいて、問われているのは「見えているか、統制できているか、信頼できるか」である**という点です。さらに、**「予測できるリスクは防ぎ、防げないものは封じ込め、継続的に改善する」**という進め方が示されました。

1 つ目は、**製品は社内の実運用から生まれた**ということです。Vivek 氏は、Microsoft が必要な機能を満たす方法として「市場の最適な製品を選ぶ」場合と、「市場に完成品がないので社内で作り、大規模運用から学ぶ」場合の 2 通りがあると説明しました。Agent 365 は後者の道をたどり、社内のレジストリ（登録台帳）や、既存のテナント信頼・アプリのライフサイクル管理の要件が、製品の形になったということです。製品を社内で使い、学びを製品に戻す循環が、Customer Zero という考え方です。

## 5. 発表内容の詳細

### 5.1 会場への質問と、使命・体制

冒頭、Karen 氏は挙手で 2 つ尋ねました。すでに Agent 365 を使っている人がいるか、そして、エージェントを統制するための何らかのプラットフォームを使っている人がいるかです。どちらにも手が挙がり、「すべての人に何かしら持ち帰れる内容にする」と述べています。

Office of the CISO の使命は、Microsoft とそのお客様、パートナーを、サイバーセキュリティの脅威から守ることです。学校や病院、身近な人々を支えるシステムを守るという意味で、「広く、かつ個人的な使命」だとも語られました。Microsoft はテクノロジー企業であり、セキュリティとイノベーションを引き換えにはできません。また価値の高い標的でもあるため、エージェントの普及によって、リスク評価・防御の提供・対応の速さに対する圧力が高まっているという説明です。

脅威は、技術スタックや事業部門、組織の境界を越えて動き、1 つのチームでは追えない速度で進みます。そのため、スライドでは縦方向に各エンジニアリング部門のスタック、左側に基盤となるセキュリティ機能を並べたマトリクスを示し、責任と権限を明確にして連携する体制を説明しました。脅威インテリジェンスのチームがどこを強化するかを導き、テストとインシデント対応のチームがどこに改善が必要かを示し、そこでの学びが製品の形を決めていきます。エージェントが増えるほど、この責任モデルの重要性は増すという位置づけです。

### 5.2 AI がサイバーセキュリティに与える 2 つの影響

Karen 氏は、AI の影響を 2 つに分けて説明しました。

- **守る対象が変わる**：生成されるコンテンツだけでなく、相互に連携したツールの呼び出しやデータへのアクセスが、新しい種類のシステムと攻撃対象領域になります。
- **防御の手段が変わる**：脆弱性の分析、セキュリティ保証、レッドチーム（模擬攻撃による検証）といった機能が、速度と規模の面で強化されます。

重要なのはこの 2 つの交点です。エージェントが防御の一部になれば、そのエージェントを守ることは Microsoft を守る力そのものを守ることになるため、「賭け金はこれ以上なく高い」と述べています。

変化の大きさを示す例として、Windows の Patch Tuesday が挙げられました。ある回には、Windows のセキュリティ修正の件数が、その年の残りの月をすべて足した数と同じだったということです。既存のリスクの発見が、かつてない速さで進んでいます。

あわせて、新しい攻撃対象領域として、タスクへの忠実さの喪失、プロンプトに対する攻撃やジェイルブレイク、過剰な権限（エージェントに与えすぎた裁量）が挙げられました。

> 注意：プロンプトへの攻撃について、発話では「prompt ejection」と聞こえる箇所があります。後半のデモでは prompt injection（プロンプトインジェクション）と発言されています。前半の表記は音声認識の都合で確定できないため、聞こえたままにしています。

### 5.3 社内の規模と、北極星・運用原則

Microsoft 社内のエージェントは **100 万を超え**、今後も増える見込みです。人手のレビューでは足りず、全体を見渡す可視性と、最も露出の大きい場所を絞り込む知的な手段が必要だと説明されました。すべてのエージェントに基本的な保護は要りますが、注意を向けるのは影響の大きい操作に絞ります。

目指す姿（北極星）は次の一文です。**Microsoft のエージェント資産のすべてが、発見され、リスクの文脈が与えられ、先回りのガードレールと事後の封じ込めで統制されている**こと。これを支える運用原則は次の 4 つです。

- 露出（エクスポージャー）：制御は「結果の重大さ」に従わせる
- ID：アクセスは範囲を絞り、取り消せるようにする
- 防止：予測できるリスクに集中し、それ以外は被害を封じ込められるよう備える
- 測定：活動量ではなく、狙ったセキュリティ上の成果が出ているかを測り、検証する

リスク軽減は 3 つの柱で考えます。1 つ目は、重要なすべての面にわたる可視性と管理です。2 つ目は、露出の把握です。3 つ目は、リスクについての共通の理解で、自律性、アクセス、被害の及ぶ範囲（影響範囲）、実行時のシグナルを材料に、何を最初に見るべきかを決めます。可視性が上がるとスコアリングが良くなり、優先順位が良くなり、対処から新しいシグナルと学びが生まれるという、循環する流れだと説明されました。

### 5.4 Agent 365 が生まれた経緯と、3 者の役割分担

ここから Vivek 氏が話しました。社内では、エージェントが急増するなかで、各チームが本番用のレジストリを作り、どんなエージェントがあり、誰が所有し、どんなアクセス権を持ち、どう・どこで使われ、いくらかかっているかを把握しました。また、既存のテナント信頼とアプリのライフサイクル管理の仕組みから、デプロイ前の評価要件が得られました。具体的には、アクセスできるデータ、実行できる操作、使う ID、そして観測・制御できるかどうかです。これらは机上の要件ではなく、実際に Microsoft のエージェントを大規模に運用して得られたものだと強調されました。

Agent 365 は、エージェントの**可観測性のためのプラットフォーム**として紹介されました。組織がエージェントを観察し、統制し、保護するためのものです。北極星に挙げたリスクベースの制御、制御の中心としての ID、ポリシーと封じ込め、そして減らした露出の測定という原則を、企業全体で実践するためのツールという位置づけです。

Agent 365 の使い方は、順序のある道筋として説明されました。

1. 1 か所でエージェント資産の全体を見る（何があるか、誰のものか、何をしているか）
2. 誰が何を許可され、問題が起きたとき誰が答えるのかを定め、説明責任を持たせる
3. リスクの所在を理解し、制御を設け、エージェントを保護する
4. その後に初めて、AI への支出がどこにあり、成果につながっているかという価値を語る

見えないものは統制できず、統制できないものの価値は証明できない、というのがこの順序の理由です。

社内のモデルでは、Microsoft Digital が IT 管理者の役割、Office of the CISO がセキュリティ管理者の役割を担います。全体は 1 チームでは管理できないため、次の 3 者で責任を分担します。

| 担い手 | 役割 |
| --- | --- |
| Microsoft Digital（IT 管理者） | エージェント資産を健全に保つ。所有者を確実に置き、ライフサイクルと継続性を管理し、コストを制御し、大規模な自動化を進める |
| Office of the CISO（セキュリティ管理者） | 最もリスクの高いエージェントを見極め、ID・セキュリティ・データの制御を適用し、脅威が出たときに調査・対応する |
| メーカーとビジネススポンサー | エージェントを作り、日々使う立場として、重要な業務上の文脈を提供する |

Agent 365 は、これらの責任を共通の制御プレーンでつなぎます。共通のシグナルとポリシーに基づき、各チームが自分の役割に合ったツールと制御で動きます。「資産は 1 つ、しかし責任は明確」という整理です。

### 5.5 シナリオ 1：可視化（何があり、誰のもので、何に届くか）

Karen 氏は、セキュリティはいつも棚卸しから始まると前置きし、可視化の中身を説明しました。エージェントは Microsoft 内でも多くの「ファクトリー（作成基盤）」で作られており、情報とツールチェーンは各所に散らばっています。把握していないツールが使われているケースもあります。そこで、発見の段階で次の問いに答える必要があります。

- どのエージェントがあるか
- それぞれの所有者は誰か
- 業務上の目的は何か
- 何に「届く」か：動作する ID、アクセスするデータの所在・種類、呼び出せるツールとスキル、そのエージェントを使える人

エージェントのリスクを評価する要素は、次の 5 つです。

| 要素 | 見るポイント |
| --- | --- |
| 自律性と操作の範囲 | 人の監督があるか、自分でトリガーするか。データの読み取りだけか、削除のように元に戻しにくい操作までするか |
| データへのアクセスと権限 | 公開情報か機微な情報か。権限は絞られ一時的か、広く高権限か |
| 入力（特に信頼できない入力） | メール、文書、Web サイト、さらには別のエージェントが、そのエージェントの挙動をどこまで左右できるか |
| 到達範囲と影響範囲 | 問題が起きても 1 つのアプリに収まるか、テナントをまたいで横方向に広がるか |
| 可逆性 | 元に戻しにくい操作ほど、制御を厳しくし、封じ込めを速くする |

封じ込めの手段は 1 つの万能スイッチではなく、技術スタック全体に組み込む必要があります。エージェントの一時停止、ネットワーク制限、キーの無効化、セッションの失効、さらにはエージェントが動いている端末やエンドポイントの切り離しなどです。どのプラットフォームでどの制御が使え、誰が使い、どれだけ速く効くかを把握しておく必要があります。

Karen 氏は、この時代の考え方の変化として次を挙げました。

- 全プラットフォームを通じて、資産の見え方を 1 つにそろえる
- 何が危険な振る舞いかを組織で合意する。リスクの見方が違えば判断が割れる
- 新しいシグナルが入るたびに、露出の見え方を素早く更新する
- すべてを「エージェントが何に届き、何をできるか」で導き、すでにある制御も考慮に入れる
- しきい値と行動を結びつける（誰が、何を、どれだけ速く対応するかを、リスクに基づいて決める）

### 5.6 デモ 1 を踏まえた、導入初期の 4 ステップ

デモの内容は 6 章に記載します。デモ後に Vivek 氏が、これから Agent 365 を始める人向けの 4 つの基本ステップを整理しました。

1. シャドー活動を含めて、資産の全体を発見する（シグナルは製品内で取得できる）
2. 説明責任と所有者を明確にする。所有者のいないエージェントは調査も是正も難しい
3. アクセスと関係性を理解する。エージェントが届くデータ、ツール、ユーザー、リソースを把握する
4. リスクで優先順位を付ける。リスクのあるエージェントは大量にあるため、最も高いものから着手し、セキュリティ担当者の時間を最適化する

すでに Agent 365 を使っている人には、さらに 2 つの深め方が示されました。エージェントの振る舞い、文脈、アクセスできるツールを調べること。そして、テレメトリを、より広い監視・セキュリティのワークフローに組み込むことです。イベントの集約や分析に使っているツールへシグナルを流せる、と説明されています。進め方としては、発見、説明責任の割り当て、関係性の理解、優先順位付け、調査、運用への組み込み、という順です。

### 5.7 シナリオ 2：対応（予測できるものを防ぎ、残りを限定する）

Karen 氏は、リスクが見えたあとにどう行動し対応するかを、「予測できるものを防ぎ、残りを限定する」という枠組みで説明しました。

露出を増やす典型的な落とし穴は、次のとおりです。

- 所有者のいないエージェント
- ある環境では適用したガードレールが、別の環境で漏れていること
- ツールや接続の誤用
- エージェントが本来の目的から逸脱していくこと（ドリフト）

それぞれに必要な行動は、所有者の割り当て、ポリシーの穴の是正、調査のあいだのエージェント一時停止などです。小規模なら個別対応できますが、Microsoft の規模では一貫した方法が必要です。そのために、明確な責任モデルと、エージェントのプロビジョニング（作成・配備）時点に組み込まれた強制の仕組みが必要になります。権限、ツール、構成は変わり続けるため効果を持続させること、そして行った対処が実際に露出を減らしたと明示的に確認することも求められます。

**事前（プロアクティブ）の対策**

- ガバナンスは ID から始まる。可能な限りマネージド ID を使い、権限の範囲を絞り、共有の資格情報は使わない
- 影響が大きい操作には人の監督を要求する
- 多くの場合、承認されたツールを使う
- 機微データを保護し、改ざんできない監査証跡を確保する

**事後（リアクティブ）の対策**

エージェントが想定外の動きをしたり、侵害の兆候を示したりした場合に備えます。多くはプラットフォーム依存で、エージェントの一時停止、アクセスの取り消し、ネットワーク制限、端末の隔離などです。すべてのプラットフォームがすべての選択肢に対応しているわけではないため、どの制御が機能し、どれだけ速く効くかを、頼る前にテストしておく必要があります。

成功は、検知、優先度付け（トリアージ）、是正という一連の流れが端から端までつながっていることです。検知は、調べるべきシグナルが資産のどこかに現れること。トリアージは、そのシグナルに、エージェントがどこで動き、何につながり、誰が使っているかという文脈を深く足すこと。是正は、露出そのものに対処し、結果が狙いどおりかを検証することです。最も高いリスクの露出を減らし、対応が機能していると確認できて、初めて成功だと語られました。

制御と対応の速さは、露出に合わせます。事前には、デプロイ前と開発時にポリシーチェックを自動化し、所有権、アクセス、ガードレールを、エージェントの作成時に定義します。また、誰が動けるかを知っておくこと、ID、ツール、データ、関係性を考慮した「エージェント対応のプレイブック」を用意してテストすることが、基本として挙げられました。リスクの高いエージェントには境界を厳しくして封じ込めを速くし、低リスクのものには余計な摩擦を与えない、という方針です。目標は、緊急の局面でその場しのぎに組み立てるのではなく、繰り返し使える封じ込めが滑らかに発動することです。

### 5.8 まとめとして示された 4 つの教訓と、持ち帰る 2 点

Vivek 氏は、デモ 2 の経験から、リスクの予防と封じ込めの両方に明確な手順が必要だとして、次の 4 点を挙げました。

1. **ガバナンスを左へ寄せる（シフトレフト）**：エージェントを作る工程にガバナンスを組み込み、ポリシーをコードとして扱い、後からの手作業や一時点の対応に頼らず一貫して制御を適用する
2. **デプロイ前にガードレールを設ける**：アクセスできるもの、使えるツール、追加承認が必要な場面を定め、予測できるリスクを本番に到達する前に防ぐ
3. **封じ込めを設計する**：悪いことは起きる。事前の保護とあわせて事後の制御が要る。万能の停止スイッチはなく、リスクとプラットフォームに応じて複数の手段を使い分ける
4. **運用に落とし込む**：エージェント対応のプレイブックを整え、検知とトリアージから封じ込めと復旧まで、誰が判断し誰が動くかを定義する

すでに使っている人には、継続的な改善が勧められました。社内で行っている循環のように、インシデント、演習、是正の結果を、ポリシーとプレイブックの改善に繰り返し反映します。目標は、**防げるものは防ぎ、防げないものは封じ込め、資産の変化に合わせて改善し続ける**ことです。

### 5.9 Q&A

発話では、発表の終わりに質疑応答の時間は確認できません。挙手による会場への質問が数回ありました。質問と反応は次のとおりです。

- ローカルエージェントを一切許可していない人：数人のみで、会場の大半は許可している
- 管理下の環境で動くローカルエージェントのすべてのインスタンスを可視化できている人：自信のある手が数人挙がった
- IT 管理者の役割を担っている人、セキュリティ管理者の役割を担っている人：それぞれ挙手があった
- 「何かが動いているので探してほしい」という趣旨の連絡を受けたことがある人：デモ 2 の導入として尋ねた

## 6. デモ・手順

このセッションでは、Agent 365（管理センターの Agents タブ）と Microsoft Defender の画面を使ったデモが 2 つ行われています。テナントは Caldova（発話の綴りのまま）という名前です。音声からは画面の細部まで確認できないため、語られた範囲だけを書きます。

### 6.1 デモ 1：全体像から、リスクのある 1 つのインスタンスを止めるまで

狙いは、リアルタイムに、広いエージェント資産の見え方から 1 つのエージェントインスタンスまで絞り込み、停止まで行う流れの紹介です。

1. 管理センター（発話では「Microsoft Admin Center」）を開き、Agents タブを展開する。Overview タブに、複数のプラットフォームで動いているエージェントのレジストリ数が表示される
2. 「All agents」を開く。上部のバーに、エージェントの総数、リスクのあるエージェント、所有者のいないエージェント、管理されていないエージェント、ローカルエージェントの数が出る
3. 多くのエージェントがマシン上でローカルに動くため、Shadow AI を開く。ここでは 35 種類を超えるローカルエージェントの種類が分類されており、Claude Desktop、OpenAI Codex、GitHub Copilot CLI などが例として挙がった。管理対象の環境で動いているインスタンス数も確認できる
4. 組織内で広く使われているという Claude Desktop を選び、Instances をクリックして、動作しているインスタンスを確認する（発話では「三百二十一」などの数が聞こえますが、音声認識の都合で正確な数は確定できません）
5. あるインスタンスのリスクレベルが「高」になっているのを見つけ、開くと、統合されたリスクレベルが「高」と表示される
6. Security タブに切り替えると、インシデントが紐づいている。View All で展開すると、重大度が低いプロンプトインジェクションに始まり、見慣れない場所からのエージェント利用や、機微なデータへのアクセス試行などが重なって、リスクが高く評価されていた
7. Access タブに戻る。管理者のタイプに応じて、エージェント自体をブロックする、Intune 連携でデバイスの状態を非準拠にする、そのエージェントの全サイトまたは特定サイトへのネットワークアクセスを制限する、といった選択肢がある
8. 発表者は「従来型のセキュリティ担当」の立場で、できるだけ厳しくする設定を選び、ブロック、デバイスの非準拠化、ネットワーク制限を併用した。Apply Policies をクリックすると、バックエンドの Entra、Intune、GSA などの製品連携を通してポリシーが適用され、そのインスタンスが環境内で動かないように制限された

### 6.2 デモ 2：IT 管理者からセキュリティ管理者へ、検知から調査・封じ込めまで

「何かが動いていておかしい」という連絡から始まる、実際にありがちな流れの紹介です。IT 管理者の役割から始め、セキュリティ管理者の役割に引き継ぎます。

1. Caldova の管理センターで Agents の Overview を開く。リスクのあるエージェントが表示され、IT 管理者として見ると、高リスクのエージェントが 79 あった
2. All agents の Agents at Risk を開くと、エージェント名と所属プラットフォームが一覧になる。Copilot Studio、Agent Builder のほか、サードパーティや Microsoft Foundry のものもあった
3. その中の customer billing agent（顧客請求エージェント）に 2 つのリスクが付いている。どのツールからのものかを調べると、Microsoft Defender から来た 2 つのリスクシグナルだった。Defender はセキュリティチームの領域なので、セキュリティチームを呼び出して調査を依頼する
4. セキュリティチームが Defender ポータルを開き、この Customer Billing Agent を探して、Incidents and Alerts タブで、優先度が低いものから非常に重大なものまでのインシデントを確認する
5. 最も重大なインシデントから開く。説明には、エージェントが開始したツール呼び出しを、Microsoft Defender がリアルタイムでブロックしたとある。ツールは Power Platform の Send Email コネクタだった
6. インシデントのページを開くと、このエージェントに対して執拗なジェイルブレイクの試みが行われ、その結果ツールが完全にブロックされていた。エージェントを利用したのは特定のユーザーだったため、そのユーザーを調べる
7. そのユーザーは MFA（多要素認証）が無効になっており、それでもパスワードの変更は行われていた。発表者は「ユーザー侵害の疑いが強い」と判断し、Defender ポータルから「ユーザー侵害」を確定した。ユーザーの状態が 「侵害済み」（compromised）に変わる
8. さらにエージェントの活動と詳細を調べるため、AI agent details のフローを使い、必要な ID を取得する
9. アドバンストハンティングで、同じ ID を使い、AI agents の情報テーブルに対してクエリを実行すると、このエージェントのメタデータがすべて返る
10. その中で、このエージェントが請求用の MCP サーバーにつながっていることに初めて気づく。同じサーバーを使う他のエージェントがないかを調べるため、コミュニティクエリを探すと、請求用 MCP に紐づくエージェントの数を見つけるものがあり、メーカーの資格情報を使っているものを特定できた
11. 結果は 5 件で、そのうち 1 件は元のエージェントのため除外し、**追加で 4 つのエージェントが MCP サーバーに接続され、メーカーの資格情報を使っている**とわかった。以降は、残る 4 つのエージェントの是正に取り組める

> 補足：デモ 2 の最後は「残り 4 つを緩和に取りかかれる」というところまでで、4 つのエージェントに実際に何かの対処を行う場面は語られていません。

## 7. 注意点・発表者の気付き

- **エージェントの数だけでは役に立たない**：何ができ、どんな条件で動き、取り消しがどれだけ難しいかを問う必要があります。
- **所有者のいないエージェントは、調査も是正も難しい**：Microsoft の IT とセキュリティの部門でも、ほぼ毎日取り組んでいる課題だと語られました。
- **ローカルエージェントの可視化は社内でも課題**：会場に尋ねたところ、大半の人が許可しており、全インスタンスを見えていると自信を持つ手は一部でした。Vivek 氏は、同じ課題が社内にもあると述べています。
- **万能の停止スイッチは存在しない**：プラットフォームごとに使える制御が異なるため、どの制御が効くか、どれだけ速く効くかを、事前にテストします。
- **環境間のガードレールの漏れ**：ある環境で適用したガードレールが、別の環境で抜けることが露出につながる例として挙げられました。
- **低リスクのエージェントに過剰な摩擦を与えない**：リスクの高いものには厳しく、低いものには負担をかけない、という調整が求められます。
- **デモ 2 で見えた点**：ユーザーの MFA が無効で、パスワードが変更されていた、というのは、ユーザー侵害を疑う手がかりでした。また、調査の途中で、エージェントが請求用 MCP サーバーにつながっていることが初めて分かり、同じ構成の他のエージェントの存在に気づいています。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。なお、このセッションでは顧客事例や成果の数値は紹介されておらず、紹介されたのは Microsoft 社内の実運用に基づく内容です。

- **1 か所で全体を把握できる**：複数のプラットフォームのエージェントを 1 つのレジストリで確認でき、所有者のいないもの、管理されていないもの、ローカルのものも集計されます。
- **ローカルエージェントの発見**：Shadow AI として 35 種類を超えるローカルエージェントの種類を分類し、インスタンス数を確認できます。
- **リスクに基づく絞り込みと対処**：リスクレベルと、紐づくインシデントを見て、ブロック、デバイスの非準拠化、ネットワーク制限を選べます。ポリシーは Entra、Intune、GSA などの製品連携で適用されます。
- **IT 管理者とセキュリティ管理者の連携**：IT 管理者の画面で見つけたリスクを、Defender、アドバンストハンティングへと引き継いで調査できます。
- **社内の運用から得た枠組みを参考にできる**：北極星、運用原則、リスクの 5 要素、シフトレフトなどの考え方を、導入の進め方として使えます。
- **テレメトリの活用**：Agent 365 のシグナルを、イベント集約や分析に使っている既存のツールへ流せます。

## 9. まとめ

Microsoft の Office of the CISO は、100 万を超えるエージェントという規模を前提に、「すべてのエージェントを発見し、リスクの文脈を与え、ガードレールと封じ込めで統制する」ことを目標にしています。Agent 365 は、その社内の運用要件から生まれた可観測性のプラットフォームで、IT 管理者、セキュリティ管理者、メーカーが、共通のシグナルとポリシーの上でそれぞれの役割を果たします。

実践の要点は 2 つの流れに集約されました。可視化では、資産を発見し、所有者を決め、アクセスと関係性を把握し、リスクで優先順位を付けます。対応では、ガバナンスを左へ寄せ、デプロイ前にガードレールを置き、封じ込めを設計し、プレイブックとして運用します。

最後の呼びかけは、エージェントはすでに組織の中にいるので、見えているか、統制できているか、信頼できているかを問い、次の一歩を踏み出すことでした。脅威インテリジェンスとガイダンスについては Security Insider のリンクを、1 つの制御プレーンですべてのエージェントを保護する方法については A365 のクイックリンクを見るよう案内され、「AI は速く動く。セキュリティはもっと速く動かそう」という言葉で結ばれました。
