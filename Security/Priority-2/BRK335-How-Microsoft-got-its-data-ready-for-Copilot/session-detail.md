# BRK335 How Microsoft got its data ready for Copilot

## 1. はじめに

このセッションは、Microsoft 自身のテナント（Microsoft 社内の Microsoft 365 環境）を運用している 2 名が、社内データを Microsoft 365 Copilot やエージェントに使えるようにするまでの取り組みを、自社が「最初の顧客」の立場で語ったものです。テーマは、Microsoft Purview の分類・秘密度ラベル・データ損失防止（DLP）ポリシーを中心に、AI に渡してよいデータと渡してはいけないデータをどう整理したかです。

結論は一貫しています。ラベルは従業員が迷わないほど単純にする、コンテナー（サイトやチーム）のラベルからファイルのラベルを自動で決める、そして従業員を信頼したうえで検証する、という 3 点です。後半の質疑応答では、ラベルの設計、ゲストや外部委託先のアカウント、既定ラベルを強化したときに起きた混乱など、現場で起きやすい論点が語られています。

## 3. 何に関する発表か

背景として、来場者や展示ブースの顧客から「AI、Copilot、エージェントに向けてデータをどう整えればよいか」という質問が絶えないことが挙げられています。そこで、実際にテナントを管理している 2 名が社内の進め方を紹介する構成になりました。

流れは次のとおりです。

1. 2 つのチーム（テナント運用とセキュリティ）の連携と、Microsoft テナントの規模
2. Copilot 展開に踏み切る判断と、既定値（インテリジェントな既定）による土台づくり
3. ラベルの設計、失敗談、従業員の文化と教育
4. Copilot から内容を隠す 3 つの制御と、セキュリティと生産性のバランス
5. 会議、エージェントへの対応
6. 組織が持ち帰れる要点のまとめと、小規模組織向けの助言
7. 質疑応答

## 4. 発表者が伝えたいメッセージ

最大のメッセージは、**AI が基盤となるデータリスクの大半を生んだわけではない**という点です。登壇者は、AI の前から持っていたデータ保護の土台が、AI の普及とともに成熟し続けていると説明しています。

次に、Microsoft は大半のデータを AI から隠していません。AI に取り込ませたほうが効果が高いためで、本当に守るべきものだけを絞って制御しています。制限しすぎれば AI の回答の質が落ち、従業員はラベルを外したり付け間違えたりして回避します。緩すぎれば過剰共有が起きます。この両方を避けるのが目標だと語られています。

そしてもう一つが「信頼して検証する」（Trust but verify）という考え方です。従業員は最初で最後の防御線であり、データの重要性を最もよく知るのは所有者です。IT はガードレールを用意して、その後に検証で確かめる役割だとされています。

## 5. 発表内容の詳細

### 5.1 2 つのチームの連携

David Johnson 氏はテナントのアーキテクチャーと統制を担い、Michael Bambrick 氏は Purview のデータ保護の適用を担います。AI の時代にはチームの壁が壁でなくなり、テナント運用チームとセキュリティチームが組まなければ成功しない、という認識です。CISO の組織がポリシーを決め、テナント側がそれを実装可能か確認してテナントを構成します。

セキュリティ側は、ポリシーを実装するだけでなく、DSPM（データセキュリティ態勢管理）と Purview の Activity Explorer で出力されるシグナルを見て、実装が有効に働いているか、業務の妨げになっていないかを確認していると述べています。なお 2 名が直接会ったのは今回が初めてで、普段はリモートで協力しているとのことです。

### 5.2 Microsoft テナントの規模

規模として次の数値が挙げられました。

| 項目 | 数値 |
|---|---|
| SharePoint サイト | 約 70 万 |
| ファイル容量（SharePoint と OneDrive のうちファイルのみ） | 40 ペタバイト |
| SharePoint と OneDrive 上のファイル数 | 66 億件 |
| Purview ポリシー | 約 140 件（標準提供のセットを利用し、独自に 40〜50 件を追加。360 という数字も挙がりましたが、内訳は発話では確認できません） |

Loop のサイトなどは別に存在する、とも補足されています。従業員がサイトやチームを自由に作成できる「従業員のエンパワーメント」が原則で、そのうえで適切なガードレール、ライフサイクル管理、データの衛生管理、データ保護を入れる方針です。ポリシーの大半は標準の機能で賄っており、Microsoft は「自分たち自身の顧客」として運用していると説明しています。

### 5.3 Copilot 展開の準備ができたと判断するまで

最初に行うのは、データリスクの把握です。会社として本当に重要で厳重に守るべきデータと、全社に公開されていても問題のないデータを区別します。そのデータの状態を Purview と SharePoint Advanced Management で確認し、リスクがある場所を特定したうえで、準備ができたグループから段階的（波状）に Copilot を展開しました。

### 5.4 インテリジェントな既定値による土台づくり

従業員が生成するデータの多くは、機密情報の種類で検出できるものではありません。例えば、あるプロジェクトチームが進める秘密のプロジェクトがその例です。その価値を判断できるのは本人たちです。

そこで Microsoft は次のように設計しています。

- 従業員はファイル単位でなくプロジェクト単位で考えるため、**SharePoint サイトやチームといった「場所」にラベルを付けてもらう**。
- サイトに「極秘・社内限定」（Highly Confidential, Internal Only）のラベルを付けると、ドキュメントライブラリの既定ラベルがコンテナーのラベルから自動的に決まる。
- 従業員がそのサイトにファイルを置く、または編集すると、最初からラベルが付く。
- OneDrive でも同様の仕組みを使い、既定は権利保護付きの「機密・社内限定」（Confidential, Internal Only）ラベル。テナントの境界を出ない。

ここで注意点も語られています。販売担当者が OneDrive にあるファイルを顧客に共有しても開けない、ということが実際に起きます。社内限定で、権利保護によりテナントに固定されているため仕様どおりの動作ですが、従業員への教育が必要だとされています。

また、ラベル付けの規模は画面で示されており、ラベルは複雑である必要はないが有効でなければならない、というのが学びです。

### 5.5 ラベル設計の教訓と失敗談

教訓は「選択肢を増やしすぎない」ことです。ラベルのグループだけでなく、従業員に見えるラベルポリシーの数も絞っています。例として、社内限定、正社員向け（スライドの表記は音声認識の都合で確定できません）、LinkedIn 限定やゲーム部門限定のような事業部門向けのラベルが挙がりました。従業員には自分に関係するラベルだけが見え、各事業部門は必要に応じて自部門限定にコンテンツを固定できます。

失敗談として、委員会で設計してしまう問題が挙げられています。法務、セキュリティ、利用体験の各チームがそれぞれ階層や法的定義を求め、結果として従業員には分かりにくくなります。過去には HBI（事業への影響大）というラベルがありましたが、「自分の仕事はすべて重要だ」と考える人が付けてしまいます。ラベルの言葉は、その言葉どおりの意味であるべきだというのが結論です。

ラベルは進化し続けるものでもあります。3〜4 年前の構成のままではなく、登壇者はセッションの直前の週末にもラベルを 1 つ変更したと述べています。事業の変化に応じて分類やラベルの要件も変わるためです。セキュリティ管理者が業務プロセスの妨げになることは避けたい、というのがセキュリティ側の立場です。

### 5.6 従業員の文化と教育

ラベルが重要な理由として、Copilot が情報を抽出して、利用者の作業コンテキストに沿った合成回答を作る点が挙げられました。従業員は元の Word や PowerPoint を見ないまま、ある回答だけを目にします。その回答の扱い方を知っている必要があります。

実例として、同僚の勤続 25 周年のために Copilot で詩を作ったところ、その人が関わったプロジェクトが盛り込まれ、その中に進行中の機密プロジェクトがあったため、詩に「極秘・社内限定」のラベルが付いて返ってきたという話が紹介されました（発話では、冗談めかしつつ実際に起きたと説明）。ラベルが付いて返ったことで Copilot は正しく動いていますが、従業員がそれを正しく扱えるかが問題です。極秘の詩をコーヒーショップで読み上げてはいけません。

そのため、シールドのアイコン（色分けされ、意味と取り扱い方を示す）を確認するよう教えています。毎年の「ビジネス行動基準」（データの扱いを含む）と年次のセキュリティトレーニングで、社内外での協業の仕方を訓練しています。人は情報を話し、写真も撮れるため、取り扱いの教育が欠かせないという説明です。Purview の導入段階によっては、ラベルを付けることに慣れてもらうこと自体がトレーニングの大きな部分になるとも述べています。

> 注意：AI に入れる情報と、AI の出力を使った後の行動の両方に気を配る必要がある、というのが司会のまとめです。

### 5.7 Copilot から内容を隠す 3 つの制御と、バランスの取り方

スライドには、Copilot にコンテンツを渡さないための 3 つの制御が示されました。登壇者が強調したのは、スライドの上部にある「Microsoft は大半のデータを AI から隠していない」という点です。AI に取り込ませたほうが効果的だからで、スマートに行うことが目的です。

3 つの制御は次のとおりです。

1. **抽出を禁止するフラグ付きのラベル**：このラベルを付けると、Copilot はコンテンツを抽出して使えません。年次トレーニングでも周知しています。
2. **Copilot 向けの DLP**：全体の中で見つけさせたくないデータ（特別なプロジェクトや財務など）にガードレールを設定します。
3. **Restricted Content Discovery（制限付きコンテンツ検出）**：同様に制限を設けます。

制限をかけるほど AI や Copilot の効果は下がることがあるため、対象を絞って適用します。AI とのやり取りは Agent 365 と DSPM で観察しています。テナントの規模上、すべてを事前に見張ることはできないので、傾向を見る運用です。ラベルの付け間違いや、同じ内容を探す複数のプロンプトが回答を得られずにいる状況などから、人が AI に苛立っている様子が分かるとのことです。

資格情報（パスワード）は、横展開（ラテラルムーブメント）を許す「クラウンジュエル（最重要資産）」の 1 つとされています。登壇者は、他人のメールを確認したいからとパスワードを尋ねたら返ってくる、という事態が最悪の例だと述べました。AI の取り組み初期にはそれに近い状況もあったそうで、Purview の基盤を正しく整える理由になっています。

Copilot はラベルを尊重し、回答にもラベルを表示し、そこから生成されるもの（例えば新しい PowerPoint）にもラベルを継承します。グラウンディングのブロックが設定されていればブロックされます。なお、CEO が進めている合併・買収のラベル付きデータを Copilot に使わせない、という運用は受け入れられないだろうと述べています。

セキュリティと生産性のバランスについては、次の説明がありました。

- DLP の仕事は、うまくいけば誰も気付かず、失敗すれば全員が気付くものです。進捗は良好だが、終着点には達しておらず、永遠に達しないという認識です。
- 制限しすぎると、従業員は回避策を探し、ラベルを付け間違える、ラベルを外す、保護を外すといった行動に出ます。緩すぎると、全員がデータを共有できる過剰共有になり、保護が付かないままになります。
- 新しいラベルの展開時には、XDR と Activity Explorer で適用状況を見ます。適用後すぐにラベルを下げる動きが増えていれば、有効でない兆候です。

失敗談として、最初のラベルは厳しすぎ、コピー＆ペーストをブロックしていました。マネージャーが Word で部下の人事評価を書く場面では、ラベルが付くとツールへ貼り付けられず、二度手間になるか、ラベルを下げて回避することになります。この経験を通じて、テナント運用（利用体験）とセキュリティの間には健全な緊張関係が必要だと述べています。

### 5.8 会議と成果物のラベル

登壇者は、意思決定の多くが会議で行われ、会議が情報の大きな発生源になっている点を強調しました。会議にもラベルが付き、ラベルの意味は同じで、ポリシーは少し異なります（ロビーから入れる人、ロビーでブロックする人、録画できる人など）。

極秘ファイルを一般の会議で共有すると、主催者に「ラベルが誤っている可能性がある、会議のラベルを修正してください」と促します。「極秘・社内限定」の会議はテナント限定になり、Teams のロビーポリシーも組織内のみで、ロビーから抜け出すことも不可になります。この 1 年で新しくなった点として、会議から生成されるファイル（録画、文字起こし、会議メモ、Loop）が会議のラベルを自動で引き継ぎます。そのためテナント外へ持ち出せず、持ち出すにはラベルを下げる必要があり、その時点で把握できます。SharePoint と同じく、会議も設計上、同じ階層の中に収まるようにしている、という説明です。

### 5.9 エージェントの増加への対応

司会から、Microsoft の環境では M365 のエージェント数が 15 倍に、大企業では 18 倍に増えたという数字が紹介されました。リスクの新しい面が生まれるなかで、信頼しつつエージェントを認めるにはどうするか、という質問に対する回答は次のとおりです。

- エージェント数は増減しており、積極的な整理を行っています。別のセッション（登壇者の上司が実施）で、孤立したエージェントを整理して台帳を管理可能に保つ方法が話されたとのことです。
- すべてのエージェントのリスクは同じではありません。データの衛生管理ができていれば、Copilot 内で作る Agent Builder のエージェントは、整備したラベルをすべて継承します。ブロックされたものはブロックされ、社内限定のものから生成される PowerPoint も社内限定になります。従業員が自分でできる以上のことはしないため、この種類のエージェントにはリスクがないと述べています。SharePoint のエージェントも同様です。
- アプリに近いエージェントでは、リスクが高まります。例として Foundry のプロ開発者向けエージェントでは、データが取り出され、テナントの外に出る可能性があります。データへのアクセスをいつ許可するか、どう審査するかを決めます。リスクスコアリングを行い、テナント外へ出るデータ量を把握し、書き込みを行うエージェントはリスクレビューを実施する、と説明しています。
- この点は、当日の Agent 365 のセッション（見逃した場合は録画の視聴を推奨）にも詳しいとのことです。

### 5.10 組織が持ち帰る要点のまとめ

David Johnson 氏は、次の方針を示しました。

1. **データの境界はテナント**：従業員のセルフサービスを認める。ゲストの招待、チームやサイトの作成を許し、Purview が全体を監視し、監査を整える。グループ（セキュリティグループを含む）にもラベルを付けられるようになった。
2. **ラベルを単純に**：従業員中心で直感的に。言葉はその意味どおりに。
3. **インテリジェントな既定値**：従業員がすべてのファイルにラベルを付けるわけではなく、DLP や機密情報の種類がすべてを網羅するわけでもないため、既定で権利保護を付け、テナント境界に固定する。SharePoint サイトとチームには必ずラベルを付ける。OneNote がラベルに対応したとき、3 週間でテナント内のすべてのアクティブなノートブックにラベルが付いた。
4. **教育**：データの扱い方を従業員に教える。
5. **検証**：DSPM、DLP ポリシー、パスワードの検出などで間違いを監視する。ライフサイクル管理を行い、誰も管理していないサイトやエージェントは削除する（家の掃除）。
6. **SharePoint Advanced Management で過剰共有を検出**：Microsoft の規則では、極秘は「知る必要がある人だけ」を意味する。大きなセキュリティグループに共有して良いわけがない。そこで、極秘のサイトやファイルが 5,000 人超に共有されているものをレポートで一覧化し、従業員に共有の縮小（バーンダウン）を実施してもらう。

Michael Bambrick 氏は、全部で 10 のステップがあるが詳細は繰り返さない、とした上で、次の点を補足しました。

- 取り組みは旅であり、すべての組織で同じにはならない。自社で機能したやり方が他社で合うとは限らない。
- 進み具合は組織ごとに異なり、今の位置にいてよい。
- AI が基盤となるデータリスクの大半を生んだわけではない。AI の前から持っていた土台が、AI の普及とともに成熟している。
- ユーザーはセキュリティの連鎖の起点。所有者の内容は管理者には分からず、ラベルが正しく付いていれば漏れたと分かる程度なので、エンドユーザーを支援する。ユーザーが採用し、日々の業務に組み込むことが成功の指標になる。

参考情報として、aka.ms/AIgovernance が案内されました。

### 5.11 小規模組織への助言

Microsoft のスケールで見ても、ツールセットのおかげで規模の運用が可能になっていると述べています。次の数字が挙がりました。

- イベントは毎秒約 390 件
- 従業員は 33 万人
- セキュリティ側の運用は 5 名とプログラムマネージャー 1 名

これを可能にしているのは、Purview の自動化、XDR、Sentinel、Agent 365 や DSPM による傾向の監視です。ほかのチームも関与しますが、データの流出を見ているセキュリティ側はこの体制だと説明しています。テナント側は、Power BI、SharePoint、Copilot など多くの中核サービスを管理するため、より大きなチームです。いずれの立場も、シンプルにして正しく進める、従業員にものを作らせる、データの衛生を保つ、標準機能を有効にする、という助言です。ラベルと Purview の面では、シンプルであるほど効果的です。

### 5.12 質疑応答

**質問 1： 詩の例で、意図せず極秘が付いてしまった場合に、どうやってラベルを下げるか。**
回答：IT 側で、完全に制限するラベルを決めておけば、そもそも回答に出てきません。抽出さえしないようにもできます。また、業務側で Copilot に再度プロンプトを出し、その中の極秘部分を尋ねられます。Copilot の回答の下部には使われたすべてのソースが表示され、各ソースのラベルも分かります。チャット全体のラベルも合わせて付き、上部にシールドが出ます。その上で、特定のソースを除外して再計算するよう指示できます。

**質問 2： 25 年来の習慣で、ファイルエクスプローラーやネットワークドライブの割り当て、手作業のコピーでバージョン管理をしており、誤ったラベルのコピーが所有者不在で残る。どう対処するか。**
回答：Microsoft ではすべての登録デバイスで OneDrive をドキュメントフォルダーにマップしており、デバイス上の作業は OneDrive に対して行われるため、中核のラベルポリシーが働きます。販売担当者が PDF をデバイスに落とすと、OneDrive のドキュメント既定ラベルが付き、共有しても権利保護により開けない（仕様）というケースも起きています。ファイル共有からファイルを利用者が取り出すと OneDrive に保存され、よく使うものから自然に移行します。さらに、90 日や 120 日触れていないドキュメントは、保持ポリシーなどでアーカイブし、電子情報開示などの法的目的のため保管します。エンドポイント DLP もあります。

**質問 3： 既定のラベル以外に、エージェントがドキュメントを読んでラベルを付けるか。人が上書きできるか。**
回答：エージェントはラベルを設定していません。ラベルを読み、継承して、作成物にラベルを付けるだけです。権限と承認があればエージェントにラベルを設定させることは可能ですが、現在は行っていません。SharePoint と SharePoint の AI が追加の推奨を出すとどうなるか、という実験はしているとのことです。ラベルは既定値を除いて人の判断で、DLP が何かを検出した場合は既定のまま残りません。例えば、ファイルが「機密・社内限定」でもパスワードが見つかればそのラベルのままではいられません。

**質問 4： 外部の人が社内アカウントを持つ場合、社内限定の利用をどう扱うか。**
回答：ゲストはテナントに招待でき、ベンダーにはアカウントを発行します（従業員の「V-」から始まるアカウント）。これらは Microsoft.com テナント上の ID として存在します。一部のラベルはテナントメンバー全員が復号でき、別のラベルは正社員のみが復号できるなど、雇用形態で区別します。従業員が使う中核ラベルはゲストに対応していないので、ゲストを含める場合は、保護を外すか、ゲストを意図的に含めるラベルを使う必要があります。

**質問 5： ラベル体系には機密度とオーディエンスの 2 軸があるが、ユーザーにはどう優先して説明するか。**
回答：まず機密度を考えます。スターバックスで極秘の話をしてはいけない、という程度の「どれくらい秘密か」です。質問者は、非ビジネス、パブリック、一般、機密、極秘といった機密度の軸と、Microsoft の正社員向けなどのオーディエンスの軸があると指摘していました（ラベル名は質問者の発話によります）。回答では、オーディエンスは「最大到達範囲」で、そのデータがどこまで広がり得るかを示します。権限は今日の時点で誰がアクセスできるかを決め、ラベルはそのデータがどこまで行けるかを決める、という説明です。公開データには、インターネットに出せるものなので保護はありません。セキュリティ側は、リスクはリーダーシップやプロの視点で、オーディエンスは「この人たちに共有したい」という人の視点で教えており、ケースバイケースだと述べました。ラベルのダウングレードや変更が多ければ、定着していないと判断します。

**質問 6： 6 月ごろ、Microsoft が既定ですべてのドキュメントを機密に分類し、質問者側を担当する Microsoft のアカウントチームが、翌日からマーケティング PDF を共有できなくなり、ラベルを付け直す必要があった。何が起きたのか。**
回答：テナント運用と CISO の判断で、すべての OneDrive にドキュメントライブラリの既定を設定しました（6 月より前だったかもしれないが、質問者が気付いたのがその時期という見方）。従業員にはトレーニングで周知していましたが、習慣のため、デスクトップの PDF を共有して開けないという失敗が最初に起きます。ただし 1〜2 回で気付きます。従業員は外部共有するなら下位のラベルに付け替える必要があります。基礎を整えることで、誤って過剰共有しても、デバイスに置き忘れても、仕様として機能しません。セキュリティ側は、既定で暗号化されたラベルを付けた際に説明責任も生じ、外部に送るためにラベルを下げると監査可能なイベントが発生して追跡できると補足しました。苦情があったことは認め、文化とトレーニングが十分に届いていなかった学びだと述べています。

質疑の終了後、登壇者は、Microsoft の IT 部門の取り組みを aka.ms/InsideTrack で読めると案内しました。残った質問については、2 名が同日 18 時から 19 時まで階下のハブにいるので気軽に立ち寄ってほしいとも述べています。

## 6. デモ・手順

このセッションでは画面を使ったデモは行われていません。スライドを参照しながらの対話形式です。手順として紹介された内容は、5.10 の整理（データの境界の設定から過剰共有の縮小まで）が該当します。

## 7. 注意点・発表者の気付き

- ラベルは単純にし、言葉をその意味どおりにします。HBI のような曖昧なラベルは、誰もが自分の仕事を重要と考えるため機能しませんでした。
- 初期のラベルはコピー＆ペーストを禁止していたため、マネージャーが人事評価を作成する際に二度手間になり、ラベルを下げる回避行動を招きました。
- 既定の権利保護ラベルにより、OneDrive 上のファイルを顧客に共有しても開けません。仕様ですが、従業員教育が必要です。
- 制限が強すぎるとラベルの付け間違い、ラベルの削除、保護の削除が起きます。緩すぎると過剰共有になります。
- Copilot の回答は、元のドキュメントを見ずに受け取られます。回答のラベルと取り扱い（シールド）の教育が欠かせません。
- 新しいラベルを展開した直後は、Activity Explorer と XDR で、ラベルがすぐに下げられていないかを確認します。
- 登壇者の取り組みは、あくまで Microsoft のケースです。同じ手順が他の組織で通用するとは限らないと述べています。

## 8. 利用者にとっての利点

- Microsoft の規模（SharePoint サイト約 70 万、ファイル 66 億件、従業員 33 万人）でも、Purview の自動化や標準機能により、セキュリティ側 5 名とプログラムマネージャー 1 名で運用できているという実例が示されました。
- Purview のポリシーは、標準提供のセットを中心に使い、独自追加は 40〜50 件でまかなえています。
- コンテナーのラベルを継承させることで、従業員の負担を増やさずに、ファイル、会議の成果物、Copilot の生成物、Agent Builder のエージェントまでラベルが引き継がれます。
- OneNote のラベル対応では、3 週間でテナント内のすべてのアクティブなノートブックにラベルが付きました。
- 大半のデータを AI から隠さず、必要な部分に絞って制御することで、Copilot の回答の質を保つ方針が示されました。

## 9. まとめ

Microsoft は、従業員が自由に作成できる環境を保ちつつ、サイトとチームにラベルを必須とし、既定で権利保護とテナント境界の固定を行う構成で、Copilot とエージェントの利用に備えました。AI が生んだリスクではなく、AI 以前のデータ保護の土台を成熟させる取り組みだと位置付けられています。

ラベルは単純にし、従業員を教育し、DSPM、Activity Explorer、DLP、SharePoint Advanced Management で検証します。制限は必要な部分に絞り、制限しすぎず緩すぎないバランスを継続して調整します。ラベルは今後も変わり続けるもので、終着点はないという点も、登壇者が繰り返し述べた前提です。追加情報は aka.ms/AIgovernance と aka.ms/InsideTrack で案内されました。
