# BRK339 Local agents are here. Can you find and secure them?

## 1. はじめに

このセッションは、従業員の端末上で動く「ローカルエージェント」を、発見し、権限を絞り、問題が起きたときに調査するまでの流れを、1 人の架空の財務担当者の四半期決算作業にそってデモで見せる内容です。ローカルエージェントとは、従業員の認証済み環境（ファイル、アプリ、既存のセッション、資格情報、ツール、ネットワーク接続）の中で、本人と並んで動くエージェントを指します。

発表の答えは一つの製品ではなく、複数の層を組み合わせることです。ID、ネットワーク、データ、エンドポイント、実行時の各層を Agent 365 で束ね、IT 管理者、ID 管理者、SOC（セキュリティ運用）管理者の 3 つの視点で、同じエージェントについて見ていきます。核となる考え方は、**危険なエージェントだけを抑え込み、従業員本人は止めない**ことです。

デモは 3 回あります。Microsoft 365 管理センターと Intune での発見と封じ込め、Microsoft Entra での動的な権限付与と条件付きアクセス、Defender XDR での調査です。

## 5. 発表内容の詳細

### 5.1 ローカルエージェントと 3 つのセキュリティコンテキスト

ローカルエージェントは、従業員の認証済み環境の中で、ファイル、アプリ、既存のセッション、資格情報、ツール、ネットワーク接続のそばで動きます。ユーザーとして動くなら、かなり広い範囲に届き得ます。有用性と、セキュリティ境界の重要性は表裏一体です。

扱う文脈は次の 3 つで、互いに作用しますが、置き換えはできません。区別しておくことで、境界を設定し、行動を特定でき、作業を続けられます。

| コンテキスト | 見る点 |
|---|---|
| エージェント | 何に責任を持つか。なぜ使われているか。誰が責任者か |
| ユーザー | 何にログインしているか。ブラウザー、インストール済みアプリ、ネットワークドライブ、端末上ですでに持っている認証トークン |
| 端末と実行時 | 動いているプロセス、そのプロセスが使えるファイルとツール、実行中に使われる資格情報とネットワーク経路 |

管理された端末は制御を適用する場所になりますが、管理が「正しいエージェントに正しい境界」を定義できていなければなりません。

### 5.2 多層の封じ込め

ローカルエージェントには多層の封じ込めが必要だとして、次の層が紹介されました。

| 層 | 製品 | 役割 |
|---|---|---|
| ID | Microsoft Entra | エージェントの活動とユーザーの活動を区別する。アクセスをタスクに合わせて絞り、リスクの変化に応じて権限を調整する |
| ネットワーク | Entra Global Secure Access | エージェントが端末の外へ接続する方法を制限する。許可する接続の権限も管理し、リスクが変われば動的に調整する |
| データ | Microsoft Purview | 機密データを識別して保護する。例えば、機密でないデータはサードパーティーのマーケティング用データベースへ送ってよくても、顧客の個人情報（PII）は送らない、といった扱い |
| エンドポイント | Microsoft Intune | 端末上のポリシーを設定し、境界を決める。Windows と Microsoft execution container（MXC）と連携して、ローカルでの実行とアクセスできる範囲を決める |
| 実行時 | Microsoft Defender | ツール呼び出し、プロンプト、応答を見て、悪意あるものが紛れ込んでいないか、エージェントに意図しないことをさせていないか、データを汚染していないかを確認する |
| 観測 | Microsoft Agent 365 | 上の 6 つの層を囲み、エージェントについての文脈を 1 か所に集約して、実行と許可の判断材料を提供する |

発表では、人間なら異変に気付ける場面でも、エージェントでは気付けないことがある、と補足されています。

### 5.3 シナリオ：財務アナリストの Melissa

Melissa は財務アナリストで、四半期決算の作業をしています。請求書を複数のデータベースと突き合わせる手作業が多く、IT が承認したローカルエージェントを使って効率化します。ローカルエージェントは、端末上のファイルやネットワークドライブ、適切なアクセスがあれば外部のデータの場所にも届きます。

作業自体は正当で、エージェントも IT の承認済みです。課題は、IT が「彼女がそのエージェントを使っていること」「その端末が彼女のものであること」「どのツールを使っているか」を把握する必要がある点です。そこで、機密性の高い決算作業でエージェントが使ってよいリソースを明示します。

3 種類の管理者の視点で見ていきます。

1. IT 管理者：環境にどんなエージェントがいるかを発見し、リスクを評価し、封じ込めの境界を適用する。
2. ID 管理者：エージェントが使えるものを統制し、リスクの変化に応じて保護する。
3. SOC 管理者：エージェントの行動を調査し、問題が起きたときに適切に対応する。

### 5.4 IT 管理者の視点：発見、評価、封じ込め

Melissa はまず、ノートパソコン内の四半期末のファイルを探し、欠けている請求書にフラグを付けようとします。IT 承認済みのローカルエージェントをインストールして使い始める場面です。

**ID が自動で付く仕組み**：Melissa がエージェントを初めて実行すると、Defender for Endpoint がそれを認識し、その文脈が Microsoft Entra に渡って、エージェント ID が割り当てられます。既知のローカルエージェントが、Entra のエージェント ID とともに Agent 365 のレジストリーに入ります。この対応済みの経路では、Defender for Endpoint があれば、追加の設定なしに発見が自動で行われます。管理者は、そのエージェントが誰の端末で動いているか（Melissa の端末番号や、財務部門に所属すること）を確認できます。また、Entra Global Secure Access を通じて、エージェントが使っている MCP サーバーなどのツール呼び出しをネットワーク越しに観測できます。

> ご参考：エージェントの処理を開始して別の作業をしていることが多いため、Entra ID でエージェントの動作と Melissa 本人の動作を区別できることが最も重要だと説明されています。

デモの内容は 6 章に記載します。続いて、デモで使われた要素を整理した図の説明がありました。

1. Defender がローカルエージェントと実行を発見した。
2. Microsoft Entra がエージェント ID を割り当てた。

4. 3 種類のリスクを集約した動的エージェントリスクが、他のエージェント情報と並んで自動で表示された。
5. Intune で、エージェントが MXC コンテナー内で動くことを保証するポリシーを作り、アクセスできる範囲と禁止する範囲を決めた。

すべてを支えて、全体を成立させているのはエージェント ID だと述べられています。

### 5.5 ID 管理者の視点：ローカルエージェントの統制と保護

Doreen が、Erica のデモで示された「ローカルエージェントが Microsoft Entra で固有の ID を持つ」ことが大きな転換だと述べました。これまでのローカルエージェントは、ユーザー自身の ID と権限でそのまま動き、エージェントの活動はユーザーの活動と区別できませんでした。Entra が自動で個別の ID を割り当てることで、ユーザーとは独立にエージェントを統制・保護できるようになります。

Melissa は次に、四半期末の売上ダッシュボードを作り、チームでレビューします。そのためにエージェントは Snowflake の財務データへアクセスする必要がありますが、Melissa のすべてのアクセスを引き継ぐべきではありません。ID 管理者の目標は 2 つで、(1) エージェントに必要な分だけ、必要な間だけのアクセスを与えること、(2) エージェントのリスクを示す証拠が変わるのに合わせて、アクセスを動的に調整することです。

そのための新しい 3 つの制御は次のとおりです。

| 制御 | 内容 |
|---|---|
| 適正化：Microsoft Entra ID Governance の動的権限 | エージェントはアクセス権ゼロから始まり、ユーザーの常設権限は持たない。作業の中で、タスクに必要な最小権限が期間限定で動的に割り当てられる。ユーザーの権限が上限で、それを超えない |
| 評価：動的エージェントリスク | Microsoft Defender や Microsoft Purview などの複数のセンサーからのシグナルを組み合わせ、エージェントに 1 つの統一リスクスコアを付ける。スコアはユーザーではなくエージェント ID に紐づく |
| 適応：Microsoft Entra 条件付きアクセスの動的制御 | 継続的な条件付きアクセス。トークン要求時だけでなく、データアクセス経路上の毎回のリクエストで継続的に評価する。リスクが変われば、特定の操作の制限、人間の承認の要求、エージェントの完全ブロックなどを行える。Microsoft と他社の両方のリソースに対応する |

### 5.6 まとめの図：エージェント ID を起点にした流れ

Doreen は、デモ後に全体を次のように整理しました。

- すべての制御はエージェント自身の ID に固定される。Entra は、Microsoft 製に限らずあらゆるエージェントに、エージェント ID を自動で割り当てる。デモで使った Claude Desktop にも固有の ID を与えて、Microsoft 自社のエージェントと同じように統制・保護できた。
- Microsoft Entra ID Governance が、タスクの間だけ範囲を絞った期間限定のアクセスを付与する。
- 端末上では Defender や Purview などのセンサーが活動を監視する。Defender は悪意のあるプロンプトを検出し、Purview は機密データの漏洩を防ぐ。シグナルは 1 つの動的エージェントリスクに集約される。
- 条件付きアクセスの動的制御が、そのリスクに応じて、データアクセス経路上でエージェントの操作を制限、またはブロックする。

提供状況は次のとおりです。3 つの機能はすべて現時点で利用できる段階で、動的権限と条件付きアクセスの動的制御は限定プレビュー、動的エージェントリスクはプレビューです。

### 5.7 SOC 管理者の視点：調査と対応

Swaroop が、前のデモの最後に Claude が高リスクのまま残っている点から話を始めました。エージェント向けの保護は機能しましたが、侵害の証拠があるため、セキュリティチームの仕事はここで終わりません。悪意のあるプロンプトが端末から機密データを持ち出そうとしたため、SOC にとってインシデントになっています。SOC には 2 つの作業があります。何が起きたか、データの漏えいがあったかという証拠の確認と、適切な是正手順の決定、そして適切ならアクセスの復旧です。

デモの注目点は、ユーザーの Melissa が侵害されたと自動で決めつけずに、エージェントを調べる点です。デモの内容は 6 章にあります。

是正（リメディエーション）の選択肢としては、次の例が挙がりました。ローカルエージェントについては現在いくつかの選択肢があり、今後さらに追加されます。

1. 保護は機能したので、リスクを却下して、エージェントが作業を再開できるようにする。
2. エージェントが恒久的に汚染または侵害されているとみなし、高リスクのままにしておく。
3. 最も深刻な例として、Melissa がインターネットから未承認のエージェントをダウンロードして使っていた場合、組織内で見たくないものとして、その使用を全面的にブロックする。このとき端末を非準拠としてマークできる。

全体の循環は次のとおりです。ローカルエージェントの活動があるたびに、エンドポイントで Defender と Purview が監視し、そのアラートが動的エージェントリスクの計算に使われると同時に XDR にも流れ、同じデータが帰属されます。その上で条件付きアクセスと権限の適正化が回り、是正後にアクセスを復旧できます。

提供状況：Defender の、ローカルエージェント向けの実行時保護は、プレビューだったものが一般提供になりました。Purview の DLP 保護はプレビューです。侵害や差し迫ったリスクを確認する場所となる、ローカルエージェント向けの Entra ID Protection もプレビューです。

### 5.8 Melissa の振り返り

IT が必要としていたことは、エージェントを特定して正しいアクセスを持たせること、エージェントの活動とリスクを（実際にエージェントが作業しているときは）Melissa ではなくエージェントに帰属させること、最小権限から積み上げ、ユーザーが持つ権限を無条件に与えないこと、そして是正とアクセスの復旧をエージェントだけに対して行い、Melissa のアクセスは完全に別にすることです。

## 6. デモ・手順

デモは 3 回あり、いずれも Melissa のシナリオです。画面の細部は音声からは確認できず、以下は語られた範囲です。

### 6.1 デモ 1：IT 管理者（Microsoft 365 管理センターと Intune）

1. Microsoft 365 管理センターで、エージェントの全体像を開く。「すべてのエージェント」ビューのエージェントレジストリーには、実行中のあらゆるエージェントが並ぶ。Microsoft のエージェントのほか、コネクターを設定していれば AWS や Google のエージェントも表示され、クラウドとローカルの両方が見える。
2. 新しい「ローカル」のナビゲーション項目を開き、ローカルエージェントを確認する。
3. Melissa が使っている Claude Code を選ぶ。Agent 365 によると、Caldova という社名の環境で検出されており（社名は音声認識の都合で表記が確定できません）、検出は初めて実行して使ったときに起きる（インストール時ではない）。
4. 「インスタンス」を開くと、端末で Claude Code を使っている 2 台のマシンが見える。新しいユーザーが初めて実行するたびにインスタンスが増え、各インスタンスにリスクレベルがある。1 台は高リスクなので、そこから見る。
5. このエージェントには、IT 管理者が手作業しなくても Entra のエージェント ID がすでに付いている。この ID を使えば、アクセスとリソースを制御できる。
6. エージェントが今触れるデータとツールを確認する。追加の制御がない状態で、3 つのツールに触れられる。リモートの MCP サーバー 1 つと、ローカルの 2 つで、合計 3 つの MCP サーバーが見える。
7. 「セキュリティ」を開き、リスクの初期評価を見る。Ignite で発表された新しい動的エージェントリスクスコアは、Defender などほかの層のリスクスコアを 1 つに統合する。実行時リスクと露出リスクが合算され、全体で高リスクになっている。リスクの算出元となった Defender のケースも関連づけて見える。
8. 活動の画面で、全インスタンスにわたる動作とトラフィックを見る。
9. 「アクセス」で、Claude Code を使うすべての人にポリシーを適用できる。財務部門のように Melissa の部門だけにも、組織の全端末にも適用できる。選択肢は次のとおり。(a) エージェントの使用自体をブロックする。ただし今回は IT 承認済みなので不要。(b) ネットワークの詳細へのアクセスの可否を決める。(c) エージェント実行中は条件付きアクセスで端末を非準拠にする。(d) Microsoft execution container と Intune ポリシーで、端末上の封じ込められた境界の中でのみ実行するよう強制する。
10. (d) のチェックを入れて適用すれば進むが、先に裏側の Intune ポリシーを見るため、Microsoft Intune のポータルへ切り替える。
11. 新しい「エンドポイントセキュリティ」のナビゲーション項目を開き、新しい「エージェントコンテナー」の項目を選ぶ。すでにエージェント封じ込めポリシーが作成済み。編集を開く。
12. ポリシー名、説明、対象の端末の種類が表示される。ここで、端末上で動くすべてのエージェントに適用するか、選択した特定のエージェントに適用するかを選べる。今回はすべてのエージェントに適用する。
13. Entra のネットワークアクセスをオン・オフする設定がある。ローカルのリソースだけで動かしたい場合は、ここで選ぶ。さらに、テストモードや追加のテレメトリー付きで実行する設定もあり、ポリシーが作業に対して正しく設定されているか確認できる。
14. 封じ込めの境界のポリシーでは、次のように設定した。ローカル端末上のエージェント自身のワークスペースは読み書きできる。財務部門のネットワークドライブの情報は読める。OneDrive と、端末にローカル同期された OneDrive のファイルへのアクセスはブロックする（デモの会社では機密性の高いデータを OneDrive に置くのが標準のため）。
15. 保存する。これでエージェントは封じ込められた。

デモのあとの説明では、Intune ポリシーで今日実施できるのは上記の範囲で、開発者向けには MXC でさらに多くの境界の種類を設定できると述べています。この Intune ポリシーは限定プレビューで、1 月ごろにより広く提供される見込み（発話では「できれば」）とのことです。

### 6.2 デモ 2：ID 管理者（動的権限と条件付きアクセス）

**事前設定（ID 管理者）**

1. Microsoft Entra 管理センターの ID Governance にある「動的権限」を開く。エージェントのタスクは動的なので、必要なアクセスをすべて事前に予測できない。少なすぎるとタスクが壊れ、多すぎるとリスクになる。
2. 対象リソースとして Snowflake（重要な業務データがある場所）の動的権限を設定している。

**Melissa の操作（適正化：権限）**

3. Melissa が Claude Desktop に、Snowflake にある承認済み CRM 顧客の Q3 売上ダッシュボードの作成を依頼する。
4. Claude が作業を始めると、Entra の動的権限が働く。売上データの読み取りに追加のアクセスが必要と判断し、Entra へアクセスを要求する承認を Melissa に求める。
5. Melissa が承認すると、データを読めるロールの候補が表示される。Melissa は Snowflake Finance reader ロールを選ぶ。
6. Entra が Melissa のプロンプトの意図から解決した、提案されたアクセス要求が表示される。このロールは Claude のエージェント ID に付与され、限られた期間だけ有効。
7. Melissa が内容を確認して承認する。アクセスが動的に与えられ、Claude は承認済みデータへの期限付きの読み取り専用アクセスを得る。Snowflake への広いアクセスではない。ダッシュボードが作られた。
8. 次に Melissa が、Snowflake の制限付きデータ（制限された顧客とコミッションの詳細）を見るよう依頼する。今度は、より高い権限の Sales intelligence reader ロールが必要になり、Entra が確認を求め、Melissa が確認する。
9. 要求は自動で数秒のうちに拒否される。レビューは不要で、Melissa 自身にそのデータへのアクセス権がないため。ユーザーの権限が上限になる。

**事前設定（条件付きアクセス）**

10. Entra 管理センターの条件付きアクセスで、2 つのルールを設定した。
    - 中リスク：動的エージェントリスクが中のとき、機微な操作を制限する。エージェントを完全には止めず、範囲を絞る。読み取りは動くが、書き込みのような機微な操作はブロックされる。
    - 高リスク：リスクが高いとき、すべての操作をブロックする。
11. これらのルールはエージェント ID を対象にし、ユーザー ID とは別。エージェントのリスクが上がっても、そのエージェントと作業するユーザーのアクセスは変わらない。

**Melissa の操作（適応：リスク）**

12. Melissa が Claude に、Q3 クローズのレビュー担当者用に Entra でセキュリティグループを新規作成するよう依頼する。Claude は Microsoft Graph 経由で成功する。画面には、Claude の動的エージェントリスクが裏側でリアルタイムに変化する様子を示す図が追加されている。今は緑（低リスク）で、書き込み操作が成功した。
13. Melissa がチーム全員をグループに追加するため、ネットで見つけた自動化の手順を貼り付ける。プロンプトには、本人が気付いていない悪意のある隠し指示が入っている。Microsoft Defender が端末上でこれを検出し、LLM が動く前にプロンプトをブロックする。これが最初のリスクシグナルで、Claude の動的エージェントリスクが中に上がる。リスクは Melissa ではなく Claude の ID に紐づく。
14. 中リスクの状態で、Melissa がグループのメンバー一覧の表示と、バックアップのレビュー担当者グループの作成を依頼する。メンバーの読み取りは成功するが、グループの作成は条件付きアクセスにより拒否される。低リスクのときは Microsoft Graph 経由で作成できたが、中リスクでは機微な書き込み操作が制限される。
15. Melissa がレビュー担当者にメールを書くよう依頼するが、プロンプトに顧客の社会保障番号が含まれている。Microsoft Purview が機密データを認識し、エージェントへの漏洩を防ぐ。先ほどの Defender のブロックに続く 2 つ目のシグナルで、両者によって動的エージェントリスクが高に上がる。
16. 高リスクの状態で、Melissa が Snowflake へ再度クエリして、地域別の Q3 売上を要約するよう依頼する。今回は Snowflake へのリクエストがブロックされる。動的権限で読み取りアクセスが付与済みでも、高リスクでは管理者のポリシーによりすべての操作がブロックされるため。権限はエージェントに何ができるかを決め、動的エージェントリスクと条件付きアクセスの動的制御が、今その権限を使ってよいかを決める。
17. Melissa 自身は、ブラウザーを開いて自分のユーザー ID で Snowflake にサインインし、同じ地域別 Q3 売上を依頼する。クエリは成功し、データを得られた。Claude はブロックされても、Melissa のアクセスはまったく変わらない。

デモの最後に、Claude は高リスクのままになっています。

### 6.3 デモ 3：SOC 管理者（Defender XDR）

1. SOC 管理者として、XDR のポータルでケースを開く。Defender XDR が、すべてのアラートを取り込んで、適切なインシデントにまとめている。
2. インシデントの 1 つを開く。左側には、悪意のあるエージェントに関する Purview と Defender のアラートが並ぶ。テストを何度か実施したため、先ほどの 2 件より多い。
3. 右側には、インシデントまたは攻撃グラフがあり、Melissa、その端末、エージェントの関係が示される。それぞれのエンティティの活動を独立して見られる。
4. 最後のほうで見た Defender のインシデントを開く。Defender がこのプロンプトインジェクション攻撃を検出したこと、起きた内容の詳細が見える。モデルが動く前に検出している。
5. 「詳細を表示」を押して下へスクロールすると、Doreen が示した、Melissa が誤って Claude に貼り付けたプロンプトそのものが見える。
6. これらの情報はすべて、Melissa ではなくエージェントに帰属されている。

高度なハンティングクエリなど、さらに進んだ操作もできますが、時間の都合で扱われていません。

## 7. 注意点・発表者の気付き

- ローカルエージェントは本人の認証済み環境で動くため、何もしなければ本人の権限がそのままエージェントに渡ります。以前は活動もユーザーと区別できませんでした。
- 検出のタイミングは、インストール時ではなく、ユーザーが初めて実行したときです。
- エージェント ID による自動発見は、対応済みの経路で、Defender for Endpoint があることが前提です。
- 動的権限では、ユーザーの権限が上限です。ユーザーに権限がないものは、エージェントも取得できません。
- 高リスクでは、付与済みの権限があってもすべてブロックされます。権限と、今使ってよいかどうかは別の判断です。
- リスクはエージェントの ID に紐づくため、エージェントを止めても本人の作業は続けられます。
- 現在の Intune ポリシーで設定できるのは、デモで示した範囲です。限定プレビューで、広い提供は 1 月ごろの見込みです。
- 提供状況：動的権限と条件付きアクセスの動的制御は限定プレビュー、動的エージェントリスクはプレビュー、Defender の実行時保護は一般提供、Purview の DLP 保護と ローカルエージェント向けの Entra ID Protection はプレビューです。
- 高度なハンティングは時間の都合で扱われていません。

## 8. 利用者にとっての利点

- エージェントをユーザーと区別して発見・統制できるため、従業員の生産性を保ちながら、エージェントだけを制限できます。
- Microsoft のエージェントに限らず、Claude Desktop や Claude Code のような他社のエージェントにも、同様に ID を与えて統制できます（デモで示されたとおり）。
- 必要な分だけ、必要な間だけのアクセスにすることで、広すぎる権限による事故と、少なすぎてタスクが壊れる問題の両方を避けられます。
- 複数のセンサーのシグナルが 1 つのリスクスコアになり、同じデータが XDR にも流れるため、SOC は同じ証拠を使って調査できます。
- 是正はエージェントに限定され、Melissa のアクセスと分けて復旧できます。

## 9. まとめ

ローカルエージェントは、従業員の認証済み環境の中で本人と並んで動くため、生産性の利点とリスクの両方を持ちます。発表では、Defender for Endpoint による自動発見と Entra のエージェント ID を出発点に、Agent 365 での可視化、Intune による封じ込め、Entra ID Governance の動的権限、動的エージェントリスク、条件付きアクセスの動的制御、そして Defender XDR での調査という流れを、3 回のデモで示しました。

要点は、アクセスは一度きりの付与ではなく、エージェントは誰か、タスクに何が必要か、今どれだけ危険かという 3 点で、リクエストごとに再評価されることです。リスクはエージェントの ID に紐づくため、危険なエージェントだけを抑え込み、従業員は止めずに済みます。そして、セキュリティはひとつの魔法の制御ではなく、各層の組み合わせで成り立つというのが発表者の結論です。
