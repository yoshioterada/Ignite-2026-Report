## 5. 発表内容の詳細

### 5.1 参加方法と練習問題

参加者は QR コードを読み取り、画面に表示されたアドレスで参加します。ホイールを回すと名前が割り当てられ、その名前が勝者の確認に使われます。個人戦で、投票が始まったら色のついた図形を選びます。

練習問題は「みなさんは今、業務でエージェントをどう使っているか」でした。選択肢の趣旨は、まだ使っていない、要約や簡単な質問、調査や推奨される対応の補助、エージェントに自動で操作させる、です。22 人が参加し、基本的な要約、調査への利用、そして「エージェントに自由にやらせている」人も少数いる結果でした。

### 5.2 Trey Research の背景

Trey Research は、他社が頼る設計・製造のパートナーです。手術器具のセンサー、電気自動車のバッテリーコントローラー、おもちゃのロボットの回路基板など、製品の内部の部品を設計・製造します。従業員は 8,000 人で、世界各地に拠点があり、他社向けの数十のプログラムを動かしていて、それぞれが他社の未発表製品を抱えています。

業務は Microsoft の生産性ツールとセキュリティツールで動いています。Microsoft Defender が脅威を見つけ、Microsoft Purview がデータを分類して保護を助け、Microsoft Entra がアクセス権を管理します。一つのセキュリティチームがこれらをすべて担当し、長年それで足りていました。

昨年、Microsoft Copilot を展開しました。3 か月分の試験データが認証申請書の最初の下書きになり、数日かかっていた作業が午後だけで終わりました。その後、AI エージェントが個人の主導で次々に現れました。自分のレビューのチェックリストを自動化した技術者、取引先の資料を要約するツール、試験結果を顧客が求める形式に変えるスクリプトなどです。どれも無謀でも悪意でもなく、本当に役に立つものでした。

### 5.3 Keystone と取締役会の問い

8 か月前、Trey は「Project Keystone」を始めました。セキュリティ・ガバナンスチームが運営する、AI エージェントの承認プロセスです。60 を超えるエージェントが承認され、それぞれが個人に紐づいていました。ところが、事業部門に何を動かしているか尋ねると、報告されたエージェントは 140 で、Keystone の一覧の 2 倍を超えていました。エージェントの利用が、追跡の仕組みより速く増えていました。

同じころ、他社でエージェントが想定外に広いアクセス権を持っていた事例や、誰も確認していない判断をエージェントが実行した事例が報じられました。取締役会は次の会議で CISO に 1 つの質問をしました。「私たちは次の見出しになるのか」です。

CISO の Oscar Ward 氏は 20 年のキャリアを持ちますが、正直な答えは「分からない」でした。エージェントの一覧はあっても、取締役会に説明できる根拠がありませんでした。翌朝、チームに問いを持ち帰ります。登場人物は次のとおりです。

| 役割 | 人物 |
| --- | --- |
| CISO | Oscar Ward |
| セキュリティ調査（6 年） | Nia Clark |
| ID の責任者 | Andre（Andre Coleman） |

チームはすでに Microsoft Agent 365 を使い始めており、午前中には、答えではなく「まず理解すべき問い」の一覧ができました。最初は「何が動いていて、誰が責任者か」です。

### 5.4 判断 1：どのエージェントが危険か（可視化）

調査では、更新された数を知るために社内調査を 3 週間かけ、140 のエージェントが見つかりました。ただし調査は「何を作ったか」を尋ねるもので、「自分は何も作っていない。インストールしたものは該当するのか」と答えた人もいて、誰も追跡していませんでした。金曜の取締役会までに、何が動いていてどこから手を打つかを知る必要があります。

選択問題：金曜までに、どのエージェントが Trey を危険にさらしているかを Nia はどう調べるか。

- 事業部門の調査を更新する
- 未登録のクラウドエージェントとその動作を見る
- クラウドとデスクトップのエージェントをまとめて見る
- 既存の Defender と Purview のログから調べる

多数派は「クラウドとデスクトップのエージェントをまとめて見る」で、Nia も同じ判断をしました。Agent 365 で登録済みのエージェントと、Defender が見つけたデスクトップのエージェントを合わせて確認すると、作業上の数は 2,000 になり、調査で漏れていたものも含まれました（数字は聞こえたとおりで、音声認識の都合で確定できません）。ただし数は出発点にすぎません。

次に、利用できるリスクのシグナルで対象を絞り、各エージェントが何に届くか、誰が依存しているかを調べました。目立ったのは、機密性の高い顧客の設計にアクセスできるのに、現在の所有者がいない有効なエージェントです。作成した技術者は Keystone の手順どおり自分を所有者として記録していましたが、更新は手作業で、その人が退職しても誰も記録を直さず、引き継ぎもありませんでした。3 つのチームが毎週使っています。業務が頼っているのに、責任者がいないエージェントでした。

### 5.5 判断 2：所有者のいないエージェントをどうするか

選択問題：3 つのチームが使うが、誰も所有していないエージェントに Nia はどう対処するか。チームが頼る機能を損なわずに責任を戻すには、どうするか。

- エージェントを止めて作り直す
- 責任を持つスポンサーを付ける
- Keystone の手順に戻り、新しい所有者を記録する
- IT に任せ、すべてのエージェントを自分たちのチェックリストで扱う

多数派は「責任を持つスポンサーを付ける」で、Nia も同じでした。Microsoft Entra と Agent 365 で、エージェントに名前のあるスポンサーを割り当てました。Entra ID ガバナンスの組み込みワークフローを設定し、そのスポンサーが退職した場合は上司が引き継ぎ、関係者に通知されるようにしました。責任者が決まったあと、Agent 365 を Microsoft Entra と Purview と組み合わせて、Keystone のポリシーを実際に適用しました。エージェントのアクセスを管理し、その業務に必要なデータ保護と保持のポリシーを適用しています。**人向けに作ったルールを、エージェントにも当てはめた**形です。

### 5.6 判断 3：デスクトップのエージェントは何に届くか

Nia の一覧には、デスクトップのエージェントも含まれていました。上位の一つは、Aiden Hunt の PC で動くローカルのエージェントで、調査で漏れていたものです。Aiden は組み込みソフトウェアの開発者で、デスクトップ用のエージェント OpenClaw を自分でインストールし、顧客の要件定義書を読ませて、実装前に設計案を検討していました。作業は速くなり、周囲にも話していました。申告を求められたことはなく、禁止されたこともありません。

Aiden は 3 つの顧客を担当しています。Trey と各顧客の契約では、その顧客の設計はその顧客のプロジェクトにしか使えず、他の作業を支えてはなりません。このエージェントは Aiden のアカウントで動いています。Nia は、どのファイルとサービスを実際に使え、どこに接続しているかを確かめる必要があります。

選択問題：エージェントが顧客データに届く範囲を、Nia はどう評価するか。

- Aiden と一緒に設定をすべて確認する
- 管理対象のデバイスすべてで OpenClaw をブロックする
- 検出とネットワークの活動を使い、セキュリティの観点でエージェントの動きを見る
- Aiden の権限を、そのとき取り組む作業だけに絞る

多数派は、エージェントのセキュリティに関する検出結果を見る、でした。Nia も同じです。Microsoft Defender が Aiden の PC で動く OpenClaw を見つけ、Shadow AI（シャドー AI）の画面で、他に検出したエージェントとともに Nia に示しました。Defender は、導入を Aiden のアカウントに結びつけ、活動を調べるための文脈を提供しました。Nia は、設定されたアクセスと、利用できる活動記録を確認しました。さらに Microsoft Entra Internet Access を使うと、エージェントから選んだサイトへの通信を止めつつ、Aiden 本人のアクセスは維持できます。ツールを取り上げずに、境界を引く手段になりました。

### 5.7 判断 4：危険な振る舞いに気づけるか

次は、エージェントの振る舞いが危険になったことをどう知るかです。ID の担当 Andre Coleman は、不審なサインインを調べていて、購買エージェントへのアクセス記録を見つけます。このエージェントは、エンジニアリング担当 VP の George Tindall が、取引先の確認、購買依頼の準備、必要な部品の発注に使っています。不審な動きは George のアカウントに関するもので、それ自体は George の通常業務です。Andre が懸念するのは、George のアカウントを使って、George が承認していない操作をエージェントに行わせた可能性です。Andre は証拠を Nia に渡し、エージェントの活動を調べます。

選択問題：このエージェントのリスクを Nia と Andre はどう評価するか。

- George と一緒に、本人が覚えているすべての依頼を確認する
- エージェントの脅威の検出、活動、セキュリティの状態を確認する
- George のアカウントの活動をすべて追跡する
- アプリケーションのチームに調べさせる

多数派は、エージェントのセキュリティ記録を調べる、でした。Nia と Andre も同じです。Agent 365 を使い、Microsoft Defender でアカウントの活動と並べて購買エージェントを調査しました。Defender は購買エージェントに関わる不審な活動を検出していました。証拠を見ると、エージェントの機能や接続を探る依頼と、呼び出されたツールの記録がありました。これらは George が通常使う購買業務とは合いませんでした。エージェントのセキュリティ状態（権限と接続されたツール）を見て、どの購買機能が影響を受けうるかを把握できました。危険な使われ方の証拠と、業務への潜在的な影響の見通しが得られたことになります。

### 5.8 判断 5：購買リスクの封じ込め

Nia はアプリのチームにエージェントとツールのレビューを依頼し、Andre は George のアカウントを保護します。アプリのチームは、危険な活動の全容をまだ確定していません。悪意のある依頼が購買の発注になる前に、レビューを続けながらリスクを抑える必要があります。

選択問題：購買リスクをどう封じ込めるか。不正な購入を止めつつ、業務への影響を最小限にしたい。

- エージェントの購買アクセスを制限する
- エージェントを全員に対してブロックする
- George のアカウントのアクセスだけを止める
- アプリのチームにエージェントをすぐ再設定させる

多数派は、購買アクセスの制限でした。Nia と Andre も同じです。Agent 365 の知見から、エージェントを作り直さずにアクセスを制限できました。アクセスと権限を確認して、検索ごとに別のコネクタを使っていることが分かり、Andre は Microsoft Entra の条件付きアクセスポリシーで、このエージェントによる発注コネクタへのアクセスをブロックしました。制限が効いているかは、Microsoft Entra のサインイン結果とエージェントの記録された活動で確認し、ポリシーの変更は Entra の監査ログに記録されました。制限を確認できたあと、取引先の検索は再開できました。アプリのチームは、George の業務への影響を抑えつつ、調査結果の検討に時間を使えるようになりました。

### 5.9 Trey が成功した理由

チームは Agent 365 でエージェントを管理・統制し、すでに人とデータを守っていた Microsoft のセキュリティツールの上に構築しました。AI のリスクを観察して制御し、対応の優先度付けに Agent 365 を、責任の確立に Microsoft Entra を使いました。Aiden は仕事に必要なアクセスを保ち、デスクトップのエージェントには境界が設定されました。データ漏えいや過剰共有を防ぐため、各エージェントのデータの使い方を、Microsoft Purview の証拠で説明できるようになりました（AI のコンプライアンスを支える）。Microsoft Defender は AI の脅威の検出を助け、Microsoft Entra のアクセス制御は、有用な仕事を続けたまま危険なアクセスをブロックしました。Oscar は取締役会に答えを持ち帰れました。

### 5.10 持ち帰ってほしいこと

Agent 365 は、AI のための可観測性のプラットフォームで、ユーザー、アプリ、デバイスにすでに適用している管理の規律を、エージェントにも持ち込みます。観点は 4 つに整理されました。

| 観点 | 問い |
| --- | --- |
| 管理 | どのエージェントが動いているか。管理外のものを含む |
| ガバナンス | 誰が責任者で、エージェントは何にアクセスし、何ができるか |
| セキュリティ | データをどう使っているか。危険な振る舞いに気づけるか。どう封じ込めるか |
| ビジネス価値 | エージェントがどんな有用な仕事をし、いくらかかるか |

最初の一歩として、事業の重要なワークフローを一つ選び、その事業オーナー、IT とセキュリティの責任者を集めて、可視化、責任、ガードレールを検討するよう勧めています。Agent 365 はこの進め方の実践を助けます。

## 6. デモ・手順

製品の画面を操作するデモは行われていません。進行の中心は、ストーリーの朗読と投票です。結果の説明では、Agent 365、Defender、Entra、Purview の働きが語られていますが、実際の画面操作は示されていません（録音からは確認できません）。

シナリオで語られた対応の流れは、次のとおりです。

1. Agent 365 で登録済みのエージェントと、Defender が見つけたデスクトップのエージェントをまとめて確認する
2. リスクのシグナルで絞り込み、所有者のいない有効なエージェントを見つける
3. Entra と Agent 365 でスポンサーを割り当て、退職時に上司が引き継ぐ Entra ID ガバナンスのワークフローを設定する
4. Defender の検出と Shadow AI の画面で、デスクトップのエージェントのアクセスと活動を確認し、Entra Internet Access で選んだサイトへの通信を止める
5. 不審な活動のあった購買エージェントを Defender で調べ、Entra の条件付きアクセスで発注コネクタへのアクセスをブロックし、サインイン結果と監査ログで確認する

## 7. 注意点・発表者の気付き

- 調査アンケートだけでは実態を捉えられず、140 件の報告に対し、Agent 365 と Defender の確認では実際の数は大きく上回った
- 承認の記録（Keystone）が手作業の更新だと、所有者の退職で責任者が不在になる
- 禁止ではなく、境界を引く方法で、使いたい人の仕事を止めずに対応できる
- 不審なアカウントの活動は、アカウントだけでなく、そのアカウントが使うエージェントも調べる必要がある
- エージェントの再構築ではなく、アクセスの制限で、調査中も業務を続けられる
- Trey Research と登場人物は物語の設定として語られます。実在の事例かどうかは発話では明示されていません。数字も物語の中のものです

## 8. 利用者にとっての利点

発表で語られた効果は、物語の中のものです。

- 調査で漏れていたエージェントを含めて、全体像を把握できる
- 所有者のいないエージェントに、名前のあるスポンサーと引き継ぎのワークフローを置ける
- 業務を止めずに、デスクトップのエージェントや購買エージェントのアクセスを制限できる
- 人向けに信頼している既存のセキュリティ統制を、エージェントにも延長して使える

## 9. まとめ

AI エージェントが急速に増えると、調査アンケートや承認の一覧だけでは、何が動いているかを答えられません。Trey Research の物語は、Agent 365 で全体を可視化し、Entra で責任者を決め、Defender と Purview で活動とデータの使われ方を確認し、条件付きアクセスで危険なアクセスだけを止める流れを示しました。

持ち帰る点は、エージェントの利用を見える化し、責任者を明確にし、一貫したガードレールを適用することです。まず重要なワークフローを一つ選び、事業オーナー、IT、セキュリティの責任者と一緒に始めるよう呼びかけて、セッションは終わりました。
