# THRSP1136 Create endpoint resilience: The missing layer in business continuity

## 1. はじめに

インフラ、アプリケーション、データについては事業継続計画を立てていても、ユーザーが実際に触れる端末（エンドポイント）が計画から抜け落ちている組織は少なくありません。このセッションは IGEL Technology の登壇者が、この抜けを「エンドポイント復旧のギャップ」と呼び、その埋め方を紹介するものです。

話の中心は、Windows 端末に並べて導入する IGEL OS への切り替えです。Windows が使えなくなっても約 3 分で業務を再開でき、侵害された可能性のある Windows 領域はフォレンジック調査（証拠保全を前提とした原因調査）のために残せる、という仕組みです。後半では、管理コンソールから端末を一斉に切り替える「緊急モード（Emergency mode）」のデモも行われました。

## 5. 発表内容の詳細

### 5.1 エンドポイント復旧のギャップ

登壇者は、レジリエンス（回復力）の計画がインフラ、アプリ、データを対象にしていて、エンドポイント自体が抜けやすいと説明しています。完全な分散環境では端末が地理的に散らばっているため、物理的に手を入れることが難しくなります。

攻撃の起点もエンドポイントです。侵害経路はユーザーの操作の有無にかかわらず端末側に多いと述べ、ランサムウェアとマルウェアに加えて、更新に起因する障害も挙げました。数年前にセキュリティツールの更新が原因で起きた障害がその例です。さらに、洪水、火災、光ファイバーの切断といった災害まで含めた、災害復旧全体の連続した問題として捉えています。

発表で挙げられた数値は次のとおりです。

| 項目 | 数値 |
|---|---|
| インシデント前の水準まで大規模に復旧するのに 100 日超かかった組織 | 76% |
| 攻撃のうちエンドポイントを起点とするもの | 90% |
| マルウェア検出の増加 | 3 倍 |

登壇者は 76% の数値について「やや控えめな数字」と述べ、同様の障害のニュースは毎週のように出ていると付け加えました。数値の出典は発話では確認できません。

### 5.2 再イメージ化が簡単ではない理由

「全端末を再イメージ化して元に戻せばよい」という考えに対して、登壇者は 2 つの反論を挙げています。

1 つ目は、サイバー保険です。保険会社に復旧費用を支払ってもらうには、いきなり再イメージ化はできません。インシデント対応の一環として、フォレンジック分析を経る必要があります。影響範囲と侵入経路を特定し、その穴をふさいで端末にパッチを当てたと示さなければ、再イメージ化した直後に再感染が起きる恐れがあります。

2 つ目は、所要時間です。1 台の再イメージ化に 1〜4 時間かかるという声があり、登壇者はこれでも楽観的だと見ています。5 万台で 1〜4 時間で済むなら話を聞きたい、と述べました。世間の認識は「3 日以内に戻せる」程度ですが、登壇者はその数字にも疑問を示しています。仮に 3 日だとしても、業種によっては 3 日分の生産性の損失が大きな影響を与えます。医療ではデジタルシステムが使えないと、一貫した品質の医療を提供しにくくなります。

### 5.3 IGEL の考え方: 不変（イミュータブル）なエンドポイント OS

IGEL は、不変なエンドポイント OS と管理基盤を提供するものだと説明されています。不変性が重要なのは、端末が起動するたびに、ハードウェア層から実行中のアプリケーション層まで、信頼の連鎖を検証できるからです。変更や改ざんがあれば端末は起動せず、不正な状態には入りません。再起動するたびに「正常と分かっている状態」に戻ります。仮想化基盤のゴールデンイメージ（基準イメージ）のエンドポイント版、という例えです。

登壇者はこの会場が Microsoft のイベントであることに触れ、聴衆が Windows のエンドポイントを使っていると仮定して話を進めました。Windows は攻撃対象になりやすく、レジリエンスの維持には課題があると述べています。IGEL は Windows を置き換えるのではなく、まず Windows をそのまま使い続けたうえで、障害時のために復旧用のコンポーネントを横に入れる形です。Windows に問題が起きたときに、IGEL 側へ素早く切り替えて事業を継続します。

切り替え後の IGEL OS のデスクトップは、Windows に慣れたユーザー向けに、スタートメニュー、タスクトレイ、デスクトップ上のアプリアイコンを備えています。事務作業、仮想化、端末にネイティブにインストールされたアプリも使えると説明されました。この状態では、次の 2 点が得られます。

- 約 3 分以内に業務へ復帰できる
- Windows のパーティションをフォレンジック調査のために保全できる。調査の時間を確保したうえで、Windows に戻すか、障害中に使った環境にとどまるかを後から判断できる

### 5.4 提供形態: デュアルブートと USB ブート

提供形態は 2 つあり、機能は同じで届け方が異なります。

**デュアルブート**

稼働中の Windows 端末に、専用のソフトウェアをインストールします。Windows は BitLocker で暗号化されていることを想定しています。配布には Intune、SCCM など、普段使っている配布手段をそのまま使います。インストールでは、次の 2 つが行われます。

- IGEL 独自の Windows システムサービスを入れる。このサービスは IGEL の管理コンソールへ状態を報告する
- 端末内に IGEL OS 用のパーティションを切り出し、Windows の隣に置く

このパーティションは意図的に隔離されており、Windows から直接マウントできません。詳細は関心があれば別途説明すると述べるにとどまりました。

**USB ブート**

IGEL OS を専用設計の USB デバイスに載せたものです。過去 10 年以内に作られた x86 の 64 ビット端末なら、どれでも対象になります。差し込んで起動すると、完全に保護され、完全に管理された IGEL のエンドポイントになります。起動すると管理サーバーと通信してポリシーを取得し、適用します。ユーザーが何を使えるか、何にアクセスできるかを管理者が決める方式です。登壇者は、USB ブートは 1 台の端末に固定されず、端末間で持ち運べる点がデュアルブートとの違いだと説明しています。

### 5.5 IGEL OS で動かせるもの

登壇者は、IGEL は 5 年前まではシンクライアントのハードウェアメーカーだったが、現在はソフトウェア企業であり、ハードウェアは作っていないと述べています。IGEL OS で使えるものは次のとおりです。

| 種類 | 内容 |
|---|---|
| 仮想デスクトップとアプリ配信 | 配信基盤を問わず統合済み。AVD、Cloud PC のほか、同様のサービスを提供する他社製品にも対応 |
| ブラウザー | 独自の Chromium 系ブラウザー、Firefox、Edge、Edge for Business、Chrome、Chrome Enterprise。セキュアブラウザーとして Island と Palo Alto の Prisma ブラウザーもネイティブに動作 |
| プログレッシブウェブアプリ（PWA） | 管理者が一元的に配布し、ユーザー操作なしで制御。Office スイートや G suite を PWA として配布できる |
| Linux ベースのアプリ | 管理者がパッケージ化して配布できる。エンドユーザーは自分では入れられない |
| パートナーアプリ | IGEL Ready エコシステムとして 140 のベンダーパートナーが自社コンポーネントを提供。CrowdStrike、Zscaler、Palo Alto など。一覧は app.igel.com で確認できる |
| クライアント側ハイパーバイザー | 仮想マシンのイメージを一元的に保管してエッジへ配布し、制御できる |
| コンテナー | 現在は Docker と Podman が対象。今後は他の形式にも対応予定。コンテナーを一元的に保管、配布、管理できる |

仮想マシンについては、既定でセキュアな OS と同じ原則に従い、不変になると説明されています。Windows 11 から DOS まで何でも不変にでき、再起動のたびに正常な状態へ戻ります。用途によっては少し永続化させることもできます。コンテナーの対応形式の拡張は将来の予定で、現時点で提供済みとして説明されたのは Docker と Podman です。

これらすべてを支えるのが管理層で、端末が世界のどこにあっても大規模に管理し、ポリシー、アプリのプロファイル、設定、ワークフローを定義できます。

### 5.6 緊急モード（Emergency mode）

デュアルブートを設定してあれば、Windows に問題が起きたときに、緊急モードを一元的に有効にできます。管理コンソールから、1 台から企業内の全端末まで、コマンド 1 つで IGEL 側へ切り替えられます。この間、Windows のパーティションは保全されます。

重要なのは、緊急モードの間は Windows をブート順序から外す点です。ユーザーが、侵害された、あるいは作り直しが必要な Windows に戻る手段はありません。緊急モードを解除して Windows をブート順序に戻すまで、再起動しても IGEL が立ち上がります。登壇者は、これによって再起動の際に侵害された Windows が起動してしまう、意図しない再感染を避けられると説明しました。

デモの内容は 6 章で述べます。

### 5.7 製品の構成要素

製品は 3 つの要素から成ります。

1. **IGEL OS**: IGEL 独自設計の Linux ベースの OS。一元管理が組み込まれており、IGEL が保守する
2. **IGEL UMS**: 大規模管理を可能にする管理層。登壇者は、顧客から、管理者 1 人（フルタイム 1 人分）で 2 万台以上のエンドポイントを管理できていると聞いていると述べました。これは他のプラットフォームで管理できる台数の 3〜4 倍に当たるという説明です。この数値は顧客から聞いた話で、発話の範囲では検証された数字として示されてはいません
3. **IGEL App Portal**: パートナーのアプリが置かれ、そこからアクセスできる

登壇者は、この仕組みがインフラ復旧とエンドポイント復旧の橋渡しになり、事業を動かし続けて影響を減らすと主張しています。

### 5.8 ネイティブ利用との組み合わせ

事業継続だけが目的でなければ、IGEL をネイティブに使う選択肢もあります。端末上の Windows を IGEL OS に置き換え、AVD や Cloud PC に接続して Windows の体験を得る方法で、IGEL Adaptive Secure Endpoint Platform がこの用途にあたると説明されました。流れは次の 2 通りが挙げられています。

- ユーザーが IGEL にログインし、Windows 365 クライアントから仮想デスクトップを起動する
- キオスクモード（特定用途専用の画面）にして、ユーザーに IGEL 層を見せず、端末を起動すると自動でリモートの Windows に接続する

後者では、ユーザーは以前と同じように Windows にログインするだけなので、操作方法の再教育が要りません。

提供方法は 2 つで、ネイティブ利用と、事業継続のための Windows 併設です。登壇者は、実際には両方を組み合わせる顧客が多いと述べています。ネイティブ利用に向く業務は IGEL を最初から使い、AVD や Cloud PC に接続します。それに該当しない、まだ Windows が動く端末には事業継続の備えを施す、という使い分けです。ネイティブ利用では、IGEL が最初から不変のエンドポイントなので、継続性の問題自体が起きにくいとも述べました。

## 6. デモ・手順

デモは行われました。登壇者は、緊急モードの動作を管理コンソールで見せています。画面の細部は音声からは確認できません。語られた範囲の流れは次のとおりです。

1. 管理コンソールを表示する。デバイスやアプリを管理する機能が多数ある
2. 委任管理（一部の管理者だけに権限を与える仕組み）の下で、緊急モードを開始する操作に進む。この機能を持たせる管理者は限定したいという前提が語られた
3. 本当に実行するかを、複数回確認される。将来は、複数の鍵（複数人の承認）による起動方式を提供する計画があると述べた（現時点では未提供）
4. 続行を選ぶ。Windows 側では、ユーザーが操作中であれば、ユーザーには閉じられないメッセージが表示される
5. カウントダウンが進む。この時間は設定で変更できる。終わると端末が強制的に再起動し、Windows をブート順序から外して IGEL OS が起動する
6. 切り替え前の画面では Windows、Office 系のアプリ、Edge ブラウザーが動いていた。切り替え後の IGEL 側には、緊急モードに入ったことを知らせるメッセージが表示される。メッセージの内容は自由に設定できる
7. 同じようなデスクトップが使える。緊急モードを終了するまで、以降の再起動でも IGEL に入る

また、5.3 で触れたとおり、登壇者は IGEL OS のデスクトップの画面も見せています。Windows に似た、スタートメニュー、タスクトレイ、デスクトップアイコンのある画面でした。

## 7. 注意点・発表者の気付き

- 再イメージ化は、サイバー保険の観点からはフォレンジック分析の後に行うものです。影響範囲、侵入経路、パッチ適用による再感染防止を示す必要があります
- 緊急モードの間、ユーザーは Windows に戻れません。解除するまでは再起動しても IGEL に入ります。誤った起動を避けるため、操作は複数回の確認があり、委任管理で権限を限定できます
- デュアルブートは、動作する Windows 端末があること、BitLocker による暗号化などが前提です。USB ブートの対象は、過去 10 年以内に作られた x86 の 64 ビット端末です
- 複数人の承認による緊急モード起動は将来の計画です。コンテナー形式の拡張も同じく今後の予定です
- 登壇者は、1 台 1〜4 時間という再イメージ化の想定時間でも、大規模な環境では現実的ではないと見ています

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- Windows に障害が起きても約 3 分で業務へ復帰できる
- Windows のパーティションを保全でき、フォレンジック調査の時間を確保できる。調査後に Windows へ戻すか判断できる
- 管理コンソールから、1 台から全端末まで一斉に切り替えられる。切り替え中は Windows を起動させないため、意図しない再感染を避けられる
- インフラ復旧と並行して端末の復旧を進められる。医療の現場では、医療の継続への影響を減らせる
- 1 人の管理者で 2 万台以上を管理できたという顧客の声がある（他のプラットフォームの 3〜4 倍という説明）
- ネイティブ利用では、キオスクモードにすればユーザーの再教育なしで AVD や Cloud PC を利用できる

## 9. まとめ

エンドポイントは、攻撃の起点であり、復旧計画から抜けやすく、大規模復旧に最も時間と費用がかかる部分です。IGEL は、Windows の横に不変の IGEL OS を置くデュアルブートか、持ち運べる USB ブートで、障害時に約 3 分で業務へ復帰できるようにします。緊急モードなら、管理コンソールから全端末を切り替え、Windows のパーティションを保全したままフォレンジック調査を進められます。さらに、ネイティブ利用と組み合わせて、AVD や Cloud PC への移行と併用することもできます。登壇者は、体験したい人にはブース 1650L でのデモを案内し、来場者向けに、来年 2 月に開催される IGEL の会議があるフォートローダーデールへの旅行が当たる抽選とカスタマイズしたノベルティを用意していると述べました。
