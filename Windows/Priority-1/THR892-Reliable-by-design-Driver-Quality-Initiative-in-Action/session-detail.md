# THR892 Reliable by design: Driver Quality Initiative in Action

## 1. はじめに

このセッションは、Windows の信頼性を高めるために Microsoft がドライバーのエコシステムと進めている Driver Quality Initiative（DQI）のうち、「architecture（アーキテクチャ）」の柱を紹介する 25 分のシアターセッションです。前半は、ドライバーをカーネルの外へ出す、標準のクラスドライバーに寄せる、カーネルに残るものを堅牢化するという 3 つの方針を説明します。後半は、その具体例としてセキュリティ製品向けの **Windows Endpoint Security Platform（WESP）** を取り上げます。

WESP は、今週の Ignite で一般提供（GA）が発表されました。Windows 11 の 25H2 と 26H2 で使えます。IT 管理者が展開や有効化をする必要はなく、セキュリティ製品がこのプラットフォームに対応した時点で効果が届くという説明です。

後半には、WESP Playground というサンプルアプリを使った 3 つのデモがあります。いずれも録画で、ライブデモではありません。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR892](https://ignite.microsoft.com/en-US/sessions/THR892)

## 3. 何に関する発表か

背景として、管理しているすべてのデバイスがエコシステム全体のドライバーに依存していること、そして 1 つのドライバーの障害がデバイス全体を止めうることが挙げられています。DQI は、ユーザーに届く前にリスクを減らし、信頼性を最初から組み込むための取り組みです。

発表の流れは次のとおりです。

1. DQI の 4 つの柱の確認
2. アーキテクチャ戦略：カーネルから出す、標準化する、残るものを堅牢化する
3. WESP：背景、GA の状況、仕組み、できること
4. WESP Playground のデモ（録画）
5. 今後と、聞き手への推奨アクション

## 4. 発表者が伝えたいメッセージ

最も強いメッセージは、**セキュリティと信頼性はトレードオフにする必要がない**という点です。これまでセキュリティ製品は、システム全体を見る、発生した瞬間に介入する、PC の起動時から動く、という 3 つを満たすために、カーネルの中でコードを動かしてきました。ただしカーネルは、1 つの障害がデバイス全体に影響しうる場所です。WESP は、セキュリティ製品のロジックをユーザーモードに置き、カーネルでの作業を Windows が代行する形で、この選択を迫られないようにするものだと説明されています。

また、Kevin 氏は、これは Windows が以前にも用いたパターンの延長だとしています。ファイアウォールが個別にネットワークスタックへ接続していた時代には Windows filtering platform（Windows firewall platform）を、ファイルシステムフィルターが衝突したときには filter manager を、起動直後にマルウェア対策ソフトが入り込む手段が必要になったときには early launch anti-malware を作りました。いずれも、プラットフォームに組み込み、パートナーがその上で製品を作る形です。

## 5. 発表内容の詳細

### 5.1 DQI の 4 つの柱

Mehmet 氏は、前日のブレイクアウトセッションで DQI を取り上げており、詳細は録画で見られると案内したうえで、4 つの柱を簡単に確認しています。

| 柱 | 内容 |
| --- | --- |
| architecture | ドライバーモデルを近代化する |
| trust | ドライバー自体と、提出できる主体に対する基準を引き上げる |
| lifecycle | 最初に作られたときだけでなく、ライフタイムを通じてドライバーを最新に保ち、サービスできるようにする |
| measure | お客様が体験する形で品質を測る |

このセッションでは、カーネルのリスクに最も直接関係する architecture に集中すると説明しています。

### 5.2 アーキテクチャ戦略：3 つの動き

エコシステムと一緒に進めている戦略は、次の 3 つです。

1. **カーネルから出す（shift out of kernel）**：デバイススタックが対応している場合は、ユーザーモードでドライバーを動かす
2. **標準化する**：Microsoft が保守する 1 つのクラスドライバーで、パートナーごとのバリアントを置き換え、共通のサービス経路を持たせる
3. **カーネルに残るものを堅牢化する**：性能などの理由でカーネルに残るものについて、セキュリティと信頼性の基準を上げる

その結果として、サードパーティのカーネルモードのコードが減り、クラッシュや攻撃経路が減り、サービスによる修正が安全になる、と説明しています。

**ユーザーモードへ**

User Mode Driver Framework（UMDF）は、すでに次のようなスタックで使えます。

- センサー
- 指紋などの生体認証
- USB Ethernet
- HID
- ほか多数

ユーザーモードのドライバーに障害が起きても、カーネルとデバイスの他の部分は動き続けます。「それが肝心な点」だと強調しています。さらに、対応するスタックを広げているところです。

- **UMDF の DMA サポート**：PCI で動作する、より多くのスタックにユーザーモードのサポートを広げるもので、性能を犠牲にせずに、はるかに広いハードウェアに対応できる
- **Wi-Fi**：作業中で、2027 年にリリース予定
- **セキュリティソフトウェア**：最大の変化。Windows Endpoint Security Platform はすでに GA（5.3 で詳しく説明）

**クラスドライバーへの標準化**

新しいクラスドライバーを作り、Microsoft が保守するドライバーへ少しずつ移しています。

| 対象 | 状況 |
| --- | --- |
| プリンター | 最も進んでいる例 |
| オーディオ（SoundWire クラスドライバー、SDCA） | 利用可能。Windows の in-box に含まれる予定 |
| I3C | I2C の後継となる新しいバス（bus driver）。古いバリアントを置き換える |
| USB Ethernet | クラスドライバーで更新 |
| カメラ（MIPI クラスドライバー） | 開発中。ほかにもいくつか作業中 |

**カーネルに残るものの堅牢化**

性能などの理由で、すべてのドライバーをユーザーモードに移せるわけではありません。カーネルに残るものについて、次の取り組みを挙げています。

- セキュリティを重視した新しいコンパイラーオプション（悪用されうるコードを減らす）
- ドライバーの分離（driver isolation）：カーネルモードでも、ドライバーがシステム全体を自由にできないようにする
- "user mode accessory APIs"（聞き取った表記のまま）：カーネルモードからユーザーモードのメモリを読み書きするための、専用の安全な関数
- DMA remapping：ダイレクトメモリアクセスを範囲内にとどめ、DMA 攻撃への対策にする

### 5.3 Windows Endpoint Security Platform（WESP）

**背景（Kevin 氏）**

Kevin 氏のチームは、Windows を保護するセキュリティ企業と日々、エンジニア同士で協力しています。セキュリティ製品が Windows に求めるものは 3 つです。

1. システム全体で何が起きているかを見られること
2. 発生した瞬間に介入して止められること
3. 攻撃者がコードを動かす前に、PC の起動時から動けること

長年、この 3 つを満たす方法は、Windows の最も深い部分であるカーネルでセキュリティ製品のコードを動かすことでした。深い可視性と制御が得られる一方、1 つの障害がデバイス全体に影響しうる場所でもあります。

**プラットフォームの考え方と協業**

Windows の顧客が、カーネルモードのドライバーにあまり頼らずに、業界をリードするエンドポイント保護を得られる状態を目指しています。そのために、セキュリティ製品のロジックはユーザーモードで動き、カーネルモードでの処理は Windows が代行するプラットフォームを作りました。リカバリーは、すべての製品に対してプラットフォームに組み込まれています。

2024 年 9 月に、Microsoft の本社へ業界のパートナーを集め、「セキュリティを犠牲にせずに信頼性を高めるには」という共通の目標で動き始めました。以来 2 年間、パートナーと協力して作ってきました。パートナーは要件を共有し、プレビュービルドで検証し、あらゆる段階でフィードバックを返し、共通のお客様を守るために設計を進化させる必要がある箇所も伝えています。

**GA と提供状況**

- Ignite の週に GA を発表。**Windows 11 の 25H2 と 26H2** で利用できる
- お客様が展開するものや、有効にする設定はなく、すでに Windows 11 の一部になっている
- 保護と追加機能は、セキュリティ製品がプラットフォームに対応するにつれて届く
- 最初の製品は **今年のカレンダーイヤー末までに**登場し、**2027 年の上半期**にかけてさらに増える
- Microsoft の Defender も、まったく同じプラットフォームと API の機能の上に作られている

Kevin 氏は、各プロバイダーは自社のロードマップで対応するため、次のことを聞くよう勧めています。

1. このプラットフォームを採用するのか
2. どのシナリオで使うのか
3. 自分の環境でいつ使えるのか

**仕組み：3 つの層**

| 層 | 内容 |
| --- | --- |
| 下の層：Windows | ファイルシステム、プロセス、レジストリ。これらを event providers と呼ぶ。デバイスで何かが起きると、イベントをプラットフォームに上げる |
| 中間：プラットフォーム | Windows が提供する。各イベントを製品のルールと照合し、製品が求めるものを渡す。カーネルは製品に代わって作業を行う |
| 上の層：セキュリティ製品 | 他のアプリと同じようにユーザーモードで動く。プラットフォームに接続し、同じデバイス上で複数が並んで接続することもできる。関心のあるイベントやプロバイダーをプラットフォームに伝えて購読（subscribe）する |

> 注意：プラットフォームが強力なため、使える主体は絞られています。現在は MVI プログラムのセキュリティ企業が対象です。ソフトウェアは Azure Artifact Signing で署名され、Windows が誰が使っているかを正確に把握でき、code integrity policies で強制できます。

要約すると、セキュリティ製品のロジックとインテリジェンスは製品側でユーザーモードに残り、Windows がカーネルで作業を行います。保護は Windows の深い部分まで届きますが、セキュリティ製品自身のコードがそこまで入る必要はありません。

**初回リリースでできること**

最初に挙げた 3 つのニーズに対応する、次の 3 つです。

1. **Observe（観察）**：PC が起動した早い段階から動いている間のシステム全体の活動を、ユーザーモードから監視する。クライアントは、イベントのプロパティやイベントオブジェクトの情報を、自分で管理するキューを通じて受け取る
2. **Enforce（強制）**：Windows が製品のルールをカーネルで確認し、製品が許可しないものをブロックする。イベントによって、アクションは allow、block、notify、または他のルールも見るための continue processing になる
3. **Start early（早期の開始）**：ルールはセキュリティアプリではなくプラットフォームに保存されるため、アプリが起動する前から Windows がルールを強制できる。製品は自分のルールを保存でき、PC の起動時から有効になる。製品が再起動しても、ルールは残って保護を続ける

> 補足：製品が保存したルールが、デバイスが想定どおり起動することを妨げる可能性が生じた場合、Windows が自動的に回復します。Kevin 氏は、これがすべての製品が使える、プラットフォームに組み込まれた信頼性だと強調しています。

### 5.4 今後

WESP は終着点ではなく、これからの旅の土台だと位置づけられています。最初は、焦点を絞った機能セットです。脅威は変化し続けるため、プラットフォームもそれに追随する必要があり、パートナーにはその上でイノベーションを続けてもらいたい、と述べています。

今後は、今回のデモで見せたもの以外のシナリオに対応します。例として、**ネットワーク保護とファイルスキャン**を挙げています。次に何を作るかは、パートナーと、お客様が持ち込む実際の製品や体験によって決まるとのことです。パートナーからの発表は今後数か月にわたって続く予定です。

## 6. デモ・手順

デモは 3 つあり、いずれも**録画**です（Kevin 氏が「What you're about to see is recorded」と述べています）。使用したアプリは **WESP Playground** という、WESP を使ったセキュリティ製品に何ができるかを示すサンプルアプリです。画面の細部は音声からは確認できません。以下は、語られた順の内容です。

### 6.1 デモ 1：観察（see / observe）

1. ユーザーモードだけで動くセキュリティクライアントが、エンドポイントセキュリティプラットフォームに接続している（他のアプリと同様のユーザーモードの実行）
2. ルールを設定し、新しいプロセスが開始されるたびに Windows に知らせるよう依頼してある
3. コマンドプロンプトを起動する
4. 背後の画面にイベントが流れ込み、通知が届く
5. クライアントのルールが起動を検出してフラグを立て、Playground に上がる。「Windows は活動を届けたが、何が重要か、何ができるかを決めたのはクライアント」と説明している。この例では、通知を受け取るだけ

### 6.2 デモ 2：止める（block）

1. このクライアントには、「Process Monitor が起動したらブロックし、ユーザーに伝える」というシンプルなルールが 1 つある
2. 画面上で、ルールにより起動がブロックされ、ユーザーに通知される様子が示される（起動操作そのものは、音声では語られていません）
3. 判断したのはクライアントで、カーネルでの強制は Windows が代行した。セキュリティ製品は、この強制のために自前のカーネルレベルのコードを使う必要がなかった

### 6.3 デモ 3：起動時に脆弱なドライバーをブロックする（start early）

脆弱なドライバーを起動時に持ち込もうとする攻撃者がいる、というのが想定です。

1. Process Monitor を、脆弱なドライバーの無害な代役として使う（Process Monitor は、起動時に自身のドライバーを読み込んで boot の活動をログに取れる）
2. 代役として、その起動時のログ機能をオンにする
3. そのドライバーをブロックするルールを追加し、再起動後も保持されるよう保存する
4. 再起動する
5. 戻ってきたとき、セキュリティ製品が作成したルールにより、プラットフォームがそのドライバーをブロックできていることが確認できる

Kevin 氏は、この 3 つのデモ（observe、block、block at boot）を、ロジックはユーザーモードのまま、状態は永続化され、起動の失敗の原因になる場合は Windows が自動で回復する、と整理しています。

## 7. 注意点・発表者の気付き

- **すべてのドライバーをユーザーモードに移せるわけではない。** 性能などの理由でカーネルに残るものがあり、そのための堅牢化が必要です。
- **WESP は、対応製品が出るまで効果が届かない。** デバイス側の作業はなく、各セキュリティ製品が自社のロードマップで採用します。
- **現時点の対象は MVI プログラムのセキュリティ企業のみ。** 強力なプラットフォームのため、利用者を絞っています。
- **初回リリースは焦点を絞った機能セット。** ネットワーク保護とファイルスキャンなどは今後の対象です。
- **ルールが起動を妨げても自動回復する。** プラットフォームに組み込まれた仕組みです。
- **Wi-Fi のユーザーモード対応のリリースは 2027 年。**

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- サードパーティのカーネルモードコードが減り、クラッシュや攻撃経路が減る。サービスによる修正も安全になる
- ユーザーモードのドライバーに障害が起きても、カーネルとデバイスの他の部分は動き続ける
- WESP では、お客様側で展開や有効化をする必要がなく、すでに Windows 11（25H2 と 26H2）の一部になっている
- セキュリティ製品のロジックがユーザーモードで動いても、保護は Windows の深い部分まで届き、起動時から有効にできる
- 製品のルールが起動を妨げる場合は Windows が自動回復し、セキュリティと回復力の両方が得られる
- Microsoft の Defender も同じプラットフォームの上に作られている

具体的な数値（クラッシュの削減率など）は、発表では語られていません。

## 9. まとめ

Mehmet 氏は、ドライバーを最も安全に動かせるモデルへ移す方針として、対応するスタックはユーザーモードへ、クラスドライバーは Windows が提供するものに標準化し、カーネルに残るものは堅牢化すると整理しています。セキュリティソフトウェアも、WESP によって同じ道筋に乗りました。

Kevin 氏は、聞き手へ次の行動を勧めています。

| 立場 | 推奨 |
| --- | --- |
| デバイスを管理している方 | デバイスを最新で保護された状態に保つ。ベンダーに、製品やドライバーをこれらの経路に沿って更新する計画を尋ねる |
| Windows デバイス向けのドライバーを作っている方 | 可能な限りユーザーモードと in-box のクラスドライバーへ移す。カーネルに残るものには、紹介された堅牢化の方法を活用する |
| MVI プログラムのセキュリティパートナー | この新しいプラットフォームで構築・検証し、フィードバックを返し続ける |

関連リソースとして、パートナーと一緒に火曜日に公開した WESP のブログがあり、今回の内容の詳細が書かれていると案内されています。
