# BRK388 Build and deploy local AI at scale across enterprise PCs w/ Windows ML

## 1. はじめに

このセッションは、Windows ML を使って、PC 上でローカルに動く AI アプリを作り、企業向けに展開する方法を紹介するものです。Windows ML は、AMD、Intel、NVIDIA、Qualcomm と共同で作られた、Windows 向けのローカル AI 推論フレームワークです。GPU、NPU、CPU のどれでも、1 つのプラットフォームから使えます。発表では、GA（一般提供）済みの本番向け機能のアップデートに加えて、新しい実験的 API も紹介されました。

内容は 3 部構成です。前半は、Windows ML CLI でモデルを最適化し、Windows ML で推論するデモです。中盤は、MLIR と DirectX Compute Graph Compiler（DXCGC）をベースにした実験的な Windows ML Runtime APIs と、Llama CPP ベースの task APIs です。後半は、パートナーの Sightful 社による事例です。**デモ 2 とデモ 3 では Wi-Fi をオフにした状態で実演され、「ローカルで動いている」ことが強調されました。**

## 5. 発表内容の詳細

### 5.1 Microsoft Foundry on Windows と Windows ML の位置づけ

Windows ML は、Microsoft Foundry on Windows の一部として位置づけられました。Foundry on Windows は、Windows PC の GPU、NPU、CPU で動くローカル AI 体験を作るための一連の提供物で、次の 3 つがあると説明されています。

| 提供物 | 説明（発表での内容） |
| --- | --- |
| Windows AI APIs | Windows に標準搭載されたモデルを使う、すぐ使える API（自然言語、ビジョンなど）。多くの場合、開発者が最も簡単に始められる方法。 |
| Foundry Local | Azure Foundry カタログのよく使われるオープンソースモデルのうち、Windows デバイス全般で良好に動くよう最適化済みのもの。 |
| Windows ML | 自分で学習したモデルや、Hugging Face で見つけて調整したモデルなど、独自のモデルを動かす場合に直接使う。 |

### 5.2 パートナー事例：Napster（ビデオ）

Napster のプロダクト責任者（音声認識の綴りは Zeev Nawat と聞こえます）が出演したビデオが流れました。Napster は、顧客のいる場所で応対し、従業員の同僚として働く "lifelike omni agents" を作っている会社だと紹介しています。Windows PC 上の Napster アプリでは、エージェントの顔をデバイス上で描画し、推論を Windows ML でローカル実行することで、レイテンシーが低く、クラウド推論コストがかからないとのことです。

また、Windows ML で AI 体験を一度作れば、AMD、Intel、Nvidia、Qualcomm の Windows PC に展開できること、エンジニアは Windows ML CLI で ONNX の生成 AI モデルの性能を測り、モデルのタスクを数日ではなく数分で評価していること、Microsoft Foundry のフロンティアモデルとローカル推論を組み合わせていることが語られました。

### 5.3 Windows ML の 3 つの強みと Windows ML CLI

Windows ML は、次の 3 つの領域に最適化されていると説明されました。

1. **Scale**：ハードウェア抽象化レイヤー。ハードウェアの細部やベンダーごとの SDK に深入りせず、チップセットをまたいでワークロードを展開できる。ONNX Runtime との統合で、動かせるワークロードの柔軟性も高い。
2. **Performance**：シリコンパートナーと緊密に連携し、新モデル・新デバイスのサポートや性能改善が、ハードウェアベンダーの execution provider を通じてスタックに入る。ネイティブの利点を 1 つのプラットフォーム経由で得られる。
3. **Deployment**：ランタイムそのものやハードウェアベンダーの execution provider を、システム全体で共有するコピーとして提供する。アプリが動くハードウェアに応じて適切なものを取得する API も提供し、アプリに個別に同梱しなくてよいため、アプリのサイズを小さく保てる。

自分で学習した独自モデルなどは、モデルをそのまま動かせるとは限らず、シナリオの性能・精度の目標に合わせて調整に時間がかかることが多いと説明されました。そこで使うのが **Windows ML CLI** です。モデルの準備、最適化、ベンチマークのためのワンストップのツールチェーンと agent skills の集合で、CLI や agent skills を直接使うことも、GitHub Copilot などお好みのツール経由で使うこともできます。

### 5.4 Windows ML の標準的な呼び出しパターン

自分のアプリで AI モデルをローカルで動かす場合の標準的な流れが、スライドで紹介されました。

1. Windows ML の NuGet パッケージをインストールする。スタンドアロンの NuGet パッケージのほか、Windows App SDK 経由でも入手できる。
2. `ensure and register certified async` を呼ぶ。certified な execution provider（一定の品質テストに合格したもの）を探し、デバイスに無ければダウンロードし、使えるよう登録する。
3. 実行に使う execution provider を決める。例では「prefer NPU」のポリシーを使い、デバイスで使える NPU の execution provider を選び、NPU が無いデバイスでは CPU にフォールバックする。特定の execution provider 向けにモデルを調整した場合は、手動で選ぶこともできる。
4. あとは標準的な ONNX Runtime の API で、モデルのロード、セッションの作成、入力の受け渡し、実行を行う。

Windows ML でワークフローを動かすと、ハードウェアエコシステム全体の最新の改善を 1 つのスタックで受け取れます。AMD、Intel、NVIDIA、Qualcomm による、今年の Build 以降の改善（性能、生成 AI と LLM、効率とメモリなど）がスライドで示されましたが、個別の内容は語られていません。

### 5.5 実験的 API：Windows ML Runtime APIs と DXCGC

ここからは Pavan が担当しました。ハードウェアパートナーが各シリコンに素晴らしい機能を持ち込むことは Windows の強みですが、一貫した体験を保ちながらハードウェアの差別化を生かすのは難しく、ローカル実行では新しいモデルアーキテクチャや実行スタックの革新が常に現れます。その答えとして、**Windows ML と MLIR** が挙げられました。MLIR は "multi-level intermediate representation" の略で、機械学習（machine learning）の略ではない、と補足されています。プラットフォームに依存しない表現から始めて、段階的に下げていくことで、目的のプラットフォーム向けの実行コードにする、層状のコンパイル方式です。

その上で、MLIR をベースにした **Windows ML Runtime APIs（Windows Native Inferencing）**が、今日試せる実験的な API として紹介されました。

* Windows のネイティブなデータ型を、実行の過程で保ちます（tensorization）。ハードウェアプラットフォーム、フレームワーク、推論エンジンをまたいで耐久性があると説明されています。
* カスタムパイプラインで、複数モデルの体験を組み合わせて新機能を作れます。

その基盤が **DirectX Compute Graph Compiler（DXCGC）** で、Microsoft の MLIR ベースのコンパイラです。DirectX により、システムのすべてのリソースを使えるよう統一的なリソース管理とスケジューリングができ、PIX などのデバッガーツールによるプロファイリングと診断、フォールバック用のシェーダーも提供されます。Windows ML CLI は、モデルをポータブルな MLIR 形式に変換できます（CLI で事前に行う方法と、WinML でランタイム中に行う方法）。また、すでに提供されている ONNX Runtime の API と機能については、Windows ML Runtime が ONNX Runtime API と変更なしで互換性を持ちます。

#### ローカル AI 実行の課題と、統合の次の段階

ローカルでモデルを実行するには、Prepare（準備）、Compile（コンパイル）、Execute（実行）の 3 ステップがあります。精度、レイテンシー、メモリ、コンパイル時間などの指標で最適に動かすため、各ハードウェアベンダーが SDK を提供します。そのため、モデルの実行品質が一定でないこと、ベンダーごとのスタックの癖を理解する必要があることが課題として顧客から聞かれていると、説明されました。

Windows ML と Windows ML CLI により、開発者は 1 か所で、複数のハードウェア向けにモデルを準備・最適化できます。ただし、ハードウェアベンダー固有のバックエンドは残るため、コンパイル時間や実行品質のばらつきは残り、デバッグも各ハードウェア SDK の理解とインストールが必要でした。そこで、Windows ML と DXCGC によるさらなる統一が示されました。DXCGC をバックエンドに加えることで、本当にポータブルな IR の契約を軸にした、統一された Windows ネイティブの実行スタックになります。DirectX との深い統合により、性能と品質を落とさずに一貫した体験を提供することを目指します。具体的な効果として、次の点が挙げられました。

* 統一された DX の視点で、システムリソースをより効果的に使える。
* GPU シェーダーのフォールバックにより、新しいオペレーターを持つ新モデルでも必ず動く。
* PIX でアプリケーションのデバッグとプロファイリングができる。

### 5.6 実験的 API：task APIs（Llama CPP と GGUF）

ここからは再び Anastasia が担当しました。LLM を含む生成 AI を Windows で動かすうえで、開発者からの要望の上位は「最新のオープンソースモデルをより速く（公開後すぐに）動かしたい」「より高い性能で動かしたい」ことだと説明されました。Hugging Face のモデルエコシステムは年々成長しており、現在 300 万を超えるオープンソースモデルがホストされています。

そのために導入されるのが、新しい実験的な **Windows ML task APIs** です。GGUF や Llama CPP の成果と、今後の DXCGC による Windows ネイティブの最適化により、オープンソースのエコシステムの速度で新しいワークロードに対応できるとのことです。

* 新しいモデルが Hugging Face に登場したら、その GGUF または Hugging Face の SafeTensors の成果物を、そのまま Windows ML task APIs で動かせる。
* 実行方法は、ネイティブの task APIs を直接使う方法と、OpenAI 互換のエンドポイントを使う方法がある。
* Llama CPP は、多くのワークロードがオープンソースの速度で拡大する手段で、DXCGC は、オープンソースモデルの幅広いモダリティを可能にし、時間をかけてさらに最適化する手段、という位置づけ。
* 大規模に展開する用途向けに、規制やコンテンツの出所（provenance）の要件を満たすための透かし（watermarking）にも対応している。

**簡単な試し方**：ローカルサーバーをモデル付きで起動し、OpenAI SDK から呼び出します。クラウドモデルで OpenAI のエンドポイントを使っている人にとっては、エンドポイント URL を差し替えて API キーを渡すだけの、1 行の変更です。

**ネイティブ統合**：準備ができたら、Windows ML task APIs でアプリに直接組み込みます。text generation API の場合の流れは次のとおりです。

1. ハードウェアターゲットを設定し、モデルをロードする。
2. モデルに付属するトークナイザーでセッションを作る。
3. 入力（ここではプロンプト）を用意する。
4. タスクを呼び出し、トークンをストリームで受け取る。

OpenAI エンドポイントより数行のコードが増えますが、制御、Windows ネイティブの統合、その結果としての性能向上が得られると説明されました。task APIs は LLM だけでなく、音声認識（例は Whisper）や、decision models（発話では "Leia" と聞こえ、名称は確定できません）にも対応し、同じ構造（ハードウェアターゲットの設定とモデルのロード、セッション作成、入力準備、タスク呼び出し）で使えます。1 つの task API を組み込めば、他も組み込みやすいはずだと述べています。

### 5.7 パートナー事例：Sightful（SpaceTop）

Sightful の President（Daniel）が登壇しました。Sightful の SpaceTop は、どこでも 100 インチの画面を提供する製品として紹介されています。外で働くと、小さなノート PC の画面で前かがみになり、機内では前の座席がリクライニングしないか気にし、公共の場では機密情報が見える危険もあると語りました。英国の大臣が電車内で画面を撮られ、首相に関する私的なメッセージが拡散した、という例も挙がっています。企業は、公共の場で機密データを閲覧することを禁じるようになってきており、SpaceTop は、エコノミー席 34B でも自分の広いオフィスに入れる、と説明しています。会場にいる CEO（発話では Tom Air と聞こえます）が、Intel Panther Lake を搭載した Surface のノート PC（機種名は音声認識の都合で確定できません）で、トラベルモードの SpaceTop をその場で使っていると紹介されました。複数のフルサイズのアプリや Copilot エージェントを並べて見られる、とのことです。

技術面では、動いている飛行機の中では、標準的な AR 画面が機体の動きでずれ、作業しにくく酔いの原因になるため、**トラベルモード**では画面が揺れに関係なくその場に固定されます。これはノート PC 上でリアルタイムに動く機械学習モデルによるものです。難しいのはモデルを作ることだけでなく、顧客が持つすべてのマシンで動かすことで、ハードウェア固有のバックエンドの挙動の違いにより、デバイスが増えるたびに統合と検証が増えると説明されました。そこで、トラベルモードを Windows ML に載せる取り組みを進めています。Windows ML Runtime APIs でモデルをロード・実行し、DXCGC が CPU、GPU、NPU 向けのハードウェア固有の最適化付きでコンパイルし、Windows がリソースとスケジューリングを管理します。そのため、シリコンをまたいで 1 つのスタックで統一された体験になり、チームは配管ではなく新しいシナリオに集中できるとのことです。この説明の間、Intel 上で Windows ML を通して動くトラベルモードの映像が示されました。Windows and Devices のブースのデバイスバーで体験できると案内されています（発話では "Muscom West" と聞こえ、会場名は確定できません）。

デモは 3 つあります（および Sightful の映像）。録音は音声のみのため、画面の細部は確認できず、語られた範囲で記します。

### 6.1 デモ 1：Windows ML CLI でモデルを最適化（Anastasia、Qualcomm 搭載の Surface Laptop for Business 8th edition）

シナリオは、Fabrikam electronics のカスタマーサポートです。顧客の質問が入り、埋め込みモデルで、よくある質問（FAQ）の中から回答候補を提案します。まず Windows ML CLI でモデルを最適化し、その後 Windows ML でデバイス上で推論します。

1. GitHub Copilot CLI に Windows ML CLI を読み込んだ状態を開く。「use WinML CLI」の skill で、「モデルを最適化して」「ベンチマークして」と言ったときに Copilot がどのコマンドを使うかを教える。skill は新しく追加されたものと説明された。CLI が対応するコマンドの一覧も画面に表示された。
2. Hugging Face の BGE base（発話は "BGE base. EN v1.5"）モデルをダウンロードし、デバイス用にビルドする。対象は Qualcomm の NPU。時間がかかるため事前に実行済みで、最適化、量子化、コンパイルがデバイスの QNN execution provider 向けに済んでいる状態を示した。
3. モデルをベンチマークする。精度、性能などのシナリオ KPI を確認する。NPU の使用が画面右側でスパイクとして見え、数回のパスで数値の安定性を確認する。
4. 結果の表では、精度（コサイン値）は 0.38 と低く（1 に近いべき）、性能も推論 1 回あたり約 17 ミリ秒で良くなかった。
5. さらに最適化する。コマンドをコピーして実行し、auto optimize の skill でベースラインモデルを最適化して保存する（時間がかかるため事前実行済み）。
6. ベースラインモデルと最適化後のモデルのベンチマーク結果を比較する。ベンチマークには WinML の eval と perf のコマンドを使っている。最適化後は性能が大きく上がり、コサイン値も 1 に近づいた。
7. サンプルアプリで確認する。まずベースラインモデルを読み込むと、顧客の質問の大半に誤って答え、精度は約 4%、レイテンシーも目標の 11 ミリ秒を大きく上回った。
8. 最適化後のモデルを読み込んで再度実行すると、すぐに精度が大きく改善し、レイテンシーも目標を十分に下回った。

### 6.2 デモ 2：落とし物キオスク（Pavan、Windows ML Runtime APIs と DXCGC）

フェア会場（発話は fairgrounds）で、1 か所の遺失物取扱所の代わりに複数の自動キオスクが落とし物を受け付けるシナリオです。拾った人が物を置くと、キオスクが写真を撮ります。CLIP の vision model が物と、色やパッチ、ループなどの特徴を識別し、共有の在庫ベクターの埋め込み空間に入ります。落とした人は、言語モデルで落とした物や場所、特徴を説明すると、似た特徴の物が見つかります。すべてローカルで動きます。

1. タスクマネージャーを表示し、他のローカル AI デモと同じく Wi-Fi をオフにしてあることを示す。
2. 「フードコートで青い水筒を拾った」と登録する。非 LLM のシナリオで、Windows ML と DXCGC のスタックで動く。ボトル、青色、運搬用のロープ（carrying rope）、スクリューキャップが識別された。
3. 落とした人として「昨日フードコートで青い水筒をなくした」と入力する。GPU が使われ、見つかった。
4. **同じ EXE** を、仕事で使っている別のデバイス（各プラットフォームから 1 台ずつ）でも実行した。写真は変えたが、同じシナリオが 4 つの異なるプラットフォームで、追加の処理や作業なしに、そのまま動いた。
5. 複数のエンジンを使う、とても早期の様子を見せる。システムには iGPU、dGPU、NPU の 3 つのエンジンがあり、非 LLM のシナリオを GPU で、LLM のシナリオを NPU で動かして、2 つのスパイクが見えることを示す。**GPU は今日実験的に使え、NPU は初期開発段階**だと、Anastasia との質疑で確認された。
6. コードサンプルでは、CLIP モデルに対して、モデルパイプラインを作り、CLIP モデルをパイプラインのステージとして追加し、入力と出力をバインドして、パイプラインを実行する。出力としてテキストと画像のベクターが得られ、それが在庫の埋め込みになる。Runtime API で複数のステージをつなぎ、単一のスタックとして実行できると説明された。

### 6.3 デモ 3：Windows ML サーバーでローカルコーディング（Anastasia、NVIDIA 搭載 Lenovo ノート PC）

Anastasia は、このデモは今後数日で提供される予定のものの先行プレビューだと説明しています（今日の実験的リリースで試せる task APIs とは別）。デバイスは、Lenovo のノート PC で NVIDIA の GPU（発話では "1590"、VRAM 24 GB と聞こえ、型番は確定できません）を搭載しています。

1. GitHub Copilot CLI を、クラウドモデルではなく、ローカルの Windows ML サーバーに向けて起動する。右下にモデル名が表示され、発話では "QUN 3.827B" と聞こえる（型番は確定できません）。Wi-Fi をオフにして、ネットワークに接続していないことを見せる。
2. コマンドでローカルエンドポイントの状態を確認する。ローカルモデルがセットアップされ、そのモデルを提供していることが表示される。
3. 「どのように提供されているか」と尋ね、Windows ML server（OpenAI 互換のローカル推論サーバー）で提供されていることを確認する。
4. トークン速度を見るため、GPU、NPU、CPU でローカル実行する利点と欠点を数項目でまとめる質問をする。すぐに回答が返り、「GPU は速度と大規模モデル向け、NPU は効率と小さいモデル向け、CPU はどのデバイスにもあるので良いフォールバック」という要約が出た。
5. コーディングタスクを与える。Fabrikam のサポートチーム向けの架空のアプリで、顧客との会話を CRM に保存できる。会話にはクレジットカード番号や電話番号が含まれ、保存時にマスクすべきだが、電話番号はマスクされてもクレジットカード番号はされない、というバグがある。
6. 「顧客メモを保存すると、クレジットカード番号全体がマスクされずに CRM に入る。バグを見つけて直し、テストを実行して」と依頼する。GPU のスパイクが見え、ほどなく修正とテスト実行が完了する。アプリを更新して再度 CRM に保存すると、電話番号とクレジットカード情報の両方がマスクされて保存された。
7. 複数ファイルにまたがるタスクとして、「ライトモードを追加し、モードを切り替えるトグルを付けて」と依頼する。クライアント側のロジックと CSS の更新が必要。styles.css の更新が進み、完了する。アプリを更新すると、ライトモードとダークモードを切り替えられた。
8. 「コードをたくさん書いたが、トークンコストはかからず、すべてこのデバイスの GPU で動いた」とまとめている。

## 7. 注意点・発表者の気付き

* Windows ML Runtime APIs と task APIs は**実験的**で、発表者は、使ってみた感想やフィードバックを求めています。GA なのは、Windows ML の ONNX Runtime API です。
* NPU を使ったマルチエンジン実行は、まだ初期開発段階です。デモは「とても早期の見え方」と断られています。
* ローカルコーディングのデモ（6.3）は、今後数日で提供予定のもので、今日の実験的リリースには含まれません。
* 独自モデルは、そのままでは精度・性能が目標に届かない場合があり（デモ 1 では、コサイン値 0.38、約 17 ミリ秒）、調整が必要です。
* ハードウェアベンダー固有のバックエンドは今も存在し、コンパイル時間や実行品質のばらつき、デバッグの難しさは残る、と説明されました。DXCGC の追加がその解決策として提示されています。
* MLIR の "ML" は machine learning ではない、と注意が促されました（発表者は「セッションの最後にクイズがある」と述べていますが、録音ではクイズの内容は確認できません）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* **ローカル AI 一般**：データがデバイスの外に出ない（プライバシー、セキュリティ、コンプライアンス）。レイテンシーの低下。オフラインで動作。トークンコストの削減。
* **展開のしやすさ**：1 度作れば AMD、Intel、NVIDIA、Qualcomm の PC に展開できる（Napster）。ランタイムや execution provider を共有コピーとして提供するため、アプリを小さく保てる。
* **モデル準備の効率化**：Windows ML CLI により、モデルのタスク評価が数日ではなく数分でできる（Napster）。デモ 1 では、ベースラインと比べて、精度と性能が大きく改善した。
* **移植性**：デモ 2 では、同じ EXE が 4 つの異なるプラットフォームで追加作業なしに動いた。Sightful の事例では、デバイスごとの統合と検証の手間が減り、新しい機能に集中できる。
* **オープンソースモデルへの追従**：GGUF や Hugging Face の SafeTensors の成果物を task APIs で動かせる。OpenAI 互換エンドポイントなら、URL と API キーの差し替えだけで試せる。
* **ローカルコーディング**：トークンコストなしで、ネットワークが無い場所でも作業できる（デモ 3）。

## 9. まとめ

発表者は、今日から使うための要点を次のように整理しました。

* GA の Windows ML ONNX Runtime APIs で、CPU、GPU、NPU（AMD、Intel、NVIDIA、Qualcomm）の全シリコンで本番向けの体験を作れる。
* 実験的な Windows ML Runtime APIs は、DXCGC を土台にした新しい Windows ネイティブの推論スタックで、より深い Windows 固有の最適化を提供する。
* 実験的な高レベルの task APIs は、Llama CPP のエコシステムの広さと DXCGC による最適化を組み合わせている。今日の実験的リリースで試せるもので、ローカルコーディングのシナリオ対応は数日後のアップデートで追加される予定。
* Windows ML CLI は、これらを支えるワンストップのツールチェーンと agent skills。

また、セッション評価の QR コードから感想を送るよう依頼がありました。同じシリーズの他のローカル AI セッションとして、コーディングタスクのオフロード、Windows AI APIs（音声認識などの機能を、より抽象化された形で使う）、デバイスエージェントや Foundry に関するもの、の録画を見るよう案内されています。
