# BRK560 Hybrid Intelligence: Making It Real with Windows PCs

## 1. はじめに

このセッションは、AI のワークロードを「ローカル（PC やサーバー）」と「クラウド」のどこで動かすかを使い分ける **hybrid intelligence（ハイブリッド・インテリジェンス）** を、Windows の PC を中心に説明したものです。agent の数が増えるとクラウドのトークンコストも増えるという課題を出発点に、次の 3 つの問いで話が進みます。

1. どの仕事を PC で動かすのか
2. そのために PC にどんなハードウェアが必要か
3. その投資にどれだけの価値があるのか

途中で、agent を安全に管理するための仕組み（Agent 365、Intune、MXC）、ローカルで動く MAI Code Flash モデルを使った GitHub Copilot の画面、Windows 向け AI PC の性能の目安、10,000 人規模の組織を想定した試算、パートナーの Insight 社の経験、そして歯科医院向けのローカル AI アプリのデモが紹介されます。

このセッションには画面を使ったデモが複数あります（詳細は 6 章）。Q&A の時間は設けられておらず、質疑は書き起こしにありません。

## 5. 発表内容の詳細

### 5.1 導入: agent の増加とコスト（Mark 氏）

Mark 氏は、Windows が「あらゆる人と組織がより多くを成し遂げられるようにする」という Microsoft のミッションを体現するもので、Windows 11 の顧客は 10 億を大きく超える、と話します。そのうえで、agent は人の野心を実現する助けとなり、ツールキットを呼び出し、他の agent を生成して仕事を進めるが、agent が増えるほどクラウドのコストも上がる、と説明しています。

企業の CIO や IT 部門から繰り返し聞く声として、次の 3 点が挙げられました。

* agent の考え方は気に入っているが、agent のコストをどう見積もればよいか分からない
* その結果、クラウドのトークンコストが上がっている
* agent が何をしていて、何にアクセスできるのかを把握する必要がある

数字としては、Gartner の最新レポート（8 月のもの）が、2028 年までに **13 億の agent** が使われると推計していることが紹介されました。Mark 氏が話をする企業の多くには、すでに数千から数万の agent があるそうです。agent が高度化し、関数の呼び出しや他の agent の生成が増えると、コストも上がります。続けて、2028 年までに agent 型ワークロード 1 件あたりの推論コストが **5 倍** になるという数字が挙げられました（この数字の出典は、トランスクリプトからは明確ではありません）。

こうした状況から Mark 氏は、edge のハードウェアを活用する好機だと述べています。この発表では PC クラスと、NVIDIA の GB シリーズによる「desktop supercomputer クラス」を扱い、オンプレミスのデータセンターのサーバーも、パブリッククラウドに加えて agent 型ワークロードを動かす場所になり得るとしています。さらに、従来クラウドや AI の予算と PC のリフレッシュ予算は別でしたが、両者は時間とともに統合され、AI の支出に PC も含まれるようになるという見方です。「2029 年までに、大企業の 80% が本番の AI を 3 つ以上の環境で動かす」という数字を挙げ、ハイブリッドは「ロゴを並べたスライド」ではなく現実の姿だと話しています。背景にはコスト、tokenomics、主権（sovereignty）や統制があります。

PC の調達については、「RAM 16 GB、ストレージ 512 GB」の構成が約 1 年前は $85 だったのに、いまは $525 になっている、という例が挙げられました。データセンター需要の増加で部品が使われていること、基板やシリコンのコスト増なども理由です。つまり、誰もがより強力な PC を求める一方で、PC がかつてなく高価になっている、というのが現在の状況です。そのため RFP では、適切な容量を適切な金額で買うことが課題になります。発表では、知識労働者向けから frontier 開発者向けまでの用途別に、どの PC クラスが合うかを整理すると予告されました。

### 5.2 hybrid intelligence とは（Kurt 氏）

Kurt 氏は、hybrid intelligence を「Windows がローカルとクラウドの AI を一つにまとめる仕組み」と定義し、PC で動かすのが妥当なものは PC で動かし、必要なときにクラウドを呼ぶ、と説明しています。Windows には、agent 向けのセキュアなプラットフォーム、PC とクラウドの間の intelligent routing（context、files、actions を伴う）、ローカル実行を支える silicon があり、セキュリティとユーザーの制御を中心に置く、という構成です。

お客様が「どの PC を買うべきか」を聞くときの整理として、次の 3 つの問いを挙げています。

1. どの仕事が実際に PC で動くのか
2. その PC にはどんなハードウェアが必要か
3. 組織にとってどれだけの価値があるのか（その投資から何を得られるのか）

### 5.3 agent をセキュアに保つ: Agent 365、Intune、MXC

ローカルに仕事を移す前提として、agent が安全に管理されている必要があります。Kurt 氏は次のように説明しています。

* これまで人、デバイス、データを守ってきたが、agent も同じアクセス権をマシンの速度で持つようになる。価値だけでなくリスクもそこから生まれる。agent はファイルを読み、Web サイトを取得でき、そこにはプロンプトインジェクション攻撃があり得る。
* agent を信頼するには、どの agent が動いているか、何に到達できるか、それぞれをどう大規模に統制するかを知る必要がある。Windows に、identity、containment、management を一つのシステムとして組み込む。
* **Agent 365** は、すでに使っているツール（Intune、Defender など）とともにこれらをまとめる。
* agent の自己申告は信頼できない。独立した observer と enforcement の層が必要で、それを Windows に作っている。

そのうえで新しい要素として紹介されたのが **Microsoft Execution Containers（MXC）** です（Kurt 氏は一部で "MXE"、"MXT" とも発音していますが、文脈上は MXC と同じものを指しています）。

* 封じ込めの強さが段階的に上がるコンテナーのスペクトラムを提供し、agent が行う作業に応じて強弱を選べる
* 現在は、agent の開発者が agent に必要なものを宣言し、組織のポリシーが境界を決め、Windows が実行時に独立した層として強制する
* 今後は Windows がポリシーを通じて、タスクに応じて封じ込めのレベルを調整できるようになる。一般的なタスクは軽量なコンテナー、より機微なタスクは agent 用の完全な仮想マシンで動かす、というイメージ

### 5.4 Copilot の hybrid intelligence

Kurt 氏は、Copilot に追加される 3 つの要素を挙げています。

| 要素 | 説明 |
| ---- | ---- |
| local context | 許可があれば、Copilot が PC 全体から必要なものを見つけて使う |
| 作業の代行 | ファイル整理から、一般的なトラブルシューティングの問題の修正まで、Copilot が操作して助ける |
| local models | ローカルモデルが Copilot に入ることで、クラウドに送らず PC へ動的にオフロードできる |

あわせて、Windows の検索とクイックアクション（ウィンドウの配置、Do Not Disturb、VPN 接続、仮想デスクトップの作成など）の短い映像が紹介されました。

### 5.5 GitHub Copilot とローカルモデル、builder PC

Kurt 氏によると、開発者はすでに多くのコーディング作業を GitHub Copilot に任せており、先月 **GitHub Copilot Fusion** がローンチされました。タスクごとに適切なモデルを選ぶ機能です。Windows PC では、この作業を **ローカルの MAI Code Flash モデル** にルーティングできます。将来は bring your own model（オープンソースや自社のモデルを持ち込む）に広げる「野心（ambition）」があるとも述べています。

これを可能にするのが、エコシステムのパートナーと作った新しい PC のカテゴリ（発表では "builder PC" と呼ばれています）です。

* NVIDIA RTX Spark と、AMD Ryzen AI Max 系（トランスクリプトでは "Ryzen AI Mac series" とも聞こえます）を搭載し、モデルをローカルで提供できる計算能力を持つ
* unified memory architecture により、Windows が必要な場所にメモリを割り当て、モデルを必要なときにメモリに載せられる
* 例として HP ZBook Ultra（AMD Ryzen AI Max Plus 搭載）が挙げられた

**Surface Laptop Ultra** は、Kurt 氏が "nerd out" して紹介したデバイスです。

* 128 GB の unified memory
* petaflop 規模の AI 計算能力。従来の PC に載らないモデルを動かせる
* 既存のノート PC の 2.5 倍以上の熱容量（thermal capacity）で、持続的な負荷でも速度を保つ
* 電源を外しても 99% 以上のパワーを維持する（"keeps over 99% of its power when unplugged"）
* 厚さ 18 mm 未満

### 5.6 量子化によるローカル実行

ローカルで動かせる理由として、Kurt 氏は量子化（quantization）を挙げています。MAI Code Flash モデルに **3-bit の量子化** を使い、効果をほとんど損なわずに小さなメモリ領域に収める、という説明です。

| 項目 | 数値 |
| ---- | ---- |
| モデルのパラメーター数 | 1,380 億（138 billion） |
| 通常のメモリ使用量 | 276 GB |
| 量子化後のメモリ使用量 | 53 GB |
| SWE-bench Verified のスコア | PC 上 70.8%、クラウド 72.6% |

SWE-bench Verified は、発表では「かなり難しいコーディングのベンチマーク」と説明されています（ローカルのスコアは音声認識で "78 70.8%" と聞こえますが、70.8% と読み取れます）。

状況としては、GitHub Copilot app、CLI、VS Code で preview 中で、Adobe、Autodesk、NVIDIA、PwC が試験運用しており、Insight も参加していると紹介されました。

### 5.7 どの仕事を PC で動かすか

Kurt 氏は、どの仕事を PC で動かすかを決めるための観点として、次を挙げています。

* どれだけ高性能なモデルが必要か
* どのくらいの頻度で動くか。一日中動く仕事ほど、ローカルに移したときの価値が大きい
* 回答がどれだけ速く返る必要があるか
* データをどこまで出してよいか。ローカルに留めたいか
* ネットワークが弱い、または無くても動き続ける必要があるか

実際の運用は、必要なときはクラウドの frontier モデル、可能なときはローカルモデル、という組み合わせになります。ワークロードごとに決定論的（deterministic）に決められるとも述べています。

### 5.8 どんなハードウェアが必要か: agentic continuum

Kurt 氏は、社内テストに基づく図解（illustration）として、**メモリがどの大きさのモデルを動かせるかを決める**と説明しています。

| メモリ・クラス | 説明された内容 |
| ---- | ---- |
| 16 GB（Copilot Plus PC の最小構成） | NPU で約 70 億（7B）パラメーターのモデルを一日中動かせる |
| 32 GB | 複数ステップの自律的な agent 作業を担える。モデルは「約 70B まで」と聞こえます |
| 64 GB | 長時間のジョブを担える。モデルは「約 70B まで」と聞こえます |

> 補足：32 GB と 64 GB の両方で同じ「約 70B まで」と聞こえます。言い間違いか音声認識の誤りかは確定できないため、聞こえたままを記載しています。
| 128 GB（builder PC） | MAI Code Flash（130B 超）、DeepSeek V4 Flash（約 284B、量子化で約 60 GB）が動く |
| DGX Station（desk-side supercomputer） | 最大 748 GB のメモリで、1 兆パラメーター級のモデルを扱える |

この範囲全体を Kurt 氏は **agentic continuum** と呼び、まず「選択肢」を持てるようにしたい、と述べています。あわせて次の数字が紹介されました。

* 現在作られているノート PC の 40% 以上が Copilot Plus PC
* inbox の Windows 機能と、Copilot Plus PC 上でお客様が行う処理を合わせて、毎月約 2 兆回の推論
* **mini desktops**: ヘッドレスの新しい agentic クラスの PC。最大 128 GB のメモリで、常時稼働の agent をその箱の中で安全に隔離して動かせる。現状は、クラウドのモデルを呼ぶ個人用 agent として使われることが多く、ハードウェアを上げればローカルでモデルを動かせる

**DGX Station**については、映像を見せたあと次のように説明しています（映像の音声は書き起こしにありません）。

* 748 GB の coherent memory、最大 20 petaflops の AI 計算で、机の下に置ける箱。ただし多くの電力が必要
* 1 兆パラメーターのモデルで単一の agent を動かすか、最大 64 の coding agent を同時に動かすか、チームの自律的な個人用 agent に使える
* Windows ベースなので、MXC による agent のセキュリティと、Intune による PC と同様の管理が及ぶ
* "800 gigabyte" のネットワーク（聞こえたままの表記）を内蔵し、複数台をつないで拡張できる。以前は AI クラスターの構築やレンタルが必要だった規模を、机の脇で動かせる

### 5.9 価値: トークン単位の効率と TCO

3 つ目の問い「何の価値があるか」について、Kurt 氏は次のように述べています。

* Azure では AI の性能を「watt あたり、dollar あたりの有用なトークン」で測っており、すでに持っている Copilot Plus PC や builder PC もトークンを作れるので、フリート全体を見るのに役立つ
* 知識労働者や開発者の PC は、同時に 20〜40% 程度の計算資源しか使っていないかもしれず、未使用の計算資源がある
* 高ボリュームの AI 作業を hybrid intelligence に移すと、**5 年間の TCO を半分以上削減できる**

これを示すため、代表的な **10,000 人規模の組織**（agent 導入から約 1 年、frontier 組織、説明用の例）を想定した試算が作られました。

* 設計は hybrid。日常的なトークンは PC で処理し、Copilot の機能、ワークフローの agent、frontier モデルが必要なものはクラウドに残す
* 次のリフレッシュ周期で、デバイスに移すことでトークン支出を **約 66% 削減**できる。これが 5 年間の TCO の数字の根拠
* これは、現在の価格で「1 日あたり約 $2.5 million」に相当すると説明されている（何と比べた数字かは、発表ではそれ以上触れていません）
* これらの PC の多くは、すでに持っているかもしれない

### 5.10 edge からクラウドまで一つのシステム

Kurt 氏は、Windows で「edge からクラウドまで一つのシステム」を作っていると述べています。Foundry tools が Azure で動き、Windows Server 2028（聞こえた表記のまま）、PC、Windows 365 の Cloud PC でも動くのは、一度作れば実行場所を選べるからで、管理も Intune や、Azure と Azure Arc 経由の Windows サーバーなど同じやり方でできるという説明です。比較として、他のプラットフォームでは、Mac、Linux サーバー、クラウドごとに設計し直す必要があると述べています。

### 5.11 Insight 社 Will 氏との対談

Kurt 氏が、Insight 社はこの hybrid intelligence のパイロットに参加していると紹介し、Mark 氏と Will 氏を壇上に招きました。Will 氏は、Insight が customer zero として、自社の事業を変革しながら学んだことをお客様に還元している、と話します。

* **社内での使われ方。** 財務、HR、法務などの知識労働者が使う場面で、hybrid intelligence が Copilot に入ってきている。財務や HR のメンバーが、ローカルモデルで GitHub Copilot を使っている例がある。コードを書く人と知識労働者の境が曖昧になり、「builders」と呼び始めている。
* **ローカルで動く価値。** トークンを使って疑わしい価値のダッシュボードを作ることもあるが、ローカルのデバイスで追加コストがなければ「やってみればいい」と述べています。
* **Windows の使い心地。** 5 年間 MacBook を使ってきたが、1 か月 MacBook を使わず、Surface Ultra で作業している。冷却が素晴らしく、一日中ローカル推論を高負荷で動かしても、温かくなるが管理可能で、うるさくない。以前の Mac は、離陸時のジェット機のような音で非常に熱くなった、と話しています。
* **パイロットから本番へ。** 仕事がどこにあるかを理解し、適切な場所へルーティングすることが鍵。ローカルや自社データセンター、ワークステーションで動くものは追加費用がかからず、frontier の知能が必要なときはクラウドにシームレスに移れるようにする。人にモデルを意識させず、「イージーボタン」にする。
* **未使用の計算資源。** 20〜30% しか使っていないデバイスの稼働率を上げるため、リアルタイムでなくてよい仕事をキューに入れ、ローカルの推論容量で処理する「21 世紀のメインフレーム」のような使い方を挙げています。
* **次の展望。** AI をさらに民主化し、スキルのギャップを埋めたい。モデルの名前ではなくアウトプットを話題にしたい。
* **サイバーセキュリティ。** Agent 365 をテストしてきた。自分のチームにデバイスを配り、機微なサイバーセキュリティのワークロードを社内（"our own four walls"）で動かしたい。一部の frontier モデルは safeguards のために、必要なセキュリティ業務の一部をしてくれないが、ローカルのモデルならその制限を回避して、防御側として必要なことに使えると述べています。それを超える作業では、別のサイバー向けモデルなどと組み合わせるそうです（モデル名の一部は音声認識の都合で確定できません）。

### 5.12 締めくくり: PC は AI インフラの一部（Kurt 氏）

Kurt 氏は、冒頭の「どの PC を買うべきか」という問いに戻り、agentic continuum に沿って、役割ごとにインフラを計画し始める必要があると述べています。PC はすでに戦略的な AI インフラの一部だからです。幅広いコンピューティングの選択肢を用意しつつ、Windows 側ではそれを抽象化する作業を進めているという説明です。その例が **Windows ML** で、DirectX が出る前は開発者がハードウェアや GPU ごとにゲームを書いていたが、DirectX によってその必要がなくなったのと同じことを、AI で行うものだと述べています。任意のハードウェアにまたがって抽象化できるため、一度作れば動きます。そして、今後 12〜18 か月のハードウェアの決定はすべて AI の決定であり、チームにできることと、次のリフレッシュまでのトークンコストを左右すると締めています。

## 6. デモ・手順

このセッションでは、複数の画面デモや映像が使われました。録音は音声のみのため、画面の細部は確認できず、以下は語られた範囲のみです。

### 6.1 Agent 365 と Intune による MXC のポリシー（映像のナレーション）

Kurt 氏が "quickly show you what this looks like" と述べて見せたものです。誰の声か、ライブか録画かは、書き起こしからは区別できません。語られた順は次のとおりです。

1. IT は **Agent 365 の estate view** から始め、どの agent が動いていて、どこにリスクがあるかを把握する。
2. IT 管理者が Microsoft Intune を使い、agent がアクセスし実行できる範囲を制御する。ポリシーは、MXC 対応のすべての agent にも、Copilot のような特定の agent にも適用できる。
3. 管理者が封じ込めの境界（Windows が agent のサンドボックスに与える最大のファイルシステムアクセス）を設定する。内容は、承認されたプロジェクトフォルダーは読み書き可、システムの残りは読み取り専用、会社の OneDrive にはアクセス不可。
4. これにより、agent が業務データをコンテキストに取り込んだり、デバイス間で同期される変更を作ったりするのを防ぐ。Intune のポリシーでネットワークアクセスなどの設定も制御できる。
5. ユーザー側の結果として、Copilot は agent がアクセスできるドキュメントでレポートの作業を続けるが、制限された場所へのファイル書き込みの要求はポリシーで拒否される。

### 6.3 Surface Laptop Ultra 上の Copilot app（ライブ）

Kurt 氏が "now I want to show you this in action on a Surface Ultra" と述べて行ったものです。

1. Copilot app で agent にプロンプトを与える。内容は、未使用のコード、インポート、パッケージ、廃止された feature flag を検出し、実行可能なサマリーを出すこと。
2. モデル選択は "auto efficiency" に設定。タスクの複雑さに応じて特定のモデルへルーティングされる。今回は比較的単純なタスクなので、ローカルモデルが使われた。左側にローカルモデルの起動が表示され、GPU が動いている。
3. 同じプロンプトを別のコードベースでも事前に実行済みで、そこでは MAI Code 1.1 Flash local が使われ、すべてローカルで処理されてトークンは消費していないと説明された。
4. リポジトリがクローン済みでインターネットが不要なため、マシンを **機内モード** にすると述べて切り替える。
5. 次に sub-session の例。Windows Terminal リポジトリで `needs repro` ラベルの付いた issue を調べ、3 件を選ぶよう agent に依頼したセッションがあり、3 つのローカル sub-session が起動して調査している。再現できていない issue なので、ローカルで調査して情報を増やしたいという意図。これらも MAI Code 1.1 Flash local を使っている。
6. 1 つの sub-session を開くと、モデルへの送信が 160 万トークン、受信が 1 万トークンで、すべて無料と表示されている。
7. **canvas**（agent と一緒に作り、双方がやり取りして更新できるカスタム UI）を開いて、session visualizer を表示。紫色がローカルで実行したセッション。同じタスクを時間を変えて繰り返しているのは、issue のトリアージが終わりのないタスクだから。
8. これらは **automations** に設定され、一定の周期で動く。モデルを MAI Code 1.1 Flash local に明示的に設定してあるため、夜間に動いても AI クレジットを使わない。

Kurt 氏は、GitHub Copilot Fusion が必要に応じてローカルモデルにルーティングするだけでなく、開発者が夜間に動く automations を設定でき、朝にクラウドのトークン請求を見て驚くことがない、とまとめています。

### 6.5 Zava Dental のライブデモ

Mark 氏が、5,000 の歯科医院を持つ Zava Dental のオーナー役となり、想定シナリオを説明します。目標は、患者の診断を自動化して時間を節約し、品質を高め、各医院でローカルに実行できるようにすることです。Kurt 氏は、優秀な歯科医の採用は難しいため、同じ人数の歯科医でより多くの患者を診られるよう、患者 1 人あたりの時間を減らしたい、という要件を説明しています。センシティブな患者データはデバイス内に留めます。

デモの前提は次のとおりです。

* **Copilot Plus PC** で完全にローカル実行。Intel Core Ultra シリーズの PC で、メモリは 64 GB だが、"full disclosure" として 16 GB の PC でも動くと説明している（アプリで使うのは 7B パラメーターのモデル）。

語られた順は次のとおりです。

1. **Windows Hello** の生体認証でサインインする。
2. 画面右上で歯のアイコンが回っている。7B モデルをメモリに読み込んでいる表示（のちに NPU への読み込みが完了したと説明された）。
3. ホーム画面に、今日の概要、今後の予約、最近のアクティビティが表示される。そのほか予約の一覧、患者の一覧があり、生年月日や保険情報などの機微な情報が含まれる。HIPAA に準拠した保存が必要。レポート画面では、ローカルで行った処理や、収益・節約の状況が見られる。
4. アプリ内蔵のチャットボットは、ローカルモデルを使うため、画面や PC 上で起きていることを踏まえて推論できる。レポート画面では「レポート案の作成」「患者メモの作成」などを、ホーム画面に戻ると「次の予約を開く」「ロスターを確認する」などを提案する。
5. **human in the loop**: 「次の予約を開く」を選ぶと、歯科医に開いてよいか確認が出る。機微な情報が、間違った患者の前で開かれないようにするため。確認したが、ライブデモの都合で開かなかったため、そのまま最初の患者の診察画面に進んだ。
6. 診察画面では、検出モデルと小規模言語モデル（small language model）を通し、検出モデルが見つけた内容を、歯科医が患者に見せられる分かりやすい文章にしている。
7. 「today's smile snapshot」に、奥歯の虫歯の可能性と、埋伏した親知らず（impacted wisdom teeth）が示される。X 線から分かる内容を動的に示し、最終判断は歯科医が行う。
8. 歯科医が患者向けのプレゼンテーションを開始し、ウォークスルーを実行すると、それぞれの所見が動的に示され、歯科医が一般的な言葉で患者に説明できる。
9. 見終えたら治療計画に進む。agent が治療オプションを引き出し、X 線の検出結果と言語モデルの推論に基づく推奨を適用する。どれが適切かは歯科医が選ぶ。今回は 3 つすべてを選ぶと、その患者向けの治療計画が作られる。
10. 計画のサマリーには、3 件をレビューしたことと、次回の予約日の提案が表示される。
11. 最後に、post summary report（聞こえた表記のまま）と、フォローアップの予定のメールの下書きが作られる。普段は見えない処理で、実演のため見せた。速すぎて見逃すかもしれないと断っている。
12. これらは **MXC コンテナー** の中で動く。新しいドキュメントを作るときに、書き込み先を患者データを安全に保存できる場所に限定しており、MXC によって agent の境界を設定できている。患者データが想定外の場所に出ない。

> 補足：デモの途中で Mark 氏が事実や数字を挟む予定だと話していましたが、実際には、HIPAA への準拠など短いコメントや相槌が中心でした。

## 7. 注意点・発表者の気付き

* **agent は自己申告を信用しない。** 独立した observer と enforcement の層が必要、という考えです。
* **ライブデモの特性。** Kurt 氏は、デモが動くか分からないと冒頭で述べ、「次の予約を開く」の確認は、ライブデモなので実際には開かないと説明しました。
* **human in the loop。** agent が機微な患者情報を、間違った人の前で勝手に開かないよう、歯科医の確認を挟みます。治療計画も、歯科医が選ぶものです。
* **Zava Dental のデモのハード要件。** 実演は 64 GB の PC でしたが、使うのは 7B モデルで、16 GB の PC でも動くとのことです。
* **PC 価格の上昇。** RAM 16 GB/ストレージ 512 GB の構成が $85 から $525 に上がっており、調達では適切な容量を選ぶことがより重要になっています。
* **表記が不確かな点。** MXC の呼称（MXE、MXT と聞こえる箇所）、メモリ 64 GB の対応モデルサイズ、Windows Server の年号などは、音声認識の都合で確定できません。
