# BRK395 Inside WSL containers for application development

## 1. はじめに

このセッションは、Windows Subsystem for Linux (WSL) に組み込まれた **WSL containers** を、開発者向けの使い方からエンタープライズでの管理・セキュリティまで通しで紹介するものです。WSL containers は今年の Build でプレビューとして公開され、9 月末から一般提供 (GA) になっています。

発表の冒頭で登壇者が示した要点は次の 3 つです。

1. Linux コンテナーが Windows の機能として第一級（first-class）になった。CLI と API の両方で使える。
2. WSL の機能の一部なので、最新の WSL にするだけで使える。追加のライセンスやセットアップは不要。
3. Intune と Microsoft Defender for Endpoint (MDE) との統合が最初から用意されており、エンタープライズで使える。

前半は CLI、API、Aspire（Intel NPU を含む）、AKS という開発者向けのデモ、後半は MDE と Intune のデモ、内部アーキテクチャの解説、ロードマップという構成です。

## 5. 発表内容の詳細

### 5.1 WSL containers の概要

冒頭で、WSL containers が今年の Build でプレビューされ、9 月末から GA になったことが説明されました。GA 後は、開発者向けの体験を広げたほか、デスクトップからエンタープライズまで使える形にしたとのことです。

提供される入口は 2 つです。

| 入口 | 用途 |
| ---- | ---- |
| CLI（`wslc`） | 開発者がコマンドラインでコンテナーを操作する |
| API（SDK） | Windows アプリケーションのコードとランタイムに Linux コンテナーをネイティブに近い形で組み込む |

CLI は `wslc` のほか、`container` というエイリアスでも実行できます。`container` と入力したい人向けに、最初から組み込まれているとの説明です。

### 5.2 アプリごとに軽量 VM が作られる仕組み（概要）

Linux コンテナーを作成する Windows アプリケーションごとに、軽量なユーティリティ用 Linux VM がバックグラウンドで透過的に作られます。そのアプリが作る Linux コンテナーは、すべてこの VM 上に同居します。CLI 経由で作るコンテナーも、CLI 用の別の軽量 VM にまとめて配置されます。

つまり、アプリごとにハイパーバイザー境界で分離されます。この設計には、次の効果があるとの説明です。

- アプリ単位でリソースを制御できる。
- あるアプリのコンテナーが使うカスタムネットワーク名やボリューム名が、別のアプリのコンテナーと衝突しない。

詳しいアーキテクチャは、後半の 5.8 で解説されています。

### 5.3 CLI の基本操作

> 以下の画面操作は、発話の範囲で整理しています。

CLI のコマンドは、既存の Linux コンテナーツールとよく似た体裁になっています。デモでは、Debian の最新イメージからコンテナーを作り、対話シェルに入りました。

- `-it` で対話シェルを取得する。
- Debian のバージョンは Trixie（Debian 13）だった。
- Ctrl-P、Ctrl-Q でコンテナーからデタッチできる。
- `wslc ps -a`（`wslc container list` でも同じ）でコンテナーの状態を確認できる。
- 再度アタッチし、シェルを終了すると、コンテナーは exited になる。

Pooja 氏は、ここで見せたのはごく単純なライフサイクル管理であり、Windows 上でネイティブに近い感覚で使えることを示したかったと説明しています。

### 5.4 イメージのビルドと GPU パススルー

開発者は既存イメージを使うだけでなく、アプリケーションをビルドし、環境と依存関係を OCI 準拠のコンテナーイメージとしてまとめます。そのイメージは、本番のクラウドにも、ローカルのインナーループにも持ち運べる、という前提が説明されました。

デモで使ったのは、GPU を使うフラクタル描画アプリです。Containerfile（発話では "container file"）には、次の内容が書かれていました。

- ベースイメージは Debian Trixie Slim
- 作業ディレクトリは `/app`
- `apt-get` などで依存関係をインストール
- アプリのコードをコピー
- アプリは Web アプリで、ポート 8090 で待ち受けるため、そのポートを公開
- ヘルスチェックのエンドポイントを指定し、アプリが unhealthy ならコンテナーも unhealthy になるようにする
- アプリの起動コマンド

この Containerfile から `wslc build` を実行し、タグ `demo` を付けたイメージ（GPU fractal）をビルドしました。`wslc images` に grep をかけると、イメージが作られていることを確認できました。ビルドが速かったのは、このマシンに既にあったキャッシュ済みレイヤーを使っているためで、表示上は 10 日前に作成されたことになっていました。

> ご参考：Windows には grep などの Linux 用コアユーティリティも追加されており、"core utils" で検索すると見つかるそうです。touch や find など、全部で約 168 個あると紹介されました。

続いて、このイメージからコンテナーを起動しました。ここで使ったオプションは 3 つです。

| オプション | 意味 |
| ---- | ---- |
| `--gpus all` | Windows ノート PC の NVIDIA GPU をコンテナーにパススルーする |
| ポートマッピング | Linux 側のポート 8090 を、Windows 側のポート 8091 に割り当てる（localhost でアクセス） |
| バインドマウント | Windows 側の現在のパスを Linux 側の `/app` に読み取り専用でマウントする |

バインドマウントの狙いは、実行環境と依存関係はコンテナーの Linux 環境のものを使い、アプリのコードは Windows 側のパスから持ってくることです。

起動後、`localhost:8091` にアクセスすると「CUDA canvas」と呼ばれる画面が表示されました。このアプリは、表示されているピクセルの数だけ CUDA スレッドを起動します。画面をズームするたびに、各ピクセルを個別のスレッドで計算し直す仕組みです。タスクマネージャーを開くと、Windows 側の NVIDIA GPU が使われている様子も確認できました。描かれていた図形は Mandelbrot 集合です。

最後に、ネットワークの作成、各種ボリューム、コンテナーのコピーや再起動など、ほかにも多くのコマンドがあることが紹介されました。

### 5.5 API で Windows アプリに Linux コンテナーを組み込む

ここからは Craig 氏のデモです。デモアプリは Windows アプリケーションで、レンダリングエンジンが Linux 上で動く構成です。

- 描画するシーン（コーヒーメーカー）は Windows 側のファイルに保存されている。
- Start を押すと、WSL container SDK が数秒でコンテナーを起動し、レンダリングエンジンを立ち上げる。
- 画面下部のデバッグ情報を出していなければ、エンドユーザーには Linux で動いていると分からない。
- 複雑なレイトレーシングを行っても、パフォーマンスは良好（performant）。
- プロセス一覧には、Windows のプロセスとして表示される。

Craig 氏によると、このレンダリングエンジンは、映画『How to Train Your Dragon』『The Bad Guys 2』『The Wild Robot』のレンダリングに使われた実際のエンジンです。それを、コードの変更なしで Windows 上で動かしている、という説明でした。アプリを閉じると、他のアプリと同様にエンジンも片付けられます。

コードの面では、使い方は簡単です。SDK を呼び出し、コンテナーの設定（イメージ名、init プロセス、マウントするボリュームなど）を指定し、コンテナーを作成して起動します。このデモでは、シーン用と出力用の 2 つのボリュームをマウントしています。起動後はアプリの一部として操作でき、後片付けなどを行う API も用意されています。

> 補足：Linux のコードを Windows に持ち込みたいとき、コンテナーを起動して操作するだけで済むようになった、というのが Craig 氏の説明です。

### 5.6 パートナー・ツールとの統合

GA 以降に進めた統合として、次の 4 つが紹介されました。

#### MXC（Microsoft execution containers）

カンファレンス内に MXC を扱うセッションが複数あり、少なくとも 1 つのセッションで MXC と WSLC を組み合わせたデモが行われていると案内されました。このセッションでは、そのデモは省略されています。

#### Aspire

Aspire は、オープンソースの、コードファースト・マルチ言語のツールチェーンで、分散アプリケーションをコードで定義できるものです。Aspire チームは、Linux コンテナーのツールをデフォルトで WSLC に切り替えた最初のチームだと紹介されました（"Props to the Aspire team"）。

デモアプリは「hot takes」です。ランダムに生成された開発者の意見を表示し、Web フロントエンドから投票できます。コードの中では、Web アプリケーションのビルダーを作り、Postgres データベースと、その上にデータ取得を速くするための Redis キャッシュを指定しています。アプリは、API、Web インターフェース、2 つのデータベース、NPU を使う生成部分で構成されます。

デモの流れは 6.3 にまとめました。Redis と Postgres のコンテナーが WSLC のコンテナーとして起動し、画面は Postgres から配信され、更新すると Redis キャッシュから取得されることが確認されました。

#### Intel NPU

GPU と同じように、WSL containers から Windows マシンの **NPU** を使えるようになったことが紹介されました。Intel にはドライバー面の協力に対する謝辞が述べられています。デモでは、hot takes アプリの AI ボットが、NPU 上のローカルモデルで開発者の意見を生成しました。

#### AKS（Azure Kubernetes Service）

AKS と WSL が連携し、Windows 上でローカルの Kubernetes シナリオを動かせるようになりました。軽量な Kubernetes クラスターを簡単に作れ、Linux 環境は WSL が提供します。1 つの CLI コマンドでローカルにクラスターを作れ、Windows 上でネイティブに近い体験になるという説明です。

クラスター作成時に指定できるものとして、次が挙げられました。

- Kubernetes のディストリビューション（K8s や K3s など）
- Kubernetes のバージョン
- `--enable-GPU`（Windows ホストの GPU を、WSL 内のクラスターで使う）
- GPU 共有のためのタイムスライシングのパラメーター（クラスター内では NVIDIA device plugin を使用）
- 作成完了後に kubeconfig を置く場所

AKS 側には **AKS Dev CTL**（音声認識の都合で表記が確定できません）という CLI が既にあり、同様の体験ができます。こちらはプレビューです。将来的には、`wslc cluster create` に統合したい、と説明されています。`wslc cluster create` は現時点では実験的な位置づけで、公開フォークで試せる（発話では "private, on a public fork" と言い直されており、正確な表現は聞き取りでは確定できません）とのことです。近いうちに正式化し、プレビューとして提供する予定です。

> 補足：Pooja 氏は、WSL2 が "AKS AI node" になることは、AKS Everywhere のビジョン（パブリック／プライベートクラウド、ソブリンクラウド、オンプレミスのデータセンター、遠隔のエッジなどに Azure Kubernetes のプラットフォームを広げ、一貫した環境・管理モデル・ツール・運用体験を提供する Microsoft の戦略）に向けた一歩だと説明しています。

### 5.7 エンタープライズ対応: Defender for Endpoint と Intune

ここからは Craig 氏の担当です。エンタープライズから寄せられる主な質問は 3 つで、それぞれに答える形で説明されました。

| 質問 | 回答 |
| ---- | ---- |
| 安全か | Microsoft Defender for Endpoint (MDE) で脅威検出と可視化ができる。Linux コンテナー内で動くすべてを見られ、Windows マシンに紐づけられる |
| 制御できるか | Intune でポリシーと構成を設定できる。この機能へのアクセスの制御と、レジストリの許可リストなどの主要なセキュリティ設定が可能 |
| 既存のアーキテクチャに合うか | Intune や MDE などの組み込みのツールを使う。既に使っているなら、導入は簡単。サードパーティ製ツール用のプラグインの仕組みもある |

MDE を使うには、**Microsoft Defender for Endpoint Plan 2** のライセンス（通常の E5 ライセンス）が必要です。設定の endpoints から、プラグインの MSI をダウンロードし、社内のマシンに配布します。

Intune では、**許可するコンテナーレジストリの allow list** を設定できます。これは、WSL の長年の要望だった「社内で実行できるディストリビューションや Linux イメージを制御したい」という声に応える設定だ、と説明されました。社内のハードニング済みイメージを置いた Artifactory のような場所があれば、そこだけに限定できます。

デモの内容は、6.6 と 6.7 に書いています。

### 5.8 内部アーキテクチャ

ここは Pooja 氏による解説です。

**入口とサービス。** 入口は Linux containers API と Linux containers CLI の 2 つで、どちらもプロセス間通信で、Windows ホスト上の **WSL service**（`WSL service.exe`）と通信します。API は `WSLC SDK.dll` として公開され、NuGet パッケージとして配布されています。WSL service は、既に WSL ディストリビューションで使っているものと同じコンポーネントで、そこにコンテナー機能が追加されました。

**ユーティリティ VM。** WSL service は、軽量なユーティリティ VM を作成し、そのライフサイクルを管理します。VM との通信には **HV socket** を使います。HV socket はネットワークソケットではなく、Winsock API の拡張で、Windows ホストとハイパーバイザー上のゲストの通信に特化したものです。ゲストごとにホストとの 1 対 1 のチャネルがあるため、VM ごとの通信は他と分離されています。

コマンドが発行されると、WSL service は HV socket 経由で Linux 側に伝えます。VM 内で動く Linux guest agent とコンテナーランタイムがコンテナーを起動します。現在のコンテナーランタイムは **Moby** で、同じ VM 上で動く containerd のデーモンと連携します。コンテナー作成後は、ユーザーとの通信の中継も HV socket で行われます。

**ストレージ。** コンテナーのメタデータやスクラッチ領域は、VM ごとに 1 か所（`/var/lib` のような場所）にまとめられます。この場所は、Windows ホスト側の仮想ディスク（VHD）に透過的にマッピングされます。VM ごとに VHD を持つので、ストレージもアプリごとに分離されます。

**Windows 側のパスのマウント。** `wslc run` でマウントを指定した場合、Linux 側にボリュームを作ってコンテナーにアタッチし、内部では Windows 側の指定パスにマッピングされます。この共有には **virtio-fs** を使っています。virtio-fs は、ハイパーバイザーのホストとゲストの間でファイルシステムを共有する比較的新しいプロトコルです。WSL のディストリビューションは Plan 9 を使っていますが、virtio-fs は現状 2〜3 倍高速だと説明されました。

**Intune の仕組み。** IT 管理者が Intune のポータルで WSL のポリシーを作ると、Windows ホスト側では **レジストリキー** として反映されます。WSL service がそれを読み取り、変換して Linux 側に渡し、コンテナーランタイムがポリシーを適用します。Intune のシナリオでは、Linux VM 側で動くものはありません。

**Defender の仕組み。** Defender では、Linux 環境内に MDE sensor が動きます。Linux 環境の可視化と観測性を提供するためです。Windows ホスト側では、WSL の plugin manager が Defender plugin をインストールし、plugin が Linux 側の MDE sensor を起動します。sensor は、eBPF ベースのライブラリを使う Linux プロセスで、プロセスとネットワークのカーネルイベント（より高度なケースではファイルシステムも）を取得します。eBPF のカーネルフックなので効率的に監視でき、イベントをまとめてテレメトリとして送信します。

将来的な話として、MDE sensor を使い、アンチマルウェアとアンチウイルスを持ち込むこと、さらにその先として、信頼できないコンテナーの隔離（quarantine）も検討していると述べています。

### 5.9 利用企業・ロードマップ・まとめ

WSL containers は、世界中の多くの顧客に既に使われているとして、次の企業と団体への謝辞が述べられました。Wells Fargo、Intel、Crones、ModTech、Bulk Graphics、Moonray（Crones、ModTech、Bulk Graphics の綴りは音声認識の都合で確定できません）。各社は、WSL の使用事例をスライドで紹介することに同意した企業で、事例の中身は音声では語られていません。

**ロードマップ**として、次が紹介されました。

- Intel NPU のサポートの追加
- Kubernetes シナリオ（WSL containers でローカルの Kubernetes クラスターを動かす）
- WSL ディストリビューション向けの USB サポート（USB デバイスを直接ディストリビューションに渡せる）
- compose のサポート（`wslc compose` で複数コンテナーを実行。ロードマップの中でも先の予定）

最後のまとめとして、4 点が示されました。WSL containers が本日 GA であること、Linux コンテナーが Windows で第一級であること、Defender for Endpoint と Intune の設定で使えること、MXC や Aspire などのパートナー統合があることです。関連セッション、WSL のドキュメント、WSL の GitHub、オープンソースの開発者向けドキュメントも案内されました。

## 6. デモ・手順

このセッションには、画面を使ったデモが複数あります。録音は音声のみのため、語られた範囲で整理します。

### 6.1 CLI: コンテナーのライフサイクル（Pooja 氏）

1. `wslc` で Debian latest のコンテナーを `-it` で起動し、Linux 環境のシェルに入る。
2. OS のリリース情報を表示するコマンドで、Debian Trixie（Debian 13）であることを確認する（発話は "cat COS release" と聞こえ、正確なコマンド表記は音声認識の都合で確定できません）。
3. Ctrl-P、Ctrl-Q でデタッチする。
4. `wslc ps -a` で、約 27 秒前から動いていることを確認する。
5. 再度アタッチして終了し、`wslc ps -a` で約 2 秒前に exited になったことを確認する。

### 6.2 CLI: ビルドと GPU パススルー（Pooja 氏）

1. Containerfile の内容を説明する（5.4 参照）。
2. `wslc build` で、タグ `demo` の GPU fractal イメージをビルドする。
3. `wslc images` を grep で絞り込み、イメージができたことを確認する。
4. `wslc run` に `--gpus all`、ポートマッピング（8090 → 8091）、読み取り専用のバインドマウントを指定して、コンテナーを起動する。
5. `localhost:8091` で CUDA canvas を開き、ズームしながら描画する。
6. タスクマネージャーで GPU 使用を確認する。

### 6.3 Aspire と Intel NPU（Pooja 氏）

1. hot takes アプリの Aspire のコードを示す（Postgres と Redis を指定）。
2. Aspire のコマンドラインでアプリを起動する。
3. Redis と Postgres のコンテナーが WSLC のコンテナーとして動いていることを確認する。
4. Aspire のダッシュボードから、アプリの Web インターフェースを開く。
5. 開発者の意見の生成と投票を行う。画面は Postgres から配信され、更新すると Redis キャッシュから取得される。
6. AI ボットで意見を書かせ、リストの末尾に追加されることを確認する。もう 1 件も追加する。
7. タスクマネージャーで、Windows ホストの NPU が使われていることを確認する。

### 6.4 API: Windows アプリから Linux のレンダリングエンジンを実行（Craig 氏）

5.5 のとおりです。Start を押してコンテナーが数秒で起動し、レンダリングエンジンが動くことを示し、プロセス一覧にも表示されることを確認しました。その後、アプリを閉じるとエンジンも片付けられること、SDK を呼び出すコードを説明しました。

### 6.5 AKS: WSL 上のローカル Kubernetes クラスター（Pooja 氏）

1. 事前に開始していたクラスター作成の画面を示す。ディストリビューション、バージョン、`--enable-GPU`、タイムスライシング、kubeconfig の出力先を指定している。
2. 作成中のログに、WSL provider を使っていることを示す WSL 関連のログが出ることを説明する。作成は数分で完了した。
3. 生成された kubeconfig にコンテキストを切り替える。
4. `kubectl get pods` で、Pod が正常に動いており、NVIDIA device plugin の Pod があることを確認する。
5. `kubectl get nodes` で、ノードが WSL2 ノードであることを確認する。
6. AI アプリケーションをデプロイし、ポートフォワーディングで、サービスをローカルの Windows ポートに転送して開く。
7. 「embedding arena」の画面で、複数の AI エージェントが、それぞれ別のローカルモデルで埋め込みを行い、右側のリーダーボードで順位付けされることを示す。最初は 2 つのモデルを並行実行した。
8. モデルの数は 3、さらに 4 まで増やせると説明し、そのとき Kubernetes が Pod の作成、スケジューリング、Service の公開を行うことを示す。

Postgres のコンテナーと、各 AI エージェントのコンテナーが作られ、Kubernetes がスケジューリングや Kubernetes の Job の実行を行います。ローカルの複雑な AI マルチコンテナーのシナリオでも、オーケストレーションを自分で気にする必要がない、というのが Pooja 氏のポイントです。Kubernetes の基本機能である reconciliation、リソース制御、セルフヒーリング、スケールアップ／ダウンも使えると説明されました。実行中は Windows ホストの GPU も使われていました。

### 6.6 Defender for Endpoint（Craig 氏、録画）

マシンを切り替えるため、このデモは録画で、Craig 氏がナレーションを付けました。

1. Defender のダッシュボードで、マシン一覧に **WSLC machine** があることを確認する。
2. 詳細を開き、WSL マシンとして正しくラベル付けされていること、ホストされている Windows マシン（このデモでは desktop machine）が分かることを確認する。
3. 導入手順として、endpoints からプラグインの MSI をダウンロードして展開する。動作確認には `healthcheck.exe` を実行する。ユーザーがコンテナーを起動するたびに、Defender がバックグラウンドで監視する。
4. インシデントとアラートを開く。Linux コンテナー内で、データ持ち出し（exfiltration）の可能性があるとして検出されている。
5. イベントを開き、実行していた PID とアプリケーションなどの詳細を確認する。タイムラインで、さらに詳細を追う。
6. 高度なハンティング（advanced hunting）では、Windows と Linux のイベントをまたぐクエリで、両者を関連付けられる。

### 6.7 Intune でレジストリの許可リストを設定（Craig 氏）

Craig 氏は、設定にかかる時間が分かるよう、ポリシー作成の最初から最後までを実時間で見せたと説明しています（映像が録画かライブかは、発話からは分かりません）。

1. Intune のダッシュボードで、devices、configuration の順に進み、新しいポリシーを作成する。
2. プラットフォームは Windows 10 or later、名前は「WSL settings」にする。
3. 設定の追加で「WSL」と検索すると、「Windows Subsystem for Linux settings」と「Windows Subsystem for Linux container settings」の 2 つのカテゴリーが出る。
4. コンテナー設定で、「allow WSL container」（この機能を完全に無効にできる）と、WSL コンテナーレジストリの allow list が選べる。
5. allow list を有効にし、registry.kates.io だけを許可する（音声での表記で、実際の綴りは音声認識の都合で確定できません）。これで docker.io や GitHub container registry は許可されなくなる。
6. ポリシーを完了して、ユーザーに割り当て、マシンに展開する。
7. エンドユーザーのマシンに切り替えてコンテナーを実行する。デフォルトの docker.io からの取得は、企業ポリシーでブロックされる。
8. レジストリを許可済みのものに切り替えると、取得して実行できる。

## 7. 注意点・発表者の気付き

- AKS との統合のうち、`wslc cluster create` は現時点では実験的です。AKS 側のプレビューとして提供されているのは AKS Dev CTL です。
- WSL をクラウドや Azure の管理・AI ガバナンスのモデルにつなぐ構想については、「純粋にビジョンであり、ロードマップではない」（"purely a vision and not a roadmap"）と明言されています。
- MDE との連携には Defender for Endpoint Plan 2 のライセンス（E5 相当）と、プラグインの導入が必要です。
- compose のサポートは、ロードマップの中でも先の予定です。
- Intune のポリシーは、Windows 側ではレジストリキーとして反映され、WSL service が Linux 側に渡す仕組みです。Linux VM 内には、Intune 用の常駐コンポーネントはありません。

発表では、パフォーマンスの具体的な数値（ビルド時間や描画性能など）は、virtio-fs が Plan 9 の 2〜3 倍速いという説明を除いて、示されていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 追加のライセンスやサードパーティのツールが不要で、最新の WSL にするだけで使える。
- CLI が既存の Linux コンテナーツールに似ているので、学習コストを抑えて、Linux のワークフローを Windows に持ち込める。
- GPU と NPU を Windows ホストからコンテナーに渡せる。
- Windows アプリケーションに、少ないコードで Linux のコードを組み込める。
- アプリごとに VM 境界で分離され、リソース、ネットワーク名、ボリューム名、ストレージが衝突しない。
- Intune と MDE により、Linux コンテナー内の挙動の可視化と、使えるレジストリの制御ができる。
- AKS の統合で、本番と同じ AKS のコンポーネントをローカルの開発・テストに持ち込める。

## 9. まとめ

WSL containers は、Windows 上で Linux コンテナーを CLI と API で使える機能として、一般提供になりました。デモでは、コンテナーのビルドと GPU パススルー、Windows アプリに Linux のレンダリングエンジンを組み込む API、Aspire と Intel NPU、WSL 上で動くローカル Kubernetes を見せています。エンタープライズ向けには、Defender for Endpoint による可視化と、Intune によるレジストリの allow list を示しました。内部は、アプリごとの軽量 VM、HV socket、VHD、virtio-fs で構成されます。今後は、Intel NPU、Kubernetes、USB、compose のサポートが予定されています。
