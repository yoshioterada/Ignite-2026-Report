# BRK404 What's New in Intune: Secure, Patch, and Scale

## 1. はじめに

このセッションは、Microsoft Intune の「新機能」を、**スケール（Scale）**、**露出の削減（Exposure）**、**AI エージェントのガバナンス**の 3 つの軸で紹介する 45 分のブレークアウトです。登壇した Jason Roszak 氏（Intune のプロダクトチームを率いる）が、ほぼ 1 人で話します。

冒頭で Jason 氏は、Intune が管理・保護する対象が「デバイスとアプリ」から「デバイス、アプリ、エージェント、コンテナー、モデル」に広がったこと、そして脆弱性が悪用されるまでの時間が極端に短くなったことを挙げ、人間の速度ではなく「マシンの速度」で運用できるツールを目指していると説明しました。発表されたのは、**Intune for Servers**、Intune Explorer と Custom Reporting、アプリの自動更新ポリシー、Deployment plans、インベントリに基づくフィルター、device health、脆弱性対応エージェント、エージェントの検出とソフトウェアコンプライアンスなどです。多くの項目で、画面を使ったデモが行われました。

## 3. 何に関する発表か

Jason 氏は、前年の同じ時期の Ignite では、Windows やモバイルから Mac や Frontline Worker へとデバイス管理を広げる話をしていた、と振り返りました。今年は取り組みの方向が大きく変わった、というのが出発点です。Jason 氏は、新しい緊急性と方向性を生んでいる「3 つの大きなこと」があると述べ、次の変化を挙げています（3 つ目が何かは、発話からは明確に区別できません）。

1. 管理・保護の対象が、デバイスとアプリから、エージェント的なアプリ、エージェント、コンテナー、モデルへと広がった。
2. 課題が出てくる速度が上がった。そのため、人間の速度で動くクライアント運用はもう通用しない、という考え方。

発表の構成は次のとおりです。

1. **スケール**: Intune の速度（遅延の指標）、Intune for Servers、Intune Explorer と Custom Reporting
2. **露出の削減**: パッチ適用の高速化（hot patch、アプリの自動更新、Deployment plans、フィルター、device health）、緊急対応（脆弱性対応エージェント）
3. **AI のガバナンス**: エージェントの検出、ブロック、安全な実行環境
4. 新機能の一覧スライドと、関連セッションの案内

## 4. 発表者が伝えたいメッセージ

Jason 氏が一貫して述べているのは、次のことです。

* **管理対象が増えても、手作業を増やさない。** 速度、サーバーとクライアントの統合、自然言語による操作で、少ない人数でも運用できるようにする。
* **露出管理（exposure management）が、このセッションで最も重要な部分。** 「持ち帰るのが 1 つだけなら、これ」と明言しています。
* **IT 部門は「セキュリティの話」と切り離さない。** 脆弱性を見つけるのはセキュリティ側でも、パッチの展開と緩和は IT の役割が大きい。
* **エージェントは、見つけて、許可しないものはブロックし、許可するものには安全な実行場所を与える。**

## 5. 発表内容の詳細

### 5.1 背景: 管理対象の拡大と、攻撃の高速化

Jason 氏が示した状況認識は次のとおりです。

* 昨年の同時期の統計では、脆弱性が脅威アクターに悪用されるまで平均 23 日だったのに対し、今年は「マイナス 10（日）」、つまりベンダーがパッチが出ると知らせる前に悪用される状況だと述べています。なお、後半では同じ指標を「negative 10 hours」とも言っており、単位は日と時間で揺れています。
* 今年 10 月の Windows の更新には 1,100 を超えるセキュリティ修正があり、2025 年の 1 年分より多い、と紹介しました。今後 12 か月の更新のペースは、これまでにないものになるという見立てです。
* 攻撃者が、脆弱性の発見から実際に悪用できる手段を得るまでの時間は、以前は週単位だったが、いまは 10 時間未満（ある指標より）で、脆弱性を探して悪用するエージェントを作る例も出てきている、と説明しました。

会場への質問では、今年ヘッドカウントが増えた人は 2 人だけで、残りの 98% 程度は今あるリソースで対処する必要がある、という話もありました。

### 5.2 スケール(1): Intune の速度

Jason 氏はまず、「Intune は 8 時間同期だ」という誤解を、LinkedIn での議論に触れながら否定しました。「Intune で 8 時間かかるなら、バグとして報告してほしい」と述べています。この 18 か月、製品のあらゆる部分を高速化することに取り組み、リーダーシップチームが毎日、速度のダッシュボードを見ているとのことです。

主な取り組みは次のとおりです。

* ポリシーに、配信を早める新しい「fast lane」を作った。
* 登録（enrollment）の見直し。2 時間かかるという問い合わせの原因が動的グループの同期にあったため、それを修正し、**enrollment time grouping** を導入した。
* コンプライアンスをリアルタイムのイベント駆動に変えた。

ダッシュボードの P90（顧客環境全体の 90 パーセンタイル）の値として、次の数値が示されました。

| 項目 | P90 |
| ---- | ---- |
| 登録（ユーザーが使える状態になるまで） | 15 分未満 |
| ポリシーのプロビジョニング（ボタンを押してから全デバイスに適用されるまで） | 30 分未満 |
| コンプライアンス状態の変化 | 5 分未満 |

ポリシーの反映や登録がこれより遅い場合は、サポートチケットを開いてほしい、と述べています。Head of Engineering の Sangee 氏が翌日のセッション（番号は 328 と聞こえます）で、fast lane、登録の遅延、ポリシーやアプリの仕組みを詳しく説明する予定、と案内されました。

### 5.3 スケール(2): Intune for Servers

「サーバーのサポートを求めてきた人は？」という問いかけから、**Intune for Servers を本日発表する**と述べました（会場から拍手）。

内容は、アプリ、コンプライアンス、パッチ、スクリプト、条件付きアクセス、auto patch、Entra を含む、**クラウドの Intune からのフルサーバー管理**で、「部分的なサポートではない」と強調しています。従来はサーバーをオンプレミスのドメインに参加させていましたが、これからは Entra に参加させます。デモは 6.1 に記載します。

### 5.4 スケール(3): Intune Explorer と Custom Reporting

Explorer は、この 12 か月続けてきたプロジェクトで、昨年も紹介されました。今回、次の 3 つを担います。

1. **自然言語で、Intune のデータを操作できる。** 昨年は用意されたクエリのカタログ（500 問ほど）に限られていたが、今回は Intune のすべてのデータについて質問できるように拡張した。
2. **データに対して、アクションを実行できる。** 答えを見せるだけでは助けにならない、という考え。
3. **Custom Reporting（新機能）。** 従来のレポートは手作業で、ドリルダウンもできず、多くの人がデータを Intune の外に出してスライスしていた。それを Intune の中でできるようにする。

Explorer はゼロから再設計され、当日のキーノートで Satya 氏が GA を発表した Project Perception の上に構築されています。仕組みは次のとおりです。

1. 利用者が自然言語で成果（知りたいこと）を述べる。
2. **coordinator agent** が意図を理解し、データを探す手順を計画する。KQL と Graph の両方、Intune のさまざまなシステムからデータを取得できる。
3. 結果は利用者のコンテキストで返る。**OBO + RBAC** で、Explorer は利用者自身の権限で動き、アクセス権のあるデータの答えだけを返す。裏でコーディングエージェントが KQL や Graph を呼んでいても、同じ。
4. 結果を、カスタムレポートとして保存できる。

Explorer の新しい体験は、Ignite 時点で限定パブリックプレビューです。デモは 6.2 に記載します。

### 5.5 露出の削減(1): 3 日でパッチを当てる

Jason 氏は、「この世界では、毎月、すべてのアプリ、ドライバー、OS の更新を、3 日で環境全体に展開できなければならない」と述べ、会場に準備ができているか尋ねました。平均パッチ適用日数について、14 日以内、30 日以内、60 日以内のどれか挙手を求める場面もありました。ほかにも次の 2 点を挙げています。

* **緩和**: 一部の脆弱性、特にパッチが出る前に悪用されるゼロデイには、緩和の戦略が必要。
* **リアルタイムの対応**。

IT の役割は、次の 3 つで捉えられると説明されています。

1. **最初から安全にしておく**: アプリの自動更新、hot patch、適切なベースライン、インターネット露出の制御。パッチ適用までの時間を稼ぐ初期のハードニング。
2. **日常の運用**: 最も力を入れるべき領域。パッチ適用を「週単位」から「日単位」にする。
3. **対応（response）**: セキュリティチームから、パッチ適用の SLO（期限）を示される。日常と緊急の両方を速くする。

Intune チームの問いは、「3 日でパッチを当てるために、Intune で何が成り立っている必要があるか」だそうです。

**現状の調査データ**として、商用顧客全体のパッチ適用の速さを示す 3 本の線が紹介されました。緑が最速の 10%、紫が最速の 25%、青が全体です。14 日の時点で、最速 25% は 83〜88% が適用済みで、残りの 75% は 46%。14 日を過ぎると曲線は平らになり、14〜28 日はほとんど伸びません。最後の数台がなかなか終わらない「ロングテール」の問題だと説明しました。30 日かかるのは長すぎる、とのことです。

投資は、次の 4 点にまとめられました（写真を撮ってほしいスライド）。

1. hot patch をデフォルトで有効にする。
2. アプリも OS と同じ速さでパッチできるようにする（app auto patching）。
3. より速いデプロイメントリングと、細かいグループ分けで、安全な展開を速くする。
4. **device health** で、パッチが入らない理由を見えるようにする。最後の 10〜20% を速く片付けるため。

### 5.6 露出の削減(2): hot patch / auto patch

最初の推奨は「hot patch を有効にすること」です。4 社の導入前後を比べた図が紹介されました。聞き取れた値は、17 日から 8 日、23 日から 8 日、25 日から 11 日（4 社と述べていますが、数値は 3 組しか聞き取れません）。平均で、hot patch を使うと、使わない場合の 2 倍速くパッチが完了する、と述べています。

製品の強化として、次が挙げられました。

* hot patch をデフォルトで有効にする（自動でオプトインする）。
* auto patch に maintenance windows（メンテナンスウィンドウ）を導入する。
* 承認をフローに入れる、新しいオーケストレーション機能。

この会場で、Carlos 氏と Aria 氏が 16 時から auto patch のディープダイブを行う、と案内されています。

### 5.7 露出の削減(3): アプリのパッチ（Enterprise App Management）

OS だけでなく、アプリも同じ速さでパッチする必要があります。**Enterprise App Management** は、クラウドからパッケージ済みのアプリを提供するもので、今年新たに次の機能が加わりました。

1. **supersedence によるアプリの更新と、in-app detection**: 「ユーザーがアプリを使用中のとき、プロセスを終了するのか、強制再起動するのか」というよくある疑問に応える。使用中のアプリの更新をどう扱うかを制御する新しいメニュー。
2. **アプリの自動更新ポリシー（新機能）**: 多くのアプリは IT が配布したものではない（ユーザーが Zoom や Chrome をインターネットから入れる）。Intune は管理しているアプリしか更新できなかったが、**どのように入ったかを問わず**、「このアプリは最新でなければならない」と指定でき、OS の更新と同じ技術を使って更新する。
3. **WinGet ライブラリの統合**: 現在 Enterprise App Management には約 1,000 のアプリがある（なお、同じ説明の中で "132 apps pre-packaged" とも聞こえ、数字が一致しません）。WinGet のアプリが取り込まれ、Microsoft が認定したリポジトリも作る。

目標は、OS と同じように、1 つのシンプルなポリシーですべてのアプリを最新に保つことです。デモは 6.3 に記載します。

### 5.8 露出の削減(4): Deployment plans とインベントリに基づくフィルター

アプリを更新できても、リング（Ring 1 で確認し、Ring 2、Ring 3 と進める）による安全な展開を、うまくできる方法がこれまでありませんでした。それを解決するのが **Deployment plans** です。もう 1 つは、Jason 氏が「入社以来、最も要望の多い機能かもしれない」と述べた、**フィルターをインベントリに拡張する**機能です。より細かい粒度の展開ポリシーを作れるようになります。デモは 6.4 に記載します。

### 5.9 露出の削減(5): device health

どんなに工夫しても、失敗するデバイスは必ず出ます。多くの顧客が、最後の 10〜20% を追いかけるチームを抱えている、という話から、それを製品に取り込むのが **device health** です。まず OS の信頼性レポートから始まり、クラッシュするアプリや OS の障害が分かります。パッチが入らない理由や、環境で起きていることを調べる場所になる、という位置づけです。

Jason 氏はデモを予定していたが時間がなく、16 時の Aria 氏と Carlos 氏のセッションと、翌日の Sangee 氏のセッションで見せると案内しています。つまり、このセッションでは device health の画面は示されていません。

このパートの要点は、「アプリを OS と同じ速さでパッチし、安全なリングで展開し、失敗の理由を把握して、継続的なループにする」ことです。

### 5.10 露出の削減(6): 緊急対応と Perception の脆弱性対応エージェント

日常のパッチが完璧でも、ゼロデイなどで「今日、直ちに」対応が必要になることがあります。Perception の一部として、**赤・青・緑のエージェントのチーム**が紹介されました。

| エージェント | 役割 |
| ---- | ---- |
| 赤（red） | ペネトレーションテスト、検証、問題の発見 |
| 青（blue） | 評価と優先順位付け |
| 緑（green） | 修復（remediation） |

Intune が、緑のエージェントの 1 つとして **Vulnerability Remediation Agent** を導入します。露出管理のワークフローは 3 つの部分からなります。

1. 脆弱性の優先順位付け（評価、環境への影響の評価、優先順位付け、修正）
2. 修復（パッチの迅速化）
3. パッチを当てられない場合（サポート切れのデバイスなど）の **shielding**。ネットワーク制御などで守る。

デモは 6.5 に記載します。全体としては、安全なデフォルト、強力な日常のメンテナンス、そしてそれでもすり抜ける 10% を助けるエージェント、という組み合わせだと説明されています。

### 5.11 AI のガバナンス: エージェントの検出、ブロック、安全な実行

エンドポイント上のエージェントについて、Jason 氏は 3 つのステップを示しました。

1. どのエージェントがあるかを知る。
2. 許可されていないものは**ブロック**する。
3. 許可されているものには、**安全に実行できる場所**を与える。

最初の取り組みは、**ソフトウェアインベントリの拡張**です。この新機能で、Intune が収集するアプリのインベントリは「一晩で 4 倍になる」と述べています。インベントリを、コンプライアンスと組み合わせて、アクションにつなげます。デモは 6.6 と 6.7 に記載します。

許可されたエージェントについては、デバイスの種類ごとに説明がありました。

* **モバイル**: 主要な LLM プロバイダーが Intune SDK を統合している。Claude や ChatGPT には Intune 対応版があり、コピー&ペーストの防止やアプリ起動のブロックが同じようにできる。MAM（アプリ管理）に対応している。
* **Windows**: 新しい Microsoft のコンテナー **MXC** が、エージェントを安全に実行するためのコンテナー。Intune が MXC をフルに管理し、特定のファイルへのアクセスのブロックなどのポリシーを設定できる。MXC のセッションは週の後半に Jess 氏が行う、と案内されました。
* Windows、Mac、モバイルそれぞれに、コンテナー化やアプリ管理の解決策があると述べられています（Mac の具体的な内容は発表では触れられていません）。

時間が足りず、すべてを説明できなかったとして、この 6〜9 か月の変更点をまとめた情報量の多いスライドが示されました。maintenance windows や ACME 証明書など、話せなかった項目がある、公開ドキュメントはすべて出ている、と案内しています。関連セッションは次のとおりです。

## 6. デモ・手順

デモは複数あります。録音は音声のみのため、画面の細部は分からず、以下は語られた内容に限ります。

### 6.1 Intune for Servers

1. サーバーを、オンプレミスのドメインではなく Entra に参加させる（「Entra は ServerNow にも完全対応している」という趣旨の発言があります。"ServerNow" は音声認識の都合で表記が確定できません）。
2. サーバーが登録されると、クライアントデバイスと同じ管理機能が使える。画面には、職場アカウントの接続、MDM サーバー URL、Entra テナント情報が表示されている。
3. サーバー上でメールを開こうとすると、条件付きアクセスにより、ユーザーがブロックされる。
4. Intune に移ると、サーバーが他のデバイスと並んで表示される。アクションやコマンドが使える。
5. 管理対象アプリ、構成（Wi-Fi、VPN、証明書、ポリシーなどのリソース）が、サーバーでも使える。

### 6.2 Intune Explorer と Custom Reporting

1. Explorer を開き、「デバイス上のすべての Edge のバージョン」を尋ねる。最初はパブリッシャー情報が返り、求めた内容ではなかった。
2. 質問をし直すと、横に新しいチャートが出て、Edge のバージョンが分かる。例として、157 が 9 台、146 が 3 台。
3. 「バージョン 150 未満」のものを探すよう、続けて質問する（脆弱性があり、Edge にパッチを当てる必要がある場合を想定）。欲しいデータになるまで反復するのがポイント、と説明している。
4. 結果を、カスタムレポートに保存する。カードの名前は "Microsoft Edge Burn Down"、新しいレポートを作成する。Edge をあらゆる場所で更新する作業の進捗を監視する用途。
5. 保存するとバックグラウンドでレポートが生成され、Intune に **Custom Reports** という新しいメニューが現れ、保存したカードが一覧される。
6. （デモではなく説明）複雑な条件（チェックインしていないデバイス、特定の OS バージョンでないデバイス、暗号化の有無など）の質問も、カードとして保存できる。

### 6.3 アプリの自動更新（Enterprise App Management）

1. 既存の Enterprise App Management の画面（アプリカタログ）を示す。
2. **インストール動作（installation behavior）のメニュー**で、自動更新時の挙動を選べる。プロセスを終了して強制更新するか、ログに残してユーザーに猶予を与えるかなど、細かい supersedence のルールが設定できる。
3. 新しい **automatic update** のセクションで、デバイス上のすべてのアプリを自動更新するポリシーを作る。auto patch と同様に、猶予（deferral）と期限（deadline）を設定できる。グループに割り当てて開始する。
4. 特定のアプリを除外することもできる。例として GitHub（マクロや拡張機能が壊れる懸念）。
5. エンドユーザーには、Windows Update に近い体験が表示され、アプリは OS が自動で更新する。

### 6.4 Deployment plans とインベントリのフィルター

**Deployment plans**

1. 新しい Deployment plan を作る。ここでは Google Chrome を選ぶ。
2. 展開の開始を、8 日の 1:30 に設定する（日付と時刻は聞こえたまま）。
3. ring creator の画面に、internal、IT validation、business validation、broad rollout のリングが並ぶ。リングは既存のセキュリティグループの上にオーケストレーションされる。
4. 作成すると、internal validation リングが Intune によって有効化され、展開が始まる。

**インベントリのフィルター**

1. 新しいフィルターのメニューで、インベントリデータ（BIOS の情報、暗号化、メモリなど）に対してフィルターを評価できる。
2. 新規フィルターを、従来どおり作る。ここでは、特定の日付より前に公開された BIOS バージョンを探す。インベントリのプロパティ（TPM の所有者、BIOS など）から、11 月 13 日より前の BIOS バージョンを持つデバイスをグループにする条件を作る。
3. ルール構文が表示され、グループの生成に使う実際のクエリが確認できる。
4. フィルターはチェックイン時に評価される。右端のインベントリの状態に、最新のもの、情報が保留のものが表示される。

### 6.5 Perception と Vulnerability Remediation Agent

**Perception ポータル**

1. Perception ポータルは、Explorer のデモの画面に似ているが、Intune の外の「目的地」だと説明されている。
2. Windows 更新の修復を加速する例。KB を選び、エージェントに更新の評価をさせる。
3. 評価では、その更新が修復する **715 件のセキュリティ CVE** と、そのパッチが必要なデバイスが表示される。
4. playbook で、**shield**（ネットワーク制御で悪用を防ぐ）か **patch** かを選べる。ここでは patch を選ぶ。
5. 操作しているのはセキュリティ担当者で、Intune でパッチを展開する権限がない。そのため、リクエストが発行され、operations グループに割り当てられる。
6. この後の流れは、説明として語られた。IT 側（Intune）がそのリクエストを受け取ってデバイスにパッチを展開し、完了するとセキュリティチームに「受領（receipt）」が返る。セキュリティのエージェントと管理のエージェントが連携する構図で、RBAC の制約が厳しい顧客を想定している。

**Intune 内の Vulnerability Remediation Agent**

1. "L1" と発話された場所に、新しい Perception タブがある（L1 が何を指すかは音声からは確認できません）。脆弱性対応（vulnerability remediation）を起動する。
2. 環境を分析して、アプリと OS のすべての脆弱性を見つけるよう依頼する。
3. 16 件の推奨が返り、影響スコアと、露出しているデバイスが表示される。最も重要なのは、修復を実行できること。
4. 先週話題になった Chrome のゼロデイを、エージェントが見つけ、Chrome のバージョンを直す自動修復を提案する（バグ名は "Chrome XML bug" と聞こえますが、音声認識の都合で確定できません）。
5. エージェントを実行すると、自動修復を行うか確認される。**remediation plan** が作られ、正しい Chrome のバージョンを選び、グループを作成し、安全な Deployment plan で更新を展開する。
6. **人が承認（human in the loop）** して実行する。

### 6.6 アプリインベントリ（エージェントの検出）

1. 新しいアプリインベントリのダッシュボードに、エージェントのインベントリも含まれる。Claude、Codex、Copilot が見える。自分で書いたエージェントがあれば、CLI としても表示される。
2. プリインストールのアプリ（カメラなど）を、インベントリから除外するフィルターがある。
3. 新しいアプリ単位のビュー（per-app）で、そのアプリが入っているすべてのデバイスが右側に表示される。例として、157 を拡大すると、3 台に入っていることが分かる。

### 6.7 ソフトウェアコンプライアンスとリアルタイムコンプライアンス

**ソフトウェアコンプライアンス**

1. **A365 のダッシュボード**を示す。Intune、Entra、Defender のエージェントインベントリが集まる。Claude Desktop が見える。
2. 会社が Claude を許可せず、Copilot だけを許可するという想定で、Intune のコンプライアンスポリシーに、新しい **software compliance policy** を作る。
3. ソフトウェア名を付ける（デモでは ChatGPT と読み上げ、その後、実際に選ぶアプリは Codex）。検出方法は、MSI の製品コードや package full name などから選べる。検出を今後増やす予定、とのこと。
4. アプリを選ぶと、そのポリシーに基づいてデバイスをブロックできる。
5. ユーザーが Codex を入れると、許可されていないというメッセージが出て、Intune では非準拠として表示される。現在と同様のコンプライアンスのフロー。

**リアルタイムコンプライアンス**

1. エンドユーザーが Defender のウイルス対策を無効にする。ログに、無効になったことが記録される。
2. コンプライアンスのプロセッサがイベントを検知し、チェックインを強制する。ローカルで状態を監視し、変化に応じてコンソールへのチェックインを起動して、デバイスを非準拠にする。
3. これにより、製品内でイベント駆動の、ほぼリアルタイムのコンプライアンスが実現する。ユーザーが有効にしていた設定を無効にすると、ウォッチャーがチェックインを強制して、リアルタイムで修復する、とも説明している。

## 7. 注意点・発表者の気付き

* **「Intune は 8 時間同期」は誤解**: ポリシーや登録が遅いと感じたら、バグとして報告する（Jason 氏）。
* **3 日でパッチを当てる、というのは非常に高い目標**: 発表者自身が「monumental task」と認めています。
* **アプリのパッチで、使用中のアプリの扱いが課題**: プロセス終了や強制再起動をどうするかが、顧客のよくあるフィードバック。
* **IT が管理していないアプリ**: ユーザーが入れたアプリは、これまで Intune で更新できなかった。
* **最後の 10〜20% は、チームが追いかけ続けている**: これを device health で支援する。
* **device health のデモは行われていない**: 時間の都合で、別セッションの案内になった。
* **Perception は IT 担当者向け**: セキュリティチーム専用ではない。
* **Explorer は限定パブリックプレビュー**: Ignite 時点の状況。ほかの機能の提供時期は、発表では詳しく語られていません。
* **音声認識の注意**: "Perception"、"ServerNow"、"Chrome XML bug" などは、聞こえたままの表記です。また、数値（アプリ数、hot patch の導入前後など）には、発話内で揺れや不一致があります。

## 9. まとめ

このセッションは、Intune を、デバイス管理の道具から、エージェントや高速化する攻撃に「マシンの速度」で対応するための道具へ広げる、という方向性を示しました。

1. **スケール**: Intune の速度を数値で示し、Intune for Servers（本日発表）で、サーバーとクライアントをクラウドから統合管理できるようにしました。Explorer と Custom Reporting は、自然言語で調べて、行動し、レポートを作れます。
2. **露出の削減**: 3 日でパッチを当てることを目標に、hot patch のデフォルト化、アプリの自動更新、Deployment plans、インベントリに基づくフィルター、device health が紹介されました。緊急時は、Perception の Vulnerability Remediation Agent が、人の承認のもとで修復を進めます。
3. **AI のガバナンス**: エージェントを検出し、ソフトウェアコンプライアンスで許可しないものをブロックし、許可するものは MXC やモバイルの MAM で安全に動かします。

最も重要な部分として強調されたのは露出管理です。詳細は、Sangee 氏や Carlos 氏と Aria 氏、Alim 氏と Ankur 氏のセッションで扱われる、と案内されています。
