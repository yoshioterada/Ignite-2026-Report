# BRK403 Every developer and agent needs a computer: Building with Windows 365

## 1. はじめに

このセッションは、Windows 365（クラウド上の Windows 環境である Cloud PC を提供するサービス）が、**人間の開発者**と **AI エージェント**という 2 つの利用者に向けてどのような投資を行っているかを紹介するものです。前半は開発者向けの「dev ready image」、ローカルモデルを使ったハイブリッドなコーディング、リモートコントロール、MXC（Microsoft Execution Containers）、Cloud PC のカスタマイズ。後半はエージェント向けの **Windows 365 for Agents** で、Microsoft Foundry、新しい Copilot harness、Autopilot（聞こえた表記のまま）との統合、persistent Cloud PC（常時稼働の専用 Cloud PC）、Kerberos 対応のオンプレミスアプリへのアクセスといった新発表が続きます。最後に Eido と Runbook の 2 社が、実際の利用例をデモ付きで紹介します。

エージェントに業務アプリを操作させたいが API が無い、ガバナンスをどう効かせるか、開発環境の整備に時間を取られている、といった課題を持つ開発者・IT 管理者の方に向いた内容です。

### 5.2 開発者向け Windows 365

#### dev ready image

Build で発表された **dev ready image** は、Windows 365 for developers にプリインストールされるイメージで、すぐに生産的に使える内容を最初から含みます。例として GitHub CLI、GitHub、Python、各種ライブラリやアプリが挙がりました。なお、この image は現在「GA（一般提供）」と話されています（発話は "this is actually NGA today" と聞こえ、音声認識の都合で表記が確定できません）。

Windows 365 の SKU は最大 32 仮想 CPU まであり、GPU も追加できます。そのため Cloud PC 上でハイブリッドインテリジェンスを実現でき、言語モデルを使うために Cloud PC の外へ出る必要がなくなり、推論コストを抑えられるという説明です。

#### ハイブリッドインテリジェンスと Copilot Fusion（デモ）

デモの内容は 6.1 にまとめます。要点は、**Copilot Fusion** がタスクに応じてモデルを選ぶ「モデルルーティング」を行い、Cloud PC と組み合わせるとローカルモデルを優先して使えるため、トークンの消費を減らせる、という点です。

#### リモートコントロール

Cloud PC は常時稼働しているため、リモートで操作できます。Phil 氏は、これは generally available の機能だと述べています。デモの内容は 6.2 に記載します。

#### MXC（Microsoft Execution Containers）

発表では「Microsoft execution containers」と話されており、「MXC」という略称は使われていません。本稿では便宜上 MXC と略します。

MXC は、GitHub Copilot のサンドボックスとして先ほど見せたものであり、ChatGPT と Codex が Windows 上で動くときにも組み込まれて使われている、と説明されました。Windows 365 の Cloud PC 上でもそのまま動きます。デモは 6.3 に記載します。

#### Cloud PC のカスタマイズ（まもなく preview）

プロジェクトリードが、開発者向けの Cloud PC を追加でカスタマイズできる仕組みです。プロジェクトによっては Neovim のようなアプリを、そのプロジェクトの開発者の Cloud PC にだけ入れたい場面があります。仕組みは次のとおりです。

1. IT 管理者が、まず Intune でこの機能を有効にする。
2. プロジェクトリードが「Windows 365 customization app」を得る。
3. そのアプリで、対象とするリポジトリを選ぶ。
4. GitHub のリポジトリに、必要なアプリやスクリプトを置く。
5. それがパッケージ化され、Intune を通じて、必要な開発者のマシンに展開される。
6. 例では Neovim と、いくつかの実行用スクリプトが入った。

この機能は「very soon」に preview になる予定とのことです。

#### 提供形態

これらの Cloud PC は、Windows 365 Enterprise と Flex のどちらでも入手でき、いずれも dev ready image と紹介された機能に対応しています。

### 5.3 エージェント向け Windows 365：企業が抱える 3 つの課題

ここから Swarnim 氏の担当です。企業が AI 導入で直面する課題として、次の 3 つが挙げられました。

| 課題 | 内容 |
| ---- | ---- |
| Modernization | 68% の企業が壁にぶつかる。主な理由は、レガシーで API の無い、エージェントに対応できていないシステムを使い続けていること。 |
| Governance | エージェントが意図しない行動をした事例がある。エージェントの可視性と強いガードレールが必要。 |
| Scale | 印象的なデモ、PoC、パイロットは多いが、1 つ以上の業務部門を超えてスケールできている企業は 23% にとどまる。 |

そのうえで、スケールに必要なものとして次の 3 つが挙げられました。

1. **Reachability（到達性）**：コアの業務ワークフローとアプリ（Web アプリ、デスクトップアプリ、重要な基幹業務アプリ、API の無い環境）にエージェントが届くこと。
2. **Trust（信頼）**：アプリとエコシステムが安全な環境で動くこと、エージェントが意図しない行動を取らないガードレールがあること、エージェントを追跡・監査できる agentic identity があること。
3. **Scale**：インフラ管理やキャパシティプランニングを気にせず、準備ができたときにスケールできること。遊休コンピュートのコストを心配しなくてよいこと。

これらに応えるために作られたのが Windows 365 for Agents で、**2026 年 6 月に GA** になった（今年）とのことです。

### 5.4 Microsoft 内部の事例：Business Operations

Microsoft の Business Operations チームは、digital workers をデプロイし、Windows 365 for Agents で業務を進めています。紹介された映像では次のように語られています。

- エージェントには、人間が使うのと同じ種類の OS 環境がある。監視、統制、ロックダウンができる。
- 判断と説明責任は人が持ち、エージェントは評判（reputation）を持つ。
- digital workers の活用により、プロセス全体で少なくとも **75% の human touch（人手の関与）削減**。
- Windows 365 for Agents を導入することで、さらに **20% の向上**が得られる。
- 担当者がいなくても、アプリをエージェントで動かせる。

### 5.5 利用形態の幅と Copilot Credits

顧客はさまざまな形でエージェントを導入しています。Microsoft Foundry のようなプロコード環境で高度なエージェントを作る顧客、Microsoft Copilot Studio のようなローコード・ノーコード環境を使う顧客、仕事を片付けたい一般の従業員。Windows 365 for Agents はこれらすべてに統合されると説明されました。

また、Windows 365 for Agents は **Copilot credits を消費する**ようになります。他の Microsoft AI サービスと同じ通貨で、請求とレポートを統合された体験にできる、という説明です。

### 5.8 Autopilot との統合（発表 3）

3 つ目の発表として、**Autopilot とのアウトオブボックスの統合**が紹介されました（発話は "Autopilot"。音声認識の都合で表記が確定できません）。デモは 6.6 に記載します。

### 5.9 Persistent Cloud PC（自律エージェント向け）

これまでは個々のエージェントの話でした。次に **autonomous agents（自律エージェント）**、つまり長時間のタスクを担い、コンテキストを保持する必要があり、バックグラウンドで常に動く digital workers の話になります。従業員に専用のコンピューターが要るのと同様に、自律エージェントにも専用のコンピューターが必要だというのが顧客の要望だったとされています。

そこで、**Windows 365 for Agents が persistent Cloud PC をサポートする**ことが発表されました。各自律エージェントに専用の、常に利用可能な Cloud PC を与え、オンプレミスのアプリや基幹業務アプリへのアクセスも可能にします。特徴は、それが独自の実行環境であり、エージェントのオーケストレーションを Cloud PC 上に置ける点です。LLM をローカルで動かすかクラウドで動かすかによって、エージェントランタイムに VM レベルの分離を実現できる場合がある、と説明されました。Microsoft 製でもサードパーティ製でも、好きな自律エージェントを動かせます。

デモは 6.7 に記載します。

#### Kerberos オンプレミスアプリへのアクセス

こうしたオンプレミスアプリや基幹業務アプリには、これまでエージェントがアクセスできないことが多くありました。**Windows 365 for Agents が、Kerberos のオンプレミスアプリへのアクセスを安全な方法でサポートする**ことが、この日の最新の発表でした。Swarnim 氏は、これで既存システムの modernization を気にする必要がなく、直接アクセスできるようになると述べています。

### 5.10 パートナー事例 1：Eido

Phil 氏が、Sean Patten 氏（Eido の founder and CEO）を招きました。Sean 氏によると、今回の Ignite で **Eido Build**（音声上は "IDA Build" と聞こえ、表記が確定できません）を発表します。Microsoft 企業向けの AI エンジニアリングプラットフォームで、エージェントが働く場所として Windows 365 for Agents を使っています。

10 月のリリースの成果として、次の数値が示されました。

- 238 件のチケットが、エージェントによって自身の Cloud PC 上で自動テストされた。
- エージェントが Cloud PC を使って、160 件のサポートドキュメントの作成を助けた。
- リリースサイクルを 1 週間から短縮しつつ、処理するチケット数は 4 倍（発話は "reduced the release cycle down from one week while processing four times the number of tickets"）。

Windows PC を使う理由について Sean 氏は、**顧客と同じように自社製品を使うから**だと説明します。本物の Windows コンピューター、本物のブラウザー、本物のアプリなので、テストスクリプトでは見つからないバグを、スクリーンショットという証拠付きで見つけられるそうです。

#### QA チケットの例

今月のリリースの実際のチケット（Eido の新しい experience ページ）を、QA エージェントが Windows 365 Cloud PC で受け入れ基準に照らしてテストしました。結果は 3 つが合格、1 つが人のレビューを必要としました。実際の Edge ブラウザー、実際のアプリ、実際のスクリーンショットを証拠としてテストしており、メニューを閉じるとページが画面外に押し出される UI バグも発見しました。エージェントは Cloud PC 上で修正前後のスクリーンショットを撮り、チームが次の判断をするための記録と証拠を残しました。

#### ドキュメント作成の自動化

ヘルプ・サポートセンターのすべてのスクリーンショットは、Windows 365 Cloud PC 上のエージェントが撮った実際の製品画面です。ダークモードに切り替えると、ページとあわせてすべてのスクリーンショットが変わります。全ドキュメントで 230 枚を超えるスクリーンショットがあり、製品が変わるとエージェントが再度アプリを開いてすべて撮り直します。スクリーンショットとドキュメントの作成に、チームの時間は**ゼロ時間**です。

Phil 氏は、Sean 氏のブースが 6452（AMD lounge の隣）にあると案内しています。

### 5.11 パートナー事例 2：Runbook

Runbook は、物流を中心に、フィールドサービス、金融サービス、小売などの業界の企業向けに、受注、予約のスケジューリング、請求処理といったミッションクリティカルな業務をこなすエージェントを立ち上げられるようにしています。こうした業務では、ERP に注文を作る、スケジューリングシステムに予約を入れるといった実際の操作が必要で、ここで「エージェントがシステムにアクセスできない」という壁に当たります。API は存在しないか、あっても作るのに数か月かかるため、「ポータルを開いて人のようにコンピューターを使えばよいのでは」と考え、Windows 365 for Agents を使った computer use エージェントを構築しました。

#### 全国規模の貨物ブローカーでの運用例

ライブで稼働中のワークフローとして、全国規模の貨物ブローカー向けの**運送会社向けの受注（inbound carrier sales）ワークフロー**が紹介されました。デモは 6.9 に記載します。

#### 効果

## 6. デモ・手順

このセッションには、複数のデモがあります。画面の細部は音声からは確認できないため、語られた内容の範囲で書きます。

### 6.1 dev ready image と Copilot Fusion（Phil 氏）

1. セットアップ直後の dev ready image を見せる。32 仮想コアの CPU を、Task Manager で確認する。
2. Start メニューで、プリインストール済みのアプリを見せる。Git、Copilot、GitHub Copilot、そしてイメージにあらかじめ入った新しい「intelligent terminal」。
3. VS Code に、あらかじめ入っている拡張機能（Python 関連を含む）がある。「これは out-of-the-box で、全員がこの状態になる」と説明。
4. GitHub Copilot で環境を設定し、sandboxing の機能をオンにして、コーディングエージェントが意図しないものにアクセスできないようにする。
5. 組織の経費を管理して支払う「expense app」を題材に、サインインの体験が無いことに気づき、コーディングエージェントにその作成を依頼する。
6. エージェントは Copilot Fusion（モデルルーティング）を使い、このとき「GPT-6 Luna」を選んで、認証ページを作成する。画面右側には、推論がどこで行われているかを示す、Vibe coding で作った表示アプリがあり、このとき Frontier モデルが使われていることを示す。
7. 追加されたサインインページを試し、サインインできたことを確認する（右上に表示されるが、文字は小さい）。
8. 次に「commit と PR を作って、すべてのチェックを終えて」と依頼する。このとき「Frontier モデルは使わず、可能ならローカルモデルを使って」と指示する。右側の表示アプリは local first になったことを示し、ローカルモデルで commit を実行する。これによりトークンを節約できた。
9. アプリで複数の人が経費を二重に支払われていることに気づき、「これを直して」と依頼する。今度は Copilot Fusion が Frontier モデルの「GPT-6 Terra」に戻る。競合状態（race condition）の解決にはより多くの能力が必要だからで、修正が完了する。

Phil 氏は、Copilot Fusion と Cloud PC を組み合わせてハイブリッドインテリジェンスを使うことでトークンコストを減らせる、とまとめています（モデル名「Luna」「Terra」は聞こえたとおりで、音声認識の都合で表記が確定できません）。

### 6.2 リモートコントロール（Phil 氏）

1. 同じ Cloud PC を使う（デモの都合で画面右側に表示）。その上で GitHub Copilot CLI を使う。
2. CLI で「remote control」をオンにする。
3. 画面左の自分のスマートフォンから、その Cloud PC をリモートで操作する。
4. 「I love my Windows 365 Cloud PC と表示する Python アプリを作って」と依頼する。

Phil 氏は、出先で子どもをチアの練習に連れて行く途中でもアプリを作れる、と述べています。

### 6.3 MXC のデモ（Phil 氏）

Windows 365 Cloud PC 上の execution container のデモです。

1. クライアント向けの財務レポートを作る。使うファイルは一部だけにしたい（Phil 氏は、自社が上場企業であるため）。
2. まず、サンドボックスにフォルダー内のファイル全体へのアクセスを与える。そこには Q4 のファイルもあるが、Q4 へのアクセスは拒否（deny）する。Q4 はまだ公表していない数字のため、これが重要だと説明。
3. 「この顧客が欲しがっているレポートとして、Excel ファイルと Word 文書を作って」と依頼する。
4. エージェントは Q4 を除外すべきだと認識し、確認を求めてくる。「はい、Q1 から Q3 だけにして」と承認する。
5. 制限に沿った正しいレポートが作られ、Q1〜Q3 だけが含まれている。

Phil 氏は、MXC は GitHub Copilot に組み込まれており、Windows 365 上でうまく動くと述べています。

### 6.4 Microsoft Foundry で Cloud PC をエージェントに与える（Swarnim 氏）

プロコードの Foundry 環境で、経費報告書を提出する expense agent を作る流れです。

1. Microsoft Foundry CLI でエージェントを初期化し、toolbox に紐づけて、必要な機能（computer use を含む）を与える。画面上で、それが取得された箇所がハイライトされる。
2. Foundry CLI から、そのエージェントをデプロイする。成功する。
3. Foundry の Web ポータルに切り替え、agent の tool セクションで、エージェントの computer use を有効にする。
4. プロンプトで「経費報告書を作成して」と依頼する。
5. エージェントは必要なときに Cloud PC をチェックアウトし、computer use を実行する。画面右側で、エージェントが操作を引き継ぐ様子が見える。
6. 必要なら、ユーザーが Cloud PC の制御を取り、エージェントを誘導することもできる。

### 6.5 新しい Copilot harness（Swarnim 氏）

1. 新しい Copilot harness の画面（右側に表示）。「Go for Launch」という、ローンチの計画と成果物の追跡のためのエージェントを作成する。
2. 指示はシンプルなテキストで書く。コーディングの経験が無い人でも、エージェントビルダーになれると説明。

### 6.6 Autopilot（Swarnim 氏）

1. 「Ignite に行くための計画を立てて。航空券の予約、ホテルの予約など全部を含めて」と依頼する。

### 6.7 Persistent Cloud PC のデモ（映像）

OpenClaw を使った Maya さんの例です（デモ映像の中で、トランスクリプトには「OpenClaw」と聞こえる部分と、後述の Intune 画面で「Open Cloud」と聞こえる部分があります。いずれも音声認識の都合で表記が確定できません）。

### 6.8 Intune で persistent agent 用のポリシーを作る（Swarnim 氏）

IT 管理者向けの手順です。数回のクリックで、各自律エージェント（digital worker）に persistent Cloud PC を提供できる、という説明です。

1. persistent agent 用のポリシーを作成する。
2. 「persistent Cloud PCs」を選ぶ。
3. 「agent runtime」を選ぶ。デモでは OpenClaw（トランスクリプトでは "Open Cloud" と聞こえる）を選ぶが、他のものも選べる。

### 6.9 Eido のデモ（Sean 氏）

5.10 に書いた内容のとおり、実際のリリースの QA チケット（新しい experience ページ。3 件合格、1 件は人のレビューが必要。メニューを閉じるとページが画面外に押し出される UI バグを、修正前後のスクリーンショット付きで検出）と、ヘルプ・サポートセンターのダークモード切り替えによるスクリーンショットの一括更新（230 枚超）を画面で見せました。

### 6.10 Runbook のデモ（Varun 氏）

通話の録音と、その後のエージェント操作を流しました。

1. AI の voice agent（「negotiator」）が電話に出る。デモの通話では、運送会社側が Lebanon から Wixom への荷物（load）について電話をかけ、コンプライアンスの確認や条件の確認（"1050 all in"）を経て、1050 で合意し、レート確認書（rate con）を送るメールアドレスを聞き取る。
2. 口頭での予約が済んだので、次に rate confirmation のメールを実際に送る必要がある。Cloud PC が立ち上がり、エージェントが操作する。
3. エージェントはまず TMS（運送管理システム）にサインインする。**LLM は、安全な認証情報を見ることがない。**
4. サインイン後、運送会社が電話してきた注文を探して特定する。
5. rate confirmation の PDF を生成し、ファイルシステムに保存する。
6. 保存後、エージェントはそれを運送会社へ送信する。

この最後の工程には、使える API が TMS に無く、computer use エージェントが必要だったと説明されています。

## 7. 注意点・発表者の気付き

- **API の無いシステム**：Runbook の事例では、顧客の TMS に使える API が無く、他の方法では API の構築に数か月かかる、というのが出発点でした。computer use で人と同じ操作を行う方法で、本番まで 2 週間で到達した、と説明されています。
- **機能の提供状況**：Windows 365 for Agents は 2026 年 6 月に GA。persistent Cloud PC と Foundry との統合は private preview で、public preview は来年初めの予定。Cloud PC のカスタマイズ機能は「very soon」に preview。
- **認証情報の扱い**：Runbook のデモでは、LLM が安全な認証情報を見ない形でサインインすると説明されています。
- **人が介入できること**：デモを通して、ユーザーはいつでも Cloud PC の制御を取り、エージェントを誘導できる点が繰り返し示されました。
- **ファイルへのアクセス制限**：MXC のデモでは、公表前の Q4 ファイルへのアクセスを拒否する例が示されました。
- 発表では、Windows 365 for Agents の料金体系の詳細（Copilot credits の消費量など）には触れられていません。

## 9. まとめ

このセッションは、Windows 365 を「開発者のためのコンピューター」と「エージェントのためのコンピューター」の 2 つの面から説明しました。開発者向けには dev ready image、Copilot Fusion とローカルモデルによるトークン節約、リモートコントロール、MXC、Cloud PC のカスタマイズ。エージェント向けには、API の無い業務アプリへ届く、信頼できる環境として Windows 365 for Agents を位置づけ、Foundry、新しい Copilot harness、Autopilot への統合、persistent Cloud PC、Kerberos オンプレミスアプリへのアクセスが新しく発表されました。

Microsoft 社内、Eido、Runbook の事例は、いずれも数値付きで示され、特に「API を待たずに computer use で本番化した」点が強調されています。興味のある機能（persistent Cloud PC と Foundry 統合）は private preview 中で、QR コードから連絡すれば設定の支援を受けられると案内されました。
