# BRK389 Put Local AI to Work: Offload Coding Tasks to run locally on Windows

## 1. はじめに

このセッションは、AI を使ったコーディング（agentic software engineering）を、クラウドだけでなく **Windows のローカル環境にも広げる**ための考え方と、そのための具体的なハードウェア・ソフトウェアを紹介するものです。登壇者の言葉でいえば「ローカルコーディング」の話です。

話は 3 つの章で進みます。最初は「なぜローカルコーディングが必要なのか」、次に Windows 11 のクライアント端末（RTX Spark など）でどこまでできるのか、最後にそれを機能チーム単位や、1 兆パラメーター級のモデルまで広げる方法です。

発表の中心にあるのは、**「適切な知能を、適切な場所に、適切な価格で置く」**という考え方です。クラウド、チーム単位で運用する推論サーバー（登壇者は token factory と呼びます）、手元の PC。この 3 層を「どれか 1 つ」ではなく「組み合わせ」で使うことが、一貫した主張でした。

デモは多めで、GitHub Copilot から Surface のノート PC 上のローカルモデルを動かす 3 つの実演、USB4 で PC 同士をつなぐ RDMA の動画、Redmond のラボにある推論クラスターへの接続デモ（こちらは時間内に完了しませんでした）が紹介されます。

Neil 氏の出発点は、顧客の現場で聞いている共通の状況です。AI コーディングツールで事業プロセスやソフトウェア開発のやり方を作り変えている企業では、CFO のもとに 3〜6 四半期続けてクラウドのトークン料金の請求が届いています。そして CISO や CTO には、CFO から「エージェント型のコーディングから価値を出す方法は分かった。今度は効率よく使ってほしい」というメッセージが届く、という話です。

このときに顧客が問うのが、「適切な知能を、適切な場所に、適切な能力と、組織に必要なコスト構造に見合う価格で置くには、どうすればよいか」です。登壇者は、この問いへの答えを次の 3 つに分けて説明しました。

- **適切な場所**：規制の環境、知的財産をどれだけ守りたいか、パブリッククラウドに出したいかどうか
- **適切な能力**：社員の仕事に必要な「モデル、ハーネス、ハードウェア」の最小の組み合わせ
- **適切な価格**：自社のコスト構造。AI の計算量が増えるほど収益も増える企業は、次の 100 万トークンの限界コストを気にしない一方、限界コストを強く気にする企業もある

そして Microsoft の目標は、クライアント、クラウド、token factory のすべての層でデバイスとサービスを用意し、各社がそれぞれの最適解にたどり着けるようにすることだと説明しています。**ハイブリッドインテリジェンスは「and」であって「or」ではない**、という言い方もされました。100% クラウドだけ、あるいは 100% ローカルだけという顧客はまれで、大多数は、クラウド、データセンター、社員の端末にまたがる本当のハイブリッドになる、という見立てです。

## 5. 発表内容の詳細

### 5.1 ローカルコーディングが必要になる理由と、3 つの層（Neil 氏）

ローカルコーディングの推論には、3 つの層があると説明されました。

| 層 | 内容 |
| --- | --- |
| クラウド | すべての始まりの場所。フロンティアモデルと、伸縮自在な計算資源がある |
| token factory | 世界各地の支店や社内のデータセンター（発話では corporate databases と聞こえます）に置き、大規模にモデルを動かす、あるいはソフトウェアエンジニアのチーム全体にサービスを提供する |
| 端末 | ノート PC や小型デスクトップの形をした、ソフトウェアエンジニアリング向けに作られた新しい高性能デバイス |

Microsoft としては、小型・軽量の Windows 11 端末から、社内データセンターで動かす大型サーバーまで、ハードウェアの品ぞろえを用意するという位置づけです。クラウドは Azure、データセンターには Windows と Azure Local の token factory があります。後者は、ノート PC やデスクトップでは到底動かせない、はるかに強力なモデルを社員にまとめて提供できます。さらに、Windows 11 の新しい端末は、従来のノート PC では不可能だった大きさのモデルを動かせる、と紹介されました。

ここで強調されたのが、**層ごとにツールを変えなくてよい**ことです。同じモデルを、同じカタログから、同じライフサイクル管理のもとで、Microsoft Foundry から利用できます。自分のモデル、ハーネス、ランタイムを持ち込むことも可能です。

もう 1 つが、管理と統制です。社内データセンターに置いたエージェントは、機密データを持つ SQL データベースのすぐそばで動きます。そこで「エージェントが何をしているかを把握し、強い制御をかけたい」というのが、顧客の次の質問になります。これに対する Microsoft の答えが、次の 2 つです。

- **Agent 365**：エージェントに ID を与えます。「このエージェントは Neil の延長」あるいは「データセンターで隣に置かれたアプリケーションやサービスの延長」と位置づけられます。
- **Microsoft Execution Containers（MXC）**：エージェントに対する強制の仕組みです。たとえば「このエージェントはコードベースのこの部分のコーディング用で、アクセスできるファイルはこれだけ」、あるいは「このエージェントはエアギャップ環境にいて、ネットワークには一切触れさせない」といった制御をかけます。

これらのガバナンスの機能を、3 つの層すべてで一貫して使えるようにする、というのが方針です。

### 5.2 デモの前提：端末とモデル（Lei 氏）

Lei 氏は、日々コーディングエージェントに頼む作業を挙げています。リポジトリには何があるか、仕様書には何が書いてあるか、ログを掘って調べる、PR をレビューする、といった作業です。これらのすべてにフロンティアモデルが必要なわけではなく、不要なのにフロンティアの料金を払いたくない、という問題意識です。

GitHub Copilot では、すでに多くの選択肢があります。CLI、GitHub Copilot app、VS Code のどれで作業するか、クラウドのどのモデルを使うか、さらに BYOK（自分のモデルの持ち込み）もネイティブに対応しています。**ローカル推論は、そこに「モデルのスタックをどこで動かすか」という選択肢を 1 つ足す**ものだという説明です。規模や深い推論が必要なときのクラウドは変わらず使え、手元の PC は、慣れた Copilot の中の選択肢の 1 つになります。

デモに使った端末は、NVIDIA の新しい RTX Spark アーキテクチャを搭載した Surface Ultra のノート PC です。CPU と GPU で共有する **128 GB のメモリ**を持ち、これがデモを可能にしています。使うモデルは **57 GB** で、メモリに全部載っています（タスクマネージャーのメモリのグラフで確認できる、と説明されました）。

Copilot app の左側には、プロジェクトとセッションが並びます。各セッションは、リポジトリのコピーで作業するため、エージェントが作業中のツリーを荒らすことはありません。モデルの選択画面には、クラウドのモデルに加えて、**MAI Code 1.1 Flash on Device** というローカルモデルが出ます。Microsoft 製で、Windows ML のプロバイダー経由で GPU 上で動きます。そのほか、オープンコミュニティ発の小さめのモデル **FLINT** も選べます（Recursive という会社のものと聞こえます。音声認識の都合で表記は確定できません）。管理されたモデルカタログは、今後さらに広げる予定です。モデルの配布、セットアップ、ランタイムスタックは、プロバイダー側がすべて面倒を見ます。

### 5.3 デモ 1：Copilot Fusion に任せる

1 つ目は「Copilot に決めてもらう」使い方です。ここで使うのが **Copilot Fusion** で、モデルルーターです。タスクの複雑さを理解して、適切なタスクを適切なモデルに振り分けます。Standard の段階では、ローカルの MAI モデルが、Fusion が選べる選択肢の 1 つになります。

Fusion は、リクエストごとに次の処理をします。

1. タスクの複雑さをスコアリングする
2. それに合うモデルを選ぶ
3. オーケストレーションのパターンを選ぶ

パターンには次の 3 つがあります。

| パターン | 動き |
| --- | --- |
| 単独（single） | 1 つのモデルにタスク全体を任せる |
| カスケード（cascade） | 安価なモデルが先に答え、必要な場合だけ強いモデルが加わる |
| クリティーク（critique） | 1 つのモデルが答えを下書きし、別のモデルが欠陥を探して、最初のモデルに見直しと手直しを依頼する |

デモのコミットメッセージ生成は複雑さが低いので、タスク全体がローカルモデルに渡されました。**現時点の Fusion Standard では、ローカルモデルはこの使い方です。今後は、カスケードやクリティークのような高度なパターンにもローカルモデルを組み込む方向で進めている**、とのことです。なお、大きなリファクタリングのような作業を頼めば、クラウドのモデルが選ばれる、と説明されています。

### 5.4 デモ 2：自分で決める（カスタムスキルとエージェント）

2 つ目は「自分で決める」使い方です。主モデルとして、自分でクラウドの **GPT-6.1-So**（音声認識の都合で表記が確定できません）を選びます。判断力に優れた最先端のモデルです。ただし、数千行の変更差分を読むのは、判断ではなく「大量の宿題」であり、大量のトークンを使う作業です。そこで「宿題はこのノート PC でやり、判断はクラウドで下し、2 つのモデルを連携させる」構成にします。これを実現するのが、**カスタムスキルと、ローカルのワーカーとして働くカスタムエージェント**です。

**スキル**は「作業指示書」にあたり、主モデルが従う手順書です。

- ステップ 1（ゲート）：主モデルが 1 つのコマンドで全部できるなら、引き継がない
- 重い読み込み作業（今回は 25 KB を超えるもの）のときだけ引き継ぐ
- ステップ 3：実際の引き継ぎ。入力と出力の形式を定義する
- ステップ 5：変更履歴で何を見るべきかという、自分用のレシピ（実践的なコツ）を追加した

Lei 氏は、何をさせたいかが明確なら、自分用のレシピをスキルやカスタムアクション、カスタムエージェントに加えられる、と補足しています。

**エージェント**は、仕事を実際にこなす「請負業者」にあたります。使えるツールは、読む、検索する、編集する、コマンドを実行する、です。**他のエージェントは呼び出せません**。ローカルのエージェントが無限ループに入るのを防ぐためです。まとめると、「スキルは、仕事をどこで実行するかを決め、エージェントは、何をしてよいかを定義する」という関係です。

ここで使った例は、Awesome Copilot（GitHub Copilot のカスタマイズ、スキル、エージェント、プラグインを集めたコミュニティ主導のリポジトリ）でも公開すると説明され、ローカルモデルがうまく動く場合は、自分のカスタムエージェントを作って公開することも勧められました。

結果として、エージェントは **12 月 1 日に起きる 3 つの破壊的変更**を報告しました。

- 返金（refund）に理由が必須になる
- webhook の署名が変わる
- カスタムのメールフィールドが変わる

Cyber Monday の返金が殺到する前に気づけてよかった、と話しています。

### 5.5 MAI モデルをノート PC に載せるための工夫

Lei 氏は、スライドを使って、MAI モデルをノート PC に載せるために行った作業を説明しました。これらは単発の工夫ではなく、他のモデルにも同じ手法を使って、Windows ML のプロバイダー上のローカルモデルのカタログを広げられる、と位置づけられています（先ほどの FLINT も同様）。

MAI のモデルは **1,380 億パラメーターの MoE（Mixture of Experts）** で、多数の小さな専門家モデルから成り、各実行で少数だけが活性化されます。そのため高速で、ローカルの計算に向いています。ただし落とし穴があります。プロンプトごとにどの専門家が使われるかが分からないため、**すべての専門家をメモリに載せておく必要がある**のです。フル精度では 276 GB となり、ノート PC のサイズにはなりません。そこで、次の 3 つを行いました。

| 課題 | 対策 | 効果 |
| --- | --- | --- |
| サイズ | 混合精度の量子化（精度が重要な部分は細かく、それ以外は粗く保持する） | 約 57 GB に縮小（タスクマネージャーで見えていたサイズ） |
| 速度 | 小さな「ドラフトモデル」が数トークン先を予測し、大きなモデルがそれを確認する | 約 2 倍高速 |
| メモリ | sliding window attention。ほとんどのレイヤーは会話履歴の直近部分だけを保持し、1 つのレイヤーが履歴全体を保持して全体像を失わないようにする | メモリ使用量を合計で約 80% 削減 |

> 補足：発話では、sliding window attention の説明が「ドラフトモデルのレイヤー」の話として語られています。どのモデルのレイヤーを指すのかは、音声からは確定できません。

### 5.6 デモ 3：クラウドを使わない完全ローカル

3 つ目は、クラウドが一切関わらない構成です。今度はアプリを閉じて **CLI** を使い、「そういう選択肢もある」ことと、ターミナルが好きだから、という理由が示されました。モデルは MAI を選びます。

Lei 氏は、Wi-Fi を切って「ローカルで動いている」と見せる実演はよく見かけるが、それより良い証明方法がある、と話しています（後述します）。

設定は、オンコールの開発者の話です。木曜の朝 9 時 22 分、前の晩から何が壊れたかを調べなければならない。チェックアウトの処理でスロットリングが起き、問題が出ている。リポジトリにはアクセスログとクラッシュレポートがあり、これをローカルで動くモデルに調査させます。

質問は次の 2 つで、順に実行されました。

1. **影響を受けているクライアントは誰か**：チェックアウトを 10 回以上叩いて 429（スロットリング）を受けているクライアントを探す。モデルがログの形式を読み取り、PowerShell のコマンドを送ってログを読む。ログはこの端末の中にあり、端末の外には出ない。結果は **6 クライアント**。ログには、わざと罠をいくつか仕込んであった。その例として、429 がちょうど 9 回のクライアントと、429 は多いがチェックアウトではなく検索のクライアントが挙げられ、どちらも結果に出なかった。
2. **今朝の 40 件のクラッシュレポートから、どこで失敗しているかを調べる**：自分のコードのスタックの最上位を特定させる。この処理は数分かかるため、先に実行してあった結果を表示した。`payment client parse response` が 40 件中 **14 件**に関わっており、Black Friday の直前に決済連携が壊れていることが分かった。そこで、朝会でチームに渡すための簡潔なブリーフを書かせた。

「ローカルで動いた」ことの証明は、**usage の表示**でした。このアクティブなセッションの usage を見ると、リストにあるモデルは MAI だけで、読み取りタスクのため、読み込みトークンが大量に出ています。

さらに 2 点が追加されました。

- ローカル AI のテレメトリーを、**Viva Insights** のような画面で見られるようにすることが、近々予定されている。これにより、テナント全体の利用状況と導入状況、ROI の指標を、詳細なダッシュボードで把握できるようになる。
- Copilot app は、この一連の作業を**自動化**できる。プロンプトをコピーして時刻を決め、たとえば毎朝 7 時に実行する。人がノート PC の前にいる必要はない。解析が 4 分で終わろうが 8 分かかろうが誰も気にせず、コストはかからず、ログは端末から出る必要がなければ出ない。人間は、できあがったブリーフを読んで、次を決めるだけ（human in the loop）。

3 つのデモのまとめは、「Copilot Fusion に決めさせる」「自分で決める」「シナリオが合えば完全ローカルにする」の 3 つで、能力、コスト、データのプライバシーによる使い分けだと説明されました。

### 5.7 RTX Spark for Windows の端末と対応チップ

Lei 氏は、紹介した Surface Laptop Ultra が最大 128 GB のメモリ（CPU と GPU で共有）と、最大 1 ペタフロップスの AI 性能を持つ、と説明しています。そして最も力を込めたのが、**これが 1 台のノート PC の話ではない**点です。RTX Spark for Windows は新しいカテゴリの端末で、ASUS、Dell、HP、Lenovo、MSI、Microsoft Surface といった OEM と進めています。

さらに、**この日、AMD の端末（Ryzen AI Max 300 / 400 シリーズ）への対応を発表**しました。これにより、GitHub Copilot のマネージドなローカルコーディング体験を、ハードウェアベンダーを選んだうえで利用できます。すでに付き合いのある PC メーカーのまま、「すでに管理している PC 群にそのまま収まる、ただの Windows PC」として使えるというのが、その理由です。

### 5.8 モデルが 1 台に収まらないとき：RDMA over USB4

次の問いは、「モデルが 1 台のクライアントに収まらない場合」です。通常の次の段階はワークステーションですが、スペクトラムの上では大きな跳躍に感じられます。そこで、その中間の選択肢が紹介されました。各 PC が高性能でも、大きなモデルには少しメモリが足りない、という場合です。

それが、**RDMA（Remote Direct Memory Access）over USB4** です。すでに持っているかもしれない 2〜4 台の高性能 PC を USB4 でつなぎ、**1 つのメモリプールを共有して 1 つのモデルを動かせます**。この機能が、**開発者プレビュー**として提供されます。

- AMD Ryzen AI Max の PC 3 台を机の上でつなぐと、1 つのモデル用に約 **288 GB の GPU メモリ**が得られる
- RDMA のアダプターもスイッチも不要で、USB4 のケーブルだけでよい
- Intel Core Ultra シリーズ 3 の PC でも動く
- 標準の Windows の RDMA なので、アプリは、リンクが USB4 だと知る必要がない

仕組みは次のとおりです。アプリやフレームワークは、データセンターのネットワークアダプターですでに使われている **Network Direct API**（Windows の RDMA API）を呼びます。そこに、**RDMA over USB4 プロバイダー**という新しい層を 1 つ加えます（これはオープンソース化されます）。更新された inbox の USB4 ドライバーの上で動くため、セットアップは簡単です。配線は**フルメッシュ**で、PC の各ペアの間に直接 1 本のケーブルが必要です。つまり、各 PC は、他の PC の数だけ USB4 ポートが必要になります。

動画では 2 つの構成が示されました。

1. AMD の PC 3 台のクラスター。Qwen3-235B のモデルを読み込み、3 台の GPU メモリが埋まる。Llama.cpp がクラスターをローカルのエンドポイントとして提供し、3 台の GPU がすべて動いて出力を生成する。「性能はかなり良好」と説明され、数値は画面に表示された（読み上げられていません）。
2. Intel Core Ultra シリーズ 3 の PC 3 台。モデルは GPT-OSS-120B で、1 台では載らない大きさだが、3 台で動かせる。こちらも入出力の数値が画面に表示された。

試す方法は次のとおりです。**開発者プレビューは、翌日にすべての Windows Insider へ展開されます**。最初は PC 2 台とケーブル 1 本から始められ、レジストリの設定を 1 つ有効にします。そのうえで、GitHub からオープンソースのプロバイダー、サンプル、Llama.cpp のテストベッドを入手します。リンクはスライドに表示されました。「限界まで使って、壊してみて、フィードバックをください」と呼びかけています。

### 5.9 token factory と DGX Station for Windows（Neil 氏）

チームとエージェントがこの規模のキャパシティを共有する段階になると、ハイブリッドインテリジェンスのスペクトラムの上で、「右に進む」ことになり、token factory の出番です。

Neil 氏は、token factory のモデルを、オンプレミスのインフラで、計算、ストレージ、ネットワーク、データベースの提供で広まっているパターンと同じだと説明します。会場のシステム管理者や IT ディレクターに「社員の机ごとにストレージクラスターを置いていますか」と問いかけ、**集中させるのは、規模の経済と性能の経済が得られるから**だ、という論理です。

Microsoft のローカルコーディング向けデバイスは、この考え方で設計されています。RTX Spark の PC、RDMA と USB4 によるクラスター化、そして上限には **DGX Station for Windows** があります。Microsoft、NVIDIA、6 社の Windows OEM の協業による端末です。

| 項目 | 内容（発言のまま） |
| --- | --- |
| メモリ | 748 GB のコヒーレントメモリ |
| GPU / CPU | Blackwell 300 GPU（音声認識の都合で表記が確定できません）、72 個の Grace コア |
| できること | 1 兆パラメーターを超えるモデルを動かせる。2,000〜4,000 億パラメーター級のモデルを、数十人の社員に同時に提供できる |
| 形状 | ワークステーション形状で、ラックマウントも可能（サーバールームやデータセンターにも置ける） |
| OEM | ASUS、Dell、Gigabyte、HP、MSI、Supermicro の 6 社 |

プールへの社員の出入りが柔軟で、時間とともに拡張できる、という点も利点として挙げられました。そして、これらはすべて**同じ Windows** で動き、**同じ Agent 365 で統制**され、セキュリティの制約は **MXC でコンテナー化**され、推論ランタイムは、RTX Spark、Windows 11 のクラスター、DGX Station のすべてで、**Microsoft の inbox 推論スタック**です。

Neil 氏は Redmond のラボで、これらを実際に動かしており、エージェント型ソフトウェアエンジニアリングの作業に日常的に使っています。負荷がかかった状態で、**1 秒あたり 4,000 を超える出力トークン**のスループットを、日常的に確認しているそうです。ただし、これは動かすモデルと、社員がそのとき行っている作業によって決まる、と断っています。DGX Station for Windows 向けの顧客エンゲージメントのチームにつながる QR コードも示されました。

### 5.10 Insight の事例（Parker Johnston 氏、Will Pocknell 氏）

Neil 氏は、Insight の 2 人を「Station のデバイスを世界で最初に手にした人たちの一部で、デバイスのラインアップ全体で何ができるかを試している」と紹介しました。

**Parker 氏**（Agentic Field CTO）は、Microsoft が実際のエンタープライズの業務でローカル AI コーディングがどこまで通用するかを確かめたいとき、早い段階で Insight を巻き込んだ、と話しています。

- 開発者は Surface Laptop Ultra をプロジェクトで使い、見つけたことを Microsoft に伝えている
- このノート PC は、**1,400 億パラメーターのモデルを端末上で直接動かせる**
- GitHub Copilot に自前のルーティングを設定し、ローカルのモデルのエンドポイントを指すようにしている。作業を端末に残すか、フロンティアのトークンを使うかを、自分たちで正確に決める
- ローカルの計算力は、ユニットテストの作成、新機能の開発、そして「hypervelocity engineering」で企業への機能提供価値を高めることに使う。クラウドの従量課金のトークンに触れずに、**一日中**動かせる
- 今週、Copilot のエージェント実行を、フロンティアモデルのクラウドランナーから、Microsoft の MAI Code 1.1 Flash（発話では "AI Code 11 Flash" と聞こえます）を使う端末上のローカルランナーに切り替えたところ、ノート PC が自分の GPU だけで **45 分間**やり切った
- クラウドは、業界のベストプラクティスの詳しい調査や、複数リポジトリにまたがる知識の取り込みなど、本当にフロンティアモデルが必要な作業のために引き続き使う

Surface Ultra が変えたこととして、Parker 氏は 3 点を挙げました。

1. **コードが端末に残る**（顧客の知的財産を扱う場合に最も重要）
2. API 呼び出し用のモデル仕様の更新のような日常的な作業に、クラウドのトークンを使わなくなった
3. ルーティングを自分で設定したため、何がどこで動くか、そのセキュリティを正確に把握している

**Will 氏**（Director of Cybersecurity）は、新しいデバイスについての最初の質問が「マネージドなエンタープライズ環境で通用するのか、デモの中だけなのか」だと話します。そこで、クラウドのエージェントと同じ **Agent 365 のセキュリティと管理の制御**を、これらのノート PC にもかけました。どこでワークロードが動いても一貫したガードレールを確保するためで、得られた知見は Microsoft のエンジニアリングチームに送り返しています。「**AI をローカルで動かしても、ガバナンスの外に出るわけではない。境界の場所が変わるだけ**」という言い方でした。

ノート PC は個人のデバイスです。チーム全体が、より大きなモデルや複雑なハードウェアを必要とするときに登場するのが DGX Station で、ローカル AI を「1 人の開発者の取り組み」から「机のそばでチーム全員が使う共有システム」に変えます。Windows が載っているため、Defender、Intune、企業が信頼してきたポリシー群で、他の端末と同じように管理できます。Insight が顧客と交わしている会話は、「**ノート PC から始め、チーム向けに DGX Station に拡張し、最も大きなジョブだけを必要に応じてクラウドに送る**」というものです。

さらに Parker 氏は、デバイスの選択は簡単な部分で、その下にある次の問いのほうが難しい、と述べています。何が本当に社外に出る必要があるか。コードとデータはどこに置くべきか。エージェントが動き出したあと、誰が見張るのか。これらを正しく決めれば、ノート PC と Station のそれぞれに明確な役割ができます。実際に動いているところは、Insight のブース（526 番）で見られるとのことです。

### 5.11 推論の「ファブリック」：Microsoft Foundry on Windows Server（Neil 氏）

Neil 氏は、DGX Station が 2,000 億パラメーターのモデルのインスタンスを 64 個、同時に動かせる場合でも、大きな組織には足りないことがある、と述べています。推論を大規模に展開するエンタープライズの顧客は、ネットワーク、計算、ストレージ、データベースですでにおおむね解決した課題に直面しています。**推論ファクトリーのフリートを、それを「ユーティリティ」として使うエンドユーザーのアプリケーションから、抽象化する**必要がある、という問題です。

- 分散した企業では、DGX Station のような端末を支店に置き、その拠点のチームに推論を提供する。チームの GitHub Copilot に、新しいモデルが現れる
- 集中型の企業では、社内データセンターにすでにあるストレージ、ネットワーク、計算、データベースに、**推論ファクトリーを 5 本目の柱として加える**

1 台の DGX Station から 50 台になると、管理の問題が生じます。そのため、**Microsoft Foundry を拡張し、Windows Server の技術（発話では 2028 と聞こえます）の上に構築して、AI 推論のコンピュートファブリックを提供する**取り組みを進めている、という説明です。ビジョンは、ローカルの token factory を抽象化したうえで、フロンティアモデルの力が必要なとき、あるいは自社のハードウェアでは足りない需要の急増時に、Microsoft Foundry 経由で**クラウドへサージ（溢れた分を逃がす）できる**ファブリックです。

## 7. 注意点・発表者の気付き

- **MoE モデルは、使う専門家が少なくても全部をメモリに載せる必要がある。** どの専門家が使われるか分からないためで、フル精度では 276 GB になる。量子化（約 57 GB）、ドラフトモデル（約 2 倍高速）、sliding window attention（メモリ約 80% 削減）の組み合わせで、ノート PC に載せた。
- **Fusion の現状は限定的。** 今回は、複雑さが低いタスクをローカルモデルに全部任せる使い方。カスケードやクリティークでローカルモデルを使うのは、今後の方向として語られた。
- **スキルとエージェントの設計。** 引き継ぎにゲートを設け（主モデルが 1 コマンドで終えられるなら引き継がない）、ローカルのエージェントには他のエージェントの呼び出しを禁止して、無限ループを防ぐ。
- **ローカルが向くのは、結果を急がない定型作業。** 4 分で終わるか 8 分かかるかを誰も気にしない解析は、毎朝 7 時に自動実行して、人はブリーフを読むだけにできる。
- **利用状況の可視化は「近日中」。** Viva Insights のような画面にローカル AI のテレメトリーを出す件は、まだ提供前の予告。
- **RDMA over USB4 は開発者プレビュー。** 配線はフルメッシュで、各 PC は、他の PC の数だけ USB4 ポートが必要。レジストリの設定の有効化が必要。「壊してみて、フィードバックを」と呼びかけられた。
- **DGX Station の収容人数は、組織ごとに異なる。** ラボの合成テストでは、DGX Station の GB300 ノードに 64 本の連続したエージェント推論ストリームを流す。ただ、実際の人間はコーヒーブレイクを取り、休暇も取る。そのため、1 台で実際に収容できるユーザー密度は、組織や、組織内の機能チームごとに異なる。大規模に展開する前に、**ある程度の負荷分析が必要**だと明言された。モデル、ハーネス、タスク、社員の使い方の選択が、支えられる負荷を左右する。
- **デモは時間がかかる。** 「準備したときは 15 秒だったのに、本番では 90 秒や 2 分かかる」と、ライブデモの難しさを笑い混じりに話している。
- **Insight からの問いかけ。** 何が本当に社外に出る必要があるか。コードとデータをどこに置くか。エージェントが動き出したあと、誰が見張るのか。

## 8. お客様にとっての利点

発表で語られた利点を整理します。

- **コストを抑えられる。** 日常的な作業にクラウドのトークンを使わなくて済む。Insight は、ユニットテストの作成や、API 呼び出し用のモデル仕様の更新といった日常作業で、クラウドのトークンを使わなくなったと述べている。Redmond のラボのデモは、すでに給電されている電力以外のコストがかからなかった、とも説明された。
- **コードが外に出ない。** 顧客の知的財産を扱うとき、コードを端末に残せる。ログの調査も、端末から出さずに実行できる。
- **統制が一貫する。** クラウドのエージェントと同じ Agent 365 と、MXC による制約を、ローカルの端末や token factory にもかけられる。「ローカルで動かしてもガバナンスの外には出ない」。
- **既存の運用に収まる。** Windows が載った端末なので、Defender、Intune など、すでに使っているポリシーで管理できる。PC メーカーも既存のまま選べる。
- **規模に合わせて段階的に広げられる。** ノート PC から、複数台の PC のクラスター、DGX Station、さらに複数の推論クラスターをまとめる Foundry のファブリックまで、同じ Windows、同じ管理、同じ推論スタックで連続している。クラウドは、フロンティアモデルが必要なときや需要の急増時にだけ使う。
- **ハードウェアを再利用できる。** USB4 のケーブルだけで、すでにある PC をつなぎ、1 台に収まらないモデルを動かせる。
- **自動化に向く。** 夜間や早朝に、人がいなくても定型の調査を回せる。

## 9. まとめ

BRK389 は、AI コーディングの効率化を、クラウドの利用料金の見直しだけで終わらせず、**クラウド、token factory、端末の 3 層をどう使い分けるか**という設計の話として示したセッションでした。

デモでは、同じ GitHub Copilot の中で、Fusion に任せる、自分でスキルとエージェントを組んで引き継ぐ、クラウドを使わずに調査を完結させる、という 3 つの方法を、128 GB の共有メモリを持つノート PC 1 台で見せています。その背景として、1,380 億パラメーターの MoE モデルを、量子化、ドラフトモデル、sliding window attention で 57 GB にまで載せた工夫が説明されました。

そこから先は、USB4 で PC をつなぐ RDMA（開発者プレビュー、翌日に Windows Insider へ展開）、748 GB のメモリを持つ DGX Station for Windows、そして推論クラスターを束ねる Microsoft Foundry というスペクトラムが示されます。Redmond のラボのデモは時間内に完了しませんでしたが、ラボで 64 本のエージェント推論を流す検証や、「収容できる人数は組織ごとに違うので、負荷分析が必要」という気付きは、導入を考える人にとって重要です。

最終的な呼びかけは、自社に合った「場所、能力、価格」の組み合わせを探すことでした。そのために、RTX Spark の端末、PC のクラスター、DGX Station のどれから始めるかを選び、DGX Station の顧客エンゲージメントのプログラムや、Windows Server のプレビューに参加してほしい、というものです。
