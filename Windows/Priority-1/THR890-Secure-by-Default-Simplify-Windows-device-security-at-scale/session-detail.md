# THR890 Secure by Default: Simplify Windows device security at scale

## 1. はじめに

このセッションは、Windows 11 のすべてのデバイスを「安全な状態」に揃えるための新しい取り組み **Windows Baseline Protection** を紹介する、約 25 分の Theater セッションです。発表では、8 つの基準（criteria）の考え方、IT 管理者が状態を確認する Microsoft 365 管理センターの画面、エンドユーザーが設定アプリから 1 回の操作で対応する流れ、そしてアプリ開発者がデバイスの状態を確かめる audit API と cloud attestation が扱われます。

この解説を読むと、Baseline Protection が何を目指し、誰がどう使うのか、現時点（preview の開始時点）で何が使えて何がこれからなのかが分かります。ロードマップとして、毎年基準を引き上げていく方針も語られました。

## 3. 何に関する発表か

背景として、約 1 年前から、ユーザーが知らないうちに他のアプリをインストールするアプリや、ユーザーの同意なくデバイスの設定を変更するアプリが増えていることが話題になった、という説明がありました。ユーザー、IT、開発者との会話から、次のような共通のテーマが浮かびました。

- Windows の整合性（アプリがシステムを変更できてしまうか）
- 管理者権限や SYSTEM に伴う特権・権限の広がり

発表者は、これを 1 つずつ穴をふさぐのではなく、**ground up（土台から）アーキテクチャとして解決する必要がある**と述べ、その出発点が Windows Baseline Protection だと説明しています。長い道のりになるが、今日はその最初の一歩を紹介する、という位置づけです。

発表の流れは次のとおりです。

1. Windows Baseline Protection の概要と 8 つの基準

## 4. 発表者が伝えたいメッセージ

Windows Baseline Protection の狙いは、次の 3 点に整理されています。

1. **すべての Windows 11 デバイスで、これらのセキュリティ機能を有効にする。** 管理された IT デバイス、コンシューマー向けデバイス、サーバーを問わず、すべての Windows 11 デバイスが対象です。そのために、IT 管理者には Microsoft 365 管理センター、エンドユーザーには設定アプリという、適切なツールと構成方法を提供します。
2. **ユーザー体験をシンプルにする。** 「PC のセキュリティを直してください」と言われて、ドキュメントの 20 手順を渡されるのは難しい。それを 1 クリックにし、設定アプリ上で何をしているかが分かる情報を示す、という考えです。
3. **エコシステム全体を巻き込む。** Windows がセキュリティの基準を示しても、アプリケーション側にも独自のセキュリティ上の要件があるため、その達成も支援する、と述べています。

## 5. 発表内容の詳細

### 5.1 8 つの基準の考え方

今日の発表では、**8 つの基準**が公表されました。個々の基準の名称は、発話では 1 つずつ読み上げられていません（スライド上の図の説明として、次の点が語られました）。

- 基準を設ける際は、**Goldilocks zone**（ちょうどよい水準）を探した。簡単すぎてどのデバイスも満たすが意味がない、というものでも、難しすぎてどのデバイスも満たせない、というものでもない。
- そのため、まったく新しい機能を足すのではなく、Windows 11 デバイスにすでにある**既存のセキュリティ機能とポリシー**に焦点を当てている。
- 図の上の行は、ハードウェアに関するもの。すべての Windows 11 デバイスが満たせるようにしたいので、**新しい Windows 11 のハードウェア要件は導入しない**。すでにあるものを活用する。
- 下の行は、ドライバーに関するもの。ドライバーはカーネルで動くため、信頼されていない、署名されていないドライバーが動くと、デバイスに大きなセキュリティ上のずれが生じる。そのため、最高品質のドライバーが使われ、署名されていることを確認するポリシーに重点を置く。

### 5.2 3 つのグループへの影響

| グループ | 説明 |
| ---- | ---- |
| エンドユーザー | セキュリティ機能が無効になっていても、自分で無効にしたのか、家族なのか、アプリやツールなのか、分かりにくい。何を変えるべきかを示し、変更を簡単にすることを優先した。なお、この箇所には「半数以上のデバイス」という趣旨の発話がありますが、文意が聞き取りにくいため、数値としては扱いません |
| IT 管理者 | 要件が明確になる。8 つの要件はすべての Windows 11 デバイスに適用される。Intune などの MDM プロバイダーや Microsoft 365 管理センターでフリートを管理する |
| 開発者 | アプリごとにセキュリティ上の要件がある。例: ゲームの不正対策、試験、機密情報を扱うコンテンツ。マルウェアが動いていない状態を確かめ、デバイスのセキュリティ状態を見たい |

### 5.3 アプリのシナリオ

- **ゲーム**: 競技的なトーナメントで不正を防ぎたい。すでにゲームでは anti-cheat と呼ばれる多くの仕組みがあり、この機能の作り方は anti-cheat から強く影響を受けている。anti-cheat の概念を広げ、anti-cheat が直面したユーザー体験上の課題を大幅に簡単にした、と説明しています。
- **機密コンテンツ**: クラウドからマシンに機密コンテンツを持ち込む場合、情報の持ち出しやマルウェアによる改ざんが課題になる。アプリは、コンテンツを持ち込む前にデバイスのセキュリティ状態を確認できる。
- **試験**: ゲームと同じく不正を防ぎたい。試験開始前にデバイスの状態を確認でき、学生は時間どおりに試験を始められる。
- **企業**: conditional access に活用できる。
- **金融機関**: 金融取引が行われるとき、改ざんされたり別の口座に誘導されたりしていないかを確認できる。
- **開発者の判断材料**: ポリシーを強制する前に、対象となり得る市場の大きさを評価できるよう、適切なテレメトリを提供したい。

さまざまな業界の複数のパートナーと協力して、何が必要かを理解してきました。得られたフィードバックや採用状況を誇りに思っており、今後さらに増えると見ています。発表者は、パートナーこそがこの取り組みが成功すると考える理由だと述べています。社名はこの部分では挙げられていません。

### 5.4 開発者向け: audit API と cloud attestation

デバイスのセキュリティ状態に確信を持てるようにするため、2 つのパートに分かれています。

**1) audit API**

- 8 つの要件のそれぞれの状態を返す、単純な API。
- 実行時にユーザーが設定を変えた場合に備えて、次回の起動時の状態も返す。
- 1 回呼べば、「このデバイスは Baseline Protection の要件を満たしているか」の yes/no が得られる。
- ただし、デバイスが侵害されている場合は audit API 単体を信頼できないため、必要に応じて attestation に進む。要件を満たしていない（何かが欠けている）と返ってきたら、設定アプリへ誘導してユーザーに直してもらう。

**2) cloud attestation**

1. アプリが Windows の API を呼び、デバイスの TPM が暗号化されたトークンを生成する。トークンの生成には、Microsoft が構築した attestation サービスへの呼び出しが含まれる。
2. トークンの生成は 1 回で足り、起動セッション全体でキャッシュされる。他のアプリや再起動したアプリは、毎回呼び出す必要がない。
3. クライアントは、そのトークンを自分のクラウドサービスに送る。試験なら結果を送るサービス、マルチプレイのゲームならトーナメントのサービスなど、すでにあるサービスを使う。
4. そのサービスが、トークンを Windows の attestation サービスに渡し、結果を受け取る。この結果は信頼できる。
5. 最後に、後片付け（clean up）をする。

サービス側では、トークンを付けて attestation を開始する REST 呼び出しを行い、レポートが返る、と説明しています。IT 管理者向けには、Device Health Attestation のようなものを使っている場合、裏側では同じ仕組みが動いている、という説明がありました。トークンの送り先としては Azure attestation service のようなサービスが例に挙がり、今回の取り組みでは、クラウドサービスが Windows 向けに呼び出せる attestation サービスを Microsoft が提供する、と説明されました。

> 注意：現時点の preview の最初の段階では、**audit の部分（最初の API）だけ**が対象です。attestation の API と attestation サービスは、private preview で提供されます（発話は "coming in private preview right now"）。

### 5.5 ロードマップ

最初に挙げた課題（システムの整合性、システム全体での特権・権限の広がり、管理者権限の多さ）を、今日の内容がすべてカバーするわけではなく、ロードマップの一部だと説明しています。

- 毎年、新しい要件を加えて、セキュリティの基準を引き上げる。
- 突然の変更で、エンドユーザー、IT 管理者、開発者に影響が出ないよう、慎重に進める。まず「任意の将来の要件」として導入し、翌年から強制の要件へ段階的に移す。
- 将来の要件の例: アプリが NTLM を使わず Kerberos を使うようにする、admin protection と Smart App Control の利用を強制して、アプリの reputation と署名の活用を進める。

詳細は、同日の午後（5:15）の breakout セッションで扱われる、と案内されました。今後の private preview に参加したい場合も、この breakout セッションで声をかけてほしいと話しています。

## 6. デモ・手順

デモは 2 つあります。録音は音声のみのため、画面の細部は分かりません。語られた範囲だけを書きます。

### 6.1 IT 管理者向け: Microsoft 365 管理センターの baseline security mode

1. Microsoft 365 管理センターで org settings に入り、baseline security mode を見つける。baseline security mode は、昨年の Ignite で Microsoft 365 チームが導入したもの（Microsoft baseline security mode）。
2. パネルを開く。ここでは、フリート全体を見渡し、まずポリシーのデプロイ状況（この機能が有効か無効か）を把握し、すぐに有効にできる。
3. 現時点では要件のうち 3 つから始めている。一般提供までに、すべての要件を含める予定。Windows が baseline security mode に直接表示される。
4. デバイスやフリートを見て、要件を満たしているデバイスの数を確認する。どのデバイスが満たし、どれが満たしていないかのレポートも得られる。
5. 現在の baseline security mode はポリシーの**レポートだけ**を行う。リリースまでには、ポリシーを設定する機能も追加し、IT 管理者がすべてのデバイスを要件に合わせて構成できるようにする。

### 6.2 エンドユーザー向け: 設定アプリとチェスアプリ（仮想マシン上）

仮想マシンを使ったのは、裏側の設定を見せるためだ、と説明されています。

1. Windows の設定を開く。サイドバーで、プライバシーとセキュリティが 2 つに分かれている。セキュリティチームが、Windows の各所の設定を「セキュリティ」の下に集約した。その一番上に **baseline protection** がある。
2. この仮想マシンは、8 つの保護のうち 2 つが不足していることが分かる。ボタンが 1 つあり、それを押せば直せる。
3. 押す前に、アプリ側から見た様子を見せる。チェスアプリでは、プレイヤーの評価（レピュテーション）は、自分より評価が高い相手に勝つことで上がるため、対戦の公平性が重要になる。1 人でプレイするなら、デバイスが侵害されていても、低いセキュリティ状態でも、トーナメントに入れる。
4. マルチプレイでマッチングしようとして「find a match」をクリックすると、「Baseline Protection の要件を満たしていない」と表示される。「open settings」をクリックすると、設定のページに戻れる。
5. 従来の anti-cheat では、Secure Boot を有効にするなど 20 手順を示された。BitLocker の一時停止、再起動、ファームウェア設定に入るためのキー操作など、難しい手順を挙げた。ここでは、設定ページの 1 つのボタンで保護を有効にする。
6. これらの要件は**起動時に測定**されるため、設定は起動セッションの間続く。設定が変わるたびに再起動が必要になる。このデモでは、Secure Boot をファームウェアで直す必要がある。これは Windows 自体ではできない（ファームウェア設定の中で行うため）。そこで、スマートフォンで読み込める **QR コード**を表示し、手順へ直接移動できるようにしている。
7. 通常のマシンでは、そこからファームウェア設定に入る。ステージでは、ディスプレイを複製していると見えないため、仮想マシン側の設定に直接入った。セキュリティで Secure Boot を有効にする必要があり、マシンの電源を切る。
8. Secure Boot を有効にする。選択肢として、Windows のみの Secure Boot と、デュアルブートの両方を許可する方式が表示された。OK を選ぶ。
9. 起動し直したあと、設定に戻って確認する。セキュリティを開くと、**8 つの要件すべてを満たしている**。ファームウェアでの操作（Secure Boot）が不要な場合は、他の設定は単純な再起動だけで済む、と説明している。
10. チェスのトーナメントに戻り、2 人対戦を選ぶと、相手とすぐにつながり、対戦に入れた。

## 7. 注意点・発表者の気付き

- 設定が変わると、**再起動が必要**になる。要件は起動時に測定され、起動セッション中は維持される。
- Secure Boot は、Windows 自体では変更できず、ファームウェア設定で行う必要がある。ファームウェアでの操作が不要なその他の設定は、単純な再起動で済む。
- audit API 単体では、侵害されたデバイスを信頼できない。cloud attestation が必要。
- 現時点では、baseline security mode は**レポートのみ**で、要件は 3 つ。ポリシーの設定機能と、すべての要件への対応は、一般提供までに追加する意向。
- 今日使える範囲は audit API のみ。attestation の API とサービスは private preview。
- 新しい要件は、いきなり強制せず、まず任意として導入し、翌年から段階的に強制へ移行する。

## 8. 利用者にとっての利点

このセッションでは、お客様事例や効果を示す数値は語られていません。発表で語られた利点は次のとおりです。

- **IT 管理者**: 要件が明確で、フリート全体の準拠状況を Microsoft 365 管理センターで確認でき、満たしていないデバイスのレポートも得られる。将来は、ポリシーを設定する機能も加わる予定。
- **エンドユーザー**: 設定アプリの 1 つのボタンで、不足している保護を有効にできる。従来の 20 手順に比べ、ファームウェアの手順も QR コードで案内される。
- **開発者**: audit API とクラウドでの attestation により、アプリを動かす前にデバイスのセキュリティ状態を確認できる。ポリシーを強制する前に、対象となる市場の大きさを評価できるよう、適切なテレメトリを提供したいと発表者は話しています。
- 新しい Windows 11 ハードウェア要件は導入されない（すでにあるものを活用する）。

## 9. まとめ

- Windows Baseline Protection は、すべての Windows 11 デバイスが満たすべき 8 つのセキュリティ基準です。ハードウェアとドライバーに関する既存の機能・ポリシーを使い、新しいハードウェア要件は加えません。
- IT 管理者は Microsoft 365 管理センターの baseline security mode で準拠状況を確認でき（現状は 3 要件・レポートのみ）、エンドユーザーは設定アプリで 1 つのボタンから対応できます。
- 開発者は audit API で状態を確認し、侵害の可能性がある場合は TPM を使った cloud attestation で結果を信頼できます。attestation は private preview です。
- 毎年、新しい要件を任意として導入し、翌年から強制に移すことで、基準を引き上げていきます。次の候補は、NTLM から Kerberos への移行、admin protection、Smart App Control です。
- ブログと開発者向け API は、スライド上の QR コードから確認できます。
