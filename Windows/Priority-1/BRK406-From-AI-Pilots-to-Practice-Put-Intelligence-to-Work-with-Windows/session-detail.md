# BRK406 From AI Pilots to Practice: Put Intelligence to Work with Windows

## 1. はじめに

## 5. 発表内容の詳細

### 5.1 導入：3 つの問い

オープニング映像は、「or」という小さな言葉が AI を頼りにしたい企業にとって大きな問題になっている、という語りで始まり、Windows は「or」を「and」に変えると続きます（速く進み、かつ統制を保つ。デバイスでもクラウドでも実行し、一つとして管理する、など）。

Stefan 氏が挙げた、テクノロジーリーダーからよく聞く問いは次の 3 つです。

1. どのワークフローを人主導にし、どれをエージェント主導にするか
2. AI とエージェントを、デバイスで動かすかクラウドで動かすか
3. スピードを最適化するか、統制を保つことを最適化するか

エージェントは作業の機械的な部分を引き受け、人は人にしかできないことに集中できます。それによって、チームはより多くの顧客に対応し、製品をより速く出荷できるようになる、という説明です。

### 5.2 エージェントのためのセキュアなプラットフォーム

開発者はコーディングエージェントに変更全体を任せ、運用チームは夜間に自律エージェントにレコードを入力させ、Copilot は日常のタスクを支援しています。長年、組織は人、デバイス、データを守ってきましたが、今は同じアクセス権を持つエージェントが、機械の速度で並行して動いています。価値の源泉であると同時にリスクの源泉でもあります。例として、エージェントが不要なファイルを読んでしまうことや、Web ページに埋め込まれた隠れた指示を拾って従ってしまうことが挙げられました。

信頼するには、「どのエージェントが動いているのか」「何に触れられるのか」「大規模にどう統制するのか」が分かる必要があります。Windows はこの信頼を OS に組み込み、**Identity（識別）、Containment（封じ込め）、Management（管理）が一つのシステムとして動く**構成にしていると説明されました。それらを Agent 365 が、すでに使っているツールと束ねます。

#### Microsoft Entra Agent ID（識別）

Microsoft Entra Agent ID は、すべてのエージェントに固有の ID を与えます。エージェントが人に代わって動く場合、その操作は「エージェントの操作」として記録され、同時にその人物にも紐づいたままになります。人に設定しているものと同じ conditional access（条件付きアクセス）ポリシーをエージェントにも適用できるため、「人がしたこと」と「エージェントがしたこと」を区別できます。

#### MXC: Microsoft Execution Containers（封じ込め）

Copilot が週次のビジネスレビューをまとめる場面が例に挙がりました。必要なのはその週のプロジェクトファイルだけですが、PC 上には機密性の高い HR 記録や法務関連のファイルなど、もっと多くのものがあります。何が関連するかはエージェントが自分で判断するため、触れるべきでないものを取り込む可能性があります。したがって境界は、エージェントが変更できない Windows の側から与える必要があります。それが MXC です。

- エージェントの開発者が、そのエージェントに必要なものを宣言する。
- 組織のポリシーが境界を決める。
- Windows が実行時にそれを強制する。

Windows では、仕事に合わせたコンテナーが用意されています。

| 用途 | コンテナーの種類 |
| ---- | ---- |
| タスク | process container（プロセスコンテナー） |
| 人と並んで動くエージェント | エージェント専用のセッション |
| リスクの高い作業 | ローカルの micro VM（作業完了後にスピンダウン） |

現時点ではエージェントの開発者がコンテナーを自分で選びます。将来は、組織がポリシーを設定すれば Windows が最適な封じ込めをその場で選ぶようになる、という方向性が語られました。

採用状況として、OpenAI は Codex で MXC を既定で有効にし、Meta は数万台の Windows デバイスで MXC を動かし、Anthropic、Hermes、Replit も支持していると紹介されました。Stefan 氏は MXC を、最も速く成長しているプラットフォーム機能の一つだと述べています。また MXC は Windows だけでなく Linux と MacOS でも動きますが、Windows では OS に組み込まれているため、エージェントがデータに対してできることを最も深く制御できると説明されました。

#### Agent 365（管理）

Agent 365 は、組織内のすべてのエージェントを一か所で管理する場所です。Copilot や Foundry で自チームが作ったもの、パートナーが作ったもの、そして**誰も承認していないもの**まで表示し、それぞれが何をしているか、どこにリスクがあるかを見られます。PC 上のローカルエージェントも、Windows が各エージェントの動作を記録する形で、他のエージェントと並んで表示されます。Agent 365 は Entra、Intune、Defender、Purview を、人やデバイスに対してすでに使っているのと同じ方法でエージェントにも働かせる、と説明されています。その結果、必要なエージェントの承認と展開が速くなるという位置づけです。

| 機能 | 状況（発表で語られたもの） |
| ---- | ---- |
| Intune での MXC ポリシー | private preview |
| Agent 365 の Shadow AI 検出 | Frontier program の一部 |

### 5.3 ハイブリッドインテリジェンスと intelligent routing

ここから Bhavya 氏の担当です。まず用語の整理として、このセッションで「PC」と言うときは、手元のノート PC と **Windows 365 Cloud PC** の両方を指します。同じ Windows、同じアプリで、同じ Microsoft のスタックで管理・保護でき、違うのは「その PC がどこで動くか」だけだ、という説明です。以降、PC 上で動くものと言えば両方を意味します。

hybrid intelligence では、Windows が PC 上で動くローカルモデルと Azure の Frontier モデルを組み合わせ、タスクごとに適切なモデルへ振り分けます。これを **intelligent routing** と呼んでいます。所有している PC のそれぞれが、自分たちが所有する知能の源になる、という言い方もされました。

#### Copilot が得る 3 つのもの

Copilot が Windows の hybrid intelligence で得るものとして、次の 3 つが挙げられました（発表者は、午前のキーノートのデモで見た内容だと言及しています）。

1. **ローカルコンテキスト**：許可を得て、PC 全体から必要なものを探して使える。
2. **ローカルアクション**：ファイル整理から問題の修正まで実行でき、変更前には確認を求める。
3. **ローカルモデル**：追加コストなしで PC 上のモデルで動き、タスクがより多くを必要とするときだけクラウドを使う。

近日中に、Copilot on Windows が、ヘッドフォンがペアリングできない、インターネット接続が遅いなど、現在 IT が呼ばれている問題の多くを診断して修正できるようになる、とも述べられました。チケットが起票されずに済む分だけ、IT チームは戦略的なプロジェクトに集中できるという説明です。

#### 開発者向け：Copilot Fusion とローカルモデル

intelligent routing の効果が最も分かりやすいのは開発者だとされています。コーディングエージェントは 1 つの問題に数千ステップを費やし、各ステップでモデルを呼び出します。そこで、ステップごとに適切なモデルを選びます。文字起こしでは「Git Copilot」と聞こえますが、GitHub Copilot の Copilot Fusion を指していると読めます（音声認識の都合で表記が確定できません）。

- 最も難しい推論は Azure の Frontier モデルへ。
- プライバシーやコストが重要なステップは PC 上に残す。
- Frontier モデルが変更全体を計画し、実装とテストを PC 上のサブエージェントに任せることで、より多くのエージェントを走らせられる。
- Cloud PC でも同様に動くため、長時間のジョブをクラウド上のコーディングエージェントに任せ、安全に統制された環境で動き続けるエージェントの状況をどこからでも確認できる。

**GitHub Copilot with local models on Windows** は、GitHub Copilot アプリ、CLI、VS Code で preview になっています。また、複数の Fortune 500 企業が、NVIDIA RTX Spark を搭載した Surface Laptop Ultra で試験運用中だと述べられました。

#### 自社で作るエージェントに使える要素

自社製エージェントでも同じことができる、として次が挙げられました。

- **MCP on Windows**：許可のもとで同じローカルコンテキストとアクションをエージェントに与え、どのエージェントが使えるかを Intune で決める。
- **Windows ML**：CPU、GPU、NPU 上でローカルモデルを動かす。開発者は一度作れば足りる。Llama.CPP が Windows ML に対応する予定で、公開された日からオープンモデルを使えるようになる。
- **MXC**：チームが作るすべてのエージェントを、定めた境界の内側に置く。

Perplexity、OpenClaw、Replit といった人気のエージェントが、すでにこの方法で Windows 上に構築していると紹介されました。事例として、世界有数の美術品オークションハウスである Christie's が Windows 上で Replit を使い、AI を活用しながら情報をローカルに保ち、Christie's の管理下に置いている、と語られています。

### 5.4 Windows 365 for Agents

これまでの話は人と一緒に動くエージェント（コーディングエージェントなど）でした。一方、人に代わって単独で、チームと同じデスクトップアプリを使って動くエージェントもあり、そうしたエージェントには、重要な基幹業務アプリへアクセスできる「自分専用のコンピューター」が必要だ、という整理です。

**Windows 365 for Agents** は、各エージェントに安全な Cloud PC を与え、Intune で他の Windows 端末と同様に管理します。エージェントは人と同じようにコンピューターを使い、固有の ID を持ち、クリックし、画面を見て、アプリ間でデータを移し、画面に入力します。つまり、事業が既に持つアプリを書き換えずにエージェントを入れられます。

#### Microsoft 内の事例

Microsoft の Business Operations チームは、Windows 365 for Agents で注文処理を効率化しています。従業員がワークフローを一度記録し、それをアップロードしてエージェントに学習させると、複数のエージェントがそれぞれ自分の Cloud PC で注文を同時に処理し、人は必要なときだけ介入します。この運用で、処理時間を **60% 削減**したと述べられました。

#### Persistent Cloud PC（preview）

自律エージェントは長時間のジョブを担い、時間をかけて文脈を蓄積します。そのため、エージェントが戻ってこられる**永続的な Cloud PC** を持てるようになり（preview）、オンプレミスのアプリにも安全に接続できます、と説明されました。この機能のデモは 6 章で触れます。

提供形態については、次のように語られています。

- Microsoft Copilot Studio では、computer-use ツールとして利用可能。
- Microsoft Foundry では「coming soon」。
- 今月末に preview（発話は "it's a preview at the end of this month"。どの提供形態にかかる発言かは、音声だけでは明確ではありません）。
- 費用は Copilot Credits（Microsoft の AI サービス共通の課金の仕組み）で賄える。

### 5.5 AI インフラ計画：PC、サーバー、クラウドを一つの計画に

Bhavya 氏は、エンドユーザーコンピューティングの担当者と、Azure サーバーで AI インフラを運用する担当者が社内で別々にいることを会場に挙手で尋ねたうえで、AI では両方が同じ知能を必要とし、AI インフラは PC、サーバー、クラウドにまたがるものになると述べています。中心にあるのは、同じ Windows、同じアプリ、同じエージェント、同じ管理スタックです。

| 構成要素 | 語られた内容 |
| ---- | ---- |
| Copilot+ PC | 大半の人にとっての出発点。日常の AI が高速・安全で常に使える。企業向けに作られているノート PC の 40% 以上がすでに Copilot+ PC。月に 2 兆回を超える推論をデバイス上で実行している。 |
| Cloud PC | 任意のデバイスで Windows を使えるようにする。デバイスの寿命を延ばせ、重いプロジェクトのためにサイズを上げて終われば下げられる。GPU 対応の Cloud PC なら、ピーク需要のためのハードを買わずに重いモデルやワークロードを動かせる。 |
| ミニデスクトップ | ヘッドレスで動き、最大 128 GB のメモリ。常時稼働のエージェントが、誰かのノート PC を占有せずに、クラウドのモデルまたはローカルモデルを動かせる。 |
| Builder PC（開発者向け） | 最大 128 GB のメモリで、1,000 億パラメーター超のモデルを動かせる。コーディングエージェントのトークンのより多くを、クラウドのモデルではなく開発者自身のデバイスから賄える。 |
| DGX Station | 最大 748 GB のメモリ（聞こえた数値のとおり）、1 兆パラメーターのモデル。かつてはクラスターを借りる必要があった能力をチームの傍らに置け、DGX Station for Windows で数十のエージェントを同時に動かせる。 |
| Windows Server 2028（preview） | モデルを、組織が運用するシステムの隣で動かせる。初めて、エンドポイントチームが Intune でサーバーを管理し、auto-patch で PC と同じようにパッチを当てられる。 |

Azure はこれらすべてと一つの fabric（織物）として連携するため、最も難しい問題は引き続き Frontier に到達できる、と説明されています。

> 補足：「Windows Server 2028」「748 GB」は聞こえた表記のままです（音声認識の都合で表記が確定できません）。

Bhavya 氏は、今後 12〜18 か月に行うハードウェアの意思決定はすべて AI の意思決定でもある、と述べています。新しい Forrester の調査として、スクリーンに示された数値が語られました。

### 5.6 顧客事例：Flagstar Bank

Flagstar Bank は、3 つの銀行を Windows 上で一つにまとめ、全支店の PC にエージェントを置いています。行員は、顧客が目の前に座っている間に必要な情報を探せるようになりました。紹介映像では、Flagstar はニューヨークに本社を置く地域銀行で、Windows 11 環境で Surface デバイス上に独自の small language model を直接動かし、「Branch IQ」という専用の AI エージェントをデバイス上に構築した、と語られています。

#### 統合の背景

Jason Pope 氏の説明は次のとおりです。

- Legacy Flagstar、Legacy Signature Bank、Legacy New York Community Bank が 2024 年ごろに合併し、現在の Flagstar Bank になった。
- 2025 年初めに着任した時点では、コントロールプレーンが約 4 つ、あらゆるモデルのコンピューター、VDI は Citrix という状態で、エンドユーザーコンピューティングの体験が一貫していなかった。
- そこで AI を念頭に Surface ラップトップを選定し、Microsoft 365 E7 SKU にいち早く契約した顧客の一つとなって、エコシステムを Microsoft スタックに集約した。
- これにより単一のコントロールプレーンを得て、Citrix から W365 へ移行し、顧客と接する人に Windows Copilot PC を渡した。

#### Branch IQ とローカル実行の理由

Branch IQ は現時点で、標準、ポリシー、手順をデバイス上に持ちます。リレーションシップ重視の銀行であるため、コーヒーショップやニューヨークの地下鉄の中で顧客と会うことも多く、LTE の利点によって顧客のいる場所へ行けるそうです。

ローカル AI を選んだ理由は次のとおりです。

- 顧客の前に立っているときは、標準やポリシー、手順をクラウドへ問い合わせたくない。素早い応答が欲しい（例：新しい口座タイプを開設するための申込書を探す）。
- KYC の検証や、アンチマネーロンダリングのチェックなど、本番移行が近づいている用途もある。これらはガバナンス、テレメトリ、トレーサビリティ、監査可能性のためにローカルで動かしている。

#### 試験から運用へ移すときの検討事項

- 規制上の義務の理解と、ローカル実行かクラウドの別モデルかを問わず、完全なトレーサビリティと監査可能性を素早く定量化・定性化できること。
- 小さく、ゆっくり始めた（Branch IQ から開始し、現在は運用チームを支援するエージェントを追加中）。
- サイバーの観点。金融機関として KYC のデータをあちこちに送ることはできないため、完全なトレーサビリティを保ってローカルで扱いたい。
- Surface デバイスを従業員に渡すと同時に、W365 へ全面移行した。この 2 つの形態を行き来できることで、100 人を追加するときも 2〜3 人を立ち上げるときもパターンがあり、運用が標準化されてスケールできた。

#### 他の組織へのアドバイス

- ローカル AI の観点で、粒度の細かい可視性を得られること、その可視性が自分の業界にとって何を意味するかを理解すること。
- Branch IQ は、デバイス上に存在する small language model です。今後は MXC を使い、デバイス外で行う操作に対してもエージェントが手を伸ばす、単なるチャット型ではなく真のエージェントワークフローへ拡大することを検討している。
- 規制のある企業では、セキュリティ、ガバナンス、リスクとコンプライアンスが極めて重要。Windows 11 プラットフォームの上にガードレールという土台を作ってスケールすれば、可能性は広がる。「大きく考えよ」という言葉も語られました。

Jason 氏は、今後掘り下げていく領域の話の中で、Agent 365 がどう役立つかにも触れています。

Stefan 氏は、銀行で最も重要な瞬間、つまり行員が顧客の向かいに座っている場面から出発して課題を解いたことが印象的だったと述べています。

### 5.7 将来像とまとめ（Stefan 氏）

1 年後の組織を想像してほしい、という形で次の姿が示されました。

- 開発者のエージェントが 1 日に数百万トークンを読み、その大部分がクラウド予算に触れない。
- 人が IT に問い合わせていた問題の多くを、チケットが起票される前に Copilot が解決する。
- エージェントが既存のアプリ上で反復作業を担い、人は重要な仕事に時間を使う。
- サーバーがデータのすぐ隣でモデルを動かし、本当に必要なときは Azure の Frontier モデルがそこにある。

それが hybrid intelligence であり、「手持ちの予算で、より多くの AI を事業に。生み出される価値は自分たちの手元に残る」ことだと説明されました。最後に、さらに深く知るために画面に示したセッションと Pavan 氏のブログ（聞こえた綴りのまま。音声認識の都合で表記が確定できません）を案内しています。

## 6. デモ・手順

このセッションのデモは、Speaker 2〜4 のナレーションで進みます（ライブ操作か録画かは音声からは確認できません）。画面の細部（ボタン名、入力値、レイアウト）は音声から分からないため、語られた内容だけをまとめます。

### 6.1 Entra Agent ID でエージェントを識別する

1. 会社で作られたエージェントが示される。役割は、人が手作業でやる反復作業である「組織レコードのビジネスアプリへの入力」。
2. エージェントが Cloud PC 上の組織入力フォームで作業している。従業員がタスクを委任し、エージェントが手順を実行している。
3. 結果には、成功した入力と失敗した試行の両方があり、確認用にキャプチャされた画面が参照できる。
4. IT は、エージェントに関連付けられた人間と、エージェント自身の Microsoft Entra Agent ID を確認できる。この別 ID によって、IT はエージェントを人間のユーザーとは別の主体として認識し、リソースへのアクセスを統制しながら、作業の背後にいる人とのつながりも保てる。

### 6.2 Agent 365 と Intune で MXC の境界を設定する

1. IT が Agent 365 の estate view から開始し、どのエージェントが稼働しているか、どこにリスクがあって対応が必要かを把握する。
2. Microsoft Intune を使って、MXC でエージェントがアクセスしたり行ったりできることを制御する。
3. Intune ポリシーは、MXC 対応のすべてのエージェント、または Copilot のような特定のエージェントに適用できる。
4. IT 管理者が、エージェントのサンドボックスに Windows が許可するファイルシステムアクセスの上限として、封じ込めの境界を設定する。設定内容は、承認済みプロジェクトフォルダーでは読み取りと書き込み、システムのその他の部分は読み取り専用、企業の OneDrive へのアクセスはなし。
5. これにより、エージェントがビジネスデータをコンテキストに取り込むこと、また複数デバイスに同期される変更を作ることを防げる。ネットワークアクセスなど、MXC が強制する他の設定も Intune ポリシーで制御できる。
6. ユーザー側の流れでは、Copilot はアクセス権のあるドキュメントでレポート作成を続け、制限された場所へのファイル書き込み要求はポリシーによって拒否される。

### 6.3 プロンプトインジェクションと Shadow AI

1. 従業員が Copilot に、ワークフローに役立ちそうなリポジトリを使うよう依頼する。
2. そのソースには、エージェントを乗っ取るためのプロンプトインジェクションの指示が隠れている。
3. Microsoft Defender が、Copilot が動く前に悪意ある指示を検出してブロックする。
4. セキュリティ担当は Microsoft Defender XDR でインシデントを確認し、なぜプロンプトインジェクションと分類されたかを見られる。SOC は、失敗したタスクだけでなく調査のための証拠を得られる。
5. Agent 365 の estate view で、IT は管理対象デバイス上で動く未承認のエージェント（Shadow AI）を特定できる。
6. 未承認のエージェントがデバイスで検出されると、IT は Intune のコンプライアンスポリシーで、そのデバイスの社内リソースへのアクセスを制限する。
7. 従業員には通知と、明確な修復手順が届く。修復とコンプライアンスの再評価の後、アクセスは回復する。

> ご参考：Stefan 氏は、その未承認エージェントが実は有用なものだった可能性にも触れています。開発チームの誰かが自分の時間を節約するために作ったのかもしれません。次の段階として、チームが MXC でそのエージェントを封じ込め、IT のポリシー境界の内側に再デプロイし、承認して必要な組織全体に展開する、という流れが示されました。

### 6.4 Windows の検索（Search）の紹介

Copilot のローカルアクションの紹介の中で、Speaker 3 のナレーションによる短い紹介が流れました。ナレーションの内容は次のとおりです。

1. Windows の検索は、アプリ、設定、ファイルを横断して必要なものを素早く見つける体験で、新しい合理化されたデザインで改善している。
2. クイックアクションで、ウィンドウの整列や画面の整理ができる。
3. Do Not Disturb をオンにして、邪魔されずに集中できる。
4. VPN に接続して、リモート作業時に社内リソースへ安全にアクセスできる。
5. 新しい仮想デスクトップを作成し、ワークフローの異なる部分に集中できる専用のワークスペースを用意できる。これらをタスクバーの Composer ウィンドウから行える。

### 6.5 Copilot Fusion による開発者の一日

1. リポジトリ設定を開き、MXC Process Isolation のサンドボックスが有効になっていることを確認する。
2. 最初の依頼は、認証の追加、テストの更新、プロジェクトの起動。Copilot Fusion がこの作業にモデルを選ぶ（ナレーションでは「Luna」と聞こえます）。ルーターは認証タスクを Frontier モデルへ送る。「可能な限りローカル AI を使い、より深い推論が必要なときにエスカレーションする」と語られる。
3. 次に「変更をコミットできるように準備して、コミットして」と依頼する。ルーティングポリシーが local first に切り替わる。
4. ルーターがコミット準備の依頼を示し、エージェントはローカルモデルを使い始める。変更のレビュー、設定ファイルの確認、ログのスキャンをローカルで行う。
5. ログから、二重送信の競合状態（double-submit race condition）の可能性が検出される。一部の従業員が、同じ経費精算レポートで二重に払い戻された、という例。
6. クラウドでの修正は「Terra」と聞こえるモデルが担当する（音声認識の都合で表記が確定できません）。ローカルのスキャンと AI がレビューを担い、Frontier モデルが複雑なコード変更を担う。

## 9. まとめ

このセッションは、AI を試す段階から運用する段階へ進むための論点を、「or」ではなく「and」で答えるという軸で整理したものでした。要点は次の 3 つです。

1. **エージェントを信頼できる土台**：Entra Agent ID で識別し、MXC で封じ込め、Intune と Agent 365 で一元管理する。Defender による検出や、Shadow AI への対処も同じ流れに乗る。
2. **知能の置き場所を選べること**：intelligent routing により、難しい推論は Azure の Frontier モデルへ、プライバシーやコストが重要なステップは PC 上のローカルモデルへ振り分ける。人と並んで動くエージェントにも、単独で動くエージェント（Windows 365 for Agents）にも対応する。
3. **PC を AI インフラ計画に含めること**：Copilot+ PC、Cloud PC、ミニデスクトップ、Builder PC、DGX Station、Windows Server 2028 を一つの計画で考える。Stefan 氏は最後に、AI 戦略を進化させるときは hybrid intelligence を考慮し、今後の AI インフラ計画に PC を含めてほしい、と呼びかけました。
