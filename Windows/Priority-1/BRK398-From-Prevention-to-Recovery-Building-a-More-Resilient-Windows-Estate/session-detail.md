# BRK398 From Prevention to Recovery: Building a More Resilient Windows Estate

## 1. はじめに

このセッションは、Windows を「止まりにくく、止まっても早く戻せる」状態にするための Microsoft の取り組みを、**予防（Prevention）**と**復旧（Recovery）**の 2 部構成で説明するものです。予防ではドライバーのエコシステムを安全にする Driver Quality Initiative、復旧では Point-in-time restore、Cloud Rebuild、Quick Machine Recovery（QMR）、WinRE の改善、リモート復旧の仕組みが取り上げられます。最後に、Windows 365 Reserve と、Windows 365 自体のレジリエンス強化が紹介されます。

主な対象は、企業の Windows 環境（物理 PC と Cloud PC）を運用する IT 管理者です。発表の結論は、レジリエンスは 1 つのツールではなく、インシデント全体への備えだということです。最後には、復旧計画を立て、障害が起きていない時にテストしておくよう勧められます。

デモは 2 種類あります。Cloud Rebuild（大幅に早送りされたもの）と、Windows 365 Reserve および Windows 365 の管理画面（Intune ベース）です。

## 5. 発表内容の詳細

### 5.1 なぜドライバーなのか（Mehmet 氏）

ドライバーは、ユーザーが毎日使うアプリケーションの下の層にあります。そこで問題が起きると、影響は 1 つのアプリにとどまりません。ビジネスへの影響は 3 つの形で現れる、と説明されています。

- **デバイスのクラッシュ**: ドライバーの障害は、1 つのアプリではなくデバイス全体を止めうる。
- **セキュリティ上の露出**: 脆弱なカーネルドライバーは、システム全体をリスクにさらす。
- **解決の遅さ**: 原因の特定、修正、ハードウェアの異なるフリート全体への展開には時間がかかる。

こうしたリスクがデバイスに届く前に減らすため、Microsoft はドライバーのエコシステムと協力して **Driver Quality Initiative** を進めています。これは 4 つの柱で構成されます。

| 柱 | 内容 |
| --- | --- |
| Architecture | ドライバーモデル自体に内在するリスクを減らす |
| Trust | ドライバーと、提出するパートナーに求める水準を引き上げる |
| Lifecycle | 良いドライバーが最新の状態を保つようにする |
| Measure | 認証テストに合格したかどうかだけでなく、実際の顧客体験を見て輪を閉じる |

目標は、中断の減少、露出の低下、修正を展開しやすい経路、デバイスの健全な維持です。この件については、翌朝にシアターセッションがあり、より深く扱うと案内されています。

### 5.2 Architecture: 1 つのドライバーの問題を PC 全体の問題にしない

3 つの方針が示されました。

1. **カーネルの外に出す。** エコシステムと協力して、サポートがすでにあるところではドライバーのコードをカーネルから出し、ユーザーモードのサポートが無いところでは拡張する。カーネル権限で動くコードが減り、脆弱性や障害を封じ込めやすくなる。
2. **標準化する。** Microsoft が保守するクラスドライバーが複数のパートナー実装を置き換えられる場合は、ばらつきを減らし、修正を配信する共通の経路を作る。
3. **カーネルに残さざるを得ないものを堅牢にする。** パフォーマンスなどの理由でカーネルに残るコードには、driver isolation、DMA remapping、メモリへのより安全なアクセスといった保護を使う。ここでもエコシステムと協力して実装する。

顧客にとっての結果は、ドライバーの欠陥や脆弱性がデバイスを止める機会が減り、保守（servicing）の経路が安全になることです。

### 5.3 Trust: 一度きりのチェックから継続的な保証へ

コード、コンポーネント、パートナーに対する保証を、4 つの方法で強化しています。

1. 開発と認証のサイクルに、多くのチェックを追加する。
2. **ソフトウェア部品表（SBOM）** で、ドライバーの中身を見えるようにする。コンポーネントに問題が出たとき、影響を受けるドライバーを特定しやすくなる。
3. AI を使った分析で、重要なカーネルバイナリ全体を大規模に調べる。
4. カーネルモードドライバーの署名について、パートナーの義務とセキュリティ上の期待を引き上げる。

要約すると、「一度きりのチェックポイント」から「継続的な保証」への移行です。

### 5.4 Lifecycle: デバイスに届いた後も健全に保つ

初日だけ動くドライバーでは足りず、修正が出たときに、すでに問題なく動いている構成を壊さずに適切なマシンへ届ける必要があります。3 つの取り組みが挙げられました。

1. OEM パートナーと協力して、不要な OEM カスタマイズを制限し、ドライバーをハードウェアベンダーのベースドライバーに近づける。修正が対応すべきバリアントの数が減る。
2. **Best known configuration**。OEM と協力し、検証済みのドライバーセットをデバイスモデルごとにまとめて保つ。ドライバー更新を個別の変更として扱わない。
3. ドライバー更新を最新の Windows Driver Kit 上で維持する。やや古いドライバーを保守する場合でも、サイクルに組み込まれた最新の開発ツールとチェックの恩恵を受けられる。

### 5.5 Measure: Driver Quality Metric

クラッシュだけではドライバーの品質は表せない、という考えから、エコシステムと一緒に **driver quality metric** を作っています。複数の観点を束ねる指標で、挙げられたのは次の 2 つです。

- **Stability（安定性）**: カーネルモード・ユーザーモードのクラッシュに加え、ドライバーのプラットフォームとしての健全性（インストールでき、起動し、健全なデバイス状態を保つか）。
- **Functional reliability（機能面の信頼性）**: そのドライバーが提供するはずの顧客シナリオを、一貫して実行できるか。Wi-Fi なら、接続できる、接続を保てる、その成功率など。

これらのシグナルにより、顧客がどこで問題を経験していて、どの対策が最も効果的かを、Microsoft とパートナーが共通の視点で見られるようになります。

### 5.6 復旧の全体像（Aaron 氏）

Aaron 氏は、障害の原因はドライバーの問題、失敗したポリシー展開、不良な更新などさまざまで、影響も 1 台から数百万台まであるため、万能の解決策は無いと述べています。そこで、Windows が提供する復旧ツールの集合を説明します。2 年前の出来事が警鐘となり、Windows の復旧を現代化し、大規模に、かつリモートで動くようにする必要があると学んだ、という経緯です。

従来から 10 年以上、基本的な復旧ツールしかありませんでした。それぞれに制約があります。

| ツール | 制約 |
| --- | --- |
| Startup Repair | 起動に失敗するときに使う |
| 組み込みのトラブルシューター | デバイスが実際に起動する場合にしか使えない |
| Device Reset | 影響が大きい。Windows をクリーンインストールすることがあり、アプリの再プロビジョニングが必要 |

過去 18 か月で、新しいツールが多く追加されています。**Device Recovery Framework** を説明するブログがあり（QR コードが提示されました）、シナリオと判断ツリーが示されています。今回扱うのは次の 3 つです。

| ツール | 使う場面 |
| --- | --- |
| Point-in-time restore | 最近問題が起きて、時間を巻き戻したいとき |
| Cloud Rebuild | デバイスの破損がひどく、ゼロからやり直したいとき |
| Quick Machine Recovery | 大規模でグローバルな障害のとき |

これに加えて、ハードウェアが動かないとき用の Windows 365 Reserve があります。

### 5.7 Point-in-time restore

Windows 365 に着想を得た機能で、名前もそこから借りたと説明されています。前提は単純で、トラブルシューティングを飛ばして、動いていたことが分かっている時点に戻します。

- **スナップショット**: 既定でおよそ 24 時間ごとに自動取得し（復元ポイント）、最大 3 日分を保持する。
- **利点は速さ**: 動いていた状態に戻るので、更新のやり直し、再ログイン、管理への再登録、アプリの再展開が不要。最大で 1 日分程度の差分を再同期する可能性があるが、フルのデバイスリセットより大幅に改善される。
- **所要時間**: 6 月のリリース以降のテレメトリで、エンドツーエンドで約 20 分（デバイスの特性により 15〜20 分）。
- **普及状況**: すでに 2 億台を超える PC で有効になっており、累計で 100 億を超えるスナップショットが取られている。

仕様の詳細も説明されました。

- **対象範囲**: OS ボリューム全体。従来からある System Restore は Windows OS の部分と状態に集中しているが、Point-in-time restore はアプリ、ユーザーファイル、設定まで、すべてを対象にする。
- **ディスク容量**: 変動量により異なる。テレメトリでは、3 日分のスナップショットで約 6 GB。数年前に更新用に実装した Windows の system reserve storage を使って影響を相殺する。ゲーマー、大きな動画ファイル、AI モデルを扱う人は、より多くの容量を使う。
- **自動で有効になる条件**: システムボリュームが 200 GB 以上のデバイスのみ。スナップショットに使うのはディスク全体の最大 2%。
- **IT 管理下のデバイス**: 現時点では既定で無効。今後、既定で有効にすることを検討しているが、グループポリシーと CSP で防ぐ制御を用意する。
- **空き容量**: 20 GB を下回るとスナップショットの取得を止め、常に 20 GB の空きを確保するようクリーンアップする。
- **構成方法**: recovery CSP で構成する。特権のあるユーザー向けに設定画面もあり、管理者権限が必要。スナップショットの間隔、保持ポリシー、最大ディスク使用量などを設定できる。

IT 管理下では既定で無効なので、必要なら有効にすることが推奨されています。問題が起きてから慌てないためです。

### 5.8 Cloud Rebuild

時間を戻しても解決しない場合や、ゼロから始めたい場合のツールです。Aaron 氏によると、10D の optional update（10 月）、または今月の Patch Tuesday 更新である 11B で提供されました（「10D」「11B」は聞き取った表記のままです）。

- PC を、**デバイス用のすべてのドライバーを Windows Update からダウンロードした**クリーンインストール状態にする。
- ディスクを消去する。sanitize オプションがあり、完了後はユーザーを OOBE（out-of-box experience）に導く。そこから会社の資格情報でサインインし、Autopilot などに進める。
- イメージの保守や、USB キーを持って PC を回ってプロビジョニングする作業が要らない。すべてインターネット上の Windows Update（Microsoft が信頼するソース）から取得する。
- 起動は、設定、recovery CSP、WinRE 自体のいずれかから行える。

Device Reset との違いとして 2 点が挙げられました。

1. **自己完結的**: Device Reset はディスク上にすでにある OS を使ってドライバーを取得するが、Cloud Rebuild はそれに依存しない。必要なのは WinRE と接続性だけで、Windows Update からビットを取得する。
2. **カスタマイズ可能**: Device Reset は今ある OS を再インストールするだけだが、Cloud Rebuild では OS のバージョン、言語、エディションを指定でき、その構成に合うドライバーを Windows Update から取得してインストールする。

**事前に整えておくこと**:

- OneDrive と Known Folder Move を構成し、ファイルがクラウドにバックアップされているようにする。
- Autopilot を構成して、プロビジョニングを効率化する。
- Windows settings backup and restore を適切に構成する。

> 注意：Windows 11 26H2 では、設定の**バックアップ**ポリシーは自動で有効になります。一方、**復元**ポリシーは IT 管理者が作成する必要があり、これがあるとユーザーが OOBE 中に設定を選べます。Aaron 氏は、該当記事を検索して手順を確認するよう案内しています（短縮リンクが無いとのことです）。

### 5.9 Quick Machine Recovery（QMR）

大規模でグローバルな障害のためのツールで、Microsoft が修正を作って公開し、世界に配信する場面を想定しています。Aaron 氏は、環太平洋に住む人の地震保険にたとえて、使わないで済めばいいが、あれば安心だと説明しています。

- 1 年前にリリースされ、約 5 億 5,000 万台の PC がカバーされている。
- 起動失敗時に自動で動き、修正は発生している障害に合わせて作られる。
- 最近、Windows Server 2025 で QMR を有効にした。Windows 365 向けは近日対応予定。
- 初回リリース時の大きなフィードバックは「IT が制御したい」だった。そこで 9 月に **Autopatch** での QMR サポートをリリースした。品質更新ポリシーで展開を制御でき、ロールアウトの承認、一時停止、再開ができる。QMR の修正が環境に届いた際の展開状況のレポートもある。

### 5.10 WinRE の改善

WinRE は復旧の基盤で、OEM があらゆる PC にプロビジョニングしており、概ね本体の OS と並行して最新に保たれます（改善にも取り組んでいる）。Windows Update が自動で更新を行い、安全な復旧環境となります。

QMR と Cloud Rebuild は接続性に依存します。以前は WinRE 内で Wi-Fi に手動で接続するか、Ethernet を挿す必要がありました。最近、次の改善が入りました。

1. **保存済み Wi-Fi プロファイルの再利用**: 本体の OS で自動接続に設定されているものを、WinRE が読み取って使う。
2. **WPA Enterprise（802.1x）への対応**: メインの Windows ボリュームにプロビジョニングされたマシン証明書ベースの 802.1x を再利用し、シームレスに接続する。

ユーザーが Wi-Fi ネットワークを選び、captive portal が無いことやパスワードを覚えていることに期待する必要がなくなる、という説明です。

> 注意：カスタムイメージやカスタム WinRE イメージを展開している場合は、**ネットワークドライバーが入っているか**を確認してください。OEM は必須として入れていますが、自前で展開するイメージは確認が必要です。接続性は、QMR のテストモードや Cloud Rebuild で試せます。

### 5.11 Recovery Remote Management Framework

Aaron 氏はこれを、現代的な復旧体験を完成させる「欠けていたピース」としています。9 月にリリースされた、Windows の低レベルの機能群で、管理ソフトウェアが WinRE と統合するプラグインを作れるようにします。

現状は、デバイスが WinRE に入っても、誰もそれを知りません（「ブラックホール」）。ユーザーがヘルプデスクに電話し、画面の状態を説明し、復旧手順を手作業で案内する必要があり、場合によっては人を現地に送ることもあります。この仕組みは、壊れたデバイスを管理サービスに安全に接続し、truck roll（人の派遣）を不要にします。

- 管理ソフトウェアのベンダーがプラグインを作る。プラグインはそのベンダー固有で、バックエンドに安全に接続する。
- WinRE のヘルスチェック、アラート、Point-in-time restore などの復旧操作の制御などを公開できる。
- エンドユーザーは待つだけで、管理者が Intune ポータルから構成・修復を進められる。

**Intune** は統合に取り組んでおり、現在プライベートプレビューです（QR コードが提示されました）。最初は Point-in-time restore をつなぐ作業をしています。ネイティブのダッシュボードで、デバイスが復旧モードにあることが見え、Point-in-time restore を開始し、スナップショットを選び、完了まで進捗を監視できる、という説明です。

### 5.12 復旧に備えるためのヒント

1. **WinRE が正しく構成されているか確認する。** `reagentc /info`（発表では「RE agent slash RE agent C slash info」と読み上げ）で状態と最新性を確認する。
2. **Point-in-time restore と QMR を有効にする。** どちらも有効でないと動かない。Point-in-time restore はスナップショットが必要で、QMR は自動で動かすためにオンにする必要がある。Cloud Rebuild は有効化の必要がなく、Windows をダウンロードするだけ。
3. **BitLocker の回復キーを用意しておく。** WinRE には管理者や認証済みユーザーとしてログインする機能がないため、悪意ある者でなく所有者による操作であることを確かめるのに、BitLocker の回復キーを要求する。Point-in-time restore と従来の Device Reset は、WinRE 経由でこれを必要とする。ヘルプデスク経由でも、AAD の回復ポータルでのセルフサービスでも、ユーザーが回復キーを入手できるようにしておく。

### 5.13 Windows 365 Reserve（Roop 氏）

WinRE が使えない場合、つまりデバイスを紛失した、プールに落とした、盗まれたといった場合には、別の解決策が必要で、それが Windows 365 Reserve です。

Windows 365 には、働き方に応じた選択肢があります。

| 製品 | 想定する使い方 |
| --- | --- |
| Windows 365 Enterprise | デスクトップに 24 時間 365 日アクセスしたい |
| Windows 365 Flex | シフト制の業務 |
| Flex Shared | タスクベースの業務 |
| Windows 365 Reserve | 障害時などに一時的な Cloud PC が必要 |

Reserve は、**Reserve ライセンスをユーザーに割り当てるだけ**です。障害が起きたら、ユーザー自身が代替の PC を取得できます。代替は物理デバイスではなく Cloud PC で、使い慣れたアプリと設定が入っています。元のデバイスが戻ったら、Reserve の Cloud PC は返却できます。会場では、Intune を使っている人が多いことを確認し、すでに適切なインターフェースがあると話しています。

Reserve はいま大きな注目を集めており、レジリエンスの観点から、組織全体に Reserve ライセンスを用意する組織もある、と述べられました。目指すのは「デバイスにトラブルがあってもユーザーが生産的でいられる、頼れるセーフティネット」です。

**ライセンス延長**: Reserve の Cloud PC は 10 日間のものです。物理 PC の復旧が 10 日を超える場合に備え、ユーザーごとに最長 30 日程度まで Reserve ライセンスを延長できる機能が追加されました。

### 5.14 Windows 365 のレジリエンス強化

Cloud PC をメインの作業場所とする場合も、ネットワークが不安定だったり障害があったりするため、レジリエンスは重要です。投資は 2 つのカテゴリに分けられています。

1. ユーザーに影響が出る前に、混乱を防ぐ。
2. 混乱が起きたとき、アクセスをより早く復旧する。

ここでは 3 つが紹介され、投資の全体はブログで詳しく確認できると案内されています。

**(1) Windows 365 Early Release**: IT 管理者の最悪の悪夢は、ユーザーのほうが先に問題を知り、夜に電話してくることだ、と話しています。Early Release は、本番のユーザーが見る前に、サービス更新を確認できるようにします。QA 用のテナントで Early Release を有効にすると、本番テナントより先にそのテナントにサービス更新が現れます。設定は簡単で、本番に入る前に更新を検証できます。さらに、変更内容の通知が届き、問題が出たときはサポートが対応し、必要なら展開を止めて本番に進まないようにすることもできます。

**(2) Admin Operations Mode**: SaaS では制御を失うのではないか、という IT の懸念に応えるものです。Windows 365 は、最新のハードウェアや適切なキャパシティを確保するため、バックエンドで作業します。その作業が、管理者が計画している他の運用（例: すべての Cloud PC へのセキュリティ展開）の妨げにならないよう、管理者が週次・月次の運用を行う時間帯をスケジュール設定すると、Microsoft 側はその間引き下がります。

**(3) 管理者向けの AI アシスタント**: ドキュメントを参照してガイダンスを出す AI ではなく、テレメトリと Windows 365 のベストプラクティスに基づく AI であり、点と点をつなぎ、次にすべきことを示します。レポート・管理の体験に統合されています。発表者はこの機能を「最近プレビューに入った」と説明しています。

## 6. デモ・手順

このセッションにはデモがあります。録音は音声のみのため、画面の細部は確認できません。以下は発話で語られた内容の範囲です。

### 6.1 Cloud Rebuild のデモ（Aaron 氏）

Aaron 氏は「大幅に早送りされているので、1 分ほどで終わると期待しないでください」と断っています（実際の所要時間は発表では示されていません）。

1. PowerPoint で作業中のユーザーを想定する。デバイスが 3 回クラッシュし、最終的に Windows Recovery Environment（WinRE）に入る。
2. バックグラウンドで Quick Machine Recovery と Startup Repair が動くが、このケースでは何も見つからない。
3. ユーザーは troubleshoot メニューから Cloud Rebuild を選ぶ。デバイスを誤って消さないよう、いくつかの確認プロンプトが出る（実際にデバイスを消去する）。sanitize オプションの確認も出る。
4. 「Erase and install」をクリックすると、Windows がこのモードで起動し、Windows Update にドライバーがあることを確認し、すべてをダウンロードしてインストールする。
5. 最終的に OOBE に入り、通常のプロビジョニングが進む。復元する設定が選択されており（Windows settings backup and restore の機能）、アプリのプロビジョニングも行われる。
6. デスクトップが表示され、タスクバーの色などの設定が復元されている。OneDrive 上にアプリがあることが確認でき（発話は「the apps are present in OneDrive」）、ユーザーは PowerPoint で作業を再開できる。

### 6.2 Windows 365 Reserve のセットアップ（Roop 氏）

Intune ポータルでの管理者操作です。

1. Intune ポータルの Cloud PC のセットアップ画面で、ユーザー向けのライセンスのプロビジョニングポリシーを設定する。
2. ライセンスの種類として **Reserve** を選ぶ。
3. Reserve の Cloud PC を置く地域（geography）を指定する。
4. シングルサインオンを有効にする。
5. ユーザーが受け取るイメージ（ユーザーが使うアプリが入ったもの）を選ぶ。
6. 残りの設定を済ませ、既定値を設定する。
7. ライセンスを割り当てるユーザーとして、IT 部門を選ぶ。
8. プロビジョニングポリシーを作成する。

IT 部門の負荷を減らす追加設定が 2 つ示されました。

**ユーザー起点のプロビジョニング設定（user initiated provisioning）**
1. 障害時にユーザーが Windows アプリから Cloud PC を自分で作成できるようにする設定を作る。IT に電話せずに済むようにするため。
2. この権限を与えるユーザーの集合を選び、ポリシーを作成する。

**非アクティブ時のプロビジョニング解除**
1. Reserve は 10 日間の Cloud PC。使っていない期間を 10 日に数えたくないため、一定日数アクティブでない場合にデプロビジョニングするポリシーを設定する。
2. デモでは日数を 1 日にしている。既定は 3 日。
3. 割り当てると、指定日数の間 Cloud PC に操作が無ければ自動でデプロビジョニングされ、その Cloud PC を必要なときにユーザーに返せる。

### 6.3 エンドユーザー側の操作（Roop 氏）

1. 使い慣れた Windows アプリを開き、自分の Reserve Cloud PC が表示されることを見る。
2. プロビジョニングをクリックする。Cloud PC のセットアップには数分かかり、バックエンドで VM などが作られる。
3. 準備ができたら、アイコンをクリックして Cloud PC に接続し、通常の PC と同じように作業する。
4. 作業が終わったら、Cloud PC を返却できる。自動デプロビジョニングを設定していれば、3 日ほどで実行される。

### 6.4 Reserve ライセンスの延長（Roop 氏）

1. 10 日を超える必要があるユーザーを選ぶ。
2. Cloud PC へのアクセスを 10 日間延長する。
3. 残り日数が 10 日から 20 日に更新されたことが示された。

### 6.5 Windows 365 のレポート・モニタリングと AI 管理者アシスタント（Roop 氏）

Intune ベースのポータルにある、新しい reporting and monitoring ページのデモです。

1. 上部の 4 つのタブを順に説明する。
   - **Connection health**: 接続の健全性の推移。
   - **Configuration monitoring**: Cloud PC 環境全体の構成状況。
   - **License and utilization**: ライセンスの利用状況と最適化の余地。
   - **Users and devices**: デバイス単位の詳細。
2. よくあるトラブルシューティングとして接続障害のシナリオを示す。ダッシュボードに多数の接続失敗が出ている。
3. admin AI assistant を開く。アシスタントは、失敗はインドでホストされている Cloud PC から出ていて、通常のベースラインを上回っていると答える。
4. さらに掘り下げると、失敗の大半は 3 台のデバイスから出ていると特定される（「ランダムなデータ」だと断っている）。
5. 失敗の詳細を見ると、接続元がスイスで、接続がインドとスイスの間で切り替わっており、人間には不可能な動きだと指摘する。接続に何かおかしい点がある。

## 7. 注意点・発表者の気付き

- **Point-in-time restore は IT 管理下では既定で無効**（現時点）。有効にしないと使えません。今後は既定で有効にすることも検討中ですが、グループポリシーと CSP で防ぐ制御が用意されます。
- **自動有効化の条件がある。** システムボリュームが 200 GB 以上のデバイスのみ。使用量は最大でディスクの 2%、空きが 20 GB を下回るとスナップショットを止めてクリーンアップします。ゲーム、大きな動画、AI モデルがあるデバイスでは、スナップショットが大きくなります。
- **QMR は有効にする必要がある。** 自動で動かすためです。Cloud Rebuild は有効化が不要です。
- **Cloud Rebuild はデバイスを消去する。** 実際に消去されるため、確認のプロンプトが出ます。事前に OneDrive の Known Folder Move、Autopilot、設定のバックアップと復元を整えておくことが復旧の速さを左右します。
- **設定の復元ポリシーは、管理者が作る必要がある。** 26H2 では、バックアップのポリシーは自動で有効ですが、復元は自動ではありません。
- **カスタムイメージでは、ネットワークドライバーを入れる。** WinRE の接続性に必要です。
- **BitLocker 回復キーを使えるようにする。** 無いと、Point-in-time restore や Device Reset を WinRE から実行できません。
- **WinRE の状態を `reagentc /info` で確認する。**
- **Recovery Remote Management Framework は、管理ソフトウェアのプラグインが前提。** Intune の統合は現在プライベートプレビューです。
- **Reserve の Cloud PC は 10 日間。** 延長はユーザーごとに最長 30 日程度。使っていない間はデプロビジョニングするポリシーで、日数を消費しないようにできます。
- **AI 管理者アシスタントは、デモ中の説明では「最近プレビューに入った」段階。**
- **復旧計画を訓練する。** 障害が起きていない時に、復旧計画が機能するかをテストし、ドリルを行うことを、発表者は繰り返し勧めています。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。具体的な顧客事例（企業名）は、発表には出てきません。

- **障害の予防**: ドライバーのコードをカーネルから外す、標準化する、SBOM と AI 分析で検査する、といった取り組みにより、ドライバー起因の停止や脆弱性の機会が減る。
- **速い復旧（Point-in-time restore）**: 更新、再ログイン、再登録、アプリ再展開が不要で、エンドツーエンドで約 20 分。2 億台超で有効、累計 100 億超のスナップショット。
- **イメージも USB も不要（Cloud Rebuild）**: Windows Update から取得するため、イメージの保守や USB キーによるプロビジョニングが要らない。OS バージョン、言語、エディションを指定できる。
- **大規模障害への備え（QMR）**: 約 5 億 5,000 万台の PC をカバーし、Autopatch により、IT が展開を承認・一時停止・再開し、状況を確認できる。
- **現地対応の削減**: WinRE が管理サービスにつながれば、truck roll をせずにリモートで修復できる（Intune は private preview）。
- **物理デバイスが使えなくても仕事を続けられる（Reserve）**: ライセンスを割り当てるだけで、ユーザー自身が代替の Cloud PC を取得できる。IT への電話が減る。
- **Windows 365 の更新リスクの低減**: Early Release、通知、Admin Operations Mode により、更新の事前検証と、自社の運用との衝突回避ができる。
- **原因特定の効率化**: AI 管理者アシスタントが、テレメトリとベストプラクティスに基づいて、問題の切り分けと次の手順を示す。

## 9. まとめ

このセッションは、Windows のレジリエンスを「予防」と「復旧」に分けて説明しました。予防では Driver Quality Initiative が、Architecture、Trust、Lifecycle、Measure の 4 本柱でドライバーのリスクを減らします。復旧では、Point-in-time restore、Cloud Rebuild、Quick Machine Recovery の 3 つの新ツールと、WinRE の接続性の改善、Recovery Remote Management Framework が紹介されました。物理デバイスが使えない場合は、Windows 365 Reserve が代替の Cloud PC を提供します。

実務で最初に行うこととして、WinRE の状態確認、Point-in-time restore と QMR の有効化、BitLocker 回復キーの準備、Cloud Rebuild に備えた OneDrive・Autopilot・設定の復元ポリシーの整備が挙げられました。そのうえで、**復旧計画を用意し、障害が起きていないうちにドリルで試す**ことが、最後の呼びかけです。
