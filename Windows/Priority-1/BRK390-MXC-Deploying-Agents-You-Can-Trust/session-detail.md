# BRK390 MXC: Deploying Agents You Can Trust

## 1. はじめに

このセッションは、Windows の Platform 部門が進めている **MXC（Microsoft Execution Containers）** を紹介するものです。AI エージェントを「信頼する」のではなく、OS 側で動作範囲を制限することで、エージェントを安全に動かすための基盤を解説します。

「サンドボックスは 1 つあれば足りる」わけではありません。タスクごとに必要な権限は異なるため、プロセス、セッション、仮想マシン、クラウドといった複数の隔離方法から、ポリシーに従って選べるようにするのが MXC の考え方です。後半では、セッション、micro VM、Azure 上の micro VM、Windows 365 for agents の 4 つの実演が行われました。OpenAI のゲスト講演もあります。

> 補足：MXC は「初期段階にある」と登壇者自身が述べています。オープンソースで公開開発されており、現時点ではコンテナーごとにポリシーの書き方が揃っていないなど、制約も説明されました（7 章）。

## 5. 発表内容の詳細

### 5.1 なぜ「1 つのサンドボックス」では足りないか

登壇者は、1 つのサンドボックスにエージェントを入れて「効果的で役立つ」状態にしようとすると、ファイルもネットワークもほぼすべてのリソースを許可することになり、サンドボックスが穴だらけで実質的にサンドボックスでなくなる、と指摘しています。

そこで目指すのが、**タスク単位の権限（task-scoped access）** です。エージェントが立てる計画のステップ（調査のための情報を集める、ドキュメントを読む、コードを評価するなど）ごとに、必要な権限だけに絞ります。最小権限（least privilege）の考え方です。

もう一つの点は、コンテナーの中での権限です。エージェントがコンテナーの中で制約を受けていないと、コンテナーから脱出する攻撃が報告されているとおり、抜け出す方法を見つけてしまいます。コンテナー内で管理者権限を持たなければ、脱出ははるかに難しくなります。爆発半径（blast radius）を抑えるとは、タスクに与えた権限を抑えることだ、という説明です。

### 5.2 業界で収束している 3 つのニーズ

| ニーズ | 説明 |
| --- | --- |
| containment | 爆発半径を抑える。エージェントにできること・できないことを明確にし、エージェントの外から制御する |
| identity | マシン上で動くアプリやプロセスの ID なのか、エージェント自身に与えられた ID（独自の資格情報を持つ）なのかが混同されがち。規制の厳しい業界では、ユーザーが何を依頼し、エージェントが何をし、その権限がどこから来たかを知る必要がある |
| governance | エージェントが破れないポリシー（能力の絶対的な上限と下限）をどう定義するか |

この発表は、主に containment を扱います。

登壇者は、業界の取り組みはすべて「エージェントや操作、プロンプトをどこまで信頼するか」という前提に基づいており、前提が異なるので「万能の答えはまだない」と述べています。隔離、ID、信頼とガバナンスのモデルが複数あり、エージェントは人間が観察も制御もできない速度で動けるため、ポリシーを理解できる形で表現する方法が業界の課題だとしています。

### 5.3 隔離方法のスペクトラム

左から右へ、次のように紹介されました。

| 隔離の種類 | 説明 |
| --- | --- |
| プロセス（process isolation） | マシン上の個別のプロセス。多くはユーザー自身の ID で動く。コマンドラインや TUI ベースのエージェントがこの形。何にアクセスできるかを制御する |
| セッション（session） | エージェントのセッションやチャットではなく、Windows のセッション（個別のユーザーに紐づく）。例として、Microsoft Store の OpenClaw では、gateway が別ユーザーとして端末にインストールされ、Task Manager で確認できる。エージェントの動作は別のユーザーから行われるので、他の形の隔離よりも守りやすい境界になる |
| 仮想マシン | ハードウェアに裏づけられ、Windows カーネルとは別のカーネルを持つ。WSLC やその他の VM をサポート |
| micro VM | 後述。ミリ秒オーダーで起動し、メモリ使用量はプロセスに近く、ディスク上のイメージは 50〜60MB を目標にしている |
| クラウド | ガバナンス、データの管理、データ主権が必要な場合。BYOD の信頼できない端末で、ローカルのエージェントを使いつつ、実際の処理はデータを管理できるクラウドで行う、といった使い方 |

micro VM の動機として、Hyper-V で Windows のイメージを起動するのに約 90 秒かかり、ファイル数を数えるといった簡単な呼び出しのためには長すぎる、という例が語られました。

OpenClaw の綴りは、前半では「OpenClaw」、後半の発話では「Open Cloud」と聞こえます（音声認識の都合で表記が確定できません）。

### 5.4 MXC の考え方と動作モデル

MXC の前提は、**「万能のコンテナーはない」** ことです。最小権限は、サンドボックスの中に最初からすべての権限がある状態では強制しにくい、と述べています。必要なリソースを選び、それぞれの制約を決め、ID、カーネルを共有するか分けるか、必要なリソース量などの軸ごとに判断する必要があります。MXC は、その判断をするための**プラットフォーム**を目指し、エージェント、ハーネス、ポリシーの強制を行うものが、OS の機能を使えるようにします。

動作モデルは次のとおりです。

1. プロンプトから始まる。エージェントは許可を求めることが多く、ユーザーが関与する。IT 部門の制約もある。
2. エージェントは、ワークロードをもとに、最小権限の隔離を定義・予測しようとする。
3. MXC SDK が、それらのポリシー情報を受け取り、エージェントが求めたもの、ユーザーが許可したもの、OS が強制するものと整合するよう調整して、境界を明確にする。

**クロスプラットフォーム**であることも特徴です。ポリシーの構造を定義する API は 1 つで、Linux の bubble wrap、Mac の seatbelt、Windows のプロセス隔離のどれでも、ポリシーの形は一貫しています。それを各 OS・各コンテナー向けの実装に変換する複雑さは MXC が引き受けます。

> 注意：指定したポリシーを、選んだプラットフォームやサンドボックスで実現できない場合、MXC は黙って失敗せず、明示的に伝えます。「コンテナー X を起動できなかったので別のものでよいだろう」とポリシーが黙って弱くなることは避けたい、と説明されました。

プロンプトの扱いについて、通常は悪意のないものとして扱いますが、必ずポリシー層を通し、リソースへのアクセスが許されるかを確認し、プロンプトを「ポリシーが強制できる認可の集合」に変換します。エージェントが実際に取った行動が、プロンプトから導かれる認可と合っているかも確認します。

例として、「失敗しているテストをエージェントに調査させる」場合を挙げています。リポジトリが手元にあるのでプロセスで実行する、自分の作業とエージェントの作業を分けたいのでセッションにする、テストが危険な操作をするので micro VM に入れる、大規模なコンパイルとテストのリソースが必要なのでクラウドで実行する、といった選択肢がすべてあり得ます。

現時点では、どのサンドボックスを使うかは**エージェントの開発者が決定的に選びます**。将来は、プロンプトやタスクを見て適切なコンテナーに振り分けることも考えられるが、「まだそこには至っていない」と述べています。

### 5.5 ゲスト講演：OpenAI の David Wiesen 氏

David 氏は、以前は Codex と呼ばれ、現在は ChatGPT とも呼ばれる製品に携わるエンジニアです。ソフトウェアエンジニア向けにコーディングを手伝うエージェントとして始まり、今は知識労働の多くのケースに広がっています。ユーザーの多くは自分のノート PC でアプリを動かすため、サンドボックスは不可欠で、「エージェントができること・できないことを伝えるサンドボックスがなければ信頼できない」という姿勢です。

- 1 年余り前に入社した際、Windows でのサンドボックス化を任された。独自の（bespoke）サンドボックスを作ったが、開発、テスト、機能と安全性の確認に何か月もかかる大きな作業だった。
- 当日、エージェントに尋ねたところ、その独自の Windows サンドボックスは**約 50,000 行**のコードだった。
- 課題：アプリケーションの立場で、エージェントの動作をサンドボックス化するのは、OS 自体ではないので正しく実装するのが非常に難しい。ここ数か月でエージェントは非常に賢くなり、邪魔になる制限があれば回避しようとする。「OS 自身でも難しいかもしれないが、OS でなければ確実に難しい」と述べた。
- 数か月前に MXC の進展を知り、インターフェースが求めていたものに近かったので、レガシーのサンドボックスから MXC へ移行している。
- 利点：保守するコードが大幅に減る。OS のサポートがある。Windows に機能が増えたとき、MXC がそれを公開してくれるので自社で対応しなくて済む、と述べている。
- 現状：同社のアプリを Windows で使っているユーザーの**約半数**が、MXC 経由でサンドボックス化されている。100% を目指している。
- 現在の方式はプロセス隔離中心で、Codex のエージェントが実行したいプロセスは、実行時にそれぞれサンドボックス化される。「旅の始まり」の段階で、ほかに何ができるか楽しみにしている。

> 補足：David 氏の講演の後、登壇者は、プロセス隔離のデモを何度も行ってきたこと、David 氏が ChatGPT に組み込んだこと、GitHub Copilot で今日動作していることを述べています。Windows でプロセスによる隔離を使うのは自然な方法だという位置づけです。

### 5.6 今ある機能と今後

登壇者は、MXC はオープンソースのリポジトリとして公開開発していると述べています。

**今日できること**

- ツールごとのタスク単位の実行
- バックエンド（どのコンテナーか）を明示的に選ぶ
- エージェントを動かす ID を選ぶ

**現在の課題**

- コンテナーごとに違いがあり、ポリシー言語や制御の表現が統一されていない。
- 異なる種類のコンテナー、デバイス、ID にまたがって、付与した権限が適切に及ぶようにする仕組みが必要。
- ポリシーの拒否やコンテナー内の動作を、使える観測データとして出す仕組みが必要。

**今後**

- コンテナーの選択を自動にする。ポリシーに暗黙に含まれ、OS が保証・強制する形を目指す。例として「この人がインターネットに接続できるのはここだけにしたい」と言えば、OS が最も効率的で安全な方法を選ぶ。
- audit と learning モードのツール。拒否の理由を理解するため。
- アクションに関するテレメトリの拡充。

観測性について Stuart 氏は、今回のデモでは見せていないが、エージェントが脱出を試みた場合に、それを IT 部門やエージェントの中核に伝えるための観測データを提供したい、と述べています。エージェントの ID で行動を帰属させ、ポリシーに合致しているか、認可していないことを試みていないかを把握できる基盤を作る、という目標です。システムは 1 つで完結せず「層」であり、OS が中核の強制を担い、その上に MXC のポリシーエンジンがあり、多くのシステムが利用する、という構図が示されました。

## 6. デモ・手順

このセッションにはデモがあります。ただし録音は音声のみのため、画面の細部（ボタン、入力値、画面構成）は確認できません。以下は、語られた範囲を、語られた順に整理したものです。

### 6.1 デモ 1：セッション隔離（Windows のセッション）

デモの前に、Microsoft Store から入れられる OpenClaw もセッション隔離を使っていると紹介されました。セッション隔離では、エージェントが人間とは別のアカウントで動きます。プロファイルやポリシーも別になり、エージェントに対する制御は OS のかなり深い部分で強制される、という説明です。

シナリオは、Microsoft の財務アナリストが、最新の決算のレポートを書くというものです。

1. SEC や Yahoo などから集めた Microsoft の情報とデータを、あるフォルダーにダウンロードしておく。
2. OpenCode（トランスクリプトでは「open code」。音声認識の都合で表記は確定できません）というオープンソースのエージェントに MXC のサンドボックスを使えるよう修正を加えたものを起動する。
3. エージェント自身に、自分が動いているサンドボックスについて尋ねる。CPU 構成、マシン名など。この場合、マシン名と CPU は、ローカルの Windows マシンのものだった。
4. 違いは、一時フォルダー（temporary folder）の場所が**別のユーザーのもの**になっていること。このセッションでは別のユーザーアカウント、別の Windows セッションで動いており、別の画面、入力スタック、デスクトップを持つ、と説明された。
5. データをもとに簡単なアブストラクト（abstract）を書かせる。同時に、サンドボックス内で動いていることを示させる。「who am I」で、別のユーザーとして動いていることが示された。
6. 新しいアブストラクトが作成された。**別ユーザーは既定ではユーザーのデータにアクセスできないため、MXC がそのフォルダーへのアクセスを許可した。** サンドボックスがポリシーを出し、「ユーザーのフォルダーへのアクセスを許可してよいか」を解釈して許可した、と説明された。

### 6.2 デモ 2：micro VM

micro VM は、Microsoft Azure Research（Microsoft Research のシステムグループ）が作った技術に基づくと説明されています。MXC には Nanvix というコードがあり、Nanvix マイクロカーネルを Azure のコードに追加して作ったのが、Azure Container Instances の NVX だそうです。この技術が Windows に導入され、OpenVMM（仮想マシンモニター）と Windows hypervisor platform が変更されて、軽量で高性能なローカルの micro VM が動くようになる、とのことです。

1. 上司に頼まれたプレゼンテーションを作るため、Python などデータの解釈に必要なツールが入った micro VM のイメージを使う。
2. 起動して、エージェントに「どのサンドボックスで動いているか」を尋ねる。起動の速さが示され、ローカルの小さな micro VM は**約 100〜150 ミリ秒**で起動すると説明された（標準的な VM の起動時間にも言及があるが、聞き取りが不明瞭）。
3. 軽量な Linux カーネルが NVX サンドボックスの中で動き、ハイパーバイザーの境界でローカルマシンから完全に切り離されている、と説明された。
4. エージェントに、データをまとめて簡単な PowerPoint を作るよう依頼。micro VM が立ち上がって実行され、Microsoft の財務に関するプレゼンテーションができあがった。

### 6.3 デモ 3：Azure での micro VM

1. ローカルで使ったのと同じ micro VM イメージを、Azure でも実行できると説明。実際に Azure で動かす。
2. エージェントに「どこで動いているか」を尋ねると、Azure でリソースがプロビジョニングされ、エージェントのサンドボックスが起動する。ネットワークが動くことを願う、と述べた上で、結果が表示された。
3. 表示内容は、Azure Container Instance で、CPU 8 コア、メモリ 32GB。ローカルと同じ dev container イメージを使っていた。
4. 次に、手元のマシンにはない機密性のあるデータを使い、CPU を必要とする分析を行わせる。8 コアで多くのメモリを持つマシンを確保したので、ローカルのマシンで足りなければ Azure を使える、という説明だった。
5. 結果：エージェントは、同じ OpenCode から、セッション、ローカルの micro VM、Azure の順に実行した。Microsoft の多くのデータを分析し、将来に対する Microsoft の業績の**モンテカルロ・シミュレーション**を SVG として出力した。重い分析は Azure で行い、ローカルにないリソースとデータを使った。Azure を使うために、エージェントに新しいことを教える必要はなかった、と説明している。1 つのプロンプトに対して実行方法が複数あり、それぞれ ID、リソース、隔離境界のポリシーが異なる、という点が強調された。

### 6.4 デモ 4：Windows 365 for agents（動画）

こちらはライブではなく、録画された動画です。

1. 直前のデモは Azure 上の Linux ベースの micro VM だったが、W365A は Azure 上の Windows コンテナーでエージェントを動かすものだという。MXC のコードを修正し、Windows 365 for agents の技術スタックを使えるようにしている。プロンプトは「やや作為的」で、GitHub Copilot のアプリを使っている。
2. エージェントが MXC を呼び出し、ポリシーを渡す。Azure クラウド上で PC（仮想マシン）のインスタンスがプロビジョニングされ、そのインスタンスの**セッション ID** が返ってくる。
3. プロセスや micro VM のように「起動して使って破棄する」使い捨てのコンテナーとは違い、VM はライフサイクルが複雑で、**ある程度の永続性**が得られる。ツールやデータの準備に時間がかかる場合に、状態を失わずに済む。
4. Stuart 氏のデモと似ているが、この場合はデータがクラウドにあり、IT のポリシーで管理されている。ローカルでは実行できない。
5. エージェントがタスクを完了し、markdown のレポートが返る。生データは残らない。
6. ユーザーが「リソースの利用は終わった」と明示的に伝えると、MXC がライフサイクルに従って仮想マシンを破棄し、リソースを解放する。

## 7. 注意点・発表者の気付き

- **MXC は開発の初期段階。** 登壇者は「早い段階にいる」と明言しています。
- **ポリシーの記述は統一されていない。** 現時点では、コンテナーごとにポリシー言語や制御の表現が異なります。
- **隔離方法の選択は、今は開発者が決める。** 自動選択は今後の課題です。
- **アプリ自身がエージェントをサンドボックス化するのは難しい。** OpenAI は独自実装に約 50,000 行を要し、エージェントが回避しようとするため、確実にするのが難しいと述べています。
- **サンドボックスが穴だらけになる罠。** 1 つのサンドボックスですべてを許可すると、実質的に意味がなくなります。
- **ポリシーを黙って弱めない。** 実現できない場合は明示的に伝える設計です。
- **ID の混同。** アプリやプロセスの ID と、エージェント自身に与えられた ID は区別して考える必要があります。
- **Windows 365 for agents の VM は、使い捨てではない。** プロセスや micro VM と違ってライフサイクルが複雑です。デモでは、ユーザーが明示的に解放を指示し、MXC がそれに従って VM を破棄していました。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- OpenAI の事例：独自のサンドボックスは約 50,000 行だった。MXC に移行すると、保守するコードが大幅に減り、OS のサポートで新しい機能も使える。現在、同社アプリの Windows ユーザーの約半数が MXC 経由で動いている。
- 1 つの API でポリシーを定義し、Windows、Linux、Mac で同じ形のポリシーが使える。
- micro VM は、約 100〜150 ミリ秒で起動し、Azure でも同じイメージが動く。
- クラウドでの実行：機密データを IT のポリシーの下に置き、ローカルに残さずに処理できる（デモの説明）。

## 9. まとめ

MXC は、エージェントを信頼する代わりに、OS が強制する境界の中で動かすための基盤です。登壇者は、containment、identity、governance の 3 つのニーズのうち containment を取り上げ、プロセス、セッション、仮想マシン、micro VM、クラウドという複数の隔離をサポートし、ポリシーは共通の API で定義できると説明しました。ただし、コンテナーごとのポリシー記述の統一はこれからです。

OpenAI は、約 50,000 行の独自サンドボックスから MXC への移行を進めており、同社アプリの Windows ユーザーの約半数がすでに MXC 経由でサンドボックス化されています。デモでは、同じ OpenCode から、別ユーザーのセッション、ローカルの micro VM、Azure 上の micro VM を順に使い、最後に動画で Windows 365 for agents 上の実行を見せました。今後は、ポリシーの統一、観測性、コンテナーの自動選択が課題です。登壇者の結びの言葉は、タスクから始めて適切な境界を作り、**権限と監督はエージェントの外に置く**、というものでした。
