## 5. 発表内容の詳細

### 5.1 前提：AI と量子コンピューター

**AI。** 登壇者は、AI が業界全体で脆弱性のライフサイクルを加速させていると述べます。「物理法則が変わった」「少しのトークンがあれば誰でもバグを見つけられる」という表現です。防御側では、研究者が脆弱性をより早く見つけ、修正して検証できる一方、攻撃者も同じ能力で攻撃を作れます。MSRC や業界全体に入ってくる脆弱性の件数が増えており、ライフサイクル全体が速くなるので、保護も速くならなければならない、という論理です。

Windows チームも、セキュリティエンジニアリング全体で AI を使っています。脆弱性をより早く見つけ、より早く直し、出荷する保護を継続的に検証します。業界のツールと社内開発のツールの両方を、Windows のコードベース全体、そして出荷前のすべての新しいパッチに使っているとのことです。

続いて、業界全体の変化を Windows に絞って見せるスライドが示されました（内容の数値は音声からは分かりません）。このとき登壇者は、**CVE の件数が増えることは Windows の脆弱性が増えていることを意味しない**と強調しています。問題が特定され、公開され、修正されているということです。目的は、問題の発見から顧客が保護されるまでの時間を縮めること、それが「AI のスピードで動く」ことだと説明しました。

**量子（PQC）。** 長期間有効な暗号化データは、今取得されて後で復号されうること、暗号移行の準備には何年もかかることから、「待つのは選択肢ではない」と述べています。鍵交換については、耐量子（post-quantum）の選択肢がすでに利用できます。認証については、まず自社の証明書の全体像と、それに何が依存しているかを把握することから始めます。今日すべてを変える必要はないが、何があるかを知り、移行の計画を今から始める必要がある、という説明でした。

### 5.2 3 本柱と時間配分

3 本柱は、(1) 安全に始め、安全を保つ、(2) 管理外デバイスを含め、仕事が行われる場所で重要なものを守る、(3) AI の可能性を安全に引き出す、です。Ignite には AI の話が多く、Windows 側でも多数あるため、このセッションでは最初の 2 本柱に集中し、基盤を深く掘り下げる、と説明しています。基盤はエージェント利用を守る作業の全体にも効いてくる、という考えです。

### 5.3 柱 1：安全に始め、安全を保つ

登壇者は、ベースラインの強化、特権とレガシー依存の削減、デバイスを保護された最新の状態に保ちやすくすること、をまとめて紹介しました。

#### ハードウェアセキュリティ

Windows 11 は、TPM 2.0、Secure Boot、仮想化ベースのセキュリティ（VBS）という強いハードウェアセキュリティのベースラインを定めています。新しい点として、サポートされるより多くのデバイスをこのベースラインに引き上げます。**Windows 10 から来る対象デバイスでは、Windows Update が VBS やメモリ整合性（memory integrity）などの保護を有効にしていきます**（発表では "is going to enable" と未来形）。これで Windows 11 のハードウェアセキュリティのベースラインに揃います。Copilot+ PC は、最初から追加のハードウェアに裏付けられた保護を備え、基準をさらに引き上げています。

#### Windows baseline protection

今回の Ignite で発表された **Windows baseline protection** は、**8 つの重要な Windows セキュリティ保護の状態を 1 つの分かりやすいシグナルにまとめる**ものです。機能を個別に確認する代わりに、ベースラインが有効かどうかが分かります。エンドユーザー、IT、アプリ、開発者がこのシグナルを使えます。エンドユーザーはデバイス上の UX で状態を確認でき、アプリやサービスがより強い保証を必要とする場合は、**ベースラインの状態をリモートで証明（attest）**することもできます。

#### Administrator protection

登壇者は「自分も管理者権限は大好きだが、攻撃者も好きだ」と述べ、モデルを変えるものとして administrator protection を紹介しました。

- 既定では標準ユーザー権限で動作する。
- 管理者権限が本当に必要になったときだけ、Windows Hello で本人確認をして、そのタスクのためだけに昇格する。
- 昇格は**分離されており、一時的**。タスクの終了または PC の再起動で権限は消える。

攻撃者はデバイスの完全な管理者権限を持てなくなり、さらに Windows Hello での確認をユーザーにだまして行わせる必要が生じるため、攻撃の障害になる、という説明です。狙いは、ユーザーが誤ってクリックしたマルウェアではなく、**ユーザー自身が Windows を制御し続ける**ことだとされました。

#### Windows endpoint security platform とドライバー品質

Windows endpoint security platform は、サードパーティのドライバーをカーネルからユーザーモードへ移すためのものです。パートナーはサポートされる API を使い、カーネルでの処理は Windows が代行します。セキュリティパートナーと協力して進めており、最も機密性の高い領域のサードパーティコードを減らして Windows の回復力を高め、それが「可用性を通じたセキュリティ」に効く、という説明です。

**Driver quality initiative** は、ドライバーの作られ方、テストされ方、デバイス上での動作に関する取り組みです。セキュリティ製品のカーネルモードドライバーに対して以前から重視していた回復力への取り組みを、Windows のドライバースタック全体に広げるものだと説明されました。

#### NTLM

「セキュリティは足すだけでなく、取り除くことでもある」として、NTLM から脱却する取り組みが紹介されました。登壇者は、環境やアプリでの NTLM の利用を減らすための協力を聴衆に求めています。NTLM は攻撃者が好む場所の 1 つで、Windows から依存を取り除きたいという理由です。移行を容易にするため、Kerberos の機能を拡張しています。

| 機能 | 説明 |
| --- | --- |
| IAKerb（音声では "IA Kerb"） | クライアントがドメインコントローラーに直接アクセスできない場合に役立つ |
| Local KDC | ローカルアカウントにも Kerberos をもたらす |

自分の環境で試し、まだ NTLM に依存している箇所を教えてほしい、とのことです。チームはそうした依存を解消するため、バックエンドで作業を進めています。

#### Autopatch と Hotpatch

修正はデバイスに入って初めて意味があるとして、2 つの機能が紹介されました。

- **Windows Autopatch**：段階的なデプロイと、環境内でどの更新が展開されているかの見える化。きめ細かな制御と、より強い既定値を追加している。
- **Hotpatch**：再起動の遅延をなくす。「更新を展開したが再起動されていない」チームは多く、再起動が保留のままではインストール済みでも意味がない、という問題意識。登壇者は、再起動が年に 12 回ほどから **4 回ほど**に減ると述べている（"something like" という言い方）。

スライドには、8 月の更新の適用状況に関するテレメトリが示され、Autopatch と Hotpatch を使う顧客が、更新のコンプライアンスを速く上げていくようすが見えるとのことです。強調されたのは最終的な数値ではなく、**更新が完全に適用されるまでの時間**です。

### 5.4 柱 2：ID・アプリ・データを仕事の場で守る

この柱は、サインインを容易にし、IT がデバイスとデータを守る手段を増やし、管理していないデバイスでの仕事にも保護を広げる、という整理です。パスワードレスはユーザーにも IT にも簡単であるべきだとして、FIDO Alliance との連携や、Windows Hello、パスキー、セキュリティキー管理の改善が語られました。

#### サインインの改善

1. **Windows Hello Face が PIN 入力中も試行を続ける。** 以前は PIN の選択肢が出ると顔認証が止まっていたが、新しい挙動では顔認証が続き、顔か PIN の先に成功したほうで入れる。デモで、左が旧、右が新の並列映像が示された。登壇者は、デスクトップに早く、より一貫して入れるようになると説明している。
2. **低照度での顔認証。** 暗い環境や夜間に、画面を一時的に明るくして Windows Hello をすばやく通す「face brightness」を使えるようにした。
3. **イベントログの情報追加。** IT から、顔・生体認証と PIN のどちらが使われたかを明確にしたいという要望があった。イベントログに、使用された Hello の方式、そのデバイスで enhanced sign-in security が有効か、どの生体認証・PIN が登録されているか、が追加される。
4. **ハイブリッド参加デバイスへの web sign-in。** これまでクラウド専用デバイスのみだった web sign-in を、Entra のハイブリッド参加デバイスにも拡張した（音声では "intra-hybrid join"）。共有 PC のある組織で、MFA のサインイン方法をより多くのデバイスに広げるのに有用、という説明。
5. **セキュリティキーのタップ位置の表示。** どこにタップするか分からないという声に応え、ディスプレイ上にタップ位置のインジケーターを出す。登壇者は、Windows and Devices のブース（メインのショーフロア）で試せると案内している。
6. **セキュリティキーの管理。** これまではキー内のすべてを削除する必要があったが、個々のパスキーを選んで削除できるようになり、キー全体を初期化する必要がない。IT 向けには、PIN 要件、ユーザー検証（user verification）、エンタープライズ アテステーションの制御も追加される。登壇者は、これが顧客からの最大級の要望だったと述べた。

#### Declarative management

前日のセッションで触れられた管理の変化として、**OMA-DM プロトコルから declarative management へ移行**します。変わる点は 2 つです。

1. ポリシーがデバイスにより速く確実に届く。サーバーとのやり取りやポーリングを待たなくてよい。
2. ポリシー到達後、Windows が**IT の意図した状態にデバイスを保つ**。ネットワーク接続がなくても保たれる。

最初は、証明書、Wi-Fi、VPN といったリソースアクセスから始め、その後ほかのポリシーに広げます。Intune チームと連携して進めており、サードパーティも利用できます。

#### BitLocker TPM + PIN と remote lock

- **BitLocker の TPM + PIN を標準ユーザーでも設定しやすく**：現状は管理者なら簡単に設定できます。しかし、最小特権の標準ユーザーと admin protection を勧めている以上、標準ユーザーも設定できるようにする、という位置づけです。標準ユーザーは、管理者権限も管理者の立ち会いもなしに、自分で PIN を設定できます。IT がポリシーを設定すると、ユーザーに通知が表示されます。クリックして PIN を設定すれば、BitLocker の TPM + PIN で保護されます。
- **Remote lock**：紛失・盗難時に、IT がデバイスをリモートでロックし、見つかった場合にはロックを解除できる。「ワイプまでは望まない」場合の最初の手段という位置づけ。Intune コンソールからのロックコマンドで、デバイスに**カスタムメッセージ**（返却先や連絡先）を表示できる。登壇者は、これは Insider で試せ、Intune で展開され、サードパーティの MDM ベンダーも対応できると述べている（remote lock の説明の締めでの発言）。

### 5.5 管理外デバイスでの仕事（Saud Al-Mishari 氏）

Al-Mishari 氏は、管理外デバイスを 2 種類とします。従業員が持ち込む個人デバイスと、契約社員（contractor）のように、自社ではなく別の会社が管理している端末です。どちらも「管理外」として扱います。選択肢は次のとおりです。

| 選択肢 | 説明 |
| --- | --- |
| Edge for Business | Web ベースの SaaS アプリや Web アプリが中心の場合。Microsoft のセキュアなブラウザーで、Intune のアプリ保護ポリシーで管理する |
| Windows 365 | SaaS 型の提供形態。リモートデスクトップやアプリを最も簡単に提供できる |
| Azure Virtual Desktop | PaaS・IaaS のインフラを自分で管理し、完全な制御のもとで完成形のソリューションを構築したい場合 |

デスクトップアプリやフルデスクトップが必要な場合、あるいは「保護されていてもデバイス上に企業データを一切置きたくない」というリスク許容度の場合に、Windows 365 や AVD が候補になる、という説明です。

Ignite で発表された新機能は次のとおりです。

- **Windows app の Intune アプリ保護ポリシー（MAM）対応**：public preview。
- **Context-based redirection**：Entra の認証コンテキストを使ってアクセス制御の判断をする。**すでに利用可能**。
- **Windows app の input protection**：public preview。キーストロークをエンドツーエンドで暗号化し、キー入力から VM までの独立した安全なトンネルを確立する。暗号化され、相互に認証される。
- **Display protection**：ローカルでの画面キャプチャからディスプレイを守る。登壇者は generally available の機能と述べている。

#### Intune アプリ保護ポリシーと context-based redirection の使い分け

Holdsworth 氏が「なぜ両方必要で、いつどちらを使うのか」と尋ね、Al-Mishari 氏が答えました。決め手は**姿勢（posture）評価をどこで行い、強制をどこで行うか**です。

- **Intune アプリ保護ポリシー**：判断の多くがクライアント側（アプリ内）で行われる。姿勢評価ではデバイス上の何かを見る必要があるためで、他のプラットフォームでも業界はこうしている。
- **Context-based redirection**：制御点をクラウドに移す。判断は Entra からのシグナルに基づき、強制は Windows 365 と AVD のサービス側で行う。

組織のリスク許容度が最初の判断点です。判断をすべてサービス側にし、クライアント側で入力に基づく判断をしたくない場合や、クライアントの対応状況に関係なく制御をかけたい場合は、後者が合います。例として、Windows app が内蔵された LG のモニターで、Intune アプリ保護ポリシーの保護が利用できないケースが挙げられました。

### 5.6 柱 3：AI 時代への備え

この柱は短く、他にも Ignite 内に多くの関連セッションがあると断ったうえで、**Microsoft execution containers（MXC）**と、エージェントおよびツールのガバナンスの 2 点が話されました。

エージェントはコンテンツの作成や変更を加速しますが、そのぶんリスクも増え、「単純な間違いがエージェントを通じて何度も複製されうる」と説明しています。問いは AI を使うかどうかではなく、**どう安全に使うか**です。重要な構成要素は 3 つです。

1. **アイデンティティ**：エージェントにもアイデンティティが必要。人間のユーザーにアカウントを与えてサインインさせてきたのと同じで、Agentic user は人間のユーザーと変わらない。アイデンティティがなければセキュリティ制御を適用できず、監査もできず、自分の操作とエージェントの操作を区別できない。
2. **封じ込め（containment）**：MXC が目指すもの。Windows にはすでに、同じサーバーにログインした複数ユーザーのセッションが分離される仕組みがある。管理者でなければ他人のセッションに入れない。これと同じ境界を、1 台のデバイス上の Agentic user と人間のユーザーの間にも作る。既存のマルチユーザーの挙動を、人間とエージェントの組み合わせに広げる、という説明。
3. **管理レイヤー**：制御を管理できなければ意味がない。Windows の機能を **Agent 365** に統合していく計画で、それにより Entra、Intune、そして Agent 365 で有効になる Microsoft のセキュリティスイートにも統合される、と説明している。

詳細はブログと、Ignite 内の MXC 関連セッションで確認できます。

### 6.1 Windows baseline protection（設定画面）

1. Windows の設定を開く。**セキュリティとプライバシーが別の項目に分かれている**（Windows Security アプリの内容の一部を設定に移し始めているため）。
2. baseline protection では、この例では「action required」と表示される。
3. 有効にしづらい **Secure Boot** を有効にする案内が表示される。多くの設定は単純なオン/オフだが、Secure Boot はユーザーが設定画面に入る必要があり少し難しい。
4. 案内に従うとデバイスが再起動する。
5. 再起動後、設定の「セキュリティ」から baseline protection に戻ると、**すべて保護されている**状態になる。

アプリが「Windows がベースラインに満たないため動かない」とユーザーに伝える場合も、アプリと連携してその状態へ導く、と説明されました。

### 6.2 Administrator protection

1. PowerShell を使う。管理者権限が必要になる。
2. **Windows Hello で本人確認する**。
3. 確認後、元の作業に戻る。

### 6.3 Windows Hello Face の新旧比較

左が旧、右が新の並列映像。旧は PIN が出ると顔認証が止まって失敗し続け、PIN を入れる必要がある。新は、PIN を入力している間も顔認証が続き、先に通ったほうで入れた。映像を再度再生して見せている。

### 6.4 Declarative management

1. 同じデバイスを、左が OMA-DM、右が declarative management として並べる。従来のモデルは、サーバーとの往復を繰り返してポリシーを届けている。
2. VPN を設定した状態で、登壇者がその VPN を**削除する**。
3. バックグラウンドで refresh が行われる（IT が間隔を設定できる）。
4. refresh 後、**VPN が戻っている**。ネットワーク接続がなくても再適用される。

### 6.5 Intune アプリ保護ポリシー（Windows app, MAM）

1. Windows app を起動してサインインする。デモではパスワードだけを使っているが、本番では耐フィッシングのパスワードレス認証を使うと登壇者は断っている。
2. デバイスの**登録（registration）**を求められる。これはデバイスの登録（enrollment）ではない。Entra にエントリーを作り、Intune アプリ保護ポリシーをアプリとデバイスに関連づけ、ポリシーの適用を確認するためのもの。
3. アプリ保護ポリシーが適用される。簡易的な姿勢評価が行われ、**このバージョンのアプリは環境で許可されていない**として、アクセスがブロックされた。OS のバージョンなど、他のチェックも可能と説明されている。

### 6.6 Context-based redirection（管理者側の設定、複数手順）

1. 認証コンテキストのプレースホルダーから 1 つを選ぶ（デモでは Windows 365 向けにコンテキスト **15**）。
2. そのコンテキストを**デバイスのコンプライアンス**に関連づける条件付きアクセスポリシーを作る。これで Entra がコンテキストを判断し、コンテキスト 15 に適用する。
3. Windows 365 で、ドライブとストレージのリダイレクトを選び、**コンテキスト 15 に基づいてリダイレクトを提供する**と設定する。

この設定により、デバイスがコンプライアントで、つまり自社の管理下であればデバイスのリダイレクトが許可され、管理外デバイスではブロックされます。登壇者は、サービス側の制御のため**エンドポイントのプラットフォームに依存せず**、Intune アプリ保護ポリシーとの統合を構築する必要もない点が利点だと述べています。

### 6.7 Display protection

1. 左の Cloud PC は display protection を有効にし、右は無効にしている。
2. 左は、ローカルデバイスからのスクリーンショットで内容が完全に黒くなる。右は自由にスクリーンショットを撮れる。
3. 画面録画でも同様。録画中は両方の内容が見えるが、**再生すると、display protection が有効な側は黒く塗りつぶされ**、右側のみ見える。

### 6.8 デモ形式でない紹介

顔認証の低照度対応、イベントログ、セキュリティキーのタップ位置、BitLocker の通知、remote lock については、デモが行われたと明言する発話は確認できません（BitLocker では「左側に見える通知」とスライドの画像に触れています）。

## 7. 注意点・発表者の気付き

- **CVE 件数の見方**：増加は脆弱性が増えているのではなく、特定・公開・修正が進んでいることを意味する。
- **量子への備え**：認証については、まず証明書の資産と依存関係を把握する。すべてを今すぐ変える必要はない。
- **Secure Boot** は baseline protection の中で有効にするのが難しい項目。
- **NTLM**：依存が残る箇所を共有してほしい、というフィードバックの依頼がある。
- **Hotpatch**：再起動が保留のままでは、インストール済みでも保護されない、という指摘。
- **Intune アプリ保護と context-based redirection の使い分け**：リスク許容度、姿勢評価と強制の場所、クライアントの対応状況で決める。
- デモのサインインはパスワードのみで、本番では耐フィッシングのパスワードレスを使うべき、という断り書きがあった。
- 提供時期（一般提供の日付など）の詳細は、多くの機能で発表では触れられていません。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。具体的な顧客事例は紹介されていません。

- **攻撃面の縮小**：administrator protection、サードパーティドライバーのユーザーモード化、NTLM からの脱却により、特権と最も機密性の高い領域の依存を減らせる。
- **更新が速く届く**：Autopatch と Hotpatch により、より多くのデバイスが、中断を減らしながら早く保護される。再起動は年 12 回ほどから 4 回ほどに減ると登壇者は述べている。
- **サインインの高速化と管理の容易さ**：Windows Hello の改善、パスキー単位の削除、イベントログの可視化。
- **ポリシーの確実な維持**：declarative management により、ネットワークがなくてもポリシーが維持される。
- **紛失への対応**：remote lock で、ワイプせずにロックし、メッセージを表示できる。
- **管理外デバイスでのデータ保護**：Intune アプリ保護、context-based redirection、input protection、display protection。
- **エージェントの安全な利用**：アイデンティティ、封じ込め、管理を組み合わせ、Agent 365 を通じて Entra や Intune と連携する。

## 9. まとめ

AI は脆弱性の発見から修正、悪用までを加速させており、量子への備えも早めに始める必要があります。このセッションは、Windows 側の答えを 3 つの柱で紹介しました。

1. **安全に始め、保つ**：ハードウェアベースラインの引き上げと baseline protection、administrator protection、NTLM からの脱却、Autopatch と Hotpatch。
2. **仕事の場で守る**：サインイン改善、declarative management、BitLocker、remote lock、管理外デバイス向けの保護。
3. **AI 時代への備え**：エージェントのアイデンティティ、封じ込め、管理という方向性。

すべてを一度にやる必要はありません。パスワードレスの加速やデバイスの安全な構成など、自分の環境で重要な 1〜2 個から始めることが勧められています。
