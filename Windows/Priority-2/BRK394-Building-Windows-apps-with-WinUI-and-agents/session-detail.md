# BRK394 Building Windows apps with WinUI and agents​

## 1. はじめに

このセッションは、Windows 向けアプリを WinUI で作る開発者に向けて、「エージェントと一緒に開発する」場合の道具立てと、WinUI プラットフォーム自体の改善状況を紹介する発表です。中心になるのは WinApp CLI というコマンドラインツールです。アプリの新規作成からビルド、実行、性能の測定、UI テスト、パッケージ化と署名までを 1 本のツールでこなせます。CLI なので、人間だけでなく AI エージェントも同じ操作ができます。

発表の前半では、航空機整備士向けの業務アプリ「Hangar」を題材に、一連の開発サイクルを実演しています。後半では、パートナーである Replit のデモ、WinUI プラットフォームの改善点、試験的に提供中の機能、入手方法が紹介されます。質疑応答の時間は取られていません。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK394](https://ignite.microsoft.com/en-US/sessions/BRK394)

## 5. 発表内容の詳細

### 5.1 なぜ WinUI か

WinUI は、新規開発でも、既存の基幹業務（LOB）アプリの移行でも、今後の進路となるプラットフォームだと位置づけられています。強みとして画面に示されたのは、モダンな入力、Fluent デザイン、GPU アクセラレーションです。これらにより、軽くて速く美しいアプリを作れると説明しています。

エージェントとの関係では、「根拠に基づく」（grounded）、「エージェント対応済み」（agent ready）という言葉が使われました。Microsoft がサポートするツール、リソース、スキルに裏付けられているので、エージェントが当て推量で動くことはほとんどない、という意味です。

スケールの面では、コンシューマー向けでもエンタープライズ向けでも、リッチなコントロール、ID（パッケージ ID）、あらゆる Windows API を 1 つのパッケージで利用できると説明しています。前日に Satya 氏が話した新しい内容（エッジでのインテリジェンス。音声認識の都合で表記が確定できません）も含まれるとのことです。

品質面では、年初に Pavan 氏が Windows 全体の品質向上に取り組むとするブログを公開した経緯が紹介され、ネイティブフレームワークの WinUI はその中核になると述べられています。ファーストパーティアプリの採用例としては、ウィジェットと新しい Run 体験が WinUI に切り替わったことが挙げられました。フレームワーク全体のチューニングも行われ、WinUI アプリが既定でより軽く速くなっているそうです。具体的な改善幅の数値は語られていません。

### 5.2 WinApp CLI と開発ループ

WinApp CLI は、アプリの作成、ビルド、実行、検査、テスト、プロファイル、パッケージ化と署名を CLI から行うツールです。CLI なので、人間にできることはエージェントにもできます。リポジトリには、エージェントに WinApp CLI の使い方や調べる場所を教えるスキルとプラグインが含まれており、エージェントが無駄に探し回ったり、でたらめな操作を生み出したりする回数を減らす狙いです。

Visual Studio Code 向けには WinApp CLI 拡張機能があります。CLI の機能の多くに UI を被せたもので、デモではマニフェスト編集と XAML の IntelliSense が使われました。

Visual Studio については、使い続けている人が多いことに触れたうえで、CLI や拡張機能で試している機能は最終的に Visual Studio に戻すと説明しています。Visual Studio は最も完全な IDE であり続け、同じプロジェクト、同じツールチェーンをどこでも使えるという位置づけです。

### 5.3 プロジェクトの新規作成（winapp new）

発表者によると、以前は Windows アプリの開始そのものが開発者の悩みで、クロスプラットフォームのフレームワークを選んで Windows アプリを作らない結果になることもあったそうです。WinApp CLI では `winapp new` を実行するだけで、テンプレート一覧が表示されます。

- 空の WinUI アプリ、ユニットテスト用アプリ、Reactor テンプレートなどから選べる
- テンプレートは .NET のテンプレートと同じものを使い、`dotnet new` 側の更新は WinApp CLI にも反映される
- デモではナビゲーションビュー（左にメニュー、右にページ内容）を選び、アプリ名を Hangar とした
- 生成されたアプリには、最初からパッケージ ID が組み込まれている。通知やスタートメニュー連携のテストがすぐ動く
- Visual Studio の「ファイル → 新規作成」に相当し、ターミナルから始める場合や VS Code 拡張でも同じ

### 5.4 評価用ベンチマーク

発表の途中で、ツールの効果を示す数値が示されています。非公開ベンチマークの結果で、今後はリリースごとに公開ベンチマークを添えて、経時変化を追えるようにする計画だと説明しています（モデルが変わり、良くなっていくため）。

| 評価項目 | ツールなし | ツールあり |
|---|---|---|
| WinApp のコマンドに関する正答率（例：アプリをパッケージ化して） | 37% | 90% |
| 品質チェック（パッケージ化されているか、警告なしでビルドできるか等の採点基準） | 68% | 87%（※） |

> 注意：品質チェックの「ツールあり」の値について、発話では「ツールなしが 60%、ありが 87%」とも聞こえ、前の文脈の 68% と食い違っています。音声認識の都合で、ツールなし側の値（68% または 60%）は確定できません。

ツールなしの場合は、一般的な提案と手作業の探索になりがちだと説明されています。ツールありでは、裏付けのある API、Microsoft が支えるサンプルギャラリー由来の XAML、そしてビルド・実行・テストを循環させるためのツールが使えると述べられています。

### 5.5 試験的に取り組んでいること（フィードバック募集）

ここまでの内容は現在提供済みです。CLI のダウンロード、スキル入りプラグインのインストールができます。それに加えて、次の 3 点が実験段階として紹介されました。QR コードでフィードバックを募っています。

1. **ホットリロード**：Visual Studio で信頼できるホットリロードが欲しいという声を受けた実験。`winapp run` で自動的に動く形を試している。ここでの知見も最終的に Visual Studio に戻す
2. **デザイン時プレビュー**：Visual Studio の拡張機能として開発中。以前のフレームワークにあったデザイナー体験に近く、アプリが実行中でなくても、編集中の箇所がブロックとして表示される
3. **Reactor**：C# で書く WinUI アプリの新しい方式。これまでの MVVM に代わり、React のような モデル・ビュー・アップデート型で書きたいという声に応えるもので、UI を素の C# で書き、1 ファイルでデプロイできると説明されています

> 補足：Reactor について発表者は「Reactor はあとで紹介する」と述べていますが、詳細な説明はこの 1 か所の紹介にとどまります。

さらに、XAML 層と WinUI を動かすエンジンを分離する取り組みにも触れられています。これにより Rust のような言語向けの性能改善がしやすくなり、Rust は WinUI チームへの要望の第 1 位だと述べられています。

### 5.6 Replit によるデモ

Replit のプロダクトリードが登壇しました。最初に会場に挙手を求め、IT・開発・技術周辺の職種の人が大半で、毎日コードを書く人は約 5 分の 1 だったと確認したうえで、「手を下ろした人も含め、全員がコードを書ける」と述べて、Replit と WinUI のエージェント用スキルでそれを示しました。

Replit の紹介として、使命は AI を特に非技術者にも使えるものにすること、Fortune 100 企業の 85% で使われていること、Microsoft Partner of the Year に選ばれたことが語られました。Ignite Hub にも出展しているとのことです。

内容は 6 章のデモで詳述します。

### 5.7 プラットフォームの改善

プラットフォーム側の改善として、5 つの領域が挙げられました。発表者は、これまで約 20 年分のバグや「小さな不満（細かな使いにくさ）」に取り組んできたが、ここ数年は特に集中して潰していると述べています。

| 領域 | 説明 |
|---|---|
| オープンソース化 | WinUI への要望の第 1 位だった。GitHub にすべてが置かれ、コードの取得、ビルド、テストのインフラが公開されている。XAML コンパイラも含まれる。チームは公開の場で作業し、ロードマップも見られる |
| モダンなツール | CLI とターミナルから VS Code、Visual Studio まで。エージェントの力を借りて、より多くのより良い WinUI アプリを作れるようにする |
| 性能 | 今年の Windows の大きなテーマ。アプリの起動時間とメモリ使用量の改善に継続して取り組む（Windows 自身のアプリの改善が参考になる、と述べている） |
| 基本機能・API の穴埋め | ウィンドウ API のギャップを埋める作業中。入力関連の API の穴も認識しており、ゲームパッド入力は最近提供された。X-Bind の不具合修正や API 改善もある |
| コントロール | TableView、チャートコントロール、InkCanvas（手書き入力）など。いずれも現在は実験的パッケージで提供中 |

TableView とチャートコントロールは、どのエンタープライズアプリにも表やグラフがあるという理由で挙げられています。InkCanvas はエンタープライズ以外からも要望が多かったと説明しています。いずれも実験段階なので、フィードバックを求めています。WinUI Gallery にも、これらのコントロールの実験版が追加されたばかりです。

## 6. デモ・手順

デモは 2 つあります。画面上の細かい操作は音声からは確認できないため、語られた範囲だけを書きます。なお、一部の場面（Copilot セッション）は、事前に実行しておいたものを見せています。

### 6.1 Hangar アプリのエンドツーエンドデモ（Jalen が実演）

アプリの題材は、夜勤の航空機整備士が整備作業を管理する業務アプリです。発表者は「整備士向けの GitHub のようなもの」と説明しています。

**手順 1：プロジェクトの作成**
1. 空のプロジェクトフォルダーで `winapp new` を実行する。
2. テンプレート一覧から、ナビゲーションビューを選び、アプリ名を Hangar にする。
3. アプリの雛形が作られる。パッケージ ID も最初から組み込まれている。
4. ターミナルのビルドでエラーが出たが、発表者はそのまま、事前に動作する Hangar を見せる別のタブに移っている。

**手順 2：完成済みの Hangar の紹介**
1. 過去 30 日の機体稼働状況を示すグラフが表示される。
2. 注意が必要な機体を選んで詳細に入る。ファンの問題があり、作業の書き込み（描画）をし、完了としてサインオフする。ほかのチケットも並んでいる。
3. GPU アクセラレーションによるネイティブ機能のおかげで動作が速いと説明している。

**手順 3：作業指示ページの遅さを調査（性能）**
1. 整備士から「作業指示（Work Orders）ページの読み込みが遅い」というチケットが届いたという設定。ページを開くと読み込みに時間がかかり、スクロールも重い。
2. 事前に実行しておいた Copilot セッションを表示する。セッションでは、エージェントに「作業指示ページが遅い。ボタンを自分で押しても確かに重い。プロファイルして原因を教えて」と依頼している。
3. エージェントは最初に WinApp performance のスキルを読み込んだ。
4. `winapp perf start` で実行中アプリを見つけ、追加のスタックトレースやメモリ情報、タイミング情報を取りながらアプリを動かす。取得結果はダンプにまとまる。
5. 続けて `winapp perf analyze` で分析し、シナリオを再実行してホットスポットを調べる。
6. 結果として、「ListView が画面に収まる以上の行を実体化している可能性が高い」という原因候補と、さらに調べる次の手順が提示された。
7. 発表者は、AI は 80% までは進めてくれるが、自分は人間による確認を重視し、すべてをエージェント任せにしないと述べている。

**手順 4：DevTools による検証とコメント機能**
1. WinApp CLI で `winapp` の開発者ツールのオプションをオンにしてアプリを再実行する。Visual Studio でおなじみの DevTools のオーバーレイが現れ、画面上で移動、要素選択、コメントの追加、レイアウトのアドーナー表示、ライト／ダークモードの切り替えができる。
2. 作業指示ページを開き、F12 に似たメニューから要素を選ぶとビジュアルツリー上の該当位置へ移動する。
3. ListView を展開すると、画面に出ていない行まで大量に読み込んでいることが確認できる。
4. 画面上に直接「1200 行を一度に読み込まない」とコメントを入力する。コメントはプロジェクトルートの .winapp フォルダーに保存され、PC を閉じて翌日戻っても残る。
5. ListView の最大高さに関するコメントも追加した。エージェントはこれらのコメントを読み取り、修正後に解決済みにできる。人間も読んだり解決したりできる。
6. 従来は、ライブのビジュアルツリーのどの行の話かを自分で覚えておく必要があったが、この方法では不要だと説明している。
7. エージェントに「DevTools に残したコメントを直して」と依頼すると、WinUI DevTools のスキルを読み込み、コメントの場所と扱い方を把握して修正した。
8. 修正後に作業指示ページを開くと、ほぼ一瞬で読み込まれ、スクロールのもたつきも無くなった。

共同発表者が、最初のプロンプトの入力やプラグインの導入、`winapp new` でのテンプレート選択を「飛ばした手順」として確認する場面があり、Jalen は「自然言語のプロンプトで、エンタープライズの誰でも使える」と答えています。

補足として、アプリがクラッシュする場合は、`winapp run` が「デバッグ出力付きで再実行」を勧め、WinUI チームの WinDbg ツールでクラッシュ分析ができると説明されました。別のプロファイラーやデバッガーを入れなくても、CLI だけで性能とクラッシュを調べられるという趣旨です。

**手順 5：新しいチケット（表ビューの機能追加）— Find UI**
1. 1 日後、整備士から作業指示の表について要望が来たという設定。財務列が切れる、列の幅を変えられない、列でソートできない、セル内で編集できない。
2. 夏に作ったとき、カスタム実装の ListView を使ったので、すべて自作になっていた。
3. エージェントに「表の要望（任意の列でソート、機体や状態でグループ化、列幅変更、セル内編集）に対し、適切な WinUI のツールを探し、サンプルコードを見せて。ただしまだ変更はしないで」と依頼する。
4. エージェントはまず該当スキルを読み込み、Find UI のコマンドで、data、grid、sort、group、resize といったキーワードを検索した。このコマンドは、WinUI Gallery、Community Toolkit Gallery、Reactor Gallery のサンプルから一致するものを返す。今後はローカル AI などを扱う AI Dev Gallery のようなギャラリーも対象に加える作業中だと説明されています。
5. 検索結果として TableView の 2 通りのシナリオが返った。エージェントは詳細を調べ、要望した機能が対応していることを確認し、サンプルの XAML と、グループ化、グループ解除、フィルターを制御する C# コードビハインドを取得した。インターネットで探したり、一から作ったりしていない。
6. 修正と再ビルドを経て（実演では飛ばしている）、完成した TableView が表示される。コンポーネントでグループ化、技術者や状態（開いている／閉じている）での並べ替え、スクロールして作業時間の編集（例：30 分追加）、列幅の変更ができる。これらは TableView で「そのまま手に入った」と説明している。
7. 発表者は、自作実装を、このシナリオに合った正しいコンポーネントに置き換えたものだと説明し、購買や在庫のシナリオにも向く新しいコントロールだと述べている。

**手順 6：列の固定（Find API）**
1. 表が横に広い（iPad のような小さな画面を想定）ので、最初の列を固定したい。Jalen は経験のある開発者として、AI を使わず自分で書いた。「FrozenColumnCount を追加」して保存する。
2. これは動かなかった。発表者は、以前使っていた古いフレームワークの記憶で書いたものだと説明している（フレームワーク名は音声認識の都合で確定できません）。レガシーフレームワークから WinUI に移行する際によくある問題で、WinUI に無いパターンや属性を持ち込んでしまう。エージェントでも同じ失敗が見られたため、Find API というツールを用意した。
3. エージェントに「エラーが出ている。作業指示番号の列を固定して、横スクロールしても残るようにしたい。アプリを直し、前面に表示して、動くことを証明して」と依頼する。
4. エージェントはまずエラーの再現を確認し、Find API のスキルを読み込む。使おうとしたフィールドを検索し、TableView のテンプレート列に存在しないことを確認する。
5. その型のメンバー一覧を取得し、`FrozenEdge` を見つける。`FrozenEdge` を `Leading`（先頭側）に設定する形に修正する。
6. 再ビルドの後、右へスクロールしても列が固定されていることを確認した。
7. Find API は Windows の API 全体に加え、アプリに組み込んだ独自の NuGet パッケージの API 面も走査して把握すると説明されています。

発表者は、Find UI が「コントロールを探す」、Find API が「関数・属性を探す」役割で、互いに補完すると整理しています。

**手順 7：UI テスト（WinApp UI）**
1. 開発が一段落し、自分がソフトウェアエンジニアリングマネージャーだとして、すべてが動くか確認したい、という設定。
2. `winapp ui help` で、アプリの検査、ウィンドウ一覧、フォーカス確認、クリック、スクロールのほか、ピンチ（原文は pin）などのジェスチャーまで、人が手で確認する操作のほぼ全部がコマンドとして並ぶことを見せる。エージェントもこれらを操作できる。
3. 事前に、これらのコマンドを使った PowerShell スクリプト `verify-work-orders`（読み上げでは「verify work orders」）を用意してあった。作業指示番号列が固定されているか、列幅を変えられるか、編集できるか、などを確認する。
4. ターミナルでこのスクリプトを実行する。エージェントが画面の操作を引き継ぎ、操作対象のウィンドウに枠が表示され、スクリーンショットが撮られる。コンポーネント列の幅が調整される。
5. 完了後、エビデンスのフォルダーが作られる。最初の画像は作業指示列でのソート、次の画像ではコンポーネント列の幅が広がっている。スクロールや、作業時間の降順ソートも確認される。デモでは「うまくいった項目と、そうでない項目があった」と述べている。
6. 疑い深い人や、テスト中に席を外した人のために、動画の記録も残るので、何が行われたかを確認できる。
7. 用途として、エラーの再現手順を決まった形で同僚に渡す、プレゼン中にエージェントにクリックしてもらう、などの例が語られた。UI テストのフレームワークを別に用意しなくても UI テストができる点も強調している。

**手順 8：隔離実行（サンドボックス）**
- 自分のマシン上でクリック操作が行われるのは気持ち悪いという共同発表者の問いに対し、`winapp ui` に サンドボックス用のコマンドがあると答えている。隔離された環境で実行すれば、横で通常の作業を続けられる。長いスクリプトに向く。
- 別の仕組みとして MXC という新しい概念があり、エージェントに与える能力と権限を明確にして、既定で安全にするものだと述べている。他の Windows のセッションでも触れられていて、あとで接続される予定とのことです。詳細は発表では語られていません。

**手順 9：パッケージ化と署名**
1. CLI を使わない場合に必要な作業として、マニフェストとアセットの用意、発行元とサブジェクトが一致する署名証明書の作成、証明書の信頼設定、ビルドプロパティの把握、インストールが挙げられた。Visual Studio のウィザードは多くを担うが、それ以外では各ステップが面倒で、つまずく箇所が多いと説明している。
2. その前に、パッケージ ID を VS Code で見せる。`package.appx manifest`（読み上げのまま）を右クリックして、WinApp CLI のビジュアルエディターで開く。発行元とアセットを変更できる。通常のエディターでも開ける。
3. 同じ VS Code で、XAML 内の誤ったプロパティに波線が表示され、ホバーすると「そのプロパティは存在しない」と教えてくれる。クイックフィックスで置き換えられる。Visual Studio 以外で XAML と C# の IntelliSense が使えるのは、これが初めてだと述べている。
4. パッケージ化は 3 つのコマンド。`winapp cert generate`、`winapp cert install`、`winapp package`（実演では `winapp pack` と読み上げ）。開発用証明書はステージ上で時間がかかるため事前に作成済み。
5. 実演では、`winapp cert install` で開発用証明書をインストールし、`winapp pack` で csproj、アーキテクチャ（デモ用 PC は ARM64）、証明書を指定して実行する。ID 付きでパッケージ化されるので、IT 管理者にとって発行元が分かり、インストール・アンインストールが綺麗になる。多くの Windows API が ID を必要とするため、最初から組み込んである。
6. 開発用証明書を使うことで、開発中から環境に証明書が設定され、これらの API を試せる。リリース時には本物のストア用証明書に切り替え、Microsoft Store など配布先に応じて出荷する。署名しないこともできる。
7. 最後に配布できるバンドルが完成した。

発表者は、約 30 分で、アプリを最初から最後まで作り終えたとまとめています。

### 6.2 Replit のデモ

1. 会場に聞いたあと、Replit に簡単なプロンプトを入力する。設定は、営業マネージャーが組織の各地域の売上状況を見たいというもの。地域別のレポートデータとドキュメントを読み、主要な指標を地図で示す WinUI アプリを作らせる。
2. 送信すると、Replit は Jalen たちが紹介したスキルと機能を内蔵していて、適切なスキルを読み込み、サンドボックスに接続する。これは MXC 上で動き、事前に許可された権限内に収まっていると説明している。
3. PowerShell を使って、このマシンのドキュメントフォルダーにあるローカルデータを把握し始める。続いてデザインのスキルを読み込み、開発ワークフローでアプリを作り、UI テストのスキルでテストする。これらはすべて裏側で行われる。
4. データは約 600 個の CSV ファイルで、完了まで約 15 分かかると説明している。待つ代わりに、事前に作成済みの「North Star」というアプリを別タブで開く（デモの神様に祈る冗談を交えた掛け合いがあり、無事に開いた）。
5. 完成したアプリは、データの意味を理解して作られている。地域別の地図があり、クリックで掘り下げられる。州別の性能を見られるチャートも並ぶ。サンプルのグラフィックスが使われ、ベストプラクティスは組み込み済みと説明している。
6. スクリーンショットを撮り、注釈を付けて保存し、同僚に共有できる（例：「フロリダの調子が悪い。ここに力を入れよう」）。
7. 与えたプロンプトは、ドキュメントを調べて主要な指標を示し、地図で表示するというもので、実際に約 15 分かかったと述べている。
8. MXC により、どのファイルにどの権限があるかが分かる。デモでは広いフォルダーへのアクセスが与えられていたが、データが入った North Star の米国オペレーションのフォルダーだけに絞ることもできると説明している。機微なデータがある場合を想定した説明です。

## 7. 注意点・発表者の気付き

- **エージェントは 80% まで。** 発表者は、AI が 80% まで進めてくれるが、人間の目で確認することが大切だと繰り返しています。DevTools の確認、証拠フォルダーと動画の確認も、その方針に沿っています。
- **移行時に古い API の記憶を持ち込む。** 旧フレームワークの記憶で WinUI の属性を書くと、エラーになります。人間でもエージェントでも起きる問題であり、Find API はその対策です。
- **ベンチマークは非公開。** 発表の数値は社内の非公開ベンチマークです。公開ベンチマークを各リリースに添える計画が語られていますが、現時点では公開されていません。
- **試験的な機能は変わり得る。** TableView、チャートコントロール、InkCanvas は実験的パッケージで提供中です。ホットリロード、デザイン時プレビュー、Reactor も実験として紹介されました。
- **実演でビルドエラーが出た場面がある。** `winapp new` 直後のターミナルでビルドエラーが出たことが発表者から語られています（その後、別タブの完成版に切り替え）。
- **サンドボックス実行と MXC。** UI テストが自分の画面を占有するため、サンドボックスでの実行が用意されています。MXC は、エージェントの権限を明確にする新しい仕組みとして触れられましたが、詳細は他のセッションを参照する形で、本発表では説明がありません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **開発の入口が軽くなる。** `winapp new` でテンプレートからすぐ始められ、ID が最初から含まれるため、通知やスタートメニュー連携をすぐテストできる。
- **性能問題の調査が一本化される。** プロファイル、DevTools、クラッシュ分析（WinDbg）が CLI に含まれ、別ツールを導入しなくてよい。
- **エージェントが推測せずに作れる。** Find UI と Find API により、実在するコントロールと API に基づいてコードを生成する。社内ベンチマークでは、WinApp コマンドの正答率が 37% から 90% に向上した。
- **UI テストの負担軽減。** 別途フレームワークを用意せずに、スクリプトで UI テストができ、スクリーンショットと動画の証拠が残る。
- **パッケージ化が 3 コマンドで済む。** 証明書の生成と導入、パッケージ化により、ID 付きで出荷できる。IT 管理者にとって発行元が明確で、インストール・アンインストールが綺麗。
- **非技術者にも広がる。** Replit の例では、簡単なプロンプトから約 600 個の CSV を元にした地図付きの WinUI アプリを約 15 分で作成している。
- **選ぶ環境を限定しない。** CLI、VS Code、Visual Studio のどこでも使える。

## 9. まとめ

- WinUI は、新規開発にも既存の基幹業務アプリの移行にも、Windows ネイティブとして推奨する道です。ファーストパーティアプリと外部パートナーの採用例が示されました。
- WinApp CLI 1 本で、作成、実行、プロファイル、DevTools によるコメント、Find UI と Find API によるエージェントの根拠付け、UI テスト、パッケージ化と署名まで一貫して扱えます。実演では約 30 分で完成させています。
- 社内の非公開ベンチマークでは、ツールを使うとエージェントの正答率が上がっています（WinApp コマンドで 37% から 90%）。
- ホットリロード、デザイン時プレビュー、Reactor、TableView、チャート、InkCanvas は実験段階で、フィードバックを求めています。
- Replit は、非技術者でも簡単なプロンプトで WinUI アプリを作れる例を示しました。
- WinApp CLI は WinGet で入手でき、VS Code 拡張機能と Copilot プラグインもあります。フィードバックは aka.ms/WinUI へ。
