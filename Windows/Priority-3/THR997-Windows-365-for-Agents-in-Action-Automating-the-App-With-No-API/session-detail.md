# THR997 Windows 365 for Agents in Action: Automating the App With No API

## 1. はじめに

このセッションは、API を持たないレガシーアプリケーションを、**Windows 365 for Agents** 上で動くエージェントに操作させる方法を、ライブデモ付きで紹介するものです。登壇者の John Jarvis 氏は、月曜日にサンフランシスコへ着いたとき、Uber の車中で見かけた「API なくして AI なし（no AI without API）」という大きな看板に触れ、「それは少し違う。API が無いアプリも自動化できることを今日は見せる」と切り出しています。

話の流れは、レガシーアプリが抱える課題、Windows 365 for Agents とは何か、誰が何を管理すべきか、架空の会社 Apex Consulting のデモ、コストと設計判断、始め方、Q&A の順です。デモでは、1 本の通話トランスクリプトを Teams のエージェントに渡すだけで、2 つのレガシーアプリの更新、請求書の作成、メール送信までが 9 分で完了し、人間が操作に関わった時間は約 71 秒でした。その途中に**承認ゲートが 2 つ**あり、人が承認するまで何も変更・送信されない点が、本セッションの強調点です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR997](https://ignite.microsoft.com/en-US/sessions/THR997)

## 5. 発表内容の詳細

### 5.1 Windows 365 for Agents とは

Jarvis 氏は、Windows 365 for Agents を「**エージェントのために作られた Cloud PC**」と説明します。自分たち人間のためのものではありません。アプリの操作を任せても安全だと言える特徴として、次の 4 点が挙げられました。

| 特徴 | 説明 |
| --- | --- |
| 専用の ID | エージェントが固有の ID を持つ（音声は "enter agent ID"。Entra Agent ID と思われますが、確定できません）。借り物のログインや、ユーザー名とパスワードを書いたサービスアカウントの Excel は不要で、操作はエージェントに紐づいて追跡される |
| 本物のデスクトップ | Intune で管理され、通常のデスクトップと同じコンプライアンスポリシー・構成ポリシーが適用される |
| プール型でステートレス | 使用ごとに Cloud PC が初期化（wipe）される。音声は "pulled and stateless" で、pooled の意味と思われます |
| 課金 | Windows 365 Enterprise のようなユーザー単位の月額ではなく、**アクティブな時間単位**で課金される |

Intune 上では、コンプライアンスベースラインと条件付きアクセスを、すでに運用しているコンソールで管理できます。

### 5.2 誰が管理するのか

Jarvis 氏は、このスライドをセッションの 2 時間ほど前に追加したと述べています。現状、自動化チームは「EUC（エンドユーザーコンピューティング）の製品だから自分たちは知らなくてよい」と考え、EUC チームは「AI は担当外」と考えている、という二重の誤解があると言います。同氏の立場は、**両方のチームが管理すべき**というものです。

| 担当 | 責任範囲 |
| --- | --- |
| 自動化チーム | エージェントそのもの。指示、モデルの選択、実行コスト、承認ゲート、ガードレール、アプリが変わったときの修正 |
| EUC チーム | Cloud PC、プール、プロビジョニングポリシー、コンプライアンス、セキュリティベースライン。レガシーアプリを Cloud PC に配布することも担当 |
| 事業部門 | なぜこの仕組みが存在するか。業務プロセス、予算、承認ゲートを持つ |

### 5.3 デモの設定：Apex Consulting と従来型エージェントとの違い

デモに登場するのは、架空の Microsoft パートナー **Apex Consulting** と、そのレガシーアプリ 2 つ、そしてエージェントです。

- **Apex CRM XP**：商談（opportunity）、ステージ、金額、アクティビティなど、営業担当者の日々の業務データを持つ。「初代 iPhone と同じくらい古い」アプリ
- **Craven Finance**：請求書、発注書（PO）、支払いを持つ。API も SSO も無い
- **エージェント**：「新しい同僚」。Teams に常駐し、Cloud PC で作業し、組織の外へ何かを出す前に必ず人に確認する

従来のエージェントは、ユーザーが Teams や Copilot などの入口からエージェントに話しかけ、MCP などのツール利用を通じて、API 経由でアプリのデータに到達します。API が無い場合は、Windows 365 for Agents を使い、ユーザー本人がクリックしているかのように操作します。Apex CRM XP と Craven Finance とのやり取りには、computer use が使われます。

Jarvis 氏は、準備中に Advania UK のアカウントマネージャー（音声は "CAT managers"）に、Dynamics CRM のような現代的なアプリを使っていても何が面倒かを尋ねたそうです。挙がったのは、タスクの更新が手作業であること、金額の確認、請求書の作成と送信、アプリ間のコピー＆ペーストでした。

### 5.4 デモのシナリオ

金曜日の顧客との通話は 24 分間で、そこで決まったのは次のことです。

- プロジェクトの承認（金額、PO 番号、請求書の宛先を含む）
- 通話の最後に、顧客が軽く触れた新しい Copilot の案件

営業担当者は、アプリ間を行き来する作業に追われ、それが顧客と話す時間を奪います。Jarvis 氏は、Apex CRM の営業担当者は顧客と話すことで稼ぐのであり、アプリをクリックして回ることで稼ぐのではない、と述べています。

### 5.5 デモの結果

Jarvis 氏は、9 分でエンドツーエンドが完了したと述べ、次の数字を挙げています。

| 項目 | 数値 |
| --- | --- |
| 所要時間（全体） | 9 分 |
| 更新・作成されたもの | 4 件のレコード更新、請求書 1 件の作成、Apex CRM の 2 つの案件、送信されたメール 1 通（発話の内訳は聞き取りにくい箇所があります） |
| エージェントの操作回数 | 137 アクション（Cloud PC 内でのクリックなど） |
| アカウントマネージャーの手間 | 約 71 秒（「承認してください」と答えるのみ） |

最も強力だったのは、**2 つの承認ゲート**で、人が「進めてよい」と言うまで組織の外へ何も出ず、何も変更されなかった点だと述べています。1 つ目は金額の変更、2 つ目はメールの送信前です。

Cloud PC は、承認待ちの間も開いたままで、2 分ごとに keep-alive が行われ、20 秒後に解放されます。Jarvis 氏は、これらが自分の設定したパラメーターで、営業担当者が承認を忘れても、あとで戻って続けられるようにするためだと説明しています（"20 seconds" は聞こえたままで、単位は確認できません）。

### 5.6 コスト

実行全体のコストは、モデルに **58 セント**でした。モデルは "GBT 6.1 Sol" と聞こえます（音声認識の都合で表記が確定できません）。Jarvis 氏は、6.1 Sol のほか、"Astra"、Anthropic のモデル（"Fable" と Opus と聞こえます）も試し、6.1 Sol が圧倒的に最良で（音声は "Sonic Soul" と聞こえ、同じモデルを指すと思われます）、安く、正確で、頼んだことをすべてうまくこなしたと述べています。

- 58 セントのうち、**92% がキャッシュ由来**（音声は "from cash"）で、これによりコストが大きく下がった
- 出力トークンは 3,794
- 何度も繰り返し実行した結果、コストは 45〜73 セントの範囲だった

### 5.7 なぜ営業担当者自身がやらないのか

エージェントは自分のペースで、頼まれたことを正確に実行します。人間はミスもあり、通話後や週末まで管理作業を後回しにすることもあります。エージェントを使えば、管理作業による疲弊（burnout）や再入力のミスが減ります。ただし判断は人の役割で、エージェントは自信が持てないときに尋ね、顧客をよく知る営業担当者がエージェントに代わって判断します。まとめとして、**「エージェントが管理作業をし、人が売る」**と述べています。

### 5.8 Intune での管理

Intune 上で、エージェント用の Cloud PC は他のデバイスと同じように見えます。説明された点は次のとおりです。

- ユーザーではなくエージェント向けなので、**プライマリユーザーは無い**
- コンプライアンスポリシーを適用できる。Jarvis 氏は Open Intune Baselines（MVP の James Robinson 氏が公開）を使っていると述べています
- Defender for Endpoint を入れられ、Purview も適用できる
- ユーザーが存在しないため、システムアカウントに対して評価される
- アプリは Intune 経由で配布でき、"robo pack" のようなパッケージングを使っている場合も、通常の Cloud PC と同様に配布できる（音声表記のまま）

### 5.9 エージェントの作り方：Copilot Studio と Foundry

今日のエージェントの作り方は 2 つあります。

| 方法 | 特徴 |
| --- | --- |
| Copilot Studio | ローコード。指示を入れるとエージェントが動く。午後のうちに作り込める |
| Foundry ＋ Agent 365 SDK | プロコード。デモはこちら |

Jarvis 氏がプロコードを好む理由は、(1) 純粋なコードで多くのガードレールを置ける、(2) Foundry のほうが使えるモデルが多く新しい、の 2 点です。モデルについては、Copilot Studio のものは少し古いと感じており、「6.2 が今日リリースされたと思うが、デモを更新する時間がなくて残念」と述べています（バージョン表記は音声のままです）。ただし、土台は同じで、Cloud PC、Agent ID（音声は "enter agent ID"。Entra Agent ID と思われますが確定できません）、Intune です。

### 5.10 始め方とリソース

Jarvis 氏が示した、今日から始めるための手順は次のとおりです。

1. **ユースケースを見つける**：API が無いアプリで、ユーザーが毎日同じ手順を、意味のある頻度で行っているもの。1 日 1 回程度では効果は薄く、1 日に何度もある作業が最適
2. **きちんと証明する**：成功とはどういう状態か、エージェントが「絶対にしてはならないこと」は何かを書き出す。同氏は自分のブログに、ガードレールのための "10 … commandments" を公開しています（正確な名称は音声からは確認できません）
3. **作る**：ローコードか、Foundry でのプロコードか。Cloud PC、モデル、人のコストを見積もる
4. 実際の実行結果から、ユースケースを作り直す

スライドには、Advania が自社で構築した「customer 0」のユースケースを紹介する QR コードがありました。また、「レガシーアプリは変わらず、それ以外のすべてがエージェント時代に変わっている」と述べています。

リソースは次のとおりです。

- Microsoft Learn（左の QR コード）
- GitHub（中央の QR コード）：Windows 365 for Agents playground。API ドキュメントと getting started が揃っており、すぐに環境を立ち上げられる
- ブログ cloudendpoint.ai：このセッションのスライドを公開予定
- コスト計算ツール：エージェントの手順を入力すると、モデルと Cloud PC のコストが出る（音声は "Kua collator" と聞こえ、calculator のことと思われます）

### 5.11 Q&A

**Q1. レガシーアプリでエージェントに正しく操作させる際の課題は？**
回答：モデルによります。Copilot Studio にあった OpenAI の computer use モデルは「ひどかった」とのことで、頼んだことをせず、ある時は間違った場所を、次は正しい場所をクリックしたそうです。最近は Sol（"5.6 かそのくらい"と聞こえます）が入り、かなり良くなりました。「保存ボタンはこの近くにある」といった適切なガードレールを入れると、さらに良くなります。Foundry のモデルでは、チームにすべてのアプリを操作してもらい、各ボタンが何をするかを学習させられるため、さらに良く、Copilot Studio より Foundry を好む理由だと述べています。

**Q2. SDK とモデルに「学習モード」はあるか？**
回答：最初にエージェントを作った際、すべてをクリックして回らせ、どこに何があるかを把握させる学習の段階を踏みました。Copilot Studio ではそれは難しいが、Work IQ が Copilot Studio に入りつつあり、組織について学べるようになる、という説明です。ただし Jarvis 氏は Foundry を好みます（Copilot Studio のほうが好きだという人もいる、とも触れています）。

**Q3. エージェントがメールを送ったとき、Exchange のライセンスやメールプロファイルはどうなっているのか？**
回答：Teams のエージェントのインスタンスを Agent 365 で作成すると、ライセンスが付与され、メールボックスなどが使えるようになる、という説明です。名前が長いライセンス名は思い出せない、と話しています。

**Q4. メールの差出人は？**
回答：共有メールボックスを作成し、その中の invoices に専用の権限をエージェントへ付与しました。そのため、メールは invoices から送信されます。この点はデモ中に説明すべきだった、と述べています。

## 6. デモ・手順

デモは**ライブで**行われました。画面上の操作は、Jarvis 氏がナレーションした範囲のみ確認でき、ボタン名や入力値の細部は音声からは分かりません。語られた順番は次のとおりです。

1. Teams のアカウントマネージャー用エージェントに、顧客との通話のトランスクリプトを入力し、「Milton Grange Hotels の顧客承認が下にあるので、請求書まで進めて顧客に送ってほしい」と依頼して送信する（トランスクリプトには、Linda 氏が「33,600 で承認した（想定した 31,200 ではない）」と述べた内容、請求書に記載する PO 番号、通話の最後に出た新しい Copilot 案件とその期限の目安が含まれる）
2. エージェントが、依頼内容を**実行前に読み上げ返す**（作業に着手する前に確認する）
3. Cloud PC が起動し、画面を見守れる。**いつでも操作を引き継いで止められる**選択肢が表示される
4. 初期化済みのクリーンな Windows 365 Cloud PC で、Apex CRM XP が開く
5. 作業の前に、エージェントが「計上されていた金額（booked value）は 31,200 だったが、承認された金額は 33,600。どうすべきか、新しい値で進めてよいか」と**確認を求める（1 つ目のゲート）**。Jarvis 氏が「進めてください」と承認する
6. エージェントは「了解、作業します」と応答し、Apex CRM をクリックして進める。案件を closed にし（音声は "closed as one"）、時刻と日付を更新する
7. 新しい案件については、アカウント、Milton Grange Hotels であること、アカウントマネージャー、おおよそのクローズ日、概算予算を、すでに知った状態で作成する。数分で完了
8. Craven Finance を開き、販売請求書を作成する。顧客と PO 番号を把握しており、PO 番号を入力し、SKU を作成して明細行を入れ、金額を更新する。数秒で請求書が完成
9. 請求書を顧客に送るため Outlook を開く。新しく初期化されたデバイスなので、数秒で新しいプロファイルが作られる
10. メールの作成が始まる。テストのため、宛先は登壇者本人。先ほど作成した請求書が添付される
11. **2 つ目のゲート**：「送信してよいか」と確認され、宛先、差出人、件名、添付、請求書の支払期限が表示される。Jarvis 氏が「送信してください」と承認する
12. メールが送信される。エージェントは Craven Finance に戻り、ステータスを「送信済み」に更新して完了する

> 補足：発話では、デモ中に一部うまく動かない様子（「何が起きたのか分からない」という発言）があり、その後メールの作成が続きました。原因は語られていません。

## 7. 注意点・発表者の気付き

- **モデルの選択で結果が大きく変わる**：Copilot Studio にあった OpenAI の computer use モデルは精度が低く、正しくクリックできないことがあったと述べています。新しいモデルでは改善しており、ガードレール（ボタンの位置を指示するなど）で更に改善します。
- **ガードレールと承認ゲート**：変更や外部への送信は、必ず人の承認を挟む設計です。エージェントに「絶対にさせないこと」を先に書き出すことを勧めています。
- **コストは見積もること**：Cloud PC、モデル、人のコストを合わせて算定するよう勧めています。
- **管理体制**：「自動化チームの仕事ではない」「EUC チームの仕事ではない」という双方の思い込みは誤りで、両方のチームが関与する必要があると同氏は考えています。
- メールの差出人など、デモ中に説明し忘れた設定（共有メールボックスと権限）は、Q&A で補足されました。
- Jarvis 氏は、最新のモデルがセッションの当日に出たため、デモを更新する時間が取れなかったと述べています。

## 8. 利用者にとっての利点

発表で語られたデモ上の成果は次のとおりです。

- 9 分で、2 つのレガシーアプリ（Apex CRM XP、Craven Finance）と Outlook にまたがる作業が完了した
- 人の手間は約 71 秒（承認のみ）で、再入力のミスも起きない
- 変更と送信は、2 つの承認ゲートで人が管理する
- 1 回の実行コストは 58 セント（範囲は 45〜73 セント）。キャッシュが 92%
- API の無いアプリを書き換えずに自動化できる（冒頭で、書き換えは 7 桁の見積もり・18 か月かかり得るとされていました）
- Intune の既存のポリシー、ベースライン、Defender、Purview で、人のデスクトップと同様に管理できる

なお、これは架空の会社を使ったデモの数値で、顧客の導入実績としての数値は発表では示されていません。

## 9. まとめ

API が無いレガシーアプリに対し、Windows 365 for Agents は、専用 ID、Intune 管理、初期化される Cloud PC、アクティブ時間課金を備えた「エージェント用の Cloud PC」を提供します。デモでは、1 本のトランスクリプトから、Apex CRM XP、Craven Finance、Outlook を横断する作業が 9 分・137 アクションで完了し、人の関与は 2 つの承認ゲートで約 71 秒、モデルコストは約 58 セントでした。始めるには、毎日繰り返される API の無いアプリを選び、成功条件と禁止事項を書き、Copilot Studio か Foundry で作り、実際の実行結果から作り直す、という手順が勧められました。
