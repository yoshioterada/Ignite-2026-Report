## 5. 発表内容の詳細

### 5.1 この発表自体の作り方と費用

登壇者は、自分でスライドを書いたのではなく、AI が作ったと話します。使ったのは約 59 個のエージェントで、聴衆の調査を行い、どのメッセージが響くかを探ったそうです。スライドの 1 ピクセルまでコードで作られ、エージェントが書いたコードを追跡したところ、スクリプト、ファイル読み取り、分析、データ検証を含めて**約 38,000 行**でした。発表内容を批評する「批評エージェント」もいました。

費用は約 **$675** で、複数のモデルを組み合わせています。ローカルモデルを使わなければ約 40% 多くかかっていたので、**約 40% を節約した**という説明です。つまり、発表で勧める手法を、資料の作成で自ら使っています。

### 5.2 トークンのパラドックス

登壇者が 1 年半〜2 年前に顧客とトークン費用の節約を話したときは、単価が日々下がっていたため誰も関心を持たなかったそうです。数字としては、年ごとに単価が「280%」下がった一方、トークンの請求と支出は **1000%** 増えたと話しています（登壇者の言い方のままです）。単価が下がるぶん、より多くの仕事をさせてトークンを多く使うようになったため、これを「パラドックス」と呼んでいます。

登壇者自身の例として、1 週間のトークン費用は自分で約 $1,200 で、チームのメンバーは平均で週 $2,000〜$3,000 を使うそうです。従業員数を掛け合わせると大きな額になる、という話でした。

### 5.3 なぜコーディングを題材にするのか

エージェントが最初に価値を発揮したのがコーディングで、コードは書いたあとにテストして動くかどうかを検証しやすいタスクだからだと説明されます。発表で示されるタスクは、コーディングのような検証しやすいタスクです。

### 5.4 タスクの 60〜70% は CPU で動く

「バグを直す」という単純なタスクでも、計画、実行、オーケストレーション、再び推論、検証、という一連の流れを経ます。登壇者によると、そのうち **60〜70%** は CPU で実行され、大きな推論モデルは不要です。計画と推論には大きなモデルが役立ちますが、サンドボックスでのエージェント実行やオーケストレーションなどは標準的な CPU で動く、という説明です。

社員が「この請求がなぜ拒否されたかを調べて異議申し立てを下書きして」と依頼する例や、MRI レポートの分析、カスタマーサポートの質問への回答といった例も挙げられました。いずれもファイルの読み取り、データの分類・抽出、レコードの検索、計画と推論、確認と再実行という流れをたどります。ファイルの読み取り、API 呼び出し、データベースやサービスの呼び出しは、CPU 上でよく制御されたオーケストレーションで動きます。

「エージェント処理にはフロンティアモデルが必要」というのは誤解だと登壇者は述べ、根拠として、コーディング、カスタマーサポート、ヘルスケア、金融サービスのエージェントを含む **120 以上の実際のエンドツーエンドのエージェントワークフロー**を検証したことを挙げています。

### 5.5 実行場所を決める要因

実行場所を決める要因として、次の 5 つが挙げられました。

- 速度：ユーザーやエージェントが待っているか
- コンテキストやメモリ
- プライバシー：登壇者は直前まで欧州にいて、どの会話でも主権（sovereignty）、データ保護、エージェントにできることが話題になっていたと述べ、米国ではあまり聞かないが欧州では大きな問題で、プライバシーを理由に多くの判断が行われていると説明しています。
- 必要な能力：フロンティアモデルか、小さなモデルか
- 費用：どこまで払うか

### 5.6 4 つのルーティング手法

登壇者が実験した手法は 4 つです。

| 手法 | 内容 |
| --- | --- |
| Complexity routing（複雑さ） | 小さなモデルが、プロンプトの複雑さ・長さ・キーワードルールなどを基に、複雑さの段階を判定する。例として、FAQ に答えるだけの処理と、アクションを実行する処理を分ける |
| Semantic routing（意味） | プロンプトの意味を少し深く分析して、小規模、大規模、中規模、コーディング用などのモデルに振り分ける。登壇者によると vLLM にもこの機能がある |
| Elastic routing（負荷） | 同時利用ユーザー数、計算資源の規模、メモリやコンピュートのボトルネックなどの負荷を見て、動的に振り分ける。ヘルスケアの顧客が「レポートは 1 日 1 回あればよい」と言うので、計算資源が空いている時間にレポートを生成する、というバッチ処理の例が挙げられた |
| Escalation routing（エスカレーション） | 小さなモデルで始め、行き詰まったらフロンティアモデルに上げる。登壇者が「一番好きな手法」と述べている |

Escalation routing の説明で登壇者が出した例は、コードベースに対するバグ修正です。プロンプトは 20〜25 トークン程度と単純でも、エージェントがコードを読み、修正し、テストし、CI パイプラインに合わせ、セキュリティポリシーを適用するという複数ステップのループを経ると、最終的に **42,000 トークン**になります（登壇者は途中で「42,000 行のコード」と言い直しているように聞こえますが、文脈からはトークン数の話です）。途中でモデルの力が足りず、同じループを繰り返して進まなくなることがあります。そこで、小さな言語モデルで始め、ルーターが行き詰まりを検出したらフロンティアモデルに上げることで、本当に必要なタスクにだけフロンティアモデルの費用を払います。

登壇者は、この考え方を自社の作業に適用し、精度低下 **1% 未満**で、トークンコストを**約 40% 削減**できたと述べています。これはオープンウェイトモデルを効果的に使う計画を立てたためだそうです。

オープンウェイトモデルについて、登壇者は Open Router の最新データを引き、今年の第 2 四半期はタスクの 38% しかオープンウェイトモデルに回されていなかったのが、第 3 四半期には **78%** に跳ね上がったと説明しています。トークンコストが非常に高くなり、各社が解決策を探しているためだ、という説明です。

### 5.7 手持ちの計算資源を使い分ける

ルーティングの先は、手元にある計算資源すべてです。

- PC：登壇者は、発表中もノートパソコン上でバックグラウンドのエージェントを動かしており、小さなモデルが実行されている
- Xeon サーバー：小〜中規模のモデルを効果的に動かせる
- ローカル GPU：各種 GPU 上でモデルを動かせる
- フロンティアモデル

「すべての答えがフロンティアモデルではない」と強調し、その例として、Claude が最近発表した "Fable 5.2" が "Fable 5.1" より安いのは、内部でルーティングを使い、プレミアムモデルが不要なときは安価なモデルに振り分けているからだ、と述べています（"Fable 5.1/5.2" は音声認識の都合で正しい製品名が確定できません）。GPT-5 も、タスクに応じて大きなモデルが必要かを判断する内部ルーターだと説明しています。

構成としては、シンプルなゲートウェイと、モデルの能力を並べた**モデルプール**があり、プロンプトの内容や意味、計算資源の弾力性、必要な能力、**ポリシーフレームワーク**といったシグナルに基づいてモデルを割り当てます。

### 5.8 ポリシーと監視

エンタープライズのポリシーは、人間に適用するのと同様にエージェントにも適用する必要がある、というのが登壇者の主張です。例として、自分はあるファイルにアクセスできるが同僚の Imran はできない、財務部門は HR 部門にアクセスできない、といった状況で、エージェントが入ってはいけない領域に入らないようにすることが挙げられました。

また、監視とテレメトリも重要だとされます。監視しないと、エージェントがデータを持ち出したり、キーを共有したり、メモリ上でも好ましくないことが起こったりするおそれがある、という説明です。

### 5.9 登壇者自身の実例

登壇者は、この資料の作成にエスカレーションルーティングを使ったと述べています。すべてをフロンティアモデルで実行すると費用が大きくなり、自分の PC で完結するローカルモデルだけにすると、追加の支払いはないものの行き詰まり、精度も十分ではありません。エスカレーションルーティングを使うと両方の良い点を取れ、ノートパソコン、Xeon サーバー、必要ならフロンティアモデルを使い分けて、**費用は約半分**になったと述べています。発表で示した「実データで実行した単純なタスク」で 50% の節約という説明です。

> 補足：5.1 では全体の節約を約 40%（$675 を支払った）、ここでは約 50% と述べています。どのタスクの数値かの対応関係は、発話の範囲では厳密に区別されていません。

### 5.10 Intel と Microsoft の連携

登壇者は、Intel と Microsoft が協力している製品として、次の層を挙げています。

| 層 | 内容 |
| --- | --- |
| AI PC（Windows ノート PC） | 個人用でオフラインでも動くエージェント。登壇者は Foundry Local と呼んでいる |
| Azure Local 上の Foundry Local | 主権のあるエンタープライズインフラ |
| Intel Xeon（サーバー CPU） | エージェントのサンドボックスの多くを動かせる |
| Azure VMs | クラウド上で動かす選択肢。MCP エージェント向け |
| フロンティアモデル | 最後の選択肢 |

アーキテクチャの詳細は、発表後に個別に相談できると案内されました。さらに、Microsoft との連携の対象として、Intel Xeon、PC プラットフォーム、Azure Local、AKS、VMs、Foundry Local、SQL Server が挙げられました。企業データのベクトル化については SQL と取り組んでおり、モデルがベクトル化されたデータにアクセスできるようにしている、と説明しています。

### 5.11 使用中のデータの保護

データを保存時や転送時に守る方法は分かっているが、**使用中（at use）**のデータは守るのが難しい、と登壇者は述べます。各エージェントがコンテキストをメモリに持ち、他のエージェントもそのメモリにアクセスできるためです。例として、あるエージェントが Git のコードにアクセスするために共有したキーを別のエージェントが読み取り、ファイルに書き込み、そのファイルがメールで外部に流出する、という流れが語られました。登壇者は、これは仮定の話ではなく実際に多くの事例があると述べています。

対策として、**Confidential VM と Intel TDX** によるデータ保護が挙げられました。また、Azure Local はエージェントとデータをまとめて置く構成を可能にします。

### 5.12 持ち帰ってほしいこと

登壇者が「1 つだけ」と言って示したのは、**サイジングを、単純なトークン単価やサンドボックス数、エージェント数ではなく、「完了したタスクあたりのコスト」で行うこと**です。モデル呼び出し、CPU が実行する各ステップ、同時実行数を見て、適切な場所へルーティングすることで削減する、という考え方です。

また、2 年前は小さな言語モデルでは力不足だったが、今は能力が上がり、ファインチューニングの選択肢も増えて、これらのタスクを実現できるようになった、と述べています。

最初の一歩としては、1 つのエージェントから始めることが勧められました。Intel のブース（Lucy 氏が担当と聞こえます）でソブリンクラウドのデモが見られ、エージェントのタスクを持ち込めば、適切なルーティング手法で節約する方法を伝える、とのことです。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **精度低下 1% 未満で、トークンコストを約 40% 削減**（自社作業への適用結果）。
- 登壇者の資料作成では、約 $675 の費用で、ローカルモデルを使わない場合より約 40% 安く済んだ。
- 実データの単純なタスクで、エスカレーションルーティングにより費用が約半分になった。
- バッチ処理的な負荷には、空いている計算資源を使う Elastic routing が使える。
- 既存の PC、Xeon サーバー、GPU といった**すでに持っている計算資源**を活用できる。
- Confidential VM と Intel TDX により、使用中のデータの保護が可能になる。
- 標準 API（OpenAI API 互換）と vLLM などで標準化されており、導入は 1 年前より容易になった。

## 9. まとめ

エージェントの処理は、計画や推論などごく一部だけが大きなモデルを必要とし、タスクの 60〜70% は CPU で動きます。登壇者は、Complexity、Semantic、Elastic、Escalation の 4 つのルーティング手法で、PC、Xeon、GPU、フロンティアモデルを使い分ければ、精度をほぼ保ったまま（1% 未満の低下）トークンコストを約 40% 下げられると説明しました。実装の足がかりとして、software catalog.intel.com と、約 1 週間後に公開予定の Tokenomics Calculator が案内されています。

持ち帰る点は 1 つで、**「完了したタスクあたりのコスト」でサイジングする**ことです。あわせて、ポリシー、監視、使用中データの保護（Confidential VM、Intel TDX）を前提に、小さく始めて必要なときだけ上位モデルへ上げる設計が勧められました。
