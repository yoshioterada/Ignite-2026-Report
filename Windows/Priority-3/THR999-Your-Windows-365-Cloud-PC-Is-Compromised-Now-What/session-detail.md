# THR999 Your Windows 365 Cloud PC Is Compromised. Now What?

## 1. はじめに

このセッションは、Windows 365 の Cloud PC で侵害の疑いが生じたときに、**Defender for Endpoint のリスク判定 → Intune のデバイス準拠（コンプライアンス）→ Entra の条件付きアクセス**という流れで、会社のデータへのアクセスをどう止め、どう戻すかを実演する約 22 分の発表です。

発表者は、Windows 365 は設計上セキュアだが「設計上セキュア」は「自動的にセキュア」という意味ではなく、Cloud PC も物理的なエンドポイントと同じく攻撃対象になる、という前提から話を始めます。そして、健全な Cloud PC でマルウェアの疑似動作とウイルス対策の改ざんを起こし、Teams へのアクセスがブロックされ、対処後に回復するまでをデモで見せます。結論として発表者が挙げるのは、**Cloud PC もエンドポイントとして守ること**、**デバイスのリスクとアクセス判定をつなぎ、検知から回復まで通してテストすること**、**デバイスの信頼を継続的に評価・検証すること**の 3 点です。

## 3. 何に関する発表か

テーマは、Windows 365 の Cloud PC が侵害された（かもしれない）ときの、**継続的な姿勢（ポスチャ）管理**です。ゼロトラストのモデルで、デバイスの状態が悪化したらアクセスを止め、回復が確認できたらアクセスを戻す、という一連の仕組みを扱います。

発表の流れは次のとおりです。

1. 問題提起：Cloud PC が信頼できないデバイスになったとき、会社のデータにまだアクセスできるのか
2. 「設計上のセキュリティ」と、管理者の責任範囲
3. デモのシナリオ説明と事前設定（準拠ポリシーと条件付きアクセス）
4. デモ：ICAR によるマルウェア疑似検知、ウイルス対策の改ざん、アクセスのブロック、回復
5. 実際のインシデント対応の 4 段階
6. まとめ（覚えておく 3 点）

## 4. 発表者が伝えたいメッセージ

発表者がまず問うのは、Cloud PC で警告が出たあとの本当の問題は「Defender が脅威を検知したか」ではなく、「**リスクのある Cloud PC から、会社のデータにまだアクセスできてしまうのか**」だという点です。

次に、Windows 365 には強いセキュリティ基盤がありますが、Cloud PC は Windows を動かし、アプリケーション、ユーザー、ID、会社のデータを持っているため、物理エンドポイントと同様に攻撃対象の一部だと説明しています。

最後に、アクセスをブロックするだけではインシデントは終わらないという主張です。何が起きたかを理解し、範囲を確認し、信頼できる状態に戻したうえで、アクセスを戻します。発表者はこれを「**restore trust before you restore access（アクセスを戻す前に信頼を戻す）**」と表現しています。

## 5. 発表内容の詳細

### 5.1 「設計上のセキュリティ」は出発点

発表者は、Windows 365 は設計上セキュアだと述べたうえで、Microsoft が基盤の Cloud PC インフラストラクチャと Windows 365 サービスを管理するものの、それは自動的に安全という意味ではないと説明しています。Cloud PC にはアプリケーション、ユーザー、ID、会社のデータがあるため、物理エンドポイントと同じく攻撃対象です。

そのため Microsoft は IT 管理者に、Cloud PC に対するパッチ適用、セキュリティ構成、エンドポイント保護、継続的な監視、脅威検知の責任を持つよう求めている、と発表者は述べています。ここで **Microsoft Intune、Entra の条件付きアクセス、Defender for Endpoint** が組み合わさり、デバイス準拠、ID 保護、リスクベースのアクセス制御、脅威の検知と対応によって、Cloud PC のゼロトラストモデルを支えます。

Windows 365 には、ほかにもデータ保護の機能があります。発表では次が挙げられました。

- 画面キャプチャ保護
- 透かし（ウォーターマーク）
- コンテンツベースのリダイレクトやデバイスリダイレクトの制御
- 新しい入出力保護（input-output protection）機能

これらは、ユーザーの入力の保護、表示されるコンテンツの保護、Cloud PC と物理エンドポイントの間でユーザーデータが移動する範囲の制限に役立ちます。それでも、これらは**出発点にすぎず**、Cloud PC を保護して管理する責任は変わらない、というのが発表者の立場です。Cloud PC を守るのは、継続的な検証と継続的な制御です。

### 5.2 デモのシナリオと事前設定

デモのシナリオは次の順序です。

1. 健全で準拠している Cloud PC から、保護された業務アプリ（例として Teams）にアクセスできることを確認する。
2. その Cloud PC でマルウェアに似た悪意のあるアクティビティを模擬し、リスクを持ち込む。
3. Defender が脅威を検知して Intune に報告する様子を見る。
4. そのシグナルを Intune のデバイス準拠で追い、デバイスが非準拠と判定されることを確認する。
5. そのシグナルを条件付きアクセスで追い、Teams や Microsoft Forms などへのアクセスがブロックされることを確認する。
6. セキュリティチームが脅威を調査・対処し、Cloud PC を「より信頼できる状態」に戻して、再び Teams などへのアクセスを許可する。

発表者は、セキュリティポリシーは事前に構成済みで、待ち時間を省くためにデモの流れを圧縮していると断っています。

事前設定は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| 対象の Cloud PC | 名前が CPC で始まる、会社所有のデバイス。Intune 上で準拠、Defender for Endpoint にオンボード済み |
| デバイスグループ | 「Ignite Demo device group」。Cloud PC はこのグループに属し、準拠ポリシーが配布される |
| 準拠ポリシー | 名前は「Ignite demo」。Windows 10、11 デバイスが対象。Defender for Endpoint の設定で「マシンのリスクスコアが **clear 以下**であること」を要求し、満たさなければ即座に非準拠とする |
| 条件付きアクセスポリシー | テストユーザーを含み、対象リソースとして Microsoft Teams と Forms（生産性アプリ）を選択。許可の条件で「**デバイスが準拠としてマークされていること**」を必須にしている |

発表者は、全体の仕組みを「Defender のリスクが Intune のコンプライアンスに影響し、条件付きアクセスがそのコンプライアンスの状態を使って、テストユーザーが Teams にアクセスできるか判断する」とまとめています。

### 5.3 健全な状態の確認

デモの最初に、すべての設定が展開された Cloud PC で、テストユーザーが Teams にアクセスできることを示しました。Intune はデバイスを準拠と表示し、条件付きアクセスはアクセスを許可しています。

Defender で Cloud PC の状態を見ると、リスクレベルは **none** で、既知のリスクはありません。これが、準拠ポリシーの設定により Intune で準拠と判定されている理由です。このデバイスに関連するアクティブなアラートやインシデントもありません。

### 5.4 ICAR によるマルウェア疑似検知

最初に起こしたリスクは、マルウェアの模擬です。発表者は「ICAR」と呼ぶファイルを使いました（音声認識の都合で綴りが確定できません）。実際のマルウェアではなく、Microsoft が Defender の保護をテストする方法として文書化している無害なテストファイル、という説明です。

ファイルを保存すると、次のことが起きました。

1. Defender ウイルス対策がファイルを検知し、脅威としてフラグを付ける。
2. ほぼ即座に、Cloud PC からそのファイルを削除する。
3. Defender に、通知やさらに詳しい情報が表示される。

発表者は、Defender がエンドポイントのアクティビティを継続的に見て不審な動作を特定し、調査と対応に必要な証拠をセキュリティチームに提供する、と説明しています。

Defender ポータルには、この操作によるインシデントが作成されます。発表者が示した内容は次のとおりです。

- Cloud PC の名前が表示される。
- リスクの重大度（severity）は **informational** で、脅威は「防止（prevented）」されたと表示される。severity が informational なのは、発表者によれば ICAR が本物のマルウェアではないためである。検知元はウイルス対策機能で、マルウェアとして検出されたと表示される。
- 証拠の詳細として、関与したファイルとデバイスが分かる。
- アラートを詳細に見ると、プロセスツリーが表示され、関与したファイルの詳細と、出来事のタイムラインが分かる。
- Defender はアクションの推奨も示す。

また、Defender for Endpoint は、インシデントやアラート以外にも多くのセキュリティ情報を提供するとして、デバイスのタイムライン、セキュリティ推奨事項、デバイス全体のセキュリティポスチャと露出の評価を挙げました。

### 5.5 ウイルス対策の改ざんでリスクを「high」にする

次に、ICAR とは別に、ウイルス対策の改ざん（tampering）でデバイスにリスクを持ち込みました。発表者は、リアルタイム監視（real-time monitoring）を無効にしようとします。この種の攻撃者による改ざんは、デバイスのリスクレベルを **high** にする、と説明され、操作した直後にリスクレベルが high になりました。

Defender には次のようにアラートが記録されています。

- カテゴリは **defense evasion**（防御回避）。試した操作がそれに当たるため。
- 検知のソースは、Defender の **EDR（endpoint detection and response）** の機能。
- 次の対応に関する情報と推奨事項も確認できる。
- 影響を受けた資産として、Cloud PC とテストユーザーが示される。

デバイスのリスクレベルが clear ではなくなったため、準拠ポリシーの要件を満たさなくなります。発表者は、しきい値をはるかに超えている、と説明しました。Intune では、デバイスは赤の「非準拠」と表示されます。

### 5.6 アクセスがブロックされる

発表者は、ここが最も重要なテストだと述べています。準拠ポリシーを満たさなくなったデバイスから、テストユーザーは Teams にサインインできるのか。

結果は、テストユーザーは Cloud PC 上の Teams にアクセスできなくなりました。ユーザーには、Cloud PC がコンプライアンスポリシーに準拠していないというメッセージが表示されます。準拠ポリシーが、リスクレベルを clear に保つことを要求しているのに、Cloud PC が high になっているためです。**Intune がデバイスを非準拠とし、条件付きアクセスが、非準拠の Cloud PC 上の Teams をブロックする**という流れです。

### 5.7 回復：リスクを解消してアクセスを戻す

次に、Cloud PC を準拠状態に戻します。

1. リアルタイム監視を無効にする操作を元に戻す。
2. Defender で、関連するすべてのアラートを「解決済み」にする。
3. 画面を更新して、インシデントがすべて閉じられていることを確認する。
4. Cloud PC のリスクレベルが「informational」になり、high ではなくなったことを確認する。

発表者は、これは脅威を手作業で模擬したため、手動でインシデントやアラートを閉じられたからだと断っています。現実のシナリオでは、**調査し、封じ込め、対処したあとでなければアクセスは復旧できません**。「アクセスをブロックしたことは、インシデントの終わりではない」というのが発表者の考えです。まだ、何が起きたかの把握、範囲の確認、Cloud PC を信頼できる状態に戻すことが残っています。

現実の流れとして、発表者は次のように説明しています。

- ファイル、プロセス、デバイスのアクティビティを調べることから始める。
- 悪意のある動作が確認されたら、封じ込めて対処する。例えば、不審なプロセスの停止、影響を受けたデバイスの隔離、必要なセキュリティ更新の適用など。
- Defender では、検知の証拠を確認し、必要ならウイルス対策のスキャンを実行し、デバイスのタイムラインを調査し、調査を続けている間はデバイスを隔離する。
- 脅威が処理されて、デバイスが健全な保護状態に戻ったことを証拠で確認できたら、アラートやインシデントを解決し、通常のアクセスの復旧を始める。

デモの中では、Defender の**インシデントグラフ**も示されました。デバイス、ユーザー、ファイル、プロセス、アラートなど関連するエンティティの関係を可視化し、攻撃経路、アクティビティの順序、インシデント全体の範囲を素早く把握するためのものです。影響を受けた資産（ユーザーとデバイス）や、ファイル、プロセス、IP、アクティビティについての詳細な証拠も確認できます。発表者は、Defender は豊富な情報を提供するが、掘り下げて確認する必要がある、と述べています。

また、アラートとインシデントの違いも説明されました。**アラートは個別の検知**で、**インシデントは関連するアラートをまとめて、より広い攻撃の流れと範囲を示すもの**です。インシデント内のすべてのアラートを解決すると、そのインシデント自体も自動的に解決されます。

アラートが解決され、リスクレベルが下がると、Intune 上で Cloud PC は準拠状態に戻ります。ユーザーが同じ Cloud PC から再び Teams を試すと、条件付きアクセスは、デバイスが準拠していることを確認してアクセスを許可し、Teams へのアクセスが回復しました。

### 5.8 実際に侵害されたときの 4 段階

デモのあと、発表者はスライドに戻り、実際の侵害であれば次の 4 段階で対応すると説明しました。

| 段階 | 内容 |
| --- | --- |
| 1. 評価と封じ込め（assess and contain） | 必要なら Cloud PC を隔離する。認証情報が漏れていれば、ユーザー ID を保護する |
| 2. 調査と範囲の特定（investigate and scope） | インシデント、アラート、デバイスのタイムライン、証拠を確認し、何が起きたか、ほかに影響がないかを把握する |
| 3. 対処（remediate） | スキャン、隔離（quarantine）、インジケーターのブロック、ライブレスポンス（live response）、セキュリティ更新などで脅威を取り除く |
| 4. 回復と検証（recover and verify） | 状況に応じて Cloud PC を修復するか、必要なら再プロビジョニングし、信頼できる復旧ポイントに戻す。クリーンな再構築が本当に必要な場合は、再プロビジョニングで済ませられる |

アクセスを戻す前の条件も示されました。

1. Defender のリスクが、準拠ポリシーが許容するレベルに戻っていること。
2. Intune がデバイスを再評価して、準拠と判定すること。
3. 条件付きアクセスが、新しいアクセス要求を評価すること。

これらのシグナルがそろって、信頼が回復したと確認できたときに、初めてアクセスを戻します。SOC のレベルでは、**Sentinel** が相関分析と自動化を助け、**Security Copilot** がアナリストの調査と脅威ハンティングを速くする、という紹介がありました（詳細な説明は発表ではありませんでした）。

## 6. デモ・手順

このセッションにはデモがあります。発表者は、準拠ポリシーなどは事前設定済みで、待ち時間を省くために流れを圧縮していると断っています。画面の細部は音声からは確認できませんので、語られた順に記します。

1. Intune で Cloud PC（名前は CPC で始まる）が準拠状態であることを示す。デバイスグループ「Ignite Demo device group」に所属している。
2. 準拠ポリシー「Ignite demo」（Windows 10、11 対象）を示す。Defender for Endpoint の設定で、マシンのリスクスコアが clear 以下であることを要求している。
3. 条件付きアクセスポリシーを示す。テストユーザーを含み、Teams と Forms を対象に、準拠デバイスを必須にしている。
4. Cloud PC 上で、テストユーザーが Teams にアクセスできることを示す。
5. Defender で、Cloud PC のリスクレベルが none で、アラートもインシデントもないことを確認する。
6. ICAR のテストファイルを保存する。Defender ウイルス対策がすぐに検知して削除する。
7. Defender ポータルで、インシデント（severity は informational、脅威は prevented）、証拠、プロセスツリー、タイムラインを見る。
8. ウイルス対策のリアルタイム監視を無効にしようとする。Defender がデバイスのリスクレベルを high にし、defense evasion のアラート（EDR による検知）を記録する。
9. Intune で、デバイスが非準拠になったことを確認する。
10. テストユーザーが Teams にアクセスしようとして、ブロックされる。
11. リアルタイム監視のコマンドを元に戻し、Defender の関連アラートをすべて解決する。インシデントが閉じられたことを確認する。
12. Cloud PC のリスクレベルが informational に下がったことを確認し、インシデントグラフと証拠の詳細を確認する。
13. Intune でデバイスが準拠に戻ったことを確認し、ユーザーが Teams に再びアクセスできることを示す。

> 注意：リアルタイム監視を無効にする際に実行した具体的なコマンドは、発表では読み上げられていません。

## 7. 注意点・発表者の気付き

- **「設計上セキュア」は「自動的にセキュア」ではありません。** Cloud PC は Windows を動かすため、物理エンドポイントと同様に攻撃対象です。IT 管理者にはパッチ、構成、エンドポイント保護、監視、脅威検知の責任があります。
- ブロックはインシデントの終わりではありません。調査、封じ込め、対処、回復の確認が必要です。
- デモでは、アラートを手動で閉じるだけでアクセスが回復しましたが、これは脅威を手作業で模擬したためです。実運用でアクセスを戻すのは、調査・封じ込め・対処を済ませたあとだ、と発表者は述べています。
- アクセスの再開には、Defender のリスクの低下、Intune の再評価、条件付きアクセスの再評価の 3 つがそろう必要があります。
- Defender は豊富な情報を提供しますが、掘り下げて見るのは担当者の作業です。

## 8. 利用者にとっての利点

発表で語られた内容に基づくと、次のとおりです。

- Defender のリスク、Intune の準拠、条件付きアクセスをつなぐことで、**リスクの高い Cloud PC から Teams や Forms などへのアクセスを止められる**（デモでは、条件付きアクセスがブロックした）。
- リスクが解消されると、Intune の準拠状態が戻り、条件付きアクセスがアクセスを許可する（デモで確認）。
- Defender のポータルで、証拠、プロセスツリー、タイムライン、インシデントグラフ、推奨アクションが得られ、調査と対処に使える。
- 侵害が深刻な場合は、Cloud PC を信頼できる復旧ポイントへ戻す、または再プロビジョニングする選択肢がある。

## 9. まとめ

発表者は、冒頭の問い「Cloud PC が侵害されたら、どうするか」に戻り、Defender、Intune、Entra の条件付きアクセスが連携して、アクセス判定とゼロトラスト、継続的なポスチャ管理を実現すると整理しました。ただし、アクセスを制限するのは始まりにすぎず、脅威に対応し、デバイスの信頼が回復したことを確認する必要があります。

覚えておく点として、次の 3 つが示されました。

1. **Cloud PC もエンドポイントである。守ること。**
2. **デバイスのリスクとアクセスの判断をつなぎ、検知から回復までの全体の経路をテストすること。**
3. **デバイスの信頼は、継続的に評価され、継続的に検証されなければならない。**

さらに、最後に「**アクセスを戻す前に、信頼を戻すこと**」と締めくくっています。
