# THR893 Next-gen streaming protocol for Windows 365 and Azure Virtual Desktop

## 1. はじめに

このセッションは、Windows 365 と Azure Virtual Desktop（AVD）の通信を支える技術スタックに付けられた新しい名前 **Direct Stream** の紹介です。約 25 分の短い登壇で、「Direct Stream とは何か」「RDP とどう違うのか」「この 1 年で何が良くなったのか」を、デモを交えて説明しています。

最初に押さえておきたい点は、**Direct Stream はブランド名であり、利用者側で設定変更や再構成は不要**ということです。ネットワーク設定もファイアウォールのルールも、これまでのままで使えると登壇者は繰り返し強調しています。一方で、Multipath、Fast reconnect、60 FPS の維持、HEVC、NVIDIA Blackwell GPU 向けの最適化など、中身は大きく進化しています。話は、接続の切れにくさ、つながるまでの速さ、セキュリティ、セッション内の画面性能の 4 つの観点で進みます。

## 4. 発表者が伝えたいメッセージ

中心にあるのは、「Direct Stream は新しいプロトコルを導入する話ではなく、クラウド向けに作り込んできた土台に名前を付けたものである」という点です。

登壇者の説明では、5〜6 年前にクラウドの取り組みを始めたとき、RDP にクラウド向けの機能を足し続けてきました。RDP は端末とサーバーが直接つながる前提で、ポートと IP アドレスを必要とします。そのため、ネットワークアドレス変換（NAT）や各種ファイアウォール装置に対応するための仕組みを、後付けで作り込む必要がありました。その積み重ねに名前を付けたのが Direct Stream です。

もう 1 つのメッセージは、**数値で改善を示せる**ことです。接続が切れるまでの平均時間は 5 時間から 15 時間に伸び、ある顧客では 1 日あたり 4,000〜5,000 件あった切断が、1 か月で 400 未満になったと紹介されています。これらはテレメトリに基づくもので、そのテレメトリを顧客自身も見られるようにする、という方向も語られました。

## 5. 発表内容の詳細

### 5.1 技術スタックの 4 つの柱

登壇者は Direct Stream の技術を、次の 4 つの柱で整理しています。

| 柱 | 説明 |
| --- | --- |
| Connection reliability（接続の信頼性） | 接続でき、かつ長時間つながり続けること。ユーザーが自分で「終わり」と言って閉じるまでに起きる切断は、すべてエラーとみなすと説明しています |
| Connection speed（接続速度） | セッション中の滑らかさに加え、接続にかかる時間も含みます。接続開始は昔から課題であり、スタック全体で最適化を進めてきたとのことです |
| Security（セキュリティ） | ユーザーを安全に保ち、第三者にデータを露出させないこと。RDP と、クラウドでの Direct Stream の違いが出てくる部分だと説明しています |
| Performance（セッション内の性能） | 接続できても、エンコードのアーティファクト、ジッター、フリーズがあればサポートへの問い合わせにつながる、という考えです |

### 5.2 Multipath（接続の信頼性）

**Direct Stream Multipath** は、クライアントとサーバーの間に複数の接続経路を**あらかじめネゴシエーションしておく**機能です。最初の接続には最適な経路を選び、通信状況が変わっても、期限切れの古い経路には乗せず、事前に確立した経路を監視し続けます。以前は単に "multipath" と呼ばれていたもので、同じ機能です。

有効化の操作は不要で、Windows 365 と AVD のすべてで既定で有効です。登壇者は、Multipath が TCP と UDP の両方に対応していること（以前は展開に段階があった）にも触れています。

効果として、次の数値が挙げられました。

- 年初より前、ユーザー操作によらない障害（切断）の平均間隔は約 5 時間。Multipath により、エラーが出るまで約 15 時間に伸びた。1 日の勤務時間を超えて切断なしで過ごせる水準です。
- ある顧客（会場にいるとのこと）は、全体で 1 日あたり約 4,000〜5,000 件あった切断が、1 か月で 400 未満になった（発話では時間単位の言い回しが乱れており、正確な比較単位は聞き取りにくい部分があります）。

登壇者は、顧客の課題を解決し、エスカレーションを減らせる機能だと述べています。

### 5.3 接続速度：10 秒未満の接続と Fast reconnect

「VDI は接続が遅い」という声に対して、登壇者は次のように整理しています。初回のプロファイル設定などで時間がかかるのは、1 日に 1 回、あるいは VM が停止して休止状態から復帰させる週に 1 回程度のことです。それ以外の通常の接続を速くするために、ログイン時間の改善に力を入れてきました。デモでは、**画面上の「Windows」をクリックしてからデスクトップに到達するまでが 10 秒未満**でした（クリックした対象の詳細は音声からは確認できません）。

**Fast reconnect** は、再接続を速くする機能です。例えば、会議室から会議室へ移動するためにノート PC を閉じたり、誤って閉じるボタンを押したりして切断された場合、従来はすべてのネゴシエーションをやり直していました。Fast reconnect では、**トークンのハッシュをキャッシュ**しておき、全体を求め直す代わりに「ハッシュチェーンが変わったか」だけを確認します。変わっていなければ同じトークンなので、はるかに速く再接続できます（この部分の説明には聞き取りにくい箇所があります）。

登壇者は、ローカルデバイスと区別がつかない水準を目指して、さらに投資を続けるとしています（発話の末尾は聞き取りにくい部分があります）。

### 5.4 グラフィックス、リダイレクション、60 FPS（セッション内の性能）

RDP は以前からグラフィックスのワークロードに対応していましたが、最適とは言えなかったため、改善に取り組んできたと説明されました。リダイレクション（周辺機器などの転送）にも投資しており、従来は **TWAIN** や低レベルの USB リダイレクション周辺に機能の穴がありました。ここ数年で新しく加わったのが **HID（Human Interface Device）リダイレクション**です。

デモでは、Logitech のデバイスを使い、クラウド PC 上で **Blender** を操作しました。登壇者は、HID リダイレクションによってシーン上のオブジェクトを操作でき、選択モードに入って草のオブジェクトを上下に動かせることを示しています。また、Windows 365 を扱った別のセッションでも紹介されたとして、HID を通じて Logitech のマウスをローカルデバイスに対して制御できる例にも触れ、完全に統合されていると説明しています（使用したデバイスの正式名称は音声からは確認できません。発話では "that little ring" と、Logitech のマウスと呼ばれていました）。

次に **60 FPS** のデモです。以前の RDP は、オンプレミスからクラウドへ持ってきた際に帯域を優先して最適化したため、60 FPS を使う場面を選んでいました。最新の取り組みでは、セッション全体で 60 FPS を維持するようにしています。デモでは、GPU を持つクラウド PC に接続し、レンダリングと Direct Stream が送信するフレームレートの両方に 60 FPS を選びました。モデルをレンダリングした画面で、60 FPS が維持されていると説明しています。従来はコンテンツの変化に合わせてフレームレートが上下していましたが、**ディスプレイドライバーの扱いと、RDP（HEVC）がディスプレイドライバーとやり取りする仕組みを変更した**ことで、固定の 60 FPS を保てるようになったと説明されています。同じ取り組みの中で HEVC も提供したかった、と述べています。

### 5.5 RDP と Direct Stream の違い

ここで登壇者は、よく聞かれる「RDP と Direct Stream は何が違うのか」に答えています。

- RDP は、端末とサーバーの**ポイントツーポイント**を前提とし、ポートと IP アドレスを必要とします。
- クラウド向けには、NAT やさまざまなファイアウォール装置に対応するための機能を足し続けてきました。
- Direct Stream は、RDP の良い部分を土台に、チームがここ数年で行ってきた多くの投資を合わせたプラットフォームです。**Azure Virtual Desktop と Windows 365 を支える技術スタックの名前**です。
- 単なるプロトコルではなく、サーバー側とクライアント側のコンポーネント、クラウドにデプロイしたサービスを含むため、「プラットフォーム」と呼んでいます。
- **RDP との後方互換性は維持**され、RDP への投資も続けます。ただし、RDP には当てはまらない投資もあります。

その例として、Multipath の一環で導入した、世界中の **TURN / STUN サーバー**があります。Microsoft 内でも最大級の展開で、通信を妨げるさまざまなネットワーク機器を回避してネゴシエーションするために使います。これらは利用者のネットワーク内で完結する RDP には意味がないため、Direct Stream だけの技術です。HID リダイレクションのように、RDP と Direct Stream の両方にある機能もあります。判断に納得できない場合は、登壇者に直接相談してほしいとも話しています。

### 5.6 Direct Stream の新機能の整理

**TURN の世界展開**：Teams の統合コミュニケーション技術を取り入れ、独自のインフラを構築したと説明されています。Teams のリレーは世界に約 12 か所で、その外の地域では、サーバーへ行ってネゴシエーションし、クライアントへ戻り、さらにサーバー側でも同じことをする必要があり、時間がかかります。1.5 秒もかかると、「10 秒で接続」は達成できません。そのため、**世界 42 以上のリージョン**に TURN を展開しました。クライアントからの最初の呼び出しは近くのサーバーに行き、ICE candidate の解決を最速にできます。その後、Azure のバックボーンに乗せて、クライアントとサーバーの間のさらに速い接続を確立します。

**Fast reconnect / 低帯域チューニング**：Fast reconnect は今後も強化します。低帯域のチューニングも継続し、さまざまな帯域のシナリオに対応するようトランスポートを最適化しています。

**HEVC**：従来世代のエンコーダーよりはるかに効率が良く、すでに提供されています。有効にしていなければ有効にするよう勧めています。

**テレメトリ**：数値を示せるのは、この体験を支えるテレメトリがあるからだと説明し、ユーザーがどこで切断されているかを確認できる仕組みが「今日から」使えるようになる、と話しています（具体的な提供形態は語られていません）。また、ユーザーの接続のボトルネックがどこにあるかを示す**オープンソースのツールが Windows アプリに入る**予定です。

**セキュリティ**：Direct Stream と RDP の最大の違いは、**IP アドレスを公開せず、TCP 3389 も必要としない**ことです。多くの方にとっては既知の点ですが、名前が無かったために AVD でも「RDP を使っている」と言うしかなく、混乱を招いていたと説明しています。実際には **WebSocket Reverse Connect** を使っており、クライアントがサーバーに接続するとき、ポートはあっても IP アドレスは見せず、Microsoft のネットワーク上の WebSocket 逆方向接続で通信します。さらに、**Private Link 向けの shortpath**（発話は "short path for private link"）を導入しました。例えば隣の席の同僚に通話する場合に、クラウドを経由する意味はありません。経路を再ネゴシエーションし、そのような場合に Private Link を使えるようにする、という説明です。

**リダイレクション**：場所などの条件によって特定のリダイレクションをオフにしたい、という**条件付きリダイレクション**の要望が多くありました。その一部は Ignite の発表に含まれています。音声、ビデオ、クリップボード、プリンターの 4 つは現在利用可能で、今後も投資を続けます。

**HEVC 4:4:4 と新エンコーダー**：HEVC 4:4:4 は対応済みで、デモでも使ったと説明しています。さらに、GPU 向けの **新しい独自エンコーダー**を開発中です。これは「次世代の Direct Stream」と位置付けられ、**4K・60 FPS を 40 Mbps 以下**で届けられるといいます。HEVC と比べて約 **50〜60% 効率が良い**とのことで、グラフィックスのワークロード向けに最適化しているためだと説明されています。

**MMR（マルチメディアリダイレクション）**：Teams の通話や YouTube では、音声がクライアントからクラウド、クラウドからさらにクラウドへ行き、また端末に戻るのは無駄になります。そこで直接の接続を確立できる、というのが簡略化した説明です。対応サイトを昨年に続き今年も増やしており、Microsoft の Teams 組織と協力して改善を進めています（登壇者は "MMR 1.5" と呼んでいます）。さらに、コールセンター向けの通信ソフトを持つサードパーティのパートナーに対しては、各社が自分の製品向けに MMR のソリューションを作れる **SDK を公開**した、とのことです。

### 5.7 ネットワークは何も変えなくてよい

登壇者は、図を使って次の点を念押ししています。**Direct Stream の発表によって、利用者のネットワークで変えるものは何もありません。** Netscaler などを含む設定済みの内容はそのままで、ファイアウォールのルールも変更不要です。この技術は、この数年間、何らかの形で提供されており、機能が増えるたびに恩恵が少しずつ増えてきたものです。お客様に通知を送らなかったのも、気にすべきことが無かったからだと説明しています。

今後、ドキュメントや UI は順次「Direct Stream」の表記に変わっていきます。各クライアントのリリース周期が違うため、時間がかかります。登壇者のメンタルモデルは次のとおりです。

- 「クラウド上の RDP」と書かれていたら、頭の中では Direct Stream と読み替える。
- オンプレミスの Windows Server や RDS を使う場合は、引き続き RDP である。

### 5.8 NVIDIA Blackwell GPU との協業

約 2 年半前、NVIDIA から、最新の GPU を作っているという連絡があったそうです。Blackwell アーキテクチャは、前世代に比べて物理的な密度が約 4 倍です。例えば A10 と RTX 6000 Pro Blackwell を 1 対 1 で比べると、Blackwell は物理的に 4 分の 1 の大きさになります。NVIDIA は、同じシャーシにその GPU を 4 つ載せるといいます。そこで Microsoft 側は、さらに次のような要望を出したそうです。

- **画面のどの部分が変化したか**（ダーティ・レクタングル）の報告をより正確にすること。新しい Blackwell 世代では、前フレームと現在のフレームの差分検出が約 **30% 効率的**になった。
- 動きの予測に関わる新しいアルゴリズム上の改善（発話は "launching hints" と聞こえ、音声認識の都合で表記が確定できません。ウィンドウ内を何かが動くとき、行き先を予測できると計算が速く解ける、という説明でした）。

その結果、**NVIDIA Blackwell RTX 6000 Pro Server Edition**（登壇者が示したフルネーム）では、同じ 4K・60 FPS の配信を **42% 効率よく**行えると説明されています。登壇者は、これはクラウドで **Direct Stream のワークロード向けに作られた最初の GPU** であり、Microsoft 向けに最適化された機能を持つとしています。

特に大きいのが **エンコーダーのプリエンプション**です。CPU やメモリには公平な分配（fair share）の概念がありますが、GPU には無く、同じ VM を共有している隣のユーザーが（デモで行ったように）オブジェクトをレンダリングすると、次のユーザーはエンコーダーを使えなくなる、いわゆる **noisy neighbor 問題**が起きます。そこで、エンコーダーの公平な共有に向けた第一歩として、プリエンプションを実装しました。エンコーダーのタイムスライスを割り当て、ラウンドロビンで回すことで、1 人の電力消費の大きいユーザーだけでなく、全員が良い体験を得られる、と説明されています。これにより、「4K・60 FPS を 2 本届けられる」と言い切れるようになったとのことです。

### 5.9 Teams の転送プロトコルの取り込みと今後

Teams との協業を続けており、**Teams の転送プロトコルを Direct Stream に取り込む**予定です。悪い回線でも Teams が動くことに触れ、Teams の転送接続を事前にネゴシエーションしておくオプションを追加し、さらに劣悪なネットワークにも対応できるようにするという説明です。

入手方法としては、現在 **プライベートプレビュー**があり、参加を希望する場合は連絡すれば GPU 付きのクラウド PC を提供してもらい、「次に来るもの」を試せると説明されています。その発表は **Q1 の早い時期**を見込んでいるとのことです（プレビュー対象の範囲は、発話上は GPU 付きのクラウド PC と述べられた範囲までです）。

## 6. デモ・手順

このセッションには、デモが複数あります。画面は音声からは見えないため、登壇者のナレーションで語られた範囲だけを記します。

1. **Multipath のデモ**：クラウド PC に接続し、最初のネットワークインターフェース（NIC）が良い経路につながっている状態で、その NIC を無効化してネットワーク切断を模擬します。ビデオ再生は一瞬も止まらず、別の NIC に自動的に切り替わりました。
2. **接続速度のデモ**：「Windows」をクリックしてからデスクトップに到達するまでが、10 秒未満でした。
3. **HID リダイレクションのデモ**：Logitech のデバイスを使い、クラウド PC 上の Blender のシーンを操作しました。選択モードに入り、草のオブジェクトを上下に動かす様子が紹介されています。
4. **60 FPS のデモ**：GPU 付きのクラウド PC に接続し、レンダリングと Direct Stream の送信の両方に 60 FPS を選択。レンダリングされたモデルの表示中も 60 FPS が維持されていました。
5. **最後のデモ**：登壇者が "this video" と呼ぶ映像で、4K・60 FPS のセッションを 2 つ同時に実行する様子を見せました（録画かライブかは明言されていません）。1 台のマシンで、Blender の「有名なアクアリウム」と、「有名な UFO のクロマテスト」を並行して動かしています。プロジェクターは 4K ではないので、見た目は異なる、と断っています。このデモに関連して、サーバー側で 4:2:0 を取得し、クライアント側で 4:4:4 にアップサンプリングする新しい **super chroma** のソリューションが紹介されました。

## 7. 注意点・発表者の気付き

- **ネットワーク側の作業は発生しません。** ブランド変更のために、構成の見直しや機能の有効化をする必要はありません。通知を送らなかった理由も、変更点が無いからです。
- ドキュメントや UI の表記は **順次** Direct Stream に変わります。クライアントごとにリリース周期が違うため、切り替わるまで時間がかかります。
- 「クラウド上の RDP」は Direct Stream と読み替え、オンプレミスの Windows Server や RDS は引き続き RDP とします。
- HEVC は提供済みですが、**有効にしていない場合は有効にすることを勧められています。**
- 次に来る機能は、現時点では GPU 付きのクラウド PC を使う **プライベートプレビュー**で、発表は Q1 の早い時期の見込みです。Teams の転送プロトコルの取り込みは「近く提供するもう 1 つのオプション」として紹介され、提供時期は語られていません。
- 条件付きリダイレクションは、一部が Ignite の発表に含まれるものの、今後さらに投資する領域として語られています。

## 8. 利用者にとっての利点

- **切断が減る**：Multipath により、障害の平均間隔が約 5 時間から約 15 時間に伸びました。ある顧客は、1 日 4,000〜5,000 件規模の切断を、1 か月で 400 未満に減らしたとのことです。
- **すぐ使える**：Multipath は Windows 365 と AVD で既定で有効です。
- **接続が速い**：通常の接続が 10 秒未満で、再接続は Fast reconnect でさらに速くなります。
- **セキュア**：IP アドレスを公開せず、3389 も不要で、WebSocket Reverse Connect を使います。
- **画質と滑らかさ**：セッション全体で 60 FPS を維持し、HEVC により以前の世代より効率が良くなります。新しいエンコーダーは、4K・60 FPS を 40 Mbps 以下で、HEVC より約 50〜60% 効率よく届けるとされています。
- **GPU の効率と公平性**：NVIDIA Blackwell RTX 6000 Pro Server Edition で、同じ 4K・60 FPS の配信が 42% 効率的になり、エンコーダーのプリエンプションで複数ユーザーが同じ GPU を公平に使えます。
- **可視化**：テレメトリにより、どこでユーザーが切断されているか、どこがボトルネックかを確認できます。

## 9. まとめ

Direct Stream は、Windows 365 と AVD を支える技術スタックの新しい名前です。RDP との後方互換性を保ったまま、クラウド向けに作り込んできた部分をまとめたプラットフォームとして位置付けられています。

4 つの柱ごとの改善は次のとおりです。

- **接続の信頼性**：Multipath と、世界 42 以上のリージョンに置いた TURN
- **接続速度**：10 秒未満の接続と Fast reconnect
- **セキュリティ**：IP アドレスを公開せず、3389 も不要な WebSocket Reverse Connect
- **セッション内の性能**：60 FPS の維持、HEVC、HID リダイレクション、新エンコーダー、MMR

ブランド変更に伴う利用者側のネットワーク設定の変更は不要です。今後の機能は、GPU 付きクラウド PC を使うプライベートプレビューで試せ、発表は Q1 の早い時期を見込んでいます。Teams の転送プロトコルの取り込みも予定されています。詳細は、登壇者が案内した投稿、更新済みの学習ドキュメント、セキュリティや性能を扱う他のセッションで確認するよう案内されました。
