# THR998 12,000 Seats. Six Months. A New Direction with Windows 365.

## 1. はじめに

このセッションは、約 12,000 ユーザーが使う EUC（エンドユーザーコンピューティング）基盤を、6 か月の固定期限で **Citrix から Windows 365 へ移行した事例**の紹介です。登壇者は、なぜ移行を決めたのか、どう進めたのか、途中でどんな想定外があったのか、あえて後回しにした項目と学びは何か、という 4 つの観点で話しています。

この移行の特徴は、ユーザーの体験を変えないことを要件にした点です。ユーザー側の変更は、Citrix Workspace app から Windows app への切り替えだけに抑えられました。事例は、**音声通話（テレフォニー）、シングルサインオンと Kerberos、プライベートネットワーク接続**といった、実際に移行でつまずいた具体的な課題を含んでいます。最後には、コストに関する質疑応答もあります。

### 5.1 プロジェクトの概要

登壇者は「プロジェクトを 1 枚で」示したスライドとして、次の数値を紹介しています。

| 項目 | 内容 |
| --- | --- |
| 移行対象ユーザー | 約 12,000 人 |
| プラットフォームの利用組織 | 約 90 のサードパーティ組織・パートナー |
| アプリケーション | 約 400 |

ユーザー体験は変えない方針で、変わるのは **Citrix Workspace app から Windows app への切り替えのみ**です。大規模なトレーニングは避けたいため、継ぎ目のなさが組み込みの要件でした。

### 5.2 移行前の構成

エンドポイントは、主にサプライヤーのデバイスと管理対象のノート PC で、ほとんどが Windows、一部が Mac でした。置き換えの対象は、スライドで赤く示された次の中間レイヤーです。

- クライアントアクセス：Citrix Workspace app
- 接続：Citrix gateway service
- VDI のブローカリング：DaaS（発話は "DAS brokering" と聞こえ、音声認識の都合で表記が確定できません）
- プロビジョニング：MCS（Machine Creation Services。Azure 上のコンピュートをプロビジョニング）
- 電源管理とオートスケール：コスト最適化を担当
- WEM（Workspace Environment Management）：パフォーマンス最適化と設定
- Director：サービス監視

ワークロードは、**AVD マルチセッションが約 9,000 ユーザー、Windows 365 Cloud PC が約 3,000 ユーザー**で、合計約 12,000 ユーザーです。

マルチセッション環境は次の構成でした。

- Active Directory へのハイブリッド参加で、Azure 上にホスト、設定と管理は GPO
- ゴールドイメージは Jenkins の CI/CD パイプラインで構築（Packer を使用）。ゴールドイメージは全社で約 5 個
- ユーザープロファイルは、Azure 上の NetApp と FSLogix（発話では "FS Logics"）で管理

Windows 365 側は、Windows 11 のシングルセッション、Intune 管理、Entra 参加で、Cloud PC の接続には Azure Network Connection（ANC）を使っていました。

接続面は次のとおりです。

- インドには MPLS で接続するユーザーがいます。これは、インドの通信規制（telco regulations）に準拠するためで、ExpressRoute 経由で Azure テナントにプライベート接続しています。
- VDI から社内アプリケーションへの接続にも ExpressRoute を使っています。
- 境界の制御は Azure Firewall、インターネットアクセスと DLP は Broadcom の Cloud web gateway です。

登壇者は、構成図には多くの部品と可動部分があったと述べ、移行後の図と見比べてほしいと話しています。

### 5.3 なぜ今、変えるのか

理由は次の 3 つです。

1. **商業的な圧力**：プライベートエクイティ系の企業がよく使う手口として、長期の契約更新、値上げ、「食べ放題」型のライセンスを挙げています。コスト圧力が見込まれ、事業部門から「今の構成は本当に必要か、代替はないか」という声が出ていました。
2. **運用の回復力**：Microsoft、Citrix、Broadcom の 3 社が重大インシデントの会議に出て、それぞれ「自分たちの製品は問題ない」と言う、責任の押し付け合いが起きていました。ベンダーを減らして回復力を高めたいという大きな目標があります。
3. **戦略的な単純化**：構成図に、多くのコンポーネント、さまざまな PaaS・SaaS サービス、異なるネットワークがありました。より単純にして信頼性を高めたいという考えです。

進め方は、従来型のプロジェクトのフェーズどおりです。最初に discovery（何があるか、ペルソナの整理）を行い、何を作るか・何で置き換えるかの設計を作り、パイロットに進み、ユーザーを移行し、最後に古い環境を廃止します。

### 5.4 検討した選択肢

| 選択肢 | 発表での評価 |
| --- | --- |
| AVD ネイティブ（Citrix を外す） | すでに AVD を Citrix と併用していたため可能だが、大規模では基本的な機能にとどまる。高度なコスト最適化、イメージ管理、適正サイズ化には、通常は追加の管理ツールが必要 |
| AVD + Nerdio のような製品 | Citrix で埋まっていた部分を補えるが、別のベンダーと追加コストが発生する。避けたかった |
| Windows 365 に全面移行 | すでに利用しており満足している。ただし、マルチセッションでコスト最適化されている AVD から、シングルセッションの Windows 365 に移ると、コスト面の課題がある |
| そのほか（発話では "omnices"、Parallels など） | 他社ソリューションも選択肢としてあった（"omnices" は音声認識の都合で表記が確定できません） |

### 5.5 6 か月でやり切るために行ったこと

登壇者は、次の 4 点が効果的だったと説明しています。

- **専用のアプリケーションテストチーム**：アプリケーションの切り分け（トリアージ）、新プラットフォームでのテスト、所有者の特定、壊れた場合の修正担当者探し、進捗の追跡が、このチームの唯一の責任でした。うまく機能したとのことです。
- **主要ステークホルダーの早期パイロット**：ユーザーの約 4 分の 3 は、大手のサプライヤー約 5 社の所属でした。この 5 社を早期に巻き込み、接続テスト、パフォーマンスの確認、主要アプリのテストを行い、問題を解決する時間を確保しました。
- **外部の支援**：すでに運用（BAU）プラットフォームの運用を支援している組織を起用しました。環境に詳しく、人手を補い、プロジェクトチームとコンサルティング部門を組み合わせることで、厳しい期限に必要なリソースを確保できました。
- **プラットフォームへの確信**：すでに Windows 365 を使っていて、パフォーマンスも良く、大きな問題がありませんでした。社内に「すでに 3,000 人の開発者が使っていて、パフォーマンスに満足している」と示せたことが、事業部門への説得に効いたそうです。

### 5.6 想定外の出来事 1：RDP は一種類ではない

登壇者は「RDP は単なる RDP ではない」と述べています。Windows 365 の RDP には複数の種類があります。

- shortpath（発話では "short path"）
- TURN サービス
- プライベートネットワーク向けの shortpath
- プライベートネットワークで使う**固定ポート版**

この会社は MPLS を使っていたため、プライベートネットワーク版を使う必要がありました。登壇者は、これを「RDP バージョン 1」と呼んでいます。一方、インターネット経由で動的ポートを使う方式は「バージョン 2」と呼び、こちらのほうがはるかに良く動作する、と説明しています。

前のプロトコル（発話は "Citrix HCX" と聞こえ、HDX の音声認識の誤りの可能性があります）から移行すると、これらの違いが想定外でした。挙動の理解、設定方法、そして**オフショアのユーザーを MPLS 経由のみに制限する方法**（インターネット経由で接続するとインドの通信規制に反するため）が課題になりました。複雑でしたが、最終的には実現できたとのことです。

### 5.7 想定外の出来事 2：テレフォニー

約 2,000 人のコールセンターユーザーが南アフリカとインドにいます。前のプラットフォームでは HDX を使い、問題なく動いていました。ところが RDP に移すと、**通話の音声に大きな遅れ（lag）**が出ました。

コールセンターは顧客に直接対応する窓口で、困っている人からの連絡を受けます。つながらない、あるいは話しにくいことは、ブランドの評判に関わる失敗になるため、確実に解決する必要がありました。

原因は、**RDP のプロトコルには音声と映像のストリームの同期の仕組みが無く**、Citrix HDX にはある、という点です。HDX では両者が常に揃いますが、RDP は時間とともにずれます。たまに音声アプリを使う程度なら問題になりませんが、コールセンターのリアルタイム音声では成立しません。

対処は、**MMR（multimedia redirection）プラグイン**を使い、音声をプロトコルの外に出すことでした。音声が独自の経路を通るため、同期のずれの影響を受けなくなりました。登壇者は、テレフォニーは想定より難しく、移行で見つかった**最大のリスク**だったと述べています。

### 5.8 想定外の出来事 3：シングルサインオンと Kerberos

以前は、ユーザーが Workspace app に Entra の資格情報でサインインし、セッションを起動したあと、セッションにも Entra の資格情報でサインインしていました。移行後は Windows app に同じ資格情報でサインインし、そこから Windows 365 Cloud PC に**シングルサインオン**します。入力する ID とパスワードが 1 つ減るため、ユーザー体験は向上します。

ただし、アプリケーションがレガシーなシステムやレガシーなドメインに接続する場合、以前のプラットフォームではキャッシュされた資格情報にフォールバックできました。シングルサインオンでは、チケットでサインインしているため**キャッシュされた資格情報が無く、100% Kerberos に依存**します。その結果、以前は動いていた一部のアプリが動かなくなりました。

対処として、Kerberos チケットを取得する必要があるすべてのドメインコントローラーやドメインへ、**ネットワーク上の到達性（line of sight）**を確保する必要がありました。

なお、シングルサインオンを有効にするのはレジストリキーの設定で、セッションに再度サインインする必要がなくなる、というのが効果だと説明されています。

### 5.9 6 か月で完了できたか

登壇者は、**期限どおりに完了した**と述べ、IT プロジェクトで予算と納期の両方を守れた数少ない例だとしています。動かせない期限が、チームの集中を生んだという見方です。旧環境の縮小（run down）の推移を示すチャート（プロジェクト最後の 2 か月分）を見せ、実際には数週間早く終わり、最後の余裕期間は使わなかったと説明しています。

### 5.10 見送った項目とその理由

「すべてを一度にはできない」ため、限られた期間のなかで次の項目を後回しにしました。

| 項目 | 現状と今後 |
| --- | --- |
| ライセンス | 現在は全員に Cloud PC の Enterprise ライセンスを割り当てている。2〜3 年前に使い始めたときは、一部のライセンスの選択肢がまだ存在しなかったため Enterprise にした。臨時利用のユーザーが多いので過剰で、プラットフォーム全体のコストが必要以上に高い可能性がある。今後は一部を Flex モデルと Pool モデルに割り当て直してコストを最適化する |
| ネットワーク | すべて ANC で接続しており、Azure に固定されている。ファイアウォールルールや NSG ルールの管理に課題がある。Azure から切り離したい。Microsoft ホストのネットワークに移れば、UK South（ランディングゾーンの所在地）に縛られず、インドや南アフリカのユーザーの近くに Cloud PC を配置し、レイテンシーを下げられる。Azure からの egress 課金も不要になり、コスト削減が期待できる |
| ビルドの標準 | Windows 365 には 2 つのビルドがある。もともとの約 3,000 台は旧来のビルドで、新しい約 9,000 台は物理 PC の Windows 11 標準と同じ基準で構築した。時間をかけて統一し、Intune で同一構成にする。PC の入れ替えに合わせて通常運用（BAU）として整理する |

### 5.11 移行後の構成

最初に見せた構成図と比べると、移行後は大きな複雑さが取り除かれています。Citrix は無くなり、中央に Windows 365 の SaaS があり、残るのは Cloud PC の部分です。オンプレミスは左下、ユーザーは左上に位置します。部品が減り、手間をかけて世話をする必要のある部分が無くなり、**その多くは Microsoft が対処する領域**になった、と説明しています。

### 5.12 学んだ 3 つの教訓

1. **discovery をもっと行う**：時間の制約で十分にできなかった。何があるか、どう使われているかを把握しないと、後で想定外が増える。より良いペルソナの整理、ライセンスの割り当てができ、未知の部分が減っていたはずです。
2. **コンポーネントではなく、ジャーニーをテストする**：個別アプリの単体テストは多く行ったが、複数のアプリを組み合わせて使うエンドツーエンドのユーザーのジャーニーはテストしきれていなかった。そのためテレフォニーや Kerberos の問題を見逃した可能性がある。マクロの問題、32 ビット／64 ビットの対応（マーケットプレイスのイメージが 64 ビット版 Office を含むが、32 ビット版が必要なユーザーもいた）も例に挙がっています。ユーザーごとに異なる構成を用意することになり、すぐ複雑になります。
3. **サプライヤーに証拠を求める**：約 90 のサプライヤーに、接続要件をまとめた文書を渡し、ネットワークやプロキシ、プロキシバイパスルールを Microsoft の標準に合わせて設定してもらうよう依頼しました。全員が「設定した」と返答しましたが、実際にユーザーが乗って性能が出ないと、再確認が必要になりました。例えば Zscaler の IP 経由でトラフィックが来ており、本来はバイパスして直接接続すべきなのに、プロキシ経由になっていました。そこで、「どこで設定したか」「バイパスルールを見せてほしい」と証拠を求めるべきでした。何度も戻って支援・調査をする必要があり、リスクになりました。

### 5.13 今なら取れる選択肢

登壇者は、自分たちの移行時には無かったが、いま利用できる選択肢を紹介しています。

- **Windows 365 の移行 API**：Azure 上のパーソナルデスクトップを使っている場合、Windows 365 への移行フローを案内する API があります。
- **サードパーティの製品**：この API を使う製品があり、例として Nodeo（発話の綴りで、音声認識の都合により確定できません）が挙がっています。この製品は、既存環境を取り込み、「このユーザーは AVD に、あのユーザーは Windows 365 に」という推奨を出し、ウィザードで移行まで手伝います。
- **Citrix の柔軟なライセンス**：Citrix などは、その後により柔軟なライセンスを導入しており、既存のベンダーに留まるという選択もありえます。登壇者が移行の議論を始めた 1 年以上前の「食べ放題」型のライセンスとは異なる、という説明です。

### 5.14 Q&A

聴衆から、コストについて質問がありました。物理エンドポイントを購入する場合は 5 年に分けてコストを評価している、という前提で、Windows 365 に全面移行したときにコストはどう変わったか、また、ライセンスの変更を経て、この間に 1 デバイスあたりのライセンスコストがどれだけ上がったか、という内容です。

登壇者の回答の要点は次のとおりです。

- 既存の Microsoft 顧客として良好な関係があり、Microsoft に対して「全員を移行してほしいなら、価格が妥当になるようにしてほしい」と課題を投げた。
- 目標は、これ以上コストが増えないこと。別のベンダーを外すことで、一定のコストを削減できる。
- Windows 365 のデバイスあたりのコストは高くなるが、全体としては収支が合うよう調整した。
- 多くのユーザーは物理デバイスを持たないため、デバイスのコストも気にしなくてよい。

ライセンスコストの具体的な上昇率や金額は、発表では語られていません。

このセッションでは、画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。スライドで紹介された移行前後の構成図は、音声からは細部を確認できません。

## 7. 注意点・発表者の気付き

- **RDP の種類を理解する**：プライベートネットワークを使う場合は固定ポート版を使い、動的ポートのインターネット経由の方式のほうがはるかに良く動くと説明されています。オフショアのユーザーに MPLS 経由のみを許可する制限が複雑でした。
- **リアルタイム音声は RDP 単体では難しい**：RDP は音声と映像の同期が無く、時間とともにずれる。コールセンターは MMR で音声をプロトコルの外へ出すことで対処した。移行における最大のリスクだった。
- **シングルサインオンではキャッシュ資格情報が無くなる**：Kerberos への完全な依存になり、必要なドメインコントローラーへの到達性が必要になる。
- **サプライヤーの設定は証拠を求める**：プロキシのバイパスルールなどを確認しないと、後で再確認が発生する。
- **ライセンスとネットワークの見直しは移行後に残る**：Enterprise ライセンスを全員に付けているため過剰になりやすく、ANC による Azure への固定も課題として残っている。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **期限内の完了**：6 か月の期限を守り、数週間早く終わった。予算も守れた。
- **ベンダー数の削減**：問い合わせ先が 1 つになり、責任の押し付け合いを避けられる。
- **構成の単純化**：Citrix のレイヤーが無くなり、手をかける部品が減った。その多くは Microsoft が扱う領域になった。
- **ユーザー体験の維持**：ユーザーの変更は Workspace app から Windows app への切り替えだけで、大きなトレーニングは不要だった。
- **コスト**：別のベンダーが不要になった分を差し引き、Microsoft と価格を交渉して、財務的に収支が合うようにした（具体的な金額は語られていません）。
- **シングルサインオン**：ユーザーが入力する ID とパスワードが 1 つ減った。

## 9. まとめ

約 12,000 ユーザー、約 90 のサードパーティ組織、約 400 のアプリケーションを持つ環境を、固定期限の 6 か月で Citrix から Windows 365 へ移行した事例です。理由は、コスト圧力、複数ベンダーに起因する運用の責任の押し付け合い、構成の複雑さでした。専用のアプリテストチーム、大手サプライヤーの早期パイロット、運用パートナーの活用、すでに実績のある Windows 365 への確信によって、期限内に完了しました。

想定外だったのは、RDP の種類の違い、コールセンターの音声遅延（MMR で解決）、シングルサインオンでキャッシュ資格情報が無くなることによる Kerberos の問題です。教訓は、discovery の拡充、コンポーネントではなくジャーニーのテスト、サプライヤーに設定の証拠を求めることの 3 つです。今後は、ライセンスの Flex・Pool への割り当て直し、Microsoft ホストのネットワークへの移行、ビルドの統一に取り組む予定です。
