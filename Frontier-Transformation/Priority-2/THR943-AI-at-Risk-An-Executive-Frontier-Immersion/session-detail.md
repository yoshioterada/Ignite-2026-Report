# THR943 AI at Risk: An Executive Frontier Immersion

## 1. はじめに

このセッションは、架空の企業「Trey Research」が AI エージェントの急増に直面する物語を題材にした、参加型のクイズ形式の発表です。聴講者は Trey のセキュリティチームの一員として、物語の途中に出てくる 5 つの判断場面で、スマートフォンから選択肢に投票します。正解は点数になり、回答が速いほど高得点で、最高得点者には景品があると冒頭で説明されました。

物語を通して語られるのは、「何が動いているのか」「誰が責任を持つのか」「データにどこまで触れるのか」「危険な振る舞いに気付けるか」「どう封じ込めるか」という、エージェントを業務で使う際の問いです。結論として最後に示されたのは、**エージェントの利用を可視化する、責任者を明確にする、一貫したガードレールを適用する**の 3 点です。解決の道具として Agent 365 と Microsoft の Defender、Purview、Entra が登場します。

## 4. 発表者が伝えたいメッセージ

エージェントの数を数えるだけでは足りない、というのが出発点です。取締役会が知りたいのは、顧客情報や重要な業務判断が管理下にあるか、誰が責任を負うか、振る舞いが危険になったらどう対処するか、であると説明しています。目標は、有用な作業を止めず、明確な責任と統制のもとで続けることです。

そのうえで、Agent 365 を AI の可観測性のプラットフォームと位置づけ、ユーザー、アプリケーション、デバイスに対して行っている管理の規律を、エージェントにも同じように適用できると説明しました。始め方としては、重要なワークフローを 1 つ選び、事業の責任者とセキュリティ責任者が一緒に、可視性、説明責任、ガードレールに取り組むことを勧めています。

## 5. 発表内容の詳細

### 5.1 ゲームの進め方

Jim 氏は、他のセッションと違い、1 つの物語を追いながら進めると述べました。聴講者はスマートフォンで QR コードを読み取り、画面に表示されたアドレスにアクセスして、ルーレットで名前を決めます。各自が個人で参加し、判断場面では、問題と選択肢が先に読み上げられ、考える時間のあとに投票が開かれます。画面上の色付きの図形のうち、自分の答えに対応するものを選びます。1 つの問題に妥当な選択肢が複数ある場合もあるので、聞いた内容に基づいて最善の答えを考えるよう求めています。景品は最後まで残って勝った人だけがもらえるとのことです。

### 5.2 Trey Research の状況

Trey Research は、他社が頼るエンジニアリング・製造のパートナーです。手術器具のセンサー、電気自動車のバッテリーコントローラー、おもちゃのロボットの回路基板など、他社製品の内部の部品を設計・製造します。従業員は 8,000 人、拠点は世界各地で、他社向けの数十のプログラムを動かしており、それぞれが他社の未発表製品を扱っています。

事業は Microsoft の生産性ツールとセキュリティツールで運営されています。

| ツール | Trey での役割 |
| --- | --- |
| Microsoft Defender | 脅威の検出 |
| Microsoft Purview | データの分類と保護の支援 |
| Microsoft Entra | 誰がアクセスできるかの管理 |

セキュリティチームは 1 つで、これらをすべて担当し、長年それで足りていました。前年に Microsoft Copilot を展開し、3 か月分の試験データが認証申請書の初稿になり、数日かかっていた作業が 1 日の午後で終わりました。

その後、AI エージェントが現れ始めます。個人が合理的な理由で素早く作ったものです。たとえば、自分のレビューチェックリストを自動化したエンジニア、サプライヤー文書を要約するツール、試験結果を顧客が求める形式に変えるスクリプトがありました。無謀でも悪意でもなく、どれも実際に役立つものでした。

8 か月前、Trey は自社のエージェント承認プロセス「Project Keystone」を、セキュリティガバナンスのチームが運営する形で開始しました。承認されたエージェントは 60 を超え、それぞれ個人に紐づいています。ところが、各部門に実際に動かしているものを尋ねると、報告されたのは 140 件で、Keystone の一覧の 2 倍以上でした。利用の広がりが、把握の手続きを上回っていたということです。

同じ頃、他社で、誰も気付かないほど強いアクセス権を持つエージェントや、誰もレビューしていない判断で動くエージェントが報じられていました。取締役会は次の会議で CISO に「次の見出しになるのは我々か」と尋ねます。CISO の Oscar Ward は 20 年のキャリアがあり優秀ですが、正直な答えは「分からない」でした。エージェントの一覧はあっても、取締役会に説明できる根拠が足りないためです。翌朝、チームに問いを投げます。

チームには、6 年間セキュリティ調査を担当してきた Nia Clark、ID 担当の Andre、データ担当の Robin がいます。チームは Microsoft Agent 365 も使い始めており、その機能を取締役会の問いに当てはめることにしました。昼前までにできたのは答えではなく、まず理解すべき問いの一覧でした。最初の問いは「何が動いていて、誰が責任者か」です。

### 5.3 判断場面 1：リスクのあるエージェントを見つける

Nia と Oscar が最初に取り上げたのは、3 週間かけた部門向けのサーベイで、140 件のエージェントが見つかったという結果です。回答者の 1 人は「自分は何も作っていない。インストールしたものも数えるのか」と答え、誰もフォローしていませんでした。Oscar は金曜日に取締役会へ戻るため、何が動いていて、どこから手を打つべきかを知る必要があります。

問題は、金曜日の取締役会までに、Trey を危険にさらすエージェントをどう見つけるか、です。選択肢は 4 つでした。

- 部門向けのサーベイを更新し直す
- Agent 365 に表示される登録済みのクラウドエージェントをすべて見る
- クラウドとデスクトップのエージェントを、セキュリティツールの情報とあわせて確認する
- Defender と Entra のログを掘り下げる

投票では、クラウドとデスクトップのエージェントをあわせて確認する案が最多で、Nia もその道を選びました。Nia は、Agent 365 で登録済みエージェントを確認しつつ、Defender が見つけたデスクトップ上の検出結果も合わせました。これで Trey の作業上の件数は **2,000** になり、サーベイが見落としていたものも含まれました。数えるだけでは始まりにすぎず、利用可能なリスクシグナルで焦点を絞り、エージェントが何に到達でき、誰が頼っているかを調べています。

目立ったのは、機密性の高い顧客設計に到達できるのに、現在の所有者がいない稼働中のエージェントです。作成したエンジニアは Keystone のプロセスに従い、自分を所有者として登録していました。更新は手作業で、そのエンジニアが退職したとき、記録の更新も引き継ぎも行われませんでした。それでも 3 つのチームが毎週使っています。

### 5.4 判断場面 2：所有者のいないエージェント

3 つのチームが使うのに誰も所有していないエージェントに、どう対応するか、という問題です。チームが依存している機能を損なわずに、責任を元に戻す方法が問われました。選択肢は次の 4 つです。

- エージェントを停止し、チームに作り直させる
- スポンサー（責任者）を割り当てて設定する
- Keystone のプロセスに戻って所有者を記録する
- 誰かが退職した際に、IT がすべてのエージェントを処理することにする

投票では、**責任を持つスポンサーを割り当てる**が最多で、Jim 氏は、すべてのエージェントに所有者が分かるスポンサーを付ける方向が目指す形だと述べました。実際の対応は次のとおりです。

1. Microsoft Entra と Agent 365 で、エージェントに名前の分かるスポンサーを割り当てた
2. Entra ID Governance の組み込みワークフローを設定し、そのスポンサーが退職した場合は上司が引き継ぎ、関係者に通知が行くようにした
3. 責任者が決まったので、Agent 365 を Microsoft Entra と Purview とあわせて使い、Keystone のポリシーを実際の運用に反映した
4. エージェントのアクセスを管理し、作業に必要なデータ保護と保持のポリシーを適用した

Jim 氏は、人のために作られたルールを、エージェントにも適用したという表現で説明しています。

### 5.5 判断場面 3：デスクトップ上のエージェントのアクセス

一覧化により、デスクトップ上のエージェントも見えてきました。Nia の一覧の上位にあったのは、Aiden Hunt のコンピューターで動いているエージェントで、サーベイが見落としたローカルのものでした。Aiden は組み込みソフトウェアの開発者で、ローカルのデスクトップエージェント OpenClaw を自分でインストールし、顧客の要件定義書を読ませて、実装の前に設計案を検討していました。作業が速くなったので周囲にも話しましたが、申告するよう求めた人も、やめるよう言った人もいませんでした。

Aiden は 3 社の顧客の仕事を担当しています。Trey と各顧客の契約では、その顧客の設計はその顧客のプロジェクトにのみ使用でき、他の作業の支援には使えません。エージェントは Aiden のアカウントで動くため、Nia は、どのファイルとサービスを実際に使えるか、どこに接続していたかを確かめる必要があります。

選択肢は次の 4 つでした。

- 設定を確認する
- 管理下のすべてのデバイスでそのエージェントをブロックする
- エージェントが実際に何をしているか、セキュリティ上の検出結果を確認する
- Aiden に注目して、彼のアクセス権を絞る

投票は大きく割れ、Aiden と話す案と、エージェントのセキュリティ検出結果を確認する案が多く挙がりました。Jim 氏は、本人と話すのは業務の文脈を知るうえで良いが、覚えている内容では、エージェントが実際に行ったことや接続先をすべて網羅できないかもしれない、と述べました。

Nia が選んだセキュリティ検出結果の確認では、次のことが分かりました。

1. Microsoft Defender が Aiden のコンピューターで OpenClaw を検出し、Shadow AI（把握されていない AI の利用）の機能で、他に見つけたエージェントとあわせて Nia に示した
2. Defender はそのインストールを Aiden のアカウントに関連づけ、調査に必要な文脈を提供した
3. Nia は、設定されたアクセスと、利用できる活動記録を確認した
4. Microsoft Entra Internet Access で、エージェントから選択したサイトへの通信だけをブロックし、Aiden 自身はそのサイトにアクセスし続けられるようにした

これにより、ツールを取り上げずに境界を設けることができました。

### 5.6 判断場面 4：危険な振る舞いに気付けるか

次に、エージェントの振る舞いが危険になった時点を知る必要がある、という場面です。ID 担当の Andre Coleman が不審なサインインを調べていると、購買エージェントへのアクセスの記録が見つかります。この購買エージェントは、エンジニアリング担当 VP の George Tyndall が、サプライヤーの確認、購買依頼の作成、チームが必要とする部品の発注に使っているものです。不審な活動は George のアカウントに関するもので、George にとっては通常の作業です。Andre が懸念したのは、誰かが George のアカウントを使い、George が承認していない操作をエージェントにさせた可能性でした。そこで、エージェントの活動を調べるため、証拠を Nia に渡します。

選択肢は次の 4 つです。

- George に、問題のあった期間に何をしていたか確認する
- エージェントのセキュリティシグナルをすべて調べる
- 同じ調査を George のアカウントについて行う
- アプリケーションチームに、エージェントの全作業と操作内容を調べさせる

投票は圧倒的に、**エージェントのセキュリティシグナルを調べる**に集まり、Nia と Andre もそう進めました。Agent 365 を使い、Microsoft Defender でアカウントの活動とあわせて購買エージェントを調べています。Defender は購買エージェントに関する不審な活動を検出していました。証拠を調べると、エージェントの機能や接続先を探るようなリクエストと、呼び出されたツールの記録が見つかりました。これらのリクエストは、George が普段使う購買の作業に合いません。さらに、エージェントのセキュリティ態勢として、権限と接続済みツールを確認し、どの購買機能が影響を受けうるかを把握しています。結果として、エージェントの危険な使われ方の証拠と、業務への影響の見通しが得られました。

### 5.7 判断場面 5：購買リスクの封じ込め

Nia はアプリケーションチームを呼び、購買エージェントとそのツールをレビューさせ、Andre は George のアカウントを保護します。ただし、アプリケーションチームは、危険な活動の全容をまだ確定できていません。悪意のあるリクエストが発注書になる前に、レビューを続けながら購買リスクを抑え込む必要があります。しかも、必要以上に作業を止めないことが条件です。

選択肢は次の 4 つでした。

- エージェントの購買アクセスを制限する
- 問題が解決するまで、全員についてエージェントをブロックする
- George のアカウントだけに集中し、他の人にはエージェントを使わせ続ける
- アプリケーションチームがエージェントを再構成して、発注機能を完全に外すのを待つ

投票は、**購買アクセスを制限する**が最多で、Jim 氏はそれが正しい答えであり、Nia と Andre も同じ道を選んだと述べています。対応の流れは次のとおりです。

1. Agent 365 から得た情報により、購買エージェントを作り直さずにアクセスを制限できた
2. アクセスと権限を確認し、各検索が別々のコネクタ（接続部品）を使っていることが分かった
3. Andre が Microsoft Entra の条件付きアクセスポリシーを適用し、このエージェントから発注用コネクタへのアクセスをブロックした
4. 制限が効いているかを、Microsoft Entra のサインイン結果とエージェントの記録された活動で確認した
5. ポリシーの変更は Entra の監査ログに記録された
6. 制限を確認したあと、サプライヤー検索は再開できた

これでアプリケーションチームは、George の作業への影響を抑えながら、検出結果への対応を進める時間を得ました。

### 5.8 振り返り：Trey はどう成功したか

Jim 氏は、Agent 365 と Microsoft Security が、セキュリティチームの作業を事業全体でどうまとめたかを整理しました。

| 領域 | 内容 |
| --- | --- |
| 管理とガバナンス | Agent 365 でエージェントを管理・統制する。すでに人とデータを守っていた Microsoft Security のツールの上に構築 |
| 可観測性と制御 | Agent 365 でリスク対応の焦点を定め、Microsoft Entra で説明責任を確立する |
| デスクトップのエージェント | Aiden は仕事に必要なアクセスを維持したまま、境界を設けた |
| データ漏えいと過剰共有の防止 | Microsoft Purview が、機密データが AI のコンプライアンスを支える形でどう使われているかの証拠を提供する（担当は Nia と Robin） |
| AI の脅威の検出 | Microsoft Defender（担当は Nia と Andre） |
| 危険なアクセスの遮断 | Microsoft Entra のアクセス制御で、有用な作業を続けたまま遮断する |

取締役会に戻った Oscar は、エージェントを管理下に置き、すでに信頼しているセキュリティ統制を拡張することで、自信を持って業務で使えるという答えを得ました。

### 5.9 持ち帰る 3 点と結果発表

Jim 氏が組織に持ち帰ってほしいと述べた 3 点は、エージェントの利用を可視化すること、責任者を明確にすること、エージェントに一貫したガードレールを適用することです。

Agent 365 を AI のための可観測性プラットフォームとし、管理、ガバナンス、セキュリティ、事業価値の 4 つの観点で問いを整理しています。

| 観点 | 問い |
| --- | --- |
| 管理 | どのエージェントが動いているか。管理されていないものも含む |
| ガバナンス | 誰が責任者か。エージェントは何にアクセスできるか |
| セキュリティ | データをどう使っているか。危険な振る舞いに気付けるか。どう封じ込めるか |
| 事業価値 | エージェントが有用な作業をどれだけ生んでいるか。実際のコストはいくらか |

結果発表では、優勝者は 5 問すべてに正解した人で、1 位は「Suspense」と「Imaginative dog」という名前のプレイヤー名が読み上げられました（聞き取りの都合で、1 位の名前は 1 つに確定できません）。

## 7. 注意点・発表者の気付き

- **サーベイだけでは実態を把握できない**：部門向けの調査は 140 件、Agent 365 と Defender を合わせた確認では 2,000 件で、見落としが大きかったという流れです。
- **手作業の所有者管理は引き継ぎに弱い**：Keystone では所有者を手作業で記録していたため、作成者の退職後に所有者が不在になりました。
- **本人の記憶だけでは足りない**：エージェントが何にアクセスし、どこに接続したかは、セキュリティ検出結果で確認するほうが網羅できる、と述べています。
- **利用者を責めない**：Aiden を含め、誰も無謀でも悪意でもなく、役に立つものを作っていました。目標は有用な作業を止めないことです。
- **全面ブロックより絞り込み**：購買エージェントは作り直さず、特定のコネクタだけをブロックして、サプライヤー検索は続けられました。

## 8. 利用者にとっての利点

発表で語られた利点は、物語の中の効果として次のとおりです。

- 取締役会に、エージェントの数にとどまらず、データ、責任者、対応方法についての根拠ある説明ができる
- スポンサーと引き継ぎワークフローで、担当者の退職後も責任の空白を作らない
- ツールを取り上げずに、デスクトップのエージェントに境界を設けられる
- エージェントを作り直さず、一部の接続だけを遮断して、業務を続けながらリスクを抑えられる
- すでに使っている Defender、Purview、Entra の統制をエージェントに拡張できる

発表の中に、実在の顧客の成果や削減額などの数値はありません。

## 9. まとめ

Trey Research の物語を通じて、エージェントの数を数えるだけでなく、何が動いていて、誰が責任者で、データにどう触れ、危険な振る舞いにどう気付き、どう封じ込めるかを示せることが重要だと説明されました。可視化、責任者の明確化、一貫したガードレールの 3 点を持ち帰り、まず重要なワークフローを 1 つ選んで、事業責任者とセキュリティ責任者で取り組むことが勧められています。
