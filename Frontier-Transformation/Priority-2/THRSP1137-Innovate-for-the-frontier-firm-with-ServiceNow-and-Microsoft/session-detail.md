## 5. 発表内容の詳細

### 5.1 ServiceNow と Microsoft の提携

Tyler 氏によると、両社は AI 革命の前から連携しており、約 2019 年から 7 年間の協力関係です。最も速く成長している提携の 1 つで、共通のお客様とユーザーは数千、ServiceNow の生産性スイートと Microsoft の間の深い統合は 100 件を超えます。ServiceNow は Microsoft にとって上位の ISV パートナーでもあります。

共同開発は 4 つの層で考えます。Tyler 氏は、下から上の順に説明しました。

| 層 | 内容 |
|---|---|
| データ | すべての土台。Microsoft Fabric と ServiceNow の Workflow Data Fabric の間をゼロデータコピー（データを複製しない接続）でつなぎ、1 つの画面で扱える |
| AI エージェント | 両社のエージェントが協力し、利用者の課題を自律的に解決する |
| デジタルワーカー | エージェント間の相互運用で、デジタルな労働力を構築する |
| ガバナンスとコントロール | AI スタックの上下にわたる安全性、セキュリティ、可視性 |

### 5.2 運用現場の課題と自律エージェント

Deepak 氏は、AI と AI 駆動の大きな潮流が仕事量を増やし、ServiceNow に流れ込むチケットや問題が技術チームを圧倒していると述べました。立場ごとの痛みは次のように整理されています。

- サービス管理の責任者：チケットの量が多い。
- 技術運用：最近のサービス停止を踏まえ、ダウンタイムを最小にしたい。
- 資産管理：CMDB と CSDM が強みの領域で、答えるべき疑問が多い。
- CISO（最高情報セキュリティ責任者）：脅威を減らし、脆弱性を把握したい。
- CIO（技術戦略）：新しい技術投資の価値を知りたい。

ServiceNow は、システム・オブ・レコード（正式な記録の置き場）と ITSM のワークフローの上に、立場ごとの自律エージェントを用意しています。

| 立場 | エージェントの役割（Deepak 氏の説明） |
|---|---|
| サービスデスク | チケットを拾い、簡単なものは完全に自律的に解決する |
| 技術運用 | アラートを優先度付け（トリアージ）し、インシデントを作成して根本原因まで見つける |
| 資産管理（CMDB） | データを読んで分析し、編集もするチャットボットとエージェント |
| セキュリティ | SecOps で優先度付けと解決策の提示を行う |
| 価値の把握 | システムを理解し、アクションを実行し、レポートを公開する |

目標は、利用者がエージェント型 AI で圧倒されている新しい世界でも、すべての仕事をこなせるだけの道具を提供することだと述べています。

### 5.4 AI ガバナンス：ServiceNow Control Tower と Agent 365

Deepak 氏が担当する AI ガバナンス製品は、エージェントが動く層の 1 つ上に位置します。説明された内容は次のとおりです。

- **レジストリ**：企業内で把握したエージェントを 1 か所にまとめる。
- **ライフサイクルと態勢（ポスチャ）**：ServiceNow などで動くエージェントを発見したら、ライフサイクルの処理を始め、品質、セキュリティ、コンプライアンスなどの観点で、運用に伴うリスクと態勢を把握する。気になる指標が下がれば、課題を作成して、プロダクトオーナーに対する是正の流れを始められる。
- **エージェントのメタデータ**：エージェントのページには、用途と目的、構築者、管理者、接続先（どの MCP、どのモデルか）の関係図が表示される。
- **リスクの分類**：エージェントについて記述した内容から自動で付与されるが、リスク担当者が更新できる。
- すべてが 1 つのエージェントのレコードに保存され、AI に関する **唯一のシステム・オブ・レコード**になる。

**Control Tower と Agent 365 の違い**：ServiceNow は、リスク分類、リスク管理、統制管理などの領域から出発する製品で、CMDB でライフサイクルを管理し、残りの態勢を作り、インシデントを実行します。一方、Azure はエージェントを作る場所です。Agent 365 では、エージェントの動き方、使えるツール、使う ID、ガードレールなど、**実際に動作を制御するポリシー**を扱うほうが適している、という説明でした。両者は連携して使い、エージェントの可視性は Control Tower と Agent 365 の両方に反映されます。Control Tower で見えたエージェントは Agent 365 にも反映される、とも説明されています。

**概念図の説明**：ガバナンスはエージェントの実行基盤の上に位置します。コネクターとトレース収集の仕組みが各システムから情報を集め、CMDB に登録します。CMDB では、エージェント、利用モデル、スキル、ツール、利用する MCP サービスをモデル化します。これが発見の工程です。発見後にライフサイクルを始め、態勢の計算を行います。態勢には 4 つの柱があります。

| 柱 | 内容 |
|---|---|
| Govern（統制） | リスク管理。エージェントを動かすことで負うリスクを答える。本来のリスク（固有リスク）と、統制を踏まえた残存リスクがある |
| Secure（安全確保） | CMDB などから情報を集め、トレース上で動くスキルを使って、セキュリティ上の異常やレッドチーミングの結果を伝える |
| Observe（観測） | 判定用のモデルを使って、エージェントの品質を示す |
| Measure（計測） | コストと価値を計算する |

これらは、何かがおかしいと考えたときに課題を作成するために使います。CMDB を AI のシステム・オブ・レコードとする総合的な仕組みだと説明されました。

### 5.5 アーキテクチャと統合ポイント（Prashant 氏）

Prashant 氏は、Azure Monitor のアラートからインシデント解決までの流れについて、統合のポイントを 3 つ挙げました。

1. 人が承認するのは 1 つの変更だけで、残りのワークフローは最小限の監督で動く。
2. Microsoft のエージェントと ServiceNow のエージェントが MCP で連携し、より深い根本原因の分析とインシデントの解決を助ける。
3. 流れの中のすべてのエージェントは、ServiceNow Control Tower と Microsoft Agent 365 で管理され、信頼性が確保される。

Microsoft の 4 つの IQ はカンファレンスで何度も紹介されているが、このインシデント修復では特に **Foundry IQ** を取り上げる、と述べました。多くのお客様にはハンドブック、ナレッジ記事、トラブルシューティングガイドがあり、Foundry IQ はそれらをまとめ、ナレッジベースとしてインシデントに結びつけます。デモのとおり、これで解決が早まるという説明です。

**課題の規模**：現状は手作業で事後対応型であり、優先度付けも手作業が多いと説明しました。DevOps や SRE チーム、エンジニア向けの最近の調査から、次の数値が挙げられています。

- 61% の組織がダウンタイムを報告しており、そのコストは 1 時間あたり 5 万ドル（発話では 5 万ドルと聞こえます）。
- 57% のチームが、アラートのうち対応可能なものは 30% 未満と答えている（発話は音声が一部乱れており、数字の対応が不明瞭です）。

解決は 4 段階で説明されました。

1. フィルタリング：大量のアラートからノイズを取り除く。
2. 診断：Foundry IQ の知識を使って診断を早める。
3. 承認：人が 1 つの変更を承認する。
4. 解決（修正）：変更が最終的な解決まで進む。

フィルタリングから修正まで複数のエージェントが協力し、すべて Agent 365 と ServiceNow Control Tower で管理され、信頼されるという流れです。

## 6. デモ・手順

このセッションにはデモがあります。Tyler 氏が自律的な IT 運用のデモを、Deepak 氏が AI ガバナンスのデモを実施しました。録音は音声のみのため、画面の細部は確認できず、ナレーションで語られた範囲だけを書きます。

### 6.1 自律的な IT 運用のデモ（Tyler 氏）

シナリオは、停止した Azure VM を、自律的な解決まで導くものです。最初に、VM の名前に注目するよう呼びかけがありました。

1. Azure VM が停止している状況を見せた。目的は VM を復旧すること。
2. VM の問題が ServiceNow 内でイベント（アラート）になった。
3. 先に Deepak 氏が説明した AIOps スペシャリスト（エージェント）がアラートを拾い、同じ VM がアラートに表示された。エージェントがインシデントの調査を生成し、ノートと分析を追加して、停止した VM で何が起きているかを深く把握していく。
4. AIOps スペシャリストが詳細な診断と分析を行い、有力な根本原因と影響を判断した。この組織のワークフローに照らして重大度が十分に高いため、インシデントに引き上げた。同じ VM がインシデントに紐づいた。
5. ITSM エージェントが Microsoft の Foundry IQ を使って、ランブック（手順書）の情報を取得した。Foundry IQ はナレッジベースの知能層であり、アラートに基づく診断と推奨を確認する。
6. 同時に、後の解決で使う Azure SRE エージェントが VM を監視しており、独自の画面で動作を追っている。
7. ServiceNow では、Foundry IQ のランブック情報にもとづくワークフローと、推奨内容が自律的に作られた。
8. 推奨内容は修復アクションとしてインシデントに追加され、変更リクエストも、Foundry IQ の推奨に基づいて作成された。
9. 修復エージェントがその変更を拾って文書化した。ワークフローの設定により、**1 人の承認が必要**となった。ここまで人の介入はなかった。
10. ユーザーが変更を承認した。
11. 修復エージェントが、ServiceNow のエージェントと Azure SRE エージェントの連携で、先に説明した修正を自動で実行した。
12. 修正は人の承認だけで実装され、すべてインシデントとアラートに記録された。

Tyler 氏は、重大度が低い問題であれば、エージェントが人の介入なしで解決またはクローズできた可能性もあり、どちらになるかは ServiceNow に作ったワークフローで決まると説明しています。

### 6.2 AI ガバナンスのデモ（Deepak 氏）

1. 自律的な IT 運用のデモで登場した 2 つのエージェントが、新しいエージェントレジストリに発見されて表示された。
2. エージェントのページを開くと、用途と目的、構築者、管理者、接続先（MCP、モデルなど）の関係図が表示された。
3. リスクの分類が表示された。記述した内容から自動で付与されたもので、リスク担当者が更新できる。
4. Control Tower で見えたエージェントは Agent 365 にも反映される、と説明された（Agent 365 の画面を見せたかどうかは、発話からは確認できません）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 大量のアラートからノイズを除き、診断から修正まで複数のエージェントが協力して進めるため、手作業で事後対応型の運用から離れられる。
- 人の関与は変更の承認 1 回に絞れる。

## 9. まとめ

ServiceNow と Microsoft は、データ、エージェント、デジタルワーカー、ガバナンスの 4 層で共同開発を進めています。デモでは、停止した Azure VM について、AIOps スペシャリストによる検知とインシデント化、ITSM エージェントによる Foundry IQ からのランブック取得、変更リクエストの作成、1 人の承認、修復エージェントと Azure SRE エージェントによる修正が、1 つの流れとして示されました。エージェントは ServiceNow Control Tower と Agent 365 で管理されます。ブースでは同じデモと、より深い内容を見られます。
