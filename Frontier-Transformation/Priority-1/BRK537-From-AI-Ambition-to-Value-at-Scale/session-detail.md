# BRK537 From AI Ambition to Value at Scale

## 1. はじめに

このセッションは、AI の利用が実験段階から日常の業務に移ったいま、「使われている量」ではなく「どれだけ価値が出ているか」をどう測り、どう判断するかを扱った発表です。Microsoft の Frontier Company で実際にお客様と AI を本番化している 3 名が、社内とお客様での経験をもとに話しています。

## 5. 発表内容の詳細

### 5.1 導入: 実験の時期から、スケールの時期へ（Sarah 氏）

Sarah 氏は、自身が率いるのは、データサイエンティスト、応用科学者、ソフトウェアエンジニア、セキュリティ担当者などからなる大きなグループで、時間の大半をお客様との作業に使い、「動くまで帰らない」姿勢だと紹介しています。

社内の Frontier Company では、AI First というプログラムを運営し、従業員が本番環境でお客様に価値を届けられるよう支援しています。その理由として、技術をできるだけ活用したいことに加え、優秀な人材を引き留めるには面白く挑戦的な仕事を任せる必要があることを挙げています。

AI 利用の初期には、月末の請求書やプランの料金から、支払った総額は分かりました。しかしその内側を追跡するのは難しい、というのが出発点です。新しい指標をどう定義するかが課題で、生産性指標や space metrics（聞こえた表記）のような高いレベルの話では足りず、投入したものと得られたものを、事業責任者や財務、エンジニアリングのリーダーとして説明できる形で追う必要があると述べています。

注目の変化として、AI を使い込んで好奇心を持つ人は増えていたものの、以前はそれを測る企業は多くありませんでした。それが現在は、**約 98% の組織が本気で取り組み始めている**と話しています（Q&A でも「98% の組織が制御を入れている」と繰り返されます）。会場周辺のブースでも FinOps や TokenOps に取り組む企業が多く見られ、これは財務の問題であるだけでなく、すべてを追跡する技術的に興味深い課題でもあると述べています。

社内の経緯も紹介されています。最初は実験の時期で、無料のトークンがあちこちで手に入り、あらゆる agent や harness、skill を試して学びました。Sarah 氏自身、欲しかったユーティリティを vibe coding で次々に作ったそうです。その後、事業側から「移行をもっと速くできるか」「お客様をより安全にできるか」「自律的な作業、監督付きの自動化、ガバナンスの効いた技術を AI でどう提供するか」「その料金をどう決めるか」「成果をどう測るか」と問われるようになり、パイロットを始めました。現在は業界全体がそれらをスケールさせようとする段階にあります。

また、ウォーターフォールではなく、DevOps の継続的改善ループに近い「運用ループ」で考える時代だと述べています。ループの基本は変わりません。

* 誰かが計画を持ち、所有する。計画には財務の側面と技術の側面がある
* どこに支出を置くかを決める
* 資産や agent を制御し続ける
* レビューを最適化し、継続的に改善する

この改善の一部は AI 自身が行うようになっており、hill climbing、stair climbing、wayfinding といった言葉も聞かれるが、人でも agent でも両方でも、ループで動いている点は同じだという説明です。ループの各段階で証拠を集めたいとして、従来のソフトウェア開発の指標に加えて、「トークン 1 つから何の yield が得られるか」「より成果の大きいものにトークンを使うにはどうするか」を各段階で考えると述べ、Gareth 氏に話を引き継ぎました。

### 5.2 agent のループとコスト、agentic efficiency score（Gareth 氏）

Gareth 氏はまず、コストも潜在的な価値も、agentic loop の内側から始まると説明します。agent は反復して動き、読み取り、生成し、ツールを使って作業を実行し、外側のループで自分の作業を評価します。これらの動作のすべてにトークンのコストが発生します。

* 単一の agent なら比較的予測しやすいが、何度も反復すればコストは積み上がる
* トークンがキャッシュされるのか、新規の書き込みになるのかで、操作の種類ごとに単価の階層が異なる
* fan-out や multi-agent システムではコストがさらに倍増する。agent は長時間のタスクを担うことが増えている

Gareth 氏がチームに最もよく尋ねるのは、agent の仕事を次の 3 つの観点で評価しているか、という点です。

| 比率 | 問い |
| ---- | ---- |
| Finished | 人の介入なしに、自律的に作業を終えているか。agent に対して人が何時間関わっているか |
| Kept | 終わった作業が必要な品質に達しているか。保持されるか、QA を通るか、少ないレビューで PR を通過するか |
| Mattered | 作業が製品やソリューションに入って使われたとき、どれだけ重要か。KPI を前に進めているか |

この 3 つを掛け合わせたものが **agentic efficiency score** です。3 つの要素は互いに積み上がるため、積を見たいという説明です。測定とチームの衛生管理が整った後は、3 つの比率を予測できるかが関心事になります。Frontier の agent でも、ローカルや sovereign AI の agent でも、特定の harness や agent クラスについて、次のタスクや次の反復で消費するトークンからどれだけの価値が得られるかを予測できるか、という問いです。そこに token ops の運用ループの力があると述べています。

### 5.3 運用ループ: 計画（plan）

運用ループの最初は計画です。Gareth 氏は、計画の対象は **task class（タスククラス）** だと説明しています。共通のパターンがある、よく行う作業のことで、特定の種類のドキュメントの処理や、agent による agentic engineering でのタスク作成などが例です。同じ task class は、共通のループ、ツール、成果を持ちます。計画の段階で必要なのは次の点です。

* その task class が提供する価値を、できればドル・ユーロ・ポンド・円といった金額で把握する
* 成功した成果 1 件あたりのコストを把握し、過去にどう測ったか、将来どう変わると見込むかを整理する
* この 2 つから yield（得られる価値 ÷ それを得るのにかかったコスト）を計算する。ここで finished・kept・mattered の 3 つの比率を使う
* 止める条件（stop condition）を定める。何千もの agent が業務プロセスを動かしているとき、想定の範囲外に出たらすぐ止める必要がある。セキュリティ、コスト、運用のいずれの懸念にもなり得るため、閾値を決め、適切なエスカレーション付きで自動的に作動するフックやトリガーを備えることが不可欠だと述べています
* その task class の owner を決める。自動化・拡張しようとしているプロセスの専門家は誰か、予算権限と運用権限を持つ人とどう協働するか

### 5.4 運用ループ: 制御（control）

制御の段階は 3 つの部分でできていると説明されています。音声で名前が挙がったのは、最初の tags and measurements（タグ付けと測定）と、続く attribution（帰属）です。そのあとに decisions（判断）、outcomes（成果）、actions（行動）の話が続きますが、3 つの部分の区切りは音声からは確定できません。

**タグ付けと測定。** Gareth 氏は、測れるものはすべて測り、タグを付けてほしいと強調しています。良いデータがあれば、複雑な問題も扱いやすくなるという考えです。問題はエンジニアリングや運用のシステムの中だけでなく現実の世界にもあり、そこはデータ取得の難しい場所だとも述べています。タグは、次の階層を貫いて付けるものとして説明されています。

* トークン、モデルを通じて消費されたときの 1 回の呼び出し（call）
* agent がループで作業しているときの反復（iteration）
* 複数のループや複数の agent が動く 1 つのタスク
* 1 つの個人またはグループが所有する task class

**帰属（attribution）。** 最も低いレベルの帰属は請求書（billing）で、月末に届くだけです。Gareth 氏は、請求より、呼び出しごとの利用状況に関心を持つべきだと述べています。どのモデルや agent harness から適切な効率や価値が得られているか、逆にどこでコストが高くなっているかが分かるからです。さらに **decisions（判断）** として、どれだけの作業が kept され、QA を通り、実際にユーザーに届いているかも把握したい、と述べています。

**成果（outcomes）。** 4 番目で、最も測りにくい領域です。請求書は最初に届き、トークンの消費量は日単位、時間単位で分かります。一方で、3 か月後に影響を与えたいユーザーや、その生涯価値（lifetime value）は、数週間、数か月、場合によっては数年後にならないと数字が出ません。ただし、これらはすべて同じ式の一部だと説明しています。

### 5.5 コストと yield の読み方（actions）

帰属が得られれば、actions（行動）を通じて制御の判断ができるようになります。Gareth 氏は、コストと yield の関係で次のような読み方を示しています。

| 状況 | Gareth 氏の見方 |
| ---- | ---- |
| 成功成果 1 件あたりのコストは上がったが、yield は維持されている | 理由は確認したいが、単に処理するドキュメントが増えただけかもしれない。意図した使い方で、むしろ良いことの可能性もある。さらに時間と費用を投資すべき場所かもしれない |
| コストが上がり、yield が下がっている | 深刻な問題。agentic loop 内で何らかの失敗モードが起きていて、作業が適切に完了しないまま、より多くのお金を使っている。ここで止めて、何をしているかを把握する |
| 支出が価値を上回っている（予算を想定より大きく消費している） | 予算の owner に相談し、どう軽減するかを考える |

こうした対応は、制御しようとしているのが **price event（価格の事象）** か **yield event（yield の事象）** かを見極めるためだと言います。それぞれに対して使えるレバーが異なり、発話では「はしご（ladder）」と呼ばれています。画面の上のほうに示されたレバーは、まず yield に作用し、特定のタスクから得られる価値を変えるうえでより効果的だと説明されています。具体例は、agent のループを直すこと、キャッシュをより上手に使うことです。一方、price に作用するのは、モデル、harness、それを動かすインフラの基礎的なコストです。

### 5.6 次の 1 か月でやること: 4 週間の進め方

Gareth 氏は、次の暦月に、チームで次の 4 週間を実行するよう勧めています。

1. 1 週目: できるものはすべてタグ付けする
2. 2 週目: yield が最も低いもの、つまりコストに対して最も効果の薄いプロセスやタスクを見つける
3. その次: はしごからレバーを 1 つ引き、変化を確認する。card と書き留めた内容と比べる（"card" の指すものは音声からは確定できません）
4. 4 週目: 変化を時間とともに追跡する

> 補足：発話では「1 週目」「2 週目」「4 週目」が明示され、3 週目という言い方は聞き取れませんでした。上の 3 番目は、2 週目に続けて語られた内容です。

これにより、冒頭で Sarah 氏が述べた判断に行き着きます。**うまくいっているものをスケールするのか、まだうまくいっていないものを改善するのか、エンジニアリングを重ねても価値の見込みがないものを止めるのか**、という判断です。Gareth 氏は、月次の AI の請求書ではなく、その月の成果に興奮できるようになるべきだと述べ、David 氏に引き継ぎました。

### 5.7 事例: Contoso Insurance のビジネス価値（David 氏）

David 氏は、Contoso Insurance（自動車保険会社）の例を使って、ビジネス価値の考え方を説明します。出発点は常に **ambition（野心・目標）** で、「事業をより良く、速く、効率的に、市場で競争力のあるものにするために何をしたいか」です。この例の ambition は「請求（claims）をより速く」です。理由には、競争上の差別化、顧客満足度の向上、同じ人員でより多くの請求を処理できること、などが挙げられています。具体的な目標は、**請求の平均処理期間を 14.2 日から 10.5 日に短縮する**ことです。

この ambition を、次のような問いに分解しています。いずれも、請求が開いている期間を短くするという事業目標に向けたユースケース、またはワークフローです。

* 損害の申告を、5 回ではなく 1 回の会話で受け付けるには
* 複数の別々のシステムにまたがる請求の各部分を、適切な担当者に適切な情報とともに素早く振り分けるには
* 写真の確認による査定を支援し、食い違いの可能性や追加情報が必要な欠落を示すには
* 査定担当者（adjuster）が、顧客、請求チーム、修理を行う車体修理会社と、素早く効率的にやり取りして判断するのを支援するには
* 決済（settlement）の工程を支援するには
* 顧客が「自分の請求がいまどこにあるか」を知るには

**価値の計算。** 財務チームと一緒に、1 件の請求を 14 日ではなく 10 日の枠で処理できたときの価値を決めます。この例では 1 件あたり $1,000 です。そのうえで 2 つの概念を使います。

| 概念 | 意味 | この例の数値 |
| ---- | ---- | ---- |
| depth（深さ） | 目標までの道のりのどこまで来ているか | 現在 12.6 日で、目標 10.5 日に対して約 43% |
| breadth（広さ） | 毎月システム内の請求のうち、agentic システムで支援している割合 | 約 500 件で、約 50% |

**1 件あたりの価値 × depth × breadth** が価値になります。これはグロス（粗）の価値で、システムのコンピュート、ストレージ、トークンなどのコストはまだ引いていません。David 氏は、これが式の最初の部分であり最も重要だと述べています。これがないと、トークンの話をするまでもなく、投資を正当化するのが難しくなるからです。

**コストと J カーブ。** コストは observability（可観測性）で捉え、定期的なレポートにします。発表では、すべての agent が動いている状況で「請求 1 件あたり平均 $5」という数字が挙がり、3 か月目にはコンピュート・ストレージ・AI のコストが「1 ドルあたり 64 セント」（"64 cents on the dollar"）だと話しています（どちらの数字も、何を分母・分子にしたものかは音声からは断定できません）。ここで止めて見ると「コストを賄えていない」と見えますが、実際には投資が別にあります。

* ソリューションの実装に約 $1,000,000 かかる
* 最初に収支が落ち込む期間（dip）がある。その位置を知り、スポンサーにあらかじめ理解してもらうことが大切
* 5 か月目あたりで ROI が出る見込みで、そこから伸びる。12 か月目には約 2.5 倍になる

月ごとに測って計画どおりか確認することが非常に重要で、リーダーは判断の前に、数字が低いことが計画どおりか計画外かを知っておく必要があると述べています。価値とコストの広がり（spread）が開いていく様子を **J カーブ**（最初に落ち込み、時間とともに伸びる）と呼び、これが operating leverage の実証であり、AI による変革に意味があることの証拠になると説明しています。

### 5.8 value ledger と scale / improve / stop の判断

observability のデータを使って、David 氏が **value ledger** と呼ぶものを追跡します。事業データと、コンピュート・ストレージ・トークンのデータを結びつけたデータモデルです。ambition に含まれるすべての agent の呼び出しには work item があり、次を記録します。

* どの agent か、どのモデルか
* 成功基準を満たしたかどうか
* リトライしたか、人の介入が必要だったか
* コストはいくらか

画面（スライド）には、上部に品質バー、左側に work ledger の全体、右側にモデルの使われ方が表示されていたと説明されています。モデルの使い方からは、あるモデルを多用しているが、前回見たときから状況が変わり、より良いモデルがあるかもしれない、といった見直しにも繋がります。もう一方の端にあるのが **intelligent spread**（音声認識の都合で表記が確定できません）で、組織全体、事業部門、あるいは ambition 単位での「創出した価値とコストの差」、つまり agentic システムによる変革の投資対効果を示します。

これらを使い、各 agent を **期待 yield** に基づいて scale・improve・stop に分類します。yield は、先に出た finished・kept・mattered の 3 つの掛け算です。事例の agent は次のとおり整理されています。

| 判断 | 対象 | 内容 |
| ---- | ---- | ---- |
| Scale | 2 つの agent（名前は音声から特定できません） | finished・kept・mattered と最終的な yield が良好。次の資金をどう出すか、月 500 件から 750 件へどう広げるかを考える。depth が保たれるなら価値が増える。breadth を広げる間も depth を監視する。新しいベースラインのカードを書き、より大きな範囲、たとえばより複雑な請求を扱うために改善が必要な点を検討する |
| Improve / constrain | assessment agent、adjuster agent（ほかに "C&D" と聞こえる agent が挙がっていますが、音声認識の都合で表記が確定できません） | yield が計画を超えるまでは新たな資金を足さず、最も弱い入力を探して直す |
| Stop（pause または retire） | 2 つの agent（名前が挙がったのは customer update agent） | 後述 |

**improve の例。** assessment 側では、査定担当者が写真の確認をやり直したり、「もっと情報が必要」と何度も再試行したりしている状況が見られました。そこでループの回数を減らす改善を進めるため、いったん止めます。直せない部分は constrain（制限）します。adjuster assistant は、より権威的に振る舞うのをやめて、**助言のみ（advisory only）** にしました。人がループに入る度合いを高め、サイクルの数を抑えることで kept が増えました。

**stop の 2 つの答え。** pause（一時停止）と retire（廃止）です。アイデアは妥当なのに期待した結果が出ないときは pause で、何が原因か、どんな場面なら効果的かを探します。対象とする請求の種類を変えたり、agent が対象とする範囲を絞ったりする余地があるかもしれません。

**retire / 見直しの例（customer update agent）。** この agent の目的は、モバイルアプリ、ウェブサイト、電話システムなどを通じて「自分の請求がどこにあるか」に答え、コールセンターの人に電話させないことでした。agent が作業を終え、データも正確で、使うたびに正しい結果が返る、という場合でも、人は「agent を信用できない、誰かと話して違う答えを得たい」と考えることがあります。この例では **mattered の面で、コールセンターへの電話を減らせず、事業側の指標を動かせませんでした。** 選択肢は、価値を生んでいないので agent を廃止するか、データが正確でニーズを満たしていること、コールセンターに電話しなくてよいことをエンドユーザーにもっと伝えるマーケティングなど、別のやり方を考えるか、です。stop によって、価値を生むものに資金を回し、さらにスケールできます。**スケールは必ずしも予算を増やすことを意味せず、あるものから別のものへ予算を移すことかもしれない**と述べています。

**判断の書き方。** 判断には owner、trigger、date を添えて書き残します。

* 何をスケールするのか。breadth と depth の新しい目標は何か
* 証拠は何を言っているか
* cohort（集団）も考える。平均の長期的な推移だけでなく、今後 4 週間、次の四半期に何を見込むか
* 目標に届かなくても価値がゼロとは限らない。ある程度の価値は出ており、それで十分か、さらに見るべきかを判断する。期待 yield のデータがその判断を助ける
* いつ revisit（見直し）し、いつ review（レビュー）するか。revisit は何かが起きたら直ちに見ること、review は決めた日付に cohort を見て次の手を決めること

David 氏は最後に、**証拠が、何がスケールに値するかを決める**、と締めます。Gareth 氏が測り方を示し、David 氏の部分では「支出し、yield を測り、判断し、行動し、報われるものをスケールする」という流れが示されました。来週職場に戻ったときの宿題として、次を挙げています。

* 自分の事業で価値を生むものは何か。その価値に数字を付けられるか
* 財務チームに、その数字に合意してくれるパートナーを見つけられるか。IT の見方ではなく、事業側が価値があると言うことが重要
* 計画に照らしてテストし、"devals"（音声認識の都合で表記が確定できません）を使い、事業にとっての意味を見る
* すべて書き残す。全員が合意でき、後から戻りやすくなる

## 7. 注意点・発表者の気付き

* **価値の定義が先。** 価値を定義できないものから始めると、トークンの請求が来るたびに「価値があるのか」と問われ続けます（David 氏）。
* **dip を前提にする。** 初期は投資のためにコストが価値を上回るように見えます。dip の位置と ROI の見込み時期をスポンサーと事前に共有し、月ごとに計画どおりかを確認します。
* **コストだけを見ない。** コストが上がって yield が下がっているときは、agentic loop の失敗モードを疑って止めて確認します。コストが上がっても yield が保たれていれば、処理量が増えただけの可能性もあります。
* **正確でも使われるとは限らない。** customer update agent は答えが正確でも、人が agent を信用せず電話をかけ続けたため、mattered が低いままでした。
* **データの品質。** Gareth 氏は、データサイエンティストとして良いデータを強く求めており、測れるものはすべて測り、タグを付けるよう呼びかけています。
* **成果は遅れて届く。** 請求やトークン量は即座に分かりますが、ユーザーの生涯価値などは数週間から数年後です。
* **目標に届かないことは無価値ではない。** 目標未達でも一定の価値はあり、それで十分かを期待 yield のデータで判断します。
* 「agent を使えば 10 倍速く開発できる」といった一般的な声だけでは十分ではなく、それが自分たちの事業で何を意味するかへ変換する必要がある、という趣旨の発言が Q&A でありました。

## 9. まとめ

AI の利用が広がっても、その量は価値を保証しません。Gareth 氏は、agent の仕事を finished・kept・mattered の 3 つの比率で見て、その積を agentic efficiency score とし、task class を単位に、計画（plan）と制御（control）を中心とした運用ループで管理することを説明しました。コストが上がったときは、yield が保たれているか、下がっているかで対応を分け、price と yield のどちらの事象かを見極めます。次の 1 か月は、タグ付け、低 yield の特定、レバーの実行、変化の追跡の順に進めます。

David 氏は、Contoso Insurance の例で、1 件あたりの価値 × depth × breadth の粗い価値にコストと投資を重ねて J カーブを描き、value ledger の記録から各 agent を scale、improve、stop に振り分ける方法を示しました。判断は owner、trigger、date とともに書き残します。**価値を定義できるところから始め、証拠で何がスケールに値するかを決める**、というのが全体を通した結論です。
