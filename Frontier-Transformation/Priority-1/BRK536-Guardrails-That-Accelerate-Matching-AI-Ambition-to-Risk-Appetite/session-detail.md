# BRK536 Guardrails That Accelerate: Matching AI Ambition to Risk Appetite

## 1. はじめに

このセッションは、AI の導入を進めたい経営層・IT 部門・セキュリティ部門が、「どこまでのリスクを取るのか」を同じ認識で話し合うための材料を提供するものです。前半は Microsoft Security の Ron Pessner 氏が、AI 導入に向けて経営層と IT チームが交わしておくべき 4 つの会話を紹介します。後半は Microsoft の CISO オフィスの Terrell Cox 氏を迎えたファイヤーサイドチャット（対談）で、Microsoft 自身がどのようにリスクと向き合っているかが語られます。

全体を貫く主張は、**イノベーションと安全性はトレードオフではなく、セキュリティこそがイノベーションを支える**、という点です。

製品のデモやアーキテクチャ解説が中心のセッションではありません。スライドと対談による、考え方と事例の共有が中心です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK536](https://ignite.microsoft.com/en-US/sessions/BRK536)

## 4. 発表者が伝えたいメッセージ

Ron 氏は、AI の機会とリスクは「別々の話ではなく、同じ能力から生まれる同じ話」だと説明します。例えば次のような対応関係です。

| AI がもたらす力 | 同時に生まれる課題 |
| --- | --- |
| より多くの顧客に届けられる速さ | ミスも増幅しうる |
| 常時稼働のサービスを可能にする自律性 | 明確な権限と説明責任が必要になる |
| 事業全体でエージェントをつなぐこと | 新しい依存関係が生まれる |

そこで、AI が何をしているかを見て、その行動を独立して検証し、許可することを制御する必要がある、というのが出発点です。

後半で Cox 氏が加えた主張は、次の 3 点に集約できます。

- セキュリティの基本（fundamentals）は今も有効で、新しい攻撃に目を奪われるよりも、基本を押さえて限られた資源を重要な対策に向けることが大事
- リスク許容度は組織内で事前にすり合わせ、安全性・ガバナンス・セキュリティ・可観測性を「譲れない条件」として成功の定義に含める
- 変化が速いため、自社で作ったものにも執着せず、実験を許す文化と、燃え尽きを防ぐ長期戦の姿勢が必要

## 5. 発表内容の詳細

### 5.1 導入：AI の野心とガバナンス

Ron 氏は冒頭、Ignite で多くの顧客が事例を語っていることに触れ、AI は既存の仕事を速くするだけでなく、本当の変革が起きていると述べます。人とエージェントとトークンのチームが大きな成果を出しており、Satya 氏がよく語る「新しい生産関数（production function）」を皆が体験している、という話です。

AI が事業にもたらすものとして、以前は対応できなかった顧客に届くこと、アイデアから実行への移行が速くなること（プロトタイプがそのまま製品になる例を気に入っているとのこと）、従来は現実的でなかった提供価値を作れることが挙げられました。常時稼働の協調型エージェントがこの新しい働き方を示している、という位置づけです。

### 5.2 AI 導入のための 4 つの会話

Ron 氏は、経営層・IT・セキュリティが進む道をそろえるための「会話のきっかけ」として、次の 4 つに絞って紹介します。

1. 基本的な統制は整っているか
2. どのエージェントが使われていて、誰が所有し、何ができるのか
3. ID やアプリの権限を含め、重要なものを露出させずにデータを活用できるか
4. 露出（exposure）を継続的に減らし、基本事項で進歩し続けるにはどうするか

#### 会話 1：基本を徹底する（Brilliant with the basics）

Ron 氏は、Fortune 500 の金融・保険会社の CIO と CISO に会った際、CIO から「チームには基本を完璧にこなしてほしい（brilliant with the basics）」と聞いたと紹介します。この言葉が多くの顧客の声を表していると感じ、借用しているそうです。

この流れで、Microsoft は FastTrack チームと緊密に連携し、顧客が AI に備えるためのイニシアチブを実施していると説明します。基本を整えるためのイニシアチブは 4 つあり、`aka.ms/securenow` で確認できます。FastTrack については次の点が語られました。

- 世界中の顧客を支援するため、300 人を超える FastTrack エンジニアを動員している
- 追加費用は無い
- 目的は、ベストプラクティスの共有と、Microsoft の推奨事項やガイダンスの実装を支援すること

#### 会話 2：エージェントの可視性・説明責任・制御

エージェントについては、次の 3 点を挙げています。

| 観点 | 発表で語られた内容 |
| --- | --- |
| 可視性 | どのエージェントが作られ、何を操作し、何が見えるのかを把握する |
| 説明責任 | 誰が責任を持つのか。エージェントに ID はあるか。誰かの代理で動くのか、独自の ID を持つのか。責任を持つ所有者を決める |
| 制御 | エージェントに与える権限を定義する |

制御については、Ignite で専用のセッションがあったため詳しくは扱わない、とのことでした。Ron 氏は、Microsoft 社内では「hundreds of thousands」（数十万規模）のエージェントが作られているのを見てきたとして、可視性は非常に重要だと述べています。

#### 会話 3：データのセキュリティ

データの話は「ラベル付けだけの話ではない」と Ron 氏は強調します。ID やアプリケーションを通じて情報に到達できることも含めて考える必要があります。目指す状態は、過剰共有（oversharing）、古くなったアクセス、過大なアプリ権限を生まずに、AI が価値あるデータを使えることです。「承認」や「OK」を何となくクリックしてしまうことが過剰共有につながり、セキュリティ面で大きな問題になる、という指摘もありました。

推奨は次の 3 段階です。

1. データから始める（分類とラベル付け。これについても Ignite で複数のセッションがあったとのこと）
2. 休眠アカウント、高リスクユーザー、非人間 ID（non-human identities）を調べる
3. 委任された同意（delegated consent）を強化し、アプリのアクセス権限を削除し、安全でないアプリの資格情報に対処する

#### 会話 4：継続的な脅威エクスポージャー管理

Ron 氏は、これを「ループ」と表現し、2 つの歯車があると説明します。

- **姿勢の強化（posture hardening）**：時間をかけて徐々に強い状態にし、AI に備える長期的な取り組み
- **新たな脅威への対応**：新しい脅威が出たときに、自分の業界・会社にとって何を意味するかを理解し、侵害が起きる前に行動する

従来のエクスポージャー管理は「長い作業リスト（toil）」になりがちでしたが、チームが取る行動によって底上げ（raise the floor）が進み、脅威対応や長期の改善作業をこなすだけで、徐々に強い状態になることを目指している、と述べています。

### 5.3 Microsoft の cyber stack

ここまでの「基本」「エージェントガバナンス」「データのエクスポージャー管理」は、Microsoft の cyber stack に集約される、と Ron 氏は説明します。この stack は 7 月末に、Microsoft Perception とともに発表されたものです（Perception の綴りは音声認識の都合で確定できません）。

3 つの層は次のとおりです。

| 層 | 内容 |
| --- | --- |
| 最下層 | シグナル、センサー、アクチュエーター。Microsoft は非常に幅広い範囲を持つと説明 |
| 中間層 | 事業上のコンテキスト。最下層とこの層は、自社および他社（first / third party）のコネクターで実現する |
| 最上層 | エージェント |

最上層にエージェントを置く理由は、脆弱性が積み上がる一方で、攻撃者がマシンの速度で動くため、防御側もエージェントと自動化によってマシンの速度で動く必要があるから、と説明されています。Ignite では、AI 展開を加速するために必要な基盤的な統制の「積み残し」を処理するエージェントが紹介された、とも述べています。

### 5.4 対談：脅威動向と新しいリスク

ここから Terrell Cox 氏との対談になります。Cox 氏は Deputy CISO として、Microsoft 自身を守る最前線と、顧客がどう環境を守っているかを学ぶ立場の両方に関わっていると自己紹介しました。サイバーセキュリティで、自分が見た中で最も激しい時期だとも話しています。

最大のトレンドとして、Cox 氏は互いに重なり合う 2 つを挙げています。

**（1）AI が攻撃者の参入障壁を下げている**

- 「RTX framework」と聞き取れる、AI エージェント型のペネトレーションテスト用フレームワークがあり、自律的に攻撃を組み立てられる（名称は音声認識の都合で確定できません）
- オープンソースで公開されていたもので、元のソースは取り下げられたが、多数の派生版や類似のフレームワークがある。RTX は可能性の一例にすぎない
- 攻撃者は、これで攻撃を組み立てるだけでなく、公開リポジトリをスキャンして API キーを探している。見つけたキーは自分で使うか、売る。これによって、以前は厳しく制限されていたフロンティアモデルに、攻撃者が（売買市場を通じて）アクセスしている
- 若い人や学生など、経験の浅い者が、本来は十分な資源を持つ攻撃者にしかできなかった水準の攻撃を行えるようになった。Cox 氏は、国家レベルの攻撃者と、何も分かっていない人物のどちらの手にこの能力があるのが怖いか分からない、エージェントは暴走しうるので脅威の状況に予測不能さがある、と話しています

**（2）脆弱性を見つけて悪用することがはるかに容易になった**

攻撃者の手元の「材料」が増え、サイバー活動のペースが大きく上がっています。

Ron 氏から「注目されすぎているもの、足りないもの」を聞かれ、Cox 氏は次のように答えました。

- 注目されすぎているのは新手の攻撃（novel attacks）。実際の攻撃で見られるのは「まだ」で、数週間のうちには出るかもしれないとしつつ、今は攻撃者にとって手近な弱点（low-hanging fruit）が多く、新手の攻撃は不要
- 過小評価されているのは攻撃の速度。開始から終了まで 3 時間未満の例が複数あり、1 時間半の例も見た。従来のやり方とは全く違う対処が必要

### 5.5 対談：基本の徹底と「3 つの柱」

Ron 氏が、ほぼすべての攻撃に ID が関わっているのに基本が疎かになりがちだと指摘したのを受け、Cox 氏は「セキュリティの基本こそが我々を救っており、今も有効だ」と述べます。IT・セキュリティには常に消化しきれない負債の山があるため、基本を押さえつつ、限られた資源を最も重要なものに向けることが大事で、そのために継続的なエクスポージャー管理で優先順位を付ける、という考えです。

Microsoft 社内では、次の 3 つの柱で整理しているそうです（Cox 氏は「我々はマーケターではなくエンジニア」と前置きしています）。

| 柱 | 内容 |
| --- | --- |
| Less visible（見えにくくする） | AI に見つけられなければ悪用されない。L7 プロキシ、WAF、不要なインターネット公開の排除など |
| Less vulnerable（脆弱性を減らす） | コードスキャン、修正、パッチ適用。サプライチェーンセキュリティ（オープンソースとの協業など）にも大きく投資している |
| Less consequential（影響を小さくする） | 侵害を前提とし、侵入されても影響範囲（blast radius）を小さくする。ネットワークのセグメンテーション、ID 管理、有効期間の短いトークンなど |

Cox 氏は、これは新しい話ではなく、庭の手入れ（草むしりや剪定）のように常に続ける作業だとたとえています。

### 5.6 対談：チームの役割の変化とリスク許容度のすり合わせ

Ron 氏は、セキュリティ、IT、ソフトウェアの各チームが協力する必要が高まり、衝突も表面化していることを話題にします。Cox 氏は、AI 変革が長年存在してきた組織のサイロの境界を曖昧にし、くすぶっていた対立を表面化させていると述べます。電話会議で激しい口論や、遠回しな非難を見たこともあるそうですが、必要な議論を行うために「健全」だと考えています。

Cox 氏は、この問題を 2 つの観点で見ています。

1. **AI をどう守るか**：組織としてのリスク許容度を揃える。どこに余地や柔軟性を持たせ、何を譲れない条件（non-negotiables）にするか。部門ごとに見方が違うと速く動けない
2. **AI をセキュリティにどう使うか**：速度のための連携と、意思決定の速さ。対応時に必要な操作が IT 側や、データセキュリティ側にあることもあるため、事前に整理しておく

Ron 氏は、経営層が「これを実現したい」と言い、現場が「その要求は実際のリスクを高める」と考えても、それが上に伝わりにくい点を課題に挙げ、すり合わせの工夫を尋ねました。Cox 氏の答えは次のとおりです。

- **危機を無駄にしない**：インシデント、障害、予定より長引くプロジェクトなど、経営層の注目が集まる場面では、見えている真実を率直に伝える。覆されることがあっても、専門性を提供して判断を良くする意味がある
- 取締役会や上級幹部は、インシデントが起きるまで影響を実感しないことが多い。CISO 仲間と、「すぐ復旧できる小さなインシデントや障害が、人々を目覚めさせるにはちょうどいい」と笑い合った。最大の競合が侵害された、という出来事が「うちにも起こりうる」という話のきっかけになることもある
- **戦略的な投資の場面**：AI 変革の計画を立てるとき、安全性、ガバナンス、セキュリティ、可観測性（observability）を譲れない条件として最初から机に載せる。成功の定義に信頼・安全・ガバナンスを含めれば、「後付けで足すもの」ではなくなる

Ron 氏は、緊張の高い状況を認め、経営層が場を整えて、各自が真実を語れるようにすることが大事だと補足しました。Microsoft には「Speak the truth with care（思いやりを持って真実を語る）」という考え方がある、とも紹介しています。

Cox 氏は、変化の激しい環境に対応するために、組織文化への投資が重要だと話しました。

- Microsoft では、これは短距離走ではなくマラソンだと伝えている。エージェント型 AI による攻撃は頻度も規模も増えるため、資源を一気に投入して乗り切る方法は取らない
- 燃え尽き、病気、家族関係の悪化は避けたい。家族と健康が最優先であり、メンバーが支えられていると感じ、組織内に人としての信頼を築くことが大事
- 心理的安全性があれば、「いったん立ち止まって話し合おう」と言える

### 5.7 対談：変化の速さへの対処（コードスキャンの例）

Ron 氏が、リスクが絶えず変化することへの対処法を尋ねたのに対し、Cox 氏は Microsoft をケーススタディとして、コードスキャンを例にしました。Microsoft では、**マルチモデル、マルチエージェント、マルチハーネス**の方針を取っています。

- **マルチモデル**：モデルごとに得意・不得意がある。新しいモデルが出たらベンチマークとテストで強みを確認し、全体のフレームワークに組み込む。得意な作業には安価なモデル、馬力が必要な作業には高価なモデルを使う
- **マルチエージェント**：発見、検証、修正、エンジニアリングチームとのワークフローの調整といった役割別のエージェントを持つ。1 つのかごに卵を盛らない
- **マルチハーネス**：複数のハーネスを使う。その 1 つとして「M-dash」と聞こえるものがあり、Microsoft 内の多くのエンジニアリングチームの経験が反映されている（名称は音声認識の都合で確定できません）

複数のハーネスがあるのは、フロンティアなサイバーモデルが登場した当初、とにかく始める必要があり、実験の中で複数のハーネスが育ったためです。ただ、最新のモデルの能力が上がり、自社製ハーネスの一部が不要になりつつあります。Cox 氏は、**誇りを持って作ったものも手放せるようにしておく**必要があると述べ、これは新規投資にも、レガシーコードにも当てはまると話します。

レガシーについては、「修正とパッチを続けるか、コンポーネントやシステムを作り直すか」の転換点に来ているという観察が語られました。AI がコードを生成するのがうまくなったため、「絆創膏を貼るのに疲れた。再設計して新しく作った方が速くて安全だ」と考えるエンジニアが増えているそうです。Ron 氏も、顧客から同じような ROI の議論を聞いていると応じています。

### 5.8 対談：実験する文化と Microsoft 社内の学び

**SOC での実験**

Cox 氏は、SOC（セキュリティオペレーションセンター）を例に、実験を後押しする文化を説明します。「未来の SOC を再構想する」と最初から決めたのではなく、まず SOC のアナリストにツールと機能を渡し、「自分に合うものを試してみて」と任せたそうです。アナリストは自分に役立つエージェントを多数作り、それらがいつの間にか仕事のやり方になりました。現在は、チーム全体を動かせる、より包括的な仕組みに作り直しているところで、出発点は個人の自発的な創意だったとのことです。

> 注意：Cox 氏は、安全に実験できる環境、サンドボックス化、適切なガバナンスを整えたうえで行うことが前提だと付け加えています。

**Microsoft 社内の AI 導入で見直したセキュリティ姿勢**

Cox 氏は、見直した例を 2 つ挙げました。

1. 当初は、エージェントはオーナー（ユーザー）の ID を引き継いで、そのコンテキストで動くと考えていた。その後、それは良くないと分かり、現在は Agent ID に注力している。エージェントに固有の ID が無いと、キルスイッチも、説明責任や意図した用途の追跡もできないため
2. インベントリ（棚卸し）と発見可能性の重要性。Agent 365 の発端は、Microsoft 自身がこの問題を抱えていたことにある。エージェントが至るところで生まれ、社内では 100 万を超えているという。対談の中で「実際は 150 万に近いと思う」という補足も入っている（どちらの発言かは文面から確定できません）。この数は増え続けているとのこと

Cox 氏は、「見えないものは守れない」と述べます。Microsoft は Agent 365 を可観測性とポリシーの両方に使っています。ポリシーの例として、条件付きアクセス（conditional access）、デバイス構成ポリシーなどが挙げられ（話の一部は聞き取りが不明瞭です）、エージェントが暴走したときに封じ込めや停止に使える手段になる、と説明されています。

### 5.9 対談：顧客へのアドバイス（今すぐ決めておくべきこと）

Ron 氏が「先送りせず、今すぐ判断すべきセキュリティ上の決定は何か」と尋ね、Cox 氏は次の 3 点を答えました。

**（1）AI の利用状況の棚卸し：AI の恩赦（amnesty）プログラム**

かつての shadow IT に対し、今は shadow AI です。ある顧客が、30 日か 60 日といった期間を決め、「あなたの AI を持ってきてください」と呼びかける AI のための恩赦プログラムを作った、という話です。お咎めも評価判断もない「裁かない領域」としたもので、セキュリティ部門や IT 部門が、どのような用途でどんな問題を解決しているかを理解する狙いです。そのうえで、許容できるリスクかどうかを判断し、事業価値は高いのにリスクが心配なものは、解決策を一緒に考えてそのユーザーの課題を解決する、という流れです。Cox 氏は、この話を複数の顧客から聞いたそうです。

**（2）ゼロから考える顧客と、既存の知見を土台にする顧客**

- 「AI やエージェントはまったく別物」と捉え、エージェント面（agentic surface）の保護をゼロから考え始める顧客
- 「インシデント対応のプレイブックもプロセスもあり、セキュリティの基本も守っている」と考える顧客

Cox 氏の観察では、既存のリスク管理、事業の優先順位、クラウンジュエル、攻撃グラフなどに立脚する後者の顧客のほうが、**速く進んでいます**。最適化の対象は速度と規模であり、車輪を再発明していないからです。

**（3）事前に決めておくべき判断**

サイバー攻撃を受けたときを想定し、事前に決められることを決めておく、という助言です。誰が会議に参加して判断するのか、必要な承認レベルは何か、環境へのインターネット接続を遮断する方法を知っているか、それを判断するのは誰か、といった点が挙げられました。最悪のケースですが、緊迫した場面ではなく今のうちに決めるべき判断だ、と述べています。

### 5.10 まとめの案内：参照先

Ron 氏は、最後に次の 4 つを案内しました。

| 参照先 | 内容 |
| --- | --- |
| Secure Future Initiative レポート | CISO オフィスが公開。最新版は今年 7 月のもの。Microsoft 自身が自らを守り、AI に備えてきた過程と、社内で調整しているリスクのトレードオフが含まれ、ベストプラクティスも共有されている |
| Secure Now（`aka.ms/securenow`） | 脅威ガイダンスと AI 準備の推奨事項を提供するサイト（下記） |

Secure Now は、顧客から多い「新しい脅威活動について Microsoft のガイダンスは何か」「AI に備えてどのイニシアチブを実施すべきか」という悩みに応えるサイトで、2 つの要素があります。

- **新たな脅威**：脅威の状況に関する Microsoft の一般的な助言。Entra ID を持つ組織内の誰でもアクセスして、最新のガイダンスを確認し、対策に進める。各推奨事項から既存のポータルへのディープリンクがあり、特定の対策に必要なライセンス要件も確認できる
- **AI イニシアチブ**：過去 5 年分の CVE と脅威活動（Microsoft Threat Intelligence）、Secure Future Initiative と CISO オフィスの経験を踏まえて作った推奨事項を、ドメイン別に整理したもの。同じ形式で、推奨事項、推奨アクション、ディープリンクが並ぶ

これらの推奨事項は Microsoft Perception にも組み込まれる予定で、組み込まれた場合は、Perception がテナントの状況と導入済みの統制を把握しているため、環境に合わせて調整されたものになる、と説明されています。

> 補足：このセッションでは質疑応答の時間は設けられず、最後にアンケートへの回答が依頼されただけでした（質問があれば連絡してほしい、とのことです）。

## 7. 注意点・発表者の気付き

- **エージェントに、ユーザー（オーナー）の ID をそのまま使わせない**：Microsoft は当初そう想定していたが、固有の ID がないとキルスイッチも説明責任の追跡もできないと分かり、Agent ID に注力するようになった
- **「承認」の安易なクリック**が、アプリ権限の過大さや過剰共有につながる
- **攻撃は速い**：開始から終了まで 3 時間未満（最短で 1 時間半の例）があり、従来型の対処では間に合わない。新手の攻撃より、手近な弱点を狙われる状況を意識する
- **API キーの流出**：公開リポジトリが走査され、見つかったキーが売買され、フロンティアモデルへのアクセスに使われている
- **自分で作ったものに執着しない**：モデルの進化により、自社製ハーネスの一部が不要になっている
- **実験の自由には前提がある**：サンドボックス化など、安全な環境と適切なガバナンスが必要
- **燃え尽きを防ぐ**：長期戦を前提に、家族と健康を優先し、心理的安全性を築く
- **事前に決める**：インシデント時に誰が何を決めるか、承認レベル、インターネット遮断の判断など

## 8. 利用者にとっての利点

発表で語られた利点・成果は次のとおりです。具体的な数値による効果測定は、発表では示されていません。

- 300 人を超える FastTrack エンジニアによる、追加費用無しの支援（Microsoft の推奨事項の実装支援）
- Secure Now で、Entra ID を持つ組織内の誰もが最新の脅威ガイダンスと、対策へのディープリンク、必要なライセンス要件を確認できる
- 過去 5 年分の CVE と脅威活動に基づく、AI 準備のための推奨事項がドメイン別に整理されている

## 9. まとめ

このセッションは、AI の機会とリスクは同じ能力から生まれるので、イノベーションと安全性を二者択一にしない、という前提で始まりました。経営層と IT・セキュリティが交わすべき会話として、基本の徹底、エージェントの可視性・所有者・権限、データと ID・アプリ権限の管理、継続的な脅威エクスポージャー管理の 4 つが示されました。

Terrell Cox 氏との対談では、AI による攻撃の参入障壁の低下と攻撃の速さ、Less visible / Less vulnerable / Less consequential の 3 つの柱、リスク許容度を組織で揃えて成功の定義に安全性を含めること、変化に備えて作ったものでも手放せる姿勢と実験の文化、が語られました。Microsoft 社内では、Agent ID と Agent 365 による可視化・ポリシー適用に至った経緯も共有されています。

次の一歩として、Secure Future Initiative レポート、Secure Now（`aka.ms/securenow`）、FastTrack、Microsoft Perception の 4 つの参照先が案内されました。
