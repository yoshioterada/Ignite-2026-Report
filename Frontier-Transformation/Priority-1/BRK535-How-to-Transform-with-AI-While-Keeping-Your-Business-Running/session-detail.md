# BRK535 How to Transform with AI While Keeping Your Business Running

## 1. はじめに

このセッションは、「事業を止めずに AI で変革する」にはどう進めればよいのかを、Microsoft 自身の取り組み（Customer Zero）の事例で語ったものです。登壇者は Microsoft の Tal Saraf 氏の 1 人で、約 21 分の発表のあと、質疑応答が行われました。

題材は、Microsoft の営業担当者（seller）が使う商談・見積もりの仕組みを AI エージェント（Sales Agent）で作り替えた事例です。そこから、AI 変革の 3 つの原則と、実際に得た 4 つの教訓が紹介されています。結論は、**「今の事業を回し続けること」と「変革すること」はどちらかを選ぶものではなく、両方を同時に行う**という考え方です。

## 5. 発表内容の詳細

### 5.1 運用と変革の緊張関係

Microsoft は数十年続く会社であり、決算を締める、システムの利用者が日々使い続けられるようにする、信頼性・品質・セキュリティを守る、といった運用の規律を持っています。これは「オプションではない」と Tal 氏は強調しています。同時に、変革のスピードで実験を進める流れがあります。ここでは、既存のプロセスをそのまま自動化するのではなく、プロセスを作り直すことも含めました。そのまま自動化しても、うまくいかないことが多いためです。

### 5.2 3 つの原則

Microsoft 社内の取り組みを導いた原則は 3 つです。

| 原則 | 説明（発表での内容） |
| ---- | ---- |
| 1. ビジネス成果から始める | 「AI は変革的だ」と言うだけでは足りない。何をしたいのか。多くのエージェントを作ることや、何千人もがエージェントを使うことは、ビジネス成果ではない。中核となる指標は何か、ビジネスがその基準値（ベースライン）をどう測っているか、その領域への投資で進捗をどう証明するかを決める |
| 2. プロセスを見直す | プロセスやシステムは、長い年月の中で正当な理由があって作られてきた。ただ、それが今後も同じ目的に役立つとは限らない |
| 3. デモではなく、本番を作る | バイブコーディングは楽しく、Tal 氏自身も夜や週末にやっているが、それはデモであって、本番向けの構築ではない。本番では、規模、セキュリティ、パフォーマンス、サポートが必要で、何が起きても動き続けることが求められる |

Tal 氏は、これらは LinkedIn で読んだような一般論に聞こえるかもしれないとしつつ、測定でき、価値を示せる原則だと述べています。

#### 「時間の節約」だけでは足りない

営業の例で、Tal 氏は「時間の節約」を成果とすることに距離を置いています。プロセスの一部を自動化して時間が減っても、それが測定でき証明できる成果につながるとは限らないからです。

### 5.3 事例：営業担当者のための商談支援

#### 背景

Microsoft の商用ビジネスの中核は商談（deal）です。そこで、営業担当者が商談を進めるためのツールをどう作るかが問われました。担当者は、**20 のシステム**を使っており、それらは **80 のデータソース**からデータを引いています。Tal 氏が気にしたのは、数字そのものよりも、担当者がシステム間を行き来し、自分でデータソースから情報を集め、時には同じ質問に何度も答えなければならない点です。担当者は意図どおりにツールを使っていますが、意図どおりに使えていることが、今後も望ましい方法、効率的で有用な方法とは限らない、と説明されました。

また、Microsoft には大企業の顧客、中堅・中小の顧客、広いパートナーエコシステムがあり、担当者はそのすべてに対応します。どのパートナーがその顧客と関係を持っているか、提案する deal book にどの特典を組み合わせるのが最適かを見たい、という要望も背景にあります。

#### 紹介ビデオの内容

Sales Agent を紹介するビデオが上映されました。音声の不具合で一度やり直しています。ビデオのナレーションは次のとおりです。

* エンタープライズの商談は、価格、ライセンス、承認が多くのシステムとチームにまたがり、非常に複雑
* Microsoft の調査では、営業担当者は時間の約 **70%** を、顧客から離れて、システムの操作や運用作業に費やしていた
* 「deal-making and sales agent」が、Microsoft 365 Copilot の中で、適切なコンテキストとインテリジェンスを提供する
* 担当者が商談について尋ねると、Sales Agent が複数のシステムから主要な商談情報と重要な日付を 1 つのビューにまとめる
* 次に、シンプルな更新から成長シナリオまで、価格付きで顧客に提示できる商談オプションを作る
* 顧客が選ぶと、Sales Agent が見積もりを下書きする。担当者は Copilot を離れずに、確認、調整、承認依頼の送信ができる
* 引き継ぎと繰り返し作業が減り、顧客と過ごす時間が増える

Tal 氏は、これは実際に Microsoft 社内で稼働している仕組みだと述べています。同じプロセスを速くしただけでなく、既存プロセスのすべてのステップの自動化の機会を見て、体験を上から下まで、エンドツーエンドで考え直したと説明しています。

#### 成果

まだ始まったばかりで、意味のある結果が出始めた段階だとして、次の数値が示されました。

* 内部データで、商談のスピード（deal velocity）が **9% 向上**
* 9 月の、Sales Agent が商談作成を支援した場合の契約更新の平均規模は、エージェントを使っていない比較対象の商談（中堅・中小企業の顧客）より **20% 大きかった**
* Tal 氏は、時間の節約ではなく、商談のスピード、成約までの時間の改善、そして大きな商談が見られるようになったことを重視している

Tal 氏は、この比較は Microsoft 内の実運用で、導入前後を実際に見られたものだと述べています。さらに、システム間を移動する時間をなくすことのほうが、時間が戻ってくること以上に面白いと述べ、これが既存の技術を捨てて置き換える（rip and replace）ことなく進められた点も強調しました。

> 補足：発表では、9% と 20% が同じ期間・同じ母集団の指標かどうかは説明されていません。数値は発言のとおりに記載しています。

#### 並行運用による導入

Microsoft は営業活動を止めるとは言わず、担当者に既存のツールとプロセスを捨てて新しいエージェントに移るよう強制もしませんでした。新旧の両方を並行して動かし、今のやり方で慣れている人はそのまま続けられるようにしたうえで、新しいエージェントのほうが明らかに良いと感じて、自分から移りたくなるように作りました。新しい場所に行かせるのではなく、担当者がすでに日々過ごしている場所にツールを置いています（ビデオでは Microsoft 365 Copilot の中で提供されています）。強制ではなく、採用を勝ち取ることができた、と説明しています。

### 5.4 事例から得た学び

Tal 氏は、ここまでが 1 回で終わる話ではないと述べ、Sales Agent も完成ではなく、継続的な旅の途中だとしています。リリースは始まりに過ぎず、学んで調整し、見直してきたと述べ、その中には謙虚にならざるを得ない教訓もあったそうです。

#### 営業担当者と一緒に作る：リングとフロンティア

deal book の設計では、営業担当者をチームに迎えて共同で進めました。Microsoft のソフトウェアの展開と同様に、リング（rings）とフロンティア（frontier）という考え方を使います。frontier ユーザーは、早い段階から積極的にフィードバックをくれる人たちで、そのフィードバックが今後の投資とトリアージ、さらにロードマップに反映されます。

#### 最初のリリースでは柔軟性が足りなかった

deal book を作るだけでは足りませんでした。担当者は、商談を調整し、シナリオを試し、パートナーと商談を進める余地を求めていて、すべての判断が自動化されることは望んでいませんでした。最初に出荷した体験は、その柔軟性が全く足りず、このフィードバックでエージェントを改善し、今も改善を続けています。

#### 1 つのステップだけではない

対象のプロセスには 20 以上のステップがあり得ます。それぞれのステップは、新しいオファー、新しい SKU、新しい商用モデルなどで、ツールを作る必要があった正当な理由があります。すでに行った約束（販売したライセンスなど）は守らなければならないため、それらを実行し続けながら、AI による柔軟性を取り入れています。この変革は、既存のシステムを人々がどう使っているかを学び、顧客の課題を理解し、担当者がシステム間で費やす手間（Tal 氏の言う「seller toil」）をなくす機会を探すことでした。

Tal 氏は、これを「一度で終わるもの」ではなく、**ヒルクライミング（hill climbing）**だと表現しています。発表者は、基調講演では言わなかったがこの言葉を使うのが好きな人物がいると話しています（人名は音声認識の都合で確定できません）。

#### 4 つの教訓の整理

| 教訓 | 内容 |
| ---- | ---- |
| 1. ビジネスが本当に気にすることを測る | AI そのものや、作ったエージェントの数、1,000 人・10,000 人・100,000 人が使ったことは重要ではない。成果物、ビジネスにとって重要な指標（deal velocity、成長、収益の伸びなど）と、比較するベースラインを決める |
| 2. 壊れたプロセスを自動化しない | プロセスは正当な理由があって今の形になっていることも多いので「壊れている」とは言いたくない。ただ、直すなら、プロセス全体をエンドツーエンドで考え直す。ステップを飛ばせないか、取り除けないか。事前承認済みなら、再承認は不要で、最良のステップは「ステップなし」かもしれない |
| 3. 利用者と一緒に作り、新旧を並行して動かす | 象牙の塔で考えるのではなく、実際にその技術を使う人が誰で、どんな課題があるかを知る。新旧を同時に動かして、信頼と採用を得る |
| 4. リリースは始まりにすぎない | 立ち上げをゴールとは見なさず、所有し、測定し、学んだことを適用して改善し続ける |

### 5.5 まとめ（本編）

Tal 氏は、「今あるもの」と「事業が求める明日の姿」のどちらかを選ぶ話ではなく、進めながら学ぶことだと述べました。AI でできることは、今年の初め、昨年、一昨年とは大きく違い、非常に速く進んでいます。それは素晴らしいことだが、これまで行ってきた約束や投資してきた領域を捨ててよいわけではなく、変革することと運用し続けることの両方を行う、というのが結論です。

また、Microsoft が自社で Microsoft 製品を使う Customer Zero のユースケースを集めたブログ記事「Inside Track」を、QR コードで案内しています。今回の事例のほか、多くの事例が読めるとのことです。

### 5.6 Q&A

**Q1. ビジネス側は売上（トップライン）を、技術側は技術的負債などを重視し、優先順位づけで綱引きになる。どう解決するか。**
誰もが直面する課題で、「両方やる」ことのバランスだと答えています。会社によっては、KTLO（keep the lights on、動かし続けるために必要な作業）に割く量を決められた例もあり、ステークホルダーと「KTLO の妥当な割合」で合意して、それを減らしながら、ビジネスを変える作業の時間を増やしていく、という方法です。Tal 氏は、変革だけに集中できる会社や技術には出会ったことがなく、運用も同時に維持する必要があったと述べています。今の期間（シーズン、年、四半期、半期）に必要なバランスを、ステークホルダー、顧客、パートナーと話し合い、時間をかけて調整していくことになります。

**Q2. AI 導入を支援する PMO を担当している。バックログに約 80 件のプロジェクトがあり、リードタイムは数百日だと思う。Copilot などを使えば効率が上がり、リードタイムを X% 下げ、継続的に改善できるはずだが、それは適切な指標か。**
Tal 氏は、誰もが持つ願望だと受け止めたうえで、次の点を述べました。

* エンジニアリングが不要な作業や、自動化できる作業を見つける。営業の toil のように、エンジニアリングの toil もある。ソフトウェアの更新対応のような、付加価値は低いが必ずやるべき作業をできるだけ自動化し、ビジネスを変える作業に使う時間を増やしたい
* エンジニアリング側で、規模の経済や効率化が実際に見えている
* 気にしているのは「ポケット」、つまり、誰かが特定のハーネスやモデル、フローで成果を出しても、それを組織全体に一貫して適用できないことである。全員の底上げ（raise all boats）が課題であり、各チームに知見を共有してもらいたい
* 基調講演で Satya 氏が語ったように、情報へのアクセスが民主化（commoditize）されており、自分のデータとバックログで、自分のナレッジグラフ、いわば自分の会社の IQ（company IQ）を作れる

> 補足：「リードタイムの低下率」が適切な指標かどうかについて、Tal 氏は明確に「はい／いいえ」とは答えていません。願望としては同意し、上記の観点から答えています。

この 2 件のあと、発表者は追加の質問を募りましたが、トランスクリプト上は追加の質問が確認できません。最後に、セッションのフィードバック用 QR コードが案内されています。

## 6. デモ・手順

このセッションでは、画面を使ったライブデモは行われていません（スライドと口頭の説明、および上映されたビデオが中心です）。

上映されたビデオ（Sales Agent の紹介）で紹介された流れは、5.3 に記載したとおりで、次の順序です。

1. 担当者が Microsoft 365 Copilot の中で商談について尋ねる
2. Sales Agent が複数のシステムから主要な商談情報と日付を 1 つのビューに集める
3. シンプルな更新から成長シナリオまで、価格付きの商談オプションを作る
4. 顧客が選んだ内容で見積もりを下書きする
5. 担当者が Copilot を離れずに、見直し、調整して、承認に送る

> 注意：これは紹介ビデオのナレーションにもとづく概要です。画面の操作の細部は、音声からは確認できません。

## 7. 注意点・発表者の気付き

* **指標は AI の利用量ではなく、ビジネスの成果で**：エージェントの数や利用者数は成果ではないとされています。
* **時間の節約だけを成果にしない**：プロセスの一部の自動化が、測定できる成果につながるとは限りません。
* **デモと本番は別物**：バイブコーディングはデモであり、本番には、規模、セキュリティ、パフォーマンス、サポートが要ります。
* **最初のリリースは柔軟性が足りなかった**：全判断の自動化ではなく、調整やシナリオ検証の余地が担当者に求められていました。なお発表では、リリース後に得た教訓の中に「謙虚にならざるを得ないもの」があったとも語られています。
* **既存のプロセスをいきなり捨てない**：既存のツールとの並行運用で、信頼と採用を得ました。「rip and replace」ができる状況ではなかった、とも述べられています。
* **組織内のポケット化**：特定のチームだけで成果が出る状況を、組織全体に広げられないことを最も懸念しています。

## 8. 利用者にとっての利点

発表で語られた成果は、Microsoft 自身の営業部門（Customer Zero）での結果です。

* 商談のスピード（deal velocity）が内部データで 9% 向上
* 9 月の契約更新の平均規模は、Sales Agent を使った場合に、比較対象より 20% 大きかった（中堅・中小企業の顧客）
* 時間の節約だけでなく、商談スピードや成約までの時間の改善、より大きな商談という成果が見られた
* 紹介ビデオでは、引き継ぎと繰り返し作業が減り、顧客と過ごす時間が増えると説明されています（調査では、担当者は時間の約 70% を顧客から離れた作業に使っていたとされています）
* 顧客側にとっても、担当者が更新の際に可能な特典をまとめやすくなり、承認済みのものを再承認のために戻らずに済む、という説明がありました

> 注意：具体的な外部顧客の導入事例や、コスト削減額などは、このセッションでは語られていません。

## 9. まとめ

Tal Saraf 氏は、事業を回し続けながら AI で変革するための考え方を、Microsoft の営業部門で作った Sales Agent の事例で示しました。原則は、ビジネス成果から始める、プロセスを見直す、デモではなく本番を作る、の 3 つです。

事例から得た教訓は、ビジネスが気にする指標とベースラインを測る、壊れたプロセスを自動化せずエンドツーエンドで見直す、利用者と一緒に作って新旧を並行運用する、リリースは始まりにすぎない、の 4 つです。商談スピードの 9% 向上と、契約更新の平均規模が比較対象より 20% 大きかったという結果も紹介されました。「運用と変革の両方を同時にやる」ことが、このセッション全体の結論です。
