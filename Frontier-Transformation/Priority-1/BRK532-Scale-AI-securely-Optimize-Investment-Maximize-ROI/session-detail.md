# BRK532 Scale AI securely. Optimize Investment. Maximize ROI.

## 1. はじめに

このセッションは、AI エージェントが組織内で増えていく中で、**安全に管理し、コストを制御し、投資に見合う価値を確認する**にはどうすればよいか、を 3 つのデモで見せる 45 分のブレークアウトです。対象は、中小企業（SME）やその IT・セキュリティ担当者、そしてパートナー企業です。

進行役の Sharon Schoenborn 氏が、架空の製造業 Fabrikam の CEO、CISO、CFO/CIO という 3 つの立場を順に演じ、それぞれの立場の課題を別の登壇者がデモで解決していきます。扱うのは、24 時間動く Autopilot、エージェントの可視化と防御を担う Agent 365 と Microsoft Perception、エージェントのコストと価値を管理する Agent 365 の FinOps 機能です。

画面を使ったデモが中心のセッションです。ただし、録音から分かるのは語られた範囲の操作だけなので、画面の細部は確認できません。

## 3. 何に関する発表か

背景として、Ralph 氏は小規模・中規模の企業を取り巻く状況を次のように説明しています。

- この種の顧客は、自身が担当する市場で従業員（労働人口）の 90% 以上、GDP の 50% 程度を占める
- 技術を大企業と同じ速度・同じ品質で小企業も使えるのは、自身の長い経験の中でもおそらく今回が初めて
- AI は、あらゆる企業のロードマップに載っている
- 導入の状況を見ると、66% の企業がすでに成果を得ている

Sharon 氏は、AI への投資が前年比 47% 増加していること、また BCG の調査によると AI への支出の 80% が IT 部門の外から出ていることを紹介しました。この点から、環境で何が起きているかを見渡す observability（可観測性）を高めることの必要性が語られました。

## 6. デモ・手順

このセッションには 3 つのデモがあります。以下は、登壇者が語った内容と画面の説明の範囲で書いています。画面上のボタン配置や表示項目の細部は、音声からは確認できません。

### 6.1 デモ 1：Autopilot（Omar Shahine 氏）

CEO の Sharon 氏が「部品の出荷遅れの報告を受けた」という設定で、Omar 氏が Autopilot の Compass（CEO 用の Autopilot）を見せました。

1. 1 か月前に設定した Compass から、「parts are slipping（部品が遅れている）」というメッセージが届いている
2. Compass がなぜ把握できたのか。Compass には目標を教えてあり、その 1 つが「重要顧客への納期を守ること」。Compass はすでに、承認を求める判断事項を用意している
3. 「Compass にタスクの一覧を渡すのではなく、目標を渡す。目標を続けるのに必要なことは Compass が把握する」と説明
4. 提示された提案を承認する。これで Compass に、仕事を続ける自律性を与えたことになる
5. ノート PC の電源を切っていても動くか、という質問に対し、動作する。Autopilot はクラウドで動き、自分の ID を持ち、24 時間動く
6. Compass は毎朝 6 時にメールを送る。この例では、準備状況のチェックを実行し、対応が必要な点をいくつか指摘していた
7. Compass は Teams のチャンネルで同僚のように動く。発売スレッドを Compass が指摘している。@ メンションで Compass の名前を指定して返信し、作業を進めるよう依頼する
8. Compass は、ドキュメントの作成と通話の設定を行った
9. Compass は、グループチャットに同僚の Elena がいないことに気づき、プロジェクトが Elena の入力なしで進められるものと仮定せずに指摘した

続いて、Dayton のプラントマネージャーである Marcus 氏が自分用の Autopilot を作る流れです。

1. 組織内の誰でも初めて Autopilot を作るときと同じ画面で、「Next」を選ぶ
2. 名前を Finch にする（好きな名前を付けられる）。色や見た目も変えられる
3. Finch は Marcus に報告する（reports to）関係であることが示される。社員と同じように社内アドレス帳に載り、メールアドレスも持つ
4. Finch の目標は、Marcus 自身の仕事（工場に関すること）に基づいて設定される。CEO のテンプレートから始まるのではない。「Continue」を選ぶ
5. Finch が Marcus の文脈を得るため、**Work IQ** を使って、メール、カレンダー、仕事のパターンを見る
6. Finch が Marcus に自己紹介し、仕事を進めるための提案を示す。Marcus が Fabrikam で何をしているか、誰と働いているかを把握していて、すぐに実行できる提案が 1 つ出る

### 6.2 デモ 2：Agent 365 と Microsoft Perception（Alym Rayani 氏）

CISO の Sharon 氏が、エージェントの可視化と、少人数でのセキュリティ運用を課題としたデモです。

**Agent 365 でのシャドー AI の発見と隔離**

1. Microsoft 365 管理センターの Agent 365 を開く。マルチテナントのビューで「Agents」を選ぶと、全テナントのエージェントが見える（5.4 参照）
2. Fabrikam の話に戻り、**Agent registry card** を選ぶ。組織内のエージェントの一覧（エージェントのディレクトリ）が表示される
3. 会場に「組織のどこかでシャドー AI が起きていると分かっている人はどれくらいいるか」と問いかけ、Alym 氏は「かなり多い」と受けた。**shadow AI** の画面で、組織内で起きていると考えられるものの一覧を見る
4. Microsoft 製とは限らず、OpenClaw や ChatGPT のようなものも、従業員のデバイス上で動くエージェントとして検出できる。例として、エンジニアが入れた **ChatGPT デスクトップエージェント** を選ぶ
5. 「Instances」を見ると、同じエージェントが **11 インスタンス、8 台のデバイス** で動いている
6. そのうち 1 台のデスクトップを選ぶと、**dynamic agent risk** が表示される。「Security」タブで、このエージェントは **very high risk** であり、セキュリティチームが対応中のケースが関連付けられていることが分かる。IT 側でもセキュリティ観点の状況が見える
7. 「Access」で、エージェントのアクセスを制限できる。**Intune を使ってエージェントの動作をブロックしたり、デバイスでの実行を防いだりもできる**が、エンジニアの作業を止めたくないので、ここでは**隔離（isolate）**を選ぶ
8. 隔離は、エージェントをコンテナで包み、できることを制限する。たとえばデバイスにインストールされたものやファイルシステムに到達できなくなり、被害範囲（blast radius）が抑えられる
9. 「Apply Policy」を選んで完了。すべて Agent 365 内で実施した

**Microsoft Perception での運用の自動化**

1. Microsoft Perception のコンソールを開く。セキュリティ担当の視点で、**estate snapshot** を見る。Agent 365 で IT チームが見ていたものと同じ情報
2. **15 件の高リスクエージェント**がある。Perception は推奨事項と、エージェントに実行させる行動計画を示す。そこにある **playbook** は、セキュリティ運用を行うエージェントのチーム
3. playbook の左側には推奨事項の一覧がある（文字が小さいと説明）。高リスクのエージェントがあるので、**Entra Global Secure Access** を有効にして、アクセスを制限し、脅威をブロックすべきだという内容。ネットワーク上のエージェントだけでなく、ローカルのエージェントも対象
4. 「Start Session」を選ぶと、playbook が実行され、Entra Global Secure Access などの保護が適用される。「Submit」を選ぶと、実行した操作のログが残り、完了
5. Alym 氏は、human in the loop の考え方に触れ、この例では人間が承認するだけでよいと説明している。操作はすべて追跡できる
6. 次に、ダッシュボードの下部に表示される、**コンテナ機能がデプロイされているデバイス**を見る。この機能は Windows の一部で、Mac と Linux でも動作する
7. 同じように playbook と推奨事項が表示される。内容は、高リスクのエージェントだけでなく、エージェントが動作するすべてのローカルマシンでコンテナを有効にすべき、というもの。「Start Session」でエージェントがコンテナを有効にする作業を実行し、「Submit」で監査ログが残る。結果のレポートも確認できる

### 6.3 デモ 3：コストと価値の管理（Ryan Jones 氏）

CFO / CIO の Sharon 氏が、エージェントへの投資とそこから得られる価値を知りたい、という設定です。Ryan 氏は、デモ 2 の続きとして Microsoft 管理センターの Agent 365 から始めました。

**コスト・価値の確認と Action Center**

1. Agent 365 に、エージェントの月ごとのコスト、傾向、見通し、コストに対して最も見返りの大きいエージェントが、他の情報と並んで表示される
2. 新しい **Action Center** は、管理者が行うべき最も重要なことを示す。よくあるのは、同じことをするエージェントが複数できる問題（Ryan 氏は「agent Twinkies」と呼んだ）
3. 詳細を見て、**what-if シナリオ**を実行する。統合しない場合と統合した場合を比べ、統合後は費用に対してより多くの価値が得られることを、実行前に確認できる
4. 例として、Proposal Builder 型のエージェントが 2 つある。Sales Pitch Writer と RFP Response Helper。エージェントを削除するのではなく、**所有者に通知**して「2 つのエージェントを連携できないか話し合ってほしい」と送る。継続的な改善と効率化につなげる意図
5. **agent registry** は、Microsoft のプラットフォームで作られたものもサードパーティのものも一覧し、リスクレベルをコストデータの隣に表示する。セキュリティ、ガバナンス、ビジネス価値のいずれの見方でも、1 つの画面で確認できる

**spending policy の作成**

1. 例として、パイロット中の **claims processing agent** を選ぶ。コストは月 100 ドル未満だが、これから展開を広げるため、予算を増やす必要がある
2. spending policy を作成して名前を付ける。今週の別のデモでは identity ベースの spending policy だったが、ここでは claims processing agent に特化したもの
3. 月の予算を **2,000 ドル**に設定する。Copilot credits ではなくドル建て。Ryan 氏は「Copilot credits で予算を組む顧客はまだ見つかっていない」という趣旨で説明している
4. 予算に近づいたときに通知が来る**アラート**を設定する
5. 誰が支払うか（**chargeback**）を設定する。**Azure サブスクリプション**を選ぶか、テナントの**前払いの Copilot capacity packs** から引き落とす。Azure サブスクリプションを選ぶと、そのエージェントの消費分がそのサブスクリプションに自動で課金される。Fabrikam は Azure を多く使い、すでにサブスクリプション単位の chargeback を設定済みなので、そこにそのままつながる
6. IT チームが小さく、すべてのエージェントや部署に対応できないため、**設定を事業部門のリーダーに委任**できる。パートナー営業組織の policy group で、Adele をオーナー（partner sales group の支出管理の責任者）に設定し、複数の delegate も設定できる。Nestor は "delegator"（非常に高い権限のユーザー）として設定される

**Agent 365 Business Analytics**

1. 業務部門の担当者は管理センターにログインするのを怖がる可能性があるため、**部門向けに作った専用ビュー**である、と説明。組織、予算、ユーザー、コストの要因（cost drivers）を、製品やサービスごとに自由に分析できる
2. Cowork の cost drivers を見て、製品別（Cowork など）、モデル別の支出の内訳を見る。Microsoft はマルチモデルである、という説明。すべてを 1 つの Sankey 図にまとめると、各製品がどのモデルにつながるかが分かる
3. 現場が知りたいのは、製品やモデルの詳細より、AI で人々が何をしているか。そのために、Copilot または Agent 365 の observability パイプラインを流れる情報を取り、**業界横断で 6,000 種類のタスクからなる labor taxonomy** に分類する。分類したタスクごとに、支出と効果の両方を集計する
4. 例として、R&D の下の experimental design and analysis、その下の hypothesis testing、さらにその下の statistical analysis plan。4 回のセッションで、クレジットに **180 ドル**使い、**470 ドル**相当の価値（効果）が得られた。価値は、タスクにかかる時間とコストから、"good old P times Q" で計算する
5. 将来の見通しとして、research 部門を選ぶ。予算は **15,000 ドル**で、月末時点の見込みコストは約 **9,300 ドル**。予算に余裕があるので、「より多くのユーザーに展開したらどうなるか」という what-if を実行できる。what-if の変更は、最終的に spending policy に反映する
6. 事業部門のリーダーとして、どのユーザーがどの製品にアクセスでき、どれだけ消費できるかを設定できる。Ryan 氏は、ここで操作に少し手間取ったと発言している

## 7. 注意点・発表者の気付き

- **Autopilot は目標を渡して動かす**もので、タスクの一覧を渡すものではありません。人が承認することで自律性を与えるという流れが、デモで示されました
- Compass は、同僚 Elena がチャットにいないことに気づき、プロジェクトを進めてよいと仮定しませんでした。Omar 氏はこれを「ちょっとした気配り」と述べています
- 脅威への対応では、エージェントを止めるのではなく、**隔離（コンテナ化）して被害範囲を限定する**という選択肢が示されました。エンジニアの作業を止めずに、リスクを下げるための方法です
- Alym 氏は、Autopilot は安全に設計されているものの、24 時間動く自律的なエージェントは多数あると述べています。それが Microsoft Perception を導入した理由の 1 つです
- Perception の playbook では、人間が承認する human in the loop が前提です。全作業の記録は監査ログとして残ります
- 予算は **Copilot credits ではなくドルで**設定する（Ryan 氏の説明）
- マルチテナントでのポリシー一括適用は**近日対応予定**で、現時点では提供されていません
- 前提として、Fabrikam は架空の会社で、デモは Fabrikam の想定に沿ったものです

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **少人数の IT・セキュリティチームで運用できる**：Autopilot が 24 時間動き、Microsoft Perception の playbook が運用を担う。Sharon 氏も「チームのスケールを得られる」と総括しています
- **エージェントの可視化**：Microsoft 製かどうかを問わず、従業員のデバイス上のエージェントまで見つけられる。リスクの高いエージェントを、業務を止めずに隔離できる
- **コストの予測と制御**：エージェント単位の予算とアラート、Azure サブスクリプションなどへの chargeback、部門リーダーへの委任により、支出を予測しやすく、所有者を明確にできる
- **価値の把握**：コストと価値を並べて見られる。タスク分類に基づく費用と効果（例：180 ドルに対して 470 ドル）を確認できる
- **無駄の削減**：重複したエージェントを what-if で比べてから、所有者に連絡して統合を検討できる

## 9. まとめ

このセッションは、AI エージェントが増える状況で、**安全性、コスト、価値**の 3 点を管理する方法を、Fabrikam という架空の会社の CEO、CISO、CFO/CIO の立場から、3 つのデモで示しました。Autopilot は目標を基に 24 時間動いて作業を進め、Agent 365 と Microsoft Perception はエージェントを見つけ、隔離し、運用を自動化します。Agent 365 のコスト管理機能は、spending policy、chargeback、部門向けの分析で、投資と価値を結びつけます。

Ralph 氏は、中小企業に向けて、すべてのモデルとサードパーティ統合を 1 か所で使え、最良のコスト管理と最新の革新が得られることが Microsoft の約束だと締めくくりました。
