## 5. 発表内容の詳細

### 5.1 導入の問い

onsemi の登壇者は、まず会場に「AI ツールを導入した組織は多いが、それによって実際に変わった、エンドツーエンドの業務プロセスを挙げられる人はどれだけいるか」と問いかけました。今回の 20 分は、そのギャップを onsemi がどう埋めようとしているかの話だとしています。

### 5.2 採用が止まった 4 つのテーマ

採用が停滞したユースケースを掘り下げたところ、どのケースにも共通する 4 つのテーマがあったと説明しています。

1. **断片化したデータ**：データがサイロ化し、ラベルが付いておらず、古く、データレイクの上にセマンティックレイヤーがない（オントロジーが存在しない）。このため AI は自信を持って答えるが、聞くたびに答えが変わりうる。「どうやって AI を信頼するのか」という問題です。
2. **ガバナンスされていないアクセス**：ID とポリシーがないと、作成するエージェントの 1 つ 1 つが、知的財産とデータへのリスクになる。
3. **場当たり的な構築（one-off builds）**：各チームが独自のコネクタや MCP サーバーを作り、車輪の再発明をして、同じパイプラインに何度も費用を払う。既存のコネクタやツールを探せる、中央のレジストリがないことが原因です。
4. **生産性のサイロ**：ドメインの専門家である業務ユーザーが、適切な AI ツールを使えば、コードを書いた経験がなくてもエンドツーエンドのアプリケーションを作れる。しかし、データにどう接続するかが壁になる。シングルサインオンや適切な RBAC が必要で、AI にプロンプトで頼めない。そこでデータを CSV でダウンロードし、AI コーディングツールに直接渡してしまう。アプリが動いたあとも、中央のサーバーにどうデプロイするか（Azure や GCP への展開、Entra ID のシングルサインオン、DNS の登録）が分からない。Claude や GitHub Copilot が使えても、ある程度の技術的素養が要る。結果として、アプリは本人のノート PC で動き、生産性は本人の中にとどまる。

> 補足：登壇者は、この 4 つ目の話は onsemi で実際に見た話で、皆さんの組織でも起きているはずだと述べています。

### 5.3 AI プラットフォームの 4 本の柱

onsemi の AI プラットフォームは、おもに次の 4 つの柱で構成されます。

**第 1 の柱：データ**

AI は、推論の対象にするデータの質に左右されます。製造、サプライチェーン、財務、人事のデータはすべて、onsemi の場合は Snowflake にカタログ化されています。セマンティックレイヤー（オントロジー）も構築中です。エージェントが注文明細について尋ねたときや、gross revenue、gross margin といった指標が何を意味するかを、正確に把握できるようにするためです。さらに、**秘密度ラベル、系統（lineage）、データオーナーシップ**を整備し、すべてのデータセットに既知のソースとスチュワード（管理者）を置きます。秘密度ラベルの部分は Microsoft Purview で実現しています。これにより、エージェントが権威あるソースから答えを取得でき、データの重複がなくなるため、精度とエージェントへの信頼が上がると説明しています。

**第 2 の柱：ガバナンスされたアクセス**

- すべてのエージェントに、マネージド ID を持たせる。onsemi では Entra ID に登録し、コントロールプレーンとして Agent 365 にも登録している。
- すべてのエージェントに、スコープ付きの権限と、責任を負う人間のオーナーを置く。エージェントは、その人間が実行できることだけを実行できる。アクセスも実行も「on behalf of（ユーザーの代理）」で行う。
- DLP ポリシー、ラベル、条件付きアクセスは、エージェントがデータをどこへ運んでも、データとともに付いていく。
- 適切なレベルの承認、監査可能性、監視を設けている。エージェントの動作をエンドツーエンドで追跡するために、LangSmith を使っている。これによって、エージェント型 AI のソリューションが監査可能だと言える。
- コンテンツフィルタリングのために、Palo Alto の Prisma も使っている（製品名の綴りは音声認識の都合で確定できません）。

**第 3 の柱：エージェント型 AI のレイヤー**

ここは、エージェントを、質問に答えるだけのチャットボットから、ユーザーに代わって行動する存在へ進化させる層です。エージェントは Microsoft Copilot や Teams の中にあり、onsemi が構築した MCP サーバーを通じて、信頼できる企業データに接地されています。onsemi には 2 つのプラットフォームがあります。

- ローコード：Copilot Studio と、自社で構築した **Agent Builder**
- プロコード：GitHub Copilot Harness の上に完全に構築されたもの（名称は聞こえたとおりで、音声認識の都合で確定できません）。登壇者は、これについて後でデモで見せると述べています（6 章）。

エージェントは、他のエンタープライズアプリケーションと同様に、登録、評価、監視、廃止（retire）されます。構成技術として、M365 Copilot、ローコードの Copilot Studio、プロコードの Azure OpenAI、EKS 上の LangGraph が挙げられました。

**第 4 の柱：再利用できる機能（reusable capabilities）**

中央の「COA チーム」（聞こえた表記で、正式名称は音声からは確認できません）が、Snowflake、Oracle Fusion、Blue Yonder、SharePoint などへのコネクタ（MCP サーバーまたは API レイヤー）の構築を担います。これらのコネクタは 2 か所に中央登録されます。

- **Microsoft APIM**：中央の AI ゲートウェイとして使い、エージェントと対応する MCP サーバーの間のすべてのトラフィックを APIM 経由にする。
- **自社構築の開発者ポータル**：各コネクタを登録し、探せる中央カタログにする。

評価、コンテンツセーフティ、ログは一度パッケージ化すれば、各チームが継承できます。また **golden template（ゴールデンテンプレート）** も用意しています。ダッシュボード用、フルスタックアプリ用、MCP サーバー用などで、新しい MCP サーバーを作る人はテンプレートからスキャフォールドし、実際の機能だけを考えればよい。デプロイ先、シングルサインオン、ガードレールといった非機能要件は自動的に処理されます。

### 5.4 全体像：onsemi AI プラットフォームとソフトウェアファクトリー

4 本の柱を合わせたものが onsemi の AI プラットフォームで、「アイデアから本番までの 1 本のガバナンスされた道」だと説明されました。スライドの全体像は、上から次のとおりです。

- **ユーザーとエージェント**：エージェントを作る人と、使う人。
- **ソフトウェアファクトリー**（自社構築）：3 つの環境があります。
  - 開発環境：作る人が緩めのルールで革新する。ガードレールの範囲内。
  - UAT への移行：承認ゲートがあり、アーキテクチャとセキュリティのガバナンスレビューを行う。
  - 本番への移行：ビジネスの承認が必要で、テストと評価の証跡が検証される。
- **ガバナンスされたデータとアクセスの層**：分析データ用にガバナンスされた Snowflake、トランザクション API 呼び出し用に Oracle Fusion などへつなぐ承認済みの MCP サーバー。常に単一の信頼できる情報源を保ち、監査証跡は LangSmith に記録される。
- **プラットフォームエンジニアリングの基盤**：GitOps（ここに「custom GitHub harnesses」があると語られています。聞こえた表記で、確定できません）と、Terraform による IaC。作る人は、どこにどうデプロイするかを気にしなくてよい。
- **開発者ポータル**：これらすべてを 1 つのプレーンにまとめる入口。
- **ゴールデンテンプレート**。

### 5.5 成熟度モデルと教訓

組織の AI 活用の旅は、次の順に進むと説明されました。

| レベル | 内容 |
| --- | --- |
| 1. 個人の生産性 | Copilot でプレゼンテーションを作る、など |
| 2. チームのワークフロー | エージェントが繰り返しのタスクを自動化する |
| 3. 人間とエージェントのチーム | 人が意図を設定し、エージェントがその代わりに実行する |
| 4. フロンティアファーム | Microsoft がフロンティアファームと呼ぶ成熟度 |

ほとんどの組織はレベル 1〜2 の間にいます。onsemi の登壇者は、自社は 2 と 3 の間で、3 にかなり近いと考えており、それは構築したソフトウェアプラットフォームのおかげだと述べています。

教訓（quick takeaway）として、次の 4 点が示されました。

1. **データを最優先にする**：AI の回答は、データの質を超えられない。
2. **スケールのためにガバナンスを敷く**：ID とポリシーを初日から整える。
3. **一度作って再利用する**：開発者コミュニティが、作ったコネクタや MCP サーバーを公開する場所を用意し、再利用できるようにする。
4. **利用量ではなく成果を測る**。

登壇者は、この旅は LTM と Microsoft の支援なしにはできなかったとし、支援のおかげで旅を 2 倍、3 倍のスケール（"2x, 3x scale"）で進められたと述べています。

### 5.6 LTM のエンタープライズ AI 提供体制（Senthil 氏）

Senthil 氏は、今回の事例で難しかったのは AI ツールやモデルそのものではなく、データの整合性、再利用、運用の規律だったと述べ、LTM のエンタープライズ AI の提供体制は、まさにそこに沿って構成されていると説明しました。レイヤーの説明は次のとおりです（一部の名称は音声認識の都合で確定できません）。

- **体験層**：フロントオフィス、voicing.ai、craft studio（聞こえた表記）など。
- **コアシステム層**：SAP や Oracle などの基幹システムを、プラットフォームを作り直すのではなく、AI から扱える（addressable）ようにする。
- **AI 主導の SDLC**：エンジニアリングと運用に AI を組み込む。ここまでを 3 つのレイヤーと呼んでいます。
- **第 4 のレイヤー：LLM とコンピュート**：フロンティアモデルをお客様に使いやすく届ける。あわせて、ドメイン特化の SLM も提供する。
- これらは、ソブリン性と信頼（sovereign and trust）で統制され、「ロジックとアクション」を顧客に提供できると述べています。

Senthil 氏は、これらの層が、onsemi の登壇者が説明したソフトウェアプラットフォームの中にも、何らかの形で現れていたと述べました。エンタープライズ AI スタック全体は「6 層」と呼ばれていますが、発話で番号づけされて説明されたのは上の内容までです。

これらを支える背骨（spine）が、「プロアクティブなキャパシティを設計に組み込むこと（proactive capacity by design）」です。具体的には、**AI 1000** のような人材プログラムで、AI を活用できる人材（聞こえた表記は「CADLs」で確定できません）1,000 人を育成し、FDE（発話では「今よく使われる用語」として紹介）がお客様や事業部門と一緒に座って AI 主導の基盤を整える、という説明です。基盤ができると、次の課題はスケールになり、スケールするとトークノミクスと FinOps が関わってきます。ここで「LTM won」（聞こえた表記。サービス名と思われるが音声認識の都合で確定できません）がお客様を支える、と述べています。

結論として、LTM のエンタープライズ向け提供は、エージェント体験時代に向けた統一的なゲートウェイとなるエコシステムだと述べ、「LTM とはビジネス成果である」としています。onsemi のケースでは、ソフトウェアプラットフォームを **2 倍のベロシティ（2x velocity）**で、市場投入までの時間を短縮して届けることを支援したと説明しています。最後に、LTM ブースへの来訪を案内しました。

## 6. デモ・手順

デモは 2 つの部分に分かれます。1 つ目は録画された映像、2 つ目は開発者ポータルの画面を見せながらの登壇者の説明です。音声からは画面上の細部（ボタン名や入力値など）は確認できません。

### 6.1 録画された映像（ソフトウェアファクトリーの説明）

最初に映像が表示されず、再生し直しています。ナレーションで語られた内容は次のとおりです。

1. 「onsemi のすべての優れたアイデアは、速く安全に本番へ届くべきだ」という前提。実験は、緩いルールの onsemi の「labs」で始まる。準備ができたらレビューと承認を経て、ガバナンスされた組織に昇格し、2 つの承認ゲートを通って、開発から UAT、本番へ進む。裏側では、GitOps、IaC、ゴールデンテンプレート、Copilot ハーネスが重い作業を担う。
2. **開発者ポータル**（ファクトリーの入口）。カタログには、アプリ、MCP サーバー、エージェント、システム、API、機能（capabilities）、テンプレート、スキルがまとまっている。既存のツールとリポジトリがここに統合されており、作る人は新しく作る前に、すでにあるものを探せる。
3. **構築**：VS Code で、作る人が onsemi のカスタムコマンドを使う。コマンドは、要件、設計、ビルド、テスト、リリースというプロダクトライフサイクル全体を、各段階の可視性とともに案内する。
4. アプリはゴールデンテンプレートからスキャフォールドされ、AI コーディングで生成される。この間、onsemi の **AI セキュリティハーネス**が、後からではなく並行してレビューする。
5. 承認が出ると、自動化が引き継ぐ。Terraform が AKS 上にインフラをプロビジョニングし、Entra ID のシングルサインオンが構成され、SSL 証明書が発行され、DNS エントリが作られる。
6. アプリは、ユーザーに代わる SSO で Snowflake API に接続する。そのため、各ユーザーには、権限のあるデータだけが見える。誰も資格情報を持たず、手作業のプロビジョニングを待つこともない。
7. 結果として、カスタムアプリケーションが、ガバナンスされた再現可能な経路で本番に出荷される。

### 6.2 開発者ポータルの説明（登壇者による画面の説明）

映像のあと、登壇者は開発者ポータルを短く見せるとして説明しました。

1. 中央カタログには、onsemi が作ったアプリ、MCP サーバー（トラフィックは中央の API を通る）、作成中のエージェント、システムと API が載っている。
2. サンプルアプリの 1 つを見ると、業務ユーザーが AI でコーディングする際、いきなりコード生成に入らず、**PDLC（プロダクトライフサイクル）を強制する**ように変更してある。GitHub Copilot や Claude Code（発話では「cloud code」と聞こえます）が、まず何を作りたいのか、誰が使うのか、どうアクセスするのかをユーザーに確認する。
3. その結果をもとに、完全なプロダクト仕様を生成する。**アイデア概要（idea brief）→要件収集→ナレッジフェーズ→ PRD** の順で、PRD（プロダクト要求仕様書）に業務オーナーがやりたいことのすべてを記録する。
4. 承認されると、設定済みの harness のルールに基づいて、ビジネスアーキテクチャと技術アーキテクチャを含むアーキテクチャを作る。
5. これが承認されると、**データマップ**も記録される。ユーザーが Entra ID でサインインして、サプライヤーダッシュボードにシングルサインオンでアクセスし、どの機能やスキルが読み込まれるか、ユーザーが本人としてどうサインインして機能がプロビジョニングされるか、Snowflake のどのセマンティックな成果物（semantic artifact）を読むかを正確に把握できる。
6. **コードマップ**には、生成されるすべてのリポジトリと、読み込まれるすべてのコンポーネントが記録され、透明性と監査可能性が確保される。
7. インフラの自動プロビジョニングについては、Terraform の IaC スクリプトも記録される。どの AKS クラスターがプロビジョニングされるか、どんなイングレス／エグレスのルールが作られるか、DNS エントリの作成、可観測性、Dockerfile が分かる。
8. DevOps に加え、特に重視しているのが **SecOps** で、業務ユーザーがコードにシークレットやパスワードを入れないようにする。Entra ID による認証とシングルサインオンを担保し、次のスキャンを行う。
   - コード内にシークレットがないかのスキャン
   - CodeQL による SAST スキャン
   - IaC のスキャン
   - 依存関係と脆弱性のスキャン

登壇者は、これによってサンドボックスやラボ環境にあるアイデアを、セキュリティが最初から組み込まれた状態で本番へ持っていく速さが得られたと説明しました。これらの多くは裏側で動くもので、「そうあるべきだ」と述べています。フロントドアの WAF、APIM、Entra ID、Palo Alto の Prisma といった非機能要件は、業務ユーザーが意識しなくてもデフォルトで裏側で動くようにし、ユーザーがビジネス課題の解決に集中できるようにする、という考えです。

## 7. 注意点・発表者の気付き

- AI ツールの配布は簡単だが、半年後に残る価値の大半は個人の生産性（メール、要約、PowerPoint）でした。業務プロセスの変革には別の取り組みが必要だった、というのが発表の出発点です。
- AI が聞くたびに違う答えを返しうるのは、データが断片化し、ラベルやセマンティックレイヤー（オントロジー）がないことが原因の 1 つだと説明されました。
- 業務ユーザーが AI でアプリを作れても、SSO や RBAC、デプロイ（DNS、Entra ID など）の壁があり、CSV を AI コーディングツールに渡したり、アプリが自分のノート PC にとどまったりします。onsemi では、この壁を、ゴールデンテンプレートと自動化で埋めています。
- 同じコネクタや MCP サーバーを各チームが作る重複を防ぐには、中央のレジストリ（カタログ）が必要です。
- 成熟度については、多くの組織はレベル 1〜2 の間にいて、onsemi 自身もレベル 3 に「かなり近い」という位置づけで、到達したとは述べていません。
- 発表では、具体的なコスト削減額や ROI の数値、使用モデルやライセンスの詳細は語られていません。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **onsemi の事例**：ソフトウェアファクトリーにより、業務ユーザーのアイデアをサンドボックスやラボから本番へ持っていく速度を得られた。セキュリティが最初から組み込まれている。パートナー支援によって、旅を 2 倍、3 倍のスケールで進められた（onsemi の登壇者）。
- **LTM の立場から**：ソフトウェアプラットフォームを 2 倍のベロシティ、より速い市場投入で届けることを支援した（Senthil 氏）。
- 業務ユーザーは、SSO、WAF、APIM、Entra ID、Prisma といった要件を意識せずに、課題解決に集中できる。
- 各ユーザーは、権限のあるデータだけを見ることができ、誰も資格情報を持たず、手作業のプロビジョニングを待たない。
- ゴールデンテンプレートと中央カタログにより、新しい MCP サーバーなどを作る人は、機能の部分だけに集中でき、重複開発を避けられる。

> 補足：2x の数値は、発表で語られた範囲では、速度（ベロシティ）の説明であり、算出根拠や比較の基準は述べられていません。

## 9. まとめ

onsemi は、AI ツールの展開が個人の生産性にとどまり、業務プロセスが変わらないという課題に対し、データ、ガバナンスされたアクセス、エージェント型 AI、再利用できる機能の 4 本の柱で AI プラットフォームを作りました。その上のソフトウェアファクトリーでは、開発から UAT、本番へ 2 つの承認ゲートを通り、Terraform、Entra ID の SSO、各種スキャンを含む作業が自動化されています。

教訓は、データを最優先にすること、ガバナンスを初日から入れること、一度作って再利用すること、利用量ではなく成果を測ることです。Senthil 氏は、LTM のエンタープライズ AI の提供体制が、まさにデータの整合性、再利用、運用の規律を軸に構成されていると述べて発表を締めくくりました。
