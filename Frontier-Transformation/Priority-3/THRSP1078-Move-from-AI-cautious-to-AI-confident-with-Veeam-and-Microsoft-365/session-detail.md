# THRSP1078 Move from AI cautious to AI confident with Veeam and Microsoft 365

## 1. はじめに

このセッションは、Veeam の David Tosoff 氏が、AI エージェントの時代における Microsoft 365 のデータ保護を「バックアップして復旧する」だけで終わらせず、「データの中身を知る」ところまで広げる考え方を紹介する約 23 分の登壇です。ランサムウェアに加えて、AI エージェントが大量のデータを高速に書き換えるという新しいリスクが出てきたため、Veeam の製品（発表では Veeam Intelligent ResOps for Microsoft 365 と聞こえます）でそれにどう備えるかが話の中心です。

登壇者が繰り返したのは、次の 3 つの問いです。

- AI は何に到達できるのか（What can your AI reach?）
- 到達すべきでないものは何か（What shouldn't it reach?）
- AI がやったことを元に戻せるか（Can you undo what it does?）

この 3 つに答えられる状態を、発表では「AI を警戒する状態（cautious）」から「AI に自信を持てる状態（confident）」への移行と位置づけています。

このセッションでは、時間の都合で本格的なデモは行われていません（登壇者自身が、デモ全体を見せる時間はないと述べています）。製品を使い始める流れを、画面を見せながら駆け足で説明する場面が終盤にあります（6 章）。

## 3. 何に関する発表か

テーマは、AI エージェントが業務データに対して作業する時代に、データ保護をどう再設計するかです。扱う中心の対象は Microsoft 365（SharePoint、Teams、OneDrive、Exchange）のデータで、Veeam のクラウドサービスである Veeam Data Cloud と、その上のデータ分析機能（データをグラフ化して問い合わせられる仕組み）が登場します。

発表の流れは次のとおりです。

1. 調査結果の数字から見る「復旧への自信」と実際の復旧率のギャップ
2. 保護すべき脅威の変遷（2006 年、2021 年、2026 年）
3. Veeam のプラットフォームと「データを知る」ステップ
4. Microsoft 365 のリスクパターンと、バックアップを超えた問い
5. 具体例：AI が機微データのファイルを書き換えた場合
6. Purview との関係、導入手順の概要、パッケージ（Express／Flex／Premium）
7. 先行利用したお客様の声とまとめ

## 4. 発表者が伝えたいメッセージ

登壇者の主張は、AI は非常に有用で恐れるべきものではないが、AI がデータを変更する速度と規模を考えると、ある程度の慎重さは必要だ、というものです。そのうえで Veeam が目指すのは、慎重な状態からお客様が自信を持てる状態へ移ることを手助けすることだと述べています。

そのための考え方が、「バックアップしてリカバリーする」を出発点とし、次に「データを知る」ステップをバックアップの後ではなく、より前の段階に持ち込むことです。バックアップの仕組みはすでにデータを取り込んで処理しているので、その過程で中身についての洞察も得ておけばよい、という発想です。

## 5. 発表内容の詳細

### 5.1 復旧への自信と実際の数字

登壇者は、Veeam が実施した調査（回答者は Veeam の顧客とは限らない、現場の組織）の数字を挙げました。

- セキュリティリーダーの **90%** が、リストアと復旧を行い、RTO（目標復旧時間）を満たせると自信を持っている。
- しかし、ランサムウェアに対する実際の達成度を見ると、データを完全に復旧できた組織は **約 4 分の 1** にとどまる。4 分の 3 程度までなら復旧できる組織は、それよりやや多い。
- 別の数字として **43%** のリーダーが、AI の導入が、自分たちが AI を管理・保護・健全に保つ能力を上回るペースで進んでいると感じている。

この 90% の自信と実際の復旧結果との開きを踏まえ、「毎回、クリーンな復旧を保証できるか」を自問するよう促しています。

### 5.2 脅威の変遷：2006 年、2021 年、2026 年

登壇者は聴衆に目を閉じてもらい、タイムマシンで 20 年前の 2006 年に戻ったと想像してもらいました。その頃の不安は、自然災害（地震や津波）で拠点のデータを失うことや、RAID 6 で想定以上のドライブを失うといった、深刻なハードウェア障害でした。挙手をしてもらうと、どちらも現在も心配事として残っているとのことです。2021 年以降は、ここにランサムウェアが加わりました。ランサムウェアは近年、お客様に大きな業務・金銭的混乱をもたらしてきた脅威です。

そして 2026 年には、AI エージェントがデータに対して作業を行うという新しい攻撃面（vector）が加わります。登壇者が強調したのは、多くの場合、悪意はないという点です。エージェントは求められたことや、自分が最善と判断したことをしているだけです。課題は、変更を加える**速度と規模**にあります。

### 5.3 Veeam のプラットフォーム

Veeam は、自社を世界でナンバーワンのデータ保護プラットフォームと位置づけ、Microsoft 365 のメールボックスを他社より多く保護していると述べています。プラットフォームは Azure を基盤とした as-a-service として提供され、次の考え方で作られています。

- 保護できるものは全て保護し、ソースデータの境界の外に、隔離したコピーを置く。
- 復旧は、クリーンかつ迅速に行えるようにする。インスタントリカバリーのほか、バックアップ済みデータにマルウェアが潜んでいないかを後から調べるツールがある。
- 登壇者は、ここまでは 2026 年時点で「table stakes（最低条件）」だと述べています。

その先として、Veeam はデータを知る（know）ことを次のステップと位置づけています。この 10 年ほどでバックアップ完了後にデータを把握する機能を数多く加えてきましたが、それを逆転させて、「知る」工程をプロセスの早い段階に持ち込みたい、という考えです。

プラットフォームの構成は、次のように説明されました。各種ワークロードを取り込み、「data AI command platform」（聞こえた名称。音声認識の都合で正確な表記は確定できません）に集約します。そこから Azure 上の Veeam Vault（発話では「VM Vault」と聞こえますが、音声認識の都合で表記を確定できません）へコピーを送り、Azure へ移したデータを含めて復旧・再保護できます。同時に、データのパターンやアクセス元を把握し、AI がデータに対して行った変更を、意図的でも誤りでも元に戻せることを重視しています。

### 5.4 Microsoft 365 とリスクパターン

登壇者は、前日の基調講演でも示されたとおり、業務は Microsoft 365（SharePoint、Teams、OneDrive、Exchange）の上で動き、すべてが Copilot に集約されつつあると述べています。そのため、ここを災害、悪意ある攻撃者、AI から守る必要があります。ただし、環境は絶えず増え続けるため簡単ではありません。

- Microsoft 365 には、毎日約 **30 億**の新しいファイルが追加され、AI の普及で増加が加速している。
- Palo Alto Networks の調査として、あるデータにアクセスする主体は、人間 1 に対して **非人間の ID が 109** ある。人間だけを心配すれば済む状況ではない。
- ランサムウェア事例の **97%** で、データの持ち出し（exfiltration）も起きている。暗号化と身代金要求だけでなく、攻撃者は営業秘密などの価値あるものがないかをデータから探しており、AI がこれを容易にしている。

登壇者は、環境内で見つけるべきリスクパターンとして、次を挙げています。

- ユーザーが作る Excel や Word などが OneDrive、SharePoint、メール添付に散らばり、共有すべきでない機微データを含むことがある。
- 組織設定によっては、匿名リンクやゲストアクセスなど外部共有が行われ、取り消すべきだったゲストアクセスが数週間、数か月、数年放置されていることがある。
- 組織内でも権限が広すぎる。例えば経理の Jim が財務サイトにアクセスでき、そこにある給与情報のファイルに、権限の継承によって実効的にアクセスできてしまう。
- AI の把握。環境内で動いているすべての AI と、それがアクセスできるデータをすべて把握していると自信を持って言える人は、と会場に挙手を求めました。登壇者は返ってきた反応に「そのとおり」と応じています（挙手の人数は音声からは分かりません）。

### 5.5 バックアップを超えて問う

バックアップは、すでにデータを取り込み、リポジトリに保存しています。そこで、その機会に次の問いを立てられる、というのが登壇者の説明です。

- 個人を特定できる情報が含まれていないか。
- データが、本来あるべきコンプライアンス上の場所にあるか。
- 冗長（redundant）、陳腐化（obsolete）、些末（trivial）なデータか。5 年前の業務プロセスに基づく古いデータは、保存コストが余計にかかるうえ、AI がそれを取り込んで使うと、無関係なデータによって回答が汚染（poison）される可能性がある。

続いて、自分の環境で確認すべき 3 つの問い（AI は何に到達できるか、到達すべきでないものは何か、やったことを元に戻せるか）を示しました。AI では「コンテキストが重要」だとし、Microsoft 365 の各データソースを Veeam の製品（発表では「Beam's Intelligent ResOps for Microsoft 365」と聞こえます）から data command graph（聞こえた名称）に取り込むと、グラフになることで事実上、自由に問い合わせられるようになると説明しています。Veeam が妥当と考える洞察、自動化されたポリシー、エージェント型のレポートが一目で見られ、そこから好きなだけ掘り下げられます。

これを有効にすると、AI を安全に加速し、被害範囲（blast radius）を小さくし、機微な可能性のあるデータを特定して隔離できる、と述べました。問い合わせ自体も、ビジネスが知りたいことを自由に尋ねられるとしています。

### 5.6 例：AI が機微データのファイルを書き換えた場合

登壇者は単純化した例で説明しました。SharePoint サイトにある Excel ファイルに、メールアドレスや社会保障番号が含まれ、財務グループ全員が読み取れる状態です。それを、AI が変更しました。例えば、経理の Jim が仕事を楽にするために作った Copilot Studio のアシスタントです。その変更は本来やるべきことではなく、そもそもこのファイルにアクセスできてはいけなかったかもしれません。

- **1 つ目の対処は復旧です。** データ保護の会社として、直前の状態に戻せます。
- **2 つ目の対処は、データの中身が分かった状態で改善することです。** このデータを保護すべきか、別の場所に置くべきか、AI にアクセスさせるべきかを検討できます。秘密度ラベル（sensitivity label）を適用するなど、何らかの是正を行って分類を改善し、体制を強化できます。

目標は、機微データがどこにあるか、**誰だけでなく何がそれに到達できるか**、そして保護されているかを理解することです。それにより、HIPAA や PCI DSS などのフレームワークへの整合に近づけると述べています。

### 5.7 Purview との関係

この仕組みは既存のプラットフォームを置き換えるものではない、と登壇者は述べています。Purview を使っているお客様には「better together」の関係で、Veeam が見つけたデータに対して、Purview の秘密度ラベルを本番環境へ適用できます。例として、payments.xls に機微データがあると分かれば、それにタグを付けて、これまでより安全に扱えるようにする、という説明でした。

### 5.8 パッケージ（Express／Flex／Premium）

Veeam Data Cloud では、次の 3 つのパッケージで提供されると説明されました。

| パッケージ | 内容 |
| --- | --- |
| Express | Microsoft 365 の境界内でのバックアップ（backup in place）。Microsoft と共同設計（co-engineered）で、ほぼ即時のデータ保護と即時のデータ復旧ができる。 |
| Flex | データを Microsoft 365 の境界の外に取り出し、お客様が選んだリージョンの、設計上イミュータブル（変更不可）な隔離リポジトリに保存する。 |
| Premium | 上記の両方を組み合わせたもの。即時性と、データが完全に独立した別の場所にある安心感を両立でき、お客様の多くはここに行き着くと述べています。 |

あわせて ID のバックアップにも触れています。Veeam Data Cloud では、Entra、管理単位（administrative units）、ユーザー、グループ、Intune ポリシー、条件付きアクセスポリシーを保護でき、現在ある 30 日のごみ箱を超える柔軟性が得られます。また、ログと変更履歴の洞察も得られ、プラットフォーム内にとどまらない監査が可能になります。

### 5.9 先行利用したお客様の声とまとめ

登壇者は、Veeam Intelligent ResOps for 365（聞こえた名称）が比較的新しい製品で、1〜2 か月前に GA（一般提供）したと述べました。プライベートプレビューで試した数社（a couple of customers）のお客様の 1 社は、「これにより AI を責任を持って採用する自信が増す」という趣旨の感想を寄せたそうです（登壇者はスライドに載った感想の最後の一文に注目して紹介しています。お客様名は発話にありません）。

Microsoft とともに目指すのは、データを理解し、重要なものを守り、データとエージェントを統治（govern）し、体制を証明すること（prove your posture）です。経営やビジネスに対して、「問題ない。すべてのエージェントは必要なものだけにアクセスしている」と答えられる状態にする、という説明でした。

## 6. デモ・手順

このセッションでは、時間の都合で本格的なデモは行われていません。登壇者は、デモ全体を見せる時間はないが始め方は手短に示すと述べ、画面を示しながら次の流れを説明しました。画面の細部は音声からは確認できません。

1. Veeam Data Cloud のポータルにログインする。Entra、Azure、Salesforce、Microsoft 365 などを保護し、Veeam Vault にデータを送っている状況が表示される。
2. 画面左下にある add-on（アドオン）ボタンをクリックする（紹介ビデオもあるが、ここでは見ない）。
3. テナントへの接続を求められるので、テナントを追加する。
4. 取り込みたいシステムやデータソースと、実行したいアクションを選ぶ。選択肢として、秘密度ラベルの分析、ファイルの隔離とラベル付け、データへのアクティビティ（誰や何が何をしているか）の確認が挙がった。
5. 「保存して続行」を押す。ほかに詳細設定もあるが、発表では詳しく触れていない。
6. スキャンとデータの取り込みが始まり、完了すると概要ダッシュボードが表示される。各指標から掘り下げられる。
7. この例（比較的小さなテナント）では、機微な情報を含むと思われるファイルが **2,400 件**、それらを変更できる AI エージェントが **3 つ**と表示された。これらをダブルクリックして詳細を見る。
8. データはグラフに取り込まれているため、左側の緑の V のロゴから、さまざまなパラメーターでグラフに対するクエリを組み立てられる。

登壇者は、これ以上の内容は Veeam のブースで見せると述べています。

## 7. 注意点・発表者の気付き

- 90% が復旧に自信を持つ一方、実際に完全復旧できたのは約 4 分の 1 という乖離があります。自信と実際の復旧は別物だという指摘です。
- AI エージェントによる変更は悪意がなくても起こり、問題は速度と規模です。登壇者は「AI を恐れよ」という意図ではないと明言しています。
- あるデータにアクセスするのは人間 1 に対して非人間の ID が 109 という数字を挙げ、人間だけを心配すればよいわけではない、と述べています。
- 冗長・陳腐化・些末なデータは、保存コストだけでなく、AI の回答を汚染するリスクがあります。
- 製品は新しく、GA は 1〜2 か月前です。
- 発表では、価格や対応範囲の詳細、導入にかかる時間などは触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- AI を安全に加速でき、被害範囲を減らせる。
- 機微データを特定し、隔離やラベル付けができる。ファイルが AI に書き換えられても復旧できる。
- Purview と併用でき（置き換えではない）、既存の秘密度ラベルに結果を反映できる。
- HIPAA、PCI DSS などのフレームワークへの整合に近づける。
- データをグラフ化することで、事業が必要とする問いを自由に問い合わせられる。
- ID のバックアップで、30 日のごみ箱を超えた保護とログ・変更履歴を得られる。
- プライベートプレビューのお客様が、「AI を責任を持って採用する自信が増した」という趣旨の評価をしている。

## 9. まとめ

AI エージェントの登場で、ランサムウェアや災害に加えて、データを高速かつ大規模に書き換える新しいリスクが生まれました。登壇者は、バックアップと復旧だけでなく、Microsoft 365 のデータの中身、アクセス元、AI の到達範囲を把握する段階に進むことを提案しています。そのための Veeam の製品が、データをグラフ化して問い合わせられるようにし、Purview の秘密度ラベルとも連携します。最後に残された問いは、「AI は何に到達できるか」「到達すべきでないものは何か」「やったことを元に戻せるか」の 3 つです。なお、Veeam のブースは 4418 番と案内されました。
