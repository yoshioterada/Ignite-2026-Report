# THR1009 Safer Agentic Workflows

## 1. はじめに

このセッションは、予定されていた共同登壇者が雨の中で会場に着けなかったため、司会兼登壇者が会場の参加者と対話する形に変わった回です。参加者は開発者やテックリードで、カナダ政府機関、銀行、Power Platform を担当する IT 部門の人たちです。それぞれの取り組み、悩み、社内の温度差が語られました。

発話からは、スライドや製品の画面を使った説明は確認できず、デモも行われていません。後半で、不在だった登壇者が話す予定だった要点（ガードレール、評価、人間の関与と、月曜日からできる三つの対策）が司会によって代読されます。内容は、エージェントを安全に作るための考え方と、規制のある業界での実情を知りたい人向けです。

## 3. 何に関する発表か

テーマは、エージェントを使ったワークフローを安全に進める方法です。ただし登壇者の到着が遅れたため、司会が参加者に、開発者かどうか、エージェント開発のどの段階か、すでに問題が起きたかを尋ねる形で始まりました。

流れは次のとおりです。

1. 参加者の自己紹介と、取り組みの現状
2. 社内で孤立しているか、支援されているか
3. 現場から見た、Microsoft への期待と要望
4. 懐疑的な人、過度に期待する人への向き合い方
5. 不在の登壇者の要点の代読
6. 最後の質問

## 4. 発表者が伝えたいメッセージ

司会が整理した全体の骨子は、**ガードレール、評価、人間による監督**の三つです。代読された内容では、月曜日に職場に戻ってからできる行動として、次の三点が示されました。ツールをリスクで格付けして危険なものには承認を付ける、エージェントが届く範囲を絞る、トレースを有効にして実際の失敗をテストに入れる、の三点です。

### 5.2 社内で孤立しているか

- Harneet は、企業として複数のチームが探索しており、業界の変化が速いため、1 か月前の想定が通用しなくなり方向転換が必要になる点を挙げました。Microsoft 製品自体も変化が速く、それが負担だと述べています。目標は、エージェント型 AI のサービスを事業全体に提供することです。Microsoft とは長く関わっており、プロダクトチームとフィードバックやアイデアを共有し、前日にも打ち合わせがあったと述べています。Foundry を中心に見ていて、Power Platform や Copilot Studio もあります。
- Ethan の会社には、IT の各分野にまたがる 12 の「V チーム」があり、法務、開発者、インフラ、アプリなどが参加しています。普段は最先端を押す文化ではないのに、採用は順調だという評価です。一方で、Power Platform の環境整備について文書を作っても、すぐに新機能が出て古くなる点が悩みです。M365 Copilot や Power Platform の新機能を試し、ビジネス側のパワーユーザーを教育する担当が複数います。

司会は、Microsoft の営業やアカウントチームに魔法の杖を渡せるなら何を望むかと尋ねました。Ethan の答えは、**新機能についてほぼリアルタイムで更新される情報**です。チャットの画面に「Cowork」のような機能が加わると、ビジネスの利用者は戸惑うため、「明日にはこれが使える」「切り替えられる、または自動で入る」といった予告があるだけでも助かるという話でした。

司会は、自分が Judson Althoff 氏の組織（顧客と営業の商用部門を統括）と一緒に展開を進めていると述べ、参加者に要望や不満をメールで送るよう依頼しました。アドレスは発話で「D-C-A-S-S、Microsoft」と綴られています。要望にもとづき、参加者の地域（アイオワ、オタワ、ニュージャージー、カリフォルニアなど）でカスタマイズしたワークショップを開く考えを示しています。司会の仕事は、世界各地での顧客向けワークショップの実施と、Microsoft の営業担当と顧客の教育です。最初のワークショップのテーマは「Safer agentic workflows（安全なエージェント型ワークフロー）」にしたい、という発言もありました。

### 5.4 懐疑的な人と、期待しすぎる人

Matthieu は、組織には新しい技術を次々に追いかける開発者がいて、影響を考えずに飛びつくと述べました。例として、ネットワークのトラフィックキャプチャを AI（Claude Code と発話）で分析した人が、AI の幻覚（ハルシネーション）に気付かず、AI の出力をそのまま繰り返して AI と往復する「人間の中継役」のようになっていた話を挙げました。ネットワーク分析の経験者ならすぐ誤りが分かる内容でした。

一方、AI を使うことに乗り気でない人もいます。Matthieu の対応は次のとおりです。

- 懐疑的な人には、小さなワークショップを開き、業務ロジックではない定型コードの置き換えなど簡単な使い方を見せます。AI に仕事が奪われるという感覚を和らげることが目的です。
- 出力をそのまま信じる人には、分析者が実際にどう確認するかを一緒に辿り、AI の答えがおかしいと見抜く方法を示します。
- 技術が出た瞬間に飛びつくのではなく、何ができるかを評価してから使う姿勢を取ります。個人ごとに対応を変えます。

Harneet も同様で、何千トークンも使っているのに用途が分からない人がいる一方、懐疑的な人もいると述べました。懐疑は、置き換えへの不安と、精度や結果の質への不安の二面があります。開発者の立場の自分たちが、使う人が無理なく慣れられる体験を作る責任がある、AI は置き換えではなく支援のためのものだという考えです。

司会は、先日の Copilot の障害で、メールの書き方が分からなくなったと感じた経験を話し、AI は仕事を奪わなくても怠惰にするかもしれないと述べました。

### 5.5 代読された、不在の登壇者の要点

司会は、Jonah Anderson 氏のメモを代読すると説明しました。内容は次のとおりです。

- 構成の予定は、ガードレールの話（Build で去年見せたエージェントが想定外の動きをした体験談）、評価（動作を知る唯一の方法）、人間の関与（どこまで自律に任せ、どこで人間の判断を挟むか）、失敗談と学び、最後に月曜日からできること、でした。
- 月曜日の三つの行動は次のとおりです。
  1. すべてのツールをリスクで格付けし、危険なものには承認を付けます。承認はコードで強制し、タイムアウトしたら「拒否」とします。
  2. エージェントが届く範囲を絞ります。例えば、過去のすべての Teams メッセージではなく、専用の ID、特定のツール、明示的な許可リスト（対象とするもの、しないもの）を使います。
  3. トレースを有効にします。実際の失敗 20〜50 件をテストにして CI に入れます。
- 要約は「ガードレール、評価、人間の監督」です。

司会は、自分のメールアドレスを知っているのだから、登壇者の話の要点を後でメールで送り、本人とも引き合わせると述べています。

### 5.6 質疑応答

Ethan から、経営層に「対象を絞った方が良い」という結論を、自分が説得しなくても伝わるようにしたい、という発言がありました。経営層はすぐに仕事全体を置き換えられると考えるが、実際は毎日の Excel 入力とメール送信のような「作業の一部」の自動化です。司会は、パイの一部を切り取って進めるという考えを良い助言だと返して、セッションを終えました。この質問への具体的な解決策は、発表では示されていません。

## 7. 注意点・発表者の気付き

- 規制のある業界（政府、銀行）では、法的枠組み、DLP、PII が課題で、セキュリティは多層で考える必要があるという声が出ました。
- 経営層から、すべての会議録画を調べるような過度な要求が出ることがあり、実現性とプライバシーを検討する役が必要です。
- AI が幻覚を起こしても、利用者が気付かずに AI の出力を繰り返す危険があります。
- 市民開発が広がり、担当者の異動や退職で保守できないエージェントが残る問題があります。
- 製品の変化が速く、社内向け文書がすぐ古くなります。
- 利用者の中には、大量のトークンを使っていても用途が把握できない人がいます。
