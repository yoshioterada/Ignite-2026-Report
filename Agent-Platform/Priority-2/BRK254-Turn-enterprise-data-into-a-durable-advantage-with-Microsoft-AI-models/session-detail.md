# BRK254 Turn enterprise data into a durable advantage with Microsoft AI models

## 1. はじめに

## 5. 発表内容の詳細

### 5.1 MAI モデルの位置づけ

発表者は、MAI モデルは新顔ではなく、すでに数十億人が使う Microsoft 製品で動いていると説明しました。

| MAI モデル | 使われている製品 |
| --- | --- |
| MAI の Code モデル | Excel |
| MAI の画像モデル | PowerPoint |
| MAI Transcribe | Dragon Copilot |
| MAI の音声モデル | Dynamics 365 |

こうした製品を通じて、効率の良いモデルを大規模に作り、学習させ、運用する方法を学んできた、という説明です。モデルは学術的なベンチマークではなく、実際の企業の業務で力を発揮するように設計されており、実データでの調整のしやすさも、後半の事例で示されるとしています。

### 5.2 新しい MAI モデル

前日に Satya と Mustafa が発表した新モデルとして、次が紹介されました。

- **Code 2**：日常のコーディングとエージェント的な推論に、フロンティア水準の価格性能比をもたらすモデル
- **MAI Cyber 2**：Microsoft のセキュリティに関する深い知見と独自データから作った、サイバーセキュリティ専用モデル。フロンティア水準の性能を、わずかなコストで提供するとしています
- **Image 2.7**：精密な編集、一貫した画像、ブランドコンテンツ向けの細かな制御ができる画像生成モデル
- **MAI Realtime**：音声向けに作られた、自然な往復の会話に対応するモデル

発表者は「1 つのモデルですべてをこなす」のではなく、**仕事ごとに適切なモデルを選ぶ**ことが要点だと述べています。

### 5.3 提供される場所

選択肢はモデルの種類だけでなく、すでに作業している場所でモデルを使えることにもある、という説明です。

- コーディングモデルは、GitHub と Windows で利用できます。
- Foundry へは近日提供の予定です（発話では「まもなく」）。これにより、OpenRouter や Vercel のようなゲートウェイでも使えるようになるとしています。
- Hermes、OpenCode、Kilo などのハーネス（エージェントの実行基盤）の中でも使えるようになるとしています。
- 画像モデルは、Fal、Figma、Adobe など、制作者がすでに作業している場所で利用できます。

### 5.4 コーディングモデル：Code 2 と Code 2 Flash

エージェント型のコーディング向けに、2 つのモデルが発表されました。

- **MAI Code 2**：日常的な企業向けタスクを想定した、大きいほうのモデルです。本番へ持っていくコード、深いデバッグ、複数ファイルにまたがる実装、リポジトリ全体にわたる推論を扱えると説明されました。現在 GitHub で利用できます。
- **MAI Code 2 Flash**：小さく、高速で効率の良いモデルです。コードの説明、的を絞った編集、定型的な修正、素早い反復が得意とされています。

比較の数値は、前日の基調講演で Mustafa が述べたものとして次のように紹介されました。

| 比較 | 性能 | コスト |
| --- | --- | --- |
| Code 2 と GPT-Sol 6（聞こえた表記のまま） | 98% | 40% |
| Code 2 と Claude Opus 5.5 | 96% | 5% |
| Code 2 Flash と Claude Haiku 5.5 | 同等 | 20% |

Code 2 Flash については、GPT-6 Luna と同等とも述べており、その際に「65%」という数字が出ていますが、何に対する 65% なのかは発話から確認できません。いずれのモデル名も音声認識の都合で表記が確定できません。発表者は、トークンを消費し続けるコーディングでは、こうしたコスト差が事業にとって大きいと強調しました。

スライドでは、Code 2 が生成したウェブサイトが紹介され、見た目が豊かで操作性も高く、忠実度の高い開発と制御ができる例として見せられています。具体的な内容は音声からは確認できません。

### 5.5 なぜモデルをカスタマイズするのか

発表者は、「フロンティアモデルは十分賢いので、そのまま使えばよいのでは」という疑問を自ら取り上げ、次の 3 点を理由に挙げました。

1. 大規模に本番展開すると、フロンティアモデルは高価すぎて、事業の利益が残らないことが多い
2. 大きなモデルで深い推論をさせると、開発パイプラインには遅すぎることが多い
3. 事業にとって重要な詳細情報が、汎用モデルには含まれていない。基調講演の Alaska Airlines の例にある、Alaska 固有の ATA コードがその一例

### 5.6 継続的な学習ループ

Microsoft の進め方は、自社データを埋め込み、継続的に改善する仕組みです。

1. **評価**：自社にとって良い状態を定義します。目標とベンチマークを決め、品質・速度・コストを含めます。
2. **構成**：Foundry で、最適なプロンプト、ツール、エージェントの振る舞いを設定します。
3. **学習**：さらに先へ進めたい場合、エージェントの中でモデルそのものを学習させます。

発表者はこれを**継続的な学習ループ**と呼び、1 回限りの最適化ではなく、データを注ぎ込みながら時間とともに改善する仕組みだと説明しています。狙いは、事業にとって重要なタスクでフロンティア水準の性能を、わずかなコストで得ることです。

### 5.7 MAI licensed weights

前日の基調講演で Satya が発表した新しい仕組みとして、MAI licensed weights が紹介されました。MAI モデルの重み（ウェイト）そのものを、お客様自身の Azure テナントの中で使うライセンスを受けられる、というものです。

- フロンティアモデルから出発し、独自データを持ち込んで、すべて安全な Azure 環境の中で適応、変更、実験、調整ができます。
- オープンソースモデルと同じ柔軟性と制御が得られる一方で、Microsoft 内で学習された信頼できる MAI の重みを土台にできます。
- 提供は、Frontier Company のエンゲージメントを通じて行われます。

進め方は 2 通りあると整理されました。1 つは MAI licensed weights。もう 1 つは、Foundry と Microsoft 365 で、すぐに始められる簡単な方法で継続的な学習の道を歩み出す方法です。

### 5.8 Foundry でのデモの概要

デモの詳細は 6 章に書きます。要点は、Foundry でエージェントを実行し、観察し、最適化するという一連の流れです。

### 5.9 顧客事例：AT&T

Rajiv は、AT&T 社内の全社向けプラットフォーム「AW」を率いていると自己紹介しました。名称はトランスクリプトでは「Ask Getting New Workflows」と書き起こされており、音声認識の都合で正式名称を確定できません（「Ask AT&T Workflows」と思われるが未確認）。AW は昨年 6 月ごろに開始され、最初は本番化に苦労しましたが、今年に入って勢いが増し、12 月には 100 件目のユースケースを本番に投入する見込みだと述べています。

当初の課題は「エージェント型で問題を解けるか」でしたが、その答えは出ました。今の課題は、**どうすればより費用対効果が高く、正確で信頼でき、企業全体で再現できる形で解けるか**、そしてトークンの最適化もどう進めるかだといいます。

取り組みは次のとおりです。

1. サンプルのユースケースを選び、Microsoft のチームと共同でプロトタイプにしました。
2. ユースケースの評価データを、AT&T 社内のツール「Trustworthy AI」にかけ、ツール呼び出しの効率や応答の質などの指標を得ました。
3. その結果を Microsoft のチームに戻し、Microsoft 側が強化学習を実施してフィードバックを返しました。
4. そのフィードバックをもとにモデルを学習させました。

結果として、Code 2 Flash を使い、**ツール呼び出しの効率が 84% から 96% に向上**したと報告されています。対象のユースケースは、AT&T の複数のネットワークチームで使われているイベントベースのものです。

続いて Dhruva（綴りは音声認識の都合で確定できません）が、5G ネットワーク向けの自律エージェント EBAT（綴りは同様に確定できません）を紹介しました。話の前提として、2 つの課題が語られています。

- つながっているシステムはいつか必ず壊れ、そのとき信号の痕跡を残す。簡単なものもあれば、クラッシュログなどの非構造化ログの中に隠れた複雑なものもあり、処理が難しい。
- AT&T は 4G から 5G、6G へとネットワークを進化させている。自動運転車やセンサーが増える中で、ネットワークの切り替え時に接続が切れて地図が止まれば、体験が損なわれるだけでなく安全上の問題にもなりうる。

どちらにも共通する結論は、**問題を早期に検知して先回りで対処する「シフトレフト」**が必要だという点です。EBAT は 5G の数十億の信号を走査し、何千ものパターンを見つけたうえで、顧客に影響のある少数だけを処理に回します。これは人の規模では不可能だと述べています。

MAI モデルとの取り組みでは、推論の精度、効率、コストの 3 つを目標にしました。結果として、**トークンが 80% 削減**されたと報告しています。また、「前日に聞いたところでは、同じ結果を得るためのコストは 50 分の 1」とも述べました。

### 5.10 顧客事例：Optimizely

Optimizely は、大企業向けのソフトウェア提供企業で、コンテンツ管理、A/B テスト、デジタルの最適化を手がけています。大手ブランドの B2B・B2C、デジタル体験が主な顧客です。自社の機能にインテリジェンスを組み込みたい立場から、モデルのポストトレーニングに取り組んだと説明されました。

ユースケースは、A/B テストの素早い展開です。Black Friday を翌週に控えた小売業者が、10% オフのクーポンのフライアウト（ポップアップ）と、10 ドルのキャッシュバックの 2 案を試す、という例が示されました。技術者ではないマーチャンダイザーやマーケターが、Optimizely のエージェントに「10% オフのフライアウトと、10 ドルキャッシュバックのフライアウトを作って」と入力するだけで、そのバリエーションが作られる、という使い方です。

これまでは Frontier モデルを使い、エージェントがプロンプトを解析し、適切なツールを呼び出し、HTML や JavaScript を書き、画像も取得して部品全体を作っていました。登壇者はこれを「レールの上を走る、企業向けのバイブコーディング」と表現しています。ただし課題は 2 つありました。

- 非常に高価で、そのコストを顧客に転嫁すると成り立たなくなる。
- 動作が遅い。

そこで着想されたのが、「食料品店に行くのにフェラーリが必要か」というたとえです。「部品を 1 つ作る」という限られた用途に、それほどの計算能力はいらない、という仮説で、Microsoft から持ちかけられたモデルカスタマイズが、この 1 つのユースケースに MAI モデルをポストトレーニングする機会になりました。

精度は、**利用者とのやり取りの回数が少ないこと**で測っています（「画像が違う、直して」という往復が少ないほどよい）。目標は 1 回で内容が出来上がる状態にできるだけ近づけることです。

Anil は、実験用エージェントは 1 つの例に過ぎず、マーケティング部門向けにはこうしたユースケースが無数にあると述べました。実験を多く回す顧客ほど成果が良く、継続利用もされるため、月 6 件の実験を 100、200、400 件へ増やしたい、という狙いです。キャンペーン数、アカウントベースのマーケティング施策、公開ページ数、ブログ記事なども同様です。一方で顧客のトークン消費は爆発的に増え、コストと成果の最適化を考える段階に来ています。

進め方として、Optimizely はすでにベンチマークデータセットと評価を自前で用意し、自社のハーネスでエージェントを測れるようにしていました。そのうえで Microsoft と組んで MAI 1.1 Flash の Code モデル（聞こえた表記のまま）でエージェントを学習させ、「ボタン 1 回で」進むようなかたちで、短期間に非常に良い結果を得た、と述べています。将来は数百、数千のモデルを別々のユースケース向けに学習させる計画です。

Anil はもう 1 点、法務とエンジニアリングの観点から次の話をしました。もともとオープンウェイトのファインチューニングへ進むつもりでしたが、クローズドソースのファーストパーティモデルを土台にできる信頼性によって、オープンウェイト領域にあるかもしれない責任問題の多くが解消される、というものです。例として、Elvis Presley のディスコグラフィーが Claude と OpenAI のモデルで再現できてしまい、訴訟で敗れた事例があると語りました（発表内の発言であり、この事例の詳細は発話から確認できません）。外部向けにモデルを運用する会社にとって、そのリスクを共に負うパートナーがいることは大きな差別化要因だと述べています。

もう一方の登壇者は、自社の知的財産としての意味を次のように補足しました（話者の切り替わりは音声のみのため、帰属は確定できません）。

- マーケティング向けのベンチマークはソフトウェア工学や法務向けにはあっても存在しなかったため、マーケティング専用の評価フレームワークを自分たちで作った。
- ブランドに沿ったバリエーションを作るには、ブランドガイドライン、どのツールをどの順番で呼ぶか、何百万人の訪問者に配信できる形式にどう整えるか、といった専門知識が必要で、それが自社のインテリジェンスにあたる。
- その知識を使い、土台の MAI モデルを「賢く、同時に小さく」して、限られた作業を最も安く行わせる。

カスタマイズの本質は、ツール呼び出しをより一貫した方法にすることだと述べています。AT&T も同じで、フロンティアモデルは賢いものの、ツール呼び出しを自由にさせると外れることがあるため、正しい呼び出しに絞り込むのが狙いだという整理です。結果のスライドが示されましたが、具体的な数値は音声からは確認できません。

#### 5.11 質疑応答

質疑応答は短く、次の 3 件でした。

**質問 1（要約）：MAI licensed weights で要件に合わせてカスタマイズできるのは魅力的だ。**
Foundry での進め方と MAI licensed weights の違いが整理されました。Foundry では、MAI ベースのモデルでエージェントを作り、スキル、プロンプト、ハーネスを最適化し、重みの調整まで、すべて素早く簡単に始められます。オープンソースモデルのような管理の水準が欲しく、かつ重みの出所を信頼したい組織には、MAI licensed weights のプログラムが向いている、という回答です。提供は Frontier Company（FDE を専門とする組織）経由で、アカウントチームに相談するよう案内されました。

**質問 2：学習の対象は Flash と、もう 1 つだけか。すべての MAI モデルが対象か。学習後に自分でホストできるか。**
MAI licensed weights のプログラムは MAI ファミリーを対象とし、アカウントチームと Frontier Company が適したモデルを一緒に決めるという回答です。最終的にはマネージドコンピュートでホストする道もあるものの、モデルの安全性を保つため、Microsoft の推論エンジンを通す必要があると説明されました。

**質問 3：Microsoft のモデルは、いつ Cowork と Copilot Studio で使えるようになるか。**
具体的な日付はない、という回答です。ファーストパーティのチームと共同で開発・テストしており、準備ができたら発表する、と述べています。

最後の案内として、MAI のブースが Expo センターの F セクションにあること、調整や最適化については Foundry を試し、アカウントチームを通じて Foundry の大きなチームの支援を受けられること、MAI licensed weights はアカウント担当者に相談すれば Frontier Company につないでもらえることが挙げられました。

## 6. デモ・手順

デモは行われました。登壇者の同僚 Kevin が、Foundry でエージェントを実行・観察・最適化する流れを見せています。想定されたシナリオは、EC 企業のショッピングアシスタントです。カタログ内の商品について推薦を求められ、ツールでカタログを検索し、回答の根拠を示し、応答を組み立てます。画面の細部（ボタン名など）は音声からは確認できません。以下は語られた順の手順です。

**手順 1：エージェントの実行とトレース確認**

1. Kevin が作ったショッピングアシスタントに、「100 ドル以下のランニングシューズを探して」という問い合わせを投げます。
2. 実行している間に、構成が説明されます。エージェントは MAI モデルで動き、Python ランタイム上で稼働し、カタログ用のツール群を使えます。
3. 応答が返り、要望に合う商品がいくつか示されました。
4. エージェントのトレース全体を確認できます。複数のツール呼び出しが行われ、例えばデータベースを検索する商品検索ツール（find product）が呼ばれていることがわかります。

進行役の発表者は、これを大規模に運用する EC のプラットフォームに置き換えて理解を確認しました。質問のたびにこのシステムが動き、複数回のツール呼び出しが走るため、大きなモデルでは高価になりうる、というやり取りです。

Kevin は、このプレイグラウンドの画面は構築・試作・デバッグには良いが、本番のトレースを手作業で見るのは時間がかかりすぎる、と述べています。

**手順 2：Insights による問題の洗い出し**

1. エージェントを本番で動かすと大量のトレースが溜まります。Insights では、そのトレースに対する確認を定期実行できます。
2. 着目したい観点として、トークン使用量やコストの最小化、出力の品質向上、ハルシネーション（事実と異なる出力）の最小化、独自の優先事項を指定できます。
3. 表示されたのは、実際のトラフィックから得られた指摘です。中程度の重大度で最初に挙がったのは、コストとトークンに関するもので、商品検索ツールの検索が 3 回別々に行われており、同じことを繰り返す非効率な動きになっていると指摘していました。
4. これで、どこに注力して改善すべきかがわかります。

**手順 3：Agent Optimizer による最適化**

1. Optimize（最適化）タブを開きます。すでに数回の実行が走っており、最初の実行は完了まで約 3 時間かかったものです。
2. 最適化の前に、目標と基準線（ベースライン）が必要です。Agent Optimizer には、根拠のあるデータセットを渡します。例として、検索の問い合わせの集まり（推薦の例としてホンダのオートバイ用ウィンドシールドなど）と、推薦が成功かどうかを判断する基準が示されました。ゴールドスタンダードのデータを含む大きなデータセットです。
3. Optimize はまず、このタスクのベースラインのスコア（精度スコアに近いもの）を計算します。今回は約 72% でした。
4. 次に Agent Optimizer は、システムプロンプトに手を入れ、スキルとツールの定義を書き換え、複数の試行と実験を行いました。
5. 最良の介入は候補 3 で、ツールの使い方を最適化したものです。精度が約 15 ポイント向上しました。この段階ではモデルの重みは変更しておらず、プロンプト、スキル、ツールだけの改善です。
6. 最良候補の差分を見ると、左側に元のツール定義があります。商品検索ツール（find product）の説明は元は「商品カタログを検索する」という 1 行でした。Agent Optimizer は、ツールの働きの詳しい説明、フィルターの使い方、同じクエリを 2 回実行することへの注意事項を加えました。これは、先に見つかった問題に対応しています。

**手順 4：強化学習によるファインチューニング**

1. さらに性能を上げるために、学習を使います。ここでは強化学習によるファインチューニングです。
2. 学習ジョブを始めるには、Agent Optimizer と同じくラベル付きデータセットが必要です。強化学習を選び、MAI Code Flash ファミリーのいずれかのモデルを選べます。
3. データセットをアップロードします。強化学習では、カスタムのグレーダー（採点関数）か、用意されているグレーダーを追加する必要があります。
4. 仕組みは、モデルがタスクに対して異なる解を試し、グレーダーが数値のスコアを付け、それに応じてモデルが調整される、というものです。

特にうまくいった学習の実行が示されました。所要時間は約 26 時間で、ダッシュボードにはレイテンシやツール使用状況も出ます。上段の 2 つのグラフに注目しています。

- 左：検証データと学習データの平均報酬。学習中に見ていないデータである検証データに注目します。汎化の良い目安だからです。ステップ 0 の平均報酬は約 83% で、学習の終わりまでに **98%** まで上がりました。
- 右：トークン使用量。検証データでの推論トークンの平均が、約 310 から約 180 に減りました。

進行役は、「学習すると、より良く、かつ安くなる」と整理しました。理由は 2 つ挙げられています。1 つは、モデルが専門性を得るとプロンプトに対する推論に要するトークンが減ること。もう 1 つは、Flash モデルで実行できるので 1 トークンあたりの単価が低いこと。これにより精度が上がりながらコストが下がる、という説明です。

なお、進行役は「ポストトレーニングは難しい」という先入観に対し、Foundry なら誰でもデータセットと採点関数があれば実行できる、と述べ、Kevin も同意しました。

## 7. 注意点・発表者の気付き

- **Foundry への Code モデル提供は近日予定**です。現時点で GitHub では利用できますが、Foundry は今後の提供と説明されました。
- Code 2 と Code 2 Flash の性能・コスト比較は、発表者が前日の基調講演の数字として紹介したものです。比較対象の名称は音声認識の都合で表記が確定できません。
- 自社データで調整するには、**評価データセットと採点基準が前提**です。Agent Optimizer にも強化学習にも、ラベル付きのデータセットが必要です。Optimizely は、マーケティング向けのベンチマークがなかったため、評価フレームワークを自分たちで作ったと述べています。
- デモの最適化の実行は 3 時間、強化学習は 26 時間かかっています。

- MAI licensed weights で自分でホストする道はありますが、安全性のため、Microsoft の推論エンジンを通す必要があります。
- Cowork と Copilot Studio での MAI モデルの提供時期は、発表では明らかにされていません。
- Alaska Airlines の例は、前日の基調講演の内容として触れられただけで、このセッションでは詳細は語られていません。

## 9. まとめ

MAI モデルは、すでに Excel や PowerPoint、Dragon Copilot、Dynamics 365 で使われており、前日には Code 2、Code 2 Flash、Cyber 2、Image 2.7、MAI Realtime が加わりました。コーディングモデルは GitHub で利用でき、Foundry には近日提供される予定です。

自社の業務で高い性能を安く得るための方法として、評価、プロンプト・ツール・エージェントの調整、モデルの学習という継続的な学習ループが示されました。Foundry のデモでは、Insights で問題を見つけ、Agent Optimizer で精度を約 15 ポイント上げ、強化学習で検証報酬を 98% まで高めつつトークンを減らす流れが確認できました。AT&T はツール呼び出し効率の向上とトークン削減、Optimizely は用途を絞ったモデルでのコスト・速度・精度の改善を目指しています。

より深い制御と、重みの出所への信頼を求める組織には、Frontier Company を通じて提供される MAI licensed weights があります。始めるなら、Foundry や Microsoft 365 での取り組みと、アカウントチームへの相談が案内されました。
