## 5. 発表内容の詳細

### 5.1 Marketplace で売る理由

Olivia 氏は、特に新しい会社や新製品にとって、調達が企業 IT における摩擦の最大要因の 1 つだと説明します。Marketplace に掲載し、標準のクリックスルー契約を使い、顧客自身のテナントにデプロイすることで、この摩擦をかなり減らせるという説明です。

さらに、次の利点が挙げられました。

- チャネルパートナーを通じた販売ができ、パートナーの既存の顧客関係を使える。
- 世界中の購入者に届く。
- 購入者の関心を購入につなげる、プロダクト主導の成長を取り込める。
- プログラムの特典とプライベートオファーで、より大きな案件を成立させられる。

### 5.2 全体の枠組み

事前に答えておくべき問いが、3 段階に対応づけられています。

| 段階 | 判断 | 問い |
| --- | --- | --- |
| 構築 | サーフェス | 購入者はすでにどこで仕事をしているか。どうやって見つけてもらうか |
| 構築 | ランタイム | エージェントはどこで動くか。誰が運用するか。AI の費用を誰が払うか |
| 収益化 | 取引 | 顧客はどう購入するか（オファーの種類と課金モデル）。関心を販売にどう変えるか |
| 拡大 | 成長 | より多くの購入者にどう届け、売上をどう伸ばすか |

これらすべての下に、意図的に最下層として「堀」、つまり競合がまねできない自社だけのものが置かれています。上のあらゆる判断の形を決めるためです。

### 5.2.1 堀のテスト

堀が成り立たなければ、他のことはあまり意味がない、として、設計中に何度も見直せる 4 つの問いが示されました。

1. 競合が手作業でまねできるか。今のツールがあれば、小さなチームがどれくらいの期間でコードを作れてしまうか。
2. 同じプラットフォームやモデルを使う競合がまねできるか。モデル、Copilot Studio、Microsoft Foundry は借りるもので誰でも使えるため、それだけでは堀にならない。
3. 使われるほど良くなるか。使用状況のテレメトリで成果を改善する学習ループは、時間とともに効いてくる。
4. 競合が現実的に競うには何が必要か。

自社で持てるものとして、独自のデータとベースライン、深いワークフロー統合、ドメインの専門性、顧客の信頼が挙がりました。既存製品にエージェントを足す場合は、顧客基盤、コードベース、サポート体制もすでに堀の一部です。新規の場合は、創業者の強みやコアの専門性が出発点になります。

現実の脅威として、プラットフォーム事業者がその機能を取り込む可能性、コモディティ化し得るモデルへの依存、対話ごとの管理できないコストも確認するよう勧められました。

堀を持つ例が 2 社紹介されています。

- **Abnormal AI**：メールとアイデンティティのセキュリティ企業。8 年分のデータで学習した独自の行動モデルを持ち、各組織に固有の数千のシグナルから、顧客ごとのベースラインを作っています。
- **Promogoat**：エージェント型の広告代理店。40 年の経験を持つ創業者が作り、欧州で大手消費者ブランドの大規模キャンペーンを手がけてきた評判があります。

Abnormal AI の差別化はデータと独自モデル、Promogoat の差別化は評判と専門性だ、と整理されています。

### 5.3 構築①：サーフェス

顧客に届ける方法は主に 2 つです。

**Microsoft 365 に置く方法**：エージェントを Copilot や Teams など、購入者がすでに仕事をしている場所に置きます。顧客の IT 管理者が、利用可能にするかの確認、承認、統制を行います。UI に時間をかけず、エージェントのワークフローとデータのロジックに資源を集中できるため、市場投入が早くなります。購入者のワークフローにはエージェントストア経由で表示され、リンクした SaaS オファーで購入されます。世界中の数百万の Microsoft 365 利用者という既存の市場も使えます。

**Azure と Foundry でフルスタックを作る方法**：UI、ランタイム、モデルのルーティングを自分で持ち、ホスティングと販売方法も自分で決めます。SaaS、コンテナー、マネージドアプリケーションから選べます。API を公開して Foundry でエージェントを連携させる「ヘッドレス」のパターンもここに入り、データガバナンスが重要になります。Microsoft 365 の外の購入者にも届き、より深いカスタマイズや、購入者がデータを自分の管理下に置けるオファー種別の選択ができます。

事例として Pangea Data が紹介されました。誤診や治療不足の可能性がある患者を見つける、AI 搭載の臨床プラットフォームを持つ初期段階の医療企業です。機微な患者の健康記録を分析するため、顧客のファイアウォールの内側で動かす必要があり、データが組織の外に出ないようにしています。ここでの問いは、購入者の意思決定がどこで行われるか、データはどこにとどまる必要があるか、の 2 つです。

2 つの方法は二者択一ではなく、組み合わせた強力なソリューションも多いと言います。Copilot エージェントを「玄関」にして、Azure を「裏のエンジン」にする形です。玄関は購入者がいる場所（Teams や Copilot など）、エンジンは差別化のロジックとデータが置かれる場所です。Abnormal AI はこの例で、サーフェスは API を通じて Outlook や Teams を含む顧客の Microsoft 365 のワークフローとつながり、特定のメールクライアントに縛られていません。エンジンは自社の行動 AI モデルで、Marketplace のプライベートオファーで販売しています。

早めに決める設計上の問いは、エージェントを誰が呼び出すか（Teams の人、別のエージェント、API 呼び出し）です。

### 5.4 構築②：ランタイム

ランタイムは、アーキテクチャと事業モデルがぶつかる場所で、後から変えると高くつく選択が多いと強調されました。検討するのは 3 つの要素です。

**ホスティング**：まず顧客と、データコンプライアンスに対するリスク許容度から始めます。規制産業は自社の機密データをマルチテナントの SaaS に送ることに慎重で、小規模な顧客は簡単なので SaaS を好むことが多いそうです。ワークロードの大きさは、通常のクラウドと同様に見積もります。常時稼働が必要か、休止できるか、バースト性や対話の頻度はどうか、データ量やコンテキストの大きさはどうか。医用画像を読むエージェントと、オンラインレビューを要約するエージェントでは、必要なものがまったく違います。一般則として、App Service は小さく予測可能なワークロード向き、Kubernetes は重いワークロード向きです。低い量では App Service が大幅に安く、月間の量が増えると Kubernetes のコスト曲線が平らになり、差が縮まります。

**品質とモデル選択**：複数モデルのワークフローが増えているので、ソリューション全体で 1 つではなく、タスクごとにモデルを選びます。品質基準を満たす最小のモデルを使うと、安く速くなります。ファインチューニングしたモデルやオープンモデルは、自社の知的財産の一部にもなります。モデルの順位は常に変わるので、継続的に再テストが必要で、Microsoft Foundry のモデルのリーダーボードで品質、安全性、コスト、スループットを比較できます。推論コストの管理も早めに計画し、プロンプトとコンテキストのキャッシュ、モデルルーティング、トークン最適化を使います。

**容量と料金モデル**：従量課金は柔軟で、サンドボックスや低ボリュームに向きますが、スループットに上限があります。Microsoft はプロビジョンドスループットを提供しており、容量を確保して、需要が急増してもレイテンシーを予測可能に保ちます。ただし一部のモデルでしか使えないため、アーキテクチャの選択で考慮する必要があります。

### 5.5 収益化①：オファーの種類

ランタイムの選択は、公開するオファーの種類に直結します。

| オファー | 動く場所と特徴 | 留意点 |
| --- | --- | --- |
| SaaS | 自社のテナントで、中央でホストする。体験を制御でき、導入が速い。最も簡単な出発点 | AI の推論費用をすべて自社が負担するので、それを見込んで価格を決める |
| コンテナー | 顧客の Azure 上の Kubernetes で動く。顧客が拡張、ネットワーク、データアクセスを管理する | 顧客は Azure の消費分を支払い、自社はデプロイとサポートの作業が増える |
| マネージドアプリケーション | 顧客の Azure サブスクリプションにデプロイされ、顧客がデータの管理を保つ。更新は通常、自社が管理する | 同上 |

購入者が Teams や Copilot にいる場合は、Microsoft 365 のエージェントを追加し、SaaS オファーにリンクして収益化します。

AI を顧客の境界内に置くべきだという圧力は高まっており、顧客はデータをどこで処理し誰が運用するかを早い段階で尋ねます。例では、Abnormal AI はデータが API 経由で届くため SaaS、Pangea Data は患者データを外に出せないので、顧客の Azure 環境で動くマネージドアプリケーションです。

> 注意：Partner Center でオファーの種類を一度選ぶと、あとから変更できません。変えたいときは、新しいオファーを最初から作る必要があります。

そのため、データが最終的にどこにあるか、誰が運用するか、誰が AI の費用を払うか、の 3 つの問いで事前によく考えるよう勧められています。

### 5.6 収益化②：価格設計

エージェントの価格がどうあるべきかは、市場全体がまだ模索中だと前置きされています。出発点は競合の価格を見ることですが、エージェントでは対話ごとの推論、API、ストレージという売上原価も考慮し、実際に利益が出る価格にします。3 つの基本モデルが示されました。

- **サブスクリプション**：定額の繰り返し課金。購入者にとって予測しやすく、自社もキャッシュフローが予測できる。
- **従量課金**：トークン、API 呼び出し、ワークフロー実行などの消費単位で課金する。コストと連動するが、使用量の予測が難しい購入者には予測しにくい。
- **成果課金**：測定できる成果ごとに課金する。公平に感じられるが、支出が変動するので、自社のキャッシュフローも考える必要がある。

顧客の種類ごとに異なるモデルを提供できます。最近多く見られるのは、CIO や CFO が予測可能な価格に傾いていることで、トークン起因のコスト変動を警戒している、という話でした。

上位の枠組みとして、スターター、プロフェッショナル、エンタープライズの 3 つの階層もよく機能します。スターターは早期導入の入口を下げ、プロフェッショナルは製品をすでに知る顧客向けに機能とサポートを加え、エンタープライズは SLA 付きのミッションクリティカルで大規模な導入向けです。対象セグメントの予算事情を反映した階層にするよう勧められました。

### 5.7 拡大①：Marketplace の導入ステップ

ここから Rajesh 氏の担当です。エージェントを公開するのは最終目標ではなく、売上を伸ばすことが目的で、Marketplace は収益を伸ばすプラットフォームだと説明されました。多くのソフトウェア企業は、はしごを 1 段ずつ登る、または一気にエスカレーターで進む形で段階的に導入しています。

**ステップ 1：Contact Me（問い合わせ）掲載**。最も簡単な入口で、デジタルな看板に自社名を出すようなものです。Marketplace には数百万の目が集まり、資料やデモ環境を用意したオファーへのリードを作れます。顧客は掲載から連絡してきて、販売プロセスは Marketplace の外で自社が管理します。マーケティングの A/B テストにも向きます。2 種類のメッセージを用意し、バナー広告やシンジケートされたリサーチコンテンツで、どちらが掲載ページへの訪問を増やすかを安価に確認できます。

**ステップ 2：取引可能にする**。実際に Marketplace を通じてソフトウェアを販売する段階で、Microsoft が請求と回収を引き受けます。Microsoft が顧客に請求し、代金を回収し、自社に支払うので、売掛金と請求にまつわる業務を Marketplace に任せられます。大企業の顧客は多くの場合、サプライヤー契約への登録を求め、典型的には 3〜6 か月かかります。Marketplace 経由なら、Microsoft が請求と回収を管理するため、その登録を省略でき、営業サイクルが短くなります。

**ステップ 3：共同販売の特典**。Marketplace 経由の請求売上が増えるほど解放される特典で、マイレージのようなものです。マーケティング特典、営業の市場投入（GTM）特典、そして Azure クレジットがあります。Marketplace 経由の請求売上に応じて、最大 200 万（通貨単位は発話では確認できません）の Azure クレジットが提供され、顧客との追加案件の成約に使えます。例えば、案件でできることをすべて提示しても顧客が「ほかに何かないか」と言うときに、このクレジットが後押しになります。

Microsoft には 2 万人のフィールドセラーがいますが、共同販売で動いてくれるのは、取引（トランザクション）をしたときだけです。セラーへの報酬が、パートナーが生み出した取引に基づいているためです。共同販売の特典の階層に到達する唯一の方法は、Marketplace で取引することだと明言されました。

**ステップ 4：Azure 消費コミットメント（MACC）**。顧客が Microsoft と交わす、一定量の Azure を消費する約束で、見返りに割引を受けます。発話では「Mac」と聞こえ、文脈から MACC に当たります。金額は Microsoft の決算資料で確認でき、数千の顧客で数十億ドル規模です。Marketplace で取引すると、購入額がこのコミットメントから直接差し引かれます。顧客がソフトを気に入ったのに予算がない場合でも、新たに予算を探す必要がなく、コミットメントの残高から差し引けます。

最終目標は、企業の調達の領域に入ることだと説明されました。

### 5.8 拡大②：成長の数値

Marketplace の実績として、次の数値が示されました。

| 項目 | 内容 |
| --- | --- |
| 成長 | 過去 3 年間、毎年 100% 成長。Marketplace で取引されるソフトウェアの売上は毎年倍増 |
| 規模 | 現在、数十億ドル規模のソフトウェアが取引されている |
| 地域 | 取引の 60% が米国外。140 か国で利用でき、17 通貨で取引できる |
| 浸透 | Microsoft とクラウドのコミットメントを持つ顧客のほぼすべてが、Marketplace で取引している |

ここまでは直接販売の話ですが、チャネル経由でも同じことが当てはまります。

- **マルチパーティプライベートオファー（MPO）**：顧客が特定のチャネルパートナーから買いたい場合に、取引をそのパートナーに送り、パートナーが最終顧客との取引を完了します。顧客の MACC からの差し引きも行われます。
- **リセール対応オファー（REO）**：地域の専門性や現地の足がかりがない市場で、リセラーに自社ソフトの再販を許可します。130 か国で、チャネルパートナーを指定して再販を任せられます。

MPO でも REO でも、チャネルを使うと案件の規模が増え、倍になると述べられています。公開したエージェントを Marketplace で販売するときは、チャネルを巻き込むことが強く勧められ、チャネルの導入と共同での販売も支援できるそうです。

### 5.9 まとめの枠組みと次のステップ

Rajesh 氏はあらためて枠組みを振り返りました。サーフェスとランタイムは購入者のいる場所から始めること、構築した後に誰が運用するかを考えること、データを自社が持つのか顧客が持つのかが取引モデルを決めること、そのうえで拡大の手段があり、すべてが「堀」の概念の中にあること、です。競争力のあるものを作っているなら、Microsoft Marketplace が成功を支援できる、という整理でした。

次のステップとして、次の資料が案内されています。

1. **App Advisor**：自分で学びたい人向けの、関心のあるテーマに沿ったガイド付きのツアーです。Marketplace に慣れたら、App Advisor から直接ソリューションを公開することもできます。Partner Center を使いたくない場合の選択肢として説明されました。
2. **Frontier Accelerate for Marketplace**：会場のパートナービジネスのパビリオンにあり、Marketplace を通じて成長するための GTM 特典について相談できます。

## 7. 注意点・発表者の気付き

- Partner Center でオファーの種類を選ぶと変更できず、変更するには新しいオファーをゼロから作る必要があります。
- ホスティング、モデル、容量に関する選択は、あとから変えるのが高くつくため、最初に決めます。
- プロビジョンドスループットは一部のモデルでしか使えないので、アーキテクチャの選択で考慮します。
- モデルの順位は常に変わるので、継続的な再テストが必要です。
- Microsoft Foundry、Copilot Studio、モデルは誰でも借りられるため、それだけでは堀になりません。
- 従量課金は購入者に予測しにくく、成果課金は自社の支出が変動するので、どちらもキャッシュフローとの兼ね合いに注意します。
- 共同販売でフィールドセラーと組むには、Marketplace での取引が必須です。

## 8. 利用者にとっての利点

ここでの「お客様」は、Marketplace で販売するソフトウェア企業です。語られた利点は次のとおりです。

- 標準のクリックスルー契約と顧客自身のテナントへのデプロイで、調達の摩擦が減ります。
- Microsoft が請求と回収を行うため、売掛金の業務を任せられ、3〜6 か月かかる大企業のサプライヤー契約登録も省けます。
- 共同販売の特典として、マーケティングと GTM の支援、最大 200 万の Azure クレジット、2 万人のフィールドセラーとの連携が使えます。
- 購入額を顧客の Azure 消費コミットメントから差し引けるため、顧客の予算の壁が低くなります。
- Marketplace は 140 か国、17 通貨に対応し、取引の 60% が米国外です。過去 3 年間は毎年 100% 成長しています。
- チャネルを使うと、案件の規模が倍になると説明されています。

## 9. まとめ

エージェントを Marketplace で売るには、作る前に、購入者がどこにいるか、どこで動かすか、誰が運用して誰が AI の費用を払うか、どう課金するかを決めておく必要があります。オファーの種類は後から変えられないため、特に重要です。その土台には、競合がまねできない「堀」があります。

販売の面では、Contact Me の掲載から始めて取引可能にし、共同販売の特典と顧客の Azure 消費コミットメントを使い、チャネルパートナーも巻き込むのが道筋として示されました。学習用の資料として、App Advisor、Frontier Accelerate for Marketplace、AI Envisioning シリーズ、パートナーコミュニティが案内されています。
