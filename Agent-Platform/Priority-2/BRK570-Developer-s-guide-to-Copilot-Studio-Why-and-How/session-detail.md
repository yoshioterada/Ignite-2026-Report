# BRK570 Developer's guide to Copilot Studio - Why and How

## 1. はじめに

このセッションは、「Copilot Studio はローコードのツールだから、自分たち開発者には関係ない」と考えている開発者に向けた発表です。Git やプルリクエスト（PR）はどうするのか、GUI のドラッグ＆ドロップで開発のライフサイクルに組み込めるのか、といった疑問に答える内容になっています。

発表の中心は、2 人目の発表者による**ライブのコードデモ**です。既存の Copilot Studio エージェントを Git 管理下に置き、ブランチ、PR、マージを通して開発環境・本番環境へ配備する流れが、コマンドライン（CLI）とコーディングエージェントを使って実演されました。さらに、このカンファレンス期間中に作られたという、米国の空港の気象情報と航空情報を扱うエージェントも紹介されています。

主張はひとつです。**Copilot Studio は「ローコードのお絵かきツール」ではなく、ソフトウェアを構築・配備できるプラットフォームである**。そのうえで、プロセスの担当者、開発者、管理者（ガバナンス担当）の 3 者が同じものを一緒に扱えるようにする、という考え方が示されました。

## 4. 発表者が伝えたいメッセージ

Seth は、このセッションの目的を「Copilot Studio はプラットフォームである」と伝えることだと述べています。ソフトウェアを構築して配備でき、しかもプロセス担当者、開発者、管理者の 3 つの視点を一緒に満たせる、という位置づけです。

Matt は、Copilot Studio が「開発サービス、開発者プラットフォーム」として語られるようになった理由を、次の 2 点で説明しました。

- コーディングエージェントが扱える形（CLI とファイル）で Copilot Studio が公開されたこと。
- 業界で一般的な SDL を、Git を土台にして Copilot Studio のエージェントにも適用できること。

後者について、Matt は「Microsoft として『こうもできる、ああもできる』と並べるのではなく、**『こうやるのです』という見解を示したい**」と話しています。新しい仕組みを発明せず Git を選んだ理由は、「世の中のコーディングエージェントはすべて Git の扱い方を理解しており、開発者コミュニティの多くも Git に慣れているから」と説明されました。

Seth の締めくくりは、Copilot Studio がかつての Power Virtual Agent から進化し、全員が同じコードを扱ってリアルタイムに前進できる開発者向けのストーリーを持つようになった、という内容です。「Copilot Studio を無視するのではなく、チームとしてどう進めるかが問題だ」とも述べています。

## 5. 発表内容の詳細

### 5.1 今日の Copilot Studio は何が違うのか

Matt は、Copilot Studio が現在「2 つのもの」として存在していると説明しています。

- 標準のハーネス
- Microsoft Copilot Harness（Matt によると、先週マーケティング部門が名称を変更。以前は GitHub Copilot Harness と呼ばれていた）

この発表で扱うのは後者です。Matt は、このハーネスによって、標準のハーネスでは扱いにくかった領域が使えるようになったと述べています。具体的には、トピックの扱い、ワークフロー、複数の要素をまとめて調整する処理の複雑さです。こちらのハーネスは、ツール、スキル、機能、調整役のワークフローを備えたエージェントを中心に構成されている、と説明されました。Matt 自身はこれまで 1 年ほど「GitHub Copilot harness」と呼んでいたため、話の途中で旧名称が出てしまうとも断っています。

また、**Copilot managed runtime** にも触れています。これは、コードでアプリを作り、マネージドなプラットフォーム上で提供するための機能です。Matt は「今週一般提供（GA）になったと思う」と話しました。この機能には 2 つの主要な側面があり、1 つは今週公開されたアプリの構築方法、もう 1 つは Copilot Studio のマネージドランタイム内でエージェントを構築する方法で、Copilot Studio はこの後者の重要な部分だと説明されています。このセッションはコードを中心に進めつつ、Copilot Studio の画面とコードの間を行き来して、UI を使う人とコードを使う人がどう協力できるかを見せる、という構成です。

### 5.2 Ms. Agent CLI とエージェントのファイル構成

会場では、日常的に使うコーディング支援ツール（Gemini、Claude Code、GitHub Copilot、Cowork など）を尋ねる挙手がありました。Matt は、こうしたコンソール型のツールが CLI と会話しながら開発できることに注目し、Copilot Studio にも複数の入口を用意したと説明しています。

その 1 つが **Ms. Agent CLI** です。Copilot managed runtime のエージェントのエコシステムに特化して作られています。Power Platform CLI（PAC）でも Copilot の名前空間を担当チームが持っていますが、Ms. Agent CLI は開発者向けの機能強化に集中し、PAC は管理運用の側へ寄せていく方針です。両者は役割を分けつつあります。理由は、エージェントが理解しやすいのは、用途を絞ったツールセットだからだと説明されています。

Ms. Agent CLI で次のことが、Copilot Studio の画面に触れずにできるようになったと述べられました。

- まったく新しいエージェントをゼロから開発する
- そのエージェントを Copilot Studio に追加する
- Copilot Studio でエージェントをテストする
- 評価（エバリュエーション）を作成し、実行する

使うコーディングエージェントは自由で、GitHub Copilot に縛られることはありません。

Copilot Studio のエージェントをディスク上で見ると、プロジェクトは**ファイルの集まり**です。ファイルシステムに慣れた人にとって意味が分かるように整理されている、と説明されました。構成は次のとおりです。

- ルートにエージェントがある。
- 設定の仕組みがあり、複数のエージェント、その配備先（デプロイメント）、種類を識別する。
- 現時点で公開されているエージェントの種類は 2 つ。Copilot Studio エージェントと、Copilot Studio ワークフロー。
- その中にスキルを配置できる。スキルのカタログから取得したものや、エージェントに作らせたものをそのまま置ける。
- コネクタと MCP の機能にも対応している。

これらはすべて、Ms. Agent CLI と、Copilot Studio 向けの Visual Studio Code 拡張機能が扱える構成になっています。VS Code 拡張機能の存在を知っているかの挙手では、知っている人は数人でした。

### 5.3 開発の始め方

これまでの Copilot Studio は、UI を開いてプロンプトの入力欄を見つめるところから始める人が多かったと Matt は述べています。新しい方法では、CLI を通じたエージェントとの会話で、アイデアを練り、計画を作り、その結果として Copilot Studio エージェントを作成できます。この方法の詳細は、Power Platform Community Conference（PPCC）などで話したことがあり、今回は説明を省くとのことです。

大事なのは、どこから始めてもよいことです。Copilot Studio の UI から始める、Cowork でエージェントを作って、それを自分のファイルシステムと SDL・管理基盤に取り込む、といった選択ができます。

### 5.4 SDL を Git ベースで適用する

このアプローチの核心として、業界で適切と考えられる**ソフトウェア開発ライフサイクル（SDL）を、Copilot Studio のエージェントと関連部品に適用できる**ことが挙げられました。これまでも部分的には提供されてきたものの、隙間があった。それを GitOps、Azure DevOps、あるいは独自スクリプトで一貫して使える形にまとめようとしている、という説明です。

> 注意：Matt は、デモで見せる内容は**今すぐ利用できるものばかり**で、1 点だけ例外があると明言しています。まだ提供していないのは、Ms. Agent CLI によるサービスプリンシパルベースの配備に対する Git アクションと Git 連携です。その基盤は今週投入されたため、比較的近いうちに提供される予定ですが、時期の具体的な日付は発話では語られていません。

### 5.5 VS Code 拡張機能の機能

デモの中で、VS Code の拡張機能について次の機能が紹介されました。詳細は 6 章に記載します。

- Copilot Studio のプロジェクトを開くと、Copilot Studio 用の言語サーバーが有効になり、エージェントやワークフローを認識する。
- 環境の再接続（reattach）機能があり、環境間の移動ができる。
- ワークフローに必要な接続（コネクション）を一覧し、設定を求められる。同じ一覧は CLI（Ms. Agent の deployment connections）でも取得できる。
- ワークフローが Copilot Studio 内でどう見えるかを、VS Code 内で図として確認できる。
- 「peek remote changes」（リモートの変更の確認）。Git に似ているが、Copilot Studio 向けの機能と説明されています。

### 5.6 コーディングエージェントの使い方についての補足

Matt は、デモで見せたコーディングエージェントは、単に操作を代行するだけでなく、テスト結果を踏まえて「何を改善できるか」と議論する相手にもなると話しています。「より良い」は主観的な言葉ですが、名前の付け方を逆にしてはどうか、といった創造的な提案が返ってくることが多いそうです。NHL エージェントの 3 つのスキルは、この種の対話から生まれたと述べています。

また、同じ手法が Gemini、Claude でも動くことを、3 つの主要なツールセットでテスト済みだと説明しました。

### 5.7 評価（エバリュエーション）

CLI からは評価を作成して Copilot Studio に反映し、評価の実行までできます。チームのプロダクトマネージャーである Sarah Critchley 氏は、この領域に非常に詳しく、エージェントを作って、検証、評価、再調整を何時間も回し続けて思いどおりに動くまで仕上げるそうです。ただし、評価の実演自体は行われていません。

## 6. デモ・手順

画面を使ったライブデモが行われました。画面の細部は音声からは確認できないため、語られた範囲で、実施順に書きます。冒頭でターミナルの接続が切れていたため再接続してから始まっています。

### 6.1 デモ 1：既存の Copilot Studio ソリューションを Git に取り込む

前提は、UI や Cowork を使って、Copilot Studio にすでにエージェントとワークフローが作成されている状況です。これを引き継いで配備パイプラインに載せるため、まずソース管理が理解できる形に出す、という流れでした。

1. GitHub Copilot に、その環境にあるすべてのエージェントとワークフローを、Git に紐付いたローカルの作業ディレクトリに作成（クローン）するよう依頼した。
2. 環境名の綴りを誤って入力したため、GitHub Copilot が確認を求めてきた。Ms. Agent CLI から読み取った環境の一覧の中から、正しい環境を選んだ。
3. GitHub Copilot は、CLI のヘルプ、環境、環境内のエージェントを確認したうえで、ローカルへの作成を開始した。会話型の操作だが、CLI を直接使えば同じことは可能で、その場合はコマンドを 1 つずつ実行する必要がある、と補足された。
4. 完了後、VS Code を開くよう依頼した。Copilot Studio のプロジェクトであることが認識され、Copilot Studio 言語サーバーが有効になった。エージェントワークフローと Copilot Studio エージェントが検出された。
5. 7 つの資産が開かれた。店舗アソシエイト向けのアシスタント（store associate assistants）のエージェントを見ると、ツールが 2 つ、スキルが 3 つあった。スキルの 1 つである返金計算（refund calculator）には、Python のコンポーネントとスキルの Markdown が含まれていた。これらはソース管理へ移せる状態になった。
6. 拡張機能で未接続の項目があり、環境へのクイック再接続（reattach）を実行した。ワークフローを特定の環境に再接続しようとすると、接続が未設定のため設定を求められた。
7. ワークフローごとの接続一覧を表示した。このワークフローには 5 つの接続があり、設定が必要だった（発話では「4 つ、5 つ」と言い直しており、最終的に 5 つと読み取れます）。
8. ワークフローを選び、Copilot Studio で作成したときの見え方を VS Code 内で表示できることを示した。

この例は、Copilot Studio チームが用意したスターターソリューションで、エージェントとワークフローが連携して動くものです。元は Power Platform のソリューションとして開発環境に配備されていました。そこから Git に移し、今後はソリューションではなく Git で管理していく、という想定です。理由は、ブランチ、フォーク、マージといった SDL の機能一式を使いたいからだと説明されました。

### 6.2 デモ 2：NHL ニュースデスクエージェントのブランチ、PR、環境への配備

次に、もう少し単純なエージェントに切り替えました。Matt が数日前に作成した NHL ニュースデスクです。公開されている情報源を使い、ホッケーの試合結果、スコア、ロースター（選手名簿）とその変更を把握するエージェントで、Copilot Studio で作られています。

構成は次のとおりです。

- スキルが 3 つ：試合レポート、ニュース要約、統計レポート
- ナレッジソースが 1 つ：NHL の Web サイト（情報は豊富だが探しにくい、と Matt は説明。GitHub Harness on Copilot Studio は情報探しが得意）

手順は次のとおりです。

1. エージェントのフォルダーで、Ms. Agent の `agent show` を実行した。NHL エージェントと、デプロイメントが 1 つ表示された。開発・テスト・本番と環境を分けるのが目的で、1 つの環境だけで作業すべきではないと説明された。
2. 開発インスタンスのエージェントに「昨夜行われた試合」を CLI の `ask` コマンドで尋ねた。エージェントは設定ファイルの定義を読み、利用可能なデプロイメントから開発用を選び、認証して問い合わせを行う。人が読みやすい形で結果が返った。
3. `ask` を JSON の非対話オプションで実行すると、エージェントへの活動イベントのストリームがそのまま返る。これを別のエージェントが分析し、その場で調整内容を決められる。スキル 3 つは、このようなテスト体験とのやり取りを重ねて、試合結果や統計の表示方法を洗練させる中で作られた、と説明された。
4. GitHub Copilot を同じディレクトリに向けた。ブランチ（baseline-1）が表示された。このブランチでは、リモート側で事前にモデルを変更してあった。使っていたモデル（「Astra 6」から「Astra 62」と聞こえました。音声認識の都合で表記が確定できません）は高価であることから、変更する流れになった。
5. Copilot Studio 側で、NHL ニュースデスクのモデル設定を `auto` モードに変更して保存した。どちら側からでも変更できることを強調していた。`auto` は、クエリごとに最適なモデルを Copilot Studio が利用可能なモデルから選ぶ設定で、必ずしも最もコスト効率が良いとは限らない、と説明された。
6. 拡張機能の「peek remote changes」を実行した。リモートのデプロイメントのモデルが「Astra 62」から Auto に変わったことが検出されたが、まだこのブランチには適用されていなかった。
7. その変更をローカルに取り込んだ（pull）。設定ファイルが、コミット前の状態で作業ツリーに現れた。
8. 新しいデプロイメントを追加した。「Ignite 開発環境」に配備するよう依頼し、GitHub Copilot が環境名を確認して作成した（環境名の綴りは、Matt が「誰の綴りも信用できない」と冗談を言いながら確認した）。
9. 続けて本番（prod）用のデプロイメントも追加した。これは、パイプラインの各段階を順に設定する作業だと説明された。
10. もう一度 `agent show` を実行すると、複数のデプロイメントが表示された。
11. 変更を追加し、コミットしてプッシュした。GitHub 上に baseline という名前のブランチ、コミット、PR が現れた。
12. GitHub の自動生成機能で PR の説明を作成した。Copilot Studio のエージェントであることを理解し、ドキュメントを読んで要約を作る。Copilot reviewer は、会社のルールに基づく監査やチェックを増やすよう設定できる、とも説明された。変更ファイルには、関係する変更だけが含まれていた。
13. このリポジトリにはルールを設定していないため、そのままマージした。その後、`git checkout main` と `git pull` を実行し、差分を取り込んだ。Matt は、main へのコミットを契機に開発環境やテスト環境へ自動で配備する DevOps パイプラインを組む場合も考えられる、と述べている。
14. Ignite 開発環境の Copilot Studio を見ると、空港気象ブリーフはあるが、NHL のエージェントはまだなかった。
15. コマンドラインから `agent deploy` を、エージェント名とデプロイメント名を指定して実行し、publish（発行）まで行った。GitHub Copilot 経由にしなかった理由は、Microsoft では GitHub Copilot の利用に多くのルールと手順が適用され、配備の確認や検証が毎回入るため、今回は単純に配備したかったからだと説明された。自分の ID（アカウント）で実行した。
16. 発行は、Teams と Copilot の 2 つのチャネルに対して同時に行われた。Copilot Studio の画面を更新すると、エージェントが 2 つになっていた。Copilot Studio の UI、ソリューションの配備、その他の仕組みは使わず、Git から出たプロジェクトに対する CLI コマンドだけで配備できた。「4 つのコンポーネントを配備した」と表示され、コンテンツが公開された。
17. `ask` コマンドを、デプロイメント名だけ変えて再実行した。自分の資格情報でテストが実行され、回答が返った。
18. 本番への配備では、GitHub Copilot に利用可能なデプロイメントを尋ねた。`agent show` が実行され、3 つが表示された。最後の配備は 20 日の 9 時 32 分と表示された。「本番へ送って、昨夜の Kraken の試合結果でテストして」と依頼した。
19. GitHub Copilot は、通常の YAML 配備のように、変更がないことの確認、公開、検証を順に行った。公開してよいかの確認を求められ、承認した。CLI より時間がかかるのは、コーディングエージェントの動き方によるものだと説明された。
20. 本番に公開されたエージェントと実際に通信して確認した。結果を公開情報源とも照合し、一致することまで確認した。

Matt はここまでを、「Copilot Studio から GitHub リポジトリを作る」流れと、「CLI で開発したエージェントを Git で管理し、PR を通して、新しい開発環境、テスト環境へ配備して共有する」流れの両方を見せたものだと整理しました。これによって、Copilot Studio の上での共同開発が可能になる、という説明です。

> 補足：Matt は、ここで使ったエージェントは単純なもので、高度なコネクタやワークフローは含まれていないとしつつ、エージェントワークフローのプロジェクトでも同じ方法で動くと述べています。この点を示すデモは行われていません。

### 6.3 デモ 3：空港気象ブリーフ

Matt が、このカンファレンスの期間中に作ったエージェントです。水曜日の飛行機の中で思いつき、昨夜完成させたと話しています。米国連邦航空局（FAA）の気象サービスと、NOTAM（航空情報）サービスにつながるツール群です。NOTAM は、飛行経路や目的地に関する警告、障害物、通信上の問題など、パイロットが把握する必要のある情報だと説明されました。大量の符号や専門用語が圧縮されて書かれており、気象報告も同様で、ニュースキャスターが約 20 分で話す内容が、同じくらいの長さのテキストの塊になっている、とのことです。

構成は次のとおりです。

- スキル 2 つ：平易な英語で伝える TAF（ターミナル空域予報）、NOTAM ブロックの整形（大量に返ってくる情報を正規化する）
- ツール：エージェントが開発したカスタムコネクタで、FAA のシステムとやり取りする。政府系システムは単純ではなく、最新でもない。FAA の場合は 1990 年代並みで、コーディングエージェントにはかなりの課題だったが、それを構築した、と説明された。
- プロジェクトの下にはコネクタのプロジェクトがあり、Power Platform のカスタムコネクタとして動くスクリプト群が、FAA の気象と NOTAM のシステムをつなぎ、分かるデータに変換している。

手順は次のとおりです。

1. UI のプレビューで、サンフランシスコ（KSFO）の TAF を依頼した。テキストの流れで見ても分かりにくいため、UI で示した、と説明された。
2. 気象エージェントから情報を取得して返した。対象期間、その期間ごとの風などが表示された。元の TAF レポートがどんな見た目かも、あわせて示された。
3. 個人用の開発環境で作ってから現在の環境に持ってきたと説明し、その環境の会話の一覧を見せた。各会話について、やり取りの回数、クライアントとコンソールのどちらから来たか、使用したクレジットが分かる。
4. コーディングエージェントの CLI で見ると、このプロジェクトの構築費用は約 30 ドルで、1 日半、ホテルやセッションの合間に作った。このエージェントの利用クレジットの合計は、これまで 5 ドル、あるいはそれ以下だと話した。単価については「0.01 クレジット、0.01 セント」と言い直しており、正確な数値は発話からは確定できません。

NOTAM はさらに複雑で、サンフランシスコには約 180 件あり、デモで処理するには多すぎるため、実演していません。Matt は、基本的なコネクタの範囲にとどまらず、GitHub Copilot harness を使えば複雑なプロジェクトも作れる、とまとめています。

## 7. 注意点・発表者の気付き

- **未提供の機能がある**：サービスプリンシパルを使う配備に対する Git アクションと Git 連携は、まだ出荷されていません。ほかのデモの内容は、すべて今利用できると説明されています。
- **PAC と Ms. Agent CLI の役割分担**：開発者向けの機能は Ms. Agent CLI に集中し、PAC は管理運用の側へ移っていく方針です。エージェントが理解しやすいよう、用途を絞ったツールにするためと説明されています。
- **コーディングエージェントは遅いことがある**：GitHub Copilot 経由の配備は、CLI の直接実行より時間がかかります。Claude や Gemini でも同様だと述べています。一方、Microsoft 社内では GitHub Copilot に多くのルールと検証が適用されるため、毎回確認が入る、という話もありました。
- **環境名の入力ミス**：デモの最初に環境名を誤入力し、エージェントが確認を求めました。
- **モデル選択とコスト**：高価なモデルから `auto` に変えた例が示されました。`auto` は必ずしもコスト最適ではない、と明確に断られています。
- **接続の設定が必要**：ワークフローを環境に再接続するときは、接続が未設定だと設定を求められます。
- **統制の観点**：Seth は、役割として管理者・ガバナンスが欠かせないと述べました。PR を Copilot reviewer で審査する際に、会社のルールに基づくチェックを設定できる点が、デモで統制に関わる部分として語られた内容です。デモで使ったリポジトリにはルールを設定していませんでした。
- **リリース時期の表現**：Copilot managed runtime について、Matt は「今週 GA になったと思う」という言い方をしています。確定的な表現ではありません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 既存の Copilot Studio のエージェントとワークフローを、Git に取り込んでブランチ、フォーク、マージの機能を使える。
- UI を使う人と、コードを使う人が、同じエージェントを共同で開発できる。どちら側（UI または Git）からの変更も、拡張機能でリモートの変更として確認し、取り込める。
- 開発、テスト、本番と複数のデプロイメントを設定し、CLI の 1 コマンドで配備と発行ができる。デモでは、4 つのコンポーネントを配備して Teams と Copilot に発行できた。
- 使うコーディングエージェントを選べる。GitHub Copilot、Claude、Gemini で検証済みと説明された。
- コストの事例：空港気象ブリーフは、コーディングエージェントの CLI で約 30 ドル、1 日半で構築できた。
- 公的な情報システムのように扱いにくい外部システムにも、カスタムコネクタを作って接続できる。

## 9. まとめ

Copilot Studio は、ローコードの画面だけでなく、Ms. Agent CLI、VS Code 拡張機能、Git といった開発者の標準的な道具で扱えるプラットフォームになった、というのが発表の要点です。エージェントはファイルの集まりとしてディスク上にあり、スキル、コネクタ、MCP の機能もその構成に含まれます。

デモでは、既存のエージェントとワークフローを Git に取り込み、PR を経て、開発環境と本番環境に配備し、検証するところまでが示されました。未提供なのは、サービスプリンシパルベースの配備に対する Git アクションと Git 連携の 1 点だけで、近く提供される予定です。作る人、開発する人、統制する人が同じ土台で協力するために、道具を揃えて選んでほしい、というのが Seth の最後のメッセージでした。
