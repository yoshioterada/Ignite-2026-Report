# THR1001 Many Domain Agents, One Governance Model: An Azure Pattern

## 1. はじめに

このセッションは、事業部門ごとにバラバラな方式でエージェントを作ってしまった組織が、どうすれば一つのガバナンス（統制）モデルにまとめられるかを扱った発表です。登壇者はまず、「エージェントがどこまで到達でき、何を許可されていて、範囲を超えたときにどう気付くのか」を会場に問いかけます。そのうえで、アイデンティティ、フロントドア（入口の API ゲートウェイ）とツール、フリート（全体の監視）という三つの観点から参照アーキテクチャを紹介し、デモで動きを見せます。

後半では、同じパターンを自前で構築せずに Microsoft Marketplace からインストールして約 1 時間で使い始める近道として、42 社の「AI Universe」が紹介されます。どちらの方法でも使える GitHub リポジトリが用意されており、手元の環境で再現できる点が特徴です。

## 3. 何に関する発表か

どの事業部門も自分たちのエージェントを欲しがる状況で、エージェントの認証・認可・監視の方式が部門ごとに違うと、統制が効かなくなります。この発表は、そのばらつき（スプロール）を抑えるための Azure 上のパターンを紹介します。

発表の流れは次のとおりです。

1. 会場への問いかけと、架空のサーモスタット会社での三つの失敗例
2. 参照アーキテクチャの全体像
3. アイデンティティの設計と、最近の Entra の機能（条件付きアクセス、ライフサイクルポリシー）
4. デモ 1：Foundry でのエージェント作成とトレース
5. デモ 2：ゲートウェイでの事前チェックと、Application Insights での確認
6. 月曜日からできること
7. 近道：Marketplace の AI Universe（デモ）

## 4. 発表者が伝えたいメッセージ

中心にある主張は、エージェントごとに認証方式やツールの接続方法を決めるのではなく、**アイデンティティ、ゲートウェイ、監視を共通の仕組みに集約する**ことです。登壇者は「コンプライアンス担当者への説明を、刺激的な会議ではなく退屈な会議にできるか」という問いで、統制の効いた状態を表現しています。

もう一つの主張は、自前で組み立てるには技術チームと基盤チームの工数が必要だという点です。そこで同じ構成を Marketplace から導入できる近道が示されます。

## 5. 発表内容の詳細

### 5.1 会場への問いかけと三つの失敗例

登壇者は、本番でエージェントを動かしている人、さらに「そのエージェントが到達できる範囲・許可された操作・範囲を超えたときの検知方法」まで説明できる人に挙手を求めました。後者で手が挙がったのは 2 人でした。

続いて、サーモスタット会社を想定した三つの事業部門の例が語られます。欧州ではこの種の企業への攻撃が最近多く、身近な題材だという説明です。

| 部門 | エージェントの構成 | 問題点 |
|---|---|---|
| サービスデスク | 共有のアプリ登録を使い、チケット管理システムへは保存済みの API キーで接続 | 何が起きているかを知る手段は Application Insights だけで、誰かが見ていなければ分からない |
| 財務 | 開発者が自分のトークンで ERP システムを直接呼び出し | 監査が入るまで誰も確認しなかった。推奨できない方式 |
| 顧客オペレーション | 非常に広い RBAC を持つマネージド ID、永続的なカスタマーコネクタ、ベンダーのダッシュボード | 発表では詳細は語られていません |

登壇者は、どれも明確に間違っているわけではないものの、多くの問題を抱えうると述べています。確認したい論点は、エージェントが誰と話せるか、誰が見ているか、どのデータに届くか、何ができるかの四つです。

### 5.2 なぜ今この話か

登壇者は、次の最近の動きを挙げています。

- Microsoft Agent 365 は GA（一般提供）済みで、レジストリがあります。コントロールプレーンは Foundry にも及びます。
- Foundry のホスト型エージェントは、7 月 9 日に GA になりました（年は発話では確認できません）。どのチームもエージェントを出荷できる一方で、全体を把握できるとは限りません。
- 条件付きアクセスポリシーは 11 月 4 日からプレビューで、共有されるエージェントのリスク条件に「ID の種類」を指定するルールを設定できます。
- 11 月 9 日に「ブルーフィッシング」（原語は blue phishing と聞こえます。音声認識の都合で表記が確定できません）という事例が公表され、Proofpoint の記事で調べられると案内されました。エージェントの ID を狙い、テナント内に別のエージェントを作らせて、テナントとデータへのアクセスを得る攻撃です。悪意あるサードパーティのブループリントに同意すると、概念実証ではテナント内に 250 を超えるエージェント ID が作れたと説明されています。設定が適切でないと危険であることを示すための実証です。

### 5.3 参照アーキテクチャ

登壇者は「持ち帰って説明するなら、この図を撮影してください」と前置きして、構成を説明します。

- 利用者と管理者は HTTPS で入り、アプリケーションゲートウェイまたは WAF を通ります。パブリック IP、TLS 証明書があり、Key Vault を使えます。
- その先は内部のコンテナーアプリ環境で、ポータル API と、運用を保守するジョブがあります。
- 各事業のドメインごとにエージェントがあります（サポートエージェント、ERP ドキュメントツールのエージェント、顧客オペレーションなど）。それぞれ Key Vault とプライベートエンドポイント経由でデータ（Postgres）に接続し、イメージはコンテナーレジストリに置きます。
- API Management（APIM）が AI ゲートウェイとして、**すべてのモデル呼び出しとツール呼び出しの統制された単一の入口**になります。アプリやエージェントが何かを呼ぶときは必ずここを通ります。
- その下で Microsoft Foundry がモデルとエージェントをコンテンツセーフティ付きでホストします。
- 監視と監査は Log Analytics と Application Insights で行い、監査の取り込みルールも確認できます。

### 5.4 アイデンティティの設計

三つの事業部門のエージェントには、ドメインごとにブループリント（ひな形）があり、エージェントごとに ID があります。主な要素は次のとおりです。

- 資格情報は各ブループリントのフェデレーション資格情報で、このパターンにシークレットはありません。
- スポンサーは、エージェントの存在を把握し責任を持つ人間です。
- ゲートウェイにはアプリロールがあります。ロールもトークンもなければ、ツールも使えません。
- 条件付きアクセスにより、承認されたエージェントだけが許可された対象にアクセスできます。
- ライフサイクルポリシーで、スポンサーの最小人数を再確認し、利用されなくなったら無効化できます。

実際の流れは、エージェントが Entra にトークンを要求し、条件付きアクセスを経て API Management に渡り、そこでドメイン用のアプリロールを検証します。そのうえで、特定の名前の MCP サーバーなどのツールを使ってよいかを判断し、許可がなければ 403 が返ります。この判断の理由は、デモのトレースで確認できます。

### 5.5 Entra の新しい機能とライセンス

- 10 月 29 日から、条件付きアクセスの「ポリシープラン」で、共有の条件と除外の下にルールをまとめられます。エージェント向けのルールを使うには E7 ライセンス、または Agent 365 と Entra ID P1 のプランが必要です。
- エージェントのリスクを扱うには P2 が必要です。登壇者は、ライセンスなしでできる範囲だけを見せると断っています。
- ポリシープランでは、リスクのあるエージェントに共有の条件を設定し、エージェント用に個別のルールを作ってブロックできます。自律型のエージェント向けの個別ルールも作れます。
- エージェント ID のライフサイクルポリシーはプレビューです。既定の非アクティブポリシーは、オフにするまで有効です。60 日で通知、90 日で無効化、450 日で削除という既定値で、変更できます。
- ブループリントの既定の作成権限は 11 月下旬にかけて展開中です。何も設定しないと、一般ユーザーでもブループリントを作成できてしまいます。

### 5.6 ゲートウェイでの事前チェック

登壇者は、監査で事後に気付くのではなく、モデルに届く前に止める流れを説明しています。リクエストが入るとコンテンツセーフティ、プロンプトシールド、MCP の確認、トークン上限、バックエンドの資格情報の確認を順に通り、応答が返ります。ポイントとして次を挙げています。

- APIM は必須です。
- ドメインごとに MCP サーバーを一つ置き、プロダクトごとにモデルのルーティングを設定します。
- 受け入れられない文言があれば止めます。

### 5.7 Defender と Purview

KQL を自分で書く代わりに、Application Insights の中にあるエージェントに質問すれば、例外やエラーを要約できると説明しています。別の領域では、Microsoft Defender がエージェントのインベントリと影響範囲（ブラスト半径）を見て、Microsoft Purview が監査と電子情報開示を担当するとしています。

### 5.8 この構成でできないこと、仕様上の注意

- 管理単位は不要です。エージェント ID はそこに参加できません。ブループリントと所有者で範囲を限定します。
- MCP を APIM のワークスペースに置く必要はありません。ドメインごと、プロダクトごとに分けられます。
- Purview ではユーザーのコンテキストが必要です。
- エージェントのリスクはプレビューです。対象指定は動きますが、リスクシグナルとポリシープランはまだプレビューで、設定は Entra の Agent ID 関連の画面で行います（画面名は音声認識の都合で表記が確定できません）。

### 5.9 近道：42 社の AI Universe

自前の構築には技術チームと基盤チームが必要です。そこで登壇者は、Marketplace からインストールする近道を紹介しました。この製品は 42 社が作っており、登壇者は同社の取締役で、透明性のために開示すると述べています。

- 共有基盤（アプリケーションゲートウェイ、APIM の AI ゲートウェイ、Foundry、ポータルのコントロールプレーン）は同じ構成です。
- 加えて「Wisdom MCP」により、特定の知識を MCP に入れられます。アプリごとにリソースグループが作られます。
- エージェント ID のブループリントやスポンサーの代わりに、Entra のロールを使います。最小権限のロールを超えて到達できないようにします。
- 推論用のトークンは一つで、アプリごとではありません。すべて同じ Microsoft 製品で、カスタムコンポーネントを加えたものです。
- Marketplace の掲載ページから導入を終え、データ分類（個人データの可否、EU の AI リスクなど、準拠する枠組み）を設定してアプリを作ります。リソースグループ、プライベートエンドポイント、リポジトリ、Foundry エージェントが作られ、テスト用のシークレットを置いて CI でブロックされることを確認し、証跡として登録できます。
- 登壇者は、手順の最後に参考情報として、Foundry のエージェント ID の概念、条件付きアクセスのプラン、REST API を API Management で MCP サーバーとして公開する方法を挙げ、Microsoft Agent 365 と Foundry のコントロールプレーンを使う方法もあると補足しています。リポジトリでは、デモで見せた構成をすべて立ち上げられると説明しています。
- エージェントだけでなく、社内でバイブコーディングによりアプリを作りたい人が多い場合に、統制を保つ手段としても有効だと述べています。

## 6. デモ・手順

デモは三つあります。画面の細部は音声からは確認できないため、語られた範囲で書きます。

### 6.1 デモ 1：Foundry でのエージェント作成とトレース

1. GitHub リポジトリを実行済みで、作られたリソースの一覧（長い一覧）が表示されます。
2. サポートエージェントのブループリントとゲートウェイアプリを見せ、両方にスポンサーが付いていることを示します。
3. Foundry を開き、エージェントが作成されていることを確認します。エージェント画面でサポートエージェントが表示され、時間があればチャットもできると説明されました。
4. 要点は、これらが GitHub リポジトリの実行で自動的に作られたことだと述べられました。Entra 側でも確認できます。
5. リクエストのトレースを辿ります。チケットを要約して修正案を出す想定で、トークンがサポートエージェントに渡り、Entra ID で可否を確認し、ゲートウェイアプリで MCP ツールと記事検索を確認します。トークンが有効なら、チャットが完了します。コンテンツセーフティやトークン予算、メトリクスも確認します。
6. 各ステップは OpenTelemetry のデータとして Application Insights と Foundry のトレースの両方で見られます。許可されない場合はエラーになり、トレースに表示されます（発話では「304」と聞こえますが、前段では 403 と説明されており、音声認識の都合で確定できません）。
7. Foundry のトレース画面で最新のエラートレースを開き、再生ボタンで各ステップを順に再生します。説明文形式の表示と、グラフ形式の表示があり、許可されなかった経路が赤で示されます。

### 6.2 デモ 2：Application Insights での確認

1. ゲートウェイでの事前チェック（5.6）の流れを説明し、Foundry のエージェント、APIM、コンテナーアプリの構成を確認します。
2. Application Insights の中にあるエージェントに依頼し、エラーや例外の要約を出します。KQL は書いていません。
3. 特定のトレースを検索し、使うべきでない MCP が使われたことの説明や、止めるべき質問が行われたことを確認します。

### 6.3 デモ 3：AI Universe のインストールと利用

1. Marketplace で「AI Universe」を検索し、「今すぐ入手」を選びます。Azure にサインイン済みなら、インストールが始まります。最大 1 時間かかると説明されています。
2. プランを選びます。従量課金で、長期間無料でも使えます。詳細情報と資格情報を入力して完了します。無料期間があります。
3. 開いたウェブページで、配置先などの質問に答えます。シェルの種類（macOS、Linux など）を選び、表示されたコマンドをコピーして実行します。
4. 完了すると、社内の誰でも理解できる画面が表示されます。アプリの一覧があり、アクセス権を与えた人だけが利用できます。Wisdom を追加して、MCP に蓄積した知識を複数のエージェントで共有することもできます。コスト、コンプライアンス、セキュリティの概要も見られます。
5. 「Ignite デモ」アプリを開き、ERP の請求書、カスタマーサービス、課題解決の三つのエージェントを確認します。許可する操作（Web 検索、特定のデータ、特定の情報源など）を決められます。Wisdom は他のアプリから再利用もできます。スキルや知識に対するベストプラクティスのルールは、あらかじめ入っていると説明されました。バイブコーディング向けのルールも設定済みです。
6. アプリを開き、チャットで、解決が必要そうなチケットを教えてほしいという趣旨の質問をします。会社名は Contoso で、未処理のタスクの一覧が返りました。以降の追加操作の細部は音声からは確認できません。

## 7. 注意点・発表者の気付き

- 利用者がブループリントを作成できる設定や、サードパーティアプリへのユーザー同意の設定を確認することが、最初の対策として挙げられています。約 10 分で済み、この攻撃の入口を閉じられると述べています。
- エージェントのリスク関連（リスクシグナル、ポリシープラン）はプレビューで、P2 が必要です。エージェント向けのルールには E7 または Agent 365 と Entra ID P1 が必要です。
- ブループリントの作成権限は、何もしなければ全ユーザーに開かれます。
- 登壇者は 42 社の取締役であることを自ら開示しており、AI Universe はその会社の製品です。
- デモで使った検証用のリポジトリは、検証環境にデプロイして試すことが勧められています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 事業部門が異なる方式でエージェントを作っても、アイデンティティ、ゲートウェイ、監視を共通化することで統制しやすくなります。
- シークレットを持たない構成（フェデレーション資格情報）と、人間のスポンサーの設定により、責任の所在が明確になります。
- 一つの入口（APIM）にモデル呼び出しとツール呼び出しを集約するため、事前のブロックと、トレースによる後からの確認ができます。
- GitHub リポジトリで同じ構成を自分の環境に展開できます。
- AI Universe を使えば、最大 1 時間のインストールで同じパターンを導入できます。

## 9. まとめ

エージェントごとに接続方式がバラバラな状態を、ブループリントとエージェント ID、APIM の AI ゲートウェイ、Foundry のトレースと Application Insights による監視でそろえるパターンが紹介されました。月曜日にできる対策として、ブループリント作成権限とサードパーティ同意の確認（約 10 分）、読み取り専用にしたいドメインのツールを一つのゲートウェイと一つの MCP サーバーの背後に置くこと、Agent 365 でアプリロールを一つ設定し「行動する前に生成し、生成する前に検索する」順序を守ること、リスクのあるエージェントのポリシープランを、エージェントユーザーとエージェントで別ルールにして、約 2 週間レポートのみで試したうえでブロックすることが挙げられました。最後に、コンプライアンス担当者への説明に不安のあるエージェントはどれか、という問いが会場に残されました。
