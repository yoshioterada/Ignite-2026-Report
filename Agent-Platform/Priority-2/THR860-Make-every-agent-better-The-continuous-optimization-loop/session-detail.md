# THR860 Make every agent better: The continuous optimization loop

## 1. はじめに

このセッションは、本番に出したエージェントの品質を継続的に上げていくための考え方と、Microsoft Foundry での実践方法を紹介する約 25 分のシアター形式の発表です。エージェントは作るだけなら簡単ですが、本番運用に入ってからの改善が難しい、という問題意識から始まります。

発表では、航空会社のサポートエージェントを題材に、トレース（実行記録）の確認、インサイト（トレースからの問題点の抽出）、評価、オプティマイザーによる自動改善、本番トラフィックの一部だけで試す実験、そして本番の記録から学ぶ継続学習までを、画面を使って順に見せています。結論は「プロンプトから始めるのをやめて、改善のループを回し始めよう」というものです。

## 3. 何に関する発表か

テーマは、エージェントを本番で使い続けながら良くしていくための「継続的な最適化ループ」です。扱う製品は Microsoft Foundry で、特にエージェントのトレース、インサイト、評価、オプティマイザー、実験（A/B テスト）の各機能を使います。サンプルのエージェントには、Foundry がマネージドで提供する Copilot ハーネス（Microsoft Copilot、GitHub Copilot、Cowork などの内部でも使われているエージェント実行基盤）が使われています。

発表の流れは次のとおりです。

1. 「コードは安い、評価を見せてほしい」という問題提起
2. エージェント開発の落とし穴（プロンプトに指示を足し続けて破綻する流れ）
3. サンプルの航空サポートエージェントの構成
4. デモ 1：インサイトとオプティマイザー、実験による段階的な本番展開
5. デモ 2：人手のアノテーションから学んで新しいスキルを作る継続学習
6. 持ち帰ってほしい 4 つのポイント

## 5. 発表内容の詳細

### 5.1 エージェントは作りやすく、本番で壊れやすい

エージェントを作る作業自体は今はとても簡単で、モデルを選び、指示を書き、ツールとナレッジをつなぐだけで始められます。指示も短くなっています。Vivek 氏は、2023 年には XML や書式に苦労してプロンプトを組んでいたが、今は「あなたは航空会社のエージェントです。お客様を助けてください」と書くだけでほぼ動く、と話しています。ナレッジとデータが整理されていないとつなぐ作業は依然として難しいものの、プレイグラウンドで試して正答率 70〜80% に届くこと自体は難しくない、という実感だそうです。

問題は 2 日目、つまり本番投入のときに現れます。発表では次の 3 点が挙げられました。

- エージェントの失敗は、4xx や 5xx のようなエラーやスタックトレースを残さず、静かに起こります。
- 動作は非決定的で、6 回中 6 回成功でも 0 回でもなく、4 回成功といった形で失敗します。4 回を 6 回に上げる方法は自明ではなく、2 つ直すと別の 2 つが壊れて 4 回に戻ることもあります。
- エージェントはより自律的で多様な作業をするようになり、新しいタスクや新しいツール、新しい文脈に出会うと、テストしていない経路をたどり始めます。

### 5.2 プロンプトに指示を足し続けると破綻する

Vivek 氏は自身の経験として、次のような流れを紹介しました。

1. 初日は構造化されたプロンプトから始め、「お客様を助ける」「Contoso 航空のポリシー担当エージェント」「ツールを適切に使う」「事実が足りなければ聞く」と書く。うまく動く。
2. テストを増やすと、ラウンジの質問にうまく答えられない。スキルを追加したのに使われないので、指示の直後に「重要：回答の前に必ずポリシースキルを読み込むこと」と足す。動くが、構造が崩れ、指示に何かが漏れ込んでいる感覚が出てくる。
3. シェルツールや計算ツールを追加しても使われないので、「必ずポリシーを引用する」「料金を推測しない」「計算機を飛ばさない」と強い口調で書く。すると計算機やポリシーを常に使うようになり、常識的な判断までしなくなって、「ポリシーにないので答えられません」と返すようになる。
4. 最後は「旅行の質問には回答前に旅行ポリシーを検索してください」と懇願する状態になる。

この状態では、エージェントを本番に出せず、自分でテストするのも嫌になり、すでに期待しているプロダクトチームに出荷時期も答えられません。この経験は、コーディングのセッションでもエージェントでも見てきたと語っています。発表の狙いは、ここに陥らない方法と、すでに陥っている場合の抜け出し方を示すことです。

### 5.3 サンプルエージェントの構成

題材は航空サポートエージェントです。顧客の依頼の例は「3 人で 2 時間遅れた。2 時間 40 分遅れて到着する。何が受けられるか」というものです。構成は次のとおりです。

| 要素 | 内容 |
| --- | --- |
| 実行基盤 | Foundry がマネージドで提供する Copilot ハーネス。自分でホストや管理をせず、ツール、指示、プロンプト、文脈を渡すだけで動く |
| 指示 | 最初は構造化されたプロンプト |
| スキル | ポリシーのスキル 9 つ。指示を追加で与える |
| ナレッジ | Foundry IQ（インデックス化した知識） |
| API | 公開 API で料金や現在のフライト状況を取得。Contoso の航空会社ツールで予約の確認や予約作成なども可能 |
| ツール | シェルの Python ツール。ポリシーと料金を使って計算させる |

ハーネスにはファイルシステムの書き込みと読み込みが最初から備わっており、このエージェントではシェルアクセスだけを有効にしています。

最初の質問への回答は、「ポリシー上、3 時間を超える遅延でないとクレジットの対象にならず、それまでは食事クーポンのみ。3 人なので 45 ドル」というものでした。計算も正しく、ベースラインのエージェントとして十分に動いています。

これから見ていく段階は、トレース、インサイト、評価、最適化、そして本番での継続学習です。

### 5.4 インサイト（デモ 1）

Bhuvan 氏が Foundry 上で実際に見せたデモです。この内容は 6 章に手順としてまとめています。ここでは説明の要点だけを書きます。

ベースラインのエージェントを公開した後、別の人が「プラチナ会員だが、ゲストをラウンジに連れて行けるか」と聞くと、エージェントは答えを持っていませんでした。スキルにはプラチナ会員本人の扱いはありますが、ゲストの扱いは書かれておらず、「窓口で聞いてください」と返してしまいます。

対応としてトレースを 1 件ずつ見ていく方法もありますが、トレースは大量で、何が正解で何が誤りか、何を改善すべきかが読み取りにくく、いずれ手に負えなくなります。そこで使うのが **エージェントのインサイト** です。すべてのトレースを見て、良いものと質問に答えられなかったものを分け、問題のパターンを見つけて、改善の推奨を出します。

### 5.5 オプティマイザー（デモ 1 続き）

インサイトを 1 件ずつ直すのも、数が増えると大変です。そこで、改善したい質問の集合（例として 100 件程度）を渡し、プロンプトをどう変えればよいか分からなくても自動で改善案を探すのが **エージェントのオプティマイザー** です。

- 最適化の目的は、品質向上とコスト削減から選べます。デモでは、コストは現状で満足なので品質向上を選びました。
- 変更の対象として、モデル、ツールの説明、エージェントの指示などを選べます。モデルについては、問題が解決するなら安いモデルを選ぶことがあり、プロンプトの種類に応じて適切なモデルを選ぶモデルルーターを提案することもあります。
- データセットは、Foundry がトレースから悪い例を探して生成するか、自分のものを渡すかの 2 通りです。
- 改善したい観点（ルーブリック）を選んでジョブを開始します。

オプティマイザーは進化的アルゴリズムのような仕組みで動きます。データセットから異なるバッチを選び、プロンプトやツールの説明を改善して候補を作り、データセットで評価してスコアを出し、その候補をもとにさらに改善します。候補 2 が候補 3 から派生するなど、進化の木ができます。デモのジョブでは候補が 4 つ生まれ、候補 1 と 4 はスコアが改善せず、候補 3 は悪化し、**候補 2 がスコアを 10% 改善** しました。

### 5.6 実験による段階的な本番展開

候補を「候補を昇格」ボタンで本番に反映することもできますが、他の部分が悪化していないか確信が持てないので、そのままの反映は勧められないと説明されました。そこで **実験**（A/B テスト） を作ります。例えば呼び出しの 10% だけを新しい候補に、90% を元のエージェントに振り分けて本番で動かし、両方のトレースを比べて、100% に切り替えてよいか判断します。この流れで、エージェントを継続的に改善していきます。

### 5.7 本番後の継続学習（デモ 2）

ここからは Vivek 氏のデモです。プロンプト、指示、モデル、スキルを繰り返し改善して、エージェントが本番に出た後の場面から始まります。

本番に来た質問は「米国のパスポート保持者で、英国で乗り継ぎ、英国で荷物を受け取る。ETA は必要か」というものです。正解は「必要」で、ETA は電子渡航認証です。ところがエージェントは「ポリシーにないので答えられません」と返しました。うそをついているわけではなく、根拠に基づいた回答ですが、顧客体験としては望ましくありません。

そこで、悪かったトレースに付けられたアノテーションを使います。テスト中に自分で付けたり、一部を選んだり、顧客に良し悪しのラベルを付けてもらったりしたものです。対象のトレースには「悪い」というアノテーションがあり、正しい答えは「はい」であること、参照すべき権威あるポリシーなどの情報源も記されています。これをどうモデル化するかはエージェント次第で、もっと親切にすべきか、控えめにすべきかといった参考情報も渡せます。正確なほど効果が高まります。

この状態で、再びオプティマイザーに戻り、今度は「過去の活動から学ぶ」という別の種類の最適化を選びます。ゴールを指定するのではなく、直近 7 日間（デフォルト）の実際の実行記録から学ばせるものです。評価器を渡すか渡さないかは任意です。

- トレースは 37 件が見つかりました。本番のトレースが数千件ある場合、すべてから学ぶと大量の LLM 呼び出しが必要になるため、一部を賢くサンプリングします。ユニークさや、人手のアノテーションまたは評価の有無で分類してまとめます。
- 目的を自分で書いて方向付けられます。デモでは「最大の問題を直す」と入力して開始しました。
- 37 件だったため 5 分で完了しました。件数が多ければ長くなるものの、何件から学ぶかは制御できます。

結果として、「エージェントは英国の ETA に関するポリシーを多く断っている」という問題が見つかりました。続いて、英国の ETA に関連する 6 件のトレース、訪問者と非訪問者、米国パスポート保持者とそれ以外などのケースから学びを作り、最後に **新しいスキル** を生成しました。人手のフィードバックと評価結果に基づいたルールを持つスキルです。

このスキルをエージェントに追加すると、9 つだったスキルが 10 個になりました。同じ質問を再度投げると、数秒から数分後に「はい、事前に ETA が必要です」と返り、参照すべき正しいポリシーと次にすべき行動も示されました。

学ぶ内容は新しい知識の追加だけに限りません。どう反応すべきか、うまくいったこと、避けるべきこと、短く 1 回で答えるか複数ターンで答えるか、といったことも含みます。これらは新しいスキルにも既存スキルの編集にも反映されます。Copilot ハーネスでは、シェル以外にも Web 検索などパッケージ済みのツールを簡単に有効にできるとも補足されました。

### 5.8 持ち帰りのポイント

番号付きで次の 4 点が示されました。

1. **すべてをトレースする**：最も簡単な部分です。多くのフレームワークとエージェント開発用 SDK は OTEL の計装を備えているので、「Azimon」または Foundry に出力して表示します（音声認識の都合で Azimon の表記が確定できません）。
2. **シグナルとノイズを分ける**：トレースが多すぎるので、パターンを見つけるインサイトの仕組みを作ります。1 つのトレースでも数十から数百のツール呼び出しがあり、見るだけでも大変です。
3. **「良い」を定義する**：最も難しい部分で、何をもって良しとするかは各自の定義です。LLM を判定者にする、正解データを使う、決定的なコードで評価する、といった評価器を選びます。評価器は固定ではなく、エージェントの進化や学びとともに変わります。評価器に最適化し尽くすと役に立たなくなるので、より難しいケースや失敗するケースを足す必要があり、多くの作業がここに充てられます。
4. **証拠をもって改善する**：優れた評価器があれば、最適化の結果を信頼して本番に出し続けられます。本番では A/B テストもでき、最近の Foundry では A/B テストを提供開始したと説明されています。

## 6. デモ・手順

デモは 2 つあります。画面は音声から確認できないため、語られた範囲の手順です。画面の細部（ボタン名の配置など）は確認できません。

### 6.1 デモ 1：インサイトからオプティマイザー、実験まで（Bhuvan 氏）

1. Foundry 上のベースラインのエージェント（航空サポートの旅行エージェント）を表示する。Copilot ハーネス、シェルアクセス、スキルとして付けたポリシー群、ナレッジベース、Contoso の航空会社ツールが付いていることを示す。
2. 公開済みのエージェントに「3 人で遅延した場合は何が受けられるか」と聞く。45 ドルの食事クーポンと正しく答える。
3. 「プラチナ会員のゲストはラウンジに入れるか」と聞く。ゲストの扱いが分からず、窓口で聞くよう返答する。
4. トレース一覧では何を直すべきか分かりにくいことを示し、インサイトを開く。ラウンジアクセスのポリシーに対してエージェントが慎重すぎるという問題と、プロンプトの改善提案が生成されている。
5. インサイトから該当トレースを開き、実際の会話の流れ（ユーザー視点）を確認する。
6. インサイトからの最適化機能に進み、提案を使ってエージェントを変更する。ここでは、ロイヤルティ階層のスキルを更新済みで、再度同じ質問をすると、会員の特典は受けられるがゲストは対象外、と正しく答える。
7. オプティマイザーを開く。目的に品質向上を選び、変更対象（モデル、ツールの説明、指示など）を選ぶ。
8. データセットは、生成するか自分のものを渡す。デモでは自分のデータセットを使う。表示された内容を確認して次へ進み、改善したいルーブリックを選び、ジョブを開始する。
9. 実行済みのジョブの結果を見る。候補が 4 つあり、スコアが改善したのは候補 2 の 10% のみ。
10. 昇格ボタンで本番に反映できることを示したうえで、実験（10% を新候補、90% を元のエージェント）を作る方法を説明する。

### 6.2 デモ 2：アノテーションからの継続学習（Vivek 氏）

1. 本番を想定したエージェントに、英国の ETA の質問をする。エージェントは「ポリシーにない」と答える。
2. アノテーション付きのトレースを開く。同じ質問、出力、「悪い」のラベル、正解が「はい」であること、権威あるポリシーなどの情報源が含まれている。
3. オプティマイザーで「過去の活動から学ぶ」を選ぶ。デフォルトの直近 7 日間、評価器は任意、トレースは 37 件。
4. 目的に「最大の問題を直す」と書いて開始する。
5. 実行済みのジョブを開く。英国 ETA 関連のポリシーを断る問題が見つかり、6 件の関連トレースなどから学びが作られ、新しいスキルが生成されている。
6. スキルをエージェントに追加し、10 個目のスキルとして確認する。
7. 同じ質問を再度投げる。「はい、事前に ETA が必要」と答え、参照すべき正しいポリシーと次の行動も示す。

## 7. 注意点・発表者の気付き

- エージェントの失敗は、エラーコードやスタックトレースを残さず静かに起こり、非決定的です。調整のたびに別の問題が出るため、方法論が必要です。
- プロンプトに強い口調の命令を足し続けると、常識的な判断まで失う副作用が出ます。
- 実験を挟まずに昇格すると、他の部分が悪化する可能性があります。本番の一部だけで試して比較する流れが勧められています。
- すべての本番トレースから学ぶと LLM 呼び出しが膨大になるため、継続学習はサンプリングされます。何件から学ぶかは制御できます。
- 評価器は固定ではありません。ある評価器に最適化し尽くすと役に立たなくなるので、難しいケースの追加が必要です。
- エージェントの回答がうそではなく、ポリシーに根拠のあるものでも、顧客体験として不十分な場合があります（ETA の例）。

## 8. 利用者にとっての利点

- トレースが大量にあっても、インサイトが良いものと悪いものを分け、パターンと改善案を提示します。
- オプティマイザーが、プロンプト、ツールの説明、モデルなどの候補を自動で作り、評価でスコア化します。デモでは 1 つの候補でスコアが 10% 改善しました。
- 実験で、本番の一部の呼び出しだけを新候補に回して比較できるため、安全に展開できます。
- 人手のアノテーションや評価結果から、新しいスキルが自動で作られるため、本番で見つかった問題を次の改善に取り込めます。
- 最適化ジョブには推定コストが表示され、費用を見て判断できます。

具体的な顧客事例や、導入企業の成果の数値は、発話では確認できません。

## 9. まとめ

エージェントはプロンプトとツールをつなぐだけで簡単に作れますが、本番では、静かな失敗、非決定的な動作、未知の経路が問題になります。プロンプトに指示を足し続けるのではなく、トレース、インサイト、評価、最適化、段階的な本番展開、本番のアノテーションからの継続学習というループを回すのが、この発表の提案です。

Foundry には、このループを支えるインサイト、オプティマイザー、実験、コスト表示が用意されていることがデモで示されました。持ち帰りは、すべてをトレースし、シグナルを見つけ、良いの定義を育て、証拠をもって改善することです。
