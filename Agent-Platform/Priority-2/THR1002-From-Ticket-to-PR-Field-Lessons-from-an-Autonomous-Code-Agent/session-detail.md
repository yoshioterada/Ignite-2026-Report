# THR1002 From Ticket to PR: Field Lessons from an Autonomous Code Agent

## 1. はじめに

ブラジルの Microsoft パートナー企業の開発者が、自社で実際に運用している「ソフトウェアファクトリー」を紹介したセッションです。Azure DevOps のチケットにラベルを付けるだけで、要件の詰め込み、計画、コーディング、コードレビューまでを AI エージェントが進めます。結果は Microsoft Teams のボットから確認でき、本番の監視情報も同じボットに質問できます。

登壇者は冒頭で、見せる内容はすべて本番環境のもので、デモ用の模擬データではないと断っています。発表時間は 25 分です。最も強調されたのは、コードを書かせる前の「質問による要件の詰め込み」に時間をかけること、そして人間が計画とコード品質の確認に残ることです。

## 3. 何に関する発表か

登壇者の会社では、全員が実質的に開発者です。約 1 年半前から Claude、GitHub Copilot、open code、Codex などのコードエージェントを使い始めました（あわせて Microsoft Foundry を使った開発や、Foundry 自体を使った AI アプリの作成にも取り組んでいます）が、チームごとにエージェントやスキルの作り方、進め方がばらばらでした。そこで全社共通のプロセスにまとめる目的で作ったのが、このソフトウェアファクトリーです。前日の基調講演で Satya Nadella 氏が触れたソフトウェアファクトリーという考え方に重なると説明されています。

必須の要素は Azure DevOps と、処理を動かすホストだけです。同社は Mac mini をホストにしていますが、Azure Kubernetes Service、Azure App Service、仮想マシン、手元のマシンでも動かせます。それ以外は必須ではありません。

発表の流れは次のとおりです。

1. 「grill」工程：チケットを質問で磨き上げる
2. コーディング工程：複雑度判定、計画、マルチエージェントによる実装
3. Teams ボットによる機械から人間、人間から機械のやり取り
4. Elasticsearch と Azure の情報をボット経由で観測する拡張
5. 運用指標、今後の展開、登壇者からの助言

## 4. 発表者が伝えたいメッセージ

登壇者の主張は三つにまとまります。

- 工程の最初に注ぐ労力と品質が、成果の質を決めます。最初の工程はコーディングではなく、よく書かれたチケットを作ることです。
- このソリューション自体はコーディングエージェントではなく、**開発者やチームが用意したエージェント、スキル、プロンプトを使う自動化の仕組み**です。チームがそれらに投資するほど品質が上がります。
- 完全な自律化は目指していません。人間は計画の確認とコード品質の確認に残り、エージェントは開発者を置き換えるものではなく、チームに腕をもう一本加える「仮想の同僚」という位置づけです。

## 5. 発表内容の詳細

### 5.1 全体の流れ

社内の流れは、アイデアや修正したいバグから始まり、本番での可観測性（オブザーバビリティ）に至ります。工程のすべてに AI が関わります。ソリューションは Azure DevOps の上に作られ、状態管理はすべて Azure DevOps で制御されます。

### 5.2 grill 工程：チケットを質問で詰める

チケットに数行の説明だけを書いてもコードは作れますが、登壇者は、最初の品質が高いほど結果が良くなると、この数か月で実感したと述べています。

1. チケットに「grill」ラベルを付けます。
2. ホストがチケットを取得し、マシンの権限（Entra ID）でリポジトリをクローンします。入力には説明文のほか、チームとのブレインストーミングの書き起こし、画像、PDF、技術文書、ガイドラインを渡せます。
3. エージェントが内容を理解したうえで、人間が答えるべき質問を出します。質問には選択肢と、コードベースを見たうえでの推奨案が付きます。推奨と違う回答も可能です。
4. 人間がチケットにコメントで回答し、ラベルを「grill answered」に付け替えると、次のラウンドに進みます。
5. 必要な情報がそろうと、エージェントが最終版のチケットを作ります。内容がよく整理され、コード内で何をすべきかが詳しく書かれています。

登壇者は大規模な例を紹介しました。空のリポジトリと空のボードから、Web API、MCP サーバー、Web アプリケーションまで含むアプリケーション全体を、1 枚のチケットで作ることを目標にしました。質問への回答に約 90 時間を使い、80 を超える質問に答えています。最終チケットは 1,300 行の説明で、技術的な詳細、コード品質、パターンなどが含まれていました。通常はこれほど大きくせず、小さなチケットに分割すると述べています。

### 5.3 コーディング工程

ここでは「ready」ラベルを付けて開始します。流れは次のとおりです。

1. ソリューションを再度クローンし、最終チケットを取得します。
2. チケットの記述が十分かを検証します。grill を通していれば問題ありませんが、人間が書いたチケットでは情報が欠けている場合があるため、この確認があります。
3. チケットの複雑度を低・中・高に分類します。複雑度ごとに使うモデルの組み合わせが決まっています。

| 複雑度 | 使うモデル（発話どおり。モデル名は音声認識の都合で確定できません） |
|---|---|
| 低 | 全工程で「Luna 6」（GitHub Copilot 経由） |
| 中 | 計画とコーディング以外は「GPT 6 Luna」、計画とコーディングは「Sonnet 5.5」 |
| 高 | 「Opus 5.5」と「Luna」 |

4. 社内用の計画モードで、複雑度を小さなタスクに分解します。サブタスクは、リポジトリの `.github` フォルダーにあるエージェントのうち、該当するものに割り当てられます。
5. 計画ができると、人間が確認します。承認するかどうかを尋ねられ、変更や削除を依頼すれば計画を修正し直すループになります。問題なければ「ready to execute」と入力します。
6. 最終チケット、計画、コードベースを使って、マルチエージェントでコーディングが始まります。

登壇者は、この工程は開発者が作った成果物を使うだけだと強調しています。製品の中身を一番よく知っているのは開発者とチームなので、エージェントのスキルや指示、プロンプトを充実させるほど品質が上がるという考えです。

先ほどの大規模チケットの実績は、GitHub Copilot の AI クレジットが 7,000 超（約 73 ドル）、コーディングに 3 時間、成果物はコード 600 ファイルでした。水曜日の夜に開始し、同日中に本番に入ったと述べています。コード品質は非常に高いという評価です。

### 5.4 Teams ボットによる機械と人間のやり取り

チームから、状態を見るたびに Azure DevOps を開く必要があるという不満が出ていました。そこで Teams を作業の場にしました。関係は「1 ボード、1 リポジトリ、1 Teams のエージェント、ホスト上の 1 インスタンス」で、チームごとに公開チャネルとボットがあります。登壇者が示したボットは「Joker」という名前です（社内ではスーパーヒーローと悪役のキャラクターをボットに当てているという説明です）。

- 機械から人間：ボットが進捗を報告し、計画の確認など人間の対応が必要なときに通知します。
- 人間から機械：ボットにメッセージを送ると Microsoft Foundry を経由してソリューションに届きます。

各実行や各ステップで消費した AI クレジットを集計しており、「過去 90 日の AI コストを教えて」と尋ねれば答えます。ただしこのときの値は正確ではありません。コーディングの提供元に Microsoft Foundry を使っているため、AI クレジットではなく Foundry のトークンとして支払っているからです。先月は AI クレジットだけでおよそ 2,000 ドルを使ったと述べています。

### 5.5 Elasticsearch と Azure の情報への拡張

可観測性には OpenTelemetry を使います。ローカルでは Microsoft Aspire ダッシュボード、本番では Elasticsearch です。Elasticsearch には MCP があり、Foundry は外部の MCP を接続できます。エージェントごとに Foundry 上に 1 エージェントがあり、Joker には、ホスト内部の MCP と Elasticsearch の MCP の二つを接続しています。

「このトレース ID の情報を教えて」と聞くと、本番で動いている情報が返ります。コードレビューに加え、ホスト内のメタデータ（価格、コスト、チケット、説明など）と Elasticsearch の情報も扱えます。

さらに、Microsoft Agent Framework で作った外部エージェント（オープンソース。LinkedIn で連絡すれば共有すると述べています）が、AKS 上で動いています。このエージェントは Azure の一部（リソースグループやサブスクリプション）への読み取り専用アクセスを持ち、Azure CLI を使って Azure のメトリクスを取得します。Joker が属する社内製品は「Atlas」で、Azure 上にあります。「Atlas Azure Explorer Agents」という外部エージェントを追加しました。

発話にある質問の例は次のとおりです。

- Atlas のリソースグループで、昨日、削除などの操作はあったか
- 昨日、データベースの DTU 使用率が 100% に達した時間はあったか。あったならいつか

来週ブラジルに戻ったら、AKS 上のアプリケーションも見えるようにする予定です。例えば、いま動いているポッドの数や、昨日のポッドの障害について尋ねる使い方を想定しています。開発エンジニアリングのメンバーは、スタックトレース、メトリクス、データベースのメトリクスを組み合わせたデバッグに、すでにこれを使っています。ボットからチケットを作ることもでき、現在その機能を作っているところです。

### 5.6 Foundry のルーティン機能による定期レポート

Foundry のルーティン（routines）機能を使うと、エージェントにプロンプトを送り、毎日午前 9 時など決まった時刻に実行できます。同じエージェントで、各チームが毎日、Elasticsearch と Azure の情報にもとづく自然言語のレポートを受け取れます。失敗したリクエストのトレース ID も含まれ、プラットフォームで調べたり、ボットに詳しく聞いたりできます。レポートは現在 Elasticsearch 用と Azure 用の 2 本で、来年は AKS 用の 3 本目を足す予定です。チャネルは Telegram や WhatsApp にも広げることを検討しています。

### 5.7 構成要素と運用指標

使っている構成要素は、Azure DevOps、物理ホスト（仮想マシンでも可）、Microsoft Teams、Elasticsearch、Foundry（多用）、Azure Bot です。

運用の指標は次のとおりです。

- 人間が作ったプルリクエストの 100% を、機械がコードレビューします。
- 機械が作ったチケットとプルリクエストの 100% を、人間がコードレビューします。
- 社内でコーディングされるチケットの 5 枚に 1 枚は、機械がコーディングしています。
- チームごとにボットが 1 つあります。

### 5.8 今後と質疑応答

先週から、ブラジルの顧客数社への展開を始めました。顧客からは「気に入ったが、これも欲しい」という要望が出ており、GitHub や GitLab との連携、Claude Code や open code といった他のハーネスへの対応が挙がっています。次のステップは、アイデアをまとめたリポジトリ（コードではなく、プロンプトや画像も含む）として共有する予定です。登壇者は LinkedIn などで記事、動画、ライブ配信（Foundry、Azure、C#、アーキテクチャ。Microsoft の PM を招くこともある）を発信しています。

質疑応答の時間は設けられておらず、質問はセッション後に個別に受け付けると述べています。

## 6. デモ・手順

登壇者は、スライドを使いながら実際の画面を見せて説明していますが、操作は「ここでラベルを付ける」「ここにコメントを書く」といった短い説明に留まり、画面の細部は音声からは確認できません。語られた順にまとめます。

1. Azure DevOps でチケットを作ります。説明は数行です。
2. ラベル「grill」を追加すると、grill 工程が始まります。エージェントがラウンドごとに質問を出し、選択肢と推奨を示します。
3. コメントで回答し、ラベルを「grill answered」に付け替えます。
4. 約 90 時間をかけて 80 超の質問に答えた大きなチケット（1,300 行）の結果を見せます。
5. ラベル「ready」でコーディング工程を開始します。チケット検証、複雑度判定、計画の順に進みます。
6. 計画を確認し、問題なければ「ready to execute」と入力します。
7. Teams で、Joker に「過去 90 日の AI コスト」を質問します。
8. Joker に Elasticsearch のトレース ID の情報を質問します。
9. Joker に Azure の操作履歴と DTU 使用率を質問します。
10. 定期レポート（Elasticsearch 用、Azure 用）の画面を見せます。

## 7. 注意点・発表者の気付き

- チケットの質に時間をかけるのが最重要です。登壇者は、grill がコーディングで最も大事な部分だと述べています。
- 開発者は、実装に費やす時間が減る代わりに、冒頭で業務ロジックと実装方針を理解し、最後にエージェントのコード品質を確認することへ時間を使うようになります。
- 完全自律は望ましくありません。計画とコードの良し悪しを人間が確認し、エージェントが何を作っているかを理解した状態で進めます。登壇者は先週の Outlook の障害に触れ、同じような事態を避けたいという趣旨で語っています（具体的な内容は発話では確認できません）。
- 大規模な 1 枚のチケットは例外的で、通常は小さく分割します。
- Foundry を使っている場合、ボットが表示するコストは実際の支払い（トークン）と一致しません。
- このソリューションは各チームが用意したエージェント、スキル、プロンプトに依存します。
- 登壇者は、今回見せた画面のチケットを先週書いたもので、モックではないと述べています。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- 大規模な例では、7,000 超の AI クレジット（約 73 ドル）、3 時間のコーディングで 600 ファイルを生成し、同日中に本番投入できました。
- 人間が作ったプルリクエストのすべてを機械がレビューし、機械が作ったものはすべて人間がレビューします。
- 社内のチケットの 5 枚に 1 枚は機械がコーディングしています。
- 進捗確認や、本番や Azure の情報への問い合わせを、Teams だけで済ませられます。
- 毎日の自然言語レポートで、障害トレースの手掛かりを得られます。
- 顧客数社への展開が始まっています。

## 9. まとめ

チケットに質問で磨きをかけ、複雑度に応じたモデルで計画し、開発者が用意したエージェントとスキルでコーディングするソフトウェアファクトリーが紹介されました。Teams のボットを通じて進捗確認、コスト確認、Elasticsearch と Azure の観測、定期レポートまで扱えます。登壇者の結論は、最初の工程に時間をかけ、最後は人間が品質を確認する、というものです。
