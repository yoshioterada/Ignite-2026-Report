# BRK273 Bring GitHub Copilot where you work

## 1. はじめに

このセッションは、GitHub Copilot を「どこで使うべきか」という、登壇者が毎日のように聞かれるという質問に答える発表です。結論は最初に示されます。**使う場所は自分の仕事場所に合わせて選べばよく、どの場所でも同じ Copilot のエージェント基盤（ハーネス）が動いている**、というものです。

内容の大半はライブデモです。2 人の登壇者が、映画の鑑賞記録アプリ「Theater Log」を共同開発しているチームという設定で、GitHub Copilot アプリ、Slack と Teams、GitHub のモバイルアプリ、VS Code、Copilot CLI を順に操作します。セッションをスマートフォンで始めて別の画面で続ける流れや、複数のセッションを並行して走らせる使い方が具体的に示されます。後半には、コネクタによるカスタマイズと、新しく提供された Automations（自動化）の紹介もあります。

開発環境が IDE、ターミナル、チャット、モバイルと分かれている開発者が、Copilot を場所をまたいで使うイメージをつかむための資料として読めます。

## 3. 何に関する発表か

デモ用の題材は Theater Log です。チームで観たい映画をウィッシュリストに入れ、短いレビューを書けるアプリで、iOS はネイティブ Swift、Android は .NET MAUI で作られています。Web サイトも制作中です。チームは Sheena と James のほか、Katie と John の 4 人で、離れた場所で仕事をしている設定です。

## 5. 発表内容の詳細

### 5.1 同じハーネスがどこでも動く

冒頭で、Copilot の接点が CLI、IDE、アプリ、Web、モバイルにあり、すべて同じハーネスの上で動くと説明されました。モデルの選択、メモリ、キャンバス、コンピューター操作、クラウドエージェントがその上にある機能です。登壇者は「1 日に 28 回くらいは聞かれる質問」として、どこで使うべきかを取り上げ、答えが一つに決まらないこと自体が製品の方針だと述べました。

なお、発表の途中でスライドが表示されない問題が起こり、最初の説明をやり直しています。内容に影響する話ではありません。

### 5.2 GitHub Copilot アプリ（Sheena のデモ）

Sheena は GitHub Copilot アプリを見せ、「Copilot のライセンスがあるのにこのアプリを使っていないなら、使い方を間違っている」と冗談めかして述べ、自分は毎日使っていると話しました。セッションを始めるときに選べる項目が整理して説明されています。

| 選択項目 | 説明された内容 |
| --- | --- |
| コンテキスト | GitHub のリポジトリ、Issue、別のセッションを添付できる |
| 実行環境 | 自分のコンピューターまたはクラウド。クラウドを選ぶと、ノート PC を閉じても作業が続き、スマートフォンから操作を誘導できる |
| モード | ガイド付き（エージェントが行う内容を確認しながら誘導）、先に計画を立てる、おまかせで任せきる |
| モデル | Copilot Fusion や、複数のモデルから選択 |

このほか、複数のリポジトリをまたいだチャット、一般的なセッション、プロジェクトやセッションに絞った作業ができます。複数のプロジェクト、サービス、セッションを扱える、エージェント中心の作り方だと説明されています。

**プロジェクト**：Sheena は、Theater Log 用に作ったプロジェクトを見せました。3 つのリポジトリを 1 つのプロジェクトにまとめて、「リポジトリを超えて、一緒に取り組んでいる仕事」という単位で整理できます。このプロジェクトは、アプリのマーケティング Web サイトを作る目的のものです。

**Web サイトのモックアップ**：最初にエージェントへ Web サイトのモックアップ作成を依頼済みで、ライブラリにいくつものモックが保存されていました。チームのフィードバックを得るため、Issue を作り、そこからプロトタイプも起動済みだと説明しています。

**チームの作業負荷キャンバス**：James が作った、チームの作業を整理するキャンバスが表示されます。Sheena は一日の始まりに、自分に割り当てられた Issue を確認する習慣があると言い、Issue の 1 つを、余裕がありそうな Katie に付け替えました。画面の更新に少し時間がかかり、反映された後に、Katie にまだ余裕があることを確認しています。

**ラベルによる一括起動**：Sheena に割り当てられた Issue に「fit and finish」（仕上げ作業）のラベルが多いことに気付き、「Theater Log の Issue のうち、自分に割り当てられていて fit and finish のラベルが付いたものについて、セッションを起動して」と依頼しました。Issue は 3 つのリポジトリのどれにあってもよく、Copilot が探し出します。説明では、画像生成を使い、GitHub にサインインしているので Issue 連携も使える、とのことです。実行場所は、クラウドを指定していないのでローカルだと登壇者は説明し、クラウドを指定すればクラウドでも動くと補足しました。結果として 4 つのセッションが起動し、概要タブで確認できました。

### 5.3 Slack のコードチャンネル

Sheena は Slack の Theater Log チャンネルを開きました。ここでチームが仕事を調整しています。前週、James からウェブサイトのモックアップについて聞かれ、Sheena が作成した Issue を共有していました。James は内容を確認し、問題ないという返信と、プロトタイプを作ってほしいという依頼をしています。

そこで Sheena は、Slack 上で GitHub を呼び出し、共有した Issue のデザインに基づいてプロトタイプを作るよう依頼しました。GitHub をエージェントとして Slack に追加し、チャンネルにリポジトリを設定しておけば動きます。Teams でも同様に使えると説明されています。

登壇者は、チームの日常的な使い方も紹介しました。誰かが別の人に質問したときに、同じ質問を GitHub に投げれば、エージェントがコードを調べて実際の状況を答えてくれます。別の画面に移動せず、1 つの会話に文脈が集まる点が利点です。GitHub 社内でも普段の仕事のやり方に組み込まれていると述べています。

**コードチャンネル**：依頼すると、コードチャンネルが立ち上がります。登壇者は、1 つの作業に関する会話をまとめた、チームと GitHub のブレークアウトセッションのようなものだと例えました。中ではインライン差分が見られ、Copilot と GitHub が会話を聞いていて、必要に応じて思い出させてくれます。デモでは、別の作業で既に作っていたプロトタイプ（エージェントが作った HTML）を表示し、そこでライトテーマの実装を依頼すると、すぐにセッションが立ち上がる様子を見せました。チャンネルは PR にリンクされます。

### 5.4 Pull Request と Agent Merge

コードチャンネルからつながった PR には、マージコンフリクトがありました。Sheena は、すでに Copilot にレビューを依頼済みでしたが、変更を加えたので、再レビューを依頼し直すつもりだと言いました（順序が逆だった、と本人が述べています）。コンフリクトを Copilot が検出していました。

PR の詳細パネルでできることとして、次が説明されました。

- Copilot のチャットを開いて、コメントについて質問する
- チャットウィンドウで直接「この問題を直して」と頼む
- マージ状態のパネルから、Copilot に PR を見張らせて修正させる

デモでは、**Agent Merge** をオンにするボタンを押し、あわせてコンフリクトの修正も依頼しました。Agent Merge をオンにすると、新しいクラウドセッションが自動で立ち上がります。コメントへの対応だけでなく、チームが複数の PR を進める間、継続的に監視を続けます。CI の失敗などの問題も自動で修正し、クラウド上でできること・できないことは利用者が制御できます。多数の PR を扱うチームでは、コンフリクトが絶えず発生するため便利だという説明でした。Agent Merge は、Copilot アプリ、VS Code、Web で使えるとのことです。

同じハーネスが Web でも、クラウドのサンドボックスで動いている点も強調されました。

### 5.5 スマートフォンからのクラウドセッション

Sheena は、あとで Web サイトの SEO 最適化に関する Issue を作りたいと思い出したという想定で、スマートフォンを使いました。theater log の Web サイトのリポジトリを開き、エージェントセッションを開始して、「このリポジトリに、Theater Log Web サイトの SEO 最適化に対応するための Issue を作成して」と話しかけます。これにより、Web と同様、新しいクラウドサンドボックスが作られます。

会場に GitHub のモバイルアプリを入れている人、スマートフォンからセッションを始めたことがある人を尋ねたところ、後者が少なく、「全員やってほしい」と述べています。登壇者が好む使い方は、会議や食事の前など待ち時間に、エージェントを待たせずにスマートフォンから作業を進めることです。前夜に BART（電車）で Oakland に戻る 30 分間、マージや新しい作業の起動を行ったと話しました。

James の提案で、セッションの 3 点メニューからターミナルを開き、ls を実行しました。これはクラウド上の実際の仮想マシンに接続していて、ディレクトリはまだ空だと説明されています（続くスタイルガイドへの言及は聞き取りが不明瞭です）。完全なクラウドマシンが用意されている、という説明です。そのセッションは、スマートフォン、Web、GitHub Copilot アプリのすべてに同期されて表示されました。

### 5.6 VS Code（James のデモ）

James は、VS Code の利用者が 5,000 万人以上いると述べ、自分は 安定版、Insiders 版、Visual Studio、Copilot アプリ、ターミナルをすべて日常的に使っていると話しました。自作の VS Code 用テーマ「Bananify」（Banana Cream）も紹介しています（Visual Studio 版もあると話しています）。

**モバイルキャンバス**：Copilot の各サービスにまたがるキャンバスのうち、.NET MAUI チームが作った、実際に動いているアプリを見せるものを開きました。GeoCities 風のテーマを試している最中だと説明しています。チームの作業負荷キャンバスも、Sheena が Copilot アプリで見せたものと同じものが VS Code 内に表示されます。

**モデルと Copilot Fusion**：新しいセッションで使えるモデルとして、Microsoft、OpenAI、xAI、Anthropic のモデルがあると述べ、自分の OpenRouter キーや OpenAI のキーを持ち込むこと、ローカルモデルを動かすこともできると説明しました。Copilot Fusion については次のとおりです。

| 設定 | 説明された内容 |
| --- | --- |
| Standard | 自動モードのようなもの。プロンプトと複雑さからモデルを自動で選ぶ |
| High、Max | エージェントのオーケストレーター。複数のモデルを使い、コストを最適化する |

登壇者は、Copilot Fusion が Terminal Bench で 1 位であり、Claude Code と Opus 5.5 を 5 ポイント上回りながら、価格は約 3 分の 1 だと述べました。Sheena も、コストと効率の両面で最適化する方法だと冒頭で紹介し、すべての場所に展開済みだと話しています。

**画像生成でアプリアイコンを作る**：アプリアイコンの新デザインを考えるという想定で、1 つではなく、選べる 5 つの異なるアイコンを作るよう依頼しました。権限は「補助的な許可」の設定にし、途中で確認を省いて進める設定（本人の言葉では YOLO）にしています。画像生成ツールを使うよう明示して再送信すると、エージェントはデザインファイルを読み、画像生成の機能を呼び出しました。登壇者の説明では、メインのモデルがプロンプトと必要な作業を理解したうえで、Web 上の専用の画像生成モデルを呼び出し、デザインガイドラインに沿った画像を作らせています。Copilot Fusion は Standard を選んでおり、モデルの選択結果が画面に出ます。結果として、暗めのテーマの興味深いデザインがいくつか出来上がり、「現在のものより良いものもある」と評価しました。なお、待っている間は VS Code のペットの Blobby が動いていて、実績や帽子、色の変更もできます。

**エージェントウィンドウ**：これまでの VS Code はエディター中心の体験でしたが、画面上部のボタンから開く「エージェントウィンドウ」で、Copilot アプリと似たエージェント中心の画面になります。このボタンは約 7 か月前から存在するとのことです。左側にはプロジェクト、複数のリポジトリ、チャットが並び、Teams、GitHub のモバイルアプリ、github.com から来るクラウドセッションやローカルセッションが同じ場所に表示されます。同じセッションが各場所で同期されるうえ、作業負荷キャンバスも利用できます。

新しいセッションを始めるときは、実行環境（WSL、Dev Tunnels、クラウドなど）、作業対象、ワークツリーかブランチか、モデルを選べます。Issue などの文脈も添付できます。

デモでは Issue 47（Android の半星評価に関するバグ）の内容を貼り付け、Copilot Fusion の High を選んで実行しました。この方法は独立したワークツリーを作り、既定の動作は Copilot アプリと同じだと説明しています。ワークツリーは、コードの浅いクローンのような形で、1 台のコンピューターで複数のブランチを同時に作業するために使います。

以前に別の Issue で同様の作業を済ませていた PR も開きました。ブランチに PR がある状態では「PR を作成」ボタンが表示され、変更が左側に出て、コメントを付けたり、拡大してインライン表示にしたりできます。PR のチェックとステータス（CI の実行結果）も見られ、**自動の Autopilot マージ**をオンにすると、準備完了としてマークし、自動でマージするかどうかも選べます。CI やコメントも見る点は、Web で見せた内容と同じと述べました。

マイクのボタンで音声入力もできます。デモでは、アプリにも音声入力のボタンがあれば良いと話し、そのための Issue を音声で作成し、新しいクラウドセッションを起動しました。VS Code 内に、クラウドセッションと GitHub セッションが表示され、サンドボックスで安全に動くと説明しています。

### 5.7 リモート接続

VS Code の「リモート接続」（Copilot アプリでも可）を使うと、自分のマシンのセッションの体験を Web と GitHub.com に公開できます。デモでは、スマートフォンに通知が多数届き、github.com の /copilot を開きました。そこにはミッションコントロールのような画面があり、手元のマシンのセッションが、スマートフォンや github.com からも見られます。登壇者は、リモートの安全な環境へ特権的なアクセスを与える操作であり、「Microsoft と GitHub は信頼の上に成り立っている」ため、アクセスするマシンを選べると述べました。ほかにも複数のマシンが「エージェントの準備ができた状態」で並んでいる様子が見られます。

### 5.8 ターミナル（Copilot CLI）

James は VS Code のターミナルで copilot と入力し、Copilot CLI を起動しました（テーマは白）。Theater Log のフォルダーで、アプリや VS Code と同じように起動します。同じ指示、MCP サーバー、カスタムエージェントがチームで共通して使えます。スラッシュコマンドも、ask、autopilot、code、VS Code を開くコマンド、コンピューター操作、コピー、委任など、ほぼ同じです。同じハーネスであることがその理由として語られました。リモート環境やクラウドセッションにつなぐことも、ここからクラウドセッションへ委任することもできます。

CLI は TUI（ターミナル上のユーザーインターフェース）です。画面上部の「sessions」で、クラウド、ローカル、リモートのすべてのセッションを一覧できます。そこから Issue、Pull Request、GIF なども見られます。

デモは次の順で進みました。

1. 実際の課題として、アプリの利用開始時に招待コードが必要で、コピー操作が面倒な点を取り上げ、ワンタップのコピー操作を追加したいと説明した。
2. Issue を選ぶと全文が読み込まれ、操作として「github.com で開く」、「チャットに追加」、W キーで「ワークツリーを作成」を選べると説明した。
3. W を選んで、この Issue 専用のワークツリーを作成した。長い名前が付いており、何が作られたか分かるという説明だった。
4. フォルダーを信頼し、Copilot Fusion を選んだまま、Tab キーを 1 回押して計画モードに入った（/plan でも可）。Autopilot モードにもでき、「実装して」と指示した。
5. 権限の扱いは Copilot アプリと同様に利用者が制御できると説明し、実行した。Copilot Fusion は単純な作業と判断し、**GPT-6 Luna** を使った。
6. 作業中に左矢印キーを押して、動作中のセッション一覧へ移り、作業負荷キャンバスを開いた。キャンバスは CLI でも使えることを示した。

別のセッションも見せました。ウィッシュリストの Issue を実装させたもので、チームでウィッシュリストに入れた映画について、Sheena が観たかどうかを James が見られなかったため作った機能です。PR は「390 行の変更と 78」を生成したと語られています（78 の単位は発話では確認できません）。確認方法として、次が示されました。

- diff を開くと、全画面のインライン差分が読み込まれ、Swift のファイルをスクロールして見られる
- 各コメントを順に見たり、差分を分岐させたり隠したりできる
- 行にインラインでコメントを付けると、それがエージェントに送られて実装される
- `/code` を実行し「Continue in Code」を選ぶと VS Code が起動し、その PR を VS Code で直接開ける（ウィンドウが他のウィンドウの後ろに隠れていたが見つかった）

これにより、CLI と VS Code が同じセッションであることを示しました。その後、Issue に戻ると先ほどのタスクがすでに終わっていたので、「これを Android でもやって」と追加で依頼しました。

### 5.9 ask コマンドと Teams

長時間動いているセッションで便利な機能として、**ask（ついでに質問する機能）** が紹介されました。実行中のセッションを中断したり、コンテキストを膨らませたりせずに、そのセッションについて質問できます。デモでは `/ask` で「iOS の実装の概要は何か」と尋ね、回答が表示され、Ctrl+E で展開でき、追加質問もできます。エージェントとのサイドチャットとして使える、という説明です。この機能はどのサービスでも使えるとされています。

また、VS Code、Visual Studio、ターミナル、スマートフォンのいずれにいても、動作中のセッションが青いバーとしてリアルタイムに表示されます。セッションの例として「retro theme audit（レトロテーマの監査）」という名前のセッションが見えました。

続いて James は Teams を見せました。Sheena が Slack 派なのに対し、自分は Teams も使う、と述べ、Teams にも同じチームのチャットがあることを見せました。そこで「@GitHub」と入力し、58 番（プッシュ通知）に取りかかるよう依頼しました。GitHub が目の絵文字のリアクションで確認したことを示し、Slack と同様に動き出します。GitHub は、Slack のチャンネル、メッセージ、会話に追加でき、Teams の会議、チャット、チャンネルにも追加できると説明されました。やり取りは各場所で同期され、チャンネルキャンバスという、コードチャンネルと同様の対話型の画面が表示され、計画、作成、マージまでが進みます（呼び名について、発表者同士が「チャンネルキャンバス」で一致させていました）。

### 5.10 コネクタと Automations による拡張

最後に、ここまでの内蔵機能ではなく、拡張の話として、最近リリースされた 2 つの機能を Sheena のマシンで紹介しました。

**コネクタによるカスタマイズ**：1 つのインターフェースで、ワンクリックで統合を追加できる仕組みです。MCP を使ってデータをセッションに取り込む作業が簡単になるという説明で、Sheena は複数の MCP サーバーを入れており、現在は Slack も入れています。「この 1 日で自分が返信し忘れたものは何か」というセッションを実行すると、探してくれると例を挙げました。

**Automations**：毎日行う作業、たとえば Slack の確認や、毎日手動で実行しているレポートの問い合わせを、自動化できます。名前を付け、実行のきっかけ（トリガー）をいくつかから選び、プロンプトを書き、スケジュールや Dependabot アラートなどで毎日実行させられます。毎日の作業を覚えておく負担がなくなる、と説明されています。Sheena は、これらのツールで自分の能力が急速に高まったと感じており、この機能は、考えることが増えた日常の作業を自動化する次の段階だと述べました。

画面での設定手順の詳細（ボタン名や入力値）は、発話からは確認できません。

## 7. 注意点・発表者の気付き

- 実行場所の指定がなければ、セッションはローカルで動く、と説明されています。クラウドで動かすには、そのように指示する必要があります。
- Agent Merge でクラウドセッションがコメントや CI の失敗に自動対応しますが、何をクラウドでしてよいかは利用者が制御する、と説明されています。
- リモート接続では、リモートの環境へ特権的なアクセスを与える、と登壇者自身が表現しており、アクセスさせるマシンを自分で選ぶ形です。
- デモの途中で、スライドが見えない問題、画面の更新が遅れる、画像生成が 1 回目で動かず再送信が必要になる、といったことがありました。画像生成は、使うツールを明示して再依頼しています。
- 登壇者は PR の再レビューの依頼順を誤ったことを、自ら指摘しています。
- 画像生成の待ち時間に、デモ用の Wi-Fi に触れる発言がありました。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 1 つのサブスクリプションで、CLI、IDE、アプリ、Web、モバイルのどこからでも使える。
- どの場所でも同じハーネスのため、スキル、MCP サーバー、カスタムエージェント、スラッシュコマンドが共通で使える。
- セッションが各場所に同期され、スマートフォンで始めて別の場所で続けられる。
- ノート PC を閉じてもクラウドで作業が続く。
- Slack や Teams の会話の中で、チームが GitHub に作業を依頼でき、文脈が 1 つの会話に集まる。
- Agent Merge により、コンフリクトや CI の失敗への対応を自動化できる。
- Copilot Fusion により、コストと効率の両面を最適化できる。登壇者は、Terminal Bench で 1 位であり、Claude Code と Opus 5.5 を 5 ポイント上回りながら、価格は約 3 分の 1 だと述べている。
- Automations により、毎日の定型作業を自動で実行できる。

## 9. まとめ

GitHub Copilot は、CLI、IDE（VS Code と Visual Studio）、GitHub Copilot アプリ、Web、モバイル、Slack、Teams のどこからでも使えます。すべてが同じハーネスで動くため、指示や MCP サーバー、カスタムエージェントを共通にでき、セッションも同期されます。実行場所は、ローカルとクラウドから選べます。
