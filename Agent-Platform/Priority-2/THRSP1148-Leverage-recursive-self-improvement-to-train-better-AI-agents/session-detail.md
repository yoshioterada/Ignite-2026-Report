# THRSP1148 Leverage recursive self-improvement to train better AI agents

## 1. はじめに

このセッションは、Napster が自社の「Omni agent」（どの Web サイトにも配置できる会話型エージェント）を、再帰的な自己改善（recursive self-improvement）で鍛える方法を紹介する、約 20 分の発表です。モデルを追加学習せず、エージェントに持たせる道具一式（発表者の言葉でハーネス）を作って直す、という考え方が軸になっています。

自己改善というと「システムが勝手に変わり、何が変わったか分からなくなる」という怖い話になりがちです。この発表は、**変更履歴、品質確認、人による公開判断を組み込むことで、自己改善を管理可能にする**手順を、3 つの段階に分けて説明しています。画面を使ったデモは行われておらず、短い紹介映像が 1 本上映されました。

## 5. 発表内容の詳細

### 5.1 Omni agent と、道具を持たせる理由

Omni agent は、Web サイト、複雑な CRM、店舗のキオスク端末（Napster Station）など、事業が顧客と接するあらゆる面に置けるエージェントです。例として旅行予約サイトが挙げられました。利用者は物件を探し、比べ、部屋を見て、予約し、第三者サイトで航空券も取ります。手順は多く、Omni agent はその複雑さを取り除きます。利用者は会話するだけで、エージェントが利用者に代わって Web サイトを操作する、つまり利用者の「手」になる、という説明です。

Web サイトごとに構造も使い方も違うため、エージェントを適応させる必要があります。方法の 1 つは対象の用途向けにモデルを追加学習することですが、追加学習のたびにモデルの挙動を制御するのが難しいと述べています。そこで Napster は、モデルは変えず、その上に堅牢なハーネス（対象サイトを操作するための道具一式）を持たせています。

### 5.2 紹介映像

映像は、Omni agent の 1 日を、エージェント自身の語りで描くものでした。映像で語られた内容は次のとおりです。

* 映像の語り手は「Sana」と名乗る Omni agent で、Booking.com に採用された。誰かと話す前に、システムがサイト全体（すべてのページ、価格、規定）を読み、訪問者が尋ねそうな何百もの質問と、たどりうる経路を予測する
* 与えられる道具は 11 個で、検索、比較、物件を開く、部屋を読み上げる、選ぶことに足りる。守る規則もあり、支払わない、サインインしない、作り話をしない
* ここまでの基本訓練は約 1 時間
* 次に「道場」へ行く。実際のサイトで何百もの実際の会話を練習し、間違える。例として、1 泊の料金を旅行全体の費用と読んでしまう。コーチはエージェントを直さず、エージェントが持っていた道具を直す。再び試して合格になる。間違いは 1 回だけ。観察し、修理し、繰り返す
* 午後には、昼に犯した間違いはしなくなる
* 会ったことのない人が、旧版と新版の同じ会話を並べて再生し、すべての答えを、ページに実際に表示されている内容に照らして判定する。結果は 16 件中 16 件で、動いていたものは何も壊れていない。ただし、公開の判断はエージェントではなく人が行う
* 6 時に公開。何千もの会話を同時に受ける。答えは記憶ではなく、必ずページから出す。予約の確定は利用者が行う。いつかどこかの会話がうまくいかなくなるので、そのときは道場に持ち帰る。エージェントは学び終えることがない、という言葉で結ばれる

Dima は、この映像は圧縮してあるが、各段階は実際のものだと補足しています。

### 5.3 ハーネスと変更管理

エージェントは設計段階で Web サイトを学び、サイトの能力を把握して、適切な道具を自分で作ります。予約サイトなら検索、比較、予約の機能に対応する道具です。

Omni agent と Web サイトのやり取りの各段階は、1 つ 1 つ別のファイル（群）になっています。そのため、追加学習したモデルと違って、道具や機能ごとの変更履歴を細かく追跡・維持できます。公開前には、次の手順を通ります。

* 品質確認（QA）を行う
* 書面の記録が残る
* 該当の道具のテスト報告がある
* 旧版と新版の差分（変更点）が示される
* **すべての変更は、人が公開する**

自動更新が体験を壊して回帰を入れる、ということが起きないようにする、という説明です。

### 5.4 3 つの段階

Napster の Omni agent を作る 3 つの段階は、次のとおりです。

| 段階 | 内容 |
| --- | --- |
| 第 1 段階：自動調査 | Web サイトの能力を調べ回る（検索、比較、予約手続きなど） |
| 第 2 段階：訓練（道場） | 再帰的な自己改善が実際に起きる段階 |
| 第 3 段階：レビューと公開 | 候補版を別のエージェントが評価し、基準を満たせば人が公開する |

第 3 段階は発話で名前が付けられていませんが、訓練の後に、レビュー用エージェントによる判定と公開が続く流れが説明されました。

### 5.5 訓練（道場）の仕組み（Igor）

訓練では、第 1 段階で分かった情報に基づき、システムが想定顧客や訪問者との会話を模擬します。

* 合成されたエージェントが、サイトが現在実際にできることを質問する
* 実際のブラウザーで、稼働中のサイトに対し、サイトが既に持つセキュリティポリシーの下で行う
* 道具の呼び出し、ページのスナップショット、エージェントの回答はすべて記録される

会話が失敗すると、修復用エージェントが診断のスキルを実行します。その役割は、失敗の原因が道具一式（パッケージ）にあるのか、エージェントの発言にあるのかを見分けることです。

* **原因が道具にある場合**：修復用エージェントが道具を直し、その事例の回帰テストを作り、一式を作り直して再実行する。流れは「観察、修理、繰り返し」
* **原因が発言にある場合**：コードは直さない。修復用エージェントが会話ごとに、指示のヒントを作り、新しい版とともに公開される。新版では、何が変わったかの報告が見られる

開発中に見た例が 2 つ挙げられました。

| 事例 | 問題 | 修正 |
| --- | --- | --- |
| 予約サイト | 1 泊の料金を、旅行全体の合計料金として提示した | モデルに「価格に注意するように」と説明するのではなく、道具を直した。宿泊全体の合計、1 泊の料金、取り消し線付きの料金を別々の 3 つの数値で返すようにし、各料金に取り消し条件と税も付くようにした |
| Decathlon | 買い物客がスノーパンツを尋ねたが、ジャケットやブーツなど 68 点が表示され、スノーパンツは 1 つもなかった。道具が買い物客の指定を落とし、絞り込み検索をせずに全体を出していた | 修復用エージェントが道具を直し、尋ねた内容そのものが表示されるようになった |

### 5.6 レビュー用エージェントと公開の基準

安全のための仕組みとして、修復を行うエージェントは、**自分の作業を自分で採点しない**と説明されました。訓練が終わり、コードを固定してハッシュ値を付けた候補版ができると、レビュー用エージェントが初期版と候補版を並べて比較します。このエージェントには、コードを変えたり、プロンプトを調整したりする権限がありません。比較して、判定と報告書を作るだけで、その報告書をもとに決定が行われます。

候補版が通るべき基準は次のとおりです。

* 確認項目の少なくとも 80% が確認され、回帰が 0 件、**または**修復が確認された割合の純増が 10 ポイントを超える
* 重大な問題がない
* 1 つの道具あたり、再試行は最大 1 回

訓練での例として、次の数値が示されました。

| 対象 | 訓練前 | 訓練後 |
| --- | --- | --- |
| Decathlon | 25 項目中 11 | 25 項目中 25 |
| Expedia Group のサイト | 56 項目中 23 | 56 項目中 56 |
| Rabobank | 発話では「40 項目中 17」から「33」と聞こえるが、数値は確定できません | 同左 |

Rabobank については、7 件の確認が実行されなかったこと、報告書上は「不合格」と記されるが、進捗の割合は 80% を超えるため公開できる、という説明がありました。

自動調査と訓練は 1 つの処理として扱われます。訓練が基準に達しなければ何も公開されず、何が起き、なぜ止まったかが通知されます。基準に達すれば、すべての確認と修復、その根拠を載せた品質報告書とともに、その版が提供されます。

### 5.7 運用中の継続学習と、評価用 LLM

Dima は、従来のやり方では、エージェントを展開するのに IT 部門やエンジニアリングチームが数か月かけて道具を整え、テストし、改善し、モデルを調整し、サイトを変えるとまた最初からになる、と対比しました。Napster の方式では、エージェントが Web サイトを自動で調べ、チームは変更管理の手順を通して新版を展開するだけです。

展開後は、サイトが変わります。機能が増え、フォームがなくなり、新機能が入ります。そこでエージェントは、例えば 1 日 1 回といった決まった周期で、サイトを調べ直します。新しい機能やフォーム、利用者の使い方を見つけ、運用しながら学び、自己学習の輪が閉じます。

評価には、「LLM を判定者にする」方法を使うと述べられました。エージェントを動かす LLM に自分自身を評価させると、ほぼ必ず満点になるため、**別の LLM が評価する**必要があるという説明です。

### 5.8 追跡可能性と外部での使われ方

AI を放し飼いにして、勝手に展開され、何かが壊れても、人が変更を所有していないため、どこから調べるか分からない、というのが怖い点だと述べています。この訓練では、変更の記録が文書として残り、各段階の差分でどこが変わったかが分かります。変更管理のため、ユーザー受け入れテストの報告書もあり、すべてのテスト結果、すべてのユースケースと利用者の流れ、それらがどうテストされたか、流れの中の抜けや改善点が確認できます。

Omni agent は世界中どこの利用者にも、同時に、大規模に応対できます。10〜15 回のクリックを、人間らしい会話に圧縮するという説明でした。

## 7. 注意点・発表者の気付き

* モデルを追加学習しないのは、変更点が追えず、再テストが必要で、回帰の危険が高いためです。
* エージェントが自分の作業を採点すると、満点に近くなるため、評価には別の LLM を使います。
* 公開は、必ず人が行います。自動更新で体験が壊れるのを避けるためです。
* 修復用エージェントは、プロンプトの注意書きではなく、道具そのものを直す方針です（価格の例）。
* 紹介映像は、時間を圧縮したものと断られています。映像中の数値（11 個の道具、約 1 時間、16 件中 16 件）は映像内の説明であり、特定の導入先で実際に測った値かどうかは、発話では確認できません。
* Rabobank の数値は、音声から確定できませんでした。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* IT 部門やエンジニアリングチームが、道具の調整やテストに数か月かけずに済む。変更管理の手順を通して新版を展開するだけで済む
* サイトが変わっても、エージェントが定期的に調べ直して学ぶため、利用者側の作業が不要
* 変更履歴、差分、品質報告書、ユーザー受け入れテストの報告書が残り、問題が起きたときに調べられ、承認と差し戻しが容易
* 利用者は会話だけで、10〜15 回のクリックが要る操作を行える

導入先での成果指標（削減時間やコスト）は、発表では示されていません。

## 9. まとめ

Napster は、基盤モデルを追加学習せず、Web サイトごとのハーネス（道具一式）を作って直すことで、Omni agent を自己改善させています。流れは、自動調査、訓練（道場）、レビューと公開です。訓練では、実際のサイトで模擬会話を行い、失敗を道具の問題と発言の問題に分けて直します。レビュー用エージェントが別に判定し、80% 以上の確認と回帰 0 件、または 10 ポイント超の純増などの基準を満たせば、人が公開します。

公開後も、1 日 1 回といった周期でサイトを調べ直して学び続けます。変更の記録と差分が残るため、自己改善を人が管理できる、というのが発表の結論です。
