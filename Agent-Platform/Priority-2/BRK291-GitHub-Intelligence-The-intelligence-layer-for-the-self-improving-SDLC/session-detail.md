## 5. 発表内容の詳細

### 5.1 デモの問い

Copilot app で入力した問いは次のとおりです。特定のリポジトリについて、2 週間などの期間にマージされた PR と、そのリポジトリの貢献者が使った Copilot セッションを見て、何が妨げになったのか、失敗の主な原因は何か、というものです。実行には時間がかかるため、完了済みの結果に切り替えて説明されました。

結果には、分析上の摩擦の原因、セッション上の摩擦の原因、PR とセッションの対応付け、エージェントあり・なしでの作業の違いなどが並びます。失敗の傾向としては、ファイルが読まれていない、成果物が欠けている、本番システムの可観測性が足りない、といったパターンが示されました。さらにエージェントは、どこに注力すべきかの推奨も返しています。

目的は、エンジニアリングマネージャーの立場なら、チームが詰まっている箇所を知り、優先順位付け、コーチング、障害物の除去に生かすことです。GitHub は Copilot 製品自体も作っているため、この使い方で得た知見を顧客向け製品にも反映していると述べています。システムの仕組みや、複数プロジェクトの関係を把握する用途にも使えるとの説明もありました。

### 5.2 内部のしくみ

構成図に沿って次のように説明されています。

1. 外側にエージェントのループがあり、ユーザーが Copilot にプロンプトを入力する。
2. GitHub の memory 機能が、関連する文脈をプロンプトに足してから送る。
3. プロンプトは MCP サーバーに渡り、agentic search を実行するサービスを起動する。
4. そのサービスは、使い捨ての GitHub サンドボックスの中で動く。データを非公開に保ち、リクエスト完了後にサンドボックスを破棄する。途中で機密度の異なるツールを使うためである。

情報源は 4 種類です。

| 情報源 | 内容 |
| --- | --- |
| GitHub のデータ | PR、コミット、Issue |
| コード検索 | コードベース自体 |
| セッション検索 | Copilot セッション全体（今回のツール呼び出し失敗はここから得た） |
| キャッシュと API | GitHub SQL のキャッシュと、サンドボックス内で読み込まれる GitHub API ツール |

GitHub API のレート制限に触れ、キャッシュの意図を説明しています。データを SQLite に保存して毎日更新し、大半のクエリはこのキャッシュで答えます。より新しいデータは GitHub API ツールで取得し、エージェントが両者を混ぜて結果を返します。このサンドボックス基盤は、Copilot のクラウドエージェント、GitHub Copilot のチャット、Slack や Teams 上の GitHub と同じものだと述べています。

### 5.3 Copilot memory

Copilot memory は、GitHub ユーザーとしての個人の好みと、作業するリポジトリの慣習を記憶し、時間とともに Copilot を効果的にする機能です。エージェントのセッションやクライアントをまたいで使えます。デモで Ignite の聴衆に向けて話しかけていたのは、事前に Ignite にいることを話して、メモリに覚えさせたためです。

管理面では、企業、組織、リポジトリ、ユーザーの各レベルで提供を制御し、内容の監査とエクスポートができると説明されました。実装は Microsoft の Copilot SDK に組み込まれ、メモリの読み書きのツールを提供します。ユーザーやリポジトリの特定と保存は GitHub のシステムに接続し、データは Azure に保存されます。各 Copilot エージェント製品は Copilot SDK を通じてメモリを扱います。

**効果の測定**：文脈を渡すこと自体が役立っているかは二次的な効果であり、測る必要があると述べています。8,000 件超のクラウドエージェントとローカルエージェントのセッションを、最先端モデルと人間による抜き取り確認で調べました。

- メモリが観察可能な形で役立ったのは、標本の 22%
- 役立ち方は 2 種類。多くは好みの合わせ込み（開発者の好み、Copilot の伝え方）
- もう半分弱は効率向上。メモリなしでも得られる情報に、少ない試行錯誤で到達でき、トークン消費も減るのでコストも下がる

文脈は、持っていなかった情報を新たに与えるわけではなく、そこにあるものから学ぶので、見つけ出す過程が効率化される、という整理です。

### 5.4 Copilot dreaming

dreaming はメモリの対になるもので、メモリがセッション中に働くのに対し、有効にした場合に裏で動きます。過去の作業とセッションを振り返るバックグラウンドのクラウドエージェントのジョブで、継続的な改善をもたらします。

実例は、発表者のチームが Copilot Code Review の開発で受けた PR レビューコメントのスクリーンショットです。人間のレビュアーが「この種の変更に変更ノートは不要で、変更履歴を汚す」といった同じ指摘を繰り返していました。dreaming の適用後は、Copilot Code Review が同種のコメントを出すようになり、コメントには dreaming に由来する旨の表示が付きます。メモリや指示を直接書いたわけではなく、dreaming が PR とセッションから学び、再利用できるスキルと指示に変えて Code Review に渡した、という説明です。もう 1 例は、AI 製品の変更時に評価（有用性、コスト、レイテンシー）を行う、というチーム内の暗黙の決まりごとで、これも自動で案内されるようになりました。

こうした「組織の暗黙のルール」は、新人がいずれ覚えるものですが、レビュアーが気付けるかに左右されず一貫して適用されるのが望ましい、と述べています。スキルのようなものだが、覚えておかなくても自動適用される点が違います。

もう 1 つの役割は、個人のメモリやリポジトリのメモリの整理です。情報を最新、正確、関連性あり、重複なしに保ち、状態を健全にします。名前の由来は、人が眠る間に一部を忘れ、一部を強め、新しい記憶を作ることと説明されました。

### 5.5 コード検索

多くの顧客は数千から数万のリポジトリを持っています。エージェントは手元にチェックアウトしたコードなら grep で探しますが、「この依存関係を他のリポジトリではどう使っているか」といった全体への問いには広範な検索が必要です。検索には 2 種類あります。

| 種類 | 説明 |
| --- | --- |
| 字句検索（lexical） | 文字列やパターンが分かっている場合。デフォルトブランチを索引化した高度に最適化されたエンジンで、完全一致を探す |
| 意味検索（semantic） | パターンが正確に分からない場合。リポジトリをオンデマンドで索引化し、AI モデルが定義する意味で推論する |

どちらも Copilot のすべてのエージェントの画面に組み込まれています。モデルは字句検索には RipGrep を好んで使うことが多く、その上に意味検索を加えられる、という説明です。

### 5.6 分析結果の活用と、組織全体への展開

デモの質問を再実行した結果、失敗の分類や、問題の起きた PR とセッションの件数が前回とほぼ同じで、推奨の優先順位は異なっていました。別のセッションと別の LLM 呼び出しなので非決定性があり、「人間の判断で何をするかを決める必要がある」と述べています。助言をそのまま実装する必要はなく、変更後に同じ検索をもう一度実行し、パターンが変わったかを確認して次に進めばよい、という進め方です。理想は、その種のツール呼び出し失敗が完全になくなることです。

さらに、automations でこのループを組めると述べました。検索し、改善を試み、再度検索して解決を確認し、解決していなければ別の方法で再試行します。この自動化のループは単一セッションに収まらず、チームの数日間の作業にまたがり、単一のリポジトリやチームを超えて組織全体にも広げられます。

**プレイブックの例**：依存関係の使い方を、うまく実現したチームの実装から一般化したプレイブックにし、他のリポジトリに適用します。エージェントに最もリスクの低い、あるいは高い 5 つのリポジトリで試させることもできます。発表者が挙げた「いつもの例」は Log4J で、Log4J を使わない実装を上手にやり遂げたチームを探し、プレイブックを作り、組織内の他のリポジトリで体系的に低コストに保守する、という流れです。組織全体のパターンを見る問題は、単一リポジトリや単一セッションでは扱いにくいという説明でした。

組織全体を見る意味として、クライアントとサーバー、別チームのリポジトリなど、現実には複雑に絡み合った情報があり、チームの頭の中にある知識が必要だと述べています。検索ツールは、パターンの当てはまり方を大規模に集められ、それを活用するのは人間とエージェントのチームです。

### 5.7 システム理解への利用

発表者は同じ道具を、自分たちのシステムの理解にも使っていました。Copilot memory と dreaming の説明、関係するリポジトリ同士のやり取り、dreaming がメモリをどう整理し、どのスコープを扱うか、GitHub のシステム内での配線の詳細などです。エージェントが書いた通信図は、必要以上に複雑かもしれないが情報の流れの感覚はつかめる、とのことでした。エージェントは頼んだ範囲を超え、両システムにまたがる変更の例とその理由も調べてきたそうです。

ここで、コード検索が答えるのは「何を」と「どのように」であり、「なぜ」は文書、Issue、PR にあるという指摘が出ました。なぜその変更をしたのか、優先した理由、正しかったか、問題は直ったか。ある変更に理由があったことを知らない人が、元に戻そうとする場面を防ぐには、その履歴が次に使える形で引き継がれている必要がある、という説明です。

### 5.8 agentic search

最初のデモで使われた機能です。リポジトリのデータの全履歴（PR、Issue、コミット）を、GitHub API や GitHub MCP サーバーで行うようなクエリで、キャッシュ済みの情報と最新の情報を橋渡ししながら問い合わせます。希望すればセッションデータも含められます。ただし含めるかどうかは選択です。好みの Copilot クライアントにつなげられ、独自の分析や automations、今回のような質問ができます。

使い方の例：機能フラグの仕組みや、Copilot クライアントが本番サービスに情報を渡すときの流れを調べる。履歴と変更の追跡、コードの内容の同期を 1 つのプリミティブで見られます。

機能フラグの例も語られました。フラグのテレメトリでトラフィックのすべてが 1 つの分岐に流れていれば、全員に有効化されたということなので、フラグを削除する時期です。1 件ならまだしも、10 件、100 件、月に数千件となると体系的な片付けが必要で、エージェントがコードを多く作るほど難しくなる、という指摘です。文脈が正しければ速く片付けられます。Datadog のテレメトリで全トラフィックが 1 経路になったのを検知して、フラグを自動で削除するよう dreaming に仕向ける、という構想も出ましたが、これは将来の発想として語られたもので、実施済みの機能とは説明されていません。

また、カスタマイズ、メモリ、指示、スキルが古くなると、エージェントが現状に合わない変更をしてしまうため、dreaming のような自己改善の仕組みが古さに気付き、更新を提案することが重要だと述べました。指示やスキルを自分で管理する場合も、メモリやコードレビュー指示を GitHub に任せる場合も、dreaming で変更できるとのことです。

### 5.9 内部ツールの表示（シーケンス図とトレース）

agentic search で作成したシーケンス図と、社内でバイブコーディングにより急いで作った内部ツールの画面が示されました。リクエストの裏側を見るためのもので、全体の所要時間、トークン使用量、回答に使ったクレジット、各所の所要時間、使ったモデルと呼び出し回数、実時間などが分かります。各ステップも表示され、プロダクト開発時のデバッグに日常的に使っているそうです。

示された例では、「プロンプトが GitHub agentic search をどう流れるかを追う図を作る」という依頼に対し、字句コード検索を何度も呼び、ファイルを開いて grep していました。この中で、不要な呼び出しをしているバグを見つけたとも述べています。新機能を作り、それで自分たちのシステムを説明し、さらにその機能自身をデバッグしたという再帰的な使い方です。ただし全機能にこの再帰が必要なわけではない、とも補足しています。

### 5.10 提供状況と導入

| 機能 | 提供状況（発話どおり） |
| --- | --- |
| Copilot memory | 有料の Copilot プランすべてで利用可能 |
| Copilot dreaming | パブリックプレビュー |
| コード検索 | 各エージェントのクライアントとセッションで利用可能 |
| agentic search | 新しい機能で、顧客と共同で作りたい。スライドのリンクからプレビューに申し込む |

agentic search を組織で有効にするには「インスタンス」を作ります。インスタンスは、agentic search を使えるユーザーの一覧と、対象リポジトリの一覧です。有効化には組織の管理者の権限が必要です。誰が、どの情報にアクセスできるかを管理者が決める設計です。申し込みの際に調査などへの連絡に同意する項目があり、共同開発のために有用だと述べています。

## 6. デモ・手順

デモは 1 回で、Copilot app の画面で実演されました（画面の細部は音声からは確認できません）。

1. Copilot app に、リポジトリ、期間（例として 2 週間）、PR とセッションを対象にした失敗要因の問いを入力して実行する。
2. 実行に時間がかかるため、事前に完了させておいた結果に切り替える。
3. agentic search による回答を示す。摩擦の原因、PR とセッションの対応、エージェントの有無による違い、失敗のテーマ、推奨を確認する。
4. 構成図で内部のしくみを説明する。
5. 後半で同じ問いをもう一度実行した結果を見せる。件数は近く、優先順位の順序が前回と違うことを確認する。
6. agentic search で作ったシーケンス図と、内部ツールでのトレース表示を見せる。

## 7. 注意点・発表者の気付き

- 同じ問いでも、実行ごとに結果の順序が変わる非決定性がある。結果の扱いは人間が判断する。
- 文脈を与える機能は、本当に役立っているかを測る必要がある。memory では 8,000 件超のセッションで調べた。
- セッションデータを agentic search に含めるかどうかは選択制。
- サンドボックスは使い捨てで、完了後に破棄される。
- コードは「何を」「どのように」を示し、「なぜ」は別の場所にある。
- 古くなったメモリ、指示、スキルは、エージェントが誤った変更をする原因になる。
- GitHub 社内で効果のあった方法が各社に当てはまるとは限らない。
- Datadog テレメトリを使った機能フラグの自動削除は、構想として語られたもので、提供済みとは述べられていない。

## 8. 利用者にとっての利点

- チームの詰まりの把握：失敗要因の分析を、PR とセッションから横断して得られ、優先順位付けやコーチングに生かせる。
- 好みと慣習の継続：memory がセッションとクライアントをまたいで使え、効率向上でトークンも減る。
- 暗黙のルールの自動適用：dreaming がレビューの繰り返しの指摘を学び、Code Review に反映する。
- 組織全体の保守：多数のリポジトリで依存関係の使い方の探索とプレイブック化ができ、Log4J のような除去作業を体系的に進められる。
- 管理：memory は企業、組織、リポジトリ、ユーザーの各レベルで制御でき、監査とエクスポートが可能。agentic search は管理者がユーザーとリポジトリを指定する。

## 9. まとめ

GitHub は、Copilot のエージェントに、memory、dreaming、コード検索、agentic search という知能の層を提供し、開発ライフサイクルが自分自身を改善する方向を目指しています。memory は有料プランで利用でき、dreaming はパブリックプレビュー、コード検索は各エージェントで利用可能で、agentic search は共同開発のプレビューです。発表者は、人間のチームの学びと、システムの自己学習の両方を前に進めるために、プレビューへの参加を呼びかけました。
