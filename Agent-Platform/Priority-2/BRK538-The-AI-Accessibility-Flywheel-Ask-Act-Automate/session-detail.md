# BRK538 The AI Accessibility Flywheel: Ask, Act, Automate

## 1. はじめに

このセッションは、AI を「仕事を速くする道具」ではなく「仕事を可能にする道具」として捉え直す内容です。登壇者はいずれも障害のある当事者で、自分たちが日々の業務で実際に使っている Microsoft 365 Copilot まわりの使い方を、3 つの段階に整理して紹介しました。

3 つの段階とは、Ask（質問する）、Act（作業を任せる）、Automate（自動化する）です。登壇者はこれを「アクセシビリティ AI フライホイール」と呼んでいます。フライホイールとは、回すほど勢いがつく弾み車のことです。質問を重ねると指示の書き方が上達し、正確な指示が信頼できる作業の委任につながり、繰り返す作業は自動化へ進む、という循環を表しています。

デモは 3 本あり、いずれも録画した動画を流す形式でした。契約書の変更点を洗い出すデモ、案件管理表を自動で作らせるデモ、そして Windows のすべてのウィンドウを自動で最大化するアプリのデモです。最後に、AI の効果を測る指標についての提案と、参加者への「宿題」、質疑応答があります。

## 5. 発表内容の詳細

### 5.1 職場の摩擦と、AI によるその除去

Jamie Dean は図を使って摩擦を説明しました。会議に参加し、文書を読み、社内ツールを使って仕事を完了するという 1 日の流れを想定します。この流れには誰にでも摩擦がありますが、障害があると機会がさらに増えます。

- 難聴の人の場合：会議の字幕がオフになっている、または動作していない。
- 盲目や弱視の人の場合：文書がアクセシブルな形で共有されず、スクリーンリーダーで読めない。
- 社内ツールが「アクセシブルではあるが使いやすくない」場合：クリックやタブ移動が大量に必要になる。

仕事は最終的に終わりますが、扱いにくい画面を操作したり、アクセシブルでない形で出された情報を探したりしている時間は、考える・作る・成果を出すための時間ではありません。摩擦がなくなれば、戦略的に考える時間と生産性と自立性が増えます。

Jeremy Curry は、AI が全員を効率化することは知られていたが、障害のある自分たちがここまで効率的になるとは予想していなかった、と述べました。技術を人に合わせられるようになり、「アクセシブル（そこに到達できる）」から「使いやすい（素早く簡単に操作できる）」へ進んだと説明しています。

### 5.2 フライホイールの 3 段階

Laurie Allen が全体像を説明しました。

| 段階 | 内容 |
|---|---|
| Ask（質問する） | AI に質問する段階。回答に慣れてくると次に進む。 |
| Act（作業を任せる） | Cowork、Scout、Autopilot などのツールに作業を任せる段階。 |
| Automate（自動化する） | 同じ指示や作業を繰り返していることに気づき、自動化に回す段階。 |

各段階は前の段階の勢いの上に成り立ちます。質問すると正確な指示の書き方が身につき、正確な指示が信頼できる作業実行につながり、信頼できる実行が自動化につながります。回すほど速く回り、Jamie Dean が話した摩擦を日々の仕事からより多く取り除けるという考えです。

### 5.3 Ask：検索から対話的な情報収集へ

Laurie Allen は、長年「検索する」を意味する動詞だった「ググる」「Bing する」の位置に、Copilot が置き換わりつつあると説明しました。検索エンジンではキーワードを入れ、リンクの一覧を受け取り、自分で読み込んで情報を整理します。いまは対話しながら情報を集める形に変わっています。

Laurie Allen の例は出張の計画です。車いす利用者としては、アクセシブルなホテルの部屋、車いす対応のタクシー、段差のない入口のレストランを調べて、旅行計画にまとめる必要があります。Copilot に「車いすで利用できるサンフランシスコ旅行を、ホテル、交通手段、レストランを含めて計画して」と頼めば、情報が集まって旅行計画にまとまります。調整は必要ですが、大幅な時間短縮になるとのことです。

Jamie Dean は、自分にとっての価値は情報の集約というより「ナビゲーションの集約」だと語りました。従来の Web 検索では 10 個の Web サイトが並び、情報そのものよりも、それぞれのサイトの中で必要な情報を見つけることが障壁になります。サイトごとに設計が違い、アクセシブルでないものもあります。Copilot なら情報が 1 か所にアクセシブルな画面でまとまり、示された出典（引用元）から、重要な一次情報のサイトへ掘り下げられます。

Laurie Allen は、世界の Web サイトでアクセシブルなものは 4% しかないという事実も紹介しました。

### 5.4 Act：作業を Copilot に任せる

Laurie Allen は、仕事ではアプリを 1 つだけ使うのではなく、1 日中切り替えながら使っていると述べました。音声や別の支援技術を使う人にとって、この切り替えは負担になります。Copilot に望む結果を指示すれば、作業の手順は任せられ、人は戦略的な作業や意思決定など、人が主導すべき仕事に時間を使えます。

**週次報告の例（Laurie Allen）**

会場に、上司への週次報告を作成している人を挙げてもらったところ、手が挙がったのは数人でした。好きな作業かと尋ねると誰も手を挙げませんでした。

- 従来：顧客のスプレッドシートを開く、顧客からの更新連絡をメールから探す、Teams のチャットを検索する、顧客との会議の有無をカレンダーで確認する、要約にまとめる、書式を整える、校正する、上司に送る。毎週金曜の午後に最低 1 時間かかっていました。手順は 6 つ、使うアプリは 4〜5 個で、クリックと音声入力が大量に必要でした。
- 現在：Copilot のアプリで、自然言語で「上司向けの週次報告を下書きして」と頼みます。1 回の指示で済み、本人は内容の確認、修正、メール本文への貼り付けだけを行います。

この指示がうまく機能している要点として、次の 3 つが挙げられました。

1. 参照させたい情報源（ナレッジソース）を指定していること。Copilot が見られるのは本人がアクセスできるもの（メール、Teams のチャット、ファイル）だけで、Jeremy や Jamie のメールは見ません。
2. 書式を指定していること。
3. 上司にとって何が重要か、上司が判断すべきことは何かを伝えていること。

### 5.5 契約書レビューのデモ動画（Jamie Dean）

Jamie Dean は弁護士の業務として契約書のレビューを挙げました。赤字（レッドライン）という言葉のとおり、他者が行った変更を視覚的に示すもので、視覚に頼る作業です。特に PDF で色や書式によって変更箇所を示されると、スクリーンリーダーでは変更を見つけにくくなります。これまでは、原本と修正版を並べて開き、スクリーンリーダーで 1 行ずつ読む必要があり、非常に手間がかかっていました。

デモは録画動画で、ステージでは Laurie Allen がクリッカーを操作しました（再生がうまくいかず、少し手間取る場面がありました）。内容は 6 に記載します。動画のあと Jamie Dean は、レビュー前は変更箇所を見つけるだけで体力を使っていたが、いまは法的な分析と判断に力を注げるようになった、これこそ報酬を受けて行うべき仕事だと述べました。

### 5.6 Automate：繰り返す作業を自動化する

**週次報告の自動化（Laurie Allen）**

3 段階目の例として、先ほどの週次報告を Copilot Agent Builder で自動化しました。説明は次の流れです。

1. Agent Builder で、自然言語により「毎週金曜日の午後 2 時に、週次報告を下書きして」と説明する。先ほど使ったプロンプトの条件も渡す。
2. Agent Builder がエージェントを作成する。内容を確認して必要なら修正し、問題がなければ「作成」を押す。
3. 毎週金曜日の午後 2 時に実行されるようスケジュールされる。
4. 午後 2 時になると Outlook の下書きフォルダーに下書きが届いている。確認して修正し、送信する。

従来は最低 1 時間かかり、しかも金曜の夕方に忘れずに行う必要がありましたが、いまは自動で用意されます。Laurie Allen は 2 つの選択を意識的に行ったと話しています。1 つは送信まで任せず、上司に届く前に自分で確認できるようにしたこと。もう 1 つは、報告をどこか別の場所ではなく、普段使っている Outlook の下書きに置かせたことです。

また、まずプロンプトとして何度か実行して使い慣れてから、Copilot Agent Builder や Copilot Studio でエージェントにするよう勧めています。エージェントにしてから調整するより、プロンプトの段階で調整するほうが簡単だからです。

**案件管理表（Jamie Dean）**

Jamie Dean は、知的財産、ライセンス、訴訟などの質問が事業部門のさまざまな部署から、それぞれ異なる期限と緊急度で届くと説明しました。課題は、未解決の案件は何か、誰が自分の回答を待っているか、助言のために誰から情報を得る必要があるかを把握し続けることです。以前は Excel で管理していましたが、問題は 160 万行という行数の上限のような Excel の機能ではなく、本人にありました。忙しくなると更新しなくなり、管理表の価値が失われ、さらに「管理表を更新する」という作業が増えてしまうためです。

そこで、世話を焼かなくて済み、日々の業務を実際に支える管理表を、Scout（現在は Autopilot と呼ばれている）で作りました。内容は 6.2 に記載します。

### 5.7 1 人のために設計し、多くの人のために解決する

Jamie Dean は、アクセシビリティの世界には「Designed for one, solved for many（1 人のために設計し、多くの人のために解決する）」という言葉があると紹介し、Jeremy Curry にその AI 分野での実践を尋ねました。

Jeremy Curry は、自分は従来型のプログラマーではなく、コードを書くくらいなら塗料が乾くのを見ているほうがましだと思うタイプだと自己紹介しました。ただしバイブコーディング、つまり自然言語で話しかけて AI にコードを書かせる方法のおかげで、数十年来の問題を解決できるようになったと話しています。

その例が、Windows のウィンドウを常に最大化する機能です。画面拡大ソフトを使うと画面の一部しか見えないため、ウィンドウが最大化されていないと画面のどこに何があるか分からなくなります。画面拡大ソフトの利用者は、ほぼ全員がアプリを開くたびに最大化ボタンを探してクリックするか、Alt+Space でメニューを開き、下矢印で「最大化」を選ぶか X を押して Enter を押す操作を行います。新しいウィンドウのたびに繰り返すと、非常に面倒です。

Jeremy Curry は、このアプリを VS Code で作ったと話しています。完成後はオープンソースとして公開し、Microsoft 社内の盲目・弱視のコミュニティで非常に人気になりました。すると Windows のチームから連絡があり、「Windows に入れる」と言われ、社内で公開してから数日ほどで Windows に組み込まれたとのことです。最新バージョンの Windows では、アクセシビリティの設定の中にこの機能が入っています。自分の問題を解くための試みが、10 億人以上の Windows 利用者に提供されるものになったと語りました。

> 補足：公開してから Windows への組み込みまでの期間は「数日ほど」という発言どおりで、具体的な日付や Windows のバージョン名は発話では確認できません。

デモ動画の内容は 6.3 に記載します。

### 5.8 AI の効果をどう測るか

Laurie Allen は、組織での AI の効果測定では通常、時間の節約（週あたりの時間、作業あたりの分）が語られると述べました。時間の節約は現実の効果ですが、障害のある人にとっては摩擦の除去も重要で、次の観点を挙げています。

- 人とツールの間の障壁を取り除くこと。
- 認知的な負荷を減らすこと（アプリをまたいで情報を集める作業をしなくて済むことで、エネルギーと時間が節約できる）。
- 操作の負荷（ナビゲーション負荷）を減らすこと。クリックや移動する画面が減る。

そして、AI の効果を測るスコアカードにこれらを加えること、障害のある従業員に AI で何が変わったかを尋ねることを勧めています。時間の節約だけではない効果が見えてくるとのことです。

### 5.9 参加者への宿題と、変革管理についての話

Jamie Dean が、AI の使い方の段階に応じた次の一歩を提案しました。

1. いまも従来の検索エンジンで質問している人は、Copilot で試す。情報を一方向に得るだけでなく、追加の質問を重ねて対話の中で掘り下げる。
2. すでにそれをしている人は、日々の中でやりたくない作業を見つけて Copilot に渡す。次にクライアント向けのデモ動画や提案資料のデッキが必要になったら、Cowork に任せてみる。
3. さらに、自分やチームに影響している問題を見つけ、Cowork や Copilot が毎日処理してくれる仕組みを作る。Jamie Dean は、自分なら毎日午後 4 時 55 分まで先延ばしにしてしまう作業が候補になると話しました。

どの段階にいても大切なのは、実際にやってみることだと強調しています。

Laurie Allen は、まだ Copilot を使ったことがない人は「Copilot の使い方を Copilot に聞く」ことを勧めました。取り組んでいるプロジェクトを伝えて、アイデアを尋ねるとよいとのことです。また、初期には変革管理（利用者が新しいやり方に慣れるための支援）の要素を過小評価していた、ライセンスを配れば全員が自然に使えると考えていた、と振り返りました。インターネットの使い方を学んだときと同様のパラダイムシフトで、インターネット、スマートフォンに続く 3 度目なので、自分に猶予を与えて始めてほしいと述べています。

Jamie Dean は、新しいバージョンの Copilot を知って嬉しかったとも述べました。ホーム、チャット、Cowork が 1 つにまとまったものと、Copilot Code が加わったことで、Maximize All Windows のようなものを Copilot の環境の中で作れるようになる点を挙げ、AI は人が働く場所にあってこそ約束を果たせると述べています。

### 5.10 質疑応答

質問者は 1 人で、契約書レビューを行う Jamie Dean に 2 点を尋ねました。

**Q1. Copilot とのやり取りの反復にどのくらい時間をかけているか。**

一つの答えはありません。最初の 1 回は短く、数ページの秘密保持契約書 2 通のような短い契約なら速く終わります。毎回同じプロンプト「この文書で変わったことをすべて教えて、変更の潜在的なリスクの評価も手伝って」を使っているとのことです。その後は変更の複雑さ次第で、追加の質問が必要か、他の調査や文書の確認が必要かによって長短があります。文言は自分で読むため、Copilot とのやり取りは変更箇所への案内が中心で短く、時間の大半は法的判断に使います。Copilot の前は、評価に入る前に情報を探す作業が約半分を占めていました。

**Q2. 文書レビューと相手方とのやり取りの時間は、どれだけ減ったか。**

相手方とのやり取りの往復については、統計は出せないと答えました。自分の変更案が相手にどれだけ受け入れられるかの問題で、相手が弁護士を雇っているか、その弁護士が高額かどうかが最も効いて、速さを決めるだろうとのことです。確信を持って言えるのは、実際の文書レビューの時間は 50% 以上短縮され、変更箇所に注意を向けられるようになった点です。

最後に、Access for All のブース（Windows and Devices のエリア）に来てほしいと案内がありました。

## 6. デモ・手順

デモはすべて事前に録画された動画で、音声ナレーションつきです。ステージの動画再生は最初うまくいかず、Laurie Allen は一度やり直しました。画面の細かい表示は音声からは確認できないため、ナレーションで語られた範囲だけを記します。

### 6.1 契約書の変更点を洗い出すデモ（Jamie Dean）

状況設定は次のとおりです。Contoso の代理人として Fabrikam との間のプロフェッショナルサービス契約書を作成し、事業部門に渡しました。Fabrikam が修正を提案しましたが、修正は Word の変更履歴ではなく、色と書式で示した PDF でした。

1. 自分の元の契約書と、Fabrikam の赤字入り版を Copilot にアップロードする。
2. 変更点を 1 つずつ順に説明し、それによって生じうるリスクも示すよう依頼する。
3. Copilot が 2 つの文書を確認し、Fabrikam の変更を次のように特定した。
   - 支払い条件を 30 日から 60 日に延長：リスクは低い。
   - 成果物はすべて Contoso の所有物とする規定を削除：Contoso が、対価を払って作らせるものを所有できなくなる可能性があり、懸念が大きい。
   - 責任制限条項を追加：契約がうまくいかなくなった場合に備えて、よく確認したい。Copilot の推奨は、より限定的な責任制限条項を提案して返すこと。
4. 弁護士として、Copilot の提案を確認したうえで自分の判断を加える、と説明した。
5. 追加の質問として、適切な例外規定（除外条件）を含めた、より限定的な責任制限条項の案を Copilot に求める。
6. Copilot が検討し、請求の種類によって責任の上限を変える代替条項を提案した。Jamie Dean は良い方針だと評価した。
7. 新しい版の作成を依頼する。内容は、Fabrikam の支払い条件の変更は受け入れる、成果物の所有権に関する変更は拒否する、Copilot の限定的な責任制限条項に差し替える、というもの。
8. Copilot は 1 分足らずで新しい草案を作成した。チャットから直接 Word で開ける。
9. 残る作業は、改訂版を読み、自分の意図と一致していることを確認して送り返すこと。

### 6.2 案件管理表を自動で作るデモ（Jamie Dean、Scout を使用）

1. 自分は、構築したいものは分かっているが作り方が分からない、という前提で Scout に頼む。弁護士で、契約、知的財産、訴訟などさまざまな種類の案件を持つクライアントを担当していることをプロンプトで説明する。
2. 要望は、受信トレイから特定のフォルダーに移したメールを自動で分類する管理表を作ること。案件の状況、次のステップ、自分がやるべきことを管理表で確認できるようにしたい。最適な作り方を Scout に尋ねる。
3. Scout が 3 つの構築を提案する。Microsoft Lists で管理表の画面を作る、メールを入れる専用の Outlook フォルダーを作る、メールを分類して管理表に取り込む Power Automate のフローを作る。
4. 自分はどれも作り方を知らないので、「いいですね、3 つとも作って」と指示する。
5. Scout がブラウザーで Microsoft Lists を開き、新しいリストを作って Contoso Matter Tracker と名づける。最初の列に Matter ID（案件 ID）を追加し、設計に沿ってクライアント、案件の種類、要約、最終メール日などの列を追加する。最後にすべての列をリストのビューに表示する。
6. 次に Outlook を開き、Contoso Matters フォルダーを作る。
7. 続けてブラウザーで Power Automate を開き、新しいフォルダーにメールが入ったときに管理表へ取り込むフローを作る。

完成した仕組みは次のとおりです。メールを受け取ったら、Outlook の Contoso Matters フォルダーに移す。Power Automate がそのメールを確認し、管理表の該当する案件を更新するか、新しい案件を作る。未解決の案件と状況を知りたいときは、自動更新されるこのリストを見ればよい。

### 6.3 Maximize All Windows のデモ（Jeremy Curry）

1. まず問題を実演する。画面拡大ソフトを使うと、画面の右下にあるクロックが見えている状態から上へ動かしても、自分がどこにいるか分かりにくい。何本かの線が見え、ようやくウィンドウの上端が見えて、メモ帳が Outlook に重なっていると分かる。晴眼者なら全体が一度に見えるので簡単だが、自分には非常に難しい。
2. 画面拡大ソフトの利用者は、アプリを開くたびに最大化ボタンを探してクリックするか、Alt+Space でメニューを開いて、下矢印または X と Enter で最大化する。新しいウィンドウのたびにこれを行うのは面倒である。
3. 追加の問題を示す。新しい Outlook を最大化した状態で縮小表示すると、フォルダーなどの一覧が見える。ウィンドウを最大化していない状態にして同じように縮小表示すると、フォルダーなどの UI がすべて消える。アプリのウィンドウの大きさによって UI が変わるためで、スクリーンリーダー利用者がこの状態の Outlook でタブ移動すると、余分な UI がどこへ行ったのか、なぜタブで移動できないのかと戸惑う。
4. Maximize All Windows を実行しておく。そのうえでメモ帳を検索して Enter を押すと、ユーザーが何もしなくても自動的に最大化された状態で開く。
5. アプリはシンプルで、Windows の起動時に開始するかどうかを選べる。ナレーションにはタスクバーに関する説明もあるが、音声からは正確な操作は確認できない。起動中は、開いたウィンドウを自動で最大化する。

Jeremy Curry は動画のあと、このアプリは必要なウィンドウだけを賢く最大化する、と補足しました。

- **人が確認する前提：** Jamie Dean は契約書レビューで、Copilot の提案を見たうえで自分で判断し、文言も自分で読むと繰り返し述べました。Laurie Allen も、週次報告は自動送信にせず下書きにとどめて、自分で確認してから送ると設計しています。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **時間の節約：** 週次報告は、従来は最低 1 時間（6 手順、4〜5 個のアプリ）かかっていましたが、1 回のプロンプト、さらに自動化により下書きが自動で届くようになりました。
- **契約書レビュー：** 実際の文書レビューの時間は 50% 以上短縮されたと Jamie Dean は述べています。Copilot を使う前は、変更箇所を探す作業が時間のおよそ半分を占めていましたが、いまは法的判断に時間を使えます。
- **ナビゲーションの負荷軽減：** 複数の Web サイトを巡る代わりに、情報が 1 か所のアクセシブルな画面にまとまり、出典から必要な一次情報に進めます。
- **管理表の維持が不要に：** 案件管理表は、メールを特定のフォルダーに移すだけで自動で更新されます。
- **日常の摩擦の除去：** Maximize All Windows により、ウィンドウを最大化するクリックやキー操作が不要になりました。このアプリは、10 億人以上が使う Windows に組み込まれています。
- **測定指標の拡張：** 時間の節約に加え、摩擦、認知的な負荷、操作の負荷を、AI 導入のスコアカードに加える提案です。

## 9. まとめ

このセッションは、質問する（Ask）、作業を任せる（Act）、自動化する（Automate）の 3 段階を回すことで、障害のある人の仕事から摩擦を取り除けることを、登壇者自身の実例で示しました。

- 検索を Copilot での対話に置き換えると、複数の Web サイトを巡るナビゲーションの負担が軽くなります。
- 作業を任せるときは、情報源、書式、相手にとって重要な点を指定し、結果は人が確認します。契約書の変更点の洗い出しでは、レビュー時間が 50% 以上短くなったと述べています。
- 繰り返す作業は Copilot Agent Builder や、Scout（現在は Autopilot）と Power Automate で自動化できます。まずはプロンプトで使い慣れてからエージェント化するのが勧められています。
- バイブコーディングで作った Maximize All Windows は、1 人の課題から Windows の機能になりました。「1 人のために設計し、多くの人のために解決する」例です。
- AI の効果は時間の節約だけでなく、摩擦、認知的な負荷、操作の負荷でも測ることが提案されました。
- 次の一歩は、いまの段階の 1 つ先を試すことです。AI は障害のある人にとって、物事を楽にするだけでなく、可能にするものだというのが発表の結論です。
