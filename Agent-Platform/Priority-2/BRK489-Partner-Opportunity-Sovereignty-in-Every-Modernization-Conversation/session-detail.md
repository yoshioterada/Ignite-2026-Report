# BRK489 Partner Opportunity: Sovereignty in Every Modernization Conversation

## 1. はじめに

このセッションは、Microsoft のパートナー企業（SI、ISV、ホスティング事業者など）に向けた発表です。顧客のクラウド・AI のモダナイゼーション（近代化）の相談の中で、デジタルソブリンティ（デジタル主権）の話題が増えています。その相談にパートナーがどう関わり、事業機会にするかを扱っています。

内容は大きく 4 つに分かれます。1 つ目は市場の需要とリスクの考え方です。2 つ目は Microsoft Sovereign Cloud の構成と Ignite で発表された新機能で、動画によるデモも含まれます。3 つ目はパートナー向けの支援策（スキル習得、専門性認定、資金支援、勝ちパターン）です。4 つ目は SI・ISV・ホスターの 3 社によるパネルディスカッションです。

発表の結論は、**主権の要件は 1 つの答えで済むものではなく、ワークロードごとの「統制・継続性・選択」の程度を決める話であり、それをモダナイゼーションの会話の初期から取り上げることがパートナーの機会になる**、というものです。

## 5. 発表内容の詳細

### 5.1 市場の機会とパートナーの役割

発表者は Gartner の予測を引用しました。主権市場は、インフラ層だけで 2,000 億ドル相当（発話では「200 billion」。通貨単位は確認できません）を超えるまで成長し、5 年間の年平均成長率（CAGR）は 38% とのことです。年の部分は聞き取りでは「2020 年より前」となっており、音声認識の都合で正確な年は確定できません。発表者は、この数字はインフラ層だけの値であり、支出と投資の方向感を示すものだと説明しています。

パートナーの機会はインフラにとどまりません。顧客のライフサイクルに沿って、次の 3 段階で説明されました。

| 段階 | パートナーが支援できること |
| --- | --- |
| 評価と設計 | 主権の要件の理解、リスクの評価、ワークロードに合う構成の決定 |
| 実装とモダナイゼーション | 主権環境の構築、ワークロードの移行、統制の実装、アプリケーションと AI の持ち込み |
| 運用と進化 | 統制の維持、コンプライアンスの証明、要件が変わったときの環境の適応 |

### 5.2 需要の背景とリスクの考え方

需要を押し上げる力として、2 つの変化が同時に起きていると説明されました。1 つは、インターネットの登場以来の大きな変化といえる AI です。もう 1 つは、国際関係、貿易政策、技術に対する国家の管理への期待が変わり続ける、複雑な地政学的環境です。

主権の意味は組織によって異なります。データの所在と規制への準拠を指す場合、機密情報を不正アクセスから守ることを指す場合、重要インフラを運用する組織で事業継続を最優先にする場合があります。これらの要件は関連していますが、ワークロードごとにリスクの大きさは違います。

そこで Microsoft は、顧客と議論するために 2×2 の枠組みを用意しています。軸は、リスクが起きたときの影響の大きさと、起きる確率です。

| 影響 | 確率 | 一般的な対応 |
| --- | --- | --- |
| 小さい | 低い | 監視にとどめる |
| 小さい | 高い | 能動的な管理と継続的な監視を組み合わせる |
| 大きい | 高い | より強い緩和策が必要（例: サイバーセキュリティのリスク） |
| 大きい | 低い | 緩和が難しく費用も大きい。代替の運用環境や完全に独立した運用施設などの備えが必要になる場合がある（例: 制裁、特定の合法的アクセスのシナリオ） |

発表者は、最後の「影響が大きく確率が低い」リスクが主権に特に関係すると述べています。重要なのは、顧客がリスクを特定して優先順位を付け、トレードオフを理解したうえで、それを持続可能で、状況の変化に適応できる構成と運用モデルに落とし込むことだと説明しました。

### 5.3 顧客との会話で出る 5 つのシナリオ

今週最も多く聞かれた質問として、顧客との会話で頻出する 5 つのシナリオが示されました。

1. **ポリシーとガバナンス**：規制上の義務をどう理解し、管理するか。
2. **データの所在と機密性**：データはどこに保存され、どう保護されるか。
3. **オペレーターのアクセス**：誰が、どのような条件でシステムにアクセスできるか。どんな監督ができるか。
4. **クラウドの耐障害性と事業継続**：障害が起きても重要な業務をどう継続するか。
5. **ソブリン AI**：データ、モデル、運用の統制を保ちながら、どう AI を開発・実行するか。

発表者は、この枠組みとシナリオから始めることで、主権についての漠然とした議論を、技術判断につながる具体的な要件に変えられると説明しています。Microsoft Sovereign Cloud の設計にも、これらのシナリオが使われたとのことです。

### 5.4 Microsoft Sovereign Cloud の 3 つのアプローチ

Microsoft Sovereign Cloud は、補完し合う 3 つのアプローチで構成されると説明されました。

| アプローチ | 説明 |
| --- | --- |
| ソブリンパブリッククラウド | 多くの顧客が、Azure にとどまったまま主権の要件を満たせるという考え方です。商用クラウドの規模とイノベーションの恩恵を受けつつ、透明性、ガバナンス、統制を強化します。 |
| ソブリンプライベートクラウド | 主権と聞くと、すべてをオンプレミスに移してプライベートクラウドで動かすと考える顧客が多いが、それは正しくない、と発表者は述べています。運用上の独立性がより必要なワークロード向けで、Azure Local を使うと、クラウド、データ、AI、生産性のワークロードを、顧客が管理するローカル環境で動かせます。 |
| パートナーのエコシステム | 地域の専門知識、専門的なソリューション、必要な場合は独立して運営される環境を、パートナーが提供します。 |

> 補足：トランスクリプトでは、2 つ目のアプローチの名称が「sovereign public cloud」と 2 回読まれています。説明内容（Azure Local、運用上の独立性）から、ここではソブリンプライベートクラウドとして整理しました。聞き取りどおりの名称は確定できません。

3 つは組み合わせて使えます。たとえばアプリケーションの大部分はパブリッククラウドで動かし、一部の重要な業務や重要なワークロードはローカルに置き、特殊な要件にはパートナーと対応する、といった形です。発表者は、Microsoft は「統制の連続体」を提供し、顧客の現在地に合わせるものだと表現しています。

### 5.5 Ignite での新発表

**パブリッククラウド**では、顧客がクラウド環境をより見て、より統制できるようにすることに重点が置かれています。

- **Sovereign Control Panel**：Ignite でパブリックプレビューとして発表された新サービスです。主権に関する情報と統制を Azure portal 内の 1 つの画面にまとめます。データの所在、暗号化、事業継続といった観点で主権の状況を把握し、ギャップを見つけて対処できます。
- **Data Guardian** と **production touch ledger**：Microsoft 自身の運用の透明性を高める機能です。まず EU と EFTA の対象となる運用から段階的に展開します。Microsoft のエンジニアが顧客環境に入ったときの追加の監督と記録を、顧客が確認できるようになります。

**プライベートクラウド**では、ワークロードの可搬性を高め、アプリケーションと AI のライフサイクルに必要な基盤をローカル環境に持ち込むことに重点が置かれています。

- SQL Server on Azure Local が利用可能になりました。
- DocumentDB がプライベートプレビューで公開されました（発話で言い直されています）。
- AI 層として Foundry Local、開発層として GitHub Enterprise Local が挙げられ、AI の全体のスタックをローカルで動かせると説明されました。

**エコシステム**では、フランスの BlurCloud とドイツの Delos が例に挙がりました。BlurCloud の表記は音声認識によるもので、確定できません。発表者によれば、同社は 10 月に、1,000 を超える Azure サービスと Microsoft 365 のサービスを BlurCloud 上で提供する、と発表したとのことです。また Azure Local では、バックアップやセキュリティなどの特定の用途に対応する、検証済みのパートナーソリューションが 20 を超えたと説明されています。

### 5.6 パートナーの道筋と支援（担当：Lisa）

動画の後、Lisa がパートナー向けの内容を説明しました。道筋は 4 つのステップです。

1. 自社のチームで、デジタルソブリンティの共通理解を作る。Azure だけの話ではなく、モダンワーク、クラウドと AI、セキュリティにまたがるため、これらのプラクティスが一緒に顧客へ提案できると機会が大きくなります。
2. 営業、プリセールス、デリバリーのチームを準備する。営業にはデータの所在、オペレーターのアクセス、耐障害性、規制の変化、AI の統制といった兆候に気付くこと、アーキテクトにはそれをパブリッククラウド、プライベートクラウド、製品機能の適切な組み合わせに落とすこと、デリバリー担当には統制を実際に実装するスキルが求められます。
3. 準備を、案件の獲得と顧客の成果につなげる。モダナイゼーションの会話ごとに「このワークロードにはどの程度の統制、継続性、選択が必要か」を尋ねます。
4. Microsoft Digital Sovereignty specialization（専門性認定）の取得で差別化する。

Microsoft の支援は、次の 4 つの領域が連動して提供されます。

| 領域 | 内容 |
| --- | --- |
| スキル習得 | チームが主権について自信を持って話し、ソリューションを提供できるようにする |
| 差別化 | 資格上の認定と専門性認定で、専門性を顧客と Microsoft の営業に見える形にする |
| 市場展開（GTM）のリソース | 需要を作り、すでに進んでいる顧客との会話に主権を結び付ける |
| 提供メニューとリソース | 条件を満たす案件を、構想から導入まで加速する |

これらは Partner Playbook に 1 か所にまとめられています。発表者は、プラクティスの責任者を集め、強みとギャップを評価し、4 つの柱のそれぞれに担当者を置くことを勧めています。

#### スキル習得の中身

準備は、最終的な導入だけでなく顧客の旅全体を対象にします。シナリオは「主権があり、信頼でき、回復力のある運用の構築を支援する」です。学習パスは 3 種類の準備で構成されます。

- 営業向け：Microsoft Sovereign Cloud をビジネスの言葉で位置付ける。
- 技術案件向け：アーキテクトが要件の範囲を決め、方式を設計し、トレードオフを説明する。
- プロジェクト向け：デリバリー担当がソブリンクラウドのプロジェクトを実装する。

これは顧客のライフサイクル（傾聴と相談、着想と設計、実行と達成、価値の実現、管理と最適化）に対応しています。主権は一時点の販売ではなく、要件、リスク、ワークロードが変わるため、ライフサイクル全体で顧客に寄り添うパートナーが大きな価値を生む、という説明です。役割別の学習パスはパートナーのスキル習得ハブで選べ、今後のライブ配信セッションも案内されました。

#### Digital Sovereignty specialization の要件

取得には、次の 3 つの基盤となる専門性認定が必要です。

1. Azure の専門性認定を 1 つ。Azure Expert MSP、AVS、または InfraDB 移行の専門性認定で満たせます（綴りは音声認識によるもので、確定できません）。
2. モダンワークの専門性認定のうち、モダナイズされたエンドポイント。
3. セキュリティの専門性認定を 1 つ。クラウドセキュリティ、データセキュリティ、ID とアクセス管理のいずれか。

発表者は、これを単なるチェックリストではなく、プラクティスの設計図として見るよう勧めています。主権にはインフラ、生産性、ID、データ保護、運用の連携が必要で、この要件はそれらをまとめて提供できる証明になるためです。次の一手として、Azure、モダンワーク、セキュリティの各プラクティスの責任者と、すでに持つ専門性認定、残る依存関係、計画の責任者を確認するギャップ評価が示されました。

#### 資金支援：Frontier Accelerate for Azure

Digital Sovereignty specialization を持つパートナーは、プログラムの適格性と承認を条件として、Frontier Accelerate for Azure のプロジェクト資金を利用できます。流れは 3 ステップです。

1. 獲得（Earn）：能力を築き、専門性認定を取得する。
2. 提案（Engage）：パートナー指名の経路で、条件を満たす主権案件を提出する。
3. 支払い（Get paid）：資金を使って、案件を計画から本番まで進める。

パートナー指名のプロジェクトでは、案件の規模に応じて、初年度の ACR が最大 500K に達する案件に資金を提供するとのことです（通貨単位は発話では確認できません）。早めの指名と、Frontier Accelerate、インセンティブガイド、専門性認定の要件の確認が勧められました。

#### FY27 パートナー GTM プレイブックの勝ちパターン

プレイブックの枠組みは、まず自社のプラクティスを整え、次に顧客ライフサイクル全体で繰り返し使える勝ちパターンを適用する、というものです。

準備段階の 4 つの行動は次のとおりです。

1. 関連する専門性認定を取得し、移行とモダナイズのパートナーフォーラムに参加する。
2. 自社が最初の利用者（顧客ゼロ）になる。Microsoft のセキュリティ機能を自社の環境で使う。
3. パートナー開発マネージャー経由で、利用可能なソブリン関心度のシグナルを使って対象顧客を特定する。
4. セキュア AI、ガバナンスされたデータ、移行、モダナイゼーションなど、すでに進行中の会話に主権を結び付ける。

勝ちパターンは次の 5 段階です。

| 段階 | 内容 |
| --- | --- |
| 1. 傾聴と相談 | パートナー向けのソブリン資産とキャンペーンでパイプラインを作る。インフラ担当だけでなく、リスク、コンプライアンス、運用、セキュリティ、事業継続の責任者を巻き込む。ワークロード単位で統制、耐障害性、選択の必要性を引き出す質問をする。 |
| 2. 着想と設計 | 会話ガイド、デモ、PoC、ソリューション評価で主権を具体化する。対象であれば Frontier Accelerate for Azure でプリセールス支援を検討する。 |
| 3. 実行と達成 | 適切な専門家を集め、障害を取り除き、技術面と運用面で顧客に利益のあるソリューションで案件を獲得する。ソブリンランディングゾーン、クラウド導入フレームワーク、Frontier Accelerate for Azure の販売後の提供メニューを活用する。 |
| 4. 価値の実現 | 3 から続けて実施する（発話では段階名のみで、詳細は語られていません）。 |
| 5. 管理と最適化 | 主権は本番稼働で終わらない。耐障害性を試し、要件の変化に合わせて統制を調整する。 |

発表者は、1 枚から 1 つだけ持ち帰るなら、「主権はアカウントのライフサイクル全体を通じて扱う」ことだと述べています。対象アカウントを選び、Azure、モダンワーク、セキュリティの責任者を集め、次のモダナイゼーションの議論に「デジタルソブリンティのどの要素が当てはまるか」という質問を加える、という具体的な行動が示されました。

### 5.7 パートナーパネル

司会は Lisa です。各パネリストに 2〜3 問を質問する形でした。

**Virji（TCS）：顧客の声とモダナイゼーションへの影響**

この 2 年ほどは教育の段階でしたが、この 1 年は本格的な取り組みの段階だと述べました。欧州では GDPR の頃から何かが来ると分かっており、欧州の各種規制が出てきたことで、発表で示された 5 段階の最後（能動的な主権）を求める顧客が出てきました。新しいモダナイゼーションの考え方が出るたびに主権が組み込まれ、これはコンプライアンスと同じだという説明です。1 年半前は感情的、政治的に語られましたが、現在は技術の選択肢として現実的に見られています。TCS は、データと AI、運用、技術の 3 領域に絞って取り組んでいます。EU が SOV-0 から SOV-8 までの明確な主権指標を出したことで、より客観的になったとも述べています。Lisa は、これを「感情的な主権」から具体的で客観的な話への変化として受け止めました。

**Kristen（Legora）：顧客の主権要件はソフトウェアの作り方と提供をどう変えたか**

Legora は、弁護士が AI を使って仕事をするのを支援する会社で、扱う情報は機密性が高く、法律事務所や案件ごとに制約が異なります。そのため、主権の話題を調達の最終段階まで待たず、顧客との会話の早い段階で取り上げ、要件をプラットフォームの設計に反映しています。Azure OpenAI を使う理由の 1 つは、モデルをリージョン単位でデプロイできることで、データの保存場所と処理場所を別々に選べます。スケールのためには、全顧客共通の標準的な選択肢と統制の基準に、顧客単位で設定できる項目を重ねています。目指すのは、弁護士がクラウドアーキテクトを副業にしなくてよい状態だと述べています。

主権のある技術への需要は大きく、それには応えていくと述べたうえで、顧客が求めているのは信頼、そして運用に対する保証だとしています。顧客は、データがどこにあり、誰がアクセスでき、誰が運用し、地政学的な変化や管轄の変更、パブリッククラウドへの接続断があったらどうなるかを知りたがっています。ここで地域のパートナーが重要な役割を果たすと説明しました。Microsoft がイノベーションの基盤を提供し、地域のパートナーは技術、データ、運用の 3 つの主権を提供できます。顧客はイノベーションと主権のどちらかを選ぶのではなく、イノベーションのために主権を求めている、というのが主張です。

**Virji（TCS）：GSI の最大の機会と最近の案件**

主権とイノベーションは反比例すると考えられがちで、主権を得ることは、すべてのデータやアプリを大きな部屋に閉じ込めて電気を消し、冷凍庫にしまうようなものだと思われているが、そうではないと述べました。主権は、手元にあるものを見直し、何が必要で何が不要か、どこにコンプライアンスやセキュリティ、異なる耐障害性が必要かを検討する機会だという説明です。

TCS はあらゆる事業領域に関わるため、ワークロードだけでなくバリューチェーン単位で見ます。デジタルソブリンティはまず事業の領域から考え始め、次にアプリケーション、インフラ、その周辺の要素へ進む、という順序だと説明しています。銀行・金融サービスでは 30〜40 年の経験があると述べています。そのうえで、**MVSE（最小限のソブリン企業、Minimum Viable Sovereign Enterprise）**という考え方を紹介しました。現在は、MVE（最小限の実用的な企業）とも呼んでいるとのことです。この考え方で最初の主権パートナーになったと述べており、あらゆるものをソブリンにしたがる「主権ウォッシング」を避けられるため、多くの顧客に受けが良いとのことです。バリューチェーンによって必要な主権のレベルは異なり、レベルの高いもの（発話では CL3）がある一方、一切不要なもの（発話では SEAL 0、音声認識の都合で表記は確定できません）はパブリックの Azure で動かせます。TTS の会社（聞き取りによる表記で、内容は確定できません）や旅行、物流の会社は、高い SEAL レベルに置く余裕がない、とも述べています。一方、現地の需要や規制のために国単位の主権は強まっています。

主な案件として、銀行業での事例を挙げました。バリューチェーンを分けて検討し、ゼロトラストアーキテクチャを作った時のように、「ゼロトラストのビジネスアーキテクチャ」としてバリューチェーンを分離することで価値を出し、コスト効率も確保したと説明しています。また、2 つの通信会社で、Azure Local のソブリンプライベートクラウドがうまく動いているとのことです（その後の「GAN 技術」への言及は、聞き取りが不明瞭です）。さらにインドの例として、3 億 7,000 万以上の口座の維持と、1 日 10 億以上のトランザクションを処理する、堅牢でイノベーションを止めない基盤が必要で、そのために Azure を中心に据えたと述べました。2 年ほど前から早期に採用したとのことです。

最後に、5 段階のうち最初の 4 段階にはすぐ到達できるが、5 段階目の能動的な主権は難しく、しかも今後は必須であり、案件を獲得して終わりにはできないと述べました。データベースのモダナイゼーションでは、前日に発表された新しいデータベースが 2×2 のどこに当てはまるかを考えていたとも語っています。Lisa は、デジタルソブリンティ専門性認定を最初に取得したパートナーであることに謝意を示しました。

**Kristen（Legora）：主権は ISV の差別化要因になるか**

Legora は創業 3 年の会社で、数年前はとても小さなスタートアップでしたが、主権への対応で、より大きな会社と戦えるようになり、洗練された顧客の信頼を得られたと述べました。現在は、80 の市場に 2,800 の顧客がいます。例として、初期の顧客であるポーランドの法律事務所 SK&S（聞き取りによる表記）を挙げました。2025 年に提案した当時は小さなスタートアップでしたが、同事務所は、データを EU 内で処理すること、データをモデルの学習に使わないという契約上の約束の 2 点を要件としていました。それを満たせたことが、受注と競合との差別化につながったとのことです。

顧客に主権を説明するときの 3 つのベストプラクティスは次のとおりです。

1. データの流れを追えるようにする。保存場所、処理場所、アクセスできる人、使うモデルの提供元などを明確にする。
2. 対応範囲を明確にする。標準で何を提供し、アカウント単位で何を設定でき、各選択でトレードオフは何かを示す。
3. 審査する人が確認しやすくする。法務やセキュリティの担当者に、何を提供し、何を契約で約束し、クラウド、ソフトウェア、SI、その他のエコシステムの間で誰が何に責任を持つのかを示す。

**Ava（Proximus）：Azure Local の進化とホスターの機会**

Proximus は、グループとルクセンブルクで、インフラに加えてライフサイクル運用、セキュリティ、コンプライアンスの経験を持っています。これらをまとめて製品化し、顧客が提供メニューから選び、自分で運用や調整をしなくてよい形にできるとのことです。単一の「ソブリンクラウド」ではなく、主権のある提供の複数の層を用意することが大切だと述べました。

## 6. デモ・手順

デモは、Pang の発表の最後に、事前に用意された**動画**として上映されました。ライブでの操作ではありません。上映の途中で、スライドが意図せず次のデモのスライドに進むなどの機材のトラブルがあり、登壇者が一部の内容を後で動画で見てほしいと述べています。ナレーションで語られた内容は次のとおりです。画面の細部は、音声からは確認できません。

1. 主権は組織、ワークロード、バランスを取るリスクと機会によって意味が変わる、と導入されます。目的は、リソースとデータを自分の判断で管理できる主権の統制を示すことです。
2. 根本にあるのは監督です。Microsoft の運用に対しては Data Guardian と production touch ledger で監督できます。顧客自身の運用の監督には、主権の状況の理解が必要ですが、その情報はポリシー、サービス、人の頭の中に散らばっています。Sovereign Control Panel はそれを 1 つの統合ビューにまとめます。
3. 画面には、データの所在（レジデンシー）、機密性、事業継続といった主権の統制の利用状況が一覧で表示されます。そこから詳細を掘り下げて対処できます。
4. データレジデンシーの例では、リソースを指定リージョンに置くというポリシーに対する準拠率が **80%** と表示されます。内訳を開くと、リージョン外のリソースを調べられ、ポリシー違反を特定できます。この例では **2 つのリソース**を別の地域に再デプロイして是正する必要がある、と示されます。
5. データの機密性では、保存時と転送時の暗号化を、レジデンシーと同様に評価し、必要なら詳細を掘り下げます。
6. 次に、パブリッククラウドへのアクセスが途絶えても運用を続けられるか、という事業継続の統制が示されます。Azure は可用性ゾーンなどでグローバルな耐障害性をすでに提供していますが、最も極端な状況でも運用を続けられるという追加の確信が求められていた、と説明されます。
7. トップレベルのビューには、Azure から、自分が所有し運用するプライベートクラウドである Azure Local へ移行できるように構築されているリソースが表示されます。例では **460 のリソースが準備済み、150 のリソースが変更が必要**です。ただし、この統計だけでは事業継続は保証されません。事業の円滑な運営の中心となるワークロードは顧客自身にしか分からないためです。
8. 準備ができていないリソースを掘り下げ、事業に不可欠で変更が必要なものを選びます。Microsoft のソブリン事業継続のアーキテクチャパターンに基づき、選んだリソースを Azure から Azure Local へ移すには、代替のメッセージングサービスを採用する必要がある、と表示されます。これにより、必要時に事業がローカルで動くように、具体的な是正作業を進められます。
9. ワークロードを Azure Local に移行した後、自分が所有・運用するソブリンプライベートクラウド環境を確認します。移したリソースはオンプレミスの Azure Local 上で動き、Azure とは接続したままなので、パブリッククラウド全体と並べて管理できます。
10. 混乱がさらに拡大した場合は、Azure からの完全な切断も選べます。簡単なスクリプトにより、重要なワークロードを、接続された Azure Local から、ローカルの制御プレーンで完全に切断された運用へ、ワークロードの処理を中断せずに移します。
11. 移行が完了し、事業は動き続け、完全に自社の統制下で動いている状態になります。その環境で、Foundry Local と GitHub Local により、モデルと開発者ツールを、最も機密性の高いデータや重要なワークロードのそばに置けます。
12. 結びとして、主権は全員に同じ答えが当てはまるものではなく、Sovereign Control Panel を通じて Microsoft Sovereign Cloud が選択と統制を提供する、とまとめられます。

> 補足：動画で示された「Azure Local の切断運用」や事業継続の統制が、どの時点で利用可能になるかは、発話では確認できません。プレビューと明言されたのは、パブリックプレビューの Sovereign Control Panel と、プライベートプレビューの DocumentDB だけです。

## 7. 注意点・発表者の気付き

- **主権の要件はワークロードごとに異なる。** 全てをソブリンにする必要はなく、必要なバリューチェーンにだけ高いレベルを適用すべきだとして、TCS は「主権ウォッシング」を避ける考え方を紹介しました。
- **「準備済み」の数字だけでは事業継続は保証されない。** どのワークロードが事業の中心かは顧客にしか分からず、それを選んで是正する必要があると、動画の中で説明されています。
- **能動的な主権（5 段階目）は難しいが必須になる。** 案件を獲得して終わりにはできず、新しいデータベースなどが入るたびに考え直す必要がある、というのが TCS の経験です。
- **主権の議論は早い段階で始める。** Legora は、調達の最終段階まで待たず、顧客との会話の初期に要件を確認するとしています。
- **専門性認定は単なるバッジではない。** 3 つの専門性認定の組み合わせが、インフラ、生産性、ID、データ保護、運用の連携を提供できる証明になる、という位置づけです。
- **資金支援には条件がある。** Frontier Accelerate for Azure は、プログラムの適格性と承認が前提です。
- 発表で触れられていないこと：Sovereign Control Panel の一般提供の時期、Data Guardian と production touch ledger の EU・EFTA 以外への展開時期、Digital Sovereignty specialization の取得にかかる期間や費用。

## 9. まとめ

主権の要件は、ワークロードごとのリスクの大きさと発生確率で考えると、具体的で実行できる議論になります。Microsoft はソブリンパブリッククラウド、ソブリンプライベートクラウド、パートナーのエコシステムの 3 つを連続的に組み合わせられるものとして提供しています。Ignite では Sovereign Control Panel（パブリックプレビュー）、Data Guardian、production touch ledger の段階的な展開、Azure Local 上の SQL Server、DocumentDB（プライベートプレビュー）、Foundry Local、GitHub Enterprise Local などが紹介されました。

パートナーは、スキル習得、専門性認定、市場展開のリソース、提供メニューの 4 つの柱を整え、5 段階の勝ちパターンで顧客のライフサイクル全体に主権を持ち込むことが求められます。Digital Sovereignty specialization は Frontier Accelerate for Azure の資金支援につながります。パネルでは、TCS と Proximus の発言を中心に、主権はイノベーションを止めるものではなく、イノベーションのために必要とされていることが語られました。**まず、次のモダナイゼーションの議論で、デジタルソブリンティのどの要素が当てはまるかを尋ねることから始めます。**
