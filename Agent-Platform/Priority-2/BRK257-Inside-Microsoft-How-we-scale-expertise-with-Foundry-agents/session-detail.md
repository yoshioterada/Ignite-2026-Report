# BRK257 Inside Microsoft: How we scale expertise with Foundry agents

## 1. はじめに

このセッションは、Microsoft 社内の 2 つのチームが、Foundry を使って「専門家の知見」をどう拡大しているかを、実際の取り組みとして紹介する発表です。1 つはマーケティングチームのブログ公開レビュー、もう 1 つは Azure エンジニアリング運用チームのインシデント後の原因分析（RCA：根本原因分析）です。冒頭で、架空の企業の話ではなく、Microsoft 自身が Foundry をどう使っているかを話す、と明言されています。

仕事の内容は大きく違うものの、後半では 2 つの事例に共通するパターンが整理されます。専門家が基準を決め、エージェントは根拠のある文脈で作業し、最終判断は人が行う、というものです。ライブデモは、RCA エージェントのほうで行われました。

## 4. 発表者が伝えたいメッセージ

2 つの事例に共通する主張は、**エージェントが作業を準備し、判断は専門家が下す**ということです。マーケティングでは「この記事は読者に出せる品質か」、運用では「何が起き、なぜ起き、次に何を変えるか」と問う内容は違いますが、パターンは同じだと述べています。

そのパターンは 3 つの要素で構成されます。

1. **専門家の基準**：何が良いかを、評価基準（ルーブリック）で定義する。
2. **根拠のある文脈**：エージェントはモデルの記憶ではなく、証拠に基づいて作業する。
3. **人の判断**：どちらの事例でも、出荷前の最終判断は人が行う。

このパターンは両チーム固有のものではなく、専門家のレビューに依存するあらゆるチームに当てはまる、と説明されています。

## 5. 発表内容の詳細

### 5.1 導入

冒頭では、前夜のイベントや、Ignite で何度も聞く架空企業の話に触れたあいさつがありました。そのうえで、今回は架空の企業ではなく Microsoft 社内での Foundry の使い方を話す、と説明されました。

### 5.2 事例 1：ブログ公開レビューをスケールさせる（マーケティング）

**背景**

Microsoft にとってブログは、製品を市場へ届ける重要な手段です。Brett がエージェントに調べさせた結果、年間 1 万件を超える投稿が、さまざまな対象読者や製品向けのプラットフォームに公開されているそうです。製品の変更の告知、実際の利用パターンの共有、オピニオン的な発信に使われています。Brett のチームは小規模で、昨年は 200 本、今年はここまでに 311 本（最後に確認した数字）を公開しています。

**従来の手動レビュー**

Azure のマーケティングチームは長年、手作業のレビュー工程を運用してきました。目的は、技術担当の協力者を支えながら品質の基準を守ることです。流れは次のとおりです。

1. プロダクトマネージャーが、数時間かけてブログの下書きを作り、メールでブログのプラットフォーム担当者に送る。
2. プラットフォーム担当者が、対象読者に合っているかを確認してフィードバックする。
3. 著者が 1〜2 時間かけて直し、何度かやり取りする。
4. プロダクトマーケター（PMM）が、製品機能が正確で明確に表現されているかをフィードバックする。
5. 最終承認までこのやり取りが続く。

プラットフォームのデータでは、一般に 6 回の下書きと 12 通のメールがあり、実作業は 8〜12 時間と見積もられていました。同僚に見せると「運が良ければ 8〜12 時間」と言われたそうです。この工程は AI 以前に作られたもので、ニュースが 1〜2 週間待たされても問題ありませんでした。しかしこの 18 か月で工程は破綻し、AI の 1 年は 1 か月に相当するという冗談が出るほどです。公開まで最大 4 週間待たされると、伝えたい内容はすでに古くなります。昨年の時点で未処理の投稿は 65 本あり、PMM をボトルネックにしないために AI を使う方針を決めました。

**ステップ 1：GitHub Copilot CLI のスキル**

当時は新しい技術が次々に登場しており、特に GitHub Copilot CLI のようなコーディングエージェントが転機になりました。65 本の積み残しを題材に、ブログが公開品質を満たすかを判定するスキルを GitHub Copilot CLI で作りました。「公開してよいか」という問いを小さな問いに分解するため、良いブログとは何かを書き出す必要があり、そこから **6 つの観点のルーブリック**ができました。

初めは、自分たちでレビューしてフィードバックを書き、コーディングエージェントに同じフィードバックを出させる作業のため、むしろ手間が増えました。しかし繰り返すうちにエージェントの出力を強く信頼できるようになり、スループットが大きく上がりました。**所要時間は数時間から、数十分〜1 時間になりました。**

**スキルだけでは解決しなかった点**

- PMM が自分でエージェントを実行し、メールのやり取りも管理する必要があった。
- 製品の更新や製品名の変更に追従するため、PMM がスキルを複製（フォーク）して改変した。標準化して共有する良い方法がなかった。
- スキルの利用と保守が任意だったため、厳密さが失われた。数か月後には、使う人と使わない人が分かれた。

**ステップ 2：Foundry の中央集約エージェント**

そこで、ブログ公開プラットフォームに組み込み、著者と PMM が公開前に必ず AI レビューを受けるようにする、中央集約型のエージェントを目指しました。Foundry は、ガバナンスの効いた 1 か所にエージェントを置く場所になり、既存のワークフローにも組み込めました。

ただし IT 部門の理解を得るのは簡単ではなかった、と語られています。マーケティングが「未公開の製品発表という漏れてはならない機密データにアクセスし、指示（命令文）を継続的に自分たちで更新でき（例えば Azure AI Foundry から Microsoft Foundry への名称変更をエージェントに自動で反映させたい）、一般に公開される面につながるエージェントを作りたい」と言えば、IT としては断りたくなる状況です。Foundry では次のようなガードレールを用意できるため、IT が「はい」と言えるようになった、という説明です。

- エージェントをプライベート VNet の背後に公開することを必須にし、機密データへ公開側からアクセスできないようにする。
- エージェントごとに専用の ID を持たせ、使ったツールや通信先を追跡し、すべての動作を監査できるようにする。
- 中央で管理するガードレールにより、プロンプトが変わっても、IT が強制したい中核の制約は維持される。

**製品のドリフトへの対応：Work IQ と Foundry IQ**

製品の変化が速いため、固定のロジックを持つエージェントは保守が大変です。スキルを複数の PMM がフォークしたときに経験した痛みでもあります。新しいモデルは毎週登場し、競合製品も現れ、自社の製品の形や名称も毎週変わります。

- **Work IQ**：採点エージェントのうち、製品機能とメッセージを評価する部分を、社内で「メッセージング＆ポジショニング」と呼ばれる更新され続ける文書につなぎます。製品が変わると、エージェントも自動的に知ります。
- **Foundry IQ**：他のチームが管理する Azure 上のデータベースにも接続できます。例として、社内の AI メッセージングアシスタント（AMA）があり、Microsoft が実施するフォーカスグループのインタビューのデータを使って、読者への伝え方を提案します。Foundry IQ によりエージェントはこのデータにつながり、洞察を取り出して著者に届けられます。そのデータベースの中身を理解する必要はなく、Foundry IQ のインスタンスにつなぐだけだ、と述べています。

**新しい公開フロー**

Foundry のエージェントとして公開したことで、安全なエンドポイントを持つ公開済みの評価エージェントを、ブログ管理ソフトに組み込めました。

1. 著者は、以前と同じ場所でブログを下書きして提出する。
2. エージェントがブログを評価し、フィードバックと修正案を著者にメールで送る。
3. 下書きが公開に必要な最低点に届いたら、PMM が最終確認に加わる。エージェントは、Work IQ の情報をもとに適切な PMM へ自動的に振り分ける。
4. PMM が公開に向けて仕上げる。

従来 **2〜4 週間** かかっていた工程全体が、**10 分** で終わるようになりました。PMM は同じフィードバックを何度も書かずに済み、著者は素早く改善を重ねられます。

**成果**

- 何千時間もの PMM の作業時間を節約し、戦略的な仕事に集中できるようになった。
- 速度は重要だが、本当の要点は読者に何が届いたかである。昨年は、Foundry のブログを読んだ人の **42%** が、現在の基準で弱い、または非常に弱いと評価される投稿にたどり着いていた（行動喚起がない、冒頭が弱い、古い製品名を使っている、など）。現在はそれが **1% 未満**。
- 弱い投稿は単に質が低いだけでなく行き止まりで、そこから始めた読者は他の Foundry の投稿へ進みにくく、ソーシャルでのエンゲージメントも低かった。
- 技術コミュニティのプラットフォームでの Foundry の発言シェア（話題に占める自社の割合）が **半分増えた**（1.5 倍）。
- ソーシャルで実際に拡散される投稿の割合が、**23% から 60%** に上がった。

**社内動画の紹介**

ここで、マーケティングチームの社内メンバーが語る動画が流れました（話者の氏名は発話からは確認できません）。内容は次のとおりです。

- マーケターはこれまで以上に、チャネルの増加、パーソナライズ、ROI の証明を求められており、変化の中心はペースの速さである。
- 立ち上げは週単位、場合によっては毎日であり、Foundry はすでに 1 万 1,000 を超える AI モデルに対応している。今年度は、前年度より 150% 多い製品ローンチを支えている。
- 最初の一歩は、エージェントがチームの実際に使うシステム（アプリ、バックログ、文書、IQ）に届くようにすること。データ基盤がなければ、エージェントは推測するしかない。
- 次に、マーケティングチーム全体にツールを配った。製品マーケティングの担当者に GitHub Copilot CLI のような AI コーディングツールを教え、Work IQ と独自の MCP サーバーを使える環境も用意した。担当者たちは自発的にツールやスキルを作って共有した。
- 年間約 200 本のブログを承認する立場の担当者は、自分の評価の仕方を反映したルーブリックを作り、エージェントに最初の確認をさせている。エンジニアがそのエージェントを下書きの工程にも組み込み、自分の製品に関する全コンテンツのダッシュボードを得た。品質基準を上げることに集中できるようになった、と話している。
- Foundry Agent Service は、エージェントを安全にホストし、Microsoft IQ と Foundry のツールにつなぐ場所。AMA は実際の顧客との会話のパターンを使い、市場に出す前に異なる読者の視点でメッセージを試せる。
- Foundry IQ で、エージェントは公式のナレッジベースや Web に基づいた回答をする。Work IQ は、社内文書、コミュニケーション、業務のシグナルからリアルタイムの文脈を提供する。
- 結びでは、マーケターの価値は大量のコンテンツを作ることではなく、判断力、センス、戦略、何が読者に響くかを知ることにあると語られた。マーケターは良さの基準を定義する「目利き」であり、戦略と基準を決め、エージェントを通じて実行を拡大する、という考えである。

### 5.3 事例 2：RCA ドラフトの自動生成（Azure エンジニアリング運用）

**チームと問題意識**

Sudhakar と Banani は、Azure エンジニアリング運用に属するミッションクリティカルサービスチームの所属です。あらゆる業界の顧客に対応しており、共通するのは、大きなインシデントのときに、すばやく対応しサービスを復旧して、事業を止めないでほしいという期待だと述べています。

Azure は前年比 **48%** で成長しており、チームも急速に拡大中です。顧客、運用上の需要、トイル（手作業の負担）が増えるため、「今のやり方で拡大を続けるか、運用を根本から考え直すか」を自問しました。約 1 年半前に、原則に立ち返って取り組みを始め、「エージェント型 AI で、特定の機能に関するエンジニアリング時間を 90% 節約できたらどうか」という問いを立てた、と語られています。

チームが提供する機能のうち、優先度が高いのは次の 2 つです。

1. 顧客のミッションクリティカルなアプリケーションに影響する重大インシデントで、インシデントコマンダー（指揮役）を務め、できるだけ早くサービスを復旧する。
2. 同じ問題が再発しないようにする。

発表者は、救急外来の医師が患者情報にアクセスできない場合、家族が急ぎの金融取引をしようとして銀行サービスが落ちている場合、小売業者が取引を何千件も失う場合を例に挙げ、自分たちには技術的なインシデントの 1 つでも、相手には人生で重要な瞬間かもしれない、と述べました。そのため、復旧はすぐの目標、防止は将来の目標であり、サービスが復旧しても仕事は終わらないとしています。

**何が難しいのか**

顧客のミッションクリティカルなアプリは複数の Azure サービスや製品を使っています。調査を始めると、データが複数のツールにばらばらに存在します。主なものは次のとおりです。

- Azure 製品の内部プラットフォームのテレメトリ
- 顧客の利用メトリクス
- 事業への影響を把握するための、サポートケース管理ツールのデータ
- Microsoft Teams の会話
- SharePoint 上のナレッジベース

これが利用製品の数だけ掛け合わされます。インシデント対応中に、データを整理している余裕はありません。ライブ調査中のデータ集約には、すでに別のソリューションを作っています。今回の発表の焦点は、**戦略的な顧客に共有する公式の RCA のドラフトを作る AI ソリューション**です。

最も時間がかかるのは、複数のツールに散らばったデータを集め、突き合わせ、検証する作業でした。RCA のドラフトができたら、サービスや製品の専門家が検証してから顧客に共有します。

**成果**

従来は、製品を問わず Azure の専門家が証拠を手作業で集め、突き合わせ、検証するのに、およそ **2〜3 時間（180 分）** かかっていました。今は AI が **2〜5 分（最大 5 分）** で済ませます。エージェントがドラフトを用意し、専門家が検証してから顧客へ送る点は変わりません。

**自動 RCA のアーキテクチャ（5 段階）**

1. **開始**：エンジニアが CLI にインシデント ID を入力する。インシデントが緩和または解決された後にのみ実行される。
2. **収集**：証拠を 2 つの主な情報源から集める。1 つはケース管理の MCP、もう 1 つは Work IQ で、Teams のチャット、ブリッジ通話、メールを取得する。毎回、新しく取得する。
3. **生成**：Microsoft Foundry 内の複数エージェントが分担する。コーディネーターエージェントが、2 つのエージェントを統括する。ドラフト作成エージェントが、証拠から 5 つのセクションの RCA を書く。レビューエージェントが、すべての主張を証拠と照らして確認し、不足を指摘する。さらに整形エージェントが、Azure の 5 セクション形式に出力を揃える。
4. **配信**：現在は 3 か所に配信する。Teams のノート、エンジニアへの技術サマリのメール、レビュー用の GitHub プルリクエスト（ドラフト）。配信先は複数に増やすこともできる。
5. **人による検証**：すべての出力はドラフトであり、人による検証が必須。エージェントが作業を準備し、結論はエンジニアのものである。

GitHub への出力は特に重要だと強調されました。インシデントから学び、将来の製品改善につなげる場所だからです。

**Foundry を選んだ理由**

発表者は、Foundry が企業向けの AI エージェントを大規模に構築・展開・管理するために必要なものをまとめて提供する点を挙げ、使っている主な機能として次を説明しました。

| 機能 | 説明（発話に基づく） |
| --- | --- |
| Agent Service | 基盤を意識せずに、AI エージェントを展開・実行・拡張できるマネージド環境 |
| モデル | 多数のモデルから選んで、エージェントの目的に合わせてカスタマイズできる（最後に知っている数字として 1 万 1,000 のモデル） |
| IQ | エージェントを企業の知識と事業の文脈につなぎ、関連性の高い、根拠のある回答にする |
| ツール | API、アプリケーション、外部システムにつなぎ、質問への回答にとどまらず行動できるようにする |
| コントロールプレーン | AI エージェント全体の可視化、セキュリティ、監視、ガバナンスを集中して提供する |
| ガバナンスされたエージェントのライフサイクル | 開発から本番まで、エージェントを安全に管理する |

## 6. デモ・手順

デモは行われました。Banani が、RCA エージェントのスコープを絞った版（顧客データ保護のため、実際のツールではなく縮小版）を見せ、続いて Foundry 上でエージェントがどう作られているかを見せています。画面の細部は音声からは確認できず、語られた範囲のみを書きます。

**前半：インシデントから RCA までの流れ（シナリオの説明）**

1. 顧客は Fabricant（聞こえた表記のまま）というサポートアシスタントを Azure OpenAI 上に載せた小売業の顧客です。このアシスタントは問い合わせを受けて回答します。
2. 顧客がマーケティングキャンペーンを始めると、アシスタントの応答が遅くなり、429（リクエストが多すぎる）エラーが出るようになりました。顧客がサポートに連絡し、オンコールのエンジニアが対応しました。
3. バックエンドのテレメトリで、トラフィックのリクエストが 3 倍になり、リクエストの 40% が絞り込み（スロットリング）されていることがわかりました。
4. オンコールのエンジニアは、毎分のトークン割り当て（TPM のクォータ）が飽和していると突き止め、クォータを引き上げました。すぐにエラー率が下がりました。
5. ここでインシデントは緩和済みとなり、エージェントが起動します（インシデント名はデモ用で、発話では聞き取りにくい箇所があります）。

**後半：エージェントの動き**

1. 最初に証拠収集エージェントが、チケット管理の MCP サーバーと Work IQ から情報を集めます。Work IQ は、ブリッジで関与した際のスクリーンショット、Teams のチャット、メールの詳細を提供します。
2. ドラフト作成エージェントが、集めたデータとプロンプトの指示に基づき、5 セクションの RCA を書きます。
3. レビューエージェントは、証拠やドラフトに不足があれば指摘し、人の承認に回します。人の評価を経ずに顧客へ送られることはありません。
4. 人の承認依頼が Teams、オンコールエンジニアへのメール、GitHub のプルリクエストに送られます。承認か却下を選べます。承認すれば Outlook にメールが送られ、エンジニアがレビューして顧客に送ります。却下した場合は、その理由を残し、学習としてエージェントの改善のための評価に回します。

**Foundry でのホスト**

1. Foundry 上でホストされている 4 つのエージェントを表示します。メインのコーディネーターは、ホスト型エージェントです。ホスト型エージェントは、自前のコードを持ち込み、コンテナーに包めば、Foundry が実行してくれるものです。今回は Microsoft Agent Framework（オープンソース）を使いましたが、LangGraph、LangChain、Anthropic SDK など任意のものを使えると説明されました。
2. 直前のインシデントのインシデント ID を入力欄に入れて、送信をクリックします。処理が始まります。
3. 画面右側に、コンテナーから出るログのストリームが表示されます。コンテナーが起動し、エージェントがステップごとに処理して、情報を埋めていきます。
4. 時間がかかるため、すでにできている出力を確認します。出力は GitHub のプルリクエストとして作られ、レビューで見え方を確認できます。人が同意すればマージされ、却下する場合は理由を書き、そのデータを自動評価に使って改善します。
5. 出力の内容として、何が起きたか、なぜ起きたか（マーケティングキャンペーンの開始で、基準のトラフィックに合わせていた TPM のクォータが飽和した）、どう対応したかが示されます。これらのタイムラインは、社内のチケット管理 MCP サーバーから得ています。
6. 重要な点として、証拠がない場合はレビューエージェントが「ない」と示すため、エージェントが作り話をしていないことが確認でき、信頼できると説明されました。
7. さらに下には一般的なガイダンスがありますが、具体的ではありません。これは Microsoft Learn の MCP サーバーから生成されたもので、RCA の指針を示す目的です。

**Foundry の機能の紹介（Sudhakar が質問し、Banani が回答）**

| 機能 | 説明 |
| --- | --- |
| トレース | エージェントのエンドツーエンドのログ。レイテンシ、所要時間、トークンが見える。レコーダーのようなもの。時間がかかる箇所や止まる箇所がわかる。右側に呼び出しの詳細も出る。現在のインシデントとエージェント自体のデバッグに役立つ。 |
| モニター | ライブのダッシュボード。生成 AI のエラー、エージェントの実行、ホスティングの vCPU 時間、メモリ、ツール呼び出しなどが見える。 |
| 評価 | 自動評価、手動評価、AI レッドチーミングの 3 種類。今回は自動評価を使い、スコアが全部緑なら本番へ出せる状態と判断する。モデル、エージェント、データに使える。本番投入後の評価にも使える。 |
| 最適化（Optimizer） | 性能とコストの両方に使える。以前はプロンプトの調整やモデルの調整に多くの時間を使っていたが、最適化を使うことで時間が大きく減った。過去のデータや本番のトレースから直接最適化でき、提案に従って学びを作れる。 |
| ガードレール | 展開時に Microsoft の既定のガードレールが標準で付く。カスタムのガードレールも作れる。ホスト型エージェントでは既定で外向きの通信が拒否されており、独自のガードレールで変更できる。プロンプトインジェクション、リスクのあるツール分析、ジェイルブレイクを本番でリアルタイムにブロックする。 |

## 7. 注意点・発表者の気付き

**技術面の学び（Sudhakar）**

- **エージェントを作るのは簡単だが、信頼を得るのは難しい。** Foundry なら数分で作れるが、エンジニアが自信を持って行動できる正確で安定した結果を出すところから、本当のエンジニアリングが始まる。
- 品質を最優先にして、コストとレイテンシの最適化は最初は一切考えなかった。間違った回答が 2 秒で返ってきても価値がないためである。品質が狙いどおりになってから、速度とコストの最適化に進んだ。

**運用面の学び（Brett）**

- **専門家をビルダーに変えることが最も重要。** エージェントは人の専門性を拡大できるが、専門性そのものは作れない。ブログの事例では、ブログの専門家がスキルを作ってそれを Foundry に展開でき、RCA の事例では、専門家がプロセスを文書化し、RCA に必要な形のルーブリックを作ったため、エージェントオプティマイザーでプロンプトを調整して信頼できる水準に持っていけた。
- **エージェントは、仕事がすでに行われている場所に組み込む。** ブログ管理プラットフォーム、Teams、GitHub など、アクセスしやすい場所に置く。そうでないと厳密さが時間とともに失われ、プロセスの本当の変革と AI からの ROI を得られない。

**その他のメモ**

- ブログの事例では、スキルを任意利用にすると厳密さが失われ、フォークで内容が分散しました。これが、中央のエージェントへ移行した理由です。
- IT 部門の合意を得るのが難しかった点は、ガードレール（プライベート VNet、エージェント専用 ID、中央管理の制約）で解決しています。
- すべての出力はドラフトで、人による検証が必須です。

## 8. 利用者にとっての利点

発表は Microsoft 社内の事例であり、語られた効果は次のとおりです。

| 事例 | 成果 |
| --- | --- |
| ブログのレビュー | 工程全体が 2〜4 週間から 10 分に。実作業が 8〜12 時間（6 回の下書きと 12 通のメール）から短縮。数千時間の PMM の時間を節約 |
| ブログの品質 | 弱い・非常に弱い投稿に当たる読者が 42% から 1% 未満へ。ソーシャルで拡散される投稿が 23% から 60% へ。技術コミュニティでの発言シェアが 1.5 倍 |
| RCA の作成 | 証拠の収集・突き合わせ・検証が 2〜3 時間から 2〜5 分へ。専門家の検証は残る |
| ガバナンス | プライベート VNet、エージェント専用 ID、監査、中央管理のガードレールにより、IT が機密データを扱うエージェントを許容できた |

## 9. まとめ

2 つの Microsoft 社内の事例は、**専門家の基準、根拠のある文脈、人の最終判断**という同じ形をしています。ブログレビューでは、6 つの観点のルーブリックを GitHub Copilot CLI のスキルから Foundry のエージェントへ発展させ、公開までの時間を 2〜4 週間から 10 分にしました。RCA では、5 段階の仕組みと 4 つのエージェントにより、2〜3 時間の作業を 2〜5 分に短縮しています。

学びとして、エージェントを作るのは簡単でも信頼を得るのは難しいこと、まず品質を整えてから速度とコストを最適化すること、専門家を作り手にすること、仕事の場所にエージェントを組み込むことが挙げられました。
