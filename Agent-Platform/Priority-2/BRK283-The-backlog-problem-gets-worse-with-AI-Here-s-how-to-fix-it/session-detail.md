# BRK283 The backlog problem gets worse with AI. Here's how to fix it

## 1. はじめに

このセッションは、AI がコードを大量に生み出すことでセキュリティ上の未対応案件（バックログ）が膨らむ問題を、GitHub Advanced Security の機能で「防ぐ・見つける・直す」の 3 段階に分けて解説する発表です。約 30 分で、GitHub のデータを示したあと、オープンソース依存関係、コードスキャン、シークレット（API キーやパスワード）の 3 種類について、実際の画面を使って設定方法と使い方を見せていきます。

発表者が最初に会場へ挙手で尋ねたところ、GitHub の利用経験者は多く、開発者とアプリケーションセキュリティ担当がおよそ半々でした。そのため基礎（101）から中級（201、301）まで順に触れる構成になっています。**最も重視されたメッセージは、問題が起きてから対処するより、起こさない仕組み（予防）を先に整える**という点です。発表で示された機能は、github.com で一般提供（GA）またはパブリックプレビューの段階にあり、今すぐ試せるとのことです。

## 3. 何に関する発表か

背景として、AI コーディングツールの普及でコードの量が急増し、それに伴って脆弱性も増え、攻撃者が脆弱性を悪用するまでの期間も短くなっている、という現状が示されます。GitHub Advanced Security が目指すのは、AI が書いたコードでも人間が書いたコードでも、ソフトウェア開発ライフサイクル（SDLC）が既定で安全かつ高品質になることです。この発表では、SDLC のうち CI やビルド・デプロイより前の、コードに関わる部分に絞っています。

発表の流れは次のとおりです。

1. データで見る現状（コード量、Dependabot アラート、悪用までの期間）
2. オープンソース依存関係：マルウェアの増加、GitHub package firewall（予防）、Dependabot のマルウェアアラート（検出）、到達可能性分析（優先度付け）、修復
3. コードスキャン：セキュリティレビュー（予防）、CodeQL と AI scan（検出）、agentic auto fix（修復）
4. シークレット：push protection（予防）、AI による検出、セキュリティキャンペーン（修復）
5. 最初に何をすべきか（101 から 301 までの進め方）
6. 質疑応答

## 4. 発表者が伝えたいメッセージ

発表者の主張は、**コードの量が増え、脆弱性が増え、悪用までの時間が短くなっている以上、見つけてから直す一辺倒では追いつかない。まず入り口で止める予防を優先し、そのうえで優先度付けと一括修復でバックログを減らす**というものです。

各領域とも「予防・検出・修復」の 3 段階で整理されています。依存関係は package firewall で止め、Dependabot で見つけ、到達可能性で絞り込んで修復します。コードはエディターのセキュリティレビューで止め、CodeQL と AI scan で見つけ、agentic auto fix で直します。シークレットは push protection で止め、検出したアラートをキャンペーンで消化します。発表者は特にシークレットについて、「ひとつだけ持ち帰るなら push protection を有効にすること」と述べています。

## 5. 発表内容の詳細

### 5.1 データで見る現状

スライドには 3 つのグラフがありました。

| グラフ | 内容 |
| --- | --- |
| コード量 | 直近の四半期で GitHub へのコミットは 74 億件。2026 年のプッシュの量は、2024 年と 2025 年を合わせた量を上回る |
| 脆弱性 | 四半期ごとの Dependabot アラートの新規件数は、直近の四半期で 4 億 3,900 万件（累積ではなく四半期の純増） |
| 悪用までの期間 | 脆弱性の公開から悪用までの期間が、2023〜2024 年は月単位だったのに対し、現在は日単位 |

発表者は、コード量の増加には AI コーディングツールが大きく関わっていると述べ、3 つのグラフを「コードが増え、脆弱性が増え、攻撃者はこれまでにない速さで悪用している」と読み解いています。直近 1 か月だけでも、PHP、Node、そして今週は Java に関する脆弱性攻撃があり、対応中の人も多いだろうと触れています（名称は音声認識の都合で表記が確定できません）。

終わりの時期が見えない点も指摘しています。Satya Nadella が今週、AI が見つけたバグへのパッチ対応がいつ終わるか分からないと述べたと紹介しました。セキュリティ業界には「最悪の 1 年になる」という見方と「誰にも分からない」という見方があり、発表者自身は後者に近い立場で、モデルがさらに高性能になった先は分からないと述べています。

### 5.2 オープンソース依存関係：マルウェアの急増

GitHub Advisory Database の勧告件数の推移が示されました。脆弱性（紫の棒）とマルウェア（ピンクとオレンジの棒）があり、マルウェアは 2023〜2025 年に倍程度のペースで増えていましたが、2026 年はそれをはるかに上回る伸びです。発表者は「8 倍」と述べたあとで言い直し、**マルウェアと脆弱性の比率が 8 対 1** になったと説明しました。

脆弱性とマルウェアの違いは次のとおりです。

| 種類 | 内容 | 通常の対処 |
| --- | --- | --- |
| 脆弱性 | 正規のパッケージに含まれるミスを攻撃者が悪用できる状態 | バージョンを上げる（例：Lodash のあるバージョンから次の非脆弱なバージョンへ） |
| マルウェア | 害を与える目的で作られたパッケージ | 削除する（例：Lodash に似せた名前の誤入力を狙うタイポスクワットのパッケージ） |

増加の理由として、発表者は次の 3 点を挙げています。

- 悪意のあるパッケージを公開レジストリに出すコストがほとんどかからず、AI によって、もっともらしい偽物を大量に作るコストがさらに下がった。
- エージェントが自分で依存関係をインストールする場合や、急いでいる人間が名前を打ち間違える場合に、攻撃されやすい。
- 防御側もマルウェアの検出と報告が上手になり、見つかる件数が増えた。

### 5.3 予防：GitHub package firewall

GitHub package firewall は、開発者のマシン、CI システム、コーディングエージェントなどのエンドポイントと、公開レジストリの間に置くプロキシーです。パッケージのダウンロードのたびに、設定したポリシーに違反していないかを確認し、違反していればインストールさせません。

ポリシーは企業（エンタープライズ）の設定画面から指定します。既定では Actions のランナーに効きます。ローカル環境にも適用できますが、レジストリの設定が追加で必要です。設定できる条件は次のとおりです。

**既知のリスクにもとづく条件**

- 既知のマルウェアをブロックする。発表者は、ためらわず有効にしてよい設定だと述べています。GitHub Advisory Database に勧告があるタイポスクワットのパッケージを、そもそもインストールさせません。
- 既知の重大度（CVSS スコア）で止める。致命的、高、中、低のどの水準で止めるかを選べます。

**バージョン間の不審な変化にもとづく条件**

- 来歴証明（SLSA provenance）が付いていたパッケージが、次のバージョンで付かなくなる「アテステーションの格下げ」をブロックする。
- これまでなかったインストール前後のスクリプトが、新しいバージョンで追加された場合をブロックする。発表者は、昨年の今ごろに起きた Shai-Hulud（発話では「Shy Halud」と書き起こされています）という攻撃で、新バージョンにこうしたスクリプトが追加されていたと触れ、これで防げたはずだと述べています。
- 公開されたばかりのパッケージをブロックする。公開直後に問題が見つかるケースがあるため、クールダウン期間（1 日、3 日、7 日、14 日など）を設定します。最先端にならず、善意の側が問題を見つけて修正する時間を稼ぐ考え方です。

**ライセンスにもとづく条件**

- ライセンスコンプライアンスとして、設定したライセンスポリシーに違反する依存関係のインストールを防げます。例として、コピーレフトのライセンスを避けたい場合が挙げられています。

発表者は、脆弱性の量が大きく増えた現在、新たに持ち込まないことが最も効くため、こうした予防機能を使っていないなら使うべきだと述べています。

### 5.4 検出：Dependabot のマルウェアアラート

予防をすり抜けた場合に備えて検出する手段として、Dependabot のマルウェアアラートが紹介されました。デモでは、リポジトリの設定の「Advanced Security」に進み、Dependabot アラートとマルウェアアラートを有効にします。悪意のあるパッケージがインストールされたとき、また意図しない脆弱性が悪用されうるときに通知します。

発表者は、これを初めて有効にした人との通話を多く経験していて、**およそ 4 回に 1 回は、数分後に通話から抜けてインシデント対応を始める**と述べています。マルウェアを使っていたことが判明するからです。無料で手間もかからないため、有効にするよう勧めています。多くの場合は何も見つからないとも述べています。

### 5.5 優先度付け：到達可能性分析

リポジトリの「Security and quality」タブの Dependabot の脆弱性一覧を開くと、デモのリポジトリには未対応のアラートが 105 件あります。今四半期に追加された機能として紹介されたのが**到達可能性分析**です。脆弱なバージョンのパッケージを使っているだけでなく、自分のコードが脆弱な関数を実際に呼び出しているかを判定します。静的解析で、直接依存と推移的依存の間のコードパスをたどる仕組みです。デモでは、105 件のうち到達可能なのは 13 件でした。

発表者は、到達可能性を単独で使うのではなく、次のような指標と組み合わせるよう勧めています。

- 重大度（CVSS スコア）
- EPSS スコア
- そのコードが本番環境にデプロイされているか（Microsoft Defender for Cloud（MDC）や JFrog と連携して判断）

到達可能性分析は、現時点で無料で提供されていて、有効にして試せるとのことです。

### 5.6 修復：Dependabot セキュリティ更新とエージェントへの割り当て

デモでは、到達可能で直接依存の致命的なアラートを例に、2 つの修復方法を見せています。

- **決定論的な Dependabot セキュリティ更新**：ボタンを押すか、設定で Dependabot の更新に登録すると、バージョンを 1 つ上げるプルリクエストを開きます。
- **エージェントへの割り当て**：バージョンを上げて破壊的変更が出て CI が失敗し、原因が分からないときなどに、アラートをエージェントに割り当てます。エージェントは Copilot のほか、Claude や Codex など任意のものを選べます。発表者は Microsoft で働いているため Copilot を選ぶと述べています。エージェントはリポジトリの文脈とカスタム指示を読み、追加の文脈も与えられます。パッケージを削除して同等の別パッケージに置き換えるよう指示する例も聞いたそうです。エージェントはプルリクエストを開き、脆弱性だけでなく破壊的変更も直します。

### 5.7 コードスキャン

Dependabot が見るのは取り込んだサードパーティーのパッケージです。コードスキャンは、自分で書いたコードの脆弱性を、静的解析エンジンの CodeQL と AI scan で見つけます。CWE（脆弱性の種別）の傾向は 2025 年から 2026 年でも変わらず、クロスサイトスクリプティングや SSRF といった、お馴染みの少数のカテゴリーが大半です。ただし件数は増えています。そのため、**コードが書かれるあらゆる場所、特にエージェントが書く場所で、コードスキャンを動かすことが重要**だと説明しています。

予防はエディターのセキュリティレビュー、検出は CodeQL と AI scan、修復は agentic auto fix という整理です。

### 5.8 シークレットスキャン

スライドのグラフでは、検出されたシークレットを修復するまでの平均時間が約 40 日で、その間は鍵が露出したままです。**5 件に 1 件は 90 日を超えます。** 新たに検出されたシークレットの内訳は、**約 30% が push protection で止められ、残り 70% は push 後か、すでにリポジトリの履歴にあったものから見つかりました。**

発表者は、AI が普及しても開発者が不注意になったわけではなく、シークレットを含む push の割合はほぼ横ばいだと述べています。ただし、AI コーディングエージェントが書くコードの量が増え、シークレットの量もコードの量にほぼ比例して増えている、という説明です。**シークレットでは予防が最優先**で、push protection は、push する時点で API キーやパスワードなどを検査し、シークレットが GitHub に届く前にブロックします。現在、GitHub 上で見られるシークレットの約 30% が、これでコミット履歴に入る前に止まっています。

### 5.9 質疑応答

質問者は、メールで届くマルウェアアラートから、手動で割り当てる代わりに、GitHub Actions のワークフローを直接起動できるかを尋ねました。発表者は、**エージェントを使う形で自動化できる**と回答しました。ワークフローを設定して自動的に動かせます。GitHub agentic workflows が適した方法で、実際にそうしている人を見たことがあるとのことです。ただし設定が必要だと補足しています。ほかに質問はありませんでした。

## 6. デモ・手順

このセッションでは、github.com と VS Code の画面を使ったデモが 4 つ行われました。画面の細部（ボタンの位置など）は音声からは確認できません。デモには、Avocado Corporation というエンタープライズと、Contoso Checkout というリポジトリが使われています。

### 6.1 package firewall のポリシー設定

1. エンタープライズの設定で、ポリシーから package firewall を開く。
2. ポリシーで指定できる項目を順に説明する。既知のマルウェアのブロック、重大度（CVSS）によるブロック、アテステーションの格下げ、新規のインストール前後スクリプト、公開直後のパッケージ（クールダウン）、ライセンスコンプライアンス。

発話では、ポリシーを保存する操作や、ブロックされる様子の実演は確認できません。

### 6.2 Dependabot のマルウェアアラートの有効化

1. デモ用の組織とリポジトリを開く。
2. 設定の「Advanced Security」を開き、スクロールして Dependabot のアラートとマルウェアアラートの項目を探す。

### 6.3 到達可能性の確認とエージェントへの割り当て

1. リポジトリの「Security and quality」タブから Dependabot の脆弱性を開く。未対応は 105 件。
2. 到達可能性の絞り込みで、到達可能なアラートが 13 件であることを示す。
3. 到達可能で致命的な、直接依存のアラートを例にする。
4. Dependabot セキュリティ更新のボタンを説明する（クリックして実行した様子は発話では確認できません）。
5. アラートをエージェントに割り当てる選択肢を示す。エージェントとして Copilot を選び、追加の文脈を入力できると説明する。

### 6.4 VS Code のセキュリティレビュー

1. 画面共有を VS Code に切り替える。リポジトリは同じ Contoso Checkout。
2. ローカルでコードを追加し、コミット前にセキュリティレビューをしたい場面を設定する。
3. 側面のバーに「security review」（セキュリティレビュー）と入力すると、通常は青い「セキュリティレビュー」ボタンが出る。デモでは出なかったため（VS Code が接続されていないかもしれないと発表者は述べています）、実行に約 3 分かかることから、朝のうちに実行済みの結果を見せる。
4. レビューは、ローカルの変更を公開側のリポジトリと比較した差分を調べ、結果を重大度順に表示する。クロスサイトスクリプティング、SSRF、SQL インジェクションが挙がり、それぞれに本物の脆弱性である確からしさ（信頼度）が付き、対処法が示される。
5. 選択肢として、重大度の最も高いものを直す、すべて直す、または発見事項の要約をコミットする、がある。

### 6.5 コードスキャンと agentic auto fix

1. github.com に戻り、同じデモリポジトリの設定「Advanced Security」を開く。コードセキュリティは有効にしてある。有効にすると CodeQL 分析が使える。
2. 「AI scan for pull requests」も有効にしてある。CodeQL が対応していない言語（例：PHP）に対して、AI がセキュリティの発見事項を生成する。
3. コードスキャンの結果として、デモリポジトリにはコードインジェクションなどが 19 件ある。
4. 1 件ずつ開発者かエージェントに割り当てられるが、依存関係と違って件数が少ないため、すべてをエージェントに割り当てる選択を紹介する。これが agentic auto fix。
5. 全件を選んで Copilot に割り当てると、Copilot が全件を調べ、1 つの大きなプルリクエストで修復する。ここでは割り当ての操作は説明されましたが、プルリクエストの結果は発話では確認できません。

### 6.6 シークレット保護の設定とセキュリティキャンペーン

1. 設定の「Advanced Security」の先頭にある「Secret protection」を示す。有効にすると、リポジトリを継続的に監視し、コミット履歴でシークレットを見つければアラートを出す。
2. push protection の設定を示す。サポート対象のシークレットを含む push をブロックする。
3. 独自のパターンがある場合に、正規表現（regex）でカスタムパターンを登録できることを説明し、デモリポジトリには、このパターンで作った偽のシークレットがあることを示す。
4. 最近追加された、パターンのないシークレットを AI で検出する機能の設定を示し、有効にするよう勧める。
5. 偽のシークレットに対するアラートの画面を見せる。
6. 「Security and quality」から「Campaigns」を開く。キャンペーンの種類にシークレットがあり、シークレットスキャンの絞り込みから作る。
7. Ignite 用に使ってきたリポジトリに絞り、偽のシークレットを対象にする。
8. キャンペーンを下書きとして保存する。名前は「Ignite Burn Down #2」。発表者が責任者（キャンペーンマネージャー）で、連絡用のリンクもある。
9. 対象の発見事項がまとめられ、期限を設定する。発表者は、期限を感謝祭にしたと述べています。簡単な説明も入力する。
10. レビューして公開すると、追跡と管理ができ、アラートを開発者に割り当てて修復させられるキャンペーンが始まる。

## 7. 注意点・発表者の気付き

- **マルウェアアラートを初めて有効にすると、インシデント対応が始まることがある。** 発表者は、およそ 4 回に 1 回、通話中にその場でマルウェアの使用が判明したと述べています。多くの場合は何も見つからないとも述べています。
- **到達可能性分析は単独で判断しない。** 重大度、EPSS、本番環境へのデプロイ有無と組み合わせるよう勧められています。
- **コードスキャンの件数と依存関係の件数は桁が違う。** 依存関係では数百、数千、大きな企業では 100 万件を超える例もあるため、エージェントへの一括割り当ては件数の少ないコードスキャンに向いている、という趣旨の説明でした。
- **シークレットは検出よりも予防が重要。** 平均修復時間が約 40 日と長く、5 件に 1 件は 90 日を超えます。
- **Dependabot の更新で破壊的変更が出る場合がある。** その場合はエージェントへの割り当てが選択肢になります。
- **自動化には設定が必要。** アラートからワークフローを自動で起動する場合、GitHub agentic workflows で実現できますが、設定は必要です。
- 発表の内容は、コードに関する部分に限られます。CI システムから本番環境までの機能にも触れていますが、詳細は説明されていません。
- 数値の表記に食い違いがあります。冒頭ではコミット数が「直近の四半期で 74 億件」、まとめでは「1 か月あたり 74 億件」と述べられ、また Dependabot アラートはまとめで「439 件の未解決（open）」と聞き取れます。本書では冒頭の数値を採用しています。

## 8. 利用者にとっての利点

発表では、顧客企業の導入事例や、導入によって得られた効果の数値は紹介されていません。語られた利点は次のとおりです。

- 予防機能（package firewall、push protection、セキュリティレビュー）により、新たな脆弱性やシークレットを持ち込む前に止められます。
- 到達可能性分析により、105 件のアラートから対応が必要な 13 件に絞り込めます（デモの例）。
- エージェントへの割り当てと agentic auto fix で、修復のプルリクエストを自動で作れます。
- セキュリティキャンペーンで、発見事項をまとめて、期限と担当者を決めて消化できます。
- Dependabot と到達可能性分析は、無料で利用できると説明されています。
- 組織やエンタープライズの単位では、多くの機能をワンクリックで展開できると説明されています。

## 9. まとめ

AI によってコードが増え、脆弱性とマルウェアが増え、悪用までの時間も日単位に縮んでいます。GitHub Advanced Security は、SDLC を既定で安全かつ高品質にすることを目指し、予防・検出・修復の 3 段階で対策を用意しています。

発表者が勧める最初の一歩は次のとおりです。

1. **今日やること**：無料の GitHub Advanced Security リスク評価を実行し、Dependabot（特にマルウェアの検出）を有効にし、組織またはエンタープライズ単位で一括して設定を展開する。入り口を止めるために、package firewall、push protection、ローカルエディターのセキュリティレビューを使う。
2. **中級（201、301）**：到達可能性分析で優先度付けの文脈を足し、MDC、Dynatrace、JFrog、自社の CI から本番の文脈を連携し、チームが信頼する絞り込み条件を合意して保存する。
3. **バックログを減らす**：Dependabot の更新、agentic auto fix、セキュリティキャンペーンで消化する。
