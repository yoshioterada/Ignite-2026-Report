# BRK288 Visual Studio governance for the agentic era

## 1. はじめに

このセッションは、組織の中で Visual Studio を配布・管理する IT 管理者や、開発者支援の担当者に向けた発表です。1,000 台規模のマシンに Visual Studio を入れて最新に保つ方法、拡張機能を管理する方法、そして AI（Copilot）の利用範囲を統制する方法を、「現在提供されているもの」「プレビュー中のもの」「検討中のもの」を区別しながら説明しています。

発表は 3 部構成です。1 部目はインストールの運用で、レイアウト（インストール用ファイル一式）の作成から、標準ユーザーによるインストール、チームごとの構成ファイル、更新のサイクルまでを扱います。2 部目は拡張機能で、プレビュー中のプライベートマーケットプレースを、エンジニアがデモで見せています。3 部目は AI ガバナンスで、AI の利用経路、ガードレールの配布、エージェントの権限、モデルや MCP サーバーの統制、組織内ノウハウの共有、今後の投資予定が語られます。

## 3. 何に関する発表か

Visual Studio は 30 年にわたりプロの開発者のためのツールとして進化してきました。AI によって開発が再び変わりつつある中で、「個々の開発者が AI の恩恵を受けながら、組織は必要な統制を保つにはどうするか」が発表の問いです。

最初に、聴衆への依頼が 2 つありました。

- 今回の内容は Visual Studio プラットフォームを対象としており、SQL Server Management Studio（SSMS）にも関係する。一部は SSMS でも今日使え、一部は検討中である。SSMS を管理していて足りない点があれば、開発者コミュニティで伝えてほしい。
- Visual Studio プラットフォームの管理方法に唯一の正解はない。ネットワークやセキュリティ要件、支援するチームによって適した方法が変わる。QR コードのアンケートに連絡先と意見を書くと、定期開催の管理者向け通話（Admin Champs call）に招待してもらえ、課題の解決を直接支援してもらえる。

## 4. 発表者が伝えたいメッセージ

全体を通じた主張は、開発者の自由と組織の統制を両立する、というものです。具体的には次の 3 点です。

- インストールは、承認済みファイル 1 式と、チームごとの構成ファイルで一本化する。
- 拡張機能は、見せるものの制御から、インストール、実行の制御へと広げていく。
- AI では「何がインストールされているか」ではなく、「エージェントがどんな機能、モデル、接続を使えるか」が統制の対象になる。

また、発表者は各項目について、今日提供できるもの、プレビュー、これから取り組むものを明確に分けると述べており、実際にそのように説明が進みます。

## 5. 発表内容の詳細

### 5.1 インストールの運用（IT 管理者の想定シナリオ）

想定は、1,000 台のマシンで Visual Studio を管理し、複数の開発チームを支える IT 管理者です。チームごとに必要なツールは違い、例えば .NET アプリを作るチームと、C で始まる別の言語（音声では「C」としか聞き取れません）を扱うチームがあります。チームごとに別の配布手順を保守したくありませんし、開発者がローカル管理者でない場合、インストール依頼がすべてサポートチームに来るのも避けたいはずです。SDK が足りない開発者はビルドできず、更新を飛ばしたマシンはセキュリティ修正が欠けるかもしれません。

目標は、承認済みのファイル一式を 1 つ持って最新に保ち、各チームの構成ファイルがインストールするツールを指定する形にすることです。手順は次の 4 ステップです。

1. 承認済みのファイルを用意する。
2. 管理者パスワードなしでインストーラーを使えるようにする。
3. 各チームが自分の構成を提供し、開発者が必要なツールをインストールする。
4. 承認済みの内容を最新に保ち、開発者が適用する。

#### レイアウトの作成

インストール用のファイルを、レイアウトと呼ぶフォルダーにダウンロードします。この段階では Visual Studio はインストールしません。レイアウトには、選んだワークロードとコンポーネントだけを含む部分レイアウトと、選んだエディションと言語で利用できるすべてを含む完全レイアウトがあります。ここでは **完全レイアウト** が推奨されています。チームごとに必要なパッケージが違い、後から足りないと分かっても、開発者がインターネットから直接インストールできない設定にしていると困るからです。

たとえとして、ソフトが入っていた CD やフロッピーディスクが挙げられました。製品全体のファイルが入っていて、その中から入れる部分を選ぶ、という仕組みです。完全レイアウトも、全員が同じ元を使い、各チームが必要な分だけインストールします。

作成方法は、使いたいバージョンの Visual Studio のブートストラッパーをダウンロードし、それを使って完全レイアウトの内容をダウンロードします。画面には、そのコマンドが表示されました（コマンドの中身は発話では読み上げられていません）。完全レイアウトは、部分レイアウトより最初のダウンロードが大きく、ディスク容量も必要です。発表者のテストでは約 30 分かかり、約 86 GB になりました。ダウンロードが終わったら、IT チームがセキュリティとコンプライアンスの確認を行い、承認された後に、そのフォルダーをチームに公開します。

#### 標準ユーザーによるインストール

開発者がローカル管理者でなくてもインストールできるようにする設定が、**標準ユーザー制御を許可する**（Allow standard user control）です。スライドでは値を 2 に設定していました。この設定により、標準ユーザーが Visual Studio のインストール、ワークロードとコンポーネントの追加・削除、更新、ロールバックを、Visual Studio インストーラー経由で行えます。

IT チームは、この設定を Intune またはグループポリシーで、Visual Studio の ADMX テンプレートを使って一括配布します。レジストリ値を手で設定する必要はありません。開発者は管理者パスワードなしで、承認済みレイアウトからチームのツールをインストールします。開発者は標準ユーザーのままで、与えられるのは Visual Studio のインストールの制御であり、マシンの管理者権限ではありません、と強調されました。

#### チームごとの構成ファイル（.vsconfig）

レイアウトに全ツールがあっても、全マシンにすべて入れるわけではありません。各チームが提供する VS 構成ファイル（`.vsconfig`）が、そのチームに必要なツールをインストーラーに伝えます。例えば .NET デスクトップアプリを作るチームでは、リーダーがインストーラーを開いて構成をエクスポートします。実際に動いているインストールからそのまま出力することも、ワークロードとコンポーネントを調整してから出力することもできます。JSON を手で書く必要はありません。

画面には、.NET デスクトップ開発用と、もう 1 つの言語（音声では「C」と聞こえます）用の 2 つの短い構成ファイルが示されました。形式は同じですが、用途は大きく異なります。リーダーが内容を確認したら、そのファイルをチームのプロジェクトやソリューションと並べてソース管理にチェックインします。以後、チーム全員が同じ構成でインストールできます。

#### 更新のサイクル

次の承認済み更新が出たとき、製品全体を再ダウンロードする必要はありません。最初に作った完全レイアウトを最新に保ちます。3 ステップを更新のたびに繰り返します。

1. **レイアウトを更新する**：更新先バージョンのブートストラッパーを入手して実行すると、すでにあるパッケージを確認し、新しいバージョンに必要な内容だけをダウンロードする。
2. セキュリティとコンプライアンスの確認を行い、新しい内容を公開する。既存のインストールは、承認済みのソースから更新するよう構成済みである。
3. 開発者が適用する。区切りの良いところで作業を保存し、Visual Studio を閉じて、更新を選ぶ。インストーラーが承認済みの内容から更新する。先に設定した標準ユーザーのポリシーにより、管理者パスワードは不要。

#### 検討中の領域

「今、調べていること」として、3 点が挙げられました。

- **内容の選択**：開発者が何をインストールし、実際に何を使っているか、その作業が何に依存するかを見やすくし、展開の途中で依存関係の不足に驚かないようにする。
- **繰り返し可能な展開**：パッケージを作るチーム、セキュリティを確認するチーム、展開するチームが別々の場合に、どこで手順が崩れるか。より良いガイダンスと、企業環境でのテストが助けになると考えている。
- **仮想デスクトップ**：多くの開発者が仮想マシンで作業している。ユーザープロファイルについて FSLogix で初期のテストを行った。その場で更新するのか、新しいイメージに入れ替えるのか、開発者がすぐ作業に戻れるよう何を引き継ぐ必要があるかを聞きたい。

なお、ここで紹介した方法は Visual Studio を展開する一つのやり方です。Microsoft から直接ダウンロードする、エアギャップ環境を支える、スクリプトや管理ツールで自動化するなど、ネットワークやセキュリティ要件、マシンの管理方法で変わります。これらの選択肢は、画面に示された管理者ガイドに詳しくあります。

### 5.2 拡張機能のガバナンス

組み込みのワークロードとコンポーネントで、多くの開発者は標準のままで生産的になれ、IT 側で審査したり追跡したりするものが増えません。ただし、製品にない特化したツールが必要なチームもあり、そこはエコシステムのパートナーが拡張機能で補っています。その追加分は、IT が支える環境の一部になります。管理者との調査や対話で、次の 3 つの要望が繰り返し聞かれたそうです。

1. どの拡張機能をインストールできるかを制御する。
2. どれを読み込めるかを決める。
3. 実際に何が動いているかを把握する。

#### プライベートマーケットプレース（プレビュー）

開発者が拡張機能マネージャーを開いたときに、自社のチームが作ったツールと、承認した公開の拡張機能が並んで見える体験です。プライベートな NuGet フィードを使っていれば、感覚は近いと説明されました。社内の拡張機能をホストし、公開マーケットプレースを上流ソースとして接続し、開発者が閲覧するときに利用できる公開拡張機能を選べます。設定はグループポリシーで IT が管理できます。

関連して、次の機能が語られています。

| 機能 | 内容 | 状況 |
| --- | --- | --- |
| クールダウン | 新しい拡張機能や更新が、開発者の目に触れるまでに少し待たせる。新しい公開コンテンツがいつ自社のマーケットプレースに現れるかを決める | 「持ち込もうとしている」と説明（提供時期は発話で確認できません） |
| 認証 | 自社向けに作ったツールを、意図した人だけに共有する | 取り組み中（5.3 のデモで詳細） |

公開マーケットプレースは、受け取るすべてのパッケージを、Microsoft Defender などの主要なウイルス対策エンジンと同じ技術でマルウェア検査しており、公開後も脅威の変化に合わせて再検査を続けています。クールダウンは、その上でさらに待たせたい場合の手段です。

### 5.4 インストールと実行の制御（取り組み中）

見せる内容を制御するだけでは半分です。開発者が直接リンクや、誰かから送られたファイルで拡張機能を入手することもあり得ます。そこで、次の制御に取り組んでいます。

- **インストールのガバナンス**：組織が許可する拡張機能を決め、承認していないものをインストールしようとすると Visual Studio がブロックする。
- **出所の確認（プロベナンス）**：公開マーケットプレースでのマルウェア検査の効果を、インストール時にも得られるようにする。Visual Studio が、VSIX が、マーケットプレースで検査されたものと同一のパッケージであることを確認し、改ざんされていればインストールを止める。

最初の対象は、エコシステム内で完結する拡張機能です。つまり VSIX として梱包され、公開またはプライベートのマーケットプレースにホストされ、Visual Studio 経由でインストールされるものです。他所でホストされるものや、VSIX ではなく MSI や EXE で提供されるものは、エコシステムのパートナーや企業顧客と共に、共通の検証方法を検討しています。

さらに先として、管理者の残り 2 つの要望に対応する領域が挙げられました。

- **監査**：マシンにある拡張機能のうち、何が実際に使われているか、入れるべきでないものがないか、を把握する。
- **実行時のガバナンス**：インストールの制御があっても、拡張機能が意図しない場所に入る可能性がある。実行時のガバナンスで、読み込みそのものを止められるようにする。

これらは今後の検討で、現時点では提供されていません。発表者は、テストへの協力を求めています。今日試せるのは、画面のリンクにある手順で作るプライベートマーケットプレースです。

### 5.5 AI ガバナンス：課題と判断

Praveen 氏の説明は、「AI では、開発者のマシンに何が入っているかだけでなく、エージェントが使える機能、モデル、接続が問題になる」という前提から始まります。顧客から聞く疑問は次の 3 つにまとまります。

- 知的財産を守りたい。コードとプロンプトがどこに行くかを知りたい。
- エージェントの行動に境界を設けたい。何にアクセスでき、どう実行するかを知りたい。
- チームとツールをまたいで統制したい。

これらを実務の判断に変えるために、次の 4 つの進め方が示されました。

1. AI の経路を選ぶ。
2. 開発者へガードレールを配る。
3. エージェントの機能、モデル、接続の境界を決める。
4. 組織のノウハウを共有する。

### 5.6 AI の経路を選ぶ

最近まで、Visual Studio に AI を持ち込む唯一の方法は GitHub Copilot のサブスクリプションでした。それが AI 支援の作業に最良のプラットフォームだと考えている、というのが前提です。ただし、医療や銀行のような機微な業界では、GitHub アカウントでサインインできない組織があります。その場合の選択肢が次のとおりです。

| 選択肢 | 内容 |
| --- | --- |
| BYOK（自分のキーを持ち込む） | Microsoft Foundry の API キー（モデルとベンダーを選べ、ファインチューニングしたモデルも使える）、Anthropic または OpenAI の API キー、Open Router のような API ゲートウェイ |
| 組織ホストの推論 | コードとプロンプトを組織の境界内に留めたい、またはエアギャップ環境の場合。自前のインフラに、OpenAI 互換のカスタムエンドポイントをホストして使う |
| ローカル推論 | 開発者のマシン上で Ollama や LM Studio などを使う |

また、最新の安定版の Visual Studio は、共通の Copilot 基盤の上に作られています。VS Code、Copilot CLI、GitHub アプリなど、ほかの Copilot の画面も同じ基盤です。管理者にとっては、共通の管理とガバナンスの層が得られることになります。

### 5.7 ガードレールの配布

配布方法は 2 つです。

- **GitHub Copilot の顧客**：GitHub.com で構成したポリシーが、Copilot アカウントに付いて利用者に届く。
- **BYOK などほかの経路**：デバイスベースの配布。IT が MDM や Intune といった既存のポリシーで、対応する設定と制限をデバイスに届ける。

### 5.8 エージェントの機能の制限

組織の準備状況に応じて、次のように制限できます。

1. エージェント主導の実行に組織が備えられていない場合は、**エージェントモードを無効にする**。開発者は質問モード（Ask モード）は使え、エージェントは使えない。
2. **プレビュー機能を無効にする**。個々の開発者がオプトインする必要がなくなる。
3. エージェントモードは使えるが、エディターの外の情報へのアクセスや操作のための接続はさせたくない場合は、**MCP を無効にする**。
4. エージェントが通常の権限確認を省いて自律的に実行できる、**権限バイパスを無効にする**。

### 5.9 モデルのポリシー

GitHub Copilot のサブスクリプションがある組織は、次のことができます。

- 組織内で使用を許可するモデルを承認する。
- 新しいモデルを既定でオフにし、使えないようにする。
- 新規または未構成のモデルに管理者の承認を求める。

Visual Studio は Fusion と Auto もサポートしており、実行中のタスクに応じてモデルを自動選択します。この選択は、管理者の制限の範囲内で動作します。

### 5.10 接続の統制（プライベート MCP レジストリ）

管理者が組織で使う MCP サーバーを承認したい場合は、承認済みのカタログ、つまり **組織のプライベート MCP レジストリ** を公開できます。先に Tina 氏が説明した、プライベートな拡張機能マーケットプレースと似たものです。GitHub 側で構成すると、Visual Studio は、そのレジストリにある MCP サーバーだけを開発者が閲覧、インストール、実行できるようにします。

### 5.11 組織のノウハウの共有

経験豊富な開発者は、アーキテクチャ、テストの慣行、チームの規約を知っています。管理者は、これらを一元的に構成して組織全体に提供できます。手段は次の 2 つです。

- **カスタム指示**：チームの規約。
- **カスタムエージェント**：再利用できる専門家。

これは強制ではなく、開発者が使えるガイダンスだと説明されました。

### 6.1 プライベートマーケットプレースのデモ（Murphy 氏）

前提：Contoso という発行元の 3 つの社内拡張機能を載せたプライベートマーケットプレースを用意済み。エンドポイントはローカルで稼働している。

1. Visual Studio で「ツール」→「オプション」を開き、「プライベートマーケットプレース」を検索する。
2. 有効にして、エンドポイントを入力する。Visual Studio はエンドポイントを検証し、プライベートマーケットプレースから想定どおりのサービス構成が返らない場合は、先に進む前に直せるよう警告を出す。
3. Intune の構成が適用されている場合は、設定画面でチェックボックスがすでにオンになり、エンドポイントも入力済みで、読み取り専用になる、と説明された（このデモの画面で実際に見せたものではなく、口頭の説明）。
4. エンドポイントを構成した後、拡張機能マネージャーを開き直す。公開マーケットプレースの代わりに、プライベートマーケットプレースにある Contoso の 3 つの拡張機能だけが表示される。
5. プライベートマーケットプレースから直接来た拡張機能にはロックアイコンが付き、公開マーケットプレースにある評価やダウンロード数などの情報がない。

続けて、3 つの追加機能を説明しています。

6. **上流接続（アップストリーミング）**：プライベートマーケットプレースが、上流の公開マーケットプレースの拡張機能を代理で提供する。有効にすると、プライベートな Contoso の 3 つの拡張機能と公開マーケットプレースの拡張機能が並んで見え、開発者から見ると同じ体験になる。
7. **許可リスト**：発行元、拡張機能 ID、バージョンに基づくルールで、インストールを許可する拡張機能を管理者が定義する。デモでは Contoso の拡張機能だけを許可する設定にしてあり、ほかの拡張機能は表示されるが、Visual Studio がブロック済みと表示してインストールを防ぐ。マーケットプレースへのアクセスを奪わずに、利用を制御できる。
8. **Entra 認証**：まだリリースされておらず、プレビュー段階だが、もうすぐ提供される。管理者は Entra ID でプライベートマーケットプレースを保護でき、承認された開発者だけがアクセスできる。デモの説明では、認証なしでアクセスするとサインインにリダイレクトされ、Visual Studio が利用者の ID を使って、そのプライベートマーケットプレースのサーバーで承認を受ける。承認されると、これまでと同様に拡張機能が表示される。

### 6.2 管理設定のデモ（Praveen 氏）

GitHub.com で設定したものが、Visual Studio にどう反映されるかを見せました。

1. テスト用の GitHub 組織の管理者として、管理設定の構成ファイル（`manage settings.json` と聞き取れます。正確なファイル名は音声認識の都合で確定できません）を開く。
2. ファイルに、権限バイパスモードを無効にするキーが「無効」に設定されている。
3. このキーに対応した、Visual Studio の最新の Insiders 版を見る。
4. エージェントモードが対話モードで使え、ツールの権限は「手動」に設定されている。一方、「すべて許可」と「オートパイロット」は、このポリシーで無効になっている。開発者からエージェントを取り上げているのではなく、自律的な実行や通常の権限確認の省略を防いでいる、と説明された。

## 7. 注意点・発表者の気付き

- **完全レイアウトのサイズ**：最初のダウンロードが大きい。発表者のテストでは約 30 分、約 86 GB だった。
- **完全レイアウトを推奨する理由**：開発者がインターネットから直接インストールできない設定では、後から足りないパッケージが分かると困る。
- **標準ユーザーでも管理者権限は与えない**：与えるのは Visual Studio のインストールの制御で、マシンの管理者権限ではない。
- **提供状況の違い**：プライベートマーケットプレースはプレビュー、Entra 認証は未リリース（もうすぐ提供）。クールダウン、インストールのガバナンス、出所の確認、監査、実行時のガバナンス、管理設定の拡大、エンタープライズコネクタ、サンドボックス、GitHub 管理の BYOK は、これから取り組むものとして語られており、提供時期は発話では確認できません。
- **出所の確認の対象範囲**：当初は、VSIX として梱包され、マーケットプレースにホストされ、Visual Studio 経由でインストールされるものだけ。MSI や EXE は共通の検証方法を検討中。
- **カスタム指示とカスタムエージェントは強制ではない**：開発者向けのガイダンスである。
- **SSMS への適用**：内容の一部は今日使え、一部は検討中。足りない点は開発者コミュニティで伝えてほしい。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 承認済みファイル 1 式と、チームごとの構成ファイルで、チームごとに別の配布手順を保守せずに済む。
- 標準ユーザーに Visual Studio のインストールと更新を任せられるため、管理者パスワードの要求がサポートチームに集中しない。
- 更新は、レイアウトの差分だけをダウンロードして済む。
- プライベートマーケットプレースで、社内拡張機能と承認済みの公開拡張機能を同じ画面で提供でき、許可リストで利用を制御できる。
- 医療や銀行のような機微な業界でも、BYOK、組織ホストの推論、ローカル推論で AI を使う道がある。
- エージェントモード、プレビュー機能、MCP、権限バイパスを組織の準備状況に応じて個別に制限でき、モデルと MCP サーバーも承認済みのものだけに絞れる。
- 具体的な導入事例や数値の成果は、発表では語られていません。

## 9. まとめ

Visual Studio の組織展開は、完全レイアウト、標準ユーザー制御の許可、チームごとの `.vsconfig`、差分更新のサイクルで、管理者の負担を抑えながら開発者に自由度を残せます。拡張機能は、プレビュー中のプライベートマーケットプレースで見せるものを制御でき、インストールと実行の制御はこれからの取り組みです。AI は、経路の選択（GitHub Copilot、BYOK、組織ホスト、ローカル）、ガードレールの配布、エージェント機能の制限、モデルと MCP の統制で組織の方針に合わせられます。発表者は、アンケートと終了後の対話、Admin Champs call で、利用者の課題と意見を集めたいと呼びかけていました。終了後は、登壇者との対話や LinkedIn でのつながりも案内され、取り上げた話題の資料へのリンクもスライドに載せられていました。Praveen 氏は、新しい Visual Studio の Copilot 体験について、午後 5 時 5 分から Moscone South でライトニングトークを行うことも案内しています。
