## 3. 何に関する発表か

**Microsoft Copilot SDK とは**：Copilot のランタイム（エンジン）とハーネス（その上の標準構成）を、プログラムから使うためのインターフェースです。ランタイムは拡張しやすく、設定でき、さまざまな環境で動くよう設計されています。そのまま使える Microsoft Copilot ハーネスの構成も付いており、社内でベンチマーク、評価、品質改善を行っているものです。ローカルでもクラウドでも、両方の組み合わせでも動かせます。

**名称と経緯**：今年の Build で GitHub Copilot SDK として一般提供（GA）されました。先月、社内の組織、アプリ、プラットフォーム、サービスで広く採用されていることに合わせ、Microsoft Copilot SDK に名称が変更されたと説明されました。前日に Copilot SDK 2.0 の出荷が正式に発表されています。

**推論プロバイダー**：特定の 1 社に縛られず、Foundry の推論、GitHub Copilot が提供する GitHub の推論、他社の推論、ローカルモデルを使えます。

## 4. 発表者が伝えたいメッセージ

最も強調されたのは、エージェントのアーキテクチャは画一的ではなく、用途に応じて組み合わせるものだ、という点です。同じアプリの中でも、共有環境に多数のユーザーを載せる部分、隔離された環境で任意のコードを実行する部分、その間を動的に移動する部分が混在でき、登壇者はこれを「混在アーキテクチャ（mixed architecture）」と呼びました。エージェント自身にその配置の判断を任せることもでき、「エージェントはこれを効率よく使うことが驚くほど上手だ」と Steve は述べています。

もう 1 つは、既定の構成だけでも多くのことができる、という主張です。既定の Copilot ハーネスはコーディングエージェントの中核から来ており、デジタルな環境に置かれたコーディングエージェントは強力だと説明されました。一方で、ハーネスを一から作ることも可能です。

さらに、今後の方向として、ランタイムとハーネスが「デプロイの時代」に入ると述べました。ローカルで作ったものをクラウドに載せる道筋が、より整備されていくという意味です。

## 5. 発表内容の詳細

### 5.1 Copilot SDK 2.0 と共有マルチテナントアーキテクチャ

2.0 の追加機能のうち、まず取り上げられたのは**共有マルチテナントアーキテクチャ**です。従来は多数のユーザーを扱うにはランタイムのインスタンスを多数作る必要があり、提供コストが高くなっていました。新しい高密度ホスティングの選択肢では、1 つのランタイムインスタンスで多数のユーザーを同時に、低コストで、しかも安全に扱えます。

構成の選択肢は多く、詳細は午後 3 時からの別の発表（Patrick と Steve が登壇）で説明すると案内されました。この発表では高い視点から、選択肢と選ぶ理由を直感的に伝えるとのことです。

### 5.2 デモのシナリオとサンプル「Managed Copilot SDK」

シナリオは、ダウンヒルのマウンテンバイクゲーム「Downhill」です。GitHub のマスコットの Mona が自転車に乗っています。今回、キャラクターのカスタマイズやスキンを購入できるストアを新しく追加し、ゲームで初めて収益を得る、複雑なリリースを想定しています。

アーキテクチャの違いを見せるため、サンプル群「Managed Copilot SDK」が用意されています。通常の SDK とは別の、オープンソースのライブラリで、さまざまな構成でのデプロイ例を示します。そのまま使うことも、自分のエージェントに読ませて、自社製品に応用できる考え方を取り出させることもできると説明されました。

### 5.3 サポートエージェント：安全に作る

Steve はユーザーとしてゲームを操作し、ストアを開くために、アプリの機能フラグを切り替えました。ストアのボタンが出現します。

ユーザーとして「neon mona」のキャラクターをカートに入れ、「trail 15 を入力すると 15% 引き」という表示を見てコードを入力すると、「無効なコードです。サポートに連絡してください」というエラーになりました。そこでサポートに連絡すると、Copilot SDK で作られた AI サポートエージェントが応対します。ここで、ユーザーが「動かない、ひどい、今すぐ直して」と入力しました。

エージェントには次の 2 つのツールが与えられています。

- ユーザーのチェックアウトの状態（カートの中身、コードを使おうとしたこと、表示されたエラー）を読むツール
- 問題をエンジニアリングチームに報告するツール

このようなエージェントは Copilot SDK 1 でも作れたと Steve は述べ、新しいのは動かし方だと説明しました。信頼できないユーザーが多数アクセスし、互いのデータを見せず、サーバーに悪さをさせたくありません。従来はユーザーごとにコンテナで別のランタイムを動かす必要がありました。今回は共有マルチテナントの機能で、すべてのユーザーを 1 つのランタイムインスタンスに載せ、**起動が速く、安く、それでも安全**に動かしています。

コード例の説明は次のとおりです。

- セッションを作るときに、コンテキスト、プロンプト、使えるツールを設定する。
- チェックアウト取得のツール（get checkout という名前で、コード上部で定義）のハンドラーを自由に提供できる。
- ユーザー同士が干渉しないよう、**エージェントが「どのユーザーのチェックアウトか」を指定できないようにしてある**。現在のユーザーの分だけを取得するように固定（ハードコード）され、他のユーザーのデータを漏らせない「構造上の安全」になっている。
- Copilot のハーネスは、シェルコマンドの実行やファイルシステムへのアクセスなど強力な標準ツールを持つ。しかしこのユーザーたちには使わせたくないので、使えるツールを自分で定義したカスタムツールだけに制限している。

### 5.4 ヘルプデスクと負荷の模擬

Steve は、社内用のアプリ群のうち、サポートの依頼が届く Help Desk を開きました。実ユーザーはいないので、届いていたのは自分の 1 件です。依頼の内容、エージェントが行ったツール呼び出し、バグの報告の内容、エージェントが会話を解決済みと判断していることなどが見られます。

次に、25 人の顧客が同時にサポートへ依頼するという状況を模擬しました。エージェントは並列で動きますが、ランタイムのインスタンスは 1 つです。ユーザーごとのメモリ空間を別に確保せず、サンドボックスも 0 個ですが、公開したツールの設計により、構造上安全だと説明しました。

その中の 1 人、Matteo Rossi の依頼を開くと、同じ trail 15 のコードの問題でした。傾向が現れているのが分かります。Steve は、同じ問題を何度も診断、報告するのは大変であり、これはこの構成の弱点だと述べました。安全のためにセッション同士を分離しているので、互いの経験から学べないからです。

### 5.5 メモリ：サポートチームの知見をエージェントに返す

そこで使うのが、Copilot エージェントランタイムの組み込み機能である**メモリ**です。コーディングエージェントでの取り組みから派生したもので、よく調整されていると説明されました。

コードは単純で、セッションを定義するときにメモリを機能として有効にし、保存先を決めます。ディスク上のファイル、データベース、BLOB ストア、Cosmos など、保存のバックエンドは自由です。メモリを保存するタイミングはエージェントが判断します。さらに、機密情報（シークレット）を除去するリダクション機能と連携します。ユーザーのセッションにトークンのような機微な情報があっても、他のユーザーと共有されるメモリに保存されないようにするためです。

デモの手順は次のとおりです。

1. エージェントに「これは既知の問題で、本日修正される」と伝える。
2. この時点ではメモリに保存されない。より高性能なモデルなら自分で保存を判断するかもしれないが、今回使っているのは小さなモデルの Haiku であるため、明示的に「メモリとして保存して」と指示する。
3. エージェントがランタイム組み込みのメモリツールを使い、チームの知識ベースに追加するメモリを**提案**する。エージェントに勝手に保存させない設定にしてあり、機微な情報が入る可能性があるため、利用者が選べる形にしている。
4. 先ほどの模擬の間にも複数のメモリが集まっており、手動で指示した 1 件のほか、別の服の商品に問題があるとエージェントが判断して提案した 1 件もある。Steve は、どれも保存して知識ベースに追加することを承認した。
5. セッションと過去のデータを破棄し、同じテストデータで 25 人の模擬をやり直した。Matteo の依頼を開くと、今回は「あなたの操作に問題はなく、Web サイトのバグです」と答えた。既知の問題だと把握していて、選んで記録した別セッションの文脈を使えた。

Steve はこれを「自己改善するシステム」と呼んでいます。

### 5.6 複数の推論プロバイダーと構造化出力

推論は、Foundry、GitHub の推論バックエンド、OpenAI または Anthropic と互換性のあるエンドポイントのどれでも使えます。さらに、**複数を同時に使える**点が珍しい機能だと説明されました。モデルの入手先も種類も、1 つに限る必要がありません。

デモでは、25 件の未分類のサポート依頼をテーマごとに分類しました。

1. 最初は Claude Haiku を使い、直列（1 件ずつ）で分類する。
2. コードは、利用できるカテゴリの一覧を定義し、「このサポート依頼を分類して」というプロンプトと分類したいメッセージを送り、出力がそのカテゴリのどれかに限られるよう結び付ける。この機能は**構造化出力**と呼ばれる。
3. 結果は 25 件を **23 秒**、**約 23,000 トークン**で完了し、正しくグループ分けされていた。
4. 次に、Foundry の「判断モデル（decision model）」を使う（モデル名は「Ms. Decision One」と聞こえますが、音声認識の都合で表記が確定できません）。単一の答えを極めて速く、安く出すために設計された種類のモデルである。
5. 同じ分類を実行すると **2.2 秒**で完了し、トークンは約 4 分の 1 だった。

1 つのアプリの中で、種類の違うモデルを組み合わせられる、という結論です。

### 5.7 Data Desk：共有ランタイムからサンドボックスへの移行

次に、リリースの状況を経営層に説明するため、Data Desk というアプリを開きました。自然言語をクエリに変換して、データストアに実行する、よくある形のアプリです。「価値が高い上位 5 件」と尋ねると、クエリに変換され、結果が返りました。

このアプリも共有ランタイムで動いていて、起動が速く安価な代わりに制約があります。任意のコードの実行、ソフトウェアのインストール、シェルコマンドは、共有環境では危険なため使えません。ただし、プロモーションコードが拒否された件数を尋ねる程度の複数のクエリなら、共有ランタイムの中で処理できます。

「Python を実行できますか？ 使えるツールを箇条書きにしてください」と尋ねると、Bash も Python もなく、データを扱うツールだけだと答えました。共有環境では、何かを変更することも他のセッションの状態を読むこともできないため安全です。ただし、**sandbox を要求する（request sandbox）ツール**だけは持っており、より強力なツールが必要なセッションは、隔離された環境へ自分で移れます。

デモの手順は次のとおりです。

1. 「注文に対する拒否の件数を、時間経過のグラフにして、公開後に増えているか見たい」という趣旨で、拒否と注文の推移のグラフを依頼する。グラフ作成にはライブラリのインストールが必要なため、共有ランタイムではできない。
2. エージェントが「サンドボックスへ移動する」ツールを呼び出す。
3. 利用者が承認すると、**状態を失わずに**セッションが隔離環境へ移行する。コンテナの起動には **3 秒**かかった。ここではコンテナを使っているが、他の種類のサンドボックスも使える。
4. セッションは、シェルの実行やソフトウェアのインストールが自由にできる場所で継続し、Bash コマンドの実行とデータの集計をして、結果を出した。

Steve はグラフの意味を自分では分からないと述べ、ビジネスアナリストに確認する場面にしました。Patrick は「緊急にオンコールに連絡して修正を始めるべきだ」と判断しています。

### 5.8 Incident Commander：頭脳と手の分離

Steve は、自分がオンコールのエンジニアであり、デモの最中に対応したくないと述べました。人間がいつも対応できるとは限らず、夜中ならなおさらです。人間を起こす代わりに AI エージェントを起こして、まず対応を始めさせる、という考え方です。

そこで使うアプリが Incident Commander です。システムからテレメトリを受け取っています。Copilot ランタイムは OpenTelemetry のデータの公開に対応しており、任意の監視・アラートの仕組みに流せます。Web アプリケーションからの情報も流してあります。しきい値とトリガーで判断する通常の決定論的なコードで、AI ではないと説明されました。プロモーション付きのチェックアウトがすべて失敗したため、インシデントが発生しています。

これを使って、**頭脳と手の分離（brain hands split）**を紹介しました。ここ 1、2 か月で広まった考え方で、今後もよく聞くことになるだろう、と Steve は述べています。

| 用語 | 意味 |
| --- | --- |
| 頭脳（brain） | エージェントループ。文脈を保持し、推論バックエンドを呼び出して、会話や手順を組み立てる部分 |
| 手（hands） | エージェントが呼び出すツール。シェル、ファイルの読み取り、HTTP リクエストなど |

通常は頭脳と手が同じ場所で動きますが、分離できます。デモの構成は次のとおりです。

- 頭脳は、安価な共有ランタイムで動く。インスタンスを速く安く起動でき、データが次々に流れ込んでも、多数のサンドボックスの起動を待たずに済む。
- 頭脳は「調査が必要か」を安く判断し、必要なら、ツール呼び出しを始める。
- 共有ランタイムではツールを実行できないので、システムが**自動でサンドボックスを起動**し、ツール呼び出しをそこへ向ける。
- 調査用の作業領域でトリアージを行い、結果を頭脳に戻す。サンドボックスは破棄され、頭脳は作業を続ける。
- 必要なリソースを、エージェント自身が判断する。

実演として、チェックアウトで HTTP 500 エラーが出る別の障害を模擬しました。共有ランタイムでセッションがすぐ起動し、ツール呼び出しを始めたため、サンドボックスが配備され、作業が終わると自動で破棄される様子が見られました。

### 5.9 ソフトウェアファクトリー

これまでのアプリ（ゲーム、Help Desk、Data Desk、Incident Commander）は、ソフトウェアを修正する理由を提供します。そこで、サンプルにはソフトウェアファクトリーも含まれています。さまざまな入力を集めて組み合わせ、これまでのアーキテクチャを使って、**人間の介入なしに**構築、テスト、デプロイまでできる仕組みで、必要なら人間を承認に入れられるものです。Steve は、普段自分のマシンで行うエージェント型のソフトウェア開発を、イベントに反応してクラウドで自動的に行うものだと説明しました。

Incident Commander が、修正を求める依頼をソフトウェアファクトリーに送っていました。レポートには、壊れている箇所、根本原因の分析、修正の見当が含まれ、大文字・小文字の区別の問題だと推測されていました。パイプラインは次の流れです。

1. 最初に**計画エージェント**が受け取る。共有ランタイムで動くので運用が安い。対処できると判断すれば、次のエージェントを生成する。
2. **ビルドエージェント**。コードベースに対する指示とスキルを与えてあり、依存関係のインストール、テスト、コンパイラーの実行ができるよう、隔離されたコンテナで動く。
3. 完了すると、**レビューエージェント**と協力し、2 者が合意して準備完了とする。
4. 最後に**リリースエージェント**に届く。作業をまとめ、リリースの時期を判断する。

Patrick は、環境の配備、他のエージェントへの委任、他のコンテナの直接操作といった判断を、エージェントが自分で行っている（「完全にオーガニック」）点が重要だと補足しました。

**人間の承認**：本番に無監視でデプロイさせるのは避け、人間を入れる構成にしてあります（入れなくてもよい）。リリースエージェントはデプロイの認証情報を持たず、**デプロイを要求するツール**だけを持ちます。要求すると、UI に承認待ちの項目が表示されます。

コード例の説明は次のとおりです。

- Copilot SDK でセッションを作るとき、エージェントが何かの許可を求めたときのコールバックを定義できる。
- 多くの場合は、隔離されたコンテナで動いており安全なので、自動で承認する。
- 特別なのは、デプロイ要求のツールだけ。すぐには応答を返さず、人間が応答するまで非同期に待つ。
- 返信は速くなくてもよく、数日かかってもよい。その間はセッションを一時停止でき、コストはかからない。人間が承認したら、エージェントを再び起こして要求を完了させ、デプロイを行う。

### 5.10 AHP でエージェントに話しかける

Steve は、変更内容の確認をしたいと述べました。成果物や PR で差分を読む方法もありますが、エージェントに尋ねる方法もあります。クラウドで動くエージェントが、どこで何をしているのか分からず、話しかけられないのは困る、という懸念に対する答えが **AHP（Agent Host Protocol）**です。

AHP は、もともと VS Code チームから出てきた標準のプロトコルで、社内で使われており、Microsoft の多くのチームが採用しています。ネットワーク越しを含め、動作場所によらずエージェントに接続するための標準インターフェースです。AHP に対応した UI なら、どれでもエージェントの動作を見たり操作したりできます。すでに出荷された AHP クライアントとして、Copilot CLI、VS Code、GitHub Copilot アプリが挙げられました。Copilot SDK のサーバー側では、任意のセッションから AHP のエンドポイントを公開できます。

デモの手順は次のとおりです。

1. セッションの AHP エンドポイントを公開し、画面の「Copilot CLI を開く」ボタンから接続用の内容をコピーする。
2. ターミナルに貼り付ける。ただし、セキュリティ上、先にログインしていないと接続できないので、ログインしてから接続する。
3. 標準の Copilot CLI が、隔離されたコンテナ内のセッションに接続した。
4. 「どう直したか。5 語以内で答えて」と尋ねる。
5. 答えは「検索の前にコードを大文字にする」だった。Steve は、エンジニアとして納得でき、この内容でデプロイしてよいと判断した。
6. 待機中のデプロイ要求の承認画面に戻り、承認する。デプロイが行われた。

Patrick の確認に対し、Steve は、この接続は GitHub と標準のインフラに閉じるものではないと答えました。GitHub のログインで認証してもよいし、独自の認証方式でもよく、GitHub のサーバーを一切経由しなくてもよい、と述べています。

最後にデモのゲームで確認しました。ローカルで動いているコードが実際に変更されており、ストアで商品を選び、コードを小文字で入力しても、大文字のコードと正しく一致し、問題は解消しました。

## 6. デモ・手順

デモは Steve のマシンで、実施順に次のとおりです。画面の細部は音声から確認できる範囲に限っています。

1. ゲーム Downhill で、機能フラグを切り替えてストアのボタンを表示する。
2. ユーザーとして neon mona をカートに入れ、trail 15 のコードを入力して、エラーを確認する。
3. サポートエージェントに「今すぐ直して」と入力し、エージェントがチェックアウトの状態を読んで問題を報告するのを確認する。
4. Help Desk で依頼の詳細（ツール呼び出し、報告）を確認する。
5. 25 人の同時依頼を模擬し、Matteo Rossi の依頼で同じ問題を確認する。
6. 既知の問題としてメモリを保存させ、提案された複数のメモリを承認する。
7. 模擬をやり直し、Matteo の回答が改善されたことを確認する。
8. Claude Haiku で 25 件を直列に分類（23 秒、約 23,000 トークン）。続いて Foundry の判断モデルで分類（2.2 秒、トークンは約 4 分の 1）。
9. Data Desk で、上位 5 件の質問、拒否件数の質問、使えるツールの確認、グラフ作成の依頼を行い、セッションをコンテナへ移行する（起動は 3 秒）。
10. Incident Commander で、自動の起票を確認し、HTTP 500 の障害を模擬して、サンドボックスが起動、破棄されるのを見る。
11. ソフトウェアファクトリーで、計画、ビルド、レビュー、リリースの各エージェントの流れを確認し、デプロイ要求の承認待ちを確認する。
12. AHP で Copilot CLI を接続し、修正内容を質問する。
13. デプロイを承認し、ゲームで小文字のコードが使えることを確認する。

## 7. 注意点・発表者の気付き

- 共有ランタイムでは、エージェントが使うツールを自分で定義したものだけに制限します。標準ハーネスはシェルやファイルシステムへアクセスできる強力なツールを持つので、信頼できないユーザーには使わせません。
- ユーザーのデータを守るため、ツール側で対象ユーザーを固定し、エージェントに指定させません。「構造上の安全」という考え方です。
- メモリは、保存するかどうかをエージェントが判断します。デモで使った小さなモデルの Haiku は自分では保存せず、明示的な指示が必要でした（より強力なモデルなら自分で判断するかもしれない、と説明されています）。デモでは、機微な情報が入る恐れがあるため、エージェントが勝手に保存せず、提案を人間が承認する形にしています。
- 安全のためにセッションを分離する構成では、セッション同士が学習し合えません。この弱点を、メモリで補いました。
- 共有ランタイムでは、任意のコード実行、ソフトウェアのインストール、シェルコマンドができません。必要なセッションは、隔離環境へ移ります。
- 頭脳と手の分離は、ここ 1、2 か月で広まった考え方だと紹介されています。
- 人間の承認は、返信に数日かかってもよく、その間セッションを一時停止でき、コストはかからないと説明されています。
- AHP の接続は、先にログインが必要です（セキュリティを重視するため）。
- デモの内容はすべて Steve のマシン上でローカルに動いたものです。
- デモの Incident Commander の根本原因は、「大文字・小文字の区別の問題だと推測している」というエージェントの分析であり、最終的な修正は、検索前にコードを大文字にするというものでした。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 共有マルチテナントにより、多数のユーザーを 1 つのランタイムインスタンスで、低コストかつ起動が速く提供できる。
- ツールの設計で、ユーザー間のデータ漏えいを構造的に防げる。
- メモリにより、サポートチームの知見が、エージェントの回答の改善につながる。
- 複数の推論プロバイダーを併用でき、分類では判断モデルで **23 秒から 2.2 秒**、トークンは約 **4 分の 1** になった（デモでの値）。
- 共有環境から、状態を失わずに隔離環境へ移れる。
- インシデント対応やソフトウェアの修正を、人間の代わりにエージェントが先に動かせる。デプロイは人間の承認を挟める。
- AHP により、クラウドで動くエージェントに、Copilot CLI や VS Code などから接続して確認、操作できる。

顧客企業の導入事例や、本番での成果の数値は、発表では語られていません。

## 9. まとめ

Microsoft Copilot SDK 2.0 は、共有マルチテナントのランタイムを中心に、メモリ、複数の推論プロバイダー、サンドボックスへの動的な移行、頭脳と手の分離、人間の承認、AHP を使って、業務のエージェントをさまざまな構成で作れるようにします。

デモでは、Downhill のストア公開というシナリオで、サポート、分類、データ分析、障害対応、ソフトウェアの自動修正とデプロイまでを、1 つの流れで見せました。重要なのは、どの構成がよいかは用途で決まり、混在させられるという点です。詳しい選択の考え方は、同日午後の別セッションで扱われます。
