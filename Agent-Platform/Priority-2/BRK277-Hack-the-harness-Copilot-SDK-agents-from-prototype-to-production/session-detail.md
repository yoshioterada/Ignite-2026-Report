# BRK277 Hack the harness: Copilot SDK agents from prototype to production

## 1. はじめに

このセッションは、Microsoft Copilot SDK を使ってエージェントアプリケーションを作るとき、「どこで・どのようにエージェントを動かすか」という構成（アーキテクチャ）を、試作から本番運用へ成熟させていく流れで見せる発表です。題材は、社員が仕事に使う「スタッフアシスタント」という 1 つのアプリケーションです。

最初は全員が 1 つの共有環境で動く最小構成から始めます。そこでファイル漏えいの問題に突き当たり、次にセッションごとのコンテナー、必要になった時点でコンテナーへ昇格させる方式、コンテナーを使い捨てにする方式、複数のワーカーに仕事を任せる方式へと、5 段階で改善していきます。各段階はオープンソースのサンプルを切り替えながら、実際のアプリケーション画面で実演されます。

**結論として、Copilot SDK 2.0 の共有ランタイム（コンテナーの外でも動くランタイム）が、これらの構成をすべて可能にしている**というのが発表の主張です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK277](https://ignite.microsoft.com/en-US/sessions/BRK277)

## 5. 発表内容の詳細

### 5.1 Copilot SDK、ランタイム、ハーネス

発表者は技術を 3 つに分けて説明しています。

| 用語 | 説明 |
| --- | --- |
| SDK | Copilot のハーネスとランタイムへの、既定のプログラムからの入口です。ランタイムを変更・設定・拡張できます |
| ランタイム | Copilot ブランドの下にあるエージェント体験すべてを動かすエンジンです |
| ハーネス | ランタイムに組み込まれた既定の構成です。評価（エバリュエーション）やベンチマークの対象で、各事業領域で改善されています |

ランタイムを使うと、ハーネスを完全に取り除いて新しいハーネスを作り直し、幅広いエージェントアプリケーションを開発することもできます。可搬性があり自己完結しているため、ローカル、クラウド、その両方のどこでも動かせます。

Microsoft の製品群では、開発者向けサービスやツールへの統合のほか、インターネット接続のない政府向けの隔離クラウド（エアギャップ）や、企業のプライベート VNet でも使われていると説明されています。Microsoft や GitHub のアプリケーションがあってもなくても利用できます。

### 5.2 SDK 2.0 の目玉：マルチテナント対応

SDK 2.0 の重要な革新は、真のマルチテナントのサポートだと説明されています。エージェントをどこで動かし、どう統括（オーケストレーション）するかという選択肢が増えます。

1.0 では、分離されたコンテナーベースの技術だけに焦点を当てていました。構成が単純で安全に動かせ、クラウドでもローカルでも動くものの、時間がたつとコストと複雑さが増し、新しいアーキテクチャーが必要になりました。GitHub のサンドボックスや、「boundary-managed agents」と書き起こされたエージェント（音声認識の都合で正確な名称は確定できません）は、現状では分離コンテナーベースの構成だと述べています。

2.0 では初めて**共有ランタイム**を導入しました。ランタイムをコンテナーなしの共有プロセスとして、OS 上で安全に仮想化された環境で動かせます。さらに、状況やインフラの選択、性能とコストのトレードオフに応じて、ローカルでもクラウドでもサンドボックスを必要になったときに動的に起動できます。市場にあるどのエージェント製品も、いずれかの構成パターンに当てはまり、このランタイムはそのどれにも必要なオーケストレーションを支えられる、というのが発表者の説明です。

### 5.3 Managed Copilot SDK とスタッフアシスタント

デモには、GitHub で公開されているオープンソースのサンプル「Managed Copilot SDK」を使います。エージェントを異なる場所に配置し、場所の間で動的に移行できるようにするライブラリです。

従来の Copilot SDK では、Copilot クライアント（ランタイムの 1 インスタンス）を作り、その中でセッションを作成し、好きなモデルを設定して、プロンプトを送り、応答を受け取ります。Managed Copilot SDK でもこの使い方は変わらず、セッションの作成と操作はそのままで、**起動方法と実行場所の定義だけが異なります**。

題材は、社員が使う「スタッフアシスタント」です。要件は次のとおりです。

- 社員が仕事を進めるために使えること
- スクリプトの実行やファイルの操作を伴う高度な作業ができること
- 起動が非常に速いこと
- 運用コストが安いこと
- 安全であること

Steve は、これらすべてを最初から満たせるとは思っていない、まず試作を作って問題を見つけ、構成を成熟させていくと話しています。

### 5.4 段階 1：共有ランタイムでの試作

**構成**：すべての利用者のセッションが、同じ 1 つの共有ランタイム内で動きます。「Staff」という名前の共有環境を 1 つだけ設定しています。起動が速く（新しいインスタンスの起動待ちがなく）、利用者ごとのインスタンスのメモリーコストもかからず、最初のトークンが返るまでの時間が非常に短い構成です。一方で、安全に実行できる内容には制約があります。設定には、`unsafe host tools` を false にする項目があり、デモでは最初は false にしています。

**デモの流れは 6.1〜6.2 に詳しく書きました。** 要点は次のとおりです。

- 共有環境では、ファイルの転送、ディスクの読み書き、任意コードの実行のどれもできないため、スプレッドシートの質問は失敗します。
- `unsafe host tools` を true に変えると、ファイル処理もスクリプト実行もできるようになります。
- ただし、エージェントがサーバー上で任意のコードを実行でき、他の利用者のセッションのファイルまで読めてしまいます。

### 5.5 段階 2：セッションごとの分離コンテナー

解決策は、**セッションごとに専用のコンテナーを割り当てる**ことです。Managed Copilot SDK では、環境の実行場所を設定で切り替えるだけで済みます。ローカルで動かす場合は、ローカルにコンテナーが作られます。クラウドで動かす場合は、ACS サンドボックスなどの分離の仕組みになりうると説明されています。

コンテナーの中なら、エージェントは任意のコードを安全に実行でき、必要なソフトウェアのインストールもできます。セッションの実体（events.jsonl というイベントの記録など）もコンテナー内にあり、そこから推論基盤へ送る新しい要求が組み立てられます。

利用者が会話を終えても戻って再開できるよう、コンテナーは簡単には捨てられません。結果として、**利用量とコストが比例して増え、コンテナーは増える一方**になります。二人のやり取りの中で、「共有ランタイムから始め、ファイルシステムへのアクセスを与えたことで、本来境界内に留めたかった利用者間でデータが漏れる状態になった。次はコンテナーという環境の上に環境を重ねたので、費用が心配だ」と課題が整理されています（発話から、どちらの発言かは確定できません）。

### 5.6 共有ランタイムが効率的な理由（Rust への書き換え）

共有ランタイムがなぜ効率的なのかを、Steve が説明しています。6 か月前まで、各コーディングエージェント製品が使い、SDK 経由でも提供されている Copilot ランタイムは、TypeScript で書かれ、Node の上で動いていました。機能が豊富でベンチマークの成績も業界最高水準でしたが、起動に最大で約 5 秒かかり、実行中のセッションがメモリーを多く消費する点で運用コストが高いものでした。

そこで、エージェントを使って約 200 万行のコードを Rust に変換しました。結果は次のとおりです。

| 項目 | 結果 |
| --- | --- |
| 起動時間 | 約 2 桁短縮し、自分のアプリケーションにプロセス内で組み込む場合は約 50 ミリ秒 |
| メモリー使用量 | 約 10〜11 分の 1 |
| スループット | 大幅に向上 |

共有ランタイムは、サポートされる 6 つの言語のどれからでもプロセス内で動かせます。発話では TypeScript、Go、C#、Java、Rust が挙がり、最後の 1 つは「Ithon」と書き起こされています（音声認識の都合で表記が確定できません）。

### 5.7 段階 3：昇格可能（promotable）な構成

観察として、**すべてのセッションにコンテナーが必要なわけではない**という点が挙げられます。デモでは、エージェント Bob と雑談しただけで、コンテナーが 2 つ目に増えました（Bob は、プログラマーなのに警官の服装をしていると冗談の種にされています）。ツールを使わず文脈だけで答える会話にも、コンテナーが作られていたことになります。

そこで、昇格可能な構成にします。セッションは共有ランタイムで速く安く始まり、シェルやファイルシステムのような危険なツールは使えません。利用者がそれらを必要とする依頼をしたときに、システムがセッションを自動でサンドボックスへ**昇格**します。セッションの内容は引き継がれます。Managed Copilot SDK には、環境を別の環境へ変換する API があり、ツール呼び出しを始めた時点で自動昇格するよう設定します。

ただし、この構成では問題を先送りしただけだと Steve は認めています。利用者は会話を削除しないので、いずれコンテナーは増え続けます。増える速度が遅くなるだけです。Patrick は、この構成は「ちょっとした質問」を速く返すのに向いており、必要な場合だけサンドボックスに上げることで複雑さを先送りできる、と補足しています。

### 5.8 段階 4：頭脳と手足の分離（direct drive）

次の構成は、「brain-hand split（頭脳と手足の分離）」または direct drive などと呼ばれます。呼び名は重要ではなく、要点は**エージェントのループが動く場所と、ツール呼び出しが動く場所を分ける**ことです。

従来は、状態を保持し、推論を呼び出し、ツール呼び出しのタイミングを決める「頭脳」と、ツールを実行する「手足」が同じ場所で動いていました。この構成では、セッションを共有ランタイムで速く安く起動し、そこには頭脳だけを置きます。外の世界に対して何かをしようとした時点でコンテナーを起動し、ツール呼び出しだけをその中で実行します。**セッション自体はコンテナーへ移しません**。ツール呼び出しの結果を受け取れば、コンテナーを破棄して続行できます。必要になれば、また別のコンテナーを作ります。

コード上は、セッションを「オーケストレーター」として設定します。オーケストレーターは他のエージェント環境を生成でき、ここでは分離コンテナーであるサンドボックス型を生成する設定にし、ツール呼び出しをそのサンドボックスへ向けるよう指定します。

### 5.9 段階 5：委任（delegation）

利用者に力を与えるほど、さらに多くを求めるようになります。夜間のジョブ、高負荷の計算の並列実行など、1 つのサンドボックスでは足りなくなる、というのが発表者の見方です。この問題に対する構成が委任です。

オーケストレーターのセッションを共有ランタイムで動かし（起動が安い）、複雑な作業が必要になったとき、エージェントにワーカーを好きなだけ生成するツールを与えます。ワーカーはそれぞれ**独立したエージェント**で、自分で判断し、自分でツールを呼び出します。調整役とワーカーは互いに会話して作業を分担し、調整役は必要な資源の量や、後片付けのタイミングも決められます。

コード上は、直接のツール実行ではなく、生成するワーカーが完全なエージェントとして動く設定です。Staff（スタッフ）とサンドボックスのワーカーを関連づけています。

### 5.10 実運用での位置づけと混合構成

Patrick は、これらの構成が Microsoft 社内の製品にも見られると述べています。

- GitHub、Foundry、Azure、M365 などの各製品が、この道のりと同じパターンをたどっている
- Cowork は、現在、昇格可能な構成を使っている。最初のトークンが速く、複雑な計算も扱える
- 社内の複数のチームが、委任と頭脳・手足の分離を組み合わせた構成へ移行しつつある
- GitHub のソフトウェアファクトリーは、自分でオーケストレーションし、環境を生成し、コンテナーを直接動かし、他のシステムから文脈を取り込む

Steve は、この 5 つに限らず、**エージェントに実行時に必要な資源の種類を決めさせる混合構成**へ一般化できると述べています。利用者がタスクを割り当てると、エージェントが適した構成を判断し、その状況に合わせた環境を生成します。

### 5.11 そのほかの要点：推論基盤、ローカル実行、Aspire

- 共有ランタイムを含むマルチテナントのランタイム（発話では「Shipton 2.0」と書き起こされ、音声認識の都合で表記が確定できません）が、6 つの構成すべてを可能にしていると述べています。数か月前まではコンテナーに閉じ込められていた状態でした。
- 推論は Foundry の推論を使っていますが、GitHub Copilot の推論や、コストと性能を最適化する別のモデルも接続できます。
- 別のブレークアウト（番号は聞き取れません）では、従来の LLM と新しい分類モデルを比べる判断モデルを紹介しており、分類モデルを使うだけで 5〜6 倍の高速化が見られたと述べています。
- これらのモデルをローカルの開発ループで動かせるのは、Aspire（分散システムをローカルとクラウドで動かすためにモデル化できる技術）のおかげだと説明しています。
- 今回のデモはすべて、Aspire のデプロイコマンド 1 つで Azure にデプロイできます。Docker ではなく、Azure Container Apps などで複雑なオーケストレーターをクラウドで動かせます。
- Copilot SDK は多くのプラットフォーム、アプリ、サービスの中核にあり、各チームはドメインに特化したカスタムツール、スキルプロバイダー、メモリーシステムを結びつけています。すべてのサンプルは、GitHub Copilot コーディングエージェントを原型とする同じハーネスを共有しています。

## 6. デモ・手順

デモは、Managed Copilot SDK のサンプルアプリケーションを段階ごとに切り替えて行われました。アプリケーションの画面には、一般的なチャット画面と、Steve が作った「3D ワールド」風の画面があり、後者ではキャラクターに話しかけてエージェントと会話します（Dave、Carol、Bob、Alice の名前が使われています）。内部の SDK とプロンプトはどちらも同じです。画面の細部は音声からは確認できません。

### 6.1 段階 1：共有環境（`unsafe host tools` が false）

1. ログインし、チャット画面で「オフィスはどこにあるか」と聞く。データがプロンプトに入っているため回答できる。
2. 3D 画面で、スタッフに話しかけて「オフィスをアルファベット順に挙げて」と頼む。
3. 会議の見込み客データ「conference leads」のスプレッドシートを画面に取り込み、Dave に「このファイルに何が入っているか」と聞く。
4. 共有環境にはサンドボックスのファイルや成果物がないため、分離環境を使うよう求めるエラーが出る。ファイルは転送できない。
5. Dave に簡単な Python のあいさつ（hello）スクリプトの実行を頼むと、コードを実行する手段がないという返答になる。プロンプトでそう指示したのではなく、システム上、ディスクの読み書きや任意のコード実行ができないため。

### 6.2 段階 1 の回避策：`unsafe host tools` を true にする

1. `unsafe host tools` の設定を true に変え、アプリを停止して再起動する。
2. 同じファイルを Carol に渡し、「このファイルの内容は何か、行数を数えて」と頼む。
3. 共有環境のまま、シェルコマンドの実行、スキルの読み込み、Python の処理が動き、回答が返る。
4. 「最初の 5 行だけの新しいスプレッドシートを作って」と頼むと、新しいファイルができる。ダウンロードして Excel で開くと、5 行が入っている。
5. アーキテクチャーの図で、アプリケーションの各エージェントが共有ランタイム内で動いていることを示す。Steve は、このオプションの意味はよく分かっていないが、出荷してもよいだろうと冗談を述べ、Patrick が複数利用者の場合を問う。
6. 利用者 Patrick としてログインし、新しい会話で「このディレクトリにあるセッションは何か」と聞く。他の利用者のセッションが見える。他人のデータを変更したり、ファイルをダウンロードしたりすることも可能だと説明される。試作には良いが、本番には向かない。

### 6.3 段階 2：セッションごとの分離コンテナー

1. 設定の環境を、スタッフが分離環境で動く版に切り替え、停止して再起動する。
2. Docker Desktop を開く。動いているコンテナーは Managed Copilot の中継用の 1 つだけ（セッションごとではなく、内部実装の詳細）。
3. 3D 画面で Dave に短くあいさつする。この 1 語で新しいセッションが作られ、サンドボックスのコンテナーが作られる。
4. スプレッドシートを Dave に渡し、行数を聞く。回答は 1 万行。
5. コンテナー内のワークスペースを調べ、conference leads ファイルが転送されていることを確認する。
6. コンテナー内の Managed Copilot、ランタイム、セッション状態のパスをたどり、セッションの実体を確認する。events.jsonl に、セッション内で起きたイベントが蓄積されている。

### 6.4 段階 3：昇格可能な構成

1. コストの推移を示す図（利用量とコストの単純な比例関係）で、コンテナーが増え続けることを確認する。
2. Bob に話しかけると、ツールを使っていないのにコンテナーが 2 つになる。
3. 環境が 2 つある版に切り替える。Staff は昇格可能に設定され、サンドボックスへ昇格できる。ツール呼び出しを始めた時点で自動昇格するよう設定されている。
4. アプリを再起動し、以前のサンドボックスを削除してから、Carol に話しかける。サンドボックスは作られない。別のキャラクターにも話しかけ、「オフィスはどこか」と聞く。文脈から直接答え、やはりサンドボックスは作られない。
5. ファイルを渡して「最初の行は何か」と聞く。アップロードとツール呼び出しが始まった時点で、セッションが自動でコンテナーへ昇格する。サンドボックスが作られ、中にスプレッドシートがあり、ランタイムもコンテナー内にある。
6. 会話を削除するとサンドボックスは消えるが、利用者は通常削除しないため、コンテナーは増え続けると説明する。

### 6.5 段階 4：頭脳と手足の分離

1. コードを示す。セッションがオーケストレーターで、サンドボックス型のインスタンスを生成でき、ツール呼び出しをそこへ向ける設定になっている。
2. コンテナーが動いていないことを確認する。Alice にあいさつしても、コンテナーは作られない。
3. 同じ行数を数える作業を頼むと、ツール呼び出しが必要になりサンドボックスが作られる。中にはアップロードされた conference leads があるが、ランタイムのディレクトリは空で、コンテナー内にランタイムはない。
4. セッションの実行中に、サンドボックスを手動で削除する。会話に戻って「本当ですか」と聞くと、セッションは文脈を失わず継続する。ツール呼び出しをやり直し、新しいサンドボックスを自動で作り直す。

### 6.6 段階 5：委任（部分的にしか成功していません）

1. コードを示す。オーケストレーターが、完全なエージェントであるワーカー（Staff に結びついたサンドボックスのワーカー）を必要なだけ作る設定になっている。
2. 古い状態を削除し、複数のファイルを画面に取り込んで、「並列のサンドボックスを使って、これらのファイルの行数を数えて」と頼む。
3. 最初の試みはうまくいかない。Steve は、前のデモの状態が残っているためだと述べ、別のキャラクターに話しかけ直す。
4. ワーカーを起動できないエラーが出て、再起動する。再度の試行では、ワーカーが 1 つだけ起動する。エージェントはワーカー起動のツールでサンドボックスを作り、ファイルをコピーして作業を行った。
5. 「終わったので片付けて」と伝えると、エージェント自身がワーカーのサンドボックスを破棄する。

> 注意：このデモは想定どおりには動いていません。Steve は、本来なら約 5 つのコンテナーが生成され、ファイルが分配されて並列に処理される様子が見えるはずだったと説明しています。並列に複数のワーカーが動く様子は、このセッションでは確認されていません。原因について、Steve は「デモのやり方を正しく行わなかった」と述べています。

## 7. 注意点・発表者の気付き

- **共有環境で `unsafe host tools` を true にしない。** 発表では、エージェントがサーバー上の任意のコードを実行でき、他の利用者のセッションのファイルを読み、変更し、ダウンロードできる状態になると実演されました。試作には使えても、デプロイには向きません。
- **セッションごとのコンテナーは、コストが利用量に比例して増え続ける。** 利用者が会話を再開できるようコンテナーを残す必要があるためです。
- **昇格可能な構成でも、コンテナーは増え続ける。** 増え方が遅くなるだけで、問題は先送りされていると、発表者自身が述べています。
- **利用者は与えられた力に応じてさらに多くを求める。** 夜間ジョブや並列の高負荷計算など、単一のサンドボックスでは足りない要望が出てくると述べています。
- 発表者は、構成の説明が多く、一度で理解するのは難しいかもしれないと断ったうえで、デモで補うと話しています。
- Managed Copilot SDK は、**そのまま使う製品ではなく、考え方を取り出すための大規模な代表サンプル**として共有されていると説明されています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **コストと速度**：共有ランタイムを使うと、利用者ごとのインスタンスの起動待ちやメモリーコストがなく、最初のトークンまでの時間が短くなります。Rust への書き換えにより、プロセス内での起動は約 50 ミリ秒、メモリー使用量は約 10〜11 分の 1 になったと説明されています。
- **安全性とコストの両立**：昇格可能な構成や、頭脳と手足を分ける構成を使うと、必要なときだけサンドボックスを使い、不要になれば破棄できます。サンドボックスの数に上限を設けることも、資源が逼迫したときに破棄することもできます。
- **実行場所の自由**：ローカル、クラウド、エアギャップの政府クラウド、プライベート VNet のどこでも動き、Microsoft や GitHub のアプリケーションがなくても使えます。
- **推論基盤の自由**：Foundry、GitHub Copilot、ローカルモデル、サードパーティーのプロバイダーなど、標準的な仕様に対応する推論を使えます。
- **配置の容易さ**：Aspire のデプロイコマンド 1 つで、デモの構成を Azure（例：Azure Container Apps）へデプロイできます。
- **多言語対応**：6 つの対応言語のどれからでも、ランタイムをプロセス内で動かせます。

発表では、顧客企業の導入事例や、具体的な導入効果の数値は紹介されていません。

## 9. まとめ

Copilot SDK 2.0（旧 GitHub Copilot SDK）の共有ランタイムは、コンテナーの外でも動き、必要なときだけサンドボックスを使えます。このセッションでは、スタッフアシスタントを題材に、共有ランタイム、セッションごとのコンテナー、昇格可能な構成、頭脳と手足の分離、委任と、構成を進化させる流れが実演されました。

最初の共有ランタイムは速くて安い代わりに、安全でない設定で動かすと他の利用者のデータが見えてしまいます。コンテナーで分離するとコストが増え続け、昇格可能な構成はその増加を遅らせるだけでした。頭脳と手足を分け、コンテナーを使い捨てにすることで、状態を失わずにコストの上限を管理できます。さらに委任では、エージェント自身が複数のワーカーを作って作業を分担します。ただし、委任のデモはワーカーが 1 つしか起動せず、並列実行までは確認できませんでした。

次の一歩として、Managed Copilot SDK（GitHub 上のオープンソース）を試すこと、GitHub Copilot のサンドボックスや Foundry の管理されたエージェントホストといった既存の選択肢を確認することが紹介されています。これらの構成を支える、今後提供予定の「整備された道筋」が追加されるとも述べていますが、時期や内容は発話では確認できません。
