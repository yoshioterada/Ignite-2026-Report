## 4. 発表者が伝えたいメッセージ

Mario 氏は、GitHub は最初から開発者のための共同作業の場であり、今後は人間とエージェントの協働に合わせて進化が必要だと述べました。その際に目指すものは、時間の節約だけではないといいます。誰にも「仕事が尽きる」ことはなく、24 時間は変わらないので、節約した時間そのものに意味はないという考えです。バグを直す、機能を出す、PR をレビューしてマージする、パフォーマンス問題を解決する、.NET や Java の移行を終える。こうした**ソフトウェアの仕事を完了させること**に注力すべきだとしています。

「開発者を置き換える」という主張には強く反対しており、GitHub は開発者とともに価値を作るためにある、という立場です。また、デモが本番に出ないまま終わること、PR の本数を競うことも目標ではないと明言しました。

Tim 氏のデモも同じ考えに沿っています。トークンを多く使うためでも、コードや PR の滞留を増やすためでもなく、完了した仕事につなげる機能に絞って紹介する、という前置きがありました。

## 5. 発表内容の詳細

### 5.1 GitHub の原点と、価値の単位

Mario 氏は 2008 年の GitHub のトップページ（「GitHub Social Coding」の見出しと、ユーザーとリポジトリの表示）を見せ、GitHub の中心は昔から開発者であり、コラボレーションの会社だと説明しました。開発者にはプロダクトマネージャーやテスターも含まれるという補足がありました。

2021 年に最初の AI アシスタントである Copilot を作り、当時は Codex という GPT-3 ベースのモデルを使っていたと振り返っています。いまは人間とエージェントのコラボレーションに変わっており、プラットフォーム側にも利用者側にも進化が必要だという流れです。

### 5.2 新しい GitHub フロー

従来の GitHub フローは、ブランチを作り、コミットを重ね、PR を作り、フィードバックを受けてメインにマージする流れでした。これからは、ユーザーの意図、コード変更、プロダクトのシグナルなど、反応すべきものを起点にします。シグナルは計画から始まることもあれば、そのままビルド、検証、観測に直接入ることもあるため、ループというより「完了させる」を中心にした流れだと Mario 氏は説明しました。

中心にあるのは知能の層（インテリジェンスレイヤー）で、ソフトウェアの仕事を完了させる過程で出る「排出物」を集めて次の実行を良くしていく、いわば学習する仕組みだと述べています。Satya 氏や Judson 氏も語った「人間の志（Human ambition）、知能（Intelligence）、信頼（Trust）」という枠組みに結び付けた説明です。

### 5.3 プラットフォームの柱

Mario 氏は、バージョン管理や Issue、PR だけでは足りないとして、次の要素を挙げました。

| 要素 | 説明 |
| --- | --- |
| 協働のための画面 | 開発者とエージェントが一緒に作業する場 |
| ランタイム | エージェントが安全に、機械の速度で実行できる実行基盤 |
| エージェントネットワーク | 常時稼働して見守り、次の作業を先回りして提案する |
| 品質とセキュリティ | エンジニアリングの水準を維持する |
| コンテキスト層 | 知能が積み重なっていく層 |
| エンタープライズの信頼 | 企業が安心して使えること |

これらを GitHub プラットフォームの柱とし、まとめて「エージェントネイティブなエンジニアリングシステム」と呼んでいます。

### 5.4 Universe での発表と Git レイヤーの拡張

2 週間前の GitHub Universe では多くの発表があった、と Mario 氏は述べています。GitHub は自前のデータセンターから Azure に移行し、100 倍、1,000 倍の規模に備えているところです。エージェントによる利用の伸び（プロダクトマーケットフィット）は極めて大きく、責任も大きいと語りました。

他のバージョン管理システムを持ち出す声がある中で、GitHub の立場は、**Git は十分によいバージョン管理システム兼プロトコルであり、新しい時代に向けて拡張する**というものです。示された数値は次のとおりです。

- メインへの書き込み：毎秒 7,200 回
- 同時エージェントセッション：5,000
- 現状比のスループット：180 倍

現時点でここまでの規模のエージェント群を動かしている利用者は多くないものの、目標は 100 倍、いずれは 1,000 倍だと述べています。

もう 1 つの証拠として、OpenClaw で観測した 24 時間分の負荷を 1 分に圧縮して流した比較が示されました。従来のアーキテクチャでは OpenClaw のチームにタイムアウトが発生しましたが、新しいアーキテクチャではゼロだった、という説明です。

### 5.5 Copilot app と Copilot Fusion

GitHub の戦略は、マルチモデル、マルチサーフェス、マルチエージェントです。サーフェスの 1 つが Copilot app で、夏に GA（一般提供）となり、顧客の間で急速に伸びていると述べました。Agentic Development Environments（ADE、エージェント開発環境）と呼ばれる種類の画面で、同時並行で多くの作業を進めつつ品質を保つことが狙いです。コネクター、ローカルとクラウドのセッション、サンドボックス、プロジェクトがまわりを固めています。

**Copilot Fusion** は、合成モデルのようなものだが、モデル以上のものだと紹介されました。意図を理解するルーティング層と、適切なタスクを適切なタイミングで適切なモデルに渡すオーケストレーション層を持ちます。Ignite 参加者向けの提供として、Copilot Fusion が 11 月 30 日まで 30% 割引になることも案内されました。

ベンチマークについては、当日の太平洋時間 9 時 30 分に Satya 氏が発表したとして、Terminal-Bench 4.1 でトップになったと説明しています。比較対象として Opus-5.5 Max、Fable-5.2 Max、Astra Max が挙がり、いずれも上回ったとのことです。さらに、Opus-5.5 と比べて約半分のコストで達成したと述べました（モデル名は音声から聞き取った綴りで、音声認識の都合で表記が確定できません）。Mario 氏はここから、ハーネスとランタイムでのオーケストレーションが重要であり、モデルとハーネスが常にセットである必要はない、と主張しました。

### 5.6 Azure DevOps リポジトリとの連携

Mario 氏は Azure DevOps を使っている人が多いことを確認したうえで、Copilot app の canvas（キャンバス）を使った連携を見せました。canvas は双方向で、そこに置いたものとエージェントが互いにやり取りできると説明されています。Azure DevOps にホストされたリポジトリにそのまま接続でき、PR を Azure DevOps に作成して canvas 上で確認し、Issue を閉じるなどの作業も Copilot app から対話的にできるとのことです。GitHub のリポジトリだけでなく、多くのバージョン管理システムで同様に使えるという趣旨でした。

### 5.7 Tim Rogers 氏のデモ：Copilot app

Tim 氏は、ここ数か月で自分の働き方を変えた 4 つを見せると宣言しました。Copilot app、Teams と Slack との連携、Copilot automations、Agent Merge と Copilot Code Review の改善です。デモ用に Fourth Coffee というコーヒーショップのアプリを使いました。

マルチサーフェスの意味として、Copilot は VS Code、Visual Studio、JetBrains、Vim、Eclipse、Xcode など、ほぼあらゆる IDE と、ターミナル向けの Copilot CLI にあると説明しました。最近は IDE や CLI から Copilot app へ移る動きがあり、同アプリは 5 月に公開され、Windows、Mac、Linux で使えます。開発者だけでなく、GitHub 社内ではプロダクトマネージャー、デザイナー、弁護士、アカウントマネージャーも使っているそうです。

### 5.8 Copilot Fusion のコスト比較（Mario 氏のデモと Tim 氏のデモ）

Mario 氏のデモでは、コーヒーアプリにギフトカード購入機能を追加する同じ依頼を、Astra、Opus、Fusion High に出して消費クレジットを比べました。1 クレジットは 1 セントです。

| 依頼 | モデル | 消費クレジット（発話どおり） |
| --- | --- | --- |
| ギフトカード購入の追加 | Astra | 約 1,000 |
| 同上 | Opus | 631 と聞こえます（音声認識の都合で確定できません） |
| 同上 | Fusion High | 147 |
| ルービックキューブの解法 | Astra | 166 から 271 に増加（100 強） |
| 同上 | Opus | 約 78 |
| 同上 | Fusion | 52 |

Mario 氏は、通常はおよそ半分のコストになると述べ、複数の問題を並列で解く組織では効果が積み上がると説明しました。

Tim 氏も「営業中（Open Now）フィルターの追加」で比較しました。Claude Opus 5.5 は 132 AI クレジット（約 1.30 ドル）、Fusion は 42 セントで、3 分の 1 未満のコストで同じ結果が得られたとのことです。

### 5.9 Tim 氏のデモ：並列実行、カスタマイズ、プロジェクト

Tim 氏は Fourth Coffee の店舗検索（地図も経路案内もない状態）を改善する作業を使いました。

- 左側にリポジトリ一覧とセッション（エージェントとのスレッド）が並びます。
- 「各店舗に経路案内ボタンを追加」と「営業中フィルターを追加」を、どちらも Fusion で同時に実行しました。
- 同じリポジトリで複数のエージェントを走らせられるのは、各実行が独立した Git ワークツリーを持つためで、テスト実行や PR 作成も互いに干渉しないと説明しています。

**Customize タブ**は、Copilot に必要なコンテキストと知識を設定する場所です。マーケットプレイスがあり、Canva や Figma などへの接続を追加できます。コネクターは数クリックで入れられ、Copilot app、VS Code、Copilot CLI、クラウドのセッションで使えます。

**プロジェクト**は、他のエージェントセッションを管理する「親分」のようなセッションと位置付けられています。1 本の PR に 1 つのエージェントという使い方は、大きな作業では管理しにくくなるためです。

### 5.10 Teams と Slack との連携

Teams のチャットで GitHub を @メンションし、Issue の作成、コードへの質問、機能実装やバグ修正の依頼ができます。実行は会議中にバックグラウンドで進み、会議の参加者全員が見え、途中で方向を修正することもできます。Slack でも同じことができます。Tim 氏は、会話の中で見つかった小さなバグや改善案が忘れられがちだとして、それを取りこぼさず出荷につなげるのがねらいだと語りました。

### 5.11 Copilot automations

automations は、毎回プロンプトを入力しなくても自動で動くエージェントです。GitHub 上のリポジトリの Agents タブと、Copilot app の Automations タブから管理します。作成時に、プロンプト、許可するツール、トリガーを決めます。トリガーの例は、毎朝 6 時、バグ Issue の作成時、PR がレビュー可能になった時です。クラウドで動くため、ノート PC のバッテリー切れや休暇中でも動作します。同じ仕組みは、セキュリティアラート、パッケージのアップグレード、バックログにある小さな顧客要望の処理にも使えると例示されました。社内では PR 検証の automation の実行が直近 18 分で 5 回あった、とも紹介されています。

### 5.12 Copilot Code Review と Agent Merge

2026 年は「レビューが新しいボトルネック」だと言われているとして、システム思考ではボトルネックを改善すべきだと Tim 氏は述べました。Copilot Code Review は数年前からあり、GitHub 社内では全 PR に自動レビューが付くようになっています。7 月に **effort level**（努力レベル、レビューの深さの指定）が導入され、Universe で最も深い Max が加わりました。Max は複数のモデルを使います。

**Agent Merge** は、PR をマージ可能にし、その状態を保つ機能です。PR のマージ欄にある「Watch and Fix」で有効にし、失敗した Actions ワークフローの修正やマージ競合の解決を任せます。社内で試験中のものとして、Copilot のコードレビュー指摘を Copilot が修正する選択肢もありました。

### 5.13 質疑応答

**Bitbucket でも Copilot app は使えるか。** 使えますが、PR 連携は得られません（Azure DevOps には現在あります）。他の機能はバージョン管理システムを問わず動作します。automations は GitHub 上ではなく、ローカルで実行する形になります。

**仕様駆動開発はどうなるか。** 今回は扱いませんでしたが期待している分野です。形式的証明（形式検証）という方法と、要件収集から仕様記述、エージェントまでの流れがあります。新しく、仕様を統合した「証明駆動開発（PDD）」を発表し、仕様キットも発展させていくと答えました。

**エージェントが大量の証拠を作るとレビューが追いつかない。** GitHub の Issue に Artifacts（成果物の添付）機能が入ったところで、PR にも導入する予定です。変更に付いて回る証拠の連鎖として使えます。Tim 氏は、コメントに積み上げず、整理する場所が必要だと補足し、多くのチームでコードを見る時間が減り、証拠を見る時間が増えていると述べました。

**VS Code と専用クライアントのどちらを使うか。** サーフェスは用途で使い分けます。完全にエージェント中心で進めたいなら Copilot app、IDE が好きなら VS Code が適しています。Copilot app でコードを編集するのは本来の用途ではないと述べ、上部にコードを開く入口があるとのことです。

## 6. デモ・手順

デモは 2 回あり、いずれも画面共有で実演されました。画面の細部は音声からは確認できません。

### 6.1 Copilot Fusion と Azure DevOps 連携（Mario 氏）

1. Terminal-Bench 4.1 の結果画面を示す。
2. コーヒーアプリを表示し、ギフトカードがないことを指摘する。
3. Copilot app でプロジェクトとリポジトリを開き、Astra に「ギフトカード購入機能を追加」と依頼する。
4. Opus、Fusion High でも同じ依頼を実行し、消費クレジットを比較する。
5. ルービックキューブを作り、Astra、Opus、Fusion の順に解かせてクレジットを比べる。
6. 販売する商品を並べた Contoso Catalog というアプリを表示し、Azure DevOps ホストのリポジトリを canvas で開き、「より祝祭らしいバリエーション」を依頼し、PR を作成して canvas 上で確認する。

### 6.2 4 つの機能のデモ（Tim 氏）

1. Copilot app で 2 つの依頼を Fusion で並列実行する。
2. Open Now の結果を Opus と Fusion で比較する。
3. Customize タブで Work IQ コネクターを検索し、Connect を押して Microsoft アカウントを選ぶ。2 クリックで接続でき、MCP サーバー設定のコピーやパッケージのダウンロードは不要だった。接続後、先に作成したセッションで「土曜日のプロジェクト計画会議で何を決めたか」と質問し、チームの会議メモから答えが返った。
4. プロジェクト機能の例として、Fourth Coffee の Web サイトの再設計を見せる。まずひな形を作って PR を出し、続けて 10 ページを 10 セッションで並列に移行した。合計 11 セッションで、巨大な 1 本ではなく 10 本の PR になった。
5. 追加で「前後のスクリーンショット」を頼むと、プロジェクトが 10 のエージェントに聞いて集め、ライブラリに保存した。スライダーで前後を比較できた。
6. Teams 連携は録画動画で示した。@GitHub に「各カフェのページに近隣カフェの欄を追加する Issue を作成」と依頼している。
7. automations の例 1（PR の検証）：GitHub UI リポジトリで実際に動いている自動化を見せた。PR が開かれたときに特定のファイル種別を対象に動き、視覚的な証拠を動画としてコメントに投稿する。プッシュや PR のクローズはできないガードレールがあり、クレジットの上限も設定されている。毎日ログを見て改善案を出す別の automation も紹介した。動画のアップロード失敗で混乱する問題を見つけ、プロンプトの修正案を出した例である。
8. 例 2（バグ修正の連鎖）：Azure Monitor で例外を追跡し、Azure SRE Agent が GitHub に Issue を作る。再現担当が再現手順と動画を投稿して 「Bug Reproduced」ラベルを付け、これを契機に修正担当が PR を作り、最後に検証担当が再確認して、マージ可能との推奨を返す。実例は、カートが空のまま「How ordering works」を押すと 500 エラーになるバグ（SRE Agent が発見）。
9. Copilot Code Review の例：店舗の地図を追加する PR で、サンフランシスコ、オークランド、シアトルの店舗フィルターを切り替えても件数が変わらないバグと、一定以上スクロールすると UI 部品が隠れて操作しにくくなる問題の 2 件を、人が見る前に指摘した。
10. Agent Merge：PR のマージ欄で「Watch and Fix」を有効にする。テスト失敗の PR に Copilot が自動で修正コミットを押した例を見せた。ユーザー設定の Copilot、Cloud にある「自分が作る PR で Agent Merge を自動的に有効にする」設定も紹介した。

## 7. 注意点・発表者の気付き

- 価値の単位はトークンやコード行数、PR の本数ではなく成果、というのが繰り返された注意です。
- Tim 氏は、バグ修正の連鎖でも、人がやるのは最後のレビューとマージだけだと説明しています。
- automations は実際に GitHub で使われているもので、ツールの権限とクレジットの上限で制限をかけていると説明がありました。
- Bitbucket では PR 連携がなく、automations は GitHub 上では動きません。
- Agent Merge の「Copilot が Copilot のレビュー指摘を直す」機能は、社内で試験中のプレビューと語られています。
- 証拠が大量に積まれる問題は、Artifacts で対処する方向ですが、PR への対応は予定として語られたもので、現時点で提供済みとは述べられていません。
- 画面の操作はナレーションの範囲でのみ確認できます。モデル名や数値の一部は音声認識の都合で確定できません。

## 8. 利用者にとっての利点

- コストと性能：Fusion はデモで、Opus と同等の結果を約半分から 3 分の 1 未満のコストで得た例が示されました。Terminal-Bench 4.1 での首位も報告されています。
- 並列作業：独立したワークツリーで複数エージェントを同時実行でき、プロジェクトで大きな作業を分割し、レビューしやすい小さな PR にできます。
- 接続の簡単さ：Work IQ コネクターは 2 クリックで接続できます。
- 反復作業の削減：PR の検証や、バグの再現・修正・検証を automations に任せ、人は確認とマージに集中できます。GitHub UI リポジトリでは 1 日に数百の PR があると語られています。
- レビューの短縮：Code Review と Agent Merge で、マージまでの停滞を減らせます。
- 既存環境との連携：Azure DevOps のリポジトリと PR を Copilot app から扱え、Teams と Slack からも依頼できます。

## 9. まとめ

GitHub は、価値の単位を成果に置き、人とエージェントの協働に合わせてプラットフォームを作り直しています。Git の拡張による規模の確保、Copilot app と Copilot Fusion によるコスト効率、automations と Agent Merge による完了までの自動化が、その具体策です。質疑では、仕様駆動開発と証拠の管理が今後の課題として挙がり、PDD と Artifacts が方向性として示されました。
