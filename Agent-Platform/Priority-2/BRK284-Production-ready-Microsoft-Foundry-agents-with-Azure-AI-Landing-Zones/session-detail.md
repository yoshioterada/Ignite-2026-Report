## 5. 発表内容の詳細

### 5.1 AI 導入の 6 つのゲートと、PoC が本番でコストになる理由

最初の登壇者は、ランディングゾーンを AI 導入のフレームワークにおける 6 つのゲートの 1 つと位置づけました。このフレームワークは、クラウドソリューションアーキテクトのチームとカスタマーサクセスのチームが作成し、顧客に提供しているものです。AI 導入で最も問題が出やすい領域をまとめたもので、特に **企業向けに本番運用するエージェント** の導入を対象としています。セキュリティ、エージェントの運用（エージェントオプス）、回復性を担当する各チームが関わる、本番寄りの話だと強調していました。

PoC は通常、機能の確認だけを目的とした隔離された環境に置かれ、本番での使われ方は考慮されません。このとき、特に AI では次の問題がコストとして表面化すると説明されています。

| 問題 | 発話での説明 |
| --- | --- |
| モデルの乱立 | 世の中に数千のモデルがあり、安全な環境で使うべきものがどれか分からなくなる。かつてマーケティング部門が作った Web アプリが乱立した状況と同じ |
| コスト | 誰が使っているのか、請求をどこに送るのか、帰属を明確にできない |
| セキュリティ | 入口が複数あり得るが、最低でも 1 つの絞り込み点（チョークポイント）が必要 |
| スケール | 規模が大きくなったときの姿を判断する方法がない |

### 5.2 フレームワークとリファレンスアーキテクチャ

AI ランディングゾーンのガイダンスは、既存の権威あるフレームワークに AI 導入を追加する形で提供されています。具体的には Well-Architected Framework、Cloud Adoption Framework、Azure Architecture Center の 3 つです。リファレンスアーキテクチャは少なくとも 3 種類あり、Foundry ランディングゾーン、AI ゲートウェイランディングゾーン、そして通常本番で使っているプラットフォームランディングゾーンのサポートです。実装は Terraform、Bicep、ポータルの 3 種類が用意されています。

注意点として、すでに Azure ランディングゾーンがある場合は、新しいランディングゾーンを入れる前に見直すよう勧められました。スコープの拡大やポリシーのずれが起きやすいためです。

関係を整理すると次のようになります。アプリのことばかり考えがちですが、プラットフォームランディングゾーンとアプリの間をつなぐ橋が必要で、それがワークロードランディングゾーン、つまり AI ランディングゾーン（同じものを指します）です。Azure ランディングゾーンからポリシーを委任またはフェデレーションし、AI ランディングゾーンが必要とするカスタムポリシーを追加します。その上で、ワークロードのチームがアプリケーションの載る構成を作ります。

### 5.3 Ofek 氏との対話

最初の登壇者が Ofek 氏に質問する形式でした。Ofek 氏の発言の要点は次のとおりです。

- 顧客に Azure ランディングゾーンを構築し、オンプレミスからクラウドへの移行と基盤の整備を行ってきた。現在は既存ランディングゾーンのレビューを行い、AI 向けの拡張を提供している。顧客の約 95% がすでに Azure ランディングゾーンを持っている。
- 顧客の規模ではなく環境の複雑さが基準になる。例えば小さな顧客が、クラウド上で 5〜6 件の PoC を動かし、20 のエージェントを展開する計画を持っていることがある。PoC ではパブリックエンドポイントを使っているが、本番ではクォータ、可観測性、統制、セキュリティとコンプライアンスの維持が必要になる。
- 原則やベストプラクティスは以前と同じで、新しいワークロードに伴う新しい課題への対応が加わる。Satya 氏が述べたように、セキュリティとイノベーションを並べて進める必要がある。
- 最大の課題は PoC から本番への移行。数時間で PoC は作れるが、例えば、数個の PDF しか必要ない 1 つのエージェントに SharePoint 全体や Fabric 全体をつないでしまった顧客がいた。適切な形でつなぎ、将来の成長に余地を残し、セキュアなベストプラクティスで進める必要がある。
- 本番に出す前に、コストの監視方法を決めておく必要がある。スタートアップからはコスト単位やコスト経済性について聞かれることが多い。ハブ側には API Management（APIM）があり、MCP ゲートウェイやプロンプトキャッシュなど、AI のコストを抑えて観測・制御する機能がある。

> 注意：Ofek 氏は、Microsoft が AI ランディングゾーンを 2018 年に考案したと発言しています。発話のまま記載しており、補足の説明は発表ではされていません。

### 5.4 Vlad 氏：設計判断の前提（Caldova の要件）

Vlad 氏は、Caldova という会社の AI アーキテクト役を演じる形で話を進めました。CTO の要望は、どのチームでもエージェントを構築・展開・運用できるプラットフォームです。

| チームが求めること | アーキテクトが保証すべきこと |
| --- | --- |
| エージェントを数か月ではなく数週間で本番化する | チーム間の分離 |
| 承認済みのモデル、ツール、ナレッジへのセルフサービスのアクセス | ID に基づくプライベートなアクセス |
| エージェントとチームを Microsoft 365 Copilot で使えるようにする | コストの集中管理、安全性、すべてのエージェントの復旧 |

設計の対象は Microsoft Foundry で、外側のリングがガバナンス、安全性、可観測性です。内側には、ネットワーク、暗号化、アクセスを備えた Foundry リソース（アカウント）があり、モデルのデプロイを持ちます。各チームはエージェント、ツール、ナレッジ用のプロジェクトを持ち、その下にランディングゾーンが位置します。ランディングゾーンは 6 つの判断すべてについて既定の設計図を提供し、変更した場合はアーキテクチャ上の判断として記録することが勧められています。

### 5.5 判断 1：Foundry の構造

最も後から変更しにくいため最初に決めるべきとされた項目です。階層は Entra テナントから Foundry プロジェクトまでで、表では事業部門を横に、環境を縦に並べます。青い箱が Foundry アカウント、白い箱がプロジェクトです。

Caldova の方針は次のとおりです。

- 事業部門どうしでアカウントは共有しない。
- 事業部門の中では、開発とテストの間はエージェント（例として請求対応とサポートのエージェント）が 1 つのアカウントを共有する。
- 本番では、エージェントごとに専用のアカウント、ストレージ、検索、データベースを持たせる。1 つのエージェントでクォータなどの障害が起きても他に影響させないためである。
- 人事は規制対象データを扱うため、すべてを共有する専用の隔離領域（エンクレーブ）を作り、テスト環境の外には何も出さない。
- プラットフォームチームが、AI ゲートウェイ、監視、Azure Policy、アクセスなどの共有サービスを下段で運用する。

セキュリティ面では、接続には API キーではなく Entra ID を使います。プロジェクト内の誰でも、接続に保存されたキーを使えてしまうためです。

### 5.6 判断 2：エージェントのデータの置き場所

エージェントは会話、ファイル、ベクトルストアを作ります。ランディングゾーンは **標準エージェント構成** を採用し、すべてを自分のサブスクリプション内に保持します。会話は Cosmos DB、ファイルは Azure Storage、ベクトルは Azure AI Search に置き、プライベートエンドポイントの背後に配置して、必要なら自分のキーを使います。基本構成は簡単ですが、ストレージとキーを Microsoft が管理します。

既定のランタイムであるホステッドエージェントは、同じストアを使いますが、**セッションごとのホームフォルダー** だけは Microsoft 管理のストレージと Microsoft のキーに置かれます。長期的なデータは自分のストアに置くこと、そして **プロジェクトのストアは後から変更できない** ため、早い段階で決めることが助言されました。

### 5.7 判断 3：ネットワーク

「なぜ Foundry のマネージドネットワークではなく、独自のネットワークを持ち込むのか」という IT 部門からの質問への回答です。マネージドネットワークは簡単ですが、現時点では自分のファイアウォールを使えず、送信トラフィックのログも取れません。

ネットワーク分離を有効にし、すでに運用しているハブに接続すると、構成は 3 つに分かれます。

- 右側：Foundry と、それが依存するすべてのサービス。パブリックアクセスはオフ。
- 中央：エージェントのスポーク。AI ゲートウェイ、アプリケーションゲートウェイと共にエージェントを展開する。
- 左側：プラットフォームのハブ。DNS、ExpressRoute、Azure Bastion を持ち、スポークからのトラフィックが流れる。

### 5.8 判断 4：エージェントの実行環境

開発者向けの判断として、誰が何を動かすかの表が示されました（自チームが動かす部分と Microsoft が動かす部分に色分け）。

| 種類 | 内容 |
| --- | --- |
| プロンプトエージェント | 最速の方法。指示を書き、ツールを選ぶだけで、残りは Microsoft が実行する |
| ホステッドエージェント | ランディングゾーンの既定。Agent Framework、LangGraph、Semantic Kernel などでコードを書き、Foundry がコンテナーで実行する。エンドポイント、ID、スケーリング、バージョン管理は Foundry が担当 |
| セルフホスト（Container Apps、AKS、Functions） | 完全な制御が得られるが、サービス全体を自分で運用する。追加の制御が必要な場合にだけ選ぶ |

セルフホストする場合も、Foundry のコントロールプレーンに接続すればトレースと評価を続けられます。ただし評価、権限、コストの責任は自チームに残ります。

### 5.9 判断 5：グラウンディング（知識とツールの使い方）

ユーザーが Teams、Microsoft 365 Copilot、または自社アプリでサインインし、その要求が Foundry 上のエージェントに届きます。経路は 2 つです。

- 知識の経路：エージェントは、複数のエージェントが共有する Azure AI Search 上の Foundry IQ ナレッジベースを呼びます。クエリを計画し、複数のソースを並列に検索し、回答をまとめます。ユーザーの ID が要求と共に伝わるため、ソースが権限をサポートしている場合、ユーザーは許可された内容だけを見られます。
- ツールの経路：エージェントは Foundry の toolbox（承認済みツール用の統制された MCP エンドポイント）を呼びます。各ツールを、Entra ID のエージェント ID、プロジェクトのマネージド ID、割り当てられたユーザーのどれで実行するかを選べます。

守るべき原則は、**グラウンディングによって成功の範囲を広げてはならない**（アクセス権を拡大しない）ことで、すべてのホップが定義済みの ID を持つようにします。

### 5.10 判断 6：AI ゲートウェイ

AI ゲートウェイの役割は 5 つです。呼び出し元の認証、トークン制限の適用、ルーティングとフェイルオーバー、安全性ポリシーの適用、使用量とコストの追跡です。運用には 2 つの方式があります。

| 方式 | 内容 |
| --- | --- |
| ローカルゲートウェイ | 1 つのワークロードに 1 つの API Management インスタンス。使い始めのチーム向け |
| AI ゲートウェイランディングゾーン | 多くのチームで共有する中央のゲートウェイ |

助言は、**まずローカルで始め、規模が大きくなったら集中化し、最終的には本番トラフィックをすべて集中ゲートウェイ経由にする** ことです。AI ランディングゾーンは 2 つの部品を提供します。共有モデルのハブである AI ゲートウェイランディングゾーンと、事業部門またはユースケースごとに 1 つ作るスポークであるエージェントランディングゾーンです。両者をつなぐのが 2 つの契約で、アクセス契約は各スポークが使えるものを定め、公開契約はチームが作ったものを共有します。詳細は AI ランディングゾーンのサイト（aka.ms/ailz）にあり、QR コードも示されました。

### 5.11 リファレンスアーキテクチャ：エージェントランディングゾーン

Caldova のプラットフォームハブに接続するスポークを、6 つの手順で説明しています。

1. **チャネル**：同じエージェントに 2 つの経路で届く。Foundry から直接公開した Teams または Microsoft 365 Copilot と、Web アプリケーションファイアウォール付きのアプリケーションゲートウェイの背後にある Container Apps 上の Caldova の Web アプリ。
2. **エージェント**：オーケストレーターと呼ぶメインのエージェントは Agent Framework で構築し、Foundry のホステッドエージェントとして動く。チームがコードを書き、Foundry がエンドポイント、ID、スケーリングを担い、各セッションに専用のサンドボックスを与えてエージェント用に委任されたサブネットに接続する。
3. **Foundry アカウント**：パブリックアクセスはオフ。モデルはアカウント単位でデプロイするため、すべてのプロジェクトが使える。各プロジェクトは自分の接続と評価を追加する。隣にある、判断 6 のローカル AI ゲートウェイ（モデルの前段にある API Management）は専用のサブネットに置く。
4. **ナレッジ**：Azure AI Search 上の Foundry IQ ナレッジベース。Caldova の Blob ストレージと既存の検索インデックスを使う。必要なら Web と、Fabric IQ や Work IQ などの Microsoft IQ のソースも追加できる。
5. **依存サービスの分離**：Key Vault、Azure Storage、AI Search が図の中に 2 回出てくる。Foundry のエージェントサービスが専用の Cosmos DB、AI Search、Key Vault を持つため、アプリやナレッジ層での変更や誤削除がエージェントサービスを壊さない。
6. **プラットフォーム部分**：すべてのサービスはプライベートエンドポイントの背後にあり、キーではなくマネージド ID を使う。送信トラフィックはハブのファイアウォールを通り、DNS と Bastion はハブから提供される。運用者は Bastion 経由でジャンプボックスに入り、ビルドエージェントはエージェントのスポーク内で動くため、パブリックアクセスを閉じてもデプロイできる。

スポークには Application Insights と Log Analytics による独自の監視もあります。歯車アイコンが付いた Agent 365、Defender、Entra とプレビューの機能は、別途構成して使えます。

### 5.12 リファレンスアーキテクチャ：AI ゲートウェイランディングゾーンを含む全体

Caldova の環境全体では、上にエージェントのスポーク、下に全チーム共有の AI ゲートウェイランディングゾーンがあります。この場合、スポーク側には専用のゲートウェイを置きません。6 つの要素は次のとおりです。

1. **2 つのハブ**：すでに運用しているプラットフォームのハブと、共有モデル、ガバナンス、安全性を担う新しい AI ゲートウェイのハブ。
2. **AI ゲートウェイのリソース**：API Management で、ID を確認し、トークンのクォータを適用し、コンテンツの安全性と個人データの検出を適用し、すべての呼び出しをルーティングする。アプリがモデルのキーやポリシーを持たずに済む。
3. **共有モデル**：ゲートウェイの背後に、リージョンをまたぐ負荷分散とフェイルオーバーを備えた Caldova の共有モデルがある。
4. **事業部門**：カスタマーサービス、財務、人事などが、それぞれ専用の AI エージェントランディングゾーン（スポーク）を持ち、独立してアプリを構築する。
5. **2 つをつなぐ契約**：アクセス契約が、チームをモデル、クォータ、ポリシーと共にゲートウェイへオンボードする（ゲートウェイにはプライベートエンドポイント経由で接続）。公開契約が、チームのツールやエージェントを Caldova 全体に共有する。
6. **集中した可視化**：すべての呼び出しが集中ゲートウェイを通るため、全スポークの使用量、コスト、監査ログを 1 か所で確認できる。

### 5.13 質疑応答

発表の最後に会場から質問を受け付けました。

**Q1. 複数の事業部門がある場合、Foundry は共有インスタンスと専用インスタンスのどちらにするか。**（Craft Heinz の Principal Cloud Engineer を名乗る方。社名の綴りは音声認識の都合で確定できません）
質問者は、プレミアム SKU が高価なために AI ゲートウェイは共有にするが、Foundry はどうなのかを尋ねました。回答は、まずワークロード用のスポークを定義し、チームやユースケースごとに環境を分離する、というものです。各スポークが Foundry アカウントと依存リソースを持ちます。必要ならスポークごとにローカルの AI ゲートウェイを置いて統制と監視もできます。単位は「チーム」ではなく **ワークロード** で、チームは Foundry 内のプロジェクトとして、リソースを共有できます。絶対に分離が必要な事業部門は、Foundry アカウントのリソースをスポークで包んで外に何も出ないようにします。共有してよいチームは、同じ Foundry に複数のプロジェクトを作ります。ゲートウェイが無いと、モデルがアカウント単位でデプロイされているため他チームのモデルを消費してしまう可能性があるので、最低でもローカルゲートウェイを置きます。完全な分離が必要なら、同じスポーク内に複数の Foundry アカウントを作ります。

**Q2. アーキテクチャの AI ゲートウェイは API Management か。今週 GA になった新しい AI ゲートウェイのリソースとの違いは。**
回答では、このアーキテクチャのゲートウェイは API Management のリソース（現状は Standard 層）で、ローカル方式ならスポークに、集中方式ならハブに置きます。新しい AI ゲートウェイは機能のサブセットで、消費を統制するための機能の大部分を提供します。ライセンスや API の制限、カスタムポリシーが必要なら API Management 自体を使います。新しい AI ゲートウェイは、モデル、エージェントのツール、トークン消費、リトライのロジックなど生成 AI のワークロードに焦点を当てているのに対し、API Management はより広いカスタムポリシーの統制もできるという説明です。

**Q3. 新しい AI ゲートウェイを AI ゲートウェイランディングゾーンに統合する計画はあるか。**
計画はあり、エージェントランディングゾーンと AI ゲートウェイランディングゾーンの両方への対応を追加する予定です。ただし、コンテンツ安全性ポリシーなど、まだプレビューの機能があるため、それらがエンタープライズ向けに提供されるのを待って取り込むと回答しました。

**Q4. AI ランディングゾーンと AI ゲートウェイランディングゾーンの組み合わせである「Studio」のプラットフォームを使う予定だが、今日の発表で触れられていないので助言はあるか。**
オフラインで話す、という回答でした。この場では回答されていません。なお、質問内の「Studio」の正確な名称は、音声認識の都合で確定できません。

**Q5. 共有サービス環境にある既存の API Management に AI ゲートウェイの機能を有効にし、AI と既存のワークロードで共有してよいか。それとも AI 専用に分けるべきか。**
回答は、どこまでやるかによる、というものでした。集中ゲートウェイと API Management から始められるなら、そこから始めることを勧めます。さらに統制の層を足したい場合は、プロキシ方式で重ねることができます。

**Q6. 共有の API Management で、13 の事業部門へのチャージバックをどうするか。**
回答は、ログを監視し、そのメトリクスとログに基づいてチャージバックを決める、というものです。API Management がゲートウェイなので、監視とログの機能を追加で適用できるという説明でした。

**Q7. Foundry のランディングゾーンを新規に作る。ハブとスポークにどう分かれ、AI ハブで何を共有するのか。**
従来のハブには、ファイアウォール、WAF、プライベート DNS、DNS フォワーダーなどがあります。AI ハブ側では、AI Search などの接続リソースを備えた主要な Foundry アカウントを定義します。モデルなど、統制と監視が必要なものはすべて AI ゲートウェイハブに移すことで、集約してモデルの消費やトークン使用量を制限でき、複数のスポークへ拡張できます。プラットフォームのハブにあるファイアウォールなどは再利用されます。エージェントは、ワークロードごとのスポークに置きます。スポークは事業やワークロードの境界を表し、相互接続したくない部門やワークロードにはそれぞれ別のスポークと分離したリソースを作ります。望むなら 1 つのスポークでリソースを共有することもできます。サブスクリプションは、スポークごとに分ける必要はなく、本番用と開発用のサブスクリプションの中に複数のワークロードを置いてもよい、という確認が取れています。

## 6. デモ・手順

Paolo 氏が、Caldova Pharmaceuticals の請求書調査アプリ「Waypoint」を題材に、エージェントランディングゾーンと AI ゲートウェイランディングゾーンの両方を導入する流れを見せました。4 段階（要件から設計判断、コードでの構成、デプロイと評価、使用量と品質の監視）で進み、画面の細部は音声からは確認できません。語られた順に整理します。

### 6.1 要件から設計判断へ

1. AI ランディングゾーンのページにある **設計チェックリスト** を開く。8 つの観点に分かれた質問集で、AI ランディングゾーンから何を使うかを決めるためのもの。
2. ネットワークの質問に対し、Waypoint はすべてプライベートネットワーク内に置く必要があるため、全サービスをプライベートエンドポイント経由で使うと決める。
3. 共有ゲートウェイでアクセス制御、レート制限ポリシー、安全性ポリシーを適用するため、AI ゲートウェイが必要と決める。
4. ID の質問（サービス間の認証方法）に対し、推奨に従ってマネージド ID を使うと決める。

### 6.2 コードでの構成

ポータルでも作れるが、拡大して自動で再現するにはテンプレートが最善と説明されました。

**AI ゲートウェイランディングゾーン側**

1. API Management の SKU を決める。ネットワーク分離と安全性ポリシーのため Standard V2 を使う。
2. バックエンドを構成する。AI ゲートウェイランディングゾーン内の Foundry リソースがモデルを提供するため、そのエンドポイントを設定し、設計どおりマネージド ID を使う。そのサービスが提供するモデルも設定に含める。
3. Waypoint 用のアクセス契約を定義する。ユースケースは財務部門の請求書調査で、アクセスできる API はモデルのみ。
4. 契約に適用するポリシーを XML ファイルで定義する。内容は次の 3 つ。
   - アクセス制御：呼び出し元のアクセストークンが Entra ID に対して有効かを検証し、呼び出し元がアクセスリストに含まれているか（ここではエージェントが含まれる）を確認する。
   - レート制限とトークン制限：呼び出し元ごとに 1 分あたり 60 リクエストと 60,000 トークン。
   - コンテンツの安全性：すべてのリクエストを検査してプロンプトインジェクションがないことを確認し、4 つのコンテンツ安全性カテゴリーすべてに合格することを求める。対象は、エージェントがこの API で使うレスポンスと補完のルートのすべてのリクエスト。

**エージェントランディングゾーン側**

1. メインのパラメーターファイルで、ネットワーク分離を有効にする。Caldova のインフラチームが用意済みの VNet を再利用し、プラットフォームハブの VNet を指定して、エージェントランディングゾーンの VNet とピアリングする。
2. 取得（検索）のバックエンドとして、エージェントが使う Foundry IQ と、そこにあるインデックスを設定する。
3. カスタムアプリである Waypoint の 3 つの構成要素（Web フロントエンド、API バックエンド、エージェント）を、プロビジョニングとデプロイの前に伝える。
4. Azure Developer CLI（`azd`）が使う azure.yaml ファイルに、契約エージェントを Foundry のホステッドエージェントとして実行することと、実行時に必要なコンテナーのサイズを記述する。

エージェントの実装では、契約エージェントに指示ファイル（Markdown）があり、請求書調査で何をすべきかが書かれています。末尾にガバナンスのセクションがあり、証拠に基づいて分析すること、レコードを作成しないことなど、システムにリスクを与えない制約（ガードレール）が加えられています。

### 6.3 デプロイ

最も簡単な方法として、端末で `azd provision` によりインフラを作成し、`azd deploy` でアプリケーションをデプロイすると説明されました。実際の本番では Azure DevOps や GitHub のパイプラインで自動化すると述べています。

### 6.4 デプロイ後のアプリの確認

デプロイした Caldova の Waypoint 画面では、契約エージェントがすでに作業を済ませ、ある請求書にフラグを立てていました。契約、請求書の情報などの証拠を見て、支払い前に 111,000 のエスカレーションが必要だと判定しています（通貨単位は発話では確認できません）。画面には判断の根拠と説明も表示されます。レポートの証拠の一部は Foundry IQ のナレッジベース（契約書）に由来し、契約には「供給元の汚染に起因するコストは請求書に載せられない」という趣旨の条項があり、これが根拠になっています。

### 6.5 監視

1. **AI ゲートウェイランディングゾーン**：ワークブックと Application Insights で運用情報を確認する。トラフィック、トークン数、API リクエスト数、呼び出し元ごとのトークン数（この場合は契約エージェント）が見られる。
2. **エージェントランディングゾーンの Foundry**：契約エージェントの詳細画面を開く。エージェントの ID は、ゲートウェイ側で見た ID と一致している。
3. **トレース**：エージェントの実行ごとの軌跡を追え、モデル呼び出しとツール呼び出しを確認できる。グラフ表示があり、各実行のデバッグや監査に使える。
4. **モニタータブ**：デプロイしたエージェントの実行回数、エラー、ホストの計算資源とメモリー使用量、ツール呼び出し、評価の要約が見られる。
5. **評価**：Foundry はエージェントの評価をサポートする。デプロイ前にパイプラインで評価を実行して品質を確認でき、デプロイ後にも定期的に実行して品質の維持や低下を把握できる。この例では、正確性、グラウンディング、ガバナンス、指示への追従の 4 つの品質観点すべてで、3 件のテストケースが 100% で合格した。

デモの最後に、始め方として AI ランディングゾーンのページ（aka.ms/ailz）への QR コードとフィードバック用の QR コードが示されました。

## 7. 注意点・発表者の気付き

- **既存ランディングゾーンの見直し**：Azure ランディングゾーンがすでにあっても、スコープの拡大とポリシーのずれが起きやすいため、AI 用を追加する前に確認する。
- **データ置き場は早く決める**：プロジェクトのストアは後から変更できない。長期的なデータは自分のストアに置く。ホステッドエージェントのセッションごとのホームフォルダーだけは Microsoft 管理のストレージと Microsoft のキーに置かれる。
- **マネージドネットワークの制約**：現時点では自分のファイアウォールを使えず、送信トラフィックのログも取れない。
- **API キーより Entra ID**：プロジェクト内の誰でも、接続に保存されたキーを使えてしまう。
- **ゲートウェイが無いと消費が見えない**：モデルはアカウント単位でデプロイされるため、ゲートウェイが無いと、他チームのモデルの利用を知らずに消費してしまうチームが出る。最低でもローカルゲートウェイでモデルのエンドポイント、トークン、コストを統制する。
- **セルフホストの責任**：自由度が高い分、評価、権限、コストは自チームで担う。
- **グラウンディングで権限を広げない**：すべてのホップが定義済みの ID を持つ。
- **PoC の落とし穴（Ofek 氏）**：少数の PDF で足りるエージェントに SharePoint 全体や Fabric 全体をつないだ顧客の例があり、適切な形でつなぐことが必要と述べられた。コストの監視方法も本番前に決める。
- **新しい AI ゲートウェイ機能の取り込み時期**：コンテンツ安全性ポリシーなど一部がまだプレビューのため、エンタープライズ向けの提供（GA）になるまで取り込みを待つ（5.13 の質疑応答を参照）。この取り込みは将来の計画であり、現時点では提供されていません。

## 8. 利用者にとっての利点

発表で語られた効果を整理します。

- 同じチェックリストを毎回繰り返す必要がなく、ワークロードのチームの摩擦と継続的な負担が減る。
- ポリシーを集約し、委任とフェデレーションでワークロードに渡せるため、エージェントを環境へ展開する速度が上がる。
- 集中ゲートウェイにより、全スポークの使用量、コスト、監査ログを 1 か所で見られる。アプリはモデルのキーやポリシーを持たずに済む。
- テンプレート（Terraform、Bicep、ポータル）と `azd` により、設計判断をコードにして自動で再現できる。
- 依存サービスをエージェントサービス専用に分離するため、アプリやナレッジ層の変更・誤削除でエージェントが壊れない。
- 顧客事例としての数値成果は、発表では語られていません。デモは Caldova（Caldova Pharmaceuticals）という想定のシナリオです。

## 9. まとめ

AI ランディングゾーンは、PoC から本番までの停滞を減らすために、Microsoft のクラウドソリューションアーキテクトの経験をチェックリストと実装テンプレートにまとめたものです。Foundry の構造、データの置き場所、ネットワーク、実行環境、グラウンディング、AI ゲートウェイという 6 つの判断を既定の設計図から出発して決め、エージェントランディングゾーン（スポーク）と AI ゲートウェイランディングゾーン（ハブ）の組み合わせで実装します。デモでは、設計チェックリストから、ポリシー XML とパラメーターファイル、`azd` によるデプロイ、ゲートウェイと Foundry の監視、評価までを一通り見せています。詳細は aka.ms/ailz で確認できます。
