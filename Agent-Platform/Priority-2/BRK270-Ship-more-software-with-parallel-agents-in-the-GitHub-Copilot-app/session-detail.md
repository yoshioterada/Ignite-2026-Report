## 5. 発表内容の詳細

### 5.1 背景：仕事の抽象度の変化

Pierce は VS Code チームの出身で、当時は単なるコードエディターだったと話しました。その後、AI による補完が 1 行から数行の補完になり、機能を書くのをエージェントに手伝わせる段階を経て、今は複数のエージェントを同時に指揮している、という変遷です。

GitHub の年次レポート Octoverse のデータとして、**9 月にはプルリクエストの 40% 以上がエージェントによって開始された**と紹介されました。コードがシステムを流れる量が大きく変わり、以前はアンチパターン（避けるべき手法）だったような野心的なエンジニアリングの課題にも手が届くようになった、という見方です。

### 5.2 事例：Copilot Agent Runtime の Rust 移植

GitHub Copilot Agent Runtime は、VS Code、CLI、GitHub Copilot app、JetBrains、Visual Studio、Xcode といったすべての GitHub Copilot クライアントで共有されるランタイムです。起動が速く、結果が速く返り、メモリ使用量が少ないことが求められます。複数のランタイムを同時に起動してエージェントを指揮する場合は、特にメモリが効いてきます。

そこで、もともと TypeScript で書かれていたこのランタイムを Rust へ移植できるかを検証しました。数か月かけて Stephen とチームが、移植の全体を GitHub Copilot app で行い、今年の早い時期に出荷しています。成果は次のとおりです。

| 指標 | 結果 |
| --- | --- |
| プロンプト送信からセッション開始までの時間 | 約 18 倍高速 |
| 同時接続クライアントがある場合 | 91% 高速 |
| コード量 | 数百行の TypeScript から、本番用の Rust 83 万 2 千行へ |

Stephen は移植を手作業で行ったわけではなく、かといって「移植して」と一言で任せたのでもありません。移植を部品ごとに分け、部品ごとに移植の戦略とガードレール（守るべき制約）、成功の基準を GitHub Copilot と一緒に決め、移植の進行に合わせて出力を検証する仕組みまで作ったと説明されています。詳細は Stephen のブログ記事にまとまっているとのことです。

### 5.3 GitHub Copilot app の位置づけ

このアプリは、エージェントと協力して作業するために GitHub が作った新しい作業画面です。モデルが進化し、コーディングエージェントがより野心的な作業をこなせるようになる中で、自分たちのチームに必要だと感じたものから生まれたと説明されています。必要としたのは次の 3 点です。

- アイデアからマージ済みのプルリクエストまでを、できるだけ速く進められること
- 価値の高い作業を見つけ、コーディングエージェントを指揮して進められること
- 大量に開いたプルリクエストの出力を検証し、取り込めること

### 5.4 アプリの概要（デモ 1）

James が画面を見せながら、次のような特徴を説明しています。

- **Issue やプルリクエストから開始できる**：自分に割り当てられた Issue を選んで「新しいセッション」を押すだけで、クラッシュレポートやスタックトレースを含む Issue の文脈を持ったままセッションが始まります。プルリクエストでも同様で、ブランチをチェックアウトする Git コマンドを思い出す必要がありません。レビュー画面からそのままセッションを操作することもできます。
- **実行場所を選べる**：自分のコンピューターか、クラウドかを選べます。クラウドなら手元の計算資源を節約できます。
- **左側のレール**：プロジェクトセッション（複数のリポジトリを 1 つにまとめられる）と、プロジェクトに紐付かないクイックチャットがあります。James はクイックチャットで、会議後に Teams のチャットの文字起こしからメモを取ってくる、といった使い方をしていると話しました。
- **追加できる対象**：GitHub のリポジトリ、Azure DevOps、ローカルフォルダーを追加できます。ドキュメントフォルダーを追加して、Word 文書同士の相関を調べさせる例も挙げられました。
- **セッションの復元**：マシンを再起動してアプリを開き直すと、すべてのセッションが戻ります。どのターミナルで何をしていたか、再開のコマンドは何かを考える必要がありません。

Pierce は、GitHub Copilot app を作る際、変更を複数のリポジトリへ反映する場面が多く、1 つのリポジトリやフォルダーに閉じた他のツールでは足りなかったと補足しています。リポジトリをまたいでセッションを指揮できることが、アプリの前提になっています。

### 5.5 オーケストレーションとプロジェクト

アプリの設計の軸はオーケストレーションです。そのためにアプリ全体をエージェントに公開しており、**アプリ自身がアプリを操作できます**。スライドの例では、上位 5 件の Issue を尋ねたうえで、それぞれの Issue に対するセッションを作らせています。エージェントが自分でセッションを生み出して調査させ、進捗を報告させることも、プランモードで各セッションを作らせて作業前に計画を個別にレビューすることもできます。これらは同時に動き、各セッションは互いに隔離されているので、コードの変更が衝突しません。

課題として挙げられたのは次の 2 点です。

- 人間が数百のセッションを同時に管理しきれない
- 仕事は 1 つのリポジトリにきれいに対応するとは限らない

その対策がプロジェクトです。プロジェクトは、ごく狭い作業から非常に広い範囲まで定義できます。Pierce は、アプリ内のほかのエージェントをすべて管理し、チームの連絡先も集めてくる個人の「チーフ・オブ・スタッフ（参謀役）」エージェントを持っていると話しました。プロジェクトは数週間前の GitHub Universe で発表されています。

プロジェクトでは、メインのチャットを**コーディネーターチャット**と呼びます。ここで指示を出すと、各セッションが進捗を報告し、確認が必要な事項もこのチャットに上がってきます。必要なら個々のセッションに入ってチャットのログや出力を見ることもできます。

### 5.6 キャンバス

キャンバスは、GitHub Copilot app に追加できる UI で、チャットだけではない視覚的な操作手段です。先ほどのオーケストレーションの仕組み（セッションの作成、作業の誘導、報告の受け取り）はすべてキャンバスからも使えます。紹介された例は次のとおりです。

| 連携先 | できること |
| --- | --- |
| Atlassian | Jira のチケットに対して、GitHub の Issue と同じ流れを実行する |
| Sentry | クラッシュレポートをキャンバスで優先度付けし、エージェントに調査と修正を割り当てる |
| GitHub のセキュリティチーム | セキュリティの推奨事項やコードスキャンのアラートを扱う |

セキュリティの推奨事項は件数が増える一方で、解消されないことが多いと説明されました。理由は、推奨事項の意味が分からないこと、対応する余力がないことの 2 つです。UI を通じてエージェントを動かすことで、この状況に取り組んでいるとのことです。自分でキャンバスを作るには、`/create canvas` というコマンドを使います（発話では「slash create canvas」と読まれています）。

### 5.7 クラウドエージェント

エージェントを並列で動かすと、次はマシンの性能がボトルネックになります。ソースのビルド、アプリの起動、Playwright による操作と検証を、3〜4 個のノードで同時に回すと、最上位クラスの MacBook Pro でも動きが止まりかけることがあると、Pierce は述べました。ワークツリー方式で複数のセッションを動かすと、ローカルディスクにリポジトリのコピーが増えるため、ディスク容量も制約になります。

そこで GitHub は、クラウドエージェントの基盤を作り直し、数週間前に公開しました。特徴は次のとおりです。

- 既定で、安全なサンドボックスの中で動く
- 起動が速く、通常は 10 秒以内にチャットへ最初のトークンが返ってくる
- スナップショットが取られるため、ノートパソコンを閉じても、あとでサンドボックスをすぐに再開できる。イメージを最初から作り直す必要がない（以前のクラウド版では課題だった点）

セッションがクラウドにあるため、GitHub のモバイルアプリや VS Code からも扱え、複数のデバイスで同じセッションを使えます。以前の旧版のクラウドエージェントを試したことがある人は、もう一度試してほしいと呼びかけられました。

### 5.8 モデル選択と Copilot Fusion

GitHub Copilot の特徴の 1 つはモデルを選べることです。しかし「どのモデルを使えばよいか」は個人差が大きく、答えにくい問題です。チームに「1 か月前、2 か月前、6 か月前の最適なモデルは何だったか」と尋ねると、モデルだけでなく提供元まで変わっていることが多いそうです。

今年の早い時期に、プロンプトに応じて知能とコストのバランスが良いモデルへ振り分ける `auto` モードを作りました。その検証の中で、**複数のモデルを組み合わせるほうが、オフライン評価で解決率が高く、コストも下がる**と分かったと説明されています。理由は、各モデル提供元が訓練データの分布について独自の考えを持ち、それがモデルの「プロダクトの好み」として組み込まれているためで、モデルには人間と同じように得意不得意があるからです。

この流れで、基調講演で Satya が触れた Copilot Fusion が紹介されました。**解決率が Opus より 5 ポイント高く、コストは「more than half the cost」**と語られています（コストの比較の意図は、発話からは確定できません）。GitHub のチームは自分たちの開発でも Copilot Fusion を使い続けており、誰も手動でモデルを選ばず、作業に合うモデルを Fusion に選ばせています。

### 5.9 キャンバスと、エージェントがエージェントを動かすデモ（デモ 2）

James は、自分の使い方を見せました。以下は語られた順の内容です。

1. **カウントダウンサイト**：子どもと作った、次の休暇までのカウントダウンタイマーのサイト（Raspberry Pi で動かしている）を開きます。見た目を整えるために、エージェントと調整しました。
2. **組み込みブラウザーと要素の選択**：キャンバスの右側のペインは自由にカスタマイズできます。組み込みのキャンバスには変更履歴や「何が変わったか」があります。キャンバス上の見出しなどを選ぶと、その要素がチャットセッションのコンテキストに追加されます。「フォントを直して」と言うと、どの部分か推測せずに把握した状態で修正できます。キャンバスとセッションの双方向の連絡が、コンテキストを増やす要点だと説明されています。
3. **Issue のトリアージ用キャンバス**：妻の店の POS ソフトウェア向けに、GitHub の Issue を扱うキャンバスを作っています。作り方は `/create canvas` を実行し、「Issue の優先度付けができて、オーケストレーションもできるものを作って」と頼んだだけです。
4. **トリアージの開始**：キャンバスの「トリアージ開始」を押すと、AI のサブセッションが立ち上がり、Issue の優先度付けを始めます。その間に、いくつかの Issue を選びます。
5. **オーケストレーターの設定**：オーケストレーターに使うモデルを選びます。Copilot Fusion を追加していなかったので、その場で追加しました（音声では「HydroFusion」と聞こえる箇所がありますが、Copilot Fusion の内部名だと思う、と James 自身が話しています）。そのうえで、「これらの Issue を片付けて。2 つはクラウドで、1 つはローカルで GWEN 3.8 を使って実行して」と指示しました。
6. **実行結果**：オーケストレーターがローカルで起動し、さらに 3 つのセッションを作ります。2 つはクラウドで、適切と判断したモデルで動きます。指定した 1 つは GWEN 3.8（音声認識の都合で表記が確定できません）で、これは GitHub や Microsoft がホストするモデルではなく、James が手元で動かしているローカルモデルです。

駆動役のモデルには、思考型のモデルを選ぶと説明されています。子セッションが行き詰まったときに、必ず親セッションへ問い合わせるため、人間の代わりに AI がセッションの世話をしてくれます。話す相手は 1 つのセッションだけになり、疲れにくくなります。クラウドで動いているセッションは、スマートフォンからも管理できます。

James は、**すべてのセッションが他のセッションと会話できる**点も強調しました。プロジェクトをまたぐこともでき、例えば、プロジェクトに紐付かないクイックチャットから、別のプロジェクトの状態を尋ねたり、「他のプロジェクトでは、これをどう扱ったか聞いてきて」と頼んだりできます。

Pierce は、Copilot app 自身の開発でも、エージェントランタイム、Copilot SDK、アプリという複数のリポジトリに変更を入れる必要があり、GitHub Copilot のクライアント（VS Code、CLI、アプリ、JetBrains、Visual Studio など）の実装は似た形をしていると補足しました。すでに参照実装があれば、「VS Code を見て、CLI を見て」と指示して、他のコードベースの文脈を読ませたうえで同じものを実装させることが多いそうです。

James の別の例も紹介されました。

- VR ゲームを複数作っていて、共通のマルチプレイヤーサーバーを更新するときは、サーバー担当のセッションが更新を行い、終わったら各ゲームに新しい API のエンドポイントと使い方を伝えるよう頼みます。4 つのゲームのセッションが立ち上がり、同時に更新されました。入れ子は必要なだけ深くできます。
- 机に置きたい「Monabot」の 3D モデリングを、複数のセッションに任せています。腕の動きが気に入らなかったので、別のセッションに腕の再設計をさせ、新しい腕を使う可視化ツールも作らせました。James が話すのはメインのセッションだけで、「状況は？」「何を印刷すればよい？」と尋ねます。複数のオーケストレーターを 1 つのチャットから指揮することも始めているそうです。

関わり方は選べます。細部まで関与したければアプリ内でそうでき、手を離したければトップのセッションから誘導できます。James は、計画づくりも 1 つのセッションと進め、要件定義書はもう自分では書かず、エージェントと一緒に Issue へ分解していると話しました。

### 5.10 成果の検証

オーケストレーションに加えて、レビューの対象が「コード」から「成果」に移ったことも、アプリの設計で重視された点です。特に Web ベースのプロジェクトでは、アプリの中で変更を検証しやすくなっています。

- ワンクリックで実行できる。独自のスクリプトも設定できる
- 組み込みブラウザーは Playwright につながっており、エージェントが UI を操作し、スクリーンショットを撮り、要件を満たすまで繰り返せる。性能の特性も調べられる

チームでは、エージェントによる**自己検証**を多用しています。セッションやプルリクエストを開いた時点で、最初の下調べがすでに済んでいる状態にするためです。選択肢は次のとおりです。

| 手段 | 内容 |
| --- | --- |
| 組み込みブラウザー | 上記のとおり |
| Chromium 系ブラウザー向けの拡張機能（今日から提供） | Chrome や Edge の通常のブラウザーで、完全な文脈のまま、GitHub Copilot がタブを操作する |
| デスクトップのコンピューター操作 | Electron アプリ、古い GUI、API のないアプリを、ユーザーと同じように操作する |

Pierce は、検証の指示をあえて曖昧にしても、エージェントが検証に苦労するなら、使い勝手に問題がある兆候だと考えられると話しました。大規模な試みとして、夜間に GitHub Copilot app の Issue をすべて確認し、セッションを立ち上げ、`main` ブランチを取得してアプリをビルドし、Issue の記述から再現を試みさせる運用を試しているそうです。チームのプルリクエストには、エージェントがアプリを操作した、変更前後の動画が自動で添付されます。フィードバックはエージェントのセッションか、プルリクエスト上で返せます。

### 5.11 マージ：Agent Merge と GitHub チームの運用

AI 以前からプルリクエストを取り込むことは、どのチームにも課題でした。コーディングエージェントによってスループットが上がり、さらに難しくなっています。そのために作られたのが **Agent Merge** です。プルリクエストを監視して、マージの競合を解決し、レビューの指摘に対応し、壊れた CI を直します。「比較的安全な」変更なら自動マージもできますが、チームでは普段これを有効にしていません。プルリクエストの世話を人間がしなくて済むようになり、GitHub Copilot app のチームではマージまでの時間の改善に欠かせないものになっていると説明されています。

レビューの指摘が的外れだった場合は、盲目的に従わず、「本当にそうすべきか」と押し返します。Agent Merge は、今は VS Code と Copilot CLI でも使えます。

GitHub チームでのプルリクエストの扱いは次のとおりです。

- プルリクエストは成果を確認する最後の関門であり、「このアイデアがコードベースに入ることを承認するか」を決める場所。スタイルの指摘のような従来のコードレビューからは離れている
- 基本的には Copilot のコードレビューを信頼している。加えて、メンバーがそれぞれ自分のレビュー用エージェントを設定している。James は Product Manager として、データが正しいか、Issue のシナリオを網羅しているかを見るエージェントを持つ
- Agent Merge が、レビューコメントへの対応を片付ける
- リスクとドリフト（意図からのずれ）をプルリクエストで自己評価するツールがある。アーキテクチャの変更や UI の変更を検出し、Teams と Slack に流れる。コーディングエージェントが意図しない UI 変更をすることがあるため
- 性能の面では、リスクの高い部分に触れるプルリクエストでは、ベンチマークのスイートが走る
- フィーチャーフラグを多用し、スタッフ向けには毎日機能を出す。テレメトリと A/B 実験で、GitHub スタッフ、Microsoft 全体、プレリリース、一般公開、既定でオフから既定でオンへと段階的に広げる。これもアプリ内で行っていて、この発表の直前にも A/B 実験を進めたとのことです

### 5.12 Agent Merge とオートメーションのデモ（デモ 3）

James は、まずオートメーションの設定を見せました。

1. **POS のプロジェクト**：Issue が入るたびに優先度付けをして、有効かどうかを判断する。Crashlytics のクラッシュごとに、スタックトレース付きで Issue を自動登録する。毎週のセキュリティレビューで、コード全体を見て新しい欠陥がないか確認する。モデルが進化するため、毎週新しい問題が見つかるそうです。
2. **毎朝のデイリーデブリーフ**：Slack、Teams、メール、カレンダーを確認して、その日の予定と、返信すべきメッセージを優先度付きで教えてくれる。カンファレンスに出ているため Slack が遅れているので、夜 9 時半か 10 時ごろに「寝る前に返信すべき Slack は？」と聞く、と話しました。
3. **実際に見つかった問題**：Issue の優先度付けで、妻の店の POS が使う Azure のデータベースが、2 GB の上限に近づいていると、その日に分かりました。エージェントにファイルサイズの上限を 5 GB へ上げさせています。放置すれば、数週間後に取引を記録できなくなっていたはずです。コードの外にあるリソースや、Azure 上で動くものも、エージェントが確認できた例です。

続いて、**モバイルキャンバス**が紹介されました。Microsoft のモバイル開発ツールを作っている人が作った外部のキャンバスで、iOS と Android のシミュレーターをアプリ内にストリーミング表示します。James は、AI に「新しい画面を追加した」と言われて開くと、そこへ移動するボタンがない、ということがよくあると話しました。シミュレーターの映像を AI が見られるようにすると、「Songs（曲）タブへ移動して」と指示できます。アクセシビリティの仕組みが公開されているため UI 要素を問い合わせられ、見つからないときは画像を送って探させることもできます。タップや操作も実際に行われ、UI テストをすべて実行させて、失敗したときにシミュレーターで見て文脈をつかめます。

最後に、進行中のプルリクエストを使った Agent Merge の操作が見せられました。

1. 日次の概要レポートを追加するプルリクエストを開く。間に合わなかったので、自動モードに入れておくべきだったと話す
2. Agent Merge で、何を任せるかを選ぶ。プルリクエストの問題への対応、競合の解決、マージ。マージを望まなければ、マージ以外をすべて行い、マージせずに残すこともできる
3. 今回はマージまで任せるため、Agent Merge を押す。セッションが始まり、準備ができ次第マージされるよう管理して、まず競合の解決を進める

James は、証明書の期限切れや API の障害などで、できるだけ早く出荷したいときにも、プルリクエストの世話をしなくてよいことは大きいと話しました。また、CI が整っていることは AI で速く進めるための前提で、CI がなければ AI に作らせればよく、コードを書くたびにテストも書かせればよいと述べています。

### 5.13 オートメーション

オートメーションは、仕事を拡大する手段です。目標が明確で、ガードレールがある仕事に向いています。例として、1 日の準備、Issue の優先度付け、アプリのバグ修正があります。個人にもチームにも設定でき、特に Issue の自動化のようなチームのワークフローが増えています。スケジュール実行のほか、イベントでも起動できます（新しい Issue が開いたとき、プルリクエストがマージされたとき、など）。

最近の 2 つの例として、チームでは CI の所要時間の最適化に使い、重要なエンジニアリング指標である「テストがすべて成功するまでの時間（time to green）」を **2 週間で 50% 短縮**しました。これは、常時動き続ける、山登り式（ヒルクライミング）の自己改善オートメーションです。明確な目標を設定し、「テストを消して速くしてはいけない」というガードレールを与えています。もう 1 つとして、David Fowler が .NET ランタイムの性能最適化に同じ方法を使い、成果を共有している、と紹介されました。

### 5.14 コード以外への広がり

エンジニアの 1 日は、AI 以前からコードを書く時間が中心ではありませんでした。仕様の作成、フィードバックの優先度付け、テレメトリの分析、マーケティング素材づくりなどです。GitHub Copilot app はこれらにも使われています。

社内で配布して分かったこととして、エンジニアと協力するものの、従来型のソフトウェアエンジニアではない人が多く使っています。**GitHub で最も導入が進んでいるのは営業チーム**だと、Pierce は述べています。法務チーム、デザイナー、プロダクトマネージャーも使っており、アプリのチームでは、デザイナーとエンジニアの人数が同じです。数人の PM を含め、全員がコードベースに貢献しているとのことです。

### 5.15 カスタマイズ：プラグイン、スキル、MCP、コネクター

アプリは、プラグイン、スキル、MCP サーバーといった一般的なエージェントのカスタマイズ構成要素に対応しています。それらを見つけ、インストールし、使い始めやすくする UI が、アプリ内にあります。

Enterprise Managed Settings を使うと、組織のマーケットプレースを定義できます。GitHub の営業チームでは、全員に、営業用に選んだプラグインのセットを使わせたいと考えています。例えば、アカウント情報の照会、レビュー会議の準備、GitHub Copilot のエンジニアリングチームの最新動向の把握です。アプリを開いたときにすでに入っている状態にします。

Microsoft には Agency という組織内のストアがあり、約 3,000 のプラグインが登録されています。Microsoft のエンジニアは、これを GitHub Copilot app から使えます。

MCP サーバーは強力な反面、設定が面倒で、認証トークンの期限切れのたびに再認証が必要です。デバイス間で引き継がれず、クラウドエージェントではローカルの認証コンテキストも使えません。そこで作られたのが**コネクター**です。MCP サーバーを設定して手元にサインインするのではなく、**1 回サインインするだけ**で、アプリ、CLI、VS Code など、すべての GitHub Copilot の画面で、どのデバイスでも、ローカルのエージェントとクラウドのエージェントの両方から使えます。クラウドへ作業を移すうえで、ツールが動かず必要な文脈を取れないことが大きな制約だったため、これは大きな改善だと説明されています。チームでは Sentry コネクターをクラウドで使っています。

コネクターの使用例は次のとおりです。

- James：Azure MCP で、テレメトリがどう保存されているかを知らないまま、「テレメトリを問い合わせて、コホート別に分けて」と頼んでいる
- Pierce：Azure Data Explorer のコネクターを毎日使っている。Slack と Work IQ のコネクターも便利。文脈は GitHub だけでなく、設計会議や Slack にもある
- James：チームの会議で取った顧客メモをすべて読ませ、相関を分析させる。会社をまたいで頻出する課題や共通のテーマを探させる。自分ではやらない作業だと話しています

### 5.16 ガバナンス：Enterprise Managed Settings

アプリを安全に管理し、チームにとって最適な設定にするためのガバナンスの機能があります。次のようなことができます。

- 既定のモデルの変更（例：組織の既定を Copilot Fusion High にする）。既定値を一切変えない利用者が多いため、既定のモデルは、成果を高め、コストを管理する最も強い手段の 1 つだと説明されています
- MCP サーバーの有効化と無効化
- プラグインのマーケットプレースの定義と、特定の利用者へのプラグインの事前インストール

これにより、アプリを組織の制約に沿って安全に使え、新しい利用者も最初から最良の既定値で生産的に始められます。

## 7. 注意点・発表者の気付き

- 並列で動かすと、人間の注意力だけでなく、マシンの性能とディスク容量が制約になります。クラウドエージェントはその対策として紹介されました
- 人間がセッションを 1 つずつ見る運用は成り立たないため、コーディネーターチャットや親子セッションで管理する対象を上げます
- CI を整えることは、AI で速く進めるための前提です。無ければ、AI に作らせます
- 自動化のオートメーションには、ガードレールが要ります。CI の高速化では「テストを削除して速くしてはいけない」と指定しました
- Agent Merge は、レビューコメントに盲目的に従わず、押し返します。自動マージは「比較的安全な」変更に限り、チームでは普段有効にしていません
- コーディングエージェントが意図しない UI 変更をすることがあるため、UI の変更はプルリクエストで見えるようにしています
- AI に画面を作らせても、そこへ移動する手段が無いまま完了とされることがあります。シミュレーターを見せるなど、文脈を与えると防げると説明されました
- 既定のモデルを変えない利用者が多いため、組織の既定値の設定が重要です
- Copilot Fusion の数値（Opus より 5 ポイント高い解決率、コストは「more than half the cost」）は、発表で語られた内容です。評価の条件は説明されていません

## 9. まとめ

GitHub Copilot app は、複数のエージェントを指揮し、成果を検証し、プルリクエストを取り込み、定型作業を自動化するために、GitHub のチームが自分たちの必要から作った画面です。管理の対象を個々のセッションから成果へ引き上げることが、設計の核になっています。

そのための要素として、プロジェクトとコーディネーターチャット、拡張できるキャンバス、新しいクラウドエージェント、複数のモデルを組み合わせる Copilot Fusion、エージェントによる検証、Agent Merge、オートメーション、コネクター、Enterprise Managed Settings が紹介されました。GitHub 内では、コード以外の仕事や非エンジニアの職種にも広がっています。6 月から一般提供されており、発表者は試用と、翌日のブースでのフィードバックを呼びかけて締めくくりました。
