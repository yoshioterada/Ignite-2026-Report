# THR869 Beyond the browser: Build a mobile app with GitHub Copilot

## 1. はじめに

このセッションは、GitHub Copilot などの AI エージェントにモバイルアプリ（およびデスクトップアプリ）の中身を「見せて」、実装から動作確認までの開発ループをエージェント自身に回させる方法を紹介するシアター形式の発表です。Web 開発ではブラウザーや Playwright のようなテストの枠組みでエージェントが動作を確かめられますが、モバイルでは同じことが難しいという課題から始まります。

発表では、同じサンプルアプリ（映画のレビューを友人のサークル内で共有するアプリ「Theater Log」）を使い、次の 3 段階で解決策を見せています。

1. コード変更なしで、動作中のアプリをエージェントに操作させる Mobile Canvas 拡張機能
2. フレームワーク固有のベストプラクティスをエージェントに教えるスキルとカスタムエージェント（例は .NET MAUI）
3. アプリの内部にエージェントを置き、ビジュアルツリーまで見せる .NET MAUI AI ツールチェーン（DevFlow など）

**3 つともデモが行われています。** 録音は音声のみのため、画面上の細かい表示は発話で語られた範囲に限って書いています。

## 3. 何に関する発表か

テーマは、「エージェントがアプリの実体を知らない」という問題です。発表者によると、エージェントは自分が作っているアプリが何か、どう操作するか、開発者本人のようにフルの開発ループ（実装→実行→確認→修正）を回すにはどうするかを知りません。James は 15 年間モバイル開発者をしており、以前は自分が学んでいたことを、今は自分のエージェントに教えていると語っています。

取り上げる課題は、モバイル・デスクトップ開発者にとっての 4 つです。

1. 実行中のアプリを見せ、変更をリアルタイムでテストさせる
2. エージェントにモバイル開発のスキルを教える
3. 2026 年末時点で、エージェントと開発者を高い生産性に導く AI 開発ツール一式がどうなっているかを見る

## 4. 発表者が伝えたいメッセージ

中心にあるのは、エージェントに推測させないことです。画面のスクリーンショットから座標を当てずっぽうに探すのではなく、アプリの要素やツリーを直接読ませるほど、速く、トークン効率よく、高い性能でテストできると説明しています。

その段階が 3 つあります。Mobile Canvas は、どのアプリにも、どの言語でも、そのままで使えます。スキルとカスタムエージェントは、フレームワークの専門家が作ったベストプラクティスをエージェントに与えます。さらにアプリ内にエージェントを組み込めば、完全なビジュアルツリーまで見えます。発表の締めでは、「検査、操作、変更、再生、検証」という閉じたループをつくることが目標だと語られました。

## 5. 発表内容の詳細

### 5.1 課題：エージェントはアプリを見てテストできない

Web サイトの開発では、統合ブラウザーや Playwright のようなテストの枠組みがあり、エージェントは機能が本当に実装できたか、バグが直ったかを推測せずに確認できます。モバイルでは歴史的にこれが難しいと説明されました。そこで、さまざまな言語・フレームワークで作られたモバイルアプリに共通して使える手段として、GitHub Copilot と VS Code 向けの **Mobile Canvas 拡張機能** が紹介されます。

Mobile Canvas を使うと、エージェントは次のことができます。

* デバイスを管理する
* 動作中のアプリをライブで見る
* 開発者と同じように実際の入力を行う
* アプリのコード変更は不要

通信は MCP 経由で、マシン上でローカルに行われます。

### 5.2 Mobile Canvas の仕組み

動作の仕組みは 2 通りだと説明されています。1 つはスクリーンショットで画面を見る方法です。もう 1 つは、Android エミュレーターや iOS シミュレーターに対して、画面上の要素を問い合わせる方法です。

アプリにコード変更を加えていないため、Mobile Canvas はアプリがどのフレームワークで作られているか、ある要素がボタンなのかも知りません。分かるのは、iOS と Android のアクセシビリティが渡してくる自動化 ID などの情報だけです。そのため、アクセシビリティの識別情報があればそれをタップし、無ければ座標をタップします。登壇者の 1 人は、動作を良くするためにアクセシビリティのフラグをたくさん設定するようになったと話しています。

また、Mobile Canvas は Copilot 専用ではなく、プラグインとして標準的に提供されており、使っているどのエージェントの枠組みでも利用できます。MCP サーバーは単独でも MCP サーバーとして使えます。

### 5.3 Mobile Canvas の機能

シミュレーターは実機のように動き、スクロールやクリックができます。そのほか、スクリーンショットの取得、録画、デバイスの回転などが挙げられました（「たくさんのことができる」とも述べています）。複数のシミュレーターやエミュレーターから選べます。

### 5.4 スキルとカスタムエージェント

ベストプラクティス、アクセシビリティ、レイアウトの最適化を守らせるために、エージェントスキルとカスタムエージェントが使われます。

* **エージェントスキル**：エージェントに、特定の目的のための能力を与える標準仕様です。アクセシビリティ、レイアウト、テーマなどのスキルを用意して、フレームワークのベストプラクティスを教えられます。
* **カスタムエージェント**：エージェントを動かすときのプロファイルのようなものです。目的に応じたカスタム指示を持ち、PR レビューやアクセシビリティの専門家のように、固有のツールや指示を呼び出せます。

James が各分野を調べたところ、次のものが挙げられました。

| 分野 | 発話で挙げられたもの |
| --- | --- |
| iOS | Two Straw（聞こえた綴りのまま。音声認識の都合で表記が確定できません）という人気の Swift 開発者による、Swift・Swift Data・SwiftUI 向けのガイダンス |
| Android | Kotlin 向けのモバイルネイティブスキル多数 |
| Windows | Windows チームと WinUI チームによる、WinUI 3 のスキャフォールディング用 CLI（James 自身も使っている） |
| .NET MAUI | .NET MAUI チームが公開したばかりの、エージェントスキル付きの .NET MAUI CLI |
| .NET 全般 | .NET skills リポジトリ（プロファイリング、デバッグ、C# など .NET のスキルすべて） |

自分で作ることもできます。.NET にはプラグインのエコシステムがあり、.NET MAUI 専用のエージェントスキルプラグインを、プラグインまたは CLI でインストールできます。MAUI のプラグインには、データバインディング、依存性の注入、セーフエリア、Shell ナビゲーション、テーマ設定などのベストプラクティスが含まれると説明されました。

### 5.6 アプリ内にエージェントを置く方式

Mobile Canvas とスキルの次に、モバイルスタック全体にエージェント向けに最適化された AI ツールチェーンがあればどうなるか、という話に進みます。この方式でも、エージェントは MCP 経由でやり取りする点は Mobile Canvas と同じです。違いは、アプリの内部に、そのアプリのフレームワーク向けの小さなサーバーが動いていることです。このサーバーは、MCP サーバーとも通信する **ブローカー** を介して公開されます。

この方式では Mobile Canvas ができることはすべてでき、さらにビジュアルツリーとすべてのコントロールが見えます。コントロール、ナビゲーション、フレームワークを理解しているため、トークンの効率、性能、速度の面で有利だと説明されています。

その例が **.NET MAUI AI ツールチェーン** です。構成要素は次のとおりです。

* MAUI CLI
* James が見せたスキル
* アプリ内エージェントと MCP サーバー（DevFlow と呼んでいる）
* アプリ内のインスペクター

.NET MAUI の開発者は、エージェントパッケージをインストールして初期化し、ブローカーを起動して接続するだけで使えます。これは手動でも、エージェントに任せても構いません。

### 5.7 他のプラットフォームとツール

発表の最後に、次のものが紹介されました。いずれも詳しいデモは行われていません。

* **AlohaKit**：同じ .NET MAUI チームによるもので、.NET MAUI 以外にも対応し、プラットフォームごとの連携で同様の機能とコントロールを提供する。
* **Windows App CLI**：Windows アプリの作成とデバッグ、エージェントによる操作のために、パッケージングなどの機能を提供する。アプリを実行するコマンドにも触れているが、発話が聞き取りにくく、内容は確認できません。
* **Maui Sherpa**：どのアプリでも使える開発支援ツール。エミュレーターやシミュレーターの管理、ビジュアルツリー、SDK、プロビジョニングプロファイル、GitHub Actions へのアップロードなどを扱う。デモの時間はなく、最後のリンク集で案内すると述べている。

## 6. デモ・手順

### 6.1 デモ 1：iOS の Swift アプリで Mobile Canvas を使う（Katie）

背景は、Theater Log の課題として、「保存ボタンが無効になる前に、レビューと会場の文字数制限を説明する」ことが開かれている状態です。James と Katie はすでにその変更を実装済みで、Copilot が何を変更したかはセッションのチャットで確認できます。残る作業はテストです。

1. GitHub Copilot アプリで、Katie のマシンの Swift アプリ（Theater Log）を表示する。
2. 左側の「Customize（カスタマイズ）」で「mobile canvas」を検索し、画像付きのプラグインを選ぶ。このプラグインには MCP とキャンバスの両方が含まれる。
3. セッションに戻り、キャンバスの領域で、すでに開いてある Mobile Canvas のタブを表示する。実際のシミュレーターが動いており、スクロールやクリックができる。
4. 用意しておいたプロンプトを送る。内容は、「この機能を実装したので、Mobile Canvas でテストし、途中でスクリーンショットを撮ってください」という趣旨である。
5. エージェントが動き出し、スクリーンショットを送ってくる。戻ってきても作業の記録が残る。
6. エージェントは Mobile Canvas を通じて画面上の要素を調べ、必要に応じて座標も使い、デバイス上を移動していく。シミュレーターが、人がテストするときのように動く。
7. 映画を記録する画面に到達し、文字数の制限を試す。以前は出なかった警告が表示され、実装が動作していることが確認できる。

> 補足：このデモ中、Katie は、Mobile Canvas を設定してあれば、実装しているときにエージェントが自然に自分の修正や機能をリアルタイムでテストするようになる、と説明しています。

### 6.2 デモ 2：Windows の VS Code で Android アプリを操作する（James）

1. James は Windows 上の VS Code にいる。iOS のシミュレーターは使えないが、Android のエミュレーターが揃っている。拡張機能として、バナナクリーム色のテーマを入れる「Bananify for VS Code」も入れてある。
2. 拡張機能の画面から、Mobile Canvas をインストールする。この拡張機能は、.NET MAUI チームのエンジニアリングリードの方（聞こえた名前は Rep。音声認識の都合で表記が確定できません）が作ったもので、非公式だが公式に近い位置づけと説明している。インストールするとプラグインとカスタム拡張機能が入る。
3. プロンプトを貼り付ける。内容は、設定に入り、アプリ用に作っている新しいテーマを有効にして、という趣旨である。
4. エージェントは Mobile Canvas の機能を確認し、許可を求めてくる。James は「許可」と「有効化」を選ぶ。VS Code にはキャンバスとネイティブ拡張機能の両方があり、両方をインストールしているため、エージェントは両方を同時に使う。
5. エージェントは UI ツリーを読み、デバイスの要素を確認して、アプリ内でタップとスワイプを繰り返す。新テーマの設定は、リアルタイムでスワイプするところを見せるために、ページの一番下に置いてある。
6. 新テーマの設定を隠しているように見える、と Katie が冗談を言うと、James は子どもの頃に作った GeoCities のサイトに着想を得たテーマだと答える。最後にもう一度スワイプしてテーマを起動すると、そのテーマが表示される。

> 補足：エージェントは、開いているエミュレーターを見ることも、その場で起動することもできると説明されています。

### 6.3 デモ 3：.NET MAUI のスキルとカスタムエージェント（James）

1. ターミナルを開き、.NET MAUI CLI がインストール済みであることを示す。`maui ai init` を実行すると、マシンをスキャンして、インストールできる項目の一覧が出る。
2. 一覧には、アプリのアーキテクチャ、アクセシビリティ、現行 API、プロジェクト構造、UI パターン、ユニットテストなどのスキルと、エキスパートレビュアーというカスタムエージェントが含まれる。
3. `maui ai --help` で、使い方を確認する。Claude、VS Code、Copilot CLI など環境ごとに実行でき、スキルの一覧表示、特定項目の初期化、利用可能な MCP サーバーの追加などができると分かる。
4. `maui ai init` に環境として Copilot CLI を指定して実行する。VS Code の中にいるが、GitHub Copilot 用のフォルダーにインストールされ、どこで使っても有効になるためだと説明している。作成されるスキルとエージェントの一覧が表示され、「はい（yes）」で確定する。
5. プロジェクトのスキルのフォルダーを開くと、カスタムスキルが読み込まれている。チームの他のメンバーも同じスキルを使える。
6. 中身を確認する。アクセシビリティとワークフローのスキル、フォントやアセットの扱いを示すプロジェクト構造のスキル、Community Toolkit についてチームとしてのベストプラクティスが書かれている。カスタムエージェントには、コードレビュー担当（開発フローの一部）があり、レビューの判断の仕方が書かれている。
7. 新しいチャットを開き、エージェントを選択する。組み込みの通常のエージェント、エキスパートレビュアー、他のマシン全体で有効なスキルとカスタムエージェント（Impeccable Design など）が出る。スラッシュコマンドでも呼び出せ、UI パターン、ユニットテスト、プロジェクト構造、アプリのアーキテクチャがある。これは Copilot の連携で一般的なやり方である。
8. 「maui」から UI パターンのスキルを呼び出し、アプリ画面で「Watched」と「Wish list」が上で切れていることを伝え、UI パターンの観点でレビューを依頼する。スクリーンショットを撮り、矢印も描いて添付する。
9. エージェントがスキルを読み込む。UI パターンやアクセシビリティなどのスキルは、「アクセシビリティをレビューして」と言えばエージェントが自動で呼び出すこともできる。スキルは必要なときだけ読み込まれるため、すべてをカスタム指示に入れて肥大化させずに済むと説明している。
10. 続けてアクセシビリティの確認も依頼すれば、キューに入れておくことで、終わった後にアクセシビリティのスキルが呼び出される。
11. もう 1 つのセッションを立ち上げ、エキスパートレビュアーのカスタムエージェントを選び、追加した「Retro」テーマの全面的な監査と概要を依頼する。.NET MAUI チームのガイドラインに沿って動く。James は、作った人たちより自分のほうが詳しいふりはしないと述べている。権限は手動の承認にしてあるため、何度も確認が出る。
12. 元のチャットに戻ると、アクセシビリティのレビュー用スキルを必要なときに読み込んだうえで、画面の切れを修正し、レビューを行っている。何を使い何を使わないか、ScrollView の検査などの情報と、検証チェックリストが出力される。

### 6.4 デモ 4：.NET MAUI AI ツールチェーンのコマンドとインスペクター（Katie）

1. ターミナルと、右側にエミュレーターを表示する。ターミナルのコマンドだけでアプリを操作できることを示す。
2. ステータスを確認する。右側に Android エミュレーターがあり、ブローカーは起動済みである。
3. ビジュアルツリーを取得する。実際の MAUI のコントロールが見えるので、操作がしやすい。
4. 「settings（設定）」という特定のコントロールを問い合わせ、見つかったのでタップする。エミュレーターが設定ページに移動する。
5. テキストでも問い合わせる。サンプルの映画と友人のテキストを探すと、そのページにあるため見つかる。
6. サークルの画面に戻る。
7. 視覚的に操作できる組み込みインスペクターに切り替える。ビジュアルツリーが表示され、要素にカーソルを合わせて確認できる。操作や、要素の非表示と再表示もできる。
8. インスペクターでは、特定の要素の検査、テストの記録と後からの読み込み、アプリのデータ（ログ、設定、センサー、ファイル）も見られる。ファイルとして Theater Log のデータベースが確認できる。
9. 以前に記録しておいた、設定を巡るテストを読み込んで再生する。エミュレーターがそのテストを順に実行する。ターミナルで使うのと同じコマンドが実行されるが、コマンドを覚えなくて済む、と説明している。

### 6.5 デモ 5：Copilot CLI がアプリ内エージェント経由でテストする（Katie）

ごく短いデモとして説明されています。

1. Copilot CLI を開く。エミュレーターには James のテーマが表示されている。
2. 公開前に、アクセシビリティが基準を満たしているかをテストしたいと考え、エージェントにそのテストの流れを任せるプロンプトを送る。
3. エージェントがスキルを呼び出す。スクリーンショットや座標の推測は不要で、DevFlow と、ブローカーの機能で、実際のツリーを取得する。
4. 接続先のエージェントの一覧が表示され、特定のエージェントに接続していることが分かる。
5. 最初から最後まで流れを分析し、実行する。アプリの見た目と操作方法を正確に知っているので、推測がなく速い。MAUI のツリーを読んで理解し、アプリ内をタップして進む。
6. 最後にレポートを出す、と説明している（レポートの内容は発話では確認できません）。

> 補足：Mobile Canvas との違いは、アプリの内部でエージェントが動いている点で、これが機能を正確にテストするうえで重要だと説明されています。

## 7. 注意点・発表者の気付き

* Mobile Canvas はアプリのコードを変更しないため、アプリの種類は分かりません。アクセシビリティの識別情報（自動化 ID など）があればそれを使い、無ければ座標になります。アクセシビリティのフラグを整えるほど精度が上がるという経験が語られました。
* スキルは必要なときだけ読み込まれます。すべてをカスタム指示に入れると肥大化するため、スキルのほうが的を絞れる、という説明です。
* 権限を手動の承認にしているので、デモ中は確認が頻繁に出ました。
* Mobile Canvas の拡張機能は、発表者の説明では .NET MAUI チームのエンジニアリングリードによる、非公式だが公式に近いものです。
* DevFlow を使う方法は .NET MAUI 向けの例として紹介されています。他のフレームワークの対応範囲は、AlohaKit などの名前が挙がっただけで、詳細は発話では確認できません。
* 時間の都合で、Maui Sherpa のデモは行われていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。ここでのお客様は、モバイル・デスクトップアプリの開発チームです。

* エージェントが、機能の実装やバグ修正が本当にできたかを、推測せずに実機に近い環境で確認できる。
* Mobile Canvas は、アプリのコード変更なしに、どの言語・フレームワークのアプリでも使える。
* スキルは、チームが共有でき、フレームワークの専門家が作ったベストプラクティスに沿った実装とレビューが得られる。必要なときだけ読み込まれる。
* アプリ内エージェント方式は、ビジュアルツリーとコントロールが見えるため、トークンの効率、性能、速度が上がる（発表者の説明）。
* インスペクターで記録したテストを再生でき、ターミナルのコマンドを覚える必要がない。

## 9. まとめ

エージェントに推測させず、動作中のアプリを直接見せて操作させるのが、このセッションの主題です。まず Mobile Canvas で、どのアプリでもコード変更なしにテストできます。次にスキルとカスタムエージェントで、.NET MAUI などのベストプラクティスを必要なときに与えます。最後に、アプリ内エージェントとブローカー、インスペクターで、ビジュアルツリーに基づく高速なテストの流れを実現します。発表者は、検査、操作、変更、再生、検証のループを閉じることを目標に挙げ、関連ツールのリンクを最後に示しました。
