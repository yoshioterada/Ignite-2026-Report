### 5.1 Bradesco の紹介

Felipe によると、Bradesco はラテンアメリカ最大級の金融機関の 1 つで、約 100 年の歴史があります。取引のほぼ 100% が、モバイルアプリやインターネットバンキングなどのデジタルチャネルを通ります。技術面の規模は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| データセンター | 3 つの大規模なもの |
| クラウドサービスプロバイダー | 4 社 |
| 技術系の従業員 | 12,000 人以上 |
| アプリケーションの標準プラットフォーム | Kubernetes |

Kubernetes を選ぶ理由として、自己修復、高可用性、設計段階からのスケーラビリティに加え、**プラットフォーム間のポータビリティ（可搬性）**が「秘伝のタレ」だと述べています。現在は、メインフレームやレガシーから、分散コンピューティングを経て、Kubernetes へ寄せて標準化する動きの途中です。

### 5.2 AI の提供形態：Bridge、Bia、Bia Tech

AI の提供は 2 つの柱に分かれています。

- **Bridge**：AI のバス（サービス層）にあたる基盤です。企業間（B2B）と企業から顧客（B2C）のサービス向けに、エージェントのデプロイを標準化し、ガードレールと品質保証を組み込んでいます。
- **Bia**：顧客と会話する AI エージェントで、約 10 年の歴史があります。支店、モバイルアプリ、インターネットバンキングなど、あらゆるチャネルにいます。WhatsApp からも使え、即時決済や口座残高の確認ができる、という例が挙げられました。

もう 1 つが **Bia Tech** で、技術者向けのペルソナです。事業向けと技術者向けは別のペルソナのため、2 つのチームと 2 人のマネージャーで分けて提供しています。Bia Tech のユースケースとして、大規模な障害が起きたときに、コマンドセンターがエージェントと対話し、直近数時間に実施した変更に原因がないかを調べられる、という例が挙げられました。VS Code で Copilot を設定する用途にも触れられています（詳細は語られていません）。

インフラの面では、Bridge をクラウド上で標準パターンとして提供しています。エージェントとやり取りするためのアクセスゲートウェイを持ち、モデルに対しては、Microsoft の複数のリージョンをまたいでラウンドロビン（順番に振り分ける）を行います。1 つのリージョンで大規模障害が起きても、高可用性の設定により自動でフェイルオーバーし、そのリージョンを無効化しても、サービスは稼働し続けます。Bia と Bia Tech は障害を感じない、という説明です。

### 5.3 課題：レガシー基盤とクラウド移行

Bradesco にはプライベートクラウドがあり、取引の大半はクラウドを通りますが、コアとなる一部の製品はオンプレミスに残っています。これをクラウドへ移し、チャネルとサービスを同じ場所に置く、ドメイン駆動設計の形にしたいと考えています。ただし、開発チームは新機能の開発や、中央銀行からの法的要求への対応で多忙です。

Felipe は、大規模な環境ならどこにでもある課題として、次を挙げました。

- 知識が失われている
- マイクロサービスとレガシー基盤の間に依存関係が多く、どこから始めればよいか分からない
- 判断がデータに基づかず、感覚になっている

過去には、クラウドへ移そうとして失敗した経験があると、率直に話しています。正しい情報が無いため戦略が間違い、クラウドとオンプレミスの間に循環した依存関係を作りました。その結果、再試行が増え、統合層に負荷がかかり、障害につながっています。リバースプロキシを置いてサービスを移し始めたものの、障害を経験して止まり、戦略を考え直すことになりました。

### 5.4 エージェントを使った移行の進め方

知識が足りないことから、AI に整理させる方針をとりました。流れは次のとおりです。

1. **ディスカバリー**：持っている情報をすべてエージェントに渡す。Prometheus、Dynatrace、パイプライン、設定（config map）などを含み、レガシー基盤にどんなアプリケーションがあるかの地図を作らせる。
2. **波（ウェーブ）の設計**：アプリケーション間の関係から、移行の単位をエージェントと一緒に設計する。1 つの波は、2 個、9 個、10 個、20 個などのマイクロサービスで構成される。一括ではなく、波ごとに、昔ながらのウォーターフォール方式で進める。コードのリファクタリングも波ごとに行い、クラウドへのデプロイも波ごとに整理して進める。
3. **価値の流れ（バリューストリーム）による分類**：アーキテクチャの種類で分け、難易度別に整理する。

| バリューストリーム | 対象 |
| --- | --- |
| 容易 | ステートレスなアプリケーション |
| 中程度 | イベント駆動のアプリケーション |
| 難易度が高い | ステートフル。SQL と NoSQL を問わず、データベースへの依存が大きく、データが移行の最大の課題 |

分類に使った親和性（アフィニティ）の基準は、サービス間の呼び出し関係、同じクラスター内か外か、データベースとの関係、Service Bus や PubSub のような統合です。さらに、各マイクロサービスの責任者のマネージャーを特定し、アーキタイプ（ステートレス、ステートフル、イベント駆動など）を付けました。

この作業の副産物として、**使われていないマイクロサービスが見つかり、停止して効率とコストを改善**できました。移行のために作ったプロキシは、不要になったら廃止し、電源も落とします。

エージェントには、開発パターンのドキュメントだけでなく、インフラの標準、パートナー、ガードレール、アーキテクチャの原則も渡しています。具体的な変換は次のとおりです。

- Java 8 から Java 21
- WebSphere Liberty から Spring Boot
- モノリスからマイクロサービス
- 巨大なデータベースの分解（AI とエージェントの助けを使う）

クラウドの標準化によって、セキュリティが高まり、レガシーに残っていた問題も解消できたと述べられています。

### 5.5 Java アプリケーションのモダナイゼーション（デモ）

Bruno が、Bradesco のような取り組みの一例として、1 つのマイクロサービスをモダナイズするデモを見せました。題材は、銀行のファイナンシャルアドバイザーとの面談を予約する Java アプリケーションです。デモの詳細は 6 章に書きました。Bruno は、IDE の GitHub Copilot のモダナイゼーション機能に加え、同じ機能のコマンドラインツール（modernize CLI）があり、数百のプロジェクトを一括で自動化できると説明しています。1 対 1 で丁寧に進めたい重要なアプリには IDE、テスト、統合、品質保証の保証水準が高い重要度の低いサービスには、CLI でのバッチ処理が向く、という使い分けです。

継続的なモダナイゼーションについては、GitHub のモダナイゼーションエージェントの CLI を使うと、CI/CD に組み込め、レポートやプルリクエストとしてチームに届けられ、プロジェクトを継続的に最新へ保てると述べられました。

### 5.7 目標アーキテクチャと仕様駆動の流れ

目標アーキテクチャでは、オンプレミスとクラウドの統合層にかかっていた負荷を減らします。ドメイン駆動設計の観点でクラウドへ移すことで、サービスに必要な高可用性を実現できる、というのが Felipe の考えです。Kubernetes を使うクラウドネイティブな構成になる、と説明されています（細部は発話が不明瞭です）。

エージェントを使った進め方は、**仕様駆動の流れ**です。評価（アセスメント）、仕様の作成、計画（アーキテクチャの出力を含む）、実装、検証の順で、常に人間が入ります。エージェントが作った新しいアーキテクチャとコードが妥当かは、チームの検証が必要だと説明されました。

### 5.8 移行の戦略と注意点

Felipe が語った戦略の項目は次のとおりです。

- ランタイム、統合、セキュリティ、設定を調べるディスカバリー
- カナリアデプロイのための Argo CD
- アプリケーション間のコントラクト（契約）のマッピング。クラウドからオンプレミスを呼ぶ依存があるため、新しいエンドポイントへの経路の付け替えを確認する
- 最も難しいのはデータベース。レプリケーションを設定し、カナリアデプロイを行ってから、データベースのフェイルオーバーを行う
- カナリアによるローリング更新を常に行うため、障害や API の応答の遅れは起こりうる。API ゲートウェイでレート制限などの適切なポリシーを設け、バックエンドが想定外に過負荷にならないよう保護する
- デプロイ後の検証

1,000 を超えるマイクロサービスの情報を手作業で関連付けて計画することは非常に難しく、エージェントがその重い作業を引き受けた、と説明されています。したがって AI は、コードのリファクタリングだけでなく、既存のデータを意味のある形に整理することにも効果があった、というのが彼の評価です。

判断の例として、時間の都合で、IBM MQ を Azure Service Bus へ移すことは選ばず、Kubernetes 上のステートフルセットとして IBM MQ を維持しました（書き起こしでは「BMQ」と聞こえますが、IBM と述べています）。SDK とコードの変更が増え、すでに複雑な移行をさらに複雑にするためです。一方、統合部分の一部は、移行と刷新以外に選択肢がありませんでした。

### 5.10 インフラ担当としての教訓

Felipe は、自分は AI や開発者ではなくインフラ担当だと前置きして、次の教訓を挙げました。

### 5.11 Microsoft の関連サービスの紹介

Bruno は、Bradesco が Microsoft のエンジニア（書き起こしでは「four deployed engineers」と聞こえ、表記が確定できません）と共に得た学びを、製品に取り込んできたとして、次を紹介しました。

**Azure Catalyst**：今週の Ignite で発表された、モダナイゼーション、移行、アップグレードのツールを 1 つにまとめたプラットフォームです。アプリケーションだけでなく、データとインフラも対象です。VM、コンテナー、Kubernetes、サービス、メッセージキュー、SQL Server、DB2、Oracle など、システムを構成する要素全体の刷新を支援すると説明されました。

**Azure Resource Manager MCP サーバー**：今週発表されました。Azure MCP サーバーとは別のもので、リソースの作成、管理、アップグレードまで、運用チームと同じように、自社のワークフローに沿って自動で行える、より深い機能を持つと説明されています。Felipe の取り組みと同じことを、これで実現できるという位置づけです。

**Microsoft Foundry のホステッドエージェント**：エージェントを作り、デプロイし、データに接続し、最適化し、さまざまなチャネルへ公開できます。Copilot Studio のようにプロンプトで定義するエージェントだけでなく、独自のコードを持ち込めると述べています。Microsoft Copilot Harness SDK で、自社の統合、データソース、ルール、業務ロジックを組み込んで開発し、デプロイ、管理、オーケストレーション、監査、監視をこの環境で行えます。インフラ運用、開発、Q&A、Bia のような顧客向けの業務エージェントのいずれにも使える、と説明されました。

**Copilot Fusion**：直前に追加した内容と前置きがありました。10 月から提供されており、Microsoft がルーターを提供し、与えられたタスクを、ベンチマークで見つけた最適なモデルでオーケストレーションする仕組みです。今週共有された terminal bench 4.1 のベンチマークでは、最大の推論努力量の設定で **解決率が 71%** となり、Opus 5.5 や Fable 5.2 といった先行モデルより **5.4%** 高いと述べられました。コストは、Fable より 88% 低く、Opus 5.5 より 57% 低いと語られています（発話の中で対象の言い直しがあり、この対応は聞こえた範囲での記載です）。利用者はモデルの選定やベンチマークの手間をかけず、Copilot Fusion を選べば、同じ品質を低コストで、継続的な進化とともに得られる、という説明です。

### 5.12 Q&A

質問は 2 件ありました。

**質問 1：オンプレミスからクラウドへのリフト＆シフトで、複数のサブスクリプションと環境をどう管理したか**

Felipe は、ランディングゾーンがハブ＆スポーク型であり、各スポークが機能ドメインに対応すると答えました。各サブスクリプションに標準化したプラットフォームをデプロイし、サブスクリプションごとにチャネルやトランザクションといった機能ドメインを割り当てています。ドメインごとにマルチテナントの Kubernetes クラスターを持ち、集中型の単一障害点となるプラットフォームはプライベートクラウドに置いて、クラウド側は機能ドメインの親和性に応じて分散させる、という説明です。

**質問 2：AS400 や RPG のような、より複雑なシステムの移行を試したか**

Felipe は、メインフレームを刷新するプログラムがすでにあり、同様の戦略を計画中だと答えました。メインフレームは集中型のトランザクションなので、機能を分解してリファクタリングする必要があり、何でも意味があるわけではない、という見解です。銀行の勘定元帳（レジャー）から始めるのではなく、課題がある場所から始めており、それがプライベートクラウドです。そのため、簡単なところから始めて、最終的にコアのメインフレームへ到達する進め方をとります。レガシーの WebSphere アプリケーションも、同じ戦略でクラウドへ移し、マイクロサービス化する対象として検討中とのことです。AS400 や RPG 自体については、発話では触れられていません。

## 6. デモ・手順

画面を使ったデモがあります。Bruno が、Visual Studio Code の GitHub Copilot のモダナイゼーション機能で、Java アプリケーションのセキュリティ問題の修正とアップグレードを行いました。画面の細部は音声からは確認できません。語られた順序は次のとおりです。

1. **題材の確認**：ファイナンシャルアドバイザーとの面談を予約する Java アプリケーションを見せる。通常のフロントエンドがあり、Bruno Borges が Jordan Lee と本日午後 1 時に予約し、確認すると、予約が表示される。
2. **前提の説明**：バックエンドは Java 8 と Spring Boot 1 で動くレガシー。2021 年のクリスマスに起きた Log4j の問題を例に、セキュリティの問題があるはずだと話す。
3. **スキャンの実行**：IDE で GitHub Copilot とモダナイゼーションのツールを使い、プロジェクトのセキュリティ問題をスキャンする。Copilot はプロジェクトを理解し、Maven、Gradle、.NET などの技術スタックを判別し、依存関係すべてについて CVE の勧告を適切な情報源で調べる。数秒から数分で、数時間はかからない。
4. **事前に取得したレポートの確認**：時間の都合で、登壇前に実行したレポートを見せる。3 件のセキュリティ問題があり、CVE が見つかっている。その 1 つは log4j 1、もう 1 つは Spring Boot 関連。
5. **アップグレードの実行**：ランタイムとフレームワークのアップグレードをクリックする。最新バージョンへ移行する。Java 8 から 21（または 25）への移行では、互換性のない依存関係が出て、連鎖的に別の依存関係の更新や、新しい API への対応、古い API の削除が必要になる。つまり単なるアップグレードではなく、モダナイゼーションのプロジェクトになる、と Bruno は説明した。実行中に権限の確認が出る。
6. **結果の確認**：修正済みのブランチに切り替えて確認する。Java のバージョンは 21 になっている。Log4j は残っているが、最新の Spring が使われ、古い版ではない。再度評価すると、セキュリティ問題は 1 件だけで、これは数値型の変換に関する潜在的な問題であり、これもエージェントが修正した。
7. **動作の確認**：修正版でアプリケーションを起動し直す。フロントエンドは Node.js、バックエンドは Java と分かれていて、同じフロントエンドのまま、バックエンドだけが刷新されている。データベースは実際のものではなく、例示用である。

Bruno は、これが数分で完了したこと、数百のマイクロサービスへ適用し、SDLC の中で継続的に使うことが、技術的負債を避けることにつながると述べています。

## 7. 注意点・発表者の気付き

- 知識が失われ、依存関係が見えない状態で、感覚的な判断により移行を進めると失敗します。Bradesco 自身が失敗し、クラウドとオンプレミスの循環した依存関係で再試行が増え、障害になった経験が語られました
- 一括移行ではなく、自己完結したブロック（波）で移し、循環した依存関係を作らないことが重要です
- データベースの移行は最も難しい部分で、レプリケーション、カナリアデプロイ、フェイルオーバーの順で慎重に進めます
- カナリアによるローリング更新でも、障害や応答遅延は起こりえるため、API ゲートウェイでレート制限などを設け、バックエンドを保護します
- 時間の都合で、IBM MQ の Azure Service Bus への移行は見送りました。複雑さを増やさないための判断です
- エージェントの出力は、人間が必ず検証します
- Java 8 から 21 への移行は、依存関係の連鎖があり、単なるバージョンアップではありません
- Felipe の成果の数値は、手作業との比較による見積もりです
- Copilot Fusion の数値は、発表で共有された terminal bench 4.1 のものです。評価条件の詳細は語られていません
