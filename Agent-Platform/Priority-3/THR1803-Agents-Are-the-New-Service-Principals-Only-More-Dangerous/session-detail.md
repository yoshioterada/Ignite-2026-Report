# THR1803 Agents Are the New Service Principals. Only More Dangerous

## 1. はじめに

このセッションは、AI エージェントを「新しいサービスプリンシパル」とみなして、承認・権限・監視・廃止の観点でガバナンスを考える約 22 分の発表です。発表者の Martina Grom 氏は、エージェントの ID（agent identity）に権限が付いていないのに、Foundry のエージェントが**権限のないはずの HR データを返してしまう**デモを見せ、「ID と権限を個別に確認しただけでは安全とは言えない」ことを示します。

核心は、エージェントの安全性を「ID」「権限」「委任」「ツール」「データ」の組み合わせ（発表者の言う effective reach、実効的な到達範囲）で見る、という考え方です。後半では、エージェントを止める方法（disable と block の違い）、ガバナンスのためにいくつものポータルを見に行く必要がある現状、承認前に確認すべき 3 点を紹介します。

## 5. 発表内容の詳細

### 5.1 サービスプリンシパルと agent identity の比較

発表者は、サービスプリンシパルと agent identity の違いを小さな表にまとめて説明しました。両者は似ていて、どちらもアプリケーションのワークロードであり、同じオブジェクトモデルに基づいています。違いは次のとおりです。

| 観点 | サービスプリンシパル | agent identity |
| --- | --- | --- |
| 資格情報 | 発表では明言されていませんが、agent identity と対比して語られています | **資格情報を持たない**。発表者は「純粋に安全（purely safe）」と表現 |
| 資格情報の保持者 | 発表では触れていません | **agent blueprint** が保持する |
| 寿命 | 通常はエージェントより長い | 数秒で終わることもある。生成され、仕事をして終了し、次回また起動される |

blueprint は、資格情報を保持し、データやアクセスを継承させる親にあたります。1 つの blueprint の下に複数の agent identity を持てる、親子の関係です。

次に発表者は、ID は始まりにすぎないと述べます。エージェントは自分自身の ID を持ち、さらに**委任されたアクセス権**を持てます。例えば、エージェントを Work IQ に接続すると、そのエージェントはユーザー自身の権限を持ち、ユーザーがアクセスできるデータにアクセスできます。さらに、エージェントがどのデータに触れられるか、どの権限があるか、接続するツールは何か、も確認対象です。

そこで発表者が示したのが「**effective reach（実効的な到達範囲）**」です。次の 5 つで構成されます。

1. identity（ID）
2. permissions（権限）
3. delegation（委任）
4. tools（ツール）
5. data（データ）

発表者は、これは 1 か所だけ見れば済むものではなく、ID だけを確認しても安全ではないと強調しています。また、これは Microsoft の公式ガイダンスではなく、発表者自身がエージェント向けに作った「ガバナンスのフットプリント」だと断っています。

### 5.2 デモの構成

デモの構成は次のとおりです。

- Foundry のエージェントが 1 つあり、ツールとして Azure Blob Storage を使う。
- Blob Storage には、**財務（finance）データ、HR データ、給与（payroll）データ**が置かれている。
- プロジェクトのマネージド ID（project managed identity）がある。
- Foundry のエージェントには、専用の agent identity がある。blueprint が資格情報とアクセス制御を持つ。

発表者は、財務部門で働いているのだから、HR データにはアクセスできないはずだ、という前提を置いています。

### 5.3 デモ 1：Entra admin center で見た「問題のない」状態

発表者は、Entra admin center で、事前に作成したエージェント ID（Ignite demo AI、Contoso finance assistant）を示しました。確認した点は次のとおりです。

- **スポンサー（sponsor）**がいる。スポンサーは、そのエージェントに責任を持つ業務側の人で、IT 担当者である必要はありません。
- **オーナー（owner）**は 2 人（デモでは同一人物）。オーナーは技術担当の IT 側の責任者で、オーナーを追加できる立場だと説明しています（この部分の発話は聞き取りにくい箇所があります）。発表者は、通常はスポンサーとオーナーは別の人になるとコメントしています。
- エージェントの ID には、権限も、ロール（発話は "entry roles"。音声認識の都合で正確な語は確定できません）もない。「すべて問題なさそうに見える」状態。

次に blueprint を見ました。blueprint は複数のエージェントを持てます。1 つの blueprint に複数のエージェントを接続でき、agent identity は、データ、アクセスなどを継承し、トークンを使います。

資格情報（credentials）のところは、アクセス制御の場所だと説明しています。

- 証明書（certificates）：なし
- クライアント関連の資格情報（発話は "client access"）：なし
- **フェデレーション資格情報（federated credentials）**：あり。これが Azure Blob Storage へのアクセスに使われている

発表者は、これでほかの誰もそのエージェント blueprint としてサインインできず、セキュリティ上は完璧に見える、と述べています。

### 5.4 スライド：Entra の構成要素とガバナンスルール

続いて、スライドで Entra 上の構成を整理しました。

- **blueprint 層**
- **agent 層**
- **ガバナンスルール**

ガバナンスルールについて、発表者は、Microsoft では現在スポンサーは必須だがオーナーは必須ではない、と述べました。ただし「すべてのエージェントにオーナーを置く」ことを推奨しています。Microsoft Teams、グループなど、ほかのものでも行われるガバナンスルールと同じだという位置づけです。

**最小権限（least privilege）**については、スコープを絞ったアクセスという観点で、先ほど確認したとおりエージェントには権限がなく、継承されたものもありません。一方で、ツール経由でより広い操作ができ、agent identity は Blob Storage と特定のリソースにアクセスできます。発表者は、「権限の観点では全部確認したが、**アクセスの連鎖全体は確認していない**」と指摘し、デモ 2 につなげました。

### 5.5 デモ 2：Foundry のエージェントが HR データを返す

Foundry で、財務アシスタントのエージェントを示しました。数日前に追加したもので、指示（instruction）が設定されています。ツールは Blob Storage を読むものが 1 つだけで、ほかのツールや Web grounding は接続していません。発表者は「完全に安全なエージェント」と呼んでいます。

プロンプトは、手で入力する代わりに、スタータープロンプトの欄に追加しておいたものを使いました。

1. **1 つ目のプロンプト**（「財務の担当者として、財務の権限のデータを読みたい」という趣旨）：エージェントが Blob Storage を照会し、財務部門のデータを返しました。ここまでは想定どおりです。
2. **2 つ目のプロンプト**（給与（payroll）と HR のデータを読む）：発表者は会場に「読めると思うか」と尋ねました。結果は、データは同じ Blob Storage にあるが、アクセス権がないので読めませんでした。「構成は完璧なまま」という状態です。なお、このプロンプトで拒否された対象が給与データだけか HR も含むかは、音声からは確定できません（次の 3 つ目で「まだ HR データがある」と言っているため）。
3. **3 つ目のプロンプト**（HR データ）：会場に再度「アクセスできると思うか」と尋ねたうえで実行すると、**今度はデータが返ってきました**。

発表者は、すべて正しく構成したのに、と述べています。エージェントに権限はなく、ストレージ側の権限だけを設定していた、という前提です。

### 5.6 原因の確認

原因として発表者が説明したのは、**プロジェクトにアクセスできるマネージド ID が、そのデータにアクセスできていた**ことです。確認の流れは次のとおりです（画面の細部は音声からは確認できません）。

1. Azure で、ロールの割り当てを確認する。マネージド ID が Ignite demo にアクセスできるかを調べると、最初の確認では「アクセスなし」と表示された。しかし HR データは見えている。
2. 同様の確認を、HR データについて行う。正しいサブスクリプション、Foundry プロジェクト、同じデモ AI へと進む。
3. その結果、**誰か（発表者は自分ではないはずと冗談を交えています）が、HR データを含むストレージアカウント全体にアクセス権を付与していた**ことが分かった。

発表者は、この状態では、別の agent を持つ blueprint が増えても、そのすべてが同じデータにアクセスできてしまうと説明しています。つまり、リソース側が持つアクセス権のせいで、意図した以上のデータにアクセスできてしまいます。

エージェント ID 側の許可された権限（granted permissions）も確認しました。エージェントには権限がなく（発話では "user content" の権限もない、と述べていますが、音声認識の都合で正確な語は確定できません）、アクセスもありませんが、それでもエージェントは HR データを返しています。発表者は、これが全エージェントのセキュリティチェックで確認すべき点だと述べました。

発表者は、Cloud Shell でも同じ確認ができると説明し、エージェントにロールはなく、ほかへのアクセスもないと述べました（スライドかデモ画面かは音声から判別できません）。ここまでに確認した内容は次のとおりです。

- エージェントは、資格情報を通じて M365 にアクセスできる。
- エージェントは、Blob Storage を通じて Azure リソースにアクセスできる。
- エージェントは、外部システムにもアクセスできる（発話はここで途切れており、詳細は聞き取れません）。

「**個々は確認したが、組み合わせを確認していなかった**」。これが危険な点だ、と発表者は述べています。そのストレージにアクセスできるマネージド ID が残っていないかを確認しなければ、このようなシナリオにつながります。エージェントの権限と blueprint の権限だけを見るのでは不十分、ということです。

### 5.7 ガバナンスのサイロを増やさない

発表者はここで、「新しいガバナンスのサイロを作らないで」と呼びかけました。顧客からは「エージェントのガバナンスをするには、少なくとも 5 つのポータルを開かないと全体が見えない」と言われるそうです。そこで、確認すべき場所として次を挙げました。

| ツール | 役割（発表での説明） |
| --- | --- |
| Entra の agent ID と blueprint | エージェント ID と blueprint の確認 |
| Microsoft Purview | データアクセスとデータセキュリティのアクセスの可視化 |
| Defender | エージェントのセキュリティの監視。高リスクのエージェントや、意図した振る舞いをしていないエージェントを検知し、止められる場合がある |
| Agent 365 | これらすべての情報が流れ込み、可視性を高める場所 |

### 5.8 エージェントを止める方法

発表者は、「誰がエージェントを止められるか」を整理しました。

- **admin center でエージェントを無効化（disable）する**：発話は「entire admin center」で、どの管理センターかは音声認識の都合で確定できません。エージェントは見えなくなりますが、Foundry 側には残っているため、そちらで片付ける必要があります。Copilot には表示されなくなります。
- **blueprint を無効化する**：配下のすべての子エージェントも無効になるため、安全な側に倒せます。
- **条件付きアクセスによるブロック**：リスクのあるエージェントをブロックできます。ただし、高リスクな振る舞いを理由にブロックしても、**エージェントはテナント内に生き続けています**。条件付きアクセスだけで十分かどうかを考える必要があり、そのうえで、リスクのあるエージェントを無効化する必要があります。発表者は「高リスクのユーザーと同じ。ID は何であれ ID」と述べ、ブロックは無効化ではないと強調しています。

続けて、Agent 365 の画面で確認しました。M365 admin portal の Agent 365 で、Contoso finance agent を探すと、作成日時、作成者、agent ID などが一覧で分かり、そこから掘り下げられます。画面には、次の 2 つの別々の操作があると説明しています。

| 操作 | 発表での説明 |
| --- | --- |
| disable（無効化） | エージェントが使えなくなる |
| block（ブロック） | ブロックの理由を選べる。ただし、Copilot 内で使えなくなるだけ（Teams や M365 で使えない） |

## 7. 注意点・発表者の気付き

- **権限のない agent identity でも、ほかの経路でデータにアクセスできます。** デモでは、プロジェクトのマネージド ID がストレージアカウント全体へのアクセス権を持っていたため、エージェントに権限がなくても HR データが返りました。
- ID の確認だけでは不十分です。ID、権限、委任、ツール、データの組み合わせを確認する必要があります。
- Work IQ のようなものに接続すると、エージェントはユーザーの権限でデータにアクセスできます。
- ブロックは無効化ではありません。条件付きアクセスでブロックしてもエージェントはテナント内に残り、Agent 365 の block は Copilot（Teams、M365）で使えなくなるだけです。
- エージェントを単に無効にするのは、ユーザーアカウントを無効にするだけに等しく、廃止（retirement）にはなりません。ライフサイクルの設計が必要です。
- スポンサーは必須だがオーナーは必須ではない、という現在の Microsoft の仕様に対し、発表者はすべてのエージェントにオーナーを置くことを推奨しています。

## 8. 利用者にとっての利点

このセッションは、導入メリットを紹介する内容ではなく、リスクと確認項目を示す内容です。発表で語られた「得られること」を挙げると、次のとおりです。

- Entra の agent ID、Purview、Defender、Agent 365 を組み合わせることで、エージェントのアイデンティティ、データアクセス、リスクを可視化し、必要なら止められる。
- blueprint を無効化すれば、配下の子エージェントも一括で無効にできる。
- Agent 365 で、エージェントの作成日時、作成者、agent ID を確認できる。

## 9. まとめ

発表者は次の 3 つを、エージェントを承認する前の確認事項としてまとめました。

1. **identity（ID）を確認する。**
2. **authority（権限）を確認する。**
3. **reach（到達範囲）を確認する。** エージェントがどのデータにアクセスできるか。

さらに、次の点を挙げています。

- 人に責任を持たせる。**スポンサーとオーナーの両方を追加する。**
- 封じ込め（containment）として、エージェントを廃止（retire）できるか考える。単に無効化するのは、ユーザーアカウントを無効にするだけと同じ程度でしかない。廃止の手順とライフサイクルのプロセスを考える。
- エージェント的な ID を ID として扱い、同時にシステムのようにも扱う（動詞は音声認識の都合で確定できません）。サービスプリンシパルのように動けることが、デモで示されたとしている。

発表者はスライドを GitHub リポジトリで共有すると述べています。Q&A は呼びかけられましたが、質問は録音上確認できませんでした。
