# THR1008 Building Real Agents

## 1. はじめに

このセッションは、規制報告（regulatory reporting）の自動化プラットフォームを作っている Datox の CTO が、「実際のビジネスで動くエージェント」をどう作ったかを、自社の経験から紹介する短い登壇です。エージェントの構成要素、エンタープライズ向けのリファレンスアーキテクチャ、Datox 独自の **コード駆動の抽出・処理（code-driven extraction and processing）**、エージェントのホスティング先、セキュリティの考え方、3 つのデモ、そして本番運用に向けた 5 つの原則が順に語られます。

中心となる主張は、**PDF や Excel などの入力ファイルを AI に直接渡して確率的に抽出するのではなく、ファイルのスキーマ（メタデータ）だけを AI に渡し、AI に抽出用のコードを書かせて隔離環境で実行する**というアプローチです。機微なデータを言語モデルに送らず、結果を決定的に検証でき、同じ質問に同じ答えを返せる、と説明されています。

このセッションでは、画面を使ったデモが行われています（6 章）。

### 5.2 エンタープライズ・リファレンスアーキテクチャ

次に、Datox がエンタープライズ向けソリューションを組み立てた構成例として、リファレンスアーキテクチャが紹介されます。上から順に、次の層です。

1. **エンタープライズアプリケーション**：BI の分析ツールや Web ポータルなど。
2. **統合レイヤー**：MCP ツール、データコネクタ、API 呼び出しなどで接続する層。
3. **エージェントプラットフォーム**：主要コンポーネントで、さらに 2 つに分けています。
   - **コントロールプレーン**：エージェントの管理、ID、モニタリング、デプロイ、セキュリティ境界を担当します。
   - **実行プレーン**：ドキュメントの理解、データの抽出、ワークフローの実行とオーケストレーション、ナレッジ、スキル、ツールの提供など、実際の作業が行われる場所です。
4. **AI Gateway とモデルガバナンス**：モデルへのアクセスを一元化し、全モデルを 1 つのインターフェースで管理します。利用状況の確認、上限の設定、ポリシーやガードレールの設定ができます。
5. **モデルエンドポイント**：Azure で許可されたモデル、サードパーティのモデル提供者、ローカルで動かす推論を持ち込めます。
6. **エンタープライズデータ層**：データベース、ストレージ、ベクトルストア、データカタログ、業務データが置かれます。

右側には、すべてのエージェント型プラットフォームを横断してセキュリティとガバナンスが適用される、という図になっています。

### 5.3 コード駆動の抽出と処理

登壇者が、時間の都合でこのアーキテクチャの中で特に取り上げたのが、Datox 独自のアプローチである **コード駆動の抽出と処理** です。流れは次のとおりです。

1. PDF などの入力ドキュメントを AI に直接送って確率的に抽出する代わりに、AI に送るのは **スキーマとファイルのメタデータ** です。Excel ファイルなら、列がいくつあり、行がいくつあるか、といった情報です。機微なデータは一切 AI に送りません。
2. エージェントは意思決定を助け、実際のデータを抽出するための **コード**（Python、SQL など、任意の言語）を生成します。
3. 生成したコードは、サンドボックス内の **隔離されたランタイム** で実行します。この生成コードを外部に送ることもありません。
4. 抽出コードが失敗したときは、常にリトライできます。
5. あらかじめ定義した検証（ルールや突合を書いたコード）をビジネスデータに対して実行します。

登壇者によると、この方法は複雑なデータを扱う他の場面、特にフィンテックでも再利用できます。Datox では RAG はまったく使っていないとのことです。コードを生成し、安全に実行し、決定的に検証することで、監査可能な結果を出せます。しかも再現性があり、同じ質問を何度しても同じ答えが得られ、精度はほぼ 100% だと説明されています。背景には、今日のモデルはコードを書けるほど強力なのだから、その場でコードを生成してすべてを処理すればよい、という考えがあります。

この仕組みで使っている技術は次のとおりです。

| 技術 | 用途（登壇者の説明） |
| --- | --- |
| OpenCode（OSS） | コードの生成と実行、ツールやエージェントスキルの適用 |
| Light LLM（OSS） | AI Gateway の境界として、複数モデルを 1 か所で管理 |
| Temporal（OSS） | 長時間かかるタスクと、耐久性のあるワークフローの実行 |
| Microsoft Foundry | クラウドでホストされるモデルの利用 |
| Microsoft Azure のクラウド基盤 | ストレージ、ID、モニタリング、データベース |

### 5.4 エージェントのホスティング先

「インフラはどうしているのか」という問いに対して、現在は 4 つの選択肢を使っていると説明されます。

1. **Microsoft Foundry**：LangChain などどのフレームワークで作ったエージェントのコードでも持ち込めます。Foundry がホストして実行してくれるため、インフラの面倒を避けたい場合に向きます。
2. **Azure Container Apps**：エージェントを自分で制御したい場合や、カスタムの API や MCP ツールを持ちたい場合の第一候補です。
3. **Azure Kubernetes Service（AKS）**：現在の Datox の主なアプローチです。エージェント単位でスケールできるためで、レポート生成やデータ分析のために 5 万を超えるエージェントを動かしているそうです。
4. **Foundry Local**：顧客が「solar AI」（音声認識の都合で表記が確定できません）を求め、すべてをローカル環境のオンプレミスで構築・デプロイしたがるため、Foundry Local でエージェントを顧客のサーバーに持ち込みます。

### 5.5 エージェントのセキュリティ

コーディングエージェントでデータを抽出する方式で、セキュリティ面の決め手だった点が次のように説明されています。

- **顧客データを AI に送らない**：最初のセキュリティ上のポイントです。
- **最小権限**：エージェントには読み取り専用など、必要最小限の権限だけを与えます。編集や更新の権限はありません。
- **実行レベルの隔離**：1 つのエージェントが使える CPU を制限し、ファイルシステム、ネットワークアクセス（どのネットワークの内側・外側で実行できるか）にも制限をかけます。
- **承認と監査**：機微な変更を扱う場面では特に重要で、実行時には人間の承認が必要です。

認可のチェックポイントは、次の 3 段階です。

1. **ユーザー ID**：Microsoft Entra ID でエージェントを識別し、ユーザー ID と結びつけます。生成されたレポートを最終的に承認するのは人間のユーザーだからです。
2. **権限によるエージェントのスコープ設定**：エージェントごとに異なる権限を与えます。
3. **自社 API によるツール認可**：エージェントがデータを保存したり、データベースを更新したりしたいときは、エージェントが直接行うことを許さず、自社の API とデータアクセスポリシーのルールを経由させます。

### 5.6 本番対応エージェントの 5 つの原則

最後に、登壇者は本番対応エージェントのための 5 つの原則をまとめています。

1. **AI のコントロールを一元化する**：使っているモデル、使った金額を把握し、ポリシーを適用し、チーム単位・顧客単位で予算上限を設定します。登壇者は、まずここから始めると述べています。
2. **すべての AI アクションに根拠を示す**：信頼度スコアはその一例です。Datox の顧客は信頼度スコアを好み、95% といった値を見ると、AI がデータに対して正しく処理していると信頼し始めるそうです。
3. **既存のソリューションで、コードをその場で生成・実行してデータを処理する**：現在の RAG ソリューションと並べて比較してみることを勧めています（トランスクリプトでは「Rack」と聞こえ、文脈から RAG の意味と考えられます）。コードでデータを処理するほうが、データはより正確になり、セキュリティ境界もより強固になる、という考えです。
4. **テナント境界を導入して顧客データを隔離し、最小権限を与える**：これにより、エージェントの実行を 1 か所に閉じ込められます。
5. **エージェントが出力するすべての結果を検証する**。

### 6.1 デモ A：Azure インシデントのトリアージエージェント

登壇者が自作し、AKS で動かしているエージェントです。ソースコードは共有すると話しています。

**作った背景**：Azure には Observability agent（Azure のサービスを監視できるエージェント）があります。登壇者は、これだけでは自分のコードベースの中も確認する必要があり、すでに 1 つの製品なので Observability agent にコードベースを接続できない、という問題に直面しました。そこで、Azure のリソースと社内コードの両方をチェックして、コードベース内の関連するバグを見つけて報告する自作エージェントを作りました。

**構成**：命令とスキルに OpenCode を使い、Azure CLI をエージェントが呼び出して bash コマンドを実行し、Azure の Insights、ログ、テレメトリを分析します。推論には Microsoft Foundry のモデルを使っています（GPT-6 や GPT-Astra と聞こえますが、音声認識の都合でモデル名は確定できません）。

**デモで語られた流れ**：

1. 画面を大きくして、自作のデモエージェントを表示します。ステージングや本番など、複数の環境にアクセスできます。登壇者によると、実際にエージェントがステージング環境に接続して問題を分析しています。
2. 「ステージング環境のバックエンド API に問題がないか」というプロンプトを実行します。
3. エージェントは、Kubernetes またはコンテナアプリで動くバックエンド API のログを確認し、リソースのコードも見て、コード上の問題を調べます。
4. Activity タブで、エージェントが診断用の bash コマンドを実行している様子が見えます（少し時間がかかる操作もあると話しています）。
5. 結果として、直近 1 時間に見つかった問題の要約が表示されます。アプリケーション、環境、ホストのログを確認した結果で、取るべきアクションと実行できる操作の推奨も含まれています。

### 6.2 デモ B：金融データのコード駆動抽出（Datox の製品）

同じコード駆動のアプローチを、自社製品で見せています。Datox は金融データを扱い、顧客は PDF、Excel、場合によっては画像など形式の異なるファイルを提供します。Excel も複雑になることがあります。ここでの課題は、この非構造化データを、コーディングエージェントで構造化することです。

1. プロンプトで、リスクデータに基づくレポートを生成し、銀行に融資を申し込んでいる企業の信用リスクを分析するよう依頼します。
2. 画面の下側では、エージェントがすべての CSV ファイルを分析する Python コードを生成しています。登壇者は、データ処理そのものに AI を使っているわけではない、と述べています。
3. 生成されたコードは、Datox の実行ランタイムで実行されます。
4. 抽出に適用されたカテゴリが表示されます。登壇者が挙げたのは、market risk、KPI、FX positions、market stress tests などです。リスク評価レポートの生成に必要なデータだけを抽出します。
5. 抽出されたデータが、表の中でハイライトされます。右側には複数のテーブルが作られ、どのテーブルにどんな変換を適用したか、データ取得後にどんな検証チェックをしたかも示されます。
6. 最後に、このデータから作られたレポートの出力が表示されます。
7. エージェントは、Power BI のダッシュボードなどを、その場で生成することもできます。このダッシュボードは登壇者の操作なしに作られたもので、データが動的に変わるため、あらかじめ書いた UI のコードは不要になる、という説明です。リスク評価のデータをリアルタイムで動的に表示しています。

登壇者は、これが現在カバーしている最良のユースケースの 1 つで、中東の銀行業務向けだと述べ、エージェントがアプリケーションの作り方を再定義していると話しています。

### 6.3 デモ C：AI Gateway

3 つ目として AI Gateway が紹介されます。ただし、トランスクリプトからは、この部分で画面操作を行ったのか、スライドで説明しただけなのかは判断できません。語られた内容は次のとおりです。

## 7. 注意点・発表者の気付き

登壇者が失敗や学びとして語った点は次のとおりです。

- ファインチューニングだけでは、権限・制御・アクセスの問題は解決できませんでした。
- 単一のツールで本番の問題がすべて解決することはなく、複数のツールの組み合わせと、自社のデータ処理ルール・検証ロジックが必要でした。
- AI Gateway は、エージェントを作り始める最初の段階から導入するべきだという立場です。
- 機微な変更の場面では、人間による承認と監査のレベルが重要です。
- エージェントにデータの保存や更新を直接許さず、自社 API とデータアクセスポリシーを経由させています。

発表では、コード駆動アプローチの制約、精度「ほぼ 100%」の測定方法、60 ファンドの規模の詳細などには触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は、次のとおりです。

- **データの境界**：顧客データを AI に送らず、スキーマとメタデータだけを渡す設計で、機微なデータを言語モデルに送らずに済みます。
- **監査可能で再現可能な結果**：コードの生成、安全な実行、決定的な検証によって、同じ質問に同じ答えが返り、精度はほぼ 100% と説明されています。
- **信頼の獲得**：信頼度スコア（例：95%）と監査履歴によって、顧客がエージェントの処理を信頼しやすくなります。
- **運用の選択肢**：Foundry、Azure Container Apps、AKS、Foundry Local から、制御の度合いや規模、オンプレミスの要望に合わせて選べます。Datox 自身は、AKS で 5 万を超えるエージェントを動かしています。
- **ダッシュボードの動的生成**：データが動的に変わる場面で、あらかじめ UI のコードを書かなくても、Power BI のダッシュボードなどをその場で生成できます。

## 9. まとめ

Datox の CTO は、規制報告のエージェントを本番で動かすうえでの課題（コントロール、信頼、再現性）に対し、エージェントの構成要素を整理し、コントロールプレーンと実行プレーンを分けたリファレンスアーキテクチャで答えています。特徴は、AI にスキーマだけを渡してコードを書かせ、サンドボックスで実行し、決定的に検証する **コード駆動の抽出** です。ホスティングは Foundry、Azure Container Apps、AKS、Foundry Local の 4 つから選び、セキュリティは最小権限、実行環境の隔離、人間の承認、Microsoft Entra ID による ID 管理で担保しています。

本番対応エージェントの 5 原則は、AI のコントロールの一元化、すべての AI アクションへの根拠の提示、コードによるデータ処理（RAG との比較を推奨）、テナント境界による顧客データの隔離と最小権限、すべての出力の検証です。
