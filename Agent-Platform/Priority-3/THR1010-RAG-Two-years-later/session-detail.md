# THR1010 RAG: Two years later

## 1. はじめに

このセッションは、RAG（Retrieval Augmented Generation）を使った AI エージェントの作り方が、この 2 年でどれだけ楽になったかを、登壇者自身の顧客案件とデモで示す約 27 分の登壇です。結論は 1 つで、**RAG を「エージェントによる検索（agentic search）」として実装する**ことです。LLM に検索用のツール群と使い方の指示を与え、考える時間と余地を与えると、数年前の「1 回検索して答える」型よりずっと良い洞察が得られる、という主張です。

登壇者は、まず用語（LLM、コンテキストウィンドウ、RAG）を手短に確認し、「なぜ RAG が重要か」「2 年前と何が違うか」を説明します。続いて、ヘルスケア系データ分析会社の事例（作業時間 80% 削減、ライセンス販売の増加）と、病院の作業指示（work order）システムを題材にした 2 つのデモを紹介します。デモでは、2 年前風の RAG と agentic search を左右に並べて比べています。

## 5. 発表内容の詳細

### 5.1 基本用語

- **チャットインターフェース**：Copilot、Claude、ChatGPT、Grok などの画面。2022 年に ChatGPT が登場した頃は、入力に対してモデルの学習内容だけで答える形でした。現在は Web 検索、リサーチ、ドキュメントストアの参照ができます。
- **AI と LLM**：登壇者は両者を同じ意味で使うと断っています。LLM は AI を支える技術です。
- **コンテキストウィンドウ**：LLM が 1 つのリクエストを処理する間に「見ているすべて」です。テキスト、送ったファイル、画像、生成した応答、持っているツールや機能まで、すべてがコンテキストウィンドウを埋めます。従来は、ウィンドウが大きくなるほど LLM が間違える可能性も高まる、と説明されています。

### 5.2 RAG とは何か、なぜ価値があるのか

RAG は Retrieval Augmented Generation の略です。AI エージェントに質問したとき、次のようなことが起きていれば、それが RAG だという説明です。

- Web 検索をする
- 会社固有のナレッジベースを開き、関連文書を探す
- データベース（Postgres、SQL Server など）に問い合わせる

つまり、**コンテキストウィンドウ（LLM が見るもの）を、関連する情報で満たすこと**が RAG のすべてです。登壇者は、聴衆に応じて「検索」「RAG」と呼び分けていると話します。具体例として次が挙げられました。

| 接続先 | 例 |
| --- | --- |
| データベース | SQL Server、Postgres、Mongo、Cosmos |
| ドキュメントストア | SharePoint、Google Drive、Dropbox |
| プロジェクト管理 | Jira、Linear（登壇者は開発者として、「同じチケットに取り組んでいる人がいるか」「このバグは既にあるか」を調べさせるのが好きだと話します） |

登壇者自身も、会社のマーケティング用に HubSpot、Apollo、アナリティクス基盤、Web サイトがある GitHub をつなぎ、「これらのシステムで何が起きているか教えて」と LLM に調べさせています。

RAG が価値を持つ理由は 2 つ説明されています。

1. **学習データには期限と範囲がある**：モデルは有限のデータで学習されます。登壇者は「ChatGPT 6.2 SOL」（聞こえた表記のままです）のような最新モデルでも、学習のカットオフがあると述べます。また社内文書は学習データに含まれません。RAG により、最新の文書や会社固有の情報を調べて答えられます。
2. **ハルシネーションを大きく減らせる**：ハルシネーションは、モデルが誤った出力をすることです。聴衆に「チャットが長くなりすぎたので、関連部分を新しいチャットに貼り直したら答えが良くなった経験があるか」と尋ね、それがハルシネーションへの対処だと説明しています。RAG は、LLM が答える前に、関連データを「ジャストインタイム」でコンテキストに入れる手段になります。

### 5.3 The big sell：ステークホルダーに何を伝えるか

登壇者は、Foundry で SharePoint に接続するエージェントを作る例を挙げます。プレビューの機能で、作るのは簡単です。ユーザーが Entra 経由で Copilot に接続すると、ユーザーの ID が SharePoint まで引き継がれ、ユーザーがアクセスできる文書にしかアクセスできません。

しかし、開発者が「Copilot エージェントを SharePoint につなぎました」と上司に伝えても、上司は「それで他に何ができるのか」と聞き返します。登壇者が顧客から何度も聞くのは、**ステークホルダーは AI に実際のインサイト（洞察）を求めている**ということです。さらに、ハルシネーションを非常に嫌います。

その例として、前日に行った table talk の話が挙がりました。「本番に出す前にエージェントに何が必要か」という議題で、法律事務所に勤める参加者が、「銀行 A の契約について弁護士が質問したのに、銀行 B の契約や情報が返ってくるのは深刻な問題だ」と話したそうです。ステークホルダーは、もう一段深く、「このデータで何ができるか」「今まで見たことのない高度な洞察を得られないか」を求めており、そのために一連の有用な検索をエージェントにさせたい、という話です。

### 5.4 2 年前との違い

昔話として、当時と今のエンジニアリングの違いが説明されています。

- **コンテキストウィンドウ**：以前の最大は 25 万トークン程度、あるいは 128,000 トークン以下でした。今は 100 万トークンで、しかもその中から情報を見つける能力が上がっています。そのため、ドリフトや「途中の事実の見落とし」を心配する度合いが小さくなりました。以前は、送るデータが多すぎず少なすぎないよう RAG をチューニングすることが重要でした。ハルシネーションやコンテキストのドリフトが問題であることは今も同じですが、その影響はモデルの能力と効率の向上で小さくなっていると説明しています。
- **サブエージェント**：エージェントが別のエージェントを立ち上げ、「この話題について専門的な調査をして」と任せられます。自分のコンテキストをきれいに保てますし、調査に適したツール群を別に持たせられます。
- **回答前の thinking**：数年前の o3 モデルで始まった革新です。モデルが答える前の thinking ステップの間に、ツールを呼び出せます。今はフロンティアモデルなら、すべてが thinking しながらツールを呼べます。取得したデータをどう解釈するか、さらにデータを探すべきかを、LLM がより良く判断できるようになりました。

以前は、複雑な検索システムを作ることが大きなコストで、多くのエンジニアリングを必要としました。今も丁寧な設計は必要ですが、良い RAG を、より速く、より良く作るための時間は、数年前より短くなったと述べています。

### 5.5 顧客事例：ヘルスケアのデータ分析会社

**顧客**は、ヘルスケア分野のデータ分析会社です。顧客のカスタマーサービスへの通話（メールやチャットもありうる）を分析して、データに分解します。通話の最初と最後で満足していたか、何についての通話か、どの部署にかけたか、特定の薬についてか、副作用についてか、といった情報です。クライアントによっては年間数百万件の通話が送られ、それを分析データに変換して、問題と解決策を探ります。

登壇者が作ったチャットエージェントの対象は、その会社の insights アプリのユーザー、つまり顧客企業の従業員と、そのクライアントの顧客です。想定された質問は次のようなものです。

- 2024 年 10 月に、発信者が不満のまま終わった会話は何件か
- 前年の第 4 四半期の請求部門への通話について、インサイトを教えてほしい
- 支払い遅延について問い合わせてきた通話を探してほしい

**2 年前（導入は約 2.5 年前）の仕組み**は、想定される質問ごとに答えられるツールセットを用意し、ユーザーの質問を見て拡張する、というものでした。1 回のクエリ（または 1 回に複数のツール呼び出し）で答えを出すだけで、推論はしていませんでした。当時は良い推論モデルが使えなかったためです。質問には答えるが、本当に役立つ形ではないことが多かった、と述べています。

**数か月前に刷新した版**は、推論できるチャットエージェントです。データに「RAG をかける（rag over）」ためのツール群を与え、thinking ステップの中で、例えば「支払いプランについて話していた人は不満だったか、なぜか」という問いに取り組みます。流れは次のとおりです。

1. まずマクロの視点で、指定期間のテナント全体のデータを見る。
2. 分解していくと、パターンが見えてくる。LLM はそのパターンを見つけて解釈するのがうまい。
3. 信頼性が重要なので、個々の会話まで掘り下げられる。引用や重要な部分を取り出し、分析データとして抽出されていない、誰も予想しなかった微妙な点まで見つけることもある。

この方式が agentic search です。

**効果**については、パイロット中に、登壇者が会ったことのない顧客企業の従業員から DM が届いたそうです。内容は、「明朝にプレゼンがあり、夕食を急いで食べて家族との時間を削って PC に戻るつもりだったが、チャットエージェントに尋ねたら 10 分で必要な材料がそろった。しかもブランド付きの PowerPoint プレゼンも生成できた。おかげで家族と過ごせた」というものでした。登壇者はこのシステムを、ほぼ 1 人で設計し、納品し、評価（evals）まで行ったと述べています（evals の詳細は語られませんでした）。

数値として、このアプリを使う **社内顧客だけで、インサイトを見つける時間が 80% 削減**されたと、保守的な見積もりとして述べています。さらに、外部の顧客にもこのアプリは販売されており、ライセンスが必要で、**ライセンスの販売が増えている**ため、時間とコストの削減だけでなく、クライアントの収益増にもつながっているとのことです。

### 5.6 デモのシナリオ（Lakeshore Health）

デモは、登壇者の複数の顧客の課題をまとめた架空のシナリオです。**Lakeshore Health** という病院システムの work order（作業指示）システムを題材にしています。データは Azure 上でホストした Postgres データベースで、約 5 万件のレコードがあり、優先度、カテゴリ、説明などの情報を持ちます。例えば、カウンターの剥がれ、水漏れ、異音といった依頼が、保守担当者に割り当てられ、優先順位づけされ、派遣されます。デモの詳細は 6 章に書きます。

### 5.7 Foundry へのデプロイと Copilot への公開

登壇者は、デモで作ったエージェントを Microsoft Foundry にデプロイでき、さらに Copilot に公開できると説明しています。ツール群は同じで、チャートを描く専用 UI はありませんが、同じ thinking が見え、出力もほぼ同じです。ただし、「デプロイ先は Foundry でも他のプロバイダーでも構わない。重要なのはインサイトを得ること」とも述べています。デモのコードは、希望者に提供するとのことです。

### 5.8 発表者の締めくくり

登壇者は、自分の仕事を「ビジネス向けのカスタムシステムを AI と意味のある形でつなぐこと」と表現します。そのためにビジネスのニーズを理解し、RAG をステークホルダーにとって意味のある形でデプロイする必要があります。そこで、収益またはコスト削減に結びつけます。デモのシステムは 2 年前なら構築がはるかに難しかった、と述べ、「RAG が簡単になったわけではなく、プロトタイプからデプロイまでが短くなった」と結んでいます。

セッション後は、Microsoft IQ の担当として、Foundry tools のところに 11 時から 2 時半までいると述べています（聞こえた表記のままです）。LinkedIn やメールでも連絡できます。

## 6. デモ・手順

このセッションにはデモがあります。登壇者は Lakeshore Health の work order データを使い、同じ質問を **左側に 2 年前風の RAG システム、右側に agentic search のシステム** を並べて実行しています。画面の細部は音声からは確認できないため、語られた範囲のみ書きます。

**準備：データの確認**

1. 画面のミラーリング設定を調整したあと、データを少し見せます。Azure 上の Postgres で、work order の優先度、カテゴリ、説明を持ち、約 5 万件あります。

**デモ 1：「なぜ配管工事の完了に時間がかかるのか」**

1. 質問は「Why do plumbing jobs take so long to close?」です。
2. ボタンを押して両方を実行します。
3. 左側の 2 年前風システムは、embeddings を使って work order を検索し、取得した情報から答えます。登壇者はこれを、2 年前なら作れた「ごく単純なシステム」と説明しています。応答は「コンテキストに基づくと、これらの配管作業は長く未完了のままのようだ…」という書き出しで、続きの内容は語られていません。
4. 右側は動きが多く、登壇者が画面をズームアウトして見せます。プロンプトには「どう調査するか」が書かれており、提供した RAG 系のツールの使い方と、問題を段階的に分解して根本原因に至る方法を指示しています。スクロールすると、使えるツール（データベース、データをスライスして分析するクエリ用ツール、個別の work order を調べるツール）が書かれています。
5. 結果として多くの洞察が得られ、**Acme Manufacturing がボトルネック**だと特定します。全 work order を横断して調べた結果、Acme の納品が遅いことが原因だという内容です。

**デモ 2：ベンダー契約を絡めた質問**

1. 質問は「Tower B の看護師が、患者用トイレが何週間も使用不能だと言っている。部品ベンダーは契約を守っているか、何ができるか」という内容です。
2. 左側は、ベンダーとの顧客契約を入れた、ごく基本的なドキュメントストア（チャンク化された文書）を検索します。回答は、Tower B の運用ニーズを完全には満たしていないようだが、それは一時的と記述されている、という程度でした。
3. 右側は work order を調べるだけでなく、別のシステム（契約文書）も参照します。この製造元の特定の部品提供元が Acme であることを把握し、**Acme は緊急注文に対して 2 営業日以内に部品を提供する契約上の義務があり、守れなければ他のベンダーから調達でき、その差額は Acme が支払う**ことを導きます。
4. 登壇者は、このエージェントを自動化し、傾向を先回りして探させれば、SLA を満たしていないベンダーに改善を求める材料にもなると語っています（デモで実演されたものではなく、可能性としての説明です）。

**Foundry へのデプロイ**

1. 配管の質問のエージェントを、Microsoft Foundry にデプロイできることを示します。
2. さらに Copilot に公開できます。同じツール群、同じ thinking が見え、出力もほぼ同じです。チャートを描く UI は無いと断っています。

## 7. 注意点・発表者の気付き

- **agentic search には、トークンと時間のコストがあります。** それでも、LLM にツールの使い方とデータの解釈を指示し、考える余地を与えるのが最善だという立場です。
- **RAG が簡単になったわけではありません。** 良い RAG には今も丁寧なエンジニアリングが必要で、短縮されたのはプロトタイプからデプロイまでの時間です。
- ハルシネーションとコンテキストのドリフトは、今も問題です（モデルの進化で小さくなっているという位置づけ）。
- 信頼性のため、マクロの集計だけでなく、**個々のデータまで掘り下げられるツール** を LLM に与えています。
- アクセス権の扱いにも注意が必要です。table talk では、法律事務所の参加者が、別の顧客（銀行 B）の情報が返ると深刻だと話したとのことです。Foundry の SharePoint 接続（プレビュー）は、ユーザーの ID が SharePoint まで引き継がれるため、ユーザーがアクセスできる文書だけが対象になる、と説明されています。
- LLM に精度の高い検索をさせるためのツールセット設計に、多くの時間をかけたと述べています（詳細は「別の機会に」とされ、このセッションでは語られていません）。

## 8. 利用者にとっての利点

発表で語られた事例の成果は次のとおりです。

- 社内顧客がインサイトを見つける時間が、保守的な見積もりで **80% 削減**された。
- 従業員が、前夜にプレゼンの材料を **約 10 分** で得られ、ブランド付きの PowerPoint も生成できた。
- アプリのライセンスが追加で売れており、コスト削減に加えて **収益も増加** している。
- デモのシナリオでは、work order とベンダー契約を横断して、**ボトルネックのベンダー（Acme Manufacturing）と、契約上の是正手段**を、エージェントが導き出せることが示された。
- Foundry にデプロイし、Copilot に公開することで、同じ分析をチャット環境から利用できる。

## 9. まとめ

RAG は、質問に応じて Web、データベース、文書ストア、チケット管理などから関連情報を取得し、LLM のコンテキストに入れる手法です。この 2 年で、コンテキストウィンドウの拡大（25 万→100 万トークン）、サブエージェント、回答前の thinking によるツール呼び出しが加わり、**LLM に検索ツールの使い方を教えて考えさせる agentic search** が実装の最適解になった、というのが登壇者の主張です。

ヘルスケア分析会社の事例では、インサイトを得る時間の 80% 削減とライセンス販売の増加につながりました。Lakeshore Health のデモでは、2 年前風の RAG が取得した文脈をもとに答えるだけだったのに対し、agentic search は Acme Manufacturing というボトルネックと、契約上の是正手段まで導きました。RAG が簡単になったのではなく、プロトタイプから本番までが短くなった、という言葉が、このセッションの締めです。
