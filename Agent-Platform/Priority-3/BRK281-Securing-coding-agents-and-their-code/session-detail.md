# BRK281 Securing coding agents and their code

## 1. はじめに

このセッションは、GitHub の Copilot などのコーディングエージェントを組織で大規模に使うときに、**「エージェント自身」と「エージェントが書いたコード」の両方をどう守るか**を扱う発表です。前半は GitHub の Ricky 氏が、エンタープライズの管理設定、リポジトリのルールセット、Copilot のサンドボックス、Agent 365 によるエージェントの可視化を説明します。後半は GitHub Advanced Security（GHAS）の Rohan 氏が、生成されたコードに潜むリスクと、secret scanning・CodeQL・Copilot Autofix などの仕組みを、デモを交えて紹介します。

全体を貫く主張は、エージェントが速くコードを書く時代でも、**人間がループに残り、同じ検査をエージェントにも人間にも課す**という点です。Rohan 氏は「これは Copilot のコードではなく、あなたのコードであり、安全にする責任もあなたにある」と話しています。

デモは前半・後半ともに画面を使って行われています。Rohan 氏のパートは、Copilot coding agent、Copilot CLI の security review、push protection、Copilot code review、Autofix を、実演と、事前に実行しておいた結果の画面で見せる構成です。

## 5. 発表内容の詳細

### 5.1 管理設定（managed settings）の推奨値

Ricky 氏は、組織向けに推奨する「planned enterprise managed settings」のスライドを見せたうえで、その設定にあたる JSON ファイルを画面に切り替えて説明しています。スライドは、写真に撮ってよいと案内されたとおり、推奨のデフォルト値をまとめたものです。取り上げられた項目は次のとおりです。

| 項目 | 説明 |
| --- | --- |
| disable bypass permissions | 無効化（bypass できない）設定。コーディングエージェントも人間も、これらの権限を回避できません。本番レベルの CLI、本番へのコード push、認証情報ストア、シークレットといった危険な操作は、エンタープライズ設定で拒否されます。 |
| ask | 重要なステップで人間をループに残す設定。ネットワークツールやパッケージのインストールでは、人間の確認が必要になります。 |
| Sandbox が有効 | エージェントがコードを実行・テストするための隔離環境を使う設定。クラウドでも、ローカルでも使えます。ローカルでは MXC を使うと説明されています。 |

MXC は発表では「Microsoft Execution Containers」と説明されています。Sandbox はこの発表の時点で GA（一般提供）になったと述べられています。

### 5.2 リポジトリのルールセット

次に取り上げられたのが、リポジトリのルールセット（repository rule set）です。エージェントも人間も、リポジトリのリソースを使うにはこのルールセットに従う必要があります。画面では次の点が示されました。

- **enforcement status が active**：人間でもエージェントでもルールに従う設定です。
- **bypass list が空**：ここにはロール、特定のチーム、ユーザー、アクターを追加して、きめ細かく例外を管理できます。
- **ブランチルール**：「merge の前に pull request を必須にする」を常にチェックします。エージェントが本番へマージする前には PR を作成し、後述するコード品質の基準を満たす必要があります。
- **CodeQL のしきい値**：この例では「high 以上」に設定されています。すべてのアラート、medium 以上、critical のみ、といった粒度に変更できます。

Ricky 氏は、これによって「人間がループに残り、あなたが完全にコントロールしている」状態になると強調しています。

### 5.3 code owners とシークレット・変数

追加の防御層として、**code owners** にも触れています。利用者が自作するカスタムエージェント（特定のタスクに特化させたもの）が、エンタープライズレベルの設定やルールセット、先に示した managed settings を迂回できないようにするための保護と説明されています。

シークレットと変数（secrets and variables）については、コーディングエージェント向けに、トークンのレベルで固有のシークレットや変数を作成できます。エージェントがタスクで必要とする認証情報やトークンを、粒度を細かくして設定し、そのエージェントの範囲に限定して管理できるという説明です。鍵が不要になれば失効させ、必要なら新しいものを作れます。スライドでは、本番レベルには届かないこと、org と repo のレベルでスコープを設定できること、そしてそれらを監視できることが挙げられています。デモ環境ではシークレットは作成されていませんが、必要なら同じ画面から作れると述べています。

### 5.4 GitHub Copilot sandboxes

Sandbox は、エージェントがコードをテスト・実行するための**隔離された一時的（ephemeral）な環境**で、本番レベルのコードには触れません。実行環境（execution plane）として、次の 2 種類が挙げられています。

| 種類 | 説明 |
| --- | --- |
| クラウド | GitHub Universe で GA。GitHub Copilot CLI または GitHub のアプリから、`copilot --cloud`（発話では「copilot dash dash cloud」）のコマンドで設定します。Azure Container Apps 上で動き、タスクの大きさに応じてハイパースケールまで拡張できます。 |
| ローカル | こちらも GA。MXC 経由で動き、自分のマシン上の隔離環境で GitHub Copilot が作業します。使えるツールセットやネットワークポリシーを、閉じた環境の中で制限できます。 |

クラウドの sandbox は、**GitHub Actions の minutes を利用できる**ように組み込まれており、新しいサブスクリプションを別に始める必要はないと説明されています。

### 5.5 デモ：package firewall と PR のマージ制御（Ricky 氏）

Ricky 氏は、自分のマシン上でローカル管理されている sandbox の GitHub Copilot ターミナルを使って実演しています。この sandbox は、先に説明したエンタープライズのポリシーやブロックするネットワークポリシーを継承しています。

1. ターミナルで npm install を実行します（トランスクリプトでは「MPM install」と書き起こされています）。
2. インストールがブロックされます。理由は、そのパッケージに既知の脆弱性・リスクがあり、エンタープライズ設定のポリシーと、sandbox をデフォルトで起動する設定が効いているためです。
3. 同じ内容を Actions のログでも確認できます。GitHub の package firewall が npm install をブロックしたこと、最新バージョンをダウンロードする必要があること、そのためのリンクが示されます。
4. バイパスをリクエストすることもできます。今回の設定では許可していませんが、管理者レベルの権限を持つ人が、リクエストを承認するか拒否するかを選べます。

続いて、PR を作る場面を見せています。ルールセットの依存関係のチェックが PR に反映され、画面上は承認が必要な状態でマージできません。Ricky 氏は管理者でもエンタープライズオーナーでもないため、自分では PR をマージできず、レビューを提出して管理者やリポジトリ責任者に承認してもらう必要があると説明しています。

PR の中では、**GitHub Copilot Autofix** と **GitHub Code Review** の働きが見えます。脆弱性を直すコードが提案され、このループは 2 回行われます。1 回目はエージェントがコードを生成したとき、2 回目は人間にレビューしてもらう準備ができたときです。これにより、生成物が基準を満たすことを二重に確認します。左上には「authored by Copilot」と表示されており、エージェントが作ったコードと特定のユーザーが作ったコードを区別できる**監査証跡（audit trail）**になると説明しています。提案は 1 つずつコミットし、レビューを提出し、承認されればメインブランチにマージされます。

### 5.6 オブザーバビリティとエージェントのガバナンス

多数のコーディングエージェントを抱える場合に備えて、エージェントの活動、特定されたリスク、そして**エージェントマップ**を見られると紹介されています。エージェントマップでは、エージェントが MCP などのツールキットを通じて何に接続しているかを確認できます。

エージェントの作り方と配備についての説明は次のとおりです。

- エージェントは GitHub 上、または Copilot Studio で作れます。非技術系のビジネスパワーユーザーは、自然言語でエージェントを生成できます。

この ID が付くと、Foundry 側で 11,000 を超えるモデルから選んでカスタマイズでき、さらに **Agent 365** にも自動で表示されます。Agent 365 は、組織内で配備したすべてのエージェントを一元的に見る画面で、各エージェントのアクティビティ確認や詳細な管理ができます。

デモ画面のエージェントマップでは、どこにどのエージェントが配備されているかが分かり、ポリシー設定や管理もそこから行えます。テナントの数は次のとおりです（デモ用テナントで、多くのエージェントを試しに作ったためと説明されています）。

各エージェントをクリックすると、使用状況やアクティビティを確認でき、GitHub Copilot coding agent の場合も、アクティビティ、アクセスできるツール、権限、使用状況を追跡できると説明しています。ただし今回の PR では別のコーディングエージェントを使ったため、画面上にデータはありませんでした。

### 5.7 生成コードに現れるリスク（Rohan 氏）

Rohan 氏は、エージェントの実行環境を固めたうえで、次に「出てくるコードそのものの安全性」を扱います。プロンプトから、仕様ベースの開発から、既存コードベースの作業から、いずれの場合も「あなたのコードであり、責任もあなたにある」という立場です。リスクの種類は 4〜5 年前に自分でコードを書いていた頃と大きくは変わらず、ただ**エージェントの規模**で起きる点が違うと言います。

発表で挙げられた主なリスクは次のとおりです。

- **従来型の脆弱性の拡張**：インジェクション攻撃は、従来の SQL インジェクションに加えてプロンプトインジェクションも出てきています。新しく生成されたコードに作り込まれる一意の脆弱性の数が、この 1 年で倍増したという数字を紹介していますが、数値の部分は音声認識の都合で正確に聞き取れません（「200 million から 200 million」のように聞こえます）。要点は、エージェントがコードを書く速度に、レビューする人間が追いつけなくなる、という点です。
- **サードパーティコードの増加**：エージェントは OSS コミュニティやメンテナの成果を活用します。そのメンテナには脆弱性の報告や開示が大量に届きます。中にはゴミ（slop）もありますが、本物の欠陥である割合が増えており、数年見つからなかったはずの欠陥が発見されています。その結果、自分たちが書いていない部分から、より多くの CVE にさらされます。
- **マルウェア入りパッケージ**：OSS パッケージにマルウェアが仕込まれたり、本物に見せかけた悪意あるバージョンや亜種に誘導されたりする手口が洗練されています。
- **シークレットの漏えい**：システム間、サービス間の通信はシークレットを介することが多く、意図せず漏れるリスクがあります。内部向けでも公開向けでも問題ですが、コミット履歴（Git history）にも残り、場合によってはずっと残り続けます。
- **保守性の負債**：生成が安価なため、重複コード、デッドコード、深く考えられていないテストされないコードが増え、後から保守が必要になります。こうした技術的負債は、脆弱性が現れるのを待っているだけになります。
- **権限のないエージェントによる攻撃**：以前は権限のない人間が悪意のあるコードを混入させる点を心配していましたが、いまは権限のないエージェントも含まれます。最近のニュースにも現れていたと触れています。

こうした状況から、AppSec の運用をエージェント開発のペースに合わせるため、**自動化されたゲートがますます必要になる**というのが結論です。

### 5.8 GitHub Advanced Security の考え方

会場に GHAS の利用者を尋ねたうえで、GHAS は新しいプラットフォームではないと前置きします。これまでの secret scanning、code security、supply chain security、code quality に加えて、「どこで・誰がコードを生成しても、すべてのゲートの段階でセキュリティ制御を使えるべき」という考え方になった、と説明しています。

| 領域 | 発表で語られた内容 |
| --- | --- |
| Secret scanning | コードが GitHub Enterprise Cloud のリモートに届く前に、シークレットの漏えいを止める。プライベートリポジトリでも、コミット履歴がクラウド上に残ることを避けたい。 |
| Code security | 脆弱性を見つけるだけでなく修正する。モデルの力を使い、古いコードベースや壊れやすいコードでも早く修復できるようにする（agentic autofix）。 |
| Supply chain | 依存関係を把握し、何をビルドしているかを証明する。OSS のライセンスが適切であることを規制当局や監査人に示す。ビルドの完全性を保つための attestation を追加する。 |
| Code quality | 生成コードが増えるほど保守が必要になるため、その機能を GHAS で提供する。 |
| Policy and governance | 制御を実効的なゲートにするには、ポリシーとガバナンスが必要。ルールセットに加えて、レポートや security overview も使える。 |

### 5.9 エージェント開発ライフサイクルへの組み込み

Rohan 氏は、開発の進め方のパターンごとに、どこでセキュリティが効くかを説明しています。

**パターン 1：Copilot coding agent に Issue を任せる場合。** GitHub で Issue を作り、Copilot coding agent に最初から最後まで任せます。タスクをこなすだけでなく、自分の作業で問題を増やさないよう、完了時に secret、コード品質、code scanning、依存関係の問題をチェックします。セッションの結果がクリーンで、脆弱性を増やさないようにする狙いです。

**パターン 2：ローカルで開発し、全権をエージェントに渡す前の段階。** Copilot CLI アプリ、VS Code の Copilot、従来から使っている IDE で、**security review コマンド**を実行できます。ステージした変更、またはコードベース全体を手元のマシンで検査し、エージェントに脆弱性を直させます。こうした問題が GitHub のクラウドに届くことはありません。

**パターン 3：Copilot を使っていない場合。** GitHub MCP server に含まれる secret scanning と dependency scanning を MCP ツールとして使えます。どのコーディングエージェントからでも、リポジトリやコード、ステージ済みの変更、コミット前の変更を検査できます。push protection と合わせた追加の保護になる（音声では「post protection」と聞こえます）と説明しています。シークレットは一度漏れると外に出てしまうため、non-developer branch であっても GitHub に push されるのは大きなリスクだと述べています。

**パターン 4：PR の状態になってから確認する場合。** Copilot code review（CCR）を使っている場合、**今週から**、CCR が PR をレビューするたびにシークレット漏えいの可能性を特定するよう、secret scanning を有効にできます。さらに**近いうちに**、Copilot code review の中で code scanning とコード品質のチェックもできるようになる予定で、この機能には GitHub Advanced Security のライセンスが要らず、Copilot code review の機能の一部として提供されると説明しています。

そのうえで、既存のゲートも引き続き使えます。CodeQL による PR とリポジトリ全体のスキャン、依存関係の問題を見つける Dependabot（音声では「dependable」と聞こえます）、secret scanning の結果を、マージ可否を決めるゲートにして、新たな脆弱性、漏れたシークレット、多数の脆弱性や悪意を含む依存関係を持つ PR のマージを止められます。

**事前の（プロアクティブな）対策：package firewall。** Universe で発表された package firewall は、明らかに悪意のあるパッケージを環境に入れません。本番システムだけでなく、開発者のマシンやビルドシステムにも届かないようにすることが重要だと述べています。ここ数年のサイバー侵害の多くがビルドシステムから始まり、メモリからのシークレット漏えいなどが起きている、という背景です。ルールセットでスキャンの実施を必須にすることも、プロアクティブな制御になります。

**修復：agentic autofix。** Copilot Autofix は以前からありましたが、新しい agentic autofix は、修正のための PR を作るだけでなく、PR をテストで検証します。修正が何かを壊す場合は、再帰的に複数回、修正を改善しようとするか、環境やテストが壊れる可能性を知らせます。場合によっては、テスト側を直すことも提案します。

### 5.10 Q&A

3 件の質問があります。

**ローカルでの secret scanning は LLM を使うのか。パスワードが漏れてしまうのではないか。** LLM は使っていません。決定論的な方法で、ハッシュを送る API として動作し、場合によっては該当プロバイダーに照会して「有効な Azure のシークレットか、無効なものか」まで確認できると回答しています。このための**ファインチューニングしたモデル**の取り組みもありますが、そのモデルは GitHub 内でホストされ、この用途のために調整されたものだと説明しています。

**教育の現場で、学生が 1 つのリポジトリにコードをアップロードし、上記のチェックを自動で行う案はどうか。1,000 人規模にスケールするか。** 可能だと回答しています。これらの制御は、Microsoft を含む数十万人規模の開発者を持つ企業でも使われているものです。セキュリティ構成（security configuration）を多数のリポジトリや組織に適用でき、ルールも複数の対象に適用できます。制御は個々のユーザーではなくリポジトリにかかるため、誰が使っても常に強制されます。回答の後に、質問者が「コードの品質とシークレットも見たい」「MCP サーバーも呼びたい。可能だと思うが」と付け加えていますが、これに対する発表者の回答は録音に含まれていません。

**自動マージの境界はどこに置くべきか。** 質問者は、すでに多くのエージェントとスキャンを使っており、GitHub のレビューと十分な CI があるなら、小さな PR は人間のレビューなしで自動マージしたいと述べ、どこまでエージェントを信頼するか（バイパスを完全に許すのは危険ではないか）を尋ねています。回答は、**まだ進化中**であるというものです。社内でも議論しており、作業の「グレード」を決めて、このグレードなら自動マージできる、できない、と分類するためのレバーを提供する方向を示しています。大企業では、SOC 2 などのコンプライアンスの理由から、少なくとも 1 人、できれば 2 人の人間による PR の確認がまだ必要だという見方も紹介されました。次にここで会うときには状況が変わっているはずだと話しています。

## 6. デモ・手順

このセッションでは、画面を使ったデモが 2 つのパートで行われています。録音は音声のみのため、画面の細部は分からず、**語られた範囲**だけを記します。

### 6.1 Ricky 氏のデモ

1. managed settings の推奨値を JSON ファイルで見せ、bypass 無効、ask、Sandbox 有効の項目を説明する。
2. リポジトリのルールセットの画面で、enforcement status、bypass list、ブランチルール、CodeQL のしきい値、secrets and variables を順に示す（code owners はこの画面の説明の中で触れられています）。
3. ローカル管理の sandbox 環境で GitHub Copilot のターミナルを開き、npm install を実行して、脆弱性のあるパッケージがブロックされることを示す。
4. Actions のログで、package firewall によるブロックと、最新バージョンへのリンクを示す。
5. 作成した PR で、承認が必要でマージできないこと、Copilot Autofix と Code Review の提案、「authored by Copilot」の表示を示す。
6. Agent 365 のエージェントマップを見せる（Foundry 52、Copilot Studio 722）。

### 6.2 Rohan 氏のデモ

デモの題材は、注文管理を想定したダミーのリポジトリです。

1. Issue に「注文検索、ノート、API エンドポイントを追加したい」と書かれたものを、Copilot（coding agent）に割り当てる。Issue に十分な情報があるため、追加のコンテキストは与えない。
2. 実行を待つ間に、以前に同じ方法で作った PR の Copilot セッションを見る。環境をセットアップし、リポジトリを把握し、API エンドポイントを追加する変更を行う過程が出る。そこで自動的に secret scanning（内部ツール）が実行される。このケースでは、PR で入りうる**レート制限の問題**も特定し、更新している。
3. Copilot CLI を開き、diff を見る。注文検索ページ、サーバー、データベースへの変更が含まれ、偽のパスワードやシークレットが混ざっている（実際には動かない値だと説明）。
4. security review コマンドを実行する（コンテキストを足しても、足さなくてもよい）。ここではステージ済みの変更が検査される。リポジトリ全体に対しても実行できる。
5. あえて security review の結果を無視して、シークレットを含む変更をコミットして GitHub に push する。**push protection** がブロックする。ブロック画面の URL をコピーして認証し、テストシステムなどの理由を付けてバイパスをリクエストすることもできる。
6. security review の結果は 2 件で、SQL インジェクションとクロスサイトスクリプティング（高い信頼度）。修正の選択肢として、high の問題だけ直す、すべて直す、とりあえず所見の要約をコミットして後で見る、が示される。この間も package firewall は有効で、悪意のある、または脆弱なパッケージのインストールを、ローカル、Actions、sandbox などでブロックできると補足している。
7. 以前に Copilot にレビューさせた同じ PR を開き、Copilot code review の結果を見る。品質上の問題に加えて、コード内のシークレットの可能性が指摘されている。ファイル変更画面からコメントを Copilot で解決することもできる。
8. マージボックスを見ると、追加のレビューが必要なことと、CodeQL が PR 内のセキュリティ問題を検出したこと、Copilot code review のものを含む会話が未解決であることからマージがブロックされている。これらはリポジトリのルールセットで強制されている。
9. Copilot CLI の security review で見つかった反射型クロスサイトスクリプティングは、無視してそのまま push したが、code scanning が自動で実行されてアラートとして検出されている。このアラートを Copilot に割り当てる。
10. 数分かかるため、前もって同様に実行した結果の PR を開く。Copilot セッションでは、auto fix のサブエージェントが起動し、code scanning のアラートを取り出し、カスタムの Copilot instructions や README を確認し、ファイルを見て変更を加える。回帰テストと、リポジトリに既にあるテスト（Actions を使っていればそれらも）を実行する。さらに secret scanning と code scanning を実行して、新たな問題を入れていないことを確認している。Rohan 氏は、この PR は信頼度が非常に高く、容易にマージできるものだと述べています。

## 7. 注意点・発表者の気付き

- **シークレットは一度漏れると取り返しがつきません。** コミット履歴にも残るため、push の前に止める（push protection、ローカル検査）ことが重視されています。non-developer branch への push でもリスクがあると述べています。
- **無視しても検出される**：security review を無視して push しても、push protection と code scanning が働きます。Rohan 氏はこれを、デモで意図的に見せています。
- **ブランチ保護よりルールセットを推奨**：従来のブランチ保護を使っている場合は、エンタープライズや org レベルで全リポジトリに強制でき、一部のリポジトリに絞って適用もできるルールセットへの移行を強く勧めています（担当プロダクトマネージャーとしての「宣伝」と本人が断っています）。
- **自動マージは慎重に**：まだ進化中の領域であり、大企業では SOC 2 などの理由で人間のレビューが必要だとされています。
- **修正が別の問題を生む可能性**：従来は、1 つの穴を塞ぐと別の穴が開くことがありました。agentic autofix は、テストと secret scanning、code scanning を再度実行して、新たな脆弱性を入れないよう検証すると説明しています。
- **機能の提供状況**：sandbox（クラウドとローカル）は GA。Copilot code review での secret scanning は今週から。code scanning とコード品質のチェックを Copilot code review に入れる機能は「近いうち」とされ、日付は示されていません。security review コマンドへの secret scanning と dependency scanning の追加も「近いうち」です。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 組織単位の管理設定、ルールセット、sandbox により、エージェントが本番や認証情報に触れないようにしつつ、人間のレビューを残したまま規模を拡大できる。
- package firewall により、悪意のあるパッケージや脆弱なパッケージが、本番だけでなく開発者のマシンやビルドシステムにも入らない。
- 「authored by Copilot」の表示によって、エージェントが作ったコードを特定でき、監査証跡になる。
- Agent 365 とエージェントマップで、Foundry、Copilot Studio などに配備したエージェントの数、使用状況、接続先のツール、権限を一元的に把握できる。
- Copilot code review でのセキュリティチェックは GitHub Advanced Security のライセンスなしで使える（secret scanning は今週から、code scanning などは近日予定）。セキュリティ対策の導入を始める入口として位置づけられている。
- ローカルの security review は、GitHub のクラウドに問題が届く前に検出・修正でき、GHAS の顧客でなくても使える。
- 数十万人規模の開発者を持つ企業（Microsoft を含む）でも使われている制御で、1,000 人規模の利用にも拡張できると説明されている。

## 9. まとめ

このセッションは、エージェント開発の速度に合わせて、エージェントの実行環境と生成コードの両方に、自動化されたセキュリティのゲートを置く方法を整理したものです。前半では、managed settings（bypass の無効化と ask）、ルールセット、code owners、シークレットと変数のスコープ、Copilot sandboxes（クラウドは Azure Container Apps、ローカルは MXC）、package firewall、Agent 365 のエージェントマップによる可視化が紹介されました。後半では、生成コードのリスクを整理したうえで、Copilot coding agent、security review、push protection、Copilot code review、CodeQL、agentic autofix をそれぞれのタイミングで使い分けることが示されました。自動マージの境界は発表者自身も「まだ進化中」としています。大企業では SOC 2 などのコンプライアンス上、少なくとも 1 人の人間によるレビューがまだ必要だという見方が示されました。
