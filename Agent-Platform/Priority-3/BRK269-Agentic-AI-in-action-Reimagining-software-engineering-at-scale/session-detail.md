# BRK269 Agentic AI in action: Reimagining software engineering at scale

## 1. はじめに

このセッションは、Hewlett Packard Enterprise（HPE）が約 1,000 人のソフトウェアエンジニア向けに、GitHub Copilot の上に構築した社内プラットフォーム **AIMS**（AI Management System）の事例紹介です。前半は HPE の Rupal Shah 氏が、AIMS を作った経緯、アーキテクチャ、自動化の仕組み、効果測定の方法を説明します。後半は GitHub の Megan 氏が、GitHub の立場から「自社の開発プロセスに合わせて GitHub Copilot をどうカスタマイズするか」を話し、最後に質疑応答が行われます。

発表の骨子は次の 3 点です。

- HPE のソースコード管理は GitHub ではありませんが、リポジトリを GitHub にミラーすることで GitHub Copilot のフルリポジトリ・インデックスを使えるようにし、それを出発点にエージェント活用を広げた
- 欠陥（defect）のトリアージから修正までを、エージェントが自動で進める運用を、人間の承認を残したまま実現している
- 効果は数値で測っており、平均解決時間（MTTR）が 87 日から 31 日に短縮（64% 減）、トリアージ精度は 10 月に 84%

### 5.1 HPE の背景と AIMS 誕生までの経緯（Rupal 氏）

Rupal 氏は CX スイッチのソフトウェアチームの立場で、巨大モノリシックリポジトリ上での開発のスケールを課題として挙げました。複雑さが増し、ワークフローが分断され、手作業が速度・品質・イノベーションの制約になっている、という認識です。

AIMS はこの課題への回答で、GitHub Copilot の上に構築されています。AIMS が満たすべき領域として、6 つの柱が示されました。

1. 計画とインテリジェンス（発話では "planning, intelligence, engineering productivity" と続けて語られ、区切りは確定できません）
2. エンジニアリング生産性（チームの手作業を減らし、機能の提供を速め、イノベーションに時間を回す）
3. 継続的インテグレーションとテスト（リリースをできる限り安全にする）
4. お客様に出た後の問題のトリアージ、根本原因の特定、修正
5. クラウド管理との統合（HPE のネットワークはクラウド管理されるため。発話では "switching portfolios" と続けて語られています）
6. 分析（進捗を継続的に測る、AI の効果を評価・改善する、AI ツールへの投資で最大の ROI を得るための効率を測る）

> 補足：発表者は「主要な柱は 6 つ」と述べ、スライドの項目を順に読み上げています。上の 6 項目への割り振りは、発話の区切りから整理したもので、項目の切れ目は発話だけでは確定できません。

経緯は次のとおりです。

- 2025 年の初めに、社内で GitHub Copilot のライセンスが使えるようになりました
- しかし、リポジトリが巨大で、GitHub ネイティブではない（ソース管理は GitHub 以外）ため、ローカルで得られるコンテキストは約 2,500 ファイルまでに限られ、AI の支援は限定的でした
- そこで、35 万ファイルを超えるリポジトリ全体を対象にしたフルリポジトリ・インデックスが必要だと考えました
- 候補の 1 つは「code drag」と聞こえる方式でした（音声認識の都合で表記が確定できません）。しかし、コードを GitHub にミラーすればリモートでのフルインデックスが得られると気づき、それを選びました。**「ゲームチェンジャーだった」** と述べています
- 完全な移行は選べませんでした。CI/CD パイプラインがソース管理と強く結びついており、時間がかかるためです
- 今年の 1〜2 月にエージェント AI に踏み込み、最初のエージェントを作りました。その後、目的別のエージェントが急速に増え、20 前後になったところで、組織全体で効果的に使うための統一プラットフォームが必要になり、AIMS に進化しました

### 5.2 AIMS のアーキテクチャ

AIMS は GitHub Copilot の上に構築され、**VS Code 拡張**としてリリースされています。**Copilot CLI** でもサポートされています。

入力と接続先は次のとおりです。

- エンジニアの自然言語のプロンプト
- 欠陥管理システム（イシューや機能要望を扱う）
- ソース管理（コードの変更とコードレビュー）
- ドキュメントやナレッジ向けの仕組み（ここは「certain drags」と聞こえ、表記が確定できません）

AIMS は、開発、テスト、クラウド管理といったドメインごとのオーケストレーターを持ち、将来のドメインも素早く追加できる構造です。直面した課題は「オーケストレーターのオーケストレーター」をどう作るかでした。そこで **意図（intent）ベースの処理**を採り、クエリの意図に応じて、最上位のオーケストレーターが該当ドメインのオーケストレーターのペルソナを取ります。これにより、ワークフロー全体を支援できます。

全ドメインは AIMS の共有ランタイムとガバナンスの上に載り、次を共通に持ちます。

- セキュリティ
- MCP ツールの共有
- 適切な統制
- 取得したい任意のテレメトリ
- すべてのエージェント的ワークフローにまたがる品質ゲート

そのうえで分析（5.6 節）があります。AIMS は、Copilot のアクティビティ、エージェントの呼び出しと効果（発話では "our entire STLC" と述べられています）、ワークロードのインサイト、エンジニアリングのコンテキストを測定し、継続的な測定が評価と改善につながるフィードバックループになっています。

### 5.3 AIMS の画面（VS Code 拡張）

Rupal 氏はデモを再生しながら、VS Code 拡張の画面を説明しました（詳細は 6 章）。開発者が VS Code を起動すると、接続先の概要（ラボのスイッチ管理を担う autoinfra、Confluence、Wiki など）とその健全性が表示されます。エンジニア一人ひとりが、タスク、対応すべき欠陥、アクション待ちのコードレビュー、クレジット使用量と改善インサイトを含む、毎日のビューを得ます。

### 5.4 運用モデルと自動化

AIMS は、1 つのプラットフォームに 2 つの実行モードを持ちます。

- **手動（エンジニア主導）のワークフロー**
- **自律的ワークフロー**：「bot」と呼ばれる、アプリサーバー上で動くサービスアカウントが、継続的に問題を見つけて自律実行します

両モードとも AIMS を使うため、共有ランタイムを持ちつつ、運用、ガバナンス、テレメトリ、分析が標準化されます。

目標は、**完全に自動化されたソフトウェアメンテナンスのループ**です。現時点でサポートしているのは次のものです。

| 機能 | 内容 |
| --- | --- |
| AI コード検査 | PR ごとにエンジニアが AI レビューを依頼できる。コーディングガイドラインや標準への適合に加え、メモリリークなどの検出も行う |
| 自動トリアージ | サポートパッケージ付きで欠陥が登録されると、bot 経由で自動的に起動し、分析してトリアージのレポートを投稿する（レポート名は「GRO report」と聞こえ、聞き取り不明瞭） |
| 自動修正・自動検証 | 精度に基づく段階的なロールアウトとして開始したところ。トリアージレポートとコードの所見から修正コードを生成し、1 つまたは複数のスイッチファミリで自動テスト、ポリシーチェックを行い、レポートを投稿する |

これにより、エンジニアが作業を始める時点で、欠陥が割り当てられているだけでなく、トリアージのレポートとコードレビューも投稿済みになります。将来はリリース準備も含めて完全自動化する計画です。現在は承認プロセスに人間が入っており、曖昧なもの、プロダクト上のトレードオフ、監督が必要なものについては、完全自動化のループになってからも人間の承認を残す、と述べています。

### 5.5 導入前後のトリアージ・修正ワークフロー

**AIMS 以前**は完全に人手で、数日から数週間かかりました。欠陥が起票されると、調査して根本原因を見つけ、修正を計画します。計画が通用しなければ戻って繰り返します。次に修正を実装し、スイッチのイメージをビルドしてテストを通し、コードレビューを投稿し、レビューの指摘で何度も反復して、最後に承認とマージとなります。

**AIMS 以後**は、欠陥が作られるとすぐに自動でトリアージされ、レポートが投稿されます。特徴は次の点です。

- **2 パスのトリアージ**：最初のトリアージを 1 つのモデルで行い、その結果を別のモデルで評価して異議を唱える。「AI を盲信しない」ためで、結果への信頼を高める
- トリアージ精度が十分高いコンポーネントでは、bot が自動修正を投稿する。それ以外はエンジニア主導で、AIMS を起動して修正ワークフローを動かす
- どちらの場合も人間の承認は残り、承認後にマージされる

精度を継続的に上げるために、次を行っています。

- **bot memories**：現状はエピソード記憶のみ。このアーキテクチャを拡張する意図がある
- **敵対的エージェント（adversarial agent）** と 2 パスのトリアージ
- **評価**：欠陥のクローズ後に bot が、結果が正確だったか追加の変更が必要だったかを評価し、その結果が bot memories に戻る
- **feature skills**：機能領域やコンポーネントごとの深い知識。エージェント的ワークフローに加え、特に難しい欠陥で結果の精度を高める重要な要素

### 5.6 AIMS Intelligence と AIMS Analytics

**AIMS Intelligence** は 3 つの柱でできています。

1. **永続的なインテリジェンス**：GitHub Copilot のメモリとセマンティック検索。さらに bot memory が精度向上に効いている
2. **ドメイン知識とエンリッチメント**：feature skills による専門知識に加え、エンジニアリング仕様書、部品データシート、トラブルシューティングガイドなどの各種 RAG が AIMS に投入されている
3. **継続的な学習と検証**：敵対的レビューとグラウンドトゥルース評価により、ドメイン知識、feature skills、bot memory を継続的に洗練する

グラウンドトゥルース評価の中身は次のとおりです。auto ワークフローで AIMS がトリアージまたは修正した欠陥ごとに、クローズ後に有効性を測ります。

| 対象 | 分類 |
| --- | --- |
| トリアージ（4 区分） | 正確な修正（exact fix）／根本原因を特定／領域（エリア）を特定／完全に外した |
| 修正（3 区分） | 正確なコード修正／修正に手が加えられた（amended）／誤った修正 |

これは欠陥ごとに行い、ダッシュボードではコンポーネント単位に集計します。平均値の陰に隠れたコンポーネントごとの弱点や、リグレッションを見つけるためです。AI 駆動のワークフローで悪影響を出さないための鍵であり、feature skills の改善やルーティングの改善が必要な箇所を絞り込むのにも使っています。

**AIMS Analytics** は、GitHub のセッションフック（session hooks）で、AI の利用とエンジニアリングワークフローにまたがる可観測性を提供します。「あらゆる行動を測り、あらゆる結果を理解し、AI ワークフローへのあらゆる投資を最適化しようとしている」と述べています。分析は「4 つの主要な領域」で提供されるとのことですが、聞き取れたのは次の 3 つです（4 つ目は発話から確定できません。採用トレンドは 1 つ目の説明の中で語られています）。

1. Copilot のアクティビティ（AIMS か否かのワークフロー、セッションとメッセージ、モデルの使用状況、AIMS の寄与、エージェントスキルと呼び出し数と精度、採用トレンド）
2. ワークフローのインテリジェンス（各ワークフローを、トリアージ、コード、修正などの 7 つの領域にマッピング。クレジットがどこに使われているか、パイプライン全体のどこに作業が多いかが分かる）
3. エンジニアリングのインサイト（AI が作成・削除したコード行数、欠陥の傾向、トリアージと修正の精度）

> 注意：HPE は個人データの保護を重視しており、分析データは **利用メトリクスのレベルで集計**されます。ユーザーデータ、プロンプト、個人的な内容を収集することは決してない、と明言しています。

分析データの可視化には Power BI ダッシュボードを使います。ダッシュボードには、欠陥管理システム、ソース管理、GitHub Copilot の利用量とエンタープライズ・メトリクス、AIMS のユーザー／bot ワークフローのデータが取り込まれます。そこから、採用状況、運用、品質と効果、取るべき改善アクションにズームインできます。マネジメントも AI ワークフローの影響と、会社が投じている投資の ROI を見られるようになりました。

### 5.8 GitHub の視点（Megan 氏）

**ローカルクライアントなら GitHub 外のソースでも使える。** HPE は VS Code、Copilot CLI、Copilot app を使っており、ローカルにあるものは何でも見られます。GitHub Copilot はさまざまなサーフェスで使え、GitHub の哲学は「お客様のいる場所に合わせる」ことです。HPE が独自のニーズを GitHub のプリミティブの上に作れたのも、この方針の例だと説明しています。

**同じハーネスを使っている。** どのサーフェスでも、同じエージェントループ、同じツール検索、同じメモリを使います。例えば VS Code で「テストはこう実行して」と伝えておくと、github.com の PR レビューや Slack や Teams（発話では "Slacker teams"）の GitHub Copilot でも、そのメモリが効きます。テレメトリと評価も一貫させています。数か月前にハーネスをすべて統一し、火曜日のキーノートで話されたとおり、**Microsoft Copilot SDK** にリブランドしました。このハーネスは、最近では Microsoft Copilot の Excel や PowerPoint、そして Cowork でも使われている、と説明しています。

**自社のエンジニアリングシステムへの統合は、完全に舗装された道ではなかった。** HPE からも「テレメトリのここを良くしてほしい」「独自の MCP を CLI に出荷してセットアップしたい」といった要望があり、GitHub 側にも作業が必要な場面がありました。ただし目標は、どの組織のニーズにも、これらのプリミティブが使えて拡張性のある体験を作れることです。

**カスタマイズの進め方。**

1. 管理したいワークフローを特定する。AIMS の場合は、欠陥のトリアージと解決策の出荷で、feature skills が重要な構成要素だった
2. カスタマイズの形は組織ごとに異なる。例として、全開発者に配りたいプラグインライブラリ、特定のプロンプトで始めて時間とともに学習させる GitHub Copilot のクラウド自動化、独自のフックによる挙動のカスタマイズやテレメトリの取得が挙げられた
3. エージェント以外の既存システムと連携する。HPE は Jira と既存のソース管理（GitHub ではない）と密に統合している。MCP、フック、カスタマイズで拡張できる

**GitHub にソースを置くと得られるもの。** GitHub Copilot は GitHub 以外のリポジトリでも使えますが、次の点は GitHub ソースを使う場合の追加の利点です。

- **メモリ**：ハーネスがある場所なら、どこでも得られる（GitHub ソースの有無に依存しない）
- **Dreaming**：数週間前に発表された機能。Copilot instructions、agents.md、エージェントに与えるスキルといったコンテキストを、時間とともに良くする。うまく動いたか、人が修正する必要があったかを見る継続的なループで、例えば API ドキュメントが古ければ、修正する PR を開く
- **コード検索**：コードが GitHub にあれば、GitHub がインデックスする。1 つのリポジトリだけでなく、全リポジトリで同じ問題がどこにあるか、変更の下流への影響はどうかを把握するため、コード検索に力を入れている。これは GitHub ソース内の方がネイティブに、より高い性能で使える

Copilot memory について、計測したセッションの **93%** で開発者のパーソナライゼーションが向上し、**42%** のセッションで効率化（繰り返しの説明が減ることでのトークン節約）につながったと紹介しました。

また、火曜日に **GitHub Copilot app が Azure DevOps をサポート**することが発表されました。顧客からの大きな要望だったとのことです。

Megan 氏の結論は、GitHub にソースが無くても今日できることは多い、ソースを GitHub に移すと追加機能が得られる、というものです。HPE の発表で特に良かった点は、テレメトリを見て継続的に改善するデータ駆動の姿勢であると述べました。バグのトリアージや自動修正は、話を聞く多くの顧客が作っているユースケースなので、GitHub としてこれらを標準で（out of the box）シームレスに動くようにしようとしています。

### 5.9 Q&A

> 補足：質問者の声は録音にほとんど入っておらず、質問の本文は一部しか分かりません。以下は、回答の内容から読み取れる範囲の要約です。

**Q1（聞き取れた範囲では、Confluence など GitHub 外のシステムの情報をどうコンテキストとして取り込むか、という趣旨）**

Megan 氏（GitHub の観点）：コンテキスト収集の多くは MCP 経由です。フックで API を呼ぶ、リポジトリに情報を置くといった方法もありますが、多くの人が望むより手間のかかる設定になる、と述べています。また **コネクタ（connectors）** があり、ユーザーがシステムに認証すると、MCP より直接的な接続でデータが取れます。組織として Atlassian（Jira）や Confluence の MCP をセットアップし、全ユーザーに配ることもできます。「全員必須」にすることも「推奨」にすることもでき、そうするとユーザーはコンテキストを最初から得られます。自動化でも、同様に接続を設定できます。

Rupal 氏（AIMS の場合）：**research agent** が Confluence、Wiki、RAG などから情報を収集します。社内で作った拡張もあり、例えば自社 ASIC の資料の検索は、社内の MCP を通じて行っています。bot memories は現在エピソード記憶のみですが、短期・長期の記憶や手順などに拡張すれば、ワークフローにさらに知識を与える手段になり得ると述べました。

**Q2（トークン使用量とコスト削減）**

質問の趣旨は、データが絶えず変わる中でトークン使用量とコストをどう抑えているか、というものと聞こえます。Rupal 氏の回答は次のとおりです。

- トークン使用とコスト削減は常に重点課題である
- データが変わり続ける場合、コンテキストを減らす必要がある。そこで research agent が、そのデータが本当に必要かを見て絞り込み、メインのワークフローのコンテキストには必要な分だけ渡す
- ステージごとに異なる LLM を使い分ける。例えばドキュメント作成のようなワークフローは、コストのずっと低い LLM に固定（ピン留め）し、高コストの LLM は特定のワークフローだけに使う（高コストの例として「Opus 55」と聞こえ、モデル名は音声認識の都合で確定できません）

**Q3（コストや使用量のガバナンスと、価値／ROI の測り方）**

質問者の声は聞き取れませんが、回答から、「トークン消費の測定とガバナンス」と「価値（ROI）の測り方」の 2 点が問われたと読み取れます。Rupal 氏が両方に答え、ベンチマークの話には Megan 氏が補足しました。なお、回答の途中で Megan 氏が安価なモデルの使い分けに触れたとみられる箇所は、録音が不明瞭で内容を確定できません。

ガバナンスと測定について：

- 手動ワークフローでも、AIMS が特定のワークフローとエージェントを特定の LLM に固定している
- 手動・bot の両方のワークフローで、セッションフックにより、セッションとメッセージのループごとに、クレジット使用量、使った LLM、ペルソナ（トリアージ、リサーチ、コード修正など）を送信している
- ダッシュボードで、個人レベルと、ワークフロー別の全体の両方について、使用モデル、トークン使用量、結果を見られる
- AIMS を補強するものとして、本番ではないサンドボックスの **test bench** がある。新しい LLM が出るたびに、性能、精度、トークンコストなどを測り、判断したうえで特定のワークフローの本番に展開する
- マネージャーも各メンバーも、VS Code の AIMS ダッシュボードで、ワークフローごとの自分の LLM 使用量とクレジット使用量を確認でき、自己評価できる。「AI ファーストだが、賢く使う責任が全員にある」という考え方

Megan 氏の補足：HPE が独自にベンチマークを走らせていたことは知らなかったと述べたうえで、同様のことをする顧客は多いと話しました。今週、**benchmarks.github.com** を公開したそうです。GitHub 自身の内部ベンチマークで、GitHub のハーネスと他社のハーネスの両方を、モデルごとに公開しています。これで、ベンチマークのためにトークンを使わなくても、曲線を見て判断できる、という説明でした。

ROI について（Rupal 氏）：

- MTTR だけでなく、複数のダッシュボードを作成済み、または作成中。欠陥が入ってからエンジニアが見るまでの時間、2024 年・2025 年のレガシーデータと AIMS 導入後の比較、修正までの速さ、リリースがお客様に届くまでの速さを、リリース・プラットフォーム・プロダクト・コンポーネントの各レベルで測っている
- 上級 VP の言葉として、現製品・現顧客の保守にかかる年間支出が X 百万ドルあるとして、AI で半減できれば、それが ROI だという例が挙げられた（目標は半減よりもさらに低い支出だと述べています）
- 欠陥あたりのコスト（トリアージと修正にかかるコスト）を、AI 導入前、AI 支援、AIMS による AI ファーストのワークフローで比較している
- エンジニアリングの帯域：同じ人数で何件多く新機能やイノベーションを出せるかを、6 か月〜1 年の期間で測る
- こうした測定は、可視性が得られたからこそ、マネジメントが推進しているもの。エージェントが分断されていた頃は可視性が無く、「良くなっている気がする」だけで、データ駆動の見方が無ければ ROI は示せなかった
- 一時期はコード行数を追いかけたが、すぐにそれは測る方法ではないと気づいた
- 方針は「意味のあるところで AI ファースト」。すでにやり方が分かっている 1 行の修正なら、AI を使わず直せばよい、と述べています。

（トランスクリプトは、「一般的には、コード行数の…」という文の途中で終わっています。）

## 7. 注意点・発表者の気付き

- **AI を盲信しない**：2 パスのトリアージ（別モデルでの評価）、敵対的エージェント、グラウンドトゥルース評価を入れている
- **平均値に注意**：全体の精度が高くても、特定コンポーネントの弱点やリグレッションを隠すことがある。ダッシュボードはコンポーネント単位で見る
- **自動修正は精度に基づいて段階的に**：トリアージ精度が高いコンポーネントだけ bot が自動修正する。全コンポーネントで 90% 以上が、完全な自動修正の条件
- **人間の承認は残す**：曖昧なもの、プロダクト上のトレードオフ、監督が必要なものは、完全自動化後も人が見る
- **コード行数は指標にならない**：一時期追いかけたが、測定の方法として適切でないと気づいた
- **個人データを集めない**：分析は集計した利用メトリクスのみで、ユーザーデータ、プロンプト、個人的な内容は収集しない
- **完全な移行が難しい場合がある**：CI/CD がソース管理と強く結びついているため、HPE は移行ではなくミラーを選んだ
- **コストへの配慮**：ワークフローごとに LLM を使い分け、リサーチエージェントでコンテキストを絞る
- GitHub 側からは、HPE の導入が「完全に舗装された道」ではなく、テレメトリの改善や独自 MCP の CLI への組み込みなど、GitHub 側の作業が必要だった点が語られた

## 8. 利用者にとっての利点

発表で語られた利点は、HPE の実績が中心です。

- MTTR が 87 日から 31 日へ 64% 短縮。精度高くトリアージされた欠陥ではさらに短い
- 4,000 件を超える問題をトリアージ済み。トリアージ精度は全体で 60%、10 月は 84%
- エンジニアが作業を始める時点で、トリアージのレポートとコードレビューが投稿済み
- 1,000 人を超えるエンジニアが AIMS を使用
- マネジメントが AI の影響と ROI を、ダッシュボードで見られる
- GitHub 側の利点：Copilot memory により、計測したセッションの 93% で開発者への最適化が進み、42% で効率化（トークン節約）が見られた

## 9. まとめ

HPE は、GitHub 以外のソース管理を使う 350K ファイル超の巨大リポジトリを GitHub にミラーすることでフルリポジトリ・インデックスを得て、エージェントを AIMS という統一プラットフォームにまとめました。AIMS は VS Code 拡張／Copilot CLI として提供され、意図ベースで各ドメインのオーケストレーターを切り替え、bot による自律的なトリアージと修正までを担います。2 パスのトリアージ、feature skills、RAG、グラウンドトゥルース評価で精度を高め、session hooks と Power BI で利用と効果を測っています。

GitHub の Megan 氏は、GitHub Copilot は GitHub 外のソースでも同じハーネス（Microsoft Copilot SDK）で使えること、GitHub にソースがあれば Dreaming やコード検索などの追加の価値が得られることを説明しました。バグのトリアージや自動修正のような共通ユースケースは、標準機能として使いやすくしていく方針です。
