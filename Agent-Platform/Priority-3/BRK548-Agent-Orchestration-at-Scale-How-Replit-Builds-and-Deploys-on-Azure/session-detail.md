# BRK548 Agent Orchestration at Scale: How Replit Builds and Deploys on Azure

## 1. はじめに

- **クラウドエージェントのフレームワーク**：作業を依頼すると、その作業がクラウド上のサンドボックスでリモート実行され、さまざまなツールに接続して処理を進めます。発表者は、Claude や OpenAI Codex のような存在に多くの点で似たフルスタックなプラットフォームだと説明しています。

### 5.4 アーキテクチャの全体像

アーキテクチャは、クライアントから社内サービスまで、次のコンポーネントで構成されると説明されています。

- **クライアント**：モバイル、デスクトップ、Web の 3 種類があります。デスクトップクライアントは、Windows 上でユーザーのマシンのネイティブな機能を多く使っていることから、Ignite で注目を集めているそうです。
- **API サービス**：ネイティブに統合された API ゲートウェイとも言える、すべてのリクエストを受ける単一の入口です。
- **API サービスと並ぶその他のサービス**："OSC service" と聞こえるサービス（エージェントの ID を含む ID 全般を扱うサービスの説明と続けて語られており、両者の関係は音声認識の都合で確定できません）と、セルラールーティングのサービスがあります。

ID について発表者は、ここで言う ID は Replit ネイティブな ID であり、Microsoft Entra ネイティブな ID ではないと断っています。そのうえで、Entra の上に載せる形でも多くの機能をサポートしていると述べています。

リクエストの流れは次のとおりです。呼び出しは API サービスを通り、**セルラーメッシュ**に入ります。これは、どのクラウドにまたがっても動く、グローバルに分散したメッシュです。エージェントの状態、サンドボックス、デプロイの大半は、社内ではここでホストされています。この構成により、どのエージェントがどの操作をしたかが分かる強力なエージェント ID と、テナンシー（利用者ごとの分離）、そして利用者が指定するクラウドインフラへのデプロイが実現できる、という説明です。

### 5.5 エージェントとユーザーのアイデンティティ

発表者は、最近は「ユーザーが操作する」だけでなく、「ユーザーに代わってエージェントが操作する」ケースがあり、これが解くべき中心的な問題の 1 つだと説明します。そこで Replit は **委任された権限（delegated authority）** の仕組みを作りました。

1. ユーザーが、自分の権限と許可を、作業を行うエージェントに委任します。
2. エージェントは、その権限を持って動きます。
3. ただし、権限を絞り込めることが重要です。トークンの中の権限を絞るために、"macaron model"（音声認識の都合で表記が確定できません）と呼ぶ仕組みを使っています。
4. オーナーであるユーザーの権限を、エージェントがそのまま継承することはありません。エージェントは権限を絞り込まれ、それぞれが自分のスコープの範囲内、つまり Replit の境界の中だけで動きます。

この仕組みの利点として、Replit のプラットフォーム内の操作だけでなく、コネクタサービスを通じた外部での操作も、起動したエージェントとユーザーの両方に帰属させられる点が挙げられています。

### 5.6 セルラーアーキテクチャを使う理由

発表者が、この講演で特に強調したいことの 1 つとして挙げているのがセルラーアーキテクチャです。Replit の中核サービス（エージェントのワークロードやデータを含む）と、ミニアプリを、任意のクラウドにデプロイできるようになるためです。発表では Azure を例に説明していますが、セルラーアーキテクチャのおかげで、Replit をどこにでもデプロイでき、同じ機能が得られるとのことです。

採用の理由として、次の 4 点が挙げられました。

- ユーザーデータの分離が明確になる
- スケーラビリティが、単一のクラウドプロバイダーに提供できる範囲に縛られない
- セキュリティ境界として重要である
- bring your own cloud（自分のクラウドで動かす）提供と、シングルテナント提供の土台になる

### 5.7 1 つのセルの中身

1 つのセルは、Azure 上のセルラーデプロイにあたります。すべて Kubernetes 上にホストされ、拡張部分は利用者のクラウド側にあります（"the extension is in your cloud" と述べていますが、「拡張」の具体的な意味は発表では説明されていません）。セルの中には次のコンポーネントがあります。

**(1) エージェントの状態とセッションのサービス**

エージェントが正確な状態を保ち、ユーザーがページを更新しても状態を失わないために必要なものがそろっています。その状態サービスを使い、サードパーティのプロバイダーとも通信するのがエージェント本体です。これらはすべて利用者の境界の内側で動き、内部の通信は gRPC で行われます。

**(2) エージェントの実行**

エージェントの実行には **durable object モデル** を使います。エージェントに対して、次に取るべき行動を「プッシュ」する考え方です。状態マネージャーは durable object の 1 種で、エージェントのステートマシンにおける状態遷移を管理します。これにより、障害をまたいで進捗が保たれ、エージェントの状態が固まったままにならず、ユーザーは障害から簡単に復旧できます。ワークロードの再起動をまたいでも同様です。

さらに、非常に長いワークロードも実行できます。発表者は、発表当日の正午ごろに公開したばかりの **missions** を例に挙げ、missions のワークロードは数週間にわたって動くと述べています。例えば、エージェントに広告費の最適化を頼むと、エージェントが長い時間をかけて変更を試し、最適化を進めるというものです。これを支えるのが durable object とエージェント実行のフレームワークだ、と説明しています。

**(3) micro VM クラスター（サンドボックス）**

Replit のチャットごとに、エージェントは自分専用のコンピューターとも言える micro VM を持ちます。この micro VM は Kubernetes クラスター内で動きます。最も重要なのはセキュリティで、「自分の境界の中でエージェントが何を実行でき、そこから抜け出せるのか」が焦点になります。そのため **多層防御（defense in depth）** の方針で守っており、発表では次の点が挙げられています。

- 生成されたコードを、信頼できない入力として扱う
- この境界の中で、コンピュートを分離する
- ファイルシステム、ネットワーク、認証情報へのアクセスを制限する（ネットワーク全体、あるいはサンドボックスの一部を個別に遮断することもでき、動いているエージェントの種類に応じて使い分ける）
- リソース使用量に上限を設け、騒がしい隣人（noisy neighbor）が出ないようにする

発表者は、サイバー攻撃に長けた高度なモデルが出てきているので、こうした制御は今後ますます重要になると述べています。

**(4) デプロイの仕組み（ミニアプリ向け）**

ミニアプリのインフラ全体を管理する、デプロイのワークフローマネージャーとコントロールプレーンがあります。

- コントロールプレーンは状態を持ちます。SQL データベースを関連付けていて、各デプロイの基盤リソースの状態を追跡します。
- ワークフローマネージャーは、おおよそ CI/CD に相当する、Replit ネイティブの仕組みで、実際にデプロイを実行します。

発表者が挙げた使い方の例は、人事チーム向けの「社員検索」ツールです。ユーザーがエージェントに話しかけると、エージェントが micro VM 上でアプリを開発し、そのまま Replit を通じてデプロイして、社内のエンドユーザーに公開します。この一連は Azure 上のシングルテナントまたは Cloud Prem で動きます。そのうえで、アプリは、コンピュートとしての VM（発表中は "Reserve VM" と聞こえます）と、アプリ用のデータベースにデプロイされます。これらのアプリは別々に存在し、データも含めて Replit のアーキテクチャ全体で管理されます。

発表者は、この全体をパッケージ化し、利用者が働いている場所ならどこにでもデプロイできる、つまりクロスクラウドで、どのクラウドにもデプロイできるようにしたいという考えを示しています。想定する利用者は、アイデアを持った一般の人から、データの安全性を確保する必要がある世界最大級の企業まで、幅広いとのことです。

### 5.8 Cloud Prem と Microsoft との協業

全体の構成の下にはサービスメッシュがあり、セルはどこにでもデプロイできます。そこで、今年後半にリリースする予定の **Cloud Prem** は、Replit のすべてを含むセル 1 つ分を、利用者自身の Azure テナントにデプロイできるようにするものです（発表中には "Cloud Prime" とも聞こえます）。

これにより、エージェントの利用、データ、サンドボックス、すべてのデプロイ、そしてそれらの状態が、利用者のもとにあり、Azure を通じて管理されます。発表者は、クラウドエージェントとアプリを自社のインフラ全体に安心して展開するために必要なテナンシーが得られる、と説明しています。

Microsoft については、この 1 年ほど良いパートナーであり、Fabric 側と Cloud Prem の両方で協業してきたと述べています。

### 5.9 Q&A

**Q1：アプリ用に生成されたコードはどこに置かれるのか。**（質問の後半は音声認識の都合で聞き取れず、比較対象の置き場所は確認できません。）

**Q2：Replit は durable execution（耐久的な実行）をどう実現しているか。**

## 7. 注意点・発表者の気付き

発表では、警告や失敗談という形では語られていませんが、次の点が、発表者が重要だと述べた設計上の注意点です。

- エージェントは、オーナーであるユーザーの権限をそのまま継承せず、スコープを絞った権限で動く。
- サンドボックスでは、生成コードを信頼できない入力として扱い、エージェントがサンドボックスから抜け出せるかどうかを常に意識する。サイバー攻撃に長けた高度なモデルが出てくるほど、この制御は重要になる。
- エージェントの状態が固まったままにならないよう、durable object で進捗を保持し、障害やワークロードの再起動をまたいでユーザーが簡単に復旧できるようにしている。
- Replit のアイデンティティは Replit ネイティブであり、Microsoft Entra ネイティブな ID ではない（Entra の上に載せる機能は多くサポートしているとのこと）。
- Cloud Prem は、発表の時点では「今年後半にリリース予定」の提供物です。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **自分の境界の中で持てる**：Cloud Prem では、エージェントの利用、データ、サンドボックス、デプロイ、状態のすべてを、自分の Azure テナントで持てる。
- **クラウドの縛りがない**：セルラーアーキテクチャにより、特定のクラウドプロバイダーの範囲に制約されず、どのクラウドにも同じ機能をデプロイできる。
- **操作の追跡ができる**：委任された権限により、プラットフォーム内外の操作を、エージェントと、その依頼元のユーザーの両方に帰属できる。
- **長時間の仕事を任せられる**：missions のように数週間続く作業でも、障害をまたいで進捗が保たれる。
- **社内ツールを作って公開できる**：エージェントが micro VM 上でアプリを作り、そのまま公開できる（人事向けの社員検索ツールが例）。
- **開発速度の実績**：Replit 社内では、エンジニア 1 人あたりの出力が約 3〜4 倍になり、リバート率とインシデント率は下降傾向にある。

## 9. まとめ

Replit は、ミニアプリの構築基盤であると同時に、クラウドエージェントの実行基盤です。発表者は、その基盤を、セルラーアーキテクチャ、委任された権限のアイデンティティ、durable object によるエージェント実行、micro VM のサンドボックス、ワークフローマネージャーとコントロールプレーンによるデプロイ基盤の組み合わせとして説明しました。

この構成を、今年後半にリリース予定の Cloud Prem で、利用者の Azure テナントに丸ごと置けるようにする計画です。発表者は、Microsoft とは Fabric と Cloud Prem の両面で協業していると述べています。Q&A では、生成コードの置き場所が Replit ネイティブな永続ファイルシステムであること、durable execution に Restate を使い、その理由が「プッシュモデルで、エージェントの応答感を保つため」であることが示されました。
