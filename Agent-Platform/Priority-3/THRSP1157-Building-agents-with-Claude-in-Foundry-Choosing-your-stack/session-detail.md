# THRSP1157 Building agents with Claude in Foundry: Choosing your stack

## 1. はじめに

このセッションは、Claude を使って本番レベルのエージェントを作るときに、「どこまで自前で作り、どこから既製品を使うか」をどう決めるかを整理した約 22 分の発表です。登壇者は Anthropic の applied AI engineer で、Anthropic 自身が Claude Code などを作る中で学んだことを、**モデル・ハーネス（harness）・インフラ**の 3 層に分けて説明します。そのうえで、Anthropic の 3 つの開発者向けサービスと、Microsoft の製品（Claude in Foundry、Microsoft Agent Framework、Copilot Studio、Foundry hosted agents）を、層ごとに対応づけています。

## 5. 発表内容の詳細

### 5.1 エージェントとは何か、何が変わったか

登壇者は、エージェントを「**目標を達成するために、ループの中でツールを使うモデル**」と定義します。モデルがツールを要求し、ツールが実行され、モデルが結果を読んで解釈し、次に何をするかを決める、という流れをタスクが終わるまで繰り返します。2024 年にエージェントが主流になったときと、ループ自体は同じです。変わったのは周囲です。

#### モデルの進化

モデルの能力を測る方法の 1 つとして、登壇者はベンチマークを挙げます。代表的なものが SWE-bench Verified（発話では "SWI Bench Verified" と聞こえます。音声認識の都合で表記が確定できません）で、実際のコーディングタスクの集合です。

- 2024 年 10 月、当時の最新モデルだった Sonnet 3.5 は、約 50%。
- それから 2 年弱で、Anthropic の最も賢いモデル（発話では "Fable" と聞こえます。音声認識の都合で名称が確定できません）は 90% 超となり、ほぼ飽和している。

賢いモデルを使う利点は、より良い計画が得られ、自分の間違いにもよく気づき、各ステップで必要な助けが少なくなることです。

#### ツールと環境の進化

ただし、エージェントは、持っているツールとコンテキストの範囲でしか力を発揮できません。賢いモデルを生かすために、より良いツールと環境が必要になりました。登壇者はタイムラインを次のように示しています。

- 2024 年：Claude がツールを呼べるようになり、computer use（画面上でマウスを動かす）が使えるようになった。
- 2025 年：サンドボックス、コード実行、ファイルシステムという「働く場所」が与えられ、その後、スキル（skills）とメモリ（memory）に抽象化された。

### 5.2 Claude が次の Claude を作る：進化の例

登壇者は、Anthropic 自身の RSI レポート（発話では "our RSI report"）から、Claude が将来の Claude モデルの開発に使われてきた様子を紹介しています。

1. 2021〜2023 年：チャットボットにアドバイスを求め、コードを貼り付けて、返ってきた助言を IDE に貼り付けていた。
2. その後：コーディングエージェントが、小さな機能を書くようになった。
3. 現在：自律的なエージェントが、他の Claude の群れ（fleets）を管理し、製品や機能のほぼ全体を開発している。

今後のモデルでも、ますます多くのコードを Claude が書くようになる、というのが登壇者の見通しです。このような長期（long horizon）で自律的な仕事を支える構成を、どう作るかが、この発表のテーマだと述べています。

### 5.3 スタックの 3 層：モデル、ハーネス、インフラ

登壇者が、お客様との会話で毎日使っているというメンタルフレームワークです。

**モデル**
どの Claude モデルを選ぶかについては、知能、価格、レイテンシーのバランスで選ぶことを勧めています。Claude には Haiku、Sonnet、Opus、Fable というファミリーがあります。加えて、モデルをどこで調達し、どこでホストするかにも、考えるべき細かな点があります。

**ハーネス**
エージェントに何を持たせるかです。登壇者は「新しいチームメイトが入ってくる」というたとえを使っています。新人には、仕事の文脈を教え、wiki、システム、コードへのアクセスを与えます。それとは別に、特にテック企業ではノートパソコンが必要です。ノートパソコンは自分で作ろうと思えば作れますが、普通は既製品を使います。エージェントのハーネスも同じで、**ループ、権限管理（permissions）、エラーからの回復、コンテキスト管理は既製品を使い**、自分のプロダクト・システム・ユースケースの中でエージェントを機能させる部分（＝エージェントを「自分のもの」にする部分）に投資することを勧めています。

**インフラ**
エージェントをノートパソコンで動かすことはできますが、ノートパソコンを閉じてもクラウドで動き続けてほしいはずです。エージェントの複数のインスタンスを同時に動かしたい、1 つまたは複数のサンドボックスが必要で、それらを起動して堅牢化（harden）する必要もあります。エージェントを本番システムに移すときに決めなければならない、重要な判断です。

### 5.4 Anthropic の 3 つの開発者向けサービスと、そこから学んだこと

登壇者は、モデルにアクセスするための主要な開発者向けサービスは 3 つあり、サービスが進むごとに、スタックの上位までを Anthropic が担う、と説明します（スライドではオレンジが Anthropic の提供範囲で、残りは自分で作って運用する）。

| サービス | Anthropic が担う範囲 |
| --- | --- |
| Messages API | モデルへの最も直接的（bare metal）なアクセス |
| agent SDK | ループとハーネス |
| Claude Managed Agents（CMA） | 本番インフラまで |

#### Messages API

最も直接的なアクセスで、file API や code execution API などでツールや機能を設定できます。最も基本的な形は、ツールを付けてリクエストを送り、回答またはツール呼び出しを受け取る、というものです。初期の要約やチャットボットの構築はここから始まりました。Azure では **Claude in Foundry** 経由で使えます。

エージェント機能に使ううちに分かったのは、開発者は引き続き、最大限の粒度と設定可能性（raw building blocks）を求めるが、ループ、権限、セッション、オブザーバビリティ、認証情報、ホスティング、サンドボックスをすべて自分で書く必要がある、ということでした。そこで、これらを 1 つずつ Anthropic 側で解決し始めた、と説明しています。

#### agent SDK

Claude Code を作る中で、良いハーネスに必要なものを学び、それを **agent SDK** として開発者に提供しました。Claude Code を動かしているのと同じハーネスを、Python と TypeScript のライブラリとして使えます。このハーネスで作ると、次のものが最初から得られます。

- リポジトリの検索やテストの実行などのための、ファイル・コードツール
- コンテキスト管理
- サブエージェント（sub-agents）
- 権限管理（permissioning）

人が間に入る Claude Code のようなエージェントに向いていますが、権限の設定を変えてヘッドレスで動かすこともできます。ボイラープレートのエージェントループを自作することもできますが、Claude モデル向けに最適化された既製品を使えば、より賢いモデルが出るたびに Anthropic が保守・改良していきます。

#### Claude Managed Agents：brain と hands の分離

長時間動くエージェントを作るようになると、ハーネスに別の要素が必要になりました。今年のリリースには Claude Tag や Claude Duet（長時間動く、パーソナルアシスタントに近いエージェント）が含まれます（製品名は音声認識の都合で表記が確定できません）。

最初の設計は、agent SDK に近く、ループ、サンドボックス、セッションを 1 つのコンテナに入れていました。ところが、そのコンテナが落ちると、何時間もタスクを実行しているエージェントが困ります。そこで 2 つに分け、**brain（脳）と hands（手）**という考え方にしました。

- **brain**：Claude へのアクセスと、エージェントのオーケストレーション（エージェントループ）。
- **hands**：コードを実行し、ファイルを変更する場所（サンドボックス環境）。

片方を入れ替える必要が生じても対応できるよう、両者を分離しています。Claude Managed Agents はこの設計を製品にしたものです。Anthropic が brain を Anthropic の本番インフラで動かし、hands（サンドボックス）は **Anthropic のクラウドで動かすか、自分の Azure サブスクリプション内のセルフホストのサンドボックスを使う**ことができます。この brain と hands を分けるパターンは、どのスタックでも使えると登壇者は述べています。

分離で得られるものは次のとおりです。

1. **回復**：サンドボックスが落ちても、別のものを起動できる。
2. **速さ**：コード実行やファイルシステムが不要なリクエストは、速く応答できる。
3. **安全性**：認証情報をサンドボックスの外に置ける。これは **vaults** として導入した機能。
4. **ネットワーク内実行**：セルフホストのサンドボックスなら、ツールを自分のネットワーク内で動かせる。大規模に、複数のセッションを並行して、それぞれ専用のサンドボックスで動かしたい場合に向く。
5. **既製のフロンティア機能**：スタックの上位まで担ったため、**dreaming** や **graded outcomes** のような機能を既製で提供できる。

長時間かかるタスクや、既製のプリミティブとフロンティア機能を使って任意のエージェントを作りたい場合に向く、と説明しています。

#### 完全セルフホスト版（プライベートベータ）

Managed Agents は今年の夏に発表され、お客様に好評でした。一方で「このハーネスは素晴らしいが、全部を自分の環境内で動かしたい。データに関する規制要件がある」という声が出たため、**先週、Claude Managed Agents の完全セルフホスト版**を出しました。プライベートベータで、設計は同じですが、brain（エージェントループ）も hands（サンドボックス）も、自分側で動かします。長時間のエージェントにフロンティアのハーネスを使いたいが、データ規制要件に従う必要があるチームに向く、と説明しています。

#### 3 つに共通して持ち越せるもの

どのサービスを選んでも持ち越せるのは、**自分のシステムとデータへのアクセス（MCP など）と、エージェントに期待する動作を書き下したプロンプトとスキル**です。モデルは変わり続け、ハーネスも進化するでしょうが、これはエージェントを自分のプロダクト向けに最適化する部分なので、ここに投資するのがよいというのが登壇者の予想です。

### 5.5 Microsoft の製品との対応

登壇者は、左側ほど自分で作る範囲が広く、制御は大きいが保守も増える、右側ほど既製品が増え、本番到達は速いが柔軟性と制御は下がる、という「メニュー」のスライドを示します。どこに着地しても、MCP、スキル、プロンプトは自分のものです。

#### モデル層：どこで Claude を手に入れるか

問いは 2 つあります。Claude をどこで調達するか、そしてモデルが実際にどこでホストされるか、です。

**Claude in Foundry** で得られるもの：

- Entra ID でのサインイン。
- Azure の請求に載り、対象のお客様は Azure の commit を消化できる（burn down）。
- ホストの選択：
  - **Azure がホストする場合**：Azure インフラ上の Anthropic サービス。対応モデルには US only の選択肢があり、**ほとんどの Foundry ワークロードで、まずはここから始めることを勧める**。
  - Messages API の特定の機能（code execution、files API など）が必要な場合は、Claude in Foundry でも使えるが、モデルが **Anthropic のインフラ上でホスト**される形でのアクセスになる。
- Claude Managed Agents のように Anthropic がホストする製品を使いたい場合は、**ファーストパーティのモデルアクセス**（Anthropic から直接、Anthropic がホスト）で入手する。

#### ハーネス層

Agent SDK、Claude Managed Agents に加えて、Microsoft の提供として次の 2 つが紹介されました。

| 製品 | 説明 |
| --- | --- |
| Microsoft Agent Framework | Microsoft のオープンソースのフレームワーク。複数モデルを同時に使う、エージェントまたはマルチエージェントのワークフローに向く。.NET と Python で提供。 |
| Copilot Studio | Microsoft のローコード。ループとホスティングが組み込み。管理者が有効化し（発話では "turn it on in Claude" と聞こえます）、ビルダーがモデルを選び、エージェントにさせたいことを平易な言葉で説明すると、指示文（instructions）が自動で下書きされ、コネクターとトリガーが推奨される。 |

選び方は次のとおりです。

- マルチモデルが必要なら Microsoft Agent Framework。
- ローコードなら Copilot Studio。
- 一から始めて Claude で作るなら、**agent SDK か Managed Agents**（特にタスクが何時間も動く場合や、指数関数的な進化に備えたい場合）。
- ループの各ステップを完全に制御したいなら、Messages API でハーネスもインフラも自分で作る。

#### インフラ層

CMA や Copilot Studio のようなハーネスを選べば、インフラは Microsoft と Anthropic がホストするので考えなくてよくなります。一方、agent SDK や Microsoft Agent Framework を選んだ場合は、エージェントをホストして実行環境（runtime）を与える方法が必要です。Foundry では **Foundry hosted agents** が推奨されています。

Foundry hosted agents は、エージェント用の **managed runtime** です。ハーネスを使った、あるいは自作のエージェントコード（ループ）を、Foundry が動かすコンテナに入れます。得られるものは次のとおりです。

- セキュリティ、スケーリング、ロギング。
- アプリから呼び出せるエンドポイント。
- セッションごとに 1 つの、分離されたサンドボックス（ユーザーが数時間後に戻ってきてもファイルが残る）。
- エージェント固有の Entra ID によるアイデンティティ。触れてよいものを決められる。
- Application Insights によるオブザーバビリティ（エージェントが何をしたかを確認）。

### 5.6 ユースケース別の推奨構成

登壇者は、6 種類の例を挙げています。

| ユースケース | 推奨構成 | トレードオフ・補足 |
| --- | --- | --- |
| 教育アプリ。学生が何週間にもわたり繰り返し戻ってくる。エージェントを時間とともに良くしたい。小さなチームで、PMF を見るため最速で本番に出したい | **Claude Managed Agents** | Anthropic がループを動かし、サンドボックスとセッション履歴が得られる。メモリが既製で組み込みなので、学生が使うほどエージェントが良くなる。ただし**パブリックベータ**で、Anthropic から直接入手する必要がある。 |
| 保険会社。複雑な保険金請求（claims）を何時間も処理する。規制要件のため、すべて自社環境で動かす必要がある | **セルフホスト版 Claude Managed Agents** | brain と hands の両方を自社ネットワーク内で動かす。サーバーの用意、アップグレード、データベースなどに少し余計な作業が要る。データ規制要件がある場合に有力。 |
| エンジニアリングチーム。CI パイプライン内で、ビルドが失敗したらログを読み、ビルドして、壊れた箇所を直すエージェント | **Claude agent SDK ＋ Claude in Foundry ＋ Foundry agent service の hosted agent（runtime）** | このエージェントは Claude 専用になり、セッション、認証情報、モニタリングは Foundry の部品で配線する必要がある。**この講演の最後に迷ったら、まずここから始める**ことを勧める（合理的で、必要な設定の自由度もある）。 |
| 複数モデルが必要。アプリにモデルピッカーを付けたい | **Microsoft Agent Framework**＋Foundry agent service の hosted agent としてデプロイ | Anthropic 以外のモデルを含め複数モデルにまたがる柔軟性があるが、Claude を中心に使う場合、ハーネスは Claude に最適化されておらず、最高の性能が出ない可能性がある。 |
| ノーコード／ローコード。M365 を多用する HR チーム | **Copilot Studio** | 管理者が有効にし、エージェントを作る人が Claude を選んで、エージェントを説明すると、すぐ得られる。 |
| すべてを最大限に制御したい。モデルが良くなるのに合わせてループを自分で作り、保守する覚悟がある | **Messages API** で自前のハーネスを作り、おそらく Microsoft のインフラにデプロイ | 設定の自由度が最大。 |

## 7. 注意点・発表者の気付き

- **ローカルのプロトタイプは簡単でも、本番は難しい**：本番への移行と、何の上に作るかの判断が難所。
- **ホスティングの違い**：Claude in Foundry で Azure がホストする場合は US only の選択肢があり、多くの Foundry ワークロードで推奨の出発点。ただし code execution や files API といった Messages API の特定の機能を使うには、Anthropic のインフラ上でホストされるモデルへのアクセスになる。Managed Agents は、Anthropic から直接のファーストパーティアクセスで入手する。
- **ステータス**：Claude Managed Agents はパブリックベータ（5.6 の教育アプリの例での発言）、完全セルフホスト版はプライベートベータ。
- **セルフホスト版の手間**：サーバー、アップグレード、データベースを自分で用意する必要がある。
- **Claude 専用になる点**：agent SDK ＋ Foundry の構成は Claude 専用で、セッション・認証情報・モニタリングの配線が必要。
- **マルチモデル向けハーネスの性能**：Microsoft Agent Framework は Claude に最適化されておらず、性能が最高にならない可能性がある。
- **ハーネスや製品の変化を前提にする**：モデルもハーネスも変わるので、MCP・スキル・プロンプトの資産に投資する。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **Claude in Foundry**：Entra ID でサインインでき、Azure の請求に載り、対象のお客様は Azure の commit を消化できる。
- **Claude Managed Agents**：既製のループ、サンドボックス、セッション履歴、メモリ、vaults（認証情報をサンドボックス外に置く）、dreaming や graded outcomes のような機能が得られる。brain と hands の分離で、サンドボックス障害からの回復や、コード実行が不要なリクエストの応答の高速化ができる。
- **セルフホスト版**：データ規制要件があるチームが、フロンティアのハーネスを自社環境で使える。
- **agent SDK**：Claude Code と同じハーネスを、ファイル・コードツール、コンテキスト管理、サブエージェント、権限管理付きで使える。Anthropic が保守する。
- **Foundry hosted agents**：セキュリティ、スケーリング、ロギング、セッション単位のサンドボックス、エージェント固有の Entra ID、Application Insights によるオブザーバビリティが得られる。
- **Copilot Studio**：ローコードで、指示文の下書き、コネクターとトリガーの推奨が自動で得られる。

発表では、具体的な顧客事例や数値による効果測定（コスト削減額など）には触れられていません。

## 9. まとめ

エージェントのループは変わっていませんが、モデルの進化とツール・環境の進化により、エージェントができることは大きく広がりました。本番で動かすスタックは、**モデル（Claude in Foundry でどこから調達・ホストするか）、ハーネス（agent SDK、Claude Managed Agents、Microsoft Agent Framework、Copilot Studio、Messages API）、インフラ（Foundry hosted agents など）**の 3 層で考えます。

登壇者のおすすめは、迷ったときは Claude agent SDK、Claude in Foundry、Foundry の hosted agent の組み合わせから始めること、長時間のタスクや記憶が要るなら Claude Managed Agents、データ規制があるならセルフホスト版、複数モデルなら Microsoft Agent Framework、ローコードなら Copilot Studio、最大の制御が要るなら Messages API です。どれを選んでも、MCP でのシステム・データへのアクセス、スキル、プロンプトは持ち越せるので、そこに投資するのがよい、というのが最終的なメッセージです。
