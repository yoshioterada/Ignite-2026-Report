# THR1804 Build an Agent Harness with Microsoft Agent Framework

## 5. 発表内容の詳細

### 5.1 harness とは何か

私たちが毎日チャットで使っているのは、モデルに質問を送り、応答を受け取る「リクエスト／レスポンス」の形です。登壇者は、Foundry にモデルをプロビジョニングしたときの API を例に、渡せるのはメッセージ履歴（システムメッセージ、ユーザーの発言）とツールの定義であり、応答を受けて会話スレッドをつなげていくことはできるものの、そこにはそれ以外のループが無いと説明します。LLM が「このツールを呼びたい」と応答しても、ツールを実際に呼ぶのは呼び出し側で、その結果を LLM が受けて動くループは API 自体には含まれていません。これを登壇者は chat responses プロトコル（の働き方）と呼んでいます。

より複雑なことをさせるには harness が必要です。harness は、このリクエスト／レスポンスを繰り返し呼び出す層だと説明されています。流れの例は次のとおりです。

1. harness が LLM に「ユーザーはこうしたい。計画（ステップの一覧）を作って」と依頼する
2. 計画を受け取ったら、「計画はこれ。最初のステップだけに集中して実行して」と再度依頼する
3. 応答を受けたら、「ステップ 1 は終わったか、追加の操作が必要か」を確認する
4. ツール呼び出しがあれば、harness が関数を実行し、結果を LLM に返す
5. タスクが完了したと LLM が判断するまで、これを繰り返す

harness が持つ機能として、次が挙げられました。

| 機能 | 説明 |
| --- | --- |
| 計画・分解 | 計画を立てて小さなタスクに分解するツール |
| 状態管理 | どの項目が解決済みで、どれが未解決かを追跡する（AI を使うアプリの画面でも見られる、と説明されました） |
| セッションの圧縮（compaction） | セッションが数分、数時間と長くなると、イベント履歴が膨大になる。セッションの冒頭を要約して、コンテキストウィンドウに収める |
| メモリへのアクセス | harness の下では、すべてのコンテキストを LLM に渡さず、一部だけを選んで渡してトークンを節約できる |
| 複雑なツール呼び出し | 繰り返し、ループ、条件、場合によっては並列の呼び出し |
| セッションの永続化と再開 | 人の承認が必要なステップで担当者が休暇中なら、セッションは数週間に及ぶこともある。メモリ上に置き続けたり、サーバーが 1 か月再起動しないことを期待したりするのは現実的でないため、保存して後で再開できる仕組みが必要 |
| サンドボックス | モデルにファイル作成やプロセス実行を許すなら、安全な形で実行できるよう、サンドボックスで動かす必要がある |

### 5.2 Microsoft Agent Framework の位置づけ

Microsoft Agent Framework は、C# などの .NET 言語と Python で使える SDK とランタイムです。多くのプロバイダーに対応しているため、プロバイダーで制約されることは少ない、と説明されています。また、最近使われ始めたプロトコルに対応しており、挙げられたのは次の 3 つです。

- **MCP**（Model Context Protocol）
- **Agent to Agent**
- **AGUI**（音声認識では "AGY" とも聞こえます）：エージェントが行っている活動（イベント）をユーザーインターフェースに送り、画面に表示してユーザーがモデルとやり取りできるようにするプロトコル

登壇者は、エージェントを作る方法は他にもある（他のセッションで紹介される）が、最も細かな制御、柔軟性、独自ロジックを差し込める拡張ポイントが欲しいなら、Microsoft Agent Framework が適していると述べています。かなり低レベルな作り方です。また、以前に使われていた Semantic Kernel は他のライブラリと統合されて Microsoft Agent Framework になった、つまり Microsoft Agent Framework は Semantic Kernel から発展したものだと説明しています。

### 5.3 デモの題材：請求書作成の業務

登壇者の会社には、顧客向けのプロジェクトがあり、コンサルタントが月末に、作業内容・かかった時間を書いた Excel のレポートを作ります。コンサルタントごとにフォルダがあり、毎月新しい Excel ファイルが増えます。顧客は Excel を見て承認することを求めるため、この部分は手作業のままです（AI で作る人もいる、という補足がありました）。レポートには、誰が、どの日に、何時間、どの作業をしたかが書かれ、最後に合計行があります。

顧客から承認と PO 番号をもらえれば請求書を発行できます。自動化したいのは、その後の次の流れです。

1. エージェントが SharePoint にアクセスし、該当月のレポートを探す
2. 合計時間を確認する。合計行が無いことがあり、その場合はエージェントが状況を判断して対処する（100 人いれば、1 人は想定の形式と合わないはず、という理由）
3. MCP サーバーを使い、社内の請求システムに請求書を作る（テスト版で、会議の場から顧客に請求書を送るわけではない）

画面は、デモ用に AI に作らせた非常にシンプルな Web インターフェースを使っています。

### 5.4 コードの解説：アプリケーションの構成

デモ画面の裏側は、.NET 10 で書かれた標準的な ASP.NET Core アプリケーションです。NuGet パッケージは Microsoft.Agents.AI で始まるもので、Microsoft Agent Framework の一部です。サブパッケージとして、harness の実装用、AGUI プロトコルへの対応用、そして OpenAI モデルを使うための OpenAI 用があります（モデルが多様なため、サブパッケージが分かれています）。

Program.cs（アプリの起動部分）は標準的な内容です。

1. 設定の検証：Foundry リソースの URL、API キー、エージェントに使うモデル名が必要
2. AGUI サーバーの追加：AGUI エンドポイントを公開するためにエージェントフレームワークが必要とするサービスを登録する
3. セッションストアの提供：セッションに時間がかかるため必要。デモなので **in-memory の agent session store** を使っており、アプリを再起動すると状態が消える
4. エージェントを作成（このメソッドは後で詳しく説明）し、URL に公開する。Web ページは AGUI プロトコルでこのエージェントと通信する

### 5.5 コードの解説：invoicing agent クラス

エージェントを作るクラスは invoicing agent です。冒頭には定数がいくつかあります。

- **承認が必要なツールの指定**：create invoice を指定している。請求システムに請求書を作る前に承認を求め、他の操作は確認なしに自由に実行できる
- **スクラッチフォルダ**：エージェントは SharePoint からファイルをダウンロードして中を見るため、一時的な状態を保存する一時パスを持つ
- **スキルのディレクトリのパス**
- **システムプロンプト**：業務プロセス全体は記述せず、エージェントが動く環境の一般的なルールだけを書く

なぜプロセスをシステムプロンプトに書かないのか。登壇者の説明では、正確な業務プロセスは時間とともに変わりうるので、スキルファイルを更新すれば済むようにしておき、一般的な条件は変わらないはずだからです。

エージェント作成の手順は、語られた順に次のとおりです。

1. 設定から URL と API キーを取得する
2. MCP サーバーのランタイムを開始する。これは MCP サーバーのためのラッパークラスで、このエージェントは 3 つの MCP サーバーを必要とし、それらはプロセスとして動くため、どのプロセスが動いているかを追跡し、アプリの終了時に止めるためのもの
3. API キーとエンドポイントで **chat client** を作る。これは最初のスライドの左側、つまり「リクエスト／レスポンスだけ」の部分で、後から harness で包む
4. **skills provider** を登録する。フォルダからスキルを探し、エージェントに渡す
5. スクラッチフォルダを準備する（存在すれば削除して作り直す）
6. サーバーツールを登録する。3 つの MCP サーバーは次のとおり
   - SharePoint 用の MCP サーバー：登壇者が自作したもので、エージェントに必要なツールだけを公開しており、SharePoint でできることのすべてはできない
   - Excel MCP サーバー
   - 請求システム用の MCP サーバー（自社の請求システム。名称は音声認識の都合で表記が確定できません）
   - これらはいずれもコンソールアプリで、標準入出力（stdin/stdout）で MCP インターフェースを公開する
7. 各 MCP サーバーが公開するツールをすべて取得する
8. 承認が必要なツールを、**approval required AI function** というラッパーで包む。モデルが「請求書を発行する」と言ったとき、セッションを止めて承認を求め、承認が得られて初めて続行する
9. すべてを組み合わせる。基本的な会話しかできない chat client に、システムプロンプトと MCP サーバーのツールを渡し、AI skills を AI context providers のコレクションに入れ、harness の挙動を調整する

### 5.6 harness のオプションと、セキュリティを意識した絞り込み

登壇者は、IntelliSense で agent harness のオプションを確認することを勧めています。機能が多く、既定で有効なものと、明示的に有効にしないと使えないものがあるためです。

- **to-do provider**：既定で有効。不要なら明示的に無効にする（opt out）
- **file access store**：明示的に有効にする（opt in）必要がある

不要なものは無効にすることが重要だと述べ、このデモでは Web 検索を無効にしました。この業務はインターネット上の情報検索を必要としないためで、これによりエージェントは Web を閲覧するツールを持ちません。さらに、他のプロセスを実行する手段もなく、Python スクリプトを書いて実行することもできません。登壇者は、必要なものだけを与えることがセキュリティの面でも役立つと説明しています。

最後にこれを harness agent として呼び出す（as harness agent の呼び出しと聞こえます）と、harness 全体が組み上がります。harness のロジックは Microsoft Agent Framework に実装済みで、AGUI インターフェース経由で使えます。

### 5.7 harness の拡張ポイント

さらに制御したい場合は、クラスのメソッドをオーバーライドできます。紹介されたのは次の点です。

- **セッションごとの実行の入口**：セッションごとに実行されるメソッドを上書きする。デモでは、「今月」「前月」という概念を扱うため、エージェントが日付を確実に把握するよう、指示に現在の日時を足している。システムプロンプトの一部になるので、エージェントが日付を知るためにツールを呼ぶ必要が無い
- **独自の AGUI イベントの送出**：進捗など UI に表示したい情報を、独自のイベントとして送れる。例えば「モデルを呼び出している」というイベントは既定では有効でないが、ここで出せる
- **イベントのループ**：エージェントが処理するイベントをすべて通るループがあり、独自のフックを差し込める

登壇者は、かなり低レベルだが、その制御と柔軟性が必要なら Microsoft Agent Framework が提供できると述べています。

### 5.8 本番で動かすには

デモでは、シンプルにするために安全な構成にしていません。エージェントが Web アプリケーションのプロセスの中で直接動いており、これは本番では避けるべき構成です。harness は安全な環境で動かす必要があります。

最も簡単なのは、**Foundry の hosted agent service** にデプロイすることです。得られる機能は次のとおりです。

- セッションごとのサンドボックスをプラットフォームが用意するので、サンドボックスの心配が要らない
- スケールする。数千のリクエストが同時に来ても動く
- セッション管理のツールがあり、セッションが 1 か月かかっても、プラットフォームに保存して復元できる
- エージェントごとに固有の ID を持てる。Azure や Microsoft 365 のリソースを呼ぶときに、その ID を使い、エージェントに権限を割り当てられる

これらが不要なら、**セルフホスト**もできます。難しくなく、ただのコンソールアプリで、すべてが正しく設定されていることを確認して動かします。ただし、コンテナの外のファイルにアクセスできる場合は特に注意が必要で、エグレス（外向き通信）が保護されていることを確認する必要があります。

## 6. デモ・手順

このセッションにはライブデモがあります。画面の細部は音声からは確認できず、以下は登壇者が語った範囲です。

**前提（デモ前に語られたこと）**

- エージェントは Web インターフェース（AI に作らせたシンプルなもの）に接続されている
- 画面に出る「考え中」「モデルを呼び出し中」といった表示は、エージェントから Web ページへ届く AGUI メッセージで、ページはそれに基づいて描画している

**実行の流れ**

1. 登壇者がエージェントに、レポートが既に揃っていると伝える
2. エージェントが 2 つのステップを実行し、to-do を作成する。情報が足りないため先に進めず、追加情報を求める
3. 登壇者が PO 番号として 12345 を渡して実行を再開する。ここでも画面は AGUI イベントを受け取って表示しているだけである
4. エージェントは to-do 項目を追跡し、SharePoint 内のファイルを一覧する。ツールの引数も画面で確認できる
5. 途中で、エージェントがスキルにアクセスしたことが画面から分かる（スキルファイルの内容は、下の「スキルファイル」で説明します）
6. あるツールで問題が発生し、AGUI のメッセージとして画面に表示された。それでもエージェントは目的の処理を続けられた
7. 登壇者は 10 月分の請求書を作りたかったが、10 月分のレポートは存在しなかった。登壇者は、このような状況に対処できる点が AI を使う理由だと説明し、決定的なコードで書けば多くの if 文や条件が必要になると述べた
8. 登壇者が「9 月で、同じ PO 番号を使って」と指示する。PO 番号は先の会話に含まれているため、繰り返す必要はない
9. エージェントがレポートをダウンロードし、各ファイルから時間数を抜き出して表にまとめた。時間単価はスキルファイルに定義されており、エージェントはそれを使って金額も計算した
10. 請求システム側でも再計算されるため、エージェントの計算が誤っていても他で補えるが、登壇者は数学的な処理をエージェントに任せるので、人が確認する承認（human in the loop）を置いたと説明している
11. エージェントが請求書の作成に進み、UI に「承認が必要」と表示される。登壇者が承認ボタンを押すと、セッションが復元されてから続行する
12. 2 件目の請求書についても承認する
13. 画面を更新すると、15 年前のシステムだと説明された請求システム（このために作った MCP サーバー経由）に 2 件の請求書が入っていることが確認できた

**スキルファイル**：デモ中に、エージェントが使ったスキルとして紹介されました。マークダウンファイルでヘッダーが付いており、業務プロセス全体を人間の言葉で記述しています。どの MCP サービスでどのリソースにアクセスするかを指示するだけで、特別なものではないと説明されています。

> 補足：デモの途中で、請求システムの応答待ちの時間があり、登壇者はそのあいだにコードの説明に移りました（5.4〜5.7）。デモの途中経過は、コード解説の合間に画面へ戻って確認し、最終結果はコード解説の後に確認しています。

## 7. 注意点・発表者の気付き

- **本番では harness をアプリのプロセス内で動かさない。** デモは簡単さを優先してエージェントを Web アプリのプロセス内で動かしているが、本番では安全な環境が必要です。
- **harness の機能は、既定で有効なものを意識して無効にする。** to-do provider は既定で有効で、不要なら明示的に無効にする。file access store は明示的に有効にする必要がある。必要でない機能（Web 検索など）を外すことが、セキュリティにもなります。
- **セルフホストでコンテナ外のファイルにアクセスさせる場合は、特に注意する。** エグレスが保護されていることを確認する必要があります。
- **承認ステップは、算術のような AI に任せたくない部分に置く。** 請求システムが再計算するため誤りは別の場所で補えるが、人が確認する意図で承認を残していると説明されました。
- デモの in-memory のセッションストアは、再起動で状態が消えます。
- デモ中にツールが 1 つ問題を起こしましたが、エージェントは処理を継続できました（原因は発表では語られていません）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 決定的なコードで多くの条件分岐を書く代わりに、エージェントがレポートの欠落や合計行の抜けといった想定外の状況を自分で処理できる
- スキルファイル（マークダウン）を更新するだけで、業務プロセスの変更に追随できる
- 人による承認を、特定のツール（請求書の作成）に限って差し込める。承認が長期間に及んでも、セッションを保存して再開できる
- Foundry の hosted agent service を使えば、セッションごとのサンドボックス、スケール、セッション管理、エージェント固有の ID と権限の割り当てが得られる
- 必要な機能と権限だけを与える設計（限定した MCP ツール、Web 検索の無効化、プロセス実行の禁止）で、セキュリティ面でも安全にできる

発表では、顧客事例や、時間短縮などの数値的な成果には触れられていません。

## 9. まとめ

harness は、LLM を繰り返し呼び出し、計画、状態管理、セッション圧縮、メモリ、承認、永続化、サンドボックスといった機能で、長く複雑なタスクを完遂させる層です。登壇者は、Microsoft Agent Framework（.NET と Python の SDK／ランタイム。MCP、Agent to Agent、AGUI に対応）を使い、月次の請求書作成を例に、その組み立て方を見せました。

コードの要点は、chat client を土台に、システムプロンプト、MCP サーバーのツール、スキル、harness のオプションを組み合わせ、承認が必要なツールを approval required AI function で包むことです。さらに細かい制御はメソッドのオーバーライドで可能です。本番では、Foundry の hosted agent service にデプロイすれば、サンドボックス、スケール、セッション管理、エージェントの ID が得られ、セルフホストの場合はコンテナ外のファイルアクセスとエグレスに注意する、というのが結論です。
