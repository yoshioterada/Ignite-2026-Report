# THR1011 Choosing the Right Model

## 1. はじめに

このセッションは、AI エージェントに使う大規模言語モデルをどう選ぶかを、3 つの戦略に分けて紹介する短い登壇です。「いちばん良いモデルを選べばよい」という単純な話に見えて、品質・コスト・レイテンシーのバランスを取ろうとすると途端に難しくなる、という問題意識から始まります。

3 つの戦略は、(1) 開発者が自分で選ぶ、(2) Microsoft Foundry の **model router** に選ばせる、(3) 自分の基準（ルール）を与えて **Microsoft Decision 1.1** に選ばせる、です。後半では、複数のエージェントが連携する構成で、メインエージェントとサブエージェントのどちらに賢いモデルを割り当てるべきかを、実験結果とともに説明しています。

このセッションでは、VS Code 上のエージェントと Microsoft Foundry の画面を使ったライブデモが複数回行われています（6 章）。

登壇者の主張は次の 3 点に整理できます。

## 5. 発表内容の詳細

### 5.1 戦略 1：自分でモデルを選ぶ

登壇者は、次のような設定でエージェントを説明しました。Global AI Community の Taoyuan チャプターリーダーである Ryan（登壇者と同じ名前で話されています）は、イベントの開催日、会場、登録リンクなどの質問をコミュニティから多く受けます。そこで、サポート用の AI エージェントを Microsoft Agent Framework で作り、大規模言語モデルには GPT-6 Luna を選び、Web ページを取得するツールを持たせました。このツールがコミュニティの Web ページから情報を取ってきて、エージェントが質問に答えます。

デモでは、まず GPT-6 Luna で動かし、次にモデルを GPT 6.1 に変えて同じ質問で比較しています（6.1 参照）。ツールとシステム指示が同じなので、入力トークン数は同じで、所要時間もほぼ同じ、出力トークンも近い値でした。違いはコストで、GPT 6.1 Sol（聞こえた表記は「soul」「so」で、音声認識の都合で表記は確定できません）を使うと、GPT-6 Luna より **20 倍高くなる**と述べています。

結論として、簡単な質問なら GPT-6 Luna で十分な品質が得られ、より整理された質の高い回答が欲しい場合は GPT 6.1 を選ぶ、という判断になります。複雑な質問では差が出るかを確かめるため、さらに質問を変えて比較しました。

### 5.2 戦略 2：model router

質問が簡単か複雑かは、ユーザーが投げてみるまで分かりません。そこで登壇者は、Microsoft Foundry の **model router** を紹介しました。model router は、質問に応じて適切なモデルを選んでくれる仕組みで、利点として次の 3 つを挙げています。

1. 効率的で、すばやくモデルを選べる
2. model router が選ぶモデルのサブセット（候補群）を指定できる
3. 透明性があり、どのモデルを選んだかを確認できる

デプロイの手順は、Microsoft Foundry で Build → Models と進み、ベースモデルの一覧からパブリッシャーを Microsoft に絞ると model router が見つかる、というものでした。デプロイ後は自分のモデル一覧に表示されます。エージェントのモデルをこの model router に切り替えて同じ質問を投げ、トレースを見ると、エージェントが実際に model router を使っていること、そして選ばれたモデルが GPT-6 Luna だったことが確認できます。

model router の既定値は、品質とコストのバランスを取る設定です。より **コスト優先** か **品質優先** にしたい場合は、Microsoft Foundry の model router の詳細画面で Edit から設定を変えます。設定できる項目は 2 つです。

| 設定 | 内容 |
| --- | --- |
| モデルのサブセット | Microsoft Foundry がサポートするすべてのモデルを対象にするか、自分で選んだモデル群だけを対象にするかを選ぶ |
| routing mode | 既定は balanced。品質優先またはコスト優先に変更できる |

登壇者はデモで、自分で選んだサブセットに GPT-6 Luna、GPT 6.1 Sol などを入れたと説明しています（モデル名の一部は聞き取りが不明瞭です）。

### 5.3 戦略 3：Microsoft Decision 1.1

「モデルは自分のルールで選びたいが、毎回手動では選びたくない」という場合に、登壇者は **Microsoft Decision 1.1** を紹介しました。これは判断を助けるためのもので、扱える質問は次の 3 種類です。

1. 真偽（true / false、yes / no）を選ぶ
2. 複数の選択肢の中から 1 つを選ぶ（今回のモデル選択はこれ）
3. ある値がどれくらいか、高いか低いかを評価する

> 補足：「Microsoft Decision 1.1」という名称は、音声認識の都合で表記が確定できません。トランスクリプトでは一貫してこの名称で話されていますが、詳しい説明や提供形態は発表では語られていません。

コードでは、種類として 2 つ目（選択型）を指定し、選択肢ごとに基準を書きます。例えば、簡単な質問には GPT 6 Luna を、複雑な質問には GPT 6.1 を選ぶ、という基準です。登壇者の言葉では、これが「自分の基準にもとづいて Microsoft Decision で選ぶ」ということになります。

### 5.4 3 つの戦略の使い分け

| 戦略 | 向いている場面 |
| --- | --- |
| 自分で選ぶ | AI エージェントの目的がすでに決まっていて、範囲が限られている |
| model router | モデルの選択を自動にしたい。モデルのサブセットや、コスト優先・品質優先といった程度の調整はできる |
| Microsoft Decision 1.1 | 自分なりの基準やルールでモデルを選びたいが、自動で行いたい |

ここまでは単一の AI エージェントの話です。

### 5.5 マルチエージェントでのモデル選択

後半は、エージェントが何層にもなるマルチエージェントシステムで、各エージェントにどのモデルを割り当てるかという話です。登壇者の例は、メインエージェントがユーザーの依頼を分解し、サブエージェントを呼ぶ構成です。「サンフランシスコにいる。今日の天気と、何を着ればよいか教えて」という質問を、メインエージェントが 2 つに分けます。

1. weather agent に天気を取得させる
2. fashion agent に服装のアドバイスを出させる

エージェントは 3 つ（メイン、weather、fashion）あり、予算の都合で全員に良いモデルは使えないという前提です。例えば、最良のモデルが 2 つ分、そこまで賢くないモデルが 1 つ分の予算しかない、というイメージです。メインエージェントはマネージャー、サブエージェントはエンジニア（開発者）のようなものです。では、どちらに賢いモデルが必要でしょうか。

登壇者は会場に挙手を求めました。「エンジニアにこそ賢いモデルが必要」と思う人も、「マネージャーにこそ必要」と思う人も多く、どちらも大勢が手を挙げました（Ignite らしく開発者もマネージャーも多い、と述べています）。エンジニアはデバッグなどの難しい問題を扱うから、マネージャーは仕事の割り当て、人の管理、意思決定をするからだ、という理由がそれぞれ語られました。

その前提として、Microsoft Agent Framework は特定のプロバイダーに縛られないオープンなフレームワークだと説明されました。Microsoft Foundry のほか、OpenAI へ直接接続でき、Amazon や Google、Gemini も使え、手元のコンピューターの Ollama のモデルも使えます。

登壇者が行った実験は次のとおりです。

- メインエージェントに、Ollama の Llama 3（3B の小さなモデル）を使った場合
- メインエージェントに、GPT-6 Luna を使った場合（サブエージェントにどのモデルを組み合わせたかの説明は、音声上やや不明瞭です）

結果、メインエージェントに 3B のモデルを使うと **すべて失敗**しました。一方、メインエージェントに GPT-6 Luna を使うと、weather と fashion のサブエージェントに小さなモデルを使っても動きました。理由として、登壇者は次の 3 つの発見を挙げています。

1. マネージャー（メイン）が賢ければ、サブエージェントがそれほど賢くなくても、成功する答えが得られるまで「やり直し、やり直し」を繰り返して呼び出す
2. サブエージェントに優れたモデルを使っても、メインエージェントが賢くなければ、良い答えにまとめ上げられない
3. サブエージェントの担当が、単純なツールだけに特化している場合は、とても小さなモデルでも使える

そこで、登壇者が先ほど尋ねた「どちらに賢いモデルが必要か」への答えは、**マネージャー（メインエージェント）** になります。

### 5.6 まとめでの確認

最後に登壇者は、3 つの戦略を再度整理しました。自分で選ぶ、Microsoft Foundry の model router を使う、そして自分の基準・ルールで選ぶ場合は Microsoft Decision 1.1 を使う、です。AI エージェントの構成そのものは Microsoft Agent Framework で組めると述べています。最後の問いである「誰に賢いモデルを使うか」については、可能ならマルチエージェントのすべてに賢いモデルを使えばよいが、選ぶのであればマネージャーを賢くすべき、と答えました。

## 6. デモ・手順

ライブデモは複数回行われています。VS Code と Microsoft Foundry の画面を使っていますが、画面の細部は音声からは確認できません。語られた範囲を、順に整理します。

### 6.1 自分でモデルを選ぶデモ（GPT-6 Luna と GPT 6.1 の比較）

1. GPT-6 Luna を選んだエージェントに、「イベントはいつか」と尋ねる。エージェントは Web ページ取得ツールを呼んで答えを得た
2. 「登録リンクを教えて」と尋ねる。ライブでページをスクレイピングして情報を取得し、Web ページと照らして正しいことを確認した
3. モデルを GPT 6.1 に変え、エージェントを再起動して、同じ質問を行う。結果はほぼ同じだが、GPT 6.1 の応答のほうが整理されており、リスト形式になっていた
4. 入力トークン数と所要時間はほぼ同じ、出力トークンも近いが、コストが異なる（GPT 6.1 Sol は GPT-6 Luna の 20 倍）と説明
5. 次に、より複雑な質問として、「すべてのイベントを一覧にして、どういうグループかをまとめて」と尋ねる。Web ページの情報をほぼ全部使うため、ツール呼び出しが多く、時間もかかった。まず GPT-6 Luna で実行
6. モデルを GPT 6.1 Sol に切り替えて同じ質問を実行。回答は Markdown の表でイベントを一覧にし、概要もまとめ、今後のイベントと過去のイベントを 2 つのセクションに分けていた。登壇者は「こちらのほうが良いが、コストは高い」と評価している

### 6.2 model router のデモ

1. Microsoft Foundry で Build → Models を開き、ベースモデルでパブリッシャーを Microsoft に絞り、model router を見つける
2. model router をデプロイする。デプロイ後、自分のモデル一覧に model router が表示される
3. VS Code に戻り、エージェントのモデルを model router に切り替える
4. 「次のイベントはいつか」と同じ質問を投げ、トレースを開く。エージェントが model router を使っていること、選ばれたモデルが GPT-6 Luna であることを確認する
5. Microsoft Foundry に戻り、model router の詳細で Edit を開く。モデルのサブセットと routing mode（既定は balanced）の設定画面を見せる。自分のサブセットとして、GPT-6 Luna と GPT 6.1 Sol などを選んだと説明

### 6.3 Microsoft Decision 1.1 のデモ

1. コードで、種類として 2 つ目（選択型）を指定する
2. 選択肢ごとに自分の基準を書く。簡単な質問には GPT 6 Luna、複雑な質問には GPT 6.1 を選ぶという趣旨
3. 最初の質問「次のイベントはいつか」で実行すると、Microsoft Decision 1.1 は GPT 6 のモデルを選んだ（聞こえた表記は「GPT 6 do not」で不明瞭です。簡単な質問向けに Luna を指定していましたが、断定はできません）
4. 別の質問に変えて再度実行すると、今度は GPT 6.1 を選んだ。基準にもとづいて選ばれていることを示した

### 6.4 マルチエージェントのデモ

1. 「サンフランシスコにいる。今日の天気と服装を確認して」と質問する
2. メインエージェントが、まず weather agent を呼び、続いて fashion agent を呼ぶ
3. 答えが返ってくる。登壇者は、特別なブランド（聞こえた表記は「Ryan MVP」）の服に関する内容も出したかったと話していますが、聞き取りが不明瞭で詳細は確認できません。
4. 成功したと述べている

## 7. 注意点・発表者の気付き

- 同じツールとシステム指示、同じ入力であれば、GPT-6 Luna と GPT 6.1 の差は出力の整理のされ方にあり、トークン数や所要時間はほぼ変わりません。差が出るのはコストで、20 倍の開きがあります。
- 質問が簡単か複雑かは事前に分かりません。これが、登壇者が model router を紹介した動機です。
- マルチエージェントで、メインエージェントに小さなモデル（実験では Ollama の Llama 3、3B）を使うと、すべて失敗しました。メインが賢ければ、サブエージェントが小さくても、やり直しの呼び出しで補えます。ただしメインが賢くなければ、サブに良いモデルを使ってもうまくまとめられません。
- 登壇者は実験を「多数」行ったと述べていますが、示されたのは上記の結果のみで、実験の詳しい条件（試行回数など）は語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は、model router の 3 つの特長（効率的に選べる、サブセットを指定できる、選択の理由を確認できる）と、コスト優先・品質優先の調整ができること、そして Microsoft Decision 1.1 で自分の基準を自動の選択に反映できることです。コスト面では、GPT 6.1 Sol が GPT-6 Luna の 20 倍であるという具体的な差が示されており、質問の難しさに応じて使い分ける意義が語られました。マルチエージェントでは、予算が限られるならメインエージェントに賢いモデルを割り当て、担当が単純なサブエージェントには小さなモデルを使えるという配分の考え方が示されています。

## 9. まとめ

モデルの選び方には 3 つの戦略があります。目的と範囲が決まっているエージェントなら自分で選びます。質問の難易度が読めないなら、Microsoft Foundry の model router に選ばせます。サブセットや routing mode（balanced、コスト優先、品質優先）で調整できます。自分のルールで選びたい場合は Microsoft Decision 1.1 に基準を与えます。マルチエージェントでは、まずマネージャー役のメインエージェントに賢いモデルを割り当てるのが、登壇者の実験から得られた答えです。
