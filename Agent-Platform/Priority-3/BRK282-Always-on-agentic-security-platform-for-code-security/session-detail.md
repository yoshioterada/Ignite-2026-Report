# BRK282 Always-on agentic security platform for code security

## 1. はじめに

このセッションは、GitHub の **GitHub Advanced Security** を使って、コードのセキュリティを「常時稼働（always on）」で守る考え方と、その実際の画面を紹介する内容です。AI コーディングエージェントが大量のコードを書く時代に、人手だけでは脆弱性のレビューも修正も追いつかない、という問題意識から始まります。

発表では、常時稼働のセキュリティに必要な要素を 4 つ挙げています。生成されるコードのチェック、既存コードの脆弱性の発見、見つかったアラートの修正、そして組織共通のルールによるガバナンスです。話の大半はライブデモで、リポジトリのルールセット、プルリクエスト上の AI スキャンと CodeQL の指摘、Copilot への修正の割り当て（Agentic Autofix）が順に示されました。

後半の Q&A では、深いスキャン（deep scan）と Emdash の関係、red team / blue team / green team との関係、既存のセキュリティツールとの置き換えやライセンスといった質問に答えています。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK282](https://ignite.microsoft.com/en-US/sessions/BRK282)

## 5. 発表内容の詳細

### 5.1 常時稼働のための 4 つの要素

Eric 氏は、必要な機能として次の 4 つを挙げました。

| 要素 | 説明 |
| --- | --- |
| 生成されるコード | コード生成ツールが脆弱性、ハルシネーションで存在しない依存関係、漏えいしたシークレットを持ち込まないようにする |
| 既存のコード | リポジトリに既にある、バックログで優先付けされてこなかった問題を見つける |
| 修正 | アラートを直す時間と優先順位がないため、エージェントに作業をさせる |
| ガバナンス | 組織で合意した共通ルール（「プレイグラウンドのルール」）で全体を統制する |

### 5.2 生成されるコードのチェック

Eric 氏によると、新しいプロジェクトのコードの大半は、いまや Copilot、Claude、Codex によって生成されています。GitHub 上でこれらのコーディングエージェントを使っている場合は、**生成されたコードが開発者の目に触れる前に**、漏えいしたシークレット、コードの脆弱性、脆弱な可能性のある依存関係が GitHub によってチェックされます。偶然に任せず先回りする仕組みで、エージェントが並行して作業している間も、コードセキュリティとシークレット保護が常に動いている状態になる、という説明です。

### 5.3 脆弱性の発見：決定論的スキャンと AI スキャン

発表では、コードスキャンによる脆弱性の見つけ方を 2 種類に分けています。

- **決定論的（deterministic）スキャン**：既知の脆弱性タイプに対する特定のルールで探します。同じリポジトリに何度実行しても同じ結果になり、計算コストが低く高速です。一方、スキャナーが対応していない言語や、ルールでは届かないコード・脆弱性の種類があります。
- **AI スキャン**：推論を使って、新しい方法や新しい種類のコード、あるいはとても古い種類のコードの脆弱性を探します。

GitHub ではこれまで、コードの大半を占める人気言語の短いリストしか決定論的にスキャンできませんでした。例えば COBOL は対象外でしたが、AI を使ったスキャンで対応できるようになりました。Eric 氏は、これでレガシーコードの保守プロジェクトがより現実的になると述べています。開発したチームが、もうその仕事をしていないことが多いためです。

（会場にした質問：GitHub で最も人気のある言語は何か。答えは JavaScript / TypeScript。COBOL を書いたことがある人にも挙手を求め、冗談を交わしています。）

### 5.4 修正：Agentic Autofix

バックログに 100 件のアラートがある程度ならまだしも、GitHub のお客様には**数万件**のアラートを抱えているところもある、と Eric 氏は話します。開発チームが自力で直すだけではバックログは縮まず増え続けます。そこで修正をエージェントに任せるのが、先月（発表時点）に導入された **Agentic Autofix** です。

- 最大 **25 件**のオープンなアラートを Copilot に割り当てられます。
- Copilot はコードベースを調べ、複数の解決策を試して（これは動く、これはダメ、のように）、最良の解決策を選びます。
- 完成した形のプルリクエストを作成し、開発者はそれをレビューしてコミットします。
- 1 件ずつ直列にではなく並行して進められ、優先度の高いリポジトリやプロジェクトのアラートから消化できます。

### 5.5 ガバナンス

Eric 氏は、「統制される」ことを喜ぶ人はいないと冗談を交えつつ、開発チームが安全な場所で自信をもって速く動けるようにするために、妥当なガイドラインをプラットフォームに組み込み、脆弱性、保守性、性能の問題を見つけて直すツールを提供することが大切だと述べています。ここから先は Leo 氏のライブデモです。

### 5.6 デモ 1：リポジトリルールセット（ガバナンス）

Leo 氏は、アクセシビリティのためにゆっくり話すと断ってから、**リポジトリルールセット（repository rule sets）** を説明しました。特定の操作が行われるのを防いだり、特定のチェックやスキャンが実行されて通る（または深刻度が閾値以下になる）ことを必須にしたりする仕組みです。デモではリポジトリの設定から操作しており、組織レベルでも同じことができ、より全体的に統制できると補足しています。

デモのリポジトリには 2 つのルールセットがあります（実際には、もっと多く持てるとのことです）。

**プッシュルールセット（push rule set）**：どのようなコードを、どうリポジトリへプッシュできるかを決めます。

- ファイル拡張子の制限：バイナリや、Word、PowerPoint、Excel のようなファイルの追加を禁止する例が示されました。理由は 2 つで、それらを置くのに適した場所が別にあることと、組織にとって機密のファイルかもしれず、GitHub のリポジトリに置くと閲覧すべきでない人が読めてしまうためです。Word 文書や実行ファイルを追加しようとすると、プッシュした時点でブロックされます。
- ファイルサイズの制限：巨大なファイルを置く理由がないことと、悪意あるものが入り込んで開発者のマシンに広がるのを防ぐ目的が挙げられました。

**ブランチルールセット（branch rule set）**：あるブランチを別のブランチにプルリクエストでマージするとき、どのチェックを実施するかを決めます。デモではデフォルトブランチを保護しています。

デモのアプリケーションは、自治体のような組織が住民に給付を割り当てる「給付金管理アプリケーション」で、COBOL から Java と JavaScript へ移行中のレガシーコードベースです。移行を補助するシェルスクリプトも同じリポジトリにあります。Leo 氏は、開発者が新しいコードを追加して本番ブランチにマージするときに、次のことを確実にしたいと説明しています。

- リスク許容度を超える脆弱性がないこと
- 大量のコードを単にあちこちへ削除・移動していないこと
- 品質の良いコードがマージされること

緊急時の例外（break glass）として、ルールをバイパスできる役割も指定できます。リポジトリ管理者、チームリード、セキュリティ担当などです。画面で示された必須項目は次のとおりです。

| 項目 | 説明（デモでの説明） |
| --- | --- |
| コードスキャン結果の必須化 | リスク許容度（深刻度の閾値）を超える脆弱性がないこと |
| コード品質の結果の必須化 | コード品質の結果を要求する |
| シークレットスキャンのアラート | マージされるコードで出たアラートが処理されていること。トークンが失効（revoke）・ローテーションされ、より安全な場所に置かれ、実行時にトークンを安全に使う形になっていること |
| ライセンス準拠 | オープンソースライセンスへの準拠。非許容的（non-permissive）なライブラリは組織のコンプライアンスに反する可能性があるため |

これによって高いレベルのポリシーを設定し、GitHub 内で論理的に強制できる、と Leo 氏は述べました。

### 5.7 デモ 2：プルリクエストでの指摘と AI による修正提案

Leo 氏は次に開発者の立場でプルリクエストを開きました（直前に Eric 氏が、セキュリティは開発者にとって「降りかかってくるもの」に感じられがちなので、その印象を変えたいと述べています）。対象は「add document and benefit note previews」というプルリクエストです。

- 新しいプルリクエスト画面（プレビュー中。フィードバック歓迎とのこと）で、実行されたチェックと失敗したチェックを見やすくするのが狙いです。
- コードスキャン結果として、新しいアラートが 2 件あり、そのうち 1 件は **critical** の脆弱性です。

**決定論的ツール（CodeQL）と AI の使い分け**：Leo 氏は、CodeQL は決定論的なツールで、対応言語が限られていると説明しました。挙げられた言語は C 系、Swift、Kotlin、Java、Go、Python、JavaScript、TypeScript です（冒頭は音声が不明瞭で正確に聞き取れず、「他にも 1 つ抜けているかもしれない」と本人も述べています）。このリポジトリには COBOL とシェルスクリプトがあるため、AI（非決定論的なツール）で CodeQL の対象外の言語の脆弱性を見つけています。

**AI スキャンの指摘（プルリクエスト用）**：コメントの投稿者は GitHub Advanced Security Bot で、名前の横に **AI のピル（ラベル）** が付いています。これがプルリクエスト用 AI スキャンからの指摘であることを示します。指摘には、問題のあるコード、何が問題か、どう直せるか、必要な変更が示され、修正案は Copilot が作成したものです。開発者は次のことができます。

- 内容がよければ、提案をコミットする
- 疑問があれば Copilot に質問する（なぜこの変更が必要か、など）
- その変更をバッチに追加して、他の変更と一緒にまとめる
- プルリクエストは共同作業のためのツールなので、エージェントと作業していても人によるレビューやコメントを加えられる

**CodeQL の指摘**：同じ Bot でも AI のラベルが付かないものは CodeQL からの指摘です。CodeQL の利点として、**ソースからシンク（source to sink）** のデータの流れを確認できる点が挙げられました。データが入ってから出るまでの間に、バリア、サニタイザー、バリデーターがあるかを見て、なければ悪用可能な弱点の可能性が高く、あればデータの汚染（taint）を防ぐ処理があるため通常は指摘されません。画面にはその過程と、どのコードがいつ・どこで触れているかが示されます。スクロールすると、Java の指摘や、シェル（この場合は Bash）スクリプトの指摘もあり、問題と修正方法が説明されていました。

Leo 氏は、CodeQL は言語カバレッジが限られるが精度の高い静的解析ツールで、AI でそれを拡張し、修正の特定と適用にも AI を使う、と整理しています。

### 5.8 デモ 3：バックログのアラートを Copilot に修正させる

**参加者への質問（投票）**：「どれがより大きなコストか」として、コードレビューの容量不足、増え続けるセキュリティバックログ、レガシーコードの保守が提示されました（複数回答可）。発表者は、バックログとレガシーコードは「何でもいずれレガシーになり、バックログは縮まない」ので関連が深いと述べ、バックログを縮める方法の説明に入っています。

**AI スキャンの実行**：1 つのリポジトリには複数のスキャナーを連携させられ、デモでは AI スキャンと CodeQL の 2 つが動いています。画面の「AI scan」ボタンを押すと、コードベースに対して AI スキャンがもう一度実行されます。

- 内部では複数のモデルを使い、バックグラウンドで重複排除（deduplication）を行って、同じアラートが何度も出てノイズになるのを防いでいます。
- どのモデルを使うかは、ボタンを押した場合は GitHub が実行するタスクに応じて選びます。OpenAI のモデルが多く、Anthropic のモデルも多い、という説明です。開発者がアクセスできるモデル自体は GitHub 内で制御できます。
- 実行中の様子は Actions で確認できます。各ステップ、使われたモデル、ジョブ完了後に消費した AI クレジット、使用トークン数も分かります。
- 「deep scan」ボタンもありますが、プライベートプレビューのためデモでは触れていません。
- Leo 氏は「Copilot Fusion に似ているが、GitHub の中で非常に特定のセキュリティスキャンを実行する点が違う」と説明しています（「Copilot Fusion」は音声認識の結果で、製品名は確定できません）。

**Copilot への割り当て**：AI スキャンで見つかった脆弱性（COBOL ファイルの OS コマンドインジェクション）を開いています。開発者には、何が問題か、どこか、どう直せるかが表示されます。**Assign to Copilot** ボタンを押すと、次の流れになります。

1. Copilot に **SARIF ファイル**をコンテキストとして渡す（SARIF は Static Analysis Results Interchange Format の略。静的解析ツールの出力を標準化する JSON ファイル）。
2. 自動修正案（autofix）があれば、「こう直すのがよいと考えている」という情報も渡す。
3. Copilot が修正を実装する。
4. 修正が脆弱性に対処できているかを検証しようとする。
5. その修正が新たな脆弱性を持ち込んでいないか、セキュリティスキャンを実行する。
6. 問題がなければ、プルリクエストにまとめる。

Leo 氏は、前日に作った例として、Agentic Autofix から Copilot が作成したプルリクエストを開き、「Files changed」で COBOL ファイルの変更を示しました。プルリクエスト内で Copilot にタグ付けして、何をしたかを質問することもできます。開発者がレビューし、理解し、安全だと判断したらマージします。複数のアラートをまとめて Copilot に割り当て、チームがレビューするプルリクエストにまとめることもできます。

### 5.9 Q&A

**Q1. 今週話題の Emdash は、Advanced Security の AI スキャンとどう関係するか。**
Eric 氏は、コードネーム Emdash を「AI を使ったセキュリティスキャンの大型の仕組み（big iron）」と説明しました。リポジトリ全体を送ると、専門化した複数の LLM が数時間から時には数日をかけて深く調べ、できるだけ多くを発見・テストしたうえで、結果を SARIF で GitHub に返します。GitHub Advanced Security との連携（deep scan）はプライベートプレビューで、担当営業や最後の QR コードから参加を申し込めます。
Leo 氏は、より技術的に補足しました。deep scan は **Emdash との統合ではなく、Emdash の技術を GitHub が使って、リポジトリに対してより深い AI スキャンを行うもの**です。実行時間は最大 30 分で、脆弱性だけでなくアプリケーションのビジネスロジックの問題も探します。違いは「コントロール」で、GitHub の deep scan は内部の細かな設定にアクセスできず、GitHub が用意したプロンプトとハーネスで、最小のコストで最良の体験になるよう整えた簡素な体験です。Microsoft が提供する Emdash は、より多くの制御と深さと長い実行時間を提供します。Leo 氏の見方では、**絶対的な制御がほしいなら GitHub の外で Emdash を使い、GitHub 内で簡単に、複数リポジトリに、低コストで短時間に結果が欲しいなら deep scan が向く**とのことです。
プライベートプレビューでは、利用者からのフィードバックを得て、パブリックプレビューまでに実用的で効果的で効率的にしていく、と発表者が述べています（AI の結果は毎回同じではなく、AI クレジットの投資に見合う価値を出したい、という趣旨です）。

**Q2. 今週か、それ以前に発表された「Microsoft Perception」（聞こえたままの表記で、音声認識の都合で確定できません）には red team / blue team / green team というエージェントの概念があり、green team は今回の話とよく似ている。関係は。**
Leo 氏は、green team が Microsoft の特定製品の概念か一般的な概念かを確認したうえで、概念的な話としては、**Agentic Autofix は、GitHub 内で問題を修正するエージェントとして green team の枠組みに当てはまる**と答えました。関わり方は Copilot への手動の割り当てだけでなく、API でも可能です。さらに **security campaigns** という機能があり、次のように使います。

- フィルターでアラートのグループを作る（例として MITRE の既知の悪用された脆弱性（KEV）が挙げられました。聞き取りは「MITRE top 10 known exploited vulnerabilities, the KEV」）。
- そのグループに期限を決めて、開発者に取り組んでもらう。
- どのアラートにいつプルリクエストが付き、いつクローズされたかなど、取り組みの状況を観察する。
- Autofix に全アラートの対応を任せることもできる。開発者はレビューして、変更するか受け入れるかを決めるだけで済む。

Leo 氏はこれを、大きなセキュリティバックログへの「アジャイルな」アプローチと表現しています。Eric 氏は、GitHub は開発者が既に作業している場所（安全で慣れた場所）なので、そこで見つけて直すことで、日常的な脆弱性がセキュリティチームのバックログに積まれる前に解消できると補足しました。ビルド時から実行時までの流れに、すべてを 1 つでこなす部品はないが、開発チーム向けのツールと、セキュリティチーム向けのツール（例えば Emdash は、悪用されると損害が大きい「王冠の宝石」のリポジトリ向け）を組み合わせて、関係者全員が必要なものを得られるのが Microsoft と GitHub の統合の利点だと述べています。

**Q3. 当社は GitLab のパイプラインで SAST、DAST などのスキャンを通さないとコードを昇格できないようにしており、Synopsys / Black Duck を使っている。今回のものは補完か置き換えか。Black Duck のようなものの知識ライブラリはどこから来るのか。**
Leo 氏は、CodeQL と AI スキャンは静的解析ツールなので、すでに静的解析ツールを使っているなら置き換えになり得るが、要件次第だと答えています。「皆が靴を履くが同じ靴ではない。用途に合う靴を選ぶべき」というたとえです。

- Black Duck は SCA（ソフトウェア構成分析）の有力な選択肢です。GitHub には Dependabot があり、GitHub Enterprise のお客様なら追加費用なしで使えます。
- 追加機能として、最近 npm 向けに出した **reachability** があり、対応言語を拡大中です。脆弱な依存関係の該当関数が、自分のコードベースから実際に到達でき、悪用できるかを特定する機能です。
- Synopsys の競合にも補完にもなり得ます。例えば Synopsys が提供する検証済みライブラリ（vetted libraries）は GitHub にはありません。
- 発表者は、多くのツールが他社の静的解析、SCA、シークレットスキャンのツールを置き換えてきた実績がある一方、複数ツールを併用するお客様も、更新時に簡素化とコスト削減を検討するお客様もいる、と述べました。継続的な対話を勧めています。

**Q4. この機能を使うのに別ライセンスは必要か。**
Eric 氏によると、今日見せたのは **code security** と、一部 **secret protection** で、これらは GitHub に追加する別々の 2 つのライセンスです。

### 5.10 無料のセキュリティリスク評価と学習リソース

最後に QR コードが 2 つ示されました。

- 無料の**セキュリティリスク評価**：人気の 20 リポジトリを対象に、CodeQL でシークレットとコードの脆弱性を調べます（AI スキャンは使いません）。実際のコードでどういう結果になるかを知る出発点になります。
- 今回の内容の「ラーニングジャーニー」：GitHub docs のランディングページです。Copilot に質問して答えを得ることもできるとのことです。

最後はプレゼント企画でした。Eric 氏が、セキュリティ問題で夜遅くまで働いたことや徹夜したことがある人を会場に尋ね、徹夜の経験を話した参加者を前に呼んで、GitHub のロゴが黒地に黒で入ったバックパックを贈りました。そのあと両氏が参加者に礼を述べて終了しています。

## 6. デモ・手順

このセッションでは、Leo 氏によるライブデモが行われています（「画面を見て」「ボタンを押す」といった発話が根拠です）。画面の細部は音声からは確認できず、以下は語られた内容に限ります。

**デモ 1：リポジトリルールセット**
1. リポジトリの設定を開く（組織レベルでも同様に設定できると補足）。
2. プッシュルールセットで、ファイル拡張子（バイナリ、Word、PowerPoint、Excel など）とファイルサイズを制限する。
3. ブランチルールセットで、デフォルトブランチを保護する。バイパスできる役割（break glass）を指定する。
4. コードスキャン結果、コード品質の結果、シークレットスキャンのアラート、ライセンス準拠を必須にできることを確認する。

**デモ 2：プルリクエストの確認**
1. 「add document and benefit note previews」のプルリクエストを開く（新しいプルリクエスト画面）。
2. コードスキャンの新しいアラート 2 件（うち critical 1 件）を確認する。
3. AI ラベル付きの GitHub Advanced Security Bot のコメントで、問題、修正案を確認する。提案のコミット、Copilot への質問、バッチへの追加ができることを説明する。
4. AI ラベルのない CodeQL のコメントで、source to sink のデータの流れを確認する。Java とシェルスクリプトの指摘も見る。

**デモ 3：バックログの修正**
1. アラート一覧で AI scan と CodeQL の 2 つのツールを確認し、「AI scan」ボタンで AI スキャンを再実行できることを示す。
2. Actions で、ステップ、使用モデル、AI クレジット、トークン数を確認できることを説明する。
3. COBOL ファイルの OS コマンドインジェクションのアラートを開き、「Assign to Copilot」の動作を説明する。
4. 前日に Agentic Autofix で作成されたプルリクエストを開き、Files changed で COBOL ファイルの変更を確認する。
5. プルリクエスト内で Copilot に質問できること、レビュー後にマージすること、複数アラートをまとめて割り当てられることを説明する。

## 7. 注意点・発表者の気付き

- deep scan（Emdash の技術を使った深いスキャン）は**プライベートプレビュー**です。デモでは扱われていません。参加は担当営業か QR コードから申し込みます。
- 新しいプルリクエスト画面は**プレビュー**で、フィードバックを求めています。
- AI スキャンは決定論的ではなく、毎回同じ結果になるとは限りません（発表者は、AI を使ったことがあれば分かるはずだと述べています）。AI クレジットを使うので、価値が出ているかを見たい、という姿勢です。
- 開発者が使えるモデルは GitHub 内で制御できますが、AI スキャンのボタンを押したときに使うモデルは、GitHub がタスクに応じて選びます。
- CodeQL は対応言語が限られます。COBOL やシェルスクリプトなどは AI スキャンで補います。
- 既存ツールを置き換えるかどうかは要件次第で、発表者は一般的な答えを出さず、対話を勧めています。Synopsys が持つ検証済みライブラリに当たるものは GitHub にはありません。
- 今回の機能を使うには code security と secret protection（別々の追加ライセンス）が必要です。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 生成されたコードを、開発者が見る前にシークレット、脆弱性、脆弱な依存関係の観点でチェックできる。
- COBOL のようなレガシー言語も AI スキャンの対象になり、保守プロジェクトが現実的になる。
- 最大 25 件のアラートを Copilot に割り当て、検証とセキュリティスキャン済みのプルリクエストを並行して受け取れる。Eric 氏は、数万件のバックログを抱える顧客もいる中で、Agentic Autofix をバックログを素早く消化する方法と位置づけています。
- ルールセットで、機密ファイルの混入、巨大ファイル、リスク許容度を超える脆弱性、シークレットの未処理、非準拠ライセンスをマージ前に止められる。
- security campaigns で、グループ化したアラートを期限付きで追跡し、Autofix に任せられる。
- 開発者は普段の GitHub のワークフローの中で見つけて直せるため、日常的な脆弱性がセキュリティチームのバックログに届きにくくなる。

数値としての導入効果や、特定の顧客の事例は、発表では紹介されていません。

## 9. まとめ

このセッションは、コード生成の増加に対して、セキュリティを人手でなくプラットフォームで常時動かす考え方を示しました。生成コードのチェック、決定論的スキャン（CodeQL）と AI スキャンの併用、Agentic Autofix による修正、リポジトリルールセットによるガバナンスの 4 本柱です。ライブデモでは、ルールセットでマージの条件を決め、プルリクエスト上で指摘を確認し、COBOL の脆弱性を Copilot に直させる流れを通しで見せました。

Q&A では、deep scan は Emdash の技術を使いつつ GitHub 内で簡素・低コスト・複数リポジトリ向けに整えたもので、絶対的な制御が必要なら Emdash を別途使う、という整理がありました。既存ツールとの関係は要件次第で、利用には code security と secret protection のライセンスが必要です。まずは無料のセキュリティリスク評価（CodeQL による 20 リポジトリのスキャン）から試せます。
