# THR864 From code to control: Building on the agent platform

## 1. はじめに

このセッションは、GitHub の 2 人が「GitHub Copilot アプリで計画し、Foundry にエージェントを作り、アプリに組み込んで Azure に載せ、Agent 365 で管理する」という一連の流れを、ライブデモで見せる約 20 分の短いセッションです。題材は、猫用品を売る架空のオンラインショップ「Octocad supply store」に、お客様からの問い合わせに答えるチャットボットを付けるというものです。

発表の核心は、**Foundry の操作をほとんど自分で行わなくても、GitHub Copilot に任せて「アイデアから本番相当の稼働まで」を通せる**という点です。発表者は、実際にこれを行うと、アイデアからデプロイ済みの状態まで通しで約 30 分かかると述べています。

このセッションでは画面を使ったデモが行われています。ただし、時間のかかる処理は、画面の外で事前に実行しておいた完成版に切り替えて見せています。

## 5. 発表内容の詳細

### 5.1 題材：Octocad supply store

画面に映したのは、猫用品を売るショップのサイトです。給餌器、フード、トイレなどが並んでいます。店主の立場で話す登壇者は、お客様からの請求書の確認や問い合わせ、質問が大量に来て対応しきれない状況にあり、それをさばいてくれるエージェントがあれば助かる、という設定にしています。これを、20 数分のセッションの中で GitHub Copilot と Microsoft の agent platform を使って作ります。

### 5.2 GitHub Copilot アプリで計画を立てる

作業の起点は GitHub Copilot アプリです。TJ 氏はこのアプリを「開発に関するあらゆることのコントロールパネル」と呼び、複数のプロジェクトにまたがる多数のエージェントセッションを管理できると説明しています。このデモでは、あらかじめプロジェクトのソースコードにつないであります。

新しいプロジェクトの最初の一歩は、やるべき作業の計画だと TJ 氏は述べます。Foundry の専門家ではなくても、アイデアを本番に移すまでの手順を Copilot に設計させることができます。そこで次のようなプロンプトを実行しました。

- 全体の作業をまとめた Issue を設計する
- サブ Issue を 2 つ作る。1 つは Foundry でエージェントを作ってデプロイする作業、もう 1 つは、そのエージェントをカスタマーサポートのチャットボットとしてユーザーが使えるように、Web サイトを変更する作業

Copilot はプロジェクト内の情報を調べ、検索を行い、サードパーティのツールを通じて最適な進め方を探します。

このとき Ricky 氏が、裏側の仕組みとして **Work IQ MCP** の話をしています。エージェントの要件については、2 人が Teams や Outlook など複数のコミュニケーションチャネルで事前にやり取りしていました。Work IQ MCP を使うと、Copilot がそれらの会話を調べ、PR や Issue に必要なビジネスコンテキストを集めて要件に反映できる、という説明です。

### 5.3 Copilot Fusion とモデルの選択

TJ 氏はこの実行を **Copilot Fusion** で行っています。Ricky 氏によれば、前日のキーノートで述べたとおり、Copilot Fusion は Terminal Bench で 1 位にランクされ、はるかに低いコストで高い性能を出します。仕事ごとに適切なモデルを選ぶことで、トークンコストに対して最良の結果を返すという位置づけです。

もっと細かく制御したい場合は、好きなモデルを選べます。GitHub Copilot はフロンティアの各社のモデル（発表では Claude の Opus や Gemini 系が挙げられています）を 1 か所で使える「ワンストップ」だとしています。

Fusion は 1 つのモデルに固定されず、1 つのタスクに複数のモデルを使うことがあります。登壇者は例として、Opus 5 で計画を立て、その結果を GPT-6 Luna に見直させて、見落としがないか批評・比較させる、という流れを挙げています。複数のモデルを使うことで、フロンティア級の品質をずっと低い価格帯で得られるという説明です（モデル名は聞こえた表記のままです。音声認識の都合で表記が確定できません）。

### 5.4 計画の確認（デモの完成版）

ライブで実行した処理が思ったより時間がかかったため、TJ 氏は、開始前に同じプロンプトを画面の外で実行しておいた完成版に切り替えました。

その結果、GitHub 上に複数の作業項目（Issue）が作られていました。1 つを開くとアプリ内で表示され、計画された作業が確認できます。Ricky 氏と交わした会話のグラウンディング情報を Copilot が見つけ、実装計画に反映しています。子 Issue も作られていて、1 つは Foundry 側のコンポーネント、もう 1 つはアプリケーション側のコンポーネントです。簡単なプロンプトだけで、追加すべき具体的なエンドポイントまで洗い出され、実装前の下準備の多くが済んでいる、と TJ 氏は述べています。

### 5.5 canvas から Foundry にエージェントを作る

次に、Foundry 側の Issue を実装します。これも GitHub Copilot アプリの中で、**canvas** を使って行います。canvas を開くと、すでに Foundry につないであり、画面の横にエージェントの実装を進めるための canvas が表示されます。

TJ 氏が説明した手順は次のとおりです。

1. Azure サブスクリプションと、接続する Foundry のプロジェクトを選ぶ（デモでは設定済み）
2. エージェントの作り方を選ぶ。選択肢は、Microsoft Agent framework を使ったカスタムコードか、Foundry 自体に組み込まれた既製の機能。デモでは後者を選んだ
3. やりたいことをプロンプトで伝える。このデモでは「issue #2 を実装して」とした。必要なドキュメントは先に作った作業項目に入っているので、すべてコンテキストに入った状態になる
4. 「create with Copilot」をクリックする

TJ 氏はこの操作自体は実行せず、以前から使っていたセッションの結果を見せています。その結果では、最初に別のモデルが使われ、Foundry 上でエージェントを構築する工程が一通り実行されました。元の要件を満たしているかを確かめるための評価とテストの実行も含まれています。

### 5.6 Foundry で確認する

画面を Foundry に切り替え、GitHub Copilot アプリでデプロイされたエージェントを確認しました。

- **指示（instructions）**：先ほどの PR と Issue から取り込まれたもの
- **詳細・ステータス・アイデンティティ**：アイデンティティについては、後で Agent 365 と合わせて説明される
- **トレース**：エージェントのトレースを見られる（発表ではこれ以上の説明はありません）
- **ツール**：CRM のビジネスデータなどの文脈をつなげられる。ツールボックスにツールを追加でき、Azure AI Search、Fabric のデータベース、CRM などが挙げられた。サードパーティ提供のプラグインのカタログもある
- **ガードレール**：組織の制約に収まるようにエージェント側で設定・管理できる

> 補足：画面を切り替える途中でタブを間違える場面がありましたが、登壇者は「ライブデモではよくあること」と述べて先に進めています。

今回のデモの構成は比較的単純で、カスタマーサポートチームが持っていると想定したナレッジベースがあり、それを検索するツールをエージェントに与えて回答のグラウンディングを行っています。この画面では、右側のサンドボックスでエージェントをライブでテストでき、ユーザー体験を試せます。

TJ 氏が「高齢の猫に向いている商品は何ですか」と尋ねると、商品カタログからいくつかの商品と価格などの情報が返ってきました。デモ向けに猫のテーマに合わせ、システムプロンプトで「楽しい調子で、猫のダジャレをたくさん入れる」よう指示してあります。

**評価（evaluations）**：エージェントを改善するために、Copilot が自動で評価を設定しています。Copilot が自動で作ったテストケースをエージェントに走らせ、根拠のある結果を返しているかを確かめます。サンプルデータでの総合スコアは非常に高い、と述べています。さらに掘り下げると、詳細なメトリクスや、テストで実行されたすべてのクエリを見られます。会話を再生して、かかった時間も確認できます。今回は単純なエージェントですが、複数のエージェントが連携して 1 つのクエリを処理する場合でも、流れをトレースして把握できる、という説明です。

**最適化（optimize）**：システムプロンプトやツール呼び出しなどを調整し、エージェントを自動で改善する機能があります。デモでは実行していませんが、「optimize」をクリックすると、評価スコアが上がるようにエージェントを再調整し、全体の成功率を高めようとします。

### 5.7 アプリ側の実装、レビュー、セキュリティ

エージェントができたので、次はアプリに組み込みます。自分で使うだけでなく、最終的にはエンドユーザーにデプロイするためです。TJ 氏は、もう 1 つの作業項目（Issue）についても、別のセッションをあらかじめ立ち上げて作業させてありました。そのセッションでは、Fusion によって Opus、Luna、Terra など 3〜4 つのモデルが使われたと述べています。時間の都合で途中は飛ばし、リポジトリに移ります。

Copilot アプリから直接プルリクエストを作らせました。この PR では約 16 ファイルが変更されています。

ここで TJ 氏は、「エージェントが書いたコードを、自分はまだ見てもいない。どうすれば信頼して本番に出せるのか」という疑問に答えています。GitHub プラットフォームの残りの機能で評価する、という答えです。

1. **自動コードレビュー**：すべての PR で、複数のモデルによるコードレビューを自動で依頼している。デモでは、Azure に接続して Foundry 経由でモデルを呼ぶときの認証情報で、タイムアウトが起こりうる点などの指摘が出ていた。分かりやすい指摘にはインラインの修正案が付き、レビューして commit すればすぐ直る。修正案が無いものは、Copilot に解決を依頼して別のセッションを立ち上げさせ、直させることもできる
2. **GitHub Advanced Security**：PR の中で自動的に実行され、取り込まれた脆弱なパッケージや、自分で書いたコード内の脆弱性（SQL インジェクションなど）を検出する

Copilot でコードを効率よく書くだけでなく、信頼してデプロイできる状態にするところまでが、PR の流れの中で自動的に行われるという説明です。

### 5.8 稼働中のアプリ

ここまでの内容は、画面の外で実際に Azure にデプロイし、コードも更新済みです。登壇者は、手元のスマートフォンで触れる稼働中のアプリであることを案内し、QR コードは後ほど再掲すると述べています。ただし、このサイトは Ignite の終了時点で撤去する予定で、ずっとは残らない、と述べています。

このとき使われているモデルは、発表では「GPT-4.0」と聞こえます（音声認識の都合で表記が確定できません）。使うモデルは Foundry のモデル設定で決まります。より良いモデルや堅牢なモデルを選びたい場合、あるいは独自のモデルを持ち込みたい場合のために、**Foundry には 11,000 を超えるモデルがあり**、フロンティアラボを含む大多数のプロバイダーから選べ、自分のモデルも持ち込める、と説明しています。

### 5.9 Agent 365 でのガバナンス

最後のパートは、作ったエージェントをどう統治するかです。Foundry にデプロイしたエージェントは、**Agent 365 に自動的に表示されます**。Agent 365 は、組織内のすべてのエージェントの「ガバナンスとコントロールのプレーン」と説明されています。

概要ページでは、次の情報が見られます。

- 組織内のエージェントの総数
- エージェントにアクセスしているアクティブユーザー
- アクティブユーザー数別のエージェント

個別のエージェントを開くと、さらに詳しく見られます。今回のショップに組み込んだエージェントの画面では、Microsoft Purview が管理するセキュリティと、Microsoft Entra ID による保護が示されています。アクティビティのパネルでは、そのエージェントの利用状況（クエリ数、アクティブユーザー数の推移）が確認でき、当日に行った問い合わせがそこに反映されていました。

エージェントには、データ、ツール、接続を結びつけて、ビジネスに合わせて調整することもできます。登壇者は、SharePoint や M365 スイートのものを追加する例を挙げ、そこで何を許可するかは管理側が制御できると述べています。これにより、組織の全員が作っているエージェントを統治できるというのが、Agent 365 の良い点だという説明です。

**今週の新機能**として、GitHub Copilot がそのイベントをすべて Agent 365 に直接ストリーミングするようになった、と紹介されました。これにより、Microsoft と GitHub をまたぐ利用状況を 1 つのポータルで監視できます。このアプリを作るために行ったエージェントの活動（Copilot による作業）と、アプリに組み込まれた AI の活動が、同じ画面で確認できます。

### 5.11 Q&A

質問は 1 件でした。質問者（Brent と呼ばれていました）は、GitHub にあまり詳しくない人が、このような作業を Copilot Studio と GitHub Copilot アプリのどちらでやるべきかを尋ねました。

回答の要点は次のとおりです。

- GitHub Copilot は、開発者でなければ難しそうに見えるかもしれないが、実際にはチャットボットであり、ただのテキストボックス。分からないことを尋ねても責められず、基本的な質問にも喜んで答えてくれる。使ったことがなければ、恐れずに試してほしい
- Copilot Studio は、エージェント版の「Power App」のようなもので、より手順に沿ったガイド付きの UI 的な体験
- Foundry は、より複雑なものを作れるパワーユーザー向け
- 目安としては、Copilot Studio はシチズンデベロッパー、Foundry はプロの開発者という分け方。ただし、ツールが強力になるにつれて、その境界は日々曖昧になっている
- 今回のデモでは、Foundry の画面でボタンを 1 つも押さなかった。すべて Copilot が canvas を通して行った。まずは脇で試してみる使い方もある

## 6. デモ・手順

このセッションではライブデモが行われています。ただし、画面の細部は音声からは確認できず、語られた範囲の流れは次のとおりです。

1. GitHub Copilot アプリで、プロジェクトのソースコードにつないだ状態から、Issue とサブ Issue（Foundry 側とアプリ側の 2 つ）を計画するプロンプトを、Copilot Fusion で実行する。思ったより時間がかかるため、事前に実行しておいた完成版に切り替える
2. 作成された Issue を開き、実装計画、グラウンディング情報、子 Issue を確認する
3. canvas を開き、Foundry に接続済みであることを示す。Azure サブスクリプションと Foundry プロジェクトを選び、Foundry の既製機能で作る方式を選び、「implement issue #2」と指示して「create with Copilot」を押す流れを説明する（実行はせず、以前のセッションの結果を見せる）
4. Foundry の画面に切り替え、エージェントの指示、詳細、トレース、ツールを確認し、ガードレールで制約を設定できることを説明する。サンドボックスで「高齢の猫に向いている商品は何ですか」を試す
5. 評価の結果（スコア、メトリクス、クエリ、会話の再生）を見せ、optimize の機能を説明する（実行はしない）
6. アプリ側の別セッションの結果から、Copilot アプリで PR を作り、16 ファイルの変更、コードレビューの指摘、インライン修正案、GitHub Advanced Security を確認する
7. 稼働中のサイトで、右下のチャットボットに「高齢の猫への贈り物」を尋ねる
8. Agent 365 の概要ページと、個別エージェントの画面（セキュリティ、アクティビティ）を確認する。GitHub Copilot のイベントが Agent 365 にストリーミングされていることを示す

## 7. 注意点・発表者の気付き

- **計画を先に固める。** 実装に進んでから意図と違うことに気づくと、トークンを無駄にする。計画を人間が確認して直してから、実装を任せることを TJ 氏が勧めています。
- **エージェントが書いたコードは、そのまま信頼しない。** PR のコードレビューと GitHub Advanced Security の確認を通して、デプロイできる状態にします。
- **デモ用のサイトは永続しません。** Ignite の終了時点で撤去される予定です。
- **拡張の余地があります。** 今回のエージェントは商品に関する質問に答える構成で、注文状況の問い合わせなどは、CRM につなぐ拡張案として語られました。
- ライブデモの性質上、処理に時間がかかる部分は事前実行の結果に切り替えています。デモの内容がすべてその場で生成されたものではありません。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **所要時間の短さ**：アイデアからデプロイまで、通しで約 30 分
- **コストと品質**：Copilot Fusion が仕事ごとにモデルを選び、複数モデルを組み合わせて、フロンティア級の品質を低いコストで得る
- **Foundry の専門知識が無くても進められる**：計画、エージェント作成、評価、デプロイまで Copilot が誘導する
- **選択の自由**：GitHub Copilot ではあらゆるフロンティアモデルを選べ、Foundry には 11,000 を超えるモデルがあり、独自モデルの持ち込みも可能
- **信頼してリリースできる**：PR での自動コードレビューとセキュリティチェック
- **全体を 1 か所で見える**：Agent 365 で、アプリに組み込まれたエージェントと、それを作った GitHub Copilot の活動を同じポータルで確認できる

## 9. まとめ

このセッションは、猫用品ショップのチャットボットを題材に、GitHub Copilot アプリ → Foundry → Azure → Agent 365 という Microsoft の agent platform の流れを通して見せるデモでした。GitHub Copilot アプリで Issue とサブ Issue を計画し、canvas から Foundry にエージェントを作り、評価で品質を確かめ、PR でアプリに組み込んで、自動レビューとセキュリティチェックを通してデプロイします。その後、Agent 365 で利用状況やセキュリティを管理します。今週から GitHub Copilot のイベントも Agent 365 に流れるようになりました。GitHub Copilot アプリのダウンロードが、最初の一歩として案内されています。
