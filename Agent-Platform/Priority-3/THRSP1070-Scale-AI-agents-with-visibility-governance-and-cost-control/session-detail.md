# THRSP1070 Scale AI agents with visibility, governance, and cost control

## 1. はじめに

このセッションは、社内のエージェントが増えてきたときに「どこから手を付けるか」を、現場目線で整理した短い登壇です。CDW の Robert Madison 氏が、エージェントの管理を **Find it（見つける）→ 統制する → Price it（コストと価値を測る）** という繰り返しの型で捉え、そのうち「見つける」と「統制する」を Copilot Studio のエージェントを題材にしたデモで見せます。

中心にある主張は、**問題のありそうなエージェントを見つけたとき、まず止めるのではなく、持ち主・対象ユーザー・触れるデータとツール・使われ方を調べ、状況に見合った小さな制限を掛けていく**という進め方です。Power Platform の ALM やパイプラインを整えた成熟した組織でも、持ち主のいないエージェントは必ず見つかる、という前提で話が進みます。

このセッションでは画面を使ったデモが行われています（手順は 6 章にまとめています）。ただし、コスト面（Price it）はフレームワークの説明のみで、デモはありません。

## 3. 何に関する発表か

テーマは、エージェントが増殖していく状況で直面する次の 3 つの症状と、それに対する運用の型です。発表者は、これらを「エンタープライズの運用モデルの欠落が生む 3 つの症状」と呼んでいます。

| 症状 | 問い |
| --- | --- |
| Unknown（把握できていない） | 誰がそのエージェントを所有し、何にアクセスしているか |
| Ungoverned（統制されていない） | 誰が、どんな条件で使えるか |
| Unpriced（価格・価値が見えていない） | どれだけのリソースを消費し、どんな価値を返しているか |

発表者は「見つけられないものは統制できない」「理解していないものの経済性は管理できない」と述べ、エージェントを見つけた途端に止めたくなる「火災報知器の発想」から抜け出すことを狙いとしています。

発表の流れは次のとおりです。

1. 問題提起と 3 つの柱（Find it / 統制 / Price it）
2. 題材のシナリオ「Rebate Radar」の紹介
3. Find it：何を確認するか（出所、所有者、対象者、利用状況、データ、ツール）
4. 統制（Govern）：誰が使えるか、何に届くか、結果として取りうる対応
5. Price it：コストではなく価値で見る考え方と、単一の運用モデル
6. デモ：Agent 365 のインベントリで調べ、所有者・対象者・条件付きアクセスを設定
7. 持ち帰りの要点

## 4. 発表者が伝えたいメッセージ

発表者がまず強調するのは、**「止める前に調べる」**ことです。持ち主の分からないエージェントを見つけたら、すぐ無効化したくなります。しかし、そのエージェントは実際には生産性や売上に貢献しているかもしれず、止めればその価値も失われます。そのため、出所、所有者、対象者、利用状況、データ、ツールをまず確認し、そのうえで制限を決める、という考え方です。

もう 1 つは、**統制は大掛かりである必要はない**という点です。発表者の顧客の多くは、機密ラベルやゼロトラストの仕組みをまだ整えていません。そうした現実を前提に、すでに手元にあるツールで、エージェントを「小さく」統制できることを示します。

3 つ目は、コストの見方です。支出額は重要ですが、発表者は意識を「価値」に寄せたいと述べ、「判断すべきは、いくら掛かったかではなく、掛けた金額で何を得たか」だと言います。

最後に、この一連の作業を一度で終わらせず、エージェントのライフサイクル全体で **rinse and repeat（洗って繰り返す）** することが、スケールのための型だと位置づけています。

## 5. 発表内容の詳細

### 5.1 問題設定とシナリオ「Rebate Radar」

発表者は、ここ（Ignite）全体が FinOps の話題で持ちきりだと触れつつ、FinOps の細部には深入りしないと断っています。状況の変化が非常に速く、今日示した内容が明日には変わりうるため、という理由です。

説明に使う架空のシナリオは **Rebate Radar** です。製造業の会社向けの Copilot Studio エージェントで、サプライヤーのリベートを見つけ、調達プロセスを開始します。発表者は、エージェントの中身にこだわらず、自社のものに置き換えて聞いてほしいと言っています。このエージェントには次の問題が仕込まれています。

- 所有者がいない
- 対象ユーザーが広い（全員に展開されている）
- 機密データに触れている
- 利用が増えている

### 5.2 Find it：何を確認するか

発表者は observability（可観測性）という単語を言いにくいと冗談めかして、この段階を「Find it」と呼んでいます。確認する観点は次のとおりです。

| 観点 | 確認すること |
| --- | --- |
| Origin（出所） | どこから来たか |
| Owner（所有者） | 誰が責任を負うか。更新やナレッジの変更時、アクセス権の判断時、問題発生時に誰が直すのか |
| Audience（対象者） | 誰が呼び出せるか、誰のためのものか |
| Activity（利用状況） | 実際に使われているか。発表者は、使われないまま環境の画面を占有しているエージェントを持つ人はどれくらいいるか、と会場に問いかけています |
| Data and tools（データとツール） | どのデータに届き、何を呼び出せるか |

ここでの注意点は、**発見（ディスカバリー）はスコープを明らかにするだけで、価値と安全性を保証するものではない**ことです。発表者は、Agent 365 のインベントリ（音声認識では "AJIT 365" と聞こえます）自体は「何があるかを見るためのもので、何かを実行するものではない」と説明しています。

### 5.3 統制（Govern）：統制の問いと 4 つの結果

> 補足：発表者が「find it」「price it」と呼ぶ場面は確認できますが、統制の段階には「Govern it」という呼び名の発話はなく、「govern」と言っているだけです。そのため本書では「統制（Govern）」と表記します。

統制というと、Power Platform の ALM パイプラインや DLP、Agent 365 の作り込んだ機能を想像しがちです。発表者は、エージェントが成長・成熟していく途中でも、もっと小さくできることがあると言います。問いは次の 3 つです。

- 所有者は誰か（オーナー、スポンサー、ライフサイクル）。エージェントが長く存在するようになり、ライフサイクルの管理が重要になっている
- 誰が、いつ使えるか（アクセスとコンテキストの制御、ID、対象者、デバイス、どこから接続するか）
- 何に届き、何を変更できるか（データ、アクション、ナレッジ、コネクタ）

発見と統制の結果として取りうる対応は、発表者の言う「4 つの結果」のうち、次の 3 つが聞き取れます（残りの 1 つは、発話から特定できませんでした）。

| 対応 | 内容 |
| --- | --- |
| Expand（拡大） | 持ち主の分からないエージェントが実はよく働いている場合に、対象者やナレッジを広げる。発表者は「めったにない」としています |
| Narrow（絞り込み） | ほとんどのエージェントはこちら。対象者・データ・ナレッジソースを絞り、アクセスできる範囲を制限する |
| Retire（廃止） | 発表者が会場に挙手を求めると、実際に廃止した人は少数でした。ネットワークのファイル共有やユーザーアカウントと同じで、「誰かが作ったから残っている」状態を整理する |

なお、SharePoint の過剰共有（oversharing）のような裏側の対策は、このセッションの範囲外で、枠組みを理解してもらうことが目的だと説明しています。

### 5.4 Price it：コストではなく価値を見る

発表者は、この段階を「Price it」、あるいは「価格／価値」と呼び、意識を価値に変えたいと述べます。構造は次の 3 段です。

1. **ネイティブなテレメトリ**：Microsoft が提供する利用状況、Copilot クレジット、キャパシティなど。発表者は、これが先週と今日でも大きく違うほど急速に変わっていると言います。
2. **エンタープライズでの計算**：総コスト、やり取りの数、成功したタスクやプロセスを合わせ、掛かった費用に意味を与えます。
3. **ビジネス成果**：返ってきた価値、サイクルタイム、品質。発表者が組織と最も時間を掛けて話すのはこの部分です。

この価値の話し合いは気が重いものだ、と発表者は言います。例えばエージェント 1 つに 1,000 ドル掛かっていても、誰かに定義された利用ケースを聞かない限り、その価値は取り戻せない、という指摘です。

### 5.5 単一の運用モデル

発表者は、運用モデルは 1 つで、「ある答えが次の問いを生む」流れだと説明します。

1. **発見**：何が存在し、何をするのか
2. **所有と負担**：誰が所有し、誰が支払うかを決めます。今はチャージバックをしていなくても、**論理的なチャージバック**ならできると説明しています。エージェント側のレポートを使えば、営業や人事がどれだけ使っているかを見られます。費用は今のところ IT 予算にまとまっているため、実際の課金でなくても、論理的に負担先を決めておく、という考え方です
3. **統制**：どんな条件でアクセスできるか
4. **最適化**：拡大するか、再設計するか（エージェントを取り巻く仕組み（harness）が変わってきているので、再設計すれば得られる利点もある）、複数のユースケースを統合するか、廃止するか

廃止の項では、そもそもエージェントが適切な手段ではない場合もあり、co-work（聞こえた綴りのまま）など別の手段で実行できるかもしれない、とも述べています。

## 6. デモ・手順

デモは Robert 氏が画面を切り替えて行い、技術的に作り込むものではなく、どこで何が見え、何ができるかを指し示すためのものだと位置づけています。画面の細部は音声からは確認できないため、語られた順に整理します。発表者は持ち時間が 25 分であること、デモ部分は約 9 分で終わることを述べています。

**前提**：Rebate Radar は、5.1 のとおり所有者がおらず、全員に展開され、機密データに触れうるエージェントとして扱われます。

1. **インベントリで探す**：Rebate Radar がインベントリに表示されています。インベントリ全体でできることは多いが、ここでは扱わないとしています。発表者は、いきなり無効化せず、誰が作ったのか、何をするのか、何が懸念なのかを調べることが最初の一歩だと述べます。
2. **所有者の確認**：このエージェントには所有者がいません。動作はするものの、問題が起きたときの相談先がなく、IT も内容を把握できません。ダッシュボードには、ライフサイクル全体にわたって所有者のいないエージェントを一覧表示するレポートがあります。ただし、このデモ用エージェントは作成されて間もなく、テレメトリが拾われていなかったため、そのレポートの代わりに個別の画面を見せています。
3. **指示の確認**：エージェントの instructions（指示）を開きます。エージェントに詳しくない管理者でも、何をするものかが分かる、と説明しています。SharePoint のナレッジソースにアクセスしていそうなこと、ツールを呼び出していそうなことが見て取れます。
4. **モデルの確認**：どのモデルで動いているかが表示されます。単純なエージェントに高度なモデルを使っていると、その分コストがかさみます。従来は Power Platform 側の Copilot Studio の奥まで入らないと分からなかった、と発表者は言います。このエージェントのモデルについて発表者は「それなりのモデル」と述べますが、モデル名とコストの評価は音声から確定できません（"Fable" のような語も聞こえますが、聞き取り不明瞭です）。
5. **展開先の確認**：誰に展開されているかを見ます。この例では全員に展開されています。発表者は、自分の顧客はどこも、そのほうが楽だという理由で全員に展開している、と述べています。
6. **ナレッジとツールの確認**：ナレッジは SharePoint サイトのようで、開くと、銀行のデータや、ルーティング番号、銀行番号があり、社会保障番号が含まれる可能性もある、と述べています。ツールとして MCP ツールが呼ばれていることも分かります。発表者は、機密ラベルやゼロトラストの話をする時間はないと断っています。実際の顧客の多くがそれらを使っていないため、そこまで進まなくてもできる変更を見せる、という方針です。
7. **Agent Map**：グラフィカルなツールで、対象のエージェントに絞った状態で、エージェントとその利用者のやり取り、呼び出したツールを可視化します。SharePoint 検索（ナレッジ検索）の他に、Azure または Bing の検索が表示されています。発表者は、エージェント作成時に Web 検索をオフにし忘れていたため、Web も問い合わせていた、と説明します。一方、MCP がマップに出ていないのは、このマップが**アクティブな接続があるときだけ表示される**ためです。デモでは MCP サーバーへのアクティブな接続をあえて作っていない、と述べています。データとツールの画面と合わせれば、フォレンジック（事後解析）のように何をしているかを突き止められる、という説明です。
8. **利用状況（Activity）**：誰が使っているかを見ると、Demo 1、2、3 の 3 ユーザーが表示されます（発表者は自分の管理者アカウントでの利用だと述べています）。「想像の帽子」をかぶり、この 3 人は調達部門だと仮定します。調達向けのエージェントだと分かれば、調達のグループだけに絞れるという流れです。発表者は、これは誰とも話さずに、手元のツールだけで調べた結果だと強調します。
9. **新しい所有者の割り当て**：新しい所有者を割り当てます。反映に少し時間が掛かります。自分自身にも、他の人にも割り当てられるので、所有権を IT から業務側の人へ移せます。
10. **対象者の絞り込み**：全員に展開されていた設定から、調達グループ（Demo ユーザーが所属）だけに変更します。画面がうまく動かないと述べる場面がありました。これで、全員に開かれていた状態から、調達グループのみに絞られます。
11. **条件付きアクセスポリシー**：データにラベルが付いていない現状で、調達グループにはまず企業管理のデバイスからだけ使わせたい、という方針です。そのために条件付きアクセスの設定に移り、ユーザーを対象にした条件付きアクセスポリシーを作ります。この画面への移動先は、音声では "intro" と聞こえます（音声認識の都合で表記が確定できません）。
    - 条件付きアクセスの詳細は 1 週間掛かる話題になるので深入りしない、と断っています。
    - エージェントには 2 種類あり、**エージェント自身の ID（agent identity）** で動くものと、**OBO（on behalf of）**、つまり利用者に成り代わって動くものがあります。この Rebate Radar は OBO です。
    - OBO ではトークンを取得するのが利用者のコンテキストなので、ポリシーはユーザーを対象に作ります。条件付きアクセスの「エージェント向け」の機能はエージェント ID 向けで、今回は使いません。
    - 手順は次のとおり語られています。名前を「radar」とし、ユーザーとグループを選び、調達グループを選択します。ポリシーの対象にこのエージェント（Rebate Radar）を指定する旨を述べ、アクセスの許可条件として、準拠している（compliant）デバイスを求めます（発話では "mobile devices, or sorry, compliant devices" と言い直しています）。
    - 発表者は、このリソース指定にはニュアンスがあるとして、急いで進めると述べています。
12. **結果のまとめ**：来場時の状態は、調達データにアクセスし、有益な動きをしているが、重大な懸念がある、全員に・どのデバイスからでも・どこからでも使えるエージェントでした。約 9 分で、所有者を割り当て、対象を調達部門に絞り、準拠デバイスのみに限定できました。発表者は、これで昼食に行ける、とデモを締めています。コスト面は今後あらためて扱うとされ、このデモでは扱っていません。

## 7. 注意点・発表者の気付き

- **すぐ止めない**：不安なエージェントでも、生産性や売上に貢献している可能性があるため、まず調べます。ただし、本当に懸念が大きいときは無効化してよい、とも述べています。
- **所有者のいないエージェントは、成熟した組織でも出る**：Power Platform の ALM・ガバナンス・パイプラインがすべて整っていても、必ず出てくる、と発表者は断言します。
- **発見は価値や安全を保証しない**：インベントリは存在を見せるだけです。
- **Web 検索のオフ忘れ**：作成時に Web を切り忘れ、エージェントが Web も検索していた、という発表者自身の失敗が、Agent Map で可視化されました。
- **Agent Map の表示条件**：アクティブな接続があるものだけが線で出るため、接続を作っていない MCP は表示されません。マップだけで判断せず、データとツールの画面と合わせて見る必要があります。
- **条件付きアクセスの対象**：OBO のエージェントには、ユーザーを対象にしたポリシーを作ります。エージェント ID 向けの機能と混同しないよう注意が語られました。
- **機能は急速に変わる**：Copilot クレジットやキャパシティの扱いは、先週と今日でも違うと述べられています。
- **ライフサイクルの管理**：エージェントが長期間残るようになり、所有者・スポンサーとライフサイクルの管理が重要になっています。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- 既存のツールだけで、持ち主のいないエージェントの所有者の割り当て、対象者の絞り込み、デバイス条件の追加が、デモでは約 9 分でできた
- 所有者を IT から業務側の担当者に移せるので、IT が問題の窓口として巻き込まれる状態を避けられる
- モデルの確認により、単純なエージェントに高度なモデルを使っていないかを管理者側から把握できる
- エージェントを止めずに制限を掛けるため、有用なエージェントの生産性を保てる
- 論理的なチャージバックで、部門ごとの利用を見える化できる

## 9. まとめ

エージェントが増える環境では、Unknown・Ungoverned・Unpriced の 3 つの症状が同時に起きます。発表者はこれに、Find it、統制、Price it を繰り返す型で対応することを勧めます。

デモでは、所有者不在・全員に展開・機密データ・Web 検索の切り忘れという問題を抱えた Rebate Radar を、インベントリ、Agent Map、利用状況の確認で洗い出しました。そのうえで、新しい所有者の割り当て、調達グループへの対象者の絞り込み、準拠デバイスを条件とする OBO 向け条件付きアクセスで、制限を掛けました。

持ち帰りの要点は、エージェントを 1 つ棚卸しし、所有者がいなければ割り当て、状況に見合った小さな制御を掛け、これを繰り返すことです。発表者は、スケールには枠組みが必要で、誰もがどこかから始める、と述べています。最後に、CDW のブース（Hall E の 5527）で終日・翌日も質問を受け付けると案内して終わりました。
