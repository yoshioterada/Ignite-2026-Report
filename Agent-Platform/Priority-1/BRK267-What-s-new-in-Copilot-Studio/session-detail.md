## 5. 発表内容の詳細

### 5.1 この 1 年の変化

Jason 氏は、1 年前の状況を、職人が手作業で物を作っている白黒写真（本人は「たぶん革細工」と述べています）になぞらえました。当時のエージェントやAI機能の開発は、カスタムな知識と多くの時間を要する「手作業」だったという説明です。

モデルの出荷ペースも変わりました。1 年前は平均 17 日ごとに新しいフロンティア LLM が出ていましたが、「確かな筋から聞いた話」として、現在は 6 日ごとに出ているとのことです。ここでいうのは上位 8 社ほどのフロンティアラボが出す LLM のことで、画像・動画の拡散モデルや小規模言語モデルは含みません。直近 7 日間だけでも主要なモデルが 5 つ出荷された、と述べています。

GPT-3.5 や GPT-4o の時代のモデルでは、出力を少しずつ修正しながら導く「steering」が必要で、旧 Copilot Studio（現在の呼び方は「standard harness」）はその時代向けに設計されていました。モデルを軌道に乗せ続けるためのコードが大量に周辺に置かれていた、という説明です。

新しいモデルは、目標に向かって非常に長い時間動き続け、推論し、ツールの失敗にも対処できます。Jason 氏はこの見方を「software factory」という言葉で表しました。8 月に出荷した新しい Copilot Studio については、次のように説明しています。

- 旧バージョンは完全に手作業で作られていた。
- 新バージョンは完全にエージェントによって作られた。人間は「エージェントを作るエージェント」を作り、それが Copilot Studio、あるいはさらに別のエージェントを作る、という間接的な関わり方になっている。
- 現行の Copilot Studio には、手で触れられたものが一つもない。
- すべてを手作業で確認する世界から、判断を信頼でき、検証もできるエージェントを作った世界に変わり、製品との関わり方が変わった。

これにより、製品全体をゼロから短期間で作り直せたとのことです。

### 5.2 Copilot Studio が適する課題

Jason 氏は「どんな課題を解決したいのか」を最初に問うべきだとして、3 つの領域を整理しました。

| 領域 | 例として語られた内容 | 使う場所 |
| ---- | ---- | ---- |
| 従業員の生産性 | メールの文面改善、PowerPoint にアニメーションを加えるスキル | Copilot、Cowork |
| 製品・サービス | 新しいアプリやサービスをゼロから作り、任意のものと接続する | GitHub Copilot |
| ビジネスプロセス自動化 | 組織が大規模に効率よく動くための課題 | Copilot Studio |

Copilot Studio が扱うのは、その中間にある「ビジネスプロセス自動化」です。

### 5.3 柱 1：メーカー体験

Copilot Studio は、エージェント、ワークフロー、アプリを一つにまとめて作れる場所です。Jason 氏は、Copilot Studio は「エージェントを作る場所というより、プロセス全体でビジネス課題を解く場所」だと述べています。3 つの役割は次のように整理されています。

- **エージェント**: 推論して問題を解くシステム。
- **ワークフロー**: 決定的（deterministic）な処理で、効率よく大規模に実行できる。
- **アプリ**: 結果の提示、コマンド操作や可視化を、エンドユーザーに見せる手段。

発表では、次の新機能が紹介されました。

- **新しいエージェントデザイナー**: ゼロから作り直したもので、「何を削れるか」「どこを AI の判断に任せられるか」を考えて、旧版より単純で直感的にしたとのことです。画面の右側にツールや機能が並び、その場で設定でき、エージェントができることが一目で分かります。
- **新しいワークフロー体験**: 決定的なワークフローに、必要なときにエージェントノードを組み合わせられます。エージェントやアプリとのやり取りを理解するよう作り直されており、Jason 氏が一番気に入っている点は「速い」ことです。
- **アプリ機能**: 同じシステムでアプリを作れる機能で、発表時点で GA（一般提供）です。

さらに、Cowork、GitHub Copilot、Claude Code、OpenAI Codex など、どのエージェント型コーディングハーネスからでも、これらを直接作れるようにしたと説明しています。Jason 氏は、ワークフローにすべきかエージェントにすべきかを人間の専門家が判断する世界ではなく、AI システムがビジネス課題から最適な構成を提案し、一緒に作り上げる世界を目指すと述べています。

### 5.4 柱 2：エージェントの機能

#### Microsoft Copilot harness と効果測定

新しいハーネスは「Microsoft Copilot harness」と呼ばれ、Jason 氏によれば、Foundry や Cowork など社内の他の製品チームも同じハーネスを使っています。背景には、モデルが賢くなった分、ツールを使い、問題を解く余地を持ちつつ、組織のポリシーで統制される「適切な動作環境」をモデルに与える必要が出てきた、という認識があります。

効果は 2 つのグラフで示されました。条件は共通で、同じモデル（Sonnet 4.6）、同じ数万件のタスクと評価（モデル受け入れテストに使う 5 万〜6 万件のテスト）で、旧 standard harness と新しい Copilot harness を比較しています。評価は、knowledge、code analysis、file analysis、multi-tool の 4 つのグループに分かれています。

- **品質**: モデルもタスクも変えていないのに、全体で大きく向上した。
- **入力トークン消費**: コストの主な要因は入力トークンだが、ほぼ半額になった。

Jason 氏は、これは少し古いデータで、その後さらに進んだため、現在はテスト自体をより難しいものに入れ替えていると述べています。エージェントは賢くなるほど安くなるべきで、そうなれば組織が Microsoft 環境にエージェントを作り込む価値も増す、という考えです。

#### 3 つのハーネス

| ハーネス | 位置づけ |
| ---- | ---- |
| Microsoft Copilot harness | 既定。高機能で、ほとんどの用途で使う。 |
| Customer Conversation harness | 10 月に新登場。顧客との会話（Web チャットや音声モデルによる電話対応など）に最適化し、品質とコストモデルの面で利点がある。Copilot Studio から構築できる。 |
| standard harness | これまでの投資がそのまま動く。更新は続き、最新モデルも一部提供されるが、Jason 氏は今後 Copilot harness に移す価値が大きいと述べている。 |

#### 移行

Copilot Studio のエージェント・アプリ・ワークフローを作る MCP サーバーは、移行にも使えます。単純な移植ではなく、作成済みの内容を推論し、「このエージェントの一部は、より効率的に動く 2 つのワークフローにできます」といった提案を返す、という説明です。

#### スキル

スキルは、ある能力を記述した .md ファイルです。業界全体で投資が進んでいますが、Microsoft 環境では、作ったスキルを Microsoft の体験に直接公開できる点が違うと説明されました。Cowork や Copilot で作ったスキルを保存して再利用でき、IT が統制・管理する形で組織全体に共有できます。カタログに公開したスキルは、どのエージェントからでも使え、逆も可能です。

#### メモリ

Jason 氏が最も期待している機能の一つです。2 つの側面があります。

1. 利用者の習慣を覚える。毎朝同じ質問をする利用者に対し、追加の質問なしで前提を置いて動ける。
2. 「どうやったらうまくいったか」を学ぶ。エージェントは多くのツール（Web 検索、SharePoint、Outlook、Teams の会議メモなど）を使うが、結果の良し悪しから最適なやり方を学び、次回に生かす。「最適」には最速・最効率などが含まれる。

その結果、エージェントは時間とともに速く、賢く、安くなります。Jason 氏は、1 か月の間にかなり安くなるのを見たと述べています。制御も可能で、いつでもオフにでき、エンドユーザーはポータルで自分に関するメモリを確認し、削除できます。

#### Auto（プレビュー）

モデルの選択肢が多いとメーカーは疲弊し、モデルの提供期間も思ったより短い（GPU が不足している）ため、最先端を追いかけ続ける負担が生じます。そこで、作ろうとしているもの・実行しようとしていることを見て、必要な最小限の知性を判断し、それを満たす最も安いモデルを選ぶのが **Auto** です。社内のコンプライアンスなどの要件も判断に含まれます。モデルの更新、テスト、検証から解放されることが狙いで、発表時点で、すべての体験でプレビューとして利用できます。

#### MCP Apps とチャット体験

Jason 氏は、チャットは今後も続くとしたうえで、チャットが静的なテキストである必要はないと述べました。日付の一覧を読むよりカレンダーウィジェットの方が分かりやすい、という例です。

- **MCP Apps**: チャットの流れの中に、カレンダー選択やデータのグラフのような視覚的な体験を組み込める機能。
- **チャット体験の更新**: chain of thought の表示（エージェントの動きやツールの利用が見える）。権限管理や接続管理（サードパーティシステムへの接続）の体験もシームレスにし、接続まわりの新機能を GA した。

### 5.5 柱 3：ガバナンスと FinOps

Microsoft 社内ではかつて「エージェントはアプリのように管理することになる」と考えていました。社内には数千〜数万のアプリがあります。その後、エージェントは人（従業員は約 25 万人）の数に近づくと考えましたが、それも超え、現在は毎日動いているエージェントが、おそらく 100 万を大きく超えているというのが Jason 氏の説明です。エージェントは別種のもので数も多いため、ガバナンスが重要になります。詳細は「A365」チームのセッションやデモに譲る、とのことでした。**ガバナンスも FinOps も Copilot Studio から始まる**というのが主張です。

#### 評価（evals）

Jason 氏は、良いエージェントと悪いエージェントを分ける最大の要素は evals の作成だと述べました。MCP サーバーを使えば、Cowork や GitHub Copilot などから、エージェントを使って評価を作れます。評価の作成に必要なスキルとツールは、さまざまな採点方式を含めて標準で提供されるため、評価の専門家でなくても作れる、という説明です。

#### Monitor タブ（プレビュー）

デプロイ前の苦労はデプロイ後の課題の 1% にすぎず、現実にぶつかるのはデプロイ後だというのが Jason 氏の見方です。Monitor タブでは、エージェントごとに次の情報を一か所で確認できます。

- 動作状況、コスト
- エラー、特定サービスとの通信でのタイムアウトなどの問題
- 従業員からのフィードバック（高評価・低評価、要望）

これらの情報は、Cowork に「自分のエージェントの調子はどうか」と尋ねて分析と提案を返してもらうなど、エージェントからも利用できます。

#### FinOps for agents（GA）

AI のコストは非常に変動が大きく、重いモデルは高く、軽すぎるモデルは役に立たないという問題があります。そこで、1 つのエージェントだけでなく、すべてのエージェントについて、支出の規模、発生源、影響を受ける人、利用状況を見られる FinOps for agents が発表時点で GA だと説明されました。予算管理にも使えます。

また、エージェントがクレジットを消費するだけでなく、**どこからクレジットを消費させるか**を制御できるのも特徴です。誰でも使える常時提供のエージェントと、複雑で特定の利用者だけが使うエージェントとで、制約や予算の出所を変えられます。

#### メーカー向けルールと制限

組織ごとにリスクへの姿勢や規制は違うため、メーカー体験にそれを反映できます。

- 「メーカーとして守るべきルール」を提示し、メーカーが確認したことを Purview で追跡できる。コンプライアンス担当者に、全員が研修を受けたことを証明できる。新しい更新も同じ体験で配信できる。
- 第三者サービスの利用可否などの制限を明示できる。例えば、Morningstar MCP が既定ポリシーで無効のとき、誰にどんなプロセスで承認を求めればよいかを、メーカーに分かるようにする。「何でも作れる無法地帯」でも「何も起きない鉄壁」でもない状態を、ワンクリックで承認に進める体験で目指す、と述べられています。

## 6. デモ・手順

デモは Alice 氏が、3 つの柱の区切りで 3 回に分けて行いました。**画面の細部は音声からは確認できず、以下は語られた範囲に限ります。**

### 6.1 Cowork で Financial Insights Agent を作る（柱 1 のデモ）

1. Alice 氏は金融アドバイザーという設定で、調査・分析・顧客への提案の連絡を自動化するエージェントを作りたい、と説明した。
2. Cowork でプロンプトを入力した（プロンプトの全文は読み上げられていない）。Cowork が応答を始め、Copilot Studio プラグインと automation プラグインを読み込んで作成を進めた。Morningstar MCP サーバーのツールを使うことがプロンプトで指定されていた。
3. 実行に数分かかるため、時間の都合で、同じプロンプトで当日先に作っておいた「Financial Insights Agent」に切り替えた。
4. 生成された内容を順に確認した。
   - エージェントの指示: 自律型のエージェントであること、包括的な財務インサイトを出すこと、市場データは Morningstar MCP からのみ取ること（LLM がネットから不確かな数字を拾ってこないようにするため）、組織のトーンとスタイルに従うこと。
   - スキル: 顧客に送るメールのテンプレートに関する既存のスキルを自動で組み込んでいた。必要なら新しいスキルも作れたとのこと。
   - ツール: Morningstar MCP サーバー。ワークフロー。「Get client holdings」というワークフローは、CRM システムから顧客の保有資産を取得する。
   - ナレッジ: 会社の投資哲学（目的、ガードレール、原則）を記した文書。
5. Alice 氏は「エージェント・ワークフロー・アプリの組み合わせが、最も低いコストで最も質の高い出力につながる」と述べたうえで、ワークフローを開いた。プロンプトで「顧客にメールを送る前に自分の明示的な承認が必要」と指示していたため、そのためのワークフローが作られていた。流れは、エージェントがメールの下書きを作ってワークフローを呼び出し、承認依頼が来て、承認すれば送信し、処理がエージェントに戻る、というものだった。決定的なので速く安く、LLM の判断に任せるより信頼できる、と説明された。
6. ワークフローの表示方向を、ワンクリックで上下方向と左右方向に切り替えられることを見せた（Jason 氏は上から下、Alice 氏は左から右を好むという掛け合いがあった）。
7. 別のユースケースの、より複雑なワークフローを見せた。共有メールボックスに届いたメールを「Classify」ノード（比較的単純なモデル）でカテゴリに分類し、以降の処理をカテゴリごとに分けている。エージェントやモデルをワークフローのノードとして組み込める例として示された。

### 6.2 エージェントのテスト（柱 2 のデモ）と評価（柱 3 のデモ）

**テスト実行**

1. モデルの選択は Auto のままにして、プレビュータブでテストした。トークン効率の向上と価格の下落が続くなかで、Auto なら利点が自動的に利用者に反映される、と説明した。
2. 顧客（役として Jason 氏）のポートフォリオにおける Microsoft の位置づけと、推奨事項・注意点を尋ねた。
3. エージェントは Morningstar MCP のツールを使い、Microsoft 単体の株だけでなく、ポートフォリオのインデックスファンド内での Microsoft の組み入れも調べた。
4. 時間の都合で、事前に送っていた結果のメールを表示した。メールテンプレートのスキルでブランドに沿った見た目になっていた。内容は、インデックスファンド内での Microsoft の現れ方、他の AI 関連テック株との重複、強気と弱気の両面の見通し、推奨事項。
5. **聞かれていないのに**、NVIDIA の比率が、同社が顧客に推奨する「1 銘柄あたり 10% の上限」を超えていることも指摘していた。
6. 実行は短時間で完了し、コストは約 1 ドルだった。Alice 氏は、通常なら数時間〜数日かかる分析が数分で出たと述べ、組織内の同じ金融アドバイザー数千人にこのエージェントを公開したいと話した。

**評価（evals）**

1. 正式な評価を作る。この評価セットでは「General quality」グレーダー（関連性と完全性に注目）を使った。ほかに「Task completion」の定義、ツール成功率、「Content safety」、独自の分類器も追加できる、と説明された。
2. 複数のモデルで評価セットを実行して、コストを比較した。
   - Astra: 1 回の実行で約 2 ドル
   - Sol: 約 50 セント
   - Terra: 約 40 セント
   （モデル名は聞こえた綴りのままで、音声認識の都合で表記が確定できません。）
3. 実行ごとに、合否だけでなくエージェントの応答と chain of thought を確認できる。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- 同じモデルとタスクで、新しい Copilot harness は品質が全体的に向上し、入力トークンのコストがほぼ半額になった（Microsoft 社内の評価）。
- Alice 氏のデモのエージェントは、通常数時間〜数日かかる顧客向け分析を、約 1 ドルで数分で出した。
- メモリにより、エージェントは時間とともに速く、賢く、安くなる。1 か月でかなり安くなる例も見ているとのこと。
- Auto により、モデルの更新・テスト・検証の手間が減る。
- スキルを IT の統制のもとで組織全体に共有でき、エージェントからも使える。
- FinOps for agents で、全エージェントの支出と発生源を把握し、予算を制御できる。
- Purview でメーカーの確認状況を追跡でき、コンプライアンス担当者に説明できる。

## 9. まとめ

Copilot Studio は 8 月に、エージェントによってゼロから作り直されました。新しい体験の中心は、エージェント、ワークフロー、アプリを一緒に作れることと、Cowork や GitHub Copilot などから自然言語で作れることです。

エージェントの面では、Microsoft Copilot harness により品質と入力トークンのコストが改善し、スキル、メモリ、Auto、MCP Apps が加わりました。運用の面では、評価、Monitor タブ、FinOps for agents、メーカー向けのルールと制限を通して、ガバナンスと FinOps を作成段階から組み込むことが提示されました。

Jason 氏は、今はメーカーにとって「作るのに素晴らしい時期」だと述べ、フィードバックを求めました。エージェント、ワークフロー、アプリを一緒に作れることで、各組織のビジネスプロセスは 1 年後には見違えるものになる、近いうちにさらに多くを見せられる、とも述べて締めくくっています。
