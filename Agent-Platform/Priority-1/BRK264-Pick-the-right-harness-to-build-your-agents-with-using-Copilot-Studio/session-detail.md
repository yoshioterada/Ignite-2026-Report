# BRK264 Pick the right harness to build your agents with using Copilot Studio

## 1. はじめに

このセッションは、Copilot Studio でエージェントを作るときに、どの「harness（ハーネス）」を選ぶべきかを整理したものです。harness とは、モデルを包んでエージェントとして動かす実行の仕組みのことです。Copilot Studio には現在 3 種類があり、発表では次のように紹介されています。

- **Microsoft Copilot harness**：複雑で長時間にわたる業務プロセス向け。今年の初めにリリース
- **customer conversation harness**：音声やカスタマーサービス向け。先月リリースされ、このセッションの日に一般提供（GA）になったと説明されています
- **standard harness**：2023 年からある従来のもの。継続性のために引き続き利用できる

発表者は、新しく作るエージェントには、新しい 2 つの harness のどちらかを推奨しています。内容は、Microsoft Copilot harness の仕組みと社内評価データ、ライブデモ、お客様の NFP（Aon 傘下）による事例、customer conversation harness の機能とデモ録画という順で進みます。

画面を使ったデモは 2 回あります。Alice 氏による Microsoft Copilot harness のライブデモと、Jason 氏による customer conversation harness のデモ録画です（Jason 氏はライブデモを予定していましたが、会場の電波状態が悪く録画に切り替えています）。

## 4. 発表者が伝えたいメッセージ

Alice 氏の主張は、「かつての standard harness の設計は、推論力の高い今のモデルの足かせになっている。新規のエージェントは新しい harness で作ってほしい」というものです。standard harness は、モデルが課題全体を見渡せないよう、ハーネス側が小さな狭いプロンプトに分解して渡す設計でした。この設計は 2023 年当時は、チューニングしやすく、ガードしやすく、応答も速いという強みでした。今ではそれが制約になっているという説明です。

もう 1 つは、**新しい harness は品質が高く、しかも安くなる見込みがある**という点です。standard harness を従量課金（consumption）で使っているお客様が「新しい harness の方が高くなるのでは」と心配しているなら、そうではないと伝えたい、という呼びかけがありました。

そして「すべてを agent にしなくてよい」という考え方です。モデルの非決定的な判断と、より規定的で速く安い決定論的なワークフローを組み合わせると、最良のコストで成果を得られると説明しています。

## 5. 発表内容の詳細

### 5.1 harness の変遷

Alice 氏は、4 年前を振り返って次のように説明しています。

| 時期 | できごと | harness の特徴 |
| --- | --- | --- |
| 2022 年 11 月 | OpenAI が ChatGPT を公開。Microsoft を含む複数社がチャット型の AI 製品を出した | chat harness。単発（single-turn）の回答。モデルの「ギザギザの（jagged）弱点」を補うため、明示的なヒントと制限を与える作りで、当時は効果的だった |
| 2024 年 12 月 | OpenAI が最初の推論モデル O1 を発表 | |
| その約 1 年後 | Anthropic が "clawed code"（書き起こしのまま）をリリース | スキルやツールといったプリミティブと、より強力な推論モデルを coding harness が支える。長い時間軸のタスク、計画・実行・検証の反復ループ、コンテキストの動的な発見が可能になった |

強力なモデルには新しい harness が必要になった、というのが背景です。Copilot Studio の側では次のように対応してきました。

1. **2023 年：standard harness。** 当時としては優れた製品だった
2. **今年の初め：Microsoft Copilot harness。** 当初は GitHub Copilot Harness という名前で、Microsoft Copilot SDK をベースに Copilot Studio が上に構築したもの。複雑で長時間にわたる業務プロセス向けの強力な agentic loop。案件ごとに変わる証拠を根拠に推論する場合や、多くのシステムを同時にまたぐ場合に向いていると説明されている
3. **先月：customer conversation harness。** 強い推論モデルと harness は目標に向けて強い成果を出すが、低レイテンシーやユーザーへのリアルタイムな応答には最適化されていない。その補完として用意されたもの

Copilot Studio で新しいエージェントを作る画面では、上から Microsoft Copilot harness、customer conversation agent、そして継続性のために残された standard harness の順に表示されます。

### 5.2 Microsoft Copilot harness の仕組み

Alice 氏は、この harness を特別なものにしている要素を、3 つ（「3〜4」と発言）挙げています。

1. **agentic loop**：standard harness は 1 回に 1 つのプロンプトをモデルに渡し、モデルがすぐ結果を返す単発の形でした。agentic loop は、満足するか、設定された予算（budget）の上限に達するまで、反復してタスクの完了を試みます。
2. **sandbox**：Azure のコンテナーで、強力なコーディングエージェントが持つ CLI ツールとファイルシステムが使えます。大量のデータをディスク上に置けるため、モデルは一度に全部を見るのではなく、反復して推論できます。
3. **trust layer（ガバナンス）**：Copilot Studio のランタイムが、すべてのモデル呼び出しと応答、ツール実行を管理します。コンテナーは「考えて作業する場所」であって、認証情報や外部へのアクセスを置く場所ではありません。

### 5.3 社内評価データ：品質とコスト

Alice 氏は、Microsoft 社内のオフラインのテストケース（業種を問わない実際のビジネスプロセスのシナリオに基づくもの）で、standard harness と新しい harness を比べた結果を示しています。

**品質**

ナレッジの扱い、コーディングタスク、ファイル分析、1 回の実行で複数回のツール呼び出しが必要な場合の各項目で、新しい harness の品質が大きく上回りました。

その理由として、standard harness は最新のモデルを過度に制約していると説明しています。モデルをより強力なものに変えたとき、standard harness では合格率（pass rate）が変わりませんでした。一方、新しい harness では、OpenAI のモデルと比べて **10 ポイント**、Anthropic のモデルと比べて **22 ポイント** 向上しました。

**コスト効率**

- 入力トークンが **45% 減少**。入力トークンは価格の面で最も高いタイプのトークンと説明されています
- 意外なことに、新しい harness は**モデル呼び出しの回数は多い**。agentic loop が簡単には諦めず、最初の方法が駄目なら他の方法を試すため
- それでも、キャッシュの仕組みが優れているため、入力トークンは少なくなる。standard harness は設計上、キャッシュされたトークンの恩恵を受けられなかった

**ライセンスと課金**

| harness | 課金 |
| --- | --- |
| standard harness | 2 通り。Microsoft 365 Copilot のユーザーライセンスで使う方法と、従量課金（prepaid のクレジット、または pay as you go）で使う方法 |
| Microsoft Copilot harness | 使用量ベース。常に従量課金 |

従量課金で standard harness を使っているお客様向けに、同じ 300 件のテストケース（オフライン評価）と同じモデル（Opus 4.8 と発言）で比較した結果が示されました。**品質（評価の合格率）は約 2.5 倍**で、コストは「大幅に削減」されています（具体的な削減率は、この箇所では語られていません）。Alice 氏は、新しい harness の方が安くなると見込んでおり、試してほしいと呼びかけています。

### 5.4 NFP（Jennifer 氏）の事例

**会社の紹介**

Jennifer 氏は、NFP は人的資本（human capital）、リスク資本（risk capital）、その基盤となる共有サービスに注力していると紹介しています。米国のほか、カナダ、英国、アイルランドにも社員がいます。顧客向けの領域としては、従業員福利厚生、損害保険、リスク管理、役員向け福利厚生、資産運用、退職年金プランのアドバイザリーを挙げています。「people-first」と「what-if」のアプローチを大切にしています。

**導入の経緯**

NFP は Power Platform とエージェントの活用にすでに長い経験があり、成長は当初は自然発生的でした。そこから 2025 年に、全員を対面でトレーニングし、Copilot Studio のライセンスを渡すという明確な方針に切り替えました。基礎が揃ったことで、2025 年にトレーニングを始めた時期から成長が大きく伸び、利用が年々複利で広がっています。

**課金とハーネスの変化への対応**

新しい従量課金や新しい harness が出たとき、NFP には大きな懸念が生まれました。すでに利用が広がっているぶん、リスクも大きかったためです。そのまま評価を続けて停滞する道を選ばず、これをフレームワークとデータに変えて、データに基づく判断ができるようにしました。

1. **最悪のシナリオをモデル化した。** 数千人のメーカー（maker）が最も高価なモデルを選び、多くの MCP サーバーが使え、自律的な再試行が多発して、すぐに悪化するかもしれないという想定です。
2. **想像を、期間を区切ったテレメトリーに置き換えた。** ある期間の変化量を評価し、新しい harness で実際に何が起きたかを確認しました。
3. **結果。** 人々はトレーニングを活かして正しく使っており、全員が新しい harness を使っているわけではなく、standard harness で作っている人もいました。これにより、どのプロセスを調整すべきかが分かりました。
4. **ガバナンスの位置づけ。** あいまいな不安をデータに基づく判断に置き換えたことで、ガバナンスは「通過しなければならない関門」ではなく「速く進むための仕組み」になった、と述べています。

**ユースケース：Medicare・個人向け医療保険の申込処理エージェント**

NFP には、個人向けと Medicare の申込書を毎日取り込む多数のプロデューサー（販売担当）がいます。年間を通じて発生し、オープンエンロールメントなど時期によって急増します。データは CRM に入れる必要があります。課題は次のとおりです。

- 申込書の書式が 20 種類を超える（手書きも、タイプされたものもあり、ばらつきとあいまいさが大きい）
- 地域が 4 つあり、連合型の組織のため、各地域に独自のやり方がある
- そのため、推論に基づく柔軟な方法が必要だった

導入前は、担当者が PDF を開き、データを CRM に再入力し、検証し、CRM に添付する作業を、申込書 1 件ごとに繰り返していました。導入後は次のとおりです。

1. 担当者が、地域ごとに決められた SharePoint のフォルダー構造に申込書を置く
2. Power Automate のトリガーが起動してエージェントを呼び出す
3. エージェントが、作成したスキルに基づいて推論し、PDF を読み、スキーマを適用してデータを抽出する
4. 厳格な精度チェックを行い、各項目について適切に処理できたかを判断する
5. 承認フローを通す
6. CRM へアップロードする

人は、外れ値や例外、精度基準を満たさなかったものをレビューします（human in the loop）。「ボトルネックはビジネス需要ではなく、非常に手作業の多い工程だった」と述べています。

**成功の定義**

開始前に成功を定義しておくことが大切だったとして、指標を事前に決めたと説明しています。サイクルタイムの短縮、スループットの向上、フィールド精度と品質の向上、エンドツーエンドでの完了の測定です。テレメトリーとモニタリングによって、社員が再入力のような手作業ではなく、重要な仕事に集中できるようにしています。

**設計の特徴**

- 「広く推論し、狭く行動する」エージェントである
- キャリアごとのレイアウト別にスキルを作ってはおらず、agentic な処理のフレームワークを重ねている
- 最後に、注意が必要なものだけに人が集中できる
- テレメトリーのログ、相関、結果が、エージェントの処理全体から収集され、データリポジトリに保存される。効率が出たか、デバッグが必要な場合にどこから始めるかが分かる
- 毎週数千件の申込（原文は聞き取りが不明瞭）が届き、人手でやるには大きな労力が必要だった。繰り返しの作業は自動化し、判断は自動化せず人の判断を残している

**新しい harness を実用的と考える理由（Jennifer 氏）**

- 再利用できるスキルで、モジュール化できる
- クレジット消費を抑えられる
- 適応的な推論が強化されており、すべてのプロセスを条件分岐で定義する必要がない
- ツールの範囲が非常に狭く、扱う対象（surface area）を小さく保てる
- イベント駆動で、ヘッドレスに動かせる
- 例外は人がレビューする
- 観測しやすいランタイムで、モデル、テレメトリー、会話、相関を記録できる（デューデリジェンスの観点）
- time to market が速く、maker に優しい。業務に近い人がエージェントを作れるため、技術部門が作っても使われないという事態を避けられる

> 補足：Jennifer 氏の事例では、時間短縮率やコスト削減額などの数値は発表では語られていません。

### 5.5 customer conversation harness（Jason 氏）

Jason 氏は、**社外の顧客と対話する必要があるとき**にこの harness を選ぶべきだと説明しています。Web サイトや電話番号に置く、音声エージェント、IVR、チャットボットを作るための harness です。

**特徴 1：ネイティブなオムニチャネル**

1 つのエージェントで、音声とチャットの両方に対応します。1 回作れば、電話番号、自社の Web サイト、Teams phone など複数のチャネルで使えます。音声は後付けではなく、harness にネイティブに組み込まれています。

- 複数の voice font から選べ、言語ごとに異なる voice font を設定できる
- 最新のリアルタイム（"real-time latent models" と聞こえます）モデルを使い、非常に低いレイテンシーの音声会話を提供する
- 許容するレイテンシーや感度（小さな声や大きな声、背景ノイズへの対応）を設定できる
- Jason 氏は、直前のデモでイタリア語で会話したと話しています

**特徴 2：1 つのキャンバスでのマルチエージェント構成**

1 つのエージェントを作ると、カスタマーサービス担当者やコンタクトセンターのスタッフのような「エージェントのチーム」を持てます。各エージェントは、それぞれツール、指示、ナレッジ、スキルを持ちます。スキルは生成型だけでなく、決定論的なワークフローも使えます。さらに、従来の MCS の topics もサポートしていると発表しています。

メモリも保持され、再度電話をかけたときに前回の内容を説明し直さず、そのまま会話を続けられると説明しています。

**特徴 3：コンタクトセンターへの拡張**

新しく発表された **Microsoft Contact Center Intelligence（CCI）** は、この日に一般提供を開始した新製品です。これを使うと、選んだコンタクトセンターにエージェントを拡張できます。

- CCI でコンタクトセンターの接続を設定するか、提供されている事前構築済みの接続から client ID をコピー＆ペーストする
- 提携している既存のコンタクトセンターとして、Genesis、Avaya、Five9、Cisco を挙げている
- ルーティングキューやコンタクトセンターの動作を変える必要はない
- 品質のインサイト：品質エージェントがバックグラウンドで各会話をスコアリングし、何が起きたか、どう改善すべきかが分かる
- 声紋認証（voice biometrics）：電話で話した声で本人確認でき、ワンタイムパスワードやアカウントのパスワードを言う必要がない。声の情報は CCI で管理できる

**作成方法**

Copilot Studio の「more ways to build」の下に、新しく customer conversation harness の選択肢があります。自然言語でプロンプトを入力すると、サブエージェントを意識した設計でエージェントを生成し、そのサブエージェントにスキルも追加します。

**提供状況と課金**

- この日から GA
- 提供地域：US、EU、オーストラリア、UK、カナダ、アジア、スイス、UAE。今後さらに地域が追加され、GCC も将来対応予定
- Copilot クレジットを消費する。Microsoft Copilot harness と非常に似た形で、見積もり用の計算ツールも提供されている

### 5.6 まとめ（Alice 氏）と今後の案内

standard harness は引き続き利用できます。すでに時間をかけて作ったエージェントはそのまま使えますが、新しいエージェントでは、プラットフォームからより多くのビジネス価値を得るため、新しい harness のどちらかを検討するよう推奨しています。

どの harness を選んでも得られるプラットフォームの価値として、次を挙げています。

- モデルの選択肢
- データやシステムとの連携
- アプリケーションライフサイクル管理
- 可視性、透明性、コントロール、データセキュリティ

## 6. デモ・手順

### 6.1 Alice 氏：Microsoft Copilot harness のライブデモ（ファイナンシャルアドバイザー向けエージェント）

Alice 氏は、デモの前にデバイスにログインしています。画面の細部は音声からは確認できないため、語られた内容の範囲で書きます。

**想定する場面**

Alice 氏はファイナンシャルアドバイザーの立場で、顧客に分析、洞察、推奨事項を伝え、市場の変化に合わせて、顧客と合意した目標とガードレールにポートフォリオが合っているかを確認します。この繰り返し作業を助け、時間を取り戻すためのエージェントです。

**エージェントの設定（語られた順）**

1. **instructions（指示）**：従来は、具体的で順序立った手順、やってよいこと・いけないことを何ページも書いていました。新しい harness では、達成したいゴールを明確に書き、最も重要なガイダンスを強調するだけにして、指示を詰め込みすぎないようにします。より強いモデルとより強い harness なので、モデルの判断に任せる部分が増えます。
2. **モデル**：「auto」を選択。Copilot Studio がユースケースに最適なモデルを選び、新しいモデルが出たときに、ユーザーが何もしなくても価値が引き継がれます。
3. **triggers**：エージェントを使える条件（トリガー）を設定済み。
4. **スキル**：クライアント向けメールを下書きするときに使うメールテンプレートのスキル。プロフェッショナルな見た目と、社のブランドガイドラインに沿わせるためです。スキルは markdown ファイルで、メールを書く場面のときだけ、モデルのコンテキストウィンドウに読み込まれます。メール以外の場面では、コンテキストを汚したり気を散らしたりしません。
5. **ツール**：Morningstar MCP（会社が信頼するサードパーティの MCP で、質の高い正確な金融データ用）を接続しています。市場データには検証済みで最新の Morningstar のデータだけを使うよう指示しています。そのほか、自分自身の情報を取得するツールなどがあり、自分でも同僚でも、正しいメールアドレスに送れるようにしています。
6. **ワークフロー**：「すべてをエージェントにすべきではない」という考えから、顧客へメールを送る前に必ず自分の承認を得るワークフローを作成。エージェントがワークフローを呼ぶと承認リクエストが送られ、承認したときだけ、エージェントがツール呼び出しでメールを送信します。Alice 氏は、新しいワークフローデザイナーを紹介し、左から右、または上から下の表示を選べると話しています。
7. **knowledge**：自社の理念（philosophy）が書かれたファイルを接続。反復する agentic loop の中で、その作業に関係するときだけ、モデルのコンテキストウィンドウに取り込まれます。

**実行**

1. 情報を求めているクライアントについて、かなりオープンエンドな形でポートフォリオの評価を依頼する（プロンプトの細部は語られていません）。プロアクティブなトリガーで、ユーザーがプロンプトを入れずに動かすこともできる、と補足している
2. エージェントはツール呼び出しを使い、接続されたナレッジの検索、Morningstar の情報の取得、クライアントの保有資産の参照を行う
3. 結果として、承認して問題なければクライアントに転送できる下書きメールが、エージェントから自分に届く。Alice 氏はこの例を、この日の早い時間に実行したものとして紹介している
4. メールの中身：
   - 現在のポートフォリオが、クライアントとの目標・ガードレールを満たしていない箇所がいくつかあった
   - クライアントは Microsoft 社員で、すでにレバレッジが高いため、Microsoft 株への露出を低くしたい。現状は 5% のしきい値を上回っている
   - エージェントは、指示に書かれていないのに、Microsoft 株を個別銘柄としてだけでなく、クライアントが投資するインデックスファンドの一部としても探していた
   - Microsoft 以外にも、NVIDIA への露出が、個別株の推奨上限として設定した 10% のしきい値を超えていることを見つけていた
   - 分析、データ、次に取るべき行動の推奨が含まれる
5. Alice 氏はこのエージェントに満足し、同僚が使えるよう組織内に公開する段階に来ている。ライブデモで依頼した処理はすでに完了しており、エージェントのページでは **1 ドル未満**で処理が終わったことが確認できた

### 6.2 Jason 氏：customer conversation harness のデモ（録画）

Jason 氏は、ライブデモを見せたかったものの、舞台裏で試したところ会場の電波が非常に悪いため、少し前に自分で録画したデモ録画を見せると説明しています。「これから登場するものの一端」であり、翌日の別セッションでフルのライブデモを見せる、と話しています。

録画の内容は、次のとおり語られています。

1. 自然言語でエージェントを作成すると、マルチエージェント構成で、mortgage（住宅ローン）、credit card（クレジットカード）、checking account（当座預金）のサブエージェントが作成された。サブエージェントはそれぞれ、ツール、ナレッジ、スキルを持てるため、コンタクトセンター担当者ができることを反映している
2. 新しいスキル「クレジットカードの推薦」を作成した。必要だったのは、新しいクレジットカードのパンフレットをアップロードし、その生成型スキルに指示を追加することだけだった
3. 音声とチャットの両方で、新規クレジットカードを申し込むための決定論的な topic を作成した
4. 口座残高を確認するために、Copilot Studio にすでにあるワークフローを使うが、ユーザーが声で認証された場合のみ実行する設定にした
5. 作成後、エージェントをプレビューした。テキストと音声の両方で試せ、電話番号は不要だった
6. 音声での会話：エージェントは「Contoso Bank Modernized Assistant、Microsoft Contact Center Intelligence を搭載」と名乗った。旅行に行くので特典の良いクレジットカードを選びたいと伝えると、年会費ありかなしかを聞かれた。年会費は構わないが、特典が良くラウンジが使えるものがよいと答えた。エージェントは Contoso Horizon Reserve カード（年会費 $4.95、Contoso Sky Lounge のメンバーシップなどの旅行特典）を提案した
7. 画面の右側では、どのように処理したかの activity trace を確認できた
8. エージェントを評価し、Web サイト、電話、コンタクトセンターなど多くのチャネルにデプロイできる
9. 公開後、Contoso Bank の新しい Web サイトに、右下にチャットウィジェットが表示された。クレジットカードの申込を依頼すると、決定論的な topic が動き、adaptive card でクレジットカードの選択肢を視覚的に表示した
10. エージェントは電話番号につながっており、電話をかけ直した。新規カード申込の件で、当座預金の残高を確認したいと伝えた。発信者番号（caller ID）と声から本人確認が行われ、残高は $68 と案内された

Jason 氏によると、録画では自分の声で電話しているため、同じ電話を Alice 氏がかけたら、エージェントは Alice 氏を拒否するとのことです。

## 7. 注意点・発表者の気付き

- **standard harness は、強力な推論モデルに対しては制約になる。** モデルを強力なものに変えても、standard harness では合格率が変わらなかったと説明されています。
- **新しい harness はモデル呼び出しが増えるが、入力トークンは減る。** キャッシュの仕組みが効くためだと説明されています。
- **従量課金の見積もりを心配する場合は、評価・テレメトリーで確認する。** NFP は最悪ケースを想定してモデル化し、期間を区切ったテレメトリーで実際の利用を確認しました。
- **instructions は詰め込みすぎない。** 新しい harness では、ゴールと重要なガイダンスを書き、モデルの判断に任せます（Alice 氏）。
- **スキルはコンテキストを汚さないために使う。** 関係するときにだけコンテキストに入る（Alice 氏）。
- **すべてをエージェントにしない。** 決定論的なワークフローの方が、規定的で速く安い場合があります。承認のように必ず通す手順は、ワークフローにしています。
- **成功の指標は事前に決める。** NFP は、開始前にサイクルタイム、スループット、精度、完了率を定義しました。
- **自動化するのは繰り返しで、判断は人に残す。** NFP の事例では、人は例外とあいまいなケースに集中します。
- **会場の電波でライブデモができないことがある。** Jason 氏のデモは録画に切り替わりました。
- **customer conversation harness は、社外の顧客との対話向け。** 長時間の業務プロセス向けの Microsoft Copilot harness とは用途が異なります。

## 9. まとめ

Copilot Studio には、2023 年からの standard harness に加えて、今年の初めの Microsoft Copilot harness と、先月の customer conversation harness があります。Alice 氏は、強力な推論モデルには新しい harness が合うと説明しています。社内評価では、同じ 300 件のテストケースで品質が約 2.5 倍になり、入力トークンは 45% 減っています。

Microsoft Copilot harness は、agentic loop、sandbox、trust layer を備え、複雑で長い業務プロセス向けです。デモでは、ポートフォリオ評価のエージェントが、クライアント向けの下書きメールを作るところまでを 1 ドル未満で実行しました。NFP は、最悪ケースの想定とテレメトリーで不安をデータに置き換え、Medicare・個人向け医療保険の申込処理でエージェントに読み取りと抽出を任せ、例外だけを人が見る形を作っています。

customer conversation harness は、音声とチャットに 1 つのエージェントで対応し、Microsoft Contact Center Intelligence と組み合わせることで既存のコンタクトセンターにも広げられます。（補足）発表の内容を踏まえた使い分けの目安は、複雑で長時間の業務プロセスなら Microsoft Copilot harness、社外の顧客との対話なら customer conversation harness、既存のエージェントは standard harness のまま継続、というものです。
