# BRK278 Inside Copilot code review: From context to approval

## 1. はじめに

このセッションは、GitHub の **Copilot code review** が、どのような文脈（コンテキスト）を集めてプルリクエスト（PR）をレビューし、どう承認（approve）にまで至るのかを、内部の作りと運用設定の両面から説明する 45 分のブレークアウトです。Azure Repos でも使えることに触れています。

内容は大きく 4 つです。(1) レビューの基本的な流れ、(2) Copilot がレビュー時に参照するコンテキスト、(3) 複数のエージェントを組み合わせたアーキテクチャと 3 つ（＋ 1 つ）のレビュー強度、(4) 品質をどう測り、承認をどう任せるか。PR のレビューがボトルネックになっている開発チームや、Copilot code review の導入・設定を検討している人に向けた内容です。

> 補足：このセッションでは、画面を使ったライブ操作は行われていません。実際の PR を使った流れの紹介（6 章）が中心です。

## 4. 発表者が伝えたいメッセージ

出発点は「**レビューがボトルネックになっている**」という問題意識です。今年、GitHub 上で 13 億件（1.3 billion）の PR がマージされており、コーディングエージェントから始まる PR の割合は 3 月の 17% から 9 月には 40% 超になったと述べています。ある企業ユーザーの「普通の人間にとっては圧倒的な量だ」という声も紹介されました。

Copilot code review の目標は、**チームの中で最良のレビュアーを再現し、場合によっては超えること**です。最良のレビュアーは、PR のタイトルと説明、差分、周辺コード、PR の目的の背景、チームのやり方、過去のレビューで出た指摘、リポジトリの外にある情報まで把握しています。Copilot code review はこれらの情報を、それぞれの手段で取り込む構成になっています。

最終ステップである「承認するか」についても、段階的に導入する進め方（リスクの低い PR から始めて広げる）が推奨されています。

## 5. 発表内容の詳細

### 5.1 導入: 会場アンケートと背景

最初に、会場への挙手の質問がありました。AI に PR をレビューさせているかには、過半数（50% 超）が手を挙げました。AI に PR を **承認** させてよいかでは、最初の挙手は、迷いながら手を挙げた人が数人いる程度でした（最初の質問で手を挙げた人の半分に満たない程度）。登壇者が「承認の意味で聞いた」と改めて「今、AI に承認させているか」と尋ねると、手は挙がりませんでした（「Nobody, cool」）。講演の最後に同じ質問が繰り返されます（5.8 参照）。

### 5.2 Copilot code review の進化: 差分だけからエージェント型へ

登壇者は、2025 年の初期の AI コードレビューアー（Copilot code review を含む）は、基本的に **差分（diff）だけを見て**、モデル本来の知能でフィードバックを出していたと振り返っています。それは「まあまあ動いた」ものの、その後に最初に取り組んだのが **エージェント型にする** ことでした。エージェントがリポジトリを探索し、差分にはないコンテキストを読めるようになり、正確で、PR の概念的な問題を網羅したコメントを出せるようになった、という説明です。

会場には「平均的なレビューで、Copilot code review は差分以外に何ファイル読むか」というクイズ（23、84、274 の選択肢）が出されました。答えは次のとおりです。

| 対象 | 差分以外に読むファイル数（平均） |
| ---- | ---- |
| 平均的なレビュー | 84 ファイル |
| max ティア（複数エージェントを並列実行） | 274 ファイル |

> 補足：84 ファイルがどのティアの値かは、発表では語られていません。

### 5.3 最良のレビュアーが持つコンテキストと、Copilot の対応

登壇者は、チームで最良のレビュアーが何を知っていて、何を見ているかを次のように整理し、それぞれに Copilot がどう対応するかを説明しています。

| 最良のレビュアーが知っていること | Copilot code review の対応 |
| ---- | ---- |
| 周辺のコードがどう動くか | エージェント型のレビューがリポジトリのファイルを探索して読む |
| PR の目的（タイトル・説明、プロダクトの文脈） | タイトル・説明を読み、リンクされた Issue もたどって、解こうとしている問題を読み取る |
| チームのやり方（組織固有の知識） | instructions とカスタムの agent skills で、チームのやり方を伝える |
| 過去のレビューで出た指摘、他のレビュアーが重視すること | 新機能 **Dreaming**（パブリックプレビュー）が、過去にレビュアーが付けたコメントから学び、最良のレビュアーを時間をかけて再現する。また、PR コメントでのチームの会話から繰り返し指摘される問題を把握し、将来のレビューで同じ問題を確認する |
| リポジトリの外にあるもの | MCP サーバーを接続して Datadog、Splunk などのサービスの情報を使う。**クロスリポジトリのコンテキスト** を Ignite でパブリックプレビューとして公開 |

登壇者は、リポジトリの外のコンテキストについて、モノレポでない限り、ある PR が他のリポジトリやサービスに影響を与えうること、Azure、Datadog、Sentry、Splunk などのサービスの状態とコード変更が交差することが多いことを述べています。

#### Issue からの文脈（PR を軌道に乗せる）

当初の Issue から大きく変わってしまった PR に対して、Copilot が PR を軌道に乗せる例が紹介されました。リンクされた Issue から 2 つの受け入れ基準（acceptance criteria）を特定し、PR を読んで、両方を満たすはずの PR が 1 つしか解決していないことに気づく、という内容です。Issue の文脈から、PR で実際に何をすべきかが分かります。

#### Repo skills（agent skills）

Agent skill は、エージェントが必要なときに読み込むガイダンスファイルです。コードを書くため、またコードをレビューするための skill を書けます。Copilot 向けだけでなく Claude や Gemini など他のエージェント向けに書かれたものでも、リポジトリ内にあれば Copilot が拾ってレビューに使います。

例として、Claude のディレクトリにある skill ファイルに「依存関係の更新は単独の PR で行う」という指示があるケースが示されました。依存関係の更新とタイムアウト動作の変更の両方を含む PR に対して、Copilot は skill のコンテキストを踏まえ、タイムアウト動作の変更を別の PR に分けるよう助言します。コメントの末尾には、その指摘に使われた skill の **アトリビューション（出典表示）** が付きます。チームの知識を全部 skill に保守したくない場合や、更新が古い場合に備え、Copilot は PR コメントの会話からも学ぶとのことです。

#### クロスリポジトリとリポジトリ外のコンテキスト

コンテキストは、依存関係のリポジトリや、プロダクトの正しい情報を持つ docs リポジトリにも存在します。Copilot はこれらのリポジトリから必要に応じてコンテキストを取り、下流への依存の影響などを指摘できます。GitHub の外にあるコンテキストは、Jira や Linear などの Issue 管理システム、Microsoft Learn や Confluence などのドキュメント、Datadog や Sentry などの本番環境にあります。MCP サーバーで Copilot code review を接続すれば、どこにあるコンテキストでも使えます。

### 5.4 レビューの実行アーキテクチャ

実行の流れは次のとおりです。

1. PR のタイトル、説明、差分、場合によっては過去のコメントやコミット、その PR での反復を集め、コンテキストを整える。
2. 整えたコンテキストを、**並列に動く複数のエージェント（アンサンブル）** に渡す。主要なレビューエージェント群は、ティアによって同じモデルを複数回使うことも、異なるモデルを使うこともある。ほかに、過去のレビュアーの指摘パターンを探す **Dreaming 専用のレビュアー** と、Ignite で追加された、オプションの **AI によるシークレットスキャン** のパスがある。
3. 出力は **集約エージェント** に渡される。集約エージェントは、各エージェントが見つけた問題を正規化し、標準化された重要度（severity）を付け、重複を取り除き、表示する品質の基準を満たしているか確認する。
4. 最終的に 1 つのレビュー、1 組の問題にまとめ、**verdict（判定）** を出す。

重要度は high、medium、low の 3 段階で、「本番に入った場合の影響の大きさ」に基づきます。

#### AI シークレットスキャン（パブリックプレビュー）

今日発表するもので、独自の AI 分類モデルを使います。PR で通常見かける問題と同じ形で表示され、PR に紛れ込んだシークレットを検出します。コメントの下部には、シークレットスキャンのエージェントによる出典表示が付きます。

#### 複数モデルを使う理由

あるモデルが見つけられない穴を、別のモデルが見つけることがよくあります。同じモデルを複数の並列エージェントで使っても自分たちの穴を埋められ、複数のモデルを使えばさらに埋められる、という説明です。

### 5.5 3 つのレビュー強度と adaptive

ティアが上がるほどアンサンブルが単純に大きくなるわけではない、と登壇者は述べています。

| ティア | 構成 | 1 レビューあたりの平均コスト |
| ---- | ---- | ---- |
| light | 主要なエージェントとして、小さめのモデル 4 つを並列実行 | 約 25 セント |
| balanced | より強いモデル 3 つを並列実行 | 約 1.50 ドル |
| max | 2 つのプロバイダーの 3 種類のモデルで、8 つの並列エージェントのアンサンブル | 約 10 ドル |

- max はコスト面で高いが、「同様の価値と精査を得るためにエンジニアに頼むより安い」ため、常に max を使う人も多いと述べています。特に必要なのは、課金の変更など確実に正しくしたい高リスクな PR です。ティアは PR ごとに選べ、個人が max に上げる運用にしても、デフォルトにしてもよいと説明しています。
- max は balanced のおよそ 2 倍の high severity の問題を見つけます。
- ティア作りの方針は、各価格帯でできる限り最良のレビューを作ることです。同じ種類のモデルを増やしたり、上位または下位のモデルバリアントを加えたりすると、ある価格帯で性能が上がることがあり、直感的でない場合もあります。新しいモデルが出るたびに、おおむね 1〜2 週間ごとに構成を調整しています。

#### Adaptive（パブリックプレビュー）

新しいティア **adaptive** は、PR のリスクと複雑さを見て、light、balanced、max のどれにするかを判断します。一般に、ドキュメントやコメントの変更、小さな誤字、リネームなどは light、通常の複雑さの変更は balanced、最もリスクと複雑さが高く規模の大きい PR は max に振り分けられます。

また、Azure DevOps と Azure Repos を使っている人向けに、**Copilot code review は Azure Repos で GA になった**と述べています。

### 5.6 品質をどう測るか

#### ReviewBench

AI コードレビューのベンチマークを先駆けて作り、**reviewbench.ai** で完全にオープンソース化していると述べています。新しいモデルが出たとき、あるいはエージェントのアーキテクチャ、コンテキスト、プロンプトを改善するときに、次の順で評価します。

1. オフライン評価（公開リポジトリの PR から選んだ、キュレーション済みのセット）を繰り返す。
2. 良い結果が出たら、GitHub 内の自社の PR でライブ実行する。
3. まず少数のユーザーに展開し、その後全員に展開する。

ReviewBench には正解データ（ground truth）があり、**200 件以上の PR** について、含まれるすべての問題を人間がラベル付けしています。LLM の judge が、レビューエージェントの最新バリアントが見つけた問題が、正解の問題と一致するかを判定し、各 PR を 2 つの指標で評価します。

| 指標 | 意味 |
| ---- | ---- |
| Precision（適合率） | 見つけた問題のうち、実際に正しかったものの割合。誤検知（false positive）は誰も喜ばないため、常に押し上げようとしている |
| Recall（再現率） | その PR にある問題のうち、実際に見つけられた割合 |

オフラインだけでなくライブでも評価する理由は、オフラインでは、MCP サーバーのようなライブ環境で起こることをすべて示せないためです。ライブでも LLM を judge として多用しています。

#### Address rate

ライブで特に見ている指標が **address rate** です。コメントの多くには自動修正（auto fix）が付き、PR の UI には「apply suggestion」ボタンがありますが、**このボタンを押す人は約 2%** にとどまります。以前は多く使われていたものの、今はエージェントに PR を指して「問題を直して」と言うほうが簡単で、ローカルで直して検証してから PR に push する人もいる、という説明です。そのため auto fix は、ユーザーとそのエージェントの両方に向けて表示し続けており、重要なのは、指摘した問題が **概念的に対処されたか** です。

Copilot code review が PR に付けた問題のうち、**約 77% が対処されました**。これは、PR がマージされる前に、指摘したコメントに対して作成者が概念的に修正したかを LLM judge が判定して求めています。

#### リポジトリの Insights タブ

address rate は、リポジトリの **Insights タブ** で見られるようになりました。次のような情報が分かります。

- Copilot code review のコメントがどれだけ対処されたか（全体の address rate、high severity のコメントなどでの内訳）
- Copilot のレビューなしでマージされた PR（リポジトリでの Copilot のカバレッジの把握）
- カテゴリー別の対処済みコメント（Copilot が内部で分類しているコメントの種類。時間による変化も見られる。例のリポジトリでは bug が最も多いが、リポジトリごとに異なる）
- カスタマイズの種類別の address rate（agent skills、MCP サーバーなど）。カスタマイズなしの場合と比較できる

### 5.7 判定（verdict）と承認の設定

Copilot はレビューを必ず **verdict** で締めくくります。

| verdict | 意味 |
| ---- | ---- |
| Changes recommended | マージ前に直すべきことが見つかった |
| Needs a closer look | 人間のレビュアーに判断を委ねる。この場合、Copilot は問題を見つけていなくても、PR が複雑またはリスクが高いと判断して人間に任せていることが多い |
| Approval recommended | 既定では PR 上のコメントとして存在する。これを **本物の承認（real approval）** に変えることもできる |

本物の承認は、人間の承認と同じように動作します。例えばブランチ保護ルールで「マージに 2 つの承認が必要」と設定している場合、Copilot の承認はそのうち 1 つとして数えられます。実際の PR で Copilot が出す verdict の分布は「かなり均等」と述べています。

承認（real approval）は **既定ではオフ** で、次のレベルで有効にできます。

1. **エンタープライズ**: 各 Organization の判断に任せるか、選択した Organization だけで有効にする。
2. **Organization**: 承認が使える場合、Organization 全体で有効にする、リポジトリごとの判断に任せる、選択したリポジトリのみで有効にする、のいずれか。例として、Organization 管理者がリスクの低いリポジトリを選んで有効にできる。
3. **リポジトリ**: 有効にできるほか、承認を特定のファイルパスやディレクトリに限定できる。リポジトリ内で Copilot がどの PR を承認するかを、決定論的にガバナンスできる。

推奨の進め方は、リスクの低いリポジトリや、リポジトリ内の特定のディレクトリの、リスクの低い PR から始め、その結果を確認してから、パスやリポジトリを広げることです。

### 5.8 まとめの挙手と Q&A

最初と同じ「AI に PR を承認させるか」という質問が再び出され、「何人か増えた。少し考えが変わった人がいた」と登壇者は述べています。

**Q1. 大規模な組織で、リポジトリごとに基準が異なる。クロスリポジトリのコンテキストで、読む範囲をどう制御するか（PR を開始した人に基づくのか、組織が持つすべてにアクセスできるのか）。**
クロスリポジトリのコンテキストはパブリックプレビューで、**現時点の既定では、他の公開（public）リポジトリのみを読みます**。近日中に、リポジトリごとに「どの他リポジトリを見るか」を設定できる構成が提供される予定で、API でも設定できるようになります。例えば 500 のリポジトリのコレクションの全員に、特定のリポジトリのコンテキストを与える設定を、API で一括して行えるようになる、という説明です。

**Q2. Copilot はレビューするだけで承認はしないという理解でよいか。承認を使う場合、人間が関与する形（human in the loop）はどう変わるか。**
どちらも可能で、既定では承認しませんが、設定をオンにすると承認します。承認に Copilot を使っている一部の組織では、承認の段階に人間はもういない、とのことです。GitHub にはすでに **auto merge**（CI が通り、承認要件を満たしたら自動でマージ）があり、承認が 1 つ必要な設定で、Copilot code review を本物の承認に設定していれば、その条件を満たせます。作成者は PR を出して auto merge をオンにして離れても、CI と Copilot の承認がそろえば自動でマージされます。まだそこまで任せたくない組織やリスクの高い領域では、承認者を 2 人必要とし、Copilot が一人分、人間がもう一人分を満たす方法や、Organization 管理者が、リスクの低いリポジトリやドキュメントのリポジトリだけで有効にする方法があります。

**Q3. セキュリティパッチを元に戻すよう AI のコードレビューが推奨する、という経験があった。どう防ぐか。**
現時点でも、instructions のカスタマイズで対応できるはずだと答えています。Copilot code review は、agents.markdown、Copilot instructions.markdown、agent skills から指示を読む、と述べています（ファイル名は音声認識の表記のままで、正確な名称は確定できません）。「そのようなことを決してしない」とこれらのファイルに明文化するのは最適なユースケースで、具体的に指示すると非常によく守られる、という経験を述べています。

**Q4. 自動承認をブランチ単位でオンにできるか。**
「まだできない。ただし良いアイデア」という回答でした。質問者に理由を尋ね、「アイデアをもらっている。これは取り組むかもしれない」と述べています。

## 6. デモ・手順

このセッションでは、トランスクリプト上、ライブでのデモは行われていません。ただし、導入の直後に、実際の PR（OpenCost というオープンソースリポジトリの PR）を使った Copilot code review の基本的な流れが、画面を見せながら説明されています。それがスライドのスクリーンショットかライブの操作かは、音声からは確認できません。以下は語られた順の流れです。

1. PR の作成者が、Copilot にレビューを依頼する。レビュー強度は light、balanced、max から選べる。この例では balanced を選んだ。
2. Copilot が PR をレビューし、変更が必要と判断して「changes recommended」の assessment を残し、未解決の問題を 1 件見つける。
3. 見つけた問題には、本番に入った場合の影響の大きさに基づき、high、medium、low の重要度が付く。
4. 見つかった問題は「このクエリは失敗する」というもので、Copilot はコードの変更を提案する。
5. PR の作成者が提案を適用する。
6. 自動レビュー設定により、Copilot に再度レビューが依頼される。
7. Copilot は問題が解決されたこと、他に未解決の問題がないことを確認し、PR を承認する。これは人間の承認として機能する本物の承認の場合も、マージ可能かを伝えるコメントだけの場合もある。
8. もう一人のレビュアーが承認し、2 つの承認がそろって PR がマージ可能になる。

## 7. 注意点・発表者の気付き

- **承認は既定でオフ。** エンタープライズ、Organization、リポジトリの各レベルで有効にでき、ファイルパスやディレクトリ単位で絞れます。導入は、リスクの低い PR・リポジトリから始めることが推奨されています。
- クロスリポジトリのコンテキストは **パブリックプレビュー**。現時点の既定では他の公開リポジトリだけを読み、リポジトリごとの対象指定は「近日中」の予定です。
- Dreaming、adaptive、AI シークレットスキャンも **パブリックプレビュー** と述べられています。
- ティアの構成（モデルの組み合わせ）は、新しいモデルが出るたびに、おおむね 1〜2 週間ごとに調整されます。
- 「apply suggestion」ボタンを押す人は約 2% です。多くの人は、エージェントに修正を頼むか、ローカルで直して検証してから push するため、auto fix を適用しなくても、指摘が対処されることはあります（address rate は約 77%）。
- ブランチ単位での自動承認は、まだできません。
- verdict の「Needs a closer look」は、問題を見つけていなくても、PR が複雑またはリスクが高いために人間に委ねる場合があります。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **対処される指摘**: Copilot code review が付けた問題の約 77% が、マージ前に対処されています。
- **リスクに応じたコスト調整**: light（約 25 セント）から max（約 10 ドル）まで選べ、max は balanced の約 2 倍の high severity の問題を見つけます。adaptive は PR ごとに強度を選びます。
- **チーム固有の知識の反映**: instructions、agent skills、MCP サーバー、Dreaming、クロスリポジトリのコンテキストで、チームのやり方や外部のコンテキストを取り込めます。
- **運用の可視化**: Insights タブで address rate、Copilot なしでマージされた PR、カテゴリー別、カスタマイズ別の効果が分かります。
- **承認の自動化の選択肢**: 本物の承認を auto merge と組み合わせれば、CI と Copilot の承認がそろった時点で自動マージできます。2 承認ルールの 1 つとして使う運用も可能です。

## 9. まとめ

PR の量が急増し、レビューがボトルネックになっているという前提のもと、Copilot code review は、差分だけを見る方式から、リポジトリを探索し、Issue、skills、過去のレビュー、他のリポジトリ、外部サービスの情報を取り込むエージェント型に進化しました。内部は、複数のエージェントのアンサンブルと集約エージェントで構成され、light、balanced、max と新しい adaptive から強度を選べます。品質は ReviewBench（200 件以上の PR）の precision と recall、ライブでの address rate（約 77%）で測られ、結果は Insights タブで確認できます。最終的に Copilot は verdict を出し、設定すれば本物の承認として機能しますが、既定はオフで、リスクの低い範囲から段階的に広げることが推奨されています。
