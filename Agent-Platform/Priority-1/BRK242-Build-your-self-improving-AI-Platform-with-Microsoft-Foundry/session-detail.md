# BRK242 Build your self-improving AI Platform with Microsoft Foundry

## 1. はじめに

このセッションは、AI アプリケーションを「作って終わり」にせず、**本番運用の中で継続的に良くしていく仕組み**を Microsoft Foundry の上でどう組み立てるかを説明するものです。登壇者は Foundry チームのプロダクトマネージャー 2 名で、旅費申請アプリ（出張の申請と承認を扱うアプリ）を題材に、デモを交えながら進めます。

### 5.4 Base 10 のゲストセッション

ゲストとして、Base 10 の共同創業者が登壇しました（聞き取れた氏名は「Amir Haggad」。綴りは確定できません）。話の要点は次のとおりです。

- Base 10 は創業 7 年で、推論に特化している。顧客には Datadog、Canva、Coinbase などがあり、オープンモデルを動かしている。
- 推論をうまく行うには 2 つの柱がある。
  1. **ランタイム層**：単一 GPU 上でモデルのウェイトを動かすとき、ハードウェアを最大限に使えるか。遅延、スループット、コストのどれを優先する場合にも最適化できるか。独自のランタイム、カスタムカーネル（以前は手書き、現在は agentic な生成と検証）、speculative decoding、コンテキストを広げるための KV compaction などを挙げた。
  2. **インフラ層**：トラフィックが増えたときに水平スケールさせる分散システムの問題。スケールアップを速くしてテールレイテンシを抑え、SLA、稼働率、セキュリティを保証する。
- Foundry に持ち込む意義として、オープンモデルの推論や新モデルの day zero サポートを、コンプライアンス対応、アクセス制御、ガバナンス、ZDR がすでに整っている場所で使え、支払いも Azure の課金に一本化できる点を挙げた。
- 今後はオープンモデルとクローズドモデルの組み合わせになるとの見方。企業はクローズドモデルから始め、コストやレイテンシ、あるいは自社データで post-train して知能を自社で持ちたいという理由でオープンモデルを組み込んでいく。そのときに評価（evals）が、どのモデルを選ぶかの判断に重要になる。
- 提供状況はパブリック・プレビューで、数か月後に GA の予定。

### 5.6 改善する：システムを観測する

後半の「改善」では、まず Naomi が、同じテスト質問に対して同じ rubric で 3 ラウンドずつ採点し、**一度に一つだけ変更する**進め方を説明しました。ベースラインは次のとおりです。

| 項目 | ベースライン |
| --- | --- |
| モデル | フロンティアモデル（Sol） |
| 正答率（テスト質問のうち） | 約 71% |
| コスト | 1 リクエストあたり約 2.5 セント。月 5 万リクエストで年間約 1 万 4,000 ドルと説明 |

「動く」ことは目標ではなく、どれだけうまく動くか、失敗したときにどう分かるか、他を壊さずにどう直すかが問題だ、というのが Naomi の問題設定です。デモでは動いていたエージェントも、本番に出るとブラックボックスになります。そこで観測性が必要になります。品質、安全性、ドリフト、コストの増加を捉え、「日単位ではなく分単位で直す」ことを目指す、と説明しています。

**3 つの制御面**として、モデルを固定したままでも次の 3 つを調整できます。

1. 指示（instructions）：プロンプトの最適化、構造化出力、タスク分解
2. コンテキストとツール：キャッシュ、メモリなど
3. モデル戦略

これらで、再学習なしに成功率を上げ、無駄やレイテンシを減らし、品質を高められる、とのことです。

Steve はここで、大規模な本番アプリケーションなのにトレース戦略を持たない顧客を見て心が痛む、と述べました。理由は 2 つで、最適化できないこと、そしてエージェントの判断がトレースに残る以上それは企業が持つ IQ であり、活用方針がなければ捨てているのと同じだからです。evals が最初の重要なプリミティブで、トレースはそれに続く 2 つ目の重要な要素だという位置づけです。組織内のすべてのエージェントが、最適化の対象になる一つの中心的なシステムに判断を流し込む明確な観測戦略を持つべきだ、と述べています。

### 5.7 Agent Optimizer と model router

Agent Optimizer は、トレースと evals をもとに変更案を提示し、その検証をゲートとして挟めるものとして紹介されました（デモは 6.3）。Naomi によれば、結果は **pass rate が 71% から 79% へ、8 ポイント向上**しました。ただし品質ゲートに必要な水準にはあと少し足りなかった、とも述べています。Agent Optimizer の専用ディープダイブが「たしか明日」あるとのことです。

次に **model router** です。1 つのモデルに全部を任せず、アプリ全体として判断する考え方で、説明は次のとおりです。

- リクエストの複雑さは大きくばらつく。
- model router は、システムメッセージ、ユーザーメッセージ、ツール定義、履歴を含めて各プロンプトを見て振り分ける。
- コスト優先、品質優先、またはその中間を選べる。スループットも見られる。
- 単純なリクエストは小さいモデルへ、複雑なものは大きいモデルへ送る。
- 現時点では chat と reasoning のモデルでよく機能する。画像、動画、decision model への対応は今後の課題。

デモの結果（6.3 参照）は次のとおりでした。

- model router を入れた版では、呼び出しの 62% が Sol、36% が 6.1 Terra（聞こえた綴り）に振り分けられた。品質は 79% のまま維持され、コストが少し下がった。これが本番に出たバージョンである。
- さらに optimizer に、より安いモデルを探させた。held-out（検証用）のテストを使い、練習用のスコアだけで決めないようにした。練習用スコアで最も良く見えたのは「5-4 mini」（聞こえた綴り）だったが、「5-6 Luna」（同）がベースラインと同じ品質に並んだ。
- 財務部門には選択肢を示す。**Option A（稼働中のバージョン）は、回答がより良く、コストは 19% 下がる。Option B（Luna）は、品質はベースラインと同じで、さらに安い。** 品質が足りない選択肢は採用しなかった。
- 最適化したプロンプトだけを使うと、Cal のコストは 30% 高くなった。そうしたトレードオフを「サプライズではなくメニュー」として財務に見せられる。

Steve は、ここまでのモデルとハーネスの最適化だけで、この事例では**60% を超えるコスト削減の可能性**があった、とまとめています。

### 5.8 トレーニング（ポストトレーニング）

次に、システム側の最適化で足りない場合の選択肢です。Steve は、これは出発点ではなく、次のステップとしてあり得るものだと位置づけました。Naomi は、トレーニングに投資すべきかの判断を次の 3 条件で説明しています。

1. ギャップが持続的か（プロンプト、コンテキスト、ツールでは既に解決できていないか）
2. ギャップが測定可能か（評価指標で、システムがどこで失敗するかを把握できるか）
3. 教えるべき「振る舞いのパターン」があるか

3 つすべてが当てはまるなら、モデルのチューニングを検討します。当日発表されたトレーニングの選択肢は次のとおりです。

| 選択肢 | 説明 |
| --- | --- |
| managed training | 複雑さが低い。自分のデータを持ち込み、トレーニングは Foundry が行う |
| programmed training | 当日プレビューに入った新機能。学習ループは自分で書き、GPU の運用は Foundry が担う |
| custom training | 複雑さが高い。アルゴリズムやインフラを含め自分のスタックを持ち込める。AKS を Foundry に接続して使うと説明された |

programmed training の API と、AKS を Foundry に接続する custom training については、翌日にディープダイブ・セッションがあるとのことです。

最後に、システム全体を 1 枚にまとめた図が紹介されました。要点は次のとおりです。

- エージェントは Foundry でホストしても、他の場所で作ったものを持ち込んでもよい。
- 可観測性で、すべてのトレースを最新に保つ。
- そのトレースを学習データとして使い、本番システムが次のシステムを良くする。
- それでも足りなければ、program training でウェイトや RL 環境を調整する。
- graders と rubrics で、候補ごとに検査し、より良くなったものだけを出荷する。
- 図の中心には MAI のモデルを置いたが、使うモデルは差し替えられる。

### 5.9 スケールさせる：デプロイ形態（shape）

ここから Steve に交代します。「すべてのタスクに合う 1 つのモデルがないように、すべてのワークロードに合う 1 つの形もない」というのが前提です。コスト、応答性、予測可能な容量のバランスを取るため、Foundry には「6 つの shape がある」と説明しました。聞き取れた範囲で順に説明されたのは、次の 5 つです。

| 形態 | 説明（発表での言い方） |
| --- | --- |
| standard | 基本の従量課金（pay per token）。開発時に多くの人が使う。「公共交通機関に乗るようなもの」。 |
| priority | レイテンシの保証がある。standard より高いが、リクエスト単位の課金。「Lyft や Uber を呼ぶようなもの」。 |
| flex | 後で実行されてよいタスク向け（ポリシーチェック、システム更新、evals など）。リアルタイム API 呼び出しだが、約 10 分のタイムアウトがあり、大幅に安い。 |
| batch | スケジュール済みのジョブ向け（大量ドキュメントのインデックス作成など）。最大 24 時間キューに入れられ、余剰容量のある夜間に完了する。こちらも安い。 |
| provisioned | 専用の容量。「自分の交通手段を持つ」イメージ。いつでも使えると分かっている。 |

多くの顧客は複数を使い分けており、「すべてを provisioned に」「すべてを standard に」ではなく、**ワークロードに形を合わせる**のが大事だと述べています。

> 補足：発表者は「6 つ」と言っていますが、トランスクリプトで説明が確認できたのは上の 5 つです。6 つ目は特定できませんでした。managed compute の GA は、この説明のあとに別の発表として紹介されています。

### 5.10 managed compute の GA

当日、**managed compute が一般提供（GA）**になると発表されました。

- カタログにある約 11,000 のオープンウェイト・モデルのどれでも、提供方法を制御できるコンピュートにデプロイできる。
- GA に合わせて、US と EU の data zone、Hugging Face のカタログ、NVIDIA、AMD などのパートナーのモデルが加わる。
- bring your own weights に対応。他のプラットフォームで学習・チューニングしたウェイトを、対応する SGLang または vLLM のコンテナーにアップロードして、Foundry で推論できる。
- ウェイト更新時の LoRA にも対応する。

### 5.11 データの保存と処理

サービス形態を決めたら、次はデータの約束（data promises）、つまりどこに保存し、どこで処理するかです。

- **保存**：既定では、リソースの地理に保存される。US のリソースなら US、EU なら EU、カナダのような単一の国のリソースならカナダに保存される。
- **処理**（processing zone）を選べる。

| 処理ゾーン | 説明 |
| --- | --- |
| Global | 最も安く、使える容量が最も多い。データは世界各地のどこかで処理される。 |
| Data zone | 3 つある。US（US 内にとどまる）、EU（EU データバウンダリ内）、APAC（レイテンシ面で有利で、その地理的範囲内にとどまる）。 |
| リージョン | 世界 32 のリージョンで、そのリージョン内で処理される。最も高く、モデルの選択肢も最も限られるが、現地のデータレジデンシーが必要な、重要かつ規制の厳しいユースケース向け。 |

### 5.12 Foundry quota

Steve は、quota の申請を「世界で最も苦痛な体験の一つ」と述べ、新しい **Foundry quota** 機能を紹介しました。

- 外部のフォームではなく、プラットフォームに統合されている。
- どのサブスクリプションで、どのリージョンで、どのオファータイプかを把握している。
- 現在は平均 7 日かかっている承認を、**1 分未満（sub-minutes）**に短縮することを目指している。

### 5.13 trusted access とセキュリティ

1. **trusted access program**：サイバー向けの新しいモデルで、環境内のコードをスキャンできる。ヘルスケア向けの「GPT Roslyn」（聞こえた綴り）や、MAI の新しいプログラムにもアクセスできると述べている。

## 7. 注意点・発表者の気付き

- **スペックを最初に書く。** 「持ち帰るのは一つだけでよい」とまで述べられた点です。成功基準がないと、後の変更を測れません。
- **モデルを疑う前にシステムを疑う。** 目標に届かないとき、多くはモデルが原因ではない、という考えです。
- **ファインチューニングは出発点ではない。** 効果の多くは、チューニングしないシステム側の最適化から得られる、と説明されています。
- **最適化の結果は人がレビューする。** Agent Optimizer が書き換えた結果を人がレビューし、不適切な箇所を取り除いたと説明されています（具体的な内容は聞き取りが不明瞭です）。
- **model router は現時点で chat と reasoning が対象。** 画像、動画、decision model は今後の課題です。
- **最適化したプロンプトはコストが上がり得る。** 今回の例では 30% 高くなりました。品質とコストを並べて比べる必要があります。
- **リージョン単位の処理は最も高価で、モデルの選択肢が最も限られる。**
- 登壇者の PC がスリープして、デモの再開に時間がかかる場面がありました。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。いずれも旅費アプリのデモや、登壇者の見解に基づくもので、他の環境での保証ではありません。

- 評価の作成：スペックから rubric evaluator を作り、一つの数字で変更を追跡できる。
- decision model：LLM でポリシー判断をしたときの約 10 秒に対し、約 1.2〜1.3 秒。
- 品質：Agent Optimizer の導入で pass rate が 71% から 79%。
- コスト：model router を含む構成で 19% 低下（Option A）。モデルとハーネスの最適化だけで、デモの事例では最大 60% 超の削減の可能性。
- Base 10 on Foundry：コンプライアンス、アクセス制御、ガバナンス、ZDR、Azure の課金が既存の場所で使える。
- quota：平均 7 日から、1 分未満を目指す。
- 選択肢の幅：standard、priority、flex、batch、provisioned などのデプロイ形態と、US・EU・APAC の data zone、32 リージョンでの処理。

## 9. まとめ

Steve と Naomi は、自己改善するシステムを次の流れで作ると説明しました。まず、成果をスペックと rubric の評価基準に落とし込み、評価を最初の土台にします。次に、タスクに合うモデルをカタログから選び、トレースと evals を使ってシステム（指示、コンテキストとツール、モデル戦略）を改善します。Agent Optimizer と model router で品質を上げながらコストを下げ、それでも足りなければトレーニングを検討します。最後に、デプロイ形態、データの保存と処理の場所、quota、セキュリティを整えてスケールさせます。
