# BRK271 Manage GitHub Copilot spending and understand team adoption

## 1. はじめに

このセッションは、GitHub Copilot の導入を組織に広げる IT 管理者やエンジニアリングリーダーに向けて、「AI にいくら使っているのか」「そのコストを管理しながら、どうやって成果を測り、展開を広げるのか」を整理した内容です。

発表は大きく 2 部構成です。前半では GitHub Copilot の FinOps の考え方を、**見る（Inform）→ 統制する（Govern）→ 成果を測る（Measure）** という流れで説明します。後半では、複数のモデルを自動で使い分ける Copilot Fusion のライブデモと、GitHub が提唱する agentic engineering system（エージェント活用のための開発体制）を紹介します。

前半の結論は「**FinOps は AI の利用を制限するためのものではなく、自信を持って AI を拡大するためのもの**」という点です。

## 3. 何に関する発表か

AI の利用が一部のコホートでの試行から、組織全体での本番規模の利用へ移るにつれ、コストが読みにくくなります。発表ではこの状況に対して、組織が答えるべき 3 つの問いを示しています。

1. AI は、企業が求める価値を生み出しているか。
2. エージェントがより多くの仕事を担い、コストが予測しにくくなる中で、チームの速度を落とさずにコストを管理できるか。
3. 1 つのチームでうまくいったことを、組織全体に展開しても同じ成果が得られるか。

3 つの問いはつながっており、コスト管理と価値の測定がなければスケールできません。そこで GitHub Copilot が提供する FinOps ツールを、利用状況を見て、ルールを決め、成果を測るための「コントロールプレーン」として紹介しています。

発表の流れは次のとおりです。

- Inform: 利用状況の可視化（API、ダッシュボード、データエクスポート）
- Govern: 予算の統制、権限委任、モデルの統制
- Measure: Impact ダッシュボードによる成果の測定
- Copilot Fusion のデモ（モデルの自動選択、モデル設定、予算設定）
- agentic engineering system と各種リソースの紹介

発表の中には、「いま使える機能」と「近日提供予定の機能」、さらに「プロトタイプ段階でフィードバックを募っている機能」が混在しています。後述の各節では、この区別が分かるように書きます。

## 4. 発表者が伝えたいメッセージ

前半のメッセージは、先に挙げた「FinOps は AI 利用を制限することではなく、自信を持ってスケールさせること」です。CFO との会話も「AI にいくら使ったか」だけでなく、「いくら使い、それが組織に何をもたらしたか」に変えていくべきだという考えです。

後半では、次の点が強調されています。

- ゴールは顧客価値の提供であり、token maxing（トークンを使い切ること）ではない。
- モデルの得意・不得意を知る専門家は少数でよい。その専門家がガードレールを設定し、Copilot Fusion を使うことで、一般の開発者はモデル選択を意識しなくてよくなる。
- 測るべきなのは PR 数やコード行数といった出力ではなく、ユーザー数の増加や定着、機能要望やバグ報告への対応速度といった成果である。
- エージェントが大量のコードを生成する時代だからこそ、ビルド、自動テスト、lint、セキュリティチェック、コードレビューのプロセスが整っていないと、下流に巨大なバックログができてしまう。発表では「DevOps はこれまで以上に重要」と述べています。

最後まで立っていた人は何人かいました（発表者は「winners」と呼んでいます）。そのうえで、請求や AI 利用に安心感を持つには何が必要か、というのが Pallavi 氏の担当領域です。

### 5.2 Inform: 利用状況を見る

「見えないものは管理できない」という前提から、GitHub Copilot では AI クレジットがどう使われているかを次のように確認できると説明しています。

- IDE、CLI、各種クライアントやエージェントにわたって、誰がアクティブかを見られる。
- ユーザー別、モデル別、モデルごとのトークン数で内訳を見られる。
- コストセンター別、チーム別にグルーピングできる。
- 近日中に、クライアント別の利用状況も見られるようになる。コストが増減したとき、チーム、個人、特定のエージェントのどれが要因かを特定するためです。
- 利用状況は、広げるべき成功パターンを見つけるためにも使える。よく使われているスキル、カスタムエージェント、MCP サーバーを確認し、AI チャンピオンの取り組みを他へ展開できる。

#### Copilot usage metrics API

スライドでは、usage metrics API の 1 レコードの例が示されました。**1 ユーザー × 1 日で、全部で 41 フィールド**あります。ユーザー単位・組織単位で、1 日分または直近 28 日のローリングで取得できます。この API は、コストセンターごとのチャージバックや導入状況の追跡を作る際の出発点になると説明しています。

#### ダッシュボードとデータエクスポート

- UI のダッシュボードで、モデル別の内訳を見られる。今後、上位ユーザーやコストセンター単位の予算使用状況といった情報を追加する計画がある。
- **データエクスポート（data warehouse connectors）** は private preview 中。AI の利用状況とメトリクスを Azure や AWS のストレージアカウントへ直接出力できる。参加を希望する場合は、アカウントチームか Pallavi 氏に連絡する。
- セッション単位のデータも、この private preview に近日追加される。時期は未定。生データを使って自社で分析したい場合の出発点になる。

これから始める場合は、API かダッシュボードがスタート地点になると説明しています。

### 5.3 Govern（1）: 予算による統制

可視化の次は、利用をどう統制するかです。統制には「予算（コスト）の統制」と「モデルの統制」の 2 種類があると説明しています。

#### 予算の設定

- 予算は、enterprise、organization、cost center、さらに個々のユーザーのレベルで設定できる。
- AI クレジットを組織内でプールし、コストセンターに割り当てたり、支出上限を設けたりできる。
- ユーザー単位だけでなく、code quality や自動セキュリティスキャンの製品、エージェントに対する予算も設定できる。
- しきい値の 75%、90%、100% に達したときに通知を受け取れる。しきい値に達したときの動作として、使い続ける、ハードストップする、より安価なモデルにフォールバックする、のいずれかを選べる。

#### 近日提供予定の 2 機能

1. **予算の増額リクエストと承認**: 例えば 100 ドルや 500 ドルの予算を月の半ばで使い切った開発者が、アプリ内で増額をリクエストし、適切な承認者が承認または却下する。
2. **予算に応じたモデルのフォールバック**: 予算が少なくなったとき、利用を止めるのではなく、よりコスト効率のよいモデルや Fusion へ自動で切り替える。

#### 中央管理から権限委任へ

大規模な組織では、開発者が増えるほど中央の管理者が判断のボトルネックになります。そこで GitHub は、委任を 3 段階で考えていると説明しています。

| 段階 | 内容 | 状況 |
| --- | --- | --- |
| 1 | 予算管理: 事業部門のリーダーが自分のチーム内の個人の予算を割り当て・管理する | プロトタイプ動画を紹介（5.4） |
| 2 | モデル管理: リーダーが自分の組織内でモデルを管理する。ただし企業全体のガードレールの範囲内 | 説明のみ |
| 3 | エージェント管理: 開発者が「エージェントのエージェントのエージェント」を管理する際に、予算の範囲内で事前に統制できるようにする | 検討中でフィードバックを募集 |

2 段階目の例として、中央の管理者が特定のモデルを企業全体でブロックした場合（発表では Astra という名前を挙げています。音声認識の都合で表記が確定できません）、事業部門のリーダーはそのモデルを使えるようにはできません。許可されている残りのモデルの中から、自分のチームに合うものを選びます。3 段階目については、気づかないうちにエージェントが暴走して被害が出る前に、開発者が利用を制御できるようにしたいという狙いが語られています。

3 段階を通じた原則は、「中央の管理者がガードレールを設定し、委任された人はその範囲内で運用する」という点です。

Dave 氏は、GitHub Universe（数週間前）で大企業の顧客と話した際、チームレベルでの予算管理が明確に求められていたと補足しています。巨大な組織では、enterprise 全体の管理者にはチームごとのニーズが分からないという課題があるためです。

### 5.4 プロトタイプ動画: コストセンター単位の権限委任

Pallavi 氏は、委任の考え方を説明する短いプロトタイプ動画を上映しました。ライブ操作ではなく、ナレーション付きの動画です。動画の内容は次のとおりです。

1. 現在、請求を扱える権限は enterprise owner と billing manager の 2 つ。この 2 者は全 organization とリポジトリの利用状況とコストを見られ、予算やコストセンターの作成、ライセンスや支払い方法の管理ができる。
2. 新しい方式では、まず**カスタムロール**を作成し、1 つのコストセンターに対して割り当てる。そのコストセンターの予算を管理できるロールと、閲覧のみのロールがある。どちらも、自分のコストセンターしか見えない。
3. コストセンター管理者の画面は、メニューが短くなり、ライセンスや支払い情報は編集できない。コストセンターを開くと、自分のコストセンター（所属する enterprise team と organization を含む）だけが表示され、編集はできない（編集は引き続き管理者の仕事）。
4. 予算の作成では、新しい予算を選び、製品レベルの予算として Actions を選ぶ。予算のスコープで選べるのは自分のコストセンターのみ。金額（動画では 5,000 ドル）を設定して作成すると、新しい Actions の予算が一覧の先頭に表示される。
5. 自分のコストセンターのユーザー予算も開ける。動画では 5 人のユーザーがそれぞれ個別の予算を持っており、編集もできる。AI usage では、AI クレジットを誰が使っているかをユーザー別に見られる。
6. 閲覧のみのロールでは、「新しい予算」ボタンが表示されず、詳細表示、ユーザー予算、利用状況の分析は見られるが、何も編集できない。
7. enterprise owner の権限は何も減らず、ライセンスや支払いを含む全メニューと全コストセンターを引き続き見られる。

提供時期は、**12 月に API 版、年明け早々に UI 版**と説明されています。詳細は QR コードから確認できます。

### 5.5 Govern（2）: モデルの統制

もう一つの統制は、開発者がモデル選択に悩まなくて済むようにするためのモデル制御です。ガイダンスは次のとおりです。

- まずガードレールを設定する。
- デフォルトモデルを設定し、毎回のセッションでモデルを考えなくてよいようにする。
- グローバルポリシーで、新しいモデルをデフォルトで有効にしておく。新モデルのたびに設定する手間がなくなり、利用とコストのパターンも把握しやすくなる。
- managed settings を使えば、組織内の全ユーザーにデフォルトモデルを設定でき、セッションを開くと新しいモデルが選ばれた状態になる。

現在使えるものとして、**モデルポリシー API**（enterprise、organization、チームの各スコープで、モデルの組み合わせとデフォルトモデルを自動管理する）と、Universe で先月リリースされた **Fusion 向けのモデルミックス設定**があります。取り組み中のものとして、機能やクライアントの「デフォルトで有効」、組織・チームレベルでのクライアントのカスタマイズが挙げられました。

詳細は、同僚の Greg Paddock 氏によるモデルガバナンスの別セッション（デモ付き）の録画を見るよう案内しています。モデルポリシーのリンクがスライドに欠けており、後で追加するとのことでした。

### 5.6 Measure: 成果を測る

次は、「このコストに見合う価値があるのか」という、リーダーが問われる質問に答えるパートです。スライドに載っている内容は、すべて現在利用可能と説明しています。GitHub Copilot の Impact ダッシュボードでできることは次のとおりです。

- PR のスループットとマージ数でチームを比較し、AI を多く使うチームと少ないチームで生産性がどう違うかを見る。
- 進捗のボトルネックを見つけ、先回りして改善する。
- 開発者 1 人あたりのコストを、PR の出力と対比して見る。
- 組織内の成熟度を追跡する。ユーザーをチャットだけの利用者、エージェント利用者、自動ワークフローやエージェントのエージェントを使うヘビーユーザーといったコホートに分け、どこに投資すべきか、どこが成果につながっているかを比較できる。
- 業界別の匿名化されたピア比較にオプトインし、同業他社に比べた利用状況を確認する。

#### Copilot Impact ダッシュボードの動画

こちらもナレーション付きの動画で上映されました。内容を整理します。

- アクティブユーザー数だけでは、たまにコード補完を使う人と、一日中エージェントを使う人が同じ扱いになってしまう。Impact ダッシュボードは、利用の仕方でユーザーを導入フェーズ（コホート）に分類する。

| フェーズ | 名称 | 条件 |
| --- | --- | --- |
| Phase 1 | code first | IDE でのコード補完またはエージェントによる編集 |
| Phase 2 | agent first | GitHub のエージェントの利用面（Copilot Cloud Agent、Code Review、CLI など）を 1 つ使う |
| Phase 3 | multi-agent | エージェントの利用面を 2 つ以上、または Copilot app を使う |

- フェーズに入るには、28 日のうち少なくとも 2 日のアクティブ日が必要。それ以外のユーザーは passive users として数える。
- 各コホートのカードには、ユーザー 1 人あたりの月間平均マージ PR 数、マージ速度の中央値、そのフェーズのユーザー数と全体に占める割合、1 日あたりの平均コード行数が表示される。
- 動画内の例では、Phase 1〜3 の engaged users は 1 人あたり月 20 PR、passive users は 10 PR で、導入倍率（adoption multiplier）は 20 ÷ 10 = **2 倍**。より深い利用に移行した場合の効果の目安になる。
- ライセンスはあるが活用していないユーザーを見つけ、推奨される次のステップに従って、より深いコホートへの移行を促せる。トレンドチャートでは、コホートの増加を 6 か月間追跡できる。
- 開くには、enterprise の **Insights** タブから **Copilot Impact** を選ぶ。**Copilot usage metrics policy を有効にしておく**必要がある。

Pallavi 氏は、これ以外にセッションデータを分析して、どのモデルがどのタスクに向いているかの知見や、開発者を適切なモデルへ導く仕組みも検討していると述べています（今後数か月で追加予定）。

### 5.8 Copilot Fusion

ここから Dave 氏の担当です。まず聴衆に Copilot Fusion を知っているか尋ねたところ、一定数が挙手しました。冒頭のエクササイズでモデル選択を把握している人が少なかったことを受け、「モデルを把握するのは新しいスキル」と話しています。

**Copilot Fusion** は、複数の AI モデルの強みを組み合わせて複雑な開発タスクに取り組む機能で、開発者がオーケストレーションを管理する必要はありません。モデルの強み・弱みを知る少数の専門家が、企業内で使えるモデル、特に Fusion で使えるモデルのガードレールを設定し、使う側の負担をなくします。

スライドの例では、PR の作成を依頼したとき、メインのパスで GPT Sol、レビューのパスで GPT Luna、批評（最終修正）のパスで Opus が使われました。開発者は、どのモデルをいつ使うか、タスクをどう分解するかを知る必要がありません。モデル名は音声認識の都合で表記が確定できません。

Dave 氏は、Opus は非常に強力だが高価なモデルだと説明し、顧客から聞いた「道路の向かいに行くのにヘリコプターは要らない」という言葉を紹介しています。用途に合った乗り物（モデル）を使うことを、Copilot Fusion が代わりに行います。

#### ベンチマーク

- Satya 氏がキーノートでも触れた Terminal Bench 4.1（音声のまま。表記は確定できません）で、**Copilot Fusion Max は resolution rate 71.2** を達成し、Opus や Fable（音声認識の都合で表記が確定できません）といった最先端モデルを上回った。コストは Fable より 88% 安く、Opus 5.5 より 57% 安い。火曜日の GitHub の changelog に掲載されている。
- benchmarks.github.com では、品質・有効性とコストの関係を確認できる。Dave 氏が示した例では、ある SWE 系ベンチマーク（音声では "deep SWE one"。表記は確定できません）で、Opus Max は 74.5% の有効性でコストが 11.83 ドル、Copilot Fusion は 80% で 4.91 ドル。Copilot Fusion High はそれに近い有効性で、コストは 91 セントだった。
- Terminal Bench 4.1 は独立したベンチマークであり、GitHub が公開しているデータは、いろいろなモデルを選んで絞り込めると説明しています。

### 5.9 agentic engineering system

8 月に公開したホワイトペーパーの内容は、GitHub well-architected framework にも組み込まれています。ここでは、エージェント活用のための開発体制を次のように説明しています。

- 目標は顧客価値の提供。上位チームには高度で高コストなモデルを使わせ、一般の開発者には範囲を絞り、予算を設定するなど、ガバナンスを整える。
- SharePoint、Azure DevOps の Wiki、あちこちにある Word 文書、さらには開発者の頭の中にしかない共有知識を、**カスタムエージェント、スキル、Copilot instructions** に落とし込む。これらは、Copilot に計画や定義を依頼するとき、実装を依頼するとき、Copilot code review を使うときに反映され、自社の標準やベストプラクティスに沿った成果が得られる。
- 図の点線の矢印で示されるように、フィードバックと学びを取り込み、継続的に改善する。

多くの組織は AI エージェントをどう展開するかに注力していますが、本当の課題は、エージェントの生産性を安全に顧客価値へ変える**開発体制**を作ることだと述べています。測りたいのは出力（PR 数、コード行数）ではなく、成果です。新しい Web サイトならユーザーが増えているか、定着しているか、機能要望やバグ報告にどれだけ速く対応できているか、といった点です。

GitHub の engineering system は、「どの仕事をエージェントに任せるか」「人間の監督が最も重要な箇所はどこか」「ガバナンス、共有知識、フィードバックループが、エージェント導入を本当のビジネス成果につなげるのか、技術的負債を加速させるだけなのかを左右する」ことを考えるための実践的なモデルだと説明されています。

## 6. デモ・手順

このセッションには、プロトタイプ動画（5.4、5.6 で紹介済み）に加え、Dave 氏のライブデモがあります。Dave 氏は「動画ではなく、ライブでやる」と話しています。画面上の細かい操作は音声からは確認できないため、語られた範囲で、語られた順に整理します。

### 6.1 GitHub Copilot app で Copilot Fusion を使う

1. GitHub Copilot app を開く。非技術系のプロダクトマネージャーでも、VS Code で JSON ファイルを管理することなく、アプリ内で MCP サーバーやプラグインを簡単に設定できる、と説明している。
2. 現在のモデルは Astra と表示されている（音声認識の都合で表記が確定できません）。モデル選択を開くと全モデルが使える状態になっている。この環境は、この enterprise・organization では事実上どのモデルも使える設定になっている。
3. スイッチを切り替えて **Fusion** にすると、effort レベルとして standard、high、max のどれにするかを選ぶ。これは推論をどこまで深くするか、そのタスクにどれだけトークンを使ってよいかという許容度に相当する。
4. Azure DevOps を使い、「このチームプロジェクトで state が active のユーザーストーリーはあるか」と尋ねる。いくつかのユーザーストーリーが見つかる。この時点で Fusion が GPT-6 Luna を選んでいる。
5. Azure DevOps の AI として Copilot が連携されている。Copilot のスキルとして取り込んだベストプラクティスやガイドラインに、このユーザーストーリーが沿っているかを尋ねる。回答は「沿っていない。definition of done がなく、タイトルも改善が必要」といった内容。
6. ユーザーストーリーを更新し、必要な内容がそろったところで「このユーザーストーリーを実装して」と依頼する。実装フェーズでも Luna が選ばれる。
7. PR を作成する段階では、マルチステージ（カスケード）のアプローチが取られる。メインのパスで GPT-6 Sol（音声では "GPT-6 one soul" に聞こえます。表記は確定できません）、レビューのパスで Luna、修正のパスで Opus が選ばれる。
8. AI の利用状況も確認できる。セッションで使ったクレジット数や、フェーズごとの内訳を見られる。
9. Copilot app には **Chronicle** がある。Chronicle と入力すると選択肢が表示される。語られた内容は次の 3 つ: 利用パターンに基づく個別のヒントを得る（Copilot をより効率よく使う方法）、Copilot instructions の改善提案を得る、トークン使用量とコストを減らすための個別のコストヒントを得る。

### 6.2 enterprise の AI controls とモデル設定

1. enterprise レベルの GitHub の **AI controls** から Copilot を開き、利用可能なモデルを設定できる。
2. 以前は有効か無効かだけだったが、チームに委任できる選択肢が加わった（チームへの委任は今後提供される部分もあるとも話しています）。例として、一般の開発者向けのモデルセットと、「AI pioneers」チーム向けの別のモデルセットを設定できる。enterprise teams のチームレベルで、利用可能なモデルを決める。
3. enterprise 全体で許可するモデルのうち、どれを **Copilot Fusion** に使わせるかも、AI controls から別途設定できる。

### 6.3 予算（Billing and licensing）

1. Billing and licensing タブの budgets から、新しい予算を作成する。ここでは enterprise credit budget を選ぶ。
2. 設定できるレベルは enterprise、organization、**cost center**。研究、財務、開発など、コストセンターごとに分けて考えられる。デモ環境にはコストセンターが非常に多数あり、その中の 1 つ（business systems、coworkers、DevOps チームに関するもの）を選んでいる。
3. そのコストセンター単体の AI クレジット予算を設定する。ハードな上限にするか目安にとどめるか、予算に近づいたときに特定のメンバーへアラートを送るかも設定できる。
4. エンドユーザーが「予算を増やしてほしい」と依頼できる機能は近日提供予定。

## 7. 注意点・発表者の気付き

- 発表では、近日提供予定のものとして、予算の増額リクエストと承認、予算に応じたモデルのフォールバック、クライアント別の利用状況、データエクスポートへのセッション単位データの追加が挙がっています。提供日が示されたのはコストセンター単位の委任（12 月に API、年明けに UI）のみで、セッション単位データは「日付はまだない」と述べています。
- データエクスポートは private preview で、利用するには申し込みが必要です。
- 権限委任の 2〜3 段階目（リーダーによるモデル管理、開発者によるエージェント管理）は検討中の段階で、フィードバックが求められています。
- Impact ダッシュボードを使うには、Copilot usage metrics policy を有効にしておく必要があります。
- モデルの統制でも、Fusion を使えば誰もがモデルの専門家になる必要はない一方、用途によってモデルの強みと弱みは異なるため、専門家がモデルの設定を担う必要があると説明されています。
- エージェントが大量のコードを生成するほど、ビルド、自動テスト、lint、セキュリティチェック、コードレビューの仕組みがないと、下流でバックログが膨らみます。
- 複数のモデルやベンチマークの名称は、音声認識の都合で確定できないものがあります（5.8、6.1 を参照）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **コストの見通しと原因特定**: ユーザー別・モデル別・コストセンター別に利用状況を見られ、コストの増減の要因を特定できる。
- **予算の柔軟な運用**: しきい値通知に加え、継続、ハードストップ、安価なモデルへのフォールバックを選べる。権限委任により、中央管理者がボトルネックにならない。
- **成果の説明**: Impact ダッシュボードで、コホート別の PR 出力を比較できる。動画の例では、engaged users の月 20 PR に対して passive users は 10 PR で、導入倍率は 2 倍。CFO への説明を「いくら使ったか」から「何が得られたか」に変えられる。
- **モデル選択の負担軽減**: Copilot Fusion により、開発者はモデルを意識せずにタスクを進められる。ベンチマークの例では、Fusion Max は Terminal Bench 4.1 で 71.2 の resolution rate を達成し、Fable より 88%、Opus 5.5 より 57% 低いコストと説明されている。
- **ライセンスの簡素化**: GitHub Copilot が GitHub Enterprise ライセンスの一部となり、利用量は AI クレジットで決まる。

## 9. まとめ

このセッションは、Copilot の費用管理を「見る、統制する、成果を測る」の 3 ステップで整理したものです。利用状況は API とダッシュボード、private preview のデータエクスポートで見られます。統制は、enterprise からユーザーまでの予算、しきい値通知、モデルポリシーで行います。成果は Copilot Impact ダッシュボードのコホートと PR 出力で測ります。さらに、コストセンター単位の権限委任や予算の増額リクエストなどが近日提供される予定です。

後半では、Copilot Fusion が複数のモデルを自動で使い分ける様子をライブデモで見せ、モデルの専門家がガードレールを設定すれば、一般の開発者はモデル選択を意識せずに済むと説明しました。測るべきは出力量ではなく顧客価値という成果であり、そのためにはエージェント活用を支える開発体制（共有知識の取り込み、ガバナンス、フィードバックループ、DevOps の基盤）が必要だというのが、発表全体の結論です。
