# BRKSP597 Turn a capable open model into a domain expert in your business

## 1. はじめに

このセッションは、オープンモデルを自社の業務の専門家（ドメインエキスパート）に育てる方法を、Microsoft、NVIDIA、EY の 3 社が共同で説明するものです。中心になるのは、今週 public preview として発表された Microsoft Foundry の新しい学習サービス **Programmed Training**（セッション概要の表記です。トランスクリプト上は "program training" と書き起こされています）です。EY が NVIDIA の Nemotron 3 Ultra を、支出分類（spend classification）のためにこのサービスで追加学習（post-training）した事例が、具体的な数字とともに紹介されます。

結論を先に言うと、EY の事例では、ベースの Nemotron 3 Ultra で 55.8% だった精度が約 86.6% まで上がり、フロンティアモデルの 71% も上回りました。1,000 件の分類あたりのコストは約 $3 で、従来型の学習手段の $45 と比べて低く抑えられた、と語られています。

このセッションでは、画面を使ったデモは行われていません。スライドを使った口頭説明が中心です。

## 5. 発表内容の詳細

### 5.1 EY の課題: 支出分類（Jon 氏）

Jon 氏はまず、使った分類体系から説明します。1998 年に国連（United Nations）と Dun & Bradstreet が作った分類体系で、購入者と販売者の取引記録を支出カテゴリーに分類するものです（コードは UNSPSC と説明されています）。ここでの入力は分類で、分析そのものではありません。分類されたデータが、後段のレポーティングで価値を持つという位置づけです。

UNSPSC のコードは 8 桁で、2 桁ずつ 4 つの階層に分かれます。

| 桁 | 階層 |
| --- | --- |
| 最初の 2 桁 | segment |
| 次の 2 桁 | family |
| 次の 2 桁 | class |
| 最後の 2 桁 | commodity |

**最も重要なのは commodity を正しく当てること**です。他の全てがその分類の上に積み上がり、ビジネスが使うレポーティングの仕組みに使われるためです。

分類の対象となる支出の記録には、サプライヤー名、会計システム（GL）上の勘定、企業ごとに任意に決まるアカウント、コストセンター、事業部門などがあります。その中で最も重要なのが、**サプライヤーが何を売っているかを説明する description** で、AI に入力する最も大切な要素だと述べています。

Jon 氏が挙げる、分類が重要な理由は 3 つです。

- 可視性: 全ての支出記録を整理し、素早く合理的な判断ができる状態にする
- 税務コンプライアンス: 品目に正しい税を割り当てているか、払いすぎ・払わなさすぎがないか。参考として、米国の企業が支出記録に関連して支払った税額が 246 billion を超える、という数字が画面に出ていたと話しています（通貨単位は語られておらず、数字は音声認識の都合で確定できません）
- 意思決定: 特定のサプライヤーに使いすぎていないか、別のサプライヤーのほうが良くないか、といった判断を、企業に入ってくる大量のデータ全体で素早く行える

### 5.2 NVIDIA と Microsoft の協業（Alex 氏）

Alex 氏は、Microsoft と NVIDIA の協業は 20 年以上続いていると説明します。NVIDIA は GPU だけでなく、CPU、ネットワーク、ストレージまでのエンドツーエンドのスタックを持ち、そのスタックはライブラリや SDK に依存していて、Microsoft のエコシステムに統合されています。Microsoft 自身のサービス（Bing、Maps、SQL Server、Fabric など）と Microsoft Foundry の両方が対象です。

Foundry では、NVIDIA のオープンソースのモデル（Nemotron、Cosmos など）をホストし、ダウンロードや各種サービスを通じて利用できます。クラウドでもエッジでも使えると説明されています。

NVIDIA はオープンソースへの貢献が大きく、**650 以上のオープンモデルと 250 以上のオープンデータセット**を公開していると述べます。重みだけでなく、レシピ、データ、デプロイやカスタマイズの方法まで提供するのが特徴で、重みだけを公開して終わりではない、という違いを強調しています。

### 5.3 Nemotron の 5 つの柱

Alex 氏は、LLM だけでなく自動運転、ロボティクス向けの Groot、フィジカル AI 向けの Cosmos など多くの分野のモデルがあると前置きしたうえで、Nemotron を 5 つの柱で紹介します。

| 柱 | 説明 |
| --- | --- |
| reasoning | エージェント型ワークロードやチャットボット向け。軽量で効率的なモデルから大きなモデルまで揃う。Nemotron 3.5 Lightning、Nemotron 3.5 Bolt、Nemotron 3.5 Super VL、Nemotron 3 Ultra が挙げられた |
| vision | 画像、動画、ドキュメントの処理（ドキュメントの抽出）。マルチモーダルの Nano Omni や Super VL がある |
| information retrieval | RAG 向け。embed、re-rank、parse など、RTX マシンなど GPU があれば動く小型モデルで、リーダーボードの上位にあり、多くの RAG パイプラインで使われている |
| content safety | 発表では詳しい説明は無し |
| speech | 優れた音声モデルがある（詳細は語られていません） |

Nemotron 3 Ultra は、EY が実際に追加学習に使ったモデルです。

### 5.4 長時間動くエージェントと「モデルのシステム」

Alex 氏は、約 1 年前からエージェント型のワークロードに移ったことで状況が変わったと説明します。チャットボットとは違い、エージェントは長時間動き、計画し、ツールを呼び、結果を確認し、修正する、というループを、ときには数百回も繰り返します。トークンの経済性（tokenomics）が大きく変わるため、**モデルのシステム**が必要になるという考えです。

- フロンティアモデルが全体を統括（オーケストレーション）し、より効率的なモデルが価値の高いタスクを担当する。「全部を 1 つのスーパーモデルにやらせる必要はない」
- 多くの顧客は、統括役のマスターモデルが、より小さい専門モデル（特化したエージェント、サブドメインのエージェント）に仕事を委ねる構成を作る
- EY の事例は、サブドメインのエージェント用に、ドメインのスキルを持つモデルを作る例にあたる
- Alex 氏は、高い効率を「3 つ目の柱」として挙げています（1 つ目、2 つ目の柱が何を指すかは、音声からは明確に確認できません）。トークンの経済性が問題になるため、より速く、より少ないトークンで処理する必要がある

Nemotron は、モデルだけでなく、教師ありファインチューニング（SFT）のデータ、RL のタスクと環境、データキュレーションなど、カスタマイズ、デプロイ、量子化のためのレシピ一式が含まれるため、クローズドではない、と説明しています。Alex 氏は、EY がそれを 48 時間未満で行ったと述べています。

Nemotron 3 Ultra については、チャートで、人工知能の指標（artificial intelligence index）で賢いだけでなく、比較対象の一部のオープンソースモデルより**約 5 倍速い**ことを示しました。

さらに、より小さい Super 3.5（最近出たばかり）について、パートナーや顧客が SFT と RL でカスタマイズし、フロンティアモデルより高い性能を、かなり低いコストで得た例のスライドを見せています。そして EY の事例の予告として、**Nemotron 3 Ultra を約 31 ポイント改善し、15 倍安く**学習できたと述べています。

### 5.5 Foundry の学習: loops と「ループの所有」（Corey 氏）

Corey 氏は、Foundry が重視しているのは、学習を使いやすくし、アプリケーションに組み込みやすくすることだと述べます。会場に学習や post-training の経験を尋ねたところ、手を挙げた人は少なかったとのことです。

Corey 氏の説明する **loops** は、アプリケーションを Foundry にデプロイし、アプリから出るデータを収集、合成、拡張、加工してアプリに戻す、継続的なフィードバックの循環です。Nemotron Super や Ultra のようなオープンモデル上のアプリが、自分たちの関心のあるタスクで継続的に改善されます。

- 外側のループ（outer loop）: アプリケーションの改善サイクル
- 内側のループ（inner loop）: モデル自体を良くする学習（Corey 氏が最も関心を持つ部分）

Corey 氏は、今週複数のセッションや Satya 氏のキーノートでも出る「ループを所有する」ことの意味を、次のように説明します。

- 継続的な改善サイクル全体を自社が所有する
- 学習の観点では、モデルをどう学習させるか、重みをどう更新するか、自社の IP、業務知識、専門性をどう学習に取り込むかを、自社が制御する
- そのためには Nemotron Ultra のようなオープンモデルが必要。クローズドなフロンティアモデルは、多くのタスクでそのまま動くが、重みを操作できず、プルーニング、蒸留、量子化ができない。アプリを高い性能と効率で動かし、自社の領域の専門家にするには、これらが必要

また、モデルの学習は、データを与えて重みを更新するだけでなく、その周りに多くの仕組みが必要だと述べます。本番の観察、データの収集とキュレーション、評価（evals）の構築、そして観察と評価から得た学びをモデルに反映する、という流れです。Foundry の observability プラットフォーム、データセットの加工、evals、agent optimizer などは別セッションで紹介されるので、そちらを見てほしいとのことです。このセッションで扱うのは、本番での性能が分かり、データも集まって、実際に学習する段階です。

### 5.6 Programmed Training（Corey 氏）

今週 **public preview** として発表されたのが Programmed Training です。

**従来の managed training との違い**

- Foundry がこれまで提供してきたのは managed training。データを持ち込み、ジョブを設定してデプロイすると、Foundry の GPU で動く、「撃ちっぱなし（fire and forget）」のサービス
- 既製のオープンモデルと、強化学習の場合の既製のグレーダーを設定でき、UI か SDK でいくつかのつまみを調整するだけ。始めるには最適で、あまり専門知識が要らない
- 一方で、システムをさらに高度にしたいときに必要な、きめ細かい制御は得にくい。強化学習で、本番を模擬する環境にモデルをつなぎたい、といった要望が顧客から出ていた

**Programmed Training の特徴**

- TRL や VRL（音声認識の都合で表記が確定できません）のようなオープンソースライブラリで得られるレベルのカスタマイズと制御を、GPU やインフラを管理せずに使える
- 顧客の悩みとして、GPU を確保できない、確保できても効率よく動かすのが大変、時間単位（場合によって秒単位）で払うので稼働率が低いと割高になる、がある
- **サーバーレスの学習プラットフォーム**で、使った分だけ、**トークン単位で支払う**
- 学習ループ全体を、手元のマシンや開発環境から Python で制御する。操作の実行は Foundry のクラウド上で行われる

EY のように、学習シグナル、評価、報酬の定義という IP を自社が持ち、自社のシステムを模した環境で、各スコアリングと学習ステップの繰り返しを制御できる、と説明されています。

**RL のワークフロー例**

1. モデルからサンプルを取る
2. モデルがツール呼び出しで応答したら、自分たちの環境でそのツールを実行し、実際の応答を得る
3. そのツール呼び出しが正しかったか、もっと良い方法があったかを採点する
4. 報酬のシグナルを集約して GPU に返し、重みを更新する

分散学習、サンプリングなどは Foundry が管理します。サンプルの生成、学習ステップの実行、そのオンデマンドでの提供を Foundry 側で担います。採点など GPU の外での処理に時間がかかる場合も、GPU を遊ばせて料金を払う必要がなく、重み更新の段階になったら GPU を呼び出す形にできる、という点も利点として挙げています。

**4 つのプリミティブ**

チームでは「back propagation as a service」と呼ぶこともあるそうです。公開しているのは、次の 4 つの基本的な GPU 操作です。

1. sampling の呼び出し（自分専用のチップに載ったモデルを呼び、応答を得る）
2. forward pass と backward pass
3. optimizer step
4. 重みの保存（状態の管理）

ほとんどの利用者はこのレベルでは操作しません。ただ、この 4 つを組み合わせることで、必要なアルゴリズムを構成できる柔軟な土台になっていて、その上に SDK が被さっています。同じ基本操作で、次のことができると述べています。

- supervised fine-tuning
- 強化学習の各種（GRPO、PPO、DPO、研究から出てくる新しい手法）
- ツール利用環境との統合
- distillation（on-policy、off-policy）

**始め方**

- GitHub にある cookbook を使い、レシピを数ステップで実行し、合うものが見つかったらフォークして自分のデータに適用する
- 必要なのはノート PC だけで、サーバーレスのため quota（クォータ）の確保も不要
- Corey 氏の個人的な使い方として、Copilot に cookbook を指し示し、やりたい ablation や実験を指定すると、Copilot がこの SDK を使って自律的に実験を回してくれる。設定を加えれば新しい実験も作れ、研究の範囲を広げられる。最終的に、自分のユースケースに合わせて調整されたチェックポイント（モデル）が得られる
- 学習したモデルは Foundry に直接デプロイして、本番で動かせる

### 5.7 EY の事例: Nemotron 3 Ultra の追加学習（Jon 氏）

Jon 氏は、EY が自社でも AI ファクトリー（購入したインフラ）を運用していると述べ、その経験と Programmed Training の違いを語ります。自社でインフラを運用するには、技術の構築と運用ができる人材が必要で、モデルを GPU にどう分散するか、NVIDIA のライブラリが正しく動いているか、並列化をどう管理するか、といった複雑さに取り組まなければなりません。Programmed Training ではそれが抽象化され、**Python のコードが分かるチームだけで進められます**。注力するのは、データと、RL の採点（モデルが望む動きをしているかを確かめる方法）の 2 点です。GPU の管理、台数が足りるか、設定やチューニングは気にせず、コードを書いて実行するだけで済んだ、と説明しています。

**出発点**

出発点は Nemotron 3 Ultra でした。このモデルだけでも質問に答えられたものの、EY が求める水準には達していなかった、とのことです。

**データと学習の規模**（Jon 氏の説明どおり）

- 約 3,700 件のレコード（画面には「31」と表示されていると述べていますが、その意味は音声からは確認できません）
- そのうち約 400 件を評価用（evals）として取り置き
- 約 139 件が検証済みの回答（verified answers）となり、学習ループに組み込んだ
- 学習ループは **370 ステップ以上**。各ステップは、**32 件の購買レコードに対し、それぞれ 8 回ずつ試行**する形

> 補足：3,700、400、139 という数字の内訳の関係（合計や重なり）は、発表では説明されていません。

**報酬の設計（reward model）**

分類の階層に沿った採点基準を、次のように設計したと説明されています。

- segment を正しく当てると、スコアが入る
- その下の family まで当てると、さらにスコアが入る
- class を誤ると、マイナスのスコアになる
- 誤ってから戻って次のデータ点（階層）を当て直した場合も、そのスコアが入る
- 学習の各ステップ（各勾配の実行）まで、これが適用される

これによって、より正確な応答を示すようモデルを強化（reinforce）する、と説明しています。

**学習の推移**

グラフでは、上が完全な答え、下が望ましくない状態です。最初の約 50 ステップで大きく改善し、モデルが賢くなっていく様子が見られました。50 ステップあたりから、さらに 150 ステップほどの間は緩やかに改善が続き、完璧なスコアに近づきました。

Jon 氏が強調したのは、これがとても簡単に行えた点です。Microsoft の Programmed Training と、裏側の NVIDIA のインフラを使えば、インフラの運用に詳しくないエンジニアでも、モデルを選び、正しいスコアを持つ環境を書いて、ステップを実行するだけで結果が出ます。

**結果**

| 項目 | 精度 |
| --- | --- |
| Nemotron 3 Ultra（学習前） | 55.8% |
| フロンティアモデル | 71% |
| Programmed Training 後 | 約 86.6% |

学習前から約 31 ポイント（Jon 氏の言う「30.8」と、Alex 氏の「約 31 ポイント」）の改善です。この作業は **24 時間**で行われたと Jon 氏は述べています（Alex 氏の紹介では「48 時間未満」と述べており、発表では両方の数字が出てきます。どちらを指すかの説明は無く、一致しません）。

コストは、**1,000 件の分類あたり、Microsoft の Programmed Training で約 $3、従来の学習ソリューションでは 1,000 トランザクションあたり $45** でした。Alex 氏が述べた「15 倍安い」と一致します。

Jon 氏は、この仕組みを会社全体に広げやすいと感じていると述べます。モデル学習の知識がない人や、素の GPU インフラしかない人でも使えるため、エンジニアを「ゼロから 100 まで」短期間で立ち上げられ、そうでなければ多くのトレーニングが必要だったはずだ、という考えです。

### 5.8 Q&A とその他

## 6. デモ・手順

このセッションでは画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。

代わりにスライドで紹介された内容として、次の手順・構成があります。

**Programmed Training を始める流れ（Corey 氏の説明）**

1. 学習のアクセスをリクエストする（現時点では承認制）
2. GitHub の cookbook から、レシピを実行する
3. 合うレシピをフォークして、自分のデータに適用する
4. 手元の環境（ノート PC）から Python で学習ループを制御し、規模を広げる
5. 学習したモデルを Foundry にデプロイして、本番で動かす

**EY の学習ループの構成**

1. Nemotron 3 Ultra を選ぶ
2. UNSPSC の階層（segment、family、class、commodity）に沿った報酬を、コードで定義した環境を書く
3. 約 3,700 件のレコードを使い、約 400 件を評価用に取り置く
4. 370 ステップ以上、各ステップで 32 件の購買レコードに 8 回ずつ試行して学習する

## 7. 注意点・発表者の気付き

- **Programmed Training は public preview で、現時点ではアクセス申請が必要。** 承認はカンファレンス後に速やかに進めるとのことです。
- **インフラの複雑さ。** 自社運用では、GPU への分散、NVIDIA ライブラリの設定、並列化の管理に専門人材が要ると、EY が自社の経験として述べています。
- **GPU の稼働率とコスト。** 採点など GPU 外の処理に時間がかかる RL では、GPU を保持し続けると割高になる、と Corey 氏が指摘します。
- **managed training と使い分ける。** 始めやすい managed training は細かい制御には向かないため、制御が必要なときに Programmed Training を使うという位置づけです。
- **オープンモデルの利点。** クローズドなフロンティアモデルでは重みの操作、プルーニング、蒸留、量子化ができません。
- **数字の食い違い。** EY の追加学習にかかった時間は、Alex 氏が「48 時間未満」、Jon 氏が「24 時間」と述べており、発表では整理されていません。
- **発表では触れられていません。** Programmed Training の料金の具体的な単価、対応するモデルの一覧、一般提供（GA）の時期。

## 9. まとめ

このセッションは、汎用のオープンモデルを、自社のデータと評価基準で業務の専門家にする流れを示しました。

1. Foundry の Programmed Training（public preview）は、4 つの GPU 操作を土台に、SFT、RL、蒸留などを、GPU を管理せず、Python で、サーバーレスでトークン課金で行えます。

3. 自社のモデルを持つには、モデルとインフラ、自社の専門知識とデータ、それを適用するツールの 3 つを揃え、ループを自社が所有することが要点です。
