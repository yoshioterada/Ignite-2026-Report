# BRK265 Apps and agents: Business process transformation in Copilot Studio

## 1. はじめに

このセッションは、Copilot Studio が「エージェント」「ワークフロー」「アプリ」の 3 つを 1 つの管理されたプラットフォームとして提供する、という考え方を紹介するものです。前半では Ashvini Sharma 氏が、AI による変革の 3 つの進め方と、Copilot Studio でのエージェントとワークフローの作り方を説明します。後半では Clay Wesener 氏が、アプリの作り方と、それを支える Copilot Managed Runtime、管理者向けのガバナンスを紹介します。

発表の中心にあるのは、次の考え方です。**エージェントは推論と対話、ワークフローは決まった手順の実行、アプリは見やすい操作画面をそれぞれ担当し、同じプラットフォームの上で組み合わせて使う**というものです。どちらのパートでも、画面を使ったデモが行われています。

なお、このセッションは多くのテーマを広く紹介する（breadth-first）構成で、個別のテーマ（ハーネスの使い分けなど）の詳細は別セッションで扱われると、Ashvini 氏が説明しています。

## 5. 発表内容の詳細

### 5.1 AI による変革の 3 つの進め方

Ashvini 氏は、よく受ける質問として「Copilot、Copilot Studio、Foundry はいつ何を使うのか」「それらはどう組み合わさるのか」を挙げ、次の 3 つの枠組みで整理しています。

| 進め方 | 対象 | 使うもの |
| --- | --- | --- |
| 全員の生産性向上 | 汎用的な AI ツールで、各自が仕事を効率化する | Copilot、Cowork |
| 業務プロセス | 1 つの業務プロセスのインスタンス（例: 従業員のオンボーディング、経費精算）。複数の関係者や複数のエージェントが関わる | Copilot Studio（ビジネス部門が、業務の進め方と AI の役割を設計する） |
| プロフェッショナルによる開発 | 開発チームや機械学習・データサイエンスのチームが、AI ソリューションを自社の製品に組み込み、他の顧客にも提供する | Microsoft Foundry |

Copilot については、以前はチャット中心で、要約やコンテンツの検索が主だったが、今年の Cowork では長時間かかる作業も任せられるようになった、と説明しています。

これらはそれぞれ単独で価値があり、かつ組み合わせて使えるように設計されています。例えば、Copilot Studio で作ったエージェントを Copilot に公開したり、Foundry のエージェントを Copilot Studio から呼び出し、それを Copilot にも公開したりできます。さらに、AI の可観測性と制御が必要な場合には Agent 365 を使う、という位置づけです（Agent 365 は昨年の Ignite で発表されたと説明されています）。

### 5.2 Copilot Studio の 3 つの要素

Copilot Studio の最上位の概念は、次の 3 つです。

* **エージェント**: 推論し、会話でき、業務の文脈に基づいてタスクを実行する
* **ワークフロー**: 「まずこれをして、次にこれをする」という決定論的な手順を表す
* **アプリ**: 魅力的な操作画面を提供し、動的なコンテンツに人が関われるようにする（Ashvini 氏のまとめでの説明）

ワークフローが必要な理由について、Ashvini 氏は人々の失敗例を挙げています。ワークフローがない状態では、エージェントに 15〜20 個のツールと 50 個のドキュメントを渡し、何ページにも及ぶ長い指示（「これをする前に必ずこれをする」「これをこれより先にしない」の繰り返し）を書いて、うまくいくことを期待していた、というものです。これは予測可能性をあまり想定していない仕組みに、固定的な経路を無理に押しつけている状態で、「向いていない」と述べています。

そこで、処理の流れが分かっていて一部のノードだけがエージェント的であればよい場合は、ワークフローの中でエージェントを使います。また、ワークフローをエージェントのツールにしたり、アプリからワークフローやエージェントを呼び出したりもできます。これらは同じシステム内で組み合わせられます。

### 5.3 エージェントハーネス

モデルそのものより、その周りの足場にあたるエージェントハーネスが重要だと分かってきた、という話が続きます。Ashvini 氏は、標準のオーケストレーションと新しい Microsoft Copilot Harness を、同じシナリオ、同じツール、同じ指示、同じナレッジ、同じモデルで比較した社内評価を紹介しています。

* 評価の対象は、ナレッジに基づく回答、コード生成、計算など。例えば、350 ページや 54 ページなど文書の複数の箇所に答えが散らばっている大きなドキュメントでは、回答品質が安定しないことがある、という顧客の声があった
* LLM は計算が得意ではないが、計算用のコードを生成させれば有効に動く
* 変えたのはハーネスだけで、全体にわたって効果が高い結果になった
* スライドの右側には、実行したトークン数などのコストも示されている。コンテキストを保持するアーキテクチャのため、キャッシュが多く使われ、同じコンテキストをモデルに何度も渡さずに済む

構成の違いとして、次の点が説明されています。

* エージェントの指示を実行する、安全なサンドボックスコンテナーがある。これはローカルファイルを前提にした設計で、表形式のデータを 1 行ずつ処理させる代わりに、ディスクに書き出してコードで処理する方が効果的
* 以前のハーネスは、ユーザーの質問から文脈を集め、プロンプトを組み立ててモデルに送る「1 回の試行」で、ベストエフォートの回答が返ることもあった
* Microsoft Copilot Harness は**エージェンティックループ**を持つ。取得したチャンクのほかに関連する部分がないかを確認し、目的が達成されるまでループを続ける。その結果、再試行や耐障害性が増え、回答の品質が上がる

標準のハーネスは引き続き提供されます。ほかに、低レイテンシーの音声会話向けにカスタマー会話エージェントとして使える「custom conversational harness」もあります。どのハーネスをいつ使うかは、この日の午後に別のセッションがあるとのことです。

マネージドなエージェント基盤を成り立たせる要素として、Ashvini 氏は、モデルのほかに、エージェントハーネス、提供するコンテキスト（Work IQ または Microsoft IQ）、ガバナンス（何が起きているかを制御する仕組み）の 3 つが重要だと述べています。

### 5.4 エージェントの構築（onboarding buddy）

Ashvini 氏は、Copilot Studio の新しいエージェント構築画面を見せながら、新入社員向けの onboarding buddy エージェントを紹介しています。構成要素は次のとおりです。

| 要素 | このエージェントでの内容 |
| --- | --- |
| Instructions | 新入社員や採用マネージャーをどう扱うか、答えをどこから得るか、メモリに何を保存するか、など |
| Work IQ | シナリオに大きな価値を加えるものとして挙げられ、デモで実際の動きが示される |
| ツール | 新入社員が入るときに、カレンダーに歓迎ランチの枠を確保する、歓迎メールを下書きする |
| ナレッジ | 新入社員向けの福利厚生ガイド、新入社員ハンドブック、IT 機器に関するドキュメント |
| トリガー | チャット（Copilot や Teams）のほか、ユーザーのメールボックスに届く新着メールを自律的に待ち受ける |
| メモリ | ユーザーごとの好みなどを保存 |
| スキル | 初週のプランなど、再利用できる手順（後述） |

> 補足：以前は「対話型エージェント」と「自律型エージェント」が区別されていましたが、発表では「同じエージェントを、チャットでも、イベントの待ち受けでも使える」と説明されています。

スキルについては、「新入社員や採用マネージャーがオンボーディングプランやチェックリストを求めたら、このスキルを使う」というように、再利用できる標準的な進め方を定義するものだと説明しています。このエージェントの中でも外でも、誰が使っても一貫した体験になります。初週のプランを作る場面が、その例です。

### 5.5 ワークフロー

次に、共有メールボックスにメールが届いたときに動くワークフローが紹介されます。顧客からもよく聞くシナリオで、汎用的なメールボックスに様々な問い合わせが届き、内容に応じて振り分けたいというものです。

このワークフローは、最初のステップでメールの種類を分類します。分類の例として発表では、新入社員の入社確認、福利厚生の質問、移民などの機微な事項、ベンダーの売り込み（このメールボックスにはスパムが多いとのこと）が挙げられています。種類ごとに処理が異なります。

* 入社確認: 先ほどのエージェントを呼び出して入社の詳細を抽出し、Excel のスプレッドシートに記録する
* 別の分岐: Copilot Chat を呼び出して、返信を作成する
* 別の分岐: IT サービスのヘルプデスクを担当する、別のエージェントを呼び出す
* ワークフローから Cowork を呼び出すこともできる、とも述べています（画面上のどの分岐かは音声からは確認できません）

Ashvini 氏は、業務プロセスの流れは分かっているので、判断が必要なところにだけ、エージェントによる推論を入れていると説明しています。ステップを追加するには、呼び出したいエージェントを選び、指示を与えます。実際の動作としては、この日の朝にメールを送って実行しており、入社確認のメールを受け取ったあと、詳細を抽出し、onboarding エージェントに問い合わせ、Excel に記録した、と説明しています。

### 5.6 メモリの動き（デモ後半）

同じエージェントに、マネージャーとして話しかける場面です。Ashvini 氏は「Maya Robinson さんがプロダクトマネージャーとしてチームに加わる。onboarding buddy を提案して」と依頼します。エージェントは Work IQ からチームのメンバーを探して候補を示し、開始日を尋ねます。感謝祭の直後だと答えると、エージェントは、月曜 12 時〜13 時のランチ枠は out of office になっている、と指摘します。

そこで Ashvini 氏は、「昼休みは自分 1 人だけの予定を入れて out of office にしている。12 時〜13 時に自分だけの予定があれば、その枠は空いていると考えてよい」と教えます。エージェントのメモリを確認すると、「新入社員のランチがある」ことと「個人の昼休みがある」ことの両方を覚えていました。次回からは、新入社員が入るときや昼の枠を探すときに、これを考慮できます。つまり、使うたびにエージェントが賢くなる、という説明です。

### 5.7 Cowork でシナリオを構築した過程

「これらを 1 つずつ手作業で作る必要があるのか、プロンプトで作れるのか」という質問（5.14 を参照）に対する答えとして、Ashvini 氏は自分が Cowork で作った経緯を紹介しています。

* 出発点は長いプロンプトで、Ignite のセッションの準備中であること、デッキにオンボーディングのシナリオのスライドがあること、顧客に関連づけて話したいこと、エージェントとワークフローを作ってほしいこと、Microsoft を代表するのでプロフェッショナルで適切なシナリオにしたいこと、を伝えた
* Cowork は、Clay 氏との Teams のメッセージ、スライドのデッキ、マーケティング担当の Vid 氏とのセッションの内容（聞き取りが不明瞭な部分があります）、成果物を作る環境などを参照してコンテキストを組み立てた
* 2 回目のメッセージでは、ワークフローを見せたいこと、顧客から「分類」がワークフローの良い例だと学んだこと、6〜7 個のノードで作ってほしいことを伝えた
* 「このエージェントを作って、このワークフローを作って」とは指示せず、解決したい業務上の課題だけを伝えた
* 「エージェントの評価（evals）も見せたい」と伝えると、それらのエージェント向けの評価も追加された

この過程は数日かけて Cowork とやり取りして、適切な成果物を作ったものだとのことです。結論として、Cowork を構築のパートナーにすることができる、と述べています。

### 5.8 アプリ: Copilot Managed Runtime

ここから Clay 氏のパートです。最近 Copilot Studio にアプリのタイルが加わったこと、アプリのスキルが Cowork、Copilot Code、CLI にも入ったことが紹介されます。

画面は、左にエージェントとの対話、右にアプリのプレビューが並ぶ構成です。他の製品でも見かける形式ですが、**この体験での操作はすべて Copilot Managed Runtime の中で管理されます。** ガバナンスのルールには、環境のルーティング、使えるデータコネクタ、共有ポリシー、セキュリティポリシーが含まれます。アプリを作るエージェントはこれらを理解しているため、組織で許可されたコネクタを使い、適切なコンテンツタイプを使い、アプリは正しい場所でホストされて動きます。Copilot Studio、Cowork、Copilot Code、CLI のどこで作っても同じです。

Copilot Managed Runtime は、セッションの前日に一般提供（GA）になったと説明されています（数か月間プレビューだった）。どこで作っても、デプロイされたアプリは Copilot Managed Runtime の上でホスト・実行・管理されます。これにより次の効果があります。

* Entra によるセキュリティが標準で得られる
* アプリが情報にアクセスする手段として、コネクタを利用する
* 管理者は 1 か所のガバナンスの場所で、どこで作られたアプリも見られ、1 組のポリシーをすべての入口に適用できる

作成の入口は複数あっても、裏で動くスキルは同じなので、どこから始めても同じガバナンスになります。

### 5.9 アプリ構築で重要な 2 点

**Work IQ のコンテキスト**: Clay 氏は、成功するアプリ（共有され、エンドユーザーに使われ、社内で広がるものを成功と見なす）は、何もない状態のプロンプトから始まるものより、会話を重ねてそこに Work IQ のコンテキストを使ったものだ、と述べています。会議、Loop コンポーネント、PowerPoint のプレゼンテーション、誰かとの会話、プラグインやコネクタの情報を参照でき、1 つのプロンプトだけに頼らずに済みます。

**コネクタ**: 利用できるコネクタは 1,500 以上あり、Microsoft のサービス、サードパーティ、カスタムが含まれます。管理者が、どのコネクタを組織で有効にするか、誰がどの組み合わせで使えるかを選び、Microsoft Admin Center の 1 か所で制限できます。Clay 氏は、これにより vibe coding の利点を保ったまま、信頼できる安全な環境で使える、と説明しています。

### 5.10 アプリにエージェントを組み込む、MCP apps

従来のアプリは静的で、データに接続し、裏にあるコードは固定的でした。最近はアプリ自体にエージェント機能を組み込む取り組みを進めており（プレビュー 2 か月目に入った機能で、最初の発表では見逃された可能性があるとのことです）、アプリのロジックを、Ashvini 氏が見せたエージェントなどで動かせます。これにより、アプリが特定のデータ参照にとどまらず、レコメンデーションや操作の実行もできるようになります。現時点で使える範囲でも、エージェントで動くアプリを作れるとのことです。

逆方向の取り組みとして、MCP apps を使うと、エージェントとの会話の中に UI やインタラクティブな操作を出せます。テキストでは足りず、より視覚的・対話的なものが欲しい場合に使うものです。提供は 2 段階で、まず独自の MCP apps を持ち込んでエージェントで使えるようにし、次に、このデモで示すアプリ構築の機能を、エージェント向けのカスタム UX 作成にも使えるようにする予定です。

### 5.11 Git リポジトリと「崖がない」開発体験

アプリを作ると、裏でプラットフォーム上に Git リポジトリが作成され、アプリのソースコード全体が保存されます。ビジネスユーザーにはコードは見えなくてもよいのですが、コードはチェックインされ、バージョン管理され、Git の操作はエージェントがバックグラウンドで行います。

コードファーストの開発者がいる組織で、より大きな規模に拡張したい場合は、Copilot Studio や Cowork で始めたアプリでも、リポジトリを取得してターミナルで作業できます。Clay 氏は「崖がない（no cliffs）」と表現し、どこで始めても vibe coding の並列画面と、コードの直接編集を行き来できると述べています。すべて Copilot Managed Runtime の上でホストされます。

### 5.12 評価と FinOps

デモのあと、Ashvini 氏が「FinOps」に関して 2 点を紹介しています。

* **評価（Evaluations）**: 製品に組み込まれており、エージェントの出力を採点する各種の grader がある。AI では成功か失敗かだけでなく、出力の品質が期待に合っているかが問題になるため
* **FinOps**: アプリだけでなく、エージェントとワークフローも対象に、消費しているクレジットの数を見られる。エージェント単位、ユーザー単位、環境単位などで上限を設定できる。アクセスさせたくない場合は、エージェントを隔離（quarantine）できる

## 7. 注意点・発表者の気付き

* **エージェントに長い指示を詰め込む作り方は避ける。** 15〜20 個のツールと 50 個のドキュメントに加えて長文の指示を与え、うまくいくと期待するやり方は、仕組みとして向いていない、という指摘です。手順が決まっているものはワークフローにします。
* 曖昧な指示でアプリを作り始めると、データの保存先などを尋ねる質問が返ってきます。
* 成功したアプリは、空のプロンプトから始まったものではなく、会話や Work IQ のコンテキストを活用したものだった、というのが Clay 氏の観察です。
* アプリを作る入口は複数ありますが、裏で動くスキルは同じなので、どこから始めても同じガバナンスが適用されます。
* コードエージェントの early access preview は、サインアップが必要です。
* 発表者は、スライドで見せた比較（ハーネスの評価）は社内で評価したものだと述べています。具体的な数値は、発話では語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* ハーネスを変えるだけで、同じモデル・同じ指示のままナレッジ、コード生成、計算などの品質が上がった（社内評価）。コンテキストを保持するためキャッシュも多く使われる
* エージェントの出力の品質を測る評価機能が、製品に組み込まれている
* クレジットの消費の可視化、エージェント・ユーザー・環境ごとの上限設定、エージェントの隔離が、アプリ、エージェント、ワークフローに対して用意されている
* 管理者は、どこで作られたアプリも 1 か所で見られ、ポリシーを 1 か所で設定できる。Entra によるセキュリティが標準で適用される
* コネクタは 1,500 以上あり、管理者が組織内の利用を制御できる
* ビジネスユーザーが作ったアプリでも、リポジトリを取得して、開発者がターミナルでコードを扱える
* Ashvini 氏によれば、以前は数週間かかっていたデモの作成が、Cowork を使うことで数分〜数時間で済むようになった。「新しい働き方が可能になった」という感想です

## 9. まとめ

このセッションは、Copilot Studio のエージェント、ワークフロー、アプリを 1 つのガバナンスされたプラットフォームとして組み合わせる、という内容でした。

* AI による変革は、生産性向上（Copilot、Cowork）、業務プロセス（Copilot Studio）、プロによる開発（Microsoft Foundry）の 3 つに分けて考え、観測と制御が必要なときは Agent 365 を使う
* エージェントは推論と対話、ワークフローは決まった手順、アプリは操作画面を担当する。手順が分かっているプロセスでは、ワークフローを軸に、必要なノードだけをエージェントにする
* Microsoft Copilot Harness のエージェンティックループにより、標準のハーネスより回答の品質が上がったことが、社内評価で示された
* アプリは Copilot Managed Runtime（前日に GA）の上でホストされ、Entra セキュリティ、コネクタ、管理者向けの一元的なポリシーと可観測性が得られる。Git リポジトリがあるため、開発者はコードを直接扱える
* 評価機能と FinOps の機能（クレジットの可視化、上限、隔離）が製品に組み込まれている
