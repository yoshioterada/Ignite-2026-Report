# BRK251 Agents in production: Observe, evaluate, and optimize with Foundry

## 1. はじめに

このセッションは、本番で動かすエージェントの品質に自信を持つための、Microsoft Foundry の可観測性（observability）の話です。従来の「動いているか、速いか、エラーはないか」に加えて、「エージェントは正しいことをしているか」を見る必要がある、という問題意識から始まります。

流れは、構築段階（trace、データセット、評価）、本番運用（insights と Agent Optimizer）、複数エージェントの監視（fleet view とコスト）の 3 部構成です。それぞれに画面を使ったデモがあり、最後に Tata Consultancy Services（TCS）の事例として、AKS 運用エージェントのトークン消費を約 66% 減らした話が紹介されます。要点は、**trace → 評価 → insights → 最適化という改善のループを、継続的に回す**ことです。

## 5. 発表内容の詳細

### 5.1 observability の考え方

従来の observability は、アプリやエージェントが上がっているか、応答するか、速いか、エラーがないか、を見るものでした。これは引き続き必要で、そのために trace でエージェントの各ステップを見ます。そこに「エージェントは正しいことをしているか」という問いが加わり、その答えを出す仕組みが**評価（evaluation）**です。評価とは、エージェントの振る舞いをテストする手段です。

### 5.2 構築段階：trace と評価

**trace**

- Foundry で動かすエージェントは、コード変更なしでデフォルトで trace が取られます。
- 他の場所でホストしているエージェントは、「Microsoft Hotel Distro」と聞こえるライブラリ（音声認識の都合で正式名称が確定できません）を追加し、数行のコードを足せば trace を取れます。
- データは App Insights に保存されます。Foundry プロジェクトの作成時に App Insights のリソースを接続するよう案内されています。IT 管理者が App Insights を使っている場合、アプリケーションとエージェントのデータを 1 か所で見られます。

**評価の方法（3 種類）**

| 方式 | 特徴 |
| --- | --- |
| コードベースの evaluator | 決定的。例えば、ツール呼び出しのスキーマを確認する場合に使う。 |
| 人による評価 | 最良だが非常にコストが高い。 |
| モデルベース（LLM）の evaluator | 上の 2 つの制約があるため最も普及している。このセッションの中心。 |

人からのフィードバックを取り込む方法にも触れる、と説明されています。

**構築段階の発表（新機能）**

- **評価データセットの task-based rubric**：より高度な評価をしたい場合に、データセットに task-based rubric を含められる。ライブのトラフィックの trace をデータセットに送ることも簡単にできる。
- **rubric evaluator**：エージェント向けに Foundry が作成を支援するカスタム evaluator。これまでは品質用のみだったが、**安全性用も作れる**ようになった。
- **decision model**：evaluator を動かすモデルとして導入する。低コストで非常に速いので大規模に使える。欠点は、スコアが低い理由が得られないこと。ライブトラフィックでスコアだけを取り、あとから分析するという使い方をしている顧客もいる。

### 5.3 本番運用：insights と Agent Optimizer

Han が、構築から本番へ話を進めます。trace で何が起きたかが分かり、rubric 評価で明確な基準に照らして判断できます。しかし本番では、個々の事象を理解するだけでは足りません。エージェントの所有者や開発者は、**自分でも気付いていない問題**のうち、どれが注意に値し、どんな根拠があり、どこから改善を始めるかを知る必要があります。そこで登場するのが insights です。

発表された内容は次のとおりです。

- **insights（本番 trace からの insights）：一般提供（GA）**
- Agent Optimizer の **3 つの新しい最適化戦略**と**人による annotation**：パブリックプレビュー

insights は、数十から数千の trace を分析し、根拠と対応への道筋を付けた形で示します。覚えるべき 4 点として、次が挙げられました。

1. **継続的な分析**：分析をスケジュールでき、一度きりの調査で終わらせない。
2. **根拠付きの insights**：すべての発見が trace に紐づき、trace や会話に戻って、説明と照らして本当の問題かを確認できる。
3. **重要なものの優先付け**：事前設定なしでもよく動く。重視したい問題が分かっているなら、カスタムカテゴリを作ると、insights がその種の問題を拾いやすくなる。
4. **insight から行動へ**：診断、根拠、推奨される対応を 1 つの引き渡しにまとめる。コーディングエージェントに渡して文脈と修正を任せることも、Foundry の **Agent Optimizer** でシームレスに修正することもできる。

Agent Optimizer の新しい 3 つの機能は次のとおりです。

| 機能 | 内容 |
| --- | --- |
| Fix insights with Agent Optimizer | レビュー済みの insight を、そのまま Agent Optimizer で修正する。 |
| Optimize skills from traces | 過去の trace から学び、新しい skill を作る、または既存の skill を改善する（発表者は「dreaming のようなもの」と表現）。 |
| Optimize for cost | 高い品質基準を保ちつつ、最もコストが低いエージェントのバージョンを探す。 |

Han は、スライドに戻って次のように振り返っています。trace から insights を作り、rubric evaluation で明確な基準に照らして判断し、人による annotation で trace を補強します。これらをすべて Agent Optimizer に渡すと、エージェントを継続的に改善できます。これが「改善のループ」です。

### 5.4 複数エージェントの監視とコスト

エージェントが 1 つではなく何百もある場合に向けた話です。**fleet view のプレビュー**が発表され、すべてのエージェントの健全性と品質を 1 か所で確認できます。「すべてのエージェントのコストを 1 か所で見られるか」という問いにも、「見られる」と答えています。

Monitor ページで見られる内容（デモの語りに基づく）は、6.3 にまとめます。

### 5.5 TCS の事例

**Deep Raj**（TCS、AI ソリューションアーキテクト）の発表です。冒頭の結論は、**AKS 運用エージェントが 1 回の診断サイクルで約 275K トークンを消費していたものを、Foundry Toolkit の助けで約 94K トークンまで下げた**というものです。

**ソリューション**

- 「TCS autonomous operations」（音声認識で「PCS」と書き起こされた箇所がありますが、TCS と読み取れます）は、顧客向けに開発したマルチエージェントのソリューションで、Azure のクラウド運用を自動化します。汎用エージェントと専門エージェントを組み合わせています。
- **AKS operations agent** は専門エージェントの 1 つです。さまざまな AKS クラスターのアラートを取り込み、分析し、詳細な根本原因分析を行い、修復の選択肢を作ります。あらかじめ用意した skill も使います。

**課題（KPI）**

- 診断ではテレメトリログを大量に扱うため、トークン消費の最適化が最重要の KPI（主な課題）だった。
- アラートごとに、適切な skill を正確に選べるか。
- 渡している recipe を正しく選び、その recipe に沿った詳細な計画を作れるか。

より上位の環境でこのエージェントを運用する確信を得られる解決策を探していた、と説明されています。

**Foundry の機能の使い方**

1. **データセット**：監視システムに取り込まれたテレメトリログから作れる点が役に立った。約 400〜600 サンプル（「4:00 to 6:00」と聞こえ、音声認識の都合で確定できません）で、さまざまな種類を含む。
2. **insights**：主に build と design の段階で使い、効果的だった。
3. **評価**：insights のあとに次の環境へ移して評価した。カスタマイズ可能な rubric evaluator を使い、重要な KPI の改善に有効だった。
4. **最適化サイクル**：AKS エージェントについて、**2 週間ごと**に設定した。候補が出てくる。**スコアが大きく改善した場合にのみ**、次の環境に昇格させるというルール。

**成果**

- トークン消費を約 **66%** 削減。
- 全体の評価スコアを **15%** 改善。
- 改善した KPI は、task adherence（AKS エージェントに守らせたいこと）、skill の読み込み、適切なツールの読み込み。

**66% 削減に効いた 2 つの insight**

1. **skill の読み込み**：エージェントが skill を繰り返し読み込んでおり、load skills ツールが頻繁に呼ばれ、入力トークンとキャッシュトークンを多く消費していた。
2. **pod status ツールの呼び出し方**：問題の pod だけでなく、クラスター全体の他の pod も照会していたため、入力トークンを多く消費していた。

どちらも修正し、Foundry の insights が問題の特定に大きく役立ったと述べています。

**評価基準と結果**

- rubric 評価を、カスタマイズした次元で使った。フォーカスした次元は、tool use quality、task completion、task adherence の 3 つ。それぞれに重み付けをした。
- ベースラインの候補の評価スコアは約 **85%**。提案された修正を適用したあと、**100%** に向上した。
- skill の読み込みは、ほぼ 15〜20% 改善した（「それ以上に効果的だった」とも述べています）。

Han は、コスト削減と品質向上が同時に得られている点を評価しています。

## 6. デモ・手順

このセッションには、3 つのデモがあります。Divya は、デモが**録画**であり、扱う内容が多いため録画にしたが、これらの機能は実際に試せると説明しています。UI のバージョンで見せるが、code-first でも提供されている、とも述べています。Han のデモは「live demo」と言っています。Deep Raj のデモは、TCS の Foundry プロジェクトの画面です。録音は音声のみのため、画面の細部は確認できません。以下は、語られた範囲です。

### 6.1 デモ 1（Divya・録画）：trace、データセット、評価

**trace の確認**

1. エージェントの traces タブで、個別の trace（リクエスト）や会話を確認する。会話ビューでは、所要時間やトークンの観点から、軌跡（trajectory）を見られる。
2. ユーザーのビューで、ユーザーの質問と応答、追加のメタデータを見る。
3. レビュー中に annotation を付け、人のフィードバック（期待される結果など）を集める。trace に対して評価を走らせていれば、間違っている理由も見られる。
4. trace のグラフィカルな表示もある。今年は、**カスタムフィルター**が追加された。trace に送る複数の属性でフィルターして、手動レビュー用の trace を絞れる。

**データセットの合成生成**

データセットは、エージェントがこなすべきタスクの大半、想定するユーザー層、あいまいなリクエストなどをカバーする「基準」となるもので、新しいバージョンのエージェントに流し、evaluator に評価させる「ゴールデンデータセット」です。ゼロから作るのは難しいので、エージェントに基づいて合成生成できます。

1. Data のナビゲーションから、synthetic data generation を選ぶ。
2. プロンプトで指示する。このデモでは、各ケースで happy path だけを作るよう指示した（エージェントに合わせて変えられる）。
3. 対象のエージェントを選ぶ。Foundry でホストしているなら、関連する文脈が自動で取り込まれる。
4. 生成に使うモデルを指定し、15 件の生成を依頼する。時間がかかるが、各件には、説明、何をテストするか、クエリ、期待される結果が含まれる。
5. すでにライブトラフィックがある場合は、該当する trace を選んでデータセットに送ることもできる。
6. テストケースの rubric が必要な場合は yes にして、rubric 情報を追加するモデルを選ぶ。

**rubric evaluator の作成**

1. 名前を付ける。対象のエージェントは「Caldova」（音声認識の都合で表記が確定できません）。品質（quality）と安全性（safety）から選べて、このデモでは quality を選んだ。
2. rubric の自動生成を選び、モデルと対象のエージェントを選ぶ。製品仕様など、エージェントが知るべき資料を添付することも、ライブ trace を例として含めることもできる。
3. 生成された品質の rubric は、多くのファイルを調べて答える投資エージェント向けに、検索（retrieval）、引用、情報が矛盾する場合の扱いなどを軸にしていた。
4. 同様に、安全性の evaluator も作成した。エージェントに関係の深い次元が選ばれ、このデモのエージェントでは prompt injection が最大の課題だったので、その観点で確認する rubric になった（発話は「prompt ingestion」と聞こえ、音声認識の都合で表記が確定できません）。

**オフライン評価**

1. 本番に出す前の、1 回きりの評価を作る。ターン単位で評価する（会話全体も選べる）。
2. 既存の合成データセットと、エージェント、評価基準に使うモデルを選ぶ。組み込みの evaluator は約 60 個あるが、今回は作成したばかりの quality evaluator を使う。
3. 実行し、「offline」と名付ける（ライブトラフィックではなく、ゴールデンデータセットで評価するため）。途中で画面が閉じるトラブルがあり、やり直している。
4. 結果は **67%**。データセットの 15 件のうち 10 件が合格、5 件が不合格。「65% 以上なら満足」と仮定して、本番に出す。失敗した場合は、その理由も確認できる。

**ライブトラフィックの評価**

1. 同じ evaluator を、ライブトラフィックに対して実行するよう設定する。**1 時間ごと**、サンプリングは、コストを抑えるために random か intelligent を選べる（intelligent の方が、より深い分析を行う）。ここでは random を選び、1 回の評価につき **100 件**の trace、モデルを指定する。
2. 開始すると、スコアは **40%** で、目標の 65% を下回った。登壇者は、顧客は想定と全く違うクエリを送ることがあり、エージェントがうまく動かないクエリが多いこともあるため、ライブトラフィックで初めて分かることがある、と説明している。

### 6.2 デモ 2（Han・live demo）：insights と Agent Optimizer

デモに使うエージェントは、「Cordova の portfolio review agent」（音声認識の都合で表記が確定できません）で、記録を検索して証拠をまとめ、**判断はポートフォリオの所有者に任せる**ものです。証拠が不十分なのに自信を持って答えることを避けたい、という前提です。

**insights の設定と確認**

1. insights タブを開き、settings で、insight の生成に使う judge model を選ぶ。
2. オンデマンドで実行するか、scheduled analysis を有効にする（これが継続的な分析）。有効にすると、新しい trace が入るたびに自動で分析され、結果がこのページに表示される。ワークロードに合わせて頻度も変えられる。セッション前にすでに数回スキャンしてある。
3. insights のページは、メールの受信箱のような見た目で、1 行が 1 つの insight。右側に詳細が出る。
4. 1 つ目の insight は、「繰り返し起きる失敗は、検索ではなく回答の生成にある」という内容。さらに、取得した記録に決定や責任者が書かれていないのに、pause や hold といった行動を選んだり、リスク受容の結果を推奨したり、全体の準備状況の単一の責任者を名指ししたりする、という趣旨の記述がある。まさに避けたかった問題だった。
5. それが本当かを確かめるため、リンクされた trace を開く。ハイライトされた trace が根拠。最初の trace のユーザービューでは、Northstar プログラムの進捗を質問され、エージェントが「selected action: pause、accountable owner: Nadia」と答えていた。オーナーとして、このプログラムには複数の責任者がいて、確定した日付ではなく、マイルストーンの日付しかないため、この答えは正しくないと判断できる。
6. annotation タブから、この trace に annotation を付けられる。付けたものは履歴に残り、この trace に永続的に紐づく。この trace を評価や最適化に送るときに、サービスへの入力の一部として使われる。

**priorities と instructions**

1. settings には、judge model の下に priorities と instructions がある。
2. priorities は、初めて insights を有効にしたとき、最も一般的な 8 つのデフォルトカテゴリが対象になる。コストとトークン、レイテンシー、ハルシネーション、安全性などが含まれる。
3. デモでは、add customer category で作った「portfolio decision evidence boundaries」というカテゴリがある。instructions の欄に、insight エンジンが探すべき問題、フラグを立てるタイミング、期待される正しい振る舞いを伝えるステアリングプロンプトを入れた。
4. 優先度は全部を選んでおらず、今後のスキャンでは output quality、context memory、security and risk と、新しいカスタムカテゴリだけに絞る。
5. 先ほどの insight が、まさにこのカスタムカテゴリに分類されていて、カスタムカテゴリが期待どおりに動いた。

**metrics ダッシュボード**

生成された insight の数、分析した trace の数、トークン使用量と推定コストが見られます。insight をカテゴリまたは重大度でグループ化もできます。このデモのエージェントでは、ハルシネーションと信頼性のエラーが上位の問題で、まずそこに対処すべきだと分かりました。

**Fix Insight による最適化**

1. 右上の紫色のボタン「Fix Insight」を押すと、optimization run の作成画面が出る。
2. 対象のエージェントとバージョン、候補（candidate）の構成が表示される。最適化と評価用のデフォルトのモデルと、候補の最大数が用意されていて、変更もできる。候補の最大数を増やして、より網羅的にすることもできる。
3. 作成後、ジョブは設定により数分から数時間かかる。
4. 1 つ直すと別の問題が悪化するかもしれない、という心配に応えて、複数の insight をまとめて修正することもできる。「select insights」ボタンで複数を選び、fix を押す。画面とフローは同じで、選んだ insight をまとめて 1 つの最適化ジョブに渡す。選ぶほど、候補を生成するためにジョブが多く走る。

**最適化ジョブの結果（典型例）**

- このジョブは 2 つの候補を作り、候補 1 の評価が最も高く、ベースラインより **0.2 高い**。スコアが 0 から 1 なのは、Divya が紹介した rubric 評価と同じ方式で、ジョブの中で rubric evaluator を作って品質を測っているため。
- run details から、評価の実行に入れる。各行が 1 つのデータで、score 列が pass か fail。view details で、rubric の次元の数や、合格した理由が見られる。
- 例として、システムが正確なファイルを検索して使い、この日付は単なるマイルストーンの計画日であって、全体の責任者による準備完了の確約ではない、と正しく説明したので合格した、と読み上げている。マイルストーンの日付を確定した日付として扱わなかったことが理由。
- 評価を確認して問題がなければ、候補を昇格（promote）して、本番の新しいエージェントバージョンとしてデプロイできる。

**Fix insights の場合の違い**

- 全体の品質に加えて、**insights improved** という列が出て、各候補でいくつの insight が改善したかを、候補間やベースラインと比較できる。
- 例では、候補 1 の方が多くの insight に対処している（4 件）のに、システムは候補 2 を推奨している。理由は、品質の基準を保つためで、候補 2 は全体の品質が上がり、候補 1 はベースラインと同じ水準にとどまった。候補 2 が対処した insight の数は、発話が「4 か 5」「5 つのうち 3 つ」と揺れていて、数は確定できません。
- 最終的に判断するのは利用者。候補 1 でも品質が許容できるなら、候補 1 か 2 のどちらをデプロイするかを決められる。

### 6.3 デモ 3（Divya）：Monitor ページ（fleet view）

1. ナビゲーションの Monitor ページで、プロジェクト全体、アクティブなエージェントの一覧、すべてのエージェント、Foundry のモデルを選んで見る。
2. 最上部のサマリーに、期間内にアクティブなモデルとエージェントの数、エージェントの実行、使用量、トークン使用量、コスト、ポリシー違反が出る。ポリシー違反があれば、詳細に入れる。
3. **運用メトリクス**：使用量、エラー、トークン使用量、レイテンシー。モデルを使っていれば、どのモデルが使われ、リクエスト量、コスト、モデル呼び出しのエラー率も見られる。
4. **エージェントの品質**：各エージェントに作った evaluator が並び、見たい evaluator を選んでチャートを見る。task completion や task adherence のように、全エージェントで共通の evaluator があれば、複数のエージェントのスコアを比べられる。特定のエージェント専用の rubric evaluator は、それを持つエージェントだけが表示される。
5. エラーがあれば、クリックして、原因となった trace をすべて見られる。このデモでは、よくある問題であるレート制限に当たったことが原因だった。
6. **コスト**：これまでの課金額と、月末の予測を表示する。プロジェクトに**予算**を設定でき、そのプロジェクト内のエージェントが使える額を、月次または日次で決められる。予算がある場合はその詳細と、各エージェントの支出、シェアが出る。
7. 支出が多い理由は、エージェントのコストページに進んで trace を見る。run ごとのコストなども確認できる。Divya は **token usage タブ**が気に入っていて、キャッシュのヒット率が下がったためにコストが上がった、といった分析ができると述べています。

### 6.4 デモ 4（Deep Raj）：TCS の AKS エージェント

1. Foundry プロジェクトと AKS エージェントを開き、insight の画面を見せる。
2. 設定した priorities は、コストとトークン、ツール呼び出しの失敗など。
3. 初めて insight を実行したとき、skill 読み込みのパターンが特定された。trace からそのパターンを見つけ、背景にある問題を特定し、修正案も出した。この修正を適用した。
4. 次の実行で、ツール呼び出し用の JSON payload の作り方に関する別の問題が見つかった。payload が、問題のない pod も含む複数の pod を指していたため、これも修正した。
5. その結果として、トークン消費が約 66% 削減された。
6. 評価基準（rubric、tool use quality、task completion、task adherence に重み付け）の画面で、最適化サイクルによって、ベースラインから多くの KPI が改善したことを示した。

## 7. 注意点・発表者の気付き

- **ダッシュボードが緑でも、エージェントが正しいとは限りません。** 完了していないのに完了したと言う、自信を持って間違えるといった挙動は、従来の指標には出ません。
- **ライブトラフィックでは、手元のデータセットより成績が下がることがあります。** デモでは、ゴールデンデータセットで 67%（目標の 65% 以上）だったものが、ライブトラフィックで 40% になりました。顧客は想定外のクエリを送るためです。
- **decision model にはトレードオフがあります。** 低コストで速いが、スコアが低い理由は得られません。
- **insight は、根拠の trace で必ず検証します。** insights は trace にリンクされており、元の trace で本当の問題かを確かめるよう勧められています。
- **最適化の候補は、スコアだけで決めません。** 対処した insight の数が多い候補でも、全体の品質が基準を保てなければ推奨されません。最終的な判断は利用者です。
- **昇格には基準を置きます**（TCS）：スコアが大きく改善した候補だけを、次の環境に昇格させるというルールにしています。
- **機能の提供状況**：insights は GA、Agent Optimizer の 3 つの新戦略と人による annotation はパブリックプレビュー、fleet view はプレビューです。
- デモ 1 の途中で、画面が固まったり閉じたりするトラブルがありました（発表の内容には影響しません）。

## 8. 利用者にとっての利点

- 本番の trace から、自分では気付いていない問題を、根拠付きで継続的に見つけられます。
- 評価の準備（データセットと evaluator）を、エージェントの文脈から自動生成でき、ゼロから作る負担を減らせます。
- 見つけた問題を、コーディングエージェントや Agent Optimizer にそのまま引き渡して、修正まで進められます。Optimize for cost で、品質を保ちながら低コストの構成も探せます。
- 複数エージェントの健全性、品質、コスト、ポリシー違反を、1 か所で確認できます。
- TCS の事例では、AKS 運用エージェントのトークン消費を約 275K から約 94K（約 66% 削減）に下げ、評価スコアを 15% 改善し、ベースライン約 85% の評価スコアが 100% になりました。

## 9. まとめ

本番のエージェントでは、「動いているか」だけでなく「正しいか」を測る必要があります。Foundry は、trace、データセットと rubric evaluator による評価、insights（GA）、Agent Optimizer（プレビュー）、fleet view とコストの監視を、継続的な改善のループとして提供します。

デモでは、オフライン評価 67% がライブでは 40% に下がる様子と、insight から trace で根拠を確かめ、Fix Insight で候補を比較する流れが示されました。TCS は、このループで AKS 運用エージェントのトークン消費を約 66% 減らしています。
