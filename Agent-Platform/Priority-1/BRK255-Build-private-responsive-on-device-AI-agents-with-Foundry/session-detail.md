# BRK255 Build private, responsive on-device AI agents with Foundry

## 1. はじめに

このセッションは、Foundry Local を使って、プライバシーを保ち、応答の速い AI アプリやエージェントを「クラウドを経由せずに」デバイス上で動かす方法を紹介する 45 分のブレークアウトです。Ignite 2026 の最終セッションとして行われました。

内容は、(1) ローカル AI の位置づけ、(2) Foundry Local のアーキテクチャと使い方、(3) ローカルで動かす **コーディングエージェント** のために行った最適化とデモ、の順に進みます。Windows や Mac、Linux のアプリにローカル AI を組み込みたい開発者が、何が用意されていて、どの程度の速度が出るのかをつかめる内容です。

> 補足：このセッションでは、画面を使ったデモが 3 つ行われています（GitHub Copilot の音声入力、ハイブリッドルーティングのデモアプリ、GitHub Copilot app でのローカルコーディング）。顧客事例は動画で紹介されました。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK255](https://ignite.microsoft.com/en-US/sessions/BRK255)

## 4. 発表者が伝えたいメッセージ

発表者が伝えているのは、次の 3 点です。

1. **ローカル AI は、チャットだけのものではなくなった。** 音声の文字起こし、埋め込み（RAG）、ランキング、判断（decision）といった複数のモダリティを扱え、本番アプリでの採用事例も出ている。
2. **アプリに自己完結した形で組み込める。** ランタイムは圧縮時で約 10 MB と小さく、ユーザーに別のツールをインストールさせずに済む。
3. **最も負荷の高いエージェント的な処理（コーディング）でも実用的な速度が出せる。** そのために、ランタイム、モデル、GitHub Copilot への統合の 3 か所を最適化した。

ローカル AI が増えている理由として、次の点が挙げられました。

- ローカル AI の対象が、端末にとどまらず、オンプレミスのデータセンターやロボットのような小型機器にも広がっている。クラウドはフロンティア級まで扱えるが、オンプレミスもそこに近づいている。
- ユーザーのデバイスの性能が上がっている（例として Windows デバイス向けの RTX Spark や、ゲーム用 GPU）。
- 蒸留（distillation）や量子化（quantization）の手法でモデルが良くなり、定型的な AI だけでなく、より複雑なタスクもデバイス上で扱える。

登壇者は、Foundry Local の発表（約 18 か月前）の頃はローカル AI のセッションが数個だったのに対し、今年の Ignite では、ブレークアウト、ライトニングトーク、シアター、ラボを合わせて 15〜20 のセッションがある、と述べています。

## 5. 発表内容の詳細

### 5.1 Foundry Local の位置づけ

Microsoft Foundry は、エージェント、モデル、IQ ツールを、コントロールプレーンで管理されたエージェントのライフサイクルとして提供します。そのうえで **Foundry Local は、利用者が所有・管理するインフラ上で動く Foundry** と説明されました。対象は、オンプレミスのクラスター、単一サーバーのエッジゲートウェイ、小型機器（ビジョン・ランゲージ・アクションモデルでロボットを制御するシアターの展示が例に挙がりました）、そして PC、Mac、Linux の個々のデバイスまでと幅広いものです。

> 注意：クラウドにあるモデルや Foundry の構成要素が、すべてのデプロイ先で使えるわけではありません。例えば 3 兆パラメータのモデルは小型機器では動かせません。そのため、Foundry Local では各対象に合ったモデルとワークロードの階層（tier）を選び、同じ Foundry の体験を持ち込めるようにしています。

このセッションが扱うのは、そのうちの **デバイス側**（Windows、Mac、Linux を横断するローカルおよびハイブリッド AI のスタック）です。

### 5.2 アーキテクチャ

登壇者は、ユーザーが外部の CLI やアプリ（トランスクリプトでは「Lama server」や「iLama」と聞こえるもの）を別途インストールしなくてもよい、**アプリに自己完結した AI 機能** を作れる点を最初の特徴に挙げています。ランタイムをアプリに埋め込み、そのサイズを圧縮時で約 10 MB まで小さくしています。

構成は次のとおりです。

| 層 | 役割 |
|---|---|
| Foundry Local SDK | 開発者の入り口。言語バインディングは C、Python、JavaScript、Rust（発話のまま。「C」は C# を指す可能性がありますが、聞き取りからは確認できません）。ABI を薄くラップしている |
| Foundry Local ABI（C で記述） | モデルのライフサイクル（ダウンロード、メモリへの読み込み）と推論を担当し、重い処理を受け持つ |
| ONNX Runtime | 推論エンジン。2017 年頃から存在し、実戦で使われ、約 5 億台のデバイスに展開されているとのこと |
| Foundry catalog | モデルの取得を担当。Azure のグローバルバックボーンを使い、最適なリージョンからダウンロードし、geo fallback もある（例：オーストラリアのユーザーはオーストラリアのデータセンターから取得） |
| WinML（Windows） | **plug-in execution provider（EP）** を提供する。NVIDIA CUDA、Qualcomm QNN、AMD の Vitis、Intel OpenVINO など、ハードウェアアクセラレーション用のバイナリを実行時に登録・読み込みする |

EP が実行時に読み込まれるため、ユーザーのデバイスに、そのハードウェア向けのドライバがあるかどうかを開発者が気にする必要はありません。

### 5.3 アプリへの組み込み方

言語のパッケージインストーラーで Foundry Local SDK を追加し、数行のコードでローカル AI を使えます。スライドにはチャットセッションが示されましたが、手順はどのモダリティでも同じです。

1. カタログからモデルを取得する
2. ダウンロードする
3. そのモデルでセッションを開始する

セッションの種類としては、RAG 用の埋め込み、ライブ文字起こし用のオーディオ、decision（判断）、ranking（ランキング）が挙がりました。推論のリクエスト／レスポンスの型は **OpenAI 互換** で、ユーザーメッセージなどがストリーミングのリクエストに積まれていきます。

実行するハードウェアは Foundry Local が選びます。GPU があれば自動で GPU を使い、GPU も NPU も無ければ CPU にフォールバックします。

**CLI** も提供されていますが、位置づけは開発者向けのツールです。異なるモデルやモダリティ（チャット、ライブ文字起こし、埋め込みなど）を試せるほか、永続的な OpenAI 互換の HTTP エンドポイントを提供するため、コーディングエージェントなどのサードパーティ製ツールを接続できます。開発・テストの用途では、本番ではクラウドのエンドポイントを選ぶ場合でも、アプリ開発中の内側のループ（dev inner loop）ではローカルモデルを使ってトークンの消費を減らす、という使い方が多いと説明されました。

### 5.6 コーディングエージェントをローカルで動かす

Sam は、この 1 年の間に開発者から繰り返し聞いた要望として、「自分のコーディングにローカル AI を使いたい」というシナリオを挙げました。当初は、Foundry Local と ONNX Runtime にギャップがあり、良い体験が作れる状態ではなかったため、この数か月かけて改善してきたとのことです。

コーディングエージェントは要求の厳しいワークロードです。1 回のプロンプトで終わらず、非常に長いコンテキストのまま、推論とツール呼び出しを何度も繰り返します。そのため、持続的に速い推論と、複数のタスクの並列処理、ハードウェアとモデルの能力を使い切ることが必要になります。登壇者は、強く量子化した小さなモデルで品質を犠牲にするのではなく、複雑な問題を解ける実用性を目指したと述べています。取り組んだ場所は **推論ランタイム、モデル、GitHub Copilot への統合** の 3 つです。

高い性能を得るには CPU だけでは足りず、十分な性能の GPU が必要だとされています。例として、128 GB のユニファイドメモリを持ち、FP4 で最大 1 ペタフロップスの AI 性能を持つ **RTX Spark**（Windows 向け）が挙げられました。RTX 5090 など他の NVIDIA デバイスでも同様にモデルとランタイムを作っています。

**ランタイム**：デコードの速度は、Llama CPP のような他のランタイムの **約 2.5 倍**（発表での見出しの数値）です。ONNX Runtime に次を加えました。

- D-Flash の speculative decoding
- prefill caching
- カーネルと fusion の追加
- tool calling の改善（コーディングなどのエージェントで重要なため）
- KV cache の量子化

これらはコーディングエージェントだけでなく、Foundry Local を使うすべてのアプリに効く改善です。

### 5.7 モデルの選び方と最適化

Foundry Local のカタログには、何でも入れるわけではありません。**幅広さではなく、名前の付いたシナリオでうまく動くモデルを絞って選ぶ** のが方針で、ライブ文字起こしで Nemotron に手を入れたのと同じ考え方をコーディング向けモデルにも適用しています。手順は次のとおりです。

1. 世の中のオープンモデルすべてを候補とし、公開ベンチマークから約 10 モデルを選ぶ。
2. それらを社内のベンチマークにかけ、公開値が実際に通用するかを確認する。
3. コーディングで特に良い数個に絞る。見る指標はスループット、品質、ツール呼び出しの成功数、SWE bench、terminal bench など。
4. ONNX のツールチェーン（トランスクリプトでは「Oliver Mobius」と聞こえる）でモデルを最適化する。グラフの fusion、量子化の手法や精度の比較、対象ハードウェア向けのカーネル最適化を行う。

この過程を経たコーディング向けモデルとして、**Qwen、Qwen Flash、MAI Code Flash on device、Nemotron Bolt** が挙がりました。

### 5.8 GitHub Copilot への統合

統合の段階は次のとおりです。

1. **当初の形**：bring your own inference。CLI をインストールして動かす必要がある。
2. **近日**：単一のプロバイダとして、何もインストールせずに使える。GitHub の音声入力と同じように、モデルをダウンロードするだけで組み込み済みのランタイムが使える。
3. **その次**：最適化したモデルを **Copilot Fusion**（GitHub Copilot 側のルーター）に取り込み、Windows でハイブリッドルーティングできるようにする。

### 5.9 Q&A

1. **NPU は今後どう位置づけられるか。** NPU は電力効率のために設計されたもので、以前はカーネルの対応が足りず CPU にオフロードしていたが、対応が進んでいる。ただし 27B クラスのコーディング用モデルが載る大きさではない。decision モデルのような小さなモデルには適している。
2. **NVIDIA、AMD 以外のハードウェアベンダーの統合方針は。** Foundry Local は ONNX Runtime のエコシステムで動き、EP を実行時にダウンロードして組み込む。対象ハードウェア向けの EP ライブラリがあれば ONNX Runtime で動き、Foundry Local のランタイム高速化として配布できる可能性がある。対応ハードウェアは現在のものに限られない。
3. **ハイブリッドルーティングはどこまでロードマップか。** Copilot には「Fusion」というルーターがあり、Windows チームがすでに一部のローカルモデルをその中に組み込む作業を行っている。ローカルモデルがクラウドモデルと同じプールに入り、トラフィックの振り分けは自動で行われる。最適化したモデルも Fusion に取り込む予定。もう 1 つの方法が、デモのように decision モデルを使う方法。
4. **開発者が自分で判断ロジックを実装する必要があるか。** Azure の Foundry のモデルルーターにローカルモデルを含める案は、ロードマップではないが検討の視野にあり、過去に議論はしたものの深くは進んでいない。Foundry Local 自体に「ローカルのルーター」を持たせる議論はこれまでしていない。質問者の「Foundry Local を入口にして、フロンティア級の推論が必要なときはクラウドへ回してほしい」という要望は、フィードバックとして受け止められた。

## 6. デモ・手順

> 注意：録音は音声のみのため、画面の細部は発話で語られた範囲だけを記します。

### 6.1 デモ 1：GitHub Copilot の音声入力（Foundry Local 埋め込み）

Sam が、GitHub Copilot が Foundry Local を組み込んだ例を見せました。ここで見せたかったのは、利用者に追加のインストールを求めない **自己完結性** です。

1. GitHub の設定で、音声入力（voice dictation）を選ぶ。サードパーティのエンドポイントへの接続を求められず、約 10 MB の組み込みランタイムが使われている。
2. 使いたい文字起こしモデルを選べる。トランスクリプトでは Nemotron 3 と、その多言語版が挙がっている（「Neematron 3」と書き起こされている）。デモでは、あらかじめダウンロード済みのモデルを使った。
3. 録音ボタンを押すと、すべて Foundry Local 上で動いている。
4. このオーディオモデル（Nemotron）は CPU 上で効率よく動くように最適化されており、このハードウェアでは CPU 使用率が約 2% だった。レイテンシと word error rate は良好、と説明された。

### 6.2 デモ 2：ローカルとクラウドを振り分けるハイブリッドルーティング

decision モデルとツール呼び出しの改善を見せるためのシンプルなデモアプリです（アプリ名は聞き取りが不明瞭ですが、Foundry と router に関わる名前に聞こえます）。GitHub リポジトリが接続されており、プロンプトをデバイスで処理するか、クラウドに送るかを判断します。

仕組みは次のとおりです。

1. 小さなモデル（トランスクリプトでは「QEN 1.5B」）が、リポジトリのファイルを読む、検索するなどのツールを使い、コンテキストを集める。送ろうとしているコンテキストの大きさや、秘密情報が含まれていないかなどを調べる。
2. その結果を **decision モデル** に渡す。出力は型付きで、「秘密情報が含まれるか」「ローカルで処理するには大きすぎるか」「深い推論が必要か」などの問いごとに確率が返る。
3. その確率に応じて、トラフィックを振り分ける。

実演は 2 つのプロンプトでした。

1. 事前に実行した「メールアドレスを検証する正規表現を書いて」：リポジトリ検索のツールを使い、一致が見つからず、デバイスで処理できると判断した。decision モデルの応答は、秘密情報なし、ローカルで処理できる大きさ、深い推論は不要。**デバイス上で実行された。**
2. 「checkout で負荷が高いとタイムアウトが多発する」旨のより複雑なプロンプト：リポジトリで checkout のタイムアウトを検索し、checkout の TypeScript ファイルを見つけた。decision モデルは、そのファイルに秘密情報がある確率が高いと返し、原因の調査には深い推論も必要と判断した。結果は **秘密情報を伏せて（redact）クラウドへ送る** というものだった。

コードの構成も紹介されました。スライドのチャットセッションと同じ形で、セッションの設定、レスポンスの投入、ツール定義の追加（add tool definition）、そして decision セッションが並んでいます。「カタログからモデルを取り、セッションを作り、リクエストとレスポンスを渡す」という同じパターンです。

### 6.3 デモ 3：GitHub Copilot app でローカルモデルによるコーディング（Baiju）

プレビュー版の体験として、GitHub Copilot app を使って見せました。

1. model providers に、Foundry Local が **managed model provider** として表示される。Foundry Local を別にダウンロードする必要はなく、GitHub Copilot app に同梱されている。
2. カタログから選べるモデルとして、QEN 3.8 27B、MAI Code Flash on device、Nemotron Bolt、QEN 3.8 Flash Next が並ぶ（トランスクリプトの表記のまま）。
3. このデモ機は 32 GB のデバイスメモリで、MAI Code Flash は大きすぎるため動かない。Foundry Local は **ハードウェアを認識し、モデルがデバイスに収まるかどうかを表示できる**。画面には、より多くのメモリが必要だと表示されている。
4. QEN 3.8 Flash Next も大きいモデルだが、CPU オフロードなどの最適化で、このデバイスに収まる。GPU と CPU が連携して動く。仕組みは ONNX Runtime が持つ、異なるデバイス種別（NVIDIA GPU と CPU）の管理と、GPU・CPU 間の効率的なデータ移動の機能を使っている、と説明された。
5. モデルプロバイダに Foundry Local を、モデルに QEN 3.8 Flash Next を選ぶ（ロード済み）。「光る宇宙船のアーケードゲームを作って」と Copilot に依頼する。
6. 実行中に、高速化のためにやったこととして次が説明された。
   - カーネル最適化、CPU オフロード、品質を落とさない積極的な量子化
   - スケジューリングの効率化：推論エンジンが複数の同時リクエストを並列に処理できる
   - D-Flash 2 の speculative decoding：実際のモデル（target model）と、複数のトークンを提案する小さな drafter model を組み合わせ、1 回の推論で 2 つ以上のトークンを予測する
7. ゲームは「数分以内」に完成した。すべてデバイス上で動いている。
8. 別のプロンプト（事前に選択したもの）で、リクエストを認識するスケジューリングを説明した。デコード（1 トークンずつ）を要するジョブと prefill を要するジョブが同時に来た場合、デコードを優先し、tokens per second を高める。prefill は並行して処理でき、複数の同時リクエストでも体験が崩れない。
9. システムプロンプトは大きい。Copilot はツール（ファイルの保存や編集など）をすべて渡すため、プロンプト長は 30,000 トークンを超える。コンテキストの内訳として、システムプロンプトが約 11,000、システムツールが約 29,000、MCP ツールとメッセージがあり、合計でおよそ 40,000 トークンに近い。それでも速度は出ている、と説明された。この例でも別の可視化（visualization）が作られた。
10. 最後に「pull request を作って」と依頼する。マルチターンに最適化されており、ツール呼び出しと推論も扱える。prefix caching により、同じエージェントワークフローを繰り返しても計算済みの部分を再利用できる。ツールを呼び出して、pull request が作成された。

登壇者は、これはコーディングに限らず、エージェント的なワークフロー全般に当てはまると述べています。また、この体験は近日中に **NVIDIA GPU 以外（AMD GPU と macOS）にも提供され、macOS、Windows、Linux のクロスプラットフォームになる** と説明されました。

> 補足：デモ中、Baiju は「QEN 3.8 27B で実行する」と話した後、実際に選んだモデルは「QEN 3.8 Flash Next」と述べています。発話の上では、どちらのモデルで動かしたかに揺れがあります。

## 7. 注意点・発表者の気付き

- **すべてのモデルがローカルに載るわけではない。** 3 兆パラメータのモデルは小型機器で動かせないため、対象に合わせてモデルを選ぶ必要があります。
- **コーディングには強い GPU が必要。** CPU だけでは、コーディングで高い実用性を得にくい、という趣旨でした。NPU についても、27B クラスのモデルは載らないと説明されています。
- **モデルは絞って選んでいる。** カタログには何でも入れず、シナリオごとに絞って最適化する方針です。
- **機能の提供時期。** GitHub Copilot の単一プロバイダ（インストール不要）、AMD GPU と macOS 対応は「近日（coming soon）」です。Copilot Fusion への統合は「その次」の予定です。Java バインディングは preview です。GitHub Copilot app の体験も preview と説明されました。
- **デモの前提。** ハイブリッドルーティングのデモは「シンプルなデモ」と位置づけられ、decision モデルには、MAI の decision モデルではなく、オープンソースのモデルを使っています（名前は「KEV」と聞こえますが、登壇者も確信なさげで、確定できません）。

## 8. 利用者にとっての利点

- **プライバシー**：機密性の高い会話や文書をデバイスの外に出さずに処理できる（Care to Translate、Foxit PDF Editor、AirGap AI Transcribe の動画での説明）。
- **オフライン動作**：インターネットもクラウドも使えない状況で動作する（Restoration Sequencing Advisor、Care to Translate）。
- **トークン費用の削減**：開発中の内側のループにローカルモデルを使えば、トークンの消費を減らせる。
- **配布の簡単さ**：約 10 MB のランタイムを埋め込むため、利用者に外部ツールのインストールを求めず、アプリのサイズもほとんど増えない。
- **ハードウェアの違いを意識しない**：GPU があれば GPU、無ければ CPU を自動で選び、EP も実行時に処理される。
- **速度**：コーディング向けのランタイムは、Llama CPP などと比べてデコードが約 2.5 倍速いと発表されました。

## 9. まとめ

1. Foundry Local は、Foundry を利用者が管理するインフラ（オンプレミス、エッジ、PC、Mac、Linux）で動かすためのもので、このセッションはデバイス側が対象です。
2. 約 10 MB の埋め込み可能なランタイム、SDK（複数言語）、ONNX Runtime、plug-in EP により、ユーザーに追加のインストールを求めず、ハードウェアの違いも吸収して、数行のコードでローカル AI を組み込めます。
3. チャット以外に、文字起こし、埋め込み、ranking、decision といったモダリティを扱えます。ハイブリッドルーティングのデモでは、小さなモデルと decision モデルで、秘密情報の有無や推論の深さに応じて処理先を振り分けました。
4. コーディングエージェント向けには、ランタイム（デコードが Llama CPP などの約 2.5 倍）、絞り込んだ最適化済みモデル、GitHub Copilot への統合の 3 点で取り組みました。デモでは、32 GB のデバイスメモリのマシンで、ローカルのモデルがゲームを作り、pull request も作成しました。
5. GitHub Copilot のインストール不要の提供、AMD GPU と macOS 対応、Copilot Fusion への統合は、今後の予定です。
