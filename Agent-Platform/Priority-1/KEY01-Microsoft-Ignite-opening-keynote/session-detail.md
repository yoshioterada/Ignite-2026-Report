## 5. 発表内容の詳細

### 5.1 オープニング映像と Satya Nadella のあいさつ

冒頭の映像は、AI の恩恵をすべての人に届けるために「フロンティアエコシステム」を築く、と語ります。そこでは、自分のインテリジェンスを所有し、重要な成果を継続的に改善し、変化の止まらない世界で優位性を加速させる、という姿が描かれました。

Satya は、先週の出来事がデジタルインフラの重要性（世界にとっての「ダイヤルトーン」）を改めて思い出させたと述べ、顧客が寄せる信頼を重く受け止めていると話しました。レジリエンスについては「まだやるべきことがある」と認め、学んで改善し続けると約束しています。参加者の組織で継続性を守っている人たちにも感謝を伝えました。

### 5.2 Satya Nadella：3 つの柱

ミッションは「すべての人と組織が、より多くを達成できるようにする」ことです。Satya は、今日これを実現する方法は 1 つ、フロンティアエコシステムを共に築くことだと述べました。そのための柱は次の 3 つです。

| 柱 | Satya の説明 |
|---|---|
| 人を中心に置く | 個人の役割、組織、システム、製品を、人の意図・野心・主体性を増幅するように設計し直します。ソフトウェアエンジニアリングは、成果物を作る仕事から、成果物を作る「ソフトウェアファクトリー」を作る仕事へ広がります。ただし人の意図、判断、経験、専門性、職人技は引き続き重要です。変わるのは「てこが効く点」です。ソフトウェアチームに限らず、あらゆる職種の仕事・ワークフロー・成果物が同様に変わります |
| インテリジェンス | AI の時代の問いは、個々の企業が自社の学習と暗黙知をどう築き、所有し続けるかです。多くの企業が存在できる経済であるためには、インテリジェンスは少数のモデルに集約されず、広く分散している必要があります |
| 信頼 | スケーリング則は有効で、規模を上げるたびに新しい能力が現れます。一方で、アライメントもモデルの内部の機構的な理解も、まだつかめていません。そのため、強力な技術をそもそも信頼できるのか、という問いが生じます。Satya は「定義上、信頼はできない」とし、インテリジェンスの供給と、それに対する権限を分離することがアーキテクチャ上の必須事項だと述べました |

Satya はこの 3 つの必須事項に応えるスタックを作る、と説明し、以降は順に各層を紹介しました。

### 5.3 Satya Nadella：Copilot は仕事の新しい OS

Satya は Copilot を「仕事の新しいオペレーティングシステム」と位置づけました。Chat、Cowork、Code、Autopilot という人とコンピューターのやり取りの形が 1 つの体験に集まり、ナレッジワーク、コーディング、業務アプリという別々の領域も 1 つになります。アプリは Copilot のプラグインにすぎず、Office のすべての機能が Copilot に組み込まれています。基盤には、タスクに合う知能を、合う文脈と形で割り当てるモデルシステムがあります。

- **Home**：簡単な質問から複数ステップの複雑な作業まで、1 か所から始められます。
- **Code**：組織内のすべての人に「無限の SaaS ファクトリー」を渡します。アプリやダッシュボードを作れ、テナント内で安全にホスト・管理されます。
- **Autopilot**：24 時間 7 日動き続ける自律型エージェントです。共同作業の場で、追加のチームメイトのように働きます。
- **Work IQ**：これらの基盤となる「データベース」です。人、人どうしの関係、メール、会議、チャット、プロジェクトという仕事の織物を深く理解します。Satya は、組織にとって最も重要なデータ資産の 1 つだと述べました。

Satya は、ここまで話した内容が「組織内で広く利用可能になった」と発表しました。

さらに Copilot を職種に広げます。営業、法務、財務、サービスの各職種向けに、スキル、コネクタ、プラグインをまとめ、サードパーティを含む業務アプリを Copilot の画面から使えるようにします。その一環として、Dynamics 365 向けのビジネスプラグインを発表し、Salesforce を Copilot に持ち込むパートナーシップにも触れました（詳細は Judson のパートで語られます）。集中作業向けの専用の形も引き続き必要だとして、Excel のアナリスト、Word の法務担当、PowerPoint のデザイナー、Discovery を使う科学者、Dragon を使う医師や看護師、GitHub を使う開発者を例に挙げました。

### 5.4 Satya Nadella：GitHub と Copilot Workspaces

数週間前の GitHub Universe では、新しい 2 つのプリミティブが発表されたと説明されました。

- **Projects**：目標を定め、1 つ以上のリポジトリを接続すると、Copilot がタスクセッションと定期的な作業を、その目標に向けて調整します。
- **GitHub Copilot Fusion**：複数のモデルを組み合わせて、フロンティア水準の結果をはるかに低いコストで出す「複合モデルファミリー」です。Satya によれば、この日 Terminal-Bench で 1 位のコーディングエージェントになりました。「Claude Core」を 5 ポイント上回り、コストは半分未満です（「Claude Core」は音声認識の都合で表記が確定できません）。

続いて Satya は、これまでの Copilot は個人とそのコーディングループ・エージェントループという「シングルプレイヤー」の世界だったと述べました。次の形は、人、そのエージェント、他の人が共通の目標に向かい、共有コンテキストで動く「マルチプレイヤー」です。これが **Copilot Workspaces** です。紹介動画が流れましたが、トランスクリプトには音楽しかなく、映像の内容は分かりません。

Satya は、数週間使っただけで自分の働き方が変わったと述べ、かつて Chat があらゆる仕事の出発点になったように、Workspaces も同じ位置を占めるだろうと語りました。

### 5.5 Satya Nadella：Microsoft IQ とマルチモデルシステム

Satya は、クラウドは「クライアントソフトウェアからクラウド上のデータの重力へ」の移行であり、AI はそのデータをインテリジェンスにつなぐと説明しました。それが **Microsoft IQ** です。組織が自分たちのインテリジェンスを築き、保持し、継続的に改善するための仕組みで、Copilot の下で作ってきたシステムを、独立した第一級のプラットフォームとして外に出すものだと述べています。

構成は次の 3 つです。

- **アクションスペース**：データ資産とアプリ資産。
- **コンテキスト**：Microsoft 365 配下のデータである Work IQ、Fabric IQ、Foundry IQ、Web 上のデータである Web IQ、サードパーティのコンテキスト。数百の新しいコネクタが付属します。
- **マルチモデルシステム**：最適化の問題は、各タスクに最も良い経済性で知能を割り当てることです。製品、ハーネス、ツール、モデルを 1 つのエンドツーエンドの最適化として調整できる点が、実世界のタスクで Microsoft に固有の強みだと述べました。

これらは、組織全体で共有・継承できるビジネスプラグインとして現れます。

### 5.6 Satya Nadella：モデル（Decision、Foundry、MAI）

**Decision Models** は、インテリジェンスをソフトウェアの中核プリミティブとして組み込めるモデルの新しいクラスです。Satya は、リレーショナルデータベースがソフトウェアエンジニアリングを変えたように、「ディシジョンエンジニアリング」も変えると述べました。

- **Microsoft Decision 1.1** が一般提供（GA）になり、エンタープライズ展開の準備ができました。マルチモーダル対応、精度と応答速度の改善が入り、すでに 4,000 社以上が使っています。
- Epic は、患者体験、臨床ケア、バックオフィスの意思決定に使っています。
- Copilot 自身が、利用者を適切なモード、モデル、推論の強さへミリ秒精度で振り分けるのに使っています。
- Xbox のチームは、ゲームの発売ごとに寄せられる多数の自由記述フィードバック（「tens and thousands」と聞こえました）の仕分けに使っています。
- LLM を使う場合と比べて、10 倍以上速く、200 分の 1 のコストだと説明されました。

**Foundry のモデル**：Foundry には主要なクローズドモデルとオープンウェイトモデルがそろっています。今日、**GPT-6.2** が Foundry に加わりました。複雑な専門業務を測るベンチマークで新しい基準を打ち立てたとされ、「GPT-6-2 Astra は前世代を、推定コストの半分以上という点で上回った」という趣旨の発言がありましたが、意味は音声認識の都合で確定できません。先週は Claude の「Fable 5.2」と「Mythos 5.2」が加わり、今日は Meta の最新モデルも Foundry に来ることが発表されました（モデル名は音声認識の都合で表記が確定できません）。

**MAI モデルファミリー**：Microsoft 自身のモデルです。事前学習は計算効率がよく、デプロイ時はトークン効率がよいと説明されました。製品内でのタスク性能という実世界の指標を踏まえ、フロンティア曲線上の点を増やすことが目標です。勢いを示す数字として、次が挙げられました。

- MAI Transcribe 2 のリクエスト数は、OpenRouter でのローンチ以降 12 倍になりました。
- MAI Code Flash は、先月の GitHub Copilot で 300 万人が利用しました。
- MAI Cyber は、Perception のコードスキャンの 40% 以上を支えています。

今日は新しいモデルがいくつも紹介されました（詳細は Mustafa のパートで語られます）。Satya が特に挙げたのは次の 2 つです。

- **MAI Code 2**：エージェント型コーディングモデルの新しいフラッグシップファミリーです。日常的なエンタープライズのコーディングで、コスト性能のフロンティアにあります。本番へ持ち込むコード、複数ファイルにまたがる実装、リポジトリ全体にわたる推論、UI を、わずかなコストでこなすと説明されました。**Code 2 Flash** は、コードの説明、狙いを絞った編集、素早い反復のような量の多い作業向けで、フラッグシップに近い品質を大幅に低いコストで出します。
- **MAI Cyber 2 Flash**：Microsoft で最も高性能なセキュリティモデルです。Flash サイズで、1 タスクあたりのコストをフロンティアモデルよりずっと低くしながら、性能はそれを上回ります。コーディングと同じく、モデル、ツール、システムを 1 つとして共同設計しており、Perception に統合されます。

**MAI Licensed Weights** も発表されました。信頼できるパートナーが、「Frontier Co.」を通じて MAI モデルのウェイトにアクセスできるようになります（名称は音声認識の都合で確定できません）。

**Foundry のマネージドエージェントハーネス**：モデルとコンテキストを Foundry に置けば、長時間動くエージェントを構築・デプロイするためのハーネスを使えます。Copilot と GitHub Copilot を動かしているのと同じものです。これを継続的改善ループにつなぎ、経験から学ばせられます。自分のプライベートなベンチマークと評価を定義すると、Foundry がエージェントをそれで測定し、本番で見えた結果に基づいてエージェントや下のモデルを改善します。Satya は、実行のたびに学習・改善でき、組織のインテリジェンスが時間とともに価値を増す「常に改善し続ける、自己修復するシステム」になると述べました。

### 5.7 Satya Nadella：信頼（Agent 365、Perception、透明性）

信頼の柱は、スタックのあらゆる層に可観測性を持たせることから始まります。

**Agent 365** は、既存のガバナンス、アイデンティティ、セキュリティ、管理の仕組みを、企業全体のエージェントに広げるコントロールプレーンです。すでに 5,000 万のエージェントが登録されています。FinOps も含み、AI の支出と、AI が組織にもたらす価値を結びつけます。今日、**Agent 365 Business Analytics** が発表されました。Satya はこれを「AI 利用のための ERP システム」と呼び、支出の要因を正確に把握し、成果と結びつけ、シナリオ横断で ROI を最適化できると説明しています。

**Perception**（Microsoft のセキュリティスタックとして語られました）：Copilot、IQ、Agent 365 に登録されたエージェントを守る、エンドツーエンドの信頼のプラットフォームです。AI の展開を守ることと、AI でセキュリティを強化することの両方を目指します。

- Agent 365 と Entra：すべてのエージェントに一意で永続的なアイデンティティを与えます。
- 「MXC and Cloud Containers」：ツールとネットワークの強い境界を提供します（音声認識の都合で表記が確定できません）。
- Purview：データと情報の流れを統制します。
- Defender：脅威をリアルタイムで妨害・封じ込めます。

事例として、独立したセキュリティ研究者が、自律型の AI 攻撃フレームワーク ARTEX を使い、Defender で保護された環境をテストしました。エージェントはネットワーク内を横方向に移動し続けましたが、Defender の自動攻撃妨害は、攻撃が続く間も侵害されたアカウントを封じ込め、デバイスを隔離し続けたと説明されました。

攻撃がエージェント化・自律化するため、防御にも機械の速度が必要です。Perception はこれに応える「エージェント型のセキュリティシステム」で、次のエージェントを使います。

- **Red チーム**：攻撃をシミュレーションします。例の Pen Test 用エージェントは、Web アプリの認証、API、インジェクション攻撃、ビジネスロジックなどを調べ、悪用できないことを確認する証拠を作ります。
- **Blue チーム**：攻撃を検知します。ARTEX の攻撃を封じた Defender がその例です。
- **Green チーム**：修復します。

個別のエージェントだけでなく、エージェントのチームを組んで複雑な仕事を自律的に実行する「プレイブック」も作れます。Perception は、アイデンティティ、クライアント、クラウド、アプリ、エージェントにまたがるシグナル、センサー、アクチュエーターもつなぎます。Satya は **Perception が一般提供（GA）になった**ことを発表しました。

**Microsoft AI Transparency Initiative**：Satya は、モデルが触れるものはほぼ見えても、モデルの内部で起きていることは見えないと指摘しました。モデルが自分について語ることは独立した証拠にならず、あるモデルが別のモデルを監視しても同じ問題が残ります。そのため、入れ子のブラックボックスを透明で検証可能にする標準が必要だと述べました。取り組みは 3 つです。

1. 「NIS」Agent Standards Initiative との協力を広げ、AI の透明性、セキュリティ、ガバナンスのオープンな業界標準づくりに研究を役立てます（「NIS」は音声認識の都合で表記が確定できません）。
2. エコシステムで進めます。どのモデルでも、誰が提供しても、説明責任があり、独立に検証でき、設計段階から安全な AI を可能にします。すでに 40 の組織が標準の定義と適用に参加しています。
3. 同じ標準を、MAI モデル、Foundry、Copilot を含む自社製品のすべてに取り入れます。

Jay Parikh は、どの CIO も「エージェントを作るのは簡単だが、本番で動かすのは難しい」と言うと切り出しました。本番のエージェントにはアイデンティティ、認証、サンドボックス、企業データへのアクセス、監視、レッドチーミングなどが必要で、多くのエージェントがそこで止まります。問いは「どう作るか」ではなく、「何千ものエージェントをどう作って動かし、信頼し、毎日良くするか」だと述べました。その基盤として、GitHub は構築の場、Fabric はデータを整理する場、Foundry は本番でエージェントを動かして改善し続ける場だと位置づけました。

Jay は Alaska Airlines を、この種のループを実際に回している例として紹介しました。見どころとして、「良い」をどう定義するか、最適化でどこまで進むか、学習で何が上積みされるか、の 3 点を挙げています。デモは第 6 章 6.7 です。

デモの終盤で Charu Jain は、運用に近い人が問題を見つけ、自分たちで解決策を作るためのツールを手にした点がよかったと語りました。AI は推奨し、決めるのは整備エンジニアで、人は常に中心にいる、という考えです。

### 5.20 Charles Lamanna：Agent 365

Charles Lamanna は、仕事は AI で動くようになり、あらゆる企業が AI を導入し、エージェントや AI アシスタントによる仕事が増えているが、セキュリティとガバナンスのリスクが普及を妨げていると述べました。AI 全体の可観測性と管理がなければ、スケールに達せません。コスト、セキュリティ、エージェントの乱立（スプロール）を管理する必要があります。

Agent 365 は 1 年前の Ignite で発表された、AI のための可観測性プラットフォームです。エージェントを 1 か所で一元管理し、展開と有効化を統制し、作った各エージェントのコストと価値を追跡し、従業員とエージェントを安全に保ちます。Microsoft 製と非 Microsoft 製のプラットフォームにまたがり、AWS、GCP、OpenAI、Anthropic のほか、Databricks、Snowflake、Salesforce などのアプリやデータ基盤にも対応します。

**Agent 365 Business Analytics** は、AI の支出、導入、価値を 1 つにまとめた新しい体験です。使われたトークンだけでなく、実行された仕事を測ります。AI が完了したタスク、節約した時間、生んだ価値を扱い、チームと事業が AI でどう前進しているかを、方向性として示します。予算、モデルの組み合わせ、プラットフォームを調整して、コストと性能のバランスを時間をかけて取れます。目標は AI の支出を減らすことではなく、投資した 1 ドルあたりの価値を増やすことだと述べました。Stephanie Cronin のデモは 6.9 です。

### 5.21 Aleš Holeček：セキュリティの 3 つの傾向と Perception

Aleš Holeček は、この 12 か月でフロンティアモデルとオープンウェイトモデルが脆弱性の発見と悪用に非常に長けてきたと述べ、3 つの傾向を挙げました。

| 傾向 | 内容 |
|---|---|
| 量 | 今月の Patch Tuesday では 1,000 件以上の脆弱性に対処したが、3 月は 100 件未満で、1 年足らずで 10 倍になった。Microsoft に限らず、主要なプラットフォーム、ブラウザー、オープンソースのパッケージで同じ傾向が見られる |
| コスト | バウンティプログラムは質の高い脆弱性 1 件に約 30 万ドルを支払うが、AI の助けで、研究者も攻撃者も 5 ドル未満で見つけている |
| 時間 | 発見から悪用までの時間はゼロに近づいている。ARTEX のようなツールキットで AI が即座に悪用できることに加え、責任ある協調的な開示のプロセスが崩れつつあるため |

攻撃者が使うのと同じ技術を、責任を持って防御側に渡すことが使命だとして、エージェント型セキュリティのための新しいサイバースタックを作ったと述べました。構成は次のとおりです。

- **センサー**：160 万の顧客がすでに信頼する Defender、Entra、Purview、Sentinel が、問題の発生時にアラートを上げます。
- **アクチュエーター**：検知だけでは不十分で、攻撃下では機械の速度で動く必要があります。デバイスをネットワーク上で封じ込める、侵害されたアイデンティティを取り消す、認可層やデータ層でブロックを作る、といった操作です。
- **コネクタ**：セキュリティスタックは異種混在のため、500 以上のセキュリティコネクタを用意しました。製品とコネクタで、1 日に 165 兆を超えるシグナルが生成されます。
- **コンテキスト**：シグナルを、Microsoft や顧客自身の脅威インテリジェンス、ビジネスインテリジェンスで補強し、リアルタイムでトークン効率のよいセキュリティコンテキストにします。毎日、適合率と再現率を評価しています。
- **エージェント、ハーネス、モデル**：専門のエージェントが連携して、防御とセキュリティの成果を出します。

これらが **Microsoft Perception**（新しいエージェント型セキュリティシステム）にまとまり、今日一般提供されると述べました。David Weston のデモは 6.11 です。

デモのあと Aleš は、すべてのエージェントとプレイブックを、実際のセキュリティ業務に根ざした厳格なベンチマークで評価していると説明しました。マルチモデル設計で、各タスクを最も適したモデルに振り分けます。その中には、Mustafa と密に共同開発した MAI Cyber 2 が入っています。MAI Cyber は、長年の実世界のセキュリティデータで学習し、最新の脅威を反映した学習環境で改善しており、その結果は CyberGym のエンドツーエンドで GPT-6 Astra より優れ、コストは 1 タスクあたり 2% です。

最後に、AI は組織の内側にも新しいリスク、つまりエージェントをもたらすと述べました。エージェントは悪意があるわけではないが、過剰な権限を持ち、広範なツールと価値の高いデータにアクセスし、24 時間業務プロセスを実行するようになっています。Perception と Agent 365 は同じコンテキストを共有し、企業全体のエージェントを機械の速度で守ります。「AI はサイバーの物理を変えた」ため、基盤を守り、脅威から防御し、「エージェント型のインサイダー」を守るための Perception を作った、と結びました。

### 5.22 BNY：Leigh-Ann Russell との対話

### 5.23 Judson Althoff：クロージング

Judson は、Microsoft の社員向けイベントで、子どもたちに自分の最大の野心をポスターに書いてもらった話を紹介しました。「日本に行きたい」「フットボール選手になりたい」「キングコブラに触りたい」などがあり、どこにも「プロンプトエンジニア」はありません。子どもたちはチャットウィンドウの中で暮らしたいわけではない、というのが彼の見方です。フロンティア変革は人間の野心を可能にするためのもので、人々が日々使うキャンバスの中に AI が組み込まれ、大切なことに時間を使えるようにするべきだと述べました。

インテリジェンスについては、AI モデルに「あまりに多くの信用」を与えてきたと指摘しました。インテリジェンスとは、情報の集約や推論ではなく、独自のアイデア、組織の独自の差別化を意味します。歴史上、持てる者と持たざる者の差は知識へのアクセスと相関してきました。AI は、これまでのどの技術よりもインテリジェンスを民主化し、不治の病の治療、科学と研究の進歩、栄養と繁栄といった社会の課題を解く機会を与えます。インテリジェンスは内側から複利で増えなければなりません。フロンティアエコシステムは、1 つのモデルの成功や、世界の GDP を市場規模と見なすモデルラボのためのものではなく、あなたの IQ、独自の差別化を、オープンでモデル多様、異種混在の形で増幅するものだと述べました。

### 6.7 Alaska Airlines（Charu Jain と Seth Juarez）：ATA コードの割り当て

背景：Alaska Airlines では、整備報告書ごとに、機材全体で作業を追うための ATA コードを付けます。コードが正確で一貫しているほど、出発間際に問題が表れる前に、パターンを見つけて先回りできます。Seth は、このシナリオに合わせて大量の合成データを作ったと説明しました。ATA は Air Transport Association の略で、コードは階層的で複雑です。

1. 整備の信頼性管理ソフトウェアを見せます。定期点検で、3 番ブレーキが摩耗限界に近いと確認された例です。エンジニアは台帳に 32-00 とコード化しました。降着装置の一部としては技術的に正しいものの、32-40 のほうがより正確です。テキストで入るデータなので、テキストから ATA コードを推定するエージェントを作りました。エンジニアが常に主導権を持ち、確認して正誤を判断します。
2. Microsoft Foundry（エージェントの構築、最適化、学習を 1 つのサービスで行う場）で、Agents ペインから「Alaska ATA agent」を開きます。**Traces** を使うとエージェントの内部が見えます。開いておいたトレースには、実行全体が表示され、ATA コードなどを含む Alaska IQ の取得も含まれます。
3. エージェントが動いていると分かるだけでは不十分なため、採点用の**ルーブリック**を作りました。Foundry が作成し、人が検証もできます。確認する項目のうち、正しい ATA コードが最も重要で、Alaska IQ に含まれる社内独自のコードも重要です。最初に作った素朴なエージェントで実行すると、結果は期待より良くありませんでした。
4. 精度を上げる方法は 2 つあります。指示やツールの説明といったエージェントの資産を直す方法と、モデルを直す方法です。まず資産を直します。**Foundry Optimizer** は、エージェントを見て、システムプロンプトとツールの説明を反復的に修正します。多くの内容が変わり、精度は大幅に向上しました。使ったのはフロンティアモデルの GPT-6 Astra（聞こえたまま）です。ただし、指示が増えて事前に読み込むトークンが増えたため、入出力のトークンコストは少し上がりました。
5. 次はモデルを学習します。指示に多くの内容があれば、それをモデルの重みに持たせられるサインだと Seth は述べました。MAI Code 2 Flash で学習ジョブを実行し、モニターで指標が上がるのを確認します。結果は、ATA コードの完全一致が 97%、コーディンググループが 93 でした（聞こえたまま）。Seth は「これが学習した MAI Code 2 だ」と述べ、これを繰り返すほど効率が上がると語りました。

### 6.8 Agent 365 の管理者向けデモ（AT&T：Vandana Sharma と Jeremy Legg）

Vandana は、Agent 365 を、Microsoft と非 Microsoft のサービスをまたぐエージェントを、管理者が見て、管理し、統制する可観測性プラットフォームだと説明しました。コネクテッドプラットフォームの拡張により、画面に見える Databricks のようなサービスの洞察も深く得られます。

2. エージェントにつながるものはすべて、エージェントマップで見られます。ツール、リソース、人、AI モデルです。赤い線が例外やエラーを示し、トラブルシューティングの手がかりになります。Jeremy は、規模で動かすにはエージェントが何をしているかだけでなく、何をすべきでないかも把握する必要があり、意図と実際の結果を突き合わせるこのオントロジーが重要だと述べました。
3. **Action Center** が、対応が必要なものを集めます。カテゴリ別にグループ化し、優先度を付け、次の手順も示します。例として、90 日間使われていないエージェントのアラートを見ます。しきい値は管理者が調整できます。個別に追いかける代わりに、クリーンアップの自動化を設定でき、所有者への通知、アイドルなエージェントのブロック、不要なものの削除を行って、散らかりとリスクを減らします。Jeremy は、忘れられたエージェントは「ローグエージェント」になり得ると述べ、デジタル従業員のようなもので、システムへの権限や認証を持ち続けるため、可観測性と自動対応が必要だと話しました。
4. コストでは、最近コストが急増したエージェントが表示されます。急増は常に悪いわけではありませんが、管理者の制御が必要です。2 つのエージェントが最近別のモデルへ切り替えていました。グラフには、3 つのケースの支出予測が出ます。何もしない場合、以前のモデルに戻した場合、急増の直前の価格です。
5. 支出ポリシーを設定すると、2 つのエージェントがしきい値に達した時点で、適切な担当者に通知されます。Microsoft のエージェントでは、さらに上限（ハードリミット）を設定でき、上限に達すると利用がそこで止まります。**支出グループ**を使うと、ビジネスユーザーが日々の予算を設定し、管理者はガードレールを置けます。Jeremy は、CTO や CIO にとって、CFO を満足させるための機能だと述べ、コストと、会社に生む便益や収益の透明性が必要だと話しました。

### 6.9 Agent 365 Business Analytics（Stephanie Cronin）

Stephanie は、IT 管理者に続き、ビジネスリーダーの立場で見せました。R&D オペレーションのリーダーが、来月の AI 予算を受け取ったところから始まります。

1. R&D に絞った Business Analytics アプリの概要ページに、Copilot、Cowork、GitHub Copilot、エージェントにわたる支出、利用、価値が表示されます。
2. 「コストと予測」で、各サービスからモデルまで 1 ドルの流れを追います。Copilot Cowork は R&D の現在の利用の 39% です。
3. **ユースケース要約マップ**で、タスクの推論により、R&D が Cowork を何に使っているか（例：仮説検証）が分かり、コストのすぐ隣に価値が並びます。価値の計算方法は、リーダー自身のタスク時間とコストで決められ、事業に合った値になります。これは仕事の価値の保守的な見積もりであり、現金の節約ではありません。
4. 前のチャートに戻ると、Copilot Cowork の利用はいくつかのモデルに分かれています。これは自動モデル選択がタスクに合わせて選んでいる結果で、価値とコストを最適化します。
5. GitHub Copilot では、コストの要因となるグループと職種が見え、チームとエンジニアリングが該当します。コストとクレジットを時系列で見ると、月次の利用が増え続けています。他のサービスの余地を残す必要があるため、低コストのモデル（トランスクリプトでは "lower-cost cloud models" と聞こえ、表記が確定できません）を使うモデルの組み合わせで、カスタム予測を実行します。予算への大きな影響が直ちに見えます。仕事への影響を確かめるため、実行前に予測をエンジニアリング部門のヘッドに送り、パイロットや評価で出力品質と事業継続性を確認してもらいます。
6. エージェントのレジストリでは、Microsoft と非 Microsoft のエージェントを 1 つの画面で見られます。Copilot Studio で作ったエージェントは、コスト、仕事を示すユースケース要約、モデルのインサイト、グループ比較が見えます。コストが Copilot Studio から直接取得されるため、支出アラートや、到達したら支出を止める上限を設定できます。
7. Agent 365 はオープンな設計です。Amazon Bedrock 上に作られた「trial recruitment agent」は、コネクテッドプラットフォームから共有された情報で、推定コストなどが見え、しきい値に達したら関係者へ通知する支出アラートを設定できます。プラットフォームが多く共有するほど、Agent 365 が提供できるコントロールも増えます。
8. リーダーは、エンジニアリングの Copilot Cowork 利用に対する支出ポリシーをすでに作っています。月次の上限があり、コストセンターに紐づく Azure サブスクリプションを通じてエンジニアリングチームに課金（チャージバック）されます。「見て、予測して、予算を組み、課金する」という流れです。
9. 提供時期：ここまで見せた内容は、今日から Frontier Public Preview で利用できます。委任された支出ポリシーと、非 Microsoft エージェントのコスト可視化は、12 月に提供予定です。

### 6.10 Agent 365 のセキュリティ機能（Yina Arenas）

1. エージェントのレジストリで、組織全体のエージェントを見て管理できます。
2. **Shadow AI** で、従業員のデバイス上で動くエージェントを検出します。検出できるローカルのエージェントの種類を広げ、合計 65 種類になりました（OpenClaw、OpenAI、Perplexity などを含む）。OpenClaw を開くと、そのエージェントの種類が展開されているデバイスと、注意が必要な箇所がすぐに分かります。
3. Microsoft は、ローカルのエージェントを含むすべての管理対象エージェントに、**動的なエージェントリスク**を導入します。ランタイム、露出、潜在的な影響範囲（blast radius）を統合し、全体像のリスクを示します。関連インシデントは、セキュリティチームがすでに対応している同じインシデントで示されるため、IT とセキュリティが同じ優先度のリストとリスク評価で動けます。リスクは、エージェントの状態の変化に合わせて追従します。
4. IT は、デバイス上のエージェントも統制できます。Intune との統合により、エージェントのブロック、非準拠デバイスのフラグ付け、Windows の MXC によるエージェントのアクセス範囲の制限ができます。適用して完了です。IT とセキュリティが、同じ優先度のインベントリ、完全なリスク把握、ポリシーで動けるのが価値だと述べました。

### 6.11 Perception（David Weston）

David は、攻撃者が機械の速度で動くため、防御側が同じ速さで動けるよう Perception を作ったと述べて始めました。

**製品の紹介**

1. Perception では、質問できるほか、個別のエージェントやエージェントのチームに仕事を委任できます。自動でトリガーするよう設定でき、人間のセキュリティチームのようにチームとして管理できます。
2. エージェントは、人間のセキュリティチームの動き方に倣って作られています。**Blue チーム**は、専門家のように探索、検知、調査し、仕事を委任できます。**Red チーム**は、環境を能動的に分析してリスクを示す、熟練のペンテスターのようなエージェントで、脅威インテリジェンスを使って高度な攻撃を模倣することもできます。**Green** は「修復担当」で、セキュリティ態勢の修復、コードの修正、検知の支援などを行います。
3. **プレイブック**は、探索や分析のような高度なタスクを行う独自のチームを作る仕組みです。David の「お気に入り」のプレイブックでは、コストと時間が透過的に見え、いつ動作させるかのトリガーも設定できます。Threat Intelligence エージェント、Recon エージェント、Web App Pen Test エージェント（検知、作成、態勢）が関わっています。
4. 「フロンティアエンジニアの受信箱」は、エージェントを管理し、人間の関与（human-in-the-loop）や入力が必要なものを確認し、タスクを委任できるかんばんボードです。
5. FinOps ダッシュボードは、どのエージェントが動き、いくらかかり、成果が何だったかを示します。この情報は A365（Agent 365）にも反映されます。

**シナリオ：Caldova のセキュリティエンジニア**

David は Caldova の Frontier Security Engineer の立場で、2 つの仕事（環境を守ること、検知と対応）を見せました。

1. Perception は、懸念すべきこととして、全社への Patch Tuesday の配信があり、その中に実際に悪用されている脆弱性が含まれていると示します。
2. Perception のセッションを開くと、どのマシンにパッチが当たっていて、どれが脆弱かを分析します。レポートでは、クライアントデバイスの約 52,000 台と数千台のサーバーが、まだ確認が必要です。今回の Patch Tuesday は大きく、約 1,500 件の CVE が含まれます。露出、重大度、脅威インテリジェンスによる悪用状況から、すぐに配信すべきパッチを決めます。通常は PowerShell を書き、分析し、CVE を調べる必要があった作業を、エージェントが 1 つの画面にまとめます。
3. すぐに配信します。クライアントには重大なパッチが適用され始めます。サーバーには、影響を分析する時間を稼ぐため、新しい**エンドポイントシールド**技術で保護するという、やや保守的な対応をとります。
4. 次に、検知と対応の仕事に切り替えます。トリアージが必要な開いているケースが多数あります。エージェントチームに、新しいアラートごとに、トリアージ、攻撃調査、検知作成のエージェントが動くようトリガーを設定します。調査の内容により、10 分から 1 時間かかると表示されます。
5. 最初の調査は、サードパーティのデータの利用例です。Okta のデータと AWS のクラウドデータの利用に基づいて検知されたアラートで、Perception はトリアージを済ませ、レポートと所見を作り、必要ならカスタム検知も作成します。攻撃調査エージェントが所見をまとめ、検知作成エージェントが補強を始めます。
6. 新しい検知レポートで、検知はうまくできたが、攻撃チェーン全体をカバーする検知を足せば、見つけたときより良い状態にできる、という提案が出ます。従来は熟練のセキュリティエンジニアで、カスタムコードも書ける人が必要でした。API とアクチュエーター、使われているコーディングモデルを組み合わせ、攻撃チェーン全体をカバーするカスタム検知を書けます。
7. 機微な操作のため、David は人間が関与し、ルールをレビューして、ワンクリックで公開します。誤検知のチェックも行われています。結果、3 つの新しい検知がデプロイされ、検知の範囲が広がりました。
