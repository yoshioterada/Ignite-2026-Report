# BRK259 See how the Microsoft Copilot harness powers Copilot Studio

## 1. はじめに

このセッションは、Copilot Studio の新しいエージェント実行基盤である **Microsoft Copilot harness**（Microsoft Copilot SDK の上に構築されたもの）を解説し、その上で動く 3 つの機能、**dynamic task agents**、**hooks**、**variables** を紹介する内容です。dynamic task agents と hooks についてはライブデモがあります。なぜ従来の標準 harness を延長せず、SDK の上に作り直したのか、その結果としてどんな効果が出ているのかが、前半の中心です。

結論を先に言えば、発表者は、新しい harness は標準 harness より品質が上がり、さらに入力トークンの面でコスト効率が約 45% 改善したと説明しています。Copilot Studio でエージェントを作る人（メーカー）や、その運用・ガバナンスを担う人に向けた内容です。

## 4. 発表者が伝えたいメッセージ

発表者は、モデルの進化に合わせて、エージェントを動かす「harness」も変わる必要があったと説明しています。チャット型モデルの時代の harness は、モデルの粗い部分を補うために、具体的で指示的でなければなりませんでした。推論モデルが登場した現在は、モデルが全体像を持ち、自ら反復できる**推論型の harness** が必要になります。Copilot Studio は標準 harness を改良し続ける道ではなく、Microsoft Copilot SDK の上に新しく作る道を選び、その方が価値と成果をはるかに速く得られたと述べています。

もう一つの軸は、**非決定的な部分（モデルの判断）と決定的な部分（確実に実行したい処理）のバランス**です。hooks と variables は、どちらもモデルに任せたくない部分を決定的にするための機能として紹介されています。さらに、Copilot Studio は単一のモデルベンダーにロックインされない形でモデルを提供し、auto によりコストと品質の改善を利用者に引き渡す、という立場が語られています。

## 5. 発表内容の詳細

### 5.1 harness とは何か: チャット型から推論型へ

発表者は、約 4 年前に ChatGPT が登場し、まもなく Copilot が出たことを振り返っています。当時のチャット型モデルでは、モデルの不安定な部分に足場を作るため、harness は具体的で指示的な必要がありました。例えば、ユーザーのプロンプトを複数の順番付きプロンプトに分解して大規模言語モデルに送ります。チューニングしやすく、ガードしやすく、応答も速いという利点がありますが、モデルがユーザーの目的の全体像を持てない、という欠点がありました。

その後、2024 年 12 月に OpenAI が最初の推論モデル（o1）を出し、2025 年 12 月には Claude Code と Cowork が強力な推論モデルを使うコーディングエージェントを広めました。こうしたモデルには**推論型の harness** が必要です。中核は **agentic loop** で、モデルが全体像を保ちながら反復し、自分でタスクが終わったと判断したときか、予算上限やタイムアウトに達したときだけタスクを完了させます。

Copilot Studio は 2023 年に、チャット型の発想で標準 harness をリリースしていました。モデルが強力になり、より自律的に動けるようになったことを受け、次の 2 択になったと説明しています。

* 標準 harness を少しずつ進化させる
* Microsoft Copilot SDK の上に新しく作る

社内で議論し、両方を試した結果、SDK のほうが、はるかに良い価値と成果をはるかに速く得られました。SDK は最初からコーディングエージェント向けに作られており、標準 harness は当時としては優れた技術だったが時代が変わった、と述べています。

### 5.2 新しい harness の構成

動作の流れは次のとおりです。

1. アプリ（チャネル）で、トリガーまたはユーザーのプロンプトが処理を開始する
2. それが harness に送られる。harness は Microsoft Copilot SDK の上に構築されている
3. ループが始まり、入力とコンテキストがモデルに送られる
4. モデルが計画・推論し、応答を harness に返す
5. 多くの場合、harness がツールを呼び出し、応答を受け取り、新しいコンテキストを組み直して再びモデルに送る。これを繰り返す

さらに次の要素があります。

* **サンドボックス**: エージェントのセッションが始まるたびに、Azure コンテナーでサンドボックスを作る。CLI とファイルシステムなど、コーディングエージェントの力を業務プロセスの自動化にも使える。大量のデータをディスクに取り込み、エージェントが順番に読み進めて処理する仕組みもある
* **ガバナンス**: 「Microsoft は信頼で動く」という考えのもと、ランタイムがすべてのモデル呼び出しとモデル応答を統制する。モデルに送られるものと返ってくるものの両方について、DLP、秘密度ラベル、監査をサポートする

### 5.3 社内での広がりと、SDK の使い方

Copilot Studio は、Microsoft Copilot SDK の上に構築した社内最初のチームの 1 つです。コーディングだけでなく業務プロセス自動化にも使えることが示されたあと、Microsoft 内で急速に広がり、現在は Copilot Studio、GitHub、Microsoft Foundry、Copilot Cowork、Copilot Code が SDK を使っています。

SDK をそのまま使うのではなく、次の 2 つの方針で用途に合わせています。

1. **システムプロンプトをモジュール式に使う。** SDK 付属のシステムプロンプトの多くの部分は使うが、顧客が Copilot Studio に求める用途にはコーディング寄りすぎる部分は含めない。業務プロセス革新に向けて足りない部分は追加する
2. **GitHub Copilot チームの成果を選別して取り込む。** GitHub Copilot チームは革新と出荷が速く、SDK に新しい価値を入れ続けている。密な関係を持ち、リポジトリにもアクセスできるため、Copilot Studio のユースケースに良いかをすばやく検証する。自動的には取り込まず、テストして評価し、価値があれば素早く取り込み、なければ見送る

### 5.4 成果: 品質とコスト効率

オフライン評価セット（約 500 のテストケースを定期的に実行。顧客に見られる幅広い業務プロセスのユースケースを含む）で、標準 harness と新しい Microsoft Copilot harness を比べています。

* **品質**: ナレッジの利用、コーディングを伴う分析、ファイルからの情報処理、複数のツール呼び出しのいずれでも向上
* **コスト効率**: タスク完了に必要な**入力トークンで約 45% の効率向上**。入力トークンは、モデルのトークン消費を Copilot credits（金額）に換算するときに最も高価なトークンだと説明されています

45% の効率向上の理由は次のとおりです。agentic loop により、モデルは標準 harness より多くの呼び出しをします（品質向上の主な理由は、これと、サンドボックスの CLI とファイルシステム）。それでもコスト効率が上がるのは、強力なキャッシュと効率的なオーケストレーションを適用できているためです。

> ご参考：発表の最後に、オフライン評価についてさらに詳しいデータを載せたホワイトペーパーとブログ記事があると案内されています。

### 5.5 モデルの扱い: auto

harness には強力なモデルが必要で、「harness とモデルは陰と陽」と説明されています。顧客からは、メーカーに適切なモデルの選び方を教育するのは手間であり、品質を保ちながら使いすぎを避けるために Microsoft に助けてほしい、という声がありました。これに応えるため、最近 **auto** をデフォルトのオプションとしてリリースしました。

* エージェントは、モデルルーティングの改善と、新しいモデルが出るたびの品質・コスト改善の恩恵を受ける
* 現在は、各ラボが少なくとも週に 1 回は新しいモデルを出す時期で、Copilot Studio には、通常ラボの公開と同じ日（数分から 1 時間程度）に出している
* 新しいモデルは品質向上だけでなくコスト効率も高い場合が多く、ラボが競争と成長のために価格を下げる動きもある。auto は、賢くモデルファミリーを選ぶだけでなく、テスト結果に基づいて最新バージョンを使い続けられる
* 単一のモデルベンダーにロックインされない。Anthropic、OpenAI、Mistral、SpaceXAI（聞こえた表記）の最新モデルがあり、他も評価を続けている
* ただ一覧を並べるのではなく、オフライン評価などで精査し、品質とコストの Pareto 効率曲線上の複数の点にまたがるポートフォリオに整えている
* auto でも、表示されるモデルの一覧でも、管理者ポリシーを常に尊重する。明示的にモデルを選ぶ場合のために、分かりやすいカテゴリーを用意している

### 5.7 dynamic task agents

**dynamic task agents** は現在プレビューで、コーディングエージェント（GitHub Copilot など）で知られる概念だと説明されています。Copilot Studio にはすでに child agents / connected agents があり、マルチエージェント構成に便利ですが、別々のエージェントとして接続・管理する手間がありました。dynamic task agents は、その手間を取り除き、**メインのエージェントが、利用者のガイダンスに従って、いつ task agent を使うかを決めます**。task agent は実行時に動的に起動され、別途管理も公開も不要です。

利点は次の 3 点です。

* **結果が速くなる**: 並列化できる作業が大量にあるとき、子エージェントを並列に動かせる
* **独立した判断を得られる**: ほかの要素に影響されずに、特定のコンテキストの確認や推論を独立して行わせたいときに向く
* **コストを下げられる**: モデル選択を指示できる。メインのエージェントをプランナーとして高機能なモデルにし、task agent に安いモデルを使わせる。逆に、メインは基本的なモデルにして、特定のワークフローで高機能なモデルに委任する構成もできる

task agent の使い方は 3 通りです。エージェントの instructions に書く（デモで実施）、いつ使うか／使わないかを書いた再利用可能な skill にする、実行時の特定のプロンプトで依頼する。プレビュー中で、**来月 GA** の予定と述べられています。

### 5.8 multi-agent

新しい harness の Copilot Studio にはすでにマルチエージェント機能があり、次に対応するとされています。

* Agent-to-Agent（A2A）プロトコルのエージェント
* Microsoft Foundry、Microsoft 365 との接続
* Microsoft 365 Agents SDK で作ったエージェント

最近プレビューに入った新機能として、**新しい harness で作った Copilot Studio のエージェントを MCP または A2A として公開**し、Foundry や Copilot などに接続できるようになりました。ユーザーが使いたい場所やインターフェースで、そのエージェントを利用できるという位置づけです。

### 5.9 hooks

**hooks** は、標準 harness の topics に相当するもの、と説明されています。「hooks」は業界で標準になりつつある用語なので、この名前にしたとのことです。対比として、ワークフローの agent node を挙げています。agent node は「決定的なワークフローの中に、推論と判断が必要な非決定的な LLM のステップを入れる」ものです。hooks はその逆で、**非決定的であるべきエージェントの動作の一部を、決定的な処理にフックさせる**ものです。

プレビュー中で、画面で説明された設定項目は次のとおりです。

* **トリガーとなるイベント**: エージェントの開始時、ユーザーのプロンプト送信時、エラー発生時、ツール呼び出しの直前または直後、ツール呼び出しが失敗したときだけ。発表者は「6 つのライフサイクルイベント」と述べています。エージェントがタスクを終えたときのイベントも追加予定（例: 追加ログの収集）で、他のイベントのフィードバックも求めています
* **名前**
* **接続先**: 現在はワークフロー。まもなく、自分で実行する Python スクリプトにも接続できるようになる予定
* **フックが失敗したときの挙動**: エージェントを続行させる（open failure）か、フックが動かなかったことでエージェントを止めてブロックするか

「post tool call」は発表者の個人的なお気に入りで、ツール呼び出しの結果として得た情報を、望まなければモデルに送らないようにできます。例えば、モデルに送りたくない種類のデータをチェックする用途が挙げられました。

### 5.10 variables

**variables** は、静的な値、または実行時に取得した情報で設定される値を、モデルに対して指示的に与える機能です。標準 harness に以前からあり、今回、新しい Microsoft Copilot harness でも使えるようになりました。AI を役立てるには、モデルの非決定性（モデルの強み）と、決定的であるべきものの両方のバランスが必要だ、という考えが背景にあります。

発表で挙がった使い方は次のとおりです。

* エンドユーザーがエージェントを使い始めたときに、そのプロフィール（部署、コストセンター、役職、権限に関すること）を取り込み、常に正確な情報を使わせる
* セッションの種類や利用者によって、呼び出せるツールの一覧を変える
* 知識の種類を変える。例えば HR のエージェントで、グローバルな HR ポリシーと、部署や地域によって異なるポリシーがあるとき、変数で適切な知識だけにスコープする

実行時の誤りが減り、正しい情報を得るための追加の推論が減ることで、コスト効率にもつながります。今日から利用可能で、知識を調整するなど、より簡単な体験が近日追加される予定です。

## 6. デモ・手順

このセッションにはライブデモが 2 つあります（dynamic task agents と hooks）。画面の細部は音声からは確認できないため、語られた内容の範囲で書きます。デモの前に、発表者は観客に挙手を求めて（dynamic task agents を知っているか、child agents や connected agents を使ったことがあるか、など）、内容を調整しています。

### 6.1 デモ 1: dynamic task agents（サプライヤー提案のレビュー）

1. Copilot Studio で、受け取ったサプライヤー提案をレビューするために作ったエージェントを開く。モデル選択は auto。エージェントは複数のナレッジソースを使い、正しいプロセスとポリシーに従うようにしている
2. エージェントの instructions に、「独立した提案レビューには独立したエージェントを使い、それらに安いモデルを割り当てる」という内容を入れている
3. 3 社（聞き取りでは Apex、Meridian、Nimbus）から届いた提案を示し、「推奨を出してほしい」と依頼する
4. chain of thought に、これが task agents を使うのに適した状況だとエージェントが認識する様子が出る。まずナレッジを取得し、安いモデルを使いたいと認識して、task agents に **Haiku**（聞き取りでは「haiku」）を選んだ。子エージェントは並列に動く
5. 各 task agent が 1 社の提案を独立してレビュー、批評、採点するため、他社の提案に影響されない。「running task」の表示は、3 社それぞれに別の task agent があることを示す。メインのエージェントが task agent ごとにコンテキストを用意して渡す
6. 各 task agent がレビューした内容をメインのエージェントに返し、メインが統合して回答する
7. 回答は、**Meridian IT Partners を使うべき**という明確な推奨。比較表を作成し、Nimbus は 2 つのチェックに不合格でスコアが最も低く、Meridian が最も高い。懸念とリスク、理由、次のステップも示された
8. 続けて、プロンプトで task agent を使う例として、別のモデルで批評させる。「この推奨を批評する独立したエージェントを起動して」と依頼する（聞き取りでは「spawn a sole agent」）。子エージェントは Haiku だったので、意図的に**別のモデルプロバイダーのモデル**を選んだ。コスト効率の良い、かなり強力な推論モデル（モデル名は述べられていません）である
9. 結果は、この推奨に同意する内容だった。発表者は、曖昧で複雑な推論をするときに、このような使い方が有効だと説明している

### 6.2 デモ 2: hooks（購買エージェント）

1. 組織の購買を支援するエージェントを開く。hooks は、画面上部の「…」（ellipsis）から hooks を開くと見つかる
2. 新規作成の画面では、フックは現在、イベントの種類でトリガーされると説明された。設定項目（イベント、名前、接続先、失敗時の挙動。5.9 参照）が画面で示された
3. このエージェントには 2 つのフックがある。1 つは**従業員の購買コンテキストを読み込む**フック、もう 1 つは**購買ポリシーを適用する**フック
4. ポリシー適用のフックは、ツール呼び出しの前、特に create purchase order ツールの呼び出しの前に実行される。呼び出されると、ワークフロー「enforce purchase policy」を実行する。失敗時は**ブロック**に設定してあり、フックが動かなければエージェントは何もできない
5. ワークフローの画面も示された。エージェントがフロー（この場合はフック）を呼ぶと、メタデータやパラメーターが含まれる。すべてのフックに入力と出力があり、入力、フック内の処理、エージェントに返る出力が順に見える
6. **比較用: フック無しの同じエージェント。** 自然言語の instructions だけでポリシーを扱わせたもの。「来週入るチームメンバー向けに標準のオンボーディングキットを 8 つ注文して」と依頼したところ、LLM はエージェントに接続されたポリシーとナレッジのドキュメントを確認し、自分に適用される上限を超える金額になると判断した。その過程で多くのツール呼び出しをした。結果として「これはできないが、数を減らして注文するか」と返してきた。そこで数を減らして頼むと、許容範囲と判断した
7. 発表者は、エージェントにすべて任せることが悪いわけではないが、ポリシーを誤って読む、解釈を誤る、ポリシーが複雑だと時間がかかる、トークンを多く消費する、といったリスクがあると説明している
8. **フック有りのエージェントで、同じプロンプトを実行する**（「新しいチームメンバー向けに標準のオンボーディングキットを 8 つ注文して」）。エージェントが動き始め、まもなくフックが実行される。まず、セッション開始のフックが、自分のユーザープロファイルに関するポリシー情報を取得する。その出力として、所属するコストセンター、通貨、上限が 2,000 ポンドであることが表示された
9. 次に、ツール呼び出し前のフックが実行された。発注を行う前に、ブロックすべきだと判定された。その出力は `continue false`、permission decision は `deny`。購買注文は作成されなかった
10. 「では 5 キットだけ購入して」と頼む。再び最初のフックがすぐ実行され、ツール呼び出し前のフックも実行された。今回は `continue true` で、購入が実際に通ったことの確認まではできないものの、購入依頼は適切なチームに提出された。前回は「ポリシー違反」と止められたのに対し、今回は処理を続けられた

## 7. 注意点・発表者の気付き

* エージェントにポリシーの判断をすべて任せると、ポリシーの誤読、解釈の誤り、複雑なポリシーでの遅延、トークン消費の増加といったリスクがあります。そこで、**決定的であるべき部分**を確実に実行したい場合に hooks を使う、という考え方です
* hooks の失敗時挙動（続行するか、ブロックするか）は選べます。デモでは購買ポリシーのフックをブロックに設定しています
* hooks と dynamic task agents は、どちらもプレビューで、来月 GA の見込みです。現時点で使えるフックの接続先はワークフローで、Python スクリプトは「まもなく」の扱いです
* 新しい Copilot harness で、モデルの呼び出しは標準 harness より多くなります。それでも入力トークンのコストが下がるのは、キャッシュと効率的なオーケストレーションによると説明されています
* 発表者は、「AI やエージェントはすべてのステップの正解にはならない」と述べており、エージェント、ワークフロー、アプリを適材適所で組み合わせる立場です
* 現状、自律型エージェントのセッションは開始のたびに新規です。継続セッションは今後の予定です

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

* **品質向上**: 約 500 のオフライン評価ケースで、ナレッジ利用、コーディングを伴う分析、ファイルの処理、複数ツール呼び出しのいずれも標準 harness より向上
* **コスト効率**: 入力トークンで約 45% の効率向上
* **モデル選択の負担軽減**: auto がデフォルトで、新モデルの品質・コスト改善を利用者に引き渡す。管理者ポリシーは尊重される。単一ベンダーにロックインされない
* **ガバナンス**: すべてのモデル呼び出しと応答を統制し、DLP、秘密度ラベル、監査をサポート
* **マルチエージェントの運用負荷の軽減**: dynamic task agents は、別エージェントの管理や公開が不要。並列実行による高速化、独立した判断、モデル選択でのコスト最適化が可能
* **決定的な制御**: hooks と variables で、ポリシー適用やユーザープロフィールの取り込みなど、確実に行いたい処理をエージェントの流れの中に入れられる
* **顧客事例**: Wipro は営業の準備作業を減らして人間関係に集中、Worley は情報の収集・検証・処理を自動化して判断が必要な部分に集中、Lumen は初期のプロトタイピング段階（具体的な成果の数値は語られていません）

## 9. まとめ

Copilot Studio は、チャット型だった標準 harness を延長せず、Microsoft Copilot SDK の上に新しい harness を作りました。agentic loop、Azure コンテナーのサンドボックス、モデル呼び出しごとのガバナンスを備え、約 500 のオフライン評価ケースで品質が向上し、入力トークンのコスト効率は約 45% 改善したと説明されています。

その上で、dynamic task agents（並列・独立・低コストな子エージェント）、hooks（エージェントの流れの中の決定的な処理）、variables（実行時の情報でモデルに指示的な値を与える）が紹介され、dynamic task agents と hooks についてはライブデモで動作が示されました。dynamic task agents と hooks は来月 GA の予定です。Copilot Studio は、エージェント単体ではなく、エージェント、ワークフロー、アプリにまたがる業務プロセス革新のプラットフォームだというのが、発表者の位置づけです。
