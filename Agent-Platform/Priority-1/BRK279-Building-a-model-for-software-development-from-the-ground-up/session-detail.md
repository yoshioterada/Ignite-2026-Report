## 5. 発表内容の詳細

### 5.1 なぜ自社でコードモデルを作るのか

開発者は、すでに非常に多くのモデルを使えます。それでも作る理由として、登壇者は「モデルピッカーに 1 つモデルを加えること」ではなく、Copilot での開発者の使い方に合わせてモデルを設計・最適化できる点を挙げます。

ソフトウェア開発はコードを書くだけではありません。大きなコードベースやリポジトリをまたいだ作業、ツール呼び出し、テストの実行、失敗のデバッグ、何度もの反復があります。エージェント型のコーディングでは、1 つのモデルがプロンプトに対して 1 つの良い応答を返すだけでは済みません。そのため、ベンチマークの成績が良くても、開発者体験全体が良くなるとは限りません。

モデルを単独で作ってから後でプロダクトに合わせるのではなく、両者を同時に開発・最適化できる。これが「自社で作る」機会だと説明されています。

### 5.2 モデルを自社で持つことの 3 つの柱

**柱 1: プロダクトに最適化する。** エージェント型コーディングでは、モデルは方程式の一部にすぎません。harness、ツール、コンテキストの組み立て方、リポジトリとのやり取りが、体験に大きく影響します。そのため、本番の agentic harness を、post-training の最初から取り入れます。実際に開発者が使う環境で、学習と評価をします。

**柱 2: トレードオフを制御する。** モデルと推論スタックを自社で持つと、品質、レイテンシ、トークン効率、提供コストのバランスを調整しやすくなります。最も高性能なモデルが、全てのタスクで正解とは限らないからです。例が 2 つ挙げられました。

- Copilot Fusion という自動ルーティングの仕組みで、うまく使われるようにモデルを設計する。全モデルをあらゆる面で最強にするのではなく、品質・速度・効率の面で互いに補完し合う強みを持たせ、モデル群全体を Copilot の体験に向けて最適化する。
- 推論の強度（reasoning effort）。Copilot では low から max までの推論レベルを選べるが、推論が多いほど良い結果になるとは限らず、トークンと待ち時間が増えるだけの場合もある。タスクごとにどれだけの推論が有効かを理解し、品質、応答性、効率のバランスをとる。

**柱 3: より速く学び、改善する。** 実際の開発ワークフローのシグナルから、モデルがどう使われ、どう動いているかが分かります。挙げられたのは、プロダクトでの利用状況、エンゲージメント指標、コードの survival（残存）指標、開発者からの直接のフィードバックです。これを学習に戻し、「出荷して、学んで、改善する」という継続的なサイクルにします。

### 5.4 モデルの学習（Yang）

**学習の全体像。** MAI は最近、frontier レベルの pre-training を発表したと述べられています。この pre-train モデルの上に、SFT と大規模な強化学習（reinforcement learning）による、大規模な post-training を行って、モデルの推論能力を鍛えます。

**コーディングエージェントに必要な 3 つの能力。**

1. **推論（reasoning）:** リクエストを分解して計画にし、プロンプトで指摘された失敗を診断し、推論に基づいて計画を修正する。
2. **行動（actions）:** 実際のエージェント環境（VS Code、Copilot CLI など）で、harness が提供するツールを使う。Web 検索、コードの閲覧、テスト実行、コンパイルなどのうち、各ステップで何を使うべきかを知っている必要がある。ツールの応答から証拠を集め、次の手を決める。環境を変更（インストールなど）することもある。
3. **判断力（judgment）:** 依頼の範囲を逸脱しない。例として、「テストを 1 つ書いて」と頼んだのに 10 個書いてしまう振る舞いは悪い、と説明されています。ユーザーの意図を尊重し、不確実性を管理し、トークンを無駄にしないよう労力を配分する。簡単なタスクでは、余計な応答をせず素早く動く。

**強化学習の例。** 分かりやすい例として、Microsoft の Kiota Python SDK の PR（発話は「Kyota」。音声認識の都合で表記が確定できません）が使われました。

- issue の内容は、「関数が 0 を返すときは 0 として出力すべきで、省略してはいけない。None のときだけ省略すべき。しかし現在のコードは全部省略している」というものです。
- この issue をプロンプトとしてモデルに与え、モデルが複数の試行（rollout）の痕跡（trace）を出します。例では 2 つの試行を想定し、1 つ目は 0 も None も書き出してしまい、2 つ目は None だけを省略し 0 を出力します。
- 単体テストは、合成データから作ることも、issue 自体や GitHub などの記録から得ることもできます。テストを実行すると、1 つ目のパッチの報酬（reward）は 0（失敗）、2 つ目は 1 になります。
- 実際には、1 つの instance に対して数百の rollout とパッチを生成し、テストを実行して報酬の分布を得ます。報酬を、正しいものが有利になるように整形（shaping）し、報酬に基づいてモデルの policy（モデルの重み）を更新します。こうして、モデルは正しい PR の書き方を学びます。
- MAI Code 2 は、実世界の instance を数十万件（発話は "hundreds of thousands"）使って学習されています。

**ベンチマーク用ではなく、実プロダクト用の学習。** モデルとの間に「bridge」を置き、そこに複数の harness をつなぎます。発話で挙げられたのは、Copilot CLI SDK、VS Code、Codex、およびその他です（他の名前は音声認識の都合で確定できません）。モデルがツールを呼びたいときは、bridge を経由して harness 側のノードがツールを実行し、結果を bridge 経由で返します。これをループで繰り返して最終メッセージを出します。実際の harness で学習することで、プロダクトと日常利用に強いモデルになる、という説明です。

**推論の考え方（adaptive thinking）。** 短くも長くも、速くも遅くもできるモデルをどう作るかについて、2 つのレベルで説明されました。

- **問題の難易度に応じたコスト:** 問題への取り組み方を知らなくても、簡単か難しいかを見積もる意図分析（intent analysis）を行います。この見積もりに応じて、簡単な問題には出力が長くなりすぎないようペナルティ（cost）をかけ、難しい問題には長い思考を許します。シナリオごとに数百〜数千の instance でこれを学習し、モデルが適応的な思考を身につけます。
- **推論レベルの非線形な調整:** 当初は low / medium / high のように線形に設計されていましたが、あえて線形ではなくしました。max ではあまりペナルティをかけず、限界まで考えさせて最も堅牢で強力な品質を出させます。low では強くペナルティをかけ、稲妻のように速くします。medium は線形で、多くの人が最もよく使うレベルなので、日常業務向けです。

### 5.5 評価（measurement）

Yanan は、「測定なしでは何も機能しない」と述べ、この枠組みは、GitHub Copilot の harness や自分の harness でモデルを本番に適用するときにも使えると言います。評価の対象や基準を誤ると、モデルを間違った方向に学習させてしまうためです。

**ベンチマーク。**

- 公開ベンチマーク: 学術的なものや、開発者の実際のタスクに基づくもの。発話では「deep suite 1.1」「terminal bench 2.1」などが挙がりました。
- 社内ベンチマーク: ユーザー意図への追従、指示追従、マルチターンの振る舞い、ユーザーの意図を過小に捉えて期待した結果を出さない「過剰設計（over-engineering）」の有無など。コーディング能力の中核と、ユーザー行動の両方を測ります。

**ベンチマーク以外の観点。**

| 観点 | 説明（発話に基づく） |
| ---- | ---- |
| harness | GitHub Copilot 向けに学習するため、GitHub Copilot SDK、CLI、VS Code の harness を学習環境に最初から組み込む。さらに、MCP ツールや新しいツール、skills、agent.md などの指示にも一般化できること（harness generalization）も確認する。harness を変えるとモデルの性能が変わるため、複数の harness で測る |
| pass rate | 100 件のケースのうち、いくつ通るか。ケースごとに、期待する振る舞いを定めた rubric や、複数のベンチマークテストがある。採点して集計したものが品質の中核の指標 |
| solution lines | 発話での表記（音声認識の都合で確定できません）。トークンはコストなので、モデルが必要以上に考えないようにする。簡単なケースでは考えすぎず、複雑なケースでは多くの思考の予算を使う。pass rate だけでなく効率も見る |
| latency | time to first token（2〜3 秒、あるいはそれより速く）と、token 間の時間（完了までの時間を決める）。エンジンや API 層の最適化に時間をかけている。出力トークン数や推論レベルにも関係する |
| cost | harness の一般化、効率、品質、推論レベルの設定の全てが、コストに関係する。最適な価格と性能を目指す |

これらのオフラインの結果で、本番に出すモデルを選び、実際の本番環境で試します。

**MAI Code 2 / Code 2 Flash の結果の位置づけ。** まず、この 2 つのモデルは、frontier の科学研究や、極端に長い時間軸の作業向けにはまだ作られていないと明言されています。エンタープライズの日常業務を代表するベンチマークを選んだという説明です。

- **MAI Code 2:** 発話では、deep suite 1.1、terminal bench 2.1、"Sway Atlas"（音声認識の都合で表記が確定できません）、および「どれだけのコードを本番に出せるか」を測る非公開ベンチマーク Frontier Code 1.1 を使ったとされます。結果は、「GPT 610」と「Opus 55」（いずれも音声認識の都合で表記が確定できません）と同程度か、わずかに下回る程度です。ただし 50% のプロモーションがあり、コストをかなり下げて日常の開発を大規模に支えられる、と説明されました。
- **MAI Code 2 Flash:** 日常的な定型の修正や、的を絞った編集、とくに量が多く、レイテンシに敏感な作業向けです。deep space 1.1、terminal bench 2.0、"space Atlas" の 3 つで測り（発話の綴りのまま。音声認識の都合で確定できません）、チャート上で「HYCU 5.5」と「6 Luna」（同様に表記が確定できません）をわずかに上回ります。コストは、50% プロモーションなしでも安いと説明されています。

### 5.6 オンライン実験（Faith）

**オフラインとオンラインの役割。** オフラインのベンチマークは、制御された環境でモデルやチェックポイントを比べ、退行（regression）を見つけ、有望かどうかを素早く確認する第一段階です。しかし、実際の開発者のワークフローは、言語、コードベース、複雑さが多様です。エージェント型では、モデルだけでなく全体の組み合わせが効きます。そこで、実際の利用データを見ます。見るのは、コード品質だけでなく、次のようなものです。

- エンゲージメント（戻ってきて使い続けるか）
- ユーザーのターン数（モデルとより多くやり取りしているか）
- コードの survival
- レイテンシ
- キャンセル
- そのほかのシグナル

**集計指標が誤解を招く理由。** 本番の指標で 2 つのモデルを並べて、数字が良いほうが良いモデルと決めたくなりますが、次の理由で誤解が生まれます。

1. モデルごとに集まるワークロードが違う。難しい問題には高性能なモデルが、簡単なタスクには速いモデルが選ばれるため、エンゲージメントが低い、キャンセルが多いからといって悪いモデルとは限らない。
2. 環境の影響が大きい。harness、ツール、レイテンシ、提供インフラが体験に影響し、モデルの品質差に見えるものが別の要因の場合がある。

そこで、集計値だけでなく、制御された A/B 実験を使います。公平な比較には、比較可能なユーザー群、テスト対象のモデルを実際に使っているという確信、できるだけ一貫した harness と条件が必要です。

**2 種類の比較。** GitHub Copilot では、自動モデルルーティング（auto model routing）を使って実験します。

| 種類 | 内容 | 分かること |
| ---- | ---- | ---- |
| 直接のモデル比較 | ユーザーをモデル A か B にランダムに割り当て、他の条件をできるだけ揃える | 似たワークロードを扱うときの、モデルどうしの比較（head-to-head） |
| モデルプールの比較 | ユーザーのクエリに対して選択され得るモデルの集合（pool）に、モデルを追加・置換したときの変化を見る。ルーティングのロジックがどのモデルを選ぶかも含めた、全体の体験を測る | Copilot 全体の体験が良くなるか。ただし、新モデルが他の全モデルより良いとは限らない |

**見る指標（4 領域）。**

1. エンゲージメント: 開発者が Copilot を使い続け、戻ってきて作業を始めるか
2. コード品質: 生成コードが受け入れられ、時間が経っても残っているか
3. トークン効率: 仕事を終えるのに必要なトークン数と、ユーザーのコスト
4. ユーザー体験: 応答性と信頼性（レイテンシ、キャンセル、エラー）

**指標の読み方の注意。**

- ユーザー起点のターンが増えるのは、役に立つので繰り返し使っている良い兆候かもしれないが、意図どおりに動かすために行き来が増えているだけの可能性もある。
- トークン使用量が減るのは良さそうだが、コード品質の犠牲になったり、タスクが完了しにくくなったりしているなら良くない。
- ワークロードが多様なので自然な変動があり、変化が統計的に有意か、効果の大きさはどれくらいか、他の指標も一貫した話をしているかに注意する。
- 勝つ実験とは、treatment と control の数字が上回っているだけでなく、全ての証拠を合わせて、トレードオフが利益を上回らない形で、より良い開発者体験を届けられていると言えるものである。これが出荷判断の基準。

**実験の運用。** 5 月以降、数週間ごとに A/B 実験を行い、測定可能な価値が示されたときに小さな改善を出荷してきたそうです。スライドのグラフでは、各点が実験で、ダイヤモンドが出荷した改善、オレンジの丸が本番を上回れなかった実験です。**全ての実験が勝つわけではなく、それは意図的**で、高い基準を設け、本番データで改善に確信が持てたときだけ昇格させます。失敗した実験は、前提を覆し、思いつかなかった改善へ導くことがあるため、試行錯誤をあえて奨励しているとのことです。

出荷した改善の例は 3 つです。

| 例 | 内容 |
| ---- | ---- |
| エンゲージメントと効率 | トークン消費の中央値（median）を減らしつつ、3 日間のエンゲージメントとユーザー起点のターン数を改善した |
| サービング性能 | スループットを 2 倍にし、time to first token と token 間の時間を短縮した |
| コード品質への集中 | 一定時間後にコードが残る割合（code survival rate）を改善し、エラーとターンのキャンセルを減らした |

### 5.7 今後の展望（Faith）

「より高性能なコーディングモデルを作る」にとどまらず、モデルの改善と GitHub Copilot の改善が互いに入力となる、継続学習のシステムを目指すと説明されています。次の 3 つの領域が挙げられました。

1. **モデル能力の向上:** 推論、複数のツール、複数ステップにわたる調整が必要な、複雑で長い時間軸のタスクへ。あわせて、さまざまなモデルのサイズやアーキテクチャも探索する（すべての開発者タスクに同じサイズ・同じ能力が必要なわけではないため）。
2. **実際の開発者から速く学ぶ:** モデルが完成してから反応を見るのではなく、実験的なチェックポイントをもっと早く開発者に使ってもらい、確定前に学習と評価へ戻す。
3. **モデルとプロダクトをさらに近づける:** harness、ツールのコンテキスト、モデルの応答などを別々の取り組みとせず、最初から一緒に設計する。

- 現在のモデルは、提供できる最高の価格性能で出されており、試用を促すために 50% の割引もある。

### 5.9 Q&A

Q&A では、質問の全文が聞き取れない箇所があります。聞き取れた範囲で整理します。

**Q. コードの survival rate はどう測っているのか。**
10 分後、20 分後といった時点で、リポジトリの diff を見て、Copilot が加えた変更が残っているかを調べます。例えば VS Code では、この情報が計測されており、diff が保持されているかを確認できます。生のトークンを記録せずに、モデルが生成したコードのうちリポジトリに残った割合を測る、という説明です。GitHub リポジトリのコミットまで追跡する commit survival rate も見ています。これは、生成コードのうち実際に本番へ入ったものがどれだけかを知るための代理指標（proxy metric）です。

**Q.（shadow での評価に関する質問。全文は聞き取れません）**
shadow の限界として（発表では shadow の定義までは説明されていません）、ユーザーが特定のモデルに返す反応が得られないことが挙げられました。クエリに対する振る舞いは分析できても、とくにマルチターンでは得られる知見が限られます。エージェント型のコーディングでは、モデルがユーザーの環境、リポジトリ、ツールに入る必要があり、全てがクラウドで動いていない限り shadow は難しい、とも説明されています。ツールの最初の呼び出しまでしか応答が得られず、現状では意味のある比較になりにくい、という話です。

**Q. decision model（どのモデルを使うかを決めるモデル）について。**
- 現在の製品は Copilot Fusion です。decision model そのものではなく、他のモデルの上に分類器（classifier）を置き、どのモデルにトラフィックを流すかを決める仕組みだと説明されています。ユーザーのプロンプトから embedding を作り、分類器がユーザーの意図と複雑さを理解します。モデルごとの profile も作られ、他のオンライン指標やランカーと合わせて、価格と性能のバランスが良い判断をします。
- 将来像（まだ作られていない、ビジョンとしての話）として、現状は開発者が、どのモデルか、どの推論レベルか、どのサイズか、価格帯はどうかを選んでいる。これらの判断を decision model のような仕組みが代わりに行い、推論レベルを選ばなくてもよくなる、という構想です。決定層を上に置くか、モデル自体が判断できるようになるかのどちらかです。サイズについても、現在は日常的な開発では Code 2、定型の的を絞った修正では Code 2 Flash とユーザーが選ぶが、オーケストレーション層があれば価格と性能を end-to-end で最適化できます。
- decision model の使いどころ（どの用途が適切か）については、まだ複数の用途で実験中だという発言もありました。

**Q. ベンチマークの評価環境はどうなっているのか。**
エージェント型のベンチマークでは、コンテナのサンドボックスと、そのイメージを使います。イメージにはソースコードと、インストール済みの依存関係が入っており、ベンチマークによっては、モデルに修正させるために依存関係をあえて欠かしてあります。テストケースもあり、採点側が、どのテストが通ったか、いくつのケースを完了したか、または期待する振る舞いの rubric で評価します。harness はこのサンドボックスの一部で、Copilot CLI が、コンテナ内からモデルのエンドポイントを呼びます。モデルは、日常で使うのと全く同じツールを呼べます。

実際に、最新の CLI をコンテナ内で使って確認しており、モデルの退行が見つかることもあります。例えば、モデルが前世代の harness で学習した後、システムプロンプトやツールが変わるなど、多くのモデルに対応する必要から、ミスマッチが起きることがあります。そのため、継続的に行っている実行（発話は聞き取り不明瞭）で早い段階で捉え、モデルと harness を同時に調整して退行を防ぎます。

**Q. 対応するプログラミング言語は。**
幅広い言語を扱え、言語ごとの特別な対応はしていません。モデルは Docker 環境で言語とやり取りするので、各言語用のイメージ（発話は聞き取り不明瞭）があります。その言語の open な PR や issue を合成または収集できれば、そのまま学習に使えるため、自然に多くの言語をカバーします。

**Q. pre-training と post-training、次のモデルの出し方について。**
- pre-training は、Web から集められる知識と社内の高品質なトークンを集めて学習するもので、数カ月と数万の GPU がかかると説明されています。
- シリーズ名の付け方として、Code 1 Flash は別の pre-train モデルの上にあり、Code 2 は新しく学習した、サイズもアーキテクチャも異なる pre-train モデルの上にあると述べられています。
- pre-train の後は、段階的な post-training を、品質と効率が出荷に値すると判断するまで続けます。その後の「アップグレード」（発話は "manual upgrade"。音声認識の都合で表記が確定できません）は、同じ pre-train チェックポイント（または以前の post-train チェックポイント）に、データや RL 環境の調整を加えるものです。例として、MAI Code 2 の後に MAI Code 2.1 を出すことがあり得る、と話されています。一方、例えば MAI 3 を出すときは、新しい pre-train モデルの上に作ることになりそうだとのことです。実際のリリース予定ではなく、仕組みの説明として語られています。
- 補足として、Code 2 は Foundry でも、カスタムチューニング用に利用できるようになる、と述べられています。

**Q. サブエージェントについて。**
サブエージェントは、サポートしたい重要なシナリオの 1 つで、すでにサブエージェントのケースに関する学習データが多くあります。今後は、異なるモデルどうしが連携して動くことを目指します。現状は、うまく動く場合も、そうでない場合もあります。ビジョンとして、複雑な長いタスクの中の単純な部分（リポジトリの探索、bash コマンドの実行と結果の取得など）を小さなモデルに任せ、大きなモデルがその結果を踏まえて推論することで、コストをさらに下げることが挙げられました。これは、まだ進行中の取り組みです。

## 7. 注意点・発表者の気付き

- **ベンチマークの選び方を間違えると、モデルを間違った方向に学習させる。** 評価の対象と基準を先に定義することが重要だと強調されています。
- **オンライン指標は単純比較すると誤る。** モデルごとにワークロードが異なる点と、harness やインフラなどの環境の影響があるため、制御された A/B 実験を使います。ターン数の増加やトークン使用量の減少のように、良いとも悪いとも解釈できる指標があります。
- **統計的有意性と効果の大きさを確認する。** 実験が勝つとは、他の指標とも一貫していて、トレードオフが利益を上回らないことです。
- **多くの実験は勝たない。** それは意図的で、失敗から学ぶことが推奨されています。
- **現時点の位置づけの限界。** MAI Code 2 と Code 2 Flash は、frontier の科学研究や極端に長い時間軸の作業向けにはまだ作られていないと述べられています。
- **harness の世代ずれ。** モデルを前世代の harness で学習した後に harness が変わると、ミスマッチや退行が起きる場合があります。
- **モデルの判断力の課題。** 依頼の範囲外のことをする（テスト 1 つで 10 個書くなど）のを避けたい、と述べられています。また、ほとんどのモデルは今も不確実性が高い、とも言っています。
- **shadow での評価は、エージェント型では難しい。** クラウドで全て動いていない限り、ツール呼び出しまでしか見られません。
- **decision model や、複数モデルの連携は構想の段階。** 発表では、まだ作られていない、あるいは進行中の取り組みとして語られています。

## 9. まとめ

このセッションは、コーディングモデルの MAI Code 2 と MAI Code 2 Flash を題材に、プロダクト（GitHub Copilot）と一緒にモデルを作る意味と、その作り方・測り方を説明したものでした。要点は次のとおりです。

1. モデルは、本番の harness を取り込んだ強化学習で、プロダクトに合わせて作る。推論の量も、タスクの難しさと推論レベルに応じて適応的に調整する。
2. 評価は、公開・社内ベンチマークに加え、harness の一般化、pass rate、トークン効率、レイテンシ、コストの観点で行う。
3. オンラインでは、モデル間の比較とモデルプールの比較の 2 種類の A/B 実験で、エンゲージメント、コード品質、トークン効率、ユーザー体験を総合して判断する。
4. 今後は、モデル能力、開発者からの早い学習、モデルとプロダクトの一体化を進める。
5. 利用者は、50% の割引期間にモデルを試し、GitHub の「MAI code」リポジトリで意見を送れる。enterprise eval program では、自社向けの eval を一緒に作れる。
