# THR861 Frontier open models, production-ready: Fireworks on Foundry

## 1. はじめに

このセッションは、Microsoft Foundry 上で提供されている「Fireworks on Foundry」を紹介する約 25 分のシアターセッションです。オープンモデル（オープンウェイトのモデル）を、評価の段階から本番運用へ進めるために、Fireworks の推論エンジンが Foundry でどう使えるのかが説明されます。内容は、オープンモデルを使う理由、Fireworks on Foundry の特長、GA 以降の更新（新モデル、デプロイ種別、PTU の始めやすさ、spillover）、そしてカスタマーサポート用エージェントのデモです。

オープンモデルに関心があり、コスト・レイテンシ・スループットを踏まえてモデルを選びたい開発者や、Azure 上で本番のエージェントを組む方に向いた内容です。

## 5. 発表内容の詳細

### 5.1 なぜ Microsoft Foundry か

Blanca 氏は、今や誰でもエージェントを作れるので、問題は「成果が出るか」だと切り出します。品質は信頼できるか、コストは予測できるか、来月さらに良いモデルが出たときに作り直さず切り替えられるか、という問いです。その答えとして Microsoft Foundry を「AI アプリとエージェントのファクトリー」と位置づけ、次の 3 つの観点で説明しています。

| 観点 | 説明 |
| --- | --- |
| Choice | Foundry のモデルはオープンで多様。ワークロードごとに適切なモデルを選び、1 つのエージェントシステムで組み合わせ、作り直さずにより良いモデルへ差し替えられる。 |
| Context | Agent service が企業規模でエージェントを動かす。IQ がデータに基づく根拠を与え、Tools と MCP が自社システムにつなぐ。安全性は組み込み。 |
| Continuous improvement | Foundry がエージェントを品質、レイテンシ、コストの観点で評価・最適化し、稼働中も続ける。 |

このセッションは、そのうち Choice（オープンモデル）に絞って掘り下げるものです。また、Foundry はすでに大規模に信頼されており、12 万を超える顧客が利用していると述べています。

### 5.2 なぜ今オープンモデルか

発表では、オープンモデルが戦略的な優位になる理由を 3 つ挙げています。

1. **経済性の再投資。** 主要なオープンウェイトモデルは、実際のワークロードを担えるほどフロンティアモデルに近づいている。量の多い作業には用途に合ったモデルを使い、フロンティアモデルは最も難しい問題のために残す。
2. **専門的なインテリジェンスを自社のものにする。** オープンウェイトなら、モデル、評価、データ、ワークフローを自社の領域に合わせて調整できる。事業が学んだことが、借りている汎用エンドポイントではなく、自社の資産になる。
3. **ロードマップを自分で握る。** 透明性、監査可能性、データ管理が最初から確保でき、モデル、リージョン、アップグレードの道筋を、ロックインをかなり抑えて選べる。

その結果、オープンモデルのエコシステムの速さに追随できる本番向けのプラットフォームが必要になる、というのが Fireworks on Foundry につなげる論旨です。

### 5.3 Fireworks on Foundry

Fireworks on Foundry は、Build での GA 以降、一般提供されています。Fireworks は推論エンジンで、最先端のオープンモデルに対して最高水準の性能を出すと説明され、インターネット規模、1 日あたり 13 兆トークン超で動いているとのことです。強調された点は次の 3 つです。

- Day 0 でのアクセス（実験から本番まで速く到達できる）
- 低レイテンシ・高スループットの提供
- 独自のカスタムウェイトのモデルも動かせる

主要なラボのフロンティアオープンモデルを、Foundry の単一の Azure エンドポイントから使え、「オープンモデル、本番の速度、Azure のガバナンス」を満たすという説明です。最新のモデルとして、次のものが挙がりました（表記は音声認識の都合で確定できないものがあり、聞こえた綴りのまま記載しています）。

| 提供元 | モデル |
| --- | --- |
| DeepSeek | DeepSeek V41 Flash |
| Moonshot AI | Kimi K3.1 Pro |
| Z.AI | GLM 5.3、GLM 5.3 Flash |
| MiniMax | Minimax M3 |
| Alibaba | Queen 3.8 |
| NVIDIA | Nimtron Ultra、Lightning |
| その他 | Google Gamma、OpenAI GPT OSS、Metalama、Muse Glimmer など（全一覧ではないと説明） |

利用方法の特徴は次のとおりです。

- **Day 0 のモデルアクセス:** 最新のモデルがリリースされ次第 Foundry に入る。
- **柔軟なデプロイ:** サーバーレスの従量課金（pay-as-you-go）で始められ、性能を保証したい場合は PTU を選べる。
- **独自ウェイトの持ち込み:** カスタムモデルをここで動かせる。

### 5.4 この組み合わせが選ばれる 4 つの理由（Jet 氏）

Jet 氏は、モデルの選択肢が多いことは出発点にすぎず、差別化の要因は次の 4 点だと説明しています。

1. **Foundry 上のファーストパーティのパートナーシップ。** Foundry ポータルから Fireworks のモデルや他の Foundry モデルを使う際に、持っているクレジットを活かせる（発話では「Mac credits」と聞こえます。詳細は発表では説明されていません）。
2. **最新のモデルを初日から使える。** 最先端（SOTA）のモデルが day 0 または day 1 からプラットフォームで使える。
3. **同じオープンソースモデルで、より高い性能。** Fireworks は Foundry を通じて推論の最適化も担う。顧客ごとに異なるワークロードパターン、レイテンシ、スループット、最初のトークンまでの時間、コストの要件があり、推論エンジンで最適化して大規模に提供する。
4. **自社事業に合わせた専門性を作る。** モデルを学習し、Fireworks on Foundry で本番ワークロード向けにホストできる。

まとめると、差別化の軸は「品質、レイテンシ、スループット、コスト」です。

### 5.5 GA 以降の更新（Blanca 氏）

Build での GA 以降、本番までの道のりの 3 か所で摩擦を取り除いてきたと説明されました。

1. **15 の新しい OSS モデル。** 最新の追加は DeepSeek V41 Flash、Kimi K3.1 Pro、GLM53、GLM53 Flash、Namtron Ultra、Lightning。ワークロードごとに合うモデルを選べる。
2. **Global Standard。** グローバルルーティングで、従量課金の標準デプロイタイプの中で最安・最広のリージョン対応。データゾーン処理が不要なら低コストで動かせる。
3. **Fireworks ネイティブの Responses API パススルー。** リクエスト経路の余分な処理を省くため、レイテンシに敏感なエージェントのワークロードに有利。

### 5.6 Ignite での発表: PTU を小さく始められる

Ignite で、Provisioned Throughput（PTU）をより始めやすくすると発表されました。DeepSeek V41 Flash、Kimi K3、GLM53、GLM53 Flash といった人気のモデルでは、**わずか 5 PTU から始め、1 PTU 単位で増やせます**。対象モデルは今後広げるとのことです。

- 最初の本番サイジングの話し合いから PTU を候補にできる。
- 小さくてレイテンシに敏感なアプリでも、プロビジョンドの性能を使える。
- 需要に合わせて 1 PTU ずつ容量を足せる。

PTU はこれまで大きなコミットメントの判断だったが、今は最初の一歩として手軽になった、という説明です。

### 5.7 PTU spillover（近日公開）

どのワークロードにも、安定した「鼓動」と、ときどきのサージ（ローンチ日や急な拡散など）があります。ピークに合わせると常に過剰な容量を持つことになり、ベースラインに合わせると急増のたびに不安になります。この二者択一をなくすのが **PTU spillover** で、Ignite の直後に fast follow として提供予定とのことです。1 つのルーティングポリシーで、2 つのステップから成ります。

1. まず PTU を使う。プロビジョンした容量が、計画した性能で安定した需要に応える。
2. あふれた分は、互換性のある従量課金（pay-go）のデプロイに流す。アプリは 1 つのエンドポイントのまま、サージが処理される。

そのため、まれなピークをベースラインに含めずに、定常状態に合わせて容量を決められます。対象は PTU の小規模開始と同じモデル（DeepSeek V41 Flash、Kimi K3、GLM53、GLM53 Flash）で、今後広げる予定です。

## 6. デモ・手順

実際のエージェントアプリで、Fireworks のモデルが Foundry 上で動いていることを見せるデモがありました。Jet 氏が、Fireworks 社内でも使っているカスタマーサポート用のエージェント「Ava」（音声認識では「Eva」「Ava」と混在）に話しかける形式です。画面の細部は音声からは確認できません。語られた順番は次のとおりです。

1. Kimi 3.1 について質問すると、Ava は次のように答えました。ネイティブにマルチモーダルなエージェント向けモデルで、パラメーター数 2.8 trillion、コンテキストウィンドウ 100 万トークン。ビジョン、ツール、ファインチューニングに対応し、Azure Foundry で global standard と provisioned、および data zone provisioned の SKU で使える。価格はグローバルで入力 100 万トークンあたり 3 ドルから。
2. 続いて DeepSeek 4.1 Flash について質問すると、Ava は次のように答えました。マルチモーダルな mixture of experts モデルで、バックボーンのパラメーター数は 552 billion。画像とテキストに対応し、コンテキストウィンドウは 100 万トークン。一度にパラメーターの一部のみを有効化して効率よく推論する設計。Azure Foundry では global standard と data zone standard、さらに global と data zone の provisioned で使える。価格はグローバルで入力 100 万トークンあたり 0.375 ドルから。

> 注意：上のモデルの仕様と価格は、デモ中にエージェントが答えた内容をそのまま書いたものです。登壇者が別途スライドで確認したものではありません。

**Ava の裏側の構成**

Jet 氏は、続けて Ava の構成を説明しました。

1. ブラウザのマイクとスピーカーが WebSocket で接続する。
2. 接続先は、Microsoft Foundry 上にあるオーケストレーターエージェントで、Azure AI の Voice Live を使っている。
3. オーケストレーターが、目的別に data agent、doc agent、web agent につながる。
4. doc agent と web agent は、埋め込み（embedding）とリランキング、ライブの Web 検索を担う役割で、Fireworks on Foundry のモデルで動いている。
5. doc agent は GLM 5.3 Flash で動く。web agent も同じ系統のモデルで動くと説明されていますが、聞こえた表記は「GLM 5.3 Fast」で、音声認識の都合で表記が確定できません。

多くの顧客が、用途ごとに異なるモデルを使い、オーケストレーターエージェントと複数の Fireworks on Foundry モデルという似た構造を取っている、と説明しています。data agent については、発表では詳しく触れられていません。

## 7. 注意点・発表者の気付き

- **オープンかフロンティアか、の二択ではない。** 量の多い作業は用途に合ったモデルに任せ、最も難しい問題にフロンティアモデルを使う、というポートフォリオの考え方です。
- **PTU spillover はまだ提供前。** 「Ignite の直後に fast follow」の位置づけで、現時点で使えるのは 5 PTU から始められる点です。
- **Global Standard はデータゾーン処理が不要な場合向け。** 低コストで動かせると説明されています。
- **デモのモデル仕様・価格は、エージェントの発話。** 正確な仕様は、実際のカタログで確認する必要があります（これは補足であり、発表の主張ではありません）。

## 9. まとめ

Blanca 氏は、冒頭の問い「オープンモデルは、どうすれば興味深いものから本番対応になるのか」に対して、次のように整理しています。

1. モデルの選択肢が増え続けている。主要ラボのフロンティアオープンモデルが、単一の Azure エンドポイントから day 0 で使え、自分のウェイトも持ち込める。GA 以降に 15 の新しいオープンモデルが加わった。
2. 提供の仕方がワークロードに合う。Fireworks が global standard と provisioned throughput の推論を最適化し、PTU は 5 PTU から始められ、spillover が近日登場する。

行動の呼びかけは次の 3 ステップです。

1. 自分の Azure サブスクリプションで Fireworks を有効にする。
2. Foundry のカタログからモデルをデプロイする。
3. 実際のワークロードを 1 つ評価し、自社のトラフィックで品質、レイテンシ、スループット、コストを測る。
