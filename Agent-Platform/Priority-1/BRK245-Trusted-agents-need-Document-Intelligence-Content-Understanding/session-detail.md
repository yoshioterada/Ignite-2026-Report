# BRK245 Trusted agents need Document Intelligence & Content Understanding

## 1. はじめに

このセッションは、AI エージェントが業務で使う文書（PDF、スキャン画像、複雑な表など）を、**信頼できる形で構造化データに変える仕組み**として、Azure Document Intelligence と Azure Content Understanding（Microsoft Foundry 上）を紹介する 45 分のブレークアウトです。エージェントが正しく動くには、まず文書から正しく情報を取り出す必要がある、という問題意識から始まります。

発表の構成は、(1) 文書から知識を取り出す 3 つの段階（Parse、Classify、Extract）と今後追加される Parse の新機能、(2) Classify と Extract の説明（プリビルト、カスタム、agentic mode）、(3) 法務向け AI の Legora による採用事例、(4) 2 つの製品が 1 つになるという発表と今後の予定、(5) Q&A です。

メタデータの概要には「ライブデモ」とありますが、文字起こしでは、画面で見せた内容がライブ操作なのか事前に用意した画面なのかは判別できません。語られた範囲で 6 章にまとめます。

## 3. 何に関する発表か

あらゆる業種でエージェントが業務に入っていくなか、エージェントは「見つけ、理解し、行動する」ために情報を必要としますが、その情報はファイルの中に閉じ込められています。読みにくいページ、枠線の無い表、複数のロケール、複数ページに散らばった情報、取り消し線や脚注の解釈、似た内容の見分けなど、非構造化データからの抽出は難しい、という説明です。

1. 信頼できる知識抽出システムに必要な条件

3. Classify（文書内のセクションの識別とルーティング）と Extract（フィールド抽出）
4. Legora の事例（法務 AI での利用）
5. Document Intelligence と Content Understanding の統合、新しい CLI、今後のロードマップ
6. Q&A

## 4. 発表者が伝えたいメッセージ

メッセージは「信頼できるエージェントには、信頼できる知識抽出システムが必要」という点です。発表では「モデルだけではなく、システムが必要」と述べ、信頼のための条件を次のように挙げています。

- 段落、表、フローチャート、数式などを、毎回安定して読み取り、推論できること。需要に応じて拡張できること。
- 抽出内容を、自社のスキーマに合わせられること。例えばレシートの明細行を、自社では「line item」「transaction」「charge line」のどれで呼んでいても、そのスキーマに揃える。
- **信頼度（confidence）スコア**を返し、自社のポリシーに応じて追加レビューに回す判断ができること。
- **情報の出所にさかのぼれる**（監査のためのトレース）こと。
- これらを低い総所有コストで実現すること。

結びでも「信頼できるエージェントには信頼できるシステムが必要」と繰り返し、Azure Document Intelligence and Content Understanding を統合されたソリューションとして紹介しています。

## 5. 発表内容の詳細

### 5.1 3 つの段階：Parse、Classify、Extract

Azure Document Intelligence and Content Understanding を、非構造化コンテンツを、グラウンディング（出所）と信頼度付きの構造化コンテンツに変える知識抽出システムと説明しています。3 つの段階は次のとおりです。

| 段階 | 内容 |
| --- | --- |
| Parse | 文書全体からテキスト、レイアウト、書式の情報を抽出し、コンテキストを作る |
| Classify | 大きな文書のセクションを識別し、セクションごとに適用するアナライザーのテンプレートと手法を決める。セクションはページ単位、ページ内、複数ページにまたがる場合がある |
| Extract | 文書の内容から情報を取り出し、または生成する |

**例：自動車ローンの書類一式**。写真付き ID、収入・居住の証明、保険の約款などを 1 つにまとめた PDF で、情報はどの順番にも現れ、保険会社や発行機関によって形式やテンプレートが異なります。Parse が全体の文字とレイアウトを読み、Classify が、どの部分が銀行関連、ローン申込、本人の同意に当たるかを識別し、それぞれの分析（フィールド抽出）に回します。個別のアナライザーが、スキーマで指定した重要情報を抽出して自社スキーマに関連づけます。結果には、抽出した内容に加え、ページ単位のトレーサビリティ（どのページの、ページ内のどこにあるか）と信頼度スコアが付きます。

### 5.2 エージェントの主なユースケース

多くのユースケースは、次の 2 つに分かれると説明されています。

- **ビジネスプロセスとワークフローの自動化**：請求処理、KYC（本人確認）処理など。文書から特定の情報を抽出・生成する。例として、請求書から Contoso が請求書番号、請求日、金額、ベンダー名、顧客名を抽出したい、という場面が示され、何を抽出するかは組織が決めることだと説明されています（この部分は音声が不明瞭で、細部は確定できません）。
- **ナレッジ抽出**：検索、チャット、e-discovery など。構造を保ち、出所にさかのぼれる正確な文書全体の抽出が必要になる。

どちらでも文書の解析（Parse）の課題は同じで、後半で Legora が、法務 AI とナレッジのユースケースでの経験を話すと予告されています。

### 5.3 Parse：人間のように読む

「エージェントは、読めるものしか推論できない」という考えです。複数列のテキスト、グラフ、ラベル、数式、透かし（watermark）が混じる密なページなど、複雑な入力には、それぞれに合うモデルと手法が必要です。Azure は 10 年以上の経験でこの分野をリードし、投資を続けているとし、複数列と表のような課題は解決済みだと述べています。そのうえで、**次の四半期に製品へ追加予定の Parse の新機能**を紹介しています。

1. **書式の保持（取り消し線など）**：文書の変更を変更管理や監査のために追跡するには、取り消し線のような書式の情報が必要で、特に法務文書のレッドラインで重要です。一方、透かしの文字は抽出内容に混ざってはいけません。次回のリリースでは、スキャンしたページから、テキストとレイアウトに加えてテキストの書式も保持します。応答の Markdown 表現では、取り消し線、太字、隠れた階層が保たれます。
2. **複雑な数式**：数式を LaTeX 構文で抽出し、エージェントが直接読めるようにする。数式の抽出は以前から対応しており、次回のリリースでさらに複雑な式にも拡張される。
3. **入れ子の表と読み取り順**：住宅保険の申込書のように、セルの中に表が埋め込まれた複雑なフォームでも、人間が読む順番どおりにフィールドを返す。入れ子の表を 1 つの実体として識別し、それぞれを独立して解析し、それぞれが自分の読み取り順を持つ。読み取り順が違うと、エージェントを誤らせて重大なエラーになり得る、という説明です。
4. **ハイブリッド表（仮想の行）**：枠線の無い仮想の行を含む表（セルの結合などが原因）。最先端のシステムでも失敗しやすく、値が違う列や行に入ると、エージェントが誤った入力を受け取ります。次回のリリースで、仮想の行を認識して構造情報を保持できるようにする。

### 5.4 Classify（Chu 氏）

実際の業務では、文書や作業は 1 枚の綺麗なフォームではなく、パケット（束）で届きます。そこで Azure Document Intelligence and Content Understanding は、**セクションごとに自動で分割・分類し、その文書タイプに定義したスキーマのアナライザーに回す**分類器を提供しています。

**例：22 ページのローン書類**。申込書、税務フォーム、補足資料などが 1 つになった文書です。

1. 想定するセクションのクラスを、自然言語で定義する（例として、出生証明書、ID、移民関連の問い合わせフォームなど）。
2. 各クラスを、プリビルトまたはカスタムのアナライザーに対応づける。この例では、住宅ローン申込と公共料金の請求書用にカスタムアナライザーを作った。
3. 結果として、移民関連のフォームが正しく識別されてアナライザーに送られ、公共料金の請求書は別のアナライザーに送られて、請求書番号、期日、残高などが抽出された。チェックボックスや署名など、生のテキストを超える情報も取り出せる。
4. 各フィールドは文書内の根拠にさかのぼれ、フィールドごとの信頼度スコアが付く。

### 5.5 Extract：4 つの選択肢

Extract は、Parse と Classify の結果から必要なフィールドを作る段階です。**シンプルさと制御のバランスを選べる 4 つの選択肢**があると説明されています。

| 選択肢 | 内容 |
| --- | --- |
| プリビルト | 一般的な文書向けに、業界のスキーマとドメイン知識を含む、すぐ使えるアナライザー。まずここから始める |
| 自分のスキーマ | 各フィールドの名前を付け、自然言語で説明する |
| ラベル付け | 説明が難しいフィールドでは、サンプルにラベルを付け、そのラベルで抽出を導く |
| agentic mode（プレビュー） | 最も複雑な文書とタスク向けに、高度な推論とツールを使う |

#### 5.5.1 プリビルトのアナライザー

スキーマは「何を抽出するか」は示せますが、数字の並びが口座番号か ID か、小計と税の合計が総額に一致しなければならないか、といったことまでは確実に伝えられません。プリビルトのアナライザーは、そうした実際の文書とルールから得た知識を、調達、税務、本人確認、財務、住宅ローン、契約、個人記録などの分野で提供します。各値には信頼度スコアとグラウンディングが付き、自動化のワークフローに組み込みやすい、という説明です。

Studio では、プリビルトのアナライザーを業界別に試せます。例として、統合された **1099 ブローカレッジの明細**を取り上げ、課税年度、支払者、受取人、口座の詳細といった業界標準のフィールドが返されること、1099-B のページにある枠線の無い仮想の行（Krishna 氏が示したもの）からも、カテゴリ、売却代金などを正確に抽出できることが紹介されました。グラウンディングと信頼度スコアも得られます。

また、**composed analyzer（合成アナライザー）**を使うと、1040、1095-A、W-2 のどのフォームでも、フォームを識別して適切なプリビルトのアナライザーに回します。文書ファミリー全体への単一の入口になります。

**新しいプリビルトの性能（advanced contextualization、プレビュー）**：19 の米国の税務フォームのカテゴリで、1.0 バージョンと比べて次のとおりです（文字起こしでは「text form」と表記されており、音声認識の都合で確定できません）。

| 指標 | 発表された内容 |
| --- | --- |
| 抽出精度 | 1.91 ポイント向上し、平均 F1 が 99.3% |
| コスト | 51% 減 |
| 速度 | 約 2 倍に高速化 |

この技術を、より多くのプリビルト領域とカスタムアナライザーにも広げる予定だとしています。

#### 5.5.2 カスタムアナライザー

プリビルトが合わないときは、フィールド名を付けて、含まれる内容を自然言語で説明します。ほとんどのフィールドは **zero shot**（例なし）で動作します。説明が難しい、抽出漏れがある、信頼度が低いといった場合に、Studio のラベル付けツールでサンプルにラベルを付け、再構築・再実行して精度を上げます。advanced contextualization では、ラベル付けした文書が強化されたスキーマに処理されます。**例そのものはアナライザーに保存されない**ため、効率的で安全に精度を最適化できる、という説明です。

保険の例では、フィールド名だけだと remark フィールドが誤った結果になりました。そこで次の順で試しています。

1. まず推奨される方法として、**フィールドの説明**を明確な言葉に更新する。
2. 次に、Studio の **knowledge タブ**でラベルファイルを用意する。文書をアップロードし、内蔵のツールでフィールドに該当する値をクリックして選び、保存し、アナライザーを再構築する。
3. 結果として remark フィールドが、出所と信頼度スコアとともに正しく抽出された。

#### 5.5.3 agentic mode

標準モードは大半のシナリオに対応します。ただし、人が何度も確認や判断をはさむような複雑な文書や難しいタスクでは、agentic mode が抽出を強化し、精度を上げます。想定されているのは、証拠が複数の表やページに分散している場合や、どの値を採用するかの判断にルールが必要な場合です。例として、支払いルールに照らした請求書のチェックや、「はい」の回答に裏付けの記載が要る申込フォームが挙げられています。

agentic mode は、ツールを使った**推論ループ**を加え、**ナビゲート、調査、計算、検証**を行います。最初のパスで食い違いがあれば、証拠にさかのぼります。「標準モードから始め、精度の向上が最も重要な難しいケースで agentic mode を使う」という使い分けです。

**例：長い請求書**。「買掛金について、何が裏付けられていて、何を保留すべきか」という問いに、請求書の明細 48 行、領収イベント 70 件、適用される多数のルールをまたいで答える場面です。スキーマには、goods、tax、credits、payable、holdback amount に当たる項目を定義します（項目名の区切りは音声から確定できません）。標準モードでは支払関連のフィールドがいくつか欠けましたが、agentic mode をオンにすると、証拠をたどって裏付けのある金額と保留額を正しく計算しました。さらに、定義したフィールドの 1 つとして「レビューのために保留すべき」という推奨も出し、計算も検算します（音声では「Goods plus tax, buyer exemption minus credits equal the supported amount at month end」。式の細部は聞き取りに依存します）。

**信頼度とグラウンディングの使い方**：自社の文書で校正した信頼度スコアにより、しきい値以上のフィールドは自動承認し、残りを二次レビューに回せます。各値はページ内の位置にさかのぼれるため、レビュー担当者がその場で確認でき、監査人も必要な情報を得られます。これらが、企業のワークフローにおける信頼できるエージェントに重要なメタデータだと述べています。

### 5.6 Legora の事例（Aman 氏）

Aman 氏は、Legora を「法務業務のための agentic operating system」と紹介しています。直接販売中心の営業手法で、売上が「1 から 1 億ドル」に達するまでが最速の企業だと述べています（「1」の単位は文字起こしからは分かりません）。

**法務の現状**：Aman 氏は、法務はコーディングと同じ道をたどっており、AI で解ける仕事の複雑さと業界での AI 導入のどちらでも、約 **12 か月遅れ**だと見ています。法務の仕事もソフトウェアエンジニアリングも本質的に「テキスト入力、テキスト出力」で、LLM が得意な種類の仕事だからという説明です。

**Legora の 4 層スタック**

| 層 | 内容 |
| --- | --- |
| LLM | 最下層 |
| agent harness | 法務に特化してカスタマイズ |
| インテリジェンス層 | 法律そのもの（世界各国の判例・先例）と、法律事務所や企業が仕事をする際の組織の知識 |
| オーケストレーション層 | 弁護士が AI で仕事をするために必要なアプリケーションと統合 |

ただし、法務の仕事は、法律事務所や企業の独自の文書の中にあり、その情報は LLM の重みには入っていません。複雑な法務の仕事を AI で行うには、この独自の知識と組み合わせる必要があります。実際の文書は、スキャン画像、複雑な表、取り消し線、レッドラインなどエッジケースだらけで、「AI エージェントは読める情報の質まで」です。

**従来の OCR では足りない**：OCR が返すのはテキストを平坦にしたもので、何が取り消され、何が追加されたかという重要な情報が失われます。これが AI の回答の正誤を分けることがあります。エージェントに必要なのは、**構造化され、検索でき、引用できる**データです。弁護士が AI の出力から、どの文書の、どのページの、どの段落の情報かにさかのぼれる必要があります。そこで「文書には事実があり、エージェントは知性をもたらし、Content Understanding がそれらをつなぐ」という図式です。

**ユーザー体験の例**：弁護士が、数十万のファイルを含むデータルームから「どの契約に change of control（支配権変更）条項があるか」を知りたい場面を挙げ、通常は弁護士が 1 週間かかる作業だと述べています。Microsoft と Legora の組み合わせでは次の流れになります。

1. 弁護士が Copilot で、文書を SharePoint にアップロードして質問する。
2. Copilot が複雑な法務の依頼と認識し、**Legora のプラグイン**経由で Legora にタスクを引き渡す。
3. Legora が SharePoint から、アップロードされた文書をリアルタイムで取り込み、リアルタイムで **Azure Content Understanding** を呼んで解析する。
4. 構造化され検索可能な内容が返り、Legora が LLM と agent harness で読み、推論する。
5. 結果を、Legora で作業を続けるためのリンクと一緒に Microsoft Copilot に返す。より深い分析が必要なら、弁護士は Legora に戻って作業を続ける。

**文書処理パイプライン**：顧客の文書は 3 種類に大別されます。

1. プレーンテキスト、メール、単純な形式のファイル：ローカルで解析する（速くて安い）。
2. 複雑でエッジケースを含む大半の法務文書：**Azure Content Understanding** を使う。
3. 画像を含む文書：ビジョンモデルで解析する。

この 3 種類はすべて 1 つの**文書インデックス**に入り、文書の内容に加えて文書の構造（ページのレイアウト）も保持されます。これにより、エージェントが agentic search と agentic reasoning を実行できる、という説明です。

**Content Understanding を選んだ理由**：提供元の選定は、複数の基準を考える必要があります。精度、取り出せる詳細（構造とページレイアウト）、規模が大きくなるほど重要になるコスト、特にリアルタイムの用途でのレイテンシー、数十万の文書を突発的に処理できる規模、の 5 つです。Legora は定期的に幅広いプロバイダーをベンチマークしており、Azure Content Understanding は 5 つのパラメーター全体で一貫して良いバランスだと述べています。利用が拡大するにつれて経済性が改善し、地域や容量の要件にも対応できたとのことです。

持ち帰ってほしい点は、「法務のエージェントは、読める文書の質までしか良くならない。OCR より多くが必要で、Azure Content Understanding が Legora のエージェントを支えるコンテキスト層になる」ことです。

### 5.7 製品統合、CLI、ロードマップ（Chu 氏）

**統合**：Azure Document Intelligence と Content Understanding は、**1 つの製品になる**と発表されました。Microsoft Foundry と Studio で今日から試せます。read、layout、プリビルトのアナライザーのバージョンを、Document Intelligence と Content Understanding にまたがって 1 か所で選べます。

**新しい CLI**：開発者とコーディングエージェント向けに、**Content Understanding CLI**（プレビュー）を発表しました。Azure Developer CLI（azd）の Foundry 拡張バンドルに含まれ、1 つのコマンドでインストールでき、Bash と PowerShell で動きます。ファイルの解析や、1 つのサンプルからのスキーマ案の作成に使えます。各ステップは単純なコマンドなので、コーディングエージェントが解析、確認、改善、再実行を自力で行えます。

### 5.8 Q&A

**Q1：ADI（Document Intelligence）と Content Understanding の価格が分かりにくい。標準化するのか。**
回答の要点は次のとおりです。

- Document Intelligence は、Parse、Classify、Extract の全体で Microsoft 独自のモデルを使い、定額で課金される。
- Content Understanding では、Parse と Classify は独自のモデルで、フィールド抽出は LLM を使う。そのため LLM は顧客が選んだものを持ち込む（GPT 4.X、5.X など。今後対応モデルを追加する計画）。価格はこの分、分かれている。
- 目的は柔軟性で、Parse だけなら支払いが少なくて済む。そのため Document Intelligence の layout の価格は高めで、Content Understanding は価格を大きく下げた、と説明している（顧客が必要な分だけ払うため）。
- Parse、Classify、Extract の合計は、両方でほぼ同じになり、プラスマイナス 10〜20% 程度。
- ただし、Content Understanding で agentic mode や大きな文書の Parse などの複雑な処理を使うと、LLM の料金が少し高くなる可能性がある。標準的な文書レイアウトでは、総所有コストは同程度になる。
- プラットフォーム料金と標準的な LLM は同じだが、上位のモデルを選べば追加料金になる。

**Q2：Anthropic のモデルに対応するか。**
要望は聞いており、現在はロードマップに入っていないが、お客様のニーズをもっと聞ければ検討する、という回答でした。

**Q3：Foundry へ移ると、ネイティブのマネージドサービスは廃止されるか。**
Azure Document Intelligence は現在 Azure のマネージドサービスとしても提供されており、**継続する。廃止の予定は無い**と回答しています。

## 6. デモ・手順

メタデータの概要にはライブデモとありますが、文字起こしからは、ライブ操作の発話（「見せます」「クリックします」など）がほとんど確認できません。Chu 氏は Studio の画面を使った例を、結果を語る形で紹介しています。画面の細部は音声からは確認できないため、語られた内容の範囲で書きます。

**フィールドの説明とラベル付けでカスタムアナライザーを改善する流れ（保険の例）**

1. フィールド名だけを指定すると、remark フィールドが誤った結果になる。
2. フィールドの説明を明確な言葉に更新する（推奨される最初の方法）。
3. Studio の knowledge タブでラベルファイルを用意する。文書をアップロードし、内蔵のツールでそのフィールドに該当する値をクリックして選び、保存する。
4. アナライザーを再構築する。
5. remark フィールドが、出所と信頼度スコアとともに正しく抽出される。

そのほか、5.4（22 ページのローン書類の分類）、5.5.1（1099 ブローカレッジ明細のプリビルト）、5.5.3（長い請求書の agentic mode）も、画面を示しながら結果を語る形で紹介されています。5.5.1 は Studio の画面です。Content Understanding CLI は、インストールコマンドや具体的な使い方は読み上げられていません。

## 7. 注意点・発表者の気付き

- **モデルではなくシステムとして考える**：信頼度スコア、出所へのトレース、自社スキーマへの整合までを含めて「信頼できる」としています。
- **標準モードから始め、難しいケースで agentic mode を使う**：agentic mode は複数の表やページにまたがる証拠、ルール判断が必要な場合に向いています。
- **フィールドの説明を最初に改善する**：説明を直し、それでも足りない場合にラベル付けを行う、という順番が推奨されています。
- **読み取り順や仮想の行の誤りは、エージェントの誤動作につながる**：入れ子の表やハイブリッド表の誤抽出は深刻だと説明されています。
- **価格の注意**：Content Understanding では、agentic mode や大きな文書の Parse を使うと LLM の料金が上がる可能性があり、上位モデルを選ぶと追加になります。
- 新機能（書式の保持、複雑な数式、入れ子の表、仮想の行）は「次の四半期に追加予定／次回のリリース」と説明されており、発表時点では今後の提供予定です。agentic mode と advanced contextualization はプレビューです。
- Anthropic のモデルは現在ロードマップに入っていません。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

- 非構造化の文書から、グラウンディングと信頼度付きの構造化データを得られる。しきい値以上は自動承認し、残りをレビューに回す運用ができ、出所の確認で監査にも対応できる。
- プリビルトのアナライザー、フィールド説明、ラベル付け、agentic mode から、文書の難しさに応じて選べる。
- 新しいプリビルトでは、19 の米国の税務フォームのカテゴリで平均 F1 99.3%（1.0 から 1.91 ポイント向上）、コスト 51% 減、約 2 倍の速度。
- ラベル付けの例は、アナライザーに保存されない。
- **Legora の事例**：Azure Content Understanding を精度、詳細、コスト、レイテンシー、規模の 5 つの観点で評価し、バランスが良いとしている。利用の拡大とともに経済性が改善し、地域と容量の要件にも対応できた。
- Document Intelligence と Content Understanding を 1 つの場所で使える。

> 補足：Legora の具体的な処理件数や削減時間の実測値は、発表では示されていません（「通常は 1 週間かかる」という例は、想定される作業の例として語られたものです）。

## 9. まとめ

- エージェントは読める情報までしか活用できないため、文書から知識を取り出す仕組みには、信頼度、出所へのトレース、自社スキーマへの整合が必要です。
- 抽出は Parse、Classify、Extract の 3 段階です。Parse には、書式（取り消し線）、複雑な数式、入れ子の表、仮想の行の新機能が予定されています。
- Extract は、プリビルト、スキーマ、ラベル付け、agentic mode（プレビュー）から選べます。標準モードから始め、難しいケースで agentic mode を使います。
- Legora は法務 AI で、OCR では足りない取り消し線や表を含む文書を Azure Content Understanding で解析し、エージェントのコンテキスト層にしています。
- Document Intelligence と Content Understanding は 1 つの製品になります。新しい CLI（プレビュー）も発表され、2027 年第 1 四半期に一部のプレビュー機能の GA が計画されています。
