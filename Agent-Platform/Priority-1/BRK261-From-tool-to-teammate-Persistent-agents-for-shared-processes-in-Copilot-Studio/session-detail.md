# BRK261 From tool to teammate: Persistent agents for shared processes in Copilot Studio

## 1. はじめに

このセッションは、Copilot Studio のエージェントを「ツール」から「デジタルなチームメイト」へ進化させるための考え方と機能を、ライブデモ中心で紹介する 45 分のブレークアウトです。対象は、繰り返し発生する**共有の業務プロセス**（複数人のチームで進める業務）です。個人の生産性向上向けの autopilot とは区別され、Copilot Studio は共有プロセス向け、という位置づけで話が進みます。

登壇者は、チームメイトとしてのエージェントを次の 3 つの観点で説明しています。

1. 同僚のように協働する（agent account による ID、メールボックス、Teams での存在、IT による管理）
2. 従業員のように装備される（skills、plugins、computer use、MCP apps）
3. 仕事を通じて学ぶ（memory）

デモの題材は、Ignite の準備をする launch チームのためのエージェント "Gopher Launch" です。最後には、顧客の Lumen による事例の説明と、導入のための質問リスト、各機能の提供時期のロードマップも示されます。

## 4. 発表者が伝えたいメッセージ

Evan 氏は、エージェントはこの 12〜18 か月でずいぶん進化したものの、いまも「ツール」のように使われていると指摘します。Copilot に貼り付けて、結果をコピーして取り出す、という使い方です。これに対して、エージェントはもっと多くのことができる、デジタルなチームメイトになれる、という考えが語られます。

その根拠として、「人をチームメイトにする方法は、新人を採用するたびに行っているのでわかっている」と説明しています。新入社員にバッジ（身元）、ノート PC、就業規則のハンドブック、メモ用のノート、入れる建物の制限を与えるのと同じことを、エージェントにも行う、という発想です。この対応づけは 5.1 で整理します。

もう 1 つの強調点は、管理のしやすさです。ID、権限、コスト上限、共有範囲、memory の削除といった管理の仕組みが、デモのなかで繰り返し示されます（セッション概要には「makers stay in control」とあります）。

## 5. 発表内容の詳細

### 5.1 新入社員のたとえ：エージェントをチームメイトにするには

Evan 氏は、2007 年に Microsoft に入社したときの持ち物（バッジ、ノート PC、ハンドブック、ノートなど）を例に、新入社員を成功させるための準備を紹介します。エージェントではそれぞれ次のものに対応します。

| 新入社員 | エージェント |
|---|---|
| 青いバッジ（所属の証明） | **agent account**（ID） |
| （職場で働く） | agent account があれば、Office、Outlook、Teams など、チームがすでに働いている場所で動ける |
| ノート PC | エージェントが使う「コンピューター」。API がないときに、Web を見て情報を取るなどに使う |
| 就業規則のハンドブック | **skills**（標準作業手順書。毎回同じやり方で処理するための手順） |
| メモ用のノート | **memory**（やり取りのたびに覚え、学び、改善する） |
| 入れない建物がある | **guardrails**（アクセスできるシステムとできないシステムを決める） |

> 補足：Evan 氏は、自分が入れなかった建物の話を後で関連づけると述べ、ここでは guardrails の例として使っています。

### 5.2 柱 1：同僚のように協働する（agent account）

2026 年のエージェントには何らかの ID が必要で、それが **agent account（エージェントに ID を与える仕組み）** です。**public preview が Frontier で来月から始まる**と発表されています。agent account を持つエージェントは次のようになります。

- Entra ID、メールアドレス、Teams のプレゼンスを持つ
- Teams、Office、Outlook など、チームが使っている場所で働ける
- IT がユーザーと同じように管理（ガバナンス）できる

例として、Ignite の準備に追われるマーケティングマネージャー（音声認識の都合で表記は "Vid" と聞こえます）が挙げられました。複数の発表、ブログ、日程、デモ、リーガルレビューがあり、日付の変更や依頼があるたびにメールの内容を Copilot にコピーし、答えをコピーして関係者に戻す、という状況です。そこで launch チーム全体と一緒に働くエージェントを置くと、この人がボトルネックではなくなり、エージェントが直接チームと協働し、承認が必要なときだけ本人に声をかけます。

### 5.3 agent account と autopilot の違い

Evan 氏は、このあとのデモのまとめとして違いを説明しています。

| 観点 | autopilot | Copilot Studio のエージェント |
|---|---|---|
| 用途 | 個人の生産性 | チームの共有業務プロセス |
| 対象 | あなたのために働く。あなたの働き方を学ぶ | チーム全体から学ぶ |
| 責任 | あなたに対して責任を負う | 作ったチーム（組織）が責任を負う |
| 異動 | 組織変更でもあなたについてくる | 組織変更や引き継ぎがあっても、仕事に残る |

### 5.4 ガバナンス：ユーザーと同じように管理する

Evan 氏が整理した内容は次のとおりです。

- IT 管理者は、誰が何をしたかを確認できる。ドキュメントの編集が人かエージェントか、オーナー、サインインログも見られる
- 条件付きアクセスで、サインインできる場所を制御できる。人と同じように、「Teams からは使えるが Outlook からは使えない」といった設定ができる
- Purview の DLP ポリシーを、人間に対してと同様にエージェントにも適用できる
- エージェントは、作り手や利用者の資格情報ではなく、**自分自身の資格情報**を使う

### 5.5 コストの管理

「支出をどう管理するのか」は顧客からよく聞かれる質問の 1 つだと述べられています。これらは Copilot Studio のエージェントなので、従量課金（consumption）で、実行には **Copilot credits** が必要です。管理者向けの機能は次のとおりです。

1. **支出の可視化**：種類別の内訳と、会話ごとのコストを確認できる。Power Platform Admin Center では、ダウンロードできる consumption report でさらに細かく見られる
2. **エージェント単位の上限**：例えば Gopher Launch にクレジット上限を設定し、しきい値に達するとアラートを受け取り、上限に達した時点で動作を停止する
3. **環境単位の上限**：環境ごとに「X クレジット以上は使わない」と決められる。上限に達すると、テナントのプールからの消費が止まり、割り当てを超えて使わなくなる

### 5.6 柱 2：従業員のように装備する（skills、plugins、computer use、MCP apps）

Evan 氏が説明した内容です。

**skills と plugins**

- skills は、エージェントが標準作業手順書（SOP）に従うための仕組み。例では、チームの SOP である "launch kit checklist" を skill にして、Go for Launch、Events エージェント、さらに Word・Excel・PowerPoint 内の Copilot でも共有できる
- Copilot Studio の編集体験を簡素化するため、tools、knowledge、skills を **plugins** にまとめた。knowledge か tools かを自分で決める必要はなく、plugin を追加すればエージェントがデータと向き合う最適な方法を決める
- skills は自然言語での説明、skill.md や skill フォルダ全体のアップロード、共有されたものの閲覧と共有ができる。この skills は数週間前に public preview になった
- plugins は、Matt 氏の説明では、ツール、MCP サーバー、skills、knowledge の**パッケージングと発見性（discoverability）の仕組み**
- 数週間後には、Microsoft plugin registry で共有された plugins を閲覧できるようになる。この plugins は skills とコネクターを組み合わせたもの

**computer use**

API がないシステムには computer use ツールが向いています。ロードマップとして次が語られました。

| 時期 | 内容 |
|---|---|
| 数週間後 | 公開 Web サイトの閲覧、サイト内のクリック、フォーム入力 |
| 12 月 | Key Vault に保存した資格情報でのサインイン |
| （時期の言及なし） | 操作を記録してエージェントに再現させる teach mode |
| 年末 | エージェント専用の Windows 365 / agents cloud PC。企業のリソースやデスクトップアプリにアクセスし、agent account でサインインする |

**MCP apps**

MCP apps により、エージェントの応答で壁のようなテキストではなく、アプリのようなインタラクティブな UI を返せます。MCP サーバーが MCP app を持っていれば、Copilot Studio のエージェントがそれを会話内に表示できる、と説明されています。Matt 氏は、これはオープン標準の MCP apps を使っていて、リッチな UI を返す MCP サーバーならどれでも表示できると述べています。

## 6. デモ・手順

このセッションにはライブデモがあります（Matt 氏が担当）。画面は音声からは見えないため、以下は発話で語られた範囲です。デモの題材は launch チーム用エージェントで、発話では "Gopher Launch" や "Go for Launch" と聞こえます（音声認識の都合で表記が確定できません）。以下では Gopher Launch とします。

### 6.1 エージェントの設定（Copilot Studio の画面）

1. Gopher Launch は launch チームの launch coordinator で、計画の作成、成果物の追跡、計画が変わったときの関係者への連絡を行う。コミュニケーションから裏側の system of record まで、このプロセスの end to end を担う
2. エージェントに **agent identity** を追加すると、メールアドレス、自分の OneDrive、Exchange を持ち、アドレス帳にも表示される。マネージャー（上述の Vid）がオーナーかつ最終的な管理者で、レポートラインが階層として表示される
3. アカウントを追加するだけで、次の trigger が既定で含まれる。Teams での 1 対 1・グループチャット・チャンネルでのチャット、メールの受信と送信、Word・Excel・PowerPoint・Copilot アプリでの @メンション
4. 常時稼働させるには、recurrence trigger などの trigger を設定する。このチームでは launch の stand-up にこの trigger を使い、Teams チャンネルに投稿している。SharePoint のファイルが更新されたときなど、他のビジネスイベントを trigger にすることもできる
5. 外部システムとの接続は tools と MCP サーバーで行う。例は Dataverse の MCP サーバーで、アクセスできるツールの確認画面がある。認証モードは agent account、end user account、shared account から選ぶ

| 認証モード | 説明（デモでの発言） |
|---|---|
| shared account | 以前は maker's credentials と呼ばれていた。便利だが、作り手の資格情報をその利用者全員が使うことになり、セキュリティとプライバシーのリスクが大きい。多くの IT 管理者はこの機能をオフにしている |
| end user account | エージェントが、やり取りしているエンドユーザーの代わりに動く。強力だが、ユーザーが接続を作る手間があり、接続がタイムアウトし、初回に設定が必要になる |
| agent account | エージェント自身のアカウントで Dataverse の読み取り、書き込み、挿入を行う。ID を与えたときに使えるようになる |

6. バックエンドは Dataverse（どんな system of record でもよいと述べている）。"Go for Launch" というソリューションにマーケティングの重要イベント、発表日、日数を計算する列、各 launch のアセット、ブログ記事などが保存されている

### 6.2 Teams でのチャンネル操作

1. launch チームのチャンネルでエージェントを @メンションし、「プロセスの最適化の機会を見ているので、標準のキャンペーンレビューを生成して SharePoint に保存して」と依頼する。人間の判断が必要な箇所には自分をタグ付けするよう依頼もしている
2. エージェントはすぐに返信し、考えている過程が更新されていく。チャンネルで行うのは、全員から見えるようにする透明性のためで、グループチャットを増やすより良いと述べている。1〜2 分かかる処理
3. 待つ間に、stand-up の trigger の結果を示した。毎日チャンネルに、この Ignite までのカウントダウンを投稿し、期限超過などを要約し、担当者にタグ付けして期限と承認状況を知らせる
4. カレンダーの会議も紹介しようとしたが、必要なデータがキャッシュされておらず表示できなかった（Matt 氏が述べています）。伝えたかったのは、**エージェントはユーザーであり、チームメイトである**ことと、招待を作るときに Evan 氏と同じようにエージェントを追加できること
5. エージェントがチャンネルにアクセスできる理由として、Teams の「チームを管理」から「メンバー」を見せた。15 人の owner と 31 人の member の一覧の中に Gopher Launch がいる（テスト用のインスタンスもある）。ユーザーと同じ方法でチームに追加するだけで、投稿や SharePoint へのアクセスが得られる

### 6.3 生成された PowerPoint と Word・Excel・Outlook

1. 生成された PowerPoint は、過去 1 年半ほどの 7 回の launch を分析したもの。予定どおりに出た launch、遅れた launch の統計がある。顧客エビデンスの確認に法務と PR との調整が入り、これが遅延の要因で、通常 5〜6 日ほど加わるとエージェントが指摘している
2. エージェントはこのドキュメントの共同作業者として表示され、「ブロックしない、あるいはブログを後で更新する、といった改善の余地がある」というコメントを残している
3. このコメントに返信して「旧式のフォーム提出プロセスをエージェントで効率化する予定。ドキュメントを更新して memory に記録して」と依頼する、という操作を、時間がかかるため**事前に実行した画面**に切り替えて見せた。エージェントはスライド 6 を更新して計画を反映し、memory に保存したと答えている。エージェントはドキュメントだけでなく、計画を持つ system of record とチームへの連絡も更新する
4. Word では、ブログ記事を作成し、ブランドガイドラインを確認し、日付を更新するやり取りがあった。ドキュメントの文章だけでなく、追跡している system of record や下流の更新が忘れられないようにするため、Dataverse にもアクセスできるのが価値だと説明している。Excel でも同じ体験になる
5. Outlook のメールの例：「Ignite のブログ記事が公開されると聞いたが、確認してチームに伝えてほしい」という内容のメールを受け取ったという場面で、Matt 氏はエージェントを @メンションして「対応して」と書き、メールを転送した。返信は待たなかったが、エージェントがメールに返信し、チャンネルで Evan 氏にタグ付けして投稿する（「その通り、今日の後ほど公開される」という内容）と説明している
6. SharePoint でファイルを見ると、変更履歴に Gopher Launch が表示される。「AI エージェントであること」と「誰にレポートするか」が分かるライブのピープルカードがある

### 6.4 管理者の視点

1. **Power Platform Admin Center**：エージェントが動く環境（AP Preview）を開く。アクセスの下に新しく **agents** のセクションがあり、Gopher Launch が一覧にある。「Add Agent」はユーザーを追加するときと同じダイアログで、セキュリティロール（"launch agent" という名前で作成）を設定できる。このロールには、Dataverse テーブルに対して insert と update のみを付与し、delete はできない
2. **Microsoft Admin Center（発話のまま）の agent map**：テナント内のエージェントを視覚的に表示する。Copilot Studio でフィルターし、チャンネルでも絞り込める。Gopher Launch を選んで「view connections」を開くと、使っているユーザーが見える。tools の表示では、Dataverse のツール（レコード作成など）、テナントに追加した際に自動で加わった **Work IQ MCP**、そして共同編集（co-authoring。ドキュメント内のプレゼンスの根拠）が見える。Canva も tool として追加されており、これは end user authentication で構成されている
3. 詳細画面では、instructions、共有先のユーザーを確認できる。このエージェントは全ユーザーに共有されている
4. **共有の設定**：メールアドレスがあるため、Teams で検索すればテナント内の誰でも見つけられる。Copilot Studio の公開直前の画面で、共有先を選ぶ。ユーザーを選び、利用のみか共同編集 (co-edit) を選べる。セキュリティグループに限定することも、org-wide のトグルでテナント全員に開放することもできる。リストに含まれない人には、エージェントが「担当のマネージャー（ここでは Vid）に聞いてください」と答える。このチームメイトは**チームがオーナー**で、1 人だけが更新できるのではない、と強調している
5. **Security タブ**：Purview では、機密ラベル（confidential、general、highly confidential など）を設定し、どのエージェント（特にエージェントユーザー）がどのラベルにアクセスできるかを選べる。エージェントに見せたくないドキュメントは、ラベルで制限でき、エージェントはそれを尊重する
6. **Entra の条件付きアクセス**：Entra はトークン生成を担う。ポリシーの対象に新しく「agents」（agent users）を選び、個別のエージェントを指定できる（ポリシーは保存していない。保存するとデモが失敗するため）。例として Office の生成をブロックする設定を挙げた。テスト、プリプロダクション、本番の各エージェントも選べる

> 補足：ALM は主題ではないとしたうえで、エージェントを pre-prod、test、prod に置くことはサポートされており、テナント内でそれぞれ別のメールアドレスを持つと述べています。

### 6.5 computer use、plugins のデモ

3. plugins の画面は発見性が高く、自分に共有されたもの、テナントで使えるものを見られる。skills は GitHub から見つけたものをアップロード、UI で生成、操作の録画から作成、ゼロから作成、など複数の方法で追加できる
4. **ブラウザーを使った customer evidence request のデモ**：「Woodgrove Bank の customer evidence request を作る」と指示した。keynote の発表とドキュメントで使う予定で、公開は 12-1、引用は Woodgrove Bank の head of digital operations の Isaiah 氏によるもの、という内容。法務部門が Microsoft Forms のフォームでの申請を使っているため、そのフォームに入力させる。数秒でブラウザーのライブビューが表示され、エージェントがフォームを開いて入力し、用途を選択して送信する。エージェントは、これを行ったことを memory に保存する

## 7. 注意点・発表者の気付き

- **共有アカウントのリスク**：shared account（以前の maker's credentials）は便利だが、作り手の資格情報を全員が使うことになるため、セキュリティとプライバシーのリスクが大きい。多くの IT 管理者はオフにしている
- **end user authentication の手間**：ユーザーごとに接続を作る必要があり、接続がタイムアウトし、初回に設定がいる。ただし、ハイブリッドな環境では強力な方法で、agent account を使っても有効
- **エージェントはテナント内で見つけられる**：メールアドレスを持つため、Teams で検索すると誰でも見つけられる。Copilot Studio では、公開の直前に共有先（ユーザー、security group、org-wide）を選べる
- **権限を絞る例**：デモでは、Dataverse のロールに insert と update だけを付与し、delete はできないようにしている
- **機密ラベルと条件付きアクセス**：エージェントに見せたくないドキュメントは Purview のラベルで制限でき、Entra の条件付きアクセスでエージェント単位の制限もできる
- **ライブデモのリスク**：MCP apps のデモはプリプロダクションのビットのため表示されなかった。Lumen の動画も再生できなかった。機能の提供時期は 5.6 と 5.9 のとおり分かれている
- **コストは従量課金**：Copilot credits が必要なため、エージェント単位と環境単位の上限で管理できる

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **ボトルネックの解消**：launch チームの例では、担当者が情報を中継する必要がなくなり、エージェントがチームと直接協働して承認が必要なときだけ声をかけてくる
- **プロセスの end to end での担当**：コミュニケーションから system of record の更新までを 1 つのエージェントが担い、データが断片化する状態を避けられる。Word の文章だけでなく Dataverse も同期される
- **ユーザーと同じ管理**：チームへの追加、共有、権限、ログ、DLP、条件付きアクセスなど、人に対するのと同じ方法で管理できる
- **透明性**：チャンネルでの作業で全員から見える。SharePoint では、誰が変更したかが分かる
- **コストの管理**：支出の可視化と、エージェント／環境ごとの上限
- **再利用**：skills をエージェント間（Go for Launch、Events、Word・Excel・PowerPoint の Copilot）で共有できる
- **学習による改善**：memory で好みやプロセスの記録を蓄積し、instructions を編集せずに改善できる
- **事例（Lumen）**：マーケティングのブランド確認を、Brand Buddy がフルマークアップ付きの PDF で返す（数値的な成果は語られていません）

## 9. まとめ

このセッションは、Copilot Studio のエージェントを、共有の業務プロセスに参加するチームメイトとして扱うことを提案しています。agent account によって、エージェントは Entra ID、メール、カレンダー、Teams のプレゼンスを持ち、Teams、Office、Outlook で人と同じように働き、IT が人と同じように管理します。skills と plugins で SOP を共有し、computer use と MCP apps で API のないシステムやリッチな UI にも対応し、memory でチーム全体の好みや経緯を学びます。

デモのうち、MCP apps と Lumen の動画は表示・再生できませんでしたが、そのほかのデモは最後まで進みました。提供時期は、triggers、skills、tools、memory がいま使え、plugins、computer use、MCP apps が今月、agent accounts が 12 月です。
