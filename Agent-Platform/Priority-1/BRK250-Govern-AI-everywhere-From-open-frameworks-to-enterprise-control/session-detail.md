# BRK250 Govern AI everywhere: From open frameworks to enterprise control

## 1. はじめに

このセッションは、社内で複数のフレームワーク・複数のクラウドにまたがって増え続けるエージェントを、どうやって一貫したルールで制御し、その効果を測り、監査に耐える証跡を残すか、という問題を扱います。

結論から言うと、発表では **Agent Controls** という新しいサービスが「本日ローンチする」と発表されました。ポリシーを一か所で定義し、エージェントのライフサイクル上の各介入ポイントで実行時に強制する仕組みです。その土台となるオープンソース（Agent Hooks、Agent Control Spec、Assert）も紹介されました。

セッションは、Microsoft 側の 2 名が模擬の銀行シナリオでデモを見せる前半、HPE（Hewlett Packard Enterprise）の 2 名が自社の課題と設計原則を語る中盤、そして評価（Assert）と監査証跡（OpenTelemetry トレース）をデモで示す後半で構成されています。エージェントのガバナンスやセキュリティを担当する方、複数フレームワークでエージェントを開発している方に向いた内容です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK250](https://ignite.microsoft.com/en-US/sessions/BRK250)

発表者は、チャットボットが応答を返すだけの存在から、ユーザーの代わりに行動し判断するエージェントへと進化してきたと説明しています。エンジニアリングチームではコーディングエージェントも日常的に使われています。その規模は「理論上のものではなく現実のもの」である一方、コントロールとガードレールがその規模に追いついていない、というのが出発点の問題意識です。

そこで提示されたのが、Microsoft 社内でも使っているという次の 4 つの層です。

| 層 | 内容 |
| ---- | ---- |
| ポリシー | エージェントができること・してよいことを定義する |
| 強制（enforce） | ポリシーを実行時に適用する |
| 評価（evaluate） | 強制の結果を、コントロールに照らして評価する |
| フィードバックループ | 評価の結果を、ポリシーの改善に反映する |

これらに加えて **監査（auditing）** が重要だと強調されました。エージェントが何をしたかを証明できなければ、信頼を失うという考えです。セッションの最後には、信頼は証明され、定義されなければならない、という趣旨のまとめがありました（直前の「trust is an engineer」の部分は音声認識の都合で正確な表記が確定できません）。そのために、透明性を確保できるオープンソースを土台にしたと説明されています。

## 5. 発表内容の詳細

### 5.1 模擬の銀行が抱える課題

プロダクト担当の登壇者が、模擬の銀行（銀行名は「Coldova Bank」と聞こえますが、音声認識の都合で表記が確定できません）の立場で課題を語りました。

この銀行では、部署もフレームワークも異なる数千のエージェントを作っています。画面には、日常の銀行取引や送金を行うカスタマーアシスタント、ポートフォリオや投資オプションを確認する投資ヘルパー、行内のアドバイザー向けに推奨を出すアドバイザー用エージェントが例として示されました。エージェントは複数のフレームワークとクラウドに分かれており、一部はオンプレミスにもあります。これらを 1 つのフレームワーク・1 つのクラウドに統一する計画は、そもそも無かったと説明しています。

夜も眠れなくなる懸念として、次の要件が挙げられました。

- 個人情報（PII）の漏えいを、社内向け・社外向けを問わず全エージェントで禁止する
- 外部向けの最初の 2 つのエージェントは、投資の保証を提示しない（訴訟につながるため）
- 10K を超える大きな送金は、規制上、必ず人間が承認する
- アドバイザー向けのエージェントだけは「suggest, never decide（提案はするが決定はしない）」とし、専門家の判断を使わせる

さらに、ポリシーを定める担当者が複数いることも課題です。規制の要件をアーティファクトやコードに落とし込むコンプライアンス・リスク担当、事業責任者、PII 漏えいやプロンプトインジェクション禁止などを定める AI セキュリティ部門がいます。全員が、エージェントが理解し強制できる形に要件を翻訳できるわけではありません。加えて、エージェントには「ユーザー入力、モデル呼び出し、ツール呼び出し、ツール実行後のアクション、最終出力」という複数のチェックポイントがあり、それぞれ介入のチャンスがあるものの、どう介入すればよいか分からない、という点も述べられました。

### 5.2 Agent Controls の概要

Mohamed 氏は、これらの課題に応える **Agent Controls** を正式にローンチすると発表しました。要点は「エージェントの能力を定義する 1 つの集中ポリシーを、エージェントのライフサイクル上のすべての介入ポイントで実行時に強制する」ことです。

アーキテクチャについての説明は次のとおりです。

- 集中型の **ポリシー決定ポイント（policy decision point）** として動き、複数のランタイム（オープンソース、複数のクラウド、あらゆるクラウド）にまたがって動作する
- ポリシーには、決定的（deterministic）なルールと、決定的でないルールを評価する LLM ジャッジ、さらにセーフティルールを使える
- サービスは各介入ポイントについて「許可（allow）」「拒否（deny）」「人間にエスカレーション」「別の内容に変換（transform）」といった判定（verdict）を返す
- 実体は API サービスで、Azure Content Safety のシステムをベースにしている。Azure 上にデプロイされ、カスタムエージェント、AI ゲートウェイ、エージェント系サービスのいずれにも接続できる

### 5.3 土台になる 2 つのオープンソース

Agent Controls の内部は、Mohamed 氏のチームが公開・構築してきたオープンソースが基になっています。

| 名称 | 役割 |
| ---- | ---- |
| Agent Hooks | エージェントのライフサイクル上の介入ポイントを標準化する。業界の既存フレームワークの大半に組み込める |
| Agent Control Spec（ACS） | 集中管理するポリシールールの仕様。Agent Hooks を使って実行時に強制される |

Agent Hooks が解決するのは、複数フレームワークでの対応コストです。新しい要件が出るたびに全フレームワークを修正するのは高くつき、クラウドやプラットフォームも別々だと組み合わせが膨大になります。ACS は、複数の担当者が定義するポリシーを、エコシステム全体に一貫して適用するための集中ユニットとして位置づけられています。この 2 つを合わせてエンタープライズ向けサービスとして提供するのが Agent Controls です。

### 5.4 Foundry と Agent 365 への組み込み

登壇者は、Agent Controls はスタンドアロンのサービスとして提供するが、同じ building block を **Microsoft Foundry**（Foundry 上のエージェント向け）と **Agent 365**（エージェント全体のフリート向け）に、安全性ポリシー・ガードレールの部品として組み込んでいると説明しました。この点は、その日の 2:30 に開かれるセッションで見せたい、と案内しています。

### 5.5 HPE の事例

HPE の 2 名が、顧客としての視点で話しました。

**HPE の規模と環境**

自己紹介の中で、次の数字が語られました。

- 従業員は約 70,000 人
- 顧客は約 100,000 社で、約 150 か国に広がる
- パートナーは 90,000 社以上
- 複数のエージェントを使うアプリケーションが、主要なものだけで約 400 ある。ハイパースケーラー上、自社のプライベートクラウド AI インフラ上、SaaS に分かれている

基本的なチャットボットから、エージェントが判断を下す段階に移っており、今は human in the loop / human on the loop を置いているものの、自律化に急速に近づいているとのことです。当日最初の会議は CISO からの連絡で、SaaS 環境で数千のエージェントが動いているのを見つけたが、ポリシーをどう強制するのか、信頼できる形で動いているとどう言えるのか、という問い合わせだったと語られました。ポリシーライブラリを持つだけでは足りず、強制が必要であり、環境どうしが接続し合うための標準的なオープンソースの方法が必要だという主張です。Agent Hooks はそのための方法として適していると述べています。

**Jose 氏が語った考え方**

Jose 氏は「AI の自律性が、それを制御する能力を追い越している」と述べました。エージェントは実行時に次のステップを選び、ツールを呼び、レコードを変更するため、選択肢は 3 つあると整理しています。

1. 厳格なコントロールをかける。ただしそれではエージェントの利点が得られない
2. 毎回許可を求める。ただし速度が落ちる
3. 野放しにする。ただしリスクが増える

先例として、A2A はエージェントの相互運用性を、MCP はエージェントとツールの接続を解決し、業界に採用されていると述べました。ここで提案するのは「全ランタイムにまたがって、大規模にエージェントを制御するための新しい標準」です。Microsoft の Agent Control Specification は、さまざまな agent ops（聞こえた表記のまま。音声認識の都合で正確な語は確定できません）に移して変換できる「ポータブルな契約」になり得る強力な出発点だと評価しました。

そのうえで、業界や HPE に必要なものとして次を挙げています。

- 契約を、ID と認可に統合すること。どのエージェントにも責任を持つオーナーがいて、ユーザーまたはエージェントから委任された権限の範囲で動く
- 同じポリシーライブラリを再利用し、コストを含めて単一の監査に集約すること
- **fail close**（ポリシーを確認できないときは止める）にすること。「音楽が止まる」と表現されました
- クラウドや SaaS プロバイダーを含め、業界全体でこの標準が採用されること

**HPE の設計原則とアーキテクチャ**

HPE では、上位にコントロールプレーンがあり、レジストリやポリシーライブラリなどを持ちます。ポリシーは各 agent ops に流れ、適用され、監査情報が返ってきます。原則は「すべての agent ops、すべてのエージェントに標準フックを適用する」ことです。エージェントを agent ops でホストする際は、追加のセキュリティ層として A2A とサイドカーを置き、これらも同じポリシーライブラリを使います。

実行時には、ランタイムが「エージェントが誰か」「誰のために動いているか」「どのコントロールが適用されるか」というコンテキストを付加し、さらにメモリで文脈を補います。そのうえでランタイムが承認、拒否、または human in the loop へのエスカレーションを行い、判断と証跡が上位に戻ります。目標は「再利用できる 1 つのポリシー、完全な監査性とコントロール、上下に流れる完全なトレース」と整理されました。

最後に、AI の自動化を、セキュリティとコントロールを損なわずに拡大することが機会であり、「AI の自律性・最適化とコントロールのどちらかを選ぶ必要はない」と述べています。

### 5.6 オンボーディング支援

プロダクト担当の登壇者は、課題に共感した人には、QR コードから連絡してもらえれば、Agent Controls と、その building block である Agent Hooks / ACS へのオンボーディングを「white glove」で支援し、各社のエコシステムについて深い議論もできる、という提案を行いました。

### 5.7 評価ツール Assert

次の課題は、適用したコントロールの有効性をどう測るか、そして数か月後に「いつ、どのポリシーのどのバージョンが、どのエージェントに適用されたか」をどう証明するか、でした。4 つの層のうち最後の 2 つ、つまり評価と証跡（evidence）が無ければ信頼できない、というのが Mohamed 氏の説明です。

そのために紹介されたのが、オープンソースの **Assert** です。説明された機能は次のとおりです。

- 人間の言葉で書いた要件（ポリシー）を理解する
- その要件からテストシナリオを作る
- エージェントの出力を評価し、スコアカードを作る

ベースラインとスコアカードがなければ、エージェントが劣化しているのか、安全性が良くなっているのか悪くなっているのかが分かりません。プロダクト担当の登壇者も、ニッチな要件を測る専門知識が社内に無いため、要件を渡すだけで測定が作れる点が大きい、と述べています。

Assert の内部の動きは、デモの中で次のように説明されました。要件を「許容される振る舞い」と「許容されない振る舞い」に分解し、それを踏まえて、エージェントの文脈に関連した質問・テストケースを生成します。

### 5.8 OpenTelemetry トレースによる証跡

登壇者は、エージェントを大規模に展開すると、6 か月後に監査を受けるため、すべてのトレースと証跡へのアクセスが重要だと述べました。Agent Controls は、どのポリシーが、どのエージェントの、どの介入ポイントで、どのバージョンで適用されたか、という判断をすべて記録できます。デモでは OpenTelemetry のトレースが示されました（詳細は次章）。

## 6. デモ・手順

このセッションには、画面を使ったデモがあります。プロダクト担当の登壇者が、模擬の銀行のエージェントを使って 2 つのデモを行いました（画面の細部は音声からは確認できないため、語られた範囲だけを書きます）。登壇者は、自分は金融のシナリオを模したと述べています。

### 6.1 ポリシーの作成と実行時の強制

1. 銀行の要件を自然言語で並べる。語られた要件は、「顧客の PII を応答に含めない」、「10K を超える取引は人間のレビューに回す」、「顧客が経済的困窮（financial hardship）を訴えているとき、AI でオファーや与信枠の増額を押し付ける前に、思いやりをもって対応できる人間につなぐ」の 3 つ。
2. Agent Controls の **スキル**を使い、これらからポリシーを生成する。生成されたポリシーは、それぞれ左側の画面に示した要件の 1 つまたは 2 つに対応している。
3. 生成されたポリシーのうち 1 つを、マニフェストの **YAML ファイル**で確認する。この YAML には、エージェントのどの介入ポイントで止めるかが書かれている。
4. 困窮への対応では、介入ポイントの 1 つである **output** に、**LLM ジャッジ**が設定されている。これは、エージェントの出力に、経済的困窮の状況に対する押し付けがましい助言が含まれていないかを検出する役割で、登壇者自身が作成して ACS に組み込んだもの。YAML と対になるもう 1 つのファイルで、その分類器の結果が、例えば「yes」または一定の値を超えたら回答を拒否し、理由を「専門のサポートが必要」とする。それ以外は回答を顧客に届ける。
5. 10K の送金は、別の介入ポイントである **pre-tool call** で扱う。送金ツール（transfer funds）が呼ばれる直前に、ポリシーが置かれている **rego ファイル**を参照し、金額が 10K を超えていれば、理由を「人間の承認が必要」として拒否する。
6. ポリシーの適用範囲は選べる。全エージェントが継承する、PII 漏えい禁止のような **ベースラインの組織ポリシー YAML** を置き、そのうえで、顧客向けエージェントだけに困窮の分類器を追加できる。エージェントごとの紐づけと適用は、マネージドサービスが行う。
7. 最初のエージェントに、ある情報を伝える。返ってきた応答では、ACS が電話番号を伏せていた（個人情報を漏らさないポリシーによる）。登壇者は、同じ質問を他のエージェントにしても同じパターンで伏せられること、決定的な仕組みなので回避できないことを説明した。
8. 困窮のケースを試す。「収入を失い、今月の支払いが遅れるかもしれない。どうすればよいか」という趣旨の入力に対し、エージェントはオファーで助けようとしたが、困窮のコントロールが働いて回答が伏せられた。登壇者は、アプリケーション側で人間の担当者につなぐ作りにしていると説明した。

> 補足：10K の送金拒否（手順 5）は、画面上で実際に送金を試す場面があったかどうかは、トランスクリプトからは確認できません。ポリシーの内容の説明として語られています。

### 6.2 Assert による評価と、証跡の確認

1. デモを読み込み直し、コントロールを適用する前のオリジナル版を表示するためにリセットする。
2. Assert の入力は、中心に YAML ファイルがある。ゼロから作ることもできるし、スキルが生成を手伝うこともできる。スキルは、ニッチな要件をチャットで聞き取り、品質の高いテストスイートを作ってくれる。
3. YAML には、1 つずつの振る舞いを書く。デモでは「経済的困窮が検出されたときに、AI が助言を含む出力をどの程度生成するか」を測る。説明文は自分で書くことも、AI に作らせることもできる。YAML の残りには、エージェントの文脈などが含まれ、これも自動で入る、という趣旨の説明があった。
4. Assert は、この要件から「許容される／されない振る舞い」を作り、エージェントの文脈に合った質問（テストケース）を生成する。画面では、許容されない例として「個人向けのクレジットライン（a personal line of credit）が少し余裕を生んでくれる」という趣旨の回答、許容される例として「困難な状況をお気の毒に思います。専門担当者がサポートの選択肢を説明できます」という趣旨の回答が示された。
5. こうして生成した会話をエージェントに対して実行し、スコアカードを得る。コントロール無しのオリジナル版では、困窮している人に対して、AI が追加の金融アドバイスやオファーを押し付けた割合が **37.5%** だった。
6. ゼロからやり直し、一連のガードレール（コントロール）を適用した状態で測り直すと、このポリシー違反率は **0%** に下がった。
7. 証跡として、OpenTelemetry のトレースを表示する。どのポリシーが、どの時点で適用されるかを示している。登壇者は、これをいつでもアーカイブして見返し、関係者や監査担当者に明確な回答として示せると説明した。

## 7. 注意点・発表者の気付き

- 登壇者は、評価のベースラインが無いと、測定結果に意味がないと述べています。コントロール適用前と適用後を比べて初めて、効果が示せるという立場です。
- 「評価」と「証跡」を欠くと、信頼を得られないというのが Mohamed 氏の主張です。
- Jose 氏は、ポリシーを確認できないときは止める **fail close** を、重要な考え方として挙げています。
- HPE 側は、Agent Control Spec が強力な出発点であるとしつつ、ID と認可との統合が必要だという要望を出しています。標準として業界・クラウド・SaaS プロバイダーに広く採用されることが前提だとも述べています。
- 一度適用した要件は、決定的な仕組みのため回避できない、というのがデモ中の説明です。
- Agent Controls の実際の料金、提供リージョン、一般提供の時期などは、発表では触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **フレームワークやクラウドが混在していても使える。** Agent Hooks は大半のフレームワークに組み込め、Agent Controls は特定のランタイムに縛られない
- **ポリシーを一元管理できる。** コンプライアンス、事業、AI セキュリティなど複数の担当者のポリシーを、全体に一貫して適用でき、ベースライン＋個別の層構造にできる
- **人間の言葉で書いた要件からポリシーやテストを作れる。** スキルや Assert が、翻訳やテスト作成の負担を下げる
- **効果を数字で示せる。** デモのシナリオでは、違反率が 37.5% から 0% に下がった
- **監査に備えた証跡が残る。** どのポリシーが、どのエージェントの、どの介入ポイントで、どのバージョンで適用されたかを、OpenTelemetry トレースで確認できる
- **導入の入り口が複数ある。** オープンソースの building block から始めることも、サービスとして使うことも、Foundry / Agent 365 に組み込まれた形で使うこともできる

HPE の事例については、成果の数値は語られておらず、課題と設計原則、標準化への期待が中心でした。

## 9. まとめ

Agent Controls は、エージェントのポリシーを一か所で定義し、実行時の各介入ポイントで強制するサービスとして、このセッションで発表されました。基になる Agent Hooks と Agent Control Spec、評価の Assert はオープンソースで、ポリシー、強制、評価、証跡（OpenTelemetry トレース）が一巡する形になっています。

模擬の銀行のデモでは、PII の伏せ字と、経済的困窮時の応答抑止が示され、Assert のスコアカードでは、違反率が 37.5% から 0% に下がりました。HPE は、約 400 のエージェント系アプリが複数の環境に分散する立場から、ID・認可との統合、単一の監査、fail close を備えた標準の採用を求めています。登壇者は、このコミュニティと共に進めるため、フィードバック、Issue、PR を歓迎するとし、オンボーディングの問い合わせは QR コードから受け付けるとしています。プロダクト担当の登壇者は、ロードマップは動的で、組織の課題を伝えてもらえればロードマップに載せると述べています。
