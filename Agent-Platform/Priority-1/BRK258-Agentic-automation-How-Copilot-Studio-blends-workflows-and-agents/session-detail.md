ワークフローにエージェントを組み込みたい開発者や IT 担当者が、機能の全体像と、コストの見積もり方まで把握できる構成です。

> Ignite の後で、あなたは何を自動化しますか？

背景として、次の数値が紹介されています。

- McKinsey の最近の調査によると、仕事で使う時間の **57%** は、現在の技術で自動化できる。ただし、仕事の 57% が自動化できるという意味ではなく、タスクの 57% に適用できる自動化がすでにあるという説明です。
- 営業担当者は時間の **14%** を「プロスペクティング」（新しい見込み客や機会の探索）に使っている。オンラインの調査や CRM への手入力が多く、エージェントなら 24 時間、夜間でも実行できる。営業担当者はお客様の課題解決により多くの時間を使えるようになる。
- **2029 年までに 10 億のエージェント** を構築する必要がある（発表者は「キーノートなどでも見た数字」として紹介）。
- 今年だけでも、Microsoft 365 エコシステム内のエージェント活動が **15%** 増えた。

一方で、コスト、ガバナンス、制御の面で課題もあります。たとえば、エージェントがいつ価値を生むかの順序をワークフローで決める、といった形でこれらに対処できるというのが発表者の考えです。

そのうえで、Copilot Studio の「ちょうど良い位置（sweet spot）」は、エージェントとワークフローの中間、つまり両者を組み合わせることだと説明しています。

## 5. 発表内容の詳細

### 5.1 エージェントとワークフローの使い分け

**エージェント** には、指示（instructions）として目標を与え、ツールやスキルを渡します。目標の達成方法は今日と明日で変わることがあり、それが良い面にもなります。例として請求書の自動処理が挙げられています。新しい様式のテンプレートが届いても、エージェントは適応して情報を抽出できます。

**ワークフロー** は、手順の順序が保証されます。「重要な業務プロセスは必ず決まった手順で進めたい。エージェントが急に方向を変えては困る」という場面に向きます。ただし弱点もあり、プロセスに変更や逸脱があると、決められた順序に従えずワークフローが失敗します。

そこで、高レベルの流れをワークフローで定義し、必要な箇所にエージェントを入れる形を勧めています。請求書の例では、プロセス全体は長く複雑でも、請求書の内容の読み取りや 3-way matching はエージェントに任せ、それをワークフローの 1 ステップにする、という構成です。

組み合わせ方は 2 通りあります。

1. ワークフローから始めて、**エージェントをワークフローのステップとして追加する**
2. エージェントにプロセスを統括させたい場合は、**ワークフローをエージェントのツールとして追加する**（エージェントの特定の経路を毎回同じ手順にしたいときに使う）

### 5.2 新しい Workflow Designer

数か月前（"a couple of months ago"）に、新しいデザイナーが公開されたと説明されています。会場に新しいデザイナーを試した人がどれくらいいるか尋ねたところ、「かなりの人数」という反応でした。発表者はフィードバックを歓迎しており、質疑の時間に加えて、その日はブースにもいると案内しています。

**ビジュアル面**
- 自由配置のキャンバスで、業務プロセスを定義する。ステップはどこにでも置ける。
- 既定は横向きのレイアウト。Power Automate 時代からのユーザー向けに、縦向きレイアウトへの切り替えもできる。

**追加できるアクション**
- Power Platform の約 1,000 のコネクタ（※後半のデモ部分では「1,500 を超える」とも説明されています。発表内で数が揃っていません）
- 数式、条件
- 新しい agentic なステップ（このデザイナーの最大の差別化点）

**agentic なステップ（Agentic actions）**

| ステップ | 内容 |
| --- | --- |
| Agent node | 既存の Copilot Studio エージェントをワークフローのステップとして呼び出す。ワークフロー内でインラインに新しいエージェントを定義することもできる |
| Classify | テキスト分類。例として、大量のメールのトリアージ。自然言語で分岐先を記述すると、classify ノードが適切な経路へ振り分ける |
| Extract | ドキュメント理解。サンプル文書を置くと、必要な情報を抽出するようアクションが構成される。非構造化データから構造化データを取り出す |
| Copilot | ワークフローのステップとして Copilot にタスクを委任する。Chat、Cowork、今週発表された autopilot を選べる |

**ステップ単位のテスト**
これまでは、ワークフローを組み立ててからエンドツーエンドでテストする方法でした。現在は、各アクションを個別にインラインでテストできます。指示の変更、モデルの選択、ツールの追加を繰り返す agentic なステップで、毎回全体を実行しなくて済む点が利点だと説明しています。

### 5.3 顧客の利用パターン

決定論的アクションとエージェントを混ぜた利用例として、次の 3 つが紹介されています。

1. **ドキュメントのインテリジェンス（リーガル分野）**：契約書が SharePoint のフォルダーに届くことがトリガー。ワークフロー内のエージェントが契約書を読み、条項やポリシーとの適合を深く推論する。その後は決定論的アクションで、契約書を別の場所に移す、必要なら担当者にエスカレーションするなどを行う。順序は毎回同じ。
2. **メールの自動化**：個人または共有メールボックスから始まるプロセスは多い。エージェントによるアクションがメールを分析して対応を決め、転送や返信の作成などは決定論的なステップにする。
3. **ファイナンス（Excel）**：「財務の世界は Excel で動いている」が、エージェントは Excel の扱いがあまり得意ではない。そこで、エージェントが Excel ファイルを推論して更新し、ファイルの移動や関係者への通知は決定論的アクションで行うワークフローにする。

### 5.4 Copilot Studio Gallery

数週間前に公開された **Copilot Studio Gallery** は、Microsoft が作成したワークフローとエージェントの厳選セットで、自分の環境にインポートできます。エージェントとワークフローの作り方のベストプラクティスも含まれています。ブースで「より多くの使用例とベストプラクティスがほしい」という質問が多かったことが、公開の背景として語られています。Gallery は開かれていて、自分が作ったものをアップロードして共有することもできます。

### 5.5 Power Automate と Copilot Studio ワークフローの違い

ブースでよく聞かれる質問として取り上げています。両方とも優れたソリューションで、必要に応じて選ぶという立場です。

- **Power Automate**：信頼できる純粋に決定論的な自動化基盤が必要で、すでに Power Automate のライセンスと投資がある場合は、引き続き使える。Power Automate は製品として存続し、Microsoft にとって健全な事業。プロンプトによる AI 機能の追加もできる。
- **Copilot Studio のワークフロー**：エージェントを活用したい、classify や extract などの新しいエージェントアクションを使いたい、新しいデザイナーを使いたい場合に向く。ライセンスを統一できる（Power Automate のライセンスと Copilot credits を別々に持つ代わりに、すべて Copilot credits で標準化される）。

### 5.6 ライセンスとコスト

Copilot Studio は **従量課金（consumption model）** で、通貨は **Copilot credits** です。購入方法は 2 つです。

1. **プリペイドパック**：一定額で事前に credits を購入し、環境やユーザーに割り当てる。
2. **Azure の従量課金サブスクリプションにリンク**：Azure のコスト管理ソリューションを使える。

ワークフローのコストは次のとおりです。

- agentic でない（AI を使わない）アクション：1 アクションあたり **0.13 credits**。1 credit は 1 ドルの 1 セント。
- agentic なアクション：スライドの計算式に従う。決め手は、**選んだモデル**（発表者は例として「Fable 5.2」と「GPT-6 Luna」では同じコストにならないと説明。いずれも音声認識の都合で表記が確定できません）、**エージェントが呼ぶツールの数**、**agentic アクションの実行時間**。

### 5.7 今回のアップデートと今後の予定

チームは、次の 3 つの領域に集中していると説明しています。

1. ワークフローにより agentic で賢いアクションを追加する
2. 本番運用に向けて、規模と信頼性を確保する
3. ワークフローを作りやすくする

#### 5.7.1 新しい agentic 機能

**Decision モデルと classify ノード**
キーノートで「Microsoft-Decision-1.1」というモデル（音声認識の都合で表記が確定できません）が発表されたと説明しています。分類に特化した新しい種類のモデルで、テキストまたは画像を入力し、出力の候補を指定すると、素早く答えを返します。毎回テキストを生成する LLM に比べ、**はるかに速く、はるかに安い** とのことです。今週、classify ノードから decision モデルを呼び出せるようになりました。既存のモデルと並んで選択できます。

**Copilot ノード**
ワークフローのステップとして Copilot を呼び出します。Copilot アプリに入れるプロンプトをそのままステップにでき、Work IQ や Cowork の機能を使えます。モードを選べて、Chat、Cowork に加え、Frontier で今回発表された機能として、すでに autopilot を持っている場合はそれを呼び出してタスクを委任できます。

**エージェントノードからのドキュメント出力**
エージェントは文書を読むだけでなく、生成もできます。エージェントノードで、ドキュメントを出力として定義できるようになりました。PowerPoint、PDF、画像などの生成を指示し、その出力を後続のアクションで使えます。スライドの例では、メールで届いた請求書をエージェントが理解してデータを抽出し、同じエージェントが Excel ファイルを生成して SharePoint に保存します。

**Code ノード**
来週から展開が始まる機能です。ワークフローのステップとして **Python** を実行できます。データ操作やファイル形式の変換など、これまで複雑な数式や、Azure Function を呼び出して戻る方法に頼っていた処理が対象です。テキストのプロンプトから AI がコードを生成する機能もあります。

| 機能 | 状況（発表時） | 内容 |
| --- | --- | --- |
| クレジットの可視化 | すでに利用可能 | 過去数か月で最も要望が多かった。実行ごと、アクションごとの credit 消費を確認でき、期間を指定して消費量を見るモニタービューもある |
| 環境変数 | すでに利用可能 | Copilot Studio のソリューションの概念。ある環境で作ったエージェントやワークフローを別の環境へ昇格させる際、ステージごとに値を変えられる。ソリューションに定義した環境変数を、ワークフロー作成時のトークンピッカーで選べる |
| Code view | 今週から展開開始 | デザイナーの裏にあるコードを見て、直接編集できる。コピーしてコーディングエージェントに渡し、更新を戻す使い方も紹介されている |

#### 5.7.3 作りやすさ

1. **Copilot Studio MCP server**（数週間前に公開）：GitHub Copilot、Codex、Claude Code など任意のコーディングエージェントに追加できる。ワークフローやエージェントの作成のほか、アクティビティ履歴の取得もでき、たとえばワークフローの全実行に基づくレポートを作らせることもできる。デザイナーは優れているものの、オプションやパラメーターが多くて圧倒されることもあるため、「このビジネス課題のためにワークフローとエージェントを作って」と頼む方法が選べる。
2. **Cowork 向けの新しいスキル**（今週発表）：Frontier の Cowork にアクセスできる場合、Copilot Studio の成果物を Cowork から作成できる。Cowork は Work IQ の仕事のデータにアクセスできるため、そのコンテキストを使って「自動化やエージェントを Copilot Studio に作って」と頼める。
3. **ガイドツアー**：ゲームのチュートリアルのように、最初のエンドツーエンドのワークフローの作り方（トリガー、メインのコンテンツ、公開）を学べる。
4. **デザイナーの継続的な改善**：複数アクションの選択と同時移動、大きなワークフローで全体を見渡せる minimap、改善された zoom 操作、**ノードの位置の入れ替え**（発表者のお気に入り）。これまでは接続を切ってスペースを空けて移動する必要がありましたが、ノードを別のノードの上にドラッグ＆ドロップすると自動で入れ替わります。
5. **バージョン履歴の可視化**（来月開始）：ワークフローはバージョン管理されており、履歴の機能自体はすでに GA。来月から、過去のバージョンを選ぶと最新版との差分を視覚的に確認できる。MCP や Cowork を使うと変更が増えるため、「ここ 5 日間で何が変わったか」を確認する用途が語られています。

## 6. デモ・手順

**デモは行われています。** 録音は音声だけのため、画面の細部は確認できず、以下は発表者がナレーションで語った範囲に限っています。

### 6.1 デモのシナリオ

Ignite の FAQ サイトに掲載されているメールアドレスを、自分たちが担当するという想定です。小さなチームで何千通ものメールには答えきれないため、エージェントとワークフローで規模を確保します。メールボックスは架空のもので、グループ登録、ラボの登録、スポンサーになりたい企業などの問い合わせが入っています。

### 6.2 ワークフローの構成（語られた順）

1. 画面の左側に、追加できるアクションが並ぶ。agentic なアクションから始まり、1,500 を超える Power Platform のサービス、コード、変数も追加できる。
2. **トリガー**：共有メールボックスに新しいメールが届くたびに開始する。
3. **Classify ノード**：標準のノードで、メール本文を設定し、「agenda に関する質問」「ticketing に関する質問」などのカテゴリを自然言語で記述する。これで分岐する経路が視覚的に決まる。
4. **モデルの比較テスト**：classify ノードの単体テストを実行した。
   1. 既定は今週発表された decision モデル。
   2. 別のモデルとして GPT-6 Luna を選択（簡単なタスクなので強力なモデルは不要、という説明）。テストの入力は、過去の実行を選ぶか、メールを直接入力できる。スポンサーになりたい企業のメールを貼り付けて実行し、数秒後に「sponsorship」と分類された。
   3. 次に decision モデルに切り替えて同じメールで実行。ほぼ即座に答えが返った。
   4. decision モデルはカテゴリに加え **信頼度スコア（confidence score）** も返す。「たとえば 85% 未満なら人間にエスカレーションする」というロジックを組める。
5. **Agenda に関する質問**：Copilot Studio のエージェント画面で単体として作成済みのエージェントを使う。Copilot や Teams からも使え、ワークフローからも呼べる。エージェントノードを追加するときは、新規作成も、この環境で公開済みのエージェントの選択もできる。ここでは公開済みのエージェントを選び、「このメールを受け取った。返信を下書きして」というメッセージを送る。**出力の形式を指定** でき、エージェントは冗長になりがちなので、「メールの返信だけを HTML で」と定義して、次のアクションで返信に使う。
6. **Ticketing に関する質問**：こちらは **ワークフロー内でインラインにエージェントを作成**。通常のエージェント作成と同様にモデルと指示を定義する。指示は「ticketing 関連の質問に答える。登録情報はすべて Dataverse にある」という内容で、ツールとして Dataverse MCP を追加している。出力は、お客様への返信と、エスカレーションが必要か（人間による確認が必要か）。ボタンを押すと、デザイナーの中でエージェント作成の画面全体を広く使えると紹介されている。
7. **Human review ステップ**：人間へのエスカレーションが必要な場合に置く。ここまでワークフローを実行して一時停止し、人間が返信するまで待つ。連絡手段はメールまたは Teams。承認または却下と、お客様に送る最終的な返信を返してもらう。
8. **証明書の依頼**：「会社に Ignite に参加した証拠を示したい」という問い合わせ用のエージェント。Dataverse のテーブルから登録・出席情報を参照する。新機能の **ファイル出力** を使って PDF の証明書を返すよう定義し（PDF、PowerPoint、CSV なども定義できる）、その PDF を SharePoint に保存して、添付ファイルとしてお客様に送る。発表者によると、Microsoft と Ignite のブランドを入れた証明書を作るよう指示しており、生成された証明書が SharePoint フォルダーに保存されていることを画面で見せている。
9. **Extract ノード（旅費精算の例）**：講演者の旅費・ホテル代の精算で、航空券などの証明書類が送られてくるという想定。例の書類はスキャンの品質が良くなく、コーヒーのしみがある、とのこと。
   1. extract ノードをドラッグ＆ドロップで配置する。
   2. テンプレートを選ぶ、出力を手動で定義する、サンプル文書をドラッグ＆ドロップする、の 3 つの方法があり、サンプル文書の方法を使う。
   3. 文書を読み取り、種類を理解し、航空券から情報を抽出するために最適化された指示が裏側で作られる。特定のテンプレートに依存せず、どの航空券にも使える。
   4. 数秒待つ間に、「Take a Tour」（3 点メニュー）と「Code View」を紹介。Code view には、Copilot Studio MCP に接続するための手順も表示される。
   5. 結果として、航空会社名、搭乗者名などの出力項目が設定された。リストにも対応し、出力名だけでなく説明も設定されるため、抽出精度が上がる。必要に応じてカスタマイズできる。
10. **スポンサーシップ**：スポンサー希望の企業とは、日程調整と、先方と会うための概要資料の準備が必要で、手間がかかる。複雑なタスクなので **Cowork に委任** する。Copilot ノードで「Cowork」を選び、モードは「Chat」「Autopilot」からも選べる（Autopilot はアカウントに持っている場合）。同じメールを使って実行し、Cowork 側に新しい会話がワークフローから起動されること、ワークフローから送られたプロンプトが確認できること、そこから操作を引き継げることを示している。
11. **スパムなど**：トークンを使う必要がないので、エージェントは作らず、決定論的な「メールの削除」または「アーカイブ」で処理する。
12. 横向き・縦向きのレイアウトを切り替えるオプションにも触れている。

### 6.3 実行履歴とコストの確認

1. 新しいメールが届くたびに実行される。実行は **アクティビティビュー** で確認でき、各実行を掘り下げられる。
2. この画面で credits の消費量を確認できる。「どのくらいのコストになるか見積もりたい」という質問が多く、**テスト実行をして、その credit 消費を見る方法** を勧めている。各アクションを選ぶと、アクションごとの消費量も分かる。
3. デモの実行では、AI アクションのコストが **7.29**（credits 表示の画面での数値）。AI を使わないアクションは常に **0.13 credits**。

## 7. 注意点・発表者の気付き

- ワークフローは順序を保証できる一方、プロセスの変更や逸脱があると失敗します。逆にエージェントは柔軟ですが、手順が毎回同じとは限りません。この両面から、両者を組み合わせることを勧めています。
- コスト、ガバナンス、制御は、エージェントによる自動化で向き合うべき課題として挙げられています。
- エージェントの出力は冗長（chatty）になりがちなので、ワークフローでは必要な出力の形を指定します（デモでは返信メールの HTML だけ）。
- ワークフローをエージェントのツールにした場合、既定ではエージェントを使うユーザーの資格情報で動きます。maker の資格情報で動かすアクション単位の指定は来月の予定です。
- コストを見積もるには、テスト実行をして credit の実測値を見ます。
- スパムなどの処理は、トークンを使う必要がないとして、エージェントを作らず決定論的なアクションだけで済ませています。
- 「来週」「来月」といった今後の機能の時期は、発表時点での話です。
- Decision モデルの名称、モデル名「Fable 5.2」などは、音声認識の都合で表記が確定できません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **順序の保証とエージェントの柔軟性の両立**：重要なプロセスの手順はワークフローで固定し、判断が必要な部分だけエージェントに任せられる。
- **コストと速度**：decision モデルを classify ノードで使うと、従来の LLM に比べて速度とコストの差が大きい。大規模なテキスト処理やメール処理で、レイテンシーとコストを下げられる。
- **ライセンスの統一**：Copilot Studio のワークフローでは、エージェントのステップも含め Copilot credits で標準化される。
- **コストの可視化**：実行単位・アクション単位で credit 消費を確認でき、テスト実行で見積もれる。
- **本番運用への対応**：環境変数、サービスプリンシパル（来月）、アクション単位の資格情報の指定（来月）、バージョン履歴の可視化（来月）。
- **作成の効率**：ステップ単位のテスト、MCP server や Cowork から自然言語で作成、ガイドツアー、Gallery のサンプル。
- **利用例**：リーガルの契約書分析、メールの振り分けと返信、Excel を使うファイナンス業務などで、すでにお客様が使っているパターンとして紹介されています（具体的な顧客名や成果の数値は語られていません）。

## 9. まとめ

Copilot Studio は、手順を保証するワークフローと、判断ができるエージェントを、1 つのキャンバスで組み合わせられます。ワークフローにエージェントや classify、extract、Copilot などの agentic なステップを入れる方法と、エージェントのツールとしてワークフローを使う方法があります。

今回のアップデートの柱は、agentic なアクションの拡充（decision モデル、Copilot ノード、ドキュメント出力、Code ノード）、本番運用への対応（credit の可視化、環境変数、Code view、サービスプリンシパルなど）、作成の効率化（MCP server、Cowork のスキル、ガイドツアー、デザイナー改善）の 3 つです。

始め方として発表者が挙げたのは、copilotstudio.com から作る、Frontier の Cowork を使う、任意の AI アシスタントに Copilot Studio MCP server を追加する、の 3 つです。フィードバックは Workflow Designer の「share feedback」ボタンから送れ、チームは全件に目を通していると説明しています。
