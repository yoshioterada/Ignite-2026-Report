# BRK290 Humans, agents, and a game plan: AI governance with GitHub Enterprise

## 1. はじめに

このセッションは、GitHub Enterprise と GitHub Copilot を使う企業の管理者向けに、「開発者やエージェントに自由度を与えつつ、企業としての統制をどう効かせるか」を、管理者の画面を見せながら説明するものです。前半は Greg 氏が考え方（ガバナンスのライフサイクル）を説明し、続いて Amrita 氏が AI controls 画面で、機能・モデルの既定ポリシー、enterprise teams によるチーム別のモデル開放、Copilot Fusion のモデル設定をデモします。後半は Greg 氏が、managed settings（設定をコードとして管理する仕組み）を、リポジトリの画面を見せながら説明し、最後にロードマップと Q&A が続きます。

結論を先に言うと、発表者が繰り返し勧めているのは、**「まずシンプルに始め、既定を決め、チーム単位で試し、使用状況を測り、必要な所だけ洗練させる」** という進め方です。

### 5.1 ガバナンスのライフサイクル（Greg 氏）

GitHub が注力している領域として、次のものが紹介されました。

| 領域 | 発表での説明 |
| --- | --- |
| サーバー側のポリシー | 従来からあるポリシーを、推論のモデル管理、Copilot 機能の提供可否、FinOps と課金のニーズへ拡張している。 |
| managed settings | 新しい制御面。Copilot app や Copilot CLI などの「クライアント」自体のカスタマイズとガバナンスを担う。チームごとの特化もできる。 |
| テレメトリとエージェントセッションの取得 | クライアントからのエージェントセッションのテレメトリと、設定可能な取得機能。既存の Copilot metrics とあわせ、エージェントの活動全体を可視化するオブザーバビリティの層になる。 |

> 補足：Greg 氏は「4 つの製品領域に投資している」と述べていますが、音声で明確に並べられたのは上の 3 つで、4 つ目は特定できません。

将来的には、エンタープライズの設定の文脈を持つエージェントに、「この人はどのモデルを使えるか」「このチームの Copilot の使い方はどうか」といった質問ができ、データウェアハウスのコネクタを使って独自のダッシュボードを作れるようにしたい、と述べています。

ガバナンスのライフサイクルの進め方は次のとおりです。

1. Copilot のコントロール、モデルのポリシー、managed settings で **強いベースライン** を作る。managed settings では、エージェントの権限、エージェントができることの境界、利用可能にするプラグインのマーケットプレイス、その中のスキルや MCP サーバーなどのエージェントのプリミティブを扱います。
2. **エンタープライズのチーム単位で特化させる。** 職種、AI のトレーニングレベル、コストセンターなどで対象を分けられます。
3. **測定する。** ガバナンスが機能しているか、煩雑すぎないか、摩擦が大きくないかを見て、絞るか緩めるかを調整し、継続的に改善します。

「正しい人に、正しい時に、正しいガバナンスを」届けることが目標です。

最近の変化として、モデルポリシーの API の抜けを埋めて click ops を減らしたこと、Fusion 向けの「model mix management」を出荷したことが紹介されました。好ましくないモデルを Fusion の対象から外せますが、Fusion は利用できるモデルが最大のときに最も良く動くとも述べています。一般提供の Copilot 機能とクライアントも、Fusion と同様にユーザーへ既定で提供し、利用実績から必要かを判断することを勧めています。

### 5.2 機能とクライアントのグローバル既定ポリシー（Amrita 氏）

Amrita 氏は、AI controls ページと API で管理できる「global default policy」を説明しています。管理者が未設定のまま残している一般提供の機能に既定を適用でき、ポリシー判断を機能ごとではなく 1 回で済ませられます。有効にすると、新機能がリリースされ次第、開発者が使えるようになります。すでに管理者が行った個別の選択は保持されます。

### 5.3 モデルのアクセス制御

GitHub Copilot では、オープンウェイトを含む複数の AI ラボのモデルを提供する方針だと述べています。日常的な変更向けに速くコスト効率の高いモデルがあり、複雑なデバッグ向けに推論力の強いモデルがあるという位置づけです。モデル用にもグローバル既定ポリシーがあり、「有効」にすると新モデルが出るたびに開発者が自動的に使えるようになります。

> 注意：オープンウェイトのモデルは、グローバルポリシーの対象外で、既定では無効のままです。

将来の進化として、プロバイダー、ファミリー、データ分類ごとにモデルのグループを承認できるようにする構想が語られました。承認済みグループに新しく加わるモデルが自動で使えるようになり、繰り返しの承認作業が減り、法務・セキュリティ・ガバナンスの要件を大規模に適用できる、という説明です。

### 5.4 チームの特化（enterprise teams）

あるチームだけ、全社にはまだ開放できないアクセスが必要な場合に使うのが enterprise teams です。エンタープライズのレベルで 1 度グループを定義し、複数の組織にまたがってアクセスを管理できます。各組織で同じチームを作り直す必要がありません。役割やトレーニングレベルなどでグルーピングできます。例として、共通の責務を持つ人たちを集めた platform engineering チームを作った、という説明がありました。

設定した enterprise teams に対しては、プレビュー機能の「enterprise teams mode」で、事前に定義したグループに追加のモデルアクセスを付与できます。例として、platform engineering チームが大規模な移行のために高価なモデルを追加で必要とする場合、そのチームだけに許可し、他の人には許可しない、という使い方が挙げられました。

### 5.5 Copilot Fusion

Copilot Fusion は、タスクに対してモデルを自動で選び、調整するモデルオーケストレーターで、コスト、速度、品質のバランスを取りながら、管理者が決めたモデル権限の範囲内で動きます。VS Code、Copilot CLI、GitHub Copilot app、JetBrains IDE で試せ、Amrita 氏と Greg 氏は毎日使っているそうです。

公開されているベンチマークのページを示し、解決率で Fusion High が「Opus 5.5 High」と「GPT-6 Astra Medium」より多くのタスクを解決し、タスクあたりの平均コストも低いと説明しています（モデル名は聞こえた表記のままで、音声認識の都合で表記が確定できません）。

なお、Greg 氏はデモのあと、モデルポリシーの API を使えば、画面のクリックなしで同じ設定ができると補足しています。GitHub はできるだけ多くのモデルを提供する方針で、Anthropic のモデルも OpenAI のモデルも GitHub の inference 経由で使えます。そのため、2 社のモデルを組み合わせた「敵対的な（antagonistic）レビュー」も可能で、Fusion はそうした使い方を助け、スキルに組み込めば選択肢がさらに広がる、という説明です。

### 5.6 managed settings（Greg 氏）

Greg 氏によれば、前年に GitHub の中で agent control plane を作り、Copilot の各種コントロールを集約しました。今年はそこに managed settings が加わりました。目的は、**config as code** のインターフェースで、クライアントのガバナンスとカスタマイズを強化することです。ガバナンスの例は「誤った MCP サーバーが起動しないようにする」こと、カスタマイズの例は、first responder（オンコール当番）のチームに、その週の当番に合うプラグイン、スキル、機能をすぐに使えるようにし、当番でないときは外すことです。既定のモデル選択から、プラグインやエージェントのプリミティブの自動有効化まで対象としています。

**既定モデルの扱い**

Fusion の model mix は「Fusion が選べるモデル」を決めますが、ユーザーがクライアントを最初に開いたときに「どのモデルが選ばれているか」は managed settings で決まります。AI の導入度合いは幅広く、すでに高度に自動化している人もいれば、まだ手探りの人もいます。GitHub が受けた最も頻度の高いフィードバックは、最終ユーザーが特定のモデルに留まったままになり、「トークンやクレジットがどこで消えているのか分からない」というものでした。そこで、新しいセッションを始めるたびに、より現実的で控えめなモデルへ戻す仕組みを入れたそうです。高度なユーザーにとっては摩擦になるため、両立できるようにしています。

**優先順位**

managed settings の階層は明快で、**エンタープライズの設定が常に優先**します。エンタープライズで設定しなかった項目は、ユーザーの設定が優先されます。高度なユーザーのローカル設定を必ずしも上書きする必要はなく、対話の機会になるかもしれない、と述べています。

**リポジトリで運用する**

設定ファイルは、内部公開（inner source）のリポジトリに置くことを強く勧めています。利用者は、設定が気に入らない場合や自分のチーム向けに別の構成が欲しい場合に、pull request を出せます。これが定期的に行われるようなら、PR の承認プロセスや four-eyes principle などをガバナンスに合わせて組み込めます。

**sandboxing**

managed settings のガバナンス面で最も重要なのは、エージェントができることの境界を決めることです。ファイルシステムが上書きされない、実行の制御がある、といった安心が採用拡大には必要で、ローカルの sandboxing がそれを助けます。多くのユーザーに有効にすることも、enterprise team ごとに変えることもできます。たとえば、より高いレベルで自由を与えたいユーザーには、制限を緩めることができます。モデルの選択と同様に、overridable（上書き可能）にもできます。また sandboxing などの機能はバージョン管理されており、古い VS Code クライアントや Copilot CLI を使っているユーザーは、バージョンの強制により Copilot へのアクセスがブロックされます。

sandbox には 2 種類あります。

| 種類 | 説明 |
| --- | --- |
| ローカル sandbox | ローカルで動く。MXC（Microsoft のエコシステムで知られているもの、と説明。音声認識の都合で表記が確定できません）の上で動き、細かく絞り込む設定ができる。 |
| クラウド sandbox | 作業をノート PC の外に出してクラウドで別の形で制御する。 |

どちらにも用途があり、チームで試して合う方を探してほしいとのことです。sandboxing は始め方が難しいという声があるため、発表者は enterprise team の特化の仕組みを使い、まず 1 つのチームで試し、調整・観察してから、成功したと感じたら全体に広げる進め方を勧めています。

**プラグインとマーケットプレイス**

スキルをプラグインにまとめ、承認した社内マーケットプレイスなどに載せ、そのマーケットプレイスを利用者に提供します。managed settings では、マーケットプレイスの場所を指定するキー、自動で有効にするプラグインのための enabled plugins キー、利用可能なマーケットプレイスを限定する強制の仕組み（発話では「strict no marketplaces」と聞こえ、キー名は音声認識の都合で確定できません）があり、いずれも enterprise team ごとに変えられます。小さなチーム単位で、自分たちでプラグインを選ぶ（curate する）境界も開発中です。

**MCP サーバー**

MCP サーバーも同様に、プラグイン、マーケットプレイスを通じて提供し、有効化します。さらに、すぐ実行を許可する MCP サーバーを置く「allowed MCP servers」と、拒否したものを置くキー（deny）があり、managed settings に組み込んでチームごとに調整できます。

## 6. デモ・手順

このセッションには、AI controls と managed settings の 2 つのデモがあります。画面の細部は音声からは確認できず、以下は語られた範囲に限ります。

### 6.1 Amrita 氏のデモ: 管理者として Copilot の既定とモデルアクセスを設定する

エンタープライズ管理者の立場で、「開始時の既定」「ガードレール」「チームごとのニーズへの対応」を順に見せています。

1. AI controls を開く。ポリシーを管理し、最近のエージェントセッションの活動を見られる中心的な場所だと説明。
2. Copilot セクションの「features and clients」ページに進む。新機能とクライアントへのアクセスを制御するポリシーで、API でも設定できると説明。
3. グローバル既定ポリシーの選択肢は 3 つ。「enabled」（新しい機能やクライアントを追加の作業なしで利用可能にする）、「disabled」（新しいリリースは明示的な承認が必要になる）、組織管理者に判断を任せる「let organizations decide」。組織の管理者には、委任された設定を構成できる同様の Copilot 設定ページが表示される。ここでは **enabled のまま**にする。
4. この基準は個別の選択を妨げない。基準を enabled にしたまま、個別の機能やクライアントを無効にしたり委任したりできる。下にスクロールして「settings and context」で、「Copilot can search the web」を無効にする例を示す。
5. このページのプレビューのコントロールは、グローバルポリシーによる自動有効化の対象外で、オプトインのままだと説明。
6. Copilot のページに戻り、「enterprise teams mode」が有効になっていることを確認（プレビュー機能）。
7. 「configure models」ページで、モデルのグローバル既定ポリシーを確認。機能のページと同様に、enabled なら新しいモデルが出るたびに使え、disabled なら新しいモデルを手動で有効にする必要がある。個別のモデルごとの例外も可能。

## 7. 注意点・発表者の気付き

- **新規の機能・モデルの扱い。** 既定を enabled にしても、プレビューの機能や、オープンウェイトのモデルは自動では有効になりません。
- **エンタープライズの設定が優先される。** managed settings で設定した内容は全ユーザーに適用されるため、本当にそうしたいか確認してから設定する必要があります。
- **ユーザーの上書きを許すかは意識して決める。** 設定しない項目はユーザーの設定が優先されます。高度なユーザーを一律に上書きしないほうがよい場合もあります。
- **ファイルは複雑になりやすい。** JSON の設定ファイルは高機能になるほど長くなるため、シンプルに始めることを勧めています。実際、デモ中にも JSON の検証エラーが見つかりました。
- **古いクライアントはブロックされうる。** sandboxing を強制すると、古い VS Code や Copilot CLI からのアクセスがバージョンの強制でブロックされます。
- **sandboxing は始めにくい。** 「少し取っつきにくい」というフィードバックがあり、まず 1 つのチームで試すことが勧められています。
- **モデルを高性能なものに固定しがち。** 利用者が特定のモデルに留まることでクレジットの消費が見えなくなるという声が最も多く、新セッションでの既定へのリセットで対応しています。ただし高度なユーザーには摩擦になります。
- **Fusion に渡すモデルは多いほうが良い。** 一方で、特定のモデルを外すこともできます。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。具体的な数値による成果や顧客事例は、このセッションでは示されていません。

- 既定ポリシーを 1 回決めるだけで、新機能・新モデルを管理者の追加作業なしに開発者へ提供できる（その分、個別の例外も管理できる）。
- enterprise teams により、チームごとに異なるモデルアクセスや設定を、組織をまたいで 1 度の定義で管理できる。
- managed settings により、既定モデル、プラグイン、MCP サーバー、sandboxing などのクライアントの設定を、コードとして一元的に配布し、PR で運用できる。
- API が整備されることで click ops が減る。
- 使用状況やスキルの採用を見て、ポリシーを改善できる（今後はレコメンデーションも予定）。
- Fusion により、利用者が自分でモデルを選ぶ負担が減り、公開ベンチマークではコストを抑えながら解決率が高いと説明されている。

## 9. まとめ

このセッションは、AI の導入が進むほど、管理者の判断を必要な文脈で、少ない手作業で効かせる必要が高まるという前提で、GitHub Enterprise と Copilot の管理手段を整理しています。AI controls の global default policy、enterprise teams によるモデルアクセスの特化、Copilot Fusion のモデル設定、そして config as code の managed settings（既定モデル、プラグインのマーケットプレイス、MCP の許可・拒否、sandboxing）が、現在使える手段として説明されました。

ロードマップとしては、予算の上限に達したときの穏やかなフォールバック、Agent 365 との連携、使用状況に基づくポリシーレコメンデーション、soft enabled plugins、policy diagnostics などが挙げられています。進め方は一貫していて、強いベースラインを置き、1 つのチームで試し、測定して広げる、という流れです。
