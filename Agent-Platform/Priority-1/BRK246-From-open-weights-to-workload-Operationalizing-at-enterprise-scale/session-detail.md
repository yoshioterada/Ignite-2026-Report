# BRK246 From open weights to workload: Operationalizing at enterprise scale

## 1. はじめに

このセッションは、オープンウェイトモデル（open weight / open source model）を本番ワークロードで動かしたい開発者・インフラ担当者に向けた発表です。Microsoft Foundry の **Managed Compute**（オープンソースモデル、パートナーモデル、カスタムモデルを専用 GPU 上でホストするサービス）を題材に、カタログからのデプロイ、スケール、カスタムモデルの持ち込み、そして AT&T の利用事例までを 45 分で扱います。

発表の結論を先に挙げると、次の 3 点です。

* Hugging Face からモデルを取得して Kubernetes で本番運用するまでに「約 1 週間」かかる作業を、Managed Compute なら「1 時間程度」に短縮できるという主張です。
* Managed Compute は発表の最後で **一般提供（GA）** になったと告知されました。
* AT&T は、カスタマーケア向けの通話処理で、フロンティアモデルに支払っていた費用の約 50% を削減したと報告しています。

発表の途中には Foundry ポータルと SDK を使ったデモがあります。

## 5. 発表内容の詳細

### 5.1 オープンソースモデルの動向とエージェント推論

登壇者はまず会場に、オープンソースモデルを使ったことがあるか挙手を求め、「多数」だったと述べています。続いて OpenRouter のデータを示し、次のように説明しました。

* 直近 1 か月で、トークンの 50% 超がオープンウェイトモデルによるものだった。
* 上位 10 モデルのうち数モデル（"a handful"）がオープンソースで、トップのモデルもオープンソースだった。

この傾向を後押ししている要因として、**エージェント推論（agentic inference）** が挙げられました。推論リクエストが人間だけでなく、ツール呼び出し、長い推論、長い入力を伴うエージェントから送られるようになったため、「最良のモデルは何か」だけでなく「そのタスクに最適なモデルは何か」を考える必要がある、という説明です。結果として複数のモデルを使い分けることになり、そこで Microsoft Foundry の出番になる、という流れです。

Foundry は、オープンソースモデルとプロプライエタリモデルの幅広い選択肢を提供し、エージェントの中で使えること、IQ ツールとセーフティが標準で使えることが紹介されています。カタログには 11,000 以上のモデルがあり（トランスクリプトでは "FileReview" と聞こえますが、文脈から Foundry を指していると判断できます）、Azure が直接提供するコレクションとパートナーモデルから選べて、モデルを切り替えて試せるとのことです。

### 5.2 Foundry のデプロイ形態

「何をデプロイするか」に加えて「どうデプロイするか」も重要だとして、3 つの形態が挙げられました。

| 形態 | 説明 |
| ---- | ---- |
| Serverless（Standard） | 最も始めやすい形態。入力・出力トークン単位の従量課金。デプロイして試し、その後スケールできる |
| Provisioned | ワークロードの規模が分かっている、予測可能なワークロード向け |
| Managed Compute | このセッションの主題。オープンソースモデル、パートナーモデル、カスタムモデルのサービング向けで、課金単位は GPU 時間 |

### 5.3 Managed Compute とは

Gulsimo 氏は、Managed Compute を「GPU プラットフォームをサービスとして提供するもの」と位置づけています。カタログのモデルを数分でマネージドエンドポイントにできます。背後のスタックは Microsoft が運用し、スケーリングやセキュリティパッチの適用も Microsoft が行います。利用者の手元に残るのはモデルの選択だけです。Foundry で提供しているベースモデルをデプロイすることも、カスタムモデルを持ち込んでデプロイすることもできます。

### 5.4 カタログからのデプロイ（デモ 1）

Manoj 氏は、Hugging Face からモデルをダウンロードし、Kubernetes 上で動かして本番に持っていくのに 1 週間未満でできる人はいるか、と会場に問いかけたうえで、これを「1 週間から 1 時間程度」にするとして Foundry のモデルカタログでデモを行いました。デモの手順は 6 章に書いています。ここでは、デモの中で語られたデプロイ設定の考え方を整理します。

* デプロイタイプは Managed Compute。グローバルのほか、GPU の割り当てを地理的な境界内に収める US または European のデータレジデンシーも選べる。
* モデルとワークロードに対して、どの GPU 構成で動かすかを選ぶ。デモのモデルは 300 億パラメーターで、重みが 60GB。
* **A100 1 枚**の構成では、重みを載せると KV キャッシュに使える領域が約 20GB しか残らないため、コンテキスト長は 16K に制限される。
* **A100 2 枚**の構成では、KV キャッシュの余裕が十分あり、フルの 256K コンテキスト長が使える。
* H200 や MI300 のような大きな GPU では、KV キャッシュの余裕を含めてモデル全体が 1 枚の GPU に収まる。
* 長いコンテキスト向け、短いコンテキスト向け、レイテンシ重視など、用途に合わせて最適化できる。
* 仮想マシンや SKU、リージョン、SKU のクォータ取得を利用者が意識する必要はなく、コストを確認してデプロイするだけになる。

> 補足：デモで選んだ具体的なモデル名は「Gemma」と話されており、カタログには Nemotron ファミリー、Gemma、DeepSeek などがあると紹介されました。上記の「300 億パラメーター、重み 60GB」がどのモデルの数値かは、音声からは確定できません。

### 5.5 Foundry エンドポイントでの利用（デモ 2）

デプロイ済みの Managed Compute モデルは、Serverless モデルと**同じ Foundry エンドポイント**を使います。認証、ネットワーク（プライベートネットワークを有効にしていればそれも含む）、アクセス制御は、Serverless と同じ仕組みで管理されます。Playground で試すことも、コードスニペットを見ることもできます。

Chat Completions SDK では、Serverless モデルからオープンモデルに切り替えるときに、**デプロイ名を model パラメーターに渡すだけ**で推論が動く、と説明されています。

さらに、ステートレスな Chat Completions のデプロイを **Foundry Agent Service** のエージェントに接続できます。Responses API を使うので、会話履歴をサービス側に保存でき、ツール呼び出しも使えます。デモでは、Web 検索を通じて天気や株価を調べられること、会話 ID を渡すと前の会話内容を取り出せること、プロンプトキャッシュが効くことが示されました。

### 5.6 自前構築との比較と Microsoft のモデル提供プロセス

Gulsimo 氏は、DeepSeek のようなトレンドのモデルを Hugging Face から取得して自分でサービングする場合の流れを次のように示しました。

1. 重みをダウンロードする
2. ライセンスを確認し、想定する用途で許されているかを確認する
3. ランタイムを選ぶ
4. GPU のサイズを見積もる
5. フラグを調整する
6. API をテストする

この一連の作業は、チームの習熟度によって数分から数週間かかり、毎週新しいモデルが出る状況では、その時間が許されない場合があるという指摘です。Managed Compute では、カタログのモデルをデプロイしてエンドポイントを得るだけで済みます。Hugging Face とのパートナーシップにより、モデルは **day zero**（公開日当日）から使えるとされています。

Microsoft 側のモデル提供プロセスとして、次の流れが説明されました。

1. 業界でトレンドのオープンソースモデルと、顧客が関心を持つモデルを調べる
2. ライセンスと安全性を審査し、信頼できないカスタムコードが動いていないことを確認する
3. ランタイムイメージを作成し、セキュリティパッチを適用する
4. スキャンを行い、ステージングに移して重みを再度検証する
5. 本番で公開する

サービングスタックのセキュリティ対応の例として、Docker Hub の OSS vLLM イメージと、Microsoft が作成したイメージを比較したデータが示され、**セキュリティ脆弱性の検出件数が 90% 少ない**と説明されました。

### 5.7 本番向けのスケールと可観測性（デモ 3）

デプロイは通常 1 インスタンスから始め、必要に応じて編集画面でモデルのインスタンス数を増やします。デモでは、1 インスタンス（4 GPU を使用）のデプロイと、5 インスタンス（合計 20 GPU）のデプロイを並べ、Azure Monitor で比較しました。結果は次のとおりです。

* 直近 1 時間に、1 インスタンスと 5 インスタンスの両方のデプロイに対して、合わせて約 14 万件のリクエストを送った（"around 140K requests to both" と話されています）。
* 処理したトークンは、5 インスタンスが約 4 億 5,000 万、1 インスタンスが約 9,000 万。

また、エンジンがそれ以上リクエストを処理できないときは 429（後で再試行）を返す仕組みで、1 インスタンスのデプロイでは 429 が非常に多く、5 インスタンスではごく少なかったと説明されています。複数インスタンスにまたがる効率的なルーティングも Foundry が行います。

Azure Monitor では、トークンの合計といった消費メトリクスのほか、レイテンシ関連のメトリクス（tokens per second、time to first token、ストリーミングと非ストリーミングのリクエスト数）が見られます。これらは **追加の可観測性ツールを設定しなくても、設定なしで使える**と強調されました。

Gulsimo 氏はこの部分の要約として、Foundry がリクエストをルーティングし、プロンプトキャッシュ、プレフィックスとセッションアフィニティ、負荷分散やスピルオーバーまで管理すると述べています。

バックエンドの推論最適化として、次の項目が挙げられました。

* スケーリングと利用率の向上（複数レプリカによるサービング、GPU の並列化）
* キャッシュとルーティング
* ハードウェアを効率よく使うためのチューニング
* **Speculative decoding**：ペアのモデルを使ってサービングを効率化する機能。これを利用可能にする取り組みを進めているとのこと（"we're also making ... available" という表現）

### 5.8 カスタムモデル：LoRA アダプターと Bring Your Own Weights

カスタムモデルの持ち込みには 2 つの方法があります。

1. **Foundry で学習し、LoRA アダプターを得て Managed Compute にデプロイする**
2. **自前の重みを持ち込んでデプロイする**

1 つ目に関連して、「program training」が **パブリックプレビュー**になったと発表されました（"program training" はトランスクリプト上の表記で、音声認識の都合で正式名称が確定できません）。Foundry 上で学習ループを書くと、Foundry が学習用の GPU を動かす、という説明です。同じ会場で午後 4 時から詳しいセッションがあると案内されました。

学習の成果物である LoRA アダプターは、差分の重みです。ターゲットとなるデプロイのサービング容量を共有し、**1 つのデプロイに最大 8 つのアダプター**を接続できます。GPU を効率よく使えますが、本番に合うかどうかを確認するために、利用率、レイテンシ、スループット、品質の監視を続ける必要があると注意されました。

2 つ目の Bring Your Own Weights は、他の場所でファインチューニングした safetensors の重みを持ち込む方法です。

デモの内容は 6 章で説明します。

### 5.9 AT&T の事例

Manoj 氏は、Managed Compute を 6 月上旬にパブリックプレビューとして出荷して以降、顧客のフィードバックを集めてきたと述べ、AT&T の 2 名を紹介しました。AT&T は、Kubernetes 上の自前スタックと Managed Compute の両方でオープンモデルを運用している、という紹介です。

#### 自前スタックの経緯（Miguel 氏）

* 約 3 年前から LLM を運用しており、最初期にデプロイしたモデルの 1 つは 2023 年の Falcon だった。
* 現在のスタックは、CNCF を中心とするオープンソースで構成され、AKS（Kubernetes）上にオーケストレーションを置いている。使用している要素として Helm、KNative、KServe、vLLM、Triton、そしてゲートウェイとして LiteLLM が挙がった。
* 発表の前半で示された課題（GPU コンピュートへの配慮、必要な機能、vLLM のバージョンとサポート状況、トラフィックの種類、speculative decoding、プレフィックスや KV キャッシュを考慮したルーティング、KV キャッシュの管理、計装）は、AT&T が経験してきたことと「100% 共感できる」と話しています。適切な技術とスタックがあっても、計装ができていなければ成功しない、という考えです。
* 急速に成長したため、Helm のテンプレートで、少しの設定で任意のモデルをデプロイできるようにした。ただし、顧客が誰か、どのワークロードを動かすか、GPU と容量がどれだけ残っているかを意識する負担はなくならなかった。
* 現在は 200〜300 GPU 程度の共有プールがあり、それでは足りないこともあり、市場や新しい施策に素早く対応できない場面がある。
* プラットフォームのトラフィックは **1 日あたり約 450 億トークン**。最近の例として iPhone の発売があり、その多くが AI に大きく依存していた。
* 小さなチームで、さまざまなモデル、ハードウェア、構成を試し、計装と分析まで行うのは難しい。Microsoft からプレビューの機会を得て、プラットフォームを補完するために探索した。

#### Managed Compute での成果（Pawan 氏）

Pawan 氏は、AKS 上の自前運用はほぼ手作業だが、Foundry の Managed Compute は、モデルとコンピュートを選んでデプロイするだけで、数回のクリックで済むと感じた、と話しています。

**テレコム向けオープンモデル（OTel）の構築**

* AT&T には、テレコム向けのオープンソースモデルがあり、ダウンロード数は 5,000 万、GSMA のリーダーボードで首位とのこと（登壇者は一度「50 billion」と言い、直後に「50 million」と言い直しています）。トランスクリプト上は "hotel model" と記録されていますが、セッションの概要に「OTel 2.0」とあるため、OTel のことと読めます。
* このモデルの学習に Managed Compute を使った。複数のオープンモデルを Managed Compute にデプロイし、ある時点では **530 GPU インスタンス**までスケールした（聞こえた表記のままです）。
* 通常の Azure デプロイよりも先に、Managed Compute で AMD を最初に利用できたのは AT&T だと思う、と話しています。
* プレビュー期間やモデル作成で試したモデルとして、「5 OSS」「Gemma 4」「Gemma 4E4B」「Nemotron」が挙がりました（最初のものは音声認識の都合で表記が確定できません）。
* データ生成と前処理には、「five」モデル（表記は音声認識の都合で確定できません）と OSS 120B を Managed Compute で動かした。この期間に処理したトークンは約 **1 兆**。
* そのうち **4,400 億トークン**を学習データとしてモデルを作成し、現時点でテレコム向けオープンモデルの中で最高のものの 1 つだとのこと。
* 現在は、埋め込み、リランカーなどの機能を加えた「2.0 または 2.5」を開発している。
* デプロイのサイズを拡大・縮小しやすく、容量が確保でき、vLLM のパラメーターなどのデプロイ設定も最適化できる点が利点として挙がりました。

**カスタマーケアの本番ユースケース**

顧客から届く大量の通話について、リアルタイムの通話要約、文字起こし、Q&A 生成、インテント分類を行っています。

* 現在は **Gemma 4 E4B を MI300 にデプロイ**して処理している。
* 処理量は **1 時間あたり最大 65 万リクエスト**。ピーク時は毎秒 130〜180 リクエスト。
* A/B テストでベンチマークを行い、この量のトラフィックには **Gemma 4 E4B の 15 インスタンス（MI300）**が最適と見つけた。
* フロンティアモデルで同様の量のリクエストとトークンを処理していたときと比べて、費用を **約 50% 削減**した。
* 休日のトラフィック増、新端末や新プランの発売で通話が増えても、すぐにインスタンス数を増やして対応できる。

既存のオープンソーススタックへの追加として使うことで、コンピュートの管理がしやすくなり、実行リージョンも意識しなくてよいと話しています。地理的な境界の制約があるため、米国リージョン内にデプロイしているとのことです。

### 5.10 まとめ、GA の告知、パートナー

Manoj 氏は次の 4 点を振り返りました。Managed Compute へのモデルのデプロイ、本番へのスケール、カスタムモデルの持ち込みまたは Foundry での学習とデプロイ、そして AT&T の事例です。

そのうえで、Managed Compute を選ぶ場合と自前で構築する場合の基準を示しました。

| 選択 | 条件 |
| ---- | ---- |
| Managed Compute | カタログにあるモデルを専用 GPU で動かしたい。Foundry エンドポイントをエージェントと一緒に使いたい。Microsoft 管理のランタイムとパッチ適用で問題ない |
| 自前のスタック・プラットフォーム | カスタムカーネルや独自のサービングアーキテクチャが必要。サービングスタックや GPU トポロジーの管理で、より高い柔軟性が欲しい |

続いて、次の発表がありました。

* **Managed Compute が一般提供（GA）になった**。本番で自信を持って使える。
* 過去 3〜4 か月で **150 以上のモデル**を出荷し、毎週少なくとも 20〜30 モデルを追加している。
* **データゾーン**の機能が使え、US や EU といった地理的境界内でワークロードを動かせる。

パートナーとの協力として、次のものが挙げられました。

* **Hugging Face**：モデルの公開パイプラインを構築し、モデルを安全に Azure に取り込む。企業の IT 環境を Hugging Face のようなオープンなドメインに接続する必要がなくなる。
* **NVIDIA と AMD**：アップストリームの transformers、vLLM、SGLang に出しているカーネルとランタイムの最適化を取り込む。
* **Canonical**：ランタイムのセキュリティ確保に協力。脆弱性スキャンとパッチ適用に Ubuntu Pro ESM を使う。

これらにより、ほぼ day zero で提供できると説明されています。深掘りしなかったテーマについては、次に参加できるセッションが案内されましたが、具体的なセッション名は音声からは確認できません。

### 5.11 Q&A

**質問 1（ブラジルの Leo さん）：LoRa アダプターの現状と今後の計画**

Leo さんは、大きなモデルで望ましい出力を生成し、それを使って Gemma E4B のような小さなモデル用の LoRA アダプターを学習する使い方をしていると説明し、アダプターを自分で学習してから Foundry にアップロードする必要があるのか、学習データをアップロードして Foundry 内で学習できるようになるのかを尋ねました。

回答の要点は次のとおりです。

* 現時点では、サーバーレスの学習機能を使って Foundry のプラットフォーム上で LoRA アダプターを学習する必要がある。
* 自分で学習した LoRA アダプターを持ち込む機能は、近く開放する予定。
* フルウェイトなら今日から持ち込める。
* 学習済みの LoRA アダプターをベースモデルにマージしてフルウェイトにし、LoRA アダプターによる性能低下をなくす使い方も、ロードマップに入っている。
* LoRA アダプターの学習と推論、Bring Your Own Weights はプレビューとして発表した。ベースモデルの機能は GA に向かい、今後数か月でより包括的にする予定。
* 自前の LoRA アダプターのアップロードは今はできないが、実現に必要なことを検討している。プロプライエタリモデルとオープンモデルの両方があるなかで、少なくともオープンモデルの LoRA アダプターのポータビリティは検討対象。

**質問 2：推論で最も重要なメトリクスは何か（毎秒 150〜200 リクエストという数字に関連した質問）**

質問者の声は聞き取りにくく、質問の全体像はトランスクリプトからは確認できません。Miguel 氏の回答は次のとおりです。

* AT&T では汎用的に構成している。Gemma 4 の 31B が現在よく使われており、ユースケースに依存する。
* そのモデルは、プレフィックスルーティング、KV キャッシュのオフロード、speculative decoding、ツール呼び出しを有効にしている。チャット、エージェントワークフロー、特定のドキュメント解析のユースケースをサポートしている。
* PDF 解析のユースケースでは 5〜7 秒程度のレイテンシは許容できる一方、RAG のユースケースは speculative decoding のパイプラインを使って素早く返せる。
* 最も大きな指標は**レイテンシ**。レイテンシが悪化すると失敗とみなされ、チケットやエスカレーションにつながる。その次がスループット。

質問のもう 1 つの部分（性能を出すための適切なサイジング）については、Miguel 氏とは別の登壇者が「プロンプトサイズを把握する必要がある」と返しています（話者は特定できません）。その先の詳しい回答は、時間切れのため行われていません。登壇者は、会場の外で会話を続けることを呼びかけて終了しました。

## 6. デモ・手順

このセッションでは、Foundry のポータルとコードを使ったデモが行われています（6.1〜6.3 は Manoj 氏が実施）。録音は音声のみのため、画面の細部（ボタンの位置や入力値の全体）は確認できません。以下は、語られた順番に沿って書いています。

### 6.1 カタログからの Managed Compute デプロイ

1. Foundry のモデルカタログを開き、Managed Compute で利用できるモデルをフィルターで絞り込む。Nemotron ファミリー、Gemma、DeepSeek などの最新のオープンソースモデルがある。
2. Gemma モデルを探してデプロイを開始する。
3. デプロイタイプは Managed Compute を選ぶ（グローバル。US または European のデータレジデンシーも選べる）。
4. GPU 構成を選ぶ。A100 1 枚ではコンテキスト長が 16K に制限され、A100 2 枚ではフルの 256K が使える。H200 や MI300 のような大きな GPU ならモデルが 1 枚に収まる。
5. コストを確認して、デプロイをクリックする。

時間節約のため、デプロイ済みのものを使って以降のデモを進めたと説明されています。

### 6.2 デプロイ済みモデルの利用

1. モデルのデプロイ一覧を開く。Serverless モデルと Managed Compute のデプロイが並んでいる。
2. Managed Compute のデプロイ（"Squent" と聞こえる名前。音声認識の都合で表記が確定できません）も、同じ Foundry エンドポイントを使う。
3. Playground で試す、またはコードスニペットを使える。
4. Chat Completions SDK で、同じ Foundry エンドポイントのまま、Serverless モデル（"GPT-62" と聞こえる表記。確定できません）から、デプロイ名を model パラメーターに渡すだけでオープンモデルに切り替える。
5. 「明日は雨が降るか」と質問する。このモデルは特定時点で学習したもので実際の天気データにアクセスできないため、「分からない」と回答するが、Chat Completions API で出力は得られる。
6. 次に、ツール呼び出しなどの高度なエージェント機能を使うため、このデプロイを Foundry のエージェントに接続する。
7. コードからこのエージェントを使い、株価を質問する。Responses API を使うので、会話履歴のサービス側での保存やツール呼び出しが使える。
8. マルチターンの会話のコードを見る。最初のメッセージでセッションコードを覚えるよう依頼し、2 つ目で再び「明日は雨が降るか」と聞く。エージェントサービス経由では Web 検索ツールを使い、天気を調べて回答する。
9. 前の会話 ID だけを渡して「セッション情報を探して」と頼むと、サービスに保存された前の会話から取り出せる。
10. プロンプトキャッシュの確認：同じ質問を 2 回送ると、1 回目はキャッシュなし、直後の 2 回目はキャッシュされたトークンが多く、リクエストの処理時間はおよそ半分になった。
11. （後半で）先ほどの株価の質問のトレースを開くと、Web 検索を行ったことが確認できる。

### 6.3 スケールとモニタリング

1. 1 インスタンス（4 GPU）のデプロイを確認し、編集からインスタンス数を増やせることを示す。
2. 5 インスタンス（合計 20 GPU）のデプロイがすでに動いており、処理できるトラフィックを確認する。
3. Azure Monitor で、1 インスタンスと 5 インスタンスのデプロイを比較する。メトリクスで合計トークンを選び、「deployment name で分割」して 2 つのデプロイを並べる。5 インスタンス側の方が、はるかに多いトラフィックを処理している。
4. 事前に作成したダッシュボードを見る。セッション開始前に実行していたテストの結果として、過去 1 時間のリクエスト数、トークン数（5 インスタンス約 4 億 5,000 万、1 インスタンス約 9,000 万）、429 の発生状況（1 インスタンス側が非常に多い）を確認する。
5. レイテンシ関連のメトリクスも見られることを説明する。

### 6.4 LoRA アダプターのデプロイ

1. Foundry Studio の学習ハブ（training hub）を開く。ここで LoRA アダプターを学習できる（詳細は同じ会場の午後 4 時のセッション）。
2. すでにアダプターが学習済みという前提で進める。示されたのは、デモで使っていた「QEN 3.8 27B」と聞こえるモデル（音声認識の都合で表記が確定できません）をベースとするアダプター。
3. デプロイを選ぶと、ベースモデルがすでに動いているターゲットのデプロイを選択するよう求められる。既存のデプロイを選ぶことも、新規に作成することもできる。操作はベースモデルのデプロイと同じ。
4. LoRA アダプターは通常ベースモデルに比べて非常に小さく、専用の GPU は不要で、ベースモデルと同じ GPU にロードされる。
5. 時間の都合で、プロジェクトにデプロイ済みのアダプターを使う。デプロイハブのアダプターの画面に 2 つのアダプターがある（財務ワークロード向けと法務チーム向け、という例えで「maybe」を付けて説明されており、実際の用途は音声からは確認できません）。両方とも同じターゲットデプロイを共有している。
6. 詳細を開くと、他のモデルと同じように見え、Chat Completions の推論 API を使える。Playground で推論リクエストを試すこともでき、操作感はベースモデルと同じ。

### 6.5 Bring Your Own Weights

1. コミュニティ（Hugging Face など）で見つけた重みや、自社で学習した重みを Foundry にインポートできる。
2. まずベースモデルを指定する。参照（browse）をクリックすると、カタログにあるベースモデル（Fireworks と Managed Compute などのプラットフォーム全体）が表示される。
3. ベースモデルを選ぶと、コマンドが生成される。それを CLI で実行すると、重みが Foundry プロジェクトにインポートされる。
4. インポートが終わると、重みが一覧に表示される。例として、"OSS 20B" のファインチューニング版で、長時間実行タスク向けに最適化されたモデルが示された（モデル名は音声認識の都合で確定できません）。
5. デプロイをクリックする。体験はベースモデルのデプロイと同じで、テンプレートを選んで開始する。

## 7. 注意点・発表者の気付き

* **GPU メモリと KV キャッシュのバランス**：GPU 1 枚だと、モデルの重みが大きいと KV キャッシュの余地が小さくなり、コンテキスト長が制限される（デモの例では 16K）。大きな GPU や複数 GPU の構成を選ぶことが、この制限の解消につながる。
* **LoRA アダプターは監視が必要**：デプロイ後も、利用率、レイテンシ、スループット、品質を継続して確認する必要がある、と明確に注意されている。
* **LoRA の機能には現時点の制約がある**：自前で学習した LoRA アダプターのアップロードは、現時点ではできない（Q&A 参照）。LoRA の学習と推論、Bring Your Own Weights はプレビューとして発表された。
* **「どちらを選ぶか」は利用者の判断**：Managed Compute は、カタログのモデルを使い、Microsoft 管理のランタイムとパッチで問題ない場合に向いている。カスタムカーネルや独自のサービングアーキテクチャが必要なら、自前のスタックが適している、と明言されている。
* **自前運用の負担（AT&T）**：GPU の種類、vLLM のバージョンとサポート、トラフィック、キャッシュ管理、計装を自分たちで把握する必要がある。さらに 200〜300 GPU の共有プールでは、新しい需要に素早く対応できない場面があった。
* **レイテンシが最優先（AT&T）**：レイテンシが悪化すると、チケットやエスカレーションにつながる。

## 9. まとめ

Managed Compute は、Foundry のカタログにあるオープンソースモデルを、専用 GPU 上のマネージドエンドポイントとして数分でデプロイできるサービスです。Serverless と同じ Foundry エンドポイントで使え、Agent Service と組み合わせてツール呼び出しも利用できます。複数インスタンスへのスケールと、Azure Monitor による可観測性も標準で備えています。

カスタムモデルについては、LoRA アダプター（最大 8 つまで 1 デプロイに接続）と、safetensors の重みの持ち込みの両方がデモで示されました。AT&T は、テレコム向けオープンモデルの学習データ生成（約 1 兆トークンを処理）と、カスタマーケアの通話処理（約 50% のコスト削減）で活用しています。

発表の最後には、Managed Compute の GA、150 以上のモデルの出荷、データゾーン機能が告知されました。Managed Compute が適するかどうかは、ワークロードごとに利用者が判断してほしい（「選択は皆さん次第」）、というのが発表者の立場です。
