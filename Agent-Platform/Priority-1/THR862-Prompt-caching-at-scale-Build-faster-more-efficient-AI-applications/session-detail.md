# THR862 Prompt caching at scale: Build faster, more efficient AI applications

## 1. はじめに

このセッションは、LLM アプリケーションの **prompt caching** を、速度・スループット・コストを同時に改善する実践的な手段として解説する約 25 分のシアターセッションです。Microsoft Foundry 側の担当者と GitHub Copilot 側のエンジニアが登壇し、GitHub Copilot での cache hit rate の改善実績、GPU 上のキャッシュの難しさ、Foundry が提供するキャッシュの選択肢、そしてベストプラクティスを順に説明します。

最も印象的な数字は、GitHub Copilot が Foundry 上で、同じプロンプト・同じリクエスト・同じモデルのまま、usage-based billing を開始した 6 月から現在までに、**費用を 68% 減らした**という点です。この記事では、その背景にある仕組みと、読者が自分のアプリで取れる手段を整理します。

LLM にリクエストを送ると、モデルは **prefill** と **decode** の 2 段階を通ります。システムプロンプトやツール定義のように毎回同じ内容を何度も prefill し直すのは無駄です。それを再利用するのが prompt caching です。発表では、これを「機能」というより、効率が良く、速く、コストを抑えられるアプリを作る実践的な手段の一つとして位置づけています。

発表の流れは次のとおりです。

2. GitHub Copilot の事例（cache hit rate、レイテンシ、コスト削減）

4. GPU 上でのキャッシュが従来の分散システムと違う理由

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**prompt caching は「オンにすれば終わり」ではない**という主張です。ワークロードごとに特性が違うため、自分のワークロードとユーザーにとって何が重要かを見極め、測定しながら調整する必要があるとされています。

もう一つは、これが**共有責任**だという点です。プラットフォーム側は routing などを最適化し、利用者側はプロンプトの構成、キャッシュキー、TTL などのベストプラクティスを守ります。両者が揃うことで、最もコスト効率の良いアプリが実現できる、というのが締めくくりの言葉です。

## 5. 発表内容の詳細

### 5.1 prompt caching の基本

LLM へのリクエストは、prefill と decode の 2 つのフェーズを通ります。

| フェーズ | 説明されている内容 |
| ---- | ---- |
| prefill | 入力を読んで理解し、transformer を通して **KV（key value）state** を作る。その state は GPU メモリに保存される |
| decode | 読み取った内容をもとに出力を生成する |

プロンプトが大きくなると、prefill の負荷が大きくなります。この段階を最適化できると、次の 3 つが同時に得られると説明されています。

- 最初のトークンまでの時間（time to first token）が速くなる
- GPU が他の処理に使える時間が増える（スループットの向上）
- キャッシュされた入力トークンの料金で済むため、コストが下がる

通常は速度、スループット、コストの間でトレードオフが生じますが、これは 3 つのバランスを取れる数少ない機能だとされています。経済性は約 **10 倍**で、キャッシュされたトークンは通常の入力の約 10 分の 1 の料金、新しいモデルではさらに安い **5%** になる場合もあるとの説明です。

特に効果が大きいのは、日常的なエージェント型ワークロードです。コンテキストが大きくなっても、システムプロンプトやツール呼び出しなどを一貫したプロンプトにまとめられれば、大規模にコストを下げられます。コーディングアシスタントのように、コードのコンテキストやプロンプトファイルが多いものが最大の効果を得やすい用途の一つで、GitHub との協業はここから始まった、と述べられています。

### 5.2 GitHub Copilot の事例

GitHub Copilot は 6 月に usage-based billing を開始しました。これにより、顧客との関係が変わり、GitHub は**顧客に代わって効率を管理する立場**になった、と Taylor 氏は説明しています。顧客自身が、ハーネスやプラットフォーム側の動きによる cache hit rate を制御できる範囲は限られているため、GitHub 側で cache hit rate を上げ続けることが重要になりました。

コスト削減の手段には、次のものが挙げられています。

- KimiK3 や MAI モデルなど、Frontier Labs の何分の一かのコストで高い能力を持つ open weight モデルの提供（モデル名は音声認識の都合で表記が確定できません）
- 過去 1 年間の、cache hit rate 改善への投資

6 月以降の改善の結果、GitHub Copilot ユーザーの**平均 cache hit rate は 90% を超えました**。プラットフォームとインフラ側の改善は「上げ潮はすべての船を持ち上げる」効果があり、コンテキスト管理や prompt caching に独自の投資をしなかったクライアントでも、cache hit rate が上がったとのことです。

**ワークロードによる違い**

スライドのグラフでは、ワークロードごとに cache hit rate の水準が大きく違うことが示されました。

| ワークロード | 特徴 |
| ---- | ---- |
| Copilot Chat（github.com で質問する） | 追加質問は 1〜2 回程度で、ユーザーはその後離れる。同じデータを何度も送らないので、hit rate は伸びにくい（グラフでは一番下の赤い線） |
| エージェント型 | ユーザーに代わって数十、数百、ときには 1,000 回以上のリクエストを送る。同じコンテキストに追記していくため再利用性が高く、prompt caching と相性が良い |

**レイテンシとコスト**

一般にコンピューティングでは、速さを求めると費用が増えるという価格と性能のトレードオフがあります。AI モデルでも、OpenAI が専用ハードウェアで動く fast / ultra-fast 版を桁違いの価格で提供している例が挙げられました。これに対して cache hit rate を上げる投資は、**レイテンシも下がる**という、直感に反する性質を持ちます。コスト削減であり、同時に性能改善でもあります。

本番データによるレイテンシのグラフ（MAI code 1.1 flash、過去 1 か月、コンテキストサイズ別のコホートに分けたもの）から、次の 2 点が読み取れると説明されました。レイテンシはモデル、reasoning effort、コンテキストサイズの影響を受けるため、このグラフは 1 つのモデルに限った見方です。

1. cache の効率が上がるにつれて、すべての線が右下がりになり、非常に小さなリクエストでもレイテンシが下がる
2. すべての線が**収束**する。hit rate が 90%、95%、97% に近づけば、コンテキストが大きすぎてユーザー体験が悪化することを心配しなくてよくなる。プロンプトを正しく構成し、cache hit を活かしている限り、モデルに必要なデータを必要なだけ与えられる

**コストの数式的な見方**

続いて、本番データではなく数式から描いたグラフが示されました。キャッシュされていないトークンは、多くのモデルで cache トークンの 10 倍のコストがかかるため、cache hit rate が 100% に近づくにつれて、ユーザーにとっての影響は**双曲線的**に大きくなります。

- hit rate を 0% から 1% に上げても、コスト削減は 1% 未満
- 97% から 98% に上げると、その 1 リクエストで **8%** 削減できる
- さらに上げると、効果は複利的に積み上がる

GitHub Copilot では、クライアント側と、Azure Foundry との協力によるプラットフォーム・インフラ側の改善により、usage-based billing の開始から現在まで、**同じプロンプト、同じリクエスト、同じモデルで、ユーザーのためのコストが 68% 減りました**。ユーザーが行動を変えなくても、Foundry 上の GitHub Copilot に払う金額は 6 月時点の **3 分の 1** になった、という説明です。Saloni 氏はこの 68% が持ち帰ってほしい数字だと述べています。

### 5.4 なぜ GPU のキャッシュは難しいのか

バックエンドの設計に詳しい人なら、「キャッシュは簡単で、Redis を置けば終わりでは」と思うかもしれません。Taylor 氏は、GPU のデータ処理の性質上、そう単純ではないと説明しています。

- キャッシュに保存されているのは **KV cache**、つまりモデルの activation にあたる**中間状態**で、データベースや API から取ってきて変わっていなければキャッシュから返す、という種類のものではない
- 使うには、この中間状態を GPU に戻す必要がある。最終的に KV cache は GPU メモリに載っていなければならない
- そのため、shared nothing アーキテクチャや広範な負荷分散といった、従来の分散システムの定石は、期待ほど効果的ではなく、別の問題も起こす

1 人のユーザー・1 つのセッションだけを見れば、すべてのリクエストが同じ GPU に行くのが理想です。ユーザーが 1 人ならそれでうまくいきます。しかし GPU は計算とメモリの両面で制約があります。KV cache の activation はモデルの重みよりずっと小さいものの、**小さくはありません**。GPU は高価なので稼働率を上げたくなりますが、90% 以上を目指すと、わずかな不均衡やトラフィックの変動で限界を超え、GPU の throttling が起こります。

throttling が起きると、リクエストがキューで待たされ、低レイテンシの恩恵が帳消しになります。また、メモリが限られているため、性質の異なるワークロードが同じ GPU に載ると cache eviction が増え、hit rate が下がります。

一方の端が shared everything、もう一方の端が shared nothing で、どちらにも良い解はありません。**その中間のどこに落ち着くかは、ユースケースに強く依存する**という結論でした。

### 5.5 Foundry のプラットフォーム側の取り組み

Saloni 氏は、Taylor 氏が挙げた問題（throttling を避けたい、TTFT を改善したい、cache rate を上げてコストを下げたい）は、Foundry で大規模に使う多くの顧客に共通するパターンだと述べ、プラットフォーム側の改善として次を挙げています。

1. **Runner**：継続的に動き続けるワークロード。監視し、見えたものをもとに改善するために使う。現状が分からなければ最適化できないため、強く勧められている
2. **Smart affinity layer**：同じセッションからのリクエストを同じバックエンドのエンジンレプリカにルーティングし、sticky にして、その後のターンも同じ場所に送られるようにする
3. **負荷分散**：キューが詰まるホットスポットでは TTFT が悪化するため、他に空いているエンジンへ振り分ける。最初に別のエンジンへ回されたリクエストは TTFT に影響を受けるが、キューで待ち続けるよりは処理される方が良い、という考え方
4. **Advisor**（社内で構築）：実際の cache rate と、プロンプトから得られる**達成可能な cache rate** の差を調べ、その原因を切り分ける。原因が deployment をまたぐ routing やレプリカをまたぐ routing なのか、あるいは適切な prompt cache key を指定していないために stickiness が得られていないのか、を見る
5. **階層キャッシュ**：キャッシュを階層として捉え、インフラで使えるものを活用しようとしている。既定では GPU メモリに置かれ、これが最速だが希少。そこで CPU メモリへのオフロードを考え、さらに GPU マシンに付いている SSD も使おうとしている。SSD は GPU や CPU より遅いが、計算し直すよりはずっと速い。さらに、ホットスポットがあるときに、同じマシンの SSD だけでなく、別の場所で使用率の低い GPU の SSD も使えないか探っている

Advisor については、製品として公開すれば役に立つかどうか、聞きたい（セッションの後で教えてほしい）と Saloni 氏が参加者に呼びかけています。階層キャッシュのうち、別マシンの SSD の活用は「探索している」段階として語られています。

### 5.6 利用者が選べる 3 種類のキャッシュ

下位の層で作った仕組みを、利用者が使えるレバーとして提供しています。

| 種類 | 説明されている内容 |
| ---- | ---- |
| Implicit cache | 自動で既定の方式。ターン数の少ない通常のチャットに向く。始めるならこれで十分。best effort で **10〜15 分**、インメモリキャッシュによる |
| Extended | 最大 **24 時間**に延ばせる。best effort で、**古いモデルでのみ**サポートされる。メモリから取れる範囲を超えられ、SSD も使えるため、多くの顧客が使い始めた |
| Explicit caching | 新しいモデル（発話では「GPD 5.6 and plus」。音声認識の都合で表記が確定できません）で提供され、標準になっている。GitHub も広く使っている。implicit と explicit の両モードがあり、explicit では**ブレークポイント**を置いて、キャッシュしたい範囲を正確に指定できる |

加えて、最近 OpenAI が導入し、Microsoft も導入した機能として、**TTL**（キャッシュを保持する時間）を設定できます。通常のエージェント型ワークフローや短いターンのマルチターンチャットなら約 30 分、長時間動くエージェントなら 10 時間といった例が挙げられました。長時間動くエージェントでも、コンテキストをその間保持してキャッシュを保証したい、という文脈です。

### 5.7 ベストプラクティス

Saloni 氏は、顧客からのチケットやサポート通話のたびに案内している内容として、次を挙げています。

**安定した内容をプロンプトの先頭に置く**

最もよく見かけるのは、プロンプトの冒頭にタイムスタンプを付けてしまう例です。送信時刻を見たいという理由ですが、これは毎回内容が変わってしまうため cache rate を損ね、常に動的にしてしまいます。システムプロンプト、ツール呼び出し、指示セットなどの**安定した内容を上に置き**、それを安定させるほど、cache hit の可能性が高まります。

**設定項目**

| 設定 | 説明されている内容 |
| ---- | ---- |
| prompt cache key | バックエンドでは、「このキーに対しては同じバックエンドのエンジン・インスタンスにルーティングし続ける」と解釈される。stickiness の確保に役立つ |
| ブレークポイント | 新しいモデルのワークロードの多くが使う。リクエストがエンジンに届いた後、そのエンジンに**何をキャッシュするか**を制御する。最大 **5 つ**まで指定できる。指定しない場合は implicit となり、ブレークポイントはプロンプトの末尾に置かれる。より細かく制御したい場合は explicit のブレークポイントを使う。発話では、これもプロンプトの末尾に付くと説明されている |
| TTL | キャッシュに残す時間。ワークロードに応じて設定する |

**ワークロードに合わせて選ぶ**

- 短いプロンプトのチャット：implicit で十分。追加費用はかからない
- 長いコンテキストのワークロード（GitHub のような copilot など）：extended か explicit を使い、何がどれだけの時間キャッシュされるかを制御する
- 長時間動くエージェント型ワークフロー：さらに長く保持する

**書き込みコストの考慮**

長く保持すると、コストがかかります。キャッシュの**書き込み**は高く、**読み取り**は大幅に安くなります。読み取りは新しいモデルで通常の入力の 10〜5% です。ブレークポイントと TTL が保持期間を決め、そこで書き込み料金が生じます。発話では、**30 分の書き込みは通常入力トークンの 1.25 倍、12 時間は 2.5 倍**と説明されています。どこで最も効くのかを、ワークロードごとに比較する必要があります（なお、別の箇所では長時間の例として「10 時間」も挙がっており、時間の数字は音声認識の都合で確定できません）。

**測定する**

パターン、token の hit rate、レイテンシ、スループットなどの指標が見えていなければ、コスト削減はできません。

### 5.8 GitHub の運用の工夫

Taylor 氏は、GitHub には挙動が大きく異なる複数のクライアントサービスがあり、「measure, measure, measure」が鍵だと述べています。測定していないものは改善できず、さらに自分のワークロードを知っている必要があります。

- GitHub には、完全に非同期でバックグラウンドで動くエージェント型の処理がある。ユーザーが画面を見て待っているわけではないので、time to first token は気にせず、処理を遅らせてもよい。そのため、cache hit rate の制御以上に複雑な方法で、異なるワークロードを組み合わせて全体に合理的な形にできる。これは、測定と、各ワークロードで何が重要かの理解があって初めて可能になる
- すべてに**異種混在のモデルプール**を使っている。チャット用とエージェント用に専用のプールを分けていない。GPU は希少で、分ける余裕がなく、大きな代替可能（fungible）なプールで動かす方が効率的に動かしやすい
- 複数のクラウドサービスプロバイダーを使っている。Foundry ではあまり問題にならないが、別のモデル群（発話は「Agentix models」で、音声認識の都合で表記が確定できません）では、24 時間キャッシュが 5 分キャッシュよりかなり高価になる。そのため、「キャッシュは良いものなので 24 時間にしておけばよい」とは言えない。基本モデルが高価で、すでに効率が高く hit rate の改善が小さいなら、本当に節約になるのかという**分岐点**を見る必要がある
- cost や cache hit rate を制御するレバーは多いが、**互いに影響し合う**。何が効いているかを知る唯一の方法は測定である

### 5.9 GitHub の改善の内訳

Saloni 氏は、GitHub のグラフの最初の上昇（約 60% から 85%）が**プラットフォーム側の改善**（先に述べた smart affinity による routing）の効果であり、その後は GitHub 側が、プロンプト、stickiness のキー、各クライアントに合わせた TTL を改善して段階的に上げた、と説明しています。

セッション内で質疑応答の時間は設けられていません。時間がほぼ終わったとしたうえで、二人が会場で質問を受けると述べています。

## 6. デモ・手順

このセッションでは画面を使ったデモは行われていません（スライドのグラフと口頭の説明が中心です）。手順として読み上げられたコマンドやコードもありません。

発表で語られた実践のポイントを順にまとめると次のとおりです。

1. 自分のワークロードを測定する（hit rate、レイテンシ、スループットなど）
2. 安定した内容（システムプロンプト、ツール定義、指示）をプロンプトの先頭に置き、タイムスタンプのような毎回変わる内容を先頭に入れない
3. prompt cache key を設定し、同じバックエンドに routing されるようにする
4. ワークロードに応じて implicit / extended / explicit を選ぶ
5. explicit では、ブレークポイント（最大 5 つ）と TTL を調整する。書き込みコストと読み取りの割引を比較する

## 7. 注意点・発表者の気付き

- **「オンにすれば終わり」ではない。** ワークロードごとに特性が違い、見るべき点が異なります。
- **プロンプト先頭のタイムスタンプは cache rate を損なう。** 最もよく見かける失敗として挙げられています。
- **GPU の稼働率を上げすぎない。** 90% 以上を狙うと、わずかな不均衡で throttling が起き、キュー待ちで低レイテンシの恩恵が失われます。異種のワークロードが同じ GPU に載ると cache eviction も増えます。
- **長く保持するほど書き込みが高い。** TTL が長いほど書き込み料金が上がるため、ワークロードごとに分岐点を確認します。
- **レバー同士は影響し合う。** 1 つだけ変えて終わりにせず、測定が必要です。
- **Extended は古いモデルのみで、best effort。** Explicit は新しいモデル向けです。
- Advisor や、別マシンの SSD の活用は、それぞれ製品化の検討・探索の段階で、提供時期は語られていません。

発表で語られた効果は次のとおりです。

- GitHub Copilot では、同じプロンプト・リクエスト・モデルで、コストが **68%** 減り、費用が 6 月時点の約 3 分の 1 になった。平均 cache hit rate は **90% 超**

## 9. まとめ

prompt caching は、prefill の重複を減らして、速度、スループット、コストを同時に改善する手段です。GitHub Copilot は、プラットフォーム側の affinity routing による改善（約 60% から 85%）と、プロンプトやキー、TTL の改善を組み合わせ、平均 cache hit rate を 90% 超、費用を 68% 削減しました。

利用者側の要点は、安定した内容をプロンプトの先頭に置くこと、prompt cache key で routing を安定させること、ワークロードに合う implicit / extended / explicit と TTL を選ぶこと、そして何より測定することです。プラットフォームと利用者の**共有責任**で最適化していく、というのが発表者のメッセージでした。
