# BRK274 Hand off the task or take the keyboard in VS Code

## 1. はじめに

このセッションは、VS Code の GitHub Copilot を使って「作業をエージェントに任せる」ことと「自分でキーボードを握ってコードを触る」ことを、どう両立させるかを紹介するものです。登壇者は VS Code チームの 2 名で、普段の自分たちの働き方を、ライブデモと録画デモを交えて見せていきます。

扱う内容は、従来のエディタ画面（editor window）での Copilot Chat から始まり、エージェント中心の画面である agents window、複数モデルの比較（compare models）、モデルを自動で振り分ける Copilot Fusion、統合ブラウザ、Canvas、画像生成、PR の作成とマージまでです。

発表全体を貫くメッセージは、**VS Code は今までのエディタのまま、エージェントの機能が追加されただけで、AI をどこまで使うかは利用者が決められる**ということです。AI の利用を始めたばかりの方にも、すでに多用している方にも向けた内容になっています。

## 3. 何に関する発表か

テーマは「AI コーディングで、作業を任せることと、コードの近くにいることのどちらかを選ばなくてよい」という考え方です。登壇者は、AI の使い方は人それぞれで、自分たち自身もいつも初心者のようなものだと話しています。そのため発表も、各自の働き方を紹介する学びの場という位置づけです。

発表は、次の流れで進みます。

1. エディタ画面の Chat から始め、モデル・エージェントモード・権限モードを選んで依頼を送る
2. 同じセッションを agents window で開く。Agent Host Protocol（AHP）によるセッションの共有と、ハーネスの切り替え
3. compare models（複数モデル・ハーネスの並列比較）と Copilot Fusion
4. agents window の紹介（セッションの一元管理、Blobby、ファイル編集、統合ブラウザ、Canvas、モックアップ、画像生成）
5. エディタ画面での詳細なレビュー（変更の Keep）
6. agents window からの PR 作成・マージ
7. カスタマイズ（plugins、MCP、skills など）の紹介とまとめ

登壇者が繰り返し述べているのは、次の 4 点です。

- **自分のワークフローに合わせてカスタマイズする。** 他の人が公開したものを見て刺激を受け、取り込んで自分向けに直す、という使い方が勧められています。

## 5. 発表内容の詳細

### 5.1 エディタ画面で依頼を送る

最初に見せたのは、おなじみの VS Code のエディタ画面です。右側に Chat パネル、左側にエディタがあり、編集もプロンプトも、暗黙のコンテキスト（implicit context）も従来どおり使えます。依頼を送る前に、登壇者は 3 つの設定を行っています。

1. **モデル**：新しい Copilot Fusion というモデルルーターを選択（詳細は後述）
2. **エージェントモード**：現在は interactive が選ばれており、ほかに plan mode と autopilot がある。いずれも Copilot ハーネスが提供するモードで、ここでは autopilot を選択。autopilot はタスクが完了したと判断するまでループを繰り返し、最初から最後まで自走するモード
3. **権限モード**：承認の手間を減らしたい場合に、エージェント自身に承認すべきかどうかを判断させる新機能 assisted permission を選択

その状態で、サイト用のモックを事前に用意していたと述べたうえで、Blobby というキャラクターのカード（性格タイプ）を実装する旨の依頼を送っています（依頼文は音声認識の都合で一部が確定できません）。

続いて、あるボタンを押して、同じセッションを新しい **agents window** で開きました。agents window はエージェント中心の画面ですが、見た目や使い心地は VS Code そのままで、エディタ画面と同じセッションを共有します。VS Code を離れたわけではなく、「ビューが 2 つある」という位置づけです。コードを中心に見たいか、チャットを中心に置きたいか、という作業時の意識に合わせて選べます。

### 5.2 Agent Host Protocol（AHP）

ここで「AHP とは何か」という説明が入ります。登壇者は、まず導入の背景を次のように話しています。

- 約 1 年半前の時点では、長時間動くセッションに問題があった。エージェントに仕事を任せても、ノート PC の蓋を閉じたりウィンドウを閉じたりするとエージェントが止まってしまう
- 以前（昨年中ごろか後半という話し方）に、チャットを離れて別のチャットに移り、複数のチャットを並列に動かせるようにした。しかしウィンドウを閉じると体験全体が終わるという点は同じだった
- もう 1 つの要因は Copilot SDK。VS Code で使っている Copilot ハーネスに SDK を採用し、VS Code、agents window、Copilot app、Copilot mobile app、GitHub.com など、GitHub Copilot のあらゆるクライアントで同じハーネス・同じランタイムを共有することで、体験を揃えたかった

AHP は、**エージェントセッションとインターフェースを安全に同期させておくための共通言語**と紹介されています。構造は次のとおりです。

| 要素 | 役割 |
|---|---|
| agent host | 1 つのホストが 1 つの実行中セッションを持つ。メッセージ、ツールの動き、承認など、ランタイムで起きることはすべてここを通る |
| エディタ、window、各クライアント | エージェントが「どこで動いているか」ではなく、「何が起きているか」を表示するだけ |

つまり、あるマシンで承認が必要なツール呼び出しが出ても、そこを離れて別のウィンドウに移ってから承認できます。セッションが永続的だからです。ブログ由来の図では、VS Code でチャットを開始すると agent host に反映され、Copilot app も同様に同期し、スマートフォンは再接続の際に行われた操作を確認して同期する、という流れが図示されていました。詳しい解説は、同チームのエンジニア（Connor）が公開したブログにあるとのことです。

録画のデモ（画面が小さかったと登壇者が述べています）では、同一セッションを Copilot mobile app、VS Code の agents window、VS Code のエディタ画面の 3 か所で同時に動かしている様子が紹介されました。承認が必要になればどこにでも通知が出ます。登壇者は「何を使えばよいか」とよく聞かれるそうですが、答えは「どれか 1 つではなく、好きなものを使い、同じセッションのまま続ければよい」です。昼間に散歩に出るときなど、スマートフォンからエージェントを動かし続けられるのが便利だと話しています。

### 5.3 モデルとハーネスの選択

最初のデモの振り返りとして、次の点が説明されました。

- モデルは、エディタ画面でも agents window でも選択できる
- ハーネスも同様に選択できる。Codex や Claude（トランスクリプトでは "cloud" と書き起こされています）の利用上限に達した場合は、**セッションの途中でハーネスを切り替え**、Copilot ハーネスで続きから再開できる。経緯を説明し直す必要はない
- 例えば Claude Code をよく使い、統合ターミナルが好きな人でも、同じ請求・同じアカウントで、Claude ハーネスや Codex ハーネスを VS Code 内から使える。使い慣れた UX やツールがあれば、そのまま VS Code で使える

### 5.4 compare models（モデルの比較）

agents window の機能のうち、まず紹介されたのが compare models です。「どのタスクにどのモデルが最適か分からない」「速度や費用など、何を最適化したいかで答えが違う」という悩みに対し、チャットをコピーして複数モデルに貼り付けて試す手間を省く機能として説明されています。実行に時間がかかるため、デモは録画でした。

手順は、語られた範囲で次のとおりです。

1. 比較したいモデルを選ぶ（ハーネスも比較対象にできる）
2. **judge**（審査役）と **synthesizer**（統合役）を選ぶ
3. 送信すると、各モデルが並列のセッションとして実行される
4. 親セッション（orchestrator）の下に、入れ子の子セッションがぶら下がる。グリッドレイアウトで同時に見られ、各セッションがそれぞれのモデルで処理を進める
5. judge が結果をまとめ、synthesizer が統合して「何が最良か」の提案を出す。勝者と、その理由も確認できる

登壇者によれば、見せた録画は少し古いものでした。その録画では、出力トークン数では MAI code 2 flash（聞き取りによる表記）が、所要時間では Claude Sonnet 5.5 が勝ち、総合判断では Copilot Fusion が選ばれました。解決策の欄には、他モデルとの比較、検証、コード品質に関する記述がありました。

さらに、Fusion と Opus 5.5 と GPT-6.2 Astra（音声認識の都合で表記が確定できません）をすべて high で比べた、より新しい録画では、Fusion が勝ったそうです。コスト面では、Fusion は 30 万〜40 万トークン程度を使い、トークン数は他より多かったかもしれないが、AI credits で見ると支出は低かったと話しています。この点は今回見せた比較画面には出ておらず、「判断の際には考慮される」という趣旨です。新しい録画は、スライド共有時に差し替えるとのことです。

使い方の考え方としては、次のように語られています。

- チームによって、コストを極端に抑えたい場合もあれば、特定の課題だけは高い計算量が必要な場合もある。タスクごとに合うモデルを見つけるための機能である
- すべてのタスクで毎回実行する必要はない。モデルの得意不得意が分かれば、そのモデルを使うようにする
- 新しいモデルが出たときに、また比較して好みを確かめられる

### 5.5 Copilot Fusion

Copilot Fusion は、依頼の複雑さや、長時間かかりそうかどうかに応じて、**モデルを選んで振り分ける（ルーティングする）**仕組みとして説明されています。

- **single**：1 つのモデルを選ぶ
- **Cascade** など複数モデルの形：ドラフトのパスをあるモデルで、メインのパスを別のモデルで、最終レビューのパスをさらに強力なモデルで行う、といった組み合わせ

登壇者は、AICs（AI credits）の節約や、オーケストレーションを任せられることが利点だと述べています。安価なモデルをある作業に、高価で長時間動くモデルを別の作業に、と作業内容に合わせて使い分けます。各パス（draft、main、review）は個別にクリックして中身を見たり、ステアリングしたりできるとのことで、登壇者は「そのデモを用意できていればよかった」と話しています。

また、体験談として、最初は 1 つのセッションをずっと見ていて出力もすべて確認していたが、モデルや用途ごとの経験が積み重なって信頼できるようになり、今は用途によってモデルを指定したり Fusion に任せたりしている、と語られています。

### 5.6 agents window の価値

登壇者が agents window の必要性として挙げたのは、次のような実体験です。

- 以前はプロジェクトごとにウィンドウを開いており、切り替えが大変だった。複数のチャットを動かすと、セッション一覧とチャットの往復に疲れ、文脈を忘れ、どのセッションが自分の入力待ちかも分からなくなった
- agents window では、**すべてのワークスペースのセッションを 1 か所で見られ、注意が必要なときは通知される**。いちいち見張らなくてよい

エディタの機能が失われないかという疑問にも、次のように答えています。

- 変更されたファイルを開いて、JavaScript でも Markdown でも編集できる。エディタは同じ Monaco エディタで、配置が変わっているだけ
- 新しい Markdown エディタがあり、プレビューのまま直接編集できる。ロックして閲覧だけにすることも、従来のテキストエディタに切り替えることもできる
- セッションを切り替えると、そのセッションに対応するリポジトリのファイルが表示される。複数のウィンドウを開かずに済む

### 5.7 Blobby（ペット／マスコット）

agents window や VS Code ウィンドウに現れる Blobby は、新しく採用したペット兼マスコットです。タブを切り替えると現れ、ドラッグして動かしたり、hacky sack のような遊びをさせたりできます。

- 楽しさだけでなく、Copilot の使い方を学ぶ手段としての **achievements（実績）** があり、機能を使うと帽子が解除される。例として、過去のリクエストを編集する、最初のチャットを送る、といった行動が挙げられている
- 有効化は「VS Code pet」から行います（設定のどこにあるかは音声からは分かりません）。`/blobby` コマンドで色を変更でき、stable、insiders、exploration の色が気に入らなければ自分で選べる
- 待ち時間に遊べる小さなゲームもあり、リリースノートに載っているかもしれない、と登壇者は話している。コミュニティ向けに、ハイスコアに何か特典を出す案も話に出たが、決定ではないという言い方でした
- 登壇者は、かつての Clippy の現代版のようなものであり、エージェント活用の学習をゲーム的にして楽しくするものだと説明しています

### 5.8 統合ブラウザをエージェントと共有する

デモのアプリは、「あなたはどの Blobby か」を診断する性格テストのサイトで、GitHub Pages で公開されています（発表の最後に QR コードで案内）。

登壇者は、agents window 内で統合ブラウザ（integrated browser）を開き、そのページをエージェントと共有しました。ブラウザを開く入り口は複数あり、ブラウザの地球アイコンや「open integrated browser」からも開けます。共有後、「クイズを代わりに受けて」と依頼すると、エージェントがクリックを重ねて回答していきました。裏では Playwright を使っているとのことです。結果として Copilot Fusion が選んだのは、top hat と monocle の Blobby でした。

登壇者は、画面を説明して往復する必要がなく、エージェントがページを見て操作できる点を評価しています。手を完全に離すことも、途中で中身を見て自分で編集することもでき、どの程度ハンズオンにするかを選べるというのが主旨です。統合ブラウザの技術的な内部については、実装に関わった Joaquin が会場にいると紹介されました。

エージェントに作業範囲を絞らせたい場合は、**「add element to chat」** ボタンを使います。ページ上で対象（デモではヘッダー）をクリックすると、チャットに要素情報（div、HTML、CSS など）が添付されます。

### 5.9 Canvas と Awesome Copilot

この Blobby の性格タイプをどれにするかを決めるために使ったのが、**Canvas** です。デモでは、チームが agents window 内でエージェントの助けを借りて作った Kanban 形式の Canvas が示されました。Canvas は、エージェントが必要なものをなんでも作ってくれる仕組みで、エージェントと直接つながり、同じワークスペースの他の人とも共有できる、と説明されています。

自分で一から作るのが大変なとき、あるいはひらめきが欲しいときに使うのが、**Awesome Copilot** という Canvas のマーケットプレイスです。デモでは、James という人が作った Canvas を絞り込んで見ており、その中の例として、バックログの issue トリアージを「Tinder のようにスワイプ」で行う backlog swipe triage が紹介されました。VS Code 内にインストールするボタンがあり、取り込んだ後に編集して、自分のワークフローに合わせられます。他の人が作ったものを見て自分の働き方を進化させている、と登壇者は話しています。

カスタマイズ（Canvas、plugins、MCP サーバー、組み込みの instructions、エージェントモードなど）の詳細は、今週の別セッションで扱われているとして、そちらの視聴を勧めています。

### 5.10 HTML モックアップと declarative UI、画像生成

agents window で現在取り組んでいる新機能として、次が紹介されました。事前に準備したものが画面に出ています。

- **HTML モックアップ**：コードを実際に変更する前に、エージェントがチャット内に HTML でモックアップを描画する。デモでは、新しい 3 種類の Blobby を 3 枚のカードとして見せた。裏側は単なる HTML で、変更前のプレビューとして使える
- **declarative UI**：グラフや指標をチャット内に直接描画する。ホバーで数値を確認でき、別アプリや別タブにしなくて済む軽量な見せ方として、依頼すればエージェントが作る
- **画像生成**：hype Blobby 用の背景画像を生成するよう依頼した。裏側では GPT image 2.5 flare（音声認識の都合で表記が確定できません）が使われている。選んでいたモデルは Copilot Fusion だったが、どのモデルを使っていても（Fable、Opus、Gemini など）、画像生成は現時点ではこのモデルに委任される。将来は使うモデルを選べるようにする予定とのこと

背景画像が生成された後、2 つの画像を組み合わせて hype Blobby を実装する依頼を出しました。実行は時間がかかるため、そのまま走らせたまま次の話題に移っています。

登壇者は、機能が多くて圧倒されるかもしれないので、小さく始めて少しずつ足すのがよい、と述べています。

### 5.11 エディタ画面での細かいレビュー

AI をどれだけ使うかには幅があります。完全に任せる「vibe coding」を好む人もいれば、差分を見たい人もいます。登壇者は、agents window から対応する work tree をエディタ画面で開き、**エージェントが行った編集を一覧し、気に入ったものを Keep できる**ことを示しました（デモ時点では、その work tree に編集はなかったと述べています）。hunk 単位、ファイル単位で受け入れる運用も、エージェントを信頼して任せる運用も、どちらも支えるという立場です。

> 補足：このデモは、バッテリー残量が少ないという話をしながら行われました。

信頼については、次のように語られています。

- 最初は「AI が悪いコードを大量に書くのではないか」と心配だった
- 生成されるコードを見続けることで品質を確認でき、今は信頼している
- compare models で、そのタスクにはそのモデルのコードが合う、と確認できることも信頼につながった

### 5.12 agents window から PR を作成する

「作業を作るだけでなく、PR まで進めたい」という流れで、最後のデモに移ります。

1. 以前に作成した work tree を選び、**create PR** を押す。PR のタイトルと説明が自動生成され、auto merge をオンにするか、手動でマージするかを選べる
2. 最初の PR 作成は、少し待っても完了しなかった。登壇者は「ライブデモの証拠ですね」と冗談を言い、別のものに切り替えた
3. 別の、実際に取り組んでいたバグ修正で PR を作成。しばらくすると、チャット内に pill が表示され、「draft PR requested」となった
4. その PR を agents window 内で直接開いた。リポジトリは公開されたもの（VS Code）で、登壇者は、会場のみなさんの協力で VS Code を更新できた、という趣旨のことを述べている
5. 新しい PR ビューでは、個人または Copilot code review によるコメント、チェックやパイプラインを確認でき、「ready」にマークできる
6. **agent merge / autopilot** をオンにすると、CI が全部成功し PR がマージされるまで、エージェントが修正を続ける

### 5.13 カスタマイズとマーケットプレイス

時間の都合で詳しく触れなかった点として、カスタマイズと自動化が挙げられています。agents window には plugins、MCP、skills、agents など、使っているものを追加でき、マーケットプレイスも統合されています。自分で持ち込むことも、マーケットプレイスから取り込むこともできます。

チーム内で使っている skills の例として、登壇者の一人は **Council Review** を挙げています。敵対的（adversarial）なコードレビューを依頼するスキルで、複数のサブエージェントを送り出し、結果をまとめて返します。Fable を使うように依頼すれば、Fable で Council Review ができます。このスキルは共有できます。VS Code のリポジトリにあるチームの skills は、ほぼ公開されているはずだとも述べています。

## 6. デモ・手順

このセッションには、**画面を使ったデモが複数あります**。ライブのもの、録画のもの、事前準備した結果を見せたものが混在します。画面の細部は音声からは確認できないため、以下は語られた範囲に限ります。

### 6.1 ライブ：エディタ画面から agents window へ（5.1 に対応）

1. エディタ画面の Chat パネルで、モデルに Copilot Fusion を選択する
2. エージェントモードに autopilot を選択する
3. 権限モードに assisted permission を選択する
4. Blobby のカードと性格タイプの実装を依頼する
5. 依頼を実行しながら、ボタンを押して同じセッションを agents window で開く

### 6.2 録画：AHP と複数クライアント（5.2 に対応）

1. 同じセッションを、モバイルアプリ、agents window、エディタ画面で同時に動かしている様子を見せた
2. 承認が必要になると、どのクライアントにもポップアップが出る

### 6.3 録画：compare models（5.4 に対応）

1. autopilot と、assisted または allow all（登壇者は「どちらかを選んだと思う」と話しています）で開始
2. 比較するモデル、judge、synthesizer を選択
3. 並列セッションが親セッションの下にグリッド表示され、judge が集計、synthesizer が統合
4. 最下部に、出力トークンと所要時間の勝者が表示され、総合では Copilot Fusion が選ばれた

### 6.4 ライブ：統合ブラウザの共有（5.8 に対応）

1. 統合ブラウザで Blobby 診断サイトを開く
2. ブラウザページをエージェントと共有する
3. 「クイズを代わりに受けて」と依頼する
4. エージェントがクリックを進め、結果が top hat と monocle の Blobby になる
5. 「add element to chat」ボタンでヘッダー要素をチャットに追加する

### 6.5 Canvas とマーケットプレイスの画面（5.9 に対応）

1. Kanban の Canvas を全画面表示で見せる
2. Awesome Copilot で James の Canvas を絞り込み、backlog swipe triage を紹介する

### 6.6 モックアップ、declarative UI、画像生成（5.10 に対応）

1. 事前に作ったモックアップ（3 枚のカード）をチャット内で表示し、エディタ画面で HTML を見せた
2. declarative UI の指標にホバーして確認した
3. hype Blobby 用の背景画像の生成を依頼し、2 つの画像を組み合わせる実装を依頼した

### 6.7 ライブ：エディタ画面での確認と PR 作成（5.11、5.12 に対応）

1. agents window からエディタ画面に移り、work tree の編集を確認する構成を見せた
2. create PR で 1 件目を実行（完了せず）
3. 2 件目のバグ修正で draft PR を作成し、PR ビューでコメント、チェック、agent merge を紹介した

## 7. 注意点・発表者の気付き

- **ハーネスの上限**：利用上限に当たっても、ハーネスをセッション途中で Copilot ハーネスに切り替えて続けられる、と説明されています。
- **機能は変化し続ける**：発表で見た内容は、翌週、翌々週にも増える可能性があるという前提で語られています。見せた compare models の録画も古いものでした。
- **画像生成のモデル**：現時点では、選択中のモデルに関わらず GPT image 2.5 flare（表記は確定不能）に委任されます。選択できるようになるのは将来です。
- **機能の多さ**：一度に全部使おうとせず、小さく始めるのがよい、という助言です。
- **信頼の築き方**：エージェントが書いたコードを見続けることで、品質を理解して信頼する、という考え方です。
- **ライブデモの失敗**：最初の PR 作成は進まず、別のものに切り替えています。原因は発表では語られていません。
- **Compare models のコスト**：「コスト面も判断で考慮される」と語られていますが、見せた比較画面では表示されていないとのことです。

## 8. 利用者にとっての利点

発表で語られた利点は、次のとおりです。

- 作業の見張りが不要になる：agents window が複数ワークスペースのセッションを一覧し、注意が必要なときに知らせる
- 場所を選ばず続けられる：AHP により、エディタ、agents window、モバイルアプリなど、どこでも同じセッションを継続・承認できる
- モデル選定の手間が減る：compare models で比較を自動化でき、Copilot Fusion は用途に応じてモデルを振り分け、AI credits の面でも有利だった、という例が紹介された
- 利用上限に強い：ハーネスを途中で切り替えて続けられる
- 編集機能が残る：agents window でも Monaco エディタ、Markdown エディタ、エディタ画面での hunk 単位のレビューが使える
- 作業を最後まで進められる：PR のタイトル、説明の自動生成から、CI 修正とマージの自動化まで、agents window で完結できる

## 9. まとめ

このセッションは、VS Code を使い慣れた人が、段階的にエージェント活用を取り入れていく道筋を示しました。エディタ画面の Chat から始め、同じセッションを agents window で開き、compare models や Copilot Fusion でモデルを選び、統合ブラウザ、Canvas、モックアップ、画像生成、PR のマージまでを 1 つの画面で進められます。必要なときはエディタ画面に戻って、差分を細かく確認できます。

登壇者が最も強調したのは、「これはあなたのワークフローであり、新しい働き方を強制するものではない」という点です。信頼を時間をかけて築き、自分に合うようにカスタマイズし、他の人が公開したマーケットプレイスの成果から学ぶことを勧めています。

なお、案内として、公式サイトは code.visualstudio.com（ドキュメントは /docs）、VS Code の 1 年を振り返る「VS Code wrapped」、そして GitHub 上の VS Code リポジトリ（github.com/microsoft/ の下。トランスクリプトでは表記が途中で崩れています）に issue を起こせることが紹介されました。QR コードは Blobby の性格診断サイトへのものです。
