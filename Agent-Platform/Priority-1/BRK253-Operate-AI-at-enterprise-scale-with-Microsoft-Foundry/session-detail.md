# BRK253 Operate AI at enterprise scale with Microsoft Foundry

## 1. はじめに

このセッションは、AI エージェントを「作る」段階から「大量に運用する」段階に進んだ組織に向けた、ガバナンスの話です。エージェントが 1 つなら、問題が起きても連絡する相手は明確です。しかし 10 個、100 個と増えると、複数のチームが関わり、質問されても答えられなくなっていきます。

発表では、架空の銀行で 2 つのエージェントを作って運用に乗せるシナリオに沿って、Microsoft Foundry に組み込まれたガバナンス機能を画面付きで紹介しています。扱う内容は、Azure Policy によるモデル・ツール・ネットワークの制限、コスト管理、AI Gateway、Foundry の guardrails（安全性ガードレール）、コンプライアンスと運用のダッシュボード、そして Agent 365 との連携です。

結論として、**Foundry には組み込みのガバナンス機能があり、Agent 365 や Purview、Defender など他の Microsoft 製品とも連携して範囲を広げられる**、というのが発表の骨子です。機能にはプレビュー中のものや早期アクセスのものが含まれます。この点は 7 章で整理します。

## 3. 何に関する発表か

発表は、冒頭で紹介された 1 つのエピソードから始まります。数週間前に Redmond を訪れた大手顧客が、「エージェントを作るのは簡単だが、スケールさせる部分が難しい。そこで時間が足りなくなる」と話した、という話です。

登壇者はこれを、エージェントの数が増えるにつれて起きる変化として説明しています。

- 最初の 1 つ目は、作る人も責任者も 1 人で、問題が起きたときの連絡先も明確です。
- 10 個になると、複数の連携先やシステムを呼び出すようになり、チームでの対応になります。
- 多くの組織が目指す規模は、数百をさらに大きく超えるものです。会場で「10 個以上のエージェントがある人」に手を挙げてもらうと、かなりの数が挙がりました。
- さらに増えると、自分が会ったことのないチームがエージェントを作り、顧客向けのエージェントが機密データに触れるようになります。

そのため、「エージェントの数が、それを把握している人の数を上回った時点で、ガバナンスは任意ではなく必須になる」と登壇者は述べています。1 つなら「プロジェクト」ですが、複数になると「チームスポーツ」になり、チケットやスプレッドシート、会議で調整することはできません。エージェントを作っているプラットフォームの中でガバナンスを行う必要がある、という考えです。

発表では、エージェントが 1 つ目でも 100 個目でも繰り返し出てくる 4 つの質問を軸にしています。

1. そのエージェントは何にアクセスできるか。
2. いくらかかるか。
3. だまされることはないか（安全性）。
4. 誰がルールを決めるのか。

発表の流れは次のとおりです。

1. 4 つの問いと、Foundry・AI Gateway・Agent 365・Purview/Defender の位置づけ（導入）
2. デモ 1：セキュリティ担当が境界を設定し、開発者がその中でエージェントを作る

## 5. 発表内容の詳細

### 5.1 Foundry が提供するガバナンスの全体像

Foundry でエージェントを動かすとき、プラットフォームが次の機能を持つと説明されています。

| 項目 | 説明 |
| --- | --- |
| agent identity と agent blueprint | エージェントごとの ID と、呼び出し元がサインインする blueprint（6.1 の手順 14） |
| アクセス制御 | 何にアクセスできるかの制限 |
| コスト管理 | 予算の上限設定など |
| 安全性 guardrails | 安全性のための制御 |

セキュリティ担当は Azure Policy で境界を設定し、開発者はその境界の内側でエージェントを作ります。これらの制約は、**リソースの作成時と実行時（runtime）の両方**で強制され、一貫して適用されます。さらに Foundry は、プロジェクトに関わる全員が、エージェントのフリート、コスト、運用メトリクス、ポリシーとその違反を確認できる統合的な管理画面を持ちます。これらの機能は Ignite の週にプレビューとして発表されたものです。

そのほかの製品との関係は、次のように整理されています。

- **AI Gateway**：AI ワークロード向けに作られた新しい Azure のゲートウェイサービスです。トラフィックを集中的に制御したい場合に、追加で入れるものとして紹介されています。Foundry は AI Gateway と連携します。
- **Agent 365**：Microsoft のエージェント管理の単一のコントロールプレーンです。Foundry だけでなく、Fabric や Copilot Studio など Microsoft のプラットフォームで作ったエージェント、さらにサードパーティのエージェントも 1 つのビューに載せられると説明しています。マルチクラウドを戦略にしている企業を想定した説明です。
- **Purview / Defender**：これらで設定済みのセキュリティポリシーやデータ保護ポリシーが、Foundry プラットフォームにも流れ込みます。

### 5.2 デモの前提となるシナリオ

デモは、架空の銀行が舞台です。作るエージェントは 2 つです。

- お客様と対話する **customer service agent**（顧客向け）
- 担当者（relationship manager）が顧客面談の準備に使う **client meeting prep agent**（社内向け）

2 つは同じガバナンスの土台を共有しますが、顧客向けの方がより厳しい安全要件を持つ、という設定です。デモの流れは「セキュリティ担当が境界を設定する → 開発者がその内側で作る → 本番に進めるときにコスト管理・集中トラフィック管理・安全性 guardrails を整える → 最後にフリート全体を監視する（Agent 365 の画面も含む）」となっています。

### 5.3 Azure Policy でモデル・ツール・ネットワークの境界を決める

最初のデモは、Azure portal での Azure Policy の設定から始まります。詳細な操作は 6 章にまとめ、ここでは設定した 3 種類のポリシーを整理します。

1. **モデルのポリシー**：「Foundry model deployments should only use approved models」という名前のポリシーです。スコープはリソースグループにしていますが、サブスクリプション全体や、Foundry リソース、プロジェクト単位にもできると説明されています。このデモでは、モデルの発行元（publisher）を OpenAI のみに許可し、それ以外は拒否しています。
2. **ツールのポリシー**：新しくプレビューになったポリシーです。許可するツールのリストを持ち、デモでは Foundry カタログの組み込みツールである file search だけを許可し、それ以外を拒否（deny）しています。effect は audit にして、そこから始めることもできると説明されています（デモでは deny に設定）。
3. **ネットワーク（egress）のポリシー**：エージェントがアクセスできる外部ホストの許可リストです。デフォルトは全拒否で、許可リストに 2 つのホストを登録しています。これもプレビューで提供されたと紹介されています。

### 5.4 コスト管理

本番にスケールするとき、最初に出てくる疑問が「何がコストを押し上げているのか」です。Foundry のポータルに、新しいコストダッシュボードが組み込まれています。

- 直近 7 日間のデモアプリの支出、エージェント別・モデル別の内訳、時間推移を見られます。
- プロジェクト別、モデル別、エージェント別に切り替えて見られます。
- **コスト制御**として、支出の上限（cap）を設定できます。Foundry リソース全体に 1 つの予算を設定するほか、エージェント別、セッション別、プロジェクト別に設定できます。上限は金額（ドル）またはトークン数で指定し、周期は日次、週次、月次から選び、周期の終わりにリセットされます。しきい値に達したときの動作として、アラートの送信か、利用のブロックを選べます。しきい値の水準も指定できると説明されています。

デモでは、エージェントごとに月次 10 ドルの上限を設定しています。画面には、全体予算のうち 4% を消費している推定が表示されていました。

### 5.5 AI Gateway

AI Gateway は、トラフィックを集中管理する新しい Azure のサービスです。デモでは、ゲートウェイのポータルに 1 つのゲートウェイがあり、その背後に 2 つのモデルが公開されている状態でした。ゲートウェイ全体にも、個別のアセットにも、1 つのポリシーを設定できます。

Foundry ポータルには、ゲートウェイとの直接統合が入ります。登壇者は「現在ロールアウト中の、ごく新しい機能」と説明しています。

- 作成したゲートウェイを、他の Foundry プロジェクトから使えるようにできます。
- どのモデルを Foundry プロジェクトに公開するかを選べます（全部である必要はありません）。
- 画面には、ゲートウェイを公開したプロジェクトと、開発者が呼び出すエンドポイントが表示されます。
- prompt agent を作るときに、AI Gateway 経由のモデルがモデルのドロップダウンに表示されます。

コードは見せていないと断ったうえでの説明です。

### 5.6 顧客向けエージェントの安全性：Foundry guardrails

顧客向けエージェントについて、銀行を想定した 3 つの懸念が挙げられています。

- **送金額の上限**：規制により、10K を超える取引は報告が必要になる。そのような取引が発生するときは、人間が承認する形にしたい。
- **経済的な困窮（financial hardship）への対応**：顧客との会話で困窮への言及があったときは、さらなる金融商品や与信枠の増額を勧めず、人間の担当者が適切な提案をするべきだ、というブランドとしての考え方。
- **PII の漏洩**：社内向け・社外向けにかかわらず、個人を特定できる情報が組織の外に出てはいけない。

デモでは、まずガードレール無しの状態を再現しています。25K の送金依頼が、人間の確認なしに実行されました。仕事を失って困っていると訴える顧客に対して、エージェントはクレジットカードの優遇金利や個人ローンを勧め続けました。さらに口座情報の確認を求められると、社会保障番号（デモ用の架空のもの）を答えてしまい、PII 漏洩になっていました。登壇者は、これらは jailbreak（脱獄）でも起こり得るので、決して出てはいけないと説明しています。

対策は、Foundry の Build タブにある **guardrails** で行います。従来の組み込みガードレールに加えて、利用者のニッチな要件に合わせたカスタマイズができる点が強調されています。

- **PII**：サポートされる全カテゴリを有効にしています。介入ポイント（intervention point）が拡張されており、PII 対策は tool input、tool output、user input、user output に対して働かせられます。
- **カスタムルール（決定論的）**：tool 名が「transfer money」で、tool の引数の amount が 10K 以上のとき、tool input の時点でブロックする、というルールを追加しています。
- **カスタムルール（LLM ジャッジ）**：financial hardship のような微妙な判断は、LLM をジャッジに使います。「hardship classifier」を作り、ジャッジに使うモデルを任意に選び、「顧客とのやり取りで経済的困窮が見られるかを 0 から 1 のスコアで判定する」という趣旨のプロンプトを入れています（発話では「0 から 5」とも言っており、聞き取りは完全ではありません）。そして、user input に対する hardship classifier のスコアが 0.5 を超えたら、AI の応答をブロックする条件にしています。ブロックされたら、バックエンドで人間の担当者を会話に入れる、という運用です。

作ったガードレールは、任意のエージェントに割り当てられます。デモでは customer care representative のエージェントに割り当てました。事前に用意した会話で結果を確認すると、25,000 の送金依頼は 10,000 を超えるため決定論的ルールで検知されて承認待ちになり、人間の承認が必要になりました。困窮の訴えは LLM ジャッジが検知し、商品を勧める代わりに、人間の専門担当者に振り分けられました。口座情報の確認に対しては、PII の分類器が有効になっているため、社会保障番号は返されなくなりました。

### 5.7 guardrails をサブスクリプション全体に適用する：Agent Control Service

質問として「セキュリティ責任者として、このルールをサブスクリプション全体に有効にするにはどうするか」が出ます。ここまでの guardrails タブは、プロジェクトのスコープです。1 つまたは複数のプロジェクト、あるいは 1 つのプロジェクトの中の 1 つ以上のエージェントやモデルに割り当てられます。組織全体に強制するには、**新しい API** を使います。UI で示した設定は、すべてこの API 経由でも有効にできます。

この API が **Agent Control Service** で、登壇者は「構成要素（building block）」と呼んでいます。

- シンプルな記法で、エージェントの介入ポイントに接続します。介入ポイントは、input、output、pre-tool call、post-tool call、pre-model call、post-model call です。
- 例えば input には、hate、sexual、self-harm、violence などの分類器を有効にし、先ほど作った hardship ジャッジも接続できます。
- この API 呼び出しを作成すると、一意の **policy ID** が得られます。

この policy ID を Azure Policy の assignment に使います。デモでは、スコープをサブスクリプション（「AI Apps and Agents」という名前）にし、配下の全リソースを対象にしました。そのために追加された、**Guardrails** という新しいポリシーを選びます。登壇者は「ポリシーを設定しても、適用するかどうかは誰かの善意次第、という仕組みではない」と説明し、設定すると Foundry の hosted agent と prompt agent の実行時に自動的に適用されると述べています。次の画面で policy ID を貼り付けて割り当てます。

確認として、別のプロジェクトの別のエージェントで困窮に関する質問をして、hardship 検知がブロックするかを試しています。結果について音声では「うまくいっていますように」と言っているだけで、ブロックされたかどうかの明言は確認できません。

登壇者は、この API は**単体のサービスとして使える**とも説明しています。どのフレームワーク、どのクラウドのエージェントでも要件を定義して評価できます。Foundry にもこれを組み込んでいます。ドキュメントの URL とは別に、初期テストと個別サポートを受けるための URL も後で案内されます。

ここまでの要点として、登壇者は次の 3 点を挙げています。

- コスト（FinOps）の可視化と上限設定。「見えないものは管理できない」。
- AI Gateway：エージェントやモデルが一握りを超えたら、モデルとツールのトラフィックに「1 つの玄関」が必要になる。
- Foundry の安全性 guardrails が、利用者のシナリオに合わせてカスタマイズできるようになった。

### 5.8 コンプライアンスダッシュボード、フリート運用、モニタリング

多数のポリシーを設定したあと、状況を追跡する場所が必要になります。それが Foundry の新しい**コンプライアンスダッシュボード**です。

- Foundry の **Manage** タブの左側にあります。
- 対象はサブスクリプション全体です。クロステナント対応に向けて取り組む、と登壇者は述べています（現時点では未対応）。
- Azure Policy で設定したポリシーが一覧され、ポリシーごとに準拠・非準拠のアセットを確認できます。
- 例として、モデルに適用した indirect jailbreak 攻撃のポリシーでは、70 のモデルデプロイが、必要なガードレールを有効にしていませんでした。そこで、モデルの guardrails タブに戻って修正します。
- Rong が先に設定した「OpenAI のモデルのみ」のポリシーでは、OpenAI ではない model router タイプのデプロイがあることが示されました。
- 先ほど作った financial hardship のポリシーは、Azure Policy 経由で適用した時点で Foundry が強制するため、デフォルトで準拠状態になります。
- **アセットビュー**では、エージェント、モデル、toolbox の視点でも見られます。エージェントが 1 つずつ確認できないほど増えたとき、注意が必要なものがすぐ分かります。
- Defender と Purview の insights も統合されています（時間の都合でデモはしていません）。セキュリティ上の実行時の問題やデータ損失防止の情報を 1 か所で見られます。

もう 1 つ、運用と可観測性が大きく強化されたとして、**Fleet and operations** タブが紹介されています。

- エラーが多いエージェントやレイテンシーが高いエージェントを一覧で確認できます。
- トークン使用量、呼び出し回数、エラー数で、並べ替えや絞り込みができます。
- 各エージェントの裏に、新しい**モニタリング**画面があります。性能、コスト、レイテンシーだけでなく、評価（evaluation）を継続的に実行できます。組み込みまたはカスタムの評価を有効にでき、red teaming の実行も含みます。
- デモでは、組み込みメトリクスの task adherence と intent resolution が下がっている例が示され、App Insights のトレースで原因を調べられると説明されました。

### 5.9 Agent 365 との連携

ここまでは Foundry のエージェント（hosted agent と prompt agent）が対象でした。他のエージェントについては、多くの利用者から要望があったとして、Agent 365 の**新しい体験（近日提供予定）**が紹介されています。

- Agent 365 に、新しい **Policy** タブがあります。
- Microsoft が推奨する、カスタムおよび組み込みの安全性制御を、ベースラインとして使うことができます。または、構成画面から白紙で始めて、**ポリシーパック**を作ることもできます。
- デモでは「AI safety pack」を例に、Foundry の組み込みの安全性分類器とフィルターがすべて有効になっていました。登壇者は、まもなくここにもカスタマイズ機能が加わり、Foundry 上で作ったエージェントだけでなく、外部で作ったもの、購入したものも含むフリート全体に、カスタムガードレールを適用できるようになると述べています。
- ポリシーをフリートに割り当てると、そのテナントの保護下にある Foundry のエージェントには、ポリシーが Azure Policy 経由で自動的に Foundry に転送され、強制されます。

登壇者は、これによって異なるフレームワークやクラウドをまたぐエージェントを、はるかにうまくスケールさせられる、と述べています。

## 6. デモ・手順

このセッションでは、画面を使ったデモが行われています（Azure portal、Foundry portal、VS Code、Web フロントエンド、Agent 365 の画面）。録音は音声のみのため、画面の細部は確認できません。以下は、語られた範囲の順番です。

### 6.1 デモ 1：境界の設定と、その内側での開発

セキュリティ担当の立場でポリシーを設定し、次に開発者の立場に切り替えるデモです。

1. Azure portal で、Azure Policy の「Foundry model deployments should only use approved models」を表示する。スコープはリソースグループ。モデルの発行元は OpenAI のみ許可で、他は拒否になっている。
2. 同じく Azure Policy で、プレビューの新しいツールのポリシーを表示する。許可リストは file search のみ。effect は deny（audit にもできる）。
3. 開発者の立場で Foundry portal のモデルカタログを開く。Kimi のモデルをデプロイしようとすると、組織で許可されていないというメッセージが上部に出て、デプロイボタンが無効になる（このあたりで画面が思うように動かない場面があった）。
4. OpenAI の最新モデルを選ぶと、メッセージは出ず、デプロイできる。モデル名は「6.2」と聞こえるが、音声認識の都合で表記を確定できない。
5. 作成済みの customer service agent を開く。prompt agent として作ってあり、モデル、ツール、instructions を定義している。instructions は「銀行のポリシーについて file search で質問に答える customer service assistant」という趣旨。file search は、銀行のカードのポリシーを説明するファイルを入れた vector store につながっている。
6. ツールに web search を追加して保存しようとすると、Azure Policy によってブロックされる。ポリシーを表示するか、ツールを削除するかを選べる。ツールを削除する。
7. 2 種類のカードの違いを質問する。エージェントは file search を呼び出し、年会費とキャッシュバックの違いを答え、参照したアップロード済みファイルを示した。
8. 「hosted agent でも同じか」という質問に答える形で、コードで定義する hosted agent を見せる。UI にはツールの項目が無く、UI でツール追加をブロックする手段が無い。この agent は VS Code で作成しており、コード内で MCP のエンドポイントをツールとして呼んでいる（Foundry toolkit for VS Code を使用）。
9. 2 つ目の制御として、**ツールの runtime control** を見せる。JSON の設定で、デフォルトは全拒否、許可リストは file search と、この hosted agent が呼ぶ MCP エンドポイントのみ。他の MCP は許可しない。コマンドを実行して、Foundry プロジェクトのプロパティとして設定すると、実行時に強制される。
10. 外部サイトへのアクセスを制限する egress のポリシーを見せる。デフォルトは全拒否で、許可リストに 2 つのホスト。
11. 開発者の立場で、エージェントの安全性ガードレールの設定として、egress のルールを編集する。画面上部に、管理者が Azure 側で設定した egress ポリシーがあることが表示される。許可できるのは、ポリシーから取得された 2 つのホストだけ。他のサイトを追加しようとすると、Azure Policy で許可されていないと表示される。開発者は特定のホストだけに絞って**ポリシーを強化することはできるが、管理者が設定した土台を弱めることはできない**。
12. customer briefing agent（Foundry で動く hosted agent）を Web フロントエンドにつなぐ。relationship manager が顧客情報と最新の市場情報を集めるための画面で、市場情報の取得方法を 4 通り試せる。
    1. 外部のウェブサイトにアクセスしようとする → 画面右側に拒否が表示された（返ってきたエラーの内容は、音声認識の都合で確定できません）。
    2. web search ツールにアクセスしようとする → 「このツールはプロジェクトの runtime tool controls で許可されていない」と拒否された。
    3. 許可されていない MCP プロバイダーにアクセスしようとする → 同じメッセージが返る。
    4. 許可リストにある MCP エンドポイントを使う → 成功し、顧客情報と、その承認済み MCP サーバー経由で取得した最新の市場情報が表示された。
13. Web フロントのモックではないことを示すため、Foundry の該当エージェントのトレースで、直前の実行（web search ツールの呼び出し）が「プロジェクトのツール制御でブロックされた」と表示されていることを確認する。
14. Foundry で動くすべてのエージェントは、Microsoft Entra ID のオブジェクトとして**固有の ID** を持ち、個別にアクセスの付与とガバナンスができる。さらに **agent blueprint** を持ち、呼び出し元は blueprint にサインインする。このとき呼び出し元は、Foundry プロジェクトの RBAC ロールを持つ必要がない。エージェントは、ユーザーが同意した権限の範囲内で、そのユーザーとして代行できる。エージェントが行ったことを追跡しやすくなる。

### 6.2 デモ 2：コスト管理と AI Gateway

## 7. 注意点・発表者の気付き

- **多くの機能はプレビューまたは早期アクセスです。** ツールのポリシー、egress のポリシーなどはプレビューと説明されています。Foundry ポータルと AI Gateway の統合は、ロールアウトの最中です。Agent Control Service は API としては利用可能ですが、Foundry と Agent 365 でのアクセスは早期アクセスです。Agent 365 の Policy タブは「近日提供」です。
- **hosted agent は、UI のポリシーだけでは防げません。** コードで定義するため UI にツールの項目が無く、ツールの追加を UI 側でブロックできません。そこで、プロジェクトのプロパティとして設定する runtime control を併用します。
- **開発者はポリシーを強化できても、弱められません。** 管理者が Azure Policy で設定した境界の内側でのみ操作できます。
- **コンプライアンスダッシュボードはクロステナントには未対応です。** 対応に向けて取り組むと、登壇者は述べています。
- **評価が下がったら、まずトレースを見ます。** 例として、task adherence や intent resolution の低下が示され、App Insights のトレースで原因を調べると説明されています。
- **デモ中の画面の不調**：デモ中に画面が思うように動かない場面があり、会場のインターネットが遅いという発言もありました。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- セキュリティ担当が Azure Policy で境界を設定し、開発者がその内側でエージェントを作る形にすると、制約をリソース作成時と実行時の両方で一貫して適用できます。
- エージェントごとの ID と agent blueprint によって、エージェントごとにアクセスを付与・管理でき、何をしているかを追跡しやすくなります。
- コストの可視化と、エージェント・セッション・プロジェクトごとの上限設定ができ、しきい値でアラートまたはブロックを選べます。
- AI Gateway で、モデルとツールのトラフィックを 1 か所に集められます。
- 組み込みの guardrails に加えて、決定論的ルールと LLM ジャッジによるカスタムルールを作れます。それをポリシーとして、サブスクリプション全体に強制できます。顧客向けエージェントでは、高額送金の承認、困窮顧客の人間担当者への引き継ぎ、PII 漏洩の防止を例に挙げています。
- コンプライアンスダッシュボードとフリート画面で、数が増えたエージェントのうち、注意が必要なものをすぐに見つけられます。
- Agent 365 経由で、Foundry の外にあるエージェントにも同じ安全性ポリシーを適用する方向性が示されています（近日提供予定）。

> 補足：発表では、これらの導入による定量的な成果や、顧客事例の数値は紹介されていません。

## 9. まとめ

エージェントの数が増えると、「何にアクセスできるか」「いくらかかるか」「だまされないか」「誰がルールを決めるか」という 4 つの問いに、プラットフォームの中で答える必要があります。Foundry は、Azure Policy によるモデル・ツール・ネットワークの制限、エージェント ID、コスト管理、AI Gateway、カスタマイズ可能な guardrails、コンプライアンスダッシュボード、フリート運用とモニタリングを提供し、Agent 365 や Purview、Defender と連携して適用範囲を広げます。

登壇者のお願いは、ガバナンスを後回しにせず、エージェントが 10 個のうちに入れておくこと、早期アクセスやラボに登録して試すこと、フィードバックを送ることでした。
