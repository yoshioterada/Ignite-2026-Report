## 1. はじめに

このセッションは、Microsoft のパートナー企業（SI、ISV など）に向けて、EMEA で「ソブリン（sovereignty）」が話題になる商談をどう勝ち取るかを説明する 25 分のシアターセッションです。ソブリンクラウドの機能紹介ではなく、商談の進め方に重点があります。

## 3. 何に関する発表か

背景として発表で語られたのは、ソブリンの意味が**データの所在（data residency）を超えて広がっている**という点です。メタデータの概要では、管轄、証明、AI ガバナンス、レジリエンシーに広がるとされています。発表の中では、国や業界によって要件が異なること、そして顧客が感情的にもこの話題に敏感であることが繰り返し語られます。

発表の流れは次のとおりです。

1. どこで競争するか: ソブリンが「障害」になる商談と、「焦点」になる商談
2. 複雑さの正体: 国ごと、業界ごとに違う要件
3. リスクフレームワークの使い方
4. Microsoft Sovereign Cloud のプラットフォームと、3 種類のパートナー
5. パートナーの取り組みを紹介するビデオ
6. パートナー 2 社のパネル
7. 勝つための 3 つの行動と、参考リソース

## 4. 発表者が伝えたいメッセージ

最も強いメッセージは、**「ソブリンでなければならない」という要望を、ワークロードごとの明確な要件に変える**ことです。顧客の「ソブリンにしたい」という言葉の背後には、本当にソブリンな要件がある場合と、「データがどこにあるのか」という感情的な懸念がある場合があります。前者はソブリンなワークロードを勝ち取る競争、後者は案件を止めずに進めることが競争の中身になります。

登壇者は、要件を整理しないまま会話すると、他のパートナーやプラットフォーム、ISV がその会話を競争上の強みに変えてしまうと警告しています。そのうえで、ソブリンは 1 社で解決するものではなく、複数の種類のパートナーが組み合わさって成功する、という考え方を示しています。

## 5. 発表内容の詳細

### 5.1 どこで競争するか: 2 種類の状況

ソブリンが商談に出てくる状況は 2 つあります。

| 状況 | 内容 | 競争の意味 |
|---|---|---|
| ソブリンが障害（blocker）になる | 移行やモダナイゼーションの案件で、「データはどこにあるのか」「誰がアクセスできるのか」という質問が出る。必ずしも本当のソブリンクラウドの要件があるわけではないが、「データがどこにあるか」に感情的なこだわりがある | 案件を前に進め続けるための競争。調査で案件が遅れ、リスクになる |
| ソブリンが焦点（focus）になる | 公共部門、重要インフラ、規制産業で典型的。特定のワークロードに、データとアプリケーション、その配置を別扱いにする要件がある | ソブリンなワークロードを勝ち取る競争 |

最初に競う相手は、**複雑さ**だと説明されています。EMEA では、ソブリンの文脈、動く場所、業界によって複雑さが生まれます。要件は国や大陸によって異なり、例として「フランスで必要なことは南アフリカと違うかもしれない」と話しています。複雑さは誤解を生み、誤解は商談の混乱につながります。この整理が、競争で有利になる出発点です。

### 5.2 リスクフレームワークの使い方

リスクフレームワークそのものの説明は前のセッションで行われたとして、ここでは「競争にどう使うか」が話されます。フレームワークは、**確率（probability）と影響（impact）**の 2 軸で構成されています。発表では、領域ごとに次のような対応が示されました。

| 位置 | 例として挙がった項目 | 説明された対応 |
|---|---|---|
| 影響が高く、確率は中程度 | データレジデンシー、訴訟（lawsuit） | 顧客が「banker strategy」と聞こえる戦略を取る必要がある（音声認識の都合で語が確定できません） |
| 右上（確率も影響も高い） | サイバーレジリエンス、コンプライアンス | 強く緩和（mitigate）する必要がある |
| 右下（確率は高いが影響は小さい） | モデルのトレーニング、メタデータ、気候（climate） | 「manager and monitoring」と聞こえる戦略（音声認識の都合で語が確定できません） |

このフレームワークを使う際の考え方が、次のように説明されています。

- ワークロードごとにリスクの種類が違う。すべてのリスクが同じワークロードに当てはまるわけではなく、必要な制御もワークロードごとに異なる。そのため、ワークロードと、関連するリスクと、制御を定義する
- 競合他社がソブリンをどう実現しているかも確認する。すべてを大きな「ソブリンの傘」の下に置いているのか、それとも、ワークロードごとに分解しているのか
- ソブリンの案件ではないと判断できる場合は、もう 1 段階掘り下げて要件を整理し、ワークロードごとにソブリンへの答え方を考える

### 5.3 Microsoft Sovereign Cloud とパートナーの 3 つの役割

要件を整理したうえで答えるのが、Microsoft Sovereign Cloud です。顧客とパートナーが、次の 3 つの層から構築できるプラットフォームだと説明されています。

1. ソブリン パブリッククラウド
2. ソブリン プライベートクラウド
3. ソブリンのパートナーエコシステム

管理とガバナンスの面では Azure Arc が例に挙がっています。Azure、オンプレミス、他のクラウドをまたいで扱えるため、Microsoft のエコシステムと既存の技術を使って、ソブリン要件の多くに答えられるという説明です。ただし、3 つの層はデータセンターごとに大きく異なるため、顧客が展開場所を尋ねてきたときは具体的に答える必要があります。

また、**プラットフォームだけが答えではなく、特に重要な答えがパートナーエコシステム**だと述べています。ソブリンの案件では、次の 3 種類のパートナーが一緒になります。

| 役割 | 担うパートナー | 内容 |
|---|---|---|
| Expertise（専門知識） | グローバルおよびローカルの SI | Microsoft の技術を熟知し、導入を支援する。前述のリスクフレームワークで複雑さを評価する手助けをする |
| Software | ISV | ソブリン向けソリューションを開発する。ガバナンスをカバーし、顧客のテナント内、または Azure Local 内に展開するものを含む（一部、聞き取り不明瞭） |
| Operating models（運用モデル） | 各国のパートナークラウド | 例として、フランスの「Bleur」と聞こえる名前（音声認識の都合で綴りは確定できません）とドイツの Delos。さらに、Azure Local のマルチテナンシーが「coming soon」で、ローカルのオペレーターとともに提供される予定 |

EMEA のソブリン関連のパートナーエコシステムは「大きく成長している」と説明され、パートナーの取り組みを紹介するビデオが流れます。

### 5.4 パートナーのビデオ

ビデオの話者の氏名は、トランスクリプトでは確認できません。内容は次のとおりです。

- 顧客は、クラウドと AI の恩恵を受けつつ（該当部分は聞き取り不明瞭）、自分たちの条件で制御を保ちたいと考えている。これは経営層レベルの会話であり、背景には地政学的な不確実性がある
- 欧州では、ソブリンはコンプライアンスのチェック項目から戦略的な要件に変わった
- 全員に当てはまる 1 つの答えは無い。北欧の公的機関、ベルギーの銀行、ポーランドの製造業など、市場ごとに異なる
- ソブリンはデータレジデンシーをはるかに超える。プライバシーとコンプライアンスが重要な顧客もいれば、運用の独立性やレジリエンスが重要な顧客もいる。要件はワークロード、業種、国、運用モデルで変わり、同じ業界でも、バリューチェーンが違えば必要なソブリンも違う
- 「スイッチではなくダイヤル」と考える。パブリックのソブリンクラウドで足りる顧客もいれば、プライベートが必要な顧客もいる。パブリッククラウド、ソブリンクラウド、ハイブリッド、ローカルを適切に組み合わせる
- 製品やプラットフォームから始めず、その顧客にとってソブリンが何を意味するかから始める。目的は、どこでも誰にでも最大のソブリンにすることではなく、ビジネスに必要で、法規制とリスクの面で許容できる、**測定可能なソブリン**を持つこと。顧客の AI の野心から始め、ソブリンの製品からは始めない
- ソブリンは最終的にローカルなものであり、技術だけでは足りない

### 5.5 パートナーのパネル

Daniela 氏の司会で、2 社のゲストが質問に答えました。

**ソブリンの商談で最近勝った事例と決め手（Segeka の Jimmy 氏）**
オランダの非営利組織の移行案件です。顧客は機密性の高いデータをオンプレミスに残したいと考えていました。そこで、「懸念は何か、この移行にどんなリスクがあるか」を聞き、ソブリンのランディングゾーン（sovereign landing zone）で、データの所在、特権アクセスを持つ人、暗号化キーの管理者のどれが心配なのかを整理できることを示しました。ワークロードの視点で見ることで、パブリッククラウドへの移行に納得してもらえたとのことです。

**差別化のポイント**
- Segeka の Jimmy 氏: 顧客が「ソブリンにしたい」と言ってきたら、まず「ワークロードは何か、何を心配しているのか」を尋ね、それを測定する方法を話し合う。Azure の managed platform services と Smart Cloud Insights で、顧客が Azure で何を持っていて、データがどこにあるかを示し、証拠にする。半年後に「どれくらいソブリンか」と再び聞かれても、制御の状況を示せる
- Veeam の登壇者: ソブリンは国や地域ごとに異なり、サポートが非常に複雑。どこでも同じプラットフォームを提供したいが、多くのカスタマイズが必要になり、それをパートナー経由で行う。Microsoft や Segeka を含むパートナーエコシステムが強みの 1 つ

**他のパートナーとの協業**
Veeam の登壇者は、Daniela 氏が示したモデル（ISV と SI）がまさに自社の位置づけだと述べ、さらに、ストレージのコピーを直接管理できるローカルの CSP とも連携していると加えました。事前の統合を行うだけのパートナーではない、という文脈での発言です。

**ソブリンの商談に向けたアドバイス**
- Veeam の登壇者: ソブリンは非常に複雑なので、最初に必要な要件をすべて検討し、組む相手を決めておく
- Segeka の Jimmy 氏: 議論を白か黒かにしない。「ワークロードは何か」「どこに照らして自分を位置づけるか」（聞き取り不明瞭）「どう証明するか」から始める。そうすれば議論が進めやすく、顧客にとっても都合が良い。環境全体を完全な confidential compute にする必要はなく、ソブリンの制御にはさまざまな種類がある

Daniela 氏は、ISV と SI の組み合わせがソブリンの機会を広げる、とまとめました。

### 5.6 まとめとして示された 3 つの行動（Robin 氏）

話題は複雑で感情的でもあり、感情が「ソブリンにしたい」という要望を生みますが、必ずしも完全なソブリンは必要ではなく、利用者がスペクトラム上のどこにいるかで程度が変わる、と述べています。そのうえで、勝つための 3 つの行動が示されました。

1. **早く関与する（Engage early）**: 他の誰かより先に会話の枠組みを作る。顧客とこの話をしていなければ、他のパートナー、プラットフォーム、ISV が話し、完全に切り離されたローカルソブリンクラウドが不要でも、それを競争上の強みに変えてしまう
2. **ワークロードごとに評価する**: それぞれの価値に応じて評価し、リスクフレームワーク上の位置を決める。これで「ソブリンでなければならない」を明確な要件に変え、商談を前に進めるか、売るべきソブリンの機会を明確にできる
3. **パートナーを巻き込む**: ISV、各国のクラウド、SI など、複数のパートナーが組み合わさって成功する。EMEA のソブリンクラウドのパートナーネットワークにいる相手を把握することで、案件を加速できる

## 7. 注意点・発表者の気付き

- ソブリンの要望が出ても、本当にソブリンが必要とは限りません。「データがどこにあるか」への感情的なこだわりが、商談を遅らせるリスクになります

- 3 つの層（パブリック、プライベート、パートナー）はデータセンターごとに違うため、展開場所を聞かれたときは具体的に答える必要があります

## 8. 利用者にとっての利点

このセッションの主な対象はパートナーですが、顧客にとっての利点として語られた点は次のとおりです。

- ワークロードごとに要件を整理するため、すべてを最大のソブリンにする必要がなく、必要な制御を必要な範囲に適用できる
- 事例（オランダの非営利組織）では、データの所在、特権アクセス、暗号化キーの管理のどれが心配かを整理することで、パブリッククラウドへの移行に納得できた
- 制御の状況を示す証拠があれば、半年後に再び確認されても提示できる（Segeka の説明）
- 「測定可能なソブリン」を、ビジネスと法規制・リスクに合わせて持てる

発表では、数値による成果（金額、期間、割合）は示されていません。

## 9. まとめ

ソブリンの商談は、「障害」と「焦点」の 2 種類に分かれ、まず競うべき相手は複雑さです。リスクフレームワークで、ワークロードごとにリスクと必要な制御を整理すれば、「ソブリンでなければならない」を明確な要件に変えられます。

Microsoft Sovereign Cloud は、パブリック、プライベート、パートナーエコシステムの 3 つの層で答えます。特にパートナーが重要で、SI、ISV、各国のクラウドという 3 つの役割が組み合わさって成功します。登壇者が示した勝つための行動は、早く関与すること、ワークロードごとに評価すること、パートナーを巻き込むことの 3 つです。
