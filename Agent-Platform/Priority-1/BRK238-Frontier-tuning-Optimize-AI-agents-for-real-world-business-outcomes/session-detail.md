# BRK238 Frontier tuning: Optimize AI agents for real-world business outcomes

## 1. はじめに

このセッションは、Microsoft が提供する **Frontier Tuning** を紹介するものです。Frontier Tuning は、自社の業務プロセスをモデル化した「学習環境」を作り、評価（evals）と改善（hill climbing）を繰り返して、自社専用の AI（スキル、ハーネス、必要ならモデル）を育てる仕組みです。

発表の中心は、「小さなモデルでもチューニングすれば、フロンティアモデルと同等の品質を、はるかに低いコストで出せるか」という問いです。Land O'Lakes、Pearson、EY の事例が示され、Pearson では、フロンティアモデルが 1 タスクあたり約 1.78 ドルかかるのに対し、チューニングした MAI-11 は約 0.25 ドルという比較が紹介されました。Frontier Tuning の開発チームによる仕組みの説明、GitHub Copilot 上のプラグインを使った画面付きのデモ、2 本のビデオ、顧客事例、という構成です。

## 5. 発表内容の詳細

### 5.1 モデルはどのように良くなるのか

Ranveer 氏はまず、フロンティアラボが新しいモデルを出すときの大まかな 3 段階を説明しました。

| 段階 | 内容 |
| ---- | ---- |
| 1 | pre-training（mid-training と呼ぶこともある）。厳選された知識をモデルに入れる |
| 2 | post-training。強化学習（RL）や教師ありファインチューニングで新しいタスクを学ぶ |
| 3 | post-training の複数の実行結果をまとめ、新しいモデルにする |

注目すべきは第 2 段階です。例えば「投資銀行家」のように振る舞わせたい場合、フロンティアラボは "Mercorp"、"Micro One"、Turing といったデータプロバイダー（社名の表記は音声認識に依存します。会場にいるパートナーとして挙げられました）に依頼します。データプロバイダーは、Goldman Sachs や McKinsey などの出身の専門家を数日間雇い、M&A や資産購入の判断といったタスクを解いてもらいます。その間のメッセージ、メール、作成したファイル、良し悪しのサンプル、rubrics、ツールがひとまとめにされ、これがモデルを訓練する環境になります。弁護士や不動産ブローカーについても同様です。

そのうえで、「RL による post-training は pre-training のようには汎化しない」という議論が昨年後半に起きたことが紹介されました。合成 RL 環境で訓練したモデルを自社に持ち込むと、結果が誤っていたり、同じ仕事にハーネスがより多くのトークンを使って支払いが増えたりする、という問題です。

### 5.2 Frontier Tuning の 3 つのステージ

Frontier Tuning は 3 つのステップで進みます。

1. **ビジネスプロセスのデジタルツインを作る。** エージェント、プラグイン、ビジネスプロセスを指定すると、実際の仕事の仕方を正確にモデル化する作業を支援します。Work IQ のデータ（メールや Teams のメッセージ）も使います。
2. **評価（evals）でギャップを見つける。** まず rubrics（評価基準）を強化して reward hacking が起きないようにし、次にモデルが失敗しやすい箇所を突く難しいサンプルを生成します。出力は、既存の大規模モデルが自社の業務でどこで失敗するか、というギャップです。
3. **hill climbing で自分専用の AI を作る。** スキル、ハーネス、必要ならモデルをチューニングします。

仕組みを 1 枚で表すグラフとして、x 軸がコスト、y 軸が精度の図が示されました。出発点は左下（低コストだが間違える）です。スキルとハーネスの hill climbing で右上（高コストだが良い結果）に移動します。この hill climb がうまくいけば、次にモデルチューニングを行い、左（低コストで良い性能）へ動かします。

### 5.3 デジタルツインと Tuning 環境の中身

デジタルツインの入力としては、まず標準作業手順（SOP）を出発点にできます（例として、HR の採用エージェントやサプライチェーンの調達エージェントが挙げられました）。ただし SOP だけでは通常不完全なので、Work IQ を通じてメール、Teams メッセージ、SharePoint のファイルを掘り下げて、より正確な表現にします。知識は文書化されておらず人の頭の中にあることも多いため、Teams のインタビューや Cowork 上のインタビューで他の専門家（SME）を巻き込むこともできます。画面を録画して「こう仕事をしている」と見せる方法にも触れられました。

こうして作る Tuning 環境（業界で言う RL 環境）には、次の 4 つが入ります。

| 要素 | 説明 |
| ---- | ---- |
| スキル | 仕事のやり方。HR 採用なら「有効な候補者を探す」「候補者への返信を調整する」など。1 つの環境に複数入る |
| rubrics / 評価基準 | 仕事の良し悪しをどう判定するか。LLM ベース、コードベース、離散的な分類器などがある |
| ツール | SAP、Salesforce、D365、Fabric など、仕事に必要なツール |
| サンプル | 正解例となるプロンプトの例（ground truth） |

### 5.4 評価プラットフォームの 3 つの工夫

一般的な評価は、サンプルと判定基準を渡して性能を測るものです。発表では、それだけでは足りないとして、次の 3 つの技術が紹介されました。

1. **より難しい rubrics を生成する。** 生産性を高めるタスクは数学の問題のように簡単に検証できないため、難しい rubrics が要ります。インタビューによる方法に加え、rubrics を壊そうとする敵対的な手法（rubrics hardening）で、評価に使える難しい rubrics の集合を作ります。
2. **難しいサンプルを作る。** 過去のプロンプトを見るだけでは、システムを試すサンプルとして不十分です。rubrics に導かれた tree search で、モデルが失敗しそうな箇所を見つけ、難しいサンプルを生成します。
3. **仮想化したツール。** メール送信やデータベースの更新を含むタスクで 100 回のロールアウトを評価すると、迷惑メールが 100 通、でたらめなデータが 100 件できてしまいます。そこで、システムからは本物のツール呼び出しに見えるが、裏側では元のツールの状態を変えない仕組みを作った、と説明されました。

評価は、性能とコスト（異なるモデルやハーネスで使ったトークン数）の 2 つの観点で行います。

### 5.5 Hill climbing の仕組み

最初の段階では、ハーネスとスキルをチューニングします。ハーネスに改善が見られたら、ファインチューニングで上積みが得られるかどうかを判定する技術（発表では "another key tech" と呼ばれています）を使います。上積みが見込めるなら、モデルの重みも更新します。現時点でチューニングできるのは、GPT-6、GPT-6 Luna、MAI-2、MAI-11、およびオープンウェイトのモデルと説明されました（モデル名は音声認識の都合で表記が確定できません。EY のビデオでは "MAI 1.1" と聞こえます）。

科学的な背景として、Tuning 環境が **評価、訓練、推論の 3 つで同じものとして使われる** ことが革新点だと説明されました。ユーザーがプロンプトを送ると、Tuning 環境が適切なスキルと rubrics を選び、中央の部分（model pool）で処理されます。この中央部分では、rubrics を最大化するための tree search（エージェントの群れのようなもの）が走り、手順を試し、必要なら巻き戻して、すべての rubrics を満たす最良の軌跡を見つけます。この仕組みはループとして説明されました。

- **内側のループ（ステップ 1）**: 見つかった軌跡でスキルを更新し、次の同じプロンプトでは正しいスキルが使われて、コストが下がるようにします。
- **中間のループ（ステップ 2）**: ハーネスとモデルを選びます。長いプロンプトや 100 行のスキルがあれば中間ステップに分解し、各ステップで満たすべき rubrics に基づいて最適なモデルを選びます。
- **外側のループ（ステップ 3）**: 内側のループはプロンプトごとに回りますが、外側のループは定期的（数週間ごと）に回ります。中間部分の rubrics 誘導型の tree search は、いわば「貧者の強化学習ロールアウト」であり、実行時にファインチューニングで上積みが得られるかを試している、と説明されました。上積みが出ていれば、学習結果をモデルの重みに反映して、自分のモデルを作ります。

業務の変化に伴い、いつ再度ファインチューニングすべきかについては、ドリフトの検知が説明されました。推論時に、ファインチューニング済みモデルが十分な頻度で呼ばれなくなったら、そのモデルが RL 環境と同じ状態にないというサインなので、再チューニングの時期だと分かります。

研究論文は主要なカンファレンスで発表されているものの、利用者はその科学を意識する必要はなく、コマンドラインやシンプルな UX で操作できるように抽象化している、と述べられました。

### 5.6 始め方（Ranveer 氏の整理）

チューニングすべき対象は、高いコストを払っている、あるいは既存のモデルでは不十分だと感じる主要なビジネスプロセスやエージェント、スキルです。対象が決まったら、ツールを設定し、RL 環境を作り、ベースラインを取り、評価と hill climbing に進みます。

### 6.1 Malik 氏のデモ（Frontier Tuning plugin と Copilot Cowork）

Malik 氏は、チューニングを試したことがある人、それが簡単でアクセスしやすいと感じた人に挙手を求め、「やはりそうですね」と受けて、そこを改善するのが Frontier Tuning だと話しました。さらに、多くの業務では「ほとんど正しい」だけでは足りず、常に正しいことが求められるため、それに応える品質向上のための仕組みだと位置づけています。Frontier Tuning は 4 つのステップで、**build（業務を表す Tuning 環境を作る）、teach（タスクが何かをシステムに教える）、hill climb、share（作ったものを共有する）** です。

デモでは、語られた範囲で次の順に進みました。

1. Frontier Tuning CLI をインストールしたマシンで、GitHub Copilot の Frontier Tuning plugin を有効にした状態で操作を開始します。
2. Tuning CLI に、利用できるサンプルの一覧を尋ねます。テンプレートが 3 つ（marketing operations、product lifecycle、talent acquisition）返ります。良い学習環境を知るためのテンプレートがプラットフォームに含まれている、と説明されました。
3. marketing operations のテンプレートを元に、marketing のデモ用の学習環境（learning environment）を作るよう依頼します。M365 上のセキュアなサービスに学習環境が作られ、63 のスキルと 100 のサンプルがプロビジョニングされました。
4. Tuning プラグインのキャンバスで、環境の中身を確認します。各スキルには、説明、rubrics、サンプルがあります。例として "build content brief" スキルを開き、詳細な instructions（マーケティングイベント向けのコンテンツ作成を助けるスキル）と詳細な criteria（rubrics）を示しました。サンプルは 4 件あり、そのうち別の人（Riaz）が寄稿したものがあり、名前が表示されます。
5. 高品質なタスクとスキルを作るため、社内の SME を巻き込みます。Tuning CLI に "build content" についての **SME interview** を開始するよう依頼すると、Frontier Tuning サービスが、専門家である同僚（Riaz）に招待を送り、Teams のチャットが始まります。複数人に依頼することもできます。
6. SME 側は Cowork 用のプラグインを入れる必要があります。入れると Cowork 上でインタビューが始まり、「今そのタスクをどうやっていますか」といった質問が出ます。その回答が学習環境に送り返されます（先ほどの最後のサンプルが、その入力によるもの）。
7. 続いて hill climb を実行します。コマンドがあると説明され、動作は次のビデオで示すとして、ここでは詳細を見せていません。
8. チューニングしたスキルを展開（deploy）するため、"publish the build content brief skill to co-work" のように依頼します。スキルが Cowork にプラグインとして公開され、アクセス権のある従業員が使えるようになります。使う際は、学習環境にある最新のモデル（チューニング済みモデルまたはチューニング済みスキル）が使われます。利用内容を学習環境に還元することも選べ、学習ループが回り続けます。
9. 最後に、Cowork 上でチューニング済みスキルを使って content brief を作成する例を見せました。

### 6.2 製品紹介ビデオ

次に、全体の流れを示すビデオが流れました。登場人物は Caldova 社の 4 人です。invoice review skill を作る maker の Maya、契約の専門家で正しい請求書を知っている Elena、そのスキルに日々頼る財務チームの Daniel、全体を統制する IT 管理者の Jordan です。ビデオの流れは次のとおりです。

1. Maya が GitHub Copilot の Frontier Tuning plugin に 1 文で依頼します。Frontier Tuning は、Maya が持つスキルを出発点にし、Work IQ と Fabric IQ を通じて Microsoft 365 のエンタープライズデータと仕事の文脈に根ざします。
2. Elena は Teams で自動的に招待されます。1 クリックで Copilot Cowork が彼女のワークフローを聞き取ります（どの証拠が重要か、判断が分かれる点、決して起きてはならないこと）。頭の中にあった知識が、承認済みのプレイブックになります。
3. プレイブックがスキルと rubrics になり、専門家のワークフローを符号化した学習環境ができます。
4. まず private evaluation（非公開の評価）を実行し、変更前にベースラインを測ります。Elena のフィードバックがテストケースと品質チェックになり、専門家の基準でスコア付けされます。結果は、ハーネスとモデルのための非公開ベンチマーク（品質とコストを同時に計測）になります。
5. 測ったギャップが求める深さまでだけチューニングします。まずスキル（instructions、context、rubrics）、次にハーネス（ツールとオーケストレーション）を直し、変更ごとに評価して、スコアが上がったものだけ残します。ギャップが残る場合は、自社のタスクでモデルをファインチューニングします。
6. ビデオでは、MAI がベースラインから GPT-5.6 に近い水準まで上がり、コストは約 1/7 と示されました（音声認識の都合でモデル名や数値の表記が確定できません）。
7. 基準を満たしたら、1 文で公開します。Daniel の Copilot Cowork に反映され、次の請求書では、すべての不一致が指摘され、指摘は請求書の行と契約条項で裏付けられます。Daniel が使うプロンプトを提供すれば、継続的な学習ループとして次の改善に使われます。
8. Jordan は Agent 365 で全体を監督します（"your sovereign intelligence governed by the control plane you already trust"）。ビデオは aka.ms/frontiertuning を案内して終わります。

ビデオの後、「ライブであることを示すために余計なメッセージも入れてある」といった補足がありました。

### 6.3 EY のビデオ

EY のセクションでは、Frank Pitman 氏（EY の tax partner）によるビデオが流れました。語られた内容は次のとおりです。

1. 出発点は、EY の最大の税務ナレッジデータベースに接続された既存の tax advisory agent でした。ユーザーのやり取りから学び、フィードバックでチューニングし、新しいモデルを活用できるよう、その周りに agent learning environment を作る必要がありました。
2. GitHub Copilot の Frontier Tuning plugin に依頼して設定します。plugin は、エージェントのスキルファイル（instruction manual）と、良い税務アドバイスの回答の品質チェックを読み込みます。
3. 現地の税務専門家と作った golden question-and-answer の集合を与え、まずスキル、次にハーネス、最後に使用する言語モデル（MAI 1.1）をチューニングしました。各ステップで品質チェックが出力を採点し、tree search で複数のリサーチ経路を試して、良いものを残します。
4. 出来上がったチューニング済みの tax research agent を、実際の end-to-end の税務アドバイザリーのワークフローに組み込みます。level 3 の agentic AI システムの中で、他のエージェントと連携します。
5. デモ環境にクライアントの質問を入れて workflow を起動します。チューニング済みエージェントがまず、ナレッジデータベースと、グラフ（"my graph" と聞こえます）上の選ばれたクライアントデータを使ってリサーチを行います。その出力を writer agent が EY のスタイルのメモにまとめ、reviewer agent が会社の基準に照らして確認します。結果が本人に共有され、本人がフィードバックを返すと、ワークフローが再度動きます。

### 6.4 declarative agents への展開予定

## 7. 注意点・発表者の気付き

- **rubrics は継続的に磨く。** 一度作って終わりではなく、品質が hill climbing の成果を左右する、と強調されました。
- **コストとの兼ね合いで配置点を選ぶ。** 品質が出るだけでなく、「グラフ上のどの点を本番にデプロイするか」を、タスクあたりのコストを見て決める必要があると説明されました。
- **評価で副作用を起こさない。** メール送信や DB 更新を伴うタスクの評価では、仮想化したツールを使わないと、ロールアウトの回数分だけ実際の副作用が出てしまいます。
- **ドリフトに注意する。** ファインチューニング済みモデルが呼ばれる頻度が落ちたら、再チューニングの合図です。
- **SME の協力が前提になる。** 専門家が rubrics を明文化していることが、早期顧客に共通する条件として挙げられました。
- 一般向けの提供時期や価格、利用条件などは、「tune with Copilot credits」が coming soon と言及された以外は、発表では触れられていません。

## 8. 利用者にとっての利点

Kalyan 氏が、早期の private preview 顧客の結果を紹介しました。共通点は、(1) 専門家がいて、rubrics を明文化していること、(2) 「小さなモデルをチューニングして、より低いコストでフロンティア品質に届くか」という問いを持っていることです。

### 8.1 Land O'Lakes（バターの会社）

business-critical な文書である sensory report（官能評価レポート）の作成プロセスがあり、専門家が基準を rubrics にして、学習環境、体系的な評価、チューニングを実施しました。フロンティアモデルの基準点（GPT-5.6 SOL と聞こえます）を点線で示し、小さなモデルと比較しています。

| モデル | 結果（発表の説明） |
| ---- | ---- |
| GPT-6 Luna | 評価時はフロンティアを下回ったが、ハーネスチューニングと tree search でフロンティアを超えた |
| MAI-11 | tree search でフロンティアにぎりぎり到達した |
| MAI-11（先にファインチューニングし、その上で tree search） | フロンティアを大きく上回った |
| GPT-5.4 mini（音声では「GPT-54 mini」と聞こえ、表記は音声認識に依存します） | MAI と似た経路で、やや低い水準 |

要点は、**Frontier Tuning ではモデルを選べ、複数のモデルから始めてフロンティア品質に到達できる** ことです。

### 8.2 Pearson（Teams 会議の録画を使うコミュニケーションコーチング）

エージェントは、従業員の Teams 会議の録画を使ってコミュニケーションのコーチングを行います。Pearson の教育設計に忠実である必要があり、学習の専門家が教育法と指示をスキルと rubrics に符号化して、非公開ベンチマークにしました。フロンティアモデルは約 0.9 のスコアという高い基準でした（数値は音声認識で不明瞭です）。MAI-11 はそれを下回りましたが、tree search とファインチューニングの 2 つの戦略でチューニングすると、どちらもフロンティアの水準に届きました。

どこにデプロイするかは、x 軸にタスクあたりのコスト、y 軸に品質を取ったグラフで判断します。フロンティアは 1 タスクあたり約 1.78 ドルでした。MAI-11 ベースのハーネスチューニング版もファインチューニング版も、緑の領域（コストが低く、品質がフロンティアの水準）に入り、**約 25 セント／タスク** でした。数千回のコーチングを行うと、Pearson では約 1,800 ドルに対し、チューニングした MAI では約 250 ドルです。Kalyan 氏は、これがコーチングエージェントが「パイロット止まり」になるか「全社展開」になるかの差だと述べました。

### 8.3 Microsoft 内のチーム

Microsoft の HR、marketing、supply chain などのチームが Frontier Tuning を採用し、自分たちの専門性と業務プロセスを RLE にして、hill climbing を効率よく進めたと紹介されました（スライドには Microsoft HR の例が示されました）。

### 8.4 EY（Ben Ambrosino 氏）

EY の税務は、国・地域ごとに規制や基準が異なり、解釈も多い領域です。「税務は 1 つのユースケースではなく、100 万のユースケース」だと述べられました。事業の大きな部分がアドバイスであり、顧客の質問に答えるものです。目標は次の 3 点でした。

- **より質の高いアドバイス**: 担当チームの最善ではなく、組織全体の最善を出せること。
- **より速い回答**: 難しい質問は数日、数週間、場合によっては数か月かかるため、リアルタイムの意思決定に使えるくらいに短縮したいこと。
- **正確で、再現可能で、説明可能であること**: EY の事業は信頼であり、説明できない AI の回答は出せないため。

このチューニングは大規模に行う必要があり、Frontier Tuning のように簡素化して専門家の手に渡す機能があって初めて実現できた、と述べられました。開発中の tax advisor は、世界の **75,000 人の EY の tax professional** に展開される予定で、全社への展開を進めています。

選んだのは、複雑なユースケースである L3 tax advisor です。例として「最新の pillar 2 の動きは Contoso に影響するか」という質問が挙げられました（pillar 2 は複数国にまたがる複雑な税規制と説明されました）。構成は次のようなマルチエージェントのワークフローです。

1. orchestrator が、タスクを適切なエージェントに振り分けます。
2. **research tax advisor agent**（ファインチューニングを使った部分）が、税務アドバイザーのやり方で質問を分解します。ツールとして Web 検索（規制や判例は頻繁に変わるため最新情報の確認用）と、EY の知識とノウハウの集積である "EY POCA"（表記は音声認識に依存）を使います。POCA には数千万件の過去の先例と EY の見解がある、と説明されました。
3. writer agent が、EY のトーンと構成、必要な注意書き（caveats）を付けて文書化します。
4. reviewing agent が、問題点や課題を指摘して修正を提案し、writer agent、場合によっては researcher agent に差し戻します。
5. その出力を、税務の専門家が最初に目にします。

現在のやり方と大きくは違わないものの、納期の制約で掘り下げる深さに限りがあった従来と比べ、**最後まで掘り下げ、あらゆる側面を、速度、信頼性、説明可能性とともに検討できる** と説明されました。

Ben 氏は、このビデオのデモを担当した Frank 氏がデータサイエンティストでも IT 部門の人間でもなく、税務の専門家であることを強調しました。Frontier Tuning チームと協力し、rubrics の抽出や継続的なファインチューニングを進め、非常に価値の高いものを作れたという話です。

## 9. まとめ

Frontier Tuning は、自社の業務をデジタルツインとして学習環境にし、評価、hill climbing（スキル、ハーネス、モデル）で、自社専用の AI を作る取り組みです。Tuning 環境（スキル、rubrics、ツール、サンプル）を評価、訓練、推論で共通に使う点が特徴で、rubrics を磨き続けることが鍵になります。

事例では、Land O'Lakes では GPT-6 Luna や MAI-11 などの小さなモデルがフロンティアの基準に届き、Pearson ではフロンティアモデルの約 1.78 ドル／タスクに対し、チューニングした MAI-11 は約 0.25 ドル／タスクでした。EY では、税務の専門家自身が rubrics を整えてチューニングし、75,000 人規模の展開が進んでいます。

最後に Ranveer 氏は、Frontier Tuning は Foundry の上に構築されており、Copilot Studio、Cowork 上の GitHub Copilot から使え、公開した先ではどのサーフェスでも使える、と説明しました。始めるには、プラグインを入れて「help me hill climb」のように話しかけるだけで、必要ならチューニング済みモデルまで届けてくれるそうです。案内された URL は aka.ms/frontiertuning です。このセッションに Q&A の時間はありませんでした（時間切れで終了しています）。

締めくくりとして Ranveer 氏は、これらのループが「自社の話し方、考え方、仕事の仕方」を捉えるもので、それが競争優位になると考えていると述べました。
