# BRK285 Your agent works. Now make it enterprise-ready.

## 1. はじめに

このセッションは、「agent が動く」状態から「企業が頼れる」状態へ進めるために、何が必要になるかを 2 つの道のり（journey）で説明したものです。1 つ目は、Tim Schaeps 氏が自作の prototype を enterprise 向けのアーキテクチャに作り直した経験です。2 つ目は、Azure のサポートで実際に稼働している autonomous resolution（自律解決）システムを、Ali Ijaz 氏と Arun Masilamani 氏が、実験から本番、そして自律運用へと育ててきた経緯です。

全体を貫く考え方は、**自律性（autonomy）はスイッチではなく、証拠に裏づけられて委譲していく責任である**というものです。prototype、enterprise ready、定義された範囲での fully autonomous という 3 段階を、評価（evals）、統制、observability（可観測性）、失敗の改善サイクルといった実践とあわせて紹介しています。

デモについては、Tim 氏が自作アプリの画面と、アーキテクチャが組み上がっていく様子の動画を見せています（6 章）。Azure サポートの事例は、発表者が「mock であり実際の製品のスクリーンショットではない」と断ったスライドによる説明です。

## 4. 発表者が伝えたいメッセージ

* **問いは「人を外すか」ではなく、「どの判断を委譲する資格を得たか」。** fully autonomous とは、無制限の権限を与えることではなく、enterprise ready なシナリオの中から条件を満たしたものを選ぶことだと説明されています。
* **agent に必要なのは「何でもできる権限」ではなく「定義した境界の中で、特定の状況での特定の行動の権限」。** 証拠が足りない、ツールがタイムアウトした、といった場合は、確認を求める、リトライする（"retry the limits" と聞こえ、意味は音声認識の都合で確定できません）、エスカレーションする、といった安全な次の一手を取ります。目標は「助けを必要としない agent」ではなく「助けが必要なときを知っている agent」です。
* **証拠が自律性を決める。** 「説明できない権限を与えない」「元に戻せない権限を与えない」の 2 つのルールが示されました。
* **ローンチ後が本番の戦い。** 本番でも agent は hallucination を起こします。本番のトレースを集め、失敗を検証済みの改善に変える仕組みが必要です。

## 5. 発表内容の詳細

### 5.1 3 つの約束と、責任のレベル

最初のスライドは 3 つの約束で構成されています。

| 段階 | 最適化する対象 | 内容 |
| ---- | ---- | ---- |
| 実験（prototype） | learning（学び） | 有用なものができ、人が結果を確認する。「追求する価値があるか」を見る |
| enterprise ready | trust、integration、control | 実際のプロセスと、実際の責任体制に収まるか |
| fully autonomous | 条件を満たしたシナリオ | 無制限の権限ではなく、enterprise ready の中から選ばれたシナリオ |

多くの人がつまずくのは、「確認したら正しく見えたから本番へ」と考えてしまうところです。最も難しいのは中間の段階で、本番に置く agent に適切な identity、証拠、権限が必要で、測定でき、誰が所有し、どんな検証が行われ、動く前に何を提案するかが分かっていなければなりません。

Om Prakash 氏は、Azure の環境を能動的に監視して問題を知らせる自律 agent を例に、「アプリケーションが失敗している」だけでは足りず、どのアプリケーション、どのリソースで、どこが悪く、診断が何を示すかまで必要だと述べています。美しい答えでも対象のリソースが違えば誤りで、hallucination は気づくのに時間がかかります。

サポート agent は、応答の下書き、各ステップの推奨、ステップの実行という **3 つの責任のレベル** で動き、同じ承認ポリシーを適用すべきではない、と説明されています。また、ケースを閉じることと、顧客の問題を解決することは同じではなく、ワークフローが完了したかどうかより成果が重要です。

### 5.2 技術マップ（スライド）

使われる製品と役割は次のとおりです（ここで示されたのは、発表者の例であり、同じスタックを使う必要はないとされています）。

| 製品 | 役割 |
| ---- | ---- |
| GitHub Copilot、Visual Studio Code | 構築と反復。変更の承認は人が持つ |
| Copilot Studio | agent の runtime と specialist agent |
| Dynamics 365 Customer Service | サポートケースの置き場所（Microsoft のコンタクトセンター製品）。解決とエスカレーションがここからサポートプロセスに戻る |
| Azure Services | 本番の基盤、実行、API、モニタリング |
| Foundry | 実験の場。モデル、評価、リリースゲート |
| Fabric、Power BI | 成果の把握。KPI の作成と agent の性能の測定 |

重要なのは製品の数ではなく、enterprise 側の責任をこのスタックで果たせるかどうか、という説明です。

### 5.3 Journey 1: prototype から enterprise アーキテクチャへ（Tim 氏）

**背景。** 多くの組織は、ボードルームで「AI をやる」と決め、次に MVP（prototype）で価値を早く示します。その後の「本番へどう持っていくか」で苦労する、というのが Tim 氏の説明です。ガードレールや強い基盤、ガバナンス、インフラ、ユーザーの扱いなどを考える必要があります。

Tim 氏がパートナー支援で使う **3 つの構成要素からなる枠組み** は次のとおりです（すべてを使う必要はなく、使える接点を見つけてほしい、という前置きがあります）。

1. **AI COE（center of excellence）**: ユースケースの発見と、安全に素早くプロトタイプを作れる場
2. **再利用できる基盤**: Well-Architected なデータ基盤、Cloud Adoption Framework など。火曜朝の keynote で大きく扱われた Agent 365 もここに組み込める
3. **agent factory**: 複数の agent を標準化された方法で作り続け、作ったものから学び、継続的なフィードバックループで価値を上げる仕組み

**prototype の内容。** Tim 氏が作ったのは、ユーザーがビジネスプロセスと業界を指定すると、関連する有用なユースケースを提案する agent ソリューション（AI discovery）です。5 年前と比べると、今は prototype を非常に速く作れるようになり、1 日で価値を出せる一方、数年前は 1 週間から数週間かかったと述べています。prototype の目的は強いアーキテクチャではなく、「このアイデアは動くか」を見ること、そして何に投資し何に投資しないかを決めることです。

**prototype の問題。** アプリを時間とともに構築する様子の映像では、feature を足していくだけで、成功するためのアーキテクチャが整っていないことが分かります。例として、Cosmos DB のバックエンドを追加したところ、デモ環境の Azure ポリシー（public endpoint を使えない）のために、しばらくは動いたのに突然動かなくなりました。GitHub Copilot が原因の特定と新しいアーキテクチャの構築を助けましたが、対応は reactive（後追い）で、望ましい形ではなかった、と説明しています。

Tim 氏は挙手を 2 回求めています。「このような体験にビジネス価値を見るか」には「数人」、「本番に出すか」には、「少なくとも自分は今の形では出さない」と述べました。

**作り直しの考え方。** prototype の上に積むか、ゼロから作り直すかという選択があり、いまの技術なら作り直しは非常に容易で、境界（アーキテクチャ、agent に何をさせ何をさせないか）を最初から決められる、という考えです。手順は次の 3 つです。

1. 機能の baseline（prototype から何を残すか）
2. 本番の要件（非機能要件、既存のアプリケーション環境への適合）
3. その 2 つを両立させるための、アーキテクチャの決定

ここで **Microsoft Learn MCP** が役立つ、とされています。Microsoft の全ドキュメント（Cloud Adoption Framework、Well-Architected Framework を含む）に直接つながり、質問すると情報を取得して選択肢に疑問を投げかけ、選択肢を示し、まだ知らないことの発見にもなります。最後に決めて検証するのは architect です。

もう 1 つの重要な学びは、prototype では派手な UI が作りやすいものの、作り直すなら、まず強いアーキテクチャとライフサイクル管理に集中し、UI は後でよい、という点です。

**作り直した結果（platform）。** Tim 氏は、守りたい原則を 5 つ決め（詳細は語られていません）、agent platform を作ったと話します。先の枠組みの 3 要素が次のように対応しています。

* コンポーネント 1: AI COE と solution envisioning。prototype の機能にあたり、AI のユースケースを出す
* コンポーネント 2: 基盤アーキテクチャと、agent をホストして動かす安全なサンドボックス環境
* コンポーネント 3: agent factory。コンポーネント 1 のユースケースを受け取り、GitHub 連携で、必要なプロンプトを入れた GitHub リポジトリをあらかじめ用意する。アプリ自体の構築は、Copilot などの既存ツールを使う

Agent 365、Foundry、Copilot は強力で進化が速いので、それらを使って統合し、この platform は引き継ぎ（handoff）の場にする、という方針です。

platform の流れは 4 ステップ（discovery、discovery から出た agent の構築、platform への publish、agent の運用）です。アーキテクチャの映像には 5 つの構成要素が出てきます（聞こえたままの表記）。

1. control plane と experience
2. 外部の build と delivery
3. platform hosting と shared foundation
4. monitoring、evolution、life cycle management（"evolution" は聞こえたままの表記で、音声認識の都合で確定できません）。agent の動きから学ぶために不可欠
5. model と tool access

原則として挙げられたのは、**separation of responsibilities（責任の分離）** と **least privilege（最小権限）** です。最小権限は、運用する agent だけでなく、構築を行う agent にも当てはまり、「災害に陥らないように」制限するとしています。それ以外の原則は音声からは聞き取れません。映像では、feature を足していく方式と違い、最初から枠組みがあり、必要な構成要素をはめていく流れだと説明されています。

**プロセス。**

1. Microsoft Learn でアーキテクチャの根拠づけ（Cloud Adoption Framework、Well-Architected Framework、強い SDLC 管理）を行い、判断を architecture design records に残す
2. infrastructure as code とテストを伴って、アプリや agent を構築する（一部聞き取り不明瞭）
3. 事前に定めたアーキテクチャに照らしてレビューする
4. 安全にデプロイする。Copilot でこうした作業を任せられると説明している（一部聞き取り不明瞭）
5. 構築を行う agent と、運用する platform が境界の中にとどまっているかを observe する

**4 つの教訓。**

| 教訓 | 内容 |
| ---- | ---- |
| Make your intent explicit | 成果を定義する。prototype なら価値を見たい、enterprise なら守るべき原則に従う。意図が異なる |
| Enforce your boundaries | 境界を強制する |
| Engineer from day zero | ライフサイクル管理を最初から自動化し、安全にする |
| Verify to change | コードとモデルを常に再確認する。新しいモデルが出ても切り替えやすくする |

### 5.4 Journey 2: Azure サポートの autonomous resolution（FACS）

Arun 氏の説明によると、**FACS（fully autonomous customer service）** は、現在 Azure のカスタマーサポートで本番稼働している autonomous resolution システムです。「最初から自律性で始めたわけではない。有用な仕事ができる agent から始め、自分で動く資格を得ていった」という正直な話から始まり、段階は experiment、enterprise ready、定義された境界つきの autonomous で、1 段階ずつ進めたとのことです。

**事例のウォークスルー（スライド上の mock）。** 先に完成形のケースが紹介されました。発表者は「mock であり、実際の製品のスクリーンショットではない」と断っています。注目する 3 つの要素は、Dynamics 365 Customer Service、FACS、そして自分たちのカスタム resolution agent です。

1. Contoso の顧客 Jordan の App Service が 503 エラーでダウンしている。ケースが登録され、FACS が agent に調査を渡す。
2. 誰も Jordan にサブスクリプション ID を尋ねず、agent が直接診断に進んで簡易チェックを行う。3 インスタンスのうち 0 が正常で、デプロイ直後（デプロイ番号の聞き取りは不明瞭）から起きている。
3. 根本原因は、最新のデプロイによる起動の失敗だと agent が推論した。修正は、（聞き取り不明瞭な確認作業をしたうえで）ロールバックすること。
4. 送信の前に、返信は evidence、quality、safety のチェックを通過した。顧客に返す前のガードレールの確認である。
5. Jordan がロールバックする。agent は文脈を保持していて、「ヘルスチェックは通っているか」と尋ねる。
6. Jordan が正常を確認し、エスカレーションは不要。ケースは、明確な根本原因、解決策、顧客が確認した解決とともにクローズされる。すべて定義された境界の中で行われる。

これが現在の状態で、条件を満たしたケースは end-to-end で解決されますが、最初からこうだったわけではないと説明されています。

### 5.5 実験の段階（Arun 氏）

* 最初の目的は自律性ではなく、有用な仕事を証明すること。サポートの解決として検証する価値があるものを定義した。
* Microsoft Copilot Studio、Foundry、Microsoft Power Platform のコネクターで、ローコードの agent を速く作って反復した。
* 技術的な正確性の基本的な評価を行い、サポートエンジニアがすべての出力をレビューした。
* 本番への統合は、広く展開する確信が持てるまで意図的に制限した。
* 得られた証拠は、人がレビューした出力、失敗パターン、agent が扱えるシナリオの明確な像。

挙手の質問として、「デモでは動くが、本番の準備ができていない agent を持つ人」には数人が挙手しました。また「明日 agent が消えたら、誰かが価値の欠如に気づくか」という問いが、次の段階に進む準備ができているかのテストとして示されています。

### 5.6 信頼を築く段階: 人によるレビューと証拠

2 段階目は trust で、人による検証が中心です。「人によるレビューを行っている人」「人が答えを変えた理由を記録している人」への挙手も求められ、その理由の記録が、このプロセスでの価値あるデータだと述べています。

* 人によるレビューは、agent が失敗した印ではなく、システムの自律性を獲得するための証拠を集める手段。
* 信頼が高まるにつれ、レビューは次のように変わる: すべての出力を人が見る → 統制と所有者を伴う構造化されたレビュー → 個別の（case-by-case）レビューなしで、証拠のみで判断。

そこに至るために行ったことは次の 4 点です。

1. **品質の評価（assess quality）**: 人間の専門家が rubric で出力を採点した。これが最初の custom evals になった。evals の重要性は強調してもしすぎることはない、と述べています。
2. **確信を築く（building confidence）**: shadow run を実施し、agent の出力と、同じケースでエンジニアなら何をしたかを比較した。
3. **失敗パターンの発見**: 個別に見るのではなく、トレースをグループ化してフィードバックをレビューし、パターンごとに分類して修正した。
4. **自律性へのゲート**: 品質、統制、証拠がすべて基準を満たしたシナリオだけが対象になる。1 シナリオずつ進める。

問いとして「リーダーが、レビューなしで agent に動かせるために必要とする証拠は何か」が示されました。

### 5.7 統制（controls）

証拠が許可を与え、自律性が増すにつれ統制が必要になります。3 段階で統制は次のように変わります。

| 段階 | 主な統制 |
| ---- | ---- |
| experiment | 人（human in the loop）によるレビュー |
| enterprise scale | 人だけでは統制にならない。ポリシー、テスト、テレメトリ、owner を整え、証拠が許す速さでだけ展開を広げる |
| agent が動く（act）段階 | 基準がさらに上がる。scoped identity、bounded actions、すべてのターンが見える状態、検知・封じ込め・ロールバックの能力 |

2 つのルールは、**説明できない権限を与えない、元に戻せない権限を与えない**です。スライドの右端の列にある統制のうち、最初のブロッカーになるものへの挙手も求められました。

### 5.8 アーキテクチャの進化（Ali 氏）

Ali 氏によると、約 18 か月前は速度と学びを最適化していました。

* **初期:** Microsoft Foundry と Copilot Studio で、no/low-code の agent による実験。MCP で多くのツールやテレメトリに接続。この分野の SME（専門家）が全応答をレビューした。
* **課題:** Azure のお客様は多様で、サポートケースは単発のやりとりではなく、複雑な場合は数日にわたる複数の会話になる。必要になったのは、永続的な状態（persistent state）、監査証跡、より強い評価、リリースゲート。Azure Functions、Cosmos DB、追加の品質統制を加えた。
* **自律性の拡大:** durable orchestration、ツール失敗時の復旧、定義された境界の中での解決またはエスカレーションを追加した。

**3 つの別々のアーキテクチャではなく、各段階が前の段階の上に積まれた**、うまくいったものを残し、agent の責任が増えるのに応じて必要な機能を足した、という点が強調されています。

使われている技術の役割は次のとおりです。

| 技術 | 役割 |
| ---- | ---- |
| Copilot Studio | 立ち上げに使い、現在も orchestrator を動かす。specialist agent もある |
| Microsoft Foundry | 評価フレームワークの一部、最新モデルの影響の測定、品質評価のスケール、リリースゲート。frontier モデルを構築する新機能にも期待している |
| Power Platform | enterprise ワークフローとガバナンス |
| MCP | ツールのブリッジ。情報や製品ドキュメントなどへのアクセスを提供し、追加を続けている |

要件が増えるにつれ、ポリシー、適切なチェック、耐障害性を追加してきました。重要な点は、成熟にあわせて技術を置き換えたのではなく、その上に積み、強みを組み合わせたことです。

### 5.9 稼働中のアーキテクチャ（Ali 氏）

現在 Azure で稼働しているアーキテクチャは、先の Jordan のケースと同じものです。

* 左: **Dynamics 365** がケース管理システムで、FACS が enterprise 規模のシームレスな agentic 体験を提供する。**Power Automate** が、顧客が返信したりケースを作成したりするたびにワークフローを起動する。
* 中央: **Copilot Studio** が orchestrator として調査を調整し、証拠を集め、次の適切な手順、または呼び出すべき agent（Copilot Studio、Foundry、ProCode のいずれか）を決める。MCP で情報とテレメトリを取得する。
* 右: **Azure Functions と Cosmos DB** による durable execution と、永続的なケース状態。
* 下: evals、モニタリング、本番の分析からなる quality and operations 基盤。

現実のケースは Contoso の例ほど順調ではなく、ツールは失敗し、顧客は数日後、場合によっては数週間・数か月後に戻ってきて、調査は中断されます。Contoso の例では、顧客が返信してきたとき、agent は調査をやり直さず、**中断したところから再開**したと説明されています。また、修正を推奨しただけではケースを閉じず、**顧客の確認を待ってから、許可された次の解決アクションを取りました**。

まとめとして Ali 氏は、これは単に回答を生成する、単純な LLM 呼び出しではなく、文脈を保って調査し、定義された境界の中で顧客の問題を確実に解決するよう設計された **システム** だと述べています。ここまでのすべては、VS Code の GitHub Copilot で作成・管理できるとも紹介されました。

### 5.10 hallucination と hill climbing

Ali 氏は、これだけの作業をしても agent は hallucination を起こしたと率直に述べています（会場に挙手を求め、数人が手を挙げました）。スケールして動かすのは課題の最初の部分にすぎず、信頼性を保って継続的に改善するほうが同じくらい、あるいはそれ以上に重要だと説明しています。

* 本番のトレース、ツール呼び出し、evals、ソースの品質指標、成果などを集め、製品ドキュメントや診断ツール、システムのテレメトリと組み合わせる。
* **失敗を見つけるのは簡単で、なぜ失敗したか、何を変えるべきかを理解するのが難しい。** Contoso の例で agent が起動の失敗を見落としたり、別の経路へ逸れたりしたとき、skills が古くなっていないか、ドキュメントか診断か、その組み合わせかなどを調べる必要があった。
* 「もっと賢く考えて」「もっと頑張って」と agent に伝えても効かない、と述べています。

そこで作ったのが **hill climbing** のプロセスです。

1. agentic ソリューションと、人間の SME を組み合わせて、プロンプト、ドキュメント、skills、ツールなどの改善点を絞り込む
2. 専門家のベンチマーク、データセット、eval の rubric で変更を検証し、改善と退行を確認してからデプロイする
3. デプロイ後も測定を続ける

目標は、本番の失敗を、個別の一回きりの修正ではなく、検証された改善に変えることです。

### 5.11 各段階の学び（まとめのスライド）

左側が agent 自体、右側が評価・セキュリティ・統制の成熟です。agent は、人がレビューする実験から、state と quality gate を加え、耐久性を高めてきました。評価・統制は、基本的なチェックから、専門家主導の rubric とリリースゲートへ進み、identity、アクセス制御、データ保護、監査可能性が強化されています。自律性が増すにつれ、安全に動かすための能力も強化する必要があった、と説明されています。

まとめの場面では、「自律性は、スイッチを入れるものではなく、獲得するもの。技術が進んでも、各段階で人が責任を持ち続けた」と述べたうえで、各段階の学びを 1 つずつ共有しようと、Tim 氏に「実験」段階の学びを振っています。ところが時間が超過していたため、別の登壇者が「手短に終える」と引き取りました。この登壇者は「最初に、頭の中の agent を思い浮かべてほしいと頼んだ」と話しており、冒頭の挨拶で agent を思い浮かべるよう求めた Om Prakash 氏です。Tim 氏の「実験」段階の学びは、書き起こしには出てきません。

* **ownership と control。** enterprise では多くのチームが異なるプラットフォームを管理しているため、問題が起きると「あのチームが」と責任の押し合いになる。そこで、すべての agent に trace studios（音声認識の都合で表記が確定できません）を有効にし、どこで問題が起きたか、どのチームが所有しているかを特定できるようにした、と説明しています。
* **コスト。** agent がうまく動くと、財務チームから「なぜこんなにコストがかかるのか」「トークンを最適化できないか」と言われる。レイテンシ、コスト、トークンの面が課題で、現在のツールで状況を把握し、最適化できる。

### 5.12 agent の枠組み（最後のスライド）

最後のスライドは、agent の段階を考える枠組みで、各段階で次の問いを立てます。

| 段階 | 問い |
| ---- | ---- |
| build | これを作る価値は本当にあるか |
| validate | 出力を信頼してよいと言える証拠は何か |
| operationalize | 動かせるか。observe できるか。モニタリングを有効にしたか。かけているコストに見合う価値か |
| automate | 誰かが各ステップを承認しなくても、安全に行うにはどうするか |
| optimize | 次のステップ、次のバージョンをどう良くするか |

冒頭で求めた「自分の agent を 1 つ思い浮かべる」ことに対して、この枠組みで、その agent がどの段階にあり、次に何をすべきかを考えるよう呼びかけています。それが次のエンジニアリングのタスクだ、という言葉でした。

## 7. 注意点・発表者の気付き

* **prototype の確認だけで本番に進まない。** 「確認したら正しく見えた」は、多くの人が間違えるところです。
* **非機能要件を後回しにしない。** Tim 氏の Cosmos DB の例のように、アーキテクチャがないと、ポリシー違反への対応が後追いになる。
* **UI より先にアーキテクチャ。** prototype を作り直すときは、まず architecture とライフサイクル管理に集中する。
* **最小権限は構築する agent にも。** 運用する agent だけでなく、構築を行う agent にも制限をかける。
* **正しそうな答えが、誤ったリソースについてのものかもしれない。** 診断の根拠まで必要です。
* **人のレビューの理由を記録する。** 答えを変えた理由が、貴重なデータです。
* **本番では現実が複雑。** ツールは失敗し、顧客は数日～数か月後に戻り、調査は中断される。durable な実行と永続的な状態が必要になった。
* **agent を責めても効かない。** 「もっと賢く」と指示しても改善せず、プロンプト、ドキュメント、skills、ツールなどを特定して直し、検証してからデプロイする。
* **責任の所在とコスト。** 複数チームが関わる agent では、誰が所有するかが問題になり、財務からはトークンコストの最適化を求められる。

## 8. 利用者にとっての利点

この発表は主に、自分で agent を本番にするための考え方と事例の共有で、導入効果の数値（削減率、件数など）は語られていません。発表で語られた成果と利点は次のとおりです。

* **Azure サポートでの実績:** FACS は、Azure のカスタマーサポートで本番稼働している。条件を満たしたケースは end-to-end で解決される。
* **顧客体験の例（mock）:** Jordan のケースでは、サブスクリプション ID を尋ねることなく診断に進み、ロールバックを案内して、顧客の確認後にクローズした。
* **失敗から学ぶ仕組み:** hill climbing により、本番の失敗を、検証された改善に変える。
* **Tim 氏の journey:** 数年前は 1 週間から数週間かかった prototype が、今は 1 日で価値を出せる、という説明。作り直した platform は、Agent 365、Foundry、Copilot などの既存ソリューションと統合し、引き継ぎ（handoff）の場にする方針。

## 9. まとめ

「agent が動く」ことと「企業が頼れる」ことの間には大きな差があります。Tim 氏は、prototype から機能の baseline を取り出し、非機能要件とアーキテクチャの決定を加えて、最初から枠組みを作る進め方を示しました。意図の明確化、境界の強制、day zero からのエンジニアリング、変更への検証が 4 つの教訓です。

Arun 氏と Ali 氏は、Azure サポートの FACS を、人によるレビュー、custom evals、shadow run、失敗パターンの分析、シナリオごとのゲートを経て育てた事例を共有しました。統制は、scoped identity や bounded actions など、検知・封じ込め・ロールバックの能力へ段階的に強まり、「説明できない権限、元に戻せない権限は与えない」が基準です。それでも hallucination は起きるため、hill climbing で本番の失敗を検証済みの改善に変えています。

**自律性はスイッチではなく、証拠に裏づけられて委譲される責任であり、人をループから完全に外すことではない**、というのが全体の結論です。
