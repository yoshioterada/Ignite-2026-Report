# BRK571 Beyond the Pilot: Turning Copilot & Agents into Business Value

## 1. はじめに

AI のパイロット（試験導入）は、いまや至るところで行われています。ところが、それを持続的なビジネス成果につなげるのは簡単ではありません。このセッションは、パイロットの先へ進んだ組織が、どのようにシナリオを選び、関係者をそろえ、ビジネスへの効果を測っているかを探るパネルディスカッションです。モデレーターの Srini Raghavan 氏（Microsoft）が、Ericsson と Bristol Myers Squibb（BMS）の 2 人の顧客、Microsoft の Steve Gustavson 氏に話を聞く形で進みます。

話題は、データの権限整理、Copilot の Chat・Cowork・Autopilot をどう使い分けるか、コストの管理と ROI、プロセスの作り直し（rewiring）、個人の生産性から全社展開へのスケール、と広がります。後半は会場からの質問に答える Q&A で、予算の立て方や、エージェントを 1 つにまとめるべきかといった具体的な悩みが出ました。

このセッションでは、画面を使ったデモは行われていません。登壇者の経験談と対話が中心です。

**Mike 氏（BMS）**

**Steve 氏（Microsoft）**
自身の担当領域を紹介し、後半の議論で、信頼、可観測性（observability）、委任をどうデザインするかを話したいと述べました。

**Srini 氏の Autopilot の例**
Srini 氏自身も、バックグラウンドで常に動く Autopilot を使っていると紹介しました。毎週少なくとも 2 件の顧客エグゼクティブブリーフィングがあり、Autopilot がカレンダーを走査します。例えば（Srini 氏の仮定の例として）Ericsson が Redmond でのブリーフィングを控えていると、顧客とのやり取り、資料、デッキ、使用状況データなどを自動で調べ、ダッシュボードを作ってくれます。同じ内容を顧客にも見せている、とのことです。

### 5.2 個人の生産性を超えて: 組織の変化とスキル

Srini 氏は、「もっと速く、もっと多く」を超えて、AI とエージェントが組織の動き方をどう変えているか、そのためにどんなスキルや人材を育てるか、と Martin 氏に尋ねました。

Martin 氏は、同社の事業部門のリーダーシップチームの例を挙げました。5 か年戦略の策定サイクルで、以前は準備や分析に時間がかかっていましたが、Cowork を使ってタスクを送り、データを入れ、回答を得て、SWOT 分析、機会、戦略的優先事項、KPI のドラフトを Cowork が作りました（"Tanner division" と聞こえますが、部門名は音声認識の都合で確定できません）。これが初日にできたそうです。さらに、別のエージェントをチームの「悪魔の代弁者」のように使い、「これは筋が通っているか」と深く問いただして挑戦させました。チームの言葉では「7 倍速かった」とのことで、1 週間かかっていたものが 1 日に収まり、説明を受ける会議から、すぐに決定に入る会議に変わったと話しています。

スキルについては、人間には創造性、判断、批判的な評価、そして変革を実現する「チェンジエージェント」としての役割が引き続き必要だと述べました。Srini 氏は、AI を使う人だけでなく、変化を伝え広げる人（mavens や connectors）が必要だと補足しています。

### 5.3 データのアクセス権限: BMS の経験

医療・ライフサイエンス業界は規制が多いため、Srini 氏は、データの権限をどう準備したかを Mike 氏に尋ねました。

Mike 氏の回答は次のとおりです。

* エージェントと SharePoint を使い始めたところ、**オーバーシェア**（本人が知らないまま権限を持っているファイル）に気づいた。危険なものではなかったが、セキュリティを通じてすぐ見つかった。30 年分のファイルがあり、レビューで固めたつもりだった。
* そこで一歩下がり、SharePoint サイト、共有などを再検証した。ファイルが正しく分類されていない、あるいはオーバーシェアされていると、**AI はそれを見つけ、しかも速く見つける**、と気づいたため。
* 今年の多くは、ファイルのタグ付けと分類、共有の確認に使った。異動した人が、元のグループに残ったままになる、という問題もあった。
* すべてを見つけられるわけではなく、常に見張っている。パイロットのエージェントを管理された形で出し、小さな問題を見つけて調整してから、大きく展開している。
* 「AI はデータから始まる。データが正しく、きれいで、安全である必要がある」と、AI を放つ前にデータを見直すことが鍵だと述べています。

### 5.4 アクセス権限とユーザー体験（Srini 氏の事例と Steve 氏の話）

Srini 氏は、前日の出来事を紹介しました。顧客との会議中、チームの 1 人から「別の会議の録画と要約へのアクセスを、ほかの 3 人にも共有してほしい」と連絡が来ました。Teams では、会議の録画へのアクセスがすべての人に自動で付与されるわけではありません。手作業では 8 クリック程度かかるため、Srini 氏は会議中に自分の Autopilot に、メールを読んでその会議へのアクセスを 3 人に付与するよう指示しました。会議を終えて確認すると、全員にアクセスが付与され、3 人にメールも送られていたそうです。

Steve 氏は、Mike 氏の話は、いままさにデザインチームが時間をかけて考えていることだと述べました。Copilot には Library と Workspaces（前日に発表）があり、どれも同じ種類の UX の課題を抱えています。Microsoft 社内では「赤いシールド」のような表示があるが、そうした手がかりがないと、重要かどうか、誰がアクセスできるかの判断をユーザーに押し付けることになる、という懸念です。

Steve 氏は、デザインの仕事が次のように変わってきていると説明しました。

* アプリが単体で優れていることに加えて、**エージェントの振る舞いをどうデザインするか**、人が「このエージェントは何を持っているのか」を知りたいときの**人間の可観測性**をどうデザインするかが重要になっている。
* 例えば、他の人のエージェントや Autopilot に Teams で話しかけたとき、自分に対してそのエージェントがどこまでアクセスできるか分からない。カレンダーを知っているのか、Srini 氏のカレンダーを自分に教えられるのか、といった疑問がある。
* 「humanist」という考え方で、人の役割を UX の中でより明確にしたい。Cowork や Copilot、Autopilot、Teams にいる他の人に、権限について明示的に尋ねて、明確な答えを得られるようにすべき、と述べた。
* 自分はビジュアルデザイン出身（以前はクリエイティブディレクター）だが、いまはデザイナーもコードでモデルを直接扱いながら、この課題を解こうとしている。まだ解決したとは言えない、とのことです。

### 5.5 Chat、Cowork、Autopilot、Copilot の使い分け

Srini 氏が、ユーザーはどう使い分けを考えるべきか、それとも体験の中でいずれ意識されなくなるのか、と Steve 氏に尋ねました。

Steve 氏の説明は次のとおりです。

* 現状は、Chat、Cowork、Autopilot、Code といったタブがあり、**選択肢を持たせる設計**になっている。これが最終的な姿ではなく、時間とともにいくつかは統合される。前日のキーノートでの Jacob 氏らのデモや、前日夕方の Copilot のセッションで、Chat と Cowork を統合する方向性が見えているはずだ、と話した。
* 自分は Cowork の最初のプロトタイプを作ったが、顧客と話して、ユーザーに「Chat と Cowork のどちらに送るか。片方はライセンス内で、もう片方はクレジットを消費する」と考えさせてはいけない、と実感した。そのため、財務の運用モデルを UX で説明する、というデザイン課題もある。
* Autopilot は Copilot の左レール（left rail）に移った。そこに載せる基準は議論を重ねており、貴重なスペースだ。
* 社内で **スマートルーター**をテストしている。例えば「会議を要約して」なら、ライセンス内で安価または無料の Chat で足りる。「第 4 四半期の売上の決算処理を手伝って」なら、Dynamics ERP や SAP などのプラグイン接続が必要で、時間もかかる。ルーターがそれを判断し、ユーザーがコストを計算しなくてよいようにする狙いです。
* 一日中ロックインして使うパワーユーザー（Excel や PowerPoint、Word を並べて見るリッチなキャンバスが欲しい）と、外出先で Teams の Autopilot にチャットして委任する場面は異なる。技術的にはユースケースに重なりがあるが、そのように考えている。
* この理由で、Cowork と Autopilot のユーザーリサーチチームを 1 つに統合した。将来的には Autopilot が Cowork をツールとして使えるようにもなる。概念は、学びながら単純化していく、とのことです。

Mike 氏は、自分が実践している暫定策を紹介しました。まず Chat でプロンプトを試し、できないと言われたら、「Cowork 向けに最適化したプロンプトを作って」と Chat に頼みます。それを Cowork に貼ると、よく動き、コストも下がるそうです。スマートルーターが入るまでのつなぎとして、トークンを効率よく使う方法として社内の人にも教えているとのことです。

Srini 氏は、Frontier では、Chat で始めると自動的に検知して、Cowork への切り替えを提案する動きがあると補足しました。いまは Home で Chat と Cowork が同じインターフェースに載っています。

### 5.6 プラグイン

Srini 氏は、GitHub に約 150 の業種別プラグインを公開したと紹介しました。約 1,700 件の顧客との詳細な会話とフィードバックに基づくもので、金融サービス、製造、ヘルスケアなどの業種が対象です。予算、勘定、決算といった業務も含まれます。リンクは LinkedIn に投稿したとのことです。

### 5.7 Microsoft のエコシステムと経済性（Martin 氏）

Srini 氏は、Ericsson が複数のプラットフォームを使っていることを踏まえ、Microsoft のどこが有効か、30,000 ユーザー分のライセンスがあると聞いていると尋ねました。

Martin 氏は、Copilot と Microsoft エコシステムの利点を、**ネイティブな統合と ID の組み合わせ**と答えました。ID（Entra）、データ、DLP、Purview、Work IQ などが組み合わさり、強力なエコシステムになり、扱いやすいとのことです。一方で、Ericsson は最初から AI について**複数プラットフォーム戦略**を取っており、ソフトウェアもコストも多様です。従業員 85,000 人という規模で、管理者やコントローラーの構造がある中で、どう管理するかが課題になります。

そこで会社として、**AI の消費（変動コスト）は、利益が生まれる場所、つまり利用者やメーカーに帰属させる**という決定をしました。具体的には、ソフトウェア料金、ライセンス費用、利用しているストレージなどを集める強力な Power Apps を作り、そこに AI の消費も取り込もうとしています。従業員は自分のフットプリントを、マネージャーはチームの消費を、コントローラーや事業部門は自分たちの消費を見られるようにする考えです。前日の朝のキーノートで発表された Agent 365 には、トークンノミクス（tokenomics）や支出の管理の兆しがあり、続きを楽しみにしていると述べています。このエージェントや行動が採算に合うかを理解する必要があるからです。

Srini 氏は、Agent 365 の一部として発表されたビジネス分析は、クレジットやトークンの消費にとどまらず、ビジネス成果を見られるものだと補足しました。さらに、OpenAI や Anthropic など他のプラットフォームの利用状況も含めたクロスプラットフォームのレポートになるかが重要で、今後に期待しているとのことです。

### 5.8 ビジネスシナリオの選び方: BMS の "rewiring"

Srini 氏が、何から始め、最重要の課題やアウトカム駆動のシナリオをどう決めたかを聞くと、Mike 氏は次のように答えました。

**3 つのタワー**: 同チームの AI は 3 つに分けて考えている。

1. 分子の発見や創薬といった、会社の方向を変えうる研究主導の AI
2. 構造化された商業・研究開発などの領域で動くビジネスの AI
3. それ以外の、日々働くナレッジワーカー

**rewiring**: BMS では "rewiring" というプロセスを回している。フロンティア企業とは、AI をただ上に載せるのではなく、現行プロセスを解体して、「それは必要か。全ステップが必要か。AI を前提にするとどうあるべきか」を問う会社だという考え方である。ライフサイエンスは SOP 駆動で規制が多く、10 年同じことを続けてきた、文書化されたプロセスが多い。そこで「承認はすべて必要か」「このステップは人がやる必要があるか」を検討し、自動化している。

**始め方**: 最初は、人が価値を実感できる「シンプルなこと」から始める（"simple" と言うが簡単ではない、と補足）。価値が見えると、人が次の段階へ押し上げる。そのうえで、フラッグシップ型の集中した AI プロジェクト（スプリント形式）にも取り組んでいる。

**コスト**: 現時点では、使ったトークン数にはそれほど注力しておらず、「ビジネス価値は何か」を見ている。将来は必ずトークンも見て、支出を調整する、としています。

Srini 氏は、Microsoft 社内でも同様の考え方を "recode" と呼んでおり、自分もビジネスプロセスの recode という言い方をする、と紹介しました。たとえとして、蒸気機関の時代の大きなモーターを挙げています。電気が登場すると、大きなモーターを使い続けるのではなく、小さなモーターを必要な場所の近くに置けるようになった、という話です（発話が途切れ気味で、細部は聞き取りにくい箇所です）。

### 5.9 エージェントを作る前に、ワークフローを設計する（Steve 氏）

Srini 氏は、エージェントを作るのは誰でもできる簡単な部分で、むしろワークフローと成果をどう設計するかが難しい、と述べて Steve 氏に水を向けました。

Steve 氏の回答は次のとおりです。

* Mike 氏の「AI を載せるだけでなく考え直す」には賛成で、3、4 年前の別の会社では、右側にチャットボットを付ければ終わり、という段階だった。いまは、**ワークフローをエンドツーエンドで再構想する**のが最初の仕事。ホワイトボードに書き出して、その写真を Copilot Studio に渡す、というやり方もできる。
* 顧客から、どのユースケースを選び、どのワークフローがどのツールで動くべきか、ワークフォースをどう訓練するかという悩みをよく聞く。
* Cowork のユースケースを調べると、複雑なプロセスでも、多くは**決定的（deterministic）**なものだと分かる。その場合は Autopilot や Cowork が不要なこともある。そこで、それを Copilot Studio にフィードバックし、組織のワークフローの一部を、決定的な形に落とし込めるようにしている。金融サービスのような規制のある業界では、エージェントのワークフローの一部が完全にマッピングされている必要があるからだ。最初は確率的（stochastic）でもよいが、そのあとはレール上に載せたい、という考えである。
* 設計パートナーシップとして、ユーザーリサーチャーを顧客の現場に送ることがあり、John Deere では「トラクターに触って、ワークフローを知ってきて」と送り出した。チームは、営業、財務、運用にわたるアイデアを持ち帰ったという。

Srini 氏は、この会話の要点を次のようにまとめました。同じプロセスを同じやり方で速くするのではなく、プロセス全体を再構想する。20% の改善だけでなく、80% も取りに行ける、という趣旨です。

さらに、一部の顧客から聞いた方法として、従業員のワークフローを Teams で録画する（または横で見て記録する）やり方を紹介しました。物理的でもデジタルでも、ワークフロー全体を記録してデジタル化します。それを Copilot Studio などのエージェント作成に渡して、「18 のステップを 4 つ程度に圧縮して考え直して」と頼むと、そのとおりにやってくれる、という話でした。書き出す必要はなく、記録するだけでよいとのことです。

### 5.10 ガードレールとガバナンス（Martin 氏）

会場に質問を開く前に、Martin 氏は 7 年間の Power Platform の経験を振り返りました。Power Platform の強みは、ガードレールを提供し、「境界のある箱」を与えることです。箱の中ではビジネスが自由にイノベーションを起こせます。同社には 5 万人のメーカーがおり、いま同じ考え方を Copilot、エージェント、Cowork に広げている、と述べています。厳格なガードレールとガバナンスと、ビジネスのイノベーターやドメイン専門家に材料を渡すことの組み合わせが非常によい、という考えです。

> 注意：Martin 氏が挙げたメーカー数は、冒頭では 15,000 人、ここでは 50,000 人（"50,000 makers"）と聞こえます。音声認識の都合か、数え方の違いかは、発表からは確認できません。

### 5.11 Q&A

会場には 3 か所のマイクが用意され、5 つの質問がありました。

**Q1. 個人の生産性中心から、エンタープライズへどうスケールするか（Allegion の Lalit 氏）**
これまでの Power Platform の経験を踏まえ、現在は個人の生産性に偏っている会社が、どうやって全社に広げるか、という質問です（質問文の一部は聞き取れません）。Mike 氏は、BMS でも同じ状況だったと答えました。市民開発者が作ったエージェントが 25,000 ありました。次の手順を勧めています。

1. まず**インベントリ**を作る。何があるかを把握する。
2. 各エージェントが何をするのかの短い説明を、所有者とともに集める。
3. 共通点を探す。どの部署も同じようなエージェントを作っている（例として PM の仕事）。
4. 共通するものを**エンタープライズのエージェントに引き上げる**。繰り返し使われるから。

「パイロットは関心を証明し、反復可能性が製品を証明する」という言い方もしています。Srini 氏は、公開されているエージェントテンプレートやプラグインを確認して、カスタマイズしながら試すのが早い、と付け加えました。

**Q2. 従量課金の予算をどう立て、CFO にどう説明するか（フランスの製薬会社の方）**
Cowork、Studio のマルチエージェント、Autopilot はいずれも従量課金で、プロンプト 1 つで 100 ドルかかるという話が平然と語られるが、数千ドルにもなり得る、という懸念が示されました。「コストが読めないのに、CFO にどう説明するか」という質問です。Srini 氏は、FinOps で予算を管理できると答えました。例えば、グループや個人ごとに「月 50 ドル分のトークン」というクレジットの上限を設けられます。同氏は「自分たちのベンダー組織の一部でも実施している」と述べています（どの組織かは文面から確定できません）。上限に達するとそこで止まります。事前に周知して最適化を促し、利用者や管理者は残りの量をダッシュボードで確認できる、とのことです。

Martin 氏は、これを補足しました。まだ誰も完全には解決していない。ガードレールとガバナンスは、大きな組織が一歩を踏み出すための手段になる。ただし、働き方の再定義が必要な場合もある。例えば 10 人の開発者のチームが AI を使えば支出は増える。あるいは、3 人の開発者が大量に消費して 5〜7 人分のコストになるとしても、結果として得になる場合がある。これは前例がないので、謙虚に、互いに学び、実験して自分たちの道を見つけよう、と述べました。

**Q3. 業務のワークフローを、現場からどう引き出すか（オランダの銀行の Vesti 氏）**
プライベートバンカーが多く、価値のある場所を知っているのは現場だが、IT 側は 5 人のチームで、全員に聞いて回れない、という質問です。Srini 氏は、誰かの作業を録画またはスナップショットとして取り、本人に説明させなくても見て分かるようにする方法を挙げました。続いて、BMS 側の回答がありました（トランスクリプト上は Martin 氏のラベルが付いていますが、内容は BMS の話で、Mike 氏の発言と思われます）。

* 「ワークフローを現場から引き出す」のではなく、「**現場とワークフローで協力する**」と考える。わずかな違いだが、現場との会話は大きく変わる。
* 答えを持っている顔で入るのではなく、課題を聞き、どこで助けられるかを聞く。
* BMS には、現場から出た「チャンピオン」のネットワークがあり、AI と可能性を話し合う。彼らは同僚に「IT と組んで解決策を作ろう」と声をかける。
* 現場には、ワークフローを取り上げられることへの恐れがある。パートナーになることで、完全にではないが、不安はやわらぐ。

Mike 氏も、人は敏感で、ワークフローを抜き出そうとした途端に文化的な側面が出てくると加えています。

**Q4. エージェントを 1 つに集約して、オーケストレーションさせるべきか（会場の質問者）**
全社に無数のエージェントがあるので、1 つのエージェントに集約して単一のインターフェースにするのはよいか、という質問です。

Srini 氏の回答は、現在と将来に分かれていました。

* 現在は、Atlassian のエージェントや SAP のエージェント、Joule などを呼ぶには、明示的に @mention する必要がある。
* 将来は、コンテキストと意味を理解して、「この帳簿の突合をして」と言えば SAP Finance から取ってくる、といったことが可能になる。
* それまでの代替として、Cowork の**プラグイン**があり、独自のプラグインやスキルを複数追加できる。質問者の考えているオーケストレーションに近い。

Steve 氏は、ユーザーリサーチでもよく聞く話だとして、金融サービスの人が、メインのオーケストレーター 1 つと、5 つのサブエージェントを作っている例を挙げました。スーパーエージェントではコンテキストやメモリが汚染されるから、というよりも、人間が「このエージェントはこの話題用」と明確に区切りたい、という理由が多いそうです。プロジェクト管理用、チーフ・オブ・スタッフ用、営業プロセス用など、別々に持つ例が挙がりました。Copilot Studio では、複数をまとめるスーパーエージェントも作れます（決定的なものも、そうでないものもある）。結局は、ワークフローのどれだけを一貫性のために中央集権にするかで決まる、という考えです。複雑なビジネスプロセスなら、決定的なエージェントを作って大規模に繰り返せるようにし、個人にはある程度の選択肢も与えます。単一の答えがあればよいが、そうではないので、必要に応じて対応できるようにしたい、と述べています。

**Q5. チャンピオンはボランティアか、専任か。昇格したエージェントは誰が作り、所有するか（Gilead Sciences の Nick 氏）**
Mike 氏の回答は次のとおりです。

* チャンピオンは**混合**。ボランティアで、通常は事業部門のリーダーが推薦する。1 年間、一定の時間をトレーニングなどに割くことを約束する。
* エージェントは、**インテークプロセス**を通して優先順位を付ける。**ハブ・アンド・スポーク**モデルで、事業部門（または事業部門の IT）が自分で作りたい場合は、ハブがガードレールを提供する。パートナーが欲しければ共同で作る。専門外なら、ハブ側が引き受ける。
* チャンピオンは指名され、同意する必要がある。1 年のサイクルで、その期間は確保できる。

## 6. デモ・手順

このセッションでは、画面を使ったデモは行われていません（登壇者の経験談と対話が中心です）。Srini 氏が、自身の Autopilot が作るダッシュボードを顧客にも見せている、と語る場面はありますが、このセッション内で実演されたものではありません。

手順として語られた内容を、参考に 2 つ整理します。

**エージェント乱立への対処（Mike 氏）**

1. エージェントのインベントリを作る。
2. 各エージェントの短い説明と所有者を集める。
3. 共通するものを見つける。
4. 共通するものを、エンタープライズのエージェントに引き上げる。

**既存の業務を作り直す方法（Steve 氏と Srini 氏のアイデア）**

1. ワークフローをエンドツーエンドでホワイトボードに書き出す（その写真を Copilot Studio に渡す方法もある）。
2. あるいは、従業員の作業を Teams で録画するなどして記録する。
3. それを Copilot Studio などエージェントの作成に渡し、ステップを圧縮して考え直すよう頼む（例: 18 ステップを 4 ステップ程度に）。

## 7. 注意点・発表者の気付き

* **AI は権限のあるデータを探し当てる**: オーバーシェアされたファイルは、AI によってすぐ見つかる。AI を広げる前に、SharePoint の共有、分類、異動した人のグループ所属を見直す必要がある（Mike 氏）。完全には防げないので、パイロットで小さな問題を見つけながら進める。
* **ユーザーに判断を押し付けない**: 重要かどうか、誰がアクセスできるかの判断をユーザーに任せる設計は負担が大きい（Steve 氏）。また、Chat と Cowork の違いでコストが変わる点を、ユーザーに計算させないようにしたい。
* **コストは未解決の領域**: 「誰も完全には解決していない」（Martin 氏）。まず上限（例: 月 50 ドル分のトークン）と可視化から始め、価値を見ながら調整する。
* **「簡単に」始めるのは簡単ではない**: Mike 氏は、価値が伝わりやすいシンプルなものから始めるよう勧めつつ、「シンプルとは言ったが簡単ではない」と述べている。
* **ワークフローは、現場から奪わない**: 現場にはワークフローを取り上げられることへの恐れがあり、IT は答えを持ち込むより、課題を聞き、パートナーとして進める。
* **使い分けの難しさ**: Steve 氏は、現状は選択肢を持たせる設計になっており、Chat、Cowork、Autopilot の使い分けをユーザーに考えさせている点を課題として挙げ、今後は統合・単純化していくと述べている。
* **集約の正解は 1 つではない**: エージェントを 1 つにまとめるか分けるかは、ビジネスごとに答えが違う。

## 9. まとめ

このパネルは、パイロットで終わらせず、ビジネス価値に変えるための考え方を、顧客の経験から伝えたものです。要点は次の 4 つです。

1. **データを先に整える。** AI は権限のあるものを見つけるので、分類と共有の見直しが先決です（BMS）。
2. **AI を載せるのではなく、ワークフローを作り直す。** 同じプロセスを速くして 20% の改善を得るのではなく、プロセス全体を再構想して 80% まで狙う、というのが Srini 氏のまとめです。
3. **コストと価値は、ガードレールの中で学びながら進める。** 上限の設定と可視化から始め、価値を確認して調整します。
4. **スケールは共通点の発見と現場との協働から。** エージェントのインベントリから共通のものを引き上げ、チャンピオンのネットワークとハブ・アンド・スポークで進めます。

Microsoft 側は、Chat、Cowork、Autopilot の統合や、スマートルーターによるコストの自動判断といった、使い分けの負担を減らす方向で取り組んでいると説明しました。
