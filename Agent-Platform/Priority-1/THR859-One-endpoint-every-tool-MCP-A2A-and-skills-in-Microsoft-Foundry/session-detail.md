# THR859 One endpoint, every tool: MCP, A2A, and skills in Microsoft Foundry

## 1. はじめに

このセッションは、Microsoft Foundry の **Foundry toolboxes** を紹介する約 25 分のシアターセッションです。複数のエージェントが、それぞれ同じ MCP サーバーや API を個別に設定・接続し直す、という手間の解消が出発点です。toolbox は、ツールの集まりを 1 つの MCP エンドポイントとして公開します。

発表では、toolbox の考え方、ツール検索（tool search）によるコンテキスト削減、Azure policy によるガバナンス、モニタリングダッシュボードが説明されました。録画ビデオの再生と、Foundry ポータルを実際に操作する場面もあります。後半は Q&A で、skills や A2A の扱い、Azure SQL の接続が取り上げられました。

## 4. 発表者が伝えたいメッセージ

中心となる考えは、**ツール、スキル、それに付随する指示を「箱（toolbox）」にまとめ、その箱を複数のエージェントにつなぐ**ことです。箱は MCP エンドポイントとして公開されるため、MCP を使える場所ならどこでも利用できます。ツールの定義や認証設定、ガバナンスは箱の側で一元的に管理します。

発表者は、特に次のような状況で toolbox が向いていると説明しています。

- 多数のツールを持っている
- ツールやスキルのセットを多数のエージェントで共有している
- それらを統制したい

また、toolbox は Foundry 上で作成・管理しますが、利用するエージェントは Foundry 上で動いている必要はありません。MCP を扱えるエージェントハーネスであれば、どこで動いていても使えます。

## 5. 発表内容の詳細

### 5.1 toolbox とは

toolbox は、ツールのコレクションを 1 つの箱にまとめたものです。その箱を、ツールを使いたいさまざまなエージェントに接続します。発表で挙げられた特徴は次の 3 点です。

| 特徴 | 説明 |
|---|---|
| MCP エンドポイント | 箱の中のツールはすべて 1 つの MCP エンドポイントの背後に置かれ、MCP が動くあらゆる場所で使える |
| tool search | エージェントが toolbox 内のツールを検索して見つけられる |
| コントロールプレーンとガバナンス | ツールと toolbox を管理でき、Azure policy で組織としての制限をかけられる |

たとえば「社内の誰もエージェントから Web にアクセスしてはならないので、Web search を禁止する」といった、組織全体のブロックを Azure policy で設定できる、という例が挙げられました。

### 5.2 toolbox に入れられるツール

Ignite 時点で toolbox に入れられるものとして、次が紹介されました。

- Web search。発表では「web IQ で動いている」と説明されました（以前からあった Web search を載せ替えたもので、toolbox の Web search ツールを使えば web IQ になる、という趣旨です）。
- A2A のツール。あわせて、VS Code にインストールするための体験も用意されている、と説明されました。
- skills と shells に関するプレビューのツール。prompt agent を作り、skills を複数のエージェントで共有できます。共有先は prompt 型、hosted 型、managed 型のエージェントのほか、ローカルのノート PC 上で動くコーディングエージェントも含まれます。
- MCP サーバー、OpenAPI で定義された API、Work IQ、Browser Automation（聞こえた表記は "Browser Automate"）など。5.8 のデモでカタログに表示されたものです。

発表者の言葉では、狙いは「エージェントの能力（agentic capabilities）をキュレーションして整理する」ことです。分析、レビュー、ブリーフィングのようなタスク固有の専門性をエージェントに与えるとき、指示をあちこちにコピーして回すのではなく、スキルと、そのスキルに必要なツールと指示を 1 つの論理的なグループ（toolbox）にまとめ、そのグループを別のエージェントに接続します。

### 5.3 tool search とトークン削減

7 個のツールを toolbox に入れて MCP エンドポイントにし、エージェントから使う分には、仕組みはわかりやすいものです。ところが toolbox に 1,000 個のツールが入っていて、エージェントがタスクごとにその一部しか使わない場合は問題が起きます。毎回すべてのツール定義がコンテキストウィンドウに入り、肥大化するためです。

そこでオプションを選ぶと、Foundry の MCP エンドポイントは「tool search」という 1 つのツールだけを見せるようになります。エージェントはそのツールで、利用可能なツール全体から必要な定義だけを検索して取り出します。

発表で示された例では、toolbox に約 1,000 個のツールが入っている状況で、**トークンが 36 倍少なく**なりました。エージェントが必要なツール定義だけを取り出してモデルに渡し、1,000 個すべてを同時にコンテキストに入れなかったためです。

> 注意：この効果はシナリオ次第です。発表者は「your mileage will vary（効果はシナリオによって変わる）」と明言し、36 倍は示された例での数値であると説明しています。

### 5.4 Foundry 以外のエージェントから使う

toolbox の作成は Foundry ポータルで行い、ツールの追加や各種設定もそこで行います。ただし、その toolbox を使うエージェントが Foundry エージェントである必要はありません。結局のところ MCP エンドポイントだからです。

- VS Code に追加する組み込みの体験があり、VS Code のコーディングエージェントから toolbox を使えます。ローカルの VS Code Copilot ハーネスに、ガバナンスされた企業向けの機能を追加できるという説明です。
- 自分で作っているエージェントにも追加できます。デプロイ先が Foundry でも、自前のサンドボックスでも構いません。
- 条件は、選んだエージェントハーネスが MCP を利用できることです。

ただし認証方式は選ぶ必要があります。環境によっては認証の仕組みがまったく異なる場合があり、その場合はトークンなどを使うことになるかもしれない、と述べられています。それでも利用自体はできるという説明でした。

### 5.5 ガバナンス（パブリックプレビュー）

プレビューで注目の機能が、ツールに対するガバナンス層です。エージェントを作るチームが増えるほど、「エージェントごとに、適切なツールだけを使っているか、会社が使わせたくないツールを使っていないか」をチェックリストで確認する方法は、スケールしません。

特に大きな組織から、「あるツール X を組織全体でブロックし、使用はケースバイケースでのみ許可したい」という要望があったと説明されています。こうした機能を toolbox に組み込み、**エージェントが使えるツールを Azure policy で制御し、toolbox 層を通して呼び出すときに、そのポリシーのパターンを実行時に強制する**仕組みです。この機能はパブリックプレビューで、今すぐ試せます。

資料については、スライドが参加者に提供される場合、各スライドのテキストに Learn ドキュメントなどへのリンクがあるとのことです。発表者によれば、ここで話した内容に非公開のものはなく、検索すれば見つかります。

### 5.6 モニタリングダッシュボード

**toolbox monitoring dashboard** では、次のことが確認できます。

- toolbox でどのようなツール呼び出しが行われているか
- toolbox がどのように、誰に使われているか
- どのポリシーが適用されているか
- 失敗の有無

toolbox を 1 つ作ってツールを入れ、7 つのエージェントが同じ toolbox 経由でツールを使っている場合でも、このダッシュボードで、そのすべてのツールの利用と実行の状況を toolbox 単位で一元的に見られます。

### 5.7 toolbox の分け方の方針

toolbox の切り分けについて、発表者は次のように説明しています。

- **エージェントごとに toolbox を作る**と、共有という目的が薄れてしまいます。ただし発表者は「それでも構わないかもしれないが、おそらく共有することになるだろう」という言い方をしています。
- 発表者のチームが最も良いと考えるのは、**capability（能力）ベース**の分け方です。例えば業務ドメインの単位で、事業の特定部分の API を操作するためのツールと、その API の使い方を伝えるスキル（ある程度の grounding にもなる）をまとめます。この環境で動くエージェントには、その toolbox をアタッチします。
- 一方で、すべてを入れた巨大な toolbox を 1 つ作り、全員が同じ toolbox を使う方法もあり、おおよそ動くとのことです。切り分け方はいくつもあります。

どの方法でも、前述のダッシュボードで一元的な見通しが得られます。

#### ライブデモ：Foundry ポータルで toolbox を見る

続いて発表者は、画面の表示を切り替えてから、Foundry ポータルの tools ページを見せました。語られた順は次のとおりです。

1. Foundry ポータルの tools ページを開く。ここには、この日の別のセッション（エージェントの実行方法に関するもの）で使ったデモ用の **daily briefing agent** がある。このエージェントは、天気予報や当日の予定など、さまざまな場所のデータソースを集め、矛盾を見つける。例として、「今日はクレーンを使う予定だが、天気予報では風が強く、風が強いときはクレーンを使えない」といったケースが挙げられた。
2. その背後にあるのが **daily briefing toolbox** で、2 つの MCP エンドポイントが設定されている。これらのエンドポイントへの認証は toolbox 内で設定されており、エージェントは Foundry 上で動いているため、MCP と統合認証で toolbox と通信する。
3. 画面にはサンプルコードも表示されている。agent framework で toolbox を使う場合や、LangGraph（聞こえた表記は "Landgraph"、音声認識の都合で表記が確定できません）、Copilot SDK で使う場合の書き方を示すもの。
4. 重要なのは、toolbox のエンドポイントが **リモート MCP エンドポイント**であること。リモート MCP エンドポイントを使えるものなら何でも、この 2 つの MCP を含む toolbox を使える。
5. add をクリックすると、スキルの追加や、ツールの追加ができる。ツールのカタログから、Work IQ や Browser Automation などを選んで追加できる。OpenAPI（Swagger）のツールも含まれている。
6. ここは実際に操作せず、手順を口頭で説明した部分です。既存 API 用の OpenAPI ドキュメントを OpenAPI ツールに設定すると、エージェントがその API の各エンドポイントを呼び出せるツールが toolbox 内にできる。そこに、API の用途や業務ドメインの知識（どう使うべきか）を説明する **skill** を同じ toolbox に追加する。
7. こうして、API とスキルが 1 つのまとまりになる。自社でその API を使いたい人は、toolbox に接続するだけでよい。使うエージェントハーネスや、エージェントが動く場所は関係ない。
8. OpenAPI ドキュメントの中に同じ API のバージョンが大量にあっても（発表者は冗談交じりに 4,570 と述べました）、tool search でコンテキストウィンドウを削減できるので、無関係なものにトークンを使わずに済む。
9. モニタリング情報を見せる。デモ準備の間の、1 つのエージェントだけの利用状況で、数百回のツール呼び出しがあった。エラーは一度もなく、ほとんど同じ incident ツールを何度も検索しただけなので、やや退屈な内容だと発表者は述べている。
10. toolbox の作成は簡単で、名前を付け、必要なら toolbox 固有のガードレールを設定し、ツールを追加するだけ。Foundry の UI で作成・管理できるが、使うエージェントを Foundry で動かす必要はない。
11. 質問を受けて A2A を見せる。A2A でほかのエージェントに接続でき、agent card のエンドポイントに接続すると、グルーピングやガバナンスなど、toolbox の機能がそこにも適用される。リモート A2A エンドポイントを toolbox 経由で使いたい場合の方法で、もちろん、あるエージェントに直接 A2A で接続することもできる。
12. toolbox には、A2A エンドポイント、MCP エンドポイント、スキルをいずれも追加できる。カスタムのものは柔軟で、加えて、さまざまなデータソースに接続し、認証も処理するためのカタログがある。発表者は Twilio の認証方式を知らないと述べつつ、画面を確認して "built-in" と読み上げ、続けて別の項目について "unauthenticated" と読み上げました（どの項目かは音声からは特定できません）。

### 5.9 Q&A

**Q. エージェント間（agent to agent）の連携は、どう追跡できますか。パラメータを渡すとき、呼び出し元は呼び出された側から呼び返されますか。**

回答は "it depends" でした。まず、すべての基盤は OTel であり、OTel のトレースでエンドツーエンドの全体像が見えると説明しています。あらゆるものが OTel と、AI 向けの Semantic Conventions を使う必要がある、という考えです。

プロトコル面での動きは場合によって異なります。発表では、次のように説明されました。

- **skills**: toolbox にスキルがある場合、スキルは MCP エンドポイントの **resource** になる。そのため、エージェントハーネスが MCP に接続し、スキルを取得（ダウンロード）する方法を知っている必要がある。
- **A2A**: A2A の情報も同様に、MCP のプリミティブを使ってエージェントハーネスと共有する。
- **OAuth の同意（consent）**: toolbox には、もう 1 つ標準とは異なる点がある。MCP には同意をフローさせる仕組みがないため、同意が必要なときは MCP エラーが返り、そのエラーに、ユーザーに提示すべき consent URL が含まれる。このエラーをキャッチして URL を取り出し、ユーザーに渡す処理が必要になる。ユーザーがその URL を開くと同意フローが進み、接続先エンドポイントへの OBO が許可される。この仕組みは toolbox でサポートされている。

発表者は、汎用の MCP エンドポイント上でこれらを実現する詳細は場合によって異なるが、そうせざるを得ない、と述べています。

**Q. すでに Work IQ や Business Central など、別の場所にスキルがある場合、どうやってここに取り込めますか。**

発表者の理解では、**現時点では、ほかの場所からスキルを取り込む provider model や connector のような仕組みはありません**。スキルは toolbox に追加し直す必要があります。スキルの「カタログ」はあるものの、それはスキルそのもののカタログで、スキルを取得できる場所のカタログではありません。発表者はチームに確認する、と答えています。

**Q. Azure SQL のようなデータソースも入れられますか。**

入れられます。toolbox は任意の MCP をサポートしており、Azure SQL MCP にはカタログのエントリがあります。「X を入れられるか」という問いの答えは、**MCP であれば入れられる**、つまり MCP があるものなら何でも動く、ということです。カタログのなかには MCP と表示されない、より個別対応のもの（画面上の SQL Server のもの）もあります。一般に、必要なデータコネクタは使えるはずで、望むものは何でも動かせるようにしたい、という趣旨の発言がありました。コネクタの多くは Logic Apps や Power Apps のコネクタと同じもので、それらが統合されているとのことです。

## 6. デモ・手順

デモはあります。5.8 に、語られた順で整理しました。録画ビデオ（ホスト型エージェントのデプロイ）と、Foundry ポータルのライブ操作の 2 つです。ビデオは早送りされており、画面の細部や操作手順の全体は音声から確認できません。

toolbox の作成手順としては、発表で次のように語られています（個別のボタン名は音声からは分かりません）。

1. Foundry ポータルで toolbox を作る（名前を付け、必要ならガードレールを設定する）。
2. ツールを追加する。カタログから選ぶか、MCP、OpenAPI、A2A などを追加する。スキルも追加できる。
3. 表示されるリモート MCP エンドポイントを、使いたいエージェントに設定する。

## 7. 注意点・発表者の気付き

- tool search の効果（36 倍少ないトークン）は例示された数値で、効果はシナリオによって変わると発表者は注意しています。
- 認証方式は選ぶ必要があります。認証の仕組みが大きく異なる環境ではトークンなどが必要になる場合があると述べられました。
- toolbox を使うエージェントハーネスは、MCP に接続してスキルを resource として取得する方法を知っている必要があります。
- OAuth の同意が必要になると MCP エラーが返ります。エラーに含まれる consent URL をユーザーに提示する処理を、エージェント側で実装する必要があります。
- 他の場所にあるスキルを取り込む仕組みは現時点ではなく、toolbox に追加し直す必要があります。
- ツールの利用制限（Azure policy によるガバナンス）はパブリックプレビューです。skills と shells のツールもプレビューとして紹介されています。
- agent ごとに toolbox を作ると共有の意義が薄れるため、capability ベースで分けることを推奨しています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 複数のエージェントが同じツール接続・設定を繰り返さなくてよい（箱を接続するだけ）。
- tool search により、ツールが多数あってもコンテキストの肥大化を抑えられる（例では約 1,000 個のツールで 36 倍少ないトークン）。
- Azure policy によるガバナンスを実行時に強制でき、組織全体でのツールのブロックなどができる。
- モニタリングダッシュボードで、ツール呼び出し、利用者、適用ポリシー、失敗を一元的に確認できる。
- Foundry 以外（VS Code のコーディングエージェントや自作のエージェントなど）からも、MCP を使えるなら利用できる。

> 補足：顧客事例の紹介は、このセッションではありませんでした。

## 9. まとめ

Foundry toolboxes は、MCP サーバー、OpenAPI のサービス、A2A エージェント、組み込みツール、スキルを 1 つの MCP エンドポイントの背後にまとめ、複数のエージェントで共有する仕組みです。tool search による token 削減、Azure policy によるガバナンス（パブリックプレビュー）、モニタリングダッシュボードが組み合わさります。

利用側は、MCP を使えるエージェントハーネスであれば Foundry の外でもかまいません。一方で、スキルの取り込み元となる別の場所との連携は現時点では未対応であり、OAuth の同意をエラーとして処理する必要がある、といった制約も語られました。toolbox は capability（業務ドメイン）単位で作り、複数のエージェントで共有する使い方が推奨されています。
