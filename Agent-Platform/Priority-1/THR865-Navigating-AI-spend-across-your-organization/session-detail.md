# THR865 Navigating AI spend across your organization

## 1. はじめに

このセッションは、組織内で増える AI の利用コストを、どう計画し、制御し、価値に結びつけるかを、Agent 365 と Microsoft Copilot の画面で見せる約 25 分のシアターセッションです。コストの可視化と制御を、エンドユーザー、IT 管理者、ビジネスリーダーという 3 つの立場から順にたどっていきます。

デモでは、エンドユーザーが Copilot の利用量を確認する画面、IT 管理者が spending policy（支出ポリシー）を作ってモデルや上限を決め、権限を委任する画面、そしてビジネスリーダーが支出・価値・ポリシーを管理する「Agent 365 business analytics」アプリが示されます。最後に、ライセンスに関する案内もあります。

## 3. 何に関する発表か

冒頭で、これまでの基調講演でも使われたスライドとして、**observability は信頼の土台**だという整理が示されます。

- 何が動いているか：Agent 365 が答える。
- 何をしているか、何にアクセスしてよいか：セキュリティが答える。
- いくらかかっていて、どんな ROI が得られているか：**このセッションの主題**。

Agent 365 の提供価値は、管理、ガバナンス、セキュリティ、ビジネス価値です。ビジネス価値とは、コストを把握し、エコシステム全体のコストを見渡し、投入したコストに見合う ROI が出ているかを知ることだと説明されています。そのために、まず計画と制御をして、次に価値と ROI を見ながら最適化する、という順序を示しています。

対象は、Anthropic や OpenAI のように接続して使うサードパーティのプラットフォームと、Copilot Studio、Foundry、Cowork、Copilot、chat などの Microsoft のサービスです。すべての AI サービスについて、IT とビジネスリーダーの両方が、コスト、価値、最適化の方法を見られることを目指しています。

役割ごとの提供内容は次のとおりです。

| 役割 | 提供するもの |
| --- | --- |
| エンドユーザー | どこで、何に使っているかが分かり、自分で制御できる |
| メーカー・開発者 | デプロイ前にコストを見ながら、エージェントを作り、デプロイし、最適化できる |
| IT 管理者・ビジネスリーダー | 適切なガードレール、制御、監視 |

今回のデモは、エンドユーザー、IT 管理者、ビジネスリーダーの 3 つで、メーカーのデモは行いません。

## 4. 発表者が伝えたいメッセージ

メッセージは、最後にまとめられた 3 つのパターンです。

1. 制御するだけでなく、**AI への投資をビジネス価値に変える**ことを考える。
2. それを、Microsoft か、接続された Microsoft 以外かを問わず、すべての AI サーフェスに対して行う。
3. 組織内のすべての役割に対して行う。

また、使用量ベースの課金サービスは、**IT がガードレールとコスト制御を先に設定しないと、エンドユーザーは使えない**ようにしている、という設計方針が語られています。

## 5. 発表内容の詳細

### 5.1 エンドユーザーの視点：Copilot の利用量メーター

Kevin が、製薬会社で大きな製品ローンチに取り組んでいるユーザー（名前は「Effie」と聞こえますが、音声認識の都合で表記が確定できません）の立場で、Microsoft Copilot の画面を見せます。このユーザーは、サプライヤー A と B のどちらが製品ローンチに必要な供給能力を提供できるかを評価しています。

- 複雑なタスクなので、Cowork が適しています。Cowork を選ぶと、右上に小さな**メーター**（ambient meter）が出ます。これで、copilot credits を使っていること、残りがどれだけあるかが分かります。
- Cowork は Work IQ をたどって、組織内の情報から A と B の比較をチャットに返します。さらに、アドバイザーや経営層と共有できる文書（Word）を生成し、サプライヤー A の採択通知と、見送りの通知も作ります。
- クレジット使用量の表示は、30% だったものが 21% に変わりました。Cowork を使っている間に、メーターが**ライブで**変わります。
- 「view usage」から、今のセッションだけでなく過去の履歴を見られ、日ごとに、Cowork の各タスクがどれだけのクレジットを使ったかまで掘り下げられます。
- Cowork に限らず、Copilot アプリには他の使用量ベースの課金サービスも入り、autopilot や code にも、同じ可視化を取り込んでいると説明されています。ユーザーは Copilot の中で 1 つのビューで確認できます。

### 5.2 IT 管理者の視点：spending policy とモデルテンプレート

次に Reshma が、admin center の IT の画面を見せます。IT 管理者はふつう、configuration から始めます。最も重要な構成要素が **spending policy** です。

デモでは、先ほどのエンドユーザー（「FA」と聞こえます）が、engineering policy に属しています。スコープは medical engineering チーム全体です。

1. policy の詳細で、Cowork にアクセスできること、policy とユーザーごとの上限、IT 管理者が通知を受けるタイミングを見られる。
2. このグループには**モデルテンプレート**が割り当てられている。現在は cost optimized で、使えるモデルは「Sonnet、Terra、Solfast」と聞こえる 3 つのみ（モデル名は音声認識の都合で表記が確定できません）。
3. この team の research は Cowork で大きな価値を出しており、事業部門のオーナーからもそう聞いている。その research は、新しく立ち上げる pharma field sales agent の元になるため、より新しいモデルを使えるようにしたい。
4. 新しいモデルテンプレートを作り、名前は「fast models」（入力時に打ち間違いがあったと言っています）。選んだモデルは「Opus Fast」「Fable」「Sole Fast」と聞こえます（表記は同じく確定できません）。作成して保存する。
5. medical engineering の全員が、このテンプレートのモデルを使えるようになる。ユーザーが選べるモデルだけでなく、Cowork が自動で使う **auto** が選べるモデルにも反映される。

### 5.3 consumption ビューと Copilot Studio の environment

IT 側の次の操作は、consumption ビューです。ここには、**policies、users and groups、services and agents、use cases、models** という切り口があり、コストと価値について、エコシステムのあらゆる断面を見られると説明されています。

- 「services and agents」で、組織内で消費されているサービスを一覧する。
- 今回は agent ビューで、**environment** を開く。これは新しく提供したビューで、Copilot Studio の environment と、その中で動いているエージェントと、消費しているコストを見られる（登壇者が会場に、Copilot Studio の environment を使っているか尋ねると、数人が手を挙げています）。
- admin center では、environment 単位のポリシーも作れる。デモでは、sales agent の開発開始時に、sales operation 向けのポリシーを設定済み。

### 5.4 エージェントを本番に上げるための spending policy

デモでは、sales agent の開発プロジェクトが進んでおり、本番に移せるかを判断する場面になります。

1. pharma fields agent の画面を開く。cost タブで、このエージェントのユーザー数が増えている。
2. 今月のコストはこれまでに「190」（単位は聞き取れません）。一方で、投入したコストの **2 倍の価値**がすでに出ている。価値の計算方法はあとで説明される。
3. コストは右肩上がりで、現在の上限のままでは月末までに枯渇し、エージェントが業務上重要なことをできなくなるおそれがある。
4. そこで、このエージェント専用の spending policy を作る。

spending policy では、2 種類の設定を選べます。

| 種類 | 内容 |
| --- | --- |
| identity-based policy | リソースを使う**人**に上限を設け、その人に課金する |
| resource-based policy | **リソースそのもの**に上限を設ける |

今回は、使う人にかかわらずエージェント自体に上限を置きたいので、resource-based です。HR エージェントのように、誰が使うかや各人の上限の消費は重要でなく、エージェント自体に上限を置きたいケースに近い、と説明されています。

5. エージェントとして pharma field sales agent を選び、ポリシー名は「pharma sales」、エージェントレベルのポリシーにする。
6. 現在の支出上限は月 200 で、足りなくなっている。上限を 5,000、いや 4,000 に変更する（本番にするときに、使う人にかかわらずエージェントに置きたい予算）。
7. アラートも設定できる。通知先のメールアドレスを入れ、3,000 に達したときに通知する設定にした。
8. 次に、**部門別チャージバック（departmental chargeback）**を選べる。すべての spending policy に組み込まれていて、ポリシーごとに変えることも、デフォルトを使うこともできる。デモでは、デフォルト（発話は「Caldova production」。表記は音声認識の都合で確定できません）を使わず、この部門用に Azure で設定した medical engineering のサブスクリプションを使う、という選択を説明した。
9. spending policy を作成する。

### 5.5 policy group による権限の委任

エージェントが本番に上がると、IT だけでは管理しきれなくなります。そこで、管理を**事業部門のリーダーに委任**します。これは基調講演でもデモされたと述べられています。

1. configuration で、policy ではなく **policy group** を作る。group は、spending policy を入れる容器で、委任する単位になる。IT に委任することも、事業部門のオーナーに委任することもできる。
2. 名前は「R&D operations」。委任先は、Morgan と聞こえる人物（「Morgan Alice」「Morgan Ellis」と聞こえます）で、**delegator** にする。
3. ロールは 3 つ：**delegator、writer、reader**。delegator は、グループを作ってさらに委任できる。writer は policy を作れる。reader という役割も挙げられましたが、権限の中身は語られていません。
4. 事業部門全体に上限を置く。ここでは **350K**。
5. 委任された側にサブスクリプションを選ばせる設定にする。エージェントは、すべて許可する。
6. モデルは「balance」と「cost optimize」のテンプレートだけを与える。
7. このグループを追加する。

### 5.6 ビジネスリーダーの視点：Agent 365 business analytics

ここから Kevin が、ビジネスリーダー（Morgan Ellis と名乗る、R&D operations のリーダー）の立場で、基調講演で紹介された新しい **Agent 365 business analytics アプリ**を見せます。ビジネスリーダー専用のアプリで、支出を把握し、得られている価値を見て、より大きな効果に向けて最適化するためのものです。

**支出の把握**

- 画面は組織全体ではなく、自分の部門（R&D operations）に絞られている。組織の階層は、**Entra**（音声認識では「Entre」と聞こえます）から取り込むか、独自の階層をインポートでき、実際の組織の構成を反映できる。
- 部門の支出は **$228,000**。
- 下にスクロールすると、**主なコスト要因（top cost drivers）**が分かる。この例では、Copilot Cowork が支出の **39%** を占める。
- クリックすると、サービス別（Cowork、GitHub Copilot、他のエージェントなど）の内訳が見られる。さらに、Anthropic や OpenAI のモデル別の粒度もあり、「Opus 5.5」や Sonnet からの使用量などを確認できる（モデル名の表記は音声認識の都合で確定できません）。
- サービスとモデルを組み合わせて、例えば Copilot Cowork が Opus 5.5 や GPT 5.5 など複数のモデルを選んでいることも分かる。登壇者は、これを auto の効果、つまり場面に合ったモデルを選ぶ動きだと説明しています。

**価値の把握（use cases）**

- 価値を計算する前に、AI の支出がどこに向かっているかを理解することが先、という考え方です。
- Copilot Cowork の **14,400 セッション**が、**6,000 以上のユースケース**の分類（taxonomy）に対応付けられる。この分類は、Department of Labor と Bureau of Labor Statistics を根拠にしている。
- research and discovery のような大きな粒度から、statistical analysis plan のような個別のユースケースまで見られ、それぞれについて、コストと、得られている価値が並べて表示される。
- 価値は、そのタスクの内容から推定され、かかる時間を計算し、その貢献を金額として表す。
- 価値の計算は組織ごとに違うので、**タスクにかかる時間と、そのタスクのコスト**の入力をカスタマイズできる。

**spending policies の操作**

- Reshma が Morgan Ellis に委任した、月 **350,000** の予算を、ビジネスリーダーが理解するだけでなく、行動に移せる。
- 作成された R&D operations の policy group の下に、**子の policy** を自分で作り、350K の予算の中で、好きなように割り振れる。IT が設定したガードレールと自由度の範囲内で行う。
- デモ画面には、discovery research、clinical operations、medical engineering がある。ポリシーを選んで編集でき、サービスの選択、上限の変更など、IT の側と同じ流れで操作できるが、IT が最初に設定した制約の範囲内に限られる。

### 5.7 ライセンスの案内

最後の案内は次のとおりです。

- Microsoft の AI サービスを管理するためのここまでの機能は、**すでに Microsoft Cloud のサブスクリプションに含まれています**。
- Snowflake や Amazon Bedrock のような、接続されたサードパーティのプラットフォームを管理するには、**Agent 365 または Microsoft 365 E7 のライセンス**が必要です。

## 6. デモ・手順

このセッションでは、画面を使ったデモが行われています。手順は 5 章に、語られた順で書いたとおりです。全体の流れは次のとおりです。

1. エンドユーザー（Microsoft Copilot、Cowork）：メーターと使用量の履歴を確認する。
2. IT 管理者（admin center）：spending policy でモデルテンプレートを変更し、consumption ビューで Copilot Studio の environment とエージェントのコストを見て、エージェント用の resource-based policy を作り、policy group を作って委任する。
3. ビジネスリーダー（Agent 365 business analytics）：支出、コスト要因、use cases の価値、子 policy を確認する。

録音は音声のみのため、画面の細部（ボタンの名称やレイアウト）は確認できません。

## 7. 注意点・発表者の気付き

- **IT が先に設定しないと、エンドユーザーは使用量ベースのサービスを使えません。** 上限やガードレールがない状態で使い始められないようにしています。
- **月次の上限は、成長するエージェントでは足りなくなります。** デモの pharma fields agent は、現在の上限のままでは月末までに枯渇する見込みで、業務上重要な処理が止まるおそれがありました（ポリシー作成画面には現在の上限として月 200 と表示されていました）。
- **価値の計算は組織ごとに違います。** そのため、かかる時間とタスクのコストを調整できるようにしてあります。
- **委任された側は、IT が設定した制約の範囲内でしか動けません。**
- **ライセンスに注意**：Microsoft のサービスの管理は Microsoft Cloud のサブスクリプションに含まれるが、サードパーティのプラットフォームの管理には Agent 365 または Microsoft 365 E7 が必要です。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- エンドユーザーは、メーターで使用状況を見ながら、自分で使い方を調整できます。
- IT は、モデルや上限を policy で一元的に制御し、エージェントごとの上限、アラート、部門別チャージバックを設定できます。
- IT だけでは管理しきれなくなったエージェントの管理を、事業部門のリーダーに委任でき、リーダーは割り当てられた予算の範囲内で子の policy を作れます。
- ビジネスリーダーは、支出、主なコスト要因、use case ごとのコストと価値を 1 つのアプリで確認でき、ROI を見ながら最適化できます。

> 補足：発表では、顧客事例や、導入による定量的な成果は紹介されていません。デモで示された数値（2 倍の価値、39% など）は、デモの画面上の例です。

## 9. まとめ

AI の支出は、観測し、計画して制御し、価値を見て最適化するという順序で扱います。Agent 365 は、エンドユーザーには利用量のメーター、IT 管理者には spending policy とモデルテンプレート、ビジネスリーダーには business analytics アプリを提供して、コストと価値を役割ごとに見える化します。Microsoft のサービスの管理は Microsoft Cloud のサブスクリプションに含まれ、サードパーティのプラットフォームの管理には Agent 365 または Microsoft 365 E7 が必要です。
