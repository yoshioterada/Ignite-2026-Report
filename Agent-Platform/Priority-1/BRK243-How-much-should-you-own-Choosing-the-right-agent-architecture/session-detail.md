# BRK243 How much should you own? Choosing the right agent architecture

## 1. はじめに

このセッションは、Microsoft Foundry でエージェントを作るときに「どこまで自分で持つか（own するか）」をどう決めるかを、4 つのデモで順に見せていく構成です。範囲を絞って Microsoft 側にハーネスを任せる **prompt agent / Microsoft Copilot harness のエージェント**から、自分のコードとフレームワークを持ち込む **hosted agent**、さらに Microsoft 365 上でチームメンバーのように常時動く **autopilot**（発表では "custom autopilot" とも）へと、デモが進むほど自由度と能力が広がります。

題材は、製薬会社の新工場の建設現場向けエージェントです。現場の安全確認、毎朝のブリーフィング、Teams への公開、そして Hermes agent を使った自律エージェントへと発展します。結論として登壇者が示す選び方は「**左から右へ、動くところまで進める**」というシンプルなものです。

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**エージェントの作り方は 1 つではなく、必要な制御の度合いで選ぶ**という考え方です。単純な用途なら Foundry にハーネスを運用させ、手軽さと低い総所有コストを得ます。厳密に決まった手順や特殊なハーネスが必要なら、コードを自分で持ち込みます。公式の概要では、Foundry は ID、認可、ガバナンス、ツール、公開をどの型でも適用し、プラットフォーム上の行き止まり（platform dead end）を作らずに選べるとされています。デモでは、managed、hosted、autopilot の順に、エージェントがより強力になっていく様子が示されました。

## 5. 発表内容の詳細

### 5.1 Foundry でのエージェントのライフサイクル

Glenn 氏は、エージェントを作って動かすまでの層を次のように説明しています。

- **構築**：好きな手段で作ってよい。手で書いてもコーディングエージェントを使ってもよく、フレームワーク、ハーネス、モデルも問わない。
- **デプロイ**：Foundry の agent service に、どこで作ったエージェントでもデプロイできる。Glenn 氏が最も深く関わる部分。
- **グラウンディング**：Microsoft の「IQ」と名のつく各種サービスを使う。
- **ツールとメモリ**：自分のツールや、memory、dreaming などで、エージェントが時間をかけて記憶できるようにする。
- **観測と最適化**：最近は最適化の機能も多く出ている。
- **届ける**：Teams、Copilot アプリ、業務アプリ、メールなど、必要な場所にエージェントを届ける。バックグラウンドで、イベントが起きるたびにエージェントを動かす使い方もある。

### 5.2 Foundry の 2 つのカテゴリ: managed と hosted

今日の範囲は、エージェントの構築とデプロイの方法の一部です。Foundry のエージェントは 2 つのカテゴリに分けられます。

| カテゴリ | 説明 |
| --- | --- |
| Managed（prompt agents など） | ハーネスを Foundry が制御・実行・ホストする。パッチや更新は不要。ユーザーは設定、ツール、プロンプト、skills を提供するだけ。総所有コストは低い。 |
| Hosted | ユーザーが用意したハーネス（LangGraph、Microsoft Agent Framework など、どんな形のエージェントでも）を Foundry がホストする。セッションごとに sandbox が自動で与えられ、セッション同士が分離される。エージェント向けのインフラ作業を Foundry が行う。 |

今日のデモは「新しい **Microsoft Copilot harness** のエージェント型」「hosted agent」「voice agent」の 3 種類です。範囲が狭く統制された、1 つの仕事をうまくこなすエージェントから始め、デモごとに能力と開放度を広げていく、と予告されました。

### 5.3 デモシナリオ

製薬会社の新しいサイト（建設現場）を建てる、という Ignite 全体で使われているデモのシナリオに沿っています。2 つのエージェントが登場します。

- **Site Safety Agent**：現場の安全ルールに関する質問に答える、範囲の狭いグラウンディング済みアシスタント。危険な行動があった場合は安全インシデントレポートの提出もできる。責任はこれだけ。
- **Daily Briefing Agent**：マネージャーが毎日チームに行うブリーフィングを作る。今日の作業計画、その作業に応じて強調すべき安全ルール、天気の影響（例として、35 マイル毎時の風でクレーンを使う計画があるとき、使用禁止の安全ルールがないか）、市のイベントなど、複数のソースからデータを集める。このエージェントは **Site Safety Agent を呼び出す**。つまり、より狭い領域のエージェントの上に立つオーケストレーターになる。

詳細は 6 章のデモで扱います。

### 5.4 3 つの型の使い分け

デモ 2 の後、Glenn 氏は 3 つの型を左から右へ並べて整理しました。

| 型 | 特徴（発表での説明） |
| --- | --- |
| Prompt agents | 現在の GA。Foundry の UI で作る。ハーネスは、Responses API を動かすための最小限の実装。多くのシナリオで高速で単純、ツールも接続できる。安い（トークン費用のみで、ハーネスを動かす計算資源の費用は転嫁されない）。一方、ゴールを追う力は弱く、sub-agent などはない。 |
| Microsoft Copilot harness | パブリックプレビュー。prompt agent の代わりに使え、Copilot の機能（sub-agent、Web アクセスなど）が使える。 |
| Hosted agents | コードを持ち込む。LangGraph、Microsoft Agent Framework など。 |

使い分けの原則は、**左から右へ、動くまで進める**ことです。左は安く、速く、簡単なので、それで動けば心配は要りません。能力や柔軟性が足りなくなったら右に進みます。

注意点として、左の 2 つ（prompt agent と harness agent）は**ワークフローではありません**。決まった手順を厳密に制御したい場合（LangGraph や Microsoft Agent Framework を使うなど）は、より決定論的な制御のために hosted agent が必要です。能力の高いモデルを使えるなら、手順を skill に書いてモデルに任せる方法でも動くかもしれず、その場合は evals で信頼できるか確かめる、という選択肢もあるとのことです。コードで書けば確実に動きます。

また、hosted agent はワークフロー型だけのものではなく、**どんなエージェントのハーネスでもデプロイできる**とも強調されました。例として、Hermes のような長時間動くエージェントは、カスタムのハーネスを使うため hosted agent になる、と述べています。

### 5.5 Teams への公開（デモ 3 の背景）

Amanda 氏は、Foundry なら数クリックで Microsoft Teams に公開できると述べています。別の登壇者は、hosted agent では複数のプロトコルから選べ、**Teams の activity protocol をエージェントまで実装**すると、Teams の機能を細かく制御できると補足しました。これはすべて任意で、1 クリックの既定の UI と体験もあり、改善を続けるとのことです。個別の UI が欲しい場合は、Teams SDK や M365 agent SDK を使い、部品は事前に用意されていて、コードをカスタマイズするだけだと説明されました。

登壇者は、エージェントの作成がやさしくなった今、業務への統合、大規模なガバナンス、必要なときに仕事の流れの中でシグナルを受け取ることが重要で、それが「有能なエージェントを毎日頼るものにする最後の 1 マイル」になると述べています。

### 5.6 Autopilot（custom autopilot / 自律エージェント）

Amanda 氏は、Microsoft 365 Copilot アプリの autopilot を知っているかもしれないとしたうえで、Foundry では、**Microsoft 365 アカウントを持つ自律エージェント**（"custom autopilot" と呼ぶこともあるが、名称は検討中）を作れると説明しました。

- すべての Foundry エージェントは agent identity を持つ。
- しかし Teams のグループチャットなど、多人数で共同作業する場所では、作成者自身の認証情報を使うと、チャットの他のメンバーが見られない情報まで露出するおそれがある。これが、この新しい型が作られた主な理由の 1 つ。
- Microsoft 365 上の仕事は共同作業が多いため、チームの一員として扱う必要があり、**専用のメールや OneDrive など M365 リソース**を持つ。M365 グループに参加し、SharePoint サイトにもアクセスでき、人間の同僚ができることは（制限の範囲内で）何でもできる。

従来の自律エージェントの限界についての説明もありました。例えば Azure のインフラを管理する運用エージェントを作る場合、agent identity に本番のリソースグループへの Azure RBAC を割り当てれば、コンテナーの起動・停止やライブアラートの取得など、自律的に動かせます。しかし、リソースへのアクセスを Foundry 側で与えるため、自分のチームに固定されてしまい、組織内のすべてのチームに ops agent を配ることができません。

autopilot では、Foundry で作るのは**ブループリント（テンプレート）**です。例えば Azure DevOps ツールを呼ぶ能力は与えますが、実際の Azure DevOps プロジェクトへのアクセスは与えません。それは後の段階で付与されます。そのため、Foundry で hosted agent を 1 つ作れば、組織全体で使えます（"agent as a service"）。

> 補足：発表では、Hermes agent を Foundry の autopilot としてデプロイできるようになったことが「今日（starting today）の発表」と紹介されています。提供範囲などの詳細は発表では語られていません。

Amanda 氏は、Hermes を「最も人気のあるオープンソースのエージェント」と呼び、これを自社に取り込んでも、一般のユーザーと同じようにガバナンスを効かせられると説明しました。Hermes は自社のインフラ上で動くため、VNet の持ち込みや CMK も使えます。エージェントはガバナンスされた agent identity を持ち、「強力なエージェントを使いつつ、IT チームも安心できる」両立が得られる、という位置づけです。

### 5.7 管理者の承認とガバナンス

Amanda 氏は、開発者として Hermes を使う流れと、管理者としての承認の流れを説明しました。

**開発者の流れ**

1. リポジトリを clone する（用意されたイメージがある）。
2. インフラを用意する（多くの場合は IT 管理者が行う）。
3. Foundry のプロジェクトに追加してもらう。
4. そのイメージで hosted agent のバージョンを作る。
5. Microsoft Admin Center に承認を申請する。

**管理者の流れ（Microsoft Admin Center の Agent 365 の画面）**

- Request タブに申請が表示される。数字が付いているものが、autopilot（アカウント付きのエージェント）で、通常のエージェントではないことを示す。実体はブループリントで、数字が付くのは agent as a service を作っているため。
- 管理者はストアに公開できる。誰がこの種のエージェントを「雇って作れる」かを選べる。20 個も持つ類のものではなく、永続的なエージェントのため、作成できる人を管理者が限定できる。
- 先ほどの Teams 公開で見た「自分だけに公開」のような**承認の回避はできない**。自分専用でも、この承認を通る必要がある。強力な種類のエージェントには監督が必要だからだと説明されました。
- ライセンスを選ぶ。既定で、Purview の policies と Defender の policies が付く（もう 1 つ "enter policies" と聞こえますが、音声認識の都合で表記が確定できません）。その上に自分で conditional access policy を設定することもできる。ディレクトリから隠すこともできる。人間のユーザーに適用できる制御は、エージェントのユーザーにも適用できるとのことです。
- 管理者が permission scope への同意（consent）を与える。
- 公開されると、A365 の registry に表示される。管理者は、ブループリントの metadata と properties（Foundry のリソース、プロジェクト、アクティビティ）に加えて、インスタンスレベルの metadata（誰が管理しているか、インスタンス固有の指示など）を見られる。ブロックや削除もできる。

### 5.8 Hermes agent と Nous Research 氏との対話

Hermes agent をプロダクトとして紹介するのが、ゲストの Jeffrey 氏（Nous Research の共同創業者・CTO と自己紹介）です。

**Hermes agent の特徴**：最大の差別化要素は、継続的に自己改善する仕組みです。「使うほど良くなる」と表現しており、使っている間にバックグラウンドで、本来は自分で書く必要のある skills を自然に作り続けます。例えば「Glenn がこう言っていた」と言えば、過去のやり取りから内容を把握するといった形で、個人に合わせて最適化されます。skills ファイルに加えて、決定論的であるべきものには、決定論的なコードも生成します。つまり、無限の時間軸を持つ長時間稼働の自律エージェントで、使い方に合わせたスキルを獲得し続けます。

**企業向けにする難しさ**：個人化されたエージェント同士でも、共有すべき知識はある一方で、個人固有で他者と共有したくない情報もあるため、ガバナンスが問題になります。成熟したガバナンスの基盤が必要で、自分たちですべては作りたくなかった。Entra、M365、Foundry、Teams など、すでに本番で使われているものがあり、それを活用できるかが論点で、これが Foundry を選んだ判断点だったとのことです。

**Foundry を選んだ理由**：Nous Research は 100% オープンソースで、データの所有と出所（provenance）を重視しています。今後は、AI の IP をどれだけ組織内に取り込めるかが強みになる、と述べています。Foundry には、信頼できるストーリーに必要なプリミティブがあり、必要なスケールも備えています。1 人の従業員が 10 個のエージェントを持つと、Microsoft 規模以上では数十万から数百万の同時稼働になる、という見立てで、**ガバナンスと実績のあるスケール**が理由だとしています。

**司会側の登壇者の補足**：最初に Nous 側と話したとき、Nous はアイデンティティ、ユーザーアカウント、メールを自前で組み立てていたが、スケールしないと話していた、と振り返っています。また、長時間動く自律エージェントをエンタープライズに入れるには、新しいパラダイムを作らず、**エージェントを別の従業員のように扱う**のが最も簡単だったと述べています。権限やリソースのプロビジョニングも従業員と同じ考え方で、これが Foundry の仕組みによく合うという説明です。

**始め方は 2 つ**：(1) Foundry で hosted agent を使い、Teams にデプロイする。(2) Nous Research 自身のポータル（トランスクリプトでは "portal at newsresearch.com" と聞こえますが、音声認識の都合で表記が確定できません）のエンタープライズ製品をセルフデプロイする。後者も sandbox 上で動く（"Appicator sandboxes" と聞こえますが、確定できません）ため、結局は Foundry を使うことになる、と説明されています。

## 6. デモ・手順

このセッションには**ライブデモが 4 つ**あります。音声のナレーションで語られた範囲のみを書きます（画面の細部は音声からは確認できません）。

### 6.1 デモ 1: Managed の Site Safety Agent と voice agent（Glenn 氏）

Foundry のポータルで作った、managed harness の Microsoft Copilot harness エージェントです。コードを書かずに設定します（コード体験もあるが後で見せると説明）。

1. モデルを選び、エージェントの動作の指示（instructions）を設定している。
2. **Foundry IQ のナレッジベース**でグラウンディングしている。すべての安全文書が入っていて、エージェントが必要な知識を常に持てるようにする仕組みが裏で動いている。
3. インシデントレポートの提出方法を教える **skill** を持つ。
4. 外部のインシデントシステムにつながる **MCP 接続**を持つ。
5. 組み込みツールも並ぶが、必要がないため使っていない。Copilot harness の標準の振る舞いを継承するため、sub-agent や Web アクセスが必要ならチェックボックスで有効にできる。GitHub Copilot の CLI やアプリのコーディングエージェントと同様に動くが、コーディング用途に限らない、とのことです。
6. Foundry の「explore and play」の UI で、「風速 100 mph のときクレーンを使えるか」と質問した。エージェントはナレッジベースを分析し、使えないと回答し、161 km/h と換算して「クレーンは絶対に使わないように」と答えた。
7. 新しいチャットで「インシデントレポートを提出したい」と入力し、エージェントが提出の手伝いを始めるところを見せた（実運用では別の場所に公開して使うとの説明）。

続いて、**voice agent** です。Lakshmi 氏が、このセッションの直前に、Site Safety Agent に音声の「頭」を付けて作りました。Glenn 氏は、このボタンを押すのは初めてだと話しています。

1. 「安全インシデントを提出したい」と話しかけると、音声のエージェントは「報告の受付を開き、詳細を集めて一緒に確認する」「正しい分類を使うために報告基準を確認する」と応答した。
2. 実際の作業は別のエージェント（Site Safety Agent）が行い、voice agent はそれを包むラッパーである。
3. Glenn 氏は、「Lakshmi が現場を歩き回り、保護具をつけない。何度も帰宅させた。けが人はいないが何とかしないといけない」という内容を報告として話した。
4. 音声エージェントが止まらなくなったため、手動で終了した。

登壇者は、この voice agent に電話番号を割り当てて匿名でインシデントを受け付ける、独自アプリや既存アプリに埋め込む、といった使い方を挙げています。声のクローンや、アバターの追加もできると述べています。

最後に Glenn 氏は、managed エージェントでは、ハーネスを設定すれば Foundry が実行すること、sandbox が必要なときは sandbox でセッションが動くこと、パッチや更新を気にしなくてよいことをまとめました。

### 6.2 デモ 2: Hosted の Daily Briefing Agent（Lakshmi 氏）

Lakshmi 氏は「コードを見せて」という開発者の立場で、Daily Briefing Agent を hosted agent として作りました。要件は、決まった手順を厳密に守り、**ハルシネーションしないこと**です。skill に書く方法もあるが、それには手順を忠実に守る高度なモデルが必要で、安いモデルでは危ういため、Agent Framework でカスタムエージェント（ワークフローエージェント）を書いたと説明しました。LangGraph でも構わないとのことです。

1. コードは一般的なエージェントのコードで、受信リクエストを処理する部分と、ワークフローのステップを定義する部分がある。ステップはそのとおりの順に実行される。
2. 具体的なステップは、(a) ブリーフィング用のデータソースを読む、(b) サニティチェックを行う（想定どおりか、想定外か）、(c) **Site Safety Agent を呼び出す**、(d) ブリーフィングを書く、の順である。
3. Site Safety Agent を作り直さなかったのは、チームが事業の領域ごとにエージェントを所有する、という顧客の傾向に合うためで、別のチームのエージェントを再作成せずに呼べばよい、と説明した。
4. **VS Code の Foundry 用ツールキット**を事前にインストールし、サーバーをローカル（localhost の 8080）で動かして、playground を使った。
5. ブリーフィングを生成した。最初に出たのは翌日分のテンプレートだったため、今日の分で再実行した。
6. クラウドにデプロイする前にローカルで検証でき、ワークフローが進むにつれてトレースが生成されるのが見える。
7. デプロイは、そこからワンクリックで行うか、AZD と標準の Bicep テンプレートや Terraform で行える。
8. 生成結果の例として、市が門の 1 つに向かう道路を閉鎖したが、その門に今日は配送が来る、という矛盾が見つかった。登壇者は、通常のコードですべてのケースを事前に書くのは難しい種類の問題だと説明している。
9. クラウドにデプロイすると同じ playground の体験が使える。すべてのメッセージ・会話について、**詳細なウォーターフォールトレース**が得られる。例えば「なぜ 23 秒かかったか」を調べられ、各ツール呼び出しやワークフローのステップを確認できる。ワークフローで定義した各 edge は、グラフの別のノードとして記録される。
10. トレースでは、LLM を呼んでブリーフィングを書いたこと、Site Safety Agent を呼び出して応答を受け取り、さらに追加情報で再度呼び出したことが確認できた。この追加の呼び出しは、Glenn 氏が示した矛盾を実行時に解消したものだと説明されている。つまり、エージェント的な能力を持ちながら、決まったステップを守る、というのが hosted agent で得られることです。

続いて、2 つのエージェントのコードを並べて比較しました。

| 項目 | Managed agent（Site Safety） | Hosted agent（Daily Briefing） |
| --- | --- | --- |
| リポジトリの中身 | インシデントレポート提出の skills と、エージェントの姿を定義する `agents.yaml` | 通常のアプリケーションのコード |
| デプロイ | 通常の CI/CD フローや AZD の CLI で行う | 同じようにシステムに組み込んで行う |

登壇者は、このリポジトリ全体が **AZD で up できる**（`azd up` / `azd down`）と述べています。Foundry のプロジェクトを、その中にあるものすべてと一緒にデプロイするとのことです。

### 6.3 デモ 3: Teams への公開（Amanda 氏）

Amanda 氏は、Lakshmi 氏のエージェントと同一のものに、自分で UI を載せたものを使いました。公開済みですが、流れを見せるため複数のコピーを作っています。

1. hosted agent の画面から、公開先のオプションのうち **Teams** を選ぶ。
2. エンドユーザーに表示される詳細を入力する。説明（「daily brief を送る」など）と名前を入れる。
3. スコープには 2 つの選択肢があり、今回は「自分だけ」を選んだ。組織全体にも公開できるが、その場合は管理者のレビューと承認を待つ必要があるため、デモでは行わなかった。自分だけなら、すぐに表示される。
4. Publish をクリックする。Teams と Copilot で利用可能になり、Teams と Copilot を直接開く入口が表示される。
5. サインインされ、公開したエージェントが表示される。Amanda 氏は、独自の UI を作ってあるため Teams 上で見せた。
6. 「brief tomorrow」と入力するか、「tomorrow's briefing」をクリックして、翌日のブリーフィングを出した。スキルを通して、振る舞いを見せるよう調整している。
7. 同じブリーフィングが新しい UI で描画される。その日の予報、全体のブリーフィングへの戻り、作業計画などを見られる。外出先のスマートフォンでも使える。
8. 画面の赤字は、例外が見つかった箇所である。天気の出力の赤は、その時間帯は天気のため予定の作業ができないことを示している。例外を、人が気づきやすい形で前面に出している。

### 6.4 デモ 4: Hermes autopilot（Amanda 氏）

Amanda 氏は、Hermes の self-hosted の例で個人用の autopilot を作ってあります。前述の開発者・管理者の流れ（5.7）を説明し、Agent 365 の Admin Center の画面でブループリントの登録と管理者の見え方を示しました。

1. Admin Center（Agent 365）の Request タブで、数字の付いた autopilot の申請を示した。自分のものは公開・設定済みだと説明した。
2. 公開の画面で、ストアへの公開、作成者の選択、ライセンス、既定のポリシー、ディレクトリから隠す設定、consent の画面を説明した。デモ中の別のエージェントは、承認が通らなかったが問題ないと話した。
3. A365 の registry で、自分の Hermes エージェントが表示されていること、クリックしてブループリントの metadata、properties、インスタンスレベルの metadata が見られることを示した。
4. Foundry 上の Hermes agent を使い、自律で動くため力を見せるのは難しいので、基本機能だけを示すと述べた。使っているテナントは、機能ごとに展開前に検証するテスト用テナント（画面の "Office of Amanda MSIT"）と説明した。
5. すでに依頼していたリキャップに続き、**そのリキャップを Word ドキュメントにする**よう依頼した。作業中に説明を続けたため、結果の画面についての発話はない。
6. ルーティンのスケジュール設定ができる。2 つ目のアカウント（Amanda 2）で見ると、エージェントがすでに会議を設定していた（Amanda 1 のアカウントから Amanda 2 のアカウントへ）。
7. 受信トレイのトリアージを行い、Amanda 氏が転送することに決めた Teams のメッセージも、スケジュールに沿って処理する。**能動的に動く**と説明された。

## 7. 注意点・発表者の気付き

- **左の型の限界**：prompt agent と Copilot harness のエージェントはワークフローではないため、手順の厳密な制御には hosted agent が必要。
- **skill に手順を書く方法**はモデルの能力に依存する。安いモデルでは確信が持てないため、Lakshmi 氏はコードで書いた。使う場合は evals で信頼できるか確かめる。
- **autopilot は管理者承認が必須**で、自分専用でも省略できない。数が多くなる型ではなく、作れる人を絞る前提。
- **グループチャットでは作成者の認証情報を使えない**。他のメンバーが見られない情報を露出するおそれがあるため、autopilot は専用の M365 リソースを持つ。
- **Teams を組織全体に公開すると管理者の承認待ち**になる。
- ライブデモは、Glenn 氏の voice agent が止まらなくなる、Teams の画面で「下に表示されるはず」の内容が出ない、といった小さな場面がありました。Autopilot のデモについては、自律で動くものは偽物に見えず力を見せるのが難しい、と述べられています。
- Hermes の企業利用では、個人に固有の情報は共有したくない一方、共有すべき知識もあるため、ガバナンスが課題とされました。
- **Hermes を autopilot としてデプロイする機能**は、発表時点で「今日から」と紹介された新しいもので、提供範囲は発表では説明されていません。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

- **Managed（prompt agent / Copilot harness）**：ハーネスのパッチや更新が不要で、総所有コストが低い。prompt agent はトークン費用のみ。
- **Hosted**：自分のコードとフレームワークを使え、決定論的な制御と、エージェント的な柔軟さを両立できる。セッションごとの sandbox による分離と、トレース、AZD などでのデプロイが得られる。
- **ローカルでの検証**：VS Code の toolkit で、クラウドに出す前にトレース付きで end-to-end の確認ができる。
- **Teams / Copilot への公開**：数クリックで公開でき、スマートフォンからも使える。
- **Autopilot**：agent as a service として、1 つ作れば組織全体で使える。人間のユーザーと同様に Purview、Defender、conditional access などの制御を適用でき、VNet の持ち込み、CMK も使えると説明された（Hermes の例）。
- **顧客事例（Nous Research）**：自前で ID・アカウント・メールを組み立てたがスケールしなかったものを、Foundry のガバナンスと実績のあるスケールに載せられる。

## 9. まとめ

このセッションは、建設現場の安全エージェントから始めて、エージェントを段階的に強力にしながら、Foundry の複数の作り方の使い分けを示したものです。簡単な型から始め、動かなくなったら右に進むのが基本です。手順を厳密に制御したい場合や、Hermes のような独自のハーネスを使いたい場合は、hosted agent を使います。

デモでは、Teams への公開（hosted agent）や管理者の承認（autopilot）も示されました。最も進んだ autopilot では、エージェントが専用の M365 アカウントとリソースを持ち、管理者の承認と各種ポリシーのもとで、チームメンバーのように動きます。登壇者は、ごく基本的なアシスタントから、現時点で最も強力なハーネス型エージェントの 1 つまでが、すべて Foundry 上で動くとまとめています。
