## 4. 発表者が伝えたいメッセージ

全体を貫く主張は、Okazaki 氏が示した「Human Ambition、Intelligence、Trust」の 3 つです。Human Ambition では人が中心であること、Intelligence では、AI モデルがどれだけ賢くなっても自社の知識をどう蓄積して育てるかが重要であること、Trust では、AI は強力な武器である一方、暴走したときは恐ろしいので、しっかり制御して安心安全に使うことが語られました。

Intelligence の具体策として、Okazaki 氏は Microsoft IQ のプラットフォームに自社の知識を蓄積し、その上で「自分たち自身の IQ」を作ることの重要性を挙げています。Toyota の事例は、その IQ をエージェントの改善ループに生かしている例として紹介されました。

もう 1 つの軸は「エージェントを作って終わりにしない」ことです。Omori 氏は「作った後にどう評価し、改善につなげ、その改善も自動化していくか」というループが AI エージェントの世界にも入ってきたと述べ、「Microsoft は生成 AI をゆりかごから墓場まで提供している」という点を、最も伝えたかったことだと語っています。

Trust については、Agent 365 の観測・管理、エージェント自身を守る Agentic Insider 保護、エージェントで組織を守る Microsoft Perception が、1 つの流れとして整理されました。

### 5.2 キーノートの問いと 3 つの柱

Okazaki 氏は、キーノート冒頭で投げかけた 2 つの問いを振り返りました。1 つ目は「指数関数的に伸びる AI の能力をどう成果に変えるか」、2 つ目は「その能力がもたらす影響に、組織としてどう備えるか」です。

例として、AI が先行しているソフトウェア開発では、これまで開発者の主な仕事はプログラミングでしたが、いまはソフトウェア工場を作るような形に仕事の進め方が変わりつつあると説明しています。同じ変化があらゆる業務領域に起こるという前提で、人が何に取り組み、周囲の組織システムをどう再構築するかを、Microsoft として一緒に考えたいと述べました。

そのために必要な「Frontier ecosystem」の構成要素が、Human Ambition、Intelligence、Trust の 3 つです。トランスクリプトの冒頭では「Human Labor」と聞こえますが、後続の Fujii 氏の説明で Human Ambition と確認できるため、そちらに合わせています。

これらを実現する Microsoft の中心的なソリューションとして、Copilot、Microsoft IQ、Agent 365 が挙げられ、セキュリティでは Perception と、それを支える Azure インフラが紹介されました。Copilot は「仕事のための新しい OS」という考え方で設計されていると説明しています。

Copilot の進化については、4 回目の大きなアップデートが行われたと語られました（前後の聞き取りは不明瞭です）。ポイントは 3 つあり、まずチャット、仕事とアプリの作成、自律型エージェントの Autopilot、そして Office 自体まで、ばらばらだった機能を 1 つに統合しました。次に、モデルを選ぶのではなく、やりたいことを伝えれば最適なモデルが選ばれる構成です。最後に、タスクについても、素早く答えるのか、自律型エージェントとして動くのかなどを、最適なものを提案して支援します。

| IQ | 説明（発表の言い方に沿ったもの） |

| 業務ナレッジの IQ | Microsoft を中心とした業務ナレッジ。聞き取りが不明瞭で、名称は確定できません |
| Fabric IQ | 業務データを接続する（非構造データにも触れていますが、どの IQ の説明かは聞き取りが不明瞭です） |
| Foundry IQ | 非構造データを知識として活用できる形にする（聞き取りは不明瞭） |

Okazaki 氏は、Microsoft IQ はあくまで仕組みであり、その上でお客様自身の IQ をどう作るかが非常に重要だと強調しています。キーノートでは、自社の IQ を構築している顧客が多数紹介され、Judson 氏（聞き取りのまま）のキーノートでは Toyota の名前も挙がりました。

### 5.4 ゲスト講演：Toyota の AI エージェント（Maeda 氏）

Japan Session として初の試みで、Toyota Motor Corporation の Maeda 氏が登壇しました。Toyota は今回の Ignite で 3 つのセッションに登壇しており、いずれも同じストーリーです。San Francisco から Napa Valley へ向かうドライバーが、目的地でわくわくすることを目標に、1 つのエージェントに 3 つの問いを立てます。Foundry のセッションでは「エージェントの振る舞いは正しいか」、Fabric IQ では「その人に合っているか」、Web IQ では「運転中の人にどう伝わるか」です。

**Foundry：振る舞いは正しいか**

ドライバーが Napa Valley へ向かう途中で「向こうに充電スタンドはある？」と尋ねたとします。従来のナビゲーションなら近くの充電スタンドを案内しますが、これは AI でなくても同じです。ところがお客様は「着いてからの話なんだよね」と言い直します。この言い直しを学びのきっかけにする仕組みを、Toyota は構築中です。

大切な点は 3 つあります。

1. ドライバーの言葉から学ぶこと。
2. 決めるのは人であること。直し方の案は AI が出しますが、選ぶのは人です。
3. 直った結果を確かめて届けること。直っているか、ほかに悪い影響が出ていないかを確認します。

この仕組みは Microsoft と一緒に Foundry を使って作っています。

**Fabric IQ：その人に合っているか**

同じ「暑い」でも感じ方は人それぞれです。車内で暑いと言われて AI が温度を 22 度に下げたところ、本人は 24 度のまま風量を上げたかったため、手動で 24 度に戻して風量を上げた、という例が示されました。従来の音声認識では温度を下げて終わりだった場面です。Toyota はこの「やり直し」を失敗ではなく手がかりと捉えます。多くの走行データから同様の傾向（例えば日差しが強いときは、まず風量を上げる人が多い）を調べ、エンジニアが確認して承認すると、その傾向が Fabric IQ に登録され、ほかのエージェントも同様に使えます。みんなで共有するのは傾向だけで、一人ひとりの好みは本人のためだけに保持するとのことです。

**Web IQ：どうすれば伝わるか**

車内では、素早く簡潔に答えることが求められます。通常の AI は交通量などを聞かれると長く答えがちですが、この場面では 1 秒でも早く、お客様に合わせた情報を提供したいとのことです。3 つの場面が挙げられました。

1. 通行料：対向車が北へ向かっているという情報があれば、「この橋の北向きは無料です」と一言で答える。
2. 充電：Foundry IQ が取扱説明書からこの車の充電プラグの種類を調べ、Web IQ が近くの充電器を探して 1 つに絞る。
3. ランチ：Web IQ が近くの最新の店舗情報を探し、Fabric IQ がその人の好みを加味して 1 軒だけ案内する。

Maeda 氏は、デモでは 3 つの場面を見せると述べたうえで、上記の 3 つの場面を説明しました（実演の形式は音声からは分かりません）。続けて、これはまだ製品ではなく技術検証中で、現在は実際の車で試していると説明しました。3 つのセッションをつなぐのは「使って、学んで、直して、また確かめる」という流れです。現在この改善を回しているのは Toyota の社員で（音声では「資金」と聞こえる箇所があり、細部は確定できません）、これを customer zero と呼んでおり、その次がお客様です。この繰り返しで体験全体をよくしていく取り組みを、Microsoft は hill climb と呼んでいるそうです。目標として「幸せの量産」が挙げられました（直前の語は聞き取りでは "self-zero" で、音声認識の都合で確定できません）。

Okazaki 氏は、IQ を構築し、情報を活用しながら改善ループを着実に回す、優れた仕組みだと評価しています。

### 5.5 モデルの多様性とコスト

AI でできることが増える中、お客様の関心は「同じアウトプットを、より最適な AI コストで実現すること」に移っていると Okazaki 氏は述べます。その方策の 1 つが、多様なモデルのサポートです。

- Microsoft Foundry は 11,000 を超えるモデルをサポートしている。
- OpenAI とのパートナーシップのもとで、最先端のモデル（今回は 6.2 のバージョンに言及）を提供し続けている。
- Meta に関連して Muse という名前が挙がり、こうしたモデルにも手厚く対応していると述べられた（聞き取りが不明瞭で、詳細は確定できません）。
- Microsoft Build 以降よく話している MAI（Microsoft AI）が作る、Microsoft 自身のモデルも今回発表した。Mustafa 氏（Microsoft AI を率いる人物）が登壇して話した。

MAI の例として、MAI Code 2（聞き取りでは "MyCode 2"）はコーディング性能に特化したモデルで、最先端のモデルと同等のコーディング精度を、コストは半分、あるいは 10 分の 1 で実現するという話がありました。画像生成は 1 位、2 位を争う性能で、Microsoft Office 製品の中ですでに多くの人が使っていると説明されています。

もう 1 つがカスタムモデルです。自社の知識を取り込むことで、精度を高め、コストも最適化します。キーノートで紹介されたカスタムモデルの 4 事例のうち 2 つが日本の顧客（Rakuten と Woven Toyota）だったと Okazaki 氏は紹介しました。

### 5.6 日本の事例：Woven Toyota と NTT Data

エージェントは作って終わりではなく、継続的に改善するもので、お客様と一緒に進化させるという考え方が強調されました。具体的な事例が 2 つ紹介されています。

**Woven Toyota**

車載ソフトウェアの開発には Misler（聞き取りのまま。標準の名称は音声認識の都合で確定できません）という標準があり、これに準拠しているかのチェックは大変な作業で、人手で行っていた部分を AI で実現したのが従来の取り組みでした。今回の Microsoft の支援は、それをさらに進化させる部分です。最先端のモデルでも解けなかった問題があったため、先ほどのカスタムモデルを使い、GitHub に蓄積された情報と組み合わせました。その結果、従来解けなかった問題の 44% を解けるようになったとのことです。また、従来の部分は 10 分の 1 のコストで実現できているとも述べられました。

**NTT Data**

システム構築では基準に沿ったチェックが必要なため、それを自動で行う PMO エージェントを作った事例です。Microsoft と継続的な改善ループを作ることで、品質スコアが 68.6% から 83.3% に向上しました。さらに約 60% の削減効果が見込まれるとも語られましたが、何の数値かは聞き取りが不明瞭です（休憩中のビデオには、プロジェクト管理タスクの時間を約 60% 削減できる見込みという趣旨の説明があります）。

### 5.7 Agent 365、Perception、AI Transparency Initiative（概要）

Okazaki 氏は、エージェントが仕事で当たり前に使われる時代を前提に、管理の重要性を説明しました。Microsoft 社内では、すでに稼働しているエージェントの数が従業員数の 22 万人を上回っているそうです。エージェントだけでなく、使うモデルや、アクセスするデータとシステムも含め、あらゆるレイヤーで管理する必要があるという考えです。キーノートでは、Agent 365 が「エージェントのコントロールプレーンから、AI 全体のオブザーバビリティプラットフォームへ」進化するというメッセージを示しました。

Agent 365 には IT Ops、Sec Ops、Fin Ops の 3 つの機能があります。

- **IT Ops**：社内でどんな AI 資産が動いていて、誰と、どのシステムと、どのデータとつながっているかを管理できるようにします。Microsoft 以外のエージェント AI ツールも把握でき、従来は SDK を使えばできていたことが、より簡単にできるようになったのが今回のアップデートの大きな点だと説明しています。
- **Sec Ops**：不正な振る舞いを止める、切り離す、制限をかけるといった対処です。管理と制御の両立が大事だとしています。
- **Fin Ops**：どの部署でどれだけ使い、具体的な成果が何かを把握します。この要望に応えるものとして発表されたのが Agent 365 Business Analytics です。エージェント、サービス、モデル、ユーザーごとのコストを、他社のものも含めて可視化できます。さらに、ビジネス KPI と紐づけて ROI を最適化できる点が大きな進化だと述べています。

セキュリティでは、AI を使った攻撃が進化し、人の手では間に合わなくなっているという認識から、数か月前に発表された Microsoft Perception（聞き取りでは "Mark Perception" などと揺れています）が今回の Ignite で GA になったと紹介されました。Perception には Red Team Agent（攻撃のシミュレーション）、Blue Team Agent（検知した事象への対応要否の判断）、Green Team Agent（具体的な修正まで実施）があり、リスクにマシンスピードで対応できる点が特徴とのことです（詳細は 5.17 で Sato 氏が説明します）。

最後に、Satya Nadella 氏が話した AI Transparency Initiative に触れています。AI の振る舞いについて透明性を持って理解したいというニーズに応えるもので、セキュリティやインターフェースの標準を 1 社ではなく関係各社と一緒に決めて業界標準にする、という考え方です。Microsoft 自身も MAI や Foundry などの製品に早く取り込み、この取り組みにコミットすると表明しました。これも Trust の一環です。

### 5.8 Copilot のアップデート（Watanabe 氏）

Watanabe 氏は、Copilot が 4 つの軸「Chat、Cowork、Code、Autopilot」に変わり、1 つのアプリに統合されたと説明しました。トランスクリプトでは Cowork が「Kouhaku」「Kohaku」と聞こえる箇所が複数あり、文脈上は Cowork を指すように読めますが、音声認識の都合で確定できません。

**Home と自動モデル選択**

Home が GA になりました。チャットで複雑な仕事を頼むと、Cowork への切り替えを提案してくれます。また、プロンプトの内容をもとに、適切なコストで適切なモデルを選んで処理する自動モデル選択が使えます。

**Code**

専門的な開発知識がなくても、やりたいことを自然言語で伝えるだけで、Work IQ を活用してアプリやダッシュボードを作れます。作ったアプリは IT 管理者の管理のもと、文書と同じ感覚で共有できます。必要に応じてエンジニアが加わり、GitHub と連携して本格的な開発もできます。現在は Frontier preview として、Copilot クレジットを使う従量課金で提供されており、数週間以内の GA が予定されています。

**Autopilot**

ゴールを渡して仕事を任せられる、常時稼働のパーソナル AI アシスタントです。独自の ID、メールボックス、Work IQ を持ちます。デモ（6 章）では、「Ignite への出張をサポートして」というゴールだけを伝える様子が紹介されました。

Watanabe 氏が挙げたポイントは次のとおりです。出張の手間が省けるだけでなく、本人が不在でもチームの仕事が止まらず、本人は戻ってすぐに優先事項に取りかかれます。任せる範囲は組織が決め、Autopilot は専用の Entra Agent ID を持ち、組織が定めたポリシーの範囲で動作します。管理責任者も指定できます。こちらも Frontier public preview で Copilot クレジットによる従量課金、現在は主に米国で、今後拡大予定です。

**Copilot Studio の AI 同僚**

Autopilot が個人の作業を助けるのに対し、Copilot Studio ではチームや組織の業務を担う AI 同僚を作れます。エージェントは専用の ID を持ち、Teams やメールで人と協業しながら、任された仕事を自律的に進めます。12 月から Frontier Preview で利用できる予定です。

**その他のアップデート**

- **Outlook の Copilot**：メール、予定表、Teams の会議、タスクを横断して見て、見落としや優先順位を抽出します。返信の下書きや日程変更の提案まで行い、人はレビューして承認するだけです。
- **Copilot workspaces**：人とエージェントが同じ目線で同じ文脈を共有する作業の場です。エージェントが下書きし、人がレビューし、そのレビューに対して AI がさらに作成する、という協業ができます。
- **@Copilot in Teams**：Teams のチャットで @ メンションして Copilot にタスクを依頼でき、会話の内容をもとに作業を進めます。
- **成果物の直接編集**：Copilot で作った Word、Excel、PowerPoint の成果物を、Copilot の中で直接編集できます。成果物は OneDrive に保存されるため、共有先の人が Word アプリなどで編集しても、同じ変更が常に同期されます。
- **Copilot force**（聞き取りのまま。営業向けの機能と説明されています）：アプリを切り替えず、次の営業アクションを考えて、そのまま CRM の操作まで進められます。画面左下のウィジェットから取引先の確認や新規商談の登録ができ、Work IQ を含めて CRM のメールや Teams の会議から商談の状況を把握し、次にやるべきことを提案します。現在はプレビューです。

### 5.9 Agentic Business Applications と Dynamics（Yamashita 氏）

**CMR（Copilot Managed Runtime）**

Yamashita 氏は、Cowork や Code など Copilot のさまざまな画面からアプリを自由に作れるようになり、アプリ開発は開発者だけの仕事ではなくなったと述べました。一方、GitHub Copilot などのコーディングエージェントでアプリを作った人からよく聞く悩みは、作ったアプリをどこに公開すればよいか、企業の中でセキュリティを保ちながらどう運用するか、だそうです。その答えとして Ignite で発表されたのが CMR（発表では "Copilot management runtime" と聞こえます）です。

- Cowork などで作ったアプリ（トランスクリプトでは "Kouhaku" などと表記）は、自動的に CMR 上にホストされて公開され、ユーザーはすぐに利用できる。
- CMR は、Microsoft のテナント上の Power Platform 環境の上に作られている。そのため、Microsoft の Entra ID 認証やセキュリティ、データ保護の権限などを使いながら、すぐに安全に運用できる。
- Excel、SharePoint、Dataverse などのデータ接続が最初から用意されている。
- 個人が自分用のダッシュボードを作るところから、チーム向けのアプリ、企業向けのアプリへと、段階的にアップグレードできる。
- Ignite の発表時点ですでに GA で、利用できる状態。

**Dynamics 365 Sales（CRM）**

CRM は、ユーザーのデータ入力が手間で更新されず、データが古くなるという悩みが多く聞かれます。これからの CRM は、エージェントが Work IQ のデータを取り込み、CRM を自動で最新の状態にできるとのことです。具体的には次のとおりです。

- プラグインを使い、先ほどの Copilot などから情報の登録や参照ができる。
- CRM に組み込まれた自律的に起動するエージェントが、フォローできていない顧客のサポートや調査を代行する。
- 顧客とのウェブ会議の議事録や音声が、自動的に CRM に取り込まれて更新される。

**ERP**

専門性の高いエージェントを組み込むことで、業務を効率化できます。Sales と同様に ERP のプラグインが用意され、例えば Cowork を通して ERP の膨大なデータを分析し、企業活動に生かせます。会計のようにミスが許されない処理では、専用の業務エージェントに実際の手順やチェック・判断をビジネススキルとして組み込み、最後まで確実に遂行させられるそうです。

**CCI（Contact Center Intelligence）**

すでに使っているコールセンターの上に追加で利用できる音声エージェントです。次のように動作します。

- ユーザーが電話をかけてくると、AI が音声で自動対応し、必要な電話だけを人が対応する。
- すべての対応を AI が評価し、声の生体認証などでなりすましを防止する。
- Genesys や Avaya（聞き取りでは Genesis）などのコールセンターシステムや電話回線を入れ替えずに追加できる。従来 1〜2 年かかっていたコールセンターの入れ替えをせずに、すぐに AI 音声エージェントを活用できる。
- 日本語環境のみプレビューなので注意が必要。

**Dynamics 365 Activate**（聞き取りでは "dimax 365 Activate"）

Dynamics を使っていないお客様向けに、ERP から Dynamics への移行を促進するツールです。基幹システムの移行は、作り込まれたカスタマイズの調査やデータ移行に多くの工数がかかり、移行の妨げになっていました。このツールは、AI の機能で環境の調査と機能のマッピングを行い、データ移行の構築まで一貫して支援します。Yamashita 氏自身も使っており、非常に細かい機能マッピングができると話しました。本日時点で、Salesforce 向けのマッピングツールは GA、SAP 向けは private preview です。

### 5.10 Agent Platform（Omori 氏）

Omori 氏は、キーノートのスライドを掘り下げながら「Microsoft が言う Agent Platform とは何か」を説明しました。複数の要素に、IQ と基盤（foundation）の部分を加えたものが Agent Platform であり、その役割はエージェントを作るだけでなく、配布し、トラッキングし、改善につなげ、その改善も自動化することだとしています。

**Microsoft Foundry**

中核は Microsoft Foundry です。Azure をベースに、約 11,000 のモデルを提供しています。Microsoft が Azure データセンターで提供するものと、サードパーティが提供するものがあり、「このモデルを使うためにこのプラットフォームを使わなければならない」ということはなく、すべて Foundry を使えば大丈夫という環境だそうです。使い方も、従量課金、専有環境、モデルをチューニングして自分でホストする方法など、複数の選択肢があります。

**Hosted agents**

Foundry でエージェントを作るサービスのうち、いま特に注目されているのが Hosted agents です。GUI で作る Prompt agent とは異なり、自分でコードを書いて制御するタイプです。GitHub Copilot や、スライドにも書かれている「dev packs」と呼ばれるスキルなどのツール群を使うことで、Hosted agents でもエージェントを作ることがかなり容易になり、自分で制御する流れが大きくなっているそうです。周辺のアップデートも多く、柔軟に、大量に使えるプラットフォームだと説明されました。

**ID とエンタープライズ制御**

最近の関心事は、ID とアクセスの扱いです。エージェントがユーザーの権限を引き継ぎ、データや他の MCP などを引き継ぐ仕組みを、Microsoft IQ と連携しながら提供しており、この部分も GA になっています。さらに、ポリシーの適用、ハーネスの適用、利用量（トークンの使用量など）の制限といった、エンタープライズ側で制御したい機能も揃ってきたと述べています。

**改善ループ**

Omori 氏が特に注目してほしいと述べたのが、作ったあとにどう評価し、改善につなげ、その改善をどう自動化するかというループです。2026 年 5 月の Build（聞き取りでは "May 6 build"）でさまざまな機能が使えるようになり、トレースの機能もありました。最適化（optimization）は以前はコマンドラインで行っていましたが、Foundry のポータルからもかなりできるようになりました。GUI で始めることも、CLI などで自動化することもできます。

そのうえで、次の進め方が説明されました。

1. 生成 AI エージェントは、ビジネスのユースケースから作り始める。
2. 評価の設定を一緒にきちんと行い、それに合わせて改善する。
3. チューニングは、まずプロンプトのチューニングを行う。
4. 次に、ハーネスやデータなどを見直す。
5. 最後に、専門用語がうまくいかないなどの場合に、モデルのチューニングを行う。

スライド右上の番号はセッション ID なので、その観点で各セッションを見てほしいとのことです。

**責任ある AI とエージェントの制御**

Microsoft は早い段階から Responsible AI を掲げており、今回のキーノートのスライドを英語のまま使った透明性（transparency）の取り組みも、業界全体に広げていくのが Microsoft のメッセージだと述べています。エージェントの制御では、1 つの全体ポリシーをすべてのエージェントに適用することと、必ず human-in-the-loop を入れることがポイントです。アラートの発行や一定の評価は自動化できますが、評価のポイントを人にフィードバックしてしっかり確認する、人が監視するプロセスを必ず入れるという監視方法の重要性を語ったセッションがあった、と紹介しています。

**ゆりかごから墓場まで**

Omori 氏が最も伝えたかったのは、Microsoft は生成 AI をゆりかごから墓場まで提供している、ということです。MAI のモデルを作り、それをホストするチップセット、データセンター、活用するためのアプリケーション、アプリをホストする環境を作り、生成 AI のモデルからエージェントまでを監視し、AI エージェントが使われなくなったら破棄するところまで見守る環境を提供する、というのが Microsoft の Agent Platform です。今後はエージェントを積極的に作り、Foundry と Hosted agents を使い、モデルも model router などで最適なものを選びながら少しずつ変え、改善ループで精度を上げていく、という進め方が示されました。

お持ち帰りいただきたい 2 点として、Microsoft は AI をゆりかごから墓場まで提供していること、そして AI エージェントをある程度自動で作り、その後の活用も自動で改善して、ビジネスの利益につなげるところまで来ていることが挙げられました。

### 5.11 データプラットフォーム（Fujii 氏）

Fujii 氏は、Ignite で強調されたこととして、意図せず持っているデータは AI 活用に使えないだけでなく、サイバー攻撃のリスクも高めると述べ、AI 時代のデータ基盤に必要な 4 つの備えを示しました。「守る」「意味づける」「生かす」「しっかり支える」です。

**守る：OneLake**

OneLake は「データの OneDrive」と呼ばれ、Microsoft の事業の中でも非常に成長しているソリューションの 1 つです。ストレージ容量は年間 290% 以上の成長でした。Fabric の公開事例で最も挙げられている理由は、OneLake の shortcut と mirroring により、データの置き場所を移動しなくてよい点だそうです。今回のアップデートは次のとおりです。

| 区分 | 内容 |
| --- | --- |
| 一般提供 | Azure Monitor、AWS、Google といったカタログを取り込めるようになった（聞き取りのまま。名称は音声認識の都合で確定できません） |
| パブリックプレビュー | Salesforce、Dynamics が加わる |
| （区分の言及なし） | Horizon DB もデータソースとして使えるようになった（GA かプレビューかは、この箇所では語られていません） |
| 一般提供 | OneLake catalog：Teams、Excel など 100 以上のアプリにすでに組み込まれ、発見、キュレーション、ガバナンス、管理、セキュリティを一元管理。Delta、Parquet などのオープンデータフォーマット、メタデータのリネージなど粒度の高いサポートもある。今回は、ガバナンスの一元管理と、"governance skills"（聞き取りは "Gaban skills"）によるリスク特定と改善アクションが新機能 |
| 一般提供 | OneLake Table API：OneLake のデータを Delta や Iceberg などのオープンデータフォーマットのまま外部のデータエンジンから直接利用できる。データのコピーや専用コネクタなしで、Databricks や Snowflake などから同じデータを安全に読み書きできる |

**意味づける：Microsoft IQ と business plugin**

AI 変革が直面している課題として、次の 4 点が挙げられました。

1. エージェントはビジネスを知らない。
2. 多くのエージェントはゼロから構築しなければならない。
3. 多くの PoC が本格展開に至っていない。
4. 外注のエージェント開発では、知的財産の管理が行き届かない。

Fujii 氏は、Intelligence の中核が Microsoft IQ であり、新入社員に業務手引書を渡すのと同じように、エージェントにも企業固有の知識と文脈を与えれば、従業員のように信頼でき、生産的な存在になるという考えを説明しています。今回の発表では、聞き取りで "work classes" と聞こえる部分（Work IQ を指す可能性がありますが、確定できません）、"Public IQ"（聞き取りのまま。Fabric IQ を指す可能性がありますが、確定できません）、Build で発表された Web IQ に加え、サードパーティの IQ も含めて自社の IQ を作ること、そして IQ を業務単位でまとめる business plugin が示されました。

- **Microsoft IQ API**：エージェントが企業のコンテキストを取得、推論、grounding するための共通の API。Copilot、ChatGPT、Claude、独自のエージェントに、同じ権限と同じガバナンスで利用できる。エージェントはまず business plugin を参照し、答えられない場合に個別の IQ を見る。既存の IQ API を置き換えるものではなく、エージェントに共通の入り口（front door）を作るもの。
- **business plugin**：自社固有のコンテキスト、スキル、信頼できる情報を 1 つにまとめ、複数の AI エージェントから再利用できるようにする仕組み。社内規定のような回答の根拠となる情報源のほか、固有の業務プロセスや意思決定のノウハウも対象にできる。IQ が企業のコンテキスト基盤なら、business plugin は特定の業務に必要な IQ を再利用可能な形でパッケージ化したもの。
- **IQ sharing in Fabric**：企業や組織を超えて、データだけでなくその意味やビジネスコンテキストを共有する仕組み。OneLake のデータをコピーせずに共有するため、提供元がデータの管理を保ったまま、受け手は自分の Fabric 環境から利用できる。ローンチパートナーとともに発表されている。
- **セマンティックコンテキストの共有（インキュベーション）**：セマンティックなコンテキストを一度定義し、異なるベンダーや AI エージェントから再利用できるようにする取り組みで、今回 Snowflake が参加を発表した。Microsoft は Snowflake と、オープンで相互運用可能なセマンティック基盤を構築しており、Snowflake でも Microsoft のデータエージェントでも、それぞれのセマンティックコンテキストを利用できるため、AI ごとにビジネスの意味を定義し直す必要がなくなる。取り組みの名称は聞き取りでは "Apache's initiative" で、音声認識の都合で確定できません。

**生かす**

正確なデータに基づくコンテキストを、Copilot、Cowork、GitHub、Copilot Studio から利用できます。例えば Excel でデータについて質問し、根拠のある回答を得て、その結果をワークブックで使えます。フィールド名を毎回指定せずに、セマンティックモデルに接続された表を作成することもできます（聞き取りでは "boat tables"）。Microsoft 製品だけではなく、ChatGPT と Claude も、この IQ のプラグインに対応するとのことです。これにより、信頼できる Power BI のインサイトをあらゆるユーザーに提供できるようになります。

**支える：Azure Horizon DB と Database Hub**

Microsoft は、ハイパースケーラーの中で PostgreSQL のコミット数が最大であり、この実績をもとに Azure Horizon DB が GA になりました。完全マネージドの PostgreSQL サービスで、性能面では次のとおりです。

- 最大 3,072 vCore と 128 テラバイトのストレージに対応する。
- 自己管理の PostgreSQL と比べて最大 8 倍の処理速度が実測されている。
- マルチゾーン構成でもコミットレイテンシが 1 ミリ秒未満（聞き取りでは "1mm sets" で、単位は確定できません）。

Fabric にはこれまで SQL database や Cosmos DB といった SaaS 型のデータベースがありましたが、パブリックプレビューとして Horizon DB が加わりました。サーバーレスで数秒で起動し、データは自動的に OneLake にミラーリングされるため ETL が不要で、そのまま分析に使えます。アプリは単一の PostgreSQL 接続のまま、行ストアと列指向エンジンのそれぞれで使えるとのことです。ベクトル検索と AI モデルの呼び出しにも対応します。

データベースが大きくなると、大規模な監視や、監視状態に応じた管理、セキュリティとガバナンスの課題が出てきます。これに対し、Database Hub in Fabric が GA になりました。Azure SQL、SQL Server、Cosmos、Horizon を一元的に可視化して管理できます。右下の data agent はパブリックプレビューで、データベースの異常を検知し、診断し、診断に基づく安全な対処を提案または実行し、その効果を検証し、継続的に学習するエージェントです。

Fujii 氏は、紹介した機能はごく一部なので、興味のあるセッションの録画を見てほしいこと、日本のお客様の声で一緒にデータプラットフォームを進化させたいことを述べて締めくくりました。

### 5.12 休憩中のビデオ

休憩中に流れた英語のビデオでは、AI エージェントでビジネスプロセス全体を変革するには、継続的にパフォーマンスを改善し、エージェントへの信頼を築くための適切な基盤（聞き取りは不明瞭）とガバナンスが必要だと語られました。内容は次のとおりです（音声認識では会社名が "entity data" となっていますが、5.6 の NTT Data の PMO エージェントの取り組みと対応する内容です）。

- プロジェクト管理エージェントを Microsoft Foundry で開発している。
- トレーシングやインサイトを含むオブザーバビリティで、継続的な改善と学習のループを構築している。
- Foundry の rubric に基づく評価で、定義した基準に対するパフォーマンスを測り、改善が必要な箇所を把握する。
- Microsoft Foundry の agent optimizer で、エージェントの指示やツール、再利用可能な PMO スキルを見直す方法を探っている。
- 改善を検証したらエージェントを再デプロイし、またプロセスを繰り返す。
- サンプルプロジェクトでの当初の見積もりでは、特定のプロジェクト管理タスクにかかる時間を約 60% 削減できる見込み。
- 重要な判断には人が関与し続ける必要がある。

### 5.13 Azure インフラ（Kawasaki 氏）

後半の最初は Azure インフラです。Kawasaki 氏は、初日のセッションで Azure の CTO（名前は聞き取り不明瞭）が述べた「Azure was built for this moment」を紹介しました。Azure は 2010 年から高性能コンピュータークラスターを商用クラウドに導入し、OpenAI のモデルの初期訓練を経て、エージェントの時代へと AI 向けの進化を続けているとのことです。現在はシリコンからインフラ、その上で動くサービスの運用、データまで、すべてが AI のために作り直されているという位置づけです。

Azure の変化を最も実感できるのは GitHub だと言います。AI エージェントの登場で、GitHub の push、commit、pull request が 2026 年に大きく増えると見込まれています。この規模に耐えるため、システム全体をシンプルにし、ストレージとコンピュートを分離し、push から commit までのステップを最小限にするなど、基盤そのものの再構築が必要になり、これが Azure の進化にもつながったそうです。

AI に対応する Azure の進化の方向性は、次の 4 つです。

1. Evolving primitives：CPU、ネットワーク、ストレージなどの構成要素の進化
2. システム全体の AI 向け最適化
3. オープンかつ安全に制御するための仕組み（聞き取りは "open and gabant" で、音声認識の都合で確定できません）
4. Intelligence everywhere：ユーザーのニーズに応じ、インフラのどこでもエージェントを動かせること

**コンピュート**

従来の VM やコンテナは、長時間動くアプリケーションを動かす基盤が前提でした。AI には、必要なときに即座に起動し、安全に実行できる環境が必要です。そのために登場したのが次の 3 つです。

- **Micro VM**：500 ミリ秒未満で作成と復元ができ、大量の環境を短時間で起動できる。
- **Agent Sandbox**：エージェントが生成したアクションを隔離して実行する機能。
- **Cobalt 200**：新しいチップで、これらの機能を支える CPU 性能を提供する。

**ネットワーク**

これまで IP アドレスとポートでつながることが重要でしたが、AI では、どのエージェントがどの権限で、どのモデルやツール、データにアクセスできるかの制御が重要になります。そのために登場したのが **Agent Grid** です。Azure Container Instances（ACI）や AKS で動作するネットワークセキュリティ機能で、エージェント ID に基づくポリシー、デフォルト拒否によるネットワーク分離、認証と暗号化によるエージェント間通信の制御ができます。従来の NSG の AI 向けの進化版と捉えてほしいとのことです。

**セキュリティ**

人、端末、アプリケーションに境界を作る従来の考え方を、エージェントのセッションや生成コード、ツール呼び出しまで広げます。サンドボックスによる隔離、処理中のデータを守る confidential AI、Agent Grid によるアクセス制限を組み合わせる必要があるそうです。さらに **Azure Integrated HSM** は、暗号鍵をハードウェアで保護する基盤で、秘密鍵を AI のモデルから切り離します。AI がだまされたり、エージェント自体が侵害されたりしても、秘密鍵そのものは盗まれないようにする仕組みです。

**Kubernetes**

従来の AKS は汎用のコンテナ基盤でしたが、モデル、GPU、推論エージェントの性能を理解する AI 実行基盤へと進化させています。今回登場した **AKS AI Manager** は、AI モデルを AKS にデプロイし、推論サービスを運用するための管理機能です。Microsoft Foundry から、既存の自社の AKS クラスターへモデルや Hosted agents をデプロイする機能が、限定プレビューとして発表されました。エージェント開発者は引き続き Foundry を使い、基盤チームは AKS AI Manager でネットワークポリシーや GPU などを管理するという、役割分担がうまくいく仕組みだと説明されています。

**アプリケーションのモダナイズ：Azure Catalyst**

AI に対応したアプリを作るには、まずアプリケーションのモダナイズが欠かせません。社内ナレッジの共有システムや、自然言語で問い合わせたり、毎週金曜日や月曜日にレポートをエージェントに自動生成して送らせたりする ERP システムなどが例に挙がりました。まず「Modernize with AI」で AI を使ってアプリを改修し、その先が AI transformation です。AI の活用で、数か月かかっていた改修作業が、数日や数週間で終わるようになってきたと述べています。

これを実現するために発表されたのが **Azure Catalyst** です。ネットワークエンジニアの経験がある人はスイッチかと思うかもしれませんが、スイッチではありません。Azure Migrate を進化させた、Azure の移行とモダナイゼーションを支援するサービスです。従来は資産を評価して Azure へどう持っていくかが中心でしたが、今回は AI がアプリ全体の刷新を支援するというコンセプトです。できることとして、次の点が挙がっています。

- 評価結果をもとに AI と対話できる（例：「移行できない理由は何か」「VM と PaaS のどちらが適切か」と尋ねられる）。
- GitHub Copilot modernization と連携し、コードの Azure 互換性、修正候補、改修の見積もりなども出せる。

**AI をどこで動かすか：Sovereign Cloud と Azure Local**

4 つ目の方向性にあたる「AI をどこで動かすか」は戦略的な意思決定が必要で、判断軸は latency、security、economics（コスト）の 3 つです。latency と security は置き場所で決まり、その組み合わせがコストにつながります。Microsoft は、クラウドからオンプレミス、エッジ、physical AI デバイスまで、AI を動かせる場所をカバーしています。

そこで登場するのが Sovereign Cloud です。データや運用の主権を守るクラウドの総称で、**それ自体がサービスではない点に注意**が必要だと述べています。この Sovereign Cloud を構成するサービスの 1 つが Azure Local で、プライベート型で自社設備の上で Azure を利用できます。今回の Ignite で発表された内容は次のとおりです。

- **SQL Server on Azure Local**：自社のアプリケーションと SQL、さらに Foundry Local を組み合わせ、アプリ、DB、AI を自社の中で動かせる。
- **接続モードの切り替え**：これまでは、クラウドに接続するタイプと完全切断型の二択だったが、自由に切り替えられるようになった。オンプレミスでもクラウドでも一貫した環境を提供できる。

AI を動かすエッジの 1 つとして、Windows Server の新機能も紹介されました（トランスクリプトでは版数が "2008" と聞こえますが、聞き取りの誤りが疑われ、版数は確定できません）。4 つの領域（ハイブリッドインテリジェンス、セキュリティの強化、インフラの高速化、大規模な管理）が紹介され、一言で言えば、サーバーをより安全な初期状態で導入し、クラウド ID の管理基盤でも運用できる方向への進化です。Kawasaki 氏が気に入った特徴として、Entra ID への参加と Intune での管理が可能になったことが挙げられました。これによりオンプレミスの AD DS が不要になり、クラウド主体で運用できるようになったとのことです。

### 5.14 Windows（Seyama 氏）

Ignite には Windows と Windows クラウド関連のセッションが 150 もあり、その中で最も印象的だったのが、AI エージェントがクラウド上の Windows を使って働く世界観だと Seyama 氏は述べました。ポイントは 2 つで、手元の物理 PC ではなくクラウド上の Windows であること、使うのが人ではなく AI エージェント専用の PC であることです。この内容は 6 章のデモで紹介されています。

Windows の責任者（聞き取りでは "Paban"）が、人と AI が一緒に働く場所へ変わるための理由として挙げた 3 点は次のとおりです。

| 観点 | 内容 |
| --- | --- |
| 基盤 | これまでセキュリティ製品は Windows の中核であるカーネルの中で動いていたが、今後はカーネルの外で動かせる。問題が起きても PC が止まりにくく、復旧しやすくなる。AI エージェントは Microsoft の execution container という囲いの中で動き、使ってよいファイルや通信先をあらかじめ決め、それ以外は Windows がブロックする。このポリシーは今後 Intune で定義できる |

### 5.16 Agent 365 のセキュリティ：Agentic Insider 保護（Fukuchi 氏）

Fukuchi 氏は、Agent 365 の 4 つの柱のうち、下の 3 つ（管理、ガバナンス、セキュリティ）を担当すると説明しました。セキュリティのキーノートでは、大きく 2 つが発表されました。組織内のエージェントを暴走から守る Agentic Insider 保護と、エージェントで組織を守る Microsoft Perception の GA です。ここでは前者を説明しています。

**なぜ必要か**

Fukuchi 氏はスライドの左端にある 68% という数字に注目するよう促し、エージェントを持つ組織で、人間との活動の区別がつきにくいことを説明しました（数字が何の割合かは、音声の聞き取りが不明瞭です）。「見えないものは守れない」という言葉のとおり、エージェントが何をしているか、存在するかが見えなければ何も守れません。区別できないと、エージェントが暴走してアクセス権を乱用した場合に、その持ち主である人もアクセス権を剥奪されてしまうことが起こり得ます。

また、エージェントは 24 時間 365 日動きます。Fukuchi 氏自身、寝る前に依頼しておくと朝には成果物ができているという使い方をしており、多くのお客様も同様だろうと述べています。一方で、寝ている間にエージェントが暴走して機密データが外部に送られたり、ファイルが削除されたりしてはいけないため、守る側も 24 時間 365 日守る必要があります。

**4 つの守りの型**

守りの型として発表されたのは "no contain protect adapt" と聞こえる 4 つです（先頭の語は音声認識の都合で確定できません）。Fukuchi 氏は全部は説明せず、次の機能に絞って紹介しました。

- **Discovered Agent ID**（Contain 内）：Microsoft 製以外のエージェントにも ID を割り振れる。Microsoft の基盤で作ったエージェントには Entra の Agent ID が自動で付与されることは知られているが、デスクトップ上のエージェントや、クラウド上の Microsoft 以外のエージェントには付与できなかった。Discovered Agent ID は SDK などを使わずに ID を付けられる。ID を持たせると、人との識別ができ、後述の Dynamic Permissions にも生きる。
- **Dynamic Permissions**：エージェントがタスクを実行する際に、必要な権限を、必要な期間だけ割り振る。例えば、必要な権限がファイルの読み取りだけなら、そのファイルの読み取り権限だけを与える。送金のように注意が必要な操作は、実行しようとするときに人の承認が必要になるようにできる。
- **Dynamic Agent Risk**：エージェントが動いているときや、必要以上に広い権限が付いていないかといったリスクを可視化する。リスクの値が高いものは、優先度をつけて対応する。
- **Risk-linked access**（Adapt 内）：Dynamic Agent Risk のリスクをもとに、条件付きアクセスでアクセスを止める。寝ている間にリスクが高いと通知されても対処できないため、自動で守る機能として追加されている。

**権限が適切でも安心できない理由**

Fukuchi 氏は、権限が適切なら安心とは限らないと指摘しています。例えば、ファイルの読み取りとメール送信の権限を与えたとき、読み込んだファイルに攻撃が仕掛けられていて、エージェントが機密情報を集めてメールで送ってしまう、という事態が起こり得ます。権限の範囲内で悪意のある操作が実行されてしまうため、Dynamic Agent Risk でリスクを評価し、リスクに連動した条件付きアクセスで、リスクが上がればアクセス制御をかけ、それほど高くないものは人の承認を必須にする、といった運用ができるようになる、という説明でした。

まとめとして、(1) Microsoft 製品以外のエージェントにも ID を付与する、(2) ID を付けたうえで、必要な権限を必要な期間だけ提供する、(3) その範囲内でもエージェントが悪さをしようとしたら、リスクスコアを見て条件付きアクセスで止める、という流れでエージェント自体を守る世界を実現したいと述べています。

### 5.17 Microsoft Perception と ISOC（Sato 氏）

Sato 氏は、エージェントを使って組織全体を守る仕組みを説明しました。

**Microsoft Perception の概要**

Microsoft Perception は Ignite で GA になりました。専門性を持ったエージェントが 3 つのチームに分かれて連携する点が特徴です。

| チーム | 役割 |
| --- | --- |
| Red Team | 攻撃経路の分析とペネトレーションテスト |
| Blue Team | インシデントのトリアージと調査 |
| Green Team | リスクの修復計画を作成し、実行を支援する |

これらのエージェントがチームになって、分析から対応計画までをマシンスピードで進められるのが特徴です。Microsoft 製品だけでなく、サードパーティの製品やデータにも、まだ一部ですが対応します。また、一部はプレビューですが API と MCP も提供するため、自社で独自にセキュリティ基盤を作っているお客様も、Perception の機能をその基盤に組み込めるとのことです。

**Playbook の機能**

Perception の playbook は、特定の目的に応じて必要なエージェントが連携してタスクを実行する機能です。アラートのトリアージ、攻撃の調査、リスクの修復計画の作成などのメニューが用意されています。利用者は目的に合った playbook を選び、必要な情報を入力して実行すると、エージェントが一連の処理を始めます。デモでは脆弱性対策として、一番下のメニューにある「ウェブアプリを保護する」playbook が示されました（6 章）。

**ウェブアプリの保護の流れ**

Sato 氏は、デモのポイントを次のように説明しました。単なる脆弱性スキャンツールのように見えるかもしれませんが、Perception の特徴は、それに連続してアプリの修復エージェントが動くことです。見つかった脆弱性に対して、エージェントが修復計画を作成します。ポリシーを提案する機能もあるとのことです（具体的な語は聞き取り不明瞭）。脆弱性を見つけるだけでなく、どう対処するかまで具体化し、それを人が判断して対応を進められる、というのが特徴です。

**ISOC（Integrated Security Operations Center）**

どれだけ優秀なエージェントを作ってデプロイしても、判断に必要なデータやインプットがなければ力を発揮できないため、基盤が重要だと Sato 氏は述べています。その基盤が ISOC（Integrated Security Operations Center）で、Defender XDR（聞き取りでは "XTR"）と Sentinel の機能を 1 つの運用基盤に集約します。シグナル、調査に必要な文脈、対応に必要な制御系を、人とエージェントが共有できるのが特徴です。

その中心にある保管・管理機能が **ケース管理（case management）** です。インシデント情報に加えて、優先度の設定、SLA の管理、コメント、添付ファイルの共有、類似ケースの調査など、調査と対応をチームで進めるための機能が 1 つにまとまっています。単にインシデントを調べて分析するだけでなく、何を優先し、いつまでに誰が対応するかを 1 つのケースで管理できる点が特徴です。

さらに、ケース管理とエージェントによる調査をつなぎ、人と AI が連携する **agentic SOC** を実現します。初動調査とトリアージだけでなく、アナリストが行うレベルの詳細な分析、レポート作成、対応計画の立案まで Perception が進められ、人は結果と根拠を確認して、必要に応じて追加の調査を指示できます。全体像は、AI が調査と計画を進め、人が判断して実行を進めるという新しいセキュリティ運用の形だと説明されました。

**セキュリティパートのまとめ**

Sato 氏は、オブザーバビリティで AI の利用を見える化し、セキュリティで AI の安全性を確保し、さらに AI エージェントで組織の守りを強化する、という全体像を示しました。信頼の基盤があってこそ、Human Ambition と Intelligence を安心して活用できるという説明です。

## 6. デモ・手順

### 6.1 Copilot Code のデモ（Watanabe 氏）

右側に見えている画面を示しながら、各国の市場実績を地図と指標で見渡せるダッシュボードを作るよう依頼している画面が示されました。編集も作成も、Code に自然言語で伝えれば作れる、という説明です。具体的な操作手順は語られていません。

### 6.2 Autopilot のデモ（出張の手配）

Autopilot が出張を手配する動画が流れ、ナレーションで次の内容が語られました（この動画は、トランスクリプトでは "Kouhaku" と表記される Cowork と思われるツールで作成されたと、Watanabe 氏が補足しています）。

1. 「Ignite への出張をサポートして」とゴールだけを伝える。
2. Autopilot が、出張の準備だけでなく、不在中の対応と帰ってからの仕事まで整理する。
3. Autopilot 自身のブラウザで出張サイトを操作し、社内規定に合うホテルを探す。機内 Wi-Fi や会場までの距離など、出張する人の好みに合った候補を提案する。
4. 進捗は Autopilot からメールで届く。人は判断が必要なときだけ返信すればよい。
5. メールで Autopilot に呼びかけると、会食の招待を手配する。
6. 出張中で本人が不在でも、Autopilot が Teams で質問に答え、最新版の資料を案内する。
7. 帰る前に、不在中の動きと、戻ってからの予定をまとめて知らせる。
8. 経費の下書きまで作成し、確認して提出するのは人。

動画のナレーションと下部のキャプションも同じツールで作ったとのことで、このように動画も生成できるようになったと紹介されました。

### 6.3 Agent 365 Business Analytics の画面（Watanabe 氏）

「見ていきたいと思います」と進め、画面の流れが次のように語られました。ナレーションのような口調で、画面の細部は音声からは分かりません。

1. AI の利用状況と支出を全体で見る。
2. どのエージェントに費用がかかっているかを見る。エージェントごとの画面で、コストと推定価値を金額で比べられ、完了率など、支援時間の見積もりの前提も確認できる。
3. 支出が増えたとき、どのモデルのコストが多いかを確認する。
4. 月末の支出見通しと予算を早めに確認する。今のペースが続く場合と利用が伸びる場合を比べる。
5. 例えば上限の設定（聞き取りでは "per cap"。1 人当たりの上限と思われますが確定できません）を変えると支出がどうなるかを、実際の設定を変えずに試せる。
6. 全社の予算のもとで、部門ごとの月額上限と、今月どこまで使ったかを見る。必要な人に範囲を絞って閲覧権限を渡せる。
7. レポートを作り、関係者と共有する。
8. 部門ごとの AI 利用額を確認し、利用やコストのデータを CSV などで出力する。営業と開発が同じエージェントを使っている場合は、利用実績をもとに、社内ルールに沿って費用を振り分けられる。

### 6.4 Windows 365 for Agent のデモ（Seyama 氏）

デモ（動画と見られますが、形式は音声からは断定できません）の内容が語られました。

## 7. 注意点・発表者の気付き

- **提供状況がまちまちです。** Copilot の Code と Autopilot は Frontier preview（Code は数週間以内に GA 予定、Autopilot は主に米国、Copilot Studio の AI 同僚は 12 月から）、Copilot force はプレビュー、CMR は GA、Home は GA です。CCI は日本語環境のみのプレビュー、Dynamics 365 Activate は Salesforce 向けが GA で SAP 向けは private preview、Perception は GA、AKS AI Manager 経由の Foundry からの展開は限定プレビュー、Database Hub は GA で data agent はパブリックプレビューです。
- **Toyota の取り組みは製品ではなく技術検証中です。** 現在は実際の車でテストしており、社員が自ら試しているとのことです（聞き取りでは "self-zero" に近く、不明瞭です）。
- **共有するのは傾向だけで、個人の好みは本人のためだけに保持する**という方針が Maeda 氏から示されました（Fabric IQ の部分）。
- **Sovereign Cloud はサービスそのものではありません。** データと運用の主権を守るクラウドの総称で、構成サービスの 1 つが Azure Local です。
- **権限が適切でも安全とは限りません。** Fukuchi 氏は、読み取りとメール送信という許可された範囲内でも、攻撃を仕掛けられたファイルによって機密情報が送られる可能性があると指摘しました。そのため、リスク評価と、リスクに連動した条件付きアクセスが必要になります。
- **エージェントの作り方と改善の順序**として、ビジネスのユースケースから始め、評価を設定し、チューニングはプロンプト、ハーネスやデータ、最後に専門用語などのためのモデルのチューニングの順で行う、というプロセスを踏むよう Omori 氏が促しています。
- **human-in-the-loop は必須**です。アラートや一定の評価は自動化できても、人が見るプロセスを必ず入れる監視方法が重要だとされました。
- **ID の管理が見えないと守れません。** スライドの 68% という数字を示しながら、エージェントを持つ組織では人間との活動の区別がつきにくいと説明されました（数字の定義は聞き取り不明瞭です）。
- 本セッションの数値や固有名詞の一部は、音声認識の誤りの影響が大きいため、各所に注記しています。

## 9. まとめ

Japan Wrap-up Session は、Ignite の内容を「Human Ambition、Intelligence、Trust」という 3 本の柱に沿って、約 2 時間で日本語に整理し直したセッションです。

Intelligence の面では、Microsoft IQ に自社の知識を蓄積し、その上で自分たちの IQ を作ることが語られました。Toyota は、1 つの車載エージェントを Foundry、Fabric IQ、Web IQ の 3 つの観点から繰り返し改善する取り組みで、その具体例を示しています。日本の事例では、Woven Toyota の 44% と NTT Data の 68.6% から 83.3% への向上が、継続的な改善の成果として挙げられました。

プラットフォームの面では、Copilot（Chat、Cowork、Code、Autopilot の統合）、CMR によるアプリの安全な公開、Dynamics のエージェント化、Foundry の Hosted agents と改善ループ、OneLake と business plugin によるデータと意味の共有、Azure の Micro VM や Agent Grid、Windows 365 for Agent まで、エージェントを動かす基盤が一通り紹介されています。

Trust の面では、Agent 365 がオブザーバビリティの基盤となり、エージェントの管理、コスト可視化、Discovered Agent ID や Dynamic Permissions によるエージェント自体の保護、そして Microsoft Perception と ISOC による「AI が調査と計画を進め、人が判断する」セキュリティ運用までが、1 本の流れとして説明されました。

最後に、12 月 11 日のオンライン Wrap-up、フィードバックのお願い、次回 Ignite（11 月 16〜19 日、San Francisco）と日本からの参加 1,000 人の目標が案内されています。
