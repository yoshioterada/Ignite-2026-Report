# BRK260 The next evolution of AI FinOps: From cost to value

## 1. はじめに

このセッションは、AI の利用料金を「見える化して抑える」段階から、「投資に見合う価値を出しているかを測って最大化する」段階へ進むための考え方と機能を紹介する発表です。前半は Microsoft の AI FinOps 責任者である Ryan Jones 氏が、エンドユーザー、メーカー（エージェントの作り手）、IT 管理者それぞれの立場でコストを管理する方法をデモで見せます。後半は Avinash 氏が、部門のリーダーやアナリストが使う Agent 365 Business Analytics アプリで、コスト、ユースケース別の価値、予算の再配分までを一続きで見せます。

押さえておきたい結論は 2 点です。

- 予算と支出ポリシーで上限（キャップ）を設定すれば、請求の「サプライズ」は起こらない。
- AI 支出の議論は IT 部門だけのものではなくなり、事業部門のリーダーが予算配分の意思決定者になっている。

## 4. 発表者が伝えたいメッセージ

Ryan 氏は、顧客との会話が毎回「最小のコストで最良の成果を得るにはどうするか」から始まると言います。その答え方がこの 1 年で変わってきたという認識が、発表全体の軸です。

- 第 1 段階は、まず利用者の手に技術を届けること。存在しない利用は制御も測定もできないためです。
- 第 2 段階は、利用が広がるにつれて予算に対して支出を管理すること。月末に想定外の請求が来ることを誰も望まないからです。Ryan 氏は、第 1 段階との間に「鶏と卵」のような問題があることも認めています。
- 第 3 段階が最も重要で、価値の最大化です。AI の請求額が最も小さいことを競う場ではなく、組織が最大の価値と事業成果を出せるようにすることが目的だと述べています。

そのうえで、AI 支出は P&L（損益計算書）上で、人件費、インフラ費、ベンダー費用、サードパーティの知的財産費用と並ぶ新しい項目になりつつあり、他のカテゴリーから予算を振り替えて AI に回す判断は、多くの場合、事業部門のリーダーが行う、と説明しています。技術者側は事業成果や業務プロセスの文脈を持たないため、その判断を代わりにできないという立場です。

Avinash 氏も同じ文脈で、AI はもはや「テクノロジーの案件」ではなく、そう捉え続ける企業は支出も得られるリターンも大きく見誤る、と述べています。

## 5. 発表内容の詳細

### 5.1 Observability の 4 つの問いと Agent 365

Ryan 氏は、Observability を「信頼の土台」と位置づけ、次の 4 つの問いに答えられるかが出発点だと説明します。

1. 何が存在しているか（存在を知らなければ管理できない）
2. それは何をしているか（存在理由は何か）
3. 組織にどんなリスクを生んでいるか
4. いくらかかっているか

多くの組織では、この 4 つのどれにも答えにくいのが現状だとのことです。その答えとして Agent 365 が紹介され、4 本柱は management、governance、security、business value です。本セッションは最後の business value を深掘りします。

### 5.2 3 つのトレンド

1. **コスト管理から価値最大化へ。** 計画（どれだけ使うか）、ガードレールと上限の設定、価値の測定と最大化、という循環で進めます。Ryan 氏はこれを「dimming cycle」の変形と呼んでいます（音声認識の都合で表記が確定できません）。
2. **すべての AI サービスを横断して見る。** 事業部門にとって、成果を出したのが Cowork か Code か GitHub Copilot かは重要ではありません。問題は解決したか、いくらかかったか、どれだけの価値が出たかです。
3. **FinOps は IT 中心の取り組みから「チームスポーツ」へ。** サッカーでみんながボールを追いかける例えで、参加者の広がりを説明しています。

| ペルソナ | 発表での位置づけ |

| メーカー・開発者 | エージェント、プラグイン、スキルを作る人。エージェントの効率に与える影響が大きい。Microsoft Copilot Studio と Microsoft Foundry の中で確認できる（デモは Copilot Studio） |

### 5.4 Microsoft Admin Center での管理（IT 管理者向け）

デモの内容は 6 章に記載します。ここでは、設計の考え方を整理します。

- **ドル建て表示。** 管理者向けの画面では、消費を Copilot credits ではなくドルで表示します。交渉済みのレートカード（rate card）を使い、実際のコストを把握できるようにするためで、「予算は Copilot credits では組まない」という顧客の声を受けた設計だと説明しています。
- **支出ポリシーが中心。** コスト管理の「錨（アンカー）」は spending policy（支出ポリシー）だとしています。
- **ポリシーの 2 つのパターン。** 1 つ目は ID（entre security group と聞こえます。音声認識の都合で表記が確定できません）に基づく方法、2 つ目はエージェント単位です。後者の例として、Microsoft 社内の Ask HR エージェントを挙げ、費用は HR 部門が負担するため、質問した社員の上司に請求が見えるべきではない、と説明しています。
- **対象の広がり。** エージェント単位は agent registry から選べます。Copilot Studio の環境にも定義できます。Foundry のサブスクリプションへの対応は「来年の初め」とのことです。Microsoft 以外のプラットフォーム向けにも定義できます。
- **上限の強制。** 上限は Microsoft のファーストパーティのプラットフォームすべてで強制されます。

### 5.5 Agent 365 Business Analytics アプリ

ここから Avinash 氏の担当です。出発点として次の数字が示されました。

- Gartner の推計では、今年の AI 支出の合計は約 2.6 兆ドルで、前年より約 50% 多い。
- 多くの企業が、売上に対する AI 支出の比率がこの 1 年でほぼ倍になったと報告している。
- BCG のレポートでは、AI 支出全体の 80% が企業の IT 部門の外にある。つまり事業部門が資金を出している。

事業部門が支払う以上、価値がすぐに見えることを期待します。IT に提供してきた Observability を事業側に広げるのが、このアプリの狙いです。

**誰のためのアプリか。** 部門リーダー（IT、財務、事業部門）が対象で、リーダーが自部門の transformation analyst や AI 変革を進めるプログラムマネージャーなどのスペシャリストに権限を委任することもできます。

**料金。** アプリ自体は Microsoft Copilot のサブスクリプションに含まれ、Microsoft の AI スタック全体の Observability が得られます。サードパーティや Microsoft 以外の支出にも広げたい場合は、A365 サービスの connected platforms で登録します。

**3 つの役割。**

1. 支出を理解する（エージェント、サービス、モデル、ユーザーまで切り替えて、コストの要因を見る）
2. ビジネス価値を引き出す（組織で何に AI が使われ、それにどれだけの価値があるか）
3. 実行に移す（将来コストの予測、ポリシー適用前のシナリオのモデリング、IT を介さずにポリシーを一部変更するガードレール、チャージバックの設定）

### 5.6 ユースケース分類と AI value の計算

Avinash 氏が最も力を入れて紹介したのが、Cowork のセッションを「何のために使われたか」で分類する機能です。

- すべての Cowork セッションを、6,000 以上のユースケースのいずれかに対応付けます。
- 分類体系（taxonomy）は、Bureau of Labor Statistics、O*NET、LinkedIn の occupation graph を科学的な裏付けとして構築したものです。求人票に書くような、人が行う業務を網羅することを意図しています。
- セッションの内容を見てユースケースに対応付けるため、これまで答えにくかった「チャットや Cowork のセッションの中で何が行われているか」に答えられます。個人的な用途や失敗したケースなど、すべてを対応付けられるわけではありませんが、デモの組織ではコストの約 80% を推定できています。

AI value の計算は、タスク単位で次のように組み立てられています（電卓アイコンから確認できます）。

1. そのユースケースが実行された頻度を使う。
2. タスクが成功した場合のみ価値に数える。
3. Cowork が完了に全面的に責任を持つわけではない（人を補助する設計である）という前提を、すでに織り込んでいる。
4. Cowork なしで人がそのタスクを行った場合にかかる工数の推定を使う。
5. それを、そのタスクを担う人の賃金率で価値に換算する。既定値は米国の中央値の賃金率。

工数、賃金率、通貨はすべてカスタマイズ可能で、「Microsoft が出した電卓ではなく自分の電卓」にできると説明しています。デモの組織では、Cowork に 80,000 ドルかかった作業の総量が、少なくとも 185,000 ドルの価値を生んでいるという結果でした。

### 5.7 ユーザー集中度とアクティブな声

デモの組織では、960 人のうち 770 人がアクティブユーザーです。グラフでは、上位 5% のユーザーがコストの 49% を占めていました。Avinash 氏は、これは今回のデモだけの数字ではなく Microsoft 社内データや複数の顧客でも非常によく見られると述べています。初期採用者やパワーユーザーが多く使うのは自然で、問題ではないとの見方です。

ただし、こうした人たちは何がうまくいき、何が障壁なのかという知見を持っています。それはテレメトリのような受動的な分析からは得られず、本人たちの声が必要だというのが、アンケート機能の趣旨です。

### 5.8 アナリスト向け機能

アナリストや Chief of Staff といったスペシャリストは、上司から具体的な質問や漠然とした質問を受け、四半期ビジネスレビューの準備をします。そのため、より深いツールが必要になると説明されました。

- **Service deep dive。** GitHub を例にすると、約 400 人のエンジニアが GitHub Copilot を使っています。利用者は成熟度で分類されていて、受動的な利用者、コード中心（code first）、エージェント中心（agent first）などに分かれます。PR の量と速度といったエンジニアリング指標では、成熟度が高い 3 段階目のユーザーは、受動的なユーザーの少なくとも 3 倍生産的でした。
- **Agent registry。** すべてのエージェントをランキングで見られ、コストと価値も確認できます。非 Microsoft のエージェントも Agent 365 に登録していれば並んで表示されます。エージェントを開くと、作成者が登録したメタデータ、説明、作成者、プラットフォーム、セッション数、コスト、そしてユースケース推定（Cowork のような 6,000 の分類ではなく、目的が決まったエージェントなので 20 ほど）が見られ、タスクごとの ROI の計算もできます。
- **Interactive insights。** 「management consultant in a box」として訓練されたエージェントです。必要なドメイン知識と問題解決の手法を持ち、アナリスト本人が見られるデータすべてにアクセスできます。
- **Reports。** あらかじめ用意されたテンプレート的なレポートで、「途中まで連れて行ってくれる」ものです。特定の分析と目的を持ったストーリーラインがあり、基盤のデータに接続済みで、カスタマイズも可能です。自社のデータ（ビジネス KPI など）を持ち込むこともできます。Avinash 氏は、UX リサーチャーから聞いた「正しい価値の指標は、自分が信じられるものだ」という言葉を紹介し、スループット、アウトプット、アウトカムのどこに置くかに唯一の正解はないと述べています。
- **エクスポート。** 画面に出るすべてのデータセットがエクスポートできます。期間と対象ユーザーを選べます。CSV のほか、Microsoft Fabric、Power BI、MCP エンドポイントにプログラムから接続できます。

また、Interactive insights のアナリストは、Cowork のプラグインとしても提供されます。アプリを開かなくても、Cowork から同じ質問ができます。

## 6. デモ・手順

このセッションにはデモがあります（Ryan 氏が 3 つ、Avinash 氏が 1 つのアプリ）。録音は音声のみのため、画面上の細かい操作は、発表者が語った範囲に限って書きます。

### 6.1 Cowork（Microsoft Copilot）— エンドユーザー視点（Ryan 氏）

1. Microsoft Copilot の Cowork を開く。右上に「ガソリンメーター」のような表示があり、Cowork で使うクレジットの残りが 30%、リセット日が 12 月 1 日だと分かる。いつでも使用量と残量が見えるので、月初に使い切って月末に困る事態を自分で避けられる、と説明。
2. プロンプトを実行する（サプライヤーに関する内容のようでした）。
3. `/cost` を実行すると、そのタスク（セッション）で使ったクレジット数が分かる。会場で実行経験のある人は約半分だったため、「家に帰ったら実行してみてください」と宿題にしていた。
4. 使用状況を掘り下げると、引き出せる複数の支出ポリシーまたは予算が表示される。この時点で残りは 21%。
5. 課金が使用量ベースの各製品（autopilot、code、cowork など）にわたって、時間軸で使用量を確認できる。Ryan 氏は、チャットで高度なモデルをかなり使っていたことが見て取れたと話している。
6. 棒グラフをクリックすると、その日の Cowork セッションごとに消費したクレジット数を確認できる。

### 6.2 Copilot Studio — メーカー視点（Ryan 氏）

1. 請求処理（claims processing）エージェントを開く。ユーザーが請求を提出すると処理するエージェント。
2. 車のホイールの曲がりについて助けを求めるテストを実行する。情報をあまり渡していなかったため、エージェントは助けられなかった。
3. 画面の上隅に、このやり取りで **9 クレジット** かかったことが表示されている。掘り下げると、時間経過に伴う消費が見え、エージェントの変更がコストを増減させているかを把握できる。
4. 評価（evals）の結果にもコストが表示される。評価セット全体の実行に **454 クレジット** かかっていた。評価セットから個々の質問に掘り下げると、1 つの質問への回答で **8 クレジット** を消費していた。
5. これにより、エージェントを変更していく中で、クレジット消費が改善しているか悪化しているかを継続的に把握できる。

### 6.3 Microsoft Admin Center / Agent 365 — IT 管理者視点（Ryan 氏）

1. Microsoft Admin Center を開く。上限に近づいている支出ポリシー、上限に近づいているユーザー、エージェントごとのコストと価値の比率などのサマリーが表示される。
2. consumption から、特定のユーザーやグループへ掘り下げる。Ryan という名前のユーザーを選択（「名前が気に入っているので」と説明）。Copilot アプリで見たのと同じ使用状況と消費（burn rate）の推移が見えるが、ここでは Copilot credits でなくドルで表示される。
3. そのユーザーの、すべてのエージェント、製品、サービスにまたがる消費を見る（「その 60 ドルがどこから来たのか」が分かる、という説明）。モデル別でも掘り下げられ、モデルの構成が時間とともにどう変わるかが分かる。Chat や Cowork の auto と、ユーザーが明示的に選ぶモデルが支出に与える影響を理解するのに役立つと説明。
4. 支出ポリシーを作成する（財務部門向けを想定したが、画面に財務のグループがなかったため、「formulation」というグループを代わりに使う、と断っている）。
   1. 対象者を決める。entre security group を選ぶパターンを実演。別のパターンとして、agent registry から特定のエージェントを選べることも説明。
   2. 消費できる製品を決める（既定値のセットがあり、誰が何を使えるかを完全に制御できる）。
   3. 支出上限を設定する。2 段階で、部門全体の上限（例として 200,000 ドル）と、一人がバジェットを使い切らないようにする 1 ユーザー当たりの上限。
   4. アラートを設定する。ポリシー全体の上限に近づいたとき（例として 90%）と、個人の上限の 90% に達したとき、特定の人に通知する。
   5. モデルファミリーを制限する。Fable というモデル名（音声認識の都合で表記が確定できません）を例に挙げ、これは formulation のチームには高価すぎるので、それ以外のすべてを使えるようにする、という例。ニュースで読んで試したくなり、月の最初の週にクレジットを使い切ってしまう確率を下げられると説明している。
   6. 「誰が支払うか」を選ぶ。テナント内の前払いの capacity pack を消費するか、部門にチャージバックする場合は、その部門のコストセンターに紐づけ済みの Azure サブスクリプションを選ぶ。既存の Azure のチャージバックの仕組みにそのまま接続できると説明。
5. 権限委任を実演する。research 部門に委任し、Morgan という担当者にフル委任の権限（ポリシー作成と、さらに他の人への委任）を与える。上限は 350,000 ドル。委任した後も、選べる Azure サブスクリプション、含められるサービス、使えるモデルプロファイルにガードレールを設定できる。IT と事業部門の間の「伝言ゲーム」をなくす狙い。

### 6.4 Agent 365 Business Analytics アプリ — 部門リーダーとアナリスト視点（Avinash 氏）

デモは、Ryan 氏が委任した 350,000 ドルの予算を持つ R&D operations リーダーが、ポリシー適用から数か月後に初めてログインした、という設定で進みます。

1. アプリを開くと、画面は自動的に自組織に絞り込まれている。組織情報がそろっていて、掘り下げられる。
2. 「cost and forecast」から始める。月初から 11 月 17 日までの表示で、組織のコストは約 227,000 ドル（予算 350,000 ドルに対して妥当）。今月の予測は約 335,000 ドルで、予算内。
3. どのサービスとモデルがコストを動かしているかを、鳥瞰するビジュアルで確認する。960 人の組織で Cowork が最大で、支出の約 40%。GitHub やその他のエージェントも大きい。モデル別の配分も見られる。
4. 「Cowork を何に使っているのか」を知るため、use cases タブに進む。コスト順に並べると、R&D 部門らしく大部分が research and discovery に分類される。ドメインからユースケースまで階層をたどれる。
5. コスト順の最上位は、statistical analysis planning。約 1,800 ドルが 369 セッションに使われており、1 回あたりおよそ 5 ドル。
6. その横にある AI value の電卓アイコンから、5.6 の計算の内訳を確認する。工数や賃金率を調整できる。Cowork に 80,000 ドルかかった作業が、少なくとも 185,000 ドルの価値を生んでいるという結果。
7. ユースケースを ROI の高い順・低い順に並べると、ROI の高いユースケースと低いユースケースが分かり、利用者への啓発の基礎になる。さらに下に、グループ別、モデル別、サービス別のヒートマップや、上位 1% のユーザーの行動などの高度なツールがある。
8. users and groups で、アクティブユーザー 770 人（960 人中）、上位 5% が 49% のコストを占めることを確認する。上位ユーザーをクリックして、組み込み済みのアンケートで声を集める。アンケートは 11 月 26 日に締め切られ、結果がアプリに戻る。上位 5% がどのグループ、職種に集中しているかも分かり、上限に達している、または近づいているユーザーも見える。
9. cost and forecast タブに戻る。現在の消費ペースだと 11 月は問題ないが、1 月から予算を超えることが分かる。要因を見ると、Opus と Astra のモデル（音声認識の都合で表記が確定できません）が強力な一方で高価で、コスト増の大きな部分を占めている。
10. model mix のレバーで、この 2 つのモデルのコストを 5% まで下げ、残りに配分して再予測する。Avinash 氏は、上位モデルを制限すればコストが下がるのは当たり前で洞察ではないと述べ、変更の前に、この予測のスニペットを自分の Lt. team や Chief of Staff に送り、小さなパイロットで実現可能かの確認を依頼する。
11. 数週間後に「その案は良くない。代わりに、支出の大きいグループにはもっと厳しい上限を設け、同じグループ内の 20 人の特別プロジェクトには大幅に高い上限を設けるべき」という回答が返ってきた、という仮定でデモを続ける。
12. 委任を受けているので、IT に頼まずにポリシーを自分で変更する。画面は IT 管理者が見たものと同じ UI が、委任されたポリシーの範囲に絞って埋め込まれている。該当ユーザーに 500 ドルの上限をかけ、他は変更しない。
13. 秘密のプロジェクト「Nova」のためのセキュリティグループを選び、他より多めに、すべてのモデルへのアクセスを与える。請求ポリシーを確認して完了する。
14. 継続的な監視のために、transformation office のアナリスト、Chief of Staff、プログラム管理のリードを代理人（delegate）に指名すればよい、と説明。
15. ここからアナリスト視点に切り替える。service deep dive で GitHub を選び、成熟度別の利用者分類と PR 指標の結果を確認する（5.8 のとおり）。
16. agent registry でエージェントのランキングを見る。人気のある protocol drafting エージェントをクリックし、メタデータ、説明、作成者、プラットフォーム、セッション数、コスト、ユースケースを見る。
17. interactive insights で、「過去 6 か月でどう変わったか」を質問する。回答には、Cowork が伸びていること、どのグループがどれだけ伸びたか、7 月から 11 月までのウォーターフォール図が含まれる。セッション数の増加によるコスト増、auto モードを使うか手動でモデルを選ぶか、より安いモデルを選んでいるかといった観点も示される。
18. この分析を PowerPoint に変換し、使いたいスライドを選べる。
19. reports で Copilot Business Impact report のテンプレートを使う。ビジネス KPI を設定してレポートを作ると、KPI と Cowork の利用を関連づけられる。パワーユーザーが案件の勝率（win rate）で実際に良い成績を出しているかを確認できる。
20. KPI で成果を上げ、かつ利用も多い人たちが Cowork を何に使っているかを task insights で見ると、顧客との会議の準備、担当アカウントに関するリサーチ（他の人より多い）、フォローアップのドラフトに使っていた。これを営業リーダーに持ち込める、という例。
21. 最後にエクスポート機能を見せる（5.8 を参照）。

## 7. 注意点・発表者の気付き

- **サプライズ請求は避けられる。** 予算と支出ポリシーの設定画面には、上限を設けるか無制限にするかを選ぶラジオボタンがあります。Ryan 氏が最も持ち帰ってほしいと述べた点です。
- **エンドユーザーは意外にクレジットを気にする。** 当初は関心を持たないと想定していましたが、有限の資源であるため非常に気にする、と Ryan 氏は述べています。
- **評価（evals）を作っている人が少ない。** 会場でエージェントの evals を作ったことのある人を尋ね、手を挙げた人は「全然足りない」と Ryan 氏は述べています。evals は品質だけでなく、ユースケースを広く動かしたときのコストを把握するのにも使えます。
- **上位ユーザーへの集中は問題ではない。** 上位 5% が 49% を占めるのは典型的で、むしろ知見を集めるべき相手だと述べています。
- **予測は「計算」であって「洞察」ではない。** モデルを制限すればコストが下がるのは当然で、変更の前に現場への確認（パイロット）をすべきだという流れで説明しています。
- **電卓の既定値は目安。** いくつかのユースケースでは工数の既定値がかなり保守的で、実際の感覚と違う場合は変更できると説明しています。
- **今回のデモは「ハッピーパス」。** Avinash 氏自身が、質問をしたので答えが出る形で見せたと断っています。実際のアナリストは、既成の画面では答えが出ない鋭い質問や抽象的な質問を受けるため、Interactive insights や Reports があるという位置づけです。
- **対応範囲の制約。** Foundry サブスクリプションへの支出ポリシー適用は「来年の初め」とのことです。Microsoft 以外の支出を見るには A365 の connected platforms への登録が必要です。分類の対象外となる個人用途や失敗したセッションもあります。
- **音声認識の都合で確定できない固有名詞。** モデル名（Fable、Opus、Astra）、「formulation」、「entre security group」、「dimming cycle」は、聞こえた綴りのまま記載しています。

## 8. 利用者にとっての利点

発表で語られた効果や利点は次のとおりです。

- 利用者自身が使用量と残量を見て、月内の使い方を調整できる。
- メーカーは、エージェントの変更によるコストの増減を、評価セット単位でも質問単位でも把握できる。
- IT は、ドル建て（交渉済みレートカード）で、ユーザー、エージェント、製品、モデルの切り口からコストを把握できる。
- 支出ポリシーで、対象者、製品、モデル、上限、アラート、支払い元を制御できる。上限は Microsoft のファーストパーティのプラットフォームで強制されるため、想定外の請求を避けられる。
- 既存の Azure のチャージバックに接続できる。
- 事業部門のリーダーに権限を委任することで、IT と事業の間の「伝言ゲーム」をなくせる。
- Cowork の使われ方をユースケース単位で把握し、コストと見積もり価値を比較して、ROI の高い領域と低い領域を見分けられる。
- 将来コストの予測とシナリオ計画で、予算超過の時期（デモでは 1 月）を事前に把握できる。
- すべてのデータをエクスポートし、Fabric、Power BI、MCP エンドポイントに接続できる。

顧客事例としての具体的な成果の紹介はなく、数字はすべてデモ用の組織のものです。ただし、「上位 5% がコストの約半分を占める」傾向は、Microsoft 社内と複数の顧客で見られると述べています。
