# BRK543 Scott and Mark learn to... live again

## 1. はじめに

このセッションは、Microsoft の Mark Russinovich 氏と Scott Hanselman 氏が、掛け合いの形式で進める講演です。AI によって「ソフトウェアを作るコスト」が急激に下がった今、開発者はどう判断力（judgment）を保ち、次の世代の技術者をどう育てるかを、自分たちが実際に作ったツールを見せながら語ります。

流れは、(1) 安く作れるようになったことの実例、(2) 「プラットフォームとは何か」という議論、(3) 判断力とは何か、(4) 判断力を育てることの課題と対策、の順です。結論として 2 人は、**人間の判断（と注意力）がボトルネックになった**ことと、そのために経験の浅い技術者を育てる仕組みが要ることを訴えています。

> 補足：トランスクリプトには Mark 氏と Scott 氏の話者ラベルがあります。ただしラベルは発言者が切り替わる箇所にしか付かないため、連続した長い発言では誰の言葉か確定できない部分があります。そうした箇所は「登壇者」と書いています。また、固有名詞（プロジェクト名やモデル名）には音声認識の誤りが疑われるものが多く、本資料では聞こえた綴りに注記を付けています。

## 3. 何に関する発表か

セッションの概要は、AI が「ソフトウェアを作る速さ」だけでなく、「知能がどこで動くか」「開発者がどれだけ制御を保てるか」を変えている、というものです。2 人は、フロンティアモデル、ローカルでのプライベートな推論、エージェント型コーディング、自律システムの限界を、率直な議論と実演で扱うとしています。

Mark 氏が冒頭で示した構成は次のとおりです。

1. ソフトウェアの制作が安くなったことと、エージェント型コーディングで作ったもの
2. プラットフォームとは何か、拡張するとはどういうことか
3. あらゆるツールの利用に必要な「判断力」
4. 判断力はどこから来るのか
5. AI が代わりにやってくれる世界で、判断力を育てることの問題にどう対処するか

## 4. 発表者が伝えたいメッセージ

発表を通した主張は次のとおりです。

**作るのは安くなったが、出荷には判断が要る。** Scott 氏は、10 億人が頼りにするものを出すことと、ただ何かを作ることは全く別だと述べています。1 週間で作れても、10 億人が頼る信頼性は別の話です。

**「1 回で作れた」は多くの場合、面白い問題ではない。** Scott 氏の「やや辛口の意見」として、vibe で 1 回で作れるなら、おそらくそれは興味深い問題ではない、という発言があります。Mark 氏も賛同しています。

**ボトルネックは人間の注意力と合意形成。** AI がコードを生成するほど、レビューや承認に人間の注意が必要になります。さらにチームをまたぐ合意が、最も大きな遅れになるという見方です。

**経験が増幅される。** 専門性や「taste」が高いほど AI から得られるものは大きくなります。そのため、経験の浅い人を育てる仕組みが急務だというのが、後半の中心的な主張です。

## 5. 発表内容の詳細

### 5.1 導入：今は異様な時期

2 人はまず、「作ることが安くなった（Creation is cheap）」という Satya 氏の発言に触れています。Mark 氏は「足元が揺れている感覚がある」と述べ、会場にも同じ感覚があるか尋ねました。大きな転機は昨年秋で、Opus の 4.5 か 4.6（Mark 氏は番号を覚えていないと述べています）が登場し、エージェント型コーディングが一気に強力になった、と振り返っています。年末年始には皆が vibe coding をしていた、とも述べています。

Scott 氏は、アセンブラから C、IntelliSense、オンプレミスからクラウドなど、これまでにも「パニックの時期」があったことに触れつつ、今回は違うのではないかという怖さも率直に認めています。

続けて登壇者は、SNS では「token maxing」を叫ぶ声があるが健全だとは思わない、AI で何を作るかは慎重に考えるべきだと述べました。また、これまでの 80/20 の法則（作業の 80% は労力の 20% でできる）はもう当てはまらず、今は**作業の 80% が労力の 2% でできる**感覚だと言います。そこで問題は、「slop cannon」から vibe coder、そして品質の高い本番コードを出せる agentic software engineer になるにはどうするかだ、としています（この部分は、話者ラベル上は Mark 氏の発言として続いており、発言者を確定できません）。

### 5.2 作ったもの 1：decision model と Venn

Mark 氏が最初に紹介したのは、約 6 週間前に突然登場した decision model です。聞こえた名前は「Jev」で、TypeSafe という会社（聞こえた綴り）が出したと説明しています。名前や会社名は音声認識の都合で確定できません。

- LLM を、質問に対する回答の候補から答えを選ぶように学習させたもの。「X の確率はこれ、Y の確率はこれ」と返す。
- 「System 1（速い、直感的な反応）」にあたる AI。深く考える LLM は System 2 にあたる。この概念は 1970 年代後半の本に由来すると Scott 氏が説明している。出力は yes/no のような列挙型（enum や bool）で、強い型付けがある。
- 確定的で頼れる答えを返し、モデルに長く考えさせるより**はるかに経済的で速い**。Mark 氏は「桁違い」「数セントと数十ドルの違い」、Scott 氏は「100 倍、1,000 倍速く、1 セント未満」と述べている。
- 例として、チケットの分類やスパム判定のように、LLM では英語の応答をパースする手間があるが、本来は enum を返せばよい場面を挙げている（Scott 氏は Luna のような安価な LLM も例に出している）。

2 週間ほど前の日曜の朝（Mark 氏の記憶による）、Mark 氏は AI ニュースレターで Google の **Gemma Embedding 2** を知りました。embedding は、テキスト、画像、音声から多次元ベクトルを作り、類似性などを比べられるモデルです（king と queen の例を使って説明）。そこで「テキストの代わりに embedding を入力にした decision model」を思いつきます。embedding なら履歴から学べる、つまり、似た embedding でこれまで良い決定をしていれば、同じ決定を繰り返せる、というのが狙いです。

このプロジェクトの名前は、聞こえた綴りで「Venn」です（トランスクリプトには「Ben」と聞こえる箇所もあり、音声認識の都合で確定できません）。Scott 氏の説明では、RAG などですでに作ってある embedding の上に、decision model 互換の「ヘッド」を載せたものです。

デモ（6.1）では、TypeSafe が decision model の例として出した **Doom** のプレイを、embedding ベースで再現しました。

Mark 氏が強調した 2 点があります。

1. TypeSafe 自身の例の一部では、元の decision model より Venn のほうが良い結果を出した。embedding にすると、過去の分類の判断から、より豊かな情報を取り出せるため。
2. プロジェクトページにあるものすべて（動画、例、ドキュメントを含む）が、**日曜から日曜までの 1 週間、本業ではなく空き時間**で、エージェント型 AI を使って完成した。以前なら数か月かかるので、試そうとも思わなかったはずだと述べている。

Scott 氏は、Mark 氏がこれを 10 日間夢中で作っていたと補足し、「自分で調べて下働きをして、そこに人間の部分を足す」ことの大切さを語りました。「vibe で研究論文は書けない」という言い方もしています。

### 5.3 作ったもの 2：Haptics Anywhere（Scott 氏）

Scott 氏は、Windows の新しい触覚マウスや、触覚タッチパッドを持つノート PC、触覚のある Surface Pen を挙げました。触覚（haptics）は単に振動するだけではなく、波形を再生して異なる感触を出せます。Windows には API があるものの、サードパーティが呼ぶ必要があります。

そこで「逆にして、画面で起きていることを見て Windows 自身が API を呼べばどうか」と考え、**Haptics Anywhere** を作りました。所要時間は「たしか約 6 時間」です。画面上の要素の上を移動すると、マウスが「ぶつかる」ような感触を返す「visual haptics」で、Mark 氏は「試したが面白い」と述べています。

この考えは、マウスを作ったチームに持ち込み、チームでブレインストーミング中で、PowerToys に入るかもしれないとのことです。Scott 氏は、コードの大半は DLL インポートなどの定型作業で、自分で書けば手間とコピー＆ペーストのミスで途中で飽きたはずだと述べています。Mark 氏は、システム系の仕事でずっとそうした作業をしてきて「PTSD がある」と応じています。

2 つのプロジェクトは、どちらも GitHub に公開されているとのことです。

### 5.4 プラットフォームとしての Windows と、「10 億台に出荷するのか」

Scott 氏は、どちらのツールも Windows 上で作ったと述べ（自身は Surface Laptop Ultra を使用）、OS とは「API の遊び場」だと説明します。実験的な API もあり、バージョンやライブラリ、ハードウェアの有無を確認しながら作ったそうです。そこで「1 週間で作れるなら、10 億人に出荷すればよいのでは」と問いかけます。

その例として、他の人が作った **Deskland** が示されました（6.2）。Scott 氏によれば、ある若い人が vibe coding で作ったデスクトップのアプリで、「その努力を貶めたくない」と敬意を示しつつ、次のように述べています。

- 内部では、署名のない DLL を Explorer.exe に直接注入するなど「革新的な」ことをしている。
- Scott 氏自身、昼食前に Windows Defender に 3 回、問題ないと伝える必要があった。
- 「これを 10 億台に出荷してよいのか。おそらくそうではない」と述べている。

Start メニューについても、「1 分で vibe した」という声に対し、Mark 氏が実際に作ったのが **SemanticStart** です（6.3）。Mark 氏の動機は、sysinternals のツールを Start メニューから探すと、インストール済みでも Process Explorer が見つからないことでした（WinGet や Microsoft Store から入れた場合を含む）。

Scott 氏は、Mark 氏が Wikipedia を参照して各ユーティリティの内容を「補強（enrich）」していることを指摘し、10 億人向けには出せない部分だと述べました。Mark 氏も、Windows の評判を損なう恐れ（誤情報や有害な情報を取り込むなど）を挙げ、**自分や使いたい人には問題なくても、信頼性を期待される 10 億人のプラットフォームでは、信頼できない情報源に頼れない**と説明しています。

Scott 氏の 3 つ目の例が **GPU Taskman** です（6.4）。Task Manager で、GPU メモリが誰に使われているかが分からないため作ったもので、そこから次の点を挙げています。

- プロセスの引数などから推論（heuristics）している。Mark 氏は「コマンドラインが変わったり、モデル名に文字が足されたりしただけで壊れる」と補足した。
- 自分の PC では動いても、他の人の環境（Intel、ARM、特定の ARM GPU など）では異なる。要望の PR が多く寄せられ、「nerd-sniped」されている。
- そのため、GPU Taskman を出荷すると、もぐらたたきを一生続けることになる。

Mark 氏は、Windows はプラットフォームであり、API の層の上に自分たちの UX を載せたと述べました。SaaS なども同じ方向に向かっており、「API の層を顧客がカスタム体験を作るために提供する」ことが将来の姿だと言います。Scott 氏は、「Windows はなぜこれを出荷しないのか」ではなく、「やりたいことに必要な API を Windows は提供しているか」と問うべきだとし、サンドボックスとして MXC や Windows Sandbox にも触れました。

### 5.5 判断力はどこから来るのか：Agent Session Insights

Scott 氏は「vibes と 1 回の生成（one shot）で作ったのか」と問い、自分たちは「何度も何度も（many shots）」だったと答えます。Mark 氏は、彫刻のように、全体の形から始めて少しずつ削っていくのがいつもの作り方だと説明しました。続けて Scott 氏は、TikTok で一度発言して散々な反応を受け動画を隠したという「辛口の意見」を紹介します。1 回の vibe で作れるなら、それは興味深い問題ではなかった、という主張です。

Mark 氏は、Venn のために、どこで自分が判断を下したか、時間とコストがどのくらいかかったかを知りたくなり、セッションを分析するツール **Agent Sessions Insights** を作りました（GitHub に公開）。Claude、GitHub Copilot、Codex など複数のエージェントのセッションを横断して取り込み、再生（Scott 氏は TiVo にたとえています）しながら、AI が判断が入ったポイントを分析します（6.5）。

Scott 氏は、GPU Taskman を次の規模で作ったと述べています。

| 項目 | 数値 |
| --- | --- |
| セッション数 | 16 |
| 期間 | 約 2 週間（実時間で 16 日） |
| ターン数 | 101（「one-shot」ではなく「101-shot」） |
| 実際に作業した時間 | 約 6 時間 |
| コスト | 140 ドル |

使ったモデルの内訳も確認できます。Scott 氏は、GitHub Fusion（聞こえた綴り）や安価なモデルも使い、必要なときに Astra（聞こえた綴り）で少し費用をかけたと述べ、「すべてにフロンティアモデルは要らない」と言っています。インタラクティブなセッション再生は Scott 氏のアイデアで、時間帯も分かります。Scott 氏は、評価システムを持つ Hyperhat（hyperhat.com、聞こえた綴り）という会社の再生機能に触発されたと説明しています。

セッションの中の例として、Scott 氏は、エージェントに「単純なトリアージを複雑にしすぎている」と指摘し、エージェントが行き過ぎを認めた場面を紹介しました。もう一つは、電力制限の挙動が本当かを証明するようエージェントに求めた場面で、約 45 セントかかったとのことです。

Scott 氏は、これはメタ認知（自分の考え方を考えること）だと述べ、このレポートは**完全にローカルで、プライベート**だと説明しました。

GitHub Copilot では **`/chronicle`** を実行すると、同様のインサイトや、コスト削減のヒントが Copilot CLI と Copilot App の両方で得られるとのことです。ローカルにプライベートな SQL データベースを作り、「何時ごろに自分の作業が崩れるか」なども調べられ、Scott 氏は「午前 2 時ごろには離れたほうがよい」と言われた、と述べています。

### 5.6 注意力と判断のボトルネック、Agent Review

コード生成が増えるほど、人間の注意力が制約になります。Mark 氏は、Scott 氏に届く大量の PR を例に、AI の出した結果を見て「OK」と押すことにも注意力が必要だと述べています。注意は、ほぼ常に何らかの決定（問題ないか、直すか、承認するか、もっと学ぶか）に向けられ、良い決定の鍵は**良いコンテキスト**だと述べました。Scott 氏は、自分には 40 年分のコンテキストウィンドウがあり、100 万トークンより大きいと冗談めかして述べ、だからこそ他の人にも知識を身に付け、業界に長く残ってほしいと語っています。

そこで Mark 氏が作ったのが **Agent Review** です（6.6）。Scott 氏は、Mark 氏を GitHub Copilot app（セッションのマルチプレクサ）へ誘っていたが、右側に canvas を置けると分かって、Mark 氏が独自の UI を作ったと説明しています。Mark 氏は、エージェントが数万行のコードを生成し多くの関数を変更するとき、チャットで往復して聞くのではなく、「重要なところを教えてほしい」のが目的だと述べています。

Agent Review は、近いうちに公開リポジトリで出す予定ですが、現在はベータテスト中とのことです。

### 5.7 合意形成のボトルネック

Mark 氏は、Microsoft で毎日見ている状況として、パイプラインの一部は AI で大幅に速くなる一方で、他チームとの調整や優先順位の確認で数日から数週間の人間による遅れが生じると述べました。実作業は AI に任せれば数日なのに、合意に数週間かかる、という例です。**エージェントによる加速の根本的なボトルネックは、人間の合意形成**だという見方です。

少人数（3 人と述べています）で 1 億ドル規模の製品を作る「AI ネイティブな会社」は、既存の顧客や後方互換性、合意形成がないので高速に動けるが、数年成功すれば同じく合意形成で身動きが取れなくなるだろう、とも述べています。Mark 氏は、Agent Review のようなツールで文脈を集め、異なる立場や優先順位を代表するエージェント同士に協調させ、人間が加わるときには情報がそろっている状態にすることが「次のフロンティア」だと述べました。

Scott 氏は、そうして「エージェントの群れ」でコードを作ると、合意形成の壁の次に、人間の判断力の壁に当たる、と続けます。

### 5.8 判断力と経験：ジュニアの育成

Mark 氏は、自分たちの数十年のソフトウェア・エンジニアリングの専門性があるから、ツールを効果的に使えると述べています。経験や taste が多いほど AI は**増幅器**として働き、10 の人は 100 に、3 の人は 30 になるという例えです。その結果、AI の影響を受ける職種全般で、ツールを最も効果的に使えるシニアを採用・維持する方向に偏っている、との見方です。

Scott 氏は、採用のパイプラインが落ち込むことを心配しています。シニアを育てなければ、競合から採用するしかありません。そこで、早期キャリアの採用を倍増、三倍増すべきだとしています。

Mark 氏が示した根拠は次の 2 つです。

| 根拠 | 内容（発表で述べられたとおり） |
| --- | --- |
| Stanford の経済学の研究「Canaries in the Coal Mine」 | AI の影響を受ける職種ではシニア採用が下がり、ジュニアとシニアの間に 13% の差（聞き取りが不明瞭）。AI の影響を受けない職種ではジュニア採用の減少は見られない |
| Anthropic が数週間前に公開した、自社採用への AI の影響 | 昨年は従業員の 3 人に 1 人が卒業間もないジュニアだったが、今年は 10 人に 1 人 |

Mark 氏は、研究に対しては「問題がある」という声もあったと述べ、Anthropic のデータをその具体的な証拠として挙げています。

Scott 氏は、Communications of the ACM に、ジュニアのパイプラインの空洞化（hollowing out）についての論文を書いたと述べ、残りの職業人生をこの問題の解決に捧げると語っています。Carnegie Mellon の人々とも協力しています。業界では早期キャリアの採用が行われておらず、AI ラボでは特に大きく落ち込んでいる、とも述べました。自分がシニアになれたのは、賢い人たちが時間を割いて付き合ってくれたからで、ツールもチームも若手を育てる必要があるという考えです。AI はシニアを後押しする一方、経験の浅い人の学習を遅らせ、コードを理解する脳の形成に影響して習熟が浅くなる、と述べ、学校では宿題の成績が良く、テストの成績が悪い子どもが増えているが、「大人であることはテストの連続」だという例を挙げました。Mark 氏も、Venn では学んだが、自分でコードを書いたときほど深くは学べなかっただろうと述べ、**脳が痛くなるほど考えることが学びと定着につながる**ため、意識的に「ジムに行く」ことが必要だと言います。Scott 氏は、筋肉は負荷がかかっている時間で育つ、と続けました。

### 5.9 対策：Preceptor プログラムと CMU との提携

Scott 氏は、従来の Tech Lead の役割（プロジェクトを出荷するために若手を集める）に加えて、看護や医療にある仕組みのように、プロジェクトを出荷する Tech Lead と、**シニア・エンジニアを育てるのが仕事の preceptor** を置く案を紹介しました。Preceptor は PR やユーザーストーリー、プロジェクトの成否ではなく、若手が「taste」を身に付けたかどうかで評価されます。目標は、若手に頭が痛くなるほど考えさせることです。

Mark 氏によると、この仕組みはすでに Microsoft で始まっています。

| 項目 | 内容 |
| --- | --- |
| 試験運用 | 春に Azure Core で、約 15 人の preceptee と 13 人の preceptor |
| 結果 | preceptor と preceptee の双方が気に入った。preceptee の上司は、preceptee の書いたコードのほうが、そうでないグループよりセキュアで信頼性が高いと評価した。AI を使う頻度が、週あたり約 1 日分多かった |

さらに Scott 氏は、Carnegie Mellon（CMU）との提携を紹介しました。学校で学んだプログラミング言語や OS はすべて廃れたが、学校では「学び方」を学んだ、という経験から、就職後も仕事を通じた学びが続くと考えています。そこで、preceptorship の一部として、若手が修士号に向かう「degree shards（学位の一部）」を受けられ、費用は Microsoft の研修予算から支払われます。学校と産業界が組む形は、従来のインターンや徒弟制度より強力だろうと述べています。

Preceptor は、教え方を学んだ正式なトレーナーです。教えることに向いている人を見つけ、教育学を教え、**シニアを育てて会社に残すことが仕事**になる、と説明しました。

## 6. デモ・手順

このセッションにはデモがあります。ただし録音は音声のみのため、画面の細部は確認できません。以下は、語られた範囲を、語られた順に整理したものです。いずれも各自が作ったツールの実演と紹介で、手順を追う形式のチュートリアルではありません。

### 6.1 Venn による Doom のプレイ（Mark 氏）

1. TypeSafe が decision model の例として Doom を遊ばせたため、同じことを試すと説明し、Mark 氏がセットアップして再生を始める（コンピューターの音楽が流れる）。
2. 説明によると、これは強化学習で、画面の画像の embedding を見て判断し、その結果を記録しながら学ぶ。たとえば「この画面なら右を向く」「この画面なら撃つ」が、ラウンドに勝つために良いと学ぶ。
3. 同じ API で多数のシミュレーションを回し、カスタムの「ヘッド」を訓練して、embedding から正しい動きを学ぶ。ランダムに撃つ場合や、画像だけを見る場合よりずっと良くなる。
4. 映像はスローで再生され、decision model の答えが表示され、正しい判断に至る例が示された。
5. Scott 氏の補足：スクリーンショットを LLM に渡して 100 ドルを使う方法は無駄でツールが合っていない。画面で起きていることを JSON のテキストにして送り、enum（左、右、撃つなど）を返してもらえば、1 セント未満でできる。

### 6.2 Deskland（Scott 氏、他の人が作ったアプリ）

1. Scott 氏が自分の PC のデスクトップを示す。小さなキャラクターを持ち上げて移動すると、雲が避ける。アイコンを動かすこともできる。
2. Mark 氏が「凧を揚げている人の下にアイコンを移動したらどうなるか」と提案する。Scott 氏が忍者を移すと、その下に隠れて影が付き、やがて歩いて抜け出す。別のものを選ぶこともできる（Mark 氏は「islands」と述べている）。
3. このあと、署名のない DLL を Explorer.exe に注入していることや、Defender への対応を話題にして、「10 億台に出荷してよいのか」という議論につなげる。

### 6.3 SemanticStart（Mark 氏）

1. SemanticStart は、システム内のインストール済みのものを幅広くスキャンする。Windows インストーラー以外で入ったもの、PATH 上のもの、Start メニュー、WinGet のインストール済みパッケージ、PowerToys などが対象。
2. 「memory」と入力すると、タイトルに含まれていないものも含めて関連するツールが見つかる。
3. 仕組みは、collectors（場所ごとに見つける。PowerToys 用の collector など）と、enrichers（見つけたものに情報を足す）。enrichers は、PE ファイルのバージョン、MSIX マニフェスト、ショートカット、ローカルのドキュメント、メニュー項目のテキストを取得し、Wikipedia も参照する。
4. Scott 氏が、「pivot table」と入力すると、メニューにその語がある Excel が見つかると説明した。Mark 氏は「試したことがない」と答え、Scott 氏が「昨日そう言っていた」と返すと、Mark 氏は「嘘だった」と述べ、2 人が声を上げ、会場から拍手が起きた（画面の細部は音声からは分かりません）。
5. そのあと、Wikipedia などの信頼できない情報源に頼ることの問題（5.4）を話した。

### 6.4 GPU Taskman（Scott 氏）

1. Task Manager を開く。Surface Laptop Ultra で、GPU メモリは約 80GB。Scott 氏は「Taskman を怒らせた」と述べ、何かの異常動作があったようだが、内容は音声からは分からない。
2. 「GitHub apps」（聞こえた表現）から、MAI Code Flash（または Flint。聞こえた綴り）を GPU に載せる。70GB 分ほどを読み込む。
3. Task Manager では、GPU メモリを誰が使っているか分からないため、自作の GPU Taskman を使う。プロセスと、そのプロセスの中で AI がどんな処理をしているかが表示される。
4. 画面では、Llama Server が「Flint」という 400 億パラメーター（聞こえた表現は 40-billion-parameter）のモデルを読み込んでいる。
5. 「how do I know what I know（なぜそう分かるのか）」を説明する項目もある。プロセスのパラメーターを調べて推論しているため、コマンドラインの変更などで壊れる、という説明（5.4）。

### 6.5 Agent Sessions Insights（Mark 氏と Scott 氏）

1. GPU Taskman の開発を、16 セッション、2 週間、複数リリース、ニッチなハードウェア、ローカライズなどとして概観する。
2. 101 ターン、実時間 16 日、実作業約 6 時間、コスト 140 ドルが表示される（5.5 の表）。
3. モデルごとの使用状況とコストが表示される。
4. 「Interactive session playback」で、時間帯ごとの作業の様子が見える（Scott 氏のアイデア）。判断が入った地点（例として番号 45 など）をたどる。
5. 紹介された例：エージェントに「複雑にしすぎている」と指摘した場面、電力制限の挙動を証明させた場面（45 セント）。

### 6.6 Agent Review（Mark 氏と Scott 氏）

1. GitHub Copilot app の左側は Copilot、右側は Mark 氏の canvas。「Maximize Panel」で、アプリの特定の部分のレビューを表示する。
2. 変更されたアーキテクチャ上のつながり（edges）が見える。そこからアプリのレビューを開始できる。
3. 変更はレイヤーとテストなど、影響を受けたものごとに分解されている。PR を取り込んだ場合の影響や関数の位置も確認でき、UML 図のようなものが生成される。Scott 氏は「ホワイトボードが生成された」と述べている。
4. diff を読むだけでなく、リスクが低い理由などの小さな文脈情報が付く。
5. 関数については、コードからセッション履歴に移動して、思考型モデルなら書いているときの思考も見られる。呼び出し元や依存関係も確認でき、プロジェクト全体が依存している部分は時間をかけて見る、という判断ができる。
6. レイヤーごとに順に見ていく。RustAdapter から Python に入る箇所では、Copilot が説明を生成する（just-in-time の AI 生成による grounding）。「どう検証されたか」「それが本当だと言える根拠は何か」を、テストとともに確認できる。Scott 氏は、Copilot に聞いて賢くなる使い方を勧めている。
7. レビューが済んだ項目に「reviewed」の印を付けて次に進む。Scott 氏は「コードの読み方が完全に変わる」と述べている。多くのコーディングツールは diff を見せるだけだが、これは diff を使って学べるようにする、という説明。

## 7. 注意点・発表者の気付き

- **ベータ版のもの。** Agent Review は、まだベータテスト中です。公開リポジトリは近日予定です。
- **ローカルのヒューリスティックは壊れやすい。** GPU Taskman はコマンドラインの変化などで壊れ、環境ごとの要望（Intel、ARM など）に追われると説明されました。
- **信頼できない情報源に頼ると評判を損なう。** SemanticStart の Wikipedia による補強が、10 億人向けに出せない理由として挙げられました。
- **Deskland は Defender との相性が悪い。** 署名のない DLL を Explorer.exe に注入する作りのため、Scott 氏は Defender に「問題ない」と 3 回伝える必要があったと語っています。
- **コストも見る。** 140 ドルのように、実際の費用を可視化することが大切だと述べられました。すべてにフロンティアモデルは不要で、安価なモデルで十分な場面もあるという話でした。
- **AI で学びが浅くなる。** 子どもの宿題と試験の例や、Mark 氏自身が Venn で得た学びが浅いという自覚が挙げられました。

## 8. 利用者にとっての利点

このセッションは、製品の紹介ではなく、開発者と組織に向けた経験談と提案です。語られた効果や成果は次のとおりです。

- 以前なら数か月かかるプロジェクトが、Mark 氏の場合は空き時間の 1 週間で完成した。
- Haptics Anywhere は約 6 時間で作れた。
- decision model は、LLM に比べて桁違いに速く安い。
- Agent Sessions Insights や `/chronicle` により、判断の分岐点、時間帯、モデルごとのコストを振り返れる。
- Agent Review は、重要な変更点、影響範囲、リスクを、少ない文量で把握できるようにすることを目的に作られている（Mark 氏）。
- Preceptor プログラムの試験運用では、preceptee の上司がコードの安全性と信頼性を高く評価し、AI の利用が週約 1 日分多かった。

## 9. まとめ

Mark Russinovich 氏と Scott Hanselman 氏は、AI でソフトウェアを作るコストが大きく下がったことを、decision model と embedding を組み合わせた Venn、Haptics Anywhere、SemanticStart、GPU Taskman などの実例で示しました。同時に、作れることと、10 億人に出荷できることは別であり、プラットフォームとしての Windows が提供する API の上で、各自が自分の体験を作る方向が望ましいと述べています。

ツール面では、判断の履歴を振り返る Agent Sessions Insights と、レビューに必要な文脈を集める Agent Review を紹介しました。ボトルネックは、人間の注意力、チームの合意形成、そして判断力の育成です。経験が増幅されるため、ジュニアの採用が減ると将来のシニアが足りなくなります。その対策として、医療の仕組みを参考にした preceptor プログラム（Azure Core で試験運用後、約 150 人ずつの規模で実施）と、Carnegie Mellon との提携が紹介されました。最後に 2 人は、各社が自分たちのメンターシップの仕組みを持つこと、教育機関と産業が協力して次の世代を育てることを呼びかけています。
