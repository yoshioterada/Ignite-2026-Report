# BRK262 Scale agents, not risk: Governance and FinOps for the enterprise

## 1. はじめに

このセッションは、エージェントを全社で使い始めた組織が「リスク」と「コスト」をどう管理するかを扱った 45 分のブレークアウトです。題材は主に Copilot Studio のエージェントで、Power Platform admin center（PPAC）、Microsoft 365 admin center（MAC）、Agent 365 といった管理画面が、それぞれ何を担当するのかが整理されます。

発表は三部構成で、第 1 部は「層になったガバナンス」の考え方、第 2 部は管理画面のデモ、第 3 部はコスト管理（FinOps）の詳細です。第 3 部では Lumen の Andrew Gaskins 氏が登壇し、自社の運用を語ります。

**結論を先に言うと、Copilot Studio のコスト制御は今後 MAC の「spending policy（支出ポリシー）」に集約されていく方向であり、Q&A では「移行戦略を考えて、今すぐ始めてください」と答えています。** 同じ MAC の spending policy は Copilot Studio のほか Cowork などの共通クレジットプールとしても使えます。

## 3. 何に関する発表か

Microsoft にはエージェントを作る方法がノーコードからプロコードまで幅広くあり、エージェントの能力が上がるほど、ガバナンスも追いつく必要があります。発表では、これを「with more capabilities, come with more responsibilities（力が増えれば責任も増える）」というスパイダーマンの言葉にたとえています。Copilot Studio は高度な機能を持つ一方で、ガバナンスの多くは Microsoft のエコシステム側の管理機能に組み込まれています。そのため、「層になったガバナンス（layered governance）」を説明する題材として適しているという位置づけです。

発表は、冒頭で次の 2 つの問いを掲げています。

1. Copilot Studio とエージェントが高機能になるなか、エージェントのガバナンスはどこで行うのか。
2. コストが発生するなか、Copilot Studio エージェントのコストをどう制御するのか。

そのうえで、次の流れで進みます。

| ---- | ---- |

## 4. 発表者が伝えたいメッセージ

発表者の主張は大きく 3 点です。

1. **ガバナンスは 1 つの画面や 1 つのチームで完結しない。** 環境（Power Platform）、アイデンティティとデータ保護（Entra、Purview）、全社の可視化（Agent 365）、脅威検知（Defender）が層になって働き、それぞれ担当する管理者の役割が異なります。
2. **コスト管理は一度設定して終わりではなく、計画・制御・見直しの循環である。** 管理者だけでなく、メーカー（エージェントを作る人）にも消費クレジットを見せることが重要だと説明されています。
3. **コスト制御は PPAC から MAC に移っていく。** MAC なら、PPAC ではできなかった pay-as-you-go への上限設定や、新規エージェントへのデフォルト上限が使えます。さらに API を使えば、管理作業自体をエージェントに任せられる（発表では「agentic governance」と呼んでいます）と述べています。

## 5. 発表内容の詳細

### 5.1 エージェントの進化とリスクの高まり

Graham 氏は、この 1 年でエージェントが大きく変わったと説明しています。最初は、数個のドキュメントでグラウンディングし RAG を行うだけの単純なチャットエージェントでした。そこに tools や connectors が加わり、外部システム、データ、認証が絡むとリスクが上がります。

さらに、agent user ID を持つエージェントは自分の受信箱とカレンダーを持ち、ドキュメント内で @ メンションでき、さまざまなトリガーで長時間動くアクションを起動できます。そのため、「ガードレール内に収まっているか」「使用状況を継続的に監視できているか」「どのシステムにつながっているか」、つまり**影響範囲（blast radius）と実際に触っているもの**を把握する必要があると語られています。

### 5.2 エージェントのライフサイクルに沿った層

Thomas 氏は、Copilot Studio エージェントのライフサイクルに沿って、各層を次のように説明しています。

| 層 | 役割（発表での説明） |
| ---- | ---- |
| Power Platform admin center（PPAC） | 作成時のガバナンス。従来からの経緯で、Copilot Studio の制御の多くは Power Platform と共有されている。メーカーを安全に開発できる「環境」へ誘導する。 |
| Entra | agent identity と access packages の設定で、エージェントがアクセスできる範囲を決める。 |
| Purview | 情報保護、コンプライアンス、ログ、機密データのラベル付けなど、セキュリティのベースラインを設定する。 |
| Agent 365 | エージェントがランタイムに入った後の、組織全体での可視化（observability）。 |
| Defender | リアルタイムの脅威検知と対応。 |

Graham 氏は「環境」を、制御の境界を持つアセットとリソースのコンテナだと説明しています。何ができるか、どの connector を使えるか（advanced connector policies）、誰が何をできるかを環境ごとに決めます。environment routing によって、ユーザーを既定の環境や個人の生産性向上用の環境へ振り分けることもできます。Power Platform は従来から環境単位で管理されてきた、という補足もありました。

### 5.3 IT 管理者の役割分担

「IT チーム」は 1 つのチームや 1 人を指すわけではなく、成果ごとに分かれた役割の集合体だと Thomas 氏は説明します。エージェントのガバナンスで重視する役割は 5 つとされ、トランスクリプトで説明されたのは次の 3 種類です。

- **Power Platform admin**：メーカーの支援（maker enablement）を担い、イノベーションを支える基盤を用意しつつリスクとのバランスを取る。
- **Security admins**：Entra、Purview、Defender を扱う。
- **AI admins**：新しい役割。主に Microsoft 365 admin center（MAC）にいて、全社の可視化を担当する。Microsoft 製だけでなくサードパーティのエージェントも対象になる。

この日は、PPAC にいる Power Platform admin と、MAC にいる AI admin の 2 つに絞って話が進みます。それぞれの管理者が仕事で自問する内容も示されました。Power Platform admin は「メーカーはどこで作れるか」「何を使って作れるか（connectors など）」「誰がエージェントを公開・実行できるか（作成権限、共有権限）」を考えます。AI admin は「誰がエージェントにアクセスできるか」「エージェントは何にアクセスできるか」「ランタイムの挙動」「どのコンテンツセーフティのガードレールが適用されるか」を考えます。

### 5.4 Power Platform admin：自然言語での管理（デモあり）

Graham 氏は PPAC の画面の細部には入らず（詳細は 2 週間前にラスベガスで開かれた PPCC カンファレンスで見られる、という説明でした）、**Power Platform admin plugin** を使ったデモを行いました。これは Power Platform に自然言語で問い合わせるためのインターフェースで、組み込みのオントロジーを使って質問に答えます。デモの詳細は 6 章に書きます。

ここで Thomas 氏がまとめたポイントは「カスタマイズ」です。自然言語で操作できるうえ、既存のダッシュボードが気に入らなければ、提供されている API で自分用のダッシュボードを作れます。

### 5.5 Agent 365 と MAC：全社の可視化（デモあり）

AI admin 向けの機能の多くは、MAC 内の Agent 365 から使います。Graham 氏は、Power Platform や Copilot Studio で作ったものだけでなく、Amazon、Salesforce、ServiceNow など**どこで作られたエージェントでも**、MAC に集約して概要を確認できると説明しています。デモの詳細は 6 章に書きます。

### 5.6 メーカー向けの可視化

コスト管理は共有責任であり、管理者が常にメーカーへ「クレジットを使いすぎです」と伝える状態は望ましくありません。そこで、メーカーに自分でクレジットを管理できるだけの可視性を渡す、というのが Graham 氏の説明です。Copilot Studio のエージェント作成画面での内容は 6 章のデモで扱います。

Thomas 氏は、顧客から聞いている成果として、メーカーが可視性を得ると**コスト見積もりもできるようになる**と述べています。プレビュー中の各タスクの実行が正確に見えるため、組織全体へ拡大するときの見積もりにもつながる、という趣旨です。

### 5.7 コスト管理サイクルと PPAC 側の機能

第 3 部の冒頭で、Thomas 氏が会場に「利用量ベースの課金の管理に不安がある人」と挙手を求め、Graham 氏が「全員だと思う」と応じる場面がありました。そのうえで、コスト管理は次のサイクルとして説明されました。

1. **計画（plan）**：予算があり、さまざまな事業部門が参加する。それぞれに適切に資金を割り当てる。
2. **制御（control）**：ガードレールを設定する。各領域で何ができるか、どのリスクプロファイルにするかを決める。
3. **見直し（review/optimize）**：誰が採用しているか、どれだけ価値が出ているか、クレジットが尽きて追加が必要か、予測は合っているかを確認し、最適化する。

Graham 氏による PPAC の機能説明は次のとおりです。

- **計画と制御の基盤**：制御の面（control surface）やガードレール、セキュリティ、環境マップの把握。
- **クレジットの割り当て**：どの環境へ（多くは事業部門単位で）何クレジットを割り当てるかを決める。これが API でもできるようになった。8 月に課金まわりの変更があって以降、規模の大きい顧客が大量に管理したがっているため、クレジットの割り当てとエージェント単位の上限設定を API で行える一連の API を公開したと説明しています。（音声では「user-based billing」と聞こえますが、文脈上の意味は確定できません。）
- **大規模管理**：数十万の環境を持つ顧客がいる。そこには個人の生産性向上用の個人開発環境も含まれる。そうした環境を一括で設定したり、テナントプールから引き出せないようにして、与えたクレジットだけに制限したりできる。
- **最適化**：インベントリの取得、レポート、ユーザー採用状況の確認、前述のカスタムダッシュボード。
- **上限（caps）**：PPAC には、クレジットパック（capacity packs）と pay-as-you-go の両方に対する上限がある。pay-as-you-go については、"arrears" と "Azure P3 credits" の両方の方式に対応していると説明されています。（この 2 つの表記は音声認識の都合で確定できません。）

> 補足：Graham 氏は、これらの機能が時間とともに MAC に移行していくとも述べています。なお、PPAC の上限は pay-as-you-go にも対応しているという上の説明と、後半（5.8〜5.11、6.4）の「PPAC では pay-go や Azure P3 クレジットに上限を設定できなかった」という発言は、トランスクリプト上では整合していません。ここでは両方の発言をそのまま記載しています。

#### 「割り当て」から「上限」へ

Thomas 氏の「allocation（割り当て）という言葉には違いがあるのか」という問いに、Graham 氏は次のように答えています。

PPAC で環境にクレジットを割り当てると、総クレジットプールから**その分が減ります**。この方式では、自分で帳簿をつけて過剰割り当てを避ける必要があります。しかし多くのプロジェクトは割り当てを使い切りません。さらに、クレジットは MAC 側（Cowork など）とも共有されるようになったため、**すべてのクレジットをワークストリームに割り当ててしまい、Cowork などで何もできなくなる**ケースが多く見られたそうです。PPAC 管理者と MAC 管理者は、特にコストの面で日常的に話しているわけではない、という事情もあります。

そのため、**割り当ては廃止され、すべてがフラットな上限（flat limits）に移行します。** MAC では、重なり合う上限を設定できます。会社全体の全環境に対するルールも、特定の環境やリソースに対するルールも作れ、ユーザー単位のポリシーも作れます。上限は「止まる単一の数値」です。帳簿管理は少し増えるものの、柔軟性が得られる、という説明でした。

#### PPAC のレポート API（パブリックプレビュー）

この日から、**PPAC のレポート API がパブリックプレビュー**になりました。エージェントやワークフローの利用状況を、プログラムから取得できる API です。粒度はこれまでで最も細かく、ユーザー別、エージェント別、機能別、日別に取得できます。

例として Graham 氏は、使わせたいモデルがあるのに別のモデルを使っているユーザーの特定や、機能別の消費（generative answers を使っているのか、ServiceNow に接続してチケットを扱っているのか）を挙げました。（モデル名は音声認識の都合で「Astra」「Sonnet」と聞こえますが、確定できません。）常に日単位（day slice）で取得できるので、トラブルシューティングで何が起きたかを正確に追えます。ドキュメントは公開済みで、告知の投稿は前日に出たとのことです。

### 5.8 MAC のコスト管理：Copilot Studio にも対応

Thomas 氏が「今日の大きな話題」と紹介したのが、MAC のコスト管理の仕組みを Copilot Studio にも広げることです。MAC の管理体験は、すでに Cowork や Work IQ 向けに存在していました。これまでは PPAC と MAC という 2 つの管理画面が、コスト管理について互いに連携せず、2 つの記録システムがある状態でした。

Graham 氏によると、**パブリックプレビューとして、MAC で Copilot Studio 向けの spending policy を設定できる**ようになりました。対象は、エージェントの構築と実行、およびその他のリソースです。コスト制御は時間をかけて MAC へ移っていく見通しで、特に Copilot Studio、Cowork、その他のインターフェースにまたがる**共通のリソースプール**を使えるようになる点が利点です。

現時点では、環境、環境のグループ、エージェントの単位で設定できます。近いうちに、Copilot Studio 向けにユーザー単位の割り当ても始まる予定です。ユーザーに毎月のクレジットを与え、Copilot Studio でも Cowork でも好きなインターフェースで使わせる、という使い方です。

Graham 氏は、spending policy のスコープを 2 種類に分けて説明しています。

| スコープ | 内容 | 向いている用途（発表での説明） |
| ---- | ---- | ---- |
| リソーススコープ | 環境や特定のアセット（多くはエージェント）に対するポリシー。従来の Power Platform の考え方に近い。 | 本番アセットや、毎晩経理向けに実行する業務など、常にクレジットが使えなければならないもの。 |
| アイデンティティスコープ | ユーザーやグループ単位のポリシー。MAC は従来、Office のライセンスに紐づくユーザー単位のみだった。 | 新しい働き方を試すユーザーや、複数プロジェクトをまたいで自分のツールを作る開発者。 |

具体例として、Microsoft 社内の HR エージェント「Ask HR」が挙げられました。ポリシーやバケーションの質問、インシデントの報告ができるエージェントです。週末に vibe coding でクレジットを使い切ったユーザーが、その月のクレジットが残っていないために HR の問題を提出できないのは困ります。そこで、本番アセットにはユーザーのクレジットプールとは別の、枯渇しないプールを用意します。一方、ユーザー側では、プロジェクトチームに一定のクレジットを渡して自由に使わせたり、個人に付与したりします。

### 5.9 顧客事例：Lumen（Andrew Gaskins 氏）

Graham 氏が Lumen の Andrew Gaskins 氏を舞台に招き、運用を尋ねました。以下は Andrew 氏の発言の要点です。

- **土台**：長年 Power Platform 上にあらゆるものを構築してきた。個人開発環境での生産性向上と、環境戦略を組み合わせたことが、Copilot Studio で作るすべてのものの下地になった。
- **個人開発環境**：入ると最初に個人開発環境に置かれ、そこで作業できる。advanced connector policies で保護している。共有できる人数にも制限があり、機能を完全に制限するのではなく、Agent Builder などで何ができるかを試せるようにしている。
- **昇格（promotion）**：共有先が 10 人の上限を超えるような場合、小さな部門を超えて、より大きな部門グループへ昇格させるべきものかを確認する。作った人が異動しても継続できるようにするためでもある。チームや部門、全社に出したいという相談は、AI ガバナンスチームと一緒に進める**インテークプロセス**で受け付け、コスト制御もそこで準備する。
- **個人の生産性向上**：M365 Copilot ライセンスの entitlement に頼り、従来型の harness を使う。
- **クレジットや pay-go が必要な場合**：新しい環境に入れる。承認は VP レベルで、「月にいくら使う見込みか」を申告してもらい、pay-go で運用する。アラートのしきい値を使い、80% に達した時点で本人に知らせる。ただし、使用を止めるところまでは行っていない。
- **PPAC から MAC への移行について**：Power Platform 管理者の負担が減るので歓迎している。これまでは、Power Platform と Copilot Studio の運用に加え、コスト制御も主に Azure のリソースグループで行っていた。今後は M365 管理者や課金ポリシーを設定するグループと連携でき、「1 環境に 1 エージェント」や「環境全体を 1 グループが負担する」といった形に縛られず、より細かく扱える。
- 大規模なものは、完全に資金を確保し、独立させるため、専用の環境が必要。Graham 氏が「1 エージェントごとに 1 環境では大混乱になる」と言うと、Andrew 氏も同意しました。

### 5.10 MAC での spending policy の作成（デモあり）

Graham 氏は、spending policy を**Copilot とエージェントに作らせる**デモを行いました。内容は 6 章に書きます。

デモを受けて Thomas 氏は、これは「agentic governance」の考え方だと述べています。先の Power Platform admin plugin（自然言語）、レポート API、そして Graham 氏が見せた GitHub Copilot の統合は、同じバックエンドを別のプラットフォームから操作できる、という説明です。

### 5.11 MAC に移ることで得られるもの

Thomas 氏は、MAC へ移る利点を 3 点にまとめています。

1. 以前、Power Platform 管理者は pay-go やプリペイドの上限を設定できなかったが、MAC ならできる。
2. すべてにデフォルトがある。spending policy にデフォルトの上限を設定でき、新しいエージェントやリソースが作られると自動でポリシーが適用される。「管理者の不安を大きく減らす」と述べています。
3. 予算と課金を自分たちの流儀で設定できる。層になった制御で、コストセンターに合わせて統合・カスタマイズできる。

### 5.12 始めるための 5 つのステップ

発表の最後に「始めるための 5 つの動き（five moves）」が示されました。トランスクリプトで説明されているのは、次の 3 つまでです（残りはスライド上のみで、音声からは確認できません）。

1. **誰が何をするかを決める。** Power Platform 管理者が MAC にアクセスできるとは限りません。AI admin ロールが必要です。環境管理者として閲覧権限しか持たない場合は、MAC の AI reader ロールが必要です。
2. **コストセンターを整理する。** リソースベースかアイデンティティベースかを決め、誰にどれだけクレジットを渡すかを決める。例として、エンジニアリング部門にマーケティング部門より多く割り当てても問題ない、と述べています。
3. **1 つまたは少数の環境でパイロットを行い、そのあと拡大する。**

あわせて、Copilot Studio のコスト管理の Learn ドキュメントと、層になったガバナンスの解説記事への短縮リンク（スライド上）が紹介されました。

### 5.13 Q&A

Q&A は、QR コードから投稿・投票された質問のうち上位のものと、会場マイクからの質問で進みました。

**Q1. Copilot Studio のコスト制御は、いつから PPAC ではなく MAC を使い始めるべきか。**
回答は「**今すぐ始めてください**」です。移行戦略を考え、何から移すかを決めます。今の MAC では、リソースや環境を設定できます。まずはリスクの低い環境、たとえば個人開発環境を少し選んで移し、管理者同士がどう連携するかを学ぶことが勧められました。MAC に spending policy がある場合は、**PPAC の設定より優先されます**。MAC で作ったものは常にまず MAC で消費され、PPAC では消費されません。ユーザー単位のポリシーは、年初にプレビューとして始まる予定です。それまでは環境とリソースから始めるよう勧めています。

**Q2. コスト制御のベストプラクティスは。**
- 「すべては上限（caps）」。環境に上限を設定し、アラートを設定して、余裕を持って気づけるようにする。
- レポート API を使って日次や週次で状況を確認する。アラートで遅れに気づく。
- リソースにも上限を設定する。PPAC でエージェントの上限を設定するには、そのエージェントを 1 日動かしてから上限を決める必要があるが、MAC ではデフォルト上限を最初から設定できる。両方の側で上限を持つのが望ましい。
- 事業部門やワークロードにどれだけ確保し、個人の生産性向上用にどれだけ確保するかを決める。ワークストリーム単位では直接の原価（COGS）から支払える一方、個人の生産性向上は得られる価値が曖昧になりやすいため、管理方法を考える必要がある。

**Q3. Copilot managed runtime を共有すると、データへのアクセスはどうなるか。**
現時点では、Copilot managed runtime のアプリを共有すると、その環境とバックエンドにあるデータへのアクセスも与えることになります。on-behalf-of や別の認証で他のデータソースにアクセスさせる方法はありますが、同じ環境内の Copilot managed runtime のアプリであれば、これらの権限が付与されます。

**Q4. リスクの low / medium / high を、何をもって判定するか、カスタマイズできるか。**
Graham 氏は、low/medium/high の判定基準そのものを設定できるとは考えていない、と答えています。Agent 365 は自分の専門領域ではないとしたうえで、フラグの設定には多くのカスタマイズがあり、スコアリングの方法に応じて項目をオン・オフできると述べました。レベルを変更できるかは分からないとのことです。

**Q5（会場マイク）. トークンやクレジットではなく、実際の通貨で表示する予定は。**
すべてがクレジットベースになっており、クレジットは共通の単位だと説明されました。クレジットは正規化されているため通貨への換算は可能で、請求は現地通貨ベースのはずだと理解している、とのことです。ただし、画面での通貨表示や地域（geo）対応の時期は分からない、と答えています。後で連絡をもらえれば、課金担当者に確認するとのことです。

## 7. 注意点・発表者の気付き

- **割り当てによる枯渇に注意。** PPAC の割り当てでは、総クレジットから差し引かれるため、すべてを割り当てると Cowork など別の用途で使えなくなる事例が多いと説明されています。割り当ては廃止され、上限に移ります。
- **MAC と PPAC の優先順位。** MAC に spending policy があれば、PPAC より先にそちらで消費されます。
- **現時点の対象範囲。** MAC の Copilot Studio 向け spending policy はパブリックプレビューで、環境・環境グループ・エージェント単位です。ユーザー単位は、年初にプレビュー開始予定です。
- **管理者ロール。** Power Platform 管理者でも MAC にアクセスできるとは限りません。AI admin ロール、または閲覧のみなら AI reader ロールが必要です。
- **Copilot managed runtime の共有。** 共有すると、同じ環境とバックエンドのデータへのアクセスも与えることになります。
- **ライブデモのリスク。** Graham 氏は、デモ中に「ライブのエージェントの応答は難しい」と述べています。エージェントは YOLO モードで動かされ、認証は手動で行ったものをキャッシュしていました。
- **自然言語で作った成果物の完成度。** エグゼクティブサマリーについて、Graham 氏は「最初は完璧でないかもしれないが、80% までは到達できる」と述べています。
- **リスクレベルの判定。** low/medium/high の判定基準を変更できるかは、発表者は把握していません。
- **通貨表示の時期。** 発表者は把握しておらず、回答は保留されました。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **管理の一元化**：MAC では Copilot Studio、Cowork、その他のインターフェースにまたがる共通のクレジットプールを使える。リソースとアイデンティティの両方のスコープでポリシーを作れる。
- **PPAC でできなかったことが可能に**：pay-go やプリペイドの上限設定、新規エージェントへのデフォルト上限、重なり合う上限の設定。
- **メーカーの自律**：作成中のクレジット消費、評価ごとのコスト、実行時の消費を見られる。管理者が常に監視して指摘する必要が減る。メーカーがコスト見積もりを行える。
- **価値の可視化**：Agent 365 で、コスト、使用モデル、ユースケースごとの価値（時間と時給で算出）、タスクの完了回数を確認でき、経営層の「支出に見合う価値は何か」という問いに答える材料になる。
- **自動化と規模への対応**：API とレポート API で、割り当て、上限、レポートを大規模に管理できる。自然言語やエージェントを使い、画面に触れずにポリシーを作成できる。
- **Lumen の事例**：Power Platform 管理者の負担が減り、M365 管理者と連携して、より細かい粒度で課金ポリシーを設定できると語られました。

## 9. まとめ

エージェントの管理は、PPAC の環境、Entra と Purview によるセキュリティ、Agent 365 による全社の可視化、Defender による検知が重なる層構造になっています。コストの面では、PPAC の「割り当て」からフラットな「上限」へ移り、MAC の spending policy が Copilot Studio、Cowork などを横断する窓口になっていきます。

発表者が勧める最初の一歩は、役割（AI admin / AI reader）の整理、コストセンターの整理、そして少数の低リスクな環境でのパイロットです。MAC の spending policy は PPAC より優先されるため、移行戦略は今から検討しておく必要があります。PPAC のレポート API がパブリックプレビューになり、spending policy も API とエージェントから作れるようになったことで、FinOps を大規模に自動化する道も開かれています。
