# BRK252 Turn your data into AI advantage with Training in Microsoft Foundry

## 1. はじめに

このセッションは、Microsoft Foundry の「トレーニング（モデルの追加学習）」機能を使って、自社のデータや業務知識を AI の競争優位に変える方法を紹介するものです。エージェントを作ること自体は簡単になったので、本当の課題は「必要な性能・速度・コストで、実際のビジネス価値を出すこと」だ、というのが出発点です。

前半では、Foundry のトレーニングの全体像（managed training、programmed training、reinforcement learning environment）と、新しく加わるモデルの選択肢が紹介されます。続いて Docusign が fine-tuning の知見を話し、Microsoft の登壇者が code review を題材にしたライブデモを行い、最後に Heidi Health がヘルスケア分野の事例を紹介します。

### 5.1 トレーニングで成果が出た 3 つの顧客事例

### 5.2 トレーニングを使うべきとき、使うべきでないとき

前述のとおり、すべてのプロジェクトにトレーニングを使う必要はありません。ここで、手法の選び方が簡単に整理されます。

| 手法 | 使う場面（発表での説明） |
| --- | --- |
| supervised fine-tuning（SFT） | 良いデータ点があり、モデルに振る舞いを教えたいとき |
| DPO | 同じ質問に対する 2 つの回答を並べ、人間がどちらが良いかを判断できるとき |
| reinforcement learning（強化学習） | 複雑なタスクで、結果の品質をどう測るかが分かっているとき |

### 5.3 トレーニングの「3 つの難所」と Foundry の 3 つの関わり方

登壇者は、トレーニングのプロジェクトには難しい点が 3 つあると説明します。

1. 学習の元になる、適切なデータとタスクを用意すること
2. トレーニングレシピ（トレーニングループの形）を決めること
3. トレーニングが動く GPU 容量（AI インフラ）を管理すること

Foundry は、どこまで自分で制御したいかに応じて、次の 3 つを用意しています。

**managed training**：データを持ち込み、fine-tune したいモデルと、あらかじめ用意されたレシピ（SFT、DPO、強化学習）を選ぶだけです。トレーニングのワークフローは Foundry が動かし、モデルを届けます。

**programmed training**：トレーニングループを自分で制御したい人向けです。どのデータやタスクから学ばせるか、結果をどう採点するか、いつ進捗を評価して最適化やチェックポイント保存を判断するかを、自分で設計します。GPU の管理という複雑な部分は Foundry が引き受けます。後半の説明では、自分のノート PC 上でコードを書き、Foundry が管理する serverless GPU につなぐ形だと補足されています。ノート PC 上で、プログラムとしてトレーニングを制御することから programmed training と呼ぶ、と説明されています。fire and forget に近い managed training を補完するものです。

**reinforcement learning environment（RLE）**：次の項で説明します。

### 5.4 Reinforcement learning environment（RLE）

複雑なタスクでは、学習用のデータやサンプルだけでは足りません。そこで強化学習の出番になります。多段階のワークフローで、各ステップの結果から学べるようになり、モデルを改善するための十分な学習シグナルが得られます。

登壇者は、強化学習を **エージェントのためのフライトシミュレーター** にたとえています。自社の業務タスクを再現し、現実的なエージェント、ツール、ルール、隔離されたサンドボックスを組み合わせます。エージェントはシミュレーションで生まれるシグナルから、複雑なタスクの進め方を学び、結果として完了の信頼性が大きく上がります。RLE は programmed training だけでなく managed training でも使えます。

後半では、RLE の考え方が次のように補足されます。

- 組織の中にある暗黙知、ドメイン知識、専門性を、環境としてパッケージ化したもの。データセットでは実現できない形でモデルを学習させられる
- データをタスクに、タスクを eval に、eval を grader に変換でき、判断（judgment）まで組み込める
- タスクセットの形式は Harbor format、OpenN（音声認識の都合で表記が確定できません）、JSONL をサポート。ハーネスは gym format と BYOH をサポートし、どこのクラウド・プラットフォームで動いているエージェントでも、RLE を使って Foundry 上で学習させられる
- programmed training は RLE を使って練習し、検証可能な報酬（verifiable rewards）と判断を得て、自社のドメイン知識の領域でモデルを hill climb（段階的に性能向上）させる。RLE は trace と報酬を返すので、評価を続けて改善を重ねられる

なお、reinforcement learning（強化学習）と reinforcement learning environment（RLE）は別の概念で、混同しやすいと注意されています。

### 5.5 トレーニングの observability

トレーニング自体が複雑なので、実行中に何が起きているかを知る必要があります。Foundry には豊富な observability ツールがあり、メトリクスと rollout を結び付けたり、trace を比較したりして、トレーニング品質のデバッグと改善点の特定ができます。

### 5.7 Docusign の事例：Agreement Manager の AI

Docusign の登壇者が、model fine-tuning で Agreement Manager の裏側の AI を作った経緯を話しました。

**背景**

Docusign の IAM は、契約（agreement）管理をエンドツーエンドで行うプラットフォームです。中核の Agreement Manager は、組織の契約を集約するリポジトリで、Docusign の AI エンジン Iris が支えています。AI で契約から主要な属性を識別して保存し、検索、フィルタリング、レポート、各種のインサイトに使えるようにします。

求められるのは、スケールと信頼性です。1 日に数百万件の文書を処理することを目標にしているため、スループットとコストが重要です。大量の一括取り込みもあれば、ほぼリアルタイムのトラフィックもあるので、レイテンシも重要です。一方で、大企業向けには高い精度も求められます。このため、両面の最適化が必要だと説明されています。

**本番の推論パイプライン**

文書が入ると、次のように処理されます。

1. OCR または PDF パース
2. 契約の分類（抽出に使うスキーマを引くため）
3. RAG のような処理で、文書内の関連スニペットを選ぶ
4. 適切な LLM による AI 抽出（ここが最も重要で、品質とコスト効率の要求が高い）

**fine-tuning のパイプライン（teacher-student）**

古典的な teacher-student の構成です。

1. 法務の専門家がキュレーションした評価用データに加え、代表性のある大規模な学習用コーパスを用意する
2. フロンティアモデルを teacher として、専門家が作ったプロンプトで動かす
3. teacher が満足できる性能に達したら、学習用データに対して teacher label を生成する
4. Foundry 上でホストされた軽量モデルを、Foundry が提供する手法（SFT、強化学習ベースの fine-tuning など）で fine-tune する
5. 反復の中で、student が teacher と同程度の精度に達したと判断したらデプロイする

これにより、高い精度が必要な AI 抽出を、管理可能なコスト効率で維持できるとされています。

**SFT と RFT での学び**

| 観点 | SFT | RFT |
| --- | --- | --- |
| 手法の詳細 | LoRA アダプターと cross entropy loss の最適化。推論を行わない（non-reasoning）モデルで利用 | GRPO による最適化。Foundry が用意する reward function のオプションを、自社のユースケースに合わせてカスタマイズ（最も時間をかけた部分） |
| 利点 | 学習が安定して効率的。広範な推論や探索を要さないタスクに向く | multi-hop の推論が必要な複雑な抽出タスクで大きな改善が出る（例: 契約総額の計算）。契約タイプの分類のようなケースでは discrete reward function が良く効く |
| 欠点 | 非常に高品質な学習データが必要で、未知のデータへの汎化が弱い。代表的なデータの用意に時間がかかる。最近の reasoning モデルでは使えないものがある | 単純な抽出では改善が小さい。RFT の性質上、時間とコストが増える |

**MAI モデルとの協業**

MAI の code 1.1 flash モデルで、前回の SFT の実験と RFT を比べた結果が紹介されました（code 2 にも取り組み中とのことです）。

- 必要な学習データは約 20% と大幅に少なくなる一方、学習の GPU 時間はずっと長くなる
- タスクを硬直的に丸暗記しにくく、Python の grader で柔軟に設計できる（soft matching など）。学習の勾配もなめらかになる
- 推論や計算が必要なフィールドの F1 スコアが **3〜18%** 向上した。単純なフィールドでは大きな差が出なかった

今後は、MAI チームとの協業を、新しいモデルの SFT・RFT の手法やクックブックの面でさらに深めること、特に RFT のために合成データ生成を充実させることが挙げられました。

### 5.8 Foundry のトレーニング製品群と、code review のデモの前提

Vijay は、1 つだけ持ち帰るなら「post-training とは何か、実際のビジネス課題にどう使えるか」だと述べています。デモは 1 つの問題を例にした説明用で、同じ手法は多くの本番課題に使えるという位置づけです。

デモの題材は、パートナー（Whitney。音声認識の都合で表記が確定できません）がブログに書いた、code review の問題です。背景は次のとおりです。

- 誰かが 100 行のコードを書くと、それが正しいか確認するために、チームの他のメンバーの時間が多く使われる
- GitHub へのコードとコミットの数は、指数関数的に増えている（期間を示す発話は聞き取り不明瞭）
- AI がコーディングの大半をこなせるようになり、仕事は圧縮された期間で終わるものと期待される。月単位だった作業が日単位、日単位だったものが時間単位になっている。その結果、code review がボトルネックになる
- 大きなモデルをレビュアーにする方法もある。フロンティアモデルなので大半は正しく指摘できるが、熟練開発者や principal engineer が持つ専門性とコンテキストは持っていない

そこで、post-training で小さなモデルを効果的にする例を見せる、という流れです。データには、GitHub の実際の PR と、著者がコードを直して PR に反映した内容を使い、フロンティアモデルのレビューも加えています。実在するリポジトリの 150 件の PR と、受け入れられた／却下されたコメントで練習し、120 件の holdout セットで、学習内容が未知のデータにも当てはまるかを確かめるとのことです。

### 5.9 Heidi Health の事例

Heidi Health は、医療向けの Scribe（診察記録）の会社で、US ではまだ大きくないが、カナダ、英国、オーストラリア、ニュージーランドの市場では相対的に大きく 1 位だと説明されました。

- 医師と患者の間の診察を、週に 270 万件扱っている
- リサーチチームは 12 人だけ

**対象の製品「evidence」**

医師が任意の質問をすると、モデルが検索し、読み、統合して最終回答を書く製品です。重要なのは、**常に評価から始める（evaluation から逆算して作る）** ことで、accuracy、faithfulness、latency、cost、completeness、certainty を測っています。

登壇者は、オープンな小さなモデルは安いが性能が良くなく、クローズドなモデルは性能が良いがコストがかかる、と整理します。狙いは、その中間の「安くて性能が高い」位置（グラフの左上）です。

**結果**

- 小さなオープンソースモデルの出発点は、社内ベンチマークで 7.5 とかなり低かった
- 最初に SFT を行い、約 3 ポイント上がった
- 次に強化学習を行って大きく伸び、フロンティアモデルの 1 つを上回った（「behind it is Opus」と述べ、医療分野では GPT のモデルのほうが性能が良かったとも補足しています）
- 短期間で、accuracy が上がり、fabrication（でっち上げ）が減り、completeness が上がった。典型的なトレーニング結果として示されました
- 推論コストは通常 10 分の 1 程度。週 30 万件規模（発話は「300K per week」。単位は聞き取りのまま）の量では、月に数百万ドルの節約になるという説明（金額の発話は聞き取りが不明瞭です）
- 小さいので推論が速く、レイテンシも改善した

登壇者は、**最も重要なのはコストではなく「所有」** だと述べています。患者と医師のプライバシーの保護や、医療業界の重いコンプライアンス要件が理由です。

**再トレーニングのアーキテクチャ**

Tinker API を使った構成です。上側は Heidi が自社で持つ部分で、ツール、サンドボックス、RE（聞き取りのまま。RLE のことかは確定できません）、評価、状態の保存、loss の計算、報酬の収集などが含まれます。Foundry 側では、Tinker API で GPU を抽象化しています。sampler と backpropagation を行い、trainer から sampler にモデルの重みを更新して、このループを回します。

**学び**

- 全体として使い方はとても分かりやすい。登壇者は「エージェントに頼んで動かした」と述べ、作業全体で 40 時間弱だったとしています
- 合成データでトレーニングはできるが、評価は実際のケースで行う。合成データと実データの差を常に監視し、実環境で動くことを確認している
- SFT を先に行い、基本的な軌跡（trajectory）の形を学ばせてから、強化学習で自分で rollout して学ばせる流れが有効だった
- 所有するものは自分で持ちつつ、GPU（計算リソース）は借りるほうがよいと考えている。Foundry は強力にサポートしてくれた

### 5.10 まとめの発言

最後に、Foundry のトレーニングは、OpenAI モデル、MAI モデル、オープンウェイトモデルのどれを fine-tune しても、本番に移すための道筋を提供する、と締めくくられました。モデルを自社のビジネス向けに学習させ、本番にデプロイして、実際の利益を見るという流れです。reinforcement learning environment（新機能）を使いたい人向けに、登録用のバーコードがスライドで示されました。

## 6. デモ・手順

このセッションにはライブデモがあります（Vijay が担当し、発話で "let's go into the demo" と述べています）。録音は音声のみのため、画面上の細部は分かりません。以下は、語られた順番どおりの内容です。

1. 1 つの pull request（PR）を作成する。この PR は、Docker イメージのビルドが失敗した場合に NPM パッケージが公開されないようにする確認を入れる、簡単なもの。
2. PR を出す一方で、新しい PR を待ち受けて動くエージェントを、デモの少し前に起動してある。PR が出されたことが、エージェントに検知される。
3. Foundry の hosted agents の画面を見る。そこには、GPT soul（音声認識の都合で表記が確定できません）で動く code review エージェントがあり、新しい PR を探してレビューする。hosted agent なので、trace に豊富にアクセスでき、どのツールを呼び、どの軌跡をたどったかなどのテレメトリを確認できる。見やすいビューやグラフビューもある。
4. 教師あり fine-tuning（SFT）のジョブを開始する（意味はあとで説明すると述べている）。
5. hosted agent の trace を、タスクセットに変換できることを示す。タスクセットの 1 つは 1 件の PR に対応し、その PR のコメントなども含めて学習に使える。約 150 件のタスクセットを使った。
6. grader を設定する。GPT、Luna などのモデルを使い、実際の PR コメントの評価に基づいて報酬を割り当てる。例として、レビュアーが 4 件のコメントをして著者が 3 件を受け入れた場合、不要なコメントが 1 件あるので満点にならない。4 件すべてが受け入れられれば報酬は 1。
7. RLE には、タスク、grader、学習するモデル、ハーネス（ここではエージェント）、トレーニングパラメータを定義する。
8. SFT を使う理由の説明：小さなモデルは、code review にどのツールを使うか、レビューやコメントがどんな形であるべきかを知らない。この「cold start」の整合を SFT で行う。強化学習のループには、sampler の動かし方や報酬の設定などの追加パラメータがあり、高レベル API より細かく制御できる。コードはすべて手元の CPU 上で動き、GPU マシンへの接続は不要で、サーバーに実行を投げられる。
9. UI に戻り、設定済みの RLE を見る（名前は聞き取れませんでした）。eval の数値は higher is better で、負の数として表示される。ベースモデルは成績が悪く、SOL は良い。
10. managed training の高レベル API では、SFT、DPO、強化学習を選べ、選べるモデルの一覧もある。新しい MAI 2 のモデルも入る予定。
11. 開始した SFT の run を、observability の画面で見る。loss curve は安定した形をしている。RL の run も同様に確認できる。
12. RLE の AZD コマンド（聞こえた表記）で、システム内の環境、使えるハーネス、モデルを確認できる。簡単なコマンドで RLE のトレーニングを開始でき、ノートブックからも、programmed training を直接使うか、RLE で run を開始できる。
13. RLE を開始すると、ローカルのモニターもあるが、リモートのモニターを見せる。F2 スコアが、モデルが採点を学べていることを示しており、良い兆候だと説明している。
14. SFT モデルと RL モデルの、LoRA アダプターのチェックポイントを選び、managed compute にデプロイする。デプロイに名前を付け、同じファミリーのベースモデルを選び、ベースモデルと SFT の LoRA の重み、RFT の LoRA の重みを同じデプロイに載せられる。
15. code review の性能を比較する。Qwen（小さいモデル）の SFT と RL を行ったものは、ベースの Qwen や SFT のみのモデルより、code review の性能が大きく上がっている（SOL モデルとの比較に当たる発話は聞き取りが曖昧です）。
16. 4 つのモデル（ベース、SFT した Qwen、RL と SFT を行ったもの、SOL）を並べて比較する。SFT と RL の組み合わせは、tool call の数もトークン数も他より大きく少ない。call stack もずっと短く、答えに早く到達している。ベースの小さいモデルは動き続ける。報酬は SOL が 1 で、SFT と RL をした小さいモデルもほぼ同じ。
17. 最初に出した PR の結果を見る。10 分ほど前に起動したライブのデモで、7 分前に SOL が戻ってきたが、コメントはなかった。ベースの Qwen もコメントなし。SFT と RL のモデルは、著者が受け入れて先に進めるような、意味のあるコメントを付けた。

デモのあとの説明では、学習前後で完了したタスク数が大きく増え、**24 倍安く、速い**と述べられています。同じ考え方は、code review 以外の「検証できるタスク」にも使えるとのことです。例としてコーディング作業が挙げられ、大きなモデル（発話では「Opus 4.5.5」「Astra 6.2」と聞こえ、表記は確定できません）はトークンコストが非常に大きく、開発者 1 人あたり数千ドルの請求になりうると話しています。そこで、大きなモデルのトレースを使い、Foundry 上の MAI モデルのような高性能なモデルを同様の手法で学習させれば、同等の結果をより低いコストで得られる、という考えです。

## 7. 注意点・発表者の気付き

- **すべてにトレーニングを使わない。** まずエージェントが価値を出せることを、最良のモデルとプロンプト調整・コンテキスト・ツールで確認する。
- **SFT の限界**（Docusign）：高品質な学習データが必要で、未知のデータへの汎化が弱く、最近の reasoning モデルでは使えないものがある。
- **RFT の限界**（Docusign）：単純な抽出では効果が小さく、時間とコストが増える。報酬関数の設計に最も時間がかかった。
- **強化学習は難しいので避けられがち**だが、検証できるもの（コードレビューの良し悪しなど）であれば使えるところに力がある、と説明されています。
- **評価から始める**（Heidi）：合成データで学習しても、評価は実際のケースで行い、合成と実データの差を監視する。
- **強化学習と RLE を混同しない。** 別の概念です。
- デモは「実際にライブで動かした」ため、結果が出るまで待つ場面がありました。パートナーがこの実験を行った時点では MAI 2 モデルは未提供で、MAI 2 での結果は今後の期待として語られています。

## 8. 利用者にとっての利点

発表で語られた効果と事例成果は次のとおりです。

- 自社の IP を使ってモデルを特化させることで、性能を上げながらコストを下げられる。3 社の事例では、pass rate の 12% 上昇とコスト 93% 削減、精度 65% から約 100% でコスト 5 分の 1、85% から 11% 向上でコスト 50 倍削減が示されました。
- Docusign：複雑な抽出（契約総額の計算など）の F1 が 3〜18% 向上し、RFT では必要な学習データが約 20% で済みました（GPU 時間は増える）。
- Heidi Health：小さなオープンモデルの社内ベンチマークが 7.5 から、SFT で約 3 ポイント、さらに RL で上がり、フロンティアモデルの 1 つを上回った。推論コストは 10 分の 1 程度で、月に数百万ドル節約でき、速くなった。モデルを自社で所有でき、プライバシーとコンプライアンスの要件に応えやすい。作業は 40 時間弱だった。
- code review のデモ：SFT と RL を行った小さいモデルが、tool call とトークンが少なく、24 倍安く速く、意味のあるコメントを付けた。

## 9. まとめ

Foundry のトレーニングは、managed training（データ・モデル・レシピを選ぶだけ）、programmed training（トレーニングループを自分で制御）、RLE（業務の暗黙知を環境にして学習）の 3 つの形で、制御の度合いを選べます。OpenAI モデルに加え、オープンウェイトモデルと MAI モデルも fine-tune できるようになります。

登壇者のメッセージは、まず最良のモデルで価値を確認し、そのうえで必要なときにトレーニングで小さなモデルを自社業務に特化させる、というものです。Docusign、Heidi Health、code review のデモは、いずれも小さなモデルで性能を保ちつつ、コストとレイテンシを下げられることを示しました。RLE を試したい人は、スライドの登録用バーコードから申し込めます。
