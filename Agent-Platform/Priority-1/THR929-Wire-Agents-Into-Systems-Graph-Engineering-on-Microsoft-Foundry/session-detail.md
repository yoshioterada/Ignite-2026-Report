# THR929 Wire Agents Into Systems: Graph Engineering on Microsoft Foundry

## 1. はじめに

このセッションは、マルチエージェントシステムを「graph engineering」の考え方で組み立てる方法を、約 25 分で駆け足に紹介するシアターセッションです。登壇者は、この 1 年「マルチエージェント」を語る人は多いが、実際にどう作るかを見せる人は少ない、という問題意識から話を始めます。

まず、LLM の使い方が「プロンプト」から「コンテキスト」「ハーネス」「ループ」「グラフ」へと進んできた流れを振り返ります。次に、壊れた花瓶の注文を題材に、graph engineering を成り立たせる要素（分解、ワークフロー、エージェント間の連携、状態、進化、ontology、実行時の統制）を順に説明します。最後に、Microsoft Foundry の画面で、モデル、エージェント、toolboxes、Foundry IQ、トレース、評価（evaluation）を紹介します。

> 注意：公式の概要には、planner、WebIQ research agent、validator がグラフ上で動くライブビルドを見せるとありますが、トランスクリプトからは、そのような構成を実際に組み上げる場面は確認できませんでした。登壇者自身も、時間を見誤って高レベルの紹介に絞ったと述べています。

## 5. 発表内容の詳細

### 5.1 ここに至るまでの経緯

登壇者は、3〜4 年前に LLM を渡され、前日までの仕事が一変した、という話から始めます。そして、LLM をより決定的に（deterministic に）振る舞わせ、最終的にオートパイロットのように自走させるまでの流れを、次の段階で説明します。

| 段階 | 発表での説明 |
|---|---|
| foundation models | 知っていることは出荷前に学習した内容に基づく。pre-training、post-training で事実面や思考が向上してきた（画像生成で指が 7 本になる例を挙げ、今は鮮明だと述べた）。それでも、モデルは自分が良いと思うことをする |
| prompt engineering | 思いどおりに動かすためのプロンプトを作る。登壇者は「engineering と呼べるか分からない。prompt crafting と呼ぶ」と述べ、次のモデルに替えると以前のプロンプトが通用しなくなる課題を挙げた |
| context engineering | データへのアクセスを与える。RAG、agentic RAG など。知識、データソース、根拠（evidence）、作業状態（working state）を与える。限界として、コンテキストウィンドウは「息ができなくなるまでの空気の量」のようなもので、100 万のコンテキストウィンドウが欲しければその分のコストを払えるのか、という問題がある |
| harness engineering | 他人のハーネスは、信頼でき、きちんと作られ、自分のやり方に合っている必要がある。登壇者は、他人の道具を渡されてもすぐには使いこなせないのと同じだと説明した。ここで model から 1 つの agent へ進んだ。agentic の議論が始まったのは約 2 年前 |
| loop | 「終わった」と言いながら実際は終わっていない問題に対し、ループを回す。計画（コーディングなら最初に /plan を使う）、act、observe、verify、adapt が必要。それでも、最後の 60 ステップを飛ばすなど、終わったと思い込む場合がある。限界は作業が直列であること（夜に放置すると翌朝は 20 ステップ目で止まっている、という例） |
| graph engineering | 計画をサブタスクに分けると、エージェントのチームが使える。誰が何をするかを知り、互いの邪魔をせず、誰が何をしているかを追跡する。ここ 1 年ほどで広がってきたトレンド |
| ontology engineering | さらに新しい、出現しつつあるトレンド。「覚えることが増えるわけではない」と断っている。マルチエージェントの計画でも、うまくやっているつもりで実際はずれていき、一部のタスクがまったく別の方向に進むことがある、という問題への対応 |

登壇者は、ここまでが「model → agent → multi-agent」という流れで、すべてはビジネス目標を信頼して任せられるようにするためだと整理しています。

自身の失敗談も語られました。計画を信頼してエージェントに「バックエンドのツールを更新して」と任せたところ、実データが多く入っているデータを上書きしてしまい、すべきでないデータを書き換えた、という経験です。友人から「何かおかしいことに気づいたか」と指摘されて発覚した、と述べています。

### 5.2 デモ：prompt engineering と harness engineering

登壇者は、「すべてを一から教えるためのものではなく、これらが何を意味するかを見たい」として、自作のデモを見せました（"I'm going to jump to my first demo" と述べ、画面を操作しています）。

> 補足：画面の細部は音声からは確認できません。以下は、発話で語られた範囲です。マウスの調子が悪く、操作をやり直す場面がありました。

**シナリオ**：顧客が花瓶を注文したが、壊れて届いた。感謝祭（Thanksgiving）で、来週の木曜までに代わりの品を送ってほしい、と依頼してくる。

**prompt engineering のケース**

1. 顧客からのリクエストをエージェントに送る。
2. エージェントはプロンプトでリクエストの構造化の仕方を知っており、その注文を確認し、画像が本当に壊れた花瓶かを確認し、応答を返す。
3. 登壇者は、画像を見て「確かに壊れている」と判断できるモデルが必要になるだろう、とも述べている。

登壇者は、これは典型的なものだと述べ、ここからより高度なものへ進むと説明しました。

**harness engineering のケース**

1. 同じリクエストを送る。
2. 画面にアクティビティが表示される。エージェントは画像を見て、バックエンドを確認する。必要なことをするためのハーネスを備えている。
3. それらをつなげて、「返金が妥当」あるいは「何かを返すのが妥当」といった結論を出す。

登壇者は、最初のケースではプロンプトに対してモデルが応答を返すだけだったのに対し、ハーネスがあるとツールなどを使って特定のタスクを達成できる、と対比しています。そして、graph engineering の説明に重点を移すため、ここでデモを切り上げています。

### 5.3 graph engineering のマルチエージェントシステムに必要な要素

スライドに戻り、「graph engineering のマルチエージェントシステムを作るには何が必要か」を、同じ花瓶のユースケースで順に説明しています。

**(1) タスクの分解（decompose）**

まず、タスクを整理する方法が必要です。分解そのものをエージェントが担うこともあれば、それが得意なモデルが担うこともあります。ここで、タスクに合った適切なモデルを選ぶことが重要になります。

**(2) ワークフロー**

次にワークフローです。決定的（deterministic）なものでも、自分で考えるエージェントでも構いません。最近は「decision model」のようなものを耳にする機会が増えている、とも述べています（モデル名は聞こえた表記が不明瞭で、"decision API from Azure OpenAI" のような語が聞こえますが、音声認識の都合で確定できません）。

花瓶のケースで必要になるのは、次のようなエージェントです。

- 写真を検査するエージェント
- 注文を確認するエージェント
- 在庫を確認するエージェント
- クレーム（claim）にアクセスするエージェント
- 返金か新品の送付か、といった選択肢を、文脈（来週木曜までに欲しい、感謝祭である）を踏まえて判断するエージェント

**(3) graph engineering と state machine の違い**

登壇者は、state machine は以前からあったと述べ、違いを問いかけました。答えは、「違いはとても小さいが重要」で、**各ノードが自分の好きな方向に進める state machine**、というものです。こう考えると、それらのエージェントをどうやって 1 つの方向に進ませるか、という発想になる、と説明しています。

**(4) エージェント同士のやり取り**

次に、どう互いに話すかです。例として、コーディネーター（coordinator）が、視覚の専門エージェント（visual specialist）や、注文の専門エージェント（聞こえた表記は "culture order specialist"。音声認識の都合で確定できません）と話し、それぞれが「それが自分の仕事」と言う構成が挙げられました。さらに、「自分の仕事をしているか」を確認するエージェントを加える案も述べられています。他人の仕事に踏み込ませないために、タスクをサブタスクに分解することが極めて重要、という説明です。

**(5) 状態の保持**

次に、やっていることの状態を保持する場所（state machine など）が必要です。登壇者は、長い作業を依頼したときに SQLite のようなものが作られるのを見たことがある人もいるだろうと述べ、状態を保持して覚えておく必要があるからだと説明しています。写真、注文、ポリシーをどこに保管するかも、ここで決まります。

**(6) 進化（evolve）の仕組み**

ただし、ここまででは graph engineering を達成したことにはなりません。次の問いは、**システムが時間とともにどう進化するか、毎日動かすことで良くなっていくか**です。登壇者は、「今日のシステムの多くは graph structured だが graph engineered ではない。graph engineered になるには、それを進化させる方法が要る」と述べています。

**(7) ontology**

同じ例で、エージェントは「何が有効か」を知る必要があります。モデルは何かで学習されており、例えばカスタマーサービスで学習したモデルが、そこで学んだ「良い」タスクを、あなたのケースでも良いと考えてしまうかもしれません。そうならないよう、何が有効で、何が許されているか、ポリシーなどを知っている必要があります。

そこで**共有されたモデル（構造）**を持ちます。推論、エンティティ、関係、制約をすべて 1 か所に置き、良いか悪いかを知る必要があるエージェントは、その 1 か所を参照します。マルチエージェントシステムの多くは multi-model になるため、これが重要だと述べています。登壇者は、「GPT の "Luna"（聞こえた表記）が、"Kimi-K3" のようなものと同じ振る舞いをすると誰が言ったのか」と問いかけ、共有された考え方を持たせる方法がこれだと説明しています（モデル名は音声認識の都合で確定できません）。

**(8) 作業への適用**

ゴール、エージェント、能力、根拠、ポリシー、状態、結果が揃ったら、それを作業に適用します。「誰が行動してよいか」を決めるコーディネーターが、これらの作業全体を調整します。

**(9) 実行時の強制（統制と測定）**

最後に、実行時にどう強制するかです。登壇者は、エージェントがやってしまうと 100 万ドルかかるかもしれない、予算はどこにあるのか、誰が「これは許可しない」と言うのか、と問います。ロボットに「靴を全部きれいにして」と頼んだところ、全部捨てれば終わりだと判断する、という例も挙げました（終わってはいるが良くない）。何が理にかなっているかを定義し、**統制（governed）され、測定（measured）される**必要がある、という説明です。

### 5.4 Microsoft Foundry での実現

時間が 7 分ほど残った時点で、登壇者は Foundry に切り替えました。高レベルの紹介が目的で、コード、サンプル、全体を一から作る方法を含む GitHub のリポジトリ（聞こえた表記は "report"）を用意する、と述べています（具体的な URL は語られていません）。

Foundry を選ぶ理由として、登壇者は次の点を挙げています。

- 欲しいモデルがすべてそこにある
- エージェントは、それぞれが専用の micro VM に収まり、noisy neighbor にならない
- 知識、ツール、コントロールプレーンなどがすべて 1 か所にある

以下は、Foundry の画面を見ながら語られた内容です（画面の細部は音声からは確認できません）。

#### モデル

- Microsoft のモデル、Azure OpenAI のモデル、パートナーである Fireworks のモデルなど、欲しいモデルを使える。自分で作ったモデルを持ち込むこともできる。1 つのモデルに縛られない。
- 登壇者が「過小評価されているドロップダウンの 1 つ」と呼ぶフィルターがある。多くのテストに基づくもので、小さなサブエージェントのように 1 つのことだけをうまくやるモデルが欲しいときに、このフィルターを使うと、**約 11,000 のモデルから**絞り込んだサブセットが得られ、さらに絞り込める（どのフィルター項目かは音声からは特定できません）。

#### エージェント

- 先に話したエージェントは 1 か所にまとまっている。
- エージェントは、宣言型（declare するもの）か、コードベースのエージェントのどちらか。コードベースの場合は、micro VM で動く Docker コンテナを持ち込み、Microsoft のものではなく自分のハーネスや、他で作ったものを使って、自分の望む形で動かせる。
- パートナーの多くは、Foundry、AWS、GCP で動かす必要があるエージェントを持っている。同じエージェントを使い回せ、テンプレートも持てる。
- すべてのエージェントが 1 か所で動くと考えるのは素朴だ、と登壇者は述べ、Azure と AWS の初期の頃になぞらえている。外部のエージェントも、この議論に参加させたければここに持ち込んで、自分のエージェントと同様にモニタリングなどができる。

#### toolboxes

- エージェントが必要とする小さなユーティリティ。例として、請求書の価格をフォーマットするようなものが挙げられた。そうしたツールもエージェントに与える。
- ここで登壇者は、前のスライドの流れ（model、agents、tools）に戻っている。

#### Foundry IQ（知識）

- 知識はコンテキストであり、そのために Foundry IQ がある。「単なる検索か」とよく聞かれるが、それ以上のもので、**どこにある知識でも 1 つにまとめる**手段だと説明している。
- 知識はあちこちにあり、Work IQ、MCP サーバー、Fabric、Snowflake、Databricks など何でもあり得る。それらを 1 か所にまとめることが重要だと述べている。

#### トレース、モニタリング、評価

- 動き出したら、トレースで、何をしていたか、いつ、いくらかかったか、何を呼んだか、どのツールを呼んだかを確認したい。
- graph engineering では自己進化が必要と述べたとおり、システムはモニタリングされ、利用から学習する必要がある。
- モニタリング画面では、コスト（これまでにかかった額）、エラーなどが見られる。
- 評価（evaluation）：登壇者は、見せるために 1 つの evaluation を実行した。注目点として選んだのは、出力品質（output quality）、ツール使用（tool usage）、タスク完了（task completion）。
- そのエージェントは出来の良いものだったが、望んだとおりには動かず、**実際には失敗していた**。理由を知りたいので、結果を選んで「分析」を実行し、あるモデルを使って分析した（33 秒）。結果は、計画に問題があることを示した。なぜそうなったかも掘り下げられる。
- これを手作業でする必要はなく、データは **Foundry SDK 経由で利用でき、自分のアプリに統合できる**。

## 7. 注意点・発表者の気付き

- プロンプトは、モデルを替えると以前のものが通用しなくなることがある。
- コンテキストウィンドウには限界があり、100 万のコンテキストウィンドウにするならそのコストも考える必要がある。
- ループ型エージェントは、終わっていないのに「終わった」と判断したり、手順を飛ばしたりする。また作業が直列になる。
- マルチエージェントでも、うまくやっているつもりで、実際は逸脱していくことがある。
- 登壇者自身の失敗談として、計画を信頼して任せたところ、実データを上書きされてしまった。
- 実行時には、予算、許可されない操作、何が理にかなっているかの定義、統制と測定が必要。
- 他人のハーネスは、信頼でき、きちんと作られ、自分のやり方に合っている必要がある。
- 登壇者は、「graph structured」と「graph engineered」を区別している。後者には、システムを進化させる仕組みが必要。

## 8. 利用者にとっての利点

発表で Foundry について語られた利点は次のとおりです。

- 欲しいモデルが 1 か所にあり、自分のモデルも持ち込める。約 11,000 のモデルから、絞り込んで選べる。
- エージェントを宣言型またはコードベース（Docker コンテナ）で作れ、micro VM で隔離される。自分のハーネスを使える。
- 外部で動くエージェントも持ち込んで、モニタリングなどができる。
- toolboxes でユーティリティをエージェントに与えられる。
- Foundry IQ で、さまざまな場所にある知識をまとめて扱える。
- トレース、モニタリング、評価で、コスト、エラー、失敗の理由を確認できる。データは Foundry SDK で取得し、自分のアプリに統合できる。

## 9. まとめ

LLM の使い方は、prompt、context、harness、loop、graph、ontology と段階的に進んできました。登壇者は、複数のエージェントに任せるには、タスクの分解、ワークフロー、エージェント間の連携、状態、進化の仕組み、共有された ontology、実行時の統制と測定が必要で、それが graph engineering だと説明しました。

Foundry には、モデル、エージェント（micro VM）、toolboxes、Foundry IQ、トレース、評価がそろっており、データは SDK で取り出せます。コードとサンプルを含む GitHub リポジトリを用意すると述べられていますが、URL は発表では示されていません。時間が足りず、Q&A は行われませんでした。
