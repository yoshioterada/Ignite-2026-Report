# BRK249 From traces to better agents: The Foundry improvement loop

## 1. はじめに

エージェントを作ることは出発点にすぎず、本番で改善し続けることが本当の仕事です。このセッションでは、Microsoft Foundry が提供する「トレース → インサイト → 最適化 → 評価」という改善ループを、実際のデモと NTT DATA の事例で紹介しています。

多くのチームはエージェントのトレースを取得し、オフライン評価も行っています。しかし、本番のトラフィックを評価し、その結果をエージェントの改善に使えているチームは多くありません。発表では、**Foundry ならこのループを 1 か所で回せる**と説明し、デモでは 1 回の最適化で評価スコアが 36% から 89% に上がる様子を示しています。

エージェントを本番運用している、あるいはこれから運用する開発者・運用担当者に向けた内容です。

## 4. 発表者が伝えたいメッセージ

発表者は、「誰も初日から最高の仕事をするわけではなく、優れた人はフィードバックを受けて成長する。エージェントも同じであるべきだ」という考えを示しています。ループがなければ、すべてのチェックが緑のままエージェントが静かに悪化し、ユーザーが最初に問題を見つけることになります。ループがあれば、1 人の専門家のフィードバックが全員にとってより良いエージェントになり、すべての変更が測定されます。

そのうえで、1 つの場所で次の 3 つの立場を支援すると説明しています。

- 開発者：Insights で失敗箇所を見つけ、Agent Optimizer で修正をテストする
- 専門家（subject matter experts）：トレースに平易な言葉で注釈を付ける。その判断が、エージェントが通過すべきテストになる
- リーダー：どのバージョンも前のバージョンより良いことの証拠を得る

Foundry で動くエージェントでも、Foundry がトレースを見られる限り他の場所で動くエージェントでも使える、とも述べています。

### 5.1 課題：見えているのに、改善に使えていない

冒頭で、トレースを設定している人、評価を実施している人、本番トレースに評価をかけている人の順に会場へ挙手を求め、これは業界全体で一貫して見られるパターンだと説明しています。

発表者が挙げたデータは次のとおりです（出典と数値は発表での紹介のまま）。

| 出典 | 内容 |
| ---- | ---- |
| LangChain（昨年、1,300 超のチームを調査） | 9 割近くが何らかの observability を持ち、多くがオフライン評価も実施。しかし本番トラフィックを評価するチームは急に減る |
| McKinsey | 74% が「不正確さ」を最も関連性の高いリスクと位置づけた（他のどのリスクよりも多い）。なお発表では、報告された AI インシデントが昨年過去最高だったとも述べている |
| Gartner | 約 40% の組織が AI エージェントを格下げまたは廃止すると予想 |
| EY | 調査対象のほぼ全社（99%）が AI 関連リスクで損失を経験。3 分の 2 近くは 100 万ドル超 |
| 今夏の調査 | 61% が、評価を通過した後に顧客向けの障害を経験した |

本番では、ユーザーや他のエージェントが、オフライン評価では想定しない形でエージェントに話しかけます。ステータスコードは緑、評価も合格なのに、静かに誤った答えを返し続けることがあります。チームはトレースを手で読むか、トークンを使ってコーディングエージェントに貼り付けて切り分けています。ツール呼び出しやロードしたスキルごとに、誰にも見えないコストが積み上がり、リーダーはエージェントが運用する価値があるのか判断できません。

### 5.2 デモ 1：Caldova Pharmaceuticals の調査エージェント（Charles 氏）

今週の Ignite で何度も登場するエージェントとして、Caldova Pharmaceuticals の調査エージェントが紹介されました。R&D プログラムを投資の観点で評価するエージェントです。

Charles 氏が画面で実行した内容を、語られた順に書きます（画面の細部は音声からは確認できません）。

1. エージェントに「North Star Separation Science の状況は？」と質問する
2. このエージェントは Foundry 上のホスト型エージェントで、Foundry の toolbox を使ってデプロイされている。裏では Fabric の接続（Fabric IQ）を通じて、各部門・各プログラムに次々とリクエストを送り、情報を集めている。応答までに時間がかかる長時間実行型のエージェントであり、単純なプロンプトと応答よりも実際の作業を行っている
3. 応答が返る。エージェントは「条件付きの評価」を返し、いくつかのフォローアップ（製造部門の担当者などへの確認）が必要だと述べた
4. Charles 氏の不満は、エージェントがもっと能動的に各部門と連携し、投資判断のために何を調整すべきかを示してほしかったのに、人間が各部門に連絡する前提の回答だったこと

Charles 氏によると、このエージェントは財務・計画チームの全員がしばらく前から使っており、顧客環境で動くエージェントは毎週フィードバックを返す必要があります。Charles 氏は、エージェントのオーナーとしての現在のやり方を説明しました。

- 回答と質問をスプレッドシートに書き出す
- 1 件ずつ良い・悪いのラベルを付ける
- どの部門の確認が漏れたかを記す（例：「この回答は clinical は見たが regulatory を見ていない」「この回答は manufacturing が漏れている」）
- プロンプトをどう更新すべきかのメモを書き、次回は良くなると期待する

手作業が多いやり方です。ここで Avinav 氏が割り込み、エージェントが調査を省いて、人が手で調査しているのでは、と指摘しました。

### 5.3 従来の改善方法と、Foundry の改善ループ

Avinav 氏は、多くのエージェント開発者のやり方を次のように整理しています。ユーザーが問題を報告する（フィードバックまたは苦情）。開発者がトレースを 1 つずつ読み、修正を推測し、再デプロイして、次の苦情まで様子を見る。

これに対し Foundry では、「フィードバックループを登ること（hill climb）」を目標にしています。**Insights が問題を見つけ、Optimizer が解決策を提案し、Evaluation が修正を検証する**という分担です。

### 5.4 デモ 2：Insights、Annotation、Agent Optimizer、継続評価（Avinav 氏）

Avinav 氏が、Charles 氏が使っていたエージェントを開いて進めました。語られた順に整理します。

**(1) トレースに注釈を付ける**

1. トレースビューで直近の会話を見て、Charles 氏が行っていた長時間の会話を探す。会話ビューの中で annotation を行う
2. Charles 氏がスプレッドシートに書いていたことを、ここに書く。まず「やり取りは良くなかった」という評価を付ける
3. 専門家として、失敗した項目は「タスクの結果（task outcome）」で、「partial success」と付ける。答えは返したが、求めていた答えではなかったという意味
4. 本来どうあるべきかも書く。「応答する前に、ユーザーがアクセスできるすべての部門を確認すること」
5. 複数の会話に同様に注釈を付けて保存できる。この実際のフィードバックは、トレースと一緒に Foundry に記録される

**(2) 最適化ジョブを開始する**

1. エージェントの optimized experience で最適化ジョブを開始する。ここで紹介された新機能が **learn from past activity** で、注釈付きのものも含めてトレースを見て、次に何を最適化すべきかを判断する
2. 指定する項目は、エージェントのバージョン（Charles 氏が使っているのは agent 1 の version 1）、スキル（今回は空欄）、見るトレースの期間、最適化用のモデルと評価用の judge モデル。トレースは自動的に検出される
3. 実行には時間がかかるため、出力例を先に示した。オプティマイザーはトレースから、エージェントがすべての部門を見ておらず、追加のプロンプトを必要とする未解決の質問が多く残っていると突き止めた
4. 改善策として、すべての部門を見るようにする新しい**スキル**を提案する。スキルは基本的にエージェントのワークフローを良くするプロンプトで、従うべき例も含む
5. 判断に使ったデータも確認できる。学習とスキルを導くためにクラスタ化されたトレースの数が分かる
6. このエージェントのバージョンとスキルを本番に昇格させて、公開できる

**(3) 問題を先に見つける：Agent Insights**

ここまでは、ユーザーの苦情が来てから注釈を付ける流れでした。顧客に言われる前に問題を見つけたいので、Agent Insights を使います。**Agent Insights は GA** で、ユーザーが直面している失敗を検出し、クラスタ化・グループ化し、順位付けして、切り分けできるようにします。Insights から直接最適化に進むこともできます。

デモでは 1 つの insight を見せ、Charles 氏が顧客視点で見ていたものに加え、さらに多くの失敗があることを示しました。部門への呼び出しは行われているものの、設定が不足していた、という内容です。その失敗を示すトレースと、構成（config）での修正案が示され、その修正を行ってエージェントの 2 つ目のバージョンをデプロイしました。

**(4) 検証：継続評価（continuous eval）の作成**

評価体験で、改善が効いているかを示す検証テストを作ります。今後は新しいエージェントがベースラインになります。語られた手順は次のとおりです。

1. 作成（create）を押し、ターゲットにエージェントを選ぶ（Charles 氏が使っていたエージェント）
2. 対象は full conversations、ライブトラフィックをサンプリングして評価する。サンプリング率や 1 回の実行に含めるトレース数も変えられる（トレース数の指定は「very soon」と言っているように聞こえますが、音声からは確定できません）
3. 基準（criteria）は、quality criteria に加えて、自分で作った custom rubrics を選ぶ
4. 評価の画面では、過去の実行、スコア、エージェントのどの部分がうまく動いたかを確認できる。エージェントの monitor タブでも、過去の実行と評価スコアを見られる。custom rubric を使っているので、評価の readiness がここに表示される

**(5) 結果の確認（Charles 氏が version 2 を実行）**

Charles 氏が、最適化して新バージョンとしてデプロイした version 2 に、同じ質問を投げました。各部門に連絡するため、時間がかかる想定で、バックグラウンドで実行しました。実行中に、Avinav 氏が結果を整理しています。

| 項目 | 最適化前 | 1 回の最適化後 |
| ---- | ---- | ---- |
| 評価スコア | 36% | 89% |
| 最終的な答えに至るまでのフォローアップ | ユーザーが何度も促す必要があった | 3 回に減少 |

最終的な答えとは、clinical、manufacturing、finance などを含む、全部門のプログラム更新のことです。これは**1 回の最適化だけ**の結果で、継続的な最適化により、さらに改善を続けられると述べています。

終盤に version 2 の回答が返りました。Charles 氏は、エージェントがすべての部門に連絡し、ギャップを整理して、投資のやり方についての推奨まで自動的に出したことを確認しました。Charles 氏がしたのは奇妙な挙動を伝えただけで、オプティマイザーがその先を解決した、と述べています。

### 5.5 ループを構成する機能と提供状況

ループの各ステップを機能に対応づけ、提供状況が示されました。

| ステップ | 機能 | 提供状況（発表での説明） |
| ---- | ---- | ---- |
| 測る・注釈 | 専門家が、エージェントが動いたその場でトレースに注釈を付ける。フィードバックはテストケースになる（annotation on traces） | preview（今週から） |
| 測る・評価 | Rubric evaluators：自分の基準で品質と安全性を採点 | preview |
| 測る・評価 | Golden dataset による評価：実際のトレースを再現可能なテストにして、各バージョンをベンチマークする | preview |
| 改善箇所の特定 | Insights：繰り返し起きる失敗をトレース横断でグループ化・順位付け（デモの部門間引き継ぎの漏れなど） | GA |
| 同上 | Foundry 外で構築したエージェントのトレース | GA |
| 最適化 | Insights から繰り返し起きる問題を Agent Optimizer に直接送る。複数の修正案を評価に対して試し、出荷するものを選ぶ | preview |
| 最適化 | Skill and prompt optimization：過去のフィードバックから、エージェントの動作を改善 | preview |
| 最適化 | コストが課題のとき：cost optimization、model router、training | preview |
| 検証と繰り返し | Continuous evaluators：各バージョンをベースラインと比較し、本番トラフィックを継続的に評価する。勝った版が新しいベースラインになる | 発表では個別の提供状況は示されていません |

Foundry 外のエージェントについては、Foundry と Foundry 外のエージェントの両方に対して、**1 つの observability の画面**で insights と evals を使えると説明しています。

> 補足：トランスクリプトのコスト関連の箇所は「cost optimization, model router, and training」と聞こえますが、音声認識の乱れがあり、個々の機能の詳細は発表では語られていません。

### 5.6 NTT Data の事例

**動画（NTT Data の取り組み）**

冒頭で Charles 氏が、NTT Data は機能の開発段階から密接に協力してきたと紹介していました。デモのあと、登壇者が NTT Data が取り組みをまとめた動画を流しました。動画の内容は次のとおりです。

- NTT Data の smart AI agent アプローチの一環として、Microsoft Foundry を使って**プロジェクトマネジメント・エージェント**を開発している
- トレースと insights を含む observability で、エージェントの動作と問題箇所を把握する
- Foundry の rubric ベースの評価で、定義した基準に対する性能を測る
- Agent Optimizer で、エージェントの instructions、ツール、再利用できる PMO のスキルの改善方法を探っている。検証後に再デプロイして、またプロセスを始める
- サンプルプロジェクトでの初期見積もりでは、一部のプロジェクト管理タスクにかかる時間を**約 60%** 減らせる
- 重要なのは信頼であり、重要な判断には人が関与し続ける必要がある

**Yuji 氏：AgentOps のビジョン**

Yuji 氏は、Microsoft Foundry を使った agent ops の実践を共有すると述べ、NTT Data の smart AI agent ビジョンを説明しました。

- 中核技術として 5 つの柱（five pillars）を定めている。1・2 つ目はデータ、3・4 つ目は運用・協調の領域、最後が物理世界
- 描く世界像は、ユーザーが personal agent とチャットし、personal agent が legal agent や sales agent のような専門のエージェントを使い、さらに特定の役割を担うデジタルワーカー（デジタルヒューマン）、最後に物理世界へ広がる、というもの
- 今日の焦点は、ガバナンス、セキュリティ、品質を備えた「agent ops with harness」
- 継続的改善のサイクルを **outer cycle と inner cycle の 2 つ**で定義している。外側のサイクルは execution、observability、evaluation で、エージェントを実行し、トレースやその他のメトリクスを観察し、評価する。ここで人が関与（human in the loop）し、改善が必要かを判断する。必要なら内側のサイクル（optimization）に進み、良ければ承認してデプロイする
- 精度の向上だけでなく、信頼できるエージェントにするために、洗練されたガバナンスとセキュリティも必要

**Takashi 氏：PMO エージェント**

PMO（project management office）エージェントから始めた理由として、調整の複雑さが高いこと、プロジェクト管理の専門知識があること、測定可能なワークフローであること、の 3 点を挙げています。

アーキテクチャの概要は次のとおりです。

1. プロジェクトデータは Azure DevOps と Teams に保存されている。Teams のデータは Work IQ から取得する
2. PMO エージェントがプロジェクトの状況を監視し、リスクを特定し、レポートを作成し、フォローアップを提案する
3. プロジェクトマネージャーが出力をレビューし、提案された変更を承認する、または最終判断をする

Foundry でエージェントを改善した手順は次のとおりです。

1. トレースを集め、insights で実行の失敗と改善提案を調べる
2. データ生成機能で、トレースから評価データセットを簡単に作る
3. rubric evaluator 用に、**14 個の重み付きのビジネス固有の品質基準**を定義した
4. 生成したデータと評価に基づき、Foundry がシステムプロンプトとエージェントのスキルを最適化する

結果の例として、PMO エージェントへの質問「Atlas の task 204 の受け入れについて、チームは何を決めたか」を示しました。左は失敗した結果、右が最適化後の正しい答えです。失敗した側は、根本原因として、ある work item ID が Azure DevOps に見つからないことが示されていました（ID の数字は音声認識の都合で確定できません。「200」と「21」のように聞こえます）。最適化後のエージェントは、正しく ID を解決して答えました。

改善の効果は、rubric evaluator の品質スコアで「8.6 から 83.3」と述べています（音声認識の都合で数値は確定できません）。最適化の前後のシステムプロンプトを並べ、黄色の部分で、Agent Optimizer が「ユーザーのクエリから Azure DevOps の ID を解決する」ための指示を追加していたことを示し、これが改善の理由だと説明しました。

ビジネスへの影響として、この実験での推定は**人手の工数が 60% 減**です。PMO エージェント適用前の工数が 907.3、適用後が 364.7 とのことです（単位は発表では聞き取れません）。これは 1 プロジェクトの話で、NTT Data は日本だけで 2,000 のプロジェクトを持っているので、PM エージェントをそれらに広げたときの影響は大きい、と述べています。

**Yuji 氏のまとめ**

主な教訓は、「AI エージェントの改善は、ビジネスにとっての品質とは何かを定義することから始まる」ことだとしています。エージェントがどう振る舞い、どこでつまずくかを理解し、改善が効いているかを測る。これが agent ops harness で目指していることです。Microsoft と Microsoft Japan との協業が、その方向への重要な一歩を支えたと述べ、今後もより多くの企業ワークフローに広げたいとしています。

### 5.8 始め方と関連セッション

多くの内容に圧倒されるかもしれないが、一度にすべてを直そうとせず、次の順で進めるように勧めています。

1. 1 つのエージェントと 1 つの問題を選ぶ
2. 専門家に少数のトレースを評価してもらい、ベースラインを作る
3. トレースを有効にし、insights に失敗の順位付けをさせる
4. 上位の問題を Agent Optimizer に送り、候補を比較して 1 つを選ぶ
5. ベースラインと比べて測り、もう一度回す

Foundry 外で動くエージェントについては、observability for external agents が GA で、OpenTelemetry のトレースも取り込めます。1 つ目の QR コードで Microsoft Foundry のスタート、2 つ目で agent optimizer のドキュメントに進めます。

### 5.9 Q&A

**Q1. GitHub Copilot、Claude Code、Codex を Foundry の中で運用できるか。それとも MCP エンドポイントなどを自分で作る必要があるか。**

Microsoft 側の登壇者は、「Foundry の中で運用する」とは GitHub の harness などを使うエージェントをホストするという意味か、と確認したうえで、managed harness の体験があると回答しました。プレビューに参加できるので連絡してほしいとのことです。現在のエージェントの種類は prompt と hosted で、harness 型のエージェントを今後さらに提供していくと説明しています。

**Q2. 最適化は継続的な改善を見るものだが、知識や情報の不足が問題の原因である場合はどうなるか。オプティマイザーが情報を収集し、組織のメモリやナレッジベースを作るロードマップはあるか（自動車業界のクライアントのケース）。**

Microsoft 側の登壇者の回答の要旨です。

- 結局は、トレーニングデータ（フィードバック）がどれだけ良いかに行き着く
- 「Microsoft IQ を使って、この会社の最新の財務記録を取得してほしい」のように、エージェントに期待する動作を人間のフィードバックとしてトレースに付け、Agent Optimizer に渡す。オプティマイザーはそれを学習データとして、エージェントが持つツールや Microsoft IQ などをもっと有効に使うべきかを見て、変更案を出す
- 変更案の例：プロンプトの指示を、環境の使い方についてより明確にする。スキルを更新し、必要に応じて正しくロードさせる。ツールの説明や、いつツールを呼ぶかの記述を改善する。エージェントは適切なタイミングでツールを使うことを忘れがちだと述べている
- ナレッジベースを自動で作るロードマップがあるかには、直接の回答はありませんでした

**Q3. トレースは主に AI エンジニア向けだが、エージェントのユーザー自身がフィードバックを返す（単なる thumbs up/down ではなく「これは違う」と言える）ロードマップはあるか。**

NTT Data 側の登壇者が答えました。半年以上前から協業しており、構想には agent ops with harness が含まれている。最適化から始めるのではなく、データから始めるべきで、「garbage in, garbage out」であり、データが非常に重要だという考えです。標準的な運用ドキュメントなどから始め、人の頭の中にある専門知識を、本番の活動を通じて引き出す必要があり、そこで継続的な改善が生きる、とも述べています。ユーザーからのフィードバックのロードマップについて、Microsoft からの回答は発表では語られていません。

**Q4. NTT Data は、事業でエージェントの運用を始めるうえでどんな課題があったか。**

NTT Data 側の登壇者の回答です。agent ops の確立は 2 年前（2024 年の初め頃）に始めた。当時は AI 分野で支援ツールが少なく、自分たちで構築した。金融、公共、エンタープライズなど各分野に複数のユースケースがあり、基本的にオープンソースのフレームワークをベースにしている。今は Microsoft から提供される機能で簡単に実現でき、2 年前と比べて劇的な変化だと述べています。

## 7. 注意点・発表者の気付き

- ステータスコードが緑で評価に合格していても、エージェントは静かに誤りを返し続けることがあります。本番トラフィックの評価が必要だという主張です。
- 提供状況が機能ごとに異なります。Agent Insights と、Foundry 外のエージェントのトレースは GA ですが、annotation on traces、rubric evaluators、golden dataset、Insights から Optimizer への連携、スキル・プロンプト・コストの最適化は preview です。
- デモの改善は、**1 回の最適化の結果**です。Avinav 氏は、継続的な最適化で改善を続けられると述べています。
- 始めるときは、すべてを一度に直そうとせず、1 つのエージェントと 1 つの問題に絞ります。
- 最適化の質は、与えるフィードバック・トレーニングデータの質に左右されると説明しています。NTT Data 側も、最適化の前にデータから始めるべきだと述べています。
- エージェントはツールを使うタイミングを忘れがちで、ツールの説明が最適化の重要な要素になるという気付きが共有されました。
- NTT Data の PMO エージェントでは、人が判断に関与し続けること（human in the loop）が前提です。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **改善が数値で確認できる**：デモでは、評価スコアが 36% から 89% に、最終回答までのフォローアップが 3 回に減少した（1 回の最適化後）
- **苦情の前に問題に気付ける**：Agent Insights が失敗をクラスタ化して順位付けする
- **専門家の判断を再利用できる**：annotation が、エージェントが通過すべきテストになる
- **Foundry 内外のエージェントを 1 画面で**：Foundry 外のエージェントも、同じ observability の画面で insights と evals が使える
- **NTT Data の PMO エージェント**：サンプルプロジェクトで人手の工数を約 60% 削減する見積もり（907.3 から 364.7）。ルーブリックの品質スコアも大きく改善した。日本だけで 2,000 のプロジェクトがあり、横展開の余地がある
- **コスト面の事例**：DocuSign は AI の処理コストを 90% 削減、Heidi は 1 ノートあたり推定 87% 低いコストで frontier モデル並みの臨床品質、Mazda は task adherence と groundedness が 96%

## 9. まとめ

このセッションの要点は、トレースを取るだけでなく、それを使ってエージェントを継続的に良くするループを回す、ということです。Foundry では Insights が問題を見つけ、Agent Optimizer が修正案を作り、Evaluation が改善を検証します。専門家の注釈がテストになり、勝ったバージョンが新しいベースラインになります。

Caldova の調査エージェントのデモでは、全部門を確認しない問題が、注釈と最適化で解消し、スコアが 36% から 89% に上がりました。NTT Data は、PMO エージェントで同じループを実践し、約 60% の工数削減を見込んでいます。

始めるなら、今週のうちに 1 つのエージェント、1 つの問題でループを 1 周回すことが勧められています。
