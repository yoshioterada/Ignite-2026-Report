# BRK275 What should you build when you can build anything?

## 1. はじめに

このセッションは、AI で「何でも作れる」時代に、開発者は何を作り、どう AI と付き合うのかを、3 人の登壇者の実例で見せる 45 分の Breakout です。製品の機能解説やアーキテクチャの説明ではなく、各自が GitHub Copilot などを使って作った、少し風変わりで、本人にとって意味のあるアプリのデモが中心です。

登壇者の主張は一貫していて、「AI にワンショットで作らせるのは party trick で、平均的な（mid な）ものにしかならない」「そこに自分の好みと専門性を入れ、学びながら作ることで、AI を使っても『タイピングが終わっても、考えることは終わらない』」というものです。デモはロールコースター・タイクーンへのモデル組み込み、中国語の声調練習アプリ、GPU のモニタリング TUI の 3 本で、最後に GitHub 提供の景品をかけたトリビアと、Copilot の使い方のヒントで終わります。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK275](https://ignite.microsoft.com/en-US/sessions/BRK275)\
YouTube URL: [https://www.youtube.com/watch?v=v-qx7J2S43Q](https://www.youtube.com/watch?v=v-qx7J2S43Q)

## 3. 何に関する発表か

メタデータの概要は、Windows、GitHub、OSS、新しい技術を、デモの連続で巡る「お祭り」のようなセッション、というものです。実際の流れは次のとおりでした。

1. Scott 氏の導入: ワンショットのデモは平均的な出来になる、という話と、AI への不安に対する立場
2. Anthony 氏: OpenRCT2 に small language model と decision model を組み込む
3. Katie 氏: 中国語の声調を練習する Web アプリ Tone Mirror
4. Scott 氏: GPU の状況を見る TUI アプリ GPU Task Man
5. トリビア（景品は GitHub のキーボード）
6. まとめと、Copilot の使い方の tip

セッションの題名にある「何でも作れるなら何を作るか」への答えは、特定の製品や技術ではなく、各自が学びたいこと、困っていること、面白いと思うことを起点にする、というものです。

## 4. 発表者が伝えたいメッセージ

Scott 氏は冒頭で、今は不安定な時期で AI は居心地が悪い、と認めたうえで、次のような考えを述べました。

- **ワンショットは party trick。** 職場の若手が「Minecraft をワンショットで作った、ソフトウェアは終わりだ」と言ってきた、という話から始まります。プロンプトは「make me a clone of Minecraft」の 6 語で、「Minecraft」という単語に意味が詰まっていて、その単語を出した時点でモデルはその意味空間（登壇者の言葉では gravity well）に入る。それは出荷するコードでも、人間ならではの創造性でもない、という指摘です。
- **平均（mid）に引き寄せられる。** 正規分布の絵を描き、左が出来の悪いもの、右が優れたもの、真ん中が mid で、LLM が世界中の知識をミキサーにかけたスムージーは灰色になる、と説明しました。
- **人間の趣味と専門性で右へ押す。** 例として、自分は design が得意でないので Azure Friday のサイトを AI に作らせたところ、きれいだが平均的なものになった（text gradient が好きなモデルだと分かる、と冗談を交えています）。そこで自分の好みを入れて GeoCities モードを作り、さらに Tiny Tool Town というサイトを作った、という流れです。
- **これは 4 つ目の 10 年にわたるパニック。** 新しい技術のたびに人々がパニックになる状況が、すでに 4 つ目の 10 年に入っているという指摘です。1980 年代には C 言語を使うと「本物のプログラマーではない」と言われ、1990 年代にはカラーモニタと IntelliSense、その後は Stack Overflow が話題になりました。今回の「コーディングの終わり」も同じ種類のパニックだと位置づけています。
- **危険は「悪いコード」ではなく、小さく、使い捨てで、監視されているように感じること。** 目指すのは、力を得て、楽しく、また自分にできると感じることだと述べています。
- **ある強い調子のツイートへの反論。** 画面に示された投稿（内容は発話では読み上げられていません）に対し、「それが仕事のすべてだ、という部分には同意しない」と述べ、仕事は創造的で、活力を与え、成長させるものだと説明しています。学位で身についたのは、個々の技術ではなく「学び方」だった、とも述べています。
- **meat proxy にならない。** 上司の質問を Copilot に投げて、返ってきた答えをそのまま伝えるだけの存在を指す言葉で、出てくるのは mid なものだ、と説明しています。同席者の一人が、学び方を学ぶだけでなく、どこに時間を使うかを意図的に選ぶことも大事だと補足しました。
- 結論として、「タイピングは終わるかもしれないが、考えることは終わらない」。

3 人の登壇者は、自分が積み上げてきた自信を聴衆にも渡したい、という目的も述べています。

### 5.1 Scott 氏の導入（GeoCities モードまで）

### 5.2 Anthony 氏: 自分が OSS から遠ざかった理由と、学び直し

- 昨年の Build 2025 では、Katie 氏と一緒に、ライブ配信で言語を vibe coding した。それはあの 14 時間の言語よりずっと良い出来で、複雑なものを作って限界まで挑戦する「苦労と面白さ」が薄れた、と感じた、と述べています。

- 学んだことの 1 つは、AI モデルがデバイス上でどう動くか、チップのレベルで何が起きるかで、過去 1 年、Surface チームと Windows チームに、デバイス上の AI モデルの性能改善に関する contribution をしてきたと話しました。デモで使った PC は Surface Laptop Ultra（登壇者は「Surface Ultra」とも発言）です。

### 5.3 Anthony 氏のデモの題材: OpenRCT2

Roller Coaster Tycoon は、Chris Sawyer 氏というスコットランドの開発者が、すべて x86 アセンブリで書き、デザイナーがグラフィックを担当した、と紹介されました。Anthony 氏は、このゲームを CD-ROM、箱版、Steam で持っています。デモで使うのは、人間が C で再実装したオープンソース版 **OpenRCT2** です。ゲームのアセットは、購入済みの本物を使います（Doom の WAD ファイルを使う再実装と同じ方式、と説明）。

学びたかったのは、small language model（LLM に似ているがずっと小さく、デバイス上で動くもの）と、decision model（登壇者の説明では、最近出てきた「決定」用のモデル。Microsoft の「decision one」は直近で 1.1 を出した、とのこと。名称は音声認識の都合で表記が確定できません）の 2 つでした。

### 5.4 Katie 氏: 中国語の声調練習 Tone Mirror

後述の 6.2 にまとめています。背景は次のとおりです。

- 中国語を学習中で、特に難しいのが声調（tone）。声調は音の高さの変化で、英語では感情や疑問を示すのに対し、中国語では単語の意味そのものを決める。例として ma の 4 つの声調を挙げ、mother（母）や horse（馬）の取り違えは困る、と説明しています。
- 音声認識（speech to text）自体は中国語もかなり正確で、Copilot の dictation で「nin hao」を話すと正確に書き起こされた。しかし、1 音節ごとに声調を機械的に身につけたい場合には、同じ文字になってしまい、確認できない。Qwen 3（聞こえた表記）でも同様の問題があった、と述べています。
- 通常の使い方では 1 音節だけを言う場面はないので、モデルが得意でなくても無理はない、しかし練習には必要だ、という整理です。

## 6. デモ・手順

> 補足：録音は音声のみで、画面の細部は分かりません。以下は発話で語られた範囲です。

### 6.1 Anthony 氏のデモ: Roller Coaster Tycoon 2（OpenRCT2）に AI を組み込む

1. **small language model で「ゲストの内なる声」を表示する。** ゲームを再開し、ゲストの Lisa が入園したところを見せる。通常のゲームでは、ゲストの考えを示す画面を見て過ごす。多くは「吐きそう」か「トイレに行きたい」で、約 900 人の幼児を管理するようなものだと説明。そこで **Llama CPP**（AI モデル用の推論ランタイム）をゲームに組み込み、small language model を動かして、ゲストが本当に何を考えているかを表示した。Surface Laptop Ultra 上で完全にローカルで動く。トイレに行きたい Adam という別のゲストを選んで、思考を見せた。
2. モデルは 15 億パラメーターのもので、Hugging Face から既製のものを取ってきて、学習はしていない。「ラップトップの力で数千億回の計算をしている」という合いの手が入り、Anthony 氏は「まったく無意味だが、楽しいからやった」と述べた。
3. **decision model に置き換える。** ゲストが次にどこへ行くか（どの乗り物に乗るか、トイレに行くか、吐くか）を決める元のロジックを取り外し、decision model に置き換えた。人がオンラインでモデルにゲームをプレイさせる動画は見たが、自分はプレイしたいので、モデルにゲストの判断を任せた、と説明している。
4. ゲストの例として Pat を選び、幸福度、エネルギー、空腹、好みの乗り物の強度（4 より大きい）、吐き気への耐性（整数のスケール）といった状態が使われることを示した。
5. 900 のエンティティの欲求や感情を LLM に入れるのは誤った使い方で、LLM は「乗り物に乗りたくない」などと脱線しかねない。decision model は strongly typed で、桁違いに速く判断する、という説明。ゲストごとに 1 つのモデルが割り当てられ、すべてラップトップ上のローカルで動く。ゲストを選んで一時停止すると、どの乗り物（Double Drop、Splash Mine、Brainstorm など）に行くかの確率が見える。
6. ゲストが緑と青のセーターを着ているのは、**2 つの decision model の A/B テスト**のため。A と B の群を色で見分けられ、例えば緑のゲストが隅で動けなくなっていれば、そのモデルにバグがあると分かる。
7. **fine-tuning。** ゲームの中で最適化したい指標を「happiness（幸福度）」にした。幸福度は各ゲストに割り当てられた数値（最近吐いたかなどが関係）。decision model を使ってシミュレーションを時間をかけて回し、全ゲストの平均 happiness を取る。それを使って **Unsloth Studio**（聞こえた表記は UnSloth Studio。ローカルでモデルを動かし、fine-tune できるツール）で fine-tuning を行った。
8. Anthony 氏と GitHub Copilot で、happiness を最大化するように fine-tune する学習プロセスを組み立てた。Copilot は研究アシスタントとして、パラメーターの説明をし、Unsloth Studio を操作してボタンをクリックすることもできる、と述べている。
9. 時間を早送りして、2 つの群の反応を観察した。

Anthony 氏は、これで儲けるつもりはなく（元の所有者に失礼なので）、Microsoft の decision one（聞こえた表記）にも、評価や fine-tuning、社内のどの問題に向くか向かないかについて意見を出すなど、貢献していると述べています。Scott 氏のまとめは、既製の small language model で内なる声を作り、fine-tune した decision model で毎秒数百〜数千の判断をし、名前や文字列の変更などの小さな改善も加え、すべてを GitHub Copilot と Surface Laptop Ultra、Windows 上で作った、というものです。

### 6.2 Katie 氏のデモ: Tone Mirror

1. 中国語の dictation で「nin hao」と話し、ほぼ正確に書き起こされることを見せる。
2. ma を 4 つの声調で言うと、同じ文字に書き起こされて声調の違いが分からないことを見せる。Qwen 3（聞こえた表記）でも似た結果だった。
3. 自作の Web アプリ **Tone Mirror** を紹介。練習できる音節の一覧があり、高品質のネイティブ話者の参照音声が得られたものが選ばれている。参照音声を聞き、自分の音節を録音すると、ライブのピッチ情報が画面に出て、参照話者のピッチと比較して表示される。
4. 評価の仕組み: マイク入力の音声が、まず品質チェック（途切れや、自分の声ではないようなピッチの飛びがないか）を通り、次に **YIN アルゴリズム**でピッチを抽出し、ピッチの変化にいくつかのルールを適用して判定する。デモでは第 1 声（高く平ら）を通過した。ピッチの幅が小さく（平ら）、高さが高いことが条件として語られた。
5. 第 4 声（ba）を試して、評価されなかった。声調を正しく出せていなかった可能性もあるが、設定がデフォルトの声調範囲だったことも理由として挙げ、人によって声の高さの範囲が違うため、**キャリブレーション**の手順を追加したと説明。実際に短時間でキャリブレーションを行った。
6. 第 3 声: 範囲の最低点で「creaky（きしむ）」音が入り、当初は音が途切れた無効な録音として捨てられていた。Copilot と作業して追加ルールを入れた。低い→高い、底できしむ、少しきしんでから上がる、の 3 つのパターンを第 3 声として認める。
7. 発音処理を可視化する図を Copilot と作った。音声の録音が声調の分類に至るまでの流れを、自分の関心（大学で言語学を学んだ）のために、視覚的に確認できる。

Scott 氏の質問への答えは次のとおりです。

- 構想から今日まで約 1 週間半から 2 週間、実時間でも数時間かかった。単純にはいかず、第 3 声が拾われない理由を、ネイティブ話者に確認してもらいながら探る必要があった。
- 最初は Copilot アプリで声で会話し、「声調を自分で鍛えたい。やり方も既存のものも分からない」と伝え、既存のものを調べるセッションを立ち上げさせるところから始めた。ワンショットではない。
- 脳が大きく賢くなる感覚だったと述べている。ネイティブ話者の録音を手に入れたので、次は小さなモデルを作ることを考えている。途中で出てくる言葉が分からなくても「はい」と答えたくなるが、ペースを落として理解するようにしている、と話した。

### 6.3 Scott 氏のデモ: GPU Task Man

1. GitHub Copilot の画面で、2 つのモデルを使っていると紹介した。使っている PC は 128 GB の RAM を積み、「6,000 コアの Blackwell GPU」と述べています（数値は音声認識の都合で確定できません）。MAI Code Flash（聞こえた表記では 52 GB、1 億 3700 万パラメーターと言っていますが、音声認識の都合で正しい数値が確定できません）と、もう 1 つ（Flint と聞こえます）。
2. Windows のタスクマネージャーでは GPU の中で何が起きているか分からないため、**GPU Task Man** を作った。TUI（テキスト UI）で、実行中のアプリ・プロセスと、その中身を表示する。Llama CPP、GGML、Vulkan が表示され、プロセス内部を調べて、CPU 上で動くプロセスと渡されたパラメーターを結びつけ、いくつかの手がかりから中身を推測する。
3. テクスチャを使うプロセスや、特定のモデルを使うプロセス、温度、クロック、電力（その時点で 1 ワット）などが見える。
4. Copilot でチャットを始め（「are you there?」）、Windows のタスクマネージャーでモデルがメモリに載る様子を見ようとしたが、最初はうまくいかず、やり直した。モデルが読み込まれ、メモリは 22 GB になり、GPU Task Man で電力消費が増える様子が見えた。温度も上がり得る、と話した。
5. TUI は、「なぜそれが分かるのか」の根拠も説明してくれる。

制作には約 1 週間かかり、その後コミュニティが参加した、と述べています。動くのは自分のマシン（Windows ARM、Nvidia の N1X チップ）で、他のチップを持つ人が来て、Intel GPU や ARM 組み込み GPU を調べることになり、他の GPU・モデル・システム向けの pull request が来ている。Windows から情報を取るほか、Mac（Apple Silicon、Apple Foundation Models など）でも動かした、とのことです。

## 7. 注意点・発表者の気付き

- **ワンショットのデモは、独自性のある、出荷できるコードではない。** 意味を担っているのはプロンプト中の「Minecraft」という単語で、出てくるものは平均的なものになる。
- **meat proxy を避ける。** Copilot の返答をそのまま伝えるだけにならない。Anthony 氏と Katie 氏は、AI に任せきらず、自分で学ぶ形で使った。
- **AI の提案を理解せずに進めない。** Katie 氏は、途中に知らない言葉が多くても、ペースを落として理解するよう努めている。
- **専門性が必要な場面がある。** Katie 氏の Tone Mirror では、第 3 声のきしみ（creak）が無効な録音として捨てられるなど、言語学の知識とネイティブ話者による確認が必要で、Copilot と協力して解決した。
- **decision model と LLM の使い分け。** Anthony 氏は、900 のエンティティの判断を LLM に任せるのは誤りで、decision model は strongly typed で桁違いに速い、と述べている。
- ゲームの中での「正しい判断」は主観的で決めにくい（次にどの乗り物に乗るかは多くの要素で決まる）、という難しさにも触れています。
- GPU Task Man は作者のマシン（Windows ARM・N1X）で動くもので、他の環境はコミュニティの contribution で広がっている。
- デモの最中に、モデルの読み込みに失敗し、やり直す場面があった。

## 8. 利用者にとっての利点

このセッションは特定の製品の導入効果を示すものではなく、お客様事例や数値による成果は語られていません。聴衆（開発者）にとっての利点として語られたのは次の点です。

- 学びたいことや身近な困りごとから出発すれば、GitHub Copilot が研究アシスタントとして機能する。Anthony 氏は、fine-tuning のハイパーパラメーターを学ぶ機会にし、Katie 氏は言語学の関心を再燃させたと話している。

- 作ったツールを公開すると、コミュニティが他の GPU やモデル向けに拡張してくれる（GPU Task Man の例）。

## 9. まとめ

- AI で何でも作れる時代でも、ワンショットで作ったものは平均的（mid）になる。自分の好みと専門性を加えて右（優れたほう）へ押すのは人間の仕事だ、というのが全体の主張です。
- 3 人の例は、OpenRCT2 に small language model と fine-tune した decision model を組み込む（Anthony 氏）、中国語の声調練習アプリ Tone Mirror（Katie 氏）、GPU を見える化する TUI の GPU Task Man（Scott 氏）で、どれも AI と対話しながら、自分で学んで作ったものです。
- 最後の tip は 2 つです。Scott 氏は、GitHub Copilot などの選択肢の質問で、内容が分からないまま推奨の選択肢を選ばず、「もっと簡単に説明して」と頼み、それでも分からなければさらに調べること。理由として、AI モデルは簡単なことでも凝った言い方で説明するため、普通の開発者が自分を愚かに感じやすいから、と話しています。Katie 氏は、恐れずに試すこと、「全部やって」と頼むのでなく、どう始めるか、誰が先にやっているか、何を学べばよいかを尋ねることです。
- 締めの言葉は、「you can just do stuff（ただやってみればいい）」でした。
