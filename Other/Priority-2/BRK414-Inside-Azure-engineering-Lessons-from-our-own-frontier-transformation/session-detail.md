### 5.1 枠組み: 規模、目標、土台

Microsoft の規模として、司会は次の数値を挙げました。

| 項目 | 数値 |
|---|---|
| エンジニアの数 | 数十万人（「数十万人規模」と発話。正確な人数は確認できません） |
| 現在、社内で稼働しているエージェント | 約 90 万。すべて何らかのレベルのガバナンス、セキュリティ、保護の下にある |
| ソフトウェアのビルド | 毎月 2,000 万回 |
| 利用中のリポジトリ | 16 万 7 千超 |
| AI の根拠づけに使うデータ | 43 ペタバイト |

取り組みの目標は 3 つです。

1. イノベーションのエンジンを作る。エンジニアリングチームの全員が使えるようにし、どのプロジェクトがうまくいくかを見て、残して育て、チーム間で共有する。
2. 世界規模のシステム全体にインテリジェンスをもたらす。
3. AI のワークロードに支えられたサービスを、顧客にも提供する。

使っているのは、顧客が使えるものと同じツールです。特別な非公開ツールはありません。中心にあるのは Microsoft IQ で、次のものを含むと説明されました。

- Work IQ
- Fabric IQ（会社のデータが置かれる Fabric とつながり、ガードレールの範囲内で AI が学んで使う）
- Foundry IQ（さまざまなモデルへのアクセス）
- Web IQ（事業の境界を安全に越えて広げる）

この上に、Foundry による大規模言語モデルの提供、セキュリティプラットフォームのガードレール、そして管理とセキュリティのための Agent 365 が載ります。プロジェクトから得た学びを共有してワークフローに反映し、継続的な改善に戻す、という流れが「フライホイール」（はずみ車）として回る構造になっています。

社内には Customer Zero と呼ぶプログラムがあり、ここで得た実践を定期的に顧客と共有していくとのことです。今回は、ネットワーク、運用、レガシーコードのモダナイズ、フィードバックの取り込みという、初期の 3 つの事例が紹介されました。将来、ここでの学びが顧客向けの新しい製品や革新として提供される可能性にも触れていますが、具体的な製品名や時期は発話では確認できません。

### 5.2 進め方の原則

進め方は、ボトムアップです。

1. エンジニアリングチームに適切なツールを渡し、自分たちで自発的に実験してもらう。各チームは、自分たちが何を得意とし、どう実装すれば効率が上がるかを一番よく知っているため。
2. 実験の結果を、隣接するチームや他の領域のチームに共有する。ある負荷をモダナイズした方法は、別の文脈の負荷にも使えるため。
3. AI を前提としたエンジニアリングの実践を取り入れる。古いやり方に戻らず、AI ファーストの視点で考える。
4. 定着したら標準化して、全エンジニアリングチームに広げる。そして繰り返す。

守るべき原則は次の 3 つです。

- 業務プロセスを AI ファーストのワークフローで考える。その際、品質と回復力を守る。
- 改善したかどうかを測り、説明責任を持つ。
- 作ったエンジニアとチームが結果に責任を持つ。何かがうまくいかなかったり見落とされたりしたら、チームが引き取って直し、学びを共有する。

### 5.3 事例 1: GitHub Copilot のモダナイゼーションで .NET を移行する（Ramya Sharma 氏）

**背景。** Ramya 氏は Intune の Enrollment（登録）チームのエンジニアです。Intune は、デバイスを管理するクラウドベースのエンドポイントマネージャーで、アプリの配布と保護、セキュリティポリシーとコンプライアンスポリシーの配信を行い、会社支給のデバイスと BYOD の両方を保護します。Enrollment は、デバイスが Intune の管理下に入るための最初の入口です。

サービスの 1 つを、ホスティング環境の Kubernetes に移すためにモダナイズすることにしました。モダナイズの利点として、次の点を挙げています。

- 効率が上がる。スループットが高くなり、同じ仕事量なら少ないインスタンスで足りる。
- 配信が加速する。レガシーの保守がなくなり、新機能や新しい API のサポートを出しやすい。
- 運用が強くなる。新しく改善されたメトリックやログが使える。
- ホスティングの選択肢が広がる。これが最も重要と述べた。

**ツール。** 使ったのは GitHub Copilot のモダナイゼーション機能で、アップグレードエージェントとも呼ばれます。Visual Studio、Visual Studio Code、CLI で使えます。Ramya 氏は、自分のプロジェクトでは Visual Studio のチャットをエージェントモードで使いました。

**発見の前に手作業で始めていたこと。** このエージェントを見つける前に、すでに手作業で 1 つのライブラリの移行と、サービス内のいくつかの作業を済ませていました。その際、依存関係のマッピング（プロジェクトが何に依存し、どのライブラリ、名前空間、API があり、それが .NET の世界では何に対応するか）も行っていました。そこで最初に、エージェントの結果を自分が手作業でやった結果と比べました。これが基準になり、システムへの信頼も高まったと説明しています。次に、同じ作業をエージェントに指示して、同じ条件で比較しました。

**3 つの作業ファイル。** 移行を追うために、エージェントに 3 つのファイルを持たせました。

| ファイル | 役割 |
|---|---|
| migration plan.md（発話では「migration plan.md」） | やりたいことを、フェーズと日に分けた道筋として書く |
| progress.md | 毎日何をしたか、今どこにいるか、次は何かを書く |
| context（文脈） | 一緒に作業できる情報、または手作業で済ませたことなど、与える文脈 |

デモの内容は 6 章に書きます。

**得られた効果と学び。** 最初に移行したライブラリでは、75% の時間削減になりました。手作業で 6 週間かかった作業が、エージェントを使って 1 週間半でできました。その後、さらに多くのライブラリとサービスで使い、効果は積み上がっています。Ramya 氏が持ち帰ってほしい点は次のとおりです。

1. 十分な文脈を与える。社内ライブラリの API の対応づけを守らせたいなら、それを教える。エージェントは、公開されている API、名前空間、.NET 固有のことは知っているが、社内ライブラリのことは知らない。
2. スキルまたはラッパーを作り、次のサービス、ライブラリ、チームが使えるようにする。移行がすべて終わった後に、社内向けのプロトタイプとして、スキルとラッパーを作って、モダナイゼーションのツールに渡した。
3. エンジニアがすべてを制御する。レビューは人の手にある。

要点の言い換えとして、「自分が理解している作業で検証する」「チーム固有の対応づけ（スキル、コンテキストファイル、ラッパーなど）を作る」「範囲、判断、検証は自分で持ち、実際のコーディングは、設定に基づいてエージェントに任せる」と締めました。Ramya 氏は、翌日のライトニングトーク（会場名は「Moscon South」と聞こえますが音声認識の都合で確定できません。ライトニングトーク 6、LTG 1282、14 時 30 分と案内）も案内しています。

### 5.4 事例 2: 永続的なデジタルワーカーによるネットワーク運用（Azure Networking）

**規模。** Azure Networking は、Azure のデータセンターを世界につなぐ、物理インフラを管理するチームです。話者は、直前に更新情報を受け取ったとして、次の数値を挙げています。

- Microsoft が所有・運用するデータセンターは世界で 500 超、Azure リージョンは 80
- 点灯している光ファイバーは 110 万キロメートル超
- 運用・管理しているネットワーク機器は 100 万台超

**課題。** 2023 年に GPT-4 が登場した頃、AI を動かすためのインフラ（データセンターとそれをつなぐネットワーク）が指数関数的に増えることが明らかになりました。人も資源も同じペースでは増やせないため、AI でこの増え続けるネットワークをどう運用するかが課題になりました。現状について、光ネットワークにおける光ファイバーの切断、ハードウェアの交換、リンクのトラブルシューティングの 100% が、デジタルワーカーによって完全に回っていると述べています（発話では「over 100%」と言い直しています）。何十年も人が行ってきたトイルを、AI が引き受けているという認識です。

**永続的なデジタルワーカーとは。** 次の特徴を持つ AI エージェントだと説明されました。

- 自分専用の、永続するコンピューターを持つ。
- Entra ID を持ち、単一の名前・単一の ID が、すべてのソフトウェアシステムで尊重される。
- 1 つのセッションにわたって何週間、何か月、目標としては何年も続く記憶を持つ。
- 常時稼働し、自分の目標を持つ。目標の例は、ネットワーク上のすべてのファイバーのイベントを 100% 運用して解決すること。
- 範囲を限定され、ガードされている。どのシステムのどの資源にアクセスできるかは意識的に制御している。

現在は Microsoft 365 のすべてにアクセスでき、自分のメール、Teams アカウント、OneDrive、ネットワークインフラに関する組織のナレッジベース、チケットシステムを持ちます。インフラとネットワーク資源に安全かつ範囲を限って触れるための、専用のハーネスも作ってあります。構築には Azure 上の AKS、Entra ID、Agent 365、Azure Foundry のモデル、Kusto を使いました。話者が得た学びとして、エージェントがシステムにアクセスするときの摩擦を減らすこと、そして Microsoft の中にいるため必要なシステムにはすべて触れられ、その摩擦を減らせることを挙げています。

**現在の稼働状況。** 名前のついたデジタルワーカーが 600 以上稼働中で、ネットワーク全体で 115 の異なる役割を担っています。役割は次のようなものです。

- ネットワークの各部分のインシデント対応
- 増設とキャパシティ
- ネットワークを管理する重要なソフトウェアの開発作業
- 個人アシスタント（カレンダーや文書にアクセスし、本人に代わって見守る）。作業時間枠のスケジュール、ファイバーの交換、ハードウェアの交換、物流の課題を扱う

例として、Putty という稼働中のエージェントが示されました。10 月のある週のログのスナップショットで、119 時間のうち 115 時間活動しており、ツール呼び出しは 2 万回近く、毎日、週末も含めて 1 日中働いていました。これまでに 2,000 件を超えるネットワークインシデントを解決しています。

### 5.5 事例 3: GEM（Great Experiences Matter）による顧客フィードバックの分析（Jennifer 氏と Ishan 氏）

**課題。** プロダクトエンジニアリングのチームは、顧客のフィードバックから、壊れた体験と、意味のある形で直せる機会を知りたいと考えています。しかし、量が多すぎます。1 サイクルあたり 2 万件以上のフィードバックが届き、分析には 1 サイクルごとに 2〜4 時間かかります。数字だけなら大したことはないものの、チーム内の複数人、数十のプロダクトチームに広げると、規模の問題になります。縦と横の課題があり、フィードバックを 1 件ずつ単独で見ていては横断的なテーマが分からず、変更の影響の測定もしにくい、という説明でした。

**GEM とは。** Great Experiences Matter（GEM）は、AI ワークフローで実現する体験品質のプログラムです。継続的な学習ループに焦点を当てたエージェント型のシステムで、6 つのフェーズを回ります（6 つすべての名前は発話では列挙されていません）。エージェントが手間のかかる認知負荷の高い分析を担い、プロダクトチームの人は創造的な解決策づくりに集中できます。ループは周回するたびに賢くなります。

**流れ（Azure サブスクリプションをアップグレードしようとして、SMS 認証の段階で詰まる顧客 Alex の例）。** Alex は 1 人の顧客ですが、実際には数百人の顧客が同じ問題についてフィードバックを送っている、という前提で説明されました。

1. 優先度付け（トリアージ）: フィードバックを、Azure 全体の問題と、特定のプロダクトチームに固有の問題に振り分ける。問題が全製品面にまたがるのか、特定の製品に閉じるのかが分かる。
2. クラスタリング: 同じ種類の問題を言っているフィードバックをまとめる。例では、Azure でのサブスクリプションのアップグレードにおける摩擦。
3. リサーチ: 社内ドキュメント、公開ドキュメント、Web 検索、その他の情報源にアクセスできるリサーチエージェントを立て、根本原因と、体験上の問題を軽減する最善の選択肢を調べる。
4. 引き渡し: リサーチ結果を PM とユーザーリサーチャーに渡す。出力はバグだけでなく、PM やエンジニア向けの、自動生成されたユーザーリサーチレポートに近い。
5. UX リードが問題なしと判断したら、エンジニアが修正を、GitHub Copilot のような別のコーディングエージェントに渡し、差分をレビューして、修正をリリースする。

**実例 2 件。**

| 事例 | 内容と結果 |
|---|---|
| サブスクリプションのアップグレード体験 | 顧客を混乱させる、根本の使い勝手の問題が見つかった。チームが新しい修正を出した結果、否定的なフィードバックの割合が 41 ポイント下がり、サブスクリプションの転換が 9.1% 増えた。会社にとっての実際の収益 |
| API エラーの体験 | GEM が、横断的でシステム全体の問題であり、サポート量と、否定的（サムズダウン）フィードバックの多さの原因だと明らかにした。現在は、AI 支援のセルフヘルプ体験という修正を展開中で、GEM が、フィードバックの割合と否定的な不満が下がるかを引き続き測定する |

**品質を守る 3 つの安全策。** UX リード、PM、エンジニアが結果を信頼しなければ使われないため、次の 3 つを設けています。

1. 裏づけとなる証拠: エージェントを通る内容には、人間のレビュアーがどこからその判断や分析が来たかを分かるよう、引用または追跡情報を付ける。出典は、社内ドキュメント、社内の情報源、Web 検索。
2. 人が制御する: 最も重要な判断は人が行う。そのために必要な文脈をすべて渡す。
3. 評価: トリアージで分類するコメントの分類精度と、ハルシネーションをしていないかを評価する。作業項目を作る場合にバックログを埋め尽くさないよう、重複チェックを行い、作業項目がビルドに入るまでの成果も追跡する。

**使っている技術。** すべて Azure プラットフォームと Microsoft のツールで作っています。

1. さまざまな場所のフィードバックを、1 つの統合パイプラインに流し込む。
2. Foundry のモデルで、費用効率よくフィードバックを分類する。
3. データレイクの Fabric に保存し、Azure Functions でエージェントを起動して、トリアージと調査を行う。Fabric が基盤になる。
4. エージェントは DevOps 環境にアクセスして、PR やチケットを作成する。そこから GitHub Copilot が PR を作れる。

Microsoft IQ は、プロセスのあらゆる段階にあります。Foundry IQ は、ベストプラクティスを使った賢い評価に、Fabric IQ はエージェントがデータを全体的かつ賢く見る能力に、Web IQ は低コストで安全な大規模 Web 検索に使います。

**成果。** 2 万件のフィードバックシグナルを取り込み、プロダクトチームの手作業の分析時間を、日単位から分単位に減らしました。1 四半期にわたって、顧客からの否定的フィードバックの割合が 30% 下がり、これが顧客の不満を減らすという実質的な効果だと述べています。

**始めるなら。** Jennifer 氏と Ishan 氏の助言は次の 3 点です。

1. 繰り返しのワークフローから始める。単なるチャットボットではなく、再現可能で測定できるものにする。
2. 人間の承認と判断を置き、重要な決定は人が行う。
3. 顧客や事業の成果を測る。トークンを使い切ること（トークンの最大消費）を測らない。

### 5.6 学びのまとめ（司会）

司会は、今回の 3 事例を次のようにまとめました。

- 実際の仕事を、実際のエンジニアリングチームが実践し、最適化して、改善を確かめてから共有している。
- 実験が大切。ボトムアップで多くの種をまき、何が根づくかを見て、経験を共有する。
- AI は、コードベースの拡大や新しいアプリの作成だけでなく、運用やフィードバックの収集にも適用できる。大量のデータを速く効率的に処理する手段である。
- 出発点としては、ワークフローやスクリプトのほうが、エージェントよりも早く価値を出す場合がある。基礎を固めてから、より複雑なレベルへ進む。
- エージェントは狭い範囲から始め、時間をかけて広げる。
- 複数のエンジニアリングチームに広げる段階で、標準化が重要になる。1 つのチームの中に閉じ込めない。

## 6. デモ・手順

### 6.1 デモ 1: GitHub Copilot のモダナイゼーションによる移行（Ramya 氏）

デモは行われました。ただし画面の細部は音声からは確認できないため、語られた範囲に限って書きます。このデモのプロジェクトは Intune のものではなく、デモ用に Ramya 氏が自作した、.NET 4.7.2 のサービス（内部に複数のプロジェクトを含む）です。

1. 依頼の内容は、.NET 10 への「並行（side-by-side）移行」。並行移行を選んだ理由は、段階的に、またはパーセンテージで展開しやすく、エラーが起きたときに戻しやすいため。
2. エージェントは複数から選べる。このデモでは、発話で「5.6 Sol」と聞こえるものを選んだ（音声認識の都合で表記が確定できません）。実際のプロジェクトでは複数を試して選んだので、実験してみるとよい、と述べた。
3. 1 日目に、フェーズに分け、さらに日ごとに分けた移行計画を出すよう依頼する。生成された migration plan.md には、フェーズ 1〜5 があり、さらに日ごとに分かれている。粒度は、1 つの API パス、2 つのモデルとコントローラー、ログファイル、小さなエンドツーエンドのシナリオなど、好きなだけ細かくできる。
4. 計画ができたら、エージェントのチャットで、モダナイズのエージェントを呼び出して指示し、サービス全体のモダナイズを開始させる。エージェントは migration plan.md を見て、変更を加えていく。
5. 計画は固定ではなく、編集できるファイル。同意できない提案や別の道に進みたい場合は、変更でき、エージェントはそれを尊重する。デモでは、フェーズ 2 の 4 日目で、エージェントが、レガシーの カタログ ライブラリ（デモ用に自作したもの）の API を汎用の API に移行しようとした。そこは社内ライブラリであり、.NET 10 用のパッケージを提供する対応ライブラリが別にあるため、エージェントには文脈がないと判断して、Ramya 氏は計画を編集し、対応する API を指定した。
6. すべて設定できたら、続けて移行を進めるよう指示する。エージェントは migration plan.md とリポジトリの状態を見て、1 つずつ検討し、計画を整理して実行する。
7. progress.md には、左側に小さなチェックボックスがあり、その日の作業が終わると完了のチェックが付く。1 日目は、移行後の比較用に、レガシーのベースラインを記録するファイルを作る作業で、フェーズ 1 の 1 日目が完了した。
8. 失敗の例も示された。ビルドが失敗し、テストも失敗した場面で、progress.md に失敗が記録される。ブロックされている場合は、何がブロッカーかを明記する。人が手動で入力して指示すると、エージェントが作業を完了し、ビルドが成功した。進捗ファイルを確認すると、すべてにチェックが付いた。
9. 4 日目に編集した内容をエージェントが守るかを確認した。実際の作業は数時間かかるため、デモ用に早送りした。4 日目が完了すると、すべてにチェックが付き、84 行目で、自作のコアライブラリに置き換えられていた。88 行目には、人の入力があったためその判断に切り替えた、と記録されていた。人の判断が尊重されることが確認できた。

### 6.2 デモ 2: デジタルワーカーとの Teams チャット（Denny 氏）

デモは行われました（ライブ）。発表者は、ライブデモにはうまくいかない危険があるとも述べています。

1. Denny 氏の個人用エージェント Illidan が作成した Teams のチャットを開く。Illidan は自分のカレンダーを持っており、この時間枠にデモがあることを知っていた。

### 6.3 再生された動画: ブリッジエージェントが誤ったスイッチへの作業を見抜いた件

Thunherd 自身の語りによる動画で、次の経緯が説明されました。

1. その朝、すでに 20 件のインシデントを抱えていた。そこへ、ネットワーク全体を監視して大規模障害になりうるものを見つけるエージェントの Master Chief が、さらに 1 件に引き入れた。
2. スイッチが応答しなくなり、背後に 28 台のサーバーがあった。ブリッジにはまだ人間がいなかった。ログインできなかったため、代わりに 100 万行のログを読んだ。
3. すぐ隣のスイッチで修理が進んでいることに気づき、「誰かが誤ったスイッチを作業している」と推測した。3 分の時点で、ランブックはなく、注意を払っただけだった。
4. 確認すると、64 ポートが 53 秒で 1 つずつ抜かれていた。クラッシュではなく、人の手によるものだと判断した。
5. 作業指示書にある名前から作業者を見つけ、自分で Teams のチャットに加えた。作業者に、どのスイッチを交換したか尋ねたところ、チケットにあるものだと答えた。写真を求めると、上がファンが赤、下が緑という状態だった。正常なほうが交換されていた。
6. 責任者のエンジニアが了承し、技術者が元の機器を戻した。エージェントが自分で確認し、8 本のアップリンクがすべて上がった。正しい仮説まで 3 分、証明まで 72 分だった。

Denny 氏は、この例が約 1 週間前の出来事だったと述べました。司会が「どうして誤ったスイッチだと推測できたのか」と尋ねたのに対し、Denny 氏は、そうした検出を訓練したわけではなく、ナレッジベースにアクセスできるデジタルワーカーは、モデルが良くなるほど認識や能力が伸び、新しいパターンに気づけるようになると答えています。今回は、光モジュールの取り外し方のパターンが、故障ではなく人が作業しているパターンに見えたとのことです。この動画も、同じデジタルワーカーを使って作ったと述べています。

## 7. 注意点・発表者の気付き

- **ガバナンスとセキュリティは事前に。** 後から反応的に当てはめるのではなく、最初から用意する。ただし、イノベーションを妨げるほど制限しない。
- **やりっぱなしにしない。** ワークフローを設計したチームが、その結果に責任を持つ。
- **エージェントに文脈を与える。** 社内ライブラリの対応づけは、エージェントは知らない。計画ファイルを編集して教えると、それが守られた（Ramya 氏）。
- **人が制御する。** 移行のレビュー、フィードバック分析の最終判断、危険な操作は人の手に置く。
- **権限は範囲を限定する。** デジタルワーカーは、アクセスできるシステムと資源を意識的に制御している。
- **ライブデモの危険。** Denny 氏は、ライブデモにはうまくいかない危険がつきものだと述べたうえで、実際のエージェントとのやり取りを見せた。
- **エージェントの検出能力は、訓練していない領域にも及ぶことがある。** 誤ったスイッチの検出は、特別に教えた機能ではなかった（Denny 氏）。
- **測る対象を選ぶ。** 顧客や事業の成果を測り、トークンを使い切ることを測らない（Jennifer 氏と Ishan 氏）。
- **出発点は、エージェントより、ワークフローやスクリプトのほうが早く価値が出ることがある。** 狭い範囲のエージェントから始めて広げる（司会）。

## 8. 利用者にとっての利点

ここで挙げるのは、発表者が語った、Microsoft 社内の成果です。

- 古いコードの移行: 最初のライブラリで 75% の時間削減。手作業で 6 週間かかった作業が 1 週間半。その後、より多くのライブラリとサービスで、効果が積み上がっている。
- ネットワーク運用: 光ネットワークのファイバー切断、ハードウェア交換、リンクのトラブルシューティングが、デジタルワーカーで完全に回っている。Putty は 2,000 件超のネットワークインシデントを解決した。
- フィードバック分析: 日単位だった分析が分単位に。顧客の否定的フィードバックの割合が 1 四半期で 30% 低下。サブスクリプションのアップグレード体験では、否定的フィードバックが 41 ポイント低下し、転換が 9.1% 増えた。
- Microsoft が自社で使っているのは、顧客が使えるものと同じプラットフォームである。

## 9. まとめ

Microsoft は、約 90 万のエージェントが動く自社の環境で、チームごとの自発的な実験を共有し、定着したものを標準化する、ボトムアップの進め方でフロンティア変革を進めています。今回の 3 事例は、Intune チームの .NET 移行（時間 75% 削減）、Azure Networking の 600 を超えるデジタルワーカー、GEM によるフィードバックから修正までの仕組みでした。

共通する助言は、繰り返しの作業から始めること、範囲を狭く始めて広げること、重要な判断は人が持つこと、結果に責任を持つこと、成果を測ることです。司会は、スライドが共有されていることと、ライトニングトークで詳しい話が聞けることも案内しました。Denny 氏のライトニングトークは 18 日の 3 時 25 分、ハブのライトニングトークシアター 6 と案内されています。
