## 1. はじめに

### 5.2 富士通と FDE の定義

富士通は、市場シェアで見て日本をリードするデジタルサービス企業だと紹介されました。年間売上は約 230 億ドル、50 を超える国と地域に顧客がいます。FDE は 100 人を超えるチームに成長しており、Microsoft とは深いパートナーシップがあるとも述べています。

発表者による FDE の定義は、「価値を生み出すフルスタックエンジニア」です。特徴は 3 つあります。

| 特徴 | 内容 |
| --- | --- |
| 現場に入り込む | 顧客の事業チームと並んで、顧客のデータの中で働く |
| 一部ではなく全体を作る | 一部分ではなく、企業向けの水準のソフトウェアやシステムを作る |
| 成果に責任を持つ | 測定可能な事業 KPI を自分たちで定め、作ったシステムを通じて結果にコミットする |

FDE は、費やした時間ではなく、生み出した価値で評価されます。富士通は、この言葉が流行する前から 6 年以上にわたり、デプロイメントストラテジスト（FDE の相手役として事業戦略を担う人）と FDE のチームを作ってきたとのことです。製造、製薬、金融サービス、小売、エネルギーの各業界で、データと AI の専門家が顧客と 1 つのチームとして価値を作ってきたと説明されています。

発表者は、品質、セキュリティ、信頼性への要求が妥協なく高い日本企業という環境で実績を積んできたことも強調しました。そのため日本では AI の導入が慎重に進みやすい一方、多くの顧客が富士通にシステム構築を任せている、という説明です。AI 時代に、富士通自身が従来の「ベース」型の提供（音声認識の表記で、正確な語は確認できません）から、価値ベースの提供へとビジネスモデルを変えようとしており、その中心に FDE が置かれています。

### 5.3 注力領域と 4 つの S

FDE 事業の注力先は System of Engagement（SOE、顧客との関わり、意思決定、成長といった、企業が競い合う領域）です。人間だけでは届かない領域に踏み込むほど AI の投資対効果が高い、というのが理由です。ただし先に 2 つの前提が必要だとしています。

- モダナイゼーション：レガシーシステムからデータが解放されていなければ、AI は機能しない
- サイバーセキュリティ：セキュリティがなければ何も本番に入らない

この 2 つは、副次的なプロジェクトではなく、FDE 事業が立つ土台として扱われています。

FDE チームが生み出す価値は、3 つの S にまとめられました。

1. Speed（速さ）：顧客と 1 つのチームになり、アイデアから動くプロトタイプまで 10 日、本番まで 2〜3 か月
2. Scale（拡張性）：契約ごとに単発のソフトウェアを作る事業ではなく、再利用できるセマンティクス（意味の定義）とエージェントを土台に、各事業の深さと全社への広がりの両方に展開する
3. Strength（強み）：発表者が「サービス・アズ・ソフトウェア」と呼ぶもの。顧客固有のノウハウを、エージェントで動くソフトウェアにして、顧客の競争力にする

富士通が従来の提供形態から価値ベースに移るのと同じように、顧客も自分たちが得意なことをソフトウェアに変えられる、という説明です。これらの 3 つの S を使い、さまざまな業界で SOE のシステム（AI エージェントを含む）を作ってきており、本番稼働中か、稼働を始めつつあるとのことです。個別の顧客名は語られていません。発表では、設計から本番までやり切る形を「エンタープライズ FDE」と呼んでいます。

### 5.4 バイブコーディングとの違い

「AI がコードを書けるなら、FDE チームやプラットフォームは要らないのでは。バイブコーディング（AI に任せて勢いで作る開発）でよいのでは」という質問がよくある、と発表者は述べています。本人もバイブコーディングは好きで、速く、アイデアの検討には良い方法だと認めています。そのうえで、速さだけでは本番に届かないと説明しました。

- 速さがやがて落ちる
- ガバナンスがその場しのぎになる
- 誰が何をしたか追跡しにくい
- 最後に、誰も保守したがらない使い捨てのコードが残る
- 結果として、すばらしいデモはできても、本番システムはそれでは動かない

本番では、セキュリティを初日から組み込み、ガバナンスを既定でポリシー駆動にし、すべての操作を記録し、共有プラットフォームと共有の標準の上に載せる必要があります。エンタープライズ FDE はこれらを、バイブコーディングの速さで届けるという位置づけです。4 つ目の S として Security（セキュリティ）も加えられました。

### 5.5 FDE 事業の構造とプラットフォームの位置づけ

発表者は、FDE 事業をビルのたとえで説明しています。細部は異なっても、IT に携わる人なら見覚えのある図だという前置きがありました。

| 階 | 内容 |
| --- | --- |
| 土台 | 認証、認可、セキュリティ、監査。建物全体を支える、あらゆるシステムの共通部分 |
| 1 階 | データ。データレイクに加え、データパイプライン、リネージュ（データの系譜）、セマンティック、オントロジー |
| 2 階 | AI 基盤。モデル、バックエンドのエージェント、そのオーケストレーション |
| 中 2 階 | インタラクション（対話）のインターフェース層。2 階と 3 階を安全につなぎ、アプリケーションとフロントエンドがある |
| 3 階 | プロフェッショナルサービスを提供する人、つまり FDE チーム |

すべての階は顧客の成果という 1 つの目的のために存在します。3 階より下のデジタルの部分が「FDE プラットフォーム」です。そのコンセプトは、AI エージェントを動かす富士通独自のノウハウに基づく、AI 駆動開発のための一体型の環境で、データと AI を活用するライフサイクル全体をカバーします。特徴は次の 2 点です。

- AI 駆動の開発であること
- エンタープライズ水準のセキュリティとガバナンスの上に載っており、最初から全工程に組み込まれていること

プラットフォームが変えることは 3 つあります。

1. プロトタイプまでの時間：実データを使うアプリケーションと AI エージェントが、1 か月ではなく 10 日で用意できる
2. 既定で安全かつ統制されていること：エージェントが構築を担当し、セキュリティとガバナンスはプラットフォームがすぐに使える形で担当する
3. 誰でも作れること：フロントエンド、セキュリティ、ガバナンスの深い専門知識がないチームでも、エンタープライズ水準のアプリケーションを本番に出せる。エンジニアリングの専門性がプラットフォームに組み込まれ、アーキテクチャによって強制されているため

### 5.6 2 つの提供形態

この考え方は 2 つの形で提供されます。どちらか一方でも、両方の組み合わせでも使え、互いに補い合う関係だと説明されています。

| 形態 | 名称 | 構成 | 向いている場面 |
| --- | --- | --- | --- |
| 管理型（Managed） | FDE Dev Studio（FDevs） | Microsoft 上のマネージドサービスの組み合わせ。Fabric、Foundry、Frontier、M365 の上に構築 | 速さが必要なとき、M365 との深い統合や Microsoft の最新の技術革新が必要なとき |
| 組み立て型（Composable） | Data and AI utilization platform（DOP） | Kubernetes 上のオープンソースパッケージ、その上の独自のオントロジーとエージェントハーネス、AI エンジンやフレームワークなどの独自 IP | 個別仕様のバックエンド、デプロイ先の提供環境、深いカスタマイズが必要なとき |

> 補足：FDE Dev Studio の構成要素として、音声認識では「Frontier、like Cloud or GPTs」のように書き起こされており、Frontier に続く部分の正確な内容は確認できません。

### 5.7 FDE Dev Studio（管理型）の構成

FDE Dev Studio は、SOE で AI エージェントのオーケストレーションを伴うワークフローを作るために必要だと考える機能に沿って設計されています。主な構成要素は 3 つです。

- 統合されたデータ：Fabric が提供
- モデルとエージェントの基盤：Microsoft Foundry
- 体験の提供：その上の React ベースのアプリ

これらは Entra、Defender、Power View（音声認識の表記で、確定できません）によって保護・統制されます。

発表者が強調したのは、作るものがダッシュボードではない点です。SOE では、データを見て集計するだけでは足りず、判断し、行動する必要があります。行動はすべてデータとして記録し、次の判断の材料にします。そのため 3 つの構成要素は、単にマネージドサービスをつないだものではなく、データを読み書きし、エージェントに提供し、人と対話する 1 つのシステムとして作られています。

AI 駆動の開発を可能にするのがエージェントハーネスです。コーディングエージェントが開発を最初から最後まで進められるように、スキルとフックを提供します。コーディングエージェントとして発表では 2 つの名前が挙がりましたが、音声認識では「code code」「codecs」と書き起こされており、正確な製品名は確認できません。エージェントは次の作業を担当します。

- ユースケースの設計
- セマンティック層のモデリング
- パイプラインの作成とテスト
- React ベースのアプリの構築
- Foundry でのエージェントのデプロイとオーケストレーション

バイブコーディングとの大きな違いは、これらのすべての手順が、企業向けのガードレールの内側で動く点です。

簡略化したアーキテクチャは次のように説明されました。

1. ERP や CRM などのデータが、Fabric と OneLake に入る
2. セマンティック層が、データに業務上の意味を与える
3. Foundry のエージェントが、その上で推論する
4. React ベースのアプリが、Web、Teams、Copilot でユーザーに届ける
5. 図の左側では、エージェントハーネスが全層を構築・進化させる
6. 図の右側では、Entra、Power View、Defender が全層を保護する

## 6. デモ・手順

デモは 2 つ行われました。画面の細部は音声からは確認できず、以下は発話で語られた範囲です。

### 6.1 ガスタービン製造のアプリとデータパイプライン

FDevs で作ったアプリケーションと、その背後のデータパイプラインを見せるデモです。題材はガスタービン製造です。製造仕様に設計変更が入ると、作業をタスクに分解して割り当て、作業量の増加や偏りを解消する必要があります。データがつながっておらず AI もない場合は、下から積み上げて分析し、問題が表面化する前に探し回ることになります。このプラットフォームではデータ、ロジック、AI がつながっているため、必要な意思決定から逆算して始められる、と説明されています。この例の意思決定は、作業量の削減です。

1. 最初の画面に、作業量が急増するリスクのある拠点の地図が表示される。トリガーは、仕様の現行バージョン 1 から、バージョン 2 への変更
2. 詳細を見るため、地図上の拠点（音声認識では「Wrinkle Works」と書き起こされ、確定できません）をクリックする
3. 右側に、作業量が多い順に部門や課が一覧表示される。下側には、最も負荷の高い設備が表示される
4. この裏側では、Fabric が時系列の作業量データを、組織、拠点、設備に分けて保持している。セマンティック層の計算ロジックがそれを集計するため、どの粒度でも負荷を表示できる。利用者は Fabric のデータをドリルダウン、ドリルアップして自分で分析し、各アラートへの対応を決められる
5. さらに掘り下げるため、精密鋳造の課を選ぶと、その課の作業量がタスク単位で表示される
6. 設計書類は通常、非構造化データである。このプラットフォームは構造化データと非構造化データをひも付けるため、各タスクが設計書のどこに現れるかを画面上で視覚的に示せる
7. 目標は作業量の削減なので、このタスクの再割り当てなど、その場で対応できる。さらに高度な選択肢として、拠点間の移管シミュレーションの実行や、AI エージェントによる対応案の提案もできる
8. このアプリのデータは、ERP、メッシュ（音声認識の表記で、確定できません）、ファイルシステムなどから来る。データパイプラインで Fabric に統合され、唯一の信頼できる情報源としてセマンティック層から提供される
9. データパイプラインとデータリネージュの画面も示された。ソースからセマンティックモデルまで、パイプラインをたどり、各段階でデータをプレビューできる。人と AI が使うデータの出どころと、それを導くロジックが分かることが、本当のガバナンスを可能にする、と説明されている

### 6.2 AI 駆動の開発の録画

次に、いま見たデータパイプラインとアプリケーションが、FDevs でどう作られたかを録画した動画で見せました。

1. VS Code 内のターミナルでコーディングエージェントが動いている（製品名は 5.7 の注記のとおり確認できません）。裏ではスキル、エージェント、MCP サーバーがタスクごとに登録されており、適切なタイミングで呼び出される
2. AI が、大まかな要件を具体的な仕様に落とし、システム設計に変換する
3. そのうえで、データパイプラインとアプリケーションを設計し、実装に進む
4. Fabric 上のデータパイプラインを PySpark で実装する。AI はメダリオンアーキテクチャの原則に従ってコードを書き、最後にデータリネージュも作る
5. 続いて、セマンティックモデルを作る
6. UI の段階では、最初から React のコードを書くのではなく、まずサンプルコンポーネントを配置し、UX の観点で動作を確認する
7. セマンティックモデルと、アクション実行のための API を定義する
8. 最後に、フロントエンドとバックエンドを接続してデプロイする

結果は、FDevs のアーキテクチャに沿ったシステムになる、と説明されました。
