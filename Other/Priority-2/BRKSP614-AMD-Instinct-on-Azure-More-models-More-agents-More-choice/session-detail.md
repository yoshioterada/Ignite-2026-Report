## 5. 発表内容の詳細

### 5.1 AI 需要の動向

冒頭で Ryan 氏が挙げた数字は次のとおりです。

- トークン量は 1 か月あたり約 **95 倍**に増加し、**月間 40 クアドリリオン（4 京）**の推論トークンに達している。AI が役に立つほど使われ、使われるほど計算資源が必要になる、という自己強化のループだと説明しています。
- トレーニングは年に約 5 倍の割合で拡大しており、当面続くとの見方です。
- 推論は現在の AI 計算全体の**約 60%** を占める。
- **2 月ごろ、エージェントによる要求が初めて人間のトラフィックを上回り**、年初来で約 14 倍の勢いで伸びている。人間は 1〜2 回要求するだけだが、エージェントは答えが得られるまで 8 回、12 回と繰り返す、という違いが説明されました。

### 5.2 Foundry の利用状況とインフラの拡張

Sai 氏が挙げた数字は次のとおりです。

- Foundry でエージェント型アプリを作っているお客様は約 **12 万社**。
- そのうち **300 社**が、2026 年に **1 兆トークン**を消費している（1 社で 1 年に 1 兆トークン）。
- Foundry に登録されているエージェントは **5,000 万**。
- Azure は今年、**88 か所の新しいデータセンター**を構築し、ペースはさらに上がる。

ここから Sai 氏は 2 つの要点を述べています。1 つは、**企業の AI がパイロットから本番へ移っている**こと。もう 1 つは、アプリケーションがチャットボットからエージェント型 AI へ移ったことです。エージェント型 AI は多くの場合、常時動き続け、新しい情報を探し、深く推論し、許可を求めるか、権限が委任されていれば自ら行動する、という性質があり、チャットボットとは負荷のかかり方がまったく違うと説明しています。

### 5.3 AI ワークロードの種類

| ワークロード | 説明 |
| --- | --- |
| トレーニング | 先端の AI ラボが主に行う。数千から数十万の GPU を同じ場所に、またはごく近接して高帯域の広域ネットワークで結んで使う |
| ファインチューニング、強化学習など | 企業が、基盤モデルを自社のシナリオとデータに合わせて調整する。要求の性質がそれぞれ異なる |
| 推論 | チャットボットから、重い推論やエージェントへ。多くのお客様は Copilot などの SaaS として使うが、Foundry でエージェントを作る企業も多い。企業アプリがモデルのエンドポイントを呼ぶ形が一般的 |
| データの前処理 | ファインチューニングのために必要。CPU を多く使う |

この 4 種類は必要とするものが違い、1 種類のシリコンですべては満たせないため、Azure は自社設計のシリコンと AMD の製品を、Azure のスタックに統合して提供している、という説明です。

### 5.4 Azure のスタック

Azure は、データセンターから、SaaS（Copilot）、プラットフォーム、モデルサービスまで、すべての層で革新を進めていると述べています。

- **データセンター層**：できるだけ速く、エネルギー効率よく、環境に配慮して容量を作る。もともと 1 社（OpenAI）のために始めた **Fairwater** データセンターに、冷却技術や、データセンター間を通信事業者並みの速度でつなぐ広域ネットワークなどの革新が集まっている。
- **ハードウェア層**：コンピュート、ストレージ、ネットワーク、AI 計算。自社設計のシリコン、AMD、その他のパートナーの製品がある。AMD は MI200X に始まり、MI300、そして現在 455 に取り組んでいる。
- **インスタンス層**：お客様に見えるのはコンピュートインスタンス。長く仮想マシン（VM）だったが、ベアメタルインスタンスへ移りつつあり、先端ラボの入口になっている。
- **クラスター管理**：数千から数十万規模になると、より高い抽象化が必要になる。社内には独自のクラスター管理がある。社外のお客様は Azure Kubernetes Service を使う。
- **モデルサービス（プラットフォーム）層**：ここが Foundry。企業のお客様の主な利用方法になりつつある。クォータがあれば、**30 分以内にモデルをデプロイ**できる。

Sai 氏によれば、MI300X 上でフルのアプリケーションやモデルを、Foundry で 30 分以内にデプロイできることを、調査で確認したとのことです。Foundry の利用モデルには、専用のコンピュートをインスタンスで予約する方法、従量課金、プロビジョニングスループット（確保した処理能力への課金）があります。

#### VM、ベアメタル、モデルサービスの違い

| 利用形態 | 説明 |
| --- | --- |
| VM | 過去 10 年のモデル。ハイパーバイザー以下は Azure が管理し、お客様はゲスト OS、ドライバー、ROCm のバージョン、モデルやフレームワークの設定を管理する。AI の世界では新しい専門知識が必要で、モデルの変化も速く、事業の中核にはなりにくい |
| ベアメタルインスタンス | 基盤計算をより細かく制御したい場合。リアルタイムのテレメトリ、ハードウェア障害の把握、場合によってはファームウェアのバージョン制御を求める |
| モデルサービス | 企業のお客様が向かうと Sai 氏が考える利用形態 |

IaaS（VM・ベアメタル）の利用は、現在も将来も主に先端の AI ラボが対象になる、というのが Sai 氏の見立てです。

### 5.5 AI スーパーコンピューティングクラスター

お客様にはコンピュートインスタンスが見えますが、その裏にあるのが AI スーパーコンピューティングクラスターで、データセンター層、ハードウェア層、IaaS ソフトウェア層の革新を組み合わせたものです。構成要素は次の 3 つです。

- **コンピュートラック（GPU ラック）**：中核。GPU を動かし続けるための CPU も含む。発表では 455 と Helios を例に説明された。
- **ネットワークラック**
- **冷却**：施設全体で冷やすデータセンターか、高密度の GPU ラックを冷却ラックで支える構成。

GPU ラックは計算とメモリが高密度で高価なため、GPU を常に稼働させて総インフラコストを下げるには、GPU 同士の通信でネットワークがボトルネックにならないようにする必要があります。小規模なら簡単ですが、数千から数万の GPU を 1 クラスターで動かすには、ネットワークの革新が必要だと述べています。ネットワークはバックエンドの 階層 0 と階層 1 の 2 層で、役割が異なります。これまでは InfiniBand 上に作ってきたが、よりオープンな Ethernet 技術へ移行しようとしている、という説明です。

### 5.6 AMD と Azure の取り組みの経緯

AMD と Microsoft は、Azure でスーパーコンピューティングクラスターを構築する取り組みを **3 年以上**続けています。

1. **MI250X（2022 年）**：主に Microsoft 社内向けに、いくつかのクラスターを構築。AMD のスタックで Azure 内にスーパーコンピューティングクラスターを作れるかを確かめる目的。
2. **MI300X**：Azure は MI300X を最初にデプロイしたクラウドで、**大規模にデプロイした最初のクラウド**でもある。当時の先端アプリケーションを動かし、Sai 氏は、**先端アプリケーションを NVIDIA 以外のハードウェアで動かしたのは業界で初めて**だと述べている。強みは高いメモリ（当時の HBM3 で約 30% 多い）で、当時のモデルで最高水準の性能を出せた。VM 上で GPT 3.5 などのオープンソースモデルを動かした後、MI300X を Foundry に統合し、AMD の協力でオープンソースの主要モデルを Foundry の MI300X に導入した。
3. **MI455X**：現在 AMD チームと密接に共同設計を進めている。Azure のデータセンターとインフラに合わせた、その世代で主導的なプラットフォームを目指しており、先端モデルの推論に最適化している。

要点として、AMD の取り組みは Azure で 3 世代・4 年にわたり、後付けのインフラではなく Azure のスタックに完全に統合されていること、お客様がインスタンスをデプロイする体験や機能は、他の Azure のコンピュート製品と同じだと説明されました。

### 5.7 Foundry と MI300X

Sai 氏は、企業が気にするのはマシンやフレームワークやモデルではなく、**最良の経済性でエージェント型・AI アプリを素早く作ること**だと述べています。

- ある外部機関の調査で、主要なモデルのいくつかを Foundry の MI300X に 30 分以内にデプロイできた。
- GPT-OSS や Gemma などの主要モデルは、AMD と Microsoft が共同で最適化済み。
- MI300X が持つ HBM の優位性により、大きなモデルを小さな構成（少ない GPU、少ない VM）に載せられ、アプリケーションの **TCO（総所有コスト）**が下がる。
- 体験はシンプルで、クォータを取得し、モデルを選び、テンプレートをデプロイするだけ。

#### AT&T の事例

AT&T のチームは、モデルの構築と提供の経験を持っています（発表では、同チームの以前のモデルが数百万回ダウンロードされたと述べられていますが、モデル名は音声認識の都合で確定できません）。Foundry と MI300X を使い、少ない GPU で数日のうちにモデルをファインチューニングし、そのまま提供まで進めました（ファインチューニングしたモデル名は聞き取りが不明瞭です）。用途ごとにモデルを使い分けていて、コーディングには Gemma、推論には OSS を使いました。「適切なモデルを適切なシナリオに」「オープンソースのモデルを、最良のインフラで、最短の時間で」という流れで、企業のチームに共通して使えるパターンだと説明されています。

### 5.8 AMD の選択肢と MI300X の仕様

Ryan 氏は、顧客に選択肢を持ってもらうことが AMD の企業理念だと述べました。画面には次の選択肢が示されています。

- Foundry 上の AMD Instinct MI300X
- その VM 版（V5 と聞こえます）
- 近日登場する ND MI455X V7（AMD Helios アーキテクチャ。聞き取りの都合で名称は確定できません）

MI300X の仕様として挙げられた数値は次のとおりです（比較は代替の参照ソリューションに対するもので、製品名は発話では確認できません）。

| 項目 | 値 |
| --- | --- |
| 演算性能（FP16 / FP8） | 約 1.3 / 2.6 ペタフロップス。最大で参照ソリューションの 1.32 倍 |
| メモリ容量 | 192 ギガバイト。最大で代替の約 2.4 倍 |
| メモリ帯域 | 約 5.3 テラバイト/秒。最大で競合の 1.6 倍 |

メモリが大きいと大きなモデルや長いコンテキストを扱え、帯域が広いとモデルデータへのアクセスが速くなり、答えが早く返ります。GPU の数が少なくて済むことは、コスト、台数、複雑さ、実行中の失敗の可能性を抑えることにつながる、という説明です。

#### DeepSeek R1 の例

6,710 億パラメーターの DeepSeek R1 は、MI300X では **8 GPU の単一インスタンス**で動かせます。競合ソリューションでは**最大 19 GPU** が必要になる、と述べています。

### 5.10 MI455X と ROCm

Ryan 氏が示した MI455X の仕様と、Sai 氏の補足は次のとおりです（将来の製品の数値です）。

| 項目 | 値 |
| --- | --- |
| メモリ | 432 ギガバイトの HBM4。業界最大の容量。競合の約 1.5 倍 |
| 演算性能 | FP4 の AI 計算で約 40 ペタフロップス。競合の約 1.15 倍（競合は 35 ペタフロップスと聞こえます） |
| ネットワーク | スケールアップ帯域が 1.2 倍、スケールアウト帯域が 1.5 倍。計算・メモリ・ネットワークで「3 つとも 1 位」 |
| 性能 | GPU あたり約 **毎秒 2 万 4,000 トークン**。ここ 48 時間ほどの新しいデータで、参照ソリューションに対し業界でリーダーの性能 |
| 経済性 | ドルあたりのトークン数が最大 30% 多い |

この製品は「まもなく Azure の V7 インスタンスとして提供される」と Ryan 氏は述べました。Sai 氏は、455 の Helios ラックがすでに Microsoft のラボで稼働していると話し、示された性能値を再現するチームが動いている最中だと述べています。

**ROCm** は AMD のオープンソース GPU ソフトウェアプラットフォームです。Hugging Face の **300 万以上のモデル**が AMD でそのまま動き、上位 10 のオープンソースプロジェクトがネイティブにサポートされている、と説明されました。設定するスタックはなく、ロックインもなく、投資は ROCm という 1 か所に集約するという説明です。

Sai 氏は、455 のポイントを 3 つ挙げています。

1. ラック内のメモリとスケールアップ帯域の優位性。HBM と、スケールアップ帯域の 20% の優位性が、GPT-6 以降のような先端モデルに最も重要。より少ない GPU でより大きなモデルを動かせる。
2. **オープン標準のスタック**。ラック、スケールアップとスケールアウトのスイッチ（Ethernet ベース）、ROCm によるプログラミングと管理のすべてが、オープン標準で構築されている。
3. Helios はすでに Microsoft のラボで稼働していて、Microsoft 以外にも提供する設計だが、Microsoft 固有のニーズに合わせた共同設計も進めている。

また、455 は先端モデルの推論を主な対象としており、今後数年で推論とエージェント型 AI の複雑さと規模が増すにつれて、このプラットフォームがそれらを先導すると見込んでいる、と述べています。

## 7. 注意点・発表者の気付き

- **エージェント型 AI は負荷の形が異なる。** 常時動き、推論を重ねるため、チャットボットとは違った負荷がインフラにかかる。
- **利用形態を選ぶ指針。** VM は管理範囲が広く、ゲスト OS、ドライバー、ROCm のバージョンなど新たな専門知識が要る。ベアメタルは、テレメトリや障害把握、ファームウェアのバージョン制御まで細かく制御したい場合向け。IaaS は主に先端 AI ラボ向けで、企業にはモデルサービスが向くと Sai 氏は述べている。
- **提供済みか将来かの区別。** MI300X（Foundry で利用可）と、MI455X（まもなく登場する V7 インスタンス）は別物。MI455X の数値は将来の製品に関するもので、Helios はまだ社内ラボの段階。
- **性能・コスト数値の読み方。** 比較対象は匿名の代替ソリューション。Signal65 の数値は、代理モデルを使った測定。MI455X の性能値は、Microsoft 側のチームが再現を試みている最中と述べられた。
- **将来のネットワークの方向。** これまでは InfiniBand 上に構築してきたが、よりオープンな Ethernet へ移行しようとしている。

## 8. 利用者にとっての利点

- **導入が速い。** Foundry でクォータがあれば、30 分以内にモデルをデプロイできる。Signal65 の測定ではライブエンドポイントまで 14〜24 分（複雑なモデルは 46〜59 分）で、サービス用スタックのチューニングも不要だった。
- **少ない GPU で大きなモデルを動かせる（TCO の低減）。** MI300X は 192 GB のメモリを持ち、DeepSeek R1 を 8 GPU で動かせる（競合は最大 19 GPU）。
- **モデルの選択肢。** GPT-OSS や Gemma などの主要モデルが、AMD と Microsoft によって最適化済み。
- **管理の負担を抑える。** モデルサービスの形なら、ドライバーや ROCm のバージョン管理を自分でしなくてよい。
- **オープンなソフトウェア。** ROCm は Hugging Face の 300 万以上のモデルに対応し、ロックインがない。
- **事例：AT&T。** 少ない GPU で数日のうちにファインチューニングし、提供まで進めた。コーディングには Gemma、推論には OSS と使い分けた。
- **経済性の目安。** 1 セッションあたりの GPU コストは、コーディング支援で約 9 セント、長いコンテキストで約 12 セント、文書分析で約 16 セント、ナレッジ支援で約 43 セント（Signal65 の測定）。
- **MI455X（将来）**：ドルあたりのトークン数が最大 30% 多いと AMD は述べている。

## 9. まとめ

AI の需要は急拡大していて、エージェントの要求はすでに人間のトラフィックを上回っています。エージェント型 AI は推論を重ねるため、1 種類のシリコンでは足りず、Azure は自社設計のシリコンと AMD Instinct を組み合わせて提供しています。

AMD は Azure で 3 世代・4 年にわたる取り組みを重ねてきました。現在 Foundry で使える MI300X は、192 GB のメモリを生かして少ない GPU で大きなモデルを動かし、30 分以内のデプロイとセッションあたりの低コストを実現する、というのが発表者の説明です。次の世代の MI455X（Helios ラック）は、メモリ、スケールアップ帯域、オープン標準のスタックを強みとして、先端モデルの推論向けに Azure へ登場する予定です。企業にとっては、Foundry のモデルサービスが最も速く、コスト効率のよい利用方法だと、Sai 氏は結んでいます。
