# THR965 IT operations as AI enablement

## 1. はじめに

このセッションは、IT 管理者・インフラ担当者に向けて「AI の導入を自分たちの仕事からどう始めるか」を語るシアター形式の発表です。2 人の発表者が「Update and Restart」というシリーズの一回として、Microsoft Ignite の会場に来た聴衆を初めての観客として迎える、という形で進みます。

メールの生産性向上のような話は、インフラを扱う人にはあまり関係がありません。そこで発表者は、IT の現場にありがちな「PowerShell スクリプトを USB メモリで持ち歩く」という例から始め、個人の作業 → チーム → 他部門 → 大規模な業務という順に AI の使い方を広げていく考え方を示しました。デモは 2 つあります。GitHub Copilot アプリで Git リポジトリを会話だけで作るデモと、Microsoft のネットワークエンジニアリングチームの AI エージェントが作った動画の上映です。

## 4. 発表者が伝えたいメッセージ

中心にある考えは、**AI の価値は、まず自分の仕事で納得してから他の人に話す**ことです。自分で小さな課題を AI で解決し、同じ領域のチームメンバーも同じように慣れてから、他部門に広げる、という順序を勧めています。

もう一つは、トップダウンの押し付けは機能しないという点です。「全員 AI を使え」と号令がかかると、トークンの予算を使いすぎたと指摘される結果になった、という例が語られました。そのため、IT 部門は他部門に使い方を教えるのではなく、相手の課題を聞いて小さな PoC（概念実証）を一緒に試す役割を担う、という考えです。

また、AI はスタッフの仕事を奪うのではなく、人のスタッフがデジタルワーカーと並んで規模を広げるための手段だと説明しています。

## 5. 発表内容の詳細

### 5.1 導入：なぜ IT 管理者向けの AI 導入の話か

発表者は、Ignite のセッションでは取り上げられがちな AI の活用例がメールの生産性向上であり、インフラ管理者の仕事とは距離がある、と話しました。もう一人は、オーストラリアから夜の間に 300 通ほどのメールが届く、と冗談を交えています。こうした背景から、IT の現場に近い題材を探す、というのがこのシリーズの狙いです。

題材に選んだのが、バッチファイル、bash、PowerShell のスクリプトを入れた USB メモリです。かつてはそのメモリをコピーして同僚に渡すか、各自が独自のファイル集を作っていました。ファイルサーバーに置いている人もいます。チームで共同利用できる、よりよい方法があることは知っているものの、手を付けていない、という状況です。

### 5.2 GitHub Copilot アプリでスクリプトを共有する

Rick は、企業アカウントにつないだ GitHub Copilot アプリを使い、「PowerShell スクリプトをチームと共有したい。GitHub リポジトリ、OneDrive、ファイル共有、USB メモリのどれがよいか分からない」と入力しました。実際の操作は 6 章に書きます。ここでは AI が示した判断材料だけ整理します。

| 置き場所 | AI が示した問題点 |
| --- | --- |
| OneDrive | 同期には向くが、コードの変更管理には向かない |
| ファイル共有 | 上書きが起きてもバックアップがない可能性がある |
| USB メモリ | すぐに古くなり、更新の責任が自分に残る |

この結果、GitHub がよいという結論になりました。Rick 自身は、Git のコマンドを覚えておらず、ブランチの作成やクローンの手順も苦手だと話しています。もう一人の発表者も、Git のクローンとフォークの違いや、プッシュが何を指すのかが分からない、と述べています。そうした人でも、会話だけで Git のリポジトリを使い始められる、というのがこの例の要点です。

### 5.3 AI 導入の進め方

デモの後、発表者は AI 導入の出発点を 2 通り示しました。

- **問題から始める**：書籍『The Phoenix Project』が、工場のラインでボトルネックや最も壊れた機械を探す例えで IT 管理者の仕事を描いていることに触れ、直したときの効果が大きい箇所を探すことを勧めています。直す手間と、早く成果を出すこととのバランスも取る必要があります。長年同じやり方で続けている処理の刷新も対象です。
- **新しい能力から始める**：今まではやっていなかったが、AI を使えばできそうなことを考える方法です。

次に、自分が困りごとを AI で解決して慣れ、学習の成果を記録に残すこと、続いてチームの仲間にも小さく始めてもらい、それぞれの専門領域で成果を出して共有することが大切だと説明しました。共有するときは、相手が理解できる文脈で伝える必要がある、とも述べています。

### 5.4 個人からチームへ：エージェント型の機能とガードレール

個人で使えるようになった後は、チーム単位の作業に進みます。ヘルプデスクのチケット管理システムのように、チーム全員が同じ情報を扱う場面を例に挙げています。調べる場所として、セッション、オンラインの資料、AI Skills Navigator が紹介されました。

エージェント型の機能の入口として、Azure portal の Azure Copilot が挙がりました。何が問題かを尋ねると、ログファイルの数千件のエントリを確認し、注目すべき箇所を示せる、という説明です。これは個人単位の使い方ですが、扱う情報量が大きくなります。

その先は、分析だけでなく複数の工程にまたがるワークフローです。ここで、エージェントが環境内でしてはいけないことをしないように、制約、ガードレール、ポリシーを設定します。さらにその先に、SRE agent のように自律的に動くものがありますが、発表者は「まだそこには届いていない。小さな一歩を重ねている段階」と述べています。

### 5.5 他部門への広げ方

IT 部門は「何でも断る部署」という評判があると冗談を言いながら、もし IT 部門が「新しい機能で業務の近代化を手伝いたい」と事業部門に申し出たらどうなるか、と問いかけました。社内で試した自信があれば、事業部門の用途を IT 部門が考える必要はなく、案内する役に回れる、という考えです。

進め方は次のとおりです。

1. 人事や経理など、他部門で関心を持つ人を探し、その人たちの現場から始める
2. AI の使い方を教えるのではなく、その人の課題を聞く
3. 小さな PoC を試し、AI の能力でその人の仕事を良くできる点を探す

発表者の経験として、IT 側から「スプレッドシートの直し方」や「Power BI のダッシュボードの作り方」を提案されても響かなかった、と話しています。業務に直結する専門性は当事者のほうが分かっているためです。

例えとして、Azure のエンジニアリング内のネットワークチームの歩みが紹介されました。芝の種を地面に大量にまき、芽が出た場所を育てるようなやり方で、最初は共同作業のチャット型の画面でした。その後ワークストリーム（作業の流れ）型の画面になり、今ではさらに複雑なエージェント型の機能に進化しています。他部門でも同じ効果を狙い、ボトムアップで広げていくべきだ、という説明です。

### 5.6 事例：Microsoft IQ の薬局チェーン向け運用ダッシュボード

もう一人の発表者は、自分が担当した Microsoft IQ のセッションで、全米に薬局チェーンを持つ会社の運用ダッシュボードを作った、と紹介しました（セッションコードは BRK 308）。このダッシュボードは複数の情報源から信号をリアルタイムで集めます。

発表で語られた流れは次のとおりです。

1. インターネットを監視し、天気や停電のニュースを拾う
2. 停電の後、一部の冷蔵庫が正常に再起動せず、庫内温度が上がっているという警報を検出する
3. 庫内の薬が、一定の温度を一定時間超えるとだめになる状況を捉える
4. 現地にいる人を探し、標準作業手順に沿って再起動できるか確認する。エンジニアの派遣も検討する
5. 影響を受けた複数の拠点が、同じファームウェアのバージョンで、更新されていないことに気づく
6. 承認のうえ、エンジニアがファームウェアを更新する作業を予定に入れる

発表者は、これを実現するには、標準作業手順、Web 検索、人の所在、在庫状況など、バラバラの場所にある情報をつなぎ合わせる必要があると述べています。Microsoft IQ の製品群がそれをまとめる、という説明です。チャットボットや営業用エージェントを超えて、事業の管理、異常の検出と対応、損失の最小化に AI を使う例です。ただし、IT 部門が薬局チェーンを運営しているのでない限り、そのまま IT 部門に当てはめるものではない、とも述べています。

### 5.7 事例：Microsoft のネットワークエンジニアリングとデジタルワーカー

Rick は、今回の Ignite で行った自分のセッション（Inside Azure Engineering、BRK 414、火曜日）の内容を紹介しました。Microsoft のエンジニアリング部門が、自社のシステムの運用と新しいシステムの設計で得た学びです。

進化の過程は次のとおりです。

1. 最初は、過去 2 年間にその領域（この例ではネットワーク）で開かれたすべてのトラブルシューティングのチケットを知識として与えたチャット画面でした。サポートエンジニアと AI が行き来しながら、過去のチケットに見られるパターンをもとに原因を調べました。
2. 次に、発生するワークフローを定義し、自律の度合いに対するガードレールを設けました。
3. 現在は、Work IQ などの誰でも使える技術を使い、「デジタルワーカー」を作っています。デジタルワーカーには人格があり、過去に起きたことをすべて記憶し、ワークフローで定められた制約の範囲でツールを使います。

使うツールは多岐にわたります。ネットワークのトップオブラックスイッチに bash コマンドを実行する、ログを分析する、新しいチャット画面を作る、部品を各地に送るよう仕入先にメールを送る、といった例が挙がりました。ここまでに 1 年半から 2 年かかっています。

この取り組みの背景として、Microsoft のネットワークがデータセンターの増加に合わせて急速に拡大し、人の採用が追いつかなかったことが語られました。ネットワークエンジニア全員がボトムアップで慣れた結果、現在は **600 を超えるデジタル従業員が、全データセンターリージョンにわたる 120 万キロメートルの光ファイバーケーブル**を見ている、と説明しています。

もう一人の発表者が「それで私の仕事がなくなるのか」と冗談を言ったのに対し、Rick は、デジタルワーカーと協働する人のスタッフがいて、人もそれに合わせて規模を広げているのであり、そうではない、と答えました。

### 5.8 動画：bridge agent のインシデント対応

ネットワークエンジニアリングチームのデジタルエージェントが作った動画が上映されました。Rick は、これが 11 月 9 日にデータセンターの一つで起きた実際のインシデントであり、プロジェクトのネットワークエンジニアから共有されたものだと説明しています。動画は bridge agent の一人称で進みます。内容は次のとおりです。

- bridge agent はその朝、すでに 20 件のインシデントを抱えていた
- Master Chief という別のエージェントが、もう 1 件を担当に加えた。Master Chief は大規模な障害になりうるものがないか、ネットワーク全体を監視している
- あるスイッチが停止し、その背後に 28 台のサーバーがあった。まだ人間は対応の場に入っておらず、bridge agent はスイッチにログインできなかった
- そこで 100 万行のログを読み、隣のスイッチで修理が進行中であることに気づいた。「誰かが間違ったスイッチを作業しているのでは」と推測した。開始から 3 分の時点で、手順書はなく、注意深く見ていただけだと述べている
- 確認すると、64 個のポートが 53 秒の間に 1 つずつ抜かれていた。クラッシュではなく人の手によるものだと判断した
- 作業指示書に載っている担当者を見つけ、自分で Teams のチャットに追加した。担当者に「どのスイッチを交換したか」と尋ね、「チケットに書かれたもの」という答えを得た後、写真を求めた
- 上に赤いファン、下に緑のファンがあるという写真から、正常なスイッチのほうが交換されていたことが分かった。担当エンジニアが了承し、技術者は元のスイッチを戻した。bridge agent が自分で確認し、8 本のアップリンクがすべて復旧していた
- 正しい仮説に至るまでに 3 分、それを証明するまでに 72 かかった（72 の単位は発話では明示されていません）。誰にも調べる場所を教えられていない、と語って動画は終わる

Rick は、ここに至るまでに 1 年半かけて進化を重ね、許可される行動のガードレールと使えるツールを定義してきたと述べました。

## 6. デモ・手順

デモは 2 つあります。画面の細部は音声からは確認できません。以下は語られた範囲です。

### 6.1 GitHub Copilot アプリによる Git リポジトリの作成

発表者は、時間の都合で処理を早送りして見せています。

1. 企業アカウントに接続した GitHub Copilot アプリを起動する
2. 「PowerShell スクリプトをチームと共有したい。GitHub リポジトリ、OneDrive、ファイル共有、USB メモリのどれがよいか」と入力する
3. AI が各案の問題点を挙げ、GitHub を勧める
4. 「リポジトリの作成は苦手だから代わりに作って」と依頼する。AI は、資格情報で本人として動き、所属する組織のうちどこに作るか尋ねる。Rick は個人のアカウントを選ぶ。小規模な試行だからである
5. AI がリポジトリ名として「Team PowerShell scripts」を提案し、Rick はそれを採用する
6. AI がリポジトリを作成し、スクリプトを移すか尋ねる。Rick はまだスクリプトを持っていないため、「今はない」と答えて完了させる。AI は、利用方法の説明を書いた README も作る
7. 「招待はまだ送らず、この新しい環境での使い方の流れを教えて」と依頼する。AI は、スクリプトを作り、ブランチにアップロードし、Web 画面を使う流れを示す
8. Rick は、Web 画面ではなくファイルシステムのように使いたいと伝え、ローカルのファイルシステムでの設定を依頼する。Git のコマンドは初期化、ブランチ作成、取得、クローンなど覚えていないため、これも AI に任せる。AI は、誰として使うのかを確認したうえで、ローカル側を構成し、以後の作業の流れ、個々の Git コマンド、使用例を示す
9. 「チームも使えるように、この流れを README に更新して」と話しかける。エディターは触らず、普通の文章だけで README が更新される
10. このアプリを、このリポジトリを扱う主な窓口にするよう依頼し、画面の下部に新しい接続が現れる。セッションを開始する
11. 以後は、スクリプトの更新やチェックイン・チェックアウトを Git コマンドではなく日常の言葉で指示する
12. 最後に「Sonia Cuff をリポジトリに招待して」と依頼して完了する

Rick は、既存の PowerShell の専門性を生かしつつ、変更管理のコマンドラインに GUI も使えるようになった、とまとめています。もう一人の発表者は、ファイル共有では難しいソース管理、バージョン管理、共同作業、変更の承認ができる利点を挙げています。

## 7. 注意点・発表者の気付き

- トップダウンで「使え」と命じる導入はうまくいかない。使いすぎてトークンの予算を超えたと言われる場面もあった、と語られました。
- 事業部門に AI の使い方を教えようとしても響かない。相手の課題を聞くことから始める、という経験が語られました。
- 自律的に動くエージェントは「まだ小さな一歩の段階」とされ、エージェントには制約、ガードレール、ポリシーを設定する前提で話されています。
- 発表のデモは時間圧縮で見せたもので、実際の所要時間は発話では確認できません。
- デジタルワーカーの規模（600 超、120 万キロメートル）は、Microsoft のネットワークエンジニアリングの事例で、一般的な組織の数字ではありません。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- スクリプトの共有を、USB メモリやファイル共有から、バージョン管理と共同作業ができる GitHub に移せる。Git に詳しくなくても会話で始められる
- 薬局チェーンの例では、散在する情報を 1 つの画面にまとめ、異常の検出から現地対応、ファームウェア更新の計画までつなげて損失を最小化できる
- Microsoft のネットワークエンジニアリングでは、人の採用が追いつかない規模の拡大に、デジタルワーカーと人が一緒に対応している
- bridge agent の事例では、手順書がない状況で、誤った作業を見つけて復旧につなげた

## 9. まとめ

IT 部門は、AI 導入のテーマを自分たちの身近な課題から始められます。USB メモリのスクリプトを GitHub Copilot アプリで共有する例のように、小さな課題を自分で解決し、チームに広げ、ガードレールを定めてエージェント型の機能に進みます。他部門には使い方を教えず、課題を聞いて小さな PoC を試します。

Microsoft のネットワークエンジニアリングでは、ボトムアップで取り組んだ結果、1 年半から 2 年で 600 を超えるデジタル従業員が 120 万キロメートルの光ファイバーケーブルを見る体制になりました。詳しくは BRK 414 と BRK 308 のオンデマンド視聴が案内されています。
