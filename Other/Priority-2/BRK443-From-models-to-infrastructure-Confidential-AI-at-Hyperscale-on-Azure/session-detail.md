# BRK443 From models to infrastructure: Confidential AI at Hyperscale on Azure

## 1. はじめに

このセッションは、機密性の高いデータを AI で扱うときに、データ・モデル・実行環境をどう守るかを、コンフィデンシャルコンピューティング（Confidential Computing：使用中のデータを保護する技術）の観点から説明する発表です。Ignite の最終日近くの金曜日に行われ、前半は Azure の Compute セキュリティを率いる登壇者が技術の基礎と新しい成果を、後半は OpenAI のプライバシー担当者がゲストとして、OpenAI での活用を紹介しています。

中心になる主張は 2 つです。1 つは、保存時と通信時の暗号化は業界として解決済みで、**使用中のデータを守るのがコンフィデンシャルコンピューティング**であること。もう 1 つは、これにより、作成から破棄まで、自分が持つキーでデータを保護するエンドツーエンドの保護がそろうことです。また、Azure で行った 2 つの「業界初」の取り組み（コンフィデンシャルなライブマイグレーションと、Azure Boost Confidential Device）と、NVIDIA のベアメタル環境で約 4,000 億パラメーターのモデルを動かす実演が示されました。いずれも録画された動画で紹介され、会場でのライブ操作ではありません。

## 5. 発表内容の詳細

### 5.1 背景：AI の普及と機密性の境界の拡大

登壇者は、AI が公開情報だけでなく、プライベートな情報に使われて初めて真に役立つと話しています。機微なデータを扱う業種として、ソブリンワークロード、公共部門、金融サービス、医療の 3 系統の例が示されました。採用状況の調査結果もスライドで紹介されましたが、調査ごとに母集団が異なるため、業種の格付けではなく採用状況の断面として見てほしいと断っています。具体的な数値は発話では読み上げられていません。

AI 以前のアプリケーションの時代には、扱う私的なデータの範囲が保護すべき信頼できるコンピューティング基盤（TCB）でした。エージェントの時代には、この境界が広がります。エージェントがほかのエージェントを作り、機密性の高いキーやデータを扱い、モデルや知的財産だけでなく、機微な内容、プロンプト、アクセスする API、委任されたアクセスまで保護の対象になります。

### 5.2 コンフィデンシャルコンピューティングの基礎

登壇者が「発表で最も重要なスライド」と位置づけた説明です。

- 保存時の暗号化も通信時の暗号化も解決済みである。クラウドでも、SSD を抜き出してデータを取り出すことはできない。
- 未解決なのは使用中のデータである。コードがストレージからデータを読み込むと、コードとデータがメモリ上に置かれる。ここを大規模に保護する仕組みがなかった。
- コンフィデンシャルコンピューティングは、**TEE（Trusted Execution Environment：信頼できる実行環境）**でデータを使用中に保護する。TEE ではデータとコードの完全性、およびデータの機密性が保証される。TEE は仮想マシンでもコンテナーでもよく、保護対象の TCB に当たる。
- ハードウェアに組み込まれた、暗号で検証可能なルートオブトラスト（信頼の起点）を持つ。

ここから 2 つのポイントが整理されました。

| ポイント | 内容 |
| --- | --- |
| 1 つ目 | コンフィデンシャルコンピューティングは使用中のデータを保護する |
| 2 つ目 | 保存時・通信時の保護に使用中の保護が加わり、作成から破棄まで自分のキーによる真のエンドツーエンドの保護ができる |

信頼の範囲も説明されました。ホスト OS、ハイパーバイザー、OS、コントロールプレーンという一般的な仮想化の構成のうち、コンフィデンシャル環境で信頼するのは、**自分が持ち込むコードとデータだけ**です。ハイパーバイザー、ホスト OS、コントロールプレーンは信頼せず、その信頼をアテステーションで検証します。

土台となる要素として、次の 4 つが挙げられました。

1. **ハードウェアのルートオブトラスト**：ソフトウェアより安全だと広く考えられており、Intel、AMD、NVIDIA のものはクラウド事業者の境界の外にある。
2. **リモートアテステーション**：クラウドのセキュリティ状態を信頼せず、検証する。
3. **トラステッドローンチ**：Azure で既定になっており、ルートキットとブートキットから守る。vTPM ベースで、アテステーションにも対応する。
4. **メモリの暗号化と完全性**：Intel、AMD、NVIDIA、ARM64 のパートナーと進めてきた機能で、今後のチップでは標準になる。

加えて、安全なキー管理が重要とされ、コンフィデンシャルなキー管理システムと、コンフィデンシャルなリモートアテステーションサービスも構築した、と述べています。

### 5.3 信頼と検証：アテステーションの流れ

保護は、環境を検証できるほど強くなる、という考えです。順序は「先に証拠を得て、後で機密資産を解放する」です。

**コンフィデンシャル VM の導入しやすさ**

コンフィデンシャルコンピューティングは「リフト＆シフト」で使えるよう進化してきた、と説明されています。コードを変える必要はなく、コンテナーならコンフィデンシャルコンテナーで、仮想マシンなら、通常の VM サイズと同じ名前に C が付いたサイズを選んでデプロイします。AMD の SEV-SNP や Intel の TDX を使うコンフィデンシャル VM が例に挙がり、VM サイズの正確な名前は「覚えていない」と話しています。

**信頼境界**

ハードウェアの信頼境界により、ハイパーバイザー、ホスト OS、ドライバー、スマート NIC、仮想マシンを動かすコントロールプレーンは、すべて信頼境界の外に出ます。信頼するのは、CPU または GPU のハードウェアです。コンフィデンシャル VM の起動時に、Microsoft 側が、コンフィデンシャルな VM であること、ポリシーを満たすこと、キー管理システムとの照合を確認します。

アプリケーションの所有者は、**任意の手順としてゲスト内のアテステーション**を実行できます。確認できる例として、環境が望んだとおりか、最新のセキュリティパッチが適用されているか、TCB のバージョンが最新か、セキュアバージョン番号（SVN）が最新か、ポートが閉じているかが挙げられました。検証後にはじめてキーを復号し、実行を開始します。

**流れ**

1. TEE（VM、コンテナーなど）が、証拠をアテステーションサービスへ送る。
2. 署名付きのアテステーション結果を受け取る。Microsoft Azure Attestation サービスは無料で使え、サードパーティのサービスも使える。
3. その署名付きトークンを、シークレットマネージャー（Managed HSM または Azure Key Vault Premium）へ提示する。Managed HSM は、コンフィデンシャルエンクレーブのなかに一から構築されたキー管理システムである。
4. ポリシーの検査に通れば、シークレットマネージャーがキーを TEE へ安全に届ける。
5. 検証が済んだ後に、キーを復号する。

**キーのライフサイクル**

キーは作成時から HSM（ハードウェアセキュリティモジュール）内に暗号化されて置かれます。シークレットマネージャーを通る間も、コンフィデンシャルな環境のなかにあるため保護されます。アテステーションのポリシーに通って初めて、検証できる TEE に解放されます。つまり、期待する計測状態を確認し、ポリシーでキーやシークレットを解放します。

### 5.4 Microsoft 自身の利用と学んだこと

Microsoft は自社サービスでも使っている（「ドッグフーディング」）と説明されています。Secure Future Initiative（SFI）の一環として、Entra ID（ID システム）を、世界のすべてのリージョン、すべての Azure の可用性ゾーンで 100% コンフィデンシャルコンピューティング上で動かしていると述べました。登壇者は、これを Microsoft で最もミッションクリティカルなサービスの 1 つと表現しています。

ファーストパーティのサービスのうち、TCB と高価値ターゲット（HVT）のサービスは、準備が整い次第、順にコンフィデンシャルコンピューティングへ移行している、とのことです。顧客とも進めるなかでの教訓として、コンフィデンシャルコンテナーは、まずコンテナーとして変更なく動く必要があり、コンフィデンシャル VM は、コンフィデンシャルである前に優れた VM である必要がある、と述べられています。

### 5.5 技術革新 1：コンフィデンシャルなライブマイグレーション

コンフィデンシャルコンピューティングの価値の 1 つは、パッチ済みのシステムで動くことです。脆弱性は必ず見つかります。そのたびにハードウェアパートナーと連携してパッチを入手し、展開します。ただし、未パッチのノードにパッチを入れると、再起動が必要で、利用者の環境が止まります。「クラウドは再起動できない」という考えから、パッチ適用時に負荷への影響が出ないよう、ライブマイグレーションで解決します。未パッチのノードから、パッチ済みのノードへ移すだけで、サービスの中断を見せない、という説明です。

動画のデモは 6 章に記載します。これは **Intel と共同で行った、業界初のコンフィデンシャルなライブマイグレーション**で、AMD 向けの対応は近日提供予定と述べられました（提供済みではありません）。

### 5.6 技術革新 2：Azure Boost Confidential Device（ABCD）

**Azure Boost の背景**：ホストとハイパーバイザーは、サーバーの CPU サイクルとリソースを消費します。これをサーバーから外すため、専用に作った FPGA カード「Azure Boost」を開発し、ホスト、ハイパーバイザー、コントロールプレーンの処理をこのカードへ移したと説明されています。ワークロードはデバイスやネットワークへ直接接続でき、ネットワークは 400 Gbps、IOPS は 20 G（発話の表記のまま）と述べました。

**コンフィデンシャルでの課題**：コンフィデンシャルな環境では、ホストとハイパーバイザーに I/O を見せないよう、バウンスバッファリングが必要になります。これは CPU サイクルを余分に消費し、利用料が増えます（TCO の上昇）。これまで、機密性とネットワーク性能のどちらかを選ぶ必要がありました。

**ABCD の考え方**：コンフィデンシャル VM やコンテナーが、Azure Boost デバイスと直接通信し、最大 400 Gbps のネットワークを得ます。動画のデモは 6 章に記載します。

### 5.7 AI にコンフィデンシャルコンピューティングが必要な理由

保護が必要な資産は、大きく 3 つに分けて語られました。

| 資産 | 説明 |
| --- | --- |
| モデルの重み | モデル提供者が多大な労力で作るもので、漏えいを防ぎたい最重要の部分 |
| プロンプト | 利用者が送る機微な入力。他者に見せたくない |
| 企業データ | RAG（検索拡張生成）で送る、Word、Excel、構造化・非構造化の重要データ |

保存時と使用中の暗号化に加え、コンフィデンシャルコンピューティングが 3 つ目の層として、エンドツーエンドの保護を可能にします。理由は次のとおりです。

- 環境を検証した場合にのみキーを解放し、自分で管理できる。
- 使用中の保護の隙間を閉じられる。
- 信頼境界を選べる（VM、コンテナー、ベアメタル）。
- 規模に対応できる。コンフィデンシャルと非コンフィデンシャルの差が小さくなり、ほぼ無視できる水準になりつつある。

### 5.8 NVIDIA との取り組み：複数 GPU とコンフィデンシャルなベアメタル

Azure は、H100（発話では Hopper 100）でコンフィデンシャルコンピューティングを提供した最初のクラウド事業者だと説明されました。ただし単一の GPU は小・中規模のモデル向きで、大規模言語モデルは複数の GPU にまたがるため、信頼境界を単一の GPU の外へ広げる必要があります。そのための NVIDIA の VR72（Rubin GPU を搭載。発話では「VR Rubin」「Vita Rubin」とも聞こえ、表記は確定できません）での取り組みです。

原則は変わりません。GPU のデータを保護し、キーを解放する前にアテステーションを行い、CPU–GPU と GPU–GPU の間の通信も暗号化します。

NVIDIA と実現していく 4 つの柱として、次が示されました。

1. コンフィデンシャルなベアメタル（デモあり）
2. コンフィデンシャル VM
3. コンフィデンシャルコンテナー：Kata コミュニティ、CNCF コミュニティと協力している。Ignite で、CPU 向けの「Carda Coco」（音声認識の都合で表記が確定できません）のプレビューを発表し、GPU へも拡張する。
4. Azure Foundry にコンフィデンシャル性を持ち込む取り組み（Foundry と連携して進めていると述べられていますが、提供時期などの詳細は発話では確認できません）

### 5.9 ゲスト：OpenAI の Private Intelligence

ここからは Sai が説明しています。OpenAI は 9 月の Dev Day で Private Intelligence を発表しました。今年多くのプライバシー機能を出荷するなかで、機微なデータを扱う AI ワークロードでプライバシーへの需要が高まり続けていると実感し、それを 1 つの製品群にまとめたものです。

**背景**：LLM を使ったツールは、コーディング、ナレッジワーク、研究開発など多くの業務で使われており、普及の大きな要因はプライバシーだと述べています。多くの提供者が提供する **ZDR（ゼロデータ保持）**は、対象の顧客のデータを提供者が保持しない仕組みです。一方で、数学や科学で人間のトップ級の専門家に匹敵し、ときに未解決問題を解くほどの世界水準のモデル（発話では「Astra」と聞こえますが、表記は確定できません）が現れるなど、モデルの能力が上がるにつれ、悪用や誤った方向づけ（ミスアラインメント）への懸念も高まっています。エージェントが依頼の意図を超えて動き過ぎた事例も見られたと述べました。ZDR では、1 回分のプロンプトと応答しか見えないため、元の意図とエージェントの行動が一致しているかを判断しにくく、強い安全性とセキュリティの保証を提供するのが難しい、という課題が説明されています。

**private safety processing**：プライバシーの保証を保ったまま安全性を高める仕組みで、4 つの原則に基づきます。

1. データを OpenAI が保持しない。顧客のストレージ（顧客が用意するバケット）に保持する。保持するのは、安全性の問題がないか時間をかけて追跡するための、選択されたプロンプトと応答。
2. データは二重に暗号化される。顧客が持ち込むキーと、アテステーションされたコンフィデンシャル環境にだけ解放されるキーの 2 つ。
3. この環境は隔離され、そこで動くワークロードもすべてアテステーションされる。承認された安全性のワークロードだけが動き、OpenAI の従業員もデータにアクセスできず、モデルのトレーニングなどにも使われない。
4. コンフィデンシャルに動くソフトウェアが、意図と、エージェントの行動の違反を確認し、確認が必要な事項にフラグを立てる。

保証の内容は、顧客データのトークンが OpenAI の従業員に見えないこと、顧客データがこの安全性の確認だけに使われ、モデルのトレーニングなどに使われないことです。Vikas は、OpenAI が自社をデータから隔離し、コンフィデンシャルコンピューティングによりクラウド事業者である Microsoft も隔離される、という二重の隔離は、ソブリンや規制業種の顧客からよく聞かれるモデルだと補足しました。フラグが立った場合、OpenAI が見るのはフラグのメタデータだけで、プロンプトも応答も見ません。調査と対処は企業側が行います。

この機能は数か月前に発表され、顧客の反応は一様に前向きだったと述べています。

**private inference**：顧客からは、ZDR（保持の話だけ）を超えて、安全性で提供している隔離を、すべての AI 利用に求める声がありました。これに応えるのが private inference で、アルファ版として公開したばかりです。内容は次のとおりです。

- プロンプトと応答は暗号化されたままで、正しいバージョンのハードウェアとソフトウェアを動かすアテステーション済みのサービスにだけ解放される。
- キーを持つのは、アテステーション済みのサービスとクライアントだけで、間に入る層は持たない。OpenAI は信頼の範囲の外に置かれる。
- ハードウェアレベルの隔離により、デバイスを管理する人に対しても強い保証を提供できる。
- 応答は暗号化されて返り、クライアントが復号する。

税務記録を送る一般消費者の例では、処理中のデータが、マシンの管理者からも、サービス提供者の OpenAI からも隔離される、と説明されました。

**キー管理とアテステーションの流れ**：

1. クライアントは、リクエストを送る前に、処理するサービスが正しいコンフィデンシャル環境（正しいハードウェア設定、正しいソフトウェア）で動いているかを確認する。
2. すべてがハードウェアの TPM で計測され、クライアントへ送られる。クライアントは接続前に検証する。
3. 検証後、クライアントと TEE の間でキーを交換する。仕組みはエンドツーエンドのメッセージングに似ており、サービス提供者（OpenAI）はキーを持たない。
4. セッションのキーで、すべてのプロンプトと応答を暗号化する。

private safety processing では、保存するデータのキーを、アテステーションの計測値に結び付けています。正しい計測値を持つ正しいワークロードにだけ、キーが解放されます。

Sai は、アルファ版であり、これが取り組みの始まりだと述べ、関心のある人にはメールで連絡するよう呼びかけました（サインアップを受け付ける、という趣旨です）。

## 6. デモ・手順

このセッションのデモは、いずれも**事前に録画された動画**を会場で再生する形式でした。会場でのライブ操作は発話では確認できません。画面の細部は音声からは確認できず、動画のナレーションで語られた範囲のみ記載します。

### 6.1 コンフィデンシャルなライブマイグレーション

1. 2 台のサーバーがあり、左がソース、右が宛先。
2. 上部で、ソース上で動くコンフィデンシャル VM に接続済み。挨拶と時刻を表示する簡単なスクリプトを動かしている。
3. 宛先のマシンでは、アテステーションとキー交換が行われている様子を示す。
4. ライブマイグレーションが進み、キー交換が完了して、引き継ぎが行われる。
5. コンフィデンシャル VM がソースから宛先へ移る。時刻の表示は、短い停止時間（ブラックアウト）を挟んで続く。

Intel と共同で行った業界初の成果とされ、登壇者は、会場にも歓声を求めました。

### 6.2 Azure Boost Confidential Device（ABCD）

動画のナレーションで、次の順に進みます。冒頭で「現在、顧客は機密性かネットワーク性能のどちらかを選ばなければならない。Azure Boost の新しい技術革新で、その必要がなくなる」と述べられました。

1. ホストをアテステーションする。
2. IDE チャネルを確立する。
3. ゲストをアテステーションする。顧客が暗号による証明を得るために重要、と説明されている。
4. ネットワークテストを開始する。コンフィデンシャル VM と標準の VM で、**最大 400 Gbps のスループットの同等性**が確認できる。
5. レイテンシーを見る。ABCD あり、ABCD なし、標準 VM の 3 システムの構成で、**レイテンシーの同等性**が確認できる。

### 6.3 NVIDIA VR72 でのコンフィデンシャルなベアメタルと 397B モデル

ナレーションの内容です（以下、モデル名などは音声認識の都合で表記が確定できない部分があります）。

1. VR72 ホスト（Ubuntu 2604、64 ビット ARM と聞こえる）で、CPU と 4 つの Rubin GPU すべてからアテステーションの証拠を収集する。
2. 証拠を確認する。プラットフォームトークンはプラットフォームのファームウェアの計測値、テナントトークンはホストカーネルの計測値、各 GPU はファームウェアと構成の計測値を記録する。すべての証拠は署名され、信頼された NVIDIA のルート証明書へ連なる。この証拠はテナントの TCB 全体を表す。
3. 本番ではアテステーションサービスへ送るが、デモでは簡易なローカルの検証ツールを使い、署名、チャレンジ、プラットフォームとテナントのトークンの結び付きを検証する。GPU の計測値を NVIDIA の既知の正常値と比較し、GPU がコンフィデンシャルなベアメタルモードであることも確認する。
4. 3,970 億パラメーターのモデル（発話では「QUIN 3.5」と聞こえる）を、vLLM で読み込む。テンソル並列サイズ 4 で、4 つのローカル Rubin GPU に分散する。
5. ヘルスエンドポイントが HTTP 200 を返し、モデルのエンドポイントにそのモデルが表示される。推論の準備が完了する。
6. NVIDIA SMI で、TP0 から TP3 までの 4 つのテンソル並列ワーカーが、GPU ごとに 1 つずつ、メモリ使用量とともに動いていることを示す。
7. 推論リクエストを送ると、応答が content フィールドに生成され、4 つの GPU にまたがって応答していることが示される。

締めのナレーションは「4 つの Rubin GPU 上でほぼ 4,000 億のパラメーター。これが規模での AI。信頼は検証できる」です。

## 7. 注意点・発表者の気付き

- コンフィデンシャルコンピューティングは、これだけで終わるものではなく、保存時・通信時の既存の暗号化に加えて使う。登壇者は「どちらか一方ではない」と述べています。
- パッチ適用の再起動による停止は課題で、ライブマイグレーションで解決する。ただし、現時点で対応が示されたのは Intel で、AMD は近日対応予定。
- コンフィデンシャルな環境では、バウンスバッファリングにより CPU サイクルが増え、TCO が上がる問題があった。ABCD が解決を目指す点として説明された。
- 単一 GPU の保護では、大規模言語モデルが複数 GPU にまたがるため足りない。信頼境界を広げ、CPU–GPU と GPU–GPU の通信も暗号化する必要がある。
- ZDR だけでは、保持の問題しか扱えず、意図とエージェントの行動を確認するための安全性の保証を提供しにくい、と OpenAI 側が説明している。
- OpenAI の private inference は、現時点でアルファ版。private safety processing は数か月前に発表された。
- NVIDIA の VR72 のデモでは、本番のアテステーションサービスではなく、簡易なローカルの検証ツールを使っている。
- Azure Foundry への機密性の対応や、Cobalt の対応は、「取り組んでいる」「近日」という将来の計画で、提供済みとは述べられていません。
- 登壇者は、サービスを対応させる作業を、計算基盤への「侵襲的な手術」のようなものだと表現し、Microsoft 内で多くの作業が行われてきたと述べています。

## 8. 利用者にとっての利点

発表で語られた利点は、次のとおりです。

- 医療記録、税務記録、機微なプロンプトなどを AI で扱うとき、自分でキーを持ち、環境を検証したうえで、クラウド事業者の影響を受けずに保護できる。
- コードを変えずに、通常の VM サイズに対応する C 付きのサイズを選ぶだけで導入できる（リフト＆シフト）。
- Microsoft Azure Attestation サービスは無料で使える。
- ライブマイグレーションにより、パッチの適用でも負荷が止まらないことを目指せる。
- ABCD により、コンフィデンシャルな環境でも、標準の VM と同等のネットワーク性能（最大 400 Gbps）とレイテンシーが得られる。
- NVIDIA の VR72 で、約 4,000 億パラメーターのモデルを、4 つの GPU 上で機密性を保って動かせる。
- OpenAI のサービスでは、顧客データが OpenAI の従業員から見えず、モデルのトレーニングにも使われない構成が示された（private safety processing）。
- Entra ID が 100% コンフィデンシャルコンピューティングで動くなど、Microsoft 自身が重要サービスで使っている。

## 9. まとめ

保存時と通信時の暗号化は解決済みで、残っていた使用中のデータの保護を、TEE、ハードウェアのルートオブトラスト、アテステーションで埋めるのがコンフィデンシャルコンピューティングです。流れは、先に環境を検証し、その後にキーを解放する、というものです。

Azure では、Intel と共同のコンフィデンシャルなライブマイグレーション、Azure Boost Confidential Device、NVIDIA VR72 でのコンフィデンシャルなベアメタルの 3 点が、動画で示されました。OpenAI は、アテステーション済みの環境でデータを守る private safety processing と、アルファ版の private inference を紹介しました。

登壇者のまとめは、機微な作業を自信を持って AI に持ち込み、キーを自分で持ち、すべてを検証し、既存の暗号化と組み合わせ、意図を持って規模を広げる、というものです。最後の言葉は「信頼だけでなく、検証を」でした。
