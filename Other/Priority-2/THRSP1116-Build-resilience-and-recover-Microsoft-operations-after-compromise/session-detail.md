### 5.1 現状の点検：問いかけと調査結果

Rob は、「今日のリスクと課題に対して十分なサイバーレジリエンス戦略を実装済みだと思う人は挙手を」と聞き手に尋ねました。手が挙がったのは 1 人でした。

Cohesity は、直前の四半期に終えた世界規模の調査を行っています。3,500 人を超えるセキュリティと IT の意思決定者に同じ質問をしたところ、今日の環境で回復力を発揮できると自信を持つ人は、約 3 分の 1 でした。発表者は、数字は不安に見えても、改善が必要だと認めることが行動の出発点になるので前向きに捉えられる、と述べています。調査レポートへのリンクは、終盤に示されました。

評価の際に自問するべき問いとして、次の 3 つが挙げられています。

**問い 1：どの復旧ポイントを信頼できるか。** 設定変更の失敗なら、直近の時点に戻せば済みます。しかしランサムウェアなどのサイバー攻撃では、話が複雑です。直近のバックアップが侵害されていないとどう分かるのか。侵害はいつ始まったのか。その時点から現在までの間に何が起きたのか。その間のものは信頼できるのか。これらを考える必要があります。

**問い 2：ID 基盤が信頼できなくなったとき、信頼をどう取り戻すか。** Active Directory や Entra などの ID サービスは、復旧する他のすべてのものの土台です。環境全体を作り直すのか。規模が大きければフォレストの復旧が必要になりますが、その手順を理解しているのか、プロセスはあるのか、フォレスト復旧について Microsoft のガイダンスを実際に確認したのか。作り直さずに、的を絞ったやり方（外科的な復旧）をとるなら、オブジェクトのコピーを持っていても、どれを戻し、どれが侵害され、どれがまだ無傷なのかを判断する根拠が要ります。

**問い 3：エージェントなどの新しい基盤が復旧計画に含まれているか。** Copilot などのエージェント技術を展開している場合、その新しい基盤が計画の対象になっているかという問いです。Cohesity の調査では、AI 技術を新しい基盤やアプリ、周辺のものを含めて計画に取り込んでいた組織は 40% だけでした。戻すべきものはデータだけでなく、状態やエージェントのメモリにも広がっています。

### 5.2 枠組み：保護・検出・復旧

発表者は、覚えやすいように「3 つの規則」としてこの枠組みを示しました。

#### 保護（Protection）

指針は「重要なものをすべて保護する」です。簡単に聞こえますが、バックアップや保護をしていない組織や、そもそも何が重要か把握していない組織が多いと述べています。データがオンプレミスからクラウド、SaaS に広がり、状況はさらに複雑になっています。事業上重要なデータがすべて保護されているかを包括的に把握することが、強いレジリエンス戦略の土台です。

データを保護したら、確実に復旧できる状態にします。その原則は次のとおりです。

| 原則 | 内容 |
| --- | --- |
| 不変コピー（イミュータブル） | バックアップ後は変更できないコピーを持つ。さらに速度のため追加のコピーも持つとよい |
| 分離されたコピー | サイバーボールト（隔離された保管庫）のような技術。プライマリ環境の ID 基盤と結びついたバックアップ環境は、プライマリが侵害されると一緒に侵害されうるため、最後の防衛線として分離したコピーを持つ |
| 強いアクセス制御 | 多要素認証に加え、暗号鍵を自分で管理して分離する。マルチパーティ認可（定足数による認可）により、侵害された管理者 1 人や資格情報 1 つで、バックアップやポリシーを削除できないようにする |

分離されたコピーについて、Cohesity が脅威調査を行った結果として、最も被害の大きい最新のランサムウェアのどれも、分離されたサイバーボールトを復旧不能になるほど侵害できなかった、との説明がありました。

#### 検出（Detection）

目的は、復旧や復元が必要になる状況を、より先回りして把握することです。機密データを特定しておき、インシデントが起きたら影響範囲（ブラストラディウス）を把握します。影響を受けたのは主要なインフラ、アプリ、データだけではなく、それに依存する下流のもの、そこに触れる ID まで含まれます。

そこで、レジリエンスの仕組み、保護の仕組み、セキュリティの仕組みを統合し、テレメトリを双方向でやり取りすることが重要になります。例として、エンドポイントのテレメトリ、ログ、通常はセキュリティオペレーションセンター（SOC）の SIEM から来る情報が挙げられました。検出があれば、影響を受けたインフラがすぐに分かり、侵害された部分と、それに依存するすべての部分を把握して、連携した復旧ができます。

#### 復旧（Recovery）

インシデントによっては、信頼できるシステムとワークロードを復旧する段階に至ります。信頼できる運用状態に戻すには、アプリケーションとデータだけでなく、ID などの依存関係も必要です。環境全体にエージェントを展開している場合は特に、膨大な依存関係があると述べています。

### 5.3 Microsoft の視点：新しいサイバースタックとエージェント

枠組みが Microsoft の立場から見てどう当てはまるかを聞かれた Jason は、次のように述べました。

- 数日前から Ignite で言われているとおり、サイバーセキュリティの物理法則が変わりつつある。AI により攻撃側が加速しており、防御側の対応が追いつかない状況にある。一貫性のある復旧計画と、その枠組みのテスト、適切なツールの活用が不可欠である
- 新しく改訂されたサイバースタックでは、セキュリティハーネス内でエージェントを活用し、ツールと連携して、レジリエンスと、復旧時のデータへの信頼を提供する。復旧は環境が安定する時点まで行う
- Microsoft Ignite の発表から見えるのは、人間と AI エージェントが協力して最善の対応を目指し、復旧を加速する方向だ

新しいサイバースタックは、エージェント、セキュリティハーネス、AI モデルを組み合わせた枠組みです。組織内のさまざまなシグナルのコンテキストと洞察を、センサーとアクチュエーターを通じて使います。人間がアラートを受け、24 時間や 48 時間かけて調査して侵害を知り、それから対応するやり方は、この新しい状況では通用しない、というのが Jason の指摘です。リアルタイムの対応と攻撃の妨害（ディスラプト）を目指し、エージェントの機能で攻撃を修復する、と説明しています。

このモデルでは、A365（AI のオブザーバビリティ基盤として説明）が極めて重要だとされました。管理層とガバナンス層を通じて、セキュリティによって事業価値を見出すことが、Ignite での Microsoft の大きなメッセージだという認識です。

また Jason は、セキュリティ責任者との会話で受ける印象を次のように述べています。

- 多くの組織は、強い戦略を持っていない

## 6. デモ・手順

デモは Jed が担当しました。侵害を受け、アカウントに変更を加えられて特権アクセスを得られたという想定です。使用したツールは Cohesity の製品ですが、Jed は、どのツールでも、使う前にテストし、定期的に使って、実際に復旧できると分かっていることが大事だ、と述べています。途中でマウスの調子が悪くなりましたが、デモは完了しました。画面の細部は音声からは確認できず、以下は語られた範囲です。

デモは 2 部構成です。

### 6.1 オンプレミスの Active Directory の特権グループの復旧

1. 保護の画面で、実際に正常と分かっている、きれいなバックアップがあることを確認する。複数のスナップショットがあり、復旧元にしたい最新の正常なスナップショットは分かっている前提とする
2. アプリケーションと Active Directory の画面に移動する
3. スナップショットをマウントし、SOC から知らされたアカウントに変更がないかを確認する。SOC から、エンタープライズ管理者やスキーマ管理者のような特権グループに不審な動きがあると連絡があった、という想定
4. Active Directory スキーマ全体ではなく、問題のアカウントだけを正常な状態に戻したい。マウント後、実際に 2 つの特権グループ（ドメイン管理者とエンタープライズ管理者）に変更があったことが、差分として表示される
5. この 2 つにチェックを入れ、復旧に進む
6. 値を上書きする設定にする。変更された可能性のあるものや余計なものを、本番に戻したくないため
7. 復旧が成功したら、スナップショットをアンマウントする。成功が確認される

### 6.2 Entra ID の削除済みユーザーの復旧

ハイブリッド環境のため Entra ID も対象です。ユーザーが削除され、復旧が必要という想定です。

1. Cohesity Cloud Protection Services で Entra ID を参照し、テナントをクリックする
2. Azure のコンソールで、複数のユーザーがテナントから削除されていることを示す。削除済みユーザーの一覧にもなく、完全に削除（ハード削除）された状態である。ごみ箱が使えるのは 30 日間だけなので、延長されたバックアップが必要だと説明している
3. 正常と分かっているスナップショットを選ぶ。侵害されたものを AD に戻さないよう、21 日のスナップショットを選ぶ。接続された SIEM のツール（例として Microsoft Sentinel）でフォレンジックが行われ、正常だと確認された、という想定
4. スナップショットを参照する
5. 復旧を開始する。削除されたアカウントは 3 つであると示される。3 つを選択する
6. 復旧オプションを設定する。プロパティとリレーションシップの両方を復元し、悪意ある変更を持ち込まないよう、上書きも選ぶ
7. 復旧を実行する。成功が表示される
8. Azure コンソールに戻ると、3 人のユーザーが戻っており、ログインして使える状態になっている

Rob は、デモの要点として次を挙げました。復旧の土台となる重要な依存関係（ID）を整えたこと。オンプレミスの Active Directory から、クラウドの Entra まで同じ流れで示したこと。検出の要素、保護されていたデータ、そして復旧が見えたこと。数分以内に、単一のプラットフォームで完了できたこと。この統合されたプラットフォームが、運用のスピードと統一された可視性を高め、通常運用への復帰を早めるという説明です。

## 7. 注意点・発表者の気付き

- ランサムウェアなどの復旧では、直近のバックアップが安全とは限らない。侵害の開始時点を考えて復旧ポイントを選ぶ必要がある
- 復旧は、環境全体の再構築と、的を絞った復旧という選択肢がある。再構築ならフォレスト復旧の手順を理解しておく必要がある
- 復旧時は、変更された値や余計なものを戻さないよう、上書きで復元する（デモで 2 回示された選択）
- Entra ID のごみ箱は 30 日間しか使えないため、延長バックアップが必要
- バックアップ環境が、プライマリの ID 基盤とつながっていると、一緒に侵害されうる。分離されたコピーが最後の防衛線になる
- どのツールを使うにせよ、使う前にテストし、定期的に使うこと
- 復旧の対象は、データだけでなく、状態とエージェントのメモリにまで広がっている
- 今回の調査結果の数値（約 3 分の 1、40%）の詳細な定義は、発話では語られていません

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 保護・検出・復旧の枠組みで、現在の状態をベンチマークし、ギャップに基づいて計画を更新できる

- 単一のプラットフォームで、保護、検出、復旧を行える。デモでは、AD と Entra ID の復旧を数分以内で行った
- 計画にエージェントを含めることで、エージェントの操作前の状態へ戻る備えができる

## 9. まとめ

侵害後の復旧では、「どの復旧ポイントを信頼できるか」「ID 基盤の信頼をどう取り戻すか」「エージェントを計画に含めているか」の 3 つの問いに答えられることが出発点です。答えるための枠組みが、保護（不変・分離・強いアクセス制御）、検出（影響範囲の把握と、セキュリティ基盤との双方向の連携）、復旧（アプリ、データ、ID などの依存関係を含めた復帰）の 3 つでした。

Microsoft 側からは、AI により攻撃が速くなっているため、人間の調査を待つ対応では間に合わず、人間とエージェントが協力して、リアルタイムに対応する方向だと説明されました。デモでは、特権グループと削除済みユーザーを、正常なスナップショットから上書き復旧しました。持ち帰る点は、能力のベンチマーク、ギャップに基づく計画の更新、そしてエージェントのためのレジリエンス機能の整備です。
