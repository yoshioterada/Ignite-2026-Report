# BRK437 Learning from disruption: Resilience against force majeure

## 1. はじめに

このセッションは、Azure の障害時にお客様へ情報を伝える立場にいる 2 人が、「障害をどう伝え、どう学び、どう備えるか」を語ったブレークアウトです。題材は、Azure 自身が原因ではない大きな出来事、つまり不可抗力（force majeure）に近い 4 つの事象です。CPU の脆弱性 Spectre Meltdown、新型コロナウイルスの世界的流行、CrowdStrike の更新による Windows 端末の大規模停止、中東の紛争によるデータセンターへの影響が取り上げられました。

冒頭の実話にあるとおり、障害そのものより、障害時の沈黙が信頼を壊すという考えが一貫して語られます。そのうえで、障害の前・最中・後に何をすべきかが、Microsoft 自身の経験と Azure のサービスを交えて紹介されました。**障害は避けられないが、影響の大きさは備えで変えられる**というのが結論です。

## 4. 発表者が伝えたいメッセージ

最初に語られた実話は、銀行の取引を記録する第三者の金融会社が起こした障害です。水曜の午後に障害が始まり、木曜も金曜も会社から連絡がありませんでした。銀行側は、事業継続の訓練に従って切り替えた部門もあれば、取引を完全に止めた部門もありました。ランサムウェアの噂が広がり、規制当局や苦情対応の担当者も動く事態になりました。月曜にシステムは復旧し、会社は「問題があったが解決した。ご迷惑をおかけした」とだけ発表しました。数年後、この会社は事業をやめており、災害時の振る舞いが要因の 1 つになった可能性があると語られています。**沈黙は危機対応の一部ではなく、失敗そのもので、障害はシステムを壊すが、沈黙は信頼を壊す**というのが出発点のメッセージです。

もう 1 つの柱は、障害の原因を 1 つに絞らず、多くの要因から学ぶという姿勢です。そして、お客様側にも責任分担があり、障害は避けられなくても、層を重ねて穴を小さくすれば影響を減らせる、という点が繰り返し語られました。

## 5. 発表内容の詳細

### 5.1 不可抗力として取り上げた 4 つの事象

不可抗力の意味を調べると辞書には「神の行為」とあり、宗教の話にはしたくないので、自分たちが経験して、聞き手も共感できる大きな出来事を選んだと説明されました。

1. Spectre Meltdown：地球上のすべての CPU が、秘密情報を読み取られる脆弱性にさらされた。
2. 新型コロナウイルス：ウイルスが世界的な流行となり、暮らしも働き方も変わった。
3. サードパーティの更新：数百万台の Windows 端末が停止し、Fortune 500 の 25% に影響し、数十億ドルの損失になった。
4. 中東の紛争：戦争が、信頼を置いている技術に近づいた。

### 5.2 障害時のコミュニケーションの 5 つの柱

障害が世界規模でも、単一リージョンの 1 サービスでも、お客様への伝え方は同じ 5 つの柱に基づくと説明されました。

| 柱 | 内容 |
| --- | --- |
| 速さ | 「自分の環境の問題か、Azure の障害か」を、すぐに伝える。お客様が最初の 1〜2 時間を環境の調査に費やし、後から Azure の障害だったと知る事態を避けたい。AI を使った自動の仕組みに投資しており、通常 5〜10 分でコミュニケーションを出せる。人が起きて顔を洗い、状況を把握して、ツールで文章を書く場合より大幅に速い。 |
| 正確さ・粒度 | 「East US 2 の一部の仮想マシン」では役に立たない（リージョン名の綴りは音声認識の都合で確定できません）。1,000 台の仮想マシンのどれが影響を受けるのかを知りたい。現在は 60〜70% の連絡で、影響を受けるリソースを具体的に示せる。確信がなくても、影響の可能性があるリソースと、正常に見えるリソースを分けて伝える。 |
| 見つけやすさ | お客様がポータルで障害を探すのではなく、通知が届く形（プッシュ）にする。Azure Service Health のアラートを設定すると、最後の通知経路を制御できる。開発・テスト用サブスクリプションなら配布リストにメール、本番なら ServiceNow、PagerDuty、OpsGenie にチケットを起票、特定のアプリなら CIO に SMS、といった設定ができる。 |
| 一貫性 | Azure には 200〜300 のサービスがあり、動作が揃わないことがある。仮想マシンでも Redis でも SQL でも、障害情報の見え方を揃えたい。データセンターや DNS のように複数サービスに及ぶ問題では特に重要。現状は、状況の説明は得意でも、サービス間の違いの突き合わせはシステムが不得意だと述べている。Microsoft 365、Power Platform、Azure を組み合わせて使うお客様にとって、別会社の製品のように見えることがあるため、その溝を埋めようとしている。 |
| 透明性 | 障害の最中は「分かっていること」と「分かっていないこと」を伝える。障害後は、振り返りと完全な調査の結果をすべて説明する。事実を隠さず、細部にこそ学びがあるので、細部を省かない。 |

透明性の取り組みとして、Azure Incident Retrospective Series を立ち上げたと説明されています。大きな障害の後、影響を受けたお客様全員を招いてライブ配信を行い、責任を持つ担当の副社長に、何が起きたか、どう対応したか、何に満足し何に満足していないか、何を学び、どう改善するかを聞く形式です。社内の役員が、この会話を LinkedIn に再投稿し、「多くの会社は障害を隠す。私たちは YouTube で公開する」と書いたことも紹介されました。

### 5.3 障害の考え方：変更が最大の原因、そして層と穴

Azure、Microsoft 365 などの多数のサービスにまたがって原則をそろえるのは難しいものの、全員が合意できる抽象度として、次の 3 点があると説明されました。

1. **業界で障害の原因の第 1 位は変更。** セキュリティの維持や最新機能の提供のために変更は続けなければならない（そうしなければ DVD が郵送されるのを待つようなものだ、という例え）。そのため、変更は段階的に展開し、世界中に一度に反映することはしない。一度に反映してしまった場合は、事後検証して学びをお客様に共有する。
2. サービスは、悪い変更が入っても耐えられる設計にする。ロールバックか前方修正のあいだ、サービス自体が持ちこたえられるようにする。
3. それでも耐えられない場合は、影響を小さくする。Azure の障害の大半で、影響を受けるサブスクリプション数は 10 や 20 といった桁で、小さいと述べている（音声認識の都合で、桁の表現は確定できません）。変更をゆっくり導入するためです。

次に、根本原因という考え方への注意が語られました。システムは複数の層でできていて、どの層にも欠陥（穴）がある。何か悪いことが起きると、人は自分が最もよく知る層を選び、1 つの穴を掘り下げ、なぜなぜ分析（5 whys）を繰り返し、「原因は 4 行目のセミコロンでした」と結論づけてしまう。ほかの層や穴は、慣れていないために無視される。実際はもっと複雑だというのが主張です。

Sammy は、この図が心に響いた体験を語っています。出張先のホテルでシャツにアイロンをかけながらニュースを見ていると、米国の悲劇について、警察の対応の速さ、銃規制、心理士が早く気づけなかったこと、ビデオゲーム、親など、出演者がそれぞれ自分の層の視点で原因を語っていたそうです。

障害の振り返りでもこの見方を使います。左側にある安全なデプロイや耐障害性の設計は Microsoft が足す層です。お客様も、層を足して穴を小さくできます。例として次が挙げられました。

- アクティブ-アクティブ構成
- 可用性ゾーンの利用
- テスト済みで実績のある BCDR（事業継続・災害復旧）
- アプリケーションの再試行ロジック（インターネットではパケットが失われるため）

David は、1 つの穴にズームしていくやり方を、「学ぶことがどんどん少ない対象について、どんどん多く学び、最後は何もないことのすべてを知る」という古い格言で批判しました。Microsoft にもなぜなぜ分析に価値を見出すチームがあるとしつつ、可能な限り多くの要因から学ぶ方針だと述べています。

### 5.4 障害の前：現状把握と改善

障害の前の段階として、まず現状の把握が挙げられました。

- Azure Essentials：どこから始めるか迷う場合の入口。
- Cloud Adoption Framework：ワークロードやチームをまたいで組織として整えるべきことの指針。
- Well-Architected Framework：特定のワークロードやアプリケーションを、コスト最適化、セキュリティ、信頼性などの観点で見る。信頼性については、評価（アセスメント）で質問に答えると、不足している点の推奨が得られる。
- Azure Advisor：リソース単位（仮想マシンなど）の推奨。バックアップは有効か、可用性ゾーンに置くべきか、など。

現状を把握したら、改善に進みます。製品ごとの説明は 1 時間かかるので、他のセッションに任せるとしたうえで、次の点が述べられました。

- 可用性ゾーン：アクティブ-アクティブ構成の 2 つを、電源、ネットワーク、冷却が完全に独立した別のデータセンターに置ける。ただし、米国西海岸で複数の可用性ゾーンに及ぶ大規模停電があったため、本当に重要なら複数リージョンを検討すべきと述べている。「East US が自社のリージョンで、そこにしか置かない」という顧客の発言を「怖い」と評しました。

### 5.5 障害の前：監視と検証

状況の把握に使うサービスとして、次が挙げられました。

- Azure Service Health アラート：Azure が把握している障害や既知の問題の通知。
- Azure Resource Health：重要なリソースについて、細かい変化まで知らせる。
- Resource Graph、スケジュールされたイベント：仮想マシン内に「15 分後にメンテナンスで停止する」という通知を出す。アプリケーションが機能を縮退させたり、その仮想マシンを負荷分散から外したりするのに使える。
- Azure Monitor のヘルスモデル：最近一般提供（GA）になった。監視シグナルのリアルタイム情報と、アプリケーションの依存関係を組み合わせる。「X が壊れているなら Y も壊れているはず」という関係を組み込み、単なる情報ではなく洞察を得られる。例えば、ゾーンをまたいで構成済みで他のゾーンが正常なら、1 台の仮想マシンの停止を通知する意味は薄く、そうした生の情報に文脈を与える。
- Azure MCP サーバー：AI アシスタントと Azure 内の運用データをつなぐ橋渡し。エンジニアがログを読んで組み立てる代わりに、Azure MCP を使う AI エージェントに「ここ数時間の可用性と最近の変更を調べて、推奨をまとめて」と依頼できる。

Chaos Studio は、理論を実践に移すためのものとして別に説明されました。「ゾーンが落ちても耐えられると思う」と「耐えられると知っている」は違います。カオスエンジニアリングやフォールト注入というと、本番環境でランダムに何かを落とす様子を連想しがちですが、本番で行う必要はないと述べています。環境の正確な複製を作り、意図的に壊して反応を見ることもできます。「午前 3 時の不意打ちより、チーム全員が待機している午後 3 時に壊れるほうがよい」という説明です。

最近、Chaos Studio Workspaces で大きく進化したとのことです。以前は、リソースと障害を選び、タイムラインに手作業で組み立てる必要がありました。いまは対象環境を指定し、用意されたシナリオ（例：DNS 障害が起きたらどうなるか）を選んで実行できます。さらに細かく指定したい場合は、シナリオデザイナーで、アプリケーションに与える痛みを細かく設計できます。翌日に Azure Chaos Studio のセッションがあると案内されました。Microsoft 社内でも Chaos Studio を多用しています。

### 5.6 Project Dial Tone

最悪の事態を想定した取り組みとして、Project Dial Tone が説明されました。名前の由来は、電話の受話器を上げると必ず聞こえる発信音です（David の 18 歳の息子は意味を知らなかった、という笑い話つき）。この取り組みは大きく 3 つのことをします。

- Azure の主要な構成要素が常に動いている状態を保つ。ときには別の基盤を使う（Azure の障害を緩和するのに Azure を使うため）。
- ジャストインタイムアクセスや、人が協力する手段が使える状態を保つ。
- コミュニケーションが使える状態を保つ。

具体例が 2 つ挙がりました。

1. Azure の DNS はすべて Windows 上にあり、拡張性も十分で問題なく動いている。しかし、Windows のゼロデイや脅威があると DNS 全体が脆弱になるため、Linux 上にバックアップを持っている。
2. 障害時、世界中のエンジニアは Teams で集まり、ジャストインタイムアクセスを取りながら緩和を進める。Teams が落ちると非常に難しいことが実際にあったため、バックアップとして別の会議ツール（WebEx と述べている）を用意している。

Azure を最初から作り直す必要が生じ、通常の Azure のツールが使えない場合に、Dial Tone を使います。費用が高く、取り込むには大きな作業が必要なので、気軽には使いません。北欧の国の貯蔵庫に保管された種子のようなものだとたとえ、「最悪の場合に出すもの」と位置づけています。

### 5.7 障害の最中：3 つの方針

前回の Ignite では 1 時間かけて話した内容を、短くまとめて説明されました。

**1. 情報の民主化。** 拡張しやすいエンドポイントを用意し、人ではなくシステムが情報を取り込めるようにします。社内外で「真実の源」を 1 つにします。サポート担当に電話しても、担当のアカウント担当者に聞いても、役員とゴルフをしながら尋ねても、答えは同じでなければならないという考えです。若い頃に親や恋人へ違う版の話をして、うまくいかなかった経験を例にしています。

**2. 分かっていることを伝える（分かっていないことも含む）。** 例えば「データセンターは調べ済み、ストレージも調べ済み、いまは WAN の問題を調べている」という具合です。お客様を同じ道のりに連れていけば、パニックではなく、情報を受け取る行動になります。以前の Microsoft には、「復旧見込み（ETA）は出すな、間違えたら恥ずかしい」という文化がありましたが、いまは変わりました。何らかの見込みがあれば「約 3 時間後と考えています」と伝えます。そうすればお客様は、その日は帰る、3 時間待つ、フェイルアウトする、残る、といった判断ができるからです。Microsoft としてフェイルアウトを勧めることはしないと述べています（過去にはあったが、すべきことではない）。10 分の停止に耐えられないお客様もいれば、10 時間は耐えられても数日は無理というお客様もいます。判断に十分な文脈を提供するのが目的です。

先週に起きた出来事が引き合いに出されました。Outlook の障害が 24 時間続き、金曜 13 日には連邦航空局が航空機を地上待機にし、みんなが点をつなぎ合わせて「陰謀だ、攻撃されている」と考えた、と述べています。情報が出ない空白は影響を生むという例です。なお、ここで触れられた Outlook や Exchange の障害については、最終のインシデント後レビューが出る前なので、この場では振り返りをしないとも述べています。

**3. お客様が取れる行動。** 影響を受けたお客様は、情報を受け取って行動するか、サポートに連絡するか、右往左往するかです。サポートに連絡すべきなのは、例えば Azure Site Recovery のフェイルオーバーで支援が必要なときです。一方、「East US の仮想マシンが落ちていると言いましたね。はい、落ちています」という連絡は、サポート担当が Service Health にある情報を伝える以外にできることがなく、勧められないと述べています。

### 5.8 障害の後：学ぶ組織になるために避けること

David は、善意でも的外れになりやすいやり方として、次の 6 つを避けるよう説明しました。Satya が基調講演で、障害から学びたいと述べたことにも触れています。復旧したことより、それをさらなる耐障害性に生かすことが重要という考えです。

1. **根本原因という発想。** 犯人と凶器を見つけて帰る推理ゲームではなく、インシデント対応やアーキテクチャの改善に使える 10 個、20 個、30 個の学びを探す。Microsoft 社内では、根本原因という言葉を使った人に「根本原因の瓶に 1 ドル入れて」と言うことがある。
2. **ヒューマンエラーという枠組み。** 人は必ず間違える。人が間違えないことを前提にするシステムは脆弱だ。担当者が予期しない操作をしたなら、システムが正しい情報や安全装置を与えなかったという信号になる。
3. **キーボードの前の人を責めること。** 「4 行目のセミコロンを書いた人や、データセンターで違うブレーカーを落とした人を解雇したか」と聞かれることがあるが、答えは「していない」。レジリエンスエンジニアリングを学んだ人は、解雇で信頼性は上がらないと知っている。エンジニアと、特にその上長が「問題が起きた、みんなで直そう」と手を挙げられるように、責任追及をしない振り返りの文化が要る。インセンティブが歪むと、問題が隠される。
4. **「だから言っただろう」と言うこと。** 共有責任モデルの中で、お客様とパートナーにも役割がある。インシデント後レビューでは、Microsoft が学んだことに加えて、お客様が学べることも書く。例えば、可用性ゾーンで設計していたお客様は、影響が 1 つのゾーンに限られたため、止まらなかった。これは、CIO に高可用性や災害復旧の予算を求めるための材料になる。お金を得ようとしているのではなく、障害から一緒に学ぶためだと述べています。
5. **同じ障害は二度と起きないと言うこと。** 似た障害でも、裏の失敗モードがまったく違うことがある。修正に、再設計が必要で 1〜2 か月かかることもある。翌週に再発したら、それも透明に伝える。この点は、Microsoft の営業担当には難しい点だと述べている。
6. **完璧な物語を語ろうとすること。** 障害の話を「昔々」から「めでたしめでたし」で終わらせたくなる。しかし実際には、副社長との対話で「どう直すかは分からない。作業仮説が 2〜3 ある」「直し方に性能面のトレードオフがあり、まだ決めていない」と話すことがある。そうした曖昧さをそのまま語る。3 語で答えを出したくなるが、それは役に立たない。

### 5.9 障害の後の実例：Azure Front Door

自分たちが原因で、自分たちで直せる障害の例として、Azure Front Door が取り上げられました。昨年 10 月に大きな障害が 2 回あり（10 月上旬と下旬）、10 月 29 日の障害は 8 時間に及びました。Azure Front Door は、Microsoft の自社ツール、Azure ポータル、Microsoft 365、多くのお客様とパートナーが依存しているため、影響が大きい障害でした。

原因は、お客様が 2 種類のコントロールプレーンのバージョンを使い、特定の順序で操作することで、破損したメタデータがシステムに入り込んだことです。それが世界中の接続拠点（POP）に配布されました。8 時間より影響が大きかったのは、障害の後、再発を防ぐため、お客様のコントロールプレーンの変更と構成変更が数週間制限されたことです。ファイアウォール規則などを変更したいお客様は多く、数週間変更できないのは大きな痛みでした。

これに対して、定期的な連絡、インシデント後レビュー、ネットワーク担当の副社長へのライブ配信でのインタビューに加えて、「それでも足りない」と判断し、何が問題だったのかと、Azure Front Door を再設計する舞台裏を伝えるブログ連載を追加で書きました。構成変更の扱い、壊れないことを確認するテスト、システムの各部分をどう分離するかといった内容は、ここでは説明しきれないとして、QR コードからブログを読むよう勧めています。

### 5.10 事例 1：Spectre Meltdown

Microsoft と Azure の外側で起きた影響の 1 つ目です。2017 年に、Google Project Zero（GPZ）から連絡がありました。GPZ はシステムの欠陥を見つけ、所有者に「90 日で直さなければ公開する」と伝える方針をとっています。業界全体を安全にし、行動を促すので健全な仕組みだと評価しています。

CPU は、これから実行しそうな処理を先に準備しておき、その処理が来れば高速に実行し、来なければ捨てます。これが性能向上の仕組みです。GPZ の研究者は、メモリに保持された内容を読み取る方法を見つけました。秘密情報も含まれます。すべての CPU がその設計だったため、Intel、ARM、AMD など、世界のマイクロプロセッサのメーカーに連絡が行きました。世界中のすべての CPU が秘密を読み取られる可能性があり、国家レベルの攻撃者もいるため、90 日では足りず、事態は、ホワイトハウスが GPZ と関係者に箝口令を敷くほどにエスカレートしたと語られています。

関係したのは Microsoft、Google、AWS、Intel、AMD など少数の会社で、さらにその中で複雑さを理解していた人はごくわずかでした。各社はそれぞれ異なる方法で緩和を進め、全体像が見えるまで数か月かかり、チップ製造元がマイクロコード修正に取り組む間に、各社が自分たちの側で緩和を始めました。

Azure での対応の順序は次のとおりです。

1. 最初に、ホスト（聞き取った語は確定できません）にパッチを適用した。
2. 次に PaaS サービスにパッチを適用した。ワーカーロールのインスタンスなので、お客様への影響はほぼなかった。
3. 12 月の終わりに、2018 年 1 月末を公開予定日として調整した。残るのは IaaS で、お客様に仮想マシンを再デプロイしてもらう必要があった。再デプロイすれば、パッチ済みのホスト上で動くからである。
4. お客様に「30 日以内に仮想マシンを再デプロイしてください。そうしなければこちらで行います」と連絡した。ただし、クリスマスの時期に通知を読む人は少なく、再デプロイが進まなかった。

ある人が、Azure の仮想マシンと AWS のインスタンスを再起動または再デプロイし、両方で CPU の挙動が違うことに気づきました。「ゼロデイの脅威でもない限り、なぜ Azure と AWS で CPU の挙動が違うのか」とツイートし、対応の痕跡が残り始めました。指令室で見ていた Microsoft は緊張しましたが、方針を変えませんでした。他の人も気づき始め、Geek Wire が記事にし、1 月 4 日の朝には CNBC も報じていました。Google からは「話が手に負えなくなっている。今日公開する。準備してほしい」と連絡が来ました。

未再デプロイの IaaS 仮想マシンが数十万台残り、概念実証が公開される状況で、数百万の顧客とビジネスが Azure に依存していました。ここで、**セキュリティを信頼性より優先する**という一般原則に従い、お客様のインスタンスを積極的に再デプロイしました。その際も、可用性ゾーンを尊重して同時に更新せず、リージョンペアも尊重して同時に更新しませんでした。数時間かかる事後検証を 3 分に圧縮した話だと断っています。

### 5.11 事例 2：新型コロナウイルス

David が担当した事例です。世界が一気にデジタル化し、クラウドの需要が急増しました。画面には Teams の例があり、1 日の通話が 9 億分から 40 億分超へと、1〜2 か月で増えたと説明されています。企業全体や学区全体がリモートに移り、Xbox やゲームの需要も同時に急増しました。一方、データセンター機器の供給は、東南アジアや中国の工場が止まったことで減りました。需要の増加と供給の減少が重なったのです。

対応は次のとおりです。

- **サーバー増設**：世界中の Azure のデータセンターとリージョンで、24 時間 3 交代制（8 時間 × 3）で増設した。深夜 3〜5 時にもハードディスクを入れる必要があった。技術者は 6 フィート（約 1.8 m）の距離を保ち、消毒の手順も追加された。
- **効率化**：Teams の例として、入力中を示す表示（点々）を毎秒確認する必要があるか、名前検索を 1 文字ごとに実行する必要があるか、数秒待ってから検索すればよいのではないか、といった見直しを行い、機能を段階的に縮退させて容量を確保した。
- **優先順位**：既存のお客様を新規のお客様より優先すると公に表明した。クラウド環境は自動スケールで伸縮するため、既存のワークロードに余裕を残す必要があった。容量が逼迫した場合の優先順位も公開し、新型コロナ対応、緊急対応機関、病院を優先した。小売業のお客様がオンラインの大型セールのために拡張したくてもできず、不満が出たが、優先順位を公に示したことには意味があった。

学びとして、逆境の中での最適化が挙げられ、SKU（仮想マシンの種類）とリージョンの代替性が重要だったと述べています。例えば、Teams に AMD のコアを割り当てると言っても、すぐには使えず、アーキテクチャの見直しが必要でした。この経験はクラウドの運用を大きく変えたと述べています。

画面の「クラウド需要が 775% 増加」という引用について、Sammy が実体験を語りました。容量の逼迫で、1% 未満のお客様が割り当て失敗に直面したため、状況を公開するブログを出すことにしました。データを集める中で「イタリアの Teams の利用が短期間に 775% 増えた」というデータがあったのですが、「Teams」が編集で抜け、「イタリア」も落ち、「クラウドサービスが 775% 成長した」と公開されてしまいました。Azure が 775% 成長したと受け取られ、株式市場が動き、「Azure は 800% 成長したのか」という問い合わせも来ました。データセンターが 800% 余っているわけではありません。

Sammy は、役員との通話では、キーボードの前の人として解雇されると思っていたそうです。しかし役員は、全員が疲れ果てていたことと、見落としは自分だけでなく複数のレビューの連鎖を通り抜けたことを先に指摘しました。訂正は、元の文を消さず、取り消し線を引いて下に訂正を書く形にしました。これは透明性を保つやり方で、担当者を解雇しなかったので、数年後にこうして話せている、と述べています。

### 5.12 事例 3：CrowdStrike

CrowdStrike は、エンドポイントを保護する会社で、特に Windows のセキュリティに強みがあり、クラウド上で生まれた会社という利点があると紹介されました。製品の Falcon エージェントは、Windows で多数のプロセスとアプリケーションが互いに通信する経路（トンネル）を監視し、脅威を探して対応します。OS の深い位置まで入り込めるので、脅威の検出と緩和には向いていますが、問題が起きるとアプリケーションだけでなく OS も不安定にします。

この仕組みは 2 月に出荷されて問題がなく、3 月に使われ、4 月にも更新があって問題はありませんでした。7 月 18 日（世界の場所によっては 19 日の 04 UTC）に Windows 向けの更新が出されました。公開されていたのは 78 分間で、その間に 850 万台超の Windows 端末が更新を取り込んでクラッシュし、復帰できなくなりました。物理マシン、ホスト、ゲストが含まれます。Azure では、お客様の仮想マシン 75 万台が該当しました。Azure も Microsoft も悪くありませんが、航空機は飛べず、空港は閉鎖され、小売も止まり、Fortune 500 の 25% が重大な影響を受け、IT の問題が社会の問題になりました。

Azure では、お客様を助けたいが、プライバシーに厳格で、仮想マシンの中に勝手に入って助けることはしない、という方針があります。そこで、許可を得る「許可証」（デジタルの同意）を作って配布しました。急いでいたため、安全なデプロイの手順は省略しました。お客様が署名した後に、仮想マシンの復旧を試みました。通常の障害は数時間から数日ですが、このときは約 10 日かかり、75 万台のうち相当な割合を復旧しました（復旧した台数の割合は聞き取り不明瞭です）。短時間の 1 回の更新が大きな影響を及ぼした例として紹介されました。

### 5.13 事例 4：中東の紛争

Sammy は、普段は戦争の悲惨さと日々の仕事を切り離せるが、このときは気持ちが仕事に入り込んだと語りました。競合（発話では「いとこ」）のデータセンターがドローン攻撃を受け、負傷者はいませんでしたが、復旧できないデータ損失が発表されました。さらに、米国のテクノロジー大手が、イランをめぐる紛争で正当な標的と位置づけられました。準備と対応が必要でした。

お客様側の動きとして、次が語られています。

- オンプレミスから Azure へできるだけ早く移りたいという需要が増えた。Azure のバックボーンに載れば、グローバルに動かしやすいため。Microsoft は Data Box を送って移行を助けた。
- リージョンの外へ移行するお客様がいて、60 ペタバイトの例もあった。他リージョンに容量があるか、ネットワークが耐えられるかを確認する必要があった。
- 主権要件を持つお客様は、それに合わせて回避策を取る必要があり、非常に難しかった。

ネットワークについて、Microsoft のネットワークは世界規模で、陸上と海底に敷設されています。その 1 つがホルムズ海峡で、9 か月前には誰も知らなかったが、いまや最も重要なインフラの 1 つになったと述べています。海峡が戦闘地帯になり、ケーブルが影響を受けても大丈夫か。「大丈夫だと思う」と答えましたが、実際には試していませんでした。短期間で次の演習を行ったと説明されています。

1. 夜間の負荷が低い時間帯に、海峡を通るすべてのトラフィックを迂回させ、問題がないことを確認した。
2. 次に、実際のお客様のトラフィックがある状態で同じことを行った。すべてを抜いて、冗長経路に載せ、縮退運転（限定的な動作）にならないことと、Azure Site Recovery のフェイルオーバーやトラフィックを引き続き処理できることを確認した。

ほとんどのお客様は影響を受けなかったはずですが、Microsoft にとって、ネットワークで過去最大級の BCDR 演習の 1 つだったと述べています。

### 5.14 障害の前の備え（再整理）とまとめの言葉

最後に、障害の前の備えを抽象度を上げて見直しました。Azure Site Recovery、GRS、Azure Backup といった具体的なサービスもありますが、助言として一段上の見方も大切だと述べています。

- CPU の脆弱性とパッチ適用に対しては、複数ゾーンに配置する。
- 世界的な流行に対しては、SKU やアプリケーションの代替性を持つ。
- サードパーティの更新に対しては、一度にすべてを取り込むことが別のリスクになる点を認識する。
- BCDR 環境は、理論だけでなく実際に動くことを試験で確認する。

Well-Architected Framework は、単一障害点やリスクに対する哲学的な指針になると述べています。Azure に 10 年以上いる経験から、ブラックスワン（想定外の大事件）は続いており、今後も増えると語りました。それを防ぐことはできず、障害や混乱は避けられないが、影響を避けられないわけではない、と結んでいます。

## 7. 注意点・発表者の気付き

- 障害の原因の第 1 位は変更です。Azure は変更を段階的に展開しますが、一度に世界へ反映してしまうこともあり、その場合は事後検証して学びを共有すると述べています。
- 1 つの原因にこだわらないこと。人を責めない、同じ障害は二度と起きないと言い切らない、完璧な物語を語らない、といった点が、学ぶ組織の条件として語られました。
- 重要なワークロードは、可用性ゾーンだけでなく複数リージョンを検討します。西海岸の大規模停電で複数のゾーンに影響が出た例が挙げられました。
- 障害時にサポートへ連絡するのは、Azure Site Recovery のフェイルオーバーの支援のような、サポートにしかできないことがあるときです。障害の事実確認だけなら Service Health で足ります。
- セキュリティと信頼性が衝突したときは、セキュリティを優先します（Spectre Meltdown の再デプロイの判断）。
- 通知は、年末年始のような時期には読まれにくく、30 日の猶予を設けても再デプロイが進まなかった、という実体験が語られました。
- データの編集ミスで「Azure が 775% 成長した」と公開されてしまった例では、訂正を、取り消し線と下の訂正文で示し、担当者を責めませんでした。
- 10 や 20 といった影響サブスクリプション数の桁と、復旧した仮想マシンの割合は、音声から確定できないため、本文でもそのように注記しています。

## 8. 利用者にとっての利点

発表で語られたお客様向けの内容を整理します。

- 障害の通知は、Azure Service Health のアラートで、メール、チケット管理（ServiceNow、PagerDuty、OpsGenie）、SMS などへ振り分けて受け取れる。探しに行く必要がない。
- 障害の影響を受けるリソースを具体的に知らされる割合が、現在 60〜70% になっている。
- 障害の一報は、AI を使った仕組みにより通常 5〜10 分で出る。
- 復旧見込みや、分かっていること・分かっていないことが共有され、お客様が継続か切り替えかを自分で判断できる。
- 重大な障害の後は、インシデント後レビュー、ライブ配信の振り返り、必要に応じたブログ連載で詳細が公開される。
- 可用性ゾーンで設計していたお客様は、影響が 1 つのゾーンに限られた障害で止まらなかった。
- Chaos Studio（Workspaces、シナリオデザイナー）で、本番の複製環境を使って障害を試験できる。
- Azure Monitor のヘルスモデルや Azure MCP サーバーで、生の監視情報から洞察を得られる。

## 9. まとめ

このセッションの要点は次の 4 つです。

1. 障害の最中の沈黙は信頼を壊します。速さ、正確さ、見つけやすさ、一貫性、透明性の 5 つの柱で、分かっていることと分かっていないことを伝えます。
2. 障害は 1 つの根本原因ではなく、複数の層にある穴が重なって起きます。Microsoft は層を足し、お客様も、可用性ゾーン、複数リージョン、検証済みの BCDR、再試行ロジックで層を足し、穴を小さくできます。
3. 障害から学ぶ組織は、根本原因、ヒューマンエラー、個人への責任追及、「だから言っただろう」、再発しないという約束、完璧な物語を避けます。
4. Spectre Meltdown、新型コロナ、CrowdStrike、中東の紛争という不可抗力の事象は、複数ゾーンへの配置、SKU やアプリケーションの代替性、一度にすべてを取り込むリスクへの意識、BCDR の実地検証の重要さを示しました。発表者は、ブラックスワンは防げないが、影響は小さくできると結んでいます。
