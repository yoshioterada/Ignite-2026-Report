# THRSP1122 Scale Azure VM storage and control costs with Everpure Cloud

## 1. はじめに

このセッションは、Azure 上の仮想マシン（VM）などで使うブロックストレージのコストを、Everpure と Microsoft が共同で提供する Azure ネイティブサービス「Everpure Cloud Azure Native」で下げる方法を紹介する発表です。Everpure は、発表中の説明で、以前は Pure Storage という名前だった会社です。

発表は、コストの課題、両社の提携と Azure Native Integrations プログラムの説明、サービスの機能（シンプロビジョニングとデータ削減）、Azure ポータルでの操作のビデオデモ、Azure Storage Center での可視化、そして Copilot Studio で作ったエージェントによる可観測性のデモで進みます。**ブロックストレージのコストは、データ削減とシンプロビジョニングの組み合わせで、平均的な 5 対 1 の削減率から少なくとも 40% 下がる**というのが、発表者の示した数字です。

## 5. 発表内容の詳細

### 5.1 提携と Azure Native Integrations プログラム

Mamta は、Everpure と Microsoft は数年前に手を組み、Azure の顧客がさまざまなストレージにまたがってワークロードを構築できる一連のソリューションを作ってきた、と説明しました。提供の種類として、Azure ネイティブのもの、ブロックストレージ向けの Everpure Cloud Dedicated、Azure Local や Microsoft のワークロード向けの高性能な Flash Array（Everpure の主力製品）が挙げられています。音声認識の都合で、このリストの一部の名称（Azure Cloud、Azure「Redshift」など）は書き起こしが不明瞭で、確定できません。

「ネイティブ」とは、Microsoft の Azure Native Integrations プログラムに基づくものです。これは、各分野の市場リーダーのみを対象にした選抜制のプログラムで、完全マネージドのサービスとして顧客に提供されます。特徴は次のとおりです。

- Azure Resource Manager（ARM）による、統合されたオンボーディング体験
- Azure Marketplace による、統一された取引（購入）の仕組み
- Azure ポータルでの、見つけやすさと取引のしやすさ
- SDK、CLI、PowerShell など、すべてのクライアントインターフェースで同じ体験
- Microsoft から Everpure へ、認証層で繰り返し入力しなくて済む、途切れのない体験
- パートナー向けの深い統合（例として VNet インジェクション）

Mamta は、これは Everpure との共同開発プログラムでもあると述べています。

### 5.2 Everpure Cloud Azure Native とは

Cody は、これを「Everpure Cloud Azure Native」と紹介しました。オンプレミスのデータセンター向けに作ったエンタープライズストレージのソフトウェアを、Azure のリソースを活用する形に作り直し、Azure ポータルに、Azure ネイティブサービスの統合プロジェクトを通じて組み込んだものです。ソフトウェアには次の機能が含まれます。

- 即時のスナップショットとリストア
- iSCSI と NVMe TCP のデータパス
- レプリケーション
- オフロードエンジン

Cody は長年パートナー向けのエンジニアリング（他社製品への統合）をしてきた経験から、利用者が日常的に使うポータルや体験から離れずに、Everpure の技術を持ち込むことを重視していると述べています。ネイティブ統合により、Azure のアクセス制御のセキュリティの考え方に沿った操作（「ARM 化」と表現）が可能になるという説明です。

これは、自分のアカウントに単に導入して手で調整するソフトウェアではなく、サービス駆動のアプローチであり、ほかのサービスと連携できます。対応先として次が挙げられました。

- Azure Virtual Machines
- Azure VMware Solution
- Azure Red Hat OpenShift
- AKS
- ほかの IaaS 全般

最近の統合先は、Azure Red Hat OpenShift と AKS です。オンプレミスのアプリをクラウドに移すとき、Azure VM への単純な移行（リフト＆シフト）ではなく、Kubernetes を目指す顧客が増えているという実感が語られました。KubeVirt（Kubernetes で従来型の VM を管理する仕組み）は、その道筋になります。Azure Red Hat OpenShift と AKS は、どちらも KubeVirt をサポートしています。オープンソース層（KubeVirt と Kubernetes）に載せると移植性が高く、CPU とコンピュートのシンプロビジョニングによる適正化も可能になる、というのが Cody の説明です。Azure Red Hat OpenShift は、直接の仮想化サポートをプレビューで近く提供すると、前日に発表された、との発言もありました。ベアメタルの上にハイパーバイザーを載せ、アプリのサイズを適正化できます。

### 5.3 コスト最適化の仕組み

**柔軟な性能と容量（シンプロビジョニング）。** 提供したサイズではなく、実際に使った分に対して支払います。あるボリュームが IOPS や帯域を使っていなければ、別のボリュームがそれを使えます。管理者が「2 TB のボリュームが必要」と言っても、実際に必要になるのは半年後かもしれません。従来のネイティブなブロックストレージでは、使っていなくても全量に支払う必要があります。容量だけでなく性能もシンプロビジョニングされ、これは FinOps の一部としての柔軟性になる、と述べています。数値の例は画面に出ていましたが、「もっと大きくもできる」とだけ語られ、具体値は音声では確認できません。

**データ削減。** 製品の中核技術です。Everpure（旧 Pure Storage）は、フラッシュを安くするという考えで事業を築き、圧縮、重複排除、パターン除去をデータパスに組み込みました。Azure 内でも同じ考えが当てはまります。

- 割り当て（プロビジョニング）した量ではなく、書き込んだ量だけに支払う
- 書き込んだデータを、さらに小さくする
- 15,000 の顧客（データセンターとクラウド）全体の平均削減率は、約 5 対 1
- クラウドの顧客に限ると、8 対 1 から 9 対 1 に近い
- 平均の 5 対 1 を基準に、ブロックストレージのコストを少なくとも 40% 削減できる
- これにシンプロビジョニングと柔軟な性能の節約が上乗せされる

### 5.4 サービスの使い方の流れ

Cody は、完全マネージドで Azure に統合されたサービスだと強調しました。流れは次のとおりです。

1. サービスに登録する
2. ストレージプール（容量と性能を割り当てる単位）をデプロイする
3. プールを、利用するリソース（Azure VMware Solution、Azure VM、Kubernetes など）に接続する
4. プールから必要な数のボリュームを作る。プール全体で重複排除、圧縮、パターン除去が行われる

Mamta は、Azure Storage Center は新しく用意された場だと説明しました。Azure のファーストパーティのサービス（Azure ネイティブのサービス）と、パートナー提供のサービスが同じ場所に並び、見つけやすくなります。顧客は KPI（主要性能指標）を監視し、サービスの状況をドリルダウンして確認できます。

### 6.1 Azure ポータルでのボリュームの作成とマウント

Cody が、クリックのタイミングを合わせながら説明しました。

1. ボリュームグループを作る。通常は特定のアプリケーション用にボリュームをまとめる。ボリュームグループは ARM のリソースで、ロールベースのアクセス制御を Azure のセキュリティ制御として直接設定できる。ポータルから操作でき、Microsoft のチームとともにリソースプロバイダーを作って実現した
2. ボリュームを作る。尋ねられるのは名前とサイズの 2 つだけ。サイズによらず、ボリュームは即時に作成される。縮小もできるため、テラバイトとギガバイトを打ち間違えた場合も救える
3. スナップショットを、即時に、またはスケジュールで作成できる
4. ボリュームグループには 1 つ以上のボリュームを追加でき、VM などにリソースとして割り当てる。Kubernetes の場合、プロビジョニングの流れは少し異なり、サービスと直接通信する CSI ドライバーが担当する
5. マウントはネットワークベースのストレージ（iSCSI または NVMe TCP）で行う。Azure VM 拡張機能が用意されており、ポータルが VM に自動でデプロイしてデータパスを設定する。iSCSI の推奨設定やタイムアウトの調整を利用者が行う必要はない。新しい推奨設定は拡張機能で展開できる
6. Linux か Windows かを問わず、ボリュームが自動でマウントされ、VM の内部で使える。デモでは VM 内部でマウントされた状態も映ったが、説明は省略された

Mamta は、このデモで示した Azure ポータルでの体験は、両チームが一緒に作った深いネイティブ体験だと述べました。深い統合により、データは顧客のプレーン（サブスクリプション）の外に出ず、信頼境界の内側に保たれる、という説明です。

### 6.2 Copilot Studio のエージェントと Pure One の MCP サーバー

背景として、クリック操作中心の運用（クリックオプス）から、LLM と対話して状況を把握する AI オプスに移りつつあると、Cody は述べています。Azure も Everpure も AI に投資しており、Everpure は自社の MCP サーバーを用意して、利用者が好きな LLM を選べるようにし、スキル、メトリクス、API を公開しているそうです。Copilot への組み込みは最近の取り組みです。

Pure One は、Everpure のストレージ製品群に対して、可観測性、傾向分析、容量管理、サポートチケットなどを提供する SaaS の管理基盤です。REST API に加え、クラウドベースの MCP サーバーがあり、Pure One を利用している顧客は何もデプロイせずに使えます。

1. Copilot Studio で、Pure One の MCP サーバーを使うエージェントを作る流れを見せる
2. Everpure の MCP サーバーを登録する。Azure Resource Management の MCP も追加する
3. エージェントに名前を付け、目的を絞る
4. エージェントに話しかける。よくある場面として「性能問題がある。何が起きていて、どこから来ているのか」を尋ねる
5. エージェントは、この質問の VM の Azure リソース情報を確認する。Everpure のデータ（性能データ、キューイングのメトリクス、SAN レイテンシ）を調べ、問題の所在を探る。SAN レイテンシは、データパス上でパケットがイニシエーターから戻ってくるまでの時間を指す

Cody は、可観測性の価値として、ボリュームがあり、これだけ割り当てて支払っている、というだけでなく、実際に何が使われているかが分かる点を挙げました。例として、容量、書き込み済み容量、データ削減の効き具合、ゼロのデータとそうでないデータ、ボリュームで実際に消費している IOPS が挙げられています。これらは MCP サーバーに入っており、Copilot に統合されています。エージェントの回答内容は、音声からは確認できません。

あわせて、Fusion の MCP サーバーも開発中で、すでに MCP サーバーとして利用可能と述べています。こちらはストレージオブジェクトの作成など、制御とコマンドのためのものです。両者を組み合わせる予定です。

## 7. 注意点・発表者の気付き

- 容量の割り当てと実使用の差は、従来のネイティブなブロックストレージでは全量に支払う原因になる。管理者が将来必要な量を先に確保しがちな点が、課題として挙げられました。
- 40% の削減は、5 対 1 を基準にしたもの。クラウドの顧客は 8 対 1〜9 対 1 に近いと述べられていますが、この数字が成り立つ条件の詳細には、発表では触れていません。
- ボリュームは縮小できるが、プロビジョニングの流れは、Kubernetes では CSI ドライバー経由で異なる。
- ハイブリッドの構成やユースケース、MCP サーバーの組み合わせは、今後の予定であり、現時点で提供済みとは語られていません（Fusion の MCP サーバーは提供済み）。
- Azure Red Hat OpenShift の直接仮想化サポートは、プレビューでの提供が近く始まる予定の段階です。

## 8. 利用者にとっての利点

- 割り当てた量でなく、書き込んだ量に応じて支払うため、過剰なプロビジョニングが減る
- データ削減により、クラウドでは 8 対 1〜9 対 1 に近い削減率。ブロックストレージのコストを少なくとも 40% 削減できると語られた
- 性能も、あるボリュームが使っていない分を別のボリュームが使える
- Azure ポータル、ARM、各種クライアントからの一貫した体験と、ロールベースのアクセス制御
- VM 拡張機能による、iSCSI や NVMe TCP の自動設定と、推奨設定の自動展開
- データは顧客のサブスクリプション内、信頼境界の内側に留まる
- Azure Marketplace での購入と、Azure ポータルでの発見
- Kubernetes（KubeVirt を含む）への移行経路でも、同じストレージを使える

顧客名や、具体的な導入事例は、発表では語られていません。

## 9. まとめ

発表者は、ストレージを、コスト最適化で見落とされやすい大きな領域と位置づけました。Everpure Cloud Azure Native は、Azure Native Integrations プログラムのもと、Azure ポータルと ARM に統合された完全マネージドのサービスです。シンプロビジョニングとデータ削減（平均 5 対 1、クラウドでは 8 対 1〜9 対 1 に近い）により、ブロックストレージのコストを少なくとも 40% 削減できると説明されました。

デモでは、ボリュームグループとボリュームの作成から、VM 拡張機能による自動マウントまでと、Copilot Studio のエージェントが Pure One の MCP サーバー経由で性能問題を調べる様子が紹介されました。Azure Storage Center では、パートナーのサービスをファーストパーティのサービスと並べて監視できます。最後に、無料トライアルへの案内と、ブースへの来訪が呼びかけられました。
