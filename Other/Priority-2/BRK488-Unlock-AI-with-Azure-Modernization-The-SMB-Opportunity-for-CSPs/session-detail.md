# BRK488 Unlock AI with Azure Modernization: The SMB Opportunity for CSPs

## 1. はじめに

このセッションは、中小企業（SMB）向けに Azure の移行・モダナイゼーションを手がけるパートナー（CSP を含む）に向けた発表です。会場は小規模で、発表者は「少人数なので距離の近い雰囲気で進めます」と最初に話しています。構成は「なぜ今なのか」「何を勧めるのか」「パートナーはどう進めるのか」の 3 部です。前半を Microsoft で Azure のアプリ・インフラ・データベースの市場展開を担当する Mayank が、後半をパートナー技術チームの Lakshmi Korada が話しました。

最初に押さえたい結論は 3 つあります。第 1 に、AI・セキュリティ・コストの 3 つの圧力が重なり、「何もしない」は選択肢ではなくなっていること。第 2 に、Azure Migrate と GitHub Copilot を統合したエージェント型のツール **Azure Catalyst** が発表されたこと。第 3 に、クラウド移行のコストを半分にすることを目指す「エージェント型モダナイゼーションのオファー」が示されたことです。

## 4. 発表者が伝えたいメッセージ

Mayank は、エージェント型モダナイゼーションをすでに始めている顧客が増えており、取り組まないパートナーは取り残されると述べています。理由は売上と利益に直結するためです。顧客側でも生産性や体験が向上します。

Lakshmi の側のメッセージは、パートナーが取り込めていない機会が大きいことです。移行は入口にすぎず、その先のモダナイゼーション、AI 向けのデータ整備、エージェント構築、マネージドサービスまで広げて考えるよう促しています。

## 5. 発表内容の詳細

### 5.1 SMB での AI エージェント導入の現状

Mayank はまず調査の数値を見せました。着目したのは「エージェントを導入している人」の割合で、AI の波が始まって 3 年目となる現在、SMB の 30〜40% がエージェントの試行や導入を進めているという内容です。試行が多く失敗も多いという見方もあるが、失敗を防ぐことこそ自分たちの機会だと述べています。パートナーのデータでも、顧客のエージェント型ツールやエージェントを使ったモダナイゼーションの量が増えており、今後も伸びる見込みだと説明しました。

### 5.2 モダナイゼーションを急ぐ 3 つの理由

**AI**：Mayank は、1 つのエージェントなら移行は不要だが、5 つ以上、10 以上、15 といった数のエージェントを作る規模ならプラットフォームとして考える必要がある、という言い方で説明しました。根拠は 2 つです。

- エージェントが使うデータの 70% は、Postgres や SQL などの業務データベースにあります。エージェントはクラウド上のサービスで動くことが多く、データと離れていると遅延が生じます。1 つなら影響は小さくても、数が増えると遅延の積み重ねがコスト（計算資源）とユーザー体験に響きます。
- 例として OpenAI の話がありました。OpenAI のバックエンド構築時に、Azure のランディングゾーン（プラットフォーム、アプリ、共有サービス、ID、ネットワーク、セキュリティをまとめた土台）に同居させなかった場合、ChatGPT の 1 クエリあたり約 0.1 秒処理が長くなった、という説明です。ChatGPT は 1 日に 1,000 万〜1,500 万クエリ（発表者の記憶による数値）あるため、積み上げると大きな差になります。小さな企業でも、規模が増えれば同じことが起きるという主張です。

移すとなれば、安全に、速く、壊さずに進める責任が自分たち全員にある、とも述べています。

**セキュリティ**：Microsoft では、すべてのサービスと製品に対して AI で攻撃を仕掛けて検証しており、基調講演で話に出た Project Perception（赤チームと青チームの取り組み。音声認識の都合で表記が確定できません）はその延長だと説明しました。Microsoft は自社製品にこの手法を適用して、AI で大幅にパッチ適用と改善、セキュリティ強化を進めてきたとのことです。AI を使って AI から身を守ることは、対策の一部にすぎないとも述べています。Project Perception の中には M-dash（音声認識の都合で表記が確定できません）というツールがあり、本日からパブリックプレビューになり、それまではプライベートプレビューでした。世界で 600〜700 の組織と協力し、スキャンを完了した 300〜400 組織の CIO・CTO から、自社のコードベースに未知の脆弱性が見つかったので支援がほしいと言われなかった例はない、という説明です。AI の脆弱性は誇張ではなく現実だと強調しています。

**コスト**：メモリやサーバーの価格が上がっており、クラウドのスケールメリットの方が有利だと説明しています。

### 5.3 エージェントを空港にたとえる考え方

Mayank は、エージェントを飛行機にたとえました。10 機を着陸させるのに、滑走路・空港・ゲート・建物を 10 組作る人はいません。1 つの空港を作ります。同じように、ランディングゾーンを 1 回作り、その上に組織の知識の層（インテリジェンス層。意味モデルを備えた信頼できる層）を 1 回作り、その上にエージェントを載せるのが望ましい構成だというわけです。

大企業はコンプライアンスや経営層の意思決定に時間がかかるため、SMB の方が速く動くと見込んでいる、とも話しました。この構築はパートナーにとって売上も利益も大きく、エージェント型ツールの利用が進むほど利益率は上がる、という位置づけです。

### 5.4 Azure Catalyst

過去 24 か月ほどの間に、2 つのツールが収れんしました。1 つは IT 資産の評価・発見・移行を担う Azure Migrate、もう 1 つはコードのモダナイゼーションエージェントである GitHub Copilot です。これらを統合したものが Azure Catalyst で、小さな企業から大きな企業まで、資産を素早く把握し、移行すべきものとモダナイズすべきものを提案し、実際のモダナイゼーションまで行います。質疑応答では、Azure Migrate は今後 Catalyst の一部になると説明されました。

### 5.5 エージェント型モダナイゼーションのオファー

デモの後、Mayank は「Azure Catalyst のように強力で簡単なツールでも、いきなり CIO や CTO に売り込むのは通用しない。説得力のあるきっかけと事業上の根拠が必要だ」と述べました。そこで今回発表されたのが、エージェント型モダナイゼーションのオファーです。スライドには、アセスメントにもとづいて50% のコスト削減を示す趣旨の記載があり、注記（アスタリスク）が付いています。

組織のコストをライセンス、運用、移行の 3 つに分けて説明しています。

| コストの種類 | 説明された内容 |
| --- | --- |
| ライセンス | クラウドでは消費量課金のためライセンス管理やソフトウェア資産管理が不要になる。「クラウドでは Microsoft にオンプレミスより多く払うことはない」という原則がある。基本は Azure Hybrid Benefit でオンプレミスの価格に合わせる。データベースでは SQL Hyperscale や Horizon DB（音声認識の都合で表記が確定できません）などライセンス費用のない製品があり、Postgres もライセンス費用がかからない。 |
| 運用 | 顧客がデータセンターやオンプレミスからクラウドへ消費を移すと、規模に応じて、初年度に 50% のクレジットを提供する。 |
| 移行 | Cloud Accelerate Factory、パートナーへの投資（ESIF）、エージェント型ツールで移行コストを下げる。 |

実績については、大企業と小規模事業者で検証し、稼働中の案件も確認したと述べています。すべての組織で達成できる約束はできないものの、50% を超えて削減できた例もあれば、20〜30% で落ち着いた例もあります。ただし 2%、3%、7% といった例はなく、すべて 2 桁の削減になっているという説明です。

### 5.6 顧客事例と Microsoft 社内の事例

- ビッグ 4 に数えられる世界最大級のコンサルティング会社が、約 9,000 の SQL コアで動く全社的な税務管理アプリを、2〜3 週間でモダナイズした。従来なら数百万ドル規模の費用がかかる作業だったという説明です。顧客名は伏せられており、大企業側が公表を望まないとも話しています。
- 世界最大級の保険会社が、400 のアプリケーションにアプリ単位で Catalyst を適用している。
- Teams：.NET 6 から .NET 8 へのコードベースのアップグレードが、数か月から数時間になった。Teams ほどの規模でできるなら、小規模な企業ではもっと容易なはずだ、と述べています。
- Xbox：Amanda Silver が率いた取り組みで、工数を 88% 削減できたと説明しています。発表者はむしろ定性的な声を重視し、GitHub 内の複数のエージェントがアプリごと、コードベースごとに移行計画を出し、担当者はレビューするだけで、人の手による作業や修正はほとんど要らなかったと紹介しました。

これらは Microsoft 社内で実際に使って作り込んだ（ドッグフーディングした）ものであり、他の 2 つの大手クラウドも同じ方向に進んでいるため、顧客はより簡単で、品質が高く、安い方を選ぶ、とも述べています。

### 5.7 「何もしない」を選ばせない／手つかずの資産

Microsoft の経営層で増えている言葉として、「何もしないは選択肢ではない」が紹介されました。AI への備えの規模、セキュリティと脆弱性の検査、コスト圧力が、今決断を迫っているという説明です。この会話は、エンジニアリングを理解した経営層が顧客と話すとうまくいくが、育成中の新しい営業担当だと同じ結果にならないことがあるので、会話の仕方が重要だとも述べました。

もう 1 つの主張は、アプリとデータベースが「手つかずの資産」だというものです。Exchange のメールボックスは 90% 以上がクラウドに移っているのに対し、SQL Server、Postgres、各種アプリは今も小さな部屋やデータセンターに残っています。エージェント型モダナイゼーションの技術と、セキュリティ・AI・コストの 3 つの条件が重なり、次に移る資産になるという見方です。

事例として、ドイツの大手自動車メーカー（発表者はビートルを作る会社と述べています）の話がありました。生産ラインを支えるアプリとデータベースは、CIO・CTO から「ミッションクリティカルなので移せない」と言われていた資産で、その環境に 2 桁の百万ドルを超える額を使っていました。そこで先ほどのオファーを示し、「今後 12 か月で請求額を半分、あるいは、ライセンス費用や運用費用についてはゼロにまで下げ、移行の一部を Microsoft が負担したらどうか」と提案すると、会話が始まった、という内容です。抵抗を感じる場面での切り出し方の例として紹介されました。

### 5.8 パートナーにとっての機会（Lakshmi）

Lakshmi は、SMB を扱うパートナーが会場にどれだけいるか手を挙げさせたうえで話しました。Forrester の Total Economic Impact 調査では、標準的な SMB 顧客として、約 125 ユーザー、平均 15,000 の ACR 消費（単位は発話では確認できません）を想定しています。3 年間で平均 95K のサービス収益（通貨単位は発話では確認できません）の機会があるのに対し、一般的な SMB 向けパートナーが実現できているのは約 23K で、およそ 25% にとどまります。つまり約 4 倍の機会があるという説明です。

移行はあくまで入口で、その後に続く仕事があります。Lakshmi は、CIO や CTO から「こうした移行は、必ず後続の作業につながる」と聞いていると紹介しました。アセスメントと移行だけで終えず、モダナイゼーション、AI 向けのデータ準備、エージェント構築、マネージドサービス、顧客への事前の提案へ広げるよう促しました。

一度きりの案件を手作業で進めると、効率も利益率も上がりません。Catalyst で自動化すれば、移行コストが下がり、顧客の導入の壁が低くなり、移行・モダナイゼーションを量の取れるビジネスにできます。自動化や AI を取り込んだ移行の能力は競合との差別化にもなり、人手が減るほど工程の予測可能性も高まります。SMB では価格圧力が強く、顧客は価値より先に金額を聞くため、自動化で説明しやすい価格にできる点が重要だと述べました。

### 5.9 Microsoft の支援策

- **スキル習得**：営業、技術者、アーキテクトを Microsoft の主要スキルで育成するフレームワークがある。SMB 領域の課題は営業パイプラインで、Microsoft の物語を語れる営業が少なく（前夜の会食で、数百人の営業担当のうち語れるのはごく一部だったという話を聞いたと紹介）、スキル習得がパイプライン作りにつながると述べています。
- **ツールと製品**：Azure Catalyst に加えて、パートナー独自の IP（知的財産）、自動化スクリプト、運用手順書（ランブック）を持てる。
- **市場展開**：プレイブックやピッチ資料があり、自社ブランドに合わせて使える。顧客との会話の進め方を示すガイド付きの手順もある。
- **オファーとインセンティブ**：Azure Accelerate（発話の中で「Frontier Accelerate」と言い直している箇所があります）が、顧客・ワークロード・国に応じたインセンティブやプログラム特典の枠組みです。Lakshmi は、パートナー向けのオファー、スキル習得、投資の「単一の入り口」であり、Azure に限らず、データベース移行、Copilot、セキュリティなど他の AI ワークロードにも使うと説明しました。インセンティブと投資の内容は、ワークロード、国や地域、案件規模で変わります。

### 5.10 質疑応答

1. **Azure Accelerate は Azure Catalyst に対応するか。**　Lakshmi は、Catalyst は移行・モダナイゼーション用のすぐ使えるエージェント型ツール群で、Azure Accelerate はインセンティブを含む枠組みであると区別しました。質問者が指していた移行ツールについては、Azure Migrate は今後 Catalyst に含まれると、登壇者が補足しています（話者は特定できません）。
2. **CI/CD（継続的インテグレーションとデプロイ）のパイプラインなど、特定の機能やジャンプスタートがほしい。**　質問者は、注文から入金までのような業務プロセスに対するソリューションアクセラレーターを求めていると、発表者が理解しました（質問の細部は録音の都合で聞き取りづらい部分があります）。Mayank は、Catalyst とは別に、「ゴールドスタンダード アクセラレーター」と呼ばれる Microsoft のソリューションアクセラレーター群があり、自分用の Copilot の構築やデータとの対話などを扱うが、注文から入金のような中核業務プロセスは対象ではないと答えました。これはロードマップになかったが、Catalyst には専任のエンジニアリングチームがあるため、持ち帰って検討するとしています。回答の時期は示されていません。
3. **自社のアクセラレーターや自動化の枠組みを使ってよいか。**　Lakshmi は、オープンであり持ち込めると答えました。ただし新規に作る前に、Catalyst に既にあるか確認してほしい、データベース移行の新規事業を始めるときも、Catalyst のツールとアクセラレーターがあるので、ゼロからは始まらない、足りない部分に自社の IP を載せて差別化する、と話しています。
4. 別のやり取りで、依存関係が担当者の頭の中にしかない「属人的な知識」になっているという指摘があり、Lakshmi は、移行・モダナイゼーションで壁が取り払われ整理されていくと同意しました。また、データセンターのアプリケーションも見られる可能性がある、という発言もありました（質問の全体は聞き取れません）。

## 6. デモ・手順

デモは、ライブ操作ではなく、**事前に用意された動画（ナレーション付き）の再生**でした。Mayank は「簡単なデモを流します」と述べています。以下は、動画のナレーションで語られた範囲です。画面の細部は音声からは確認できません。題材は製薬会社の架空の顧客 Caldova Pharma です。

1. **発見と判断**：Caldova は 3 つの目標（アプリケーションの Azure へのモダナイズ、コスト削減、レジリエンスの向上）を共有する。Catalyst が道筋の構築を始め、現在の資産を把握する選択肢を提示する。ServiceNow にある構成データを使い、ゼロからの調査を避ける。
2. IT チームが、依存関係を確認できる 1 つのビューを得る。AI が資産全体をマッピングし、ワークロードを業務上の重要度と複雑さでアプリケーションごとにまとめる。
3. AI が経営層向けのモダナイゼーション提案をまとめる。事業案件と ROI、アプリの準備状況、ターゲットアーキテクチャ、資産全体のセキュリティ脆弱性、ウェーブ（段階）に並べた推奨のモダナイゼーション経路が含まれる。
4. **計画**：Catalyst が、Cloud Adoption Framework と Azure Well-Architected Framework に沿った Azure ランディングゾーンを推奨する。ネットワーク、ID、セキュリティ、ガバナンス、コンプライアンスをまとめ、レジリエンス要件に合わせる。プラットフォームチームがレビュー・調整・承認できる。
5. アプリケーション単位の計画：Caldova Asset Manager を対象に、Azure App Service、Azure SQL Managed Instance、Azure Files を推奨する。アプリの所有者が業務上の重要度を「低」から「高」に直すと、Catalyst が設計を更新し、パフォーマンスのために Azure Cache for Redis を加える。
6. 実行ウェーブを数分で作成する。アプリの依存関係、準備状況、工数、重要度を考慮して、インフラ、アプリ、データベースの全体を並べる。Caldova Asset Manager が最初で、SQL Server がサポート終了に近づいており、セキュリティリスクがあるため。
7. **実行**：共有ビューで、共通のインフラ構築とアプリごとの手順をつなげて進める。SQL Server を Azure SQL Managed Instance に、Azure Files の移行と並行して移す。データベースの移行は、計画時に決めた対象・依存関係・判断を引き継いだまま、同じ実行計画に含まれる。データベースチームは専用の移行機能を使える。
8. アプリ開発チームは、GitHub Copilot 内の Azure Catalyst で作業する。実際のコード、依存関係、構成を解析し、変更が必要な箇所を特定する。フレームワークと依存関係のアップグレード、クラウド構成の更新、セキュリティ問題の修正まで支援する。
9. Asset Manager の .NET アプリを Azure App Service 向けにモダナイズする。Caldova 独自の標準とセキュリティポリシーをルールブックで適用し、シークレットとキーは Azure Key Vault で安全に管理する。
10. 開発者は実際のコード変更をレビューし、GitHub Copilot でビルドを検証し、テストを実行し、デプロイの準備をする。アプリが検証され、Azure に正常にデプロイされる。

ナレーションの結びは、「古い資産から出発し、レジリエンスを高めコストを最適化しながら Azure へモダナイズした」というものでした。

## 8. 利用者にとっての利点

- ライセンスの複雑さの解消と、構成によってはライセンス費用の削減（Azure Hybrid Benefit、ライセンス費用のないデータベース製品）。
- 運用コストについて、初年度に消費額の 50% のクレジット（規模に応じて）。
- 移行コストの低下。事例として、約 9,000 SQL コアのアプリが 2〜3 週間で、Teams の .NET 6 から .NET 8 へのアップグレードが数時間で完了、Xbox で工数 88% 削減。
- 保証ではないが、ほぼ 2 桁の削減（50% 超から 20〜30%）が実績として語られた。
- 脆弱性の洗い出し（M-dash のスキャンで、未知の脆弱性が見つかった例が多い）。
- パートナー側では、Forrester の調査で、実現できている収益の約 4 倍に相当する機会があり、自動化による低価格化・差別化・予測可能性の向上が得られる。

## 9. まとめ

SMB の 30〜40% がすでにエージェントを試している今、AI の備え、セキュリティ、コストの 3 つの圧力が、アプリとデータベースの移行・モダナイゼーションを後押ししています。Microsoft は Azure Migrate と GitHub Copilot を統合した Azure Catalyst を発表し、発見・判断・計画・実行を 1 つの流れで扱えるようにしました。あわせて、ライセンス、運用、移行の 3 つのコストを下げる50% 削減を掲げたオファーを示し、大手事例と Microsoft 社内の事例で効果を裏付けています。パートナーには、移行を入口にしてモダナイゼーション、データ準備、エージェント構築、マネージドサービスまで広げ、Catalyst や自社 IP、スキル習得、Azure Accelerate の支援を組み合わせて、量の取れる事業にすることが呼びかけられました。
