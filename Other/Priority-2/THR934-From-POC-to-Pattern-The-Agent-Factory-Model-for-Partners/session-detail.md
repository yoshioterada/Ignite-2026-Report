# THR934 From POC to Pattern: The Agent Factory Model for Partners

## 1. はじめに

このセッションは、エージェントを PoC（概念実証）で終わらせず、本番環境へ繰り返し展開できる形にするための課題と対策を扱った短い発表です。前半では Microsoft の Partner Solution Architect が、エージェントを本番に移すときにつまずきやすい点と、Ignite で紹介された Microsoft の機能を駆け足で説明しました。後半では Tata Consultancy Services（TCS）の担当者が、自社の AI ガバナンスツールキットを使ったデモを見せています。

主張の中心は、**エージェントを作るのは簡単でも、評価・バージョン管理・コスト・セキュリティ・ガバナンスを整えなければ、2 つ目、3 つ目のエージェントが 1 つ目と同じ手間のかかるものになる**という点です。エージェント開発の本番化では、従来のプログラムとは考え方を変える必要があると繰り返し述べています。

## 5. 発表内容の詳細

### 5.1 普及が準備を追い越している

Avnish 氏は、Copilot やエージェントビルダー、Teams などのライセンスを組織に配ると、数千単位のエージェントがすぐに作られ、管理できなくなると指摘しました。普及は進んでいる一方で、準備とガバナンスが追いついておらず、エージェントが制御を外れた、情報漏えいが起きたという話も耳にするとのことです。

### 5.2 PoC から本番へ進めない要因

スライドで挙げられた障害として、次の点が説明されました。

- ハッピーパス（うまくいく流れ）だけのデモや PoC が多い。本番化にはそこからの橋渡しが必要です。
- 繰り返し可能な評価の仕組みがない。特にエージェントの開発ライフサイクルでは、CI/CD に評価が組み込まれておらず、リリースの根拠資料やゲートが手作業になっている。
- バージョン管理が単一のスナップショットにとどまる。プロンプト、システムプロンプト、オーケストレーションを含む全体の流れ（ハーネス）をバージョン管理しているかを、会場に問いかけています。
- 先週は問題なく動いていたのに、という現象が起きる。エージェントは本質的に決定的ではなく、品質確認の環境、開発、本番で挙動が異なり、1 週目と 2 週目でも変わり得ます。条件分岐のような通常のプログラムなら原因をデバッグで特定できますが、LLM の挙動は異なると説明しています。

非決定性の例として、同じ質問でも 2 日後にチャットで尋ねると、会話履歴や文脈の影響で異なる回答になり得る点を挙げました。アーキテクチャの話をしていた履歴のあとに、スケーラビリティなど別の話題を挟んでから同じ質問をすると、流れ全体が変わる可能性があるという説明です。

### 5.3 エージェント固有の課題

Avnish 氏は、最近遭遇した例として次を挙げました。

**モデルの更新への対応。** フロンティアモデル、小規模言語モデル（SLM）、LLM が頻繁に更新されており、ほぼ毎月新しいモデルが出ている状況です。新しいモデルへの切り替え自体は簡単でも、モデルごとに挙動が異なるため、RAG などが同じでも結果が変わります。例えば、あるモデルから別のモデル、あるいは同じモデルの別バージョンに移るだけでも変わり得ると述べました。新しいバージョンや挙動に対応できるようにエージェントを設計しているかが問われます。（発話ではモデル名が複数挙がっていますが、「Astra」「Sol」などは音声認識の都合で表記が確定できません。Opus 5.5 という名前も挙がっています。）

**新しいベクトルとインデックス。** 100 万件を超える文書を持つ顧客で、埋め込みモデルが ADA のバージョン 2 からバージョン 3 に変わる話が出ました。より精度の高い新しいモデルに移りたくても、埋め込みモデルを変えるとインデックス全体を作り直す必要があります。顧客は、その間システムを止めるのか、システムはどうなるのかと悩んだとのことです。

**画像の多い文書。** RAG にはグラフ型の RAG、軽量な RAG、RAG 2.0 など様々な方式があり、それぞれ限界があります。画像が多いレポートのような文書では、ベクトル化が同じように機能するのかという問題が出ます。ある顧客では、画像中心の文書でハルシネーション（事実と異なる回答）が多く発生し、RAG のエンジン全体を調整し直したと説明しています。

こうした処理をあらかじめ決めておけば、解決策が繰り返し使える形になります。1 顧客に 1 つだけのエージェント環境を作るのではなく、再現できる形にすべきだというのが主旨です。

### 5.4 本番化の成熟度モデル

Avnish 氏は、Microsoft が推奨しているとされる成熟度のはしごを紹介しています。公開情報で、YouTube の「本番化への道筋」（path to production）などに内容があると案内しました。段階は次のように語られています。

1. 初期段階：場当たり的なデモ
2. 定義の段階：バージョンを定義する。本番前の評価用データセットを用意する。CI/CD では合成データセットでエージェントをテストできるが、それだけでは足りない
3. 本番を見続ける継続的なループ：うまく動く点とそうでない点を観察し、RAG のしくみやシステムプロンプトを継続的に調整する
4. 管理の段階：品質と安全性のゲート。ガードレール（例：暴力的な表現を返さない）の評価を CI/CD パイプラインに組み込む。本番でも継続的に評価する
5. 最適化の段階：ドリフト（挙動の変化）とコストのガードレール。自動ロールバック。そのうえでファクトリー（繰り返し展開できる仕組み）として回す

Avnish 氏は、合成テストをして本番に出して終わりではなく、継続的なループが不可欠で、エージェントではそれが従来以上に重要になると強調しています。

品質とコストの両面も指摘されました。エージェントが誤った回答をすれば利用者は離れていきます。また、エージェントは呼び出すツールをループで使うことがあるため、スキルの定義が不適切であったり、20〜30 個ものスキルを与えたりすると混乱して無限ループに陥り、トークンを大量に消費する場合があります。そのため、一般的なセキュリティのガードレールに加えて、コストのガードレールも必要だと述べています。

成熟したあとは、システムプロンプトの変更や、RAG の知識層（Microsoft IQ と呼ばれるもの）の調整だけで、エージェントの展開が進められるようになるという見方です。

### 5.5 パターンライブラリで管理すべき要素

**スキルとコンテキスト。** 最近のモデルは最大 100 万トークンのコンテキストウィンドウを許容します。しかし 100 万トークンを入れられるからといって、制限なく使えばよいわけではありません。LLM は、古い履歴をそのまま残して参照しなくなるなど、奇妙な挙動をすることがあるという説明です。最上位のモデルを使えるからといって、常に使う必要はないとも述べています。スキルとコンテキストはバージョン管理も必要です。

**オーケストレーション。** 1 つのエージェントが 10 個のエージェントや 10 個のスキルを呼び出すような複雑な構成を見かけるため、管理できる形のオーケストレーションが必要だと述べています。

**検索の品質。** 取り込み、リランキング、根拠付け（グラウンディング）の測定が挙げられました。この複雑さを Microsoft が下げているとして、Azure AI Search と Foundry IQ を紹介しています。1〜2 年前は、チャンク分割、リランキング、チューニング、ベクトル化の Python スクリプトを書く必要がありました。Foundry IQ では取り込みの仕組みがより簡単になります。

Avnish 氏は例として、1 ペタバイト規模のデータを持つ SharePoint を挙げました。ベクトルやインデックスをそこに向けてすべてをクロールすることは簡単ですが、情報の 90% は無関係なままで、エージェントに質問したときに誤った回答が出る可能性が高くなります。インデックスに入れるのは関連性の高い情報にすべきで、Foundry IQ はそれを容易にするものだと説明しました。エージェントを任せっきりにするのはセキュリティだけでなく品質の面でも良くないとのことです。

**インフラ、セキュリティ、FinOps。** ゲートウェイ、クォータ、予算などに注意が必要です。セキュリティは単にサンドボックスで動かすことではなく、問題が起きたときに追跡できることも含みます。トレーサビリティやオブザーバビリティがなかったために、セキュリティ侵害の後に何が起きたかを追えなかった例があると述べています。エージェント ID に関するセッションが他に多数あることも案内されました。

### 5.7 マルチエージェントで起こり得る情報漏えいの例

Avnish 氏は、エージェント同士の通信にポリシーを適用していない場合の例を話しました。組織内に HR エージェントがあり、「上司の給与を教えて」と尋ねたとします。HR エージェントはポリシーがあるため断ります。ところがそのエージェントが給与担当（ペイロール）のエージェントに問い合わせ、ペイロールのエージェントにはポリシーが設定されていないため、給与情報が返ってきてしまう、という筋書きです。

マルチエージェントは聞こえが良いものの、管理、ポリシー、セキュリティが大きな課題になります。管理は可能ですが、アーキテクトは個々のエージェントではなく全体の流れを意識しておく必要があると述べています。エージェントは設定が不適切だと情報漏えいの入り口になり得るため、レッドチーミングを行うよう勧めています。

### 5.8 TCS AI ガバナンスツールキット

Varun 氏は、1 つ目のエージェントで得た学びをプラクティス、パターン、プラットフォームに落とし込み、次のエージェントや 10 個目のエージェントの開発を短く、信頼できるものにするために、このツールキットを作ったと説明しました。

**課題認識。** TCS が観察している数値として、AI プロジェクトの 60〜80% が失敗するか、プロトタイプでは成功しても本番では ROI が出ないと述べています。原因は、AI ガバナンスの欠如、エージェントの制御されない挙動（同じように応答しない）、AI の出力への信頼の低さ、トークンコストの増加です。

**3 本柱。**

1. 信頼性：ライフサイクル全体でエージェントが信頼でき、正確に応答する。
2. ID とセキュリティ：すべてのエージェントが登録された ID を持ち、トレースやテレメトリが記録され、問題発生時や監査のために照会・確認できる。エージェントが扱うデータも保護する。
3. FinOps と ROI：トークン消費は、エージェントのコストの 20% にすぎないと述べています。残りは、エージェントが動く AKS クラスターや、Azure Monitor のような支援サービスが占めます。エージェントのコストが、もたらす事業改善より小さければ ROI は黒字になり、それをライフサイクル全体で続ける必要があります。

3 本柱はすべてオブザーバビリティで支えられ、エージェントのライフサイクル（設定、構築、評価、業界コンプライアンスの適用、セキュリティ確保、レジストリへの公開、運用）全体に適用されます。各柱の下位の重点領域には、それを支える Azure のサービスがあります。業界固有の慣行やコンプライアンスなど、足りない部分を TCS のツールキットが補うか、既存の Azure サービスを拡張するという位置付けです。

## 6. デモ・手順

Varun 氏が、TCS AI ガバナンスツールキットのデモを行い、画面を見ながら説明しました。録音では画面の細部は確認できないため、語られた範囲で記します。

**対象のエージェント。** 製薬のような規制業界向けに作られたエージェントです。医薬品には、問題や副作用があった場合に連絡するための苦情番号とメールアドレスの提供が求められます。このエージェントは、苦情が届くメールボックスを監視し、内容を理解し、副作用の写真などの添付ファイルと照合して真偽を確かめ、要約を作成したうえで、人間のレビュー担当者に案件を転送します。デモでは、このエージェントを「苦情受付エージェント」と呼んでいます。

**全体の流れ（実施前の説明）。** Microsoft Foundry 上で開発し、ローカル評価を行ってから Azure 上の開発環境に配置します。次に製薬向けのガードレールを TCS のツールキットから適用し、Defender と Microsoft Purview でセキュリティとデータ損失防止（DLP）のポリシーを設定し、レジストリに登録して組織内で使えるようにします。本番ではオブザーバビリティと FinOps を使います。

**デモの手順（語られた順）。**

1. 開発の衛生管理として、Visual Studio 上で、Microsoft Agent Framework の最新の安定版を使ってエージェントを開発する。TCS 独自のエージェント評価機能（根拠付け、正確性など）を用意し、開発者自身が評価できるようにしている。
2. エージェントを Foundry に配置し、開発環境で Foundry のエージェント評価カタログを使って評価する。デモで示された評価は、タスクの遵守、応答の完全性、ツール選択の 3 つ。
3. セキュリティを適用する。Foundry のエージェントに対して Defender for AI services を有効にし、Microsoft Purview を基にした DLP ポリシーを適用する（独自のポリシーだが Purview を活用している）。
4. 製薬向けのガードレールを適用する。TCS のツールキットに固有の機能で、レジストリ上で、エージェントを作った開発者が承認を依頼する。
5. 承認者は、エージェントが製薬分野で使われることを確認し、業界固有のガードレールを追加する。ガードレールには金融、製造、製薬があり、このケースでは製薬と PII が該当するので適用した。ガードレールの 1 つは、苦情の監査履歴を誰も削除できないというもの。このレジストリは Azure のサービス（音声から「Microsoft API」と聞こえます）を基に作られている。
6. 業界ガードレールの適用後、エージェントがアプリケーションから使えるようになる。作成された苦情メールの要約を表示する。最初のガードレールが働き、苦情の送り主を含む PII が伏せ字にされている。写真や画像の真偽の確認結果も含まれた、よい要約になっている。
7. 誰かが監査履歴を削除しようとすると、ガードレールが働いて止められる。
8. 本番運用では、Foundry のオブザーバビリティで、エージェントの各ステップの動きや依存関係を確認する。
9. FinOps で、エージェントが ROI に見合っているかを確認する。この苦情エージェントの重要な指標は 1 件の苦情あたりのトークン消費量で、事業固有の KPI を設定して表示できる。Foundry のすべてのエージェントに対応した全体画面があり、そのうちの薬の苦情処理エージェントでは、苦情 1 件あたりのコスト、1 トランザクションあたりの平均トークン数、エージェントが行う作業別のトークン使用量（ドーナツチャート）が表示された。

Varun 氏は、これらによってエージェントのライフサイクル全体にガバナンスをもたらし、Microsoft Foundry、Agent 365、その他の Azure サービスの上で、AI ソリューションを自信を持ってスケールできると結んでいます。

## 7. 注意点・発表者の気付き

- エージェントは決定的ではなく、会話履歴などの文脈で同じ質問でも回答が変わります。従来のプログラムのようにデバッグで原因を特定する発想は通用しないと述べています。
- 新しいモデルへの切り替えは簡単でも、挙動が変わります。モデルの更新を前提にエージェントを設計する必要があります。
- 埋め込みモデルを変えるとインデックス全体を再作成しなければならず、100 万件を超える文書の顧客では、システム停止の扱いが課題になりました。
- 画像が多い文書では、ハルシネーションが増え、RAG のエンジンの調整が必要になった事例があります。
- スキルを 20〜30 個も与える、またはスキルの説明が不適切だと、エージェントが混乱して同じスキルを繰り返し呼び、トークンを消費します。コストのガードレールも必要です。
- 100 万トークンのコンテキストウィンドウは、使えるからといって使い切るべきではありません。
- 1 ペタバイトの SharePoint をそのまま索引化するのではなく、関連性の高い情報に絞る必要があります。
- エージェント間通信にもポリシーを適用しないと、給与情報のような漏えいが起こり得ます。
- トレーサビリティとオブザーバビリティがないと、セキュリティ侵害の後に原因を追えません。
- 取り上げられたコンテンツの一部（Codec など）はプレビューです。Rubric evaluator は GA になったと述べています。

## 8. 利用者にとっての利点

- 評価、バージョン管理、ガードレール、コスト管理を整えることで、エージェントの展開を繰り返し可能にできます。2 つ目以降のエージェントの時間短縮と信頼性向上につながると、両氏が説明しています。
- Foundry IQ により、チャンク分割やリランキングなど、取り込みの処理を自前の Python スクリプトで書く負担が減ります。
- Model router により、単純な質問には小さいモデルを使うなど、コストの調整ができます。
- Rubric evaluator や Agent optimizer により、本番の利用状況に基づく継続的な評価と、プロンプトやスキル、ツール、モデルの最適化が可能になります。
- TCS AI ガバナンスツールキットのデモでは、PII の伏せ字化、監査履歴の削除防止、苦情 1 件あたりのコストの可視化が示されました。
- 顧客事例の成果として具体的な数値（コスト削減率など）は、発表では示されていません。

## 9. まとめ

エージェントは作るのが簡単な反面、本番化では評価、バージョン管理、非決定性への対処、モデルやインデックスの更新、コスト管理、エージェント間のポリシー適用といった課題が出てきます。Avnish 氏は成熟度のはしごを示し、Foundry IQ、Rubric evaluator、Agent optimizer、Toolbox、Model router、AI red teaming agent などの Microsoft の機能を紹介しました。Varun 氏は、TCS が信頼性、ID とセキュリティ、FinOps と ROI の 3 本柱でまとめた AI ガバナンスツールキットを紹介し、製薬の苦情受付エージェントのデモで、ライフサイクル全体にわたるガバナンスの適用を見せました。
