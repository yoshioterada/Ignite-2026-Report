### 5.2 背景：DevOps と一貫したデプロイ

発表者は聴衆に開発者か運用かを尋ね、開発者の挙手のあと、それ以外は運用担当かと確認し、聴衆の中心が運用担当者であることを押さえました。

業界は、毎月、毎週、毎日のように新しいバージョンのアプリケーションを出す方向に進んでいます。VM でも可能ですが、それを安全に構造化して進める実践がありません。その実践が DevOps であり、DevOps は技術ではなく、ソフトウェアを継続的に、安全策を持ちながら適切に展開するための実践の集まりだ、という説明です。そのためには、ワークロードを一貫した方法でデプロイする仕組みが要ります。

開発者から「自分の環境では動くのに」と言われる問題も挙げられました。開発者のマシンには、複数のバージョンを含むあらゆる依存関係が入っているためです。

### 5.3 コンテナーイメージ、Dockerfile、レジストリ

VM では、まず OS を展開してから、アプリケーションを構成します。コンテナーでは、OS、依存関係、アプリケーション、その構成までを含んだ構成済みのパッケージ、つまりコンテナーイメージを使います。コンテナーを起動すれば、アプリケーションは正しい形で動いており、開発者の環境でも本番でも同じ動きになります。

Dockerfile は、そのイメージを作る手順書です。VM なら OS の展開と構成、前提条件の展開と構成、アプリケーションの展開と構成という手順を順番に行います。Dockerfile はそれと同じことを一式の手順として書いたものです。発表者は、Dockerfile の細部は理解しなくてよいと話しています。

作ったイメージは、誰でもダウンロードできる中央のリポジトリーに保存します。発表者は、プッシュとプルという用語は、アップロードとダウンロードにすぎないと説明しました。開発環境でアップロードし、本番のサーバーでダウンロードします。画面では Azure Container Registry にリポジトリーとイメージがあり、Dockerfile やアプリのバージョンを変えるたびに、新しいバージョンのイメージを保存する様子が示されました。

### 5.4 Kubernetes はフェールオーバークラスタリングとネットワーク負荷分散

IT の経験が長い人になじみのある技術として、次の 2 つが挙げられました。

| 技術 | 役割 |
| --- | --- |
| フェールオーバークラスタリング | 状態を持つアプリケーションが、あるノードで動き、障害時は次のノードで動き続ける |
| ネットワーク負荷分散 | 高トラフィックのとき、背後にある複数の計算単位へトラフィックを振り分ける |

発表者は、**Kubernetes は誰も教えてくれなかったが、これらを実装するリソーススケジューラー**だと説明しました。他にも多くのことをしますが、最も基本の形ではこの 2 つだけです、とも述べています。

開発環境では単純なアプリケーションで、かつては階層（ティア）で考えたものを、今はサービスで考えます。マイクロサービスなら、アプリケーションの特定の部分を支えるコンテナーが複数あります。本番では複数のアプリがそれぞれ複数のサービスを持つため、コンテナーのスケジューリングを管理する仕組みが必要で、ノードが落ちたら別へ移し、トラフィックを正しいコンテナーへ向ける必要があります。

#### 5.4.1 構成のずれと、宣言的な管理

VM を複数管理するときの問題は、構成のずれ（ドリフト）です。Desired State Configuration のような仕組みはありますが、VM はそのように運用する前提で作られていません。VM に入って構成を直す方式で、すべての VM が正しく構成されているかを確認する必要があります。

Kubernetes では、環境にアクセスしてコンテナーの構成を変えることはしません。変更が必要なら、デプロイしたい望む状態を変えます。その状態は仕様書として書き、Kubernetes では YAML を使います。

### 5.5 YAML の仕様：Deployment、Service、水平ポッドオートスケーラー

画面には、フロントエンドとバックエンド（ワーカー）の YAML が示されました。発表者は、細部は学びながら分かるようになるので、今は「どう展開したいかを指定している」点だけ理解してほしいと述べています。

**Deployment（デプロイメント）**
- レプリカ数（何個動かすか）、実行するノード、使うイメージを指定する。イメージの取得元として、先に公開したコンテナーレジストリのアドレスを書く。ノードはそのアドレスからイメージをダウンロードして実行する
- アクセス方法、アプリが必要とする環境変数、ノードから使えるメモリと CPU の量なども設定する
- 更新時は、すべて削除してから作り直すのではなく、新しいポッドを 1 つ追加し、古い 1 つを削除する、という入れ替えを繰り返して新バージョンに移る。問題があれば元に戻せる
- 発表者は、Deployment を、環境で動いているコンテナー（計算単位）とその数を抽象化するものだと説明している

**Service（サービス）**
- コンテナーに直接トラフィックを向けると、そのコンテナーが落ちたとき接続が失われる。そこで、背後の計算単位の前に置く仮想 IP アドレスが Service
- コンテナーを増減しても、Service が常に正しい宛先へ振り分ける
- 画面の例は、種類がロードバランサーの Service で、フロントエンドのアプリに向け、ポート 80 の HTTP を振り分ける

**水平ポッドオートスケーラー（HPA）**
- スケールの判断に何を測るかを指定する。この例では、CPU 使用率が 60% を超えたら、ポッドを 1 つから 50 に増やす、という指定

発表者は、これらは長年扱ってきた仕組みと同じで、違いは手作業ではなく、YAML に書いたスクリプトで構成する点だと話しました。

### 5.6 運用の変化：VM とコンテナーの管理の違い

コンテナーは、俊敏性のために作られました。何年も動き続ける VM の代わりに、数週間、あるいは数か月で入れ替わるコンテナーを使います。1 年動くコンテナーも問題ではありませんが、通常は新しいバージョンを展開する必要があるから使うので、環境は常に変わります。管理の方法も変わります。

| 項目 | VM | コンテナー |
| --- | --- | --- |
| 寿命 | 長い | 週や月の単位 |
| 管理 | 個々の VM の情報を集中管理。ドメインに参加させ、インベントリーと状況を把握 | 大規模に管理する。望む状態を定め、その状態からの逸脱を監視する |

### 5.7 監視・可視化のツール

AKS（Azure Kubernetes Service）で動かす場合に学ぶべきツールとして、次が挙げられました。

- **Log Analytics と Container Insights**：ログ、イベント、インベントリー、クラスターやアプリケーションの状況を確認し、トラブルシューティングにも使う。Azure のインフラを管理している人にはなじみがある、と説明されています
- **Prometheus**：オープンソースのツール。メトリックと時系列データを扱う。クラスターのインフラ層からアプリケーションまでの情報を、同じ中央のデータベースに集められる。開発者がアプリから Prometheus にデータを送るよう構成することもできる
- **Grafana**：同じくオープンソース。Prometheus のデータへのアクセス方法は使いやすくないため、よりよいダッシュボードを作るのに使う

Prometheus と Grafana は、Kubernetes 以外でも使えるが、主に Kubernetes 環境で使われる、という説明です。

### 5.8 セキュリティ：サプライチェーン

コンテナーで新たに加わるのがサプライチェーンの問題です。Dockerfile の先頭は FROM という文で、Microsoft、Docker Hub などの他のコンテナーイメージのリポジトリーから、すでにあるイメージを出発点にダウンロードします。作った人を信頼できるのか、ダウンロードされたバイナリーを信頼できるのかは、分かりません。つまり、開発者が書いていないコードが環境に入ります。

Kubernetes には、ダウンロードするものが運用チームによって承認されたものであることを確認する仕組みがあります。中央のリポジトリーに公開するとき、署名されたものだけがノードに降りてきて、ノードがそのイメージを署名し承認したものか検証できるツールがある、という説明です。具体的なツール名は発話では確認できません。

それ以外は既知の知識が使えます。Hyper-V や VMware のノードを守るように Kubernetes のクラスターノードも守る、OS も守る、という点は同じです。新しいのは、以前なかったサプライチェーンだけだと述べています。

### 5.9 VM を置き換えるのか、学習リソース

発表者は冒頭の問いに戻りました。ここまでの仕組みで得られるのは、DevOps の実践に基づいて、ワークロードをより安全にデプロイできることです。プラットフォームエンジニアリングと呼んでも構いません。目標は、デプロイするものをコードとして管理するインフラストラクチャー（IaC）で展開し、複数のデプロイを安全に行うことです。

では VM を置き換えるのか、という問いには「いいえ」と答えました。スケールが要らない、ソフトウェアを頻繁に展開しない、開発チームがいないのであれば、Kubernetes を見る必要はありません。VM が適しているワークロードは VM を使い続け、Kubernetes が適したワークロードにその方法を使えるよう、学んでおくべきだ、という考えです。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 新しいバージョンのアプリケーションを、安全策のある形で継続的に展開できる（DevOps の実践）
- イメージに OS、依存関係、アプリケーション、その構成が含まれるため、開発環境でも本番でも同じ動きになる
- 負荷が上がると、新しいポッドを自動で作り、応答時間を下げられる。デモでは参加者の接続で実際に確認された
- Deployment により、新旧のポッドを入れ替えながら更新でき、問題があれば元に戻せる
- 既存のセキュリティの知識がそのまま使える

## 9. まとめ

Kubernetes は、フェールオーバークラスタリングとネットワーク負荷分散を、YAML の宣言で実現するリソーススケジューラーです。VM では構成を直しに行きますが、コンテナーでは望む状態を変えます。Dockerfile でイメージを作り、レジストリーに保存し、Deployment、Service、水平ポッドオートスケーラーで展開、公開、スケールを定義します。

監視には Log Analytics、Container Insights、Prometheus、Grafana を調べるよう勧められました。新しいセキュリティ上の論点はサプライチェーンです。VM が適した用途には引き続き VM を使い、頻繁なデプロイや大規模なスケールが必要な用途に Kubernetes を使い分けるのが、発表者の結論です。
