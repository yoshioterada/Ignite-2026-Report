## 5. 発表内容の詳細

### 5.1 チームと顧客

2 人は Azure Engineering Operations に所属しています。このチームは、Azure の最重要顧客向けに Azure Engineering Direct という、エンジニア主導のプログラムを提供しています。対象は 500 社を超える戦略的な顧客で、合計すると数十億ドル規模の Azure 消費額になると説明されました。業種は通信、小売、エネルギー、金融、医療、航空などで、1 時間のダウンタイムでも大きな問題になる顧客です。

重大インシデントが起きると、このチームが対応を主導します（エンジニア主導の危機管理）。顧客を問い合わせの待ち行列に待たせず、最初の 1 分から Azure のエンジニアがインシデントを引き取り、必要に応じて製品グループ（実際に製品を作っている人たち）を直接巻き込み、最初から最後まで 1 つのチームが責任を持ちます。これが緩和（影響の軽減）を速くする要因だと説明しています。

インシデントが起きる前の準備も行っています。顧客の重要なアプリケーションとビジネス上の優先度を、Nomi と呼ぶ構造化されたプロファイルに記録し、主要なワークロードを事前に監視します。プラットフォームのアラートが早期警告になり、障害時にはすでに顧客にとって何が重要かが分かっている状態になります。

復旧後の対応は次のとおりです。

- 10 営業日以内に根本原因分析（RCA）を提供する
- 的を絞った再発防止項目を進める
- 繰り返し発生する傾向に対して、サービス改善計画を作る
- 年間を通じて、エンジニアリングのロードマップに関する情報、製品へのフィードバック経路、重要プロジェクトを期限どおりに進めるための協力を提供する

### 5.2 課題: インシデント数の増加と人手の作業

過去 1 年で重大インシデントの件数は 82% 増えました。増加の要因は、顧客の Azure 利用が拡大していることと、プログラムに参加する顧客が増えていることの 2 つです。事業にとっては良い知らせですが、インシデントはすべて、担当のオンコールエンジニア（DRI）に回ってきます。従来のやり方で対応するなら、毎年 50% 多く人を採用する必要がある計算でした。

ただし、人を増やしても本当の問題は解決しないと発表者は述べています。インシデント対応では、優先度付け（トリアージ）、ビジネスへの影響の把握、過去のインシデントの調査、本格的な調査、必要に応じた製品チームの招集、顧客の緩和支援、そして長い時間をかけた RCA の執筆まで、すべての段階をインシデントごとに手作業で行っているからです。

そこで取った方針は 2 つです。

1. インシデントの原因そのものを突き止めて、根本から直す。これを運用需要エンジニアリング（operational demand engineering）と呼んでいる。
2. 繰り返しの作業を AI エージェントに任せ、専門家が大きな判断に集中できるようにする。

### 5.3 想定シナリオ: 空港の搭乗券スキャン

状況を共有するために、作り話のシナリオが示されました。午前 3 時の混雑した空港で、普段はミリ秒で済む搭乗券のスキャンに数分かかっています。乗客は搭乗できず、行列は伸び、フライトが遅れる危険があります。空港のスタッフが航空会社の IT チームにエスカレーションし、IT チームが切り分けて Azure 側の問題だと判断し、Microsoft に重大インシデントを起票します。

Microsoft のエンジニアはスキャナの背後にあるサービスを診断し、原因を特定して修正し、航空会社の IT チームと協力して解決します。ここで発表者が強調したのは、原因の特定に数時間かかったのに、修正は数分で済んだことです。これを面倒な反復作業（トイル）と呼んでいます。数週間後に同様のインシデントが起きるかもしれず、その夜に復旧しただけでは翌月の問題は解決しません。1 晩の間に、引き継ぎの多さ、あちこちに散らばる事実、原因発見までの数時間という運用上の課題が見えました。

エージェントがここで役立つ可能性はあるものの、作る側にも課題があります。

- 事実は刻々と変わる。
- 診断のチェックは安全に実行されなければならない。
- エージェントの答えは信頼できなければならない。

これらが、このチームの言う「エージェントによるインシデント管理」の中身です。

### 5.4 デモの設定（詳細は 6 章）

デモは、顧客（Caldova というオンライン小売サイト）と Microsoft、それぞれのエージェントが 1 つのインシデントを一緒に調べる内容です。画面の下部には「インシデントメモリ」「永続的な実行」「セキュリティ・評価・ROI」という 3 つの要素が並び、デモの進行に合わせて該当箇所が強調表示されると説明されました。この 3 つは、いずれも実際のエンジニアリング上の課題を 1 つずつ解決するものとして紹介されています。

- インシデントメモリは、作戦会議室のホワイトボードにたとえられました。分かっていること、疑っていること、除外したことを書き出しておく場所です。
- 永続的な実行は、エージェントが何を確認するかを決める部分です。
- セキュリティ・評価・ROI は、正しい人とエージェントだけが入れること、危険な操作は人が承認することを担います。

### 5.5 アーキテクチャの全体像

ここから Sai 氏が、持ち帰れる設計パターンとして内部構造を説明しました。全体像は次のとおりです。

| 要素 | 役割 |
|---|---|
| 証拠（evidence） | 監視メトリックなどのライブのシグナル、社内で書いた、あるいはインターネットから集めたナレッジ記事、アプリや基盤のエンジニアが書いた PowerShell や Python のスクリプト（これらがランブックになる）、過去のインシデントからの学び。エージェントが仮説を立てて調査を進める出発点になる |
| エージェントとハーネス | エージェントは推論だけを担当する。会話の制御、必要なツール、コンテキスト、実行の境界は、ハーネスが受け持つ。ハーネスには Microsoft Copilot SDK（以前の名称は GitHub Copilot SDK）を使っている |
| 実行ランタイム（実行エンジン） | エージェントが診断を要求すると、ランブックを実行する層 |
| インシデントメモリ | エージェントが頼るべき、信頼できるデータ。上限のある（無制限に増えない）作業用の視点で、発見事項、仮説、決定事項、要約、すでに対応済みのこと、調査中の場所を保持する |
| エンジニア | エージェントの仮説に異議を唱え、危険な操作を誘導または承認する |

全体を通して、セキュリティ、評価、可観測性が適用されます。証拠とエンジニアは自明で、以前からどのシステムにも存在するため、インシデント管理向けに工夫が必要だったのは、実行、インシデントメモリ、セキュリティ・評価・ROI の 3 つだったと説明しています。

### 5.6 永続的な実行と実行エンジン

エージェントはどの診断が調査に役立つかを決め、対象のリソースと必要な入力パラメータを付けて、実行エンジンに依頼を送ります。実行エンジンは、システム全体で最も重要な部品の 1 つとされています。担当は、Azure Data Explorer からのデータ取得、ログのクエリ、外部 API の呼び出し、機微なデータの収集です。

**エージェントの境界と実行系を分ける理由**は、機微なデータや顧客データを扱う可能性があり、そうしたデータを LLM にも最終的な利用者にも渡したくないからです。さらに計算処理を LLM のコンテキストの外に置く理由として、VPN ゲートウェイの例が挙げられました。Azure に置いた VPN と、クライアントの間で BGP セッションが切れている問題を調べ、IPSec のログを見る場面です。バックエンドから 1 万行ものログが生成される場合、それをエージェントのコンテキストにすべて入れて分析させるのは現実的ではなく、エージェントは失敗します。そこで実行エンジンが決定論的に問題の箇所を見つけ、エージェントには必要な具体的な回答だけを返します。10 のシステムを組み合わせて 100 万行のログを見る場合も同じで、エージェントは時間内に処理できないか、途中で幻覚（ハルシネーション）を起こすと説明しています。

実行エンジンは次の統制も、LLM やエージェントの境界の外で決定論的に行います。エージェントからは見えません。

- スコープの強制（どのリソースに、どの呼び出し元が、どのエンドポイントにアクセスできるか。許可リストに載っているエンドポイントはどれか）
- ガバナンスと開示（システムが生成しうる大量の詳細を、すべて LLM のコンテキストに入れて判断させることはしない）

クエリやAPI の呼び出しの結果はこの層でガバナンス処理された後にエージェントへ戻り、エージェントは別の診断を実行エンジンに要求するかどうかを決めます。

**ランブック**は、アプリケーションチームや基盤チームが長年にわたって作ってきた手順書で、それを YAML のスキーマに変換して、実行エンジンに渡します。ランブックには 2 種類あります。

1. レビュー済みのランブック: アプリ、基盤、データベースなどのチームの専門家が作ったもの。
2. エージェントが調査中にその場で動的に生成するランブック: すべてのシナリオを専門家がカバーできるわけではない、という反論への答えとして紹介されました。

どちらも「信頼境界（trusted boundary）」の検証を通ります。スキーマの構造、スコープ、権限、ランブックが守るべき制限を確認し、この信頼ポリシーは開発者が設定するもので、エージェントからは見えません。エージェントが「ルールがあっても上書きして回避しよう」とできないようにするための設計です。さらに、スキーマとしては完璧な Kusto クエリが生成されても、呼び出したユーザーがそのデータを読む権限を持つとは限りません。権限がないと判断された場合は却下され、エージェントには「この人にはアクセス権がない。アクセスを得るためにエスカレーションするか、別のクエリを考えてほしい」と返されます。動的生成のときは、このやり取りが繰り返されます。

もう 1 つの要点は、**失敗したステップがあっても最初からやり直さないこと**です。実行の途中で 1 つのステップだけが失敗した場合に、エージェントが同じログや同じデータを集め直すのは無駄なので、実行エンジンが状態を保存します。流れは次のとおりです。

1. エージェントが実行するランブックや診断を選び、実行エンジンへ渡す。
2. 対象を解決する（正しいリソース ID か、正しいパラメータが渡されているか）。
3. ログやメトリックを取得する。例として、Azure Monitor から VM の可用性メトリックを取得する場面が挙がった。一時的な障害で取得に失敗した場合は、ランブックにあらかじめ指定されたリトライの仕組みが処理する。対象の解決からやり直す必要はない。
4. 取得結果を解釈する層に送る。ガバナンスは前段で済んでいるため、ここでは小さな LLM を使える。解釈の役割は、エージェントに渡す情報を書き直すことだけである。
5. エージェントが結果を受け取る。

実行エンジンの開発に時間をかけたのは、ガバナンス、渡したくない機微なデータ、そしてコンテキストエンジニアリングのためだと説明しています。インシデントは、エージェントとの 1 回の会話では済まず、複数のシステムがデータを出し、解決のために見るべきデータが多いためです。

### 5.7 インシデントメモリ

なぜインシデント調査に専用のメモリが必要なのか。Sai 氏は次の問いを挙げました。

- ログ、チケット、人同士のやり取りという構造化されていないデータを、コンテキストを超えずに調べるにはどうするか。
- 新しい証拠が届くたびに、インシデントの現在の姿をどう明確に保つか。
- 元の事実と関係を切らずに、仮説を進化させるにはどうするか。
- エンジニアが結論に異議を唱えたとき、根拠の出どころまでたどれるか。
- 引き継ぎや再起動の後に、次のエンジニアやエージェントが調査を再開するにはどうするか。

「LLM のコンテキストを広げればいいのでは」という議論には、容量を増やしてもキャッシュには役立つかもしれないが、そのときのトラブルシューティングで何が関連するかは改善されず、インシデントの現在の姿も維持されないと答えています。

具体例として、あるシステムが「10 時に変更があった」と検出し、ブリッジ（対策会議）のチャットで誰かが「デプロイが原因だ」と言い出し、一方でエージェントが診断を実行して「外部 API の呼び出しがタイムアウトを起こしている」と見つけた場面が語られました。このなかでエージェントが進むべき方向を決める材料は何か、という問題です。右側の 3 つの問い（今、何が関連しているか。理解は何が変わったか。調査の方向を支える証拠は何か）に答えるのがインシデントメモリです。

通常の方式では、ターン 1、2、3 と呼び出すたびに、新しい情報はごくわずかなのに、コンテキストは上限なく膨らんでいきます。そこでインシデントメモリを、**ある時点でのインシデントの、上限のある作業用の視点**として持ちます。中身は 2 種類に分かれます。

| 種類 | 内容 | 扱い |
|---|---|---|
| 元の事実（source facts） | 社内の IT アプリケーションなどが持つ状態。優先度（P1、P2、P0 など）、緩和済みかどうか、エンジニアが確認した時刻、別チームに移った時期 | 決定論的なデータなので、エージェントに更新させない。ステータスを LLM に判断させて更新することはしない |
| 解釈（interpretation） | 複数の情報源から集めた発見事項、仮説、会話の要約 | 別のメモリ保守パイプラインが、意味の理解を維持する |

メモリ保守パイプラインでは、LLM が新しく届いたデータと現在の状態を受け取り、メモリへの変更を提案します。提案は、確認されるか、除外されます。インシデントに関係のない新情報は除外され、メモリは更新されません。こうして、エージェントが正しい方向へ進めるよう、上限のある信頼できるメモリが保たれます。

もう 1 つの要素が、証拠の履歴です。上限は例えば 200K のコンテキストウィンドウだとします。インシデントの開始直後に誰かが「デプロイの変更があったから障害が起きている」と言ったものの、3 時間調べて調査の方向が大きく変わったとします。そこへ誰かが同じ主張を繰り返したとき、エージェントは証拠の履歴に戻り、出どころを特定してデータを引き出し、現在のコンテキストを更新します。これでインシデントメモリのループが閉じます。

要するに、**インシデントメモリはエージェント自身のメモリとは別に持ちます。** エージェントが調査を正しい方向へ進めるための、運用上最も信頼できるデータという位置づけです。

### 5.8 セキュリティ、評価、ROI

エージェントを本番に入れたら、リーダーシップも含めて、次の 3 つの問いが出ます。

1. やるべきことをやっているか（セキュリティ）
2. うまくやっているか（評価）
3. コストに見合うか（ROI）

**セキュリティ**: すべてのエージェントに固有の ID、限定されたスコープ、リスクのある操作に対する承認のガードを与えます。エージェント、実行、結果の流れのなかで、モデルがそう思ったというだけでは何も実行されません。モデルが自信を持って「これを実行しろ」と言っても、自信は許可ではありません。許可は、設定したポリシーと、関与するエンジニアの承認から出ます。

**実行記録（run record）**: これらの層を通して、操作、出力、かかったコストを記録します。会話やセッションと呼んでもよいものです。記録は、あとの評価の入力にもなります。

**評価**: 証拠を、評価基準（ルーブリック）に照らして採点します。3 つの層で行います。

- コードによるチェック
- モデルによる採点
- 人によるレビュー

エージェントは、もっともらしく聞こえるからという理由では信用せず、測定するという考え方です。

**価値（ROI）**: モデルのコストと利用状況を追跡します。例として、ある出力の手作業の基準時間が 30 分で、その出力を 10 件生成した場合、30 分 × 10 件で、手作業に換算して 5 時間分の工数に相当します。ただしこれは推定であり、実現した削減額ではないと、最初から明示すると説明しています。誰かに疑問を持たれても数値が持ちこたえるようにするためです。

要約すると、セキュリティが安全にし、評価が良いものにし、ROI が価値あるものにします。1 つの記録で、この 3 つすべてを追跡できます。

### 5.9 AI を適用する場所の見つけ方と、エージェントが担う仕事

Azure Engineering Direct Intelligent Assistant（ADA と略している）を始めるとき、まず「どこに AI を適用するか」を考えました。出発点は、エンジニアが今どこで運用上のトイルに時間を使っているかを問うことでした。インシデント管理で洗い出した課題は次のとおりです。

- 毎回、ケースの履歴とビジネスへの影響を調べる。
- 複数のダッシュボード、アラート、ツールを行き来する。
- 類似の問題や根本原因を探し回る。
- RCA を毎回手作業で下書きする。
- 危機対応中に、エグジット（終了時）のブリーフィングを用意する、または組織内の誰かに更新を送る。

発表者は、調査する時間そのものが貴重ななかで、これらがすべてオーバーヘッドになっていると述べています。さらに、品質は電話に誰が出ているかにも左右されます。ネットワークの専門家はその専門性ゆえに速い緩和に導けますが、問題がネットワークなのにデータベースのエンジニアが担当すると、解決はネットワークの専門家ほど速くなりません。

そこで、トイルを取り除ける箇所のチェックリストを作り、エージェント型のソリューションを当てはめました。エージェントが引き受ける内容は次のとおりです。

- すべてのケースでの自動的なエージェントの関与
- 履歴、影響、ワークロードの把握（数分）
- 過去のインシデントから推定した、考えられる根本原因
- 顧客向け RCA の下書き（数秒）
- 承認済みの、顧客向け更新の下書き（発話の聞き取りが不明瞭で、正確な表現は確認できません）

これによって、すべての顧客が、専門家レベルの支援を一貫して受けられるようになると説明しています。

## 6. デモ・手順

デモは行われました。顧客側のエージェントと Microsoft 側のエージェントが、同じインシデントに一緒に取り組む様子を、画面で見せる形式です（映像を再生する形式で、発表者が画面の内容を解説しています）。登場するシナリオは、前述の作り話とは別の、Caldova というオンライン小売サイトのインシデントです。画面の細部は音声からは確認できず、以下は発表者が語った範囲に限っています。

1. Azure App Service 上で動く Caldova のオンライン小売サイトで、買い物客がパーカーを購入しようとしている。チェックアウトが一部のユーザーで非常に遅い。別の一部のユーザーでは、チェックアウトできていない。
2. 買い物客が最初に気づくが、同じ 1 分以内に Caldova 自身の監視が検知して、アラートを出す。画面の右側に、Caldova のエージェントが出したアラートが表示される（アラートの呼称は「7 alert」と聞こえますが、音声認識の都合で表記が確定できません）。
3. 画面の下部には、前述のインシデントメモリ、永続的な実行、セキュリティ・評価・ROI の 3 要素が並び、進行に合わせて強調される。まずインシデントメモリが強調され、最初の事実として「アラートがエージェントのストアに記録され、問題が UTC 21 時 49 分に発生した」ことが取り込まれる。
4. 左に Caldova のエージェント（顧客側）、右に、Microsoft 側の環境で動く MCP（発話は「AD intelligent MCP」と聞こえますが、音声認識の都合で表記が確定できません）がいる。両者は、明確な境界のある安全な MCP セッションでつながっている。
5. Caldova のエージェントは、まず自分の環境を調べる。App Service の正常性とエラー、最近のデプロイ、構成変更を確認する。結果は、変更なし、構成のずれなし、デプロイなし、コードのエラーなし。インシデントメモリの左下に、最初の仮説（Caldova のコード、デプロイ、ドリフト）が「除外」として記録される。
6. Caldova のエージェントは、シグナル、リソース、時刻を 1 つのメッセージにまとめて、Microsoft 側へ送る。
7. Microsoft 側では、何かを実行する前に、システムが要求者の認証を確認し、その診断を対象のリソースに対して実行してよいかを確認する。次に、Caldova から送られた証拠を付けて、Microsoft のチケットを自動で起票する。
8. 実行の途中でタイムアウトが 1 回起きる。エージェントは最初からやり直さず、そのステップだけを再実行した。発表者は、これが永続的な実行の働きだと説明した。
9. 結論: West US 2 のサーバーが劣化している。Caldova 側には何も変更がなく、Microsoft も確認した。自然災害により、データセンターのラックの一部で電源が失われている。プラットフォームの障害と確認され、次の手順は別のリージョンへのフェイルオーバーであることが明確。この結論は顧客に共有される。
10. Microsoft の回答は、同じ安全なセッションを通じて、Caldova のエージェントに返される。インシデントメモリでは、仮説が「Caldova のコード」から「プラットフォーム障害」に変わり、確認済みになる。障害番号は Z123456。事実は変わらず、障害番号が応答に含まれる。
11. Caldova のエージェントは、その障害番号を使って次の質問をする。「影響範囲（ブラスト半径）、つまり影響を受けたサブスクリプションとリソースの数」を問い合わせる。Microsoft の回答は、3 つのサブスクリプション、約 80 のリソース。Caldova は推測せず、障害番号を指定して詳細を求めた。
12. これで、チケットを開いたり、1 つのダッシュボードを探し回ったりせずに、最初にフェイルオーバーすべきワークロードが分かる。Caldova のエージェントの画面には、障害番号、障害のあるリージョン、影響を受けたサブスクリプション数、結論が表示される。Caldova 独自のランブック（Microsoft が結論を出したとき何をするか）も表示される。
13. エージェントはここで止まる。フェイルオーバーを提案するだけで、承認はできないためである。人間が判断し、承認して初めて、すべてのサブスクリプションとリソースが移行される。
14. 緑のシグナルを鵜呑みにせず、買い物客が実際にチェックアウトできるか確認する。移行が終わると、買い物客はパーカーのチェックアウトに成功する。

なお、デモのあとに Sai 氏が、3 つの要素（インシデントメモリ、永続的な実行、セキュリティ・評価・ROI）をそれぞれ開いて詳しく説明しました（5.5〜5.8）。

## 7. 注意点・発表者の気付き

- **エージェントの境界と実行系は分けます。** 機微なデータや顧客データは、LLM や最終的な利用者に渡したくないためです。
- **生のログを大量にコンテキストへ入れません。** 1 万行のログでエージェントは失敗し、100 万行なら時間内に処理できないか幻覚を起こします。決定論的な処理で必要な回答だけを返します。
- **スキーマが正しくても、実行してよいとは限りません。** 構造の検証と、呼び出したユーザーの権限の確認は別のものです。
- **自信は許可ではありません。** 実行の可否はポリシーと人の承認で決めます。
- **ROI の数値は推定であり、実現した削減ではないと明示します。** 例の 30 分 × 10 件 = 5 時間は、手作業換算の目安です。
- **コンテキストを広げても、解決にはなりません。** キャッシュには役立つかもしれませんが、何が関連するかも、インシデントの現在の姿も維持されません。
- 自動化の価値は、誰が対応するかによって対応品質がばらつく問題をならすことにもあります。
- 最初の一歩は、モデルではなく、繰り返される作業の選定です。

## 9. まとめ

Azure Engineering Operations は、重大インシデントが前年比 82% 増えたなかで、採用を増やすのではなく、原因の根本対策とエージェントによるトイルの肩代わりを選びました。作ってみて分かった課題は、モデルの性能ではなく、永続的な実行、インシデントメモリ、セキュリティ・評価・ROI の 3 点でした。エージェントは推論に専念させ、データの取得と統制は決定論的な実行エンジンに任せ、信頼できる事実は上限のあるインシデントメモリに置く、という分担が設計の核です。

結果として、高重大度インシデントの緩和時間は半分以上短縮され、RCA の下書きは数秒になり、顧客満足度は 4.92 を保ちました。発表者の助言は、まず繰り返しの作業を 1 つ選び、範囲を限定し、ガードをかけ、測定することです。
