# THR963 From one automation to many: GitHub Agentic Workflows at scale

## 1. はじめに

このセッションは、エージェントを増やすのではなく、信頼できるプロセスを作り、それを数千のリポジトリへ広げる方法を扱った発表です。前半では、1 つのチームで信頼できるプロセスを作る「チームのファクトリー」を、GitHub Agentic Workflows を中心に紹介しています。後半では、企業全体で何がどこで動き、いくらかかっているかを統括するための研究プロトタイプ、Central Agentic Ops を説明しています。最後には、Azure DevOps の利用者や実行環境に関する質問への回答がありました。

発表の出発点は、エージェントが好きなだけコードを書けるようになった今、難しいのは「エージェントが作ったものを信頼すること」、つまり何に触れてよいか、誰が最終的に承認するかだ、という認識です。

## 3. 何に関する発表か

発表は 2 つの「ファクトリー」という考え方で進みます。1 つ目は、チームが 1 つのリポジトリ、または少数のリポジトリで回すプロセスを、人とエージェントが信頼して使える状態にすることです。2 つ目は、そのプロセスを企業全体に広げることです。エージェントを足すだけでは企業に広がらない、人間が主導権を持ち、信頼できるプロセスを作るべきだという立場です。

流れは次のとおりです。

1. 既存のプロセス（プルリクエスト）にエージェントを組み込む例
2. エージェントがあって初めて可能になった新しいプロセス（毎日のコード改善）
3. GitHub Agentic Workflows の仕組みと、安全性の設計
4. 重複コード検出のワークフローの例（スライド上のサンプルと、実際のプルリクエスト）
5. 企業全体への展開（Central Agentic Ops）
6. 始め方のまとめと、質疑応答

## 4. 発表者が伝えたいメッセージ

冒頭の引用は「エージェントを増やすな。信頼できるエージェント型のプロセスを作れ」という趣旨です。登壇者は、エージェントを電動工具にたとえています。変更を提案し、コードを作ってくれる道具ですが、目標、境界、レビュー、最終結果の責任者を決めるのは人間と開発者の役割だと述べました。目標は、意図をコードに変えることだけでなく、信頼できるプロセスを設計することです。

## 5. 発表内容の詳細

### 5.1 チームのファクトリー：既存プロセスにエージェントを足す

Peli 氏は、プルリクエストを例にしました。開発者がコードを書いて別の開発者に引き渡す、日常的なプロセスです。GitHub にはドラフトモードがあり、共有する準備ができていないことを示します。「レビューの準備完了」を押すと、見てもらいたいという意思を伝えます。このイベントを起点にエージェントを実行できる、という説明です。

- GitHub に組み込まれているエージェント：Code Review、Dependabot、Secret Scanning など
- 自作のエージェント：コード品質、テスト指標、コンプライアンスなどの確認

これらがプルリクエストにレビューコメントを生成します。次に「sous chef（副料理長）」と呼ぶエージェントが、フィードバックを集めてプルリクエストを自動で修正します。修正後、レビューする側が再度レビューするという循環ができ、全員が合意した時点でコードが開発者に戻り、開発者が流れを締めくくります。これは既存のプロセスをエージェントで拡張したもので、「人とエージェントのプロセス」と呼ばれています。

### 5.2 エージェントがあって初めて可能な新しいプロセス

ソフトウェアを書けば技術的負債は溜まり、望むと望まざるとにかかわらず低品質なコードが入り込む、と登壇者は述べました。そこで、毎日エージェントが悪いコードや技術的負債を探して取り除くパターンを作ったと説明しています。例えば重複コードを探し、リファクタリングし、テストを追加して、開発者がマージできる、小さく的を絞ったプルリクエストを作ります。翌日は別の重複を見つけます。これを **デイリーコードインプルーバー** と呼んでいます。エージェントがなければできなかったプロセスで、ファクトリーを自己修復・自己修正させるものだという位置付けです。この種のプロセスは、GitHub Workflows を基盤として構築されています。

### 5.3 どこから適用するか

最初は、多くの人が日常的に持っている普遍的なパターンで、慣れた領域から始めるよう勧めています。ドキュメントの更新、重複コード、モダナイゼーション、セキュリティなどです。ただし Alejandro 氏によると、顧客からは「自社向けにカスタマイズしたい」という要望がよくあります。そこで使うのが GitHub Agentic Workflows です。

### 5.4 GitHub Agentic Workflows の仕組み

まず、意図とガードレールを自然言語で書きます。良い状態がどういうものかを記述する、典型的な Markdown ファイルです。それを、すでに信頼している基盤である GitHub Actions 上で実行します。エージェントは制御された信頼できる環境、つまりサンドボックスの中で動きます。

### 5.5 安全性の設計

Peli 氏は、安全性は基盤であり、すべてがそこから始まると説明しました。エージェントについては、まず「制御を失った、敵対的なもの」と想定し、その前提でセキュリティを組み立てるとのことです。エージェンティックワークフローでは、設計による安全性、多層防御、ガードレールが得られます。

1. 信頼できない入力のフィルタリング。Web ページや issue には敵対的なコードが含まれる可能性がある。
2. コンテナーまたはマイクロ VM によるサンドボックスでエージェントを実行する。
3. エージェントからすべてのシークレットを取り除く。見えなければ漏らせない。
4. エージェントには読み取り専用のトークンだけを見せる。被害範囲を小さくするための多層防御の一部。
5. エージェントによる書き込みは、すべてガードレールをかけて監査する。エージェントは読み取り専用の世界にいて、例えば issue を作りたいという意図を伝える。その内容を、決定論的なツールとエージェントによる脅威検出で確認する。これらを通過して初めて書き込みが適用される。

開発者に教えられる、理解して信頼できる考え方であり、安全がなければイノベーションもないというのが登壇者の言葉です。

### 5.6 サンプル：重複コード検出

登壇者は、重複コード検出のワークフローを疑似コードで見せました。スライドには次の要素が示されています。

- スケジュール（いつ実行するか。この例は毎日）
- 読み取り（エージェントがアクセスできる範囲）
- セーフアウトプット（書き込める範囲）。これらは別々のジョブで実行される
- エージェントが何をするか（意図とガードレール）

信頼できる GitHub Actions 上で動くため、成果物、ログ、オブザーバビリティなど既存の利点がそのまま使えます。エージェントには専用のジョブがあり、次に脅威検出、最後にセーフアウトプットで実際の書き込みが行われます。**エージェントには書き込み権限が一切なく**、トークンがエージェントの中に入った時点でそのトークンは侵害されたものと見なす、という考え方です。

実際のプルリクエストの例では、行を追加するのではなく削除していました。重複コードが検出された箇所、行数、関数が示されています。

### 5.7 企業への展開：Central Agentic Ops

チームで機能したものを、会社全体でどう価値のあるものにするかが課題です。ドキュメント、テストなどの共通パターンはあっても、企業としては、何がどこで動いているか、そして何よりコストをどう制御するかという中央の監督が必要です。そのため作っているのが Central Agentic Ops です。研究プロトタイプで、現時点では製品ではありません。（略称は、音声認識で「CAO」「COW」「Cal」などと聞こえ、表記が確定できません。以降は Central Agentic Ops と書きます。）

背景は、企業にはチーム単位の問題だけでなく、セキュリティ、モダナイゼーション、ドキュメントのように全社で中央から適用したい問題もあるという観察です。これは GitHub Agentic Workflows の上に構築されています。

**仕組み。** 1 つのリポジトリに、ディスパッチャー（オーケストレーター、キャンペーンの司令塔）となるエージェントを置きます。このエージェントが、たとえばセキュリティ対応をどのリポジトリで行うかを決めます。10 個のリポジトリを選んで 10 個のエージェントを割り当てることも、1,000 個に広げることもできます。ディスパッチされるワーカーは GitHub Agentic Workflows です。目標とワーカーを定義し、ワーカーが作る issue、プルリクエスト、コメント、ラベルは、セーフアウトプットで定義します。ワーカーはすべて GitHub Agentic Workflows なので、同じセキュリティ基盤の上で動きます。

**最適化。** 仕事の量は通常、予算を超えます。そのためキャンペーンはテレメトリを送り返し、そのデータを分析して、エージェントが使うトークンを減らし、運用上の価値と成果を高めるよう最適化します。登壇者は、1 つのプロンプトから、数十万のリポジトリにまたがるキャンペーンを定義できるようにすることを目指していると述べました。

**キャンペーンの定義。** 重複コードのキャンペーンの例が示されました。構成は、スケジュール（たとえば毎時）、認識（どの MCP サーバーを対象にするか。Central Agentic Ops 自体を対象にして、将来の実行でワークフローを最適化できるようにする）、セーフアウトプットによるガードレール（キャンペーンがディスパッチしてよいもの）、そして自然言語で書いた目標です。

**画面と運用。** 登壇者は、これは研究プロトタイプで UX は最終版ではないと断りました。1,000 から 10 万のリポジトリの規模では通常の UX が通用せず、動いているか、価値を生んでいるか、いくらかかるか、どこで介入して最適化すべきかを知る必要があります。Azure Monitor との統合も予定していると述べています。スライドには、グレーダー（採点）やファクトリーの健全性などの指標が表示されていました。オペレーターを圧倒せず、介入すべき場所を示すことが狙いです。

**コストの最適化。** トークンを多く使っているキャンペーンやエージェントを把握すれば、「デイリーエージェントインプルーバー」のようなものを作れます。毎日、ファクトリーで最もトークンを消費しているエージェントを選び、エージェント型の最適化を実行して理由を調べます。設定の誤り、大きすぎるモデルの使用、効率を上げる MCP の不足などが原因として挙げられました。毎日改善することで、企業全体でより多くのエージェントを動かせるようになります。

**更新。** デプロイしたワークフローを保守するため、エージェント群の更新とアップグレードも組み込んでいます。CI/CD の世界は以前は動きが遅かったものの、エージェントの世界は速く、毎月新しいモデルが出て、それぞれが特定のバージョンのエージェント CLI と結び付いているため、常にアップグレードが必要です。これは、企業でエージェントを大規模に運用し保守する「Agentic Ops」の一部として取り込んでいると説明しています。

### 5.8 始め方

1. 1 つのチームと、信頼できる 1 つのプロセスを選ぶ。
2. GitHub Agentic Workflows で構築し、実行を観察して最適化する。
3. 完成したら、中央の Central Agentic Ops を導入して企業全体に広げる。
4. エージェントを観察し、最適化し続ける。トークンを多く使うものや失敗の多いものを調べ、自己最適化に取り込む。

GitHub Agentic Workflows は **一般提供されている** ため、QR コードから利用でき、開発チームのリポジトリには多くの構築例があります。Central Agentic Ops は研究プロトタイプで、GitHub Pages を使ってローカルにデプロイし、自社でどう見えるかを確認できると説明しています。

### 5.9 Q&A

**Q. Azure DevOps（ADO）を使っているが、この中でどう位置付けられるか。**
ADO の issue を利用してアクションを起動するコネクターがあります。連携のさせ方次第で使える方法の 1 つ、という説明でした。ソースとパイプラインも ADO で運用している場合は、GitHub Next の組織にある研究プロトタイプ ADO-AW があります。GitHub Agentic Workflows の兄弟にあたり、Markdown のファイル、フロントマターのガードレール、意図、同じセキュリティの考え方を持ち、パイプライン向けに作られています。オープンソースで公開されていますが、現時点では製品として一般提供されていません。

**Q. エージェントはワークフローのコンピュートで動くが、Azure Container Apps のサンドボックスに処理を移すことは検討したか。**
GitHub Actions に備わるコンピュートを使っています。Azure も支えるマイクロ VM 技術上で動いており（音声認識の都合で技術名は確定できません。「NVX」と聞こえます）、同水準のセキュリティがあります。さらに、企業向けにはセルフホステッドランナーを持ち込んで自社のコンピュートで動かせます。Actions のフレームワークを使っているため、VM かランナーを差し替えるだけで済みます。

**Q. エージェンティックワークフローはどこに置くのか（別の聴衆からの質問）。**
通常のワークフローは各リポジトリにあります。Central Agentic Ops では、すべてのワークフローが Central Agentic Ops のリポジトリにあり、そこから中央でディスパッチして実行します。何かをデプロイする必要はなく、必要なトークンを持つ、DevOps チームが所有する 1 つのリポジトリにすべてがあります。会社全体でワークフローのフリートを保守するのは困難だという声を聞き、中央に 1 チームで扱える形にしたと説明しました。

## 7. 注意点・発表者の気付き

- Central Agentic Ops は研究プロトタイプで、UX は最終版ではありません。
- GitHub Agentic Workflows は一般提供で、ADO-AW も研究プロトタイプ（オープンソース、製品としては未提供）です。両者の提供状況は異なります。
- エージェントにトークンを持たせない、書き込みはセーフアウトプットを通す、という設計が安全性の核です。
- 仕事の量は予算を超えがちで、コストの把握と最適化が欠かせません。
- 新しいモデルが毎月出て、エージェント CLI のバージョンと結び付くため、フリートを継続的に更新する必要があります。

## 8. 利用者にとっての利点

- 既存のプルリクエストのプロセスに、レビュー用エージェントと自動修正を組み込めること。
- 毎日の重複コード除去のような、自己修復するプロセスを作れること。
- 意図を Markdown と自然言語で書き、GitHub Actions の成果物、ログ、オブザーバビリティをそのまま使えること。
- セルフホステッドランナーで自社のコンピュートで実行できること。
- 数千のリポジトリへの展開と監督を、中央の 1 つのリポジトリで扱える方向性（プロトタイプ）。
- 発表では、顧客事例の成果や削減率などの具体的な数値は示されていません。

## 9. まとめ

エージェントを増やすのではなく、信頼できるプロセスを作ることが主張の核です。1 つのチームで 1 つのプロセスを GitHub Agentic Workflows で構築し、サンドボックス、シークレットの排除、読み取り専用トークン、セーフアウトプットによる監査で安全を確保します。そのうえで、研究プロトタイプの Central Agentic Ops を使って、企業全体への展開、コストの最適化、更新を中央から行うという構想が示されました。
