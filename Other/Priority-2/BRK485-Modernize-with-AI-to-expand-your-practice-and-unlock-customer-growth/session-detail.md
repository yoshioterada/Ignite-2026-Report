## 5. 発表内容の詳細

### 5.1 冒頭：優先課題とプラットフォームの考え方（Mayank 氏）

最初に Mayank 氏は、パートナーが顧客のモダナイゼーションとイノベーションを支援するうえで、信頼と運用の回復力（レジリエンス）が重要だと述べました。そして、今週の冒頭で Satya Nadella 氏から話があった先週の出来事に触れ、Microsoft はこれを重く受け止めていると説明しています。出来事の具体的な内容は、発話では説明されていません。Satya 氏の方針として、機能とセキュリティや品質のどちらを優先するか迷ったら、セキュリティと品質を優先すると紹介されました。

Microsoft が営業、コンテンツ、マーケティングを通じて顧客と話す際の軸は、次の 3 つです。

| 軸 | 発表での説明 |
|---|---|
| エージェント | エージェント中心の将来に向けて、サプライチェーンから人の時間まで大きな投資が行われている |
| セキュリティ | エージェントを守ることが極めて重要。Microsoft が出荷するパッチ数は過去最多で、AI を使って AI に対する防御を固めているため。製品チームが AI で環境への侵入を試み、その後に修正方法を見つけるレッドチーム／ブルーチームの演習も行われている |
| コスト | 業界全体でコストが意識されている。Microsoft 自身も、支出をエージェント中心の将来の構築に優先配分している。顧客やパートナーにとっても、コストの合理化が必要 |

セキュリティについては、Microsoft の規模と力で製品を守る水準は、個々の組織が単独で実現できるものではないという説明でした。そのため「この領域は Microsoft に任せてほしい」という姿勢で顧客と話すそうです。

#### 飛行機のたとえ

Mayank 氏はエージェントを飛行機にたとえました。1 機を着陸させるなら滑走路、空港を作って着陸させれば済みます。しかし 15 機を着陸させる場合、15 本の滑走路と 15 のターミナルを作る人はいません。1 つの空港を作り、そこにすべての飛行機を着陸させます。AI を大規模に動かすプラットフォームも同じ考え方で作るべきだという説明です。

#### IQ レイヤーと共有ランディングゾーン

画面に示された構成では、最上位にエージェントがあり、その下に「知性と信頼のレイヤー」である IQ レイヤー、さらに共通の基盤があります。

- **IQ レイヤー**：エージェントを企業の知識に結び付ける意味的な文脈を担います。このレイヤーを作らないと、データについて学習していないエージェントが正確さを出すために何度もクエリを投げることになります。クエリが増えればトークンが増え、計算量とコストが増え、ユーザー体験が悪くなります。この点は McKinsey の調査でも、Microsoft の経験でも確認されていると述べました。「今投資するか、後で支払うか」の違いです。
- **共有ランディングゾーンへの同居**：すべてを共有のランディングゾーンに置くと、遅延が減ります。長い処理ループで余計な計算を使わないため、コストも下がります。個々のエージェントごとではなく、1 回の対策でセキュリティを確保できます。共有サービスのモデルになるという説明です。
- **データの所在**：エージェントが使うデータの 70% は、SQL のような運用データベースにあります。

Mayank 氏は、経営層に技術の話をする際、この構成を使って「この進め方では失敗する」とあえて伝えているそうです。後になって「なぜもっと強く言ってくれなかったのか」と言われた例が数多くあるためです。

#### モダナイゼーションの最大の競合は「何もしないこと」

プラットフォームのモダナイゼーションは、いつも「何もしない」という最大の競合に直面してきました。予算がない、工数が大きい、他に優先事項がある、人も資源も足りない、といった理由です。Mayank 氏は、AI でこれがずっと簡単になったと述べています。

Microsoft 社内の例として次の 2 件が挙がりました。

- Teams の .NET 8 へのアップグレード
- Xbox のコードベースのアップグレード

どちらも作業の 80〜90% がエージェントによって行われ、大きなチームが数か月かけていた作業が、数週間から数時間で終わったということです。大手コンサルティング会社や保険会社でも、エージェント型ツールでモダナイゼーションが行われ、コスト、時間、工数、正確さのすべてが良い方向に向かっていると紹介されました。

#### Azure Catalyst の発表

Mayank 氏は、今週発表された **Azure Catalyst** を紹介しました。Azure Migrate の移行エージェントと、GitHub Copilot のモダナイゼーションエージェントを 1 つの仕組み（エージェントの実行基盤）にまとめたものです。

| 構成要素 | 役割（発表での説明） |
|---|---|
| 移行エージェント（Azure Migrate 側） | 検出、計画、IT 資産の把握。何がモダナイズ可能か、移行可能か、準備がどの程度できているかを見る |
| モダナイゼーションエージェント（GitHub Copilot 側） | コードベースのモダナイゼーションそのもの |

Azure Catalyst は、すでに Microsoft のファクトリー（支援組織）や一部のパートナーを通じてプレビュー、試行されていると述べました。

### 5.2 TCS の取り組み：agentic SDLC（Varun 氏）

Varun 氏は、アプリケーションのモダナイゼーションは生成 AI の最も費用対効果が高いユースケースの 1 つであり、AI を大規模に採用するための準備にもなると述べました。AI エージェントは、組織のアプリ、API、ナレッジにつながる必要があるためです。

現場で見えた、顧客が解決したい課題は 4 つあります。

1. **モダナイゼーションの典型パターン（アーキタイプ）**：例えば .NET 2 のアプリを .NET 10 に上げる技術アップグレードが必要な場合もあれば、モノリシックなアプリをマイクロサービスに変換したい場合もあります。アプリが取れる経路を明確にしたいという要望です。
2. **複数提供元のエージェントの協調**：顧客は、GitHub Copilot のモダナイゼーションエージェントに加えて、Angular から React への変換を行う自作エージェントも使いたいと言います。Microsoft、TCS のような GSI（グローバルシステムインテグレーター）、顧客のエージェントが連携できるプラットフォームが必要です。
3. **モダナイゼーションの記憶**：作業中には、たとえばファイル共有上のファイルにエージェントが権限不足でアクセスできない、といった問題が起こります。こうした情報をチェックポイントで拾い、フィードバック用のエージェントがナレッジリポジトリに蓄積すれば、次回は同じ問題に遭遇しないか、遭遇してもエージェント自身が対処できます。
4. **エージェントのガバナンス**：信頼、信頼性、セキュリティ、ID、FinOps（クラウド費用管理）、ROI（投資対効果）です。

これらに応えるために TCS が開発したのが **TCS agentic SDLC** です。Azure Migrate と緊密に統合され、GitHub Copilot のモダナイゼーションエージェントを展開します。機能は次の 3 点です。

- 既存アプリを理解し、適切なモダナイゼーションの経路へ導く
- 顧客が自分のエージェントを組み込める
- ガバナンスと記憶を伴ってモダナイゼーションを実行する

#### 進め方の例（データセンター撤退）

Varun 氏は、データセンターから撤退したい組織を例に説明しました。

1. Azure Migrate を立ち上げ、プラットフォームの検出などを行う。
2. アプリの約 80% を非常に速く移行することを目標にする。この部分は Azure Migrate のエージェントと既存のツールを使う。
3. モダナイズしたい残りの約 20% のアプリに、TCS agentic SDLC を導入する。
4. TCS agentic SDLC が GitHub Copilot のモダナイゼーションエージェントを展開する。TCS 独自に開発したエージェントも使い、顧客が自分のエージェントを組み込むこともできる。

顧客が得られるのは、構築済みのモダナイゼーションのアーキタイプ（既存資産のほぼすべてをカバー）と、**30〜50% の工数削減**です。AI をより採用しやすい状態になり、Frontier になるという説明でした。Azure Migrate、TCS agentic SDLC、GitHub Copilot のモダナイゼーションエージェントの 3 つを組み合わせて、多数の飛行機を同時に着陸させられるプラットフォームにするという位置付けです。TCS agentic SDLC のデモは TCS のブースで見られると案内されました。

### 5.3 ReadyWorks の取り組み（Andrew Sweeney 氏）

ReadyWorks の CEO である Andrew 氏は、同社の歩みを話しました。1990 年代後半にサービス組織として、大手銀行や金融サービス向けにインフラのプログラムを手掛けて始まりました。2020 年にその知見をソフトウェアにしようと考え、Credit Suisse から シリーズ A の資金を調達して SaaS プラットフォームを作りました。しかし AI の登場で状況が変わり、昨夏に シリーズ B を調達して、サービスと SaaS の経験を AI プラットフォームに変換しているところです。取り組みは約 6 年になります。

この経験から得た教訓として、次の点が語られました。

- **脅威ではなく機会**：同社にとっては、AI は「自社の居場所がなくなる」という存在脅威に見えたそうです。Copilot と ServiceNow だけが残って他は市場から消えるのではないかという不安です。しかし 1 機でなく 15 機、50 機、100 機を着陸させる段階になれば、サービスプロバイダーの居場所は確実にあるという結論に至りました。企業向けのプラットフォームは、午後に作れるバイブコーディングのデモとは別物で、大規模に動かすには作り込みが必要です。
- **車輪の再発明をしない**：変化が非常に速いため、ペースを保つことが最も重要です。Catalyst をゼロから作り直すのではなく Catalyst を使い、他の提供元のツールも使い、その周りに自社の枠組みとサービスを載せることが勝ち筋だと述べています。
- **自社の差別化はナレッジ**：自社のやり方を、構築した基盤の上に載るプレイブック（手順書）に落とし込んだことが成功につながったそうです。
- **パートナリング**：18 世紀に号砲とともに皆が土地を取りに走った出来事にたとえ、今は未開拓の領域で、重要なのはスピードだと話しました。同社には、自社のプレイブックを販売するパートナー、同社のプラットフォーム上に自分のプレイブックを載せるパートナー（それを同社が販売）、エージェントを持つパートナー（同社が統合して販売）がいます。
- **企業では「旅」になる**：1 年以内にすべてが AI で動くことにはならず、10 年規模の旅になるという見方です（本人も、人気のない意見だと述べています）。2027 年に向けた社内への指針は、2027 年に実際に解決できる問題に足掛かりを作ることです。すべてを外部委託してエージェント AI に載せることも、来年に American Express を動かす完全自律のインフラを作ることも起こらないという例が挙げられました。
- **移行案件を入り口にする**：すでに予算が付いているプログラムの代表が移行です。人手で賄う代わりに AI で行おうと事業リーダーに提案し、移行を AI で届ければ、それを継続収益（アニュイティ）にできるという考えです。今やコードは堀（競争優位）ではなく、堀は企業に入り込んでいること、つまり契約、セキュリティアーキテクチャ、統合、関係者の合意といった「惰性」だと述べました。
- **例：VMware からの移行**：Broadcom の動きにより、5 年以内にどの企業も VMware から離れるだろうという見方を示しました。AI で VMware からの脱出を行うと、ServiceNow、VMware、Azure、Intune など必要な各システムと統合されるので、それが橋頭堡になります。先に入り込めば未開拓領域を取れます。

まとめとして Andrew 氏は、顧客が資金を出す移行で価値を証明し、AI がデモ以上のものを企業規模で提供できることを示したうえで、データベースのモダナイゼーション、アプリのモダナイゼーション、データセンターやローカル SQL、Oracle から Azure への移行など、追加のユースケースを素早く獲得することを勧めました。小さな事業者にも勝つ機会があり、この分野に携わるうえで今が最高の時期だと述べています。

### 5.4 Azure Catalyst の構成とパートナーの収益（Barry Wardell 氏）

Barry 氏はまず、AI アプリと AI ワークロードのセキュリティとレジリエンスは、ワークロードがモダナイズされているほど高まると強調しました。モダナイゼーションがなければ AI の到達点は限られ、むしろリスクが増える場合もあります。

#### Azure Catalyst とは

Azure Catalyst は現時点で、Azure Migrate の一部である Azure Copilot の移行エージェントと、GitHub Copilot のモダナイゼーションエージェントで構成されています。ただし、単なる 2 つのエージェントの寄せ集めではなく、世界の変化が速いため、毎日モダナイゼーションのエージェント機能に多額の投資を続けていると述べました。

特徴は、つながった 1 つの体験であることです。バラバラのツールも、新たな権限やグループ設定も、行き来する手間もありません。顧客の環境全体（インフラ、データ、アプリケーション、コードまで）を俯瞰できます。説明された機能は次のとおりです。

- グラフ構造の依存関係マップ
- ROI や TCO（総所有コスト）の表示（ビジネスケースの作成を支援）
- Azure ランディングゾーンの推奨
- 実際の移行の実行
- コードの分析、リファクタリング、モダナイゼーション。特にコードのセキュリティ（脆弱性の検出）に力を入れており、人が判断に関わる方式で、修正するかどうかを開発者に尋ねる
- コードのレジリエンス（Azure で安全に動かすための書き方）

Barry 氏は、パートナーとの摩擦を生むことが目的ではなく、パートナーがすでにファクトリーに多額を投資していることを理解していると話しました。目指すのは共生と補完の関係です。パートナーがすでにエージェント型 AI のファクトリーを持っているなら、それを組み合わせます。

#### パートナーの収益試算

Microsoft は、実際の案件サンプルを使った調査を行い、パートナーにとっての案件の姿を示しています。画面には、アドバイザリーとデプロイメント、ソリューション開発、マネージドサービスの付随率（アタッチ率）が示されました。マネージドサービスは継続的な収益であり、中核になるという説明です。

具体例は次のとおりです。調査に基づく、ACR（Azure の消費収益）が 150 万ドルの案件を想定すると、パートナーにとっての機会は約 200 万ドルになります。その内訳はマネージドサービス（継続収益）、ソリューション開発、その他の追加です。さらに、販売前と販売後に対して、Frontier Accelerate からの投資も用意されています。

### 5.5 対談：Accenture の事例（Frederico 氏と Brendan 氏）

Frederico 氏の司会で、今年のモダナイゼーション部門のパートナーアワード受賞者である Brendan 氏が、Accenture の見方を話しました。

#### 市場の見方

「クラウドに移るべき企業はすでに移った」という見方（アナリストや営業担当から聞く）は、パイプライン、売上の伸び、Microsoft から得るテレメトリから見て、まったく正しくないと述べました。多くの顧客は AI への野心が大きい一方で、まだサーバーやデータベースをオンプレミスに持ち、それが AI の取り組みを止めています。

そのため Brendan 氏は、移行とモダナイゼーションは全盛期にあると話しました。理由は、ここ 1 年から 1 年半で経済性が大きく変わったことです。従来は、数千から数百万行のコード、仕様もドキュメントもなく、コメントも不十分で、書いた人はすでにおらず、保守担当も半分程度しか理解していないアプリが多く、モダナイズは複雑でした。いまは次のことが 1 日でできます。

- 数百万行のコードを分析する
- 機能要件と仕様をリバースエンジニアリングする
- 必要なら新しい言語に変換する
- ネイティブサービスへモダナイズする

数年前に始まったものの複雑すぎて止まっていたモダナイゼーションも、動き出しているそうです。同社が推進する ACR は、直近 1 年で 45% 増えました。

#### 事例：大手医療機関の Epic 移行

Brendan 氏は、医療サービス組織の事例を紹介しました。夜中 3 時に看護師が患者記録を開き、医師が薬を確認する、その一連が Epic（医療機関向けの電子カルテシステム）を経由します。非常に複雑で、おそらくクラウドへ載せるのが最も難しい医療システムだと述べています。

| 項目 | 内容 |
|---|---|
| 規模 | Epic のインスタンスが 3 つ、移行対象の環境が 50、統合が 1,000 以上、技術が 70 以上 |
| 顧客からの要件 | 患者のケアを妨げずに移行し、移行後は以前より安全にすること |
| セキュリティの取り組み | プロジェクトの成果として最初から組み込んだ。あらゆる場所で多要素認証を有効化。ゼロトラスト環境を 150 設定。ペネトレーションテストを 14 回実施し、72 万件の脆弱性を見つけて修正 |
| 期間 | 3 年の計画だったプロジェクトを 18 か月で完了 |
| 結果 | 稼働率 99.969%。看護師や医師向けの応答性の基準をすべて超え、厳格なセキュリティ指標も大きく上回った |

期間短縮の要因は、プロジェクトの早い段階で AI ツールと移行エージェントが力を発揮し始め、チームが素早く適応してツールを使いこなせたことだと述べています。結果は Azure と、使えたツールやフレームワークのおかげだという説明でした。

#### モダナイゼーション成功の 4 つの要素

Frederico 氏の問いに、Brendan 氏は 4 点を挙げました。

1. **旅として扱う**：「サーバー 1,000 台を移行したい」と言われると、プロジェクトとして扱いがちです。しかし顧客の立場に立ち、計画、ランディングゾーンの構築、サーバー移行、環境のモダナイズ、その上で構築する AI とエージェントまでを 1 つの旅と考えます。その下には、セキュリティ、FinOps、ソブリンティ（データ主権）のガバナンスを見るオーケストレーション層が必要です。引き合いは RFP やプロジェクトの形で来ても、全体像を想像することが重要です。
2. **工業化する**：繰り返し使える資産を作ります。業界が違っても共通点があるため、共有サービスチームがテンプレート、ツール、資産を作り、何度も同じ作業をこなして習熟します。案件が来たとき、「前にやったことがある、良いツールがある」と言える状態を目指します。
3. **データに集中する**：アプリだけをモダナイズしてデータをモダナイズしなければ半分しか終わらず、AI は機能しません。同社にとって Fabric は中核で、AI のエコシステム全体を動かす魔法のようなツールだと述べました。Fabric は、すべてを Azure に入れる必要はなく、オンプレミスや他のクラウドの場所にあるデータも扱えます。データの整理、ガバナンス、安全性を担う不可欠なオーケストレーション層であり、その上に AI を構築します。
4. **適切な作業を適切な場所に置く**：Microsoft の Cloud Accelerate Factory（略称 CAF）を活用することです。Accenture は CAF の最大の利用者で、他のどのパートナーよりも多くの作業を渡しています。当初は、自社がやっていたはずの作業を CAF が行うことに戸惑いがあり、デリバリーチームが納得して統合するまでに時間がかかりました。いまはそれを乗り越え、さらに活用を倍増する計画です。CAF 自体も機能とワークロードを広げています。深い業界知識を要する作業は自社が担当し、Azure Migrate に IP アドレスを読み込んでボタンを押すような作業は CAF に任せます。CAF は速く、パートナーにも顧客にも費用がかからないと述べました。

### 5.6 締めくくり：次の 4 つの一歩（Frederico 氏）

Frederico 氏は、パートナーへの次の一歩として、次の 4 点を挙げました。

1. **チームを訓練する**：今月後半から会計年度の残りの期間に、今週発表したソリューション（まず Azure Catalyst）の提案と展開方法を学ぶスキル習得イベントが開催されます。
2. **自社の強みを持ち込む**：知的財産、専門性、つまり各社の IQ が差別化の要因です。
3. **需要を作る際に Microsoft のツールを使う**：Azure Catalyst はエージェント環境のモダナイゼーションを速めます。
4. **自分たちが最初の顧客になる**：Azure Catalyst を知らなければ、今すぐ試してください。

イベントの案内と、午後のブースでの再会の呼び掛けで終了しました。

## 6. デモ・手順

ライブのデモではなく、Barry 氏が約 2 分の**録画された動画**（ナレーション付き）を上映しました。架空の企業「Caldova Pharma」を題材に、アプリケーションのモダナイゼーションを Azure Catalyst で進める流れが示されています。画面の細部は音声からは確認できず、ナレーションで語られた範囲だけを記します。

1. Caldova Pharma は、アプリケーションのモダナイズ、コスト削減、レジリエンス向上を目指している。Azure Catalyst はこれを、検出と設計から実行まで 1 つの連続した流れにする。
2. 構成データから始め、チームが依存関係を確認する。この種の分析は通常、手作業で数週間かかる。Caldova はアプリ中心の資産ビューを得て、インフラ、データベース、アプリの変更を併せて計画できる。
3. Catalyst がビジネスケース、準備状況、セキュリティの検出結果、目標アーキテクチャを集約する。経営層は、何をモダナイズし、なぜ重要で、どこから始めるかを把握できる。
4. その文脈が設計と実行計画に引き継がれる。Catalyst は、Caldova の要件と Microsoft の Cloud Adoption Framework に基づいてランディングゾーンを推奨する。
5. Asset Manager アプリについて、Azure App Service、Azure SQL Database Hyperscale のエラスティックプール、Azure Files を、アプリとデータ向けの 1 つのアーキテクチャにまとめる。
6. Catalyst が、依存関係、準備状況、工数、業務上の重要度に基づいて作業の順序を決める。Asset Manager は第 1 ウェーブ。
7. 実行ランブックが、インフラ、データベース、アプリの作業を、検証と承認のチェックポイントも含めて調整する。データベースチームは、SQL Server から Azure SQL Database Hyperscale への専門的な移行機能を使い、Catalyst はアプリの変更、依存関係、検証手順と連携させる。
8. IT チームと開発チームは、すでに使っているツールで同じ計画に基づいて作業する。Azure での判断や文脈が、開発者の実行に引き継がれる。
9. GitHub Copilot で、開発者が Azure 向けのアプリ変更をレビューする。変更は Caldova の標準、コーディング作法、セキュリティポリシーに沿う。Copilot がフレームワーク、構成、セキュリティの変更を支援する。開発者は変更を確認し、ビルドを検証し、テストを実行する。
10. 検証後、アプリはデプロイできる状態になり、Azure App Service 上で動いている様子が映る。Caldova は、資産全体に適用できる再現可能な進め方を得た。

> 補足：このほかに、TCS agentic SDLC のデモは TCS のブースで行われると案内されましたが、会場のセッション内では実施されていません。

## 8. 利用者にとっての利点

## 9. まとめ

- AI を大規模に動かすには、1 つの空港のような共通基盤（IQ レイヤーと共有ランディングゾーン）が必要で、モダナイゼーションはその前提になる。
- Azure Catalyst は、Azure Migrate の移行エージェントと GitHub Copilot のモダナイゼーションエージェントを 1 つの体験にまとめた仕組みで、依存関係の把握、ビジネスケース、ランディングゾーン推奨、移行、コードの修正までをつなぐ。
- パートナーは、ツールを作り直さずに使い、自社のプレイブックや業界知識を載せて差別化する。移行のように予算が付く案件が入り口になり、継続的なマネージドサービスにつながる。
- Accenture の成功要素は、旅として扱う、工業化する、データ（Fabric）に集中する、CAF を活用する、の 4 点。
- 次の一歩は、チームのスキル習得、自社の強みの持ち込み、Microsoft のツールの活用、そして Azure Catalyst を自分たちで最初に試すこと。
