# BRK439 Sovereign cloud mythbusters: Separating fact from fiction

## 1. はじめに

このセッションは、ソブリン（主権）クラウドについて顧客からよく聞かれる「6 つの誤解（神話）」を取り上げ、一つずつ検証していく約 45 分のブレイクアウトです。通常のセッションのようなマーケティング用スライドやアーキテクチャ図は使わず、「何が誤解か」「どう解決できるか」に絞って進められました。

進行の特徴は、会場と配信の参加者が QR コードから 6 つの神話に投票し、「Busted（誤りだった）」「Plausible（ありうる）」「Confirmed（正しかった）」の 3 択から選ぶ点です。以下ではこの 3 つの語を原語のまま使います。登壇者は各神話の最後に投票結果を見せ、自分たちの判定と比べていきます。

結論を先に書くと、ソブリン性は単一の製品ではなく、**ワークロードごとに構成する一連の統制**であり、法務部門・事業部門・エンジニアリング部門で話し合って決めるものだ、というのが全体を通した主張です。デモは 2 つあります（Azure Policy による配置場所とキー管理の制限、Customer Lockbox の有効化）。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK439](https://ignite.microsoft.com/en-US/sessions/BRK439)

## 4. 発表者が伝えたいメッセージ

最初に強調されたのは、ソブリン性が**ワークロードごとに構成する統制の集合**であり、1 つの製品ではないことです。setup.exe を実行すれば主権が手に入るようなものではなく、どのプロバイダーが何を売り込んできても同じだと説明されています。

そのうえで、ワークロードを見直す際には、ワークロードを設計・運用するエンジニアリングチーム、要件を持つ事業責任者、規制や国ごとの事情を判断する法務チームを同席させるよう勧めています。登壇者は「自分たちは弁護士ではない（舞台上で演じているだけ）」と断っており、法的な適用範囲は必ず自社の法務チームに確認するよう繰り返しています。

もう一つの柱は「最も軽い構成から始める」ことです。最も複雑な構成にいきなり向かわず、法務・事業部門と照らして要件を満たせるか確認し、満たせるなら軽い構成のほうが実装が速く、運用コストも低く、最新状態も保ちやすいと述べています。

## 5. 発表内容の詳細

### 5.1 ソブリン性を考える 4 つの観点

登壇者は、ソブリン性を考えるときの観点を 4 つ挙げています。

1. **データの所在**：デプロイ先の場所は、ソブリン性の議論の一部（全部ではない）に影響します。デプロイ先を決めるだけでなく、その範囲にデータをとどめる制約やガードレールも設けられます。また Microsoft は EU Data Boundary の尊重を約束しており、Azure だけでなく Dynamics や Microsoft 365 も、その範囲内にとどめられると説明されました。
2. **キーを誰が管理するか**：データが暗号化されているとき、キーの場所と保有者によって、誰がデータを読める・書けるかが変わります。
3. **誰がシステムを運用するか**：サポートチケットを起票したとき、裏側で対応するサービス提供者や基盤の運用者がどこにいて、データにアクセスできるかという観点です。対策として Customer Lockbox、Data Guardian、エージェント向けのスコープ付き ID（スコープ付きエージェント ID）が紹介されました。スライドの一覧は網羅的ではなく、ほかにも多数あると補足されています。
4. **どの規制・依存関係が適用されるか**：国ごと、また医療や金融などの業種ごとの要件です。

### 5.2 神話 1：デジタル主権にはローカルのクラウドプロバイダーが必要

関連する観点は、運用、適用される規制、ワークロードの依存関係です。解決策として、デプロイ形態を 3 つ示しています。

| 形態 | 内容 |
| --- | --- |
| ソブリンパブリッククラウド | パブリックな Azure に、データを所定の場所にとどめ、規制を満たすための制約と統制を加えるもの。例として、会社やサービスを紹介するだけの公開 Web サイトは、完全に分離するほどの労力をかける必要がないかもしれない、と述べられました。 |
| ソブリンプライベートクラウド | Azure Local を Azure に接続して使う、または完全に切断して運用するもの。切断運用の Azure Local も現在あります。Microsoft 365 Local、GitHub Local、ADO Local など多数のサービスが Azure Local の上で動くようになり、Foundry Local も使えます。オンプレミスの完全なエアギャップ（外部から到達できない）環境を想定しています。 |
| 各国のパートナークラウド | 運用担当者も国内にいて分離されている必要がある場合のためのもの。現時点では、フランスの Bleu とドイツの Delos の 2 つです。パートナーが自社のハードウェア上で Azure のバージョンを運用し、顧客はパートナーと契約します。 |

フランスでは SecNumCloud 要件、ドイツでは BSI Cloud 要件がある場合に、それぞれ該当する国のパートナーと話す必要があると説明されました。Microsoft との契約ではなく、パートナークラウドとの契約になる点も強調されています。

登壇者の判定は **Busted** です。ワークロードごとに選択肢を評価し、3 つの形態の組み合わせで要件を満たせるという考えです。トレードオフとして、次の 2 点が挙げられました。

- ローカルのプロバイダー：管轄の面では利点があるが、Microsoft がプロバイダーに提供し、プロバイダーが顧客に提供する構造のため、パブリックな Azure の最新機能に遅れる場合がある。
- 切断運用やオンプレミスの Azure Local：リージョン間の冗長性を失う可能性がある。バックアップ、保守、電力、空調など運用責任が自社に移る。

### 5.3 神話 2：データレジデンシーだけでソブリン性は満たせる

関連する観点は、データの所在とキー管理です。3 つの検討事項が示されました。話者はカナダ人だと述べ、カナダ政府との会話で毎回出る話題だと紹介しています。

1. **ストレージアカウントを物理的にどこに置き、誰がアクセスできるか**：例えばカナダなら Canada East や Canada Central を選べます。ただし、これだけでは足りません。
2. **キー**：データが暗号化されていなければ問題が残ります。顧客管理キー、Key Vault Managed HSM、あるいは任意の HSM（ハードウェアセキュリティモジュール）でキーを保持すれば、データの場所は本質的な問題ではなくなります。復号できるキーを自分が持っているため、誰かが不正にアクセスしても読めないからです。
3. **使用中の暗号化**：保存時は暗号化、通信時も常に暗号化されますが、VM がメモリ上でデータを処理している間は暗号化されていません。これにはコンフィデンシャルコンピューティングを使います。ポリシーで「このワークロードはコンフィデンシャルコンピューティングで動かす」と要求でき、メモリ上のデータまで暗号化されます。コンフィデンシャルコンピューティングだけを扱う別セッションが、翌日に開かれると案内されました。

登壇者は、これを眠っているデータにたとえています。保存時のデータは暗号化していなければそのまま置かれた状態で、キーは「誰が起こしてよいか」を決めるもの、使用中の暗号化が 3 つ目の段階です。

デモの内容は 6 章に記載します。判定は **Busted** でした。ただし次の 2 点が注意として挙げられています。

- Azure Front Door、Traffic Manager、Azure DNS、Azure Policy のように、世界規模で動作し、1 つの地理的範囲に閉じ込められないサービスがある。顧客はそれらにアクセスし、そこから目的の場所へ振り分けられます。
- すべてのサービスが、顧客管理の HSM キーに対応しているわけではない。サービスは順次更新されており、現時点では重要なサービスが対応している。

### 5.4 神話 3：切断（オフライン）運用は常により安全

登壇者は、ハサミでケーブルを切ることが脅威検知だという図で、この神話を紹介しました。関連する観点は運用です。Azure Local を切断状態で使う場合、次の点が負担になると説明されています。

- **パッチ適用**：ハードウェア、ソフトウェア、その上のワークロードの保守は自社の責任になり、更新が遅くなりうる。
- **脅威インテリジェンスと検知**：Microsoft が大量に得ているシグナルを使えず、新たな脅威や攻撃者の検知を自社で担う。
- **障害復旧と監視**：Azure Local はクラスター構成で一定の冗長性と復旧機能があるが、1 つのデータセンターの外まで含めて期待どおり動くよう、自社で計画する必要がある。
- **内部脅威**：エアギャップ環境では、更新のために誰かが何かを持ち込むので、内部者リスクが生じる。例として、パッチ入りの USB キーをサーバーまで運ぶ人が挙げられました。

こうした運用は、共有サポート契約のなかで顧客がより高い水準で担う責任になる、とも述べています。

参加者の投票は誤り 56%、ありうる 21%、正しい 23% でした。登壇者の判定は、**Busted だが注釈付き**で、誤りとありうるの中間です。注釈の理由は、Azure Local が切断モードで動作するようになったことです。具体的には次のとおりです。

- Azure に接続されている Azure Local は、最大 30 日間切断しても正常に動作する。
- 切断運用そのものは、Azure なしで継続的に動かせる。ただし責任は顧客が負う。
- Microsoft 365 も、ローカルの切断版が利用可能になった（資料へのリンクがスライドにある）。
- 設定済みのポリシー、RBAC、監査、コンプライアンス設定は、切断状態でも動作し続ける。これらは Azure Local の機器上でローカルに保持される。
- 更新と障害復旧は顧客が管理する。更新が必要になる点は Microsoft と連携する。

結論として、切断運用は「より安全」というより、**統制と継続性のための選択**だと述べられました。

### 5.5 神話 4：ソブリンにすると最新の AI は諦めることになる

関連する観点は、データ、および処理が国内か国外かといった規制と依存関係です。

**パブリッククラウドでの対応**

- サービスと Microsoft 365 を同じリージョンに置く場合、Copilot の AI データについて、国内処理の約束を守れる。今後 EU 以外の国にも広がり、カナダも含まれる。
- EU Data Boundary 内にデプロイし、データもそこに置く場合、Foundry と適切なソブリン統制を備えたパブリック Azure を使えば、すべての処理と計算が EU Data Boundary 内で行われる。
- Microsoft 365 Copilot の国内処理は、現在 15 か国で動作し、2026 年にさらに追加される。カナダ、ドイツ、米国などが含まれる。

**オンプレミスでの対応**

Foundry Local on Azure Local が、切断・接続の両方の状態で動作します。これは当日の発表で、一般提供（GA）になったと述べられました。大規模なマルチモーダルモデルの推論も、接続・切断の両方で動作します。厳選されたモデルの一部が対象ですが、それでも 11,000 通りのモデルを自社の GPU・データセンターで動かせる、という説明です。ローカルで大規模言語モデルを動かすことも可能です。

ただし、パブリック側にしかない最先端のフロンティアモデルは含まれません。モデルはまずパブリッククラウドに展開され、その後ほかの形態へ、Microsoft が単独では決められない時期に、パートナーと連携しながら展開されます。切断環境では、オープンウェイトのモデル（ダウンロードして自分で動かせるモデル）が対象です。また GPU は自分で購入する必要があり、ガバナンス、ログ、監視、アクセス制御もモデルの動く場所に付いて移動し、顧客の責任になります。GPU の価格についても冗談交じりの会話があり、H200 の中古価格として 135,000 ドルという数字が出ました（発話どおり。出典は確認できません）。

投票は 79% が Busted でした。登壇者の判定は **Busted/Plausible**で、遅れが生じる可能性があるだけで、ローカル処理や国内処理が必要と判断したワークロードに影響するとは考えていない、という立場です。質問に「最新（modern）」の語を入れた、引っかけだったとも述べています。

### 5.6 神話 5：プロバイダーのエンジニアはいつでも自分のデータにアクセスできる

ソブリン構成かどうかに関係なく、ハードウェア基盤を運用するプロバイダー（ハイパースケーラーやホスティング事業者）について、よく聞かれる質問だと紹介されました。答えは「いいえ」で、1 つ目の統制は**承認**です。

- **Customer Lockbox（Azure Lockbox）**：Microsoft のサポート担当者がデータにアクセスする必要が生じたら、申請を出さなければなりません。顧客がその申請を確認し、承認または拒否します。顧客が明示的に同意しない限り、誰も環境にアクセスできません。
- **近日提供予定のプロダクション・タッチ・レジャー（production touch ledger）**：変更できない台帳で、改ざんされれば検知されます。データへのアクセス履歴をすべて確認できます。これは「まもなく来る」と説明されたもので、提供済みとは述べられていません。

トレードオフとして、サポート対応の遅れが挙げられました。承認者が寝ている時間帯にチケットが起票されると、起きて承認するまでアクセスできません。

デモは 6 章に記載します。参加者の投票は誤り 65%、ありうる 29%、正しい 5% で、判定は **Busted** です。補足として次の点が述べられました。

- 承認フローはサポートの解決や診断を遅らせうる。承認者が 1 人だと詰まりやすいので、世界の複数のタイムゾーンをカバーできるよう複数人を置く。深夜 2 時の通知を誰が受けるかも決めておく。
- 顧客管理キーを使えば、キーがない限りアクセスは意味をなさなくなる。相手が人でもエージェントでも、ワークロードによってはキーと Lockbox の両方が必要になる。

ほかの手段として、Data Guardian と Clean Room も挙げられ、Ignite の会場で確認できると案内されました。

### 5.7 神話 6：クラウドプロバイダーの本社所在地で、どの政府がデータにアクセスできるかが決まる

最初に免責が示されました。自分たちの状況への当てはめは、法務チームに確認してほしい、という内容です。関連する観点は規制です。考慮される要素として、サービスの運用者、適用される規制、パートナーまたは Microsoft との契約上の約束、対象のデータ、技術的なアーキテクチャ、暗号化キーを持つのは誰か（自分のキーを使う場合）が挙げられました。

3 つの検討事項は次のとおりです。

1. **誰が運用するか**：どのプロバイダーもどこかに本社があり、その地域の法令と国の規制に従います。必要な場合は、フランスやドイツのように、国のクラウドパートナーに基盤と運用を完全に任せ、規制に合致させます（神話 1 で説明済み）。Microsoft はデータを保護し、地域・国の規制に従うことを、契約上も約束していると述べました。この点は、スライドの文言を意図的に読み上げたと断っています。
2. **どの規則が自分に適用されるか**：コンサルタントなら「場合による」と答える領域です。所在地や事業内容で変わるため、事業部門、エンジニアリングチーム、法務チームと話す必要があります。医療、保険、金融、教育、政府といった業種と、事業を行う国が関係しますが、45 分で網羅することはできないとのことです。
3. **どのワークロードに適用する価値があるか**：エンジニアリング、事業、法務と見直し、どのワークロードで規制に沿ったソブリン性が必要かを判断します。設計・実装の労力と、その後の運用も含めて考えます。Microsoft など各プロバイダーは幅広い選択肢を用意しているので、最大・最難関の構成に飛びつかず、ワークロードごとに必要な水準を選ぶよう助言しています。

登壇者は「データセンターの場所やプロバイダーの本社だけでは、政府のアクセスを評価できない」という文言を、法的に読み上げなければならなかったとして読み上げました。政府によるアクセスの規制は、特定のプロバイダーだけでなくすべてに適用される、とも述べています。

参加者の投票は誤り 51%、ありうる 18%、正しい 31% でした（登壇者は誤りの割合が予想より低かったと発言）。登壇者の答えは、Busted でも Confirmed でもなく **「場合による」** です。キーを管理しているか、データが保存時のみか使用中も保護するか、規制が運用モデルを要求するか、によって変わるためです。地理的な範囲だけで決まらず、**誰がキーを持ち、誰がシステムを運用し、どの規制が適用されるか**がポイントだとまとめています。

### 5.8 5 つの質問のフレームワーク

神話の検証の後、ワークロードごとの評価の冒頭で使う 5 つの質問が示されました。

1. **データはどこに置く必要があるか**：規制やコンプライアンスにより、カナダ、フランスなど特定の国にある必要があるか。根拠を示して答える。
2. **キーを誰が持つか**：Key Vault、Managed HSM、自分で持つ専用の Managed HSM から選べます。誰が管理するかは運用負担にもなります。
3. **誰がシステムを運用できるか**：顧客またはオペレーターのアクセス。Customer Lockbox、Data Guardian、スコープ付きエージェント ID、プロダクション・タッチ・レジャーなど。エージェントの時代には、エージェントもデータにアクセスするため、その制御が必要です。
4. **リンクやプロバイダーが失われたらどうなるか（接続性）**：インターネットを失う、道路工事でファイバーが切れるなどの場合に、そのワークロードは生き残れるか。生き残れないなら Azure Local のような選択肢を考える。
5. **どの規制と依存関係が適用されるか**：法務チームに確認する。

規制は変わり続けるため、一度評価して終わりではなく、定期的に見直すよう勧めています。Microsoft 側も、パブリック Azure、切断された Azure Local、拡大するパートナークラウドのそれぞれで、機能とガードレールを追加し続けると述べました。

### 5.9 利用できるツールとリソース

- **Sovereign Cloud Explorer**：発表日から利用可能。9 つの質問に答えると、現時点で把握している世界の顧客のソブリン要件に基づく推奨と、組織に合わせて試せる出発点が示されます。どの統制を有効にし、どれを無効にするかの指針にもなります。
- **Azure sovereignty landing zone**：ガードレール、ポリシー、追加サービスを一式で実装した既製のモデルで、開発環境や本番環境で試せます。ドキュメントが付属し、以前から提供され、どこからでもデプロイできます。
- **ソブリンポータル**：まだプレビューのため今回は見せていません。環境全体を調べ、自社のポリシーに照らして準拠・非準拠をグラフィカルに示すものです。
- 会場の階下のメインハブエリアに、キー管理やコンフィデンシャルコンピューティングなどを構築しているエンジニアに相談できる場所があると案内されました。

関連セッションとして、ソブリン性とモダナイゼーションを扱うブレイクアウト、シアターセッションの議論やパネル、そして翌日 4 時からの「ミッションクリティカル環境向けのソブリンプライベートクラウドの構築」が挙げられました。

## 6. デモ・手順

このセッションの大半はスライドと投票を使った対話で、画面を使ったデモは次の 2 つです。画面の細部は音声からは確認できず、語られた範囲のみ記載します。

### 6.1 Azure Policy によるデプロイ場所とキー管理の強制（神話 2 の中）

1. 登壇者がオーナーを務めるサブスクリプションを使う。そのサブスクリプションは現在 West US にある。
2. サブスクリプションのポリシーを開き、割り当て済みのポリシーを表示する。そのサブスクリプションとデモ用リソースグループに、多数の割り当てがある。
3. 一覧の下のほうに、場所に関するポリシーがある。West US 以外にデプロイされるものはすべて拒否される設定で、承認されるのは West US だけ。カナダの利用者なら、Canada East か Canada Central を選ぶ、と補足された。
4. ストレージに関するポリシーもある。ポリシー定義で、ストレージは専用の HSM を使うことを要求している。Key Vault や Microsoft 管理キーには頼らず、自分で管理する HSM（オンプレミスなどどこにあってもよい）を使う。
5. VM をコンフィデンシャルコンピューティングにすることを要求するポリシーも作れると触れられた。

要点は、ポリシーで制限とルールを強制でき、誤って別の場所にデプロイしてコンプライアンスを外れることを防げる点です。ソブリン専用の有効化は不要だとも述べられました。

### 6.2 Customer Lockbox の有効化（神話 5 の中）

1. Azure のヘルプとサポートで、現在のサポートプランを確認する。サブスクリプションは Standard プランで、Developer 以上のプランであれば Lockbox を有効にできる。
2. 「Customer Lockbox for Microsoft Azure」の管理画面で、有効にする。
3. Lockbox はサブスクリプション単位のため、アクセスを制限したいサブスクリプションのアクセス制御で、ロールの割り当てを追加する。
4. 「Customer Lockbox 承認者」のサービスのロールを選び、特定のメンバー（もう 1 人の登壇者）に割り当てる。
5. 説明を入力し、ロールを「対象（Eligible）」にして、利用者が申請する必要があるジャストインタイム管理にする。割り当てには開始と終了の期間を設け、承認者に時間制限を付けられる。ロールを適用する。
6. これで環境の Lockbox が有効になり、承認者が設定された。以後、そのサブスクリプションに対して誰かがサポートチケットを起票し、Microsoft のサポートエンジニアがトラブルシューティングのためにリソースの閲覧・アクセスを必要とすると、Lockbox が関与する。

デモ用にサポートケースも起票したが、「デモ用です」と書いたため自動的にクローズされた、と話しています。代わりに、Lockbox を有効にした別のサブスクリプションのスクリーンショットで、申請の一覧と詳細（作成日時、申請者、正当な理由の記入欄など）を見せ、承認または拒否できることを示しました。

## 7. 注意点・発表者の気付き

- ソブリン性は製品ではなくワークロードごとの統制の集合で、「これを入れれば主権が手に入る」ものではない。
- 登壇者は弁護士ではなく、法的な適用は必ず自社の法務に確認するよう、何度も述べている。
- Azure Front Door、Traffic Manager、Azure DNS、Azure Policy は世界規模のサービスで、1 つの地理的範囲に閉じ込められない。
- すべてのサービスが顧客管理の HSM キーに対応しているわけではない。現時点では重要なものが対応している。
- ローカルのプロバイダー（パートナークラウド）は、パブリック Azure の機能に遅れる場合がある。パートナークラウドを使う場合の契約相手はパートナーである。
- 切断運用では、パッチ、脅威検知、障害復旧、監視、内部者リスクが自社の責任になる。
- Lockbox の承認フローは、サポートの対応時間を延ばす可能性がある。承認者の不在がボトルネックになるため、タイムゾーンをまたいで複数人を置く。
- 最新のフロンティアモデルはパブリッククラウドが先で、切断環境では厳選されたモデルとオープンウェイトのモデルが中心になる。
- 規制は変わり続けるため、評価は定期的にやり直す。

## 8. 利用者にとっての利点

発表で語られた利点は、次のとおりです。

- ワークロードごとに、パブリック Azure のソブリン統制、Azure Local（接続・切断）、各国のパートナークラウドを使い分けられる。
- ポリシー、顧客管理キー、コンフィデンシャルコンピューティングを組み合わせ、デプロイ場所だけでなくキーと使用中のデータまで保護できる。
- Customer Lockbox により、Microsoft のサポート担当者のアクセスを顧客が承認・拒否でき、ジャストインタイムで期間も制限できる。
- Foundry Local on Azure Local の一般提供により、接続・切断の両環境で大規模なマルチモーダルモデルの推論ができる。
- 軽い構成から始めることで、実装が速く、運用コストが低く、更新しやすい。
- Sovereign Cloud Explorer と Azure sovereignty landing zone を使って、検討と試行を始められる。

## 9. まとめ

6 つの神話のうち、判定が **Busted** になったのは神話 1、2、5 で、神話 3 は注釈付きの Busted、神話 4 は Busted/Plausible、神話 6 は「場合による」でした。共通する答えは、ソブリン性が単一の製品や場所で決まるものではなく、データの所在、キー、運用者、接続性、適用される規制という複数の観点で、ワークロードごとに決めるものだという点です。

進め方として、エンジニアリング、事業、法務の 3 者で話し合い、最も軽い構成から評価し、規制の変化に合わせて見直すことが勧められました。出発点としては、Sovereign Cloud Explorer と Azure sovereignty landing zone が案内されています。
