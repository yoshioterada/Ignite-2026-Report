## 5. 発表内容の詳細

### 5.1 Commvault の概要と、今回の話の前提

Mike は Commvault を、オンプレミス、クラウド（特に Azure）、さらに SaaS にあるデータを保護、復旧、保全する会社と紹介しました。エージェントの世界に入るなかで、エージェントも保護・復旧・保全の対象にしていくと話しています。昔は OU（組織単位）やいくつかのファイルを戻せば済んだのに対し、いまは状況が大きく違うという説明でした。会場の Commvault 顧客を確認する質問には、数名が手を挙げています。

### 5.2 エージェント時代に変わる 4 つの側面

Mike はまず Gartner の統計を挙げ、今年は運用を見直し、戦略を考え直す重要な年になるという見方に触れました（具体的な数値は話されていません）。そして、この 2 週間の出来事（会場の天井から水が漏れた出来事、世界規模の障害）を例に、人々のレジリエンスへの考え方が変わりつつあると述べました。

エージェントの未来で変わる側面として、次の 4 つが挙がりました。

| 側面 | Mike の説明 |
| --- | --- |
| スコープ（範囲） | 20 年前にやっていたことと現在では、守る範囲が大きく違う |
| 自律性 | エージェントが自ら作業する。最小権限、最小限の主体性で安全に動かすことが望まれる。基本的なことはなくならない |
| コンテキスト | エージェントが環境を出入りするため、コンテキストと、それを支えるデータが重要になる |
| スピード | 以前からの攻撃でも新しい攻撃でも、AI によって速度が重要な要素になる |

あわせて、**ツールの乱立（スプロール）**が多くの組織で見られると説明されました。統合したいというのは、ツールだけでなく、それを管理する人の負担の問題でもあります。AI が一部を助けるとしても、ツールの乱立は残ると見ています。スタックが複雑になり、相互依存が増えるほど、より大きな問題を解く製品が求められ、プラットフォームであることが Commvault の強みだと述べました。

Commvault の CEO が語る 3 つの面として、**発見（discover）、検知（detect）、復旧（recover）**が示されました。発見は死角を見つけることで、保護していないものや、ポスト量子暗号の観点での機密データ、データの状況を把握して適正な規模の解決策にすることなどを含みます。今回の発表は、Azure ネイティブなやり方でこれらにどう取り組むかが主題だと述べました。

### 5.3 リカバリーの変化：相互依存と頻度

Rob は、DR 計画の作成や机上演習をしてきた経験から、変化は 2 点だと話しました。

- サービスが稼働しているとき、相互依存が非常に多くなった。オンプレミスでは ID の管理などを自分でやっていたが、いまは ID プロバイダーなど複数のサービスが組み合わさっている
- 復旧の頻度。昔は年に 1 回の訓練をして何も起きないことを願ったが、いまは障害もリカバリーも一般的な出来事になっている

Mike は、リカバリーを事後対応ではなく能動的にすべきだと応じました。昔は Sungard に出向き、顧客を支援して、毎年 24 時間の DR を行っていたそうです。いまは製品の中に、隔離されたリカバリーを行う方法が多くあり、継続的に練習できます。データだけでなく、スタックの状態（ステート）も復旧する話は後で触れるとしています。AI が助ける場面はあっても、実際に復旧するときに人が慣れていて、体が覚えているように感じられることが重要で、**練習して復旧に自信を持てること**を最優先に位置づけています。

### 5.4 Azure Backup との関係と、Azure の中に置かれるということ

Azure Backup で VM を保護している人を尋ねると、手を挙げたのは少数でした。Mike は、Azure Backup が適した規模のワークロードもあるため、Azure Native が完全に置き換えるものではないと説明しました。スナップショットで管理するのが適切な場合はそれを続けつつ、より深いリカバリーが必要なものもあるとき、Azure Native で両方の経路を管理できます。

Azure Backup の顧客からは、バックアップは「チェックボックス」で、課金も主アカウントに集約されるという声があり、調達、請求などの摩擦を取り除くことが Azure ネイティブにした理由の 1 つでした。調達、請求まで含めて Azure ネイティブな体験になります。

特に強調されたのは、「Azure の上に乗っている」のではなく「Azure の中に入っている」という点です。これを主張できる ISV は少なく、競合だけでなく、Commvault 自身の過去の Azure 向け提供とも決定的に違うと述べています。Commvault は、発話では「たぶん 10 年ほど」と不確かな言い方でしたが、以前から Marketplace に出ていますが、今回はそれとは異なる提供です。Azure ポータルの一部になっている ISV は 12 社ほどだと、Commvault 側の発言で語られました。

### 5.5 体験の流れ：購入からリカバリーまで

高い水準では、購入、オンボーディング、保護、リカバリーのすべてを Azure で行い、Azure ポータルを離れる必要がありません。Azure の他のファーストパーティサービスと同様に、Marketplace から申し込み、ワークフローが基盤を用意します。高度な機能が必要なら、Commvault の他の製品も使えます。

発見から拡張までの流れでは、Azure ポータルで発見し、他の Azure ネイティブサービスと同じように購入します。オンボーディングは、次の 3 つを用意する流れです。

1. **プラン**：何をバックアップするか、頻度、保持期間、スナップショット、フルのデータ保護などを決める
2. **エアギャップストレージ**：通常のストレージとは分離された、変更不可（イミュータブル）の保管先。復旧が必要になったときにデータが安全に残っていること、マルウェアに侵されていないことを重視している。そのための機能は製品群の一部にある
3. **リカバリーグループ**：ルールベースで、複雑にも単純にも作れる。タグや命名規則を使って、追加のワークロードを自動的に見つけられる

ルールを設定しておけば、VM を 1 台ずつ選ぶ「クリック操作」は不要になり、自動検出と、適切な階層への保護が続きます。手動でワークロードを選ぶことも可能です。ルールの詳細はブース 5350 で説明されます。

登録後は、フル、増分、変更ブロック追跡による効率的なバックアップが行われ、すべて重複排除と暗号化がされます。リカバリーの方法は、ファイル単位、ディスク単位、VM 全体、別の場所への復旧、リージョンをまたぐ復旧など多様です。

### 5.6 採用が伸びている機能と、顧客の変化

Mike によれば、特に使われているのは、基本の Azure VM です。オンプレミスから Azure VM への移行が多く、顧客はモダナイゼーションをリスク要因と捉えています。製品がスタック全体を管理できるため、モダナイゼーションのリスクを下げられると話しました。

リカバリーの進め方が組織に与える影響としては、部門をまたぐ協力が増えていると述べました。誰がインフラを管理し、誰がセキュリティを担当するかについて、Commvault は前提を置きません。そのため、製品群の大きな部分は信号（シグナル）の共有に重きを置いています。異常を検知したらセキュリティチームに共有し、被害の範囲を最小にしてできるだけ早く復旧する、という考え方です。顧客はこの形で「最小限の事業継続」を進めているそうです。

### 5.7 内部構成

構成図は大まかなものとして説明されました。

- 顧客環境には VM があり、オンボーディングの手順 1・2 を終えると、図の左側に 2 つ目のボックスが現れる
- Azure コントロールプレーン側に、Azure Marketplace のサブスクリプションがあり、登録ウィザードで保護を設定する。基盤は 1 度で設定できる
- メタデータと構成は、顧客の環境の中に置かれる
- バックアップから、バックアップを可能にするインフラの管理まで、管理対象の ID なども含め、**Commvault 側の環境**で動く。顧客はそのインフラを管理しない
- 保護、管理、構成を担うインフラは Commvault のサブスクリプションにあり、顧客の環境とは分離されている。マネージド ID と保存された資格情報で安全に接続し、これを可能にするのが Azure Native のリソースプロバイダーで、これが「秘伝のタレ」だと述べた

### 5.8 対応ワークロードとリージョン

- GA は月曜に行われ、**対象は Azure VM のみ**。最も多いワークロードから始める現実的な方針
- 今後の拡大として挙がったのは、ADLS Gen2、Blob、SQL Server、Cosmos、AKS など。他のワークロードの需要を見ながら広げる（今後の計画であり、提供済みではありません）
- 今回の発売で重視しているのは、人々が Azure ネイティブの体験に慣れること
- Azure VM では、ポリシーベースの保護（設定して放置を推奨）、変更ブロック追跡、複数のリカバリー方法を提供
- Commvault の Azure 保護は、パブリッククラウドだけでなく政府向けなどのリージョンにも広く及ぶ。コア製品が FedRAMP High 認定を受けているため
- Azure Native の開始リージョンは US East 2。以降拡大する予定

### 5.9 エージェント型 AI とリカバリー

Rob が、エージェント型 AI がリカバリーの世界とその頻度に与える影響を質問しました。Mike は、冒頭の 4 つの圧力が、AI が影響する理由であり、最初に Azure VM を保護し、残りは製品群全体で守るという異なるアプローチを取った理由だと答えています。エージェントの仕組みは Azure VM だけではありません。構成、ベクトルデータベース、ガードレール、その下のデータと基盤など、広い範囲を守る製品群が必要で、エージェントが ID、ガードレール、ベクトル、データ、機密データにどう影響するかを理解していることが重要だと述べました。

Azure Native はあくまで始まりで、人が使い慣れたシステムの中にとどまれるようにしたいとのことです。Commvault の画面を新しく覚えなくて済みます。一方で、MCP や Claude のようなツールを使ったヘッドレスな構成で作業したい人もおり、コア製品にはそのための選択肢もあると話しました。

## 8. 利用者にとっての利点

- 購入、請求、オンボーディング、保護、リカバリーまでを Azure で完結できる。調達や請求の摩擦が減る。
- Azure ポータルから離れずに使える。高度な機能が必要なら、Commvault の他の機能も使える。
- 保護、管理のインフラは Commvault 側にあり、顧客は管理しなくてよい。
- 変更不可のエアギャップストレージ、重複排除、暗号化、変更ブロック追跡による効率的なバックアップ。
- タグや命名規則による自動検出で、保護漏れを防ぎ、手作業を減らせる。
- ファイル、ディスク、VM 全体、別の場所、リージョン間など、多様な復旧方法。
- オンプレミスから Azure VM への移行でも保護を続けられ、モダナイゼーションのリスクを下げられる。
- 隔離された環境で復旧を繰り返し練習できる。

## 9. まとめ

Azure Native Commvault Cloud は、Azure ポータルの中で購入から復旧まで完結する、Azure の中に置かれた Commvault のサービスです。今週月曜に Azure VM を対象として一般提供が始まり、US East 2 から展開されます。その他のワークロードは今後の拡大予定です。

発表者は、エージェントの時代に、範囲、自律性、コンテキスト、スピードが変わるなかで、復旧は年に一度の訓練ではなく、練習を重ねる日常の運用になると述べました。始めるには、Azure Marketplace で検索するか、Azure ポータルのパートナーソリューションを使い、デモはブース 5350 で確認できます。
