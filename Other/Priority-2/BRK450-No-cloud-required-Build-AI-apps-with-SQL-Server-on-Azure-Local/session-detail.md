# BRK450 No cloud required: Build AI apps with SQL Server on Azure Local

## 1. はじめに

このセッションは、SQL Server をオンプレミスで動かし続けたいお客様が、クラウドにデータを出さずに AI を活用する方法を扱います。Azure Local の上で SQL Server を動かし、モデルのホスティングには Foundry Local を使う構成を、架空の病院向けアプリケーションで順に見せていきます。

発表の中心は次の 3 点です。Azure Local とは何か、その上で動く SQL Server の位置づけ、そして SQL Server のエンジン内部で完結させる AI の使い方です。ベクトル検索、RAG（検索拡張生成）、改ざんできない監査記録までを、すべてオンプレミスの閉じた環境で動かします。さらに、SQL Server Management Studio（SSMS）や Visual Studio Code から GitHub Copilot を使うときも、クラウドのモデルではなくローカルのモデルを使える点を紹介します。最後にライセンスの考え方と、将来クラウドへ移行する（または一時的にクラウドから戻る）場合の備えも説明します。

## 5. 発表内容の詳細

### 5.1 Azure Local とは

Azure Local は、クラウドと操作感が一貫したインフラです。Azure CLI、リソース管理、コントロールプレーンの操作、Azure portal といった Azure の操作感を、オンプレミスで得られます。Lenovo、Dell、HP などの OEM パートナーが提供するハードウェアに Azure Local をインストールして使います。自社のプライベートなデータセンターに置けます。

その上で動かせるものとして、発表者は次の 3 つを挙げています。

- 仮想マシン：マーケットプレースのイメージからのデプロイなど、Azure と同じ方法で管理します。
- Azure Virtual Desktop：Azure Local の上でも動きます。
- Azure Kubernetes Service（AKS）：Kubernetes と聞いて身構えなくてよいが、Azure Local で AI を動かす土台になるので重要、と説明しています。

提供形態は 2 つあります。

| 形態 | 内容 |
|---|---|
| 接続型 | オンプレミスで動かしつつ、Azure Arc を通じて Azure に接続します。データを Azure で動かすわけではありません。課金や、クラウド側での管理に使います。従来はこの形態だけでした。 |
| 切断型（エアギャップ） | 比較的新しい形態です。必要なイメージを、データセンター内のネットワーク共有にダウンロードしておき、Azure Local のソフトウェアも含めて、Azure CLI やリソース管理で完全に切断された環境にデプロイします。 |

切断型では、実行できないものが出る場合があり、接続型ではすべて実行できます。それでも切断型は人気のある選択肢になりうる、と発表者は話します。

### 5.2 VMware、Windows Server との比較

発表者は、ブースで「VMware から移りたいが Azure Local だとどうなるのか」と聞かれることが多いと言い、1 枚の比較図を右から順に説明します。

- **Windows Server**：管理ツール（管理センター）、Hyper-V、AKS、リモートデスクトップサービスなどは使えますが、ホストも仮想マシンも、基盤全体をお客様自身が管理します。
- **VMware**：優れたソフトウェアで、ハイパーバイザーと、管理を楽にするソフトウェアを提供します。契約相手は Broadcom です。SQL Server と仮想マシンを動かす基盤として世界で最も使われている、と発表者は述べています。
- **Azure Local**：OEM から購入したホストにソフトウェアを展開すると、管理された基盤一式が手に入ります。Azure portal と同じ画面をデータセンター内のブラウザで使えます。仮想マシン、AKS、Azure Virtual Desktop が揃います。

Azure Local OS はハイパーバイザーに相当し、Hyper-V の要素を含み Windows Server を基にしていますが、利用者がそれを意識する必要はありません。ソフトウェアの管理と更新は Azure Local が受け持ちます。Azure Update Manager が、Azure Local のソフトウェアコンポーネントやゲストなど、基盤全体の更新を自動で維持します。VMware から Azure Local への移行を支援するツールやチームがあることも触れられていますが、詳細はブースで、とのことです。

### 5.3 シナリオ：搬送調整センターのアプリ

デモ用の題材は、Caldova 地域の搬送調整センター（Regional Care Transfer Center）です。救急車などで病院へ向かう患者の情報が、救急隊員から病院側のシステムに入り、受け入れ側の看護師や医療従事者が到着予定の患者を画面で確認します。バイタル、救急隊員が書いた自由記述の所見も見られます。

発表者は、これは認定された医療ソリューションではなく、あくまで例であり、実際の病院にそのまま導入しないよう念を押しています。

病院側の要望は、患者一覧を見るだけでなく AI を使って、より効率的で質の高い治療につなげたい、というものです。ただし条件があります。**コンプライアンス上の理由から、システム全体を病院の管轄区域の内側で動かさなければならず、クラウドは使えません。**

アーキテクチャは次のとおりです。発表者の手描きで、GitHub Copilot の助けも受けて作成したそうです。

1. ケアチームの作業端末は Azure Virtual Desktop で、Azure Local 上のデスクトップに入ります。ブラウザは手元のもののように見えますが、実際には管理された領域の内側で動いています。
2. アプリケーションは、Azure Local 上の仮想マシンで動く SQL Server に接続します。SQL Server は、サポートされている任意のバージョンを仮想マシンで動かせますが、今回は AI 機能があるため SQL Server 2025 を使います。
3. 右側が Foundry Local です。Microsoft Foundry がローカル環境で動くものと考えてください。AI モデルを、GPU を備えた別の AKS クラスター（別のノード）で動かします。
4. 今回の構成は、管理目的のためだけに Azure のパブリッククラウドに接続しています。データはクラウドで動かしていません。接続しなくても構成できます。

アプリケーションの機能は次のとおりです。

- 到着予定の患者の一覧（キュー）。
- 患者ごとのバイタルと、救急隊員の自由記述。
- 自由記述から重要な情報（シグナル）を取り出す機能。
- 患者の履歴を自然な言葉で探す検索機能。
- 受け入れブリーフィング（受け入れ時の要約と、対応の推奨）の生成。医療従事者が承認することが前提です。
- AI モデルとのやり取りの監査履歴。SQL Server の中に記録されます。

### 5.4 Azure Local 上の環境

発表者は、Azure Local 上の Azure Virtual Desktop の画面を示します。Azure portal もデータセンターの中で動いており、クラウドではありません。仮想マシンの画面では、左上のアイコンが Azure Local の仮想マシンであることを示します。この仮想マシンは Windows Server Datacenter で、SQL Server 2025 が動いています。Azure Arc に接続しているので、SQL Server のライセンスを従量課金（Azure の支払い方式）にできます。

また、AKS が 2 つのモデルを提供しています。1 つは埋め込み（エンベディング）用、もう 1 つはチャット補完用です。いずれも同じローカル環境の中で動きます。

### 5.5 SQL Server on Azure Local と Foundry Local

**SQL Server on Azure Local**は、特別なエンジンではなく、これまでの SQL Server です。Azure Local チームと協力して、サポートされている任意のバージョンの SQL Server が、Azure Local の仮想マシンで正しく動くことを検証しています。ストレージには Storage Spaces Direct を使い、Azure Local が提供する高可用性などにも対応します。VMware や Windows Server 上の SQL Server と互換性があります。

**Foundry Local**は、AKS を通じて AI のホスティングサービスを提供します。モデルを SQL Server に読み込むのではなく、エンドポイントを通じて呼び出します。このチームは今回のイベントで多くの発表を行っており、詳細はそれらのセッションで確認するよう案内されています。目標は、Microsoft Foundry の力を Azure Local の環境に持ち込むことで、Azure Arc が支えています。

### 5.6 エンジン内で AI を使う仕組み

#### ベクトル検索

SQL Server 2025 の発表時に、ベクトルのサポートが加わりました。発表者の説明では、ベクトル検索は「より良い検索」です。LIKE 句や全文検索に代わり、埋め込みモデルによる類似度検索を行います。検索語が履歴の文章に含まれていなくてもよく、その処理はすべてエンジン内で行います。

アプリでの例は、入力された「胸の中央が締め付けられる感じ」という表現です。履歴にこの言葉がなくても、「胸部圧迫感」や「胸部の不快感」などに関連する記録が返ります。

仕組みは次の順です。

1. 埋め込みを生成するモデルとして、Nemotron のモデルを使います。この処理は GPU を使い、検索のたびに実行するのではなく、別に行うオフライン処理です。
2. 生成した数値（ベクトル）をデータベースに保存します。
3. 検索時は、SQL Server の仮想マシンの CPU が、クエリプロセッサの中で検索を処理します。

T-SQL のコードでは、次のように定義します。いずれも T-SQL の延長で書けます。

- モデル定義：Foundry Local のモデルを指す URL を指定します。
- ベクトルデータ型：SQL Server に新しく追加されたデータ型です。これを持つテーブルを作り、メモと結合します。
- 埋め込みの投入：INSERT SELECT 文を書くだけで、裏でモデルとやり取りして埋め込みを取り込みます。数値の意味を利用者が理解する必要はありません。
- インデックス：ベクトルデータ型の上に特別なインデックスを作ります。大量のデータでも検索が速くなります。
- 検索用ストアドプロシージャ：アプリが患者の重要情報を渡して呼び出します。プロンプトから埋め込みを生成し、データベース内の数値と比べて、近い結果を返します。

#### JSON 型と正規表現

発表者は、SQL Server は開発者向けの最新機能も備えていると言い、2 つを挙げています。

- ネイティブの JSON 型：アプリ開発者が、すべて JSON で返してほしいと要望したため、JSON を保存して返しています。
- T-SQL の正規表現：救急隊員の自由記述から、重要な手がかり（シグナル）を取り出すのに使っています。

#### RAG による受け入れブリーフィング

ブリーフィングは、検索とは別のストアドプロシージャです。埋め込みモデルの役割は数値を作ることだけですが、こちらは Copilot や ChatGPT のような推論用のチャット補完モデル（GPT）を呼び出します。

プロンプトを組み立てるのは SQL Server 側です。アプリは患者の ID を渡すだけで、SQL Server がすべて処理して JSON を返します。画面で「履歴を含める」にチェックを入れて「ブリーフィング生成」を押すと、エンジン内で次の処理が走ります。

1. ベクトル検索で類似した履歴を探します。
2. 患者 ID から、その患者のシグナルとバイタルを引きます。
3. 指示とあわせて、モデルに渡します。

AI モデルは、医学的な知識は学習済みですが、Maria Santos さんも Caldova Regional Care Transfer も知りません。そこで患者の情報で、モデルの知識を補います。これが RAG パターンです。モデルに渡すときは、個人を特定できる情報（PII）を隠し、症状や問題と履歴の結果だけを渡します。発表者の将来の義理の娘さん（研修医）が出力を見て、悪くない、むしろかなり良いと評価したそうです。ただし最終的に推奨を採用するかどうかは、医療従事者が決めます。

#### スキルとエンドポイントをテーブルに保存する

発表者は、スキルという概念を使います。スキルは、モデルにどう振る舞うかを指示する JSON で、データベースのテーブルに保存します。ストアドプロシージャにハードコードしません。エンドポイントも別のテーブルに保存し、動的に引きます。デモのコードでは、以前は「535」と聞こえる名前のモデルを呼んでいたが、今は GPT を呼んでいると説明しています（前者のモデル名は音声認識の都合で表記が確定できません）。

ブリーフィングのストアドプロシージャの処理は次のとおりです。

1. 患者の情報を取得する。
2. 「履歴を含める」がオンなら、ベクトル検索のストアドプロシージャを呼ぶ。
3. 先ほどの正規表現でシグナルを取り出す。
4. 転送用のスキルを呼び出す（モデルと話す中心の処理）。

スキルの呼び出しの内部では、次のことを行います。

- データベース内のバージョン管理から、使うスキルとモデルのエンドポイントを動的に読む。
- AI アプリが送るのと同じ形の REST 用のプロンプトを組み立てる（Copilot が裏でやっていることと同じ）。
- REST を呼ぶシステムストアドプロシージャで、GPT のエンドポイントを呼ぶ。

GPT は相手が SQL Server だと知らず、アプリも GPT を使っていることを知りません。SQL Server のエンジンで AI を抽象化することで、SQL Server のセキュリティが AI の利用を制御できます。発表者は、プロンプトの作成には GitHub Copilot の助けを借りたと話しています。GPT がどんな入力を期待するかを知っているからです。

#### 台帳テーブルによる監査

AI の利用すべてを監査したい、という要望に応えるのが台帳テーブル（Ledger テーブル）です。

- 改ざんが検知できる。
- さらに追記専用（append only）にすれば、更新も削除もできず、DBA でも触れません。

モデルに送った入力（スキル、患者データ、プロンプトや指示）と、返ってきた応答は、すべて JSON です。これをそのまま台帳テーブルに記録すれば、AI との全やり取りを後から監査できます。

作り方は、テーブルの作成文の最後に、台帳で追記専用（with ledger、append only）と付けるだけです。列には、JSON の列、日時、使ったモデル、戻りコードなどを持たせます。ストアドプロシージャがモデルを呼ぶたびに、この挿入を必ず行うよう作ってあり、トランザクションの中で処理されます。失敗も含めて、すべて記録されます。誰でも、いつでも、この監査を照会できます。

ここまでの内容は、切断された状態でも作れます。完全には使えない機能もありますが、多くは使えます。構成図では Azure との通信がなく、Azure Arc を通じて、リソース管理、Azure CLI、ポータルなど、管理に必要なものをすべて切断環境の中で使います。完全な切断を求めるお客様が実際にいるそうです。

### 5.9 ライセンス

発表者は、自分は価格の担当ではないと前置きしたうえで、よく聞かれるので説明しています。資料のリンクに詳細があり、実際には Azure Local の導入を支援する Microsoft のチームや OEM と詰めることが多い、とのことです。

| 対象 | 接続型 | 切断型 |
|---|---|---|
| Azure Local | コア単位で Azure 経由で課金されます。Datacenter の Software Assurance（SA）があれば、Azure ハイブリッド特典で免除されます。ただし 30 日間は Azure に接続し、コア使用量を確認できるようにする必要があります。SA のライセンスがなければ、Azure 上と同様にコア単位の時間課金です。 | ハイブリッド特典はありません。物理コアに対して課金されます。接続は不要ですが、導入内容を伝える手段が必要です。 |
| Foundry Local | モデルを動かす AKS は無料です。取得するモデルの多くは無料のオープンソースです。カタログにはライセンス付きのモデルもあり、その場合の支払いはお客様の責任です。 | 同様 |
| SQL Server | Azure Local のライセンスは使いません。既存の SQL Server ライセンスを使います。Azure Arc を接続すれば従量課金も選べます。仮想マシンで SQL Server を Azure で動かすときのように、コア単位で時間課金されます。SQL Server をあまり使わない場合は、こちらが適することもあります。 | 同様のライセンス体系です。 |

### 5.10 Azure SQL への移行・戻りと顧客事例

将来クラウドに移る準備もできている、と発表者は説明します。Azure のポータル、リソース管理、CLI、AKS、Azure Virtual Desktop、SQL Server の仮想マシンという経験は、そのままクラウドにつながります。デモのアプリは Azure SQL と互換です。

例として、Hyperscale を使い、同じコードで、同じモデルのエンドポイントの考え方を使う構成を示しています。違いは、モデルのエンドポイントがクラウドの Microsoft Foundry にある点だけです。同じアプリを Azure App Service に置き、同じデータベースを Hyperscale に置きます。スキルとエンドポイントはテーブルにあるので、これらを入れ替えて Azure SQL にデプロイすれば動きます。逆に、すでに Azure SQL を使っているお客様が、一時的に Azure Local へ戻すこともできます。

## 6. デモ・手順

デモは事前に録画した映像で、発表者が口頭で解説しながら進めました。画面の細かい操作は音声からは確認できないため、語られた範囲だけを順に書きます。

### 6.1 アプリケーションの確認

1. Azure Virtual Desktop に入ると、到着予定の患者の一覧（キュー）が表示される。
2. 患者の中央のエリアに、バイタルと救急隊員の所見が出る。
3. 自由記述から、T-SQL でシグナルを取り出している。
4. 患者履歴を自然な言葉で検索できる。「胸の中央が締め付けられる」と入力すると、胸部圧迫感などに近い履歴が返る。
5. 履歴を含めて、受け入れブリーフィングの推奨を生成できる。
6. 監査履歴が SQL Server の中に記録されている。

### 6.2 Azure Local 環境の確認

1. Azure Local 上の Azure Virtual Desktop の画面を見せる。ポータルはデータセンター内で動いている。
2. 仮想マシンの画面を見せる。Azure Local の仮想マシンで、Windows Server Datacenter と SQL Server 2025 が動き、Azure Arc で接続されている。
3. AKS が、埋め込み用とチャット補完用の 2 つのモデルを提供していることを示す。

### 6.3 ベクトル検索とブリーフィングのコード

1. モデル定義、ベクトルデータ型のテーブル、INSERT SELECT による埋め込みの投入、ベクトルインデックスのコードを示す。
2. 検索用ストアドプロシージャで、プロンプトから埋め込みを作り、ベクトル検索で類似結果を取得するコードを示す。
3. ブリーフィングのストアドプロシージャを示す。履歴を含めるにチェックを入れて「ブリーフィング生成」を押すと、ベクトル検索、患者のシグナルとバイタルの取得、指示の付与が行われる。
4. スキル（JSON）とエンドポイントがテーブルにあり、そこから読み出して、REST を呼ぶシステムストアドプロシージャで GPT を呼ぶ処理を示す。

### 6.4 台帳テーブルによる監査

1. 監査機能は、アプリに追加で付けた表示である。実運用では通常アプリに見せない。
2. 台帳テーブルを読むと、AI モデルと SQL Server の生のやり取りが残っている。
3. 「Request JSON」を押すと、スキル、患者データ、プロンプトと指示という入力と、応答が見られる。
4. 台帳テーブルの作成文（末尾に with ledger、append only）と、挿入のコードを示す。

### 6.5 SSMS でのデッドロック分析

1. SSMS を、Foundry Local の GPT を使うオートパイロットモードに設定する。
2. 「システムヘルスセッションを見て、デッドロックを分析してほしい」と依頼する。
3. 回答は、2 つのテーブルを逆の順序で更新したことによる、典型的なデッドロックだった。
4. 回答に含まれていたデッドロックグラフを取得するクエリを、クエリウィンドウで実行する。
5. XML のレポートが返り、SSMS の中で可視化できた。追加のトレースは不要だった。

### 6.6 Visual Studio Code でスキーマと対話

1. Azure Local の環境内にある開発者の仮想マシンで、Visual Studio Code を使う（MS SQL 拡張機能）。
2. データベースを右クリックして、スキーマの視覚化を実行する。テーブルの関係が図になる。
3. 図の画面にある Copilot のボタンを押すと、Copilot のチャット画面に、スキーマデザイナーを使うプロンプトが入る。GitHub Copilot が使い方を知っているツールも付く。
4. 既定でスキーマの要約が返る。さらに AI 関連のスキーマ（ベクトル型や外部キーの関係など）の詳細を依頼すると、ローカルの GPT が、ツールを通じてデータベースの文脈を受け取って回答した。

## 7. 注意点・発表者の気付き

- 切断型では、実行できないものがある。接続型ならすべて実行できる。
- 今回のデモのアプリは、認定された医療ソリューションではない。実際の病院にそのまま導入しないよう、発表者は注意している。
- 推奨を採用するかどうかは、必ず医療従事者が決める。
- ハイブリッド特典での免除には、30 日間 Azure に接続して、コア使用量を確認できるようにする必要がある。切断型にはハイブリッド特典がない。
- Foundry Local のカタログにライセンス付きのモデルがある場合、その支払いはお客様の責任になる。
- ライセンスや価格は発表者の専門ではなく、導入を支援するチームや OEM と詰めるのが一般的と述べている。
- Azure Local の SQL Server は、サポートされている任意のバージョンを仮想マシンで動かせる。今回 SQL Server 2025 を使ったのは、AI 機能のため。

## 8. 利用者にとっての利点

- データをクラウドに出さずに、AI による検索と推奨をオンプレミスで実現できる。管理だけのためにクラウドに接続する形や、完全な切断型も選べる。
- 既存の SQL Server と互換で、VMware、Windows Server、Azure Local の間で同じエンジンを使える。
- SQL Server のセキュリティモデルで AI の利用を制御でき、モデルとの通信は暗号化される。モデルはエンジンから分離された Foundry Local のサービスにある。
- アプリ開発者は、ストアドプロシージャを呼ぶだけで済み、AI を意識しなくてよい。
- 台帳テーブルにより、AI との全やり取りを、DBA でも書き換えられない形で監査できる。
- SSMS や Visual Studio Code の GitHub Copilot を、ローカルのモデルで使える。
- Datacenter と SA を持つ場合は、接続型の Azure Local 費用をハイブリッド特典でまかなえる。
- 将来クラウドへ移る、あるいはクラウドから戻る場合も、スキルとエンドポイントをテーブルで管理しているため、同じアプリとデータベースの設計を使える。

## 9. まとめ

Azure Local は、Azure の操作感をオンプレミスに持ち込む基盤で、接続型と切断型を選べます。その上の SQL Server は、これまでと同じエンジンです。Foundry Local のモデルを REST で呼べば、ベクトル検索や RAG を T-SQL のストアドプロシージャとして実装でき、台帳テーブルで AI の利用を改ざんできない形で記録できます。同じ環境で、SSMS と Visual Studio Code の GitHub Copilot もローカルのモデルで使えます。ライセンスは、Azure Local、Foundry Local、SQL Server で別々に考え、Azure SQL への移行や戻りにも同じ設計が使えます。資料とコードは、発表者の公開リポジトリで入手できます。
