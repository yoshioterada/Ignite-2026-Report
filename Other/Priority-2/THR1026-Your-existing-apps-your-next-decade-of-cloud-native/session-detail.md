# THR1026 Your existing apps, your next decade of cloud-native

## 1. はじめに

このセッションは、すでにクラウドネイティブ化（モダナイズ）したアプリを、本番環境で効率よく運用するにはどうするか、を扱う発表です。アプリをどう作り変えるかではなく、作り変えた後の運用（セッションでは「Day 2」と呼ばれる段階）が主題です。

前半で、クラウドネイティブでない構成と、Azure Container Apps での構成を比較します。後半は、実際に動くアプリを使ったライブデモです。デモでは、トラフィック増加に伴う自動スケール、リビジョン間のトラフィック分割とロールバック、そして新機能として発表された **Debug with SRE Agent** による原因調査と復旧を順に見せています。

## 5. 発表内容の詳細

### 5.1 従来の構成が抱える課題

発表者は、典型的なアプリ構成として、利用者がロードバランサーを通じて複数の Web サーバーにアクセスし、各サーバーにアプリとランタイムがあり、バックエンドに非同期ジョブやストレージ、キューがある図を示しました。この構成自体に問題はなく、クラウドに移しても基本は同じです。ただし、クラウドを使わない環境では次の心配が残ります。

- **スケール**：先を読んで容量を計画する必要があり、需要の予測が要ります。突発的なスケールはできず、リソースが使われないときにコストを下げるために縮小することもできません。
- **パッチ適用**：アプリだけでなく、周りのインフラ全体を気にする必要があります。
- **監視**：別々のシステムにまたがる問題を診断し、関連付けるのが難しくなります。

### 5.2 Azure Container Apps での構成

クラウドネイティブな構成では、箱の数が大幅に減り、残る箱もそれほど自分で管理しなくなります。Azure Container Apps は、まず **Azure Container Apps の環境**から始まります。環境は、プロセスとネットワークを分離する境界であり、その中に複数のアプリやジョブが動きます。それぞれのアプリとジョブには、次の特徴があります。

- 独立してスケールできる
- 複数のリビジョンを持てる。複数のデプロイを通じて管理でき、ブルーグリーンデプロイもできる
- シークレットと ID を、個別に管理できる

プラットフォームが担うことで利用者が気にしなくてよくなる事柄として、スケール、更新（リビジョンの管理とトラフィック分割）、デバッグが挙げられました。デモでは、この 3 つの流れを、実際のアプリで見せると予告されています。Nazim は「4 つの事柄」と話していますが、発話で具体的に挙がったのはスケール、更新、Debug with SRE Agent の 3 つです。

### 5.3 デモの設定

Vinny は、開発チームがアプリをモダナイズし、リリースを祝った後、運用を引き継いだインフラ担当の立場を演じています。アプリは、音楽ストアの MVC アプリケーションで、コンテナ化され、.NET 10 で動き、Container Apps 上にあります。2 日前までは、誰も触りたがらない .NET Framework の MVC アプリだったと説明しました。

デモの内容は 6 章に詳しく書きます。

### 5.4 Debug with SRE Agent の仕組みと制約

デモ中の説明をまとめると、次の特徴があります。

- Container Apps は、**埋め込み型の一時的な（エフェメラルな）SRE Agent を使う最初のサービス**だと説明されました。新しくリソースを作る必要はなく、追加のインフラも要りません。読み取り専用の一時的なインスタンスを使ってアプリをデバッグします。発表者はこれを、今回発表する新機能と位置付けています。
- エージェントに送るデータは、ユーザー自身がブラウザーから、自分のアクセス権で収集したログとメトリックです。ユーザーにアクセス権がないログは送れず、ユーザーが読めないリソースをエージェントが読むこともできません。エージェントは新しいアクセス権を持ちません。
- エージェントは Azure Container Apps のサンドボックス内で動作し、ユーザーが送ると決めたデータの範囲でしか動けません。発表者は、聞いたことのあるサンドボックスと同じ技術だと説明しています。
- 各デバッグセッションには **30 分の制限時間**があり、時間が過ぎるとサンドボックスは破棄され、送ったデータもすべて破棄されます。何も保持されません。
- セッションの活動ログを確認でき、終了時にセッションのトランスクリプトをダウンロードできます。自動承認に当たる設定にも触れていますが、音声認識の都合で正確な名称は確定できません。
- SRE Agent は読み取り専用で、強制してもリソースの変更は行いません。

## 6. デモ・手順

デモは画面を使って行われました。音声で語られた範囲だけを、語られた順に書きます（画面の細部は音声からは確認できません）。

### 6.1 自動スケール

1. 実運用のアプリには何らかのトラフィックがあるという前提で、トラフィックを流し始める。
2. 同時接続のトラフィックを送る。アプリは、常に 2 つのレプリカが動くように構成してあり、予想外のトラフィックが来る状況を作る。
3. Azure portal とは別の、Container Apps の新しいユーザー体験を紹介する（会場に、Container Apps を使っているか、この新体験を知っているかを尋ねている。従来の Azure portal の体験も引き続き使える）。管理よりも、アプリを見て、監視し、何が悪いかを把握することに重点を置いた画面と説明している。
4. ライブビューで 2 つのレプリカを確認する。エラーがいくつか出ている。トラフィック増加に伴い、新しいレプリカが 2 つ追加される。
5. スケールのセクションで、デモ用の HTTP スケールルールを見せる。既存のリクエストに対し、5 つの同時リクエストごとに新しいレプリカを起動する設定。オンプレミスや IIS、VM からモダナイズした場合、この作業は担当者の仕事ではなくなる、と述べる。

### 6.2 トラフィック分割とロールバック

1. 開発チームがエラーを修正した新バージョンをリリースしたので、デプロイしてほしいと依頼された、という設定。
2. 以前の仕事では、保守ウィンドウを計画し、週末や夜中に作業した。今回は、新バージョンはデプロイ済みで、そこにトラフィックを振り向ける。
3. コマンドで、バージョン 1 に 90%、バージョン 2 に 10% のトラフィックを割り当てて実行する。ロードバランサーの変更も保守ウィンドウも不要で、統制された形でのリリースだと説明している。
4. V2 のレプリカが起動するが、V2 はエラーになる。
5. 完全なデプロイや複雑なスクリプトは使わず、設定を V1 に 100%、V2 に 0% に戻して切り戻す。直近 10 秒のエラーが消えることを確認する。
6. ライブメトリックで、エラーが増えてから消える様子を見る。レプリカ数も増えている。Azure Monitor を使っており、アプリには計装を一切していない、と述べている。エラーが消えたことを確認する。

### 6.3 原因不明の障害と Debug with SRE Agent

1. リリースも変更もないのに、朝になるとエラーが出ている、という設定。トラフィックは続いており、4 つのレプリカが動いている。エラー（赤い表示）が増える。
2. アプリがまだ動いているかを確認する。応答に時間がかかっている。
3. クラウドネイティブが提供する機能としてプローブがあると触れる（深くは扱わない）。
4. ログストリームを開き、アプリのエラーか、プラットフォームのエラーかを並べて確認するが、引き継いだばかりのアプリで、調査の方法が分からない、という設定にする。
5. **Debug with SRE Agent** を使う。デバッグセッションの開始時に、エージェントに送るデータを選ぶ（セッションの冒頭でチェックボックスをオンにしたデータ）。
6. 「ユーザーから Web サイトでタイムアウトが出ていると報告されている。何も変更していない。助けてほしい」と入力する。
7. エージェントが症状を整理し、リソースの枯渇はないと判断する。
8. エージェントが追加のリソース情報を要求する。リソースグループ内のすべてのリソースの取得（get）だと表示される。ユーザーは許可でき、送信前にエージェントが読む内容を確認し、不要なものは削除できる。発表者は、自分のメールアドレスが含まれているのを見つけ、それを削除してから送信する。
9. エージェントがさらにデータを要求し、アプリは SQL に認証していること、アプリが 3 分前に最終変更されたことを示す。アプリに変更はないため、ほぼ確実に SQL への接続の問題だと述べ、確認を求める。発表者はそれを許可する。その後、SQL ファイアウォールのルールに関する情報の取得も求められる。
10. 画面右側に、Azure 上のリソース、ブラウザー、エージェント、エフェメラルストレージの間の情報の流れが表示される。画面上部にはセッションのタイマーが表示される。
11. エージェントが SQL サーバーのパブリックネットワークアクセスの設定を見つけ、根本原因として、ファイアウォールがアウトバウンドの IP をブロックしている、と示す。
12. 発表者が調査する時間がないとして、エージェントに「修正して」と頼むが、SRE Agent は読み取り専用で、修正はできない。代わりに、修正用のスクリプトを提示する。
13. スクリプトを整形し、PowerShell で実行する。エラーが減っていくのを確認し、アプリを更新して、動作が戻ったことを確認する。
14. セッションを終了する。スクリプトとファイルをダウンロードできる。

発表者は、デモで「リリースとロールバック」「障害からの復旧と原因特定」を行ったとまとめました。

## 7. 注意点・発表者の気付き

- **Debug with SRE Agent は新機能として発表されたものです。** Container Apps が、埋め込み型のエフェメラルな SRE Agent を使う最初のサービスだと述べています。
- **エージェントの権限は限定されています。** 読み取り専用で、ユーザーが送ったデータの範囲でのみ動き、新しいアクセス権はありません。強制しても変更は行いません。修正は、エージェントが示したスクリプトを、ユーザー自身が実行する形です。
- **送信するデータは事前に確認できます。** デモでは、メールアドレスが含まれていたため削除してから送信しました。
- **セッションは 30 分で終了し、データは破棄されます。**
- デモで見せた HTTP スケールルール（5 つの同時リクエストごとに新しいレプリカを起動）は、発表者が「デモ目的」の設定と説明したものです。
- サンドボックスも同時に公開されると案内されましたが、サンドボックスの内容は発表では詳しく説明されていません（資料を読むよう案内）。
- 冒頭で触れられたシークレット、ID の扱い、エージェントとのやり取りの課題のうち、ID とシークレットの具体的な説明やデモは、発話では確認できません。

## 8. 利用者にとっての利点

発表者が語った利点は、次のとおりです。

- **スケール**：トラフィックに応じて自動でスケールアウトし、トラフィックがないときは 0 までスケールダウンしてコストを抑える。オンプレミスや VM から移行した場合、容量計画や帯域・ロードバランサーの増強という仕事から解放される。
- **更新**：トラフィック分割で段階的にリリースし、問題があれば設定の変更だけで元に戻せる。保守ウィンドウやロードバランサーの変更は不要。
- **監視**：Azure Monitor で、計装なしにメトリックを確認できる。
- **障害対応**：Debug with SRE Agent で、不慣れなアプリでも原因を絞り込め、修正スクリプトの提示を受けられる。データはユーザーの権限の範囲で、時間制限付き、かつ保持されない。
- 箱の数が減り、管理するインフラが少なくなる。

## 9. まとめ

アプリのモダナイズは出発点であり、その後の本番運用でも、スケール、安全な更新、障害対応が必要になります。Azure Container Apps は、これらの多くをプラットフォーム側で担います。デモでは、トラフィック増加に伴う自動スケール、90% 対 10% のトラフィック分割とロールバック、そして Debug with SRE Agent による SQL ファイアウォールの原因特定と修正スクリプトの提示を行いました。

発表の最後には、関連セッションの案内と、Azure Container Apps チームの発表、今日から始められるラボ、同時に公開されるサンドボックスの紹介がありました。質疑応答には約 90 秒が用意されましたが、会場からの質問は確認できません。
