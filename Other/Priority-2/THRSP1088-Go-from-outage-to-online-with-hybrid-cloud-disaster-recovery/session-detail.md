# THRSP1088 Go from outage to online with hybrid cloud disaster recovery

## 1. はじめに

このセッションは、Nutanix Cloud Clusters（NC2）を使って、オンプレミスの仮想マシンを Azure へ災害復旧（DR）するまでの流れを、画面操作つきで見せる短い発表です。発表者はもともと展示会場で行う予定だったものを、このセッションとして実施したと冒頭で話しています。

内容は大きく 3 つに分かれます。NC2 の概要と DR の選択肢、Azure 側に必要なネットワーク構成、そして Prism Central 上でレイヤー 2 延長・保護ポリシー・リカバリープランを作り、計画的フェイルオーバーを実行するデモです。**デモの最後には、2 台の仮想マシンが同じ IP アドレスのまま Azure 上で起動します。**

## 5. 発表内容の詳細

### 5.1 Nutanix Cloud Clusters（NC2）の概要

NC2 は、Nutanix のソフトウェアスタックを Azure のベアメタル上で動かすサービスで、共同開発されたサービスだと説明されています。Nutanix は仮想マシンとコンテナーのためのプラットフォームです。他社との違いの 1 つとして、セキュリティが組み込まれている点を挙げ、自動化されたセキュリティ STIG により、3 時間で米国国防総省（Department of Defense）レベルの設定を組織内に用意できると話しています。

仮想化とストレージの課題を軸に発展してきた製品で、オンプレミスやプライベートデータセンターから Azure へワークロードを移すと、次の利点が得られると説明されています。

- アプリケーションをリファクタリングせずに再起動できる高可用性
- ストレージと DR の機能一式
- Flow Virtual Networking によるレイヤー 2 延長（今回のデモで使用）。ワークロードを簡単に移動でき、IP アドレスを維持できる

NC2 は、顧客自身のアカウントにデプロイされます。アカウント全体を顧客が所有するため、他の Azure サービスへの移行も選べます。Nutanix のデータベースサービスを使うことも、Azure SQL を使うこともでき、そのためのネットワーク接続も確保されます。

### 5.2 Nutanix DR の選択肢

Azure との組み合わせで、次の方式が紹介されました。

| 方式 | 説明 |
| --- | --- |
| 非同期（async） | 一般的な 1 時間間隔の DR |
| ニアシンク（near sync） | 20 秒程度の間隔にもできる |
| MST（multi-cloud snapshot technology） | Nutanix のスナップショットをオブジェクトストレージへ送る新しい仕組み。今回の説明では Blob ストレージが対象 |

MST を使えば、Azure 上に Microsoft の利用実績も Nutanix の環境もない顧客が、Blob へスナップショットだけを送っておけます。大きな事故が起きたときに NC2 クラスターを立ち上げ、Blob から Nutanix クラスターへ直接復元します。

復元を速くする仕組みが「インスタント リストア」です。Blob にあるワークロードの実際の VM のうち、約 15〜20% だけを Nutanix クラスターに先に読み込みます。その後は稼働中の書き込みが高速な NVMe オールフラッシュストレージに入り、残りの読み取りは Blob から行われます。コストの低いストレージを使いながら、すぐに作業を再開できると説明されました。

運用イメージとして、2 つの階層が示されています。重要なワークロードには、常時待機の最小構成クラスター（パイロットライト）で素早く復元し、残りのワークロードは MST の階層で扱います。

### 5.3 Azure 側のネットワーク構成

スライドの構成図は細かく、発表者自身も見づらいと断ったうえで、押さえるべき点は 3 つだと述べています。

1. ベアメタル用の VNet が 1 つ必要
2. 管理用の VNet がもう 1 つ必要。どちらもサブネットは委任され、Azure のネイティブ IP を使う
3. Nutanix 上で動く仮想マシンやコンテナーのために、Flow ゲートウェイを使う

Flow ゲートウェイは、ネイティブな Azure の仮想マシンです。南北方向の通信をすべて担当し、レプリケーションは担当しません（レプリケーションはベアメタルに直接届きます）。そのためサイジングの心配は不要で、ゲートウェイは最大 4 台まで置け、合計で最大 64 Gbps の帯域になります。発表者の認識では、まだこの上限に達した顧客はいません。

構造を分けると、Azure のアンダーレイにはベアメタル（ハイパーバイザーとストレージコントローラー）があり、その上に Flow Virtual Networking のオーバーレイがあります。管理は Prism Central が担います。

**NAT あり・なしの違い**

- 発表者によれば、Nutanix 顧客の 95% は NAT なしを使い、Azure 上でも完全にルーティング可能にしています。この完全なルーティングは Flow ゲートウェイの助けで実現されます。
- NAT ありは最も簡単な経路です。Flow ゲートウェイがネイティブな Azure IP を取り、Nutanix 上の仮想マシンに NAT で割り当てます。Azure 内のルーティングは非常に簡単になります。
- NAT なしでは、外向きの通信は簡単です。完全にルーティング可能にするには、Prism Central の外部ルーティング可能プレフィックス（発話上は「ERP」）を、デプロイされる BGP の仮想マシンに広告し、これが Azure Route Server と通信します。Azure Route Server を使いたくない顧客向けには、より安価な選択肢もあるとのことですが、詳細は話されていません。
- 内向きの通信は、NAT ありの場合、外部 NIC の Azure アドレスから Flow ゲートウェイを通ります。NAT なしの場合は、Flow ゲートウェイ経由でトランジット VPC に入り、ハイパーバイザーのリダイレクトシャーシ（発話上の名称）が、仮想マシンのあるホストを選んで届けます。利用者がこの経路を意識する必要はない、と説明されています。

発表者は、NC2 で最も難しいのはネットワークだとしつつ、よく計画するか Azure に詳しい人がいれば単純で、時間がかかるだけだと話しています。

## 6. デモ・手順

デモは、オンプレミスの Prism Central の画面から始まります。以下は発話で語られた順の手順です。画面上の細かい表示は、音声からは確認できません。

### 6.1 可用性ゾーンの接続

1. オンプレミスの Prism Central で、管理メニューから「可用性ゾーンの接続」を開きます。NC2 の Azure デプロイ時には、専用の Prism Central も一緒にデプロイされます。
2. Azure 側の Prism Central の IP アドレスを入力し、接続します。
3. 到達可能と判定されると、保護ポリシー、リカバリープラン、セキュリティポリシーの同期が始まります。セキュリティポリシーが同期されるため、移動後も元の場所と同じポリシーが仮想マシンに適用されます。

### 6.2 レイヤー 2 延長の設定

1. 接続メニューで、まずオンプレミス側にゲートウェイを作成します。名前を付け、デプロイ先のオンプレミスクラスターを選び、次へ進みます。
2. 「VTAP」が選択されています。VTAP は VXLAN トンネルの端点で、IP アドレスはオンプレミスネットワークのルーティング可能なプールから割り当てます。VXLAN 番号は既定値のままで作成します。画面にはゲートウェイが「Phoenix local」と表示されたと聞こえますが、この名称は音声認識の都合で表記が確定できません。
3. Azure の NC2 側でも同じ手順を行います。最初のデプロイから作られた BGP ゲートウェイが表示されています。違いは、フローティング IP を指定する手順です。このフローティング IP は Flow ゲートウェイから取られ、トンネルの外側の接続になります（発話では Flow ゲートウェイが Azure 仮想マシンへのアクセスを持つ数が「50」と聞こえますが、音声認識の都合で確定できません）。
4. 両側のゲートウェイができたら、サブネットの延長を作成します。2 つの環境のオーバーレイネットワークをつなぐ操作です。オンプレミス側が VLAN でも可能なので、Flow Virtual Networking は必須ではありません。
5. 両側に同じネットワーク構成があることを確認します。ゲートウェイ自身は、延長するレンジの中にそれぞれ専用のプライベート IP を持ちます（発話に出た 10.38 で始まる範囲は、音声認識の都合で正確なアドレスが確定できません）。保存します。
6. この画面に含まれないのは、実際の VPN または Direct Connect です。これがすでにあれば、自分で設定できる状態だと説明されています。

### 6.3 DR の有効化と保護ポリシー

1. DR（保護ポリシーとリカバリープラン）は Prism Central に組み込まれていますが、自動では有効になりません。有効化する必要があります。Prism Central は高可用性構成でデプロイされるため、有効化により追加メモリが使われます。
2. 保護対象は、金融ソフトウェアを想定した名前の 2 つのアプリケーション（FinServ App 1 と App 2）の仮想マシンです。IP アドレスの末尾は 200 と 201 で、Azure への DR 後もこの IP を変えないことが目的です。
3. 保護ポリシーは、スナップショットを相手側へどれだけ速く送るかを決めるものです。更新画面では、元の可用性ゾーン（プライマリのクラスター）と、送り先の Azure 側を選びます。
4. 次の画面で復旧時間の目標に当たる間隔を編集します。ステップスケジュール（発話では「24 hourly、7 daily、one weekly」。1 時間ごと 24 世代、日次 7 世代、週次 1 世代と聞こえます）にすると、容量の節約になります。単純な線形のスケジュールも選べます。
5. 保護の対象は、個別の仮想マシンでも選べますが、デモでは「DR: Azure」というカテゴリを使い、これをポリシーに関連付けています。セキュリティポリシーも同様に扱えます。表示すると、金融系の 2 台の仮想マシンが保護されていることを確認できます。更新すると、Azure へのレプリケーションが始まります。

### 6.4 リカバリープランの作成

1. 「Restore to cloud」という名前のリカバリープランを更新します（以前のテスト実行の履歴が表示されています）。名前と復旧先を指定します。リカバリープランは常に復旧先側から実行します。DR が発生したときは元の側へ到達できないのが通常のため、という説明です。
2. 今回は、ステージが 1 つだけの単純な構成です。ステージ間にタイマーによる遅延を入れたり、独自のスクリプトを実行したりでき、ステージは最大 20 まで追加できます。典型的には、ステージ 1 がインフラストラクチャー、ステージ 2 が次の段階のアプリケーションです。リカバリープランは複数作れます。
3. 次のネットワークマッピングでは、レイヤー 2 延長を使う場合、以前はボタンがありましたが、現在は不要になりました。延長されたレイヤー 2 が作成済みで、両側に同じネットワークがあるためです。
4. 静的マッピングが表示されます。これは Nutanix のハイパーバイザー固有の機能で、HVIPAM を使い静的 IP を設定します。DHCP に近いものですが、仮想マシンが存在する限り変わらないため、自動化が簡単になります。保存します。

### 6.5 計画的フェイルオーバーの実行

1. Azure 側の Prism Central（デモ環境の「W2」と呼ばれる環境）に移り、リカバリープランから「Restore to cloud」を開きます。
2. 「計画的フェイルオーバー」を実行します。これは移行に近い操作で、ソースの仮想マシンを停止し、もう一度スナップショットを取ってからフェイルオーバーします。計画外のフェイルオーバーは、移行先にあるスナップショットをそのまま使います。
3. 確認のため、フェイルオーバーと入力して実行します。リカバリープランが走り、仮想マシンが起動し始めます。
4. Azure 上の仮想マシン一覧で、IP の末尾 200 と 201 の 2 台が稼働していることを確認します。仮想マシンは Linux の簡易なものです。

## 7. 注意点・発表者の気付き

- ネットワークは NC2 で最も難しい部分だと明言されています。計画があるか、Azure に詳しい人がいれば単純で、時間がかかる作業という位置づけです。
- DR の保護ポリシーとリカバリープランは組み込みですが、自動では有効になりません。有効化すると、Prism Central の高可用性構成のため追加メモリが使われます。
- レイヤー 2 延長のデモには、VPN や Direct Connect の設定は含まれていません。
- リカバリープランは、復旧先側から実行します。
- Azure Route Server を使わない、より安価な選択肢があるとのことですが、このセッションでは詳細は話されていません。
- デモで使われた IP アドレスの一部や、ゲートウェイの名称は、音声認識の都合で正確な表記が確認できません。

## 8. 利用者にとっての利点

- 仮想マシンやコンテナーを、リファクタリングなしで Azure 上で再起動でき、高可用性、ストレージ、DR の機能が使えます。
- レイヤー 2 延長とネットワークマッピングで、DR 後も IP アドレスを変えずに済みます。
- アカウントを顧客自身が所有するため、Azure SQL など他の Azure サービスへの移行も選べます。
- MST と Blob ストレージの組み合わせで、Azure 上の既存環境がなくても、低コストでスナップショットを保管し、事故のときだけ NC2 クラスターを立ち上げて復元できます。インスタント リストアにより、VM の約 15〜20% を読み込めば作業を再開できます。
- 重要なワークロードにはパイロットライト、それ以外には MST と、使い分けができます。
- セキュリティ STIG の自動化で、3 時間で米国国防総省レベルの設定を用意できます。
- Flow ゲートウェイは最大 4 台で最大 64 Gbps の帯域を持ち、発表者の知る限り、この上限に達した顧客はいません。

## 9. まとめ

このセッションは、障害の原因が自分たちの操作になりやすい時代に、NC2 と Azure を使って DR をどう用意するかを見せるものでした。Nutanix の DR には非同期、ニアシンク、MST の 3 つの方式があり、MST では Blob から必要な分だけを先に読み込んで素早く復元します。

デモでは、可用性ゾーンの接続、VTAP によるレイヤー 2 延長、保護ポリシー、最大 20 ステージまで組めるリカバリープランを順に作成し、計画的フェイルオーバーで IP が 200 と 201 の 2 台を、同じ IP のまま Azure 上で起動しました。
