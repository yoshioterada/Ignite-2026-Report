## 5. 発表内容の詳細

### 5.1 なぜオンプレミスか

オンプレミスに置く理由として、冒頭で挙げられたのは次の点です。

- 厳しいレイテンシー、規制、コンプライアンス、工場設備との連携、データ生成設備への AI 適用
- 事業継続：発表者は、1 週間前にメールの返信が一日来なかった出来事を冗談交じりに挙げ、公共のクラウドへの接続を失ったときに、機械や生産ラインが影響を受けるなら、素早く復旧する手段が必要だと述べています。オンプレミスの基盤をクラウドの補完として持つのは賢明な判断になりやすい、という考えです。

> 補足：メールの件について、原因や障害の名称は発話では確認できません。

### 5.2 Azure Local のおさらい

会場に挙手で習熟度を尋ね、「かなり多くの人が知っている」という反応だったため、知らない人向けに簡単に説明しています。

- Azure Local は、**自分が選んだ場所に置く、Azure の小さな一切れ**です。お客様が所有し、管理する機器の上で動きます。
- コア部分は Windows Server と似ていますが、どんなハードウェアでも使えるわけではありません。動かすだけなら古い機器でも動きますが、サポートを受けるには、Microsoft が公開しているカタログ上のハードウェアを使う必要があります。カタログには Premier Solutions と Integrated Systems の 2 つの階層があり、Dell も載っています。
- ラックに設置して配線した後は、Azure からデプロイし、Azure から監視し、Azure からライフサイクル管理を行い、VM や Kubernetes のコンテナーも Azure から展開します。つまり **Azure がコントロールプレーン（管理の中枢）** です。

導入前に自問すべき点として、「Azure のやり方を受け入れる準備ができているか」が挙げられました。従来型の仮想化基盤の運用のまま使おうとすると、スキル、準備、運用の面で苦労する。無理に従来型の仮想化基盤として使うと不満が出るので、本格導入の前にスキルと考え方を固めておくことが成功に不可欠だ、という趣旨です。

ワークロードについては次のように説明されています。

- Windows Server や Linux の VM は問題なく動きます。しかし発表者は **Kubernetes こそが魅力の中心**だと述べています。
- Azure Local には Kubernetes が組み込まれていて追加費用なしで使えますが、導入済みのお客様の多くはまだ使い始めていない、という認識です。
- Azure で作ったコンテナーのワークロードを、オンプレミスにも同じ方法で展開できます。また Azure から Azure Local に降りてくる多くのサービスの土台が Kubernetes です。

セキュリティについては、Dell を含む OEM や、NVIDIA、Intel、AMD などの部品ベンダーが、シリコンからソフトウェア、クラウド管理までの一貫した安全性に取り組んでいると説明しています。Azure Local のセキュリティ機能（ネットワークのセキュリティや各種設定項目）の多くは、Azure で生まれたものが Azure Local に入ってきたものです。

柔軟性については、大小さまざまな組織が、自社のオンプレミス基盤の進化形として Azure Local を検討しているとのことです。単一種類のサーバーでは足りず、耐環境性を高めた機種や、さまざまな形状（SMB、中堅、大企業向け）が必要になる、そして Microsoft もデプロイの構成や選択肢を広げている、と述べています。

### 5.3 2026 年に GA になった Azure Local の機能

発表者は、2026 年だけで多くの機能が GA になったと紹介しています。

| 機能 | 発表での説明 |
| --- | --- |
| Key Vault との統合（ローカル ID） | Active Directory のない遠隔拠点で、ドメインコントローラーを置かずにシークレットを Key Vault で扱えるため、各拠点に AD を展開する手間が省ける |
| 切断環境へのデプロイ | 外部に接続できないエアギャップ環境やダークサイトにも Azure Local を展開できる。ライセンスモデルが少し変わり、考慮点がある。パブリックな Azure に到達できなくても、ソブリンの目標を満たせる |
| 外部 SAN のサポート | 2026 年 4 月頃（発話では「2604」）に導入。ファイバーチャネルのストレージと、新たに iSCSI のストレージを接続できる。コンピュートとストレージを別々に拡張でき、ハイパーコンバージドだけの場合のように両方を同じ割合で増やす必要がない |
| ラックアウェアクラスター | 大学のキャンパスのように、地下の高速ネットワークで結ばれた 2 か所に設備がある場合、2 か所にまたがる 1 つのクラスターを作れる。一方を失うと、ワークロードが自動的にもう一方へフェールオーバーする（事前に移すこともできる） |

ラックアウェアクラスターについては、**SAN をつなげる構成が現在プレビュー中**で、Dell も Microsoft のプレビュープログラムに参加していると説明されています。この件については、来年の暦年の早い時期にさらに情報が出る、と述べています。また、更新プロセス、VM やワークロードの管理、GPU を使う VM の構成など、毎月細かな改善が続いているとも述べています。

> 注意：ラックアウェアクラスターを SAN 構成で使えるようにする機能は、発話の時点ではプレビューです。一般提供済みのラックアウェアクラスターとは区別して読んでください。

Azure Local の上で動くワークロードやサービスとして、次が紹介されました。

- **Microsoft 365 Local**：Exchange、SharePoint、Skype for Business をテンプレート化して自動展開する。発表者は、外部には届かなくても、社内の全員とメールをやり取りできる、完全に管理された生産性基盤になると説明しています（発話中の一部の製品名は聞き取りが不明瞭です）。
- **GitHub Enterprise Local**：開発者向け。プレビューが終わったところです。
- **Foundry Local**：Azure の Foundry モデルを、テンプレート化・オーケストレーションされた形で Azure Local に展開できる。1 ノードの小さな構成から大きな構成まで対応する。
- **Agentic Retrieval**（旧称 Edge RAG）：自分のオンプレミスのデータに対して、Copilot のような体験をすぐに始められる、構築済みのチャット体験。
- **AI ビデオインデクサー**：カメラの映像を分析する。ゼロから作らず、Microsoft が作ったものを自社向けに調整して使える。
- **Azure Migrate は終了し、Azure Catalyst が登場した**：発表者は「スライドがすでに古くなった」と述べて紹介しています。Hyper-V や VMware など他のプラットフォームから Azure Local へのワークロード移行を助けるものです。
- **Azure Site Recovery が GA**：オンプレミスのワークロードを Azure に保護する。

他にも AVD、SQL Managed Instance などが Azure Local 上で使える例としてスライドに載っていて、今回の会期中に DocumentDB と Blob ストレージの発表もあったと触れています。「もっと Azure のサービスをオンプレミスで動かしたい」と Microsoft に求め続けてほしい、という呼びかけもありました。

### 5.4 Dell のソリューション

Dell には、Azure Local カタログの Premier Solutions 階層にある、2 つの提供形態があります。

| 提供形態 | 構成 | 向いている場合 |
| --- | --- | --- |
| Dell AX system for Azure Local | ハイパーコンバージド | コンピュートとストレージを同じ割合で増やしたい場合。コンピュートの要求がストレージより強い場合 |
| Dell Private Cloud | 分離型（ディスアグリゲーテッド）。外部 SAN を接続 | コンピュートとストレージを別々に拡張したい場合。将来ソフトウェアを変えたい場合 |

#### Dell Private Cloud の考え方

目的は柔軟性です。将来、別のソフトウェアへ方針を変えたくなったときに、それを妨げるハードウェアを渡さない、という考えです。

- 業界標準の汎用ハードウェアである **PowerEdge**（サーバー）と、Dell のストレージ（PowerStore、PowerMax など、今後も拡充）を使います。
- ネットワークは持ち込みです。Dell にもネットワーク製品はありますが、他社製も使えます。
- その上に、Dell Automation Platform を載せ、好みのソフトウェアのデプロイ、オーケストレーション、自動化、修復、廃棄を行います。

発表者はたとえ話として、VMware で始め、1 年後に Nutanix に切り替え、さらに 1 年後に Red Hat を試し、最後に Azure Local にたどり着く、という流れを挙げています（現実にそう頻繁に変えるわけではない、とも断っています）。どの段階でも、同じハードウェアを、前のソフトウェアを廃棄したうえで再展開でき、「このハードウェアはこのソフトウェアのみ対応」といった制限にはなりません。ライセンスは持ち込みで、Dell はソフトウェアからハードウェアまでの全体をサポートします。各ソフトウェアベンダーと検証・認定を受けており、構成は分離型のみです（コンピュートは PowerEdge、ストレージは PowerStore などの Dell ストレージ）。

Azure Local 向けの具体的な構成は次のとおりです。

- サーバーは PowerEdge R660、R670、760、770 などの一般的なラックマウント型（1U、2U）。
- ストレージは PowerStore で、iSCSI またはファイバーチャネルで接続します。
- 「小規模環境でファイバーチャネルのスイッチを使いたくない場合、PowerEdge からストレージへ直接接続できるか」という、よく受ける質問に対し、発表者は「できる」と答えています。スイッチ類への投資を避けたい小規模環境に向く選択肢です。
- ストレージだけ増やしたいときはストレージだけ、コンピュートが必要ならコンピュートノードだけを追加できます。
- PowerStore には、対象モデルについて **6 対 1 のデータ削減率を保証する、金銭的な裏付けのあるギャランティ**があります（利用条件あり）。ハイパーコンバージドを含む比較対象よりもストレージ使用量が少なくなる、という説明です。

### 5.5 Dell Automation Platform のブループリント

Dell Automation Platform では、UI 上で「ブループリント」と呼ばれる、テンプレートまたはワークフローを使います。Azure Local 向けには次の 5 つがあります（Nutanix、Red Hat、VMware、VCF 向けのブループリントも別にあります）。

| ブループリント | 内容 |
| --- | --- |
| クラスターのデプロイ | 裸の機器から Azure Local インスタンスを作る。デモで使ったもの |
| ノードの追加 | 新しいサーバーを受け取り、手動で、またはセキュアデバイスオンボーディングによって、自動的にプラットフォームへ登録する。購入時にセキュアなオンボーディングを設定しておくと、ネットワークにつないだサーバーが自分で自動化プラットフォームを見つけて安全に登録される。既存の Azure Local インスタンスの情報を渡せば、残りを処理する。数分で開始し、数時間でノード追加とインスタンス拡張が完了する。ストレージのマッピングや Azure Local のインストールも含む |
| ノードの修復 | サーバーは動くが、ハードウェア部品の不具合などがあるとき、再イメージ、削除、再追加を通じて正常な状態に戻す |
| ノードの交換 | サーバーが故障したとき。Dell が保証で代替機を送り、新しいサービスタグの機器へ、削除から交換までを一貫して処理する |
| 廃棄（デコミッション） | Azure Local が合わないと判断し、ハードウェアを他の用途に転用するとき。Azure Local を削除して工場出荷状態に戻し、Azure 側に作ったリソースもクリーンアップする |

これらに加えて、次の機能も紹介されています。

- **オートメーションスタジオ**：独自のブループリントを作れる。パートナーがお客様に代わって作ることも、エンドユーザーが自分のインフラの課題向けに作ることもできる。Azure Local へのワークロード展開や、Kubernetes クラスターの展開などが例です。
- **API**：すでにソフトウェア層の自動化があるが、ファームウェアやドライバー、ハードウェア層までは触れない場合に、既存の自動化から Dell Automation Platform を呼び出してハードウェア層の作業を任せられる。

### 5.6 顧客事例：New Belgium

ゲストの Adam 氏は、New Belgium の立場から、Azure Local に至った経緯を話しました。

- 長い間、VMware のワンストップの構成を使ってきた（Adam 氏が会場の聴衆と似た状況として語ったものです）。1〜2 年前、Broadcom と将来について話し合った。
- すでに Azure の顧客でもある。ERP と CRM は Azure 上にあり、データの多くは Fabric にある。
- 分担は次のとおりです。**製造のワークロードとデータはオンプレミス（VCF 上。発話では VCP とも聞こえます）、営業と需要予測のデータは Azure 上**。Broadcom との交渉の結果、製造側では VCF と構築済みの基盤が適切だと判断した。
- Azure Local を知ったとき、この 2 つのプラットフォームの「最良の混合」だと感じた。課題は、製造側のデータを営業・予測のためにクラウドへ送り、またその逆も行うこと。
- スライドには、製造拠点ごとの状況、Azure Local を選んだ理由、Azure Local のノードの写真、Dell のデータ保護が載っていた。クラスターが VMware（vSAN ReadyNode、VxRail）であれ Azure Local であれ、Dell のデータ保護を同じように使っている。
- チームは、自社データセンターで使える機能に期待していた。ネイティブな AX ノードから Dell Private Cloud と Dell Automation Platform への進化を見ると、これを活用しない手はないという。
- **今後の方針**：VxRail や vSAN ReadyNode のクラスターが更新時期を迎えたら、Dell Private Cloud に切り替える。VMware のワークロードを減らして Azure Local を増やしたくなったら、再プロビジョニングで対応できる。
- 製造業なので、オンプレミスのワークロードは常に残る。Azure Local はそこに合う。

Matt 氏が、Ignite で話題の Foundry など、どの点に期待しているかを尋ねたところ、Adam 氏は次のように答えています。

- Foundry のオンプレミス展開に大きな関心がある。
- 2 つの AI の取り組みで始めた。1 つは**製造のデジタルツイン**。自社で最もデータの準備が整っている領域であり、かつ、パブリッククラウドには置きたくない重要なデータでもある。
- オンプレミスなら、モデルや手法を素早く試せて、失敗しても巨額のクラウド費用が発生するリスクが低い。開発者に、外部から隔離された安全な環境を提供できる。
- Azure Local は、Microsoft が機能を少しずつオンプレミスへ降ろしてくるのも利点で、更新を適用するたびに「10 個の新機能が手に入った」と感じる。事業が製造データでより多く実験できるようになる、と述べています。

### 5.7 オンプレミスの AI

Matt 氏は、オンプレミスの AI は選択肢が多くて圧倒されると述べています。Foundry Local、Agentic Retrieval、AI ビデオインデクサー、各種 Copilot などです。

- **Foundry Local は無料**で、自分に合った速度で始められる。小規模な環境（Dell AX system や Dell Private Cloud 上の、CPU で動くモデル）から始め、外部ストレージを備えた大きな Azure Local クラスターに育てられる。GPU は NVIDIA の L4 や RTX 6000 Pro などが挙げられた。
- さらに大きな要求向けに、**2027 年上期（来年前半）に Dell AI Factory の一部を市場投入する**予定。オンプレミスで大規模な AI を動かすために調整・最適化された構成で、Dell Private Cloud for Microsoft の一部。ブループリントで紹介した自動化、オーケストレーション、拡張、修復がそのまま適用される。
- ハードウェアは、NVIDIA HGX を採用した、GPU を詰め込んだ非常に大規模なシステムで、機種名として XC9780 が挙げられた。安くはないが非常に強力、という説明。
- DIY で組むと、自社でもどのベンダーにもサポートしにくいものができるリスクがある。オーケストレーション、自動化、設計、検証、承認、サポートが揃った構成を選ぶ利点が大きい、という考え。

## 6. デモ・手順

デモは画面を使って行われました。発話で語られた範囲だけを、語られた順に書きます。画面の細部は音声からは確認できません。

### 6.1 クラスターのデプロイ（Dell Automation Platform）

1. UI の 5 つのブループリントのうち、一覧の下にあるクラスターのデプロイを選び、「デプロイ」をクリックする。
2. 名前を付ける（発話では「AZL deploy001」）。
3. フォームをすべて手入力すると時間がかかり、間違いも起きやすいため、**JSON をインポート**する。標準化でき、誤りを減らし、複数のデプロイで繰り返し使える。
4. JSON には次の情報が入っている。
   - 対象ノード（この例では 2 ノード）と IP アドレス。サーバーにソフトウェアが残っていても、消去して上書きする。
   - ライセンスの選択。Dell が用意した、Dell サーバー向けに最適化された Azure Local のゴールデンイメージの場所。
   - ネットワーク設定（DNS、NTP など）。
5. ストレージの対象を選ぶ。選択肢は 2 種類。
   - **プラットフォーム統合**：ボリュームの作成、ホストへのマッピング、ポリシーや MPIO の設定などを自動化プラットフォームが実行する。デモではこちらを選び、PowerStore に接続している。
   - **プラットフォーム互換**：ストレージ設定は自分で行う。設定の検証はするが、ボリューム作成などは代行しない。
6. Azure 固有の設定を入れる。クラウドの種類、リージョン、リソースグループ、サブスクリプション、Azure Arc ゲートウェイを使うかどうか。
7. 「自動化プラットフォームが Azure Local インスタンスの展開を最後まで行うか」のチェックボックスを決める。チェックすると標準的な Azure Local インスタンスだけが展開される。プレビュー中のラックアウェアクラスターや、Key Vault によるローカル ID などは現状のブループリントでは非対応なので、その場合はチェックを外し、残りを Azure portal で行う。デモではクラスターの自動作成を許可している。
8. 最後の Azure 固有設定を入れる（Active Directory 連携、ドメインなど）。セキュリティ設定は Dell の推奨設定を選ぶ。この設定では、**クラスターボリューム（LUN）の BitLocker を無効**にする。PowerStore 自身が暗号化するため、同じボリュームで二重に暗号化するべきではない。Azure portal の汎用の推奨設定では BitLocker が有効なので注意が必要、と発表者は自身の経験として述べている。
9. ネットワークの最終設定を入れる。Azure portal で設定する内容と同じものを、ここで取りまとめ、「デプロイ」時に Azure へ送る。
10. 認証情報は、自動化プラットフォームにセキュアなシークレットとして保存し、処理の途中で呼び出させる。平文の認証情報を共有しなくて済む。
11. 「次へ」「デプロイ」をクリックする。2 ノードのクラスターで、裸の機器から使える Azure Local まで、**約 5〜6 時間（やや短い場合もある）**。ストレージのプロビジョニングやマッピングも含む。

### 6.2 すでにデプロイ済みの環境での工程の確認

別の、すでにデプロイ済みの環境に切り替えて、工程の図を拡大しながら説明しています。

1. 開始のあと、**最初に検証**を行う。Azure への接続、Key Vault 名の重複、同名の Azure リソースの有無、ハードウェアが均質か、互換性チェックを満たすか。深く設定した後で失敗するよりも、早い段階で失敗させるため。
2. 追加の検証と、Azure Local 用の**システムプロファイルの適用**。BIOS、ファームウェア、iDRAC を最適化する（Azure Local、VMware、Red Hat、Nutanix など、展開するソフトウェアに応じて異なる）。NIC のファームウェアも更新する。一般的な自動化ツールでは到達しにくい粒度だが、API 経由で可能になる。
3. プロビジョニング。ベアメタルの PowerEdge に最新の Azure Local ソフトウェアをイメージとして展開する。
4. ストレージの構成。LUN の作成、ノードへのマッピングなどを自動で行う。
5. Azure 側の処理。ノード（この環境では 4 ノードと発話）を Azure Arc に登録する。
6. ウィザードで入力した内容を使って ARM テンプレートを実行し、Azure Local インスタンスを作る。

### 6.3 展開後の検証で見つかった問題

発表者は、わざと残した例として、デプロイは成功し、Azure portal ではすべて緑（正常）なのに、Dell が実装した展開後の検証では**NIC に問題がある**と出たログを見せました。Azure Local の展開自体はこの問題を検出しなかったが、追加の接続テストで異常が見つかったとのことです。ネットワークの問題（パケット損失やケーブル不良の可能性）をスイッチ側で調べる必要があり、Azure の管理画面だけでは気づけなかった、という説明です。

## 7. 注意点・発表者の気付き

- **Azure Local は、Azure のやり方を受け入れられる組織に向く。** 従来型の仮想化基盤の運用を持ち込むと苦労する。導入前に、スキルと進め方を固める。
- サポートを受けるには、Microsoft のカタログに載ったハードウェアを使う。
- 切断環境にデプロイする場合は、ライセンスモデルが少し変わり、考慮点がある。
- Dell Automation Platform が「最後まで展開する」を選ぶと、標準のインスタンスしか作れない。ラックアウェアクラスター（プレビュー）や Key Vault によるローカル ID は、現状のブループリントでは非対応なので、チェックを外して Azure portal で続ける。
- PowerStore 側で暗号化する場合、Dell の推奨設定ではクラスターボリュームの BitLocker を無効にする。Azure portal の汎用の推奨設定では BitLocker が有効になるので注意する。
- 6 対 1 のデータ削減率の保証は、対象の PowerStore モデルに限られ、条件があります。
- Dell Private Cloud は分離型の構成のみです。ハイパーコンバージドが不要になるわけではなく、依然として重要な場面があると、発表者は述べています。
- 顧客事例で語られた効果は Adam 氏自身の見解です。数値による効果は、発表では語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **自動化による構築の簡素化と再現性**：JSON のインポートで標準化でき、裸の機器から数時間で Azure Local を展開できる。ノードの追加、修復、交換、廃棄も、ブループリントで自動化できる。
- **早期の失敗**：展開の最初に検証を行い、問題があれば早く止める。展開後にも追加の接続検証を行う。
- **ファームウェアなど下位層まで自動化**：システムプロファイルの適用、BIOS、iDRAC、NIC ファームウェアの更新。既存の自動化から API で呼び出せる。
- **ロックインの回避**：同じハードウェアで VMware、Nutanix、Red Hat、Azure Local を入れ替えられる。顧客の New Belgium は、VxRail や vSAN ReadyNode の更新時に Dell Private Cloud へ移行する方針で、VMware を減らして Azure Local を増やす場合も再プロビジョニングで対応する。
- **コンピュートとストレージの独立した拡張**：不要な構成を買い足さずに、要件に合わせられる。発表者は、ストレージ容量の効率とコンピュートの効率によって、大きなコスト削減につながり得ると述べています。
- **ストレージの削減**：対象の PowerStore モデルでは、6 対 1 のデータ削減率の保証がある。
- **ソブリンの要件への対応**：切断環境への展開、データと制御がお客様の手元にあること。
- **段階的な AI の始め方**：無料の Foundry Local を小さな環境から始め、大規模な AI Factory まで広げられる。New Belgium は、製造のデジタルツインで、安全に隔離された環境で実験できることを利点に挙げた。

## 9. まとめ

Azure Local は、規制、遅延、事業継続、工場設備との連携といった理由で、パブリッククラウドに置きにくいワークロードを、Azure のやり方のまま自社の場所で動かすための基盤です。Dell は、ハイパーコンバージドの Dell AX system と、コンピュートとストレージを分離して外部 SAN をつなぐ Dell Private Cloud を提供しています。

Dell Automation Platform のブループリントにより、デプロイからノードの追加・修復・交換・廃棄までを自動化でき、デモでは、展開の設定から工程の確認までを見せ、2 ノードのクラスターで裸の機器から約 5〜6 時間で Azure Local を展開できると説明されました（所要時間は発話による説明で、実際に計測して見せたものではありません）。展開後の追加検証が、Azure portal では見えない NIC の問題を見つけた例も紹介されています。製造業の New Belgium は、VMware の更新時期に Dell Private Cloud へ移行する方針を語りました。

AI については、無料の Foundry Local を小規模から始められ、さらに大規模な要求には 2027 年上期に Dell AI Factory（発売前）が予定されています。パートナーには Dell Private Cloud の認定取得が勧められ、お客様には Dell Services による支援が案内されました。
