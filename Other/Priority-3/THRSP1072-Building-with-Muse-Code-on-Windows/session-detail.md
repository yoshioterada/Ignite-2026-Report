# THRSP1072 Building with Muse Code on Windows

## 1. はじめに

このセッションは、Meta Super Intelligence Labs で Muse code とエージェント型ワークフローに取り組んでいる Evgeni 氏が、**Muse code** を開発ワークフローに組み込む方法を約 25 分で紹介するものです。Muse code は、Muse モデルで動くコーディングエージェント（ハーネス）で、CLI から使えるほか、GitHub や Azure のパイプライン、独自の UI、既存のエディタにも組み込めると説明されています。

全体を通した主張は、エージェント型ワークフローは「トークンを食う高価なもの」という思い込みがあるが、Muse code はサブエージェントによる並列実行を前提にしており、**トークン効率も予算効率も良い**という点です。その根拠として、SVGO ライブラリの Rust 書き換えで 71 million トークン・約 31 ドルという数字が示されました。

デモは多く、Rust への書き換え、スキル生成、フック、Blender による 3D 再現、GitHub Actions / Azure Pipelines での自動修正、セッションプロトコルを使った Windows デスクトップアプリの作成が順に行われます。

## 5. 発表内容の詳細

### 5.1 CLI と harness の特徴

Evgeni 氏は、CLI はソフトウェア開発者にとって「シンプルで速く、使いやすい」ものであり、Muse の harness も同じだと述べています。harness は Muse モデルで動くエージェントで（発話は "query agent" と聞こえ、正確な表現は確定できません）、長時間のデータベースマイグレーション、自動修正、複数ファイルのレビューなどのタスクを与えます。設計上は、サブエージェントでの作業を重視しています。

### 5.2 デモ：SVGO ライブラリを Node.js から Rust へ書き換える

「AI 時代にエンジニアが好んでやることの一つが、何かを Rust で書き直すこと」という前置きで、Node.js の SVGO ライブラリ（SVG アセットを最適化するライブラリ）を Rust で書き直すライブデモが行われました。SVGO には主要モジュールが 6 つと、ヘルパー関数用のモジュールが 1 つあるという説明です。

harness の動きは次のように説明されています。

1. リードエージェントがプロジェクト構造を分析し、作業をサブエージェントに分割する
2. 各サブエージェントはチャンネルを通じて互いに連絡できる。例えば共有されるヘルパーモジュールを担当するエージェントが、その情報を他のエージェントへ伝え、全体で作業を進める
3. 作業が終わると、harness が自動で「パリティエージェント」を起動する。パリティエージェントは元の Node.js ライブラリに対するベンチマークテストと品質テストを実行する

プロンプトは「SVGO ライブラリを Rust で、マルチコア CPU 処理に重点を置いてサポートする」という趣旨でした（発話では "support the SVGO library in Rust, focusing on the multi-core CPU processing"）。画面では 6 つのサブエージェントが並列で動き、完了後にパリティエージェントが移行結果を分析してテストを書き、Node.js 側のテストも通ることを確認しました。結果は次のとおりです。

| 項目 | 結果 |
| --- | --- |
| サブエージェント数 | 6 |
| テスト | 元ライブラリのテストをすべてパス |
| 速度 | マルチコア処理で約 2.2 倍 |
| トークン消費 | 71 million |

### 5.3 他の harness とのコスト比較

Evgeni 氏は、harness 間で「正直なテスト（honest tests）」を設定したと述べています。すべてのエージェントを最大 effort で動かした結果、Muse code は **37 分で完了し、費用は 31 ドル**でした。同氏の説明では、"cloud code"（音声認識の表記。Claude Code を指すかどうかは発表からは確定できません）はトークンをより多く使う傾向があり、"Codus"（同様に表記が確定できません）も意外に良い結果でした。具体的な他社の数値は、音声からは示されていません。

結果の差には、例えばコードベースが訓練データに含まれていたかどうかなど、いくつかの理由があり得るとも述べています。出力品質については、各エージェントともよい仕事をしており、多くが実行速度を向上させたと評価しています。Muse code の 71 million トークン（31 ドル）は、サブスクリプションで使えば、上限が十分に大きいので無料になる、とのことです。

### 5.4 スキル生成とフック

harness を柔軟にし、他の harness からの移行を楽にするため、使い勝手を上げる機能が追加されたと説明されています。

**セッションからのスキル生成**：harness がセッションのログを自動で分析し、ツール呼び出しを抽出して、トークン消費が少なくなるよう最適化されたスキルを作ります。デモでは、プロジェクトをまたいで再利用でき、自動でインストールされるスキルを作るよう依頼しました。このスキルは、コードをレビューして PR のノートを作成します。スキルがインストールされた後、変更点のレビューと GitHub への PR 公開を実行し、PR が公開される様子が示されました。Evgeni 氏は、これは基本的な例で、長くて複雑なセッションからのスキル抽出もできると話しています。

**ライフサイクルフック**：harness には 15 を超えるライフサイクルフックがあり、harness のライフサイクルを制御できます。モデルがプロンプトとして何を受け取るかを制御したり、プロンプトが送信される前にフックを走らせたりできます。デモでは、プロジェクトの環境変数を守る「ガードフック」を作りました。モデルによる環境変数の読み取り・書き込みを防ぐもので、秘密鍵を環境変数に追加させようとすると、harness がエラーを受け取り、読み取れない理由が表示されました。

### 5.5 デモ：Blender による 3D 再現

研究者が力を入れている領域として、3D と Blender が紹介されました。コードには強い harness が多いが、3D ではどうか、という問いかけです。3D では、エージェントとモデルの間に良い協調ループが必要だと説明しています。

- 実行役（executor / builder）のエージェントが作業を終える
- 批評役（critic）のエージェントが結果を分析し、修正を送る
- 望む結果になるまでこのループを繰り返す

最初の例として、部屋の画像を渡して部屋を再現させた結果が紹介されました。GPU が良いほど、制限時間内に回せる反復が増えます。この例では 2 時間に制限し、修正は 4 ラウンドでした。

続けて、同じデモを再度行いました。条件は次のとおりです。

- 時間制限は 3 時間
- Windows マシンの GPU が弱いため CPU レンダリングになり、5〜6 ラウンド程度で、数ラウンドごとに約 35 分かかる
- 既存のテクスチャを再利用しないよう、プロジェクトは空の状態にする
- プロンプトは、Blender 5.2 を使って画像にできるだけ近づけて再現するよう依頼する内容

画面では、最初のビルドが終わるとレビュー（critic）エージェントが起動して修正を次のエージェントへ送り、このループを 5 回繰り返しました。ラウンドごとに、元の画像に近づいていく様子が示されています。最後に、作成された部屋のフライスルー映像も見せています。

コストは、約 **24 million トークン、約 16 ドル**（現在のトークン価格で）でした。サブスクリプションの上限に達することは考えにくい量とのことです。

### 5.6 ヘッドレスモード（muse exec）

成熟したプロジェクトには、Azure Pipelines や GitHub のパイプラインがあります。AI エージェントをそこへ組み込むために、Muse には `muse exec` コマンドがあります。説明された特長は次のとおりです。

- 1 回の実行で消費できるトークン数を制御できる
- JSON スキーマを渡して、エージェントに期待する出力の形式を指定できる
- タスクにかかったトークン数とターン数が取得でき、ワークフローの最適化に使える

Evgeni 氏は、これを使って組み込める「現実的な」パイプラインとして、次の 5 つを挙げました。

1. GitHub リポジトリの issue を AI エージェントに任せる
2. PR を常時レビューし、セキュリティ問題を探すセキュリティループ
3. 公開 Web サイトを変更するたびに Lighthouse の指標が悪化しないかを確認し、悪化したら AI に自動修正させるサイト監査
4. すべての PR で A/B テストを実行し、結果を分析して、劣化があれば修正させるパフォーマンス分析
5. コードベースを巡回して継続的に最適化するエージェントチーム

### 5.7 デモ：GitHub Actions での issue 自動修正

GitHub Actions でのパイプラインは次のように単純だと説明されています。

1. issue に `muse fix` ラベルを付ける
2. `muse exec` が、コードベースと issue を分析する
3. PR を公開し、再発防止のための回帰テストも付ける

デモでは、先ほど Rust に移行した SVGO のパーサに、色を誤って変換する問題がある、という issue を使いました。issue に muse fix ラベルを付けると GitHub Actions のワークフローが動き始め、Muse がコードベースを分析して問題の修正に取りかかります。Muse はバグを再現し、修正を作り、回帰テストを実行して、既存テストがすべて通ることを確認しました。完成した PR には、何が問題だったか、どのようなガードレールを入れたかの説明も付いています。この PR は後でマージできる状態になったと述べています。

### 5.8 デモ：セキュリティレビューのループ

最近はセキュリティ問題が多く、毎日多くのコードをマージするパイプラインでは、脆弱性を持ち込まないことが重要だと説明されています。設定するワークフローは、PR ごとに次の流れで動きます。

1. 読み取り専用モードの Muse が PR のセキュリティ問題を分析する
2. 推奨事項を別の Muse エージェントに渡す
3. そのエージェントが修正を適用し、テストが通ることを確認する
4. セキュリティレビューが通って PR がグリーンになるまで、これを繰り返す

デモでは、SVGO に「SVG アセット内に画像をインライン化する」機能を追加する PR を使いました。この変更により、攻撃者がユーザーフォルダのローカルパスを挿入すると、そのユーザーファイルが SVG にインライン化され、ファイルにアクセスされる問題が生じます。Muse はこれを critical なセキュリティ問題として検出し、コードベースを分析して、修正を含む新しい PR を公開しました。続けて 2 回目のレビューが走り、コードが修正されて PR のチェックがグリーンになり、マージできる状態になりました。

### 5.9 デモ：パフォーマンス回帰（Azure Pipelines）

パフォーマンスに敏感なパッケージで、性能劣化を持ち込まないためのワークフローです。PR ごとにパフォーマンスのベンチマークを実行し、エージェントが結果を分析して、問題があれば PR を自動で修正します。このデモは Azure Pipelines で行われました。

画面では、PR が理由不明のまま **57% 遅く**なっていました。この結果を Muse エージェントに渡すと、結果を調査してコードを分析し、修正してテストを実行し、性能劣化が解消されたことを確認します。そのうえで、何をどう直したかの説明付きの PR を公開し、劣化のない状態でマージされる流れが示されました。

### 5.10 デモ：サイト監査（Lighthouse）

常に更新される Web アプリでは、新しいページを追加しても、SEO（発話は "CO score" と聞こえます）やアクセシビリティのスコアが高いことを保つ必要があります。そこで、PR ごとに Lighthouse テストを実行し、スコアが悪化したら Muse に作業させて、修正付きの PR を公開させます。

デモでは、SVGO パーサ用のギャラリーページを追加する PR を Muse に分析させ、Lighthouse のチェックを実行しました。アクセシビリティと SEO（音声は "as a CEO"）に劣化が出ました。エージェントがコードを分析すると、area 属性（音声認識の表記で、aria 属性を指すかは発表からは確定できません）やラベル、見出しなど、アクセシビリティに重要な属性が不足していました。エージェントはこれを修正し、Lighthouse スコアの高い状態で PR を再公開しました。

Evgeni 氏は、より複雑なサイトでは、コードの分析とテストにエージェントがもっと長く動く必要があり、ここまで簡単にはいかないと断っています。

### 5.11 コードモダナイザー

最後のパイプラインは、エージェントチームがコードを巡回し、継続的に更新する「コードモダナイザー」です。例として、Rust の crate パッケージを、モダンな Rust の構成へ常時更新するパイプラインが挙げられました（画面操作の描写は音声にありません）。これを定期実行のジョブ（発話は "Chrome job"。cron job のことと思われます）にすれば、コードを定期的に更新し続けられると説明しています。ここまでの 5 つの例は、自分のパイプラインに組み込める「レゴブロック」だという位置づけです。

### 5.12 Muse session protocol と SDK

自分でエージェントを作りたい場合のために、Muse CLI は **Muse session protocol** の上で動いています。このプロトコルでは、CLI とインターフェースを拡張できます。SDK が提供されており、Muse code を土台に独自のクライアントやエージェントを作れます。

プロトコルはシンプルで、SDK を通して処理できるイベントが送られてきます。各セッションは initialize イベントで始まり、セッションの開始と終了の間に、エージェントからの質問、トランスクリプトの内容など、セッションに関するイベントを受け取ります。

### 5.13 デモ：Muse session protocol で Windows デスクトップアプリを作る

プロトコルの使いやすさを示すため、Muse code 用の Windows デスクトップアプリをプロトコル上で作るデモが行われました。

- 左側：新しいセッションプロトコルから得るセッション一覧
- 右側：動作中の並列エージェント
- 中央：質問と入力欄（composer）を含むトランスクリプト

テンプレートを渡し、Muse Code SDK をエージェントに与えて、アプリの再現を始めます。セッション一覧、composer、トランスクリプト、並列エージェントの表示が順に出来上がりました。この作業には約 40 分かかったとのことです。SDK には公開ドキュメントがあります。

アプリが実際に動くことの証明として、このアプリを使って簡単な**フォトエディタ**を作るデモも行われました。10 個のサブエージェントが動いて完成し、トークンは 1 million 未満でした（音声は "less than 1 million talking"。tokens を指すと考えられます）。フィルターを適用できる UI を持つ簡単なフォトエディタです。Evgeni 氏は、独自の harness も作れる、また GitHub 上にはこのセッションプロトコルを使った独自 harness がすでに多く登場している、と述べています。

### 5.14 ACP モード

既存のエディタがある場合は、ACP モードで組み込めます。発表では、Muse は agent session protocol をサポートしており（音声認識の都合で、この名称の表記は確定できません）、既存のパイプラインに組み込めるため、別の harness に乗り換える必要はなく、そのままで動く、と説明されています。具体的な設定手順やデモは、発表にはありませんでした。

GitHub Actions でのパイプラインの手順は、発表では次の 3 ステップで語られています（コマンドやワークフローの記述は示されていません）。

1. issue に `muse fix` ラベルを付ける
2. `muse exec` コマンドでコードベースと issue を分析する
3. PR を公開し、回帰テストも付ける

## 7. 注意点・発表者の気付き

- コスト比較は、発表者自身が設定したテストの結果です。他のエージェントとの差には、コードベースが訓練データに含まれていたかなど複数の理由があり得ると、発表者自身が断っています。
- 3D の作業は GPU の性能に左右されます。GPU が良いほど、制限時間内に回せる反復が増え、出力が良くなります。Windows マシンで CPU レンダリングを使う場合は、数ラウンドごとに約 35 分かかります。
- 複雑な Web サイトでは、サイト監査の修正は例ほど簡単ではなく、コードベースの分析とテストにエージェントが長く動く必要があります。
- 環境変数など機密性の高い情報へのアクセスは、フックで制限できます。

## 8. 利用者にとっての利点

発表では顧客事例は紹介されていません。語られた効果は次のとおりです。

- Rust 書き換えで約 2.2 倍（マルチコア）の高速化を得ながら、トークンは 71 million、費用は約 31 ドル、所要は 37 分
- サブスクリプションで使えば、上限が大きいので、これらの作業は追加費用にならない
- 3D 再現のような大きな作業でも、約 16 ドル程度
- issue 修正、セキュリティレビュー、性能劣化の修正、アクセシビリティ修正、コードの更新を、既存の GitHub / Azure のパイプラインに組み込める
- 他の harness から移行する場合も、スキル生成やフックで運用を調整できる

## 9. まとめ

Muse code は、サブエージェントを並列に動かすコーディング harness で、発表では「トークン効率が良く、予算を抑えられる」ことが繰り返し強調されました。CLI での大規模な書き換えや 3D 作業、`muse exec` によるヘッドレス実行で GitHub Actions と Azure Pipelines に組み込む 5 種類の自動化、Muse session protocol と SDK による独自クライアント作成、ACP モードによる既存エディタへの統合という 4 つの入口が紹介されました。SDK のリンクと Muse code のダウンロード用 QR コードがスライドに示され、質問は発表後に個別に受け付けるとされました。
