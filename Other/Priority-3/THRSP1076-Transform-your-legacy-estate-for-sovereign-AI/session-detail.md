# THRSP1076 Transform your legacy estate for sovereign AI

## 1. はじめに

このセッションは、**Concerto** のチームが、自社のプラットフォームを紹介する発表です。Concerto は「ソブリン・インテリジェンス・プラットフォーム」と説明され、社内の境界の内側で完結する AI 環境（ソブリン層）の上に、エンドユーザー向けの生産性アシスタント、エンジニア向けのコーディングアシスタント、そしてクラウド移行・モダナイゼーションのための変革エンジンを載せた構成です。

発表の主張は、「変革を数か月で終えること」「インフラ・アプリ・データベースの各層を一緒に動かすこと」「すべてを自社の境界の中に留めること（ソブリン）」の三つを、どれかを諦めずに両立できる、という点です。トークン課金がなく、利用量はプロビジョニングした環境の容量で決まる点も繰り返し強調されています。

## 4. 発表者が伝えたいメッセージ

Prashant 氏は、企業が置かれた状況を次の二つの要求の板挟みとして説明しています。

- 変革を、従来のような年単位ではなく **数か月** で終えること。インフラ層、アプリ層、DB 層をまとめて近代化すること
- 同時に、すべてを自社の境界の内側に **ソブリン** に保つこと

どちらかを犠牲にしがちなところに、「選ばなくてよいプラットフォーム」を提示するというのが、全体の主張です。具体的には、アーキテクチャ上最初からソブリンで、自社の境界（Azure の VNet か、組織が選ぶ他の環境）の中で動き、アプリ・インフラ・DB の変革から、AI アシスタント、コーディングアシスタントまで全部入りで、しかも **無制限**（トークン課金なし）である、という点を挙げています。トークンコストがなく、使える量はプロビジョニングで決まるので、AI をすべての従業員に民主化できると述べています。

CG Joseph 氏は、変革を「フェーズごと、チームごとの縦割り」で進める従来のやり方を否定します。数年前までは、まず一つのチームが統合アセスメントを行い、3、4 か月後に別のチームが別のソリューションを持って移行を始める、といった形が一般的でした。ときには移行チームとモダナイゼーションチームが、互いの作業を知らないまま並行して動くこともあります。CG Joseph 氏はこの状態を「phase blindness（フェーズごとの視野の狭さ）」や縦割りの進め方と呼んでいます。Concerto は、これらを一つにつなぐものだと説明しています。

### 5.3 変革エンジンの概要（CG Joseph 氏）

CG Joseph 氏は、変革エンジンは 5 つまたは 6 つのソリューションが積み重なり、つながっている構成だと説明しました。数字としては、**80 社以上のパートナー**、**300 件以上の顧客エンゲージメント**（日々増加）、**23 か国** での利用を挙げています。

特に紹介されたのは次の二つです。

- **Concerto Migrate**：スケールとスピードを表す二つのキーワード「Cloud Ignite」と「Cloud Mock」（音声認識の都合で表記が確定できません）を使う。エージェントレスのディスカバリーで、インフラだけでなくアプリケーションやデータを含めた相互関係を把握し、アセスメントを **48 時間未満** で出せる。数年かけた移行計画ではなく、変革の期間を数か月に圧縮してきたと述べている
- **Concerto Modernize**：モダナイゼーションの前に、アプリケーション環境を理解し、モダナイズできる状態かを判断する。この詳細なアセスメントを行うのが「Compass」（聞こえた表記）というソリューションで、アセスメントしたことを実行する Modernize Studio も含まれているので、別のソリューションに頼る必要がない

CG Joseph 氏は、これらすべてを、**エアギャップ（air gap）のデプロイで 100% の egress 保護** をかけたソブリン AI ソリューションの中に載せて展開していくと述べています。

### 5.4 コントロールプレーン「Orchestra」

Prashant 氏は、特に注目を集めている層として、コントロールプレーン（発話では「orchestra」）を紹介しました。ここで企業のデプロイ、ユーザーの利用状況、ガードレールを管理します。説明された機能は次のとおりです。

- 企業全体の利用状況の確認
- **ソブリン性のメトリクス**：定義したガードレールを超える外部への流出がないか、ブロックされたポリシーがあるか、などのダッシュボード
- **コンシューマプション（消費量）の比較**：公開されたトークン課金型のシステムを使った場合の同等コストを、期間ごとに測れる。Concerto は無制限で境界内で動くため、誰が何をどれだけ使うかを組織側で決められる
- 他のアプリケーションやデータの登録。Salesforce、SQL Server など、企業内のデータソースを定義でき、これでモデルが一般的なものではなく自社の事情を知ったものになる
- 社内開発のアプリケーションが使える API キーの有効化
- 他のモデルの登録。Concerto が標準で提供するモデルだけでなく、オープンウェイトのモデルを基に自社で作ったモデルや、他の公開 LLM も登録できる
- ユーザー管理。組織の既存のデプロイから継承したロールベースのアクセス制御ができる
- セーフティルールとガードレールの設定。アプリケーションごとに、既存のものを使うか新しく設定し、監視できる
- 複数の言語での表示

## 6. デモ・手順

### 6.1 デモ 1：アシスタント、コーディングアシスタント、Orchestra（Prashant 氏）

Prashant 氏は、感触をつかんでもらうための簡単なデモであり、詳細はブースで見せると断ってから切り替えました。

1. **Concerto のアシスタント**（発話では「C composer」と聞こえます）：一般的な AI アシスタントと同様に、プロンプトで質問する。エンタープライズのナレッジを学習したモデルが使われ（発話では「C tunes」と聞こえます）、すべてのプロンプトは境界内にとどまる。外部の Web 検索に出る場合は、どの範囲まで出てよいか、何を公開してよいかをガードレールで定義できる。プロジェクト、アーティファクト作成、ドキュメントやプレゼン資料の作成など、他のアシスタントで使う標準機能も備えている
2. **コーディングアシスタント**：VS Code などの拡張機能としてインストールできる。簡単な To-Do アプリを作るプロンプトを与えると、HTML、スタイルシート、JavaScript を生成し、完了後すぐにローカルホストにデプロイして、使えるアプリが立ち上がる。時間の都合で詳細には入らなかった
3. **Orchestra（コントロールプレーン）**：5.4 に挙げた、利用状況、ソブリン性メトリクス、消費量の比較、データソースや API キーやモデルの登録、ユーザー管理、ガードレール設定の画面を順に説明した

### 6.2 デモ 2：Concerto Migrate のビジネスケースと統合アセスメント（Gopi 氏）

Gopi 氏は、10 分程度で事業案件を作れることを説明しつつ、時間の都合で TCO をライブで生成するのは難しく、すでに作ってあるものを見せると述べました。語られた内容は次のとおりです。

**ビジネスケース（TCO レポート）の作成**

1. 簡単なインベントリ（「RV tool」などのファイル。聞こえた表記）があれば、10 分未満でビジネスケースを作れる
2. 会話型のインターフェースで、インベントリファイルをアップロードし、Azure のどの価格モデルを使うかなどの質問に答える
3. CMDB や、監視ツールから得た使用率メトリクスがあれば、それも追加でアップロードできる
4. 数分で、オンプレミスの現状コストと Azure に移行した場合のコスト、ROI を含む TCO レポートが生成される。顧客にそのまま提出できる内容で、現状の支出と Azure での想定支出の財務サマリーが入る
5. インフラ分析が詳細にまとまり、顧客の環境をどのように Azure のインスタンスに対応付けるか、移行すべきでない VM（アプライアンス、電源が切れている VM、プリントサーバーなど）は自動で除外される
6. 単純な VM 対 VM の対応ではなく、ワークロードの種類を判定して適切な Azure サービスに対応付ける。例として、監視ツールは Azure Monitor に、ファイルサーバーやログサーバーは VM としてではなく Blob Storage に対応付ける。ストレージも、高価なディスクにすべて載せるのではなく、適切な場合は Blob を使う
7. 結果をレポートにして持ち帰れるため、翌日には顧客に戻れる

**ライブディスカバリーと統合アセスメント**

1. ビジネスケースが承認されたら、同じエージェント機能で、顧客環境のライブディスカバリーを実行し、データベース、アプリケーション、相互依存関係などの詳細情報を収集する
2. ディスカバリー結果は、プラグインのような形で提供され、「統合アセスメント（unified assessment）」と呼ばれる。インフラ、データベース、アプリケーションの 3 つの観点を扱う
3. インフラの観点：検出された VM 数、CPU の総数、メモリの総量、Azure に移行する可能性のあるディスク容量
4. データベースの観点：使われているエンジン（SQL、Oracle など）、Enterprise エディションか Standard エディションか
5. アプリケーションの観点：どんなアプリケーションを使っているか、パッケージ製品か自社開発かの内訳（この箇所は音声認識で語が不明瞭で、確定できません）
6. アプリケーション依存関係マッピング：アプリ同士の接続、内部依存、外部依存を示す
7. アプリケーションの重要度マッピング：連携の複雑さや、社内向けか外部向けかなどをもとに、スコアカードが自動で作られ、どのアプリが重要かが分かる
8. 先に作った方向性を示す TCO より詳細な TCO レポートも作られる。Azure に移行したときのコストと ROI が分かる
9. ウェーブ計画：アプリケーションを何回に分けて移行するかを計画し、プロジェクトの期間を決められる。例として 20 週間で終えたい場合は週数を選び、必要な帯域を計算する。1 Gbps 接続（聞こえた表記は「GBBS」）しかないと、20 週間では終わらないという警告が出て、帯域を増やす必要があると分かる

Gopi 氏は、これらによりアセスメントと計画が「データドリブン」な作業になると述べました。Modernize を含む残りのモジュールの詳細は、ブースでの説明に回しています。

- 生産性スタックとソブリン層の無料トライアルが提供されている。顧客案件があれば、会場にいる間に無料アセスメントを実施するとのことです

## 9. まとめ

Concerto は、シリコン層を含む 4 層（生産性層、変革層、ソブリン層、シリコン層）のスタックを、顧客の境界内でトークン課金なしに動かすプラットフォームとして紹介されました。Prashant 氏はアシスタント、コーディングアシスタント、Orchestra で「データを外に出さずに AI を使い、組織が使い方を管理する」ことを示し、CG Joseph 氏と Gopi 氏は、Concerto Migrate でビジネスケースから統合アセスメント、ウェーブ計画までを短期間で進める流れを説明しました。

Azure と組んで推進している提案は、SQL Server から Azure SQL、VMware から Azure、Oracle から Azure PostgreSQL の 3 つです。聴衆への案内は、ブース 5435 番への来訪、無料トライアル、顧客案件を持ち込んだ場合の無料アセスメント、concerto.com または concerto.ai です。
