# THR980 Who Owns This Agent? Identity, Data, & Control across Microsoft Clouds

## 1. はじめに

このセッションは、Microsoft Foundry で作ったエージェントを本番に出す前に、「誰がそのエージェントを所有するのか」「どの ID で動くのか」「どのデータまで届くのか」「ライフサイクルをどう管理するのか」を確認する約 25 分の登壇です。Foundry のエージェントが Work IQ 経由で Microsoft 365 のデータを取得するシナリオを使い、3 つのデモ（開発者視点での動作確認、Copilot／Teams への公開、IT 管理者視点での Agent 365 と Entra）で、見落としやすい点を順に見せます。

押さえておきたい点は次の 3 つです。

- **エージェントは「1 つの ID」ではない。** 発表のシナリオでは、Microsoft Entra 側に 4 つ、Foundry プロジェクト側に 2 つの、合計 6 つのオブジェクトがある。
- **「動いた」だけで本番に出してはいけない。** 委任されたアクセス許可で動いていても、トレースへのデータ蓄積や、誤って広く公開されたサイトのデータが見える問題がある。
- **エージェントには必ず所有者（owner）が必要。** オーナーのいないエージェントは公開できる状態ではない、というのが発表者の主張。

このセッションでは、デモが 3 つ行われています（6 章）。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR980](https://ignite.microsoft.com/en-US/sessions/THR980)

## 3. 何に関する発表か

テーマは、エージェントが「新しい ID」として各テナントに増えていくなかで、**Foundry で作ったエージェントのオーナーシップ、ID、データ境界、ライフサイクル**をどう管理するかです。Martina 氏は、Ignite でも至る所で「エージェントは新しい ID」「Agent 365 が重要」という話を聞くと述べ、1 つのエージェントが環境内の複数の場所に存在する話をしますと切り出しました。

シナリオの前提は次のとおりです。

- エージェントは **Microsoft Foundry** で構築されている（Copilot Studio や App Builder で作ったエージェントではない）。
- エージェントは **Work IQ** を使って、組織のデータ（メール、会議、ファイルなど）を取得し、そのコンテキストを得る。Martina 氏は、Microsoft 365 のデータを追いかけることがねらいだと述べています。

> 注意：トランスクリプトでは Work IQ が「WorkerQ」「worker queue」などと書き起こされていますが、文脈から Work IQ を指していると判断し、本書では Work IQ と表記します。サイト名の「Fabricam」は聞こえた綴りのままにしています（音声認識の都合で表記が確定できません）。

1. 本番前に確認すべき 4 つの問い

Martina 氏は、顧客と話すとき、エージェントが動いたところで「成功だ、本番に出せる」と皆が止まってしまうと述べています。しかし、そこからが本題です。エージェントは委任されたアクセス許可で動作し、ユーザーがアクセスできるデータしか返さないため、その意味では情報漏えいではありません。それでも、トレースにデータが残る、サイトのアクセス権が広すぎる、といった問題が残ります。一方、機密性の高いドキュメントについては、機密ラベルと DLP ポリシーでエージェント経由の返却を防げる、というデモも示されました。

### 5.1 シナリオと、本番前の 4 つの問い

### 5.2 デモ 1：Foundry でのエージェントと Work IQ の委任アクセス

Martina 氏は Foundry の Playground で、**customer briefing agent（顧客ブリーフィング用のエージェント）**を作成済みです。このエージェントは、指示（instructions）を与えたうえで、**Work IQ MCP** を追加して Work IQ に接続しています。Work IQ MCP を通じて、メール、連絡先など、自分のデータにアクセスできます。

ここで出てくる疑問は、「エージェントは Work IQ で利用できるすべてのデータにアクセスできるのか」です。答えは No で、この接続は**委任されたアクセス許可（delegated permissions）**で動作します。つまり、エージェントがユーザーに返すのは、そのユーザーがアクセスできるデータだけです。Martina 氏は、これが非常に重要だと強調しています。

さらに、Web 検索を外しています。エージェントは Work IQ のデータだけを使い、他の情報源は見ません。

最初のプロンプトは、「私は Martina。コンテキストデータがほしい。次の Contoso との会議の準備をして。関連するメール、会議、ファイルなどを使って」という内容です。Martina 氏は結果を待つ間、聴衆に「データは返ってくるでしょうか」と問いかけ、返ってきた情報は、自分がアクセスできるデータに基づく議論などでした。これは**情報漏えいではない**、と述べています。そして、顧客と話すとき、多くの人はここで「成功、エージェントができた、本番に出せる」と止まってしまう、と指摘しました。

### 5.3 問題 1：トレースにデータが残る

次に Martina 氏は、エージェントの**トレース**を見せました。トレースは Azure 上にあります。完了したトレースを開くと、実行タイプなどが分かり、さらに、Martina 氏がアクセスできるデータが、トレースの中にも返されているのが確認できます。

つまり、データがトレースの領域にも保存されることになり、トレースにアクセスできる人が多すぎれば、**情報漏えいにつながりうる**、という指摘です。

対策の 1 つ目の学びとして、**機密コンテンツを、App Insights に登録することで専用のテーブルにルーティングする**方法が挙げられました。これは現時点ではプレビュー機能で、トレースに保存されたデータが、アクセス権の必要のない多くの人に見えてしまうことを防ぎます。

### 5.4 問題 2：誤って広く公開されたサイトのデータ

2 つ目の例として、Martina 氏は Playground に戻り、Fabricam の価格表（price list）などがある前提で、「Fabricam について、どんな価格情報にアクセスできるか」というプロンプトを実行しました。すると、本来得るべきではない情報が返ってきました。

理由は、**Fabricam のプロジェクトサイトが、誤って「外部ユーザー以外の全員」に公開されている**ためです。この場合、Copilot も Work IQ も、そしてこのエージェントも、そのサイトにアクセスできます。Martina 氏は、これも情報漏えいではないが、そのデータがトレースに入り、さらに SharePoint Online の検索を使うだけの他の人にも届いてしまうことを考えてほしい、と述べています。

### 5.5 問題 3：機密データと Adele の視点

3 つ目のプロンプトは、進行中の買収に関する機密データをエージェントで使えるようにしたい、というシナリオで、「私が進めている機密の買収計画は何か」と尋ねる内容です。エージェントは呼び出して調べたあと、結果として「ブリーフィングはまとめたが、買収計画は見つからなかった」と返しました。Martina 氏は、この買収計画が存在するのかと問いかけ、ここで視点を切り替えます。

視点は **Adele** です。Adele は買収の担当者で、そのデータを OneDrive に持っています。Adele はそのドキュメントにアクセスできます。したがって、Adele がドキュメントを開くか、ブリーフィング用エージェントを使えば、エージェントはその情報を返します。ただし、委任されたアクセス許可で動作するため、**返るのは Adele に対してだけ**です。

さらに Martina 氏は、その Word ドキュメントを開いてみせ、「**strictly confidential**（極秘）」というラベルが付いていることを示しました。**strictly confidential のコンテンツを返さない DLP ポリシー**があれば、Adele 本人であっても、エージェント経由でその情報は返らなくなります。こうして、複数の側面から防げる、と説明しています。

続けて、Fabricam の価格表の件に戻り、公開サイトのサイトアクセス権を示しました。「外部ユーザー以外の全員」がアクセスできる設定で、これだけで、Work IQ に接続した Foundry のエージェント経由でアクセスできます。これも情報漏えいシナリオになりうる、というのが Martina 氏の指摘です。

### 5.6 エージェントを構成する 6 つのオブジェクト

スライドに戻り、Martina 氏は、このエージェントには **6 つのオブジェクト**があり、ID は 1 つではなく、複数の経路に分かれていると説明しました。

| 場所 | オブジェクト |

| Microsoft Entra（4 つ） | エージェント ID（agent identity）、エージェントブループリント（agent blueprint）、Work IQ のプリンシパル（音声では「principle」と聞こえます）、Work IQ に接続するための app registration とシークレット |

ここから、誰が何を所有し、ガバナンスの観点で誰が責任を持つのかが問題になります。エージェントを無効化（disable）するだけでは十分でしょうか。無効化しても、Entra ID にはオブジェクトが残ります。ライフサイクルの観点では不足している、という指摘です。

### 5.7 役割：スポンサー、オーナー、データオーナー、プラットフォームオーナー

責任の所在は、次のように複数の役割に分かれます。

| 役割 | 説明 |
| --- | --- |
| ビジネスオーナー（sponsor） | 業務の観点で、エージェントに責任を持つ人。「Work IQ につながってブリーフィングデータを返すエージェントを作りたい」と決める。ライフサイクルの決定（不要になった、廃止するなど）にも責任を持つ。 |
| 技術オーナー（owner） | 構成と運用に責任を持つ。Entra に存在し、エージェントを無効化でき、再度有効化もできる。 |
| データオーナー | Work IQ のデータに責任を持つ。どんなデータが M365 環境に入り、どんなアクセスがあるかを管理する。 |
| プラットフォームオーナー | 役割としては名前が挙げられました。具体的な責任範囲は、発表ではそれ以上説明されていません。 |

Martina 氏は、**スポンサーはエージェントを無効化できるが、再度有効化はできない**点が重要で、知っておく必要があると述べています。ガバナンスの判断ごとに役割が必要で、「すべてのゲストにスポンサーが、すべてのチームにオーナーが、すべてのエージェントにオーナーが必要」という言い方で整理しています。

Martina 氏は、**オーナーのいないエージェントを公開しようとしているなら、そのエージェントは公開の準備ができていない**と述べています。組織内で責任の所在が必要だからです。

役割の要約として、Martina 氏は次の点を説明しました。

- **オーナー（技術管理者）**：必須ではなく、任意です。Agent 365 では、オーナーのいないエージェントが強調表示されます。
- **スポンサー（ビジネス上の責任者）**：作成時に必須で、自動的に作成されます。例えば Foundry でエージェントを作ると、自動的に作成者がスポンサーになります。その後に変更できます。このほかに manager も関わると述べていますが、詳細は発表では説明されていません（聞き取り不明瞭）。
- **オーナーになれる ID**：ユーザー、ゲスト、サービスプリンシパルです。グループは不可で、ID 自体である必要があります。
- **スポンサーになれる ID**：ユーザー、ゲスト、動的メンバーシップのグループ、M365 グループです。
- **スポンサーの上限**：1 つのエージェントにつき最大 100 人で、グループは 5 つまでです。

> 補足：オーナーが「必須でない」としながら、「オーナーのいないエージェントは公開できる状態ではない」とも述べています。発表では、この 2 つの関係について、これ以上の説明はありません。

### 5.8 1 つのリクエストと 2 つの ID パス

Martina 氏は、「どの ID が動いているのか」という観点で、1 つのリクエストに 2 つの ID パスがあると整理しました。

1. **データパス**：サインインしているユーザーが、Foundry エージェントに委任されたアクセス許可を与える。Foundry エージェントが Work IQ に問い合わせ、ユーザーがアクセスできるデータが返る。
2. **エージェントパス**：最初にサインインユーザーを必要とせず、エージェントは常にそこにいる。Foundry エージェント、Entra のエージェント ID、その背後にある Azure リソースで構成される。

デモではエージェントを Work IQ にだけ接続していますが、他のデータソースにも接続できます。エージェントが Entra ID に ID を持っていても、それだけでは完全な答えではなく、**ID、権限、ツールを確認する必要がある**、と述べています。

### 5.9 データアクセスの制御

次に挙げられたのは、データアクセスの制御です。確認すべき観点は次の 3 つです。

- エージェントはそのデータにアクセスできるか（can）
- アクセスすべきか（should）
- そのデータを使ってよいか（may）。このプラットフォームで、エージェントがそれらのデータを使うことが許されているか

データがエージェントにとって適切でなければ、保護（セキュリティ強化）が必要です。さらに、見つかってはいけないデータが見つかった場合の対処も必要で、Fabricam の価格表の例がそれにあたります。

### 5.10 デモ 2：Copilot／Teams に公開したエージェント

続いて、公開したあとの確認に進みます（この導入部分は音声認識が不明瞭で、発言の意図を確定できません）。Martina 氏は、このエージェントを Copilot に公開しており、Copilot と Teams で利用できます。Copilot でエージェントを探しますが、読み込みに手間取り（Martina 氏は「雨の日はエージェントが出てきたがらない」と冗談を言っています）、**Ignite Demo 2** というエージェントを開きました。

公開されたエージェントは Copilot と Teams の両方で使え、同じ質問に答えます。Martina 氏は Adele の視点で「Fabricam の現在の価格を教えて」と尋ね、エージェントはそのまま回答します。**自分の環境にエージェントを公開していれば、Copilot ライセンスも必要ありません**、と述べています。

また、これは通常の動作ではなく、承認の仕組みを見せるためとして、このエージェントは毎回 Work IQ データへのアクセスの承認を求めるようになっています。承認を押すと、応答がアプリに返され、その後エージェントのデータ（Work IQ のデータ）にアクセスできるようになります。これは、正しいアクセス権が付与されるかをテストするものだと説明しています。

### 5.11 デモ 3：Agent 365 と Entra でのコントロール

公開されたエージェントは Teams と Copilot で使えますが、まだ ID、スポンサー、マネージャーがない状態かもしれない、という問題があります。Martina 氏は、デプロイして動かした後に**コントロールポイントが必要で、それは Entra にある**と説明しました。

IT 管理者の視点で、開発者から「言われたとおりにエージェントを作って公開した、すべて順調」と報告を受けても、IT 管理者はそのエージェントを知りません。そこで **Agent 365** で発見する、というデモです。

Agent 365 では、すべてのエージェントの一覧に切り替え、「Ignite」で検索します。ここで AI がエージェントを検索し、ブリーフィング用エージェントが表示されました。Foundry から Agent 365 に自動的に現れる様子が示され、Foundry のエージェントであることが分かります。

ここからエージェントを**無効化（disable）**できます。無効化すると、Copilot や Teams からはアクセスできなくなり、ユーザーは使えません。しかし、Entra、Foundry、Work IQ 接続には残っています。したがって、**エージェントを廃止（retire）するには、無効化だけでは不十分**です。Martina 氏はグローバル管理者なので再度有効化できますが、他の人は有効化できない可能性が高い、と述べています。

さらに新しい機能として、**ブロック（block）**ができます。ブロックにはブロック理由を追加する必要があり、ブロックされたエージェントにはアクセスできなくなります。

最後に Entra で、エージェント ID を確認します。「Ignite」で検索すると多くの ID が表示され、その中に customer briefing agent があります。そこでスポンサー、オーナー、Entra の ID を確認できます。Martina 氏は、「エージェントは権限を何も持っていないように見える」点が気に入っていると述べ、これも重要だとしました（この発言の意味は、発表ではこれ以上説明されていません）。

### 5.12 まとめの 4 つのチェックと次のセッション

最後に、エージェント ID を進めるなら次の 4 つを確認するよう述べました。

1. すべてのエージェントにオーナーが必要
2. ID を確認する
3. そのエージェントがアクセスできるデータを確認する
4. ライフサイクルを確認する

そして、エージェントは公開の準備が整ったときにだけ公開します。Martina 氏は、翌日の午後に別のシアターセッションがあり、そこで**サービスプリンシパルとエージェントプリンシパルの違い**をもう少し深く扱うと案内しました。

6. 2 つ目のプロンプト：Fabricam の価格情報にどんなアクセスがあるか。本来得るべきでない情報が返る。理由は、Fabricam のプロジェクトサイトが誤って外部ユーザー以外の全員に公開されているため。
7. 3 つ目のプロンプト：機密の買収計画について。Martina 氏の視点では結果が見つからない。
8. Adele の視点に切り替える。Adele は OneDrive にそのドキュメントを持つ。Adele が開く、またはエージェントを使う場合は、Adele にだけ情報が返る。Word ドキュメントは strictly confidential とラベル付けされており、DLP ポリシーがあれば Adele にも返らない。
9. Fabricam のサイトのアクセス権を表示し、外部ユーザー以外の全員がアクセスできる設定で、Work IQ に接続した Foundry エージェント経由でも十分アクセスできることを示す。

### 6.2 デモ 2：Copilot／Teams に公開したエージェント

1. エージェントを Copilot に公開済み。Copilot の一覧から Ignite Demo 2 を探して開く（読み込みに手間取った）。
2. 公開されたエージェントが Copilot と Teams で使えることを示す。
3. Adele の視点で「Fabricam の現在の価格を教えて」と質問し、エージェントが回答する。Copilot ライセンスは不要。
4. エージェントが Work IQ データへのアクセスの承認を求める。承認を押すと応答がアプリに返され、データにアクセスできるようになる。

### 6.3 デモ 3：Agent 365 と Entra

1. Agent 365 で、すべてのエージェントに切り替え、「Ignite」で検索する。Foundry のエージェントが自動的に表示される。
2. エージェントを無効化できる。無効化すると Copilot や Teams から使えなくなるが、Entra、Foundry、Work IQ 接続には残る。グローバル管理者は再度有効化できる。
3. ブロックの機能。理由の入力が必要で、ブロックされるとアクセスできなくなる。
4. Entra のエージェント ID で「Ignite」を検索し、customer briefing agent を開く。スポンサー、オーナー、Entra の ID が表示される。

## 7. 注意点・発表者の気付き

- 委任されたアクセス許可で動いていても、**トレースにデータが残る**。アクセスできる人が多すぎれば漏えいにつながりうる。機密コンテンツは App Insights に登録して専用テーブルにルーティングする（プレビュー機能）。
- サイトが誤って「外部ユーザー以外の全員」に公開されていると、Copilot、Work IQ、エージェントのいずれからもそのサイトのデータが取得できる。
- 機密ラベル（strictly confidential）と DLP ポリシーを組み合わせれば、当事者本人でもエージェント経由では返らないようにできる。
- エージェントの無効化だけでは廃止にならない。Entra、Foundry、Work IQ 接続のオブジェクトが残る。
- スポンサーは無効化できるが、再度有効化はできない。オーナー（技術）は無効化も再有効化もできる。
- オーナーのいないエージェントは公開できる状態ではない。
- オーナーはユーザー、ゲスト、サービスプリンシパル（グループは不可）。スポンサーは最大 100 人、グループは 5 つまで。
- ID を持つだけでは不十分で、ID、権限、ツールを確認する必要がある。
- ブロックは新しい機能で、理由の入力が必要。

## 8. 利用者にとっての利点

このセッションで語られたのは、導入効果の数値や顧客事例ではなく、運用上の利点です。

- 委任されたアクセス許可により、エージェントはユーザーがアクセスできるデータだけを返す。
- Foundry で作ったエージェントは、Agent 365 に自動的に現れ、IT 管理者が発見、無効化、ブロックできる。
- 機密ラベルと DLP ポリシーにより、機密データがエージェント経由で返らないようにできる。
- 自分の環境に公開したエージェントは、Copilot ライセンスなしで Copilot と Teams から使える（発表者の説明）。
- スポンサー、オーナー、データオーナーなどの役割を明確にすることで、ライフサイクルの責任を持たせられる。

## 9. まとめ

Martina Grom 氏は、Foundry で作り Work IQ に接続したエージェントを例に、「動いた後」に確認すべきことを示しました。トレースへのデータ蓄積、誤って広く公開されたサイト、機密ラベルと DLP による防止、6 つのオブジェクトの管理、スポンサーとオーナーの役割、2 つの ID パス、データアクセスの 3 つの観点（can／should／may）、そして Agent 365 と Entra でのコントロールです。

結論は、すべてのエージェントにオーナーを置き、ID、アクセスできるデータ、ライフサイクルを確認し、準備ができたときにだけ公開する、という 4 つのチェックです。
