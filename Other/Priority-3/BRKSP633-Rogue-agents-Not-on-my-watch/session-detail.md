# BRKSP633 Rogue agents? Not on my watch

## 1. はじめに

このセッションは、Splunk by Cisco の Field CTO である Craig Hyde 氏が、AI エージェントが広がる時代のセキュリティと運用をどう組み立てるかを、Cisco と Splunk の取り組みに沿って紹介する内容です。「rogue agents（暴走・悪意あるエージェント）」という題名のとおり、攻撃者側のエージェントと、自社が配備するエージェントの両方を対象にしています。

Hyde 氏が示す対応は 3 つの柱です。

1. **データを整える**（Cisco Data Fabric）。各所にあるデータを集約せずに横断で相関させる。
2. **防御側にもエージェントを持たせる**（SOC 向けの専用エージェント）。
3. **AI 自体を観測する**（Observability for AI）。セキュリティ・ガバナンス・コストを含めて見る。

最後に、Microsoft との契約コミットメントを Splunk の利用で消化できる話も紹介されます。このセッションでは画面を使ったデモは行われていません。口頭の説明が中心です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRKSP633](https://ignite.microsoft.com/en-US/sessions/BRKSP633)

## 4. 発表者が伝えたいメッセージ

Hyde 氏の出発点は、エージェントはもう元には戻せないという認識です。攻撃側ではエージェントの群れ（swarm）が常に環境を狙い、守る側も自社でエージェントを展開しています。そのうえで、誰もが猛スピードで新しい機能を作っている状況だからこそ、まず何が起きているかを把握しなければならない、という考えを示しています。背景として、自社の従業員へのエージェント展開、市場にいる暴走エージェントへの防御、データ主権やデータガバナンスへの対応が同時に求められている、と語っています。

主張は 3 点に整理できます。

- **データを正しく扱うことが先**です。品質が悪い入力からは、AI も自律システムも良い結果を出せません（"slop in, slop out" と表現）。
- **防御側もエージェントで対抗する**必要があります。ただし完全自律はまだ現実的ではなく、分析者の作業を速くする実用的な使い方から進める、という立場です。
- **エージェントの可観測性は、ガバナンスであり、セキュリティであり、運用でもあります。** 「observability」という言葉では少し控えめすぎる、と述べています。

## 5. 発表内容の詳細

### 5.1 Cisco と Microsoft のパートナーシップ

発表者はまず、火曜日の発表として、Cisco が Microsoft の Global Partner of the Year の 1 つ（business transformation marketplace 向け）を受賞したと紹介しました。協業は 90 年代初頭にさかのぼると説明しています。あわせて、Cisco は老舗の大手テクノロジー企業であり、エージェントの時代に向けて自らを作り替えているところだ、とも述べています。直近 12 か月でマーケットプレイス経由の共同ビジネスが 800% 成長し、製品の消費量も 2 桁成長したとのことです（約 20 年の協業での成長として「前例がない」と述べています）。

役割分担のイメージは次のとおりです。Microsoft は Office 365 などのワークプレイスと Azure に強く、企業が Microsoft 標準に寄せていくなかで、Cisco と Splunk は Azure の外側（他のネットワーク、他のデータセンター、他のハイパースケーラー）にまで可視性を広げます。インフラ、セキュリティ、接続性の観点でそれらを束ねる、という説明です。

### 5.2 背景：Mythos 以降の脆弱性と攻撃の高速化

Hyde 氏は、セキュリティと運用の面で意識している大きな出来事として **Mythos** を挙げています。Mythos の発表の翌月曜日に、ニューヨークのグローバルなフィンテック事業者を訪ねたところ、部屋にパニックに近い空気があったという体験談を紹介しました。Mythos や Glasswing（Hyde 氏の発話では "the Glasswing"）の詳細は、発表では説明されていません。

Hyde 氏が Mythos の意味合いとして述べたのは、ソフトウェアとハードウェアがこれまでよりはるかに堅牢である必要があり、AI によってバグが即座に見つかるようになった、という点です。数字としては、次のものが語られました。

| 項目 | 発表で語られた内容 |
| --- | --- |
| CVE の数 | Microsoft の Patch Tuesday で出るパッチ数に見られるように、この数年で約 10 倍 |
| 脆弱性の発見から悪用まで | 2 年から約 10 時間に短縮 |

あわせて、Hugging Face や Astra に関する攻撃（音声認識の都合で表記が確定できません）に触れ、エージェントの群れが環境を攻撃し続けているとしています。簡単なスクリプトを使う攻撃者でも、能力が大きく跳ね上がっているという説明です。

### 5.3 3 つの取り組みの全体像

Hyde 氏は、ここまでの状況に対し、まず **エコシステム全体の可視性** を得ることが必要だと述べます。ただし、あらゆる箇所を可視化するとデータ量が爆発し、コストの面で成り立たなくなります。そのため、データを調整し、複数のソースをつなぎ、**エージェントの速度で判断できる**ようにしなければなりません。Teams の会議で全員にそれぞれのシステムへログインして確認してもらうようなやり方は、エージェント相手の防御では通用しない、と述べています。

そこから、次の 3 つの領域が示されました。

| 領域 | 内容 |
| --- | --- |
| Cisco Data Fabric | ネットワーク全体の情報を集め、経済的に扱えるようにする |
| SOC のエージェント化 | 検知、トリアージ、対処を行う SOC を「工場のフロア（factory floor）」と見立て、自社の専用スキルでエージェント化する |
| Observability for AI | エージェントが既存のシステム群の中で正しく動いているかを監視する |

Hyde 氏は、これらによってセキュリティ運用と AI ガバナンスを「オートパイロット」に近づけるための材料を組み立てる、と話しています。

### 5.4 Cisco Data Fabric

#### 単一の作業画面と、Cloud Control

Cisco と Splunk が得意とするのは、セキュリティ運用と技術運用（オブザーバビリティやネットワーク運用）の領域です。Hyde 氏は、Microsoft が発表した AI fabric のように、Teams や Office 365、営業関連のシステムなど社内のコミュニケーションを 1 つにつないで扱う発想を、技術側でも実現し、**単一の作業画面**を目指していると述べました。

Splunk は 20 年以上の歴史があり、数千の連携を持っています。セキュリティ側では 1,300 のセキュリティ製品との連携があり、運用側でも同様だと説明しています。重視しているのは、人が日常的に使うコミュニケーションの画面ではなく、その裏側で「エージェントや各システムがどう連携して動いているか」を計装することです。

Cisco は **Cloud Control** という製品も出しています。Cisco は 40 年の歴史があり、多数の企業を買収してきましたが、その複数のドメインを 1 つの UI にまとめ、横断して作業できるようにしたものです。ここに Splunk をつなぐと、「自分の Wi-Fi で何が起きているか」といった質問ができ、さらにデータファブリックを経由してサードパーティのシステムにも質問してトラブルシュートできます。Hyde 氏は Cloud Control を、データファブリックへの入口（ポータル）と位置づけています。

#### SIEM 型の集約をやめ、フェデレーションへ

従来の SIEM（発話では "SIM" と聞こえます）は、全データを 1 つのデータベースに入れて一緒に見るという考え方です。Hyde 氏は、これはもう通用しないと述べます。理由は、データ量が多すぎること、クラウド事業者のデータ送出（egress）コストが大きいこと、運用上も成り立たないことです。そこで、データを一か所に集めず、各所にあるまま、規模に耐える形で横断的に相関させる**フェデレーション**を採ります。そのうえで、データが正しく、正規化されていて、何が入っているか分かっていることが、AI を動かす前提だとしています。

> 補足：Cisco Data Fabric の "Fabric" は Microsoft Fabric と同じ単語ですが、見ている情報とその場所が異なり、別のものだと Hyde 氏は断っています。

#### コンテキストをつなぐ例

アプリケーションの利用ログ、ミドルウェア、AI システム、電話システムなどのデータがつながっていれば、コンテキストを大規模に持てる、という例が語られました。1 週間前に起きた FAA の障害を例に、航空会社のコールセンターに電話が入ったとき、電話番号からその顧客に関するあらゆる情報を引けるなら、「その顧客はアトランタで足止めされ、サンフランシスコでの Microsoft のカンファレンスに向かっている」といった状況がすぐ分かり、より良い判断ができる、という説明です（カンファレンス名は音声認識の都合で確定できません）。

データの整備は、運用を立ち上げるときに最初に最も時間をかけるべき部分だとしています。また、サーバー同士の通信のような生の技術データも、ビジネスの動きと重ねれば事業の指標になります。例としてクレジットカード会社の取引では、不正、承認率、レイテンシーなどが見えます。インフラ運用から CEO や CIO 向けのダッシュボードに結びつけ、IT が受け身で支えるだけでなく事業を前から引っ張れるようにする、というのが目標だそうです。

#### データのティアリングとフェデレーテッド検索

Splunk は約 2 年前に Cisco に買収され、単独のデータストアではなく、組織の業務に組み込まれたデータレイク／データファブリックとなるよう、急ピッチで機能を作ってきたと述べています。語られた機能は次のとおりです。

- **低コストのデータレイク（仮想データレイク）**: 世界中のシステムのデータを、技術の種類を問わず federated search で扱います。
- **データティアリング**: 悪意あるエージェントの活動のように即座に知りたいデータは、高価な「ホットティア」（従来の Splunk）に置いてアラートや処理のトリガーにします。それ以外は、監査人が求める期間だけ保存しておき、重要になったときにデータの価値を上げ下げできます。
- **フェデレーテッド検索（federated analytics）**: Splunk は元々ダウンロードして使うソフトウェアで、ログを Splunk に入れて検索する方式でしたが、規模が大きくなる局面ではそこから離れようとしている、という説明です。大規模なパートナー側の顧客からは、「データは Azure Blob Storage に置いている」「データ主権のために Azure Local に置いている。そのデータをそのまま使えないか」といった要望があるそうです。そのため、運用向けの AI が、利用者のシステムにそのままつながり、データの複製を作らずに済むようにしている、と述べています。

これらの接続を人手で行うのは大変なので、AI を使って進め、データをエージェントに渡すことも想定しています。

#### 古いデータセットに AI を使った事例（ナッシュビルの医療機関）

データが整うと、古くて特殊なデータセットにも AI を活用できるという例が紹介されました。担当者が 1 人しか分からない、その人が異動や退職をしたら困るようなデータです。

Hyde 氏が関わったのは、ナッシュビルにある医療機関の事例です。年式もメーカーも異なる放射線画像の機器が、DICOM ルーターという基盤でつながっていました。機器ごとに特殊なプロトコルを使っています。その情報をデータファブリックに取り込み、**市販の LLM をつなぐだけで**、数分のうちに次の問題を扱えるようになった、という話です。

- ある患者が自分の情報にアクセスできない
- 医師が MRI や X 線を読めない
- 出たエラーは技術的で意味が分かりにくいものだった（"pixel truncated" や数値の 64 と 8192 に触れていましたが、詳細は聞き取り不明瞭です）

AI があらゆるシステムのマニュアルを知っているため、そのエラーを入れると、数秒で、古いインフラの特殊な問題を解くための runbook が得られたと説明しています。トラブルシュートが速くなる一方で、適切な内容にアクセスできることが前提だと付け加えています。

### 5.5 エージェントによる SOC の効率化

運用を支える目的に加え、いまはサイバー攻撃を受けないようにすることも運用の一部になっています。Mythos 由来の脆弱性の増加、エージェントの群れ、スクリプトを使う攻撃者の能力向上により、SOC には疑わしい活動のアラートが大量に届きます。Hyde 氏は、ユーザー起点などで発生する、インシデントに見えるもの（「little i incident」と呼ぶもの）が増えていると説明します。

現状の問題は次のとおりです。

- 高給で専門性の高いセキュリティアナリストが、アラートを 1 件ずつ手で見て「本物のインシデントではない」と判断している。
- すべてを見ないと、重大なものを見落として新聞の一面になりかねない。
- アナリストの市場は人手が足りず（"negative unemployment" と表現）、育成にも時間がかかる。
- トリガーが出ると人が見て、Teams で他の人に情報を求め、別の人がまた見る、という連鎖で作業が遅れる。

Hyde 氏は、これを「工場のフロア」にたとえ、調査を終わらせるまでの工程を整理しています。アニメーションのような派手な使い方ではなく、実用的に AI を使うことを重視し、予算は増えないのに作業は増えている現場の**スループット**を上げることが狙いです。アナリストが時間を使っている仕事を洗い出し、どこを圧縮できるかを見て、面倒な作業をこなす**専用のエージェント**を作っているという説明です。対象には、検知、脅威ハンティング、調査と対応（アカウントのロックアウトや自動化を含む）が含まれます。

作ったエージェントは **enterprise security** としてまとめられています。新しい領域別の機能ができたらその中に加えていく考えです。現時点の数は次のとおりです。

| 区分 | 数 |
| --- | --- |
| すぐに使えるワークフロー向けエージェント | 約 12 個 |
| テスト中でこれから追加予定のもの | 約 6 個 |

Hyde 氏は、当初は完全な自律を目標としていたが、サイバーセキュリティのアナリストの仕事では「まだそこには至っていない」と述べます。これらは幻覚が許されず、正確である必要があるためです。外部の悪意あるエージェント、自社のおかしな挙動のエージェント、内部脅威などを把握できるようにしたうえで、ワークフローを改善し、自律型 SOC に近づけていく、というのが実際の進め方です。目標は完全自律ですが、実態としては、チームのスループットを上げることに集中しているとしています。

### 5.6 Observability for AI（AI のガバナンス）

Hyde 氏はこれを「最後のとっておき」と紹介し、実質的には AI のガバナンスだと位置づけます。見るべきことは次のとおりです。

- モデルに何が入力されているか。プロンプトインジェクションでモデルをだまそうとしていないか。例として、自動車販売店のエージェントをだまして 1 ドルで車を売らせた有名な事例を挙げています。
- 銀行などの金融業界では、銀行業務の手続きや口座の数値について、エージェントが誤ってはいけない。事実に基づいて答え、幻覚を起こしていないかを確認する必要がある。
- 実際のアプリケーションとの連携が正しく動いているか。これが最も難しい。

エージェントは従来の決定的なソフトウェアではなく、確率的で、時に脱線します。Hyde 氏は、Microsoft の会場にいるとエージェントの話ばかりになりがちだが、エージェントもサーバー上で動くソフトウェアで、他のシステムやレガシーアプリにつながっていると指摘します。エコシステムのすべての部品を監視してはじめて、エージェントのアプリケーションが正しく動いているかが分かる、という立場です。

#### AI SRE

Hyde 氏自身は、ユーザーエクスペリエンスの計装から Splunk に入り、それがオブザーバビリティという大きな全体像の一部になったと説明しています。信号機のように、アプリが緑・黄・赤のどれかを知るには、ドメインごとの知識が必要です。システムが分断され、部品が絡み合うほどトラブルシュートは難しくなります。

そこで、焦点を絞った AI を使って広く複雑な問題を解きます。ログ、アプリ内部の動き、エージェント自身のテレメトリ、ユーザーのデスクトップ（エンドポイントで AI をどう使っているか）の情報を集めて分析する **AI SRE** を作っているとのことです。これらを相関させることで、自動でトラブルを素早く切り分けられるようになっています。完璧ではなく人の監督は必要ですが、チューニングが進むほど根本原因に早くたどり着けると述べています。対象は、エージェント駆動のものに限らず、従来のソフトウェア、クラウド、SaaS、オンプレミス、メインフレームまで含みます。

#### Galileo と Luna：AI 出力の評価

LLM 呼び出しは「ただの Web サービス呼び出し」とも言えますが、特別な見方が必要だと Hyde 氏は述べます。そのために Cisco と Splunk は、約 1 年前に **Galileo** という会社を買収しました（時期は「約 1 年前、または 6 か月ほど」と聞こえ、はっきりしません）。その技術は、モデルの入出力を理解するために蒸留された、小さな言語モデル（SLM）です。

- 軽量で、大きなモデルを呼ぶコストの 1/40 程度。
- 入力がプロンプトインジェクションではないか、エージェントが幻覚を起こしていないか、脱線していないか、回答が正しいか、ガードレールを破っていないか、といった判定を高い精度で素早く行う。

この SLM は **Luna** と呼ばれ、ダウンロードして無料で試せ（無料トライアルあり）、可視化に取り組みやすい入口だとされています。「モデルを AI foundry に入れて使い始められる」とも述べていますが、これが Microsoft Foundry を指すかどうかは明言されていません。

事例として、発表当日の電話で、トップ 10 に入る銀行と、そのコアのモバイルアプリと AI エージェントの評価について話したことを挙げました。評価によって AI を運用できる状態にでき、秘密裏に始めたプロジェクトを本番に出した後、エッジケースを 1 つずつ調整していくにはテレメトリが必要だという説明です。また、可視化ができれば、使うモデルが適切か、蒸留すべきか、従来のソフトウェアで足りないか、この部分は本当にエージェントである必要があるか、といったコストの議論も進めやすくなります。さらにガードレールを設けられ、例えばローン申請で何かおかしいときに、承認の応答をブロックすることもできます。

#### コスト（tokenomics）

次の課題はコストです。Hyde 氏は、今週話した大手スポーツチームの CIO の例を紹介しました。

- エージェントを本番に出して全員が使っている。
- フロンティアラボの導入向けパッケージで利用しており、1 月 1 日からは定価での支払いになる。
- Hyde 氏によると、現在の条件と定価の差は桁違いに大きく、約 100 倍高くなる。
- 試して広めるための期間を過ごし、数か月後に請求が来る。誰がどの技術をどれだけ使っているか、削減の余地はどこかを、慌てて調べている。
- 対処しなければ、予定していなかった 7〜8 桁の請求が来る。しかも観客席の数が決まっているので、収益は増えない。

エージェント内部を計装すると、どのアプリケーションが、誰が、どのモデルを使っているかが分かります。さらに、モデルやラボ、実装によらず 1 トークン呼び出しのコストを重ねられます。顧客は、この **tokenomics** の理解に多くの時間を使っているとのことです。Hyde 氏は、エージェントのオブザーバビリティは、ガバナンスでありセキュリティでありオペレーションでもあるので、「observability」という言葉は控えめすぎると繰り返しています。

#### フルスタックの計装と OpenLLmetry

すべての AI がモデル提供者からトークンを借りる形ではありません。データセンターの競争やモデルのコスト、データの機密性から、自前のインフラを持つ組織も増えています。その場合、エージェントを**フルスタック**で計装する必要があります。GPU の利用率を見て、ラックからもっと価値を引き出せないかを探り、エージェントから出てくるものとアプリケーション内部の動きをつなぐ、という話です。

そのためのパッケージとして **OpenLLmetry** が紹介されました（OpenTelemetry をもじった名前で、アプリケーションの計装に使うもの）。エージェントと、それがつながる従来のソフトウェアを関連づけられます。例えばデータベースの容量問題があるとき、フロントでどのエージェントがどの呼び出しをしているかが分かり、その呼び出しをチューニングできます。個別に対処するモグラ叩きではなく、全体が調和して動く形にできる、という説明です。

### 5.7 方針の要約、Microsoft との契約コミットメント、顧客事例

発表者は、暴走エージェントに追いつくための方針を、社内で開発するエージェントを使う場合も、周辺から入ってくるエージェントの能力から守る場合も、次のように要約しました。

1. データを正しく整える。
2. 社内のセキュリティチームが「毒を以て毒を制す」ように、自分たちのエージェントで攻撃側のエージェントに対抗できる状態にする。
3. 実行しているアプリケーションを深く可視化し、研究プロジェクトにとどまらず運用の成熟度まで引き上げる。

Splunk と Cisco が取り組むこれらの内容は、Microsoft のエコシステムで勢いを増しているそうです。

Microsoft との協業で特徴的なこととして、契約コミットメントの消化が紹介されました。Hyde 氏は "burn down the Mac" と述べています（音声認識の都合で表記が確定できませんが、Microsoft との契約上のコミットメントを指す文脈です）。Microsoft とのコミットメントがある会社では、**Splunk への 1 ドルは、Microsoft への 1 ドルとして**そのコミットメントから差し引けます。Microsoft にとっても、これまで Microsoft の外にあった情報を、Microsoft の環境に取り込める範囲が広がると説明されています。Microsoft のスタックに標準化しつつ、他のプラットフォームの選択や可視性を捨てなくてよい、という意味です。

顧客事例として、前夜に会った **Kona**（Coca-Cola North America、ボトラー各社）が挙げられました。工場や在庫を SAP システムで運用しており、Splunk は基幹アプリケーション向け、特に SAP に関する取り組みとして、運用を支える AI SRE を構築中とのことです（発話では "AR SRE" と聞こえます）。ほかにも、Microsoft と共通の顧客は多いと述べています。

## 7. 注意点・発表者の気付き

- **完全自律はまだ早い。** SOC のエージェントは、幻覚が許されない領域だと述べています。AI SRE についても、完璧ではなく人の監督が要るとしています。
- **すべてを可視化するとコストが成り立たない。** ログの集約型では、データ量と egress コストが問題になります。
- **データの品質が先。** 正規化され、内容が分かっているデータがなければ、自律システムを動かせません。
- **エージェントは確率的で、脱線する。** 従来の決定的なソフトウェアと違うため、入出力の評価（プロンプトインジェクション、幻覚、ガードレール違反）が必要です。
- **本番化の後にコストが跳ね上がる。** スポーツチームの例のように、導入向けの条件から定価に変わると、請求が桁違いになることがあります。
- **エージェントも一般のソフトウェア。** サーバー上で動き、レガシーアプリとつながります。周辺のすべての部品も監視する必要があります。

## 8. 利用者にとっての利点

発表で語られた利点・効果は次のとおりです（多くは製品の目的として語られたもので、数値で示された成果はパートナーシップの成長率が中心です）。

- Microsoft Azure 以外のネットワークやデータセンター、他のハイパースケーラーまで含めて可視性を広げられる。
- データを集約せずに横断で相関でき、egress コストや運用上の負担を避けられる。
- データのティアリングにより、重要なデータだけを高価な層に置ける。
- 古くて特殊なシステム（DICOM ルーターを使う医療機器の事例）でも、LLM を組み合わせて、数分のうちに対処に入り、エラーから数秒で runbook を得られた。
- 専用の SOC エージェントにより、アナリストの手作業を減らし、スループットを上げる。
- Luna などの小型モデルによる評価が、大きなモデルの呼び出しの 1/40 程度のコストで行える。
- tokenomics の可視化により、誰が何をどれだけ使っているかを把握し、コストを統制できる。
- Splunk への支出を Microsoft とのコミットメントの消化に使える。

## 9. まとめ

Hyde 氏は、エージェントの広がりでセキュリティの脅威と運用の難しさが同時に増えているとして、Cisco Data Fabric によるデータの整備、専用エージェントによる SOC の効率化、AI 自体の可観測性という 3 つの取り組みを紹介しました。

背景には、Mythos 以降の脆弱性の増加（CVE は約 10 倍）と、発見から悪用までの時間が 2 年から約 10 時間に縮んだという変化があります。対応の中心は、データを正しく整えること、自社のエージェントで攻撃側のエージェントに対抗すること、そして AI を含むアプリケーションを深く可視化することです。ただし、完全自律は目標であって現状ではなく、人の監督を前提に実用的なところから進めるという姿勢が一貫していました。
