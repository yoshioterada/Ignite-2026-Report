# THRSP1107 How Commvault reduced cloud storage costs by 40%

## 1. はじめに

このセッションは、Azure 上の Managed Disk のコスト（発表では "managed disk spends" と表現）を、Commvault がどのように 40% 削減したかを紹介する約 23 分の発表です。前半は Lucidity の共同創業者 Vatsal 氏が、ストレージ最適化が難しい理由と、Lucidity の「AI actions engine」と「Disk Autoscaler」を説明します。後半は Commvault の Karunakar 氏が、ディスクの過剰割り当てに悩んでいた状況と、Lucidity 導入後の成果を語ります。

Commvault 側の成果として語られたのは、Lucidity が管理するストレージのコスト 40% 削減、約 2 年間での純削減額 200 万ドル、利用率の 60% から約 90% への向上、そしてディスク追加に伴うインシデント（アラート）の約 50% 削減です。最後に Vatsal 氏が、ダウンタイムなしでディスクを拡張・縮小できる仕組み（ディスクのプール化）を明かします。

> 注意：このセッションは Lucidity の製品紹介を兼ねており、数値は登壇者が語ったものです。第三者による検証や、導入前後の詳細なコスト内訳は発表では示されていません。

テーマは、クラウドのストレージコストを実際の請求額として下げるにはどうすればよいか、という問題です。Vatsal 氏は、FinOps ツールが示す「節約できる額」と、実際に請求書に反映される額の間に大きな差がある、という問題提起から始めます。

## 4. 発表者が伝えたいメッセージ

Vatsal 氏の主張は、「節約の発見」ではなく「節約の実行」が本当の課題だということです。同氏が挙げた Lucidity の調査では、FinOps ツールが示した節約額のうち、実際に請求額に反映されるのは多くても 25% です。一方、Lucidity は、特定した節約額の最大約 87% を実現したとしています。これは過去数年に関わった 50 社以上のエンタープライズ顧客での数字だと説明しています。

その差が生まれる理由として、推奨事項が浅く（請求書の表面しか見ない）、コンテキスト（文脈）が欠けていること、そして実装までに信頼の不足や摩擦、やり取りの多さがあることを挙げています。この結果、「数百ドルの節約のために貴重な開発者や DevOps の工数を使いたくない」と判断され、変更が見送られる、というのが Vatsal 氏の説明です。

Karunakar 氏は、ユーザーとして、ディスクの過剰割り当てと手作業の運用が SLA と SRE の工数に与える影響を示し、Lucidity の導入で、コスト削減と運用負荷の軽減の両方が得られたと述べています。

## 5. 発表内容の詳細

### 5.1 ストレージ最適化が難しい理由（Vatsal 氏）

Vatsal 氏は、ストレージは自動化がもっとも難しい領域だと述べ、理由を次のように挙げています。

- データの増え方が一様でなく、予測しにくく、しかも継続的に増える。止めることができず、最適化しにくい。
- 性能と容量が相互に関係しているため、性能を保つために容量を過剰に確保しがちになる。
- あらゆる変更が稼働中のシステムに触れる。OS、アプリケーション層、セキュリティに影響があり、変更が難しい。
- 変更は静的で、変更したら前の状態に戻れない。

### 5.2 節約は「見つける」より「届ける」ほうが難しい

Vatsal 氏は、節約の余地を見つけることは最も難しい問題ではなく、実行することが難しいと述べています。多くの FinOps ツールは節約できる額を分かりやすく示しますが、実際の削減はその一部にとどまります。前述のとおり、Lucidity の調査では請求に反映されるのは多くても 25%、Lucidity では最大約 87% だとしています。

推奨が実行されない理由として、次の点を説明しています。

- **推奨が浅い**：請求書を見て、表面的な洞察を出すだけでは足りない。大きな効果のある洞察は、VM の中、リソースの中、アプリケーションの中に深く存在し、それを見に行く必要がある。
- **コンテキストが欠けている**：例として、ある顧客は、VM のライトサイジング（縮小）の推奨を受けたが、その VM では SAP HANA が動いていて、HANA は一定の値より下げられない。このようなノイズのために、他の正しい推奨まで実施されなくなったという。
- **信頼の不足・摩擦・やり取りの多さ**：組織ごとに事情や課題が異なるため、それぞれに合わせた対応が必要。

### 5.3 AI actions engine

こうした課題に対して、Lucidity が提供するのが **AI actions engine** です。Vatsal 氏は、Azure Ignite の数日前にこれを発表したばかりだと述べています。特徴は次のとおりです。

- **深さ**：請求書上の洞察にとどまらず、VM レベル、アプリケーションレベルまで入り込む。エンタープライズ規模では見つけにくい洞察を出す。
- **コンテキスト**：重要度、アプリケーション、環境、利用頻度、ポリシーなどを踏まえた推奨を出す。例えば、ある顧客が「Azure の deny policy で特定の SKU に変更できない。それを推奨するのか」と尋ねたことを紹介しており、システムはこうした情報を取り込み、カスタマイズして提示できると説明している。
- **実行**：洞察を出すだけで終わらず、信頼して実行できるだけの情報を示す。実行の方法は複数ある。変更は安全に行われ、実行後は監視し、問題が起きたら自動でロールバックして以前の状態に戻す、と説明している（発話では「previous day」と聞こえますが、文脈から「以前の状態」と読んでいます）。

AI actions engine には複数のモジュールや洞察がありますが、この日の中心は **Disk Autoscaler** です。Disk Autoscaler は Lucidity のフラッグシップのモジュールで、ダウンタイムなしにドライブを縮小する既知の方法はこれまでなかった、という問題を解決するとしています。容量の拡張と縮小を、性能への影響もダウンタイムもなしに行えるという説明です。

エンタープライズ向けとして最初から設計されており、ガードレール、ゼロトラストポリシー、最小権限を備え、クリティカルパスの外に置かれたうえで、組織のポリシーの管理下に置かれる、と述べています。

### 5.4 Commvault SaaS の環境（Karunakar 氏）

Karunakar 氏は、Commvault SaaS を、クラウド、オンプレミス、ハイブリッドにまたがるデータのバックアップ、復旧、保護を行う、データ保護とサイバーレジリエンスのプラットフォームだと説明しています。

- バックアップデータには Azure Blob Storage を使う。
- インデックスやメタデータの管理など、一時的（エフェメラル）なデータには SSD ディスクを多く使う。Blob Storage ではなく SSD ディスクで管理している。
- ワークロードは種類が多い。実データのバックアップ、バックアップ処理、インデックス管理、メタデータ管理など。それぞれ必要な容量、IOPS、性能が異なる。
- 容量とコンピュートの両方で、垂直・水平にスケールする。OS は Red Hat、Windows、Amazon Linux。
- 環境は、数千の VM と数万のディスクがあり、Azure と AWS で動いている。

ワークロードごとの特徴として、インデックスノードは永続的で、高い耐障害性が必要で、増え続けるため、ストライピングを使います。バックアップ処理ノードはデータが増減し、SLA（トランスクリプトでは SLEs と聞こえる）を満たすためにスループットが必要です。こうした要件がぶつかるため、容量管理は非常に複雑で、ストレージを積極的に最適化しすぎると、SLA の未達や性能低下、バックアップの失敗を招くおそれがある、と述べています。課題は、性能・可用性・耐障害性を保ちながら、利用率を上げ、コストを下げることです。

### 5.5 Lucidity 導入前の運用

導入前は、手作業と運用手順書（ランブック）でストレージを管理していました。ディスクの追加には SRE の時間が必要で、追加すればダウンタイムが発生して SLA を下げるため、最初から過剰に割り当てていた、と説明しています。グラフでは、網掛けの領域が過剰割り当て、実線が実際の使用量で、過剰な部分にも料金を払っていました。

容量が上限に達すると、手作業で拡張します。アラートが上がり、SRE が、まずインフラ側でディスクを追加し、続いて OS 側で追加する、という複雑な手作業で、ダウンタイムが発生し SLA に影響します。拡張時にもまた過剰に割り当てていました。

縮小も難しく、Azure はデータを縮小する機能を持たず、データをコピーするなど多くの手作業が必要で、1 台の VM で縮小するのに約 4 時間のダウンタイムが必要だったとしています。その結果、水平スケールしてもディスクを縮小できず、容量は増える一方でした。

### 5.6 Azure の 3 つの制約

Karunakar 氏は、容量が増え続けた理由として、Azure の 3 つの制約を挙げました。

1. **ディスクを縮小できない**：利用が 50% 程度でも、ワンクリックで容量を縮小する機能がない。
2. **Premium SSD v2 が当初なかった**：SaaS の取り組みを始めたときには、Azure Premium SSD v2 が存在しなかった。v2 では容量、性能、スループットを独立にスケールできるが、v1 ではサイズと性能が比例して増える。例えば約 6,000 IOPS が必要なら、実際のデータが 100 GB 程度でも 1 TB のディスクを用意する必要があった。
3. **v1 から v2 への自動変換がない**：v2 が登場しても、v1 から変換する機能が Azure になく、コピーと書き込みによる移行が必要で、VM を止める時間が数時間、場合によっては数日かかる。

これらが原因で、プロビジョニング済みの容量が増え続ける一方、実使用量は低く、Lucidity 導入前の利用率は約 60% だったと述べています。

> 補足：後の説明では、改善前の利用率を「約 50%」とも語っており、60% と 50% の表現が混在しています。測定対象（ディスク単体か全体か）の違いなのかは、発表では説明されていません。

### 5.7 Lucidity 導入の進め方と成果

Karunakar 氏が説明した進め方は次のとおりです。

1. ワークロードごとのストレージ特性を把握する。インデックスサーバーは永続データで、耐障害性が必要で、ストライピングする。バックアップ処理のデータは一時的で、ステージングして処理したあと、その容量は不要になる。
2. VM ごとに確認し、容量計画を行う。v1 のまま縮小できるもの、v2 に移すもの、そのままにするもの（例：インデックスサーバーはすでに 85% 使用しているのでそのまま）に分ける。
3. 方針が決まったら、Lucidity で自動スケールを行う。グラフでは、実線が実使用量、階段状の線が Lucidity による管理を示す。最初は過剰割り当てを検出して縮小し、需要が増えれば自動で拡張し、データを別の VM に移す水平スケールで使用量が減れば、再び縮小する。Lucidity がなければ、減っても容量はそのままだった。
4. v2 への移行も、まず分析を行う。v2 には制約があり、一部のディスク（トランスクリプトでは「worst disks」と聞こえ、種類は聞き取れません）には使えず、すべてのリージョンで使えるわけでもない。Lucidity の分析で、v2 に移せるディスクと、v1 のままにするストレージプールを分けた。
5. v2 に移すものは、Lucidity が移行を実施した。v2 は安く、サイズ・スループット・IOPS を独立に調整できる。サイズを下げて IOPS を上げた。移行後に、ワークロードの性能要件を踏まえたポリシーを再適用し、スループットと IOPS を必要な値に調整した。

成果として語られた数値は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| 利用率の改善 | 約 50% から約 80% |
| 特定のディスク（発話の "that particular disk"）のコスト | 約 56% 削減 |
| 割り当て済みディスク容量全体 | 約 20〜30% 削減 |
| Lucidity の利用期間 | 2 年強 |
| 純削減額 | 200 万ドル |
| Lucidity 管理分のストレージコスト | 40% 削減 |
| Lucidity で管理しているデータ量 | 約 3 PB |
| その 3 PB の利用率 | 60% から約 90% |
| インシデント（アラート）数 | 約 50% 削減 |

ディスクの追加はそのつど SRE の時間を要する運用だったため、インシデントが約 50% 減ったことで、SRE はサービスを健全に保つほかの作業に時間を使えるようになった、と述べています。コストだけでなく、エンジニアの時間が戻った点を強調しています。

### 5.8 ダウンタイムなしで拡張・縮小できる仕組み（Vatsal 氏）

Vatsal 氏は、「秘密の仕組み」を説明しました。仕組みは単純で、**サイズの異なる複数のディスクをプールにまとめ、その上に仮想ディスクを作り、すべてのドライブをそこに置く**というものです。

- **拡張**：使用率があるしきい値を超えたら、プールに新しいディスクを追加する。処理は数秒で終わり、影響なく容量を増やせる。
- **縮小**：プールからディスクを取り除く。アルゴリズムが、いつ取り除くべきかを判断し、稼働中のシステムや性能に影響を与えずにデータを移し、安全に容量を引き上げる。
- **ディスクの種類の変更**：Premium v2 のディスクを追加し、古い種類のディスクを取り除くだけで、無停止・性能影響なしに変更できる。
- **既存ワークロードの取り込み**：稼働中のワークロードを、影響なしに Lucidity の Disk Autoscaler へ移すことができる。

また、すべての変更は、Commvault のガバナンスポリシーの下で行われたと強調しています。エンタープライズが本番環境で安心して変更できるよう、多くの制御を設けており、変更は信頼でき、予測可能で、それが信頼を築くことにつながる、という説明です。

### 5.9 得られた教訓

Vatsal 氏は、Commvault との取り組みから得た学びとして、次の 3 つを挙げています。

1. **リソースの中を見る**：浅い洞察にも効果はあるが、本当の効果は深いところにある。VM の中まで見て、深い洞察を出す。
2. **節約は届いてはじめて意味がある**：届かなければ、ダッシュボード上の数字にすぎず、請求には反映されない。
3. **顧客にルールを決めさせる**：組織ごとに違い、エンタープライズはシステムを動かし続ける責任がある。そのため、顧客が自分のルールとガードレールを設定でき、プラットフォームはその範囲内で動く。

これが AI actions engine につながったと説明しています。深い洞察を推奨し、コンテキストを踏まえて分かりやすく示し、ガバナンスポリシーを内蔵し、最後に、安全・確実に実行できる実行レイヤーを備えます。エンジンは実行後も検証し、すべてが正常に動いていることを示す、という説明です。

## 7. 注意点・発表者の気付き

- v2 への移行は、すべてのディスクに適用できるわけではありません。一部のディスクには使えず、すべてのリージョンで使えるわけでもないため、事前の分析が必要だと説明しています。
- ストレージを積極的に最適化しすぎると、SLA の未達、性能低下、バックアップの失敗のリスクがあります。
- 推奨が現場の制約を無視していると、他の正しい推奨まで実施されなくなります。発表では、SAP HANA が動く VM に縮小の推奨が出た顧客の例が紹介されました。
- 数値の一部（利用率の改善前の値 50% と 60%）は、発表内で表現が揃っていません。

## 8. 利用者にとっての利点

Commvault の事例として語られた成果は、次のとおりです。

- Lucidity が管理するストレージのコストを 40% 削減し、約 2 年強で純削減額は 200 万ドル。
- 管理している約 3 PB の利用率が 60% から約 90% に向上。
- ディスク追加に関わるインシデント（アラート）が約 50% 減り、SRE が他の作業に時間を使えるようになった。
- 縮小のために約 4 時間の VM ダウンタイムが必要だった作業を、ダウンタイムなしで行えるようになった（Vatsal 氏による仕組みの説明）。

なお、Lucidity が特定した節約額の最大約 87% を実現できるという数値は、50 社以上のエンタープライズ顧客での実績として語られたもので、Commvault 個別の数値ではありません。

## 9. まとめ

このセッションでは、Lucidity の Vatsal 氏が、FinOps ツールの推奨は請求書の表面しか見ておらず、実際に節約につながるのは一部（多くても 25%）にとどまると指摘しました。深いコンテキストと安全な実行を備えた AI actions engine と、その中核の Disk Autoscaler で、ダウンタイムなしの拡張・縮小を実現するという提案です。

Commvault の Karunakar 氏は、数千の VM と数万のディスクを持つ SaaS 環境で、過剰割り当てと手作業の運用に悩んでいたこと、Lucidity の導入で、2 年強で 200 万ドルの純削減、約 3 PB の利用率 60% から約 90% への改善、インシデントの約 50% 削減を得たことを報告しました。教訓は、リソースの内部まで見ること、節約は実行してこそ意味があること、顧客がルールを決められることの 3 点です。
