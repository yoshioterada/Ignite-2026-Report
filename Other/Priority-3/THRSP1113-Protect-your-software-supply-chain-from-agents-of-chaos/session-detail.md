# THRSP1113 Protect your software supply chain from agents of chaos

## 1. はじめに

このセッションは、AI コーディングエージェントがコードを大量に生成する時代に、ソフトウェアサプライチェーン（開発者が取り込むオープンソースのライブラリやコンテナーイメージなど）をどう守るかを扱う短い登壇です。話し手は Chain Guard の Developer Relations に所属する Chuck Friedman 氏です。

主張は明快で、「脆弱性をスキャンして後から修正する」やり方はもはや危うく、**脆弱性を最初から含まない信頼できるオープンソースを土台にするべき**というものです。そのための製品として、Chain Guard が提供する 3,300 以上のコンテナーイメージと、Azure との連携が紹介されました。

このセッションでは、登壇者が「短いデモ」と予告したうえで、イメージ一覧サイト（images.chainguard.dev）を開いて見せる場面があります。あわせて、コーディングエージェントで試した結果の報告もあります（6 章）。

## 4. 発表者が伝えたいメッセージ

メッセージは大きく 3 つです。

- AI エージェントのおかげでコードは大量に、速く書かれるようになったが、取り込むオープンソースも攻撃対象領域も、それに伴って増えていること
- 攻撃者も AI を使っており、最新のフロンティアモデルは脆弱性を見つけて悪用するのが非常に得意になったため、スキャンして修正する方式は成り立たなくなりつつあること
- 対策は、後追いで対処することではなく、**CVE を発生源で取り除いた「信頼できる」オープンソースを使い、最初から安全な状態で作る**こと

登壇者は、パッケージの作られ方についての検証可能な証明（来歴）がなければ、信頼の問題は解決できないとも述べています。

## 5. 発表内容の詳細

### 5.1 Chain Guard の概要

Chain Guard は創業から約 5 年の会社だと紹介されました。オープンソースを毎日ゼロからリビルドし、上流のパッチもリアルタイムで取り込み、必須ではないコンポーネントをすべて取り除きます。その結果、重大な脆弱性やエクスプロイトがほぼゼロの状態になり、本番環境で安全にアプリケーションを動かせるとしています。現在提供しているコンテナーイメージは 3,300 以上です。

ソフトウェア開発ライフサイクル（SDLC）の考え方自体は大きく変わっていないものの、速度は大幅に上がりました。そこで Chain Guard は、プログラミング言語のライブラリ、デプロイを担う CI/CD システム、コードが動くオペレーティングシステムとコンテナーまで、スタック全体を守る製品群に広げています。人間でもエージェントでも、コードを書く・レビューする・保守する場面にガードレールを与えて、コードを信頼できるようにするという位置づけです。これを支えているのが、AI を使って保守を行う Chain Guard の「agentic factory」で、地球上で最大の信頼できるオープンソースのカタログを提供できるのはこの仕組みのおかげだと説明しています。

### 5.2 オープンソース依存のリスク

開発の多くはオープンソースに依存しており、作るものの約 98% を占めると推定されていると、登壇者は述べています。登壇者は、開発者が NPM や PyPI からパッケージを取得するたびに、道ばたで拾った USB ドライブを本番環境に挿しているようなものだ、というたとえを使いました。多くの人がこのリスクを受け入れてしまっているものの、攻撃対象領域は非常に大きく、ここでいう攻撃対象領域とは、オープンソースのコードに混入する、攻撃を受けやすいあらゆるエクスプロイトやマルウェアのことです。

AI コーディングエージェントの世界では、悪意ある攻撃者が現行ツールの見落とすすき間にマルウェアを仕込むため、特に危険だと述べています。問題の核心は、どのライブラリが安全で、どれが侵害されているかを、手遅れになるまで知る手段がないことです。そして、パッケージがどう作られたかの検証済みの証明がなければ、信頼の問題は解決できません。ビルドの「誰が、何を、どこで」と、ライブラリやコンテナーの来歴を知らないまま deploy するのは、祈るようなものだと表現しています。

### 5.3 エージェントによるコード急増

AI エージェントによって開発は加速しており、コード量が 10 倍になったという推計があると紹介されました。必要なコードの取得も、多くをエージェントに任せるようになっています。かつては人間がすべての行を書いていましたが、いまは Copilot、Cursor、Cloud Code（聞こえた表記のまま）といったツールに生成を頼るようになりました。これらのツールはオープンソースに強く依存しており、それがエージェントにとってのサプライチェーンです。登壇者は、NPM のダウンロード数が 2 年で 2.6 倍になったこと、GitHub のコミットが今年 140 億件を超えるペースであることを例に挙げています（数値は音声から聞き取った内容です）。要するに、はるかに多くのコードが、はるかに速く書かれ、はるかに多くのオープンソースを取り込んでいます。

ただし、速度が上がる一方で、攻撃者も AI を使って攻撃を強めています。登壇者は、次の 2 つが同時に起きているとしています。

1. 最新のフロンティアモデルは脆弱性の発見と悪用が非常に得意になり、「スキャンして修正する」方式が通用しなくなっています。ハードン済みコンテナーは「あれば良いもの」から「必須条件」になった、というのが登壇者の言い方です。デプロイするコードを把握し、脆弱性が無いことを確かめる必要があります。
2. 攻撃者はサプライチェーンの別の部分も狙っています。AI を使って、開発者が毎日取り込むライブラリ、エージェントのスキル、ビルドツールを攻撃しています。

根本原因は、開発者を効率的にしているものと同じです。つまり、コードと依存関係が増え、それと同時に攻撃対象領域も、AI による攻撃の効果も増えています。最近のニュースでは、5 年以上コードに潜んでいた脆弱性が、AI が見つける場所を知っているために表面化している例が増えており、それが攻撃者に新しい攻撃先を与えているとも述べました。

### 5.4 チームごとに異なるプレッシャー

AI をより速く効率的に使えというプレッシャーは各チームに降りてきますが、その受け止め方は異なります。登壇者は次のように整理しました。

| 立場 | 関心事 |
| --- | --- |
| プロダクト | 新しい市場と発売日。誰かに先を越されないか |
| エンジニア | AI ツールで開発速度を維持したい |
| セキュリティ | 本当に信頼できるものの上に作っているのか。影響を受けるか、AI 生成コードを信頼できるか、どう追いつくか |

どのチームも間違っておらず、AI を受け入れる必要があり、革新の機会は大きい一方でリスクも増えている、というのが登壇者の見方です。

### 5.5 「スキャンして修正する」方式がなぜ危ういか

コーディングエージェントの利用で、コードを生成する人が増えます。コードが増えるとレビューが難しくなり、保守が必要なレガシーコードの上にさらに積み重なります。その結果、コードが増え、依存関係が増え、コードとアプリを安全に保つ責任が誰にあるかの文脈が減るという状況になります。サプライチェーンそのものを改善できる影響力がない限り、開発者だけに責任を負わせるのは酷だと述べています。

また、開発者の立場では、コードの出どころが清潔で安全だと分かっていれば安心でき、デプロイするリスクも下がります。脆弱性の少ないコードを入れていると証明できれば、ほかの人の仕事も楽になります、という趣旨です。

一方の攻撃側は、1 人の攻撃者が数百のエージェントを使うこともできます。新しいモデルのおかげで、何年も眠っていた脆弱性さえ見つけやすくなっており、より多くの攻撃が、より速く、より多くの標的に向かってきます。

従来の脆弱性への対処は、繰り返しのパターンです。取得する（またはエージェントが取得する）、ビルドしてスキャンする、そして修正とリビルドに時間を費やします。このサイクルは新しい CVE やゼロデイのたびに繰り返され、AKS（Azure Kubernetes Service）の規模では特につらいと述べています。良い知らせは、CVE を発生源で取り除き、最初から安全な状態でビルドできることです。後追いで対応せず、先回りで取り組むべきで、Chain Guard はそれを徹底して行うという説明でした。

### 5.6 Chain Guard と Azure の連携

Chain Guard は、Azure のスタック全体で互換性のある 3,300 以上の安全なコンテナーイメージを提供しています。まず挙げられたのが、新しい「ゼロ CVE」のコンテナーイメージで、終わりのない脆弱性トリアージをなくします。Microsoft Defender for Cloud と組み合わせると、アラートのノイズが減ります。リアルタイムスキャナーとして Defender を使っている場合、コードに現れる脆弱性が少ないほど、アラートも少なくなるという説明です。これにより、初日から信頼できて準拠した、オープンソースの土台が手に入ります。

登壇者は、Chain Guard を使うと防御から攻めへ重心が移り、チームは事業を成長させる仕事に時間を使えるとして、一貫して得られる成果を 3 つ挙げました（8 章）。

イメージのカタログは次のような構成だと紹介されました。

| 区分 | 例 |
| --- | --- |
| ベースイメージ | Python、Go、.NET |
| アプリケーションイメージ | Nginx、Kubernetes |
| AI / 機械学習イメージ | PyTorch |
| FIPS 準拠のバリアント | （種類は個別に列挙されていません） |

これらはいずれも SLA の対象で、SBOM（ソフトウェア部品表）とビルド情報が付き、本番運用に耐える品質だとされています（音声認識では「assigned SBOM」と聞こえており、署名付きかどうかは確定できません）。ブースでは InfoSec や AppSec の担当者から「ソフトウェアの出どころはどこか」という質問が多く、Chain Guard から取得すれば、その一覧をオープンな場所からではなく提供できると説明しました。

Chain Guard は Azure Marketplace で提供されており、Chain Guard を土台にしたワークロードを AKS Automatic で動かせます。Defender は可視性とポスチャー管理を維持し、結果として、堅牢な基盤による移行の加速が得られるとしています。

### 5.7 ワークフロー全体像

流れは次のとおりです。

1. 開発者は、オープンソースから取得する代わりに Chain Guard のイメージを取得する
2. ローカルでビルドしてテストする
3. CI/CD パイプラインに入る

ここ数週間で、新しいツールとして Chain Guard Checks と Workspaces を発表したとのことです。移行用の Gardener（聞こえた表記のまま）など既存のツールと合わせて、最初から安全なワークフローをエンド・ツー・エンドで提供するという位置づけです。パートナーと連携して各マーケットプレイスにも統合しており、パートナーのツールで使えるようテスト済みだと述べています。最も効果が大きいのは、コンプライアンスが必要な組織です。認証済みのコンテナーとライブラリの一覧を提供し、その審査を通す助けになります。

### 6.2 コーディングエージェントでの検証（報告）

登壇者が最近試したこととして、次の結果が語られています。これは会場で実演されたものではなく、過去に行った試験の報告です。

## 8. 利用者にとっての利点

登壇者が「Chain Guard と組むと一貫して得られる」と述べた成果は次の 3 つです。

1. **AI の速度とセキュリティの両立**：エンジニアとエージェントが、信頼できるサプライチェーンの上で速く作れる。脆弱性が 98% 減り、ほぼゼロの CVE になる。速度とセキュリティの二者択一にならない
2. **イノベーションへの集中**：CVE のトリアージや修正に費やす時間がなくなる。顧客は年間およそ 10,000 時間の開発者の時間を取り戻している
3. **継続的なコンプライアンス**：FedRAMP、FIPS、SOC 2 に対応するイメージがあり、自動生成される。数週間かかる監査対応の駆け込みがなくなる（すでに用意されているため）

そのほか、Microsoft Defender for Cloud と併用するとアラートのノイズが減る点も、利点として語られました。

## 9. まとめ

登壇者が最後に示した要点は 3 つです。エージェントによるコーディングの高速化には、コードの出どころを知ることへの信頼が、これまで以上に必要です。信頼できるオープンソースを使えば、攻撃対象領域は縮まります。そして Chain Guard のコンテナーイメージは、Azure のワークフローにネイティブに組み込めます。Chain Guard の 3,300 以上のイメージを Azure Marketplace から入手でき、images.chainguard.dev で閲覧できます。詳しい話はブース 5316 で聞けるとのことでした。

> 補足：終盤、登壇者は会場の質問に答えた人に景品を投げて渡していました（イメージの数、CVE がどこまで減ったかなど）。内容の理解には関係しないため、本文では扱っていません。
