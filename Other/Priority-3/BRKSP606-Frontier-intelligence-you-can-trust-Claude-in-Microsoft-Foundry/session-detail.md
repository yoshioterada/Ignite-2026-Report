# BRKSP606 Frontier intelligence you can trust: Claude in Microsoft Foundry

## 1. はじめに

このセッションは、Anthropic のプロダクトマネージャーが、Microsoft Foundry 上で最も高性能な Claude モデルを「信頼を手放さずに」使う方法を約 23 分で説明する内容です。登壇者は、現場は最も高性能なモデルを求め、リーダーは自分が責任を持てる統制を求めるため、多くの企業が両者を二者択一だと考えている、と問題を設定します。そのうえで、Claude と Microsoft Foundry なら両方を得られると主張します。

構成は、Claude の位置づけ、Foundry で Claude を使う 4 つの理由（性能、Microsoft のスタック、本番までの速さ、安全性とガバナンス）、そして「エージェントを本番に出す前に答えるべき 3 つの質問」です。後半には、架空の銀行の紛争（dispute）対応デスクを題材にした動画のデモと、原子力分野の Everstar の事例が含まれます。

## 5. 発表内容の詳細

### 5.1 背景：不均一な進捗とモデルの更新速度

登壇者は、2024 年には多くの組織がパイロットを動かしていたが、現在は本番のエージェント、ガバナンス委員会、予算枠を持つようになったと述べます。ただし進捗は均一ではありません。PwC の調査（今年 4 月）では、5 社に 1 社が AI の生む価値のほぼ 4 分の 3 を得ています。

登壇者によれば、多くの企業は高性能なモデルと統制のどちらかを選ばなければならないと考えています。一部の企業は、他社が「このモデルは十分に安全だ」と証明するのを待ちますが、終わるころには次のモデルが出ています。別の企業は、安全対策をすべて自前で構築しようとしますが、モデルが変わるたびにその作業は難しくなります。

モデルの変化の速さについては、トランスフォーマーとスケーリング則の間が 3 年、複数ステップの作業をするエージェントから、本番で信頼されるエージェントまでが 1 年、という例を挙げています。今ではモデルが数か月、数週間単位で変わります。2022 年はチャット、2024 年はコーディング支援、現在は実際の仕事をエージェントに任せて結果を確認する段階です。この秋には新しい Sonnet、Opus、Haiku が出て、Foundry でも利用できるようになりました。そのため、前の四半期に評価したモデルは、もう最新ではない可能性があります。多くのチームは、モデルを選び、堅牢化し、セキュリティの承認を得て先へ進みますが、基準が動き続ける今回の分野ではこの方法はうまく働かない、と指摘しています。

### 5.2 Anthropic と Claude

Anthropic は研究機関として始まり、今もそうだと登壇者は述べます。フロンティアで作業するため、モデルができることと、うまくいかないことを最初に目にすることが多く、安全性を最後の工程や副産物としては扱わないという立場です。責任あるスケーリング（responsible scaling）、解釈可能性（interpretability）、constitutional AI が Claude の振る舞いを形づくり、それが Claude Code、computer use、MCP（モデルをツール、スキル、データにつなぐオープン標準）、skills といった使える機能につながっている、という説明です。

Claude はフロンティアの知能（コーディングとエージェント能力を中核に持つ）を、Foundry は企業が必要とする周辺（データとコンテキスト、アイデンティティとガバナンス、本番までの道）を担います。コンテキストも統制もない高性能なモデルは、デモのままで終わる、と登壇者は述べ、両方が必要だとしています。

Claude が加える価値として、次の 2 点が挙げられました。

- **仕事のために作られている**：Anthropic は enterprise-first の企業であり、Claude は企業の実務をこなすために作られている。
- **信頼できるパートナー**：Microsoft 自身も Claude で構築している。Claude は Microsoft 365 Copilot、Copilot Studio、GitHub Copilot に入っている。Claude の constitution を公開し、すべてのモデルに system card を公開しているため、リスク部門は、データに触れる前に Claude がどう振る舞うよう設計されているかを確認できる。

### 5.3 Foundry で Claude を使う 4 つの理由

登壇者は、チームが Foundry で Claude を選ぶ理由を 4 つに整理しています。

| 理由 | 内容 |
| --- | --- |
| Intelligence | 仕事ごとに適した Claude モデルを選べる。 |
| Microsoft のスタックに収まる | すでに使っている Microsoft の環境に入る。 |
| 本番までが速い | パイロットから本番へ速く進める。 |
| 安全性とガバナンス | すべての土台に組み込まれている（5.6〜5.9 で詳しく説明）。 |

はじめるのは簡単で、Foundry に Claude を追加するのに移行は不要です。すでに結んでいる同じ契約、同じ Entra ID、同じ Azure コミットメントの下で使えます。

### 5.4 モデルの選び分け

1 つのモデルですべてをこなす必要はなく、用途に最も合うモデルを選ぶほうがよい、と登壇者は説明します。紹介された各モデルの位置づけは次のとおりです。

| モデル | 位置づけ |
| --- | --- |
| "Fable 5.2"（聞こえたまま） | 最も難しい問題向け |
| Opus | 多くのチームが最初に使うべきモデル。深い推論と、長時間動くエージェント向け |
| Sonnet | 能力、速度、コストのバランス型。範囲が明確な仕事を大規模に行うのに向く |
| Haiku | 高速で、実行コストがかなり低い。大量処理向け |

> 注意：最初のモデル名は、音声認識の都合で表記が確定できません。後半でも "Fable and Mythos hosted on Anthropic today" と読める箇所があり、これらのモデル名は聞こえたままです。

組み合わせて使うことも勧められています。あるモデルが作業を計画し、小さなモデルが定型のステップを実行する形です。初日から完璧に選ぶ必要はなく、Opus から始めて、必要以上だと分かれば下げ、足りなければ上げる、という使い方も紹介されました。

実際の仕事では、Claude が複雑な作業を担当し、手順を計画し、サブエージェントを並列に動かし、非常に長い作業の間もタスクに集中し続ける、と説明されています。規制対応のレビュー、コードベースの監査、文書の山にまたがる分析も、1 回のセッションで終わらせられるとのことです。さらに、Foundry Agent Service が MCP を通じて、初日から Claude をツールやデータにつなぎます。これにより、エージェントは推奨するだけでなく、実際に行動できます。

### 5.5 購入と運用（IT 部門向け）

登壇者は、IT 部門にとって最も関心の高いスライドかもしれないとして、次の点を挙げています。

- 新たな調達は不要。Claude はすでにある Microsoft の契約の下で動く。
- Azure のコミットメントを消化する。すでに承認済みの予算が使える。登壇者は、今週この点について質問を受けたため、あらためて強調すると述べています（このときの発話は "Mac commitment" と聞こえ、音声認識の都合で表記が確定できません。直前には "Azure commitment" と述べています）。
- エージェントは Entra ID を使う。人を管理しているのと同じアイデンティティシステムで管理できる。
- 開発者は、使い慣れた Azure SDK と Foundry のツールの中にとどまる。

前回ベンダーを導入したときにどれだけ時間がかかったかを思い出してほしい、と登壇者は述べます。Claude は Microsoft 内のネイティブな体験なので、その大半を省略できるという説明です。

本番への道筋は次のとおりです。まず、うまくいくものから始めます。Anthropic からはリファレンスアーキテクチャが、Foundry からはデプロイテンプレートと、すぐに始められる MCP コネクタが提供されます。「パイロットしたものがそのままスケールする」ことが売りで、サーバーレスで、ガバナンスが組み込まれており、規模を拡大してもアーキテクチャが変わりません。サポートも、Claude は Anthropic、Foundry は Microsoft と、両社の担当者に直接アクセスできる形です。

### 5.6 安全に運用するための前提：責任の分担

登壇者は、モデルが高性能になるほど、そのモデルはより多くの自社システムを自律的に扱え、失敗したときの影響が大きく、悪用や、依頼していないことをエージェントが行う余地も増える、と説明します。安全性は後から付け足せるものではなく、後から追いつけるものでもありません。

また、リスクを 1 社だけで管理することはできず、層ごとに責任者がいるとしています。

| 層 | 責任者 |
| --- | --- |
| Claude とそのセーフガードの運用 | Anthropic |
| Foundry のプラットフォーム制御と、プロンプト・出力が処理され、保持されるコンテンツが保存される Azure インフラ | Microsoft |
| エージェントと、それを誰が使えるか | 利用者（顧客） |

エージェントは利用者のものなので、エージェントごとに答えられるべき 3 つの質問があります。これに答えられなければ、そのエージェントはおそらく実世界に出す準備ができていません。そして、新しいモデルが出るたびにこの 3 つの質問は答えにくくなる、と登壇者は述べています。

### 5.7 質問 1：どこで動くのか

Claude と Foundry は、すでに使っている Azure のクラウド上で動きます。モデルについては、Opus、Sonnet、Haiku が Azure 上でホストされています。一方、Fable と Mythos は、現時点では Anthropic 側でホストされていると述べました（モデル名は聞こえたままです）。データについては、プロンプトと completion（応答）、保持されるコンテンツは Azure のインフラ内にとどまります。デプロイは、global standard か、US data zone から選べます。

選び方として、各ワークロードが扱うデータから出発し、そのワークロードの最も厳しい要件を判断基準にするよう勧めています。モデルと同様に、デプロイもワークロードごとに混在させられます。避けたい失敗は、単純だからという理由ですべてのワークロードを 1 つの経路に通すことです。

### 5.8 質問 2：誰がデータを見られるのか

登壇者は、スライドの文を「そのまま読み上げる」としたうえで、次のように説明しました。

- 既定では、Anthropic の担当者はデータを読めない。
- 人間によるレビューが行われるのは、自動の安全システムが、害のある可能性や利用ポリシー違反としてコンテンツにフラグを立てたときだけ。
- レビューは制御されたアクセス経路を通り、承認された少人数のグループが行い、アクセスはログに記録できる。
- Anthropic は、明示的な許可なしに、企業のデータでモデルを学習させない。

では、データが保護されているのに、なぜ悪用を探す必要があるのか、という疑問に対して、登壇者は次のように答えています。最も深刻な悪用は見つけにくいからです。まともな攻撃者は「攻撃を手伝って」と 1 回では頼まず、リクエストを分割し、あるセッションで小さな依頼を、次のセッションで別の依頼を、というように送ります。1 つずつ見ると無害ですが、長期で見るとパターンが見えてきます。1 社が自社のトラフィックだけで全体像を見ることは難しく、自前でセーフガードを作るだけでは、チームがどれほど優秀でも足りません。そのため Anthropic は、利用者が持つ制御と並んで自社のセーフガードを運用し、深刻な悪用が顧客や評判に影響する前に捕捉できるようにしている、と説明されました。

### 5.9 質問 3：何ができ、どうやって把握するのか

登壇者は、Claude を含め完璧なモデルはなく、間違える、読んだ内容に誤導される、依頼の意図を取り違える可能性があるとして、それを前提に計画するよう勧めます。モデルが常に正しいという前提で戦略を立てるのではなく、モデルが間違えても保たれる境界をエージェントの周りに設ける、という考えです。エージェントが課題から逸れても、境界がどこまで行けるかを決めます。

そのために、3 つの仕事があります。

1. **Declare（宣言）**：各エージェントが到達でき、操作できる範囲を決める。Entra ID で、エージェントごとに固有のアイデンティティとアクセス権を持たせる。
2. **Contain（封じ込め）**：その境界と制限の中にエージェントをとどめる。Foundry の hosted agents とプラットフォームのポリシーを使う。
3. **Detect（検知）**：問題が起きたときに、起きている最中にそれを見られるようにする。Foundry observability と Azure Monitor を使う。

登壇者は、これらはすでに Foundry で今日使えるツールであり、チームにとって新しいものではないと述べています。

### 5.10 顧客事例：Everstar

登壇者は、原子力エネルギー分野の Everstar を紹介しました（社名は聞こえたままで、音声認識の都合で表記が確定できません）。原子炉の認証には数百万時間のエンジニアリング工数がかかり、誤りが許されない領域です。

Everstar は **Gordian** というプラットフォームを構築しています。規制、設計仕様、エンジニアリング記録を取り込み、引用付きのエンジニアリング文書とライセンス関連の文書（engineering and licensing documents）を作成します。Claude と Foundry の上で動き、米国の原子力輸出規制に合わせて設定されています。処理は米国内で行われ、アクセスは米国の人員に限られます。

エネルギー省（Department of Energy）とのデモでは、208 ページの安全解析文書を 1 日で作成しました。登壇者によれば、通常の基準は 4〜6 週間です。そして、人が主導権を持つ点は変わらず、規制当局に出す前に、資格のあるエンジニアが出力をレビューします。同社の founding product lead（創設メンバーのプロダクト責任者）である Matt Huang 氏は次のように語っています（発表での引用）。

> Anthropic と Azure の組み合わせで、世界最高の能力と世界最高のセキュリティが得られる。それはまさに原子力が必要としているものだ。

登壇者は、これを、厳しい精査の下で動く機微な仕事が Claude と Foundry で動いている例として示しました。

## 6. デモ・手順

登壇者は、再生する前に確認してほしい点を 4 つ挙げています（"Let me show you an example"、"before I play this" などの発話から、事前に用意した動画を再生する形式だと分かります）。画面の細部は音声からは確認できず、ナレーションで語られた範囲だけを書きます。

確認ポイントは、①エージェントが必要なアクセスだけを持つ固有の Entra ID を持つこと、②実際の仕事（架空の銀行のカード紛争）を行うこと、③範囲外のものに手を伸ばしたとき境界が保たれること、④すべてのステップが Foundry Observability と Azure Monitor に表示されることです。

語られた順序は次のとおりです。

1. 架空の銀行の紛争対応デスクを見せ、いくつかのケースを確認する。一次対応を行うエージェントと、判断を下すアナリストがいると説明される。
2. 最初のエージェントは Opus 5.5 を使い、Azure 上でホストされている（モデルのバージョンは聞こえたままです）。固有の Entra ID を持ち、ケースファイルの読み取りと下書きの書き込みはできるが、credits ledger（クレジット台帳）にはアクセスできない。
3. アナリストがエージェントにケースの処理を依頼する。
4. エージェントはケースを読み、ポリシー情報とトランザクションを取得し、ポリシーを読み、下書きの推奨を保存する。実際の二重請求（real duplicate）はクレジット対象とし、他の 2 件の請求は認めないという内容になる。レビューを省略するよう求められても、レビューは省略しない。
5. アナリストが承認し、エージェントにクレジットの発行を指示するが、Azure がそれをブロックする。このエージェントには credits ledger へのアクセス権がなく、実行する権限がないためで、登壇者はこれを「境界が働いている」と述べている。
6. 2 番目のエージェントが引き継ぐ。これは Sonnet 5.5 上で動き（聞こえたまま）、台帳には書き込めるが、ケースファイルは見られない。
7. 2 番目のエージェントがもう一度実行し、今回はクレジットが発行される。
8. トレースと Azure Monitor で、ブロックされた呼び出しを含むすべてのステップを確認できる。

## 7. 注意点・発表者の気付き

- モデルは完璧ではなく、間違えたり、読んだ内容に誤導されたり、意図を取り違えたりします。モデルが常に正しい前提で設計せず、間違えても保たれる境界を作ることが求められています。
- 1 つのモデル、1 つのデプロイ経路にすべてを寄せる単純化は避けるべきだと説明されています。
- モデルを選び、堅牢化し、セキュリティの承認を得て先へ進むという従来の進め方は、基準が動き続けるこの分野ではうまく働かない、と指摘されています。
- 3 つの質問（どこで動くか、誰がデータを見られるか、何ができ、どう把握するか）に答えられないエージェントは、実世界に出す準備ができていません。
- 最も深刻な悪用は、小さな依頼に分割されるため 1 社では見つけにくく、自前のセーフガードだけでは足りません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 既存の契約、Entra ID、Azure コミットメントの下で使え、移行も新たな調達も不要。
- エージェントを、人と同じアイデンティティシステムで管理できる。開発者は Azure SDK と Foundry のツールを使い続けられる。
- パイロットで使ったものがそのままスケールし、規模を拡大しても構成が変わらない。サーバーレスで、ガバナンスが組み込まれている。
- プロンプト、応答、保持されるコンテンツが Azure のインフラ内にとどまり、デプロイは global standard か US data zone から選べる。
- 既定では Anthropic の担当者がデータを読めず、明示的な許可なしに企業データでモデルを学習させない。
- Everstar の Gordian は、208 ページの安全解析文書を 1 日で作成した（通常の基準は 4〜6 週間）。人間のエンジニアのレビューは残る。

## 9. まとめ

登壇者は、最初の問いに戻ります。高性能なモデルと、責任を持てる統制は二者択一ではなく、Claude と Foundry で両方を得られるという主張です。3 つの質問への答えは、どこで動くか＝利用者がすでに使っている Azure 上、誰がデータを見られるか＝既定では Anthropic の担当者は見られず、深刻な悪用は時間をかけて検知する、何ができ、どう把握するか＝Entra ID、Foundry、Azure Monitor が境界を保ち、すべてのステップが見える、というものでした。

次のステップとして、自社のワークロードごとにこの 3 つの質問に答えられるかを確認し、答えられるなら、新しいモデルが Foundry に登場したときに評価できる状態だと述べています。案内として、前日だったと思う、と登壇者が述べたセッション "Claude Keeps Building"（BRKSP624）がオンデマンドで視聴できること、ハブのブースでのライブデモとシアタートーク、Microsoft Learn 上の Claude と Microsoft Foundry のドキュメント（Claude API のドキュメントと Microsoft のドキュメントの両方）が挙げられました。録音には Q&A は含まれておらず、登壇者は終了後に会場の脇で質問に応じると述べています。
