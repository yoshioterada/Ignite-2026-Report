# THRSP1075 Modernize industrial architecture for AI-powered operations

## 1. はじめに

このセッションは、産業機器（コンプレッサーやターボ機械など）の保全・信頼性管理を支える Baker Hughes のソフトウェア「Cordant」を題材に、EPAM、Microsoft、Baker Hughes が共同で進めている取り組みを紹介する約 15 分の登壇です。取り組みは 3 本柱で語られます。(1) GitHub Copilot とエージェントによる、AI ネイティブな製品開発ライフサイクルへの刷新、(2) 顧客データを取り込む「オンボーディング」をエージェントで加速すること、(3) 顧客の基幹システム（ERP など）との連携を速くすること、です。土台はいずれも Microsoft Azure で、Azure Databricks も使われます。

発表を通じた主張は、「エージェント自体を作ることは難しくない。難しいのは、エージェントが働く環境に正しいコンテキストを与え、正しいプロセスで統制することだ」という点です。また、エージェントは人を置き換えるものではなく、専門家（ヒューマン・イン・ザ・ループ）の「出発点」を作るものだと繰り返されます。

このセッションでは、画面を使ったデモは行われていません（スライドと口頭の説明が中心です）。

Mark 氏は、エージェントは人を置き換えず、「ドメイン専門知識を加速するターボチャージャー」だと位置づけています。

## 5. 発表内容の詳細

### 5.1 産業界の顧客が直面する課題

David 氏は、産業の顧客が過去 10 年ほど取り組み続けている課題を、次のように説明しました。

**データの統合**：配管計装図（P&ID）、ヒストリアン、仕様書、OEM のマニュアル、運転手順書など、多様なデータを統合して使える状態にしたいが、多くの顧客はまだデータをサイロから取り出せていません。

**人材不足**：LNG トレインや製造・生産施設に配置できる保全エンジニア・信頼性エンジニアが足りない、という課題です。David 氏は、有能で意欲のある人が入ってきていないという意味ではないと断っています。足りないのは、特にコロナ禍以降、その設備や機械の周りで育ち、履歴、経緯、動き方、故障の仕方を深く知っている人だと述べています。新しい人材のなかには、プラントではなく遠隔センターから監視する、遠隔の信頼性エンジニアや運転担当者もいます。こうした人たちに、20 年、15 年という設備の運用の文脈（どれが既存設備で、どれが最近導入された新設備か、どう動いているか）を身につけてもらうことが求められています。

**コンテキストの与え方**：David 氏は、単純なインサイトを出して「手順どおりやってください」と言うのではなく、その機械がどのように保全されてきたかという背景まで伝え、人が正しい判断ができるようにする、という方針を示しました。

**開発速度**：上の 2 つの結果として、顧客から「より多くの機能とインサイトを、より速く」という要求が出ており、Baker Hughes と EPAM が共有するソフトウェア提供のエコシステム自体を加速する必要がある、と述べています。

### 5.2 3 社の役割と 3 本柱

David 氏は、取り組みに関わる 3 社を次のように紹介しました。

| 会社 | 役割・特徴 |
| --- | --- |
| EPAM | デジタルソフトウェアエンジニアリング・AI エンジニアリングの 65,000 人規模の人員を世界の顧客に提供。ここ数年、Baker Hughes と協業 |
| Microsoft | 技術ベンダー。GitHub Copilot、Azure、Azure Databricks の上に構築 |
| Baker Hughes | 100 年超のドメイン専門知識を持つ。コンプレッサーやターボ機械が、どう壊れ、どう動くかのモデルなど、独自の IP を持ち、ソフトウェアプラットフォームを通じて顧客に提供 |

そのうえで、課題への対応を 3 本柱として説明しました。

1. **ソフトウェア提供の加速**：製品、エンジニアリング、アーキテクチャの各チームを巻き込んだ、新しい「AI ネイティブでエージェント型の製品開発ライフサイクル」を構築する。
2. **エージェントによる顧客の迅速なオンボーディング**：顧客独自のデータ（P&ID、機器マニュアル、仕様書など）をエージェントで抽出・変換し、ステージングして Cordant に戻す。これにより、顧客は自社のコンプレッサーやポンプなどの機器と、それに関連するデータを画面で確認できる。
3. **連携の高速化**：顧客が使っている ERP の種類やバージョンを問わず、Azure を基盤として Baker Hughes のサポートとプラットフォームに直接つなげる、拡張可能な方法を作る。ERP として挙げられたのは、SAP ECC、S4HANA、IBM Maximo、Oracle JD Edwards、Hexagon です。

3 本柱を技術側から整理した発言は次のとおりです。

- GitHub Copilot と Azure Databricks を通じて、統制された（governed）リリースを速く出す
- 顧客オンボーディング用の構成（configuration）エージェントを作る
- 診断（diagnostician）エージェントで、アラームから原因（cause）まで進める
- Azure 上の統制されたデータ基盤と連携コネクタで、接続までの速度を上げる

David 氏は、顧客から見える成果を「より速く製品が届く、素早くオンボーディングできる、インサイトからアクションへ進める、日々使うシステムへデータがつながる」と整理し、すべての土台が Microsoft Azure であると述べました。

### 5.3 GitHub Copilot による製品開発ライフサイクルの再設計（David 氏）

David 氏は、エージェントそのものは「テーブルステークス（当たり前の前提）」であり、ソフトウェア提供を管理するエージェントを作ること自体は目新しくないとしました。EPAM が取り組んだのは、**産業用ソフトウェアを作るための適切なプロセスをどう組み込むか**です。具体的には、製品、アーキテクチャ、開発、テスト・QA といったチームをまたいで調整する仕組みです。

要件の聞き取りや、高レベル設計・詳細設計を作るエージェントを置くだけでは足りません。次のコンテキストをエージェントに与えることが必要だと説明しました。

- そのソフトウェアがどう使われているか
- 顧客が個々の機能からどんな価値を得ているか
- 顧客が現在、インターフェース、オプティマイザー、エンジンをどう使っているか

これにより、顧客から製品チームに新しい要望が来たときに、エージェントが顧客が変更や新機能を求める文脈を理解でき、それを要件に反映して「正しく作られる」ようにします。David 氏は、エージェントを作ることは「正直なところ簡単な部分」で、**難しいのは**、すべての必要なコンテキストと知識があるエコシステムでエージェントを動かし、速さを保ちつつ、商用・製品アーキテクチャ・開発の担当者が作る過程のすべてを承認するプロセスを組むことだ、と述べています。

### 5.4 Cordant と顧客データのオンボーディング（Mark 氏）

Mark 氏は、David 氏が「どうソフトウェアを作るか」を話したのに対し、自分は「顧客がどう使うか」を話すとして切り出しました。

Baker Hughes はエネルギー企業で、事業の一部は油田サービスと機器、もう一部は産業エネルギー技術（天然ガスの輸送と、それに伴うターボ機械全般）です。これらに外部の第三者センサーを組み合わせて 1 つにまとめるのが、ソフトウェア製品 Cordant です。バランス・オブ・プラント、企業全体の資産を取り込み、保全戦略、保全計画、プロセス最適化、排除すべき不具合の発見を 1 つのパッケージで支援します。

課題は、多数のセンサーがあるプロジェクトでデータを整理するのに、想像以上に時間がかかることです。スライド左側の「ソース情報」にあたるデータは、P&ID、プロセス図、Excel スプレッドシート、メール、レガシーシステム、暗黙知（tribal knowledge）など、あらゆる場所から来ていて、整理されていません。各資産が互いにどう関係し、どのシステムにつながり、どのプロセスで使われるかが分かるまで、誰もそのデータを活用できません。

目指す姿は、スライド右側の、明確な**資産階層（asset hierarchy）**です。サイトレベルで起きていること、資産、その整理のされ方、資産を使うプロセスが分かる状態になれば、ソフトウェアを適用してインサイトと成果を出せます。

従来、この整理には時間がかかり、ドメイン専門知識を要し、顧客ごとにカスタム対応になりがちでした。同じ整理をしている顧客は 2 社とないため、価値が出るまでの時間が長くなります。そこで**エージェント**を使います。エージェントは人間の関与（ヒューマン・イン・ザ・ループ）を置き換えるわけではなく、専門知識が引き続き必要ですが、データ整理を始めるための「良い出発点」を作ります。複雑で理解しにくい状態から、顧客の価値実現までの時間を短縮し、ソフトウェアを素早く動かせる状態に持っていく、という説明でした。

### 5.5 午前 2 時のアラームと診断エージェント（Mark 氏）

次に Mark 氏は、実運用での場面として「午前 2 時にアラームが鳴る」状況を挙げました。誰に連絡するか、どの程度巻き込むかは難しい判断で、しかも毎回ゼロから情報を集め、アプリケーションやカンファレンスコールを開くことになりがちです。これは本来、再現性のあるものにすべきだ、という問題意識です。

Baker Hughes の解は、関連するデータを集約し、**診断エージェント（diagnostic agent）**を適用して、考えられる原因の候補を出すことです。受け取る側の信頼性エンジニアにとっての出発点になります。ここでも人を外さず、エンジニアのドメイン専門知識に対する「ターボチャージャー」と位置づけています。

さらに、顧客基盤全体を横断して成果を積み上げ、Baker Hughes が持つドメイン知識を組み込むことで、価値が出るまでの時間をさらに短縮できるといいます。Baker Hughes には、数十年の歴史を持つ状態監視サービス事業があり、そのコンテキストをエージェントに適用できることが、エージェントを「本当にユニーク」にする点だと述べました。

Mark 氏は、エージェントを作る人への教訓として、「コンテキストがすべてであることは皆さんご存じだが、計画を進めるなかでそれを忘れないでほしい」と述べています。

### 5.6 ERP などとの連携（Mark 氏）

Cordant は、資産の状態監視・ヘルスデータの作成と、それを最も効率の良い成果につなげる戦略づくりを支援します。しかし、その先が重要です。顧客には独自のワークフローとシステムがあり、代表例として SAP や Maximo が挙げられました。顧客が従業員にやるべきことを入力し、実施されたかどうか、いつ実施されたかを追跡するのがこうしたシステムで、Cordant がここに連携できなければ「役に立たない」と述べています。

難しい点は、このデータもまた顧客ごとに独自で、独自の構成になっていて、顧客が上に載せた知見の層が異なる場合もあることです。**API をつなぐだけ**では済みません。そこでエージェントを使い、これまでの連携の進め方を横断的に見て、顧客のデータの整理のされ方を理解する作業を加速し、連携を「シンプルで、安全で、拡張可能な」形で改善します。Mark 氏は、データを取り込み、より効果的に使えるようになり、顧客がより効果的にアクションを取れるようになった、と整理し、これは David 氏が話した Azure の統制されたプリンシプル（Azure Foundation、Azure Databricks）の上に成り立っていると述べました。

### 5.7 全体のループ

Mark 氏は最後に、全体を「ぐるっと一周」にまとめました。

1. AI とエージェント型のユースケースで、データをうまくつなぐ。
2. 過去の理解と知識に基づくコンテキストを提供して、行動につなげる。
3. その結果を製品にフィードバックする。これが、David 氏が話したエージェント型のユースケースと開発プラクティスに戻り、製品ライフサイクルのループが閉じる。

これにより、オンボーディング、理解、接続が信頼できて再現可能な形になり、新しい顧客を迎えるたびにゼロからやり直さずに済む、という説明です。

## 7. 注意点・発表者の気付き

- エージェントを作ること自体は「簡単な部分」。難しいのは、エージェントに適切なコンテキストと知識を与え、速さを保ちつつ、関係部門の承認を得るプロセスを組むこと（David 氏）。
- 人を手順リストに従うだけの存在にしない。コンテキストを与えて判断してもらう（David 氏）。
- エージェントはヒューマン・イン・ザ・ループを置き換えない。専門知識は引き続き必要で、エージェントは出発点を作るもの（Mark 氏）。
- エージェントを作る人への教訓は、コンテキストがすべてであり、計画を進めるなかでそれを外さないこと（Mark 氏）。
- 顧客のデータは顧客ごとに独自で、同じ整理をしている顧客は 2 社とない。ERP 連携も「API を挿すだけ」では済まない（Mark 氏）。
- 数値としては、EPAM の 65,000 人規模の人員、Baker Hughes の 100 年超の歴史が語られた以外、導入効果（ダウンタイム削減率や期間短縮など）の具体的な数値は、発表では示されていません。

## 8. 利用者にとっての利点

発表者が整理した、顧客が得られる体験は次のとおりです。

- 製品がより速く届く（GitHub Copilot と統制された開発プロセスによる、リリースの加速）。
- 迅速なオンボーディング（エージェントが P&ID、機器マニュアル、仕様書などを抽出・変換し、Cordant 上で機器と関連データを確認できる状態にする）。価値が出るまでの時間が短くなる。
- インサイトからアクションへ（診断エージェントが考えられる原因の出発点を提示し、信頼性エンジニアの判断を支える）。
- 日々使うシステムへのデータ連携（SAP、Maximo などの ERP と、シンプル・安全・拡張可能な形でつなぐ）。
- 最終的な目的は、計画外のダウンタイムの削減。

発表では、具体的な顧客名や成果の数値は示されていません。

## 9. まとめ

EPAM、Microsoft、Baker Hughes は、データのサイロ、保全人材のコンテキスト不足、顧客からの開発速度の要求という課題に対し、Cordant を軸に 3 本柱の取り組みを進めています。GitHub Copilot とエージェントによる製品開発ライフサイクルの刷新、エージェントによる顧客データのオンボーディング、ERP などとの連携の加速です。運用の場面では、診断エージェントがアラームの原因候補という出発点を示します。基盤は Azure と Azure Databricks です。

通底する考え方は、エージェントは人を置き換えず専門家の出発点を作るものであり、成否を分けるのはコンテキストと統制されたプロセスだ、という点です。最後に、成果を製品開発に戻すことで、新規顧客のたびにゼロから始めない、再現可能なループにすると語られました。
