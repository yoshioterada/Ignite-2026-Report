# THR962 Why access isn't adoption: GitHub Learn's guide to AI enablement

## 1. はじめに

このセッションは、GitHub の学習支援チームの担当者が、「ツールを配っただけでは使われない」という問題にどう向き合うかを、実際の顧客とのやり取りを軸に語った約 25 分の発表です。題材は GitHub Copilot ですが、登壇者は、使っていない製品であっても、持ち帰ってチームや組織、ビジネスリーダーに使えるフレームワークとリソースを 1 つでも渡したい、と述べています。

発表の中心は、「200 人の開発者に GH600 試験を受験させたい」という顧客からの依頼です。登壇者は、その依頼に対して「なぜ？」と問い返し、本当の目的と現状を確認し、測定の方法を決め、定着させる仕組みを組み立てていきます。話は 3 つの章（依頼を紐解く、必要な能力を定める、定着させる）で進みます。

結論をひとことで言えば、**トレーニングは成果や行動を変えるための手段であり、唯一の手段ではない**という点です。トレーニングに加え、コミュニケーション、コミュニティとチャンピオン、運用（オペレーション）の 4 つを組み合わせる考え方が示されます。

このセッションでは、画面を使ったデモは行われていません。スライドを使った口頭の説明が中心です。

## 3. 何に関する発表か

テーマは、AI ツールの「導入（アクセス）」と「活用（アダプション）」は別物であり、その差を埋めるための支援（enablement）をどう設計するか、です。登壇者は、日々 GitHub の顧客が GitHub 製品を採用し、使い続けられるよう支援している立場から話しています。

発表の流れは次のとおりです。

1. 導入：ゴールと、実際の顧客の事例
2. 章 1「依頼を紐解く」：なぜ GH600 の受験を求めるのか、真の目的は何か
3. 章 2「能力を定める」：Copilot adoption maturity dashboard で現状を知る、Copilot Pro バッジで能力を定義する、成功をどう測るか
4. 章 3「定着させる」：トレーニング、コミュニケーション、コミュニティ（チャンピオン）、運用の 4 つのレバー、そして成果の検証
5. まとめ：リソースを集めたランディングページの案内

## 4. 発表者が伝えたいメッセージ

登壇者の主張は、「ツールを渡しても使われるとは限らず、必須の研修を 5 つ割り当てても使われるとは限らない」という点にあります。研修を行う理由は、成果や行動を変えるためだけであるべきだ、と述べています。

そのため、依頼を受けたら、まず「なぜ」を確認します。登壇者はこれを、次の 3 つの観点で整理しています。

- 解決したい問題は何か
- 将来に向けて見えている機会は何か
- 埋めたいギャップは何か

これらは、どれか 1 つのこともあれば、組み合わさることもあります。2026 年の今は、トレーニングの修了数を追うところから抜け出す必要がある、というのが登壇者の考えです。

もう 1 つのメッセージは、定着には時間がかかり、1 回の施策では足りないということです。登壇者は習慣形成に 21 日かかるという例を挙げ、ジムに 1 回行っただけで目標を達成できないのと同じで、1 回のウェビナーや 1 回の（8 時間の）ハッカソンでは続かないと述べています。

## 5. 発表内容の詳細

### 5.1 導入と顧客の依頼

登壇者は、あるサービス契約の窓口を通じて来た顧客の話を紹介します。依頼は「200 人の開発者を GH600 試験で認定したい」というものでした。GH600 は、GitHub が提供する最初のロールベースの試験で、エージェント型ワークフロー（agentic workflows）の開発を扱います。製品ベースの試験と比べると、高度で複雑な試験だと説明しています。

登壇者は受験への意欲を歓迎しつつ、「でも、なぜ？」と尋ねる癖があると述べます。研修が終わったのに何も起きなかった、という経験は誰にでもあるはずだ、という問題意識から、この「なぜ」を確認する流れに入ります。

### 5.2 章 1：依頼を紐解く（Unpack the request）

ここでの問いは、認定バッジを取ってリンクトインで共有すれば満足なのか、それとも別に達成したいことがあるのか、です。登壇者は、顧客から「研修の受講状況は追跡する必要があるか」と聞かれることが日常的にあるそうです。答えはたいてい「はい」で、登壇者は内心でため息をつきつつ、規制業界で追跡の要件があるかもしれないと考えたうえで、研修の目的（成果と行動の変化）に議論を戻そうとします。「たいてい負けますが」と述べています。

### 5.3 章 2：能力を定める（Determine the capability）

研修は、能力（capability）・コンピテンシー・行動を生み出すためのものです。そのためには、人が何を知り、何ができるべきかを定義し、それをどう測るかを決めます。登壇者は、測定の話だけで長い時間が取れるが、この回は 25 分なので簡単に触れる、と述べています。出発点と到達点の両方を知る必要があります。

**現状を知る：Copilot adoption maturity dashboard**

GitHub Copilot では、今年の夏に、Copilot adoption maturity framework を測るエンタープライズ向けダッシュボードを公開しました。ユーザーを、Copilot の使い方に基づいて 4 つのコホートに分けて見せるものです（スライドの数字は説明用で、実数ではないと断っています）。Copilot のテレメトリを使い、ユーザーが GitHub Copilot とどう関わっているかで分類します。研修・イネーブルメントの観点では、「人々がどこにいるか」が分かる点が大きな利点だと説明しています。

顧客の例では、登壇者は、多くのユーザーが第 3 フェーズ（顧客が求めていたエージェント型ワークフローに当たる段階）にいると言いたかったものの、実際は大半が「chat first」の第 1 フェーズにいて、その割合は 65〜75% だったと述べています。つまり、購入したライセンスの価値を十分に引き出せていません。第 1 フェーズで満足して成果を出しているなら問題はありませんが、多くの場合はもっとできることがあり、少なくとも「agent first」の環境へ移したい、という考えです。

もう 1 つ最近公開された機能として、**業界比較（industry comparisons）**があります。オプトインすると、同規模・同種の業界のベンチマークデータと比較して、自社の位置付けを知ることができます。

**能力を定義する：GitHub Copilot Pro バッジ**

登壇者は、「GitHub Copilot Pro バッジ」を紹介しています（知らない人に会場で挙手を求め、GitHub Learn のブースへ来るよう案内しました）。同種のものとしては初めてで、個人が所有する能力の証明（capability statement）であり、個人が所有する指標だと説明しています。たとえとして挙げられたのは、「クレジットスコアのようなもの。共有したくなければ共有しなくてよい」です。

学習・イネーブルメントの担当者にとって利点なのは、各レベルに「GitHub Copilot で何を知り、何ができるべきか」を示す能力のステートメント（capability statements）があることです。100・200・300 や初級・中級・上級といった呼び方は、人によって定義が違い、何を指すのか分かりにくいものでした。バッジのレベルは、組織の基準に合わせて「これは当社では初級のタスク」「これはもう少し上級」と調整してよく、出発点になる枠組みを提供します。公開済みのレベルは 3 つで、近く合計 5 つになる予定です。

GitHub Copilot を使っていない場合は、「jobs to be done（その役割が実行すると期待されるタスクは何か）」のような考え方で能力を定義できます。登壇者は、ペルソナやロールも非常に重要で、人は一律ではなく、全員を同じ研修パスに入れて同じ結果を期待することはできないと強調しています。

**成功をどう測るか**

成功を測るには、データを使う必要があります。登壇者は、測れるものは多くあるとして、いくつかの例を挙げています。

| 指標の例 | 登壇者の説明 |
| --- | --- |
| 製品テレメトリ | ツールによっては最も簡単な指標の 1 つ。重要で役に立つが、それがすべてではない。使っていることは出発点にすぎず、いずれは「使っている」から「十分に使いこなしている」へ進む必要がある |
| 生産性 | 皆が測りたがるが、「導入前はどう測っていましたか」と聞くと沈黙になることが多い。導入前後の比較が難しくなる。生産性は最大手企業から小規模事業まで誰もが苦労しており、定義が難しく、役割や組織によっても変わる。それでも、指標を整理する方法を見つけることを勧める |
| サポート依頼 | 生産性と関連する。サポートチケットや質問が減れば、ワークフローでつまずく人が減り、生産性が上がる |

登壇者は、これは網羅的なリストではなく、考える材料にすぎないと断っています。

あわせて、**習慣化にかかる時間**にも触れています。スライドでは 21 日と示されていました。何度も繰り返す必要があるため、1 回のウェビナーや 8 時間のハッカソンで利用率が 100% に跳ね上がっても、その後は必ず下がる、という説明です。急落することもあれば穏やかに下がることもあります。1 回の施策ですべてが解決することはなく、繰り返し、期間を分けて行う必要があります。また、施策の結果が見えるまでにも時間がかかるため、見る期間が短いか長いかでデータが示す内容は変わります。登壇者は、これをリーダーに理解してもらう必要があったと述べています。

> 注意：登壇者は、測定の議論は最初に済ませるべきだとしています。ある施策の最後に「成功したかどうか、どう測るか」と聞くと、顧客が「研修を作ってくれればいいと言った」と答えることがある。6 か月前に測定の話をしたはずだが、頼まれたとおりに作った、という自身の経験を紹介しています。

測定を考え込みすぎず、**小さく始める**ことを勧めています。自分でコントロールできる指標を、いくつか選んで始め、時間をかけて調整します。

### 5.4 顧客のその後（ディスカバリー）

ここで顧客の話に戻ります。登壇者は顧客とディスカバリーのセッションを行い、計画を提示して、実際の adoption maturity dashboard の指標を見せました。顧客は「それは知らなかった。確かにほかのユーザー層にも対応が必要だ」と反応したそうです。

なぜ認定を求めたのかを聞くと、顧客は「開発者にエージェント型ワークフローを使わせたいから」と答えました。登壇者は、認定だけでそこに到達するのは難しいと考え、本当にやりたいことを一緒に整理するため、追加のディスカバリーを行ったと述べています。認定そのものに問題はなく、価値はありますが、唯一のレバーではありません。定着には、研修とイネーブルメントのマルチモーダル（複数手段）なアプローチが必要だと説明しています。

### 5.5 章 3：定着させる（Make it stick）

ゴールは、ローンチから持続的な活用へ移ることです。登壇者が使う 4 つのレバーは、次のとおりです（この 4 つのうち、どの組み合わせもありうると述べています）。

| レバー | 位置づけ |
| --- | --- |
| トレーニング | 自分のチームの仕事であり、このセッションがスキリング分野でもあるため最初に挙げた |
| コミュニケーション | 「なぜこれを、なぜ今やるのか」を伝える |
| コミュニティとチャンピオン | 仲間同士で学び合う場と、その担い手 |
| 運用（オペレーション） | 仕組みやプロセスが行動を支えているか |

#### 5.5.1 トレーニング：「コンテンツの山」ではなく「道筋」を作る

標語は「Build a pathway, not a content pile（道筋を作る。コンテンツの山にしない）」です。多ければよいわけではなく、たいていは少ないほうがよく、複数の手段を組み合わせることが鍵だと述べています。紹介された推奨リソースは、GitHub Learn のリソースと、AI Skills Navigator です（GitHub のモジュールの多くは AI Skills Navigator でも共有されています）。

登壇者は、トレーニングを次の流れで構成します。

1. **学ぶ（learn）**：まず知識を得る。なぜか、どう動くか、何をしてよく、何をしてはいけないか
2. **練習する（practice）**：安全な環境で練習する。GitHub には、無料で一般公開されたハンズオン演習があり、「GitHub を GitHub で学ぶ」というタグラインを使っている。GitHub Copilot 関連のリソースも多数ある
3. **検証する（validate）**：GitHub Copilot Pro バッジのほか、認定（製品知識の検証）や、他のハンズオンラボ・スキリングでも検証できる
4. **設計・調整する（architect）**：リンクを大量に投げるのではなく、調整され、間隔を空け、なぜこの研修を受けるのかという文脈を伝える。登壇者は「orchestrate」とも迷ったが、この語に落ち着いたと述べています

実践例として、AI Skills Navigator でプレイリストを作り、顧客に「1 つのリンクですべてを」渡した話があります。第 1 週、第 1 コホートのトレーニングパス、ペルソナ別のパスなどを、学ぶ・練習する・検証するの順で、時間とともに複雑さが上がるように意図的に並べました。さらに、GitHub Copilot アプリでもパスを作り、マイクロサイトやランディングページも作成しました。大事なのは、利用者が関連性を理解し、意図された順番で進められることです。

#### 5.5.2 コミュニケーション

「なぜこれをやるのか」「なぜ今か」を伝えることが重要です。「そう決まったから」「最新機能だから」という返事は意外に多いが、人は理由を知りたがる、特に移行や行動の変更を求める場合はなおさら、と述べています。登壇者の見解では、このレバーは十分に使われていません。

実際の仕事に結び付けて伝えます。登壇者は、GitHub Copilot アプリと一連のカスタムインストラクションを使ってキャンペーン計画を作りました。学習パスやランディングページへ人を戻し、理由を説明し、懸念に答え、やり方を示す、ドリップキャンペーンのような形です。「3 週間でこの学習パスを終えてください」と言って放置するのではなく、21 日の習慣化に合わせて働きかけを続けるためです。仕事があるので忘れてしまうのが普通です。

新しいチャネルを作らず、すでに使っている Teams や SharePoint ページなど、**既存のコミュニケーション手段**にナッジ（促し）を載せることを勧めています。新しい仕組みは障壁になるためです。

#### 5.5.3 コミュニティとチャンピオン

ピア・ツー・ピアの学びは最良の方法の 1 つで、人は似た立場の人から学ぶのを好みます。登壇者は、GitHub は顧客の成功を支援するが、組織の細かな事情を知っているのは顧客だけだと述べ、ベストプラクティスや、つまずいた箇所を共有し合う場があるかを問います。

- **GitHub Discussions** を使う方法が紹介されています。投稿への賛成票（upvote）や回答ができ、議論をさまざまな形で整理できます。
- GitHub の community チーム（Success and Scale のチーム）には、「community in a box」と呼ばれるセットがあり、始めるのに役立ちます（このリソースは発表の最後に共有されるリンク集に含まれると述べています）。
- 他のプラットフォームや形式でも構いません。重要なのは、人々が直接コミュニケーションできる場を作ることです。

通常、これは**チャンピオン**として位置づけます。チャンピオンは非常に重要で、選び方、研修の仕方など考える点が多くあります。一般ユーザーとは違うレベルの研修が必要で、組織・地域・役割をまたいで配置するのが重要です。また、コミュニティの運営の多くをチャンピオンに任せることを勧めています。そうして、community of practice や center of excellence（呼び方は何でもよい）を作ります。

> 注意：チャンピオンは最初は意欲的でも、「こんなに大変だと思わなかった」となることがあります。期待役割を明確にしてください。人材管理（タレントマネジメント）と結び付け、チャンピオンになることで何が得られるか、どう報いるか、成長や役割の支援になるか、そして**終了時期があるか**を決めます。登壇者は、結婚契約なのか、賃貸契約なのかと冗談を交えつつ、「1 年」または「6 か月」といった任期を決めておくことを強く勧めています。

#### 5.5.4 運用（オペレーション）

運用のレバーでは、プロセスが行動を支えているかを問います。登壇者は冗談として「ライセンスの申請が 17 ステップある」という例を挙げ、しかし実際にあったことだと述べています。人々を難しくしていないか、容易にしているか。ツール・設定・プラットフォームを使える状態にしているか。製品をどう使うことが期待されているか、ルールやガバナンスは何か、そして、それをどう保つか、という点を明確にします。運用は最後に置いたが、全体にとって極めて重要だと述べています。スライドの下部には「sustainable adoption needs structure, not just launch energy（持続的な採用には、ローンチの勢いだけでなく構造が必要）」と書かれていました。

#### 5.5.5 エビデンス（成果の検証）

最初に決めた測定内容と時期に沿って、施策の終わりに、成功したかを見ます。人が居心地よく感じる期間より長くなることもあり、「1 か月で効果が出たかは言えない」と述べています。そのうえでエビデンスを見て、調整します。最初から完璧にはならないが、学び、育て、反復し、進化させることが重要だという趣旨です。

### 5.6 リソースのランディングページ

最後に、QR コードで案内されたページが紹介されました。これは登壇者自身が GitHub Copilot アプリで作ったランディングページで、発表中に触れたリソースへのリンクをまとめたものです。登壇者は「自分は開発者ではない」と述べ、GitHub Copilot アプリを使えば自分でもものを作れる、とも語っています。

## 7. 注意点・発表者の気付き

- **研修の修了数を追うだけにしない。** 目的は成果と行動の変化。ただし、規制業界などで追跡の要件がありうることには触れている。
- **測定の方法は、施策の最初に決める。** 施策の終わりに測定方法を聞いても、最初に決めていなければ困る。
- **使っていること＝使いこなしていること、ではない。** 製品テレメトリは出発点で、それだけでは足りない。
- **生産性は導入前の測り方がないと、導入前後の比較が難しくなる。**
- **1 回のイベントでは定着しない。** 21 日の習慣化、繰り返し、時間を空けた実施が必要。結果が出るまでの期間も長めに取る。
- **リンクの山を渡さない。** 学ぶ・練習する・検証する順に、間隔を空けて設計する。
- **新しいコミュニケーション手段を作らない。** 既存のチャネルを使う。
- **チャンピオンには期待役割と任期を伝える。**
- **運用（ライセンス申請など）が行動の妨げになっていないか確認する。**
- **最初から完璧にはならない。** 結果を見て調整する。

## 8. 利用者にとっての利点

発表で語られたのは、効果の数値ではなく、顧客が得られる気付きと使える手段です。

- adoption maturity dashboard により、ユーザーが Copilot をどの段階で使っているかが分かる。事例の顧客では、65〜75% が chat first の第 1 フェーズにおり、ライセンスの価値を十分に引き出せていないと分かった。
- 業界比較で、同規模・同種の組織と自社の位置を比較できる（オプトイン）。
- Copilot Pro バッジの能力ステートメントを、社内のレベル定義の出発点として使える。
- 無料で公開されている GitHub のハンズオン演習や、AI Skills Navigator のプレイリストを学習パスに使える。
- GitHub Discussions と community in a box を使い、コミュニティを立ち上げられる。

## 9. まとめ

アクセスは活用と同じではない、というのがこの発表の軸です。200 人の GH600 認定という依頼に対し、登壇者は「なぜ」を確認し、adoption maturity dashboard で現状を見せ、真の目的がエージェント型ワークフローの活用であることを引き出しました。

進め方は、依頼を紐解き、能力と測定方法を定め、トレーニング・コミュニケーション・コミュニティ（チャンピオン）・運用の 4 つのレバーで定着させ、最後にエビデンスで検証して調整する、というものです。トレーニングは大事ですが、唯一のレバーではありません。小さく始めて、測って、繰り返すことが勧められました。
