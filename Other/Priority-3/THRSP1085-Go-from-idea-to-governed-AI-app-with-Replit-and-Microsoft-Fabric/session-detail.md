## 1. はじめに

このセッションは、**Replit** で自然言語から **Microsoft Fabric 上で動くアプリケーション** を作り、そのまま Fabric に公開する流れを、約 19 分のライブデモで見せる発表です。想定する作り手は、ソフトウェアエンジニアではなく、業務の課題に最も近い「ドメインエキスパート」です。

## 5. 発表内容の詳細

### 5.1 Replit とは

Pablo 氏は、まず会場に Replit を使ったことがあるかを尋ね、多くの人が経験者であることを確認しました。Replit は、AI を使ったソフトウェア作成のプラットフォームで、ミッションは「次の 10 億人のソフトウェア作成者」を支えることです。ゼロからソフトウェアを作る複雑さを抽象化し、今回のような会話と同じくらい簡単な体験にする、と説明しています。

エンタープライズでは、コードの生成だけでは足りません。システムへの接続、アプリの実行、デプロイ、組織のセキュリティ要件の下での管理が必要で、Replit はこれらを一体で提供します。

- エンタープライズ向けのセキュリティ
- ガバナンスの制御
- 500 を超える連携先へのワンクリックの接続
- 組み込みのインフラとデプロイ

### 5.2 シナリオと前提

今回作るのは **Fabric のアプリケーション** で、作成の層として Replit を使います。登壇者は「店舗の業績を複数の地域で見ている販売リーダー」になりきって説明しました。

- 売上データはすでに Fabric にある。
- すべての店舗の売上をまとめた semantic model がすでにある。
- このデータを誰が見られるかは、Azure と Fabric のガバナンスで定義済み。
- そのため、この上に Fabric アプリを誰が作れるかは、Microsoft 側の権限による。

### 5.3 作成の始め方：Microsoft Fabric app template

semantic model を使ったダッシュボードは、semantic model の URL を取得し、Replit で **Microsoft Fabric app template** を選ぶだけで作り始められる、と説明しています。このテンプレートは登壇者が「月曜日の時点でリリースした」と述べたもので、**エンタープライズプランであれば利用できます**。内部では Rafin CLI を使って Fabric にデプロイします。

あとは、ほしいソフトウェアを説明するだけです。デモでは semantic model の URL を貼り付け、必要な機能を細かく列挙することもできるが、今回は一度で作れるかを見るために大づかみにして、「store sales を追跡するダッシュボードを作って」と入力しました。

### 5.4 裏側の仕組み

Replit エージェントが依頼を受けて構築を始める間に、登壇者はスライドで仕組みを説明しました。

- テンプレートは、プロジェクトが特定のバックエンドを使うように構成する（音声では「Raven backend」と聞こえ、表記は確定できません。中身は発表では説明されていません）。設定とデプロイのための **skills** も含まれる。
- **一度だけ必要な設定** を、Replit の管理者が行う。Fabric コネクターで、Azure のアプリ登録（app registration）を使う。Azure 上でアプリ登録を作り、クライアントシークレットを作成して、その情報で Replit の連携を設定する。
- Replit のワークスペースの integrations には 500 を超える連携先が並ぶ。「Your Integrations」タブで「Fabric」と入力すると、今回の連携が見える。ここでクライアントとシークレット、スコープ、**アプリの実行時にコンピュートを提供する Fabric の capacity ID**、テナント ID を設定する。
- Rafin CLI が Fabric 上にワークスペースを作成（プロビジョニング）し、設定にある capacity を割り当てる。
- Fabric コネクター経由で、semantic model とその配下のデータソースからデータを読み、スキーマを理解してクエリを生成する（音声では「tax queries」と聞こえ、音声認識の都合で表記が確定できません）。そのため、ゼロから始めたり、データ構造を手作業で説明したりする必要がない。

### 5.5 権限と共同作業

構築する人には、semantic model に対する **少なくとも view と build のアクセス**、または Fabric ワークスペースの **contributor** の権限が必要です。どちらが必要かは、Fabric のガバナンスをどう管理しているかによって変わる、と述べています。

作業は共有ワークスペースで行うので、Replit プロジェクトにチームメンバーを招き、会話で改善を続けられます。招待は、Entra ID から割り当てられたグループを追加するか、メールアドレスで個別のユーザーを追加して行います。

構築には 7〜8 分ほどかかるため、時間の都合で、同じプロンプトで先に作っておいた別のタブに切り替えてデモを続けました。

### 5.6 成果物：静的な React アプリケーション

Fabric アプリケーションの成果物は **静的な React アプリケーション** で、Fabric 上へ直接公開します（公開の処理は抽象化されています）。プロジェクトを Fabric に載せるには、publish ボタンを押して、もう一度押すだけです。

デモの時点では、ダッシュボードに、店舗の詳細ページがあり、ダークモードもありました。この後、変更を加える流れになります（6 章）。

### 5.7 読み取り専用の設計と、SQL データベースによる書き込み

登壇者は、設計上、**semantic model からはデータを読むだけで、書き戻せない** と説明しています。例えば、総売上や成長率を勝手に変更できてはいけません。それは Fabric で管理されるデータで、店舗の業績の「正」は Fabric だからです。そのため、Replit でアプリを作るドメインエキスパートは、元のデータソースには書き込めません。

一方で、状態を保持する必要があるユースケースでは、Rafin CLI を使って **プロジェクトスコープの SQL データベース** を立ち上げ、アプリがデプロイされるのと同じ Fabric ワークスペースにデプロイできます。これでフルの CRUD 操作をユースケースに応じて扱えます。店舗のメモはその一例で、他のエンティティの CRUD にも応用できます。

この SQL データベースを使うと、フルスタックアプリケーションも作れます。semantic model から読む必要がないアプリを、100% Replit で作って Fabric にデプロイする、というパターンです。

この連携が対応するのは、次の 3 種類のユースケースです。

| 種類 | 内容 |
| --- | --- |
| 読み取り専用 | semantic model のデータを読んで表示する（ダッシュボードなど） |
| フルスタック | プロジェクトスコープの SQL データベースを使い、semantic model が不要なアプリを丸ごと作る |
| ハイブリッド | semantic model から読みつつ、プロジェクトスコープの SQL データベースにも書き込む（デモで扱ったもの） |

### 5.8 デプロイ後の構成：Fabric が本番の正

ワンクリックのデプロイで、アプリは Microsoft の環境内で動きます。成果物の静的な React アプリは、React hooks で semantic model にクエリを送り、そのクエリは semantic model 側で実行されます。本番でのコンピュートは、Replit の連携に設定した **Fabric の capacity** を使います。

- エンドユーザーは Replit に行く必要がなく、Fabric に直接アクセスする。
- 見られるアプリは、Azure のどのグループに属しているかに基づいて、アクセスを与えられたものになる。
- デプロイ後は Fabric が本番環境の source of truth で、Replit は開発用。作るのは Replit だが、動かすのはすべて Fabric 側。
- デプロイされるサービスの 1 つが Fabric 内の SQL データベースで、**SQL analytics endpoint** も得られ、そのデータは OneLake に入る。アプリがプロジェクトスコープのデータベースに書き込む内容はすべて可視化される。

登壇者は、「Replit でアプリを作って改善し、ユーザーは Fabric で直接実行する。コンピュートは capacity から来る」という形で、両者が組み合わさると要約しています。

### 5.9 最初のユースケースの選び方と協業の意味

最初のユースケースについての助言は次のとおりです。

1. ビジネス上の問いと、既存の semantic model を選ぶ。
2. すでにある semantic model の上にアプリを作ることから始める。
3. semantic model の上で構築できる権限を得られるよう、チームとアクセスを調整する。
4. ドメインの専門知識を活かして、焦点の絞られた、読み取りが中心のアプリを作る（音声では「focus ready heavy」と聞こえ、表記が確定できません）。
5. 必要になった時点で SQL データベースを追加し、プロジェクトスコープのデータに対する書き込み（フルの CRUD）をサポートする。
6. Fabric アプリの作成に慣れたら、Fabric に直接デプロイするフルスタックアプリを作る。

Microsoft との協業の価値は、Copilot が技術チームに CLI を使ったアプリの構築とデプロイを可能にする一方で、Replit が技術者ではないチーム、つまりドメインエキスパートに、自然言語で同じ結果を可能にする点だと述べています。開発環境では、アプリの一部のスクリーンショットも使い、チームメイトと会話するように反復できます。

### 5.10 ガバナンスの尊重

もう 1 つ強調されたのが、**Fabric のガバナンスを尊重している** ことです。デモでは Fabric にサインインするポップアップが出ていました。別のビルダーをこのユースケースの共同作業に招いた場合も、その人に view と build の権限が必要です。権限がなければ、UI に、データの表示または構築に対して「unauthorized（権限なし）」というエラーが出ます。

### 5.11 公開時のセキュリティチェックとビルド

公開時の流れとセキュリティチェックについて、登壇者は次のように説明しました。

- Fabric 側ではすでにいくつかの資産がプロビジョニングされている（ワークスペース、アプリアイテム）。新機能を追加した際には Microsoft SQL データベースも立ち上げており、そのデータベースを Fabric ワークスペースのアイテムとして作成している。
- **セキュリティチェック** を実行する。ドメインエキスパートが作るユースケースなので、フロントエンドに認証情報が誤って入っていないかを確認する。平文のパスワードを調べる。
- 依存関係（React と一緒に使うライブラリ）に脆弱性がないかも確認する。
- ワークスペースの設定で、一定の脆弱性があるときに **公開をブロック** できる。例えば critical や high があれば公開をブロックする設定にでき、必要に応じて medium や low まで対象にできる。
- 脆弱性が見つかって公開がブロックされると、ユーザーに通知し、管理者にも知らせる。ユーザーはエージェントで修正できる。平文のパスワードの削除や、ライブラリのアップグレードはエージェントが簡単にできる、と述べています。
- セキュリティチェックを通過すると、ビルドを実行する。ビルドには、アプリをデプロイする CLI コマンド（音声では「rayfin up」と聞こえ、表記は確定できません）を使う。

### 5.12 Fabric 上のワークスペースとその他の機能

公開後の Fabric のワークスペースについて、次の点が示されました。

- 作成されたワークスペースに、アプリアイテムと、機能に対応した SQL データベースがある。
- 新しい CLI の機能として **functions** が加わり、Fabric の外にある外部サービスへのリクエストを送りたい場合や、何らかの処理を起動したい場合に使える（「trigger some notes」と聞こえ、後半は音声認識の都合で確定できません）。
- アクセスは Fabric の中で管理される。ワークスペースへのアクセスをチームメイトに付与でき、Fabric なので Entra ID のグループを使って、チーム全体や特定のメンバーに権限を渡せる。

## 6. デモ・手順

このセッションでは、Replit の画面を使ったライブデモが行われています。画面の細部（ボタンの位置、デザイン）は、語られた範囲しか確認できません。デモは語られた順に、次のように進みました。

### 6.1 アプリの作成

1. Replit で、semantic model の URL を取得して持ち込み、**Microsoft Fabric app template** を選ぶ。
2. semantic model の URL を貼り付け、「store sales を追跡するダッシュボードを作って」というプロンプトを入力する（機能の一覧を細かく書くこともできるが、今回は大づかみにした）。
3. Replit エージェントが構築を始め、内部では Rafin CLI を使う。
4. 構築の待ち時間のあいだ、登壇者はスライドに戻って仕組みを説明し、続いて Replit ワークスペースの integrations 画面に移り、Fabric の連携の設定項目（クライアントとシークレット、スコープ、capacity ID、テナント ID）を見せた。
5. プロジェクトの画面に戻り、チームメイトを（Entra ID のグループ、またはメールで）招待できることを説明した。
6. 構築に 7〜8 分かかるため、同じプロンプトで構築が済んでいる別のタブに切り替えた。

### 6.2 完成したアプリの確認と変更

1. 出力された Fabric アプリケーション（静的な React アプリ）を確認した。ダッシュボードと、店舗の詳細ページがあり、ダークモードもある。
2. 別ページの追加を考えたが、既存の show page に足すことにして、「各店舗にメモを残せるようにして。プロジェクト内の SQL データベースを使って」とエージェントに依頼する（登壇者の依頼文は「add a way to leave notes on each store using the SQL database in this project」）。
3. エージェントから、SQL データベースを有効にする確認が来る。**continue** を押すと、エージェントがそのエンティティのデータベースの設計（スキーマ）を作り始める。
4. 構築が終わるまで、デプロイの仕組み（5.8）を説明した。

### 6.3 公開

1. 構築が完全に終わるまで待ってから公開することを説明した（コードがまだ書かれている最中のため）。
2. 別のタブで先に作っておいたダッシュボードで、メモ機能の追加が完了しているのを確認した。店舗の一覧から 1 つの店舗に入ると、各店舗にメモを追加できる。例として「follow up with the store manager by end of day」というメモを入力した。
3. 画面右上の **publish** ボタンを押し、もう一度 publish を押す。進捗を開いて、裏側で起きていることを説明した（5.11 の内容）。ワークスペースとアプリアイテムは作成済みで、新機能のために Microsoft SQL データベースを追加で立ち上げた。
4. セキュリティチェック（平文のパスワード、依存関係の脆弱性）を経て、ビルドが実行された。
5. ページを更新すると、公開された URL が表示された。これは **Fabric の URL** で、Fabric に直接公開されたアプリが見られた。
6. 作成されたワークスペースを開き、アプリアイテム、SQL データベース、functions を確認した（5.12）。アクセスは Fabric で管理され、ここからチームメイトにワークスペースへのアクセスを付与できる。

## 7. 注意点・発表者の気付き

- 一度だけ、Replit の管理者によるセットアップが必要です。Azure でアプリ登録を作り、クライアントシークレットを発行し、Replit の Fabric 連携に設定します。
- 構築する人に必要な権限は、semantic model への view と build、または Fabric ワークスペースの contributor です。権限がなければエラー（unauthorized）になります。
- semantic model のデータは、設計上、読み取りだけです。総売上などの Fabric で管理するデータを、Replit のアプリから書き換えることはできません。書き込みが必要なら、プロジェクトスコープの SQL データベースを使います。
- Microsoft Fabric app template はエンタープライズプランで使え、登壇者の説明では「月曜日の時点でリリースした」ものです。
- 公開前に、フロントエンドへの認証情報の混入（平文のパスワード）と、依存ライブラリの脆弱性がチェックされます。しきい値（critical、high、medium、low）に応じて、公開をブロックする設定にできます。
- 構築が完了する前に公開しないよう、登壇者は完了を待ちました。
- 発表では、料金、対応する地域、アプリの規模の上限など、ここで書いた以外の制約には触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **技術者でなくてもアプリを作れる**：ドメインエキスパートが、自然言語だけで Fabric のアプリを作れる。エンジニアリングのリソースを使わずに、エンタープライズ品質のソフトウェアにできる、という説明。
- **既存の semantic model をそのまま活用できる**：スキーマの理解とクエリの生成をエージェントが行うので、データ構造を手作業で説明しなくてよい。
- **ガバナンスの一貫性**：データのアクセス、アプリの閲覧権限が、Azure と Fabric の既存の権限（Entra ID のグループなど）で管理される。エンドユーザーは Fabric で直接アクセスする。
- **公開前のセキュリティチェック**：平文のパスワードや脆弱な依存ライブラリを検出し、設定に応じて公開をブロックでき、エージェントが修正できる。
- **データの保護**：総売上などの Fabric の正のデータは、アプリから書き換えられない。
- **公開は publish ボタンを 2 回押すだけ**：アプリが Fabric の URL に公開され、SQL データベースも Fabric のワークスペース内のアイテムとして用意される。

導入効果を示す数値（工数の削減など）は、発表では語られていません。

## 9. まとめ

このセッションは、Replit を作成の層、Fabric を実行と統制の層とすることで、ドメインエキスパートが自然言語で Fabric アプリを作り、ガバナンスを保ったまま公開できる、という流れを見せました。デモでは、semantic model の URL から店舗売上のダッシュボードを作り、プロジェクトスコープの SQL データベースで店舗メモの機能を足し、セキュリティチェックを経て Fabric の URL に公開しました。

最初のユースケースとしては、既存の semantic model の上で、権限をチームと調整したうえで、読み取りが中心のアプリから始めることが勧められています。書き込みが必要になれば SQL データベースを足し、慣れてきたらフルスタックのアプリへ進める、という段階的な進め方です。
