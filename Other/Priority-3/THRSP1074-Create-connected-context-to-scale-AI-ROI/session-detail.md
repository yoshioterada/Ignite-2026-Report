# THRSP1074 Create connected context to scale AI ROI

## 1. はじめに

このセッションは、Atlassian の AI エージェントと、その土台になっている **Teamwork Graph** を題材に、「個人の生産性向上にとどまっている AI の効果を、チーム全体・組織全体の ROI にどうつなげるか」を扱う短い登壇です。

発表の中心にある主張は、**エージェントに共有コンテキスト（context graph）を持たせ、チームが実際に働いているツールの中でエージェントを動かす**ことです。Atlassian の登壇者がこの考え方と Teamwork Graph の構成を説明し、続いて、独立系レストランを顧客に持つ Spot On の Ryan 氏が、本番で動かしている Rovo の活用事例（開発ワークフロー、PRD 作成、営業サポート）を数値付きで紹介します。途中で Atlassian の登壇者が補足を挟み、最後にガバナンスと行動の呼びかけで締めます。

このセッションを読むと、Teamwork Graph がどんなデータをつなぐのか、Spot On が開発ワークフローをどう自動化して日数を短縮したのか、そしてセキュリティ・ガバナンスの面で Atlassian がどんな管理機能を用意しているのかが分かります。

## 5. 発表内容の詳細

### 5.1 Teamwork Graph：6 つのコンテキストをつなぐ

Atlassian が投資してきた共有コンテキストが **Teamwork Graph** です。6 つの異なるコンテキストのデータをつなぐ context graph で、次のものが挙げられました。

| コンテキスト | 内容（発表での説明） |
| --- | --- |
| Knowledge | スプレッドシート、ドキュメント、プレゼンテーションなどの仕事のデータ。何を作っているか、仕事の状況、ゴール、作業中に下された決定 |
| People | 作業をしている人、誰が誰と、何に取り組んでいるか |
| Communications | Microsoft Teams や Zoom の会議、Slack を使っている場合はそこでの発言 |
| Code | デプロイされたコードやリポジトリ。なぜその仕事が行われているのか、周辺のコミュニケーションと関連づけられる |
| Assets | CMDB（構成管理データベース）にあるデータ |

> 補足：登壇者は「6 つの異なるコンテキスト」と述べていますが、音声から区別して聞き取れた名称は上の 5 つ（knowledge、people、communications、code、assets）です。Knowledge の説明の中で、ドキュメントなどのデータに続けて「何を作っているか、仕事の状況、ゴール、決定」と語られているため、この部分が別のコンテキストとして数えられている可能性もありますが、発表では明示されていません。

コンテキストをつなぐ意義として、登壇者は 2 つの例を挙げています。

1. インシデントが報告されたとき、根本原因を探すエージェントが、組織で何が変わったか（デプロイされたコード、作業していた人、インシデントに至るまでのコミュニケーションなど）を把握している。
2. エージェントでコードを書くときに、なぜその仕事をしているのか、ゴール、誰と一緒に取り組んでいるのかを把握している。

### 5.2 コネクタと独自データ、そして効果

Teamwork Graph には、すぐ使えるコネクタが **80 以上** あります。Atlassian 製品のデータだけでなく、サードパーティの SaaS アプリケーションのデータも対象です。さらに、Atlassian が公開している API を通じて、自社独自のシステムにある独自データを取り込み、グラフを拡充することもできます。

効果として、共有コンテキスト（共有グラフ）をエージェントに与えた顧客では、**エージェントの性能が最大 44% 向上**し、トークンの消費にも節約効果が出ているとのことです。

### 5.3 Rovo と、他のエージェントからの利用

Teamwork Graph は、Atlassian の AI エージェント **Rovo** から使えます。Rovo は Teamwork Graph を土台にしており、さらに、仕事ごとに最適なモデルを選ぶ AI ゲートウェイを備えています。Atlassian の製品群に組み込まれているため、Jira Service Management を使っていれば Teamwork Graph がそこにあり、Jira、Confluence、Loom など他の製品でも同様です。

Teamwork Graph は Rovo の中に閉じず、**MCP または CLI を通じて**、ChatGPT、Copilot などの他のエージェントにも提供されます。登壇者は「コンテキスト自体は仕事をしない。チームやエージェントがコンテキストを使って働く必要があり、チームが共同作業するツールの中に置く必要がある」と述べて、次の事例へ進みます。

### 5.4 Spot On の紹介

Ryan 氏は、Spot On の使命を「独立系レストランの顧客がより強く、より収益性の高いビジネスを築けるよう支援すること」と説明します。散らばった雑多なデータを実行可能なインサイトに変え、無駄を減らして顧客に集中できるようにするというものです。AI にも同じ視点を求めており、無駄を省き、従業員がより高次の成果にすばやく到達できる手段を探している、とのことです。ここが Rovo と Atlassian の話につながるという位置づけです。

### 5.5 事例 1：開発ワークフローの自動化

最初の事例は、Ryan 氏が「messy middle（雑多な中間）」と呼ぶ開発ワークフローです。IT 組織内で Ryan 氏に報告する Salesforce エンジニアリングチームには、項目やドロップダウンの追加など、ビジネスを回すための「run the business」型の作業が多くあります。こうした作業は積み重なり、開発者や管理者が戦略的な大きな仕事に集中する妨げになっていました。

Atlassian を使って、この自動化にガイドラインとガードレールを加えました。スライドに示された流れは次のとおりです。

1. ビジネスシステムのプロダクトチームが、自動開発（auto development）の条件を満たすチケットを探す。
2. 開発チームのワークフローに移り、Rovo がプロンプトを生成する。このプロンプトが、以降の工程にコンテキストを引き継ぐ。
3. そのプロンプトで、依頼に関連するコードを調べ、開発用のサブタスクを作成する。サブタスクは Jira チケットの中に作られる（スライド右下に表示）。
4. Jira のコーディングエージェントがその作業を引き取り、ブランチを作成して開発サイクルを進める。
5. 結果はプルリクエストとして開発者に届き、開発者がレビューして先に進めるか判断する。調整が必要な場合もある。

Ryan 氏は、これは **human in the loop（人が判断に入る）** のプロセスであり、いきなり本番に出るわけではないと強調しています。

成果は次のとおりです。

| 指標 | 導入前 | 導入後 |
| --- | --- | --- |
| 同程度の規模のチケットの所要時間 | 約 38 日 | 4 日 |
| 1 週間以内に納品できたチケットの割合 | 約 12% | 70% |

さらに、短縮した時間を合計すると **1,200 日を超える納品時間**になる、と Ryan 氏は述べています。（その直後に「something that is like 90 days old」とも話していますが、何を指すかは音声からは確定できません。）管理者と開発者の時間を大きな案件に振り向けられることと、ビジネスへの価値をとても速く届けられること（time to value）の 2 点が重要だと話しています。

### 5.6 「Left of code / Right of code」

Atlassian の登壇者は、自社のツール群でソフトウェア開発ライフサイクルを回している顧客では、コーディングはほぼエージェントに任されていて、ほとんど解決済みの問題だと述べています。ただし、エンジニアが多くの時間を使うのはコードの前後です。これを **left of code / right of code**（発話では "lift of code" とも聞こえます）と呼んでいます。具体的には、ブレインストーミングや計画、会議、コードのテスト、プルリクエストのレビューといった作業です。

コーディングの実行時間は小さくなっているため、ソフトウェア開発ライフサイクルを設計する人は、エージェントがコーディングを担うほど、この前後の工程に焦点を当ててほしい、というのがこの登壇者の勧めです。

### 5.7 事例 2：要件の評価と PRD の作成

Ryan 氏は、ビジネスシステムでの計画段階にも Rovo を取り入れたと説明します。

まず、仕事の依頼を受け取ると、複数の基準で採点するエージェントが動きます。依頼が取りかかれる程度に具体化されているか、求める条件に合っているかを早期に把握するための、チームが頼れる分析担当のような役割です。Ryan 氏は、これが Rovo での最初の「aha moment」の 1 つだったと話しています。

アイデアが固まると、次は **PRD（製品要求仕様書）エージェント**が登場します。白紙から PRD を書き始めるのは大変ですが、このエージェントはチケットと関連するコンテキストをたどり、自動化を通じて PRD を書きます。テストの結果では、**ワンクリックで約 70% の完成度**に到達します。

Ryan 氏は、製品チームから聞いた話（定量的な計測ではない、と断っています）として、このプロセスは以前は数日かかっていたのが、今は数時間になったと述べています。PRD を作り込む担当者が細部に入る必要がなくなり、戦略や、サービスのポートフォリオ全体で何を届けるかに視点を上げられるようになったという効果です。

### 5.8 Rovo を働く場所に置く

Ryan 氏は、ここまでの自動化に加えて、開発トラック以外のワークフローにも Rovo を置く方法を見つけたと話します。Atlassian の登壇者はこれに合わせて、従業員が普段働いている場所で Rovo を使えるようにしたと説明します。Microsoft Teams に持ち込めるほか、Copilot と統合でき、ブラウザ拡張機能、デスクトップアプリ、モバイルアプリもあります。必要なときにすぐ使える場所に埋め込むことが要点です。

### 5.9 事例 3：営業サポートエージェント

Ryan 氏が紹介する 3 つ目は、約 1 年前の初期の実験から、いまでは営業チームの支援に欠かせないものになった営業サポートエージェントです。Spot On は営業主導の組織で、現場に多くの営業担当者がおり、製品とサービスについての質問を抱えています。そこで、質問するとリアルタイムで回答するエージェントを作りました。

| 指標 | 内容 |
| --- | --- |
| clean deflection rate（V1） | 約 40%（独自計測） |
| clean deflection rate（5 回の改善後） | 66% |
| 同期間の human interaction | 63% 増加 |

「clean deflection」とは、質問が 1 回、回答が 1 回で、追加のやり取りが不要だったケースを指すと Ryan 氏は説明しています。また、Rovo が他のチャネルや場所に人を向かわせるような答え方になっていないかも確認したかった、とのことです。最終的に、人へのエスカレーションは「例外であって通常ではない」状態になったと述べています。

> 注意：「human interaction が 63% 増加」という数値が何を指すのか、また人へのエスカレーションが減ったことと両立する理由は、発表では詳しく説明されていません。上の表は聞こえた数値をそのまま記載しています。

### 5.10 セキュリティとガバナンス

Atlassian の登壇者は、Atlassian プラットフォームには Fortune 500 の **85%** の企業が乗っているため、その AI の展開が安全であることを担保する必要があると述べます。そのために次の機能を用意したと説明しています。

- **エージェント ID**
- **エージェントのインベントリ**：Atlassian プラットフォームに持ち込まれる全エージェント。Rovo のエージェントでも、MCP・CLI・Copilot・ChatGPT・Claude などで接続したエージェントでも対象
- **監査ログ**：エージェントの Atlassian プラットフォーム上でのすべての活動を追跡できる

管理者は、気になる動きがあればエージェントを **無効化（deactivate）** し、そのエージェントが何なのか、誰が作ったのか、ユースケースは何か、ROI があるかを調べる時間を確保できます。

### 5.11 行動の呼びかけ

登壇者の呼びかけは次の 3 点です。

1. **context graph の構築に投資する。** AI 導入に乗数効果を与える鍵で、個人の生産性からチーム全体の生産性へ進める手段。
2. **ワークフローのボトルネックを特定する。** SDLC は代表例で、サポートやカスタマーサクセスのワークフローも挙げられました。
3. **従業員が働く場所にエージェントを埋め込む。** Jira、Confluence、Microsoft Teams、Outlook など（発話では「Glue」とも聞こえますが、音声認識の都合で確定できません）で、エンジニアや従業員を普段のワークフローから外に出さずにエージェントが働くようにする。

最後に、ブースへの来場と、QR コードから Atlassian が社内で AI をどう活用してソフトウェア開発ライフサイクルを変えているかをまとめた PDF をダウンロードできることが案内されています。

## 7. 注意点・発表者の気付き

- コーディングがエージェントに委ねられるほど、エンジニアの時間は left of code / right of code に残ります。SDLC の設計では、この前後の工程にも目を向けるよう呼びかけられています。
- Spot On の開発自動化でも、人は常にループに入れていて、本番に直接出す運用ではないと、Ryan 氏が明言しています。
- 成果を出している組織について、Atlassian は「必ずしも最新のフロンティアモデルを使っているわけではなく、共通していたのは共有コンテキストの構築に投資していたこと」と説明しています。
- 発表の最後では、エンジニアや従業員を普段のワークフローから連れ出さずに、Jira や Microsoft Teams などのツールの中でエージェントが働くようにすることが成功の鍵だと述べられています。

## 8. 利用者にとっての利点

発表で語られた成果は次のとおりです。

- **共有コンテキストの効果**：顧客はエージェントの性能が最大 44% 向上し、トークンの支出にも節約効果が見られる。
- **Spot On の開発ワークフロー**：同規模チケットの所要時間が約 38 日から 4 日に、1 週間以内の納品率が約 12% から 70% になった。短縮の合計は 1,200 日超。
- **Spot On の PRD 作成**：ワンクリックで約 70% を作成。製品チームの実感では、数日が数時間になった。
- **Spot On の営業サポート**：clean deflection rate が V1 の約 40% から、5 回の改善で 66% になった。

## 9. まとめ

AI の ROI を組織全体に広げられている組織は、エージェントをチームのワークフロー（Jira、Microsoft Teams、Outlook など）に組み込み、共有コンテキストに投資している、というのが Atlassian の調査から導かれた結論です。Atlassian はこの共有コンテキストを Teamwork Graph として提供しており、Knowledge、People、Communications、Code、Assets などをつなぎ、80 以上のコネクタと独自データ用の API を備え、Rovo のほか MCP・CLI を通じて他のエージェントからも使えます。

Spot On の事例では、開発チケットが 38 日から 4 日になるなど、具体的な数字が示されました。一方で、人のレビューを残すこと、エージェントの ID・インベントリ・監査ログ・無効化でガバナンスを効かせることも同時に語られています。
