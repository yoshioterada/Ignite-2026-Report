# BRK416 Drive modern operations with Azure Monitor

## 1. はじめに

このセッションは、AI エージェントの時代に Azure Monitor でオブザーバビリティ（可観測性）をどう実現するかを、3 つのテーマで紹介するものです。1 つ目は **エージェントのオブザーバビリティ**（Foundry などで作ったエージェントを、アプリ・インフラまで含めて追跡する）、2 つ目は **AI を使った運用**（Observability Agent と、GitHub Copilot 向けの Azure Monitor Skills プラグイン、サービスの健全性を定義する Health models）、3 つ目は **運用テレメトリとビジネスデータの結合**（Azure Monitor Logs の Fabric へのミラーリング）です。最後に、テレメトリを集める Azure Monitor pipeline の新機能にも触れています。

登壇者は、同じキッチン家電サポートのアプリを題材に、ポータルでの調査から、VS Code 上のコーディングエージェントによる「検知 → 調査 → 修復 → 検証」、さらにビジネス影響の分析までを、画面を使ったデモで見せています。このセッションを読むと、次の点が分かります。

- エージェント、アプリ、データ、インフラを 1 本のトレースでつなぐ考え方
- Observability Agent の 3 つの役割と、Azure Monitor Skills プラグイン（プレビュー）
- Azure Monitor health models（一般提供の発表）の定義方法と使いどころ
- Azure Monitor のデータを Fabric に取り込んでビジネス影響を分析する方法
- Azure Monitor pipeline の VM 対応や PII の難読化などの新機能

## 3. 何に関する発表か

テーマは、「エージェントを作る側」と「エージェントを使って運用する側」の両方に対して、Azure Monitor がどのように役立つかです。冒頭の説明によると、業界では次の変化が起きています。

- エージェントは Foundry、Copilot Studio、Fabric など複数のプラットフォームにまたがり、モデルやツールもそれぞれ異なります。従来のフルスタック（アプリ・インフラ・ネットワーク）に、エージェントという層が増えました。
- 開発者は、問題の検出・トラブルシューティング・修復・洞察の取得にもエージェントを使うようになりました。
- テレメトリやヘルスのデータを、ビジネスの文脈と結び付けて優先順位を付ける必要があります。
- メトリック、トレース、ログを大量に集めるため、コストを抑えた効率的な収集が必要です。

Azure Monitor は、スタックの各層で同じ運用上の成果を提供するという位置づけです。エージェント層ではエージェント固有のテレメトリ、アプリケーション層では Application Insights による標準的な APM、データ層では SQL や Fabric などのデータ基盤、インフラ層では Azure・オンプレミス・マルチクラウドのインフラを対象にします。想定する利用者は、AI ビルダー、開発者、SRE、データチームなどです。

6. 全体のまとめ

## 5. 発表内容の詳細

### 5.1 エージェントのオブザーバビリティ（Hong 氏）

Hong 氏は、成功はエージェントの数ではなく、それを大規模に、自信を持って運用できるかで決まると述べています。午前のキーノート（発話では Judson の名が挙がっています）で語られたとおり、Agent 365、Azure Monitor、Foundry が連携し、エージェントの品質データと本番での信頼性、ビジネス成果をつなぐ統一的なエージェント・オブザーバビリティを提供するという説明です。エージェントのオブザーバビリティは複数のペルソナにまたがる問題であり、作る側のツールと運用する側のツールのどちらかを選ばされるべきではない、という考えです。どの入口から始めても、一貫した情報が得られる統一プラットフォームを目指しています。

発表では 4 つのペルソナが挙げられました。

| ペルソナ | 主な問い |
| --- | --- |
| エージェントビルダー | ビルド時に、どうエージェントを作り、評価し、運用するか |
| SRE | インフラに加え、自分が作っていないエージェントも運用する。フルスタックのどこに問題があるかを素早く特定し、信頼性をどう確保するか |
| IT 管理者 | アクセス制御があり、セキュアでコンプライアンスを満たすエージェントをどう確保するか |
| ビジネスオーナー | エージェントへの投資の ROI は何か |

これらの入口をまたいで、Agent 365 と Azure Monitor を土台にした統一プラットフォームが、見えているものをつなぎ、問題の相関付けやチーム間の協力を助けます。データ収集は **オープンスタンダードの OpenTelemetry** に基づく統一的な仕組みで、収集したデータは好きな場所に持っていけると説明されています。

### 5.2 デモの題材とポータルでの調査（Rahul 氏）

デモの題材は、**キッチン家電のサポートアプリ**です。お客様がエージェント型チャットボットで、家電の不具合を問い合わせたり保証の予約をしたりします。チームは Foundry のプロコード・エージェントを構築しており、スケジューリングを担い、技術マニュアルを AKS 上の Redis キャッシュから取得し、実際の予約には Azure Functions を使っています。複数の Foundry エージェントが、AKS や Azure 上の依存先をツール呼び出しで利用している構成です。

SRE の視点での調査は、次のように進みます（詳細な手順は 6 章）。

- **Foundry のモニタリング**: エージェント（tier 1、tier 2 の warranty agent など）を選ぶと、エージェントの実行、Gen AI のエラー、基本的な運用メトリックが見えます。groundedness は問題ありませんが、Foundry に保存された品質・正確性の評価（evals）に問題が出ており、これが調査のきっかけの「赤信号」になります。
- **Application Insights のアプリケーションマップ**: Azure Monitor で同じデータを開くと、コンポーネントの依存関係をトポロジとして見られます。ホットスポットや、どのコンポーネントがどこ（例: AKS）でホストされているかも分かります。
- **エージェント固有のビュー**: Foundry と重なるデータに加え、トークン消費量、ツール呼び出しごとの詳細、レイテンシなどが見えます。デモでは、あるツール呼び出しに 20 秒のレイテンシがあることが分かります。
- **Events ビュー**: 評価がどれだけ失敗しているか、傾向、成功しているものを確認できます。評価をクリックすると Foundry で開くこともできます。AI コンポーネントとして Observability Agent などが組み込まれていると述べています。
- **新しいトレースビュー**: 再設計されたトレース画面で、Foundry から tier 2 のエージェント、Azure Function への呼び出しが 1 本につながり、各スパンの所要時間、LLM モデルの所要時間、失敗箇所が分かります。この例では、technician availability の関数が失敗しており、null を返していました。
- **トレース分析（trace analytics）**: その失敗が 1 回限りか、傾向やパターンがあるかを、大量のトレースにまたがって評価します。デモでは約 107 件のトレースを対象に、エラーの多いものをコホートとして選択しています。すると、失敗していた technician availability の呼び出しは、ワシントン州の都市 Tacoma からのものでした。その日の Tacoma は技術者の空きが少なく、本来は「空きなし」を返すべきところで null を返したため、ツール呼び出しの失敗になった、という結論です。

さらに Rahul 氏は、この関数の代わりに Work IQ を層として使う構成にも触れています。Work IQ はエコシステムや技術者のコンテキストを既に持つので、技術者の空き状況の把握に役立てられる、という考えです。ここで伝えたかった点は、Foundry から Foundry、Foundry から AKS、Foundry から関数への呼び出しに加えて、Copilot Studio、Work IQ、Fabric データエージェントなどとのエージェント間呼び出しも、**1 本のトレースに載る**ことです。Foundry の呼び出しが劣化したとき、原因が Work IQ 層なのか、最後の Fabric データエージェントの劣化やキャパシティのスロットリングなのかを、エンドツーエンドで追えます。

### 5.4 Observability Agent（Rahul 氏）

2 つ目のテーマは、ポータルで見たようなトラブルシューティングを、自分の AI 運用の中でも行う方法です。最初に紹介されたのが **Observability Agent** です。一般提供は数か月前に発表済みで、Azure Monitor の一部としてパッケージされています。対象は、Azure Monitor で収集しているデータです。

- Azure プラットフォームが自動で出すデータ（VM、AKS、アプリ、リソースの健全性、サービスの健全性、可用性など）
- OpenTelemetry、Prometheus、ログなどから追加で収集しているデータ

このエージェントは、次の 3 つのことを得意とします。

1. **分析の質問に答える**: Log Analytics のクエリや PromQL を考える代わりに、自然言語で質問すると、データを調べて答えを返します。
2. **深い調査**: Completeness の評価劣化、AKS の "Umkil" アラート（音声認識の都合で表記が確定できません）、VM のダウンなどのアラートや問題を起点に、依存関係を追ってスタックの各層を調べ、根本原因の分析と次のステップの推奨を示します。
3. **自動アラートトリアージ（自律運用）**: **パブリックプレビュー** の機能です。フリート全体でアラートがノイジーになる（例: 100 台の VM で CPU アラートが一日中鳴り続ける）代わりに、自律モードの Observability Agent が、アラートを 1 つの代表的な問題にクラスタリングします。インシデントを作って通知すべきタイミングも判断し、設定に応じて深い調査を自動で実行します。「何かがおかしい」と伝えるだけでなく、「原因はこれです。修正してよいですか」と承認を求める形で、何時間もの作業を肩代わりするという説明です。

顧客事例として、KPMG が環境全体で Observability Agent を使っており、エンジニアリングの時間を取り戻せているという声が紹介されています。Rahul 氏は、新しいデータや新しいクエリ機能を足しているのではなく、同じデータに対して、エージェントがベストプラクティスを符号化して、より速く到達させるのだと説明しています。

### 5.5 VS Code でのコーディングエージェントによる検知・調査・修復・検証

同じ Foundry のキッチン家電アプリを使って、VS Code 上の GitHub Copilot で「検知 → 調査 → 修復 → 検証」を通しで見せています（手順は 6 章）。Rahul 氏は、開発者や SRE でなくても、ビジネス側のお客様が VS Code の GitHub Copilot に質問する使い方を始めていると述べています。

このデモで使われているのは、**Azure Monitor のスキル**であり、その裏側の API、CLI 呼び出し、MCP サーバー、そして AKS や Foundry が提供する追加のスキルです。これらを組み合わせて、通常は面倒な調査を数分で行える点が強調されています。

その後 Rahul 氏は、Observability Agent の力の源泉をあらためて整理しています。新しいデータ収集ではなく、アプリについての深い知識です。Azure Monitor と連携すると、トポロジ、パターン、どこで壊れるか、何につながっているかを既に知っています。すべてのデータソースを見て、トレース・ログ・メトリックにまたがる深い推論を行い、環境に応じた専門スキルも使います。このスキルは、AKS、Foundry、VM のチームなどと協力して作られており、Gen AI の問題でも、インフラの問題でも、プラットフォームの可用性の問題でも、エージェントが何が悪いかを示せる、という説明です。

Observability Agent の体験をパッケージにしたものとして、**Azure Observability（Azure Monitor）Skills プラグインのプレビュー** が、Azure Skills Marketplace で利用可能になったと発表されました。GitHub Copilot にインストールすると、関連する Azure Monitor の機能を自動で見つけ、必要な MCP を有効にして、検知・調査・修復・検証までの流れを案内します。発表のスライドには、手順を解説したブログ記事へのリンクがあり、記事には GitHub リポジトリへのリンクもあります。Skills Marketplace から自分で導入することもできます。Rahul 氏は、別のアイデアや機能のコントリビューションも歓迎すると述べています。

### 5.7 Azure Monitor health models（一般提供）

エージェントに与えるコンテキストが、テレメトリから発見できる範囲に限られていると、できることは限られます。そこで、**Azure Monitor health models の一般提供** が発表されました。例えば Redis キャッシュが落ちたとき、それが一時的なインフラの問題なのか、"self-zero"（音声認識の都合で表記が確定できません）と呼ばれる重大な問題として午前 2 時に起きて対応すべきものか、サービス全体の劣化につながるのかは、テレメトリだけでは分かりません。サービスが自分にとって何を意味するか、健全とは何かを定義し、エンタープライズの運用の成熟度を高めるための機能です。

定義は 3 段階で説明されています。

1. **サービスを定義する**: Redis キャッシュだけか、AKS フリートか、それとも家電サポートサービス全体か。サービスグループでも、複数のリソースを投げ縄のように囲んだものでも構いません。
2. **健全性を定義する**: 単一の層でも、入れ子（ネスト）の Health model でも定義できます。例えばアプリ全体に、チェックアウトサービス、チャットボットサービス、スケジューリングサービスがあり、それぞれに Health model を持てます。
3. **劣化の計算方法を定義する**: まず SLI、SLO、ゴールデンシグナル（可用性やレイテンシ）から始め、依存関係を加えていきます。Health の集約（roll-up）は best of や worst of などで設定でき、カスタマイズの余地が大きいと説明されています。

また、System Center / SCOM の経験がある方には、サーバーのリフト・アンド・シフトの環境でその機能を補う追加機能になると紹介されています。

顧客事例として **Ecolab** が、Health models を使って、インシデントの特定を速め、複数のサービスにわたるインシデントを減らしており、特に価値が大きいのは、価値の低いアラートのノイズを減らせたことだと述べています。サービスに影響しない VM の CPU スロットリングなどは気にしなくてよい、という考えです。

> 補足：コーディングエージェント向けの Health models の API と MCP は「近日中に提供予定」と述べられています。現時点で見せているのは、Azure portal 上のビジュアルな体験です。

### 5.8 Fabric へのミラーリングでビジネス影響を分析する（Evgeni 氏）

3 つ目のテーマは、観測の視点をさらに引いて、IT 部門だけでなく **ビジネス全体** の洞察につなげる話です。取り上げられた機能は、**Azure Monitor Logs の Fabric へのミラーリング** です。Fabric の OneLake に Azure Monitor のデータを公開する **ショートカット**（ファイルのショートカットやコードのポインタのようなもの）で、**追加コストはありません**。Fabric に入れば、売上や CRM などのビジネステレメトリと Azure Monitor のテレメトリを突き合わせられます。

Evgeni 氏のデモは、約 1 時間かけて作って録画したものです（手順は 6 章）。同じ考え方を、Observability Agent のテレメトリを使った自分の別プロダクトにも適用しており、今後のビジネスレビューでも同じ形で使うと話しています。要点は次のとおりです。

- Fabric で **Mirrored Azure Monitor** という新しいタイプのアイテム（Azure でいうリソースのようなもの）を作ります。作成後、ミラーリングされたカタログのエンティティがプロビジョニングされ、その配下に Eventhouse（Azure Data Explorer、Kusto）があり、SQL か KQL でクエリできます。
- Redis の障害で、特定モデルの詳細がキャッシュされなかったことが分かっていたので、CRM のデータ（どの家電をどの顧客に売ったか）と突き合わせ、影響を受けた顧客を特定します。
- ビジネス指標の簡単な式を作り、特定の例外ごとに、顧客あたりいくら失う可能性があるか、どの顧客に最初に連絡すべきかを算出します。
- Fabric MCP を通じて Copilot にレポートを生成させます。Copilot が仕様を作り、アプリを作成してデプロイし、フィルター付きのレポートができます。発話では "Raven apps or Fabric apps" と述べており、「Power BI ではなく、コードによるバックエンド・アズ・ア・サービスで、データの上にレポートを作る仕組み」と説明しています（アプリ名は音声認識の都合で表記が確定できません）。
- さらに、ビジネステレメトリと Application Insights のテレメトリの両方を考慮するよう Copilot に依頼すると、架空のデモ環境で、**25,000 ドル** の損失が見込まれる問題が 1 件見つかり、ほかに即座の金銭的影響がない問題も見つかります。

Evgeni 氏は、ミラーリング（ショートカット）自体は無料だが、エージェントの利用には料金がかかる、と注意を添えています。

### 5.9 Azure Monitor pipeline の進化（Evgeni 氏）

最後の話題は、Azure Monitor に入る前のデータを収集・加工する **Azure Monitor pipeline** です。テレメトリの収集は 3 本の柱で進めると説明されています。

1. **何でも収集できること**: トレース、メトリック、ビジネスデータなど。アプリケーションのテレメトリは、業界標準である OpenTelemetry（発話では "Hotel"）を使い、同じ標準をあらゆるものに広げたいという方針です。**Ignite で発表された新機能として、Azure Monitor pipeline を Kubernetes だけでなく VM にもデプロイできるようになりました。** 境界のマシンやオンプレミスのマシンからテレメトリを集めたいケースで、VM は既にプロビジョニングされているのに対し、Kubernetes クラスターは新規の作業になる、という理由です。
2. **コストの管理**: 無差別に集めるとテレメトリは急に膨らみます。データのフィルタリングや、余分な列の削除によるサイズ削減など、さまざまなオプションがあります。変換の機能として、メールアドレス、電話番号、住所などの **PII の難読化とトークン化** という新機能も発表されました。
3. **可用性**: キャッシュやリレーの機能により、確実にデータを届けられます。

Evgeni 氏は、これだけで 1 セッションになる話題だと述べ、詳細はブログを参照するよう案内しています。

## 6. デモ・手順

このセッションにはデモがあり、**ポータルの操作は録画ビデオ**（"let's jump into a video"）、Fabric のデモも録画（Evgeni 氏が「録画した」と説明）です。VS Code のデモと Health model の画面は、録画かライブかについて発話での言及がありません。録音は音声だけのため、画面の細部（ボタン名、入力値、レイアウト）は確認できません。以下は、語られた順の記述です。

### 6.1 ポータルでのエージェント調査（Rahul 氏）

1. お客様が Foundry バックエンドのエージェントに保証の予約を依頼するやり取りの画面を示す。
2. SRE として Foundry のページを開き、tier 1、tier 2 の warranty agent などのエージェント一覧を確認する。
3. エージェントを選んで、Monitor で実行状況、Gen AI のエラー、基本的な運用メトリック、groundedness を確認する。groundedness は問題なく、Foundry に保存されている品質・正確性の評価に問題が出ている。
4. 同じデータを支える Azure Monitor で開き、Application Insights のアプリケーションマップでトポロジ、ホットスポット、ホスト先（例: AKS）を見る。
5. エージェント固有のビューで、トークン消費、ツール呼び出しの詳細、レイテンシを見て、あるツール呼び出しの 20 秒のレイテンシを確認する（後で調べるため保留）。
6. Events ビューで評価の失敗数、傾向、成功したものを確認する。
7. 再設計されたトレースビューで、Foundry から tier 2 のエージェント、Azure Function までのスパン、所要時間、LLM モデルの時間、失敗箇所を見る。technician availability の関数が null を返して失敗していた。
8. トレース分析で、約 107 件のトレースからエラーの多いコホートを選び、失敗が Tacoma からの呼び出しに集中していることを確認する。
9. トレースとツール呼び出しを調べ、その日の Tacoma は技術者が少なく、空き無しを返すべきところが null を返していたと判断する。

### 6.2 VS Code での検知・調査・修復・検証（Rahul 氏）

1. VS Code のコーディングエージェントに、「このカスタマーサポートアプリの Foundry エージェントの本番の健全性を確認し、最近の実行から見て、何が起きているかを教えてほしい」と依頼する（趣旨）。
2. エージェントが適切な API、MCP サーバー、スキルを見つけ、問題のトリアージ一覧を返す。technician availability の問題が進行中であること、Redis キャッシュのスロットリングが見つかったこと、トレース分析にもとづく「全体で継続的に起きている問題」のデータが示される。チャット内にインラインのダッシュボードも出て、アプリマップやトレースビューへのディープリンクも付く。
3. Redis キャッシュの問題が 20 秒のレイテンシを加えていたため、Observability Agent を使って根本原因を調べるよう依頼する。数分かけて AKS や Functions を含む利用可能なデータを調べ、中〜高の確信度で因果の連鎖を示す。原因は、CPU が 250 millicores に設定されていてスロットリングされ、ワークロードの処理能力を食っていたこと。
4. 対応前に、1 回限りか大規模に起きているかを確認するため、コーディングエージェント側の **traces MCP** でトレース分析と同様の質問をする。クリティカルパス分析と属性分析で、過去 12 時間にわたり多くの呼び出しがスロットリングされており、4〜6 時間ごとに問題を代表する事象があるため、1 回限りではなく **システム的な問題** と判断する。
5. 修復を依頼する。Azure Monitor スキルの裏付けで、本番データで検証したうえで、Kubernetes マニフェストの設定を 250 millicore から 500 millicore に変更するよう提案される。ロールバック条件や、本番に入れる前のテスト方法も示される。
6. 本番投入の前に、テスト環境で、Azure Monitor の本番テレメトリを使って検証し、すべてのゲートが通ったら承認すると指示する（「まだそこまで信頼していない」という趣旨の冗談つき）。結果は、自分が書いた Python スクリプトのテストを含め、すべて成功（グリーン）で、本番に入れてよい状態になる。

### 6.3 Health model の表示（Rahul 氏）

1. Azure portal で、Health model の全体のトポロジを見る。
2. タイムラインビューで、関心のある期間に、いつ劣化し、いつ unhealthy になったか、どのシグナルを捉えたか（groundedness や task completion の評価の問題など）を見る。Application Insights で見た Foundry エージェントの問題が、Health model 上でも明確に定義されている。
3. コーディングエージェントで示した因果の連鎖が、Health model にも定義されており、Foundry エージェントのツール呼び出しの問題が、Redis キャッシュのスロットリングによるものと視覚的に分かる。
4. タイムラインを変えたり、追加の詳細を確認できる。worst of / best of などの集約、追加のヘルス制限、データポイントの変更といった設定が用意されていると説明される。
5. （口頭の説明）成熟度が上がると、コンポーネントが落ちたときの影響を「標準の影響」「フォールバックがあり限定的」などと明示でき、重要でない「あれば良い」コンポーネントの影響を抑制（visibility のみ）にもできる。
6. ネストした構造を見ると、エージェント部分は劣化しているが、フォールバックがあるため、サービス全体は影響を受けていない。AKS 上の Web サイトは正常で、チャットボットの問題の間は Web サイトのリンクに誘導するようエージェントに指示できる。

### 6.4 Fabric ミラーリングのデモ（Evgeni 氏、録画）

1. Fabric で、Mirrored Azure Monitor という新しいタイプのアイテムを作成する（細かい設定は省略されている）。
2. 作成後、ミラーリングされたカタログのエンティティがプロビジョニングされる。配下の Eventhouse に、SQL か KQL でクエリする。
3. Rahul 氏と Hong 氏がデモしたのと同じ Application Insights リソースから取り込まれたテレメトリを確認する。
4. Copilot に生成させた KQL の 1 本目で、CRM の販売データ（どの家電をどの顧客に売ったか）と Redis キャッシュの障害を突き合わせて、影響を受けた顧客を特定する。生成には数分かかったと説明されている。
5. 2 本目のクエリで、架空のビジネスチームと決めたビジネス指標の式を使い、例外ごと・顧客ごとの想定損失額と、最初に話すべき顧客を割り出す。
6. Fabric MCP を通じて Copilot にビジネス影響のレポートを依頼する。Copilot が仕様を作り、アプリを作成してデプロイし、フィルター付きのレポートが表示される。クロス集計もでき、エージェントが CSV エクスポートのボタンまで付けた。
7. ビジネステレメトリと Application Insights のテレメトリを合わせて、どのエラーが最もビジネスに影響するかを Copilot に分析させる。デモ環境では、25,000 ドルの損失が見込まれる問題が 1 件見つかり、ほかに金銭的な影響が即座には無い問題も見つかる。

## 7. 注意点・発表者の気付き

- **新規データは足さない。** Observability Agent は、新しいデータ収集や新しいクエリ機能を提供するものではなく、同じデータに対するベストプラクティスの適用だと明言されています。
- **提供状況が混在している。** Observability Agent は一般提供（数か月前に発表）、自動アラートトリアージ（自律運用）はパブリックプレビュー、Azure Monitor Skills プラグインはプレビュー、Health models は一般提供の発表です。Health models の API と MCP、そして Skills プラグインへの Health MCP の取り込みは「近日中」とされています。
- **Fabric ミラーリング自体は無料だが、エージェントの利用には料金がかかる。** Evgeni 氏が明確に分けて説明しています。
- **コーディングエージェントを盲信しない。** Rahul 氏は、修正案を本番に入れる前に、テスト環境で本番テレメトリを使って検証し、すべてのゲートが通ってから承認するように指示しています。「最近の障害が多いので、まだそこまで信頼していない」という趣旨の発言もあります。
- **ツール呼び出しの失敗の扱い。** デモでは、空きが無いだけなのに、null を返したことでツール呼び出しの失敗として扱われていたため、「空きなし」を返すべきだったと指摘しています。
- **デモの前提。** Evgeni 氏のデモの顧客データと損失額は、架空のデモ環境のものです。また、デモは録画で、エージェントが 20 分考え続ける様子を見せないよう、一部の工程を省いています。
- **音声認識の都合で表記が確定できない語。** "Umkil"（AKS のアラート名）、"self-zero"（"wake up at 2 a.m." が必要な重大な問題という文脈で使われています）、"Raven apps"、"hardware HPC observability" は、聞こえた表記のまま扱っています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **フルスタックでの原因特定**: エージェントの評価劣化から、ツール呼び出し、AKS 上の Redis、その CPU 設定まで、トレースと Observability Agent で数分のうちに辿れることを、デモで見せています。
- **クロスエージェントの追跡**: Foundry、AKS、Functions、Copilot Studio、Work IQ、Fabric データエージェントなどの呼び出しを 1 本のトレースで追えます。他のプラットフォームや、GCP・AWS 上のエージェントにもトレース分析が使える、という説明です。
- **運用時間の削減**: KPMG が、Observability Agent でエンジニアリングの時間を取り戻していると述べています。自動アラートトリアージは、ノイジーなアラートを 1 つの問題にまとめ、原因まで調べて承認を求める形で、何時間もの作業を肩代わりします。
- **アラートのノイズ削減と優先順位付け**: Ecolab が Health models で、インシデントの特定を速め、複数サービスにわたるインシデントを減らし、価値の低いアラートのノイズを減らしています。サービスにとって重要かどうかで、夜中に起きる対応か翌日でよいかを判断できます。
- **ビジネス影響の可視化**: Fabric ミラーリングにより、障害の影響顧客と想定損失額を算出し、どの問題から直すべきかをビジネスの観点で決められます。ミラーリング自体は追加コストがありません。
- **テレメトリ収集の柔軟性とコスト管理**: Azure Monitor pipeline が VM にもデプロイできるようになり、境界やオンプレミスのマシンから収集しやすくなりました。フィルタリング、列の削除、PII の難読化とトークン化でコストと機密情報を管理できます。

## 9. まとめ

このセッションは、Azure Monitor で、エージェントのオブザーバビリティ、AI を使った運用、ビジネスとの結合、そしてテレメトリ収集の効率化までを一続きに扱う内容でした。Foundry などのエージェントはアプリやインフラと同じトレースで追え、Observability Agent は Azure Monitor Skills プラグイン経由で GitHub Copilot からも使えます。Health models でサービスの健全性を定義すれば、問題の優先順位付けがビジネスに合ったものになります。Azure Monitor のデータを Fabric に取り込めば、障害を顧客と金額の影響で語れます。Azure Monitor pipeline は VM に対応し、コスト削減と PII 保護の機能が加わりました。登壇者は、詳細を解説したブログ（スライドの QR コードまたは aka.ms のリンク）を案内し、セッション後も質問を受け付けるとしています。なお、録音にはセッション内の Q&A は含まれていません。
