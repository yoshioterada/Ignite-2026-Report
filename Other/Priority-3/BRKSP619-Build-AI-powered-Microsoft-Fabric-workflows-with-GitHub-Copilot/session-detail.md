# BRKSP619 Build AI-powered Microsoft Fabric workflows with GitHub Copilot

## 1. はじめに

このセッションは、Microsoft Fabric の開発（データエンジニアリングと Power BI）に **GitHub Copilot** を安全に取り入れるための考え方と、実際の使い方を、2 本のデモ付きで紹介するものです。対象は、自分の分野には詳しいが、AI とのペアプログラミングは初めてという人です。

話の中心は 3 つです。1 つ目はライセンスとコスト（AI クレジットの予算設定を最初にやること）、2 つ目は「GitHub Copilot はコードの書き方は知っているが、あなたのデータや業務は知らない」ので、**instructions ファイル、ローカルのファイル、MCP サーバー**でコンテキストを渡すこと、3 つ目は Git のブランチとプルリクエストによる**安全網**です。デモでは、データエンジニアの側で、Fabric の Lakehouse / Warehouse に対するクエリ、ストアドプロシージャ、PySpark ノートブックを Copilot に作らせました。Power BI の側では、セマンティックモデルへの説明の一括追加と、モデルビューのレイアウト生成を行っています。

このセッションでは、画面を使ったデモが 2 本行われています（6 章）。

## 5. 発表内容の詳細

### 5.1 ライセンスとコスト

最初に押さえるべき点として、コストが他のツールより少し複雑だと述べています。

- GitHub Copilot の**個人ライセンス**が必要で、シートを持つユーザーごとに支払う
- VS Code のコード補完（オートコンプリート）は、このライセンスの範囲に含まれる
- **今年の 6 月以降**、このセッションで見せる agent mode での利用の多くは **AI クレジット**を消費する
- 管理者は、**ユーザーまたはグループ単位で予算を設定**できる。予期しない請求や、試行錯誤の多い人（効率的な使い方をまだ知らない人）が組織のクレジットを使い切ってしまう事態を避けるために、人にクレジットを使わせる前に最初にやるべきことだと強く勧めています
- Fabric 側では、GitHub Copilot は Fabric の容量（capacity）を消費しない。ただし、Copilot が作ったものも、通常どおりサービス上で容量を使う。Git 連携を使うには Fabric の容量が必要で、**トライアル容量でも可能**

### 5.2 誰のためのセッションか、何から始めるか

主な対象は、Fabric でパイプライン、ノートブック、SQL を扱うデータエンジニアと、Power BI の実務者です。ただし、概念は特定の分野に依存しないため、「自分の専門に自信があるが、AI ペアプログラミングは初めて」という人すべてが対象だと説明しています。

始め方は次の順です。まず VS Code を入れ、GitHub Copilot と Copilot Chat を入れます。そのうえで、簡単なことから始めます。例えば、コードベースについて説明してもらうことです。経験上、最も重要なのは **copilot instructions を書き始める**ことだそうです。チームでも個人でも、人は繰り返しの決まった方法で仕事をするので、その方法をエージェントに教えておくと効果が大きい、という説明です。

データエンジニアリングで安全に始められる題材として、ノートブックやソリューションの説明、ストアドプロシージャ、関数などが挙がりました。登壇者が特に重要だとしているのは**データ品質チェックの作成**です。データエンジニアリングでは、制約でチェックしてくれるデータベースを使う機会が減っているため、検証クエリのような繰り返し使えるものを書けることが大事だという話です。

Power BI 開発者向けの安全な出発点としては、次が挙がりました。

- セマンティックモデルに**コンテキスト（説明）を追加して AI に備える**（デモで実施）
- 複雑なモデルを理解しやすくするための**レイアウトビュー**の作成（デモで実施）
- 時間の関係でデモできない簡単な改善もいくつかある
- **Best Practice Analyzer のチェックを、すべてのプルリクエストに組み込む**。Power BI のセマンティックモデルとレポート開発に自動テストを入れる手軽な方法で、チェック不足や手作業の煩雑さを減らせる

### 5.3 Copilot のモードとリスク

GitHub Copilot には複数のモードがあり、リスクが大きく異なります。

| モード | 内容 | リスク・備考 |
| --- | --- | --- |
| Inline suggestions | コードのオートコンプリート | Copilot ライセンスに含まれ、追加の AI クレジットは使わない |
| Ask mode | コードを説明する。読み取り専用 | 完全に安全。他人から引き継いだコードを理解する出発点に向く |
| Plan mode | 変更を調査し、書き込む前にアプローチを提案する | 一歩ずつ進めながら学べる。リスクを考えやすい |
| Autopilot mode（以前は agent mode と呼ばれていた） | 自律的に動く。複数ファイルの編集、コマンド実行、ツールの利用ができる | 強力だが、「AI にプロジェクトを壊された」という話の多くはここから出ている |

指針は、**タスクに合わせてモードを選ぶ**こと。できることが多いほど、途中でのレビューと、追加すべきコンテキストが増えます。

### 5.4 Copilot が理解していないこと

Copilot は大量のコードを見ており、構文と一般的なパターンを知っていて、速く書けます。しかし、データ、業務、チームの標準、受け入れ基準は知りません。足りない情報があるとき、止まって質問するのではなく、推測で埋めます。それが、他の出力と同じくらい自信ありげに出てきます。このセッションで見せる内容は、すべてこのギャップを埋めるためのものだという位置づけです。

### 5.5 コンテキストの渡し方と、依頼の仕方

1. **instructions ファイル**：チームの標準、パターン、組織で重要なことを書いておくと、**すべてのリクエストで読まれる**。1 つのファイルで同じ種類の仕事をしているチーム全体が恩恵を受ける。
2. **ローカルのコンテキスト**：コード、モデル、そのタスクに関係する定義ファイルなどを見せる。
3. **ライブのコンテキスト（MCP サーバー）**：Fabric ワークスペースの現在の状態や、最新の Microsoft のドキュメントなどを、その場で調べられる。始めるときに勧められたものは、**Fabric and Power BI MCP server**、**GitHub**（GitHub を使っている場合）、**Microsoft Learn の docs MCP server**（古い情報に基づいて動くのを避け、最新のドキュメントを取り込める）。
4. **依頼を小さく、明確に、1 つずつにする**（コンテキストそのものではなく、依頼の仕方）：他の変更をレビューに出すのと同じ考え方。「パイプラインを作って」では推測で作られる。一方、「このノートブックで customer ID に対するチェックを追加して、却下された行を表示して」のように言えば、レビューしやすく、必要なものに沿った結果になる（発話は "an old check on customer ID" と聞こえ、チェックの種類は音声認識の都合で確定できません）。

### 5.6 ガードレール：Git とバージョン管理

バージョン管理は安全網だと述べています。AI ペアプログラマーを使うと、変更が速く、手に負えない速度で進む可能性があるため、Git によるバージョン管理（Fabric で使えるバージョン管理手段）を最初から使うことが勧められています。

流れは次のとおりです。

- **main ブランチは保護**する
- 作業は常に、自分専用のローカルな **feature ブランチ**で行う。手作業で変更する場合も、Copilot で高速に変更する場合も、ローカルで行うので他の人に影響しない
- **プルリクエストのレビュー**で、人が承認して初めて main に入る

リポジトリに早い段階で入れるべきファイルとして、`copilot instructions` の Markdown ファイルが挙がりました。チームと個人の標準を多く入れるほど、エージェントの精度が上がります。さらに進んだ段階では、GitHub の **code owners** と **PR テンプレート**で、レビューの一貫性を高めることを勧めています。原則は「**人のレビューなしに main へは入れない**」です。

### 5.7 繰り返し使えるワークフロー

エージェントの視点で見ると、次の流れになります。

1. コンテキスト（instructions と、作業中のファイル）
2. プロンプトの追加
3. 何かが生成される（コード、ドキュメントなど）
4. 出力が出る。それを**人がレビュー**する
5. 満足なら commit する。不満なら、やり直す
6. タスクが完了したら、**プルリクエスト**を出し、同僚にレビューしてもらう
7. 承認後、内容を Fabric に同期し、意図どおりになったかを実行して検証する

## 6. デモ・手順

デモは 2 本あります。いずれも画面の細部は音声からは確認できず、以下は語られた範囲の記述です。

### 6.1 データエンジニアリングのデモ（Kevin 氏）

テーマは、コーヒーショップを題材にした Fabric のソリューション（メダリオンアーキテクチャ）を Copilot で扱う流れです。

**準備：ツールと拡張機能**

1. VS Code を開き、拡張機能を入れる。**Microsoft Fabric 拡張機能**（環境に接続できる）と、SQL 向けの **MSSQL 拡張機能**（SQL プロジェクトを整理できる。最終的にワークスペースに反映される）。
2. MCP サーバーは、拡張機能の検索で「add MCP」と入力して MCP サーバーの一覧に切り替え、「Fabric」と入力して見つける。Microsoft Learn は、「learn」と入力しても出てこず、**「docs」と入力する**必要がある（Microsoft Learn がそう分類されている、という説明）。
3. GitHub にはすでに接続済みで、自分のブランチにいる。この手順はデモでは見せていない（簡単な手順だと述べています）。

**copilot instructions の中身**

4. リポジトリの copilot instructions Markdown を開く（VS Code では Ctrl + Shift + V でプレビューできる）。
5. 内容は、デモ用のコーヒーショップのシナリオ、アーキテクチャ（bronze、silver、gold のメダリオンアーキテクチャ）、実装方針です。CSV ファイルを取り込んで bronze を作り、silver では **クレンジング、重複排除、不良データの隔離（quarantine）**、gold は Warehouse に作る、という方針です。
6. Python / PySpark のコードには追加の instructions を使うよう指定し、チーム標準は別の standards フォルダーに置いてある。こうすることで、メインの instructions ファイルが巨大にならず、毎回のプロンプトで必要なものだけを読み込める。

**プロンプト 1：プロジェクトを理解する**

7. prompts フォルダーに、デモ用のプロンプトをすべて保存している（後で再現できるように、リポジトリで共有するとのことです）。1 つ目は、Ignite に出張する間、同僚がこのプロジェクトを引き継げるようにするため、リポジトリを確認し、技術的な考慮点をまとめるよう求めるもの。
8. 実行時間は **1 分 44 秒、9 ステップ**。結果として、プロジェクトの内容、エンドツーエンドのフロー、gold 層の主なオブジェクトとそれを埋めるストアドプロシージャ、追加のディメンション、データ品質、リネージ、再実行などが示された（gold の主なオブジェクト名は、音声では "the cell line" と聞こえますが、音声認識の都合で表記が確定できません）。

**プロンプト 2：隔離されたレコードを調べる読み取り専用 T-SQL**

9. 読み取り専用で、特定のテーブルに対して特定の列だけを取得する、的を絞った T-SQL クエリを書かせるプロンプト。長いプロンプトだが、Copilot を使って繰り返し使える形に磨いたものだと説明しています。
10. クエリの生成は **30 秒**。
11. Fabric のワークスペースで Silver Lakehouse の **SQL エンドポイント**を開き、同じクエリを実行すると、**483 行**が返った。つまり 483 件のレコードが隔離されていた。
12. 隔離の理由を見ると、**unit price mismatch**（単価の不一致）があった。取引ファイルとメニューのファイルを読み込んでおり、一部の取引の価格がメニューの価格と一致していなかった。

**プロンプト 3：ストアドプロシージャを作る**

13. 同じ分析をストアドプロシージャとして作るプロンプト。このセッションで Kevin 氏だけが分析できる状態にせず、繰り返し実行できるようにする狙い。
14. 実行時間は **約 2 分 30 秒、17 ステップ**。長くなった理由は、ストアドプロシージャを作る過程で Copilot が検証とプロジェクトのビルドを行い、「うまくいかない」と判断して、結果が得られるまで修正したため。
15. 作成されたストアドプロシージャは、**チームの標準（コードにコメントを書く）に従って**いる。
16. Fabric の Warehouse で実行すると、**同じ 483 行、同じ条件**の結果になった。

**プロンプト 4：PySpark ノートブックを作る**

17. 常に SQL を書くとは限らないデータエンジニア向けに、同じレベルの分析を**ノートブック**で行うプロンプト。対象のテーブルと、行いたい分析を指定して、出力が一貫するようにしている（このプロンプトも長いが、Copilot を使って繰り返せるように作ったものだと説明）。
18. ブランチで commit したあと、Fabric 側でノートブックを開く。Wi-Fi の状態が分からなかったので、事前に実行済みにしてある。
19. ノートブックはテーブルを読む関数を作り、データフレームを作ってクエリし、同じ分析を行う。結果は **483 行、13 列**で、同じ条件を確認できる。

### 6.2 Power BI のデモ（Leslie 氏）

**デモ 1：セマンティックモデルに説明を追加する（AI-ready にする）**

1. 使うセマンティックモデルとレポートは GitHub リポジトリの一部（後で共有）で、リポジトリ内のプロンプトによって**決定論的に**作られている。ここでは、その作成プロンプトの話はしない。
2. 課題は、フィールドがたくさんあるのに**説明（description）がない**こと。エージェントや AI ツールで使うなら、データを AI-ready にするため説明が必要。すべてのテーブルとフィールドに手作業でコピー & ペーストはしたくない。
3. フォルダーを開き、チャットで instructions を選択（「+」で、これが重要なコンテキストだと指定）。そのうえで「説明を追加するプロンプト」を実行する。
4. 説明の出典は **CSV ファイル**。レポート内の全フィールドに基づくテンプレートを生成させるプロンプトもリポジトリにあるとのこと。Excel ではなく、CSV として保存すれば読みやすい。
5. プロンプトの規則（語られたもの）：
   - 説明は**書かれたとおりに使い、書き換え・短縮・改善をしない**（Copilot は冗長にしたがるため、はっきりした説明を与えて「盛らせない」）
   - **説明を作り出さない**。欠けているものは触らず、報告する
   - 終了時に、テーブルごとに更新したオブジェクト数、モデルと一致しなかった CSV 行、説明が空のためスキップしたもの、CSV に行がないモデル内のメジャーを報告させる（両方向から不一致を確認できる）
   - 報告は**短いリストだけ**。追加のチェックや説明・コメントは不要。長く装飾的な説明はトークン使用量を増やすため、簡潔に絞る
6. 実行が終わると、モデル内の更新オブジェクト数が出る。**不一致の行はなし、空の説明によるスキップもなし、CSV から欠けているメジャーもなし**。
7. データモデルを読み込むと、**各フィールドとテーブルに説明が付いている**。
8. VS Code でこのような変更を行うとデータが消えたように見える（一部のテーブルが「データが不完全または無い」と表示される）が、実際には何も変わっておらず、**更新（refresh）すれば戻る**。

補足として、**今週発表された Fabric IQ の GitHub Copilot app でのプレビュー**に触れています。オントロジーを使っていてビジネス上の説明がある場合は、CSV よりも直接取り込める方法になります。外部ソースがない場合は、データ辞書を使う方法もあります。

**デモ 2：モデルビューのレイアウトを整える**

9. 対象のレポートには 3 ページがあり、モデルビューは 1 つだけで、全テーブルが自動配置されているが、使いやすい並びではない。
10. 同じように instructions をコンテキストに追加し、レイアウト用のプロンプトを実行する。このプロンプトは、**GitHub Copilot が作ったスクリプトを実行して、モデルビューを決定論的に生成する**もの。
11. 利点はトークン消費が大幅に少ないこと。リポジトリの instructions に従って Copilot（または他のコーディングアシスタント）に毎回この処理を行わせる方法もあるが、毎回同じ量のトークンを使い、テスト時には**約 6〜8 分**かかる。今回は**25 秒**で終わった。最初にトークンを使ってスクリプトを作っておき、以後はそのスクリプトを呼ぶだけで済むため。
12. モデルがレイアウトビューの作成に向いているかを確認するプロンプトもある。テーブルを取り込んだだけのモデルは、散らばったスノーフレーク型になり、レイアウトに向かない。**スタースキーマ（またはそれに近いもの）**を想定している（Power BI Desktop がそれを前提に動くため）。
13. Power BI Desktop で結果を確認する際、最初は期待どおりにならなかった。原因として、新しい Power BI Desktop が**自動日付/時刻（auto date/time）をときどき再び有効にしてしまう**ことを挙げている。これは、非表示の日付テーブルとは相性が悪い。そこで設定をオフにして、プロンプトを再実行した（数秒で完了）。
14. 結果として、**レポートの各ページに対して、ページごとのレイアウトビュー**が作られた。ページ上のビジュアルとスライサーで使われているテーブルだけが表示され、あるメジャーがレポートでうまく動かない理由を調べるときのメンタルモデルを作りやすいと説明しています。
15. 作業はローカルで行っているため、本番サーバーには影響していない。ファイルの再読み込み（"Apply external changes"）の場面でも、開くのが早すぎたのが原因だったとの説明があり、登壇者は「デモの神様があまり優しくない」と話しています。

> 注意：Power BI Desktop の auto date/time は、**ローカルファイルとグローバル設定の両方でオフ**にしておくべきだとされています。この設定は、モデル内のすべての日付/時刻フィールドごとに非表示の日付テーブルを生成し、モデルのサイズを大幅に増やす可能性があるためです。

## 7. 注意点・発表者の気付き

発表の最後に、アンチパターンとして次の点が挙がりました。

- **大量のコンテンツがすぐに生成される**：agent mode は速いので、データ品質やセキュリティに大きな影響が出る変更を入れないよう、レビューする。
- **本番に対してプロンプトを実行しない**：「絶対に、絶対にやらない」と強く述べています。少なくとも dev / test / prod のワークスペースの土台を整えてから、プロンプトによる開発支援を導入する。
- **「動いたから」でテストを省略しない**：テストが完走したからといって、テストのレビューも省略しない。
- 組織のポリシーを理解する。個人プロジェクトであっても、**シークレットやログイン情報など、インターネットに公開されて困るものをプロンプトに入れない**。

その他、デモ中に語られた気付きは次のとおりです。

- Copilot に説明を**生成させず**、業務で意味のある自社の説明を使う（Leslie 氏の助言）。
- Copilot は冗長な出力になりがちなので、**短いリストだけ報告させる**ことでトークンを節約できる。
- 繰り返す処理は、**スクリプトを作らせて呼ぶ**と、トークンも時間も大幅に減る（レイアウトビューの例：6〜8 分 → 25 秒）。
- VS Code 側の変更後、Power BI のデータが空に見えたら refresh する。
- 新しい Power BI Desktop で auto date/time が再びオンになることがある。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- データエンジニアリング：リポジトリの理解（1 分 44 秒）、隔離データを調べるクエリ（30 秒）、検証と修正を自分で行いながら作るストアドプロシージャ（約 2 分 30 秒）、PySpark ノートブック。同じ分析が 483 行という同一の結果で、SQL・ストアドプロシージャ・ノートブックの 3 通りに繰り返せる。
- Power BI：全フィールド・テーブルへの説明の一括付与、ページごとのレイアウトビュー作成（スクリプト化で 25 秒、トークンも節約）。
- 1 つの instructions ファイルで、同じ種類の仕事をするチーム全体に標準が行き渡る。標準を別ファイルに分けると、毎回のプロンプトの読み込みを抑えられる。
- コミットメッセージ、プルリクエストの説明、ER 図、モデルのドキュメント、トラブルシューティング（エラーを理解して方向を示してくれる）、データ品質チェック、パラメーター化、パイプライン式など、すぐに試せる題材が示された。

## 9. まとめ

**持ち帰りとして語られた要点**は次のとおりです。

1. 既存のワークフローに取り入れ、持っている専門性を**拡張**する。Fabric 上のデータ基盤に対して、実用的で安全な確認方法を持った状態で進める。
2. **コンテキスト**を渡す。何が必要で、組織にとって何が重要で、チームの標準は何かを伝える。
3. **Git が安全網**であり、変更を行う経路でもある。dev / test / prod のようなデプロイが未整備なら、AI 支援コーディングの前に、ソース管理と CI/CD の良い習慣を整える。

**月曜日に仕事に戻ったら**：すでに Git を使っているなら、コミットメッセージやプルリクエストの説明の下書きから始める。次に、Copilot に copilot instructions を作らせる（時間の節約になり、個人だけでなくチームでも繰り返し作れるようになる）。BI 開発者・データエンジニアは、ER 図、モデルドキュメント、Best Practice Analyzer、トラブルシューティング、データ品質チェック、パラメーター化やパイプライン式などの簡単な題材で慣れる。

**データ関連プロジェクトで効果的だったプロンプトのコツ**：

- コンテキストを入れる。参照したいファイルや、ファイルとして保存したプロンプトは、**ハッシュ記号（#）**で参照できる（Leslie 氏のデモで、ファイルを素早く選ぶ場面があったと触れています）。
- **データに名前を付ける**。大きなデータでは、特定のテーブルやパーティションを指定して、余計なトークンや時間を使わせない。
- **テストを頼む**（誰もテストを書くのは好きではなく、業務が変わって前提が成り立たなくなったテストを直すのも面倒）。
- **「何がうまくいかなくなりうるか」を尋ねる**。スキーマがずれたら？ データ量が 10 倍になったら？

最後に、2 人のそれぞれの GitHub リポジトリから始められること、この発表の PDF（今回は扱わなかった追加コンテキストのスライドを含む）も入手できることが案内されました。さらに、コーディングアシスタントを Fabric で深く使うための参考リンクと、当日開催される関連セッション（データチームへの AI 活用をさらに掘り下げるもの）も紹介されました。
