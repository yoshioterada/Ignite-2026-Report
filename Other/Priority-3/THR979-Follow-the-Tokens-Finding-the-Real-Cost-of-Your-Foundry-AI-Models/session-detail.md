# THR979 Follow the Tokens: Finding the Real Cost of Your Foundry AI Models

## 1. はじめに

このセッションは、Microsoft Foundry 上のモデルやエージェントを使ったときに「実際いくらかかっているのか」を、トークンの数え方から追いかける約 25 分の短いセッションです。登壇者はライブデモを交えながら、次の 4 つの話題を順に扱います。

1. コストはどう計測されるか（トークンとは何か）
2. モデルの価格をどこから取得するか
3. 1 回のリクエストにいくらかかったかを、開発者がどう求めて保存するか
4. 管理者が Azure Monitor を使って、モデル単位のコストをどう集計するか

発表の中心にある課題は、**Azure の請求（Azure Billing）はリソースグループや Foundry のプロジェクト単位のコストしか出せず、「どのモデルがいくら使ったか」までは分からない**という点です。登壇者は、リクエストごとの usage 情報から計算する方法（開発者向け）と、Azure Monitor からモデル別の使用量を取って計算する方法（管理者向け）の 2 通りを示し、あわせてコストを下げるための最適化のコツを紹介しています。

このセッションを読むと、トークン数の見積もり方、価格 API の見方、コスト計算式、プロンプトキャッシュなどの節約策、そして Azure Monitor を使った集計の流れが分かります。

## 4. 発表者が伝えたいメッセージ

登壇者のメッセージは、**入力側は自分でコントロールできるので、トークンを意識して最適化し、開発者は usage 情報を保存・表示して、管理者は Azure Monitor でモデル別コストを把握しよう**というものです。

根拠として挙げられているのは次の点です。

- LLM の処理では、入力（プロンプト）は制御できる一方、課金は出力に対して大きくかかる。出力は内部の計算をすべて含むため、入力より高い。つまり、コストに影響を与えられるのは入力側の工夫。
- 請求画面（Azure Billing）はプロジェクト単位までしか分からないため、モデル単位のコストは別の手段で出す必要がある。
- 顧客からは「エージェントがいくらコストを生むか分からなくて使うのが怖い」という声がよく出る。だからこそ、コストをできるだけ透明にして、ユーザーに見せることが大事。

## 5. 発表内容の詳細

### 5.1 コストはどう計測されるか：トークンの考え方

登壇者はまず LLM の処理の流れを次のように説明しています。入力されたプロンプトはトークナイザーで分割され、それがベクトル化（埋め込み）され、計算によって変換されて、出力が返ります。コストの観点では、**入力は自分で制御でき、課金は出力に対してもかかる**ため、出力のほうが入力よりずっと高くなります。処理を実際に左右できるのは、入力という 1 つのステップだけだという位置づけです。

トークンは「ID」です。例えば "I love cats" のような文を、トークナイザーが ID に変換します。登壇者によると、GPT-5 のようなモデルは 5 万〜10 万語程度の辞書を持っていて、"I" は辞書の 40 番、"love" は 850 番、といった形で対応づけられます。

#### トークナイザーのデモ

トークン数の目安を知るために、登壇者は"the tokenizer" と呼ばれる画面を開き、文章を入力して見せています。このデモでは **15 トークン・33 文字**と表示され、おおむね 1 単語が 1 トークンに対応していました。ただし、単語の長さによっては 1 単語が複数トークンになることもあります。

目安として、**100 トークンは英語でおよそ 75 語**です。式にすると、**単語数に 1.3 を掛ければ、おおよそのトークン数が見積もれます**。

### 5.2 モデル選択とコストの考慮点

課金はトークン単位で、使うトークンが多いほど請求も増えます。登壇者は、課金の対象として次を挙げています。

- 入力：入力プロンプトに加え、場合によってはキャッシュされたトークン
- 出力

また、コンテキストウィンドウもトークンで測られます。以前のモデルは 10 万トークン程度が上限のものが多かった一方、新しいモデルでは最大 100 万、あるいは 110 万トークンのウィンドウを持つものがあります。Claude モデルのコンテキストウィンドウは 20 万以上、という例も挙げられました。

登壇者は、どのモデルを使ってもトークナイザーは同じ考え方であり、モデルによって異なるのはサイズや能力だと説明しています（この部分は音声が不明瞭で、「同じ」の範囲が正確かは確定できません）。さらに Foundry では、モデルに **ガードとフィルター（guards and filters）** を適用でき、これらもトークンのストリームを計算に使います。そしてコスト削減で重要な要素として、**プロンプトキャッシュ**（prompt caching）が挙げられ、最適化の章で改めて取り上げられます。

### 5.3 モデルの価格を取得する方法

モデルの価格を取得する方法は 2 つあるという説明です。

1. **リテール価格表（retail price list）**：Enterprise Agreement を結んでいない、または Cloud Solution Provider（CSP）経由でない場合に使う、一般消費者向けの価格表。
2. CSP として顧客向けのコストを知りたい場合は、価格を返す API に問い合わせる（発話では 2 つ目の方法の説明が簡潔で、詳細は語られていません）。

以下のデモは、この API を呼び出すものです。

#### 価格取得スクリプトのデモ（PowerShell）

登壇者は `get prices` という名前の PowerShell スクリプトを実行しています。次の流れで語られています。

1. スクリプトはパラメーターを尋ねてくる。登壇者は、モデルがデプロイされているデータセンターとして West US、通貨として USD、出力形式として CSV または JSON を指定した。
2. スクリプトは URI を組み立てる。これが「US ドルで、West US2 にあるすべての Foundry モデルの価格をください」という API 呼び出しになる（発話では West US と West US2 の両方が出てきます）。
3. 価格データは**ページング**されることがあるため、次ページのリンクが存在すれば続けて取得する処理が組み込まれている。
4. 結果をオブジェクト（`results`）にまとめ、出力する。画面の出力だけでは価格が見づらいので、事前に作っておいた 2 つのファイル（価格の JSON など）を開いて見せた。

JSON の中身については、"MAI" モデル（発話では "MAI models code 11 flash" と聞こえます。音声認識の都合で正式名称が確定できません）を検索して説明しています。

- 同じモデルが API の中に複数回出てくる。入力、キャッシュされた入力、出力それぞれに別の価格行があるため。
- 入力の価格は、そのリージョン・そのモデルで 100 万トークンあたり 2 セントと説明されています（音声認識の都合で数値が正確か確定できません）。
- **キャッシュされたトークン**（前のプロンプトなどで既に処理済みの情報を再利用するもの）は、リテール価格が入力の **10 分の 1** で、はるかに安い。そのため、可能な限りキャッシュを使う意味がある。
- **出力**の価格は入力よりずっと高い。出力には必要なすべての計算が含まれ、計算のたびにコストが発生するため。

つまり、コストを計算するときには、少なくとも**入力・キャッシュ入力・出力**の 3 つの価格を考慮する必要があります。

#### Anthropic など他社モデルの価格

API で "Claude" を検索しても見つかりません。登壇者の説明では、Microsoft は Microsoft Foundry で販売しているサービスをこのリテール API に含めていますが、Anthropic のような他のモデルベンダーは自社で課金することが多く、その場合は "cloud consumption units（CCU）" が Azure Marketplace でコストに換算されます。このため、これらのモデルの価格は自分で調べる必要があります。

一方で、**Azure Marketplace のオファーはすべて Microsoft Azure Consumption Commitment（MACC）の対象**です。Enterprise Agreement で一定額を Azure に使うことを約束している場合、そうした支出もカウントされます。CCU の価格表へのリンクはスライドに載せられています。

#### AI credits

Microsoft には AI credits もあり、2 種類が紹介されています。

| 種類 | 説明 |
| --- | --- |
| Copilot credits | Microsoft 365 のエコシステム側 |
| GitHub AI credits | GitHub 側 |

どちらもトークン使用量から自動的に換算され、現時点のリテール価格では **1 クレジット＝1 セント**（GitHub AI credits も同額）と説明されています。

これが重要なのは、組織の開発者が GitHub Copilot でアプリを開発していることが多いからです。価格表から読み取れる例として、登壇者は "Claude Opus 5.5"（発話では "Cloud Opus 5.5"。音声認識の都合で表記が確定できません）を挙げています。コンテキストウィンドウは 110 万と大きく、入力が 400 クレジット、出力が 2,000 クレジット（いずれも 100 万トークンあたり）です。そのため、「この用途なら Claude の Sonnet 系で十分」（発話は "ClaudsonNet"。音声認識の都合で確定できません）として、価格が半分のモデルを開発者に勧める、といった選択肢も検討する価値がある、と説明しています。

### 5.4 リクエスト単位のコストを取得する

次の話題は、「開発者に何を伝えれば、Foundry モデルへのリクエストのコストを取得できるか」です。結論は、**エージェント／モデルのレスポンスに含まれる usage 情報を使う**ことです。

#### Foundry でのエージェント実行デモ

デモの流れは次のように語られています。

1. スライドに、プロジェクトの AI サービスにあるデモ用エージェントを呼び出すエンドポイントが示される。ボディには天気を尋ねるチャットが入っている。
2. Foundry のプレイグラウンド（"my chat agent"）で、"How is the weather in San Francisco and what should I wear?" と入力して Enter を押す。
3. 出力が返る（登壇者は「明日は雨だと分かっているので、AI に聞く必要はなかったのですが」と冗談を言っています）。
4. プレイグラウンドで YAML を見ると、開始時のプロンプトや使用したエージェントのバージョンなどは分かるが、**コストは分からない**。

そこで、開発者側からの呼び出しとして同じことを PowerShell で行います。

1. 簡単なスクリプトでエージェントを実行する（スライドと同じく、エンドポイント、エージェント名、プロンプトを指定する）。
2. ブレークポイントを置き、ファンクションキーで実行する。会話（conversation）を作成し、エージェントに問い合わせる。
3. 出力が見やすいよう、結果を `response.json` というファイルにも保存する。傘が推奨される、という回答メッセージが得られる。
4. `response` 変数の中に、**usage** 情報が含まれている。

usage の内容として、登壇者は次の点を説明しています。

- この例では、入力トークンが約 1,500。
- 最初の送信なので、キャッシュされたトークンは無い。
- 出力トークンの数が示される。トークンの種類ごとに価格が違うため、入力トークン分、キャッシュトークン分、出力トークン分の価格をそれぞれ計算して足す必要がある。
- 合計トークン数も得られる。
- エージェントがツールを使っていれば、そのツール（この例では "chat agent toolbox"）の情報も含まれる。

> 注意：ほとんどの主要な LLM は usage データを返しますが、**形式は普遍的に標準化されているわけではありません**。コスト計算のロジックをアプリに組み込むときに、どのモデルでも同じ項目が得られると仮定してはいけません。何が返るかはモデル次第です。

登壇者は、アプリがリクエストを送るたびに、開発者がトークン情報を取得してデータベースに保存したり、ユーザーに見える形でアプリに表示したりする、というやり方を勧めています。顧客から「コストが分からないのでエージェントを使うのが怖い」とよく言われるため、できるだけ透明にするのがよい、という理由です。

#### コスト計算式

登壇者が示した計算式は次のとおりです。

1. 入力トークンから、キャッシュされたトークンを引く（キャッシュ分は別価格のため）。
2. それに、キャッシュトークンの価格分を加える。
3. 出力トークンの分を加える。
4. エージェントがツールを使っている場合は、ツールの使用分を加える。

これがトークンコストになります。価格は多くの場合 100 万トークン単位で表示されるため、価格表の形に合わせて計算します。

具体例として、登壇者は 1 回のリクエストの数値を当てはめています（発話の数値は聞き取りが不明瞭な部分があります。入力は 650.85 のように聞こえ、GPT-5 の価格として 1.25 ドル、リージョンは "South Central Plus" と聞こえますが、いずれも音声認識の都合で確定できません）。結論として、**キャッシュされた入力が多かったため、このリクエストのコストはおよそ 1 セント程度で、キャッシュが無い場合の約 3 セントよりかなり安くなる**ことが示されました。

### 5.5 コスト最適化の推奨事項

#### プロンプトキャッシュ

キャッシュの仕組みと、自分の側でコントロールする方法として、次の点が語られています。

- **安定した内容を先頭に置き**、次のプロンプトでは、すでに得たデータについて尋ねる。例えば RAG のモデルで、最初のリクエストでは「これを要約して」、次のリクエストでは「リスクを見つけて」と頼むと、キャッシュがよく効いてコストが大きく下がる。
- プロンプトキャッシュについての詳しい情報へのリンクがスライドに載せられている。

#### Foundry toolbox

2 つ目は **Foundry toolbox** です。登壇者がデモのエージェントで使っていたもので、エージェントが複数のツールを持つ場合に特に有用だと説明しています。toolbox がオーケストレーションして「このツールを使うので、このツールの定義を読む」という形にでき、その定義も内部でキャッシュされるため、リクエスト数やトークン使用量が減る、という説明です。

#### 推奨事項の一覧

| 推奨事項 | 補足 |
| --- | --- |
| プロンプトキャッシュを最大限に活用する | 例として、GPT 5.6 のようなモデルでもプロンプトキャッシュやキャッシュブレークポイントが使え、開発者側から指定できる、と説明。 |
| Foundry toolbox を使う | 複数ツールを持つエージェントで有効。 |
| エージェントの instructions を短くする | 可能な範囲で。 |
| RAG の取得サイズを絞る | AI Search などを使う場合、しきい値やセマンティックランキングなどで出力を制御できる。 |
| 出力の長さを制御する | プロンプトに「150 語未満で答えて」「出力はこの JSON 構造にして」などと書く。出力トークンが高いため。 |
| ツールの結果を小さく保つ | API やデータベースの結果は、関連するデータだけに絞る。返ってきた情報をすべて入れない。 |
| 最新のモデルが常に最適とは限らない | PDF から情報を取り出して要約するような単純な用途なら、古いモデル（発話では "GPT-4 or 5 or so"）で十分なことがある。試して確認する。 |

### 5.6 管理者向け：Azure Monitor でモデル別のコストを取得する

ここまでが開発者向けで、次は管理者の視点です。標準の Azure Billing は、Foundry プロジェクトという**リソース単位**のコストしか出ません。プロジェクトの中にモデルが 5 つあっても、どのモデルがどれだけ消費したかは分かりません。そこで使うのが **Azure Monitor** です。

登壇者は、Azure Monitor に「特定の 1 プロジェクトの詳細をください」と依頼するサンプルのリクエストを示し、SDK を使う場合はパラメーターを追加してデータを取得できると説明しています。サンプルとスライドは **Ignite の GitHub リポジトリ**で公開されており、最後にリンク（QR コード）が示されます。

#### 事前準備（アプリ登録とロール）

デモで使うアプリケーション（`Get Foundry Usage` という名前）について、次の点が語られています。

1. アプリの **API permissions** には、特に何の権限も必要ない。
2. このアプリで認証できればよい。認証には証明書またはシークレットを使っている。
3. 重要なのは、**対象プロジェクトに対してこのアプリに権限を与える**こと。リソースのアクセス制御（ロール管理）で、このアプリに **Monitor Reader** の権限を付与する。
4. これで、アプリは認証し、その Foundry プロジェクトにあるすべてのデータを要求できる。

これらの要件は、リポジトリに手順付きの README として書かれています。

#### C# アプリのデモ

簡単な C# アプリを使ったデモです。環境変数は、対象のテナントとアプリケーション ID を指定するものが 1 つあるという説明でした。運用では、このアプリを **Azure Functions などで毎晩実行して、前日のモデル別コストを取得する**使い方を想定しています。

1. 対象のリソースを指定し、**過去 30 日分**のデータを取得するように設定する。
2. デモ用として、価格は**ハードコード**してある（「1,000 リクエストで 2 セント未満くらい」といった値を置いた、と話していますが、聞き取りが不明瞭で数値は確定できません）。
3. F5 キーでアプリを実行する。まずトークンを取得し、認証される。
4. Azure Monitor に対して、この特定のプロジェクトのデータを問い合わせる。
5. 戻ってきたデータから、各モデルで使われたトークン数が分かる。
6. 出力には、サブスクリプションとプロジェクト名、30 日間の範囲ごとに、**モデル別のコスト**が表示される。例えば GPT-5 については、リクエスト数、入力トークン数、出力トークン数が表示され、それをもとに計算したコストが **1.07 ドル**と示された。

#### Power BI での可視化

取得したデータは、データベースなどに保存できます。登壇者は Power BI を使い、例えば「11 月に GPT 5.1 をどれだけ消費したか」を尋ねられる形にしていると説明しています。そこでは、リクエスト数、推定コスト、1 リクエストあたりの平均（「30 セントくらい」と述べています）が確認できます。

## 6. デモ・手順

このセッションにはライブデモがあり、発話から確認できたのは次の 5 つです。画面の細部（ボタンや画面レイアウト）は音声からは確認できないため、語られた範囲だけを書きます。

1. **トークナイザー**：文章を入力し、15 トークン・33 文字と表示されることを確認（5.1）。
2. **価格取得（PowerShell の `get prices`）**：West US、USD、CSV/JSON を指定して価格 API から価格を取得し、JSON ファイルで MAI モデルの入力・キャッシュ入力・出力の価格を確認（5.3）。
3. **Foundry のチャットエージェント**：プレイグラウンドで "How is the weather in San Francisco and what should I wear?" を実行。YAML にはコスト情報が無いことを確認（5.4）。
4. **PowerShell でのエージェント実行**：ブレークポイントを置いて実行し、レスポンスの usage から入力トークンが約 1,500、キャッシュなし、出力トークン、合計、ツール情報を確認（5.4）。
5. **C# アプリ（Get Foundry Usage）**：Azure Monitor からモデル別の使用量を取得し、30 日分の GPT-5 のコストを 1.07 ドルと算出。Power BI で可視化する例も紹介（5.6）。

管理者向けのアプリを動かす前提手順（アプリ登録、API permissions は不要、証明書またはシークレットで認証、対象プロジェクトで Monitor Reader ロールを付与）は 5.6 にまとめています。

## 7. 注意点・発表者の気付き

- **usage の形式はモデルごとに異なる**：主要な LLM は usage を返すが、普遍的に標準化されていない。コスト計算ロジックを組み込むときは、どのモデルでも同じ情報が返ると仮定しない。
- **Anthropic などの他社モデルは、Microsoft のリテール価格 API には載らない**：CCU が Azure Marketplace でコストに換算されるため、自分で調べる必要がある。ただし、Azure Marketplace のオファーは MACC の対象になる。
- **Azure Billing はプロジェクト単位まで**：モデル単位のコストは、Azure Monitor などで別に求める必要がある。
- **出力トークンは高い**：出力の長さを制御することが節約につながる。
- **最新モデルが最良とは限らない**：単純な用途なら古いモデルで十分な場合がある。
- デモでは価格をハードコードしている。実運用での価格の持ち方については、発表では詳しく触れていません。

## 8. 利用者にとっての利点

発表で語られた利点は、次のとおりです。

- 部門やコストセンターの単位で「このエージェントを使うといくらかかるか」を答えられるようになる。ユーザーが感じる「コストが分からず怖い」という不安に、透明性で応えられる。
- キャッシュされたトークンは、価格 JSON で確認した例ではリテール価格が通常の入力の 10 分の 1 だった。実際のデモ例では、1 リクエストが約 3 セントから約 1 セントになった。
- Foundry toolbox の利用、プロンプトの短縮、RAG の取得サイズの制御、出力長の制御などで、トークン使用量を減らせる。
- 管理者は、Azure Monitor と SDK のアプリを夜間に実行するなどして、プロジェクト内のモデル別コストを、Power BI などで可視化できる。
- AI credits の価格表を見て、より安いモデル（例：価格が半分のモデル）への切り替えも検討できる。

## 9. まとめ

Foundry の AI モデルのコストは、**入力は自分で最適化でき、課金は出力に大きくかかる**という前提で考えます。トークン数は、英語なら単語数に 1.3 を掛けて見積もれます。価格はリテール価格 API で取得でき、入力・キャッシュ入力・出力の 3 つの価格がある点に注意が必要です。

開発者には、リクエストごとの usage 情報（入力、キャッシュ、出力、ツール）を取り出して、計算式でコストを求め、データベースに保存したり画面に表示したりすることが勧められています。プロンプトキャッシュと Foundry toolbox の活用が主な節約策で、モデルの選び方も見直す余地があります。管理者は、Azure Billing では分からないモデル別のコストを、Azure Monitor で取得できます。サンプルとスライドは Ignite の GitHub リポジトリで公開されています。
