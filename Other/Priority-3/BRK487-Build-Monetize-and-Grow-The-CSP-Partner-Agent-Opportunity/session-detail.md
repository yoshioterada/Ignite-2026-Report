### 5.2 Why Microsoft：プラットフォームと Microsoft IQ

「Microsoft ならゼロから始めなくていい」という説明です。顧客はすでに Microsoft のエコシステムにいるため、「built-in の流通モデル」があるとしています。AI の勢いについては、スライドには出ていない数字として、次の 2 点を挙げています。

- 月間アクティブなエージェントの利用が、年初来で 6 倍になった
- Microsoft Foundry の顧客数が 120,000 に達し、売上は前年比で 3 倍になった。その多くが SMB の勢いによる

**プラットフォームの全体像。** Naila 氏は、エージェントを 1 つ作ることと、エージェンティックで拡張できるソリューションを作ることはまったく違う、と強調しています。顧客データへの接続、セキュリティとガバナンスの管理、性能の改善、1 社向けに作ったものを他の顧客に広げる方法、という課題に対し、各製品の役割は次のように説明されています。

| 製品 | 役割（発表での説明） |
| --- | --- |
| Copilot Studio、GitHub Copilot | エージェントを構築する場 |
| Foundry | エージェントの開発・実行・最適化のためのモデルとツールを提供 |
| Microsoft Fabric | データと分析を統合し、顧客がデータを実用的な洞察に変えられるようにする |
| Azure | インフラとスケール |
| Agent 365 | セキュリティ、ガバナンス、管理 |
| Microsoft IQ | 中心にあり、エージェントを組織のコンテキストと知識につなぐ |

**Microsoft IQ。** Naila 氏は、Microsoft IQ を今年の Ignite の目玉の 1 つだとして、あらゆるエージェントを賢くする、顧客のビジネスデータにつなぐ仕組みと説明しています。コンテキストは複数の IQ から来て、それぞれ別の種類のデータに接続されます。

| IQ | 扱うもの |

これらを合わせたものが「顧客の IQ」、つまりその組織固有のコンテキストで、オープンでマルチモデルの、改善し続ける基盤の上にあります。パートナーにとっての価値は、個別の AI ソリューションから、1 つのつながったプラットフォーム上の、より広い managed service の提供へと移れることだとしています。

**パートナーの役割。** エージェントを作る方法は複数あるため、パートナーは顧客が選択肢を整理し、適切な出発点を見つけるのを助けます。そのために、誰が作るのか、どんなビジネス成果を狙うのか、どの技術が合うのかを理解することから始めます。これにより、顧客が選択疲れ（decision-making fatigue）を避け、技術選定から実装へ早く進めるとしています。

**パートナーの実践に必要な 3 つの能力。**

1. 明確な境界と人の監督のもとで、委任された仕事を担えるエージェント
2. 顧客の知識、プロセス、専門性を束ねるビジネスコンテキスト
3. エージェントの性能と ROI を高め続ける継続的な最適化

これにより「1 度作って顧客全体に広げ、継続的なサービス収益を作る」機会が生まれる、というのが Naila 氏のまとめです。

### 5.3 Copilot Studio か、Foundry＋GitHub か：5 つの質問

ここから Jaden 氏が担当します。最もよく聞かれる質問は「どこから始めるべきか」だと述べ、まず身近なシナリオとして、同じ質問に毎日答えている小規模な HR チームを挙げます。1 つのエージェントが、オンボーディング、ポリシーの質問、福利厚生、休暇申請を扱えば、HR は時間を取り戻し、従業員はより速く一貫した回答を得られます。

このエージェントは、**Copilot Studio** でも、**GitHub と Foundry** でも作れます。選ぶための 5 つの質問は次のとおりです。

| # | 観点 | 問い |
| --- | --- | --- |
| 1 | プロセス要件 | 繰り返しのワークフローか、固有のロジックが必要か |
| 2 | データとシステム | 顧客は、すぐ使えるコネクタのある Microsoft 365 上か、自社構築・レガシーのシステムか |
| 3 | セキュリティとコントロール | Microsoft 365 の ID と権限で足りるか、プライベートネットワークやデプロイのコントロールが必要か |
| 4 | 従業員のアクセス | Teams や Copilot などの標準チャネルか、カスタムの Web、モバイル、さらにフロントライン向けの体験か |
| 5 | パートナーの体制 | 高度にカスタマイズするエージェントのために、低コストのスキルや開発者を用意できるか（音声では「low-cost skills」と聞こえます） |

ニーズが標準的なら Copilot Studio、カスタムロジックと厳密な制御（音声では「title control」と聞こえ、表記は確定できません）が必要なら Foundry＋GitHub を指します。大事なのは、各顧客に合う道を選ぶフレームワークを持つことで、「最良の構築とは、その顧客固有のシナリオに最良の成果を出すもの」と述べています。

- **Path A：Copilot Studio** — 特定の業務プロセス向けの、素早くマネージドな道
- **Path B：Foundry＋GitHub** — カスタムロジック、連携、自社 IP のための、より深い道

### 5.4 Path A：Copilot Studio（小規模企業の HR エージェント）

同じ HR エージェントを、2 つの顧客像に当てはめて説明されます。1 つ目は、パートタイムの HR 担当者と、外部委託の IT があり、開発者はいない小規模企業です。HR のハンドブックは SharePoint にあり、従業員は Teams で仕事をしています。Copilot Studio はマネージドなので開発者が不要で、エージェントは SharePoint の内容から、Teams の中で回答します。オンボーディング、ポリシーの質問、休暇の承認は、**数日から数週間で稼働**でき、HR チームの時間を **週 10 時間以上** 節約することを目標にします。パートナーにとっては、拡張の道筋が明確な「クイックウィンの入口オファー」です。

収益の試算は次のとおりです（通貨単位は発話では明示されていません）。

- **2.4K のライセンスの案件が、1 年目のパートナー収益 10K〜18K になりうる。**
- ライセンスとインセンティブは一部にすぎず、価値の大半は、アドバイザリー、エージェントの構築とデプロイ、毎年戻ってくる managed services などの**サービス**から来る。
- そのため、ライセンスを案件のすべてと見ず、顧客の成果を軸にサービスをパッケージ化し、エージェントを継続的に改善していくべきだ、と述べています。

### 5.5 Path B：Foundry＋GitHub（中堅製造業の HR エージェント）

2 つ目は、GitHub で開発している自社の開発チームを持つ中堅の製造業です。HR と給与のデータは **Workday と ADP** にあります。エージェントは HR・給与システムに書き戻し、キオスク、モバイル、Teams を通じて従業員に届く必要があり、ライセンスを持たない交代制の従業員にも対応する必要があります。

そのため Foundry＋GitHub が合うと説明されます。

- Workday と ADP への書き戻しは、カスタム API で処理する。
- エージェントは、ライセンスを持たない作業者を含め、あらゆるデバイスに届けられる。
- 開発者は GitHub 内で、適切なモデルを選ぶ柔軟性を持ちながら、安全に構築・出荷できる。

パートナーにとっては、**パートナー IP、マーケットプレイスの可能性、Azure 消費、managed services** につながります。労力は大きくなりますが、上振れも大きいとされています。

収益の試算：**1 年目の Azure 案件 15K が、パートナー収益 44K〜84K になりうる。** これはクイックウィンの約 4〜5 倍です。Frontier Accelerate（音声では「front to accelerate」と聞こえます）のようなインセンティブも助けになりますが、ここでも価値の大半は、カスタム構築、連携、managed services といったサービスから来ます。

**2 つの道の比較。** Copilot Studio は軽く素早い最初のプロジェクトで、扉を開くのに向いています。Foundry＋GitHub は労力も開発スキルも必要ですが、上振れが大きい道です。どちらでも Microsoft IQ により、エージェントは初日から顧客のビジネスを理解します。

### 5.6 Foundry と GitHub Copilot が埋めるギャップ

Jaden 氏は、**Foundry** について、「素晴らしいエージェントのデモが本番に届かない」という、多くの人が経験したことのあるギャップを埋めるためのものだと説明します。

- プロトタイプを超えて、数千のモデルから選べる。
- 先の Workday や ADP のような実際のエンタープライズデータでエージェントを grounding（根拠づけ）できる。
- 組み込みの評価（evaluations）とトレーシングで、本番前に精度と安全性を顧客に示せる。性能とコストは継続的に調整できる。
- Azure 上で作ったエージェントは再利用でき、各デプロイが**パートナーの IP と継続収益**になる。

「Foundry はデモとビジネスの違いを生む」というのが要約です。

もう 1 つの落とし穴は、すべてのプロジェクトが単発になってしまうことです。**GitHub Copilot** は、開発者がすでに使っているリポジトリとワークフローの中でエージェントを作り、Copilot がコードを書き、テストを実行するのを助けます。すべての変更が自動でテスト、レビュー、デプロイされるため、1 社向けの修正が他社を壊しません。作ったコンポーネント（プロンプト、スキル、コネクタ）は、すべての顧客と次の案件で再利用するライブラリになります。その結果、10 本目のエージェントは、最初のものより「ずっと速く、ずっと収益性が高く」なるとしています。

### 5.7 エージェントの連鎖と managed services

どちらの道から始めても、最初のエージェントは始まりにすぎません。顧客での成功が信頼を生み、次の会話を容易にします。例として、HR エージェントから、売掛金（account receivable）、販売予測、カスタマーサポートへと広がる流れが示されました。**4 本目のエージェントの時点で、継続収益が約 14.5K になり、複数のエージェントを管理することでマージンを倍にできる**とされています。ただし、この数字は **illustrative（例示）** で、本当に言いたいのは「複利で増える」ことだと断っています。エージェントごとに売りやすく、サポートも速くなります。

こうしたエージェントを継続収益に変えるのが、managed services です。実践の組み立て方は次のとおりです。

1. すでに提供しているオファーにエージェントを組み込む。
2. 自社 IP を使ったカスタムエージェントを作り始める。
3. それをさらに多くのシナリオに広げる。

各段階で価値とマージンが増え、チューニング、セキュリティ確保、ガバナンスなど、各エージェントに関わる managed services が続きます。エージェントはコストが時間とともに増えるため、支出を抑える **AI FinOps** も新たな managed services の機会になると述べています。**CSP であれば、顧客との関係と請求（billing）をパートナー自身が持てる**ため、顧客のエージェントの使われ方を見て、支出を最適化し、次の機会を見つけられます。これにより、プロジェクトが継続的な顧客関係に、単発の収益が継続収益に変わる、という説明です。

最後に、これには技術だけでなく、パートナー自身の実践を進化させる必要があるとして、次の 3 つの進化を挙げています。

- エンドツーエンドの成果をリードする
- 経済モデルを転換する
- AI を使うパートナー（AI-powered partner）になる

（発表では、この 3 点の詳細な説明は行われていません。）

### 5.8 パートナースポットライト：RSM との対談

Microsoft 側の登壇者が、「Microsoft の人間には簡単に言えるだろう、パートナーの実践を運営しているわけではないから」という疑問を挙げ、日々それを行っているパートナーとして RSM の 2 人を招きました（この発言の話者は特定できません）。

**Customer Zero。** 対談の進行役は、「SMB はもうパイロットを必要としていない。本当にスケールするソリューションを求めている」という前置きで、Customer Zero の話に入りました。Pat 氏の説明では、Customer Zero とは、**顧客に提供するツールを自分たちで使うこと**です。

- 社内のワークフローを見て、GitHub や Copilot Studio などのどれを使うかを特定し、そのモデルを活用し始めた。
- 複数のサービスラインやチームで同じ繰り返しが見えてきたため、顧客に持ち込む際にも、学んだことを活かして、業界をまたいで似たソリューションを展開できる。

Dolly 氏によると、Pat 氏は先週、顧客向けに「どのツールをいつ使うか」のセッションを開催し、大勢の参加がありました。多くの顧客がこの問いに悩んでいます。進行役は、「自分たちもこのツールを使っていて、こういう効果を得ている」と顧客に伝えることほど強力なことはない、と応じました。

**エグゼクティブスポンサーシップ。** RSM の登壇者は、社内でも顧客でも同じくらい重要だと答えています。顧客と話すときは、AI で何がうまくいき何がうまくいかないか、どのビジネスプロセスが対象か、といった会話のために、経営層を連れて来たり、例を持ち込んだりします。また、先の Path A と Path B の話で共感したのは、システムが分断されていることで、HR システムが ADP や Workday の場合、Copilot Studio から得られるほど構造化されていない、これは自社でも同じ課題だと述べました。続けて、「作る」「ツールを買って現場に作らせる」という話より、**経営層の賛同（buy-in）が重要**で、顧客の多くは「どこから始め、どうするか」で悩むため、経営層と「どんな成果を解くのか」を一緒に決めることが大切だと補足しています。Microsoft が言う「技術をサイロで売るのではなく、ビジネス成果で売る」という考え方につながり、パートナーはそれをどう助言するかが問われる、という話でした。

**ビジネスモデルと人員体制。** AI は、RSM の顧客への関わり方を変えたと Pat 氏は述べています。

- managed services の側面：agent managed services や Copilot managed services が変化の 1 つ。
- 提供の面：アセスメントで、ビジネスプロセスの情報を集め、顧客がどの道を選ぶべきかを特定する際にも AI などのツールを使っている。これは人員体制や提供モデルにも関わる。

Dolly 氏は、サービス会社全体としてビジネスモデルが変わったと述べます（かつては時間と経費（time and expenses）が中心だった）。いまの顧客は「1 時間あたり数百（通貨は明示なし）」という標準的な請求ではなく、「一緒に取り組んでほしい」と求めており、RSM のリーダーシップは、時間ではなく顧客の課題に焦点を当てたオファーを作っているとのことです。Pat 氏も、日常生活で AI を使うときと同様に、顧客は同じかそれ以上の成果を期待するため、time and materials モデルより成果に焦点を当てた形になっている、HR エージェントでも、document intelligence などを使ったカスタムエージェントでも成果が焦点になる、と答えました。

**Marketplace。** RSM にはかなり充実したマーケットプレイスの掲載があるものの、一部は古くなっていたため、リーダーシップが今年の初めに全体の棚卸しを決めました。AI エージェントの機能も含めて最新にしています。社内で作った IP や資料を、マーケットプレイスに出して顧客が使えるようにすることは、アライアンス戦略の大きな部分です。Microsoft の営業と話すときは、その年の Microsoft の会話に合わせた最新のオファーを知ってもらいたいとしています。SMB では Microsoft の営業は多くないため、SMB の vendor チームなどと連携しつつ、多くは自社で動いています。また、パートナー主導で Partner Center に載せる話が、先のセッションで取り上げられていたことにも触れています。

**Foundry による再利用。** Pat 氏によると、顧客の技術スタックはどれも複雑です。Foundry を使うことで、自社開発の CRM や ERP のようなものに出会ったときも、そこで得た知見を他のクライアントに繰り返し適用でき、より一貫した、強いデリバリーモデルが可能になった、とのことです。

**月曜日に最初にすべき 1 つのこと（パートナーへの助言）。**

- Pat 氏（認定トレーナーの立場から）：**教育**。営業チームから技術チーム、さらに顧客まで、組織全体で、何ができるか、何が使えるか、それがプロセスをどう変えうるかを学ぶこと。
- Dolly 氏：たくさんの情報が提供されている中で、まず座って「パートナーシップとして何に注力するか」を決めること。新しい能力を作るのか、CSP を行うのか。社内のストーリーと戦略を固めてから外に出てソリューションを作らないと、顧客に「やめるよう」言っている単発（one-off）の取り組みになってしまう。戦略という言葉が嫌われがちでも、「ステップ 1、2、3」としてどこから始めるかを決めることだと述べています。

### 5.9 Q&A

対談のあと、会場から 3 つの質問がありました。質問者の声は録音で聞き取りにくく、回答の内容から質問を整理しています。回答は主に Pat 氏です。

**Q1. time and materials から成果ベースの課金へ移る際の考え方**（Pat 氏が質問を言い直す中で、Baker McKenzie の法律事務所のケーススタディに触れています）

- エージェントは、最初の顧客のための構築に多く投資し、それを他の顧客に繰り返すことで、より長期の成果ベース課金につなげられる。
- managed services も、最初の案件で出た超過分を取り戻す手段になる。
- 1 本目、2 本目、3 本目のエージェントでは、どれだけの時間と労力がかかるかを把握する間、**やや小さいマージンを受け入れる必要**がある。
- time and materials は予測しやすく、保護が厚い。成果ベースは、研修、必要な人員、パイプラインの計画を立てやすい。両方に長所と短所がある。
- 最初の 1 回目は time and materials でデプロイまでにかかる時間を把握し、そのあと素早く成果ベースの案件に転換することを勧めている。

**Q2. 成果ベースのアプローチで、請求可能な作業と請求できない作業の境界をどこに置くか**

- スケールが 1 つの論点であり、新しいモデルなどが出るたびに多くの学習がある。
- その学習を managed services の側に移すことを挙げている。
- 従来の managed services はコアのインフラが中心だったが、カスタムエージェントを作れば、それはソフトウェアになる。「ヘルプデスクに電話して助けてもらう」では済まず、ファインチューニングのような調整が必要になる。
- 学習を managed services の枠に入れることで、より強い人材とスキルを持ち、より速くデリバリーできるようになる。

（発表では、請求可能・不可能の線引きそのものを示す具体的な基準までは語られていません。）

**Q3. agent managed services は、Foundry が動くようなマネージドクラウドプラットフォームの一部として含めるのか**

- 顧客ごとに異なる。エージェントの managed services を単品（a la carte）で提供する場合もあれば、スケール、研修、定着に重点を置く managed Copilot、さらに Agent 365 と「E7 スタック」（音声での表記）を活用する場合もある。
- SMB や SME の領域では、完全な managed services も一部の組織にとって同様に重要。
- 組織が大きくなり、自前の開発者がエージェントを管理できる場合は、パートナーからは助言が中心になり、a la carte に近くなるのが、RSM の経験だという。

### 5.10 Microsoft の支援策と次のアクション

Jaden 氏は、パートナーが 1 人で進める必要はないとして、各段階での支援を挙げています（名称は音声認識で崩れている箇所があります）。

| 目的 | 支援 |
| --- | --- |
| スキル | ロールベースのトレーニング、AI boot camps、パートナー特典パッケージ（チームがスコープ・設計し、顧客に出せるエージェントを提供するための支援。まず自社ビジネスで AI を使うところから） |

スライドにすべてのリンクがあり、これらのリソースを 1 か所にまとめたものが **SMB partner playbook** です。さらに深く知りたい場合は、Ignite の期間中に Microsoft AI Cloud Partner Program のセッションが多数あります。

## 7. 注意点・発表者の気付き

- **技術選定を製品起点で決めない。** 最適な道は、顧客のシナリオと必要な成果で決まります。5 つの質問のようなフレームワークが必要です。
- **ライセンスを案件のすべてと見ない。** 収益の大半は、アドバイザリー、構築・デプロイ、毎年の managed services から来ます。
- **単発案件にしない。** 1 社向けに作ったものを、リポジトリ、プロンプト、スキル、コネクタとして再利用できる形にしないと、プロジェクトが単発になります。
- **デモと本番の差。** 優れたエージェントのデモが本番に届かないことがあるため、評価とトレーシングで精度と安全性を示すことが必要です。
- **エージェントのコストは時間とともに増える。** そのため、AI FinOps も managed services の機会になります。
- **成果ベースへの移行にはリスクがある。** 最初の数本のエージェントは、時間と労力が読めないため、小さめのマージンを受け入れるか、最初は time and materials で測る、というのが RSM の助言です。
- **試算の前提。** 14.5K の継続収益は例示（illustrative）の数字で、10K〜18K や 44K〜84K といった収益も試算です（通貨単位は発話で明示されていません）。
- **経営層の賛同と戦略。** 顧客でも自社でも、経営層の賛同が重要で、パートナー自身も戦略を決めてから動かないと、顧客に避けるよう言っている単発の取り組みになります。

## 8. 利用者にとっての利点

発表で語られた、パートナー（および最終顧客）にとっての利点は次のとおりです。

- **顧客（Path A のシナリオ）：** HR チームが、数日〜数週間で稼働するエージェントにより、週 10 時間以上の時間を取り戻す（目標値）。従業員はより速く、一貫した回答を得る。
- **顧客（Path B のシナリオ）：** Workday と ADP への書き戻し、キオスク・モバイル・Teams、ライセンスを持たない交代制の従業員を含むあらゆるデバイスへの提供ができる。
- **パートナー：** 4 分の 1 しか取れていない機会の拡大、Path A で 10K〜18K、Path B で 44K〜84K の 1 年目収益（試算）、再利用による 10 本目のエージェントの高速化と高収益化、managed services による継続収益。
- **事例：** Call Reboot（ディーラー全体でのリード転換の増加）、Qualis Service（1 分あたり 500 万件の税関連ドキュメント処理）。RSM は、同じ経験を業界をまたぐ展開に活かしている。

## 9. まとめ

BRK487 は、SMB 向けの CSP パートナーに対し、AI エージェントを「作って売る」だけでなく、**再利用と managed services で継続収益に育てる**ための考え方を示したセッションです。Forrester の試算では、小規模企業 1 社あたり 3 年で 95,000 ドルの機会のうち、パートナーが取れているのは 4 分の 1 にとどまります。

選択の軸は、Copilot Studio（素早く管理された道、HR 例で 2.4K のライセンスから 10K〜18K）と Foundry＋GitHub（カスタムロジックと自社 IP の道、15K の Azure 案件から 44K〜84K）の 2 つで、5 つの質問と顧客の成果で選びます。RSM の事例からは、Customer Zero として自社で使うこと、経営層の賛同、時間課金から成果ベースへの移行、Marketplace の整備が語られました。まず「1 つのエージェント、1 社の顧客、1 つの成果」で 60 日以内にパイロットを始めることが、発表の呼びかけです。
