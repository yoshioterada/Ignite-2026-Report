# THRSP1066 Build an intelligent search pipeline for grounded AI

## 1. はじめに

このセッションは、検索パイプラインの品質を上げるために、Cohere が提供する 3 つのモデル（**Parse**、**Embed**、**Re-rank**）を紹介する約 14 分の短い登壇です。3 つとも Microsoft Foundry で利用できます。

登壇者の主張は明快で、「ユーザーに正しい答えを返すには、まず正しいパッセージを検索で取り出せなければならない」というものです。そこで、検索パイプラインを「文書の取り込み（Parse）」「ベクトル化（Embed）」「検索結果の並べ替え（Re-rank）」の 3 段階に分け、それぞれに専用モデルを当てる考え方を、デモと顧客例（Nike、Boeing）を交えて説明します。

このセッションでは、Parse のライブデモが行われ、Embed と Re-rank についても画面を使った実例が示されました（6 章）。

## 5. 発表内容の詳細

### 5.1 Parse モデル

Parse は、視覚的なパースや OCR が必要な場面で使うモデルです。文書からテキストを抽出するだけでなく、チャート、表、グラフなどの視覚要素も抽出し、検索インデックスに渡せる構造化された出力を返します。業種を問わず使え、デモでは医療分野で見かける文書が使われました。

登壇者は、Opus のような大規模 LLM でも視覚的なパースはできると認めたうえで、課題は大規模なデータセットに使うとコストが非常に高くなる点だと述べています。そこで Cohere は、出力品質は大きなモデルと同程度で、TCO を下げられる専用モデルを作る戦略を取っています。登壇者は画面の右側を指し、大きなモデルに比べてはるかに安価で効率的だと説明しました。特に超大規模なデータセットで効果があるとのことです。

また、Microsoft のテクノロジストである Mohamed 氏（名前は聞こえたままの表記です）が、Cohere のモデルを Mistral OCR4（音声認識の都合で正確な名称が確定できません）と比較評価し、いくつかの評価で Cohere のスコアが高かったと紹介されました。登壇者はこれを、専用モデルへの注力が価値を生んでいる例としています。

### 5.2 Embed モデル

従来は、テキストのベクトル化には OpenAI のテキストモデルのようなモデルを使い、画像やマルチモーダルには別のモデルが必要になることがありました。Cohere Embed は、**テキストと画像の両方をネイティブに扱い、1 つのモデルで統一されたベクトル空間にベクトルを生成** します。

背景として、チャートやグラフ、画像の中に閉じ込められたデータが多い点が挙げられています。テキストでも視覚的な表現でも、正しい情報を取り出せるようにすることを重視したという説明です。

登壇者は、次の 2 つの例を挙げました。

**Nike（EC・小売、ファッション）**

ユーザーが探したい商品のイメージを持っている場面を想定しています。テキストと画像の両方でマッチングでき、完全一致、2 番目、3 番目に近い結果が順に表示されます。

ただし、ユーザーが画像全体と一致させたいとは限りません。アップロードした画像の中で帽子だけを探したい場合は、画像全体ではなく、「黒い帽子」というユーザーが気にしている部分に焦点を当てて検索できます。登壇者は、正しい結果が出てユーザーがクリックし、カートに入れるかどうかは、完全に計測できる指標だと述べています。

**Boeing（製造）**

Boeing には、1 つの PDF が約 800 ページに及ぶ大規模な整備（repair）マニュアルがあります。技術者が、あるつまみのページを覚えていなくても、iPhone で撮った写真があれば、その部品が載っている PDF のページを特定できます。入力は画像でもテキストでも、両方の組み合わせでもよいとのことです。実際の PDF を開くと、巨大な PDF の中から該当ページに移動でき、それが正しいページであることが示されました。

**Fast と Pro**

Embed には Fast 版と Pro 版の 2 種類があります。共通の仕様は次のとおりです。

- 100 言語に対応
- 次元数と圧縮を設定可能
- 価格はスライドに表示（金額は音声では読み上げられていません）
- Voyage や Gemini など競合の強力なモデルと、同じ種類のデータセットで比較し、高いスコアを出した

2 つのモデルは同じベクトル空間にあるのが特徴です。最高品質が必要な用途には Pro、スループットとレイテンシーが重要な用途には Fast を選びます。さらに同じベクトル空間なので、**インデックス作成側では Pro で最高品質のベクトルを作り、検索側では Fast でレイテンシーとスループットを最大化する** という併用ができます。

### 5.3 Re-rank モデル

Re-rank は、既存の検索システムを残したまま使えるモデルです。登壇者は、検索基盤が Elastic、Pinecone、Azure AI Search のいずれであっても、残す判断をしてよいと述べています。Re-rank は最初の検索結果を受け取り、ユーザーのクエリに基づいて再スコアリングして、より良い順位付けを返します。

必要になる場面として、次の 2 つが挙げられました。

1. **数値推論**：ユーザーが「130 センチメートルより低いスタンディングデスク」を探すケースです。スライドの左側の他社 Re-ranker は 130 のものを返しますが、それは正しい答えではなく、「130 以下」を取得すべきだと説明しました。右側の Cohere の Re-rank の方が効果的だと述べています。
2. **複雑な推論**：1 つの検索に複数の側面（multi-aspect）が含まれるケースです。

### 5.4 Re-rank の Nike デモの説明

単純な「shoes」の検索（登壇者は head query と呼びました）では、ベクトル検索でも Re-rank でも結果は同じで、Re-rank の価値は出ません。より複雑な「80 ドル未満の女性用の靴」で検索すると、ベクトル検索のみ（左）では女性用の靴は返りますが、80 ドル未満かどうかは満たされません。Re-rank を使った右側では、女性用の靴で、なおかつ価格条件も満たす結果が返りました。

このクエリには、「靴」という商品タイプ、「女性用」という性別、「80 ドル未満」という数値の 3 つの側面があり、可能な限り 3 つすべてを満たしたい、という説明です。

Re-rank にも Fast 版と Pro 版があり、複数のデータセットでスコアを比較しました。比較対象として Voyage と Gwen（音声認識の都合で表記が確定できません）が挙げられ、競争力のあるスコアが出ていると述べています。

### 5.5 まとめと案内

登壇者は、Parse、Embed、Re-rank の 3 モデルがすべて Microsoft Foundry で利用でき、Cohere が Microsoft のパートナーであることを述べました。Cohere はカナダの会社で、多様なモデルを作っており、この 3 つはその一部です。他のモデルも Microsoft で利用できます。質問がある場合は、ブース 5539 に立ち寄ってほしいとのことでした。

## 6. デモ・手順

### 6.1 Parse のライブデモ

登壇者は「ライブデモをします」と述べて実演しました。画面の細部は音声から確認できないため、語られた範囲で、順に記します。

1. 医療分野で見かける文書を選び、パース処理を開始する。
2. 画面中央にテキストが抽出される。左のロゴと右のロゴといった視覚要素も、モデルが説明として出力する。
3. 2 ページ目にはチャートがあり、チャートも要素として抽出される。
4. 3 ページ目にはテキストと表がある。左側に、テキストだけ、表だけ、または両方を抽出して表示できる。

登壇者は、この高品質な視覚的抽出結果を検索パイプラインに渡せると述べています。

## 7. 注意点・発表者の気付き

- 大規模な汎用 LLM でも視覚パースはできますが、大規模データセットではコストが大きな課題になる、と登壇者は述べています。
- 数値条件を含むクエリ（130 センチメートル未満など）や、複数の側面を持つクエリは、Re-rank が効く場面だと説明されています。実際、Nike の例ではベクトル検索だけでは価格条件が満たされませんでした。
- 既存の検索システム（例として Elastic、Pinecone、Azure AI Search が挙げられました）を残したまま、Re-rank で結果を再スコアリングする構成が取れます。
- 検索側では、インデックス作成と同じ Embed モデルでユーザーの入力文字列をベクトル化する必要がある、と冒頭で述べています。なお、同じベクトル空間にある Fast と Pro は組み合わせて使えます。
- 発表では、Foundry 上での具体的な導入手順、料金の金額、各ベンチマークの数値は触れられていません。

## 8. 利用者にとっての利点

- **Parse**：文書内のテキスト、チャート、表などの視覚要素を、検索インデックス向けの構造化出力にでき、大規模データでも大きな LLM より低い TCO で運用できる、と説明されました。
- **Embed**：テキストと画像を 1 つのモデルで同じベクトル空間に載せられます。Nike の例では画像内の「黒い帽子」だけを検索対象にでき、Boeing の例では 800 ページ規模の PDF から、写真を手がかりに該当ページを特定できました。
- **Fast / Pro の併用**：インデックス側は Pro、検索側は Fast と使い分けて、品質とレイテンシー・スループットの両立を図れます。
- **Re-rank**：既存の検索基盤を保ったまま、「女性用で 80 ドル未満の靴」のような複合条件の検索精度を高められます。

## 9. まとめ

検索パイプラインの目的は、AI が答えるために正しいパッセージを取り出すことです。Cohere は、そのための 3 つの専用モデルを Microsoft Foundry で提供しています。Parse は文書の視覚要素まで構造化して抽出し、Embed はテキストと画像を同じベクトル空間で扱い、Re-rank は既存の検索基盤の結果を、数値条件や複数の側面を持つクエリに合わせて並べ替えます。Embed の Fast と Pro は同じベクトル空間のため、インデックス側と検索側で使い分けられます。詳細はブース 5539 で聞けます。
