# THRSP1158 Model Frontiers: Ask more of Claude in Foundry

## 1. はじめに

このセッションは、Anthropic の Applied AI Architect が、Microsoft Foundry 上で Claude を使う開発者・チームに向けて、「新しいモデルが出るたびに、頼める仕事の範囲も広がる。それなのに多くの人は以前のモデルに頼んでいたのと同じ小さな仕事ばかり頼んでいる」という問題を扱う約 25 分の登壇です。

登壇者の提案は 3 つの「アップグレード」です。**(1) 基準（bar）を決め、それを満たすモデルを選ぶ**、**(2) 仕事を細切れにせず、まるごと任せる**、**(3) 結果と品質を自分の管理下に置く**。後半では、8 社の給与計算ベンダーの提案書を Claude に評価させる事前収録のスクリプト実行例が示され、ここで 3 つのアップグレードがどう適用されるかを説明します。モデル選択の目安、コストの考え方、Foundry での提供状況（compaction は beta など）も語られます。

## 5. 発表内容の詳細

### 5.1 frontier とは、去年見送った仕事の再評価

登壇者は、新しいモデルごとに考え方も変える必要があり、しかも私たちは以前のモデルに頼んでいたのと同じ仕事を新しいモデルにも頼み続けている、と指摘します。見送った理由として挙げたのは、ジョブの手順が多すぎた、曖昧すぎた、結果の確認に、自分やチームが作業するのと同じだけ時間がかかった、の 3 つです。対象は、チームで 1 週間かけて作るレポートのような日常業務から、科学者が取り組むような未解決の問いまで幅広いとしています。

### 5.2 frontier な課題の例

**Earthrise（Opus 5.5）**：1968 年のクリスマスイブに Apollo 8 から撮影された、月周回軌道から見た地球の写真です。この写真について、Opus 5.5 に「いつ、どこで撮影されたか」を尋ねたとのことです。フィルム写真には日時も場所も書かれておらず、月の地平線とその上の地球という手がかりから、1 つの地点・時刻を割り出す必要があります。登壇者は、これを見せる動画を上映し、Claude が**約 3,000 の点**をたどり、NASA と "Japan Space Agency"（登壇者の発言どおり）の地図を参照して、**秒単位の正確な時刻**と、**月面の約 70 マイル上空**という位置を特定し、その場面を 3D で再構成する様子を説明しました。ミッションレポート、雲のデータ（音声は "cloud data"）、海底地形図、計算を使ったとのことです。曖昧で、データと判断点が多い課題の例だと説明しています。

登壇者は、ほかに 3 つの公開済み事例を紹介しました（参考としての紹介です）。

- **設計**：Fable 5.2 に、スピーカーフォンのようなものの短い説明を与え、3 つの動作するプロトタイプを開発させました。基板、ソフトウェア、筐体までを設計したとのことです。
- **公衆衛生**：WHO のアフリカチームが、コンゴ東部でのエボラの広がりを日次報告として公開していました。Claude が日々の報告の差分を検出し、1 日がかりだった作業が 1 時間未満になったと述べています。
- **科学**：研究室の機器を AI につなぐ標準（research preview）が出ており、数週間から数か月かかっていたものが数時間から数分になります。7 つのプログラムが必要だったセットアップも、より簡単になるとの説明です。

登壇者は、どの事例でも「誰かがその結果を確認できる」点を挙げ、フロンティアを語るなら、人間による監督を強め、安全にどう取り組むかも語る必要があると続けました。

### 5.3 Anthropic の安全への取り組みと Foundry での利点

Anthropic は public benefit corporation であり、frontier AI の会社です。登壇者は、**研究、安全、プロダクトが連携し、中心に顧客がいる「フライホイール」**があると説明します。安全面では、2023 年に責任ある AI スケーリングに関する方針（登壇者の言葉では "public policy for scaling AI responsibly"）を公開したと述べました。プロダクトでは、ソフトウェア向けの Claude Code と、ツールやデータをつなぐ MCP が出発点です。顧客から学んだことは研究に戻され、Anthropic は最初から企業向けに作られている、とも述べています。

Microsoft と責任ある AI の開発という共通のコミットメントを持つことを誇りに思う、と述べ、Anthropic と Foundry の顧客の例として、安全が最優先の原子力会社 **Everstar** を挙げました。Everstar は Foundry で Claude モデルを（他のモデルとともに）使っており、Anthropic の使命とモデルに組み込まれた価値観が、Foundry 上の Claude への信頼を強めた、と説明しています。

エンタープライズで Claude を使う利点として、登壇者は次を挙げました。

| 観点 | 内容 |
| --- | --- |
| 確認できること | 引用（citations）が出典に戻る。各モデルに system card がある |
| スケール | Foundry で global standard と US data zones がある |
| 既存資産の活用 | MCP とエージェント用の agent SDK など、チームが使っているものを使える |
| Azure との適合 | Entra ID でも Azure roles でもセキュリティロールを使え、使用量は 1 つの Azure 請求書に反映される |

Microsoft Foundry カタログで使えるモデルは一般提供（GA）で、1 つの API の利用量として引き落とされると説明しています。

### 5.4 モデルの使い分け

登壇者は、先週発表した Fable 5.2 が、金融、ソフトウェアエンジニアリング、ヘルスケアとライフサイエンスといった分野の、より複雑な仕事に向けて開発が進んでいると述べ、4 つのモデルが API で利用できると話しました（"I imagine"（私の想像では）と前置きしています。また Fable は "hosted on Anthropic in Foundry today" と発言しており、ホスト形態の詳細は聞き取りでは確定できません）。使い分けの目安は次のとおりです。

| モデル | 向いている仕事 |
| --- | --- |
| Haiku（最小のモデル） | 大量処理、または誰かが応答を待っている場面 |
| Sonnet | 速度と知能のバランス |
| Opus | 長めのジョブ、エージェント型のコーディング、ナレッジワーク |
| Fable | より複雑で長期（long horizon）の仕事 |

どこから始めるか迷う場合は、Opus 5.5 で始めて自分のテストで品質を評価し、基準を満たすモデルが見つかったら一段下げていく、という進め方を勧めています。

ソフトウェアの仕事で言い換えると、Haiku は 1 ファイルや素早いタスク、Sonnet は機能を端から端まで、Opus はシステムの設計とコードベースの理解、Fable はコードベース全体にまたがる作業や中核プラットフォームの再設計、という段階になります。図には「beyond the frontier」という領域があり、これは AI の分野での未解決問題で、Claude の予定機能やロードマップではない、と断っています。

### 5.5 想像力がボトルネック、そして capability overhang

登壇者は、フロンティアが動き続けると、「1 年前に有効だったので、ジョブを小さく分けて頼む」という習慣が残る問題が出てくると述べ、**ボトルネックは Claude に何を頼むかという私たちの想像力**だと強調しました。簡単な演習として、チームが今は細切れにしている仕事を 1 つ選び、Foundry の Claude に全体を任せたらどうなるかを想像するよう促しています。

聴衆に、過去 1 か月に「このバグを直して」「マージコンフリクトを解決して」あるいは文書の要約のような依頼を入力した人を挙手で尋ね（登壇者自身も該当）、これが一般的な依頼だと述べました。右側の列は、同種の仕事を今年のスケールで行う例で、初期のテスターや顧客に見られる方向性だと説明されました。**1 つのジョブの結果であり、結果は異なる場合がある**と断っています。

| いつもの依頼 | 今年のスケールでの依頼 |
| --- | --- |
| このバグを直す | 20 万行のコードを 3 時間未満で監査して修正する |
| 関数を移植する | 数十万行のコードベースを 1 日未満で移行する |
| 要約する | 規制当局や専門家のレビューに向けて準備できる、ライセンスに関する文書を作る（Foundry の他のモデルも使用） |

登壇者は、ロードマップにあるのに、複雑すぎる、曖昧すぎる、で手が回らなかったプロジェクトこそ、新しいシリーズのモデルで試す候補だと述べました。この「もっと頼んでいない」というギャップを、Anthropic は Claude Code の使われ方の研究で見つけ、**capability overhang** と名付けたと述べています。

登壇者が顧客から聞く質問は 3 つで、「このタスクにはどのモデルを使うか」「本当にその仕事を丸ごとこなせるか」「結果が本当に良いと、どう確認し、自信を持つか」です。「信頼がデプロイとスケールの鍵だ」という理由から、これを妥当な懸念としています。これに対する 3 つのアップグレードが、以降の構成です。

### 5.6 アップグレード 1：基準を決め、それを満たすモデルを選ぶ

登壇者は、社内で行った 3 モデルのテストを紹介しました。課題は、ある企業の四半期のレポートをまとめることです。決算発表が見つけにくい企業を選び、モデルに「Web のコピー」を渡してレポートを作らせました。このテストの特徴は、**良さの基準が非常に厳しい**ことです。自動採点（automated grader）が、すべての数値、事実、引用を確認し、でっち上げが 1 つでもあればその実行は失敗となります。

結果として、**Opus 5.5 は 18 回中 16 回で基準を満たしました**（異なる effort 設定をまたいだ結果）。Fable 5.1 と Opus は、正確さの基準を満たせませんでした。登壇者は、自分たちで行った 1 つのテストだと断ったうえで、**簡単な仕事はモデル間で差が出にくく、複雑な仕事で正確さの差が出る**ので、何が良いかを厳密に採点する仕組みが重要だと述べています。

ビジネスの例として、回答が表面上は自然に読めても、ポリシーとしては間違っている、または一貫していない場合を挙げました。キーワードや書式を見るルールベースのチェックは通ってしまうことがあります。一方、**Claude を判定役（judge）として使い、回答を読むだけでなく、ポリシーや正解（ground truth）と照合させる**と、良し悪しをよりうまく見分けられます。

ベストプラクティスは、**モデルを選ぶ前にこのテストを書く**ことで、モデル選択の助けにもなります。進め方は次のとおりです。

1. エージェントが普段間違える実際のケースを 20〜50 件用意する
2. 合格がどういうものかを書き出す
3. その分野の専門家 2 人が同意できるものを、合格とする

これが、エージェントに設定すべき基準（bar）です。基準が決まれば、使うモデルを決めやすくなります。

### 5.7 アップグレード 2：仕事をまるごと任せる

**Fermat の定理の例**：17 世紀に Fermat が本の余白に「証明を持っているが余白が狭すぎて書けない」と書いたという話です。登壇者は、「Anthropic らしく」、これはエージェントに解かせるのによい問題だと考え、**1,000 体の Fable 5.2 エージェント**に、定理をコンピューターが検証できる形で、コードとして表現させたと述べました（音声は "normalized that theorem" で、formalize を指すと考えられますが、この箇所では確定できません。後段で登壇者は "formalizing theorems" と言っています）。結果は、**最小限の人手で 30 時間**で完了しました。長期かつ複雑な仕事を任せられる例です。

次に、より日常的な業務の例として、**架空の給与計算ベンダー 8 社の提案書（各約 50 ページ）**が示されます。最後に Claude に 1 つの推薦を出してほしい、というシナリオです。5.8 のとおり、基準を決め、仕事を任せ、良さを定義し、最後に確認する流れが紹介されました。

### 5.8 ベンダー提案書の評価（スクリプトの実行例）

登壇者は、この実行例を次のように説明しました。スクリプトは Foundry の Opus 5.5 を呼び出します（登壇者は "it's not Claude or Cowork" と明言しています）。数回の実行ログから作成した、**リアルタイムではなく短縮した**ものです。詳細は 6 章に書きます。

ここでは、登壇者が語った**依頼（brief）の組み立て方**を整理します。

| 要素 | 内容 |
| --- | --- |
| 成果を最初に定義 | 8 件の提案書から 1 つの推薦。完了とは 64 個の回答（8 ベンダー × 8 の must-have 基準）を出すこと |
| 環境 | 提案書は読むだけで変更しない。Claude が書く出力は別の notes フォルダーに保存し、原本を変えない |
| 権限と予算 | 何ステップ、何トークンまで使えるかを決め、費用を追跡する |
| 提案書ごとのメモ保存 | 各提案書の後にメモを保存して確認に使う。Claude の記憶とコンテキストを助け、自分の仕事を途中で点検でき、ミスを早く見つけられるので、直すコストが下がる |

もう 1 つの半分が **system prompt** です。登壇者は、新しいモデルでは多くの人が「二度確認して」「徹底的に」「ステップごとに考えて」といった指示を足すが、ベストプラクティスは**足すのではなく、まず行を削る**ことだと述べました。たとえば「二度確認して」は、新しいモデルでは文字どおりに受け取られ、毎回複数回確認する可能性があります。Anthropic のベンチマークで、Claude Code 内でこの "scale prompt audit"（音声のとおりの表記で、正式名称かは確定できません）を行ったところ、**コストが平均でさらに 9% 下がった**と述べています。system prompt の各行について、「この行はどのモデル向けに書かれたか」「今のモデルに合っているか」を考えるよう勧めています。

仕事を軌道に乗せる追加の設定として、次の 3 つが挙げられました。

- **effort**：Claude がどれだけ頑張るか、どれだけ深く考えるかを決める設定で、費やす時間とトークン数にも影響します。基準を決める段階で作ったテストに合格する、**最も低い effort** を選びます。
- **context**：設定した上限を超えたとき、古い部分が要約され、ジョブが続きます。
- **memory**：Claude 自身が、アプリ側が管理するファイルに残すメモです。コンテキストが集中し、学んだことが次のジョブに引き継がれます。

提供状況として、Foundry では現在、**compaction は beta**、**effort と memory のツールは一般提供（Azure 上でホスト）**だと述べています。

### 5.9 アップグレード 3：結果を管理下に置く

Claude が「終わった」と言ったとき、本当に完了していて品質が良いと、どう分かるか。登壇者は、基準が戻ってきて、brief がそれを記述し、スクリプトがそれを確認できる、と述べます。先の実行で、Claude は 64 個のスコアのうち 1 つを外しており、完成したように見えて正しくなかった、という例を挙げました。

Claude は自分のジョブとして単独で動きましたが、途中に **4 つのコントロール**がありました。

| コントロール | 内容 |
| --- | --- |
| scope（範囲） | 触れるもの。提案書は読めるが、書けるのは notes フォルダーだけ |
| sandbox | 実行される環境。封じ込められており、ターン数とトークン数の上限で費用も制御する |
| log（記録） | 何をしたか。毎ターンが記録される。トレースを Azure Monitor に送り、どこで何がうまくいかなかったか、どのモデルを使ったか、何トークン消費したかを調べられる |
| gate（関門） | 誰が決めるか。元に戻せないこと（シナリオで最も重要なもの）は人が承認する。この関門は、プロンプトの中だけでなく**コードの中**に置くことを勧める |

### 5.10 コストの考え方

登壇者は、トークンの単価ではなく、**完了したタスクあたりのコスト**で評価するよう勧めています。自社のユースケースでテストするときは、各タスクのコストと、うまくできた度合いの両方を記録し、**合格する中で最も低コストの選択肢**を選びます。コストに効くものとして「4 つ」を挙げましたが、トランスクリプトで確認できたのは次の 3 つです。

- **effort**（先に説明したもの）
- **キャッシュ**：繰り返し出てくるものをキャッシュして、毎回満額を払うのを避ける。強力な節約手段です
- **適切なモデルの選択**：各 5.5 モデルは、一般にそれ以前のものより実行コストが低い。節約額はワークロード次第で、**Azure Cost Management** のモデル別の表示（Monitor タブ）で確認できる

### 5.11 結びと次のアクション

登壇者は、最初のテーマ「フロンティア」に戻りました。閾値は "where agents were"（エージェントが到達していた水準）で、それは 2025 年 11 月、つまりほんの 1 年前のことだと述べています。また、今年の早い時期に、サイバー業務でも同じ閾値を越えたとのことです。次の境界線は、あなた自身の仕事（自分の業界とユースケース）にあります。

次のモデルが出たときの提案は、次のとおりです。

1. 自分がモデルに頼んでいる内容を見直す
2. テストを再実行する
3. 仕事を任せる（特に複雑なものを）
4. 証拠を確認する
5. **「not yet」リスト**を作り、良さの基準になる実際の入力を保存して、新しいモデルが出るたびにやり直す

登壇者は、ブースでコンテキストエンジニアリング（Claude と Foundry）や、シナリオの最適化に向けた evaluations と hill climbing を詳しく話していること、また Claude in Foundry でのコストガバナンスとコスト管理に関するウェビナーを最近行ったことを案内しています。このウェビナーはオンデマンドで視聴できると述べています（視聴先は「ここで」とだけ語られ、URL などは音声から分かりません）。

## 6. デモ・手順

画面を使った紹介が 2 つありました。どちらも事前に収録されたもので、ライブのデモではありません。画面の細部は音声からは確認できません。

**(1) Earthrise の動画（5.2）**：Opus 5.5 に、写真が「いつ・どこで」撮られたかを尋ねる例です。登壇者が「これから見せる動画」と述べて上映しました。Claude が約 3,000 の点をたどり、秒単位の時刻と月面の約 70 マイル上空という位置を割り出し、場面を 3D で再構成する様子が説明されました。

**(2) ベンダー提案書の評価スクリプト（5.8）**：登壇者は、Foundry の Opus 5.5 を呼び出すスクリプトで、"it's not Claude or Cowork" と述べ、数回の実行ファイルから作った**短縮版（リアルタイムではない）**だと断っています。語られた順は次のとおりです。

1. 登壇者がスクリプトを開始する。Claude に、**8 社のベンダーを 8 つの must-have 基準で評価**するよう依頼している（合計 64 のスコア。1 つでも誤りがあれば、実行全体が失敗）。
2. Claude が作業を始め、各提案書を読み、表（グリッド）を埋めていく。答えの根拠がどこから来たかを判断し、基準に照らしてスコアを付ける。
3. 画面の黄色い枠（vendor G）を指摘する。本来 Claude が合格にすべき項目だが、別の役割を想定して、満たしていない（miss）と判定してしまい、これが失敗として現れる。
4. 別のスクリプトが、その回答を見直して確認する。今回はこれを通す（発話は "It's going to pass it this time"）。
5. 結果として、提案内容から表面上は安く見えたベンダーがあったが、Claude が詳細と根拠を掘り下げ、**別のベンダーのほうが実際には安い**ことを見つけ、基準に基づく自分のポリシーで裏付けた。
6. Claude が推薦を提示する。最終判断は人間が行うが、多くのデータにまたがる意思決定を補強できる例だと説明している。

> 補足：ベンダーや提案書は架空のものです（登壇者が "fictional" と述べています）。手順 3〜4 で、画面のレイアウトや、見直しの具体的なやり方は語られていません。

## 7. 注意点・発表者の気付き

- **結果は異なり得る**：5.5 の事例は特定の顧客の 1 つのジョブの結果で、結果は一般化できません。登壇者自身がそう断っています。
- **1 つのテストだけに基づく数字**：Opus 5.5 の 16/18 は Anthropic の社内テストの結果で、「自分たちで行った 1 つのテスト」と述べています。
- **「完了」を鵜呑みにしない**：Claude が完成したように見せても、64 個のうち 1 つを外していた例があります。厳密な採点や別スクリプトでの検証が必要です。
- **system prompt は足すより削る**：古いモデル向けの「二度確認して」などの指示は、新しいモデルでは文字どおりに受け取られ、コストを増やすことがあります。
- **元に戻せない操作は、コード側で人の承認を要求する**：プロンプトだけに頼らない、と述べています。
- **beyond the frontier は予定機能ではない**：未解決問題を示すもので、ロードマップではないと明言しています。
- **ツールの提供状況**：compaction は beta です。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。具体的な数値は、登壇者が挙げた事例の範囲に限ります。

- **Foundry 上で Claude を使う利点**：引用と system card で確認でき、global standard と US data zones があり、MCP と agent SDK を使え、Entra ID や Azure roles が使え、1 つの Azure 請求書に集約されます（5.3）。
- **顧客事例**：Everstar（原子力）が、Foundry 上で Claude を使っています。
- **作業時間の短縮として語られた例**：WHO 日次報告の差分確認が、1 日から 1 時間未満へ。研究室の機器接続が、数週間〜数か月から数時間〜数分へ。コード監査・修正が 20 万行を 3 時間未満で、コードベース移行が数十万行を 1 日未満で（初期テスターや顧客の 1 つのジョブの例）。
- **コスト面**：system prompt の見直しで、平均 9% のコスト削減。キャッシュの活用や、effort の最適化。各 5.5 モデルは、一般に以前のモデルより実行コストが低い。

## 9. まとめ

新しいモデルが出るたびに頼める範囲は広がりますが、多くの人は 1 年前のモデルに合わせた小さな依頼を続けています。登壇者はこのギャップを capability overhang と呼び、ボトルネックは想像力だと述べました。

対策は 3 つです。①自分のテスト（実際に間違いやすい 20〜50 件のケースと、専門家 2 人が同意できる合格基準）を先に書き、それを満たす最も低コストのモデルと effort を選ぶ。②仕事を細切れにせず、成果、環境、権限と予算を brief に書いてまるごと任せる。③scope、sandbox、log、gate の 4 つのコントロールで結果を管理し、元に戻せない操作はコードで人の承認を必須にする。次のモデルが出るたびに、テストを再実行し、「not yet リスト」を見直すことを勧めて締めくくっています。
