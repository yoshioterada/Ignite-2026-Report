## 5. 発表内容の詳細

### 5.1 なぜモダナイズするのか

登壇者は、まず「なぜモダナイズの話をするのか」を問います。理由の 1 番目は**インフラの老朽化**です。登壇者自身の関心はサーバーですが、ストレージやネットワークも時間とともに古くなります。サポート契約や部品が入手できなくなり、時間が経つほど取り返しがつかなくなるため、次にどこへ移るかを考える必要があります。

次に、Windows Server 2016 をまだ使っている人に挙手を求めたうえで、**1 月に延長サポートが終了する**と指摘します。Windows Server 2016 が動いているインフラ、ワークロード、サーバーを評価し、次の手を考えるよう促しています。

その後に見るのが移行先（landing zone）です。選択肢として、次が挙げられました。

- 引き続きオンプレミスに置く
- コロケーション（colo）に移す、データセンターの場所を変える
- パブリッククラウドに移す
- ワークロード自体を近代化し、レガシーなオンプレミスから、Windows サーバーのインフラと Windows や Azure のサービスを組み合わせたハイブリッドな形にする

最後に運用の方法です。多数のツールやスクリプトでレガシーなインフラを運用し続けるのか、API とクラウドの機能で管理する時代に移るのかを決める必要がある、と説明しています。管理対象がオンプレミスでもクラウドでも同じ問いです。

### 5.2 台数・消費電力と、世代ごとのリスク

登壇者は、現在のインフラで気にしてほしい点として、**ワークロードを支えるインフラの量**と、**インフラが消費する電力**を挙げます。

会場に HPE の Gen 8、Gen 9、Gen 10、Gen 11 サーバーを使っているかを順に尋ねています。発言からは、Gen 8、Gen 9、Gen 10（「数人」）で手が挙がったことが分かります。そのうえで次のように整理しています。

- **Gen 11**：「リスクなし」の領域。ただし統合して、ワット当たりの性能を高めることは可能
- **それより古い世代**：今の構成と、将来できる構成の差が大きい。サポート契約が終わり、部品が入手できなくなる前に、次を検討する必要がある
- **Gen 10 を使っている場合**：Gen 12 と、まもなく登場する Gen 13 の機能を評価するよう促している

Windows Server のバージョン別の位置づけは次のとおりです。

| バージョン | 登壇者の位置づけ |
| --- | --- |
| Windows Server 2016 | **すぐにリスクがある領域**。1 月に延長サポートとパッチが終了する。インプレースアップグレードか、新しいプラットフォームか、まったく別の OS かを検討する |
| Windows Server 2019 | 今から検討を始めるべき。3 年ごとに繰り返されるサイクルの出発点 |
| Windows Server 2022 | 現時点では安全な領域 |
| Windows Server 2025 | 非常に良い状態 |
| Windows Server 2028 | 移行を考えているなら「先を行っている」（バージョン名は発言のとおり） |

新しいバージョンに移る理由として、顧客からよく聞かれる質問に対し、登壇者は**機能、セキュリティ、スケーラビリティ**の 3 点を挙げています。新機能に限らず、既存の機能や役割への強化も大きいため、調査したうえで、いま移るべきかを判断するよう勧めています。

### 5.3 運用モデルと Azure Local

運用モデルでは、レガシーなやり方のまま運用するのか、現代的な運用に進むのかを選びます。Azure の機能で管理する方法もあれば、オンプレミス独自の方法もあり、例として「Morpheus」でインフラ全体をオーケストレーションし運用化する、という話も出ました（音声認識の都合で表記が確定できません）。

Azure first のお客様にとって、Azure Local は現代的な運用スタイルへの良い入口だと説明されます。

- **Azure portal と Azure API** で、オンプレミスのインフラを管理できる
- Azure のサービスをオンプレミスに延ばしたい顧客に適している。例えば SQL Server や Azure SQL を使い、クラウドと同様にオンプレミスの SQL Server を管理したい場合の着地先になる
- ハイブリッドクラウド運用を、Azure の API と portal で行える
- Azure で使っている**管理、セキュリティ、ガバナンス**の機能が、オンプレミスの Azure Local にも届く

HPE は、Azure Local に関心のある顧客に対し、導入を支援するサービスをエンドツーエンドで提供しています。順に、教育、設計とアーキテクチャ、導入と実装、そして希望すれば環境の運用管理までです。これらのサービスはオプションで、顧客の状況に合わせると述べています。

### 5.4 すべてのワークロードがクラウド向きではない

登壇者は、**すべてのワークロードがクラウド対応とは限らない**と強調し、ワークロードとその要件を理解して、それぞれに合う landing zone を見つけるよう求めます。確認すべき観点は次のとおりです。

- **レイテンシに敏感か**。製造施設や、製造運用を支える環境にあるか。小売店舗にあり、POS（point of sale）を支えているか
- **コンピュータビジョン**を、例えば盗難防止に使っているか
- **エッジで AI 推論**をしているか。クラウドへ簡単に移せるか、レイテンシが妨げにならないか
- **規制と主権**。登壇者は EMEA の参加者に挙手を求め、これは注目度の高い話題だとして、自国の規制環境と主権要件を理解するよう促しています

Windows Server と Azure Local のどちらも、これらを支えられます。「どちらか一方」ではなく、どちらでも実現でき、望む運用モデルによって選ぶ、という説明です。

Azure Local、またはオンプレミスにインフラを残す場合の重要な観点は、次のとおりです。

| 観点 | 説明 |
| --- | --- |
| データの所在（data residency） | データがどこで使われ、どこで最も必要かによる。中央のデータセンターやクラウドに集約するデータなら問題ないが、運用データで、工場や店舗など現地で必要なデータ、リアルタイムまたは準リアルタイムで処理するデータは、オンプレミスに残る可能性が高い |
| 切断への対応 | パブリッククラウドからの長期的な切断に耐える必要があるか。インターネットなどのパブリックネットワークに一切触れない、完全なエアギャップ（air gap）が必要か |
| 運用上の権限（operational authority） | 認証情報と技術を手元に持っていれば完全に制御できていると考えがちだが、侵害や脆弱性は多く、誰が侵入して制御を奪い得るかも考える必要がある。上から下まで安全な環境を保つことが重要 |
| レジリエンス | 設計段階からのレジリエンス。インフラを層で守り、セキュリティ機能を活用する。Azure first の顧客が Azure Local を使うなら、Azure の**ポリシー**機能をオンプレミスのインフラに適用できる。データ保護の計画も維持し、障害から復旧できるようにする |

### 5.5 Azure Local の機能と使われ方

**外部ストレージ**：登壇者によると、Azure Local は今年の新機能として**外部ストレージ**に対応しました。既存のストレージアレイを活用でき、アレイ自体に備わるデータの耐障害性と復旧の技術（SAN ベースのコピー、SAN ベースのレプリケーション）を使えます（発話は「sand-based」。SAN と思われます）。現在のインフラで何を使っていて、それを引き継げるか、インフラを導入したあとにリリースされた新しい機能が使えないかを確認するよう勧めています。

**Azure と一貫した運用**：Azure Local は、インフラがどこにあっても、Azure と一貫した運用を持ち込めます。多くの場合はオンプレミスまたはコロケーションで、クラウドにある機能をオンプレミスに展開します。多くの顧客は、**接続された形**で展開し、パブリックな Azure の portal や API で管理しています。必要なら**切断された形**での展開もでき、先に述べた完全なエアギャップにも対応します。これは、オンプレミスの Azure Local クラスターを管理する、Azure のコントロールプレーンの層をオンプレミスに置くものだと説明しています。

**顧客の使い方（登壇者が挙げた例）**

- **小売**：多くの小売顧客が店舗（実店舗）に Azure Local を展開し、エッジで AI を使っている。セルフレジでの盗難防止に使い、レジを通らずに出ようとする人について、セキュリティに警告を出して出口に着く前に止められる。コンピュータビジョンとエッジの AI によるもの。登壇者は、会場近くの Target のセルフレジを身近な例として挙げていますが、Target が Azure Local の顧客だという発言ではありません。
- **製造**：製造施設で、危険区域を監視するコンピュータビジョンが使われている。人が入ると重傷を負う区域に人が入った場合、製造ラインを停止できる。登壇者は「命を救う技術」と述べています。

**ワークロードの幅**：自社開発または市販のコンテナー化アプリケーションを、**Azure Kubernetes Service（AKS）**を使って Azure Local に持ち込めます。これは現在すでにある組み込みの技術で、市販の技術（off-the-shelf）だという説明です。

### 5.6 セキュリティ：ハードウェアとソフトウェアの接点

登壇者は、セキュリティはハードウェアとソフトウェアが出会う場所で、OEM としてのすべてが Microsoft の取り組みと連携して動くことを確かめたい、と述べます。これは Windows Server と Azure Local の両方に当てはまります。

HPE の取り組みは次のとおりです。

1. **信頼できるサプライチェーン**：すべての製品、機能、部品を信頼できる調達元から得て、適切な国の適切な工場を通すことで、トラステッド サプライチェーンを主張できるようにしている。
2. **HPE iLO**（baseboard management controller、BMC）：すべての HPE サーバーに組み込まれ、Windows Server と Azure Local をサポートするサーバーも対象。Gen 12 では **iLO 7**、近いうちに **iLO 8** を提供。いずれにも **secure silicon root of trust** があり、これが HPE ProLiant のセキュリティの基盤。ソフトウェアがハードウェアの中核要素をセキュリティの観点で使えるようにする。
3. **ポスト量子コンピューティングのセキュア エンクレーブ**（iLO 7 と iLO 8）：鍵を保管し、量子コンピューティング攻撃に耐えられるようにする。登壇者は、**CNSA 2.0** とその要件に対する防御で業界初だと述べている。
4. **iLO 8 で追加される機能**：インフラのライフサイクル全体にわたるエンドツーエンドの対応と、**SPDM** によるコンポーネント検証。起動時に、ファームウェアと ProLiant サーバー内のハードウェアコンポーネントを検証できる。
5. **TPM 2.0** と **Microsoft Secure Core**：TPM 2.0 は長期にわたり信頼されてきた技術。Microsoft Secure Core は HPE が Microsoft と先駆けて開発した機能で、BIOS・ファームウェアが OS と連携し、OS がハードウェアによるセキュリティを活用できる。

Azure Local は、OEM と Microsoft が共同設計・共同開発するプログラムです。ハードウェアに組み込まれたセキュリティを生かしたソリューションを市場に出せ、導入は自社の担当者、HPE、または選んだ他の OEM やパートナーが行えます。HPE にはパートナーを教育して HPE ハードウェアのサポートを担えるようにするプログラムもあります。

ソフトウェア側では、次が挙げられました。

- **BitLocker**：Microsoft が上から下まで実装。ブートディスクと、Azure Local で展開するクラスター共有ボリューム（CSV）の保存データ（data at rest）を保護する。BitLocker の下で、**自動で有効になる暗号化ディスク**（auto-enabled secure encrypted disks）にも対応。HPE は最新の **Gen 13** プラットフォームで初日から有効にしており、Azure Local のクラスターを展開する前にディスクが自動で暗号化される（登壇者の言葉は「automatically encrypt those disks before Azure Local, before your clusters even deploy」）。
- **Microsoft Defender for Cloud と Azure Arc**：Azure Local にネイティブに統合され、標準（out-of-the-box）で利用できる。
- **サードパーティの SIEM** との統合：オンプレミスで SIEM を使っている場合、イベントとセキュリティのフィルタリングを渡せる。
- **コンプライアンス**：common criteria、HIPAA、FedRAMP などをはじめとする基準に準拠している、と述べている（SIEM 連携の話に続く発言で、何が準拠するのかの主語は音声から明確ではありません）。

### 5.7 Solution Builder Extension

HPE は、Azure Local 向けに **solution builder extension** を提供しています。これは Azure Local のエコシステムに接続する HPE の方法で、ファームウェア、ソフトウェア、ドライバーの更新を Azure Local に取り込み、Microsoft のセキュリティフレームワークと更新技術を使います。インフラをハードウェアとソフトウェアの両方、エンドツーエンドで 1 回の操作で更新できる点が重要です。登壇者は「ほぼ 1 クリック。2〜3 クリックかもしれない」と述べ、PowerShell などで自動化もできるとしています。

### 5.8 AI への備え

登壇者は、小規模な組織のエッジなど、現時点では AI を導入していない場合もあるとしながら、**AI-ready であること**は今後に向けて重要だと述べます。AI への備えとして考える点は次のとおりです。

1. **データ**：何であるか、何に使うか、どこにあるか
2. **プラットフォーム**：そのデータを、AI と組み合わせて活用できるか。AI に何が必要か、何に使うか（万能の答えはない）
3. **Foundry Local と AKS**：AI を使うなら、AKS と Foundry Local を組み合わせられる。Foundry Local は、最新の AI モデルをオンプレミスに持ち込み、オンプレミスで推論に使えるようにするもの。登壇者は、これに関する発表が「17 日の月曜日」ごろから出始めたと思う、と述べている（日付は聞き取りの表記）。
4. **アクセラレーション**：すべての AI モデルが GPU を必要とするわけではないが、GPU は多くの場合に AI モデルの能力を高める。プラットフォームが少なくとも GPU に対応できるようにしておく。HPE はこれを得意とし、市場投入を支援すると述べている。

AKS、Foundry Local によるモデルのサービング、CPU、GPU を、自分の環境で AI を支えるために何が必要か理解するよう求め、支援が必要なら相談に乗ると話しています。

### 5.9 HPE からの案内

最後に、HPE には、認定・検証済みのサーバー、ストレージ、ネットワークがあると述べ、会場の「hub」にあるブース（登壇者の話では、まだ開いていない時点）が開いたら立ち寄るよう呼びかけています。あわせて、次の案内がありました。

- **サービス**：Azure Local に関する世界水準のサービスがある。HPE のサービス部門は、Windows Server を長年扱ってきた組織だと述べている
- **ファイナンス**：適切な価格帯でソリューションを組めるよう、ファイナンスのサービスもある
- **HPE GreenLake**：これらを単一の契約にまとめられる。運用管理を HPE に任せる場合も、自分たちで管理する場合も GreenLake が選択肢になる、と説明している

終了時には、進行役と思われる人物が「Eric、ありがとうございました。質問があれば Eric が後ろで受けます」と述べ、質疑は登壇後に個別に受ける形でした。会場全体での Q&A の時間は設けられていません。

- **サポート契約の終了と部品の入手**：古い世代のサーバーは、サポート契約が終わり、部品が入手できなくなる前に次の手を考える。
- **場当たり的なクラウド移行は避ける**：レイテンシ、設置場所、規制・主権、データの居場所、切断への耐性を、ワークロードごとに確認する。
- **既存の技術を見直す**：ストレージアレイの機能（SAN ベースのコピーやレプリケーション）など、すでに持っている技術を引き継げるか、導入後にリリースされた新機能が使えるかを確認する。
- **AI は一律の答えがない**：AI に何を使うかで必要な構成が変わる。AI-ready を意識して、データ、プラットフォーム、アクセラレーションを確認する。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **Azure と一貫した運用**：Azure portal と API で、オンプレミスのインフラを管理できる。管理、セキュリティ、ガバナンス、ポリシーの機能が、オンプレミスにも届く。
- **配置の柔軟性**：工場や店舗など、レイテンシに敏感な環境や、規制・主権の制約がある環境でも、接続された形または切断された形で Azure Local を展開できる。
- **既存資産の活用**：外部ストレージ対応により、既存のアレイとその機能を使える。
- **更新の簡素化**：Solution Builder Extension により、ハードウェアとソフトウェアをほぼ 1 クリックで更新できる。
- **ハードウェアレベルのセキュリティ**：secure silicon root of trust、ポスト量子セキュリティ エンクレーブ、起動時の検証、BitLocker、Defender for Cloud、SIEM 連携。
- **エッジの活用例**：小売店舗のセルフレジでの盗難防止、製造施設の危険区域の監視と製造ラインの停止。
- **AI への備え**：AKS と Foundry Local によるオンプレミスでの推論、GPU による強化。

## 9. まとめ

古いハードウェアと、1 月に延長サポートが終わる Windows Server 2016 は、モダナイズを検討する具体的な理由です。移行先はワークロードごとに、レイテンシ、設置場所、規制と主権、データの所在、切断への耐性、運用上の権限、レジリエンスを確かめて決めます。Windows Server と Azure Local はどちらもその選択肢で、運用モデルによって選びます。

Azure first のお客様には、Azure Local が Azure portal・API・ガバナンスをオンプレミスに延ばす入口になります。HPE は、iLO、信頼できるサプライチェーン、BitLocker、Solution Builder Extension などで、ハードウェアとソフトウェアの両面から安全な基盤と簡単な更新を支え、AI への備えとして AKS と Foundry Local、GPU も挙げました。サービス、ファイナンス、HPE GreenLake による単一契約の提供もあり、詳細は HPE のブースで相談できます。
