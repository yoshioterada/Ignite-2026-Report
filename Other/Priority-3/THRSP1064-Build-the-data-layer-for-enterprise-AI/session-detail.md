# THRSP1064 Build the data layer for enterprise AI

## 1. はじめに

このセッションは、企業の AI エージェントに「自社のデータに基づいた、役に立つ正確な答え」を返させるための**データレイヤー**を、Eon と Microsoft（OneLake / Fabric）の連携でどう作るかを紹介するものです。扱う例題は「今月、配送が遅れた顧客はどこで、売上にどれだけ影響したか」という、データが複数のクラウドや DB に散らばっていると答えにくい質問です。

発表は 2 つの課題に分けて話を進めます。1 つは、地域・サービス・形式がばらばらなデータを 1 か所から使える形にすること（統合）。もう 1 つは、仮に 1 か所に集めても、エージェントがそのデータの意味を理解できなければ答えられないこと（コンテキスト）です。前者は OneLake のカタログ連携とショートカット、後者は Power BI のセマンティックモデルと Fabric IQ の Ontology（オントロジー）で扱います。Eon 側は、バックアップを取り込む段階でデータ分類を行い、そのコンテキストを OneLake に引き渡す役割を担います。

このセッションにはデモがあり、Eon のコンソールから OneLake、データエージェントまでを順に見せます（6 章）。

## 3. 何に関する発表か

テーマは、エンタープライズ AI のためのデータ基盤です。出発点として、小売業のように顧客の注文を履行する企業を想定します。

顧客データは Azure 上の Postgres や Azure SQL（PaaS、VM 上のものもある）にあり、配送イベントは物流拠点の IoT から Blob storage に入り、返品システムは AWS など別のクラウドにある、という状況です。この中で「今月配送が遅れた顧客と、その売上への影響」を尋ねるには、多くのことを整える必要がある、と説明しています。

発表の流れは次のとおりです。

1. 課題設定：散在するデータの統合と、エージェントに意味を理解させるコンテキスト層（Lior 氏）
2. OneLake によるデータ統合：カタログ連携、ショートカット、オープンなアクセス、AI への準備（Roy 氏）
3. セマンティックモデルとオントロジー（Fabric IQ）（Roy 氏）
4. Eon の位置づけ：バックアップを Iceberg 形式で扱い、取り込み時に分類する（Lior 氏）
5. デモ：Eon から OneLake へ、そしてデータエージェントで質問（Lior 氏）
6. デモへのコメントと、ブース・関連ページの案内

## 4. 発表者が伝えたいメッセージ

中心にあるのは、**エージェントを推測させず、毎回同じ正しい答えを返させるには、統合されたデータにコンテキストを持たせることが必要だ**という考えです。

Roy 氏は、エージェントにデータの場所を示すだけでは足りず、キーノートやこの週の多くのセッションでも語られたとおり、より多くのコンテキストを与えて「推測させない」ことが必要だと述べます。セマンティックモデルで表のリレーションを、オントロジーで transaction、user、supply chain task といったビジネスの概念を表現することで、エージェントは「推測で答えている状態」から「常に正しく、毎回同じ答えを返す状態」に近づく、という説明です。

Lior 氏のメッセージは、コンテキストを後から別工程で作るのではなく、**データの取り込みと同時に作る**点にあります。Eon は取り込み時に分類を行い、その結果を OneLake のセキュリティロールに反映します。そのためデータが着地した時点から、保護が効いた状態になると語っています。

このほか Roy 氏は、OneLake ではデータパイプラインを作らずに AI の準備ができること、すでに取っているバックアップをクエリできれば CDC パイプラインを作って管理する手間が減ることを挙げています。

## 5. 発表内容の詳細

### 5.1 課題の整理

Lior 氏は、冒頭で例題を示します。「今月、配送が遅れた顧客はどこで、売上にどれだけ影響したか」という質問に答えるには、次のようなデータが関わるとしています。

- Azure 上の Postgres、Azure SQL、PaaS や VM 上のデータにある顧客データ
- 物流拠点から IoT 経由で Blob storage に入る出荷イベント
- AWS など別クラウドにある返品システムのデータ

必要なのは 2 つです。1 つ目は、地域、サービス、データソースの種類をまたいで散らばるデータを、質問に答えられる形にすること（方程式の半分）。2 つ目は、すべてのデータを 1 か所にまとめられたとしても、エージェントがそれをどう扱えばよいかを知っていること。これは、エージェントのユースケースを本番に持ち込むときによく見られる問題だと説明しています。そこで、エージェントがデータで答えられるようにする**コンテキスト層（オントロジー）**を作る、というのが全体の構成です。

### 5.2 OneLake によるデータの統合

Roy 氏は、すべては「データを統合すること」から始まると述べます。OneLake は、Microsoft のデータに限らず、Snowflake や Databricks などのデータプラットフォーム、AWS や Google といったクラウドのデータを横断して統合できるよう設計されている、という説明です。

OneLake は複数の要素で構成されています。

| 要素 | 説明 |
| --- | --- |
| 検出とガバナンス | 製品に組み込みのカタログがあり、統合したデータをエンジンから問い合わせられるようにすると同時に、利用者がどんなデータがあり、どう使い、どう統制・監査するかを理解できるようにする。セキュリティ制限、きめ細かなアクセス制御、ライフサイクルポリシーなど、エンタープライズグレード |
| 統合（Catalog federation） | カタログ同士を接続する。OneLake と、互換性のある他のカタログの間を **Apache Iceberg REST API** でつなぐ。個別の接続を作る必要はなく、1 つの接続を作れば、そのカタログのデータが OneLake に持ち込まれる（実際にはコピーしない。5.3 参照） |
| ショートカット | ストレージ同士をつなぐ機能。SharePoint への接続や AWS S3 への接続があり、データがそこにあれば持ち込める。同様の接続が他にも多数ある |
| オープンなアクセス基盤 | 4 つ目の要素。ストレージとして開かれており、相互運用できる。Fabric のエンジンを使えるだけでなく、データをオープンなテーブル形式で保存し、オープンな API を提供するので、**自分のコンピュートやエンジン**も使える |
| AI への準備 | インデックス作成、追加コンテキストの作成、関連情報のエクスポートを、データパイプラインを作らずに行える。すべて組み込み |

Eon のプラットフォームが OneLake のデータを使って関連情報を抽出し、それをカタログに反映して、ガバナンス、セキュリティ、エージェントに使えるようにする様子は、後で Lior 氏が見せると予告されています。

### 5.3 カタログ連携とゼロコピー

Eon のユースケースで特に重要なのが、カタログ連携です。Roy 氏は、業界が標準として落ち着いた API である Apache Iceberg REST API を使い、クラウドプロバイダーやデータプラットフォームにつなげられると説明します。

画面の例では、OneLake のカタログを **AWS Glue のデータカタログ**と **Google Lakehouse のカタログ**に接続しています。これらのクラウド上で Eon を動かしている場合、Eon はデータベースのバックアップを取り、オープンな Apache Iceberg 形式で保存します。そこでカタログ同士を接続すると、別のクラウドにあるデータが OneLake に見えるようになります。

利点は**ゼロコピー**であることです。データを移動も複製もせず、データは作られた場所に残ります。Microsoft のエコシステムで問い合わせを行うときに初めて、必要な部分だけ（クエリが必要とする特定のファイルなど）が転送されます。性能とコストのためにローカルにキャッシュすることも、キャッシュせず必要なたびに取りに行くことも選べます。Roy 氏は「シンプルだが優れたアーキテクチャ」と評し、Eon がバックアップしたエンタープライズ DB のデータを、どこにあっても OneLake につないで使えると述べています。

### 5.4 セマンティックモデルからオントロジーへ

データを統合したら、次はエージェントにとって使いやすくします。Roy 氏は、エージェントに生データを指し示すだけでは足りず、「エージェントに推測させたくない。ガイダンスを与えたい」と述べます。

**セマンティックモデル（Power BI）**：Power BI は Fabric の一部で、データをクリックして新しいセマンティックモデルを作れば、データセット間のリレーション（どの表がどのキーで関係するか、その追加情報）を持つモデルができます。素早く始める方法として紹介されました。

**オントロジー（Fabric IQ ontologies）**：次の段階です。表の技術的な関係の上に、ビジネスの文脈を載せます。「取引（transaction）とは何か」「ユーザーとは何か」「サプライチェーンのタスクとは何か」といった、セマンティックモデルでは必ずしも定義されないビジネスの抽象概念を表現します。Fabric には、データを指し示して「オントロジーを作って」と頼めるエージェントがあり、このあとデモにも出ると予告されています。このエージェントは、表の説明、列名、列の説明、データの中身から、最適なリレーションを推測し、オントロジーに注釈を付けて使えるようにします。

データ、オントロジー、セマンティックモデルがそろうと、Copilot、Fabric Data Agent、Copilot Studio で作った独自エージェントなどが「非常に賢くなる」と説明され、冒頭の質問に答えられるようになるとのことです。

Roy 氏が挙げた補足は 2 点です。

- **統合セマンティックモデル**：リレーション、情報、メトリクス、メジャーをひとまとめにして、オントロジー層に取り込めるので、作業を重複させなくて済む。すでに Fabric には **3,000 万を超えるセマンティックモデル**が作られている。Power BI で作っているなら、そのままオントロジーに持ち込めば、すでに先へ進んでいる。
- **オントロジーのエージェント**：データとセマンティックモデルから情報を素早く導き出してオントロジーを作るので、エージェントがすぐに動き出せる。長い手作業のカスタム作業は要らない。

### 5.5 Eon：自律的なデータ基盤

Lior 氏は、1 年前にも Eon と Fabric の連携の始まりを発表したと振り返り、OneLake と Fabric に多くのリリースがあったことを喜んでいます。AI の普及に伴い「エージェントで問題を解くために十分なコンテキストをどう得るか」が課題で、これまではコンテキストを手作業でつなぎ合わせられる「腕の立つ人（whiz kid）」がいなければ正確にできなかった、と話します。Roy 氏のチームが作ったツールや機能で、これを**再現可能な形で、組織に大規模に展開できる**ようになる、という見方です。

Eon の位置づけは、「**autonomous data foundation（自律的なデータ基盤）**」を提供する会社です。ここ数年、世界最大級のクラウド顧客にデータ保護ソリューションを提供してきました。Eon のデータ保護では、顧客がクラウドバックアップに対して直接クエリできます。バックアップは Apache Iceberg 形式で利用できるように保存されます。バックアップを取り込む際には分類も行うため、**コンテキスト層は取り込みの過程で作られ、別の工程にはなりません**。具体的には、ランサムウェアやマルウェアの検出、データの分類（データベースやオブジェクトストレージに PII や PHI があるか）などです。これにより、Eon が取り込んだデータを使うエージェントやエージェンティックなワークフローは、必要なコンテキストを持った状態になります。

Roy 氏は、この点を繰り返して強調します。すでに安全のために取っているバックアップを Iceberg テーブルとして保存してクエリできる、という点です。多くの顧客のためにデータパイプラインや CDC パイプラインを作って管理してきた経験から、すでに会社が多額の費用をかけているバックアップに対してクエリできるのは素晴らしい、と述べています。Lior 氏は、別のコピーを作らずにその価値を得られることが要点だと補足しました。

最近の発表として、Lior 氏は **Eon Yukon**（音声認識の都合で表記が確定できません）を挙げています。これは Eon のバックアップとデータ保護の取り込みを支えるエンジンで、他のソース（Kafka、Event Hubs、各種のイベントストリーミング、データベースの CDC、Blob storage などのオブジェクトストアからの大規模な取り込み）にも使えるようにするものです、という説明でした。

### 5.6 取り込み時のコンテキスト発見と OneLake セキュリティ

Lior 氏は、Eon がデータを大規模に取り込みながらコンテキストを発見し、単一のカタログに書き込んでエージェントが使えるようにする、と説明します。データベースをバックアップするとき、またはイベントストリームを取り込むときに、次のことをするという話です。

- どのエンティティが存在するかを認識する
- 明示的に定義されていなくても、データ間のリレーションを推測する
- ツールと連携する

OneLake には**セキュリティロール**があり、レイクの中でデータがどうアクセスされるかを統制します。Eon は取り込み時に、機密データがあるかを、組み込みの分類器またはカスタム分類器で判定します。この連携を使えば、データレイク上のセキュリティレイヤーが常に更新され、**管理の手間なしに維持される**と説明されています。ルールを設定したり、パイプラインを作ったりする必要はなく、データを見て、機密かどうかを判断してラベルを付けます。その結果が OneLake の security に反映され、きめ細かいアクセス制御を定義できます。このやり取りの中で、「keeping the agents honest（エージェントを正直に保つ）」という表現も出ています。

## 6. デモ・手順

ライブのデモがあります（Lior 氏）。ただし画面操作は音声のナレーションで語られた範囲しか分からず、ボタン名や入力値の詳細は確認できません。冒頭の質問（配送が遅れた顧客と売上への影響）に、Eon と Microsoft の道具だけで、エージェンティックなワークフローが答えられるかを見せる、という位置づけです。

1. **Eon のコンソール**：バックアップと取り込まれたデータが着地する場所。Azure のさまざまなリソース、VM、Azure SQL、PaaS、他のクラウドにまたがるデータを表示。データクラス、アプリの分類、ストレージサイズなどが見える。
2. **スナップショットへのクエリ**：Eon のスナップショットは、単に復元するだけの通常のスナップショットではない。例として SQL データベースを挙げ、スナップショットのある任意の時点に対してクエリを書いて実行できる。内部では Kusto と Blob storage を使っている。復元は不要。
3. **Zero ETL 統合**：Eon に置かれているデータ（Blob storage や任意のオブジェクトストレージ）を、Apache Iceberg 形式または Delta Lake で公開して、Fabric と連携できる。画面では、これを **OneLake のショートカット**として公開している。データのコピーは不要。
4. **OneLake セキュリティ統合**：取り込み時に行われる Eon のデータ分類を使って、OneLake の中にセキュリティロールを作る。Iceberg のパーティショニング、ソート、コンパクションをカスタマイズでき、既定のままにして Zero ETL 処理に任せることもできる。Eon のデータ分類を OneLake のセキュリティロールにどう結びつけるかも設定できる。
5. **OneLake 側の確認**：ショートカットにより、データを移動せずに中身を確認できる。オンデマンドで安全にデータとやり取りできる。出荷データは Azure SQL 由来。返品データは AWS 由来で、S3 とのショートカット連携を使っている。
6. **オントロジー エージェント**：オントロジー エージェントを使ってデータのマップを作る。カスタム作業は不要。
7. **ルールの追加**：この上にルールを作る。デモで注目するのは「late shipment（配送遅延）」で、目標の配達（delivered at target）を満たさないものがあれば把握したい、というルール。
8. **OneLake のデータエージェントで質問**：text to SQL で、冒頭の質問を尋ねる（発話は「Which customers had late deliveries in October 26th and how did it impact our revenue?」）。回答は、互いのことを知らないはずの複数のシステム（別のクラウド、別のデータソース）を考慮したものになった。
9. **ガバナンス**：エージェントがメールアドレスの提供を求めても、取得できない。PII が検出されてフラグが付いたデータには、セキュリティロールが設定されているため。
10. **イベントのフック**：データの異常や他のイベントを使って、Fabric 内で別のフックやイベントベースのワークフローを作ることもできる、と触れている。

> 補足：回答の具体的な内容（顧客名や金額）は、音声では語られていません。

デモの後、Roy 氏が振り返ります。Azure で動く SQL Server の標準的なバックアップが Iceberg テーブルになり、Fabric で開いてクエリできたこと、そして分類結果（PII を含むデータがあった）から OneLake のセキュリティポリシーが自動で作られ、エージェントやユーザーが該当データを選択するとブロックされたことが印象的だった、という内容です。顧客のもとでは、これを理解し、情報を抽出するパイプラインを作り、ポリシーをセキュリティルールに対応付ける自動化まで作るのに、通常は大変な労力がかかる、と述べています。

## 7. 注意点・発表者の気付き

- **機密データを不明なまま公開する不安**：Lior 氏は、重要なデータをツールに公開して、エージェントに走らせるのは「怖いこと」だと言います。機密データがあるか、財務情報や知的財産、競合情報があるかが分からないままだからです。取り込みの過程でデータ分類を組み込み、それを連携させることで、その不安に対応できるという主張です。
- **分類を後工程にしない**：デモ後のやり取りで、セキュリティが二次的な作業（データが着地したあと誰かが作業する）ではなく、フローの中に組み込まれていること、データが着地したらすぐに安全になることが評価されています。
- **エージェントにはコンテキストが必要**：生データだけを指すのではなく、ガイダンスを与え、エージェントに推測させない。
- **ゼロコピーでも問い合わせ時には転送が起きる**：Microsoft のエコシステムで問い合わせるとき、必要な部分だけが移動する（5.3）。性能とコストのために、ローカルにキャッシュするかどうかを選べる。

## 8. 利用者にとっての利点

- **データを動かさずに統合できる**：Iceberg REST API によるカタログ連携とショートカットで、AWS、Google、Snowflake、Databricks などのデータを、コピーなしで OneLake から使える。
- **すでに取っているバックアップを活用できる**：バックアップを Iceberg 形式でクエリでき、別途データパイプラインや CDC パイプラインを作って管理する手間を減らせる。
- **コンテキストの構築が自動化される**：オントロジー エージェントが、データとセマンティックモデルからオントロジーを作る。Power BI の既存のセマンティックモデル（Fabric 上に 3,000 万以上）を再利用できる。
- **セキュリティが運用負荷なしで維持される**：取り込み時の PII などの分類が OneLake のセキュリティロールになり、管理者の作業なしで更新される。デモでは、PII のあるメールアドレスはエージェントから取得できなかった。
- **オープン**：オープンなテーブル形式とオープンな API なので、独自のコンピュートやエンジンも使える。
- **答えの一貫性**：オントロジーとセマンティックモデルにより、エージェントが毎回同じ正しい答えを返すことを目指せる（Roy 氏の説明）。

## 9. まとめ

散在したデータで業務上の質問に答えさせるには、「データを 1 か所から使える形にすること」と「エージェントにデータの意味を教えること」の 2 つが必要です。前者は OneLake のカタログ連携（Apache Iceberg REST API、AWS Glue と Google のカタログへの接続）とショートカットによるゼロコピーの統合で、後者は Power BI のセマンティックモデルと Fabric IQ のオントロジー（オントロジー エージェントによる自動作成）で実現します。

Eon は、バックアップを Iceberg 形式で扱い、取り込み時にデータ分類を行って、その結果を OneLake のセキュリティロールとして反映します。デモでは、Azure SQL と AWS S3 のデータを OneLake のショートカット経由で扱い、データエージェントに配送遅延の質問をし、PII のあるデータにはアクセスできないことを示しました。

発表後は、会場に残って質問に答えること、ブースに立ち寄ってほしいこと（参加者向けに「treats」を用意しているとのことです）、Eon と OneLake のアーキテクチャに関するパートナーシップのページと、Fabric IQ と Ontology の紹介を見てほしいことが案内されました。
