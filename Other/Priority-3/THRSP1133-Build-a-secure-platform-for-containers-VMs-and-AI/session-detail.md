# THRSP1133 Build a secure platform for containers, VMs, and AI

## 1. はじめに

このセッションは、Red Hat の 2 人が、本番環境で動き続けている「アップグレードできない古いアプリ」の脆弱性を、どうやって安全に修正するかを、ライブデモで見せる内容です。使うのは **Project Lightwell**（IBM と Red Hat がこの夏に発表した、上流（upstream）のオープンソースライブラリの脆弱性修正サービス）、GitHub の Dependabot、Ansible、そして今日 GA（一般提供）を発表した **Red Hat Enterprise Linux（RHEL）の GitHub runner** です。

デモでは、Python の脆弱なライブラリ（SQL parse）を最新版へ上げられないアプリに対し、Lightwell の修正済みパッケージを自動で取り込んでテストし、コンテナーと RHEL VM の両方に約 2 分で本番反映するまでを見せています。既存の CI/CD に小さな設定変更を足すだけで、アプリを止めずに脆弱性に対応できる、というのが結論です。テーマ名にある「AI」については、トランスクリプト上、AI に特化した説明やデモは確認できません（Lightwell の開発に frontier AI model が使われているという言及があるのみです）。

## 5. 発表内容の詳細

### 5.1 Project Lightwell とは

Aaron 氏は、会場に「mission critical なアプリを、自分たちで面倒を見る余力がないまま本番で動かしていないか」と挙手で問いかけています。そのうえで、この夏に IBM と Red Hat が **Project Lightwell** を発表したと説明しました。両社による 5B（50 億ドル、「5B as in billion」と発言）の投資で、上流の脆弱性修正を市場に提供する取り組みです。

対象は、サードパーティのオープンソースの Java と Python のライブラリで、JavaScript と .NET も近く対応予定と説明しています。最新バージョンへのアップグレードを求めず、修正を施したものを提供する点が特徴です。

Lightwell には 2 つの提供形態があります。

| 提供形態 | 内容 |
| --- | --- |
| Network | セルフサービス版。年間サブスクリプションで、リポジトリ内の各ライブラリにアクセスできる。設定は、サービスアカウントを追加し、リポジトリに接続し、既存の CI/CD パイプラインに組み込むだけで、パイプライン自体は変更しなくてよい |
| Clearinghouse | Network のすべてに加えて、手厚い支援が付く。例えば、ベンダーが廃業した 5 年前のパッケージのように、組織側にリソースがない場合に、Red Hat が修正を行い、署名して、契約者だけがアクセスできる形で提供する。TAM（Technical Account Manager）のサポートも付く |

Clearinghouse について、もう一人の登壇者が「手厚い（kid gloves）ケアが必要な人向けか」と尋ね、Aaron 氏は「ホワイトグローブのサービス」と答えています。例えば、requirements.txt に 10 個のパッケージがあり、それぞれに 5 つの脆弱性があるような、とても大変な作業を引き受けるという説明です。

例として、SQL parse 0.55 を使っていて最新の 6 系へは上げられない場合、このバージョンに留めたまま（pin して）使い続けられ、Red Hat がテストと検証を行うと述べています。

実績として、サービスはこの夏に始まったばかりで、これまでに Java のパッケージを約 600 個修正したと述べています。Python も同程度の数に向けて進んでおり、.NET と JavaScript が近く加わります。

また、Red Hat の流儀として、SQL parse などの上流パッケージにメンテナーがいる限り、修正は最終的に上流へ戻す（隠さない）が、上流にメンテナーがいる必要がある、とも説明しています。

### 5.2 デモのアプリと構成

デモで使うのは、チケットの受付アプリ（transcript では ticket intake app と聞こえます）です。単一のソースが GitHub のリポジトリにあり、それが本番へ展開される際の「信頼できるリポジトリ」になります。同じコードが、Python のコンテナーと、RHEL 10.2 の VM の 2 か所で動いています。

全体の流れは、次のように説明されました。

1. コードは GitHub にある。GitHub の **Dependabot** は、有効にするとリポジトリの脆弱性をスキャンし、見つけるとアラートを出す。
2. アラートでどうするかは組織次第である。Dependabot にルールを作らせて自動修正することも、既存の CI/CD パイプラインを使うこともできる。今回は後者である。
3. Dependabot が SQL parse の脆弱性を見つけ、同じ CVE 群を **Microsoft Defender** も見つけて「最新版へアップグレードせよ」と案内するが、アップグレードはできない。
4. Dependabot が Ansible に webhook を送り、Ansible が 2 つの playbook（verify と remediate）を実行する。
5. playbook は、Lightwell を契約済みで、そのパッケージが利用可能かを確認し、あれば取り込み、動作を検証し、PR（プルリクエスト）を作る。
6. PR が RHEL runner を起動してテストを行う。テストが通ると、PR をマージして本番へ反映する。

登壇者は、コンテナーと VM は別の場所で動いていてもよいと補足しています。例えばコンテナーがオンプレミスの OpenShift 上、VM が Azure 上でも、Ansible がそれらへ接続できればよい、という説明です。

また、スキャナーは選べるとも述べています。ここでは Dependabot を使っていますが、「sync」のようなスキャンツール（音声認識の都合で表記が確定できません）を使っても、エンドツーエンドで同じ流れになります。

画面上では、Dependabot のアラートに SQL parse の CVE が 5 件（high と moderate）表示され、Defender for Cloud にも同じ CVE が並び、「バージョン 6 が最新なので修正せよ」と表示されていると説明しています。どちらもソース（GitHub）を見ており、本番の中身ではなく、信頼できるソースを本番へ展開する方針です。Dependabot アラートの有効化は、簡単な 2 クリックの設定だと述べています。

### 5.3 GitHub runner（RHEL）の GA

Mark 氏は、Red Hat の GitHub runner が今日 GA になったと発表しました。プロジェクトには本人が GitHub のチームと一緒に関わっています。

**経緯**：ある大手金融機関（名前は伏せられた）が「Red Hat のディストリビューションが runner として使えないのはなぜか」と依頼してきたことが発端で、昨年 3 月から取り組みが始まりました。5 月ごろに tech preview を出しています（本人は「5 月ごろだと思う」と発言）。

**仕組み**：runner は短命（ephemeral）な VM で、起動してタスクを実行し、終わると消えます。GitHub がホストすることも、自分でセルフホストすることもできます。提供される runner は、GitHub のイメージの partner 領域にあり、組織を持つエンタープライズ顧客向けです。提供の基盤は、Azure の image gallery を、GitHub が持つサブスクリプションへ direct share する形です。

**必要性**：多くの開発者・環境が本番で RHEL を使うのに、GitHub 上に RHEL のテスト環境が無かったため、他のディストリビューション（例として Ubuntu）でテストして本番へ移しており、差異が問題を起こしていたと説明しています。

**使い方**：ワークフローを YAML ファイルで定義し（自由にカスタマイズできる）、runner を作り、その runner に対して YAML をジョブとして実行します。結果は、ジョブのステップ一覧として画面に表示されます。

### 5.4 デモの実行と結果

デモの内容は 6 章に書きます。ここでは、デモで確認された重要な点を整理します。

- runner は短命な RHEL 10 のイメージを立ち上げるため、セルフホストのようにインフラを管理する必要がありません。
- ジョブは、Lightwell パッケージの取り込みと修正、修正が動作しているかのテスト、追加で作成したユニットテストを順に行い、すべて通れば完了です。
- 完了までのエンドツーエンドのコンテナーテストは、約 34 秒でした。
- バージョン表記に新しいサフィックスが付き、それが「署名された、信頼できる Lightwell 版のパッケージ」であることを示します。これにより、元の PyPI 版ではなく Lightwell 版に切り替わったと分かります。
- テストが失敗していれば、ロールバックされ、PR に記録が残り、本番には何も起きません。
- 全体は約 2 分で終わります。

### 5.5 Q&A とそのほかの補足

**Q1. 新しい Linux ユーザーが RHEL を使っている場合、yum update で直せばよいのではないか。なぜ Lightwell が必要なのか。**（Aaron 氏が後から「Mark 氏の質問」と言及しています）

Aaron 氏は、pip install で最新版を入れること自体は簡単にできるが、それが冒頭の問いに戻る、と答えています。つまり、組織には余力、リソース、コンプライアンスの面で、最新版に上げるとアプリが壊れかねない事情があります。Lightwell から署名された、信頼できる修正済みのバージョンを取得するなら、変わるのはバージョンと取得先のパスだけで、再テストのために追加の作業が要りません。デモでも、新しいパイプラインや新しいテストは作らず、既存のものに「Lightwell から取得する」と指示しただけでした。Java は、Maven を使っていれば同様に組み込めます。JavaScript も同様に対応し、将来的に言語を追加する予定です。

**Q2. 上流とダウンストリームの区別（登壇者からの確認）**

問いかけた登壇者は、OS に組み込まれた部分の脆弱性は Red Hat が対応して提供し、上流のサードパーティやカスタムなライブラリ・コンポーネントの脆弱性に Lightwell が役立つ、という理解でよいかと確認し、Aaron 氏は「その通り」と答えています。Red Hat がプラットフォームレベルで提供してきたものは今後も続け、Lightwell で、これまでやっていなかったサードパーティのパッケージを上流で対応する、という位置づけです。

**Q3. Lightwell が何を対象にするか、優先順位はどう決めているか（質問者は音声から確認できません）**

サービスはまだ新しく、進化中だと前置きしたうえで、優先順位は 2 つの軸だと答えています。顧客からの要望と、CVE のスコアが高いもの（higher CVSS score）です。最初の顧客層は金融サービスで、そこから順に広げています。すべての脆弱性には対応できないので、最も重大なものから順に進めます。デモの例では、SQL parse を修正することで 5 件が直りましたが、25 件を抱えるものもあり得ます。アプリの要件によっては、一度にすべてのパッケージが直ることもあれば、1 つ今直し、もう 1 つは対応中のため、デプロイを段階的にずらす必要も生じる、という説明です。

また、この投資は 50 億ドル規模で、登壇者の記憶では約 2 万人のエンジニア（「if I recall」と断っています）と、スキャンと修正を助ける frontier AI model が関わっていると述べています。業界のリーダーとも連携しており、さらに **Project Ocrities**（音声認識の都合で表記が確定できません）にも言及し、Linux Foundation とともに、通常の枠組みの外で上流の脆弱性に対処するための追加のオープンソースの取り組みだと説明しています。詳細は終了後に話すとのことです。

**補足：カスタム runner（Mark 氏）**

金融機関から「標準の runner には必要なものが入っていない。例えば GitHub CLI を入れたい」という声があったとして、独自のカスタムイメージを作って保存し、「クッキーの型抜きのように」展開してスケールできると説明しています。標準イメージを自社環境に合わせて変更したい人の多くが、現在この方法を取っているとのことです。

**補足：セルフホストからマネージドへの切り替え（Aaron 氏）**

セルフホストの runner を使っている場合、ワークフローの 1 行を変えるだけでマネージドに切り替えられ、短命なイメージが立ち上がるようになります。GitHub のマネージド runner は、常に最新の 9.x と 10.x が使えるため、更新、セキュリティ、設定の管理を気にしなくてよい、と述べています。

**締めくくり**

質疑のあと、登壇者は、質問があれば Red Hat のブースで対応すると案内して終了しています。

## 6. デモ・手順

このセッションにはライブデモがあります。画面の細部は音声からは確認できないため、語られた範囲の手順を書きます。

1. 登壇者がアプリを画面に表示した。下部の表示から、Python のコンテナーで動いており、SQL parse に脆弱性があること、そのバージョンは上げられないことを示した。同じコードが RHEL 10.2 の VM でも動いている。
2. Dependabot のアラートを見せた。SQL parse に関する CVE が 5 件（high と moderate）。同じ CVE が Defender for Cloud にも並び、バージョン 6 が最新だと案内されている。
3. 本来、アップグレードが許されるなら Defender の修正ガイダンスに従えるが、今回は上げられない、と説明した。
4. デモを開始した（「デモを kick off した」と発言）。裏側で動いており、PR が作られ、runner が起動しているところだと説明した（この間の仕組みは 5.2 の流れのとおり）。
5. runner の YAML ワークフローと、runner の実行画面を見せた。runner は、固定した Lightwell のビルドをインストールし、アプリのテストと smoke test を実行して結果を返す。
6. requirements.txt を見て、SQL parse 0.55 に留まる必要があることを示した。
7. runner の実行結果で、テストが通ったこと、コンテナーのビルドと smoke test、最後のクリーンアップが行われたことを確認した。サマリーでは、約 34 秒でエンドツーエンドのテストが終わり、リアルタイムに Lightwell からライブラリを取得して修正したこと、サフィックス付きの署名済み Lightwell 版に変わったことを示した。
8. 登壇者が確認する前に、PR は自動でマージされていた（「私が素早く動かなかったので」と説明）。この PR では、Mark 氏の runner が自動で Lightwell の新しいバージョンに更新した。自動マージの代わりに、アプリの担当者が目視で確認する運用にもできるが、今回は自分たちが作ったテストを信頼してそうしなかった、と説明している。
9. PR がマージ・クローズされると、最終ステップが動く。Ansible が webhook 経由でオーケストレーションを行い、playbook を実行して変数を埋め、GitHub にステータスを返す。runner の成功後には 2 つの playbook（コンテナーのデプロイ、VM のデプロイ）が走り、どちらも本番へデプロイされた。
10. アプリの隅に表示される内容が最新バージョンに更新され、完了した。全体で約 2 分。

> 補足：トランスクリプトでは、デモの途中で画面を切り替えながら話しており、手順 4〜9 の個々の画面操作（どのボタンを押したか）は音声からは確認できません。上の手順は、語られた内容の順に整理したものです。

## 7. 注意点・発表者の気付き

- Lightwell の修正が提供されるのは、対象のパッケージが Lightwell に含まれている場合です。パッケージが利用可能かは playbook が確認します。
- 上流にパッケージのメンテナーがいなければ、修正を上流へ戻せません（上流にメンテナーがいる必要がある）。
- すべての脆弱性には対応できず、優先順位は顧客の要望と CVE のスコアで決まります。最も重大なものから順に対応を進めている、という説明でした。
- 1 つのパッケージ修正で解決する脆弱性の数は異なり（デモは 5 件、25 件を抱えるものもあり得る）、アプリによってはデプロイを段階的にずらす必要が出る場合があります。
- 登壇者は、デモを「大きなリスクを取る」ものとして始めています。デモ中は、PR が確認前に自動マージされました。
- Network と Clearinghouse の料金は、発表では触れていません（Network は年間サブスクリプションと説明されたのみです）。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 最新版へ上げられないアプリでも、現在のバージョンを保ったまま、署名された修正済みパッケージで脆弱性に対応できる。
- 既存の CI/CD パイプラインやテストを変えずに導入できる。デモでも新しいパイプラインやテストは不要だった。Ansible の顧客なら、設定は数時間で済む。
- 検出から本番反映まで約 2 分（デモ）。コンテナーと VM の両方に反映できる。
- テストに失敗すれば、本番には何も起きず、PR に記録が残る。
- RHEL runner により、本番と同じ RHEL でテストでき、差異を減らせる。マネージド runner なら、インフラ管理やアップデートの手間が要らない。
- スキャナー、CI/CD、デプロイ先は自分の環境に合わせて選べる（オンプレミスの OpenShift と Azure の VM の組み合わせなど）。

## 9. まとめ

Project Lightwell は、アップグレードできない古いアプリでも、現在のバージョンを保ったまま、修正済みのパッケージを使えるようにする上流の脆弱性修正サービスで、セルフサービスの Network と、手厚い支援の Clearinghouse があります。デモでは、Dependabot が検出し、Ansible が Lightwell の利用可否を確認して PR を作り、今日 GA になった RHEL runner が約 34 秒でテストし、成功後にコンテナーと VM へ約 2 分で本番反映する流れを見せました。登壇者は、既存のパイプラインに少し足すだけでアプリを止めずに脆弱性に対処できると呼びかけ、詳細は終了後に話すと締めくくっています。
