# BRK421 Operate a global AKS fleet across regions, edge, and sovereign clouds

## 1. はじめに

このセッションは、Azure Kubernetes Service（AKS）のクラスターが複数のリージョンやエッジ、ソブリン環境に広がったときに、どう運用を揃えていくかを扱います。前半は、JetBlue の事例をもとにした「小さなクラスターに分け、フリートとして束ねて管理する」という考え方と、Azure Kubernetes Fleet Manager の機能の説明です。後半は、オンプレミスなどのコンピュート（GPU を含む）を既存の AKS クラスターのワーカーノードとして取り込む **AKS Flex Node**（public preview）の紹介です。

Fleet Manager のデモが 3 つ、Flex Node のデモが 2 つ（GPU ノードの取り込みと、接続断への耐性）あり、画面操作を伴う説明が多いのが特徴です。Kubernetes を本番で複数環境にまたがって運用している方が、運用負荷を増やさずに規模を広げる方法を知るための内容です。

## 3. 何に関する発表か

Kubernetes が AI やモダンなアプリの実行基盤として広がるにつれ、クラスターの数と置き場所が増え、運用が複雑になります。このセッションでは、その課題に対して Microsoft が AKS に何を用意しているかを、次の流れで説明します。

1. AKS の方針と、Kubernetes の利用状況（CNCF や Gartner の数値）
2. JetBlue がたどった道のり（VM から単一の大きなクラスター、そして小さな複数クラスターとフリート管理へ）
3. Azure Kubernetes Fleet Manager による「一貫した運用」「自信を持った変更」「成長への備え」
4. Fleet Manager のデモ（クラスターの登録、アップグレード、Flux を使ったワークロードのロールアウト）
5. AKS Flex Node（オンプレミスの GPU マシンを AKS クラスターに参加させる）と、接続断への耐性（disconnect tolerance）のデモ
6. まとめと、関連セッションの案内

## 4. 発表者が伝えたいメッセージ

メッセージは、**「クラスターが増えても、1 つのフリートとして運用する」**ことです。JetBlue は、1 つの巨大なクラスターに戻りたくはないが、小さなクラスターの利点を保ったまま、管理は 1 か所にまとめたいと考えました。Shuman 氏によれば、これは多くの組織に共通する流れで、VM から Kubernetes に移行し、アプリとクラスターが増えたところで、更新、デプロイ、運用を場所を問わず揃える段階に進みます。

もう一つは、AKS を「どこでも」動かせるようにするという方針です。Azure のリージョン、ソブリンクラウド、マルチクラウド、パートナーのハードウェア、エッジデバイスのどこでも、同じ Kubernetes の体験（同じ API、同じツール）で使えることを目指しています。Flex Node はその最新の具体例です。

## 5. 発表内容の詳細

### 5.1 Kubernetes と AKS の位置づけ

冒頭で Shuman 氏は、会場に「本番で Kubernetes を動かしている人」「複数環境で動かしている人」を挙げてもらっています。

Kubernetes は、ワークロードのスケジューリング、コンピュートリソースの調整、更新の管理を担い、ビジネスの需要が増えてもサービスを動かし続けます。AI では、GPU 容量の割り当てや、モデルのサービングもアプリケーションのサービスと並べて扱います。Shuman 氏は、こうした Kubernetes の利用状況として、次の数値を紹介しています。

| 出典 | 内容 |
| ---- | ---- |
| CNCF の調査 | コンテナーのユーザーの 82% が Kubernetes を本番で運用 |
| CNCF の調査 | AI モデルをホストしている組織のうち、66% が推論ワークロードに Kubernetes を使用（音声上は "generic AI models" と聞こえます） |
| Gartner（予測） | 2028 年までに、新しい AI デプロイの 95% が Kubernetes を使う |

AKS のミッションは「Kubernetes でより多くを達成できるようにする」ことで、2 つの原則に導かれています。1 つはコミュニティと共に作るベンダーニュートラルなオープンソース、もう 1 つは Azure のエコシステム（クラウド規模のデータと AI の機能）の活用です。この 2 つの原則から、6 つの投資領域が決まっています。トランスクリプトで確認できる領域は次のとおりです（項目の区切りが音声認識の都合で確定できず、5 つしか数えられません）。

- AKS everywhere（Azure、エッジ、ソブリン環境へ実行場所を広げる）
- ワークロードの保護と secure by default（音声上は "Proactive workloads and secure by default" と聞こえ、2 つの領域に分かれるかは確定できません）
- 開発者向けに、AI 駆動のコーディングから本番運用までを支える production-ready な AKS
- 高性能な AI 推論
- ビジネスの成長に合わせてコンピュートを確保する elastic capacity

Microsoft は CNCF プロジェクトへの最大級の貢献者の 1 つで、貢献、採用、寄贈を行っているとのことです。また、Microsoft 社内のチームも Bing、Office 365、Teams、Xbox、GitHub Copilot などの主力サービスのために、AKS で数百万のコンテナーワークロードを運用しています。そこで得られる知見（キャパシティの効率的な使い方、更新の安全な展開、問題の素早い診断）が、AKS のロードマップに反映されていると説明しています。

### 5.2 AKS をどこで動かすか

GPU をデータの近くに置きたい、レイテンシーやデータソブリンティの要件がある、すでに持っているインフラを使いたいなど、複数の環境にまたがって実行する場面は多くなっています。AKS は Azure リージョン、ソブリンクラウド、マルチクラウド、パートナーのハードウェア、エッジデバイスを選べるようにしながら、それらすべてで一貫した Kubernetes の体験を提供する、と説明しています。

### 5.3 JetBlue の事例

JetBlue の Ameen 氏は登壇できなかったため、Shuman 氏が事例を紹介しています。

**出発点**：JetBlue は、VM とオンプレミスのデータセンターで、大きなアプリケーションを 1 つの単位として運用していました。小さな変更でも全体を再デプロイする必要があり、メンテナンスとパッチ適用に大きな労力がかかっていました。チェックイン、フライト変更、ゲートへの案内を支えるアプリなので、止められません。

**第 1 段階**：大きなアプリを小さなサービスに分割してコンテナー化し、Azure に移行しました。ただし、すべてを 1 つの大きな共有 AKS クラスターに載せ、Azure CNI で、ノードと Pod が同じサブネットから IP アドレスを取る構成でした。成長するにつれて IP アドレスが枯渇し、スケールやアップグレードのたびに同じ仮想ネットワークのサブネットから IP を消費するため、**規模の上限（hard ceiling）**とクラスターを最新に保つことの難しさにつながりました。Shuman 氏は、コンテナー化は必須だが、クラウドネイティブな形で作ることも必要だという教訓だとしています。

**第 2 段階（4 つの対応）**：

1. **小さなクラスター**：大きな 1 つから、それぞれ明確な目的を持つ小さな複数のクラスターへ。メンテナンスの計画と変更の制御が容易になりました。
2. **ネットワーキング**：Azure CNI overlay を採用して IP の制約に対処。Pod 専用の IP アドレスプールを使うため、Pod を増やしても同じサブネットから IP を取らなくなりました。
3. **AKS の機能の活用**：トラフィック制御とネットワーク管理のためのサービスメッシュ（音声上は "CDN and STO" と聞こえ、製品名は確定できません）と、イベント駆動スケーリング用のコンポーネント（"KIDA" と聞こえ、表記は確定できません）を取り入れています。機能ごとにゼロから作る必要がなくなった、という説明です。
4. **CI/CD とセキュリティ**：CI/CD に Flux と Argo CD を使い、Azure Container Registry のネイティブなアクセスと Microsoft Intra ID（音声認識の表記）を使ってセキュリティを強化しています。

**次の課題とフリート管理**：小さなクラスターは境界が明確になる一方、数が増えると追跡する環境が増えます。「個々のクラスター」ではなく「プラットフォーム全体」をどう管理するかが課題になりました。JetBlue は、小さなクラスターの利点を残したまま管理を 1 つのフリートにまとめるため、Azure Kubernetes Fleet Manager の評価と試行に Microsoft と取り組んでいます。求めているのは、次の 3 点です。

| 柱 | 内容 |
| ---- | ---- |
| Consistent operations | 構成、ポリシー、GitOps（音声上は "get ops" と聞こえます）を 1 回定義して、すべてのクラスターに適用する |
| Confident change | アップグレードを巨大な 1 回のメンテナンスにせず、段階（ウェーブ）に分けて実施する。アプリのロールアウトも同様に、検証済みの更新を後からフリート全体に適用する |
| Ready for growth | クラウドに加えてオンプレミスやハイブリッドにも広げ、1 つのフリートで同じ運用モデルを保つ |

Shuman 氏は、JetBlue の歩み（VM から Kubernetes へ、クラスターとアプリの増加、そしてクラスターを束ねる段階）が、多くの組織に共通する流れだと述べています。

### 5.4 クラスターの運用を支える AI エージェント

Simon 氏は Fleet Manager の説明に入る前に、Azure 上でクラスター管理に使える Agentic AI の選択肢を 3 つ紹介しています。

| 名称 | 説明 |
| ---- | ---- |
| Azure Copilot | Azure 全体に対応するサービス。AKS クラスターの問題の診断や、解決できない場合のサポートチケットの起票を支援 |
| AI investigator for AKS（プレビュー） | クラスター内で動く、切断された（disconnected）体験。Azure の内外どちらのクラスターでも利用可能 |
| Azure SRE agent | Log Analytics ワークスペースに接続してテレメトリを参照できる。ロールベースのアクセス制御と、制限されたコンテンツ制御を与え、トラブルシューティングと、場合によっては修復も支援する |

SRE agent については、エージェントが対処できる問題であれば、人間の SRE を夜中に起こさずに済む、と説明しています。

### 5.5 Fleet Manager の概要と一貫した管理

AKS クラスターに加え、エッジ向けの AKS on Azure Local や AKS on Bare Metal、さらに Arc-enabled Kubernetes クラスターなら場所を問わず、Fleet Manager に取り込めます。一貫した管理操作、Kubernetes リソースの段階的なロールアウト、AKS クラスターの安全なアップグレードを行えます。

- 1 つの Fleet Manager に、種類を問わず **最大 1,000 のクラスター**を追加できます（複数の Fleet Manager を作ることも可能）。
- Azure Policy を使って、新しく作成されたクラスターの Fleet Manager への登録を強制できます。
- クラスターを登録するとメンバーラベルが付き、複数のラベルも設定できます。名前ではなくラベルで対象を選べるようになります。

ラベルを使った基盤の上で、次の機能が使えます。

- **マルチクラスターアップグレード**：AKS の Kubernetes バージョンとノードイメージのアップグレード。
- **Cross-cluster networking**：マネージドな Cilium multi-cluster ソリューション。
- **AKS identity binding のスケール管理**。

もう一つの選択肢が **hub cluster** の追加です。Microsoft が代わりに管理する AKS クラスターで、次のような機能が使えるようになります。

- 複数クラスターへの Kubernetes リソース管理（例: cluster role binding の配布）
- GitOps とリソース配置（resource placement）
- **マネージド fleet namespace**：名前空間を 1 回作成し、リソースクォータ、ネットワークポリシー、Azure RBAC の制御を設定して、複数クラスターに配布できる

#### Cross-cluster networking（GA）

Ignite で一般提供（GA）が発表されました。Pod 間通信のための高性能な east-west のマルチクラスターネットワーキングで、eBPF ベースの Cilium multi-cluster を使っています。

- 1 つの cross-cluster network に最大 **255 のメンバークラスター**を追加できます。
- 1 つのフリートに複数のネットワークを作れますが、メンバークラスターが同時に参加できるのは 1 つだけです。
- ネットワークへの参加対象は、クラスターのラベルで選びます。
- サービスにアノテーションを付けてデプロイすると、他のすべての参加クラスターにローカルサービスとして表現されます。複数クラスターに同じサービスを置いて global として公開すれば、ユーザーに影響を与えずにサービスをフリート内で動かせる「ワークロードの透過性」が得られます。
- Advanced Container Networking Services の可観測性ツールで、クラスターをまたぐトラフィックフローの確認とデバッグができます。

#### AKS identity binding（GA）と Fleet Manager による管理（プレビュー）

AKS identity binding 自体は Ignite で GA になりました。バインディングは、名前、ユーザー割り当てマネージド ID、クラスター上で使用を許可する subject で構成されます。Fleet Manager で管理する部分は、Ignite でプレビューとして発表されました。Fleet Manager ではプロファイルを作り、どのクラスターに配置するかを指定します。例では、`app pool equals prod` というラベルで 3 つのクラスターを対象にし、3 つとも同じバインディングが配置されます。

Fleet が配置したバインディングは、クラスター側で直接変更できないよう強制されます。現時点では Azure CLI で作成・管理でき、ポータル体験は「近日中」に提供される予定です。

### 5.6 Fleet Manager による自信を持った変更

JetBlue の 2 つ目の柱である「confident change」には、2 つの領域があります。

**クラスターアップグレード**：Kubernetes とノードイメージのアップグレードを複数クラスターに調整して実施し、本番より先に非本番クラスターを更新します。現在は AKS と Azure のみが対象で、今後拡張する予定です。

**ワークロードのロールアウト**：Deployment、Service、cluster role binding など Kubernetes リソースを配布します。最近 Flux を使う方法も発表されました。

#### 更新戦略（update strategy）

- 再利用可能なリソースで、更新したい対象に応じて複数作成できます。
- **ステージは順番に、グループは並列に**実行されます。
- 同時に更新するクラスター数を制御できます。
- 大規模環境では 1 つも失敗しないことは珍しいため、**失敗許容（failure tolerance）**を、割合または固定数で設定でき、その範囲内なら更新を継続します。
- 承認（approval）と、開始時刻を指定する start gate も使えます。

自動アップグレードも同様の仕組みです。OS と CVE パッチを適用したマシンイメージがリリースされると、画面にあるのと同じ更新が自動的に作成されて開始されます。セキュリティパッチの適用後にノードプールをスケールアウトした場合も、新しいノードには更新済みのパッチが適用されます。Simon 氏は、AKS のアップグレード機能の全体が、マルチクラスターアップグレードで使えるようになっていると述べています。

#### リソース配置（resource placement）

想定されるシナリオは 2 つです。リージョン A のクラスターが停止または復旧不能になったときに別リージョンのクラスターへ素早くリソースを移す場合と、ビジネスポリシーの変更でクラスターをあるリージョンから別のリージョンに移す場合です。クラスター自体の作成は比較的簡単ですが、ワークロードの移動には、デプロイパイプラインなどの手動更新が必要になりがちです。Fleet Manager の resource placement では、クラスターにラベルや一致するプロパティがあれば、異なるリージョン、場合によっては別のクラウドやエッジ環境にも、同じアプリのリソースを再デプロイできます。AKS、Arc-enabled、エッジのいずれにも対応しています。

仕組みは次のとおりです。

1. Fleet Manager の hub cluster に、cluster resource placement（または resource placement）という Kubernetes リソースを作成します。
2. 対象のクラスターを、ラベルまたは特定のクラスターで指定します。選択できるプロパティには、特定の VM SKU のノード数、メモリや CPU の空き（または割り当て済み）の量などがあります。
3. 標準のローリング更新を使うと、変更はすぐにフリートへ適用されます（surge 設定を使用）。メンバークラスターに書き込まれるリソースは、必須ではない override で変更できます。
4. 多くのユーザーがより細かい制御を求めたため、**rollout strategy**（クラスターアップグレードの更新戦略とよく似た、再利用可能な戦略）が導入されました。クラスターを選んでも直ちに展開せず、戦略に従い、開始のタイミングを選べます。

#### Managed Flux extension の Fleet Manager への導入

先週発表された機能で、Microsoft Managed Flux extension を Fleet Manager にインストールできるようになりました。従来は、新しいクラスターを追加するたびに、そのクラスターに Flux を用意し、リポジトリやコントローラーが新しい配布先として認識するための設定作業が必要でした。

Fleet Manager では、hub cluster に Flux をインストールして Git リポジトリを hub cluster に向け、個々のクラスターへのリソースのロールアウトは Fleet Manager で制御します。各クラスターには、Flux extension がインストールされてコントローラーとカスタムリソースがあればよく、ベースラインの設定は不要です。Flux が reconcile を行い、Fleet がクラスター間のロールアウトを制御するため、dev、test、production の順に配布したり、ブルーグリーン型のデプロイを戦略で制御したりできます。

### 5.7 AKS Flex Node（public preview）

Shuman 氏は、AKS を「ビジネスが必要とする場所すべて」で動かせるようにする最新の提供物として、Flex Node for AKS を紹介しています。複数のクラスターを一緒に運用し、個々の AKS クラスターが使えるコンピュートを拡張するためのものです。

- CPU、GPU、仮想マシン、ベアメタルなど、クラウド、オンプレミス、パートナーのキャパシティにある任意のコンピュートを使えます。
- すでに Azure で使っている AKS クラスターに参加させるため、同じツール、ポリシー、セキュリティで統一された運用ができます。
- AKS のコントロールプレーンは Azure に残り、オンプレミスなどのコンピュートはワークロードの実行に専念します。マネージドなワーカーノードとして既存の AKS クラスターに参加し、x64 と ARM64 のどちらにも対応します。

#### お客様のシナリオ

Shuman 氏は、現在取り組んでいる実際のお客様の事例を紹介しています。このお客様は、何百、何千もの店舗を持ち、一部の店舗を、顧客がローカルで動くテクノロジーに触れられる「experience center」に変えようとしています。そのためにローカルの GPU を購入しました。Flex Node を使えば、拠点ごとにクラスターを作らず、ローカルの GPU を同じクラスターに参加させるだけで済みます。ワークロードは、他のリージョン、Azure VM、支店のサーバーや VM でも動かせます。ノードが参加した後は、マネージドソリューションとして Microsoft がセットアップを担い、他の AKS ノードと同様に Pod がスケジュールされます。

### 5.8 Disconnect tolerance（近日提供）

ローカルで動かすアプリがミッションクリティカルになると、「管理用の接続が切れたらどうなるか」という議論になる、と Shuman 氏は述べています。Kubernetes は、ホスト側の Kubernetes サービスと API サーバーの間の接続に厳しい要件があります。そこで Flex Node に **disconnect tolerance** を追加します。近日提供で、すべての Flex Node でデフォルトで有効になります。接続断の間も継続性と耐障害性を保ち、再接続後に Pod が退避（evict）されないようにします。切断中に Kubernetes のサービスが再起動しても耐えられる、とも説明しています（ノードの再起動を模したものです）。

また、GPU ノードとクラウドの間を流れるのは管理トラフィックで、アプリケーションのデータは、すべてローカルで処理されます。そのため、低レイテンシーとデータソブリンティの要件の両方を満たせると説明しています。

### 6.1 デモ 1：クラスターを Fleet Manager に追加する（Simon 氏）

Azure portal で行われました（Azure CLI や Terraform でもできると説明されています）。

1. 既存の Fleet Manager に、新しい AKS クラスターを 2 つ追加します。
2. 1 つのクラスターに update group を設定します（マルチクラスター更新で使うもの）。現在はラベルを使った指定にも対応しており、update group の定義は必須ではありません。
3. 登録後、クラスターに付いたラベルを編集します。あらかじめ、クラスター名、メンバー名（フリート内でクラスターを表すプロキシリソース）、サブスクリプション、Azure リージョン名、リソースグループ名のラベルが設定されています。カスタムラベルも追加できます。
4. 2 つ目のクラスターには、cross-cluster network に参加させるためのラベル（network を prod network に設定）と、後のアプリのロールアウトのデモで使う app group のラベルを設定します。既存のラベルを選んで値を変更し、適用します（入力中に打ち間違えた、と話しています。最終的な値は聞き取り不明瞭です）。

### 6.2 デモ 2：マニュアルのアップデート実行（Simon 氏）

クラスターの更新を実行する手前までの設定が、画面で示されました。Simon 氏は「開始はしていない」と述べています。

1. 既存の戦略を選びます。この画面では、クラスターを個別に選ぶ必要はありません。
2. Kubernetes のバージョンを 1.37 に設定します（音声認識の都合で、バージョン表記が確定できません。後で "1.37.0" とも述べています）。
3. 一貫したノードイメージ（consistent node image）を設定します。すべての環境のすべてのクラスターが同じノードイメージを受け取ります。Simon 氏は、規制の厳しい環境で重要だと説明しています。
4. 内容を確認します。すべてのクラスターが同じノードイメージ（Ubuntu 2404 のノードイメージ）を使っているため、全クラスターに同じものが適用されます。フリート内にさまざまなノードイメージがある場合は、一貫した最新のバージョンが選ばれます。
5. ステージの構成を確認します。最初の 2 つのステージは各 1 クラスター、3 つ目のステージは 2 クラスター、最後のステージは 1 クラスターです。承認が有効で、並列数と待機時間を指定できます。このデモでは、ステージ間の一時停止はありません。

### 6.3 デモ 3：Flux を使った Helm チャートの段階的ロールアウト（Simon 氏）

AKS store demo アプリケーションを Helm チャートとして、5 つのクラスターに、ロールアウト戦略を使って配布します。クラスターには Flux がインストール済みで、hub cluster にも Flux があります。配布するのは、Helm repository（チャートの取得元）と Helm release（デプロイに使う内容）の 2 つのリソースです。Simon 氏は、一部の手順を早送りしたと述べています。また、この体験はまだプレビューで、YAML を貼り付ける操作も含まれると説明しています。

1. hub cluster に名前空間を作成し、特定のラベルを持つすべてのメンバークラスターに配布します。5 つのクラスターが選ばれ、ステータスはすべて緑になります。dev クラスターで名前空間を確認します。
2. 作成した名前空間を Flux が管理できるように、role binding、role、service account の 3 つを作成し、同じメンバークラスターに配布します。配布は成功します。
3. 再利用可能な rollout strategy を作成します。ポータルのフォームでも作成でき、クラスターアップグレードの更新戦略とよく似た構成です。
4. 「apply a YAML」のショートカットで、hub cluster を Git リポジトリに接続します。Flux の Git リポジトリとカスタムリソースを使って、Helm release と Helm repository を hub cluster に配置します。
5. 先ほどの戦略を使ってロールアウトします。戦略による制御を指定しているため、この時点ではまだ開始されていません。
6. ポータルでロールアウト実行（rollout run）を作成します。名前を付け、namespace を選び、resource placement（対象クラスターを決める）と戦略を選んで作成します。開始前に、各ステージで何が行われるか確認できます。
7. 開始します。dev クラスターの Helm の項目で、Helm release が進行していることが確認できます。これは、クラスターに既にある Flux コントローラーが行っています。Simon 氏は、このクラスターには一切触れていないと述べています。結果が気に入らなければ、ロールアウトを停止もできます。
8. prod クラスターで、この名前空間でフィルターすると何もありません。dev や test より先に本番にデプロイされていないことが確認できます。
9. 本番リリースの承認（approval）を行います（「問題なし」の趣旨で承認）。残りの 2 つのステージに進みます（一部は早送り）。
10. test クラスターで、Service と Ingress を確認します。store アプリケーションには Web フロントエンドがあり、クリックすると store のフロントエンドが表示されます。

この結果、ソースコントロールにある Helm チャートを、fleet の resource placement と AKS 向けの Flux extension により、5 つのクラスターに制御された形で展開できました。

### 6.4 デモ 4：Flex Node でオンプレミスの GPU を AKS クラスターに参加させる（Shuman 氏）

1. オンプレミスにある、お客様の GPU マシンを示します。Azure portal 上では、Arc-enabled マシンとして見えます（機種名は "media JSON store" のように聞こえ、音声認識の都合で表記が確定できません）。

4. エージェントのデプロイは Microsoft が行います。しばらくすると、ノードが利用可能になり、flex node pool とオンプレミスの GPU がクラスターのノードとして追加されたことが確認できます。この時点では、Deployment はまだ開始されていません。

### 6.5 デモ 5：disconnect tolerance（Shuman 氏）

1. 先ほどのアプリの状態から始めます。ノードに SSH 接続し、ノードのステータスが Ready であることを確認します。
2. 簡単な Python スクリプトでファイアウォールルールを適用し、接続を断ちます。4 つのファイアウォールルールが適用されました。
3. 更新すると、ノードのステータスは Unknown になります。`kubectl get nodes` では API の応答を取得できません。
4. それでも、デモアプリは別の角度の動画を処理し続けています。
5. 次に、Kubernetes のサービスを再起動します（ノードの再起動を模したものです）。再起動後も、同じアプリで別の動画をレンダリングでき、アプリは動き続けます。
6. ネットワークを再接続します。しばらく時間が経った後にノードが戻っても、すべての Pod は動いたままで、退避も再デプロイもされません。

## 7. 注意点・発表者の気付き

- **JetBlue の教訓**：Azure CNI で 1 つの大きな共有クラスターを作ると、ノードと Pod が同じサブネットから IP を取るため、スケールとアップグレードの両方に上限がかかります。コンテナー化だけでなく、クラウドネイティブな設計が必要でした。
- **小さなクラスターの代償**：クラスターが増えると追跡すべき環境が増えるため、フリート管理が必要になります。
- **失敗を前提にする**：大規模環境で 1 つも失敗しない更新は珍しいため、失敗許容の設定が用意されています。
- **対応範囲**：クラスターのアップグレードは、現在 AKS と Azure のみが対象です。resource placement は、AKS、Arc-enabled、エッジを含む任意の Kubernetes クラスターで動きます。
- **提供状況**：cross-cluster networking と AKS identity binding は GA、identity binding の Fleet Manager による管理はプレビュー（ポータル体験は近日）、Flex Node は public preview、disconnect tolerance は近日提供です。AI investigator for AKS はプレビューです。なお、Fleet Manager のハブ上でのロールアウト体験（namespace の作成など）は、プレビューで、さらに作り込む予定とのことです。
- **通常の Kubernetes との違い**：標準の Kubernetes では、一定時間後にノードが戻っても API サーバーがノードを not ready と見なし、Pod を退避しようとします。disconnect tolerance はこれを避けるためのものです。

## 8. 利用者にとっての利点

- **JetBlue の事例**：VM 上で大きな単位として運用していたアプリを、小さなサービスとコンテナーに分けて AKS に移行しました。IP 枯渇という上限には、Azure CNI overlay で対処しました。現在は Fleet Manager を評価しており、一貫した運用、段階的な変更、ハイブリッドへの拡張を期待しています（発表では、具体的な成果の数値は示されていません）。
- **運用の一貫性**：ラベルを使い、最大 1,000 クラスターを 1 つの Fleet Manager で扱えます。名前を指定せずに対象を選べます。
- **安全な変更**：ステージ、並列数、失敗許容、承認、開始時刻の指定で、非本番から本番へ順に変更を展開できます。ノードイメージを揃えることは、規制の厳しい環境で重要だと説明されています。
- **ワークロードの移動**：クラスターが停止した場合やビジネスポリシーでリージョンを移す場合に、デプロイパイプラインの手動更新なしに、ラベルで選んだ別のクラスターへ再デプロイできます。
- **Flux との連携**：新しいクラスターごとの Flux の設定作業が不要になり、dev、test、production の順やブルーグリーンも戦略で制御できます。
- **Flex Node**：拠点ごとにクラスターを作らず、ローカルの GPU を既存のクラスターに参加させられます。アプリのデータはローカルで処理され、低レイテンシーとデータソブリンティの要件を満たせます。
- **接続断への耐性**：接続が切れても、ローカルのアプリは動き続け、再接続後も Pod が退避されません。

## 9. まとめ

Shuman 氏は最後に、次の 5 点を振り返っています。

1. Kubernetes を 1 つのフリートとして運用する。
2. AI とアプリを、ビジネスが必要とする場所で実行する。
3. AKS の体験を、選んだ任意のコンピュートに広げる（Flex Node）。
4. 一貫性、制御、自信を持って変更を届ける（Fleet Manager）。
5. 運用の複雑さを増やさずに、フットプリントを拡大する。
