# BRK440 Cobalt 200: Delivering Azure's best performance and efficiency

## 1. はじめに

このセッションは、Azure の Arm ベース CPU である **Cobalt 200 の仮想マシン（VM）が一般提供（GA）になった**ことを受けて、その設計の考え方、OpenAI による本番利用の結果、新しい VM ファミリー、Arm64 への移行の進め方を紹介するものです。

発表の中心は「価格性能（price performance）を高めるには、チップだけでなくサーバーやラック全体、さらにワークロードまで一緒に最適化する必要がある」という考え方です。Cobalt 100 と比べて最大 50% の性能向上、OpenAI の ChatGPT 基盤での本番トラフィックにおけるスループット 45% 向上といった数値が示されました。これから Arm64 への移行を検討している開発者・インフラ担当者に向いた内容です。

## 3. 何に関する発表か

Cobalt は、Microsoft が Arm の CPU コアを組み合わせてカスタマイズし、Azure 向けに作っているチップとインフラです。発表の冒頭で、Arm は命令セットアーキテクチャ（Intel や AMD の x86 に相当するもの）であり、同時に企業名でもあること、Arm 社が「IP」と呼ばれる部品を提供し、Microsoft がそれを組み合わせて Cobalt のチップとインフラを作っていることが説明されました。

発表の流れは次のとおりです。

2. 価格性能を出すための設計アプローチ（ワークロード分解、ラックスケールのモデル化）

9. 提供リージョンとロードマップ、まとめ

## 4. 発表者が伝えたいメッセージ

最大のメッセージは、**価格性能の高さは製品設計の最初から作り込むものであり、チップ単体では決まらない**という点です。Cobalt の開発チームは、数年前に「Azure で最高の perf per dollar（1 ドルあたりの性能）を出す」という目標を示すステッカーを作り、シリコン、サーバー、その上のワークロードを一体で最適化してきたと説明しています。

もう 1 つのメッセージは、Arm64 への移行が以前より大幅に容易になったことです。OpenAI は、コーディングエージェントの Codex を使ってマルチアーキテクチャ化を進めたと語り、Azure VM Sizes チームの登壇者は、数年前には顧客によって 12 か月、長い場合は 18 か月かかった移行について、GitHub Copilot を使った Microsoft 社内のチームが約 4 か月で終えた例を紹介しました。

そして、Cobalt は単発のチップではなく**複数世代にわたるプログラム**であり、Arm への投資（ソフトウェア、スキル、運用手順）は次世代にも引き継がれるという点が、締めくくりで繰り返されました。

## 5. 発表内容の詳細

### 5.1 Cobalt 200 の GA と、価格性能を出す設計の考え方

セッション冒頭で、Cobalt 200 VM の一般提供が発表されました。ワークロードによって差はあるものの、Cobalt 200 は**最大 50% の性能向上**を提供し、Azure の中で最も価格性能に優れた選択肢だと位置づけられています。

価格性能を出す方法として、まず設計の視野を広げることが挙げられました。チップを作るだけでなく、シリコンの構成要素から最終的なラック、その電力消費、ネットワーク、接続性まで、システム全体を共同設計（co-design）・共同最適化するという考え方です。

### 5.2 ワークロードの分解とラックスケールのモデル化

Azure では、顧客のワークロードと Microsoft 自身の製品・サービスのワークロードが非常に幅広く動いています。ただし、それらすべてを将来製品のモデルに通すことはまだできません。そこで、ワークロードを構成要素に分解し、小さなベンチマーク（ミニベンチマーク）として扱っています。その数は**合計で約 140** です。発表では次の例が挙げられました。

| ワークロード | 分解のイメージ |
| --- | --- |
| Azure SQL | TPC 系のベンチマークに相当すると捉えている（音声認識の都合で正確な名称が確定できません） |
| Azure Storage のバックエンド | 3 分の 2 がストレージ特有の処理、残り 3 分の 1 がデータを処理する整数演算 |
| Teams（IC3）のワークロード | Teams 通話でのメディア処理（トランスコード）。ネットワーク処理、実際のトランスコード、Web サービングの組み合わせ |

次に、まだ作っていないインフラのラックスケールのモデルを作り、選択肢を評価します。モデルの変数には、コア数、コアアーキテクチャ、キャッシュといったシリコン固有の要素に加えて、ストレージ容量、メモリ、システムに供給するネットワーク帯域、ファンの数、サーバーの高さ、ラックの消費電力まで含まれます。シリコンの性能・消費電力をブロック単位でモデル化し、選択肢同士の依存関係も考慮するため、すべてを自由に組み合わせられるわけではありません。

発表では、あくまで**架空の構成例**として、いくつかの候補構成を比較するスライドが示され、その中の構成 C を例に説明されました。構成 C はコア数が適度で、キャッシュが増えており、シミュレーション上でコアあたりの性能が最も高くなります。コアあたりのコストはやや高くなるものの、狙いは性能あたり TCO、つまり価格性能の最適化にある、という説明でした。

### 5.3 Cobalt 200 のシリコン

Cobalt 200 のチップについて、次の仕様が説明されました。

| 項目 | 内容 |
| --- | --- |
| CPU コア | Arm Neoverse V3（Arm の最新の高性能 CPU コア）を 132 コア |
| 製造プロセス | TSMC の 3 nm プロセス |
| メモリコントローラー | カスタム設計で、メモリの暗号化がデフォルトで有効 |
| 電力・性能制御 | システム上の個々のコアごとに、性能、周波数、電圧を調整可能 |
| キャッシュ | コアごと・システムレベルとも大きめのキャッシュ |
| アクセラレーター | 共通処理をオフロードする新しいアクセラレーター |

**アクセラレーター**は、設計時のワークロード分析から生まれました。140 のミニベンチマークのうち約 30% が、圧縮・展開、暗号化・復号をかなりの量で行っていたためです。Arm v3 のコアも圧縮や暗号処理は得意ですが、専用シリコンには及びません。そこで Cobalt 200 では、これらの処理を CPU から取り除き、専用ブロックで高い性能と低い消費電力で処理します。アクセラレーターはダイ上では非常に小さいものの、これらの共通処理で約 30% 高い性能が得られ、処理にかかるレイテンシは 15%（発話は "15% the latency to get the work done"）で済むと説明されています。登壇者は、Azure SQL をはじめとする **Microsoft 内部のプロダクト向け**の機能として紹介しており、顧客の VM に直接公開される機能とは述べていません。

### 5.4 Processor mode：コアごとの周波数・電圧制御

コアごとに電力と性能を制御できる点は、Arm のエコシステムでは新しい取り組みだと説明されました。周波数を変えること自体はクラウドで新しくありませんが、顧客のニーズには幅があります。最大限の性能を求め、多少のばらつきを許容する顧客もいれば、予測可能で一貫した性能を最優先する顧客もいます。

そこで、VM の作成時、またはライフサイクルの中で選べる **processor mode** が用意されました。

| モード | 特徴 |
| --- | --- |
| Opportunistic | 最大性能を狙う。多少のばらつきがある |
| Deterministic | 高いが、決定的（予測可能）な性能 |

Azure で VM を作成する方法は多様ですが、そのいずれの方法でもこのパラメーターを変更できると説明されました。

### 5.5 予測可能な性能と、周波数のチャート

Arm をクラウドで使う大きな価値として、**CPU をより高い負荷まで予測可能に使い切れる**点が挙げられました。Cobalt 100 や 200 で購入する 1 vCPU（1 vCore）は**物理コア 1 つ分**です。SMT（ハイパースレッディング）のようにリソースを共有しないため、ワークロードのサイジングで、コアをより高い負荷で使っても性能を見通しやすく、場合によっては必要なコア数の総量を減らせるという説明です。

これを示したチャートの内容は次のとおりです（縦軸は最大周波数に対する割合、横軸は負荷をかけたコアの割合）。

- 負荷には、SPECrate 2017 のうちトランスコードを行う部分を使用（音声認識の都合で表記が確定できません）。
- Cobalt 200 は、opportunistic を有効にした状態でも、負荷をかけたコアが 80% を超えるまで周波数がほぼ変わらない。
- 85% 程度（聞こえた表現は "85 and change"）まで負荷をかけても、失う周波数は最大周波数の 2%。動作周波数は 3.4〜3.5 GHz（発話は「3.5 or 3.4 gigahertz」）。
- 他の CPU サプライヤーの VM（緑とピンクの線）は、負荷を半分かけた時点で最大周波数を約 10〜14% 失い、負荷が増えるほど低下が続く。

登壇者は、他社の製品が悪いという意味ではないと断ったうえで、予測可能な性能と高い稼働率までの負荷をかけやすさが重要なら、Arm と Cobalt に独自の機会があると述べています。

### 5.6 サーバーとラックの設計、Cobalt 100 比の性能

最適化はチップにとどまりません。サーバー設計では次の点が紹介されました。

- 同じマザーボードに **2 ソケット**を搭載。これ自体は特に新しくないが、コストと、1 ラックあたりに提供できる容量の最適化につながる。
- 最新版の **Azure Boost** を搭載し、ネットワークとリモートストレージを高速化。
- 鍵の保護に **Azure integrated HSM** を搭載。
- ファンの選定（種類、数、回転数、オン・オフの制御）にも多くのエンジニアリングを費やしており、ファンの制御と性能の最適化で大きな効率が得られる。

こうした取り組みの結果として、Cobalt 100 から 200 へ、段階的な飛躍があったとされます。Microsoft 内部の評価では、一般的なベンチマークで **50% 以上**の向上、ワークロード別のベンチマークでは **Java ワークロードで 65%** の向上、データベース系ワークロードでの大きな向上が示されました。Microsoft 自身の製品でも、Cobalt 200 の性能による大きな効果が出ているとのことです。

### 5.7 OpenAI の事例（Vadim Filanovsky 氏）

Pat 氏の紹介を受けて OpenAI の Vadim Filanovsky 氏が登壇しました。氏は ChatGPT のインフラを担当しており、プロンプトを入力して送信ボタンを押してから、モデルがリクエストを受け取るまでの間には多くの CPU 処理がある、と説明しています。画面に見えているのは氷山の一角で、ChatGPT の成長、機能追加、新製品のリリースに伴い、追加のキャパシティが必要になったことが Cobalt に至った理由です。

OpenAI はもともと、リージョン、VM ファミリー、サイズにまたがるフリートにワークロードを配置しています。**マルチアーキテクチャ**にして x86 と Arm の両方に同じワークロードをスケジュールできるようにしたことで、新しいキャパシティのプールが得られ、昨年、その Cobalt のキャパシティを使えるようにしたことが、成長への対応を支えたと述べています。

#### マルチアーキテクチャ化は思ったより容易

登壇者は、マルチアーキテクチャを検討している人に向けて次のように説明しました。

- OS、フレームワーク、ランタイム、言語、ツールチェーンといった基盤の大半は、すでに両方のアーキテクチャをサポートしている。
- ソフトウェアのビルドは、コンパイルとリンク、イメージの組み立て、単体テスト、結合テスト、という再現可能で決定的な手順の連続である。どこかで失敗すれば、通常は問題を明確に示す診断が出る。この性質は**エージェントのループ**に非常に向いており、OpenAI は自社のコーディングエージェント **Codex** の助けを借りて、この変換を行った。
- 最初は共通ライブラリの変換や CI/CD システムの調整が必要で、多少手間がかかるが、その効果は将来の世代にも続く（"Convert once, benefit forever"）。
- Cobalt 100 向けにこの作業を済ませていたので、Cobalt 200 が出たときには、ほとんど作業せずに採用できた。

#### 本番環境での結果

Azure の支援で、ChatGPT スタックの一部に Cobalt 200 を限定的にデプロイし、実際の本番トラフィックの一部を処理しています。Cobalt 100 と CPU 使用率を揃えて比較した結果は次のとおりです。

| 指標 | Cobalt 100 比 |
| --- | --- |
| スループット | 45% 向上 |
| レイテンシ | 10〜40% 低下 |

登壇者はこれを「世代間の向上を超える結果」（beyond generational result）と評し、ハードウェアを 1 世代更新してこれだけの向上が得られたのはいつ以来か、と述べています。社内でも自社ワークロードでベンチマークを取り、Pat 氏が示した数値と同じ傾向だったそうです。

#### Processor mode の選択

OpenAI は processor mode も試験しています。あるワークロードの結果では、ホスト上の負荷が小さいうちは opportunistic のほうが周波数を高く保てる余地があり、負荷が高くなるとその余地は小さくなります。カーブの傾きはワークロード次第で、示されたグラフは**これまで見た中で最も悪い部類**のケースです。多くのワークロードではカーブはほぼ平坦で、終盤でわずかに下がる程度でした。

この結果から、ChatGPT のワークロードでは **opportunistic を選択**しています。他の条件が同じなら、スループットが約 10% 向上するからです。このワークロードではばらつきはあまり問題にならず、x86 側ですでに対処しているとも述べています。

#### さらに性能を引き出す 2 つの機能

1. **Neon 命令セット**：Arm の SIMD（ベクトル化）命令セットで、Cobalt と Arm ISA の過小評価されがちな機能だと紹介されました。OpenAI では、レイテンシに敏感な検索（lookup）サービスで、ホットパス上のペイロードのデコードに Neon を使い、性能向上につなげました。
2. **PMU（Performance Monitoring Unit）**：すべての Cobalt インスタンスにコア PMU が付属します。基本的な IPC（1 サイクルあたりの命令数）から top-down のマイクロアーキテクチャ分析まで、ワークロードの最適化に使えます。

締めくくりとして、Cobalt 100 は需要への対応を助け、Cobalt 200 はあらゆる測定可能な点で前世代を上回った、利用者にとっては待ち時間の短い快適な体験、OpenAI にとってはより大きな処理容量とより多くのプロンプトの処理につながる、と述べています。

続いて Amar 氏は、OpenAI は Arm64 に早くから賭けており、その成果が Cobalt 200 で現れていると語り、Vadim 氏が Cobalt 200 VM の形成にも協力したと謝意を示しました。

### 5.8 Cobalt 200 VM の仕様と VM ファミリー

Amar 氏（Azure VM Sizes チーム所属と自己紹介）が VM の側面を説明しました。

**性能の位置づけ**：Pat 氏のチャートはコアあたりの性能で、棒の長さはワークロードごとに異なるため、実際の性能向上はワークロード次第です。「最大 50%」は、Cobalt 200 VM が Cobalt 100 に対して提供するよう設計された計算性能であり、世代間の向上としては通常見られない数字だと説明しています。

**Azure Boost**：CPU を取り巻くプラットフォームで、次の向上をもたらします。

| 項目 | 向上 |
| --- | --- |
| ネットワーク帯域 | 15% 向上 |
| リモートストレージ IOPS | 20% 向上 |
| NVMe 経由のリモートストレージスループット | 10% 向上 |

**Arm64 のワークロードの広がり**：Arm64 は、クラウドネイティブ、Web ワークロード、データベース、キャッシュ、開発者のパイプラインで広がりました。これらは Azure の Arm64 上で引き続き大きく伸びています。Cobalt 200 では、さらに次のような新しい種類のワークロードに対応できるようになったと説明されました。

- エージェント型 AI サービス（AI のための CPU 周辺の処理全般）
- エンタープライズおよびインメモリ処理（vCPU あたりのメモリが多く必要）
- データ分析と検索（コンピュートの隣に大容量のローカルストレージが必要）

これを受けて VM のシェイプを刷新し、新しいサイズを追加しました。

**VM ファミリー（全 5 種）**

| ファミリー | メモリ / vCPU | 想定される用途（発表での説明） |
| --- | --- | --- |
| DPLSv7、DPLDSv7（汎用） | 2 GB | マイクロサービス、ゲームサーバー、メディアエンコード、小規模データベース |
| DPSv7、DPDSv7（汎用） | 4 GB | エージェントのオーケストレーションやツールのサンドボックスなどのエージェント型 AI サービス、小〜中規模データベース、Web・アプリケーションサーバー、キャッシュ |
| EPSv7、EPDSv7（メモリ最適化） | 8 GB | 大規模な NoSQL・リレーショナルデータベース、Redis や Memcached などのインメモリキャッシュ、ベクトル検索、エージェントのメモリストア、リアルタイム分析、メモリ集約型の EDA |
| MPSv4、MPDSv4（高メモリ最適化・新規） | 16 GB | 大規模インメモリデータベース、エージェント型 AI 向けの大規模ベクトル検索、ERP、大規模キャッシュ層、メモリ集約型の分析 |
| LPSv5（高密度ローカルストレージ・新規） | （メモリ量は発表では触れていません） | ストレージを大量に使い、データへの低レイテンシなアクセスが必要なワークロード |

> 補足：メモリ量の単位は、発話では "GB bytes" と聞こえる表現で、音声認識の都合で表記が確定できません。表では「GB」と書いています。

汎用とメモリ最適化の 3 ファミリー（DPLSv7 系、DPSv7 系、EPSv7 系）は仕様が上から下まで刷新され、MPSv4 系と LPSv5 が Cobalt 100 にはなかった**新規の 2 ファミリー**です。

LPSv5 は、他の 4 ファミリーに比べてコンピュートの隣に置かれる**ローカル NVMe ストレージが大量**にある点が特徴です。他のファミリーが vCPU あたり 55 GB（聞こえた数値のまま）であるのに対し、LPSv5 は **vCPU あたり 240 GB** で、最大サイズで**最大 23 TB** まで利用できます。それ以外のスペックは、サイズ、ネットワーク帯域、リモートストレージともに他のファミリーとほぼ同様と説明されています。

**サイズの幅**：これらの VM は 1〜128 vCPU のサイズで提供されます。2022 年に最初の Arm VM を出したときの最大は 64 vCPU、Cobalt 100 で 96 vCPU、そして今回 128 vCPU です。一方で下限も下がり、**1 vCPU の VM** が Arm64 上で初めて使えるようになりました。これは開発者から、CI/CD パイプラインを Azure の Arm64 で実行したいという要望があったためです。

**共通のスペック**：

- ローカル NVMe は、D バリアントで 7 TB まで（発話は "across the series, 7 terabytes of local NVMe with the D variants"）
- ネットワーク帯域は最大 85 Gbps
- リモートストレージは Standard、Premium SSD、Premium SSD v2、Ultra Disk に接続でき、リモートストレージのスループットは最大 70 Gbps

> 注意：Cobalt 100 の汎用・メモリ最適化 VM を使っているワークロードは、**コードを 1 行も変更せず**に Cobalt 200 で動かせる、と明言されました。

### 5.9 Arm64 への移行：以前と今

2022 年、あるいは 2024 年ごろの Arm 移行は大きなプロジェクトでした。リソースの確保、時間と費用の投資、依存関係を書き出した表の作成、スクラム、ウォールームなどが必要で、顧客によっては約 12 か月、18 か月かかった例もあり、ワークロード次第で大きく異なりました。

状況は大きく変わったとして、登壇者は、昨日 Microsoft のチームメンバーから聞いた話を紹介しました。そのチームはコードベースを Arm に移し、Cobalt 200 に載せる方法を尋ねてきたそうです。かかった期間は**約 4 か月**で、しかもコードは単純ではなく、データベースへのアクセス、ベクトルエンジン、C/C++ や一部 Java を含んでいました。使っていたのは **GitHub Copilot** です。つまり、Codex や GitHub Copilot のような AI ツールを活用して、移行の道のりを短くできるという趣旨です。

移行は、これまでと変わらず次の **5 ステップ**で進めます。

1. Assess（評価）
2. Build（ビルド）
3. Validate（検証）
4. Deploy（デプロイ）
5. Optimize（最適化）

### 5.10 最適化のヒント

5 番目の Optimize について、プレビュー期間と Cobalt 100 の顧客から学んだこととして、次の点が挙げられました。

1. **最新のカーネルを使う。** 無理なら、カーネル、ランタイム、ドライバー、ライブラリのできるだけ新しいバージョンを使う。基盤のハードウェアアーキテクチャに最適化されているため、必要な性能が得やすくなる。
2. **PMU を活用する。** OpenAI が「ハードウェアで何が起きているか見たい」と要望し、PMU を公開した経緯がある。コードベースの中で遅い箇所を見つけて最適化できる。
3. **processor mode を使い分ける。** 一貫性・予測可能性が欲しければ決定的な周波数で、最大限の性能が欲しければ最大性能で動かせるようにした仕組みである。
4. **Java、.NET、Python、Go などのランタイムは、Arm64 への移行が最も容易。** まだなら今すぐ始められる。

スライドの QR コードは、Arm のウェブページ（5 ステップの移行プロセスの概要）につながっていると紹介されました。

### 5.11 提供リージョンとロードマップ

- Cobalt 200 VM は、**昨日（発話は "yesterday"）14 リージョン**で提供が始まりました（「geared」と聞こえる箇所があり、音声認識の都合で正確な動詞は確定できません）。**今年末までに 23 リージョン**になる予定です。
- 目標は、できるだけ早くすべてのリージョンで提供することです。それまでは「product by region」のウェブサイトで提供状況を確認できます。
- Cobalt は**複数世代のプログラム**であり、単発のチップではありません。2024 年に GA した Cobalt 100 は、Azure で大規模な Arm の選択肢として定着し、多くの Microsoft サービスを支え、数千の顧客がワークロードを動かしており、50 以上のリージョンで利用できます。
- Cobalt 100 の VM は今後も継続して提供されます（"here to stay"）。Cobalt 200 を評価して合うならそのまま採用し、Cobalt 100 で十分ならそれを使い続け、ロードマップに合わせて移行していく、という進め方が示されました。
- Arm への投資（ソフトウェア、スキル、運用手順）は次世代にも引き継がれ、Cobalt 100 で動くワークロードがそのまま Cobalt 200 で動く状況は、今後も続く見込みだと述べられました。次世代の Cobalt も、顧客の要望と、価格および価格性能の面でのワークロードのニーズに応える方針です。

## 6. デモ・手順

このセッションでは、画面を使ったデモは行われていません。スライドと口頭の説明が中心です。

スライドで紹介された「導入の進め方」としては、締めくくりに次の流れが示されました。

1. 自分のワークロードが何かを整理し、依存関係を洗い出す。
2. Cobalt 200 で提供されている VM サイズに合わせる。
3. 5 ステップのプロセスを通して、性能面と TCO 面の効果を検証する。
4. アカウントチーム経由で、あるいはプレビュー参加者であれば手元の連絡先から、Microsoft に連絡する。

最後のスライドには、Cobalt 200 VM のドキュメント、移行の概要、エコシステムの概要ダッシュボード、リージョン別の提供状況ページへのリンクが載っていると紹介されました。

## 7. 注意点・発表者の気付き

- 性能向上の幅はワークロード次第です。「最大 50%」は上限的な数字で、チャートの棒にも長短があると明示されています。
- 周波数のチャートは、あくまで特定のベンチマーク（トランスコード系）での比較で、他社製品を否定する意図ではないと断られています。
- OpenAI の processor mode の結果では、カーブの傾きはワークロードによって異なります。示されたのは最も悪い部類の例で、多くの場合はほぼ平坦でした。このため、processor mode は自社のワークロードで試した結果で選ぶ、というのが OpenAI の進め方でした。
- Arm への投資は初期に手間がかかります（共通ライブラリの変換、CI/CD の調整）。ただし一度行えば、世代をまたいで効果が続くと説明されています。
- 内蔵アクセラレーターは、発表では Microsoft 内部のプロダクト向けの機能として説明されています。
- Azure の Cobalt 200 VM は、リージョンによってまだ提供されていない場合があります。提供状況は事前に確認が必要です。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- Cobalt 100 に比べて**最大 50%** の計算性能（コアあたり、ワークロード次第）。
- 1 vCPU が物理コア 1 つ分なので、リソースを共有せず、高い負荷までコアを使っても性能が予測しやすい。結果として、サイジングの最適化や、必要コア数の削減が期待できる。
- Azure Boost により、ネットワーク帯域 15%、リモートストレージ IOPS 20%、リモートストレージスループット 10% の向上。
- Processor mode により、最大性能か予測可能性かを選べる。
- 1〜128 vCPU の幅広いサイズと、vCPU あたり 2・4・8・16 GB のメモリ比、大容量ローカル NVMe の VM。
- Cobalt 100 で動いているワークロードは、**コード変更なし**で Cobalt 200 に載せられる。
- **OpenAI の事例**：Cobalt 100 と CPU 使用率を揃えた比較で、スループット 45% 向上、レイテンシ 10〜40% 低下。opportunistic モードを選んだ ChatGPT のワークロードでは、スループットが約 10% 向上。
- Microsoft 内のチームが、GitHub Copilot を使い、約 4 か月で Arm64 へコードベースを移行した。

## 9. まとめ

Cobalt 200 VM は GA となり、Arm Neoverse V3 の 132 コア、TSMC 3 nm、コアごとの周波数・電圧制御、メモリの暗号化、専用アクセラレーターを備えています。性能は Cobalt 100 比で最大 50% 向上しました。その背景には、約 140 のミニベンチマークによるワークロード分解と、ラックまで含めたモデル化があります。

OpenAI は、Cobalt 200 の本番トラフィックでスループット 45% 向上、レイテンシ 10〜40% 低下を確認し、マルチアーキテクチャ化は Codex の助けで進められたと報告しました。VM は 5 ファミリー（うち MPSv4 系と LPSv5 が新規）で、1〜128 vCPU のサイズが揃っています。

Arm64 への移行は、AI ツールの活用で短縮できます。進め方は Assess、Build、Validate、Deploy、Optimize の 5 ステップです。まずは自分のワークロードを Cobalt 200 で評価し、最新のカーネルやランタイム、PMU、processor mode を使って最適化する、というのが発表の提案です。
