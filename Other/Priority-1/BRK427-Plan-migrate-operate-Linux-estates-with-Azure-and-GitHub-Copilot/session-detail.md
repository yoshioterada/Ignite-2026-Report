# BRK427 Plan, migrate, operate Linux estates with Azure and GitHub Copilot

## 1. はじめに

このセッションは、複数の Linux ディストリビューションが混在する既存アプリケーションを Hyper-V から Azure に移し、容量を追加し、さらに障害を調査する流れを、一つの物流アプリケーションを使って見せる 45 分のブレークアウトです。主役は「Linux には詳しいが Azure は初めて」という架空の運用担当者 Alex で、GitHub Copilot CLI（ターミナルで動くエージェント）が彼の作業を支援します。

特徴は、会場の参加者が実際にアプリケーションへ荷物を登録し、**投票で「Alex の次の悪い日」（注入する障害）を選ぶ**点です。障害の調査では、Copilot に答えではなく症状だけを渡します。移行の部分は事前に収録した映像で、それ以降はすべてライブのデモです。

伝えたい結論は、AI エージェントを使っても、アプリケーションについての自分の知識（何を残すべきか、どう動くべきか）が、結果を判断するうえで欠かせない、という点です。

## 4. 発表者が伝えたいメッセージ

発表の最初の問いは「ターミナルの横にエージェントがいたら、何を任せるか。成功と呼ぶには、どんな証拠が必要か」でした。判断の基準は、出荷記録の裏にいる「届くのを待っている人」にとって、荷物が動き続け、履歴が残っているかどうかです。

結びでは、次のように語られています。

- Alex はクラウドには不慣れだったが、Linux の経験が役に立った。すべての Azure コマンドを知らなくても始められた。ただし、どのデータを残すべきか、ワーカーが何をすべきか、アプリがどう動くべきかは知っている必要があった。
- エージェントは何をしたかを説明できるが、それで十分かどうかを判断し、アプリに頼る人たちが納得できるかを考えるのは Alex の責任。
- 試すなら、よく知っているアプリケーションと 1 つの作業から始める。変更の前にアプローチを話し合う。エージェントの言葉を鵜呑みにせずに結果を確認する方法を用意する。
- **エージェントは常に正しいとは限らない**。自分の知識は AI を使い始めても手放すものではなく、結果を信頼してよい場面と、AI が自信満々に間違っている場面を見分ける助けになる。

また、アプリケーションが AI アプリケーションになる必要は無く、それでも「AI は運用の仕方を変えられる」という点を、登壇者は繰り返して強調しています。

## 5. 発表内容の詳細

### 5.1 Alex と Caldova の物流アプリケーション

Alex は Caldova の物流アプリケーションを担当しています。Caldova は Azure をクラウドとして選んだが、Alex は Azure での運用経験がない、という設定です。登壇者は「自分が選んだわけではない技術を引き継ぎ、それでも問い合わせは自分に来る」という経験を会場に尋ねています。

アプリケーションは 4 つのチームの 4 つの標準が混在した構成です。

| 層 | ディストリビューション・役割 |
| --- | --- |
| Web フロントエンド | Ubuntu |
| API | SLES |
| SQL Server | RHEL。キューに入った作業も保持する |
| ワーカー | CIQ の Rocky。SQL のキューを処理する |

リクエストは入り続けるのに、処理が追いつかなくなることがある、という関係が後半で重要になります。4 つのディストリビューションの混在は、デモのために意図したもので、チームごとの Linux の選択をそのまま扱う狙いだと説明されています。アプリケーションは、それぞれ独自のパッケージ、systemd サービス、ファイルシステムを持つ、引き継いだ仮想マシンとして扱われます。

移行を通して追う荷物は、**ZAV94388224**（Seattle から Paris へ）です。デモでは配達直前で止めてあり、Azure への移行が終わったあとで記録を確認し、Seattle からの履歴が残っていること、配達が完了することを確かめます。

### 5.2 Azure と Linux

登壇者は、Alex が Azure を「Windows Azure」の頃のイメージのまま捉えている、という設定から、会場に「まだ Windows Azure と思っているか」と尋ねています。そして次のように説明します。

- **Azure は Linux プラットフォームである**。Linux は Azure の基盤にあたる。
- Azure の外部コアの約 **70%** は Linux を実行している。
- Microsoft は自社サービスを Linux と Azure 上で動かし、独自ディストリビューションの Azure Linux を開発している。
- お客様がすでに使っているディストリビューションの提供元とも協力している。

したがって Alex の問いは「Linux が Azure に合うか」ではなく、「アプリケーションが事業の必要どおりに動き続けるか」です。そこでの判断（OS のバージョン、サポート条件、ワークロードに必要な統合）には Linux の経験が活き、新しいのは Azure の部分だ、という整理です。

Caldova の判断は 1 つのアプリケーションより大きく、混在した環境、VM とマネージドサービスの両方を支える 1 つのクラウド戦略、チームをまたぐ共通の管理・セキュリティ・可視性、そして全アプリを一度に変えなくてよいモダナイズの道筋を求めています。既存のアプリが先に移り、必要に応じて新しいサービスを採り入れ、すべてのワークロードが同じ行き先とは限りません。そのため Alex は、始めるために出荷アプリケーションを再設計する必要がありません。

### 5.3 運用に AI を持ち込む入口

Alex の責任は Azure に移っても無くなりません。エージェント型の運用への期待は、証拠集めや繰り返しの手作業を減らし、ツールやチームに散らばった運用知識を活用できることです。ただし、エージェントに有用な作業を任せるなら、**どこまでの権限を与えるか**（何を調べられるか、何を変更できるか、何を Alex が承認するか）を決める必要がある、と述べています。これは従来のアプリケーションにも AI ワークロードにも当てはまります。

AI の支援を持ち込む入口として、次の 3 つが挙げられています。互いに補完する入口であり、置き換え可能な製品ではないという説明です。

| 入口 | 発表での説明 |
| --- | --- |
| Azure Copilot agents | Azure の運用体験に支援を持ち込む |
| Azure SRE agents | 設定したインシデントの調査・対応のワークフローを支援する |
| GitHub Copilot CLI | Alex が普段使うツールと並んで、ターミナルにエージェントを持ち込む |

Alex は何かが動かなくなり原因が分からないとき、ターミナルに行きます。荷物が止まる理由は、起動していないサービス、誤ったアドレスに解決される名前（登壇者は「It's always DNS」と冗談を言っています）、データベースに届かなくなったワーカーなど、何段階か先にあることがあります。調査はアプリケーションのコード、Azure の構成、Linux のゲスト OS にまたがるため、エージェントが許可されたツールとアクセスの範囲で、調査の結果を一か所にまとめます。

### 5.4 移行計画と収録映像（Azure Catalyst と GitHub Copilot CLI）

最初の依頼は「何も変更する前に、移行の計画を手伝って」です。内容は、Azure のマシンとディスクの選定、アプリが依存するネットワーク接続の維持、切り替え時のサービスの安全な停止の検討です。中断が発生するため、Alex は承認の前に理解する必要があります。

続く映像は、**実際の 4 VM の移行を編集した収録で、シミュレーションではない**と説明されています。Azure Catalyst がマシンを移し、GitHub Copilot CLI が計画の作業を進めます。（製品名の綴りは音声認識の都合で表記が確定できません。文字起こしでは一貫して「Azure Catalyst」です。）見どころとして 3 つの場面、つまり「隔離されたテストでアプリが動くこと」「切り替えの判断」「荷物処理と履歴が残った証拠」が示されました。映像の流れは次のとおりです。

1. 目的は「Azure Catalyst でこのアプリを Azure に移す」こと。Copilot が、検出されたインベントリをソースと照合し、Azure の構成（マシン、マネージドディスク、プライベートネットワーク）を準備する。既存のプライベートアドレスは維持できる。
2. Alex が計画を確認してレプリケーションを承認する。Copilot が作業を実行し、Azure Catalyst がコピーを作る。
3. データベース、API、Web 層、ワーカーは、それぞれ既存のディスクとマシン構成を持ち込む。レプリケーション中も元のアプリは稼働を続ける。4 つのワークロードすべてで、正常な復旧ポイントが得られた。
4. コミットの前にテストを行う。Azure Catalyst が隔離されたテスト用コピーを作る。Copilot は、ゲスト統合、プライベート接続、古い環境から残った前提への対応を進める。テストは Web リクエストからデータベース、処理するワーカーまで全層を通り、通常の荷物が Azure 上のコピーを通過する。「移行ジョブが緑」というだけでなく、アプリケーションとしての証拠が得られる。
5. テスト後、Azure での処理は止まり、権限は Hyper-V に戻る。リハーサルが、気付かないうちに本番の移行に変わらない。
6. Alex が計画された中断と最終移行を承認する。Copilot が元のアプリを静止し、4 台のマシンがすべて停止したことを確認する。Azure Catalyst が最後の変更を同期する。本番を同時に更新するワーカーが 2 つになることはない。
7. RHEL が起動したものの、既存のアプリケーションボリュームが有効化されなかった。Copilot が Azure の起動の証拠をたどり、Azure 側コピーのブート構成を修復し、既存のボリュームを有効化した。データベースは再構築していない。SQL Server が戻り、アプリのチェックが続き、データベース、API、Web 層がチェックに合格した。
8. その後で、Hyper-V のワーカーを停止したまま、Azure のワーカーが処理を開始する。新しい荷物が Azure で拾われる。荷物の履歴は変わらず、Linux のアイデンティティと作業が維持された。

### 5.5 荷物のライブ確認と、参加者による登録

ここからはすべてライブだと登壇者は述べています。

1. 最初の荷物 ZAV94388224 を開く。以前のスキャンが残り、最終ステップを待っている。
2. Caldova Logistics アプリケーションの画面で、環境内のさまざまなマシンと、さまざまな状態の荷物が一覧できる。
3. 画面上で、この荷物が最後にオンプレミスの Hyper-V 環境の CIQ Rocky ワーカーに処理されたことが分かる。
4. 荷物を「release」すると、Azure で動いているアプリケーションが拾い、配達済みになる。スキャンしたのは「CIQ Rocky Worker Azure West US2」だった。それまで完全にオンプレミスだったアプリが、トラフィックを戻した後に Azure で動き、荷物が最後まで通った。

次に、参加者へ QR コードか `track.99b.org` で荷物を 1 件登録するよう呼びかけています。実際に動く環境なので、**架空の名前と住所を使い、実在の個人情報は入れない**よう依頼しています。追跡ページを開いたままにして、進み具合を見ます。この荷物はバックグラウンドのトラフィックに加わり、運用しながら観察する「実際の作業」になります。同じアプリケーションを、後の投票にも使います。

続いて「network」タブでは、Hyper-V から Azure への移行を表すエステートのトポロジーと、荷物の動きを示すライブの荷物ネットワークマップを見せています。運用ページでは、環境内の各メンバー、キューの深さ、5 分あたりのスキャン数、荷物の一覧が表示されます。

### 5.6 可観測性の構築と Ansible による再現

マップから分かるのは、人々がアプリを使っていることまでで、追いつけているかは分かりません。そのために必要なのが**ビジネスの視点**です。Copilot は可観測性のスタックの構築とトラブルシューティングを手伝い、その後、動作した構成を **Ansible のプレイブック**として残しました。別の運用者が会話を再構成せずに、同じデプロイを確認して再実行できる、という狙いです。

デモでは、Azure Linux 4（WSL 上）でプレイブックを実行します。

1. Copilot CLI にプロンプトを貼り付け、GitHub 上のプレイブックを使って、用意された Caldova の可観測性を Ansible でデプロイさせる。
2. 時間のかかる準備（Azure リソース、権限、ソフトウェアのインストール）は事前に済んでいる。今回のパスでは、ビジネスのエクスポーターと Prometheus コレクターを有効にし、スクレイプと Azure への remote write の構成を適用し、荷物フローのダッシュボードを公開する。アプリは動き続ける。
3. Copilot が実行内容をスクリプトにまとめて実行する様子を、画面で展開して見せる。Ansible の出力が Copilot CLI の画面に流れる。
4. その後「ダッシュボードのみ」の段階が実行され、Grafana の画面を更新すると「Caldova shipment flow」のダッシュボードが現れる。

構成要素の説明は次のとおりです。

| 要素 | 役割 |
| --- | --- |
| ビジネスエクスポーター | SQL Server からビジネスフローのメトリクスを提供 |
| ホストメトリクス | Linux システムの視点 |
| Inspector Gadget | eBPF で、調査に必要なカーネルレベルの証拠を提供 |
| プライベートコレクター | マネージド ID で、メトリクスを Azure Monitor workspace に送る |
| Azure Monitor | メトリクスをマネージドサービスとして保存・提供（Alex が自前のメトリクスのデータベースを運用しなくて済む） |
| Azure Managed Grafana | 共有の運用ビュー（メトリクスへの窓） |

ダッシュボードには、現在のバックログ、最も古い未処理の作業、到着する作業と完了した作業、1 分あたりの到着数と完了数、ライブのワーカー貢献度、ハートビートの経過時間、層ごとの CPU 使用率、Inspector Gadget が観測した API から SQL への接続（カーネルレベルの eBPF メトリクス）、データベースのブロック I/O レイテンシー、ワーカーの TCP 再送が並びます。「出荷は十分な速さで動いているか」に答えるための構成で、この時点では上部の青い線のバックログが大きくなっていました。

> 注意：登壇者は、この発表のすべてのデモで Copilot CLI を「allow all」（人の確認なしで実行を許可する設定）で実行していると述べています。デモとして時間の制約があるためで、本番環境なら自分で介入し、allow all は使いたくない、という趣旨です。

### 5.7 Azure Linux のワーカーを追加する

アプリは応答し、元のワーカーは処理を続けていますが、バックログは増え続けています。止まったわけではなく、作業の到着が処理を上回っている状況です。Alex が必要なのは作業を担う手であり、チームが頼っているシステムを置き換える理由ではない、という位置づけです。そこで、既存の CIQ Rocky ワーカーと並べて、同じキューから処理する **Azure Linux のワーカー**を追加します。アプリのほかの部分はそのままです。

デモの手順は次のとおりです。

1. Copilot に、Azure Linux のワーカーを Cobalt 上にデプロイするよう依頼するプロンプトを貼る。登壇者は、動作を確認済みの固定バージョンを指定していると言い、今週の GA に非常に近いと述べている。
2. Copilot が、指定サイズ・固定イメージのプライベートな Azure Linux ワーカーを作り、レビュー済みのブートストラップを実行し、突合（reconciliation）を行うと説明する。ソフトウェアと可観測性スタックのインストールもプロンプトに含まれている。
3. 単一の VM 作成コマンドでデプロイされたことを確認する（音声では「a single native AZVM create」）。固定イメージとプライベート IP があり、パブリック IP は無い。
4. Grafana で、Azure Linux のワーカーがハートビートに現れ、ワーカーの貢献が入り始め、バックログの増加が緩やかになるのを確認する。CPU メトリクスも表示される。運用ダッシュボードにも「Azure Linux 4.0 cloud variant」のワーカーが表示された。

> 補足：コマンドの詳細（引数など）は読み上げられていません。

デモの間に、イメージの選び方も説明されています。

- Azure Marketplace には、ベース OS から完全なアプリケーションスタックまで、発行元のイメージがある。イメージを見つけるのは始まりにすぎず、**更新を誰が出すか、リリースがどれだけの期間サポートされるか、どのサポート契約が適用されるか**も確認が必要。
- 発行元の約束は、Alex が管理を計画する助けになる。ワーカーの責任は Alex にある。
- すべての Linux ディストリビューションを Azure は歓迎している。Azure Linux を含む「endorsed distribution」は、確立された発行元との関係とエンジニアリング面の協力を反映する。ただし、**サポート条件がどの画像でも同じになるわけではなく、イメージと発行元による**。
- 自社のカスタムイメージを保存・バージョン管理するには Azure Compute Gallery を使い、検証済みの構成を各マシンに持ち込める。

このワーカーには、Azure Linux 4 を Microsoft Cobalt 200 上で使っています。**Azure Linux 4 は今週の Ignite で一般提供（GA）になった**と述べ、会場でチームに拍手を促しています。Alex の既存マシンは x86、新しいワーカーは ARM64 です。Python のアプリケーションコードと構成は再利用できますが、ランタイムとネイティブな依存関係は、アーキテクチャに合わせる必要があります。作業はデータベースのキューにあり、各ワーカーが別の荷物を取得するため、ワーカー同士が同じ Linux ディストリビューションである必要はありません。

結果として、Alex は Linux の選択を保ったまま容量を追加でき、「マシンを 1 台増やす」ことではなく「アプリの作業を処理する力を増やす」ことができたと説明されています。

### 5.8 投票で選んだ障害と Copilot による調査

「ここで終わっても良いが、荷物がまた遅れ始めたら」という流れで、会場の投票で障害を選びます。QR コード、アプリ内の vote ボタン、または `track.99b.org/vote` から投票します。選択肢は次の 5 つです。

1. Azure Linux ワーカーを固める（freeze）
2. ワーカーから SQL へのネットワークを劣化させる
3. ワーカーのキュー取得を遅らせる
4. SQL のトランザクションでワーカーの取得をブロックする
5. Azure Linux ワーカーの起動を壊す

投票の結果、6 票を得た「**SQL のトランザクションでワーカーの取得をブロックする**」に決まりました（「ワーカーのキュー取得を遅らせる」には誰も投票しませんでした）。登壇者が障害を注入します。

**Grafana での症状**：Grafana はほぼリアルタイムですが、データの収集と伝搬のため少し遅れます。やがて 2 桁のハートビート経過時間が黄色に入り、バックログの増加が見え、ワーカーの貢献が落ち始めます。登壇者は、これで問題があることが分かり、Alex のマネージャーから電話が来る頃だとコメントしています。

**Copilot への依頼**：新しい Copilot セッションを開き、allow all にして、「Ignite troubleshooting context」の Markdown を渡します。内容は環境へのアクセス方法で、28 行です。プロンプトには**答えではなく症状だけ**（バックログが増えている、ワーカーの Azure 層のハートビートの範囲が伸びている）を書きます。Copilot は環境に接続するスクリプトを持ち、curl で API を読む方法や、マシンへ直接 SSH する方法など、複数の手段で情報を集めます。

調査の流れは、Copilot が画面上で語った順に次のとおりです。

1. まずライブのアプリのメトリクスを確認する。ビジネスのメトリクスとワーカーのエラーログを読み、ワーカーのハートビートが 2 分以上古く、キューに 273 件の未処理があることを確認する。SQL 接続のタイムアウトが出ているが、API は SQL に届いている（ワーカーだけが困っている）。
2. ワーカーから SQL への経路を確認する。Azure のネットワークルールでワーカーから SQL へのフィルタリングを調べ、ワーカーから SQL への接続を確かめる。TCP ソケットを調べるために、ss コマンドや Python 3 のソケットなど、さまざまなスクリプトを書いて使う。
3. 「SQL はワーカーからの TCP 接続を受け付け、データベースホストには十分な容量がある。両方のワーカーがデータベース操作でタイムアウトする」と判断し、ネットワークルールを変えるのではなく、**SQL セッションとブロッキング**の調査に移る。
4. SQL のコマンドを書いて実行するが、最初のスクリプトは失敗し、Copilot が書き直す。パッチを当ててやり直す。
5. 「軽減策の前に、ブロックしているトランザクションとロック対象の SQL オブジェクトを正確に確認する」というメッセージが出る。
6. 「SQL セッション 54 が 「DBO USP claim scan」 に対する未コミットのスキーマ変更ロックを保持し、両方のワーカーをブロックしている」と特定する。
7. そのセッションだけを終了して未コミットの変更をロールバックし、サービスを再起動せずにロックを解放すると説明して実行し、すぐの回復と、継続トラフィック下でのハートビートの回復・バックログの減少を確認する。

画面では、最初にハートビートの経過時間が戻り、作業が少し戻り始め、バックログが 355 から 353 に下がるのを確認しました。Copilot の報告は次のとおりです。ワーカーの処理が復旧した。未コミットの SQL トランザクションがスキーマロックを保持し、両方のワーカーをブロックしていた。ブロックしているセッションだけを終了して未コミットの変更をロールバックした。両方のハートビートは 3〜9 秒に戻った。ワーカーは 21 件を完了し、到着は 16 件で、バックログは 359 から 354 に減った。

（補足：オブジェクト名は、音声から聞こえた綴りのままで、正確な表記は確認できません。）

## 7. 注意点・発表者の気付き

- **エージェントに与える権限を決める**：何を調べ、何を変更でき、何を承認が必要とするか。本デモは allow all で実行しているが、本番では自分で介入したいと述べています。
- **エージェントの言葉だけを信じない**：結果をエージェントの報告に頼らずに確認する方法を用意する。エージェントは常に正しいわけではない。
- **リハーサルが本番に変わらないように**：移行前の隔離テストの後は、権限を Hyper-V に戻し、本番切り替えは別の判断として承認した。
- **ワーカー追加のときはアーキテクチャに注意**：x86 から ARM64 では、Python コードと構成は再利用できるが、ランタイムとネイティブな依存関係は合わせる必要がある。
- **イメージ選びではサポート条件を確認**：endorsed であっても、サポート条件がすべて同じではない。
- **Grafana にはわずかな遅れがある**：データの収集と伝搬のために、障害の兆候が表示されるまで遅れがある。
- 登壇者の環境では、ダッシュボードのデモを時間内に収めるため、時間のかかる準備を事前に済ませています。
- ライブのアプリには、実在の個人情報を入れないこと。

## 8. 利用者にとっての利点

発表で語られた利点を整理します。

- 既存の Linux の選択（RHEL、SLES、Ubuntu、Rocky）と荷物の履歴を保ったまま、Azure に移せる。
- 移行前に、隔離したコピーで、Web からデータベース、ワーカーまでのアプリケーションとしての証拠を得られる。
- 起動の問題など、移行中に出た問題を Copilot が調査し、データベースを再構築せずにボリュームの有効化で解決した。
- 既存のシステムを置き換えずに、Azure Linux のワーカーを追加して容量を増やせる。ワーカー同士は同じディストリビューションでなくてよい。
- 運用の手順を Ansible で残し、別の運用者が再実行できる。
- 障害時、Copilot が症状から複数の手段で情報を集めて原因を絞り込める。この例では、原因のセッションだけを終了し、サービスを再起動せずに復旧した。
- Alex は、すべての Azure コマンドを知らなくても始められた。

> 補足：発表では、移行の所要時間やコスト、パフォーマンスの数値は示されていません。
