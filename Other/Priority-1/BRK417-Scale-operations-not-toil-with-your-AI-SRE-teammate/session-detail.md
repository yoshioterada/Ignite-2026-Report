# BRK417 Scale operations, not toil, with your AI SRE teammate

## 1. はじめに

このセッションは、Azure の運用チームが自分たちのために作り、いまは社外にも提供している **Azure SRE Agent** を紹介するものです。SRE Agent は、オンコールの呼び出しを受けたときの調査や、日常的な運用作業（toil）を肩代わりする AI の運用担当です。

発表は 3 部構成です。最初に Azure App Service などを担うチームが、SRE Agent の位置づけ、仕組み、今週の発表内容を説明します。次にエンジニアリングマネージャーが、「なぜエージェントが以前より自律的に動けるようになったのか」という設計の考え方を説明し、障害対応のライブデモを見せます。最後に、顧客である InEight の DevOps エンジニアが、導入から 6 か月の成果を語ります。

結論として繰り返されるのは、**エージェントをモデルの「お願い」で縛るのではなく、モデルの外側の環境で、決定的（deterministic）に制限する**という設計思想です。

## 5. 発表内容の詳細

### 5.1 Azure SRE Agent とは

SRE Agent は、AI を使った運用のエキスパートです。問題を先回りして検出し、インシデントをより速く解決し、定型的な運用を自動化して、アプリケーションが動き続けるようにします。もともと自分たちのために作りましたが、Microsoft 内の他チームも使い始め、2025 年春に preview を開始、今年の Build で製品として提供されました。

Microsoft 内での利用は、次のように説明されました。

| 項目 | 数字 |
| ---- | ---- |
| 本番で動いているエージェント | 11,000 |
| 利用しているチーム | 3,000 |
| インシデントの緩和（mitigate）にかかる時間 | グラフ左下の数字が「最も重要な数字」と紹介されましたが、具体的な値は音声では語られていません |

当初は「すべてを直してくれる全知の魔法使い」という、非現実的なビジョンから始めたものの、できあがったのは **使うほど賢くなるプラットフォーム**だった、と説明されています。toil を引き受け、イベントに反応して対処します。対象は Azure だけでなく、オンプレミス、そして「昨日から」AWS と GCP にも及びます。MCP、A2A、ツール、HTTP フックで拡張できます。

**使い方は 3 通りです。**

- **対話（interactive）**：ポータルや Teams、GitHub Copilot のキャンバス、MCP から話しかける。live report 機能で、エージェントが生成するダッシュボードも見られる
- **リアクティブ**：ServiceNow、PagerDuty、Azure Monitor、自社システムからの HTTP フックなどのインシデントに反応する。インシデントの種類に応じて何をするかを指示する、「reaction plan」のようなものを作れる
- **プロアクティブ**：スケジュールでスキャンを実行できる。顧客の例として、毎朝、構成と本番のドリフトや、セキュリティスキャンを調べている

### 5.2 内部構成

登壇者は、エージェント型のシステムを「人間の体」にたとえています。

| 体の部位 | 構成 |
| ---- | ---- |
| センサー | ポータル、CLI などで話しかける。アラートやインシデントで起こす。スケジュールされたタスク。各種プロトコルでのプログラムからの呼び出し |
| 脳 | 推論エンジン。選べるモデルは数種類で、**独自のモデルは持ち込めない**。使うモデルをテストして認定し、きちんと動くことを保証するため |
| 手足 | セキュアなサンドボックス（ツールがインストール済みで、エージェントが頼んだ操作を実行する）。他のシステムとやりとりするコネクターのライブラリ（メッセージの受信・送信など） |
| 知識と記憶 | ドキュメントのアップロードや Web サイトとの接続で、自社の知識を与える。コネクターで、在庫や他の監視機能など動的なシステムからデータを引ける。コネクターには、Datadog、New Relic などのサードパーティが含まれる |

管理できるクラウドリソースは、Azure 上のすべてと、オンプレミス、そして今週発表された GCP と AWS です。

**セキュリティの層**

- 基盤に Azure RBAC があり、複数のセキュリティ層がある
- すべての操作は既定で人間の承認が必要
- インストール直後は read-only モードで、信頼するにつれて権限を増やす「段階的な有効化（progressive enablement）」
- サンドボックスは隔離されており、サンドボックスからの egress を制御できる。インストールされる CLI（Azure CLI、AWS CLI など）も細かく制御できる
- ツール呼び出しの前後、会話の開始と終了に、宣言的・命令的なコードや LLM への指示を実行できるフックがある

### 5.4 エージェントが自律的に動けるようになった理由

Sanchit 氏は、2025 年には、エージェントの多くが「モデル、いくつかのツール、その周りのループ」という数行の疑似コードで、毎ステップで承認を求めていたと説明しました。2026 年には、エージェントは毎ステップの許可を求めなくなり、より自律的になり、人間を本当に必要な場面で呼ぶようになりました。信頼レベルの何が変わったのか、というのが問いです。数時間動くクラウドのエージェントでは、自分の PC で自分の資格情報を使うときのような YOLO モードは避けたい、とも述べています。

モデルが良くなったことに加えて、次の 4 つの原則が挙げられました。

1. **エージェントにコンピューターを与える**：コードを書き、実行し、ツールを動かし、必要なものをインストールできる作業領域（スクラッチパッド）
2. **そのコンピューターを制約する**：SRE Agent のように信頼できないデータを多く読むエージェントは、悪意あるインジェクションや意図せぬ形で、望まない操作を実行しようとし得る。そのため、できることを制限し、サンドボックスからシークレットを取り除く
3. **エージェントを統制し、監査する**：エージェントに固有の ID を持たせ、「あなたが実行した操作」として現れないようにする。A365 のポータルで見え、Purview や Defender の DLP の設定が使え、長期にわたってエージェントの行動を見返せる
4. **エージェントを、チームがすでにいる会話の場に参加させる**：Teams や Slack のチャンネルにエージェントがいれば、そこで対話でき、「見えないところで勝手に動く」状態にならない。信頼にとって最も重要だと述べています

中心にあるのは、いまも同じエージェントループですが、その周りに、永続的な状態、隔離された実行、ID、ポリシー、コラボレーションのツールが取り巻いています。信頼を高めるカギは、モデルそのものをセキュリティの境界とするのではなく、エージェントの周りを作り込んだことだ、と説明されました（発話は "start creating the model as a security boundary" と聞こえ、前後の文脈からこの意味に読んでいます）。

### 5.5 アーキテクチャ：brain と hands の分離

Sanchit 氏は、開発の経緯をたどりました。

1. **バージョン 1：1 つの箱**。ハーネス、ループ、エージェントが書いたコード、トークンがすべて並んで存在する。コーディング CLI のモデルに近く、一歩ずつ見ているなら問題ない。ただし数時間動くエージェントは、何個のコマンドを実行するか分からず、自分のハーネスや指示を変更したり、ログを削除したりできるかもしれない
2. **brain と hands の分離**：brain は信頼できる側で、エージェントループとハーネスを動かし、推論・計画・どのツールを呼ぶかの決定を行う。hands はツール呼び出しを実行する、信頼できないサンドボックスで、別の環境にある。大きな改善だが、資格情報がまだ hands 側にあり、エージェントがそれを持ち出したり、Teams で頼まれて環境変数の出力を実行したりし得る
3. **現在の構成**：
   1. 呼び出しが Teams から来て、イベントがキューに入り、ハーネスとループが処理する
   2. モデルがどのツール呼び出しをするか決め、サンドボックスに送って実行させる
   3. サンドボックスの外に出るすべての呼び出しは、**egress proxy** を通る。これは既定で拒否で、信頼できる Azure のエンドポイントなど、許可されたものだけが通る
   4. サンドボックス内には **シークレットが無い**。egress proxy は、呼び出し先を見て、その呼び出しがエージェントにより要求されたものと確認し、ガバナンスの層を通したうえで、**トークンを注入する**
   5. エージェントは、手（hands）を通じてもトークンを持たず、呼び出し先（AWS、Azure リソース、他のエージェント）が正しいトークンを受け取って認証し、応答する

当初の 10 行ほどのコードはいまも残っており、変わったのは、モデルやループの外側に設けたガードレールです。これらのガードレールは決定的に強制され、エージェントが回避する方法はない、と説明されました。また、これはデモ用の環境ではなく、**数千の Microsoft のサービスが、同じセキュリティ原則で、毎日インシデント対応に使っている**と述べています。

### 5.6 InEight の事例

Babji 氏が、InEight（トランスクリプトでは「Inate」と聞こえます）の事例を話しました。同社は、建設プロジェクト管理ソフトウェアのマーケットリーダーで、850 社以上を支援していると説明しています。建設・エンジニアリング、石油・ガス・化学、電力・再生可能エネルギーなどの分野の、複雑な資本プロジェクトを対象に、コスト、スケジュール、契約、請求、現場と実行を管理するソフトウェアを提供しています。

環境の規模は次のとおりです。

| 項目 | 数字 |
| ---- | ---- |
| Azure リソース | 80,000 |
| うち Azure SQL データベース | 40,000 |
| App Service | 30,000（30 以上のリージョン） |
| テレメトリ | 毎日 2 テラバイト |

**経緯**：2025 年 10 月に、経営陣が小さな AI シンクタンクを始め、市場のエージェント型ソリューションの調査を任されました。そこで Azure SRE Agent を知り、sandbox のサブスクリプションで有効にして試し、壁にぶつかったときにプロダクトチームに現地ワークショップを依頼しました。2 日間のワークショップが「ゲームチェンジャー」で、そこから 6 か月で、パイロットから本番へ進みました。現在は **21 のエージェント**と、**100 以上の専門サブエージェント**があります。

課題領域は 3 つに分類されています。

| 領域 | 取り組み |
| ---- | ---- |
| reliable operations | バグトリアージ・エージェント（状況を端から端まで評価・分析し、短期・長期の解決策を示す）。環境とテナントの健全性のライブレポートとダッシュボード（インフラ全体を俯瞰から詳細まで見て、先回りで対応） |
| engineering velocity | agentic SDLC の「ソフトウェアファクトリー」（ユーザーストーリーを端から端まで開発し、サンドボックス環境にデプロイして、人間の承認用に PR を出す）。最近のグリーンフィールドの取り組みとして、ビルドを顧客に出す前に確信をもって認証する「control engineering lab」（Azure リソースやツイン環境を作り、開発ブランチのビルドをデプロイして比較し、スコア付けする）（名称は音声認識の都合で確定できません） |
| engineering intelligence | FinOps ダッシュボードを成熟させ、クラウドコストを最適化。Compute Savings Plan を分析し、ワークロードに合う最適なものを選ぶ |

**代表的なユースケース**

- 主力製品の計算ロジックのリグレッション：3 分未満で 200 万行のコードを調べ、複雑なアルゴリズムの回帰を見つけ、3 分未満で修正した
- ブラウザーのメモリリーク：サードパーティのアプリ内ガイダンスソフトが、顧客のブラウザー側でメモリリークを起こしていた原因を特定した
- 遅い API のパフォーマンスチューニング
- マルチテナント SaaS 環境でのボトルネック（「cube bottleneck」と聞こえ、音声認識の都合で表記が確定できません）の特定・診断・修正
- CI/CD パイプラインの失敗が、分析と判断により大きく改善した

6 か月の作業の量は、スレッド数、モデル呼び出し数、ツール呼び出し数の数字として示されましたが、具体的な値は音声では読み上げられていません。Babji 氏は、「最も難しい問題から簡単な問題まで選んだ」「名前は Site Reliability と誤解を招くが、それ以上の可能性がある」と述べています。

**多層防御（defense in depth）**：InEight 独自の harness と InEight IQ を、SRE Agent の不変（immutable）なプラットフォームの上に構築しています。譲れないガードレール、ガバナンス、エージェントを自社の VPN 内でのみ動かせる egress の層があり、セキュリティを最も重視して進めたと述べています。さらに「intelligence loop」として、機械学習のパイプラインが、スレッドの内容を収集・分析し、知識、スキル、指示のファイルとして整理・生成して再利用します。

InEight の哲学は「顧客に提供するソリューションと製品が、お金を節約し、稼ぎ、優れた体験を与えるべきだ」というもので、Azure SRE Agent は、それに 100% 合致すると述べています。

## 6. デモ・手順

このセッションには、Sanchit 氏によるライブデモがあります（画面の細部は音声からは確認できないため、語られた範囲のみ書きます）。

**デモの設定**：題材は「Moonshot Fest」というイベントのチケット販売アプリです。ストアフロント（顧客がパスを申し込む）と、入場管理など発券のライフサイクルを担う別のデータプラットフォームがあり、データプラットフォームは AWS 上の課金サービスも呼び出します。それ以外は Azure 上で動き、ストアフロントとデータプラットフォームは別々のチームが管理しており、それぞれが自分の SRE Agent を持っています。デモの前提は「何かが壊れているらしい、と聞いただけ」の状態です。デモの前に、会場の人がキュー（VIP とシャトルの列）に参加できる QR コードも示されました。

1. Teams から、エージェントに「人々がキューで止まっているという報告がある。何か起きているか」と尋ねる。エージェントがメッセージを受理し、調査を始める。これは新しい Teams 連携で、作業の様子を Teams の中にストリーム表示する。すでに PR のステータスの確認などを始めた
2. 予約サイトで実際にチケットを予約しようとして、キューに並ぶ。数秒待ち、さらに 10 秒待っても動かず、問題があると確認する
3. エージェントから返答が来る。権限を求められるが、いったん取り消し、何が起きているのかを尋ねる
4. 返ってきた回答：ゲストが待合室（waiting room）で 40 分間止まっている。アラートが発報している（名称は聞き取り不明瞭）。原因は、誰かのコード変更で、人々が入るキューが、パフォーマンスを改善した別のキューに切り替えられ、以前のキューが削除されたこと。以前のキューでリースを持っていた人が止まっている
5. 相関チャートも示された。ある時点までは人が流れていたが、デプロイされた変更の後で止まったことが分かる。緩和策が直接提示され、問題を直す PR も作られていた
6. 緩和策を実行するよう頼む。問題はデータプラットフォーム側にあり、エージェントは自分ではこの操作を実行せず、「この操作はアプリケーションに影響を与える可能性があるが、実行するか」という最も重要な判断を、人間に回してきた
7. その間に、分析が正しいかを確かめるため、ダッシュボードの作成を頼む。キューが動き続けていたか、停止の指標があったか、修正後にキューが動き出す指標があるかを見たい、という意図
8. インシデントを確認する。Azure Monitor のアラートが、セッション開始の約 16 分前に発報している。エージェントは、メモリを読み、Log Analytics のクエリを複数実行し、App Service のコンソールログを調べ、アプリ設定の一覧を取得し（デプロイで変わったと疑ったため）、Git の履歴とデプロイの時刻も確認した
9. 問題はデータプラットフォーム側にあるので、ストアフロントのエージェントの言うことをそのまま信用できない。そこで、ストアフロントのエージェントが、データプラットフォームのエージェントを呼び出し、ライブの入場キューの設定、ログ、Redis や RDS（AWS 側）の問題ではないこと、エントリー数などを尋ねていた
10. データプラットフォームのエージェント側では、A2A の呼び出しが入ったのが確認できる。このエージェントは az CLI のコマンドを複数実行し、AWS の Lambda や RDS のメトリクスを調べ、「問題なし」としたうえで、「あなたの言ったことを確認した」と返答した
11. 根本原因が正しいと判断し、自分の権限で、緩和操作の実行を許可する
12. ダッシュボードのタスクに戻る。エージェントは Log Analytics のクエリを複数実行し、HTML テンプレートを作り、テンプレートを試すハーネスまで作って実行し、ライブレポートのスクリーンショットを撮って、正しく描画されているかを確認してから、レポートを作った。レポートには、キューが動いておらず、約 1,795 人が待っているのが示されていた
13. Teams に戻ると、うまくいっていないので自分で操作しようとする。Teams 上のスレッドは、SRE Agent ポータルの **Communication Hub** からも見られる。エージェントはコマンドを実行済みで、アプリ設定が正しいかを検証中で、アプリの再起動を待ってから結果を返す
14. ダッシュボードのスレッドで、まだ止まっているのを確認する。しばらくして、キューが動き始め、エージェントからの通知も届く。調査、緩和操作の実行、問題の解決までが、数分で済んだ。自分のパスも作成され、列が進んでいる

**長期的な可視性のデモ**（同じ画面での確認）

1. エージェントは Entra の agent identity を持つため、agent ID の observability ページで、エージェントが取ったすべての操作を確認できる。メッセージへのリンクをたどって、送られたメッセージを追跡することもできる
2. A365 では、組織全体で利用できるエージェントと、そのインスタンスと活動を見られる。誰が使っているか、エージェントの構成も分かり、管理者はポータルから制御し、ブロックすることもできる
3. Defender のログと、Purview の DLP のログも得られる。エージェントが攻撃を受けていないか、不審な活動はないか、会社のデータがエージェントに渡されていないかを、より詳しく把握できる

## 7. 注意点・発表者の気付き

- **既定は人間の承認**：すべての操作は既定で人間の承認が必要で、インストール時は read-only です。信頼に応じて権限を広げます。デモでも、影響が出うる緩和操作は、エージェントが自分では実行せず、人間に判断を求めました。
- **プロンプトで制限するだけでは足りない**：モデルが 99.9% 正しくても残りの 0.1% が問題になるため、環境の側で不可能にする、という考え方です。
- **1 つの箱では危うい**：ハーネス、コード、トークンが同居していると、エージェントがハーネスや指示を変更したり、ログを削除したり、資格情報を出力させられたりする恐れがある、と説明されました。
- **独自のモデルは持ち込めません**：テストして認定したモデルだけを使います。
- **信頼できないデータを読む**：SRE Agent は、信頼できないデータを多く読み、悪意のあるインジェクションの可能性があるため、できることを制限し、サンドボックスからシークレットを取り除きます。
- **確認を怠らない**：デモの発表者は、エージェントの要約を信頼しつつも、分析が正しいかをダッシュボードで確かめていました。
- 一部の機能は preview 段階です。Slack 連携は private preview と聞こえます。

## 8. 利用者にとっての利点

- **運用能力のスケール**：Microsoft 内で、11,000 のエージェント、3,000 のチームが利用。発表の冒頭では、小さなチームで 1,800 万コア、約 50 万の顧客を支えるために作った、と説明されました
- **対応時間**：インシデントの緩和にかかる時間は、利用チームの重要指標として示されました（数値は音声では語られていません）。デモでは、調査から緩和まで数分で完了
- **既存の仕組みにつながる**：ServiceNow、PagerDuty、Azure Monitor、Teams、Slack、ADO、GitHub、Outlook など。Azure、オンプレミス、AWS、GCP を対象にできる
- **InEight の成果**：6 か月でパイロットから本番へ。21 のエージェントと 100 以上のサブエージェント。200 万行のコードを 3 分未満で調べて回帰を修正。ブラウザーのメモリリークや遅い API、CI/CD の失敗の改善。クラウドコストの最適化（FinOps）。エンジニアに時間が戻り、実際の課題に集中できるようになった、と述べています
- **ガバナンスと監査**：agent identity、A365、Defender、Purview の DLP ログにより、エージェントの行動を長期間にわたって追跡できる

## 9. まとめ

Azure SRE Agent は、Azure App Service などのチームが、自分たちの運用の規模に対応するために作ったエージェントで、今は 11,000 のエージェント、3,000 のチームが社内で使っています。対話、リアクティブ、プロアクティブの 3 通りで使え、今週は Teams 連携、AWS・GCP の調査、agent identity と A365 での管理、CMK などが発表されました。

エージェントが自律的に動けるのは、モデルが良くなったからだけではなく、「コンピューターを与える」「制約する」「統制し監査する」「会話の場に参加させる」の 4 つの原則を、モデルの外側で決定的に強制しているからだ、というのが Sanchit 氏の説明です。egress proxy によるトークン注入のように、エージェントがシークレットを持たない設計が、その中核にあります。InEight は、6 か月で 21 のエージェントを本番に出し、障害対応、開発、コスト最適化の各領域で成果を上げたと報告しました。
