# BRK412 Rethink modernization end to end with agents

## 1. はじめに

このセッションは、アプリケーション、データ、インフラのモダナイゼーション（近代化）を、AI エージェントで最初から最後まで進めるための発表です。中心になるのは、この Ignite で提供開始が発表された **Azure Catalyst** です。Azure Migrate と GitHub Copilot modernization agent を 1 つの体験にまとめ、資産の棚卸しから、設計、計画、実行までをつなげます。

構成は、Lumen Technologies の顧客事例、Azure Catalyst のデモ（クラウドアーキテクトの視点とアプリ開発者の視点）、セキュリティの 3 層の考え方、Microsoft の専門家支援プログラム、そして質疑応答です。モダナイゼーションの計画や実行に責任を持つ方に向けた内容です。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK412](https://ignite.microsoft.com/en-US/sessions/BRK412)

## 4. 発表者が伝えたいメッセージ

Ashish 氏は、モダナイゼーションを「単発の移行」から「エージェント主導のプロセス」へ変えることを主張しています。エージェントによって作業の経済性が変わり、資産の把握、アプリケーションやランディングゾーンの設計、計画の作成と実行、セキュリティ修正まで、多くがエージェント支援あるいはエージェント主導になると述べています。その結果として、**エンドツーエンドで最大 70% 速いモダナイゼーション**を見ている、という説明です。

もう 1 つの強調点は**コンテキスト**です。Nish 氏は「エージェントの出来は、与えられるコンテキストの量で決まる」と述べ、エンタープライズ規模で、セキュリティとガードレールを守りながら進めるために、オーケストレーションが必要だと説明しています。また、組織のポリシーや標準をエージェントに持たせることで、組織ごとの専門性を一貫して使える点も語られています。

## 5. 発表内容の詳細

### 5.1 なぜモダナイゼーションか

冒頭で Ashish 氏は、多くの企業が AI による変革を急ぎたいのに、技術的負債のために動けない、と述べています。コストは上がり続け、開発者は古いシステムの維持で燃え尽きがちで、その間に AI プロジェクトは待たされ、セキュリティとコンプライアンスのリスクも高まります。この時代、セキュリティはエージェントという存在に左右されるため、最新のインフラを使った最高水準の防御が不可欠だ、という考えです。

顧客成果として、Levi's が業務プロセスのワークフロー向けにモダナイズして AI エージェントを使えるようにしたこと、P&G が Azure への移行で大きな性能向上を得たことが紹介されました。多くの顧客で、チームがコードベースを速いペースでアップグレードし、新しい AI 体験に向けた余力ができているとのことです。ただし、これらは同一の実装ではなく、共通するのは「レガシーの制約を回避する時間を減らし、事業を前に進める時間を増やせる」点だと説明しています。

### 5.2 Lumen Technologies の事例（Shannon Gray 氏）

Shannon Gray 氏は、クラウド移行を、Lumen 全体の事業変革の一部として位置づけています。事業が変わるなかで、技術基盤にも俊敏さ、自動化、シンプルな運用が必要になった、という説明です。

**当時の環境：**

| 項目 | 内容 |
|---|---|
| データセンター | 6 か所 |
| サーバー | 50,000 台 |
| アプリケーション | 3,500 超 |

課題は、数千のワークロードを動かすことではなく、「クラウド移行を機に Lumen を近代化し、単純にすること」だったと述べています。Lumen はマルチクラウド環境にあり、運用コストの上昇、レガシーな技術的負債、老朽化したインフラ、ドキュメントも専門知識もないアプリケーションを抱えていました。AI を使った支援のモダナイゼーション基盤が、エンジニアには必要だったとのことです。単一のアプリケーションスタックやクラウドに押し込めず、Microsoft および Azure とパートナーを組んで基盤を作った、という説明です。Microsoft は、アプリケーションの評価と優先順位づけ（ツールや Copilot の機能を活用）、そして AI を使ったモダナイゼーションを支援したと述べています。FinOps のディレクターの立場からは、自動化され、安全で、信頼性とスケーラビリティがあり、**コスト意識のある**アーキテクチャを目指したとも語っています。

**具体例：** 20 年以上前の「Net Transformation Application」（音声認識の表記で、名称は確定できません）を取り上げています。

| 項目 | 内容 |
|---|---|
| コード量 | 24,000 行をモダナイズ |
| エンジニアリングと移行の工数 | 82% 削減 |
| TCO | 20% を超える削減 |
| 移行前の構成 | Java 1.7、EJB 2.0、WebLogic、単体テスト・移行テストなし |
| 移行後 | Java 17、WildFly |

Microsoft のツールと GitHub Copilot で、この作業を加速できたと述べています。最後に、「クラウドはアプリの動く場所を変え、AI クラウドは、アプリが動く場所、データが置かれる場所、データをつなぐ速さを変えている」とまとめました。

### 5.3 Azure Catalyst の発表

Ashish 氏は、今日の発表として **Azure Catalyst** の提供開始を紹介しました。

- IT チーム、開発者、データベース管理者向けの体験を 1 つにまとめた、モダナイゼーションのための「接続された体験（one connected experience）」。
- 既存の **Azure Migrate** と **GitHub Copilot modernization agent** を 1 つの傘の下に統合し、強化したもの。
- 資産の探索（discovery）、適切なサイズでの評価、アーキテクチャと設計、モダナイゼーション計画と実行を、インフラ、データベース、アプリケーションをまたいで 1 つのコンテキストで扱う。
- 計画と実行は、事業の優先順位、アーキテクチャ、ガバナンス標準に沿って調整される。
- 既知の脆弱性は自動で修正され、コードが安全になる。

### 5.4 新機能のまとめ（デモ後の整理）

デモのあと、Ashish 氏は Azure Catalyst の新機能を次のように整理しています。

- 依存関係を含む資産全体の把握と、数週間〜数か月ではなく数分でのモダナイゼーション計画づくり。
- TCO、プラットフォームとアプリケーションレベルの設計、ウェーブに分けた順序づけを含む提案。事業上の重要度と複雑さを、顧客が定義したとおりに反映する。
- Microsoft Cloud Adoption Framework に準拠し、モダナイゼーションの目標に沿った設計。
- アプリケーション、データベース、インフラにまたがる、規模に合わせた調整済みの実行（移行とコード変換をエージェントが支援）。
- ガバナンスのルールがエージェントの作業を導き、カスタムの実行ステップやスキルで自社の知見を各プロジェクトで一貫して使える。

### 5.5 セキュリティの 3 層

Ashish 氏は、セキュリティをモダナイゼーションの一部として考えるとして、3 層で説明しました。

| 層 | 内容 |
|---|---|
| 第 1 層 | Azure Catalyst が、コード内の既知のセキュリティ脆弱性を自動で修正する（デモで Nish 氏が示したもの） |
| 第 2 層 | M-Dash（音声認識の表記）。Defender の一部で、マルチモーダルなエージェント型のスキャンシステム。既知の脆弱性を超えて、ゼロデイの悪用やコードの弱点を探し、修復を支援する |
| 第 3 層 | Azure にデプロイしたあと、同じ規律を Azure の資産に広げる。継続的な保護と堅牢化には「Microsoft Perception」（音声認識の表記。製品名は確定できません）を使う |

これらは互いに補完する層で、セキュリティをデプロイ後の後付けではなく、移行の道のりの一部にする、というのが目標です。

### 5.6 Frontier Accelerate program for Azure

Azure Catalyst を補完するものとして、クラウドと AI の導入を支援する **Frontier Accelerate program for Azure** が紹介されました（文中では Azure Accelerate とも呼ばれています）。

- 初期の分析フェーズと、モダナイゼーション計画の実行フェーズの両方で、**信頼できる専門家に無償でアクセス**できる。
- Azure クレジットなど Microsoft の追加投資で、プロジェクトの初期コストを下げられる。この資金は、プロジェクトの規模や段階を問わず利用できる。
- 設計と検証のための無償のサンドボックス環境、ハッカソン向けの専門家支援、オンデマンドコンテンツ、チーム向けのライブのスキルアップ。

専門家支援の流れは次のとおりです。

1. **Solution Assessment Desk**：Azure Catalyst を使って環境を深く分析し、モダナイゼーション計画を無償で作る。
2. **Azure Accelerate Factory**：計画を受け取って洗練させ、実装する実務の専門家。この Microsoft の専門家による実装は無償で、しきい値の下限も上限もないと述べています。現場での知識移転も行われ、Azure で初日から稼働できるようにするとのことです。

実績として、**過去 4 年ほどで 7,000 の顧客、20,000 件の案件**で検証済みと述べています。事例として、Caminos（音声認識の表記）が Accelerate Factory を使い、デジタルバンクの **30 TB の SQL Server ベースの勘定系アプリケーション**を、プライベートクラウドから Azure にモダナイズしました。ダウンタイムはゼロで、銀行規制にも完全に準拠していた、と紹介されています。

プログラムは 30 を超えるサービス（Azure のセキュリティ、AI ビジネスソリューションなど）に及び、最初のエージェントを最初のユースケースから本番まで開発する支援も含みます。Frontier Accelerate は、Microsoft の人員が行う作業は無償で、既存の SI がいる場合は SI パートナーと連携して動く、とも説明しています（Q&A での回答）。

## 6. デモ・手順

デモは 2 部構成で、Ankit 氏（クラウドアーキテクトの役、「Caldova Pharma」の設定。音声認識の表記ゆれで Caldiva などとも聞こえます）と、Nish 氏（アプリ開発チームの役）が行いました。Nish 氏は「時間の都合で早送りした」部分があると述べています。画面の細部は音声からは確認できず、語られた範囲で書きます。

### 6.1 インフラとデータ側（Ankit 氏）

1. モダナイゼーションの目標を Catalyst agent に伝える。すぐに、現在の資産を把握する方法の選択肢が提示される。
2. すでにある構成データ（ServiceNow CMDB のレポートを含む）を受け付けるため、ゼロから始めなくてよい。ServiceNow CMDB のレポートなどのファイルをアップロードする。
3. agent が資産全体を自動でマッピングし、全ワークロードの依存関係を確認できるビューを見せる。データのヒューリスティクスでワークロードをアプリケーションにまとめ、事業上の重要度と複雑さも割り当てる。以前は複数のスプレッドシートや別々のツールで数週間かかった作業が数分で終わる、と説明している。
4. 経営層と ROI を確認するため、エグゼクティブ向けの提案書をダウンロードする。内容は、Azure に移行するビジネスケース、アプリケーションの準備状況とターゲットサービスのマッピング、注意すべきセキュリティ脆弱性。この報告書で、プロジェクトの承認を得たと説明している。
5. 実行計画として、まずプラットフォームランディングゾーンを扱う。Catalyst が資産と目標から設計を推奨する。設計は Microsoft の CAF と WAF の原則に沿い、ネットワーク、セキュリティ、管理、ID、コンプライアンスをまとめ、回復性の要件に合わせて最適化している。自分たちに合わせて調整し、承認する。
6. アプリケーション所有者を巻き込み、アプリケーション単位の計画に進む。Catalyst は評価した各アプリケーションに対し、モダナイゼーション向けのアーキテクチャを生成する。根拠は、Azure Architecture Center の **700 超のリファレンスアーキテクチャ**を整理したナレッジグラフ。
7. 「Caldova Asset Manager」アプリケーションでは、設計の推奨は次のとおり。.NET Web アプリに Azure App Service、SQL Server に Azure SQL Database Hyperscale Elastic Pool、ファイル共有に Azure Files。そのほか、アプリの動作に必要なサービスを、組織のポリシーに従って推奨する。
8. 事業上重要なアプリなので設定を調整すると、Catalyst が設計を更新して、性能向上のために **Azure Managed Redis** を追加する。ここまでを以前はコンサルタント主導の複数回のワークショップが必要だったが、数分でできる、と説明している。
9. 実行前に、アプリケーションと依存関係、準備状況、移行工数、重要度に基づいて、アプリケーションとワークロードを**ウェーブ**に分けた計画を作る。Asset Manager は第 1 ウェーブ（SQL Server がサポート終了に近く、セキュリティリスクがあるため）。ウェーブを確認して確定する。この計画により、インフラチームとアプリ開発チームの間で調整し、実行の成否を一元的に追跡できると説明している。
10. 実行を 1 つのビューで開始する。Asset Manager の実行計画は、共通のセットアップ手順から始まり、SQL Server から SQL DB Elastic Pool（Hyperscale）へのデータ移行と、ファイル共有から Azure Files への移行が続く。
11. データベース移行に必要なパラメーターを確認し、更新して保存する。データ移動の実行を開始すると、データ同期が始まる。同期が終わるのを待つ間に、コードのモダナイゼーションを Nish 氏に引き継ぐ。

### 6.2 コード側（Nish 氏）

1. VS Code で、Ankit 氏が始めた同じ Asset Manager アプリを開く。.NET のモノリシックな Web アプリケーション。Visual Studio でも使えると述べている。
2. **GitHub Copilot modernization 拡張機能**から、評価、新しい .NET へのアップグレード、Azure への移行タスクを IDE から実行できる。1 つのアプリならこれで足りるが、ポートフォリオ全体を評価するために、新しい **modernize CLI** を使う（すでに GA）。流れは「評価 → 計画 → 実行」で、各段階で人が確認できる。
3. 使用するモデルを選ぶ。Ignite で追加された **bring your own model**（BYOM と BYOK の両方に対応）にも触れている。
4. 複数のリポジトリを一度に評価するため、設定ファイル（JSON のキーと値）で評価を開始する。リポジトリは GitHub 上でもローカルでも、スケール用の VM 上でもよく、取得に必要な情報が JSON にあればよい。
5. 評価の設定で、最小の CVE の重大度などを決める。Java と .NET を同じツールでまとめて評価する。評価の観点はアップグレード（目標のランタイム）、クラウド対応（今回の配置先は App Service）、セキュリティで、完全な分析を選ぶ。
6. 評価には時間がかかるため、早送りしている。完了すると統合レポートが表示される。各リポジトリにも個別の評価レポートが GitHub のリポジトリまたはローカルに作られる。
7. 統合レポートでは、ポートフォリオの .NET と Java が同数であること、複数のビジネスアプリの評価結果を確認できる。Caldova の Asset Manager を開くと、ドメインごとの詳細が見られる。クラウド対応では、重要度や、クラウド移行に必須の CVE と CWE が示され、「重大か、後で対応できるか」が分かる。
8. コードからリバースエンジニアリングされた**アーキテクチャ図**を見せる。開発者が異動して資料が乏しいが本番で動いているという顧客の声に対し、エージェントがコンポーネントの関係を把握して洞察を与えるという説明。
9. データベース構成の情報も見せる。今日、modernize CLI に、**Azure SQL readiness と Oracle to PostgreSQL readiness のレポート**を preview として追加すると発表している。アプリと DB を一緒にモダナイズするため、DB 側の重要な問題を開発者も把握できるようにするためだ、と説明している。IDE で評価した場合も、リポジトリ単位で同レベルのレポートが得られる。
10. ここまでが評価。次は計画。その前に、組織のポリシーをすべての計画に注入するための **rulebooks**（今週 GA）を使う。企業内に置く中央のリポジトリで、ポリシーを Markdown ファイルとして定義する。PPT や SharePoint から生成してもよい、という説明。例として、レガシーな Windows ホスティングを App Service に移す、セキュリティやシークレット管理など、.NET でも Java でも従うべきポリシーを挙げている。
11. `modernize plan create` で計画を作る。これはヘッドレスのコマンドで、`modernize` を開いてから進める必要はない。社内に DevOps パイプラインなどでモダナイゼーションの仕組みを作る場合に便利だと述べている。やりたいことをプロンプトで入力する。
12. rulebook が読み込まれ、組織のポリシーを反映した計画が作られる。人が計画を確認して、組織で決めたことに従っているかを見る。rulebook 準拠のレポート（compliance の Markdown ファイル）も提供される。問題があれば直して繰り返す。
13. 実行の準備ができたら、チャットウィンドウで実行する。CLI でも実行できる。どの画面を使っても、エージェントは何をしようとしているかを把握して引き継ぐ、と述べている。
14. 実行は時間がかかるため省略している。すでに、ランディングゾーンの情報に基づいてインフラのファイルが生成されている。実行後に、セキュリティの確認、ビルドと検証を行う。単体テストと統合テストが生成される。
15. アプリは Azure の App Service に移行完了。App Service で「View app」を開くと、10〜15 年以上前のレガシーアプリが動いている。インフラ、データベース、コードを含めてモダナイズできたと述べている。

> 補足：画面上のボタン名や表示内容は、ナレーションで語られた範囲しか分かりません。上の手順は語られた順に整理したものです。

## 7. 注意点・発表者の気付き

- **エンタープライズ規模にはオーケストレーションが必要。** Nish 氏は、Copilot でコードのモダナイズが簡単になったと思うかと会場に尋ね（挙手は少数）、コードを変換できても、エンタープライズ規模でセキュリティとガードレールを守るには優れたオーケストレーションが要る、と説明しています。
- **人が確認する。** modernize CLI の各段階で、人が計画をレビューし、ガードレールを守らせる、と説明しています。
- **評価とテスト。** Q&A で登壇者が「しっかりした evals とテストスイートを整え、機能テスト、セキュリティテストで近道をしないこと」と述べています。
- **Dapr は標準では未対応。** Dapr 専用のスキルは組み込まれておらず、カスタムスキルで対応する必要があります。
- **rulebooks の対象。** 現状はプロのコード向けで、ローコードには適用されません。
- **時間の都合で省略した操作。** データ同期の待ち時間、評価の実行、コード変換の実行は、デモで早送りまたは省略されています。

## 9. まとめ

Azure Catalyst は、Azure Migrate と GitHub Copilot modernization agent を統合し、資産の把握、提案、ランディングゾーンとアプリケーションの設計、ウェーブ計画、データ移行とコード変換までを、1 つのコンテキストでつなぐ体験です。modernize CLI（GA）、rulebooks（GA）、BYOM/BYOK、Azure SQL と Oracle to PostgreSQL の readiness レポート（preview）といった機能も発表されました。

Lumen の事例では、24,000 行のアプリで工数を 82% 削減しました。発表者は、セキュリティを 3 層（既知の脆弱性の自動修正、M-Dash、Azure 資産の継続保護）で捉え、移行後の後付けにしないことを強調しています。また、Frontier Accelerate program を使えば、分析から実装まで Microsoft の専門家支援を無償で受けられます。目標は、複雑さと技術的負債を減らし、AI に対応できるアプリを得ることです。
