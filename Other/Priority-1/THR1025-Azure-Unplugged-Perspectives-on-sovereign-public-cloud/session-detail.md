# THR1025 Azure Unplugged: Perspectives on sovereign public cloud

## 1. はじめに

このセッションは、ソブリン（sovereign）クラウドを「レジリエンス」「データ管理」「ソブリン AI」の 3 つのシナリオに分けて語り合う、25 分のシアターセッションです。進行役が各シナリオの課題を投げかけ、Microsoft の 2 人の登壇者が、パブリッククラウドの機能から Azure Local、Foundry Local までを順に答えていく対談形式で進みます。

全体を貫く答えは、**「ワークロードごとに、パブリッククラウド、ハイブリッド（Azure Local 接続型）、切断型（disconnected）のどこで動かすかを選ぶ。選択は後から変えられる」** というものです。画面を使ったデモはありません。

## 4. 発表者が伝えたいメッセージ

Microsoft の登壇者は、ソブリンへの対応を「パブリッククラウドか、オンプレミスか」の二択としてではなく、**パブリッククラウドから Azure Local（接続型・切断型）へ続く「continuum（連続体）」** として説明しています。Azure Local に持ち込まれるサービスは、Azure と同じ見た目と動きになるよう一貫性が保たれる、というのが中核の主張です。

最後のまとめでは、次の 3 点が語られました。

- 基本を押さえ、自分のワークロードを理解する。全部に同じ解を当てはめようとすると、コストが高くなる
- 組織全体で 1 つの解を選ぶ必要はない。ワークロードごとに考える
- 選択は「一方通行のドア」ではなく、後から変えられる。規制や枠組みは変わっても、ワークロードを変える必要はない

## 5. 発表内容の詳細

### 5.1 自己紹介

Allison 氏は、Azure 組織で chief product officer 部門に所属し、顧客・パートナー・フィールド組織を支援する役割だと説明しました。製品戦略や新製品開発にも関わっています。もともと業界出身で、銀行で「皆さんと同じ課題」に取り組んでいたとのことです。Meena 氏は、sovereign private cloud と Azure Local の product management を担当していて、ここ 1〜2 年でソブリンに関する顧客の関心が急速に高まっているため、素早く開発を進めていると述べました。

### 5.2 シナリオ 1：レジリエンス

進行役が示した例は、公共機関が大きな雷雨の中でも住民に情報提供を続けなければならない場面です。「パブリッククラウドを使い続けられるのか、オンプレミスに戻るべきか」が問いです。

**パブリッククラウドでの考え方**

Microsoft の登壇者（インフラ出身と自己紹介した人）は、基本から順に積み上げる説明をしました。

1. 公共機関であれば、まずデータを国内（in country）に置くことが関心事になる。Azure には事実上すべての地域をカバーする、**世界 80 リージョン**がある
2. 最初にワークロードを洗い出し、次にデータを洗い出す
3. その上で、必要なレジリエンスのレベルを決める
4. 多少のダウンタイムを許容できる本番アプリなら、**ゾーン冗長（zonal resilience）** から始める。これは常に推奨しており、プラットフォームの大半に組み込まれている
5. ダウンタイムが許されず、公開サイトに機微データがあり、データを自国内（geo）に留める必要がある場合は、国内の**2 つ目のリージョン**を探してマルチリージョン構成にする。ただしその 2 つ目のリージョンが使えるかどうかは地域によって異なる（「あとで戻る」と述べていますが、このセッションでは詳しく説明されていません）
6. マルチリージョンでは、データレプリケーションを使い、通常リージョンはペアになる

**データの扱い（バックアップ）**

登壇者は、データはダウンタイムを許容できる業務でも守る必要がある、と述べ、現在 preview（登壇者は「I think we're in preview」と話しています）の機能を紹介しています。従来 Azure はリージョンをペアにし、バックアップもペアのリージョンに置いてきました。その考え方を見直し、**バックアップの保存先を「選択したリージョン」にできる**ようにしています。ソブリン性を保つ配慮は残るので、どこにでも置けるわけではありません。Azure のバックアップから順次提供が始まり、世界の各リージョンへ少しずつ展開中で、今後 1〜2 年でストレージ面の選択肢も増えていく、という説明です。

**Azure Local へ**

自国内に 1 つのリージョンしかなく、ミッションクリティカルなアプリがある場合の次の選択肢が Azure Local です。リージョンとアベイラビリティゾーンによる耐障害性という考え方は、そのまま当てはまります。ただし、重要なインフラのすべてをリージョン単位のレジリエンスに頼れない顧客もいます。データを国内、特定のデータセンター、あるいは許可された人のみが運用する範囲に留めなければならない、といったソブリンの枠組みや規制がある場合です。そこで Azure Local を使います。

Azure Local の基本方針は、Azure の外でワークロードを動かしても、**Azure と一貫した体験を保つこと**です。持ち込むサービスは、Azure と同じ見た目と動きになるようにしています。登壇者は、機能の同等性（feature parity）を目指すものではなく、サポートする機能については一貫性を保つ、と区別しています。

レジリエンスについては、次のように説明されています。

- 平常時は Azure、障害時は Azure Local を「フェイルオーバーの保険」として使う。たとえ話として、スペアタイヤ（トランスクリプトでは "donut"）を挙げ、パンクしたときだけ使って、直したら通常のタイヤに戻すイメージだと説明している
- パブリッククラウドに一切出られず Azure Local だけで完結させる場合も、複数サイトを使ったディザスタリカバリが組み込まれている
- ディザスタリカバリは、クラウド側で動く **Azure Site Recovery**、または完全にオンプレミスのインフラのみで行える
- RTO / RPO の構成は、アプリケーションが許容できるダウンタイムに合わせて選ぶ（トランスクリプトに聞き取りにくい箇所があります）
- スケジュールバックアップでのデータコピーは、日次でも時間単位でもよい。クラウドへの経路が現実的でない場合に備え、**完全にオンプレミスで完結する DR** も設計できる

また、自社（first party）のソリューションだけでなく、業界の ISV とも連携して、顧客が耐障害性のあるアプリケーションを構築できるようにしている、と述べています。

**Sovereign control panel**

登壇者は「sovereign control panel の発表を見ましたか」と会場に尋ね、現在 **public preview** であると紹介しました。説明された機能は次のとおりです。

- ソブリンのポスチャ（態勢）が適切かを把握できる
- 推奨事項を提示する
- ハイブリッドの観点から、アーキテクチャの推奨を示す。ワークロードの一部をパブリッククラウド、一部を Azure Local で動かしたい場合に、たとえば Local で利用できないサービスを使っていないかなど、複雑な判断を支援する
- ワークロードが Azure Local で動かせるかどうかを評価する

Azure Local のコントロールプレーンは、Azure に**接続した状態でも、完全に切断した状態でも**運用できます。登壇者はこれを「逆さの漏斗」にたとえました。最上位が Azure で、Azure Local の接続型で使えるサービスはその部分集合、切断型ではさらに少ない部分集合になります。Azure はリージョン規模で多数のサービスを動かしていますが、オンプレミスでは最小限のフットプリントで必要なサービスだけを持ち込みたく、自前のデータセンターを運用するにはコストも要因になるため、「リージョン規模のサービスをエッジで動かしたくはない」という理由です。sovereign control panel は、オンプレミスの展開状況に基づいてこの評価を行い、アプリケーションが Azure Local へデプロイできる状態かを示します。

また、**sovereign landing zones を Azure Local でも使えるようにした**ことが、プロセスを簡素化する大きな一歩だと紹介されました。

### 5.3 シナリオ 2：データ管理

進行役は、銀行で働いており機密情報を扱っていること、情報が外部に漏れれば国全体のニュースになりうることを挙げ、「誰がデータにアクセスしたか、誰が鍵を持っているか、データを持ち出されずに転送するにはどうするか」と問いかけました。

**暗号化と鍵管理**

Microsoft の登壇者（セキュリティ部門に 3 年いたと述べた人）は、課題を 2 つに整理しました。1 つはデータをどう守るか（暗号化）、もう 1 つはそのデータへの運用者のアクセスをどう管理するかです。オンプレミスの時代にも、データベース管理者が勝手にデータを変更できないよう複雑な統制を作っていたと振り返っています。

暗号化については、ベストプラクティスとして次の 3 点が示されました。

| 状態 | 説明 |
|---|---|
| 保存時（at rest） | 暗号化する |
| 転送時（in transit） | 暗号化する |
| 使用中（in use） | confidential compute により、メモリ上のデータも暗号化できる。悪意ある攻撃への対策として特に有効 |

鍵の管理には customer managed keys を使い、できれば managed HSM と組み合わせます。さらに **External Key Manager** が GA したことが紹介され、第三者が自分の機器（third party device）で鍵を保持できるようになるとされています。

> 注意：鍵を外部で管理する場合、**鍵を失うと Microsoft には助けられません。** 外部管理の鍵は Microsoft が所有していないため復旧できず、バックドアもありません（自分でバックアップしている場合を除く）。登壇者は「柔軟性には責任が伴う」と述べ、鍵管理を 24 時間 365 日、確実に運用できる組織か、信頼できるパートナーがいる場合にのみ向く、と強調しました。Microsoft は顧客のプロファイルに応じて、この方法が適切かどうかを強く案内するとのことです。「find my phone のような機能はない」という例えも使われています。

**運用者アクセスの管理**

誰がデータにアクセスできるかについては、次の仕組みが紹介されました。

1. **Just-in-time アクセス**：運用でシステムに入る人は、必ず統制のゲートを通る。ゲートでのすべての操作は、改ざんできない台帳（immutable ledger）に記録される
2. **Lockbox**：一部のサービスが備える。データへのアクセスに、顧客が通知を受け、許可に関与できるようにする。たとえば SQL Server のプラットフォームを Microsoft に管理させる場合、Microsoft はデータを見ずに運用する。顧客からの問い合わせで調査のために入る必要があるときに、Lockbox で保護できる
3. **Data Guardian**：ヨーロッパで発表された追加サービス。「hands on keyboard」の作業を現地に留め、escort（付き添い）サービスなどを伴う。すべての操作が分かるようにする追加統制（音声認識の都合で一部の語が確定できません）

**Azure Local 接続型でのオプション**

パブリッククラウドの統制が十分でなく、運用統制をデータセンター内で行う必要がある場合、Azure Local connected が選択肢になります。データ、ワークロード、アクセスの運用管理を自分で完結でき、一方で ID 管理、アクセス制御の構成、Azure Policy、ネットワークセキュリティグループといった **Azure と同じ機能を、ワークロードをオンプレミスで動かしながら使えます**。これは、ソブリンの取り組みの「統制の連続体」の一部として降ろしてきたものと説明されています。

**Confidential computing とその他の機能**

- Confidential VM は**一般提供（GA）**
- Confidential GPU は**来年初めに提供予定**
- Trusted VM、secure boot を提供
- 切断型の環境でも、ローカルの Azure Key Vault 体験があり、BitLocker キーをオンプレミスで管理できる
- 将来的には、切断型の Azure Local で Azure Key Vault から **Key Vault Premium** へ進める方向で検討中

登壇者は、どこでワークロードを動かしても、データが自分の制御下にあるという信頼を得られるようにしたい、とまとめています。

### 5.4 シナリオ 3：ソブリン AI

進行役の例は、製薬会社です。世界中から集めた情報でモデルを学習させたいが、それは知的財産なので失いたくなく、誰がアクセスし、どう再利用されるかも知りたい。公開された AI を使わずに Microsoft の機能を使えないか、という問いです。

Microsoft の登壇者は、ソブリン AI では「**逆向きのアプローチ**」を取ったと説明しました。最も安全で統制された環境、つまり切断型環境から出発し、その中に Azure の AI 機能を持ち込みます。それが **Foundry Local** で、完全に切断された環境でソブリン AI を動かすためのツールを提供します。説明された「ツールボックス」は次の構成です。

| 要素 | 内容 | 状況 |
|---|---|---|
| Models | AI 推論用のモデルを動かす。Foundry カタログのオープンソースモデルをオンプレミスにデプロイできる。モデルプロバイダーと直接の関係があり、自分の環境で動かすライセンスがあるなら、**自分のモデルを持ち込める**。推論エンドポイントを作り、ワークロードから利用する | GA |
| Knowledge | ローカルでのチャット体験、エージェントによる検索（agent retrieval）、ドキュメントや機微データへの自然言語でのアクセス | GA |
| Tools | レガシーなツールやサービスと AI の推論エンドポイントをつなぐため、**MCP servers** をコネクタとして使う | preview |
| Agent services | AI エージェントを管理するサービス。多くの顧客がエージェントを作りたがっており、その管理のために用意した | preview |

これは Foundry を土台に、Azure AI サービスの機能をエッジに延ばしたもので、ここでも「連続体」の考え方が使われています。confidential compute と confidential GPU も組み合わせ、Microsoft と Azure のデータガバナンス、アクセス制御、強固なセキュリティポスチャの一部として提供する、という説明です。

**AI 基盤の土台（AKS 上の Foundry）**

もう一方の Microsoft の登壇者が、基盤側の進展を補足しました。製品グループが別々に進んできた状況を改めて揃え、ツール群の下に**一貫した基盤（ハーネス）** を提供するというもので、一部は preview として提供が始まったところです。主な点は次のとおりです。

1. **AI Foundry が AKS 上で動くようになる。** プラットフォームで、AKS 上でワークロードを動かす選択ができる
2. **Agent sandbox**：エージェントがコードを実行するとき、microVM という隔離された仮想環境で動かす。封じ込められた仮想環境で動くため、厳しく制限される
3. **Agent grid**：サービスメッシュのようなもので、セキュアな接続を確保する。自分のデータにつながっていること、Entra に裏づけられた形でつながっていることを確認できる。ソブリンで重要になる。Entra チームが、この AI プラットフォームに ID を組み込む作業を進めてきた
4. Foundry Local、クラウド上の Foundry、あるいは Foundry を使わず**直接 AKS** のいずれからでも、これらの機能を使える
5. **AKS の FlexNodes**：GPU の確保は難しいが、使い切れていない GPU があれば、Microsoft のガバナンスと機能をそこに適用してワークロードをデプロイできる。データをまだクラウドに置く準備ができないためオンプレミスに残している場合でも、セキュリティとソブリンの要件に対応しながら、必要な場所で動かせる

### 5.5 最後のテイクアウェイ

進行役が「小さな要点を」と促し、各登壇者が次のように答えました。

- 1 人目：基本を正しく押さえ、ワークロードを理解する。全部に同じ解を当てはめようとしない（コストがかかりすぎるため）
- 2 人目：Azure の一貫性を、ソブリンの連続体全体で保つことを重視している。ワークロード単位で考え、「ポリシーは何か」「AI ガバナンスは何か」「接続を失ったらどうなるか」「事業継続計画は何か」を自問する。回答に応じて、ソブリンの選択肢を 1 つまたは複数選ぶ。パブリッククラウドにも多くのアクセス制御とガバナンスがあり、それで足りなければプライベートクラウドを検討する。プライベートクラウドの中にも、ハイブリッドモデルと切断型モデルがある。**選択は一方通行ではなく、後から変更できる**。枠組みや規制は変わるが、ワークロードは変えなくてよい

進行役は最後に、すべてはリスク管理、リスク分析、そして組織が採用しているリスクアペタイト（risk appetite）の枠組みの問題だとまとめ、ソブリンクラウドに関するアンケートへの回答を呼びかけました。

## 7. 注意点・発表者の気付き

- **外部管理の鍵は復旧できません。** 鍵を失うと Microsoft は助けられず、バックドアもありません。運用体制を整えられる組織向けの選択肢で、Microsoft は顧客のプロファイルに応じて適否を強く案内するとしています
- **Azure Local は機能の同等性を目指すものではありません。** サポートされる機能については Azure と一貫性を保ちますが、持ち込まれるサービスは Azure の一部です。接続型より切断型の方が、使えるサービスはさらに少なくなります
- **2 つ目のリージョンが使えるとは限りません。** 国内にリージョンが 1 つしかない場合は、Azure Local を検討します
- **機能の提供状況に差があります。** バックアップの保存先選択（登壇者は「I think we're in preview」と話しています）、Foundry Local の Tools と Agent services は preview、sovereign control panel は public preview、Confidential GPU は来年初めの予定です。External Key Manager、Confidential VM、Foundry Local の Models と Knowledge は GA です
- **GPU の確保は難しい**と述べ、使っていない GPU があれば FlexNodes で活用する案が示されています
- 最後のテイクアウェイでは、全社で 1 つの解にそろえるのではなく、ワークロードごとに考えることが繰り返し強調されました

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- パブリッククラウドの利点を保ったまま、レジリエンス、データ管理、AI の各面でソブリン要件に対応する選択肢（パブリッククラウド、Azure Local の接続型・切断型）を、連続体として選べる
- Azure Local でも Azure と一貫した体験（ID 管理、アクセス制御の構成、Azure Policy、ネットワークセキュリティグループ）を使いながら、運用統制をデータセンター内に置ける
- 完全に切断された環境でも、Foundry Local により、自分のモデルやオープンソースモデルの推論、ローカルのナレッジ、MCP servers によるコネクタ、エージェント管理を使える
- 選択は後から変更でき、規制が変わってもワークロードを変更する必要がない
- sovereign control panel と sovereign landing zones で、Azure Local への展開の判断と準備を進めやすくなる

## 9. まとめ

ソブリンクラウドは、防衛や政府だけでなく銀行、保険、医療、製造業にも広がり、取締役会レベルの議題になっています。このセッションは、レジリエンス、データ管理、ソブリン AI の 3 つのシナリオで、Azure のパブリッククラウドから Azure Local（接続型・切断型）、Foundry Local までが連続した選択肢であることを説明しました。

レジリエンスはゾーン、マルチリージョン、Azure Local の順に考え、データ管理は暗号化、鍵管理、運用者アクセスの統制（Just-in-time、Lockbox、Data Guardian、confidential computing）で組み立てます。ソブリン AI は切断型を出発点に、Foundry Local と AKS 上の基盤で整えていく方向です。最終的な結論は、基本を押さえ、ワークロードごとに選び、選択は後から変えられる、という点でした。
