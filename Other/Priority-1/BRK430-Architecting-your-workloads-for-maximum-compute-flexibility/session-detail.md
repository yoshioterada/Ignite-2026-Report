# BRK430 Architecting your workloads for maximum compute flexibility

## 1. はじめに

このセッションは、Azure のコンピュート（VM、VM Scale Sets、AKS など）で「必要な容量をどう確保し、コストを抑えるか」を、**ワークロード側が柔軟になる**という観点から整理した内容です。登壇者は、容量の確保が Azure に限らずどの環境でも難しくなっていることを前提に、柔軟性を 3 つの軸（SKU、場所、時間）で説明します。

新しい製品や機能も多く出てきます。主なものは、Adaptive placement、Compute templates（プレビュー）、Standby pool の予測機能、Azure Compute Fleet の GA 機能、IBM Spectrum 向け Azure Resource Connector（GA）、Spot Plus（パブリックプレビュー）、DT シリーズ VM です。IaaS の構成を見直したい開発者やインフラ担当者向けの話で、スライドに加えて 4 つの画面デモが行われました。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/BRK430](https://ignite.microsoft.com/en-US/sessions/BRK430)

## 4. 発表者が伝えたいメッセージ

一貫した主張は、「**柔軟性をアーキテクチャの一部として組み込み、個々のワークロードごとに最適化しなくてよいようにする**」ことです。オーケストレーターは自分のもの（LSF、Symphony、Compute Fleet、AKS など）を持ち込み、ワークロードの柔軟性に応じて Azure のツールや製品がコスト削減、デプロイの高速化、管理の簡素化を支えます。

Rajesh 氏は特に、HPC や EDA の顧客に対して「**スケジューラーは今のまま使い、Azure が容量を提供する**」（Keep your scheduler. Azure gives you the capacity.）という立場を強調しました。また「柔軟性とは最も安い VM を選ぶことではなく、ワークロードごとに適切な容量を選ぶこと」とも述べています。

## 5. 発表内容の詳細

### 5.1 なぜ柔軟性が必要か

Varun 氏は、容量の確保はどの環境でも逼迫しているとしたうえで、顧客が直面している課題を 3 つ挙げています。

| 課題 | 内容 |
| --- | --- |
| コスト | 1 つの固定 SKU に縛られてプレミアムを払わないこと。価格や新 SKU の登場に応じて切り替え、より良い価格性能比を取り込みたい |
| デプロイの加速 | 特定の種類の容量に固執せず、より多くの容量にアクセスしたい。希望の SKU が取れないときは別の SKU に切り替えたい |
| 管理 | 1 つの SKU を指定して取れるかどうか分からず、取れなければ次を試す、という試行錯誤の繰り返しになる。運用チームが払っているこの見えにくいコストを減らしたい |

### 5.2 3 つの軸と対応する製品

柔軟性は次の 3 つの軸で整理されています。

| 軸 | 意味 | 関連する製品・機能 |
| --- | --- | --- |
| SKU の柔軟性 | 異なるハードウェアの種類でワークロードを動かす | AKS の Node auto provisioning（NAP）、VMSS の Instance mix、Azure Compute Fleet、Compute templates、単一 VM の Adaptive placement |
| 場所の柔軟性（リージョン） | 複数リージョンへのデプロイを簡単に管理する | Azure Compute Fleet のマルチリージョンデプロイ |
| 時間の柔軟性 | 実行のタイミングや時間に影響されないワークロードでコストを下げる | Spot、Spot Plus、DT サブファミリー |

Varun 氏の説明では、NAP は Kubernetes（AKS）向けで、異なる SKU から容量を得られます。同じ考え方が VMSS では Instance mix です。Azure Compute Fleet では SKU そのものではなく、SKU に合致する属性を指定すると、Azure が該当する SKU をデプロイします。Compute templates は、VM の構成をデプロイパイプラインの外側で定義するもので、Ignite でプレビューになりました。マルチリージョンの Compute Fleet は、もうすぐ GA になると説明されています。

### 5.3 Adaptive placement（単一 VM）

通常、単一 VM では SKU（例として D32SV5）を指定し、その容量がなければデプロイは失敗します。Adaptive placement では、参照 SKU を指定したうえでオプトインします。Azure はまず指定された SKU で容量を満たそうとしますが、できない場合は**同じファミリー内の別の SKU**（例：V5 ファミリーで Intel から AMD へ）で満たします。多くの顧客がデプロイで Intel と AMD の両方を混在させて使っていることが背景にある、という説明です。

- 常に参照 SKU を優先し、それが無い場合にだけフォールバックします。
- イメージやネットワーク構成などは同じものを使うため、他の部分は変わりません。
- Azure の自社サービスや一部の顧客で採用が進み、通常の（単一 SKU の）場合に比べて**割り当て成功率が大幅に高い**と述べています（具体的な数値は示されていません）。
- 試行錯誤の手間を減らし、制約を伝えたうえで容量の充足を Azure に任せられます。

提供状況（プレビューか GA か）については、発表では述べられていません。

### 5.4 Compute templates

VM の構成を複数のデプロイで使い回すと、タイプミスや別の構成の混入で意図した内容から簡単にずれてしまうことがあります。Compute templates は、**構成をデプロイから切り離し**、1 か所で定義してバージョン管理し、複数のデプロイで共有する仕組みです。バージョンを変えると、デプロイ時には最新バージョンの構成が使われます。

単一 VM 向けにプレビューで提供されており、構成に起因するデプロイの時間とエラーが大きく減ることを確認していると、Varun 氏は述べています。

### 5.5 Standby pool と予測

Standby pool は少なくとも 2 年前に GA した機能で、スケールアウトに備えて、事前にウォームアップ・構成済みの VM をプールしておきます。トラフィックが来たらすぐに使えますが、プールにいる VM にも料金がかかります。そのコストを減らすために、**予測機能**を加えると説明されています（提供状況は述べられていません）。利用パターンを見て、スパイクが起きる時間を予測し、それより前にプールの VM をウォームアップします。

Standby pool は Azure Container Instances でも使え、同じ予測モデルを適用できます。

### 5.6 クラウドネイティブな大規模柔軟性：Instance mix と NAP

ここから Rajesh 氏の担当です。需要には、安定して予測できる容量を必要とするもの、数十から数千コアまで数時間だけ拡大して戻るもの、厳しい締め切りがあるものが混在します。クラウドネイティブなアプリでは、AKS や VM Scale Sets を使い、レプリカや VM を複数の VM ファミリーにまたがってスケールすることが柔軟性にあたります。一方、企業の HPC や EDA はワークロードオーケストレーター（スケジューラー）に依存しているため、アプリの再設計やオーケストレーターの置き換えなしにクラウドの弾力性を得たい、というニーズがあります。

- **VMSS の Instance mix**：最大 **5 種類**のサイズを列挙でき、最低価格、容量、または優先順位のいずれかで VM が選ばれます。1 つのスケールセットで複数サイズを扱えます。世界的な決済プラットフォームの企業が約 4 週間で導入し、割り当て失敗が **68 fold** 減ったとのことです（話者は「64 folds、sorry、68 folds」と言い直しています）。あるサイズが取れなくても別のサイズで完了できたと説明しています。
- **AKS の Node auto provisioning（NAP）**：同じことを 1 層上で行います。Pending の Pod が必要とするものを宣言し、オープンソースの Karpenter をベースにした NAP が、ノードプールの許可範囲から VM サイズを選んでノードを追加します。需要が減ると統合（consolidate）します。VM でもコンテナーでも「SKU ではなく必要なものを記述する」考え方です。

### 5.7 Azure Compute Fleet の新機能

自前のオーケストレーション（Kubernetes、バッチシステム、独自のコントロールプレーン）を持つ顧客のための機能が Azure Compute Fleet です。Ignite では次が発表されました。

| 機能 | 状態 | 内容 |
| --- | --- | --- |
| Single instance VM launch mode | GA | 1 回のリクエストで、サイズ、ゾーン、価格タイプをまたいで VM をプロビジョニングし、オーケストレーターに引き渡す |
| vCPU capacity type（トランスクリプト上は「VM CPU types」とも聞こえる） | GA | VM の台数ではなく総コア数を指定し、受け入れ可能な VM サイズを伝える。Spot、オンデマンド、またはその組み合わせも指定できる |
| マルチリージョン | プレビュー（GA は近日） | 3 つのリージョンにまたがって検索範囲を広げる |

vCPU 指定では、Fleet が対象となる VM の中から価格と容量の空き状況を見て最適な組み合わせでコア数を満たします。グリッドスケジューラーにとってコア数は自然な単位だと説明されています。また、**Fleet はジョブを管理せず、容量だけを確保します。ジョブの制御は引き続きスケジューラーが担います**。起動した VM は素の実行ホストとして立ち上がり、ジョブを動かす仕組みに登録されます。

### 5.8 IBM Spectrum 向け Azure Resource Connector（GA）

Rajesh 氏は、**Azure Resource Connector for IBM Spectrum Symphony and IBM Spectrum LSF** の GA を発表しました。入手方法は、Marketplace で「IBM Spectrum」を検索し、Symphony または LSF 用のプロバイダープラグインを入手する、というものです。プラグインは**無料**とのことです。

対象は、Symphony のリスクグリッドや LSF の EDA ファームのように、すでに IBM Spectrum を使っているチームです。従来はクラスターが固定で、リスク計算やリグレッションの波が来るとジョブはキューで待つか、ピークに合わせてサイズを決めて残りの時間は遊休になる、という状態でした。コネクターを使うと次のようになります。

1. キューが容量を決める。IBM Host Factory がバックログを見て、Compute Fleet に新しいホストを要求する。
2. Fleet が、顧客が指定したサイズの中から選ぶ。
3. ホストがクラスターに参加し、処理して、キューが空になるとスケールダウンする。

役割分担は、上から順に、HPC／EDA アプリケーションがジョブを投入し、Symphony／LSF がキュー、優先度、スケジューリング（ワークロードの知見）を担い、IBM Host Factory と Azure Resource Connector が需要をリクエストに変換し、Azure Compute Fleet が承認済みの VM サイズから選ぶ、という構成です。VM は IBM のクラスターに参加してワークロードを実行します。

### 5.9 ストレージの新情報

ワークロードにはそれに見合うストレージも必要です。

- **EDA：Azure NetApp Files（ANF）**が標準。最新のベンチマークでは、ボリュームセットあたり 1.85 倍の EDA ジョブという結果が示されました（付随するレイテンシの話は聞き取り不明瞭です）。オンプレミスのデータを ANF に持ち込む **Cache volumes が GA**、逆方向（ANF からオンプレミスへ）はプレビューです。
- **HPC：Azure Managed Lustre**（トランスクリプトでは「managed lusters」）が 5 倍にスケールし GA。容量は「25 から 120」、スループットは「112 ギガバイトから 2.5 テラバイト／秒」と発言されています（容量の単位は聞き取れませんでした）。

### 5.10 設計の 4 ステップとジョブの置き方

ジョブとキューから設計を始める 4 つのステップが示されました。

1. ワークロードごとに制約（メモリ、ライセンス、実行時間、締め切り）を分類する。
2. キューごとに 1 つのサイズを固定せず、動かせる VM サイズを広げる。
3. キューごとに容量ポリシー（capacity policy）を設定する。
4. チェックポイントとリトライでレジリエンスを組み込む。

同じクラスターでの例として、次が挙がりました。

- **RTL リグレッション**のように短時間の独立ジョブが数千単位で走る場合：Spot を広い VM プールで使い、退避されたらスケジューラーに再試行させる。
- **Place and route**（トランスクリプトでは「Place on route」と聞こえます）のように長時間かつメモリ負荷の高いジョブ：オンデマンドに置く。チェックポイントも使う。

### 5.11 IBM Spectrum Computing（Chris Bailey 氏）

IBM の Chris 氏は、IBM Spectrum Computing を「あらゆるハードウェア上のあらゆるワークロードを統合してオーケストレーションする」ものと紹介し、4 つの成果があると述べました。説明は次の 3 項目で、「利用率の向上」と「コスト最適化」は 1 つにまとめて語られています。

1. **結果を速く**：ワークロードを最も速く実行できるインフラに割り当てる。CPU、GPU、アクセラレーター、さらに量子も対象。
2. **利用率の向上とコスト最適化**：リソースを動的に共有し、パーティショニング、プリエンプション、リソースの入れ替えを行う。足りなくなればオンプレミスからのクラウドバースト、または Azure 上だけでの伸縮ができる。
3. **生産性の向上**：運用の簡素化、エンドユーザーのセルフサービス、大規模なワークロードの監視と管理。

これらは LSF、Symphony、Conductor の長年の実績の上にあり（トランスクリプトでは「IBM Spectrum Collective」とも聞こえます）、最大級の企業が使っていると説明しています。1 社で数百万コア、製品全体では数億コアを管理しているとのことです。

| 製品 | 位置づけ | 利用例（発言どおり） |
| --- | --- | --- |
| LSF（Load Sharing Facility） | インフラレベル。従来は HPC や科学用途 | 世界の大手半導体メーカー 25 社のうち 23 社が EDA に利用。大手自動車メーカー 12 社のうち 10 社。医療・ゲノム研究。米国の主要がん研究センター上位 3 つ |
| Symphony | 1 つ上の層。サービスとして結果を返す | 米国の大手金融機関 5 社のうち 4 社がリスク計算に利用。日中取引のリスクは低レイテンシが必要 |
| Conductor | さらに 1 つ上。Apache Spark、Dask、Anaconda などの分析機能の実装 | （発表では顧客例は述べられていません） |

従来型のワークロードに加えて、AI のトレーニングやファインチューニング、推論のように CPU や GPU を大量に使う処理にも使われます。推論を優先し、空いている GPU でトレーニングやファインチューニングをバックグラウンドで行う、といったバランスの取り方も説明されました。

サービス型ワークロードでは、コンソール、CLI、または多くの場合 API 経由でワークロードを投入し、タスクキューに入って最適なコンピュートに配置されます。キューを継続的に多次元で分析し、まず既存のコンピュートに密に詰め、キューが伸びたら Compute Fleet に追加のコアや CPU とメモリの比率を要求してスケールアウトし、キューが縮むと戻す、という動きです。

### 5.12 Spot Plus（パブリックプレビュー、全 Azure リージョン）

Rohan 氏は、標準の Spot に対するフィードバックを受けた機能だと説明しています。

| 項目 | 内容 |
| --- | --- |
| 実行時間 | 標準の Spot より長い |
| 課金の保護 | 60 分未満で VM が退避された場合は、その Spot Plus の料金は請求されない |

### 5.13 DT シリーズ VM（DTv7、DTAv7）

ほとんどのワークロードはピーク性能の 100% を常に必要としないのに、顧客はピークに合わせて確保して不要な性能に料金を払っている、という問題意識から作られた新しいサブファミリーです。

- 最新世代の Intel と AMD プロセッサー上で動作します。
- **DTv7** は前世代の Dv7 より **20%**、**DTAv7** は前世代の DAv6 より **35%** 性能が良いと述べています。
- サイズは 2〜32 vCPU で、コアとメモリの比率は「4」（聞こえたまま）、ローカル NVMe ストレージを有効／無効にするオプションがあります。
- 向くのは、VDI、開発・テスト、CI/CD のように CPU 使用率が変動するワークロードです。
- 「コストを下げたいなら DT、性能を最大化したいなら D」という選び方が示されています。

## 6. デモ・手順

このセッションには 4 つのデモがあります。いずれも録音は音声だけのため、画面の細部は確認できず、語られた範囲で書いています。

### 6.1 Adaptive placement のデモ（Varun 氏）

2 部構成のデモです。

1. 1 台の VM（Standard E16v5）をデプロイした。デプロイ前に容量があるかは分からないが、デプロイ後に確認すると、要求した SKU が割り当てられていた。
2. ポータルで VM1 を開き、JSON を見ると、「VM size」と「preferred VM size」の 2 つの項目があり、この場合は両者が同じだった。
3. 次に、同じ SKU で **5 台**をデプロイした。出力を見ると、5 台のうち 1 台は容量が見つからず、要求された Intel 版ではなく **AMD 版**がデプロイされたが、デプロイ自体は成功した。
4. 5 台すべてが表示され、その 1 台では preferred size と実際のサイズが異なっていた（5 台のうち 4 台は要求どおりの SKU）。AMD を指定した場合に Intel が割り当てられることもあり得ると補足している。

### 6.2 Standby pool の予測のデモ（Varun 氏）

画面を見せながら説明するデモです。手順は語られた範囲では次のとおりです。

1. スケールセットがあり、午前 8 時ごろから夕方にかけてスケールアップとダウンを繰り返すパターンがある。
2. 履歴から、予測の確度は 90% と判断した。
3. プールの最小を 5、最大を 40 台に設定する。
4. 午前 9 時にピークが来る想定の可視化では、その前はスタンバイプールが 5 の閾値以下に保たれ、9 時前にプールが増え始める。
5. トラフィックが来ると、プールの VM がスケールセットに取り込まれ、バックグラウンドでスタンバイプールが補充される。
6. 日が進むと予測どおりに 5 台まで下がり、常に 40 台を動かし続けるコストを払わずに済む。

### 6.3 IBM Spectrum と Compute Fleet のデモ（Chris 氏）

Chris 氏は、インフラのスケールイン／アウトを見せても面白くはない、とした上で、次のデモを見せています。

1. 右側に Azure コンソールで見たコンピュートインフラ、その下に CLI（マシンとリソースの top 表示）がある。2 台のマシンが起動している。バックグラウンドのワークロードがあり、リソースプールの最小を 2 台にしているため。
2. 左側のロードドライバーで **6,000 の並列タスク**を一度に投入した。
3. 使用可能なインスタンスタイプの範囲と、アプリが必要とする CPU とメモリの比率が設定されている。2 台から **14 台**へ急速にスケールした。1 種類のインスタンスタイプではなく、許容する範囲を指定し、残りは Fleet に任せている。
4. 各タスクは 5 秒で終わる想定で、スケールアウトしたため、キューで順番待ちにならず、実際にほぼ 5 秒で完了した（画面が小さいと本人も述べています）。
5. タスク完了後、追加のリソースを自動的に解放した。Spot インスタンスを使っても、消えた分は Fleet が自動的に置き換えるとも述べています。

### 6.4 Spot Plus のデモ（Rohan 氏）

1. 最新の V7 VM で VM Scale Set を作成する。
2. 優先度のミックス（priority mix）にオプトインし、オンデマンドと Spot Plus を混在させる。約 20% がオンデマンド、残り 80% が Spot Plus。
3. Spot Plus は従量課金価格に比べて **80% 以上割引**になっていると述べ、これを目玉の機能（hero feature）としている。
4. VM が正常にデプロイされ実行される。数時間後、**リバランス通知**（15 分前の警告で、この Spot Plus VM が退避の危険にあることを知らせる）が届く。
5. VM に入ると、VM がリバランス通知を受け取り、チェックポイントを開始している。
6. 退避の 2 分前に**プリエンプト通知**が届き、VM は正常にシャットダウンして終了した。
7. スケールセット内の残りの Spot Plus VM は通常どおり動き続けている。

## 7. 注意点・発表者の気付き

- **Fleet はジョブを管理しません。** 容量の確保だけで、スケジューラーが引き続きジョブの管理を担います。
- 柔軟性は「最も安い VM を選ぶこと」ではなく、「ワークロードごとに適切な容量を選ぶこと」です。長時間でメモリ負荷の高いジョブをオンデマンドに置く例が示されました。
- 退避への備えとして、**チェックポイントとリトライ**を設計に組み込むことが推奨されています。
- Spot と Spot Plus の使い分け：非常に再試行しやすくレジリエンスが高いワークロードには、最低コストの Spot を引き続き勧めています。長い実行時間が要る HPC や ML トレーニング、長めの通知が要る CI/CD エージェントには Spot Plus が向いています。
- DT と D の使い分け：一貫したピーク性能が要る場合、または 32 vCPU を超えるサイズが要る場合は、D シリーズを選びます。
- Adaptive placement はまず参照 SKU で満たそうとするため、デモのように、複数台のうち一部だけが別 SKU になる場合があります。
- 管理コストに関する指摘として、SKU を 1 つずつ試す試行錯誤は、運用チームが見えない形で払っているコストだと説明されています。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。詳細は 5 章を参照してください。

- Instance mix を使った決済プラットフォーム企業の例では、約 4 週間で導入でき、割り当て失敗が 68 fold 減少しました。
- Adaptive placement を採用した顧客では、割り当て成功率が通常の単一 SKU より大幅に高くなりました（数値は示されていません）。
- Compute templates は、構成に起因するデプロイ時間とエラーを大きく減らしたと述べられています。
- Standby pool の予測は、プールで VM が遊んでいる時間を減らし、常に 40 台を動かし続けるコストを避けられます（デモの設定例）。
- Spot Plus は、デモの設定で従量課金に比べて 80% 以上の割引となり、60 分未満の退避では課金されません。
- DTv7 は Dv7 より 20%、DTAv7 は DAv6 より 35% 性能が良く、変動の大きいワークロードのコストを下げられます。
- IBM Spectrum のコネクターにより、スケジューラーを変えずに Azure の容量を使え、固定クラスターのピーク対応による遊休を減らせます。

## 9. まとめ

このセッションの要点は次のとおりです。

1. 容量の確保は逼迫しており、**SKU、場所、時間**の 3 つの軸で柔軟性を持たせることが、コスト、デプロイ速度、管理負荷に効きます。
2. 単一 VM には Adaptive placement と Compute templates、スケールには Instance mix、NAP、Azure Compute Fleet（Single instance VM launch mode と vCPU capacity type は GA）が用意されています。
3. HPC・EDA 向けには、IBM Spectrum Symphony／LSF 用の Azure Resource Connector が GA になり、スケジューラーはそのままで Azure の容量を使えます。
4. コスト面では、Spot Plus（プレビュー）と DT シリーズ VM（DTv7、DTAv7）が発表されました。
5. 登壇者は、手持ちのワークロードを見直し、紹介された製品のいくつかを選んでインフラを最適化するよう呼びかけています。
