# THRSP1109 Deploy intelligent SRE for autonomous cloud ops

## 1. はじめに

このセッションは、Dynatrace と Microsoft が共同で行った 25 分のシアターセッションです。Azure 環境が複雑になり、アラートが増え続けるなかで、障害対応をどこまで自動化できるのかを扱います。

中心になるのは、Dynatrace が検知した問題を Azure SRE Agent に引き渡し、原因調査からメール通知までを人手を介さずに進める連携です。Microsoft 側の登壇者がこの連携の設定と動作を「シミュレーションしたデモ」で見せ、後半では Commerzbank の登壇者が、自社のオンラインポータルで Dynatrace と SRE Agent をどう使っているかを紹介します。

発表全体を通した結論は、**「ゼロオペレーションはゼロ人間を意味しない」** という点です。エージェントが動く場面でも、人間が統制（ガバナンス）を担い続けるという考え方が、最初から最後まで一貫しています。

## 4. 発表者が伝えたいメッセージ

発表者が繰り返し強調しているのは、次の 3 点です。

1. **ゼロオペレーションは、ゼロ人間ではない。** エージェントが動いても、人間が統制します。
2. **問題は「エージェントが動けるか」ではなく「動くべきか」。** そのために、エージェントを自社の状況に合わせ、自律度を自分で制御できることが重要だという主張です。推奨アクションだけを出させるのか、エージェントに実行までさせるのかは、利用者が設定で決めます。
3. **ブラックボックスの自動化は無い。** すべてのアクションは監査され、追跡（トレース）され、必要な場所に人間の関与（human in the loop）を置けます。

発表では、Dynatrace が問題を検知し、Azure SRE Agent が調査し、実行するかどうかを判断し、最後にサマリーで一連の流れを閉じる、という 4 つのステップが示されました。

## 5. 発表内容の詳細

### 5.1 背景：増えるアラートと減る時間

冒頭で Ashley 氏は、Dynatrace が今年実施した調査を紹介しています。クラウドプラットフォームエンジニアや SRE、クラウド変革を担う経営層に向けて、次のような状況を示しています。

| 調査の結果 | 数値 |
| --- | --- |
| まだ「火消しモード」（リアクティブ）にある組織 | 50% |
| 複雑なハイブリッド／マルチクラウド環境で運用している組織 | 73% |
| クラウド支出が無駄になっている割合 | 29% |

このほか、「オブザーバビリティにまだ AI を使っていない」という回答も多かったと述べています（こちらは数値の言及なし）。アラートは増える一方でコンテキストは少なく、時間も足りず、支出は増えるという状況が、この連携を作った動機として語られました。

### 5.2 Dynatrace の役割

Dynatrace は、問題がユーザーに影響する前に見つけ、「何が壊れたか」「どう直すか」を知るための道具を提供するプラットフォームとして紹介されました。説明された要素は次のとおりです。

- **Clouds アプリ**: Azure クラウド環境からネイティブにデータを取り込みます。インベントリを接続でき、リソースが一度宣言されて終わりではなく、時間が経っても最新の状態に保たれます。
- **一元的なビュー**: メトリクス、ログ、トレースといったシグナルを 1 つの画面にまとめ、トポロジーも組み立てます。トポロジーは SmartScape アプリで相関を確認できます。
- **環境の健全性の把握**: ノイズではなく環境全体の健康状態を見て、本当に夜中に人を起こすべきアラートと、そうでないものを分けます。
- **所有者とコストの把握**: Azure のタグを取り込むことで、アイドル状態や過剰にプロビジョニングされたリソースを見つけ、クラウドコストの最適化につなげます。

### 5.3 自律クラウド運用への成熟度モデル

Ashley 氏は、自律運用への道を「はしご（ladder）」にたとえた成熟度モデルとして説明しました。段階は次のとおりです。

1. **可視化**: Dynatrace がテックスタック全体の可視性を提供します。基盤は、信頼できるデータを土台にした Dynatrace の AI 層（Dynatrace intelligence）です。何が起きているか、なぜ起きているかが分かります。
2. **ガバナンスとガードレール**: エージェントを、動かしたいときに動かし、動かしたくないときには動かさない、という制御を入れます。
3. **ガイド付きの推奨**: エージェントから推奨アクションが提示されます。
4. **自動化された判断**: 信頼できる状態になれば、エージェント自身の自動判断に任せる段階も考えられます。

### 5.4 Dynatrace と Azure SRE Agent の「better together」

両者の役割分担は、次のように整理されています。

| | Azure SRE Agent | Dynatrace |
| --- | --- | --- |
| 見ているもの | Azure のネイティブなリソースとプラットフォームの健全性 | フルスタック（マルチクラウド、各種アプリケーション）のトレース、ログ、メトリクス、トポロジー |
| 強み | ネイティブな信頼性ワークフローによる推論と、運用コンテキストに基づく実行 | 因果関係に基づくルート原因分析（Dynatrace intelligence）。ビジネスへの実際の影響や ROI を示す |

Ashley 氏によれば、両者を組み合わせることで「共有された運用インテリジェンス」が得られ、調査が大幅に速くなり、より自信を持ったアクションが取れるようになります。Dynatrace がクラウド横断のコンテキストを持つことで、決定論的な答え（deterministic answers）を返せる点が強みだとも述べています。

そのうえで Ashley 氏は、Dynatrace の情報に根ざして、エージェントを自分の組織向けにパーソナライズ（何が起きていて、何が必要で、何を得たいか）することを強調しています。

### 5.5 SRE Agent の運用実績（Microsoft 社内）

Shamir 氏は、SRE Agent を Microsoft 社内でも導入していると説明しました。

- 3,000 を超えるサービスチームが、本番環境で SRE Agent を使っている
- 最大の賛辞の 1 つとして、オンコールのエンジニアから「SRE Agent のおかげで夜通し眠れるようになった」という声が届いている（金額には換算できない価値だと述べています）

### 5.6 Commerzbank の事例（Laurenz 氏）

ここからは Laurenz 氏のパートです。

#### 5.6.1 背景

Laurenz 氏は、自分たちがオンラインバンクであり、エンタープライズ企業でもある、という立場から話しました。複数のアプリケーションがクラウドをまたいで動いており、多くの組織と同じくマルチクラウド戦略をとっています。自身は法人顧客向けオンラインポータル全体の責任者で、アプリケーションは Azure 上で動いています。

顧客から見た経路は、次のように説明されました。

1. 顧客はインターネットからアクセスする
2. セキュリティ層を通る
3. リバースプロキシ（オンプレミスのデータセンターで動いている可能性がある）を通る
4. Express Route で Azure に接続する
5. 下流のシステム（Azure、オンプレミス、Google などで動く複数のアプリケーション）に至る

例として挙げられたのは、トレーディングポータルです。何か起きたとき SRE Agent も気づきますが、Azure の監視や Application Insights などで見えるものしか受け取らないという課題があります。そこで、全データセンター・全クラウドのメトリクスを取得できるオブザーバビリティ層として、Dynatrace の導入を進めていると説明しています（"launching" と聞こえ、導入済みか導入中かは明確ではありません）。Laurenz 氏は、Dynatrace が複数アプリケーションのイベントを受け取り、先ほど Shamir 氏が説明した MCP を通じて Azure SRE Agent の状況も扱える、と説明しています（この部分は音声が不明瞭です）。

#### 5.6.2 Dynatrace で見る全体像

1. **アプリケーションダッシュボード**: アプリケーションを、Azure、GCP、オンプレミスのどこで動いているかに関係なく一覧します。健全性、ユーザー満足度、不満、問題の発生を高いレベルで見られます。管理者の視点で、どのアプリが問題なく動いているかが分かります。
2. **問題の引き渡し**: 問題が起きたときは、ビジネス部門が付いている特定のアプリケーションに絞り込めます。それを開発者や運用チームに渡す場面で、Laurenz 氏は SRE Agent を、24 時間稼働する運用担当に渡すイメージで使っていると説明しました。

> 補足：Laurenz 氏が SRE Agent を何にたとえたかの単語（トランスクリプトでは "employer"）は、音声認識の都合で表記が確定できません。直後の「24 時間稼働する運用」という説明に沿って書いています。

#### 5.6.3 SRE Agent の「ライブレポート」を使った顧客視点の可視化

Laurenz 氏のチームでは、Dynatrace で高いレベルの状況は見られても、個別のアプリケーションに入ったときに「顧客から見たとき、自社のインフラ全体としてどう見えるか」を知る必要がありました。そこで、SRE Agent のライブレポート機能（"a live report"）を使い、ダッシュボードを作っています。

- Dynatrace と Azure のリソース、そして Azure SRE Agent に与えたナレッジベースをつなぎ、グラフを構築しています。
- 画面では、顧客のサインインから始まり、リバースプロキシ、Application Gateway、ビジネスのアプリケーションが動く Azure Container Apps、Cosmos DB や Entra ID といった Azure サービス、という経路が確認できると説明されています。
- 下流のシステムは RP ゲートウェイの背後に隠れていて、自分たちの責任範囲ではありません。そのため、Application Insights から「何を呼び、何が返ってきたか」を受け取り、これを Dynatrace にも接続しています。
- さらに拡大すると、より詳細なデータや、Azure 側のコンテナーのヘルスレポート、トレースまで掘り下げられると説明されています（一部は音声が不明瞭です）。
- 自分のアプリケーションにリクエストを送ったとき、そのアプリケーションが全体として健全かどうかも気になります。Dynatrace が問題を示していても、自分たちのフロー（経路）で見れば影響はなく、安心して眠れる場合があります。逆に下流のシステムでエラー率が上がっていても、Dynatrace の視点では全体の障害にはなっていない、という見方もできる、と説明しています。

> 注意：このパートは Laurenz 氏による画面の説明で、デモ形式かどうかは明言されていません。発話は "what you could see here" のように画面を見ながらの説明ですが、操作の手順は語られていません。

#### 5.6.4 ルート原因分析：リクエスト単位とユーザーセッション単位

ここがこの事例の中心です。

1. 問題を可視化したうえで、ルート原因分析を行います。SRE Agent はシグナルを受け取り、どのバックエンドが影響を受けているか、エラー率はどのくらいかを調べます。
2. 「全顧客が影響を受けているのか、ごく少数なのか」を把握することが重要で、本当の問題なのか、特定の顧客に依存した問題なのかの目安になります。
3. 顧客のリクエストからのトレース全体を見ると、下流のシステムがデータサービスを呼んで HTTP 400 が返り、そのエラーがライフサイクルを通ってリバースプロキシまで伝わり、そこで 500 に変わっていました。最終的に、ユーザーには 400 / 503 が返っていました。
4. 次に、トレースの単位を「リクエスト」から「ユーザーセッション全体」に切り替えます。すると状況は一変します。
   - ユーザーはサインインし、すべて問題なく動いていた
   - 承認すべきものを確認するため、注文の一覧を見た
   - 注文、支払い、トレーディングなど複数のビジネスアプリケーションが読み込まれた。トレーディングには問題があったようだが、ユーザーはそのまま支払い承認に進んだ
   - 支払いを 1 件開いて承認し、サインオフした
5. つまり、Dynatrace と SRE Agent の組み合わせで多くの問題が見えるようになるが、「ユーザーはそれに気づいたのか」「本当に問題なのか」まで確認できます。このケースの問題は、多数のうちの 1 つとして無視できる場合もある、という判断が可能になります。

#### 5.6.5 Laurenz 氏の学びと今後

- SRE Agent はインシデント調査の面で非常に助けになり、毎月または毎週のペースで新機能が提供されている点も高く評価しています。
- 一方、Dynatrace が提供するクロスステージ（"cross stages"。音声認識の都合で表記が確定できません）の情報は、本当の結論にたどり着くうえで不可欠で、「大きなアンロック（huge unlock）」だと述べています。
- 今後は、SRE Agent を自律運用のための運用担当として位置づけたいと考えています。かつては深夜に起きて対応していたものが、今は数分で済み、結果に驚いていると語っています。

## 6. デモ・手順

Shamir 氏は冒頭で「simulated demo（シミュレーションしたデモ）」と断っています。Dynatrace と Azure SRE Agent の連携が数クリックで設定できること、そして Dynatrace の持つ豊富なコンテキストを SRE Agent に渡して、統制された形で問題を修復できることを見せる、という趣旨です。

> 注意：録音は音声のみのため、画面上の細かな表示や入力値までは確認できません。以下は、語られた順に整理した内容です。

### 6.1 Dynatrace 側の設定（Dynatrace から SRE Agent を呼び出す）

1. Dynatrace で SRE Agent の設定画面をクリックします（音声では「cloud SRE agent」と聞こえます）。ここで、Dynatrace intelligence が起動する SRE Agent を設定します。
2. 「Open」ボタンをクリックし、読み込まれたあと、いくつかの項目を入力します。エージェント名、そのエージェントが何をするかの説明、ドロップダウンからの Azure SRE agent の選択、エンドポイントと認証情報です。
3. 保存します。残りは Dynatrace が処理し、SRE Agent との間に一方向の通信が確立されます。

### 6.2 SRE Agent 側の設定（SRE Agent から Dynatrace を理解させる）

1. sre.azure.com にアクセスします。ここが SRE Agent の体験（ポータル）です。
2. 「build and set up」へ進み、Dynatrace へのコネクタを作成します。接続には Dynatrace MCP を使い、MCP が公開するツールを通じて、Dynatrace が持つコンテキストや問題カード（problem cards）にアクセスします。
3. Dynatrace コネクタの入力項目（名前、Dynatrace 環境、認証ヘッダー）を埋め、接続をテストします。
4. 利用可能なツール一覧が表示されます。このデモでは 21 個のツールが見つかり、SRE Agent がオンデマンドで呼び出せるように、21 個すべてを有効にしています。
5. 続けて、調査結果のサマリーを送るための Outlook コネクタを作成します。コネクタの枠組みから Outlook を検索して選択し、いくつかの項目を入力します。この例ではユーザーアカウントでサインインしていますが、サービスアカウントでも、また agent identity を使って SRE Agent 側のエージェントアカウントから送ることもできると説明されました。
6. Outlook では「メール送信」ツールだけを有効にします。

> 補足：Shamir 氏は、データを再取り込み（re-ingest）せず、必要なときに Dynatrace のデータをオンデマンドで使うだけで、「車輪の再発明」はしていないと強調しています。

### 6.3 実際の動作結果

設定のあと、Dynatrace に戻り、Dynatrace のインテリジェントなシグナルによって作成された問題（problems）を確認する流れです。

1. 問題を開くと、SRE Agent が自動的に調査を終えていることが分かります。画面右に緑色のボックスが表示され、Azure SRE Agent の調査結果が Dynatrace の中で見られます。SRE Agent の画面に行かなくてもよい、というワークフロー内での完結が強調されました。
2. 調査結果にはルート原因、推奨事項、次のステップが含まれます。
3. 同じ内容は SRE Agent 側でも確認できます。Dynatrace の問題カードが SRE Agent 側で開かれ、AZ CLI コマンドや kubectl コマンドなど利用可能なツールで推論し、ルート原因、緩和策、次のステップに到達しています。
4. SRE Agent には「critique engine」があります。目的は偏りなく、ユーザーの入力と結果が一致しているかを検証することです。タイムライン、そしてエージェントがどう動いたか（うまくいった点・いかなかった点）の評価スコアが示されます。
5. この評価を使って、エージェントの知識を定期的に自動更新する「自己改善」を設定できます。知識コンテンツも自動で更新され、「エージェントが毎日良くなっていく」と説明されました。
6. 調査スレッドでは、ブラックボックスが無いことも示されました。すべてが監査され、Application Insights で確認できます。ツール呼び出しもモデル呼び出しも、渡されたパラメーターとともに追跡されます。
7. 調査が終わると、エージェントが自動的に管理者向けのメールを送信します。タイムラインとメトリクスのビジュアルが 1 か所にまとまっています。

Shamir 氏は、この一連の流れが「真夜中に起こされたり、今の作業を邪魔されたりすることなく」完了すると述べています。

### 6.4 ROI の確認

## 7. 注意点・発表者の気付き

1. **「動けるか」ではなく「動くべきか」。** 自律度（推奨だけか、実行までか）は利用者が設定します。人間を入れる場所も選べます。
2. **全アクションが監査対象。** ツール呼び出しやモデル呼び出しが、パラメーターごとに Application Insights で追跡できると説明されています。
3. **サービス全体の問題か、個別ユーザーへの影響か。** Commerzbank の事例のように、リクエスト単位だけでは誤解しやすく、ユーザーセッション単位に切り替えると見え方が変わる、という気付きが語られました。
4. **接続はデータの再取り込みではない。** Dynatrace のデータは、必要なときにオンデマンドで呼び出されます。
5. **今回のデモはシミュレーション。** Shamir 氏自身が「simulated demo」と述べています。

その他、前提条件、料金体系、対応範囲の制約などについて、発表では特に触れられていません。

## 9. まとめ
