## 5. 発表内容の詳細

### 5.1 Azure Storage のスケールと要件の進化

登壇者は、Azure Storage を世界最大級の分散クラウドストレージシステムの一つと位置づけ、次の規模を紹介しています。

- 現在 1 秒あたり 15 億トランザクション（1.5 billion transactions per second）を処理
- 700 兆を超えるオブジェクトを管理（more than 700 trillion objects）
- AI のトレーニングでは、OpenAI と Microsoft AI の双方が Azure Storage を使って複雑なモデルを学習
- 推論では、ChatGPT や Copilot にアップロードしたファイルや成果物は Blob Storage に保存される

ストレージには、ブロック、オブジェクト、ファイルの 3 つのカテゴリがあります。要件の進化は次のとおりで、前の要件が消えずに積み上がっています。

| ワークロード | 主な要件 |
| ---- | ---- |
| ミッションクリティカル（VM とディスク） | 高い耐障害性、サブミリ秒の低レイテンシ、多くの IOPS |
| クラウドネイティブ（例: 分析） | 複数の分析エンジンが多数のファイルとペタバイト級データに同時アクセスするための高スループットと大容量 |
| AI（トレーニング） | エクサバイト規模、非常に高いスループット |
| AI（推論） | 低レイテンシ、高スループット、多くのペタバイト |

会場への挙手アンケート（AI を拡大する際の最大のストレージ課題は何か。A: データ増加とコストの管理、B: 性能とレイテンシ要件への対応、あと C もあり）も行われました。C の内容は書き起こしからは分かりません。人数も集計されておらず、登壇者は「挙手の合計が合わない。想定していたとおりで、発表内容に沿っている」という趣旨を述べています。

### 5.2 ミッションクリティカル: Azure Block Storage

ブロックストレージは、VM や Kubernetes 上で動くミッションクリティカルなワークロード（例: 数百万 IOPS を低レイテンシで求められるデータベース）を支えます。ファミリーは 2 つあります。

- **Azure Disk**: Ultra Disk、Premium Disk、Standard Disk で構成され、選ぶディスクによって性能とコストのバランスを取ります。Premium V2 は IOPS、スループット、容量を独立して拡張できます。
- **Elastic SAN**: ボリューム間で容量と性能を共有でき、SAN に近いセマンティクスを提供します。

投資の柱は「耐障害性」と「運用のシンプルさ」です。耐障害性の改善として、次の発表がありました。

| 機能 | 内容 | 状態 |
| ---- | ---- | ---- |
| VMSS Flex 連携の Availability Set | 約 10 年前に導入された Availability Set（単一ゾーン内で障害ドメインを使って VM をデプロイし、VM 間のレイテンシを低く保つ）を VMSS Flex に統合。障害ドメインのプロビジョニングと管理を VMSS Flex が担う。SAP や Epic のデータベースのようなアプリケーションに重要と説明 | プレビュー（今回が初発表） |
| Immutable snapshot | 保持期間を定義し、その間はスナップショットの更新・削除ができない。機密データの復旧時にスナップショットが確実に残る | プレビュー |
| Multi-disk crash consistent snapshots | データとログが別ドライブにある SQL データベースのような構成で、複数ディスクにまたがるクラッシュ整合性を、アプリケーション層での調整や手作業なしで取得 | 発表では状態に触れていません（「今日発表する機能」の 2 つ目として紹介） |
| VM restore point 経由の instant access | スナップショット（復元ポイント）を作成するとすぐに復旧でき、スナップショットのレプリケーション完了を待つ必要がない。多数のスナップショットを取り、何度も復旧するワークロードに重要 | GA |

> 補足：Availability Set を「VMSS で強化したもの（on steroid）」と説明し、会場に「10 年前に導入したことを覚えているか」と挙手を求める場面がありました。

### 5.3 NAS/SAN データの Azure への移行と Azure Files

共同登壇者は、AI で企業データを使いたいという顧客は多いが、データはオンプレミスの NAS や SAN、他のクラウドに分散している、という課題から話を始めています。移行と活用の流れは次のとおりです。

1. **Azure Catalyst**（以前の Azure Migrate）で、オンプレミスの NAS 環境のサイズを見積もり、Azure Blobs、Azure Files、Azure NetApp Files のどこに置くべきかの推奨を得る。移行の前に着地先が分かる。
2. **Azure Storage Mover** で移行する。エージェントレスでスケールするように作られており、Google Cloud、Oracle、AWS、オンプレミスの S3 などから Azure Blobs や Azure Files へデータを持ち込める。
3. ファイル、SAN、分析データが混在する複雑な環境では、storage migration program のエコシステムであるパートナー移行プログラムを使える。ツールは追加コストなしで使え、自社ツールとパートナーツールを併用できる。
4. 一部のデータをオンプレミスに残すハイブリッドでは、**Azure File Sync** を Azure Files に接続し、クラウド階層化（cloud tiering）やハイブリッドアクセスを使う。

要点として「データを評価し、移行し、AI 向けの知識に変える」という流れが示されました。

Azure Files は、オンプレミスデータのリフト＆シフトとクラウドネイティブアプリケーション向けの、フルマネージドの NAS です。今回のアップデートは次のとおりです。

- **NFS on Azure Files HDD**（プレビュー）: 汎用的な Linux アプリケーションをより幅広く動かせるようにする。
- Windows 側では、SMB メタデータキャッシュにより、仮想デスクトップ環境のスケール向上とログインの高速化を進めている。
- BCDR（事業継続・災害復旧）: 直近 2 週間で多数の BCDR 機能を発表済み。同一リージョンまたは別リージョンに信頼できるコピーを持てる。
- AI との連携: Copilot、Work IQ、Foundry agent、AKS または ACA 上のエージェントから、Azure Files のデータをプラットフォームを移し替えずに直接マウントして使える。エージェントのセッションをまたぐ状態の管理もできる。

#### Azure Files の scale performance（SSD、プレビュー）

「Azure Files with scale performance」が SSD 上でプレビューになりました。想定ワークロードは、地震探査データの処理やゲノム解析パイプラインなどの HPC、AI 推論など、1 か所の大量データに多数のクライアントが並列にアクセスする用途です。

| 項目 | scale performance の上限（共有あたり） |
| ---- | ---- |
| 容量 | 最大 1 PB（従来の 4 倍） |
| IOPS | 最大 100 万（従来の 10 倍） |
| スループット | 最大 20 GiB/s |

「これは皆さんがすでに知っている Azure Files」であり、アプリケーションは従来どおりのまま、上限だけが広がると説明されています。これらの上限に到達するために、アーキテクチャを次のように変更しました。

1. **Name resolver を導入**: 各ファイルの場所を記憶する。NFS、REST、今後は SMB のいずれでアクセスしても、探索に時間をかけずに目的のファイルに直接リクエストが届く。
2. **スケールアウトした名前空間**: 名前、フォルダー、一覧情報などのメタデータをファイル内容と分離し、複数のパーティションに分散させる。一覧取得と実データの読み書きがバックエンドで競合しなくなり、今後もパーティションを追加して拡張していく。

デモについては 6.2 で説明します。

### 5.4 Azure NetApp Files

Azure NetApp Files（ANF）は、NetApp のネイティブなエンタープライズ機能を Azure に提供しつつ、クラウドで最高の性能が出るよう最適化されたサービスです。

- EDA（電子設計自動化）を例に、公開ベンチマークで、他のクラウドストレージだけでなく、オンプレミスの専用システムに対しても先行する性能を示したと説明されています。
- breakthrough mode を使った large volumes では、1 ボリュームあたり最大「80,000 GB bytes per second」のスループットが得られると説明されています（単位と数値は音声認識の都合で確定できません）。これには 6 つのストレージエンドポイントと専用容量を使います。最新の EDA ベンチマークでは、5,000 を超える完了ジョブセットで、従来比 1.8 倍の性能になりました。
- cool access を使うと、1 ボリュームで 7.2 PB までスケールし、データを冷却して低コスト化できます。
- オンプレミスの ONTAP システムからの移行には **ANF Migration Assist** を使います。増分コピーによって、ダウンタイムを最小限にしつつ効率的に移行できます。

### 5.5 クラウドネイティブ: 次世代 Azure Elastic SAN

次は SAN とクラウドネイティブのワークロードです。計算リソースを増やしたとき（処理ジョブの作業者を 2 倍にする、データベースへのリクエストが増える、など）に、レイテンシを低く保ちたいという前提で説明されました。

Elastic SAN は 2 年前に、SAN モデルをクラウドに初めて持ち込み、ミッドティア向けにコスト効率と管理のしやすさを提供するものとして発表されました。今回、**次世代 Elastic SAN** が発表されました。主な特徴は次のとおりです。

- ミッションクリティカル級の性能を提供する 2 つのティアを追加。
- Azure Block Storage で以前紹介した direct drive 技術の上に構築され、エンドツーエンドで最適化された性能とサブミリ秒の低レイテンシを提供。

| ティア | 接続方法 | 上限 | 用途の例 |
| ---- | ---- | ---- | ---- |
| Business critical | VM へのダイレクトアタッチ | 最大 40 万 IOPS、10 GB/s、サブミリ秒のレイテンシ | SAP HANA、Epic などのミッションクリティカル |
| General purpose | ダイレクトアタッチ、またはベアメタル向けの iSCSI | 最大 8 万 IOPS、10 GB/s、サブミリ秒のレイテンシ | データベース、エージェントの永続ストア |

次世代 Elastic SAN は **シンプロビジョニング** にも対応しました。必要な物理容量を最初に全量確保する必要がなく、論理ボリュームは最大 5 倍まで増やせます。将来の成長に備えて「今必要な分」だけをプロビジョニングし、自動スケール（auto scale）で伸ばします。

1 つの SAN 全体では、最大 1 PB、400 万 IOPS、集約で 160 GB/s のスループットに達します。ロードマップとして、高速コピーのための thin clones と、VM のアプリケーション整合性バックアップ／リストアのための VM restore points が挙げられました。

会場にも「将来 150 TB に増える見込みで、今は 30 TB 近く使っている場合、いくらプロビジョニングするか」というクイズが出され、答えは 30 TB（余裕を少し持たせる）、将来は 5 倍の 150 TB まで自動で拡張される、という説明でした。

具体例として、Epic、データベース、エージェントストア、アプリケーションサーバーなど 5 つのワークロードが 1 つの Elastic SAN で動く構成が示されました。

- 容量: 論理ボリューム合計は 150 TB、実使用は約 25 TB。バッファを足して約 30 TB をプロビジョニングし、支払うのもその分だけ。将来の成長に向けた物理容量のプロビジョニングが **80% 少なくなる** と説明されています。
- 性能: 5 つのワークロードのピークを足し合わせると約 60 万 IOPS になるが、通常は同時にピークを迎えない。Epic や SAP HANA は予約した IOPS とスループットを持つ Business critical ティアに置き、General purpose のアプリケーションは SAN 内の残りの性能を使ってスケールする。この例では約 50 万 IOPS をプロビジョニングし、必要に応じて自動スケールさせる。

デモは 6.3 に記載します。

### 5.6 アナリティクス: ADLS、Fabric、Azure Databricks

登壇者は、データの使い方が急速に変わっており、複数の分析エンジンを使いつつデータを何度もコピーしたくない、という状況を前提に、**Azure Storage を、すべてのエンジンの下にある永続的なデータ基盤にする** ことを目標に挙げています。

Azure Data Lake Storage（ADLS）は、データ分析のために作られた Microsoft のクラウドストレージで、Microsoft Fabric、Azure Databricks、Spark と統合されています。焦点は「性能、オープン性、AI」の 3 点です。性能では vectored reads、オープン性ではどのコンピュートエンジンを使ってもデータが開かれた状態にあること、AI では同じデータを Microsoft Foundry や Azure Databricks 上のアプリケーションやエージェントから使えることです。「データは永続的で、コンピュートは選択できる」というのが要点です。

#### Vectored reads

Vectored reads は、コードを変更せずに ADLS 上の Spark 分析を高速にする機能です。Spark は同じ Parquet ファイルの多数の断片を読み、断片ごとにストレージへのネットワーク往復が発生します。これは数千のファイルや多数のジョブに及ぶと積み上がります。Vectored reads は ABFS ドライバーの改善により、読み取りを検証し、近くにある読み取りを結合して並列に取得します。バックエンドに届くリクエストが減ります。Microsoft のテストでは次の結果でした。

- クエリが最大 12 倍高速
- 読み取り呼び出しが 22% 減少
- P90 レイテンシが最大 41% 低下

結果はワークロードによって異なります。コードの変更は不要ですが、**利用するには有効化が必要** で、登壇者は自分の環境で試すよう呼びかけています。

#### Microsoft Fabric と OneLake

Fabric は、データの取り込み、変換、リアルタイムストリーム処理、分析、レポートまでを扱う統合 SaaS 分析プラットフォームで、OneLake の上に構築されています。OneLake は ADLS の上に作られています。ADLS が規模、耐久性、セキュリティを提供し、OneLake が単一の名前空間、カタログ、セキュリティモデルを加えます。可用性ゾーンやペアリージョンへのジオレプリケーションによる災害復旧といった耐障害性は Azure Storage に由来します。SQL、Spark ノートブック、Power BI のどこからアクセスしても、同じセキュリティモデルでデータに接続できます。

#### Azure Databricks（ゲスト: David Meyer 氏）

David Meyer 氏（Azure Databricks の SVP of product として紹介）は、Azure Databricks が 2018 年から提供されている製品であり、ここまでに出た内容の多くを抽象化して扱っている、と述べています。

- **レイクハウス**: 2019 年にレイクハウスアーキテクチャを語り始めた当時は、業界から「アンチパターンの親玉」と呼ばれたが、今ではすべてのウェアハウスがレイクハウスになっている、という話です。すべてのデータを低コストストレージ（ここでは ADLS）に置き、ウェアハウス用途の処理をデータを移さずに実行します。Delta や Iceberg といったテーブルフォーマットが基盤になっています。
- **スケール**: Azure のお客様のレイクハウスでの処理のために、1 日に約 3,500 万台の VM を起動していると述べています。ADLS には 1 日に 1 兆を超えるリクエストが届き、1 日に約 50 PB が書き込まれ、読み取りはそれ以上だと説明しています。
- **Lakebase**: 今年から語り始めた Postgres をレイク（ADLS）に静止データとして置く仕組みです。コンピュートとストレージを完全に分離します。通常のデータベースで本番を複製するには数十分から数時間かかりますが、Lakebase では瞬時かつ無料（ディスク上のポインターにすぎない）で、チェックポイントの復元や新規データベースの作成は 1 秒未満、巨大なデータベースを作る場合にもプロビジョニングすべきストレージはなく、データベースの成長に合わせて拡張します。コードのようにデータベースをブランチできる「この種で唯一のブランチ可能なデータベース」と説明され、現在、お客様の環境で GA とのことです。
- **AI**: Databricks 上の多数のエージェントや AI は、Copilot や Foundry でも動作し、すべてレイクに存在します。Azure Databricks 全体が「レイクのシステム」であり、コンピュートは伸縮し、データはレイクに置かれる、という構造です。
- **構成要素**: Lakehouse はレイクにデータを置いたウェアハウスで、使っていないときはストレージ料金だけを払います。データは自分の ADLS にあり、標準ベースで、完全に制御できます。Lakeflow は大規模な ETL パイプラインの処理基盤です。Genie、Genie Agents、AgentBricks などの検索機能もレイク上で動きます。中心にある **Unity Catalog** が、データと AI のすべてを、RBAC ポリシー、属性ベースのアクセス制御、リネージなどで統制します。構造化データ（Delta、Iceberg など）、非構造化データ（ファイル、動画など）、データベースのデータ（Postgres ファイル）、AI 検索のインデックスデータまで、すべて ADLS 上で管理されます。
- **ディスク／ブロックストレージの利用**: 大規模クラスターで処理するデータのシャッフルデータがメモリに収まらない場合にディスクに置きます。また AI 向けの GPU クラスターでは、GPU ノードのローカルストレージをコンテキストのキャッシュに使い、トークン消費を抑えます。
- **Fabric / OneLake との連携**: Unity Catalog で整理した Databricks のものは Fabric のエンジンにゼロコピーで提供でき、逆に Fabric のものも Delta と Iceberg のインターフェース経由で Unity Catalog にゼロコピーで提供できます。今年は、Databricks の managed catalog を OneLake にネイティブに保存するオプションも提供されました。OneLake か ADLS のどちらに保存しても使い方は変わらず、Unity Catalog で統制され、下流の Fabric ツール向けに OneLake へミラーされます。
- **Azure Core との共同開発**: 2018 年に Databricks を Azure に移したとき、多くのお客様が急速にスケールし、Azure Core の基盤プリミティブのスケーラビリティ上限に何度も達したと振り返っています。共同で解決策を作り、直近 1 年の Azure Core の基礎的な強化（例: アカウントあたりのバケット数、サーバー側コピーによるエッジネットワーク経由の I/O 回避）により、Azure Databricks が世界最大級の Azure のお客様のデータと AI を支えられるようになった、と述べています。

> 補足：トランスクリプトでは、ADLS へのリクエスト数について「1 日に 1 兆トランザクション」と「1 日に 1 兆を超えるリクエスト」の 2 通りの言い方が出てきます。ここでは後者に合わせています。

### 5.7 AI: Azure Managed Lustre と Blob Storage

最後のセクションは、AI 向けのストレージ投資と発表です。

#### Azure Managed Lustre

Linux の並列ファイルシステムで POSIX 準拠を必要とするお客様向けで、AI と HPC のトレーニングに適しています。

- 単一の名前空間のスケールを 5 倍に拡大。
- **seamless expansion**（アプリケーションを動かしたまま容量とスループットを拡張）を GA として発表。
- AKS とシームレスに統合され、AKS 経由で AMLFS（Azure Managed Lustre）をプロビジョニングでき、Azure CLI のコマンドでも有効化できる。

#### Azure Blob Storage: AI の基盤として

Azure Blob Storage を AI の基盤（substrate）と位置づけ、3 つの発表がありました。

1. **Accelerated listing（製品名 Photon）**: AI/ML のワークロードは数百万オブジェクトを 1 秒で列挙する必要があり、Apache Arrow を使って数百万の Blob を 1 秒以内に一覧できるようにする。
2. **Session-based authentication**: AI エージェントが Blob にアクセスするには認証が必要で、1 回ごとにラウンドトリップが発生する。指定した時間、コンテナーに対するセッションベースの認証を作成し、その期間は再認証が不要になる。Blob アクセスが高速化される。
3. **Blob over RDMA**: GPU から Blob への RDMA による直接アクセスを提供するクラウドは自社のみ、と述べています。従来の経路では CPU がクリティカルパスに入り、Blob から GPU メモリやホスト RAM へバイト単位でコピーする必要があり、CPU 使用率とレイテンシが高くなります。Blob over RDMA では CPU がクリティカルパスから外れ、NIC 上で RDMA がオフロードされ、Blob から GPU メモリ、ホスト RAM、NVMe に直接コピーされます。CPU コアが空いて他の処理に使えるうえ、**レイテンシは 88% 低下** します。登壇者は PM チームが作ったこのスライドを「AI に与えればコードを生成してくれるような良いスライド」と紹介していました。

加えて **Azure Blob Storage Turbo Tier**（プレビュー、発表中にリンクが示されました）が発表されました。AI ワークロードには低レイテンシと非常に高いスループットが必要で、同時にペタバイト級のデータを扱います。Turbo Tier では、ホットな書き込みが SSD 層に入るので高スループットと低レイテンシが得られ、同じストレージアカウント・同じ名前空間内で、ライフサイクル管理を使って冷めたデータをコールドな Blob ストレージに階層化してコストを下げられます。同一ストレージアカウントの単一名前空間でこれを実現できるクラウドは自社のみ、と述べています。

### 5.8 パートナーと Blob access point

登壇者は、Azure Storage の現在の姿はパートナーの支えなしにはありえないとして、戦略パートナーの一覧スライドを紹介し、パートナーが GA として発表するイノベーションにも触れています（個別のパートナー名や機能の内容は、トランスクリプトからは聞き取れません）。

Microsoft 側の発表として **Blob access point** が挙げられました。パートナーのオンプレミスデータを、データをビット単位でコピーすることなく AI ワークロードで使えるようにする機能です。データはオンプレミスに置いたまま、Microsoft の 1P ワークロードが慣れ親しんだ Blob API 経由でアクセスできます。

登壇者は最後に、ストレージのセッションを 14 年間担当してきたが、今回の Ignite はブロック、ファイル、オブジェクトとパートナーエコシステムの全体を通して最も強いものの一つだと述べ、Redmond で多くのメンバーが取り組んでいることに謝意を示しました。

## 6. デモ・手順

このセッションでは、トランスクリプト上、次の 3 つのデモが行われています。録音は音声のみのため、画面の細部（ボタン名や入力値など）は確認できません。以下は語られた範囲に限ります。なお、Blob 関連のデモは、時間の都合で省略されました。

### 6.1 インスタントアクセスによる復元（Azure Disk、Epic を想定した環境）

発表では、データベースが複数のディスクにまたがるミッションクリティカルなアプリケーションで、スケール、分析、復旧のために環境のコピーを作ると、従来は数時間かかることがあると説明されています。昨年は instant access snapshots で、スナップショットのデータが標準ストレージからレプリケーションされるのを待たずにディスクを作成して使える点を紹介しており、今年はこれが複数ディスクに拡張された、という位置づけです。

1. 環境は、Ultra Disk を持つ E372SV7 の VM（シミュレートした電子医療記録）と、コピー先となる E192SV7 の VM（いずれも音声認識の都合で表記が確定できません）。
2. VM に対して restore point collection を作成し、instant access を有効にする。
3. restore point では、アプリケーション認識（application aware）のスクリプトでデータベースを静止させ、未書き込みを flush してからキャプチャできる。これにより、アプリケーション整合性のある時点のコピーになる。
4. アプリケーションを構成するディスクだけを選択できる。関係のないストレージのコピーを避けつつ、データ、ログ、構成といった必要なものを保つ。
5. restore point を作成したら、すぐにそこから新しいディスクを作成できる。ポータルで見せているが、自動化ツールや CLI でも同じことができる。
6. 新しいディスクをコピー先の VM にアタッチし、同じシミュレートデータベースを起動して、iostat で性能を確認する。
7. 「R08」と「W08」の列（音声認識の都合で表記が確定できません）で、コピーした環境がすぐに使え、ディスクがバックグラウンドでハイドレーションされる間も本番相当の性能が出ることを示した。
8. ハイドレーション完了後、ディスクは通常の Ultra Disk の性能・レイテンシのプロファイルに戻る。

登壇者は、昨年の単一ディスクのスナップショットから、今年は 1 台の VM に属する複数ディスクのアプリケーション整合性スナップショットへ進化した、と整理し、医療機関に限らず他のミッションクリティカルなアプリケーションにも有効と述べています。

### 6.2 Azure Files scale performance による地震探査処理

1. 各ファイル共有が 1 PB、100 万 IOPS、20 GiB/s まで対応することを確認する。スループット重視のワークロードでは、同じスループットで他のクラウドと比べ月額コストが約 5 分の 1 になる、と説明されている。
2. オンプレミスからの移行は、Azure Catalyst（Azure Migrate）による評価から始める。地震探査処理を支える、4 つの大規模 NFS 共有を持つストレージアレイの例が示され、共有は 500 TB 以上ある。
3. そのうち 1 つの共有を確認すると、594 TB のデータがあり、IOPS とスループットの要件が大きい。この結果を踏まえ、Azure Files SSD を移行先にできるかを評価する。
4. 実際のワークロードとして、地球科学者がよく使う NV 系の GPU アクセラレーテッド VM の 10 台クラスターを使う。高帯域ネットワークと GPU 対応の可視化、単一の NFS Azure file share への並列アクセスで、要求の厳しい科学ワークロードを実行する。
5. シミュレートした 100 TB のサーベイを、10 台の Azure VM で処理する。同じジョブ、同じ VM を、左側は従来の Azure Files、右側は scale performance 付きの Azure Files で実行する。
6. scale performance 側は先に処理が終わる。登壇者は、従来の Azure Files SSD のおよそ 2 倍速いと述べ、このシミュレーションではスループットが 2 倍になった分、時間が半分になったと説明している。
7. 処理完了後、科学者は 3D の解釈（層や断層の確認）にアクセスできる。

### 6.3 次世代 Elastic SAN（プレビューでの体験）

1. プレビューでは、Azure Elastic SAN の SKU を選び、次世代では容量と性能を独立してプロビジョニングする。
2. 例として、約 40 万 IOPS、4,000 MB/s のスループット、20 TiB の容量を指定する。これがこの SAN の最大上限になる。
3. 環境には、General purpose ボリューム上で動く基幹業務データベースと、Business critical ボリューム上で動く決済処理のミッションクリティカルな SQL Server がある。
4. Business critical は低いサブミリ秒レイテンシを提供し、IOPS とスループットを予約することで、ノイジーネイバーの競合からミッションクリティカルなワークロードを守れる。このワークロードには 8 万 IOPS と 640 MB/s を予約した。
5. 負荷は HammerDB（6,000 ウェアハウス、32 仮想ユーザー）と iostat で生成する。
6. ワークロードは SAN を共有する。General purpose のボリュームは一緒に上昇するが、Business critical ボリューム用に予約された 8 万 IOPS を超えて使うことはない（トランスクリプトではここで SAN の上限が「40,000 IOPS」と語られていますが、手順 2 の 40 万 IOPS との関係は音声認識の都合で確定できません）。
7. Business critical 側の SQL データベースは、SAN に余力があれば予約の 8 万 IOPS を大きく超え、20 万 IOPS 超まで伸びた。
8. 結論として、SAN に余力があるとき Business critical は予約分を大きく超えて使え、General purpose ボリュームは利用できる分を使いつつ、ピークの時間が異なるため SAN のプロビジョニング済み性能を必要に応じて使う、と説明されている。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **復旧・コピーの待ち時間の短縮**: instant access により、レプリケーション完了を待たずに復旧でき、複数ディスクでもアプリケーション整合性のあるコピーをすぐ使えます。
- **データ移行の見通し**: Azure Catalyst で着地先を事前に把握でき、移行ツールは追加コストなしで使えると説明されています。
- **HPC・AI の性能向上**: Azure Files の scale performance でデモの地震探査処理が従来の約 2 倍の速さで完了し、スループット重視では他のクラウド比で月額コストが約 5 分の 1 とされています。
- **コスト最適化**: 次世代 Elastic SAN のシンプロビジョニングで、将来の成長分の物理容量のプロビジョニングが 80% 少なくなります。Blob Turbo Tier ではライフサイクル管理でコールドデータを低コストの階層に移せます。
- **分析の高速化**: Vectored reads でコード変更なしにクエリが最大 12 倍、読み取り呼び出しが 22% 減少、P90 レイテンシが最大 41% 低下。
- **AI 向けの低レイテンシ**: Blob over RDMA でレイテンシが 88% 低下し、CPU を他の処理に回せます。
- **データの再利用**: Azure Files のデータを Copilot や Foundry agent、AKS/ACA のエージェントから直接使えるため、AI のためにプラットフォームを移す必要がありません。

## 9. まとめ

発表の軸は、ストレージを AI の「メモリ」と見なし、ミッションクリティカル、クラウドネイティブ、AI の 3 つのワークロード向けに投資を積み上げているという点です。ブロックでは、VM restore point の instant access（GA）や immutable snapshot などの耐障害性の強化、ファイルでは 1 PB・100 万 IOPS・20 GiB/s の scale performance（プレビュー）と Azure NetApp Files の大規模化、SAN では 2 つのティアとシンプロビジョニングを備えた次世代 Elastic SAN が紹介されました。分析では ADLS の vectored reads と、Azure Databricks（Lakebase を含む）との連携、AI では Azure Managed Lustre、Blob の accelerated listing、session-based authentication、Blob over RDMA、Turbo Tier、Blob access point が発表されています。
