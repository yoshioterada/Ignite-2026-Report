# BRK422 Run open-weight models, post-training, and agents on AKS

## 1. はじめに

このセッションは、Azure Kubernetes Service（AKS）の上で AI ワークロードを動かすための 45 分のブレークアウトです。扱うのは、オープンウェイトモデルのサービング、独自データでの追加学習（ポストトレーニング）、そしてエージェントの安全な実行という 3 つです。Microsoft の 2 名が AKS 側の機能を紹介し、法務・専門業務向けの AI 製品を作る Harvey AI のインフラ責任者が、AKS 上のエージェント用サンドボックス基盤の実例を話します。

- AKS AI Manager（パブリックプレビュー）で、Qwen をカタログから AKS にデプロイする流れ

- Harvey AI がエージェントのサンドボックスで求めた要件と、その実現方法
- Agent Sandbox、Pod のスナップショットと復元、Kata の改善、Agent Substrate といった、エージェント向け機能の現状と数値

| ワークロード | 内容 | 主な関心事 |

## 4. 発表者が伝えたいメッセージ

AKS の上で、**サービング、再トレーニング、エージェントの実行という「AI の学習ループ」を、Kubernetes のツールとオープンソースのまま自前で組める**、というのが共通の主張です。理由として Lachie 氏は、次の業界のトレンドを挙げています。

- モデルの能力は、フロンティアモデルが出るたびに安くなり、広く行き渡っている。フロンティアモデルとオープンウェイトモデルの差も縮まり、オープンウェイトでも多くの能力を持つ。
- オープンウェイトモデルは自分のテナントで動かせるため、コストやトークン消費を管理でき、すでに用意したインフラを活用でき、データとクラウド費用を自分の手元に置ける。
- 再トレーニングによって、自社ドメインの知識を持たせられる。例えば法律事務所なら、法務文書のコーパスを使って、ドメイン固有の質問に答えるエージェントを作れる。

自前で持ちたい動機として、データの所有と居住性（フロンティアモデルにデータを渡したくない）、トークン費用の管理、ドメイン知識による精度向上、どこでも動かせること（オンプレミスでもクラウドでも）が挙げられています。使うツールはオープンソースで公開されており、AKS はそれをマネージドな機能として提供する、という位置づけです。

## 5. 発表内容の詳細

### 5.1 AKS AI Manager：カタログからモデルをデプロイ

Ignite でパブリックプレビューとして発表された新機能です。登壇者の説明では、オープンウェイトモデルのカタログから 1 クリックでデプロイでき、「ベストオブブリード」の技術スタックで保護されたエンドポイントができ、本番投入までが速くなります。プレイグラウンドで試すこともでき、Azure のセキュリティとガバナンスの制御でエンドポイントを管理できます。デモは 6.1 を参照してください。

### 5.2 巨大なモデルの読み込みを速くするキャッシュ

オープンウェイトモデルは非常に大きく、テラバイト、時にはペタバイト規模になるとのことです。そこで、Azure Storage の上に作った「distributed accelerator for cloud storage」を AKS に提供しています（略称は書き起こしで「a DAX」「DACs」と揺れており、音声認識の都合で表記が確定できません）。クラスターの各ノードにローカルキャッシュを持たせ、モデルのレイヤーを参加ノードに分散することで、イメージやモデルの取得待ちを減らし、プル時間と起動時間を短くします。

### 5.3 GPU のコスト最適化

GPU は高価なので、プロビジョニング中の時間を使い切れるようにしています。紹介された機能は次のとおりです。

- **マネージド GPU ノードプール**：GA。ドライバーのライフサイクルなどを AKS が管理するので、ドライバーのバージョンや更新を気にせずワークロードを載せられる。
- **混在 MIG パーティション**：ノードプール内に異なる構成を混在させ、必要な GPU を必要なときに用意できる。
- **Azure の最新ハードウェア**：Grace Blackwell GPU、NVLink、RDMA ネットワーク。
- **マネージド DRA net**：GPU ワークロードで RDMA を使い、最大のネットワーク性能を出す。

### 5.4 ポストトレーニング用の機能

Qwen のようなモデルは、そのままでは自社のビジネスの文脈を知りません。そこで再トレーニングのために、次の機能が紹介されました。

**KubeRay extension**：KubeRay は、トレーニング、データ、サービングを含む、分散 ML / AI のためのプラットフォームです。AKS のマネージド拡張として提供され、ワンクリックで入ります。標準でサポートするリソースは 4 種類と説明され、聞き取れたのは Ray Job（ジョブのスケジュール）、Service（推論用エンドポイントの構築）、Cron Job（定期実行）です。

**マネージド Kueue extension（パブリックプレビュー）**：Kueue は、スケジューラ兼キューイングの仕組みです。複数のチームが GPU のプールを共有するとき、1 つのクォータにまとめ、チームごとにジョブを出し、優先度順に GPU を使うようにできます。KubeRay と同様にライフサイクルは AKS が管理します。Kueue 用のプラグインも提供され、Headlamp でスケジューリングの状況とリソース使用率を可視化できます。

**TauGrid**：Kueue と KubeRay による分散トレーニングを、オープンソース化して導入したものです。スケジューリングの Kueue と、分散フレームワークの KubeRay を結びつけ、ノードの GPU メトリクスも統合して、複数の AKS クラスターにまたがる再トレーニングジョブを 1 画面で扱えます。AKS とやり取りする CLI が付属し、ジョブのスケジュール、監視、表示ができます。CLI、Kueue、KubeRay、GPU の健全性を 1 つのマネージド拡張にまとめ、「バッテリー込み」でポストトレーニングを行える、という説明です。

> 注意：「TauGrid」という綴りは、書き起こしで「TauGrid」「Tau Grid」「TAO」などと揺れており、音声認識の都合で表記が確定できません。

**Anyscale on Azure**：10 月から GA のパートナー製品です。KubeRay と Ray プラットフォームを、AKS 上で企業向けに使えるようにするもので、セキュリティ、ID プラットフォームとの統合、AKS クラスターをまたぐマルチテナンシーを備えます。データサイエンティスト向けのワークスペース、ポータルからのワンクリックの統合、Anyscale と Azure での ID のミラーリングも提供します。ユーザーのドメイン、テナント、クラスター内で動き、データが環境の外に出ることはない、と説明されています。

### 5.5 Harvey AI の事例：エージェントのサンドボックス基盤

Harvey は、法務・専門業務向けの AI ネイティブなソリューションを作る会社です。弁護士や専門サービスのチームが、調査、起案、レビュー、データや文書の分析に使います。コンピュート、ネットワーク、ストレージの全体が、Azure のマネージドサービスで動いています。

コンピュート面では、AKS 上に次の 3 つの用途があります。

1. 主力製品の **Harvey Assistant**（弁護士向けの ChatGPT のような製品）
2. Temporal を使った**ワークフローマネージャー**（耐久性のあるオーケストレーション）
3. **エージェントのサンドボックス**。インフラチームが数か月かけて作った基盤で、Harvey の各製品が分離された環境でサンドボックスのエージェントを動かせる。

#### サンドボックスに求めた要件

| 要件 | 理由 |
| --- | --- |
| 分離 | マルチテナントで多数のユーザーがインフラを共有するため、エージェント同士が干渉してはいけない |
| 高速な起動 | Assistant は対話型で、ユーザーが画面の前で待っている |
| 使い捨て | 会話の「ターン」ごとにサンドボックスを作り、ターンが終わったら削除する。状態をシステムに残さない |
| 弾力性 | 顧客の大半が企業で、平日 9 時から 5 時に負荷が集中し、週末や休日は少ない。急増に対応しつつ、低負荷時のコストを抑えたい |
| データガバナンスとセキュリティ | 法務領域のため重要 |
| 可観測性 | AI がすべて自動化するので、エージェントの行動を追跡できるようにし、問題があれば修正できるようにしたい |

#### AKS での実現方法

- **分離**：専用のノードプール、Kata Containers、ネットワークの egress は可能な限り意図的に無効化し、例外は 1 つだけ（その内容は後のスライドで説明するとのことでした）。
- **高速起動**：事前に作ったサンドボックスのウォームプールを維持する。エージェントが会話を投入するとサンドボックスを渡し、ターンが終わると回収する。サンドボックスが払い出されるたびに 1 つ補充する。
- **弾力性**：オートスケーリング。負荷があるときは最大容量までスケールアップし、無いときはスケールダウンする。
- **ライフサイクル管理**：宣言的なサンドボックスリソースを持つ Kubernetes コントローラーを多用する。
- **Azure のその他の機能**：ユーザーデータは Blob Storage、さらに Azure Container Registry、ID 管理など。
- **オープンソース**：Kubernetes の Agent Sandbox プロジェクトの上に基盤を構築しており、その機能を自動的に取り込める。

#### 1 つのタスクの流れ

クライアントは Harvey の Web サービスで、Office プラグインもあります。リクエストは、まずメインの Harvey Assistant エージェントに入ります。サンドボックスを扱うサービスの中では、サンドボックスコントローラーがオーケストレーションを行い、サンドボックスルーターが、分離されたサンドボックスのコンテナーへ呼び出しを振り分けます。モデル（フロンティアモデルやオープンウェイトモデルなど多数）の呼び出しは、分離を保つため**サンドボックスの外**で処理します。データは Blob Storage に置き、サンドボックスからデータを保存できる唯一の経路として、アクセスを厳しく制御する **Blob ストレージプロキシ**を構築しています。

1 つの会話ターンの処理は、次の順です。

1. 以前の状態があれば、最後のスナップショットから復元する（連続したターンで会話を切れ目なく続けるため）。
2. ユーザーがアップロードしたファイルを入力としてマウントする。
3. エージェントを動かし、コードとツールを実行する。
4. 最後にスナップショットを取る。会話のターン間でデータの耐久性を保つため。

セキュリティについては、強い分離、制限したネットワーク egress、エージェントへの最小権限の付与、オーケストレーション層とサンドボックス実行の完全な分離を、各層に組み込んでいると説明されています。

#### Harvey の学び

1. **ハーネスとサンドボックスを切り離す**。裏側のプラットフォームを入れ替える柔軟性が得られる。
2. **サンドボックスの状態は使い捨てとし、トランスクリプトとファイルは耐久性を持たせる**。
3. **本番展開は慎重に、段階的に行う**。顧客は約 60 か国、数千社にのぼる。
4. エージェントのワークロードは新しいもので、プラットフォームも使い方も変わり続ける。次のバージョンも検討している。

### 5.6 エージェントの実行基盤：AKS 側の機能（Jorge 氏のパート）

Harvey の話を受け、Jorge 氏は、エージェントが信頼できないコードを安全に実行すること、状態を切り離すこと、アイドルとバーストの両方に対応することが要件になると整理しました。AKS と Azure の構成は次のとおりです。

**ハーネスとクライアントの分離**：ハーネスとクライアントは疎結合に考えるべきで、「bring your own harness」と呼ぶ考え方をとっています。どんなハーネス、フレームワーク、SDK でも使えるよう、モジュール化されています。

**ルーティング層**：agent gateway と、新しく発表された **agent grid** 製品で、エージェントのトラフィックをルーティングし、ネットワークレベルで保護します。従来型の FQDN フィルタリングで、エージェントからの egress を一括ブロックする（Harvey の例のように）ことも、ネットワークやクラスターのレベルだけでなく、エージェント単位で設定することもできます。MCP を使う場合は、特定の MCP サーバーを許可またはブロックでき、agent grid と agent gateway はこれを理解します。

> 注意：登壇者は、エージェントでは**「明示的に許可したものだけを許可し、他はすべて拒否する」方式を推奨**すると述べています。「この 1 つ以外はすべて許可」という逆の方式にすると、最近のニュースで見かけるような問題につながるという趣旨です。

**サンドボックス層の拡張**：

- **Agent Sandbox**：クラスター拡張としてパブリックプレビュー。AKS が管理するので、Helm Chart で自分でインストールする必要がない（Harvey は始めた時期が早く、オープンソースのプロジェクトを自分で入れていた）。
- **Pod snapshot and restore 拡張**：別の拡張として提供。2 つに分けた理由はモジュール性で、スナップショットと復元を他のサンドボックスと組み合わせ、Agent Sandbox を別のものと組み合わせることもできるようにするため。Agent Substrate、Open Sandbox などの他のプロジェクトにも触れています。
- **マイクロ VM / サンドボックス層**：Kata、または Azure Container Instances（ACI）。AKS は VM ノードのほかに、インフラが見えないサーバーレスの「仮想ノード」として ACI も使えます。同じサンドボックス機能が ACI でも使え、スナップショットの保存先には Azure Storage を使えます。

**Kata V2 ランタイムクラスの改善**（下の層から順に説明）：

| 項目 | 内容 |
| --- | --- |
| 再設計 | Pod サンドボックス（Kata）を Rust で作り直した |
| Pod のメモリオーバーヘッド | 600 MB から 32 MB へ。10 倍超の削減 |
| 起動遅延 | 42% 低下（マイクロ VM の起動が 42% 速い） |
| VM テンプレート | あらかじめ初期化したテンプレートから新しいサンドボックスを複製する。ゼロから起動しない |
| Azure Disk | これまでマイクロ VM では使えなかったが、使えるようになり、Azure Disk の性能を活かせる。Virtio blocks で安全にサンドボックスへ見せる |

**Agent Sandbox の API**：Pod サンドボックスは分離は提供しても速度が足りない、という課題に対し、ウォームプールの API を提供します。VM テンプレートとスタンバイの UVM（ユーティリティ VM）で、エージェントが来たらすぐ使えます。エージェントは 1 つずつでなく大量に来るため、重要だという説明です。pause、resume、ストレージの保持といったプリミティブもあります。数値は次のとおりです。

- ウォームプールからの新規サンドボックス：**77 ミリ秒**
- ウォームプールが無い場合の、ゼロからの作成：**2 秒未満**

**スナップショットと復元**：リスクのある作業の前にスナップショットを取る、週末にコンピュートを遊ばせないために保存して後で復元する、といった用途があります。拡張は提供済みで、Kata のノードでも ACI でも使え、pause、snapshot、メモリからの restore ができます。

**Agent Substrate**：Agent Sandbox に加えて取り組んでいるもので、AKS に自分でインストールして今日から使えます（リポジトリは「github.com slash azure slash substrate AKS」と聞こえ、正確な URL は書き起こしからは確定できません）。コントロールプレーンの性能が課題でした。何百、何千というサンドボックスが毎秒来るとき、1 件ごとの処理が重くなるためで、この調整を Harvey と協力して進めたと述べています。数値として、**1 クラスターで 28,000 のエージェント、エージェントの再開（resume）までの中央値が 160 ミリ秒**が示されました。

### 5.7 どこでも動かせること

登壇者は、これらのコンポーネントはどこでも動くと述べています。AKS には **flex nodes**（Satya 氏が Tuesday に言及したものだと触れています）があり、任意のハードウェアを AKS クラスターに接続できます。モデルのデプロイは AI Manager 経由でも直接でも flex nodes を対象にでき、エージェント拡張もそこで動きます。Kata によるサンドボックス作成はエッジのノードでも可能です。クラスター全体には **AKS bare metal** があり、同じコンポーネントをエッジで動かせます。

### 5.8 Q&A

GitHub Copilot CLI でコーディングエージェントに、丸め誤差のバグを直させ、危険な変更を行い、元に戻します。語られた流れは次の順です。

## 7. 注意点・発表者の気付き

- **エージェントのネットワークは deny-by-default に**：許可リストで明示した宛先だけを許可する方式を、登壇者は推奨しています（5.6）。
- **サンドボックスの状態は使い捨てにする**：Harvey は、耐久性を持たせるのをトランスクリプトとファイルだけにしています。
- **ハーネスとサンドボックスを切り離しておく**：プラットフォームを入れ替えられる柔軟性のためです。
- **段階的にロールアウトする**：エージェント基盤は新しく、今後も変わると Harvey は話しています。
- **コントロールプレーンのボトルネック**：データプレーンを速くしても、1 秒に数百〜数千のサンドボックスが来る規模では、コントロールプレーンが重くなるという指摘があります。Agent Substrate で対応を進めています。
- **プレビューと GA の混在**：AKS AI Manager、マネージド Kueue、Agent Sandbox は、パブリックプレビューです。マネージド GPU ノードプールは GA、Anyscale on Azure は 10 月から GA と語られています。
- **デモは短縮・録画**：Lachie 氏のデモは時間の都合で短縮されており、GitHub の examples で自分で試すよう案内されています。
- 一部の製品名・綴り（TauGrid、DACS、Agent Substrate のリポジトリ URL など）は、音声認識の都合で確定できません。

## 9. まとめ

AKS は、オープンウェイトモデルのサービング、ポストトレーニング、エージェント実行という 3 つの AI ワークロードを、Kubernetes とオープンソースの上で動かすための機能を揃えています。

1. サービングでは、AKS AI Manager（プレビュー）でカタログから Qwen をデプロイし、分散キャッシュとマネージド GPU ノードプールで効率を上げる。
2. ポストトレーニングでは、KubeRay と Kueue のマネージド拡張、TauGrid によって、COBOL の学習で精度を 27% から 39% に高められることが示された。企業向けには Anyscale on Azure が GA。
3. エージェントでは、Harvey が Kata、ウォームプール、Blob プロキシ、スナップショットを使い、分離、高速起動、弾力性、データ保護を実現している。AKS 側は Agent Sandbox、Pod のスナップショットと復元、Kata V2、Agent Substrate、agent grid を提供する。拡張は、どんなハーネスやサンドボックスとも組み合わせられるよう、モジュール式にしてある。

登壇者は、Harvey のように AKS のチームと協力しながら使ってほしい、と締めくくっています。
