## 5. 発表内容の詳細

### 5.1 Azure のセキュリティ原則と SFI

Vikas 氏は、セキュリティは一度きりのリリースではないと説明します。ファームウェアと OS のベースラインを定義し、そこから生成される署名を検証・構成証明（attestation）にかけ、既知のベースラインで動いていることを確認します。テレメトリでドリフト（想定からの変化）を検出し、検出したら迅速に対応します。この循環が「フィードバックループ」です。

Microsoft は、ID、メール、エンドポイント、クラウドインフラなどからシグナルを観測し、脅威インテリジェンスを、自社の ID ポリシー、ワークロードのテレメトリ、対応のパターンと組み合わせて、広い可視性を得ています。自社のエンタープライズも Azure 上で運用しており、ファーストパーティーの多くのワークロード（PaaS サービスなど）が Azure 上で動いているため、それらも監視する責任があると述べています。

**Secure Future Initiative（SFI）** は、数年にわたる取り組みで、「secure by design、secure by default、secure operations」を掲げています。単なる施策ではなく文化の変革で、この数年で 3 万 5 千〜4 万人の従業員が、ID とシークレットの保護、テナントの保護、エンジニアリングシステムの保護などに取り組んできたと説明されています。その例として、**Entra ID のスタック全体が、世界中のすべてのリージョン・すべての AZ で、100% confidential computing 上で動いている**という説明がありました。Vikas 氏は、これを「自分たちが使う製品を自分たちで使う（eat your own dog food）」の実践だと述べています。

### 5.2 コンピュート

#### 分離の境界

コンピュートのセキュリティは、脅威をテナントごとに分けるところから始まります。ノード上の各テナントは、ハイパーバイザーによって互いに分離されています。Vikas 氏は、ハイパーバイザーの脆弱性に対して 25 万ドルの報奨金（bounty）がある、と述べています（本人も「I think」と付けており、金額は確実ではありません）。さらに、Microsoft 自身をお客様のワークロードから分離するための投資として、データセンターの secure control module、Azure Boost、そしてさらに踏み込む confidential computing が挙げられました。これらは単独では十分ではなく、攻撃者との間に何層もの障壁を作るためのものだ、という説明です。

#### 改善点 1：trusted launch は既定で有効

**trusted launch** は、rootkit や bootkit への対策です。UEFI 層とブートローダーが計測され、vTPM が計測結果を保持します。構成証明で環境が想定どおりかを確認でき、Defender for Cloud と連携できます。**trusted launch は現在、既定で有効**になっており、Vikas 氏は「すべてのワークロードで trusted launch を使うべき」と述べています。信頼できるブートチェーンを確立して監視し、そのうえでランタイム保護などを足す、という考え方です。

#### 改善点 2：ゲスト OS 更新後のイメージ参照の整合（プレビュー）

ゲスト OS をインプレースでアップグレードしたあとも、Azure のイメージ参照が古い OS を指したままになり、管理記録が合わなくなる問題があります。プレビューの機能が、同じ仮想マシンとディスクの種別を維持したまま（聞き取りにくい箇所があります）、このイメージ参照のメタデータを修正します。ゲスト OS のアップグレード手順に、このメタデータの整合を含めるよう勧められました。パッチ自体は引き続き自分で適用する必要があります。

#### 改善点 3：uniform スケールセットの定期評価

uniform なスケールセットでは、パッチの不足を定期的に把握できる周期評価（periodic assessment）が使えます。評価モードを「automatic by platform」に設定すると、24 時間ごとに実行され、イメージのメタデータが正確に保たれます。

#### IMDS とゲストプロキシエージェント

Instance Metadata Service（IMDS）では、ゲストプロキシエージェントが VM 内部の境界とネットワークの境界を守ります。メタデータへの不要なアクセスで、ワークロードが侵害されることを避けるのが目的で、SSRF やトークンの露出への対策になり、VM 内の過剰な信頼を取り除きます。メタデータが必要なプロセスだけに粒度の細かいポリシーでアクセスを絞り、既定で全員に与えないようにします。

#### Azure Boost

Azure Boost は、長年開発してきた専用の FPGA で、ノード上の処理をこの専用ハードウェアにオフロードします。すべての新しいサーバーに搭載されています。利点として、ネットワーク 400 Gbps、「20 gigabytes IOPS」と聞こえる性能（単位は音声認識の都合で確定できません）、デバイスへの直接アクセスが挙げられました。セキュリティ面では、Azure のインフラをホストのリソースから分離します。仮想マシンやコンテナーはセキュリティ境界で分離され、ホストの管理層はその下に置かれます。TCO（総所有コスト）の改善と、ワークロードの分離という追加の利点がある、という説明です。

#### confidential computing

保存時と転送時のデータ保護は業界の標準になっていますが、**使用中（メモリ上で処理中）のデータの保護**は、業界がまだ大規模には解決できていない、と Vikas 氏は説明します。confidential computing は、このメモリ上のデータの保護を助けます。もう 1 つの要点は、データとワークロードを、作成から破棄まで、自分が持つ鍵でエンドツーエンドに保護できることです。Entra ID を confidential computing で動かす意向は、2024 年ごろに公表した（本人は「I think」と述べています）と説明され、現在はその 100% が動いています。

ポートフォリオも拡大しています。AMD、Intel とのパートナーシップによるインフラ、Azure Boost や Azure Integrated HSM のような専用ハードウェア、コンテナーと Kubernetes への対応、ファーストパーティーのサービスの confidential 化です。スライドは細かい表（Vikas 氏は「eye chart」と呼び、意図的だと述べています）で、読ませるものではないと断っています。方針は、confidential VM を「まず良い VM」にすることです。

### 5.3 ストレージ

Mohammad 氏は、ストレージも同じく層で守ると説明します。データは攻撃者の主要な標的です。認証情報が含まれていれば、さらに多くのデータへ入られます。PII やクレジットカードなどの顧客データも含まれます。さらに、ランサムウェアでアプリケーションやエージェントからデータを使えなくされる懸念もあります。

層は 3 つに整理されました。

| 層 | 内容 |
| ---- | ---- |
| アクセス層 | エージェントやアプリケーションには managed identity を使う。RBAC は最小限のアクセスにする（例: エージェントが Blob やファイルにだけ話す必要があるなら、そこに絞る）。タグなどによる ABAC（属性ベース）で、さらに絞り込める。**ストレージのセッションベース認証**（パブリックプレビュー）は、エージェントとのセッションの間は認証が有効で、毎回再認証が不要になり、エージェントとストレージの通信が効率的になる。時間制限付きのトークンを要求に付ける SAS も使え、期限が切れるとトークンは無効になる（音声では "secure access signature" と聞こえます）。 |
| トランスポート層 | クライアントとストレージの間は TLS（ファイル、Blob、キューのいずれも）。ネットワークへのアクセスは Private Link や NSP を使う（ネットワークの章で説明）。 |
| 保存データ | マネージドキーで暗号化する。攻撃者がデータに到達しても、鍵がなければ復号できない。vaulted backup と immutable storage で、ランサムウェアのときに戻れるチェックポイントを持つ。geo の resiliency / residency で、特定の地域での保管要件を満たす。 |

アクセスのパターンとして、2 つが挙げられました。1 つ目は、アプリやエージェントがストレージにアクセスする通常のパターンで、上記の最小アクセス化に加えて、誰がアクセスしているかを継続的に監視し、ログを取ります。

2 つ目は、AI で増えている**パイプラインインジェクション**です。エージェント（例として OpenAI や MAI が挙げられました。音声には "cloud" とも聞こえますが確定できません）に問い合わせると、RAG（検索拡張生成）でデータを取得して LLM に送ります。この取得の際に、汚染されたファイルから取り込まれると、攻撃者がそのファイルに仕込んだプロンプトや指示で、エージェントが悪意ある動作をします。対策として、エージェントが利用するファイルを取り込み時にスキャンしてマルウェアが無いことを確認します。**Defender for Storage** を有効にすると、設定ミスや公開されたアカウントなどのデータ露出の問題をスキャンし、変更を監視し、ストレージアカウントや Blob を継続的に監視して、必要な対応を通知します。

### 5.4 ネットワーク

Mohammad 氏は、コンピュート、ストレージ、ネットワークのどれも外から内へ境界を守る点は同じだが、ネットワークには **lateral movement（横展開）** という違いがあると説明します。攻撃者は最も弱い場所（公開された VM や脆弱な VM）から入り、ネットワーク間を移動して、データやリソースといった価値の高い標的に達します。適切なセグメンテーションが無ければ、そこへ到達されます。

そこで、攻撃者の視点で「経路」に着目し、経路ごとの対策が整理されました。

#### Ingress（VM へのアクセス）

推奨は Azure Bastion です。ただし現実には、パブリック IP を使う人がいます。例えば、テスト担当者が「エージェントに VM をデプロイさせる」と、エージェントがドキュメントを見てパブリック IP を選択肢の 1 つとして使い、デプロイしたことを忘れた VM が弱い入口になります。パブリック IP を防ぐポリシーと Bastion の強制が 1 つの方法です。

#### インターネットからのデータ（AFD / Application Gateway）

Web Application Firewall（WAF）を使います。ルールセットをアプリケーションに合わせて調整できます。

#### Egress

Azure の VM は、既定でインターネットにアクセスできます。更新などを楽にするためですが、データの持ち出し（exfiltration）に使われる懸念があります。約 1 年前に **private subnet** を導入し、Microsoft 自身もこれを強制しています。private subnet は既定のアウトバウンドを無効にし、VM は専用のアウトバウンド手段を使います。例として NAT gateway、プロキシサーバー、AKS では egress のみを許し ingress をブロックするパブリック IP が挙げられました。

PaaS リソースへは、Private Link、または NSP と組み合わせた service endpoint を勧めています（NSP は昨年開始）。パブリックなファイアウォール経由の PaaS アクセスは使わないようにします。

#### セグメンテーション

VM には NSG と ASG、あるいは VNet 全体に効く NSG のような admin rules を使います。細かく分けすぎるとルールが足りなくなる、という課題があります。これに対して、**NSG と ASG をこの 1 年で 2〜3 倍に拡張した**と述べ、さらに倍増に向けて作業中だと説明しています（何の上限かは音声からは明確ではありません）。

#### AFD / Application Gateway の WAF の新機能

- HTTP DDoS 対策のルールセット
- service tag に基づくルールセットのフィルター
- **エージェントベースのルールセット**：Gemini、Claude、OpenAI などのエージェントは許可し、素性の分からないエージェントは Application Gateway への通信をブロックできる。
- **WAF Adaptive Defense**：AI でゼロデイのシグネチャを検出し、ルールセットを更新する。**現在プレビュー**で、興味があればサインアップできる。
- DDoS 保護の新機能として、カスタム緩和（DDoS が発動する条件を調整できる）と、平常時のテレメトリ（peacetime telemetry）。実際の DDoS か、自分のデータ量が増えただけかを区別できる。

#### PaaS の NSP

PaaS も IaaS と同様にファイアウォールで守る必要があります。推奨は **NSP（Network Security Perimeter）** で、リソースを 1 つの NSP に入れ、相互に通信させます。昨年開始し、その後 NSP grouping / NSP link（2 つの NSP グループ同士を通信させる）、Databricks のようなものに対する service tag のサポート、アクセスと拒否を見られる監視が追加されました。現在、**約 100 万のリソース**が NSP で動いていると述べています。また、Microsoft が SFI で何をしているかは、半年ごと（または四半期ごと）に公開される SFI レポートで確認でき、自社にも応用できる、と案内されました。

### 5.5 Securing AI：Agent Grid

Ashish 氏は会場に、エージェントを作っている人と、そのエージェントが安全だと自信を持っている人を尋ねました。後者は「おそらく誰もいない」という反応でした。

エージェントのワークロードは「信頼できない内部者（untrusted insiders）」で、LLM、別のエージェント、ツール、MCP、SaaS、PaaS、インターネットとの間で相互作用が網の目のように広がります。業界の答え（そしてこれまでの Microsoft の答えも）は、エージェントの前に AI gateway を置く、または後ろに egress proxy を置いて通信を検査する、というものでした。しかし単一のエージェントなら機能しても、相互作用の網には**スケールしません**。多数置けば集中管理と可観測性が課題になり、少数にすれば単一障害点になる、という理由です。

そこで、プラットフォームとして守る **Agent Grid** が紹介されました。Ignite のキーノートで発表され、火曜日の Igor 氏のセッションでも発表されたものです。

- クラウドネイティブでゼロトラストの、エージェントを守るソリューション。
- **エージェントの変更は不要。** SDK もフレームワークも提供せず、Agent Grid のリソースを作ってエージェントを管理・保護するだけ。
- エージェント ID と最初から統合されている。ネットワーク分離、マイクロセグメンテーション、L3 から L5 までの完全な検査を、ツール制御や MCP フィルタリングを含む粒度の細かいポリシーで適用できる。
- エージェントが生まれた時点で ID を付与し、以降の通信はエンドツーエンドで暗号化し、検査できる。
- AKS、VM、ACI、Foundry、Copilot Studio など、エージェントが動く環境（substrate）が多様でも、1 つのコントロールプレーンで同じポリシーを適用できる。異なる環境のエージェント同士（例: AKS のエージェントと Foundry や Copilot Studio のエージェント）を、同じネットワークに無くても安全にプライベート接続できる。

**現在プレビュー**で、最初に対応するのは次の 3 つの substrate です。

1. 新しく発表された AKS agent sandbox
2. ACI の sandbox group（音声では一部「ACS sandbox groups」と聞こえます）
3. 従来の AKS（クラウドネイティブなワークロード）

サポートするポリシーは 5 種類です。

| ポリシー | 内容 |
| ---- | ---- |
| TLS inspection | 通信の中身の完全な可視化 |
| content inspection | prompt shields によるプロンプトインジェクション対策 |
| FQDN filtering | FQDN によるフィルタリング |
| URL filtering | URL によるフィルタリング |
| MCP policy | ツール単位の粒度でのツール呼び出しのフィルタリング |

デモは 6.1 に書きます。

### 5.6 Secure with AI：Azure Adaptive Virtual Patching

企業のパッチ管理では、ゼロデイ脆弱性が公表されると、管理者が脆弱性と影響を分析し、パッチの内容、展開方法、パッチによる変更と影響を確認します。検証が済んでから展開するという流れです。Ashish 氏によると、**通常 5〜7 週間、中規模の組織でも少なくとも 4〜6 週間**かかります。これは攻撃者にも同程度の時間がかかっていたから成り立っていましたが、「私たちが vibe coding をしている間に、攻撃者は vibe hacking をしている」ので、今は脆弱性の公表から数時間（場合によっては数分）でエクスプロイトが作られます。防御側の時間は縮んでおり、数週間はかけられません。

そこで **Azure Adaptive Virtual Patching** が紹介されました。実際にパッチを当てるのではなく、AI で「先回りの盾」を張ってゼロデイから守ります。「嵐の中の傘」で、屋根（完全なパッチの適用）の下に入るまでの時間を稼ぐ、というたとえでした。傘が守るのであって、完全なパッチを配るわけではありません。

3 つの「セマンティック層」で動きます。

1. 脆弱性そのものを完全に理解する層。
2. Azure 上の資産を理解する層。ワークロードの展開状況、実行中のプロセス、インストールされたモジュールやパッケージ、開いているポート、インターネット対プライベートネットワークの露出面を把握する。
3. 上記を相関させて、悪用されうる攻撃対象領域と、そのワークロードに固有の緩和策を導く層。

デモは 6.2 に書きます。

### 5.7 Azure Firewall の AI Security アドオン

Azure Firewall は、Azure 上の南北・東西の通信を保護する既存の製品です。**今日、新しい Premium SKU のアドオン「AI Security」を発表**しました（Ashish 氏）。securing AI、secure with AI、AI による運用の簡素化の 3 つをカバーします。

| 領域 | 機能 |
| ---- | ---- |
| Securing AI | **Prompt injection protection**：社内の生成 AI アプリへの悪意あるプロンプトを防ぐ。**Network DLP**：Microsoft Purview の流出防止ポリシーを、許可していない生成 AI アプリへのデータ送信にも拡張する。例として、Word ドキュメントが DeepSeek に送られるのを防ぐ場合が挙げられた。 |
| AI による運用の簡素化 | **AI policy**：ファイアウォール上のトラフィックとポリシーを相関させ、インサイトを出して運用とポリシーを簡素化する。 |
| インラインの知能（スライド右側の 2 つ） | **Malware detection** と **Application vulnerability protection**（アドオンの 5 つ目の機能）。ネットワーク上のインラインの知能（inline intelligence）。 |

最後の 2 つは、専用の AI モデルを、**GPU ではなく CPU で、回線速度（line speed）で**インライン実行します。手頃でスケールできる構成にするためです。

#### Malware detection

既知のマルウェアは多くの製品が防げますが、未知のマルウェアは課題です。業界の標準は**サンドボックスと detonation（実行して挙動を観察）**です。シグネチャに無い新しいファイルをブロックしてオフラインで解析し、サンドボックスで動かして、ファイル I/O やネットワーク操作を観察し、悪性か良性かを分類します。

Ashish 氏は、現代の脅威にはこれが成り立たないと 3 つの理由を挙げました。

1. 初めて見るファイルごとにサンドボックスが必要で、計算資源がかかり高コストになる。
2. オフラインで解析するため、分類に 5〜10 分かかり、インラインでは使えない。
3. 高度なマルウェアは、サンドボックス内で動いていることを検知して、本来の挙動を見せない。

Azure Firewall は、**数百万の悪性マルウェアのペイロードで学習した AI モデル**を使い、**アセンブリの opcode**（機械命令）に基づいて分類します。LLM は言語の理解が得意で、英語に限らず任意の「言語」を学習できる、という考え方で、悪性な opcode を理解するよう学習させたモデルで、ネットワーク上のファイルを回線速度でインラインに分類します。デモは 6.3 に書きます。

#### Application vulnerability protection

特化した AI モデルに「従来のアプリ保護（特定のルールセット）を回避せよ」という目標を与えると、エージェントがモデルを使って悪意ある Web リクエストを作り続け、最終的に**数分で**従来の保護を回避します。したがって従来のアプリ保護は現代の脅威に対応できない、というのが Ashish 氏の主張です。

これに対し、Web アプリへの悪意あるリクエスト数百万件で学習した新しい AI モデルを使い、**数ミリ秒**で Web リクエストを悪性か良性かに分類し、悪性ならポリシーでインラインにブロックできます。デモは 6.4 に書きます。

### 5.8 Azure Bastion：RDP vision と SSH vision

Azure Bastion は、パブリック IP を公開せずに VM へ RDP と SSH で接続するためのサービスです。昨年、**session recording** が発表され、RDP と SSH のセッションを動画として Blob ストレージに保存できるようになりました。

課題は量です。数百人の従業員と数百のワークロードがあると、毎日数千本の動画ができ、「誰が全部見て悪意あるまたはリスクのある操作を見つけるのか」という干し草の中の針探しになります。そこで今年、**RDP vision と SSH vision** を導入します。AI でセッションの内容を見て、リスクのある操作にフラグを立て、セッションの要約も付けます。デモは 6.5 に書きます。

### 6.1 Agent Grid のデモ

**事前の構成**（説明より）

- Agent Grid のリソース（最上位のリソース）を作成済み。
- ACI の sandbox group（ハイパーバイザーによる分離でエージェントを動かす新機能）にエージェントを置いている。
- 同じ Agent Grid に、デモの中で AKS クラスターを追加する。クラスターは、ツール呼び出し用の MCP サーバーを動かし、新しく発表された AKS agent sandbox（ハイパーバイザー分離）で動いている。

**手順（語られた順）**

1. Agent Grid の画面で、オンボード済みのリソースが 1 つであることを確認する（ACI の sandbox group）。
2. AKS の MCP サーバーを追加する。AKS クラスターを検索して選択し、クラスターを追加する。
3. クラスターが追加されると、その中で動くワークロードが自動で検出される。1 つ見つかる（MCP サーバー）。まだ enroll されていないので、enroll ボタンをクリックし、ファブリックにオンボードする。
4. 追加された時点で、エージェントと同様に、「spiffy ID」（聞こえた表記のまま）が割り当てられる。
5. **シナリオ 1（正当な呼び出し）**：顧客がサポートエージェントに「ライセンスが動かない」と相談する。エージェントが LLM に問い合わせ、LLM の指示でツールを呼び出してライセンスの状態を取得する。結果は「ライセンスを使い切っているので、新しく購入が必要」。
6. **シナリオ 2（悪意あるプロンプト）**：プロンプトを細工して、呼び出してはいけないツールをエージェントに呼び出させる。Agent Grid のポリシーをまだ定義していないので、**成功してしまう**。
7. ポータルに戻り、MCP ポリシーを作る。「export customer records」というツール呼び出しを許可しない、というポリシーを定義し、特定の spiffy ID（エージェント ID）に紐づける。
8. 同じ悪用シナリオをもう一度実行する。今度は**ツール呼び出しがブロックされ**、顧客データは露出しなかった。
9. live inspect で、許可された呼び出しと拒否された呼び出しを一覧する。
10. flow map で、エージェントと MCP サーバー、その間の相互認証されたトンネル、流れているすべてのフローを見る。ブロックされたフローを選ぶと、そのフローを止めた**具体的なポリシー**も確認できる。

### 6.2 Adaptive Virtual Patching のデモ

題材は、「数週間前に表面化した PHP の脆弱性」です。Ashish 氏は「世界を席巻した。インターネットの 70% が突然露出した」と述べています。

1. 脆弱性の概要を確認する。PHP のバージョンに影響し、細工したリクエストで out-of-memory 例外を起こし、実行中のメモリの状態を持ち出せる。続けてリクエストを重ねるとリモートコード実行につながる。
2. 対象の PHP のバージョンが 8.1.2 で、脆弱であることを確認する。
3. 攻撃する。**成功し**、PHP サーバーの実行中のメモリダンプを取得できる。このダンプの情報は、後続のリクエストによるリモートコード実行を細工するために使える。
4. Azure ポータルで Adaptive Shield（最上位のリソース）を開く。デモ用に作成済みで、この VM（PHP のワークロード）が追加されている。
5. このワークロードを開くと、デプロイすべき緩和策がすでに見つかっている。PHP のものを開くと、粒度の細かい緩和策が表示される。実際のパッチではなく、AI で算出し、**human in the loop（人間の確認）で検証した**、ワークロードに固有の仮想パッチである、という説明。
6. 緩和策を確認して承認する。承認すると、ワークロードに配信されて適用される。
7. 同じ攻撃を再度実行する。**メモリは持ち出されず、攻撃はブロックされた。** ワークロードにパッチも当てず、停止もしていない。
8. なお、あとから実際のパッチを適用した場合は、この緩和策をシームレスにロールバックできる、とデモ中に説明されています。

### 6.3 Azure Firewall：malware detection のデモ

1. anti-malware のセキュリティプロファイルを、alert と deny のモードで用意する。ファイルが通過すると解析されてマルウェアのリスクスコアが付く。**スコア 50 超でアラート、80 超で自動ブロック**。
2. このプロファイルをセキュリティプロファイルグループに入れる（複数のセキュリティ機能をまとめて適用するためのもの）。
3. アプリケーションルールは 2 つ。Bob のマシン用と Alice のマシン用。セキュリティプロファイルグループは、Bob のルールにだけ関連付けられている。Alice のトラフィックは保護されない。
4. 画面の左に Alice と Bob のマシン、右に 2 つの監視ウィンドウ（上はマルウェア検出モデルの出力、下は Azure Firewall のログ。ファイルごとのリスクスコアと結果の処理を含む）。
5. Alice が悪意あるファイルを OneDrive にアップロードする。検査されないので**そのままアップロードされ**、マルウェア関連のイベントは出ない。
6. Bob が**同じ悪意あるファイル**をアップロードする。ファイルが検査され、モデルが悪性と判定し、拒否のしきい値を超えるスコアが付き、**直ちにブロック**される。モデルの分類結果と、Azure Firewall のアラート・実施した処理の記録が両方のウィンドウに出る。
7. Bob が問題の無いファイルをアップロードする。低リスクのスコアで**許可**され、ログには評価して安全と判断した記録が残る。

### 6.4 Azure Firewall：advanced application threat protection のデモ

導入では、AI で悪性・良性のリクエストを合成して混ぜ、Azure Firewall 上の AI モデルが悪性を防いで良性を通す様子を見せる、と説明されました。

1. advanced application threat protection のセキュリティプロファイルを作成する。アラートのしきい値は 50、拒否のしきい値は 80。エンジンが通過するコンテンツを解析して信頼度スコアを出す。
2. プロファイルをセキュリティプロファイルグループに追加する。
3. このグループを、クライアントのトラフィック用のアプリケーションルールに関連付ける。ルールを保存すると、クライアントのトラフィックが検査される。
4. クライアントのマシンから、**脆弱性を狙うものと問題の無いものを混ぜた 2,000 件のリクエスト**を送る。すべて Azure Firewall 経由。画面の左上にクライアントのマシン、右上に AI モデルの解析ログ、下に 2 つのバックエンドインスタンスの Azure Firewall のログ（脅威の信頼度スコアを含む）。
5. トラフィックを流すと、拒否のしきい値を超えた脆弱なトラフィックがブロックされ、残りは検査のうえ許可される。
6. テスト終了後、左上にエンジンの全体の精度が表示される。Ashish 氏は、複数のテストの平均で**精度は約 90〜95%**であり、従来のアプリ保護で同様の AI を使ったテストをすると**約 10〜15%** だと述べています。

### 6.5 Azure Bastion：RDP vision と SSH vision のデモ

**RDP**

1. Azure ポータルから Bastion 経由で Windows VM に接続する。この Bastion の premium host は、session recording と RDP vision が有効で、Bastion ホストに設定した ID を使って、セッション全体が Blob ストレージに録画される。
2. 悪意あるユーザーとして、Windows Defender Firewall を開き、ファイアウォールの保護をオフにする。
3. デスクトップにある平文のファイルを開き、中に保存された API シークレットを確認する。
4. セッション終了後、RDP vision が録画に対して推論を実行し、結果を公開する（少し時間がかかる）。
5. Bastion のポータルの session recordings に、AI のインサイトとともにセッションが表示される。RDP vision がセッションを要約し、**2 つのリスクのある操作**（ファイアウォールの無効化、平文ファイル内の API シークレットの閲覧）にフラグを立てる。検出結果を選ぶと、録画のその時点へ直接ジャンプする。

**SSH**

1. Bastion 経由で Linux VM に接続する。command logging と SSH vision が有効で、セッションの全コマンドが記録される。
2. ユーザーが、特権シェルを起動して、自分のアカウントにパスワード無しの昇格アクセスを設定するといった、リスクのある操作を試みる。
3. セッション終了後、SSH vision がコマンドログに対して推論を実行し、結果を公開する。
4. セッションがポータルに分析結果とともに表示される。SSH vision が要約し、権限昇格の試行にフラグを立て、**各検出結果を元のコマンドログの該当コマンドに紐づける**。

これにより、管理者はリスクのある操作を見つけ、調査の焦点を絞り、AI のインサイトを元のセッションの証拠と照らして検証できる、と説明されています。

## 7. 注意点・発表者の気付き

- **trusted launch は既定で有効ですが、すべてのワークロードで使う前提**にするよう勧められています。
- **ゲスト OS のアップグレードでは、パッチ適用に加え、イメージ参照のメタデータの整合も必要です。** パッチ自体は自分で適用します。
- **IMDS へのアクセスは既定で全員に与えず、必要なプロセスだけに絞ってください。**
- **Azure の VM は既定でインターネットにアクセスできます。** データ持ち出しのリスクがあるため、private subnet と専用のアウトバウンド手段を使います。
- **エージェントにインフラを作らせると、パブリック IP が使われて、そのまま忘れられる恐れがあります。** ポリシーで防ぐ、Bastion を強制する、という対策が示されました。
- **細かいセグメンテーションでは、ルールが足りなくなる課題があります。** NSG と ASG は、この 1 年で 2〜3 倍に拡張したとのことです。
- **ゲートウェイ型の対策は、エージェントの網にはスケールしません。** 多数置くと集中管理の課題、少数だと単一障害点になる、という説明です。
- **RAG で取り込むファイルには、プロンプトが仕込まれている恐れがあります（パイプラインインジェクション）。** 取り込み時のスキャンが対策です。
- **パッチの適用が数週間かかる一方、エクスプロイトは数時間から数分で作られます。** 仮想パッチは、パッチの代わりではなく、パッチを当てるまでの時間稼ぎです。緩和策は人間の確認を経て承認します。
- **ステータスの区別：** Agent Grid、ストレージのセッションベース認証、ゲスト OS 更新後のイメージ参照の整合、WAF Adaptive Defense は発表でプレビューと述べられました。Adaptive Virtual Patching、Azure Firewall AI Security アドオン、RDP vision / SSH vision の提供状況（プレビューか一般提供か）は、発表では触れられていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **既定で守られる**：trusted launch は既定で有効。Azure Boost は、ホスト管理層を分離しつつ、TCO の改善にもなる。
- **使用中のデータまで保護**：confidential computing で、作成から破棄まで自分の鍵で保護できる。Entra ID の全スタックが confidential computing 上で動いている。
- **エージェントを変更せずに守れる**：Agent Grid は SDK もフレームワークも不要で、複数の環境にまたがるエージェントに 1 つのコントロールプレーンから同じポリシーを適用できる。デモでは、ツール呼び出しをブロックして顧客データの露出を防いだ。
- **パッチ適用の前に守れる**：Adaptive Virtual Patching は、ワークロードを止めずに、人間の確認を経た緩和策を適用できる。実際のパッチを適用したあとは、緩和策をロールバックできる。
- **インラインで AI により検査**：Azure Firewall の AI モデルは CPU で回線速度で動くため、手頃でスケールできる。サンドボックス型で 5〜10 分かかる分類を、インラインで行える。デモの精度は約 90〜95%。
- **監査の手間を減らす**：RDP vision / SSH vision で、毎日数千本の録画から、リスクのある操作を見つけられる。

## 9. まとめ

Azure のセキュリティは、ID、ネットワーク、データを重ねた層構造で、コンピュート（trusted launch、Azure Boost、confidential computing）、ストレージ（アクセス、トランスポート、保存データの 3 層）、ネットワーク（ingress、egress、PaaS、セグメンテーション）のそれぞれに組み込まれています。

後半では、AI で攻撃の速度が上がったことを前提に、エージェントを守る Agent Grid、ゼロデイに対する Adaptive Virtual Patching、Azure Firewall の AI Security アドオン、Azure Bastion の RDP vision / SSH vision が紹介されました。Vikas 氏の言葉どおり、セキュリティは 100% にならず終わりのない仕事なので、AI の時代に合わせて、セキュリティ文化を含めて見直すことが勧められています。
