### 5.2 GitHub Copilot app と Copilot Fusion

AISDLC のなかで特に注目の 2 つの発表として、次の 2 つが挙げられました。

**GitHub Copilot app** は、Ignite の発表ではなく、すでに話題にしてきたもので、GitHub Universe で紹介されたものと説明されています。使いやすく、「やみつきになる」開発体験だそうです。スライドには Matt 氏の趣味のプロジェクト（自宅ネットワークをゼロトラストネットワークにする）のスクリーンショットが映されました。デバイスの分離、デバイスが到達できるインターネット上のエンドポイントの制限、監査とアラートなど、実現したいことを AI の助けでスペックにまとめ、「let's go」と指示すると、画面右側で複数のエージェント型開発が並行して始まったと説明しています。複数のエージェントのストリームを、中央のオーケストレーターが取りまとめる「project」という概念があり、1 行ずつ手でコードを書く作業から、全体を指揮する作業へ移れる点を評価しています。

**Copilot Fusion** は GitHub Copilot の複合モデル（composite model）機能です。有効にすると最適なモデルが選ばれ、フロンティア水準の性能を大幅に低いコストで得られると説明されました。スライドのグラフでは左ほど安く、上ほど高性能で、Fusion は Opus や GPT-6（聞こえた表記のまま）を上回る位置に描かれていたとのことです。詳細は benchmarks.github.com で確認できると案内しています。価格と性能の両方で勝つのは珍しく、それが GitHub Copilot だけで提供されている、という主張です。

### 5.3 事例: GitHub Copilot SDK ランタイムの TypeScript から Rust への変換

AISDLC の教訓を語るために、Microsoft の事例が 1 つ取り上げられました。本番で重要な役割を担っているシステムの変換です。

| 項目 | 内容 |
| --- | --- |
| 対象 | GitHub Copilot SDK のランタイム |
| 規模 | TypeScript 約 43 万行を Rust 約 130 万行に変換 |
| 担当 | GitHub の開発者 1 人（氏名は音声認識で「Steven Toob」と聞き取れますが、表記が確定できません）。パートタイムで 3 か月 |
| コスト | トークン代で約 12 万ドル |
| 期間 | グラフ上は 5 月から 8 月。最終的に TypeScript は無くなり Rust だけが残った |

> 補足：後半で Sandy 氏は「1.2 million lines」と言い換えています。表の数字は Matt 氏が説明した 130 万行です。

移行前の構成は、SDK の中に headless CLI があり、その中で Node.js 上の TypeScript ランタイムが動くマルチプロセスの構成でした。素早く出荷するには適した構成でしたが、プロセス内で動かしたい、メモリ安全な言語にしたい、ランタイム性能を大きく上げたい、という理由で Rust への移行が選ばれました。

移行は一括ではなく、少しずつ進められました。Rust のコードを段階的に本番に入れ、残りの部分は TypeScript のまま相互運用させながら、顧客が使っている状態で 3 か月かけて TypeScript をなくしています。行数の推移を示すグラフでは、TypeScript のユニットテストはむしろ増えていました。安心して移植できるよう、テストカバレッジを引き上げる必要があったためと説明されています。

**人間の時間の使い方**（スライドの内訳）

- レビューとテスト: 30%
- 設計の議論: 17%
- 完了まで確実にやり切らせるためのオーケストレーションの押し込み: 15%
- プルリクエスト、リポジトリ、セッションなど成果物の管理
- 残りは細かな作業

**エージェントの時間の使い方**

モデルのオーケストレーションを移植した 42 時間の区間が例として示されました。フェーズごとに使われたモデルは異なり、複数のモデルが混在していました。エージェントの作業を見ると、Rust を書いている時間はごくわずかで、大半は読み込みと検索でした。そのうえで、レビューと、ビルド・テストが多かったとのことです。

なお、Matt 氏によれば、この件を当事者が書いた公開ブログ記事があり、読むのに 1 時間ほどかかります。発表はそこから一部を抜粋し、補足したものです。

**リグレッション**

リグレッションはおよそ数十件発生しました。多くは本番投入前に見つかり、一部は本番で見つかっています。いずれも大きな問題ではなく、検出後すぐに修正されました。すり抜けているものがある可能性や、まだ残っているものがあることは認めつつ、大きなものは残っていないと見ており、現在は大規模に使われているとのことです。

**成果**

| 指標 | 移行前 | 移行後 |
| --- | --- | --- |
| 1 クライアントセッションでの 1 ターンの所要時間 | 5 秒 | 55.3 ミリ秒（プロセス内） |
| 共有クライアントのスループット（空のターン。ランタイムのオーバーヘッドを見る指標で、高いほど良い） | 毎秒 7.55 | 毎秒 120 |
| 10 クライアント時のメモリ（ワーキングセット） | 1,300 MB | 126 MB |

Matt 氏は、1 人がパートタイムで 3 か月というこのプロジェクトは、1 年前なら分別のあるチームは誰も着手しなかったはずだ、と述べています。多数の人員と 6〜9 か月が必要で、リグレッションも複雑さも多く、ROI が合わなかったからです。今は「もう一度、十数回でもやればいい」ほどの価値があるとしています。ただし、Rust が最終解で TypeScript をやめるべきだという主張ではなく、エージェント型 SDLC が仕事のやり方を変える力の大きさを示す例だと断っています。

### 5.4 Microsoft 社内の事例から得た教訓

Matt 氏は、Microsoft 社内でエージェントの活用が突出しているプロジェクトの関係者に聞き取りを行い、次の教訓をまとめています。

1. **小さなチームを決めて、目的を与える。** 例えば、顧客のフィードバックをできるだけ早く実装できるようにする、パフォーマンスのリグレッションをなくす、すべてを常にアクセシブルにする、といったものです。
2. **最初はプロダクトを変えない。** プロダクトを囲む「品質のシステム」に集中します。リポジトリのバグ、テレメトリ、ライブサイトのインシデントを見直し、継続的なパフォーマンス検証を行い、テストカバレッジを上げます。さらに、あらゆるリージョン、あらゆる構成でプロダクトのすべての部分を動かす合成ランナーを本番に置き、問題を常に見つけられる状態にします。これらは後悔のない低リスクの取り組みで、顧客体験を改善します。
3. **品質の仕組みができてから、メインのコードベースにエージェントを使う。** 問題が起きても気づける確度が高まります。その前に、成果を明確にしておきます。ユーザー体験、API の形、非機能要件を具体化するほど、エージェントが暴走して間違ったことをする可能性が減ります。
4. **「人間はコードを理解しなくてよい」という考えについては、状況次第としています。** ただし、10 年前に退職者が書いて今は誰も仕組みを知らないコードは、すでにどの組織にもあります。エージェントはそうしたコードの理解や周辺の運用を以前より助けてくれるので、それ自体は障害になりません。
5. **人間の説明責任は変わらない。** 「エージェントが間違えた」は許されず、成果には人間が責任を持ちます。
6. **エンドユーザーの声を見る。** eval の結果は良いのにユーザーの評価が低いなら、eval が十分に厳しくないというシグナルです。
7. **新人（ジュニア）の育成方法は、まだ誰も答えを出せていない。** シニアは良い状態を知っていて速く動けますが、ジュニアには難しいとされ、業界全体で解くべき課題と位置づけています。

### 5.5 Wipro の Ramu 氏との対談

ここから Wipro の Chief Partnership Officer、Ramachandran 氏（愛称 Ramu）との対談になります。Ramu 氏は Wipro に 30 年在籍し、ここ 10 年はソフトウェアの構築、組織づくり、変革に関わってきたと自己紹介しています。Microsoft のエコシステムとの付き合いは約 20 年です。

**Wipro 社内での取り組み**

- Wipro は Microsoft にとっての「frontier company」になったと述べています。当初、約 35,000 人が GitHub Copilot を使っていました（この数字の文脈は、音声認識の都合で聞き取りが不明瞭な箇所があります）。最初に Center of Excellence を立ち上げ、さまざまな業界・領域での活用方法を理解する開発者を集めました。
- Microsoft 365 Copilot は約 10 万人以上が使っています。そのほか Fabric と Foundry、Foundry 上のさまざまなモデルの活用も進めています。
- そのために、組織変更の管理も行いました。例えば、リポジトリは複数ではなく 1 つにする、といった整理です。
- 仕事全体を約 20 の成果物（artifact）にまとめ、「Wipro Intelligence」という 1 つのブランドで顧客に伝えています（音声認識では「Pro Intelligence」と聞こえます）。
- 運用（run）の領域、つまりサポート・保守やインフラ保守は、エージェントで自動化する方針です。そのプラットフォームが「Next Generation Services Platform」で、現在 70 ほどのエージェントを実用水準に仕上げています。
- 構築・変革（build and transform）側の生成 AI プラットフォームは「Vega」です。ここでは 20 の成果物が重要だとしています。
- 業界が直面している課題としてレガシーコードのモダナイズ（メインフレームなど）を挙げ、どのモデルがどの用途に向くかのベンチマークと、トークン経済性の検討も行っています。

**開発者の役割**

Ramu 氏は、Matt 氏が挙げた事例の開発者は「author から orchestrator へ」移っていると表現しています。仕様と意図を与え、バックログから GitHub が成果を引き出し、朝に出社してその結果を確認し、テストする、という流れです。ここで secure by design を最初から組み込むことが重要で、そこがパイロットから本番へ進めない原因になりやすい、と述べています。secure by design については、前日の発表でも多くが示されたと述べています。開発者には非機能面にも注目するよう伝えているそうです。仕様から「ハッピーパス」を作るのは簡単ですが、スケールした環境で成立させるのは難しく、エージェントにそれを教える必要があるためです。

**顧客事例（メインフレーム）**

レガシーコードのモダナイズに関する取り組みは、銀行や医療などの規制業種が多いそうです。その一例として、レガシーなメインフレームのコードをモダナイズした顧客が挙げられました。2 年を見込んでいた作業が約 7 か月で終わっています。MIPS 消費が最大のモジュールを対象に、信頼性を確かめながら進めたとのことです。

**新卒・ジュニア育成**

大学を出る多くのエンジニア志望者を将来に向けてどう育てるかについて、Wipro は学習のためのツイン（twin）とメンタルモデルを作ることに力を入れています。「シニアだけを採用するのは短期的な成功戦略であり、長期的な戦略ではない」と述べています。

**GSI ビジネスの変化**

- すべての GSI が、人に依存してきたビジネスから、「人間 + エージェント」というモデルへの転換という大きな課題を抱えている。これは運用モデルの転換である。
- 工数を売る形から、成果を売る形へ移っている。時間・材料費、固定価格、固定キャパシティではなく、「30〜40%」といった成果を出せるシステムを作れるかが問われる。
- スキルも変わっており、各 GSI が forward deployed engineering に取り組んでいる。1 人で担う形か、少人数のポッドかを検討している。Microsoft の learning team と連携して人材を育てている。
- 業界は破壊的な変化のたびに作り替えられ、そのたびに新しい AI サービスが生まれる。パートナーシップはより統合的になり、エコシステムが重要になる。Ramu 氏自身、エンジニアリングの責任者からパートナーシップの責任者に配置換えされたのも、成果型のソリューションが中心になったためだと述べています。
- 「問題解決者」や「レゴブロックを組み立てる人」を育て、エージェント同士を連携させて成果を出す。
- 成長はプラットフォームビジネス、つまり非線形で、成果に基づく課金のモデルから生まれるという見方です。空港の手荷物ハンドリングの改善を成果として課金するような例が挙げられています。

**今後に期待していること**

Wipro は直近 6〜7 か月、use case factory に力を入れています。エージェントファクトリーは各社が作っていますが、こちらは AI の強度（AI intensity）と ROI を理解するためのものです。10 の業界と 6 つのサービス領域で行い、ブループリントの仕組みにまとめようとしています。購入パターンも変わり、これまで話したことのない相手と話すようになっています。エネルギー企業と Microsoft で進めている例では、フィジカル AI と工場の digital twin を再構築しており、NVIDIA のスタックと Microsoft の上で動かしています。これを次の複数の工場に展開するテンプレートにしたい、と述べています（工場の数や年は音声認識の都合で確定できません）。

### 5.6 Adobe と Kore.ai を交えた議論

Sandy Gupta 氏は、グローバルのソフトウェアエコシステムを統括する立場です。プラットフォーム企業の価値は、その上に載るイノベーションの質で決まると述べ、GitHub（エージェントとともに共同で構築する場）、Foundry（AI ファクトリー。ランタイムとオブザーバビリティ）、Microsoft IQ、コントロールプレーンとしての Agent 365 を挙げています。続けて、Adobe の Olof 氏（Unified Platforms の SVP で CIO、Microsoft の元社員）と、Kore.ai の Prasanna 氏（AI ネイティブ企業の CTO）を紹介しました。

**Adobe: GitHub Copilot の導入**

Olof 氏によると、Adobe はまず「1000 輪の花を咲かせる」アプローチで、集中管理よりも AI の採用を優先しました。一部に懐疑や不安があったものの、想定より抵抗は少なく、これほど速く浸透したものは見たことがないそうです。その後にガバナンス、コスト管理、全体の管理という課題が出たため、標準化することにしました。市場の選択肢を検討した結果、GitHub Copilot が最良の選択肢でした。理由は 2 つです。

1. Microsoft と長年のパートナーシップがあり、共同で進められること。
2. モデルやフロンティアラボへのロックインを避けたいこと。毎週のように、より良い、安い、速いモデルが出るため、その柔軟性が GitHub Copilot にあります。

**Adobe: Foundry の活用**

Adobe は「AI で AI プロダクトを作る」と説明しています。ツールセット、モデルの選択肢、クラウド上のガバナンスとランタイムが揃っていることで、社内のプロダクトチームは、新しいモデルが出たときにアーキテクチャを作り直したり IT の承認を取ったりせず、安全なサンドボックスで試せています。すべて社内で統制・承認された状態です。

顧客も同様に、日々の作業の手間を減らすことを求めています。1 年前は「AI は助けになるのか、代替するのか」という不確実性がありましたが、いまは助けになるものだという理解が進んでおり、特にクリエイティブ分野では人間の創造性が必要だとしています。例として、作ったデザインがブランドに沿っているかを、ブランド文書を人が読む代わりに、Foundry のモデルでブランド文書や過去のアセットと照合して確認する、という使い方が語られました。モデルのファインチューニングにも取り組んでおり、フロンティアモデル、コスト効率の良いモデル、オープンウェイトモデル、そして Adobe 自身のモデルである Firefly（Adobe がホストしていると述べています）まで、幅広く試せる「遊び場」だと表現しています。

**Kore.ai: Foundry を開発ランタイムとして使う**

Prasanna 氏によると、Kore.ai は大規模で複雑な、規制の厳しい企業を 10 年以上支援してきました。音声エージェントとビジネスプロセスのエージェントを提供しています。Foundry 上で動く AI ネイティブな新プラットフォーム「Artemis」により、エージェントによる成果をより速く届けられます。

銀行が、紛争、カード紛失、旅行の通知などに対応する音声 AI エージェントを導入したい場合を例に、ゼロから何か月もかける代わりに、Foundry から Kore.ai の「AI for banking」を取得できます。さらに「Autoloop」（音声認識では「outer loop」とも聞こえます）という仕組みがあり、業務手順書（operating procedures）をアップロードすることで、事前構築済みのエージェントを自社の業務に合わせてカスタマイズします。通常は API と統合され、Autoloop が eval を実行してエージェントを更新します。Foundry の堅牢なインフラの上で、モニタリングに Agent 365、エージェントの可視化とガバナンスに Foundry の control plane を使うことで、Microsoft のガバナンス水準を保ちながら速く、低コストで成果に到達できるという説明です。

Foundry に対して Kore.ai が加える価値として、3 つの観点が挙げられました。

1. **展開の速さ**: 銀行、ヘルスケアなどのワークフローを組み込み済み・統合済みのエージェントを用意しており、Autoloop で運用手順への適合も手作業なしで行えます。
2. **安全性と信頼**: 顧客がカスタマイズした事前構築エージェントは、Foundry のガバナンス、Defender、Purview と統合され、コンプライアンス境界の中で動きます。オブザーバビリティとコントロールプレーンは自動的に継承されます。Artemis 上で作ったエージェントは Foundry のエージェントとして動かせ、深く統合されています。
3. **インテリジェンス**: 低レイテンシの音声対話で必要な、バックチャネルの扱いやターン検出など、人間らしい体験のためのモデル群を作っています。高速ガードレールモデル、ターン検出モデル、判断モデルがあり、いずれも Foundry にデプロイできます。

Sandy 氏は、これを Ramu 氏の Vega プロジェクト（できるだけ自律的にしたいという方向）にとっても機会になりうると触れています。

### 5.7 今後の展望（Olof 氏と Prasanna 氏）

最後の質問は、数十年の経験を持つ多数のシニア開発者を支える立場から、次に何が来るか、機会と注意点は何か、というものでした。最初に答えた Olof 氏の発言と、「Olof 氏の指摘に沿って」と受けた Prasanna 氏の発言をまとめます。

**Olof 氏**

- ジュニアについては、AI が怒らないので質問し放題であり、ジュニアが早く立ち上がる助けになっている。
- 第 1 の波である支援型の開発（オートコンプリートの延長）は、生産性の向上が 5〜10% 程度だった。ユニットテストも書いてくれた。
- 第 2 の波である委任型・エージェント型の開発で大きく伸び、生産性向上は 40〜50% 程度と見ている。
- エキサイティングな変化として、コーディングから離れていたマネージャー、アーキテクト、VP、CTO などが、楽しいので戻ってきている。
- 運用、デプロイ、セキュリティにはまだ多くの時間がかかる。次の 2 倍、5 倍、10 倍を引き出すために、AI ファクトリーと RSI（recursive self-improvement）に取り組んでいる。
- まだエージェントが書くコードを完全には信頼できないが、敵対的なモデルによるコードレビューは十分良くなってきた。シニアエンジニアに「AI と人間のどちらにレビューしてほしいか」と聞くと、AI を選ぶ人が増えている（両方が望ましいという前提）。ただし、AI がコードを書く場合の人間によるレビューは難しく、ボトルネックになる。
- 本番の責任は人間にある。リスクスコアリングなどにより、人間が見るべき変更と、安全な変更（アクセシビリティの変更や単純なセキュリティ修正など）を分けられる段階に近づいている。
- 10 倍の飛躍は、書くコードの量ではなく生み出す価値で決まる。コードが無料になると悪い製品も素早く作れるため、人間は顧客と向き合い、価値を理解する時間に使うべきだと述べています。

**Prasanna 氏**

- Kore.ai もプラットフォーム全体を AI で書き直す同様の旅路をたどった。
- AI が逸れないようにフィードバックを与え、自己評価できる環境とハーネスが十分に強い必要がある。AI がソフトウェア工学で間違えるパターンは識別されており、標準化されていく。自律的なソフトウェアエンジニアリングへの変革は、すでにそこまで来ている。
- エンジニアは、Rust か TypeScript か、フレームワークの細部ではなく、成果とそれが生む価値を考えるようになる。
- 今後より大きく影響を受けるのは、ビジネスプロセスの自動化だと見ている。数日や数か月かかるプロセスを数時間に圧縮できる。
- 今回のカンファレンスで多くの人が信頼（trust）を重視していた。エージェントを信頼できるかが皆の待っている点で、ツール、パターン、プラクティスが確立し信頼が育てば、採用は自然に進む。

## 7. 注意点・発表者の気付き

- **人間が責任を持つ。** 「エージェントが間違えた」は理由にならないと Matt 氏は述べています。
- **eval だけでは足りない。** eval が良好でもユーザー評価が低いなら、eval が甘いというシグナルです。
- **非機能要件と secure by design。** Ramu 氏は、パイロットから本番へ進めない原因はここにあると指摘しています。
- **リグレッションは起きる。** Rust 移行では数十件のリグレッションがあり、まだ残っている可能性も認めています。
- **ジュニアの育成は未解決。** Matt 氏は誰もモデルを示せていないと述べ、Ramu 氏は「シニアだけの採用は長期戦略ではない」と述べています。
- **まだ完全には信頼できない。** Olof 氏は、エージェントが書いたコードを現時点で完全に信頼できる段階にはなく、人間によるレビューがボトルネックになると語っています。
- **単に Rust をすすめているわけではない。** 事例は、言語選択ではなくエージェント型 SDLC の変革力の例として紹介されています。

## 9. まとめ

エージェントを使った開発は、1 人のパートタイムの開発者が 3 か月で 43 万行の TypeScript を 130 万行の Rust に置き換えられる水準に達しています。ただし成功の条件は、品質を測る仕組みを先に整えること、成果を明確に定義すること、そして人間が最終責任を持つことでした。

パートナーにとっては、工数ではなく成果を売る方向への転換、forward deployed engineering、特定領域の専門性、スキルへの投資が課題です。Matt 氏が Azure Catalyst について「独自の IP とサービスを組み合わせて顧客の環境を変革できる」と述べたように、Microsoft の基盤にパートナー独自の価値を重ねることを、Matt 氏はパートナーに呼びかけています。
