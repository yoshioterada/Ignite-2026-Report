## 5. 発表内容の詳細

### 5.1 前置き

冒頭で登壇者（Vamshi 氏）は、顧客とパートナーへの感謝を述べます。ストレージは、利用者が依存するサービスであり、常に耐久性が高く、いつでも使えなければならないため、その責任を重く受け止めている、という趣旨です。また、サービスの設計、クラスターの構築・運用、容量管理、エンジニアリング、プロダクトマネジメント、マーケティング、財務など、多くの人の力で成り立っていることにも謝意を示しています。今回は、ここ数年で最も機能追加の多い Ignite の発表になるとも話しています。

### 5.2 Azure Storage の全体像と規模

Azure Storage は、block、object、file のサービスを一つのストレージプラットフォームとして提供します。Azure Disks、Azure Files、Azure NetApp Files、Blob Storage がその構成要素です。AI ワークロードで中心になるのは、data lake の機能を持つ（持たない場合もある）object storage です。ワークロードによっては、ディスク、コンテナーストレージ、ファイルも使われます。データ管理・移行のサービスもあります。

規模については、次の数値が示されました（スループットとトランザクション数は、月間の平均値で、ピーク値ではないとのことです）。

| 項目 | 数値 |
| --- | --- |
| スループット | 1 ペタビット/秒を超える（1.5 ペタビット/秒） |
| 読み書きされるデータ量 | 毎月 400 エクサバイト |
| トランザクション | 毎秒 15 億超 |
| 月間トランザクション | 4 クワドリリオン超 |
| 1 日あたり | 約 130 兆 |

AI ワークロードはこのうち増えている部分だが、まだ最大の割合ではない、と説明されています。Azure や Microsoft のサービスの多くは、このレイヤーにデータを保存していて、Microsoft にとっての長年のファイルシステムでもあります。この規模が、基盤モデルを作る AI ラボ（Microsoft 自身のものとパートナーのもの）の受け入れや、これからのエージェントワークロードの状態管理の下地になっている、という位置づけです。

### 5.3 AI ワークロードがストレージに求めるもの

**学習・ファインチューニング**：基盤モデルの立ち上げには、エクサバイト規模の生データを準備して、巨大な GPU クラスターに供給する必要があります。GPU クラスターは学習データを読むだけでなく、障害からの復旧、モデルの重みの保存、研究者向けの履歴のために、エクサバイト規模のチェックポイントも書き出します。これは主にスループットと容量の課題です。分析ワークロードの数百ギガビットから、単一のワークロードで数十テラビット、さらに数百テラビットまで拡大する必要がありました。

2010 年の GA 時点の設計目標と比べると、現在は、単一のアカウント・単一のリージョンで、当時の **1 万〜10 万倍**（4〜5 桁）で動く顧客がいる、と話されています。さらに 6〜7 桁へ向かっているとのことです。

**推論**：多くの参加者が主に取り組むのは推論で、場合によってはオープンウェイトのモデルを自分のデータでファインチューニングすることもある、という前提です。要件は次のとおりです。

- 企業データの保護（不正・誤アクセスの防止）
- 情報ワーカーに正しく答えるための、最新のコンテキスト
- レイテンシ。チャットやエージェントでは処理の経路上に入るため重要になる

**エージェント（長時間動くワークロード）**：

- 再計算を避ける KV cache が必要。
- エージェントの状態のスナップショットと高速な復元が必要。
- エージェントは自分用や他のエージェントと共有する記憶を持つので、レイテンシ要件に加え、バージョン管理、状態、ロールバック、高速な再読み込みが必要になる。
- 企業に数百万から数十億のエージェントが人間の従業員と並んで存在する状況では、何が起きたかを追跡する必要がある。監査可能性、ツール呼び出しのログ、トレース、リプレイ、判断の理由の診断が求められ、これもデータ量が多い。容量と不変性（immutability）、いわば「証拠の連鎖（chain of custody）」を保つことが課題になる。

こうして増えるデータの管理について、CISO・CIO・CTO から説明を求められたときの助けとして、AI を使ったデータ管理ツールが後半で紹介されます。

### 5.5 Managed Lustre

Azure Managed Lustre は、Lustre の使い慣れた機能を、Azure がデプロイ・スケール管理してくれるサービスです。必要な容量とスループットを伝えれば、残りは Azure が対応します。

- 今回、容量とスループットのスケールが **4〜5 倍**に拡大すると発表されました。
- NVIDIA の DGX Cloud（Azure 上で顧客向けに提供）は、内部で Managed Lustre を使っています。昨年の Ignite でも話題にしており、利用は続いています。
- 今年の前半に ML Perf のベンチマークに公式結果を提出し、パブリッククラウドの並列ファイルシステム（Lustre）の中で、帯域幅が **1 位**になったと説明されています。システムを限界まで追い込んだ結果ではなく、1 位に必要な水準を満たした程度だとも話しています。

### 5.6 Blob Storage とツール

Lustre を使う場合も、データを Blob に動的に tier として出し入れできます。Blob は、スケールの経済性、容量、コスト効率の面で、データの大部分が置かれる場所だからです。

Blob Storage には、REST API の flat namespace と、ファイルシステムの構造を持つ階層型名前空間（hierarchical namespace）があります。後者の上に、Data Lake Storage や、互換性のための NFS、SFTP プロトコルが構築されています。

ツールの整理は次のとおりです。

- 右側（長く存在するもの）：Storage Explorer、AzCopy、SDK。
- 左側（AI ワークロード向けに作り込まれてきたもの）：BlobFuse など。BlobFuse は、Linux のコンテナー、VM、エージェントに Blob のマウントポイントを提供する簡単な構成です。Python のツールチェーン向けにも、Blob との統合があります。BlobFuse の詳細は、推論の部分（5.11）で Saurabh 氏が説明します。

### 5.7 Turbo Tier（プレビュー）

**背景**：Blob Storage には、フラッシュ（SSD）ベースの Premium Blob storage（2019 年から GA）と、HDD ベースの Standard Blob storage（2010 年から）があります。顧客から繰り返し聞かれたのは、Premium は使いたいが、データ全部を置くと高価であり、2 つのアカウントを使い分けてデータを移動する管理が負担だ、という声でした。これはどのハイパースケーラーにも当てはまる状況だと説明されています。「正しいデータをフラッシュに置く作業は、アプリケーションやストレージ管理者ではなくシステムが行うべきではないか」というのが課題設定です。

**Turbo Tier の概要**：

- Premium Blob storage 相当の SSD ベースのストレージを、別アカウントではなく**同じストレージアカウント、同じ名前空間、同じエンドポイント、同じ認証情報**の中の tier として提供する。
- 既存の Hot、Cool、Cold、Archive と同じように扱え、ライフサイクル管理も使える。
- Turbo Tier を有効にすると **Smart Placement** のエンジンが動く。メタデータとすべての書き込みは、まず Turbo Tier に着地する（書いた後に読む可能性が高く、メタデータは素早く引きたいため）。その後は自動的に下の tier へ移し、アクセスされたら上に戻す。エンジンは今後、ワークロードから学習して事前配置を行うなど、改善していける。
- 目標は、超低レイテンシ・高スループットと、コスト効率の両立。

**料金の特徴**：

- 10 PB のワークロードの例で、10 PB すべてをフラッシュ tier に置く場合と比べ、**既定の設定でも 74% 低コスト**。設定を変えればさらに節約できる。
- Turbo Tier では **トランザクション課金をなくした**。変動するトランザクション課金はなく、データ量に応じた一定のスループットを含む形で課金される（発話の一部は聞き取りが不明瞭です）。スループットの費用が見えず、ストレージ料金だけが見えるかもしれない、とも話しています。
- 既存の Premium Blob storage、および他クラウドの競合サービスよりも大幅に安い、と述べています。

**提供状況**：プレビュー中で、サインアップのリンクがあります。Premium Blob storage があるリージョンにはハードウェアがすでに展開されており、GA では、ほぼすべてのリージョンで提供する予定です。既存のストレージアカウントをボタン一つでアップグレードして Turbo 対応にでき、コードや認証情報の変更は不要だと説明されています。AI 以外でも、Databricks や Snowflake などの分析、レイテンシに敏感なワークロードで恩恵が大きい、と話しています。

### 5.8 Turbo Tier の性能テスト（録画デモの説明）

録画された負荷テストの結果が紹介されています（ツール名は発話の表記で「El Bencho」です）。

| テスト | 条件 | 結果 |
| --- | --- | --- |
| 小さい I/O、高 TPS | El Bencho を使用、256 ワーカー（約 25,000 コア） | 単一アカウント・単一リージョンで、ほぼ即座に **1,000 万 IOPS** |
| 高スループット（4 MB の読み取り） | 645 ワーカー（約 50,000 コア強）。リージョンで確保できる計算資源が上限 | **20 テラビット/秒**の読み取りスループット |

グラフの立ち上がりは Pod の起動時間によるもので、その後は安定している、と説明されています。レイテンシは、サーバー側が 1 ミリ秒未満で安定し、計算や HTTP スタックを含むエンドツーエンドでも **P99 が 2 ミリ秒未満**でした。これをさらに短くする取り組みとして、後述の Blob over RDMA が紹介されます。

### 5.9 list blobs、session-based auth、Blob over RDMA

AI ラボが使い、すべての顧客に展開していくものとして、3 つが挙げられました。

1. **list blobs の高速化（本番提供中）**：単一アカウントに 5,000 億の blob があると、1 回 5,000 件ずつの list blobs では時間がかかりすぎる。アーキテクチャを変更し（Apache RO フォーマットと発話。音声認識の都合で表記が確定できません）、毎秒数百万件の blob を返せるようになった。従来は 1 回あたり 5,000 件。
2. **session-based auth（プレビュー）**：Entra ID（発話は "Enter ID"）はデータを守る最良の方法で、使ってほしい。しかし接続ごと・Get Blob や Put Blob ごとの認証のオーバーヘッドが大きい。そこで、セッションベースの認証を作った。これを発行したコンテナーや VM に紐づき、時間制限があり、安全性は保ちながら、スループットとレイテンシが大幅に改善する。
3. **Blob over RDMA（プレビューに入る段階）**：HTTPS ではなく RDMA でデータを転送する。プレビューに向けた結果として、**最大 6 倍高速なデータ転送、クライアント CPU 95% 低減**が示された。続く説明では、レイテンシは最大 88% 低減、CPU は最大 95% 低減とされている。高性能なストレージでは、サーバーだけでなくクライアントも、データの運搬に多くの CPU 時間を使っている。NIC へのオフロードと RDMA の経路で、それを減らす。NVIDIA と緊密に連携して開発している。

### 5.10 NVIDIA による cuObject の紹介（Harish 氏）

Harish 氏は NVIDIA に約 5 年在籍し、cuObject という技術のプロダクトマネージャーだと自己紹介します。

**動機**：NVIDIA 社内の基盤モデル学習チーム（言語モデルだけでなく、視覚言語モデルや、Cosmos のような physical AI 用のモデルを含む）と、外部の大規模顧客からのフィードバックが出発点です。

- 大規模な学習・ファインチューニングでは、数千の GPU から同時にストレージへアクセスする必要がある。5〜10 年前は 1,000 GPU でも多かったが、今は **32,000 GPU** が標準的になった。チェックポイントの書き込みや学習データの読み込みで、これだけの同時アクセスが生じる。
- object storage はこの規模に自然に合う。さらにコモディティなインフラ上に作られ、専用アプライアンスが不要なのでコスト効率が高く、メタデータ操作などの賢さはソフトウェアで実現される。
- NVIDIA は GPU だけでなく RDMA 対応のネットワーク製品でも市場をリードする会社であり、object アクセスに **RDMA による高速化**を持ち込んだ。

**技術の構成**：cuObject は、クライアントライブラリとサーバーライブラリの 2 つで構成されます。約 2 年半〜3 年開発してきており、当初の対象はオンプレミスのプロバイダー（サーバーライブラリを自社ストレージに組み込み、クライアントライブラリは CUDA toolkit に含まれて、各種のプラットフォーム SDK やミドルウェアとリンクする）でした。そのビジョンと技術概要を Azure チームと共有し、一緒に Blob Storage 向けの RDMA サポートを設計しました。サーバー側のロジックは Azure チームが Blob Storage サービスに実装し、RDMA による高速化にはクライアントライブラリを使います。

**動作（Get の例）**：

1. 制御経路（control path）は、従来どおり標準の REST API。
2. アプリケーションは、cuObject のクライアントライブラリでメモリを登録する。
3. その結果として、RDMA 操作の対象となるメモリを記述する ASCII エンコードされた文字列（RDMA トークン）が返る。
4. このトークンをサーバー側に渡すと、サーバーはクライアントのどのメモリに RDMA で書けばよいかを知る。
5. サーバーが、ストレージからクライアントへ RDMA でデータを転送する。

その結果、データ転送は、オペレーティングシステムのスタックや TCP ストリーミングをバイパスして、はるかに高いスループットとごく少ない CPU サイクルで行われます。さらなる改善の余地として、4 GB や 8 GB のような非常に大きなオブジェクトが、複数のストレージノードに分割されて保存されている場合に、並行した RDMA ストリームでクライアントへ返してスループットを上げる案が挙げられています。

**顧客にとっての価値**：Blob RDMA サービスを使うだけで、ある AI ファクトリーで **48% 多くのトークンを生成**できた、と述べています。トークンは顧客の収益に直結するので、同じコスト基盤で収益が 48% 増えるなら使わない理由がない、という訴えです。

Vamshi 氏は、この技術を現在、自社のクラスターで使っており、顧客のオンボードを歓迎する、と補足しています。

### 5.11 推論とエージェント（Saurabh 氏）

**推論のパイプライン**：企業の大量のデータを取り込み、鮮度とセキュリティのために AI 向けのデータに変換する。推論用に、モデルを GPU ノードへ速く読み込む。エージェントはツールを動かしながら企業データを取り出す。パイプライン全体で、モデルのロードのための低レイテンシ・高スループット、企業データのセキュリティ、そしてその規模でのコスト効率が必要です。Turbo Tier は、SSD の性能と HDD の経済性のバランスでこれを実現する、と位置づけられています。

学習と同じ 3 つの経路は推論にもあり、ストレージは企業データとモデルの共通の基盤です。推論向けには、モデルとデータをより速く読み込み、複数の推論ワーカーが互いの作業結果を共有できるようにする統合が、ツール側に入っています。

**Foundry IQ**：Azure Blob Storage は、現時点で Foundry IQ の最大のデータソースで、Foundry IQ がインデックスするデータソースの **95%** がすでに Azure Blob Storage から来ている、と話されています。下位レイヤーと Foundry の双方で、効率化の作業をしている、とのことです。

**BlobFuse**：Azure Blob Storage 用の、Microsoft のオープンソースの仮想ファイルシステム。POSIX 風のアクセスを保つので、AI アプリケーションはインターフェースを変えなくて済みます。キャッシュは 2 種類あります。

- **streaming block cache**：チェックポイントのような大きいデータセット向け。RAM、またはローカルディスク／NVMe を使う。
- **file caching**：小さいファイルをローカルディスクにコピーして使う。企業データを準備する分析パイプラインに向く。

**DAX**：BlobFuse のキャッシュは、ノードローカルです。あるワーカーが Blob から取ったデータは、そのワーカーのローカル NVMe にしか残らず、他のワーカーは再利用できません。そこで、DAX（発話の説明では distributed accelerator for cloud storage）が、各ワーカーノードのローカル NVMe を使った**共有キャッシュ**を提供します。Blob Storage を正式なデータ源として、一度取得したデータを他のワーカーのキャッシュから再利用できるため、毎回 Blob に戻らずに、モデルのロードと推論全体を高速化できます。BlobFuse と DAX は互いを認識するので、アプリケーションは共通の POSIX 風インターフェースで Blob にアクセスしつつ、DAX による再利用の恩恵を受けられます。数万ワーカーへのスケールアウトや、ワーカーが故障して新しいワーカーが立ち上がる場合にも、リモートストレージまで取りに行かず共有キャッシュを使えます。

**エージェント推論と、ストレージの機会**：推論は 1 回で終わる処理ですが、エージェントはコンテキストを推論し、行動し、ツールを呼び、結果を観察して、再度戻るかを判断するという処理を繰り返します。この知能はエージェントのハーネス（harness）にエンコードされており、その実行中に、ランタイムの状態が生まれます。セッションが終わった後や失敗後に、別のエージェントや同じエージェントが戻ってきたときにも、同じ状態を再利用できます。主なパターンは次の 2 つです。

1. **KV cache の再利用**：GPU が高い計算コストで作るコンテキスト内の関係を、再利用して GPU の再計算を省く。
2. **エージェント状態の保存と復旧**：計画や中間ファイルを保存し、セッションをまたいで記憶として使う。サブエージェントへの引き継ぎ、作業の監査、ロールバックにも使える。

**ログ**：エージェントが作業を終えたら、実行中に生成されたすべてのログを保存して監査できる必要があります。Blob Storage には、セキュリティ、不変性、耐久性、tier の機能がすでにあります。ログを追記し続け、エージェント自身が変更できないよう不変にし、長期間たまってもコストを抑えられる、という説明です。

**コンテキストキャッシュ（KV cache）の図**：推論クラスターが、2 人のユーザーから同じ共有プレフィックスを受け取る例です。

1. 最初に、このコンテキストは Blob Storage と、DAX による共有 NVMe 層の両方に書き込まれる。
2. 2 回目のリクエストでコンテキストが追記されても、大部分は以前と同じなので、そのコンテキストを検索できる。
3. 共有 NVMe クラスターにあれば素早く戻せ、なければ Blob Storage から戻せる。
4. 永続層があるので、**コンテキストを数日〜数週間**保持できる。長時間動くエージェントや、長い間隔をあけて戻るエージェントでも、GPU でコンテキストを再計算し続けなくてよい。

このデモはここでは行わず、前日に Ong 氏（音声認識の都合で表記が確定できません）が話した what's new and what's next のセッションで見るよう案内されています。

**エージェントのファイルシステム**：エージェントがファイルシステムを持つと、エージェントと人間が協働しやすくなる、という考えです。LangChain との強い協業があり、LangChain を使う場合は、Azure Blob のバックエンドを選べます。これは Azure Blob Storage アカウントを、deep agents のインターフェースで使える永続的なファイルシステムとして見せるもので、ファイルの一覧、検索、必要に応じたロールバックができます。

LangChain はハーネスですが、エージェントは作業のために実行環境も立ち上げます。Azure Container App Sandboxes は、エージェントの隔離された実行環境を提供します。Blob Storage は、ハーネスにファイルシステムとして接続されるだけでなく、この実行環境にも接続され、実行環境で行った作業を Blob Storage に保存できます。選択肢は 2 つあります。

- Microsoft が管理する Blob Storage アカウント（裏側は Blob Storage）を使う。
- 自分の Blob Storage アカウントを接続する。

Blob の上に作られているため、セキュリティと RBAC、そして長時間動くエージェントのロールバック用のバージョニングが使えます。

**フィードバックの依頼**：次世代のエージェント向けファイルシステムを検討中で、すべてのエージェントランタイムに単一の名前空間を提供できるかを探っている、と説明されています。実現すれば、より速く動き、永続的で、統制しやすく、作業の透明性、共有、記憶管理に優れたエージェントを可能にする、とのことです。QR コードのリンクで、何を作りたいかの意見を求めています。

**エージェントへの安全なアクセス**：

- shared access signature（SAS）を拡張して、**エージェントの ID またはユーザーの ID を持たせる**。その ID でアクセス範囲を、特定のプレフィックスに限定できる。これにより、特定のディレクトリへのアクセスや書き込みを禁止できる。
- session-based auth（プレビュー）：単一のエージェントセッションの間は、繰り返し認証しなくて済み、エージェント操作のレイテンシがさらに下がる。

### 5.12 AI を活用したデータ管理（Vamshi 氏）

時間を超過していたため、駆け足で紹介されました。構成は、**Mover**（データ移行）、**Storage Discovery**（データ分析）、**Storage Actions**（アクション）の 3 つです。

- **Blob access points**：今回の大きな発表の一つで、過去のセッションでも触れたもの。データを移行しなくても、主要な ISV から Azure のあらゆるサービスまで、データを接続できる。**パブリックエンドポイントでは GA、プライベートエンドポイントではプレビュー**。
- **Mover**：引き続き改善されており、特に数ペタバイト規模の大規模な用途向け。
- **Storage Discovery**：エクサバイト規模で動いており、数百ペタバイトからエクサバイトのデータを持つ顧客を支援している。単一の画面で確認できる。新機能の **capacity details** で、最終アクセス時刻でデータを区分でき、削減してコストを節約できるデータが見つかる。また、コンテナーをダブルクリックして中を見られる（コンテナーが実質的にファイルシステムとして扱われる場合に重要、という説明）。
- **Storage Actions**：サーバーレスの環境。ルールを作るビジュアルビルダーがあり、新たに **mock run** が追加された。顧客から「実行ボタンを押すのが怖い」という声があったためで、実際に何が起きるかを事前に確認してから、アクションを開始できる。まだ発表していない機能もあり、来年の第 1 四半期に、この actions の枠組みをより柔軟にすると話している（時期の発話は聞き取りが不明瞭です）。

## 7. 注意点・発表者の気付き

- **Turbo Tier はプレビュー段階。** サインアップが必要で、GA は「ほぼすべてのリージョン」の予定です。
- **session-based auth と Blob over RDMA も、プレビューまたはプレビューに入る段階。** list blobs の高速化は本番提供中です。
- **Blob access points は、パブリックエンドポイントでは GA、プライベートエンドポイントではプレビュー。**
- **認証のオーバーヘッドは大きな要素になりうる。** Entra ID を使うことは推奨しつつ、大量のオペレーションでは接続ごとの認証コストが問題になるため、session-based auth が用意された、という説明です。
- **クライアント側の CPU も性能のボトルネックになる。** サーバーだけでなく、データの運搬にクライアント CPU が使われている点は、あまり知られていないとして触れられています。
- **BlobFuse のキャッシュはノードローカル。** ワーカー間で再利用するには DAX が必要になります。
- **Storage Actions を実行するのが怖い人向けに mock run がある。** 顧客の声から生まれた機能です。
- 発表では、Turbo Tier の料金の詳細な単価、Blob over RDMA の GA 時期、DAX の提供状況（プレビューか GA か）は説明されていません。

## 8. 利用者にとっての利点

発表で語られた効果・成果は次のとおりです。

- **コスト**：10 PB の例で、全量をフラッシュ tier に置くより既定設定で 74% 低コスト。Turbo Tier ではトランザクション課金がない。
- **運用の簡素化**：別アカウントへのデータ移動や認証情報・コードの変更が不要で、同一アカウント内の tier として、ボタン一つで既存アカウントをアップグレードできる。
- **性能**：1,000 万 IOPS、20 テラビット/秒の読み取り、P99 が 2 ミリ秒未満（テスト結果）。分析（Databricks、Snowflake など）やレイテンシに敏感なワークロードにも有効。
- **Blob over RDMA**：最大 6 倍のデータ転送、クライアント CPU 95% 削減、レイテンシ最大 88% 低減。NVIDIA の説明では、ある AI ファクトリーで 48% 多くのトークンを生成できた。
- **list blobs**：毎秒数百万件（従来は 5,000 件ずつ）。
- **推論の高速化**：DAX の共有キャッシュにより、モデルのロードとスケールアウト、ワーカー故障時の復旧が速くなる。KV cache を数日〜数週間保持して、GPU の再計算を省ける。
- **統制と監査**：不変のログ、RBAC、バージョニング、エージェント ID 付きの SAS、Storage Discovery と Storage Actions（mock run）による管理。
- **Foundry IQ**：データソースの 95% が Azure Blob Storage 由来で、効率化が進められている。

なお、顧客名を挙げた導入事例は、NVIDIA の DGX Cloud が Managed Lustre を使っている点を除き、このセッションでは紹介されていません。

## 9. まとめ

AI のためのストレージは、学習ではスループットと容量、推論ではセキュリティ・鮮度・レイテンシ、エージェントでは状態管理と監査と、求められるものが変わります。Azure Storage は block、object、file の 3 種類を一つのプラットフォームで提供し、月に 400 エクサバイトを扱う規模を、AI ラボとの取り組みから得た機能として顧客に届けようとしています。

今回の主な発表は次のとおりです。

1. **Turbo Tier**（プレビュー）：同じアカウントの SSD ベース tier。チェックボックス一つで有効化し、Smart Placement が配置を管理する。
2. **Blob over RDMA**（NVIDIA の cuObject と共同）：クライアント CPU を大きく減らし、転送を高速化する。
3. **DAX と BlobFuse**：ワーカー間のキャッシュ共有で、推論のモデルロードや KV cache 再利用を高速化する。
4. **エージェント向け**：LangChain の Azure Blob バックエンド、Azure Container App Sandboxes との接続、エージェント ID 付きの SAS、session-based auth。
5. **データ管理**：Blob access points、Storage Discovery の capacity details、Storage Actions の mock run。
