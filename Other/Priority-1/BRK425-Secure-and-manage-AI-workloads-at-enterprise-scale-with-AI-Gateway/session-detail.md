# BRK425 Secure and manage AI workloads at enterprise scale with AI Gateway

## 1. はじめに

このセッションは、Azure AI Gateway を使って、企業内のモデル、MCP サーバー、エージェントへのアクセスを 1 か所で保護・統制・監視する方法を紹介するものです。発表の冒頭で、Azure AI Gateway が**前日に一般提供（GA）になった**ことが発表されています。

構成は 3 部です。最初に Komatsu の Raghu Balam 氏が、社内で AI を広げる際の課題と、共通の AI 基盤を作った経緯を話します。次に Microsoft の 2 人の Principal Product Manager が、ゲートウェイのポータルを使ったデモを続けて見せます。最後に Raghu 氏が戻り、ゲートウェイを導入して得られた 4 つの利点を説明します。デモでは、モデルの登録、Entra による認証、MCP サーバーの登録、429 エラーへの対処、ログに混入したシークレットの遮断、複数の MCP サーバーの束ね方、自動モデル選択までが、一連の流れで紹介されます。

発表者は、AI の利用が組織の中で、さまざまなモデル、ツール、エージェントのハーネスにまたがって分断したまま広がっていると指摘します。そうなると統制が難しくなり、セキュリティ、コスト、コンプライアンス、データレジデンシー、プライバシー、ガバナンスなどのリスクが生まれます。

## 5. 発表内容の詳細

### 5.1 課題と Komatsu の事例

Mike 氏は、チームごとの草の根の AI 導入が、断片化したモデル、ツール、エージェントのハーネス、独自のエージェントアプリケーションを生み、手に負えなくなりつつあると述べました。リスクの例として、AI を使ったサイバー攻撃に対するセキュリティ、コストが膨らむ問題、コンプライアンス、データレジデンシー、プライバシー、ガバナンスが挙がっています。

Raghu 氏は、Komatsu（鉱山・建設機械を製造するグローバル企業）で約 8 年勤務するクラウドソリューション・エンタープライズアプリケーション開発のマネージャーと自己紹介しました。各アプリケーションチームから、次の同じ質問が繰り返し出ていたとのことです。

- AI モデルにどう接続するか
- セキュリティをどう管理するか
- アクセスをどう制御するか
- 利用状況とコストをどう監視するか

チームごとに答えていてはスケールせず、新しいモデルが次々に出る状況ではなおさらです。そこで、アプリケーションごとに基盤を作り直すのではなく、「一度作って承認済みのアプリケーションに使わせる」方針に切り替え、**AI Gateway を中心に据えた共有のエンタープライズ AI プラットフォーム**を作りました。各チームは、アクセス、クォータ、利用状況の可視性が組み込まれた 1 本の統制された経路で接続します。Raghu 氏は、これは AI アプリケーションではなく、ビジネスのアイデアをゼロから始めずに AI ソリューションにできる、安全で再利用可能な基盤だと説明しています。

### 5.2 Azure AI Gateway の概要

Azure AI Gateway は、クライアント（エージェント、エージェントのハーネス、ユーザー、チャットボットなど）からの呼び出しを、AI のバックエンドに仲介するゲートウェイです。バックエンドには次のものが含まれると説明されました。

- さまざまなプロバイダーのモデル：OpenAI の GPT モデル（Microsoft Foundry 上など）、AWS Bedrock、Google Vertex のモデル、セルフホストのモデルなど
- MCP サーバー：MCP サーバー自体、MCP サーバーに変換したい REST API、SaaS サービスを表すコネクタ

すべてのトラフィックがゲートウェイを通るため、オブザーバビリティ、各種ポリシーによるガバナンス、アプリケーションの認証・認可などをここで適用できます。

GA に合わせて語られた点は次のとおりです。

- **自動スケーリング**に対応した。ユニットを手動でスケールアウトする必要はなく、エージェントアプリケーションやワークロードの需要に合わせて自動でスケールする。
- GA は **16 の Azure リージョン**で利用でき、さらに追加される。
- **プライベート接続**に対応している。VNet 内のバックエンドに対するアウトバウンドの VNet 統合と、プライベートなインバウンドが使える。

専用のポータルがあり、プラットフォームチームだけでなく開発者向けにも作られていると説明されています。

### 5.3 モデルの追加、エイリアス、Entra 認証（デモ 1）

ポータルでは、Microsoft Foundry のリソースから、選択したサブスクリプション内のモデルをインポートできます。デモでは、「Caldova Pharmaceuticals」という製薬会社を想定したサンプルが使われ（社名の綴りは音声認識の都合で確定できません）、East US、Sweden Central、West US 3 にあるリソースの GPT モデル、Grok、埋め込みモデルなどが対象でした。ゲートウェイは **マネージド ID** でこれらのモデルに認証します。

ここで重要な機能が**エイリアス**です。エイリアスは「クライアントに見せるモデル名」で、クライアントはバックエンドのモデルではなくエイリアスを呼び出します。インポート時にエイリアスが自動で作られるので、モデルはすぐに呼び出せます。

カタログから GPT 6.1（East US）を選ぶと、モデルの詳細、エージェントアプリケーションでの使い方、テスト機能が表示されます。Chat Completions と Responses API をサポートし、認証は API キーで行えます。ただし、本番環境で API キーを使うことに抵抗のある組織が多いため、ゲートウェイは **Microsoft Entra** による保護に対応しています。ユーザー、エージェント、アプリケーションが Entra のトークンでゲートウェイに認証でき、どのアセットにアクセスできるかを制御できます。すべてのモデルとツールへのアクセスを与えることも、特定のモデルや特定のツールだけに絞ることもできます。ゲートウェイからバックエンドへの Entra 認証（先のマネージド ID）にも対応し、ツール向けの On-Behalf-Of フローなどの高度な設定もあります。

### 5.4 GitHub Copilot でエージェントを作り、MCP サーバーを追加する（デモ 2）

次に Facundo 氏が、ゲートウェイを使う最も簡単な方法の 1 つとして、製品に付属する**プラグイン**を紹介しました。コーディングエージェントからゲートウェイに接続し、使えるアセットを探索できます。管理者権限があれば、ゲートウェイの管理もできます。

次に、ゲートウェイの MCP サーバーを作りました。

- MCP サーバーの名前を付け、対応する MCP 仕様のバージョンを選ぶ（ゲートウェイは複数の MCP 仕様をサポートする）。
- バックエンドとして、他の MCP サーバー、OpenAPI 仕様、Azure にデプロイ済みのリソース（APIM や API Center の API）、SaaS ソースへのコネクタなどを追加できる。
- 今回は、すでにある MCP サーバーの URL を指定し、API キー認証で接続した。より高度な接続オプションもある。

### 5.5 ルーティング機能（エイリアスの詳細）

429 エラーの対処のため、Mike 氏が、ゲートウェイのモデルルーティング機能を説明しました。エイリアスの特徴は次のとおりです。

| 機能 | 説明 |
| ---- | ---- |
| クライアント向けモデル名の分離 | バックエンドのモデルを、クライアントを変更せずに差し替えられる（新モデルの登場時など） |
| モデルのプール | 複数のバックエンドモデルを、ルーティング条件付きの 1 つのモデルとして公開できる |
| 自動モデル選択（プレビュー） | プロンプトと目的に基づいて、リクエストごとにモデルを自動選択する。プロバイダーをまたいで動作し、Microsoft Foundry のルーターで動いている |
| 優先度（priority）と重み（weight） | 優先度は、事前確保した容量とグローバルなバックエンドの使い分けなどに使う。重みは A/B テストや、プロバイダー側の容量比に応じた振り分けなどに使う |
| セッションアフィニティ | セッションを特定のバックエンドモデルに固定し、キャッシュされたトークンを再利用して、レイテンシとコストを下げる |
| 条件付き包含 | リクエストのパラメータに基づいて、バックエンドを含める・除外する（例：ヨーロッパで動くエージェントでは、非ヨーロッパのデプロイを隠す） |
| フェイルオーバー | 失敗の条件を満たしたバックエンドを、一定時間、循環から外す |

### 5.6 ポリシーの階層、Agent 365 との連携

Facundo 氏は、ゲートウェイが企業のポリシーを適用する場所になると説明しました。その利点として、エージェントごとにこの詳細を実装しなくて済む点が挙げられています。ポリシーは次のような分類で提供されます。

| 分類 | 内容 |
| ---- | ---- |
| 消費（consumption） | コスト上限、トークン上限、リクエスト上限など。消費量を制限する |
| セキュリティと安全性 | コンテンツ セーフティ、ツールの脅威保護（tool threat protection）など。ツールの出力を制御する（ほかに「API フィルター」と聞こえる語もありますが、音声認識の都合で確定できません） |
| 拡張 | 例として **agent hooks**。ツールが呼ばれる前、ツールが呼ばれて結果がエージェントに届く前などの介入ポイントを指定し、任意のコードを実行できる。ゲートウェイがその処理を通すかどうかも決められる |

また、ポリシーは**階層の適切なレベル**に適用できます。ゲートウェイ上のすべてのアセットに高レベルのポリシーを適用することも、特定のエイリアスに固有のトークンレート制限を適用することも、特定のバックエンドにポリシーを設定することもできます（例として「GPT 6.1 に会社として 2,000 ドル以上使わせたくない」）。リクエストは、すべてのポリシーを満たして成功する必要があります。

さらに、組織が **Agent 365** をデプロイしている場合、ゲートウェイは Agent 365 で作成したポリシーの実行ポイントにもなります。例として、すべてのツール呼び出しを Defender に通してシークレットや悪意のあるコードが混入していないか確認する、ツールの出力をすべて Purview に通して社内の情報が外に出ないようにする、といったポリシーが挙げられました。一度定義すれば、ゲートウェイが強制します。

### 5.7 Federated MCP サーバー（デモ 5）

MCP サーバーを 1 つ接続するだけでは、エージェントは大したことができません。かといって MCP サーバーを増やすと、2 つの問題が起きると説明されています。

1. **コンテキスト管理**：バックエンドが増えるとツールが増え、コンテキストウィンドウを消費し、コストが上がる。
2. **誤ったツールを選ぶ可能性**：ツールが多いほど、エージェントがタスクに合わないツールを選ぶ確率が上がる。

そこで、Azure AI Gateway では **Federated MCP サーバー**を実装しました。1 つの MCP サーバーを、それぞれ固有の設定を持つ複数のバックエンドにつなぎ、各バックエンドからどのツールを公開するかを選べます。

### 5.8 コスト管理と自動モデル選択

詳細は、翌日 17:30 のシアターセッションで扱うとして深入りしませんでしたが、Mike 氏はコスト管理を 3 つの区分で説明しました。

1. 監視：コストと消費量を把握して帰属させる
2. 制御：アクセスと予算を強制する
3. 最適化：主にモデルルーティングによる最適化。先に示した決定論的なルーティングと、自動モデル選択がある

**自動モデル選択**では、目的を balance、quality、cost から選べます。呼び出し側がその設定を上書きできるようにするかも選べます。

### 5.9 モニタリングと Foundry との連携

- ダッシュボードで、推定支出（ドル）とトークン消費量を全モデルで確認できる。
- トレースで、バックエンドモデルへの解決や自動モデル選択の詳細を確認できる。
- コストの帰属を、特定のモデルやエイリアス、キー、Entra ユーザー単位で見られる（例：「このエイリアスまたはバックエンドモデルが推定支出の 80% を占める」）。
- **OpenTelemetry** に対応し、メトリクスやトレースを任意の OpenTelemetry の送信先に出せる。Application Insights を選べば、ダッシュボードが組み込みで使える。
- **Microsoft Foundry** との連携：Foundry でエージェントを作る場合、ハブ&スポーク構成を勧めている。モデル用のハブ Foundry リソースを作り、そのモデルをゲートウェイにインポートし、チームごとのスポーク Foundry リソースに、ゲートウェイから必要なモデルだけを追加する。この機能は新しい Azure AI Gateway に対応済みと述べられました。

### 5.10 Komatsu による 4 つの利点

Raghu 氏は、まず空港のセキュリティのたとえを使いました。どの航空会社の乗客も保安検査場を通るのと同じように、クラウドアプリケーション、API、エージェントのどれもが、1 本の統制された経路を通ります。ゲートウェイは、ID の確認、セキュリティポリシーとクォータの適用、すべてのリクエストのログと監視、適切なモデルへのルーティングを行います。プライベートとパブリックの両方のアクセスに対応し、モデルとの接続はプライベートのままなので、データが組織の外に出ない点が最大の利点だと述べています。新しいモデルが出たらゲートウェイの背後に追加するだけで、作り直しやロックインは不要だとのことです。

利点として 4 点が語られました。

1. **AI のオンボーディングの高速化**：以前は、チームがアプリケーションごとに AI のインフラを作っていた。今は、チームが「アプリケーション ID、必要なモデル、使い方（usage）」の 3 つを伝えれば、統制された 1 つのエンドポイントを受け取り、初日から開発を始められる。以前は行き来に時間がかかったが、簡単で再現可能なプロセスになった。
2. **安全な AI アクセス**：以前は各チームが自分でキーとモデルへのアクセスを管理していたが、今は 1 つの統制された API で、アプリケーション ID を持ち込み、ゲートウェイが「誰が」「どれだけ」使えるかを決める。キーの混乱やポリシーのパズルがなくなる。
3. **セルフサービスのクォータ管理**：チームは自分の利用状況を確認でき、上限に達する前にアラートを受け取り、標準的なプロセスで追加のクォータを依頼できる。
4. **コストの透明性とチャージバック**：トークン消費が重要な AI の世界で、チームごとのトークン使用量とコストを追跡できる。チームから「AI にいくら使っているか」と聞かれたときに示し、適切な事業部門にチャージバックできる。

Raghu 氏の一番のメッセージは「企業として AI のコストを、中央で制御して管理する」ことでした。

## 6. デモ・手順

このセッションには、ゲートウェイのポータルと GitHub Copilot を使ったデモがあります。登壇者が途中で「Pause this」「let me speed up this a bit」と話しており、録画を再生しながら説明している可能性がありますが、発話からはライブか録画かを断定できません。**画面の細部は音声からは確認できません**。以下は、語られた順序に沿った記録です。

### 6.1 ポータルでのモデル追加と Entra 認証（Mike 氏）

1. ポータルで、すでに Anthropic のモデルが登録されているゲートウェイに、Microsoft Foundry のモデルを追加する。
2. 選択したサブスクリプション内の Foundry リソース（East US、Sweden Central、West US 3）から、GPT モデルや Grok、埋め込みモデルなどをインポートする。インポートによりエイリアスも自動作成される。
3. GPT 6.1（East US）をカタログで開き、詳細と使い方を確認する。API キーでテストし、モデルから応答が返ることを確認する。
4. Entra 認証を有効にするため、ゲートウェイのポータルの access ページで、ロールの割り当てを選ぶ。
5. 自分自身の ID を選ぶ。プリセットから、コントロールプレーンまたはデータプレーンの権限を選べる。今回は、すでにオーナーとしてコントロールプレーンの権限があるため、データプレーンのみを付与し、すべてのモデルとすべてのツールへのアクセスを与える。
6. テスト画面で Entra ID を使ってモデルを呼び出し、GPT のモデルから成功の応答が返る。

### 6.2 GitHub Copilot でエージェントを作成（Facundo 氏）

1. ゲートウェイのポータルでカタログを開くと、AI コーディングエージェントを使うことを勧めるセクションがあり、コピーできるプロンプトが表示される。プロンプトの内容は、Azure のリポジトリからマーケットプレース プラグインを追加してインストールするもの。
2. GitHub Copilot にそのプロンプトを貼り付ける（プラグインはすでにインストール済み）。Azure アカウントでログイン済みなので、アセットの取得に必要なものが揃っている。
3. Copilot が、この時点では MCP サーバーは登録されていないこと、フロンティアモデルや、よりコスト効率の良いモデル、埋め込みモデルがあることを返す。
4. 「オンコール対応のサポートエンジニアを支援するエージェントを作って」と依頼する。モデルは 1 つ指定し、ツールはまだ指定しない。Copilot がエージェントを作成する。
5. 作成されたエージェントに「何ができる？」と尋ねる。プロンプトに応答するだけのエージェントである。

### 6.3 MCP サーバーの作成と動作確認

1. ゲートウェイで MCP サーバーを追加し、名前を付ける。エンジニアが、アクティブなインシデントの有無やバックエンドのログを確認できるサーバーである。
2. MCP 仕様のバージョンを選ぶ。
3. バックエンドとして、既存の MCP サーバーの URL を指定し、API キーの認証情報を渡して作成する。
4. 作成後、ゲートウェイのプレイグラウンド（詳細ページのテスト）で接続を開始し、ツールの一覧を取得する。接続に成功し、feature flags の相関（correlate feature flags）、get active incidents、get audit logs などのツールが表示される。
5. get active incidents を実行すると、レイテンシに関連したインシデントが 1 件返る（e コマース サイトの checkout API サービスに影響）。
6. Copilot に、エージェントをこの MCP サーバーを使うように更新するよう依頼する。Facundo 氏は、Copilot がゲートウェイ用のスキルを使ってアセットの探索や接続方法を判断していると説明している。Copilot はエージェントを編集してテストし、プレイグラウンドと同じインシデントが 1 件あることを確認する。
7. ターミナルでエージェントを実行する。「現在アクティブなインシデントは？」と尋ねると get active incidents が呼ばれ、プレイグラウンドと同じ結果が返る。
8. 「レイテンシの原因は？」と尋ねると、correlate feature flags と query metrics などのツールが呼ばれた後、**429（リクエスト過多）エラー**が返る。

### 6.4 429 エラーの原因調査とエイリアスによる解決

1. ゲートウェイのトレースを開く。ゲートウェイではトークンレート制限のポリシーが評価されていたが、そのポリシーは成功しており、原因ではない。エラーは、転送先のバックエンドモデルから返されたものだった。
2. エージェントが多くのツールを一度に使い、大量のコンテキストをモデルに返したために、バックエンドモデルのクォータを使い切ったと説明された。
3. Mike 氏が、モデルページでエイリアスを追加する。名前は「OpenAI latest」。自動モデル選択は、後で扱うので無効のままにする。
4. エイリアスに含めるモデルとして、リージョン（Sweden Central、East US、West US 3）にデプロイした GPT 6.1 のモデルを複数選び、さらに GPT 6 Luna を加える（GPT 6.1 の容量が尽きた場合のフェイルオーバー先）。
5. セッションアフィニティは CEL 式で、セッション ID を取り出す方法を定義する（ハーネスごとにヘッダーなどが異なるため、標準の式が用意されていて、カスタマイズできる）。
6. 優先度と重み：すべてのモデルは優先度 0、重み 1（均等に配分）のまま、Luna だけを優先度 1 にする。優先度 0 のモデルがどれも使えない場合にのみ Luna が呼ばれる。
7. ルーティングオプション（ルールの優先順位）は、既定のままにする。
8. フェイルオーバールールを追加する。複数の条件を追加でき、標準の CEL 式として「400〜600 のレスポンスコードは失敗」が用意されている。2 回リトライし、3 回連続で失敗したバックエンドは 20 秒間、循環から除外する。
9. Facundo 氏が、Copilot にバックエンドのモデルを「OpenAI latest」に切り替えるよう依頼し、エージェントを再実行する。
10. 同じ質問（アクティブなインシデント）の後、3 つのツール呼び出しがすべて成功し、回答が生成される。「engine」（音声認識の都合で表記が確定できません）が 2,000 ミリ秒でタイムアウトしているかもしれない、という提案が返った。

### 6.5 ログ内のシークレットの遮断

1. 上記の処理中、エージェントがログを読んだ際に、シークレットや PII が含まれていた。モデル（GPT-6 と話者が述べていたもの）は賢く、シークレットを使わなかったが、別のモデルでも同じとは限らない、と Facundo 氏は述べた。
2. 作成した「Incident Commander」の MCP サーバーに接続し、ログ取得のツール（tail logs）を、サービス名 checkout API で実行する。
3. 接続文字列などは一部が伏せられていたが、GitHub のトークンがログに含まれていた。開発者の中に、正しく扱っていない人がいる、という指摘。
4. MCP サーバーに新しいポリシーを追加する。ポリシーの一覧から **Agent 365 tool threat protection** を選ぶ（管理者が設定したチェックを継承できる）。介入ポイントは、ツールが呼ばれて結果がエージェントに届く前（after tool invocation）を選ぶ。
5. エージェントを同じ質問で再実行し、最新の checkout API のログを尋ねる。エージェントはシークレットを受け取らず、ゲートウェイが結果を保留して、エージェントにはエラーが返る。**シークレットはエージェントに届かなかった。**

### 6.6 Federated MCP サーバーの作成

1. 新しい MCP サーバー「on-call responder」を作る。オンコール中のエンジニア支援用。
2. バックエンドを 2 つ追加する。1 つ目は、インシデント、ログ、運用情報にアクセスする既存のもの。ここで **namespace** を指定し、そのバックエンドのツール名の先頭にプレフィックスを付けて、どのバックエンドのツールか分かるようにする。
3. 2 つ目として CRM 情報の MCP サーバーを追加する。顧客データを含むため、キーではなく、利用者本人の ID でアクセスする必要がある。そのため、認証方式に OAuth を選び、Entra の On-Behalf-Of を使う。
4. Entra On-Behalf-Of のシナリオとして、(a) ユーザーがゲートウェイ経由で MCP サーバーに接続し自分の資格情報を渡す、(b) エージェントが自分自身として動く、(c) エージェントがユーザーの代わりに動く、の 3 つが挙げられた。ゲートウェイでこれらを使える。
5. 公開するツールを設定する。CRM のバックエンドからはすべてのツール、もう一方のバックエンドからは get active incidents と get audit logs の 2 つだけを選ぶ。これにより、エージェントに必要なツールだけを持つ MCP サーバーを作れる。

### 6.7 自動モデル選択とモニタリング

1. 「customer support agent」というエイリアスを作り、自動モデル選択を有効にする。
2. 目的（balance、quality、cost）から選び、呼び出し側による目的とモデル一覧の上書きを許可する。
3. モデルとして GPT 系のモデル（Sol、Luna）と DeepSeek を選ぶ（DeepSeek は「最もコスト効率が良いと思われる」ため追加と説明）。すべて優先度 0 のグループに入れる。
4. 自動モデル選択を追加したことでルーティングオプションが広がる。どの設定を優先させるかを選べる。例として、「全優先度グループから最適なモデルを選ぶ」か、「最高優先度のグループに絞ってから最適なモデルを選ぶ」かが挙げられた。ここでは選択肢の 3 番目の設定を選び（内容は音声からは確認できません）、フェイルオーバーは維持する。
5. テスト画面で「次のレビューの感情を分類して」と入力すると、「ネガティブ」と返り、選ばれたのは Luna（単純なプロンプトなので、よりコスト効率の良いモデル）だった。
6. 呼び出し側として、より難しいタスク向けに quality を優先し、プールの中のいくつかのモデルに絞ることもできる。
7. ダッシュボードで、推定支出とトークン消費、トレース、コストの帰属を確認する。

## 7. 注意点・発表者の気付き

- 429 エラーの原因は、ゲートウェイのレート制限ポリシーではなく、バックエンドのモデルのクォータ消費でした。エージェントが多くのツールを一度に呼び、大量のコンテキストをモデルに返したことが原因と説明されています。トレースで、どこで失敗したかを切り分けられる点が、ゲートウェイの強みとして示されました。
- ログに GitHub トークンなどのシークレットや PII が含まれるケースが実際にあり、エージェントがそれらのデータにアクセスできてしまう点が懸念として語られました。モデルによっては、シークレットを使ってしまう可能性があります。
- MCP サーバーを増やすと、コンテキストの消費、コストの上昇、誤ったツールの選択が起きやすくなります。
- 顧客データを持つ MCP サーバーでは、API キーではなく、利用者本人の ID（Entra On-Behalf-Of）でアクセスすべきだとして、デモでは OAuth を選びました。
- 自動モデル選択は**プレビュー**です。ルーティングオプション（優先度グループと自動選択の順序）は、組織が優先順位を決められます。
- デモ中、MCP サーバーのツール設定などで操作をやり直す場面があり、登壇者は一部を早送りして進めたと述べています。

## 8. 利用者にとっての利点

発表で語られた利点は、主に Komatsu の事例と機能説明です。

| 観点 | 語られた内容 |
| ---- | ---- |
| オンボーディング | アプリケーション ID、必要なモデル、使い方を伝えれば、統制されたエンドポイントを受け取り、初日から開発できる |
| セキュリティ | 1 つの統制された API で、Entra ID により誰がどのモデル・ツールを使えるかを中央で制御。キーの乱立を避ける |
| データの保護 | モデルとの接続がプライベートで、データが組織の外に出ない（Komatsu） |
| クォータ | チームが自分の利用状況を見られ、上限前にアラートを受け取り、標準のプロセスで追加を依頼できる |
| コスト | チーム別のトークン使用量とコストの追跡、チャージバック。ダッシュボードで推定支出を確認 |
| 柔軟性 | 新しいモデルはゲートウェイの背後に追加するだけで、作り直しやロックインが不要。エイリアスで、クライアントを変えずにモデルを入れ替えられる |
| 信頼性 | フェイルオーバー、優先度・重みによるルーティング、セッションアフィニティ |

## 9. まとめ

Azure AI Gateway は、クライアントと AI のバックエンド（モデルと MCP サーバー）の間に置く統制の層で、前日に GA となり、自動スケーリング、16 リージョン、プライベート接続に対応しています。デモでは、Foundry のモデルのインポート、Entra による認証、エイリアスによるルーティングとフェイルオーバー、Agent 365 のツール脅威保護によるシークレットの遮断、Federated MCP サーバー、自動モデル選択（プレビュー）、ダッシュボードによるコストの帰属までを一通り示しました。Komatsu は、この仕組みで共通の AI 基盤を作り、オンボーディング、セキュリティ、クォータ、コストの透明性を改善した事例を紹介しています。

発表の最後には、QR コードから Azure AI Gateway を無料で始められること、さらに深く知るために、高度なルーティングとコスト帰属に関するセッション、MCP サーバーの運用のスケーリングに関するセッションを勧めていることが案内されました（なお、コスト管理とルーティングについては、発表の途中で、翌日 17:30 の専用シアターセッションがあると案内されています）。
