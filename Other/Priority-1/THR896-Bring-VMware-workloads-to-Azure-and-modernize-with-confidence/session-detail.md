# THR896 Bring VMware workloads to Azure and modernize with confidence

## 1. はじめに

このセッションは、VMware を使っているお客様に向けた 25 分のシアターセッションです。Broadcom による買収後のライセンス変更をきっかけに、多くの組織が VMware の資産をどうするかを判断する局面にあります。発表は、Azure にはその移行の各段階に応じた選択肢が用意されていること、そしてどの選択肢でも Azure の AI やデータ、セキュリティの各サービスにつなげられることを説明しています。

ポイントは「すべてを一度に動かす必要はない」「ワークロードごとに答えが違う」という考え方です。AVS、Nutanix、Azure Local、Azure のネイティブサービスという 4 つの選択肢、移行計画を支援する Catalyst、SQL Server や Oracle などのデータ層の扱い、AI 活用への橋渡しが順に紹介されます。

> 注意：このセッションは、スライドと口頭の説明が中心です。画面を使ったデモは行われていません。

## 3. 何に関する発表か

テーマは、VMware 環境を持つお客様が Azure でどのような道筋をたどれるかです。背景として、発表では次の点が挙げられています。

## 4. 発表者が伝えたいメッセージ

発表者は、次の 3 点を軸に話しています。

1. **最初の判断は「長期的に Broadcom のライセンス保有者であり続けるかどうか」。** 登壇者は、ライセンス変更を受けて、お客様が自分のワークロードとアプリケーションの今後を考え直したと説明しています。この判断のあとは、「残る」か「どこへ行くか」という比較的わかりやすい選択になる、という見方です。
2. **すべてを一度に動かす必要はなく、ワークロードごとに考える。** モダナイズ（作り直し）する準備ができているものと、そうでないものがあります。ライセンス変更の影響を受けたからといって、そのアプリケーションが事業にとって重要でなくなるわけではありません。何を守り、何を残し、何を改善し、どんな成果を求めるかを決めることが出発点です。「万能の答えはない」と繰り返されています。
3. **どの経路で Azure に来ても、Azure の AI・データ・セキュリティとつながる。** データをクラウドに置くことが AI 活用の前提であり、Azure 上であれば、アイデンティティや業務成果物を含む文脈も使えるという主張です。

## 5. 発表内容の詳細

### 5.1 VMware を取り巻く現状

登壇者は、Microsoft が VMware と 5 年以上クラウド向けのソリューションを提供してきたこと、企業として 20 年以上にわたってさまざまな形で協業してきたことを述べています。現在は Microsoft と Broadcom の関係になっています。

Azure 側でこの事業を始めた目的は「選択肢を提供すること」でした。VMware をオンプレミスで動かしているお客様が、ワークロードを変えずにクラウドへ行ける移行先を必要としていた、という経緯です。その約束は今後も維持すると述べられています。

### 5.2 4 つの選択肢

発表では、次の 4 つの選択肢が紹介されています。どれも、エンタープライズ水準の信頼性、セキュリティ、Azure との統合が得られるとされています。

| 選択肢 | 発表での説明 |
| --- | --- |
| AVS（Azure VMware Solution） | Microsoft が提供するマネージドサービス。Broadcom のライセンスを持ち続けて使いたいお客様がいる限り、マネージドサービスとして提供し続ける |
| Azure Local | Microsoft のオンプレミス向けソリューション。オンプレミスにとどまりつつ、ネイティブな Microsoft 製品が必要なお客様向け。クラウドにつながった形でマネージドに運用できる |
| Azure のネイティブスタック（Azure VMs、AKS） | ワークロードをモダナイズしたいお客様向け。特に AI に向けて進める場合 |
| Nutanix（Azure 上） | プライベートクラウドを Azure で維持したい、または KVM への移行を望むお客様向け。Microsoft はパートナーの Nutanix と運用している（発表では「C2」と聞き取れる箇所と「NC2」と聞き取れる箇所があり、音声認識の都合で表記が確定できません） |

#### AVS

AVS は、Broadcom から長期のライセンス契約を購入するお客様、または少なくとも 2〜3 年はそのエコシステムにとどまりたいお客様に最適だと説明されています。次の点が利点として挙げられています。

- 使い慣れたツールとスキルを維持できる
- ワークロードを中断なしに移せる
- プラットフォームの管理を Microsoft に任せられる

セキュリティ脆弱性とパッチの増加を背景に、マネージドサービスによって環境を最新に保ち、パッチをできるだけ早く適用できる、という点が語られています。VMware の最新版（VCF 9.1 や 9.2 と聞き取れます）へのアップグレードも Microsoft が行います。お客様は HCX のような使い慣れたツールで、Microsoft の支援を受けながらサービスを移行します。

#### Azure のネイティブスタック

ワークロードの一部をモダナイズしたいお客様の例として、コードを Azure のネイティブなインフラに移す、データソースを構造化データベースから Postgres のようなものに移す、ワークフローを AI で最適化する、という場合が挙げられています。そのために、Azure Catalyst（発表では Azure Catalyst と Catalyst の両方の呼び方が使われています）が、VMware の VM を Azure IaaS の VM に移すのを助けます。AKS との統合も用意されており、VMware ベースのオンプレミスのワークロードをクラウドに移行し、さらに AKS を使ったアプリケーションにモダナイズする道筋が「比較的容易」と説明されています。特に AI をワークフローに組み込みたい場合に向くとされています。

#### Nutanix

プライベートクラウドの制御を保ちたい、自分の運命を自分で決めたいが VMware では動かしたくない、というお客様向けの選択肢です。AVS 環境と同じハードウェアで動き、お客様の取引相手は Nutanix になります。登壇者は、大きなモダナイズではなく Azure に残ることを選ぶお客様が増えていると述べています。

#### Azure Local

オンプレミスから動かさないが、Microsoft がマネージドするソリューションを求め、クラウドにつながった形を好むお客様向けです。クラウドから、オンプレミスにあるものを制御できます。

> ご参考：会場では AVS のブースは出ておらず、Nutanix、Azure Local、Azure IaaS のブースがあると案内されています。

#### 共通点：セキュリティ・監視・Foundry

どの経路で Azure に来ても、Azure の監視基盤とセキュリティ基盤につながり、Defender によるワークロード保護と Defender のセキュリティスイートが利用できます。接続されたネットワークを通じて、Microsoft Foundry などのサービスにもつなげられます。

### 5.3 お客様の傾向と事例

登壇者は、AVS のお客様数千社と同じ会話をしていると述べ、次の傾向を紹介しています。

- 多くのお客様は **Broadcom に残る** ことを決めていて、その中に 2 つの陣営がある。プラットフォームに長期的にとどまりたい陣営と、短期ではモダナイズできない陣営
- ライセンス移行期を経ても、**大多数のお客様は AVS にとどまる** ことを選んでいる
- 次の層は、プライベートクラウドの構成を保ちながら Nutanix に移るお客様
- さらに、可能な範囲でモダナイズを始めるお客様がいる

大規模なお客様にとっては「or ではなく and の話」だと説明されています。事例とパターンは次のとおりです。

| 例 | 内容 |
| --- | --- |
| 大手銀行 | VMware ワークロードを縮小し、オンプレミスからクラウドへ移す際に、一部だけを Azure に移し、そのうち**約 30%** を移行と同時にモダナイズした。その 30% は、AI によってお客様や従業員の生産性を高める余地があり、ROI が明確だったため |
| 2 段階のアプローチ | すべてのワークロードをいったん Azure に移し、その後 Azure Migrate を使ってゆっくり移行する |
| 混在 | 事業部ごとに判断する |

登壇者は、事業の進み方にかかわらず、適切なソリューションに着地させられると述べています。

### 5.4 移行には時間がかかる：Catalyst による支援

移行は急いでできるものではなく、計画が必要だというのが登壇者の説明です。Broadcom との再交渉があるかもしれませんし、その後に全体の移行戦略を計画する時間も要ります。AVS をオンプレミスからクラウドに移すだけの場合でも、次の点の検討が必要です。

- オンプレミスのコントロールが、クラウドでも少なくとも同等に機能するよう、セキュリティ組織と調整する
- ネットワークの egress を計画する

もっとも簡単な移行でもある程度の計画は必要で、大規模なエンタープライズのワークロードでは数か月かかりうると述べられています。そうしたお客様には、cloud migration factory とベストプラクティスのガイダンスで支援しているとのことです。

キーノートで発表された **Catalyst**（発表では「新しいエージェント型のモダナイゼーションソリューション」と説明）は、上記の選択肢を後押しするツールとして紹介されています。説明された機能は次のとおりです。

- オンプレミスの VMware 環境を評価する
- ワークロードを移す際のコストと選択肢を示す（AVS（パブリッククラウド）に置くか、Azure IaaS に置くか）
- コスト比較ができる
- ワークロードをどう分割するかを決めるための計画ツールが豊富にある

### 5.5 データと AI

アプリケーションの周辺にはシステムがあり、SQL や Oracle のデータベースを動かしているお客様は多いと説明されています。AI 戦略の観点では、データを集約し、どこにデータがあるかが重要だという主張です。

登壇者は前日の Satya 氏のキーノートに触れ、データがクラウドに入ってこそ AI が使えるようになることが明確に示された、と述べています。関連する製品・サービスとして、次のものが挙げられています。

- 「Horizon DB」と聞き取れる新サービス。SQL Server をマネージドサービスとして提供するものと説明されている（製品名は音声認識の都合で表記が確定できません）
- AVS や Nutanix。プライベートクラウドの形で SQL Server、Windows Server、その他のアプリケーションを動かせる
- ネイティブなネットワークによって、OneLake と Fabric によるデータ分析にもつながる
- AVS のプライベートクラウドから Azure Foundry などへ直接つなぐ方法について、Web サイトにホワイトペーパーがある。アプリケーションをその場で AI 対応させたい場合に使える

インフラからデータ層、アプリケーション層、work IQ を使うユーザー層まで、AI をあらゆる層に載せていく Microsoft の取り組みは、Azure の中に移せばインフラのプラットフォームを問わず使えると説明されています。

#### Oracle の扱い

ODAA（発表では「Oracle Database on Azure」と説明。音声認識の都合で表記が確定できません）が、システム・オブ・レコードとして重要な Oracle のデータを、クラウドや AI サービスの近くに集約する簡単な第一歩になる、と紹介されています。オンプレミスの VMware 上で Oracle を動かしてきたお客様が、クラウドでは同じ方法を取らず、Azure 上の Oracle のサービスに移すことは、よくあるパターンだと説明されています。Azure 上で Oracle のインフラを動かすことも、Exascale などのマネージドサービスを使うこともできます。VMware 環境につないだまま使えるほか、SQL をネイティブに動かす選択もあります。

登壇者は、アプリケーション層とデータ層では見方を変える必要があることがある、という趣旨のことを述べています。

#### AI にはデータと文脈が必要

登壇者は、AI ソリューションに必要なものは、動かす対象となるデータと、何をしようとしているかを理解するための文脈の 2 つだと整理しています。データをクラウドに置くことは AI 準備の前提であり、文脈は Azure のほかの部分から得られます。

Microsoft 365 と AVS（VMware ソリューション）を併用しているお客様は、知識労働者の業務プロセスを、インフラ層やデータ層で起きていることと結びつけられるようになります。ここから、次のようなアプリケーションが生まれうるという話です。

- ヘルプデスクが知識労働者に自動で統合され、IT に連絡しなくても問題を解決できる
- ユーザーが問題に遭う前に、システムが検知して IT がすぐに関与できる

Azure には文脈、ユーザーのアイデンティティ情報、業務成果物へのアクセスがそろっているため、こうしたソリューションが今後数年で増える、と述べられています。

### 5.6 全体像と、移行の利点

スライドの全体像は、週を通じて何度も見せられているもので、Azure を中心に、事業の継続的な改善、業務の文脈、エージェントや Copilot 連携、セキュリティ、そして Foundry 上でのエージェント構築をまとめるものだと説明されています。登壇者は「現在手に入るエージェント型オペレーションの構築ツールとして、最も完全なセット」と述べています。エンドツーエンドのシステムが、かなりうまく統合された形で提供されているため、新米の開発者でもモダナイズのワークフローを使い始められるとのことです。また、どの経路で VMware ワークロードを Azure に移しても、この全体につながり、開発者、IT 担当者、知識労働者が活用できる、と述べています。登壇者は、これは競合クラウド事業者が提供できないものだと主張しています。

発表で挙げられた移行の利点は次のとおりです。

- VMware ソリューションをオンプレミスからクラウドへ移すと、あらゆる形態で一般にコスト削減と性能向上がある。更新され続ける最新のハードウェアで動くため
- 多くのお客様が TCO と運用パフォーマンスの両面で利点を得る
- AI サービスにネイティブにつなげてアプリケーション層の生産性を高められ、Microsoft のセキュリティツールとも直接統合できるため、TCO の利点がさらに明確になる

また、AVS はプロダクション対応の成熟したサービスであり、**数千社**のお客様がワークロードを動かしているとも述べられています。

### 5.7 次に取るべきステップ

締めくくりとして、登壇者は次のステップを示しています。

1. **自分の資産（estate）を把握する。** Catalyst とそれを支える取り組みで、資産とその準備状況を評価する
2. **事業の優先順位で選択を決める。** 万能の答えはなく、どの部分がいつ、どのように、どの時間軸で動かせるかを考える
3. **パイロットを行う。** Microsoft には小規模なパイロットを支援するプログラムがある
4. **助けを求める。** 話の中で「4 つ目のポイントとして追加すべき」と加えられたもので、多くの選択肢があるため、自分で検討したうえで相談してほしい。意思決定と移行を支援するチームが待機している

## 7. 注意点・発表者の気付き

- **移行は一朝一夕にはできない。** 最も簡単な移行でも、セキュリティ組織との調整（オンプレミスの統制をクラウドに移す）やネットワーク egress の計画が必要で、大規模なエンタープライズのワークロードでは数か月かかりうるとされています。
- **再交渉のあとに計画の時間が要る。** Broadcom と再交渉することになり、そのあとで資産全体の移行戦略を計画する時間が必要になることがある、という説明です。
- **アプリケーション層とデータ層で答えが違うことがある。** 例えば、Oracle のデータベースだけを Azure の Oracle のサービスに移し、VMware の環境は別に扱う、というお客様がいます。
- **AVS が向くお客様像がある。** AVS は、Broadcom の長期ライセンスを購入するお客様、または少なくとも 2〜3 年はそのエコシステムにとどまりたいお客様に向く、と位置づけられています。
- 会場に AVS のブースはありません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **選択肢の幅**：AVS、Azure Local、Azure ネイティブ、Nutanix から、ワークロードごとに選べる。
- **中断のない移行と管理の委任**：AVS では、使い慣れたツール（HCX）とスキルを維持して移行でき、プラットフォームの管理・パッチ適用・アップグレードは Microsoft が担う。
- **Azure サービスとの接続**：どの経路でも、Azure の監視・セキュリティ（Defender）基盤につながり、Foundry などにも接続できる。
- **コストと性能**：一般にコスト削減と性能向上があり、TCO と運用パフォーマンスの両面で利点が得られる（具体的な数値は示されていません）。
- **段階的なモダナイズ**：大手銀行は、一部のワークロードを Azure に移し、そのうち約 30% を移行時にモダナイズして、AI による生産性向上の ROI を確保した。

## 9. まとめ

VMware のライセンス変更を受けて、組織の 67% がほかの選択肢を検討し、約 19% は移行の計画または加速に進んでいる、という状況の中で、発表は「ワークロードごとに適した道を選ぶ」ことを勧めています。Azure には、AVS、Azure Local、Azure のネイティブスタック、Nutanix という選択肢があり、どれを選んでも Azure の監視、セキュリティ、Foundry につなげられます。

移行を進めるには、Catalyst で資産を評価し、事業の優先順位で選び、パイロットで確かめ、必要なら Microsoft に支援を求める、という順序が示されました。データ（SQL Server や Oracle）を Azure に置くことが AI 活用の前提だという点も、繰り返し語られています。
