# THR902 Take control of runaway AI costs with AI Gateway

## 1. はじめに

このセッションは、AI の利用が広がる中で膨らむコストを、**Azure AI Gateway** で「監視（monitoring）」「制御（enforcement）」「最適化（optimization）」する方法を紹介する 25 分のシアターセッションです。プラットフォームチームや、複数のモデル・プロバイダーを使うエージェントアプリの開発者に向けた内容です。

内容は、登壇者のデモが中心です。サポートケースを調査するエージェントアプリを例に、モデルの追加、モニタリングの有効化、アクセス制御、エイリアスによるルーティング、自動モデル選択、予算の上限設定を、順番にゲートウェイ上で設定していきます。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR902](https://ignite.microsoft.com/en-US/sessions/THR902)

## 3. 何に関する発表か

Azure AI Gateway は、**AI クライアント（ユーザー、エージェント、エージェントハーネス、エージェントアプリ）から、AI バックエンド（ツールやモデル）への呼び出しを仲介する新しいサービス**です。モデルは Microsoft Foundry 上でも、AWS Bedrock、OpenAI、Anthropic、Google Cloud などでもホストできます。すべての呼び出しがゲートウェイを通るので、監視、制御、最適化を 1 か所で適用できる、というのが基本の考え方です。

登壇者によると、Azure AI Gateway は**このセッションの 2 日前に一般提供（GA）となった**新サービスです。前日の別セッションにも触れており、そちらを見ていない人向けに、概要から説明しています。

発表の流れは次のとおりです。

1. コストに関する課題
2. 解決策の概要（監視、制御、最適化の 3 つの機能群）
3. デモ
4. まとめと開始方法

## 4. 発表者が伝えたいメッセージ

登壇者は、AI コストの課題を顧客から聞く 3 つの問題に整理しています。

1. AI コストの**可視性の不足**
2. **予算の強制の不足**
3. AI コストに対する**規律の不足**

これに対応する形で、AI コストを管理する道のりを 3 段階で考えるべきだと述べました。最初が**監視**（誰が、どのモデル・プロバイダーに、どれだけ使っているか。どのユーザーやエージェントがコストを生んでいるか）、次が**制御**（すべてのクライアントとユーザーに対して強制され、超えられない予算の設定）、最後が**最適化**（設定した予算の中で、開発者がより多くを達成できるようにすること）です。Azure AI Gateway はこの 3 つすべてに対応する、というのが発表の主張です。

## 5. 発表内容の詳細

### 5.1 コストの課題

背景として、AI の導入が急速に進み、モデル、エージェント、エージェントハーネス、チーム、モデルプロバイダーが断片化していることが挙げられました。

### 5.2 3 つの機能群

| 段階 | 機能 | 発表された内容 |
| --- | --- | --- |
| 監視 | OpenTelemetry | ログ、トレース、メトリクスに対応。**estimated cost メトリクス**で、リクエストごとのモデルの支出を見積もれる。観測したトークン数と公開されている価格から計算される。製品組み込みのダッシュボードがあり、自分でダッシュボードやアラートを作ることもできる |
| 制御 | cost limit policy | 予算を強制するポリシー。ゲートウェイ全体のすべてのモデル、または特定のモデルに対して設定できる |
| 最適化 | モデルルーティング | コスト最適化に効果的なのは、model router による**自動モデル選択**、**重み付きルーティング**、**セッションアフィニティ**の 3 つ（重み付きルーティングの前の語は「pertinent」と聞こえ、音声認識の都合で確定できません。デモでは priority と weight の設定として登場します） |

また、これらの制御は、利用中のモデルプロバイダーが持つ制御の上に重ねて使えます。Microsoft Foundry にもコストの制御はありますが、地域の異なる複数の Foundry リソースや、Foundry と他のクラウドなど複数のプロバイダーを使う場合は、AI Gateway が制御を実装する自然な場所になる、と説明しています。

## 6. デモ・手順

デモは、Caldova Pharmaceuticals（音声認識の都合で綴りが確定できません）向けに登壇者が作ったエージェントアプリで行われました。サポートケースをモデルで調査するアプリで、ケースの一覧があり、ゲートウェイに接続しますが、最初はゲートウェイにモデルがないため動きません。画面の細部は音声からは確認できません。

> 補足：モデル名は、トランスクリプトでは "GPT-6 Luna"、"GPT-6 SOL"、"GPT 6.0 SOL"、"GPT 6.1 SOL" などと書き起こされています。音声認識の都合で表記が確定できません。

### 6.1 モデルの追加とモニタリングの有効化

1. 新しい **AI Gateway ポータル**（プラットフォームチームと開発者向け）を開く
2. Microsoft Foundry のリソースを選び、4 つのモデルを 1 クリックで追加する（1 秒後に追加される）
3. 先にモニタリングを有効にする。Azure Application Insights、または既存の OpenTelemetry の送信先を使える。ここでは Microsoft Foundry で使っている既存の Application Insights リソースを選び、呼び出しを帰属させるため **token claims のモニタリング**を有効にする。Application Insights を使うと、ポータル内でダッシュボードが使える
4. アプリで追加したモデル（GPT-6 Luna）を使い、サポートケースを調査する

### 6.2 アクセス制御（Azure RBAC）

1. 手順 4 で **access denied** のエラーになる。これが制御の最初の段階で、どのモデルを誰が使えるかを管理することから始まる
2. 最も強力なモデルは特定のアプリだけに限定するなど、全員にすべてのモデルを与えないようにする。アクセスは、ゲートウェイ内のすべてのモデル、または特定のモデルに対して割り当てられ、**Azure の RBAC** で制御される
3. 数クリックで、自分にモデルの runtime invocation アクセスを付与する
4. もう一度呼び出すと、応答が返る。ゲートウェイ経由の最初の呼び出しに成功した

### 6.3 モニタリングの確認

1. まだデータが少なく、金額は 0 ドルと表示される。トークン数は表示されている。集計方法は、独自の aggregate メソッドか、プロバイダー固有のトークン種別を選べる
2. 期間を直近 1 時間に絞ると、サポートケースの調査に **0.3 セント**かかっていることが分かる。呼び出し元は、アプリが使っている自分の Microsoft ID に帰属している

### 6.4 別プロバイダー（AWS Bedrock）のモデルの追加

1. AWS Bedrock のモデルを追加する。Bedrock のキーを入力し、120 billion パラメーターの GPT オープンソースモデル 1 つだけをインポートする（自分の AWS テナントにデプロイ済み）
2. 開発者向けの **catalog experience** で、ゲートウェイ内のすべてのモデルを試せる。responses API を選び、自分の Microsoft Entra ID で認証すると、Bedrock のモデルから応答が返る。別プロバイダーのモデルを、トラフィックをゲートウェイに集約したまま呼べた

### 6.5 エイリアスとルーティングの設定

1. **alias**（クライアント向けのモデル名で、バックエンドのモデルを抽象化するもの）として「support assistant」を作る。バックエンドに GPT の Foundry モデルと AWS Bedrock のモデルを選ぶ
2. **session affinity** を設定する。エージェントのセッションを、以前に使ったバックエンドモデルに固定し、通常のトークンより安い**キャッシュトークン**を再利用するための設定。リクエストからセッション鍵を取り出す **CEL 式**を指定でき、デフォルトの式は、エージェントハーネス（"cloud code" と聞こえます。音声認識の都合で確定できません）や AWS Bedrock のエージェントなどで一般的なヘッダーを見る。ここではデフォルトを使う
3. **priority と weight** を設定する。
   - priority は、事前にプロビジョニングした容量があるモデルを優先し、その容量を使い切ってから従量課金にフェイルオーバーする、といった場合に使う
   - weight は、同じ priority グループ内でトラフィックの割合を制御する。例えば、あるリージョンに 10 倍の容量があるなら、10 倍のリクエストをそこに送る。A/B テストにも使える
   - ここでは weight を 1 対 1 に戻し、Microsoft Foundry のモデルを優先して、AWS Bedrock のモデルは Foundry のモデルが応答しないときのフェイルオーバー専用にする
4. **routing options** を設定する。モデルの選択時に、先にセッションアフィニティを見るか、先に priority グループを考慮するかを決める設定。ここでは各 priority グループにモデルが 1 つなので影響せず、デフォルトのままにする
5. **failover rule** を追加する。デフォルトの式は、応答のステータスコードが 400 から 600 の間（エラー応答）なら数回リトライし、それでも失敗するとそのバックエンドモデルを 30 秒間除外して、下位の priority グループのモデルにフェイルオーバーする
6. alias をテストすると、最優先の GPT のモデルから応答が返り、priority ルーティングが期待どおりに動いた
7. AWS Bedrock のモデルはオープンソースで、GPT よりずっと安いため、priority を入れ替えて Bedrock を優先する。catalog experience で再度テストすると、Bedrock のモデルから応答が返った
8. support assistant の alias を使ってアプリでサポートケースを調査する。ここまでがルーティング（最適化）の手順

### 6.6 モニタリングでの帰属確認とトレース

1. ダッシュボードのデータが増え、費用が増えている。この費用を alias 単位、バックエンドモデル単位、呼び出し元の ID 単位で帰属できる。表示には 2 つの API キーも出ており、Microsoft Entra ID と API キーを混ぜて支出を帰属させられる
2. **traces** で個別のリクエストの詳細を見る。同じアプリを使ったとき、最優先として設定した Bedrock のモデルに解決されていた
3. トレースのウォーターフォールには、呼び出しがゲートウェイ内の各コンポーネントを進む様子が表示される。トークン消費数、呼び出し元の ID、ルーティング方法と詳細を含む、関連付けられたログも見られる

### 6.7 自動モデル選択

1. alias の設定を編集し、**auto model selection** を有効にする。Microsoft Foundry の **model router** が裏で動き、プロンプトと目的に合わせて最適なモデルを選ぶ機能。目的は balanced、quality、cost から選べ、ここでは quality にする
2. クライアントが目的を上書きできるようにするなど、より詳細な制御もある。Foundry の model router 単体との違いは、**プロバイダーをまたいで、ゲートウェイ内の対応するすべてのモデルから選べる**点。ここでは Bedrock と Foundry の 2 つのモデルから選ばれる
3. 念のため failover rule を削除すると、alias の保存でエラーになる。ここで登壇者は routing options の話に戻る。以前は 2 つの選択肢だったが、自動モデル選択という次元が加わり、**6 つの選択肢**になる。ここでは、まず自動モデル選択、次にセッションがすでに確立しているモデルデプロイメント（キャッシュトークンを減らすため）、最後に、条件に合うモデルのうち priority が最も高いデプロイメント、の順にした。登壇者は「複雑だが、慣れるでしょう」と述べている
4. 目的を quality にして、「量子物理学に基づいた、人生の意味についての 1,000 語の詩を書いて」という高度なプロンプトを送ると、GPT の上位モデルから応答が返った。このモデルは priority が Bedrock より低い（priority 1 と priority 0 の比較として説明されている）にもかかわらず選ばれており、priority グループをまたいで最適なモデルを選べている
5. 目的を cost に変え、「インシデントを 100 語で要約して」という簡単なプロンプトを送る。モニタリングのトレースで解決先のモデルを確認すると、安価なオープンソースの Bedrock モデルになっていた
6. トレース ID をコピーして、Azure ポータルの Application Insights を開き、logs でそのトレース ID を入力すると、各 OpenTelemetry の span を調べられる。モデル選択の span には、目的（この場合は cost）と、ユースケースに最も合うと判断されたモデルの順位付きの一覧が属性として入っている

### 6.8 cost limit policy による予算の強制

1. ダッシュボードの費用は 2.2 セントに増えていた。すべて自分に帰属している
2. ゲートウェイのポリシーを開く。ポリシーは複数あり、**token quota policy** もあるが、まず **cost limit policy** を使う。予算は、ゲートウェイ全体で ID ごとに、または特定のモデルや alias に対して強制できる
3. ID ごとのデフォルト予算を、**月 1 セント**に設定する。特定の ID については上書きでき、例えば重要なエージェントには 100 万ドルの予算を与えることもできる。ポリシーを保存する
4. ポリシーは遡及して適用されないため、予算を超える呼び出しを先に行う必要がある。そこで、より高価な GPT のモデル（6.1 SOL と聞こえます）を使い、「インシデントに対する Python のソリューションを設計して」と「その提案をレビューして」という複雑なプロンプトを送る
5. 2 つ目のプロンプトで、予算の強制にかかる。前のプロンプトで 1 セントを超えて使ったため、もう呼び出せない
6. モニタリングに戻ると、費用は 3.5 セントになっており、新しい alias（GPT 6.1 SOL 用）に帰属できる。monitoring の **policies タブ**で、1 つの呼び出し元 ID による 1 件のリクエストがブロックされたことが見られる。結果は "blocked by policy" で、詳細から cost limit policy によりブロックされたことが確認できる

## 7. 注意点・発表者の気付き

- **cost limit policy は遡及適用されません。** 予算を設定した後のリクエストから効きます。デモでも、予算を超える呼び出しを一度行ってから、次の呼び出しがブロックされました
- 登壇者はモニタリングを「AI コストを管理する土台」と位置づけ、デモでも、他の操作より先にモニタリング（token claims の有効化を含む）を設定しています
- 最も強力なモデルは全員に開放せず、特定のアプリだけに限定したほうがよい、という考え方が示されました（アクセス制御）
- ルーティングオプションは、自動モデル選択、セッションアフィニティ、priority を組み合わせると選択肢が 6 つになり、複雑になる、と登壇者自身が述べています
- Microsoft Foundry の model router 単体と違い、AI Gateway の自動モデル選択は複数のプロバイダーをまたいで使えます
- セッション概要には rate limit や semantic caching も挙げられていますが、発表では説明されていません。token quota policy も、ポリシーの一つとして名前が出ただけです
- コストの数字（0.3 セント、2.2 セント、3.5 セントなど）は、デモ環境での少額の例です。実運用のコスト削減額や割合は、発表では示されていません

## 8. 利用者にとっての利点

このセッションで語られた利点は次のとおりです。

- モデル、プロバイダー、呼び出し元の ID、エージェントごとに、コストを帰属して見られる
- 予算（ID ごと、モデルごと、alias ごと）を強制し、超えた場合はリクエストをブロックできる。重要なエージェントには、別の予算を設定できる
- 事前にプロビジョニングした容量の活用、キャッシュトークンの再利用、安価なモデルの優先、プロンプトに応じた自動モデル選択で、予算の範囲内で効率よく利用できる
- Microsoft Foundry と他のクラウドのモデルを、1 つのゲートウェイで一元的に扱える
- 無料で始められる

## 9. まとめ

Azure AI Gateway では、AI コストを**監視**（OpenTelemetry のログ・メトリクス・トレースによる、ID、バックエンドモデル、alias への帰属）、**制御**（RBAC によるアクセス制御と、cost limit policy による予算）、**最適化**（priority、session affinity、自動モデル選択などのモデルルーティング）という 3 つの段階で管理できます。デモでは、月 1 セントの予算を自分で超えて、ゲートウェイにブロックされるところまでを見せました。

始めるには ai.gateway.azure.com を開きます（QR コードも案内されました）。登壇者によると、無料で始められ、2 日前に一般提供となっています。
