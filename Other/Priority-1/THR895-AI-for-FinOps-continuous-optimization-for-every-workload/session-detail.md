# THR895 AI for FinOps, continuous optimization for every workload

## 1. はじめに

このセッションは、Azure の最新の「AI for FinOps」機能を、**計画（plan）・統制（control）・最適化（optimize）**の 3 つの段階に分けて紹介する約 25 分のシアターセッションです。クラウドコストに関わる判断は、1 つのツール、1 人の担当者、1 つのタイミングだけで行われるわけではありません。そこで、IDE で作業する開発者には coding agent を、FinOps や運用のチームには cloud ops agent を通して、コストの情報を「判断が行われる場所」に近づけるというアプローチが説明されます。

扱われる主な要素は、ARM MCP（Azure Resource Manager MCP）と skills、Azure Copilot（Cost Analysis からの呼び出しを含む）、Azure SRE Agent、Azure Copilot の optimization agent、Azure MCP 経由の Advisor AI cost optimization skills です。どの段階も、架空の組織を題材にした画面付きのシナリオで紹介されました。

セッション URL: [https://ignite.microsoft.com/en-US/sessions/THR895](https://ignite.microsoft.com/en-US/sessions/THR895)

## 3. 何に関する発表か

クラウドコストは組織全体の共有責任になりつつある、というのが出発点です。登壇者は、立場ごとの判断の例を挙げています。

| 立場 | 判断の例 |
|---|---|
| IDE で作業するエンジニア | コスト見積もりを見て、2 つの構成のどちらをデプロイするか決める |
| FinOps 担当者 | コストの急増を調べ、対応が必要なのか、新しい標準になったのかを判断する |
| チーム | レポートやダッシュボードのデータから、最適化の注力先を決める |

発表の流れは次のとおりです。

1. セッションの狙いと、ARM MCP と skills の紹介
2. 計画：開発者が GitHub Copilot と ARM MCP でコストを見積もる
3. 統制：FinOps チームが Azure Copilot の chat agent、Cost Analysis、Azure SRE Agent を使う
4. 最適化：optimization agent（運用チーム向け）
5. 最適化：Advisor AI cost optimization skills（サービスオーナー向け）
6. まとめとリソース

## 4. 発表者が伝えたいメッセージ

メッセージは、**コストに関するインテリジェンスを、判断が行われる場所（IDE、Azure Portal、運用エージェント）に持ち込む**ことです。開発者は IDE を離れずに見積もりができ、FinOps や運用のチームは、使い慣れた画面や Teams の中でコストを調べて自動化できます。そして最適化では、推奨を見るだけでなく、根拠の確認、安全性の検証、作業チケット化、効果測定までを 1 つの流れで行えることが示されています。

また、これらの機能はコストだけでなく、カーボン排出（carbon emissions）にも使える、とまとめで述べられています。

## 5. 発表内容の詳細

### 5.1 ARM MCP と skills

ARM MCP は、AI エージェントを Azure のコントロールプレーンに接続する仕組みです。使うエージェントは問いません。登壇者は例として、GitHub Copilot、Claude、Codex、そして cloud ops agent 側では Azure Copilot と Azure SRE を挙げています。

ARM MCP が提供するものは次のとおりです。

- cost API を呼び出す、デフォルトのコストツール
- 同じく cost API を呼び出す、オプションのコストツール
- skills。インストールして使うか、Arm の新しい実験的機能を使うことで、5 つの組み込み cost skills が使える

これらにより、計画から統制、最適化までの範囲をカバーする機能が使えます。登壇者が挙げた機能は次のとおりです。いずれも「今日、ARM MCP から使える」と説明されています。

- コストの見積もり、予測（forecasting）
- AKS のコストを namespace レベルまで掘り下げる
- リソース全体のコストの可視化の向上
- skills を使ったコスト調査（急増の原因の把握）
- 予算（budget）のサポート
- 最適化

### 5.2 計画：開発者が IDE でコストを見積もる

ここからは、Trey Corporation（トランスクリプト上の表記）のチームが Q4 の計画を立てるシナリオです。この会社は「FinOps の shift left」に取り組んでおり、エンジニアリングチームが、日々の作業の中でコストをより考慮する立場になっています。

#### デモ：GitHub Copilot と ARM MCP での見積もり

開発者の Alex は、IDE での通常の作業の流れを崩さずに、事前にコストを見積もりたいと考えています。語られた内容は次のとおりです。

1. Alex は ARM MCP を GitHub Copilot にインストール済み。
2. GitHub Copilot に、3 つの新しいチームが、それぞれ 2 台の標準ノード（聞こえた表記は "standard DDS V5"。音声認識の都合で表記が確定できません）を持つ 3 つの node pool を求めている、という内容のプロンプトを入力し、価格を知りたいと依頼する。
3. ARM MCP をインストールしているため、GitHub Copilot は ARM MCP と、インストール済みの skills を呼び出し、定義した条件に基づく見積もりを返す。
4. 返ってきたのは retail price の見積もり。retail pricing API を呼んだもので、顧客にネゴシエーション価格がある場合は、別のツールでそれも出せる。
5. 見積もりは**月額およそ 2,000 ドル**。さらに、現在割り当てられた 2 ノードを超えて拡張が必要になった場合に、オートスケーリングで価格がどう上がるかの追加情報も示される。
6. Alex はこの見積もりをチームに示して承認を得て、デプロイの準備ができた時点で、それも IDE の中から実行できる。

### 5.3 統制（1）：Azure Copilot の chat agent と Cost Analysis

FinOps チームも Q4 に、コスト管理の改善と新しいツールの導入を進めています。その手段の 1 つが、Azure Copilot の新しい chat agent 体験です。これは GitHub Copilot SDK を利用し、バックエンドでは ARM MCP も使っています。画面には、コスト機能を呼び出す ARM MCP のツールと skills が表示されていました。これにより、FinOps チームは Azure Copilot に話しかけるだけで、ARM MCP 由来のコストの専門知識を使えます。

さらに、Azure Portal の Cost Analysis ブレードに、Azure Copilot を呼び出す **3 つの新しい入り口**が加わりました。

| 入り口 | 内容 |
|---|---|
| show cost | コストを表示する（発話は "allow users to show cost" まで。詳細は発表では語られていません） |
| explain cost changes | コストの変化を説明する |
| recommend ways to lower costs | コストを下げる方法を提案する |

いずれも、画面に出ている文脈を引き継いだまま Azure Copilot に話しかけられる、という点がポイントです。

#### デモ：explain cost changes

FinOps チームの Maya が Azure Portal を開き、コストの急増（スパイク）を見つけて、詳しく調べる場面です。

1. Maya が **explain cost changes** をクリックする（途中、画面操作がうまく動かず、発表者が別の場所から操作し直す場面がありました）。
2. Copilot との会話が始まり、画面上の文脈が引き継がれる。日付範囲、リソース、サブスクリプションのスコープ。
3. ARM MCP をインストール済みなので、Azure Copilot も ARM MCP と skills を呼び出して回答を作る。
4. Azure Copilot は、**変化がいつ起きたか、どのリソースが関わったか、なぜ変わったか**を説明する。画面では、理由は scale-up（容量の増加によるもの）と示されている。
5. Maya はこの情報をチームに持ち帰り、この状態が続くと見込まれるのか、コストを改善するために変えるべきことがあるのかを検討できる。

### 5.4 統制（2）：Azure SRE Agent

FinOps チームは、業務の自動化と効率化にも取り組んでいます。登壇者は **Azure SRE Agent** を、クラウド運用エージェント（cloud operations agent）であり、FinOps のようなさまざまなクラウド運用のタスクのための機能を取り込める、拡張性の高いプラットフォームだと説明しています。このシナリオのチームは、次のものを組み込んでいます。

- ARM MCP
- skills と plugins
- Microsoft Teams などのコミュニケーションチャネルとの連携

これにより、Azure SRE Agent とチャットしたり、スケジュールタスクを作ったり、live report を作ったりできます。

#### デモ：live report の作成

Maya が FinOps の live report を作ります。語られた範囲では次のとおりです。

1. Azure SRE Agent に、自然言語で、欲しい内容を説明する。
2. live report は、好きな頻度で更新できる。
3. 見るデータは、ARM MCP 由来でも、Azure SRE Agent に接続した他のデータストリームでも自分で制御できる。IT のヘルプやデータ分析チームのサポートは不要。

#### デモ：週次コストレポートのスケジュールタスク

チームがレビューしている週次のコストレポートを自動化します。

1. Maya が Azure SRE Agent で **create a scheduled task** をクリックする（最初は動かず、2 回目で動いた旨の発言があります）。
2. タスクの詳細を自然言語で説明し、ARM MCP も組み込む。
3. Azure SRE Agent との会話が始まり、望むレポートのスコープについて更新を伝える。
4. 週次のレポートが Teams に送られる。内容は必要に応じて更新できる。

ここまでが、コストの計画と統制の話でした。

### 5.5 最適化（1）：Azure Copilot の optimization agent

ここから、Mark 氏が最適化を担当します。シナリオは、新しい AI プロジェクトの資金を、クラウド利用コストの削減で捻出したい Three Research（トランスクリプト上の表記）です。必要なのは次の 3 つです。

- コスト削減の機会がどこにあるかを見つけること
- 推奨内容を理解すること
- 推奨が本当に目標どおりにコストを削減しているかを測定すること

関わる人は 2 種類です。推奨をレビューして優先順位を付ける**運用チーム**と、推奨を検証して必要な手順を実行する**サービスオーナー**です。

登壇者は、2 つの Azure の機能を取り上げています。運用チームが上位のコスト要因を下げるために使う **Azure Copilot の optimization agent** と、サービスオーナーが未使用リソースを見つけて節約するために使う **Azure Advisor の advisor AI skills** です。

optimization agent の機能は、運用チームが最適化できる内容のサマリーを得る、最適化プランを理解する、そのプランをカスタマイズする、推奨の根拠を得る、の 4 つと説明されています。サマリーは 1 つの画面で、次の情報を提供します。

- 上位のコスト要因
- コストの傾向と予算
- アクティブなアラート
- Azure Advisor のアクティブな推奨
- どこに注力すべきかの示唆と、これらのリソースについて「支払っている金額に対して実際にどれだけ使っているか」のハイライト

#### デモ：サマリーを見る

1. 運用チームが optimization agent に "give me a summary of what I could optimize" と尋ねる。
2. エージェントが、上位のコスト要因のサマリーを返す。ここでは仮想マシンで、**月 4,500 ドル**にのぼる。
3. あわせて、カーボン排出の傾向、アクティブな予算アラート、アクティブな cost management アラート、Advisor のコスト推奨も 1 つの画面に出る。
4. エージェントが最適化の機会として示したのは、このサブスクリプション全体の仮想マシン。ピーク時でも使用率が **18%** にとどまっており、使用に余裕があることが分かる。
5. チームが進める際のチェックリストも提示される。
6. 登壇者は、**Ignite で新たに打ち出した考え方**として、最適化できるリソースについて、実際にどう使われているかを見せる点を挙げている。このサブスクリプションの全 VM で使用率が低いことが示される。

#### デモ：推奨を見る

1. 運用チームが optimization agent に "give me virtual machine recommendations" と尋ねる。
2. エージェントがサブスクリプション全体をスキャンし、3 件の推奨を見つける。
3. そのうち "Pluto Lander"（聞こえた表記）が**月 318 ドル**で、これが月額の節約額として示される（発話では「月 318 ドルのコストがかかっている」とも述べており、やや曖昧です）。移行先の SKU も示される。
4. チームが推奨の説明を求めると、現在の SKU と推奨 SKU が示される。CPU、メモリ、ネットワークの使用率も出て、このワークロードが VM をどう使っているかが分かる。
5. ルックバック期間の情報もある。この例では過去 7 日間、このマシンは稼働しているので推奨の対象になる。登壇者は、短命なものではなく長期間稼働するリソースを最適化したいからだと説明している。
6. 現在の SKU での使用率は 25% 未満。新しい SKU に移行すると最大使用率は 75% になる。ワークロードが必要とすれば VM がスケールできる余裕（headroom）が十分ある。

#### デモ：制約によるカスタマイズと実行手順

チームごとに制約があるため、エージェントは制約に沿って代替案とそのトレードオフを示せる、と説明されました。

1. チームが "only give me Intel SKUs" と依頼する。
2. エージェントが利用可能な Intel SKU をスキャンし、すべてを示したうえで、代替案の中で最良の候補を示す。
3. ここでは "E2S to V3"（聞こえた表記）への移行を推している。理由は、CPU がピークになるときにメモリ使用も予想されるため（音声認識の都合で SKU 名は確定できません）。
4. チームが「この推奨を採用するための手順」を尋ねると、エージェントは、自分たちの側で安全に実行できるコマンドのセットを示す。

登壇者は、運用チームがこの 1 つの画面で、最適化の概要の把握、プランのカスタマイズ、プランの理解までを行えたと説明し、コストだけでなく時間も節約できると述べています。

### 5.6 最適化（2）：Advisor AI cost optimization skills（Azure MCP）

次は、GitHub Copilot を使うサービスオーナーが、未使用リソースのコストを節約するシナリオです。登壇者は、Advisor が助ける 5 つのステップを挙げました。

1. 未使用リソースからのコスト削減の、優先順位付きリストを得る
2. 推奨の安全性を検証し、トリアージする
3. 未使用リソースを片付けるための計画を作る
4. その計画を、エンジニアリングチームが取り上げられる作業項目（work item）にする
5. 実際にどれだけ節約できたかを測定する

#### デモ：未使用ディスクの整理

1. チームが "give me my recommendations for the unused resources" と尋ねる。
2. Advisor が、未使用リソースから節約できる可能性のある額として **2 万 1 千ドル（21K）**を示す。この金額の単位（月額か年額か）は、トランスクリプト上は明示されていません。続いて、未使用リソースの優先順位付きリストを示し、コストと、年間で節約できる可能性のある額が表示される。
3. チームは 2 行目の、10 個の未使用ディスクを片付けることにする。
4. トリアージが始まる。チームが "check if these resources are still not used" と依頼する。
5. Advisor は大規模に一連のチェックを行い、直近数日間にこれらのリソースの使用がないことを確認して、推奨が有効であることを確かめる。**この過程で変更は一切行われない**。チームが推奨に確信を持つためのチェックだと強調された。
6. 結果は 2 つ。使用がないと判断された **7 個のディスク**と、過去 7 日間に使用があると検知されたため確認を促された **3 個のディスク**。
7. チームは、使用がない 7 個のディスクの整理を進めることにする。トリアージの一環として「どう検証できるか」を尋ねると、Advisor は、リスクと、自分たちでチェックするための手順を示す。
8. さらに、整理を実行するための手順も示す。
9. 次に、Advisor に work item のチケット作成を依頼する。Advisor は、サービスチームがすでに使っている **Jira** にチケットを作成する。先のスキャンで見つかった 7 個のディスクと、実施した文脈とチェック内容が入る。エンジニアリングチームは、文脈と明確さをもって整理を実行できる。
10. 数週間後、サービスオーナーのチームが「この推奨でどれだけ節約できたか」と Advisor に尋ねる。Advisor は、未使用ディスクの整理により **450 ドル**が節約されたと示す（期間の単位は発表では語られていません）。

登壇者は、Advisor skills によって、サービスオーナーが未使用リソースの機会を見つけ、整理の計画を立て、サービスに影響を与えずに整理できるかの安全性と検証のチェックを行い、計画を work item にして、推奨の目標達成度を測定できた、と整理しています。

## 7. 注意点・発表者の気付き

- 発表者は、見積もりが retail price であり、ネゴシエーション価格は別のツールで出せる、と説明しています。
- Advisor のトリアージでは、チェックの間に変更は行われません。確信を得るための確認だと強調されています。
- 優先して最適化するのは、短命ではなく長期間稼働しているリソースです（推奨の対象になる前提として、7 日間のルックバックが示された）。
- 推奨の実行手順では、エージェントは、チームが自分たちの側で安全に実行できるコマンドを示します（エージェントが自動で実行する、とは語られていません）。
- デモで示された金額や SKU は、シナリオ上の例です。節約額（21K、450 ドル）の期間の単位は発表では説明されていません。
- 最適化のサマリーに、リソースの実際の使用状況を併せて見せる点は、Ignite で新たに打ち出した考え方、と述べられています。

発表で語られた利点は次のとおりです。

- 開発者は、IDE の作業の流れを崩さずに、コスト見積もりを事前に得て、チームの承認を取れる。

- optimization agent により、サマリー、推奨、根拠、制約を踏まえた代替案、実行手順を 1 つの画面で得られ、コストだけでなく時間も節約できる。
- Advisor skills により、未使用リソースの特定から、安全性の検証、Jira へのチケット化、節約額の測定までを一貫して行える。

## 9. まとめ

コストに関する判断は、IDE、Azure Portal、運用エージェントなど、さまざまな場所で行われます。このセッションでは、ARM MCP と skills をコアに、**計画**（GitHub Copilot での見積もり）、**統制**（Azure Copilot の chat agent、Cost Analysis の 3 つの入り口、Azure SRE Agent）、**最適化**（optimization agent、Advisor AI cost optimization skills）の 3 段階で、その判断の場所にコストの情報を届ける機能が示されました。
