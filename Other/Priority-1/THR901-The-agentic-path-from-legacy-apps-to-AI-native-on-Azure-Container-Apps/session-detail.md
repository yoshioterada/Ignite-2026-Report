# THR901 The agentic path from legacy apps to AI-native on Azure Container Apps

## 1. はじめに

このセッションは、古い .NET Framework アプリケーションを、GitHub Copilot の modernization 機能を使って .NET 10 とコンテナーに移行し、Azure Container Apps で動かすまでを、デモ中心で見せる 25 分のシアターセッションです。IIS と Windows Server 上の旧アプリに負荷をかけて限界を確認し、モダナイズ後のアプリが Azure Container Apps でレプリカを増やしながら負荷を受け止める様子を比較します。最後に、Azure Container Apps Express でアプリを手作業で素早く作成する短いデモも行われました。

登壇者は、アプリケーションのモダナイズが止まってしまう理由（人が残っていない、コードや構成を誰も把握していない、など）に対し、エージェントによる作業が助けになると説明しています。

## 5. 発表内容の詳細

### 5.1 Azure の移行ツールと GitHub Copilot modernization

登壇者は、以前は Azure Migrate と呼ばれ、現在は **Azure Catalyst** と呼ばれていると説明しています（呼称は音声のまま）。これは、アプリケーションやインフラの現状を評価し、Azure へ、または Azure Arc を通じて移行する計画を作るツールまたは仕組みです（音声の表現がやや不明瞭です）。画面には 3 つの経路が示され、そのうち 1 つはデータベース移行、もう 1 つが GitHub Copilot Modernization です（残る 1 つは音声からは確認できません）。このセッションで扱うのは GitHub Copilot Modernization です。古いコードのアプリを新しいフレームワークに変えるため、コード自体を開いて変更する必要があるからです。

**GitHub Copilot modernization** は、GitHub Copilot 向けの評価機能（スキル）です。リポジトリを開くと、依存関係とコードをスキャンし、アップグレードの計画を作ります。計画を承認すると移行が行われ、それには 2 つの意味があります。

1. **コードの変更**: 古いフレームワークから新しいフレームワークへ
2. **オンプレミスの前提の置き換え**: たとえばオンプレミスのストレージを Azure に移す、シークレットを Key Vault に移す、など

その次の段階として、追加のテストとコード カバレッジの拡充を生成できます（登壇者は会場に「レガシー アプリのテスト カバレッジに満足している人は」と尋ね、反応がなかったため、テストを強化する良い機会だと述べています）。さらに**コンテナー化**として、Copilot が Dockerfile を作り、Container Apps へ簡単にデプロイできるようにします。今回のような規模のアプリでは、Copilot が Bicep ファイルも丸ごと作りました。

### 5.2 題材アプリと、Windows VM 上での限界

題材は、いわゆる「MVC Music Store」（音楽カタログ アプリ）です。IIS と Windows Server 上で動く、.NET Framework 4.8 の MVC アプリで、ローカルの SQL データベースを使います（認証は Windows 認証が想定され、「ユーザー名とパスワードでないことを願う」との発言があります）。トランスクリプトの冒頭付近では ".NET framework 3.8" と聞こえる箇所がありますが、その後の説明では 4.8 です。モダナイズ先は .NET 10 です。

デモの冒頭で登壇者は、古いアプリのモダナイズを頼まれたときにまず思いつくのは「VM に載せてクラウドに置く」ことだと話しています。しかしそれは同じアプリを別の場所でホストしただけで、「クラウドで動いている」とチェックを付けられても実際にはモダンではない、という位置づけです。

負荷テストでは、Windows Server の VM に載せた同じアプリに対し、リクエスト数を増やしていきました。見る数字は 2 つで、1 秒あたりのリクエスト数と平均レイテンシです。毎秒約 200 リクエストあたりから劣化が始まり、それ以上にかけるとレイテンシが急上昇し、アルバムのページを開くのも非常に遅くなります。サーバー側では IIS の CPU が上限に張り付き、タスク マネージャーも開きにくい状態になります。

### 5.3 GitHub Copilot app modernization の実行

次にモダナイズです。GitHub app modernization は Visual Studio の一部で、VS Code でも使えます（後者は後で説明）。プロジェクトのプロパティを見ると .NET Framework 4.8 で、これは Windows 前提であり、マネージド ID に対応しない古い Entity Framework が使われている可能性がある、と説明されます。

Visual Studio では、プロジェクトを右クリックして modernize を選び、「このアプリを評価して Azure Container Apps にデプロイできますか」と依頼します。評価は事前に実行済みで、画面の左側にレポートが表示されます。レポートに挙がった移行のステップは次のとおりです。

| ステップ | 内容 |
| ---- | ---- |
| データベース移行 | 標準の SQL Server から Azure SQL へ。このアプリはサンプルで、起動時にデータが投入されるため、データ自体の移行は省略している（実際には、データの移行という別のステップが必要）|
| ファイルシステム | ローカルの temp フォルダーなどではなく、Blob ストレージまたはファイル ストレージへ |
| 認証情報 | 平文の認証情報を避ける |
| データ アクセス | system.data から Microsoft.data へ。Microsoft.data はマネージド ID に対応しており、ユーザー名とパスワードを含む接続文字列を使わずに SQL に接続できる |

登壇者は、必要なことがすべてレポートに示され、ステップを 1 つずつ進められると説明しています。さらに、自分は PM に過ぎないが、Visual Studio で動いている .NET Framework のアプリから Azure 上のデプロイ済みアプリまで **半日**で到達したと話しています。

**VS Code の場合**: インストール済みの拡張機能として 2 つがあります。

- **GitHub Copilot Upgrade**: アプリのフレームワークを新しいバージョンにアップグレードする
- **GitHub Copilot modernization**: アップグレードに加えて、Azure にデプロイできるようモダナイズを支援する

評価を実行すると、Visual Studio と非常に似た洞察が得られ、ステップごとに進められます。

### 5.4 Bicep によるデプロイと、作成されたリソース

モダナイズの過程では、Azure 上に必要なオブジェクトを記述する **Bicep のスクリプト**も生成されます。それを AZD（聞き取りでは "AZD app" と聞こえる）で実行するか、デプロイ パイプラインに通すと、リソースのセットができます。登壇者どうしの会話で、「もう MSI パッケージや zip ファイルではなく、Bicep になる」というやりとりがありました。

作成されたリソースには、マネージド ID（コンテナー レジストリからイメージを取得する ID）、SQL Server、複数のデータベースなどが含まれます。このとき「端から端まで半日で可能」だったと述べています。

### 5.5 Application Insights

モダナイズ後のアプリを見る前に、Application Insights が紹介されました。失敗したリクエストや応答時間、サーバーのリクエストを確認でき、アプリが OpenTelemetry を出力していれば、その詳細も見られる、という説明です。

### 5.6 モダナイズ後のアプリと負荷テスト

モダナイズ後のアプリは、基本的に同じアプリですが、その過程で Copilot に頼んでデザインを少し変更しており、カテゴリごとにカラー テーマが付いています（メタル、ディスコ、レゲエなどのアルバムが例に挙がりました）。アプリは Azure Container Apps にデプロイ済みです。

> 注意：負荷テストの前提として、登壇者は「SQL は外してある」と明示しています。SQL は最初のボトルネックになる依存先なので、先ほどの負荷テストと同様に、アルバムをメモリ上にキャッシュした構成にしています。このアプリ名が "modernized-cache" になっているのはそのためです。したがって、このテストは SQL を含む実運用に近い構成のものではありません。

Azure Container Apps には**スケール設定**があります。

| 設定 | デモでの内容 |
| ---- | ---- |
| レプリカ数 | 最小 1、最大 10（常に最低 1 レプリカが動く） |
| クールダウン期間、ポーリング間隔 | スケールの速さに関わる設定（値はトランスクリプトでは読み上げられていません） |
| スケーラー | HTTP スケーラー。100 リクエストごとにレプリカを追加する |

モダナイズ後のアプリに切り替えて、負荷テストを始めました。説明としては、モダナイズで、古い .NET から新しい .NET へコードを移し、コンテナーに入れたため、.NET Core をコンテナーで動かして、スケールアウトできるようになったとのことです。

1. 毎秒 100 リクエストをかけたところ、レプリカは 1 つのまま
2. 200、さらに 400 と上げていったが、しばらくレプリカは増えなかった（音声では "200 replicas" と聞こえますが、音声認識の都合で表記が確定できません。文脈ではリクエスト数を上げている場面です）
3. 負荷をかけているエンドポイントが "modernized cached" であることを確認して、さらに負荷を上げる
4. 2 つ目のレプリカが作成される。作成には時間がかかり、登壇者は「忍耐は花をもたらす」という諺を引いた
5. 2 つ目が稼働し、さらに増えて 4 レプリカになる。レプリカが使えるようになるまでの間は、スループットがわずかに落ち、レイテンシがスパイクした可能性がある
6. 最終的に 10 レプリカまでスケールアウトする。レイテンシは「まずまずの範囲」で、ページを開いても重くは感じない、と登壇者は話した
7. 「2,000 まで上げてみようか」という話が出て、プロビジョニングが終わるまではゆっくり進め、そのあと一気に負荷を上げようとしたところで、会場から質問が入った

アプリは負荷の間も動き続け、応答していました。

## 6. デモ・手順

このセッションは、デモが中心です。画面の細部は音声からは確認できないため、語られた内容を順に整理します。

### 6.1 Windows VM 上の旧アプリの負荷テスト

1. IIS 上の MVC Music Store を開く（ストアのカテゴリとアルバムが表示される）。ローカル ホストで動いているものに加え、Windows Server の VM 上でも動かした状態にしてある
2. 負荷テストで、リクエスト数とレイテンシを見ながら負荷を上げる
3. 毎秒約 200 リクエストで劣化が始まり、それ以上でレイテンシが急上昇する
4. アルバムを開くと非常に遅く、サーバー側では IIS の CPU が上限に張り付いている

### 6.2 GitHub Copilot app modernization（Visual Studio）

1. プロジェクトのプロパティで .NET Framework 4.8 であることを確認する
2. プロジェクトを右クリックして modernize を選ぶ
3. 「このアプリを評価して Azure Container Apps にデプロイできるか」と依頼する
4. 事前に実行済みのレポート（画面左）で、移行のステップを確認する（5.3 の表）
5. ステップを順に進める。登壇者自身は半日で、動作する .NET Framework のアプリを Azure 上のデプロイ済みアプリにした
6. VS Code で同様の拡張機能（GitHub Copilot Upgrade、GitHub Copilot modernization）があることを示し、評価を実行すると類似の洞察が得られると説明する

### 6.3 デプロイと確認

1. 生成された Bicep を AZD（または、デプロイ パイプライン）で実行する
2. 作成されたリソース（マネージド ID、SQL Server、複数のデータベース、など）を確認する
3. Application Insights で、失敗したリクエスト、応答時間、サーバー リクエスト、OpenTelemetry の詳細を確認できると説明する
4. モダナイズ後のアプリ（カテゴリごとのカラー テーマ付き）を開く

### 6.4 スケールアウトの負荷テスト

5.6 のとおり、スケール設定（最小 1・最大 10 レプリカ、HTTP スケーラーで 100 リクエストごと）を示したうえで、負荷を段階的に上げ、レプリカが 1 → 2 → 4 → 10 と増えるのを確認しました。

### 6.5 Azure Container Apps Express でのアプリ作成

時間が残り少ない中での最後のデモです。

1. 新しいポータルで、アプリを Azure Container Apps **Express** としてプロビジョニングする
2. 選んでいたマネージド ID が正しくなかったことに気付き、正しいものを選び直す
3. ポート（8080 と聞こえる）などを入力して作成する
4. 最後のスライドを説明している間に完了し、**23 秒**でアプリが起動して動いた

## 7. 注意点・発表者の気付き

- **負荷テストは SQL を外している**: SQL は最初のボトルネックになるため、アルバムをメモリにキャッシュした構成でテストしています（5.6）。
- **実際の移行では、データの移行が別途必要**: サンプル アプリのため DB の中身を移行していませんが、実際にはデータを Azure に移すステップが加わります。
- **スケールアウトには時間がかかる**: 新しいレプリカが使えるようになるまでの間、スループットの低下とレイテンシのスパイクが起こり得る、と説明されています。デモでも、レプリカが増えるまでしばらくかかりました。
- **Entity Framework とマネージド ID**: 古い Entity Framework はマネージド ID に対応しない可能性があるため、system.data から Microsoft.data への移行が必要になります。
- **トークン費用の負担者**: エージェントの処理を実行する環境にサインインしている人が負担します。
- **Express のデモ**: 時間切れ間近で、マネージド ID の選び間違いがありました。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **モダナイズ期間の短縮**: 動作する .NET Framework のアプリから Azure 上のデプロイ済みアプリまで、半日（登壇者自身の経験）。
- **スケールの課題への対応**: VM を増やしてロード バランサーを用意する、数か月かけて書き直す、という選択肢のかわりに、コンテナー化して Azure Container Apps のスケールアウト（最大 10 レプリカ）を使える。
- **移行作業の自動化**: コードの変更に加え、ストレージ、シークレット（Key Vault）、認証（マネージド ID）といったオンプレミス前提の置き換え、テスト生成、Dockerfile と Bicep の生成まで Copilot が行う。
- **可観測性**: Application Insights で、失敗したリクエスト、応答時間、OpenTelemetry の詳細を確認できる。

なお、顧客名を挙げた導入事例は紹介されていません。冒頭の「モダナイズの 35% が行き詰まる」という数字の出典も、発表では触れられていません。

## 9. まとめ

古い .NET Framework のアプリをそのまま VM に載せても、負荷への限界は変わりません。このセッションでは、GitHub Copilot modernization で評価、コード移行、コンテナー化、Bicep の生成を行い、Azure Container Apps で動かすことで、負荷に応じてレプリカが 1 から 10 まで増える様子を見せました。登壇者のメッセージは、エージェントによるモダナイズを敬遠せず試すこと、進める過程で可観測性を加えること、コンテナーでスケールさせることです。最後に、Azure Container Apps Express でのアプリ作成が 23 秒で完了するデモも示されました。

案内されたリソースは、チームからの発表を載せたプロダクト ブログ、Azure Container Apps に関する 2 つの QR コード、そして 5 分後に隣の部屋（3020 と聞こえる）で始まる Lab 722 です。Ignite で行われた関連のラボやセッションも次のスライドで紹介されています。
