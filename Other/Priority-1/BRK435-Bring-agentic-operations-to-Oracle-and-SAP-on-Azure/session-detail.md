# BRK435 Bring agentic operations to Oracle and SAP on Azure

## 1. はじめに

このセッションは、Oracle と SAP という基幹業務のワークロードを Azure 上で運用している IT 管理者やパートナー向けに、**Azure Workload Center** と **run agents** を紹介する 45 分のブレークアウトです。発表の序盤で、両機能が **limited preview（限定プレビュー）として発表**されています。

個々のコンポーネントの運用ガイドはあっても、アプリケーション・データベース・ネットワークを含めた「ワークロード全体」を、問題が起きる前に見通しながら運用する手段がない。これが、数百社の顧客から聞いた共通の悩みとして語られています。その解決として、ワークロードの文脈を保持する新しい ARM リソース「WVI」、go-live 前の構成検証、本番障害の調査と修復が、デモを交えて紹介されました。最後には、ビジネスユーザー向けに Work IQ と組み合わせる、将来の構想（GA 前に提供したいと説明された内容）も示されます。

## 5. 発表内容の詳細

### 5.1 背景：運用にかかる時間とコスト

Brett 氏は、基調講演で Satya 氏が「human ambition」と「intelligence が広く利用可能になること」を語ったことに触れ、ミッションクリティカルなアプリケーションの領域では「まだ始まったばかり」だと述べています。Gartner に確認した数値として、次を挙げました。

| 項目 | 数値 |
| --- | --- |
| IT 運用予算のうち、クラウドでの運用そのものに使われる割合 | 74%（つまり約 4 分の 3） |
| ミッションクリティカルなワークロードの、計画外ダウンタイム 1 時間あたりのコスト | 50 万ドルから 100 万ドル |
| 手動の検出・トリアージ・トラブルシューティングに費やす時間 | 50% |
| 本番環境の問題のうち、構成の問題が原因の割合 | 20%（本番投入前にも後にも検出できた可能性がある） |

> 補足：Brett 氏は 20% の構成問題について、「systems が本番に入る前にも、入った後にも検出できた」と説明しています。

### 5.2 Azure Workload Center と run agents

Brett 氏は、Azure Workload Center と run agents の限定プレビュー開始を、このセッションで発表しています。対象は **Oracle Database@Azure と SAP on Azure** 向けです。

Workload Center は「ワークロードの健全性についての、信頼できる情報源（reliable source）」として位置づけられます。run agents は、その上でダウンタイムと影響を最小化し、ナレッジワーカーの体験を改善するために運用を助けるエージェントです。この 2 つの組み合わせで、先に挙げた指標を前進させたい、というのが説明でした。

また、run agents は Microsoft 単独ではなく、Oracle や SAP といったパートナー側のエージェントや技術とも連携します。後のデモでは、Oracle 側の「fleet central AI agent」にも触れられました（音声認識の都合で表記が確定できません）。

### 5.3 WVI（workload virtual instance）

Azure は、クラウド上のリソースについて豊富な API とデータベースを持っています。しかし、それだけでは足りず、アプリケーションの情報、データベースの情報、利用者が作成したポリシーとつなぐ必要があります。そこで導入するのが、新しい ARM リソース **WVI** です。

Brett 氏は WVI を次のように説明しています。

- ワークロード全体のコンテキストとして働く。登録すると、ワークロードの依存関係や、技術のバージョンの最新情報を保持し続ける。
- エージェントや人が、ワークロードを 1 つの単位として推論できるようになる。
- 登録後は、すべてのエージェントに、ワークロードについての「簡潔で信頼できる概要（compact, authoritative brief）」を渡し、重要な証拠（evidence）へのポインターを示す。
- 最新に保たれるため、エージェントは依存関係を何度も調べ直さずに、既知の良い状態から作業を始められる。
- 中身は、Azure のリソース（例：受注アプリケーションの一部になる Web アプリケーション、データベース、ISV の技術、ネットワーク、ローカルまたは間接的なストレージ）と、それらを束ねる関係・依存関係・メタデータの集合。インフラ、データベース、アプリケーションを結びつける。
- Azure Copilot 上で動くエージェントや、Oracle・SAP といったパートナーの ISV エージェントが、このコンテキストの中で動作できる。
- 「set it and forget it（設定したら任せきり）」のモデル。ワークロードを登録すれば、WVI によってすべてがワークロード対応になる。

Workload Center では、登録したワークロードを一覧でき、デモで示されたように、コンポーネント単位でもワークロード単位でも見られます。人による調査用のポータルとしても使え、同じコンテキストが SAP / Oracle の run agents にも渡されます。Brett 氏は、SAP の Basis 管理者や Oracle のデータベース管理者が、それぞれの環境で動くエージェントを持つ姿を想像するよう呼びかけています。

### 6.1 デモ 1：ワークロードの登録（SAP）

1. Kalyan 氏が、SAP 環境を持つ「Mike」（Coldova 社と聞こえる）というペルソナを設定する。
2. Mike は、SAP 向けの Azure Workload Center に移動する。ここでは、新しい WVI の登録、run configuration validation、ワークロード健全性の監視・管理が 1 か所でできると説明された。
3. Mike は WVI の enrollment を開く。SAP Basis 環境のリソースは、すでにデプロイ済みである。
4. 登録（enroll）の手順に進み、システムのメタデータ（「ごく簡単なメタデータ」）を定義して、システムが何であるかを Azure に伝える。

ここで Kalyan 氏のデモが途中で止まり、Brett 氏が引き取って補足しました。

- 顧客から「オンボーディングが難しすぎると、手間に見合わない」と言われてきたため、**オンボーディングを自動化**した。
- メタデータを入力し、特定の VM を選ぶと、**ワークロードまでのすべての依存関係を自動検出**し、WVI をすばやく登録する。
- 従来は複数チームが関わって、Azure 全体の依存関係を洗い出すのに何時間もかかっていた作業が、デプロイ済みのシステムなら簡単になった。

### 6.2 デモ 2：go-live 前の構成検証（SAP）

導入として、Kalyan 氏と Brett 氏は、本番の問題の 20% が既知の構成問題に起因することを再確認しています。構成検証は、Azure 上で環境を安定させる最も簡単な方法の 1 つという位置づけです。

1. Mike は本番デプロイを終え、WVI を登録済み。ほかの WVI と並んで表示される。
2. go-live の直前、設定の変更やベストプラクティスの進化があった可能性があるため、最終チェックをしたい。
3. Mike が Copilot に、Coldova システムの go-live が近いと伝え、最終の構成チェックを依頼する。
4. **run SAP agent** が動き、メタデータからどのチェックを実行すべきかのプランを立て、チェックを完了して主要な findings を報告する。Microsoft のベストプラクティスの知見が使われる。
5. 完了すると、チェック結果はコンポーネントごとに整理される。Mike は、失敗しているチェックが複数あることを確認する。
6. Mike は逸脱（deviations）の一覧を開く。以前なら 15 のチームを巻き込んで修復方法を聞き回るところを、Copilot に修復手順を尋ねるだけで済む。
7. Microsoft と SAP の知見により、このワークロード向けに文脈化された修復手順（必要な構成を含む）が返ってくる。
8. Mike は内容を確認し、pull request を作成し、ダウンロードして、GitHub Copilot にスクリプトを取り込み、実行する。
9. 修復の実行は Mike のアカウントとして（impersonate して）行われ、見つかった問題を修正する。数分かかり、完了後にステータスが報告される。
10. Mike は同じ確認をもう一度依頼する。同じチェックが再実行され、すべて修正されたことが確認できる。これで本番に進める。

Brett 氏は結果を次のように整理しています。数分で、Microsoft・SAP・パートナーのベストプラクティスに沿った検証ができ、データベース層、アプリケーション層、ネットワーク層の問題が見つかり、場所が示され、適切な文脈つきのスクリプトが GitHub に貼り付けて実行できる形で得られた、という内容です。

安全性についての質問（スクリプトの実行は権限のある人が行う必要がある）には、次のように答えています。

- Mike の資格情報で実行される（impersonate）ため、システムは Mike の権限をすべて把握している。
- run agents は Mike の代わりに動き、その権限を引き継ぐ。
- これらは Agent 365 に登録されており、すべてがログに記録される。
- さらに、Microsoft が何千もの SAP システムを運用してきた長年の知見が、利用者にインテリジェンスとして返される。

Brett 氏は「エージェントが何をできるかが気になるなら、それを開示する。データの出どころが気になるなら、それも透明に確認できる」と述べ、これを**毎回の launch の前に実行**すれば、go-live 前に修復したい項目が見つかるはずだと説明しています。

### 6.3 デモ 3：本番障害の調査と修復（Oracle E-Business Suite）

go-live 後に本番で障害が起きた場合のシナリオです。例として、Coldova の「auto management system」（音声認識の都合で表記が確定できません）が、Oracle Database@Azure 上の EBS（音声では「EBIS」とも聞こえます）で動いている、という設定です。

従来の流れとして、ビジネスユーザーが問題を見つけ、他の人に同じ現象かを確認し、チケットを切り、重要度・優先度に応じてキューで待つ、場合によっては数日かかる、という説明がありました。新しい流れは次のとおりです。

1. ビジネスユーザー（Jan と聞こえる）と、アプリケーション管理者（Meher と聞こえる）のグループチャットがある。2 人のユーザーが、システムが遅いと報告している。
2. 管理者は、**run Oracle agent** に対象のアプリケーションを指定して、何が問題か尋ねる。
3. Microsoft と Oracle が連携したエージェント統合により、Microsoft と Oracle の複数のコンポーネント（Oracle が公開している最新の fleet central AI agent を含む）にまたがって、問題のコンポーネントが特定される。
4. このケースでは、影響の 80% が「hard page failure」と聞こえる問題によるものと特定される。
5. 次の対応として、コード修正もあり得るが、DBA による修復もできる。管理者は artifacts を開き、実行すべきスクリプトをエージェントに尋ねる。
6. 適切なパラメーターを含めて文脈化されたスクリプトが返され、GitHub Copilot で実行してデータベースに直接適用すると、インシデントが緩和される。
7. 最後にもう一度確認して解決を確かめてから、グループチャットのユーザーに「解決したように見える。そちらはどうか」と伝える。

登壇者は、「何日も待つ」従来の流れと比べて速いと述べ、BASIS 管理者にすでに付与されていた権限と機能の範囲で、登録・構成ドリフトの検出・本番障害の修復を示せたと総括しています。また、Teams の通話に専門家（SME）が来てくれるのを待たなくてよい点も強調しました。

### 6.4 将来構想デモ：Work IQ と連携したビジネスユーザー向けの体験

ここまでの内容は、限定プレビューで**すでに利用できる**ものです。これに対し、以下は GA までに提供したいと説明された機能で、Brett 氏はデモを実行しながら説明しています。

背景として、顧客から「インフラレベルだけでなく、ビジネスを動かすプロセスを考えたい」という声が強いことが語られ、Work IQ（組織についての情報）とパートナーの AI 機能を橋渡しして、ナレッジワーカーを支援する、という方針が示されました。

1. Oracle run agent の画面に戻る。ここでは、会話だけでワークロードの登録を行い、エージェントが情報を見つけてワークロードを検出する。
2. 検出されたワークロードに、受注処理（order processing）のアプリケーションがあることが分かる。
3. Brett 氏が、Oracle からビジネスプロセスを検出するよう指示する。Oracle は procure to pay の agent skill を提供しており、顧客サービスのデータなどに対する作業を助ける。この skill を、最後まで公開（publish）する。
4. ナレッジワーカーは、Copilot から直接 EBS システムで作業できるようになる。データベースに問い合わせ、オープン中の注文の情報を得る。
5. データベース内のレコードを変更するリクエストを作成すると、エージェントが承認を求めてくる。それを承認することで、読み取り専用ではなく、Oracle database agent 経由でテーブルへの**読み書き**ができる。
6. skill を使ってビジネス分析を行い、例外（exceptions）の評価を始める。Work IQ とつながっているため、データを Excel のスプレッドシートにエクスポートして、例外の管理を続けられる。
7. Copilot から始めて、使い慣れたツールに橋渡しできた。右クリックで共有リンクを作る必要も、どのユーザーに権限があるかを確認する必要もなかった（オンボーディングを正しく行い、最新に保っているため）。

さらに、Oracle が新しい skill をリリースしたときは、IT 部門が組織への公開を承認し、適切なユーザーだけがアクセスできるようにする運用になる、と説明されています。もう一方の登壇者は、システム管理者の立場から「ナレッジワーカーに agentic な skill を提供する側に回れる。どんな skill があり、自分のシステムに何が当てはまるかを何か月もかけて調べなくて済む」と受け止めています。これに対し、パートナー（Oracle、SAP など）の知識を組織内の信頼できるユーザーに届ける必要があること、そのためにデモでは Work IQ と Microsoft Graph をワークロードと併用し、どの skill をどのユーザー集団に公開すべきかを判断していることが補足されました。

GA は「来年の初めのいつか」とされています。Copilot は、すべてのワークロードの「将来のホーム」になる、とも述べられました。

> 注意：この 6.4 は、現時点で利用可能な機能ではなく、「GA までに提供したい」と説明された開発中のものです。

| 障害対応の時間 | チケットを切って数日待つ代わりに、グループチャットから run agent に尋ね、DBA 向けスクリプトで緩和できる。SME が Teams 通話に参加するのを待たなくてよい |
| 工数の削減 | 15 チームを巻き込んで修復方法を確認する代わりに、Copilot に尋ねる |
| 安全性・透明性 | ユーザー権限での実行、Agent 365 でのログ、エージェントの動作とデータの出どころの透明性 |
| ビジネスユーザーへの展開（将来） | Copilot から EBS に問い合わせ・更新し、Excel へエクスポートできる。IT 部門が skill の公開を承認する |

## 9. まとめ

Azure Workload Center と run agents は、Oracle と SAP のワークロードを Azure で運用する人のための、limited preview の新機能として発表されました。ワークロードの文脈を保持する WVI が土台にあり、エージェントが依存関係を調べ直さずに作業を始められます。

デモでは、登録の自動化、SAP の go-live 前の構成検証と修復、Oracle EBS の障害調査と修復が示されました。いずれも、実行はユーザー自身の権限で行われ、記録が残る点が強調されています。さらに GA 前の構想として、Work IQ と組み合わせ、ナレッジワーカーが Copilot から Oracle の skill を使う姿も紹介されました。

プレビューへの参加は QR コードから申し込めると案内され、登壇者はその場で質問を受け付けると述べています（今後 6 か月間の利用を楽しみにしている、とも述べています）。質疑応答の内容はトランスクリプトに含まれていません。
