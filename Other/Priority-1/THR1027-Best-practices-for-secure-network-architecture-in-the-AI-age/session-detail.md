## 5. 発表内容の詳細

### 5.1 ネットワーク分離という大原則

ワークロードをプライベートな環境に置き、外部に露出させないことが、AI を含むあらゆるワークロードに共通のベストプラクティスだと説明されています。外部からの脅威に加え、エージェント型ワークロード自身がデータを外に出す可能性があるため、より重要になったという考えです。発表者は、次の 3 本立てで話を組み立てています（このあとに Load Balancer と NAT Gateway の話が続くと予告しています）。

1. 分離のための制御と最新アップデート
2. PaaS への接続（自社・第三者サービスを問わず）
3. Azure での AI ワークロードのスケール

発表者は、IaaS だけで運用するより PaaS を使ってビジネスロジックに集中するほうが、コスト最適化の面でも望ましいと述べています。

### 5.2 Inbound と egress の保護（全体像）

中心にあるのは VNet です。インターネットに公開せずワークロードを動かせます。公開が必要な場合は、制限や保護の層を重ねる方法があるという説明で、次の製品が挙がっています。

- **Front Door と Application Gateway**：Web application firewall（WAF）を持ち、一般的な脅威から保護する。
- **Bastion、Express、VPN**：VM への RDP や AKS クラスターへの接続、またはオンプレミスからの接続に使う（「Express」は音声のまま。ExpressRoute を指すかは確定できません）。

これらで inbound 接続をとれば、公開エンドポイントを介さないため、高い分離が得られます。可能なら、ワークロードへの直接のパブリックエンドポイントはなくすべきだ、という立場です。

AI 向けの後半は egress の保護です。ストレージや SQL データベースなどの自社 PaaS には PrivateLink で接続し、同じ制御の層を保ったまま重要な資産への脅威を排除できます。リポジトリのダウンロードなど、どうしてもパブリックな宛先に出る必要がある場合は、egress を検査して承認されたものだけを許可することが「必須（must have）」だと述べています。エージェントは「慣れ親しんだレシピ以外のこと」を学習して試みるため、**firewall や NVA（音声認識では「MVA」と聞こえます）で、既知の宛先だけに egress を制限する**のがよいとしています。

### 5.3 PaaS への接続の更新（PrivateLink、service endpoints、NSP）

#### private endpoints

あらゆるクラウドサービスに接続する最良かつ最も安全な方法として、private endpoints が紹介されました。SQL やストレージなどの自社サービスだけでなく、サードパーティのサービスも多数、private endpoint service として提供できます。オンプレミスからもクラウドからも接続でき、**組み込みの data exfiltration protection** がある点が特長です。アクセスを許可するのは、自分が所有する特定のリソースだけであり、他のテナントのストレージアカウントなどへもデータを出せなくなります。

#### Private endpoint の IPv6（public preview）

IPv4 アドレスが枯渇しつつあり、クラウドに来るワークロードが IPv6 接続を求めるようになっているため、private endpoint の IPv6 対応を public preview としてリリースしたと説明しています。**まもなく GA の予定**です。private endpoint の背後にある 100 以上のサービス（サードパーティを含む）が対象です。

#### Standard service endpoints（改良版）

主にサードパーティのサービス提供者向けの仕組みです。VNet ではなく、予測しやすい **ネットワーク識別（パブリック IP）** を使います。ワークロードが複数のサブスクリプションにまたがっていても、「自分のワークロードはこの IP から出ている」と追跡でき、宛先側では NSP を使って、アクセス元のネットワークを指定して承認できます。

発表者が挙げた利点は次のとおりです。

- パブリック IP と同様に偽装（spoof）できません。この IP はサービス提供者が所有し、自社の VNet に置いたものです。
- サブスクリプションをまたいで使え、VNet やサブネットを大量に作らなくてよい。多数の数値が、1 つのネットワーク識別にまとまる。
- 権限、サブスクリプション、VNet、ID などを交換せずに、予測可能なネットワーク識別だけを共有すればよい。
- 高いトレーサビリティ（追跡可能性）が得られる。

#### NSP の改善

NSP は、リソースを分離して境界で守るための機能として説明されています（発表では略称のままです）。今回の更新は 2 点です。

- **Perimeter link**：別の perimeter にあるリソース同士が通信する必要があるとき、ある perimeter から別の perimeter へのアクセスを承認できる。すべてを承認する必要はなく、特定のリソース群に絞れる。
- **Service tags への対応**：Microsoft 自身のサービスのパブリック IP を service tag で識別する方式は、NSG、UDR、firewall、admin rules などですでに使われている。これを NSP でも使えるようにした。大量のプレフィックスの一覧を追う代わりに、タグでアクセスを承認できる。

PaaS サービスの public ingress と egress を保護することも重要です。完全に無効化できるのが最善で、NSP はそれを可能にします。既知のプレフィックス（オンプレミスの egress 機器の IP など）からのアクセスが必要なら、それだけを許可し、**残りは deny by default** にします。

### 5.4 VNet 側のスケール対応

ワークロードが大きくなると、トポロジーも大きくなります。多くの顧客は hub-and-spoke を採用し、firewall、gateway、Application Gateway などの共有リソースを hub に置き、新しいワークロードごとに spoke を足していきます。発表者は、1 つの VNet が大きくなり、hub-and-spoke の環境全体も大きくなっていると述べています。次の更新は、運用を単純にするものと、プラットフォームの上限の引き上げです。

| 項目 | 発表での説明 |
| --- | --- |
| プレフィックスの集約（summarize） | gateway がオンプレミスへ広告できるプレフィックスは現状 1,000 個までで、spoke が増えると個別・非集約のため管理が難しくなる。集約して予測しやすい範囲として広告できるようにした。 |
| peering routes の無効化 | spoke 間を NVA や firewall 経由で通信させる場合に、peering ごとの追跡が不要になり、UDR をシンプルにできる。 |
| IPv6 only peering | IPv4 が重複する再利用のアドレス空間でも、IPv6 のみでルーティング可能な spoke を作って本体のネットワークに peering でき、ワークロードを再デプロイや削除せずに IPv6 接続を得られる。 |
| VNet routing appliance | 今夏ごろのリリースと聞こえる。AI ワークロードですでに使われており、多数の private endpoint や VM、spoke 間・hub 間の接続を高スケールに最適化した機器。上限に達する顧客のために用意した。 |
| 上限の引き上げ | NSG のルール数、ルール内の IP やプレフィックス数、UDR などの上限を、少なくとも倍にすることを目指すなど、ここ数か月で引き上げ。ブログなどで目立つ形では紹介されないが、一覧をスライドに載せている。 |

> 補足：VNet routing appliance のリリース時期は、音声が「around summer this year」とあいまいで、確定できません。個別の上限値の具体的な数字は、発話では読み上げられていません。

### 5.5 AI によるトラフィックの増加（Akshay 氏）

Akshay 氏は、キーノートで Satya 氏が GitHub の成長に触れたことを挙げ、同じ成長をネットワークの視点で見ると、Azure に入ってくる公開トラフィックだけでなく、**Azure 内部のトラフィックが急激に増えている**と説明しました。要因は次の 3 点です。

1. **エージェントのループ**：1 回のプロンプトが多段のエージェントループになり、それぞれの側面を別のバックエンドが処理するため、トラフィックが何倍にもなる。
2. **マルチモーダル化**：プロンプトがテキストから画像、動画、音声を含む形に進化し、その文脈が推論や embedding のために内部ネットワーク全体を伝わる。
3. **エージェントのメモリ**：利用者の好みを知っていることが期待され、エージェントの各ステップの行動や監査用のデータがメモリに保存される。

ネットワークはこの両面を見られる立場にある、と Akshay 氏は述べています。以降は、Azure 内部のトラフィックをバックエンドへ分散するときのベストプラクティスと、AI ワークロードがインターネットへ出ていくときの話に進みます。

### 5.6 Load Balancer の構成：複数の VIP を使う

典型的な構成として、複数の顧客での知見をまとめた想定例が紹介されました（特定の顧客の事例ではないと断っています）。

- AKS 上で動くチャットエージェント
- 埋め込みモデルを呼び出すパイプライン（音声認識では「rack pipeline」。RAG の可能性がありますが確定できません）
- メモリを扱うエージェントランタイム
- これらが接続する、LLM と embedding モデルをホストする GPU の VM のバックエンド

すべて Azure のネットワーク内の通信です。Azure の Standard Load Balancer でバックエンドプールに分散するときの推奨は、**1 つの Load Balancer に複数のフロントエンド IP（VIP）を持たせる**ことです（音声認識では「WIP」とも書かれています）。次の 3 つの効果があります。

1. **スケール**：トラフィックが分散され、low entropy を防げる。
2. **最小権限**：バックエンドのサービスごとに特定のポートで公開できる。例えばチャットエージェントには推論用のポートだけを許可すればよい。
3. **分離**：VIP ごとにトラフィックのパターンが分かれ、VIP 単位でメトリクスと可観測性が得られる。そのデータで判断や分離ができる。また VIP ごとに DDoS protection も付くため、内部トラフィックでも未知のパターンや想定外のパターンの検知に役立つ。

### 5.7 Egress の選択肢と default outbound access

エージェントはタスクを完了するためにインターネットへ出ていきます。コンテナーイメージのダウンロード、SaaS との連携、OS アップデートの取得などが例に挙がりました。Azure の選択肢は、NAT Gateway、Azure Firewall、Load Balancer の outbound rules などです。

ここで警告されたのが **default outbound access** です。VNet に新しい VM をデプロイして egress の方法を明示しないと、Azure が自動的にパブリック IP を割り当て、それでインターネットに出られる仕組みです。発表者が挙げた問題点は次のとおりです。

- Zero Trust の原則に反する。
- IP が裏側で動的に変わることがあり、allow list を作れない。
- 利用者が求めたわけではなく、システムが暗黙に与えている。

そこで **展開を確認し、明示的な egress に移行する**ことを強く推奨しています。今年 3 月以降、新しい VNet は常にプライベートサブネットが既定になり、default outbound access を持ちません。ただし 3 月より前にデプロイした既存の VNet には残っている可能性があります。

### 5.8 Standard V2 NAT Gateway

egress の方法の 1 つとして、Standard V2 NAT Gateway が紹介されました。設定が簡単で、サブネット単位のアウトバウンド接続を提供し、完全にゾーン冗長です。以前の Standard V1 と比べて **最大 100 Gbps のスループット**を持ち、AI ワークロードでは、この上限の高さが重要だと述べています（監視の中でより高い上限が必要だと分かった、という説明）。また SNAT ポートをオンデマンドで割り当てるため、ポート枯渇も避けられます（音声認識では「snap ports」と書かれています）。

発表者が整理した 5 つのポイントは次のとおりです。

| 項目 | 説明 |
| --- | --- |
| プライベートが既定 | バックエンドの VM はインターネットに露出せず、egress はすべて NAT Gateway 経由になる。 |
| アウトバウンド専用 | 接続はサブネットの内側から開始する必要がある。インターネットからの新規着信は拒否する（戻りのトラフィックは通る）。 |
| 静的 IP またはプレフィックス | 前述の allow list が使え、もう 1 つの保護層になる。 |
| 監査可能性 | flow logs で個々のフローを確認でき、コンプライアンスとデバッグに使える。 |
| DDoS protection | Standard V2 の IP にはプラットフォームレベルの DDoS protection が付き、同じ IP を NAT Gateway に紐づけられる。**現在 public preview**。 |

## 7. 注意点・発表者の気付き

- **default outbound access を確認する**。今年 3 月より前の VNet には残っている可能性があるため、確認して明示的な egress に移行するよう強く推奨されています。
- エージェントは想定外のことを試みるため、egress を既知の宛先に限定して検査すること（firewall や NVA）が必須と説明されています。
- 上限に達する顧客は一部で、「すべての顧客がそこにいるわけではないが、いつも上限に当たる顧客がいる」と述べています。
- ここで紹介された機能には、private endpoint の IPv6（public preview、まもなく GA）と、Standard V2 IP の DDoS protection（public preview）など、まだ preview のものが含まれます。
- 後半の構成例は特定の顧客ではなく、複数の案件の知見をまとめた想定例です。

## 8. 利用者にとっての利点

発表で語られたもののみです。顧客名や数値による事例成果は紹介されていません。

- private endpoint は組み込みの data exfiltration protection により、アクセスを自分が所有する特定のリソースに限定できる。
- Standard service endpoints は、サブスクリプションや VNet の情報を共有せずに、第三者サービス提供者に対して予測可能なネットワーク識別を示せる。
- ルート集約や peering routes の無効化で、大規模な環境での管理や UDR が簡素になる。
- 上限引き上げと VNet routing appliance により、上限に達する大規模環境でも拡張を続けられる。
- 複数 VIP により、スケール、最小権限、サービス単位の可観測性と DDoS protection が得られる。
- Standard V2 NAT Gateway で、プライベート、アウトバウンド専用、静的 IP、flow logs、最大 100 Gbps のスループットが得られる。

## 9. まとめ

AI ワークロードのネットワークは、まず分離が基本です。inbound は公開エンドポイントを避け、PaaS には PrivateLink、第三者サービスには service endpoints と NSP を使い、egress は検査して既知の宛先に絞ります。

スケールの面では、VNet のルート集約、IPv6、VNet routing appliance、上限引き上げが進んでおり、Load Balancer では複数 VIP、egress では default outbound access をやめて Standard V2 NAT Gateway などの明示的な方法に移ることが推奨されています。発表者は、これらのインフラの部品で、AI をスケールさせながら保護もできると結んでいます。
