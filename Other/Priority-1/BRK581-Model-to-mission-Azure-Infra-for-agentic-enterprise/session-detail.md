# BRK581 Model to mission: Azure Infra for agentic enterprise

## 1. はじめに

このセッションは、AI の回答の裏側で Azure のインフラがどう動いているかを、1 つの問いに沿って追いかけるブレイクアウトセッションです。AI の話はモデルや GPU に集中しがちですが、登壇者は、企業の価値はデータ、コンピュート、ネットワーク、ストレージ、セキュリティなどをつないだ **クラウド全体のシステム** から生まれると語ります。

## 3. 何に関する発表か

## 4. 発表者が伝えたいメッセージ

登壇者が伝えたいのは、AI の成果は 1 つの部品ではなく、**データ、コンピュート、スピード、トラストが 1 つのシステムとして連動すること** から生まれる、という点です。これらを個別の部品としては考えず、まとまったシステムとして計画していると説明しています。AI inference の容量を稼働させるたびに、汎用コンピュートも一緒に提供しているのは、その考えの表れです。

さらに、「選択」と「統合」の両立も主張されています。登壇者は **「Choice without integration creates complexity. Integration without choice creates vendor lock-in.」** と述べ、Azure はその両方を提供すると位置づけています。

もう 1 つ、F1 の例えで強調されたのは、システムが判断を下すのではないという点です。システムはデータと洞察を提供し、人間（ここでは Joey）が判断します。

## 5. 発表内容の詳細

### 5.1 F1 の問いと、4 つの要素

登壇者は Mercedes の Formula One を例に出します。Mercedes のピットウォールの専門家である Joe McMillan（Joey）が、レースの残り 12 周でピットウォールにいて、数秒で決断する場面です。問いは「新しいタイヤのために今ピットに入るか、それともそのまま走って判断を信じるか」です。

画面上は単純な問いですが、背後では多くのことが必要になります。登壇者は 4 つに分けます。

| 要素 | 問い | 登壇者の言い方 |
| ---- | ---- | ---- |
| データ | システムはレースの今（天候、レース状況）を知っているか | 出発点になるデータ |
| コンピュート | 正しいエンジンが、必要な瞬間に必要なだけ働くか | compute |
| スピード | 何かが待たされていないか。プロセッサーがデータを待つと時間とお金が無駄になる | performance |
| トラスト | 肝心なときに、毎回、止まらず機能するか | trust |

この 4 つが同時に必要なので、個々の部品ではなく集合的なシステムとして考えている、と説明します。AI SuperFactory では、自分のデータ、ワークロード、モデルを持ち込むことも、Azure が提供するモデル（オープンソースを含む）を選ぶこともできます。自分のモデルを pre-train / post-train することも、データでモデルを fine-tune することも可能だとされています。「万能な 1 つの解はない」というのが登壇者の考えです。

AI factory には複数のレイヤーがあり、今週の Ignite では、インフラのコンポーネントや agent についての複数のセッションがありました。このセッションは 1 段深く、データセンターインフラ（CPU、GPU による inference と training の容量、学習に必要な高性能ストレージ、数千〜数万の CPU・GPU をつなぐネットワーク）から見ていきます。

### 5.2 データ：AI に正しいコンテキストを与える

「どの回答も、持っている知識の範囲までしか良くならない」という考えです。Mercedes の場合、知識はチーム自身のデータの中にあります。ライブのテレメトリ、GPS 信号、ラップ、セクタータイム、競合のデータです。Mercedes のテレメトリと運用データは、**Azure SQL Server** で保存・管理されている、と説明されています（トランスクリプトの表記のまま）。

登壇者が気に入っているという Mercedes の話があります。F1 の車に付けるセンサーは重さを増やし、重さはラップタイムのペナルティになります。IT director の Michael Taylor 氏（聞き取りどおりの氏名）は「センサーは重さを持ち、重さはラップタイムのペナルティだ」と述べています。そのため、持っているデータをできるだけ活用して、判断に必要なインテリジェンスを得ようとしている、という説明でした。

これはビジネスにも当てはまります。システムは、顧客、契約、運用の原則など、どのモデルも知らないことを知っています。F1 のピットウォールでも、事業の運用コントロールセンターでも、状況は違っても、そのシステムとデータにしかないコンテキストに基づいて判断する、という点は同じです。

AI というと GPU に話が行きがちですが、まずデータが必要で、データを準備し、モデルを学習・fine-tune し、インデックスを作り、複数のモダリティのデータをまとめるためのコンピュートが必要です。さらに、さまざまなコンピュートと GPU をまとめて調整する scaling engine（スケーリングエンジン）も必要です。

データの前処理向けとして、Azure の製品として次が挙げられました。

- **Cobalt**（トランスクリプトでは "Cobalt DND series"、後の箇所では "Cobalt DE series" と聞こえます。音声認識の都合で表記が確定できません）
- **HD v2**（トランスクリプトの表記は "HDV2" / "AMD HD v2"）：数週間前に GA（一般提供）を発表。1 つの VM で最大 500 コア、大容量メモリとストレージを備え、AI シナリオでのデータの前処理を特に想定している、との説明です。

### 5.3 コンピュート：モデルをミッションに合わせる

前処理されたデータが整うと、次の目標は **match the model to the mission** です。登壇者は、この旅はワークフローで、複数のステージがあると説明します。データ、モデル、ワークロードを持ち込むか、Foundry で提供されているモデルを使うかして、自分のデータで学習します。そのためのツールとして、**Azure Batch、Azure Kubernetes Service、CycleCloud** などが挙げられました（"GPS as a service" とも聞こえますが、音声認識の都合で確定できません）。

Mercedes は「複数の入口」を使う例とされ、次の構成が紹介されました。

- レース戦略のシミュレーションは、Azure Batch と、Azure 上の HPC インフラで実行する。
- virtual sensor model により、車体にセンサーを足さずに既存のテレメトリを活用し、リアルタイムの判断に使う。

登壇者は、**インテリジェンスの種類ごとに必要なコンピュートは異なる**、と述べます。AI というと GPU に行きがちですが、多くの処理は今も CPU で動き、データ準備や agent のオーケストレーションに使われます。agent の世界では、データを前処理する容量だけでなく、agent を連携させる容量も必要になる、という考えです。

GPU については、AMD と Nvidia の複数の SKU があり、ここには Microsoft 自社の **「Maya 300」**（トランスクリプトの表記。今週発表と説明。音声認識の都合で確定できません）も含まれると語られました。何万もの GPU が協調して最短で学習する分散 GPU の容量もあります。登壇者は、**インフラを決めるのはワークロードであって、その逆ではない** ため、複数の SKU を用意して、ニーズに合うものを選べるようにしている、と述べています。

製品の構成は、compute tray（GPU を含む）から始まり、その上に Azure の機能を加え、ラックレベルになります。多くの「super factory」が構築されており、最大で数万の GPU が信頼性高く動く、大規模な AI スーパーコンピューターです。ここで "NDV7 VitaRubin Exascale Supercomputers" と聞こえる製品名が挙がりました（音声認識の都合で表記が確定できません）。

ML Perf（業界の独立して監査された AI ベンチマーク）では、inference のパフォーマンスで、GB300 と GB200 の両方について、2 回連続でトップになった、と登壇者は紹介しました。ただし、重要なのは、パフォーマンスだけでなく、最速のコンピュートに正しいコンテキストのデータが供給されることだ、というのが登壇者の主張です。

### 5.4 スピード：コンピュートに食べさせ続ける（Max）

ここからは Max が担当します。「正式な流れから少し寄り道する」と断ったうえで、Azure のインフラで観察されるパフォーマンスを支えているものを話しました。

**Azure のサーバー**

Max は一般的な Azure のサーバー（liquid cooled ではなく air cooled のもの）を見せ、Azure 固有のカスタマイズが多数あり、他のクラウドプロバイダーや新興クラウドにはない、と述べます。受け取るハードウェアを、安全で高性能で AI に必要な処理ができるように、数十億ドルを投じてカスタマイズしている、とのことです。

次の点が挙げられました。

- **PQC（ポスト量子暗号）**：量子コンピューターが現在の既存の暗号を 6 時間以内に破れるという話を聞いたことがあるだろう、と前置きして、AI と汎用コンピュートを含む、出荷するすべてのブレードに PQC を導入していると説明。
- **integrated HSM**：シークレットをハードウェアに保存し、自分たちからも、上位レイヤーのワークロードからもアクセスできないようにする。
- **Azure Boost SSD**：ローカル SSD のスループットが大幅に高く、現状で約 2,000 万 IOPS で、さらに伸びている。
- **Azure Boost（ハードウェア NIC）**：ブレード上で通常行っている処理を別のハードウェアにオフロードする。このカードは、AI SKU と汎用コンピュート SKU の両方で、現在出荷されるほぼすべてのサーバーに入っている。Ignite では、このカードで 100 万 CPS（聞こえた略称のままです）や、リモートストレージの約 2,000 万 IOPS を達成できることをデモした、と説明されました。深くは触れていません。

登壇者（Max）は、このモデルを自分たちで開発しており、進化とカスタマイズを続けて、フリート全体で最高のパフォーマンスを出せるようにしている、と述べています。

**Ignite で発表された技術からの 2 点**

Max は、Ignite で多数の技術を発表したが、時間がないため一部を紹介する、と述べました。

1. **Confidential AI bare metal**：Nvidia と初めて、Vera Rubin 72 による confidential AI の SKU を提供し、ブレード上で動く情報とモデルを保護する。Mercedes の例では、Ferrari に Mercedes のセンサーの内容を知られたくないはずで、メモリ内の保護と暗号化が、データの機密性を保つ要件になる。エンタープライズ顧客だけでなく、AI ラボも、競合の状況でモデルを見られたくない、と述べています。
2. **AI クラスターのマルチリージョン化**：AI クラスターやスーパーコンピューターは広い空間にまたがり、マルチリージョンにもなりえるが、単一のコンピューターのように動く必要がある。通常の TCP/IP スタックでは遅延が大きく、失敗と再試行が起きるため、**cross-region RDMA**（トランスクリプトでは "EC RDMA" とも呼ばれています）に投資した。遅延は非常に小さくでき、間のネットワークがすべて RDMA に対応していれば、多数のネットワーク設備に分散していても 1 つのクラスターのように見える。

**Cobalt 200 と MRC**

- **Cobalt 200**：今回の Ignite で出荷。agent 向けに最適化されており、AI sandbox や agent の sandbox を書くときの味方になる、と説明しています。
- **MRC（multi-path reliable connections と聞こえます。表記は音声認識の都合で確定できません。トランスクリプトでは "multi-pass" と聞こえます）**：Chicago のスーパーコンピューティングのイベントでも触れたイノベーション。現在のネットワークは ToR スイッチなどの接続の仕方から、単一の ToR の故障や不安定さに依存してしまう。学習のように高速で価値の高い処理では、混雑すると何も達成できなくなる。Microsoft は業界の多くのプロバイダーとこのプロトコルを作り、すべてのスイッチが MRC に対応していると述べていますが、この箇所は音声認識の都合で表記が確定できません。

MRC の成果として、Max は次の数字を挙げました。

| 項目 | 数字 |
| ---- | ---- |
| 実行した規模 | 42K GPU（"fair water environment"。Fairwater と思われますが、聞き取りのままです） |
| NIC あたりのスループット | 92%（100 Gbps の NIC で 92 Gbps） |
| 理論上、対応できる規模 | 100K 超 |

挙動は 1 つのコンピューターのようだった、とのことです。Max は、Microsoft がこの分野で先行しており、NVIDIA や OCI などが採用を進めていると述べました。さらに、MRC をフロントエンドにも持ち込むことは、「発表ではなく約束」だと話しています。業界は MRC を RoCE v2（トランスクリプトの表記は "Rocket v2"）の上に構築する方向に向かっており、Microsoft がその先頭に立っている、との説明でした。

### 5.5 トラスト：信頼して使えるか

進行役に戻り、「それに本当に頼れるのか」が次の問いだとされます。Mercedes は、レース中に条件が刻々と変わる中で、リアルタイムの判断のためにシミュレーションに頼っています。必要なのは、速く、一貫して、信頼できるテクノロジーです。クリティカルなワークロードを動かすとき、ビジネスを支えるインフラへの信頼が必要で、そのために、サーバー、ラック、クラスター、リージョンの各レベルで状況が変わるため、**すべてのレイヤーにレジリエンスを組み込んでいる**、と説明されました。これにはサーバーの管理、ソフトウェア更新、ラックレベルでのハードウェア修理などが含まれます。

### 5.6 ピットウォールに戻る：Mercedes のシミュレーション

登壇者は、残り 12 周で嵐が近づく設定に戻ります。ここまでの内容は、1 周の中ですべて起きており、データは最新で、必要な瞬間にコンピュートがあり、何も待たず、何も失敗しません。ただし、**判断を下したのはシステムではなく、データと洞察を提供されたうえで判断する人間（Joey）** です。チームでも、人または agent があらゆるシナリオを見て、ライブで多数（数百〜数千）のシミュレーションを走らせ、結果に人の専門知識を当てて判断する、という説明です。

Mercedes の数字として、次が語られました。

- レースウィークエンドに、最大 **1,000 万回** のシミュレーションを実行する。
- その多くは Azure のコンピュートで動く。いくつかは複数の理由でローカルで実行する。
- **75%** は、トラックの条件が変わる中でライブに実行される。

また、レースウィークエンドに合わせて拡張できることも述べられました（David という人物の言葉がまとめになっていると紹介されましたが、内容は聞き取れません）。コンピュートは弾力的で、必要に応じて増減でき、コストを予算の範囲内に抑えられる、という説明です。「レースが必要なときにコンピュート、不要なときは節約、予算の上限内で」というバランスは、他のビジネスでも同じだと述べています。

## 7. 注意点・発表者の気付き

- 「AI は GPU だけではない」。データの前処理や agent のオーケストレーションには、今も CPU が重要だと繰り返し述べられています。
- インフラはワークロードに合わせて選ぶもので、その逆ではない。
- 「選択のない統合はベンダーロックイン、統合のない選択は複雑さを生む」。

- 量子コンピューターに関する発言（既存の暗号を 6 時間以内に破れる）は、Max の前置きとして語られたもので、根拠は発表では示されていません。
- ML Perf の結果や各種の数字（42K GPU、92%、1,000 万回のシミュレーションなど）は、登壇者の発言どおりで、詳細な条件はスライド・発話からは分かりません。

## 8. 利用者にとっての利点

発表で語られたのは、次のような点です。

- 自分のデータ、モデル、ワークロードを持ち込むことも、Azure のモデル（オープンソースや Foundry のモデル）を使うこともできる。選択肢がある。
- ワークロードに合わせて CPU、GPU、スーパーコンピューターなど複数の SKU から選べる。
- 前処理向けの CPU（HD v2 は最大 500 コア）から、最大で数万 GPU のスーパーコンピューターまで、同じ Azure 上で一貫して使える。
- confidential AI や PQC、integrated HSM など、データとモデルの保護がハードウェアレベルに組み込まれている。
- サーバーからリージョンまでのレジリエンス。
- 弾力的なコンピュートで、必要な時に拡張し、コストを予算内に収められる（Mercedes の例）。

## 9. まとめ

Joey の問いに答えるには、正しいデータ、正しいプラットフォーム、仕事をこなす正しいシリコン、それらを 1 つにまとめる統合、そして信頼が必要でした。登壇者は、自分のモデルでも、オープンソースや Foundry のモデルでも、必要な規模で素早く答えを出せることを示し、選択と統合の両立が重要だと締めくくっています。Mercedes の例が示すように、システムは判断を代わりに下すのではなく、人が判断するためのデータと洞察を、速く、信頼できる形で届ける、というのがこのセッションの要点です。
