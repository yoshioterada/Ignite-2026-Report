# BRK526 Run on it, Build on it: Digital Natives Scaling with M365

## 1. はじめに

このセッションは、デジタルネイティブ企業（スタートアップや AI ネイティブ企業）が、Microsoft 365 の**上で自社を運営し（Run on it）**、さらに Microsoft 365 の**上に自社製品を構築して（Build on it）**収益につなげる、という 2 部構成の話です。題材は、リーガルテック企業の Litera です。前半は、Microsoft 365 E5 や Entra Suite、Copilot、Agent 365 を使った Litera 社内の運用と、社内エージェントの成果。後半は、Litera が自社のリーガルワークフローを Word、Outlook、Microsoft 365 Copilot に載せる構成と、約 15 分のライブデモです。

ISV やパートナーとして Microsoft 365 / Copilot 向けのソリューションを作る方、自社の業務を Microsoft 365 上でエージェントとともに回したい方に向いた内容です。

## 5. 発表内容の詳細

### 5.1 Litera と 4 年間の modernization

Pramod 氏によると、Litera は 30 年にわたりリーガルテックを開発しており、15,000 を超える法律事務所に提供しています。「AMLA 100」（聞こえた表記のまま。米国で最も売上の大きい法律事務所 100 社を指すと説明されています）のうち 99 社が顧客です。事業は、法律ビジネス（business of law）と法律実務（practice of law）の両方にまたがり、文書のドラフト作成やレビューといった複雑なワークフローを含みます。法務では「だいたい正しい」では足りず、正確性が重要であり、そのためセキュリティとガバナンスも重要だ、という位置づけです。弁護士が自分の名前をかけて使うため、技術を信頼できる必要があります。

modernization は、過去 4 年間かけて意図的に進めた旅だったと説明されました。

| 年 | 内容 |
| ---- | ---- |
| 2022 | 4 人のエンジニアのチームが、COM の Office アドインを、新しい Office のソリューション（Office add-ins）へ移行し始めた。30 年かけて作った、決定論的（deterministic）なエンジンによるリーガル機能を捨てないこと、デスクトップの Office だけに縛られず Mac や Web を含む Microsoft 365 の各アプリで使えるようにすることが狙い。 |
| 〜2024 | 確立された業界の製品を多数クラウドプラットフォームに移行。Microsoft の Office 側 API チームと協力し、既存のアドイン（聞こえた表記は "Visto add-ins"）との機能差を特定して埋めた。2024 年にベータを開始。この協業が、Microsoft Build 2024 のセッションにも取り上げられた。 |
| 2025 | Office add-ins の GA。確立された複数の製品が、初めてクラウドプラットフォーム上に集まった。業界をリードする比較エンジン Litera Compare もこの一部。Litera Web と、当時は Semantic Kernel で作られた法務 AI エージェント「Lito」（聞こえた表記。音声認識の都合で表記が確定できません）を提供開始。 |
| 2026 | Microsoft Agent Framework に移行した。これは「その年の早い時期に GA になった」と語られています（GA になったのが Agent Framework か Litera 側かは、発話からは明確ではありません）。先週、Litera の plugin を Copilot に提供開始。 |

Pramod 氏は、この modernization が Litera の Microsoft プラットフォームへの依存と深く関わっており、そのおかげで確信を持って、数十年分の法務の知見にエージェント型のワークフローを加えるのを加速できた、とも説明しています。

法務業界は、技術の変化への適応が遅いことで知られています。4〜5 年前、法務の顧客は「この 10 年代の初め」まで Windows 上の COM アドインに限られていました。今は Microsoft 365 が各 OS・各エコシステムで使えるため、Mac OS や iPad でも同じ機能が使えます。これが Litera の 4 年間の変革と重なり、顧客がどこで働いていても機能を提供できるようになった、と説明されました。

### 5.2 Act 1：デジタルネイティブはなぜ Microsoft 365 で運営するのか

Dmitriy 氏は、スタートアップ、デジタルネイティブ、エンタープライズに共通する 3 本柱を挙げました。

1. **セキュアな生産性**：Microsoft 365 E5 と、ID のための Entra Suite。
2. **業務フローへの AI の組み込み**：Microsoft Copilot と Copilot Cowork。
3. **エージェントのガバナンス**：エンタープライズ内で稼働するすべてのエージェントを統制・管理・レポートし、可観測性を持つための Agent 365。

これが支持される主な理由として、次の 4 つが挙げられています。

| 理由 | 説明 |
| ---- | ---- |
| Consolidation（集約） | 共通のプラットフォームでつながった単一のスイートを使う。ポイントソリューションは、継ぎ目にサイバーリスクがあり、コストも高くなりがち。 |
| Agent governance | Agent 365 により、エージェントの統制、管理、レポート、可観測性を提供。 |
| Zero trust とセキュリティ | Purview、Defender、Entra などで、人、データ、デバイスを守る。AI ネイティブ企業も、成長とともに自社の IP を守ることが重要になる。 |
| Model choice | Work IQ による組織内コンテキスト（SharePoint のファイル、Teams や Outlook のメッセージ、社内の関係性のグラフ）でグラウンディングしつつ、Anthropic、OpenAI、オープンウェイトのモデル、Microsoft AI のモデルを使える。モデルルーティングにより、タスクごとに適切なモデルを最小のコストで選び、ROI を最大化する。 |

典型的な道のりとして、複数のポイントソリューションから出発し、Microsoft 365 と Teams で（例：ワークスペース、ビデオ、チャット）集約する、というパターンが紹介されました。Entra Suite は人だけでなく**エージェントの ID** も提供し、これが重要だと強調されています。Defender XDR と Purview でデータを守り、Copilot は仕事向けに作られた AI アシスタントです。Agent 365 については、Ignite で registry、policy、governance、observability、cost management、FinOps などの大きな発表があり、AI の支出とエージェントを大規模に管理できるようになる、と説明しています。

### 5.3 Litera が Microsoft 365 で運営する方法

Pramod 氏は、次の 3 点で具体的に説明しました。

- **Microsoft のバックボーン**：すべてのアプリと、社内ワークフローを支えるパートナーとのシングルサインオン連携に、Entra Identity を使っている。
- **すべてのエージェントのガバナンス**：過去 18 か月ほどで、エンジニアリングを中心に、各チームが多くのエージェントを作ってワークフローを自動化してきた。エージェントの数は毎週・毎月増えており、Agent 365 は「これ以上ないタイミング」で来た。すべてのエージェントを監視し、ID を割り当て（人とエージェントの zero trust）、管理できる。
- **E7 スイート**：Agent 365 と E7 スイートに含まれる Defender と Purview が、安心感を与えてくれる。

#### 社内エージェントの成果（過去 18 か月の指標）

| 項目 | 語られた内容 |
| ---- | ---- |
| エンジニアリング部門の pull request | 200% 以上増加。多くのエージェントが作業していることによる。 |
| 品質 | 開発の生産性が 200% 上がっても、escape bug（流出バグ）の率を 65%（に抑えた）と語られた（発話は "keep the escape bug rates down to 65%"。何に対する 65% かは音声からは確定できません）。QA チームが、バグを先回りして見つけて報告するエージェントを作ったことで実現できた、と説明。 |
| Newton（IT ヘルプデスクエージェント） | Litera の Copilot インスタンス内で動く。解決チケットの時間について平均 75% 以上の解決（発話は "over 75% resolution on average for resolution ticket time"。意味は音声からは確定できません）に貢献。 |
| プロダクト要件ドキュメント | プロダクトオーナーやプロダクトマネージャーが生成する PRD は、スキル（聞こえた表記は "product made skill"）で支援されている。 |
| SecureMate（AppSec チームが開発） | AppSec の P3、P4 の問題を、エンジニアのレビューなしで、自動で修正してブランチにマージできる。 |

### 5.4 Act 2：Microsoft 365 の上に構築する理由

Dmitriy 氏は、Litera のような ISV が、共同の顧客（法律事務所など）向けにソリューションを構築する理由を挙げています。これは会場の方にも当てはまる、という前置きつきです。

1. **業務フローの中でユーザーに会える**：Teams、Outlook、Excel、Copilot などを使う情報労働者に、導入の障壁が低い形で、使っている画面の中で届けられる。
2. **エンタープライズデータでのグラウンディング**：Microsoft IQ、Work IQ によって、MCP サーバーやエージェントが賢くなる。顧客のコンテキストでグラウンディングしながら、顧客の環境内で安全に保てる。
3. **既定でのガバナンス**：ID を提供でき、Agent 365 のフレームワークにつなげられるため、展開しやすくなる。
4. **デプロイの手間の低さ**：別途のインストールが不要。管理者が Copilot の plug-in marketplace で承認するだけで、顧客のいる画面に展開される。例えば MCP サーバーが承認されてテナントに展開されると、GitHub Copilot を含む複数の Copilot、複数のサーフェスで自動的に有効になり、管理者が Litera のようなソリューションを有効化するのが簡単になる。
5. **セキュリティレビューの容易さ**：CISO によるセキュリティレビューを通すのは複雑だが、スタックの上に作られたソリューションは、テナント内に存在し、セキュリティの権限を継承し、ID と Purview 連携を持つ。そのため、IT 管理者が長いレビューではなく「Yes」と言いやすくなる。
6. **Microsoft marketplace と co-sell**：Dmitriy 氏が個人的に一番好きだと述べた点。Microsoft marketplace に載せ、Microsoft のフィールド（営業）と共同で販売できる。Copilot の利用を増やすことは Microsoft の使命にも合致し、Microsoft の営業担当が Litera のようなパートナーの共同顧客への展開を助け、収益と go-to-market を進められる。

> 補足：Dmitriy 氏は理由を「4 つ目」などと数えながら話していますが、内容が行き来しているため、上記は語られた内容を整理した並びです。

## 6. デモ・手順

Pramod 氏が、ライブデモとして実際のワークフローを見せました（「デモの神様が味方してくれるといい」と述べています）。文書は 3 つのバージョン（ドラフト、相手方から戻ってきた交渉版、パートナーの指示を反映した版）で進みます。Pramod 氏は、自分が担当する法律事務所のアソシエイトを演じ、途中でシニアパートナーの役に切り替えます。相手方の弁護士 Sam は、交渉版を返してくる側として登場します。題材は、資金調達のために株式を売却する契約をまとめようとしている「Tony Stark Industries」です。画面の細部は音声から分からないため、語られた範囲で記します。

> 補足：実際の法務ドラフトには長い時間がかかるため、デモでは一部を省略している（"taking a few liberties"）と本人が説明しています。

### 6.1 Word でのドラフト作成（アソシエイト）

1. 白紙の文書から開始し、Litera for Word アドインを開く。
2. テンプレートから、企業が承認した「securities purchase agreement（証券購入契約）」のテンプレートを選ぶ。
3. クライアント（Tony Stark Industries）向けに、契約日を選んで finish を押す。顧客と日付に合わせた新しい文書が生成される。
4. 詳細な条項の作成は済んでいると仮定し、目次が入っていることを確認。気になるのは「survival（存続）条項」の 1 つだけで、期間が経験上おかしいと感じる。
5. Litera for Word から、事務所が過去に使った先例ライブラリ（precedent library。事務所が提供した、再利用用にマークされたゴールデンドキュメントから抽出されたもの）を開く。「curated content」から、securities purchase agreement の survival 条項だけを検索する。
6. 結果の中から適切に思えるものを選び、既存の条項と置き換えて挿入する。
7. 最終確認として、校正（proofreading）機能を実行する。これは数十年使ってきた決定論的エンジンと同じで、何も変わっていない。クラウドプラットフォーム経由で、エージェント型ワークフローと統合された形で提供される。
8. 2 つの重大な問題が見つかる。1 つ目は数値の不一致で、文字で書かれた 20% の表記と数字の値が合わないため、数字の側を更新する。2 つ目は曜日の問題で、11 月 19 日は木曜日であるべきだったので、修正する。
9. 再スキャンして、重大な問題がすべて解消されたことを確認する。
10. ドラフトが整ったので、相手方の弁護士 Sam に送る。パートナーも CC に入れて、内容を見られるようにする。

### 6.2 Outlook での比較（アソシエイト）

デモでは「タイムトラベル」として、相手方 Sam がレビューして交渉済みのバージョン 2 を返信してきた状態へ進みます。

1. Outlook で、Sam からのメールを開く。スレッドの最初のメール（自分が送った）にはバージョン 1、Sam の返信にはバージョン 2 が添付されている。
2. Litera の Outlook アドインを起動する。同じ機能、同じインターフェイスで、弁護士が働く場所についてくる。
3. Lito が、このスレッドに同じ文書の 2 つのバージョンがあることを認識し、比較（compare）を提案する。それを実行する。
4. 比較結果が表示される。Pramod 氏は、compare は Litera にとって最も重要なツールだと述べ、比較を生成 AI モデルに任せるのではなく、弁護士がソフトウェアを信頼する必要があるため、Word 文書の要素を 1 つずつ比較して差分を特定し、変更をすべて含む redline 文書を生成していると説明する。
5. ビューアーを開き、変更点を確認する。バージョン表記の変更のように軽微なものがある一方、株価が下がっていること（Sam が低い価格を交渉した）、購入全体の合計金額も大きく下がっていることが重要な変更。
6. アソシエイトとしては差分は分かるが、Tony Stark Industries を知るシニアパートナーの判断を待ちたい。そこでこの文書をダウンロードして手元に置く。
7. 保存方法は複数あるが、「track changes」文書として保存する（Word のネイティブ機能を使うため）。その文書を開き、パートナーの指示を待つ。

### 6.3 Microsoft 365 Copilot での分析（パートナー）

1. パートナーのペルソナに切り替える。パートナーは Copilot を使うのが好きな人で、新しくリリースされた Litera plugin を Copilot で使う。「これはライブです」と発言。
2. パートナーは、redline の変更を 1 つ 1 つ見る時間は使わず、リスクと、それが顧客にとって何を意味するかを見たい。
3. 基本的なプロンプトを送信する。プロンプトに「Litera compare」を含める。Pramod 氏は、画面右側のワークスペースパネルに注目するよう促す。
4. このプロンプトは、Copilot に、受信トレイを見て、メールスレッドの添付ファイルを取得し、サードパーティの plugin である Litera を呼び出すよう求めるもの。Copilot は最初に Outlook へのコネクタを確立し、ファイルをダウンロードして、メモリに載せ、Litera を呼び出す。Litera が plugin として表示される。
5. 文書のアップロードを承認する必要がある。2 つの文書について、複数回確認が求められる。
6. その後、Copilot は Litera の機能を使い、redline エンジンを実行してリスクを分析し、レポートを返す。通常は 1 分ほどかかる。
7. 待たずに、以前に実行した結果に切り替える。以前は 1 分 14 秒かかった。
8. 結果として、上位 3 つのリスクが返る：株価の引き下げ、調達額（合計金額）の縮小、そして IP 保護期間の問題。
9. パートナーは、Tony Stark は資金を強く必要としているため価格の引き下げは許容できると判断し、価格変更を承認する。ただし IP 保護条項は、アソシエイトに押し返して強く維持するよう指示する。

### 6.4 Word での交渉対応（アソシエイト）

1. アソシエイトに戻る。先ほど Litera からダウンロードした redline 文書を Word で開き、Litera for Word を起動すると、新しいタブが表示される。
2. エージェントのワークフローが、この文書が track changes の文書であることを認識し、「manage changes」というスキルを有効にした。文書内の各変更を順に見て、取り得る対応についてガイダンスを得られる。
3. 契約の種類が securities purchase agreement として認識されている。準拠法（governing law）の項目にも触れたうえで、代理する当事者の追加は可能だがスキップする。交渉スタンス（negotiation stance）は「firm」を選ぶ。
4. 文書をスキャンする。スキャンでは、前画面のメタデータとバージョン 2 での各変更が送信される。結果は 5 件の変更（重要 4 件、軽微 1 件）。
5. パートナーの指示どおり、価格の変更と合計金額の変更を承認する。承認のたびに再スキャンすると、更新された文書がサーバー側の処理に送られ、決定論的エンジンが実行される。
6. 3 つ目は、IP 保護の期間が 3 年に延長されている変更。パートナーの指示（強く維持）に従い、再スキャン後に同じ条項に戻って、「suggest rewrite（書き直しの提案）」を依頼する。
7. バックエンドのエンジンが、先例ライブラリにある組織の知見を使って、よりよい文面を提案する。もともと交渉済みの期間は 2 年で、相手方が 3 年にしてきた。提案は 2 年に更新されている。
8. 提案を文書に挿入し、再スキャンする。
9. 最後に残るバージョン表記の軽微な変更を承認する。これでバージョン 3 になる。

Pramod 氏は、Litera は弁護士が Word、Outlook、Web、Copilot のどこで働いても、同じ機能が使える形でついていくのだ、とまとめています。

## 7. 注意点・発表者の気付き

- **正確性を最優先する設計**：Litera は、比較エンジンを生成 AI に任せず、Word の要素を 1 つずつ比較する決定論的エンジンを使っています。「弁護士が信頼できる」ことが理由です。エージェント型の仕組みを導入した後も、同じ正確性を保つことを重視していると説明されました。
- **承認ステップ**：Copilot から plugin に文書を渡すとき、アップロードの承認が複数回求められます（デモ中の説明）。
- **処理時間**：Copilot での分析は通常約 1 分（デモの実行時は 1 分 14 秒）かかるため、待たずに事前の実行結果に切り替えた、と説明されました。
- **デモの簡略化**：実際の法務ドラフトには長い時間がかかり、デモでは一部を省略しています。
- **既存機能の継続利用**：Litera は、30 年かけて作った機能を捨てずに、新しい Microsoft 365 アドインへ移行することを modernization の方針にしました。
