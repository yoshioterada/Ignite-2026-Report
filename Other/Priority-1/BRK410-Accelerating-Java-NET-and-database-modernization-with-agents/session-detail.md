## 4. 発表者が伝えたいメッセージ

**モダナイゼーション自体は目的ではなく、それによってイノベーションと新しい機能を解放することが目的**だ、という考えが全体を貫いています。そのために、これまで障壁になっていた手作業（toil）を、エージェントに任せるという主張です。

もう 1 つは、エージェントを任せるときに必要な 3 つの要素、**スケール、カスタマイズ、ガバナンス**です。顧客から繰り返し聞く要望として挙げられており、デモもこの 3 つを意識した構成になっています。

- スケール：1 つのアプリを 1 つのエディターで扱うやり方は通用しなくなっている。アセスメント、移行計画、バージョンアップグレード、フレームワーク変更、コードレビューまで、ライフサイクル全体をまとめてスケールさせたい。
- カスタマイズ：アプリは 1 つ 1 つ違うので、画一的な移行はできない。エージェントが、各アプリ固有の要件と目的に基づいてコードを評価・変換する必要がある。
- ガバナンス：安全に進めること。human-in-the-loop のレビューに加え、承認済みのポリシー、禁止パターン、コンプライアンスルールを組み込み、監視と監査証跡を残す。

## 5. 発表内容の詳細

### 5.1 なぜモダナイゼーションが急務なのか

冒頭で Elizabeth 氏は、「経営層から期限を課されて技術スタックを近代化している人」を会場に尋ね、数人が手を挙げました。続いて、Forrester の 2026 年第 1 四半期の調査を紹介しています。

- IT リーダーの **94%** が、今後 6〜12 か月の最優先の投資の 1 つとしてモダナイゼーションを挙げている。
- モダナイゼーションのプロジェクトの **3 分の 1 以上**が、モノリスの複雑さ、リソース不足、セキュリティの懸念が重なって止まっている。

プロジェクトが止まっても負債はそのまま残らず増え続け、AI への備えに使うべき時間を食いつぶします。技術的負債は、何十年もかけて作られた大規模で複雑なモノリス、カスタマイズの多いアプリに積み上がり、スキル不足とリソース不足が返済を難しくしている、という説明です。その結果、コストが上がり続け、セキュリティとコンプライアンスの脆弱性が増え、AI のイノベーションが遅れ、開発者が古いシステムの維持に時間を使い、性能や運用の制約が事業全体の足を引っ張ります。

### 5.2 Azure Catalyst

今回の Ignite で発表された **Azure Catalyst** は、技術資産全体（アプリケーション、インフラ、データ）のモダナイゼーションを、1 つにつながった体験として提供するものです。発見（discovery）、アセスメント、計画、実行を 1 か所で扱い、IT チームと開発者が、仕事を受け渡しする代わりに同じ場所で協力できる、と説明されています。

- アーキテクチャ、優先事項、標準に合わせた計画とエージェントでカスタマイズでき、チームの既存の知識を再利用でき、モデルも選べる。すべて自社のセキュリティとガバナンスの中で行える。
- インフラ、アプリ、データを近代化して Azure 上の AI 機能につなぐと、すでに行った投資の上に構築でき、価値を早く得られる。

要約すると、速度、精度、イノベーションを、安全に、すべてのワークロードで、あらゆる段階にエージェントを置いて実現し、IT と開発者が使い慣れたツールで AI を使ってモダナイズ・構築できるようにする、という位置づけです。期待する結果は、複雑さの軽減、技術的負債の削減、AI に対応したアプリです。

### 5.3 GitHub Copilot modernization

Azure Catalyst のポートフォリオの中で、アプリ部分を担うのが **GitHub Copilot modernization** です。既存のアプリケーション、コード、データベースの理解と変換を、開発者の既存のワークフローの中で支援する、エンドツーエンドのエージェント型アプリモダナイゼーションのシステムと説明されています。

| 項目 | 説明 |
| --- | --- |
| 操作の入口 | CLI。複数のアセスメントと移行計画を同時に走らせ、その計画を開発者に渡して、IDE で実行・検証してもらう |
| Java と .NET のフレームワークのアップグレード | modernize CLI からエンドツーエンドで自動化 |
| データベースのモダナイゼーション | CLI で、本日（Ignite）からプレビュー。データベースを検出し、適切な Azure のターゲットを推奨する。アプリのコードとデータベースを一緒に変更し、リポジトリをまたいで安全にスケールさせる |
| ルールブックとカスタムスキル | ガバナンスとカスタマイズのため。チーム固有の移行パターンとポリシーを 1 回コード化して、ポートフォリオ全体で再利用する（write once, reuse at scale） |
| 利用できる場所 | 好みのエディター、CLI、GitHub |

提供の考え方として、次の 3 つが挙げられています。

1. **作業している場所で使う**：開発者の 76% が、VS Code、Visual Studio、IntelliJ、CLI、GitHub を常用している。新しいツールを覚えさせるのではなく、エージェントをそこに持ち込んだ。
2. **あらゆるワークロードに対応する**：16 million を超える .NET と Java の開発者を対象にし、アプリ、データ、インフラを合わせて理解するという、資産全体（estate レベル）のアプローチを取る。VMware、Windows と Linux のワークロード、.NET と Java のアプリ、Oracle、Sybase、SQL のデータベース、さらにメインフレーム（パートナーの専門家とエージェントを組み合わせる）が対象。
3. **カスタマイズとガバナンス**：ブラックボックスの引き渡しがない。エージェントは、60 を超える専門のスキルを標準で備えており、その上に独自のカスタムスキルとルールブックを重ねて、組織のやり方を学ばせられる。

### 5.4 データベースのモダナイゼーション

Nish 氏は、アプリとデータベースは一緒に近代化すべきだと説明しています。多くの組織では、データベースチームとアプリチームが別々に作業しますが、全員が連携しなければなりません。そこで今回、**Microsoft の SQL Server と Azure Postgres の SQL チームと連携して、データベースの統合を modernize CLI に追加した**と発表しています（プレビュー）。

- データベースの知見（data intelligence）が CLI に組み込まれ、アプリとデータベースを一緒にアセスメントでき、準備ができたら一緒に移行できる。
- 特に、Oracle から Postgres への**異種移行（heterogeneous migration）**では、データベース関連のコード（ドライバーなど）も変換する必要があり、データベース側で何が変わったかをエージェントが理解して、コード変更に反映させる必要がある。
- 安全にスケールするためのガードレールは、このあと説明される。

### 5.5 ルールブック（Rulebooks）

Elizabeth 氏が、今日の発表として、**Rulebooks が GitHub Copilot modernization で一般提供（GA）になった**と説明しています。組織の標準を、チームごとに解釈が違う状態に任せず、モダナイゼーションのプロセスに直接適用するものです。

1. 標準を、プレーンな Markdown で 1 回だけまとめる。アーキテクチャとポリシーを最もよく知る人が、読みやすく、レビューしやすく、維持しやすい形で書ける。
2. 標準には、ターゲットのフレームワーク、命名規則、禁止するコーディングパターン、必要な Azure サービスのターゲット、実行の特定の段階で使うべきカスタムスキルなどが含まれる。
3. CLI がそれを、**トークン最適化されたドキュメント**に変換し、中央の GitHub リポジトリに公開する（音声では「3 token optimized documents」と聞こえ、数は確定できません。のちのデモでは「トークン最適化した形式」と語られています）。組織全体のモダナイゼーションの方法について、単一の信頼できる情報源になる。
4. ポートフォリオ全体のすべての実行計画が、既定でルールブックに従う。誰も強制を覚えておく必要がなく、標準は「従うよう求められる文書」ではなく、すべての計画の作り方の一部になる。

### 5.6 カスタムスキル

Nish 氏は、組織によっては、エージェントに特定の作業を組織の推奨するやり方で行わせたい場面があると述べています。例として、命名規則に従うこと、PII のマスキングを行うスキル、そして一般的なログ出力とは異なる、独自のログ用 SDK を使うことが挙がっています。**カスタムスキルは 5 月から GA** で、実行パイプラインに直接組み込めます。会社ごとにやり方が違い、LLM は自力でそれを把握できないので、カスタマイズの手段が必要だ、という説明です。

### 5.8 モダナイゼーションの先：migrate、modernize、transform

モダナイゼーションは「ゴール」ではなく、イノベーションの「発射台」だというのが、ここでの主張です。すべて Azure 上で、次の 3 段階として整理されています。

1. **Migrate**：アプリとデータを、安全に、大規模に Azure に移す。老朽化したインフラから、構築のできる基盤に移る。
2. **Modernize**：最新のプラットフォームと API にアップグレードし、技術的負債を取り除いて、AI に備える。ここまでを、Azure Catalyst と、コード部分の GitHub Copilot modernization が支援する。Caldova がここまでを実施した。
3. **Transform**：実際のビジネス成果を出す AI エージェントを構築する。企業のシステムとデータの上に AI の体験を作れるのが、技術的負債を片付けた見返りである。

そのためのツールとして、Azure の、AI 向けのフルスタックの基盤が挙げられ、Microsoft Foundry や Fabric などのツールでエージェント型のワークフローを構築でき、Copilot と Agent 365 がその管理を支援し、各段階でセキュリティを確保する、という継続的な改善のサイクルが説明されています。

| 期間 | 内容 |
| --- | --- |
| 最初の 30 日 | 2〜3 つのビジネス成果を選ぶ。資産をアセスメントし、価値と労力で、最初のウェーブのワークロードを選ぶ。ID、セキュリティ、ポリシーのガードレールを備えたランディングゾーンを設定する |

## 6. デモ・手順

このセッションには、Nish 氏による長いデモがあります。「自分のマシンに切り替える」と述べ、画面を操作しながら説明しています。ただし、アセスメントの結果は「編集の魔法で最終のレポートを見せる」と述べ、データベース担当者の作業の部分は「早送りにしている」と述べており、一部は編集・短縮されています。画面の細部（ボタン名や入力値）は音声から確認できないため、語られた範囲だけを書きます。

### 6.1 題材：Caldova Insurance

- 顧客向けのポータルで、ユーザー名とパスワードでログインし、保険金の請求（claim）を出せる。
- **Caldova Auto**：自動車保険。.NET で、バックエンドは SQL Server。保険証券番号、事故の日付と場所、状況、車両の損傷を入力し、写真を添付して送信する。以前は電話で対応していた。
- **Caldova Home**：買収した住宅保険の会社のもの。まったく別の技術スタックで、Java（Java 17 のコードがある）。見た目は Auto と似ている。データベースは Oracle（のちに「請求がもう Oracle には送られない」と語られます）。
- 保険の担当者（adjuster）がログインして審査を完了する。
- 全体は大きなモノリスで、最初にモダナイズの対象として語られるのは Home（Java 17 のコードを含む）。Nish 氏は、複数のアプリを持つポートフォリオを扱う想定で、「動いていることは分かっているが仕組みが分からない古いコード（掛け合いの中では 90 年代から動いているとも）の近代化を任された、リードアーキテクト」という設定で進めています。

> 補足：Nish 氏は、1 つのアプリだけなら、IDE の GitHub Copilot modernization の拡張機能から、アセスメント、ランタイムのフレームワークやセキュリティ脆弱性のアップグレードができると説明しています。今回はスケールを示すため、CLI を使います。

### 6.2 アセスメント（ポートフォリオ全体）

1. `repos.json` を見せる。エージェントにリポジトリの場所を伝える単純なキーと値のファイル。GitHub のリポジトリにリンクしてスケールさせることもできるが、ローカルにコードがある顧客も多いため、今回はローカルで行う。
2. modernize CLI を起動する。assess、plan、execute のワークフローが表示される。アセスメントは現状の理解、計画は目標を決める仕様駆動の作成、その後に実行。
3. モデルを選べる。既定の選択肢のほか、今回の Ignite で **BYOM（bring your own model）が GA** になった。LLM を自社のセキュアな環境に置きたい要件に応えるもので、政府機関や公共クラウドの企業などに向いています。modernize CLI が Build で GA して以来、最も多い要望だったと説明されています。
4. `repos.json` を指定すると、**12 個のリポジトリ**が表示される。
5. 設定として、分析範囲（coverage）は full analysis（エージェントがより深く分析できるため推奨）、セキュリティの要件のチェックも入れる。Java と .NET を一緒に扱う。
6. ターゲットは、Java が OpenJDK 25、.NET が .NET 10（LTS）。アセスメントのドメインは、古くなったアプリスタック、クラウドへの準備状況（cloud readiness）、セキュリティ脆弱性。
7. ローカルで実行することも、クラウドエージェントに任せること（fire and forget。GitHub の agent HQ で状況を確認できる）もできる。今回はローカル。
8. 結果として、統合された **HTML レポート**を見せる（実行には時間がかかるため、最終のレポートを見せている）。

レポートの内容として、語られたものは次のとおりです。

- 12 個のアプリ（Java が 6、C# が 6）。現在のランタイムは、Java 8、Java 11、Java 17、.NET Framework 4.7.1 など。
- 推奨事項と、ウェーブ計画（どこまで近代化できるか、どれだけ早く行えるか）。
- 概算のコスト見積もり。小売価格に基づく目安であり、顧客の契約に基づくものではなく、リーダーシップとの会話を始めるためのもの。推奨するアーキテクチャに基づく。
- 個別のレポート（Caldova Auto の例）：アップグレード、クラウドへの準備状況、セキュリティのドメインごとに、必須の修正事項、データベースの対応などが並ぶ。
- **アーキテクチャ図の生成**：開発者が去ってしまい、ドキュメントも乏しい、という顧客の悩みに対して、エージェントがコードからリバースエンジニアリングして、データベースのアーキテクチャやエンティティモデルなどを提供する。

### 6.3 データベースを含むアセスメント

1. `modernize assess` を直接コマンドで実行できる。これは**ヘッドレス**な操作で、DevOps のパイプラインや VM の実行などに組み込み、組織のモダナイゼーションのシステムを自動化できる。
2. 今回は Auto と Home だけをアセスメントする。データベースが検出されると、既定でデータベースのスキルが呼び出される。プロンプトで、評価の方法を指定することもできる。
3. 例として、アプリ開発者がローカルで使っている SQL Express などの詳細も指定できる。PostgreSQL（Home の移行先）は、ライブのデータベースには接続せず、オフラインの手法で評価する。
4. 実行の最後に、データベースの知見を含む新しい readiness レポートが表示される。コードとデータベースの情報、推奨されるデータベース、ブロッカーなどが分かる。
5. Home には、**Oracle から PostgreSQL への readiness レポート**と、すでに提供されている「データアーキテクチャと永続化レイヤー」のレポートがある。後者は、DDL の観点で何を変更するか、それをアプリコードの近代化にどう生かすか、の理解を深める。
6. 集約されたアセスメントレポートから、アプリとデータベースの全体を見られる。アプリとデータベースのチームは別のペルソナだが、同じ知見を統一されたレポートで共有できる。

### 6.4 データベース担当者の作業（Oracle から PostgreSQL へ）

1. 「データの帽子（data hat）をかぶる」と言って、VS Code の PostgreSQL 拡張機能を使う。create migration project を選び、実際の Oracle サーバーに接続して、アセスメントを開始する。
2. 以降は、データベースチームの作業として、**早送りで見せている。** アセスメント、データの移動、スキーマの移行が完了し、DDL が得られる。
3. アプリ開発者として、DDL を置くフォルダーを用意し、modernize CLI に DDL の場所を伝える。
4. Oracle から PostgreSQL へのスキルには、変換オプション（baseline の確立、ユニットテストの作成など）がある。異なるプラットフォーム間の移行では、ビジネス層の動作が、データ層でも成功することを確認したいため。
5. `modernize plan create` で計画を作る。今回は、**Oracle から PostgreSQL への Java 側の移行だけ**を行い、既存の Java と Spring Boot は維持する。計画は仕様のようなもので、人間がレビューする。エージェントが裏で作業するが、計画の内容が意図どおりかを人間が確認する。
6. 計画から実行を作成する。完了後、Caldova Home で請求を送信すると、Oracle ではなく **PostgreSQL** に入る。Azure PostgreSQL のデータベースに直接接続してクエリを実行すると、先ほど作成した「roof damage」のレコードが表示された。

### 6.5 ルールブックでフレームワークをアップグレード

1. ルールブックは、Markdown ファイル。ガバナンスのポリシーが SharePoint、PowerPoint、Word にある場合も、Markdown にまとめる。
2. `modernize rulebook create` で、Markdown ファイルを指定して実行する。CLI がトークン最適化した形式を作る。内容は、charter、policies、targets、source。
3. 今回のルールブックには、Java を最新の LTS に、.NET を最新の LTS に、という内容がある。
4. すべてのリポジトリに適用するため、`.github` の下の modernize フォルダーに `config.json` を置き、そこに、ルールブックの中央リポジトリを指す portfolio の URL を定義する。近代化するリポジトリが、すべてそれにリンクしていれば、開発者が計画を生成するたびにルールブックが適用される。
5. 「upgrade to LTS」を指示し、エージェントが作業して、計画のプレビューが表示される。今回の例は、**.NET Framework 4.7.1 から .NET 10 LTS**、**ASP.NET MVC 5 から ASP.NET Core MVC**。
6. 実行が成功することを確認し、.NET のビルドが完了する。
7. 計画に戻り、**rulebook evidence**（ルールブックに定義された内容に、計画と実行が従ったかの証跡）を確認する。.NET と Java の両方で実施済みで、今回は Java の証跡ファイルを見せた。

### 6.6 カスタムスキルで Azure に移行

1. Caldova には、Azure のリソースを追跡するための独自の命名ルールがある。これを、カスタムスキル（Caldova Azure naming）として作成してある。一般的なスキルの形式で、スクリプトや参照資料を含められる。例えば、既存の PowerShell スクリプトや、決まった方法で作る Bicep を含められる。
2. 計画を作る。Caldova Home は Azure Container Apps に、Caldova Auto も Container Apps に移す。Auto は .NET と SQL、Home は Oracle から PostgreSQL。
3. 生成された計画には、スキルが選ばれて入っている。標準で提供される **infrastructure Bicep 生成**のスキルのほか、**Caldova Azure naming** と **Caldova Azure readiness** という、カスタムスキル由来のスキルが表示された。
4. 移行が完了し、アプリケーション全体が **Azure Container Apps** で動く。コンテナー化もされている。リンクを開くと、同じ Caldova のアプリケーションがクラウドで動いている。

この結果について Nish 氏は、以前は数か月かかっていた作業（何を評価するか、どれをクラウドに移すか、LTS へのアップグレードとコード変更）が、**数日**でできるようになった、と述べています。掛け合いの中では、今回の作業は「おそらく 1 週間で終わった」とも話しており、対象は「最も古いアプリの 1 つ」でした。コンテナーなので、負荷が上がればスケールできます。

### 6.7 イノベーション：チャットベースの新しい UI

2026 年なので、チャットアプリになるはずだ、という導入です。

1. 利用者は、姓と郵便番号で自分の契約（coverage）を探す。複数のフォームを入力する代わりに、自然言語でインシデントを報告する。
2. 例では、雹（ひょう）で車と屋根が被害を受けたことを書く。画像（AI 生成のもの）や、ワシントンのナンバープレートが写っているものを添付した。ナンバープレートの番号をチャットに書いていないが、必要ないという。
3. 送信すると、エージェントが書いた内容からすべてを推論し、**自動車の報告と住宅の報告の 2 つが必要**だと判断する。足りない情報は、自然言語で質問してくる（例：牽引が必要か、家にはまだ住めるか）。回答を返すと、エージェントが請求フォームを自動で作成する。
4. 担当者（adjuster）の画面では、会話の全体と、エージェントが生成した内容と顧客が入力した内容の違いが見られる。追加の質問は同じポータルでできる。提出すると、審査のプールに入り、担当者が審査を始められる。顧客はオペレーターとの保留待ちが不要になり、Caldova の従業員にも使いやすい。

**作り方の説明（語られた範囲）**

- 同じモダナイズ済みのコードを使い、GitHub Copilot でさらにリファクタリングした。巨大なモノリスではこれに対応できないため、マイクロサービスに分割し、API では同じロジックを保っている。
- 新しい API があり、モダンな .NET で始めている。
- 新しい **intake サービス**が、自動車の申請か住宅の申請かで、トラフィックを振り分ける。
- テストも完了している。
- 裏側に、Foundry の **intake agent** がある。ユーザーが画像を入れた場合に、車か家かを確認する、詳細を推論する、質問は最小限にする、という指示がある。また、既存の REST API（home API と auto API）を参照し、必須項目を満たす情報が揃っているかを確認し、足りなければ質問する。

Nish 氏は、AI を持ち込むだけでなく、ビジネス価値を足すための前提として、**まずアプリケーションをモダナイズする**ことが必要で、GitHub Copilot modernization がその開始を容易にする、と述べています。

## 7. 注意点・発表者の気付き

- **モダナイゼーションは「fire and forget」の旅ではありません。** 段階を踏み、最初に近代化する層を決め、テストを終えてから次に進むことを勧めています。デモでも、データベース、フレームワーク、Azure への移行、UI を、順に行っています。
- 計画は仕様のようなもので、**人間がレビューする**前提です。エージェントが作業しても、計画が意図どおりかを確認するのは人間の役割という説明です。
- データベースの統合は、現時点では**プレビュー**です。
- 概算のコスト見積もりは、**小売価格**に基づくもので、顧客の契約に基づく数値ではありません。リーダーシップとの会話を始めるための目安です。
- アセスメントでは、分析範囲を **full analysis** にすることが推奨されています（エージェントがより深く分析できるため）。
- 異種移行（Oracle から PostgreSQL）では、データベースだけでなくコード（ドライバーなど）の変更も大きく、データベースの変更をエージェントが理解してコードに反映させる必要があります。
- 発表では、料金、対応する具体的なバージョンの一覧、プレビューの利用条件は説明されていません。

## 9. まとめ

このセッションは、技術的負債が AI への取り組みを妨げているという課題から出発し、Azure Catalyst と GitHub Copilot modernization を、スケール、カスタマイズ、ガバナンスの 3 つの観点で説明しました。デモでは、12 リポジトリ（Java 6、C# 6）のアセスメント、Oracle から PostgreSQL へのデータベースとコードの移行、ルールブックによる .NET と Java のアップグレード、カスタムスキルを使った Azure Container Apps への移行を、順に示しています。

発表で新しく示されたのは、データベースの統合（プレビュー）、Rulebooks の GA、BYOM の GA です。さらに、モダナイズが終わったあとに、エージェントと新しい UI で、保険金請求の体験を変えられることも見せました。始め方としては、Cloud Adoption Framework の 90 日間のパスと、ドキュメント、ブログ、翌日のラボなどが案内されています。
