# BRK446 Build portable applications with Adaptive Apps

## 1. はじめに

このセッションは、アプリケーションを一度書けば、Azure でもオンプレミスでもエッジでも、さらに他社クラウドでも動かせるようにするための設計パターン **Adaptive Apps** を紹介するものです。登壇者自身が冒頭で「とても変わったセッション」と断り、Microsoft のイベントで Azure から出る方法を見せると述べているとおり、データ主権やデータレジデンシー、地政学的なリスクを背景に、Azure から切り離されても事業を継続できる構成を目指しています。

## 5. 発表内容の詳細

### 5.1 動機と、これまでのポータビリティ手法の限界

今このテーマに取り組む理由として、発表者は 3 点を挙げています。

* 顧客の声が明確であること（データレジデンシーとソブリンティへの継続的な対応）
* Arc 対応サービスや、OSS プロジェクトが数年で成熟してきたこと。とくに Radius は Azure CTO のイノベーション部門が始めた OSS で、アプリケーションをプラットフォーム固有の依存から切り離す抽象化を提供するもの
* AI 推論でのデータプライバシーへの懸念から、AI をエッジに移して手元でガバナンスしたいという要望が増えていること

ポータビリティ自体は新しい話題ではなく、これまで何度も試みられてきました。発表者は、代表的な 4 つのアプローチを挙げ、それぞれの難点を説明しています。

| アプローチ | 発表者が挙げた難点 |
| ---- | ---- |
| プラットフォームパリティ（クラウドとオンプレミスで同じ Azure を使う） | 100% の互換性は達成が難しく、あちこちに差が残る |
| 最小公倍数的な機能セット（複数プラットフォームの共通機能だけを使う） | プラットフォーム固有の機能が使えず、使える機能がごく小さくなる（発表者は「正確な用語ではない」と断っています） |
| Dapr のような抽象化でアプリケーションランタイムを分散させる | 複数のプラットフォーム依存が Dapr への依存に集約されるだけで、中間サービス無しにネイティブな書き方をしたいという希望に合わない |
| ポータブルなアプリケーションサーバー（J2EE、WebLogic、ASP.NET Core など）を使う | そのサーバーに制約される |

> 補足：発表者は Dapr について、初期バージョンに関わり最初の Dapr の本を書いたと述べたうえで「素晴らしいプロジェクト」と評価しています。

### 5.2 Adaptive Apps の原則

目標はシンプルで、アプリを一度書けば環境に合わせて適応し、どこでも動かせるようにすることです。デプロイ先として、Azure 上のクラウド、Arc やローカルの Kubernetes クラスター、ローカルサーバー、Amazon などの他クラウドが挙げられています。どこに置くかは、事業継続の要件や各ベンダーとの契約次第だと説明されています。そのための原則は次の 3 つです。

1. **パターンであり、フレームワークではない。** ツールやユーティリティは提供するが、核心は設計パターンで、ツールを使わず自分で選択してもよい
2. **ロックインしない。** データプレーン、管理プレーン、プロビジョニングの関心事を分離する。データプレーンは完全にネイティブで、Microsoft のランタイムやライブラリを読み込む必要はない。管理プレーンにも介入せず、デプロイと Day 2 運用は既存のネイティブな管理プレーンで行う。Adaptive Apps が提供するのは**プロビジョニング時のサポート**だけで、デプロイ後は各プラットフォームの管理下になる
3. **自分のペースで採用できる。** ごく小さな範囲から始め、徐々に広げられる

なお、Azure 上では最初からうまく動くようにするが、使わない選択をしても構わない、というのが発表者の立ち位置です。

### 5.3 抽象化のレイヤーと recipe の仕組み

ポータビリティには抽象化が不可欠で、「黒魔術はない」と発表者は述べています。概念としては 6 層の抽象化を考えており、スライド上は 7 層に見えるが、最下層の substrate はインフラの関心事として扱う、という説明でした。各層について、Azure が対応するプロトコルや標準、対応する OSS プロジェクトを調べ、**意見を持ったスタック（opinionated stack）**を組み立てています。パターン自体は汎用ですが、ツールはこのスタックに対応しています。選んだ OSS は Microsoft とは無関係で、完全に中立だと説明されています。

実装の流れは次のとおりです。

1. アプリケーション定義の中で、イングレス、サービス呼び出し、データベースなどのプラットフォーム依存を、「この種のイングレスが必要」のように**抽象リソース**として宣言する
2. 環境（environment）ごとに **recipe** を読み込む。recipe は、抽象リソースを具体的なデプロイに変換（hydrate）する
3. 例えば Azure 上ではイングレスの recipe が Azure Front Door にデプロイし、サービスは AKS の pod にデプロイする。AKS everywhere や自前の Kubernetes クラスターでは、そちらのネイティブなものに置き換える

ここで繰り返し強調されているのは、これは**管理プレーンの話**だという点です。コードを書く段階では、プロトコルを選んで使います。例えばメッセージングでは MQTT を推奨しており、MQTT で書いておけば、環境ごとの recipe で別のメッセージブローカーに対応づけられます。つまり Microsoft の API に対して書くわけではありません。データベースも好みのものを選べて、各環境に対応する recipe を用意してプロビジョニングします。

### 5.4 提供している共通機能と、認証の例

共通するアプリの関心事として、認証、認可、コンポーネント間のメッセージング、AI モデル管理、ワークロード ID、ガバナンスが挙げられました。スライドには選定したプロトコルが示されていましたが、トランスクリプトで具体的に言及されたのは、MQTT（メッセージング）、OIDC（認証）、OPA（ポリシー）、OpenTelemetry（可観測性）などです。この選択に同意すればツールで手早く構成でき、同意できなければ同じパターンで自分の選択をしても構わない、と説明しています。

例として認証が詳しく語られました。Azure 上では Microsoft Entra ID の利用を勧めますが、インターネットから切断された場合やエアギャップ環境ではどうなるか、という問題があります。断続的な接続なら token caching でしばらくしのげますが、新規ログインは難しくなります。そこで、**アプリケーションが自前の ID プロバイダーを持つ**方式をとります。選んだ OSS は **Keycloak** で、OIDC に対応しています。ID プロバイダーがアプリケーションと同じ場所にあるため、アプリが動いている限り認証できます。

フェデレーションにより、次との連携が可能です。

* Microsoft Entra
* ローカルの Active Directory（Entra の追加機能で Entra Connect と聞こえるもの〔音声認識では「Android Connect」〕を使うと、ローカル AD の資格情報を Entra テナントに同期できる、という説明）
* その他の ID プロバイダー

アプリケーションに必要な機能をアプリ側に持たせ、デプロイ時に基盤側の構成を変える、というのがここでの設計の考え方です。

### 5.6 Adaptive Apps から Adaptive AI へ

Adaptive Apps を紹介してまだ数か月ですが、反応は非常に好意的で、多くのセッション、ハッカソン、顧客とのプロトタイプが進んでいると発表者は述べています。同時に AI（特にエージェント型システム）についての質問が増えたため、自然な拡張として **Adaptive AI** を考えたとのことです。

まず既存のエージェント関連エコシステムを調査し、呼び出しチェーンを次のように整理しました。クライアントがネットワークメッシュやサービスゲートウェイを通じてアプリケーションを呼び、アプリケーションが（場合によってはエージェントゲートウェイ経由で）エージェントと通信します。エージェントはホスト上のランタイムで動き、大規模言語モデルを直接、またはモデルルーター経由で呼びます。これに、ガバナンスやオブザーバビリティといった横断的な関心事が加わります。Adaptive Apps と同じ方針で、独自のものを作るのではなく、人気のあるものを選ぶ、というやり方です。ランドスケープは日々変化しており、調査にかかるコストを顧客が負わずに済むのがこの取り組みの価値だと発表者は述べています。

現時点でのエージェント向けの選択は次のとおりです。

| 領域 | 発表で語られた内容 |
| ---- | ---- |
| Agent gateway | 利用を推奨。今回の例では、プラットフォームごとに管理方法が異なるエージェント ID のブートストラップに使っている |
| エージェントのホスティング | Foundry をサポート。他のホスティングでも構わない |
| エージェントフレームワーク | 意図的に特定のものに依存しない。どれを使ってもよい |
| 言語モデル呼び出し | AI gateway／AI router を推奨。今回は「light RIM」と聞こえる製品を選択（音声認識の都合で表記が確定できません）。他のプロジェクトでもよい |
| AI サービング | Project Kaito（Kubernetes 上でネイティブに動作。言語モデルを Kubernetes のリソースとして管理できる Microsoft の別プロジェクト） |
| オブザーバビリティ | OpenTelemetry |
| ID | Keycloak |
| ガバナンス | agent governance toolkit を OPA ポリシーに接続 |

AI gateway の価値としては、顧客がコストと価値創出に敏感になっていることを挙げています。少なくとも、複雑なリクエストは大規模言語モデルへ、単純なリクエストはより小さなモデル、ローカルモデル、あるいは決定的な関数にまで振り分けることで、性能とトークン消費のバランスを取れるという説明です。

これらは典型的なエージェントのワークロードを支えるには十分だと発表者は見ています。長期的な目標は、**ポータブルなエージェント**、つまり環境をまたいで適応できるエージェントを実現することです。

### 5.7 データ同期とエージェント統制の考え方

データ同期は難題であり、例えば Azure Fabric（聞こえた表記）にあるデータを、接続が途切れたあともローカルで扱えるようにするにはどうするか、という問題を発表者は挙げています（なおこの点のスライドは時間の都合で非表示にしたとのことです）。

推奨しているのは、**一方向の同期から始める**ことです。この言い回しには「すべてのシステムに当てはまるわけではない」という断りが付いています。単一の信頼できる情報源（source of truth）はクラウドのデータベースに置き、同期したい要素やオントロジーを選んでローカルに同期します。これにより、複雑な競合の可能性を避けられます。実際、メモリ同期のデモでも、クライアント側からは新しいメモリをコミットできない一方向設定にしています。

また、データ同期の機能は現時点でツールチェーンには組み込んでいません。各データベースプラットフォームには固有のツールがあり、そのレプリケーション機能を再現することは目指していないためです。ガイダンスとしては、データ同期はデータプラットフォームと直接取り組むよう勧めています。

エンタープライズ級のエージェントには、エージェントがどこにあっても一元的な制御とポリシー適用が必要です。ところが、クラウドから切断されたとき、「業務ができない」か「ガバナンス無しで業務を続ける」の二択になってしまうのが難しい点です。そこで追加するパターンが **grant-based consumption** です（発表者は「名前はその場で作った」と述べています）。

* クラウド側に grant 管理システムがあり、各エージェント／クライアントが定期的に新しい grant を受け取る
* 例として、「1 時間あたり 1,000 ドルまで業務を行ってよい」という grant を与える
* 切断されても、有効な grant を持っている間は動作を続けられる
* quota を超えたリクエストは拒否される
* grant はサーバー側で暗号化され、クライアントで検証される。クライアントの活動は改ざん不能な台帳（immutable ledger）に記録され、不正の可能性を減らす

これにより、接続の有無にかかわらず大規模なエージェント制御とガバナンスを実現できる、というのが発表者の説明です。

### 6.1 デモ 1: 株取引アプリ（認証とデプロイ環境の違い）

1. 株取引アプリが紹介された。銘柄は実在のものではないと断っている。フロントエンドとバックエンドが異なる言語で書かれたマルチティアのアプリで、MQTT ブローカーを介して通信する
2. デプロイ構成の画面で、利用しているプラットフォーム機能が示された。認証は Keycloak と Entra のフェデレーション、ローカルの agent gateway、AI gateway、イベントメッセージングは Azure Event Grid、エージェントは Foundry 上でホスト、といった構成で、すべて Azure ネイティブの構成だと説明されている
3. ポートフォワーディングを使っているため、アクセス先は localhost になっているが、実際には自分のマシンで動いているわけではない。リソースグループを開くと、コンピュートを担う Kubernetes クラスター、Event Grid、データコレクターが確認できた
4. Kubernetes クラスターのサービス一覧では、Istio、Otel collector、Keycloak のデプロイなどが動いていると説明された（Istio 関連の表記は音声認識の都合で確定できません）。発表者によれば、この構成は公開リポジトリにあり、後で同じことを再現できる。現実的な複雑さを持たせるために、意図的に複雑なアプリを選んだ
5. ポータルアプリには、Keycloak のローカルユーザー Alice としてログインしている状態だった
6. Keycloak の管理コンソールを開くと、実際の ID プロバイダーとして Entra が構成されている。フェデレーションは双方向の信頼関係が必要なので、Entra テナント側にも、ローカルホスト環境への信頼が構成されている。テナントには発表者本人のユーザーがあり、Windows Live アカウントで登録している
7. プライベートウィンドウを新しく開き、これを「クラウドデプロイ」として使った。OIDC でサインインすると Keycloak の画面が出て、Entra でのログインが選べる
8. Entra でログインした。画面は通常の Entra の体験で、発表者は顔認証を使ってサインインを完了した。サインインしたユーザーは発表者自身（Haishi Bai）だった
9. 続いて**ローカルデプロイ**を見せた。これはこのノート PC 上の K3s クラスターで動いており、すべてローカルである。Event Grid の代わりに Mosquitto の MQTT ブローカーを使っている。AI もローカルで、Kaito（発表者は発音に自信がないと述べつつ綴りを K-A-I-T-O と説明）を使い、言語モデルを Kubernetes のリソースとして管理している
10. まとめとして、同じアプリケーションを異なる環境にデプロイでき、recipe によってクラウドではクラウド側のインフラに、エッジでは全く異なるインフラに展開されることを確認した。プロトコルの互換性があるため、アプリはポータブルだという説明

### 6.2 デモ 2: エージェントのメモリのフェイルオーバー

発表者は「まだ開発中で、磨かれていない初期の成果」と断っています。クラウド上のエージェントで業務をしている最中にクラウドが落ち、クライアント側にエージェントを再展開すると、動くには動くものの文脈を失ってしまう、という課題に対し、**メモリのポータビリティ層**を用意したものです。片側でコミットしたメモリがクライアントに同期され、会話を引き継げます。

1. エージェントに「王様はロバの耳を持っている」と覚えさせる旨を伝えた
2. Boris 氏がリハーサルで乱数を言うことになっていたとして、会場に乱数を求めた。会場から「42」が出た
3. エージェントに到達できることを確認し、再度画面を更新してサインインした。メモリ同期に使うアカウントである Alice に切り替えた
4. 「Boris は 42 と言った」と伝え、メモリに保存された（保存先の名称は「advisor memory」と聞こえるが、音声認識の都合で表記が確定できません）。裏では、メモリは Postgres データベースに保存されていて、クラウドとローカルの間で同期される。ストアは別のものでもよい
5. ローカル環境にフェイルオーバーしたと仮定して、「メモリから、Boris は何と言ったか思い出して」と依頼した。何度か画面の更新が必要になった（発表者は「アプリのバグだと思う。直すか、PR を送ってほしい」と述べています）。質問を言い直した
6. 「Boris は 42 を選んだ」という回答が返った。この回答は、クラウドから同期されたローカルのデータベースに基づく
7. 一方向のコミット設定を確認するため、ローカルのクライアント側で「Boris は 400 と言った」と上書きを試みると、ローカル側のメモリは read-only になっていて、上書きできないことが示された

### 6.3 デモ 3: grant-based consumption（ピザ工場）

1. 設定は、100 人のシェフ（エージェント）を持つピザ工場で、合計 1,000 枚のピザを作ること。シェフは通信が不安定で、ときどきクラッシュする
2. grant ポリシーの画面では、grant は任意の数値指標に基づけるとしたうえで、この例ではピザの金額を指標にしている。ピザ 1 枚が 5 ドルという前提で、各シェフは最初は 3 ドル（単位はセント）しか持たず、初期状態ではピザを作れない
3. 時間が経つと grant が補充され、そのたび 3 ドルが追加される（補充の単位は音声認識の都合で確定できません）。サーバーとの接続が切れると更新できなくなるが、残高があれば作業を続けられる。エージェントごとに上限があり、60 ドル分のピザまでしか作れない
4. このポリシーは、エージェントがクラッシュしても切断されていても適用される。作業の前に、必ず grant を確認・検証するためである
5. 障害注入を設定した。30% の確率で切断、10% の確率でクラッシュする
6. Overview 画面で 100 のエージェントを読み込み、すべてオンラインで注文を受けられる状態にして、大きなジョブを起動した
7. 直後に、赤いエージェントがクラッシュし、黄色のエージェントがクラッシュはしていないが切断された状態になった。青いエージェントは、生涯のクォータを使い切って sleeping 状態になったもの。稼働中のエージェントが減るため、注文の処理は遅くなる
8. 切断中のエージェントには、割り当てられたがローカルにキューされた注文や、サーバーに送れないローカルのピザがあるかもしれない。再接続すると、差分は照合（reconcile）される。クラッシュや再起動、切断があっても、最終的にちょうど 1,000 枚を作ることが狙いだと説明された
9. 進捗を見ると、残りが 60〜70 枚の段階があった。グラフでは、最初は誰も 1 枚作れる分の grant を持たないので立ち上がりが遅く、grant が溜まると作り始め、使い切ると作れなくなり、最終的に安定する。黄色い線は一時的なネットワークの混雑で、ローカルにキューされたピザが提出できない状態を示し、時間がたてば照合される
10. 最後に、100 のエージェントで作る注文が完了した（最終枚数の数字は、聞き取りでは「one pizza」とあり不明瞭です）

## 7. 注意点・発表者の気付き

* 発表者は、Adaptive Apps の提供範囲は**プロビジョニング時**であり、データプレーンにも管理プレーンにも入らないと明確に述べています。デプロイ後の運用は、各プラットフォームのネイティブな仕組みで行います
* 一方向同期の推奨は「すべてのシステムに当てはまるわけではない」と断られています
* データ同期はツールチェーンに統合しておらず、各データプラットフォームのツールを使うことが推奨されています
* ポータブルメモリは「ごく小さなおもちゃのサンプル」であり、Adaptive AI のデモは「まだ進行中で、磨かれていない」ものだと述べられています
* ツールが採用しているのは、あくまで意見を持ったスタックです。パターンに従えば、別の選択も可能です
* Azure パブリッククラウドの方針（データレジデンシーやリージョン対応の継続強化）は変わらない、と発表者は明言しています
* 時間の都合で、データ同期のスライドは非表示にされました。デモ中には、アプリの不具合で何度か画面の更新が必要になる場面がありました

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* 接続が切れても、ローカルに置いた ID プロバイダー（Keycloak）で認証を継続できる
* 同じアプリを、Azure、ローカルの Kubernetes（デモでは K3s）などの異なる環境に、recipe を切り替えるだけで展開でき、プロトコルの互換性でポータビリティが保たれる
* 特定のフレームワークや技術、Microsoft 自体にもロックインされない。小さな範囲から段階的に採用できる
* AI gateway により、リクエストの複雑さに応じて大規模モデル、小さなモデル、ローカルモデル、決定的な関数に振り分けられ、性能とトークン消費のバランスを取れる
* grant-based consumption により、切断中でも有効な grant の範囲で業務を続けられ、超過した要求は拒否されるため、接続の有無にかかわらず統制が効く
* 出口が用意されていること自体が、顧客が Azure にとどまる安心感を高めている、というフィードバックが得られている
* 製品選定の背景調査を、顧客が自分でする必要がない

導入事例の固有名詞や数値は、発表では示されていません。

## 9. まとめ

Adaptive Apps は、アプリケーションの意図とプラットフォーム実装を分離する**設計パターン**です。抽象リソースと環境ごとの recipe によって、プロビジョニング時にだけ環境へ適応させ、データプレーンと管理プレーンはネイティブのままに保ちます。認証では Keycloak を自前の ID プロバイダーとし、Entra やローカル AD とフェデレーションすることで、切断時にも使える構成にしています。

Adaptive AI では、agent gateway、AI gateway、Kaito、OpenTelemetry、OPA などを使ったエージェント向けの構成を示し、デモでは、一方向同期によるメモリの引き継ぎと、grant に基づく切断時のガバナンスを見せました。長期的な目標は、環境をまたいで動くポータブルなエージェントです。OSS として公開されており、イシュー、PR、マイクロハッカソンを通じたフィードバックが呼びかけられています。
