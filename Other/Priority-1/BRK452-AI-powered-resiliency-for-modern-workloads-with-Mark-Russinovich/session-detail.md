# BRK452 AI-powered resiliency for modern workloads with Mark Russinovich

## 1. はじめに

このセッションは、Azure でアプリケーションを動かしている開発者・IT 管理者に向けて、「障害を前提にした設計（レジリエンシー）」をどう進めるかを解説したものです。前半では Mark Russinovich 氏が、自身が経験した 2014 年のストレージ障害を出発点に、Azure が障害から学んで取り入れた仕組みと、利用者側が持つべき心構えを話しています。後半では Azure Resiliency チームの Amit Ganguli 氏が、AI エージェントを含む新しいレジリエンシー向けの体験をデモで紹介しました。最後は Banco Santander の Enrique González Bejarano 氏による実体験の紹介と、Ignite で発表された新機能の整理で締めくくられています。

先に結論を挙げると、発表の核心は次の 2 点です。

- 障害対策は「最初から」計画する。後から足すほど難しく、費用もかかる。
- Azure Infrastructure Resiliency Manager や Resiliency Agent などのツールで、「新規構築時から (Start)」「今ある環境を (Get)」「維持し続ける (Stay)」の各段階を、AI で簡単にできるようになってきた。

## 4. 発表者が伝えたいメッセージ

Mark 氏が一貫して伝えているのは、「プラットフォームが何をしてくれて、何は自分でやらなければならないのかを、はっきり理解したうえで設計する」ということです。リージョンがまるごと止まる可能性は、Azure の責任かどうかにかかわらず存在します。それでも、1 つのリージョンに置いたデータが自動的に別リージョンへ移ると考えている顧客が、今でもいると Mark 氏は述べています。可用性ゾーンも同じで、ゾーンに固定した仮想マシンは、そのゾーンが止まっても自動では別のゾーンへ移りません。

もう 1 つのメッセージは、AI 時代だからこそ信頼が差別化要因になるという点です。AI がソフトウェアを書くようになり、複雑なソフトウェアでも容易に複製できるため、「ソフトウェアを持っていること」自体は以前ほど競争上の堀になりません。Mark 氏は、データのほかに差別化できるのは信頼だと話し、隣のスタートアップがバイブコーディングで作った競合製品に顧客が流れないようにするため、レジリエンシーは以前にも増して重要だとしています。

Amit 氏のパートでは、レジリエンシーは一度で終わるものではなく、ライフサイクルとして捉えるべきだというメッセージが続きます。デモ全体が「Start（最初からレジリエントに）→ Get（レジリエントにする）→ Stay（レジリエントであり続ける）」という流れで組み立てられていました。

## 5. 発表内容の詳細

### 5.1 2014 年のストレージ障害と Safe Deployment Policy

Mark 氏は 2010 年から Azure に関わっており、自身にいちばん深く影響したインシデントとして、2014 年の「great storage outage」を挙げました。

発端は、ストレージチームの技術者が行った小さな性能改善でした。変更対象は、Xbox が多用していたテーブル（table）提供のコードです。Xbox はすでに Azure の大口利用者で、プレイヤー情報やゲーム統計の取得が速くなる見込みの変更でした。担当者は優秀で、統合テストと機能テストをこなし、テストクラスターに展開して確認し、すべて合格しました。そこで「軽微な変更で低リスク」と判断して、世界中のストレージの環境に展開しました。

しかし 1 時間ほどで、ストレージの環境が応答不能になり始めます。変更したコードは Blob のコードパスと共有されており、誰かが長さゼロの Blob 読み取り（Mark 氏いわく、0 バイトを読む理由はないはずのリクエスト）を渡すと、無限ループに陥るというものでした。フロントエンドが無限ループに入るとクライアントは応答がないのでリトライし、ロードバランサーは「このサーバーはオフライン」として次のサーバーへ振り向けます。こうして障害が世界中のストレージに広がりました。

この経験から、「どんなに小さな変更でも低リスクとは言えない。すべての変更を高リスクとして扱う」という方針を立て、**Safe Deployment Policy** を導入しました。現在も続いています。展開は、まず pilot リージョン、次に small、medium、heavy の順に進め、各段階の間にはかなり長い時間を置いて、問題が起きていないか監視します。Mark 氏は、これで Azure の信頼性は大きく向上したと話しています。

### 5.2 なぜ今、レジリエンシーなのか

レジリエンシーを軽んじれば、収益の損失、顧客の信頼の毀損、ブランドへの影響につながります。Mark 氏は、これが AI とソフトウェアの安価な生産の時代にさらに重要になると述べています。前述のとおり、差別化の軸がデータと信頼になるためです。

### 5.3 利用者が陥りやすい誤解と、Azure 自身の教訓

Mark 氏は、Microsoft 自身も落ちてきた罠だと断ったうえで、いくつかの点を挙げています。

**（1）プラットフォームがやること／自分がやることの混同。** 初期のころから、リージョン障害に備えるよう顧客に話してきたとのことです。原因は Azure 側の問題かもしれませんし、電力会社の停電で発電機が起動しない、インターネットから切り離される、地震や洪水でリージョンのデータセンターが被災する、といった Azure の手に負えない理由かもしれません。それでも「アプリを別のリージョンに移してくれるのでは」と考える顧客がいたそうです。

**（2）計画を後回しにすること。** 最初に計画しないと、後からやるのは格段に難しく、高くつきます。Mark 氏は、エージェントによってコストは下がっていくとしつつも、レジリエンシーの計画を終盤や本番稼働後にすると、コストや期間を読み違えると警告しています。

**（3）何をレジリエンシーとして測るか。** Azure ではこれに長く苦労したそうです。「サービス X が応答しない」と顧客から苦情が来ても、社内のダッシュボードでは「サービス X は正常」と出ていました。掘り下げると、ヘルスの見方が顧客の体験を見ていなかったのです。そこで、全サービス共通の SLO（Service Level Objective）と SLI（Service Level Indicator）を採用しました。例として、秒あたりの成功リクエスト数、スループット、失敗率、秒あたりに処理されたリクエスト量などが挙がっています（最後の項目は音声が不明瞭です）。これらは共通のライブラリで Azure のすべてのサービスから出力されます。

その上で、Brain と呼ばれるシステムが、ML と AI を使って SLI を見て SLO からの逸脱（drift）を検知します。SLO はリージョンの利用状況によっても変わりうるため、システムが自動で推定します。逸脱があればチームにインシデントを起票したり、規模が大きければ障害を宣言したりします。Mark 氏は、これを「顧客レベルのレジリエンシーと信頼性を定義して測る」例として示しました。

**（4）共通標準の採用。** SLI/SLO をチームごとに独自に決めていたら、共通基盤と Brain による全体の推論のメリットが得られません。Safe Deployment も同様で、以前は各サービスが独自の展開システムを持っていましたが、共通の展開システムに統合しました。さらに、「SDP を使ってください」というルールだけでは不十分で、現在はステージの順序（stage map）と待ち時間（bake time）を強制するポリシーを置いています。チームが間違えられない仕組みにしてあるということです。

### 5.4 共有責任の考え方

Mark 氏は、クラウド初期の 2010 年代前半から示されてきた共有責任の図を、現在のハイパースケーラーの概念に当てはめて説明しました。

| 項目 | Mark 氏の説明 |
| --- | --- |
| Azure の責任 | ハードウェアのインフラと、Resilient Foundation（回復性のある基盤）。ゾーン指定のサービスは、VM をあるゾーンに置いたらそのゾーンで動かし続ける。 |
| ゾーン回復性のあるサービス | 例として Azure Storage。LRS（ローカル冗長）とゾーン回復性のあるストレージがあり、後者は、どれか 1 つのゾーンが落ちても、他の 2 つのゾーンが読み書きを支えるため、完全に運用を続けられることを保証する。 |
| Azure が提供するツール | Azure Chaos Studio と、Azure Advisor の Resiliency Insights。ガイダンスと自動化により、アプリやサービスをより回復性の高い状態に移せる。例えば、ゾーン回復性が必要なアプリの一部なのに LRS のままのストレージアカウントを、ゾーン回復性のあるストレージアカウントに移す、といった提案。 |
| 利用者の責任 | 自分のアプリケーションを定義し、その下にあるプリミティブを使って回復性を実現する。 |

リージョン障害に耐えたいなら、「リージョンが落ちるリスクと影響はどれくらいか」を考える必要があります。Mark 氏は、Azure 上の大手小売業の顧客の例を挙げました。ブラックフライデーには 1 時間止まるだけで数千万ドル規模の売上を失い、評判にも大きな傷がつきます。顧客は別の小売業者に移れるためです。そこでそうした顧客は、2 つのリージョンにとどまらず、米国と欧州にまたがる複数のリージョンで回復性を確保しているとのことです。

### 5.5 エージェントによるレジリエンシーの強化と 3 つの柱

Mark 氏は、前日のイノベーションセッションで話した内容（Azure Catalyst と呼んでいます。音声認識の都合で表記が確定できません）に触れ、エージェントの時代には、エージェントにアプリを回復性のあるものにしてもらえると述べました。以前は、チームを何週間も本来の業務から外して計画を練り、Bicep テンプレートを書き換える必要がありました。今は、エージェントに脅威モデルを作らせ、リスク分析を返させ、コードの更新と最小限のダウンタイムでのデプロイ更新まで任せられるという考えです。エージェントは、エンジニアリングチームを支えるアドバイザー兼エンジニアになります。

その上で、考えるべき 3 つの柱として次を挙げています。

1. **インフラ**: 仮想マシンが動き続けること、使うサービスのゾーン回復性（例: App Service のゾーン回復性のあるバージョンを使っているか）。
2. **データ**: バックアップを取り、そのバックアップをテストして復元できること。毎日バックアップは動いていると言っていたのに、久しくテストしていなかったために復元が失敗した、という IT 管理者の失敗はよくある話だと Mark 氏は述べています。あわせて、オフラインのコピーを持つことも重要だとしました。
3. **サイバーリカバリ**: システムが止まったとき、攻撃者が環境に入り込んだとき、どうやってその攻撃者を環境から排除するか。

データについて Mark 氏は、AI を使った攻撃の主要なカテゴリとして、ランサムウェアが増えるという予測を述べています。金銭的な価値があり、今ではエージェントを手に入れれば誰でも身代金を要求できるからです。重要なデータをどう守るか考えてほしいという呼びかけでした。

### 5.6 紹介動画

Mark 氏の話の後に、動画（Speaker 1 によるナレーション）が流れました。内容は次のとおりです。

- 重要な業務を支えるアプリには、インフラ・データ・サイバーという 3 つの柱のレジリエンシーが必要。アーキテクチャも脅威も変わるため、レジリエンシーは継続的に検証しなければならない。
- Azure のポータル、API、AI を使ったエージェント型サービスを通じたレジリエンシー体験を、1 か所に統合して提供する。
- Resiliency Agent が、目標の定義、リスクの検出、対応の推奨、準備状況の検証をし、トレードオフを評価しながら回復できる。
- 個々のリソースやアプリケーションのレジリエンシーを見て調整できる。破損や構成ミスから長期保持まで、回復に対応する。
- サブスクリプションやテナントをまたいだ、迅速でスケーラブルな復旧に対応する。

### 5.7 Amit 氏のパート：新規アプリのレジリエンシー構成（Start）

Amit 氏は、Azure Resiliency が独立したプロダクトチームであることを強調したうえで、約 15 分のパートで、顧客シナリオや社内で学んだ教訓、ツールの進化を紹介すると述べました。題材は、Amit 氏が「our favorite customer」と呼ぶ「Caldova」が新たに追加する決済処理アプリです（Caldova の綴りは音声認識の都合で確定できません）。

構成は次のとおりです。

- 顧客のアクセスは Azure Front Door から入る
- Web アプリは Azure App Service
- 複数の仮想マシンへのトラフィックをロードバランシングする
- バックエンドのトランザクションには PostgreSQL
- メッセージングに Azure Service Bus
- キー管理に Azure Key Vault

この図からは、セキュリティやパフォーマンス、ネットワーク構成の見通しが得られます。一方、インフラ障害の影響を抑える（ゾーン回復性など）観点では、リソースの種類ごとに考える必要があるため、より複雑になります。Amit 氏は、この複雑さを抽象化するのが今回のレジリエンシー体験だと述べました。具体的には次の 3 つです。

1. アーキテクチャ図を、AI を使ったレジリエンシーのエージェントにアップロードして、あるべき状態に必要なことを特定できる。
2. Terraform、Bicep、ARM など、選んだ形式のインフラストラクチャ・アズ・コードのテンプレートを生成できる。
3. これまでもリソースからサブスクリプション、管理グループまでの階層には対応してきたが、さらに、複数のサブスクリプションにまたがるリソースを **Service Group** としてまとめ、アプリケーションの境界として扱える。

### 5.8 Amit 氏のパート：運用中の環境をレジリエントにする（Get）

Azure 上でアプリを運用していると、構成のドリフトが起き、リソースが追加されたり削除されたりします。これまでは、そうした重要な資産を追跡し、単一障害点を特定し、望ましい状態に到達するために何をすべきかを把握するのが、事実上不可能だったと Amit 氏は述べています。

そこで次の機能が紹介されました。

- Azure Resource Graph 上で、リソースの相互関係と依存関係をもとに、AI がアプリケーションの境界を検出する。
- アプリケーションの重要度（criticality）と目標（goals）を入力してもらうことで、推奨事項を個別化（hyper-personalize）する。これにより、コストと投資対効果を考慮した推奨ができる。
- 推奨に基づいて行動する。Mark 氏が話した SLO と SLI は、オブザーバビリティの観点でも取り入れられており、アプリケーション境界に対して SLI を確認でき、Azure のヘルスモデルでリソースの状況を把握できる。また、Chaos Studio を利用したドリルで、レジリエンシーの状態を検証できる（トランスクリプトでは "Kiosk Studio" と表記されています。Mark 氏は先に Azure Chaos Studio に言及していますが、音声認識の都合で確定はできません）。
- これらをダウンロード可能なレポートとして書き出し、ポータルを開かない関係者との意思決定に使える。

### 5.9 Amit 氏のパート：ステイ・レジリエント（データ、リージョン、サイバー）

Amit 氏は、運用を続ける中でのリージョン構成とデータ保護の話に移りました。

**リージョンの選択。** 現在の地政学的な状況もあり、従来のペアリージョンの考え方をやめて、セカンダリリージョンを自分で選べる「region of choice」を求める声が増えているとのことです。レジリエンシーのためだけでなく、データ所在地（ソブリン）の要件とのトレードオフにならないようにするためにも重要です。ほとんどのサービスが region of choice に対応し始めているものの、「まだ完全には完了していないが、正しい道を進んでいる」と説明しています。

**セカンダリのデータコピーの置き場所。** Mark 氏が話したとおり、リージョンが落ちたときにセカンダリリージョンが自然に立ち上がると想定してはいけません。Azure Backup では region of choice を使い、セカンダリリージョンのコンテナー（vault）に復旧できます。

**サイバーリカバリ。** システムは相互に接続されており、サイバー攻撃の可能性は常にあります。テナントがロックアウトされることもありえます。したがって、復元ポイントだけでなく、まったく新しいテナントに復旧できる能力にも自信を持つ必要があります。

### 5.10 Banco Santander の事例（対談）

Surya 氏は Banco Santander を、ヨーロッパ最大級の銀行の 1 つで、9 つの主要市場で 1 億 8,900 万人を超える顧客にサービスを提供していると紹介しました。AI 主導の変革と運用レジリエンシーを組み合わせて進めているとのことです。Enrique 氏は、Global Azure Architecture Lead として登壇しました。対談の内容は次のとおりです。

**Santander のレジリエンシー戦略。** Enrique 氏によれば、レジリエンシーは設計段階から始まります。複雑な課題をレイヤーに分け、レイヤーごとに解決します。まず基本として、プラットフォームとアプリケーションのランディングゾーンで複数の可用性ゾーンを使います。次にバックアップです。強く規制された業界のため、規制がベストプラクティスの順守にもつながっています。Azure Backup では、データを最長 10 年保持する場合があり、そのため Microsoft のチームとともに製品の限界に直面したとのことです（この部分は音声が不明瞭です）。最後に、設計だけでなくテストも行います。定期的にドリルを実施し、ゾーンのリソースを落としても、アプリが動き続けることを実証しています。

**不確実な情勢への備え。** 毎週ニュースを開くと不確実な時代だと感じるが、備えることしかできない、と Enrique 氏は述べ、Mark 氏と同じく、レジリエンシーはごく初期の段階から組み込むべきだと話しました。規制の面では、一部の会社がローカルレジデンシー（特定の国や地域に置くこと）を重視しており、そこが出発点です。そのうえで、クラウドでは旅として捉え、マルチリージョンの災害復旧シナリオに進めているとのことです。

**Azure の機能で助かっている点。** Enrique 氏は 3 つ挙げています。

1. **Azure Backup のネイティブバックアップ。** 主要コンポーネントの 1 つが Azure Data Lake で、今年ネイティブバックアップを実現でき、大きな改善になった（対象の言い方は聞き取り不明瞭）。
2. **region of choice。** 待ち望んでいた機能で、現在パイロット中。マルチリージョン化に向けた主要な機能の 1 つ。
3. **Azure Infrastructure Resiliency Manager。** アプリは設計し、デプロイし、その後も進化していく。テストはしているが、レジリエンシーを大規模に維持する助けになるツールは非常に有用なので、パイロット中。

Enrique 氏は最後に、AI アシスタントを伴った監査人についても触れています。監査プロセスに規模と深さをもたらすので、このツールによってレジリエンシーの状態を維持するだけでなく、継続的に評価されていることを証明する助けにしたい、という期待を述べました（この部分は音声に途切れがあり、発言の細部は確定できません）。

### 5.11 Ignite での発表事項と直近 6 か月の提供開始機能

最後に Surya 氏が、新機能を整理しました。

| 領域 | 内容 |
| --- | --- |
| インフラ | **Azure Infrastructure Resiliency Manager が Ignite で一般提供（GA）。** ゾーン回復性の基盤を、リージョン回復性にも広げている。同様のアプリケーション構成要素で、クロスリージョンの DR ができる。Azure Site Recovery にも投資を継続している。影響の大きい信頼性リスクやコスト削減の機会を確認できるようになり、ServiceNow や Jira といった ITSM との統合もある。 |
| データ | ワークロードの対応範囲を拡大した（例として Cosmos DB。ほかにも多数）。要望の多かったクロスリージョンバックアップ（region of choice）が利用可能になった。 |
| サイバーリカバリ | Azure Backup が air-gapped vault と immutable backup に対応していることは従来どおり。そこにサイバーリカバリの準備（cyber recovery readiness）を加えた。クロステナントのリストア、大規模リストア、脅威検出を組み合わせたシナリオに対応し、リカバリプランも提供する。これらの一部はすでにパブリックプレビューになっている。 |

## 6. デモ・手順

デモは Amit 氏が 3 本行いました（画面の細部は音声からは確認できないため、語られた範囲だけを書きます）。

### 6.1 デモ 1：Resiliency Agent で新規アプリのゾーン回復性を構成する

1. ポータルの「Resiliency Overview」ページで、Azure Copilot を呼び出す。
2. 名前の付いた 6 つのエージェントの 1 つ、Resiliency Agent を開く。
3. 先に示した決済アプリのアーキテクチャ図をアップロードし、「ゾーンのレジリエンシー姿勢を適切に構成するのを手伝ってほしい」と依頼する。
4. エージェントが数秒で図の中のリソースを識別する。Azure Front Door について、Standard か Premium の SKU のどちらにするかなど、個別の質問もしてくる。
5. すべてのリソースを確認すると、リソースの種類ごとにゾーン回復性を構成する方法をまとめた詳細な Markdown ファイルが生成される。例えば VM の構成方法が書かれており、ロードバランサーはデフォルトで回復性があること、App Service のようにそのオプションを提供する特定の SKU があることが示される。
6. 内容に納得したら、インフラストラクチャ・アズ・コードのテンプレートを作成する。今回は Bicep を選択（Terraform や ARM テンプレートも選べると説明）。
7. 生成された各リソースの Bicep テンプレートを開くと、ゾーン回復性がデフォルトで構成されている。複数ゾーンの複雑さがどう扱われているかも確認できる。
8. 納得すればデプロイする。これが新しいアプリのデプロイ方法だと説明。
9. 続いて、境界の観点から見る。ここでは手動で、「Caldova Pay」というアプリケーションを作成し、先ほど作ったリソースをメンバーとして追加する（後ほど AI を使うやり方を示すと予告）。
10. レジリエンシーのポータルに戻ってそのアプリケーションを検索し、グループ化された境界を開くと、すべてのリソースが適切なゾーン回復性の状態でデプロイされていることが確認できる。

### 6.2 デモ 2：ポータルでの境界検出とリスク評価

1. レジリエンシー体験のオーバービュー（ランディング画面）を示す。インフラのレジリエンシー、Service Group、タブのドロップダウンがあり、重要度と目標、ドリル、上位の推奨事項を見られると説明。
2. Service Group をまだ作っていない状況を想定し、「resources at scale」ビューでゾーン回復性の状態を確認する。
3. 画面上部のアクションから、Copilot で境界を自動判定して Service Group を作る操作を選び、エージェントに、指定したサブスクリプション内のアプリケーション境界に含まれるリソースの特定を依頼する。
4. エージェントはしばらく実行した後、リソースごとに信頼度（high / medium / low）のスコアを返す。先に示した変更を含めたアプリケーション境界と比べ、信頼度が high のリソースが、境界にしたいものと一致していることを確認する。
5. Service Group の作成を指示する。デモ 1 と同じ画面が表示され、詳細が分かる。ここで重要度のティア（criticality tier）とゾーン回復性の目標を追加でき、ゾーン回復性に関する具体的な推奨が得られる。
6. コストとダウンタイムの影響を、同じくエージェントに尋ねる。リソースの種類ごとに、コストへの影響と必要な作業が一覧で返る。
7. 詳細なレポートを開く。左側にゾーン回復性の状態、右側により豊富なコンテキストが表示される。リスク評価ビューでは、エラーバジェットが使い切られつつあること、リカバリプランが構成されていないこと、ドリルが実施されていないことが指摘され、ミッションクリティカルなワークロードなら優先して対処すべきだと示される。
8. このレポートはダウンロードして持ち出せる。

なお Amit 氏は、Ignite の直後にこれをリージョンのレジリエンシーにも拡張し、RPO（目標復旧時点）と RTO（目標復旧時間）を設定できるようにすると述べています。

### 6.3 デモ 3：バックアップと復旧（データ・サイバー）

1. 同じ「Resiliency Overview」ページから始め、前に見せた resources at scale ビューで、ゾーンの情報から、バックアップの状態に切り替える。
2. 保護されていないリソース（unprotected resources）を開き、サブスクリプション内の VM のバックアップを構成する。
3. やり方が分からない場合は Copilot に尋ねられる。PowerShell やスクリプトを使う方法など、いくつかの選択肢が示される。ここではポータルを使う方法で進める。
4. backup のブレードから Azure の Recovery Services Vault に進み、セカンダリリージョンにこの vault を作成する。サブスクリプションの VM は UAE North にあり、vault は Sweden Central に作る（トランスクリプトでは "UA North" とも表記）。リージョン選択で region of choice のオプションを選び、Sweden Central を指定する。これで、vault はペアリージョンではない、UAE North から離れたリージョンに置かれる。
5. 次に、保護するリソースを追加する。まずバックアップポリシーを設定する（バックアップの頻度と保持期間）。
6. UAE North の VM から対象を選び、検証が進むとバックアップが Sweden の vault に保存される。
7. リストアには複数の選択肢がある。VM を一括でリストアすることもできる。ここでは単一の VM を、セカンダリリージョンの Sweden にリストアする様子を示し、vault から復元するオプションを選んで「Restore」を押す。
8. レジリエンシーのブレードに戻り、サイバーリカバリの観点で、作成した Recovery Services Vault を確認する。Amit 氏は、テナント内で取るバックアップよりも安全な理由として、次を挙げた。
   - 論理的にエアギャップされている
   - vault とストレージの両方のレベルでイミュータブル（変更不可）
   - 誤削除を防ぐソフトデリートがある
   - マルチユーザー認証があり、単独のユーザーが全権限を持てない
   - 暗号化は、Microsoft が提供するキーでも、顧客が用意するキーでも使える
9. サイバーリカバリの観点では、脅威検出、サブスクリプションをまたぐリストア、サイバーテナントリストア（cyber tenant restore）がある。テナントがロックアウトされても、新しいテナントにバックアップから直ちにリストアできると説明している。

## 7. 注意点・発表者の気付き

- **リージョンやゾーンへの「自動移行」を期待しない。** 1 つのリージョンに置いたデータは自動で別リージョンには移らず、ゾーンに固定した VM は、そのゾーンが落ちても自動で別のゾーンに移りません。セカンダリリージョンも勝手に立ち上がりません。
- **小さな変更も高リスクとして扱う。** 2014 年の障害は、軽微な性能改善と、共有されていたコードパスが原因でした。テストがすべて通っても世界規模の障害になりえます。
- **ダッシュボードが正常でも顧客体験が正常とは限らない。** 測るべきは顧客レベルの体験で、SLI/SLO を共通化して測る必要があります。
- **ルールだけでは足りず、ポリシーで強制する。** Safe Deployment は、ステージの順序と待ち時間をポリシーで強制しています。
- **バックアップは復元テストまでが仕事。** 毎日動いていても、復元を試していなければ失敗する可能性があります。オフラインコピーも重要です。
- **ランサムウェアの増加。** AI で誰でも攻撃を仕掛けやすくなるため、重要データの保護とサイバーリカバリを考えるべきだという予測です。
- **最初に計画する。** 後から足すほどコストも期間も読みにくくなります。
- **リスクと影響の大きさに応じて、冗長化の範囲を決める。** 大手小売業の例のように、影響が大きければ 2 リージョンにとどまらず複数リージョンに広げています。
- **region of choice はまだ道半ば。** Amit 氏は、ほとんどのサービスが対応し始めているが、まだ完全には終わっていないと述べています。
- **Santander の指摘。** データを 10 年保持するような使い方では、Azure Backup の製品の限界に直面したことがあるそうです。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **複雑さの抽象化。** リソースの種類ごとのゾーン回復性の設定を、アーキテクチャ図のアップロードと対話から、IaC テンプレートの生成まで進められる（デモ 1）。
- **既存環境の可視化。** Service Group とアプリ境界の AI 検出、重要度と目標に基づく個別化された推奨、コストとダウンタイムの影響、レポートの書き出しで、関係者との意思決定が速くなる（デモ 2）。
- **回復の柔軟性。** region of choice により、ペアリージョンに縛られず、データ所在地の要件も満たしながらセカンダリリージョンに復旧できる。テナントがロックアウトされた場合でも、新しいテナントに復旧できる（デモ 3）。
- **Banco Santander の実例。** ゾーン障害を想定したドリルでアプリが動き続けることを実証していること、Azure Data Lake のネイティブバックアップが大きな改善になったこと、region of choice と Azure Infrastructure Resiliency Manager をパイロット中であることが語られました。成果の数値は発表では示されていません。

## 9. まとめ

このセッションは、2014 年のストレージ障害という Azure 自身の失敗談から始まり、障害対策は最初から計画し、プラットフォームの責任と利用者の責任を区別して設計することの重要性を示しました。レジリエンシーはインフラ・データ・サイバーの 3 つの柱で捉え、新規構築時、既存環境の改善、継続的な維持という流れで進めるものです。Azure には、Resiliency Agent、Service Group、Azure Infrastructure Resiliency Manager、region of choice 対応の Azure Backup といった道具が揃ってきています。Ignite では Azure Infrastructure Resiliency Manager の GA に加え、データ保護の対象拡大とサイバーリカバリ機能の強化が発表されました。
