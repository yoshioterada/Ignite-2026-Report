## 5. 発表内容の詳細

### 5.1 学びのフレームワークと SRE Agent

Bilal 氏は、新しいインフラを作るのは「学びの問題」だとして、次の 3 ステップを示しています。

1. **難しい問題を選ぶ**。デモ用ではなく、日常で本当に必要な、利害の大きい問題を選ぶ。
2. **問題を解く（作る）**。
3. **学びを顧客に返す**。

選んだ「難しい問題」は、自分のチームが運用するサービス群の運用負荷です。規模は次のとおりです。

| 項目 | 規模（発表での表現） |
|---|---|
| 管理する VM コア数 | 8 桁 |
| VM 数 | 7 桁 |
| 顧客数 | 6 桁 |
| 開発・運用するエンジニア数 | 3 桁前半 |

サービスは 24 時間 365 日、全リージョンで動いており、障害対応に加え、サービスの健全性の傾向を監視して長期的な問題を予見する作業もあります。これらを engineering toil と呼び、**Azure SRE Agent** を自己資金で開発して負荷を減らそうとした、という経緯です。

### 5.2 エージェントを本番で動かすための技術課題

SRE Agent は本番環境の一部として動き、信頼できる場所で、安全に動く必要がありました。Bilal 氏は、これは課題の「ごく一部」だとしたうえで、次の点を挙げています。

1. **エージェント単位の ID（per agent identity）**：各エージェントに、呼び出すリソースへの必要最小限の権限だけを与える。
2. **「脳」と「手」の分離**：LLM（脳）が外部とやり取りし、ツールを呼び、コードを書いて実行する部分を「手」と呼ぶ。手は信用できないため、**ハイパーバイザーで隔離された sandbox** に閉じ込める。
3. **sandbox の外での監視**：sandbox に出入りするネットワークアクセスは、sandbox の外側にある egress レイヤーで検査・監視し、制限もできるようにする。sandbox 内のコードは信用しないため、内側では行わない。
4. **シークレットを持たない sandbox（secretless sandbox）**：手にシークレットを渡すと、保存や外部送信が起きるおそれがある。そのため sandbox は秘密情報に直接アクセスさせない。

> ご参考：Bilal 氏は、この構造を「層になったケーキ（layer cake）」にたとえています。

### 5.3 社内での広がりと成果

SRE Agent を作っている間に、Microsoft 内の多くのサービスチームが同じ課題（多数のコアに対して少数のエンジニア）を抱えていることが分かり、**営業をしなくても自然に（organic に）** ほぼ全ての部門で使われるようになった、と説明しています。

直近の数字は次のとおりです。

* 3,000 を超えるエンジニアリングチームが利用
* 先月だけで約 400 万件のインシデントを処理。ここでの「処理」は、エージェントがコンテキストを提供して支援する場合と、ごく一部の安全な操作では実際に緩和措置を実行する場合の両方を指す
* 自動的に緩和アクションが実行されたケースで、緩和時間の中央値が「100 から 4」に減少（単位は発表では語られていません）
* 社内の本番で稼働するエージェントは、グラフを正しく読めていれば約 12,000

外部の顧客向けにも SRE Agent が提供され、外部利用は急成長している（hockey stick growth）と述べています。

### 5.4 顧客に提供するビルディングブロック

Bilal 氏は「インフラ屋として、他の人が必要なものを作れる部品を作りたい」として、次の 3 つを挙げています。

1. **zero trust sandbox**：上記の設計原則に基づく sandbox
2. **governance layer**：sandbox の外側にコードを置き、仲介された egress などを制御する層
3. **エージェントごとの ID** を簡単に与える仕組み

### 5.5 Nir 氏：プロダクトへの実装

Nir 氏は、会場の利用状況（App Service、Functions、ACA、SRE Agent）を尋ねて謝意を述べたあと、上記の学びをプロダクトに反映した内容を順に紹介しています。目標は、AI を足すために別プラットフォームに移らなくてよいことです。ここで紹介する機能は既存の製品群に組み合わせて使えるほか、Foundry から呼び出すことも、Foundry を呼び出すこともできると説明しています。

**Sandboxes**

* エージェントとそのツールの中核。Foundry の agent service や GitHub のエージェントの内部でも使われている。
* マイクロ VM を起動できるプリミティブ。プラットフォーム構築者や、安全な計算単位でアプリを拡張したい人向け。
* 翌日に詳しいセッションがあり、最後にセッション一覧が示される。

**Azure Functions hosted skills**

* Azure Functions の新しいプログラミングモデル。英語の Markdown で記述する。
* ローカルで作った skills ファイルをクラウドにデプロイでき、Functions のトリガーやバインディングが使える。
* 既存の Function アプリに組み込める。例として、アプリやビジネスロジックのエラーをモデルに渡して分析させ、クラッシュさせずに穏当な動作にする使い方を挙げている。
* 「現在利用可能」と説明されている。

**Durable Task Scheduler**

* エフェメラルなストレージとコンピュートでの状態保持は難しく、エージェントのコンテキスト（チャット履歴など）でさらに難しくなっている、という背景。
* 完全マネージドの水平スケール型バックエンドサービス。実行状態を永続化し、クラッシュからの復旧、インフラが 0 にスケールしても同じ地点から再開する長時間の処理、human in the loop に対応する。
* テレメトリとダッシュボードで、ワークフローの状態が見える。
* hosted skills の Markdown を読み、**Durable Task のコードに変換する機能**がある。非決定的な指示を決定的なワークフローにコンパイルするイメージで、初回にコード化したあとは DAG として実行し、トークンを節約できる。

**Connector namespace**

* Logic Apps の 1,500 以上のコネクタ（各種 SaaS、Azure サービス、他クラウド、カスタム）を、Logic Apps から切り出して独立したリソースにした。
* ユーザー割り当て ID またはシステム割り当て ID を付けてインスタンス化し、アプリの構成要素として使える。小さな単位なので、エージェントがアプリを組み立てる際にも使える。

**AI gateway（今週 GA）**

* モデル、エージェント、ツールを一元的に管理する。
* AI 固有のセキュリティポリシー（例：fault injection や PII の拒否。「fault injection」は聞こえたままの表記で、音声認識の都合で確定できません）が組み込まれている。
* エージェント ID に対応し、呼び出し元と別の ID で処理を開始できる。
* 最適なモデルを選ぶ組み込みのモデルルーター。
* トークン消費とすべてのトランザクションが見えるため、コストを管理できる。スロットリングも行える。
* Foundry と統合されており、Foundry で新しいモデルのエンドポイントを作る際に、それを表す（エイリアスする）新しい AI gateway を作れる。

**App Service Builder（新規発表）**

背景として Nir 氏は、Stack Overflow によると約 60% の開発者がコーディングで LLM（生成 AI）を信頼している、と紹介しています。ただしインフラのデプロイや保守を任せられると考える割合は、それより小さいとのことです。それでも AI を信頼する人は増えており、ソフトウェアは人間が書く時代から、エージェントと人間が協働して作る時代に移ると考えている、と述べています。

App Service Builder は、エージェントと人間が協働して、GenAI アプリを構築・デプロイ・管理するための新しいホスティングオプションです。設計原則は次のとおりです。

1. **オートスケール**：ACA sandboxes の上に構築されており、0 までのスケール、高速なコールドスタート、sandbox のセキュリティが得られる。
2. **意見を持った部品（opinionated building blocks）で、任意に組み立て可能**：前述のコネクタをアプリに組み込める。フロントエンドを作り始め、進めながら接続を足せる。
3. **extreme transparency**：起きていることをすべて監視・統制できる。

サービスは「ちょうど開始した」と説明され、試すための QR コードがスライドに示されました。

### 5.7 KPMG の事例（Greg 氏）

Greg 氏は、KPMG は世界の 4 大会計事務所の一つで、約 270,000 人が働いていると紹介しています。自身は技術者ではなく CPA（公認会計士）であり、税務が AI 導入の最も難しい領域の一つだと述べています。税務は、ルールとデータが多く、間違えたときの影響が大きいからです。

**これまでの経緯**

1. 以前は作業がノート PC 上のファイル（Word、Excel）に分散していた。
2. そこで **Digital Gateway** プラットフォームを作り、アプリとエージェントのためのグローバルで一貫したアプローチをクラウドネイティブにした。Microsoft をパートナーに選び、2023 年に複数年・20 億ドルの投資で提携を固めた。
3. 生成 AI の登場後（Greg 氏は 2022 年と発言）、従来の機械学習から転換した。データを Microsoft Fabric で管理し、Copilot を Microsoft の初期のエンタープライズ顧客の一つとして導入し、Azure OpenAI を使った「Digital Gateway Gen AI Chat」を公開した。
4. **今年 5 月に「Digital Gateway powered by Claude」を公開**。チャットにとどまらず、専門家の指導・レビューのもとで実作業を行う「AI co-worker」であり、各専門家のエージェントは、Microsoft と共同設計した **Azure Container Apps 上の専用 sandbox** で動く。
5. 先月、7 年間の共同投資である **Frontier Innovation Hub** を開設した。KPMG と Microsoft のエンジニア、顧客が集まって Agentic AI を構築する。

**4 つの差別化要因**

1. 別々のアプリを 1 つのシステムにする（以前は人間が「コピー＆ペースト層」だった。エージェントの harness が税務アプリとエンジンを結ぶ）。
2. 統制されたデータだけを使い、専門家が閲覧を許可された範囲に限る。
3. 時間を付加価値の高い業務に使える。専門家は skills、ワークフロー、エージェントを作り、事務所のガバナンスされたプロセスで共有できる。
4. **設計による機密性**：専門家ごとに専用の隔離された sandbox を持つ。

**実際の流れ（画面を見せながらの説明。スライドか動画かは音声からは分かりません）**

税務の担当者は Digital Gateway powered by Claude に目標とタスクを入力します。harness が、適切なツールを探し、計画を立て、必要な skills を特定し、エージェントを起動します。

1. Fabric 上の legal entity manager から、所有関係などの法人情報を取得する。
2. SharePoint 上の Digital Gateway docs にある顧客文書を照会し、文脈を集める。文書は安全な Azure 環境で扱われる。
3. 結果を税計算ツール・税エンジン（決定的なモデル）に渡し、回答を得て確認・対応する。
4. 途中で担当者に質問が出され、その回答を Claude のモデルが考慮する。
5. 最後に Word、Excel、PowerPoint のドラフトが生成され、人間がレビューと編集を行い、KPMG の税務知識を加える。

**なぜ sandbox か**

共有サービス 1 つで済ませる案も検討したそうです。しかしエージェントは、ファイルを開き、コードを実行し、システムを呼び、機密文書にアクセスします。悪意のあるコードが含まれた文書があると、全員の情報が危険にさらされ、顧客の情報が混ざれば顧客との信頼が壊れます。そこでエージェントごとに専用のマシンを持たせました。**隔離はコードではなく sandbox の性質として得られる**、というのが要点です。

「ユーザーとクライアントごとの専用 sandbox は高価で遅いのでは」という疑問に対し、Greg 氏は Microsoft が次の 4 点を満たしたと述べています。

1. sandbox が 1 秒未満で起動する
2. アイドル時はコストがかからない
3. セッション間で作業の続きを覚えている
4. KPMG の統制されたネットワーク内にある

**アーキテクチャ（Greg 氏の説明）**

* ユーザーは通常の Web アプリにサインインし、リクエストは 1 つのセキュアなフロントドアを通る。ルーターが適切な sandbox を見つける。
* sandbox 内のエージェントは 2 つのマウントを持つ。**読み書き可能**な領域にはセッション、skills、ファイルがある。**読み取り専用**の領域にはガバナンス用の skills と指示があり、Gen AI のリーダーシップチームが全員向けに更新を配布でき、誰も改ざんできない。
* エージェントはセキュアな MCP 経由で、税務アプリ、税エンジン、Fabric や SharePoint のデータにつながる。税務アプリとエンジンの背後に、KPMG の税務知識と独自の方法論がある。
* 全体を統制されたネットワークが囲み、Microsoft と作ったプロビジョニングサービスが sandbox の起動・一時停止・再開をほぼ即座に行う。

**本番での実績（Greg 氏の発言）**

* 「これはパイロットではなく日常業務」。世界の税務専門家 **35,000 人**が利用できる。
* ピーク時に **7,000 を超える**専用 sandbox が同時に稼働した。
* 直近数週間で、エージェントが税務システム内で約 **200 万回**の実作業を行った。
* 世界のユーザー基盤への展開として「1,000 から 7,000」という数字を挙げ、複数の法域（「three server regions」を含む）で動いていると説明している（聞き取りの都合で、数値の意味は確定できません）。
* 速さより、新しく空いた時間の使い道（難しい税務の問い、出力の確認、顧客への助言）が大事だと述べている。

Greg 氏は「エンジニアが他のチームに伝える 5 つの教訓」を紹介すると切り出しましたが、技術者ではないとして、自分が驚いた点だけを話しています。トランスクリプトで語られたのは次の 2 点です。

1. **Micro は small を意味しない**：マイクロ VM と聞いて小さなものを想像したが、各 sandbox には十分な計算能力とメモリがあり、本番で実際の税務作業をこなせる。
2. **エージェントを信頼できる**：期待しているからではなく、隔離とガバナンスが設計されているから。

最後に、先月 Satya が「AI を新しい形のインサイダーとして扱い、その周りに zero trust アーキテクチャを作る必要がある」と述べたことに触れ、「それが KPMG と Microsoft が作ったもの、つまり専門家一人ひとりのための、鍵のかかった専用マシンだ」と結んでいます。

## 6. デモ・手順

デモを行ったのは Paul 氏です。録音は音声のみのため、画面上のボタンや入力欄の細部は分かりません。以下は、語られた順の説明です。

**デモの構成（アーキテクチャ図）**

自動車の購入者とディーラー向けのアプリです。フロントエンドは Builder、エージェントは Foundry-hosted agent で構成します。ローン処理やドキュメント処理など、マイクロサービスのような部品が外部システム（在庫、貸し手、顧客）につながります。**すべてのツールとモデルの前に AI gateway を置き**、ローン文書の扱いなど注意が必要な処理には sandbox を使います。

**手順 1：GitHub Copilot app（または Copilot CLI）と canvas**

1. GitHub Copilot app を開く。左がセッション、中央がチャット、右に新しく「canvas」がある。
2. canvas は、決定的な UI と、Copilot やチャットから呼べるバックエンドの決定的なアクション（ツール）を提供する。ベストプラクティスやパターンに沿い、ターン数が減るため速く、トークンも少なくて済む。
3. 1 時間前に、新しい canvas **Azure App Platform** がリリースされ、マーケットプレイスから入手できると案内された。

**手順 2：App Service Builder でフロントエンドを作る**

1. 「ユーザーが近くの車を検索する」フロントエンドを作る。テンプレートは generative UI なしでも使えると説明したうえで、アプリを素早く肉付けするために何かを使うと述べている（指示語のため、対象は音声からは確定できません）。
2. 出来上がったのは JavaScript の Web アプリ（一部 Python）。canvas に実際のソースが表示され、いつでも VS Code で開ける。ソースは自分のもので、セキュリティのベストプラクティスに沿った ID が構成済み、トークンはどこにもない、と説明された。
3. アプリを実行（F5 のようなもの）し、「North Seattle 近くで、4 万ドル未満の EV、中古可」と入力した。
4. フロントエンドはゲートウェイに安全に接続されており、ツールが呼ばれ、データを取得して整った応答がエージェントのフロントエンドに返った。
5. Builder は code-to-cloud に最適化されており、CLI、canvas、組み込みの CI/CD から、変更やコミットごとにデプロイできる。デプロイはシンプルな zip deploy。
6. ポータルでデプロイ済みの Builder アプリを開き、ライブ接続、ログ、スケールなどの運用面を確認できると説明した。

**手順 3：sandboxes と AI gateway のスターターでローン文書処理を作る**

1. 新規作成で、sandboxes と AI gateway のスターターを選ぶ。複数のエージェントがゲートウェイ経由で、危険になり得るツールを呼ぶケースに向く、という説明。
2. シナリオは、ローン文書の処理と PII のマスキング（redact）。ツールがテンプレートの空欄を埋める。
3. 文書を処理するツールは **ACA sandbox の中**で動く。コードは「退屈なもの」にし、データの処理・マスキング・次に進めてよいかの判断に集中させる。egress や漏えいの防止は、改ざんされやすい自分のコードではなくインフラに任せる。
4. 文書にはプロンプトインジェクションのような内容が含まれ得るため、sandbox がほかのコンポーネントを守る、と説明した。
5. イベント駆動のクライアント（フロントエンドを作らなくても使える）で、サンプルをアップロードして実行する。サンプルは、名前と架空の「socials」を含む安全なものと、安全でないものを用意した。canvas は、インフラがすでに行っていることを可視化しているだけだという説明。
6. sandbox は **1 秒未満**で起動した。コード内で egress がないことの確認、変数に関する処理（聞き取りのまま「projecting the variables」）、処理とマスキングを行って結果を返し、エージェントが処理して判断した。
7. 画面上で、マイクロ VM の sandbox にはシークレットもキーも存在しなかったことを確認した。マネージド ID のエンドポイントを呼んで自分でトークンを作ることもできないことは、すでに確認済みだと説明した。

**手順 4：攻撃的なテスト**

1. 設定上は禁止されている egress を、あえて試みる。sandbox の境界で **egress プロキシが阻止**した。ツールが失敗するため、エージェントは危険なものを処理しない。
2. 文書に含まれる想定の標準的な **jailbreak プロンプト**を試す。今度は sandbox ではなく **AI gateway** が、モデルとの間で安全・安全でないを判断し、**429 エラー**を返した。

**手順 5：アプリ全体の組み立て**

1. フロントエンドを sandbox のツールにつなぎ、在庫検索などのために hosted skills を加える。このアプリは canvas に同梱されており、オンラインで公開されている。
2. VS Code で開くと、hosted skills は「イベント駆動の関数」であり、トリガーベースの Markdown が薄いロジックを表現し、決定的なツールを呼んで在庫を検索する。
3. 時間の都合で、デプロイ済みの環境に切り替える。sandbox グループ、AI gateway、マネージド ID、Foundry hosted agent が連携して動いている。
4. 「4 万ドル未満で航続距離 250 マイルの EV」を検索し、オーケストレーション全体が動き、ツールが安全に呼ばれ、ゲートウェイを通って応答が返った。

**手順 6：SRE Agent による業務監視**

1. 24 時間働く自律的なエージェントの例として、**Azure SRE Agent** を、技術的なテレメトリだけでなく、在庫が受注の速度に足りているかというビジネス指標の監視にも設定してある。
2. 在庫が不足しているという実際のアラートが SRE Agent から上がっていると示し、人間の承認者として、その業務ロジックを承認できると説明した。

Paul 氏は、中心は ACA sandboxes で、AI gateway はツールとモデルの重要なインフラであり、Builder による豊富なフロントエンドと、canvas と VS Code によるエンドツーエンドの開発体験が見られた、とまとめています。

## 7. 注意点・発表者の気付き

* **ローカルのエージェントは難題を避けている**：多くのエージェントは開発者のマシンで動き、per agent identity、脳と手の分離、egress 監視、secretless といった課題を無視している、という指摘です。
* **信用できないのは「手」**：ツール呼び出しやコード実行の部分は何をするか分からないので、隔離すべきだという考え方です。
* **隔離はコードではなくインフラで担保する**：Paul 氏は、自分のコードは改ざんされ得るとして、egress の防止などはインフラに任せる方針を取っています。
* **ガードは層で効く**：デモでは、egress は sandbox の egress プロキシが、jailbreak は AI gateway が防いでいます。Paul 氏は、両者の組み合わせが安全なインフラになると述べています。
* **社内での学び**：Bilal 氏は、新しいことを学ぶたびに古い学びを捨てる（unlearn）ことになると述べています。

## 9. まとめ

Microsoft は、自社の SRE Agent を本番で動かす過程で得た学びを、sandboxes、AI gateway、エージェント ID、hosted skills、Durable Task Scheduler、connector namespace、App Service Builder などのビルディングブロックとして提供しています。

デモでは、AI gateway をツールとモデルの前に置き、リスクのある処理を ACA sandbox で動かす構成が示されました。egress の試みは sandbox の境界で、jailbreak は AI gateway で止まりました。

KPMG の事例では、専門家ごとの専用 sandbox を使った Digital Gateway powered by Claude が、すでに 35,000 人が使える本番環境で動いています。セッションの結論は、エージェントの安全性を、期待ではなく **隔離とガバナンスの設計で担保できる** ということでした。
