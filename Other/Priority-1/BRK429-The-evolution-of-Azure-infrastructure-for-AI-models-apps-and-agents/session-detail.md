# BRK429 The evolution of Azure infrastructure for AI models, apps, and agents

## 1. はじめに

このセッションは、AI の利用が「学習（training）」から「推論（inference）」、さらに「エージェント型 AI（agentic AI）」へと広がるなかで、Azure のインフラ（IaaS）がどう進化しているかを、3 人の登壇者が分担して紹介するものです。発表は次の 3 つの問いを軸に進みます。

### 5.4 推論の最適化（Azure Storage の登壇者）

2 人目の登壇者は、学習済みモデルを推論に使う場面での投資を、**トークンあたりのコストの最適化**を軸に 3 つ紹介しました。

1. キャッシュ技術（context cache と distributed cache）で GPU 利用率を上げる
2. 推論ワークロードに適したインフラを選ぶ
3. Azure のグローバルリージョンにまたがる GPU・ストレージ・ネットワークの空きキャパシティを活用する

#### Distributed accelerator for cloud storage（DAX）

推論の最適化というと GPU の増強に目が向きがちですが、GPU の利用率に影響する要素は他にもあります。その 1 つが**コールドスタート**です。推論エンドポイントを用意するとき、GPU は Blob storage からモデルを読み込み、GPU メモリや NVMe に置きます。エンドポイントが数百〜数千の GPU ノードに拡張されると、各 GPU がそのたびに Blob storage からモデルの重みを取得するため時間がかかり、その間 GPU はアイドル状態になります。

そこで発表されたのが distributed accelerator for cloud storage（DAX）です。登壇者は「名前は大げさだが、実体は**共有キャッシュ**」と説明しています。GPU ノードの NVMe ドライブを使って共有キャッシュを作り、最初の GPU が起動したときにモデルの重みをそのキャッシュに載せます。その後スケールアウトで起動する GPU は、キャッシュから重みを読みます。

AI ラボと行ったテストでは、主要なシナリオでモデルのロード時間が **3 倍以上**短縮されました。Blob storage から GPU へのロードで約 50 秒かかっていたものが、DAX では 1 ノードあたり 16 秒です。数千ノードに拡張する場合の GPU 時間の節約は大きく、この技術は Satya 氏の基調講演でも触れられたと述べています。

#### Context cache

コーディングエージェントでは、ターンごとの指示とコンテキストはほぼ同じです。それでも context cache がなければ、各リクエストを GPU に送って推論させるため、GPU 時間を多く使います。Context cache は、計算済みのコンテキストとその結果を、context hash を用いて保存します。新しい推論リクエストが来ると、キャッシュを調べて計算済みの結果を取り出すため、GPU に推論リクエストを送る必要がなくなります。

モデル設計のよいコーディングエージェントでは、**計算結果の最大 90% を context cache で再利用できる**ことが分かったと述べられました。これにより GPU の利用率が空きます。

#### Project Optima（プレビュー）

推論に適したインフラを選ぶ作業は手間がかかります。メモリは足りるか、GPU の種類は適切か、同じデータセンターに適切なストレージ、コンピュート、ネットワークがあるか、といったことを、現状は試行錯誤で確かめることになります。**Project Optima** は、推論ジョブのワークロード特性を記述すると、それに基づいて GPU、ストレージ、ネットワークの種類を推奨するプレビュー機能です。AKS との統合も紹介されており、AKS で推論ジョブを動かすときに、より具体的な（prescriptive な）推奨を得られるとされています（連携先の名称は音声認識の都合で確定できません）。

#### GPU を見つける・確保する

現状、Azure 上の推論ジョブの多くは NVIDIA か AMD の GPU で動いています。選択肢を広げるものとして、次の 2 つが発表されました。

- **Maya チップ**：データセンター、ネットワーク、ソフトウェアスタックとの緊密な統合を前提に、ゼロから作られたチップです。
- OpenAI との提携による**チップ**：大規模言語モデルを作る会社のチップだと説明されています（チップの名称は聞き取りが「Nexus」となっており、音声認識の都合で確定できません）。

シリコンの選択肢が広がることで、Azure 上で適切な GPU を見つけやすくなる、という考えです。

もう 1 つの対策が、キャパシティの**収穫（harvesting）**です。推論ジョブは通常、ホームリージョンで開始されます。別のリージョンに GPU やストレージの空きがあっても、そのままでは使えません。**Azure Kubernetes Fleet Manager** を使うと、キャパシティのあるリージョンに AKS クラスターを作り、Fleet Manager のプールに参加させられます。Fleet Manager は、空きキャパシティと配置ロジックに基づいて、推論ワークロードをキャパシティのあるリージョンに置くオーケストレーターです。

さらに DAX と組み合わせると、データが別リージョンにある場合でも、GPU の隣に DAX を配置してモデルをキャッシュでき、リージョンをまたいだデータ取得を避けられます。Fleet Manager と DAX の組み合わせは、推論ジョブにとって魅力的なシナリオだと述べられました。

#### ストレージの改善

推論、学習、エージェント型のワークロードでは、企業データを GPU の近くに置くことが最も重要だと説明されています。

| 項目 | 説明 |
| --- | --- |
| Azure Managed Lustre（AMLFS） | Linux の POSIX 的なセマンティクスと Lustre プロトコルで、高スループットが必要な場合に使う。名前空間が 120 ペタバイトまで拡張された。ストレージのベンチマーク（"ML path storage benchmarking" と聞こえ、音声認識の都合で表記が確定できません）での checkpoint の数値は、業界で最も高いと述べられた。AKS とも密に統合されている |
| Turbo tier | SSD ベースの Blob ストレージ階層。高スループット・低レイテンシが必要な AI ワークロードを、**単一の名前空間・単一のストレージアカウント**で扱える。ホットデータは SSD の Turbo tier に置かれ、Lifecycle Manager で同じストレージアカウント内の HDD（安価で低温のストレージ）に階層化できる。AI ワークロードの経済性が大きく改善する |
| Session API | 推論ジョブでは、リクエストのたびに Blob オブジェクトごとに権限を確認していた。コンテナーレベルで、あらかじめ決めた間隔のセッションベースのトークンを発行することで、オブジェクトごとの認証が不要になり、GPU の利用率も空く |
| Blob RDMA | 後述 |

Turbo tier の詳細は、翌日の Azure Storage のセッションで掘り下げると案内されました。

#### Blob RDMA

Blob RDMA がない場合、Blob storage から GPU へデータを読むには CPU を使い、1 バイトずつコピーします。CPU がクリティカルパスに入り、GPU メモリ、ホスト RAM、NVMe にコピーするため、CPU が常にピーク近くになり、レイテンシが高くなります。Blob RDMA では、データコピーというクリティカルパスを **NIC にオフロード**し、CPU を外します。NIC が RDMA プロトコルで、GPU ノードの NVMe、GPU メモリ、ホスト RAM へ直接データをコピーします。必要な CPU コアが大きく減り、**レイテンシは最大 6 倍**改善します。登壇者は、この機能を提供しているクラウドプロバイダーは Azure だけだと述べています。

### 5.5 エージェント型ワークロード向けのインフラ（Narayan 氏）

Narayan 氏は、Max 氏が「AI を学習させる」話、Azure Storage の登壇者が「AI に考えさせる」話をしたのに対し、自分は「AI に仕事をさせる」話をする、と切り出しました。インフラの最適化の軸が、学習時間からトークンあたりのコストへ、さらにエージェントへと移っています。

従来のアプリケーションは、決められた範囲の中で起動・実行する、ある程度予測可能なものです。これに対しエージェント型のワークロードは自律的で、起動し、コードを書き、実行し、停止して、ユーザー入力や外部イベントを待ち、再び動き出します。モデルや他のエージェントとも通信します。多数のエージェントを動かすには、**新しいコントロールプレーン**が必要で、エージェントを第一に考えたインフラが求められる、という立場です。

エージェントのライフサイクル（作成、スナップショット、クローン、復元、削除）は、VM に期待するのと同様に、**インフラの第一級の機能**と位置づけられています。提供方法は 2 つで、AKS の agent sandbox を使うか、API を直接使います。いずれも ACI（分離）、Entra ID for agents、Azure Files と Blob（スナップショット）、agent grid といった、すでになじみのあるものや新しいものの上に作られています。

#### Agent sandbox（AKS）

エージェントは何をするか分かりません。LLM が書いたコードを実行するため、ホストや他の Pod に影響しないよう、**分離されたコンテナー**で実行する必要があります。また、必要なインフラをすぐに用意する必要もあります。AKS では、テンプレートとして agent sandbox を定義し、そこからインスタンスを作成します。

- ステートフルな Pod として提供される。
- **Kata container** により VM レベルの分離を実現し、同じノードで動く他の処理から切り離す。
- 即座にキャパシティを用意するため、**ウォームプール**を用意する（複数の sandbox のスナップショットを事前に作っておく）。
- エージェントは常時動く必要がなく、一時停止する。その間はリソースを他の用途に再利用できる。ストレージのスナップショットと読み戻しを素早く行う必要があり、AKS の sandbox がそれを提供する。
- 現在は**パブリックプレビュー**で、試せる。

#### Azure Container Instances（ACI）

Kubernetes クラスターを自分で動かし、所有したくない場合は、API を直接使えます。**ACI** は、エージェント型ワークロードを動かすためだけに作られる、分離されたコンテナーグループです。仮想ネットワークに置かれ、マネージド ID が使えます。1 つのコンテナーからモデル、インターネット、データなど何にでもアクセスでき、要件（分離と素早いアクセス）は AKS の場合と変わりません。コスト面では、ACI のインスタンスに対してのみ料金が発生し、それを支えるインフラ分は払わないため、効率が高いと説明されています。

#### Identity：Microsoft Entra agent ID

人間をアイデンティティで保護するのと同様に、エージェントにもアイデンティティを与える必要があります。**Microsoft Entra agent ID** が提供する要素は次のとおりです。

1. ID を持つエージェントを検出（discover）できる
2. エージェントは、何かをする前に認証し、ID の所有を証明する
3. 証明後に、最小権限の認可を与える
4. ガバナンスにより、権限が時間とともにずれないようにする
5. 保護：エージェントが予想外に大量の呼び出しをするなどの場合に備える
6. ネットワークセキュリティ：エージェントが通信するトラフィックを検査し、URL レベルのフィルタリングなどを行う

#### Storage：スナップショットと復元

エージェントは常時動かないため（例：コーディングエージェントが、コードを書いたあと人間のレビューを待つ間は停止する）、素早く復元したい状態が 2 種類あります。

| 状態 | 保存先 |
| --- | --- |
| プログラム（エージェントそのもの）の状態 | Azure Blob。エージェントがどこで起動しても、すぐに読み出せる |
| ワークスペース（メモリ、リポジトリ、パッケージ、ファイル、出力） | Azure Files（**coming soon**） |

#### Networking：AI-aware な ingress と AI gateway

Kubernetes を AI ワークロードに使うなら、ingress も AI を意識したものにする必要があります。Kubernetes 内には複数のモデルがあり、エージェントがそこにアクセスするため、適切なモデルへの負荷分散を行うゲートウェイが必要です。LLMD のような標準（表記は音声認識の都合で確定できません）に沿って、KV キャッシュやモデルの負荷状況に基づき、適切なモデルへ負荷分散します。

MCP サーバーはさまざまなツールを持ちます。AI gateway は、これらのツールへの**単一の URL**を提供し、ツールへのアクセスのログを 1 か所で取れるようにして、セキュリティも確保できます。この AI gateway は、Application Gateway for Containers を通じて提供され、現在は**パブリックプレビュー**です。

#### Agent grid

ユーザーの単一のリクエストが、エージェント同士の呼び出し、モデルとのやり取り、インターネットの参照、MCP サーバーの呼び出しなど、裏で多数のネットワーク呼び出しになります。そのたびに「このエージェントにそれを許してよいか」「どう検査するか」が問題になります。

セキュリティポリシーを独立した複数のゲートウェイで実装すると、ワークフローごとに実装箇所が増えます。1 つのプロキシにすべてのトラフィックを集めると、単一障害点になります。そこで、sandbox の外側のネットワークで、すべてのトラフィックが流れる点を使い、パケットにポリシーを適用します。セキュリティの担当者がポリシーを別の場所で定義し、参加するエージェントなどの構成要素を agent grid に加えることで、**すべてのワークフローに統一されたポリシーを適用**できます。

## 6. デモ・手順

### 6.1 Context cache のデモ

2 人目の登壇者が「context cache のデモをします」と述べたあと、結果を説明するナレーションが流れました（画面の細部は音声からは確認できません）。語られた内容は次のとおりです。

1. ベースラインは再計算し、候補（context cache）は保持された KV を取り出す。
2. 同じプロンプトで、回答を開始するまでの時間は、通常の vLLM が約 11 秒、context cache では約 741 ミリ秒。
3. 最初に見える応答までの時間（発話は "TTFD"。音声認識の都合で表記が確定できません）が短くなることで、アシスタント、コーディングツール、エージェント間の引き継ぎで体験が改善する。
4. 規模を広げたテストでは、平均の最初の応答までの時間が、通常の vLLM で 11,614 ミリ秒、context cache で 711 ミリ秒で、**16 倍の高速化**。
5. 出力スループットは、同じハードウェア構成の比較で、毎秒 2.65 トークンから 27.54 トークンに向上。
6. 本番では、デプロイ済みのフリートでより多くの作業をこなせるか、一定の需要とレイテンシ目標に対し、キャッシュ、ネットワーク、ストレージのコストを含めても必要なリソースが少なくて済む、という機会がある。

### 6.2 Agent grid のデモ

Narayan 氏が、ACI と AKS クラスターを agent grid に追加するデモを行いました。画面の赤と緑の線を見ながら、ポリシーで悪意のあるトラフィックを止める、という説明で始まっています。ナレーションで語られた範囲を、順に整理します（画面の細部は音声からは確認できません）。

1. **Agent grid を作成する。** トップレベルのリソースで、メンバーを追加できる。
2. 追加できる対象は、AKS クラスター全体や AKS の sandbox グループなど。AKS クラスターを追加すると、そのクラスター内のメンバー（モデルなど）が一覧に表示される。
3. AKS クラスター内で動いている **MCP サーバー**を、agent grid に登録する。
4. こうして、MCP サーバーと **ACI 上のエージェント**の両方が grid のメンバーになる。
5. **正常な呼び出し**：顧客向けのシンプルなエージェントが、顧客からの入力を受け、ソフトウェアのライセンス状況を調べる。エージェントがモデルと通信して「ライセンスは有効で、あと何日」といった結果を返す。許可すべき呼び出しである。
6. **悪意のある呼び出し**：エージェントがモデルに対して、呼び出すべきでないツールを呼び出そうとする。このツールは顧客レコードをエクスポートするもので、出力すべきでないレコードが露出する様子が示された。
7. grid でポリシーを追加する：この grid 上のエージェントは、このレコードのエクスポート用 MCP 呼び出しを**行えない**ように設定する。
8. 同じシナリオを再実行する。エージェントが同じようにレコードをエクスポートしようとすると、ブロックされ、「認証されていない呼び出しで、呼び出せない」という趣旨の結果が示される（発話の表現は "unauthenticated call"）。
9. エージェントが grid 内で行ったすべての呼び出しが表示され、**完全な監査証跡**が得られる。トラフィックのパターンが可視化され、各リンクをクリックすると、誰が誰と通信し、何が許可され、何がブロックされたかを確認できる。

## 8. 利用者にとっての利点

発表で語られた効果は次のとおりです。

- **モデルロード時間の短縮**：DAX により、Blob からのロードで約 50 秒かかっていたものが 1 ノードあたり 16 秒（3 倍以上の短縮）。
- **GPU 利用率の向上**：Context cache により、コーディングエージェントでは計算結果の最大 90% を再利用。デモでは、最初の応答までの平均時間が約 16 倍高速化し、スループットが毎秒 2.65 から 27.54 トークンに向上。
- **CPU 使用量とレイテンシの低減**：Blob RDMA でレイテンシは最大 6 倍改善、必要な CPU コアが大幅に減少。Turbo tier（RDMA）は GB あたりの CPU 使用量を約 95% 削減。
- **経済性**：Turbo tier と Lifecycle Manager により、ホットデータは SSD、冷たいデータは HDD に同一ストレージアカウント内で階層化。ACI では、支えるインフラ分ではなく ACI インスタンスに対してだけ支払う。
- **キャパシティの確保**：Fleet Manager による複数リージョンの活用、シリコン選択肢の拡大。
- **エージェントの安全な運用**：分離（Kata container、ACI）、Entra agent ID、agent grid による一元的なポリシー適用と監査証跡。
- **顧客事例**：Air India（1 日 4 万件の顧客対応の電話）、Harting（27,000 製品からコネクターを 1 分で選定）。

## 9. まとめ

Azure は、AI のトレーニング、推論、エージェント型 AI を、CPU・GPU・ストレージ・ネットワークがつながった 1 つの基盤で支える方針です。今回の Ignite では、Cobalt 200 の GA、Guest RDMA のプレビュー、confidential AI の SKU、エージェント向けの sandbox と API が発表されました。

推論では、DAX と context cache で GPU の待ち時間を減らし、Project Optima でインフラの選定を支援し、Fleet Manager でリージョンをまたいだキャパシティを活用します。ストレージ側では、Turbo tier、Session API、Blob RDMA が紹介されました。

エージェントについては、AKS の agent sandbox や ACI による分離、Entra agent ID、Blob と Azure Files によるスナップショット、AI gateway、そしてネットワークで統一ポリシーを強制する agent grid が紹介されました。詳細は、案内された後続のセッションで説明される予定です。
