## 4. 発表者が伝えたいメッセージ

Lachie 氏が最初に示すのは、Satya 氏が今年 6 月にネット上で公開した文章にある「AI learning loop」という考えです。Satya 氏の言葉として、組織には 2 種類の資本があるとされ、1 つは人の判断力とドメイン知識（human capital）、もう 1 つはモデル、トークン、コンピュートといった AI capital です。人がコンテキストや判断をモデルに渡し、モデルは人の手が届かない規模で洞察を返し、人がそれに基づいて動いて、その学びがまたループに戻ります。この循環が学習ループで、回すほど知識が複利的に積み上がり、自社のデータやビジネスの文脈に作用すると説明しています。発話では、この仕組みを「hill climbing machine」とも呼んでいます。

そこで「自分のループを持つ」には、2 つの次元で選択肢が必要だとしています。

1. **どのモデルを、いつ使うか**
2. **どこで動かすか**

登壇者の立場は、オープンなプラットフォーム、API、コンポーネントを使うことで、この 2 つの自由度を確保できるというものです。後半の Azure Linux パートでは、同じ考えを OS に当てはめ、「**自分たちは道路を作る。どの車で走るかは顧客が選ぶ**」という表現で、標準的な基盤づくりの重要性が語られます。

## 5. 発表内容の詳細

### 5.1 AI learning loop とモデル・実行場所の選択

**モデルの選択**

多くの組織は、能力が最も高い proprietary な frontier モデルから始めます。タスクが十分に理解されてくると、低コストの特化・最適化モデルや、自分たちの条件で動かせる open weight モデルに移れます。実際に、proprietary から特化モデル、さらに open weight へと移る顧客が多いと述べています。大事なのは、モデルを切り替えても、構築したナレッジやコンテキストを失わないようにすることです。右側（open weight）へ移ると、データも AI も自分のものになるという説明です。

**実行場所の選択**

自前で動かせる、あるいは小さなマシンで動かせるなら、ワークロードを動かす場所を選べます。ソブリン環境（管轄、ルール、データが自分のテナントと環境から出ない）、自分で管理する施設のオンプレミス、そしてパブリッククラウドの間を、学習ループを作り直さずに移動できるのが目標です。パブリッククラウドの利用も問題ないと明言しています。

**Microsoft 自身の利用**

市場に出ている多くの AI 製品は、内部では OSS のスタックで動いていると述べています。例として次が挙げられています。

- MAI は、frontier モデルを作るために Kubernetes と OSS のツールを使っており、最近 case study が出ていた
- Copilot のチームは Kubernetes の上で動いている（もう一つ挙げられた基盤の名前は、音声認識の都合で確定できません）
- 核になる OSS として Linux があり、Linux は VM のカーネル、Kubernetes は分散コンピュートの「カーネル」。さらに vLLM、Agent Substrate、Sandbox といったプロジェクトがこのインフラを支えている

どの frontier モデルでも、内部では Linux で動いている、という点を、このセッションで掘り下げると予告しています。

### 5.4 Azure Linux パート：Microsoft と Linux の歴史

交代した Azure Linux チームの登壇者は、まずタイムラインを示します。

1. **2009 年頃**：Linux カーネルへの貢献を開始。クラウドが台頭してくる中で、Samba のファイルシステム対応など、相互運用性の作業から入った
2. **2011 年**：上流への投資が増え、カーネルへの貢献者の上位 5 社に入る。Hyper-V への投資も拡大。社内で、経営陣の承認の有無にかかわらず自然発生的に進んだと述べている
3. **2012 年頃**：クラウド領域に本格参入し、CentOS、Ubuntu などを取り込む。その頃に、Microsoft Loves Linux キャンペーンや .NET Foundation の創設もあった
4. **2015 年**：VS Code の登場。登壇者は毎日のように使っているが、これが OSS のアプリケーションであることは意識されにくい、と述べている

このタイムラインは高い山だけを拾ったもので、網羅的ではないと断っています。

**CBL Mariner から Azure Linux へ**

2019〜2022 年頃が社内の転換点でした。それまで各チームは好きな Linux ディストリビューションとバージョンを使っていて、それがコンプライアンスの面で苦痛でした。FedRAMP、FIPS といった規制や認証に対応する必要があり、複数のディストリビューションとバージョンにまたがって「この CVE にはパッチ済みで、このバージョンに当てはまる」と証明することが、社内のコンプライアンス追跡を悪夢にしていた、という説明です。

そこで、標準化したプラットフォームとして **CBL Mariner** が使われ、社内のサービスの大半を CBL Mariner、のちに名前が変わった Azure Linux に移しました。コンプライアンスと実現可能性、FIPS を早く出せることが動機でした。

当初は社内向けプログラムにとどめる意図でしたが、社内外の境界がきれいに分かれていないサービスがあり、問題が出ます。AKS が典型例で、顧客が使う AKS が社内の複数チームも支えています。AKS に Azure Linux を入れると、顧客から「これは何か、使えるのか」という質問が来るようになり、外部提供の是非を考え直しました。**2023 年から 2026 年の間に外部提供を決定**し、顧客向けに磨き込んだと述べています。

社内での導入は、dogfooding ではなく「fast food」（社内チームに素早く試してもらう）と呼びたい、という冗談を交えつつ、過去 3 バージョンにわたって本番で使ってきたと説明しています。LinkedIn や AKS など社内のサービスを Azure Linux に移した経験が数年分あり、LinkedIn はその移行についてブログを公開しているとのことです。これらは、AI の話が本格化する前の取り組みで、昨年あたりから AI が大きく動き出した、と述べています。

### 5.5 Azure における Linux の比重

Carl 氏の担当として、次の数字が紹介されています。マーケティングやエンジニアリングで検証した数字だそうです。

- **Azure の顧客コアの 70% 超が Linux で動いている**
- Xbox、Minecraft、AKS を含む、数百の Microsoft サービスが Linux で動く
- AKS は Linux で動き、Microsoft の日常的なアプリケーションの多くも Kubernetes 上（AKS 上、Azure Linux 上）で動く
- Azure Linux は今週 GA。VM として使えるほか、コンテナホスト製品の **Azure Container Linux** もある
- OpenAI と ChatGPT も Azure の Linux で動いており、ChatGPT のモデルを使うときのトラフィックは Azure の Linux を通る

**Endorsed distribution program**

Azure には endorsed distribution program（推奨ディストリビューション）があり、各社と技術的な関係を持っています。Canonical、SUSE、Rocky Linux の CIQ、Oracle、Red Hat などが挙がり、Red Hat はこの日の後の時間帯に自社のセッションがあると案内されています。Azure Linux も、今週から endorsed に加わり、Learn の endorsed Linux distribution のページに載ります。

Azure Marketplace には、次が並んでいると説明されています。

| 区分 | 例 |
| --- | --- |
| Rocky Linux | コミュニティ版と、商用で支える CIQ の RLC（Rocky Linux by CIQ） |
| コミュニティイメージ | Fedora、CentOS |

CentOS については、**使わないでほしい。使うなら CentOS Stream（Red Hat Enterprise Linux のアップストリーム）を**と述べ、CentOS 7 や 8 を使っている場合は「話をする必要がある」と強い言葉で移行を促しています。非常に古く、今年は特に脆弱性が多いためです。

AI 企業として、Hugging Face や Mistral などの名前も挙げ、**AI ワークロードは Linux 上で動く、Linux は AI ワークロードのネイティブなホーム**だと述べています。

### 5.6 なぜ Linux が AI の基盤なのか

MCP サーバーや A2A など、エージェントやモデルの通信技術の話は今週よく聞かれたはずだが、**モデルがどのようにオーケストレーションされるか**が根底の技術であり、そこで Linux ディストリビューションが強みを発揮する、と説明しています。ディストリビューションは、グラフィックスドライバー、言語スタック、モデルを扱うために必要なツールを提供する立場です。IaaS は 15 年以上前からあるものですが、IaaS のワークフローは、すべてのモデルを支える基盤として、いっそう重要になったとしています。

Azure が Linux ディストリビューションに求める条件は、次の 3 点でした。

1. Azure 上で良く、速く、確実に動くこと
2. システムレベルの性能が予測できること
3. セキュアであること

**セキュリティについて**

ここ 2〜3 週間で CVE が雪崩のように押し寄せていると、登壇者は述べています。AI により、これまで低〜中程度とされた脆弱性を横方向に連鎖させて足場を広げることが速くなり、必ずしも完全な侵害ではなくても、顧客データの流出のような重大な被害が起こりうると説明します。ひとつひとつは低い脆弱性を束ねて、以前なら「高」に相当する成果を得られる連鎖攻撃を懸念しています。そのためパッチの適用期間も短くする必要があり、標準化したプラットフォームを使うと、どのバージョンにパッチを当てるか、必要な機能が有効かといった判断が簡単になります。これが Azure Linux が Microsoft にもたらした利点で、顧客にも提供したい点だと述べています。

また、コスト効率と起動の速さ（ノードをフリートに速く追加できること）も挙げています。AI のスケールに限らず、米国の Black Friday のように、ショッピング関連の事業が急にスケールしなければならない場面で効くという例です。

### 5.7 Azure Linux と Fedora の関係

Azure Linux は Fedora をベースにしています（rebase）。登壇者は、自身が Fedora のエコシステムで育ったという個人的な事情を前置きしつつ、次の理由を挙げています。

- RPM 系のディストリビューションがビジネス領域の主流だった。Red Hat Enterprise Linux も、SUSE（SAP ワークロードが多い）も RPM 形式で、競合の Amazon Linux も RPM 系。同じ形式なので、ワークロードの行き来をしやすい
- パッケージの取得元として、安定していて、リリース周期が信頼できる
- Fedora の 6 か月ごとのリリース周期により、新しい技術を素早く試し、顧客に有用なものを見極められる

Fedora 側の利点としては、エンタープライズ顧客の重みが加わることと、ワークロードに対するエンタープライズ側の評価を得られることが挙げられています（Fedora はデスクトップ向けだけのディストリビューションではない、という説明です）。また、libpng のような下層のライブラリは、どの会社も差別化の材料にしないので、共有して協力するのが合理的だと述べています。

**AI に関する方針**

登壇者が持ち帰ってほしいのは、**AI を載せるための基盤を作っている**という点です。Fedora は AI ポリシーを持ち、open weight モデルを出荷する予定です。Microsoft も AI ポリシーを持ち、Foundry の提供を行い、open weight モデルも良く動くようにします。顧客がどのモデルを使うかは問わず、顧客を支えるのが役割だと説明しています。

そして、この点を「道路」にたとえています。**自分は道路を作る。その上でどの車を走らせるかは完全に利用者の自由**。ただし道路は必要で、ある程度標準的でなければならない。Fedora、Red Hat、Ubuntu、Microsoft が、その構造づくりで協力できる、という考えです。

OpenAI は顧客であり、同社のプラットフォーム上で動いています。AI を大規模に運用する知見を得るほど、それを Fedora に還元します。Fedora のアップストリームに入れば、他のディストリビューションも取り込めるためです。

**開発の公開**

Azure Linux のコードはすべて GitHub（`github.com/microsoft/azurelinux`）で公開されており、開発をオープンに進めています。ディストリビューションのためのビルドはすべてこのリポジトリにあり、Fedora の spec ファイルをどこで、どのように変更しているかも見えます。変更の理由は、多くの場合、開発者向けのメモとして書かれています。登壇者は、「同じものを自分で組み上げたければ、ドキュメントは公開されている」と述べ、何を、なぜ行っているかを公開することが、良い OSS の担い手として重要だと述べています。

### 5.8 Q&A

登壇者は、より対話的にするため、会場のマイクで次のような質問を募っています。AI を使ってパッケージのビルドやパッチをどう行っているか、AI の取り組みをどう支えるか、基本的な Linux の質問、「どうすれば Microsoft を信頼できるか」。実際に出た質問は、次の 1 件です。

**Q. 最新の Ubuntu リリースで脆弱性パッチが遅れたことについて、各ディストリビューションのリリースサイクルも含めてどう考えるか**

回答（Azure Linux チームの登壇者）の要点は次のとおりです。

1. 質問は、CVE のリリース周期と、Ubuntu に関する話題の 2 つに分けられる。Ubuntu と Red Hat は、長年かけて築いた従来のパッチモデルを持ち、顧客の期待もそれに沿っている。どのパッチをいつ取り込むかは各ディストリビューションの判断で、その決定を否定する立場にはない
2. ただし、この 1 年、モデルで脆弱性をより効率的に見つける取り組み（トランスクリプトでは「Project Accredi's」と聞こえ、音声認識の都合で名称が確定できません）が発表され、20 年、30 年、50 年前のソフトウェアの脆弱性まで見つかっていると主張されており、直近 2 か月で CVE が殺到した。そのため、以前は妥当だったパッチ判断を見直す余地がある。業界として、rolling release に近いモデルを検討すべきかもしれない。CVE の発生速度は落ちないと感じている
3. Patch Tuesday のような周期や、FedRAMP の以前の指針である「重大な脆弱性に 30 日」では、もう時間が足りない。AI を使えば、脆弱性が知られたあとの類似の探索が可能になるためだ。例として PHP に関するエクスプロイトが出た直後に、Java に関する類似のものに話題が移ったことを挙げ、セキュリティ研究者がモデルに「この言語で似たものを探せ」と指示したのではないか、と述べている（トランスクリプトの固有名詞は音声認識の都合で確定できません）
4. Red Hat の場合は、6 か月ごとにマイナーリリースがあり、その間に約 6 週間ごとのリリースがあると会話の中で説明されています。これではもはや速さが足りない、という見方です
5. 問題は顧客側にもある。6 週間ごとのパッチ適用すら難しく、毎週や毎日はなおさら無理という顧客がいる。テストが必要で、再起動に 12 時間かかるサーバーもある、といった事情がある
6. 業界全体（顧客、ディストリビューション、プロバイダー）で、テスト品質を落とさずにどの速度でパッチを維持できるかを見つける必要がある。大規模なテストスイートがあるのは、顧客を壊せばニュースになるからで、金融サービスは今週の初めに厳しい週を過ごした、という言及もある（関連性は不明と述べている）
7. 顧客がパッチを受け入れる能力、AI で速まった適用の必要性、壊さないための厳密なテストの 3 つの間に板挟みがある。パッチを速く出すほど顧客の負担が増えるので、顧客の手間とセキュリティの必要性のバランスを取る必要がある

**客席からの補足（Canonical の Aaron Conklin 氏）**

質疑の途中で、Canonical の Aaron Conklin 氏がマイクで意見を述べています（登壇者が名前を呼んで紹介）。要点は次のとおりです。

- セキュリティを保ちつつ壊さない、という緊張関係は業界全体の課題で、ディストリビューションを作る側は、セキュリティと安定性のバランスを非常に重視している。多くのユーザーは自動更新（unattended updates）を毎日回しており、十分にテストされていないものを出せば壊れる
- CVE を見つける手段と同じツールを使って、パッチを各リリースに **backport** する方が、扱いやすい問題だと考えている。Canonical 側でのパッチの自動 backport の話にも触れている
- 基盤の依存関係が絶えず変わる rolling release に合わせてソフトウェアをテストするのは、非常に難しい。大手の銀行などから見ても、rolling release に対応したソフトウェアを作るよりも、パッチの backport の方が扱いやすいと考える

質問者と Aaron 氏への謝辞のあと、時間が少し超過したと断って、Lachie 氏のまとめに交代します。

## 7. 注意点・発表者の気付き

- **CentOS を使わない**：CentOS 7 や 8 は非常に古いので、移行が必要だと述べられています。使うなら CentOS Stream です
- **AI により、脆弱性対応の前提が変わった**：連鎖攻撃や、類似の脆弱性を探す作業の高速化により、「30 日以内のパッチ」のような従来の期間では間に合わないという指摘です
- **パッチ速度とテスト品質、顧客の負担のトレードオフ**：パッチを速く出すほど顧客の負担が増え、一方で、テストを省くと壊れて障害になる、という緊張関係があります。業界全体で解く課題だとされています
- **社内向けにとどめておくと問題が出た**：Azure Linux は当初、社内プログラムにとどめる意図でしたが、AKS のように社内外の境界が曖昧なサービスがあり、顧客からの問い合わせも受けて外部提供に方針を変えたと説明されています
- **標準化の効果**：社内で多様なディストリビューションが使われていた時期は、コンプライアンスの追跡が非常に大変だったと説明されています
- **Jef Spaleta 氏**：登壇者として名前が挙がっていた人が今回は同席していない、という発言があります（理由は述べられていません）

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。顧客事例としての具体的な成果の数字は、このセッションでは示されていません。

- **選択の自由**：モデルを proprietary から特化モデル、open weight モデルへ切り替えても、構築した知識やコンテキストを失わない
- **実行場所の自由**：ソブリン環境、オンプレミス、パブリッククラウド、他のクラウドの間を、学習ループを作り直さずに移動できる。Microsoft が自社システムで使っているものと同じソフトウェアを、自分の環境で動かせる
- **透明性**：Azure Linux の開発は GitHub で公開され、Fedora の spec ファイルの変更箇所と理由も確認できる
- **標準化された基盤**：パッチ適用やコンプライアンスの判断が簡単になる
- **OSS 版の AI ツール**：Kaito（ワンクリックのモデルデプロイ）、AI Runway（デプロイ・トレーニング・強化学習）、Radius（クラウド非依存のアプリモデル）、MIT ライセンスの open weight モデル
- **ノードの追加の速さ**：起動の速さが、急なスケールの場面で効くと説明されています

## 9. まとめ

このセッションは、**AI learning loop を自社の管理下に置く**ための基盤として、OSS を使う意義を説明するものでした。モデル（proprietary から open weight まで）と実行場所（ソブリン、オンプレミス、パブリッククラウド）を自由に選べることが前提で、Microsoft は OS（Azure Linux、Flatcar）、Kubernetes（Kaito、AI Runway）、アプリモデル（Radius）、モデル（MIT ライセンスの open weights）の各層で OSS を使い、貢献していると説明しています。

Azure Linux のパートでは、CBL Mariner から続く歴史、Azure の顧客コアの 70% 超が Linux であること、AI ワークロードの土台としての Linux の重要性、Fedora との協力関係が語られました。質疑応答では、AI で加速する CVE への対応という、業界共通の課題が議論されています。業界全体で、パッチ速度、テスト品質、顧客の負担のバランスを見つける必要があるというのが結論です。

Lachie 氏は、Microsoft がオープンソースに貢献する理由を「簡単だからではなく、一緒に作るほうがより良いソフトウェアになり、顧客の成果も良くなるから。顧客自身もそれを求めている」と説明しています。そのうえで、紹介したソフトウェアを実際に使い、Issue や PR でフィードバックを返してほしいと呼びかけています。また、自分自身も自宅に小さな環境（lab）を作って、自分の学習ループを組み始めていると述べ、小さく始めることを勧めています。
