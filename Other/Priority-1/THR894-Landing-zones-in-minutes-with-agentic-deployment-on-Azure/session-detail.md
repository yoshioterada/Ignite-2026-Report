# THR894 Landing zones in minutes with agentic deployment on Azure

## 1. はじめに

このセッションは、クラウド移行（モダナイゼーション）を進めるうえで避けて通れない **ランディングゾーン** を、Azure Catalyst でどのように短時間で設計し、デプロイできるかを紹介する 25 分のシアターセッションです。

発表は、製薬会社「Caldova Pharma」のクラウドプラットフォーム担当者という役を一人の登壇者が演じ、もう一人の登壇者（Azure Catalyst の Product Manager）が解決策を見せる掛け合い形式で進みます。**セキュリティ承認**と**予算**という 2 つの課題に対して、Azure Catalyst が「プラットフォームのランディングゾーン」と「アプリケーションごとの設計」を提案し、Terraform テンプレートとしてダウンロードできることが説明されました。最後は会場からの質問に充てられ、現時点の制約（greenfield 中心、監査証跡なし、など）が率直に語られています。

## 5. 発表内容の詳細

### 5.1 Caldova Pharma の現状と課題

Pradeep 氏が演じる担当者は、Collector を使った探索を終えており、Azure Catalyst が生成した成果物を使って経営層の了承（green signal）も得ていました。しかし、**Azure にはまだ 1 つのアプリケーションも移せていません**。理由は次の 2 つです。

| 課題 | 内容 |
|---|---|
| セキュリティ承認 | CISO は、アプリを移す前に、クラウド基盤の設計の承認を求めている。一貫したネットワーク設計、適切な ID とアクセス制御、集中的なガバナンスポリシーが必要で、設計・調整・承認に時間がかかる |
| 予算 | アプリケーションごとの Azure アーキテクチャを決める必要があるが、全アプリについてコンサルタントやアーキテクチャワークショップの費用を出せない。重要なアプリだけが手厚く扱われ、残りは lift and shift になるため、モダナイゼーションの利点を得られず、AI 対応（AI ready）にもならない |

現在の進め方は、アーキテクト、ネットワーク、ID、セキュリティの各チームが集まり、Cloud Adoption Framework の標準テンプレートから始めて、複数回のワークショップで設計を固めるというものです。自社の要件・セキュリティ標準・ポリシーに合わせてカスタマイズするので、**数週間から数か月**かかります。CISO が全体像を初めて見られるのは数か月後です。また、アーキテクトがそれぞれ強い意見を持つため、ベストプラクティスに揃えるのに時間がかかり、「基盤の設計より、アーキテクトの意見調整のほうが時間がかかることもある」とのことです。

### 5.2 プラットフォームランディングゾーンとアプリケーションランディングゾーン

Azure Catalyst は、**プラットフォームのランディングゾーン**と、**ワークロードのランディングゾーン**の両方を設計します。これにより、CISO は初日から全体像を確認できるとされています。認識を揃えるため、登壇者は新しい都市のたとえで説明しました。

- 家が建つ前に、都市の行政が道路・水道・電力といった基本設備を整え、共有スペースの使い方や家の建て方のルールを決めます。Azure でこれにあたるのが**プラットフォームランディングゾーン**です。ネットワーク、セキュリティ、ID、管理、コンプライアンスの基盤を整え、ポリシーと監視の仕組みも設定します。
- 土地の所有者は、自分の区画に、必要に応じて家を建てます。ただし行政が決めたルールには従い、道路や電力といった共有サービスも使います。これにあたるのが、アプリケーション（ワークロード）ごとのランディングゾーンです。アプリの要件に応じて、中核となるワークロードのリソースと、それを支える Azure リソースをデプロイします。ポリシーはプラットフォームチームが先に決めたものに従います。

> 補足：トランスクリプトでは、アプリケーション側の区画を指して「platform landing zone」と言い間違えている箇所があります。文脈上は、ワークロード（アプリケーション）ランディングゾーンを指しています。

CISO がまずプラットフォームランディングゾーンの承認を求める理由として、「アプリの所有者は創造的で、それぞれが自分の理想の街を作り始めてしまう」ためだと、掛け合いの中で語られました。街がばらばらに増えると一貫性を保つのが難しくなります。登壇者は会場に「アプリの移行を始めてから、ネットワークや ID の設定を変更する必要があった人は？」と質問しましたが、手は挙がりませんでした。そのうえで、この設定は**後から変更するのが非常に難しい**ため、最初に正しく作るべきだと述べています。セキュリティと集中ガバナンスを初日から組み込めば、すべてのアプリが同じやり方で Azure に着地し、組織が望むコンプライアンスとポリシーに従います。

### 5.3 プラットフォームランディングゾーンの提案

Azure Catalyst は、**資産の状況とモダナイゼーションの目標という文脈**に基づいてプラットフォームランディングゾーンを提案します。ネットワーク、セキュリティ、管理、ID、コンプライアンスをまとめ、回復性の要件も満たす構成です。

提案をそのまま使えるとは限らないため、次のカスタマイズが用意されています。

- ネットワークは **hub-and-spoke** と **virtual WAN** のモデルから選べます。
- ファイアウォールは、デフォルトでは Azure Firewall が推奨されますが、サードパーティのファイアウォールも選べます。
- DDoS protection と ExpressRoute のデプロイを有効・無効にできます。

### 5.4 アプリケーションごとの設計

予算の課題に対して、Azure Catalyst は**評価したアプリケーションごとに、モダナイゼーションに適したアーキテクチャを生成**する機能を、今年提供予定とのことです（「this year, Azure Catalyst is coming up with a capability」という説明です）。この推奨は、Azure Architecture Center にある標準アーキテクチャのカタログから作ったナレッジグラフを根拠にしています。Cloud Adoption Framework のベストプラクティスにも沿っており、ランディングゾーンのどの部分も、チームがカスタマイズできます。

#### Asset Manager

Asset Manager は、SQL Server クラスター 1 つ、Web アプリ 2 つ、ファイル共有 2 つで構成されたアプリです。推奨は次のとおりです。

| 階層 | 推奨サービス |
|---|---|
| Web 層 | Azure App Service |
| データベース層 | Azure SQL Database Elastic Pool Hyperscale |
| ファイル共有 | Azure Files |

これらは中核ワークロードにすぎません。アプリを安全に動かすため、ネットワーク、セキュリティ、回復性などを組み込んだ**アプリケーションランディングゾーン**の設計が付きます。具体的には次のとおりです。

- 各階層のサブネットが定義され、ネットワークのフロー（どう流入するか、どのサービスをデプロイするか）が分かります。
- セキュリティの管理方法や、シークレット・パスワードの扱い、Key Vault が必要かどうかが分かります。
- 階層ごとのコスト内訳が分かり、このアプリの見積もりは **$589**（月額。発話では「$589 a month」）です。

#### Clinical Ops

Java と Oracle データベースのアプリです。推奨は、アプリ層が Azure Kubernetes Service、データベースが Azure Database for PostgreSQL flexible server です。AKS 用の Container Registry など、同様の支援サービスも推奨されます。

> 補足：すべてのアプリとプラットフォームが整うと、全アプリが同じネットワークと ID を共有し、ポリシーは初日から設定され、各アプリがモダナイゼーションに適したアーキテクチャを持つ、と登壇者は整理しています。Caldova 側は、これで architecture review board の承認が早まり、lift and shift だけでなく、より多くのアプリをモダナイズできるようになると述べています。

### 5.5 Terraform テンプレートのダウンロードとデプロイ

承認された設計は、**infrastructure as code としてダウンロード**できます。Terraform テンプレートが提供され、ネットワーク、セキュリティ、ID の変数があらかじめ入っています。利用者は変数を更新したうえで、**一度にデプロイ**できます。提供されるスクリプトを使えるほか、ユーザー自身のモデルや VS Code などと組み合わせてデプロイすることもできます（発話では「any of your models or any of your cloud or VS code」と聞こえます。音声認識の都合で表記が確定できません）。

Caldova 側は、現在はエンジニアがアプリごとに、異なるツールやエージェントを使ってデプロイテンプレートを書くのに多くの時間を使っていると述べ、その時間が戻ってくる点を歓迎しています。

### 5.6 Q&A

最後に会場からの質問を受け付けました。

| 質問 | 回答の要点 |
|---|---|
| Azure Policy はどこで適用されているのか | ベースとなる CAF（Cloud Adoption Framework）と WAF の原則から始める。そのすべてをコード化した MD ファイルが提供され、カスタマイズできる。Terraform テンプレートもカスタマイズ可能。現時点で提供されるのはベースのテンプレートで、パラメーターで変更できる範囲は限られるが、今後パラメーターを大幅に増やす予定。Azure Policy という名称そのものに対する直接の回答は、発話からは確認できなかった |
| CISO が承認した設計の監査証跡はどこに残るのか | 現時点では、**監査証跡は完全には組み込まれていない**。有用なフィードバックとして持ち帰る。設計は変更してダウンロードし、チームに持ち帰れるが、監査証跡を製品に組み込む機能は今のところない |
| greenfield 専用か、既存のプラットフォームランディングゾーンを分析できるか | 現在は **greenfield 向け**。数日のうちに **brownfield** の対応も提供する。その間も、アプリケーションランディングゾーンの設計は greenfield と brownfield の両方の顧客で使える |
| 費用はかかるか | **完全に無料** |
| 紹介されたアプリは、収集した情報や移行ウェーブに対応づけられるか | アプリケーション設計は、オンプレミス環境で特定したワークロード（データベース、サーバー、Web アプリ）と、取得できるネットワーク情報から始まる。これらをまとめて中核となるターゲットリソースを特定し、アプリの重要度と複雑さに基づいてアプリケーションランディングゾーン（回復性・バックアップ・ネットワークのサービスなど）を推奨する。ファイアウォールの種類、マルチリージョンかシングルリージョンかもここに組み込める。移行ウェーブへの対応づけについては、直接の言及は確認できなかった |
| リソースは private endpoint 付きでデプロイされるか | 何を求めるかによる。Azure Files やデータベースなどを private endpoint の背後に置くよう指定すれば、そのとおりに推奨される。デフォルトの設計は CAF と WAF の原則に基づき、dev/test アプリなら private endpoint は不要だが、本番レベルや事業上きわめて重要なアプリでは推奨が変わる |
| プラットフォーム（バックボーン）とアプリのどちらの展開に対応するか | 現時点では両方に対応する。ただしプラットフォームランディングゾーンは主に greenfield 向けで、WAF と CAF の原則に基づくベース設計であり、カスタマイズ性は低い（変更できるパラメーターは少数）。アプリケーションランディングゾーンのカスタマイズ性ははるかに高く、必要なリソースの種類やデプロイするワークロードの種類を変更できる。例として、ストレージのターゲットを GRS から LRS や GZRS に変える、といったことが挙げられた |

最後の質問への回答では、将来の計画として、回復性・セキュリティ・コスト・パフォーマンスの**スケール（尺度）**を用意し、上げ下げできるようにする構想が語られました。たとえば回復性を高くすれば、費用も増えるため、これらを連動させて推奨する、という考えです。登壇者は「製品に入れてみて、どうなるかを見る」と述べており、確定した機能としては紹介されていません。

## 6. デモ・手順

**画面を使ったデモがあります。** 登壇者は「this is the platform landing zone that Azure Catalyst recommends」「Let's see what we have here」などと言いながら、Azure Catalyst の画面を示しています。ただし録音は音声のみで、ボタン名や画面レイアウトなどの操作の細部は語られておらず確認できません。語られた範囲で、順に整理します。

1. Caldova 向けに Azure Catalyst が推奨する**プラットフォームランディングゾーン**を表示します。資産の文脈とモダナイゼーションの目標に基づく構成で、ネットワーク、セキュリティ、管理、ID、コンプライアンスをまとめ、回復性の要件も満たしています。
2. Caldova 側が、自社のサードパーティ製ファイアウォールを使えるかを尋ね、ネットワークモデル（hub-and-spoke か virtual WAN）、ファイアウォール（Azure Firewall か他製品）、DDoS protection、ExpressRoute のデプロイを選べると回答しています（5.3 参照）。
3. アプリケーションとして **Asset Manager** を選びます。SQL Server クラスター 1 つ、Web アプリ 2 つ、ファイル共有 2 つという構成を確認し、推奨アーキテクチャを見ます（App Service、Azure SQL Database Elastic Pool Hyperscale、Azure Files）。
4. サブネット、ネットワークフロー、デプロイするサービス、セキュリティの管理（シークレットや Key Vault の要否）、階層ごとのコスト内訳を確認します。見積もりは月額 $589 です。
5. 続いて **Clinical Ops** を開き、AKS と PostgreSQL flexible server の推奨、Container Registry などの支援サービスを確認します。
6. 承認された設計を Terraform テンプレートとしてダウンロードする方法が、口頭で説明されました（5.5 参照）。このダウンロードやデプロイそのものを画面で実行したかどうかは、発話からは分かりません。

## 7. 注意点・発表者の気付き

Q&A で、現時点の制約が率直に語られています。

- プラットフォームランディングゾーンは、**主に greenfield 向け**です。brownfield の対応は、数日のうちに提供予定とされています。
- プラットフォームランディングゾーンのカスタマイズ性は限定的で、変更できるパラメーターは少数です。アプリケーションランディングゾーンのほうが、はるかにカスタマイズできます。
- **監査証跡**は、現時点で製品に完全には組み込まれていません。
- 提供されるのはベースのテンプレートで、今後カスタマイズが増える予定とされています。
- アプリケーションごとのアーキテクチャ生成は、発表では「今年提供予定」の機能として紹介されています。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 数週間から数か月かかっていたランディングゾーンの設計を、数分で提案できます。CISO は初日から全体像を確認できます。
- 全アプリについてコンサルタントやワークショップの費用を出さなくても、アプリごとにモダナイゼーションに適した設計を得られます。lift and shift だけの選択を避けられます。
- 階層ごとのコスト内訳つきの見積もりが得られます（デモの Asset Manager は月額 $589）。
- Terraform テンプレートをダウンロードして一度にデプロイでき、エンジニアは、アプリごとのデプロイテンプレート作成から解放されます。
- 利用は無料です。

## 9. まとめ

Azure Catalyst は、プラットフォームのランディングゾーンと、アプリケーションごとのランディングゾーンの設計を提案し、Terraform テンプレートとして取り出せるようにします。このセッションは、「セキュリティ承認」と「予算」で止まっていた Caldova Pharma の課題に、それぞれ答える形で構成されていました。

一方で、プラットフォームランディングゾーンは現在 greenfield 中心でカスタマイズ性が低く、監査証跡も未対応です。brownfield は数日のうちに提供予定とされています。試すには、スライドの QR コードから Azure Catalyst のページに移動でき、登壇者はブースでも相談を受け付けると案内しています。
