# BRK441 Inside Azure Maia: Purpose-built for AI inference at scale

## 1. はじめに

このセッションは、Microsoft が自社設計している AI アクセラレーター **Azure Maia** の中身を、チップ、ラック、ネットワーク、検証手順、ソフトウェアスタックまで順に解説するものです。Copilot に 1 つ質問をしたとき、回答が返るまでの間にインフラ側で何が起きているのか、という問いから出発します。

発表の結論は、推論性能は「チップだけの性能」ではなく「システム全体の性能」で決まるので、シリコン、システム、ネットワーク、データセンター、ソフトウェアを一体で共同設計する、というものです。最新世代の Maia 300 では、Maia 200 に対してラック単位で HBM 帯域 5 倍、ラック規模のトークンスループット 7 倍などが示されました。ハードウェアやインフラの設計に関心がある人向けの内容で、API の使い方やコードの解説はありません。

### 5.1 質問の裏側にある Microsoft の AI スタック

発表者はまず、コードを書かせる、文書を要約させるといった日常的な質問を例に挙げ、今後はエージェントのチームを立ち上げて、新薬の発見のような課題に取り組ませる世界に移っていくと述べています。

発表者は、Copilot やコマンドラインツールで質問したときの流れを、次のように説明しています。

| 層 | 発表で語られた役割 |
| ---- | ---- |
| Copilot など | 最初にモデル呼び出しを行う |
| Azure AI Foundry | マルチモデルの API 層。OpenAI、MAI、オープンソースのモデルを扱う |
| Manifold | Foundry からのリクエストを受け、どこでジョブを実行するか（キャパシティの割り当て先）を決め、下位の AI ハードウェアインフラに要求を送る |
| AI ハードウェアインフラ | ネットワークで接続されたシリコンとラック |

その「簡単な質問」の下には非常に大きな機械があり、答えが「速く、信頼でき、経済的」でなければならない、というのが発表の出発点です。

### 5.2 インフラが直面する制約と、スペクトラムの考え方

Microsoft は、上位の大規模 AI ワークロード（基調講演で触れられたもの）、それを動かすクラウドプラットフォーム、さらにシリコンやシステムの設計、データセンターの運用まで、全体を見渡せる立場にあると述べています。そのため、制約が 1 つの層に閉じていないことが多く、層同士の連携で解く必要があると説明しています。

AI ワークロードは、大規模トレーニングからエッジでの推論までスペクトラムを成しており、インフラも多様化しています。

* **汎用 GPU**: 最大の柔軟性があり、幅広いモデルとワークロードに対応する。何でもうまくこなす必要がある
* **専用 AI アクセラレーター**: 効率は非常に高いが、扱える問題、モデル、ユースケースの範囲が狭い

専用化しすぎると、変化の速い領域では将来変わるものに最適化してしまうリスクがあります。発表者は「6 か月前とは、ワークロードが全く違う」と述べています。一方で汎用のままでは、規模が大きくなったときに効率を取りこぼします。そこで、分かっていることとトレンドの見通しに基づいて最適化しつつ、未知の将来に適応できる柔軟性も残す、という位置づけに Azure Maia を置いています。

### 5.3 Maia の歩み

Maia は、Microsoft が自社で作った、**推論とスケールに最適化した AI アクセラレーター**です。

| 世代 | 発表での説明 |
| ---- | ---- |
| Maia 100 | シリコンを作り、データセンターに展開し、実際のモデルとワークロードを動かせることを自分たちで証明するための最初の取り組み |
| Maia 200 | 今年に入ってから発表。現在、データセンターで Microsoft の自社サービスの本番ワークロードを実行中 |
| Maia 300 | 数週間前に発表した次のステップ。発表では、来年データセンターに届けるものは数年がかりで開発してきたもの、と述べられています |

### 5.4 アーキテクチャの原則

まず推論ワークロードを理解することから始めました。ラボで 1 回動かすだけでは不十分で、フルスタックが動き、顧客のすべてのワークロードが同時に負荷をかけている状況でどこに時間がかかり、何がボトルネックになるかを把握する必要があった、と述べています。そこから見えた原則は次の 4 点です。

1. **推論はデータ移動の問題である。** 推論では、モデルの重みとアクティベーションをメモリと計算の間で常に移動させ、シリコン内部、ノード内、ラック内の複数のアクセラレーター間でも大量のデータを高速に動かす。そこで、データがいつどこへ動くかを正確にプログラムできる、ソフトウェア定義のデータフローアーキテクチャをゼロから作った。目的は計算を増やすことではなく、計算を通るデータの移動を効率的にすること
2. **リソースのバランスを取る。** 計算の FLOPS だけ、HBM 帯域だけを最大化するのではなく、HBM 帯域、チップ上の SRAM 量、計算 FLOPS、ネットワーク帯域を並行して釣り合わせる
3. **アーキテクチャを 1 チップの外へ広げる。** データはシリコンの端で止まらない。ラック内やクラスター全体でチップ間のデータを行き来させる。ネットワークアーキテクチャは、データフローアーキテクチャの延長として設計している
4. **データセンターと共同設計する。** かつては 1 ラックに何チップ詰めるかという高密度化が主眼だったが、非常に電力の大きいラックがデータセンターの真ん中に 1 つだけある、という配置は理想的ではない。データセンターのクラスター全体で、提供できる計算と性能を最大化する方向で設計する

これらの原則は、1 ドル・1 ワットあたりの有用なインテリジェンスを最大化するためのものです。

### 5.5 Maia 300 の概要

Maia 300 は、この原則に沿って設計した最新世代です。狙いは次の 2 つと説明されています。

* perf per watt を最大化し、顧客が最良の性能を最低のコストで使えるようにする
* 効率が高く拡張可能なシステムアーキテクチャを提供する。最適化の単位は「集約された性能」であり、推論性能はシリコンだけでなくシステム全体の性質だと考えている

そして、これらすべてがフルスタックのソフトウェアと開発者エコシステムの上に成り立っているという位置づけです。

### 5.6 シリコン: マルチチップレット設計

Maia 200 はモノリシックな SoC でしたが、Maia 300 は**マルチチップレット設計**に移行しました。複数のチップレットを 1 つの SoC として同一パッケージに載せる構成で、発表者は「レゴブロックの問題」と呼び、シリコンアーキテクトには「そう単純ではない」と言われると冗談めかして述べています。利点は 2 つです。

1. SoC 内で計算、メモリ、ネットワークのバランスを取れる
2. シリコン上の **shoreline（海岸線）問題**を解ける。メモリを計算ダイに直接つなげて性能を最大化し遅延を下げたいが、計算ダイは北から南までチップ全長には伸びていない。そこで、メインの計算ダイと、北側と南側の 2 つの IO ダイの間に、メモリインターフェースダイを置いた。これによって shoreline が広がり、計算ダイ自体を増やさずにメモリ搭載量を増やせる

結果として、このパッケージは次の仕様になります。

| 項目 | 値 |
| ---- | ---- |
| HBM スタック数 | 8 |
| HBM 帯域 | 18 TB/s |
| 電力 | 950 W 以内（「比較的控えめな電力枠」と表現） |

計算だけを増やす道を選ぶと電力が爆発し、システムレベルで足かせになるため、この選択をしたと説明しています。

### 5.7 ラックと pod サイズ

HBM 帯域に加え、pod サイズを倍にしました。ラックあたりのアクセラレーター数は、Maia 200 の 48 から Maia 300 では 96 になります。発表者は「非常に高密度なラックというわけではない」と述べています。この 2 つを合わせて、**ラックレベルの集約 HBM 帯域は 5 倍**になり、ラックの電力は 200 キロワット未満です。固定の MW 枠に、より多くの SoC を載せられるため、クラスターの展開が効率的になるという主張です。

### 5.8 バックエンドネットワーク

AI インフラのネットワークでは、複数ラックをつなぐ scale-out ネットワークと、ラック内のチップをつなぐ scale-up ネットワークがよく語られます。Maia では、両者を一体にした **unified scale-up fabric** を採用しています。帯域を、ラック内に送るか、クラスター全体に広げるかを選択的に決められる点が特徴です。ここでは scale-up ドメイン自体を拡大することに力を入れており、そのドメイン内の遅延と帯域が一部のワークロードにとって重要だと説明しています。

Maia 300 では、接続できる Maia の数とラック数も増えており、このトポロジーで**最大 12,000 個の Maia 300 を接続**できます。モデルが 10〜30 兆パラメータ規模に育つ場面で、Maia 300 のクラスターが真価を発揮すると見ています。

### 5.9 実物の紹介: ボード、トレイ、ラック（Vikram 氏）

ここからは、Vikram 氏が Maia 300 の中身を実物とともに説明しました。録音のため具体的な見た目は分かりませんが、語られた内容は次のとおりです。

* Maia 300 の SoC は、それぞれ個別のボード（board accelerator module）に載る。ボードの実物と、ボードに載る Maia 200 の SoC を見せている
* 1 ノードに、このボードが 4 枚入る
* 1 ラックには 24 台のトレイが入り、合計 96 個のアクセラレーターになる
* 統合されたアクセラレータートレイは、1 CPU に 4 GPU の「1 対 4」アーキテクチャ（発話では GPU と表現）。CPU と GPU の両方が液冷。DDR5 メモリ、PCIe Gen 6 対応のストレージドライブ 4 台、液体の接続用コネクター、カスタムのネットワークアダプター、データセンターセキュア制御モジュールを備える。ケーブルバックプレーンのコネクターがあり、バックエンドネットワークを担う背面のスイッチにつながる
* ラックには、3 台のバックエンドネットワークスイッチ、ラック前面と上部のスイッチ、専用の管理スイッチがある。計算、ネットワーク、電力、冷却のマニホールドを収めた、高密度で電力効率の高いラックとして紹介された

> 補足：発表者は「トレイの中のどれが何か」を指さしながら説明しているため、音声だけでは位置関係は分かりません。

### 5.10 冷却とデプロイ

Maia 300 のラックは、**空冷データセンターと液冷データセンターの両方**に展開できるよう設計されています。これにより、最新世代のラックを既存（レガシー）のデータセンターにも展開し、世界中の顧客にすばやく届けられるとのことです。空冷データセンターでは、Microsoft の最新の液体から空気への熱交換ユニット（発表では「Mount Atlas」と聞こえます。音声認識の都合で表記が確定できません）を使います。これは第 3 世代の HRU で、第 1 世代と比べて約 10 倍の冷却性能があるという説明です。

### 5.11 検証とラック立ち上げの戦略

重視しているのは、**シリコンとシステムを直列ではなく並行して立ち上げる**ことです。これにより、エンドツーエンドの開発が速くなり、システムをできるだけ早く顧客に届けられると説明しています。

* 最初のシリコンに依存しないものは、すべて事前に作って検証しておく。シリコンが届く「Day 0」から実行できる状態にする
* 機構、熱、ボード、トレイ、ケーブル、スイッチは、シリコンの到着前にそろえる。機能のおよそ 70% は、シリコン到着前に確認する
* 数千のテストとサイクルでバグを洗い出す。その結果、最初のラックの電源投入を、シリコン到着後の最初の数週間以内に行える。これを「speed of mire」と呼んでいる（音声認識の都合で表記が確定できません）
* ファームウェアとソフトウェアもシリコンを待たず、プリシリコンのプラットフォーム上で並行して有効化する

システム開発を加速するために、速度、可視性、忠実度のトレードオフが異なる 4 つのプラットフォームを使うと述べています。トランスクリプトで具体的に説明されたのは、ファームウェア開発の戦略として語られた次の 3 つの段階です。

1. **ソフトウェアエミュレーション**: ファームウェアとソフトウェアスタックの開発に使う。機能面の確認が中心
2. **RTL エミュレーション**: アクセラレーターを、プラットフォームに公開されるすべてのインターフェースを実際の RTL でモデル化した FPGA に置き換える。プラットフォームレベルでファームウェアのリスクを下げる
3. **tape-out サイン オフ**: 高忠実度のプラットフォームで実際の RTL を動かし、ハードウェアとソフトウェアの両方のリスクを下げる。最終的な tape-out サインオフに役立つ

加えて、目的別のハードウェアテストビークルを使い、シリコン、パッケージ、電力、ネットワーク、スイッチング、ラック統合のリスクを事前に下げて、シリコンが「待っているシステム」に届くようにします。発表者は、これらのプラットフォームにより、問題をより簡単に、速く、安く、デバッグできると説明しています。

> 補足：発表では「4 つのプラットフォーム」と言いながら、ファームウェア向けの 3 段階と、ハードウェアテストビークルが続けて語られています。4 つの内訳を明示した発言は確認できませんでした。

### 5.12 ソフトウェアスタックと Maia SDK（Andrew 氏）

ハードウェアだけでは意味がなく、Microsoft AI プラットフォームに統合し、異種混在のフリートの中で他のシステムと同じように振る舞う必要がある、と発表者は述べています。そのために、Maia のハードウェアの上に **Maia inference stack** があります。

* **対象モデル**: Mustafa 氏および Microsoft AI チームと密に連携し、MAI 2 モデルファミリ（朝の発表に言及。音声認識では「MAI2」）を Maia 上で最良に動くよう最適化している。加えて OpenAI のモデルとオープンソースモデルも、高い性能と効率で動かせるようにしている
* **Maia SDK**: 開発者が複数の抽象度でスタックに関われるよう設計されている。最上位の PyTorch、カーネルライブラリ、コンパイラのリファレンス実装を使える。さらに、ハードウェアに近い層でプログラムするニーズが高まっているため、**Maia NPL プログラミング言語**にもアクセスできる（言語名は音声認識の都合で表記が確定できません）
* **AI 支援ワークフロー**: 過去 6〜9 か月で AI 支援の開発が普及し、SDK は人間のエンジニアだけでなく、エージェント型のワークフローからも使える必要が出てきた。新しいモデルやワークロードを Maia へできるだけ速く移植・最適化するためである。この統合に時間をかけており、Maia 200 でテストしてきた
* **後方互換性**: Maia 200 でこれまでにやってきたことは、Maia 300 にも引き継がれる

### 5.13 ワークロードでの成果

Maia 200 は現在、Microsoft の自社サービスの本番を動かしており、重視するユースケースで最高水準の性能を出していると説明されています。発表者は、スループット対インタラクティビティのチャートは見せない（あえて持ち込まなかった）と述べ、ユースケースごとに最適化点が違うことが重要だとしています。

| ユースケース | 最適化の方向 |
| ---- | ---- |
| Microsoft AI チームの合成データ生成（次世代モデルの学習用） | 最大スループットを重視。インタラクティビティは重視度が低い |
| Microsoft 365 のオフライン・バッチ・非同期の用途 | 同上。レイテンシー SLA はない |
| GitHub の同期的なコーディングシナリオ（GitHub Copilot） | 回答がすぐ必要で、5〜20 ミリ秒のレイテンシー目標が重要。曲線上の別の部分を最適化する |

これらをまとめた Maia 200 の成果は、**トークン/メガワットが約 40〜70% 向上**したことです。顧客にとってのコストと経済性の改善につながると説明されています。これはアーキテクチャの原則とフルスタック統合戦略を裏づけるもので、Maia 300 にも引き継がれる見込みだと述べています。

Maia 300 に期待される値は次のとおりです。

* Maia 200 に比べ、**ラック規模のトークンスループットが 7 倍**になる見込み（速度と構成、ラック密度の増加による）。複数ノードにまたがる次世代モデルに役立つ
* クラスターレベルでは、電力最適化とモデル最適化により、固定の MW 電力枠に **Maia 300 を 80% 多く詰め込める**と見込む。これが、**2027 年にトークン/メガワットで 40% の向上**につながる

> 補足：上記はいずれも発表者の「見込み」「期待」であり、Maia 300 の実測結果としては示されていません。

## 7. 注意点・発表者の気付き

* 専用化しすぎると、変化の速い領域で将来変わるものに最適化してしまうリスクがあり、汎用のままだと規模が大きいときに効率を取りこぼす。このバランスが設計の難所と語られています
* インフラは「トークンが 3,000 倍になったから 3,000 倍に拡張する」というわけにはいかず、電力、冷却、ラック内の計算・メモリ・ネットワーク帯域に実際の制約があります
* 高密度な 1 ラックだけを追求しても、データセンター全体のレイアウトとしては理想的でない場合があります
* 推論性能はシリコンだけでなくシステム全体の性質で決まる、という点が繰り返し強調されています
* インフラの開発には年単位かかり、来年データセンターに展開されるものは数年がかりで開発されたものだ、と語られています
* Maia 300 の数値の一部（7 倍、80%、40%）は期待値であり、実測値として示されたのは Maia 200 の約 40〜70% のトークン/メガワット向上です

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* **コストと経済性**: perf per watt を最大化することで、最良の性能を最低のコストで提供する。Maia 200 ではトークン/メガワットが約 40〜70% 向上し、コストと経済性の改善につながる
* **スケール**: Maia 300 は最大 12,000 個を接続でき、10〜30 兆パラメータ級のモデルでの性能を想定している
* **複雑さの隠蔽**: 発表で語られた複雑さは顧客に転嫁せず、顧客は意識せずに恩恵を受けられるようにする
* **幅広いモデルへの対応**: MAI、OpenAI、オープンソースのモデルを高い性能と効率で動かす。Maia SDK では PyTorch から低レベルのプログラミングまで複数の入口がある
* **レイテンシーが重要な用途への対応**: GitHub の同期的なコーディングシナリオで 5〜20 ミリ秒のレイテンシー目標を意識して最適化している

顧客の導入事例や具体的な課金・提供リージョンの情報は、発表では触れられていません。

## 9. まとめ

Azure Maia は、推論を「データ移動の問題」と捉え、データフローアーキテクチャ、バランスの取れたリソース配分、統合 scale-up fabric、データセンターとの共同設計で作られた AI アクセラレーターです。Maia 300 では、マルチチップレット設計で HBM を 8 スタック、18 TB/s を 950 W 以内に収め、ラックあたり 96 アクセラレーター、最大 12,000 個までのクラスターを構成します。シリコン到着前に機能の約 70% を検証する方針で、立ち上げも速めています。

Maia 200 は自社サービスの本番で、トークン/メガワットを約 40〜70% 改善しました。Maia 300 では、ラック規模のトークンスループット 7 倍、2027 年にトークン/メガワット 40% の向上を見込んでいます。Maia 300 については、発表の最後に「来年が楽しみ」と述べられています。
