## 5. 発表内容の詳細

### 5.1 AI ワークロードを動かす 4 つの形

Azure 上のワークロードは、次のスペクトルのどこかに位置づけられます。左ほどインフラ管理が少なく、右ほど自分で管理する範囲が広がります。

| 位置 | 形態 | 説明 |
| ---- | ---- | ---- |
| 左端 | Microsoft Foundry | モデルをエンドポイントやサーバーレスとして実行する。インフラ管理はすべて Microsoft が行う |
| 左から 2 番目 | Foundry managed compute のデプロイ | 専用のキャパシティを支払い、Microsoft が管理する。インフラは引き続き Azure が管理 |
| 右から 2 番目 | AKS ベースのデプロイ | 自分のモデルを持ち込む。ノードプールやサービングスタックなどのインフラを自分で管理する |
| 右端 | 自己管理の Kubernetes | インフラに加えて、オーケストレーションも自分で管理する |

多くの組織は左側の pilot から始めます。しかし、アプリケーションがスケールして、独自の要件、コストの検討、多数の顧客への提供、データ所在地（特定のリージョンでホストする必要）といった制約が出てくると、右へ移っていきます。右へ行くほど管理するインフラが増えるため、インフラの運用に「インテリジェンス」が必要になる、というのが発表者の見立てです。このセッションは、自分で管理する範囲が広い AKS と自己管理 Kubernetes が対象です。

### 5.2 顧客調査で見えた 2 つのループ

顧客調査の結果として、AI インフラのデプロイは 2 つのループだと説明されています。

1. **Pilot のループ**：GPU を選び、実際のトラフィックでアプリを動かし、レイテンシ、GPU の利用率、ワークロードの性能などの KPI を監視する。要件に合わなければ別の GPU SKU を選び、これを繰り返す。このループは何週間も続くことがある。
2. **本番のループ**：アプリが稼働した後、ワークロードを本番にデプロイし、レイテンシ、コスト、性能などの KPI を監視しながら、アプリケーションを調整して KPI を改善していく。

### 5.3 Day 0 の課題

day 0 は、デプロイのためにインフラを準備する段階です。複雑になる理由として、次の点が挙げられました。

- 公開されている情報は一般的で、自分のアプリケーション要件（特定のレイテンシ要件や負荷要件）にそのまま当てはまらない。「他人のワークロード」の情報である。
- GPU の供給が限られている。希望のリージョンで必要な GPU が取れないことがあり、他のリージョンでキャパシティを交渉して、そこでアプリを試すことになる。
- こうした作業に数週間かかる。「念のため」に余分なキャパシティを確保するチームも多く、遊休 GPU が増えてコストが上がる。
- 稼働後にも、コストの驚きが出てきて、想定と異なるため再調整が必要になる。

### 5.4 Project Optima

発表者は、数週間かかるデプロイの時間を、数分から数日に縮められるかという問いのもと、Project Optima を Ignite のプレビューとして紹介しています。「AI インフラの頭脳」にたとえ、ワークロード向けの AI infrastructure intelligence と位置づけています。

- **day 0**：適切な SKU を推奨する。推奨は、MLPerf、vLLM などのベンチマークデータと、Microsoft 自身がモデルを動かしているベストプラクティス（まとめでは Microsoft Foundry の managed model hosting 由来と説明）に基づく（トランスクリプト上の綴りは「MLPerf」「VLLM」。音声認識では「MLPA」とも出てくる）。
- **稼働後**：推論を遅くしているもの、最適でない原因を自動的に見て、最良のレイテンシ、コスト、性能のために改善できる点を推奨し続ける。
- **使える場所**：Azure Portal、Azure Copilot、MCP サーバー（任意のコーディングアシスタントから使える）、チャットなど、使い慣れたインターフェースから利用できる。別の場所へ移動する必要はない。

### 5.5 Day N の課題

稼働後（day N）の動かし方が、レイテンシ、スループット、コストを決めます。AI 推論のデプロイで特に多い課題として、3 つが説明されています。

1. **KV cache**：プロンプトが長くなると、モデルの重みと GPU メモリを奪い合う。GPU メモリから CPU メモリやリモートストレージにあふれ（overflow）、time to first token が悪化する。
2. **バッチング**：バッチ処理にするとスループットは上がるが、最適なバッチサイズを超えると詰まり、推論の出力のレイテンシが上がる。バランスの問題。
3. **キャパシティと、理想構成からの乖離（drift）**：ピーク向けにプロビジョニングすると、ほとんどの時間は使われず、コストが積み上がる。また、理想の構成を選んでいない場合（例：RDMA の構成を使っていない）、ワークロードのレイテンシが増える。

これらが、稼働中のコストの課題につながります。

### 5.6 day 0 と day N の変化（発表者のまとめ）

発表者は、これまでと今の違いを次のように説明しています。

- これまで：GPU を選んで、それが性能要件を満たすか手探りで確かめ、ループを繰り返していた。
- 今：推測を避け、最適な SKU と構成から day 0 に始められる。希望リージョンで SKU が使えなければ、同じリージョンや別のリージョンの代替 SKU を探せる。ベンチマークデータも見られる。
- 数週間の反復が簡単になり、1 分で始め、数日で最適な構成を推論ワークロードにデプロイできる、と述べている。

## 6. デモ・手順

3 つのデモがあります。画面の詳細は音声からは確認できないため、語られた範囲だけを書きます。

### 6.1 デモ 1：Kubernetes Center で SKU を選ぶ

発表者は、Ignite で発表した「AKS AA Manager」（音声認識の都合で表記が確定できません）を使って、モデルを AKS クラスターに直接デプロイできると述べたうえで、デモを行っています。

1. Kubernetes Center で、モデルを選ぶ。デモでは「Microsoft 5.4」モデル（音声認識の都合で表記が確定できません）を選んだ。
2. デプロイをクリックする。
3. リージョンに East US を指定した。最適な SKU が自動的に選ばれ、コストの見積もりが表示される。この見積もりは Azure の小売価格ではなく、自分のサブスクリプションに適用される価格（エンタープライズ割引などを含む）に基づく。1 時間あたりのコストが分かる。これらの情報は、裏側の Project Optima から提供される。
4. 下へスクロールして「edit SKU」をクリックする。サブスクリプションで利用可能なすべての SKU と、1 時間あたりのコスト、time to first token のベンチマーク指標、1 秒あたりのトークン数が表示される。業界標準のデータソースとベストプラクティスのベンチマークデータが元になっている。
5. サブスクリプションにまだ無い代替 SKU も表示され、価格、レイテンシ、time to token を確認できる。
6. 理想に合う別の SKU があれば、クォータをリクエストし、推論デプロイのためのキャパシティを確保できる。

### 6.2 デモ 2：VS Code と ARM MCP server

1. VS Code に、最新の ARM MCP server がインストール済みの状態から始める（「ARM MCP server を検索してインストールするだけ」と説明）。
2. VS Code の Copilot のチャットを開き、プロンプトを入力する。内容は「Red Hat Llama モデル（聞こえた表記のまま。音声認識の都合で確定できません）を Central US で動かしたい。ベンチマークと価格を含めて、適切な SKU を特定してほしい」という趣旨。発表者は、これは数時間前に実行した結果だと述べている。
3. プロンプトは Azure ARM MCP server に届き、裏で Project Optima が呼び出される。
4. 結果として、指定したモデルに適した構成、クォータの有無、コスト、推定性能、さらにモデルの適合（モデルのサイズ GB と KV cache など）が表示される。SKU、トポロジー、トークン、コスト、サブスクリプションのクォータなど詳細が並んだ順位付きの選択肢も表示される。
5. 自然な会話の言葉で、ワークロードに理想的なデプロイ構成について質問を続けられる。チャットインターフェースや、どのコーディングアシスタントからもそのまま使える。

### 6.3 デモ 3：day N の推論の遅延を特定して改善する

こちらはシナリオを語る形式で説明されています。

1. 「A coin model」と聞こえるモデル（音声認識の都合でモデル名は確定できません）が、AKS 上で vLLM を使って動いている。
2. 突然、time to first token が急上昇し、ユーザーは応答に数分待つことになる。
3. オーナーが VS Code で Project Optima に質問する。裏には、マネージド Prometheus、vLLM、DCGM のメトリクスがある。インシデントの時間帯に絞る。
4. 利用可能なすべての detector を評価し、1 つの問題を見つけた。**KV cache のプリエンプション圧力（preemption pressure）**。プリエンプションがしきい値を大きく上回り、待機中のリクエストが 137 を超えていた。リクエストが一時停止され、再計算されることで、time to first token が増えている。
5. causal graph（因果グラフ）が、detector の証拠から所見までをたどる。
6. 次にオーナーが改善策を求め、現在のサービング構成を共有する。3 つの順位付きの推奨が返る。それぞれに、変更内容、期待される効果、信頼度（confidence）、確認方法が含まれる。
7. 最上位の修正を AKS に適用する。同じ高負荷の状態で、平均の time to first token が **14.9 分から 2.2 分** に下がり、プリエンプションは 0 になった。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **day 0 の手探りを減らす**：最適な SKU と構成から始められる。希望リージョンで取れなければ、代替 SKU を同じリージョンか別のリージョンで探せる。数週間のループが、数日、最短では 1 分で始める形になる。
- **コストの見通し**：自分のサブスクリプションの価格（割引込み）で、1 時間あたりのコストを確認できる。
- **根拠のある推奨**：MLPerf、vLLM などのベンチマークデータと、Microsoft がモデルを動かしているベストプラクティスに基づく。
- **day N の改善**：原因の特定（detector と causal graph）、順位付きの改善案（変更内容、期待効果、信頼度、確認方法）。デモでは time to first token が 14.9 分から 2.2 分に下がった。
- **使い慣れた場所で使える**：Azure Portal、Azure Copilot、MCP サーバー経由の任意のコーディングアシスタント、チャット。

## 9. まとめ

GPU の利用率の低さとコスト上昇が同時に起きている背景には、容量不足ではなく、適切なサイズ選びの問題があります。Project Optima は、day 0 では MLPerf や vLLM などのベンチマークと Microsoft のベストプラクティスに基づく SKU の推奨を、day N では推論の遅延の原因の特定と順位付きの改善案を提供します。

day 0 の体験（Kubernetes Center）は Ignite からプレビューで、ARM MCP server、Azure Copilot、day N の最適化は今後数週間でプレビューの予定です。発表者は、画面の QR コードから、サインインしてプレビューアクセスを得ることと、Project Optima へのフィードバックを求めています。
