# BRK449 Modernize Windows Server apps with no code rewrite to App Service

## 1. はじめに

このセッションは、Azure App Service のプロダクトチームの 2 人が、「コードを書き換えずに」既存アプリを App Service に載せ、そのうえでプラットフォームの機能を使ってアプリを良くしていく流れを、デモ中心に紹介したものです。公式概要では、.NET や Windows Server 上のアプリを VM で運用している企業が対象とされています。

話は「過去・現在・未来」の 3 部構成です。過去から取り残された Windows 依存のアプリを **App Service Managed Instance** で現在に持ち込み、コードに触れずに AI 機能を足し、さらに geo-redundancy、ポスト量子暗号の TLS、egress 制御、App Service Builder といった、App Service の新しい機能を見ていきます。発表者自身が「デモが盛りだくさんのセッション」と述べており、時間切れで Q&A は行われませんでした。

## 5. 発表内容の詳細

### 5.1 なぜ App Service か：パッチ適用を任せられる

Byron 氏は、Cybersecurity Awareness Month にちなんで次のスライドを示しました。過去 3 か月に、.NET、Node、PHP、Python などで **12 回のセキュリティリリースの波**がありました。App Service のようなプラットフォームを使っていなければ、CVE の評価、自分のアプリが影響を受けるかの判断、修復方法の検討、パッチ適用を自分たちでやる必要があります。App Service 上のアプリなら、それをすべてプラットフォーム側が行います。

ブログに出た例として、PHP や Brotli 関連（音声認識の都合で正確な名称は確定できません）、証明書関連（"eMudra" と聞こえます）の対応に加え、カナダがタイムゾーンを変更した件にも対応した、と述べています。開示から数時間以内にパッチを適用したという説明です。

コスト比較の際に見落とされがちなのは、CVE ごとに影響を評価し、修復計画を立て、パッチを当て、失敗したらロールバックする運用チームのコストだ、という指摘でした。

### 5.2 過去から現在へ：背景と課題

Andrew 氏は、次のようなモダナイズの動機を挙げました。

- 2016 のサポート終了、SQL Server のサポート終了が迫っている（「2016 end of life」という発言で、対象の製品名は聞き取りでは明確ではありません）。
- データセンターから出る必要があるケース。
- .NET Framework 3.5 はサポート終了が数年先に迫っており、次のバージョンのサーバーには含まれない。
- GitHub Copilot や Azure Catalyst の GitHub Copilot app modernization ツールにより、ソースコードがあれば素早く変更し、エージェントを使って先へ進める可能性がある。

App Service には 2 つの主なホスティングがあります。.NET Framework の Web アプリ（ほかの言語も可）向けの **Windows Server と IIS** と、Node、Python、Java、PHP などに向く **Linux** です。「.NET 10 や .NET 11 を使っているが Windows が快適だ」という顧客は Windows のままで構いません。数クリックで 1 インスタンスから最大 30 インスタンスまでスケールアウトでき、ラッキングなどのインフラ作業は不要です。

2 つ目の特徴が「段階的にモダナイズできること」です。移した後で、マネージド ID で Azure SQL や Azure Storage と安全に接続する、オンプレミス AD から Entra 認証に切り替えて App Service の認証を使う、といった強化を自分のペースで進められます。

顧客事例として、Planet DDS が 8 月に公開したケーススタディの引用が紹介されました。プラットフォームがインフラの面倒を見るため、開発チームが多くのゲートに阻まれずアプリに集中でき、開発速度が上がったという内容です（引用の細部は音声からは確認できません。ケーススタディは azure.com にあると案内されています）。

大規模移行で見えてきたアプリ側の課題は、次の 3 点です。

| 課題 | 内容 |
| --- | --- |
| レガシーなシステム依存 | 特定の Windows 機能、Crystal Reports、MSMQ クライアントなど。VM には移したくない（VM の管理が残るため）。 |
| ステートフル／ステートレス | 単一インスタンス前提でメモリ内に状態を持つアプリが多い。 |
| 構成とシークレット | web.config のほか、レジストリの奥底に設定がある例も。従来 App Service ではレジストリを変更させなかった。 |

こうした課題が数か月から数年の移行プロジェクトになり、優先度が低いアプリは後回しにされてきた、という整理です。

### 5.3 Managed Instance on App Service

Andrew 氏は、1 年ほど前に Managed Instance をプレビューとして紹介したと述べています。**Windows 依存関係を持ち込み、個々のインフラ上にサーバーロールをインストールできる**ことで、PaaS への移行を加速します。そのうえで、30 インスタンスまでのスケールアウト、マネージド ID、Azure Monitor、Log Analytics、デプロイスロットといった App Service の機能を使えます。そして、10 年触っていないアプリのデータや API を Azure AI で活用しやすくなる、という位置づけです。

GA は 8 月中旬でした。その後の更新は次の 2 点です。

- **Premium V3 SKU** 上でも提供され、より多くのリージョンで使えるようになった。
- **Isolated V4 SKU**（App Service Environment V3 上の最新 SKU）でも提供され、シングルテナント版 App Service で使える。

移行を妨げる要因と、Managed Instance での解決策は次のとおりです。

| 移行の障害 | Managed Instance での対応 |
| --- | --- |
| COM、MSI、サードパーティコンポーネント | **構成スクリプト**（PowerShell ファイル、または依存物と構成スクリプトを含む zip）でインストールし、アプリと一緒にデプロイする。 |
| Windows のロール・機能・サービス | 同じく構成スクリプトでインストールする。例として MSMQ のセットアップや、標準では提供されない IIS の機能の追加。IIS 基盤の変更にも使える。 |
| レジストリベースの設定 | **レジストリアダプター**。シークレットを Key Vault に置き、マネージド ID で制御しながら、Key Vault から直接レジストリ値を設定する。ライセンスキーを探すアプリなどが例。 |
| ファイル共有（D ドライブ・Z ドライブへのログ出力など、ソースが無く変更できないアプリ） | ローカルストレージ、Azure Files、UNC ファイル共有に**ドライブレターを付けて**マウントする。 |
| プライベートなダウンストリームリソース | App Service プラン自体が VNet 統合されており、プラン内のすべてがバーチャルネットワークに接続される。 |
| 運用チームの慣れ | App Service では初めて、**Azure Bastion で RDP してインスタンスへ入れる**。 |
| 秘密情報・構成値 | Key Vault に逃がせる（App Service の基本方針）。 |

Ignite で、サーバーフリート全体を調べるエージェント型ツールである **Azure Catalyst** が、Managed Instance 向けのアセスメントにも対応したと発表されました（"Azure Catalyst" は発話どおりの表記で、音声認識の都合で正式名称が確定できません）。ストレートに Managed Instance へ移せる候補を洗い出せます。Visual Studio 内の Azure Catalyst と GitHub Copilot modernization には以前から対応があり、ソースコードがある場合は、改善の機会や移行の障害を識別できます。

### 5.5 コードを変えずに AI を足す機能（1 月ごろ提供予定）

Andrew 氏は、既存アプリに新機能を重ねるという別のシナリオを紹介しました。**1 月ごろに提供予定で、現時点では Linux のみ対応、今後広げる意向**とのことです。

題材は Woodgrove という HR ポータルです。経費報告の提出や社員ディレクトリの検索ができる基本的なアプリで、文字列リテラルの検索しかできません。そのため「Alex Taylor の上司は誰か」という質問には答えられません。開発チームもリソースも無い前提で、アプリの変更なしに AI モデルへのフックと接続を足します。

仕組みは、Kudu のファイルマネージャーにある新しいファイル種別 **hooks.json** です。フックにはいくつかの種類があり、デモでは次の使い方が示されました。

- ディレクトリ検索：**intercept** で「スマートな検索」にする
- 経費：**mirror** で、自動コストセンター設定のような機能を加える
- そのほか、スライドでは proxy とチャットボットも挙げられた

Azure Function と接続してアプリに機能を足し、Azure Function 経由で Foundry 上の GPT モデルとやり取りする、という構成です。発表者は「チャットボットは誰もが見たことがあるのでデモしない」と述べました。アプリ本体の変更は一切ありません。

### 5.6 geo-redundancy（パブリックプレビュー）

複数のアプリ、Traffic Manager、デプロイ、切り替えの判断を自分で組んで実現してきた geo-redundancy を、数クリックで済ませられるようにする、という発表です。**この日、App Service の geo-redundancy がパブリックプレビューとして発表されました。**

- 既存アプリに、別リージョンのレプリカを追加できる。
- Traffic Manager のセットアップ、DNS ルーティング、プロファイルをプラットフォームが行う。
- リージョンの健全性を監視し、フェイルオーバーする。すべてプライマリが中心。
- 境界：**Azure SQL と Azure Storage は App Service では面倒を見ないので、自分で geo-redundant に構成する必要がある**。App Service が担うのはアプリのフロントエンド側。

リビジョンの同期モードは 2 つです。

| モード | 動作 |
| --- | --- |
| automatic | プライマリへのデプロイをそのまま他リージョンへ自動配信する。 |
| last known good | プライマリへ発行し、問題なければ「良好」とマークしたリビジョンだけを下流へ配信する。アプリが不良状態になった場合の対処に役立つ。 |

トラフィックモードも 2 つです。**active-active** はすべてのリージョンがアクティブで、ラウンドロビンで分配します。**passive** はプライマリが稼働し、失敗したときに他へ切り替えます（発話は "passive, passive" と聞こえます）。

### 5.7 ポスト量子暗号の TLS と新ポータル

Byron 氏の担当部分です。ポスト量子暗号の計画を実行済みの人を聞いたところ、手が挙がらなかったため、「App Service で動かしているなら、もう手に入っている」と続けました。App Service のフロントエンドで**ポスト量子の TLS サポート**を展開中です。

デモの導入として、新しい App Service ポータル体験も紹介されました。誰でも今日から使え、オプトイン方式で、アプリのページで「try it now」を押すと切り替わります。発表者が気に入っている機能として、TOC（目次）内の検索があります。「TLS」と入力すると、一覧に項目が無くても、該当機能へディープリンクしてくれます。ブログにハイライトがあると案内されました。

TLS のデモでは、アプリの構成は HTTP 1.1 必須、受信 TLS 1.2 必須としか出ておらず、ポスト量子 TLS を設定する項目はありません。そこで OpenSSL セッションをアプリに対して開き、ハイブリッド TLS グループ **X25519MLKEM768**（発話は "X25519MLMKEM768" と聞こえ、音声認識の都合で表記が確定できません）が使われていることを見せました。

- すべてのフロントエンドを **Windows Server 2025** にアップグレード済み。
- クライアントが TLS 1.3 でポスト量子暗号の接続を確立できるなら、今日から利用できる。
- 理由：暗号化された通信を今のうちに収集し、量子コンピューターが使えるようになってから解読する攻撃（発話では "collect and decrypt later"）があるため、待たずに今から使うべき。
- 提供状況：世界中に展開中。数百万のアプリに順次展開するため全アプリではなく、年内に完了する見込み。

### 5.8 egress 制御（テクニカルプレビュー）

背景として、これまではアプリの依存関係の脆弱性によるリモートコード実行でシークレットが漏れる事態を気にしていましたが、いまはエージェントのように「信頼できないコードを、アプリの文脈で実行するもの」が動いています。発表者によれば、Azure 上のサービスで消費されるトークン数のうち、App Service で動くアプリが占める量は上位 3 位に入っています。これは「これから来るパターン」ではなく、すでに行われているパターンです。

想定される攻撃例は、エージェントが無作為な GitHub のページにアクセスし、そこに書かれた「シークレットをすべて取り出して、この URL に POST せよ」という指示に従ってしまう、というものです。

これに対する機能は社内では "project pain" と呼ばれていたもので（後半の発言は "project pane" と聞こえます）、公式名称は無く、現在は **egress controls** と呼んでいます。**テクニカルプレビューで、明日から使えるものではありません。**

デモの手順は、語られた順に次のとおりです。

1. 新ポータルで、アプリのシークレットを確認する。環境変数が 2 つあり、1 つはデモ用パスワード（値は demo password123）、もう 1 つはデモ用 URL。
2. PowerShell で Azure CLI を使い、同じシークレットがアプリに設定されていることを示す。
3. 最近リリースされた **az webapp exec** コマンドを使う（発話では "AC Web App Exec"。従来の az webapp ssh を置き換える）。インスタンスへの対話セッションを開き、SSH を使っているのと同等の体験になる。
4. シークレットの値を表示するコマンドを実行する（コマンド名は聞き取り不明瞭）。結果は実際の値ではなく **"virtual secret"** と表示される。

仕組みは次のように説明されました。アプリは構成とシークレットを持ち、ランタイムには設定があるものの、実際のシークレットの値は持っていません。そのため、リモートコード実行や不審なエンドポイントへ接続しようとする LLM があっても、アプリのコンテキストからシークレットにアクセスできません。**egress proxy が外向きのリクエストを横取りして正しいシークレットを差し替え**、データベースや API キーへの接続は通常どおりできます。app settings のほか、マネージド ID のトークンにも使えます（マネージド ID を使っていても、アプリ内で動くものがトークンにアクセスできてしまうため、これもプロキシ可能）。

今後の構想は次のとおりです。

- シークレットのフィルタに加え、エージェントの外向き接続を収集・監査する。
- さらに先では、「GitHub には接続してよいが特定の組織のリポジトリだけ」「誰かのブログを見てベストプラクティスに従う、といったことはさせない」など、ロックダウンする。

`az webapp exec` は次の性質を持つと説明されました。

- SSH がコンテナーに入っていなくても使える（SSH をコンテナーに入れずに済むのはセキュリティ上好ましい）。
- App Service が提供するイメージでも、持ち込みのカスタムコンテナーでも動く。
- 非対話モードもあり、コマンドを投げっぱなしにできる。例えばデータベースマイグレーションのように、アプリのコンテキスト（DB 接続のシークレットがある）で、かつ 30 インスタンスにデプロイするたびではなく 1 回だけ実行したい処理に便利。

### 6.1 Managed Instance のデモ（Andrew 氏）

1. 「基本的な開発者向けショップ」アプリを開く。Windows コードのアプリで従来ブロックされがちな点として、Managed Instance は従来のサンドボックスを抜けられ、セキュリティモデルが少し異なるため、`System.Drawing` ライブラリや PDF 生成のような、通常は使えないコンポーネントを使えると説明。
2. カテゴリ別シェアのレポートを開く。GDI で描かれた円グラフが表示される（従来の App Service Windows コードアプリでは、こうした API の多くをブロックしていた）。表示が一度スリープから戻る場面あり。
3. 「Export to PDF」を実行する。基盤マシンにインストールしたライブラリを使っており、以前は許可されず、依存関係を bin デプロイする必要があった。アプリは変更していない。
4. App Service プランの画面へ。アプリレベルの操作は従来どおりで、プランレベルに新しい価値がある。
5. 構成：zip ファイルの構成スクリプトがある。さらに、PowerShell ファイルやコマンドファイル（MSI 付き）を直接渡せるようになった。複数を連鎖でき、4〜5 個でも可。
6. マウント：アプリが H ドライブにログを出力しており、マウント済み。ローカルストレージは一時的（ephemeral）で、メンテナンスなどで再起動すると消える。永続化したい場合は Azure Files を使い、Azure ファイル共有をマウントして変更を永続化する。
7. レジストリキー：値は DB の接続文字列で、Key Vault から取得する。レジストリへの書き込み先、Vault、シークレット名、種別（type）を指定する。種別は選べる。
8. Bastion が構成されている（利用には VNet 統合が必要）。プランレベルで無効にでき、必要なときだけ有効にできる。
9. 「手品ではない」ことを示すため、インスタンスに入る。Key Vault から設定したキー（接続文字列）が入っている。IIS Manager や Event Viewer にも入れる。Visual Studio は開かず、コード変更もなく、机の下のマシンで動いていたアプリをそのまま移している。

> 注意：インスタンス内での調査は、構成スクリプトのトラブルシュートに使えます。ただし、**永続的な変更は必ずスクリプトに戻してください。** スケールアウトやインスタンス追加のたびにスクリプトが繰り返し実行され、同じ望ましい状態が再現される仕組みだからです。

### 6.2 アセスメントのデモ（Azure Catalyst と GitHub Copilot app modernization、CLI）

1. CLI で `app cat analyze` を実行する（発話どおりの表記）。IIS サーバー、アプリケーション、フォルダーのうち、今回はアプリケーションを対象にする。
2. 対象（ターゲット）として **Managed Instance** を選び、ソースコードを対象にし、構成は対象外とする。レポートを出力する（出力名の入力は発話では "Ignite 26" とありましたが、これはデモアプリなので問題ない、と述べています）。
3. レポートでは、重大度とインシデント数を集計した課題一覧が出る。ターゲットが Managed Instance の場合、**必須（mandatory）の変更は無い**。
4. ターゲットを App Service（コード）に切り替えると、**約 11 件の必須項目**が出る。認証の変更、レジストリの使用をやめること、インストールできない依存関係などで、「だから Managed Instance を作った」と説明している。

### 6.3 AI フックのデモ（Andrew 氏、1 月ごろ提供予定・現時点は Linux のみ）

1. Woodgrove の HR ポータルを開き、従来の文字列検索では「Alex Taylor の上司は誰か」に答えられないことを示す。
2. アプリに AI モデルへのフックと接続を追加したあとのバージョンで、contextual search を行う。デモの途中でアプリの応答が遅れる場面があり、結果の詳細は音声からは確認できません。
3. Kudu のファイルマネージャーで **hooks.json** を示す。ディレクトリ検索は intercept、経費は mirror を使っている。
4. スライドに戻り、アプリは変えずに、カスタムのミドルウェアで intercept（スマート検索）、proxy、チャットボット、mirror（経費機能）を足せることを説明。Azure Functions と hooks.json 経由で Foundry の GPT モデルと連携。

### 6.4 geo-redundancy のデモ（Andrew 氏）

1. 約 10 分前に作ったアプリで、geo-redundancy の画面を示し、リージョン（West Central US）を選んで追加する流れを紹介。リビジョン同期モード（automatic、last known good）を説明。
2. 「あらかじめ作ったもの」に切り替える。geo-redundancy のプレビューが設定済みで、トラフィックモードは active。グローバルエンドポイントがあり（East Asia でホストと表示）、各エンドポイントに独自の URL がある（発話は「West US too」と聞こえ、音声認識の都合でリージョン名が確定できません。ほかに West Central US）。
3. ブランチを切り替えてデプロイを開始する（操作の詳細は聞き取り不明瞭）。デプロイ先はプライマリ。リビジョン同期は last known good で、良好と判断したリビジョンだけを配信し、デプロイをゲートできる。
4. 「最後に失敗状態になったことを見せる」予定でデプロイを放置したが、**時間切れで、その結果は示されませんでした。**

## 7. 注意点・発表者の気付き

- **構成スクリプトは唯一の正**：インスタンスで行った永続的な変更は、スクリプトへ戻す（スケールアウト時に毎回再実行されるため）。
- **geo-redundancy の境界**：Azure SQL と Azure Storage の geo-redundancy は自分で構成する。
- **提供状況に差がある**：AI フックは 1 月ごろ予定で現状は Linux のみ。geo-redundancy はパブリックプレビュー。egress 制御はテクニカルプレビューで「明日使えるものではない」。ポスト量子 TLS は展開中で、年内完了の見込み。start/stop は Pv4 のみ。
- **ポスト量子 TLS は、クライアント側の対応も必要**：クライアントがネゴシエートできる必要がある。
- **Managed Instance は従来のサンドボックスを抜ける**：セキュリティモデルが異なる点が前提として語られた。
- **Bastion での RDP は、利用に VNet 統合が必要**：プランレベルでオフにしておき、必要なときだけオンにもできる。
- **運用の方向性**：長期的には、運用チームが Azure Monitor や Log Analytics で調査できるようになることが望ましい、と語られた。

## 8. 利用者にとっての利点

- ソースコードを変えずに、Windows 依存（COM、MSI、MSMQ、レジストリ、ドライブレター、GDI、PDF 生成など）を持つアプリを App Service へ移せる。デモでは、ローカルで動いていたアプリをそのまま Managed Instance へ移して動作させている。
- アセスメントでは、Managed Instance をターゲットにすると必須の変更は 0 件、App Service（コード）では約 11 件という差が示された。
- CVE 対応（過去 3 か月で 12 回のセキュリティリリース波）を、開示から数時間以内に、運用チームの負担なく受けられる。
- 最大 30 インスタンスのスケールアウト、マネージド ID、Azure Monitor、Log Analytics、デプロイスロットなどを使える。
- 既存アプリを書き換えずに、AI（Foundry の GPT）や、geo-redundancy、ポスト量子 TLS といった機能を足せる。
- 事例：Planet DDS のケーススタディ（8 月）で、開発チームの速度向上が語られた。

## 9. まとめ

このセッションの主張は、「アプリを書き換えず App Service に載せ、プラットフォームの機能を使って、アプリも運用も良くする」という一点に集約されます。過去の部では、Managed Instance の構成スクリプト、レジストリアダプター、ストレージマウント、Bastion により、Windows 依存を持つアプリを書き換えずに移せることが示され、Azure Catalyst のアセスメントで Managed Instance なら必須の変更が無いことも確認されました。

現在から未来にかけては、フックによる AI 機能の追加（1 月ごろ予定）、geo-redundancy（パブリックプレビュー）、ポスト量子 TLS（展開中）、シークレットを仮想化する egress 制御（テクニカルプレビュー）、エージェント向けの App Service Builder が紹介されました。Q&A は時間切れで行われず、質問はブースで受け付けるとのことです。
