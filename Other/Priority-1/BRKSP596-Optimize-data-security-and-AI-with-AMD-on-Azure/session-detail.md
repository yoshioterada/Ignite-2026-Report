### 5.1 AMD と Azure：10 年の協業と VM ラインナップ（Steve 氏）

Steve 氏は、Microsoft との協業が約 10 年に及び、最初の EPYC「Naples」が Microsoft のインフラに入ったときから続いていると説明しています。また、Microsoft は次の「初」を重ねてきたとのことです。

- EPYC を採用してクラウド環境に入れた最初の企業
- ハイパフォーマンスコンピューティングで最初
- 3D V-Cache を CPU の高速化に使った最初
- AMD の GPU「Instinct MI300X」を使った最初

Azure には **60 種類を超える VM タイプ**があります。汎用、メモリ最適化、ストレージ、Confidential Computing などです。VM 名のアルファベットの並びで重要なのは「A」で、A の付く VM は AMD の技術を使っています。V5 → V6 → V7、そして今日発表された V8 と数字が上がるにつれて、EPYC の次世代の技術になります。

汎用 VM の例では、V5 を使っている場合、V7（Turin。現在、大量に提供されている GA の世代）では **80% の性能向上**になり、インフラの近代化と TCO の改善が見込めると説明しています。V8 がこのグラフのどこに来るかも楽しみだと述べています。

**展開のペース。** スライドには、OEM が提供するプラットフォーム数の世代ごとの増加（世代が上がるごとに 100 以上の増加）と、利用できる VM の累積数が示されました。Turin は、近年で最も速く立ち上がった製品です（グラフの注釈は「V6 が V7 の VM で利用できる」と聞こえますが、発話が不明瞭で世代の対応は確定できません）。Venice（V8）はそれより速く立ち上がると見込んでいます。現時点で、さまざまな製品タイプにわたり**約 1,700 の VM** があります。

Azure では、Turin は GA 時点で 11 リージョンでしたが、現在は **47 を超えるリージョン**で提供されています（「増え続けている」とのこと）。さらに、Microsoft 自身も、Microsoft 365 から Copilot まで、ほぼすべての自社サービス（first party）で使っていると述べています。

### 5.2 Horizon DB と AMD（Charles 氏）

Charles 氏は、今朝ニューヨークで新しいフラッグシップの Postgres サービスを発表したと述べています（トランスクリプトでは「Azure Crys」と聞こえる箇所があり、サービス名の表記は音声認識の都合で確定できません。以降、トランスクリプトで繰り返し使われている「Horizon DB」と書きます）。これは多くの AMD コンピューティングの上で動いています。

**スケールの必要性。** データベースで最も重要なのは安全性（セキュアなネットワーク、ID、暗号化など）ですが、スケールも重要です。AI アプリケーションが embedding を使った類似検索などを使うようになり、データ量が非常に大きく、CPU やストレージを大量に使い、従来なかった負荷がデータベースにかかっていると説明しています。

**GA での仕様と性能。**

| 項目 | 内容 |
| ---- | ---- |
| Postgres ワークロードのサイズ | 最大 128 TB |
| スケールアウト | 共有ストレージ上で最大 3,072 vcores |
| 性能 | キーノートでも触れたとおり、ゾーンをまたいで高可用性の Postgres をオープンソースで自前構築した場合に比べ、最大 8 倍高速 |
| コミットレイテンシ | ゾーンをまたいで 1 ミリ秒未満 |
| フェイルオーバー | ゾーンをまたいで一貫性を保ち、5 秒未満 |

**アーキテクチャ。** 上位は、1 つの読み書き可能なノード（read-write）と複数の読み取りレプリカからなるコンピュート層です。ストレージ側は、ログサーバーとストレージに分離（disaggregated）されたシステムで、自動的にゾーン耐性を持ち、すべてが Azure Storage に支えられています。コンピュート層は独立してスケールでき、ワークロードに応じてレプリカを増減したり、ノードのサイズを拡大・縮小したりできます。

従来のデータベースは、クエリ実行もストレージ管理も 1 つのノードで動きます。コンピュートとストレージの分離は以前からありましたが、それは「上位層で全コンピュートが動き、下位層にデータがある」という意味でした。Horizon DB では、さらに**ストレージを管理するプロセスと、コンピュートのプロセスを分離**します。ストレージ管理側（データ、write-ahead log、チェックポイントなど）を下位のストレージ層に押し下げ、そこでも AMD の機材が動いています。この結果、上位層の CPU はクエリ実行に専念でき、Postgres のアプリケーションを 2 つの層に分割して、両方の CPU を使い切ることで、スループットとストレージ性能の両方を最大化できる、という説明です。

**ベンチマーク。** 業界標準のベンチマーク HammerDB を使い、NOPM（1 分あたりの注文数）で比較しています。

| 構成 | 結果 |
| ---- | ---- |
| Postgres を自前で構築（ゾーンをまたぐ高可用性） | おおよそ 5 万 2,000 前後 |
| Horizon DB | 40 万超 |

Charles 氏は、これは上記のアーキテクチャと、Horizon が行う他のいくつかの工夫の組み合わせで実現していると述べています。ゾーン耐性のある高可用性が組み込まれており、データをゾーンをまたいで永続化するための追加の処理でも性能を犠牲にしない、と説明しています。

**世代ごとの性能。** Steve 氏は、このワークロードでは、Turin ベースのインスタンスを使うと、**ドルあたりの性能が 54% 向上**すると補足しています。Venice での結果も楽しみだと話しています。

### 5.3 Confidential Computing（Vikas 氏）

**背景。** Steve 氏の紹介のあと、生成 AI は Confidential Computing の火に油を注いでいるようなものだ、という話が始まります。脅威が増し続けているため、当初からハードウェアの各ベンダー（AMD を含む）に、Confidential Computing をどこでも使える形にするというビジョンを話してきた、と説明されています。この少しあとから、AMD への謝意が語られるところまでは、セッション中に流れた動画の音声が含まれているとみられ、話者は確定できません（動画には、Azure CTO で deputy CISO の Mark Russinovich 氏が登場しました）。動画のあとで、Vikas 氏とみられる登壇者が、同氏をこのプロジェクトのエグゼクティブスポンサーであり、実現を可能にしたビジョンを持つ人物だと紹介しています。

**データの 3 つの状態。**

| 状態 | 保護の状況 |
| ---- | ---- |
| at rest（保存時） | 暗号化で解決済み。データセンターでハードディスクを持ち出しても、データにはアクセスできない |
| in transit（転送時） | 暗号化で解決済み。エンドポイント間の通信を盗み見られない |
| in use（使用中） | メモリ上にあり、実際に処理されているとき。業界はこの保護をまだ十分に解決していない。ここを Azure Confidential Computing が保護する |

3 つを組み合わせると、エンドツーエンドのデータ保護になります。Vikas 氏はこのスライドの重要な点として 2 つを挙げています。1 つは、使用中（メモリ上）のデータを保護できること。もう 1 つは、データが作成されてから破棄されるまで、**自分が持つ鍵でエンドツーエンドに保護**できることです。これは AI 時代の、セキュリティに敏感なワークロード（健康記録、税務データなど、公開インターネット上にないデータ）で特に力を発揮すると述べています。

**顧客が信頼する範囲（動画の音声とみられる部分）。** Confidential Computing により、顧客が信頼しなければならない対象は「自分自身」まで減ります（VM を書いているのは自分だからです）。最初の技術は secure encrypted virtualization で、その後 secure nested paging に拡張して整合性の保護が加わった、と説明しています（略称の表記は音声認識の都合で確定できません）。attestation（構成の証明）は AMD EPYC プロセッサから来ており、ハードウェアに根ざし、暗号化されているため、顧客は安心できます。Microsoft が加えているのは、パブリッククラウドの顧客要件に合う機能の優先順位付けと、その上で動くサービス、そして自社サービスでの利用です。

**自社での利用（同上）。** Entra の認証トークンに署名するトークン署名サービスを、Confidential Virtual Machine の中で動かし、署名を行うコードとシークレットを保護しています（トランスクリプトでは主語が聞き取りにくい箇所です）。設計では、実用的でデプロイできること、アプリケーションの所有者がコードを書き換えたり再設計したりしなくてよいこと、プラットフォームの所有者がプラットフォームの管理方法を全面的に作り直さなくてよいこと、が重要な考慮点だったと説明しています。さらに、AMD と協力して Confidential VM をより安全に、より高性能にするための共同設計を続けています。

Microsoft では、最もセキュリティに敏感なワークロードを順次 Confidential Computing に移行しており、TCB サービスや HBT サービス（trusted computing base サービス、high value target サービス）が対象です。最も重要なサービスの 1 つである **Entra ID は、世界中のすべてのリージョンと可用性ゾーンで、100% Confidential Computing 上で動いています**。

続けて、障壁がなくなりつつあり、「Confidential Computing ではなく、ただの Computing」と言える日が見えてきたこと、AMD との共同設計への謝意が語られています。

**AI における 3 つのユースケース。**

1. **モデルの重み**：モデルを開発し、ファインチューニングや学習をした側は、重みを保護したい。
2. **プロンプト**：企業やエンドユーザーは、プロンプトを保護したい。
3. **企業データ**：RAG のシナリオでも、推論や学習の間に企業データを保護したい。

AI の価値は、公開インターネットを超えて自分のデータを与えたときに生まれるため、データがエンドツーエンドで保護されるという確信が得られる、と述べています。

**プレビュー発表：Turin ベースの Confidential VM。** 今日、V7 の Turin ベースの Confidential VM のプレビューを発表しました。汎用とメモリ最適化の **DCasv7 と ECasv7**（トランスクリプトでは「DCAS V7、ECAS V7」と聞こえます）です。

| 項目 | 内容 |
| ---- | ---- |
| 比較対象 | 同等の 1 つ前の世代の Confidential VM |
| 8 vCPU | メモリ帯域幅が最大 45% 向上、メモリレイテンシが 64% 低下 |
| 32 vCPU（負荷時） | 帯域幅が 43% 向上、レイテンシが 71% 低下（Windows CVM） |

さらに詳細な性能データのブログが、今日か明日に公開予定とのことです。ほかの特徴として、これらは **secure AVIC を備えた最初の Confidential VM** で、Accelerated Networking、Accelerated Storage、Azure Boost オフロードカードとの統合があります。スライドにプレビュー用のリンクと QR コードがあり、サインアップすると、受け入れを始める段階で試せる、と案内しています（受け入れ範囲の言い方は聞き取りにくい箇所です）。前の世代がグローバルに展開されたように、これらもグローバルに展開される予定だと述べています。

### 5.4 AI インフラと VM の選び方（Stefanie 氏）

Stefanie 氏は、自身の担当は AI インフラ全体ではなく、汎用コンピュートだと断っています。

**AI インフラの考え方。** AI の性能は、コンピュート、メモリ、ネットワーク、ストレージ、ソフトウェアがどれだけ効果的に連携するかで決まる、システムレベルの成果です。Azure はスタックの各層で革新を進めています。

- **シリコン**：AMD の最新の CPU と GPU を含め、選択肢を広げている
- **システムアーキテクチャ**：メモリを増やした新しい提供形態と、インフラ処理をオフロードする Azure Boost
- **ファブリックとデータ**：システムが分散化する中で、AI アプリケーションがデータにアクセスし、移動する速度を上げるネットワークとストレージの改善
- **運用**：配置、スケーリング、可観測性による効率の向上

目標は、エンドツーエンドの性能とコスト効率の向上です。

**どこから始めるか。** ワークロードで起きそうなボトルネックから始め、テストで性能を検証することを勧めています。学習と大規模モデルの推論は主にアクセラレーターに依存しますが、汎用 VM が重要な役割を果たす領域が 4 つあります。

| 領域 | 汎用 VM が向く理由 |
| ---- | ---- |
| 小規模モデル／バッチ推論 | モデルが小さい場合や需要が変動する場合は、CPU のほうがコスト効率が良いことがある。スループットが上がると、アクセラレーターのほうが魅力的になる |
| RAG | モデルの外側で、データの取り込み、検索、フィルタリング、再ランキングなど多くの処理が発生する |
| エージェント型 AI | エージェントがツールを呼び、データベースにアクセスし、コードを実行するため、インフラへの負荷が突発的（bursty）になる |
| AI サービス | API やアプリケーションロジック |

Vikas 氏の話にあったとおり、これらすべてのワークロードで、使用中のデータにハードウェアに裏付けられた保護を与える Confidential Computing も考慮に値する、としています。

**LASV5 と LAOSV5（第 5 世代 AMD EPYC、GA）。** AI ワークロードで大量のデータを移動、ステージング、処理するために高速なローカルストレージが必要な場合の VM です。モデルの周囲のデータパスを高速化し、特にストレージ性能がエンドツーエンドの性能に直結する場面に向きます。

| VM | ローカルストレージ | 読み取り IOPS | 向く用途 |
| ---- | ---- | ---- | ---- |
| LASV5 | 最大 30.7 TB | 最大 960 万 | ストレージのキャッシュ、検索エンジン、分散データベース、データウェアハウス、ビッグデータ分析。AI パイプラインでは、ドキュメント処理、embedding 生成、ベクトルインデックス、検索キャッシュ、一時的なデータのステージング |
| LAOSV5 | 最大 138 TB | 最大 2,070 万 | 大規模な AI データのステージング、前処理、インデックス作成、分散データプラットフォーム、キャッシュクラスター。データを CPU の近くに置いて、リモートストレージへの繰り返しの読み取りを減らす用途 |

どちらも第 5 世代 AMD EPYC を使い、最大 200 Gbps のネットワーク帯域幅があります。CPU 性能、高速ネットワーク、高性能なローカル NVMe ストレージの組み合わせで、データ集約型の AI パイプラインを効率よく動かし続けられるという説明です。**どちらも現在 GA** です。

**DHASV8 と EHASV8（第 6 世代 AMD EPYC「Venice」、プレビュー）。** 今回発表された新しい VM ファミリーです。AI パイプラインがますます分散・並行化しており、1 つのアプリケーションが、多数のエージェント、ツール呼び出し、検索リクエスト、データ変換、モデルエンドポイントを同時に調整することがあるため、並列度の高い段階向けに開発したと説明しています。

| 項目 | 内容 |
| ---- | ---- |
| vCPU | 最大 480 vCPU。より多くのエージェント、ツールワーカー、パイプライン処理を 1 つの VM で同時に動かせる |
| メモリ | DHASV8 は vCPU あたり最大 4 GB、EHASV8 は vCPU あたり最大 8 GB。最大サイズでは最大 3.8 TiB（セッション状態、大きなキャッシュ、インメモリインデックス、検索データに向く） |
| 前世代（DA / EASV7）との比較 | 最大サイズで、リモートストレージ IOPS とネットワーク帯域幅が最大 2 倍 |
| 互換性 | x86 ベースのため、プロセッサアーキテクチャを変えずに、既存の AI サービス、フレームワーク、ソフトウェア依存関係を引き継げる |

向いているワークロードの候補として、エージェントのサンドボックス群、オーケストレーションとツール実行、RAG の取り込み層と検索層、CPU での前処理と ETL、大規模な Web と API のキャッシュ層を挙げています。プレビューには、スライドの QR コードからブログとサインアップのリンクにアクセスできます。

**VM シリーズ選びの簡易ガイド（CPU 中心の AI ワークロード向け）。**

| ワークロード | 出発点 |
| ---- | ---- |
| バランスの取れたスケールアウト | 汎用の DA ファミリー（アプリケーションサービス、エージェントオーケストレーション、ツール実行、バランスの取れた RAG パイプライン） |
| 計算集約 | FAS V7（メモリとコアの比が 3 種類。小規模モデルやバッチ推論、パース、変換、前処理など、コア当たりの計算性能が最高） |
| メモリ集約 | EA シリーズ（大きなキャッシュ、セッション状態、インメモリインデックス、メモリを多く使う検索） |
| ストレージ集約 | LASV5、LAOSV5（RAG の取り込み、インデックス構築、データステージング、キャッシュ、ローカルストレージがボトルネックの検索パイプライン） |
| Confidential Computing が必要 | 汎用とメモリ集約の両カテゴリに選択肢がある |

Stefanie 氏は、これはあくまで出発点であり、制約が解消され要件を満たしていることを確認するためにテストが常に推奨される、と話しています。データ量、モデルサイズ、並行性、アーキテクチャ要件によっても変わるとのことです。

## 7. 注意点・発表者の気付き

- **VM の選定は、ボトルネックの把握と検証から。** ワークロードの制約を見極め、テストで性能を確認します。データ量、モデルサイズ、並行性、アーキテクチャ要件で結果は変わります。
- **汎用 VM のほうがコスト効率が良いのは、小規模モデルや需要が変動する場合。** スループットが上がると、アクセラレーターのほうが魅力的になる可能性があります。
- **プレビューの範囲。** DCasv7 / ECasv7（Confidential VM）と DHASV8 / EHASV8 はプレビューです。Confidential VM は、サインアップした顧客から受け入れる方式だと案内されています。LASV5 と LAOSV5 は GA です。
- Confidential Computing の設計では、アプリの書き換えやプラットフォームの再設計が不要なことが、実用性の面で重要な考慮点だったと説明されています。
- 発表では、料金や、各 VM が提供されるリージョンの詳細には触れていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

| 分野 | 利点 |
| ---- | ---- |
| コスト・TCO | 最新世代の AMD VM への移行でコスト最適化と TCO 改善。V5 から V7 で 80% の性能向上（汎用 VM の例） |
| データベース | Horizon DB は、自前構築の高可用性 Postgres より最大 8 倍高速（HammerDB で、約 5 万 2,000 vs 40 万超）。Turin ベースで、ドルあたり性能 54% 向上 |
| セキュリティ | 使用中のデータを含めて、ユーザーが持つ鍵でエンドツーエンドに保護。モデルの重み、プロンプト、RAG の企業データの保護にも関係 |
| Confidential VM の性能 | 前世代比で、メモリ帯域幅が最大 45% 向上、メモリレイテンシが 64% 低下（8 vCPU）など |
| AI パイプライン | LASV5 / LAOSV5 で高速なローカルストレージ。DHASV8 / EHASV8 で最大 480 vCPU と大容量メモリ。x86 のため既存の AI 資産を移行しやすい |

> 補足：数値はすべて登壇者が口頭またはスライドで示したもので、測定条件の詳細は発表では説明されていません。

## 9. まとめ

AMD と Microsoft は 10 年にわたって Azure のインフラを共同で進化させており、V5 から V8 へ世代が進むごとに、性能とコスト効率が向上しています。データベースでは、Horizon DB がコンピュートとストレージのプロセスを分離する設計で、HammerDB で約 8 倍の性能を示しました。セキュリティでは、Turin ベースの Confidential VM（DCasv7 / ECasv7）がプレビューになり、Entra ID はすでに全リージョンで Confidential Computing 上で動いています。AI では、CPU 中心のワークロードに向けて LASV5 / LAOSV5（GA）と DHASV8 / EHASV8（プレビュー）が紹介され、ボトルネックに合わせて VM を選び、テストで確かめる進め方が示されました。
