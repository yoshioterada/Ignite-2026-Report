## 4. 発表者が伝えたいメッセージ

登壇者が繰り返し強調しているのは、**「無駄な作業と無駄な容量を徹底的になくすことが効率につながる」** という考え方です。

- 冷却では、GPU を必要以上に冷やさないようにする。
- ストレージでは、データを CPU やメモリを経由させずに GPU へ直接流す。
- AI モデルには、計算済みの KV キャッシュを再計算させず、Azure Storage から取り出させる。
- GPU 容量では、チーム間の割り当ての壁をなくして断片化を解消する（"eliminate fragmentation" と呼んでいます）。

もう 1 つの柱はセキュリティです。エージェントを「内部リスク（insider risk）」として扱うという考えのもと、ネットワークの出入りを制御する Agent Grid と、コンテキスト内のデータにラベルを付けて追跡する情報フロー制御を紹介しています。登壇者は、いまの「YOLO モード」でのエージェント利用は、1990 年代の人々のインターネットの使い方のように、将来は振り返られるだろうと述べています。

冒頭で挙げられた規模の数字は次のものです。登壇者は 2010 年から Azure にいるとしたうえで、**直近 18 か月でデプロイした容量が、Azure の最初の 15 年間の合計より多い**と述べています。

## 5. 発表内容の詳細

### 5.1 データセンターの冷却

**ゾーン別冷却（zonal cooling）。** 空冷ラックには、チラーで冷やした空気を使います。これに対し、液冷の GPU や Maia アクセラレーターは、はるかに高温の液体を流せます（液体は空気より効率よく熱を奪えるため）。空冷ラックと同じ温度まで冷やすと GPU を過冷却することになります。そこで最新のデータセンターでは、液冷用と空冷用の 2 つの放熱システムを分け、それぞれ異なる温度で冷やすゾーン別冷却を採用しています。

発表で語られた温度は次のとおりです。ただし、スライドを見ながらの説明で、音声だけでは温度の意味づけを完全には確定できません。

- 空冷側: 空調ユニット（air handling unit）に入る水は 20℃、または約 30℃ と語られ（聞き取りでは判別できません）、そこから約 30℃ の空気を送り出す。
- 液冷側: CDU（coolant distribution unit、冷却液分配装置）に入るのは 20〜40℃ の水で、GPU 向けの液体は 45℃ まで冷やす、と説明されています。

これだけで、データセンターの冷却コストを 10〜40% 削減でき、約 6 か月で元が取れると説明しています。Azure ではこうしたハイブリッドなデータセンターが標準になりつつあります。

**マイクロフルイディクス（microfluidics）冷却。** 現在の液冷では、cold plate（コールドプレート）にクーラントを通します。マイクロフルイディクス冷却は、**シリコンの真上に直接液体を流す**方式です。冷却層を積み重ねることもでき、マイクロピンフィンのヒートシンクが、シリコン上の流路を通る液体で熱を奪います。

- 登壇者が示したのは、Intel Ice Lake CPU の上部のヒートスプレッダー（蓋）を外し、チップ上に流路をエッチングしたものです。
- 流路は、Ice Lake プロセッサーの発熱を解析し、熱の多く出る場所に合わせた、生物の模様のような形をしています。
- 冷却能力は約 1 kW/平方センチメートルで、cold plate 方式の液冷より 20〜40% 効率が良いと説明しています。
- 数年来取り組んでいますが、まだ本番環境の主流にはなっていません。現在はパイロット運用で、性能と信頼性を分析している段階です。
- 現状は自社でエッチングしているため、部品の保証が無効になります。今後は、サプライヤーが工場で加工した状態で納品してもらう形を目指しています。

登壇者は、これをシリコン全般の冷却の未来だと確信していると述べています。

### 5.2 シリコン: Maia と AI による最適化

Maia については、「Maia 300」という名称で紹介されています（音声認識の都合で型番の表記が確定できません）。登壇者は、これを AI アクセラレーションの面で世界水準のチップだと述べ、このスライドではスケールアップ構成に絞って説明しています。

狙いは、1 兆パラメーター級のモデルを大きなドメインにまたがって推論できるようにすることです。こうしたモデルには、テキスト処理部分に画像認識モデルが付くなど、別々のアクセラレーターで動かす部分があり得ます。そのため、アクセラレーター間の低遅延・高帯域な接続と、容量の断片化を避けるために大きなドメインのどこにでも配置できる柔軟性が必要です。

Maia のスーパーポッドの構成は次のとおりです。

| 項目 | 数 |
| ---- | ---- |
| トレイあたりのアクセラレーター | 4 |
| ラックあたりのトレイ | 24 |
| スーパーポッドあたりのラック | 最大 128 |
| アクセラレーター間の遅延 | 5 マイクロ秒未満 |

**AI による最適化（mega fusion blocks）。** AI を使って Maia を最適化している例も紹介されています。モデルの配置の仕方も重要で、アクセラレーターをプログラムするものがカーネルです。大規模言語モデルの行列演算を個別に実行して結果をいちいち戻すのではなく、融合してアクセラレーター内で最後まで処理させたいと説明しています。この融合ブロックを mega fusion block と呼び、最適化に AI を使います。

- 48 時間という圧縮された時間枠で実施する。
- 14 の implementer（実装担当）が高速化案を実装し、14 の reviewer（レビュー担当）が検証する。
- 上位の analyst（分析担当）が新しいアイデアを出して executor に渡し、結果を受け取って次のアイデアを出す。
- 結果として 108 の実験を行い、うち 17 が従来の最良を上回り、**融合カーネルが従来より 30% 高速になった**。

登壇者は、このようなシリコンからソフトウェアまで一貫して取り組む力が、他社のアクセラレーターと競争するうえでの強みになると述べています。

### 5.3 ストレージ: RDMA over Azure Boost と DACS

#### RDMA と Azure Boost

RDMA（Remote Direct Memory Access）は TCP/IP スタックを迂回する技術です。従来のエンタープライズネットワークでは、データセンター内であっても、パケットがネットワークデバイスドライバー、TCP/IP スタックを通ってアプリケーションに届きます。Azure Boost（Azure のアクセラレーテッドオフロード）が RDMA をサポートすることで、2 つの仮想マシンが RDMA のプロトコルでメモリ同士を直接やり取りできます。VM 内のネットワークスタックとデバイスドライバーは完全に迂回されます。同一サーバー上でも、データセンター内の別サーバー間でも使えます。

> 補足：RDMA は、Azure Boost 対応のすべての VM タイプで、現在プレビューとして利用できると説明されています。

**Azure Storage への RDMA の拡張。** 通常の Azure Blob Storage は HTTP（レイヤー 7 の HTTP スタックを含むフルスタック）でアクセスします。これを RDMA に置き換えて、Azure Storage から VM のメモリ、さらに AI では GPU のメモリに直接データを引き込もうというものです。最新の GPU は GPU Direct（RDMA を、アクセラレーターを通して HBM に直接つなぐ仕組み）に対応しています。GPU に直接流すので、パケット処理で CPU を通らず、CPU 側のメモリ負荷も増えません。効果として語られたのは、1 秒あたりのトークン数の向上と、VM の CPU・メモリへの負荷の軽減です。スライドのグラフには **43 倍**の効果が示され、Azure Storage から VM へ移動するペイロードが大きいほど効果が大きくなると説明しています。

#### DACS（Distributed Accelerator for Cloud Storage）

VM に引き込んだデータを複数の VM が使う場合は、他の VM が取得し直さなくて済むようにキャッシュしたいところです。同じモデルを提供する GPU 群があり、モデルのロード・アンロードやコンテキストのキャッシュへの取得を繰り返す推論基盤が典型例です。例えば、エージェントがツール呼び出しの間、数分間アイドルになりキャッシュが追い出された後、同じクラスター内の**別の VM** に戻ってくることがあります。重みの再計算やコンテキストの再投入は、できれば避けたい作業です。

そこで作られたのが **DACS（Distributed Accelerator for Cloud Storage）** で、オープンソースのプロジェクトです（スライドに GitHub の URL が表示されていました）。次の点が説明されています。

- AKS で使えるように提供している。
- 自社の推論基盤 Manifold の内部でも使っている。
- RDMA（GPU Direct を含む）に対応している。
- 例えば、クラスター内のあるサーバーが必要とするモデル重みが、DACS の管理する別のサーバーの NVMe キャッシュにあれば、ホストメモリを経由せずに、Azure Boost を通して GPU メモリに直接取得できる。

### 5.4 コンピュート: Manifold

Manifold は、登壇者が 8〜9 年前に CTO オフィスでインキュベートしたシステムで、本番に移行し、現在は **Microsoft 全体の学習・サービング基盤**になっています。Foundry の基盤でもあり、今後 1 年ほどで顧客も直接利用できるようにしたいと述べています（"hopefully" と付けた見通しです）。

主な特徴は次のとおりです。

- ハードウェアを抽象化するサーバーレスの基盤である。ワークロードやモデルをそのままデプロイすると、コンテナーのセットアップと管理、障害処理、ネットワークの配線、DACS のような仕組みの接続までを Manifold が引き受ける。学習ジョブ、推論ワークロード、モデルサービングのいずれでも、アプリケーション所有者の作業を減らす。
- **断片化の解消。** チームごとに「これがあなたたちの GPU 群」と割り当てると、未使用分が他のチームから使えず無駄になる。Manifold は世界中の GPU、FPGA、アクセラレーターを 1 つのプール（"one pool"）として扱う。条件を満たす空きがあれば、そこにデプロイされる。
- **3 つの優先度**（basic、standard、premium）。クォータは premium で割り当てられ、premium にはオーバーサブスクリプションがない。例えば GB300 を 10 台確保すれば、必ず 10 台が得られる。流入するワークロード、解放される容量、低優先度で追い出し可能なバッチ容量を常時監視する。

登壇者が挙げた成果は 3 件です。

| 事例 | 内容 |
| ---- | ---- |
| Foundry チームの未使用 GPU | Foundry チームに割り当て済みで未使用だった 1,000 台の GB300 を、Manifold が GitHub Copilot に回した。追加容量がまだ立ち上がっていなかった GitHub Copilot は、追加容量の必要時期を遅らせられた。 |
| A100 | 約 13 万台の A100 システム（古いがいまも人気があると説明）の利用状況を約 1 か月分見て、低優先度の追い出し可能なワークロードを活用した結果、実質的に追加で **3 万 5 千台分の A100** を回収できた。 |
| OpenAI との simship | 新モデルを OpenAI と同日に発表する simship について、約 1 週間の遅れ（delay）があったと語られている（何の遅れかは音声からは確定できません）。simship のために確保した容量は、その 1 週間は使われないはずだったが、確保済みの **3,700 台の GB300** を、バッチ容量に回して使えた。登壇者は、前日に発表した最新の「GPT 6.2」モデルに触れています（音声認識の都合で型番が確定できません）。 |

### 5.5 AI ランタイム

#### プロンプトキャッシュとコンテキストキャッシュ

AI コードレビューアーの例が使われています。1 ターン目は約 2,400 トークンで、PR の diff がコンテキストに追加されて約 150 トークン増え、2 ターン目以降もやり取りに応じてプロンプトが伸びていきます。すでにモデルと GPU を通して計算した KV キャッシュは高コストな作業の結果なので、再計算したくありません。

Manifold は、アイドルになったエージェントを外して別のアクティブなエージェントに GPU を回します。ツールの結果が戻ったエージェントが再開するとき、元と同じサーバーに戻るとは限りません。長時間アイドルのままになることもあります。そこで、パフォーマンストレースを分析し、「KV キャッシュをリージョン全体で、多数のモデルとエージェントにまたがって保持できたらどうなるか」をモデル化したところ、大量の作業が省けると分かりました。

これを受けて発表されたのが**コンテキストキャッシュ技術（context cache technology）**です。考え方は単純で、Azure Storage の上に、コンテキストキャッシュ専用の抽象化レイヤーを載せ、エージェントのコンテキストを Azure Storage に保存しておきます。別のサーバーで再開されたら、そこから取り出し直します。

#### ACI サンドボックス

エージェントが起動するたびに、ユーザーは結果をすぐに期待します。オーケストレーターエージェントがサブエージェントを起動し、そのサブエージェントが独自のサンドボックスを起動するような構成では、サンドボックスの起動に 2 分も待たされるわけにはいきません。AI サンドボックスには、エンタープライズワークロード以上に厳しい要件があります。

登壇者は次の点を説明しています。

- **ACI（Azure Container Instances）**: コンテナー（またはコンテナーグループ）をデプロイすると、基盤インフラは Azure が引き受ける。Microsoft 自身もこの上に構築されており、サーバーレスコンテナーの ACI への移行を進めている。ACI のコンテナーはそのまま直接起動・管理することも、AKS の仮想ノード（virtual node）としてつなぐこともできる。後者では、コントロールプレーン以外は完全にサーバーレスな AKS にできる。
- **分離境界**: AI ワークロードやエンタープライズアプリケーションは強く分離されるべきだという考えから、分離境界には Hyper-V を使う。
- **ダイレクト仮想化（direct virtualization）**: 従来の入れ子の仮想化（nested virtualization）から、ベアメタル上に Hyper-V を 1 層だけ置き、その上に ACI のコンテナーを直接載せる形へ進化させている。これにより、ACI のコンテナーも、ネットワーク、ストレージ、GPU や SSD の直接アタッチといった、VM が受けてきた Azure の統合の恩恵を受けられる、ファーストクラスの存在になる。入れ子の構成では、ACI のコンテナーに GPU を直接接続できなかった。いまは InfiniBand ネットワークにも接続でき、GPU や SSD などのデバイスを直接アタッチできる。
  - 登壇者は、コンテナーと VM が並存する期間を経て、最終的にはすべてがコンテナー化されるとの見方を示し、「10 年後かどうかは分からないが、VM はいずれなくなる」と述べています。
- **AI 向けの新要件 1: 高速な起動。** 1 つのサンドボックスの起動は約 0.5 秒かかると述べています。
- **AI 向けの新要件 2: スナップショットと復元。** 多くのエージェントのワークロードは、ライブラリやコンテキストをセットアップした状態から始まり、そこからエージェントをフォークしたくなります。そのため、サンドボックスを起動してスナップショットを取り、ストレージに保存し、そこから復元できる必要があります。アイドルになったエージェントの復元にも、複数コピーのフォークにも使えます。
- **AI 向けの新要件 3: 伸縮できること。** ワークフローの局面によっては RAM や CPU が全部は要らないため、エージェントが拡大・縮小できるようにしている。
- ACI のエージェントサンドボックスは、AKS でも、VM 上のエージェントでも、どの AI プラットフォームにも接続できるようにしたいと説明しています。スナップショット／復元と伸縮の 2 つは、この ACI エージェントサンドボックスの機能になっています。

#### Agent Grid

エージェントを内部リスクとして扱うなら、エージェントに出入りするすべてを制御する必要があります。プロンプトインジェクションや、エージェントが混乱して不適切な動作をする可能性があるためです。Azure Networking チームは、サンドボックスから出るものをすべて傍受し、出入りを許可するポリシーを実装できる仕組みを作りました。典型的には、通信先を遮断するといった制御です。ACA サンドボックス、ACI サンドボックス、ACI のサーバーレスエージェントサンドボックス（音声のまま記載）に対応し、顧客自身の AKS にも Agent Grid を接続できると説明しています。

> 注意：このネットワーク用のプロキシは、サンドボックスの**外側**に置かれます。サンドボックス内にライブラリを入れる方式では、エージェント自身がそのライブラリに手を加えられるため問題になります。エージェントの影響が及ばない場所で制御する必要がある、というのが登壇者の説明です。

Agent Grid は**プレビュー**です。

### 5.6 セキュリティ: Confidential Computing

Confidential Computing は、転送中のデータ、保存中のデータに続き、これまで欠けていた「使用中のデータ」を保護します。登壇者は、Microsoft が "confidential computing" という名前を考え出したと述べ、最初のローンチから約 10 年、研究から数えればさらに長く取り組んできたと説明しています。

登壇者は、**この先の 1 年が Confidential Computing が爆発的に広がる年になる**と見ています。その兆候として次を挙げています。

- フロンティアラボが Confidential Computing に言及したり、関連スタートアップを買収したりしている。
- Apple や Meta のコンシューマー向けサービスが、Confidential な推論に深く取り組んでいる。
- AI を土台に Confidential ハードウェアが使えるようになった一方で、IP、コンテキスト、モデルの機密性のリスクが需要を押し上げている。この 2 つが合わさって爆発的な広がりが起きるという見方です。

その鍵の 1 つが、NVIDIA の Vera Rubin NVL72 の登場です。登壇者は、これを市場で初めての大規模な Confidential アクセラレーターシステムと位置づけています。搭載する個々の GPU と CPU すべてを Confidential な境界（TEE）で囲み、サーバー間や 1 台のサーバー内の GPU 間も高速な接続でつなぎます。これによって、これまで不可能だった大規模推論・大規模学習を Confidential Computing で実現できると説明しています。

### 5.7 セキュリティ: 情報フロー制御（Information Flow Control）

Agent Grid が制御するのは、ネットワークアクセスと、モデルがアクセスできる FQDN やツールです。足りないのは、モデルに入るデータそのものの理解です。コンテキストには機密情報が含まれる一方、信頼できるデータと信頼できないデータが混在するからです。

登壇者の例はこうです。自分の機密情報だけを含むコンテキストなら、他者に漏れてほしくありません。その判断には、コンテキストに「これは Mark の機密データ」というラベルが付いている必要があります。そこに、インターネット上の見知らぬユーザーやウェブページのような信頼できないデータが混ざると、プロンプトインジェクションのような罠が含まれていないとは言えなくなります。エージェントがツールを呼ぼうとしても、だまされていないかを心配しなければなりません。信頼できないデータが入る前は、自分のデータだけだったので、だまされる余地はないと分かっていました。

**情報フロー制御**は、ラベルを追跡します。ラベルには、誰がアクセスできるかという機密性と、プロンプトインジェクションなどで自分をだまそうとしない、信頼できるデータかという信頼性があります。指定したポリシーに基づく動作は次のとおりです。

| 状況 | 動作 |
| ---- | ---- |
| 自分のデータだけを含むメールを自分に送る | 通す（ポリシー違反なし） |
| 自分の非公開データを、アクセス権のない相手に送ろうとする | ブロックする |
| 信頼できないデータを含んだ状態で、エージェントがツールを呼ぼうとする | 承認を求める（本当に呼んでよいかを確認したい） |

オープンソース版の情報フロー制御ポリシーが公開されています。登壇者は、これを GitHub Copilot、Agent Framework（「クリーンな版の Agent Framework」と述べていますが、その意味は音声からは明確ではありません）にコントリビュートしたと説明しています。

## 6. デモ・手順

このセッションには、画面を使ったデモが **7 つ**含まれています。録音は音声のみのため、語られた範囲だけを順に書きます。画面の細部は音声からは確認できません。

### 6.1 RDMA over Azure Boost のデモ

1. オープンソースのモデルを、4 基の NVIDIA GB200 GPU 上で、サービング層に vLLM、さらに LM Cache（音声認識の都合で綴りが確定できません）と Azure Blob Storage を使って実行する。
2. 約 198,000 トークンの『A Tale of Two Cities』（二都物語）を入力し、ゼロからプリフィルする。この処理に約 25 秒かかる。
3. 同じプロンプトを、プリフィル済みのチャンクを RDMA で Azure Storage から取得する設定（RDMA の構成が画面に表示された）で、もう一度 vLLM に通す。同じ 198,000 トークンが処理され、**最初のトークンまでの時間（time to first token）は約 4 秒**になった。
4. 登壇者は、約 **6 倍**の高速化だと説明し、モデル重みのロード、コンテキストの取得など、Azure Storage を使うあらゆる処理に同じ効果が当てはまるとしています。

### 6.2 DACS のデモ

1. AZ Copy で、Azure Blob Storage から約 60 GB のデータを直接ダウンロードする。
2. 約 **3 秒**と約 **38 秒**という 2 つの所要時間を並べて見せ、DACS を使うと大きな差が出ると説明している。

> 補足：登壇者は巻き戻して見せながら、「左が Azure Storage からの GPU Direct、右が DACS」といった説明をしており、左右のどちらがどの構成か、音声だけでははっきりしません。時間だけが 3 秒と 38 秒として語られています。

### 6.3 コンテキストキャッシュのデモ

左右 2 つの構成で競走させます。

1. 左は、キャッシュなしの vLLM。エージェントが別のサーバーで目覚め、コンテキストが失われて再計算が必要になる場面に相当する。
2. 右は、コンテキストキャッシュ技術を使った vLLM。Azure Storage にすでにあるキャッシュを取り出して使う。
3. 共有プレフィックスは 64K で、再計算したくない現実的なサイズとして選んだと説明している。
4. 数値として「最初のトークンまでの時間が 741 ミリ秒」「約 500 ミリ秒で取得した」と語られ、キャッシュありのほうが約 **14〜15 倍高速**と説明されている。

> 補足：741 ミリ秒と 500 ミリ秒がそれぞれどちらの構成の値なのかは、音声からは確認できません。14〜15 倍という倍率だけが明確に語られています。

登壇者は、再計算は高速な処理だが、それでもすべてのトークンをモデルに流す必要があると述べています。リモートから RDMA で取り出すほうが速い、というトレードオフです。

### 6.4 1 万個の ACI サンドボックス起動のデモ

1. 10 個のワーカーが、それぞれ 1,000 個のサンドボックスを起動する（合計 10,000 個）。
2. 画面上に 10 個の pod が表示され、エージェントの各部分を表すブロックが起動する。時間を早回しにはしていない。
3. すべてのブロックが緑（ready 状態）になった。**P50 は 2 秒**だった。

登壇者は、「1 万個のエージェントサンドボックスを 2 秒で起動する」ことは驚異的な数字だが、まだ十分ではなく、さらに短縮に取り組んでいると述べています。

### 6.5 Agent Grid のデモ

1. Agent Grid の画面で "Add" を選ぶ。複数の選択肢の中から AKS クラスターがあり、AKS のエージェントデモ用クラスターを追加する。
2. これでクラスターのすべての通信が Agent Grid を通る。ただしポリシーは未登録で、最初は何もアクセスできない（"it starts with nothing"）。
3. クラスターに 1 つのポリシーを登録し、MCP サーバーへのアクセスを許可する。
4. そのエージェントとのチャットで、MCP サーバー経由で顧客情報を問い合わせる。Agent Grid が監視し、データの流出（exfiltration）は見られなかった。返ってきたのはその顧客のサービス記録だけだった。
5. 次に、顧客が他のユーザーの情報や追加の情報を求める。モニタリングを確認すると、本来見られないはずの他の顧客の情報が、この 1 人の顧客に流出していた。
6. MCP サーバー内に、ブロックすべきツールがあると判断し、`export customer records` に対する deny ポリシーを設定する。適用すると、deny のルールが表示される（もう 1 つのルールにも言及がありましたが、聞き取り不明瞭です）。
7. もう一度同じ操作を実行すると、Agent Grid がそのツールへのアクセスをブロックしたため、顧客記録は流出しなかった。
8. Agent Grid はあらゆるログも収集する。画面には、エージェントがさまざまなエンドポイントと通信している様子を表す地図が表示され、MCP のツール経由で顧客記録にアクセスしようとしてブロックされたリクエストも含まれていた。

登壇者は、監査（何が起きたか、どう流出したか、誰に流出したか）のために、サンドボックスに出入りしたものについてエージェント固有のコンテキストが必要だと述べています。

### 6.6 Confidential Computing（CCA）の起動デモ

登壇者は「とても生のデモ」と断ったうえで、Confidential computing architecture（CCA）を、Vera プロセッサー（ARM）と Confidential な GPU の上で、初めて立ち上げた（first bring-up）ものだと説明しています。

1. 画面は、VR72 ホスト上の Ubuntu Linux。4 基の GPU が接続されている。
2. Confidential Computing ハードウェアからのアテステーションが表示され、4 基すべての GPU が Confidential Computing で保護されていることを確認する。
3. その 4 基にまたがって vLLM サーバー（音声のまま "VLM" と聞こえます）を起動する。モデルは 4 基の Rubin GPU すべてが必要で、**3,970 億（397 billion）パラメーター**のモデルである。
4. VRAM（HBM）の使用量を確認する。
5. 数学の問題を投げ、モデルが答えを返した。

登壇者は、見た目は 4 基の GPU で大きなモデルが質問に答えているだけだが、これが VR72 プラットフォームの Confidential Computing で保護されていることが重要で、これまでできなかったことだと述べています。

### 6.7 情報フロー制御のデモ

メール（メールボックス）の例で、語られた順に書きます。登場人物の名前は、音声認識の都合で綴りが確定できません（聞こえたまま Aashish、Ales Holacek と記載します）。

1. 受信箱に、Satya から Aashish に宛てた決算発表（earnings call）に関するメールがあり、Ales Holacek が CC に入っている。登壇者は「実際の決算ではないのでスクリーンショットは撮らないで」と冗談めかして述べています。
2. 受信箱には、Ales から Aashish に宛てた、Satya の決算に関する情報を求めるメールもある。
3. Aashish がエージェントに、未読メールを処理するよう指示する。エージェントは未読メールを確認して対応が要るものを選び、対応が必要なスレッドが 1 つあると報告する。内容は、Ales が AI インフラのレポートを集約して欲しいと依頼しているというもの。返信は正常に送信された。
4. 返信が許可された理由は、Ales が元の Satya のメールの宛先に入っていたからである。ラベルを追跡しているため、Ales がコンテキスト内のそのデータに、すでにアクセス権を持っていることが分かる。
5. 続けて、Ales が宛先に入っていないメールの場合が示される。この場合、Ales の要求が正当かどうか分からない。情報フロー制御はラベルの追跡から「ちょっと待って、Ales がデータを求めているが、渡してよいか」と判断する。登壇者はこれを **declassification（機密区分の引き下げ）操作**の例だと説明しています。

> 補足：この 5 の場面で、画面上の最終的な結果（承認の確認が出たか、ブロックされたか）は、トランスクリプトでは明確に語られていません。

登壇者は、Agent Grid ではこのレベルのラベル追跡は見えず、コンテキストに入るものを非常に細かい粒度で見て初めて、何をすべきかが分かると述べています。

## 7. 注意点・発表者の気付き

- **マイクロフルイディクス冷却は、まだ主流にはなっていません。** パイロット運用中で、現時点では自社でチップをエッチングしており、保証が無効になります。サプライヤーによる工場での加工を目指しています。
- **Manifold の顧客向け提供は「できれば来年あたり」という見通し**です（"hopefully in the next year or so"）。
- **RDMA は Azure Boost 対応 VM タイプでプレビュー**、Agent Grid もプレビューです。
- Agent Grid のようなネットワーク制御だけでは、コンテキスト内のデータの機密性・信頼性は分かりません。この層は情報フロー制御が補います。
- サンドボックス内にライブラリを入れる方式でエージェントを制御するのは問題です（エージェント自身がライブラリに手を加えられるため）。制御はサンドボックスの外側に置く必要があります。
- 1 万個のサンドボックスを P50 2 秒で起動できても、登壇者は「十分ではない」として改善を続けるとしています。
- 登壇者自身が、時間の都合で「用意した内容の半分未満しか紹介できなかった」と述べています。

## 9. まとめ

- Azure は、規模の大きさと新しい AI ワークロードを背景に、冷却からシリコン、ストレージ、コンピュート、ランタイム、セキュリティまで全層で最適化しています。直近 18 か月のデプロイ容量が最初の 15 年間を超えるほどの成長が前提にあります。
- 共通のテーマは、**重複した作業と断片化した容量をなくす**ことです。冷却のゾーン分け、RDMA と DACS によるデータの直接転送、コンテキストキャッシュ、Manifold の「1 つのプール」がその例です。
- エージェント向けには、起動が速くスナップショットと伸縮ができる ACI サンドボックス、サンドボックス外側でネットワークを制御する Agent Grid（プレビュー）、コンテキストのラベルを追跡する情報フロー制御が紹介されました。
- Confidential Computing は、Vera Rubin NVL72 の登場で大規模な推論・学習に広がる転換点にあると登壇者は見ており、4 基の Rubin GPU で 3,970 億パラメーターのモデルを動かす初期のデモが示されました。
