# BRK415 Put AI agents to work in Azure cloud operations

## 1. はじめに

このセッションは、AI を「コードを書く場面」だけでなく「ソフトウェアを運用する場面」にも持ち込もう、という内容です。題材は Azure の運用（Agentic Operations）で、FinOps、SRE、プラットフォームエンジニアリングの担当者に向いています。

発表は短い導入のあと、4 本のデモで進みます。ARM MCP server によるデプロイとリソース管理、Azure Copilot によるコスト急増の分析、SRE agent によるインシデント対応と事前の障害防止、そして Azure Policy を使った AI エージェントの統制です。

結論として発表者が強調したのは、**エージェントに運用を任せるには、コンテキストとガードレール（統制）の両方が必要**という点です。

## 5. 発表内容の詳細

### 5.1 運用モデルが変わる背景

導入部分で Brendan Burns 氏は、次の変化を挙げています。

**システムの「正常」の定義が変わっている。** 以前はエラー率が、システムが動いているかどうかの目安でした。しかし AI を使うシステムでは、応答の品質が稼働率と同じくらい重要になります。AI が返した結果が、利用者の目的を達成したかどうかという主観的な評価も必要です。

**AI ワークロードは変化しやすい。** プロンプト、ユーザーが送るテキスト、モデルのどれを変えても出力と品質が変わります。そのため、ソフトウェアのバグだけでなく、ソフトウェアに渡されるコンテキストのバグも気にする必要があります。具体例として、Azure ドキュメントを担当するチームの話が挙がりました。ドキュメントは人が読むだけでなく、エージェントが人の目の届かない場所で自律的に Azure を更新するためにも読まれます。そのため、鮮度と正確さがいっそう重要になります。

**システムに求められる変更速度が上がっている。** 発表者は、Wikipedia に「Black October」のページがあることに触れ、11 月、12 月、1 月にも同様のページができるだろうと冗談交じりに述べています。AI が他の領域に与える影響に合わせて、システムを極めて速く変更できる必要がある、という趣旨です。

**障害はチームやシステム間のつながりで起きやすい。** そのため AI には、自分が運用する個々の部品だけでなく、変更が他の環境にどう波及するかまで含めた全体のコンテキストを理解させる必要がある、と説明しています。

### 5.2 Agentic Operations が目指すもの

Agentic operations とは、ソフトウェア開発ライフサイクルの各段階を AI とエージェントでカバーし、それらが連携して「デプロイされ、保守され、運用されるソフトウェア」という成果にたどり着く考え方です。目標として、次の 3 点が挙げられました。

1. **運用の手間（toil）を減らす。** 優秀なエンジニアに AI を使わせても、デプロイ後の手作業で足を引っ張られては意味がない、という問題意識です。
2. **本当の理解に基づいて判断する。** 発表者はエージェントが情報へのアクセスを民主化した点を利点に挙げています。以前は、あるインシデントの直し方を知っているのは対応した DRI（オンコール担当）だけでした。エージェントがチケット管理システム全体を読めば、その知識がすべてのオンコール担当者に引き継がれます。先週別の人が対応した障害の知見も、翌週のオンコール担当者を助けるエージェントに渡ります。
3. **エージェントが安全に変更できるプラットフォームにする。** 例えば「使われていないストレージアカウントを片付けて」と頼んだとき、使用中のストレージアカウントまで消されないようにするためのガードレールです。

顧客事例として、Ecolabs（音声認識の表記）が Agentic operations に取り組み、問題の検出が速くなったこと、根本原因分析のスピードが大きく上がったこと、アラート 1 件あたりに DRI が費やす時間が大きく減ったことが紹介されました。ログを掘る時間が減った分を、オンコール担当者の睡眠や、システムの先回りの開発に回せるという説明です。具体的な数値はこの事例では示されていません。

### 5.3 全体像：体験・インテリジェンスエンジン・リソース資産

発表者は全体像を 3 層で説明しています。

| 層 | 内容 |
|---|---|
| 体験とツール | GitHub CLI、Azure Copilot、SRE agent など、エージェント的な体験への入り口 |
| インテリジェンスエンジン | エージェントが動く対象の広いコンテキストを理解する役割 |
| リソース資産（resource estate） | Azure 環境にあるすべてのものと、それらのつながりを示すマップ（Resource Graph） |

これらはパブリッククラウド、ハイブリッド、さらに工場や支店にある IoT デバイスまで含めた、あらゆる環境をまたぐものとして位置づけられています。発表者は、エージェントとのやり取り、必要なコンテキストの提供、変更の統制、環境全体の把握が揃う点が、Azure、ひいては Microsoft プラットフォームの強みだと述べています。

### 5.4 ARM MCP server（Steven Bucher 氏）

Steven Bucher 氏は、Agentic Ops の最初の領域として「Azure のコンテキストと運用を、好きなクライアントから使えるようにすること」を挙げました。任意のコーディングエージェントから Azure にデプロイ・設定できるようにするものです。

その手段が **Azure Resource Manager MCP server（ARM MCP server）** です。次のように説明されています。

- 既存の ID と権限を使い、自然言語で Azure リソースにアクセスできる**リモートサーバー**。
- Azure MCP server とは異なり、Azure のコントロールプレーン全体につながっている。
- 1 つのサーバーと少数のツールで、あらゆる Azure リソースタイプの読み取り、作成、変更、管理ができる。
- 自然言語から Azure Resource Graph クエリを生成し、検証してから実行する。データはリアルタイムで正確であることを重視している。
- デプロイの what-if 実行や、作成を妨げるポリシーの詳細取得ができる。
- 変更を伴う運用タスクでは、通常、人による確認（human in the loop）を求める。

デモ後のまとめでは、次の点が紹介されました。

- ARM MCP server は現在 **public preview**。
- リソースの作成・管理・更新の新機能を最近発表した。
- コスト分析と追加の予算設定も可能で、エージェントに対する運用上のコントロールに役立つ。
- 詳細は `aka.ms/arm MCP server`（トランスクリプトでの聞こえ方）。

### 5.5 Azure Copilot とコンテキスト：Spaces

Ruhiyyih Mahalati 氏は、コストの急増や、原因が分からない請求に悩んだ経験は多いはず、という問いかけから始めました。Azure Copilot には組み込みのツールとスキルがあり、コスト急増の分析だけでなく環境の最適化にも使えるという説明です。

新機能として **Spaces** が紹介されました。Copilot に常に保持させる「永続的なコンテキスト」を作る機能です。アプリケーションのコンテキストだけでなく、ビジネスや運用のコンテキストも含められます。

- アプリケーションの参照は、リソースグループ、サブスクリプション、さらに「entry applications」と聞こえるものから追加できる（最後の語は音声認識の都合で確定できません）。
- SLA 文書やアーキテクチャ文書などのビジネスコンテキストをアップロードできる。
- 「application brief」には、運用面とビジネス面の指示を書ける。リソースからは分からず、ビジネスオーナーだけが知っている情報を渡すためのものです。

### 5.6 Azure Copilot の新機能（アナウンス）

この Ignite で発表される Azure Copilot の新機能として、次が挙げられました。

- GitHub の SDK（Copilot）で完全に作り直したチャット体験。追加情報を尋ねる elicitation に対応。
- 使いやすくする可視化。
- 既定で追加される多くの新しい・改善されたスキル。
- ARM MCP に加え、Entra MCP などによるより深いコンテキスト。
- 永続的なコンテキストのための Spaces。
- カスタマイズ機能：特定のツールやスキルの有効化・無効化、独自スキルの作成、別の MCP server の追加。

ある顧客が、すでにこれらの新機能を使って**根本原因分析で最大 50% の時間短縮**を得ており、Copilot の知見によるコスト削減も得ている、とのことです。

## 6. デモ・手順

このセッションには 4 つのデモがあります。画面の細部は音声からは確認できないため、語られた範囲で書きます。なお、デモの環境は架空の「Caldova Pharmacy」（音声認識の表記ゆれで Coldova、Keldova とも聞こえます）で、インシデントは説明のために事前に作成したものだと発表者が述べています。

### 6.1 デモ 1：ARM MCP server（Steven Bucher 氏）

VS Code で ARM MCP server を動かした状態から始めます。この日の作業は、本番前（pre-prod）のセットアップという設定です。

1. サブスクリプションにあるリソースを、ARM MCP server に自然言語で一覧させる。必要なら各リソースのより深いプロパティも尋ねられる。
2. 手元の Bicep ファイルを、Bicep MCP server と ARM MCP server でデプロイするよう依頼する。
3. ARM MCP server が検証の途中で、作成しようとした Key Vault の 1 つが Azure Policy でブロックされることを検知し、使える代替案を提示する。
4. リージョンを Canada Central から Canada East に変更して入力し、検証が続行される。
5. 検証が整うと、デプロイの承認を求められる。変更を伴う操作では人の確認を求めるという仕組みで、内容を確認して承認する。
6. デプロイが進み、最後に概要が表示される。途中で解消したブロッカー（ポリシーによる拒否や名前の問題など）も示される。
7. 作成したリソースに対し、Azure Advisor の推奨事項を ARM MCP server 経由で取得し、セキュリティ強化の提案を受ける。
8. コンテナレジストリを安全にするための変更を依頼する。長時間かかる操作で、意図を確認する質問が何度かある。接続先として VNet を作成させる。
9. バックグラウンドで実行させている間に別の作業をし、ステータスを確認する。一部の変更は完了し、いくつかは未完了。新しい VNet などが作成されている。
10. 同じ ARM MCP server を Claude desktop にも接続し、同じサブスクリプションとリソースが取得できることを示す。
11. GitHub Copilot app では、canvas や可視化を作るプラグインやツールがあるので、ARM MCP server から得た Azure のデータで組織向けの可視化を作れる、と説明する（画面の詳細は音声からは確認できません）。

### 6.2 デモ 2：Azure Copilot によるコスト急増の分析（Ruhiyyih Mahalati 氏）

Caldova Pharmacy の FinOps 担当という役割で、予算しきい値の超過を知らせるアラートを受け取った状況から始めます。

1. アラートのリンクから Azure portal のコスト分析ビューに入る。10 月中旬からコストが増えているが、原因の特定には多くのクエリや画面、ワークロードオーナーへの確認が必要になる、と説明する。
2. ポータル内の Azure Copilot を開き、「help me understand the cost spike」と尋ねる。Copilot はサブスクリプションのコンテキストをすでに持っている。
3. Copilot がコストのスキルを呼び出して請求情報をまとめ、Azure Resource Graph にクエリして、アプリケーションのライブな状態や依存関係を把握する。さらに、請求データとアプリケーションデータを対応づけ、前後比較の分析もする。
4. 日次コストの急増と、主要ワークロードとして「AKS QA load test」が示される。オーバーサイズのノードやクラスターの余剰キャパシティを調べられる、とも提案される。
5. ここで Spaces を新規作成する。アプリケーション参照を追加し、SLA 文書やアーキテクチャ文書などをアップロードする。
6. application brief に含まれるビジネスカレンダーで、「組織の繁忙期（ピーク）が 11 月中旬から始まる」という情報を Copilot に渡す。
7. 同じ質問をもう一度する。今度はビジネスコンテキストが取り込まれ、コスト分析のライトサイジング情報、現在の使用率、各リソースプロバイダーの推奨、予約プランなどのコミットメントベースの節約も含めた包括的な見解が返る。
8. 結果は「ロードテストが必要な時期だった」「コスト削減の話ではなく、ロードテストのコストを予算に入れていなかったことが問題」という内容。予算の見込みを更新すべき額の見積もりも示される。
9. さらに「他にコストを下げる方法はあるか」と尋ねる。組織は Bicep でデプロイしているため、必要なら Bicep の変更も出してほしいと頼む。Copilot は ARM MCP と Resource Graph を使い、依存関係を把握する。
10. 提案は、QA ロードテストのインスタンスに auto scaling を有効にすること（ゼロまで縮退できる）と、コストが膨らまないよう上限を設けること。Bicep コードが出力され、エンジニアリングチームに渡すか、標準の CI/CD パイプラインに通す前に検証できる。節約額の見積もりも示される。
11. 聞いていないのに、運用ドキュメントをコンテキストに持っているため、本番の構成が単一ノードで動いている点も指摘される（必要なノード数は音声が不明瞭で確認できません）。本番についても修正コードを依頼できる。

### 6.3 デモ 3：SRE agent（Ruhiyyih Mahalati 氏）

SRE（または DevOps）エンジニアという役割で、3 つのシナリオを示しました。

**シナリオ 1：自律的な緩和**

1. SRE agent が開いた GitHub issue から始める。注文処理が使えなくなったが、agent が緩和した、という内容。
2. issue に根本原因分析と影響が書かれている。緩和までに約 7、8 分。バックエンドのデータベースサーバーが停止していたのが原因で、承認済みの安全な操作として agent がデータベースサーバーを再起動した。
3. 詳細を開くと、起点は自律対応が紐づいた Azure Monitor アラート。agent は記憶（過去のインシデント、runbook などの指示）を参照し、CLI コマンドやアクティビティログで診断し、データベースサーバーの停止を突き止めて、再起動後にアプリが復旧したことを確認している。
4. 設定画面で、agent が実行できるツール、実行前に承認が必要なツール、拒否するツール（例：本番での削除操作。ステージングでは許可してもよい）を運用者が決められることを示す。

**シナリオ 2：レビューモード（運用者が主導）**

1. Azure Monitor アラートでレビューモードのインシデントが始まる。agent は記憶と runbook を参照し、診断情報を集める。
2. 高い確信度で、Postgres サーバーの認証の問題で、パスワード更新が必要だと報告する。ただし、これは agent に承認された操作ではないので、人が行う必要があると明示する。すべてを記録した GitHub issue も作る。
3. 「それでも直すのを手伝って」と依頼すると、agent は自分ではパスワード変更ができないと答え、実行用のコマンド（スクリプト）を出す。本来は別のエンジニアのレビューを受けてから使うもの、と説明されている。
4. 時間の都合でバックエンドに適用し、パスワードを更新したと agent に伝える。
5. agent が、パスワード更新を反映させるためコンテナインスタンスの再起動に進む。レビューモードなので承認を求められ、「一度だけ承認」と「スレッドに対して承認」から選べる。承認する。
6. コンテナアプリのインスタンスが再起動され、agent がアプリの復旧を確認し、GitHub issue を更新する。調査時間が数時間から数分になった、という説明。

**シナリオ 3：デプロイガードによる障害の予防**

1. SRE agent のワークフロー自動化は、HTTP トリガーまたはスケジュールで起動できる。事前に作成した「deployment guard」は、ステージングにデプロイが push されたら起動する設定。
2. ステージングへ push すると、runbook に従って合成テスト（synthetic test）を実行し、診断情報も集める。160 件中 160 件が 200 応答で可用性は良好。レイテンシとパフォーマンスも良好だった。
3. 続くヘルスチェックの結果、デプロイの挙動変更が見つかる。応答がデータベースではなくソースのモック（mock）から返っていた。
4. 高い確信度で「このビルドは良くないので本番に push しないように」と推奨される。

### 6.4 デモ 4：Azure Policy によるエージェントの統制（Ruhiyyih Mahalati 氏）

**ポリシー 1：SRE agent の作成と設定**

1. 事前に作成した、SRE agent 用の Azure Policy の定義を見せる。内容は「Azure OpenAI のモデルだけを使い、かつレビューモードだけで動かす」。これを本番スコープに適用する。
2. 本番スコープで新しい SRE agent を作成する。必須パラメーターを入力し、モデルプロバイダーに Anthropic を選んで作成する。
3. 検証で Azure Policy が作動し、承認されないと返る。
4. Azure OpenAI に変更して作成すると、検証を通り、デプロイが進む。
5. 事前に作成済みの SRE agent の設定で、エージェントモードを review から autonomous に変えようとする。ポリシーによって、この変更もブロックされる。

**ポリシー 2：ARM MCP server を呼ぶカスタムエージェント**

1. 開発者が作るカスタムエージェントが ARM MCP server を呼ぶ場合に備えたポリシーを示す。定義は「ARM MCP server への create や update を、本番サブスクリプションでブロックする」。ステージングで適用することもできる。これは自分たちの方針次第、と説明している。
2. 本番スコープに適用したうえで、エージェントに自然言語で、Caldova の本番スコープに Key Vault を作るよう依頼する。
3. エージェントが Azure Resource Graph MCP で現状を把握し、クエリを組み立てる。ポリシーのデモのため、ツールの実行はすべて許可している。パブリックアクセス無効といった既定値も選んでいる。
4. 作成を実行すると、ポリシーによって操作がブロックされたと返る。

## 7. 注意点・発表者の気付き

- **エージェントには権限の線引きが要る。** 使っていないストレージアカウントの掃除を頼んでも、使用中のものを消さないようにする、というのが発表者の挙げた例です。
- **SRE agent の承認設定は運用者が決める。** ツールごとに「実行を許可」「承認が必要」「拒否」を設定できます。本番では削除を拒否し、ステージングでは許可する、といった使い分けが例示されました。
- **ARM MCP server の変更系操作は、通常、人の確認を求める。** デモでは、デプロイの前に承認を求められました。
- **ARM MCP server のデモでは、一部の変更が未完了のまま終わった。** 長時間かかるセキュリティ強化の操作で、ステータス確認時には完了した変更と未完了の変更が混在していました。
- **インシデントのデモは事前に作成したもの。** 発表者自身が、フローを説明するために作ったインシデントだと述べています。
- **SRE agent の社内数値は Microsoft 内の組織での値。** 発表者が、これは自社組織での利用結果だと明示しています。
- **ポリシーのデモでは、ツール実行をすべて許可した。** ポリシーの挙動を見せるための設定です。
- **ARM MCP server は public preview、SRE agent の新機能の多くも public preview。**

## 9. まとめ

このセッションは、Azure の運用を AI エージェントに広げる取り組みを、4 本のデモで示したものです。

- **ARM MCP server**（public preview）は、自然言語と任意のクライアントで、Azure リソースの調査、デプロイ、変更を行える。変更時は人が承認する。
- **Azure Copilot** は、Spaces でビジネスや運用のコンテキストを持ち続けることで、同じデータからもより的確な判断を返す。コスト急増の例では、原因が「ロードテストの予算未計上」だと分かった。
- **SRE agent** は、自律対応、レビューモード、デプロイ前の健全性チェックの 3 通りで使える。Microsoft 社内では 25 倍速い修復などの成果が出ている。
- **Azure Policy** で、エージェントが使うモデルやモード、ARM MCP server 経由の作成・更新を本番でブロックできる。

自律性が高まっても、Azure ランタイムに組み込まれた統制の上で動くため、運用者は常にコントロールを握り続けられる、というのが発表者のメッセージです。
