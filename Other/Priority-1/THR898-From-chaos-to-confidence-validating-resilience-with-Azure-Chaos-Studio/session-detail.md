# THR898 From chaos to confidence validating resilience with Azure Chaos Studio

## 1. はじめに

このセッションは、Azure Chaos Studio の新しい体験「Azure Chaos Studio Workspaces」と、AKS 向けの拡張（AKS extension）を、ライブデモ中心で紹介する 25 分のシアターセッションです。

ダッシュボードはすべて緑で、オブザーバビリティにも問題がない。それなのにユーザーからは「遅い」「動かない」という声が届く。そんな経験のあるプラットフォームエンジニアに向けて、**本番に近い構成に実際に障害（フォールト）を注入し、レジリエンスを検証する**という考え方が示されます。デモでは、チケット販売アプリケーションの AKS と Cosmos DB 間のネットワークを切断し、冗長構成のあるサイトとないサイトで挙動がどう違うかを見せています。

## 5. 発表内容の詳細

### 5.1 新発表：Azure Chaos Studio Workspaces と AKS extension

Nikhil 氏は、Azure Chaos Studio が Ignite で **Azure Chaos Studio Workspaces** という新しい体験を発表したと説明しています。過去にもらった多くのフィードバックを受けて、Chaos Studio を「アクセスしやすく、価値を感じやすいもの」にするために、この 1 年間取り組んできたものだそうです。

あわせて、AKS extension も紹介されています。この拡張には、pod delete、CPU・メモリのプレッシャーといったフォールトがあります。今回のデモでは、そこから**ネットワーク障害（パケットロス）**を、実際に動いているアプリケーションに注入します。すべて同じワークスペースから実行します。

デモの題材は、AKS と Cosmos DB で構成したチケット販売アプリケーションです。発表者は、シミュレートできる障害として次を挙げています。

* コンピュートのゾーンダウン
* DNS
* データベースのフェイルオーバー
* 自分で作成するカスタムシナリオ

### 5.2 ワークスペースとシナリオの考え方

Abhi 氏は、ワークスペースの作成は手間のかかる作業ではなく、すぐに作れると説明しています。ワークスペースには、スコープ（対象リソースの範囲）を指定します。スコープは、サービスグループ、リソースグループ、サブスクリプションのいずれでも構いません。ワークスペースを作ったあとに、その中で**シナリオ**を作成します。

シナリオには、実行するアクションと対象リソースが含まれます。作成後には「validation（検証）」が走ります。これは、ワークスペースが対象のクラスターに実際に接続でき、そのアクションを実行できるかどうかを確認するものです。

シナリオの作成方法は複数あります。ポータルで作成・編集できるほか、デモのように Copilot に自然言語で頼むこともできます。さらに、オープンソースの GitHub リポジトリ（「Chaos Studio GitHub」で検索）に、サンプルアプリケーション、MCP、導入ガイドが公開されています。デモで使ったものもここに投稿する予定だと述べています。Abhi 氏によると、「easy chaos API」（音声認識の都合で表記が確定できません）のモジュールを使えば、自分でもこれらの操作を作成できます。この API を MCP 経由で直接使うこともできます。プラグインをインストールすれば、すぐに使える状態になるとのことです。

### 5.3 実際に障害を注入するときの流れ

デモで示された流れから、Chaos Studio の実行時の特徴は次の 2 つです。

* **実行前の確認がある**：実行しようとすると確認画面が出ます。発表者は「are you sure ボタンのようなもの」と呼び、何が起きるかを顧客に事前に把握してもらうためだと説明しています。
* **反映までに少し時間がかかる**：登壇者（話者ラベルがなく、どちらの発言かは特定できません）の経験では、実行を始めてから挙動の変化に気づくまで約 45 秒です。シナリオのセットアップ、リソースへの到達、アクションの適用という順で進むためです。

### 5.4 実際のアプリで想定すべき障害

デモのあと、Nikhil 氏はデモ用に Copilot に描かせたというアーキテクチャ図を使って、Chaos Studio が多くのサービスにわたってフォールトを提供していると説明しています。実際の本番チケットアプリを、単一リージョンの Cosmos DB と AKS だけで組むことはなく、実際の障害ではさまざまなサービスが関わるという前提です。

チケット販売アプリでの影響の例として、次のものが挙げられています。

| 障害の対象 | チケット購入で起きること（発表での例） |
| --- | --- |
| DNS | Web サイトを引けず、チケットを買いに行けない |
| Entra | 注文したのが本人かを確認できない |
| Key Vault | 支払いが処理できない。Key Vault が落ちているわけではなく、そこへのリクエストの経路が塞がれている場合もある |
| Service Bus | 支払いは受理されたのにチケットが届かない |
| コンピュート | 最も人気のあるフォールト（今回は未デモ）。ワーカーが 1 つのゾーンに集中していると、そのゾーンが失われたときにチケットが遅延するかもしれない（挙動は想像がつかないと発言） |

Nikhil 氏は、プラットフォームエンジニアは「Entra が落ちたら何が起きるか」といったことを見落としがちだと述べています。コンピュートのゾーン障害については、マルチゾーン構成ならワークは別のワーカーに分散されるため問題にならない、そしてそれを実際に体験して確かめることが検証の目的だと説明しています。また、定常状態で期待どおりの挙動になっているかも確認したいと述べています。

発表者は、この図に出てくるものは**すべて、今日の Chaos Studio で利用できる**と述べています。時間の都合で、今回は AKS extension を選んでデモしました。

### 5.5 どんなときに使うと価値が大きいか

Nikhil 氏は、顧客が最も価値を感じている場面として次の 3 つを挙げています。

1. **ローンチ前**：ホリデーシーズンの買い物商戦や製品ローンチの前に使い、ローンチ後に引き返せなくなる前に、コストの小さいうちに弱点を見つける。（発表では、ブラックフライデーが目前なので間に合わないかもしれない、という冗談も添えられています。）
2. **大きな変更があるとき**：特に、エージェントがコードを書き、誰もコードを読まなくなっている今、「Copilot が言うとおりにコードが動くか」を確かめる手段として、**決定論的なフォールト注入**の価値が高いと述べています。
3. **スケジュール実行**：最も成熟した顧客が行っていることで、Microsoft 社内の顧客や大規模な外部顧客も実践しています。ビルドパイプラインやデプロイパイプライン（コードのチェックイン時）にカオス実験を組み込み、その結果でパイプラインを進めるかどうかを判定（ゲート）します。

これは高度な使い方ですが、製品として簡単に実現できるようにしているとのことです。Nikhil 氏はこれを「good, better, best」の段階として整理しています。

## 6. デモ・手順

このセッションにはライブデモがあります。録音は音声のみのため、画面の細部は分からず、以下は発話で語られた範囲に限ります。

### 6.1 デモ 1：チケットサイトを障害で壊す

1. Nikhil 氏が、稼働中の Contoso tickets サイトを表示します。Jane Doe のコンサートのチケットサイトで、AKS 上で動き、データベースは Cosmos DB です。Cosmos DB にはチケットやクレジットカード情報など、チケット販売アプリに必要なものを保存しているという説明です。
2. 画面には、HTTP リクエストがログとして表示される DevTools 風の UI があります。これは、このデモのために Copilot で急いで作ったものだと述べています。
3. 席を選び、購入します。購入は成功し、リクエストが記録されます。テストで一部の席はすでに埋まっていました。
4. Abhi 氏がワークスペースの画面を見せます。時間の都合で、ワークスペースは事前に作成済みです。
5. シナリオの作成は、ポータルではなく Copilot への自然言語のプロンプトで行います。プロンプトは事前に入力済みで、シナリオの内容を平易な言葉で指示しています。実行を速くするための追加の指示も含まれていました。Abhi 氏によると、反映までに 30〜45 秒ほどかかります。
6. 裏側では、Copilot がそのワークスペースを対象に、**100% のパケットロスを起こすネットワークアクション**を使ったシナリオを作成します。
7. ワークスペースに戻ると、「live demo scenario」が作成されています。アクションは「primary region loss」で、対象は 2 つのクラスターです。どちらも validation 済みです。
8. シナリオを実行します。確認画面が出るので承認し、「run is being prepared」の表示になります。この間も元のサイトはまだ動いています。
9. 数十秒後、チケットを検索しようとしても何もできなくなります。顧客が見るのはこの状態であり、起きたことは**クラスターと Cosmos DB 間のネットワーク切断**だけだと説明しています。

### 6.2 デモ 2：冗長構成のあるサイト

1. 同じサイトを、適切なバックアップ用 DB を備えた構成で立てた別のサイトに切り替えます。
2. このサイトでも、本来向かうはずのプライマリデータベースは壊れています。同じフォールトを Cosmos DB の両方に適用したためです。
3. しかし、バックアップがあったため、そちらに切り替わり、サイトは動き続けます。発表者は「レジリエンスの設定がすでにあるサイトは、この状況でも動く」と説明しています。

### 6.3 デモ 3：シナリオの編集と validation の失敗

最初のシナリオはまだ実行中でした。Abhi 氏は、以前に実行した別のシナリオを使って、編集の流れを見せます。

1. プロンプトでシナリオを作ったあとでも、プロンプトを追加して更新できます。ポータル版でも、シナリオを編集してアクションを追加できます。
2. アクションは AKS 向けだけではなく、大きなアクションライブラリから選べます。次回の実行で、追加したアクションが適用されます。
3. 例として、Cosmos DB のアクションを追加します。リージョンは East US 2 のように聞こえます（音声認識の都合で表記が確定できません）。実行時間は 10 分で、アクションは順番に実行されます。
4. 更新すると、シナリオは自動的に validation を実行します。Abhi 氏は、権限が十分に設定されていないため validation が失敗する、あるいは戻ってこないかもしれないと予告します。
5. 実際には、すべてが再 validation されている状態になりました。Abhi 氏は、別のフォールトが実行中のリージョンを同じく対象にしたため、アクセスできないのが原因だと説明し、「ライブデモではこうなる」と述べています。

なお、デモ後の補足として、ポータルで可能な設定とシナリオの作成は、Copilot への指示でもできます。

## 7. 注意点・発表者の気付き

* 本番に近いアプリでも、単一リージョンの Cosmos DB と AKS だけで構成することは勧められないと述べています。冗長構成があると、同じ障害でも結果が変わります（デモ 2）。
* シナリオの実行前には、何が起きるかを確認する画面があります。意図しない障害を避けるための仕組みです。
* 障害が反映されるまでに 45 秒ほどかかります。
* すでに別のフォールトが走っているリージョンを対象にすると、validation が完了しません。デモでは実際にこれが起きました。
* 障害を考えるときは、DNS、Entra、Key Vault、Service Bus など、アプリが依存するサービスが止まったらユーザー体験がどうなるかまで見る必要がある、というのが発表者の気付きです。
* コンピュートについて、発表者はマルチゾーン構成にしていてほしいと述べています。1 つのゾーンにワーカーが集中していると、そのゾーンの喪失がそのまま影響します。

## 8. 利用者にとっての利点

発表で語られた価値は次のとおりです。

* ダッシュボードが緑でも見えない弱点を、実際のフォールト注入で見つけられます。
* ローンチ後に引き返せなくなる前に、コストが小さいうちに問題を見つけられます。
* エージェントが書いたコードが意図どおり動くかを、決定論的なフォールト注入で確かめられます。
* ビルド・デプロイパイプラインでカオス実験を定期実行し、その結果でパイプラインを進めるかどうかを判定できます。Microsoft 社内の顧客や大規模な外部顧客が実践しています。
* ポータル、Copilot、API、MCP のどこからでも使えます。
* 夜中に呼び出される前に、日中の勤務時間に障害を見つけられます。

なお、特定の顧客名や数値による導入効果は、発表では紹介されていません。

## 9. まとめ

Azure Chaos Studio は、実際にフォールトを注入して、環境のレジリエンスを検証するサービスです。Ignite では、新しい **Azure Chaos Studio Workspaces** と、**AKS extension** によるネットワーク障害の注入が紹介されました。

デモでは、Copilot への自然言語のプロンプトからシナリオを作成し、AKS と Cosmos DB 間のネットワークを切断して、バックアップ DB のないサイトが止まり、バックアップを備えたサイトは動き続ける様子が示されました。ポータル、Copilot、API、MCP のいずれからでも使えます。公式ドキュメントとパブリックな発表に詳細があります。
