## 4. 発表者が伝えたいメッセージ

発表の中心は、「ソブリンティは単なるポリシーの話ではなく、アプリがどこで動くか、データがどこにあるか、AI をどこで動かすかまで含めて**実際に機能しなければならない**」という考えです。

もう 1 つの軸は、**「ソブリンティは全員に同じものではない」**という点です。公開 Web サイトと国の医療インフラでは、必要な制御が違います。そのため、ワークロードごとに制御のレベルを選べるようにする、というのが Microsoft の方針として語られています。

そして、これを支えるのが「あとから変えられる」ことです。接続環境から非接続環境への移行（rehoming）や、小さく始めて大きくする拡張、AI やデータサービスの段階的な追加は、いずれもインフラを作り直さずに進められる、という点が繰り返し強調されています。

## 5. 発表内容の詳細

### 5.1 Microsoft のソブリンティへの考え方

登壇者は、課題が 1 つずつではなく、まとめて来ると述べています（「ミュートできないグループチャット」のようなもの、というたとえです）。規制の変化、サイバー脅威の増加、地政学的な不確実性があっても、アプリの稼働とイノベーションは続けなければなりません。だからソブリンティは、ポリシーや技術の話にとどまらず、義務を果たしながらデータと運用の主導権を持つという「信頼」の話になる、という説明です。

Microsoft はデジタルソブリンティを、**組織が安全に、かつ独立して運用できる力**と捉えています。考え方は次の 3 原則です。

1. ソブリンティは、誰もが使えるものでなければならない。
2. 強いガバナンスと制御に基づいていなければならない。
3. 制御のレベルは、ワークロードの必要性に合っていなければならない。

その選択を、次の 5 つの柱で整理しています。

1. Policy and governance
2. Sovereign AI
3. Cloud operator access restrictions
4. Data residency and confidentiality
5. Cloud resiliency and business continuity

登壇者は、これらを 5 つの別々の機能としてではなく、判断のたびに自問する 5 つの問いとして使うよう勧めています。問いは、データはどこにあるか、誰がアクセスできるか、誰がインフラを運用するか、AI を自分の境界の中で動かせるか、パブリッククラウドとの接続を失ったらどうなるか、の 5 つです。答えはワークロードによって異なり、パブリッククラウドで十分なものもあれば、ミッションクリティカルなものでは運用面でより高い独立性が必要になります。

これを受けて、Microsoft Sovereign Cloud の選択肢として次の 3 つが示されます。

- **Sovereign Public Cloud**：クラウドの規模とイノベーションに、データガバナンス、データ所在地、アクセス、セキュリティの制御を加えたもの。
- **Sovereign Private Cloud**：重要なワークロードを自社の拠点内で動かすためのもの。パブリッククラウドに接続して動かすことも、完全に非接続で動かすこともできます。
- **Sovereign partner ecosystem**：現地の専門知識や専門ソリューション、運用スキルを提供するパートナー。

これらは組織全体で 1 つを選ぶのではなく、ワークロードごとに使い分けられ、全体で「制御の連続体」になる、と説明されています。このセッションは、Sovereign Private Cloud に焦点を当てています。

### 5.2 Sovereign Private Cloud と Azure Local

Sovereign Private Cloud は、**Azure Local の上に作る完全なプライベートクラウドのスタック**として紹介されています。

- 土台の Azure Local が、仮想マシン、Kubernetes、独自の業務アプリを動かすインフラを提供します。
- その上に、AI 向けの Foundry Local、Microsoft 365 Local、GitHub Enterprise Local、そして生産性と開発者ワークフロー向けの Azure Virtual Desktop があります。
- データサービスとして、SQL Server、Blob Storage、DocumentDB があります。

段階的に採用できる点が強調されています。まずワークロードのモダナイズから始め、次にデータサービス、そして AI を追加します。最初からすべてを導入する必要はなく、サービスを追加してもインフラを変えずに済み、管理、セキュリティ、ガバナンスは一貫した Azure の体験のままです。

Azure Local の展開規模は、リモート拠点の 1 台のサーバーから、工場や小売店舗向けのクラスター、データセンター規模のマルチラックまで選べます。Azure に接続して運用することも、完全に非接続で運用することもできます。どの規模でも、初日から日々の管理まで同じ Azure の体験です。「どこまで大きくできますか」という質問には、「どれくらいの大きさが必要ですか」と答える、という話もありました。

### 5.3 rehoming：コントロールプレーンだけを移す

ソブリンティの会話でよく出る質問が、**接続や運用の要件が変わったらどうなるか**です。例えば、Azure Local を Azure から管理して順調に動かしているところに、新しい規制で独立した運用が必要になる、あるいは一部のワークロードを非接続の環境に移すことになる、といったケースです。従来こうした変更は大きな移行作業になっていた、と説明されています。

新しい **rehoming** は、Azure Local のインスタンスを、Azure 管理からローカル管理へ移す機能です。ワークロードやデータは動かさず、**動くのはコントロールプレーンだけ**です。

- 管理プレーンが切り替わる間も、仮想マシン、Kubernetes クラスター、アプリケーションは動き続けます。
- データのコピーも、アプリの作り直しも、インフラの移行作業も不要です。
- コントロールプレーンの移行が終わると、リソースはローカル管理側で使えるようになります。
- ID やアクセス構成は、移行に伴って引き継がれます。

登壇者は、接続された Azure から非接続の Azure への、シンプルな移行の仕組みであり、事業継続とソブリンティの考え方を変えるものだと位置づけています。

### 5.4 マルチテナンシー（プレビュー）

サービスプロバイダーや大企業が、複数の顧客や事業部門向けに、別々のインフラや管理体験を作らずにプライベートクラウドを運用する、という課題に対応する機能です。各顧客や事業部門を**テナント**と見ます。

発表で示された例は次のとおりです。

- オペレーターが「Europe West」でプライベートクラウドを運用している。
- テナント 1 は厳格な分離が必要なので、専用の、物理的に分離された Azure Local を割り当てる。
- テナント 2 と 3 は、ワークロードが論理的に分離されていればインフラを共有してよい。
- テナント 2 と 3 は、別拠点にまたがる耐障害性を高めたい。そこで「Europe East」という別の拠点を追加し、フェイルオーバー用の容量を割り当てる。
- Europe East に、テナント 4 を追加で受け入れることもできる。
- 各テナントは自分の ID とアクセス制御を持ち、オペレーターは集中管理できる。すべて 1 つの共有コントロールプレーンで動き、テナントごとの消費の状況が showback のために見える。

ポイントは、**分離は「全か無か」ではない**ということです。テナントごとに適切な分離レベルを選びながら、オペレーターが一元管理できます。

構成要素は、次の順で説明されました。

1. **コントロールプレーン**：接続・非接続のどちらでも、同じように動きます。
2. **private zone**：複数の Azure Local インスタンスの容量をまとめ、1 つのデプロイ先として見せます。
3. **capacity pool**：新しい概念です。テナントに、消費上限を強制した形でインフラへのアクセスを与えます。テナントは 1 つ以上の capacity pool を持ちます。pool は、オペレーターからテナント管理者への引き渡し点です。
4. **capacity slice**：テナントが pool の中で、アプリ担当者や部署向けに作ります。チームは、そのたびにオペレーターに依頼せず、VM や Kubernetes などのワークロードをセルフサービスで作れます。

オペレーターは、毎回テナント管理者に問い合わせずに、プライベートクラウド全体の制御を保てます。運用の集中・簡素化、テナント管理者の自立、サポート依頼の減少が利点として挙げられています。

### 5.5 confidential computing

保存時と転送時のデータ保護はすでに一般的ですが、**処理中のデータ**を保護するのが confidential compute です。

- Azure Local の **confidential VM** は、ハードウェアベースの trusted execution environment とメモリ暗号化で、使用中の機密データを保護します。
- **attestation** に対応し、機密のキーを渡す前に、環境が信頼できることを検証できます。
- Dell、HPE、Lenovo といったパートナーと協力して、solutions catalog 経由で提供する取り組みが進んでいます。
- AI ワークロードでは、CPU だけでなく GPU の保護も必要になります。NVIDIA と取り組む **confidential GPU** は、機密データで学習・ファインチューニングしたモデル自体にも知的財産が含まれるため、**データとモデルの両方**を保護します。

提供状況は、**confidential VM が一般提供（GA）、confidential GPU は近日提供**とされています。

### 5.6 GitHub Enterprise Local（GA）

ソースコードは最も価値の高い知的財産の 1 つであり、規制のある環境では、コードを境界の内側に置くことが機密データの保護と同じくらい重要になります。そこで、**GitHub Enterprise Local の一般提供開始**が発表されました。

- Azure Local の上に、セルフホストの GitHub 環境を動かせます。
- 開発者は、使い慣れたワークフローを使いながら、ローカルの運用ニーズと規制要件を満たせます。
- 導入を簡単にするため、検証済みのリファレンスアーキテクチャが用意されています。
- 規制のある環境、政府機関、非接続の環境でも、制御やソブリンティの要件を損なわずに、開発者に慣れたワークフローを提供することが目標です。

### 5.7 Foundry Local（GA）

規制のある環境では、AI について最初に出る質問は「データはどこへ行くのか」です。**Foundry Local は一般提供**になり、大規模な AI モデルを自社の Azure Local インフラで動かせます。推論はデータの近くでローカルに行われ、非接続環境でも動作します。AI の採用と機密情報の管理のどちらかを選ばなくてよい、という説明です。

構成要素と提供状況は次のとおりです。

| 構成要素 | 内容 | 状況 |
| --- | --- | --- |
| Models | Foundry カタログのモデル、または持ち込みのモデルを、ローカルのインフラで推論 | GA |
| Knowledge | 環境内のデータから AI アプリが情報を取得 | GA |
| Tools | AI アプリを、環境内の他のシステムやサービスにつなぐ | プレビュー |
| Agent services | ローカルで動く AI エージェントの構築と管理 | プレビュー |

これに、開発ワークフローを支える GitHub Enterprise Local、エッジに Azure の管理の一貫性をもたらす Azure Arc、下層のインフラを提供する Azure Local が加わります。まずモデルを動かしてローカル推論を始め、そこから knowledge と tools に広げる、というように、小さく始めて育てられる点が強調されています。

### 5.8 NVIDIA HGX B300 対応

AI ワークロードが大きくなり、複数の GPU にまたがる大規模推論が必要になる場合に向けた話です。Azure Local が **NVIDIA HGX B300 システム**に対応し、Foundry Local による大規模な AI 推論を、自社環境の中で実行できるようにします。データは自社の環境にとどまり、モデルは Foundry カタログのものでも持ち込みでもよく、小さな構成から始めて GPU の要件に合わせて拡張できます。

単に新しい GPU に対応するだけではなく、Azure Local、Foundry Local、NVIDIA HGX B300 システム、パートナーのエコシステムをまとめた、**検証済みの AI インフラストラクチャのソリューション**として提供するのが狙いです。AI 推論の基盤には、強力な GPU だけでなく、インフラ、ソフトウェア、デプロイツール、管理機能、セキュリティが必要であり、それらを統合する手間を減らすためとのことです。

- この構成に confidential computing も組み込む予定で、時期は 2027 年の上半期（first half of 2027）です。
- Dell、HP、Lenovo と協力して、検証済みのハイブリッド AI インフラ構成を提供します。ハードウェアは各社のものですが、土台は同じ Azure Local と Foundry Local、NVIDIA HGX B300 です。
- これらの構成は solutions catalog に、**premier tier** のソリューションとして掲載されます。

### 5.9 シナリオ動画：地域の医療ネットワーク

ここから Sydney に交代し、データの話に入ります。AI は、アクセスできるデータの範囲でしか役に立たず、そのデータが境界の外に出てしまうと、AI の価値が最も高い場面でソブリンティが失われる、という問題意識です。そこで、産業のシナリオを動画で見せています。

動画の内容は次のとおりです。

1. 舞台は、患者の転院を準備している地域の医療ネットワーク。「Caldova」（音声認識の都合で表記が確定できません）は、臨床医が患者の受け入れを調整する、転院ハブです。
2. この AI エージェントは Azure Local 上で動き、病院の業務データのすぐ隣にあります。
3. 病院の業務データは SQL Server にあり、AI は Foundry Local が直接もたらします。機密性の高い患者情報は、インテリジェンスを求めて外に出る必要がありません。モデルとアプリは Azure Local 上で動き、患者データは、Azure に接続された状態のまま病院の管理下の環境にとどまります。
4. 起動の時点から信頼できる必要があるとして、trusted launch、secure boot、virtual TPM、integrity attestation、保存時の暗号化という、インフラからデータまで重ねたセキュリティが挙げられます。
5. 大規模な障害でクラウドとの接続が切れた場合、病院ではケアを止められません。クラウド上のモデルから、完全に非接続の Foundry Local のモデルに切り替えられ、使い勝手は変わりません。モデルが非接続環境の中だけで動くので、プロンプト、スキーマ、アプリのコンテキストは境界の外に出ません。
6. 動画の結びは、「ソブリン AI はソブリンなデータから始まる」というものです。

### 5.10 データサービス

**SQL Server on Azure Local**：自社が制御するインフラ（ソブリンな拠点でも、完全に非接続の場所でも）で、ミッションクリティカルな SQL Server を動かせます。メッセージは「**モダナイズせよ、ただし移行する必要はない**」です。既存のエンタープライズデータをそのままにして、周囲に Copilot やローカルの AI エージェントを加えます。

- 開発者は、Foundry Local を使った GitHub Copilot の体験を使えます。
- ローカルのエージェントが、SQL のエンタープライズデータに、その場所のままアクセスできます。
- セキュリティ面は、trusted launch、RBAC、暗号化、SQL Server audit。
- いずれも、大規模な移行を必要としません。

**Blob Storage on Azure Local（プレビュー）**：Azure と一貫したオブジェクトストアを、自社環境に持ち込みます。非構造化データは急増し、AI に与えるデータになることも多いため、Azure Blob Storage のように動くオブジェクトストアをローカルで持てるようにする、という位置づけです。

1. Azure と同じように、ストレージアカウントとコンテナーを作成する。
2. アプリは、Azure と一貫した API で、ローカルの Blob エンドポイントに接続し、データを保存・取得する。
3. Blob サービスは Azure Local 上で動き、下層のストレージ（S2D または SAN）を使う。サービスもデータも完全にローカルにとどまる。

**DocumentDB on Azure Local（プレビュー）**：ドキュメント形式（JSON）でデータを保存する最近のアプリ向けのローカルな置き場所です。RAG エージェントなど、グラウンディングする AI のシナリオで、データを AI の近くに置けます。MongoDB 互換のワークロードに対応し、**オープンソースの PostgreSQL ベースのドキュメントデータベース**を、Kubernetes ネイティブのオペレーターで管理する、と説明されています。

### 5.11 アプリを Azure から Azure Local へ移す道筋

すでに Azure で動いているアプリが、再構築なしにソブリンやエッジの拠点へ移せるかどうか、という実務的な問いに対し、次の 3 ステップが示されました。

1. **調査**：sovereign landing zone のもとで Azure Policy を使い、アプリが Azure 専用のサービスに依存している箇所を見つける。Azure Local で動くもの・動かないものが分かる。
2. **適応と検証**：規範的なガイダンスに従い、必要に応じてアプリを調整し、正しく動くことを検証する。
3. **移行**：検証済みのワークロードを、計画した切り替え期間に移す。

結果として、切り替えの日に想定外が起きにくく、推測を証拠に置き換えられます。このプロセスは繰り返し使え、すべてのワークロードに同じ道筋を適用できる、という説明です。

### 5.12 パートナーエコシステム

Azure Local の 1 つのデプロイには、ハードウェア、ソフトウェア、セキュリティ、ネットワークなど幅広い専門性が必要で、ソブリンや規制環境では要求がさらに高まります。そこで、現地での導入力と実績あるベストプラクティスを持つパートナーが重要になる、という話です。

- **Hybrid and sovereign private cloud specialization**：Azure Local の導入に実績のあるパートナーを見つけるための認定です。Azure Local をエンドツーエンドで対象とし、自己申告ではなく**証拠**で基準を設けています。パートナーは、Azure の Microsoft solutions partner の指定を持つこと、複数の顧客で稼働中の Azure Local の導入を示すこと、認定を受けた Azure アーキテクトを雇用していること、最近の顧客案件について第三者の独立した監査に合格することが必要です。
- 現時点で **10 社**が認定を取得しており、今後も Azure Local の学習パスやハンズオン教材とあわせて拡大する予定です。
- **Validated solutions**：Azure Local で検証済みのパートナーソリューションを、用途別にまとめたものです。すでに信頼しているツールを、ソブリンな環境に持ち込めるようにします。
- **Platform co-innovation partners**：Azure Local を共に作るシリコン、サーバー、ストレージの企業で、GPU からストレージまでのソリューションがあります。

### 5.13 お客様事例：Golden Gate Bridge Highway & Transportation District

最初に動画が流れ、その後、Matt へのインタビューが行われます。

**動画で語られた内容**

- 160 台のバス、7 隻のフェリー、料金所、Golden Gate Bridge を運営しており、事業は 24 時間 365 日止まらない。
- 以前は、複数のベンダー、契約、知識・スキルセットが必要で、維持が難しかった。支えるチームは非常に小さい。
- SaaS で動かせるアプリも多いが、データの置き場所が重要であり、選定に影響した。

- 移行は、利用者にも一般の人にも気付かれずにシームレスに行え、停止もなかった。
- Bay Area で何かあったときもサービスを提供したいため、ASR（Azure Site Recovery）が唯一の方法だと考えている。AI も新しい可能性の 1 つ。

**Matt へのインタビュー**

## 7. 注意点・発表者の気付き

- **提供状況がばらばらです。** 一般提供：GitHub Enterprise Local、Foundry Local の Models と Knowledge、confidential VM。プレビュー：マルチテナンシー、Foundry Local の Tools と Agent services、Blob Storage on Azure Local、DocumentDB on Azure Local。近日提供：confidential GPU、NVIDIA HGX B300 構成への confidential computing の組み込み（2027 年上半期）。
- **移行の教訓**（Matt）：VMware からの移行は、複数回のやり直しがあり、一番大変なのは planning だった。助言は「test first, test again, test one more time」。
- **導入までの経緯**：Matt は、3 年前に同じことを頼まれたら「やらない」と答えていたが、今の Azure Local は良い状態で、毎月良くなっていると述べています。

## 8. 利用者にとっての利点

発表で語られた内容に限ると、次のとおりです。

- 制御のレベルをワークロードごとに選べ、接続と非接続の間を、データを動かさずに移れる（rehoming）。
- 小さく始めて、規模、AI、データサービスを、インフラを変えずに追加できる。
- 処理中のデータやモデル、ソースコード、AI 推論を、自社の境界内に置ける。
- 検証済みのパートナー構成と、移行の 3 ステップにより、導入の不確実性を減らせる。
- 事例（Golden Gate Bridge Highway & Transportation District）では、複数ベンダーの管理から単一の基盤になったこと、停止時間なしのパッチ適用、利用者に気付かれない移行、約 150 VM の移行、パッチ管理の手間の削減が挙げられました。バックアップはローカルに取ったうえで Azure のクラウドへレプリケートしており、災害復旧の ASR は設定とテストを始めた段階です。

> 補足：事例の数値は、動画と Matt、Meena の発言によるものです。それ以外の定量的な効果（コスト削減率など）は紹介されていません。

## 9. まとめ

Microsoft は、ソブリンティを「全員に同じもの」ではなく、ワークロードに応じて選ぶものと位置づけ、Sovereign Private Cloud を Azure Local 上の完全なスタックとして示しました。新機能は、rehoming、マルチテナンシー、confidential VM / GPU、GitHub Enterprise Local、Foundry Local、HGX B300 対応、そして SQL Server・Blob Storage・DocumentDB のローカル提供です。

Golden Gate Bridge Highway & Transportation District の事例は、ローカルでしか動かせないアプリを抱えながら、Azure Arc でクラウドとつなぐ「ローカルとクラウドの両立」と、VMware からの 3 年がかりの移行を、実体験として示しています。
