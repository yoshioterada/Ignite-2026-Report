# BRK409 Modernize faster with AI-powered discovery, planning, and execution

## 1. はじめに

このセッションは、オンプレミスのシステムをクラウドに移行・モダナイズする IT リーダーやアーキテクト、開発者に向けた発表です。Microsoft は、探索（discovery）、提案、計画、実行を 1 つにつなげた体験として **Azure Catalyst** を発表しました。発表者は、移行がこれまで「ツールごとの受け渡し」の連続で、受け渡しのたびに文脈が失われてきたと指摘します。その課題に対し、AI エージェントが探索から実行までを 1 本の流れでつなぐ、というのが発表の骨子です。

構成は、英国の銀行 Aldermore の CTO による移行事例、Azure Catalyst の新機能の紹介、架空のシナリオ（Caldova Pharma）でのデモ、無償の支援プログラム Cloud Acceleration Factory、そして多くの質疑応答です。質疑応答では、Terraform の扱い、アプライアンスの権限、GovCloud、Brownfield、他クラウドからの移行など、実務に直結する質問への回答が出ています。

> 補足：セッションのタイトルとメタデータの概要では「Azure Copilot Migration Agent」という名称が使われています。一方、トランスクリプトでは発表者が一貫して **Azure Catalyst** と呼んでいます。本書ではトランスクリプトの呼称に合わせます。

1. 問題提起: 移行の「中間の長い道のり」は、熟練した人手、手作業の探索、スプレッドシートでの依存関係管理、使い捨てのスクリプトに頼っていた。

発表者は、**エージェントが作業を進めても、判断するのは人**である、という点を繰り返し強調しています。「Assisted. Your people are still taking the calls.」という言い回しや、後述の「チョークで印を付ける」たとえ話で、エージェントはあくまで支援役で、人が計画のレビュー、修正、承認、実行の判断を行う、という立場が示されています。

## 4. 発表者が伝えたいメッセージ

発表の最後に、次の 3 点が示されました。

1. 技術的負債が、AI 導入の計画を遅らせている。
2. エージェントが、それを直すために必要な作業量とコストを変える。
3. 自分たちだけで抱え込む必要はない（Microsoft の支援プログラムがある）。

また、「1 つの旅であり、積み重なった受け渡しではない」という整理もありました。環境の把握が判断を形づくり、判断が計画を形づくり、計画がそのまま実行に持ち越される、という流れです。インフラ、アプリ、データベースを 1 つの体験で扱い、組織のセキュリティや耐障害性の要件に合わせて調整でき、**自分たちの優先順位で、大規模に進められる**（AI の導入を進めるのは顧客側で、Microsoft の優先順位ではない）と述べています。

## 5. 発表内容の詳細

### 5.1 問題提起: 移行の「中間」が難しい

冒頭、発表者は会場に「移行がうまくいかないとき電話がかかってくる人」と「移行予算の承認権を持つ人」を挙手で尋ねています。続いて、目的地について迷う人はいないはずで、問題は「中間」の道のりにあると述べました。

- 探索は手作業である。
- 依存関係はスプレッドシートで管理されることが多い。
- 一度しか動かない、壊れやすいスクリプトがある。
- これらを進めるには、多くの熟練した人材が必要になる。

モダナイズのビジネスケース自体は大きく変わっておらず、変わったのは**作業にかかるコストと労力**だとしています。探索、計画、コード変換、移行、テストの各ステップを、AI エージェントが支援できるようになりました。

### 5.2 事例: Aldermore Bank（英国）

Gabriel Pepe 氏（CTO）は、まず自社を紹介しました。Aldermore は英国の専門特化型の銀行で、4 つの主要事業があります。

| 事業 | 内容 |
| --- | --- |
| Property | 住宅所有者と不動産投資家向けのモーゲージ商品（Mortonova ブランドを含む） |
| Motor Finance | ディーラーネットワーク経由での車両購入の資金提供 |
| Business Finance | 中小企業向けの運転資金と資産の資金提供 |
| Savings | 貯蓄商品の提供。グループ全体の資金調達の源泉 |

**移行の背景**

数年前に、レガシーなテクノロジーから出る必要があると判断しました。理由は次のとおりです。

- 商用モデルが合わなくなっていた。物理資産をデータセンターに調達・導入するのに多額の費用がかかっていた。
- ビジネス側から、より柔軟で俊敏であることへの期待が高まっていた。
- 規制環境が変わり、オペレーショナル・レジリエンス（運用の耐障害性）への期待が高くなっていた。

サービスは 8 つのデータセンターに分散しており、これを統合する計画でした。その中でデータプラットフォームは、オンプレミスのアーキテクチャで、物理的な容量に縛られ、運用が複雑で、ピーク時の需要に対応する柔軟性もありませんでした。報告はすべて時間に制約があり、障害から復旧するのも容易ではなかったため、事業への影響は大きかった、と述べています。事業の重要なレポートや規制当局向けのレポートが、このデータプラットフォームに依存していたためです。

**規模と課題**

- 100 TB を超えるデータ
- 日々、さまざまな基幹システムから約 55 のデータフィード
- 数百の業務上重要なレポートと、規制当局向けのレポート
- ドキュメントに多くの欠落があった（「レガシーとドキュメントは相性が悪い」と表現）

発表では、最初のフェーズである**探索と設計**が、プロジェクトのクリティカルパスだったと述べています。もうひとつの重要なフェーズは**テスト**で、手作業のテストには多くの時間がかかり、実際の現場では何かを見落としてしまっていた、とのことです。

**使ったツールと成果**

| 工程 | 使ったもの | 語られた成果 |
| --- | --- | --- |
| 探索とアセスメント | Azure Migrate | 6〜7 か月の予定が 2 週間に短縮 |
| データ移行 | Azure Storage Mover | 100 TB のデータを、実データでのテスト、耐障害性テスト、本番切り替えの日と、数回にわたって移動 |
| 耐障害性テスト | Chaos Studio | 知らなかった問題点を複数発見し、それをカバーできるように環境を再設計。「プロジェクトで最もエキサイティングな部分」と表現 |

**得られた効果**

1. **柔軟性**: 四半期末や年度末などのピークに合わせて、コンピュート、ストレージなどの容量を拡張し、不要になったら縮小できる。
2. **復旧力**: 毎日 50〜60 件ほどのデータフィードがそろわないと夜間バッチを始められない。以前は、バッチがほぼ締め切りぎりぎりで終わり、復旧の余裕がなかった。現在はバッチが 2〜3 時間早く終わり、問題があっても復旧してレポートを期限に間に合わせられる。**Azure に移行してから、期限を 1 度も逃していない**、と述べています。
3. **チームの変化**: インフラの障害対応に追われるのではなく、ビジネス価値の提供に集中できるようになった。チームの士気にも良い影響がある。

Pepe 氏は、Azure への移行は「データセンターから別のデータセンターへの引っ越し」ではなく、レジリエントでスケーラブルな、現代的な技術基盤を作ることだった、と締めくくりました。

### 5.3 市場の数字: 技術的負債は 3 つの予算に影響する

進行役は、Aldermore の話は特別な例ではなく「普通のこと」だとして、IT リーダーの調査結果を示しました。

- 70%: セキュリティのために、すべて、またはほとんどのアプリをモダナイズする必要がある
- 75%: イノベーションのボトルネックを解消するために、モダナイズが必要
- 64%: 運用コストのために、モダナイズが必要

セキュリティ、プロダクト、財務の 3 つの予算に、技術的負債が同時に影響する、という整理です。過去を延命するために使われる 1 ドルと開発者の 1 時間は、モダナイズに回らず、結果として AI の価値も実現できない、と述べています。

現在の移行は一連の受け渡しです。あるツールが探索し、アセスメントはスプレッドシートに残り、コンサルタントが計画を支援し、別の誰かが実行します。受け渡しのたびに文脈が失われます。

### 5.4 Azure Catalyst の発表

Azure Catalyst は、**探索から計画、実行までを、インフラ、アプリ、データベースにわたってつなぐ 1 つの体験**として発表されました。IT は Azure 上で、開発者は GitHub Copilot で作業しながら、同じ 1 つの計画で動けます。計画は自社の事業、標準、ルール、ポリシーに合わせてカスタマイズでき、強制もできます。エージェントは、そのルールの「外ではなく内側」で動作する、と説明されています。

> 補足：質疑応答で、Azure Migrate と GitHub Copilot の app mode は、どちらも Azure Catalyst に統合された、と回答されています。

**探索（Discover）と判断の新機能**

- **CMDB と observability データの取り込み**に対応。従来から取り込んでいる VMware、Hyper-V、物理環境のデータに加えて使える。
- AI エージェントが依存関係を追跡し、アプリケーションを見つけて、そのアプリを動かしているサーバーをグループ化する。「移すのは個々のサーバーではなく、アプリケーションだから」という説明です。
- **Azure Value Uplift** という新機能。リフト・アンド・シフトとモダナイズのどちらを選ぶか判断する際、コスト削減だけでなく、**レジリエンシー、アジリティ、生産性**を並べて比較できる。発表者は「コスト削減はプロジェクトの承認に役立ち、Azure Value Uplift は優先順位付けに役立つ」と述べています。
- 対象ワークロードの拡大。サーバーと SQL に加え、Oracle、OSS データベース、コンテナー、ネットワーク、ストレージなどが追加された（一覧は長いので省略、と発表者）。アプリを効率よく動かすための多くのマネージドサービスも含まれる。

その結果、ステークホルダーの承認を得る提案書の作成は、数週間から数か月かかっていたものが、**ボタン 1 つで可能**になるとしています。TCO、削減額、モダナイズ戦略の推奨、設計、ウェーブ（wave）、データ資産全体のセキュリティ分析が得られます。

**計画（Plan）の特徴**

計画の難しさを表すたとえ話として、発表者は次の逸話を紹介しました。ヘンリー・フォードの工場で発電機が故障し、エンジニアが原因を突き止められず、電気工学の専門家 Charles Stemis 氏（音声認識の表記）を呼びました。氏は 2 日間発電機を見つめ、チョークで 1 か所に印を付け、そこが故障箇所でした。請求は 10,000 ドルでした。フォードが明細を求めると、「チョークで印を付けるのが 1 ドル、どこに付けるかを知っているのが 9,999 ドル」という内訳でした。

発表者はこれを、ランディングゾーンやプラットフォームのデプロイは「チョークで印を付ける」作業で、**どの設計が自社のアプリや組織に合うかを知っていること**が高価だ、と結びつけます。Azure Catalyst はその「知っていること」を裏側に持っています。

- エージェントは、**700 以上のアーキテクチャのブループリントから作られたナレッジグラフ**の上に構築されている。
- 人のアーキテクトは、AI エンジンの助けを借りて、自社のセキュリティや耐障害性の要件に合わせて調整できる。
- AI エンジンは、アプリケーションとサーバーの依存関係を特定し、デプロイの順序を決める。アプリの重要度、複雑さ、依存関係が考慮される。依存関係を 1 つ見落とすと、週末の切り替え計画が障害になりうる、と発表者は説明しています。

エージェントが印を付け、人が判断する、という構図です。人はレビュー、修正、承認を常に行います（「100% of the time」）。

**実行（Execute）の新機能**

- **ネットワークとストレージのモダナイズ**に対応した。従来から対応しているサーバーのデプロイに加えての追加。発表者は、競合のような単純な同等移行（like to like）ではなく、モダナイズの推奨を理解したうえで、オンプレミスのネットワークを、ファイアウォールルールやネットワークセキュリティ構成を含めて、ターゲットのサービスに変換する、と説明しています。
- **SQL モダナイズを大規模に**実行する機能が追加された。データベースのためにツールを渡り歩く必要がなく、Catalyst に組み込まれている。今後も、この自動化ワークフローの対象ワークロードを追加する予定です。
- **Catalyst と GitHub Copilot で、アプリとデータベースを一緒にアセスメント**できるようになった。現在は **プレビュー**。開発者は、今までの場所で作業を続けながら、IT が見ているものと同じ視点で見られる、と述べています。
- **Rulebook 機能が GA（一般提供）**。承認済みパッケージ、禁止パターン、コーディング標準、命名規則などをコード化して強制できる。エージェントが印を付け、ルールが何を行うかを決める、という説明です。

### 5.5 Cloud Acceleration Factory と顧客成果

ツールの次は、プログラムの紹介でした。優れたエンジニアや開発者はすでに別の仕事で手一杯だという前提で、**Cloud Acceleration Factory**（Frontier Accelerate の一部）が、Microsoft の専門家を顧客のそばに配置する、と説明されています。

- 30 以上のサービス（セキュリティ、AI、ビジネスソリューションを含む）。
- **無償**。Charles Stemis 氏のような請求書は発行されないと発表者は述べています。
- 実績: 7,000 以上の顧客、20,000 以上のエンゲージメント、8 million 以上のコアをモダナイズ。
- 対象はサーバーのリフト・アンド・シフトだけでなく、アプリとデータベースの PaaS へのモダナイズ、AI エージェントの本番化、セキュリティとアナリティクスのサービスまで。6 つのワークロード領域がある。

**顧客事例**

| 顧客 | 語られた成果 |
| --- | --- |
| Temenos | 30 TB の SQL 基盤のコアバンキングアプリを、プライベートクラウドから Azure に、事業の中断なしに移行。Cloud Acceleration Factory と Azure Catalyst を使用。CAF の専門家が、ランブック、Infrastructure as Code のテンプレート、標準化された VM イメージを資産として残した。最初の移行が最も難しく、以降はテンプレート化すべき、という考え。 |
| Delmont Foods | 主要アプリを 3 か月未満でモダナイズ（「Faster」の例） |
| Aldermore | 100 TB で、規制当局向けレポートの所要時間が 1 日あたり 2 時間以上短縮（「Performance」の例） |
| Levi Strauss | 基幹システムをモダナイズし、1,000 以上のエージェントを展開（「AI」の例） |

> 補足：発表者は、Temenos、Delmont Foods、Levi Strauss の詳細（使った機能など）には触れていません。

### 5.6 Q&A

質疑応答では、次のやり取りがありました。

**設計の制約（使う技術の指定）**
- 質問: Kubernetes のような使えない技術を提案されたとき、「この技術の専門家しかいない」と制約を指定できるか。
- 回答: 設定で好みを指定できる（例: App Service、または App Service のコンテナーのみをターゲットにする）。設計はそれに合わせて調整される。今日の時点で可能であり、デモで見せた機能はすべて試せる。

**Azure Migrate との関係**
- 質問: Azure Catalyst は Azure Migrate の後継か、並行する製品か。
- 回答: Azure Migrate と GitHub Copilot の app mode は、どちらも Azure Catalyst に統合された。

**Terraform**
- 質問: 事前定義した Terraform ベースのインフラに移行できるか。移行後に環境を壊して作り直し、Terraform の state に取り込む手間が大きい。
- 回答: Terraform のテンプレートをそのまま生成する。デモで見せた設計が出来たら、すべての Terraform テンプレートをダウンロードしてカスタマイズでき、帯域外（out of band）でデプロイもできる。
- 追加質問: カスタマイズしたものを再アップロードできるか。回答: まだ無いが、近いうちに追加する。会話形式で変更できる vibe editing のサポートも検討しており、設計を変更して再アップロードすることもできるようになる予定。

**計画を作る仕組み（LLM）**
- 質問: 計画は LLM が書くのか。どの LLM か。
- 回答: 両方の組み合わせ。700 以上のテンプレートから作られたナレッジグラフを使って構成するので、**大部分は決定論的**。ユーザーの意図やターゲットサービスの好みを受け取って反映する部分に AI を使い、クラウド設計のテンプレートとして提示する。どの LLM かは、発表では回答されていません。
- 追加質問: 複数の候補からどう選ぶか。回答: 推奨のターゲットがアセスメントのライトサイジングで選ばれ、その推奨ターゲットについてナレッジグラフをたどり、トポロジーを特定してアーキテクチャ図にまとめる。
- 追加質問: なぜその選択かを説明できるか。回答: アセスメントにはある程度の説明可能性がある。今後は「なぜこれで、あれではないか」と問い合わせできる推論の説明を拡充する予定で、現時点では提供されていない。

**データベースの標準化（Oracle など）**
- 質問: Oracle、SQL Server、Postgres が混在する大学で、Oracle から別のデータベースへ、開発側の接続を保ったまま移せるか。
- 回答: Catalyst と GitHub で、Oracle データベースのスキーマ変更とデータベースコードの変換（例: PostgreSQL へ）を支援する。Oracle から Postgres、Sybase から SQL などの標準的な構成に対応している。「ある程度は今日可能で、組み合わせは今後追加される」。

**既存のクラウドアプリのモダナイズ**
- 質問: オンプレミスだけでなく、既存のクラウドアプリにも使えるか。
- 回答: Azure 上で動くアプリのコードに対しては、Catalyst と GitHub（GitHub Copilot）で、モダナイズの推奨を得られる。インフラ側は、VMware、Hyper-V、物理などの標準構成に対応しているが、Azure 環境を物理環境として扱う方法もある。

**GovCloud**
- 回答: 一部のバージョンは利用可能だが、最新のものはまだ。機能はまずパブリッククラウドで提供され、他のクラウドには後から展開される。

**アセスメントの取り込み方法とアプライアンス**
- 質問: 内部で Azure Migrate を使うなら、これまでどおり OVA をハイパーバイザーに配置する必要があるのか。
- 回答: データの取り込みには複数の方法がある。Migrate アプライアンス（現在は Catalyst アプライアンス）のほか、RVTools のエクスポート、CMDB データ（デモの ServiceNow のエクスポートなど）、observability ツールのデータ。アプライアンスが必要になるのは、サーバーを実際に移行するときのみ。それも、生成された Infrastructure as Code のテンプレートを使えば、GitHub Actions や Azure DevOps パイプラインなどの標準的な CI/CD でリソースを作成できる。

**社内利用**
- 質問: Microsoft の社内のアセスメントチームも Catalyst を標準にするのか。
- 回答: 社内のプログラムは、Catalyst に標準化していく。

**コードにアクセスできない場合の深いアセスメント**
- 質問: アプリケーションのリポジトリにアクセスできない場合、どう選択肢を提示するのか。
- 回答: Catalyst には 2 つの部分がある。1 つは従来の Azure Migrate が行っていたインフラ側（接続またはデータのアップロード、SKU のライトサイジング、ターゲットの推奨）。もう 1 つは GitHub Copilot 上の Catalyst によるコード分析。リポジトリのパスを複数渡せる CLI があり、VS Code に戻るか modernize CLI でリポジトリを指定すると、コード全体をアセスメントして推奨を出せる。将来は、Catalyst のブラウザ上で大規模にオーケストレーションできるようにする予定。リポジトリにアクセスできない場合の方法は、質問に対して直接は回答されていません。

**依存関係の取得（アプライアンスを使わない場合）と権限**
- 回答: **コレクター（collector）**というオフライン探索ツールがある。オンプレミスにローカルで配置し、ネットワークトレースなどから依存関係を取得でき、Azure への接続は不要。New Relic や Dynatrace のような observability ツールにも依存関係情報があり、それも取り込める。
- 質問: アプライアンスはドメイン管理者権限や Linux の sudo 権限が必要で、規制の厳しい企業では使いにくい。コレクターも同じか。
- 回答: アプライアンスもコレクターも、権限を減らす改善を重ねてきた。最新のドキュメントには、最小の権限から始めて段階的に付与するレベルが書かれている。付与した権限に応じて、取得できるデータの精度が変わる（例: プロセス名やポート番号は取得できないが、2 つのマシン間の接続はわかる）。リモートで取得するには WinRM や SSH が必要だが、それが難しい場合は、Ansible やグループポリシーなどの既存の自動化でマシン上でスクリプトを実行してデータを集め、取り込めば、権限は不要になる。CMDB に依存関係情報があれば、エクスポートを取り込むだけで始められる。ここ 6 か月から 1 年ほどで多くの改善を行ったので、確認してフィードバックしてほしい、と述べています。

**Brownfield**
- 回答: 現在のランディングゾーンの推奨は Greenfield 向け。Brownfield は次に対応する。7 章の進め方を参照。

**AWS / GCP からの移行**
- 質問: AWS や GCP の環境のアセスメントに使えるか。
- 回答: 直接の対応はしていないが、物理環境として扱えば対応できる（物理構成はサポート済み）。クロスクラウドの顧客の要望は認識しており、検討している。

## 6. デモ・手順

デモは Swati が担当しました。架空の製薬会社「Caldova Pharma」のクラウドアーキテクトという設定で、探索、提案、計画、実行の 4 段階を順に見せています。画面の細部（ボタン名やレイアウト）は音声からは分かりません。以下は語られた内容を、順に整理したものです。

> 注意：冒頭では「ライブでお見せする」と紹介されていますが、質疑応答の中に「動画で見たデザイン（the video）」という発言もあり、録画だった可能性があります。音声からは断定できません。

### 6.1 探索から提案書まで

1. 自社のモダナイズの目標を Catalyst のエージェントに伝える。エージェントがすぐにモダナイズの道筋を作り始め、既存環境を把握するための選択肢を提示する。
2. すでに持っている構成データ（ServiceNow の CMDB レポートを含む）を、ゼロから始めずにそのままアップロードする。
3. Catalyst が AI で環境全体をマッピングする。特定したワークロード間の依存関係を分析する画面もある。
4. ワークロードを、利用可能なヒューリスティクスでアプリケーションに自動でグループ化し、ビジネス上の重要度と複雑さのラベルを付ける。以前は、スプレッドシートや分断されたツールで数週間かかった作業が、数分になった、と述べています。
5. 経営陣に ROI を説明するため、提案書をダウンロードする。提案書の内容は次の順です。
   - Azure に移行するビジネスケース
   - アプリケーションの準備状況（readiness）
   - ターゲットサービスのマッピング
   - 既存環境で注意すべきセキュリティ脆弱性
   - ウェーブに分けた、推奨のモダナイズ戦略
6. この包括的なレポートが、リーダーシップからプロジェクトの承認を得る助けになった、と述べています。

### 6.2 計画

1. **プラットフォームのランディングゾーン**: 現在の環境の知識と目標に基づき、Catalyst が推奨のランディングゾーンを生成する。設計は Microsoft の CAF と WAF の原則（クラウド基盤のベストプラクティス）に従い、ネットワーク、セキュリティ、管理、ID、コンプライアンスをまとめて扱い、耐障害性の要件に合わせて最適化する。承認前に、要件に合わせて調整することもできる。
2. **アプリケーション単位の設計**: アプリケーションオーナーを巻き込み、アプリごとにモダナイズ向けのアーキテクチャを生成する。700 以上のリファレンスアーキテクチャのカタログに基づくナレッジグラフが根拠になっている。
   - **Caldova Asset Manager**（トランスクリプトでは「Caldo YSIP Manager」とも聞こえます）: Web 層に Azure App Service、データ層に Azure SQL Database Hyperscale Elastic Pool、ファイル共有に Azure Files を中核のターゲットとして推奨。そのほか、組織のポリシーに沿った必要なサービスも含まれる。事業にとって重要なアプリなので、アプリのプロパティをそれに合わせて設定すると、設計が即座に更新され、より高いパフォーマンスのために Azure managed readers（音声認識の都合で表記が確定できません）が追加された。従来は、コンサルタント主導の複数回のワークショップが必要だった、と述べています。
   - **Caldova Clinical Ops**: Java と Oracle DB を使う多層アプリ。Web 層は Azure Kubernetes のクラスターへのコンテナー化、データ層は Azure Database for PostgreSQL Flexible Server を推奨。
3. **ウェーブ計画**: 実行の前に、アプリとワークロードを、依存関係、準備状況、重要度、移行の労力に基づいて順序付けしたウェーブに分ける。Asset Manager は、SQL Server がサポート終了に近づいてセキュリティ上のリスクになっているため、第 1 ウェーブに入った。計画をレビューして確定（commit）し、インフラチームとアプリチームを同じウェーブ計画に合わせ、実行状況を 1 つの体験で追跡する。

### 6.3 実行

1. 実行は 1 つの共有ビューで、前の段階で確定したウェーブの順に始める。実行計画には、アプリのスコープに含まれる各ワークロードの移行ステップが並ぶ。
2. データベースの移行を開始するために、必要なパラメータ（サブスクリプション ID、デプロイのリージョン、リソースグループ）を確認・更新する。
3. 更新したパラメータを保存すると、データ同期が始まる。データベースとファイル共有の実行状況は、1 つのビューで追跡する。
4. その間にアプリケーションオーナーは、GitHub Copilot 上の Azure Catalyst で作業を続ける。実際のコードの依存関係と構成を分析し、ターゲットの Azure アーキテクチャに移るために必要な変更を特定する。コードのアセスメントにとどまらず、フレームワークのアップグレード、クラウド構成の更新、セキュリティ問題への対応など、モダナイズの変更も支援する。
5. Asset Manager の場合は、.NET アプリを Azure App Service で動かせるようにモダナイズする。同時に、rulebook を通してガバナンスのポリシーを適用する（例: Azure Key Vault によるシークレットの安全な管理）。
6. 開発者は、実際のコード変更を確認し、ビルドを検証し、テストをすべて実行して、Azure へのデプロイに向けてモダナイズしたアプリを準備する。
7. アプリが検証され、Azure 上で動作している状態になった。デモでは、探索の知見が、アーキテクチャの判断、ウェーブ計画、インフラ・データベース・アプリのチームの連携した実行に結びつく点を価値として強調している。

## 7. 注意点・発表者の気付き

- **人が判断する**: エージェントは支援役で、レビュー、修正、承認、実行の判断は人が行う、と繰り返し強調されています。
- **Brownfield は未対応（ランディングゾーン）**: ランディングゾーンの推奨は、現時点では Greenfield のみです。Brownfield は次に取り組むと回答されています。既存の Azure 環境がある場合、発表者は、新規ワークロードには推奨のランディングゾーンを使い、既存アプリについては戦略、SKU、サイジング、コスト、効果の推奨を使う進め方を「妥当」としています。
- **GovCloud**: 一部のバージョンは利用可能だが、デモで見せた最新の機能は利用できない。機能はまずパブリッククラウドで提供され、他のクラウドには後から展開される。
- **提供済みの機能と未提供の機能**: Terraform テンプレートの再アップロードや、会話形式の編集（「vibe editing」）、判断理由の説明の拡充は、「まだ無いが近日」と説明されています（5.6 の Q&A を参照）。
- **権限の扱い**: アプライアンスやコレクターに必要な権限は大幅に改善され、権限のレベルに応じて取得できるデータの精度（fidelity）が変わる。「セキュアでない裏口はない」と説明されています。
- **ドキュメントの確認**: 質問者が引用した権限要件（ドメイン管理者権限など）について、発表者側は「古い情報を見ているのではないか」と述べ、最新のドキュメントを参照するよう案内しました。
- **プレビューの機能**: Catalyst と GitHub Copilot のアプリ・データベース同時アセスメントは**プレビュー**です。

## 8. 利用者にとっての利点

発表で語られた利点と成果は次のとおりです。

- 探索とアセスメントの期間が、6〜7 か月の予定から 2 週間に短縮（Aldermore）。
- 提案書の作成が、数週間から数か月かかっていたものから、ボタン 1 つへ。デモでは、手作業で数週間かかっていた分析が数分になった、と説明されている。
- Aldermore: 必要に応じて容量を拡張・縮小でき、バッチが 2〜3 時間早く終わり、移行後に規制報告の期限を 1 度も逃していない。チームは障害対応からビジネス価値の提供に移れた。
- Temenos: 30 TB の SQL コアバンキングを、事業を止めずに Azure に移行し、ランブックや IaC テンプレートなどが資産として残った。
- Delmont Foods: 主要アプリを 3 か月未満でモダナイズ。Levi Strauss: 1,000 以上のエージェントを展開。
- Cloud Acceleration Factory は無償で、30 以上のサービスを提供する。発表者は、これを「雇わなくても使えるデプロイの体制（deployment capacity you don't have to hire）」と表現しています。
- アセスメント、設計、計画、実行を 1 つのツール（Azure Catalyst）で扱えるため、受け渡しのたびに文脈を失う、という従来の課題に対する答えとして位置づけられています。

## 9. まとめ

Azure Catalyst は、探索、提案、計画、実行を、インフラ、アプリ、データベースにわたって 1 つにつなぐ体験として発表されました。CMDB・observability データの取り込み、Azure Value Uplift、ネットワーク・ストレージ・SQL のモダナイズ実行、アプリ・データベースの同時アセスメント（プレビュー）、Rulebook（GA）が新機能として挙げられています。設計は 700 以上のアーキテクチャのナレッジグラフに基づき、エージェントが作業を進めても、判断と承認は人が行います。

Aldermore の事例では、探索の期間短縮、容量の柔軟性、復旧力の向上、規制報告の期限遵守が成果として語られました。質疑応答では、Terraform、権限、GovCloud、Brownfield、他クラウドといった実務的な論点について、対応済みの範囲と今後の予定が整理されています。
