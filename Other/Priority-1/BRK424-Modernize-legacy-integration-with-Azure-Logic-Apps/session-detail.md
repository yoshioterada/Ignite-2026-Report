# BRK424 Modernize legacy integration with Azure Logic Apps

## 1. はじめに

このセッションは、BizTalk Server などのレガシーな統合基盤から Azure Logic Apps（Standard）へ移行する際に、単なる「移行」で終わらせず、業務プロセスそのものをモダナイズする方法を紹介する 45 分のブレークアウトです。前半で Microsoft の Principal Product Manager が、レガシー統合を AI で移行する **Logic Apps migration agent** と Logic Apps の新機能を、画面を使って見せます。後半では、ドイツの Schaeffler（シェフラー）が、Logic Apps を土台に社内の事務作業向け AI 自動化基盤を作った経験を話します。

BizTalk Server の利用者はもちろん、MuleSoft や Boomi などの統合基盤から移行を考えている方、あるいは Logic Apps で AI エージェントを業務プロセスに組み込む設計を知りたい方に向いた内容です。

## 5. 発表内容の詳細

### 5.1 なぜモダナイズするのか

Harold 氏は「まだ動いているものを、なぜモダナイズするのか」が顧客との毎週の議論だと語り、前向きな理由として次を挙げています。

- ワークロードを agentic（エージェント的）にできる。
- 1,400 を超えるコネクタで、ソフトウェア、サービス、データ API、データベースなどにつなげられる。
- 人材面：現代的なツールを使えるため、人材を見つけやすい。レガシーの技能を持つ人材を探すのは市場全体の問題になっている。
- 継続的に進化できる。Azure が新機能を出すたびに取り込める。セキュア、ハイブリッド、ガバナンスにも対応する。

一方で、足かせとして次を挙げています。レガシーは変更が難しく、AI への直接の道が無いこと。専門スキルを持つ人が少なく、コストが高くなること。データがサイロ化していること。そして、数十年前に作られたソフトウェアが非推奨や EOL（サポート終了）になり始めていることです。得られる成果としては、企業は変化を速く進められ、運用コストを下げられ、政府機関であれば市民サービスを 24 時間体制（24 by 7）でより良く提供できると説明しています。

また、この状況は BizTalk に限らず、MuleSoft、Boomi、IBM WebMethods、そのほかの統合製品にも当てはまると述べています（「Typical」という製品名も挙がっていますが、音声認識の都合で表記が確定できません）。

### 5.3 Logic Apps の位置づけ

Harold 氏は Logic Apps を「統合のオーケストレーター」「AI 統合オーケストレーター」と呼びます。システムとの統合は REST API を呼ぶことではなく、形式・プロトコル・パターンを理解することであり、Logic Apps がそれを担うという説明です。

AI でコーディングが安くなった時代に、なぜ Logic Apps のような製品が重要なのか、という問いにも答えています。コードを書けば、テストケースも保守も必要になり、「発見する必要のないものを再発見する」ことになりがちです。例として、医療の HL7 形式への対応、金融の Swift メッセージ、製造業の企業間取引で使う複雑な EDI の定義を挙げ、それらは「ブラックボックス」として提供され、自分のコードと組み合わせられると述べています。AI が生成したグルーコードを管理する懸念は、Logic Apps でオーケストレーションすれば、機能が決まった部品として提供されるため、多くが既に解決されている、という主張です。

**オンプレミス**：「Logic Apps はオンプレミスで動くか」という質問が多いと言い、動くと答えています。低レイテンシーの要件があるお客様や、段階的に進めたいお客様、クラウドに置く意味が無いシナリオ向けに、**ハイブリッド展開**があります。Kubernetes、OpenShift、Rancher 上で Logic Apps を動かせます。お客様からは「環境は Azure portal から管理したいが、統合基盤はクラウドに移したくない」という要望があり、それに応えるものだと説明しています。

### 5.4 最近の Logic Apps の新機能

過去 6 か月から 1 年で、お客様の要望に応えて多くの機能を追加してきたと説明しています。

- **AI データマッピング**：XSLT をクラウドで処理できる点は評価されているが、既存資産を活かしつつ、マップを変更・モダナイズしたいという要望に応えるもの。
- **レガシーコネクタ**：SOAP や MSMQ を今も使うお客様が多いため、レガシーシステムとつなぐ手段を作っている。例えば、ベンダー製品が MSMQ を使っていて、すぐには Service Bus に置き換えられない、というケースです。
- **統合ダッシュボード**、**動的接続**（同じ情報を複数の宛先に送る場合）、**ルールエンジン**、**オンプレミスの統合アカウント**、医療向けの **HL7** など。

プラットフォーム全体の改善として次を挙げています。

- **より高速なステートレスワークフロー**：アーキテクチャを変更して「超高速」にした。ステートレスを使っている方はぜひ試してほしい、と述べています。
- **大規模な開発チーム向けのアーキテクチャ変更**：約 200 人の開発者がワークフローを作っている顧客がいて、スロットリングなどが起きないよう再設計した。
- ほかにも、近日提供予定のものがあるとしています。

### 5.5 Logic Apps migration agent

**従来の移行の問題**：手作業による調査と分析、時間のかかる移行計画、労力のかかるコード変換が重なり高コストになり、顧客が「製品を、やり方を提供してほしい」と求め、あるいはあきらめてしまう、と説明しています。

**エージェントの考え方**：エージェントが成果物と依存関係を分析し、コンテキスト情報を作り、成果物とワークフローの変換を支援します。Harold 氏は「migration」と呼ぶのは馴染みのある言葉だからで、実際には lift and shift ではなくリファクタリングだと述べています。MuleSoft や Boomi などで昔に作った複雑な統合を対象に、次の特徴があります。

- 1 対 1 の変換ではなく、**統合全体の意図（目的）を捉える**。システムに潜んでいるバグを見つけて知らせることもある。
- 分析、計画、変換の順に進める。変換には**テストが含まれる**。成果物を生成するだけでなく、テストケースも作り、まずローカル環境で実行し、ターゲット環境にデプロイしてさらにテストする。独自のテストケースを取り込む**ブラックボックステスト**の選択肢もある。
- 提案する解決策を示し、「これを作ります。変更はありますか」と尋ねる。人が変更を入れ、その後にテストする。
- エージェントは 2 つのことを保証すると述べ、1 つ目に**動作するソリューションを作ること**を挙げています（2 つ目は、文字起こしでは語られていません）。例えば、元のソリューションが「ファイルを置くと SAP に送る」ものなら、Logic Apps Standard と Azure Integration Services 上でも同じことが動く。

複雑な移行が 1〜2 日で終わった例もあり、最初は少し怖かったと語っています。ただし、誰も 1〜2 日で移行したいわけではなく、時間をかけてテストし、検証し、機会を見つけたい。その作業をエージェントが助ける、という位置づけです。

**オープンソース**：エージェントはオープンソースで、再利用・変更・適応できるスキルとして作られています。独自アプリケーション向けのパーサーを作ることもでき、リポジトリは終盤に案内する予定だと述べています（発話の範囲では、リポジトリの URL は読み上げられていません）。成果物は **VS Code 拡張機能**で、Marketplace からインストールします。

### 5.6 Data Mapper・トポロジ・運用インサイト

migration agent の説明の途中で、BizTalk 利用者が何年も求めてきた **Data Mapper** が紹介されます。BizTalk のマップは Logic Apps のクラウドでそのまま動かせるが、顧客は 200、300、2,000 といった数のマップを抱えており、変更や JSON マッピング、AI 支援のマッピングを使いたい、という要望です。Data Mapper は定義を検証・コンパイルし、テストして、ローカルのワークスペースに発行できます。

Harold 氏は、約 18 の機能を強調したいと述べたうえで、全部は説明せず、次の 2 つを見せています。

- **統合トポロジビュー**：ワークフロー同士や、ワークフローが呼び出す技術の関係を視覚的に把握できる。最近作った機能とのこと。
- **運用インサイト**：環境、実行、インスタンス、ラン（実行履歴）の統計を見られる。ランの再送信、詳細確認、成功・失敗、操作結果の確認ができる。

### 5.7 Azure Catalyst への組み込み

Harold 氏は、ここ数日で話題になった **Azure Catalyst** を「組織の優れた AI ベース機能の上位集合（super set）」と説明しています（製品名の綴りは音声認識の都合で表記が確定できません）。migration agent の機能も Catalyst に組み込んだとのことです。環境全体を調べる場合は、特定のフォルダーのワークロードを一つずつ拾うのではなく、大規模に動く仕組みが必要です。そのために、**BizTalk の探索（discovery）**を Catalyst で行えるようにしました。CLI コマンドで探索を実行すると、見つかった成果物をまとめた**集約アセスメントレポート**が得られ、環境全体を対象にできる、と説明しています。

### 5.8 モダナイズ後に Logic Apps でエージェントを組み合わせる（Divya 氏）

Divya 氏は、モダナイズが次のイノベーションへの準備になると述べています。

- Logic Apps は何十年も実績のあるエンタープライズ向けプラットフォームで、Azure 上の専用コンピュート、セキュリティ、スケーラビリティを備える。VNet やコンテナーというセキュアな境界で動かせる。
- 既存の投資とスキルの上に積み上げられ、ゼロから始めなくてよい。
- **ワークフローとエージェントを一緒に使える**。エージェント的な推論を業務プロセスに組み込み、自分のペースで進められる。
- エージェントは、ワークフローと同じデータ、プロセス、システムを使うことが多い。そのため、同じ基盤にエージェントを置くほうが簡単になる。ワークフロー内で決まった手順として使うコネクタが、エージェントのツールになる。ワークフローを **MCP として公開**することもできる。
- 人による監督が必要な場合のために、標準のコネクタやネイティブ機能があり、ヒューマン ガードレールを備えたエージェント型の業務プロセスを作れる。
- エージェントに最も重要なのは業務コンテキスト。Logic Apps は業務プロセス、システム、データの中心にあるため、そのコンテキストをエージェントに渡しやすい。標準で備わる**ナレッジ機能**で、業務コンテキストに基づく自分用のエージェントを作れる。
- Logic Apps の外でエージェントを作る場合、会話型・対話型に限られたり、ローカルにとどまったりしがち。Logic Apps のワークフローを使えば、AI を「個人の利点」から「チームスポーツ」にできる。
- **エージェントはどこで作ってもよい**。Foundry や GitHub で作ったエージェントを Logic Apps から呼び出して組み合わせられる。サポート対象は Foundry hosted agents、Foundry prompt agents、GitHub Copilot で動くエージェント。

### 5.9 Schaeffler の事例（Fabian 氏）

**背景**：Schaeffler は「motion technology company」で、5 つの事業部（電動モビリティ、パワートレイン、シャシー、産業用ベアリングなど）、本社はドイツ、従業員は 10 万人以上です。大きな会社には事務作業が多く、出張の手配から注文変更までさまざまで、AI でさらに自動化できるという位置づけです。

**Admin AI Factory**：2026 年初めに始めた取り組みで、事務作業を AI で自動化し、ユースケースを「次々に量産する（factory）」ことを目指しています。最初に事業部門から 50 件のユースケースが提案されました。

**共通パターン**：受信箱に届く作業項目（取引先や顧客からで、形式は一定でない）が起点になります。

1. まず、作業項目の**意図**を AI で正しく読み取る。添付ファイルの分析に OCR が必要なこともある。
2. 分析結果に対して、人が正しさを判断する **human in the loop** のステップを置く。
3. その後、プロセスは分岐する。個別プロセスはさまざまだが、大きくは 3 種類の手順がある。情報を取り込む「エンリッチメント」、作業項目を解決する「リゾルブ」、他システムに情報を送る「アクト」。

複雑さはプロセス自体より、数の多さにあり、最初の 50 件だけで 500 を超えるサービスへの接続が必要だと分かりました。そこで、広い統合レイヤーと AI 機能が必要になったと説明しています。また、機密または極秘のデータを扱うため、最高水準のセキュリティが要件で、開発速度を時間とともに上げることも目標でした。

**Logic Apps Standard を選んだ根拠（3 つの PoC）**

1. Logic Apps Standard の既存の接続（統合レイヤー）を、500 のサービスと比較した。
2. 組み込みの agent loop の機能を、最初の 50 件のユースケースで必要なエージェント機能と比較した。
3. セキュリティ・バイ・デザインの原則を満たす形で、infrastructure as code を構築する方法を見つけた。

**構成**

| 要素 | 内容 |
| --- | --- |
| プラットフォームオーケストレーター | infrastructure as code。ユースケースとステージごとに、リソースグループを 1 つ展開する |
| 各リソースグループの事前構成 | 中央に Azure Logic Apps。Schaeffler のネットワーク内の仮想ネットワーク接続。マネージド接続（エージェント機能のための OpenAI、資格情報管理の Key Vault、監視の App Insights） |
| 保護 | 構成済みのインフラを守るカスタムロール |
| テンプレートリポジトリ | ロールバック、評価（evaluation）、ローカル開発環境など高度な CI/CD の部品を提供する |

この 2 つにより、開発チームはユースケース固有のコードに集中でき、それ以外は抽象化されています。Fabian 氏は、これがプロセス自動化の「スイートスポット」だと述べています。

**タイムライン（2026 年）**

- 第 1 四半期：エージェント型プロセス自動化の選択肢を比較・評価。3 月に Azure Logic Apps に決定。
- 製品グループの支援を受け、2 か月でプラットフォームオーケストレーターとテンプレートリポジトリを構築。第 2 四半期末に準備完了。
- 第 3 四半期：ユースケースの開発速度が本格的に上がった。

**成果**：最初のユースケースはプラットフォームと並行して開発したため、本番まで **10 週間**かかりました。直近に携わった最後のユースケースは **10 日**でした。理由として、次の 2 点を挙げています。

1. インフラのコード化による標準化で、IT セキュリティチームが何を期待すればよいか分かっており、標準化された承認プロセスを使える。
2. 開発チームが、最初から企業データを使って開発を始められる。

**学び（Fabian 氏）**

- Logic Apps では、インフラの面でちょうどよい位置を選べる。Schaeffler では、仮想ネットワーク統合やマネージド ID の統合を、プラットフォームチーム（イネーブルメントチーム）が抽象化している。
- ユースケースのチームは、個別の要件に集中する自由と柔軟性を持つ。新しい要件も、アジャイルにプラットフォーム開発へ取り込めた。
- これは、成熟した統合レイヤーと AI 機能が最初から揃っていたから可能だった。最初から価値を生み出せるため、事業部門の信頼が得られた。

## 6. デモ・手順

Harold 氏が画面を使ったデモを行っています。画面の細部は音声からは確認できないため、語られた範囲で書きます。Fabian 氏の発表では、冒頭で「デモします」と述べていますが、その後の発話はスライドを使った説明で、実際に画面を操作する様子は確認できません。

### 6.1 migration agent（VS Code 拡張機能）のデモ

1. 拡張機能は Marketplace からインストールする。最初に「reset migration」の表示のあるところで、レガシー統合ワークロード（BizTalk や MuleSoft など）があるパスを指定する。
2. 自動で探索が行われ、見つかったフローが示される。BizTalk のオーケストレーションが 10 個あっても、フローが 10 個になるとは限らず、例えば 2 個になる。フローは変更・統合できる。
3. 各フローで分析ができる。既存ソリューションで見つかった内容、メッセージフロー、コンポーネント、不足している依存関係（種類や、用意すべきもの）が示される。
4. 次に計画の段階で、クラウド側のターゲット設計が示される。ワークフローの数を増やしたい場合などは、変更を依頼できる（human in the loop）。
5. 作成の段階で、Logic Apps のワークスペースが生成される。コードが必要な箇所のためのローカル関数が含まれる。
6. 生成されたマップ（Data Mapper）を見せる。移行の終盤に、ローカルのブラックボックステストでテストケースを選んで実行できる。
7. 最後にクラウドへデプロイされ、Logic App として動いている画面を見せる。この例では、最も単純なフローだったため、ワークフローは 1 つだけだった。EDI のソリューションで、ループとマッピングを行い、マップへの参照がある。マップ名は聞き取り不明瞭です。元は BizTalk のソリューションから来たものです。

### 6.2 統合トポロジビューと運用インサイト

統合トポロジビューを示したあと、運用インサイトで環境、実行、インスタンス、ランの情報を見せています。ランの再送信、詳細の確認、成功と失敗、操作結果などの情報が見られると説明しています。

### 6.3 Azure Catalyst での BizTalk 探索

1. BizTalk 環境に対して CLI コマンドを実行し、探索を行う。
2. すべての成果物が識別されたあと、集約アセスメントレポートが出る。レポートで環境にあるものを確認できる。

## 7. 注意点・発表者の気付き

- **移行は 1〜2 日で終わることもあるが、それが目的ではない**。時間をかけてテストし、検証し、新しい機会を探すべきで、エージェントはその作業を助けるものです。
- **エージェントは意図を理解して再構成する**。1 対 1 の変換ではなく、元より少ないフロー数になることがあります。提案を人が確認し、変更できます。
- 環境全体を調べるときは、特定のフォルダーを 1 つずつ拾う方法では足りないため、Catalyst に BizTalk の探索機能を入れた、と説明しています。
- BizTalk Server は、2027 年 3 月 31 日に販売終了、2028 年にメインストリームサポート終了という日程があり、有償サポートの選択肢は予定です。
- Schaeffler の学び：最初のユースケースはプラットフォームと並行して作ったため 10 週間かかっています。標準化とプラットフォーム化の効果が出るのは、その後です。
- 発表では、移行エージェントの対応範囲の制限、料金、対応する製品バージョンの詳細には触れていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- 手作業の調査・分析・コード変換というコスト要因を、エージェントが減らす。複雑な移行が 1〜2 日で終わった例がある。
- 統合の意図を捉え、テスト（ローカル、デプロイ後、ブラックボックス）まで含めて、動作するソリューションに導く。
- 既存資産（マップなど）を活かしつつ、Data Mapper で変更や AI 支援のマッピングができる。
- オンプレミスや Kubernetes（OpenShift、Rancher）でも動かせるハイブリッド展開があり、段階的に進められる。
- 既存のコネクタ、データ、システムをそのままエージェントのツールとして使え、ワークフローを MCP として公開できる。
- **Schaeffler の成果**：ユースケースが本番に出るまで 10 週間から 10 日に短縮。インフラのコード化による標準化で、IT セキュリティの承認プロセスが標準化され、開発チームは最初から企業データで開発できる。

## 9. まとめ

- BizTalk Server は 2027 年 3 月 31 日に販売終了、2028 年にメインストリームサポートが終了します。同様の状況は、MuleSoft や Boomi などにも当てはまると説明されました。
- Logic Apps migration agent は、レガシー統合の意図を捉えてリファクタリングし、テストも含めて動作するソリューションを作る、オープンソースの VS Code 拡張機能です。環境全体の探索は Azure Catalyst に組み込まれています。
- 移行後は、Logic Apps 上で決まった手順とエージェントを組み合わせられます。Foundry や GitHub Copilot のエージェントも呼び出せます。
- Schaeffler は、Logic Apps Standard を中心にしたプラットフォームを 2026 年に構築し、ユースケースの本番化を 10 週間から 10 日に短縮しました。
