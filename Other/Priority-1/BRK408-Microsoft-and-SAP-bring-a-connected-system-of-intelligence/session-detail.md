エージェントが同じ共有コンテキストにアクセスし、結果から学び、有用なら再現可能な知識として組織に蓄積する。そうすれば、次のエージェントやアプリケーション、ワークフローがその成功を引き継げます。何が重要か、エージェントが何を学び組織がどう強くなるかを決めるのは、「human in the loop」としての人間だと Mike は述べています。

### 5.1 Mike：Microsoft の「つながったシステム」と Azure

Mike は、Microsoft のスタックを次のようにつながった全体として説明しています。

| 層 | 役割（発表での説明） |
| ---- | ---- |
| IQ | コンテキストを提供する |
| Foundry と Fabric | モデルとデータ、事業の理解、知識、業務ロジックをつなぐ |

Azure は、シリコン、コンピュート、ストレージ、ネットワーク、モデル、コンテキスト、エージェントを、プラットフォームとして end-to-end で設計していると述べています。そのため、パフォーマンス、セキュリティ、経済性を、層ごとではなく end-to-end で最適化できるという説明です。推論のルーティング、ストレージからのコンテキスト供給、エージェント間の通信なども一体で捉えています。

#### Azure と SAP の共同エンジニアリング

SAP の最も要求の厳しいジョブをうまく動かすために、SAP と共同エンジニアリングしている、と説明しています。ロードマップとして次の項目が挙げられました。

- 新しい **Azure Center for SAP** による、スタック全体にわたる安全な AI トラブルシューティング

具体的な提供時期や数値は、発表では示されていません。

#### Microsoft IQ と SAP を組み合わせたときの価値

IQ と SAP を合わせると、次のものにアクセスできるようになると述べています。

- ナレッジグラフ
- 何百万ものデータフィールド
- エージェントの追加コンテキストとなるドメインモデル

これらは、事業ロジックや SAP 自身のコードから学び、SAP と非 SAP のデータにまたがる**セマンティックレイヤー**を作ります。

#### サプライチェーン障害の例（説明）

SAP のデータ（注文、在庫、サプライヤー）と、Microsoft 側の情報（会議、ファイル、メール、チャット）を組み合わせた例を示しています。

1. 重要なサプライヤーが納期に間に合わないことをエージェントが検知する。
2. 契約条件、運用ポリシー、そのベンダーや他のサプライヤーとの最近のやり取りを参照する。
3. Web 情報など、外部の障害シグナルも組み合わせる。
4. アラートを出すだけでなく、代替案を提示し、下流への影響を評価し、承認されたステップを開始する。
5. すべてが、組織の権限とポリシーの範囲内で行われる。

Mike は、こうして「一般的なインテリジェンスやアラート」ではなく、事業に合わせた、ポリシーで統制された「アクション」が得られると述べています。

### 5.2 Mike：連携の 4 つの領域

#### (1) Joule と Copilot の双方向連携

ユーザーは Copilot からでも SAP からでも、仕事を始めたり終えたりできます。使い慣れた環境にとどまったまま、事業の詳細を、仕事全体の文脈とともに理解できます。AI は質問に答えるだけでなく、「チームの一員のように」アクションを取ります。Joule は SAP から事業コンテキストを得て、Work IQ は「常に最新でガバナンスされた、仕事の理解」を提供します。

Mike はここで、製造プランナーが主役のデモ動画を流しています（6.1 参照）。

#### (2) ガバナンス：Agent 365 と SAP Agent Hub

この 2 つの組み合わせで、end-to-end のガバナンスを実現します。

- SAP と Microsoft のエージェントの**完全なインベントリ**
- アーキテクチャやセキュリティなどの、IT チームによる発見・監視の改善
- 単なるレジストリ上の可視化にとどまらない、深いテレメトリ
- アクセス制御と、Microsoft と SAP にまたがるクロスプラットフォームの制御

#### (3) SAP の表形式（tabular）基盤モデルを Foundry へ

SAP の新しい tabular foundation model を Foundry に直接取り込む、と述べています。表形式のデータに対して、**事前に学習させなくても業務結果を予測**できるというものです。

- 従来の LLM は、構造化された業務データでの正確な予測が苦手です。
- 例として挙げられたモデルは **Tab PFN** です（音声認識上の表記）。
- 予測できる例：支払い遅延、サプライヤーリスク、キャッシュフロー予測、顧客離反。
- 欠損値や、混在するデータ型、製品・顧客コードなどの社内情報を扱えます。
- 事前学習済みなので、固有の学習やチューニングは不要です。
- Foundry では、こうした専用モデルを他のモデルと組み合わせられます。自社の情報やサービスの推論は別のモデルが担当し、Tab PFN が表データから正確な予測を返す、というマルチモデルの構成です。

#### (4) Fabric と OneLake による統合データ

SAP のデータを Fabric の OneLake に統合することで、チームにとって単一のデータソースを実現します。すべてのエージェントがそれを使って動け、一貫性があり、責任ある形でガバナンスできます。**Fabric IQ** が、基盤全体で事業上の意味と関係性を保ちます。これにより、Copilot、Joule、各種アプリケーション、エージェントが、信頼できる 1 つのコンテンツソースを共有し、一貫した形で判断・行動できると説明しています。

Mike は最後に、「SAP を Azure 上で動かすだけでなく、ポートフォリオ全体にわたる end-to-end の深い統合だ」と述べ、今週この関係を新しい段階に進めると話しています。

#### デジタル・データ変革の 3 つのステップ

5 年前に「デジタル成長エンジン」を作ることを決めたといいます。単なる IT プログラムではないと述べています。

1. **コアを作る（2021 年）**：全ての国で S/4HANA に移行して共通の基盤を整えました。顧客ポータルを SAP Commerce Cloud にアップグレードして、本格的な B2B チャネルにしました。ビッグデータの土台づくりも始め、顧客への訪問をパーソナライズする「segmented execution」を実現しました。
2. **スケールする（2022〜2024 年）**：すべてのアプリを Azure（クラウド）に移し、その上に機能を積み上げました。営業担当が店舗でクーラーや棚の写真を撮り、生産性と正確なデータにつなげる**画像認識**、CRM の D365 への移行、顧客・ベンダー・製品のマスターデータを強化する SAP MDG、工場の予知保全（障害を避け顧客により良く対応するため）が挙がっています。
3. **AI をワークフローに組み込む（直近 2 年）**：プロモーションと収益成長管理の分析で AI を強化し、「suggested orders」に AI を組み込みました。あらゆるチャネルで顧客に提案が届きます。主要工場に**デジタルツイン**を導入し、サステナビリティ目標に合わせてエネルギーと水の消費を最適化しています。

さらに、**10 日前に S/4HANA から SAP RISE へ移行**し、全ての国を 24 時間ほどで移したと述べています（Dan は「たしか」と付けています）。これにより、SAP の新しい機能（聞き取りでは「SAP Dual」と聞こえる部分があり、表記は確定できません）などが使える土台ができたという説明です。

#### 成果

- 5 年連続の成長。この期間で売上が **89%** 成長。
- デジタル注文がほぼ倍増。**15 万社**の顧客がデジタル注文を利用。
- 顧客満足度（NPS）は年々向上し、現在 **78**。

#### データの課題と、統一された基盤

IQ を作る過程での大きな課題はデータでした。

- 環境内に **3,000 超の断片化したモデル**があった。
- ユーザーは SAP BW からデータを抽出し、標準化されていないツールで加工した。「KBI」を追加して手直しし（聞こえた表記のまま。KPI のことかは確認できません）、その結果、アドホックな分析、シャドウレポート、データの重複が発生した。

目指すのは、単一で統一されガバナンスされた基盤です。ユーザーは質問や達成したい成果から始め、**AI-ready なデータプロダクト**から、認証された信頼できるデータを探して使います。必要ならローカルな KBI を追加できますが、AI エージェントが示す洞察により多くの時間を使えます。つまり、多数のローカルレポートから、人・アプリケーション・AI エージェントが再利用できる 1 つのガバナンスされた真実のソースに移ります。

#### 技術基盤（Dan の説明）

- **左側：データメッシュプラットフォーム（Microsoft Fabric 上）**。約 50 TB のデータ、10 の異なるソースシステム、定期的にアクセスする 10,000 の利用者で実績があります。
- **右側：AI-ready 化の部分**。最下部に Databricks のレイクハウスがあり、SAP 以外のデータと SAP のデータを取り込みます。SAP の Business Data Cloud からレイクハウスにデータを取り込むパイロットを実施中です。その上のデータレイクに、**オントロジーとセマンティックレイヤー**を加えてデータプロダクトを提供し、エージェントを載せられるようにします。Power BI でセルフサービスのレポートや標準ダッシュボードも使います。
- データカタログとデータリネージには **Atlan** を使い、ユーザーが正しいデータプロダクトと信頼できるデータを見つけられるようにしています。

#### AI のユースケース：フロントラインのカスタマーコンシェルジュ

顧客ポータルから使える、全顧客向けの仕組みです。

- コンシェルジュは**オーケストレーションエージェント**で、注文管理（変更、アップロード、ステータス確認）、チケットのリクエスト、財務情報などを担当する一連のエージェントとつながります。
- それらは SAP のバックエンドと同期し、データがリアルタイムで、トランザクションデータの変更も可能です。
- ポータルの右側にエージェントが表示されます。顧客は、スプレッドシートや PDF で作った注文をエージェントにアップロードできます。
- エージェントは形式に関係なくデータを理解し、製品、数量、金額をマッピングして、「これで合っていますか、修正しますか」と確認を返します。
- 会話型（生成 AI）なので、注文を正しくするために、さまざまな質問や修正ができます。

### 5.4 Hiren：Microsoft スタックと SAP の位置づけ

Hiren は、Foundation として Azure、Microsoft Foundry、Microsoft Fabric があり、すべてが Microsoft のセキュリティソリューションで保護されていると説明しています。その上に **Microsoft IQ** があり、関係性、人、組織のコンテキスト、カスタムのスキルとエージェントをまとめます。キーノートで語られた**ガバナンス・管理ツール**で、これを「自社の IQ」に仕立てます。どのスキルを組織全体で使うか、特定の人にだけ開くかを決められ、Copilot 上で仕事の流れの中で使えます。エージェントや AI は **A365** で管理され、信頼性とコンプライアンスを確保できる、という説明です。

### 5.5 Hiren：SAP ワークロードでエージェント AI を使う 2 つの方法

#### Agent-to-Agent（A2A）

- これまで、Copilot と Joule の間には双方向の統合がありました。どちらの体験からも質問・プロンプトを送り、もう一方のエコシステムから回答を得られます。
- **新発表**：オープンソースの **A2A（agent to agent）プロトコル**でのエージェント連携を有効にします。Copilot や Excel から、Joule の組み込みエージェントや、Joule Studio で作ったカスタムエージェントに、質問やタスクを委任できます。時間とともに、与えるコンテキストが少なくて済むようになる、と述べています。
- これは SAP RISE と Joule を使っている場合に向いています。

アーキテクチャは次のように説明されました。

1. Microsoft 側のアプリ（Copilot、Teams、Excel、Outlook、PowerPoint）の中で、仕事の流れの中にいる。
2. Joule のエージェントにタスクを委任したいとき、プロンプトを送ると、A2A プロトコルで SAP の **agent gateway** に渡る。
3. agent gateway が推論して適切なエージェントを見つけ、呼び出す。
4. SAP 側の**セキュアなエージェントランタイム**で動き、システム・オブ・レコードに安全でコンプライアンスを満たす形でアクセスする。
5. **Microsoft Entra** がユーザー ID を検証し、ユーザーは権限のあるデータだけにアクセスできる。

今後の方向として、Joule のエージェントが追加されると、それをカスタムエージェントから使えるようになります。さらに Copilot 側に適切なプラグインやスキルを用意し、自分でエージェントを作らなくても Joule 側のエージェントを呼べるようにしていく、と述べています。

#### MCP 連携

SAP の複数アプリを他のアプリとつなぐ場合、RISE や Joule をまだ使っていない場合、あるいは情報を読むだけ・分析の最終結果を SAP に書き戻すだけの場合には、MCP 連携が向いていると説明しています。MCP サーバーのホスト先は 2 つあります。

| 選択肢 | 内容 |
| ---- | ---- |
| SAP の BTP と Business AI Foundation | MCP gateway を使って MCP サーバーをホストする。ID は Entra で安全に管理されると説明している（前のアーキテクチャと同様、という発言） |
| Azure API Management | BTP と Business AI Foundation を使わない場合に、シナリオに合う API を選んで MCP サーバーとして有効化し、ホストする。Copilot がそこに接続できる |

Copilot には、MCP サーバーやプラグインをインストールできます。

### 5.6 Hiren：データ統合 ― SAP と非 SAP を Fabric で

SAP データと非 SAP データ（CRM などの運用データ）を組み合わせたい、という要望が多いと述べています。環境は複雑で、Salesforce、Dynamics、ServiceNow などのシステム・オブ・レコード、複数の分析スタック、Kubernetes などのインフラ、工場からのストリーミングデータを送る IoT アプリケーションなどがあります。そこでリアルタイム分析と Power BI を、**Fabric の OneLake** 上で行うことを勧めています。

Fabric へのデータ統合には複数の選択肢があります。

1. **SAP Business Data Cloud と zero copy sharing**：昨年初めに発表され、現在 **private preview**。関心があれば連絡してほしい、適合するか確認する、一般提供に向けて進めていると述べています。
2. **レプリケーション**：RISE や BDC をまだ使っていない場合や、パフォーマンス要件がある場合向け。
   - ソースシステムにインストールしてデータをプッシュする、ABAP 向けの copy job（音声認識上の表記のまま）。
   - **SAP Data Sphere** の premium outbound connection と、Fabric の **open mirroring** の統合。
   - Fabric の open mirroring と統合された、認定済みのサードパーティソリューション。

SAP の移行状況、コスト、パフォーマンス、ユースケースに応じて選べる、という説明です。

#### Business process solutions

つなぐだけでなく、適切なデータの選定、正規化、分析・Power BI 向けの準備には、ETL、データエンジニア、機能の専門家、データサイエンティストの工数がかかります。そこで、より簡単な出発点として **business process solutions** を用意した、と説明しています。

- 対象は人気のユースケース：財務のインサイト、販売、調達、製造。
- 適切なデータセット、ダッシュボード、インサイトを事前に作成している。
- その上で動く、使いやすい**データエージェント**を構築中。
- すでに利用できる。**Fabric Workload Hub** で「business process solutions」を探す。
- ダッシュボードやインサイトを構成し、ソースシステムにつないでデータを取り込むだけで、**6〜8 か月かかる ETL プロジェクト**を数時間に圧縮できる、と述べています（音声認識では「EKL」）。

### 5.7 Hiren：まとめ

- **Microsoft Entra ID** がユーザー ID を管理し、**Entra ID governance** によって、権限の範囲を超えたデータにアクセスさせないことが、これらの AI ワークロードを安全にしています。
- 構造化・非構造化データに基づいて、Copilot と Fabric で意思決定を支える。

### 6.3 MCP 連携のデモ：売掛金（Accounts Receivable）の分析（Hiren）

## 7. 注意点・発表者の気付き

- **管理対象が増えるだけにならないように**：AI の数ではなく、価値が積み上がっているかを確認する、というのが Mike の問いかけです。
- **ガバナンスはレジストリを超える**：Mike は Agent 365 と SAP Agent Hub の価値を、単なるレジストリ上の可視化ではなく、深いテレメトリとアクセス制御だと説明しています。
- **LLM は構造化データの予測が苦手**：そのため、表形式データには専用の基盤モデルを使う、という整理です。
- **Coca-Cola HBC のデータの課題**：3,000 超の断片化したモデルとシャドウレポートが障害でした。Dan は、ユーザーが信頼できるデータを見つけるために、データカタログとリネージ（Atlan）が重要だと説明しています。
- **コンテキストの重要性**：Dan も Mike の話を受けて、コンテキストが「非常に重要」になっていると述べ、LeanIX、Signavio、S/4HANA をその例に挙げています。
- **A2A の対象**：RISE と Joule を使っている場合に向いています。そうでない場合や、読み書きだけでよい場合は MCP が向いています（Hiren）。
- **Zero copy sharing は private preview**：現時点では一般提供ではなく、適合するかの確認が必要です。
- **発表で触れられなかったこと**：価格、各機能の提供時期（Azure Center for SAP、MV4 VM などの具体的な一般提供日）、A2A 連携の一般提供状況は、発表では語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **業務の流れの中で AI を使える**：Copilot や Excel などの使い慣れた環境から SAP の情報を見て、そのままアクションを取れる（Mike、Hiren のデモ）。
- **権限の範囲内で動く**：Entra による ID の検証で、ユーザーは権限のあるデータだけにアクセスできる（Hiren）。
- **Microsoft と SAP のエージェントを一元的に統制できる**：Agent 365 と SAP Agent Hub（Mike）。
- **事前学習不要の予測**：支払い遅延、サプライヤーリスク、キャッシュフロー予測、顧客離反などを表データから予測できる（Mike）。

## 9. まとめ

Microsoft と SAP の取り組みは、SAP を Azure で動かすことにとどまらず、IQ、Foundry、Fabric、Copilot を含むポートフォリオ全体との深い統合へ進んでいる、というのが発表の主張です。Mike が挙げた連携の柱は、Copilot と Joule の双方向連携、Agent 365 と SAP Agent Hub によるガバナンス、Foundry での SAP の表形式モデル、Fabric と OneLake による統合データの 4 つです。Hiren は、Copilot から SAP を使う具体的な方法として A2A と MCP を紹介しました。

Coca-Cola HBC の事例では、S/4HANA、Azure、Fabric、Databricks、Atlan などを組み合わせたデータ基盤の上で、顧客向けコンシェルジュのエージェントを動かしています。今後は 11,000 の Copilot ライセンスを窓口にして、LeanIX、Signavio、S/4HANA のコンテキストを活用する計画です。Hiren は 3 つのデモで、Copilot から SAP の作業を委任・分析・Excel への展開まで進められることと、business process solutions でデータエージェントをすぐ使い始められることを示しました。

最後の言葉は、構造化・非構造化データに基づく判断、分析から行動への移行、そして IQ とスキルの継続的な積み上げです。
