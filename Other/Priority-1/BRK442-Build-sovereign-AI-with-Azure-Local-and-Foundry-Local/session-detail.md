# BRK442 Build sovereign AI with Azure Local and Foundry Local

## 1. はじめに

このセッションは、規制や社内のデータ管理要件のために、AI とデータを自社の管理下（オンプレミス、工場、拠点、切断された環境）に置いて運用したい人に向けた発表です。Azure Local（Azure の管理体験を自社のインフラに持ち込む基盤）の上で動く **Foundry Local** の一般提供（GA）が発表され、モデルのデプロイと評価、エージェント、検索（agentic retrieval）、ガバナンスまでを、Woodgrove Bank という銀行のシナリオで 2 回のデモを交えて紹介しています。

結論を先に整理すると、発表された内容は次のとおりです。

* Foundry Local（Azure Local 上）は **GA**。Foundry Local knowledge（agentic retrieval）も GA。
* Foundry Local Agent Service と Foundry Local Tools は **パブリックプレビュー**。
* GitHub Enterprise Local は **GA**。
* 大規模推論向けに、NVIDIA の GPU を Azure Local でサポートする計画（来年の暦年**上半期**のプレビューを目標）。

## 5. 発表内容の詳細

### 5.1 課題設定とソブリン AI

登壇者は、Woodgrove Bank の CTO という設定で話を始めました。この 1 年でクラウド上に多くの AI を作り、上司も絶賛している従業員向けアシスタントエージェントがあります。しかし、顧客データなどの機微なデータをエージェントに含めるには、国の銀行規制と社内のデータ管理要件を満たす必要があります。つまり、**AI をデータのところへ持っていく**必要があり、その答えがソブリン AI だという流れです。

ソブリン AI を必要とする例として、次の 3 つが挙がりました。

* 自社の独自データが、AI ソリューションの中でどこで、どう使われるかを自分で決めたい製造業
* 社内で開発した独自の AI モデルを守りたい医療研究企業
* 接続状況に関係なく、現場の従業員の安全モデルを動かしたいエネルギー企業

### 5.2 Microsoft のソブリンクラウドの選択肢

| 選択肢 | 説明 |
| ---- | ---- |
| Sovereign Public Cloud | クラウドの規模とイノベーションを保ちつつ、データレジデンシー、アクセス、ガバナンスの統制を適用する |
| Sovereign Private Cloud | 運用の統制と継続性が重要な環境向け。インフラとデータを自社の境界内に置き、Azure に接続していても切断されていても、ミッションクリティカルなワークロードを動かせる |
| Sovereign Partner ecosystem | 現地の専門性と専用ソリューションを加える |

このセッションの対象は、Sovereign Private Cloud の AI です。

### 5.3 Foundry Local の構成要素

Microsoft Foundry は、AI アプリケーションとエージェントを構築、グラウンディング、統制するプラットフォームと説明されています。Foundry Local は、オンプレミスで AI アプリケーションを作って動かすための、モデル、エージェント、ツールのソリューションです。

| 構成要素 | 状況 | 内容 |
| ---- | ---- | ---- |
| モデルカタログと推論エンジン | GA | vLLM と ONNX のランタイムを選べる。コミュニティモデルのキュレーションされたカタログと、自分のモデルやランタイムの持ち込みが可能 |
| Foundry Local knowledge | GA | ローカルのデータに対する agentic retrieval と、組み込みのチャット体験 |
| Foundry Local Tools | パブリックプレビュー | MCP を通じて、すでに動いている AI システムに接続する |
| Foundry Local Agent Service | パブリックプレビュー | エージェントをローカルで構築、ホスト、統制する |
| GitHub Enterprise Local | GA | セルフホストで安全なソブリン DevOps |

基盤として、Azure Arc が全体に一貫した管理とガバナンスを提供し、Azure Local が、小型のエッジシステムからラックまでの AI 最適化ハードウェアを提供します。OpenAI 互換 API と、開発者が既に知っている Foundry のツールを使って、速く作ってデプロイできるとのことです。（トランスクリプトでは "VLM" と記録されていますが、文脈から vLLM を指すと思われます。）

### 5.4 モデルカタログと推論

Anders 氏は、Foundry Local のモデルカタログと推論が行う 3 つのことを説明しました。

1. Azure Local での動作が検証された、さまざまな AI ワークロード向けに最適化されたモデルを**見つける**。
2. CPU または GPU 上で、**OpenAI 互換のエンドポイント**の背後にデプロイして動かす。エンドポイントは TLS で保護され、認証は API キー、Microsoft Entra ID、Kubernetes のサービスアカウントトークンから選べる。
3. すべてのモデルのデプロイを、接続時も切断時も**一貫した体験**で管理する。

カタログには、Microsoft、OpenAI、Mistral、DeepSeek、Qwen（"Quen"）、NVIDIA などの、検証済みコミュニティモデルが数百あり、毎月追加されています。一覧は aka.ms/FLModels で確認できます。自分でファインチューニングしたモデルも、ONNX または vLLM のランタイムで持ち込めます。SLM、LLM、推論（reasoning）モデルのほか、OCR モデルや NVIDIA Nemotron Nano のようなマルチモーダルモデルもあると説明されています。

**CLI とポータルの両方**で使えます。Kushmeen 氏のデモは、切断環境で使うコマンドラインでした。接続環境では、開発者がクラウド AI で使っている Microsoft Foundry ポータルを使えます。ポータルの流れは次のように説明されました。

1. 探す：Foundry Local のコレクションに、Azure Local で動作が検証・テストされたモデルが並ぶ。
2. 選ぶ：例として OpenAI のオープンウェイトモデル GPT OSS 20B を選ぶ。
3. デプロイ：ターゲットに Azure Local を選び、Foundry Local 拡張機能が入った Arc 対応の Kubernetes クラスターを選ぶ。レプリカ数、必要なコンピュートリソース、推論ランタイムを設定する。
4. Foundry Local がクラスターにモデルをデプロイし、保護されたエンドポイントを公開する。デプロイはこの画面で追跡でき、すぐテストできる。

自分のデータセットを使った**評価は、現時点では CLI から実行**し、ポータルへの対応は近日予定とのことです。接続時はポータル、CLI、API、切断時は CLI と API を使えますが、モデルもエンドポイントも同じです。（ポータルの説明は、ライブ操作かスライドかが音声からは確認できません。）

#### パートナーのモデル

* **Mistral**：オープンソース、オープンウェイト、プロプライエタリ、クローズドウェイトを含む幅広いモデルを提供する。プロプライエタリとクローズドウェイトのモデルは、Microsoft 管理の配信で顧客のオンプレミスで使えるようにする。
* **Cohere**：エンタープライズ向けの Command A Plus と North Minicode（"North Minicode" は音声認識の都合で表記が確定できません）が、Foundry Local で利用可能。Command A Plus は最小限のリソースで最大の性能を目指して設計されているが、強力な LLM のためマルチ GPU 構成が必要。

### 5.5 インフラ：Azure Local と NVIDIA

Kushmeen 氏は、モデルとエージェントは必ずどこかで動くもので、データと AI を自分の境界内に置くならその場所が Azure Local だと述べています。Azure Local は、CPU から GPU 対応サーバーまで、ワークロードに合わせたサイズで Foundry Local のモデル、エージェント、ツールを動かす AI 対応インフラです。

Woodgrove Bank の例では、大きなクラスターは不要で、効率的な入口として **NVIDIA L4** を搭載した小さな GPU 対応サーバーから始められ、より大きなモデルやユーザー数に余裕を持たせたい場合は、より大型の **RTX Pro 6000** を検討できます。AI はデータの隣で動き、需要に応じて拡張します。エッジの単一ノードから、データセンターの複数ラッククラスターまで、Azure リージョンに接続していても、完全に切断されていても、同じプラットフォームと管理体験です。

**大規模推論**については、NVIDIA との取り組みとして、Azure Local が **NVIDIA HGX Blackwell GPU** をサポートすると発表されました。トランスクリプトでは "HGX P300" と "HDX B300" の 2 通りの表記があり、音声認識の都合で正確な型番が確定できません。

* Azure Local、Foundry Local、NVIDIA の GPU、パートナーのエコシステムを組み合わせた、検証済みの AI インフラソリューション。
* Foundry Local が、カタログまたは自前のオープンモデルで推論をデプロイ・オーケストレーションし、Azure Local がその下で、**confidential compute**（機密コンピューティング）を使って管理・スケール・統制する。実行中のデータとモデルの知的財産（ファインチューニングしたモデルを含む）を保護するため。
* **Dell、HPE、Lenovo** と協力し、Azure Local カタログのプレミアなソリューションとして提供する。どの構成も Foundry Local の推論で検証済み。
* 最も大きなモデルも、自社のインフラ上で、必要な統制をかけたまま動かせる。「最も高性能な AI」と「データの管理」のどちらかを選ばなくてよいようにする、という位置づけ。
* プレビューは**来年（暦年）の上半期**を目標としている。

### 5.6 agentic retrieval（Foundry Local knowledge）

「モデルは学習したことしか知らず、実際の答えは SharePoint やファイル共有、自社のデータにある」という前提で、**Foundry Local の agentic retrieval が GA になった**と発表されました。仕組みは次の 3 ステップです。

1. **Ask（質問）**：組み込みのチャット体験、または API 経由の自社アプリから質問する。
2. **Retrieve（取得）**：システムが意図を読み取り、質問を複数の的を絞ったクエリに分解する（計画）。各クエリを、すべてにではなく適切なソースへ、ハイブリッド検索で送る。得られた証拠は 1 つにまとめられる。証拠が薄いときは、クエリを書き換えて範囲を広げ、確信のある証拠が得られるまで再取得を続ける。従来の検索は 1 回で終わるが、これは確信が持てるまで続く。
3. **Answer（回答）**：根拠のある回答を出し、何をどこで検索し、結果がどこから来たかを示すアクティビティログでたどれる。

ソースは 2 種類です。

| 種類 | 例 | 特徴 |
| ---- | ---- | ---- |
| インデックスソース | NFS ファイル共有、SharePoint Server | 事前に取り込んで埋め込みを作る。データ全体への深さがある |
| リモートソース | 自社の MCP サーバー | ライブで問い合わせる。インデックスを待たず最新のデータが得られ、アプリケーションやデータリポジトリにつながる |

### 5.7 Foundry Local Agent Service（パブリックプレビュー）

Kushmeen 氏は、AI が質問に答えるだけでなく行動を起こす部分だと説明しています。Agent Service は、モデル、企業データ、ツールをまとめるオーケストレーターで、自社のインフラ上に展開され、必要な統制の下で動きます。流れは次のとおりです。

1. **構築**：開発者が、agents and tools 拡張機能を通して、Microsoft agent framework で prompt agent を作る（指示、モデル、使えるツールを定義）。
2. **実行**：エージェントランタイムが、framework のハーネスで、計画と実行をループしながら動かす。
3. 下回りとして、保護されたランタイム上のモデル（Foundry Local のものでも自前のものでも）、隣で動くガードレールと評価、agentic retrieval によるローカルデータのグラウンディング、そしてカスタム MCP 用の単一の MCP 互換エンドポイントである **Toolbox** を使う。
4. **改善**：Playground、CLI、近日中に Foundry ポータルでテストして改善する。組み込みのトレース、モニタリング、評価シグナルによる最適化は近日提供予定。
5. **配布**：ユーザーのいる場所に、エージェントの体験を届ける。

### 5.8 全体像

Anders 氏が、すべてを組み合わせた全体像を示しました。左側の境界の内部は、接続、断続接続、切断のいずれでも動かせます。

* **Azure Local**：自社で所有・運用するハードウェア（CPU と GPU、小型から複数ノードまで）。Azure Arc が、すべてを拡張機能としてデプロイ・更新する。接続時は Azure がデプロイ、更新、ガバナンスを担い、完全切断時は **Azure Local disconnected operations** が管理をローカルに保つ。
* **Foundry Local のモデルと推論**：カタログ、自前モデルの持ち込み、ONNX と vLLM のランタイム、ノードをまたぐ CPU と GPU のサービング、保護されたエンドポイント。
* **agentic retrieval**：コンテンツを取り込んでインデックス化し、ローカルとハイブリッドのベクトル検索で、エージェントが使える knowledge base を通して提供する。データは元の場所に残る。
* **Agent Service**：プロンプト、モデル、ツールにまたがってエージェントをオーケストレーションする。**guardrails プラグイン**で、アプリに最適なガードレールモデルを持ち込める。
* アプリは、OpenAI 互換 API で呼び出すか、組み込みのチャット体験から始められる。
* **GitHub Enterprise Local**：オンプレミスの DevOps を開発者に提供し、Foundry Local が、開発者がコーディングに使うモデルをホストする。

Woodgrove Bank の CEO の問いに対する答えは、モデル、プロンプト、検索インデックス、埋め込み、推論ログのすべてが環境内に残ること、とまとめられています。

### 5.9 GitHub Enterprise Local

ソースコードは知的財産であり、多くの組織では規制上の確認の対象にもなります。この観点から、GitHub Enterprise Local が今週 GA になりました。GitHub Enterprise Server を、構築済みの**仮想アプライアンス**として Azure Local に持ち込みます。リポジトリ、パイプライン、成果物は自社のインフラとセキュリティ境界の中に留まり、開発者は使い慣れた GitHub の体験を使えます。

* **接続モード**：コントロールプレーンを Azure リージョンに置き、集中管理する。
* **切断モード**：コントロールプレーンをローカルのアプライアンス VM に置き、クラウドリージョンは不要。
* デプロイは、Azure ポータルのガイド付きフォーム、または複数拠点に展開するチーム向けの PowerShell スクリプト。
* GitHub 管理者は、リポジトリ、セルフホストランナーを使う Actions、パッケージ、advanced security を、これまでどおり管理する。
* AI は接続性に合わせて選ぶ。インターネットへのアクセスが使える環境では（聞こえた表記は "improved internet access"。音声認識の都合で正確な語が確定できません）、リポジトリをローカルに置いたまま GitHub Copilot を使える。AI の処理を境界内に留める必要がある場合は、Foundry Local が Azure Local で承認済みのモデルを動かし、プロンプトとコードのコンテキストは環境内に残る。

### 5.10 セキュリティ

AI を境界の内側で動かすのは、最も機微なデータや自社の IP を扱うためであり、セキュリティは組み込みである必要がある、という前提で、2 つの側面が説明されました。

**1. インテリジェンスを守る**（モデルの盗用、推論の改ざん、サプライチェーン攻撃から）

* オープンウェイトのモデルも、自社データでファインチューニングすると機微なデータになる。
* 原則は「インテリジェンスを有効にする前に信頼を確立する」こと。
* Azure Local の **confidential computing** が、使用中のモデルとデータを保護する。**attestation-gated key release** により、ハードウェアが信頼できると証明されるまで暗号化が解除されないようにできる。
* **AMD の confidential VM は GA、Intel はプレビュー**、NVIDIA の confidential GPU は準備中。
* Azure Local のアクセス制御で、誰が・何がモデルにアクセスできるかを統制する。

**2. インテリジェンスから守る**（責任ある AI）

* **Foundry Local Guardrails**（パブリックプレビュー）が、プロンプトと応答を、有害コンテンツ、プロンプトインジェクション、個人データについて検査する。ガードレールのモデル、ポリシー、しきい値は利用者が選び、アプリは同じ Foundry Local API を呼び続ける。
* ハルシネーションに対しては、agentic retrieval で自社データに基づいて回答させる。
* ガードレール、confidential computing、アクセス制御に加えて、完全な戦略が必要だとして、エンドツーエンドのセキュリティのセッション（「Securing Edge and OT Workloads」、午前 11 時 30 分）が案内された。

### 6.1 デモ 1：Foundry Local のインストールとモデルの評価（Kushmeen 氏）

役割は Woodgrove Bank の AI 開発者です。CEO は、クラウドのエージェントの成果を称えたうえで「顧客の金融データをいつ載せられるか」と尋ねました。銀行のデータは厳しく規制されており、本番どころかパイロットでもクラウドに移せません。チームは 2 つのエージェント（銀行のリスク調査担当と窓口担当）を作ろうとしていて、まずモデルの選定が必要です。

1. Azure ポータルで、Azure Local 上で動く AKS クラスターを準備し、Foundry Local の拡張機能をインストールする。サブスクリプションを選び、デプロイのワークフローを開始する。
2. リージョンを選び、Azure Local 上で動く AKS クラスターを選ぶ。拡張機能に名前を付け、アクセスは Entra で管理する。
3. 拡張機能がデプロイされれば、モデルの検討を始められる。これは完全に切断した状態でもできるとして、ターミナルに切り替える。
4. Foundry Local の拡張機能が inference operator としてインストールされ、他の Pod もコンテナーの準備ができた状態で動いていることを示す。
5. Foundry Local カタログのモデル一覧（チャット、埋め込み、音声のモデル）を表示する。これは一部で、カタログには 300 以上のエントリーがある。
6. エージェント用に 3 つの候補を選ぶ：**GPT OSS 120B、Mistral Small 4、NVIDIA の Nemotron モデル**。Foundry Local の組み込みのモデル評価で、銀行の質問に対する性能を比べる。
7. デプロイには数分かかるため、3 つの候補が動いている評価用クラスターを事前に用意してある。**審査役（judge）となる小さな 4 つ目のモデル**もある。別の審査役モデルを使うのは、候補が自分で自分を採点しないようにするため。これらのモデルは **NVIDIA RTX Pro 6000 GPU** を搭載した Azure Local で動いている。
8. テストデータセットの CSV ファイルを見せる。銀行の質問と、期待される回答がペアになっている。
9. 評価は数分かかるため事前に実行済みで、評価の画面で結果を確認する。品質スコアは 1〜5 で、**similarity**（期待する回答との意味の近さ）、**completeness**（回答がどれだけ網羅されているか）、**relevance**（質問に答えているか）を、均等に平均している。
10. この結果から **GPT OSS 120B** を選ぶ。エージェント用の OpenAI 互換の保護されたエンドポイントが示される。

各モデルのスコアの具体的な数値は、音声では語られていません。

### 6.2 デモ 2：2 つのエージェントを作ってテストする（Anders 氏）

役割は、Kushmeen 氏の同僚で Woodgrove Bank の AI 開発者です。Kushmeen 氏がデプロイした GPT OSS モデルを使い、銀行の窓口担当向けと、銀行のアナリスト向けの 2 つのエージェントを作ります。Kushmeen 氏はモデルと推論用の拡張機能に続いて、エージェントとツール用の第 2 の拡張機能もインストール済みという前提です。

1. CLI で、まず拡張機能に対して認証する。
2. **local model endpoint** をインストールする。これで 2 つの拡張機能がつながり、Agent Service と agentic retrieval の両方がモデルにアクセスできるようになる。
3. 数秒で、ローカルモデルのエンドポイントが保存される。
4. **knowledge base**（データソースを入れる入れ物）に進む。2 つのペルソナを想定する。多くのデータソースが必要な、権限のある**銀行のリスクアナリスト**と、必要なものが少ない**窓口担当**。
5. **banking risk investigator** エージェントの定義を示す。名前、モデル（GPT-OSS 120B）、指示（このデモでは省略表示）、ツール（MCP。データへの接続）が定義されている。ツールには SharePoint があり、下にスクロールすると NFS ファイル共有がある。エージェントは MCP でデータソースに接続し、そのデータで回答を根拠づける。
6. Enter でエージェントを作成する。
7. **banking teller assistant** も作る。同じモデルで指示もほぼ同じだが、接続するデータソースの数が少ない。Enter でもう一度作成し、2 つのエージェントが準備できる。
8. チャット UI に切り替える。エージェントとツールの拡張機能をインストールしたときに、チャット UI は自動的にデプロイされ、すでに動いている。2 つのエージェント（bank risk investigator と banking teller assistant）が見える。
9. 画面の上部にモデル（GPT OSS 120B）が表示されている。bank risk investigator には 4 つのソースがあり、banking teller assistant にはそのうちの 2 つがある。
10. 全従業員に展開する前のテストとして、リスク調査エージェントに **75 万ユーロの国際送金**の調査を依頼する。4 つのデータソースをまたいで推論するので少し時間がかかる。窓口担当アシスタントには、特定の顧客の送金について尋ねる。
11. 通常は、agentic retrieval アプリの登録 URL の末尾に「/chat」を付けてアクセスする（自前のチャット UI を作ってもよい）。
12. リスク調査エージェントに戻ると、回答が出力されはじめ、出典がインラインで表示される。出典の中に、NFS ファイル共有からのものが 2 つ、bank risk system MCP へのアクセスがある。下部の sources をクリックすると、右側にすべての引用が表示される。
13. これで、Woodgrove Bank 自身のデータセンターで動き、ローカルの機微なデータに根拠づけられた 2 つのエージェントができた、と締めくくっている。実際の展開前には、もう少し厳密なテストを行うとのこと。

## 7. 注意点・発表者の気付き

* **別の審査役モデルを使う**：評価では、候補モデルが自分の結果を採点しないよう、別のモデルを judge にする、と説明されています。
* **デプロイと評価には時間がかかる**：モデルのデプロイと評価は数分かかるため、デモでは事前に用意・実行したものを使っています。
* **評価は CLI のみ**：自分のデータセットでの評価は現時点で CLI から実行し、ポータルは近日対応予定です。
* **ファインチューニングしたモデルは機微なデータ**：オープンウェイトのモデルでも、自社のデータで調整すれば保護の対象になります。
* **Command A Plus はマルチ GPU が必要**：強力な LLM のため、マルチ GPU 構成が前提です。
* **ガードレールだけでは足りない**：ガードレール、confidential computing、アクセス制御を組み合わせた、エンドツーエンドの戦略が必要と述べています。
* **NVIDIA の大規模推論は、まだプレビュー前**：発表時点の目標は来年（暦年）の上半期のプレビューで、詳細は後日共有されます。NVIDIA confidential GPU も準備中です。
* **Agent Service の最適化機能は今後**：組み込みのトレース、モニタリング、評価シグナルによる最適化は近日提供予定です。

## 9. まとめ

Foundry Local は Azure Local 上で GA になり、ソブリンな環境でのモデルのデプロイと評価、OpenAI 互換のエンドポイント、agentic retrieval による検索が使えるようになりました。エージェントを動かす Foundry Local Agent Service はパブリックプレビュー、開発環境の GitHub Enterprise Local は GA です。インフラ面では、小さな GPU サーバーから始めて、NVIDIA の大規模推論構成（目標は来年上半期のプレビュー）まで、同じ管理体験で拡張できます。

デモでは、Woodgrove Bank の設定で、拡張機能のインストール、3 つの候補モデルの評価と GPT OSS 120B の選定、権限の異なる 2 つのエージェントの作成と、出典付きの回答の確認が示されました。セキュリティについては、confidential computing とアクセス制御でモデルを守り、Guardrails と agentic retrieval で AI の出力を守る、という 2 つの面が説明されています。
