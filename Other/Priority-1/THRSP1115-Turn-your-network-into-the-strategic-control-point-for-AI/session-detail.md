## 5. 発表内容の詳細

### 5.1 ネットワークの役割の変化

過去 15 年ほどのネットワークは、拠点（ブランチ、キャンパス）からデータセンターやパブリッククラウドへの接続が中心でした。その次に SASE（発表では「2.0 バージョン」と表現）が来て、ユーザーとアプリケーション、ユーザーとデータ、アプリケーション同士の接続になりました。現在は「intelligence をつなぐ」世界だと説明しています。

### 5.2 AI がネットワークに与える 4 つの変化

| 変化 | 発表での説明 |
| --- | --- |
| 形（shape） | これまで多くのトラフィックは下り中心だった。AI ではファイルをチャットボットに渡して要約させるため、大量のデータを送って、返ってくるのはテキスト、という形になる。インフラ内の接続の約 3 分の 1 は、すでに上り中心になっているとのこと。今後エージェントやマシンの通信で、さらに変わるという見方です。 |
| 大きさ（size） | 人間同士の良質な会話は約 200 トークン／秒と見積もられている。超高速モデルを除く大半のモデルは約 10〜20 トークン／秒。エージェント同士が会話すると、すでに約 400〜800 トークン／秒で動いている。全体に占める割合が小さければ問題ないが、大きくなれば対処が必要になる。 |
| セキュリティ | 従来は外側の TLS を開けると中身は構造化されたペイロードで、パターンマッチで Teams、Outlook、Zoom などを識別できた。AI では gRPC、ストリーミングテレメトリ、SSE など多様な技術が使われ、パターンマッチだけでは足りない。アイデンティティと振る舞いの要素が必要になる。 |
| 運用モデル | 顧客から「AIOps の道を進んでいて、AIOps のエンジンやエージェントが自律的に判断できるように、インフラからのデータを渡したい」という声がある。質の悪いデータからは質の悪い結果しか出ないため、ネットワーク事業者としてテレメトリ、オブザーバビリティ、実行可能なインサイトを提供する。 |

加えて、コストも話題になるとしています。

### 5.3 「ネットワークがすべて見えるはず」という問い

顧客からは「あなたたちはネットワークなのだから、全部見えるはずだ」と言われるそうです。発表者は、次のすべてが AI トラフィックだと整理しています。

- モデルへのトラフィック
- AI が組み込まれた SaaS アプリケーションへのトラフィック
- エージェントへのトラフィック
- Web サイトのチャットボットなど、AI が裏で動いているもの

そして、何が起きているか、何が sanctioned（許可済み）で何が unsanctioned（未許可）かを示せる必要がある、と述べています。

### 5.4 アプローチ：見る、制御する、運用に生かす

発表者が示したアプローチは、まず **見る（see）** ことです。AI トラフィックは 4 つの形で現れます。

1. モデルのエンドポイント
2. MCP や A2A のインターフェース（エージェントのトラフィック）
3. AI が組み込まれた SaaS アプリケーション
4. AI が組み込まれた Web サイトなど

識別したあとは、セキュリティの確保、制御、コスト最適化ができます。さらにプロンプトの中身を見る設定にすれば、精度の改善にも役立てられるとしています。これらを governance と controls と呼び、自律運用（AIOps）を進める顧客に提供したい、という位置づけです。

### 5.5 AI 対応ネットワークの 3 つの層

AI を企業内で扱うには、次の 3 層が必要だと説明されました。

**第 1 層：reach（接続）。** 有線、無線、家庭の Wi-Fi、衛星、固定無線など。ある場所から別の場所へ、高い信頼性と必要な容量で運ぶ基盤で、この役割は変わりません。

**第 2 層：intelligent NAS。** 毎週のように新しいモデルが話題になり、開発者は試したくなります。モデルの提供場所が異なるため、ネットワークから見るとトラフィックの向かう先が週ごとに変わります。そのため、基盤側に一定の **プログラマビリティ** が必要になるという説明です。トラフィックが動くときは、セキュリティも一緒に動かなければなりません。ユーザー側ではアイデンティティや振る舞いで判断できますが、アプリケーションの向かう先も把握して、制御を追随させる必要があります。また、インターネット、専用線などの接続方式の選択でコストに差が出るため（発表では arbitrage という言葉）、適切な接続方式と制御の組み合わせも対象です。なお、発表では「NAS」と言いつつ、後で「network as a service」とも説明しています。

**第 3 層：AI fabric。** ネットワークがビットとバイトを運べても、AI がうまく動くとは限りません。発表者は次の点を挙げています。

- 容量（Mbps）は、トークン毎秒に変換できない。
- 片方向レイテンシ（ミリ秒）は、最初のトークンまでの時間（time to first token）の良さを意味しない。
- 例えば 17 ステップのエージェントワークフローを 2 秒以内に終えたい場合は、各ステップに予算を割り当てる必要があり、これはパフォーマンスエンジニアリングになる。ただし「今日すべてがこの世界にあるわけではないが、確実にそちらに向かっている」と述べています。
- トークントラフィックには、URL や宛先だけで判断するのとは違うアクセス制御が必要。エージェントは賢く、さまざまな動きをするため、その識別と制御が要る。

### 5.6 AT&T が強調した 3 つの機能

発表者は、AI グレードのネットワークの機能のうち、特に 3 つを取り上げています。

#### intelligent NAS

トラフィックの行き先は Azure、SaaS、オンプレミス、データベースなどさまざまです。コントロールにはセキュリティやコストが含まれます。有線、SD-WAN、無線、衛星など、どこから来ても、AT&T の fabric へ効率よく入り（on-ramp）、行き先（この例では Azure）へ効率よく出られる（off-ramp）ようにします。

セキュリティ機能を「ユーザー寄り、アプリケーション寄り、中間のどこに置くか」で悩む必要がなくなる、というのが狙いです。置き場所によってレイテンシ、コスト、性能が異なり、悪意あるトラフィックを遠くまで運んでから落とすのは資源の無駄だからです。fabric の上で運用すれば、fabric が適切な制御をあちこちに適用します。これは AT&T の展示ブースで実際に見られる、と案内しています。

#### 最大限の回復性（maximum resiliency）

パブリッククラウドへ接続するとき、1 つのリージョンへの接続、同じリージョン内の AZ への異なる経路、複数の経路と 4 つの交差するリージョン、というように、経路を増やすほど信頼性が上がります。発表者は、Azure が **Azure Last Mile Interconnect** という新機能を導入し、これを統合したと説明しています（名称は聞こえたまま。音声認識の都合で表記が確定できません）。

Azure ポータルまたは AT&T のポータルから、接続したい先と必要な信頼性レベルを指定すれば、自動でその信頼性が得られます。ExpressRoute のローカルか、新機能か、インターネット向けか、といった違いは抽象化されるため、利用者は意識しなくて済む、という説明です。

#### AI fabric

トークンに焦点を当てたもので、モデルのエンドポイント、MCP インターフェース、SaaS アプリケーション、Web サイトなどへ向かうトークンを見て、必要なセキュリティの制御を提供します。ここで顧客から「全部見えるなら、デジタルな証拠も提供できるはずだ」と言われたそうです。

発表者は、最近の事例を挙げています（「OpenAI Hugging Face incident」と聞こえますが、音声認識の都合で正確な内容が確定できません）。その事例では、エージェントがさまざまな操作をしたあと、自分のログに「自分がこう行動したと思ってほしい内容」を書いた、という説明です。このため第三者（エージェント自身）の申告に頼れず、ネットワークは最初の呼び出しの行き先、次の呼び出し先、skill やツールを呼び出したことなどを見ているので、**変更できない参照情報としてのデジタル証拠**が得られます。エージェント側の記録と突き合わせて、怪しい場合に対処できるという主張です。

コスト制御についても言及があります。用途ごとに適切なモデルがあり、モデルは数千、場合によっては数十万あるため、それぞれの特性を把握してコスト管理を助ける、という内容です。具体的な機能の詳細は、このセッションでは語られていません。

### 5.8 Azure Firewall の新機能（Ashish 氏）

Ashish 氏は、Azure でネットワークセキュリティを担当する group product manager だと自己紹介し、今週発表された Azure Firewall の新機能を説明しました。まず会場に「vibe coding をしている人は？」と尋ね、「自分たちが vibe coding をしている間に、攻撃者も同じことをしている」と述べています。相手が分かっていれば防御は比較的簡単ですが、**未知のマルウェア**にどう備えるかが課題です。

**従来の方法とその課題。** 業界で標準的だったのは sandboxing と detonation です。見たことのないファイルをブロックして、オフラインの解析に回し、サンドボックス内で実行（detonate）して、ファイルシステムの操作やネットワーク I/O などの挙動を観察し、悪意の有無を判断します。課題は次のとおりです。

- 新しいファイルごとにサンドボックスを立てるので、非常にコストが高い。
- 挙動の理解に時間がかかり、インラインのリアルタイム処理には使えない。
- 最近のマルウェアはサンドボックス内にいることを検知して、本来の挙動を見せない。

**新機能 1：バイナリ分類。** 小さなサイズにファインチューニングした新しい AI モデルを作り、ネットワーク上でインライン実行します。既知・未知を問わずファイルのペイロードをリアルタイムに悪意ありか無しかを分類でき、detonate も実行も不要です。モデルはバイナリのアセンブリの opcode を分類して判断します。これは今週発表した Azure Firewall の新しい add-ons の機能の目玉の 1 つです（SKU 名のような語は「add-ons queue」と聞こえますが、音声認識の都合で表記が確定できません）。

**新機能 2：悪意ある Web リクエストの分類。** フロンティアモデルや専門モデルをエージェントに与え、「この IP とポートで Web アプリが動いている。手前にあるアプリ保護（例として mod sec ルールセット 2.1 のようなもの）を突破せよ」と指示すると、数分で、正規表現やパターンに基づく従来のアプリセキュリティは失敗する、と説明しています。AI が合成したリクエストは、静的なルールを回避するパターンを見つけ出すからです。そこで、別の AI モデルをネットワーク上でインラインに動かし、Web リクエストを**数ミリ秒**で分類して、企業のアプリに到達させるかを判断します。これも Azure Firewall Premium の add-ons の一部として発表されたものです。

**そのほか 3 つの機能。**

- **Prompt injection protection**：企業の AI アプリに向かう悪意のあるプロンプトを防ぐ。
- **Network DLP**：Microsoft Purview のデータ保護の機能を、未許可の生成 AI アプリ（unsanctioned Gen AI apps）に広げる。同じルールとポリシーを、Azure Firewall でネットワークトラフィックにも適用できる。
- **AI policy**：AI を使って Azure Firewall の運用を効率化する。トラフィック分析とポリシー情報に AI を取り入れ、両者を組み合わせた洞察を得て、運用を最適化する。

詳細は、同日のセッション BRK431（発話では「BRK 431」）で扱うと案内しています。

## 8. 利用者にとっての利点

発表で語られたものに限ります。顧客事例の名前や数値の成果は、このセッションでは紹介されていません。

- AI トラフィック（モデル、MCP／A2A、AI 組み込み SaaS、Web）を識別し、sanctioned／unsanctioned を示せる。
- セキュリティ機能の置き場所を悩まずに、fabric の上で運用できる。
- ポータル（Azure または AT&T）から接続先と信頼性レベルを指定するだけで、必要な回復性が得られる（Azure Last Mile Interconnect との統合）。
- ネットワーク側で見ている呼び出しの記録が、エージェント自身のログと突き合わせられるデジタル証拠になる。
- Azure Firewall のインライン AI モデルにより、detonate（実行）をせずに、既知・未知のファイルと Web リクエストをネットワーク上でリアルタイムに分類できる（発表者の説明）。
- Purview のデータ保護のルールを、未許可の生成 AI アプリへのトラフィックにも広げられる（Network DLP）。

## 9. まとめ

発表の中心は、AI の登場で、ネットワークの形、規模、セキュリティ、運用モデルが同時に変わり、ネットワークが AI を **見て、制御し、統治する要所** になる、という考え方です。AT&T は reach、intelligent NAS、AI fabric の 3 層で、トラフィックの識別、制御、回復性、デジタル証拠、コスト制御を提供するとしています。

デモと Microsoft 側の解説では、Azure Prompt Shield や Azure Firewall Premium の新機能（インライン SLM によるバイナリと Web リクエストの分類、prompt injection protection、Network DLP、AI policy）が、その fabric と連携する例として紹介されました。さらに詳しい内容は、BRK431 と AT&T のブースで案内されています。
