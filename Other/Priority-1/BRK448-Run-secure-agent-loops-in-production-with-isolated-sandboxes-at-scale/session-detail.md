# BRK448 Run secure agent loops in production with isolated sandboxes at scale

## 1. はじめに

このセッションは、エージェントを本番環境で安全に動かすための実行基盤として、**Azure Container Apps（ACA）の Sandboxes** を紹介するものです。公式の概要にもあるとおり、エージェントを本番で動かすことは「モデルの問題ではなく、プラットフォームの問題」だという立場で話が進みます。

構成は、問題提起と全体像、Nous Research（Hermes Agent）の事例、ACA Sandboxes のデモ付きディープダイブ、Cognite の産業向けエージェントの事例、まとめの順です。ACA Sandboxes は、ハードウェアで分離された microVM を、ネットワークや ID のガードレール付きで提供する Azure のマネージドサービスです。発表の中心は、microVM による分離、egress proxy によるネットワーク制御と secretless（シークレットを置かない）構成、snapshot、コネクターとトリガーといった機能と、それを実際に使っている 2 社の話です。

## 5. 発表内容の詳細

### 5.1 エージェントの本番運用：リスクと sandbox の位置づけ

Devanshi は会場に、エージェントを本番で動かしているか、それを安全に、意図どおりに動かせているかを手を挙げて尋ねました。続いて、エージェントが設定した境界を越えて動き、会社がニュースになる事態を想定させ、どう止めるか（ガバナンス、権限、分離などの答えが会場から出ました）を問いかけています。

数値としては、IT アプリケーションのリーダーの **74%** が、エージェントが攻撃ベクトルになると答える一方で、フリート（エージェント群）を管理するガバナンスが整っていると答えたのは **13%** にとどまる、と紹介されました。

隔離の選択肢については、次のように比較しています。

| 方式 | 特徴（発表での説明） |
| --- | --- |
| VM | 分離は強いが、重く、遅い |
| コンテナー | 速くて高密度だが、カーネルを共有する。モデルが生成した信頼できないコードに対しては境界が薄い |
| ハードウェア分離の microVM | カーネルの境界と、高速な起動、アイドル時のコストなし、の両方が得られる |

Azure Container Apps Sandboxes は、このマネージドな microVM を、ネットワークや ID のガードレール込みで提供するものとされます。短時間のエージェントも長時間動くエージェントも、コンテキストを保ったまま動かせ、バースト的な負荷にも対応し、アイドルの計算コストはかかりません。すでに顧客と Microsoft 内部の両方で大規模に採用されており、Foundry Agent Service、GitHub Copilot の体験、Copilot Studio、SRE Agent などの基盤層になっていると説明されています。

### 5.2 Nous Research の事例：Hermes Agent

Hermes Agent は、Open Router 上の公開オープンエージェントで 1 位にランクされ、1 日に 2 兆トークン近くを処理している、と紹介されました。以下は、Jeffrey の発言です。

**Hermes Agent の成り立ち**

約 1 年前にオープンソース化したもので、もともとはモデル研究者が学習用の RSI ループのようなものに取り組むための社内ツールでした（RSI の意味は発話では説明されていません）。計画した製品ではなく、公開が「偶然」「後付け」のようなものだったそうですが、2 週間で GitHub の 1 位になりました。決め手は、エージェント自身の **継続的な自己改善ループ** です。

- ユーザーが意識しなくても、使うほど良くなる。OpenClaw のようにスキルファイルを自分で書く必要がない
- 使っているうちにバックグラウンドでスキルファイルを自動的に育てる
- 決定論的な処理だと気づいたものは、LLM を通さず、決定論的なコードのワークフローとして組み立てる

エンタープライズでの意味合いとして、「最も優秀な社員のスキルを、全社員に広げられる」というたとえが使われました。

**企業に持ち込むときのリスク**

- 1 人でローカルで使うなら、信頼境界は自分の PC 全体で済む。企業では「できるからといって、すべきとは限らない」ため、それを明文化する必要がある
- 個人に固有で、組織には無関係な内容がスキルファイルに入ってほしくない。全社員に配られる内容を検査・制御するガバナンス層が要る

**Azure Container Apps Sandboxes を選んだ理由**

「自分たちの要件にぴったり合った」と述べ、次を挙げています。

- スキルファイルを従業員全体に自然に広げたい
- 支出を管理するコントロールプレーンが欲しい（2027 年に向かう中で、トークンの支出を考えない企業の人はいない、という趣旨）
- 信頼できるスタックであること。Hermes Agent はオープンソースで、特定のモデルベンダー（Anthropic や OpenAI のトークンなど）に縛られない
- チームが使うほど蓄積される「AI IP（集合的な知恵）」を自社の資産にし、ガバナンスとデータの出所（data provenance）を確保したい

**アーキテクチャ**

1. **入り口（フロントドア）**：デスクトップクライアント、API 経由のエージェント・アズ・ア・サービス、メッセージングプラットフォーム（Teams や Slack）の 3 種類。ベータ中のモバイルアプリは、ACA Sandboxes だけで動き、ローカルの選択肢はない
2. **エンタープライズのコントロールプレーン**：SAML や Entra ID による認証設定、モデルごとの支出管理など。「Spend Intelligence」という機能で、ユーザーの種類別にどのモデルを使っているかを見て、たとえば 100% 同じモデルを使う代わりに 95% にしても同じ挙動か、といった調整ができる（モデル名は「Fable」と聞こえますが、音声認識の都合で表記が確定できません）。SaaS のような従来型のガバナンス層
3. **sandbox**：エージェントは何かを構築・実行するため、状態を持つこと（statefulness）が特徴で、従来のサーバーレスの部品に分解するのは非常に難しい。「VM の良い部分だけを持ち、悪い部分がない」ものが理想だった。ユーザーや従業員ごとに複数のエージェントを持つ段階では、将来は数十万、数百万、数千万のエージェントになり得る、と述べています

**本番での実績**

- ホスト型の Hermes Cloud 製品は、最初は別のクラウドプロバイダー上で始め、Azure の Container Apps Sandboxes に切り替えた
- 先月時点で、**約 20,000 のアクティブなインスタンス**。大手企業数百社が利用しているが、これはユーザー全体のごく一部で、ローカルで動かす人が多い
- 負荷は非常にバースト的（ユーザーが別のウィンドウに切り替える等）。常に存在する VM のような見え方と状態保持が必要で、かつ起動が即時なので、scale to 0 が成り立つ。2 万、10 万、100 万のインスタンスを常時課金したら経済性が合わない

**会場への学び（Jeffrey）**

1. セキュリティは、最も信頼しない領域である、ハードウェア VM のカーネルレベルで確保する
2. 経済性を考え、必要な分だけ払う
3. ソフトウェアの機能としての「知能」は誰でも使えるものになる。組織が積み上げる AI IP を、自社の付加価値（secret sauce）にする。Satya 氏が話した tacit knowledge と同じ考え
4. CPU や RAM の価格は上がり続け、1 年で 2 倍、3 倍になる前提を持つ。最悪なのは、成功したのにスケールできないこと（pinch point）

### 5.3 ACA Sandboxes のディープダイブ（Jan）

Jan は、ACA Sandboxes が、44 のリージョンで 1 日あたり **200 万を超える** sandbox として動いていると述べています。

**概念**

- sandbox は Azure のリソースで、**sandbox group** というエンティティの中に作られる
- sandbox は running、stopped などの状態を持つ
- 前身の製品は **ACA Dynamic Sessions**。そこでの大きな学びは、顧客が依存関係やカスタムのエージェントハーネスを動かすため、**自分のカスタムイメージ** を持ち込みたがる、ということだった。そのため、カスタムのディスクイメージと、長時間のタスク向けの snapshot がある
- **ingress proxy**：sandbox の外にあり、sandbox 内のコードに制御されないプロキシ。ポートの対応付けと、認証の設定ができる
- **egress proxy**：同様に sandbox の外にあるリソースで、sandbox 内のコードは sandbox ごとのポリシーを変更できない。エージェントが必要とする外部エンドポイント（LLM、社内のデータベースやナレッジベースなど）への通信を制御する。さらに **secretless sandbox** として、sandbox がシークレットを持たずにエンドポイントに認証できる
- **永続化**：sandbox は一時的で削除されるため、sandbox より長く残したいデータは、マネージドのデータディスクやマネージドの Blob で保存できる（標準で用意）。自分の Blob ストレージも持ち込める。まもなく、SQL または Postgres へのデータ保存も発表予定で、これも secretless の原則に従う
- **マネージドのトリガーとコネクター**：トリガーは必要なときに sandbox を起こし、コネクターはサードパーティのシステムに、シークレットを意識せずに安全にアクセスする

### 5.4 Cognite の事例：Atlas AI

Christian は、Cognite が 10 年前に創業し、石油・ガス、製造、エネルギーなどの重工業に、機械学習と AI を持ち込むことを目指した、と紹介しました。

**データの問題から始めた**

製油所のポンプ 1 台でも、圧力データ、保守の作業指示、配管計装図（P&ID）、3D モデルが、別々のソースシステムにあり、形式も識別子も異なります。そのまま使うとシステムごとの point-to-point の統合が必要で、スケールしません。そこで **Cognite Data Fusion** を作りました。ソースシステムに 1 回つなぎ、コンテキスト付きのコピーを作ってナレッジグラフにすることで、ポンプとセンサーデータ、保守データなどが 1 つの API でつながるようになります。

現在のデータ基盤は、業界で最大級のコンテキスト付き産業データを保持しており、**100 兆を超えるデータポイント、50 億のグラフノード、4 億のドキュメントとファイル** があり、すべて 1 つの API で使えるとのことです。

**Atlas AI のエージェント**

約 3 年前に、この API の上でエージェントのサービス **Atlas AI** を開始し、産業現場の本番のユースケース（生産の増加、運用の安全性向上）で使われています。システムプロンプト、言語モデル、ハーネスが制御するツール、スキル、サブエージェントといった標準的な構成要素を持ちます。

ブレークスルーは、**エージェントに「コンピューター」を与えたこと** で、それが sandbox でした。産業の質問は汎用ツールの集合には収まらず、エージェントがコードを書き、最も機密性の高い運用データにつながったまま安全に実行する必要があるためです。理由として次の 5 点が挙がりました。

1. ユーザーごとの会話を、エージェントを信頼するのではなく、カーネルで分離する必要がある
2. egress を制御し、エージェントが使えるエンドポイントを正確に把握したうえで、シークレットを sandbox の外に置く
3. 企業にはプライベートネットワークがあり、sandbox がそのネットワーク経由で接続する必要がある
4. 高速な起動に加え、依存関係を含めるため、カスタムのディスクイメージが不可欠だった
5. メトリクスやログなど、観測性が必要

結果として、sandbox を使った最初のエージェントは **数日** で開発でき、**数週間** で本番に入りました。すでに中核のエージェント機能の一部になっているそうです。

**学び（Christian）**

- セキュリティを前提に設計する。カーネルを分離し、エージェントが正しく作るとは信頼しない
- デモでは sandbox の複雑さは見えない。顧客価値に集中することが狙い
- Microsoft とパートナーを組み、sandbox の配管（plumbing）を自分で作らず、すでにあるものを使う

## 6. デモ・手順

このセッションでは、Jan が 4 つのデモを行い（途中でタイプミスが続き、Devanshi が操作を手伝う場面があります）、Christian が Cognite のデモを紹介しています。録音は音声のみのため、画面の細部は分かりません。以下は語られた内容を順に書いたものです。

### 6.1 デモ 1：sandbox を 3 つの方法で作る

1. Azure portal で、sandbox（または「container apps sandbox groups」）を検索する。sandbox group は事前に作成済み
2. 「create sandbox」を選び、ベースイメージを選ぶ。ベースイメージは Microsoft が作成し、少なくとも月に 1 回リリースされる。多様な開発フレームワークや、エージェントのハーネスも含まれる。デモでは Python のイメージ（バージョンは聞き取り不明瞭）を選択
3. サイズを選ぶ。**1/4 コアから 16 コア** まで選べる。ラベルは任意
4. 作成を押すと、検証が成功し、sandbox が起動する。bash を使ってリスト表示ができる
5. 画面の側面に egress（あとで触れると説明）が表示され、そのほかリソース統計、ログストリーム、プロセス、ファイルシステム、ボリューム、コネクター、トリガーが見られる
6. SDK（Python と .NET に聞こえます。ほかも追加予定）、CLI、Bicep と Terraform でも sandbox group を作れる。エージェントスキルを好きなエージェントに入れれば、エージェントが sandbox の作成、コードのデプロイ、デバッグまで行える
7. CLI：サブスクリプション、リソースグループ、sandbox group は設定済み。sandbox を作成するコマンド（「ACS sandbox create」と聞こえます。音声認識の都合で表記が確定できません）に名前（CLI）を付けて実行し、portal で CLI から作った sandbox が増えたことを確認
8. **VS Code の Azure Resources 拡張機能が、sandbox をネイティブにサポートする**（この場で発表）。同じパラメータで作成し、sandbox shell を開く。ローカルの Windows ではなくリモートのマシンで動いていることを、OS release ファイルを表示して確認（Ubuntu）

### 6.2 デモ 2：カスタムイメージ、ingress、snapshot

1. 起動済みの sandbox と、2 つのカスタムイメージ（Orchestrator と Metrics）を用意。これらはコンテナー（OCI）イメージを、sandbox が起動できるイメージに変換したもの
2. sandbox に ingress 用の URL がある。ポートの割り当て、トラフィックが来たら起動する設定、認証（テナント ID を追加すればそのテナントの全員、自分の ID なら自分だけ）を設定できる。デモでは設定済みのものを開く
3. sandbox 内で動くアプリが、**25 個の sandbox を追加で起動**し、Metrics イメージで 1 から 1,000,000 までを数える
4. それらを停止して snapshot を作成し、再開すると、中断した続きから動く
5. 実際のエージェントではスケジュールが異なる。sandbox group には 26 個（Orchestrator 1 個と 25 個）があり、削除すると Orchestrator だけに戻る

### 6.3 デモ 3：egress proxy と secretless

1. 起動した sandbox で、egress proxy を通ったトラフィックが、許可と拒否で表示される。全トラフィックは deny all で、github.com と、LLM を想定した独自のエンドポイントだけ allow ルールがある
2. 許可リストにある GitHub へ curl で通信する（タイプミスが続いたため、Devanshi に手伝ってもらい、www.github.com に curl して、通信が通った緑の行が表示されるのを確認）
3. 独自のエンドポイントへ通信するスクリプト ping.sh は、リクエストに「my secret」というシークレットを埋め込む。別の sandbox で動くトラフィックインスペクターに、その API の値がそのまま表示される
4. security で、シークレットのキーと値のペアを定義する（設定済み）
5. ルールを allow ルールから **transform ルール** に変え、X API key のヘッダーが、定義したシークレットを参照する変換を追加して保存する
6. インスペクターで、X API key の値が proxy によって注入されたものに変わっていることを確認

### 6.4 デモ 4：GitHub Copilot sandbox とコネクター

1. sandbox の作成で、**GitHub Copilot sandbox** を選ぶ。エージェントが正しく動くよう、transform ルールと allow ルールがあらかじめ設定され、GitHub アカウントのトークンが注入される
2. 下の方に、Work IQ のカレンダーコネクターなどがある。Logic Apps チームのコネクターが 1,700 以上あるという説明（Logic Apps チームがこれを「container namespace」として最近発表した、という発話は聞き取りが不明瞭）。Azure Functions にも統合されている
3. Work IQ カレンダーを追加する。作成時に認証が必要（設定済み）。on-behalf-of にも対応し、プログラムから sandbox を作る場合でも、個人に代わって認証できる
4. Copilot を実行すると認証され、チャットできる。「今週のカレンダーを要約して」と依頼し、Ignite の今週の予定が返ってくる。Work IQ コネクター経由でカレンダーにアクセスできたことになる

### 6.5 Cognite のデモ：保守エンジニアの isolation boundaries 作成

Christian が、保守エンジニアの例を、画面を見せながら説明しています（「Let's take a look」「Here we found an engineering diagram」といった発話）。ライブか録画かは、音声からは判別できません。語られた内容は次のとおりです。

1. 製油所の熱交換器（高温の流体やガスを、接触させずに低温の流体で冷やす機器）の保守を行う保守エンジニアという設定。インシデントを起こさず、生産を必要以上に止めないようにする必要がある
2. 従来は、エンジニアが正しい配管計装図を 1 つのソースシステムで探し、ほかと突き合わせて手作業で行う
3. エージェントが、ナレッジグラフで engineering diagram を探し、ダウンロードして調べ、見つけた図をユーザーに提示して確認してもらう。図には 2 つの楕円（熱交換器）と、周囲の配管、円、四角がある
4. 「isolation boundaries（隔離境界）を作って」と依頼すると、sandbox でファイルをダウンロード・検査し、コードを実行し、ナレッジグラフから追加情報を取得する。事前に定義したツールなしで、コンピューターへのアクセスだけで行う
5. ユーザーが検証できる計画を作成し、さらに図の機器を強調表示して、安全に保守するために閉めるべきバルブを特定する

## 7. 注意点・発表者の気付き

- 権限を減らすと安全になるが、エージェントの価値も減る。バランスが必要。
- コンテナーはカーネルを共有するため、信頼できないモデル生成コードの境界としては薄い。
- sandbox は一時的で、削除されると中身は消える。残したいデータは、sandbox の外のストレージに置く。
- エージェントはバースト的で、状態を持つ。常時課金では経済性が合わないため、アイドルのコストがなく、起動が速いことが重要。
- 企業で自己改善型エージェントを使う場合は、個人固有の学習が全社に広がらないよう、検査と制御のガバナンス層が必要。
- 前身の ACA Dynamic Sessions の経験から、カスタムイメージの需要が大きい。
- CPU や RAM の価格は上がり続けるため、成功してもスケールできない事態に備える。

## 8. 利用者にとっての利点

- **Nous Research**：約 20,000 のアクティブなインスタンスを Azure Container Apps Sandboxes で運用し、大手企業数百社が利用。scale to 0 により経済性を成立させている。
- **Cognite**：sandbox を使った最初のエージェントを数日で開発し、数週間で本番に入れた。保守エンジニアの手作業だった isolation boundaries の作成を、エージェントに任せられる。
- 発表全体：sandbox が、カーネル分離、egress の制御、secretless な認証、snapshot、コネクターとトリガーを標準で提供するため、利用者がこれらを自前で作らずに済む。

## 9. まとめ

公式の概要によれば、エージェントの本番運用は、モデルではなくプラットフォームの課題であり、分離、ID、ガバナンス、観測性、コスト管理が求められます。Azure Container Apps Sandboxes は、ハードウェア分離の microVM をマネージドで提供し、egress proxy、ingress proxy、snapshot、ストレージ、コネクターとトリガーを備えています。Nous Research と Cognite の事例は、実際に本番で使われていることを示しています。
