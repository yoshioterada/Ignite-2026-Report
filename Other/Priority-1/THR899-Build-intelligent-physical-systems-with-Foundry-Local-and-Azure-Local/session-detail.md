## 5. 発表内容の詳細

### 5.1 従来のオートメーションの課題

従来の製造オートメーションは、動作ルーチンやウェイポイントをハードコードし、すべてが常に同じ構造化された環境で、ロボットが掴む対象と置く先のインターフェースの許容差も非常に厳しいことを前提にしています。生産量の多い製品には適しています。

一方で、次の課題があります。

- 開発と統合のコストが高く、同じことを大量に繰り返す場合にしか採算が合いません。
- 柔軟性がないため、人が行う工程とロボットが行う工程が混在するワークフローにロボットを参加させるのが難しい。人が途中まで作業し、次の工程をロボットに引き継ぐ形は、従来のロボティクスでは非常に難しいとされています。

### 5.2 Danfoss の事例

Danfoss は、ポンプ、バルブ、ドライブなどの部品を作る、デンマークの大手メーカーです。**80 万種類を超える固有の製品を、しばしば小ロットで**生産している、非常に高混合な製品構成が特徴です。

例として、**IC7 variable frequency drive（VFD）**が紹介されました。これは 1 つの製品ではなく製品ファミリーで、船舶用、建物や HVAC 用、重工業用など、業界ごとの要件に合わせた派生版があります。物理的なサイズと形が少しずつ異なるため、組み立ても少しずつ異なります。受注生産で、たとえば 10 隻の船のために 10 台を注文すれば、その分が作られます。このような製品構成では、ロボットやオートメーションの導入が難しくなります。

そこで Danfoss が Universal Robots に相談し、Universal Robots が Microsoft に、AI の専門性を活かせないかと声をかけました。Microsoft は、物理的な知能に対してより一般化したアプローチを取り、製品ラインの異なる派生版でも問題なく動くシステムを作ることに挑戦しました。

### 5.3 動画で示されたロボット

動画に映っているのは、Universal Robots の **UR7 cobot** が、IC7 VFD の一部を組み立てている様子です。

- ロボットには、ハードコードした動作ルーチンも、移動先のウェイポイントも与えていません。
- 与えたのは「fit the heat sink into the bottom plate」という平易な指示だけで、ロボットがそれを解釈し、自分で動作を計画して作業を完了します。
- 部品の置き方が少し違っても、ヒートシンクとボトムプレートの開始位置が逆であっても、同じように作業を完了できると説明されました。

登壇者は、次の 2 点を断っています。

> 注意：これは Microsoft のテスト施設で動かしたもので、Danfoss が実際に工場で運用しているものではありません。また、動画は理解しやすいよう**早送り**してあり、実際のロボットは、何も壊さないよう、また学習しながら進めるため、かなりゆっくり動かしています。

### 5.4 ハードウェア構成

登壇者は「魔法ではない」として、ハードウェアを説明しています。

| 要素 | 内容 |
|---|---|
| ロボット | 業界標準の UR7 cobot（6 自由度のロボットアームで、非常に普及している） |
| グリッパー | 先端に adaptive gripper を接続 |
| カメラ | 複数の RealSense カメラ。D410 は視野が狭く精密な操作向け、D435 はより広い視野向け（機種名は音声認識の都合で表記が確定できません） |
| エッジコンピューター | NVIDIA Jetson の開発キット（型番は音声認識の都合で確定できません。後半で Jetson Thor と Jetson Orin が例に挙がります）。ロボット開発の定番になりつつあるとのこと |

これらがすべてエッジコンピューターにつながり、その上で動くソフトウェアが、動画で見た動作を実現しています。

### 5.5 VLA モデル

動作を担うのは、**vision language action モデル（VLA）**という新しい種類の AI モデルです。言語モデルは、テキストを入れてテキストを出力します。これに対して VLA は、**ロボットの現在の関節位置と、カメラ映像を入力として、次の関節位置を予測**します。ロボットはこれを繰り返して一歩ずつ動くため、動画でも小刻みに動いて見えます。

実行はすべて、ロボットにつないだ NVIDIA Jetson 上の、Azure Local 上の Foundry Local で行われています。このデモで使った VLA は **Pi 0.5** で、会場の近くにある企業 Physical Intelligence が作ったオープンソースのモデルです。ほかにも使えるモデルはあり、NVIDIA の新しい「group」モデルも例に挙がりました（綴りは音声認識の都合で確定できません）。

登壇者は「平易な指示でロボットが動くなら、もう終わりか」と問いかけ、「そうではない」と述べています。解決すべき課題があるためです。

### 5.6 学習: Microsoft Foundry

VLA は、そのまま使えるわけではありません。**ロボットの身体性（embodiment）を学習する必要があります**。具体的には次の点です。

- 関節の数と、可動範囲の限界
- カメラの数、位置、フレームレート、解像度、視野
- 扱うタスクと物体の種類（たとえばヒートシンクなら、見た目と、落とさない持ち方を練習する必要がある）

登壇者は、新入社員に仕事を練習させるのと同じで、VLA にも担当する仕事を「オンボード」する必要があるとたとえています。

そのために **Microsoft Foundry** を使いました。手順は次のとおりです。

1. Foundry の trusted catalog から、ベースモデルを選ぶ。カタログは 11,000 を超えるモデルから選べる。今年新しく、Pi 0.5 のような physical intelligence モデルが private preview で加わった。今回は Pi 0.5 を選んだ。
2. トレーニング用のエピソード（実行させたいタスクの練習走行）を用意する。取得方法は 2 つ。teleoperation（遠隔操作）、またはロボットの 3D 表現を作って simulation で訓練する方法。今回は始めやすい teleoperation を選んだ。
3. タスクを数回行って記録し、クラウドにアップロードする。
4. クラウドで fine-tuning を実行し、新しい checkpoint（そのロボットの身体性に特化した新しいモデルの重み）を作る。
5. 最後に、ロボットにデプロイする。

### 5.7 推論: Foundry Local

デプロイ先で使うのが **Foundry Local** です。**Linux コンテナーとして提供される推論サーバー**で、ロボット上で動き、モデルをローカルで提供します。今回は NVIDIA Jetson に配備しています。

デプロイ後は、実行時にクラウドへ依存する必要がありません。次の関節位置の予測をローカルのコンピューターだけで繰り返し行うため、レイテンシや信頼性の面で**挙動が一定で予測しやすい（deterministic）**と登壇者は説明しています。ここまでが、Microsoft Foundry と Foundry Local で物理的な知能を作る前半の話で、「難しかったが楽しかった」とのことです。

### 5.8 大規模展開の課題と Azure Local

前半の話は 1 台の知的な物理システムです。実際には、Danfoss は世界に 100 を超える工場を持っており、大規模に展開する手段が要ります。ここから Teodora 氏が説明します。

VLA モデルを動かすには、リアルタイムかつデバイス上で判断できる、AI 対応の強力なデバイスが必要です。例として Jetson Thor や Jetson Orin が挙がりました。これらは ARM64 ベースで、強力な GPU アクセラレーションとコンパクトで省電力な設計を組み合わせており、ロボティクスと物理 AI の定番プラットフォームです。

しかし、100 台や 1,000 台を運用するのは別の問題です。登壇者は、ラボで見られる運用を次のように挙げています。

| フェーズ | 従来のやり方 |
|---|---|
| インストール | キーボードとモニターを物理的につないで OS を入れる |
| 構成 | ネットワークとソフトウェアの設定に、カスタムスクリプトを使う |
| アクセス | チームでパスワードを共有してしまい、セキュリティリスクになる |
| 監視 | 自前運用のオープンソースか、有償のベンダー製品との統合に頼る |

これはデモや試作ならよくても、複数拠点の 100 台、1,000 台には、実用的でなく、遅く、セキュリティ上のリスクがあります。

そこで、**エッジデバイスをクラウドのリソースのように管理する**というのが Azure Local の考え方です。**今週、Azure Local の NVIDIA Jetson 対応が発表されました**。エッジマシンは新しいリソースで、Azure Local の RP によってプロビジョニングされます。Azure portal に VM のように表示され、Azure portal、Azure CLI、テンプレートといった使い慣れたツールで構成・管理できます。Azure Arc を拡張しているので、Arc の機能に加えて、Azure ベースのプロビジョニング、管理、セキュリティも得られます。

### 5.9 デバイスのライフサイクルに沿った機能

#### インストール

**ゼロタッチプロビジョニング**を使い、デバイスを開始用の環境に載せて、ownership voucher を収集します。そのうえで Azure portal から、複数のマシンをまとめて追加し、クラウドから OS イメージを選びます。画面の例では Ubuntu をインストールしており、Azure Linux も選べます。

#### 更新

更新も Azure portal から行うため、更新に失敗しても現地へ人を送らずに済みます。**イメージベースの A/B swap モデル**を使い、稼働中の OS とは別の非アクティブなパーティションに新しいイメージをダウンロードします。再起動時に新しいイメージへ切り替わり、失敗した場合は、最後に正常だったバージョンへ**ロールバック**します。ワークロードの中断を抑えられる更新方法だと説明されています。

#### ハードウェア資産の管理

デバイスがオンラインになると、Azure がハードウェアを検出し、**ネットワークインターフェース、ディスク、GPU を子リソースとして**管理できるようにします。静的 IP アドレスの設定やストレージボリュームの構成ができます。ロボットのように常に有線とは限らないシステム向けに、Wi-Fi への参加も一元的に行えます。これらは例で、さらに追加していく予定です。また、デバイスが報告する値と、ユーザーが構成した値が食い違う場合は、その差分に印を付け、ユーザーが変更できるようにします。

#### アクセス: パスワード共有の置き換え

共有パスワードの代わりに、**短命のローカルアカウントと、secure な just-in-time アクセスモデル**を作ります。登壇者は、チームはすでに Entra ID を使っているはずなので、改めて設定する必要はないと説明しています。接続したいときに、privileged identity management（PIM）を通じて、接続する時間と理由（トラブルシューティングなど）を選び、**短命の証明書**で接続します。

- パスワードを共有したり書き留めたりする必要がなく、一度も更新されない長命のパスワードもなくなります。1 人に 1 組の資格情報です。
- PIM により、誰がデバイスにアクセスしたかの監査履歴も簡単に確認できます。
- デバイスの隣にいる必要はありません。ユーザーがクラウドに、デバイスがクラウドにそれぞれ到達できれば、SSH で入って変更できます。

#### 監視

標準で **30 を超えるメトリクス**が含まれます。物理 AI で重要な、GPU 使用率、温度、電力も含みます。Azure workbook などで可視化でき、アラートやルールも設定できます。たとえば過熱の問題があれば、先手を打って対処できる、と説明されています。

### 5.10 ARM64 のスタック全体

インフラ層は始まりにすぎず、**ARM64 のサポートがスタック全体に広がっています**。

- NVIDIA Jetson 上で、Bare Metal と Arc 対応の Kubernetes を実行できる。
- Azure IoT Operations、Foundry Local、独自のカスタムコンテナーなど、用途に合ったアプリケーションを実行できる。
- Intel ベースの 64 ビットと ARM64 のどちらのハードウェアでも、Microsoft は物理 AI のシナリオに全体のスタックを使えるようにする。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

## 9. まとめ

Danfoss の事例では、UR7 cobot が、平易な指示だけで IC7 VFD の組み立てを行いました。これは、Microsoft Foundry で VLA モデル（Pi 0.5）を fine-tuning し、Foundry Local でロボット上の NVIDIA Jetson に配備して実現したものです。

それを大規模に展開する基盤として、Azure Local が NVIDIA Jetson に対応し、インストール、更新、アクセス、監視を、クラウドのリソースと同じ感覚で扱えるようになりました。ARM64 のスタックは Kubernetes や Azure IoT Operations、Foundry Local にまで広がっています。プレビューは今日から試せます。
