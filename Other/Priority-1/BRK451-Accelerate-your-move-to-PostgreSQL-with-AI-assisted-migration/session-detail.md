## 5. 発表内容の詳細

### 5.1 なぜ Azure HorizonDB か

Aditya は、Azure HorizonDB を選ぶ理由を、データベースのサイズではなく性能と可用性に置いています。

| 観点 | 説明（発表での内容） |
| --- | --- |
| 性能 | 負荷の高いトランザクション系のアプリケーションの応答性を保つように設計されている |
| AI アプリケーション | ベクトル検索により、キーワードの完全一致ではなく、類似した情報を探せる。PostgreSQL のデータと並べて使える |
| 可用性 | 別のゾーンにレプリカを置き、プライマリが失敗した場合にスタンバイが素早く引き継ぐ |
| 読み取り | リードレプリカが読み取りのトラフィックを引き受け、プライマリの負荷を減らす。変更は、ごくわずかなラグでレプリカに反映される |
| 書き込み | 書き込みが多いワークロードのため、低レイテンシのコミットを備え、コミットしたデータはゾーンをまたいで保護される |
| ストレージ | データの増加に合わせて自動的に拡張される |

### 5.2 PostgreSQL から HorizonDB への移行（Azure DMS、パブリックプレビュー）

**PostgreSQL から Azure HorizonDB への移行が、Azure Database Migration Service（Azure DMS）を通じてパブリックプレビューになった**、と発表されました。移行元は、Azure の仮想マシン、他のクラウド、オンプレミスの PostgreSQL です。

homogeneous な移行には 2 つのモードがあります。

| モード | 使う場面と流れ |
| --- | --- |
| オフライン | 計画されたダウンタイムが、データのコピー、検証、アプリケーションの切り替えに足りるだけ許容できる場合 |
| オンライン | コピー中もアプリケーションがユーザーに対応し続ける必要がある場合。最初の全件コピー（initial load）が終わると、CDC（change data capture）が始まり、変更データのレプリケーションが完了したら、アプリケーションを Azure HorizonDB に向けるカットオーバーを行う |

**事前の確認**

- Azure DMS は多くのリージョンで使えるが、対象が広がり続けている段階なので、選ぶリージョンで移行がサポートされているかを事前に確認する
- ネットワークは、パブリックエンドポイントとプライベートエンドポイントの両方に対応する。パブリックでは、DMS が提供する IP アドレスを移行元でホワイトリストに登録する。プライベートネットワークでは、オンプレミスや他のクラウドのプライベートネットワークに、ExpressRoute または IPSec VPN で接続し、HorizonDB へはプライベートエンドポイントで接続する

### 5.3 Oracle から HorizonDB への移行の全体像

アプリケーションが Oracle のパッケージや Oracle 固有のクエリに依存している場合の経路です。Oracle の移行には 3 つの柱があり、それぞれにツールが割り当てられています。

| 柱 | ツール |
| --- | --- |
| スキーマ変換 | VS Code 内の、Microsoft が提供する PostgreSQL 拡張機能 |
| アプリケーション変換 | 同じ拡張機能（および、GitHub Copilot CLI のスキル） |
| データ移行 | Azure DMS |

**スキーマ変換のアーキテクチャ**

1. Azure PostgreSQL 拡張機能の中のスキーマ変換が、Oracle データベースに接続し、DDL を抽出する
2. Microsoft Foundry を使って、その DDL を Azure PostgreSQL 向けの DDL に変換する
3. スキーマ検証用データベースで、変換した DDL をコンパイルし、正しく実行できるかを確認する
4. HTML のレポートと、conversion object explorer（どのオブジェクトが変換され、どれが変換されなかったか、差分がどうか）を生成する
5. レビューしたあと、setup experience を使って HorizonDB にデプロイする

**アプリケーション変換**

アプリケーションが Oracle とどう対話しているか（SQL クエリ、データベースドライバー、Hibernate などの ORM フレームワークを含む）を分析し、Oracle 固有の依存関係を見つけ、Azure HorizonDB で動くように変換を支援するスキルが用意されています。画面に示されたのは GitHub Copilot CLI での実際の実行例で、1 つの convert コマンド（コマンド名は音声認識の都合で表記が確定できません）で、エージェントが移行を計画し、自律的に作業を進めるとのことです。この実行例でも、変換のサマリーは 100% でした。スキルは GitHub Copilot CLI で使え、GitHub で入手できる、と後半で述べています（「I think」と留保付きで、詳細な公開場所は発表では確認できません）。

**Oracle からのデータ移行（Azure DMS）**

- 現時点では、Oracle から Azure HorizonDB への移行は **オフラインモードのみ**、対象は **Oracle 19c 以降** のみ
- Oracle の移行ではテーブル単位のモニタリングがある
- パブリック／プライベートのネットワーク、Oracle の TLS など、そのほかは homogeneous と heterogeneous で共通

### 5.5 ツールキットと次のステップ

Aditya は、移行ツールキットを次のように整理しています。

1. **スキーマ変換**：Oracle のスキーマや複雑な PL/pgSQL コードを Azure HorizonDB に変換する。Azure PostgreSQL 拡張機能をインストールすると、スキーマ変換とアプリケーション変換の両方が同じ拡張機能にある
2. **アプリケーション変換**：Oracle を向いているアプリケーションを、Azure HorizonDB に向け直すためのスキル。GitHub にあると思う、という言い方で、Copilot CLI から使えると説明された
3. **データ移行（Azure DMS）**：スキーマを変換して HorizonDB にデプロイしたあと、Oracle のデータを移行する

つまり、「スキーマを変換し、アプリケーションコードを適合させ、データを移行する」という流れです。スキーマ変換と Microsoft Foundry の連携の仕組み、アプリケーション変換、データ移行（PostgreSQL と Oracle の両方、オンライン・オフラインの両モード）の内部については、スライド上の QR コードからドキュメントを読めると案内されました。

## 6. デモ・手順

このセッションにはデモがあります。Aditya が操作を語りながら進めたものです。画面の細部は音声からは確認できず、以下は語られた範囲です。

### 6.1 デモ 1：PostgreSQL から HorizonDB へのオンライン移行（Azure DMS）

1. Azure Database Migration Service を選び、DMS のリソースを作成する。名前は「DMS ignite-migrations」と聞こえる。タグは省略し、確認して作成する。リージョンは「Japanese region」と聞こえ（聞こえたままの表記です）、リソースグループは「Aditya PM」
2. 移行を開始し、ソースに PostgreSQL、ソースサーバーのタイプに仮想マシン、ターゲットに Azure HorizonDB、モードにオンライン移行を選ぶ
3. ネットワークの画面で、表示された IP アドレスをコピーし、ソース側でホワイトリストに登録して、DMS がパブリックにソースへ接続できるようにする
4. ランタイムを設定する（ソースとターゲットへの接続に使う）
5. ソースの接続情報（サーバー名、パスワードなど）を入れ、接続テストをする。続いて、ターゲットの情報（HorizonDB のパスワード）を入れ、接続テストをする
6. 移行するデータベースを選ぶ。homogeneous の PostgreSQL 移行では、データベースを選ぶとスキーマとデータの両方が移行される。設定はデフォルトのままにして、「migrate」を押す
7. 移行 ID が作成されて provisioning の状態になり、1 つのデータベースが、Azure の仮想マシンから HorizonDB へ、オンラインモードで移行されていることが表示される
8. 移行 ID を開いて監視する。まず検証（HorizonDB と互換性があるかを確認するチェック）が走り、**23 件のチェックが成功** する。更新すると initial load が始まり、スキーマと全データが読み込まれ、**21 個のテーブル** が移行される
9. VS Code で HorizonDB に接続して問い合わせ、スキーマが移行されたこと、テーブルの初期件数を確認する
10. CDC の確認：画面の左がソース、右がターゲット。ターゲットに存在しない行があることを確認し、ソースに **3 件のレコード** を挿入して、ターゲットに複製されたことを確認する
11. ソースとターゲットが同期していることを確認し、カットオーバーを開始する。その後、アプリケーションを Azure HorizonDB に向ければ移行は完了。移行は成功した

### 6.2 デモ 2：Oracle スキーマの変換（VS Code）

1. ワークスペースを作成し、VS Code に Microsoft の PostgreSQL 拡張機能をインストールする
2. VS Code で HorizonDB のサーバー接続情報を作成し、接続テストをして保存する
3. スキーマ変換の migration project を作成する。プロジェクト名は「migration_ignite」と聞こえる
4. Oracle の接続情報を入力し、変換するスキーマを選ぶ（「ignite」。のちに DMS でも使う）
5. 「next discovery」で、抽出が必要なオブジェクト、スキーマ変換に必要な権限、サポートされないオブジェクトを確認する
6. 「next Postgres connections」で、定義済みの HorizonDB の接続情報を使い、スキーマ検証用データベースを選んで検証する。Microsoft Foundry の情報を入力し、AI モデルを使ったスキーマ変換ができるようにする
7. Microsoft Foundry への接続テストが成功したら、migration project を作成する
8. 変換を開始する。まず全オブジェクトを抽出する（**22 個のオブジェクト** が抽出された）。変換はオブジェクトをチャンクに分けて進む
9. 変換が終わったら、conversion summary を確認する。**変換率は 100%** で、テーブル、ビュー、パッケージなどの種類すべてが変換され、抽出されたオブジェクトはすべて変換された
10. conversion object explorer で、各オブジェクトの変換状況と、ソースの Oracle と Azure HorizonDB の DDL の差分を確認する。**ask モード** では、変換で何が起きたか、オブジェクトの依存関係、なぜ HorizonDB でそのパターンになったかを確認できる（「ask and fix モード」と説明されたが、fix モードの詳しい説明は発話にはない）
11. スキーマ、オブジェクトの種類、ステータスなどのフィルターで絞り込める。デモではパッケージを選び、1 つのプロシージャが正しく変換されたことを確認した。左にパッケージのメンバー、右にターゲットの HorizonDB の内容が表示される。右側の DDL は手で修正でき、再生ボタンでスキーマ検証用データベースでコンパイルし直せる
12. conversion report で、Oracle で検出されたオブジェクト数、抽出数、変換数、discovery タブで除外された数、抽出（22 個）、種類ごとの変換率、パッケージのメンバー数などを確認する
13. VS Code で、Ignite スキーマを右クリックして可視化し、HorizonDB のテーブル構造を確認する
14. **setup instructions** に従い、セットアップスクリプトを実行する。デプロイ先の PostgreSQL ホストを尋ねられ、新しいデータベース名（「PGTS ignite」と聞こえる）を入力して、成果物が HorizonDB にデプロイされる。このセットアップガイドは、上位の環境や、ほかの Azure PostgreSQL 環境にデプロイしたい場合の手順として紹介された
15. デプロイのレポートで、失敗したオブジェクトとその理由を確認できる。このデモでは、すべてのオブジェクトが正常にデプロイされた。VS Code で、PGTS Ignite スキーマが setup experience でデプロイされたことを可視化して確認する

### 6.3 アプリケーション変換（スクリーンショット）

アプリケーション変換は、ライブのデモではなく、GitHub Copilot CLI での実際の実行のスクリーンショットで示されました。スキルを使った 1 つのコマンドで、エージェントが移行を計画して実行し、変換サマリーが 100% でした。GitHub Copilot CLI を入れるための QR コードも示されています。この変換結果のスキーマも、すでにデプロイ済みだと述べられています。

### 6.4 デモ 3：Oracle から HorizonDB へのデータ移行（Azure DMS）

1. 「start migration」を押し、Oracle、オンプレミスサーバー、ターゲットに Azure HorizonDB を選んで続行する
2. パブリックアクセスを選ぶ。表示された IP アドレスを Oracle サーバー側でホワイトリストに登録し、DMS が接続してデータを読めるようにする
3. 「setup runtime」でランタイムを立ち上げる（DMS 用。ソースとターゲットに接続する主要コンポーネント）
4. Oracle の接続情報（パスワードを含む）を入れて接続テスト、続いて HorizonDB のターゲット情報を入れて接続テスト。いずれも成功
5. データベースを選ぶ。Oracle の Ignite スキーマを選択し、設定はスキップして「migrate」を押す
6. provisioning と検証が走り、**9 件の検証が成功**。オフラインのため、全件のロードのみが行われる
7. 完了すると、**5 個のテーブル** について、コピーされた行数とバイト数などのテーブルメトリクスが表示される（発話の中で「21 tables、or five, sorry」と言い直している）
8. VS Code で HorizonDB に問い合わせ、5 つのテーブルのデータが入っていること、行数が全部で **76 行** であることを確認する

## 7. 注意点・発表者の気付き

- 移行を始める前に、選ぶリージョンで Azure DMS の移行がサポートされているかを確認する。
- Oracle から HorizonDB への DMS の移行は、現時点ではオフラインのみで、Oracle 19c 以降だけが対象。
- ネットワークは、パブリック（IP のホワイトリスト）とプライベート（ExpressRoute または IPSec VPN、プライベートエンドポイント）の両方が選べる。
- 変換結果は、conversion report と object explorer で確認し、デプロイ後は失敗したオブジェクトとその理由をレポートで確認する。右側の DDL は手動で修正できる。
