## 4. 発表者が伝えたいメッセージ

最初のメッセージは、**AI の性能はシステム全体の結果**だということです。計算、メモリ、ストレージ、ネットワーク、ソフトウェアがどれだけうまく連携するかで決まるため、Azure はスタックのすべての層で改善を進めていると述べています。

もう一つは、VM は「最大のもの」や「最高スペックのもの」を選ぶのではなく、**ボトルネックを見極めて選び、ベンチマークして適正サイズにする**ということです。1 つの AI パイプラインでも段階ごとにボトルネックが異なり、スケールすれば変わるため、最初にボトルネックの当たりを付け、テストで検証し、スループット、レイテンシー、使用率、有用な作業あたりのコストで評価する、という手順が示されました。OpenAI の事例は、モデル以外の多くの処理が汎用コンピュート上で動いていることを裏づけるものとして紹介されています。

## 5. 発表内容の詳細

### 5.1 Azure が改善している 4 つの層

AI の性能を高めるため、発表者は次の 4 つの領域で取り組んでいると説明しています。

1. **シリコン**: Azure Cobalt と、パートナーの最新の CPU・GPU で選択肢を広げる
2. **システムアーキテクチャ**: より大容量メモリの新しいオファリング、インフラ処理をオフロードして IO 帯域を高める Azure Boost
3. **ファブリックとデータ**: ネットワークとストレージを改善し、データへのアクセスと移動を速くする（ワークロードの分散化が進む中で重要）
4. **運用**: 配置、スケーリング、オブザーバビリティの改善

### 5.2 どこから始めるか: 汎用 VM が活きる 4 つの領域

インフラ選択では、ワークロードの想定ボトルネックから始め、テストで検証することを勧めています。トレーニングと大規模モデルの推論は主にアクセラレーターに頼りますが、汎用 VM は次の 4 つの領域で重要だと説明しています。

* **小規模モデルとバッチ推論**: 特にモデルが小さい場合や需要が変動する場合に、CPU のほうがコスト効率が良いことがある。スループットが増えるとアクセラレーターが魅力的になる
* **RAG（Retrieval Augmented Generation）**: 回答生成の前に幅広いソースから関連情報を集めて応答を改善する手法。モデルの外側で、データの取り込み、取得、フィルタリング、再ランキングなど多くの処理が発生し、汎用 VM に向く
* **エージェント型 AI**: エージェントがツールを呼び、データベースにアクセスし、コードを実行するため、インフラにバースト的な負荷がかかる
* **AI サービス**: API やアプリケーションロジック

これらすべてを通じて、Confidential Computing（使用中の機密データをハードウェアで保護する仕組み）が検討事項になる、という整理です。

### 5.3 新しい VM シリーズ

今週一般提供（GA）が発表されたのが **Cobalt 200 VM** です。ARM ベースのポートフォリオを拡張するもので、前世代より最大 50% 高い CPU 性能、より大きなキャッシュ、組み込みのオフロード機能を備えます。Azure Boost がストレージとネットワークをさらに高速化します。

用途別の新シリーズは次のとおりです（シリーズ名は音声認識による書き起こしです）。

| シリーズ | 発表で語られた用途・仕様 |
| ---- | ---- |
| DPLSv7（聞こえた表記: DPLSV7） | スケールアウトのマイクロサービス、ツール実行 |
| DPSv7 | エージェントのオーケストレーション、RAG サービス |
| EPSv7 | 埋め込み、リトリーバル、キャッシュ。最大 1 TiB のメモリ |
| MPSv4（新ファミリー） | 大規模な RAG やベクターデータベースなど、より多くのメモリが必要なワークロード向け。最大 1.3 TiB のメモリ |
| LPSv5（新しいストレージ最適化シリーズ） | データ前処理とインデックス作成。最大 23 TB のローカル NVMe ストレージ |

**Cobalt 200 とエージェントの実行層**: Cobalt 200 は、エージェントが分離されたサンドボックスを作り、データを取得し、コードを実行し、ツールを呼ぶスケールアウト層に向く、と説明されています。Microsoft の agent developer compute benchmarks で、Cobalt 100 と比べた改善は次のとおりです。

| 指標 | 改善 |
| ---- | ---- |
| サンドボックスの作成 | 最大 22% 高速（起動レイテンシーが下がる） |
| サンドボックス密度 | 25% 超の向上 |
| ツール実行 | 55% 超の高速化 |

コアあたりの有用な作業が増えるため、エージェントの同時実行をより多く支えられ、スケールしたときのエージェントあたりのコストを下げる可能性がある、という説明です。

**リモートストレージ向け**: **EBSv6 と EBDSv6**（音声認識では EBSV6、EBDSV6）が今週 GA となり、最大 96 vCPU のサイズがあります。ベクターデータベースと RAG、エージェント型 AI を支えるデータベース、フィーチャーストアやデータウェアハウスなど、リモートストレージへの高速アクセスに依存するワークロードに向き、リモートストレージ IO が主なボトルネックの場合に有力な選択肢と説明しています。

**ローカルストレージ向け**:

| シリーズ | 仕様 | 用途 |
| ---- | ---- | ---- |
| LASv5 | 最大 30.7 TB のローカルストレージ、960 万の読み取り IOPS | インデックス作成、リトリーバルのキャッシュ、データ処理 |
| LAOSv5 | 最大 138 TB、2,070 万の読み取り IOPS | より大きなデータのステージングとキャッシュ |

計算とローカルストレージのバランスなら LAS、ローカルストレージの容量と性能を最大にしたいなら LAOS を選ぶ、という使い分けです。この 2 つのシリーズは今日から GA とのことです（音声認識では「LASB5」「LAOSB5」とも書かれており、表記は確定できません）。

**高い同時並行向け**: 第 6 世代 EPYC プロセッサーを使った **DHASv8 と EHASv8**（音声認識の表記）は、最大 480 vCPU までスケールし、より多くのエージェント、ツールワーカー、パイプラインプロセスを同時に動かせます。DHAS は vCPU あたり 4 GB のメモリで、EHAS はその倍です。最大メモリは 3.8 TiB。最大サイズでは、前世代の最大 2 倍のリモートストレージ IOPS とネットワーク帯域を提供します。エージェントのオーケストレーション、サンドボックスのフリート、RAG、データ前処理に向き、**プレビュー提供中**です。発表資料の QR コードから、ブログ記事とサインアップのリンクにアクセスできると案内されています。

### 5.4 Azure Boost とカスタムシリコン（Max 氏）

Max 氏は、Azure のサーバーブレードを見せながら（実物かスライドかは音声からは分かりません）、Microsoft が自前で作る多くのカスタムシリコンが、他社に負けない（本人の言い回しでは「業界で主要な水準の」）性能とセキュリティの源泉だと説明しています。基調講演で触れられたものとして、次が挙げられました。

* **統合 HSM**: 鍵をハードウェア内に保管し、Microsoft 自身を含めて誰も鍵にアクセスできないようにする。ハードウェアのセキュリティを保証する要素
* **Caliptra**（聞こえた表記）: 量子攻撃から守るためのポスト量子暗号のモデルと説明。発表者は、現在の多くの鍵は量子コンピューターで 6 時間以内に解読できるといわれ、各サーバーブレードに導入することが重要だと述べています

VM の側で見える要素としては、ローカル NVMe ドライブである **Azure Boost SSD** と **Azure Boost** があります。Max 氏は顧客に、「他社（Amazon や Google など）ができないことができる理由は、これらのコンポーネントに数十億ドルを投資しているからだ」と話すと述べ、これらのコンポーネントは販売していないと付け加えています。

Azure Boost の位置づけは、Azure のハードウェアエンジニアリングチームが設計したもので、プラットフォーム側の処理と性能向上を、顧客が見る・動かす仮想化プロセスから分離することです。数値としては次が語られました。

| 項目 | 内容 |
| ---- | ---- |
| ネットワークスループット | V7 VM で 400 Gbps |
| 接続数 | 最大 400K connections/s |
| セキュリティ | ハードウェアで分離、FIPS と NIST の認証あり。信頼されたデバイスであることを確認するプロトコルにも言及があるが、名称は聞き取り不明瞭 |
| 搭載状況 | 本番に出荷する SKU の 100%（AI SKU、Vera Rubin、Maia、HPC SKU も含む）が Azure Boost を搭載。フリートの約 50% がすでに Azure Boost |
| 料金 | 多くの顧客は Azure Boost の体験を無料で得られる。課金は VM SKU のサイズに対してのみ |

### 5.5 Confidential Computing

Max 氏によると、AI によって多くの顧客がデータをクラウドへ移しており、「誰がデータにアクセスするのか」「モデルは何ができるのか」「盗まれないか」「オペレーターのアクセスはあるのか」という懸念が毎回話題になります。転送中のデータの保護（VNet 暗号化、ストレージ暗号化）は誰もが知っていることですが、**使用中のデータをどう守るか**が焦点で、それが Confidential Computing です。実行しているものが本来実行すべきものであることの証明（attestation）もその一部です。以前は決済事業者のような例外的な要件でしたが、今ではすべての顧客との会話で上位の話題になっていると述べています。

今回発表された内容として、次が挙げられました。

* AMD の次世代（発表では「Turing Gen 7」と聞こえます。音声認識の都合で表記が確定できません）のプレビュー。前世代は Genoa で、さらに良い体験と性能になるとのこと
* **Intel TDX**: 以前の Intel（SGX）から大きく進歩し、**ライブマイグレーションに対応**。継続的なライブマイグレーションをサポートするのは TDX と Azure が初めてだと述べています。「Confidential VM が良い VM であるためには、まず良い VM でなければならない」という発言を引用し、運用をサポートできる VM を目指していると説明しています
* **Azure Boost Confidential Device**（ABCD）: Confidential VM と Azure Boost を統合し、本番で実現でき、顧客が遅延を感じない技術にしたもの（デモは 6.1 参照）
* 今週リリース、または発表した他の項目: Turing 向けの Confidential VM、Confidential container（発表では「Cata CC」と聞こえます）への対応、NVIDIA と共同で行った Vera Rubin 上の Confidential AI の最初のデモ（基調講演でも話題に出たとのこと）。VM だけでは足りず（音声認識の表記は「IS」）、データサービスやバックアップなどの追加サービスも必要だという顧客の声があり、Confidential の拡張として提供される予定とのことです

### 5.6 エージェント時代のネットワークと RAG のための機能

Max 氏は、従来のワークロードは過剰にプロビジョニングされ、ネットワークもストレージも使い切らないことが多かったが、**エージェント型では輻輳が現実の問題になる**と述べています。そのため、SKU ごとにアプリケーションの種類に合わせた最適化を進めており、Cobalt 200 の例に続けて、ネットワークスループットの課題に対する **Network Optimized VM**（プレビュー中。もうすぐ GA の予定）が紹介されました。AI エージェントと顧客のワークロードは IO 集約的になり、数百万のフローを管理し、接続が頻繁に開閉する状況（connection churn）を扱う必要がある、という背景です。Azure Boost では、SDN の接続セットアップをホスト CPU ではなく専用ハードウェア（発表では rule offload engine。音声認識では「ROV」とも）で処理できます。実際の効果はデモ（6.2）で示されました。

RAG については、エンタープライズデータで AI エージェントを強化するワークロードとして、VM シリーズの使い分けが次のように示されました。

* まず D シリーズ（DSv7）から始める。パイプライン向けに最適化されているが、メモリが多くなく、ローカルディスクもない
* メモリを多く使う場合は E シリーズ
* 計算を多く使う変換処理は F シリーズ
* 実際にはノード単体ではなく、複数の VM が協調することが多い

そこで発表されたのが **VM 間の guest RDMA** です。ノード上の TCP スタックをバイパスして VM 間の接続を作るもので、レイテンシーと CPU 使用率が大きく改善します。Max 氏は、業界のプロバイダーとして初めて公開発表したのではないか（"I think" と留保付き）と述べています。複数のパートナーが協力しており、OpenAI も取り組んでいます。Azure での VM 間通信の将来像として力を入れており、**現在はパブリックプレビュー**（URL または QR コードで試せる）です。GA までは、フィードバックを集めるために数か月かかる見込みと説明されています（デモは 6.3）。

### 5.7 OpenAI の事例: ChatGPT の音声リクエストを支える汎用コンピュート（Vadim 氏）

Vadim 氏は、ChatGPT に話しかけて答えが返ってくるとき、モデルと直接話しているように感じるが、実際にはリクエストがモデルに届く前に多くの要素が動いており、**それらの多くは Azure の汎用コンピュート上で動いている**と述べています。説明のために、氏がこの発表の準備で ChatGPT に頼んだ実例を使っています。内容は、Azure 汎用コンピュートの例と、OpenAI での使い方を紹介するまとめのスライドを作ること、過去の会話を参照すること、公開されている VM のスペックを調べて 1 枚のスライドにまとめること、そしてタイピングが面倒なので音声で依頼したことです。

処理の流れは次のとおりです。

| 順序 | コンポーネント | 役割と、使っている VM |
| ---- | ---- | ---- |
| 1 | **Voice relay**（リージョンごと） | クライアントが送る小さな音声パケットを受け取り、最初のパケットでは transceiver へのルートを確立し、以降のパケットでは同じセッションの transceiver を見つけて転送する。パケット処理量が支配的で、**F シリーズ**を選んだ。Stephanie 氏が述べた「ボトルネックから選ぶ」手順に沿い、コンピュートがボトルネックなので F にした、という説明 |
| 2 | **Transceiver** | 双方向の WebRTC セッションを保持し、音声の大きなかたまりの組み立てやパケットの並べ替えを行う。**D または E**（汎用） |
| 3 | **Voice model** | 推論を実行して音声を返す。ただしツールは使えない |
| 4 | **Conversation service** | ツールを使う必要があるとき、voice model が処理を渡す先。ターンの流れ全体を調整する。**D または E** |

Conversation service とモデルの間では複数のターンが行われ、各ターンでモデルが異なるツールを使ってコンテキストを更新します。モデルは並列にツールを呼ぶこともありますが、ここでは単純化して順番に説明されています。この依頼では、(1) 会話履歴の検索、(2) VM スペックを取得する Web 検索、(3) それらをまとめて PowerPoint のスライドを作る、という順で処理されました。

**会話履歴の検索（Rockset）**: 社内のリアルタイム分析データベースである Rockset を使います。ChatGPT で行った会話（プライベートな会話を除く）は、ほぼリアルタイムで取り込まれ、インデックスされます。構成は 3 層で、次のとおりです。

* メインのデータとインデックスは、**オブジェクトストレージ**に置く
* 共有インデックスキャッシュ（ホットなインデックスシャード）は **L シリーズ**で動かす。ストレージの量と速度が重要なため、L インスタンスが最適。よく使うフィールドをオブジェクトストレージから取ってくることもある
* クエリワーカーはクエリを実行して結果を組み立て、インデックスキャッシュからデータを取る。キャッシュミスやキャッシュにないフィールドが必要なときは、共有インデックスキャッシュのサービスがストレージから取ってくる。ワーカーは「主力の D または E インスタンス」で動く

この 3 層構成の利点は、**各層を個別にスケールできる**ことです。クエリ量が増えればワーカーを、データセットとキャッシュが大きくなれば L インスタンスのインデックスキャッシュとストレージを増やします。

**Web 検索**: Web のクロールとインデックス作成は別のサービスです。検索インデックスは非常に大きなデータ構造で、より多くのメモリと高いメモリ帯域が必要なため、専用の高性能コンピュートのワーカーでインデックスを保持しています。検索時の結果アグリゲーター（result aggregator）は、その専用ワーカーから出して汎用コンピュートへ移すことができました。貴重な専用コンピュートを、インデックス、クロール、検索、ランキングに回せることが利点で、ワークロードをバランスさせて汎用コンピュートの利用を増やしているという説明です。

**スライド作成（コード実行）**: モデルは Python を書き、それを OpenAI の **CAS**（発表では「container compute as a service platform」と説明。名称の綴りは音声認識の都合で確定できません）で実行します。コンテナと呼んでいますが、実際はより分離性の高いマイクロ VM に近いと述べています。メモリが必要なため主に **E シリーズ**で動かし、需要と供給に応じて D でも動かします。モデルが Python とコンテキスト（例、VM スペック）を投入すると、コマンドラインのユーティリティや Jupyter カーネルを実行でき、スライド作成用のオフラインツールでスライドを書き出し、ファイルへのリンクを共有して、最終回答がユーザーに届きます。

最後に、その結果のスライド（使われたインスタンスタイプを要約したもの）が示され、「インスタンスタイプのスライドを頼んだら、そのインスタンスタイプを使ってスライドが作られた」と、メタな話として紹介されました。結論として、ChatGPT でモデルが主役であることは確かだが、モデルをより賢く・便利にするための作業は、モデルの外側で行われ、その多くが汎用コンピュート上で行われている、と述べています。

### 5.8 VM を選ぶためのガイド（Stephanie 氏）

最後に、CPU ベースの AI ワークロードで Azure VM を選ぶための簡潔なガイドが示されました。出発点は、何が性能を制限しているかです。

| 状況 | 推奨 |
| ---- | ---- |
| 比較的バランスの取れたワークロード | **D シリーズ**から始める |
| 小規模モデルの推論や前処理など、計算集約的／レイテンシーに敏感 | **F シリーズ** |
| キャッシュやリトリーバルなど、より多くのメモリが必要 | **E シリーズ** |
| 非常に大きなメモリフットプリントが必要 | **M シリーズ** |
| ストレージがボトルネック | 高速なローカルストレージなら **L シリーズ**、高性能なリモートストレージなら **EBSv6** |
| ネットワークがボトルネック | デモで見せた **Network Optimized VM**。ゲートウェイ、分散サービス、ネットワークに敏感なワークロードに向く |
| Confidential Computing が必要 | 汎用とメモリ集約型の両方にオプションがある |

加えて、1 つの AI パイプラインでも段階によってボトルネックが違い、スケールに伴って変わることを覚えておくこと、最大の VM や最高スペックの VM が常に必要なわけではないこと、VM を選んだらスループット、レイテンシー、使用率、有用な作業あたりのコストをベンチマークして適正サイズにすること、が示されました。

## 6. デモ・手順

Max 氏が紹介した 3 つのデモがあります。いずれも Max 氏の説明に続いて、ナレーション付きで進みました（3 つ目の前に Max 氏は「チームに作ってもらった」と述べています。録画かライブかを明示した発話はありません）。画面の細部は音声からは確認できません。以下はナレーションで語られた内容です。

### 6.1 Azure Boost Confidential Device（ABCD）

ナレーションの冒頭では、これまで顧客は機密性とネットワーク性能のどちらかを選ばなければならなかったが、Azure Boost の新しい技術によりそうではなくなった、と述べられています。「業界初のデモ」と位置づけられています。

1. ホストを attest（証明）し、IDE チャネルを確立し、続いてゲストを attest する。これは、顧客が暗号学的な証明（attestation）を得るために重要だと説明された
2. ネットワークテストを開始する。Confidential VM と通常の VM とでネットワーク性能が同等で、最大 400 Gbps のスループットを達成した
3. レイテンシーを確認する。3 つのシステムを並べた構成で、1 つ目が ABCD あり、真ん中が ABCD なし、3 つ目が標準 VM という説明。レイテンシーも同等だった

Max 氏は、多くのハードウェアプロバイダーとソフトウェアエンジニアリングの成果で、「ほとんど魔法」だと述べています。これは次世代の Confidential VM で提供される予定で、**今日はまだ使えず、近日提供**と明言しています。

### 6.2 rule offload engine による接続数の比較

1. 複数のホストにまたがる 12 台のクライアント VM を用意し、1 台のサーバーに対して接続を開く構成にした
2. rule offload engine を無効にした場合: SDN の接続セットアップがホスト CPU で実行され、そのサーバーの新規接続は毎秒約 57,000 というベースラインだった
3. 同じワークロードを、rule offload engine を有効にしたサーバーに向ける。クライアントは変更しない
4. 12 台すべてがトラフィックを生成すると、1 台のサーバーで毎秒 **100 万超の新規接続**を処理した
5. クライアントマシンを増やしたわけではなく、接続セットアップをハードウェアで効率よく処理した結果である。ナレーションでは、57,000 から 100 万超への向上を「このテストで約 18 倍」としている

Max 氏は、通常この規模の接続数には、専門ベンダーの高価なアプライアンスを買う必要があるが、これを 1 枚の Azure Boost カードと 1 台のサーバーで実現した、と述べています。ただし、**100 万の水準はまだ提供しておらず、リリース予定は 400K で、100 万はそれより後**です。デモの対象の Network Optimized VM はプレビュー中で、もうすぐ GA の見込みと説明されています。

### 6.3 Guest RDMA による time to first token の改善

1. 3 台の VM を使う構成。VM1 が共有 KV キャッシュプールを持ち、VM2 と VM3 は GPU ワーカー（GPU worker A、B）で、どちらも VM1 の共有 KV キャッシュプールをマウントし、vLLM のモデルサーバーを動かしている
2. 各トライアルで、新しい 28,000 トークンのプロンプトを VM2 に送る。VM2 は GPU で prefill を最後まで実行し、KV キャッシュを VM1 の共有プールに保存する
3. 同じプロンプトを VM3 に送る。VM3 はこのプロンプトを見たことがなく、再計算ではなく、プールからキャッシュデータを取得して、time to first token を測定する。これを 10 回行う
4. まずベースラインとして NFS over TCP を使う。10 回の中央値は time to first token 1,075 ミリ秒、キャッシュデータの移動に約 6 CPU コア、約 10.1 GB/s
5. 同じプールを、今度は NFS over RDMA で再マウントする
6. 結果は次のとおり

| 項目 | TCP | RDMA |
| ---- | ---- | ---- |
| time to first token（中央値） | 1,075 ミリ秒 | 757 ミリ秒（TCP より約 42% 高速） |
| CPU 使用 | 約 6 コア | 約 0.5 コア（約 91% 少ない） |
| スループット | 約 10.1 GB/s | 最大 15.1 GB/s（TCP の 1.5 倍） |

> 補足：デモ後に Max 氏は CPU 使用について「95% の改善」と述べていますが、ナレーションで示された数字は約 91% 減です。

## 7. 注意点・発表者の気付き

* **Azure Boost Confidential Device は今日は提供されていません。** 次世代の Confidential VM で近日提供の予定です
* **100 万 connections/s の水準も提供前です。** 提供予定は 400K で、デモは能力を示すものです
* Network Optimized VM と guest RDMA はプレビューで、guest RDMA は GA まで数か月かけてフィードバックを集める予定です
* DHASv8/EHASv8 はプレビュー提供中です
* VM はボトルネックから選び、ベンチマークし、適正サイズにする。ボトルネックは段階とスケールで変わる
* 発表者は、エージェント型では過去のような「過剰プロビジョニングで使い切らない」運用が成り立たず、輻輳が課題になると述べています
* 数値の多くは Microsoft の内部ベンチマークまたはデモ環境での結果で、各デモの条件（クライアント 12 台、28,000 トークンのプロンプトで 10 回など）は 6 章のとおりです。ほかの環境で同じ値になるかについては、発表では触れられていません

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

* **コスト効率**: 小規模モデルやバッチ推論では CPU のほうが効率が良いことがある。Cobalt 200 はコアあたりの有用な作業が増え、エージェントあたりのコストを下げる可能性がある（Cobalt 100 比で、サンドボックス作成が最大 22% 高速、密度が 25% 超向上、ツール実行が 55% 超高速）
* **ネットワーク**: rule offload engine で、1 台のサーバーが毎秒 100 万超の新規接続を処理できる能力（デモ。製品としての提供は 400K が先）
* **VM 間通信**: guest RDMA で、デモでは time to first token が約 42% 短縮し、CPU 使用が約 91% 減り、スループットが 1.5 倍になった
* **機密性と性能の両立**: ABCD のデモで、Confidential VM と標準 VM の間でネットワーク性能とレイテンシーの同等性が示された（提供は今後）
* **Azure Boost**: 多くの顧客は追加料金なしで Azure Boost の体験を得られる（課金は VM SKU のサイズのみ）
* **選択肢の拡大**: メモリ、ストレージ、リモートストレージ、同時並行など、用途別の VM シリーズが増えた
* **実例**: OpenAI が ChatGPT の音声リクエスト処理で、voice relay（F）、transceiver・conversation service・クエリワーカー（D または E）、インデックスキャッシュ（L）、コード実行（E または D）と、用途に応じて汎用コンピュートを使い分けている

## 9. まとめ

AI の性能は、計算、メモリ、ストレージ、ネットワーク、ソフトウェアの連携で決まります。トレーニングと大規模モデルの推論はアクセラレーターが中心ですが、小規模モデルやバッチ推論、RAG、エージェント型 AI、AI サービスでは、CPU ベースの汎用 VM が重要な役割を持ちます。Azure は、Cobalt 200、新しい D/E/M/L 系の VM シリーズ、Azure Boost、Confidential Computing、guest RDMA などで、その選択肢を広げています。

OpenAI の事例では、ChatGPT の 1 回の音声リクエストの裏で、F、D、E、L の各シリーズが役割ごとに使い分けられていました。VM を選ぶときは、ボトルネックを見極めて適切なシリーズを選び、スループット、レイテンシー、使用率、有用な作業あたりのコストをベンチマークして適正サイズにする、という手順が示されています。
