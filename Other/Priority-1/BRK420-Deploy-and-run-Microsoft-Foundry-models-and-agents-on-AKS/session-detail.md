# BRK420 Deploy and run Microsoft Foundry models and agents on AKS

## 1. はじめに

このセッションは、Microsoft Foundry で選んだモデルやエージェントを、自分で管理する Azure Kubernetes Service（AKS）クラスターに載せて動かす、新しい連携の紹介です。Foundry の画面から、AKS 上のオープンウェイトモデルのデプロイ、チューニング、ホステッドエージェントの実行までを一続きで扱えるようになります。この連携の中核が **AKS AI Manager for Foundry** です。

内容の大半は、架空の製薬会社を題材にしたデモです。モデルのデプロイ、追加学習、工場内の機器でのモデル実行、エージェントのサンドボックス実行とネットワーク制御、最後にオンプレミスへの展開までが、1 つのシナリオとして語られます。最後に約 10 分の質疑応答があります。

AKS や Foundry をすでに使っている開発者・プラットフォームエンジニアが、「既存の AKS 基盤を活かして AI ワークロードを動かす」道筋を知るための発表です。

## 5. 発表内容の詳細

### 5.1 エージェントがインフラのルールを書き換えている（Brendan）

Brendan は、次の点を挙げています。

- エージェント自体が興味深いワークロードで、ワークロードの定義を生成します。成功させるには、コンピュート、ストレージ、ネットワークへの高速なアクセスと、エージェントに必要なコンテキストの一式が必要です。
- エージェントは、処理対象のデータやプロセスの近くに置きたい、さまざまな場所に置きたい、というニーズがあります。
- コスト管理と制御の観点から、オープンソースとオープンウェイトの解決策を求める流れがあります。
- 以前 CPU に使われていた支出の一部が、推論のための GPU に向かっています。
- Kubernetes は、AI 以前から現代的なアプリケーションの基盤でしたが、今は AI アプリケーションの**絶対的な基盤**になっています。AI アプリケーション、エージェント、推論に関するイノベーションの大多数が、Kubernetes の上で起きていると述べています。
- コンテナ初期と同様、新しいプロジェクトやモデルの入れ替わりが激しく、追いかけるのが疲れるほどです。オープンウェイトモデルへの動きもあります。
- 大規模なモデルとエージェントの分散的な性質のため、実行モデルは**分散システム**になっています。大きなモデルを複数の GPU にまたがって動かす分散推論や、並行してジョブを実行するエージェントの群れが例です。

#### Kubernetes が選ばれる理由

Brendan によれば、モダナイゼーションで Kubernetes が選ばれた理由と似ています。

| 理由 | 説明 |
| ---- | ---- |
| ポータビリティ | クラウド間、クラウドとオンプレミスの間 |
| GPU の確保 | GPU は見つけにくいので、空きのある場所にワークロードを持っていける価値がある |
| 素早い反復 | アプリケーションや動かし方を素早く変えられることが成功の鍵 |
| スケーラビリティ・耐障害性 | GPU を中心に理解するインフラ |

本番の AI アプリケーションで考えるべきことは多く、スライドでは「長いリスト」として示されました（発表では個々の項目は読み上げられていません）。

### 5.2 AKS AI Manager for Foundry（Jorge）

Brendan が流した紹介動画は「AKS AI manager が、Foundry のマネージドサービスから Azure Kubernetes Service まで、点をつないでいる」ものだと説明されました。動画自体の音声内容はトランスクリプトには含まれていません。

Jorge は、Foundry を使ってきたユーザーの中に、すでに AKS 上でアプリケーションを展開しているユーザーが重なっており、「AI やエージェントのアプリケーションも Foundry と AKS で一緒に開発できないか」と尋ねられた、と説明しています。それに応えるのが、次の機能です。

- **Foundry から AKS にモデルをデプロイする API（AKS AI）**。10 個の Helm chart を自分でインストールして挙動を理解する必要はありません。
- インストールされるのは、**完全にオープンソースのスタック**です。Foundry から実行して利用できます。
- Foundry カタログにあるオープンウェイトモデルをすべて実行できます。
- 自分のキーを持ち込んだり、自分の Hugging Face アカウントから実行したりすることもできます（発言は「hugging space」。音声認識上の表記です）。
- カタログについて「通常は推奨している」という趣旨の発言がありますが、内容は聞き取れません（聞き取り不明瞭）。
- サンドボックス、ポリシー、セキュリティの機能を使って**エージェントもデプロイ**できます。
- Foundry から AKS まで、**ファインチューニング、学習、セキュリティ、ポリシー**を継続して行えます。
- 行うことはすべて、可観測かつ監査可能で、すでに持っているインフラを活用します。

### 5.3 デモのシナリオ：Caldova Pharmaceuticals

Jorge が説明したシナリオです。

- 架空の製薬メーカーで、世界に **4 つの工場、120 本のライン**があり、1 日に複数シフトで動いています。
- 生産ラインでは、「微小停止（micro stop）」が起きて、ラインが止まったりアラートが出たりし、技術者が修理に入ります。これが 1 日に数百時間、月末には数百万ドルの損失になります。
- AI を使って、停止の回数を減らす、あるいは停止から再開までの時間を短縮したい。そのためエージェントとモデルで、より速いトラブルシューティングを目指します。

重要な前提は次の 3 点です。

1. すでに規制対象の企業で、AKS 上でアプリケーションを動かしており、そのインフラは審査済み・コンプライアンス適合済み・規制当局の承認済みである。既存のインフラを活用できることが、今回の発表の重要な点。
2. 規制業界なので、データとインフラを完全に自分で制御したい。
3. 複数の工場・地域にまたがるヘテロジニアスな環境で、複数のクラスターがあり、クラウドとオンプレミスの両方がある。

### 5.4 デモ後に整理された要点（振り返り）

Jorge は、デモの終わりに次のように整理しています（6 章のデモの流れと合わせて参照してください）。

1. **Foundry と AKS でモデルを動かす**：今と同じ Foundry の API と UI を使える。
2. **工場にある Flex nodes にデプロイ**：どこにあるマシンでも、GPU マシンを含めて AKS クラスターに参加させられる。
3. **AKS 上でホステッドエージェントを動かす**：AKS が提供するセキュリティと分離（micro VM、Kata、agent sandbox、ネットワーク制御の Agent Grid）を利用する。
4. これらは、エージェント時代に向けて進化している **Azure のコア**の上に成り立つ。AI 向けに最適化したプリミティブとして、サンドボックス、context cache などが挙げられ、AKS と ACI の両方で、同じ AKS コントロールプレーンからサンドボックスを使える。
5. エージェント的な運用（agentic operations）でクラスターを管理することもできる。複数クラスターに **Fleet Manager** をつなぎ、**SRE agent** を使えば、day 2 の運用負荷をほぼなくせる、という説明。

### 5.5 Azure 全体の位置づけ（Brendan）

Brendan は、これらは AKS だけでなく Azure 自体の機能であり、**Microsoft Foundry から AKS までの「つながった道のり」**のためのものだと述べています。

さらに、Azure を「フロンティア変革」の基盤と位置づけ、Copilot（Word 文書での標準的な機能、コード統合を含む）から、Foundry・Azure・データ・Fabric を中心にした Microsoft IQ プラットフォームへ、さらにセキュリティ、そして **Agent 365** へとつながる、と説明しています。Agent 365 によって、エージェントが何をしているかを把握し、適切なガードレールと制御を設けて、Azure にデプロイするエージェントや Copilot からアクセスするエージェントが期待どおり動くようにします。

**Q1. エージェントを複雑に組み合わせて展開すると、エージェント間のトークンのやり取りなどでコストとデータの管理が課題になる。コストを抑えつつセキュリティを保つには？**

回答者（1 人目）：

- すでに支払っているインフラの中にすべてを置けるので、何にいくら払っているかが明確になる。
- スケールの仕方を定義でき、reserved instances や savings plans も使える。Flex のように、すでに所有しているインフラも使える。
- ガバナンスでは、Agent 365 などの機能が連携し、コストを観察できる。「このモデルがうまく動いていない」と分かれば、Foundry でモデルを変更できる。例として、Llama ではなく、今日発表された新しい **MAI モデル**をコスト削減のために使う、という選択を挙げています。

もう 1 人の登壇者の補足：

- AKS のエコシステム（クラウド上または AKS on-prem）の利点は、広いツール群を使えること。**OpenTelemetry** でトークン使用量を監視し、どこに向かっているかを把握できる。
- Agent Grid のガバナンスで、ネットワークを文字どおり遮断することもできる。完全ではないかもしれないが、ネットワーク egress を完全に止めるところから、可観測性ツールで監視・アラートするところまで、幅広い選択肢がある。

質問者は、GPU を使った推論が高コストの中心になるのではないかと続けました。これに対する回答は次のとおりです。

- 今日発表したのは「自分の GPU を持ち、savings plan をかける」やり方だが、反対のケースもある。例えばモデルを常時提供せず、短期間だけ使うなら、**Foundry managed compute** のようなサーバーレスに近い方式のほうが有利な場合がある。
- 最初はトークン課金で始め、しきい値を超えたら、GPU を所有して月額で払う方が合理的になる、という使い分けができる。同じモデルを、これまでどおり行き来してデプロイできる。

もう 1 人の登壇者の補足：画像をエッジでテキストに変換するなら、ネットワークで送るのはテキストなので小さく、複雑な LLM でテキストを処理するほうが画像を処理するより安い。つまり、プライバシーだけでなく**コストの面でも、効率的なアーキテクチャ**を作れる。

質問者が「画像をテキストにすると文脈が失われるのでは」と指摘しました。もう 1 人の登壇者は、「文脈が失われる」というより「抽象化・意味化（semanticify）」だと答えました。続くやり取りで「ピクセルが重要かどうかによる」という指摘が出て、登壇者はそれを課題と認め、システム設計の工夫の一部だと述べました。そのうえで、エッジで一定のデータキュレーションをしてから送ることには、コスト、ネットワーク、アプリケーション性能の面で価値がある、と説明しています。

**Q2. サンドボックス化して、何を許可し何を許可しないかをどう決めるのか。特にエッジでは具体的に絞りたい。**

- 「通常は規制当局が決める」という冗談めかした回答のあと、最小権限（least privilege）から始めることを勧めています。何もできないサンドボックスから始め、動くか確認し、おそらく動かないので、必要なものだけを足していきます。
- エージェント的なシステムでは、**明示的に許可する（explicit）** ことを勧めます。デモは「すべて許可して例外を拒否」ではなく、「これらだけを許可」というものでした。
- もう一方の登壇者は、エージェントがサンドボックスから抜け出して報じられたセキュリティ事例は、いずれも「すべてへのアクセスを与え、ブロックしようとしたものを 1 つ見落とした」という形だと指摘し、すべてをブロックして、少しずつ許可する方式を強く勧めています。
- 質問者の懸念は、API へのアクセスを与えると、それをプロキシにして他のすべてに到達されることです。回答者は、これは明らかな課題で、全員が考え続けている点だと答えています。

## 6. デモ・手順

デモは、セッション冒頭の紹介動画と、Jorge による本編デモがあります。本編デモは、画面を示しながら「ここにあるのは」「ご覧のとおり」と語る形式で進みました（ライブか録画かは発話からは分かりません）。画面の細部は音声からは確認できないので、語られた範囲で、順に記載します。

### 6.1 生産ラインの課題を確認する

1. Caldova の生産ラインアプリケーションの画面。複数のラインが表示され、**line 7** で問題が起きている。
2. 製造オペレーション担当の VP の立場で、トラブルシューティングする。信号（signals）の確認、準備状況のチェック（readiness checks）、対象機器のマニュアルへの直接リンク、RCA（根本原因分析）のための各種プロセスなどがあるシステム。
3. 完全に解決するまでに **40 時間以上**かかることがあり、最良の場合でも機器 1 台の再起動に**少なくとも 20 分**かかる。

### 6.2 Foundry リソースを作成して AKS を接続する

1. AI エンジニアにエージェント作成を依頼する、という流れで、まず Foundry リソースを作成する（音声認識では「founder resource」）。
2. リージョンを選び、connected resources で監視機能や Key Vault を追加する。
3. **agent hosting** の項目で、Foundry managed compute だけでなく **AKS compute** も選べる。新しいエージェントごとに、デプロイ先として AKS を選べる。
4. ストレージを構成し、クラスター全体で動作できる ID を設定する。独自の ID を持ち込むことも、システム割り当てにすることもできる。
5. 作成すると、エージェント用のクラスターがあらかじめ接続された Foundry リソースができる。

### 6.3 Foundry ポータルでクラスターを追加し、モデルをデプロイする

1. Foundry ポータルに戻り、**compute clusters → add cluster** でクラスターを追加できる。作成時に追加したエージェント用クラスターが見える。推論クラスターや学習クラスターも追加できる。
2. 2 つ目として、**West US の推論クラスター**を接続する。以降、どちらのクラスターにもデプロイできる。
3. 通常の Foundry のワークフローで、オープンウェイトモデルを選ぶ（音声認識では「Lama 3.37DB instruct」と聞こえます。後の説明では「Llama 70B」とも言っています）。
4. コンピュートタイプで **AKS** を選び、先ほど接続した推論クラスターを選ぶ。
5. Foundry と AKS の間で、適切な GPU とレプリカの選択が行われる。**オートスケール**、**モデルストリーミング**（サービングと推論を高速化）、**イメージキャッシュ**と**イメージストリーミング**（モデルを含むコンテナの取得が「数分から数秒」になる）といった機能があり、これらは自分で設定する必要がない。
6. **Deploy** をクリックするだけ。

### 6.4 モデルを自社データで学習する

1. ベースの Llama 70B だけでは、工場の問題の解決成功率が高くなく、適切なコンテキストが無い、と説明される。そのためクラスター上で、自社データを追加して学習できる。
2. 学習には時間がかかるため、ここでは Caldova 固有のデータで**学習済みのモデル**を使う。学習率と失敗ケースが時間とともに下がるグラフが示される。失敗ケースの改善は「たしか 70%」と述べられている。
3. 学習・チューニングしたモデルも、同じ流れでクラスターを選んでデプロイする。

### 6.5 AKS 側（AI Manager 画面）の確認

1. 新しい **AI Manager** 画面（ポータル）で、ベースモデルと学習済みモデルのデプロイと、使っている GPU を確認できる。
2. この画面からもデプロイできる。

### 6.6 FlexNodes でモデルを工場内で動かす

1. Caldova は 4 つの工場で、ラインを CCTV で記録している。映像は機器の物理的な異常や、製造した薬の品質の確認に使いたいが、技術面とコンプライアンス面の理由で、画像や情報をクラウドに送りたくない。
2. そこで **FlexNodes** を使う。9 月に AKS で発表されたもので、Satya も今朝触れたと説明されている。**どこにあるマシンでも AKS クラスターに接続できる**。Foundry と AKS の統合により、そのマシンへのモデルのデプロイもできる。
3. 画像からテキストを生成するモデルとして **QEN3VL**（音声認識上の表記）を選ぶ。工場内で画像を処理し、エージェントはクラウドからそのモデルのエンドポイントに問い合わせる。画像やデータはクラウドに行かない。
4. デプロイ先として、このモデルが載る **A100**、または Flex を選べる。工場にある機器としては **NVIDIA Jetson AGX**（音声認識では「AGX store」）を使う。これは、Redmond のデスクにあった実機だと説明されている。
5. デプロイを実行する。このノードは Azure が構築したものではなく、Azure のコアではなく工場で動いている。Azure 側では、AKS でこのノードを管理するための**管理料金**がかかる。
6. デプロイ後、ほかの Azure ノードと同様にノードを調べられ、モデルの認証情報も確認できる。エージェントがモデルにアクセスするために、API キーや静的トークンは使わない。**Microsoft Entra ID と ID を使った、短命なトークン**で保護される。
7. エージェントには、学習済み Llama（音声認識では「30B」と聞こえます）と、視覚モデル（音声では「Quen vision model」。先に選んだ QEN3VL のことです）の 2 つのモデルが使えるようになる。
8. クラスターには、system ノードプール、GPU ノードプール、学習用ノードプール、エッジノードがある。学習していない間はオートスケールで 0 になっているプールもあり、サービング用プールと、最後に Flex ノードがモデルを提供している。

### 6.7 可観測性とコスト

1. Foundry からは、メトリクスや学習結果を確認できる。
2. インフラ側では、レイテンシ、インフラの状態、クラスターメトリクス、ノードの状態、**GPU 使用率、GPU パフォーマンス、メモリ使用率、効率**を見られる。
3. プラットフォームエンジニアと AI エンジニアが協力して、モデルのチューニング、GPU の選択、reserved instances を最適化できる。
4. 画面には、平均レイテンシ、平均スループット、パフォーマンスモード（この例では「fully balanced」だが、設定できる）が表示される。
5. コストは、クラスター全体のほか、リソースごとに内訳を見られる。例えば GPU ベースのプールでは、ベースモデルと調整済みモデルのサービングにそれぞれいくらかかるかが分かる。予測可能なコストとして管理できる、という説明。

### 6.8 エージェントのデプロイ（VS Code）

1. ビジネスゴールは、トラブルシューティングを高速化するエージェント。**調査エージェント（investigation agent）** を作る。命令（instructions）が用意されている。
2. Python ベースで、ツールを持つ。モデルの呼び出し（特に画像の処理依頼）や、機器マニュアルを提供する API など、社内システムへのアクセスがある。
3. **VS Code から Foundry へのデプロイフロー**を使う。ここで見せるものに新規の機能は無いが、新しい部分もある、と断ったうえで進める。サブスクリプションとプロジェクト名を選ぶ（標準的な手順）。エージェントと言語を選ぶ。Foundry のワークスペースにデプロイする。
4. このワークスペースは AKS クラスターに接続されているので、エージェントは自動的に AKS クラスターにデプロイされる。Foundry でホステッドエージェントを開くと、ホスティングターゲットが AKS クラスターになっている。
5. 単純な pod ではなく、**サンドボックス**としてデプロイされる。エージェントは専用の **micro VM** の中で動き、さまざまなセキュリティポリシーとネットワークセキュリティポリシーが適用されている。内容を確認でき、Kubernetes のアプリケーションと同様に、独自のポリシーを追加することもできる。
6. トラブルシューティングの体験について、以前は何時間もかかっていたが、ボタンを押すだけで「4 分」まで短縮した、と述べられている（この「4 分」が何の所要時間かは、発話からは細かく分かりません）。
7. エージェントが何をしたかを確認できる。ワークフローを展開すると、工場のローカルビジョンから得た画像が見え、ロットの表示に問題があることが分かる。センサー（温度）で何が起きたか、そのラインで何が問題だったかが見える。
8. Foundry の**トレース**で、エージェントの行動のタイムライン全体を確認できる。

### 6.9 Agent Grid によるネットワーク制御

1. トレースで、エージェントが**特定のリモート URL へのアクセスを自動的に拒否された**ことが分かる。エージェントには社内データ・社内 API だけにアクセスさせたい。エージェントは、サプライヤーにエラーコードの追加情報を問い合わせようとしていたが、データ流出（exfiltration）を許せないため、拒否された。
2. この制御は、AKS のエージェントトラフィックを制御するネットワークポリシーのトラフィック制御「**Agent Grid**」が自動で行った。
3. Azure ポータルで Agent Grid を開くと、ポリシーの一覧（allow maintenance、allow telemetry など、明示的に許可しているもの）が見える。Foundry で見た拒否の記録が、ここでもライブで確認できる。
4. エージェントの呼び出しとさまざまな API をグラフで表示できる。社内向けの records や tracing の呼び出しがあり、赤く表示された 1 本が、先ほどブロックされた support 宛ての呼び出し。
5. Agent Grid では、FQDN によるフィルタリングだけでなく、特定の **MCP 呼び出しの許可・拒否**、特定の **MCP サーバーの検出**もできる。ここでは AKS にデプロイしたアプリケーションからの 2 つの MCP サーバー（maintenance と inventory）がある。
6. maintenance の MCP を、エージェントから「get」に限って呼び出せるように許可する。これでより効率的な新しい MCP サーバーが使える。
7. AKS の他の機能も、そのまま使える。例えば、デプロイを許可するイメージを制御するポリシーが、同じように動く。

### 6.10 規制変更への対応：オンプレミスへの移行

1. Caldova で規制が変わり、このアプリケーションをオンプレミス環境に戻さなければならなくなった、という想定。
2. 本来は難しい移行だが、アプリケーションがすでに Foundry と AKS で動いているので簡単だと述べられている。
3. 工場にあるハードウェアに、ノード 1 つを接続するのではなく、**完全なクラスター**をデプロイする。plant 2 のハードウェアを選び、バージョンを選ぶ。Ubuntu 上で動く。作成すると、エッジの工場内で AKS クラスターが動く。
4. Copilot に「アプリケーションを完全にこのクラスターに持ってくるには何が必要か」と尋ねる。Copilot の回答は、クラウドの AKS とエッジの違いは大きくなく、マニフェストにごく小さな違いがあるだけ、というもの。
5. 必要な変更を画面上で確認して適用し、残すと決めたら、PR を作って Git リポジトリに出す。
6. **GitOps** のワークフローで、2 つのクラスターに同期する。クラウドにあったアプリケーションのレプリカがオンプレミスにできる。
7. アプリケーションを開くと、最上部に **plant 2** が表示される。

Jorge は、所要時間は「たしか 15 分ほど」と述べ、AKS 上のモデルのデプロイ、チューニング（学習時間は省略）、エージェントのデプロイ、両者の接続、ポリシーのデプロイ、工場内へのモデルのデプロイ、オンプレミスへのアプリケーションの移行を行った、とまとめています。デモ全体の要素として、Flex nodes での視覚推論、ベアメタルへの移行、Agent Grid による FQDN と MCP サーバーのアクセス制御が挙げられました。

## 7. 注意点・発表者の気付き

- **本番の AI アプリケーションは複雑**：Helm chart だけでは途中までしか進めず、考えることが多い（Brendan）。この複雑さを下げることが、取り組みの目的です。
- **最小権限から始める**：エージェント的なシステムでは、すべてを許可して例外を拒否するのではなく、何もできない状態から明示的に許可を足す方式を、2 人とも強く勧めています。エージェントがサンドボックスから抜け出した事例は、「すべてを許可して、ブロックし損ねた」形が多い、という指摘です。
- **API 経由の迂回（プロキシ化）の懸念**：許可した API をエージェントが他のものへの経路にしてしまうことが心配で、全員が考えている課題だと、Q&A の中で述べられています。
- **GPU が高コストの中心**：推論で GPU を使うほどコストは急に膨らむ、という質問者の指摘に対して、短期間なら Foundry managed compute、継続的に使うなら自前 GPU、という使い分けが示されました。
- **画像をテキストにすることの意味**：コストとプライバシーの面で利点がある一方、ピクセルが重要かどうかによっては情報の抽象化になる点が、Q&A で議論されました。
- **FlexNodes の課金**：Azure のコアで動くのではなく、AKS でノードを管理するための管理料金がかかります（Jorge）。金額は発表では示されていません。
- **発表では示されていないこと**：AKS AI Manager の提供状況（GA かプレビューか）、価格、対応モデルの完全な一覧、サポートされる GPU の一覧などは、このセッションでは語られていません。

## 8. 利用者にとっての利点

発表で語られた利点は次のとおりです。

- **既存の AKS 基盤を活かせる**：審査済み・コンプライアンス適合済みのインフラのまま、AI やエージェントを展開できる（Jorge、Caldova の前提）。
- **操作の簡単さ**：10 個の Helm chart を自分で入れる必要がなく、Foundry の API と UI から AKS にモデルをデプロイできる。
- **起動の速さ**：イメージキャッシュとイメージストリーミングで、モデルを含むコンテナの取得が「分から秒へ」。
- **データを工場内にとどめられる**：FlexNodes で、画像をクラウドに送らずに工場内でモデルを動かせる。
- **セキュリティ**：Entra ID と短命なトークン（API キーや静的トークンを使わない）、micro VM のサンドボックス、Agent Grid による FQDN と MCP のアクセス制御。
- **可観測性とコストの見通し**：GPU 使用率などのインフラ指標と、リソースごとのコストを確認できる。
- **移植性**：同じアプリケーションを、マニフェストの小さな変更と GitOps で、クラウドの AKS からオンプレミスのクラスターに展開できる。
- **デモで示された効果**：トラブルシューティングが、以前の数時間から、ボタンを押して「4 分」に短縮（デモ内の説明）。デモ全体の所要時間は約 15 分。

> 補足：デモの数値（70% の改善、4 分、15 分）は、架空の会社 Caldova を題材にしたデモの中での説明であり、実際の顧客事例の成果ではありません。

## 9. まとめ

このセッションは、Foundry と AKS を **AKS AI Manager for Foundry** でつなぎ、「イージーボタンから自社インフラのオープンウェイトモデルまで」を一続きにする発表でした。Brendan は、エージェントが新しい種類のワークロードであり、その基盤が Kubernetes になっている背景を説明しました。

Jorge は、架空の製薬会社のシナリオで、次のことを一通り見せました。

1. Foundry から AKS へのモデルのデプロイと、自社データでの学習
2. FlexNodes による工場内でのモデル実行（画像がクラウドに行かない）
3. AKS 上でのホステッドエージェントのサンドボックス実行と、Agent Grid による通信制御
4. GitOps によるオンプレミスへの展開

質疑応答では、コスト管理には Agent 365、OpenTelemetry、Foundry managed compute との使い分けが挙げられ、セキュリティでは「最小権限から始めて明示的に許可する」ことが強く勧められました。
